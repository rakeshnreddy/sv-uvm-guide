## Quick Take
- **What it is:** An **interface** is a bundle of signals that connects modules together. A **modport** (module port) defines the direction of those signals from one module's point of view (e.g., master vs. slave).
- **Why it matters:** Interfaces replace error-prone, wire-by-wire connections with a single handle. Modports state what each connected module may do: a module on the `monitor` view cannot drive the bus.
- **The Analogy:** An interface is like a USB cable: it bundles power, ground, and data lines. The modport is the connector type (Type-A vs. Type-B) that ensures you plug it in correctly.

module master_driver (simple_bus_if.master bus, input logic rst_n);

## Key Concepts

### Interfaces (LRM Clause 25)
An `interface` is a named bundle of nets and variables. It can also contain:
- **Tasks and Functions:** To encapsulate bus protocols (e.g., `read()`, `write()`).
- **Assertions:** To verify protocol compliance directly on the bus.
- **Parameters:** To make the interface reusable (e.g., `ADDR_WIDTH`).
- **Clocking blocks:** To give testbench code race-free timing (F4C).

### Modports (LRM Clause 25.5)
`modport` lists provide directional views of the interface signals, declared "as if inside the module" that uses them (§25.5).
- **Safety:** A module can only do what its view allows: through the `monitor` view nothing can be driven, and names not listed in a modport are not reachable through that port.
- **Limits:** A modport does not stop two modules that both use the `master` view from driving the same signal, and a hierarchical reference such as `tb_top.bus_if.ready` bypasses modports entirely.
- **Clocking modports:** A modport can list a clocking block, for example `modport drv (clocking cb);` (§25.5.5). A module using it can reach the signals only through `cb`, with the clocking block's sample and drive timing.
- **Clarity:** The modport documents the intent of each connection.

## The Bridge to Classes: Virtual Interfaces
_How dynamic objects talk to static hardware._

In modern verification (UVM), your testbench drivers are **classes** (objects created at run time). Your DUT and interfaces are **modules and interface instances**, built at elaboration before time 0. A class cannot contain an interface instance.

Enter the **virtual interface**: a variable that holds a handle to a real interface instance (§25.9).

- **Static world:** `tb_top` instantiates `simple_bus_if bus_if`, and the DUT connects to it through a port.
- **Dynamic world:** the driver object holds `virtual simple_bus_if.drv vif`, a handle that starts as `null`.
- **The bridge:** someone must copy `bus_if` into `vif` before the driver uses it. Forget that step and the first `vif.cb...` access is a **fatal run-time error** (§25.9).

First, give the interface a clocking block and a synchronous modport for the driver (F4C explains the timing):

```systemverilog
// Added inside simple_bus_if
clocking cb @(posedge clk);
  default input #1step output #0;
  output addr, data, rw, valid;
  input  ready;
endclocking

modport drv (clocking cb);   // the driver sees only cb (§25.5.5)
```

Then the driver class drives through the handle, and `tb_top` binds the handle to the real instance:

```systemverilog
class bus_driver;
  virtual simple_bus_if.drv vif;     // 1. a handle: null until assigned

  task drive(logic [31:0] a);
    @(vif.cb);                       // 2. wait for the clocking event
    vif.cb.addr  <= a;               // 3. drive through the clocking block
    vif.cb.valid <= 1'b1;            //    (VALID does not wait for READY)
    do @(vif.cb); while (!vif.cb.ready);  // hold VALID until READY is sampled high
    vif.cb.valid <= 1'b0;
  endtask
endclass

module tb_top;
  logic clk = 0, rst_n = 0;
  always #5 clk = ~clk;

  simple_bus_if bus_if (.clk(clk));                    // the real interface instance
  slave_dut     dut    (.bus(bus_if.slave), .rst_n(rst_n));

  bus_driver drv;
  initial begin
    drv = new();
    drv.vif = bus_if;   // 4. bind the handle: an instance may be assigned to a modport-typed virtual interface
    #12 rst_n = 1;
    drv.drive(32'h1000);
  end
endmodule
```

In UVM you do step 4 through the configuration database instead of a direct assignment, because the test, not `tb_top`, creates the driver. The type parameter must be identical in `set` and `get`:

```systemverilog
// tb_top
initial uvm_config_db#(virtual simple_bus_if)::set(null, "uvm_test_top.*", "vif", bus_if);

// driver's build_phase (the driver declares: virtual simple_bus_if vif;)
if (!uvm_config_db#(virtual simple_bus_if)::get(this, "", "vif", vif))
  `uvm_fatal("NOVIF", "virtual interface was not set for this driver")
```

The `uvm_fatal` check turns a missing `set` into a clear message at build time, instead of a null-handle fatal later in `run_phase`.

## Make It Work
1.  **Define the Signals:** List all wires in the interface.
2.  **Define Modports:** Create a modport for each type of component that connects to the interface (Master, Slave, Monitor), plus a clocking modport for class-based drivers.
3.  **Instantiate:** Create an instance of the interface in your top-level testbench.
4.  **Connect:** Pass the interface instance to the module ports. Use the modport name in the module definition: `module m (my_if.master ifc);`.
5.  **Bind the virtual interface:** Assign `vif` (or `uvm_config_db` set/get) before any class touches it. A null `vif` is a fatal run-time error.
6.  **Never wait for READY before raising VALID.** One side must move first, and in ready/valid protocols that is always the sender.
