## Quick Take

- **What it is:** An **expression** combines operands with operators to produce a value. Beyond the C operator set, SystemVerilog has 4-state equality (`===`, `==?`), set membership (`inside`), reduction operators, concatenation and replication, arithmetic shifts, and **streaming operators** that pack and unpack bits in a chosen order (IEEE 1800-2023 Clause 11).
- **Why it matters:** Checkers, reference models and monitors are built from expressions. Most expression bugs compile cleanly and print a plausible number: a sum that lost its carry, a negative value treated as a huge positive one, a precedence surprise, bytes in the wrong order, or an `x` that a comparison quietly turned into "not equal". Predicting the result before the simulator does is the skill this lesson builds.
- **The Analogy:** Evaluating an expression is like a kitchen where each recipe uses one bowl size. The chef picks the bowl from the largest ingredient and from the serving dish (the **context**), pours every ingredient into that bowl, cooks, and serves into the dish, spilling whatever does not fit. Precedence is the order of the steps on the recipe card. *Where it breaks:* some ingredients are always prepared in their own small bowl, whatever the recipe (self-determined operands such as concatenation members and shift amounts), and this kitchen stocks an "unknown" ingredient, `x`, with rules of its own.

2. Calculate the width and signedness of an expression from its operands and its context, and predict the value stored after extension or truncation.

## Build Your Mental Model

### The operator families at a glance

An **operator** acts on **operands**; together they form an expression, and every expression has a width (a number of bits), a signedness, and a value that may contain `x` or `z`. This table is the map for the rest of the lesson. You will meet each row again with its rules and a picture.

| Family | Operators | Result width | With `x` or `z` in an operand | Clause |
|---|---|---|---|---|
| Arithmetic | `+ - * / % **` | the context width | the whole result is `x`; dividing by 0 also gives `x` | §11.4.3 |
| Relational | `< <= > >=` | 1 bit | `x` | §11.4.4 |
| Logical equality | `== !=` | 1 bit | `x` only when the answer is ambiguous | §11.4.5 |
| Case equality | `=== !==` | 1 bit | never `x`: `x` and `z` are compared as values | §11.4.5 |
| Wildcard equality | `==? !=?` | 1 bit | `x`/`z` in the right operand match anything | §11.4.6 |
| Logical | `&& \|\| ! -> <->` | 1 bit | `x` when a truth value is ambiguous | §11.4.7 |
| Bitwise | `& \| ^ ~^ ~` | the context width | bit by bit; a 0 still decides `&`, a 1 still decides `\|` | §11.4.8 |
| Reduction (unary) | `& ~& \| ~\| ^ ~^` | 1 bit | folds all bits with the bitwise tables | §11.4.9 |
| Shift | `<< >> <<< >>>` | the left operand's width, in context | an `x`/`z` shift amount gives all `x` | §11.4.10 |
| Conditional | `c ? a : b` | the wider of `a` and `b` | an `x` condition merges both branches bit by bit | §11.4.11 |
| Concatenation, replication | `{a, b}`, `{n{a}}` | the sum of the operand widths | bits are copied | §11.4.12 |
| Set membership | `inside` | 1 bit | members compared with `==?` | §11.4.13 |
| Streaming | `{<< n {…}}`, `{>> {…}}` | the width of the stream | bits are copied | §11.4.14 |

### Precedence and associativity: how the compiler groups what you wrote

**Precedence** decides which operator takes its operands first when an expression has no parentheses; **associativity** decides the grouping among operators of the same precedence. Table 11-2 of the standard, highest precedence first (§11.3.2); the standard's table has no numbers, so the rank column is this lesson's, for reference:

| Rank | Operators | Associativity |
|---|---|---|
| 1 | `()` `[]` `::` `.` | left |
| 2 | unary `+ - ! ~ & ~& \| ~\| ^ ~^ ^~ ++ --` | — |
| 3 | `**` | left |
| 4 | `* / %` | left |
| 5 | binary `+ -` | left |
| 6 | `<< >> <<< >>>` | left |
| 7 | `< <= > >= inside dist` | left |
| 8 | `== != === !== ==? !=?` | left |
| 9 | binary `&` | left |
| 10 | binary `^ ~^ ^~` | left |
| 11 | binary `\|` | left |
| 12 | `&&` | left |
| 13 | `\|\|` | left |
| 14 | `?:` | right |
| 15 | `-> <->` | right |
| 16 | assignment operators `= += -= <<= …` | none |
| 17 | concatenation `{}` `{{}}` | lowest |

All operators group left to right except `?:`, `->` and `<->`, which group right to left (§11.3.2). The groupings that cause real bugs:

- `flags & mask == 0` means `flags & (mask == 0)`. Equality binds tighter than the binary `&`, `^` and `|`: in Table 11-2 the equality row sits above the three binary bitwise rows, as in C.
- `x << 1 + y` means `x << (1 + y)`: addition binds tighter than shifts.
- `!a == b` means `(!a) == b`: unary operators bind tightest.
- `a < b < c` means `(a < b) < c`, which compares a 1-bit result with `c`.
- `a || b && c` means `a || (b && c)`.
- `s ? x : t ? y : z` means `s ? x : (t ? y : z)`: a right-associative priority chain.

- A **bitwise** operator (`&`, `|`, `^`, `~^`, `~`) works bit by bit and returns a vector. A **controlling value** decides a bit even next to an `x`: `0 & x` is 0 and `1 | x` is 1. Without one the bit is `x`, and `^` with any `x` or `z` input is always `x` (§11.4.8, Tables 11-11 to 11-15).
- A **reduction** operator is the unary form: `&a`, `|a`, `^a` and their inverted versions `~&a`, `~|a`, `~^a` fold all the bits of one operand into 1 bit, using the same tables (§11.4.9).
- A **logical** operator (`&&`, `||`, `!`) first turns each operand into a **truth value**: true if it has a known 1 bit, false if every bit is 0, and ambiguous (`x`) otherwise. It is the same test `if` applies, `operand != 0` (§11.4.7, §12.4). The result is 1 bit.

Traced on `a = 4'b1x10` and `b = 4'b0000`:

| Expression | Result | Why |
|---|---|---|
| `a & b` | `4'b0000` | 0 controls AND in every bit |
| `a \| b` | `4'b1x10` | 0 is neutral for OR, so the `x` survives |
| `&a` | `1'b0` | bit 0 is 0, and one 0 decides AND |
| `\|a` | `1'b1` | one known 1 decides OR |
| `^a` | `1'bx` | parity needs every bit |
| `a && b` | `1'b0` | `b` is false, so `&&` is false whatever `a` is |
| `a \|\| b` | `1'b1` | `a` has a known 1, so it is true |
| `!a` | `1'b0` | `a` is true |
| `a + 4'd1` | `4'bxxxx` | arithmetic: any `x` bit makes the whole result `x` (§11.4.3) |

Two mistakes everyone makes once, bits against truth value:

| Expression | Result bits | What an `if` sees |
|---|---|---|
| `4'b0100 & 4'b0010` | `4'b0000` | false: no bit is 1 |
| `4'b0100 && 4'b0010` | `1'b1` | true: both operands are non-zero |
| `~4'b0001` | `4'b1110` | true: a known 1 bit remains |
| `!4'b0001` | `1'b0` | false |

- **`&` for `&&`.** Use `&&` to combine conditions: `&` between two true conditions can make them false.
- **`~` for `!`.** Use `!` to negate a condition: `~` on a condition usually leaves it true.

- `&a` is `x` for `4'b1x11`: no bit is 0, and the `x` could be either value. As soon as one bit is 0 the answer is a definite 0.
- `|a` is 1 because one known 1 decides OR, and `^a` is `x` because parity depends on every bit.
- In the Logical family, `a = 4'b0x00` has no known 1 bit and one unknown bit, so its truth value is `x`. With `b = 0`, `a && b` is 0 (false decides AND) and `a || b` is `x`.

In a testbench, reduction operators compute parity (`^data`), "any bit set" (`|irq_vec`) and "all ones" (`&mask`). To ask "does this value contain `x` or `z`?", use `$isunknown(v)` (§20.9): it says what it means.

### Equality: `==`, `===` and the wildcard `==?`

The module index introduced these operators ([F2A: Core Data Types](/curriculum/T1_Foundational/F2A_Core_Data_Types/index)). This section gives the complete rules and the two details that still catch experienced engineers: wildcards work in one direction only, and operands of different widths are extended first. There are three pairs of equality operators, and they differ only in how they treat `x` and `z`:

- **`==` and `!=`** compare bit by bit. If a known bit differs, the answer is a definite 0 (or 1 for `!=`). If no known bit differs but an `x` or `z` makes the relation ambiguous, the answer is `x` (§11.4.5).
- **`===` and `!==`** compare `x` and `z` as values, like the `case` statement, and always return 0 or 1 (§11.4.5).
- **`==?` and `!=?`** treat `x` and `z` bits **in the right operand** as wildcards that match any value. `x` and `z` in the left operand are not wildcards, so they can still make the result `x` (§11.4.6).

If the operands differ in width, the narrower one is zero-extended, or sign-extended when both are signed (§11.4.5). Traced on `a = 4'b1x10`:

| Expression | Result | Why |
|---|---|---|
| `a == 4'b1x10` | `x` | bit 2 is `x` on both sides: ambiguous |
| `a == 4'b0x10` | `0` | bit 3 is a known mismatch, which decides |
| `a === 4'b1x10` | `1` | `x` matches `x` as a value |
| `a !== 4'b1010` | `1` | `x` is not 0 |
| `4'b1010 ==? a` | `1` | `a` is now the right operand, so its `x` is a wildcard |
| `a ==? 4'b1010` | `x` | the `x` is in the left operand: not a wildcard |
| `a ==? 4'b1??0` | `1` | `?` means `z`; both `?` bits are wildcards |


### Set membership: `inside` and `case inside`

**`inside`** asks whether a value belongs to a set (§11.4.13):

- The set is a list of values, ranges written `[lo:hi]` (inclusive; `$` stands for the smallest or largest value of the left operand's type), and unpacked arrays, which contribute every element.
- For integral values each member is compared with `==?`, so `x` and `z` bits **in a member** are wildcards, and `x` and `z` in the value on the left are not.
- The result is the OR of all the comparisons: 1 if any member matches, 0 if none does, and `x` if none matches but at least one comparison was `x`.
- Non-integral values, such as strings, are compared with `==`.

```systemverilog
// snippet: the assignments run inside an initial block
logic [7:0] addr;
logic [2:0] op;
bit         legal, is_rw;

legal = addr inside {[8'h00:8'h3F], 8'h80, [8'hF0:$]};  // two ranges and one value
is_rw = op inside {3'b00?};                             // matches 3'b000 and 3'b001
```

**`case inside`** is the statement form (§12.5.4). Each case item is a list of values and ranges, and the case expression is compared with each item using `inside`. An item matches only when `inside` returns 1; an `x` result counts as no match. As in every `case`, the first matching item wins.

```systemverilog
// snippet
typedef enum {NOP, RW, ALU, JUMP, ILLEGAL} cls_e;
cls_e cls;

always_comb begin
  case (op) inside
    3'b000:          cls = NOP;
    3'b001, 3'b010:  cls = RW;
    [3'b100:3'b110]: cls = ALU;
    3'b11?:          cls = JUMP;     // 3'b110 already matched ALU: first match wins
    default:         cls = ILLEGAL;  // 3'b011, and x/z values that no item matches
  endcase
end
```

`case inside` treats `x` and `z` as wildcards only in the items, never in the case expression. That makes it the safer replacement for `casez` and `casex`, which ignore `z` bits (`casez`) or `x` and `z` bits (`casex`) in the case expression as well as in the items (§12.5.1). [Procedural Flow Control](/curriculum/T1_Foundational/F2C_Procedural_Code_and_Flow_Control/flow-control) covers `case`, `casez`, `casex`, `unique` and `priority`.

The same corrupted opcode through the four case forms. The three plain forms are shown with the decoder's plain items, because a range item such as `[3'b100:3'b110]` exists only in `case inside`:

| Statement | `x`/`z` wildcards apply to | `op = 3'b0x0` against the first item, `3'b000` | Branch taken |
|---|---|---|---|
| `case` | nothing: every bit must match exactly, `x` and `z` included (§12.5) | bit 1 is `x` against 0: no match | `default`, `ILLEGAL` |
| `casez` | `z` and `?` bits in the case expression and in the items (§12.5.1) | bit 1 is `x`, not `z`, so it still counts: no match | `default`, `ILLEGAL` |
| `casex` | `x` and `z` bits in the case expression and in the items (§12.5.1) | bit 1 is skipped: match | `NOP`: a corrupted opcode runs a real branch |
| `case inside` | `x`, `z` and `?` bits in the items only (§12.5.4) | `3'b0x0 ==? 3'b000` is `x`, which is no match | `default`, `ILLEGAL` |

### Expression width: context-determined and self-determined operands

The module index walked through the five steps the simulator uses to size an assignment, with the 200 + 100 example ([F2A: Core Data Types](/curriculum/T1_Foundational/F2A_Core_Data_Types/index)). In short: the expression is evaluated at the width of its widest **context-determined** operand, **including the assignment target**; every such operand is extended to that width before any operator runs; and the result is truncated or extended into the target (§11.6, §11.8.2, §10.7). This section adds what the short version leaves out: which operands take part in that context, and which do not.

- An operand is **context-determined** when its width depends on the expression around it: the operands of `+ - * / % & | ^ ~^`, unary `+ - ~`, both branches of `?:`, the left operand of a shift, and the right-hand side of an assignment.
- An operand is **self-determined** when its width depends only on itself: a shift amount, the exponent of `**`, every member of a concatenation, the condition of `?:`, and the operands of `&&`, `||` and the reduction operators. The context stops at these operands.
- The operands of a comparison (`== != === !== < <= > >=`) form a context of their own. They are sized against each other, never against the rest of the expression, and the result is 1 bit (§11.8.2).

The width rules of Table 11-21 (§11.6.1), where `L(i)` is the width of operand `i`:

| Expression | Result width | Operands |
|---|---|---|
| unsized constant, such as `12` or `'hFF` | at least 32 bits | — |
| sized constant, such as `8'd200` | as written | — |
| `i + j`, and likewise `- * / % & \| ^ ^~ ~^` | max(L(i), L(j)) | context-determined |
| unary `+i`, `-i`, `~i` | L(i) | context-determined |
| `i == j`, and `!= === !== > >= < <=` | 1 bit | sized to max(L(i), L(j)) against each other |
| `i && j`, `i \|\| j`, `->`, `<->` | 1 bit | self-determined |
| unary `&i`, `~&i`, `\|i`, `~\|i`, `^i`, `~^i`, `!i` | 1 bit | self-determined |
| `i << j`, and `>> <<< >>> **` | L(i) | `j` is self-determined |
| `i ? j : k` | max(L(j), L(k)) | `i` is self-determined |
| `{i, …, j}` | L(i) + … + L(j) | self-determined |
| `{i{j, …, k}}` | i × (L(j) + … + L(k)) | self-determined |

### Signedness: one unsigned operand makes the expression unsigned

The sign of an expression decides how its operands are extended and how comparisons and divisions behave. The module index showed the headline case, a signed plus an unsigned operand giving 22 instead of 6. The complete rules (§11.8.1):

- The sign of an expression depends **only on its operands**, never on the target.
- Simple decimal numbers such as `12` and `-4` are signed. Based numbers such as `8'd12` and `'hFF` are unsigned unless written with `s`, as in `4'sd12`.
- Bit-selects, part-selects (even of the whole vector), concatenations, and the results of comparison and reduction operators are unsigned.
- If any context-determined operand is unsigned, the whole expression is unsigned. Only when all of them are signed is the expression signed.
- Operands are sign-extended only when the expression is signed (§11.8.2).

### Concatenation and replication

A **concatenation** `{a, b, c}` joins its operands into one vector, the first operand in the most significant bits (§11.4.12). Each operand keeps its own width (self-determined), and the result is unsigned. A **replication** `{n{a}}` repeats a concatenation `n` times; `n` must be a non-negative constant without `x` or `z` bits (§11.4.12.1).

```systemverilog
// snippet: the assignments run inside an initial block
logic [7:0]  hi = 8'h12, lo = 8'h34;
logic [15:0] word;
logic [31:0] fill;
logic [3:0]  n = 4'b1010;     // -6 as a signed 4-bit number
logic [7:0]  b;

word     = {hi, lo};          // 16'h1234: hi lands in the MSBs
{hi, lo} = 16'hBEEF;          // a concatenation as a target: hi = 8'hBE, lo = 8'hEF
fill     = {4{8'hA5}};        // 32'hA5A5_A5A5
b        = {{4{n[3]}}, n};    // sign-extend by hand: 8'hFA, still -6
```

| Statement | Result |
|---|---|
| `word = {hi, lo};` | `16'h1234` |
| `{hi, lo} = 16'hBEEF;` | `hi = 8'hBE`, `lo = 8'hEF` |
| `fill = {4{8'hA5}};` | `32'hA5A5_A5A5` |
| `b = {{4{n[3]}}, n};` | `8'hFA` |
| `word = {hi, 1};` | compile error: unsized constants are not allowed in a concatenation |

Rules worth remembering:
- **No unsized constants inside.** `{hi, 1}` is illegal because `1` has no defined width; write `{hi, 1'b1}` (§11.4.12).
- **A concatenation can be a target**, as in `{carry, sum} = a + b;`. A replication cannot, and it cannot connect to an output or inout port (§11.4.12.1).
- **A zero replication** `{0{a}}` is allowed only inside a concatenation that has at least one operand of positive width, which is useful in parameterized code (§11.4.12.1).
- **`{}` is not `'{}`.** Braces with an apostrophe are an assignment pattern, which builds structs and arrays member by member (§11.4.12, §10.9).

- `{a, 1}` is rejected: an unsized constant has no width to concatenate (§11.4.12).

### Shifts: logical versus arithmetic

There are two kinds of shift (§11.4.10):

- **Logical shifts** `<<` and `>>` fill the vacated bits with 0.
- **Arithmetic shifts**: `<<<` is identical to `<<`, while `>>>` fills with copies of the sign bit **only when the result type is signed**. In an unsigned expression it fills with 0, just like `>>`.
- The shift amount is self-determined and always treated as unsigned. If it contains `x` or `z`, every bit of the result is `x`. The result has the width of the left operand, extended to the context.

Traced with `logic signed [7:0] s = -8;` (`8'hF8`), `logic [7:0] u8 = 8'hF8;` and 8-bit targets:

| Expression | Result | Why |
|---|---|---|
| `s >>> 1` | `8'hFC` (−4) | signed: the sign bit is copied in |
| `s >> 1` | `8'h7C` (124) | logical: 0 is shifted in |
| `u8 >>> 1` | `8'h7C` | unsigned, so `>>>` fills with 0 |
| `s << 1` | `8'hF0` | left shifts always fill with 0 |
| `s >> k`, with `k = 2'bx1` | `8'hxx` | an unknown shift amount makes the whole result unknown |

The explorer starts on the shift family with a signed `a = 4'b1000` (−8) and `n = 1`. Choose `a >>> n` and **predict** the result, then clear the "declare a as logic signed" box and predict it again. Try `a >> n` and `a << n` the same way.

<OperatorExplorer family="shift" />

What the explorer showed: with `a` signed, `a >>> n` is `4'b1100`, because the sign bit fills the vacated position. Unsigned, the same operator gives `4'b0100`. Nothing in the operator changed, only the type of the expression. The marked bits show which positions were vacated and how they were filled.

### Streaming operators: pack and unpack in a chosen order

A **streaming concatenation** turns data into a **stream** of bits and can reorder it on the way (§11.4.14):

1. **Pack:** the operands are concatenated into one stream, left operand first. A packed value contributes its bits; a struct contributes its members in declaration order; an unpacked array contributes its elements in order (§11.4.14.1).
2. **Reorder:** `{>> {…}}` streams left to right and never reorders; any slice size is ignored. `{<< n {…}}` cuts the stream into **slices** of `n` bits, starting from the right (least significant) end, and reverses the order of the slices. Bits inside a slice keep their order. The slice size defaults to 1, which reverses every bit, and may be a type such as `byte` (§11.4.14.2).

The last two lines of the next snippet use a **queue**, declared `q[$]`: an ordered list of elements, numbered from 0, that grows and shrinks while the simulation runs. Its method `q.size()` returns the number of elements. Queues are taught in [F2B: Dynamic Data Structures](/curriculum/T1_Foundational/F2B_Dynamic_Structures/index); here it is enough to know that a queue target is resized to hold what is assigned to it.

```systemverilog
// snippet: the assignments run inside an initial block
logic [31:0]  w = 32'h1234_5678, r;
byte unsigned q[$];

r = {<< 8 {w}};      // 32'h7856_3412: byte swap (endianness change)
r = {<< 4 {w}};      // 32'h8765_4321: nibble order reversed
r = {<< {w}};        // 32'h1E6A_2C48: every bit reversed (slice size 1)
r = {>> 8 {w}};      // 32'h1234_5678: >> never reorders
q = {>> {w}};        // q holds 8'h12, 8'h34, 8'h56, 8'h78: q[0] gets the MSB byte
{>> {r}} = q;        // unpack: r is filled from the MSB end of the stream
```

How the stream meets its target (§11.4.14, §11.4.14.3):
- **As a source**, the target must be at least as wide as the stream. A wider fixed-size target is filled with zeros **on the right**, because the stream is left-aligned; a narrower one is an error. A queue or dynamic array target is resized to hold the stream.
- **As a target** (unpacking), `{>> {a, b, c}} = src;` fills `a`, then `b`, then `c` from the most significant end of `src`. If `src` has too few bits it is an error; extra low bits are ignored.
- **Not as an operand.** A streaming concatenation can be the source or target of an assignment, the operand of a bit-stream cast, or part of another streaming concatenation, but not an operand of another operator. Assign it to a variable first, or cast it to a bit-stream type (§11.4.14).

### Bit-stream casting: change the shape, keep the order

A **bit-stream cast** converts a value from one **bit-stream type** to another, keeping every bit in order (§6.24.3). Bit-stream types are integral, packed and string types; unpacked arrays, structs and classes of those; and dynamic arrays, associative arrays and queues of any of them. The cast is the explicit way to turn an unpacked struct into a vector and back: a plain assignment between the two does not compile, because they are not assignment compatible (§6.22.3).

The conversion runs in two steps. The source is flattened into one packed value, first member (or element 0) in the most significant bits; then that value is cut into the destination type from the left (§6.24.3).

```systemverilog
// snippet: the assignments run inside an initial block
typedef struct {               // unpacked: three separate members, no bit numbers
  logic [7:0]  len;
  logic [15:0] addr;
  logic [7:0]  kind;
} hdr_rec_t;                   // 8 + 16 + 8 = 32 bits as a stream
typedef logic [31:0] word_t;   // the cast type must be a single name

hdr_rec_t rec, back;
word_t    w;

rec  = '{len: 8'h04, addr: 16'hBEEF, kind: 8'h01};
w    = word_t'(rec);           // 32'h04BE_EF01: len in [31:24], kind in [7:0]
back = hdr_rec_t'(w);          // back.len = 8'h04, back.addr = 16'hBEEF, back.kind = 8'h01
```

Traced bit by bit: the stream is `len`, `addr`, `kind` = `04`, `BEEF`, `01`, so `w` is `32'h04BE_EF01`. Casting back cuts `w` from the left: 8 bits to `len`, 16 to `addr`, 8 to `kind`, and the round trip is exact.

The same source through three operators:

| Expression, assigned to a 32-bit `w` | Result | What happened |
|---|---|---|
| `w = word_t'(rec);` | `32'h04BE_EF01` | bits copied in order; the sizes must be equal |
| `w = {>> {rec}};` | `32'h04BE_EF01` | the same bits, left to right; a wider target would be zero-filled on the right |
| `w = {<< 8 {rec}};` | `32'h01EF_BE04` | 8-bit slices reversed: `kind` comes first and the two bytes of `addr` swap |

Three pitfalls, each as a prediction. Commit to an answer, then open the card:

<details>
<summary>Predict: does <code>{"logic [31:0]'(rec)"}</code> parse?</summary>

No. **The cast type must be a name.** The casting type is a single type name, such as a typedef or `int` (§6.24.1, Syntax 6-7). `logic [31:0]'(rec)` does not parse, and a size cast such as `32'(rec)` is not a bit-stream cast: a size cast needs an integral operand (§6.24.1). Declare `typedef logic [31:0] word_t;` and write `word_t'(rec)`, which is why the snippet declares the typedef first.
</details>

<details>
<summary>Predict: does a 24-bit unpacked record cast to <code>int</code> compile?</summary>

No. **The sizes must be equal.** When both types have a fixed size and either is unpacked, a size difference is a compile error (§6.24.3), and 24 is not 32. With dynamically sized types the error comes at compile time or at run time, as soon as the sizes are known. Check with `$bits` on both types. Streaming is the tool when the sizes differ.
</details>

<details>
<summary>Predict: what does an <code>x</code> in <code>rec.addr</code> become in <code>{"int'(rec)"}</code>?</summary>

0. **4-state data can become 2-state.** If the source holds any 4-state data, the flattened value is 4-state; parts of the destination that are 2-state are assigned as if cast to 2-state, so `x` and `z` become 0 (§6.24.3, §6.11.2). `int'(rec)` compiles (both are 32 bits), but an `x` in `rec.addr` arrives in the `int` as 0.
</details>

Use a cast when only the shape changes, and streaming when the order changes or the sizes differ.

| You need to | Use | Watch for |
|---|---|---|
| change only the shape, with equal total sizes (`$bits` agree) | a bit-stream cast, `word_t'(rec)` | the cast type must be a single type name (§6.24.1); an `x` arriving in a 2-state destination becomes 0 (§6.24.3, §6.11.2) |
| change the order: a byte swap or a bit reversal | streaming with a slice size, `{<< 8 {rec}}` | a slice size of 1 reverses bits, not bytes (§11.4.14.2) |
| fill a wider or dynamically sized target, or move between different total sizes | streaming, `{>> {rec}}` | a wider fixed target is zero-filled on the right; a narrower one is an error (§11.4.14) |

### The conditional operator and `x` merging

`c ? a : b` returns `a` when `c` is true and `b` when it is false, and evaluates only the chosen branch. When `c` is `x` or `z`, it evaluates **both** branches. If they are equal (`==` returns 1), that value is the result; otherwise, for integral values, they are **merged bit by bit**: bits that agree keep their value and bits that differ become `x` (§11.4.11, Table 11-20). The result is as wide as the wider branch, the condition is self-determined, and the operator groups right to left.

Traced with `sel = 1'bx` and `y = sel ? 4'b1100 : 4'b1010;`:

| Bit | `?` branch | `:` branch | `y` |
|---|---|---|---|
| 3 | 1 | 1 | 1 |
| 2 | 1 | 0 | `x` |
| 1 | 0 | 1 | `x` |
| 0 | 0 | 0 | 0 |

So `y = 4'b1xx0`. The same choice written as `if (sel) y = 4'b1100; else y = 4'b1010;` produces `4'b1010`: `if` treats an `x` condition as false and runs `else`, which hides the unknown (§12.4). The 1-bit version of this contrast is the "if / case with x" tab of the explorer in [F2A: Core Data Types](/curriculum/T1_Foundational/F2A_Core_Data_Types/index).

The merge rule itself, Table 11-20 (§11.4.11), for one bit of the `?` branch (rows) against the same bit of the `:` branch (columns):

| `?` branch bit ↓ / `:` branch bit → | `0` | `1` | `x` | `z` |
|---|---|---|---|---|
| `0` | 0 | `x` | `x` | `x` |
| `1` | `x` | 1 | `x` | `x` |
| `x` | `x` | `x` | `x` | `x` |
| `z` | `x` | `x` | `x` | `x` |

Only agreeing 0s and 1s survive; every other pair, including `z` against `z`, gives `x`.

Table 11-20 merges `z` with anything into `x`, so a tri-state model `assign bus = en ? data : 'z;` drives `x`, not `z`, when `en` is unknown. A reference model written with `?:` propagates unknowns honestly; when it disagrees with a DUT written with `if` only on cycles where a control input is `x`, look for the `x` before blaming either side.

**Debugging: symptom, cause, fix.**

| What you see | Likely cause | Fix |
|---|---|---|
| A sum or average wraps for large inputs (200 + 100 gives 44) | the context is only as wide as the operands and the target (§11.6) | a wider target, `{carry, sum} = a + b`, or a wider operand such as `+ 9'd0` |
| A negative value compares as larger than a positive one | one unsigned operand made the comparison unsigned (§11.8.1) | declare both signed, or use `$signed()` |
| `>>>` fills with 0 | the expression is unsigned: an unsigned operand or a part-select (§11.4.10, §11.8.1) | make every operand signed, or shift into a signed variable first |
| A condition with `&` and `==` behaves oddly | `==` binds tighter than `&` (Table 11-2) | parentheses |
| A checker never reports a mismatch on `x` data | `!=` returned `x` and `if` took the else branch (§11.4.5, §12.4) | `!==`, or `$isunknown()` first |
| `inside` or `==?` matches values you did not expect | `x`, `z` or `?` bits in a member or in the right operand are wildcards (§11.4.6, §11.4.13) | write those bits explicitly, or compare with `===` |
| Bytes arrive reversed, or a value is bit-reversed | `{>>}` versus `{<< 8}`, or a slice size of 1 where 8 was meant (§11.4.14.2) | choose by endianness; test with `32'h1234_5678` |
| Compile error on an expression containing `{<< …}` | a streaming concatenation used as an operand (§11.4.14) | assign it to a variable first, or cast it to a bit-stream type such as `word_t'({<< 8 {w}})` |
| Compile error on a cast such as `hdr_rec_t'(bits)`, or an `x` vanished after a cast | the two types differ in size and one is unpacked; or the destination part is 2-state (§6.24.3) | compare `$bits` of both types; keep 4-state destinations for DUT data |
| An `x` opcode ran a real branch of a decoder | `casex` or `casez` treats `x` or `z` in the case expression as a don't-care (§12.5.1) | use `case inside`, which wildcards only the items (§12.5.4), and report the `default` branch |
| A model output shows `1xx0` where `if`-based code shows a clean value | `?:` merged the branches under an `x` condition (§11.4.11) | find the `x` on the condition; the model is telling the truth |

## Make It Work

This self-checking file runs every rule of the lesson once: width, sign, shifts, precedence, 4-state equality and `inside`, the `x` condition, and streaming through a byte queue.

```systemverilog
// compile
module tb_top;
  // A 32-bit header; the first member is the most significant byte.
  typedef struct packed {
    logic [7:0]  len;
    logic [15:0] addr;
    logic [7:0]  kind;
  } hdr_t;

  int pass_count = 0;
  int fail_count = 0;

  // Callers compute ok with ===, so an x counts as a failure, never a pass.
  function automatic void check(string what, bit ok);
    if (ok) pass_count++;
    else begin
      fail_count++;
      $display("FAIL: %s", what);
    end
  endfunction

  logic        [7:0] a = 8'd200, b = 8'd100;
  logic        [7:0] s8, avg8, avg32;
  logic        [8:0] s9;
  logic              carry;
  logic signed [3:0] sn  = -4;          // 4'b1100
  logic        [7:0] u   = 8'd10;
  logic signed [7:0] r_mixed, r_signed;
  logic signed [7:0] neg = -8;          // 8'hF8
  logic signed [7:0] r_ashr, r_lshr;
  logic        [3:0] flags = 4'b0101, mask = 4'b0010;
  logic        [3:0] nib = 4'b1x10;
  logic              sel;               // never assigned: x
  logic        [3:0] y_cond, y_if;
  logic       [31:0] word = 32'h1234_5678, w_byte, w_bit;
  hdr_t              hdr, back;
  byte unsigned      wire_q[$];

  initial begin
    // 1. Width: the target joins the context; an 8-bit context drops the carry.
    s8          = a + b;
    s9          = a + b;
    {carry, s8} = a + b;
    avg8        = (a + b) >> 1;
    avg32       = (a + b + 0) >> 1;    // the unsized 0 makes the context 32 bits
    $display("width : s8=%0d s9=%0d carry=%b avg8=%0d avg32=%0d", s8, s9, carry, avg8, avg32);
    check("8-bit target wraps",         s8 === 8'd44);
    check("9-bit target keeps carry",   s9 === 9'd300);
    check("{carry, s8} catches it",     carry === 1'b1);
    check("8-bit average",              avg8 === 8'd22);
    check("32-bit average",             avg32 === 8'd150);
    s9 = {a + b};                      // a concatenation member is self-determined
    check("{a + b} is self-determined", s9 === 9'd44);

    // 2. Sign: one unsigned operand makes the expression unsigned.
    r_mixed  = sn + u;
    r_signed = sn + $signed(u);
    $display("sign  : sn + u = %0d, sn + $signed(u) = %0d", r_mixed, r_signed);
    check("mixed is unsigned", r_mixed === 8'sd22);
    check("all signed",        r_signed === 8'sd6);

    // 3. Shifts: >>> copies the sign bit only in a signed expression.
    r_ashr = neg >>> 1;
    r_lshr = neg >> 1;
    $display("shift : neg >>> 1 = %0d, neg >> 1 = %0d", r_ashr, r_lshr);
    check(">>> keeps the sign", r_ashr === -8'sd4);
    check(">> fills with 0",    r_lshr === 8'sd124);

    // 4. Precedence: == binds tighter than the binary &.
    $display("prec  : flags & mask == 0 -> %b, (flags & mask) == 0 -> %b",
             flags & mask == 4'b0000, (flags & mask) == 4'b0000);
    check("groups as flags & (mask == 0)", (flags & mask == 4'b0000) === 4'b0000);
    check("parentheses state the intent",  ((flags & mask) == 4'b0000) === 1'b1);

    // 5. Four-state equality, wildcards and inside.
    $display("equal : == %b, === %b, 4'b1010 ==? nib %b, nib ==? 4'b1010 %b, inside %b",
             nib == 4'b1x10, nib === 4'b1x10, 4'b1010 ==? nib, nib ==? 4'b1010,
             4'b1010 inside {nib, 4'b0000});
    check("== with an x bit is x",   (nib == 4'b1x10) === 1'bx);
    check("=== matches x literally", (nib === 4'b1x10) === 1'b1);
    check("==? wildcards the right", (4'b1010 ==? nib) === 1'b1);
    check("but not the left",        (nib ==? 4'b1010) === 1'bx);
    check("inside uses ==?",         (4'b1010 inside {nib, 4'b0000}) === 1'b1);

    // 6. An x condition: ?: merges both branches, if runs the else branch.
    y_cond = sel ? 4'b1100 : 4'b1010;
    if (sel) y_if = 4'b1100;
    else     y_if = 4'b1010;
    $display("cond  : sel ? 1100 : 1010 = %b, if/else gives %b", y_cond, y_if);
    check("?: merges to 1xx0", y_cond === 4'b1xx0);
    check("if (x) runs else",  y_if === 4'b1010);

    // 7. Streaming: reorder slices, then pack and unpack through a byte queue.
    w_byte = {<< 8 {word}};
    w_bit  = {<< {word}};
    $display("stream: {<< 8} %h, {<< 1} %h", w_byte, w_bit);
    check("byte swap",    w_byte === 32'h7856_3412);
    check("bit reversal", w_bit === 32'h1E6A_2C48);
    hdr    = '{len: 8'd4, addr: 16'hBEEF, kind: 8'h01};
    wire_q = {>> {hdr}};               // big-endian: wire_q[0] is the MSB byte
    {>> {back}} = wire_q;              // unpack: back is filled from the MSB end
    $display("bytes : %h %h %h %h", wire_q[0], wire_q[1], wire_q[2], wire_q[3]);
    check("four bytes",     wire_q.size() == 4);
    check("len byte first", wire_q[0] == 8'd4);
    check("round trip",     back === hdr);
    wire_q = {<< 8 {hdr}};             // little-endian: the kind byte comes first
    check("little-endian",  wire_q[0] == 8'h01);

    $display("PASS=%0d FAIL=%0d", pass_count, fail_count);
    $finish;
  end
endmodule
```

## Push Further

### Expert: Comparison operands size each other, and constants decide the width

<details>
<summary>Predict: with a 4-bit <code>sig = 4'b1000</code>, is <code>sig == 1'bx</code> equal to <code>x</code> or to 0?</summary>

0. The 1-bit constant is zero-extended to `4'b000x` before the compare, and bit 3 is then a known mismatch, which decides the answer (§11.4.5). The branch of an `if` would not run either way, because `if` treats 0 and `x` alike.
</details>

The operands of relational and equality operators are neither fully self-determined nor fully context-determined. They are sized against each other, to the wider of the two, independently of the rest of the expression, and the result is always 1 bit unsigned (§11.8.2). Three consequences:

- `if (a + b > 255)` evaluates the sum in 32 bits because the unsized `255` is 32 bits wide, so the carry survives. `if (a + b > 8'd255)` evaluates it in 8 bits and is never true. Changing how a constant is written changes the width of an addition.
- In `sig == 1'bx` with a 4-bit `sig`, the 1-bit constant is zero-extended to `4'b000x`. Any 1 in `sig[3:1]` makes the result a definite 0 rather than `x` (§11.4.5). The branch never runs either way, because `if` treats 0 and `x` alike; test with `$isunknown(sig)` (§20.9).
- Unsized constants are "at least 32 bits" (Table 11-21). Simulators commonly use exactly 32, but code that depends on the exact width of an unsized constant relies on the implementation (tool-dependent).

<details>
<summary>Predict: <code>2 ** 3 ** 2</code> and <code>-2 ** 2</code></summary>

64 and 4. `**` groups left to right, so the first is `(2 ** 3) ** 2`; unary minus binds tighter than `**`, so the second is `(-2) ** 2` (Table 11-2).
</details>

Two grouping corner cases from Table 11-2: `**` groups left to right, so `2 ** 3 ** 2` is `(2 ** 3) ** 2` = 64, not 512; and unary minus binds tighter than `**`, so `-2 ** 2` is `(-2) ** 2` = 4. Integer `**` with a negative exponent follows Table 11-4: `2 ** -1` is 0 (the reciprocal truncates toward zero), `(-1) ** -3` is −1, and `0 ** -1` is `x` (§11.4.3).

Table 11-4 (§11.4.3) in full, for an integral `op1 ** op2`:

| `op1` | `op2 > 0` | `op2 == 0` | `op2 < 0` |
|---|---|---|---|
| `op1 < -1` | `op1 ** op2` | 1 | 0 |
| `op1 == -1` | odd `op2`: −1; even `op2`: 1 | 1 | odd `op2`: −1; even `op2`: 1 |
| `op1 == 0` | 0 | 1 | `'x` |
| `op1 == 1` | 1 | 1 | 1 |
| `op1 > 1` | `op1 ** op2` | 1 | 0 |

### Expert: Sign traps that survive code review

<details>
<summary>Predict: <code>{"logic signed [7:0] s = -8;"}</code> what does <code>{"s[7:0] >>> 1"}</code> store into an 8-bit variable?</summary>

`8'h7C` (124), not `8'hFC`. A part-select is unsigned even when it spans the whole vector (§11.8.1), so the expression is unsigned and `>>>` fills with 0 like `>>`.
</details>

- **`>>>` inside an unsigned expression.** In `r = (s >>> 1) + u;` with `u` unsigned, the whole expression is unsigned, so `s` is converted to unsigned before the shift and `>>>` fills with 0 (§11.8.1, §11.8.2, §11.4.10). Shift into a signed variable first, or make `u` signed.
- **Part-selects and concatenations are unsigned**, even `s[7:0]` covering all of `logic signed [7:0] s`, and `{s}` (§11.8.1). `s[7:0] >>> 1` therefore fills with 0.
- **Extension of an unknown sign bit.** Resizing a signed value whose sign bit is `x` fills the new bits with `x`; a `z` sign bit fills with `z` (§11.8.4).
- **Mixed 2-state and 4-state operands** evaluate as if all were 4-state (§11.3.4): `i + l` is all `x` when the `logic` operand `l` holds an `x`, even though `i` is an `int`. Stored into an `int`, that `x` silently becomes 0 (§6.11.2).
- **Literal signedness.** `-4'sd12 / 3` is 1: `4'sd12` is the 4-bit pattern `1100`, which is −4, and negating it gives 4 (§11.3.3). Write negative constants as simple decimals, or size them generously.

### Expert: Streaming aggregates and byte order at scale

<details>
<summary>Predict: <code>{"{<< byte {rec}}"}</code> for the header <code>rec</code> above (<code>len = 04</code>, <code>addr = BEEF</code>, <code>kind = 01</code>): do the fields swap?</summary>

Yes. `byte` is an 8-bit slice, so this is the `{<< 8 {rec}}` row of the casting table: `32'h01EF_BE04`. The fields come out in reverse order and the two bytes of `addr` swap places. To change only the byte order inside each field, stream each field on its own (§11.4.14.2).
</details>

- **What gets streamed** (§11.4.14.1): structs member by member in declaration order; unpacked arrays element by element (associative arrays in index order); queues and dynamic arrays with element 0 first; an untagged union through its first-declared member; a class object through its data members, base class first. Null class handles are skipped.
- **Whole-struct reversal.** `{<< byte {pkt}}` reverses every byte of the whole struct, so the fields swap order as well as their bytes. If only the byte order inside each field should change, stream each field on its own.
- **Variable-length fields.** In an unpack, `with` limits how much of an array is filled: `{>> {hdr, payload with [0 +: hdr.len]}} = stream;` fills `hdr.len` elements of `payload`. The `with` expression is evaluated just before `payload` is unpacked, so it can use `hdr.len`, which the same operation unpacked a moment earlier (§11.4.14.4).
- **Cast or stream?** A bit-stream cast keeps the order and, when either type is unpacked, needs equal total sizes (§6.24.3); streaming can reorder, left-aligns into a wider target, and resizes dynamic targets (§11.4.14).

### Expert: Evaluation order, side effects and short-circuits

<details>
<summary>Predict: <code>ptr_valid</code> is 0. Is <code>f(ptr)</code> called in <code>{"if (ptr_valid && f(ptr))"}</code>? And in <code>{"if (ptr_valid & f(ptr))"}</code>?</summary>

No, then yes. `&&` short-circuits: once the left operand is 0 the right operand is not evaluated. The bitwise `&` is not a short-circuit operator, so every operand is evaluated and `f` runs with its side effects (§11.3.5).
</details>

Precedence and associativity decide how operands are grouped, not when each operand is evaluated:

- An expression that both updates and reads a variable has an undefined order. After `i = 10; j = i++ + (i = i - 1);`, `j` may be 18, 19 or 20 (§11.4.2).
- Only `&&`, `||`, `->` and `?:` short-circuit: the right operand of `&&`, `||` and `->` is not evaluated when the left operand decides the result (§11.3.5, §11.4.7). Every other operator evaluates all of its operands, so `if (ptr_valid & f(ptr))` calls `f` even when `ptr_valid` is 0, and any side effect of `f` happens (§11.3.5).
- `?:` evaluates only the selected branch, unless the condition is `x` or `z`, when both branches are evaluated (§11.4.11). A function with side effects in a branch can then run unexpectedly.
- An assignment operator such as `a[i] += 2` evaluates the index expression once (§11.4.1).

### Kata: fix the packet checker

**Objective:** Find five expression bugs in a checker that compiles cleanly, fix each one, and prove the fixes with self-checks.

The code under review:

```systemverilog
// snippet: the checker under review. The declarations sit in a module that
// also declares ok_count and err_count; statements 1 to 5 run inside an
// initial or always block. Every line is legal and compiles.
logic        [7:0]  len_a, len_b;   // two fragment lengths from the DUT
logic        [7:0]  total;
logic        [3:0]  status;         // bit 3: error flag
logic signed [7:0]  temp_c;         // a signed sensor reading
logic        [7:0]  limit_c = 8'd50;
logic        [31:0] payload, swapped, expected;

total = len_a + len_b;                       // 1
if (status & 4'b1000 == 0) ok_count++;       // 2: count frames with the error flag clear

```

**Requirements:**
- For each numbered line, predict the wrong behaviour for these inputs: `len_a = 200`, `len_b = 100`, `status = 4'b0101`, `temp_c = -10`, `payload = 32'h1234_5678`, and for line 5 a `payload` of `32'h1234_56xx` with `expected = 32'h1234_5678`.
- Name the rule and its clause for each bug.
- Write a `tb_top` that applies the fixes to those inputs and self-checks every result with `===`, ending with `PASS=<n> FAIL=0`.

```systemverilog
// compile
module tb_top;
  int pass_count = 0;
  int fail_count = 0;

  function automatic void check(string what, bit ok);
    if (ok) pass_count++;
    else begin
      fail_count++;
      $display("FAIL: %s", what);
    end
  endfunction

  logic        [7:0]  len_a = 8'd200, len_b = 8'd100;
  logic        [8:0]  total;                    // fix 1: room for the carry
  logic        [3:0]  status = 4'b0101;         // error flag (bit 3) clear
  logic signed [7:0]  temp_c = -10;
  logic signed [7:0]  limit_c = 8'sd50;         // fix 3: signed, like temp_c
  logic        [31:0] payload = 32'h1234_5678, swapped;
  logic        [31:0] bad = 32'h1234_56xx, expected = 32'h1234_5678;
  bit                 frame_ok, too_hot, mismatch;

  initial begin
    total = len_a + len_b;
    check("total keeps the carry", total === 9'd300);

    frame_ok = ((status & 4'b1000) == 0);       // fix 2: parentheses
    check("error flag clear", frame_ok === 1'b1);

    too_hot = (temp_c > limit_c);
    check("-10 is not above 50", too_hot === 1'b0);

    swapped = {<< 8 {payload}};                 // fix 4: 8-bit slices
    check("byte swap", swapped === 32'h7856_3412);

    mismatch = (bad !== expected);              // fix 5: x counts as a mismatch
    check("x is a mismatch", mismatch === 1'b1);

    $display("PASS=%0d FAIL=%0d", pass_count, fail_count);
    $finish;
  end
endmodule
```
