## Quick Take
- **What it is:** Nets, variables, and the four-value system (0, 1, `x`, `z`) that decide how a signal is driven, stored and resolved.
- **Why it matters:** 2-state types silently turn `x` and `z` into 0 and hide reset bugs. Declaring a variable where several drivers meet is a compile error; declaring a net gives strength-based resolution. Knowing which one you have tells you what an `x` in a waveform means.
- **The Analogy:** A net is a copper trace: it shows whatever its drivers fight out, and it floats when nobody drives it. A variable is a labelled box: it keeps whatever was written into it last.
- **The Standard:** IEEE 1800-2023 §6 (Data Types) and §7 (Aggregate Data Types).

## Build Your Mental Model

### Picture four values, then predict how they behave

Every bit of a 4-state type holds 0, 1, `x` or `z`. An `x` is not a voltage: it is the simulator saying "I cannot tell whether this bit is 0 or 1". A `z` means nothing drives the net. Start with the picture at the top of the explorer, then work through each tab and commit to a prediction before you reveal the answer.

<LogicStateDiagram />

What the four tabs show, one line each:

1. **Operator tables:** an `x` input does not always give `x`. A controlling value decides (`x & 0` is 0, `x | 1` is 1); without one the result is `x` (Tables 11-11 to 11-15).
2. **`==` vs `===`:** `==` gives `x` only when the comparison is genuinely ambiguous. A known bit that differs makes it a definite 0, so `4'b1x00 == 4'b0000` is 0 (§11.4.5). `===` compares `x` and `z` literally and always returns 0 or 1.
3. **`if` and `case`:** an `x` condition is not true, so `if (a)` takes the else branch, and so does `if (!a)` because `!x` is still `x` (§12.4, §11.4.7). `casex` treats an `x` in the select as a do-not-care and runs a real branch (§12.5.1).
4. **Into 2-state:** assigning to `bit`, `int` or `byte` turns every `x` and `z` bit into 0 (§6.11.2).

| System | Values | Starting value | Integral types | When to use |
|--------|--------|----------------|----------------|-------------|
| **4-state** | 0, 1, `x`, `z` | `'x` for variables (Table 6-7); `'z` for nets, `x` for `trireg` (§6.7.1) | `logic`, `reg`, `integer`, `time`; nets such as `wire` and `tri` | DUT interfaces, reset logic, anything where an unknown must stay visible |
| **2-state** | 0, 1 | `'0` (Table 6-7) | `bit`, `byte`, `shortint`, `int`, `longint` | Scoreboard math, counters, loop indices, randomization |

`real`, `shortreal` and `realtime` are not integral types, so they are neither 2-state nor 4-state. They start at 0.0 (Table 6-7).

> [!WARNING]
> **The X-masking trap (IEEE 1800-2023 §6.11.2):** When a 4-state value containing `x` or `z` is assigned to a 2-state variable, those bits silently become 0. A DUT output that nothing drove after reset turns into a clean-looking 0 in your testbench:
> ```systemverilog
> logic [7:0] dut_data;          // DUT output nobody drove after reset: still 'x
> bit   [7:0] tb_data;
> tb_data = dut_data;            // tb_data becomes 8'h00: the bug is masked
> ```
> **Best practice:** check `$isunknown()` (§20.9) before crossing the boundary, and compare with `===`/`!==` when an `x` must count as a mismatch.

### Who may drive a signal: nets vs. variables

This is the rule behind most "why is my signal `x`?" questions (§6.5). Nets and variables differ in who may write them and in what happens when several writers disagree.

### The `logic` vs. `wire` vs. `reg` Decision Tree

This is a classic interview question. Here's the complete decision tree:

```
Is the signal driven by multiple continuous sources (e.g., tri-state bus)?
├─ YES → Use `wire` or `tri` (need resolution function)
└─ NO → Is this in synthesizable RTL?
    ├─ YES → Use `logic` everywhere (replaces both reg and single-driver wire)
    └─ NO (testbench) → Is X/Z visibility needed?
        ├─ YES → Use `logic` (4-state)
        └─ NO → Use `bit` (2-state, faster sim)
```

> [!TIP]
> **One type, two names (IEEE 1800-2023 §6.11.2):** `logic` and `reg` denote the same type. A `logic` variable replaces `reg` everywhere, and replaces `wire` whenever there is exactly one continuous driver (§6.5). The name `reg` is misleading: it does not imply a hardware register.

### The Complete Type Family

| Category | Types | Size | Signed? | Use Case |
|----------|-------|------|---------|----------|
| **4-state integral** | `logic`, `reg`, `integer`, `time` | variable, variable, 32b, 64b | unsigned, unsigned, signed, unsigned | RTL signals, DUT interfaces |
| **2-state integral** | `bit`, `int`, `byte`, `shortint`, `longint` | variable, 32b, 8b, 16b, 64b | unsigned, signed, signed, signed, signed | TB arithmetic, counters |
| **Real** | `real`, `shortreal`, `realtime` | 64b, 32b, 64b | — | Analog modeling, timing |
| **String** | `string` | dynamic | — | Report formatting, path manipulation |
| **Enum** | `enum` | user-defined base | depends on base | FSM states, opcode encoding |
| **Net types** | `wire`, `tri`, `wand`, `wor`, `trireg`, `supply0/1` | variable | unsigned | Multi-driver signals |

Integral sizes and signedness come from Table 6-8.

> [!IMPORTANT]
> **Signedness Trap (IEEE 1800-2023 §6.11.3):** `int` is **signed** but `bit` is **unsigned**. This catches people:
> ```systemverilog
> bit [7:0] counter = 8'hFF;  // unsigned: value is 255
> int result = counter;        // signed: result is still 255 (zero-extended)
> byte b = counter;            // signed: b is -1! (8'hFF reinterpreted as signed)
> ```
> Always be explicit about signedness when mixing types.

- Keep math in `int/longint` and only slice into packed logic at the edges. It keeps overflow and sign extension predictable.

### Packed vs. Unpacked Arrays — The Memory Layout

Understanding packed vs. unpacked is critical for correct bit manipulation:

```systemverilog
// Packed: contiguous bits, can be sliced as a vector (IEEE 1800-2023 §7.4.1)
logic [3:0][7:0] packed_data;    // 32 contiguous bits
// Access: packed_data[2][3] or packed_data[23:16]

// Unpacked: separate elements, each independently addressed (IEEE 1800-2023 §7.4.2)
logic [7:0] unpacked_data [0:3]; // 4 separate 8-bit elements
// Access: unpacked_data[2] — cannot slice across elements
```

| Aspect | Packed | Unpacked |
|--------|--------|----------|
| **Memory layout** | Contiguous bits | Separate elements |
| **Bit slicing** | Yes — treat as one wide vector | No — index by element only |
| **Part select** | `data[15:8]` works | Illegal across elements |
| **Typical use** | Bus lanes, protocol fields | Memories, register files |
| **Casting** | Casts directly to an integral type | Bit-stream cast to a type of the same total size (§6.24.3), or the streaming operators (§11.4.14) |

- Enums give type safety and built-in iterators (`first()`, `next()`, `num()`, `name()`). They beat magic numbers for FSMs and coverage bins (IEEE 1800-2023 §6.19).

> [!WARNING]
> **Enum Gotcha: the default base type is 2-state.** An enum with no explicit base uses `int` (§6.19), which starts at 0 (Table 6-7). When the first member has the value 0, an FSM state variable that is never reset already looks like it sits in that state, so the missing reset is invisible. Give FSM enums a 4-state base:
> ```systemverilog
> typedef enum logic [1:0] { IDLE, RUN, DONE, ERROR } state_t;  // starts at 2'bxx
> ```
> With a 4-state base the state starts at `'x`, and `state.name()` returns `""` until a reset assigns a real state (§6.19.5.6).

## Deeper Understanding

### Why X-Pessimism and X-Optimism Matter

The same `x` behaves differently depending on where it lands:

| Construct | What happens with `x`/`z` | Effect |
|-----------|---------------------------|--------|
| `if (a)` and `if (!a)` | The condition is not known true, so the else branch runs (§12.4). `!x` is still `x` (§11.4.7), so both forms take else. | X-optimistic: the else path looks like valid behavior |
| `case (sel)` | Items must match bit for bit including `x` and `z`, like `===` (§12.5). An `x` select only matches an item that spells out the same `x`. | Usually falls to `default` |
| `casez (sel)` | `z` and `?` bits in the select or in an item are do-not-cares (§12.5.1). An `x` still has to match exactly. | A floating select matches items it should not |
| `casex (sel)` | `x` and `z` bits in the select or in an item are do-not-cares (§12.5.1). | X-optimistic: an unknown select runs a real branch |
| `a ? b : c` | With an `x` condition both sides are evaluated and bits that differ become `x` (§11.4.11, Table 11-20). | X-pessimistic: the unknown stays visible |
| Arithmetic `x + 1` | Any `x` or `z` operand bit makes the whole result `x` (§11.4.3). | X-pessimistic: propagates the unknown |
| `==` / `!=` | `x` only when the comparison is ambiguous; a known differing bit gives 0 (§11.4.5). | `if (a == b)` takes else when ambiguous |
| `===` / `!==` | `x` and `z` compared literally; always 0 or 1 (§11.4.5). | Correct for TB checks: an unexpected `x` is a mismatch |

**Best practice for RTL:**
- Use `unique case` or `priority case`: the simulator reports a violation when no item matches (§12.5.3), which catches an unknown select falling through. Leave out the `default` item so the check can fire.
- Use `always_comb` instead of `always @*` to get an inferred sensitivity list and the single-writer check (§9.2.2.2).
- Avoid `casex` in RTL; prefer `casez` or `case ... inside`.
- Many simulators offer an X-propagation mode that makes `if` and `case` more pessimistic. Check your tool's documentation before relying on it.

### The `$cast` and Type Compatibility Rules

When working with enum and class types, `$cast` (IEEE 1800-2023 §6.24.2) is essential:

```systemverilog
typedef enum { A, B, C } abc_t;
int i = 1;
abc_t e;

// e = i;             // Compile error: an int needs a cast to become an enum (§6.19.4)

// Static cast: compiles, but performs no range check
e = abc_t'(i);        // If i=5, e holds a value that is not a member!

// $cast: runtime check, returns 0 and leaves e unchanged on failure
if (!$cast(e, i))
  $error("Value %0d is not a valid abc_t", i);
```

### Real-World Corner Cases Interviewers Love

1. **What is `trireg`?** — A net that keeps its last driven value when every driver goes to `z`, at its declared charge strength (`small`, `medium` or `large`) (§6.6.4). It models charge stored on a capacitive node. The **trireg holds charge** tab in the simulator above shows it next to a `wire`.

2. **Can you assign to a `wire` in an `initial` block?** — No! A net cannot be procedurally assigned (§6.5). Use `force`/`release` for a test override, or declare the signal as `logic` if it has a single writer.

3. **What happens when you `$display` an uninitialized `bit`?** — It prints `0` (2-state default, Table 6-7), making it look initialized. This is why 4-state types are safer for DUT signals: an uninitialized `logic` shows `x`, which is immediately visible.

4. **What is the difference between `== 'x` and `=== 'x`?** — `sig == 'x` compares against an all-`x` value, so every bit is ambiguous and the result is always `x`: `if (sig == 'x)` never runs its then branch. In general, `==` gives `x` only when no known bit differs (§11.4.5). Use `sig === 'x` to test for all-`x`, or `$isunknown(sig)` to test for any `x`/`z` bit.

- Use the sandbox to check each type's width, signedness and starting value, and to see what happens when you write `4'b1x0z` into it. It applies the standard's type tables; it is a model, not a simulator.

- **Pattern:** 4-state at the interfaces, 2-state in math-heavy logic, cast when crossing the boundary.
- **Guardrails:** Prefer `===`/`!==` for reset checks so `x`/`z` stays visible. Add assertions when collapsing 4-state to 2-state types.
- **Audit:** Does every signal have a reason to be packed or unpacked? If not, clarify now to avoid later lint churn.
