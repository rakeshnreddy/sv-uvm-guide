## Quick Take

- **What it is:** A **self-checking testbench** drives a **design under test (DUT)**, predicts the correct answer for every input from the specification, compares each answer the DUT gives with that prediction, and ends with a one-line verdict such as `PASS=14 FAIL=0`. Nobody has to open a waveform to know whether the run passed.
- **Why it matters:** It is the smallest bench that counts as verification, and it is milestone M0 of this course. Every later bench, up to a full UVM environment, keeps the same loop: drive, predict, compare, count, report. A bench that only produces waveforms needs a person for every run; a self-checking bench reruns after every change, unattended, and fails loudly.
- **The Analogy:** An exam with an answer key. Every question (the stimulus) has its answer worked out in advance (the expected value), and grading (the comparison) is mechanical, so a thousand papers can be graded overnight. *Where it breaks:* an answer key can be wrong, and an exam with only easy questions lets a weak student pass. A bench has both weaknesses, so you check the key against the specification and plant a known mistake (a **mutant**) to prove that the grader catches it.

**You will be able to:**
1. Write a `tb_top` module with a time unit, a clock, a reset sequence and a DUT instance.
2. Write stimulus tasks, an expected-value queue and a checker that compares with `!==` and counts passes and failures, and end every run with one `PASS=<n> FAIL=<m>` line, a `$fatal` watchdog and `$finish`.
3. Prove the bench can fail: inject a DUT bug (a stuck bit or an off-by-one) and choose the directed test, selected with a plusarg, that catches it.
4. Explain why the bench drives DUT inputs with `<=` (or on the opposite clock edge) until you learn clocking blocks, and predict what a blocking drive at the active edge can do.
5. Debug a first bench from its log: a vacuous pass, an X that slips through `!=`, a check made one cycle too early, and a hang.

## Build Your Mental Model

### Why self-checking beats eyeballing waveforms

After writing your first stimulus, the natural move is to open the waveform and look. For one addition that works: find the edge where the result is valid, read it, and add the inputs in your head. For the fourteen additions in this lesson's bench, after every RTL edit and on every simulator, it does not. People miss things, a waveform cannot fail a nightly regression, and it says nothing about the cases nobody looked at.

A **self-checking testbench** (TB) moves the judgement into code. For every stimulus it computes the **expected value** with a **reference model** of the specification, compares it with the actual output of the DUT, counts passes and failures, and prints one verdict line. A run becomes a yes-or-no answer that a script can collect for thousands of tests.

| | Eyeballing a waveform | Self-checking testbench |
|---|---|---|
| Who decides PASS | a person, every run | the bench, every run |
| How many results are checked | the few someone looks at | every one |
| An X on an output | easy to miss | a failure, when compared with `!==` |
| After an RTL change | look again | rerun and read one line |
| Evidence that it can fail | none | plant a bug and watch FAIL appear |

Waveforms stay essential for debugging: once a check fails, the dump shows why. This lesson's bench writes one only when you ask for it.

There is a catch. A self-checking bench can lie: a checker that never runs prints PASS, and so does one that compares the wrong thing or cannot see X. The rule from [F1B](/curriculum/T1_Foundational/F1B_The_Verification_Mindset/index) applies: a test you have never seen fail is no evidence. This lesson builds the bench, then proves that it can fail.

### Meet the DUT: a registered adder

The DUT is `adder_reg`, a registered 8-bit adder with a valid flag. Write the bench from this specification, not from the RTL: if you read the RTL to decide what is correct, you inherit its bugs.

| Port | Direction | Meaning |
|---|---|---|
| `clk` | input | Clock. Everything happens on its rising edge. |
| `rst_n` | input | Synchronous reset, active low. |
| `in_valid` | input | `a` and `b` hold an addition to perform this cycle. |
| `a`, `b` | input, 8 bits | The operands. |
| `out_valid` | output | `sum` holds a new result. |
| `sum` | output, 9 bits | `a + b`, with the carry in bit 8. |

On every rising edge of `clk`:
- **R1.** If `rst_n` is 0, `out_valid` becomes 0 and `sum` becomes 0.
- **R2.** Otherwise `out_valid` becomes the value of `in_valid`: one result per valid input, one cycle later.
- **R3.** If `in_valid` is 1, `sum` becomes `a + b`, all 9 bits of it.
- **R4.** If `in_valid` is 0, `sum` keeps its value.

The RTL in Make It Work has one extra parameter, `BUG`, that plants a known bug on request. Real designs have no such parameter; it exists here so you can prove that the bench fails.

**In a real testbench.** A UVM bench in Tier 2 splits the same jobs into classes: a driver drives, a monitor takes over the checker's reading of `out_valid` and `sum`, a predictor plays `model_add()`, a scoreboard plays `exp_q` and the compare, and a test (with its sequences) chooses the stimulus. The diagram's tags name those roles, so this bench is the skeleton you will recognise later.

### Time, clock and reset

**Time unit.** `#5` means 5 time units. `timeunit 1ns; timeprecision 1ps;` as the first items of a module set its time unit (1 ns) and the precision that delays are rounded to (1 ps), whatever order the files are compiled in (IEEE 1800-2023 §3.14.2.2). The older `` `timescale 1ns/1ps `` directive applies to every module compiled after it, so a module's unit can change with file order (§3.14.2.1). Mixing is an error: if some design elements have a time unit and precision and others do not, the standard rejects the design (§3.14.2.3), which is why the DUT declares one too. [F3A](/curriculum/T1_Foundational/F3A_Simulation_Semantics/index) covers time units in depth.

**Clock.** A free-running clock is one variable and one `always` procedure:

```systemverilog
// snippet
logic clk = 1'b0;        // set before any procedure starts (§6.8)
always #5 clk = ~clk;    // 10 ns period: rising edges at 5, 15, 25 ns ...
```

The initializer matters. A `logic` variable without one starts at x (§6.8, Table 6-7), and `~x` is x (§11.4.8), so `logic clk; always #5 clk = ~clk;` never toggles and nothing clocked ever runs. The other common form, an `initial` block that sets `clk` to 0 and then loops `forever #5 clk = ~clk;`, works as well.

**Reset.** `reset_dut()` drives every DUT input to a known value, holds `rst_n` low for two rising edges, then releases it with `<=` just after an edge, so the DUT sees the release on the next edge. Rule R1 needs at least one edge with `rst_n` low; check your design's specification for how many it needs. Until reset is released the checker compares nothing; afterwards it insists that `out_valid` is never x or z, using `$isunknown` (§20.9). If your DUT resets asynchronously, assert reset at any time but release it the same way; [F4C](/curriculum/T1_Foundational/F4C_Clocking_Blocks/index) explains why reset stays outside clocking blocks.

### Drive the DUT without a race

**The rule:** drive DUT inputs with `<=` right after the clock edge, or with `=` at the opposite edge. Never use `=` at the edge the DUT samples on, its **active edge**.

Here is why. The DUT's `always_ff` and the bench's `send()` both wake on the same rising edge, and the standard lets the simulator run processes woken by one event in any order (§4.7). A **blocking assignment** (`=`) changes the variable at once, so whether the flop reads the old or the new value depends on which process ran first: a **race condition** (§4.8). A **nonblocking assignment** (NBA, `<=`) computes the value now but schedules the update for later in the same **time slot** (all the activity at one simulation time), after every process woken by the edge has run (§4.9.4, §10.4.2).

**Predict.** In `+TEST=gaps`, `a` is 7 just before the edge on which `send(9, 10)` runs. On that edge, `send()` drives `a` to 9 while the DUT's flop reads `a`. Which value does the flop capture with each drive style?

| How `send()` drives `a` | Order the simulator picks | Value the DUT samples on this edge |
|---|---|---|
| `a = a_val;` (blocking) | the DUT's `always_ff` first | 7, the old value, as intended |
| `a = a_val;` (blocking) | `send()` first | 9, the new value: one cycle early |
| `a <= a_val;` (nonblocking) | either order | 7: the update lands after every read |

With blocking drives, the edge on which the DUT sees each input depends on an order the standard leaves open. The same bench can pass on one simulator and fail on another, or change behaviour after an unrelated edit. The reset release has the same problem: `rst_n = 1'b1;` right after `@(posedge clk)` lets the DUT leave reset on that edge or on the next, depending on the order.

**Check your prediction against a model.** The comparison below is a one-flop DUT, `always_ff @(posedge clk) q <= din;`, and a bench that drives `din` from 3 to 7 on the clock edge and reads `q` on the same edge. It runs each drive style through **every** process order the standard allows. Answer its question before you look at the verdicts. The strip in each card names scheduler regions that [F3B](/curriculum/T1_Foundational/F3B_Scheduling_Regions/index) teaches; for now, read only the verdict and the values.

What the model shows:
- **`din = 7` is a race.** Some legal orders let the flop capture 7, one cycle early, exactly like the blocking row of the table above.
- **`din <= 7` is deterministic.** The flop captures 3 in every order. This is the style `send()`, `idle()` and `reset_dut()` use.
- **`cb.din <= 7` is deterministic too.** It is the clocking-block form you will write from F4C onward.
- **The bench's read of `q` sees the old value in every order**, because the DUT writes `q` with `<=`. This lesson's checker relies on the same fact; Push Further explains when it stops being true.

The opposite-edge style is also race-free, because no flop in this DUT reads anything on the falling edge:

```systemverilog
// snippet: the opposite-edge style, an alternative to send()
task automatic send_negedge(input logic [W-1:0] a_val, input logic [W-1:0] b_val);
  @(negedge clk);
  in_valid = 1'b1;   // the DUT samples on the next rising edge, half a cycle later
  a = a_val;
  b = b_val;
  exp_q.push_back(exp_t'{a: a_val, b: b_val, sum: model_add(a_val, b_val)});
endtask
```

Inputs then change mid-cycle, which reads well in a waveform. The style breaks when the design also uses falling edges or several clocks, and in gate-level simulation the half cycle becomes a real timing budget. This lesson drives with `<=` after the rising edge, because that is the idea a **clocking block** formalises: a declaration, taught in F4C, that fixes when a bench samples and drives a group of signals relative to a clock. [F3C](/curriculum/T1_Foundational/F3C_Delta_Cycles_and_Race_Conditions/index) lets you run every legal process order and watch the race appear and disappear; [F4C](/curriculum/T1_Foundational/F4C_Clocking_Blocks/index) replaces this rule with clocking blocks, which every bench from milestone M1 onward uses.

**Code-review rule until F4C:** no `=` to a DUT input after `@(posedge clk)`.

What the waveform shows:
- **Edge 1.** `reset_dut()` releases `rst_n` with `<=`, so the DUT first sees `rst_n = 1` on edge 2.
- **Edge 2.** `send(5, 5)` wakes, drives `in_valid`, `a` and `b` with `<=`, and pushes the expectation 10 onto `exp_q`. The new values appear just after the edge.
- **Edge 3.** The DUT samples `in_valid = 1`, `a = 5` and `b = 5`, and schedules `out_valid <= 1` and `sum <= 10`.
- **Edge 4.** The checker, woken by the same edge as the DUT, reads `out_valid = 1` and `sum = 10`: the values from before this edge's updates. It pops 10 from `exp_q`, a match.

A result is therefore checked two edges after it was driven, although the DUT's latency is one cycle: one edge for the DUT to sample the inputs, one for the checker to read the registered result. You count those edges once, here. The queue in the next section means the checker never needs to know the latency.

### Expected values: a model and a queue

**The reference model** answers "what should the DUT say?" from the specification alone:

```systemverilog
// snippet
function automatic logic [W:0] model_add(input logic [W-1:0] op_a,
                                         input logic [W-1:0] op_b);
  return {1'b0, op_a} + {1'b0, op_b};   // widen first, so the carry is kept
endfunction
```

It is written differently from the RTL on purpose. The RTL relies on its 9-bit target to widen `a + b` (§11.6); the model widens each operand itself. If you copy the RTL's expression into the model, you copy its bugs, and the check can no longer disagree with the design. For a DUT with state, such as a counter, the model is a variable that you update every cycle; for a pure function like this adder, a function is enough.

**Why a queue.** The result for a stimulus arrives after the stimulus, and with back-to-back inputs several results are in flight at once. One `expected` variable cannot hold them: the next `send()` overwrites it before the earlier result arrives. A queue ([F2B](/curriculum/T1_Foundational/F2B_Dynamic_Structures/index)) keeps them in order. `send()` pushes one expectation per transaction with `push_back` (§7.10.2.7), and the checker pops the oldest one for each result with `pop_front` (§7.10.2.4). Each expectation is a struct ([F2A](/curriculum/T1_Foundational/F2A_Core_Data_Types/structs-unions-enums)) that also keeps the inputs, so a failure message can name them. Together, the queue of expectations and the compare that consumes it form a **scoreboard**: the part of a bench that holds expected results and matches each actual result against one of them.

**Predict.** In `+TEST=gaps`, what does `exp_q` hold after edge 6? Trace it:

| Edge (time) | Bench | DUT samples | Checker sees | Expected sums in `exp_q` after the edge |
|---|---|---|---|---|
| 2 (25 ns) | `send(5, 5)` pushes 10 | `in_valid = 0` | `out_valid = 0` | `{10}` |
| 3 (35 ns) | `idle` | 5 + 5 | `out_valid = 0` | `{10}` |
| 4 (45 ns) | `idle` | `in_valid = 0` | `sum = 10`: pop 10 ✓ | `{}` |
| 5 (55 ns) | `send(7, 8)` pushes 15 | `in_valid = 0` | `out_valid = 0` | `{15}` |
| 6 (65 ns) | `send(9, 10)` pushes 19 | 7 + 8 | `out_valid = 0` | `{15, 19}` |
| 7 (75 ns) | `idle` | 9 + 10 | `sum = 15`: pop 15 ✓ | `{19}` |
| 8 (85 ns) | `send(11, 12)` pushes 23 | `in_valid = 0` | `sum = 19`: pop 19 ✓ | `{23}` |
| 9 (95 ns) | `idle` | 11 + 12 | `out_valid = 0` | `{23}` |
| 10 (105 ns) | (draining) | `in_valid = 0` | `sum = 23`: pop 23 ✓ | `{}` |

At edge 6 two results are in flight, and the queue absorbs them. Matching on `out_valid` instead of counting cycles is what lets one checker serve any mix of valid and idle cycles.

Three queue pitfalls:
- **Popping an empty queue.** `pop_front` on an empty queue returns the element type's default value (here, an `exp_t` whose `logic` members are all x; §7.10.2.4, Table 7-1) and may only warn. Check `exp_q.size()` first, and report a result that nobody expected as a failure.
- **Leftovers.** Expectations still in the queue at the end are results that never arrived. Count each one as a failure.
- **Order assumptions.** An in-order queue is right for a DUT that answers in order. A DUT that may reorder its answers needs keyed matching: F2B's associative array of queues, and later [A-UVM-6](/curriculum/T3_Advanced/A-UVM-6_Scoreboards_and_Reference_Models/index).

### Compare with `!==` and count

The checker compares with the **case inequality** operator `!==`, never with `!=`. With `!=`, if the bits that are known agree and some bit is x or z, the result is x (§11.4.5). An `if` treats x as false and runs its `else` branch (§12.4). So `if (sum != e.sum) fail_cnt++; else pass_cnt++;` counts an unknown result as a **pass**. `!==` compares x and z as values and always returns 0 or 1.

| `sum` from the DUT | Expected | `sum != 10` | The `if`/`else` counts | `sum !== 10` |
|---|---|---|---|---|
| `9'd10` | 10 | 0 | pass ✓ | 0: pass ✓ |
| `9'd11` | 10 | 1 | fail ✓ | 1: fail ✓ |
| all bits x | 10 | x | **pass ✕** | 1: fail ✓ |
| `9'b0_0000_101x` | 10 | x: the known bits match 10 | **pass ✕** | 1: fail ✓ |
| `9'b1_0000_101x` | 10 | 1: bit 8 differs | fail ✓ | 1: fail ✓ |

Two more ways X hides:
- **In a control signal.** `if (out_valid)` with `out_valid` at x simply skips the compare: no failure, no pass, nothing. The checker therefore tests `$isunknown(out_valid)` first (§20.9).
- **In a 2-state copy.** Copying `sum` into an `int` or a `bit` turns x into 0 before any compare ([F2A](/curriculum/T1_Foundational/F2A_Core_Data_Types/index)). Keep DUT values in 4-state `logic`.

Each compare ends in `pass_cnt++` or in `fail_cnt++` plus a `$error` message. `$error` reports and lets the run continue (§20.10), so one run shows every failure, not just the first.

### Directed tests from a plan

A **directed test** is a fixed list of stimulus values chosen to exercise one row of a verification plan. Use the plan-row format from [F1B](/curriculum/T1_Foundational/F1B_The_Verification_Mindset/index): a feature, a scenario, a check, and the bug the check must catch.

| Plan row (rule) | Test | Stimulus | The check proves | Mutant it catches |
|---|---|---|---|---|
| R3 for ordinary values | `smoke` | 1 + 2, 10 + 20, 100 + 27 | the basic path works end to end | off-by-one (`BUG=2`) |
| R3 keeps the carry | `corners` | 255 + 1, 255 + 255, 128 + 128 | bit 8 of `sum` can be 1 | carry stuck at 0 (`BUG=1`) |
| R3 at the boundaries | `corners` | 0 + 0, 255 + 0, 0 + 255, `8'hAA` + `8'h55` | 0 needs every bit at 0; 255 needs bits 0 to 7 at 1 | any bit of `sum` stuck at 1; bits 0 to 7 stuck at 0 (bit 8 stuck at 0 is the carry row's job) |
| R2: one result per valid input | `gaps` | valid, two idle, two back to back, idle, valid | `out_valid` follows `in_valid` one cycle later, with no extra or missing result | dropped or duplicated results |
| R1: outputs known after reset | every test | `reset_dut()` | `out_valid` is never x or z after reset | a reset that does not clear `out_valid` |

Tests are chosen at run time with a **plusarg**, a `+name` or `+name=value` argument on the simulator's command line (§21.6):

```systemverilog
// snippet
if (!$value$plusargs("TEST=%s", test_name)) test_name = "all";
```

`+TEST=corners` runs one test; no plusarg runs them all. `$value$plusargs` returns 0 and leaves the variable untouched when the plusarg is missing (§21.6), which is why the default sits in the same line. A misspelled name stops the run with `$fatal`, because a bench that runs nothing must never look like a pass. One trap: plusargs match by prefix, so `$test$plusargs("DUMP")` is also true for `+DUMPALL` (§21.6). Pick names that are not prefixes of each other.

**Predict, then check.** With the carry bit stuck at 0 (`BUG=1`), which tests fail? This matrix comes from a cycle model of the Make It Work code; each cell is the run's summary line:

| `+TEST=` | `BUG=0` (correct) | `BUG=1` (carry stuck at 0) | `BUG=2` (off by one) |
|---|---|---|---|
| `smoke` | `PASS=3 FAIL=0` | `PASS=3 FAIL=0`, escapes | `PASS=0 FAIL=3` |
| `corners` | `PASS=7 FAIL=0` | `PASS=4 FAIL=3` | `PASS=0 FAIL=7` |
| `gaps` | `PASS=4 FAIL=0` | `PASS=4 FAIL=0`, escapes | `PASS=0 FAIL=4` |
| `all` | `PASS=14 FAIL=0` | `PASS=11 FAIL=3` | `PASS=0 FAIL=14` |

The off-by-one is loud: every result is wrong. The stuck carry is quiet: `smoke` and `gaps` never produce a sum of 256 or more, so bit 8 is 0 in every result they check, broken or not. A directed test catches only the bugs its stimulus provokes and its checks observe.

### End every run with a verdict

Four statements decide how a run ends:

| Statement | Effect (IEEE 1800-2023) | Use it for |
|---|---|---|
| `$error("...")` | Prints a run-time error with the tool's prefix (file, line, scope, time); the run continues (§20.10). | A failed check. |
| `$fatal(1, "...")` | Prints a fatal error and ends the run: it implies a call to `$finish` (§20.10). | A broken bench: an unknown test, a timeout. |
| `$finish` | Ends the simulation and returns control to the operating system (§20.2). | The normal end, after the summary. |
| `$display("PASS=%0d FAIL=%0d", ...)` | Prints the verdict. | Exactly once per run. |

The first argument of `$fatal` and the optional argument of `$finish` (0, 1 or 2) only choose how much diagnostic text the tool prints (§20.2, §20.10).

**The summary line** is the bench's contract with whatever runs it: exactly one line, in a fixed format. Milestone M0 requires a clean run to print a line that matches `^PASS=\d+ FAIL=0$`. Two guards keep that line honest. Expectations left in `exp_q` count as failures, and a run that checked nothing at all fails, because `PASS=0 FAIL=0` would otherwise match the pattern.

**Ending the run.** A simulation stops by itself when there is no further activity of any kind (§9.6.1). A free-running clock is activity forever, so without `$finish` this bench never ends. Before the summary, `drain()` waits until every expectation has been checked, then watches two more quiet edges so that a late or extra result still fails. It reads `exp_q` on the falling edge, when the checker is not running.

**The watchdog.** If the bench hangs (a wait that never completes, a clock that never toggles), no summary appears and a regression stalls. A **watchdog** races the test against a timer:

```systemverilog
// snippet: the end of the main initial block in tb_top
fork
  begin : run
    reset_dut();
    if (test_name == "all") begin
      run_one("smoke");
      run_one("corners");
      run_one("gaps");
    end else begin
      run_one(test_name);
    end
    drain();
  end
  begin : watchdog
    #(TIMEOUT);
    fail_cnt++;                  // a hang is a failure, never a pass
    report();
    $fatal(1, "WDOG test '%s' still running at %t", test_name, $time);
  end
join_any                         // resume when either branch ends (§9.3.2)
disable fork;                    // stop the branch that is still running (§9.6.3)
report();
$finish;
```

What to take from the race:
- `join_any` resumes `main` when the first branch ends (§9.3.2). In a normal run that is `run`, and `disable fork` kills the waiting watchdog.
- `disable fork` kills **every** descendant of the process that calls it (§9.6.3). Here `main` has no other children, so only the watchdog can die; the checker is a separate `always` procedure, not a child of `main`. If `main` had forked a background process earlier, `disable fork` would kill it too, and [F2C](/curriculum/T1_Foundational/F2C_Procedural_Code_and_Flow_Control/index) shows the isolation wrapper that prevents it.
- If the timer wins, the watchdog counts the hang, prints the summary and calls `$fatal`, so even a hung run ends with a verdict line.
- A delay-based watchdog cannot catch a loop that never lets time advance, such as `while (exp_q.size() != 0);` with nothing inside it: the timer's moment never comes. Every loop that waits needs a clock edge or a delay inside it.

**Why the checker is an `always`, not an `always_ff`.** `always_comb` and `always_ff` forbid any other process from writing the variables they assign, including variables written by the functions they call (§9.2.2.2, §9.2.2.4). The checker's `check_result()` writes `fail_cnt`, which `report()` and the watchdog also write, so the checker must be a plain `always @(posedge clk)`. Keep `always_ff` for flops.

### Reporting conventions

A log is read by people and by scripts. These conventions serve both:

| Message | Code | Why |
|---|---|---|
| Test start | `$display("%t TEST %s", $time, name)` | Shows where each test begins, in the log and on the waveform's time axis. |
| A failed check | `$error("CHK a=%0d b=%0d: sum=%0d, expected %0d", ...)` | The tool adds the severity, file, line and time (§20.10); the inputs let you reproduce the failure without a waveform. |
| A broken bench | `$fatal(1, "TEST unknown test ...")` | Stops at once: nothing after a configuration error is meaningful. |
| The verdict | `$display("PASS=%0d FAIL=%0d", ...)` | Exactly once, in a fixed format. |

- **Tag every message** (`TEST`, `CHK`, `WDOG`), so that searching the log for `CHK` finds every check failure.
- **Stay quiet on success.** A line for every passing check buries the one that failed.
- **Print time in one unit.** `$timeformat(-9, 0, " ns", 0)` once, at time 0, makes every `%t` print nanoseconds with a suffix (§20.4.3).
- **Make unknowns visible.** With `%0d`, an all-x value prints as `x` and a partly unknown one as `X` (§21.2.1.3), so an X result shows in the message.
- **Debug the first failure first.** Later failures are often its echoes.

### Waveforms on demand

Dumping a waveform costs run time and disk space, so this bench writes one only when the run has `+DUMP`:

```systemverilog
// snippet
if ($test$plusargs("DUMP")) begin
  $dumpfile("tb_top.vcd");    // name of the VCD file (§21.7.1.1)
  $dumpvars(0, tb_top);       // 0: tb_top and every level below it (§21.7.1.2)
end
```

A **value change dump (VCD)** is the portable waveform format defined by the standard (§21.7); waveform viewers generally read it, and simulators also offer faster formats of their own (tool-dependent). To debug a failure, rerun the failing test with `+DUMP`, go to the time of the first `CHK` error, and look one and two edges earlier at the inputs that produced that result.

### Common bugs and how to debug them

| What the log shows | Likely cause | Fix |
|---|---|---|
| `nothing was checked`, then `PASS=0 FAIL=1` | The test sent nothing: an empty or unfinished test task, or a `case` branch that calls the wrong task. | Read the test task named on the `TEST` line. |
| `result(s) never arrived` (with `PASS=0` if none came back) | Reset was never released (`rst_n` stuck low, or never driven and so x, which makes the checker skip every edge), the DUT dropped results, or the run ended before they came out. | Rerun with `+DUMP` and look at `rst_n`, `in_valid` and `out_valid` on the first edges; check that every test ends with `idle()` and that `drain()` ran. |
| `unexpected result ... nothing was sent` | The DUT made an extra result, or a test left `in_valid` high (no final `idle()`). | Look at the last `send()` before the error time. |
| Each actual value equals the previous expected value | The check reads `sum` one cycle too early, or one `expected` variable is overwritten by the next `send()`. | Match results on `out_valid` with the queue; do not count edges. |
| An X result passes | `!=` instead of `!==`, or `sum` copied into an `int` or `bit`. | Use `!==`; keep DUT values in `logic`. |
| Passes on one simulator, fails on another (or after reordering files) | A blocking drive (`=`) to a DUT input at the clock edge. | Drive with `<=` after the edge, or at the opposite edge. |
| The summary prints, but the run never ends | No `$finish` after `report()`: the free-running clock keeps the simulation busy, and `disable fork` has already killed the watchdog. | End `main` with `$finish`. |
| The run ends with the `WDOG` fatal | A wait for a value that never comes, or a clock that never toggles (`logic clk;` starts at x). | Find the blocked process at the timeout time with your simulator's debug commands; look at `clk` first. |
| Simulation time stops and the watchdog never fires | A zero-delay loop, such as `while (exp_q.size() != 0);`. | Put a clock edge inside every loop that waits. |
| An error about missing time units | Some modules have a time unit and others do not (§3.14.2.3). | Give every module a `timeunit`, or use your simulator's default time-scale option. |

### Recap

- A self-checking bench predicts every result from the specification, compares with `!==`, counts, and prints one `PASS=<n> FAIL=<m>` line.
- `tb_top` has a time unit, a clock with an initializer, a reset released with `<=` after an edge, and the DUT instance.
- Drive with `<=` after the edge (or with `=` at the opposite edge) until you learn clocking blocks.
- Expectations go into a queue when you drive; results pop them when `out_valid` says so. Leftovers and zero checks are failures.
- Directed tests come from plan rows, and a plusarg picks them at run time.
- `$error` continues, `$fatal` ends, `$finish` ends, and a watchdog guarantees that every run ends with a verdict.
- A PASS is evidence only after you have seen the same bench FAIL on a planted bug.

## Make It Work

### The complete bench

One file holds the DUT and the bench, so you can copy it and run it as it is. In a project the DUT lives in its own file (or, on EDA Playground, in the design pane). The `// compile` tag marks a complete compile unit.

```systemverilog
// compile
// tb_top.sv: a registered adder (the DUT) and its self-checking testbench.

// ------------------------------------------------------------------- DUT
module adder_reg #(
  parameter int W   = 8,
  parameter int BUG = 0              // 1 or 2 plants a known bug; real RTL has none
) (
  input  logic         clk,
  input  logic         rst_n,        // synchronous, active low
  input  logic         in_valid,
  input  logic [W-1:0] a,
  input  logic [W-1:0] b,
  output logic         out_valid,
  output logic [W:0]   sum           // one extra bit, so the carry is kept
);
  timeunit 1ns; timeprecision 1ps;   // every module needs one (1800-2023 3.14.2.3)

  logic [W:0] next_sum;

  always_comb begin
    next_sum = a + b;                // evaluated at W+1 bits, the target's width
    case (BUG)
      1:       next_sum[W] = 1'b0;           // mutant 1: carry bit stuck at 0
      2:       next_sum    = a + b + 1'b1;   // mutant 2: off by one
      default: ;                             // 0: the design as specified
    endcase
  end

  always_ff @(posedge clk) begin
    if (!rst_n) begin                // R1
      out_valid <= 1'b0;
      sum       <= '0;
    end else begin
      out_valid <= in_valid;         // R2: one result per valid input, a cycle later
      if (in_valid) sum <= next_sum; // R3; otherwise sum holds its value (R4)
    end
  end
endmodule

// ------------------------------------------------------------- testbench
module tb_top;
  timeunit 1ns; timeprecision 1ps;

  localparam int      W       = 8;
  localparam realtime TIMEOUT = 10us;  // far longer than the longest run (250 ns)

  // Signals between the bench and the DUT
  logic         clk = 1'b0;            // must start known: ~x stays x
  logic         rst_n;
  logic         in_valid;
  logic [W-1:0] a, b;
  logic         out_valid;
  logic [W:0]   sum;

  // Scoreboard: one expectation per transaction, oldest first
  typedef struct {
    logic [W-1:0] a, b;                // the inputs, so a failure can name them
    logic [W:0]   sum;                 // the expected result
  } exp_t;

  exp_t exp_q[$];
  int   pass_cnt = 0;
  int   fail_cnt = 0;

  // The DUT. Set .BUG(1) or .BUG(2) to prove that the bench can fail.
  adder_reg #(.W(W), .BUG(0)) dut (
    .clk(clk), .rst_n(rst_n), .in_valid(in_valid), .a(a), .b(b),
    .out_valid(out_valid), .sum(sum)
  );

  always #5 clk = ~clk;                // 10 ns period: rising edges at 5, 15, 25 ns ...

  // Reference model: the specification's answer, written independently of the RTL.
  function automatic logic [W:0] model_add(input logic [W-1:0] op_a,
                                           input logic [W-1:0] op_b);
    return {1'b0, op_a} + {1'b0, op_b};  // widen first, so the carry is kept
  endfunction

  // Reset: hold rst_n low for a number of rising edges, then release it.
  task automatic reset_dut(input int cycles = 2);
    rst_n    <= 1'b0;
    in_valid <= 1'b0;
    a        <= '0;
    b        <= '0;
    repeat (cycles) @(posedge clk);
    rst_n    <= 1'b1;                  // just after an edge: seen on the next one
  endtask

  // Drive one addition for one cycle and record what the DUT must answer.
  task automatic send(input logic [W-1:0] a_val, input logic [W-1:0] b_val);
    @(posedge clk);
    in_valid <= 1'b1;                  // <= lands after the DUT's flops read this edge
    a        <= a_val;
    b        <= b_val;
    exp_q.push_back(exp_t'{a: a_val, b: b_val, sum: model_add(a_val, b_val)});
  endtask

  // Drive no addition for n cycles.
  task automatic idle(input int n);
    repeat (n) begin
      @(posedge clk);
      in_valid <= 1'b0;
    end
  endtask

  // Compare one DUT result with the oldest expectation.
  function automatic void check_result(input logic [W:0] actual);
    exp_t e;
    if (exp_q.size() == 0) begin
      fail_cnt++;
      $error("CHK unexpected result sum=%0d: nothing was sent", actual);
      return;
    end
    e = exp_q.pop_front();
    if (actual !== e.sum) begin        // !== : an x or z bit is a mismatch
      fail_cnt++;
      $error("CHK a=%0d b=%0d: sum=%0d, expected %0d", e.a, e.b, actual, e.sum);
    end else begin
      pass_cnt++;
    end
  endfunction

  // Checker: a testbench process, so always, not always_ff (1800-2023 9.2.2.4).
  // It reads out_valid and sum as they were before this edge: the DUT
  // updates them with <=, after every process woken by the edge has run.
  always @(posedge clk) begin
    if (rst_n) begin                   // no checks while the DUT is in reset
      if ($isunknown(out_valid)) begin
        fail_cnt++;
        $error("CHK out_valid is %b after reset", out_valid);
      end else if (out_valid) begin
        check_result(sum);
      end
    end
  end

  // Directed tests: one task per row of the test table.
  task automatic test_smoke();
    send(8'd1, 8'd2);
    send(8'd10, 8'd20);
    send(8'd100, 8'd27);
    idle(1);
  endtask

  task automatic test_corners();
    send(8'd0, 8'd0);                  // every result bit 0
    send(8'd255, 8'd0);                // largest sum without a carry
    send(8'd0, 8'd255);
    send(8'd255, 8'd1);                // carry: 256
    send(8'd255, 8'd255);              // largest sum: 510
    send(8'd128, 8'd128);              // carry with a zero low byte
    send(8'hAA, 8'h55);                // alternating bits: every low bit 1
    idle(1);
  endtask

  task automatic test_gaps();
    send(8'd5, 8'd5);
    idle(2);                           // no result may appear on idle cycles
    send(8'd7, 8'd8);
    send(8'd9, 8'd10);                 // back to back: two results in flight
    idle(1);
    send(8'd11, 8'd12);
    idle(1);
  endtask

  task automatic run_one(input string name);
    $display("%t TEST %s", $time, name);
    case (name)
      "smoke":   test_smoke();
      "corners": test_corners();
      "gaps":    test_gaps();
      default:   $fatal(1, "TEST unknown test '%s' (use smoke, corners, gaps, all)",
                        name);
    endcase
  endtask

  // End of test: wait (bounded) until every expectation is checked, then two
  // quiet cycles, so that a late or extra result cannot slip past the summary.
  task automatic drain(input int max_cycles = 20);
    repeat (max_cycles) begin
      @(negedge clk);                  // mid-cycle: the checker is not running
      if (exp_q.size() == 0) break;
    end
    repeat (2) @(negedge clk);
  endtask

  // The verdict: exactly one line, in a format a script can match.
  function automatic void report();
    if (exp_q.size() != 0) begin
      fail_cnt += exp_q.size();
      $error("CHK %0d result(s) never arrived", exp_q.size());
    end
    if (pass_cnt == 0 && fail_cnt == 0) begin
      fail_cnt++;                      // a run that checked nothing proves nothing
      $error("CHK nothing was checked");
    end
    $display("PASS=%0d FAIL=%0d", pass_cnt, fail_cnt);
  endfunction

  initial begin : main
    string test_name;
    $timeformat(-9, 0, " ns", 0);      // %t prints nanoseconds: "15 ns"
    if (!$value$plusargs("TEST=%s", test_name)) test_name = "all";
    if ($test$plusargs("DUMP")) begin  // waveforms only on request
      $dumpfile("tb_top.vcd");
      $dumpvars(0, tb_top);
    end
    fork
      begin : run
        reset_dut();
        if (test_name == "all") begin
          run_one("smoke");
          run_one("corners");
          run_one("gaps");
        end else begin
          run_one(test_name);
        end
        drain();
      end
      begin : watchdog
        #(TIMEOUT);
        fail_cnt++;                    // a hang is a failure, never a pass
        report();
        $fatal(1, "WDOG test '%s' still running at %t", test_name, $time);
      end
    join_any
    disable fork;                      // main has no other children: only the watchdog
    report();
    $finish;
  end
endmodule
```

**Expected output** of a run with no plusargs. It is illustrative: it was derived from a cycle model of this code, not captured from a simulator, and your simulator adds its own banner and `$finish` lines.

```text

135 ns TEST gaps
PASS=14 FAIL=0
```

The run ends at 250 ns: the last result is checked at 225 ns, `drain()` finds the queue empty at 230 ns, and two quiet edges follow.

### Prove it can fail

1. Change `.BUG(0)` to `.BUG(1)` in `tb_top`: bit 8 of `sum` is now stuck at 0. **Predict** which tests will notice.
2. Run `+TEST=smoke`. The bug escapes:

```text
PASS=3 FAIL=0
```

3. Run `+TEST=corners`. The bench catches the bug. Here `[error @ t]` stands for your simulator's own `$error` prefix, which includes the time, file and line (§20.10):

```text
[error @ 75 ns] CHK a=255 b=1: sum=0, expected 256
[error @ 85 ns] CHK a=255 b=255: sum=254, expected 510
[error @ 95 ns] CHK a=128 b=128: sum=0, expected 256

```

## Push Further

### Expert: X and Z in self-checks (`===` versus `==`)

- **Where X hides.** `==` and `!=` return x only when the relation is ambiguous: the bits that are known agree, and at least one bit is x or z (§11.4.5). `9'b1_0000_101x != 9'd10` is 1, because bit 8 differs, while `9'b0_0000_101x != 9'd10` is x. A `!=` check therefore fails some X results loudly and passes others silently, which is the worst kind of check.
- **Polarity.** An immediate assertion treats x as false and fails (§16.3), so `assert (sum == e.sum)` catches an X result, while `if (sum != e.sum) fail_cnt++;` passes it. Write every check so that an unknown lands on the failing side; `!==` and `===` do that whichever way round you test. Assertions arrive in [I-SV-4A](/curriculum/T2_Intermediate/I-SV-4A_SVA_Fundamentals/index).
- **X in the expectation.** `===` matches x against x. If the model is fed x (an undriven stimulus variable), an X result matches an X expectation and passes. Guard the model: `if ($isunknown(e.sum))` should be a bench error, never a comparison.
- **Wildcards on purpose.** `==?` treats x and z in its right operand as don't-care bits (§11.4.6). Use it when the specification leaves bits undefined, for example `sum ==? 9'b0_0000_1xxx`. An x in the left operand, the DUT's value, is not a wildcard.
- **2-state traps.** Assigning `sum` to an `int` or a `bit` turns x into 0 before any compare. Some simulators are 2-state throughout, so X checks cannot fire on them; run X-sensitive regressions on a 4-state simulator (tool-dependent).
- **Interview angle:** "Why does `assert (a == b)` fail when `a` is x, while `if (a != b) err++;` lets it through?"

### Expert: The cost of directed tests versus constrained-random

- **Counting the cases.** The adder has 256 × 256 = 65,536 input pairs, so exhaustive simulation is affordable: one addition per 10 ns cycle is 655.36 µs of simulated time. Raise `TIMEOUT` first, or the watchdog fires at 10 µs:

```systemverilog
// snippet: an exhaustive directed test for W = 8 (raise TIMEOUT to 1 ms first)
task automatic test_exhaustive();
  for (int i = 0; i < 256; i++) begin
    for (int j = 0; j < 256; j++) begin
      send(i[7:0], j[7:0]);
    end
  end
  idle(1);
endtask
```

- **Where exhaustion ends.** With 16-bit operands there are 2³² (about 4.3 × 10⁹) pairs, about 43 s of simulated time at 10 ns each; with 32-bit operands there are 2⁶⁴ (about 1.8 × 10¹⁹) pairs, far beyond any simulation. Wall-clock time per simulated second depends on the simulator, the design and the machine (tool-dependent).
- **What directed tests buy.** You get exactly the cases you wrote, cheaply, and they are the right tool for bring-up, for known corners such as 255 + 1, and for reproducing a bug. Their cost grows with every feature and corner, and they never find a case nobody imagined.
- **What constrained-random buys.** The bench chooses the values within constraints ([I-SV-2A](/curriculum/T2_Intermediate/I-SV-2A_Constrained_Randomization_Fundamentals/index)). The cost moves into a checker that can predict any input (this bench's model and queue already can) and into functional coverage that measures which cases actually ran ([I-SV-3A](/curriculum/T2_Intermediate/I-SV-3A_Functional_Coverage_Fundamentals/index)). Formal tools can prove properties for every input at once ([E-INT-1](/curriculum/T4_Expert/E-INT-1_Integrating_UVM_with_Formal_Verification/index)).

| | Directed | Constrained-random | Formal |
|---|---|---|---|
| Who picks the cases | you, one by one | the solver, within your constraints | the tool: all cases at once |
| What it needs to be useful | a check per test | a model that predicts any input, plus coverage | properties and assumptions |
| Finds the case nobody imagined | no | often | yes, within the assumptions |
| Typical use | bring-up, corners, bug reproduction | the bulk of block-level regression | control logic, protocols, small arithmetic |

- **Interview angle:** "When would you still write a directed test inside a constrained-random environment?"

### Expert: Race-free sampling, a preview

- **Why this bench's sampling works.** The checker reads `out_valid` and `sum` right after `@(posedge clk)`. That is deterministic only because the DUT writes them with `<=`: the update lands after every process woken by the edge has read them (§4.9.4, §10.4.2). F3C proves it by running every legal order.
- **When it breaks.** The read becomes order-dependent if the RTL writes its flops with `=`, or if an output is combinational logic of inputs that the bench changes with `=` on the same edge. In gate-level simulation with timing, outputs change a propagation delay after the edge instead of in the same time slot, so the delays, not the scheduler, decide what a read at the edge returns; clocking-block input skews (§14.4) make that sampling point an explicit part of the bench.
- **The queue is shared, too.** `send()` pushes and the checker pops on the same edge, in either order. That is safe here: the expectation a result needs was pushed two edges earlier, and `push_back` and `pop_front` work on opposite ends of the queue. Only a result nobody expected can meet an empty queue at that moment, and it fails in either order, just with a different message. `drain()` sidesteps the question by reading the queue on the falling edge.
- **What clocking blocks change.** By default a clocking block samples its inputs with a `1step` skew, which returns the value each signal had before the current time slot began, its Preponed value (§14.3, §14.13); it drives its outputs in the Re-NBA region, after the design's NBA updates (§14.16). This bench's `@(posedge clk); a <= a_val;` becomes `@(cb); cb.a <= a_val;`, and the timing rule moves from code review into a declaration. [F4C](/curriculum/T1_Foundational/F4C_Clocking_Blocks/index) teaches them, together with program blocks (§24.3), another way to separate the bench from the design.
- **Interview angle:** "A monitor reads a DUT output right after `@(posedge clk)`. Does it see the old value or the new one, and what has to be true for that to be guaranteed?"

### Expert: What an in-order queue cannot see

- **Latency.** The queue matches values and order, not timing. A mutant with one extra pipeline stage passes every test on this page. If the specification fixes the latency, add a `time sent;` field to `exp_t`, store `$time` in `send()`, and fail in `check_result()` when `$time - e.sent` differs from 20 ns, the two edges from drive to check.
- **The end of the run.** A result that arrives after the summary is never checked. That is why `drain()` waits for an empty queue and then watches two more edges, so a late or duplicated result still fails.
- **Reordering.** A DUT that may answer out of order (several IDs or channels) needs keyed matching: a queue per key in an associative array ([F2B](/curriculum/T1_Foundational/F2B_Dynamic_Structures/index)), then the scoreboards of [A-UVM-6](/curriculum/T3_Advanced/A-UVM-6_Scoreboards_and_Reference_Models/index).
- **Reset in the middle of traffic.** Expectations for transactions that a reset discards must be flushed, or they are reported as missing; a later module on reset handling and error injection is planned.
- **Equivalent mutants.** Swapping `a` and `b` in the RTL changes the code but never the behaviour, because addition commutes, so no test can kill that mutant. A **mutation score** (killed mutants divided by non-equivalent mutants) measures how much a bench really checks; commercial mutation-analysis tools automate it (tool-dependent).
- **Interview angle:** "Your scoreboard passes, but the designers say latency went from one cycle to two. Why did your bench not catch it, and what would you add?"

### Expert: Pass and fail signals a regression can trust

- **Exit codes.** `$fatal` terminates the simulation "with an error code" (§20.10), but the standard does not define its value, and `$finish` only returns control to the operating system (§20.2). Exit statuses are tool-dependent, so regression scripts decide from the log.
- **The contract.** Exactly one summary line per run. A missing summary (a crash, an early `$fatal`, a killed job) is a failure. Match the whole line, `^PASS=\d+ FAIL=0$`; some simulators prefix every transcript line (for example with `# `), so strip the tool's prefix first (tool-dependent).
- **Errors your counters never see.** A `$error` from an immediate assertion in the RTL, from a vendor model or from someone else's code does not touch `fail_cnt`. Scan the log for the tool's error messages as well, or route every check through one counter. The planned UVM lesson on reporting and pass/fail does the same for UVM's report counts.
- **Seeds.** A directed bench gives the same result on every run. Once stimulus is random, the seed must be in the log so that a failure can be reproduced ([I-SV-2B](/curriculum/T2_Intermediate/I-SV-2B_Advanced_Constrained_Randomization/index)).
- **Interview angle:** "Your regression marked a test as passed because the simulator exited with status 0. What can go wrong?"

### Kata (guided): catch a bug the bench cannot see yet

**Objective:** add a directed test and a check for a rule the bench ignores, plant the bug that breaks the rule, and prove that the bench now catches it.

**The rule:** R4 says that when `in_valid` is 0, `sum` keeps its value. Nothing in the bench checks it, because the checker looks at `sum` only when `out_valid` is 1.

**Steps:**
1. Add mutant 3 to `adder_reg`: change `if (in_valid) sum <= next_sum;` to `if (in_valid || BUG == 3) sum <= next_sum;`, so `sum` also updates on idle cycles. Set `.BUG(3)`.
2. **Predict**, then run with no plusargs. Does the bench notice?
3. Write the plan row: rule R4; scenario: idle cycles that carry new values on `a` and `b`; check: `sum` does not change while `out_valid` is 0; mutant: `BUG=3`.
4. Write the stimulus: a task `send_invalid(a_val, b_val)` that drives `a` and `b` with `in_valid` low for one cycle, and a test `test_hold()` with one valid addition, two such invalid cycles, then `idle(1)`. Register it as `hold` in `run_one()` and in the `all` list.
5. Write the check: in the checker, remember the last result the DUT reported (0 after reset) and fail if `sum` changes while `out_valid` is 0.
6. Run the correct DUT (`.BUG(0)`) with no plusargs and with `+TEST=hold`, then `.BUG(3)` with `+TEST=hold`.

**Acceptance:** with `.BUG(0)` the run with no plusargs ends `PASS=15 FAIL=0` and `+TEST=hold` ends `PASS=1 FAIL=0`; with `.BUG(3)`, `+TEST=hold` reports `FAIL` greater than 0.

**Step 1, the mutant** in `adder_reg`:


**Step 2.** The run ends `PASS=14 FAIL=0`: the bug escapes. No check looks at `sum` on idle cycles, and on idle cycles the existing tests never change `a` or `b`, so recomputing `a + b` gives the same value anyway.

**Step 3, the plan row:**

| Plan row (rule) | Test | Stimulus | The check proves | Mutant it catches |
|---|---|---|---|---|
| R4: `sum` holds while `in_valid` is 0 | `hold` | 3 + 4, then two idle cycles that carry 50 + 60 and 70 + 80 | `sum` stays 7 while `out_valid` is 0 | `sum` updates on idle cycles (`BUG=3`) |

**Step 4, the stimulus and the test** in `tb_top`:

```systemverilog
// snippet: tb_top additions
  // One idle cycle that still carries new data: the DUT must ignore it (R4).
  task automatic send_invalid(input logic [W-1:0] a_val, input logic [W-1:0] b_val);
    @(posedge clk);
    in_valid <= 1'b0;
    a        <= a_val;
    b        <= b_val;
  endtask

  task automatic test_hold();
    send(8'd3, 8'd4);                  // sum becomes 7
    send_invalid(8'd50, 8'd60);        // a correct DUT keeps 7
    send_invalid(8'd70, 8'd80);
    idle(1);
  endtask
```

Add `"hold":    test_hold();` to the `case` in `run_one()`, add `run_one("hold");` after `run_one("gaps");` in the `all` branch of `main`, and add `hold` to the list in the `$fatal` message.

**Step 5, the check** replaces the checker:

```systemverilog
// snippet: tb_top, the checker with the hold check
  logic [W:0] last_sum;                // the last result the DUT reported

  always @(posedge clk) begin
    if (rst_n) begin
      if ($isunknown(out_valid)) begin
        fail_cnt++;
        $error("CHK out_valid is %b after reset", out_valid);
      end else if (out_valid) begin
        check_result(sum);
        last_sum = sum;                // only this process uses last_sum, so = is safe
      end else if (sum !== last_sum) begin   // R4: no new result, so no change
        fail_cnt++;
        $error("CHK sum changed to %0d while out_valid=0 (held %0d)", sum, last_sum);
      end
    end else begin
      last_sum = '0;                   // R1: sum is 0 after reset
    end
  end
```

The result 7 is checked at 45 ns. ### Kata (independent): bench the counter you planned in F1B

**Objective:** build an M0 bench from a specification alone, for a DUT with state.

**The DUT:** `cnt4`, a 4-bit counter (the one from the planning kata in [F1B](/curriculum/T1_Foundational/F1B_The_Verification_Mindset/index)).
