## Quick Take

- **What it is:** The verifier's way of thinking. Assume the design is broken, plan how to show it, check every result against an independent model, and measure honestly how much of the plan you have exercised. A designer asks "how do I make this work?"; a verifier asks "how can this fail, and would my test notice?"
- **Why it matters:** A test that cannot fail proves nothing, and coverage that looks complete can hide features nobody checked. These habits decide whether the verification effort you met in F1A finds bugs or only produces green results.
- **The Analogy:** A designer builds a bridge to carry 10 tons. A verifier asks about 10.001 tons, about 10 tons during an earthquake, and about the wrong grade of steel. *Where it breaks:* a bridge has a handful of load cases, while a chip's inputs form billions of sequences. Imagination is not enough: a verifier needs a written plan, automatic checks and measurements.

**You will be able to:**
1. Explain why a self-checking test must be able to fail, and prove it by injecting a bug and watching the check fire.
2. Compare directed, constrained-random and formal verification by strength, cost and fit, and choose a method or a mix for a given scenario.
3. Evaluate a "100% coverage" claim: tell code coverage (statement, branch, condition or expression, toggle, finite state machine) from functional coverage, and explain why neither alone means "done".
4. Write a feature-level verification-plan row (feature, scenario, check, coverage item, method) for a small block from a spec excerpt.
5. Debug a check that can never fail: a vacuous antecedent, a tautology, a `cover` used where `assert` was meant, or a compare that is blind to X.

## Build Your Mental Model

### The words you need

Every testbench, from a 30-line module to a full UVM (Universal Verification Methodology, introduced in F1C) environment, has the same parts:

- **DUT (design under test):** the design being verified. IEEE 1800.2-2020 §3.2 and IEEE 1800-2023 §14.2 expand DUT as "device under test"; both names mean the same thing.
- **Testbench (TB):** everything that verifies the DUT. It applies inputs, watches outputs and decides pass or fail. IEEE 1800.2-2020 §3.1 also calls it the verification environment.
- **Stimulus:** the input values and sequences the testbench applies.
- **Reference model:** code that computes what the spec says the DUT should produce, written independently of the RTL.
- **Checker:** code that compares the DUT's actual output with the expected value and reports a mismatch. This is not the SystemVerilog `checker` construct, a language feature for packaging assertions (IEEE 1800-2023 Clause 17).
- **Scoreboard:** a checker for whole transactions. IEEE 1800.2-2020 §3.1 defines it as the mechanism that predicts the design's response and checks the observed response against the prediction.
- **Coverage:** a measurement of what the stimulus exercised. IEEE 1800-2023 §19.2 defines coverage as the percentage of verification objectives that have been met. It records what happened; it never decides pass or fail.

### Constructive vs destructive thinking

The most important tool in verification is not a language; it is a mindset.

- **Designers think constructively.** They build paths for data to flow and ask, "How do I make this work?"
- **Verifiers think destructively.** They look for cracks and ask, "How can I make this fail?"

When you are handed any feature or block, ask these six questions in order:

1. **What is the normal operation?** Understand the intended path first.
2. **What are the boundary values?** Minimum, maximum and one past the maximum.
3. **What happens on illegal inputs?** Should the design ignore them, flag them or recover?
4. **What are the concurrent interactions?** What if two features fire in the same cycle?
5. **What are the reset and power-on behaviours?** Does the block come up clean, and does reset work in the middle of activity?
6. **What does the spec not say?** Unspecified behaviour is where bugs breed.

### A test must be able to fail

A **self-checking test** compares every output with an expected value from a reference model and counts failures, so nobody has to read waveforms to know whether it passed. Its check is only worth something if it **can fail**: if the design were wrong, the test would say so. A green result from a check that cannot fail is the most dangerous output a testbench can produce.

> [!NOTE]
> **How to read the assertions on this page.** [I-SV-4A](/curriculum/T2_Intermediate/I-SV-4A_SVA_Fundamentals/index) teaches the full syntax; four pieces are enough here.
> - `assert property (@(posedge clk) A |-> B)`: at every rising edge of `clk` where `A` is true, `B` must be true **at that same edge**.
> - `A |=> B`: at every edge where `A` is true, `B` must be true **at the next rising edge**.
> - `disable iff (rst)`: while `rst` is 1, attempts are disabled, so reset cannot cause failures.
> - `cover property (A)`: counts the edges where `A` matches; it never fails.
>
> To try `|->` and `|=>` on a trace you can edit, open the [SVA Trace Lab](/practice/visualizations/assertion-builder).

<details>
<summary>Edge by edge</summary>

The two checks are `assert property (@(posedge clk) disable iff (rst) count == 3'd2 |-> count == 3'd3)` and the same with `|=>`, one marker per edge. As in the bug hunt, `rst` changes away from the clock edges, so `disable iff` sees the value drawn at each edge.

1. **Edge 0 (⊘):** `rst` is 1, so both attempts are disabled: neither a success nor a failure.
2. **Edge 3 (✕):** `count` is 2, so the antecedent matches. `|->` checks `count == 3` at edge 3 itself and fails, because `count` cannot be 2 and 3 at once: a false alarm on a correct design.
3. **Edge 4 (✓):** `|=>` checks `count == 3` at edge 4, where `count` is 3, and passes.
4. **Edges 1, 2 and 5 (○):** the antecedent is false, as it is for the attempts that start at edge 4: vacuous successes, which card 2 below explains. `cover property (@(posedge clk) count == 3'd2)` would count one match, at edge 3: the `cover` row.

</details>

Now be the verifier. The designer has handed you a 3-bit up counter and a one-line spec. Work in this order:
1. Compare the spec with the waveform before you look at the code, and find the first edge that is wrong.
2. Find the line of RTL that caused it.
3. Before you choose an assertion, predict which of the offered ones can never fail on this counter, and why. Then pick the one that would have caught the bug.
4. Ask whether a check that never fails ever ran: predict how many nonvacuous successes it collects, then read its tally of nonvacuous successes, vacuous successes, failures and attempts disabled by `rst`.

<FirstBugHuntGame />

What the hunt showed. The game's model scores each assertion over its 12 edges, with `rst` high at edge 0; the first three carry `disable iff (rst)`. ✓ is a nonvacuous success, ○ a vacuous success, ⊘ an attempt disabled by `rst`, ✕ a failure:

| Assertion | Buggy counter (wraps at 6) | Fixed counter |
|---|---|---|
| `count == 3'd6 \|=> count == 3'd7` | ✕ fails at edge 8 | ✓ 1 nonvacuous success; never fails |
| `count == 3'd7 \|=> count == 3'd0` | ○ never fails, and never checks: 0 nonvacuous successes (11 vacuous, 1 ⊘) | ✓ 1 nonvacuous success; never fails |
| `count <= 3'd7` | ✓ 11 nonvacuous successes; never fails | ✓ 11 nonvacuous successes; never fails |
| `count == 3'd6 \|-> count == 3'd7` | ✕ fails at edge 7 | ✕ fails at edge 7 |

Read the tally and the failures together. Zero nonvacuous successes and zero failures mean a check never ran (a cover on its antecedent reads 0). Many nonvacuous successes still do not prove that a check can fail: a property that is a plain sequence, such as the boolean `count <= 3'd7`, is always nonvacuous (§16.14.8), yet it holds on every design whose `count` is known. Only a design that breaks the rule can show that a check can fail.

- **The debug workflow** is always the same: spec, then the first divergent sample, then the line that caused it, then a check that would have failed. Debug from the first divergence: every later value is wrong too, but only the first one points at the cause.
- **Two of the four assertions can never fail** on the buggy counter. The wrap check `count == 3'd7 |=> count == 3'd0` never fails: every attempt that `rst` does not disable is a vacuous success, because the counter never reaches 7. `count <= 3'd7` is a tautology.
- **One assertion is a false alarm:** `count == 3'd6 |-> count == 3'd7` checks the same cycle, so it fails even on a correct counter.
- **Only `count == 3'd6 |=> count == 3'd7`** fails on the bug and stays silent on the fix. "Apply the fix" is the mutation idea in reverse: a good check separates the broken design from the fixed one.

### Directed, constrained-random and formal

There are three ways to look for bugs, and each explores a different part of the design's behaviour:

1. **Directed testing.** You write each scenario by hand.
   - Strengths: easy to write, deterministic, easy to debug. Ideal for bring-up, smoke tests and specific protocol sequences.
   - Weaknesses: you only find the bugs you can imagine, and the number of tests does not scale.
2. **Constrained-random verification (CRV).** You write the rules (**constraints**) and a solver generates legal scenarios, a new set for every random **seed**. Functional coverage then shows which scenarios actually happened.
   - Strengths: finds bugs nobody imagined. One test samples a huge space of legal scenarios.
   - Weaknesses: harder to debug (you reproduce a failure with its seed), and it needs checking and coverage infrastructure before it is useful. It samples the space; it does not exhaust it.
3. **Formal verification.** A tool explores every reachable state to prove that a property (written as an assertion) always holds, or returns a **counterexample**: a short trace that breaks it.
   - Strengths: exhaustive within its assumptions, so it finds corner cases simulation rarely reaches.
   - Weaknesses: a proof holds only under its input assumptions, and an over-constrained assumption hides real bugs. Large designs can exceed tool capacity, so a run can end with a bounded or inconclusive result (tool-dependent).

To see what each method explores, take a counter slightly bigger than the bug hunt's. It has a synchronous reset, an increment enable `en`, and a load `ld` with data `d`: `count` becomes `d` when `ld` is 1 (load wins), otherwise `count + 1` when `en` is 1, otherwise it holds. The bug: when `ld` and `en` are both 1 while `count` is 7, the RTL increments to 0 instead of loading `d`. If `d` happens to be 0 the bug is invisible, because 7 + 1 also wraps to 0.

<details>
<summary>Edge by edge: how the bug shows up</summary>

1. **Edge 0:** `rst` is 1, so both rows read 0 at edge 1.
2. **Edge 1:** `ld` is 1 with `d` = 7, so both read 7 at edge 2.
3. **Edge 2 (●):** `count` is 7, `ld` and `en` are both 1, and `d` is 3. The spec loads 3; the RTL increments 7 to 0.
4. **Edge 3 (✕):** `count` is 0 where 3 was expected, the first divergence. With `ld` and `en` low the counter holds, so edge 4 still disagrees.

With `d` = 0 at edge 2, both rows would read 0 and the bug would stay hidden.

</details>

The three directed tests a busy engineer might write are: count from 0 through the wrap back to 0; load 5 right after reset, then count on; and hold with `en` low right after reset. The random test draws `en` high half the time, `ld` high one cycle in ten, and `d` uniformly.

Two points from the tour matter later:
- **Emulation runs the RTL**, compiled onto hardware, so it belongs to pre-silicon work. That is why it answers the diagram's question: simulation is too slow to boot an operating system on a full chip, and lab validation needs chips that do not exist before tape-out. - **Equivalence checking runs after synthesis.** It proves that the gate-level netlist matches the RTL. It cannot tell you whether the RTL itself is right.

### How the methods combine

No single method is enough. Here is how a team would split the verification of a 4-requester arbiter:
- **Formal:** prove mutual exclusion (never two grants in one cycle) and no starvation (every request is eventually granted), under assumptions that match how the real requesters behave.
- **Constrained-random simulation:** run long, mixed request patterns with back-pressure. A scoreboard checks every grant against a model; coverage shows which request patterns and grant orders happened.
- **Directed tests:** bring the block up with a single request, then all four at once, and check reset behaviour.

| Method | Strengths | Weaknesses | Typical cost | Ideal for |
|---|---|---|---|---|
| Directed | Deterministic, easy debug | Only what you imagine; does not scale | Low to start; grows with every test you write | Bring-up, smoke tests, specific sequences |
| Constrained-random | Finds unexpected bugs; one test, many scenarios | Harder debug; needs checks and coverage first | High setup; then mostly compute time | Bulk regression of data paths and protocols |
| Formal | Exhaustive within its assumptions | Capacity limits; assumptions can hide bugs | Specialist skills and tool licences; cheap per property on small blocks | Control logic, arbiters, protocol rules, deadlock freedom |

The cost column describes typical practice; it is not measured data.

> [!IMPORTANT]
> **A common interview mistake:** "I'd use constrained random for everything." A strong answer says which method answers which question. Formal proves properties of blocks, directed tests check specific sequences, and constrained-random simulation explores the space between them.

Now sort each job into the method that answers it best. Some of it looks ahead: the CDC and power-aware bins, and the last three cards, come from the coverage closure trap and the bug taxonomy later in this lesson.

### Coverage: measuring what you exercised

IEEE 1800-2023 §19.2 describes two kinds of coverage. **Code coverage** is extracted automatically from the design code. **Functional coverage** is user-defined: it measures how much of the design specification, as listed by features in the test plan, has been exercised. Both measure; neither checks. A test with 100% coverage and a disabled compare proves nothing.

| Question | Code coverage | Functional coverage |
|---|---|---|
| Where does it come from? | Extracted automatically from the design code (§19.2) | Written by you, from the features in the test plan (§19.2) |
| What does it see? | Which statements, branches, conditions, bits and FSM states of the RTL were exercised | Which planned features, scenarios and corner cases happened |
| What is it blind to? | Behaviour that has no code, such as a missing handler | Features missing from the plan, and plan items nobody wrote a coverage item for |
| Who defines the metric? | §40.2.2 defines statement, toggle and FSM coverage; branch and condition coverage are tool-defined | You do, with covergroups ([I-SV-3A](/curriculum/T2_Intermediate/I-SV-3A_Functional_Coverage_Fundamentals/index)) and `cover property` statements |
| What does it cost up front? | Nothing to write: the tool extracts it | Someone has to write the coverage model (§19.2) |
| Does it decide pass or fail? | No: it records what ran | No: it records what happened |

The code-coverage metrics you will meet:

| Metric | What it counts | What it misses |
|---|---|---|
| Statement (line) | Each statement executed at least once | Whether the result was right; behaviour that has no code |
| Branch | Each branch of an `if` or `case` taken | Combinations of conditions |
| Condition or expression | Each operand of a condition seen true and false | Whether the outcome was right |
| Toggle | Each bit seen at both 0 and 1 | When and why it changed |
| FSM (finite state machine) | The states reached and transitions taken | States and transitions the RTL never encodes |

IEEE 1800-2023 §40.2.1 requires a tool's coverage interface to support at least statement, toggle, FSM (states and transitions) and assertion coverage, and §40.2.2 defines statement, toggle and FSM coverage. Branch and condition coverage are defined by each tool.

Here is a coverage report for the Make It Work run, traced by hand. Read it before the bench: it is the picture of what code coverage can and cannot see.

```text

(traced by hand; real report formats are tool-dependent)
hits  line

   1    if (rst)                   count <= '0;
   2    else if (count == WRAP_AT) count <= '0;
  17    else                       count <= count + 3'd1;

  reset to 0 ............  1   (only at the first edge)
  increment ............. 17
  wrap 7 -> 0 ...........  2

  checks with !== ....... 20
```

Every line and branch ran, yet one planned feature, reset in the middle of counting, was never exercised. The reset branch counts as covered because of the reset at the first edge. Code coverage cannot tell the two situations apart; the plan can. (Under §40.2.2, `rst` counts as toggled because it was seen at 1 and at 0. Tools that count 0-to-1 and 1-to-0 transitions may report it as only partly toggled.)

**A war story (composite).** A team reached 100% code coverage on a one-hot state machine (one flip-flop per state, exactly one set at a time), and the chip taped out. In the lab, the state machine occasionally held two set bits. The cause was two next-state conditions that could be true in the same cycle, so the RTL set two bits at once; no test happened to make both conditions true together. Code coverage measures the code that exists, and there was no illegal-state handler, so there was nothing to cover. One concurrent assertion would have flagged the state the moment any simulation produced it:

```systemverilog
// snippet
a_state_onehot: assert property (@(posedge clk) disable iff (!rst_n) $onehot(state));
```

`$onehot` is a built-in system function (IEEE 1800-2023 §20.9), the assertion's clock is `@(posedge clk)`, and `disable iff (!rst_n)` stops it firing on the unknown state before reset. A formal tool, which explores every reachable state, would also have shown how to reach it. Had the cause been an unsynchronized asynchronous input instead, RTL simulation would not show it at all: that is the job of clock-domain-crossing (CDC) analysis.

The lesson: code coverage tells you what code ran. Assertions and scoreboards check the intended behaviour; functional coverage shows whether the planned scenarios happened.

The **coverage closure trap** is coverage that looks closed while proving little:
- bins hit while the checks were off or vacuous, so they were counted but nothing was checked;
- holes waived without review;
- a coverage model that misses items in the plan, so 100% means 100% of an incomplete model;
- more seeds of the same random stimulus thrown at a plateau, instead of a targeted test or formal.

The guards: review the coverage model against the plan, count coverage only from runs whose checks are live (and proven able to fail), review every waiver with a reason, and close rare bins with targeted stimulus or formal.

### From spec to plan

A **verification plan (vplan)** turns each feature in the spec into rows. Each row has five fields:

| Field | Question it answers | Example for the counter's wrap |
|---|---|---|
| Feature | What does the spec promise? | 7 wraps to 0 |
| Scenario | What stimulus exercises it? | Run at least 9 cycles after reset |
| Check | What decides pass or fail? | Compare `count` with the model every cycle |
| Coverage item | How do we know it happened? | The 7-to-0 transition was seen |
| Method | Directed, random or formal? | Directed |

A row is complete when it can fail: it names a check, not just a scenario, and its coverage item proves the scenario ran. Make It Work writes the full plan for the counter. Linking each plan row to coverage, so every bin traces back to a feature, is taught in [I-SV-3B: linking coverage to the plan](/curriculum/T2_Intermediate/I-SV-3B_Advanced_Functional_Coverage/linking-coverage).

### Bug taxonomy

Naming the kind of bug tells you which method is most likely to catch it:

| Category | Example | Typical detection |
|---|---|---|
| Functional | Wrong ALU output for specific operands | Scoreboard against a reference model |
| Protocol | An AXI (Arm AMBA bus) VALID that drops before READY (IHI0022E §A3.2.1 requires VALID to stay asserted until the handshake) | SystemVerilog Assertions (SVA) on the protocol rules |
| Corner case | FIFO overflow on a simultaneous read and write while full | Constrained random plus functional coverage |
| Reset | A register that does not return to its specified reset value | Register reset tests with a register abstraction layer (RAL, taught in [A-UVM-4A](/curriculum/T3_Advanced/A-UVM-4A_RAL_Fundamentals/index)) |
| Clock domain | Metastability on an asynchronous FIFO pointer crossing | CDC structural analysis and formal |
| Performance | Arbiter starvation under heavy load | Performance counters plus assertions |
| Power | A retention register corrupted after power-down | Power-aware simulation driven by a power-intent file in UPF (Unified Power Format, IEEE 1801) |

Severity belongs to each bug, not to its category: any category can be critical in the wrong product.

### Recap

- A test must be able to fail. Prove it with a deliberate bug, and watch for the four silent failures: a missing compare, a vacuous antecedent, a tautology or `cover`, and an X-blind `!=`.
- Directed tests find what you imagine, random stimulus finds what is probable, and formal finds what is possible within its assumptions. Real projects combine them.
- Coverage measures; only checks decide. Code coverage cannot see missing features, and functional coverage is only as complete as the plan.
- A plan row names a feature, a scenario, a check, a coverage item and a method.

## Make It Work

### Worked example: plan the counter, then prove the check can fail

**Step 1: the plan.** Five rows for the bug-hunt counter. The last column traces each row to the bench below; one row is deliberately not in the bench yet.

| Plan row | Scenario | Check | Coverage item | In the bench below |
|---|---|---|---|---|
| Reset to 0 | `rst` high at the first edge | First check expects 0 | Reset seen | `rst` starts at 1; `expected` starts at 0 |
| Increment | Count for 20 cycles | `count` equals the model every cycle | Increments checked | The `repeat (20)` loop and the `!==` compare |
| Wrap 7 to 0 | Run at least 9 cycles after reset | The cycle after 7 shows 0 | `seen_max` greater than 0 | `expected + 3'd1` wraps; `seen_max` counts the 7s |
| Reset mid-count | Assert `rst` while counting | `count` is 0 on the next cycle | Reset seen at a nonzero count | **Not in this bench yet:** a known hole the kata fills |
| No X after reset | Every check after reset | `!==` fails on X | All checks | `count !== expected` |

**Step 2: the bench.** This is a preview: read it now, and you will write your own in [F2E](/curriculum/T1_Foundational/F2E_First_Self_Checking_Testbench/index) after F2A to F2D teach the syntax. The comments say why each line is there.

```systemverilog
// compile
`timescale 1ns/1ps

// DUT: the bug-hunt counter. The wrap value is a parameter only so that a bug
// can be injected from the testbench without editing the RTL.
module up_counter #(parameter int WRAP_AT = 7) (
  input  logic       clk,
  input  logic       rst,      // synchronous, active-high
  output logic [2:0] count
);
  always_ff @(posedge clk) begin
    if (rst)                   count <= '0;
    else if (count == WRAP_AT) count <= '0;
    else                       count <= count + 3'd1;
  end
endmodule

module tb_top;
  logic       clk = 1'b0;
  logic       rst = 1'b1;
  logic [2:0] count;
  logic [2:0] expected;          // reference model: what the spec says count is
  int         pass_cnt = 0;
  int         fail_cnt = 0;
  int         seen_max = 0;      // coverage: how many checks saw count == 7

  // Mutant: change WRAP_AT(7) to WRAP_AT(6) and rerun. The test must fail.
  up_counter #(.WRAP_AT(7)) dut (.clk(clk), .rst(rst), .count(count));

  always #5 clk = ~clk;

  initial begin
    @(posedge clk);              // the DUT samples rst = 1 at this edge
    rst <= 1'b0;                 // nonblocking: released after the edge, so no race
    expected = 3'd0;
    repeat (20) begin
      @(negedge clk);            // check mid-cycle, when count is stable
      if (count === 3'd7) seen_max++;
      if (count !== expected) begin  // !== so an X can never pass
        fail_cnt++;
        $error("count=%0d expected=%0d", count, expected);
      end else begin
        pass_cnt++;
      end
      expected = expected + 3'd1;    // 3-bit add: 7 + 1 wraps to 0, as the spec says
    end
    $display("PASS=%0d FAIL=%0d", pass_cnt, fail_cnt);
    $display("COVERAGE seen_max=%0d", seen_max);
    $finish;
  end
endmodule
```

Expected output (traced by hand and with a cycle model; not from a simulator run):

```text

COVERAGE seen_max=2
```

In the diagram that is check 7 (shaded): the model expects 7, but the mutant has already wrapped to 0. Checks 12 to 19, not drawn, fail the same way, as the log shows. Coverage agrees from a different angle: `seen_max=0` says the wrap scenario never happened, because 7 never appears in `count`. `$error` reports and lets the run continue, so you see every failure. A real simulator adds its own prefix to each `$error` line, with the severity, file, line, scope and time; that format is tool-specific (IEEE 1800-2023 §20.10).

**How to do it on any block:**
1. Write the plan row: feature, scenario, check, coverage item, method.
2. Write the check against a model, never against a copy of the DUT's own output.
3. Run the test and see PASS.
4. Inject the bug the row is meant to catch, rerun, and see FAIL.
5. Revert the mutant and rerun to see PASS again.
6. Record which row caught the mutant, and look for plan rows whose coverage is still 0.

To run it, compile both modules with an IEEE 1800-compliant simulator and make `tb_top` the top module. The exact commands are tool-dependent.

**Checklist before moving on:**
- [ ] Every row of my plan has a scenario, a check and a coverage item.
- [ ] I have seen my check fail on a mutant, and pass again after reverting it.
- [ ] I compare with `!==`, so an X output fails.
- [ ] I can name four ways a check never fails.
- [ ] I can say which plan row this bench does not exercise yet.

## Push Further

### Expert: `$onehot` and X

- `$onehot(e)` returns 1 when `$countbits(e, '1) == 1` (IEEE 1800-2023 §20.9). It counts only bits that are 1, so a vector with one 1 and some X bits, such as `4'b01x0`, passes.
- An all-X state, before reset, has no bits at 1, so `$onehot` is false there. An ungated assertion fires at every edge before reset; gate it with `disable iff`.
- When X must fail too, add `!$isunknown(state)`. §20.9 itself shows a one-hot check built from `$countones(v) == 1` and `$countbits(v, 'x, 'z) == 0` for the same reason.
- `$onehot` returns type `bit`, so it never returns X itself.

Traced on four values of a 4-bit `state` (§20.9):

| `state` | `$onehot(state)` | `$onehot(state) && !$isunknown(state)` |
|---|---|---|
| `4'b0100` | 1: exactly one bit is 1 | 1 |
| `4'b0110` | 0: two bits are 1 | 0 |
| `4'b01x0` | 1: one bit is 1, and the X is not counted | 0: `$isunknown` is 1 |
| `4'bxxxx` (before reset) | 0: no bit is 1 | 0 |

```systemverilog
// snippet
a_state_onehot_known: assert property (@(posedge clk) disable iff (!rst_n)
  $onehot(state) && !$isunknown(state));
```

### Expert: Vacuity in practice

- An implication with no antecedent match succeeds (§16.12.7), and that vacuous success is neither a pass nor a failure (§16.14.8). §16.14.8 also notes that vacuous success on every attempt may indicate a problem in the design or in the property.
- A `cover property` reports the number of times the property succeeded because of vacuity, alongside attempts and successes (§16.14.3).
- By default the pass action of an assertion also runs on vacuous success. `$assertvacuousoff` stops that, and none of the action-control tasks changes the assertion statistics (§20.11).
- How a simulator lists vacuous successes in logs and coverage reports is tool-dependent.
- Practice: give every important implication a `cover property` on its antecedent, and review the "never triggered" list before sign-off.

The four ways one attempt can end, with the glyphs the bug hunt uses:

| Attempt ends as | What happened | Action block, by default | In `cover property` results (§16.14.3) |
|---|---|---|---|
| ✓ Nonvacuous success | The antecedent matched and the consequent held: a pass | Pass statements (§16.14.1) | Counted as succeeded |
| ○ Vacuous success | The antecedent did not match, so the consequent was never checked (§16.12.7): neither a pass nor a failure (§16.14.8) | Pass statements too, unless `$assertvacuousoff` stops them (§20.11) | Counted as succeeded because of vacuity |
| ✕ Failure | The antecedent matched and the consequent did not hold | Fail statements, or `$error` when there is no `else` (§16.14.1) | Counted as attempted only |
| ⊘ Disabled | The `disable iff` condition was true during the attempt: no success or failure (§16.12) | None (§16.14.1) | Counted as attempted only |

### Expert: A proof is only as good as its assumptions

- For formal analysis, `assume` properties are hypotheses: a formal tool is not obliged to verify that they hold. A simulator must check them and report failures, like assertions (§16.14.2, §16.2).
- A `restrict` property constrains formal analysis only; simulators do not check it (§16.2).
- Over-constraint hides bugs. In the methods figure, assuming `!(ld && en)` made the proof pass with the bug inside.
- Two guards: write `cover` properties for scenarios that must stay reachable and confirm the tool can still cover them under the assumptions; and run the same assumptions as checks in simulation, where a violation shows an environment that breaks them.
- Bounded proofs, inconclusive results and capacity limits are tool-dependent. [E-INT-1](/curriculum/T4_Expert/E-INT-1_Integrating_UVM_with_Formal_Verification/index) covers formal flows next to UVM.

The four assertion statements side by side:

| Statement | In simulation | In formal analysis |
|---|---|---|
| `assert` | Checked: a failure runs the fail statements (§16.14.1) | An obligation to verify (§16.2): proved, or a counterexample |
| `assume` | Checked and reported if it fails, like an assertion (§16.14.2) | A hypothesis that constrains the inputs; the tool need not verify it (§16.2, §16.14.2) |
| `cover` | Counts attempts, successes and vacuous successes; never fails (§16.14.3) | Monitors the property for coverage (§16.2): the reachability guard against over-constraint above; how tools report it is tool-dependent |
| `restrict` | Not checked (§16.2) | A constraint on the analysis (§16.2) |

### Expert: Qualifying the testbench

- Who checks the checker? **Mutation testing**: inject one deliberate bug per plan row, as `WRAP_AT(6)` did, and confirm some check fails. A mutant that survives points at a missing or weak check.
- Keep a small set of mutants in the regression, so a later change that silently disables a check is caught.
- A scoreboard must also report what it never matched: items still pending at the end of the test are failures, not passes ([A-UVM-6](/curriculum/T3_Advanced/A-UVM-6_Scoreboards_and_Reference_Models/index)).
- Commercial mutation-analysis tools automate mutant generation; what they support is tool-dependent.

### Expert: Coverage at sign-off

- Coverage from many tests and seeds is merged into one database before sign-off. IEEE 1800-2023 §40.3.2 provides system functions such as `$coverage_merge` and `$coverage_save`, but how a tool merges and stores coverage is tool-dependent.
- Every exclusion or waiver is reviewed and carries a reason. A waived bin is a decision, not a fix.
- The coverage model itself is reviewed against the plan, because 100% of an incomplete model is the commonest false closure.
- Code coverage (§40.2.2 metrics plus each tool's branch and condition metrics) is read alongside functional coverage: an unexercised line is a question to answer, not a number to push.

### Kata: plan a 4-bit counter

Write a verification plan for this spec excerpt. Aim for at least six rows. For each row, also name a **mutant**: a small deliberate bug that only that row's check would catch.

> `cnt4` has a 4-bit output `count`. A synchronous, active-low reset `rst_n` sets `count` to 0. A synchronous load `ld` loads `d[3:0]` and has priority over the increment enable `en`. With `en` high and `ld` low, `count` increases by 1 and wraps from 15 to 0. With both low, `count` holds.

<details>
<summary>Worked solution</summary>

| Feature | Scenario | Check | Coverage item | Method | Mutant it catches |
|---|---|---|---|---|---|
| Reset | Pull `rst_n` low in the middle of counting | `count` is 0 on the next edge | Reset seen at a nonzero count | Directed | Reset clears only bit 0 |
| Increment | `en` high from every value 0 to 14 | `count` equals the previous value + 1 | Every value 0 to 14 seen with `en` high | Random | Adds 2 at odd values |
| Hold | `en` and `ld` low | `count` unchanged | Hold seen at several values | Random | Ignores `en` and counts anyway |
| Load | `ld` high with every `d` | `count` equals `d` on the next edge | Every `d` value loaded | Random | Ignores `d[3]` |
| Load priority | `ld` and `en` high together, including at 15 | `count` equals `d`, not the increment | `ld` with `en` seen, including at 15 | Directed and random | Increment wins over load |
| Wrap | Count up to 15 with `en` high | 15 is followed by 0 | The 15-to-0 transition seen | Directed | Saturates: holds at 15 |
| Reset priority (expert row) | `rst_n` low while `ld` is high | `count` is 0, not `d` | Reset seen with `ld` high | Directed | Load wins over reset |

Two habits to notice. Every check compares with a model written from the spec, never with the DUT's own output. And the load-priority row is the one a hand-written test list usually forgets, which is exactly where the methods figure's bug lived.

One mutant is easy to file under the wrong row. A counter that wraps at 14 never reaches 15 by counting, so the Wrap row's check never triggers: every attempt is a vacuous success, which counts as neither a pass nor a failure (§16.14.8), and only its coverage item, still at 0, shows the hole. The Increment row catches it, because 14 is followed by 0 instead of 15. F2E builds the bench for a plan like this one.

</details>

### Debug challenge: which checks can never fail?

All of these run against the bug hunt's buggy counter (it wraps at 6). Which ones can never fail on it, and why? One of them is a good check.

1. `assert property (@(posedge clk) disable iff (rst) count == 3'd7 |=> count == 3'd0);`
2. `assert property (@(posedge clk) disable iff (rst) count <= 3'd7);`
3. `cover property (@(posedge clk) count == 3'd7);`
4. `if (count != expected) fail_cnt++;` in a testbench, with `count` stuck at X
5. `assert property (@(posedge clk) disable iff (rst) count == 3'd6 |=> count == 3'd7);`

<details>
<summary>Worked solution</summary>

1. **Never fails: vacuous.** The counter never reaches 7, so the antecedent never matches and every attempt that `rst` does not disable is a vacuous success (§16.12.7, §16.14.8). A cover on `count == 3'd7` would show 0 hits.
2. **Never fails: a tautology.** A 3-bit value is at most 7 whenever it is known, so the property checks nothing. Without the `disable iff (rst)` gate it would fire only on the unknown value before reset: an X compared with `<=` gives x, and an assertion treats x as false (§11.4.4, §16.6).
3. **Never fails: it is a cover.** A cover counts matches; it reports 0 here, which is useful information, but it never fails.
4. **Never fails: X-blind.** `!=` gives `1'bx` when `count` is X (§11.4.5), and the `if` skips its statement (§12.4). Use `!==`.
5. **Fails, correctly.** `count` is 6 at one edge and 0 instead of 7 at the next, so the assertion fails exactly where the bug is, and it stays silent on the fixed counter.

</details>
