## Quick Take

- **What it is:** Three kinds of **unpacked array** whose size changes while the simulation runs (IEEE 1800-2023 §7.5, §7.10, §7.8). A **dynamic array** (`int a[]`) is sized by `new[N]` or by assigning a whole array to it. A **queue** (`int q[$]`) grows and shrinks at either end, and a bound (`int q[$:7]`) caps its size. An **associative array** (`int aa[string]`) holds an entry only for each key you write, and keeps the entries in key order.
- **Why it matters:** Testbench data rarely has a size you know when you compile: stimulus lists, requests still waiting for a response, sparse memories, results by ID. The wrong container wastes memory, hides ordering bugs or turns every lookup into a search. The bugs are quiet: a wiped array prints nothing, and a dropped queue entry or a missing-key read prints one warning that is easy to miss in a long log.
- **The Analogy:** A dynamic array is a tray of numbered slots that you swap for a new tray (`new[N]`) instead of stretching it. A queue is a conveyor belt, optionally with an end stop. An associative array is a filing cabinet with a drawer only for each label you have used, kept in label order. *Where it breaks:* the end stop holds nothing back. Whatever does not fit falls off, and after `push_front` the item that falls off is the old last one, not the new one. The cabinet files by character code, so `"Gamma"` comes before `"alpha"`, and class-handle labels have no meaningful order at all.

### Choose the right structure

Every container answers one question: how will the testbench find an element again? By a position fixed when you compile, by a position fixed at run time, by arrival order, or by a key. A **fixed-size array** covers the first case and belongs to [F2A](/curriculum/T1_Foundational/F2A_Core_Data_Types/index), together with packed and unpacked dimensions. This lesson covers the three kinds whose size changes at run time.

The same choices as testbench jobs:

| Testbench job | Best choice | Why | Avoid |
|---|---|---|---|
| Register file, or a lane count fixed at compile time | **Fixed-size array** `int lane_err [4]` | No allocation; the size is checked when you compile | A dynamic array, which adds a `new[]` for nothing |
| Per-lane results, lane count read at run time | **Dynamic array**, `new[n_lanes]` once | Every index exists at once, so you can write lanes in any order | A queue: a write past `q[$+1]` is ignored, so you must fill it in order |
| Stimulus list, monitor output, a burst of unknown length | **Queue** `[$]` | Keeps arrival order; `push_back` and `pop_front` | A dynamic array: no `push_back`, and growing means `new[n+1](arr)` each time |
| FIFO of fixed depth in a model | **Bounded queue** `[$:DEPTH-1]` plus your own `size()` check | The depth is part of the declaration | Trusting the bound to apply backpressure: it discards |
| Expected data by transaction ID, one outstanding per ID | **Associative array** `exp[int]` | Keyed lookup, `exists()`, cleanup with `delete(id)` | A queue searched with `find_first_index`: a linear scan per lookup |
| Several outstanding per ID, in order within each ID | **Associative array of queues** `exp_by_id[int][$]` | The key finds the ID; the queue keeps its order | One entry per ID: the second request overwrites the first |
| Memory model over a 32-bit address space | **Associative array** `mem[bit [31:0]]` | Only written addresses use memory | A dynamic or fixed array with 2³² entries |
| Lookup table by name | **Associative array** with an enum index, or `[string]` | Self-documenting keys | A string key where an enum would do: a mistyped string is just another key |

Three choices that look right and are not:

- **A queue used as a lookup table.** `find_first_index` scans the queue on every call, so a checker that searches per response gets slower as the queue grows. Key the data by ID instead.
- **A string key where an enum would do.** A mistyped string is a different key: a write creates a new entry and a read returns the default with a warning. With an enum index type (`int count[state_e]`), a mistyped name does not compile.
- **A queue shared by two threads.** A queue never blocks, so you write the waiting yourself. A mailbox blocks `get()` for you, and a bounded mailbox also blocks a producer when it is full ([I-SV-5: mailboxes](/curriculum/T2_Intermediate/I-SV-5_Synchronization_and_IPC/mailboxes)).

**Table 7-1** is the LRM's list of what a read of a nonexistent element returns (§7.4.5); this page calls that result the *missing-element value*:

| Element type | What a read of a nonexistent element returns (Table 7-1, §7.4.5) |
|---|---|
| 4-state integral (`logic`, `integer`, …) | `'x` |
| 2-state integral (`bit`, `int`, `byte`, …) | `'0` |
| Class handle | `null` |
| `string` | `""` |
| Variable-size array element (dynamic, queue, associative) | An empty array (which is why a missing `exp_by_id[id]` reads as an empty queue) |

What the lab should have taught you:

- `arr = new[N]` is a fresh array. Every element restarts at its type's default from Table 6-7 (§6.8): `x` for 4-state `logic`, `0` for 2-state `int` (§7.5.1). Of the `new[]` forms, only `arr = new[N](arr)` keeps the old values. `push_back` on a dynamic array does not compile: it is a queue method.
- An invalid index never stops the simulation, but the warning rules differ by kind (see the table below).
- A bounded queue never blocks. A `push_back` past the bound behaves as if the item were written, and then the item is discarded with a required warning (§7.10.5).
- Associative arrays do not remember insertion order. `first()`, `next()` and `foreach` follow index order, and `"Gamma"` comes before `"alpha"` because uppercase letters have smaller character codes (§7.8.2). Switch the index type to `int` and the keys come back in signed numeric order: `-5, 3, 10` (§7.8.4).
- Reading a missing key returns the default with a warning and does **not** create the entry. `exists()` asks without a warning (§7.8.6, §7.9.3).

| Kind | Invalid read | Invalid write | Warning |
|---|---|---|---|
| Fixed-size and dynamic arrays | A read returns the value Table 7-1 lists for a nonexistent element | A write does nothing | Either *may* warn (§7.4.5) |
| Queue | Returns the Table 7-1 value (§7.10.1) | A write outside `0` to `$+1` is ignored, while a write to `q[$+1]` appends | Read *may* warn (§7.4.5); write outside `0` to `$+1` *shall* warn (§7.10.1) |
| Associative array | Missing key reads the Table 7-1 value or the declared default | A write to a missing key is valid and creates the entry; an `x`/`z` key is ignored | Reading a missing key *shall* warn, unless the array declares a default (§7.8.6, §7.9.11); an `x`/`z` key *shall* warn (§7.8.4, §7.8.6) |

### Dynamic arrays: size them, copy them, never stretch them

A **dynamic array** is an unpacked array whose size you set at run time (§7.5). You declare it with empty brackets, `int a[];`, and until you size it, it has zero elements. A write never grows it. These are the operations that matter:

| Statement | Effect | Clause |
|---|---|---|
| `a = new[N];` | N fresh elements at the type default (`x` for `logic`, `0` for `int`, `null` for a class handle); old contents discarded | §7.5.1, Table 6-7 |
| `a = new[N](src);` | Copies `src`, truncated or padded with defaults to N elements. `a = new[N](a)` is the resize that keeps the data | §7.5.1 |
| `a = q;` or `a = {a, x};` | Assigning a whole array value (dynamic, queue or fixed-size, with an equivalent element type) resizes `a` to the source | §7.6, §10.10 |
| `a.size()` | The number of elements; there is no separate capacity | §7.5.2 |
| `a.delete();` | Empties the array: `size()` becomes 0 | §7.5.3 |
| `a[i] = v;` with `i` outside `0` to `a.size()-1` | Ignored (a warning is allowed); the array does not grow | §7.4.5 |

Two later constructs also resize a dynamic array: `randomize()` with a size constraint (§18.4, taught in [I-SV-2A](/curriculum/T2_Intermediate/I-SV-2A_Constrained_Randomization_Fundamentals/index)), and a streaming unpack into a dynamic target (§11.4.14.4, in [F2A: operators and expressions](/curriculum/T1_Foundational/F2A_Core_Data_Types/operators-and-expressions)). An associative array can never be assigned to a dynamic array (§7.9.9).

```systemverilog
// compile
module tb_top;
  logic [7:0] buffer [];  // 4-state elements: new slots start as x
  int         lens   [];  // 2-state elements: new slots start as 0

  initial begin
    buffer = new[4];
    foreach (buffer[i]) buffer[i] = i * 10;
    $display("new[4] + writes : %p", buffer);
    buffer = new[6](buffer);  // copy, then pad: keeps the data
    $display("new[6](buffer)  : %p", buffer);
```

The mistakes everyone makes:

- **The silent wipe.** `buffer = new[8];` when you meant `new[8](buffer)`. Values you wrote earlier read back as `x` (or `0` for 2-state types), and the log shows nothing, because the resize is legal.
- **`push_back` on a dynamic array.** It does not compile. If the count grows one item at a time, you wanted a queue.
- **Growing one element at a time.** `a = new[a.size()+1](a)` copies the whole array on every call. Use a queue.
- **A saved reference goes stale.** After any `new[]`, even `new[N](a)`, references to the old elements are outdated (§7.5.1). Push Further explains what that means for a task holding an element by `ref`.

**In a testbench:** per-lane or per-channel results when the count comes from configuration, a buffer sized once per test, or the payload bytes of a transaction whose length you know before you fill it. Do not use one when items arrive one at a time (use a queue) or when the indices are sparse (use an associative array).

### Queues: an ordered list that grows at both ends

A **queue** is a variable-size unpacked array with constant-time insertion and removal at either end and constant-time access to every element (§7.10). Index `0` is the front and `$` stands for the last index. A queue declared without an initial value starts empty, and `{}` is the empty queue.

You can also update a queue by assigning it a new value built with unpacked array concatenation (§7.10.4, §10.10):

```systemverilog
// snippet
q = {q, 6};                // same value as q.push_back(6)
q = {0, q};                // same value as q.push_front(0)
q = q[1:$];                // same value as void'(q.pop_front())
q = {q[0:1], 9, q[2:$]};   // same value as q.insert(2, 9)
```

A queue never blocks. A thread that must wait for data writes the wait itself: `wait (q.size() > 0);` is legal, because built-in array methods may appear in an event expression, and a change of the queue's size re-evaluates it (§9.4.2, §9.4.3).

The wait and the `pop_front()` are still two separate steps. With two consumers on one queue, anything that runs between those steps (a consumer that waits for a clock edge first, or the simulator switching to the other consumer between the two statements, which the LRM permits, §4.7) lets both see the same single item, and the second `pop_front()` then returns the missing-element value. A mailbox's `get()` waits and removes in one call, so each message goes to exactly one `get()` (§15.4.5, [I-SV-5](/curriculum/T2_Intermediate/I-SV-5_Synchronization_and_IPC/index)).

### Bounded queues: what gets thrown away

The same program runs on `int q[$]` and on `int bq[$:N]`. Predict what the bounded queue keeps, then find the first step where the two diverge. Pay attention to which end loses an element.

<QueueOperationLab />

The rule (§7.10.5): every write to a bounded queue first behaves as if the queue were unbounded; then every element beyond index N is discarded and a warning is issued. So `push_back` on a full queue loses the **new** item, but `push_front` and a middle `insert()` lose the **old last** item. Nothing blocks, and the bound counts indices: `[$:3]` holds four items. Assigning a longer array to a bounded queue follows the same rule: the excess is ignored with a warning (§7.10.5, §10.10).

If the producer must wait, or you need a count of drops, check `size()` yourself before you push. This buffer turns a tool warning that is easy to miss into a counted event in your own log:

```systemverilog
// snippet: inside a module
bit [31:0] pending_q [$:63];  // bound 63 is the last legal index: at most 64 items
int        n_dropped;

// A bounded buffer that reports its own drops
function automatic bit try_enqueue(bit [31:0] item);
  if (pending_q.size() == 64) begin
    n_dropped++;
    $warning("pending_q full: dropped %h (%0d drops so far)", item, n_dropped);
    return 0;
  end
  pending_q.push_back(item);
  return 1;
endfunction

// A producer that must not lose data waits for room instead
task automatic enqueue_wait(bit [31:0] item);
  wait (pending_q.size() < 64);  // queues never block on their own
  pending_q.push_back(item);
endtask

task automatic dequeue(output bit [31:0] item);
  wait (pending_q.size() > 0);
  item = pending_q.pop_front();
endtask
```

### Associative arrays: entries only where you write

An **associative array** maps a key to a value and allocates an entry only when you write one (§7.8). The key's type, the **index type**, decides which keys are legal and the order in which the array is walked.

| Declaration | Keys | Order of `foreach`, `first()`, `next()` | Clause |
|---|---|---|---|
| `int aa[int]` (any integral type) | Values are cast to the index type; x/z is invalid | Numeric, signed or unsigned by the index type | §7.8.4 |
| `int aa[string]` | Strings of any length; `""` is valid | Lexicographic by character code | §7.8.2 |
| `int aa[pkt]` (a class) | Handles of that class or a derived class; `null` is valid | Deterministic but arbitrary | §7.8.3 |
| `int aa[*]` (wildcard) | Any integral value, treated as unsigned | Numeric, but `foreach` and the traversal methods are not allowed | §7.8.1 |
| `int aa[key_t]` (another type, such as an unpacked struct) | Any type with `==` defined; `real` is not allowed | Without relational operators, can vary between runs | §7.8.5 |

| Call | Returns | Clause |
|---|---|---|
| `aa.num()`, `aa.size()` | The number of entries | §7.9.1 |
| `aa.exists(k)` | 1 if `k` has an entry, else 0; never warns | §7.9.3 |
| `aa.delete(k)` | Removes the entry `k`; silent if `k` has no entry | §7.9.2 |
| `aa.delete()` | Removes every entry | §7.9.2 |
| `aa.first(k)`, `aa.last(k)` | 1, and sets `k` to the smallest or largest key; 0 if the array is empty | §7.9.4, §7.9.5 |
| `aa.next(k)`, `aa.prev(k)` | 1, and moves `k` to the next larger or smaller key; 0 at the end, with `k` unchanged | §7.9.6, §7.9.7 |

**Reads, defaults and allocation.** Reading a key that has no entry returns the missing-element value (`0` for `int`, `x` for `logic`) **with a warning**, and creates nothing (§7.8.6). Only three things allocate an entry: being the target of an assignment, being passed to a `ref` argument, and a read-modify-write such as `aa[k]++`, which first allocates the entry with its default (§7.8.7).

A declared default changes what a missing key reads, and removes the warning: with `int hits[string] = '{default: 0};`, reading `hits["nack"]` before anything wrote it returns 0 quietly (§7.9.11). A counter such as `hits[name]++` works with or without a default, because a read-modify-write allocates the entry, at its default, before it reads it (§7.8.7). The default does not change the methods: `exists()` still returns 0 and `num()` still counts only written keys. A literal can set entries and the default together: `int tab[string] = '{"Peter":20, "Paul":22, default:-1};`.

Associative arrays assign only to associative arrays of a compatible type with the same index type, and assignment clears the target first (§7.9.9). Arguments follow the same rule (§7.9.10).

Starting from an empty array (`num() == 0`) and a missing key `k`, **Yes** in the last column means `num()` and `exists(k)` become `1` after the statement, and **No** means both stay `0`:

| Statement on missing `k` | Without default | With `'{default: d}` (§7.9.11) | Allocates? |
|---|---|---|---|
| `v = aa[k];` (read, §7.8.6) | Table 7-1 value (`0` for `int`, `'x` for `logic`), **warns** | `d`, **no warning** | **No** |
| `aa[k] = v;` (write, §7.8.7) | Stores `v`, no warning | Stores `v`, no warning | **Yes** |
| `aa[k]++;` (read-modify-write, §7.8.7) | Allocates at Table 7-1 default, then increments; no warning | Allocates at `d`, then increments; no warning | **Yes** |
| `task_with_ref(aa[k]);` (`ref` arg, §7.8.7) | Allocates at Table 7-1 default before call; no warning | Allocates at `d` before call; no warning | **Yes** |
| `aa.exists(k)` (§7.9.3) | `0`, **never warns** | `0`, **never warns** | **No** |
| `aa.delete(k)` (§7.9.2) | Silent no-op, no warning | Silent no-op, no warning | **No** |

```systemverilog
function automatic logic [31:0] mem_read(bit [31:0] addr);
```

### Array manipulation methods

Built-in methods search, reorder and reduce any unpacked array (§7.12). Three families matter daily, and each has one rule to remember: **locators return a queue**, **ordering methods are void and work in place**, and **reductions return the element type**.

| Family | Methods | Returns | Rule to remember |
|---|---|---|---|
| Locator (§7.12.1) | `find`, `find_first`, `find_last`, `min`, `max`, `unique` | A queue of elements, even for one result | `int m = q.max();` does not compile |
| Index locator (§7.12.1) | `find_index`, `find_first_index`, `find_last_index`, `unique_index` | A queue of `int`, or of the index type for an associative array | The `find` family needs a `with` clause |
| Ordering (§7.12.2) | `sort`, `rsort`, `reverse`, `shuffle` | Nothing: reorders the array itself | Illegal on associative arrays |
| Reduction (§7.12.3) | `sum`, `product`, `and`, `or`, `xor` | One value of the element type, or of the `with` expression's type | Narrow elements wrap |

Inside `with (...)`, `item` names the current element and `item.index` its index (§7.12, §7.12.4). You can rename the iterator: `q.find(x) with (x > 5)`. Unpacked structs and class handles have no `<` operator, so give `sort`, `rsort`, `min`, `max` and `unique` a key: `pkts.sort() with (item.addr);` (§7.12.1, §7.12.2). `reverse()` and `shuffle()` take no `with` clause at all. Structs are taught in [F2A: structs, unions and enums](/curriculum/T1_Foundational/F2A_Core_Data_Types/structs-unions-enums).

IEEE 1800-2023 adds a fifth kind of method, `map()`, which returns a new array holding the `with` expression's value for each element. Simulator support is still uneven; Push Further covers it under *Expert: Result types and widths of array methods*.

### Array query functions

The system functions `$left`, `$right`, `$low`, `$high`, `$increment`, `$size`, `$dimensions` and `$unpacked_dimensions` describe any array dimension (§7.11, §20.7). They return an `integer`, so they can return `'x`. On a queue or dynamic array they describe the current contents. On an associative array with an integral index type, `$left` is 0 and `$right` is the largest possible index, not the largest key. 1. `int f [7:0]` (fixed-size)
2. `int q[$] = '{10, 20, 30}`
3. `int q[$]`, empty
4. `int aa[int]` holding keys 5 and 9
5. `int aa[int]`, empty

### Passing arrays to tasks and functions

Arrays pass to subroutines **by value** unless you say otherwise: the subroutine gets a copy, for every kind of array, associative arrays included (§7.7). Writes inside the subroutine change only the copy, and a large array is copied on every call. **`ref`** passes the array itself: no copy, and writes land in the caller's array (§13.5.2). **`const ref`** passes it without a copy and forbids writes.

```systemverilog
// compile
module tb_top;
  int q[$] = '{1, 2, 3};

  function automatic void zero_first(int a[$]);         // by value: a is a copy
    a[0] = 0;
  endfunction

  function automatic void zero_first_ref(ref int a[$]); // by reference: a is q
    a[0] = 0;
  endfunction

  initial begin
    zero_first(q);
    $display("after zero_first     : q = %p", q);
    zero_first_ref(q);
    $display("after zero_first_ref : q = %p", q);
  end
endmodule
```

**Expected output** (illustrative, not from a simulator run):

```text
after zero_first     : q = '{1, 2, 3}
after zero_first_ref : q = '{0, 2, 3}
```

| Step | By value: `zero_first(q)` | By reference: `zero_first_ref(q)` |
|---|---|---|
| Call | `a` is a new copy: `'{1, 2, 3}` | `a` refers to `q` |
| `a[0] = 0;` | `a` is `'{0, 2, 3}`; `q` is still `'{1, 2, 3}` | `q` is `'{0, 2, 3}` |
| Return | The copy is discarded: `q` is `'{1, 2, 3}` | `q` is `'{0, 2, 3}` |

Which actual argument a formal accepts:

| Formal | Accepts | Notes |
|---|---|---|
| `int a[]` or `int a[$]`, by value | Any dynamic array, queue or fixed-size array of `int` | A copy (§7.7) |
| `int a[4]`, by value | A fixed-size array of 4 `int`s, or a dynamic array or queue holding 4 (checked at run time) | A copy (§7.7) |
| `ref int a[$]` | Only a queue of `int`: the types must be equivalent, and a queue is not equivalent to a dynamic array | The subroutine must be `automatic` (§13.5.2, §6.22.2) |
| `const ref int a[$]` | The same as `ref` | Read-only, no copy (§13.5.2) |
| `int a[string]` | Only an associative array of `int` with a `string` index | A copy (§7.9.10) |

**In a testbench:** helpers that check or print a whole queue take it as `const ref`, so a per-transaction call does not copy thousands of items. Helpers that fill a caller's array take it as `ref`, or return the new value. [F2D: tasks and functions](/curriculum/T1_Foundational/F2D_Reusable_Code_and_Parallelism/tasks-functions) teaches argument directions in general; the rules above are the array-specific part.

### Iterate safely, store safely

**Do not resize what you are iterating.** If a dynamic array, queue or associative array changes size inside a `foreach` over it, the results are undefined (§12.7.3). Cleanup loops that delete matched or empty entries are the usual victims. Collect the keys first, then delete them in a second pass:

```systemverilog
// snippet: two-pass cleanup of an associative array of queues
int empty_ids [$];
empty_ids = exp_by_id.find_index with (item.size() == 0);  // pass 1 only reads
foreach (empty_ids[i]) exp_by_id.delete(empty_ids[i]);     // pass 2 deletes
```

Starting from three keys, where keys 4 and 9 hold empty queues:

| Step | Statement | Keys in `exp_by_id` | `empty_ids` |
|---|---|---|---|
| 0 | (start) | 1, 4, 9 | `'{}` |
| 1 | `find_index` | 1, 4, 9: pass 1 changes nothing | `'{4, 9}` |
| 2 | `delete(4)` | 1, 9 | `'{4, 9}` |
| 3 | `delete(9)` | 1 | `'{4, 9}` |

**Store copies, not shared handles.** This is a preview of [I-SV-1](/curriculum/T2_Intermediate/I-SV-1_OOP/index): a queue of class handles stores handles, not objects (§8.12). A monitor that reuses one object and pushes it every cycle fills the queue with the same object, seen three times:

```systemverilog
// snippet: inside a class-based monitor's task (classes arrive in I-SV-1)
pkt p = new();          // one object, created once: the classic aliasing bug
repeat (3) begin
  p.data = sample_bus();  // overwrites the one object
  seen_q.push_back(p);    // stores another handle to it
end
```

| After cycle | `p.data` | `seen_q` holds | Every `seen_q[i].data` reads |
|---|---|---|---|
| 1 | 10 | 1 handle to `p` | 10 |
| 2 | 20 | 2 handles to `p` | 20 |
| 3 | 30 | 3 handles to `p` | 30 |

The fix is to construct a new object for each transaction (`p = new();` inside the loop) or to push a copy ([copying and cloning](/curriculum/T2_Intermediate/I-SV-1_OOP/copying-and-cloning)). Nothing in the log warns you: the values are simply wrong.

## Make It Work

### Worked example: an expected-transaction tracker and a sparse memory model

A DUT accepts requests tagged with an ID and answers each one later. Answers for different IDs may overtake each other, but answers for the same ID come back in request order; AXI uses this rule ([B-AXI-3](/curriculum/T3_Advanced/B-AXI-3_AXI_Ordering_and_IDs/index)). The checker therefore needs a table keyed by ID with a FIFO per ID: an **associative array of queues**. The bench also needs a memory model for a 32-bit address space that the test touches in only a few places: an associative array keyed by address.

The traffic below is scripted, so the example runs without a DUT. `INJECT_BUGS` plays the DUT: set to 1, ID 1 answers out of order and ID 3 never answers.

```systemverilog
// compile
// A plain-SV expected-transaction tracker and sparse memory model (no DUT, no UVM).
module tb_top;
  localparam bit INJECT_BUGS = 1;  // 0 replays the same traffic from a correct DUT

  bit [31:0]   exp_by_id [int][$];  // expected data per ID, oldest first
  logic [31:0] mem [bit [31:0]];    // sparse memory: only written addresses exist
  int n_match, n_mismatch, n_pending;

  // Record what the DUT must return for a request with this ID.
  function automatic void add_expected(int id, bit [31:0] data);
    if (!exp_by_id.exists(id)) exp_by_id[id] = {};  // allocate the key explicitly
    exp_by_id[id].push_back(data);
  endfunction

  // Check one response against the oldest outstanding item of the same ID.
  function automatic void check_actual(int id, bit [31:0] data);
    bit [31:0] expected;
    if (!exp_by_id.exists(id)) begin  // never read a key you have not checked
      $error("UNEXPECTED id=%0d data=%h", id, data);
      n_mismatch++;
      return;
    end
    expected = exp_by_id[id].pop_front();  // order must hold within one ID
    if (expected !== data) begin
      $error("MISMATCH id=%0d exp=%h act=%h", id, expected, data);
      n_mismatch++;
    end else begin
      n_match++;
    end
    if (exp_by_id[id].size() == 0) exp_by_id.delete(id);  // keys = pending IDs
  endfunction

  // An unwritten address reads x without the missing-key warning.
  function automatic logic [31:0] mem_read(bit [31:0] addr);
    return mem.exists(addr) ? mem[addr] : 'x;
  endfunction

  initial begin
    add_expected(1, 32'hA1);
    add_expected(2, 32'hB1);
    add_expected(1, 32'hA2);
    add_expected(3, 32'hC1);
    check_actual(2, 32'hB1);    // legal: ID 2 overtakes ID 1
    if (INJECT_BUGS) begin
      check_actual(1, 32'hA2);  // DUT bug: ID 1 answers out of order
      check_actual(1, 32'hA1);  // ...and ID 3 never answers
    end else begin
      check_actual(1, 32'hA1);
      check_actual(1, 32'hA2);
      check_actual(3, 32'hC1);
    end
    mem[32'h1000] = 32'hDEAD_BEEF;
    $display("mem[1000]=%h mem[2000]=%h", mem_read(32'h1000), mem_read(32'h2000));
  end  // no clock: the run ends here, then final runs

  final begin
    foreach (exp_by_id[id]) begin
      $error("PENDING id=%0d count=%0d", id, exp_by_id[id].size());
      n_pending += exp_by_id[id].size();
    end
    $display("SCB_SUMMARY matches=%0d mismatches=%0d pending=%0d",
             n_match, n_mismatch, n_pending);
  end
endmodule
```

**Run it.** Save the module as `tb_top.sv`, compile it with any SystemVerilog simulator (it uses no IEEE 1800-2023 additions), and run it with `tb_top` as the top module. It needs no plusargs and ends by itself when the `initial` block finishes: with nothing left to schedule, the simulation ends and the `final` block runs (§9.2.3). Then set `INJECT_BUGS` to 0 and run it again.

How to build one yourself:

1. On each request, push the expected data onto the queue for its ID. Allocate the key first with an assignment. Simulators commonly also allocate when you call `push_back` on a missing key, but that is tool-dependent: §7.8.7 names only assignment targets, `ref` arguments and read-modify-writes.
2. On each response, call `exists(id)` before you read anything. An unknown ID is an error, not a default value.
3. Compare against `pop_front()` from that ID's queue: order holds within an ID, not across IDs.
4. Delete the key when its queue empties, so the keys left are exactly the IDs still pending.
5. At the end, raise an error for every pending ID and print one summary line that counts the pending items.
6. For the sparse memory, write with `mem[addr] = data` and read only through a helper such as `mem_read()` that calls `exists()` first and returns a value you chose for an unwritten address (`'x` here, so it cannot pass for real data). The read then gives no missing-key warning and allocates nothing, and `num()` counts the addresses written, not the writes (§7.9.1, §7.9.3).
7. Make the bench prove it can fail: run once with injected bugs and check that the summary fails, then once clean.

### Debug the silent bugs

None of these stops the simulation. The last column says what the log gives you to go on.

| Symptom | Cause | Fix | What the log shows |
|---|---|---|---|
| Samples written earlier read back as `x` (or `0`) | `arr = new[N]` without `(arr)` wiped the array (§7.5.1) | `arr = new[N](arr)`, or a queue with `push_back` | Nothing: the resize is legal |
| A check passes although nothing was expected for that ID | A missing-key read returned the default: with `bit [31:0] exp [int]`, `if (exp[id] == act)` passes whenever `act` is 0 (§7.8.6) | `exists()` before every keyed read | One warning per read, worded by the tool and easy to lose in a long log |
| An in-order checker passes a response although nothing was expected | `pop_front()` on an empty queue returned the missing-element value (0 for a 2-state element), and the response data was 0 (§7.10.2.4) | Check `size()` before every pop and report UNEXPECTED, as the kata's checker A does | Nothing, or a warning the tool may choose to give |
| Items missing from a bounded FIFO model | A write past `[$:N]` was discarded (§7.10.5) | Check `size()` before you push and count drops | One required warning per discard |
| A checksum or count is wrong | `sum()` on narrow elements wrapped (§7.12.3), or a 1-bit `with` expression wrapped (§11.4.4) | `sum() with (int'(item))` | Nothing |
| A cleanup loop skips or repeats keys | The array changed size inside its own `foreach` (§12.7.3) | Collect keys first, then delete; or a `first()`/`next()` loop | Nothing, or tool-specific invalid-index warnings |
| A function "fills" an array but the caller sees no change | The array was passed by value (§7.7) | `ref` in an `automatic` subroutine, or return the array | Nothing |
| A test passes although a response was lost | Leftover expectations were printed, not counted | An error per pending ID, and `pending=0` in the pass criterion | Only your own report |
| Every queued transaction shows the same values | The monitor reused one object handle (§8.12) | A new object, or a copy, per transaction | Nothing |

**Checklist before moving on:**

- [ ] I pick a queue for an unknown count in arrival order, a dynamic array sized once for a count known at run time, and an associative array for sparse or non-integer keys.
- [ ] Every resize that must keep data uses `new[N](arr)` or assigns a whole new value; plain `new[N]` appears only where I want a fresh array.
- [ ] I treat a bound as a discard rule, not backpressure: I check `size()` before pushing and count drops myself.
- [ ] Every keyed read whose default could pass for real data is guarded by `exists()`, or the array declares a `'{default: v}` on purpose.
- [ ] My sparse memory model reads through an `exists()` helper, and I can predict its `num()` after a test's writes.
- [ ] Locator results go into a queue, and reductions over narrow elements use `with (int'(item))`.
- [ ] Empty per-ID queues are deleted, and nothing is deleted inside a `foreach` over the same array.
- [ ] My end-of-test report counts pending items, and the pass line needs `mismatches=0` and `pending=0`.

- **A narrow traversal variable truncates.** The argument to `first()`, `last()`, `next()` and `prev()` must be assignment compatible with the index type. If it is a smaller integral type, the method returns −1 and truncates: with `string aa[int]; byte ix;` and `aa[1000] = "a";`, `aa.first(ix)` returns −1 and leaves the low 8 bits of 1000 in `ix` (§7.9.8). The LRM calls that value 232; because `byte` is signed, `%0d` prints it as −24. Declare the traversal variable with exactly the index type.
- **A narrow key type aliases keys.** An integral index expression is cast to the index type (§7.8.4). With `int aa[byte];`, `aa[300] = 1;` writes key 44, and `aa[44]` reads it back.
- **x and z keys are invalid.** A read with an x/z key warns and returns the missing-element value; a write is ignored with a warning (§7.8.4, §7.8.6).
- **Wildcard arrays are nearly unusable for traversal.** An `[*]` array cannot be used with `foreach`, with `first`/`last`/`next`/`prev`, or with any array method that returns an index or an array of values (§7.8.1, §7.9.4–§7.9.7).
- **Allocation hides in read-modify-write.** `aa[k]++`, `aa[k] += 2` and passing `aa[k]` to a `ref` argument all allocate a missing entry first (§7.8.7). A plain read never does (§7.8.6).
- **A default changes reads, not methods.** With `'{default: v}`, a missing key reads `v` without a warning, but `exists()` still returns 0 and `num()` still counts only written keys (§7.9.11).
- **Deleting during a `first()`/`next()` walk is defined.** `next()` finds the smallest index greater than its argument, whether or not that index still exists (§7.9.6). For integral and string keys this one-pass cleanup is well-defined, unlike the same deletes inside `foreach` (§12.7.3). For user-defined keys without relational operators, the order may change after a delete (§7.8.5).

```systemverilog
// snippet: one pass with first()/next(), legal for integral and string keys
function automatic void drop_empty_ids();
  int id;
  int found;
  found = exp_by_id.first(id);
  while (found) begin
    if (exp_by_id[id].size() == 0) exp_by_id.delete(id);
    found = exp_by_id.next(id);  // smallest key above id, even if id is gone
  end
endfunction
```

### Expert: Stale references and hidden copies

- **What an outdated reference is.** A task that holds an array element by `ref` keeps that element alive until it returns, but if the element was removed or the array was resized meanwhile, its writes are no longer visible in the array (§13.5.2). These operations outdate references: a dynamic array resized by `new[]` (even `new[N](a)`) or emptied by `delete()`; deleting the referenced associative entry; assigning to the whole queue or dynamic array; and deleting the referenced queue element with a method (§13.5.2, §7.5.1).
- **Queue methods are gentler than assignment.** `push_*`, `pop_*`, `insert` and `delete(i)` leave references to surviving items valid. `q = {q, x}` gives the same value as `push_back(x)` but outdates every reference (§7.10.3, §7.10.4). On a bounded queue, a `push_front` or `insert` that pushes the last item out outdates that item (§7.10.3).
- **By value copies, always.** Every array kind is copied when passed by value, associative arrays included (§7.7, §7.9.10). A function called per transaction with a 10,000-item queue by value copies it every time; use `const ref`.
- **`ref` is strict.** It needs an `automatic` subroutine and an equivalent type (§13.5.2). A queue is not equivalent to a dynamic array, because they are different kinds of array (§6.22.2), so a queue cannot bind to `ref int a[]` even though it binds to `int a[]` by value (§7.7).
- **Handles in containers alias.** A queue of class handles holds handles (§8.12): store a new object or a copy per transaction, as the aliasing trace in Build Your Mental Model shows.

| Operation | `ref` to a surviving element | `ref` to a removed or replaced element | Clause |
|---|---|---|---|
| Queue method (`push_*`, `pop_*`, `insert`, `delete(i)`) | **Stays valid** (follows its element even when the index shifts) | **Outdated** (for the popped or deleted element) | §7.10.3, §13.5.2 |
| Bounded queue `push_front` / `insert` when full | **Stays valid** for elements remaining within `0 .. bound` | **Outdated** for the old last element discarded past the bound | §7.10.3, §7.10.5 |
| Whole-queue assignment (`q = {q, x}`, `q = q[1:$]`) or `q.delete()` | **Outdated** (every element reference is outdated) | **Outdated** | §7.10.4, §13.5.2 |
| Dynamic array `a = new[N]`, `a = new[N](a)`, whole assignment, or `a.delete()` | **Outdated** (`new[N](a)` copies values into a new array; old refs are outdated) | **Outdated** | §7.5.1, §7.5.3, §13.5.2 |
|Associative array `aa.delete(k)` / `aa.delete()` | **Stays valid** for every other key `j != k` | **Outdated** for key `k`, or all keys on `aa.delete()` (§13.5.2; whole assignment clears the target, §7.9.9: treat as outdated) | §7.9.2, §7.9.9, §13.5.2 |

### Expert: Result types and widths of array methods

- **Reductions take the `with` type.** A reduction returns the element type, or the type of the `with` expression (§7.12.3). `bytes.sum() with (item > 0)` on `'{200, 100}` returns 0: the relational expression is 1 bit wide (§11.4.4), so 1 + 1 wraps to 0. Count with `int'(item > 0)`.
- **Reductions need values the operation is defined for.** Without a `with` clause, the element type itself must support the addition, multiplication or bitwise operation; with one, the `with` expression's type must (§7.12.3). An array of structs therefore needs a `with` clause that picks a member: `pkts.sum() with (int'(item.len))`.
- **Index locators return the index type.** `find_index` and friends return a queue of `int`, except on an associative array, where they return a queue of the index type (§7.12.1). `item.index` follows the same rule, and `item.index(2)` asks for the index in dimension 2 (§7.12.4).
- **New in IEEE 1800-2023: `index_argument`.** If the element type has a member named `index`, rename the index method with a second argument: `arr.find(item, iter_index) with (item.index != item.iter_index)` (§7.12, §7.12.4).
- **New in IEEE 1800-2023: `map()`.** `A.map() with (item + 1'b1)` returns an array of the same shape whose element type is the self-determined type of the `with` expression (§7.12.5). Support in simulators is still uneven: tool-dependent.
- **No side effects in `with`.** If the `with` expression has side effects, the results may be unpredictable (§7.12).

### Expert: Memory and performance at scale

Only the queue's constant-time ends and element access are stated in the LRM (§7.10). The rest of this table is typical simulator behaviour, labelled implementation-dependent:

| Operation | Dynamic array | Queue | Associative array |
|---|---|---|---|
| Read or write `[i]` | Constant time, typically | Constant time (§7.10) | Typically logarithmic (tree) or amortized constant (hash) |
| `push_back`, `push_front` | Not available | Constant time (§7.10) | Not available |
| `insert(i)`, `delete(i)` in the middle | Not available | Typically proportional to the items moved | `delete(key)` costs about one lookup |
| Growing | `new[N](a)` copies every element | One item per push | One entry per write |
| `foreach`, `find*`, `sum`, `unique` | Linear | Linear | Linear, in key order |

- **Searches multiply.** A checker that calls `find_first_index` on a long queue for every response does work proportional to the queue for each one, so the whole test slows quadratically. Key the data by ID.
- **"Leaks" are references you still hold.** SystemVerilog reclaims memory automatically, but only for data nothing refers to (§8.29). An expected table you never delete from grows for the whole test: delete matched entries and empty per-ID queues, and cap the outstanding count per ID.
- **Handles keep objects alive.** A container of class handles keeps every object it refers to. IEEE 1800-2023 adds `weak_reference#(T)`, which refers to an object without keeping it alive (§8.30); simulator support varies, so it is tool-dependent.
- **Copies cost.** Pass large arrays to per-transaction helpers by `const ref`, not by value (§7.7, §13.5.2).

### Expert: The same structures inside UVM

- **`uvm_pool` is a class-based associative array** (IEEE 1800.2-2020 §11.2). Its `get(key)` allocates a missing key with the Table 7-1 value (§11.2.2.4), which a native read never does (IEEE 1800-2023 §7.8.6). That is where "phantom entries" come from: they belong to `uvm_pool`, not to the language.
- **Deleting a missing key differs too.** In uvm-core 2020.3.1 (`uvm_pool.svh`), `uvm_pool::delete(key)` on a missing key issues a `POOLDEL` warning, while native `delete(k)` is silent (§7.9.2).
- **`uvm_queue`** (IEEE 1800.2-2020 §11.3) wraps a queue in an object, so components can share it by handle. [I-UVM-5](/curriculum/T2_Intermediate/I-UVM-5_UVM_Container_Classes/index) covers both classes.
- **The configuration database is built from these structures.** In uvm-core 2020.3.1 (`uvm_resource_pool.svh`), the resource pool keeps an associative array keyed by name (`rtab[string]`) and one keyed by type handle (`ttab[uvm_resource_base]`); each entry is a handle to an object that holds a queue of resources. The handle-keyed table is a real use of a class index type.
- **Where the end-of-test check goes.** A UVM scoreboard uses the same associative array of queues as Make It Work, but checks for leftovers in `check_phase`, not in `final`. In uvm-core 2020.3.1 (`uvm_root.svh`), `run_test` prints the report summary and then calls `$finish`, so an error raised in a `final` block is missing from the summary's counts ([A-UVM-6](/curriculum/T3_Advanced/A-UVM-6_Scoreboards_and_Reference_Models/index)).

### Kata: an in-order checker and a by-ID tracker on the same traffic

**Goal:** see why the container must match the ordering rule the DUT promises (objectives 1 and 4).

**Start from** the `tb_top` in Make It Work.

1. Add checker A: one queue, `bit [31:0] exp_q [$];`. `add_expected` also pushes onto it, and `check_actual` also pops its front item and compares, counting matches and mismatches.
2. In the `final` block, print a second summary line for checker A that counts its leftover items.
3. Run with `INJECT_BUGS = 0`, then with `INJECT_BUGS = 1`.

**Acceptance:**

- With `INJECT_BUGS = 0`, the by-ID tracker passes (`mismatches=0 pending=0`) and checker A reports 2 mismatches. Explain in one sentence why they are false alarms.
- With `INJECT_BUGS = 1`, both checkers report one item still pending: the request for ID 3.
- No missing-key warning appears in either run.

**Extension 1:** cap each ID at 4 outstanding items with `bit [31:0] exp_by_id [int][$:3]`, and count the drops yourself before each push instead of relying on the bound's warning.

**Extension 2 (sparse memory, objective 4):** in the Make It Work `tb_top`, add `mem_write(addr, data)`. Write `32'h1000` twice and `32'h2000` once through it, then print `mem.num()` and `mem_read(32'h3000)`. Predict both before you run, and check that no missing-key warning appears.

<details>
<summary>Worked solution</summary>

The sparse-memory lines are left out to keep the focus on the two checkers; Extension 2's solution follows the checker answers.

```systemverilog
// compile
module tb_top;
  localparam bit INJECT_BUGS = 0;

  bit [31:0] exp_by_id [int][$];  // checker B: one queue per ID
  bit [31:0] exp_q [$];           // checker A: one queue in request order
  int a_match, a_mismatch;
  int b_match, b_mismatch, b_pending;

  function automatic void add_expected(int id, bit [31:0] data);
    if (!exp_by_id.exists(id)) exp_by_id[id] = {};
    exp_by_id[id].push_back(data);
    exp_q.push_back(data);
  endfunction

  function automatic void check_actual(int id, bit [31:0] data);
    bit [31:0] expected;
    // Checker A assumes one global order.
    if (exp_q.size() == 0) begin
      $error("A: UNEXPECTED id=%0d data=%h", id, data);
      a_mismatch++;
    end else begin
      expected = exp_q.pop_front();
      if (expected !== data) begin
        $error("A: MISMATCH id=%0d exp=%h act=%h", id, expected, data);
        a_mismatch++;
      end else a_match++;
    end
    // Checker B keeps order only within an ID.
    if (!exp_by_id.exists(id)) begin
      $error("B: UNEXPECTED id=%0d data=%h", id, data);
      b_mismatch++;
      return;
    end
    expected = exp_by_id[id].pop_front();
    if (expected !== data) begin
      $error("B: MISMATCH id=%0d exp=%h act=%h", id, expected, data);
      b_mismatch++;
    end else b_match++;
    if (exp_by_id[id].size() == 0) exp_by_id.delete(id);
  endfunction

  initial begin
    add_expected(1, 32'hA1);
    add_expected(2, 32'hB1);
    add_expected(1, 32'hA2);
    add_expected(3, 32'hC1);
    check_actual(2, 32'hB1);
    if (INJECT_BUGS) begin
      check_actual(1, 32'hA2);
      check_actual(1, 32'hA1);
    end else begin
      check_actual(1, 32'hA1);
      check_actual(1, 32'hA2);
      check_actual(3, 32'hC1);
    end
  end

  final begin
    foreach (exp_by_id[id]) begin
      $error("B: PENDING id=%0d count=%0d", id, exp_by_id[id].size());
      b_pending += exp_by_id[id].size();
    end
    if (exp_q.size() > 0) $error("A: PENDING count=%0d", exp_q.size());
    $display("A: SCB_SUMMARY matches=%0d mismatches=%0d pending=%0d",
             a_match, a_mismatch, exp_q.size());
    $display("B: SCB_SUMMARY matches=%0d mismatches=%0d pending=%0d",
             b_match, b_mismatch, b_pending);
  end
endmodule
```

**Expected output with `INJECT_BUGS = 0`** (illustrative; `Error:` stands for each tool's own prefix):

```text
Error: A: MISMATCH id=2 exp=000000a1 act=000000b1
Error: A: MISMATCH id=1 exp=000000b1 act=000000a1
A: SCB_SUMMARY matches=2 mismatches=2 pending=0
B: SCB_SUMMARY matches=4 mismatches=0 pending=0
```

**Expected output with `INJECT_BUGS = 1`** (illustrative):

```text
Error: A: MISMATCH id=2 exp=000000a1 act=000000b1
Error: A: MISMATCH id=1 exp=000000b1 act=000000a2
Error: B: MISMATCH id=1 exp=000000a1 act=000000a2
Error: A: MISMATCH id=1 exp=000000a2 act=000000a1
Error: B: MISMATCH id=1 exp=000000a2 act=000000a1
Error: B: PENDING id=3 count=1
```

**Why checker A false-alarms:** the DUT may legally answer ID 2 before ID 1, but checker A compares against one global order, so a legal overtake looks like two mismatches.

**Extension 1 hint:** before the push, `if (exp_by_id.exists(id) && exp_by_id[id].size() == 4)` counts a drop and skips the push; the `&&` stops the read when the key does not exist yet.

**Extension 2 solution:**

```systemverilog
// snippet: add to the Make It Work tb_top, which already declares mem and mem_read()
function automatic void mem_write(bit [31:0] addr, logic [31:0] data);
  mem[addr] = data;  // an assignment allocates the entry (§7.8.7)
endfunction

// at the end of the initial block
mem_write(32'h1000, 32'h1);
mem_write(32'h1000, 32'h2);  // same key: replaces the value, num() unchanged
mem_write(32'h2000, 32'h3);
$display("num=%0d read3000=%h", mem.num(), mem_read(32'h3000));
```

It prints `num=2 read3000=xxxxxxxx` and no warning. `num()` counts entries, not writes (§7.9.1), and `mem_read()` asks `exists()` before it reads, so the unwritten address neither warns nor allocates (§7.9.3, §7.8.6).

### Debug challenge: four silent bugs

Each of these helpers compiles and runs without stopping the simulation, and each one is wrong. For each bug, name the symptom, the cause and the fix before you open the answer.

```systemverilog
// snippet: inside a module
logic [7:0] samples [];
bit   [7:0] payload [$];
bit  [31:0] exp_by_addr [int];
int         chk;

function automatic void collect(logic [7:0] s);
  samples = new[samples.size() + 1];                // bug 1
  samples[samples.size() - 1] = s;
endfunction

function automatic bit check_read(int addr, bit [31:0] act);
  return exp_by_addr[addr] == act;                  // bug 2
endfunction

function automatic void checksum();
  chk = payload.sum();                              // bug 3
endfunction

function automatic void drop_zero_entries();
  foreach (exp_by_addr[a])
    if (exp_by_addr[a] == 0) exp_by_addr.delete(a); // bug 4
endfunction
```

<details>
<summary>Answers</summary>

| Bug | Symptom | Cause | Fix | Log |
|---|---|---|---|---|
| 1 | Every earlier sample reads back as `x`; only the newest survives | `new[N]` without `(samples)` allocates a fresh array (§7.5.1) | `samples = new[samples.size() + 1](samples);`, or better a queue with `push_back` | Nothing |
| 2 | A read from an address the test never wrote passes when the DUT returns 0 | A missing key reads the 2-state default 0 (§7.8.6), which matches `act` | `return exp_by_addr.exists(addr) && exp_by_addr[addr] == act;` and report the missing key as an error | One warning per missing-key read |
| 3 | The checksum is wrong whenever the bytes add up to 256 or more | `sum()` returns `bit [7:0]` and wraps before the assignment (§7.12.3) | `chk = payload.sum() with (int'(item));` | Nothing |
| 4 | Some zero entries survive, or the loop misbehaves on another simulator | Deleting inside a `foreach` over the same array is undefined (§12.7.3) | Collect first: `dead = exp_by_addr.find_index with (item == 0);` then `foreach (dead[i]) exp_by_addr.delete(dead[i]);` with `int dead [$];` declared | Nothing, or tool-specific warnings |

The `&&` in fix 2 short-circuits, so the missing key is never read (§11.3.5).

</details>
