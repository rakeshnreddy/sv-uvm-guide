## Quick Take

- **What it is:** A **clocking block** gathers the signals that are synchronous to one clock and makes their timing explicit: it names a clock event and fixes when each signal is sampled and when each drive takes effect relative to that event (IEEE 1800-2023 §14.2, §14.3). A **program block** is a testbench scope whose code is scheduled in the reactive region set, after the design's activity in the same time slot (§24.2, §24.3.1). Both are current parts of the standard; neither is deprecated.
- **Why it matters:** The testbench (TB) and the design under test (DUT) wake on the same clock edge, and the simulator may run them in any order (§4.7). Through a clocking block, the TB reads the values from just before the edge, and its drives land after the DUT's flops have read their inputs, whichever order the simulator picks. Every bench in this curriculum from milestone M1 onward, including the UVM drivers and monitors of later tiers, drives and samples the DUT this way.
- **The Analogy:** A clocking block is a photographer and a courier stationed at the clock. Just before each edge the photographer takes a **photo** of every input, and your code reads the photo, never the live signal. The courier takes every value you **drive** and delivers it just after the edge, once the flops have taken their own snapshot. *Where it breaks:* the default photo shows the last value before the edge's time slot, however long ago that value changed, not a picture taken a fixed time earlier. A photo with an explicit `#0` skew is taken at the edge itself, after the design's nonblocking updates. A zero-skew delivery happens in the same time slot as the edge, in the Re-NBA region, not "a little later" in simulated time. And if you hand the courier two parcels for one signal in one cycle, only the last one is delivered (§14.16.2).

**You will be able to:**
1. **Predict** when a clocking block samples each input and when each synchronous drive changes its signal, for `#1step`, `#N` and explicit `#0` input skews and for zero and nonzero output skews.
2. **Predict** where a process that waits on `@(cb)` resumes compared with one that waits on `@(posedge clk)`, and **write** cycle delays that compile: `##N` with a default clocking, and `cb.sig <= ##N v` in a drive.
3. **Write** a task-based driver and monitor that touch the DUT only through `cb` and `mon_cb`, keep an asynchronous reset outside the clocking block, and predict the value driven when two drives hit one signal in one cycle.
4. **Debug** a racy bench by converting it to clocking blocks, and explain why the result no longer depends on process order or source order.
5. **Explain** what a program block changes (reactive scheduling, no `always` procedures, how it ends the run) and that it is not deprecated, and **choose** between a module and a program as the top of a testbench.

### The Race Condition Problem

The TB and the DUT wake on the same clock edge, and IEEE 1800-2023 §4.7 lets the simulator run them in any order. The dangerous case is the TB **driving** a DUT input with a blocking assignment at that edge: if the TB happens to run first, the DUT's flop captures the *new* value instead of the value from before the edge.

```systemverilog
// snippet: the racy pattern (do not copy)
// DUT: reads din in the Active region, writes q in the NBA region
always_ff @(posedge clk) q <= din;

// TB: wakes in the same Active region on the same edge
always @(posedge clk) begin
  din = next_value;   // blocking write: the flop may or may not see it
end
```

**Trace the legal orders of one edge.**

| What runs at the edge | What the flop captures | Verdict |
|---|---|---|
| The DUT's flop first, then the TB's `din = next_value` | the old `din` | what real hardware does |
| The TB first, then the flop | the new `next_value`, one cycle early | a race: the order is the simulator's choice (§4.7) |
| The TB waits on `@(cb)` and drives `cb.din <= next_value` | the old `din` in every order: `din` changes in the Re-NBA region, after the flop has read it | race-free (§14.16) |

Reading DUT outputs is a separate question. A read of `q` right after `@(posedge clk)` is deterministic *only* while every writer on that path uses `<=`: the read happens in the Active region, before the NBA update. If any design logic on that path uses blocking assignments, the read races too. A TB that drives with `<=`, as in [F2E](/curriculum/T1_Foundational/F2E_First_Self_Checking_Testbench/index), already avoids the drive race. A clocking block adds three things on top: reads of the values from before the edge that do not depend on how the DUT is written, explicit skews, and one place in the interface that owns all the timing. To watch this race appear and disappear in every legal order, step through the testbench scenarios in [F3C](/curriculum/T1_Foundational/F3C_Delta_Cycles_and_Race_Conditions/index).

### Anatomy of a clocking block

Here is the driver's view of the bench you will build in Make It Work, declared inside its interface:

```systemverilog
// snippet: inside interface pipe_if (the complete code is in Make It Work)
default clocking cb @(posedge clk);   // block name, then the clocking event
  default input #1step output #0;     // the default skews, written out
  output in_vld, in_data;             // the TB drives these: output clockvars
  input  out_vld, out_data;           // the TB samples these: input clockvars
endclocking
```

| Term | In the example | Meaning |
|---|---|---|
| **Clocking event** | `@(posedge clk)` | The event the block is clocked on. Every skew is measured from it (§14.3, §14.4). |
| **Clocking signal** | the interface variable `in_vld` | A net or variable in the surrounding scope that the block lists (§14.3). |
| **Clockvar** | `cb.in_vld` | The block's own view of a clocking signal, reached with a dot (§14.3, §14.7). An input clockvar holds the latest sample; an output clockvar is the target of drives. |
| **Skew** | `#1step`, `#0` | How long before the clocking event an input is sampled, or how long after it an output is driven (§14.4). |
| **Synchronous drive** | `cb.in_vld <= 1'b1;` | The only legal way to write an output clockvar (§14.16). |
| **Clocking block event** | `@(cb)` | An event named after the block. The block triggers it in the Observed region, after it has processed its clocking event and stored the new samples (§14.10, §14.13). |

Keep the last term apart from the first. The **clocking event** is the clock edge itself; the **clocking block event** is the notification the block sends once it has finished with that edge. Code that waits on `@(cb)` waits for the second.

**Rules you will meet on day one:**
1. **Directions are checked.** Directions are seen from the TB: `output in_vld` means the TB drives `in_vld` into the DUT (§14.9). Writing an input clockvar or reading an output clockvar is a compile error (§14.3).
2. **Defaults.** Without a `default` item, inputs use `#1step` and outputs use `#0` (§14.3).
3. **Skew values.** A skew is a time literal such as `2ns`, or a constant expression that evaluates to a non-negative integer, and it may be a parameter (§14.3, §14.4). A plain number uses the time unit of the enclosing scope: `#2` in an interface with `timeunit 1ns` means 2 ns. `1step` is one unit of the global time precision, the finest precision in the whole design (§3.14.3).
4. **Where it may live.** A clocking block is declared in a module, interface, checker or program. It cannot be declared in a package, class, task or function, and clocking blocks cannot be nested (§14.7). One copy exists per instance of the enclosing block, so every instance of `pipe_if` has its own `cb`. That is why class code reaches a clocking block through a virtual interface handle, `vif.cb` (§25.9.1, [F4B](/curriculum/T1_Foundational/F4B_Interfaces_and_Modports/index)).
5. **Several blocks.** A scope may declare several clocking blocks, for different clocks or for different roles on one clock (§14.6, §14.8). Blocks on the same clock share one synchronization event, so `@(bus.cb)` and `@(bus.mon_cb)` fire at the same point of the same time slot (§14.6).

**Other forms you will meet:**

| Form | Example | Effect |
|---|---|---|
| Per-signal skew | `input #1step addr;` | Overrides the default input skew for `addr` only (§14.3). |
| Input and output skew on one signal | `input #5 output #6 data;` | Samples `data` 5 time units before the edge and drives it 6 time units after (§14.4). |
| Edge skew | `output negedge ack;` | Drives `ack` at the falling edge of the clock (§14.3). |
| `inout` | `inout data;` | An input clockvar and an output clockvar with one name. It is not an `inout` port, so `data` may be a variable (§14.3, §14.5). |
| Hierarchical expression | `input state = top.cpu1.state;` | Samples a signal from another scope under the local clockvar name `state` (§14.5). |
| Naming an existing block as the default | `default clocking cb;` | Makes an existing clocking block the default for `##` in this scope (§14.12). |
| Unnamed block | `default clocking @(posedge clk); … endclocking` | Only a default clocking block may be unnamed (§14.3); a global clocking, below, may also omit its name (§14.14). Its clockvars cannot be referenced, so an unnamed default serves only as the clock of `##` and of concurrent assertions (§14.12, §16.16). |

What to take from it:
- Only `cb` drives DUT inputs, and only `send()` uses `cb`. `mon_cb` has no outputs, so `monitor()` cannot drive the DUT even by mistake.
- Both blocks belong to the interface instance `bus`, not to the tasks that use them. The timing is declared once, next to the signals.
- `rst_n` is in no output list. The TB writes it directly, between edges, and `mon_cb` only samples it. "Reset stays outside the clocking block" below explains why.

**Pitfalls.**
- Reading `cb.in_vld` when `in_vld` is an output of `cb` does not compile (§14.3). Read it through a block that lists it as an input, such as `mon_cb`, or declare it `inout`.
- A continuous assignment, a procedural `assign` or `force`, or a primitive output may not write a variable that a clocking block lists as an output (§14.16.2). Synchronous drives and ordinary procedural assignments may.
- A clocking block declared in a package or a class does not compile (§14.7).

### Sampling: the photo

Every input clockvar is sampled at its clocking event (§14.13). The input skew decides which value the photo shows:

| Input skew | Value sampled | Where in the time slots |
|---|---|---|
| `#1step` (the default) | The last value before the edge's time slot began, however long ago it changed | Identical to sampling in the Preponed region of the edge's time slot (§4.4.2.1, §14.4) |
| `#N`, N > 0 | The value N time units before the edge; a change at exactly that time is included | The Postponed region of the time slot N time units before the edge (§14.13) |
| Explicit `#0` | The value at the edge itself, after the design's nonblocking updates for that edge | The Observed region of the edge's time slot (§14.4, §14.13) |

- Between clocking events, an input clockvar keeps returning the sample of the most recent clocking event (§14.13). The photo does not change until the next edge, whatever the live signal does.
- `@(cb.out_vld)` and `@(posedge cb.out_vld)` wait for a change of the *sampled* value, not of the live signal (§14.15).
- A nonzero input skew is a setup window: a DUT output that changes inside it is seen one cycle later. In zero-delay RTL simulation, keep the default `#1step`.

**Classic mistake:** an input skew longer than the time a DUT output needs to settle after the edge. The bench then silently samples the previous cycle's value. The experiment below shows it.

### Driving: the delivery

- A drive with output skew `#0`, executed at the clocking event, updates its signal in the Re-NBA region of that same time slot (§14.16). By then the design has made its nonblocking updates for the edge: the DUT's flops have captured the old value, and they capture the new one at the next edge.
- With a nonzero output skew, such as `output #2ns`, the signal changes in the Re-NBA region of the time slot that lies the skew after the edge (§14.16).
- It does not matter which code issues the drive: module, interface, class or program code all land in Re-NBA (§14.16).
- A drive executed **between** edges does not block. Its right-hand side is evaluated at once, but the drive acts as if it had been executed at the next clocking event (§14.16). That is why the M1 bench's `bus.cb.in_vld <= 1'b0;` at time 0 changes `in_vld` at the first edge, at 5 ns.
- Only the synchronous-drive form may write a clockvar. `assign` and `force` on a clockvar are illegal, and so is an ordinary intra-assignment delay: `cb.din <= #4 v;` is an error (§14.16). The target may be a bit-select or a slice, as in `cb.data[3:0] <= 4'h5;`, but not a concatenation (§14.16).
- When the clocking signal is a net, the block creates its own driver on that net, initialized to `'z`, so the net sees nothing from the block until the first drive (§14.16).

**Classic mistake:** thinking that a drive changes the signal at once, like a blocking assignment, or in the NBA region together with the design's flops. A synchronous drive always lands in Re-NBA.

### The clocking block event

- `@(cb)` waits for the clocking block event. The block triggers it in the Observed region, after it has stored the samples of this edge (§14.10, §14.13). Module and class code that waits on it resumes in the next Active pass of the same time slot, after the design's nonblocking updates for the edge.
- So "`@(cb)`, then read `cb.x`" always reads this edge's sample, whatever region the waiting process runs in (§14.13).
- Module or class code that waits on `@(posedge clk)` resumes in the same Active region as the clock edge. If it then reads `cb.x`, it races the block's own update of its samples and may get the old sample or the new one (§14.13, §14.4 NOTE). Program code is the exception; see "Program blocks" below.
- The rule for every bench: wait on the clocking block event of the block you read or drive. Never wait on `@(posedge clk)` and then touch a clockvar.

- **Defaults:** `cb.dout` is 2 at edge 3. The photo shows the value from before the edge; the DUT's update to 3 lands later in that time slot.

### Cycle delays and default clocking

A **cycle delay** `##N` waits for N clocking block events of the **default clocking** (§14.11). Declare a block as the default with `default clocking cb @(posedge clk); … endclocking`, or name an existing block with `default clocking cb;` (§14.12). The M1 interface uses its default clocking for one task:

```systemverilog
// snippet: inside interface pipe_if, where cb is the default clocking
task automatic wait_cycles(input int n);
  ##(n);                              // n clocking block events of cb (§14.11)
endtask
```

| Statement | Blocks the process? | Counts cycles of | Needs a default clocking? |
|---|---|---|---|
| `##2;` | yes | the default clocking | yes: without one the compiler reports an error (§14.11) |
| `##2 cb.din <= v;` | yes, then drives | the default clocking | yes |
| `cb.din <= ##2 v;` | no: `v` is evaluated now, and `din` changes two cycles of `cb` later | `cb` itself | no (§14.16) |
| `repeat (2) @(vif.cb);` | yes | `cb`, through the handle | no: this is the form class code uses |

- **One default per scope.** A module, interface, program or checker may declare one default clocking; a second is a compile error. The default applies in that scope and in modules, interfaces and checkers nested in it, but not in other instances (§14.12).
- **So it does not follow the handle.** The default clocking of `pipe_if` reaches neither `tb_top`, which instantiates the interface, nor a class in a package. `##2;` in either place is a compile error. Use `repeat (2) @(vif.cb);`, or call an interface task such as `wait_cycles()`.
- **Partial cycles.** `##1` executed between edges waits only for the rest of the current cycle (§14.11).
- **Not for ordinary assignments.** `x = ##1 y;` and `x <= ##1 y;` are illegal (§14.11). The synchronous drive `cb.x <= ##1 y;` is the only assignment-like form that takes `##` (§14.16).
- **Assertions too.** A default clocking also clocks concurrent assertions that have no clock of their own (§16.16; [I-SV-4A](/curriculum/T2_Intermediate/I-SV-4A_SVA_Fundamentals/index)).

**Predict with the visual.** Go back to the experiment above, open "Show advanced: ## and default clocking", and untick "Declare cb as default clocking". Before you look at the result: which of the three drive forms stops compiling?

**Debrief.** Only `##1 cb.din <= v;` fails, because its `##1` counts cycles of the default clocking. `cb.din <= ##1 v;` still compiles, because its `##1` counts cycles of `cb` itself. Tick the box again and compare the capture edges: the plain drive is captured at edge 3 and both `##1` forms at edge 4, but only the prefix form blocks the testbench thread until edge 3.

### Clocking blocks in an interface: one per role

Two roles touch the DUT, and each gets its own clocking block in the interface:
- The **driver** uses `cb`: outputs for every DUT input it drives, plus inputs for any DUT output it must react to, such as a `ready` signal.
- The **monitor** uses `mon_cb`: inputs only, for every signal it checks, including reset. It cannot drive, so a monitor bug can never disturb the DUT. A passive agent, which only watches, needs nothing but `mon_cb` ([I-UVM-2A](/curriculum/T2_Intermediate/I-UVM-2A_Component_Roles/index)).

For M1, both roles are tasks in `tb_top`. These are excerpts; the complete bench is in Make It Work.

```systemverilog
// snippet: the M1 driver and monitor, tasks in tb_top
task automatic send(input logic [7:0] data);
  bus.cb.in_vld  <= 1'b1;            // Re-NBA after this edge: captured at the next
  bus.cb.in_data <= data;
  exp_q.push_back(data + 8'd1);
  @(bus.cb);
endtask

task automatic monitor();
  logic [7:0] expected;
  forever begin
    @(bus.mon_cb);                   // wakes after this edge's samples are stored
    if (bus.mon_cb.rst_n !== 1'b1) continue;   // ignore samples taken in reset
    if (bus.mon_cb.out_vld === 1'b1) begin
      expected = exp_q.pop_front();  // the full bench also guards an empty queue
      // ... compare bus.mon_cb.out_data with expected and count the result
    end
  end
endtask
```

The pair keeps a fixed rhythm. `send()` drives after `@(bus.cb)` at edge *k*, the DUT captures the item at edge *k* + 1, and the two-stage pipeline presents the result so that `mon_cb` samples it at edge *k* + 3.

**A preview of the class form ([I-SV-1](/curriculum/T2_Intermediate/I-SV-1_OOP/index)).** From Tier 2 on, the driver and monitor become classes. A class cannot contain a clocking block (§14.7), so it holds a virtual interface handle and reaches the blocks through it:

```systemverilog
// snippet: a preview of classes (I-SV-1); the M1 bench uses the task form
class pipe_drv;
  virtual pipe_if vif;               // a handle to an interface instance (F4B)

  task send(input logic [7:0] data);
    vif.cb.in_vld  <= 1'b1;          // the same synchronous drive, through the handle
    vif.cb.in_data <= data;
    @(vif.cb);                       // a class has no default clocking: no ## here
  endtask
endclass
```

Bind the handle in `tb_top` before its first use, with `drv = new(); drv.vif = bus;`, as in [F4B](/curriculum/T1_Foundational/F4B_Interfaces_and_Modports/index). In a UVM bench the driver is a `uvm_driver` that gets the handle from the configuration database, `uvm_config_db` ([I-UVM-2C](/curriculum/T2_Intermediate/I-UVM-2C_Configuration_and_Resources/index)); the clocking-block code inside it does not change.

**Modport-typed handles.** Dot access to a clocking block through a virtual interface, as in `vif.cb`, works directly only for interfaces that declare no modports (§25.9.2). When the interface has modports, list each clocking block in the modport of the role that uses it, and type the handle with that modport (§25.5.5):

```systemverilog
// snippet: modports that expose one clocking block each (§25.5.5)
modport drv_mp (clocking cb);        // a driver reaches cb and nothing else
modport mon_mp (clocking mon_cb);    // a monitor reaches mon_cb, so it cannot drive

// in a monitor class:  virtual pipe_if.mon_mp vif;  ...  @(vif.mon_cb);
```

### Reset stays outside the clocking block

An asynchronous reset must be able to change between clock edges, at the moment the TB decides. A synchronous drive cannot do that: a drive executed between edges acts as if it were executed at the next clocking event, and lands in the Re-NBA region of that time slot (§14.16). The picture compares two ways of asserting `rst_n` at 12 ns, with rising clock edges at 5, 15 and 25 ns.

In words:
- **Direct write**, `bus.rst_n = 1'b0;` at 12 ns: `rst_n` falls at 12 ns, and the DUT's `negedge rst_n` branch resets the flops at 12 ns.
- **Through a clocking block**, `cb.rst_n <= 1'b0;` executed at 12 ns: nothing happens until the 15 ns edge. At 15 ns the flops first make their normal capture in the Active region; then `rst_n` falls in Re-NBA, and the `negedge rst_n` resets them in a later pass of the same time slot (§14.16, §4.5). The DUT ran through one more clock edge than you asked for.

The M1 bench therefore:
1. Declares `rst_n` as a plain interface variable with a declaration initializer, `logic rst_n = 1'b0;`. The initializer runs at time 0, before any `initial` or `always` procedure starts (§6.8), so the DUT is in reset from the start.
2. Releases it with a direct write between edges: `#12 bus.rst_n = 1'b1;`. This is practice, not a rule of the standard: assert reset whenever you need to, but release it away from the active clock edge. Real cell libraries add recovery and removal checks, whose values are library- and tool-dependent.
3. Lists `rst_n` as an **input** of `mon_cb`. Sampling a signal through a clocking block is fine; only driving it through one is the problem. The monitor skips every edge whose sample shows reset asserted.
4. Starts driving only after the release, then synchronizes with `@(bus.cb)`. A reusable driver that does not release reset itself does the same with `wait (bus.rst_n === 1'b1); @(bus.cb);`.

Reset in the middle of a test, with a driver, monitor and scoreboard that flush their state, is planned for Tier 3.

### Several drives to one signal in one cycle

Sooner or later two drives hit one clockvar in the same cycle. §14.16.2 defines what happens:

- **The last value wins.** When several synchronous drives to one clocking output mature in the same Re-NBA region of the same time slot, only the last value is driven. This holds whether the drives executed at the clocking event or between edges in the same cycle, and whether the signal is a variable or a net.
- **Cycle delays keep drives apart.** Drives that mature in different future cycles each take effect in their own cycle.
- **Two processes make it a race.** Inside one process, "last" is the statement order. Between two processes woken by the same event, it is the process order, which the simulator chooses (§4.7). Give each clockvar one writer per cycle.

The standard's own example:

```systemverilog
// snippet: IEEE 1800-2023 §14.16.2
default clocking pe @(posedge clk);
  output nibble;                     // a 4-bit output
endclocking

initial begin
  ##2;
  pe.nibble <= 4'b0101;
  pe.nibble <= 4'b0011;              // same Re-NBA region: only 4'b0011 is driven
end
```

A second example from §14.16.2 shows how cycle delays count. `cb` is the default clocking, and cycle *n* is its *n*-th clocking event after time 0:

| Statement, in order | Executes at | Matures in |
|---|---|---|
| `##1;` | waits for cycle 1 | |
| `cb.v <= expr1;` | cycle 1 | cycle 1: `v` becomes `expr1` |
| `cb.v <= ##2 expr2;` | cycle 1 | cycle 3 |
| `#1 cb.v <= ##2 expr3;` | 1 time unit after cycle 1 | cycle 3 |
| `##1 cb.v <= ##1 expr4;` | cycle 2, after its `##1` | cycle 3 |

In cycle 3 three drives mature in one Re-NBA region, and `expr4`, executed last, is the value `v` takes. A rule that fits every drive in the table: a `<= ##N` drive matures at the *N*-th clocking event after the statement executes, not counting the event of the time slot it executes in; a drive without `##` matures at the clocking event of its own time slot, or at the next one when it executes between edges.

**Mixing drives with other writes.** An ordinary procedural assignment to a variable that a clocking block lists as an output is legal: it changes the variable at once, and the value holds until the next drive or assignment. If a synchronous drive and a nonblocking assignment write the same variable in one time slot, they take effect in arbitrary order (§14.16.2). Push Further covers glitches, nets and double-data-rate drives.

### Program blocks

A **program** is a testbench building block with special scheduling. §24.2 gives it three purposes: an entry point for testbench execution, a scope for program-wide data, tasks and functions, and a context whose code is scheduled in the reactive region set.

- **What it may contain** (§24.3): ports declared like module ports, data declarations, class definitions, subroutines, object instances, continuous assignments, concurrent assertions, and `initial` and `final` procedures.
- **What it may not contain** (§24.3): `always` procedures, primitives, UDPs, and declarations or instances of modules, interfaces or other programs.
- **Where it lives** (§24.3): a program is instantiated like a module, usually at the top level. It can also be nested in a module or interface. Nested programs without ports, and top-level programs that nothing instantiates, are instantiated implicitly once.
- **How it is scheduled** (§24.3.1): statements sensitive to design signals and the `initial` procedures run in the Reactive region, `#` delays resume there, and nonblocking assignments update in the Re-NBA region. A subroutine called by a program thread runs in the reactive region set even when it is declared in a module, interface or package. Design code may not call program subroutines (§24.5).
- **How it ends** (§24.3): when all `initial` procedures of a program have finished, that program immediately ends every thread they started, so a monitor forked from them dies with them. If any program has an `initial` procedure, the simulation ends with an implicit `$finish` as soon as every thread started by the `initial` procedures of all programs has ended. `$exit` ends a program's threads on purpose (§24.7).
- **Clocking blocks still matter.** A program without clocking blocks is "more prone to races" with the design (§24.3.2). A program that reads design values only through clocking blocks clocked by design signals is insensitive to read-write races (§24.4).
- **Not deprecated.** Annex C lists what has been deprecated (C.2, C.3) and what is under consideration for deprecation (C.4: `defparam`, procedural `assign` and `deassign`, and some VPI definitions). Program blocks appear in none of these lists.

**See it.** In the region map below, a DUT flop and a program thread wake on the same edge. The program reads `q` into `seen` and drives `cmd <= 1`, and a design `assign` reads `cmd`. **Predict** what the program reads before you reveal the answer.

**Debrief.** `seen` gets the *new* `q`: program code runs in the Reactive region, which starts only after the active region set, including the NBA update of `q`, is empty (§24.3.1). Its `cmd <= 1` lands in Re-NBA, and the design's `assign led = cmd` then runs in a later Active pass of the same time slot (§4.5). A clocking-block read of `q` in the same program would return the photo from before the edge instead.

The same contrast in a program you can run:

```systemverilog
// compile
module tb_top;
  timeunit 1ns; timeprecision 1ps;

  logic clk = 1'b0;
  always #5 clk = ~clk;              // a module makes the clock: edges at 5, 15 ns

  // A design-side counter with a known start value. Plain always: some tools
  // reject a declaration initializer on a variable that an always_ff writes.
  logic [7:0] count = '0;
  always @(posedge clk) count <= count + 8'd1;   // NBA: count is 1 after 5 ns

  // A nested program without ports is instantiated implicitly (§24.3).
  program tb_prog;
    timeunit 1ns; timeprecision 1ps;

    clocking cb @(posedge clk);
      input count;                   // default #1step: the value before the edge
    endclocking

    initial begin
      @(posedge clk);                // program code resumes in Reactive (§24.3.1)
      $display("%0d ns: count=%0d cb.count=%0d", $time, count, cb.count);
    end                              // the last program thread ends: implicit $finish
  endprogram
endmodule
```

**Expected output** (illustrative: derived from §14.13 and §24.3.1, not captured from a simulator):

```text
5 ns: count=1 cb.count=0
```

The raw read sees the value after the edge's NBA update; the clockvar holds the photo from before the edge. Both reads are deterministic here, because program code runs after the clocking block event and the clock comes from a module (§14.4 NOTE, §14.13 NOTE). The run then ends at 5 ns by the implicit `$finish`, although `always #5` would run forever.

**How to work through it:**
1. Predict both numbers, then run it.
2. Add a second `@(posedge clk);` before the `$display`, predict again, then check: the line becomes `15 ns: count=2 cb.count=1`.
3. Replace `@(posedge clk)` with `@(cb)`. The output does not change: in a program both waits resume after the samples are stored.
4. If your simulator rejects the nested program, move it after `endmodule` and refer to the module's signals by hierarchical name: `@(posedge tb_top.clk)` in the clocking event and in the `initial`, `input count = tb_top.count;` in the clocking block, and `tb_top.count` for the raw read. A top-level program that nothing instantiates is instantiated implicitly (§24.3).

**Module or program at the top?** Both work. Practice, not a rule of the standard: class-based and UVM benches conventionally put the top in a module, here `tb_top`, and rely on clocking blocks, and that is what this curriculum does from here on. Class code inherits the region set of the thread that calls it (§24.3.1), so when `run_test()` is called from a module, every UVM thread runs in the active region set. Reach for a program when its reactive scheduling buys you something the clocking blocks cannot, such as several simultaneous clocks or clocks generated with nonblocking assignments (§24.4).

### Global clocking (awareness)

A clocking block may also be declared as the **global clocking** for all or part of the design (§14.14):

```systemverilog
// snippet: IEEE 1800-2023 §14.14
module top;
  logic clk1, clk2;
  global clocking sys @(clk1 or clk2); endclocking
  // ...
endmodule
```

Its main purpose is to say which clocking event in simulation corresponds to the primary system clock that formal verification uses. A module, interface, checker or program contains at most one, and the system function `$global_clock` refers to the one that is effective where it is called (§14.14). Testbench drivers and monitors do not use it; you will meet it in assertion code, where the global-clocking sampled value functions such as `$past_gclk` depend on it (§16.9.4).

### Debugging clocking blocks

Tools word their messages differently, so the symptoms below describe what you see rather than quote a message.

| Symptom | Cause | Fix |
|---|---|---|
| Monitor values differ between simulators, or change after an unrelated edit; the waveform looks fine | The monitor waits on `@(posedge vif.clk)` and then reads a clockvar, racing the sample update (§14.13) | Wait on `@(vif.mon_cb)` |
| Compile error on `##2;` in a class or in `tb_top` that points at a missing default clocking | `##` counts cycles of the default clocking, and none applies in that scope (§14.11, §14.12) | `repeat (2) @(vif.cb);`, or an interface task that uses `##` |
| Compile error when reading `cb.in_vld` or writing `cb.out_vld` | Reading an output clockvar or writing an input clockvar (§14.3) | Read through an input of `mon_cb`, or declare the signal `inout`; drive only outputs |
| The DUT sees only one of two values driven in one cycle | Both drives matured in one Re-NBA region; the last one wins (§14.16.2) | One drive per clockvar per cycle; send the second value next cycle |
| After a larger input skew, or with gate-level timing, outputs appear one cycle late or flicker between runs | The skew reaches back past the point where the output settles (§14.13) | Shorten the skew; use `#1step` in zero-delay RTL simulation |
| Reset takes effect only at the next clock edge | Reset is driven through a clocking block (§14.16) | Write it directly, between edges |
| The first stimulus appears at the first clock edge, not at time 0 | A drive issued before the first clocking event matures at that event (§14.16) | Expected. For a value at time 0, use a declaration initializer |
| A bus net stays `z` until the first drive | A clocking output on a net starts with its driver at `'z` (§14.16) | Drive an idle value at the start of the test |
| Compile error on `assign in_data = ...;` | A variable that a clocking block lists as an output may not be continuously assigned (§14.16.2) | Remove the `assign`; drive through `cb` |
| Compile error on `cb.din <= #4 v;` | Only `##` cycle delays are allowed inside a drive (§14.16) | Use an output skew, or `cb.din <= ##1 v;` |
| `vif.mon_cb` is not found through a handle of type `virtual pipe_if.mon_mp` | The modport does not list the clocking block (§25.5.5, §25.9.2) | Add `clocking mon_cb` to that modport |
| A program-based bench stops checking as soon as its main `initial` ends | Program termination ends every thread the `initial` procedures started (§24.3) | Keep the main thread alive until checking is done, then end the test on purpose |

### Recap

- A clocking block takes a photo of its inputs before each edge (`#1step`: Preponed; `#N`: N before; explicit `#0`: Observed) and delivers drives in Re-NBA, after the flops have read their inputs.
- `@(cb)` fires in Observed, after the photo is stored. Wait on it, never on `@(posedge clk)`, before you touch a clockvar.
- `##N` needs a default clocking in the same scope; `cb.sig <= ##N v` does not.
- One block per role: `cb` drives, `mon_cb` only samples. Asynchronous reset is written directly.
- Programs schedule testbench code in the reactive region set and are not deprecated; most benches use a module top with clocking blocks.

## Make It Work

### Worked example: a race-free pipeline testbench (M1)

This is the milestone M1 bench. It keeps the self-checking conventions of [F2E](/curriculum/T1_Foundational/F2E_First_Self_Checking_Testbench/index), an expected-value queue, `!==` comparisons, one `PASS=<n> FAIL=<m>` line and a watchdog, and adds an interface with two clocking blocks and an asynchronous reset. Read it top to bottom and **predict** the time of the first PASS line before you look at the trace.

```systemverilog
// compile
// tb_top.sv: a two-stage pipeline (the DUT) and its M1 testbench.

// ------------------------------------------------------------------- DUT
module pipe2 #(
  parameter int BUG = 0              // 1 plants an off-by-one bug; real RTL has none
) (
  input  logic       clk,
  input  logic       rst_n,          // asynchronous, active low
  input  logic       in_vld,
  input  logic [7:0] in_data,
  output logic       out_vld,
  output logic [7:0] out_data
);
  timeunit 1ns; timeprecision 1ps;

  logic       vld_q;
  logic [7:0] data_q;

  // Stage 1 computes in_data + 1; stage 2 registers it. Latency: two edges.
  always_ff @(posedge clk or negedge rst_n) begin
    if (!rst_n) begin
      vld_q    <= 1'b0;
      data_q   <= '0;
      out_vld  <= 1'b0;
      out_data <= '0;
    end else begin
      vld_q    <= in_vld;
      data_q   <= in_data + ((BUG == 1) ? 8'd2 : 8'd1);
      out_vld  <= vld_q;
      out_data <= data_q;
    end
  end
endmodule

// ------------------------------------------------------------- interface
interface pipe_if (input logic clk);
  timeunit 1ns; timeprecision 1ps;

  logic       rst_n = 1'b0;          // in reset from time 0 (§6.8); never a cb output
  logic       in_vld;
  logic [7:0] in_data;
  logic       out_vld;
  logic [7:0] out_data;

  // Driver view, with the default skews written out: sample #1step, drive #0.
  default clocking cb @(posedge clk);
    default input #1step output #0;
    output in_vld, in_data;
    input  out_vld, out_data;
  endclocking

  // Monitor view: inputs only, so code that uses it cannot drive the DUT.
  clocking mon_cb @(posedge clk);
    input rst_n, in_vld, in_data, out_vld, out_data;
  endclocking

  // ## is legal here: cb is this interface's default clocking (§14.11, §14.12).
  task automatic wait_cycles(input int n);
    ##(n);
  endtask
endinterface

// ------------------------------------------------------------- testbench
module tb_top;
  timeunit 1ns; timeprecision 1ps;

  logic clk = 1'b0;
  always #5 clk = ~clk;              // rising edges at 5, 15, 25 ns ...

  pipe_if bus (.clk(clk));

  // Set .BUG(1) to prove that the bench can fail.
  pipe2 #(.BUG(0)) dut (
    .clk(clk), .rst_n(bus.rst_n),
    .in_vld(bus.in_vld), .in_data(bus.in_data),
    .out_vld(bus.out_vld), .out_data(bus.out_data)
  );

  logic [7:0] exp_q[$];              // expected outputs, oldest first
  int pass_cnt = 0;
  int fail_cnt = 0;

  // Driver. Call it right after @(bus.cb): the drives land in Re-NBA after
  // this edge (§14.16), so the DUT captures them at the next edge.
  task automatic send(input logic [7:0] data);
    bus.cb.in_vld  <= 1'b1;
    bus.cb.in_data <= data;
    exp_q.push_back(data + 8'd1);    // the specification: out = in + 1
    @(bus.cb);
  endtask

  // Monitor. It wakes on the clocking block event, after this edge's samples
  // are stored (§14.10, §14.13), and reads nothing but mon_cb.
  task automatic monitor();
    logic [7:0] expected;
    forever begin
      @(bus.mon_cb);                 // never @(posedge clk) before a mon_cb read
      if (bus.mon_cb.rst_n !== 1'b1) continue;   // ignore samples taken in reset
      if (bus.mon_cb.out_vld === 1'b1) begin
        if (exp_q.size() == 0) begin
          fail_cnt++;
          $error("CHK unexpected output %h", bus.mon_cb.out_data);
        end else begin
          expected = exp_q.pop_front();
          if (bus.mon_cb.out_data !== expected) begin
            fail_cnt++;
            $error("CHK got %h, expected %h", bus.mon_cb.out_data, expected);
          end else begin
            pass_cnt++;
            $display("%0d ns PASS data=%h", $time, expected);
          end
        end
      end
    end
  endtask

  initial monitor();                 // runs for the whole test

  initial begin : main
    bus.cb.in_vld <= 1'b0;           // no clocking event yet: lands at 5 ns (§14.16)
    #12 bus.rst_n = 1'b1;            // release between edges, directly, not via cb
    @(bus.cb);                       // the 15 ns edge
    send(8'h10);
    send(8'h20);
    send(8'h30);
    bus.cb.in_vld <= 1'b0;           // lands after the 45 ns edge
    bus.wait_cycles(4);              // drain: the interface counts cycles with ##
    fail_cnt += exp_q.size();        // expectations that never arrived
    if (pass_cnt + fail_cnt == 0) fail_cnt++;   // a run that checked nothing fails
    $display("PASS=%0d FAIL=%0d", pass_cnt, fail_cnt);
    $finish;
  end

  initial begin : watchdog
    #1us;                            // far longer than the 85 ns this test needs
    $fatal(1, "WDOG still running at %0d ns", $time);
  end
endmodule
```

**Expected output** (illustrative: derived by hand from §14.13 and §14.16, not captured from a simulator; your simulator adds its own banner and a line for `$finish`):

```text

65 ns PASS data=31
PASS=3 FAIL=0
```

What happens, edge by edge:
- **Before the window.** The time-0 drive `bus.cb.in_vld <= 1'b0;` lands at the 5 ns edge, where the DUT is still in reset. `rst_n` rises at 12 ns, between edges.
- **Edge 0, 15 ns (◆).** `main` resumes from `@(bus.cb)` and calls `send(8'h10)`. `in_vld` and `in_data` change in Re-NBA, after the DUT's flops have read their old values.
- **Edge 1, 25 ns (▼).** The DUT captures `in_vld = 1` and `in_data = 10` into stage 1, the same values `mon_cb` samples. `send(8'h20)` drives the next item.
- **Edge 2, 35 ns.** Stage 2 takes `11`, so `out_vld` and `out_data` change just after this edge. The X on `out_data` is stage 1's value from 15 ns, when `in_data` had never been driven; `out_vld` is 0, so nobody reads it.
- **Edges 3 to 5, 45 to 65 ns (✓).** `mon_cb` samples `out_vld = 1` with `11`, `21` and `31`, and the monitor prints a PASS line each time. After the 45 ns edge, `main` drives `in_vld` low.
- **Edge 7, 85 ns.** `wait_cycles(4)` returns, and `main` prints `PASS=3 FAIL=0` and calls `$finish`.

### Prove it can fail

1. Change `.BUG(0)` to `.BUG(1)`: stage 1 now adds 2. **Predict** the log before you run.
2. Run it. Every result fails. Here `[error @ t]` stands for your simulator's own `$error` prefix, which names the time, file and line (§20.10):

```text

[error @ 55 ns] CHK got 22, expected 21
[error @ 65 ns] CHK got 32, expected 31
PASS=0 FAIL=3
```

3. Set `.BUG(0)` again before you continue.

### Convert a racy bench in six steps

Use this whenever you inherit a bench that drives the DUT with raw assignments:

1. **Driver block.** Add a clocking block to the interface for the driver: the DUT inputs it drives as outputs, and any DUT outputs it reacts to as inputs. Make it the default clocking if code in the interface uses `##`.
2. **Monitor block.** Add a second clocking block with inputs only: every signal the monitor checks, including reset.
3. **Drives.** Make the driver wait on `@(bus.cb)`, and turn every `bus.sig = v;` or `bus.sig <= v;` into `bus.cb.sig <= v;`.
4. **Reads.** Make the monitor wait on `@(bus.mon_cb)` and read only `bus.mon_cb.sig`. Delete every `@(posedge clk)` from testbench code.
5. **Asynchronous signals.** Leave reset, and any other asynchronous input, as direct writes made between edges.
6. **Verify.** Declare time units in every design element, rerun, compare the log with the old one, and run the mutant: the bench must fail with `.BUG(1)`.

**Checklist before moving on:**
- [ ] Every DUT input except the asynchronous reset is written only through `cb`.
- [ ] Every clockvar read follows `@(bus.cb)` or `@(bus.mon_cb)`, never `@(posedge clk)`.
- [ ] `##` appears only where a default clocking is in scope.
- [ ] No clockvar is driven twice in one cycle, unless the last value is the one you want.
- [ ] Every design element declares its time unit and precision.
- [ ] The bench prints `PASS=3 FAIL=0` with `.BUG(0)` and `PASS=0 FAIL=3` with `.BUG(1)`.
- [ ] I can explain, edge by edge, why the first PASS line appears at 45 ns.

## Push Further

### Expert: synchronous-drive corner cases

- **Glitches inside one time slot.** The scheduler can pass through Re-NBA more than once in a time slot, for example when reactive code wakes the design and the loop comes back. Drives that assign different values to one clockvar in different passes make its signal change more than once in that time slot; the standard's example has a variable go 1, 0, 1 at the first edge (§14.16.2).
- **Drives and nonblocking assignments.** A synchronous drive and a procedural nonblocking assignment to one variable in the same time slot take effect in arbitrary order (§14.16.2). Give such a variable one kind of writer.
- **Two clocking blocks, one variable.** A variable driven by a `posedge` block and a `negedge` block takes whichever value was driven most recently, and each block writes only in cycles in which it is driven. One module can model a double-data-rate device this way; it is equivalent to a single block clocked on `edge clk` (§14.16.2).
- **Nets.** Each clocking output on a net is its own driver with (strong1, strong0) strength, initialized to `'z`. Several clocking outputs and any other drivers on one net resolve as the net type defines (§14.16, §14.16.2).
- **`inout` reads.** A drive to an `inout` clockvar does not change its input side: after `cb.a <= c;`, reading `cb.a` still returns the last sample (§14.16.1).
- **Counting.** The cycle-delay rule in "Several drives to one signal in one cycle" summarizes the examples of §14.16, where `#3 cb.v <= expr1;` matures in cycle 1, and of §14.16.2. It does not follow from applying the general between-edges sentence of §14.16 and then counting the cycle delay, which would put `#1 cb.v <= ##2 expr3;` in cycle 4 instead of cycle 3. `##0` on the right-hand side of a drive has no effect (§14.11).

### Expert: cycle-delay and default-clocking corner cases

- **`##0`.** If the clocking block event of the current time slot has already happened, for example right after `@(cb)`, `##0` continues at once; otherwise it waits for that event (§14.11).
- **Expressions.** `##(expr)` accepts any expression that evaluates to a non-negative integer, including a variable, as in the `wait_cycles()` task (§14.11).
- **Default scope.** A default clocking covers its module, interface, program or checker and the modules, interfaces and checkers nested in it, but not instantiated ones (§14.12). `default clocking busA;` may name a clocking block declared in an enclosing module (§14.12, Example 2).
- **Assertions share it.** The same default clocking clocks concurrent assertions that name no clock (§16.16). Changing it to suit a cycle delay also changes those assertions.

### Expert: input-sampling corner cases

- **Explicit `#0` is not resampled.** When the scheduler comes back through Observed in the same time slot, explicit-`#0` inputs keep the value from the first pass, unless a new clocking event occurs in the active region set (§14.13).
- **Programs and the clock source.** Program code that reads a clockvar after `@(posedge clk)` does not race when a module generates the clock. When program code triggers the clocking event, reads that do not synchronize to it race with the sample update (§14.13 NOTE).
- **Synchronous events use samples.** `@(cb.sig)`, `@(posedge cb.sig)` and slices of them use the sampled values; a dynamic slice index is evaluated once, when the `@` executes (§14.15).
- **Assertions.** When a concurrent assertion uses a clockvar, its value comes from the clocking block's sample alone (§16.18). Properties and sequences can be declared inside a clocking block (§14.3, §16.16). [I-SV-4A](/curriculum/T2_Intermediate/I-SV-4A_SVA_Fundamentals/index) owns assertion clocking.
- **`1step` can change size.** `1step` is the global time precision (§3.14.3), so adding any module with `timeprecision 1fs` shortens it. The sample is still the last value before the edge.
- **Before the first edge.** §14.13 defines a clockvar's value only as the sample of the most recent clocking event, so what a read returns before the first one is tool-dependent. Do not rely on it.
- **What may be named.** A clocking signal may not be a variable restricted to a procedural block (§14.3): an automatic variable, or an element or member of a dynamic variable such as a dynamic array, whose references §6.21 limits to procedural code.
- **One signal, many blocks.** Each block samples a shared signal with its own clocking event (§14.13).

### Expert: several clocks and testbench-internal races

- **Programs and several clocks.** §24.4 states the limit plainly: input sampling addresses a single clocking block. With several clocks, the arbitrary order in which simultaneous or overlapping clocks are processed is still a race source. The program construct addresses it by running after all design events, including clocks driven by nonblocking assignments.
- **One clock, many testbench threads.** Blocks on one clock share one synchronization event (§14.6), so processes waiting on `@(bus.cb)` and `@(bus.mon_cb)` wake together and run in any order (§4.7). In the M1 bench the driver pushes onto `exp_q` and the monitor pops from it. That is deterministic only because the DUT's latency puts every push at least two edges before its pop. If a push and the pop that needs it could fall in one time slot, the result would depend on which thread ran first. Pass data between testbench threads through a mailbox or queue whose order you control ([I-SV-5](/curriculum/T2_Intermediate/I-SV-5_Synchronization_and_IPC/index)), or let one thread own both ends.

### Expert: skews as a timing model

- **Zero-delay RTL.** `#1step` inputs and `#0` outputs are exact; nonzero skews only move the sample and the update in time (§14.4, §14.16).
- **Gate-level timing.** With back-annotated delays, DUT outputs settle some time after the edge. The input skew then acts as a setup window: each output must settle before the sample point, the edge minus the skew, or the bench reads last cycle's value. The visual's +9 ns path with a `#2ns` skew is exactly this failure.
- **Output skew.** A nonzero output skew models clock-to-output delay and gives the DUT hold margin in gate-level runs, and it makes waveforms easier to read. It also moves every drive into a later time slot (§14.16).
- **Parameters.** Practice, not a rule: verification IP often exposes skews as parameters, which §14.4 allows, so one agent serves RTL and gate-level runs. The right values depend on your library and tool flow (tool-dependent).

### Expert: program blocks in depth

- **Scope.** Code outside every program may not reference program signals, the variables and nets declared in a program. Hierarchical references from one program into another are legal (§24.3). Anonymous programs in a package or compilation unit add tasks, functions and classes to the program-wide space without creating a scope (§24.6).
- **Calls.** A program may call module tasks and functions; a module task called from a program runs in the reactive region set, and the same task called from a module runs in the active region set (§24.5).
- **Assertions.** Concurrent assertions in a program are evaluated in the Observed region on Preponed values, exactly as in module code (§24.3.1).
- **`$exit`.** Called from a thread that originates in an `initial` procedure of a program, it ends all `initial` procedures of that program and their descendants. Called from any other thread, it is ignored, and the tool may warn (§24.7).
- **Ports without clocking blocks.** Program ports update their design-side objects in the reactive region set, which forces extra passes of the scheduler loop (§24.3.2).
- **UVM.** In uvm-core 2020.3.1, `run_test()` ends the simulation with `$finish` when `finish_on_completion` is set, which it is by default (`src/base/uvm_root.svh`). Call it from a module top, and the whole UVM run lives in the active region set (§24.3.1).

### Expert: methodology trade-offs

Practice, not rules of the standard:

| Approach | Race-free drives | Pre-edge reads of DUT outputs | Costs |
|---|---|---|---|
| Clocking blocks (`cb`, `mon_cb`) | yes: Re-NBA (§14.16) | yes, for any DUT: `#1step` | Declarations to keep in step with the interface; the `@(posedge clk)` trap |
| `<=` drives after `@(posedge clk)`, as in F2E | yes | only while the DUT writes its outputs with `<=` | Timing spread over many tasks; no skews to tune |
| Drives on the opposite clock edge | yes, for one clock | yes: reads at the opposite edge see settled values | Halves the timing budget in gate-level runs; breaks with several edges or clocks |

- **One block per role.** `cb` for the driver and `mon_cb` for the monitor, with modport-typed handles (`virtual pipe_if.drv_mp`) so that the compiler enforces the split (§25.5.5, §25.9.2).
- **Narrow monitor blocks.** Every input clockvar is sampled at every clocking event (§14.13), so a block that lists a wide bus samples it every cycle, used or not. The run-time cost is tool-dependent; list what the monitor checks.
- **Module or program top.** Module top and clocking blocks for class-based benches; a program when reactive scheduling solves a real problem, such as several simultaneous clocks (§24.4).

### Expert: global clocking in detail

- **Placement.** At most one global clocking per module, interface, checker or program, and never in a generate block. Several may exist in different parts of the hierarchy, but at most one is effective at each point (§14.14).
- **Lookup.** `$global_clock` searches the enclosing instance, then its parents, for the nearest global clocking declaration; reaching a top-level block without one is an error. In sequences, properties and checker arguments, the search starts where the assertion appears, after substitution (§14.14).
- **Compatibility.** IEEE 1800-2009 allowed only one global clocking in the whole design, usable everywhere. A design that declares it in a non-top module and uses `$global_clock` outside that subhierarchy does not conform to IEEE 1800-2023 (§14.14 NOTE).
- **Use.** The global-clocking sampled value functions, such as `$past_gclk` and `$future_gclk`, may be used only when a global clocking is defined (§16.9.4).

### Kata 1 (guided): expose a hidden race, then fix it

**Objective:** see why a value-only checker can miss a race, catch it with a cycle-accurate check, and remove it with the six conversion steps (objective 4).

**Starter.** Take the Make It Work bench. Add the racy driver below next to `send()`, and in `main` replace everything from `@(bus.cb);` to `bus.wait_cycles(4);` with the lines shown in the comment.

```systemverilog
// snippet: Kata 1 starter, a racy driver (do not copy into real benches)
task automatic send_racy(input logic [7:0] data);
  @(posedge clk);                    // wakes in the Active region with the DUT's flops
  bus.in_vld  = 1'b1;                // blocking writes at the active edge race (§4.7)
  bus.in_data = data;
  exp_q.push_back(data + 8'd1);
endtask

// in main, after #12 bus.rst_n = 1'b1;
//   send_racy(8'h10);
//   send_racy(8'h20);
//   send_racy(8'h30);
//   @(posedge clk) bus.in_vld = 1'b0;
//   repeat (4) @(posedge clk);
```

**Steps:**
1. **Predict.** Does the queue-based monitor notice anything if the simulator runs `send_racy()` before the DUT's flops at every edge? Write down why.
2. **Add a cycle-accurate check.** The DUT's output at edge *e* must equal the input `mon_cb` sampled at edge *e* − 2, plus one. Write an `initial` block that keeps the last two input samples and compares.
3. **Run** on your simulator. If it always picks the same order, swap the textual order of the DUT instance and the `initial` blocks, try a second simulator, or use the debugger in [F3C](/curriculum/T1_Foundational/F3C_Delta_Cycles_and_Race_Conditions/index) to see both orders.
4. **Convert** the driver with the six steps from Make It Work, and rerun.

**Acceptance:** after the conversion, no cycle-check errors and `PASS=3 FAIL=0` in every order and on every simulator you try, and a failing run with `.BUG(1)`.

<details>
<summary>Worked solution (try the kata first)</summary>

**Step 1.** The queue-based monitor checks values and their order, not their timing. If `send_racy()` runs first at an edge, the DUT captures each item one edge early, so the results arrive one edge early, in the right order and with the right values: `PASS=3 FAIL=0` either way. The race is real but invisible to that checker.

**Step 2.** A cycle-accurate check sees the shift:

```systemverilog
// snippet: Kata 1 cycle-accurate check, added to tb_top
initial begin : cycle_check
  logic       vld_d1, vld_d2;        // in_vld sampled 1 and 2 edges ago
  logic [7:0] dat_d1, dat_d2;        // in_data + 1 sampled 1 and 2 edges ago
  forever begin
    @(bus.mon_cb);
    if (bus.mon_cb.rst_n !== 1'b1) begin
      vld_d1 = 1'b0;                 // the pipeline is empty in reset
      vld_d2 = 1'b0;
    end else begin
      if (bus.mon_cb.out_vld !== vld_d2 ||
          (vld_d2 && bus.mon_cb.out_data !== dat_d2)) begin
        fail_cnt++;
        $error("CYC out_vld=%b out_data=%h, expected %b %h",
               bus.mon_cb.out_vld, bus.mon_cb.out_data, vld_d2, dat_d2);
      end
      vld_d2 = vld_d1;
      dat_d2 = dat_d1;
      vld_d1 = bus.mon_cb.in_vld;
      dat_d1 = bus.mon_cb.in_data + 8'd1;
    end
  end
end
```

**Step 3.** In the order where `send_racy()` runs first, the DUT captures `8'h10` at 15 ns, while `mon_cb`'s photo at 15 ns still shows `in_vld = 0`. The result appears at the 35 ns sample, one edge earlier than the check expects, so it reports `CYC` errors from 35 ns on. In the order where the flops run first, both views agree and the check passes. Same code, two outcomes: that is the race.

**Step 4.** After the conversion, `send()` drives through `cb` after `@(bus.cb)`. The drive lands in Re-NBA, after the flops have read their inputs, so the DUT always captures at the edge after the drive, and that is the edge at which `mon_cb` samples the same values. The check passes in every order because no read and no write of `in_vld` or `in_data` share a region any more (§4.7, §14.13, §14.16).

</details>

### Kata 2 (independent): back-to-back bursts

**Objective:** write a driver that sends bursts with no idle cycles, and a monitor that keeps up (objective 3).

**Requirements:**
- Add `send_burst(input logic [7:0] items[$])`, which drives one item per cycle with no idle cycle between items, then drops `in_vld`.
- Add `idle(input int n)`, which keeps `in_vld` low for `n` cycles.
- In `main`, send a burst of four items starting right after the 15 ns edge, idle for two cycles, then send a burst of two.
- No `@(posedge clk)` anywhere in testbench code; `##` only inside the interface; at most one drive per clockvar per cycle.
- **Predict** the edges at which the monitor checks the first burst, then run. The bench must print `PASS=6 FAIL=0` with `.BUG(0)` and fail with `.BUG(1)`.

<details>
<summary>Worked solution (try the kata first)</summary>

```systemverilog
// snippet: Kata 2 worked solution, tasks in tb_top
task automatic send_burst(input logic [7:0] items[$]);
  foreach (items[i]) begin
    bus.cb.in_vld  <= 1'b1;          // one drive per clockvar per cycle
    bus.cb.in_data <= items[i];
    exp_q.push_back(items[i] + 8'd1);
    @(bus.cb);
  end
  bus.cb.in_vld <= 1'b0;             // the cycle after the burst is idle
endtask

task automatic idle(input int n);
  bus.cb.in_vld <= 1'b0;
  repeat (n) @(bus.cb);
endtask

// in main, after @(bus.cb) at 15 ns:
//   send_burst({8'h01, 8'h02, 8'h03, 8'h04});
//   idle(2);
//   send_burst({8'h05, 8'h06});
//   bus.wait_cycles(4);
```

**Prediction.** The first burst is driven after the edges at 15, 25, 35 and 45 ns, captured at 25, 35, 45 and 55 ns, and checked by `mon_cb` at 45, 55, 65 and 75 ns. At 45 ns the driver pushes the fourth expectation while the monitor pops the first one, in the same time slot and in either order. That is safe only because the queue already holds three entries, so the pop never depends on the push.

**Why one drive per cycle matters.** `send_burst()` drives each clockvar once per loop iteration and then waits on `@(bus.cb)`. Its final `in_vld <= 1'b0` and the first drive of `idle()` fall in the same cycle, but both write 0, so the last-drive-wins rule (§14.16.2) changes nothing; with different values, only the later statement would count.

</details>

### Drill: drive forms, skews and the default clocking

Use the experiment visual's advanced controls. For each setting, predict when `din` changes and at which edge the DUT captures `A5`, then reveal. The drive executes right after `@(cb)` at edge 2, at 15 ns.

1. `cb.din <= v;` with output skew `#0`, then `#2ns`.
2. `cb.din <= ##1 v;` with output skew `#0`.
3. `##1 cb.din <= v;` with output skew `#0`, then with the default clocking unticked.

<details>
<summary>Answers</summary>

1. With `#0`, `din` changes in Re-NBA at 15 ns and is captured at edge 3 (25 ns). With `#2ns`, it changes in Re-NBA at 17 ns and is still captured at edge 3 (§14.16).
2. The update is postponed one cycle of `cb`: `din` changes in Re-NBA at 25 ns, and the DUT captures it at edge 4 (35 ns). The statement does not block (§14.16).
3. The thread blocks until edge 3 and then drives, so `din` changes in Re-NBA at 25 ns and is captured at edge 4. Without a default clocking the line does not compile (§14.11).

</details>
