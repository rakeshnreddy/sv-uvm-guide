## Quick Take
- **What it is:** **Clocking blocks** define a timing discipline for driving and sampling signals relative to a clock edge. **Program blocks** are an older mechanism (still in IEEE 1800, not deprecated) for running testbench code in the reactive region set.
- **Why it matters:** Without clocking blocks, you risk "race conditions" where the testbench and DUT try to read/write a signal at the exact same simulation time, leading to unpredictable results.
- **The Analogy:** A clocking block is like an airlock. It ensures that data only enters or leaves the clean room (the testbench) at specific, safe times, preventing contamination (race conditions).

## Build Your Mental Model

### The Race Condition Problem

The testbench and the DUT wake on the same clock edge, and IEEE 1800 lets the simulator run them in any order (§4.7). The dangerous case is the testbench **driving** a DUT input with a blocking assignment at that edge: if the testbench happens to run first, the DUT's flop captures the *new* value instead of the pre-edge value.

**Race-Prone Testbench (Avoid this):**
```systemverilog
// RTL: reads din in Active, writes q in NBA
always_ff @(posedge clk) q <= din;

// Testbench: also runs in Active on the same edge
always @(posedge clk) begin
  din = next_value; // RACE: the flop may or may not see this value
end
```

Reading `q` with a plain `@(posedge clk)` is deterministic *only* while the DUT writes `q` with `<=`: the read happens in Active, before the NBA update. If any design logic on that path uses blocking assignments, the read races too. A clocking block removes both risks. See F3C's Race Condition Debugger to try every legal order.

**Clocking blocks solve this by:**
1.  **Sampling** inputs before the clock edge. With the default `#1step` input skew the sample is taken in the **Preponed** region, so the testbench reads the stable, old value. A `#N` skew samples N time units earlier, in the Postponed region of that time step; an explicit `#0` samples at the edge, in **Observed** (§14.13).
2.  **Driving** outputs synchronized to the clock edge. With the default `#0` output skew the update is scheduled in the **Re-NBA** region of that time step, whichever code issued the drive (§14.16), so it lands after every design NBA update.
3.  **Signalling** the clocking event `@(cb)` in the **Observed** region (§14.10), after the design's NBA updates. Code that waits on `@(vif.cb)` therefore never competes with the flops for the same edge.

Picture the clocking block as a camera and a delivery truck on the timeline: it takes a **photo** of each input just before the edge (▼) and **delivers** each drive after the edge (◆). The visual below runs a tested model of those rules over four clock cycles.

What to take away:

- The photo is taken *before* the edge for every skew except an explicit `#0`. A nonzero input skew is a setup window: a DUT output that changes inside it is only seen one cycle later.
- `@(cb)` then `cb.x` is always safe. `@(posedge clk)` then `cb.x` races the clocking block's own update (§14.13), so never mix the two styles.
- A synchronous drive issued after `@(cb)` at edge *k* reaches the DUT's flops at edge *k* + 1, whatever the output skew below one period.

## Key Concepts

### Clocking Blocks (LRM Clause 14)
- **Input Skew:** When to sample inputs relative to the clock (default: `#1step`).
- **Output Skew:** When to drive outputs relative to the clock (default: `#0`).
- **Cycle Delay:** `##N` waits for N clocking events of the **default clocking** block. It needs a `default clocking` declaration in that module, interface, program or checker (§14.11, §14.12); otherwise the compiler reports an error. A class in a package has no default clocking, so class-based drivers use `repeat (N) @(vif.cb);` (or call an interface task that uses `##`).
- **`##` inside a drive:** `cb.sig <= ##2 v;` evaluates `v` now and updates `sig` two cycles of `cb` later; the statement does not block, and it needs no default clocking because it counts `cb`'s own clock (§14.16). `##2 cb.sig <= v;` instead blocks the process for two default-clocking cycles first.

### A driver and a monitor through `vif.cb`

This is the pattern every UVM agent uses. The interface owns the timing; the classes only wait on clocking events and touch signals through clocking blocks.

```systemverilog
interface fifo_if (input logic clk);
  logic       rst_n;            // asynchronous reset: drive it directly, not through cb
  logic [7:0] din, dout;
  logic       push, full;

  default clocking cb @(posedge clk);   // the default clocking of this interface (§14.12)
    default input #1step output #0;
    output din, push;
    input  full, dout;
  endclocking

  clocking mon_cb @(posedge clk);       // monitor view: inputs only, #1step by default
    input din, push, full, dout;
  endclocking

  // ## is legal here because cb is this scope's default clocking (§14.11).
  task automatic wait_cycles(int n);
    ##(n);
  endtask
endinterface

class fifo_driver;
  virtual fifo_if vif;

  task push_byte(byte data);
    @(vif.cb);                          // resume after the clocking event (Observed)
    while (vif.cb.full) @(vif.cb);      // full is the #1step sample: no race with the DUT
    vif.cb.din  <= data;                // lands in Re-NBA of this edge (§14.16)
    vif.cb.push <= 1'b1;
    @(vif.cb);                          // the DUT captured din/push at this edge
    vif.cb.push <= 1'b0;
  endtask
endclass

class fifo_monitor;
  virtual fifo_if vif;

  task run();
    forever begin
      @(vif.mon_cb);                    // never @(posedge vif.clk) before reading mon_cb (§14.13)
      if (vif.mon_cb.push && !vif.mon_cb.full)
        $display("%0t push %h", $time, vif.mon_cb.din);
    end
  endtask
endclass
```

The driver raises `push` after `@(vif.cb)` at edge *k*; the DUT's flops capture it at edge *k* + 1. The monitor wakes on `@(vif.mon_cb)` at edge *k* + 1 and sees `push` = 1 in its #1step sample, the same edge on which the DUT accepted the byte. Both classes get `vif` from `uvm_config_db` (F4B).

### Program Blocks (LRM Clause 24)
- **Purpose:** Originally designed to separate testbench execution (Reactive region) from DUT execution (Active region).
- **Modern Usage:** rarely used with UVM (the standard has not deprecated them). UVM class code runs in the active region set, so UVM benches rely on clocking blocks — not phases, which order whole phases rather than events within one time slot — for same-edge race avoidance.
- **Recommendation:** Avoid `program` blocks for new UVM testbenches. Use `module` for the top-level testbench and `clocking` blocks for timing.

## Make It Work
1.  **Define Clocking:** Add a `clocking` block to your interface for each agent (Driver, Monitor).
2.  **Set Skews:** Start from the defaults, `default input #1step output #0;`. A nonzero output skew (for example `#1ns`) makes waveforms easier to read but moves drives to a later time step; choose it deliberately.
3.  **Drive/Sample:** In your testbench/UVM driver, *always* access signals through the clocking block handle (e.g., `vif.cb.req`).
4.  **Wait for Events:** Use `@(vif.cb)` to wait for the clock edge. Do not wait on `@(posedge vif.clk)` and then read `vif.cb` inputs: that read races the clocking block's update (§14.13).
5.  **Keep reset out of the clocking block** when it is asynchronous: drive it directly so it can change between edges.
