## Quick Take

- **What it is:** A **time slot** is everything the simulator does at one simulation time. Inside it, the scheduler works through ordered **regions** and loops back to the Active region whenever new events appear (IEEE 1800-2023 §4.5). Each loop back is a **delta cycle**: more work, zero simulated time. A **race condition** is code whose result depends on the order in which the simulator runs processes that are ready at the same time, an order the standard deliberately leaves open (§4.7).
- **Why it matters:** A race can pass on one simulator and fail on the next, or flip after a harmless-looking file reorder, and the waveform looks innocent because everything happens at one time stamp. The race that costs verification engineers the most sits between the testbench (TB) and the design under test (DUT), which wake on the same clock edge. The cure is a rule you will apply for your whole career: a flop reads in Active and writes in the NBA region (`<=`), and a testbench writes where the flops' reads cannot see it on that edge.
- **The Analogy:** A time slot is a stage play with a strict act order. Actors who enter in the same act may speak in any order, and if the plot depends on who speaks first, the script is broken. *Where it breaks:* a real play never returns to an earlier act, but the scheduler goes back to Active many times in the same instant (the §4.5 loop), and it may even pause an actor in mid-speech to let another one speak (§4.7).

**You will be able to:**
1. Trace one clock edge through its delta cycles and predict every variable's final value, including what `$display` and `$strobe` print.
2. Diagnose a read-write or write-write race: show that the result depends on the order of processes woken in the same time slot (§4.7, §4.8), and prove it by exploring every legal order.
3. Debug testbench races from their symptoms: blocking drives at the active clock edge, `#0` workarounds, and reads of DUT signals written by blocking code.
4. Choose a hardware-faithful fix (nonblocking drives, opposite-edge drives, clocking blocks or program blocks) and justify it by its trade-offs.
5. Write race-free code: flops with `<=`, one writer per variable, and testbench drives with `<=` today and through a clocking block from F4C.

### Picture a ladder, not an instant

When you read `@(posedge clk)`, do not picture one moment. Picture this ladder. The clock edge drops an event into **Active**. The scheduler drains Active, then moves the events of the next non-empty region back into Active and loops, all at the same simulation time (§4.5). Select each rung and, before you read its card, name one statement from your own code that lands there.

<TimeSlotRegionMap />

Three things to burn in:

1. **Preponed** and **Postponed** are read-only. Preponed holds the "before" photo of every value; concurrent assertions and clocking-block inputs use that photo (§4.4.2.1, §16.5.1, §14.13). Postponed is where `$strobe` prints the settled values (§4.4.2.9, §21.2.2).
2. A blocking assignment (`=`) writes **at once**, in the region its process runs in: Active, for module code. A nonblocking assignment (`<=`) reads its right side when it executes but writes later, in **NBA** (§10.4.1, §10.4.2, §4.9.4).
3. Processes that are ready in one region run in **any order** (§4.7). Statements *inside* one `begin`…`end` always run in source order (§4.6).

**A delta cycle, precisely.** When the NBA region applies an update and that change wakes a process, for example `assign y = ~q`, the scheduler returns to Active in the same time slot (§4.5, §4.9.1). Each such return is one delta cycle; the visualizer below counts them as Δ. A slot may need many, and none of them advances `$time`. (F3B explains three simplified cards on the map: the Preponed assertion example, the Reactive program example and the Re-NBA wording.)

### Watch one clock edge, step by step

Step through the scheduler below. Three things move together: the highlighted line of code, the ▶ marker on the ladder, and the waveform cursor. The waveform's horizontal axis is **scheduler steps**, not time; a real waveform viewer would draw all of it at `t = 10 ns`.

**Predict first.** For each scenario, write down the final `q2`, or the printed values, for every process order before you press play. Then work through the scenarios in this order:

1. **Shift register · `=`** with *Stage A → Stage B*.
2. The same scenario with *Stage B → Stage A*. Same code, a different `q2`.
3. **Shift register · `<=`**. Both orders now agree.
4. **$display vs $strobe**. One process prints two different values of `q` in one time slot.
5. **TB drive · `=`**, **TB drive · `<=`** and **TB · clocking block**: the same story at the boundary between testbench and DUT, which the rest of this section explains.

<TimeSlotTraceVisualizer scenario="shift-blocking" scenarios={["shift-blocking", "shift-nba", "display-vs-strobe", "tb-blocking-drive", "tb-nba-drive", "tb-clocking-block"]} />

What you just saw, in words:

- With `=`, Stage A's write to `q1` is visible the instant it happens. Whether Stage B sees it depends only on which stage ran first.
- With `<=`, both stages read in Active **before** either write lands in NBA. Order cannot leak into the result, which is exactly how two physical flip-flops behave.
- `$display` prints during Active, before the NBA update lands. `$strobe` prints at the end of the time slot, after every update (§21.2.2).
- Every step happened at one simulation time. That is why a race hides in a waveform: both orders produce the same time stamp.

### What a race is

A **race condition** needs three things:

1. Two or more processes are ready in the same time slot, usually because one event, such as a clock edge, woke them all. The standard lets the simulator consider the processes woken by an update in an arbitrary order (§4.3), and take ready events from the Active region in any order (§4.7).
2. They share a variable: one writes it, and another reads it or writes it too.
3. The result depends on which one runs first.

Take away any one of the three and the race is gone. The standard states the consequence itself (§4.8): races are possible, and a simulator that picks either order is correct. So code that is right in only one order is wrong, even if your simulator always happens to pick that order.

Races come in two shapes:

| Shape | What happens | Example | Cure |
|---|---|---|---|
| **Read-write** | One process writes a variable with `=`; another process woken by the same event reads it and sees the old or the new value | The blocking shift register above | Write with `<=`, so every read on this edge comes before the write lands |
| **Write-write** | Two processes write the same variable in the same time slot. The last write decides the value (§6.5), and which write is last depends on their order | Two `always` blocks that both assign `cnt` on one clock edge | One writer per variable |

The **testbench race** is a read-write race across the boundary between testbench and DUT; it gets its own section below.

**A write-write race, traced.** Even `<=` does not save two writers:

```systemverilog
// snippet: inside a module with logic clk, clr; logic [3:0] cnt;
always @(posedge clk) cnt <= cnt + 4'd1;      // P1: count
always @(posedge clk) if (clr) cnt <= 4'd0;   // P2: clear
```

With `cnt` = 5 and `clr` = 1 before the edge:

| Order in Active | NBA updates, in execution order (§4.6) | `cnt` after the slot |
|---|---|---|
| P1, then P2 | 6, then 0 | 0 |
| P2, then P1 | 0, then 6 | 6 |

Both rows are legal (§4.7). §10.4.2 describes exactly this case: when two blocks that execute concurrently assign one variable with `<=`, its final value is indeterminate. The fix is a single writer, `always_ff @(posedge clk) cnt <= clr ? 4'd0 : cnt + 4'd1;`. With `always_ff`, a second process that writes `cnt` is illegal (§9.2.2.4, which applies the rule of §9.2.2.2), so the tool reports this race as an error instead of letting it run.

### Experiment: make and break the race yourself

Flip any assignment between `=` and `<=`, predict, then let the model run **every** legal order. Two experiments are worth doing:

- On **Two-flop shift register**, make one stage `<=` and leave the other `=`. Predict which of the two mixes still races before you look.
- On **TB drives the DUT input**, set the testbench drive to `<=` and flip the DUT's `<=` to `=`. The flop now captures correctly, but the testbench's read of `q` into `seen` races: that is a read of a signal written by blocking RTL.

Open *advanced experiment* to see why `#0` is not a fix: it moves a process to the Inactive region, where the next process that also uses `#0` races it again.

<RaceConditionDebugger />

**What the experiments show.**

- A race needs a blocking write that another process reads on the same edge. In the shift register, `q1 <= d` with `q2 = q1` is safe: Stage B reads `q1` in Active, before Stage A's update lands. The other mix, `q1 = d` with `q2 <= q1`, still races, because Stage B's read of `q1` may come after Stage A's blocking write.
- *Deterministic* is not the same as *correct*. With `#0` at the start of one stage, every order can agree and still differ from what real flops do: `#0` changed *when* a process reads, not whether the code models hardware.
- **Limits of the model.** It varies only the order of ready processes. It does not model nets with several drivers, `force` and `release`, nonzero clocking skews, a process paused between its own statements (§4.7), or a woken process running between two updates of one NBA batch (Push Further covers the last two). Those only add more legal orders, so a race the model shows is always a real race; the katas use a real simulator for the rest.

### The race that bites testbenches

Design engineers learn "use `<=` in flops". Verification engineers have a second problem: **the testbench and the DUT wake on the same clock edge.** If the testbench drives a DUT input with `=` right after `@(posedge clk)`, the DUT's flop may sample the *new* value instead of the value from before the edge. That is a race even though the DUT code is perfect.

The comparison below runs three driving styles through every legal order. Before you look at the results, answer its question: which styles make the flop capture the pre-edge value in every order?

<TestbenchDriveComparison />

**What the comparison showed.** `din = 7` writes in Active, the region where the flop reads `din`, so the flop captures 3 or 7 depending on the order. `din <= 7` and the clocking-block drive both put the write after the flop's read: in NBA for the first, in Re-NBA for the second (§14.16). Look at the testbench's read of `q` as well. The plain read sees the old `q` only because the DUT writes `q` with `<=`; the clocking-block read returns the Preponed sample, which stays correct even against blocking RTL (§14.13).

**Preview: interfaces and clocking blocks.** A testbench usually reaches the DUT through an **interface** (F4B), a named bundle of signals. Most reusable interfaces also declare **clocking blocks** (F4C), which fix when the driver writes and when the monitor samples (common practice, not a rule of the standard). You only need their timing here:

```systemverilog
// snippet: preview of F4B and F4C syntax; no DUT or top module
interface fifo_if (input logic clk);
  logic [7:0] din;
  logic [7:0] q;
  logic       push;

  // Driver view: outputs land in Re-NBA (#0 output skew, §14.16).
  // Monitor view: inputs are Preponed samples (#1step input skew, §14.13).
  clocking drv_cb @(posedge clk);
    default input #1step output #0;
    output din, push;
    input  q;
  endclocking

  clocking mon_cb @(posedge clk);
    default input #1step;
    input din, push, q;
  endclocking
endinterface
```

### Which testbench patterns race?

Assume the usual setup: the clock is generated with a blocking assignment, `always #5 clk = ~clk;`, and the DUT input `din` feeds a flop, `always_ff @(posedge clk) q <= din;`. Read each row as "the testbench does this; is the result fixed?"

| Testbench code | Result | Why | Source |
|---|---|---|---|
| `@(posedge clk); din = v;` | **Race** | The testbench's write and the flop's read of `din` are both in Active, in either order | §4.7 |
| `@(posedge clk); din <= v;` | Deterministic: the flop captures the old `din` | The write waits for NBA, after every Active read | §4.9.4, §4.5 |
| `@(negedge clk); din = v;` | Deterministic, for a DUT that samples on the rising edge only | The write happens in a different time slot from the read | practice |
| `#10 din = v;` while `clk` also rises at 10 ns | **Race** | The testbench and the clock process resume in the same Active region | §4.7 |
| `@(posedge clk); seen = q;` with `q <= din` (and only `assign` after it) | Deterministic: `seen` gets the old `q` | The read is in Active; the DUT's update of `q` waits for NBA | §4.5, §4.9.1, §10.4.2 |
| `@(posedge clk); seen = q;` with a DUT that writes `q = din` | **Race** | The DUT's blocking write and the testbench's read are both in Active | §4.7 |
| `@(vif.cb); seen = vif.cb.q;` (F4C) | Deterministic: the Preponed sample | `@(cb)` wakes only after the clocking block has stored its samples | §14.10, §14.13 |
| `@(posedge clk); seen = vif.cb.q;` (F4C) | **Race** | The read may run before or after the clocking block updates its sample | §14.13 |
| `@(vif.cb); vif.cb.din <= v;` (F4C) | Deterministic | The drive matures in Re-NBA, after the flop's read | §14.16 |

**The deterministic-read rule.** A testbench read right after `@(posedge clk)` sees the old value of a DUT signal as long as every write on that signal's path on this edge goes through NBA, for example `q <= din` followed by `assign out = q`. Any blocking write on the path makes the read a race. Clocking-block inputs (F4C) remove the question, because they return the Preponed sample whatever the DUT does.

### Classic races you will meet

Most races you will debug have one of these shapes. The first four appeared above; the rest show that a race needs neither a clock nor two writers.

| Race | Code shape | Why it races | Fix |
|---|---|---|---|
| Blocking flops | `always @(posedge clk) q1 = d;` and `always @(posedge clk) q2 = q1;` | Stage B reads `q1` before or after Stage A writes it (§4.7) | `<=` in every flop |
| Two writers | Two processes assign `cnt` on the same edge, even with `<=` | The last write wins, and either process can be last (§4.6, §4.7) | One writer; `always_ff` |
| Testbench drive at the edge | `@(posedge clk); din = v;` against a flop that reads `din` | Same Active region as the flop's read (§4.7) | `<=`, opposite edge or clocking block |
| Testbench read of blocking RTL | DUT `q = din` at the edge; testbench `@(posedge clk); seen = q;` | Same Active region as the DUT's write (§4.7) | Clocking-block input (F4C) |
| Delay-timed stimulus | `#10 din = v;` while the clock also rises at 10 ns | The testbench and the clock process resume in one Active region (§4.7) | Time stimulus from clock edges, not absolute delays |
| A read right after a write that propagates | `assign y = a;`, then `a = 0; $display(y);` | The update of `y` and the `$display` may run in either order (§4.8) | `$strobe`, or read at a later, defined point |
| Time 0 | `initial a = 0;` against `always @(a)` | `initial` and `always` procedures start in no defined order (§9.2) | A declaration initializer (F3A) |
| Event trigger and wait | `-> done;` and `@(done);` in one time slot | A trigger that runs before the wait is missed (§15.5.2) | `wait (done.triggered)` (§15.5.3) |

**A race with no clock, traced.** IEEE 1800-2023 §4.8 uses this shape as its own example of a race:

```systemverilog
// compile
module tb_top;
  timeunit 1ns; timeprecision 1ns;

  logic a = 1'b1;
  logic y;
  assign y = a;                          // a process, evaluated again whenever a changes

  initial begin
    #1 a = 1'b0;                         // t = 1: the update of y is now pending
    $display("t=%0d y=%0d", $time, y);   // races that update (§4.8)
    $strobe ("t=%0d y=%0d settled", $time, y);
  end
endmodule
```

| At t = 1, after `a = 0` | The simulator updates `y` first | The simulator continues the `initial` first |
|---|---|---|
| `$display` prints | `t=1 y=0` | `t=1 y=1` |
| `$strobe` prints | `t=1 y=0 settled` | `t=1 y=0 settled` |

Both columns are correct behavior (§4.8). Nothing is scheduled after t = 1, so the run then ends by itself. The fix depends on what you need: `$strobe` for the settled value (§21.2.2), or a check at a later, defined point such as a clock edge. Time-zero and event races are covered in Push Further.

| Fix | Why the race disappears | Trade-off | Source |
|---|---|---|---|
| Design: `always_ff` with `<=` | Every flop reads in Active; every write waits for NBA | None for flop-to-flop transfers; it does not cure two writers | §10.4.2 |
| Testbench: `<=` after `@(posedge clk)` | The testbench's write lands in NBA, after the flop's read | Raw testbench reads of DUT outputs stay exposed to blocking RTL | §4.9.4 |
| Testbench: drive after `@(negedge clk)` | The write is in another time slot, half a cycle before the sampling edge | Inputs get half a cycle to settle in gate-level simulation; designs that use the falling edge or several clocks race again | practice |
| Testbench: clocking block (F4C) | Drives land in Re-NBA; reads return Preponed samples; `@(cb)` wakes in Observed | Read clockvars only after `@(cb)`; one more construct to learn | §14.10, §14.13, §14.16 |
| Testbench: program block (F4C) | Testbench code runs in the Reactive region set, after the design's events, including clocks written with `<=` | Program threads still race each other; the run ends when every program `initial` has finished; modules cannot call program subroutines | §24.3, §24.3.1, §24.4, §24.5 |
| `#0` (not a fix) | It does not: the process only moves to Inactive in the same slot | The next `#0` on that path races it there, and the intent is hidden | §4.4.2.3 |

**A practical default.** In RTL, use `always_ff` with `<=` for every flop and `always_comb` with `=` for combinational logic. In a testbench written before F4C, drive DUT inputs with `<=` right after the clock edge, or on the opposite edge, and say why in a comment. From F4C on, drive and sample only through clocking blocks. Never use `#0` to order processes, and never change the DUT to suit the testbench. Push Further weighs the testbench options against each other.

### Pitfalls and misconceptions

1. **"`<=` everywhere removes all races."** It removes read-write races between flops, and between a testbench drive and the flops it feeds. It does not help two processes that write one variable (the NBA executed last wins, §4.6, §4.7), a testbench that reads a signal written by blocking RTL, or a flop clocked by a clock that is itself written with `<=` (Push Further).
2. **"Simulators run same-event processes in source order."** The standard leaves the order open (§4.3, §4.7). Your simulator may happen to use source order today and another order after an upgrade, a new optimization option or a file reorder (tool-dependent). Code that is right in only one order is wrong.
3. **"`#0` reliably fixes a race."** `#0` moves the rest of the process to the Inactive region of the same time slot (§4.4.2.3). It works until another process on that path also uses `#0`; then the two race in Inactive. It hides the ordering assumption instead of removing it.
4. **"If the waveform looks right, there is no race."** Every step of a time slot shares one time stamp, so a waveform viewer draws both orders as one instant. The evidence is in the log and in what each process read.
5. **"Two statements in one `begin`…`end` can race."** They cannot: statements in one sequential block run in source order (§4.6). `begin q1 = d; q2 = q1; end` always gives `q2` the new `q1`. That is a design bug if you meant a two-stage shift register, but it is deterministic.
6. **"A clocking block fixes races inside the DUT."** It removes the race between the testbench and the DUT. Two DUT processes that communicate through `=` still race each other, and the testbench samples whichever result the DUT produced.

### Recap

- A time slot runs its regions in a fixed order and loops back to Active whenever an update wakes a process. Each loop back is a delta cycle, and none advances time (§4.5).
- A race is a result that depends on the order of processes ready in the same time slot, which the standard leaves open (§4.7, §4.8). A read-write race needs a write that another process reads in the same region; a write-write race needs two writers.
- Flops use `<=`, every variable has one writer, and testbench writes land where the flops' reads cannot see them: in NBA, on the opposite edge or, from F4C, in Re-NBA through a clocking block.
- A raw testbench read right after `@(posedge clk)` is deterministic only while every write on that path goes through NBA. Clocking-block inputs return the Preponed sample.
- `#0` is never a fix, and changing the DUT to suit the testbench is never a fix.

## Make It Work

### A race you can run

This bench contains the testbench race and two fixes, selected at run time by a plusarg (F2D). One process drives `din`; a flop captures it; a checker compares `q` at every falling edge with the value the flop should have captured. Read it, predict what each of the three runs prints, then check the trace.

```systemverilog
// compile
module tb_top;
  timeunit 1ns; timeprecision 1ns;

  logic       clk = 1'b0;
  logic [7:0] din = 8'd3;      // initializers run before any process starts (§6.8)
  logic [7:0] q;
  logic [7:0] expected[$];     // what the flop must capture at each rising edge
  string      drive = "blocking";
  int         pass_n = 0, fail_n = 0;

  always #5 clk = ~clk;        // rising edges at 5, 15, 25 and 35 ns

  // DUT: one flop. It reads din in Active and writes q in NBA.
  always_ff @(posedge clk) q <= din;

  // Driver: the only process that writes din.
  initial begin
    void'($value$plusargs("DRIVE=%s", drive));
    for (int i = 4; i < 8; i++) begin
      @(posedge clk);
      expected.push_back(din);           // din before any write at this edge
      if (drive == "nba") begin
        din <= i;                        // FIX 1: the write waits for NBA
      end else if (drive == "negedge") begin
        @(negedge clk);                  // FIX 2: change din half a cycle early
        din = i;
      end else begin
        din = i;                         // BUG: a write in Active races the flop
      end
    end
    @(negedge clk);
    #1 $finish;
  end

  // Checker: at each falling edge, q holds what the flop captured at the rising edge.
  initial forever begin
    @(negedge clk);
    if (expected.size() > 0) begin
      if (q === expected.pop_front()) pass_n++;
      else                            fail_n++;
    end
  end

  final $display("drive=%s PASS=%0d FAIL=%0d", drive, pass_n, fail_n);
endmodule
```

Two details keep the checker itself free of races. The driver records `din` before it writes, and no other process writes `din`, so `expected` always holds the pre-edge value (§4.6). And the checker runs at the falling edge, when nothing it reads changes.

**Expected output** for the two fixed runs. It is illustrative: it was traced by hand from the IEEE 1800-2023 rules on this page, not captured from a simulator run, and your simulator adds its own banner and `$finish` message.

```text
drive=nba PASS=4 FAIL=0
drive=negedge PASS=4 FAIL=0
```

The run with no plusarg is the race. IEEE 1800-2023 allows every one of these results, and which one you get is tool-dependent:

| At each rising edge, your simulator runs… | Last line of the log |
|---|---|
| the DUT flop before the driver, every time | `drive=blocking PASS=4 FAIL=0` |
| the driver before the DUT flop, every time | `drive=blocking PASS=0 FAIL=4` |
| different orders at different edges | `drive=blocking PASS=n FAIL=m`, with n + m = 4 |

The first row is the dangerous one: the bench passes today and fails on the next simulator, or after the next file reorder.

**The racy edge at t = 5, traced.** Before the edge, `din` = 3 and `q` is unknown (x).

| Step | Order A: flop first | Order B: driver first |
|---|---|---|
| Active, first process | The flop reads `din` = 3 and schedules `q <= 3` | The driver pushes 3 into `expected`, then writes `din` = 4 |
| Active, second process | The driver pushes 3 into `expected`, then writes `din` = 4 | The flop reads `din` = 4 and schedules `q <= 4` |
| NBA | `q` becomes 3 | `q` becomes 4 |
| Checker at t = 10 | 3 matches 3: PASS | 4 against 3: FAIL |

With `+DRIVE=nba`, the driver's write becomes an NBA update, so the flop reads 3 in both orders. With `+DRIVE=negedge`, the driver writes `din` at t = 10, in another time slot, and the flop reads it at t = 15.

**Run it.** Save the code as `tb_top.sv` and compile it once with any IEEE 1800 simulator; `tb_top` is the top level. Then run it three times: with no plusarg, with `+DRIVE=nba` and with `+DRIVE=negedge`. **How to work through it:**

1. **Predict.** Before running anything, write down what each of the three runs should print, and which results the standard leaves open.
2. **Run the fixes.** `+DRIVE=nba` and `+DRIVE=negedge` must both print `PASS=4 FAIL=0`. If either does not, check that the driver is still the only process that writes `din`.
3. **Run the race.** With no plusarg, note the result. Then swap the textual order of the `always_ff` and the driver's `initial`, rebuild and run again. A flip proves the race on one simulator. No flip proves nothing: the code still allows both orders (§4.7), and the Race Condition Debugger above shows the one your tool did not pick.
4. **Break the DUT instead.** Restore the order, change the flop to `always @(posedge clk) q = din;` and run with `+DRIVE=nba`. The bench still passes, because the testbench's write still lands after the DUT's read. But any testbench read of `q` right after `@(posedge clk)` would now race (see "Which testbench patterns race?").
5. **Explain every line** of every log with a region and a clause, not with "the simulator did it".
6. **After F4C,** replace the three drive styles with one clocking-block drive, `@(vif.cb); vif.cb.din <= i;`, and keep the checker unchanged.

### How to debug a suspected race

Races show up as symptoms, not as messages. Match the symptom first:

| Symptom | Likely cause | How to confirm | Fix |
|---|---|---|---|
| A test passes on one simulator and fails on another, or flips after a file reorder, a simulator upgrade or a new optimization option | A same-slot race (§4.7), or different random stimulus on the two runs | Rerun the same stimulus on one simulator with the processes or files reordered | Find the shared variable (procedure below) |
| The scoreboard's actual value is one cycle early: the DUT captured the value driven on the same edge | The testbench writes a DUT input with `=` at the edge the DUT samples on | Print the input with `$display` in the driver and with `$strobe`; swap the process order | `<=`, opposite edge or clocking block |
| A monitor sometimes records a DUT output's new value on the edge where it changes | A raw read after `@(posedge clk)` of a signal written by blocking RTL | Find the RTL that writes the signal | Clocking-block input (F4C) |
| A counter or state variable sometimes ignores a clear or a load | Two processes write it on the same edge | Search for every writer; `always_ff` turns a second writer into an error | One writer per variable |
| Adding a `#0`, or moving code around, makes the failure go away | The race was moved, not removed | Look for any other `#0` on that path; reorder again | Remove the `#0` and apply a real fix |
| A flop on a divided or generated clock captures data one cycle early in RTL simulation only | A clock written with `<=` changes in the same NBA pass as its data | Check how the clock is generated; trace the edge | Clock enable (Push Further) |
| An immediate assertion in combinational code fails at a time where the settled waveform is correct | A zero-delay glitch: the block ran on a transient value | Check whether the block ran twice at that time stamp | Deferred assertion (Push Further) |

Then work the procedure:

1. **Fix the stimulus.** Reproduce the failure with the same stimulus on one simulator: a directed test, or the same simulator and seed. The same seed on two simulators is not the same stimulus (Push Further).
2. **Find the time stamp.** Take the first failing time from the log and open the waveform at that time.
3. **List the suspects.** Write down every process woken at that time (the same clock edge, the same `#` delay, the same event) and every variable that two of them share.
4. **Match a shape.** Look for a variable written with `=` by one process and read by another (read-write), a variable written by two processes (write-write), or a testbench read or write of a DUT signal without `<=` or a clocking block.
5. **Prove it.** Print the variable with `$display` inside the reading process and with `$strobe`, reorder the processes or files, or rebuild the shape in the Race Condition Debugger and let it run every order.
6. **Fix it** by moving the write or the read out of the other process's reach: `<=`, an opposite-edge drive or a clocking block. Never `#0`.
7. **Prevent it.** Use `always_ff` and `always_comb` in design code, so a second writer is an error. Add a code-review rule against raw `vif.signal = value` at a clock edge, and use lint that flags blocking assignments in edge-triggered blocks (tool-dependent).

### A race-free checklist for every testbench you write

1. **Design flops:** `always_ff` with `<=` only. Combinational logic: `always_comb` with `=`.
2. **One writer per variable.** Two processes writing the same variable on the same edge race, even with `<=`: whichever NBA executes last wins (§4.6, §4.7). `always_ff` and `always_comb` make a second writer illegal (§9.2.2.2, §9.2.2.4).
3. **Testbench drives** go through a clocking block (F4C). Before F4C, use `<=` right after the edge or drive on the opposite edge. Never use `=` at the edge the DUT samples on, and time stimulus from clock edges rather than from absolute delays.
4. **Testbench samples:** prefer clocking-block inputs, which return the Preponed value. A raw read after `@(posedge clk)` is deterministic only while every write on that signal's path on this edge goes through NBA; any blocking write on the path makes it a race.
5. **Never "fix" ordering with `#0`.** It only moves the race to the Inactive region.
6. **Prove it on one simulator:** reorder processes or files and rerun the same stimulus. Across simulators, first rule out different random stimulus: the same seed does not give the same values on two tools.

**Checklist before moving on:**
- [ ] I can trace the shift register through one edge with `=` and with `<=`, and name the region of every read and write.
- [ ] I can tell a read-write race from a write-write race, and show both legal orders of each.
- [ ] I ran or traced the bench in all three drive styles and can explain every line of each log.
- [ ] I can say which testbench patterns race and which are deterministic, and why.
- [ ] I can choose a fix for a testbench race and explain why `#0` is not one.

## Push Further

These items go beyond the core path: corner cases from the standard, tool-dependent behavior (labelled as such), and the trade-offs a senior engineer weighs.

### Expert: counting delta cycles and what they cost

- **Where the passes come from.** Each return to Active is caused by an update that wakes a process (§4.5): an NBA update that feeds combinational logic, a continuous assignment whose input changed (§4.9.1), or a port connection, which is an implicit continuous assignment (§4.9.6). A flop that feeds three levels of `assign` needs several passes in one slot. The visualizer's Δ counter shows the passes; a simulator never reports them in `$time`.
- **Zero-delay loops.** Logic that keeps waking itself without a delay, such as a combinational loop whose value keeps changing, holds the scheduler in one time slot forever, so time never advances. Simulators stop such a run with an iteration-limit error; the limit, the message and any option to change it are tool-dependent. A long chain of passes at one time stamp is the clue for zero-delay feedback.
- **Cost.** Delta cycles take no simulated time, but they do take simulator time. Polling loops, `#0` chains and long zero-delay chains slow a run; by how much is implementation-dependent, and the standard says nothing about speed. [E-PERF-1](/curriculum/T4_Expert/E-PERF-1_UVM_Performance/index) covers measuring it.

### Expert: glitches and assertions

- **Zero-delay glitches.** A combinational process can run more than once in a time slot while its inputs settle, so it can see a mix of old and new values that never exists once the slot has settled. Take `assign a_n = ~a;` and an `always_comb` block that checks `a_n != a`. When `a` changes, the block may run first with the new `a` and the old `a_n`, then again after `a_n` follows (§4.5).
- **Immediate assertions report glitches; deferred ones do not.** An immediate `assert (a_n != a);` in that block can fail on the first, transient run. An observed deferred `assert #0 (a_n != a);` queues its report instead, and the queue is flushed when the block runs again, so only the settled result is reported (§16.4, §16.4.2, which discusses this very shape). The `assert final` form reports at the end of the time slot (§16.4.1). F3B's item on [where assertion messages come from](/curriculum/T1_Foundational/F3B_Scheduling_Regions/index#expert-where-assertion-messages-come-from) compares all four assertion forms.
- **Concurrent assertions do not race with the flops.** They are evaluated in Observed on the values sampled in Preponed (§16.5.1), so a value written on this edge cannot reach them. In the shift-register trace above, an assertion clocked on that edge would see `q1 = 0` even after NBA has written 1. Their action blocks run in Reactive with current values, which is a different surprise: print `$sampled(x)` to report what the property checked (§16.9.3).

### Expert: interleaving inside one process

§4.7 names a second source of nondeterminism: statements without a timing control need not run as one uninterrupted event. The simulator may suspend a process between statements, run other processes, and resume it later. Source order inside the process still holds (§4.6); what changes is that other processes can see it halfway through.

```systemverilog
// snippet: inside a module with logic a = 1'b0, b = 1'b0;
initial begin
  #1 a = 1'b1;                                 // wakes the always block below
  b = 1'b1;                                    // no timing control in between
end
always @(a) $display("a=%0d b=%0d", a, b);     // b=0 and b=1 are both legal at t = 1
```

Many simulators run a process until it reaches a timing control, so you may never see `b=0` on your tool (tool-dependent), but code that depends on it is not portable. The scheduler model on this page never interleaves; that only removes orders, so every race it shows is still real. The fix is to make readers wait for a defined point, such as a clock edge or an event triggered after the last write, never for an intermediate value.

### Expert: write-write races, single writers and multiple drivers

- **Variables: the last write wins.** A variable can be written by several procedural statements, and the last write decides its value (§6.5). Two processes that write it in one time slot race on which write is last, with `=` or with `<=`: NBAs are performed in execution order (§4.6), but the two processes are not ordered (§4.7). §10.4.2 also shows the converse: nonblocking writes from two blocks are determinate when they execute at different times, even if they mature in the same slot.
- **`always_ff` and `always_comb` turn the race into an error.** Variables they assign must not be written by any other process (§9.2.2.2, §9.2.2.4), so the tool reports a second writer instead of letting it race. A variable written by a continuous assignment cannot also be written procedurally (§6.5).
- **Nets resolve; they do not race.** A net with several drivers takes the value its net type's resolution gives: conflicting values of equal strength on a `wire` give `x` (§6.6.1), in every order. That is deterministic but almost always a bug. Declare single-driver nets as `uwire` to make a second driver an error (§6.6.2).
- **Clocking drives.** When two synchronous drives to the same clocking-block output mature in the same Re-NBA region, only the last value is driven (§14.16.2). From two testbench threads, that is a write-write race on a DUT input. A clocking output can also glitch when the scheduler passes through Re-NBA more than once in a time slot and different values are driven in each pass (§14.16.2).
- **In a UVM bench** (practice): exactly one driver owns each interface signal, and monitors never write.

### Expert: clocks generated inside the simulation

A clock written with `<=` changes in the NBA region, together with every other `<=` update of that pass. §4.6 orders those updates only among themselves. After one of them wakes a process, §4.5 lets the scheduler take any event next: the woken process or the next update. So a flop on such a clock can see some data updates of the same pass and not others.

```systemverilog
// snippet: inside a module with logic clk, clk_div; logic [3:0] cnt, cap;
always @(posedge clk)     clk_div <= ~clk_div;   // divide-by-2 clock, written with <=
always @(posedge clk)     cnt     <= cnt + 4'd1; // data, launched by clk
always @(posedge clk_div) cap     <= cnt;        // capture flop on the divided clock
```

| At a `clk` edge where `clk_div` rises… | `cap` gets |
|---|---|
| `cnt` is updated before `clk_div`, because its process ran first in Active | the new `cnt` |
| `clk_div` is updated first, and the capture flop runs before the `cnt` update | the old `cnt` |
| `clk_div` is updated first, but the `cnt` update is applied before the capture flop runs | the new `cnt` |

The intended behavior, and what the circuit does once its hold timing is closed, is to capture the value from before the edge. A simulator that captures the new value captures it one cycle early, and RTL simulation then disagrees with the hardware; which outcome you get is tool-dependent. The scheduler model on this page applies a whole batch of NBA updates before any process they wake, so it never shows the middle row.

- **Fix in RTL** (practice): do not clock logic with a flop output. Run the capture flop on `clk` with an enable that toggles like `clk_div`: `always_ff @(posedge clk) if (!en_div) cap <= cnt;`. Kata 3 builds both versions.
- **Fix in a testbench** (practice): generate clocks with a blocking assignment, `always #5 clk = ~clk;`. The edge then happens in Active, every flop it clocks reads its inputs in that pass, and every `<=` of the slot lands later, in NBA. A clock written with `<=` gives up that guarantee: `#10 din <= v;` timed to land on its edge races the edge, because both updates sit in the same NBA pass.
- **Why programs exist.** §24.4 names exactly this problem: with several clocks, or clocks driven by nonblocking assignments, input sampling alone cannot order everything, so program code is scheduled in the Reactive region, after all design events of the slot have been processed.

### Expert: choosing between opposite-edge drives, clocking blocks and program blocks

All three make testbench-to-DUT timing deterministic. They differ in what else they buy and what they cost.

- **Opposite-edge drives** (practice). The write happens in another time slot, so no ordering question arises for a design that samples on the rising edge only. The costs: the DUT's inputs get half a clock period to settle, which matters in gate-level and timing simulation; designs that also use the falling edge, or several clocks, race again; and drive and check points are spread over two edges, which makes waveforms harder to read.
- **Clocking blocks** (§14). Inputs are sampled before the edge (`#1step`, Preponed, §14.13), the `@(cb)` event is triggered in Observed after the samples are updated (§14.10), and zero-skew drives mature in Re-NBA (§14.16). Timing is declared once, in the interface, and skews can model input and output delays. The traps: a clockvar read after `@(posedge clk)` instead of `@(cb)` races the clocking block's own update (§14.13); a drive executed between clocking events takes effect at the next one (§14.16); and two drives to one clockvar in the same cycle keep only the last value (§14.16.2).
- **Program blocks** (§24). All program code runs in the Reactive region set (§24.3.1). A program that reads design values only through clocking blocks clocked by design signals is insensitive to read-write races, and programs also handle several simultaneous clocks and clocks driven by `<=`, which sampling alone does not (§24.4). The costs: program threads still race each other (§4.7); the whole run ends by an implicit `$finish` once every program `initial` thread has finished (§24.3); modules cannot call program subroutines (§24.5); and class code has no region of its own, because it inherits the region of the thread that calls it (§24.3.1).
- **What UVM benches do** (practice, not a rule of the standard). Most call `run_test()` from a module `initial`, so their classes run in the active region set, and they get race freedom from clocking blocks in their interfaces, not from program blocks. Program blocks are not deprecated. F3B compares the two constructs region by region in [program blocks versus clocking blocks](/curriculum/T1_Foundational/F3B_Scheduling_Regions/index#expert-program-blocks-versus-clocking-blocks), and F4C teaches the syntax.

### Expert: time-zero and event races

Two classic races need no clock at all:

- **Time 0.** `initial` and `always` procedures start in no defined order (§9.2), so an `initial` that assigns a variable at time 0 races an `always @(a)` that may not be waiting yet. Declaration initializers run before any procedure starts (§6.8), which is why they are the fix. F3A traces both legal outputs and lists everything the standard fixes at time 0 in [time zero, step by step](/curriculum/T1_Foundational/F3A_Simulation_Semantics/index#expert-time-zero-step-by-step).
- **Named events.** A process blocked on `@(done)` wakes only if it was already waiting when `-> done;` executed (§15.5.2). When the trigger and the wait happen in the same time slot, their order decides whether the waiter hangs. `wait (done.triggered)` reads the event's triggered state, which persists until simulation time advances, so it unblocks in either order (§15.5.3). [I-SV-5: Events](/curriculum/T2_Intermediate/I-SV-5_Synchronization_and_IPC/events) owns named events in depth, including `->>`.

### Expert: reproducing a race across tools, seeds and builds

- **Rule out different stimulus first.** The standard requires a seed to repeat the same random sequence on one simulator (§18.13.1), but the generator's state is implementation dependent (§18.13.4). The same seed on two simulators therefore normally gives different constrained-random stimulus (tool-dependent), and a result that differs across tools proves nothing until the stimulus is the same. Compare a directed test, or stimulus recorded on one tool and replayed on the other.
- **Reproduce on one simulator.** The order a simulator picks can change with source order, file order, compilation-unit grouping, optimization options or the simulator version (tool-dependent). Reordering processes or files and rerunning the same stimulus is the cheapest proof; Kata 1 does exactly that.
- **Ask the tools.** Some simulators can report races, or vary the order of same-time processes; whether yours can, and the option names, are tool-dependent, so check its documentation. Lint tools commonly flag blocking assignments in edge-triggered blocks and variables with several writers (tool-dependent), and `always_ff` and `always_comb` make a second writer illegal everywhere (§9.2.2.2, §9.2.2.4).
- **Debug at one time stamp.** The log and the waveform show one time for the whole slot. Print the suspect variable with `$display` inside the reading process and with `$strobe`: `$display` shows what that process saw, and `$strobe` what the slot settled to (§21.2.2). If changing the process order changes the `$display` line, you have found the race.

### Kata 1 (guided): reproduce the race on a real simulator

**Objective:** make the testbench race visible in a real tool, prove it on one simulator, then remove it.

Start from the Make It Work bench. In the driver, right after `@(posedge clk)` and before `expected.push_back(din)`, add these two lines:

```systemverilog
// snippet: the first two statements after @(posedge clk) in the driver
$display("%0t display din=%0d q=%0d", $time, din, q);
$strobe ("%0t strobe  din=%0d q=%0d", $time, din, q);
```

**Requirements:**
1. Run the bench with no plusarg and keep the log.
2. Swap the textual order of the `always_ff` and the driver's `initial`, rebuild and rerun. Compare the two logs line by line.
3. If neither log ever shows a strobed `q` equal to the value the driver wrote on that same edge, your simulator kept one order. Set up the same shape in the Race Condition Debugger (*TB drives the DUT input*) to see the other order; the code still races (§4.7).
4. Run with `+DRIVE=nba` in both file orders and show that the two logs are identical.
5. **Observable artifact:** a log in which, on some edge, the strobed `q` equals the value the driver wrote on that same edge.

**What to reflect on:**
- In which region did the original drive land, and in which region did the flop read `din`?
- Why does the `display` line never show this edge's new `q`, while the `strobe` line can?
- Why does the waveform viewer show nothing suspicious at the failing time stamp?
- How would you explain this bug to a designer who says "the DUT is fine"? (They are right.)

<details>
<summary>Worked solution (try the kata first)</summary>

The first two edges of the racy run, in the two legal orders (`x` is the unknown value of `q` before the first capture):

| Log line | Order A: flop first | Order B: driver first |
|---|---|---|
| t = 5, display | `5 display din=3 q=x` | `5 display din=3 q=x` |
| t = 5, strobe | `5 strobe  din=4 q=3` | `5 strobe  din=4 q=4` |
| t = 15, display | `15 display din=4 q=3` | `15 display din=4 q=4` |
| t = 15, strobe | `15 strobe  din=5 q=4` | `15 strobe  din=5 q=5` |
| last line | `drive=blocking PASS=4 FAIL=0` | `drive=blocking PASS=0 FAIL=4` |

In order B every strobed `q` equals the strobed `din`: the flop took the value the driver wrote on that same edge, one cycle early. With `+DRIVE=nba`, both orders print the order-A lines with `drive=nba`.

- **Regions.** The blocking drive wrote `din` in Active (§4.9.3), the same region in which the flop's `<=` read it, and the order of the two processes is free (§4.7).
- **Display versus strobe.** The `$display` runs before the driver's write and before any NBA update, so it always shows the values from before the edge. The `$strobe` prints at the end of the slot (§21.2.2), after the flop's update, so it shows what the flop captured.
- **The waveform.** In both orders `din` and `q` change at the edge's time stamp. A viewer draws one time slot as one instant and cannot show which process ran first; order B just looks like a flop with no latency.
- **The designer.** The DUT is correct. The testbench changed `din` in the same region in which the flop samples it; real hardware changes its inputs after the clock edge, which `<=` or a clocking block models.

**Objective:** build an interface and a monitor that sample correctly even when the DUT is written badly.

**Requirements:**

- Add a naive second monitor that reads the raw `vif.din` and `vif.q` after `@(posedge clk)`.
- Prove with logs that the clocking-block monitor records the same pairs whichever order the DUT and the monitors run in: swap their order in the source. Show that the naive monitor's `q` can change.
- Choose the clocking-block defaults yourself, and justify them in a comment that cites the clause. Give every design element in the file a time unit.

**What to reflect on:**
- What does the monitor record for `q` on the edge where `q` changes, and why is that the right answer for a scoreboard?
- Why can't a clocking block fix a race inside the DUT?
- Which part of your solution would move unchanged into a UVM agent?

<summary>Worked solution (try the kata first)</summary>

  clocking mon_cb @(posedge clk);

  endclocking
endinterface

  timeunit 1ns; timeprecision 1ns;

  always #5 clk = ~clk;            // rising edges at 5, 15, 25, 35 and 45 ns

  bad_dut dut (.clk(clk), .din(vif.din), .q(vif.q));

  // Driver: a new value after each rising edge, written with <= (lands in NBA).
  initial begin

    for (int i = 1; i <= 3; i++) begin

      vif.din <= 8'(i);

    repeat (2) @(posedge clk);
    #1 $finish;

  initial forever begin
    @(vif.mon_cb);
    $display("%0t CB  din=%0d q=%0d", $time, vif.mon_cb.din, vif.mon_cb.q);
  end

  // Naive monitor, for comparison: raw reads after the raw edge race the DUT.
  initial forever begin

  end

**Expected output** (illustrative, traced by hand; shown for the order in which the DUT runs before the naive monitor):

```text
5 RAW din=0 q=0
5 CB  din=0 q=x
15 RAW din=1 q=1
15 CB  din=1 q=0
25 RAW din=2 q=2
25 CB  din=2 q=1
35 RAW din=3 q=3
35 CB  din=3 q=2
45 RAW din=3 q=3
45 CB  din=3 q=3
```

At each time the RAW line prints first, because the naive monitor runs in the first Active pass and the clocking-block monitor resumes only after Observed (§14.10). Swap the order and the CB lines do not change. The RAW lines at 5 to 35 ns can then show the old `q` (`x`, 0, 1, 2): the naive read races the DUT's blocking write. At 45 ns `q` does not change, so both orders agree there.

- **The value on the changing edge.** The monitor records the old `q`, the Preponed sample. That is what a flop in the monitor's place would capture, and it makes the scoreboard rule simple: `q` sampled at one edge equals `din` sampled at the edge before.
- **Races inside the DUT.** A clocking block only decides when the testbench samples. If two DUT processes race each other, the DUT itself produces either result, and the sample faithfully records whichever one it produced.
- **Into UVM.** The interface with its clocking block moves unchanged; the monitor loop becomes a UVM monitor's `run_phase` reading through a virtual interface (Tier 2).

</details>

### Kata 3 (expert, optional): the divided clock that captures early

**Objective:** reproduce the clock-generated-with-`<=` race from Push Further, then remove it without changing what the design captures.

```systemverilog
// compile
module tb_top;
  timeunit 1ns; timeprecision 1ns;

  logic       clk = 1'b0, clk_div = 1'b0;
  logic [3:0] cnt = 4'd0, cap = 4'd0;

  always #5 clk = ~clk;                            // rising edges at 5, 15, 25, ...

  always @(posedge clk)     clk_div <= ~clk_div;   // divide by 2 with <=: the suspect
  always @(posedge clk)     cnt     <= cnt + 4'd1;
  always @(posedge clk_div) cap     <= cnt;        // capture flop on the divided clock

  always @(posedge clk_div) $strobe("%0t cap=%0d cnt=%0d", $time, cap, cnt);

  initial begin
    repeat (4) @(posedge clk_div);
    #1 $finish;
  end
endmodule
```

**Requirements:**
1. Predict both legal logs before you run, using the table in Push Further.
2. Run it and say which outcome your simulator produced.
3. Replace the divider and the capture flop with an enable on `clk` that captures at the same edges, run again and show that the log is the intended one.
4. Explain why your fix cannot depend on the simulator.

<details>
<summary>Worked solution (try the kata first)</summary>

The divided clock rises at 5, 25, 45 and 65 ns. At each of those edges `cnt` also changes, from 0 to 1, from 2 to 3, and so on. The two legal logs (illustrative, traced by hand):

| Intended: the capture flop takes the old `cnt` | Early: it takes the new `cnt` |
|---|---|
| `5 cap=0 cnt=1` | `5 cap=1 cnt=1` |
| `25 cap=2 cnt=3` | `25 cap=3 cnt=3` |
| `45 cap=4 cnt=5` | `45 cap=5 cnt=5` |
| `65 cap=6 cnt=7` | `65 cap=7 cnt=7` |

Which column you get depends on the order in which your simulator applies the two NBA updates and runs the capture flop (tool-dependent). The fix replaces the divider, the capture flop and the print, and changes the `initial` to `repeat (8) @(posedge clk); #1 $finish;`:

```systemverilog
// snippet: replaces the three clk_div processes in the bench above
logic en_div = 1'b0;
always @(posedge clk) en_div <= ~en_div;           // an enable, not a clock
always @(posedge clk) if (!en_div) cap <= cnt;     // same clock as cnt
always @(posedge clk) if (!en_div) $strobe("%0t cap=%0d cnt=%0d", $time, cap, cnt);
```

`clk_div` rose at the edges where its old value was 0, so `!en_div` selects the same edges. The log is now always the intended column. The capture flop runs on `clk`, like the flop that launches `cnt`, so it reads `cnt` in Active before the NBA update, in every order (§4.5, §10.4.2). No clock is written with `<=`, so no clock edge can appear in the middle of an NBA pass.

</details>
