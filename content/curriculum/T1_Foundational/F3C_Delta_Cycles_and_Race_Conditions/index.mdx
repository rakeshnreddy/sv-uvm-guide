## Quick Take

- **What it is:** A **time slot** is everything the simulator does at one simulation time. Inside it, the scheduler works through ordered **regions**, looping back whenever new events appear. Each loop back is a **delta cycle**: more work, zero simulated time.
- **Why it matters:** When two processes wake on the same event, IEEE 1800 lets the simulator run them in **any order** (§4.7). If your result depends on that order, you have a **race condition**. It may pass on one simulator and fail on the next, or after a harmless-looking file reorder.
- **The rule you will apply all career:** A flop reads in **Active** and writes in **NBA** (`<=`). A testbench drives through a **clocking block**, so its writes land in **Re-NBA** and its reads come from **Preponed** samples.
- **The Analogy:** A time slot is a stage play with a strict act order. Actors who enter in the same act may speak in any order. If the plot depends on who speaks first, the script is broken.

## Build Your Mental Model

### Picture a ladder, not an instant

When you read `@(posedge clk)`, do not picture one moment. Picture this ladder. The clock edge drops an event into **Active**. The scheduler drains Active, then promotes the next non-empty region and loops, all at the same simulation time. Select each rung and ask yourself: *which of my statements land here?*

<TimeSlotRegionMap />

Three things to burn in:

1. **Preponed** and **Postponed** are read-only. Preponed holds the "before" photo of every value. Assertions and clocking-block inputs read that photo (§4.4.2.1, §16.5.1).
2. Blocking assignments (`=`) write **immediately, in Active**. Nonblocking assignments (`<=`) read their right side in Active but write in **NBA** (§10.4.1, §10.4.2).
3. Ready processes in one region run in **any order** (§4.7). Statements *inside* one `begin…end` always run in source order (§4.6).

Step through the scheduler below. Watch three things move together: the highlighted line of code, the ▶ marker on the ladder, and the waveform cursor. The waveform's horizontal axis is **scheduler steps**, not time. A real waveform viewer would draw all of it at `t = 10 ns`.

What you just saw, in words:

- With `=`, Stage A's write to `q1` is visible the instant it happens. Whether Stage B sees it depends only on who ran first.
- With `<=`, both stages read in Active **before** either write lands in NBA. Order cannot leak into the result, which is exactly how two physical flip-flops behave.
- `$display` prints during Active, before NBA updates land. `$strobe` waits for Postponed and prints the settled value (§21.2.2).

### The race that bites testbenches

Design engineers learn "use `<=` in flops". Verification engineers have a second problem. **The testbench and the DUT wake on the same clock edge.** If the testbench drives a DUT input with `=`, the DUT's flop may sample the *new* value. That is a race even though the DUT code is perfect.

<TestbenchDriveComparison />

This is why every reusable UVM interface declares a **clocking block** for its driver and monitor:

```systemverilog
interface fifo_if (input logic clk);
  logic [7:0] din;
  logic [7:0] q;
  logic       push;

  // Driver: outputs land in Re-NBA (#0 output skew, §14.16).
  // Monitor: inputs are the Preponed sample (#1step input skew, §14.13).
  clocking drv_cb @(posedge clk);
    default input #1step output #0;
    output din, push;
    input  q;
  endclocking

  clocking mon_cb @(posedge clk);
    default input #1step;
    input din, push, q;
  endclocking
endinterface
```

## Make It Work

### Debug a real-looking failure

You will meet this race as a scoreboard error that only some runs show. Find the culprit line, then choose a fix. The model reruns every legal order and grades the fix twice: is it deterministic, and does it behave like real hardware?

<RaceDebugChallenge />

### A race-free checklist for every testbench you write

1. **Design flops:** `always_ff` with `<=` only. Combinational logic: `always_comb` with `=`.
2. **One writer per variable.** Two processes writing the same variable on the same edge is a race, even with `<=`: the last NBA executed wins (§4.6).
3. **Testbench drives** go through a clocking block (`vif.cb.sig <= v`). As a stopgap, use `<=`. Never use `=`.
4. **Testbench samples** come from a clocking block input (`vif.cb.sig`), which returns the Preponed value.
5. **Never "fix" ordering with `#0`.** It only moves the race to the Inactive region.
6. **Prove it:** run the same seed on two simulators, or reorder files. Results that change point to a race.

## Push Further

- **Delta cycles you can count:** When an NBA update changes a value that a combinational `always_comb` reads, the scheduler moves back to Active. Each move is one more Δ in the visualizer. Long Δ chains are a debugging clue for zero-delay feedback loops.
- **Program blocks and the reactive set:** Code in `program` blocks runs in the Reactive region set (§4.4.2.6), another way to separate testbench and design. UVM classes are not program blocks: they execute in the active set, which is why clocking blocks carry the race-avoidance burden in UVM benches.
- **`@(cb)` is later than `@(posedge clk)`:** A clocking-block event is triggered in the Observed region (§14.10). A driver that waits on `@(vif.drv_cb)` therefore wakes after the design's NBA updates for that edge, never in competition with the flops. Switch the trace above to **TB · clocking block** and watch for the `@(cb) event` in the Observed queue.
- **Assertions see the past:** A concurrent assertion clocked on `posedge clk` evaluates in Observed, but on values sampled in Preponed (§16.5.1). In the shift-register scenario it would see `q1 = 0` even after NBA has written 1.
- **What the model does not cover:** It does not model nets with multiple drivers, `force`/`release`, nonzero skews, or interleaving inside a process (§4.7 permits it; it only adds orders). Use a real simulator for those. The katas below require one.

### Kata 1 (guided): reproduce the race on a real simulator

**Objective:** Make a race visible in a real tool, then remove it.

**Requirements:**
- Write `tb_race.sv` with a free-running clock and a DUT flop `always_ff @(posedge clk) q <= din;`.
- In a testbench `initial` block, drive `din` with `=` immediately after `@(posedge clk)`, for 4 cycles of distinct values.
- Log `$display("%0t din=%0d q=%0d", $time, din, q)` with `$strobe` on the same line set.
- Run it on two simulators (for example on EDA Playground), or swap the textual order of the DUT and testbench processes.
- **Observable artifact:** a log in which `q` sometimes equals the value driven on the *same* edge.
- Change the drive to a clocking block (`drv_cb.din <= v`). Show that the logs now agree across simulators and orders.

**What to Reflect On:**
- Which region did the original drive land in, and which region did the flop read in?
- Why does the waveform viewer show nothing suspicious at the failing timestamp?
- How would you explain this bug to a designer who says "the DUT is fine"? (They are right.)

### Kata 2 (independent): race-proof a monitor

**Objective:** Build an interface and monitor that sample correctly even when the design is badly written.

**Requirements:**
- Write a DUT that uses `=` inside its clocked block (deliberately bad).
- Write an interface with a `mon_cb` clocking block and a monitor that collects `{din, q}` pairs every cycle.
- Prove with logs that the monitor's samples are identical whichever process runs first. Change the source order of the DUT's processes to test this.
- No hints this time. Decide which clocking-block defaults you need and justify them in a comment that cites the clause.

**What to Reflect On:**
- What does the monitor observe for `q` on the edge where `q` changes, and why is that the right answer for a scoreboard?
- Which part of your solution would move unchanged into a UVM agent?

    <details>
      <summary>How do nonblocking assignments prevent races between flops?</summary>
      <p>Every flop triggered by the edge evaluates its right-hand side in the Active region, reading the old values. The updates are deferred to the NBA region, which only runs after Active is empty. No order of the ready processes can let one flop see another's new value on the same edge (§10.4.2, §4.4.2.4).</p>
    </details>
    <details>
      <summary>Is `begin q1 = d; q2 = q1; end` inside one always block a race?</summary>
      <p>No. Statements inside one begin-end execute in source order (§4.6), so `q2` always receives the new `q1`. Simulation behaves like one flop whose output feeds a wire, and synthesis infers the same. It is a design bug if you wanted a two-stage shift register, but it is deterministic. The race only appears when the two assignments sit in **different** processes woken by the same edge.</p>
    </details>
    <details>
      <summary>Your test passes on simulator A and fails on simulator B with the same seed. What is your first hypothesis, and how do you confirm it?</summary>
      <p>A scheduling race: the result depends on an order that IEEE 1800 leaves to the tool (§4.7). Confirm it by reordering source files or processes on a single simulator. Then look for a variable that one process writes with `=` while another process reads it on the same event. In testbenches, look first at any raw `vif.signal = value` in drivers and any raw `vif.signal` reads in monitors.</p>
    </details>
    <details>
      <summary>Why is `#0` a bad fix for a race?</summary>
      <p>It moves the delayed process to the Inactive region. It only works until a second process also uses `#0`, and then the two race again in Inactive. It hides the ordering assumption instead of removing it, and reviewers cannot see the intended timing. Use `<=` or clocking blocks to state the intent.</p>
