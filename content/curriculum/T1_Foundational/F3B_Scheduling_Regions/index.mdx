## Quick Take
- **What it is:** The IEEE standard divides each simulation time step into ordered scheduling regions: Preponed, Active, Inactive, NBA, Observed, Reactive, Re-Inactive, Re-NBA and Postponed (plus PLI regions), §4.4.
- **Why it matters:** Without these regions, RTL and Testbench code would step on each other's toes, creating non-deterministic race conditions.
- **The Analogy:** Think of the time step as a factory assembly line. Parts are inspected (Preponed), assembled (Active), shifted down the line (NBA), QA tested (Observed), logged (Reactive), and shipped (Postponed).

## Build Your Mental Model

SystemVerilog fixes the **order of the regions** within a time step (IEEE 1800-2023 §4.4–4.5). It does **not** fix the order of processes that are ready in the same region: those may run in any order (§4.7), and that freedom is exactly where races come from. The regions give you places to put work so that order stops mattering. Here are the regions you must understand for interviews:

| Region | Primary Purpose | Examples |
|---|---|---|
| **Preponed** | Sample stable values from the previous time step before any new changes occur. | Used by clocking blocks (input sampling) and concurrent assertions. |
| **Active** | Evaluate and update variables using blocking assignments, evaluate RHS of non-blocking assignments. | `a = b;`, `$display();` |
| **Inactive** | Process `#0` delaying statements (legacy, avoid using). | `#0 a = b;` |
| **NBA (Non-Blocking Assignment)** | Update LHS of non-blocking assignments evaluated in the Active region. | `a <= b;` |
| **Observed** | Evaluate concurrent assertions (SVA) using values sampled in the Preponed region. | `assert property (...)` |
| **Reactive** | Execute testbench program blocks and testbench checks. | Program block execution, action blocks of assertions |
| **Re-NBA** | Apply clocking-block drives and nonblocking updates made by program code, after the design's NBA updates. | `vif.cb.req <= 1;` |
| **Postponed** | Execute read-only tasks after all other regions have settled for the current time step. | `$monitor()`, `$strobe()` |

> [!IMPORTANT]
> **The Active vs. Reactive Split:** The original intent was to separate RTL (active region set) from testbench code in `program` blocks (reactive region set). That separation reduces races but does not guarantee their absence: program code can still race with other program code. UVM components are classes called from module code, so they run in the **active** region set; UVM testbenches get same-edge race safety from **clocking blocks** (Preponed sampling, Re-NBA drives), not from phasing, which orders whole phases rather than events within one time slot.

## Make It Work
- **Avoid `#0` delays:** They were used in Verilog-1995 to fix races by pushing assignments to the Inactive region. In SystemVerilog, use non-blocking assignments (`<=`) instead.
- **Use `$strobe` for debug:** If you need to print a variable's final value at the end of a time step after all NBA updates, use `$strobe` (which executes in the Postponed region) instead of `$display` (which executes in the Active region).

## Push Further
- Investigate how clocking blocks span multiple regions: inputs are sampled in the Preponed region (§14.13), outputs are driven in the Re-NBA region (§14.16) — a separate region in the reactive region set — and the `@(cb)` event fires in Observed (§14.10). F3C lets you step through all three.
- Read IEEE 1800-2023 §4.4 for the regions and §4.5 for the reference scheduling algorithm that loops through them. Notice that the scheduler can loop back from NBA to Active if new events are triggered.
