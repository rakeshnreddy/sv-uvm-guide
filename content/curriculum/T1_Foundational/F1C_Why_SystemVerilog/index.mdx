## Quick Take

- **What it is:** SystemVerilog, IEEE 1800-2023, is one language for hardware design, specification and verification (§1.1). It contains all of Verilog (IEEE 1364) and adds design features, such as `logic`, `always_ff` and enums, and verification features: classes, constrained randomization, functional coverage and assertions. UVM (Universal Verification Methodology) is a separate standard, IEEE 1800.2-2020: a class library written in SystemVerilog.
- **Why it matters:** Every lesson from F2A onward uses these features. Knowing which standard defines what tells you where to look things up, why a legacy file suddenly fails to compile, and why `uvm_component` is not in the SystemVerilog standard.
- **The Analogy:** SystemVerilog is to Verilog roughly what C++ is to C: almost all old code still compiles, but new reserved words (`class`, `new`) break a few legal old files. *Where it breaks:* SystemVerilog absorbed the Verilog standard into one document in 2009, and UVM, unlike C++'s standard library, is not part of the language standard at all.

**You will be able to:**
1. Explain how IEEE 1364 (Verilog), IEEE 1800-2023 (SystemVerilog), IEEE 1800.2-2020 (UVM) and Accellera's uvm-core 2020.3.1 library relate.
2. Match a verification problem to the SystemVerilog feature and clause that solves it: classes (Clause 8), constrained randomization (Clause 18), functional coverage (Clause 19) and assertions (Clause 16).
3. Predict whether a legacy Verilog file compiles as SystemVerilog, and fix it with `` `begin_keywords `` (§22.14), a rename or an escaped identifier.
4. Name the design features SystemVerilog adds, and explain why it is one language for design and verification.

## Build Your Mental Model

### From Verilog to SystemVerilog

In the 1990s Verilog (IEEE 1364) was the standard language for describing hardware, but it was weak for building testbenches. Verification engineers often wrote testbenches in separate hardware verification languages such as **e** (Specman) and **Vera**. Designers and verifiers spoke different languages.

**SystemVerilog** closed that gap in steps, and the standards record the steps precisely:
- **Accellera**, an industry standards body, built SystemVerilog as extensions to Verilog. Its SystemVerilog 3.1a manual was the precursor to IEEE 1800-2005 (IEEE 1800-2023 §1.4). Industry accounts credit Co-Design Automation's Superlog as the starting point for the design extensions and Synopsys's OpenVera donation for most verification features; those donor details come from industry history, not from the IEEE text.
- **IEEE 1800-2005 held only the extensions.** It relied on IEEE 1364-2005 for the base Verilog language and was not a self-contained standard (§1.3 NOTE, §1.4 NOTE).
- **IEEE 1800-2009 merged the two** into one document. Since 2009, SystemVerilog contains all of Verilog (§1.3 NOTE).
- Revisions followed in 2012, 2017 and 2023. **IEEE 1800-2023** is current.
- The e language was not merged. It was standardized separately as IEEE 1647.

A common pitfall is saying "SystemVerilog replaced Verilog." It did not: it absorbed it. A Verilog file is SystemVerilog code, with the keyword exceptions explained below.

### One language for design and verification

IEEE 1800-2023 §1.1 describes SystemVerilog as a unified hardware design, specification and verification language. The design half matters as much as the verification half:

| Design feature | Problem it fixes | IEEE 1800-2023 |
|---|---|---|
| `logic` | One 4-state type for what Verilog split between `reg` and `wire` uses; `logic` and `reg` are the same type. [F2A](/curriculum/T1_Foundational/F2A_Core_Data_Types/index) teaches the rules for driving it. | §6.11.2 |
| `always_comb`, `always_ff` | State the intent; tools should warn when the code does not match it, for example an inferred latch in `always_comb` | §9.2.2.2, §9.2.2.4 |
| `unique` and `priority` on `if` and `case` | State that conditions are exclusive or ordered; violations are reported | §12.4.2, §12.5.3 |
| `enum` | Named states instead of magic numbers | §6.19 |
| `struct` and `typedef` | Bundle related fields into one type | §7.2, §6.18 |
| Packages | Share types and functions between the RTL and the testbench | §26.2 |
| Interfaces | Bundle a bus's signals once; used by both the RTL and testbenches | Clause 25 |

Two opposite mistakes, both wrong: "SystemVerilog is only a verification language, so RTL stays in Verilog," and "SystemVerilog is a design language, and testbenches are written in UVM." The RTL in this course is written in SystemVerilog, and UVM is SystemVerilog code.

### Four verification features and the problems they solve

Each verification feature answers one testbench problem that Verilog left to hand-written code:

| Testbench problem | Feature | IEEE 1800-2023 |
|---|---|---|
| Reuse one driver or checker across tests and projects | Classes, with inheritance and polymorphism | Clause 8 |
| Generate many legal stimuli without hand-writing each one | Constrained randomization | Clause 18 |
| Know whether every interesting case actually happened | Functional coverage (covergroups) | Clause 19 |
| Check timing rules on every clock, automatically | Assertions (SVA) | Clause 16 |

Here are tiny previews. You do not need to follow every keyword yet: I-SV-1, I-SV-2A, I-SV-3A and I-SV-4A teach the syntax.

**Classes and constrained randomization.** Instead of hand-writing 1,000 packets, you state the legal values once and call `randomize()` in a loop. Always check its result: it returns 0 when the constraints cannot be met.

```systemverilog
// snippet: preview of Clauses 8 and 18
class Packet;
  rand bit [7:0] length;
  constraint c_len { length inside {[1:99]}; }   // the legal range, stated once
endclass

initial begin
  Packet p;
  p = new();
  repeat (1000) begin
    if (!p.randomize()) $fatal(1, "randomize failed");
    // ...send p to the DUT
  end
end
```

**Functional coverage.** A covergroup records which values actually occurred. One declared inside a class can see the class's fields, and it is created in the class's `new()` (§19.4). This one has no clocking event, so the testbench calls `sample()` after each randomization.

```systemverilog
// snippet: preview of Clause 19
class Packet;
  rand bit [7:0] length;
  constraint c_len { length inside {[1:99]}; }

  covergroup cg_len;                 // embedded covergroup: it can see length
    coverpoint length {
      bins low  = {[1:32]};
      bins high = {[33:99]};
    }
  endgroup

  function new();
    cg_len = new();                  // an embedded covergroup is created in new()
  endfunction
endclass

// After each successful p.randomize(), record the value:
// p.cg_len.sample();
```

**Assertions.** One line states a timing rule, and the simulator checks it on every clock:

```systemverilog
// snippet: preview of Clause 16
a_req_gnt: assert property (@(posedge clk) req |-> ##2 gnt);
```

Read it as: at every rising edge of `clk` where `req` is sampled 1, `gnt` must be sampled 1 exactly two rising edges later. `|->` means "if the left side matches, check the right side starting from the same edge", and `##2` means "two clock cycles later". Values are sampled at the clock edge, and nothing is checked about `gnt` in between.

### UVM: a separate standard and a library

**UVM** (Universal Verification Methodology) is not part of IEEE 1800:
- **The standard.** IEEE 1800.2-2020 defines UVM as a set of application programming interfaces (APIs) for a base class library, built on IEEE 1800 (IEEE 1800.2-2020 §1.1; its Clause 2 lists IEEE 1800 as its normative reference). It is a revision of IEEE 1800.2-2017.
- **Its roots.** The standard's informative Introduction says UVM is built on the Open Verification Methodology (OVM), which combined the Advanced Verification Methodology (AVM) and the Universal Reuse Methodology (URM) with concepts from the e Reuse Methodology (eRM). UVM also adds concepts and code from the Verification Methodology Manual (VMM), and its transaction-level modeling (TLM) is based on the Open SystemC Initiative's (OSCI) work for SystemC.
- **The library.** A standard defines an API; code implements it. Accellera's **uvm-core 2020.3.1** is a SystemVerilog library "matching the requirements of IEEE 1800.2-2020", under the Apache-2.0 license. Its deviations from the standard are listed in its `DEVIATIONS.md` file (uvm-core README).
- **How you use it.** Like any SystemVerilog package: all of UVM is exported through `uvm_pkg` (IEEE 1800.2-2020 §1.4.5). It needs an IEEE 1800-compliant simulator; check your vendor's supported versions.

```systemverilog
// snippet: how UVM code starts (taught from I-UVM-1A)
`include "uvm_macros.svh"   // uvm-core's file of UVM macros, such as `uvm_component_utils
import uvm_pkg::*;          // every UVM class, from the library
```

The second classic mistake is "UVM is part of IEEE 1800." `uvm_component`, `uvm_test` and every other `uvm_` class are defined by IEEE 1800.2 and shipped as a library; a SystemVerilog simulator knows nothing about them until you compile `uvm_pkg`.

### Recap

- IEEE 1800-2009 merged Verilog (IEEE 1364-2005) into SystemVerilog, so SystemVerilog contains all of Verilog; IEEE 1800-2023 is current.
- SystemVerilog is one language for design (`logic`, `always_ff`, `unique`, enums, structs, packages, interfaces) and verification (classes, constraints, coverage, assertions).
- Classes (Clause 8) give reuse, constrained randomization (Clause 18) gives stimulus breadth, functional coverage (Clause 19) gives measurement, and assertions (Clause 16) give timing checks.
- UVM is a separate standard (IEEE 1800.2-2020) implemented by a library (uvm-core) that you import as `uvm_pkg`.
- New keywords can break legal legacy files; `` `begin_keywords ``, a rename or an escaped identifier fixes them.

## Make It Work

### Worked example: bring a legacy Verilog file into a SystemVerilog bench

A legacy Verilog-2001 counter names its output port `logic`. That was legal in Verilog-2001; it is a keyword in SystemVerilog. The first file keeps the legacy code unchanged and selects the Verilog-2001 keyword set for it alone.

```systemverilog
// compile
// legacy_cnt.v: legal IEEE 1364-2001 Verilog. 'logic' is an ordinary name there.
`timescale 1ns/1ps
`begin_keywords "1364-2001"
module legacy_cnt (clk, rst, logic);
  input        clk;
  input        rst;
  output [7:0] logic;
  reg    [7:0] logic;

  always @(posedge clk)
    if (rst) logic <= 8'd0;
    else     logic <= logic + 8'd1;
endmodule
`end_keywords
```

The second file is an ordinary SystemVerilog testbench. It cannot write `.logic(q)`, because `logic` is a keyword here; it names the port with an escaped identifier instead.

```systemverilog
// compile
// tb_top.sv: compiled with SystemVerilog keywords.
`timescale 1ns/1ps
module tb_top;
  logic       clk = 1'b0;
  logic       rst = 1'b1;
  logic [7:0] q;

  // .logic(q) would be a syntax error here: logic is a keyword in SystemVerilog.
  // An escaped identifier names the port; the space before '(' ends it.
  legacy_cnt u_cnt (.clk(clk), .rst(rst), .\logic (q));

  always #5 clk = ~clk;

  initial begin
    @(posedge clk);              // reset is sampled at this edge
    rst <= 1'b0;                 // nonblocking: released after the edge, so no race
    repeat (3) @(posedge clk);   // three increments
    @(negedge clk);              // check mid-cycle, when q is stable
    if (q !== 8'd3) $error("q=%0d, expected 3", q);  // self-checking, as in F1B
    else            $display("PASS q=%0d", q);
    $finish;
  end
endmodule
```

Expected output (traced by hand; not from a simulator run):

```text
PASS q=3
```

Why it works, line by line:
- `` `begin_keywords "1364-2001" `` reserves only the Verilog-2001 keywords for the code that follows, and the matching `` `end_keywords `` restores the previous set, so the testbench file is unaffected (§22.14). The directives must sit outside any module.
- `\logic ` is an **escaped identifier**: it starts with a backslash and ends at white space. An escaped keyword is treated as a user-defined identifier (§5.6.1), so it names the port called `logic`.
- Both files carry `` `timescale ``, because it is an error for some design elements to have a time unit and others not (§3.14.2.3).
- The counter resets at the first edge (5 ns), then counts at the next three edges (15, 25 and 35 ns). The testbench checks at the falling edge at 40 ns, when `q` is stable at 3.
- Remove the `` `begin_keywords `` pair and compile the legacy file with SystemVerilog keywords, and it fails: that is the clash the pair fixes. Which keywords a tool uses for a `.v` file with no directive is tool-dependent, which is exactly why the explicit pair is safer.

**How to bring any legacy file in:**
1. Compile it as SystemVerilog and read the errors: they name the identifiers that became keywords.
2. Wrap the legacy file in a `` `begin_keywords `` pair naming the Verilog version it was written for, and leave its contents unchanged.
3. In the SystemVerilog files that connect to it, name each clashing port with an escaped identifier (`\logic `, with the space) or connect by position.
4. When the legacy file can be edited, rename the identifier and drop the directives.

To run it, compile both files with an IEEE 1800-compliant simulator, with `tb_top` as the top module. How a tool decides which files are SystemVerilog, and its exact commands, are tool-dependent.

## Push Further

### Expert: How a tool picks the keyword set

- With no directive, the reserved keyword list is the implementation's default set, and that default is implementation dependent (§22.14). The standard mentions invocation options and source file extensions as possible ways to choose it; what your tool does is tool-dependent.
- `` `begin_keywords `` can appear only outside a design element. It affects all source that follows, even across file boundaries, until the matching `` `end_keywords ``; `` `resetall `` does not affect it; and pairs can nest, each `` `end_keywords `` restoring the set that was in effect before (§22.14).
- An implementation that does not recognize the version specifier must report an error, and implementations may add their own specifiers (§22.14).
- The directives change only which identifiers are reserved. They do not change the language's semantics (§22.14), so `` `begin_keywords "1364-2001" `` does not make a file behave like a Verilog-2001 simulator.

### Expert: Keywords by revision

- Each version specifier reserves the keywords of its revision: 1364-1995 (Table 22-1), plus Table 22-2 for 1364-2001, Table 22-3 for 1364-2005, Table 22-4 for 1800-2005 (which brought `bit`, `logic`, `class` and `final`), Table 22-5 for 1800-2009 (`checker`, `let`, `until` and others) and Table 22-6 for 1800-2012 (`implements`, `interconnect`, `nettype`, `soft`). IEEE 1800-2017 and 1800-2023 add no new reserved keywords (§22.14.2 to §22.14.9).
- IEEE 1800-2023 Annex B lists every keyword of the current revision.
- A `"1364-2001-noconfig"` specifier also exists: it removes the configuration keywords, such as `config` and `library`, from the 1364-2001 list (§22.14.4).
- An escaped keyword, such as `\logic `, is a user-defined identifier (§5.6.1); keywords are only ever the nonescaped, lowercase forms (§5.6.2).

### Expert: Not only keywords

Keywords are not the only difference legacy code can meet. In IEEE 1364-2005, a declaration initializer ran as if it were an assignment in an initial procedure, after simulation started. In SystemVerilog, a static variable's initial value is set before any initial or always procedure starts (IEEE 1800-2023 §6.8 and its NOTE).

```systemverilog
// snippet
reg ready = 1'b1;   // Verilog-2005: like "initial ready = 1'b1;" at time 0
always @(ready) $display("ready changed to %b", ready);
```

Under the Verilog-2005 rule, the change from X to 1 at time 0 could wake the `always` block, depending on which process ran first. Under SystemVerilog, `ready` is already 1 before the `always` block starts waiting, so it never sees a change at time 0. Legacy code that relied on that time-0 event behaves differently.

### Expert: What IEEE 1800-2023 added

The 2023 revision added no keywords, but it did add features. Four that testbench writers notice:
- **Triple-quoted strings** (`"""…"""`) that can contain unescaped quotes and newlines (§5.9).
- **The array `map()` method**, which returns a new array with each element replaced by an expression (§7.12.5).
- **`:initial`, `:extends` and `:final` method specifiers** (§8.20). `:initial` says the method must not override a virtual method, `:extends` says it must override one, and `:final` says no subclass may override it. The tool reports an error when the code breaks the promise, so an accidental override, or a missing one, no longer passes silently.
- **Weak references** (`weak_reference#(T)`), which refer to an object without preventing its garbage collection (§8.30).

Simulator support for each 2023 feature arrives at different times (tool-dependent). Check every tool in your flow before a shared testbench depends on one.

### Expert: Standard vs implementation

- IEEE 1800.2-2020 is a revision of IEEE 1800.2-2017 and defines the UVM API (front matter, §1.1). Accellera's uvm-core 2020.3.1 implements it and lists where it deviates in `DEVIATIONS.md` (README).
- Code can test which UVM it is compiled with. The standard requires `` `UVM_VERSION `` (defined as 2020; Annex B.7.1), a `UVM_VERSION_STRING` string parameter in `uvm_pkg` that identifies the implementation (B.7.2), and `` `UVM_VERSION_POST_2017 `` for versions after IEEE 1800.2-2017 (B.7.3).
- uvm-core also defines `` `UVM_POST_VERSION_1_2 ``, so code written for Accellera's older UVM 1.2 can test for it. That macro is uvm-core implementation, not standard (uvm-core 2020.3.1, `src/macros/uvm_version_defines.svh`).
- Which UVM version a simulator ships precompiled, and how to point it at a different uvm-core, is tool-dependent.

```systemverilog
// snippet
`ifdef UVM_VERSION_POST_2017
  // code that needs an IEEE 1800.2-based UVM
`else
  // fallback for an older Accellera UVM
`endif
```

### Drill: problem to feature

For each testbench or design problem, name the SystemVerilog feature and its clause.

1. Reuse one driver across several projects.
2. Generate only legal bursts.
3. Know whether every burst length was tried.
4. `gnt` must follow `req` within 3 cycles.
5. One type for what Verilog split between `reg` and `wire` uses.
6. Catch an accidental latch in combinational code.
7. Bundle a bus's signals once, for both RTL and testbench.
8. Share types between the RTL and the testbench.

<details>
<summary>Worked solution</summary>

| # | Feature | IEEE 1800-2023 |
|---|---|---|
| 1 | Classes, with inheritance | Clause 8 |
| 2 | Constrained randomization | Clause 18 |
| 3 | Functional coverage (covergroups) | Clause 19 |
| 4 | Concurrent assertions | Clause 16 |
| 5 | `logic` | §6.11.2 |
| 6 | `always_comb` (tools should warn when latched behaviour is inferred) | §9.2.2.2 |
| 7 | Interfaces | Clause 25 |
| 8 | Packages | §26.2 |

Items 1 to 4 are the verification half and items 5 to 8 the design half; interfaces and packages serve both.
