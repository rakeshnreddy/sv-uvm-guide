## Quick Take
- **What it is:** SystemVerilog (IEEE 1800) is the industry-standard hardware design and verification language. It extended Verilog's RTL capabilities with design features from Co-Design Automation's Superlog and verification features largely from Synopsys's OpenVera (Vera) donation.
- **Why it matters:** Before SystemVerilog, designers and verifiers spoke different languages. SV eliminated the language gap and enabled reusable, scalable verification methodologies like UVM.
- **The Standard:** IEEE 1800-2023 is the current revision. Since IEEE 1800-2009, the Verilog standard (IEEE 1364-2005) has been merged into it, so SystemVerilog contains all of Verilog. It also reserves new keywords, so a few legacy files need `` `begin_keywords `` to compile (§22.14).

## The Evolution of a Language

In the 1990s, Verilog was king. It was great for describing hardware (RTL) but weak for verifying it. Verification engineers often used separate hardware verification languages such as **e** (Specman) or **Vera** for complex testbenches. This created a "language gap": designers spoke Verilog, verifiers spoke something else.

**SystemVerilog** closed that gap. Accellera built it from donations, and IEEE standardized it as IEEE 1800-2005. It combined:
1.  **Hardware description:** All of Verilog, plus design extensions from Co-Design Automation's **Superlog** donation.
2.  **Verification features:** Classes, constrained randomization and functional coverage, largely based on Synopsys's **OpenVera** (Vera) donation. Assertions (SVA) grew from the **OpenVera Assertions** donation.
3.  **C-like types:** `typedef`, structs, enums, 2-state `int` and `bit`.

The **e** language was not merged into SystemVerilog. It was standardized separately as IEEE 1647.

The result is one language for both design and verification.

## Key Superpowers

### 1. Object-Oriented Programming (OOP)
SystemVerilog introduced **Classes** (IEEE 1800-2023 §8). This allowed verification engineers to build reusable testbench components (Drivers, Monitors, Scoreboards) that could be instantiated dynamically. This is the foundation of **UVM**.

### 2. Constrained Randomization
Instead of writing a loop to generate 1,000 packets, you define a class with random variables and constraints (IEEE 1800-2023 §18).
```systemverilog
class Packet;
  rand bit [7:0] length;
  constraint c_len { length > 0; length < 100; }
endclass
```
The solver does the hard work for you.

### 3. Functional Coverage
You can define "Covergroups" to track what values a variable has taken (IEEE 1800-2023 §19). A covergroup embedded in a class can see the class's fields and is created in `new()` (§19.4):
```systemverilog
class Packet;
  rand bit [7:0] length;
  constraint c_len { length > 0; length < 100; }

  covergroup cg_len;          // embedded covergroup: sees length
    coverpoint length {
      bins low  = {[1:32]};
      bins high = {[33:99]};  // length < 100, so 100 is never legal
    }
  endgroup

  function new();
    cg_len = new();           // embedded covergroups are created in new()
  endfunction
endclass

// After each p.randomize(), record the value:
// p.cg_len.sample();
```
This covergroup has no clocking event, so the testbench calls `sample()` explicitly after each randomization.

### 4. Assertions (SVA)
A concise way to specify temporal behavior (IEEE 1800-2023 §16).
`assert property (@(posedge clk) req |-> ##2 gnt);`
(If `req` is high, `gnt` *must* be high 2 cycles later).
