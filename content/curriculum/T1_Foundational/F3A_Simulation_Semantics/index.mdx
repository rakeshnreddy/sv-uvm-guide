## Quick Take

- **What it is:** A SystemVerilog simulator is a *discrete-event* engine (IEEE 1800-2023 §4.3). Nothing runs on a tick of its own. A **process** (an `initial` or `always` block, a continuous `assign`, a gate) runs only when an **event** wakes it, and simulation time jumps straight to the next moment that has events once the current moment has none left (§4.4). Every `#d` is a plain number that its module's **time unit** and **time precision** turn into a real delay (§3.14).
- **Why it matters:** The first bugs a new testbench (TB) meets live here: a delay 1000× too long or too short, a log time stamp that disagrees with the waveform, a compile error about missing time units, two prints "at the same time" that show different values, and a first log line that one simulator prints and another does not. Knowing what the standard fixes, and what it leaves to each simulator, is what makes a bench give the same answer on every tool.
- **The Analogy:** A to-do list sorted by due time. You finish everything due *now*, including new items those tasks add for *now*, then jump straight to the next due time without ticking through the empty minutes in between. *Where it breaks:* "now" is split into ordered stages (the regions of [F3B](/curriculum/T1_Foundational/F3B_Scheduling_Regions/index)), and the list never says which of two items due at the same stage comes first. [F3C](/curriculum/T1_Foundational/F3C_Delta_Cycles_and_Race_Conditions/index) shows when that order changes the result.

### Processes, events and time slots

A design is a set of small programs running side by side. IEEE 1800-2023 calls each one a **process** (§4.3): every `initial`, `always`, `always_comb`, `always_ff` and `always_latch` procedure, every continuous `assign` and every gate primitive. At any moment a process is either running or suspended, waiting for something.

Two kinds of **event** move the simulation forward (§4.3):

- An **update event** is a change in the value of a net or variable.
- An **evaluation event** is one execution of a process, for example because an update it is sensitive to has happened or because its delay has run out. When an update executes, every process sensitive to it is considered for evaluation, in an arbitrary order.

All the events scheduled for one simulation time form a **time slot** (§4.4). The simulator executes and removes every event of the current time slot before it moves on to the next non-empty time slot, in time order. It never goes backwards in time (§4.4).

**What wakes a process.** A suspended process waits on a timing control, and each kind wakes on something different:

| A process waiting on … | wakes when … | Example | Clause |
|---|---|---|---|
| an event control `@(expr)` | the value of `expr` changes; with `posedge` or `negedge`, only on that edge | `@(posedge clk)` | §9.4.2 |
| a level wait `wait (expr)` | `expr` is true, at once if it already is | `wait (ready)` | §9.4.3 |
| a delay `#d` | simulation time reaches now + d | `#10` | §9.4.1 |
| its own inputs (implicit) | any value it reads changes | `assign y = a & b;` or `always_comb` | §4.9.1, §9.2.2.2 |

Only a real change counts. Writing a variable's current value again wakes no `@(a)`, and `@(a & b)` wakes only when the result of `a & b` changes (§9.4.2).

**The two mistakes everyone makes:**

1. *"Time advances after every statement."* It does not. A process runs in zero simulated time until it reaches a timing control or ends. Only a delay puts work into a *later* time slot.
2. *"`@(expr)` notices a change that already happened."* It does not. An event control sees only changes that occur while the process waits. Use `wait (expr)` for a level that may already be true.

### The scheduler loop: how time advances

IEEE 1800-2023 defines simulation through a reference algorithm (§4.5). A simulator may work differently inside, as long as everything you can observe is consistent with that algorithm (§4.3). The same loop as text, simplified from §4.5:

```text
T = 0; initialize nets and variables; schedule time-0 events
while (some time slot is non-empty) {
  move to the first non-empty time slot and set T   // the only place time advances
  while (this time slot has events) {
    E = any event of the slot                         // "any": the order is not fixed
    if (E is an update event)
      change the value, then schedule an evaluation event
      for every process sensitive to it               // same time slot
    else
      run the process until it suspends or ends       // it may schedule new events,
  }                                                   // now or at a later time
}
```

In the real algorithm a time slot is emptied region by region, so "any event" means any event of the current region (F3B).

**Predict first.** The loop's last comment says a process may schedule new events "now or at a later time". Sort these six before you open the answer or read on, because rule 3 below gives the reasoning: which ones book an event at a later time? `#10`, `q <= #2 d;`, `q <= d;`, `@(posedge clk)`, `wait (ready)`, `-> done`.

<details className="my-4 rounded-xl border border-border/70 p-3">
<summary className="cursor-pointer font-semibold">Check your sort</summary>

| Item | Books an event at a later time? |
|---|---|
| `#10` | yes: the process resumes 10 units ahead |
| `q <= #2 d;` | yes: the update lands 2 units ahead |
| `q <= d;` | no: the update lands later in this time slot |
| `@(posedge clk)` | no: it only waits for a change |
| `wait (ready)` | no: it only waits for a level |
| `-> done` | no: it wakes its waiters in this time slot |

Two more also book an event at a later time: a gate or net delay, and a clocking-block output skew (F4C).

A process asleep on `@` or `wait` can wake at a later time, but only because a delay somewhere else booked an event there.

</details>

Read four rules off the loop:

1. **Time moves in one place only.** When the current time slot is empty, the simulator jumps to the next non-empty one. There is no fixed step size and no tick in between.
2. **Work inside a slot can create more work in the same slot.** A write wakes a reader, which may write again. Every extra pass takes zero simulated time.
3. **Only a delay reaches a later slot.** `#d`, an intra-assignment delay such as `q <= #2 d;`, a gate or net delay, and a clocking-block output skew ([F4C](/curriculum/T1_Foundational/F4C_Clocking_Blocks/index)) schedule events at a future time. `@`, `wait`, `->` and a `<=` without a delay do not.
4. **The run ends when no event is left at any time** (§9.6.1), or earlier at `$finish` (§20.2). A free-running clock (`always #5 clk = ~clk;`) always has a next event, so a bench with one must call `$finish`. A loop with no timing control at all, such as `always areg = ~areg;`, never empties its time slot: time stops and the simulator hangs. §9.2.2.1 calls this a zero-delay infinite loop. A bench built with program blocks also ends when all of them have finished (§9.6.1); F3B shows why that matters.

**How a run ends, at a glance.** The last two rows are the two "it never stops" symptoms, and the time stamp tells them apart.

| What happens | Does the run end? | Time stamps | Clause |
|---|---|---|---|
| no event is left at any time | yes | stop at the last event, and the log simply stops | §9.6.1 |
| a process calls `$finish` | yes, at that time; `final` procedures run, and nothing booked for later runs | stop at that time | §20.2, §9.2.3 |
| every program block has finished | yes, by an implicit call to `$finish` | stop at that time | §9.6.1, §24.3 |
| a free-running clock and no `$finish` | never | keep growing | follows from §9.6.1 |
| a zero-delay loop, such as `always areg = ~areg;` | never: the simulator hangs | stop changing | §9.2.2.1 |

#### Event-driven versus cycle-based simulation

IEEE 1800-2023 defines simulation as a discrete-event model (§4.3). Cycle-based evaluation is a technique some tools use instead: evaluate the design once per clock cycle and ignore what happens between edges. The standard mentions it in its assertion overview: many tools, such as formal verification tools, use cycle-based semantics and abstract away any timing between clock edges, and in some scenarios that gives different behaviour from SystemVerilog's event-based evaluation (§16.2). It also calls the clocking block a key element of a cycle-based *methodology* for writing testbenches (§14.2), which is a way of writing code, not a different simulator.

| | Event-driven (what IEEE 1800 defines) | Cycle-based (a tool technique) |
|---|---|---|
| Unit of work | one event: a value change or a process evaluation | one clock cycle: evaluate all logic once |
| How time moves | jumps to the next time that has events; any delay value works | one clock cycle at a time |
| Delays, glitches, order inside a time slot | modelled | abstracted away |
| Where you meet it | every SystemVerilog simulator | formal tools, and some fast simulation and emulation engines (tool-dependent) |

module tb_top;
  timeunit 1ns; timeprecision 1ns;

  logic clk = 0;           // initializers run before any process starts (§6.8)

**Zero-time iterations have a name.** Steps 5 to 7 are a second pass through the same time slot, triggered by the nonblocking update. Such passes exist because zero-delay logic still has cause and effect: `q` must change before `q_n` can follow it, and the simulator orders that chain with extra passes instead of inventing a delay. Engineers call each such pass a **delta cycle**. IEEE 1800-2023 never uses the word; it describes iterations of the §4.5 loop. Two facts to keep: a delta cycle takes no simulated time (`$time` is 5 in every step above), and the number of passes a slot needs never shows up in a time stamp. [F3C](/curriculum/T1_Foundational/F3C_Delta_Cycles_and_Race_Conditions/index) traces delta cycles region by region and shows how they create races.

**A preview of `#0`.** `#0` suspends a process and resumes it later in the *same* time slot, still before the nonblocking update of step 5 (§4.4.2.3, §4.4.2.4). It never advances time. Code that uses `#0` to wait for another process is betting on an order the standard does not promise. F3B places `#0` in its region, and F3C shows why it is not a fix.

**Pitfalls:**

- *"A nonblocking update happens at a later time."* No: step 5 is in the same time slot (§4.9.4). `<=` changes *when within the slot* the value lands, not the time stamp.
- *"Delta cycles take simulated time."* No: all eight steps happen at t = 5 ns.

### The order the standard leaves open

The trace above has one freedom: steps 3 and 4. The standard deliberately leaves several such choices to the simulator:

1. **Processes woken together run in any order.** When an update executes, the processes sensitive to it are considered for evaluation in an arbitrary order (§4.3), and ready events can be taken in any order (§4.7).
2. **A running process can be paused part-way.** Statements without a timing control do not have to execute as one event: the simulator may suspend a process and run others in between (§4.7). Statements inside one `begin … end` still execute in source order (§4.6).
3. **`initial` and `always` start in no particular order.** The standard implies no order between `initial` and `always` procedures, and `initial` procedures need not run first (§9.2).

| Fixed by the standard | Left to the simulator |
|---|---|
| statements in one `begin … end` run in source order (§4.6 a) | a process may be paused between those statements while others run (§4.7) |
| nonblocking updates apply in the order the statements executed (§4.6 b) | which process ran first, so updates from two processes can land in either order (§4.7) |
| declaration initializers run before any `initial` or `always` procedure starts (§6.8) | whether `initial` or `always` starts first (§9.2) |
| every event of a time slot happens at that slot's time (§4.4) | the order of processes woken together (§4.3, §4.7) |

None of these is a simulator bug. Different tools, versions or optimization switches may choose differently, and the standard expects such differences (§4.3). Here is the classic place this bites, at time 0:

```systemverilog
// compile
module tb_top;
  timeunit 1ns; timeprecision 1ns;

  logic a;                      // starts as x: no declaration initializer

  always @(a) $display("t=%0d a=%b", $time, a);   // wakes on every change of a

  initial begin
    a = 0;                      // t = 0: is the always block waiting yet? Not defined.
    #10 a = 1;
    #10 a = 0;
  end
endmodule
```

#### Why simulator-independent code matters

Each freedom above, and each default the standard leaves to the tool, is a way for one bench to give two answers:

| Freedom or tool default | How it shows up in a log | The defence |
|---|---|---|
| the order of processes woken together, and of `initial` versus `always` at time 0 (§4.3, §4.7, §9.2) | a first line that appears on one simulator only, or comes and goes when files are reordered | a declaration initializer, and no same-time processes that depend on their order |
| the time unit and precision of a file that declares none (§3.14.2.3, §22.7) | a delay 10× or 1000× too long or too short | a time unit in every file |
| which files form one compilation unit, and therefore how far a `` `timescale `` reaches (§3.12.1) | delays that change when the file list is reordered | `timeunit` and `timeprecision` inside each element (§3.14.2.2) |
| the default `%t` format (§20.4.3, Table 20-3) | time stamps that look scaled, such as `@ 15000` for an event at 15 ns | one `$timeformat` call |

A result that depends on any of these can pass on one simulator and fail on another, or change when someone reorders the file list. Sign-off needs results that do not depend on the tool. So declare a time unit in every file, set `$timeformat` once, use initializers instead of time-0 assignments, and never let two same-time processes depend on their order ([F3C](/curriculum/T1_Foundational/F3C_Delta_Cycles_and_Race_Conditions/index)).

- the **time precision** says how finely delays are rounded before they are used (§3.14.1). It must be at least as fine as the unit (§3.14).

Both settings are written as 1, 10 or 100 of `s`, `ms`, `us`, `ns`, `ps` or `fs` (§3.14). There are two ways to set them:

```systemverilog
// snippet: three design elements in one file
`timescale 1ns / 1ps       // compiler directive: outside any design element (§22.7)

module a_mod;              // no timeunit: takes 1ns / 1ps from the directive above
endmodule

module b_mod;
  timeunit 100ps;          // keywords inside the element (§3.14.2.2);
  timeprecision 10fs;      // they come before any other item in it
endmodule

module c_mod;
  timeunit 1ns / 1ps;      // one-line form: unit / precision
endmodule
```

**Prefer the keywords.** A `` `timescale `` applies to every design element compiled after it that has no `timeunit` of its own, until the next `` `timescale ``, across all the files of one **compilation unit**, the group of source files a tool compiles together (§3.12.1, §3.14.2.1, §22.2). A file without its own setting therefore inherits whatever the previous file left behind, and the result depends on compile order. §3.14.2.1 shows a module that gets nanoseconds in one compile order and picoseconds in another. `timeunit` and `timeprecision` inside the element remove that dependency (§3.14.2.2).

**Rounding.** Each delay is scaled by the unit, then rounded to the precision of the element that contains it (§3.14.1):

| Unit / precision | You write | Scaled | Rounded to the precision |
|---|---|---|---|
| 1ns / 100ps | `#2.75` | 2.75 ns | 2.8 ns (the standard's own example, §3.14.1) |
| 1ns / 100ps | `#1.26` | 1.26 ns | 1.3 ns |
| 10ns / 1ns | `#1.26` | 12.6 ns | 13 ns |
| 10ns / 1ns | `#2.5` | 25 ns | 25 ns (no rounding needed) |
| 1ns / 1ns | `#0.4` | 0.4 ns | 0 ns: the statement runs in the same time slot |
| 1ps / 1ps | `#5ns` | 5000 ps | 5000 ps, because a time literal is scaled to the current unit (§5.8) |

A finer precision elsewhere in the design does not help a coarse module: its delays are accurate only to its own precision (§3.14.1). The picture shows one delay in two modules.

**Which unit applies?** If a design element declares no `timeunit`, the first of these rules that applies decides (§3.14.2.3):

1. a nested module or interface inherits the unit of the module or interface around it;
2. else the last `` `timescale `` seen earlier in the same compilation unit applies;
3. else a `timeunit` declared in the compilation-unit scope (outside every design element) applies;
4. else the tool's default applies, which the standard leaves implementation-specific.

The precision follows the same rules. The compilation-unit scope can take its unit only from a `timeunit` declaration, never from a `` `timescale `` (§3.14.2.3). One more rule overrides convenience: it is an **error** for some design elements to have a time unit and precision while others have none (§3.14.2.3). How a tool reports that, as an error or a warning, is tool-dependent.

**The global precision and `1step`.** The **global time precision**, also called the *simulation time unit*, is the finest precision anywhere in the design. It counts every `timeprecision`, every precision written with `timeunit … / …`, and the smallest precision of all the `` `timescale `` directives (§3.14.3). Every simulation time is a whole number of these steps. `$printtimescale($root)` prints it (§20.4.2). The special delay `1step` equals the global precision (§3.14.3); clocking blocks use `#1step` for sampling, as [F4C](/curriculum/T1_Foundational/F4C_Clocking_Blocks/index) shows.

**Time literals.** `#5ns`, `#2.1ns` and `40ps` carry a unit where you write them: the literal is converted to a real number in the current time unit (§5.8). So `#5ns` waits 5 ns in a 1 ns module and in a 1 ps module alike, which makes literals the safe way to write delays in shared code. The delay is still rounded to the module's precision: in a 10ns/1ns module, `#2.1ns` becomes 0.21 units, which rounds to 2 ns (§3.14.1). The conversion happens where the literal is written, though: a value stored in a variable has no unit (Push Further).

**Pitfalls:**

- *"A finer precision elsewhere rescues a coarse module."* No: `#0.4` in a 1ns/1ns module is 0 even if another module uses 1 fs (§3.14.1).
- *"`$timeformat` changes delays."* No: it changes only how `%t` prints (§20.4.3).
- *"A `` `timescale `` belongs to its file."* No: it reaches every later file of the same compilation unit (§3.14.2.1, §22.2), which is how a delay ends up 1000× off.

### Reading the time: `$time`, `$stime`, `$realtime` and `%t`

Three system functions read the current simulation time. All three are scaled to the **time unit of the module that calls them**, not to the precision and not to the global precision:

| Function | Returns | Clause |
|---|---|---|
| `$time` | a 64-bit integer, rounded | §20.3.1 |
| `$stime` | a 32-bit unsigned integer; the low 32 bits if the value does not fit | §20.3.2 |
| `$realtime` | a real number that keeps the fraction | §20.3.3 |

The standard's own example (§20.3.1, §20.3.3) uses a 10 ns unit, a 1 ns precision and two delays of 1.55. Here is the same experiment written as a complete unit:

```systemverilog
// compile
module tb_top;
  timeunit 10ns; timeprecision 1ns;

  initial begin
    #1.55;   // 15.5 ns, rounded to the 1 ns precision: 16 ns
    $display("$time=%0d $realtime=%.1f", $time, $realtime);
    #1.55;   // another 16 ns: t = 32 ns
    $display("$time=%0d $realtime=%.1f", $time, $realtime);
  end
endmodule
```

**Expected output** (traced by hand; it matches the values in §20.3.1 and §20.3.3):

```text
$time=2 $realtime=1.6
$time=3 $realtime=3.2
```

| Statement | Absolute time | In units of 10 ns | `$time` | `$realtime` |
|---|---|---|---|---|
| first `#1.55` (15.5 ns, rounded) | 16 ns | 1.6 | 2 | 1.6 |
| second `#1.55` | 32 ns | 3.2 | 3 | 3.2 |

The NOTE in §20.3.1 makes the point: the times `$time` reports (2 and 3) do not match the times the delays ended (16 ns and 32 ns). `$time` is not wrong; it is coarse.

**`%t` and `$timeformat`.** The `%t` format prints a time "in current time format" (§21.2.1.1). It treats its argument as a time in the caller's unit and converts it to the units chosen with `$timeformat` (§20.4.3):

```systemverilog
// snippet
$timeformat(-9, 3, " ns", 0);   // units, decimals, suffix, minimum field width
$display("t=%t", $realtime);    // after the first #1.55 above: t=16.000 ns
```

| Argument | What it is | In the call above | Default with no call (Table 20-3) |
|---|---|---|---|
| **units_number** | a power of ten from 2 (100 s) down to −15 (1 fs): −9 is ns and −12 is ps (Table 20-2) | `-9` | the smallest precision among the `` `timescale `` directives |
| **precision_number** | the number of digits after the decimal point | `3` | `0`: no decimals |
| **suffix_string** | appended after the number, such as `" ns"` | `" ns"` | none |
| **minimum_field_width** | pads the result to at least that many characters | `0` | `20` |

| `units_number` (Table 20-2) | 0 | −3 | −6 | −9 | −12 | −15 |
|---|---|---|---|---|---|---|
| Unit | 1 s | 1 ms | 1 us | 1 ns | 1 ps | 1 fs |

One call sets the format for every `%t` in the design until the next call (§20.4.3). Without any call, the defaults are: units equal to the smallest precision among the `` `timescale `` directives in the source, no decimals, no suffix, and a minimum width of 20 characters (Table 20-3). `timeunit` declarations do not count toward that default, so a design that uses only `timeunit` has a tool-dependent default.

**Asking for the settings.** `$printtimescale` prints `Time scale of (<name>) is <unit> / <precision>` for the current scope, for a named instance, for `$unit` (the compilation unit) or for `$root` (the global precision, shown as both unit and precision) (§20.4.2). `$timeunit` and `$timeprecision` return the same information as an integer exponent, such as −9 for 1 ns, for code that checks it (§20.4.1).

**Pitfalls:**

- *"`$time` reports in the precision unit."* No: in the caller's time unit, rounded (§20.3.1). `#1.5` in a module with `timeunit 1ns; timeprecision 1ps;` gives `$time` = 2, not 1500.
- *"Two equal `$time` values mean the same moment."* Only within one module. Across modules with different units, compare `%t` output.
- *"`%t` of `$time` is exact."* No: `$time` has already been rounded, so pass `$realtime` to `%t`.

### Debugging time problems

| What the log or waveform shows | Likely cause | Confirm with | Fix |
|---|---|---|---|
| A delay is 10× or 1000× too long or too short | the file inherited another unit from a leaked `` `timescale ``, or got the tool default | `$printtimescale;` inside that module | `timeunit`/`timeprecision` at the top of the file |
| Elaboration stops with a message about time units or precision | mixed specification: some elements have a unit and others none (§3.14.2.3) | the message names the element, often a package | give that element its own `timeunit` |
| Time stamps look scaled, such as `@ 15000` for an event at 15 ns | no `$timeformat`, so `%t` uses the finest `` `timescale `` precision in the build (Table 20-3) | `$printtimescale($root);` | `$timeformat(-9, 3, " ns", 0);` at time 0 in `tb_top` |
| A printed time is off by a fraction of a unit | `$time` was rounded to the module's unit (§20.3.1) | print `$realtime` beside it | print with `%t` and `$realtime` |
| A small delay has no effect | it rounded to 0 at the module's precision (§3.14.1) | `$printtimescale;` | a finer `timeprecision`, or a larger delay |
| A shared task waits 1000× too short or too long | a unitless number crossed into a scope with another unit (§5.8) | print `$realtime` before and after the call | scale inside the callee, such as `#(delay_ns * 1ns)` |
| The first log line appears on one simulator only | a time-0 race between `initial` and `always` (§9.2) | reorder the files or processes and rerun | a declaration initializer (§6.8) |
| The run never ends | a free-running clock and no `$finish` (§9.6.1) | time stamps keep growing | the test calls `$finish` |
| The run hangs and time stops moving | a zero-delay loop (§9.2.2.1) | the time stamp stops changing | add a timing control to the loop |

### In a real testbench

- **Every file declares its unit.** Put `timeunit 1ns; timeprecision 1ps;` (or your project's agreed values) first in every module, interface, program and package, as the [F2E](/curriculum/T1_Foundational/F2E_First_Self_Checking_Testbench/index) bench does. Packages matter too: a package's delays, and the `$realtime` its classes read, use the package's unit.
- **One `$timeformat`, at time 0, in `tb_top`.** In a UVM bench, call it before `run_test()`, so every `%t` in the log uses one format.
- **UVM log time stamps follow it.** uvm-core 2020.3.1 builds the time in every report message with `$swrite(time_str, "%0t", $realtime)` (`compose_report_message` in `src/base/uvm_report_server.svh`), so the `$timeformat` call in `tb_top` controls the `@ …` stamp of every `` `uvm_info `` line.

- **Delays make clocks, resets and timeouts; everything else waits on events.** Drivers and monitors wake on clock edges, and from F4C on clocking blocks. A test waits for a condition with `@` or `wait`, never for a guessed `#delay` that breaks as soon as the design's latency changes.

- A process runs only when an event wakes it; an update event is a value change, and an evaluation event runs a process sensitive to it (§4.3).
- Time jumps to the next non-empty time slot only when the current one is empty (§4.4). Delta cycles are extra passes inside one slot and take no time.
- The standard leaves the order of same-time processes open (§4.7, §9.2). Code whose result depends on that order is a race.
- `#d` is scaled by the element's time unit and rounded to its precision (§3.14.1). Declare `timeunit`/`timeprecision` in every file.
- `$time`, `$stime` and `$realtime` are in the caller's unit (§20.3). Print logs with `%t`, `$realtime` and one `$timeformat` call.

## Make It Work

### Worked example: two modules, two time units

Two design elements in one file, each with its own unit. `tb_top` sets one time format for the whole design, prints the time settings, and both modules print the same three views of the time after the same `#1.26`.

```systemverilog
// compile
// One file, two design elements, two time units. Each element declares its own
// unit, so nothing depends on compile order (IEEE 1800-2023 §3.14.2.2).

module slow_gen;
  timeunit 10ns; timeprecision 1ns;      // a model written in 10 ns steps

  initial begin
    #1.26;                               // 12.6 ns, rounded to the 1 ns precision
    $display("slow_gen $time=%0d $realtime=%.2f %%t=%t", $time, $realtime, $realtime);
    #1.26;                               // another 13 ns
    $display("slow_gen $time=%0d $realtime=%.2f %%t=%t", $time, $realtime, $realtime);
  end
endmodule

module tb_top;
  timeunit 1ns; timeprecision 100ps;

  slow_gen u_slow ();

  initial begin
    $timeformat(-9, 1, " ns", 0);        // all %t output: ns, 1 decimal, no padding
    $printtimescale;                     // this module
    $printtimescale(u_slow);             // the instance
    $printtimescale($root);              // the global precision
    #1.26;                               // 1.26 ns, rounded to the 100 ps precision
    $display("tb_top   $time=%0d $realtime=%.2f %%t=%t", $time, $realtime, $realtime);
    #30 $finish;                         // after u_slow's last print at 26 ns
  end
endmodule
```

**Run it.** Save both modules in one file, compile the file as one compilation unit and elaborate `tb_top` as the top module. Any SystemVerilog simulator should accept it, for example on EDA Playground. Support for `$printtimescale` and fractional delays in open-source simulators varies, and this example has not been run in this project's CI.

### How to apply this in your own bench

1. Put `timeunit` and `timeprecision` at the top of every module, interface, program and package you write.
2. Call `$timeformat` once, at time 0, in `tb_top`, before anything prints. In a UVM bench, do it before `run_test()`.
3. Print times with `%t` and `$realtime`. Keep raw `$time` for arithmetic inside one module.
4. When a delay or a time stamp looks wrong, add `$printtimescale;` to the suspect module and `$printtimescale($root);` to `tb_top`.
5. In shared code (packages and interfaces), write delays as time literals such as `#5ns`, or scale a real argument inside, such as `#(delay_ns * 1ns)`.
6. Give variables their starting values in their declarations, and make the first real change after a delay.

A bench header that follows these steps:

```systemverilog
// snippet: the numbered comments match the steps above
module tb_top;
  timeunit 1ns; timeprecision 1ps;    // step 1: the first items in the element

  logic clk = 0;                      // step 6: the starting value in the declaration

  initial begin
    $timeformat(-9, 3, " ns", 0);     // step 2: once, at time 0, before anything prints
    $printtimescale;                  // step 4: this module's unit and precision
    $printtimescale($root);           // step 4: the global precision
    #1 $display("t=%t", $realtime);   // step 3: %t with $realtime, not raw $time
  end
endmodule
```

Consequences an expert uses (the first two explain what you just ran; with `=`, running every order shows the time-0 race):

- An `always @*` block whose inputs never change after their initializers never computes its output, while `always_comb` does (§9.2.2.2.2). That is one reason RTL style guides prefer `always_comb` (practice, not a rule of the standard).

### Expert: which time unit applies

The precedence rules (§3.14.2.3) interact with how files are grouped into compilation units:

- **Compilation units are tool-specific.** A tool must support both "all files on one command line form one compilation unit" and "each file is its own compilation unit", and it may offer other mappings (§3.12.1). A directive from one compilation unit never affects another (§3.12.1), so a `` `timescale `` in file 1 reaches file 2 only in the first mode.
- **`` `resetall `` stops a leak.** It sets the compiler directives that have a default, `` `timescale `` among them, back to that default (§22.3). After it, a file without its own `timeunit` falls through to a compilation-unit `timeunit`, if there is one, or to the tool's default (§3.14.2.3, §22.7).
- **The mixed-specification error covers packages.** A design element is a module, program, interface, checker, package, primitive or configuration (§3.2), and §3.14.2.3 makes it an error for some to have a unit while others have none. uvm-core 2020.3.1's `src/uvm_pkg.sv` declares no time unit, so UVM takes its unit from a `` `timescale `` earlier in its compilation unit, from a compilation-unit `timeunit`, or from the tool default.
- **Tool-dependent:** command-line options that give files without a unit a default `timescale`, whether the mixed case is reported as an error or a warning, and the default unit itself.

### Expert: global precision and `1step`

- **One file can change it.** The global precision is the minimum over every precision in the design, including the precision of every `` `timescale `` directive, even one that every element overrides with `timeunit` (§3.14.3). Add one vendor model compiled under `` `timescale 1ns/1fs `` and `$printtimescale($root)` reports 1fs / 1fs, `1step` becomes 1 fs, and the default `%t` units (Table 20-3) become femtoseconds.
- **`#1step` in a clocking block** samples a value just before the clock event, which is the same as sampling in the Preponed region of the time slot (§4.4.2.1). So it always sees the values from just before the current time slot, whatever the global precision is. F3B and F4C cover the sampling rules.
- **Cost.** Whether a finer global precision slows a simulation is implementation-dependent; the standard says nothing about speed.
- **`$stime` wraps.** In a design where every unit and precision is 1 ps, `$stime` passes 32 bits after 2^32 ps, about 4.29 ms of simulated time. At 5 ms it returns the low 32 bits of 5,000,000,000, which is 705,032,704 (§20.3.2). Use `$time` (64 bits) or `$realtime` for long runs.

**What one vendor file under `` `timescale 1ns/1fs `` changes, and what it leaves alone:**

| What | After that file joins the build | Why |
|---|---|---|
| `$printtimescale($root)` | 1fs / 1fs | the global precision is the minimum over every precision (§3.14.3) |
| `1step` | 1 fs | it equals the global precision (§3.14.3) |
| default `%t` units, with no `$timeformat` call | femtoseconds | the smallest `` `timescale `` precision (Table 20-3) |
| `%t` after a `$timeformat` call | no change | the call sets the format (§20.4.3) |
| delays in a module with its own `timeunit` and `timeprecision` | no change | each element rounds to its own precision (§3.14.1) |
| what `#1step` samples in a clocking block | no change: the values from just before the current time slot | §4.4.2.1 |

### Expert: time values that cross scopes

- **Numbers carry no unit.** A time literal is converted to a number in the scope where it is written (§5.8). `time`, `realtime` and `int` variables hold plain numbers (`realtime` is the same type as `real`, §6.12). When a value crosses into a scope with another unit, such as a package task, an interface task or a class method compiled in a package, the receiver reads the number in *its* unit.
- **The 1000× bug.** A package with `timeunit 1ps` exports `task automatic wait_t(time t); #t; endtask`. A 1 ns caller writes `wait_t(5ns)`: the literal becomes 5 in the caller, and the task waits 5 ps. The Debug challenge below walks through it.

Without that call, the units come from the `` `timescale `` directives in the build (Table 20-3), which is how a log ends up printing `@ 15000` for an event at 15 ns.

### Expert: delay values that are not what they look like

**Predict what each delay becomes:** `#0.4` at 1ns/1ns; a delay that evaluates to x or z; `#(-1)`; `#2.75` at 1ns/100ps; `#2.85` at 1ns/100ps. Answer before you open the table or read on.

The bullets below give the reasoning behind those rows.

- **A delay can round to nothing.** `#0.4` in a 1ns/1ns element becomes 0 (§3.14.1). The statement runs in the same time slot, a classic "my delay did nothing" bug.
- **x, z and negative delays.** A delay expression that evaluates to x or z is treated as zero. A negative delay is reinterpreted as an unsigned number as wide as `time`, so `#(-1)` waits about 2^64 − 1 units, which is effectively forever (§9.4.1).
- **Exact halves.** The standard's own examples settle two halfway cases, 2.75 ns to 2.8 ns (§3.14.1) and 15.5 ns to 16 ns (§20.3.1), and both round up under every common tie rule. §3.14.1 states no tie rule of its own, though, and decimal delays are not exact in binary, so the last bit depends on each simulator's arithmetic. A halfway delay where the rules disagree, such as `#2.85` at 1ns/100ps (28.5 steps: 29 when halves round up, 28 when they round to even), is tool-dependent. If two simulators must agree, keep delays clear of halfway points.

### Debug challenge: the 1000× delay

A shared package was written by a team that works in picoseconds. Your bench works in nanoseconds.

```systemverilog
// compile
package util_pkg;
  timeunit 1ps; timeprecision 1ps;   // the library team's convention

  task automatic wait_t(time t);
    #t;                              // waits t units of THIS package's time unit
  endtask
endpackage

module tb_top;
  timeunit 1ns; timeprecision 1ps;

  initial begin
    $timeformat(-9, 3, " ns", 0);
    util_pkg::wait_t(5ns);           // intent: wait 5 ns
    $display("expected 5 ns, woke at %t", $realtime);
    $finish;
  end
endmodule
```

The log shows `expected 5 ns, woke at 0.005 ns`. Explain the number, then fix the package so that callers in any time unit get the delay they ask for.

<details className="my-4 rounded-xl border border-border/70 p-3">
<summary className="cursor-pointer font-semibold">Show the worked solution</summary>

**Why 0.005 ns.** The literal `5ns` is converted where it is written, in `tb_top`'s 1 ns unit: it becomes the number 5.0 (§5.8). Passing it to a `time` argument makes it the integer 5. Inside `util_pkg`, `#t` means 5 of the package's 1 ps units (§3.14). Nothing converts a number when it crosses from one scope into another.

**Fix.** Take a real number of nanoseconds and scale it inside the package, where the literal `1ns` is converted in the package's own unit (1000.0):

```systemverilog
// snippet: replaces wait_t in util_pkg
task automatic wait_ns(realtime delay_ns);
  #(delay_ns * 1ns);                 // 5.0 * 1000.0 = 5000 ps = 5 ns
endtask
```

Call it as `util_pkg::wait_ns(5);`. The log then shows `expected 5 ns, woke at 5.000 ns` (traced by hand). An alternative is a project rule that every package uses the bench's `timeunit`, but the scaled task stays correct whatever the caller's unit is.

</details>
