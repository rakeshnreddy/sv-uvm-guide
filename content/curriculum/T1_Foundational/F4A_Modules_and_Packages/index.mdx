## Quick Take

- **What it is:** The fundamental building blocks of SystemVerilog—**modules** for hierarchy and **packages** for shared definitions. A module's **ports** say who may drive what across its boundary, its **parameters** let one module definition take a different shape in each place it is used, and a package holds the types, constants and functions that the design and the testbench must agree on (IEEE 1800-2023 Clauses 23 and 26).
- **Why it matters:** The first compile errors of every new testbench (TB) come from here: a port that cannot be written, a connection whose types do not match, a name imported from two packages, a package compiled too late, or two copies of "the same" enum that refuse to be assigned to each other. One package definition is also what makes the design under test (DUT) and the bench agree on one transaction type, which every later milestone builds on.
- **The Analogy:** A module is a circuit board with labelled connectors; a package is the parts catalogue every board designer orders from. The table shows where that picture breaks.

| In the catalogue picture | In SystemVerilog |
|---|---|
| Ordering from a catalogue copies a part onto your board | Importing a package copies nothing: the name simply becomes visible, and every importer refers to the one declaration in the package (§26.3) |
| Two catalogues list the same part number | They only clash when you actually order that part, not when you open both catalogues (§26.3) |
| A catalogue holds no running hardware | A package cannot contain `always` or `initial` processes (§26.2) |

**You will be able to:**
1. Write a parameterized module with ANSI ports, and instantiate it with named, `.name` and `.*` connections and parameter overrides.
2. Explain why an `input logic` port is a net and an `output logic` port is a variable, and predict which drives of each are legal, including the multiple-driver consequence.
3. Write a package of types, constants and functions. Choose an explicit import, a wildcard import or `pkg::item`, and predict which declaration a name binds to, or why it is an error.
4. Debug compile-order errors and the "same `` `include `` in two packages makes two incompatible types" trap.
5. Trace a hierarchical name such as `tb_top.dut.q` or `$root.tb_top.dut.q` to the object it names, and justify why reusable code connects through ports instead.

A few words first. A **module definition** is the code between `module` and `endmodule`. An **instance** is one copy of that definition placed inside another module, with its own name and its own signals; the same definition can be instantiated many times. **Compiling** reads the source files and checks the syntax and the names; **elaboration** then builds the instance tree from the top module down, applies parameter values and makes the port connections, before simulation time 0 (§3.12). ### Modules and ports: who may drive what

A **module** is a named design element with a header and a body (§23.2). The header lists its **ports**, the signals that cross its boundary, each with a **direction** (`input`, `output`, `inout` or `ref`). This course writes headers in **ANSI style**, where each port's direction, kind and type are declared in the port list itself (§23.2.2.2). The older **non-ANSI style** lists only port names in the header and declares them in the body (§23.2.2.1); you will meet it in legacy RTL, and a module must use one style or the other, never both.

```systemverilog
// snippet: an ANSI header with a parameter port list
module counter #(parameter int WIDTH = 4) (
  input  logic             clk,
  input  logic [WIDTH-1:0] din,
  output logic [WIDTH-1:0] q
);
```

Every port also has a **port kind**: it is either a **net** (a wire-like object that continuously takes the resolved value of all its drivers) or a **variable** (an object that holds the last value written to it). You met both in [F2A](/curriculum/T1_Foundational/F2A_Core_Data_Types/index). The keyword `logic` is a *data type*, not a kind, so `input logic` does not say "variable". When you omit the kind, §23.2.2.3 decides it:

| ANSI declaration | Port kind | What it means (§23.2.2.3) |
|---|---|---|
| `input logic a` | net | same as `input wire logic a`: inputs default to a net of the default net type |
| `input var logic a` | variable | `var` asks for a variable explicitly |
| `output logic y` | variable | an output with an explicit data type defaults to a variable |
| `output y`, `output [3:0] y` | net | an output with no data type, or only a range or `signed`, is `output wire logic ...` |
| `inout wire [7:0] d` | net | an `inout` can never be a variable (§23.3.3.2) |
| `ref logic [7:0] m` | variable | a `ref` port is always a variable, shared with the connected variable |

The **default net type** in the first row is the net kind used when none is written: `wire`, unless a `` `default_nettype `` directive changes it (§22.8).

The kind decides who may write the port, because nets and variables obey different rules (§6.5):

- **A net cannot be assigned procedurally.** It is written only by continuous assignments, primitive outputs and ports, and its value is the resolution of all of them.
- **A variable is written either by procedural statements (any number of them; the last write wins) or by exactly one continuous assignment or one port**, never a mix.
- **An input port that is a variable cannot be assigned inside the module at all** (§23.3.3.2), and the outside connection is an implied continuous assignment.
- **For an output port, the parent's signal decides.** A parent *variable* connected to an instance's output port takes no other driver: no procedural write and no `assign` in the parent. A parent *net* connected to an output port may take more drivers, and they resolve. This holds whether the port itself is a variable or a net (§6.5, §23.3.3.2, §23.3.3.3).

**The two mistakes everyone makes:**

1. *"`input logic d` is a variable, so I can write `d <= 1'b0;` inside the module."* It is a net, so a procedural write is a compile error (§6.5). `logic` names the value set (0, 1, x, z), not the kind.
2. *"Something else in the parent can also drive the signal connected to my `output logic q`, and the simulator will resolve the drivers."* Only nets resolve, and the signal that collects the drivers is the parent's, not the port. If the parent connects `q` to a variable (`logic [7:0] q8;`), a parent `assign` to `q8` is a compile error, not an `x`. Only if the parent declares the signal as a net (`wire [7:0] q8;`) are extra drivers permitted, and then they resolve (§23.3.3.2). Inside the module, a variable written by an `always_ff` may not be written by any other process either (§9.2.2.4).

What the model showed, mapped to ports:
- **`wire y` with procedural writers does not compile.** Replace `y` with an `input logic` port: inside the module the port is a net, so `always_ff ... d <= ...` is rejected for the same reason (§6.5).
- **`logic y` with two `assign` statements does not compile.** A variable takes one continuous driver. Connecting a variable to an instance's output port implies a continuous assignment (§23.3.3.2), so one more `assign` in the parent is the second driver the rule forbids (§6.5). The pattern **assign + always** fails for the same reason: a parent may not write that variable procedurally either.
- **Two `assign` statements on `wire y` compile and resolve.** That is the one case where several drivers are legal: the signal that collects the drivers is a *net*, as on a tri-state bus. For ports, that means the parent's signal is a net; the output port itself may be a variable or a net (§23.3.3.2, §23.3.3.3).

**Unconnected and default inputs.** An input that is a net and left unconnected floats at `'z`; an input that is a variable keeps its type's default initial value (§23.3.3.2, §23.3.3.3). In ANSI style an input may declare a default, `input logic en = 1'b1`, which is a constant evaluated in the declaring module and used only when the instance omits the port (§23.2.2.4).

**Inheritance in the port list.** A later ANSI port that gives no direction, kind or type inherits all three from the previous port; one that gives only a type inherits the direction, and its kind is worked out again by the table above (§23.2.2.3, examples mh14 to mh21). So `input logic [7:0] a, b` declares two 8-bit input nets.

| Port list | What the later port gets | Why (§23.2.2.3) |
|---|---|---|
| `input logic [7:0] a, b` | `b`: input net, 8 bits, the same as `a` | it gives nothing, so it inherits direction, kind and type |
| `input var integer x, wire y` | `y`: `input wire logic` | direction inherited; it gives a kind, and the data type defaults to `logic` (mh17) |
| `output signed [5:0] x, integer y` | `x`: `output wire logic signed [5:0]`; `y`: `output var integer` | `y` gives a type, so only the direction is inherited and its kind is worked out again (mh19) |

**Debugging ports.**

| Symptom | Cause | Fix |
|---|---|---|
| the compiler rejects an assignment inside the module and names the port | the port is a net (an `input` with no kind) or an input variable | compute into an internal signal instead; inputs are read-only by design |
| "multiple drivers" or "illegal assignment" on a signal in the parent | the parent's signal is a variable, it is connected to an output port, and the parent also assigns it | give the parent's assignment its own signal, or declare the parent's signal as a net (`wire`) if several drivers are really intended |

### Parameters: one module, many shapes

A **parameter** is a constant that is fixed at elaboration and can be given a different value for each instance (§6.20.2, §23.10). It is how one `counter` definition becomes a 4-bit counter in one place and an 8-bit counter in another.

| Form | Example | Who can change it |
|---|---|---|
| value parameter in the parameter port list | `#(parameter int WIDTH = 4)` | each instance, by name or by order (§23.10.2) |
| local parameter | `localparam int MAX = (1 << WIDTH) - 1;` | nobody directly; it follows the parameters it is computed from (§6.20.4) |

**Overrides.** Override by name, `counter #(.WIDTH(8)) dut (...)`, or by position, `counter #(8) dut (...)`. One instance uses one style only: the two "shall not be mixed" (§23.10.2). Prefer names: positional overrides silently change meaning when someone reorders the parameter list. Give value parameters a type (`parameter int WIDTH`): an untyped parameter takes the type and range of whatever value overrides it (§23.10).

### Instances and connections: ordered, named, `.name` and `.*`

An **instantiation** creates one instance and connects its ports: `module_name #(overrides) instance_name (connections);` (§23.3.2). Four connection styles exist:

| Style | Example | Rule |
|---|---|---|
| ordered list | `counter #(8) dut (clk, rst_n, op, din, q);` | matches by position, so it breaks silently when ports are reordered (§23.3.2.1) |
| named | `.din(din_bus)` | port name and expression; the expression is sized and converted like an assignment (§23.3.2.2, §23.3.3.8) |
| implicit named | `.din` | means `.din(din)`, but the names must exist and the types must be **equivalent**; no implicit net is created (§23.3.2.3) |
| wildcard | `.*` | an implicit `.name` for every port that has a same-named signal of equivalent type; mix named connections to override (§23.3.2.4) |

**Equivalent** types have the same structure: for vectors, the same total number of bits, both 2-state or both 4-state, and the same signedness (§6.22.2).

With `.din`, a 4-bit `din` in the parent and an 8-bit port is a compile error, where `.din(din)` would compile and zero-extend.

| Connection | Result | Rule |
|---|---|---|
| `.din(din)` | compiles; `din` is zero-extended, sized like an assignment | §23.3.2.2, §23.3.3.8 |
| `.din` | error: the types are not equivalent | §23.3.2.3, §6.22.2 |
| `.*` | error: it is an implicit `.din` for this port | §23.3.2.4, §6.22.2 |

This is the same case as Break-it step 2 in Make It Work.

</details>

**`.name` versus `.*` when a name is missing.** `.name` is an error if no signal of that name exists, even when the port has a default. `.*` uses the port's default value instead, and an error follows only if there is no default (§23.3.2.3, §23.3.2.4). To leave a port unconnected on purpose, write `.name()`.

**When a port gets no signal, at a glance:**

| Connection | Port has a default | Port has no default |
|---|---|---|
| named list, port left out of it | default used (§23.2.2.4) | unconnected (§23.3.2.2) |
| `.name()` | unconnected; the default is not used (§23.3.2.2) | unconnected (§23.3.2.2) |
| `.name`, and no signal of that name | error, even with a default (§23.3.2.3) | error (§23.3.2.3) |
| `.*`, and no signal of that name | default used (§23.3.2.4) | error (§23.3.2.3, §23.3.2.4) |

An input left unconnected is `'z` if it is a net and its type's default initial value if it is a variable (§23.3.3.2, §23.3.3.3).

**Traced example: what `counter #(.WIDTH(8)) dut (.*);` connects in `tb_top`.**

| Port of `counter` | Signal in `tb_top` | Connected? |
|---|---|---|
| `input logic clk` | `logic clk` | yes, same name, equivalent type |
| `input logic rst_n` | `logic rst_n` | yes |
| `input op_e op` | `op_e op` (the same `cnt_pkg::op_e`) | yes: a typedef from a package matches itself in every importer (§6.22.1) |
| `input logic [7:0] din` | `logic [7:0] din` | yes |
| `output logic [7:0] q` | `logic [7:0] q` | yes; `tb_top` must not assign `q` itself (§23.3.3.2) |

**Pitfall.** `.*` connects *any* same-named signal. If the parent happens to have a `valid` that means something else, `.*` wires it in without a message. Use `.*` where the bench declares signals for exactly this DUT, and named connections at integration levels.

### Hierarchy: instance names, hierarchical paths and `$root`

Elaboration builds a tree. A **top-level module** is one that no other module instantiates; it becomes an instance with its own name (§23.3.1). Every instance, task, function, named block and generate block inside it opens a new branch, and any object can be named by its **hierarchical path**, the instance names joined by dots (§23.6).

**`$root`** is the root of the instance tree. A path such as `A.B.C` is first looked up from the current scope, and a local match wins; `$root.A.B.C` forces the search to start at the top (§23.3.1).

**Scope rules.** Modules, interfaces, programs, checkers, packages, classes, tasks, functions, `begin`-`end` and `fork`-`join` blocks and generate blocks each open a **scope**, a region in which a name can be declared once (§23.9). A name used without a path is looked up in the current scope, then in the enclosing ones; for a variable the search stops at the module boundary (§23.9). Objects inside an `automatic` task or function have no hierarchical name (§23.6).

**Why reusable code avoids hierarchical references.** A checker that reads `tb_top.dut.q` only works in a bench whose top is called `tb_top` and whose instance is called `dut`. Move it into a chip-level bench and it fails to elaborate. Ports (and, from [F4B](/curriculum/T1_Foundational/F4B_Interfaces_and_Modports/index), interfaces) carry the same signal without baking the path into the code; `bind` ([I-SV-4C](/curriculum/T2_Intermediate/I-SV-4C_Checkers/index)) attaches a checker to a design without editing it. Hierarchical paths stay useful in a bench's top module and in debug code, where the path is known.

### Packages: one definition shared by design and bench

A **package** is a named scope, declared outside every module, that holds declarations for other scopes to use (§26.2). It is the single place where a type such as `op_e` is defined, so the DUT's ports and the bench's variables have *the same* type.

```systemverilog
// snippet: a package of types, constants and functions
package cnt_pkg;
  parameter int W = 8;                     // in a package this is a localparam (§6.20.4)
  typedef enum logic [1:0] {OP_HOLD, OP_INC, OP_LOAD} op_e;

  function automatic logic [W-1:0] next_q(input logic [W-1:0] q, input op_e op);
    return (op == OP_INC) ? q + 1'b1 : q;
  endfunction
endpackage
```

**What a package may hold, and what it may not** (§26.2):

| In a package? | Item | Note |
|---|---|---|
| ✓ yes | parameters, types, nets, variables | |
| ✓ yes | tasks, functions | |
| ✓ yes | classes | from [I-SV-1](/curriculum/T2_Intermediate/I-SV-1_OOP/index), every UVM component lives in one |
| ✓ yes | sequences, properties, checkers and covergroups | |
| ✕ no | processes: no `initial`, `always` or continuous `assign` | A package describes; it does not run (§26.2). The one exception is a process inside a checker declared in the package |
| ✕ no | references to the compilation-unit scope (`$unit`, below) | §26.2 |
| ✕ no | hierarchical references to anything outside the package and what it imports | §26.2 |

**Two practitioner traps:**
- **A package variable is one shared global.** `int count;` in a package is a single object that every importer reads and writes, and it is initialized before any `initial` or `always` procedure starts (§26.2). That is occasionally useful and often a hidden coupling between tests.
- **Package subroutines are static by default** (§6.21): a static function's arguments and locals are shared by every caller, so two processes calling it at once can overwrite each other. Declare package tasks and functions `automatic`, or the whole package `package automatic cnt_pkg;`.

Here is the second trap with a task, where it is easy to see. Package tasks are static by default, so all callers share one `id` (§13.3.1):

```systemverilog
// snippet: a static package task; initial send(1); and initial #1 send(2); both call it
package log_pkg;
  task send(input int id);          // static by default: one shared id
    #5 $display("id=%0d", id);
  endtask
endpackage
```

### Using a package: `pkg::item`, explicit import, wildcard import

There are three ways to reach a package item, plus one placement:

| Form | Example | Effect |
|---|---|---|
| scope resolution | `cnt_pkg::op_e op;` | names the item directly, in any scope, with no import (§26.3, Table 26-1) |
| explicit import | `import cnt_pkg::op_e;` | makes exactly that name visible in this scope (§26.3) |
| wildcard import | `import cnt_pkg::*;` | makes every name of the package a *candidate*, imported only if a reference needs it (§26.3) |
| header import | `module counter import cnt_pkg::*; #(...) (...);` | an import in the module header, visible in the parameter and port declarations too (§26.4) |

Importing copies nothing: "Importing does not copy the declaration of that identifier into the importing scope" (§26.3). Every importer refers to the one `op_e` in `cnt_pkg`.

**Traced example.** Two packages define the same names; `p::x` is 1 and `q::x` is 2:

```systemverilog
// snippet: the packages used in the traced table and the drill
package p; int x = 1; typedef int        data_t; endpackage
package q; int x = 2; typedef logic [7:0] data_t; endpackage
```

| Code in module `m` (in this order) | What happens | Rule |
|---|---|---|
| `import p::*; import q::*;` | legal: both packages offer `x` and `data_t`, but nothing is imported yet | candidates only (§26.3) |
| `data_t d;` | **error**: the reference matches candidates from two wildcard imports | §26.3 |
| replace with `import q::data_t;` before `data_t d;` | legal: the explicit import is locally visible and wins over every wildcard candidate | step 1 (§26.3, Table 26-1) |
| `initial $display(x);` in a module with only `import p::*;` | prints 1; `p::x` is now imported into `m` | step 2 |
| `int x = 5;` *after* that `$display(x)` | **error**: `x` already means `p::x` in this scope | "any later locally visible declaration of the same name in that scope shall be illegal" (§26.3) |
| `int x = 5;` *before* any reference | legal, and a later `$display(x)` prints 5: the local declaration wins | step 1 |

**The misconception to drop.** "Importing two packages that define the same name is always an error." It is an error only when a reference resolves to that name through two wildcard imports. Explicit imports and local declarations win over wildcard candidates. The one import that is always an error is an *explicit* import of a name that is also declared in the same scope (before or after the import), or already explicitly imported from another package (§26.3).

**Enum literals are separate names.** `import pkg::state_e;` imports the type name only, not its literals: to write `IDLE`, also import `pkg::IDLE` or write `pkg::IDLE` (§26.3, the `teeth_t` example). A wildcard import has no such gap, which is one reason benches use it for type packages.

| The scope has | `state_e` usable? | `IDLE` usable? |
|---|---|---|
| `import pkg::state_e;` | yes | no: also import `pkg::IDLE`, or write `pkg::IDLE` |
| `import pkg::state_e, pkg::IDLE;` | yes | yes |
| `import pkg::*;` | yes, imported when referenced | yes, imported when referenced |

**Imports are not transitive.** `tb_pkg` imports `cnt_pkg`, but a module that imports `tb_pkg` does not see `op_e` through it (§26.6). That answers prediction 1: `tb_top` imports both packages. A package can re-export with `export cnt_pkg::*;`, covered in Push Further.

**Where to put imports.** Inside the module, interface or package that needs them, or in the module header. Not at the top of a file outside every module: there the import lands in the compilation-unit scope and leaks into every later module of that compilation unit (§3.12.1). An `import` written directly inside a class is illegal (§26.3); a class sees the imports of the package or module around it.

**The `std` package.** Every compilation unit implicitly wildcard-imports the built-in package `std`, which holds `semaphore`, `mailbox`, `process`, `randomize` and the weak-reference class (§26.7, Annex G). A user declaration with the same name hides it, and `std::` always reaches the built-in one, for example `std::process`.

### `include` versus `import`, compilation units and compile order

These two look alike and are not:

| | `` `include "file.svh" `` | `import pkg::...;` |
|---|---|---|
| What it is | a compiler directive | a language declaration |
| What it does | pastes the entire text of the file at that point, as if you had typed it there | makes names visible |
| Where the declarations live | the pasted declarations belong to whatever scope the directive sits in | in the package; every importer refers to the one declaration |
| Copies a declaration? | yes, one copy per `` `include `` | no: it pastes and copies nothing |
| Clause | §22.4 | §26.3 |

Testbenches use both together. Each class lives in its own `.svh` file, and the files are `` `include ``d *inside exactly one* package, which everyone then imports. The UVM library itself is built this way: `uvm_pkg` is a package whose body is mainly a list of `` `include `` lines (uvm-core 2020.3.1, `src/uvm_pkg.sv`).

**The two-types trap.** Include the same typedef into two packages and you get two declarations, and therefore two types: a typedef matches only within the scope where it is declared (§6.22.1).

What fails depends on the type: enum variables reject a literal of another enum type (§6.19.3); class handles of two "identical" classes are type incompatible with each other (§6.22.5), so a `uvm_config_db` lookup or a `$cast` between them fails; packed structs, by contrast, are *equivalent* to any packed type of the same total width, state and signedness (§6.22.2), so they assign silently. **The fix** is one owner: put `mode_e` in one package (`mode_pkg`), and let `pkg_a` and `pkg_b` import it.

**Compilation units.** A **compilation unit** is a set of source files compiled together; its **compilation-unit scope** holds every declaration outside all modules, packages and other design elements, and `$unit` names that scope (§3.12.1). Which files form one unit is tool-specific, but every tool must offer both modes:

| Same four files, compiled as | A typedef written outside every module in `a.sv` | `` `default_nettype `` or `` `define `` set in `a.sv` | A package used before its file is compiled |
|---|---|---|---|
| one unit (all files on one command line) | visible in every later file of the unit | applies to all later files on the command line | error |
| one unit per file | visible only in `a.sv` | applies only in `a.sv` | error |

The table explains why "it compiles on my machine" fails elsewhere: code that relies on the compilation-unit scope, or on a directive leaking from an earlier file, changes meaning when the file order or the compilation mode changes (§3.12.1). Packages do not have this problem: they are visible in every compilation unit (§3.12.1), provided they are compiled first.

**`` `default_nettype none `` as a practice.** Without it, a misspelt signal name in a port connection silently creates a new one-bit **implicit net** (§6.10). With `` `default_nettype none `` every net must be declared, and a typo becomes an error (§22.8). The directive belongs to [I-SV-6](/curriculum/T2_Intermediate/I-SV-6_Compiler_Directives_and_Generates/index), but it has one port consequence you should know now: an `input logic` port is "a net of default net type" (§23.2.2.3), and under `none` there is no default net type, so tools differ on what they do with it (tool-dependent). Write `input wire logic` or `input var logic` in files compiled under `none`, and restore the default at the end of the file with `` `default_nettype wire ``.

### Recap

- An `input` with no kind is a **net**: read it, never assign it procedurally. An `output logic` is a **variable**. A parent variable connected to an output port takes no other driver; a parent net may take more, and they resolve.
- Parameters shape each instance: override by name, never mix name and position; body parameters become local when a parameter port list exists.
- `.name` and `.*` need same-named signals of **equivalent** types; `.*` silently connects every name that matches.
- Hierarchical paths (`tb_top.dut.q`, `$root...`) are fine in a top module and debug code, not in reusable components.
- A package is one shared definition. `pkg::item` needs no import; explicit imports beat wildcard candidates; a wildcard clash is an error only when the name is used; imports are not transitive.
- `` `include `` copies text, `import` shares a declaration. Include a type file into one package only, and compile packages first.

### Worked example: a counter bench with a shared package

This is the bench from the picture, in one file you can run as it is. It continues the [F2E](/curriculum/T1_Foundational/F2E_First_Self_Checking_Testbench/index) bench pattern (reset, drive, predict, compare with `!==`, one verdict line) and adds what this lesson teaches: two packages, a header import, a parameter override and a `.*` instantiation. The `// compile` tag marks a complete compile unit.

```systemverilog
// compile
// counter_tb.sv: two packages, a parameterized DUT and its self-checking bench.
// Order in the file: cnt_pkg, tb_pkg, counter, tb_top. A package must be
// compiled before any scope that imports it (IEEE 1800-2023 26.3).

package cnt_pkg;                         // shared by the design and the bench
  timeunit 1ns; timeprecision 1ps;       // every design element declares a unit
  // logic base type: a 4-state enum is a legal type for an input port, a net
  typedef enum logic [1:0] {OP_HOLD, OP_INC, OP_LOAD} op_e;
endpackage

package tb_pkg;                          // bench only: the DUT never imports it
  timeunit 1ns; timeprecision 1ps;
  import cnt_pkg::*;

  typedef struct packed {
    op_e        op;
    logic [7:0] din;
  } cmd_t;

  // Reference model: the value q must hold one clock after cmd c is applied.
  function automatic logic [7:0] predict(input logic [7:0] q, input cmd_t c);
    case (c.op)
      OP_INC:  return q + 8'd1;          // 8-bit result: 255 + 1 wraps to 0
      OP_LOAD: return c.din;
      default: return q;                 // OP_HOLD
    endcase
  endfunction
endpackage

module counter
  import cnt_pkg::*;                     // header import: op_e usable in ports
  #(parameter int WIDTH = 4)
  (
    input  logic             clk,        // input, no kind given: a net
    input  logic             rst_n,
    input  op_e              op,         // also a net, of type op_e
    input  logic [WIDTH-1:0] din,
    output logic [WIDTH-1:0] q           // output with a data type: a variable
  );
  timeunit 1ns; timeprecision 1ps;

  always_ff @(posedge clk or negedge rst_n)
    if (!rst_n)             q <= '0;
    else if (op == OP_INC)  q <= q + 1'b1;
    else if (op == OP_LOAD) q <= din;
endmodule

module tb_top;
  timeunit 1ns; timeprecision 1ps;
  import cnt_pkg::*;                     // tb_pkg does not re-export cnt_pkg
  import tb_pkg::*;

  logic       clk = 1'b0;
  logic       rst_n;
  op_e        op;
  logic [7:0] din;
  logic [7:0] q;                         // written only by dut.q (23.3.3.2)
  logic [7:0] model_q;                   // the bench's own expected count
  int         n_pass = 0;
  int         n_fail = 0;

  always #5 clk = ~clk;                  // rising edges at 5, 15, 25 ns ...

  // Named override; .* connects clk, rst_n, op, din and q, because each has a
  // same-named signal of an equivalent type in this scope (23.3.2.4).
  counter #(.WIDTH(8)) dut (.*);

  // Drive at a falling edge, half a cycle before the DUT samples (the F2E
  // opposite-edge style), then check q at the next falling edge.
  task automatic apply(input op_e o, input logic [7:0] d);
    cmd_t c;
    c       = '{op: o, din: d};
    model_q = predict(model_q, c);
    op      = o;
    din     = d;
    @(negedge clk);                      // the rising edge in between updated q
    if (q !== model_q) begin
      n_fail++;
      $error("%s din=%0d: q=%0d, expected %0d", o.name(), d, q, model_q);
    end else begin
      n_pass++;
    end
  endtask

  initial begin
    rst_n   = 1'b0;
    op      = OP_HOLD;
    din     = '0;
    model_q = '0;                        // the counter's reset value
    repeat (2) @(negedge clk);           // falling edges at 10 and 20 ns
    rst_n = 1'b1;
    apply(OP_LOAD, 8'd254);
    apply(OP_INC,  8'd0);
    apply(OP_INC,  8'd0);                // 255 + 1 wraps to 0 in 8 bits
    apply(OP_HOLD, 8'd7);                // din is ignored on HOLD
    apply(OP_INC,  8'd0);
    $display("PASS=%0d FAIL=%0d", n_pass, n_fail);
    $finish;
  end
endmodule
```

- `tb_top` imports **both** packages. Delete `import cnt_pkg::*;` and `op_e`, `OP_HOLD` and the other literals become undeclared, because imports are not transitive (§26.6).

### How to structure a new bench

1. **Find what both sides share** (opcodes, transaction fields, widths) and put it in one *type package*. Give enums a 4-state base (`logic [1:0]`) if they cross input ports.
2. **Import the type package in the DUT's header** (`module dut import my_pkg::*; #(...) (...)`), so the ports can use its types.
3. **Put bench-only types and models in a *bench package*** that imports the type package. Make every package function `automatic`.
4. **In the top module, import every package you use by name.** Nothing arrives transitively.
5. **Declare one signal per DUT port, with the port's name and type**, then instantiate with `.*` (or named connections where names differ). Override parameters by name.
6. **List the files packages first, in dependency order**, then the design, then the bench.
7. **Run, then prove the bench can fail** with a deliberate DUT mutation, as in F2E.

### Debugging compile and elaboration errors

Error wording varies by tool, so this table names the error *class*.

| Symptom | Likely cause | Fix |
|---|---|---|
| A type or enum literal from a package is undeclared | the package is not imported in *this* scope (imports are not transitive), or an explicit import named the type but not its literals | import it here, or write `pkg::name` |
| "Unknown package" or the same name undeclared only when files are compiled in some orders | the package is compiled after a file that imports it | list packages first, in dependency order (§26.3) |
| A name "imported from two packages" or "ambiguous" | the reference matches wildcard candidates from two packages | add an explicit import of the one you mean, or use `pkg::name` (§26.3) |
| "Already declared" on a local declaration | an earlier reference in the same scope already imported that name from a wildcard package | move the declaration above the first use, or rename it (§26.3) |
| Illegal assignment to an input, or "procedural assignment to a net" | the port is an `input` (a net), or an input variable | compute into an internal signal; inputs are read-only |
| Multiple drivers on a variable | the parent's variable connected to an output port is also assigned, or two continuous drivers write one variable | one writer per variable; declare the signal as a net only for real multi-driver buses (§6.5, §23.3.3.2) |
| A `.*` or `.name` connection is rejected | same-named signal with a different width, signedness or 4-state/2-state kind, or a missing name | declare the signal with the port's exact type, or connect that port by name |
| An enum or class assignment fails between two types with the same name | the same `.svh` file is `` `include ``d into two packages: two types | one package owns the type; others import it (§6.22.1) |
| A hierarchical reference such as `tb_top.dut.q` cannot be resolved after a block is reused or an instance is renamed | the path is baked into the code, and the new bench has different top or instance names | pass the signal through a port or interface, or `bind` the block where the path is known (§23.6) |

**Checklist before moving on:**
- [ ] Every type shared by the DUT and the bench is declared once, in a package.
- [ ] You can say the kind (net or variable) of every port you wrote.
- [ ] Parameters are overridden by name, and no instance mixes name and position.
- [ ] No declaration or import sits outside a module or package (nothing relies on `$unit`).
- [ ] Packages come first in the compile order, in dependency order.
- [ ] The bench prints a verdict line and fails on a deliberate DUT mutation.

## Push Further

### Expert: name-resolution corner cases

- **Calls search further.** For a task or function call, the locally visible names up to the *end* of the scope are searched, so a function declared below the call is found; if the search fails in every lexical scope, it continues by upward hierarchical resolution (§26.3, §23.8.1). For every other reference, only names before the point count, and failure is an error.
- **Order matters in outer scopes too.** Only wildcard imports that lexically *precede* the reference are considered, in each scope searched. In the standard's Example 4, `f()` in a nested block binds to `p::f`, because `import p2::*` comes after the block (§26.3).
- **Imports stay inside the importing scope.** An imported name is not visible by a hierarchical reference into that scope, nor through an interface port that refers to it (§26.3). If an interface imports a package, the modules connected to it must import the package themselves.
- **`.*` is not a reference.** A `.*` connection "does not create a sufficient reference for a wildcard import" (§23.3.2.4): a port named like a package item is not connected to it. A `.name` connection to a name that is only a wildcard candidate *is* a reference, and imports it.
- **Table 26-1 in one line:** a local declaration (made before any binding reference) beats every wildcard candidate; an explicit import of a name declared locally, or explicitly imported from another package, is an error; an explicit import after a reference that already bound the name through a wildcard import is an error (§26.3, §26.5 (Table 26-1)).

The full table, for `c` declared in package `p` (and in `q`, where a column names `q`), reads:

| Code in the scope | Scope declares its own `c` | No other `c` | Scope has `import q::c;` | Scope has `import q::*;` |
|---|---|---|---|---|
| `p::c` | OK: `p`'s `c` | OK: `p`'s `c` | OK: `p`'s `c` | OK: `p`'s `c` |
| `import p::*;` then a reference to `c` | OK: `c` is the local one | OK: `c` is `p::c` | OK: `c` is `q::c` | error at the reference, because `c` is undefined here; the imports alone are legal |
| `import p::c;` | error: the name is declared in this scope | OK: `c` is `p::c` | error: one name from two packages | OK: `c` is `p::c`, but any earlier reference to `c` makes it an error |

### Expert: type identity across scopes and packages

- **Per-instance types.** "Each instance with a user-defined type declared inside the instance creates a unique type" (§6.22). A struct typedef declared *inside* a module therefore differs in every instance; for matching across instances, classes, enums and unpacked structs must come from a package or an outer scope, and for strict matching even packed structs must (§6.22).
- **Package typedefs match everywhere.** "A typedef for an enum, struct, union, or class type declared in a package always matches itself, regardless of the scope into which the type is imported" (§6.22.1 h).
- **Anonymous types** match only objects declared in the same declaration: `struct packed {...} a, b;` gives `a` and `b` one type, and a second identical declaration gives another (§6.22.1, §6.22.2).
- **Equivalent is weaker than matching.** Packed structs, packed unions, packed arrays and integral types of the same total width, state and signedness are *equivalent* (§6.22.2 c), so a two-types trap with packed structs compiles and silently connects fields in whatever order each copy declares them. Enums are strongly typed (§6.19.3), and class handles of different class types are incompatible (§6.22.5), so those fail loudly.
- **UVM consequence.** If `my_cfg.svh` is included into two agent packages, `uvm_config_db#(pkg_a::my_cfg)::set` and `uvm_config_db#(pkg_b::my_cfg)::get` use two different specializations, and the `get` returns 0 although the code "looks identical". The fix is the one-owner rule. ([I-UVM-2C](/curriculum/T2_Intermediate/I-UVM-2C_Configuration_and_Resources/index) teaches the configuration database.)

**The same rules as one table:** what you get when you compare the two sides, by where the typedef is declared.

| Typedef of | In one package, imported everywhere | Inside a module, across two instances | One `.svh` included into two packages |
|---|---|---|---|
| enum | matching (§6.22.1 h) | not equivalent (§6.22) | not equivalent: an assignment needs a cast (§6.19.3) |
| class | matching (§6.22.1 h) | type incompatible (§6.22, §6.22.5) | type incompatible (§6.22.5) |
| unpacked struct | matching (§6.22.1 h) | not equivalent (§6.22) | not equivalent (§6.22.2) |
| packed struct | matching (§6.22.1 h) | equivalent if width, state and signedness agree, but not matching (§6.22, §6.22.2 c) | equivalent, not matching: it assigns silently (§6.22.2 c) |

### Expert: compilation units, `$unit` and include guards

- **The compilation-unit scope is local to its unit.** Its items "cannot be accessed by name from outside the compilation unit", and which files form a unit is tool-specific; tools must support both all-files-one-unit and one-unit-per-file (§3.12.1).
- **Directives do not cross units.** "Compiler directives from one separately compiled unit shall not affect other compilation units" (§3.12.1). A `` `define `` or `` `default_nettype `` that worked in single-unit mode can vanish in per-file mode.
- **Include guards change the symptom of the two-types trap.** With an `` `ifndef MODE_DEFS_SVH `` guard and both packages in one compilation unit, the second `` `include `` is skipped, so `pkg_b` has *no* `mode_e` and fails with an undeclared type. In per-file mode each package gets its own copy and you get two types. The cure in both modes is the same: one package owns the type. (`uvm_pkg.sv` uses exactly this guard, `` `ifndef UVM_PKG_SV ``, around the whole package; uvm-core 2020.3.1.)

  | `mode_defs.svh` included into `pkg_a` and `pkg_b` | No guard | With an `` `ifndef MODE_DEFS_SVH `` guard |
  |---|---|---|
  | one compilation unit | two `mode_e` types | second `` `include `` skipped: `pkg_b` has an undeclared `mode_e` |
  | one unit per file | two `mode_e` types | two `mode_e` types: the guard's `` `define `` does not cross units (§3.12.1) |

- **Packages are walled off from `$unit`.** A package "shall not refer to items defined in the compilation-unit scope" (§26.2), and its compile-before-use rule (§26.3) means two packages that import each other cannot both be compiled first; a logical consequence of the rule, not a sentence in the standard. Break such a cycle by moving the shared items into a third package.

### Expert: `export`, umbrella packages and the `std` package

- **Imports into a package are private by default.** "Declarations imported into a package are not visible by way of subsequent imports of that package" (§26.6).
- **`export pkg::*;`** re-exports every name *actually imported* from `pkg` into the exporting package. A name that was only a candidate (never referenced) is not exported (§26.6, example `p3`).
- **`export pkg::name;`** counts as a reference: it imports the name, so a later local declaration of that name in the package is an error (§26.6, example `p6`).
- **`export *::*;`** exports every declaration *actually imported* into the package, from any package (§26.6, example `p8`). Wildcard candidates the package never references are not imported, so they are not exported either (example `p3`). An *umbrella package* that only says `import apb_pkg::*; import axi_pkg::*; export *::*;` therefore exports nothing it does not reference itself. To build one that lets a test write one import instead of five, import the names explicitly in the umbrella (each explicit import is an actual import), or simply import the agent packages directly where they are used. Tools have differed on this corner (tool-dependent), so test an umbrella package on every simulator you use.

  | Form in the exporting package | What it makes available | A reference? | §26.6 example |
  |---|---|---|---|
  | `export pkg::*;` | names actually imported from `pkg`; unreferenced candidates stay hidden | no | `p3`: `p1::x` passes on, `p1::y` does not |
  | `export pkg::name;` | that name; an error if it is not a candidate for import | yes: a later local declaration of it is an error | `p6` |
  | `export *::*;` | every declaration actually imported, from any package | no | `p8`: both explicit imports pass on |
  | `import a::*; import b::*; export *::*;` and nothing else | nothing: no name was actually imported | no | follows from `p3` |

- **Multiple paths do not conflict.** Importing the same declaration through two export paths is legal, because both are the original declaration (§26.6).
- **`std` is always there.** It is wildcard-imported into every compilation-unit scope, user declarations hide its names, and `std::` reaches them unambiguously (§26.7, Annex G). A bench class named `process` hides `std::process` in its scope; write `std::process::self()` to get the built-in one.

### Expert: parameter and port corner cases

- **Local parameters in the header.** A parameter port list may contain `localparam` entries; every declaration after a `localparam` keyword, up to the next `parameter` keyword, is local (§6.20.4).
- **Untyped and ranged parameters.** An untyped value parameter takes the type and range of its final override; a ranged untyped parameter is unsigned and the override is converted to its range (§23.10). Typed parameters avoid both surprises.
- **Restricted type parameters.** `parameter type enum T = ...` (also `struct`, `union`, `class`, `interface class`) makes it an error to override `T` with a type of another kind (§6.20.3).
- **`input var` for single-driver inputs.** `input var logic a` makes the input a variable, so nothing inside the module can drive it, not even a continuous assignment (§23.2.2.3, §23.3.3.2).
- **Port coercion.** A net input that is driven inside the module "may be coerced to inout. If not coerced to inout, a warning shall be issued" (§23.3.3.1). Coercion never makes a *procedural* write to a net legal (§6.5).
- **2-state input types (tool-dependent).** The default rule makes `input int n` "a net of default net type" of type `int`, but §6.7.1 allows only 4-state data types on built-in nets. Tools differ in how they handle this. Write `input var int n` to say what you mean portably.
- **`default_nettype none` and inputs (tool-dependent).** As above, `input logic a` under `none` has no default net type to use; write `input wire logic a` or `input var logic a` (§22.8, §23.2.2.3).

**Five ways to write an input, side by side:**

| Declaration | Kind | Procedural write inside | `assign` inside | Under `` `default_nettype none `` |
|---|---|---|---|---|
| `input logic a` | net of the default net type | error (§6.5) | coerced to `inout`, or a warning (§23.3.3.1) | tool-dependent |
| `input wire logic a` | net | error (§6.5) | coerced to `inout`, or a warning (§23.3.3.1) | fine |
| `input var logic a` | variable | illegal (§23.3.3.2) | illegal (§23.3.3.2) | fine |
| `input int n` | a net of type `int`, which built-in nets do not allow (§6.7.1) | tool-dependent | tool-dependent | tool-dependent |
| `input var int n` | variable | illegal (§23.3.3.2) | illegal (§23.3.3.2) | fine |

  ]}
/>

- **Layering.** From the bottom of the picture up: shared types and constants, then one package per agent (classes `` `include ``d, one class per file), then an environment package, then a test package. Each layer imports only the layers below it, which also prevents import cycles.
- **Recompile fan-out.** Everything that imports a package depends on it. A widely imported "everything" package forces most of the bench to recompile when one constant changes; separately compiled, layered packages keep incremental builds small (tool-dependent).
- **Globals.** Package variables are shared global state across all tests and all instances; prefer configuration objects passed down the hierarchy (I-UVM-2C) for anything a test may change.
- **Naming.** Prefix package items (`apb_item`, `APB_ADDR_W`) so that wildcard imports of several agent packages rarely collide, and use explicit imports or `pkg::` in shared code where they still might.

### Kata (guided): refactor the F2E bench into a package

**Starting point:** the complete bench from [F2E](/curriculum/T1_Foundational/F2E_First_Self_Checking_Testbench/index). Its `tb_top` declares `localparam int W = 8`, the struct `exp_t` and the function `model_add()` locally, and connects `adder_reg` by name.

**Steps:**
1. Create `package adder_tb_pkg;` above `tb_top`, with `timeunit 1ns; timeprecision 1ps;`. Move `W`, `exp_t` and `model_add()` into it.
2. In `tb_top`, delete those three declarations and add `import adder_tb_pkg::*;`.
3. Replace the long named connection list with `.*`, keeping the parameter overrides `#(.W(W), .BUG(0))`.
4. Compile and run. The verdict must still be `PASS=14 FAIL=0`, and `.BUG(1)` must still fail.
5. Reflect: in the package you wrote `parameter int W = 8` or `localparam int W = 8`. Which can a test override, and why? What would happen if `tb_top` kept its own `localparam int W = 8` *and* imported the package?

**Acceptance:** the same verdicts as before the refactor, no declaration outside a module or package, and the package compiled before `tb_top`.

<details className="my-4 rounded-xl border border-border/70 p-3">
<summary className="cursor-pointer font-semibold">Show the worked solution</summary>

```systemverilog
// snippet: the new package, placed before tb_top
package adder_tb_pkg;
  timeunit 1ns; timeprecision 1ps;

  parameter int W = 8;                   // a localparam: no test can override it

  typedef struct {
    logic [W-1:0] a, b;                  // the inputs, so a failure can name them
    logic [W:0]   sum;                   // the expected result
  } exp_t;

  function automatic logic [W:0] model_add(input logic [W-1:0] op_a,
                                           input logic [W-1:0] op_b);
    return {1'b0, op_a} + {1'b0, op_b};  // widen first, so the carry is kept
  endfunction
endpackage
```

```systemverilog
// snippet: the changed lines in tb_top
module tb_top;
  timeunit 1ns; timeprecision 1ps;
  import adder_tb_pkg::*;               // W, exp_t and model_add() come from here

  // ... signals clk, rst_n, in_valid, a, b, out_valid, sum as before ...

  adder_reg #(.W(W), .BUG(0)) dut (.*); // every port has a same-named signal
```

Why it works: every DUT port (`clk`, `rst_n`, `in_valid`, `a`, `b`, `out_valid`, `sum`) has a signal of the same name and an equivalent type in `tb_top`, so `.*` connects all seven (§23.3.2.4). `W` reaches the signal declarations and the override through the wildcard import.

Reflection:
- In a package, `parameter` and `localparam` mean the same thing: a constant no one can override (§6.20.4). A width that tests must vary belongs in the DUT's parameter port list and the bench's top, not in a package.
- If `tb_top` declares its own `W` *before* any use of `W`, the local declaration wins and the package's `W` is never imported. If some use of `W` comes first, that use imports `adder_tb_pkg::W`, and the later local declaration is a compile error (§26.3). Either way, keep one owner.

</details>

```systemverilog

module pipe_reg #(parameter type T = logic [7:0]) (

  input  T     d,                  // an input: a net of type T, so T must be 4-state

//   logic [7:0] d8, q8;

//   pipe_reg #(.T(cmd_t))   u_cmd  (.clk, .d(dc), .q(qc));
```
