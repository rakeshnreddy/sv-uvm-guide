## Quick Take
- **What it is:** Procedural constructs are SystemVerilog’s sequential code paths—`initial`, `always`, `final`, loops, and conditionals—that choreograph stimulus and checking.
- **Why it matters:** Misusing blocking vs. non-blocking assignments or mis-scoping procedural code leads to race conditions, false failures, and weeks of lost debug time.
- **The Analogy:** Picture a stage production: `initial` is the stage manager’s countdown, `always_ff` and `always_comb` are the actors following scripted cues, and flow control is the choreography keeping every move in sync.

> **Visual cue:** This page pairs simulators, code overlays, and animated timelines with the narrative so you can *see* how procedural elements run frame by frame.

## Build Your Mental Model

### Watch procedures run over simulation time

`initial` and every `always` procedure start together at time 0, in no promised order (IEEE 1800-2023 §9.2). An `initial` runs its statements once, an `always` loops forever, and a `final` runs once when simulation ends. Pick a program, predict what it prints, then step through it: watch each procedure's lane, and the region badge on every `<=` update.

<ProceduralBlocksSimulator />

What the four programs show:

- `always @(posedge clk)` sleeps between rising edges. Its `count <= count + 1` lands in the **NBA region of the same time step** as the edge, never at a later time.
- In the swap program, `$display` prints the old values because the `<=` updates have not landed yet; `$strobe` waits for the end of the time step and prints the swapped values.
- Delays inside `fork … join` all count from the moment the fork starts.
- `@(posedge ready)` waits for a *new* edge; `wait (ready)` passes at once if `ready` is already 1.

### Timeline of a Simulation Tick

SystemVerilog simulators run every timestep through distinct event regions. Internalizing this timeline eliminates the feeling that the tool is acting randomly.

| Region | What lands here | Debug cue |
| --- | --- | --- |
| **Preponed** | Value samples for concurrent assertions and clocking-block inputs (read-only) | Assertions see the values from *before* the edge. |
| **Active** | `initial`/`always` processes, blocking assignments (`=`), right side of `<=` | Watch waveform edges jump immediately. |
| **Inactive** | Processes resumed after `#0` | Rare today; a `#0` "fix" only moves a race here. |
| **NBA** | Updates from non-blocking assignments (`<=`) | Values "snap" to their new state *after* all Active code finishes. |
| **Observed** | Concurrent assertions are evaluated (on Preponed samples) | Assertion failures report on the edge, using pre-edge values. |
| **Reactive / Re-NBA** | Program-block code; clocking-block drives land in Re-NBA | Testbench drives arrive after design updates. |
| **Postponed** | `$strobe` and `$monitor` output (read-only) | Prints settled end-of-slot values. |

`final` blocks are not in this table: they run once when simulation ends (IEEE 1800-2023 §9.2.3), not in a time-slot region. F3B and F3C build this ladder step by step.

logic clk, reset_n, d_in, q_out;

// Sequential region: non-blocking keeps flip-flops in sync
always_ff @(posedge clk or negedge reset_n) begin
  if (!reset_n)
    q_out <= 1'b0;
  else
    q_out <= d_in;
end

// Combinational region: blocking to model logic equations
logic [2:0] state_next;
always_comb begin
  unique case (q_out)
    1'b0: state_next = 3'b001;
    1'b1: state_next = 3'b010;
    default: state_next = 3'b000;
  endcase
end

// Testbench stimulus using initial + fork/join_none
initial begin
  reset_n = 0;
  d_in = 0;
  #10 reset_n = 1;
  fork
    begin // drive pattern
      repeat (5) begin
        #5 d_in = $random;
      end
    end
    begin // monitor
      forever @(posedge clk) $display("time=%0t q_out=%0b", $time, q_out);
    end
  join_none
end

final begin
  $display("Simulation complete. Final state=%0b", q_out);
end
  `}

### Fork, join, and cleaning up threads

A `fork` turns each statement inside it into its own process. The join keyword decides when the parent continues: `join` waits for every child, `join_any` for the first one to finish, and `join_none` not at all (IEEE 1800-2023 §9.3.2). One rule surprises almost everyone: **spawned processes do not start until the parent blocks or finishes**, whichever join you use.

Predict when the parent continues for each join keyword, then step through the lanes. Save *fork in a loop* for last: it is the most common fork bug in real testbenches.

<ForkJoinVisualizer />

What the lanes showed:

- With `join_none`, the parent prints before its children have even started. They run at its next blocking statement (`#`, `@`, `wait`) or when it ends.
- A `for` loop has **one** loop variable. Children forked with `join_none` run after the loop ends, so they all read its final value. Declare `automatic int k = i;` inside the `fork` itself to give each child its own copy.
- `wait fork` waits for the calling process's immediate children only, not for processes those children spawned (§9.6.1).
- `disable fork` kills **every** descendant of the calling process, not just the children of the last fork (§9.6.3). A monitor forked earlier by the same process dies too.
- `disable <block_name>` uses the block's static name, so it ends that block in **every** process executing it (§9.6.2). In a task called by several threads at once, one call's cleanup kills the others' threads.

The safe cleanup idiom gives the race its own parent process, so `disable fork` has nothing else to reach:

```systemverilog
task automatic wait_for_response(int timeout_ns);
  fork begin                 // isolation wrapper: a new parent for the race
    fork
      @(rsp_seen);           // response wins…
      #(timeout_ns) $error("response timeout");   // …or the timer does
    join_any
    disable fork;            // kills only the losing branch
  end join
endtask
```

### Common Pitfalls
- **Mixing assignments:** Never mix `=` and `<=` on the same signal. It creates unpredictable races.
- **Implicit Latches:** Using `always @(*)` instead of `always_comb` can hide missing default cases, leading to unwanted latches.
- **Zombie Threads:** Forgetting to terminate `fork/join_none` threads leaves them running forever, potentially hanging the simulation.
- **The `disable fork` Trap:** `disable fork;` kills *every* descendant of the calling process, including threads it forked long before (§9.6.3). Wrap the fork you want to clean up in its own process (`fork begin … end join`) so `disable fork` only sees that fork's children. Disabling a named block is **not** a safe substitute: it ends every activation of the block, including ones started by other concurrent calls (§9.6.2).

## The Forbidden Fruit: `always_latch`
_When you actually want a latch (which is almost never)._

SystemVerilog provides `always_latch` to model transparent latches. Unlike flip-flops (`always_ff`), latches pass data through when the enable is high and hold it when low.

```systemverilog
always_latch begin
  if (enable)
    q <= d;
  // No 'else' branch! This infers a latch.
end
```

> [!CAUTION]
> **Avoid Latches**
> In 99% of digital design, latches are accidental (due to incomplete `if/case` in combinational logic) and cause timing headaches. Only use `always_latch` if you are explicitly designing a clock gating cell or a low-power state retention block. If you see a latch inferred from `always_comb`, it is a bug.

### Case Study: Sequence Detector FSM
Put the guidelines into context with a classic problem: detect the bit pattern `101` on a serial input. A clean implementation separates sequential state updates (`always_ff`) from combinational next-state logic.

<InteractiveCode
  language="systemverilog"
  fileName="sequence_detector.sv"
  code={`
module sequence_detector (
  input  logic clk,
  input  logic reset,
  input  logic din,
  output logic detected
);

  typedef enum logic [1:0] {
    S_IDLE,
    S_GOT_1,
    S_GOT_10
  } state_t;

  state_t state, state_next;

  // Sequential evolution of the state register
  always_ff @(posedge clk or posedge reset) begin
    if (reset)
      state <= S_IDLE;
    else
      state <= state_next;
  end

  // Combinational next-state logic
  always_comb begin
    state_next = state;
    detected = 1'b0;
    unique case (state)
      S_IDLE:   state_next = din ? S_GOT_1  : S_IDLE;
      S_GOT_1:  state_next = din ? S_GOT_1  : S_GOT_10;
      S_GOT_10: begin
        detected   = din;
        state_next = din ? S_GOT_1 : S_IDLE;
      end
    endcase
  end

endmodule
  `}
/>

**What to notice:**
- State updates use non-blocking assignments in `always_ff`, mirroring flip-flop behavior.
- The combinational block seeds `state_next` and `detected` with safe defaults, preventing unintended latches.
- Using `unique case` catches missing branches while documenting intent for tools and reviewers.

## Make It Work

### Debug: the monitor that went silent

A test forks a coverage monitor, then runs a transfer with a timeout. The monitor stops reporting after the first transfer, and nothing fails. Find the line that kills it, then pick a fix: the model reruns your fix with one transfer and with two concurrent transfers, so a fix that only works in the simple case is caught.

### Build it yourself

1. **Set the stage:** Draft a timing diagram for your DUT, marking where sequential and combinational regions live. Annotate which constructs you’ll use (`always_ff`, `always_comb`, `initial`).
2. **Instrument aggressively:** Run a linter (for example `verilator --lint-only` or SpyGlass) to flag `=` in sequential blocks and `<=` in combinational ones. This is a coding-style check, so it belongs in lint, not in assertions.
3. **Prototype the flow:** Use the interactive snippet above as a template. Swap in your DUT signals and run a quick sim to validate ordering.

**Checklist before moving on:**
- [ ] You can explain why sequential logic needs non-blocking assignments and combinational logic prefers blocking.
- [ ] You’ve run a mini-simulation that includes `initial`, `always_ff`, and `final` blocks working together.
- [ ] You can describe the event scheduling order (active → inactive → NBA → postponed) and place each construct within it.
