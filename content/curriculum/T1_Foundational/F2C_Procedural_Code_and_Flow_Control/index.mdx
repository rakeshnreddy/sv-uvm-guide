## Quick Take

- **What it is:** **Procedural code** runs statement by statement inside a **procedure**: an `initial`, `always`, `always_comb`, `always_ff`, `always_latch` or `final` block (IEEE 1800-2023 §9.2). Procedures run concurrently. Inside one, you assign with blocking (`=`) or nonblocking (`<=`) assignments, wait with timing controls (`#`, `@`, `wait`), and split work into parallel threads with `fork`.
- **Why it matters:** Every RTL model and every testbench is built from procedures. Pick the wrong procedure or assignment and your design and testbench race each other, so a test can pass on one simulator and fail on another. Misjudge when forked threads start and stop, and a timeout kills the wrong thread or leaves threads running.
- **The Analogy:** A kitchen during service. Each procedure is a cook working down one recipe card in order. A timing control is the cook pausing for a timer or for the order bell. A nonblocking assignment is a plate put on the pass: cooks still reading this round's orders see the old plates, and all the new plates appear together afterwards. `fork` hands steps to helper cooks. *Where it breaks:* cooks who hear the same bell start in no promised order (§4.7), and a helper you fork does not start until you yourself stop to wait or finish (§9.3.2). A real helper would start at once.

**You will be able to:**
1. Choose `initial`, `always`, `always_comb`, `always_ff`, `always_latch` or `final`, and `=` or `<=`, for a given RTL or testbench job, and justify the choice.
2. Predict what `$display` and `$strobe` print when blocking and nonblocking assignments execute in the same time slot.
3. Predict when the parent process resumes after `fork … join`, `join_any` and `join_none`, and when the children start running.
4. Write an isolated per-transaction timeout with `fork … join_any` and `disable fork`.
5. Debug the fork-in-a-loop capture bug and a `disable fork` that kills a long-lived monitor.

### Procedures over simulation time

A **procedure** is a block of statements that the simulator runs as its own **process** (§9.5). Three kinds matter first:

- `initial` starts at time 0, runs its statements once, and ends (§9.2.1).
- `always` starts at time 0 and repeats forever (§9.2.2). It must contain a timing control. Without one it loops at time 0 and time never advances: the standard's own example, `always areg = ~areg;`, is a zero-delay infinite loop (§9.2.2.1).
- `final` runs once, when the simulation ends through an explicit or implicit `$finish`. It takes no simulation time and may contain only statements that a function may contain, such as `$display` (§9.2.3).

All `initial` and `always` procedures start at time 0 **in no promised order** (§9.2). Never write code that needs one `initial` to run before an `always`.

- Each `count <= count + 1` lands in the NBA region **of the same time slot** as its clock edge, never at a later time. The section on assignments below explains why.
- `final` runs exactly once, at 22 ns, the moment `$finish` ends the run, and takes no simulation time.

Which procedure for which job:

| Job | Procedure | Assignments |
|---|---|---|
| Stimulus that runs once: reset, a test sequence | `initial` | `<=` for signals the design reads; `=` for the bench's own variables |
| Clock generator | `always #5 clk = ~clk;` | `=`: the clock's own change is the edge every flop waits for |
| Flip-flops | `always_ff @(posedge clk ...)` | `<=` |
| Combinational logic | `always_comb` | `=` |
| A latch you really want | `always_latch` | `<=` |
| End-of-run summary | `final` | none: `$display` only |

### Choosing an RTL procedure: always_comb, always_ff, always_latch

For RTL, the plain `always` has three specialized forms. They state your intent, and the tool enforces rules that catch mistakes:

| Procedure | Models | Rules the tool enforces |
|---|---|---|
| `always_comb` | combinational logic, with `=` | Sensitive to what it reads, apart from variables it declares or writes itself (§9.2.2.2.1). Runs once at time 0, after all `initial` and `always` procedures have started. No other process may write its outputs (§9.2.2.2). No blocking timing controls or forks (§9.2.2.2.2). |
| `always_ff` | flip-flops, with `<=` | Exactly one event control and no blocking timing controls. No other process may write its outputs (§9.2.2.4). |
| `always_latch` | latches, with `<=` | The `always_comb` rules, with tool checks for latch behaviour instead of combinational behaviour (§9.2.2.3). |

Tools *should* also warn when an `always_comb` body infers a latch, or an `always_ff` body does not describe flip-flops (§9.2.2.2, §9.2.2.4). Those warnings are tool-dependent; the single-writer and timing-control rules are language rules.

**`always_comb` is not `always @*`.** Both infer a sensitivity list, but they differ in five ways (§9.2.2.2.2). The one you will meet first is time 0:

```systemverilog
// snippet
logic a = 1'b1;          // declaration initializer: set before any procedure starts
logic y1, y2;

always @* y1 = a;        // waits for the first change of a
always_comb y2 = a;      // also runs once at time 0

initial #10 a = 1'b0;
```

| Time | `a` | `y1` (`always @*`) | `y2` (`always_comb`) | Why |
|---|---|---|---|---|
| 0 | 1 | x | 1 | The initializer happened before any procedure was waiting, so `@*` never saw a change (§6.8). `always_comb` runs once at time 0. |
| 10 | 0 | 0 | 0 | The change of `a` wakes both. |

The other four differences: `always_comb` also reacts to variables read inside functions it calls (`@*` sees only their arguments); it forbids other writers to its outputs; it forbids blocking timing controls and forks; and it reacts to expressions in immediate assertions inside the functions it calls (§9.2.2.2.2).

#### When you really want a latch

`always_latch` models a transparent latch: the output follows the input while the enable is 1 and holds while it is 0.

```systemverilog
// snippet
always_latch
  if (en) q <= d;        // transparent while en is 1; q holds while en is 0
```

A latch can also appear by accident. An `always_comb` that leaves a variable unassigned on some path must remember the old value, and remembering is a latch; tools should warn about it (§9.2.2.2). Assign every output at the top of an `always_comb` block, as the state machine below does, and no path can leave it unassigned.

### Blocking and nonblocking assignments

A **blocking assignment** (`=`) updates its variable before the next statement in the same `begin … end` runs (§10.4.1). A **nonblocking assignment** (`<=`) works in two steps (§10.4.2):

1. It evaluates the right-hand side now, in the **Active region**, where procedure statements run.
2. It updates the variable later in the **same time slot**, in the **NBA region**.

So every process that runs in this time slot before the NBA region still reads the old value. `$strobe`, which prints in the Postponed region at the end of the time slot, sees the new value, and so does any process the update wakes.

**Predict first.** The simulator opens on the swap program. At t = 10 ns one process runs `a <= b; b <= a;` with a = 1 and b = 2, then calls `$display`, then `$strobe`, then prints again 1 ns later. Predict the first two lines and step through. Then switch the assignments to `=` and predict again.

<ProceduralBlocksSimulator scenario="nba-swap" />

What the trace showed:

- With `<=`, `$display` prints a=1 b=2: both right-hand sides were read and neither update has landed yet. `$strobe` prints a=2 b=1 at the same t = 10 ns.
- With `=`, the first statement overwrites `a` at once, so `b = a` copies 2 back. Both lines print 2 2, and there is no swap.
- The misconception this removes: *"a nonblocking assignment updates at a later simulation time."* It updates later **in the same time slot**. Only an intra-assignment delay such as `q <= #1 d;` moves an update to a later time (see Push Further).

#### The race that nonblocking assignments prevent

Inside one process, statement order is fixed (§4.6), so `=` and `<=` both behave predictably there. Races come from **two processes** woken by the same event, which the simulator may run in either order (§4.7). The classic case is a two-stage shift register:

```systemverilog
// snippet
// Racy: stage A and stage B wake on the same edge, in no promised order.
always @(posedge clk) q1 = d;        // stage A
always @(posedge clk) q2 = q1;       // stage B

// Race-free: both stages read old values, then both update in the NBA region.
always_ff @(posedge clk) q1 <= d;
always_ff @(posedge clk) q2 <= q1;
```

The rules that follow from this picture:

- **Flip-flops use `<=`.** Every flop reads in the Active region before any flop updates.
- **Before F4C, testbench writes to design inputs use `<=`**, or happen on the opposite clock edge. From F4C on, they go through a clocking block.
- **A reset applied at time 0 uses `<=`.** The update lands after every procedure has started and is waiting (see Push Further).
- **One writer per variable.** Two processes that write one variable at the same edge race even with `<=`: the last update performed wins. `always_comb` and `always_ff` make a second writer an error (§9.2.2.2, §9.2.2.4).
- **`=` is right for values local to one process:** combinational logic in `always_comb`, and a testbench's own counters and temporaries.

F3C traces this race region by region with an interactive scheduler: [Delta Cycles and Race Conditions](/curriculum/T1_Foundational/F3C_Delta_Cycles_and_Race_Conditions/index).

### Timing controls: #, @ and wait

A **timing control** suspends a process until something happens (§9.4). There are three kinds:

| Control | Waits for | Example |
|---|---|---|
| `#d` (delay) | d time units of the current module. An x or z delay counts as 0 (§9.4.1). | `#10 rst_n <= 1'b1;` |
| `@(...)` (event) | a change, an edge or a named event (§9.4.2) | `@(posedge clk);` |
| `wait (expr)` (level) | nothing if `expr` is already true; otherwise until it becomes true (§9.4.3) | `wait (ready);` |

Time units and precision belong to F3A: [Simulation Semantics](/curriculum/T1_Foundational/F3A_Simulation_Semantics/index).

Event controls in more detail (§9.4.2):

- `posedge` and `negedge` follow the edge table below, and `edge` means either one. For a vector, only changes of the least significant bit count as edges.
- `@(a or b)` and `@(a, b)` mean the same thing: either event wakes the process (§9.4.2.1).
- `@*` waits on every variable the statement reads (§9.4.2.2). For combinational logic, `always_comb` is better.
- `@(posedge clk iff en)` wakes only on edges where `en` is true at that moment (§9.4.2.3).

| From → to | 0 | 1 | x | z |
|---|---|---|---|---|
| **0** | no edge | posedge | posedge | posedge |
| **1** | negedge | no edge | negedge | negedge |
| **x** | negedge | posedge | no edge | no edge |
| **z** | negedge | posedge | no edge | no edge |

This is Table 9-2 of the standard. Note that x → 0 is a negedge: an active-low reset that starts as x and is driven to 0 at time 0 triggers `negedge rst_n`, but only in a flop that is already waiting for it.

<ProceduralBlocksSimulator scenario="edge-vs-level" />

What the trace showed:

- `wait (ready)` passes at once. It checks a level, and `ready` is already 1.
- `@(posedge ready)` never passes. The edge happened at 10 ns, before the process started waiting, and an event control does not remember past events.
- In a testbench, this is the driver that hangs because it waits for an edge of a handshake signal that is already high. Wait for a level with `wait`, or sample the signal at a clock edge.

A timing control can also sit inside an assignment, as in `a = #5 b;`, which reads `b` now and writes `a` later (§9.4.5). Push Further covers that form.

### Timeline of a Simulation Tick (preview of F3B)

Everything the simulator does at one simulation time is a **time slot**. Inside it, the simulator works through ordered **regions**, and loops back whenever new work appears (§4.4). This module needs four of them:

| Region | What runs there | Where you met it |
|---|---|---|
| Active | procedure statements, blocking assignments, the right-hand side of `<=` | almost all of your code |
| Inactive | processes resumed after `#0` | a `#0` "fix" only moves a race here (F3C) |
| NBA | the updates of nonblocking assignments | `q <= d` lands here, in the same time slot |
| Postponed | `$strobe` and `$monitor` output; nothing may change any more | `$strobe` prints settled values |

This table is a simplified preview. [F3B: Scheduling Regions](/curriculum/T1_Foundational/F3B_Scheduling_Regions/index) adds Preponed, Observed, Reactive, Re-Inactive and Re-NBA, plus the PLI regions, and [F3C](/curriculum/T1_Foundational/F3C_Delta_Cycles_and_Race_Conditions/index) traces delta cycles through all of them. `final` procedures belong to no region: they run once, when the simulation ends (§9.2.3).

### Blocks: begin-end and fork-join

Statements are grouped into blocks (§9.3):

- A **sequential block**, `begin … end`, runs its statements in order. Each delay counts from the previous statement (§9.3.1).
- A **parallel block**, `fork … join`, turns each statement into its own process. Every delay counts from the moment the block starts (§9.3.2).

```systemverilog
// snippet
initial begin             // sequential: delays add up
  #5 a = 1;               // t = 5
  #5 b = 2;               // t = 10
end

initial fork              // parallel: every delay counts from the fork's start
  #5  c = 1;              // t = 5
  #10 d = 2;              // t = 10
join
```

<ProceduralBlocksSimulator scenario="fork-timing" />

Debrief: "join done" prints at 15 ns. Both branches start at 5 ns, so `a` is set at 10 ns and `b` at 15 ns, and `join` waits for the later one. Adding the delays one after another (20 ns) is the sequential-block rule, not the parallel one.

Details you will need in real code:

- **Names and labels.** `begin : name … end` names a block (§9.3.4), and `name: begin … end` is the same thing written as a statement label (§9.3.5). A name lets you refer to the block's variables hierarchically and target the block with `disable`.
- **Local variables.** Declarations at the top of a block are local to it. In a module's `initial` or `always`, they are static, one copy shared by every pass, unless you write `automatic`. A declaration with an initializer there needs an explicit `static` or `automatic` (§6.21).
- **What creates a process.** Each `initial`, `always`, `always_comb`, `always_ff`, `always_latch` and `final` procedure, each statement of a fork, and each dynamic process (§9.5). A `begin … end` does **not**: it runs inside the process that reaches it. `fork begin s1; s2; end join` is one child process that runs two statements in order.

### Fork and join

The keyword that closes a fork decides when the **parent**, the process that executed the fork, continues (§9.3.2, Table 9-1):

| Keyword | The parent continues |
|---|---|
| `join` | when every child has finished |
| `join_any` | when the first child finishes; the others keep running |
| `join_none` | at once; every child keeps running |

One rule surprises almost everyone: **spawned processes do not start until the parent blocks or finishes**, whichever keyword you use (§9.3.2).

**Predict first.** The visualizer opens on a parent that forks A (`#10`), B (`#30`) and C (`#20`) and then prints "parent continues". Predict the print time for `join`, `join_any` and `join_none`. Then switch to *fork in a loop*, the most common fork bug in real testbenches.

<ForkJoinVisualizer scenario="join-variants" scenarios={["join-variants", "fork-loop-capture"]} />

What the lanes showed:

- `join_none`: the parent prints at 0 ns, before A, B and C have even started. They start at the parent's next blocking statement (`#`, `@`, `wait`) or when it ends.
- `join_any`: the parent resumes at 10 ns, when A ends. B and C keep running until something stops them (next section).
- `join`: the parent resumes at 30 ns, when the slowest child, B, ends.
- **Fork in a loop.** A `for` loop has one loop variable. `join_none` children start only after the loop has ended, so all of them read its final value: 3, 3, 3. Declaring `automatic int k = i;` in the fork itself gives each child its own copy, because declarations at the top of a fork are initialized when the fork executes, before its children are spawned (§9.3.2). The same declaration inside a child's `begin … end` runs when the child starts, which is too late.

```systemverilog
// snippet
for (int i = 0; i < 3; i++)
  fork
    automatic int k = i;      // set when the fork runs, before its child exists
    $display("k = %0d", k);   // the three children print 0, 1 and 2
  join_none
```

Testbench threads usually call **tasks**: named blocks of statements that may wait for time or events. `task automatic` gives every call its own copy of the task's variables, so concurrent calls do not share them. F2D teaches tasks in full: [Tasks and Functions](/curriculum/T1_Foundational/F2D_Reusable_Code_and_Parallelism/tasks-functions).

### Waiting for and cleaning up threads

Three statements control threads that you have forked (§9.6):

- `wait fork;` blocks until every **immediate child** of the calling process has finished. Grandchildren do not count (§9.6.1).
- `disable fork;` kills **every descendant** of the calling process, not just the children of the last fork. A monitor that the same process forked earlier dies too (§9.6.3).
- `disable name;` ends the named block or task in **every process** that is executing it (§9.6.2). In a task called by two threads at once, one call's cleanup kills the other call's work.

**Predict first.** The visualizer opens on a test that forks a background monitor, then runs a transfer whose response races a timer with `join_any`, and cleans up with `disable fork`. Predict which processes `disable fork` kills. Then try the *isolation wrapper* variant, the *disable by name* scenario with two concurrent calls, and the *wait fork* scenario.

<ForkJoinVisualizer scenario="timeout-disable-fork" scenarios={["timeout-disable-fork", "named-disable", "wait-fork"]} />

What the lanes showed:

- Plain `disable fork` kills the timer **and the monitor**, because the test forked both. The monitor goes silent with no error.
- With the isolation wrapper, `disable fork` runs inside a new parent whose only descendants are the response and the timer, so the monitor survives.
- `disable guard` with two concurrent calls ends both activations of the block, so the second call never prints its response.
- `wait fork` returns at 20 ns, when the last immediate child ends. It does not wait for the grandchild G.

The safe per-transaction timeout gives the race its own parent process, so `disable fork` has nothing else to reach:

```systemverilog
// snippet
// Waits up to timeout time units for rsp_valid to rise. The outer fork gives
// the race its own parent, so disable fork reaches only these two branches.
task automatic wait_for_response(input int timeout, output bit timed_out);
  timed_out = 1'b0;
  fork begin
    fork
      @(posedge rsp_valid);                      // the response wins...
      begin #(timeout); timed_out = 1'b1; end    // ...or the timer does
    join_any
    disable fork;                                // kill the losing branch
  end join
endtask
```

`#(timeout)` counts in the module's time unit, so `timeunit 1ns` makes it nanoseconds, and `timed_out` tells the caller which branch won. The same wrapper bounds a `wait fork`: put the threads you want to wait for, and the `wait fork`, inside `fork begin … end join`, and a monitor forked earlier no longer holds it up.

```systemverilog
// snippet
typedef enum logic [1:0] {S_IDLE, S_GOT_1, S_GOT_10} state_t;
state_t state, state_next;

always_ff @(posedge clk or negedge rst_n) begin   // the only writer of state
  if (!rst_n) state <= S_IDLE;
  else        state <= state_next;
end

always_comb begin
  state_next = state;      // seed every output: no path can infer a latch
  detected   = 1'b0;
  unique case (state)      // no default: an x or illegal state is reported
    S_IDLE:   if (din)  state_next = S_GOT_1;
    S_GOT_1:  if (!din) state_next = S_GOT_10;
    S_GOT_10: begin
      detected = din;      // Mealy output: depends on the state and on din
      if (din) state_next = S_GOT_1;   // the final 1 can start the next match
      else     state_next = S_IDLE;
    end
  endcase
end
```

Tools differ in how strictly they enforce that rule, so the `if` form is the portable one.

What to notice:

- **One writer, the right assignment.** `state` is written only by the `always_ff`, with `<=`. The `always_comb` uses `=` and writes only `state_next` and `detected`.
- **Seeded outputs.** `state_next` and `detected` get a value before the `case`, so every path assigns them, even when `state` is x. No latch can be inferred.
- **`unique case` without a `default`.** A `state` that matches no item is reported at run time. Before reset, `state` is x (the default value of a 4-state enum), but a report appears only if `state` is still x when time slot 0 ends. The bench in Make It Work resets with `<=` at time 0, so `state` is legal by then and nothing is reported. [Procedural Flow Control](/curriculum/T1_Foundational/F2C_Procedural_Code_and_Flow_Control/flow-control) explains the timing of these reports.

### Pitfalls and misconceptions

| Misconception | Why it is wrong |
|---|---|
| "A nonblocking assignment updates at a later simulation time." | It updates in the NBA region of the same time slot; `$strobe` at that time already sees the new value (§10.4.2). |
| "`join_none` children start running immediately." | They start only when the parent blocks or finishes (§9.3.2). |
| "`disable fork` kills only the children of the last fork." | It kills every descendant of the calling process, including a monitor forked earlier (§9.6.3). |
| "Wrapping the race in `begin … end` isolates `disable fork`." | A `begin … end` creates no process (§9.5). You need `fork begin … end join`. |
| "Disabling a named block is a safe, targeted cleanup." | It ends that block in every process executing it (§9.6.2). |
| "Never mix `=` and `<=` in one block." | Inside one process the order is fixed (§4.6). The real rules are one writer per variable, and `<=` for anything another process reads at the same edge. |
| "`initial` blocks run before `always` blocks." | There is no implied order at time 0 (§9.2). |
| "`always_comb` is a new spelling of `always @*`." | They differ in five ways, starting with time 0 (§9.2.2.2.2). |
| "A `forever` loop with delays hangs the simulation." | It keeps the run alive until `$finish`; only a loop with no timing control stops time (§12.7.6). A bench that waits for events to run out never ends, so end it with `$finish`. |

### Recap

- Procedures are concurrent processes that start at time 0 in no promised order; `final` runs once at the end, in zero time.
- `always_comb` (with `=`), `always_ff` (with `<=`) and `always_latch` state your intent and are checked; `always_comb` also runs once at time 0.
- `<=` updates later in the same time slot. Flops, testbench writes to design inputs and time-0 resets use it.
- `#` waits for time, `@` for a change or edge that happens while you wait, and `wait` for a level.
- Forked children start when the parent blocks. `join`, `join_any` and `join_none` decide when the parent continues. Isolate each timeout with `fork begin fork … join_any; disable fork; end join`.

## Make It Work

### Worked example: a self-checking bench with a guarded watchdog

This complete file puts every idea on this page to work: the two-process detector from the case study, a clock, a time-0 reset, stimulus driven with `<=`, a long-lived monitor, a watchdog isolated with the wrapper idiom, and a `final` summary. Read it once top to bottom, then follow the numbered walk-through.

```systemverilog
// compile
// seq_detect_tb.sv: a 101 detector and a self-checking bench in one file.

module seq_detector (
  input  logic clk,
  input  logic rst_n,      // active-low asynchronous reset
  input  logic din,
  output logic detected    // 1 while state is S_GOT_10 and din is 1 (Mealy)
);
  timeunit 1ns;            // if one module in a design declares a time unit,
  timeprecision 1ps;       // every module must (§3.14.2.3)

  typedef enum logic [1:0] {S_IDLE, S_GOT_1, S_GOT_10} state_t;
  state_t state, state_next;

  always_ff @(posedge clk or negedge rst_n) begin   // the only writer of state
    if (!rst_n) state <= S_IDLE;
    else        state <= state_next;
  end

  always_comb begin
    state_next = state;    // seed every output: no path can infer a latch
    detected   = 1'b0;
    unique case (state)    // no default: an x or illegal state is reported
      S_IDLE:   if (din)  state_next = S_GOT_1;
      S_GOT_1:  if (!din) state_next = S_GOT_10;
      S_GOT_10: begin
        detected = din;    // Mealy output
        if (din) state_next = S_GOT_1;
        else     state_next = S_IDLE;
      end
    endcase
  end
endmodule

module tb_top;
  timeunit 1ns;
  timeprecision 1ps;

  localparam logic [7:0] PATTERN = 8'b1010_1101;  // sent MSB first: 1 0 1 0 1 1 0 1

  logic clk = 1'b0;        // set before any procedure starts: no process sees a change
  logic rst_n, din, detected;
  int   pass_count, fail_count, detect_count;     // 2-state: they start at 0

  seq_detector dut (.clk(clk), .rst_n(rst_n), .din(din), .detected(detected));

  always #5 clk = ~clk;    // rising edges at 5, 15, 25, ... ns

  initial begin
    // A long-lived monitor, forked by this process: it counts detections.
    fork
      forever @(posedge clk) if (detected === 1'b1) detect_count++;
    join_none

    // The test body races a watchdog. The wrapper gives the race its own
    // parent, so disable fork kills the loser and cannot reach the monitor.
    fork begin
      fork
        drive_and_check();
        begin
          #1us;
          fail_count++;
          $error("watchdog: drive_and_check did not finish within 1 us");
        end
      join_any
      disable fork;
    end join

    @(negedge clk);        // let every process finish its work for the last edge
    $finish;
  end

  // Drives PATTERN one bit per clock and checks detected against a model.
  task automatic drive_and_check();
    logic [1:0] hist = 2'b00;   // the two previous input bits: the model's state
    logic       expected;
    rst_n <= 1'b0;              // <= at time 0: lands after the DUT flop is waiting
    din   <= 1'b0;
    repeat (2) @(posedge clk);
    rst_n <= 1'b1;              // release just after an edge, never on one
    for (int i = 7; i >= 0; i--) begin
      din <= PATTERN[i];        // changes just after the edge, like a flop output
      @(posedge clk);           // the DUT samples din here; detected is stable
      expected = (hist == 2'b10) && PATTERN[i];
      if (detected !== expected) begin
        fail_count++;
        $error("bit %0d: detected=%b, expected %b", 8 - i, detected, expected);
      end else begin
        pass_count++;
      end
      if (expected) $display("t=%0d ns: 101 detected at bit %0d", $time, 8 - i);
      hist = {hist[0], PATTERN[i]};
    end
  endtask

  final begin
    $display("monitor counted %0d detections", detect_count);
    $display("PASS=%0d FAIL=%0d", pass_count, fail_count);
  end
endmodule
```

**Expected output** (worked out by hand from the rules on this page, not captured from a simulator run; your simulator also prints its own start-up and `$finish` lines):

```text
t=45 ns: 101 detected at bit 3
t=65 ns: 101 detected at bit 5
t=95 ns: 101 detected at bit 8
monitor counted 3 detections
PASS=8 FAIL=0
```

How it works, step by step:

1. **The DUT is two processes.** The `always_ff` is the only writer of `state` and uses `<=`. The `always_comb` seeds its outputs, then decodes with a `unique case` that has no `default`.
2. **The clock.** `clk` starts at 0 through its declaration initializer, which takes effect before any procedure starts, so no process sees it as a change. `always #5 clk = ~clk;` then gives rising edges at 5, 15, 25 … ns.
3. **The monitor.** The test process forks a `forever` monitor with `join_none`. It starts when the test process blocks at the wrapper's `join`, and counts detections for the whole run.
4. **The guarded body.** The test races `drive_and_check()` against a 1 µs watchdog inside `fork begin … end join`. Whichever branch finishes first, `disable fork` kills the other one, and only that one: the monitor is a child of the test process, not of the wrapper.
5. **Reset and stimulus.** `drive_and_check` asserts `rst_n` with `<=` at time 0, releases it just after the second rising edge (t = 15 ns), then drives one pattern bit per clock with `<=`. Bit 1 is sampled at 25 ns, bit 8 at 95 ns.
6. **Checking.** At each rising edge the DUT and the checker see the same stable `detected`: it changes only after nonblocking updates. The checker compares it with `!==` against a two-bit history model, so an x output fails the check instead of passing it. The timing diagram in the case study shows the same eight edges.
7. **Ending.** The test waits for a falling edge, so the monitor has finished with the last rising edge, then calls `$finish`. The `final` procedure prints the summary in zero time.

## Push Further

### Expert: Time zero and initialization order

- **No order at time 0.** `initial` and `always` procedures start in no implied order (§9.2). A bench that runs `rst_n = 0;` with a blocking assignment at time 0 may run before the DUT's `always_ff @(posedge clk or negedge rst_n)` has reached its event control. The flop then misses the x → 0 negedge, and `state` stays x until the first clock edge with reset low.
- **The fix is `<=`.** A nonblocking update at time 0 lands in the NBA region, after every procedure started at time 0 has run up to its first timing control (§4.5). The standard's own `forever` clock example initializes its clocks with `<=` (§12.7.6).
- **Declaration initializers run before any procedure waits.** `logic clk = 1'b0;` is set before any `initial` or `always` procedure starts (§6.8, §10.5). No process is waiting on `clk` yet, so none of them sees a change. That is right for a clock's starting value and wrong for a reset that flops must react to. In IEEE 1364-2005 such an initializer behaved like an assignment from an `initial` procedure after simulation had started (§6.8, NOTE), so legacy code may rely on an event that no longer happens.
- **`always_comb` runs once at time 0**, after all `initial` and `always` procedures have started (§9.2.2.2), so its outputs match its inputs from the first moment.
- **Interleaving.** A simulator may suspend a process between statements and run others (§4.7). Only the order of statements inside one `begin … end` is guaranteed (§4.6).

### Expert: Nonblocking order, intra-assignment delays and lifetimes

- **Order of updates.** Nonblocking updates are performed in the order their statements executed, so `a <= 0; a <= 1;` in one process leaves `a` at 1 (§4.6 b).
- **Intra-assignment timing.** A timing control inside an assignment evaluates the right-hand side now and assigns later (§9.4.5). `a = #5 b;` writes after 5 time units and blocks the process meanwhile. `q <= #1 d;` schedules the update one time unit later without blocking: the one case where a nonblocking update really lands at a later time. `a <= repeat (3) @(posedge clk) d;` writes after three rising edges. The standard's race-free swap is `fork a = #5 b; b = #5 a; join`.
- **No nonblocking writes to automatic variables** (§6.21, §10.4.2). In a `task automatic` driver, `<=` to a task-local variable is a compile error; `<=` to module or interface signals is fine.
- **Two writers still race with `<=`.** If two processes write one variable at the same edge, the last update performed wins, and which one is last depends on process order. `always_ff` and `always_comb` turn a second writer into an error (§9.2.2.2, §9.2.2.4).

### Expert: Fork corner cases

- **Fork-local variables are initialized before the children exist.** Declarations at the top of a fork are initialized each time the fork executes, before any child is spawned (§9.3.2). That is why `automatic int k = i;` in the fork captures each iteration's value, while the same declaration inside a child's `begin … end` runs when the child starts. In the standard's own example, that late copy reads the loop's final value.
- **Explicit lifetime.** In a module's `initial` or `always`, a block declaration with an initializer must say `automatic` or `static` (§6.21). So `int k = i;` in the fork is a compile error, not a silent bug.
- **`return` inside a fork is a compile error** (§9.3.2): the forked statement runs in another process.
- **`ref` arguments.** Inside `join_any` or `join_none`, a task's `ref` argument may be used only to initialize fork-local variables, unless it is declared `ref static` (§9.3.2).
- **No jumps across a fork.** `break` and `continue` cannot control a loop outside the fork (§12.8).
- **Children outlive their parent.** When a parent with `join_none` children ends, the children start and run to completion. Only `disable fork`, `disable`, `process::kill()` or the end of the simulation stops them.

### Expert: disable in depth

- **Every activation.** Disabling a task or a named block ends all of its activations, including every concurrent execution of an automatic task (§9.6.2).
- **Loop bodies.** Disabling a named loop-body block acts like `continue`; disabling a block that is not executing does nothing (§9.6.2).
- **Unspecified leftovers.** After a task is disabled, its `output` and `inout` results, its scheduled but not yet performed nonblocking assignments, and its procedural continuous assignments are unspecified (§9.6.2). Never rely on the outputs of a disabled task.
- **Descendants of finished children.** `disable fork` also kills the descendants of children that have already finished (§9.6.3).
- **`process::kill()`** kills a process and all of its descendants, even if the process itself has finished (§9.7). I-SV-5 teaches the `process` class: [Synchronization and IPC](/curriculum/T2_Intermediate/I-SV-5_Synchronization_and_IPC/index).

### Expert: final procedures and the end of the run

- `final` procedures run when the simulation ends through an explicit call to `$finish` or an implicit one, such as the call `$fatal` makes (§9.2.3, §20.10). A run with no activity of any kind left also terminates on its own (§9.6.1), but a bench that ends with an explicit `$finish` leaves no doubt about when its `final` procedures run.
- They run as a series of function calls from one process, in an order the standard leaves arbitrary; tools should keep it the same from run to run (§9.2.3). Never make one `final` depend on another.
- No scheduled event runs after the last `final` procedure (§9.2.3). Anything a `final` schedules for later never happens, so a `$strobe` in a `final` prints nothing: use `$display`. Whether a tool rejects a nonblocking assignment in a `final` or silently drops it is tool-dependent.
- `$finish` inside a `final` ends the simulation at once (§9.2.3). `$stop` only suspends the run (§20.2); `final` procedures run when the run really ends.
- In UVM benches, the end-of-test summary belongs in `report_phase`: [I-UVM-1C: UVM Phasing](/curriculum/T2_Intermediate/I-UVM-1C_UVM_Phasing/index).

### Expert: Sensitivity lists in detail

- `always_comb` leaves out variables declared inside the block and variables the block writes (§9.2.2.2.1). `always @*` includes written variables: the standard's example `always @* begin tmp1 = a & b; tmp2 = c & d; y = tmp1 | tmp2; end` is sensitive to `tmp1` and `tmp2` as well as to `a`, `b`, `c` and `d` (§9.4.2.2).
- `always @*` sees only the arguments of a function it calls; `always_comb` also sees the variables the function reads (§9.2.2.2.2).
- An edge event is detected on the least significant bit only, and a change in an operand that leaves the expression's value unchanged is no event (§9.4.2). `@(posedge bus)` on a vector watches `bus[0]`.
- In `@(a iff en)`, the guard is evaluated when `a` changes, not when `en` changes (§9.4.2.3).

### Expert: Thread hygiene at scale and in UVM

- **The same guard in uvm-core.** uvm-core 2020.3.1 waits for the end of a task phase with the same isolation pattern: `fork begin // guard`, then `fork … join_any; disable fork;`, then `end join // guard`, in task `execute_phase` of `src/base/uvm_phase_hopper.svh`.
- **Phase-end kill.** When a task phase ends, uvm-core kills the threads it started for every component. The header comment of `src/base/uvm_task_phase.svh` says that `exec_task()` threads still running when the phase completes are killed at once, and `cleanup_phase` in `uvm_phase_hopper.svh` calls `kill()` on the phase's process. A component's `forever` monitor loop in `run_phase` therefore needs no cleanup of its own. A per-transaction timer inside a driver still does, because it would fire within the phase.
- **Leaked timers cost.** Every timer you do not kill stays a live process until it expires. How much memory and run time thousands of them cost is tool-dependent; kill them with the wrapper.
- **`wait fork` and long-lived children.** `wait fork` waits for every immediate child, monitors included (§9.6.1). For a bounded set of threads, give them their own parent, or keep `process` handles (I-SV-5).

### Kata A (guided): fix the racy shift register

**Objectives 1 and 2.** Two flops written with blocking assignments race on every edge. Predict both legal outcomes, then fix the code and predict the one log every simulator must print.

```systemverilog
// compile
module tb_top;
  timeunit 1ns;
  timeprecision 1ps;

  localparam logic [4:0] D_BITS = 5'b10110;   // d values in order: 1 0 1 1 0

  logic clk = 1'b0;
  logic d, q1, q2;

  always #5 clk = ~clk;                       // rising edges at 5, 15, 25, 35, 45 ns

  // Two flops written with blocking assignments: a race.
  always @(posedge clk) q1 = d;               // stage A
  always @(posedge clk) q2 = q1;              // stage B

  initial begin
    for (int i = 4; i >= 0; i--) begin
      d <= D_BITS[i];                          // drive with <= between edges
      @(posedge clk);                          // both stages sample here
      #1 $display("t=%0d d=%b q1=%b q2=%b", $time, d, q1, q2);
    end
    $finish;
  end
endmodule
```

1. Before you run it, write down the `q2` column twice: once assuming stage A runs first at every edge, once assuming stage B runs first.
2. Run it. Which of your two columns did your simulator print? Either one is legal (§4.7).
3. Rewrite both stages as `always_ff` with `<=`, predict the single correct log, and run it again.

<details>
<summary>Worked solution</summary>

Each line prints 1 ns after an edge, so it shows the values just after that edge settled.

If stage A runs first, stage B reads the `q1` that stage A has just written, so `q2` equals `q1` on every line:

```text
t=6 d=1 q1=1 q2=1
t=16 d=0 q1=0 q2=0
t=26 d=1 q1=1 q2=1
t=36 d=1 q1=1 q2=1
t=46 d=0 q1=0 q2=0
```

If stage B runs first, it reads the old `q1`, and the log matches a real two-stage shift register:

```text
t=6 d=1 q1=1 q2=x
t=16 d=0 q1=0 q2=1
t=26 d=1 q1=1 q2=0
t=36 d=1 q1=1 q2=1
t=46 d=0 q1=0 q2=1
```

The fix makes the second log the only possible one:

```systemverilog
// snippet
always_ff @(posedge clk) q1 <= d;    // both stages read old values in Active...
always_ff @(posedge clk) q2 <= q1;   // ...and update together in NBA
```

Both stages now read `d` and `q1` in the Active region and update in the NBA region, so process order can no longer leak into the result. The timing diagram in the section on assignments shows the same values, sampled at the edges.

</details>

### Kata B (independent): a timeout that cannot kill the monitor

**Objectives 4 and 5.** The starter's monitor goes silent after the first transfer.

```systemverilog
// compile
module tb_top;
  timeunit 1ns;
  timeprecision 1ps;

  // One transfer: its response (after lat ns) races a 40 ns timer.
  task automatic xfer(input int id, input int lat);
    fork
      begin #(lat); $display("t=%0d xfer %0d response", $time, id); end
      begin #40;    $display("t=%0d xfer %0d TIMEOUT", $time, id); end
    join_any
    disable fork;                       // meant to stop the losing branch
  endtask

  initial begin
    fork                                // a monitor that should run all test long
      forever #10 $display("t=%0d monitor alive", $time);
    join_none
    xfer(1, 13);
    fork                                // two transfers in flight at once
      xfer(2, 12);
      xfer(3, 24);
    join
    #20 $display("t=%0d test done", $time);
    $finish;
  end
endmodule
```

1. Run the starter, or trace it by hand, and explain why "monitor alive" stops after t = 13 ns.
2. Fix `xfer` so that the monitor runs until the end. Do not use `disable` with a block name.
3. Add `output bit timed_out` to `xfer`, set it in the timer branch, and print all three flags in the "test done" line.
4. Predict the full log, then check it. Pass criteria: "monitor alive" keeps printing to the end, no TIMEOUT line appears, all three responses print, and every `timed_out` flag is 0.

<details>
<summary>Worked solution</summary>

The starter calls `xfer(1, 13)` directly from the test process, so its `disable fork` kills every descendant of the test process: the timer and the monitor (§9.6.3). Its log is:

```text
t=10 monitor alive
t=13 xfer 1 response
t=25 xfer 2 response
t=37 xfer 3 response
t=57 test done
```

The fix gives each call's race its own parent process:

```systemverilog
// compile
module tb_top;
  timeunit 1ns;
  timeprecision 1ps;

  // The outer fork gives each call's race its own parent process, so
  // disable fork reaches only this call's response and timer branches.
  task automatic xfer(input int id, input int lat, output bit timed_out);
    timed_out = 1'b0;
    fork begin
      fork
        begin #(lat); $display("t=%0d xfer %0d response", $time, id); end
        begin
          #40;
          timed_out = 1'b1;
          $display("t=%0d xfer %0d TIMEOUT", $time, id);
        end
      join_any
      disable fork;                     // kills only the losing branch
    end join
  endtask

  initial begin
    bit to1, to2, to3;
    fork
      forever #10 $display("t=%0d monitor alive", $time);
    join_none
    xfer(1, 13, to1);
    fork
      xfer(2, 12, to2);
      xfer(3, 24, to3);
    join
    #20 $display("t=%0d test done: timed_out = %b %b %b", $time, to1, to2, to3);
    $finish;
  end
endmodule
```

Expected log (worked out by hand; no two lines share a time, so the order is fixed):

```text
t=10 monitor alive
t=13 xfer 1 response
t=20 monitor alive
t=25 xfer 2 response
t=30 monitor alive
t=37 xfer 3 response
t=40 monitor alive
t=50 monitor alive
t=57 test done: timed_out = 0 0 0
```

Why not a named block with `disable guard`? Calls 2 and 3 overlap. At 25 ns, call 2's `disable guard` would also end call 3's block, and "xfer 3 response" would never print (§9.6.2).

</details>
