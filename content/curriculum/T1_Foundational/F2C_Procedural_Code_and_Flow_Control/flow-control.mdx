## Quick Take

- **What it is:** **Flow control** statements decide which statements in a procedure run, and how often: `if`–`else`; `case`, `casez`, `casex` and `case … inside`; the `unique`, `unique0` and `priority` qualifiers; the loops `for`, `repeat`, `while`, `do … while`, `foreach` and `forever`; and the jumps `break`, `continue` and `return` (IEEE 1800-2023 Clause 12).
- **Why it matters:** Every decision has to handle two values your software habits never meet: x and z. An `if` with an x condition quietly takes the `else` branch, a plain `case` with no matching item quietly does nothing, and a `repeat` with an x count quietly never runs. The qualifiers turn the worst of these silent cases into run-time violation reports.
- **The Analogy:** A railway junction. `if` and `case` are switches that send the train, the flow of execution, down one track; a loop is a turntable that sends it round again; `unique` and `priority` are signal inspectors who report a switch set to no track or to two tracks. *Where it breaks:* a real switch in an unknown position would derail the train. In SystemVerilog an unknown condition quietly takes the `else` track, and an unmatched `case` takes no track at all, with no alarm unless an inspector is posted.

**You will be able to:**
1. Predict which branch of an `if`, `case`, `casez`, `casex` or `case … inside` runs when the condition or case expression has x or z bits.
2. Choose between plain, `unique`, `unique0` and `priority` decisions, and predict when each reports a violation, with and without `default`.
3. Write `for`, `repeat`, `while`, `do … while`, `foreach` and `forever` loops with `break` and `continue`, and predict how many times they run.
4. Debug decisions and loops that fail silently: an unknown select, a violation report at time 0, a loop that never runs or never lets time advance.

## Build Your Mental Model

This lesson builds on the procedures and timing controls of [the previous lesson](/curriculum/T1_Foundational/F2C_Procedural_Code_and_Flow_Control/index) and on the four values 0, 1, x and z from [F2A: Core Data Types](/curriculum/T1_Foundational/F2A_Core_Data_Types/index). Every statement on this page runs inside a procedure.

### if–else and unknown conditions

An `if` runs its first statement only when the condition is **true**, which means a known, nonzero value. A condition of 0, x or z is **false**, so the `else` branch runs if there is one (§12.4). This is **X-optimism**: the code takes a clean-looking branch even though the value is unknown.

| `a` | `if (a)` runs | `if (!a)` runs | `a ? 1'b1 : 1'b0` gives |
|---|---|---|---|
| 0 | `else` | then | 0 |
| 1 | then | `else` | 1 |
| x | `else` | `else` | x |
| z | `else` | `else` | x |

`if (!a)` does not rescue you: `!x` is x, which is not true either (§11.4.7). The conditional operator `?:` behaves differently. With an unknown condition it evaluates both results and merges them bit by bit, so bits that disagree become x and the unknown stays visible (§11.4.11).

Two more rules:

- An `else` belongs to the nearest earlier `if` that has no `else`. Use `begin … end` to attach it elsewhere (§12.4).
- In an `if`–`else if` chain the conditions are tested in order and the first true one wins. A final `else` catches everything left (§12.4.1).

### case, casez and casex

A `case` statement evaluates its case expression once, compares it with each item **in source order**, and runs the **first** item that matches; `default` runs only if no item matches (§12.5). Two rules surprise newcomers:

- The comparison is exact over all four values, like `===`. An x in the case expression matches only an x in the item.
- If no item matches and there is no `default`, **nothing runs and nothing is reported** (§12.5).

`casez` and `casex` add **don't-care** bits, which are skipped in the comparison (§12.5.1):

| Statement | Don't-care bits, in the case expression **and** the items | An x in the case expression |
|---|---|---|
| `case` | none | must match an x in the item |
| `casez` | z and `?` | must still match exactly |
| `casex` | x, z and `?` | is skipped, so a real item can match |

The last cell is the hazard. An unknown select under `casex` runs a real branch, and the bug hides. Prefer `casez` for don't-care decoding, or `case … inside`, below.

**Predict first.** In the explorer's case panel, set `sel` to x0, then predict the branch under `case`, `casez` and `casex` before revealing each answer. The items are A `2'b00`, B `2'b1?` and C `2'bx1`, with a default D.

What the model showed: `case` and `casez` both fall through to the default D, because the x bit has to match exactly, while `casex` skips the x and runs A. Same input, two different answers.

A constant case expression turns `case` into a chain of conditions: `case (1'b1)` runs the first item whose expression is 1 (§12.5.2). The one-hot select in the next section uses it.

### unique, unique0 and priority

The keywords `unique`, `unique0` and `priority` in front of an `if` or a `case` add **violation checks**, which the simulator must run every time the statement executes (§12.4.2, §12.5.3). They never change which branch runs: every form runs the first matching item.

| Form | Reports when **no** item matches and there is no `default` or final `else` | Reports when **more than one** item matches |
|---|---|---|
| plain `case` or `if` | no: nothing runs | no: the first match runs |
| `unique` | yes | yes |
| `unique0` | no | yes |
| `priority` | yes | no: overlaps are allowed, the first match wins |

A traced example. Run this decoder with each qualifier in turn by replacing `unique` with nothing, `unique0` or `priority`:

```systemverilog
// snippet
always_comb begin
  y = 4'b0000;                 // seed: y is assigned on every path
  unique case (sel)            // no default, on purpose
    2'b00: y = 4'b0001;
    2'b01: y = 4'b0010;
    2'b10: y = 4'b0100;
  endcase
end
```

| `sel` | plain `case` | `unique` | `unique0` | `priority` | `unique` with a `default` |
|---|---|---|---|---|---|
| `2'b01` | item 01 runs | item 01 runs | item 01 runs | item 01 runs | item 01 runs |
| `2'b11` | nothing runs, silent | nothing runs, **report** | nothing runs, silent | nothing runs, **report** | `default` runs, silent |
| `2'bxx` | nothing runs, silent | nothing runs, **report** | nothing runs, silent | nothing runs, **report** | `default` runs, silent |

Overlaps behave the other way round. With `casez` items `2'b1?` and `2'b?1` and `sel` = `2'b11`, both items match. Every form runs the first one, `2'b1?`; `unique` and `unique0` also report the overlap, while plain `casez` and `priority` stay silent.

The same qualifiers work on an `if`–`else if` chain, where a final `else` plays the part of `default` (§12.4.2):

```systemverilog
// snippet
always_comb begin
  grant = 2'b00;               // seed: grant is assigned on every path
  unique if (req[0]) grant = 2'b01;
  else if (req[1])   grant = 2'b10;
end
```

| `req` | plain `if` | `unique if` | `unique0 if` | `priority if` |
|---|---|---|---|---|
| `2'b10` | second branch | second branch | second branch | second branch |
| `2'b11` | first branch, silent | first branch, **report** (overlap) | first branch, **report** (overlap) | first branch, silent |
| `2'b00` | nothing runs, silent | nothing runs, **report** | nothing runs, silent | nothing runs, **report** |

With `req` = `2'b11` both conditions are true. A `unique if` still runs the branch of the first true condition, but it reports that the conditions were not mutually exclusive.

Rules that follow:

- **A `default` silences the no-match check.** It matches every leftover value, so "no match" can never happen (§12.5.3, NOTE). Leave it out when an unmatched value is a bug, and seed the outputs at the top of the block instead, so that no path infers a latch.
- **Not just a synthesis hint.** Simulators must report violations. The wording and severity of the report are tool-specific.
- **Reports wait for the time slot to settle.** The check runs when the statement executes, but the report is held until the Observed region of that time slot, and is discarded if the procedure runs again first (§12.4.2.1, §12.5.3.1). So a zero-delay glitch that makes an `always_comb` run again within the time slot is not reported, while a bad select seen by the procedure's last run in that time slot is.

When to use which:

- `unique` for decoders where exactly one item must match: state decoders and one-hot selects.
- `unique0` where "nothing matches" is legal but two matches would be a bug, such as optional enables.
- `priority` where order matters and overlaps are expected, but "nothing matches" is a bug: priority encoders.
- Plain `case` with a `default` where every leftover value has a sensible meaning.

```systemverilog
// snippet
// One-hot select: exactly one bit of gnt may be 1.
always_comb begin
  data_out = '0;
  unique case (1'b1)           // constant case expression (§12.5.2)
    gnt[0]: data_out = data0;
    gnt[1]: data_out = data1;
    gnt[2]: data_out = data2;
  endcase
end

// Priority encoder: the lowest set bit wins; req == 0 is a bug here.
always_comb begin
  idx = '0;
  priority casez (req)
    4'b???1: idx = 2'd0;       // these items overlap on purpose:
    4'b??1?: idx = 2'd1;       // priority allows it, and the first match wins
    4'b?1??: idx = 2'd2;
    4'b1???: idx = 2'd3;
  endcase
end
```

With `gnt` = 3'b011, the `unique case (1'b1)` finds two matching items: it runs `data_out = data0` and reports an overlap. With `req` = 4'b0110, the `priority casez` runs the `4'b??1?` item (`idx` = 1) silently, and with `req` = 0 it reports that nothing matched.

### case inside

`case (expr) inside` compares the case expression with each item through the set-membership operator `inside` (§12.5.4, §11.4.13). Items can be single values, lists and ranges:

```systemverilog
// snippet
always_comb begin
  kind = 2'd3;                       // seed: 3 means "not a known opcode"
  unique0 case (opcode) inside       // opcode is logic [3:0]
    [4'd0:4'd7]:      kind = 2'd0;   // a range: ALU operations
    4'b10??:          kind = 2'd1;   // wildcard bits in the item: loads
    4'b1100, 4'b1101: kind = 2'd2;   // a list: stores
  endcase
end
```

The decoder classifies 4'b1110 and 4'b1111 as unknown opcodes, so "no match" is legal here, and `unique0` checks only that no two items overlap. If an unlisted opcode could only come from a bug, `unique` would report it instead. The price of `unique0` is that an unknown `opcode`, such as 4'bxxxx, also lands silently on kind 3; an immediate assertion such as `assert (!$isunknown(opcode))` catches that ([I-SV-4A](/curriculum/T2_Intermediate/I-SV-4A_SVA_Fundamentals/index)).

The wildcards are **asymmetric** (§11.4.6). An x, z or `?` in an **item** is a wildcard that matches any value; an x or z in the **case expression** is not a wildcard, so it matches only a wildcard bit of the item. An item matches when the `inside` comparison returns 1; a result of 0 or x is no match (§12.5.4). So an unknown select never silently matches an ordinary item:

| `sel` | `casex`, items `2'b10` and `2'b11` | `case inside`, items `2'b10` and `2'b11` | `case inside`, item `2'b1?` |
|---|---|---|---|
| `2'b10` | `2'b10` runs | `2'b10` runs | `2'b1?` runs |
| `2'b1x` | `2'b10` runs (both items match) | no match | `2'b1?` runs |
| `2'bx1` | `2'b11` runs | no match | no match |
| `2'bxx` | `2'b10` runs (both items match) | no match | no match |

This is why style guides prefer `case … inside` to `casex`: the don't-care bits stay where you wrote them, in the items. F2A's sub-lesson on operators covers `inside` and `==?` as expressions: [Operators and Expressions](/curriculum/T1_Foundational/F2A_Core_Data_Types/operators-and-expressions).

### Loops

| Loop | Runs its body | Key rules |
|---|---|---|
| `for (int i = 0; i < n; i++)` | while the condition is true | A variable declared in the header is automatic and local to the loop. An x or z condition ends the loop (§12.7.1). |
| `repeat (n)` | n times | `n` is evaluated once, before the first pass. A negative, x or z count runs zero times (§12.7.2). |
| `while (cond)` | zero or more times | The condition is tested before each pass (§12.7.4). |
| `do … while (cond);` | one or more times | The condition is tested after each pass (§12.7.5). |
| `foreach (arr[i])` | once per element | Loop variables are automatic and read-only, typed like the index. Do not resize the array inside the loop (§12.7.3). |
| `forever` | until disabled or the run ends | Needs a timing control, or simulated time stops (§12.7.6). |

A traced example with both jumps:

```systemverilog
// snippet
for (int i = 0; i < 5; i++) begin
  if (i == 1) continue;        // skip the rest of this pass, then run i++
  if (i == 3) break;           // leave the loop at once
  $display("i = %0d", i);
end
```

| Pass | `i` | `i == 1` | `i == 3` | Prints |
|---|---|---|---|---|
| 1 | 0 | no | no | `i = 0` |
| 2 | 1 | yes: `continue` | not tested | nothing |
| 3 | 2 | no | no | `i = 2` |
| 4 | 3 | no | yes: `break` | nothing |
| none | 4 | not reached | not reached | the loop has ended |

Three more one-line traces to remember:

- `repeat (n)` while `n` is still x: zero passes, and no message.
- `while (0) …` runs zero passes; `do … while (0);` runs exactly one.
- `forever x = ~x;` with no timing control loops forever at one simulation time, so time never advances.

### break, continue and return

- `continue` jumps to the end of the loop body and runs the loop's step; `break` leaves the loop (§12.8). Both are legal only inside a loop.
- In a multi-dimensional `foreach`, `break` leaves the whole loop, not just the innermost dimension, and `continue` moves to the next combination of indices (§12.8).
- Neither can reach a loop outside a `fork … join`: a child process cannot break its parent's loop (§12.8).
- `return` leaves a task or function, not a loop. F2D covers it: [Tasks and Functions](/curriculum/T1_Foundational/F2D_Reusable_Code_and_Parallelism/tasks-functions).

### Testbench patterns

These are the loops a directed testbench uses every day:

```systemverilog
// snippet
initial begin                       // clock: set a start value, then toggle
  clk <= 1'b0;                      // <= at time 0, like the standard's own example
  forever #5 clk = ~clk;            // a forever loop always needs a timing control
end

task automatic drive_bus();
  repeat (10) @(posedge clk);       // wait for 10 rising edges
  enable <= 1'b1;                   // <=: the DUT samples the old value on this edge
endtask

task automatic wait_ready(input int max_cycles, output bit ok);
  int n = 0;                        // automatic task: an initializer is fine here
  while (ready !== 1'b1 && n < max_cycles) begin
    @(posedge clk);                 // poll once per clock, never in zero time
    n++;
  end
  ok = (ready === 1'b1);            // === so that an x ready counts as not ready
endtask

initial begin                       // visit every expected value in a queue
  foreach (expected_q[i])
    $display("expected_q[%0d] = %0h", i, expected_q[i]);
end
```

`wait_ready` polls a level once per clock and gives up after `max_cycles`, so a DUT that never answers ends the loop instead of hanging the test. When you wait for an event instead of polling a level, use the isolation wrapper from the previous lesson. Queues and dynamic arrays are F2B's topic: [Dynamic Data Structures](/curriculum/T1_Foundational/F2B_Dynamic_Structures/index).

### Pitfalls and misconceptions

| Misconception | Why it is wrong |
|---|---|
| "`unique` is only a synthesis hint." | Simulators must check it and report violations (§12.5.3). |
| "A `default` makes a `unique case` safer." | The `default` matches every leftover value, so the no-match check can never fire (§12.5.3, NOTE). |
| "`priority` means first match wins, and a plain `case` does not." | A plain `case` also runs the first match (§12.5). `priority` adds the no-match report and allows overlaps. |
| "A `case` with no matching item reports something." | A plain `case` silently runs nothing (§12.5). |
| "`if (a)` with `a` = x is undefined." | It is defined: x is false, so `else` runs (§12.4). |
| "`casex` is fine for don't-care decoding." | It also skips x bits in the select, so an unknown select runs a real branch (§12.5.1). Use `case … inside` or `casez`. |
| "`repeat (n)` with an unknown `n` runs some arbitrary number of times." | It runs zero times, silently (§12.7.2). |
| "A `forever` loop without a delay is fine in a testbench." | Simulated time stops (§12.7.6). |

### Recap

- An x or z condition is false: `if` takes `else`, and `!x` is still x.
- `case` matches all four values exactly, runs the first match, and does nothing when nothing matches; `casez` and `casex` skip don't-care bits on both sides.
- `unique` reports overlaps and no match, `unique0` overlaps only, `priority` no match only; a `default` removes the no-match report.
- `case … inside` treats x and z as wildcards only in the items, so an unknown select does not match.
- Count loop passes from the rules: `repeat` evaluates its count once, x gives zero passes, `do … while` runs at least once, and `forever` needs a timing control.

## Make It Work

### Worked example: a traffic-light controller and its self-checking bench

The controller cycles red, green and yellow, holding each state for a number of clock edges set by a down-counter. Its decoders use `unique case` without a `default`, and the bench checks the light at every edge against an expected sequence. Read the code, then the walk-through.

```systemverilog
// compile
// traffic_light_tb.sv: a traffic-light controller and its bench in one file.

module traffic_light (
  input  logic       clk,
  input  logic       rst_n,      // active-low asynchronous reset
  output logic [2:0] light       // {red, yellow, green}
);
  timeunit 1ns;                  // if one module in a design declares a time unit,
  timeprecision 1ps;             // every module must (§3.14.2.3)

  typedef enum logic [1:0] {RED, GREEN, YELLOW} state_t;
  state_t     state, next_state;
  logic [3:0] timer;             // edges left in this state, counting down to 0

  // Next state: move on when the timer reaches 0.
  always_comb begin
    next_state = state;          // seed: assigned on every path, so no latch
    unique case (state)          // no default: an x or illegal state is reported
      RED:    if (timer == 4'd0) next_state = GREEN;
      GREEN:  if (timer == 4'd0) next_state = YELLOW;
      YELLOW: if (timer == 4'd0) next_state = RED;
    endcase
  end

  // Output decode.
  always_comb begin
    light = 3'b100;              // seed with red, the safe value
    unique case (state)
      RED:    light = 3'b100;
      GREEN:  light = 3'b001;
      YELLOW: light = 3'b010;
    endcase
  end

  // State and timer registers.
  always_ff @(posedge clk or negedge rst_n) begin
    if (!rst_n) begin
      state <= RED;
      timer <= 4'd3;             // red lasts 4 edges: timer 3, 2, 1, 0
    end else if (next_state != state) begin
      state <= next_state;
      unique case (next_state)   // load the length of the new state
        RED:    timer <= 4'd3;
        GREEN:  timer <= 4'd2;
        YELLOW: timer <= 4'd0;
      endcase
    end else begin
      timer <= timer - 4'd1;
    end
  end
endmodule

module tb_top;
  timeunit 1ns;
  timeprecision 1ps;

  logic       clk;
  logic       rst_n;
  logic [2:0] light;
  int         pass_count, fail_count;   // 2-state: they start at 0

  // The light expected at each rising edge after reset is released:
  // red for 4 edges, green for 3, yellow for 1, then red again.
  logic [2:0] expected_light [12] = '{3'b100, 3'b100, 3'b100, 3'b100,
                                      3'b001, 3'b001, 3'b001,
                                      3'b010,
                                      3'b100, 3'b100, 3'b100, 3'b100};

  traffic_light dut (.clk(clk), .rst_n(rst_n), .light(light));

  initial begin
    clk <= 1'b0;                 // <= at time 0, like the standard's own clock example
    forever #5 clk = ~clk;       // rising edges at 5, 15, 25, ... ns
  end

  // Report every change of the light once reset is over.
  always @(light)
    if (rst_n === 1'b1) $display("t=%0d ns: light=%b", $time, light);

  initial begin
    rst_n <= 1'b0;               // assert reset at time 0 with <=
    repeat (2) @(posedge clk);
    rst_n <= 1'b1;               // release just after an edge
    foreach (expected_light[i]) begin
      @(posedge clk);            // light is stable here: it changes after NBA updates
      if (light !== expected_light[i]) begin
        fail_count++;
        $error("edge %0d: light=%b, expected %b", i, light, expected_light[i]);
      end else begin
        pass_count++;
      end
    end
    @(negedge clk);              // let the last edge's updates and prints finish
    $finish;
  end

  final $display("PASS=%0d FAIL=%0d", pass_count, fail_count);
endmodule
```

How it works, step by step:

1. **Seeded decoders.** Both `always_comb` blocks assign their output before the `case`, so every path assigns it. The `unique case` has no `default`, so a `state` that matches no item is reported instead of silently decoded.
2. **No report at time 0.** Before reset, `state` is x and both decoders match nothing. The bench drives `rst_n` with `<=` at time 0, so the flop resets `state` within time slot 0, the decoders run again, and the queued reports are discarded before they mature.
3. **The timer.** On a change of state, the `always_ff` loads the new state's length through a `unique case` on `next_state`; otherwise it counts `timer` down. A state lasts one edge more than the value loaded: red 4, green 3, yellow 1.
4. **The clock.** A `forever` loop with a delay toggles `clk`, and its time-0 start value is set with `<=`.
5. **Checking.** `foreach` visits the 12 expected values, one per rising edge, and compares with `!==`, so an x light fails the check. At the rising edge, `light` still holds the value decoded after the previous edge, and the DUT updates it later in the time slot.
6. **Logging.** `always @(light)` prints every change once reset is over: after edges 3, 6, 7 and 11, at 55, 85, 95 and 135 ns.
7. **Ending.** After the last check, the bench waits for a falling edge so the change at 135 ns is printed, then calls `$finish`, and `final` prints the summary.

## Push Further

### Expert: When violation reports appear, and how to control them

- **Deferred, then confirmed.** A `unique`, `unique0` or `priority` check runs when the statement executes, but the report waits in a per-process queue for the Observed region of that time slot (§12.4.2.1, §12.5.3.1). If the procedure resumes after an event control or `wait` first, or an `always_comb` or `always_latch` is re-triggered by an input change, the queued report is discarded. These are the flush points. A zero-delay glitch that re-runs the procedure therefore produces no report, while the result of the procedure's last run in the time slot matures in the Observed region and can no longer be flushed.
- **Per process.** A report belongs to the process that executed the check. A function containing a `unique if`, called by two `always_comb` blocks, can report twice in one time slot, once per caller (§12.4.2.2, §12.5.3.2).
- **Compile time is allowed.** A tool may report a violation at compile time if it can already prove it; otherwise it reports at run time (§12.5.3).
- **Controlling the reports.** The assertion control tasks also control these reports (§20.11). `$assertcontrol(4, 224)` turns reporting off for unique (32), unique0 (64) and priority (128) checks, and `$assertcontrol(3, 224)` turns it on again (Tables 20-5 and 20-6). `$assertoff` does **not** reach them: it is defined as `$assertcontrol(4, 15, 7)`, which covers concurrent and immediate assertions only.
- **A time-0 corner.** At time 0, a decoder's `always_comb` may run before the `initial` block that calls `$assertcontrol(4, 224)`, because procedures start in no promised order (§9.2). The standard does not say whether Off discards a violation report that is already queued (for deferred assertions, queued reports may still mature), so whether that one report still appears is tool-dependent. Every check after the call is silenced.
- **Wording and severity are tool-specific.** Make your regression scripts treat the report as an error. Adding a `default` to silence it hides real bugs.

```systemverilog
// snippet
initial begin
  $assertcontrol(4, 224);          // Off: unique, unique0 and priority reports
  @(posedge rst_n);                // wait for the end of reset
  $assertcontrol(3, 224);          // On again for the rest of the test
end
```

### Expert: X and the case family

- **Don't-cares on both sides.** `casez` and `casex` skip don't-care bits in the case expression as well as in the items (§12.5.1). So `unique casex (sel)` with `sel` = 2'b1x and the items 2'b10 and 2'b11 finds **two** matches: it runs the 2'b10 item and reports an overlap.
- **`case inside` is asymmetric.** An x, z or `?` in an item is a wildcard; an x or z in the case expression is not (§11.4.6). The standard's own example uses `priority case (status) inside` with the item `3'b0?0`, which matches 'b000, 'b010, 'b0x0 and 'b0z0; values such as 'b00x and 'bxxx match no item and are reported (§12.5.4). An x in the select is accepted only where the item has a wildcard.
- **Detecting x on purpose.** A plain `case` compares x and z literally, so `case (sig) 1'bz: … 1'bx: … default: … endcase` can tell a floating signal from an unknown one (§12.5).
- **Item evaluation order.** In `unique` and `unique0` forms, items may be evaluated and compared in any order, so item expressions with side effects give nondeterministic results (§12.5.3). One item that lists several expressions which all match is not an overlap.
- **Synthesis is tool-dependent.** How synthesis tools read `unique`, `unique0` and `priority`, and the older `full_case` and `parallel_case` pragmas, is tool-dependent: the standard defines only the simulation checks. In intent, `unique` corresponds to both pragmas together, `unique0` to `parallel_case` alone and `priority` to `full_case` alone.

### Expert: Loop corner cases

- **for:** a variable declared in the header is automatic and lives in an implicit block around the loop. Declare either all or none of the control variables in the header. Two parallel loops that share one module-level control variable can corrupt each other's count, which header declarations prevent (§12.7.1).
- **repeat:** the count is evaluated once; a negative, x or z count runs zero times (§12.7.2). Signedness decides what "negative" means: a 4-bit unsigned variable holding 4'b1101 is 13, not −3.
- **foreach:** loop variables are automatic and read-only, take the type of the index, and with several indices the rightmost one changes fastest. Resizing the array inside the loop gives undefined results (§12.7.3).
- **while and do … while:** a `while` loop may run zero times; a `do … while` loop always runs at least once (§12.7.4, §12.7.5).
- **forever:** without a timing control it is a zero-delay infinite loop, and simulated time never advances (§12.7.6). `while (1)` without a timing control behaves the same.
- **break in foreach:** in a multi-dimensional `foreach`, `break` leaves the whole loop, and `continue` moves to the next index combination (§12.8).

### Kata C (guided): make the decoder complain

**Objectives 1 and 2.** A `unique case` decoder sees an unknown select at time 0. Predict what happens, then change the qualifier and the items and predict again.

```systemverilog

module tb_top;
  timeunit 1ns;
  timeprecision 1ps;

  logic [1:0] sel;                 // not assigned until t = 10 ns, so x before that
  logic [3:0] y;

  always_comb begin
    y = 4'b0000;                   // seed: y is assigned on every path
    unique case (sel)              // no default
      2'b00: y = 4'b0001;
      2'b01: y = 4'b0010;
      2'b10: y = 4'b0100;
      2'b11: y = 4'b1000;
    endcase
  end

  initial begin
    #10 sel = 2'b01;
    #1  $display("t=%0d sel=%b y=%b", $time, sel, y);
    $finish;
  end
endmodule
```

1. Predict: at t = 0, which item runs, what is `y`, and is a violation reported? Then run it.
2. Add `default: y = 4'b0000;` and predict again. Explain why the report disappears.
3. Remove the `default` and change `unique` to `unique0`. Predict again.
4. Change the decision to `unique case (sel) inside` with two items, `2'b0?: y = 4'b0011;` and `2'b1?: y = 4'b1100;`. Then make the `initial` block drive `sel = 2'b1x;` at 10 ns and `sel = 2'bx1;` at 20 ns, printing `y` after each. Predict `y`, and any report, for both values.

<details>
<summary>Worked solution</summary>

1. At t = 0, `always_comb` runs once with `sel` = 2'bxx. A plain comparison treats x literally, so no item matches: no item runs, `y` keeps its seed 4'b0000, and `unique` queues a no-match violation. Nothing runs the block again before time slot 0 ends, so the report appears at t = 0, worded the way your simulator words it. At t = 10 ns `sel` = 01 selects the second item, so the log ends with `t=11 sel=01 y=0010`.
2. With a `default`, every value matches something, so there is no no-match violation. The report disappears, and so does your detector for an unknown select (§12.5.3).
3. `unique0` never reports a missing match, so it is silent too. It would still report an overlap.
4. `2'b1x` matches `2'b1?`: the item's `?` makes bit 0 a wildcard, so the select's x in that bit is accepted, and `y` = 4'b1100 with no report. Nothing runs, `y` stays 4'b0000, and `unique` reports a violation at 20 ns (§12.5.4, §11.4.6). The time-0 report remains too, because 2'bxx matches neither item.

### Debug challenge D: the enable that arrived early

**Objectives 3 and 4.** A counter should start counting on the eleventh rising edge after reset is released. Depending on process order, it can start one edge early.

```systemverilog
// compile
module counter (
  input  logic       clk,
  input  logic       rst_n,
  input  logic       enable,
  output logic [7:0] count
);
  timeunit 1ns;                    // every module declares a time unit (§3.14.2.3)
  timeprecision 1ps;

  always_ff @(posedge clk or negedge rst_n)
    if (!rst_n)      count <= '0;
    else if (enable) count <= count + 8'd1;
endmodule

module tb_top;
  timeunit 1ns;
  timeprecision 1ps;

  logic       clk = 1'b0;
  logic       rst_n, enable;
  logic [7:0] count;

  counter dut (.clk(clk), .rst_n(rst_n), .enable(enable), .count(count));

  always #5 clk = ~clk;            // rising edges at 5, 15, 25, ... ns

  task automatic drive_bus();
    repeat (10) @(posedge clk);    // wait for 10 rising edges
    enable = 1'b1;                 // the suspect line
  endtask

  initial begin
    rst_n  <= 1'b0;
    enable <= 1'b0;
    @(posedge clk);
    rst_n  <= 1'b1;                // release reset just after the first edge
    drive_bus();
    repeat (3) @(posedge clk);
    #1 $display("t=%0d count=%0d", $time, count);
    $finish;
  end
endmodule
```

1. `drive_bus` returns at the tenth rising edge after reset is released. At which time is that, and at which edge does the counter first count if the bench runs before the DUT at that edge? If the DUT runs first?
2. Predict both possible logs.
3. Fix the bench, not the DUT, and predict the one log every simulator must print.

<details>
<summary>Worked solution</summary>

1. Reset is released just after the edge at 5 ns, and `repeat (10)` counts the edges at 15, 25 … 105 ns, so `drive_bus` returns at 105 ns. Its blocking `enable = 1'b1;` runs in the Active region of that time slot, together with the DUT's flop. If the bench runs first, the flop already sees `enable` = 1 and counts at 105 ns. If the DUT runs first, it sees 0 and first counts at 115 ns (§4.7).
2. The three more edges end at 135 ns, and the print is at 136 ns. Bench first: counts at 105, 115, 125 and 135 ns, so the log is `t=136 count=4`. DUT first: counts at 115, 125 and 135 ns, so the log is `t=136 count=3`.
3. Drive with a nonblocking assignment, `enable <= 1'b1;`. The update now lands in the NBA region, after the flop has read the old value, so every simulator first counts at 115 ns and prints `t=136 count=3`. F3C traces this race step by step: [Delta Cycles and Race Conditions](/curriculum/T1_Foundational/F3C_Delta_Cycles_and_Race_Conditions/index).

</details>
