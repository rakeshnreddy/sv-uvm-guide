## Quick Take

- **What it is:** Two things every real testbench (TB) must survive without lying. **Reset in the middle of traffic:** the design under test (DUT) throws away the transfers it was working on, so every bench component must drop its own share of that work and the test must restart stimulus. **Error injection:** the test sends illegal stimulus on purpose (here, a request with bad parity) to prove the DUT detects it, and must then tell the expected error reports from real ones. This lesson adds both to the `mem` bench you built in [I-UVM-3C](/curriculum/T2_Intermediate/I-UVM-3C_First_Complete_Testbench/index).
- **Why it matters:** Chips reset in the middle of work (watchdogs, software resets, power events), and error paths (parity, ECC, error responses) are where bugs hide. A bench that is not reset-aware fails on a correct DUT, and the usual "fix", demoting every error during the test, then hides the real bugs too. The skill is to make reset and injected errors *accounted for*, not *tolerated*.
- **The Analogy:** A power cut in a restaurant kitchen during service. Each cook drops the dish in hand (the driver releases its item), the runner throws away half-plated dishes (the monitor discards the partial transfer), the inspector tears up the list of what each table is still owed (the scoreboard flushes), and the manager restarts service (the virtual sequence). Error injection is a mystery shopper who orders something deliberately wrong: the kitchen must refuse it, and the complaint that follows is expected, but only that complaint, from that table, that many times; every other complaint is real. *Where it breaks:* a real kitchen notices a power cut by itself, while every testbench component must be written to notice reset; and a report catcher is code that can silence any complaint at all, so it has to be written as narrowly as a list of named mystery shoppers.

**You will be able to:**
1. **Write** a reset-aware driver (stop, release the current item safely, wait for deassertion) and monitor (discard partial transactions), and **flush** the scoreboard's expectations on reset.
2. **Choose** a reset strategy (reset-aware `run_phase` threads, or run-time phase jumping and its hazards) and **write** a mid-test reset virtual sequence with `stop_sequences()` and `kill()`.
3. **Inject** errors with an error sequence, a factory override and a driver callback, and **account** for the expected errors in the scoreboard and the checkers.
4. **Demote** expected errors with a narrow report catcher (one ID, one reporter, a count) and **prove** that unexpected errors still fail the run.
5. **Plan** coverage of reset × state and error × response.

## Build Your Mental Model

### Words you need first

Terms from earlier lessons are linked; the new ones are defined here. The UVM features this lesson uses are sequence control (IEEE 1800.2-2020 §14.2.5.11, §15.3.2.14), callbacks (§10.7), the factory (§8) and report catchers (§6.6).

- **Reset, assert, release:** reset returns the DUT to a known state. This bench's reset, `rst_n`, is **active low**: it is *asserted* when 0 and *released* (deasserted) when 1. A **synchronous** reset acts only at a clock edge, like this lesson's DUT; an **asynchronous** reset acts the moment it changes.
- **Sampled value, time slot:** a clocking-block input holds the value its signal had just before the clock edge (input skew `#1step`), which is the value the DUT's flip-flops use at that edge; a time slot is all the activity at one simulation time ([F3B](/curriculum/T1_Foundational/F3B_Scheduling_Regions/index), [F4C](/curriculum/T1_Foundational/F4C_Clocking_Blocks/index)).
- **In flight, partial transaction:** a transfer that has started but not completed. Here: a request on the bus that the DUT has not yet accepted, or a request accepted whose response (`rdata`, `err`) has not yet been sampled.
- **Flush:** throw away stored items or expectations that can never be matched.
- **Error injection:** deliberately illegal stimulus, sent to check that the DUT detects and handles it. **Expected error:** an error report the test caused on purpose.
- **Protocol checker:** code that reports `` `uvm_error `` when the bus breaks a rule. Here it lives in the monitor.
- **Report catcher:** an object of a `uvm_report_catcher` subclass (IEEE 1800.2-2020 §6.6). The report server runs every registered catcher on each report *before* counting it; a catcher can change its severity, ID, message or action, pass it on (`THROW`), or swallow it (`CAUGHT`). **Demote** means lowering the severity, for example from `UVM_ERROR` to `UVM_INFO`: the message is still printed but no longer counted as an error ([I-UVM-1D](/curriculum/T2_Intermediate/I-UVM-1D_Reporting_and_Run_Control/index) shows where catchers sit in the report pipeline).
- **Virtual sequence:** a sequence that runs on no sequencer of its own and starts other sequences on the agents' sequencers ([I-UVM-3B](/curriculum/T2_Intermediate/I-UVM-3B_Advanced_Sequencing_and_Layering/index); applied to several agents in [A-UVM-8](/curriculum/T3_Advanced/A-UVM-8_Multi_Agent_Topologies/index)).
- **Run-time phases and phase jumps:** the twelve phases from `pre_reset_phase` to `post_shutdown_phase` that run beside `run_phase`, and `phase.jump()`, which ends a phase early and restarts the schedule elsewhere ([I-UVM-1C](/curriculum/T2_Intermediate/I-UVM-1C_UVM_Phasing/index)).
- **Callback** and **factory override:** hooks a component calls so a test can change its behaviour ([A-UVM-5](/curriculum/T3_Advanced/A-UVM-5_UVM_Callbacks/index)); replacing a type wherever the factory creates it ([I-UVM-1B](/curriculum/T2_Intermediate/I-UVM-1B_The_UVM_Factory/index)).
- **Parity:** one extra bit chosen so that the number of 1s is even. Flip any one bit and the parity is wrong, which is how hardware detects a corrupted request.
- **Mutant:** a copy of the code with one deliberate defect. A check you trust is one you have seen fail on a mutant.

### The bench you are extending

The DUT is I-UVM-3C's `mem_dut`, a 16-entry, 8-bit memory with a one-cycle request bus, with two additions and one rule made explicit:

| Signal or rule | Meaning |
|---|---|
| `par` (input, new) | Even parity over the request: a correct requester drives `par` equal to `^{we, addr, wdata}` on every request, reads included. |
| `err` (output, new) | 1 in the cycle after the edge that accepted a request with bad parity; the DUT then **ignores** that request (no write, `rdata` unchanged). Like `rdata`, it is sampled one edge after the accept. |
| `rst_n` (input) | Synchronous, active low. At an edge where `rst_n` is 0 the DUT accepts nothing, every location and `rdata` become `00`, and `err` becomes 0. |
| Reset and responses | A request is accepted only at an edge where `rst_n` is 1. Its response belongs to the next edge; if `rst_n` is 0 there, the transfer is **aborted** and its response is not valid. |

To control reset from a test, `rst_n` moves into a small interface, `rst_if`, with one clocking block; `tb_top` still applies the power-on reset. **Predict** before you read the caption: which component sees the reset first, and how does the scoreboard find out about it without touching any pin?

**Debrief.** Only the pins carry reset, so the components that read pins see it first: the driver through `drv_cb` and the monitor through `mon_cb`, at the same clock edge as the DUT. Nothing else touches a pin. The scoreboard learns about reset the way it learns about everything else, from the monitor: a second analysis port, `rst_ap`, publishes "reset asserted" and "reset released". The test acts on reset through the virtual sequence, which is also what *causes* the mid-test reset here. The catcher is attached to one reporter, the monitor, because that is the only component allowed to raise the expected error.

### What reset does to a transfer in flight

Reset can arrive at any edge, so at that edge every component holds some state. Each must react in its own way:

| Component | Holds at the reset edge | Must do |
|---|---|---|
| Driver | the item it took with `get_next_item()`, perhaps already on the pins | stop driving, give the item back with `item_done()`, wait until reset is released |
| Monitor | a request accepted at the previous edge whose response it has not seen | discard it (it is not a completed transfer), tell its subscribers that reset happened |
| Scoreboard | expectations: what the DUT still owes (here, what each address holds) | check what completed before reset, then forget what reset destroyed |
| Sequences | items they are waiting to send | be stopped, then restarted by whoever owns the scenario |
| Test | its objection | keep the run alive across the reset |

Here is the reset this lesson's test applies. Values are the ones **sampled at each rising edge**, which is what the clocking blocks and the DUT's flip-flops see; edge 0 is 225 ns and edge 6 is 285 ns. Before you read the markers, **predict**: at 245 ns a read of address 5 is on the bus and the read of address 4, accepted at 235 ns, still waits for its data. What happens to each?

**Debrief.** At 245 ns the read of address 5 was never accepted: the DUT was in reset at the edge that would have accepted it. The driver sees the same thing (it samples `rst_n` as 0 at that edge), so it gives the item back instead of reporting it done. The read of address 4 *was* accepted at 235 ns, and its data `4b` is even on the bus, but its response edge is 245 ns, where reset is asserted: by this protocol's rule the transfer is aborted, so the monitor discards it rather than publishing it. Neither read reaches the scoreboard, and the scoreboard does not expect them: its expectations about memory are flushed in the same time slot. Nothing is driven or published until reset is released.

### The reset-aware driver

The driver from I-UVM-3C waited for reset only once, at time 0. A reset-aware driver checks reset at every edge that matters, in one thread, so there is no race between "the item was accepted" and "reset arrived":

```systemverilog
// snippet: the core of mem_drv::run_phase (complete file in Make It Work)
vif.drv_cb.valid <= 1'b0;
wait_reset_released(vif);                      // do @(drv_cb) while rst_n !== 1
forever begin
  seq_item_port.get_next_item(req);
  if (vif.drv_cb.rst_n !== 1'b1) begin         // reset came while we waited
    release_item("before it was driven");
    wait_reset_released(vif);
    continue;
  end
  // ... drive valid, we, addr, wdata, par through drv_cb
  @(vif.drv_cb);                               // the accept edge
  vif.drv_cb.valid <= 1'b0;
  if (vif.drv_cb.rst_n !== 1'b1) begin         // reset won: not accepted
    release_item("reset at its accept edge");  // item_done(), counted, logged
    wait_reset_released(vif);
  end else begin
    seq_item_port.item_done();
  end
end
```

- **Stop.** `valid <= 0` is driven at every accept edge, so the bus goes idle during reset.
- **Release the current item safely.** `release_item()` calls `item_done()`. That is the only way to tell the sequencer the driver no longer holds the item. Skip it (and let nothing reset the sequencer meanwhile), and the next `get_next_item()` after reset reports `Get_next_item called twice without item_done or get in between` (uvm-core 2020.3.1, `uvm_sequencer.svh`) and hands back the *old* item.
- **Wait for deassertion.** `wait_reset_released()` waits for the first edge where `drv_cb` samples `rst_n` as 1, exactly as at time 0.
- **Why one thread.** A common alternative forks the drive loop against `@(negedge vif.rst_n)` and calls `disable fork`. For a synchronous reset that watches the wrong moment: the raw signal falls when reset is *driven* (here just after 235 ns), not at the edge where the DUT acts on it (245 ns); and when reset is driven at a clock edge, the watcher and the drive loop wake in the same time slot, in an order the simulator chooses. Checking the sampled `rst_n` after the accept edge decides acceptance exactly as the DUT does, once.

**Pitfall: releasing after the sequencer was reset.** The driver's `item_done()` and a test's `stop_sequences()` must not happen in the wrong order. See [the virtual sequence below](#the-mid-test-reset-virtual-sequence).

### The reset-aware monitor

The monitor now holds *every* request for one edge, because `err` (like `rdata`) is sampled one edge after the accept. On reset it drops what it holds and says so:

```systemverilog
// snippet: the reset branch of mem_mon::run_phase (complete file in Make It Work)
@(vif.mon_cb);
if (vif.mon_cb.rst_n !== 1'b1) begin
  if (!in_reset) begin                       // the first edge of a new reset
    in_reset = 1;
    if (pending != null) n_discarded++;      // accepted, but no response yet
    rst_ap.write(MEM_RST_ASSERTED);          // subscribers flush now
  end
  pending = null;                            // a partial transfer is not a transfer
  continue;
end
if (in_reset) begin
  in_reset = 0;
  rst_ap.write(MEM_RST_RELEASED);
end
// ... publish pending with its response; capture a new request; check its parity
```

- **Discard partial transactions.** A transfer exists for the checkers only when it completes. Publishing the half-seen read of address 4 would make the scoreboard compare `4b` against a memory the DUT has just cleared.
- **Publish reset as an event.** `rst_ap` is a `uvm_analysis_port #(mem_rst_e)`, where `mem_rst_e` is an enum with `MEM_RST_ASSERTED` and `MEM_RST_RELEASED`. Subscribers stay pin-free, and a passive copy of the agent tells its scoreboard about reset the same way.
- **Nothing during reset.** Requests seen while `rst_n` is 0 are never captured, so they are never predicted.

### An asynchronous reset is watched outside the clocking block

This bench's DUT resets synchronously, so sampling `rst_n` through `drv_cb` and `mon_cb` sees exactly what the DUT sees, without races. A DUT with an **asynchronous** reset reacts as soon as `rst_n` falls, possibly between edges, and its clock may even stop while reset is held. A clocking block only samples at its clocking event (IEEE 1800-2023 §14.13), so it would see the reset late, or never. Watch the raw signal instead:

```systemverilog
// snippet: monitor loop for a DUT with an asynchronous reset (not this bench's DUT)
forever begin
  wait (vif.rst_n === 1'b1);             // release: the level, on the raw signal
  fork
    collect();                           // the clocked loop through mon_cb
    @(negedge vif.rst_n);                // assertion: at once, clock or no clock
  join_any
  disable fork;                          // stop collect() in the middle of a transfer
  discard_partial_and_publish_reset();
end
```

`@(negedge vif.rst_n)` is an event control on the signal itself (§9.4.2), so it fires when the reset is asserted, whatever the clock does. `disable fork` is safe here because no sequence runs below the monitor (§9.6.3 kills every descendant of the calling process). Assertions follow the same rule: the disable condition of `disable iff (!rst_n)` uses the current value of `rst_n`, not the sampled one (§16.5, §16.12), so a concurrent assertion is cut off at once on an asynchronous reset. The release is usually synchronized inside the DUT, so the monitor resumes sampling at the next clocking event.

Here is the difference traced for an example DUT with an asynchronous reset whose clock is gated off (stopped) while reset is held. Reset falls at 238 ns, between two edges; the clock stops until reset is released at 268 ns and restarts with an edge at 275 ns. A request was accepted at 235 ns.

| Time | raw `rst_n` | `clk` | `mon_cb.rst_n` (last sampled value) | `@(negedge vif.rst_n)` | Monitor that only reads `mon_cb` | Monitor with the raw-signal watcher |
|---|---|---|---|---|---|---|
| 235 ns | 1 | rising edge | 1 | waiting | holds the request accepted at 235 ns | same |
| 238 ns | 1 → 0 | stops | still 1: no edge, no sample | **fires** | waits at `@(vif.mon_cb)`, unaware | `disable fork` stops `collect()`; the partial transfer is discarded; reset is published |
| 238–268 ns | 0 | no edges | 1, stale | done | still waiting | waits for `rst_n === 1` |
| 268 ns | 0 → 1 | still stopped | 1 | waiting again | still waiting | `wait` returns; `collect()` restarts |
| 275 ns | 1 | first edge | 1 | waiting | wakes, sees `rst_n` 1, never learns of the reset, and publishes the 235 ns request with post-reset data | samples normally |

The clocking-block monitor is not one cycle late: it misses the reset completely, and publishes a transfer the DUT aborted.

**The driver for an asynchronous reset.** The same rule applies to the driver. The driver shown above learns about reset only at `@(vif.drv_cb)`; with a gated clock it can sit at that edge through a whole reset and wake with `rst_n` already released. A driver for an asynchronous reset races its drive against the raw signal, and keeps `get_next_item()` outside the fork so that a kill never lands inside a sequencer call:

```systemverilog
// snippet: drive loop for a DUT with an asynchronous reset (not this bench's DUT)
forever begin
  seq_item_port.get_next_item(req);
  if (vif.rst_n === 1'b1) begin
    fork
      drive_one(req);                    // through drv_cb, returns after the accept edge
      @(negedge vif.rst_n);              // assertion: at once, clock or no clock
    join_any
    disable fork;                        // stop drive_one() wherever it was
  end
  seq_item_port.item_done();             // accepted or abandoned: give the item back
  if (vif.rst_n !== 1'b1) begin
    vif.drv_cb.valid <= 1'b0;            // idle the bus at the next clocking event
    wait (vif.rst_n === 1'b1);
  end
end
```

A clocking-block drive takes effect only at a clocking event (§14.16), so the idle value reaches the pins when the clock runs again; that is enough here because the DUT ignores its inputs while it is in reset. The virtual sequence must still let the driver release its item before it calls `stop_sequences()`.

**Drivers that hold more than one item.** A pipelined driver uses `get()`, which reports the item done at once, and answers later with `put()`; a sequence that wants the answer blocks in `get_response()`. On reset such a driver holds several outstanding items and owes each one a response. Either `put()` a response marked as aborted for every outstanding item, so that each waiting `get_response()` returns, or kill the waiting sequences before the restart: `stop_sequences()` also removes the responses already queued (§15.3.2.14). A sequence left waiting for a response that will never come keeps the run alive until the timeout.

### Flushing the scoreboard: expectations, not observations

**Misconception: "pending expectations survive reset."** They do not. Reset destroys the DUT state those expectations describe. Every scoreboard holds some of them:
- a **queue-based** scoreboard (the reference-model form of [A-UVM-6](/curriculum/T3_Advanced/A-UVM-6_Scoreboards_and_Reference_Models/index)) queues *predictions* for responses that have not yet arrived; reset means they never will, so `check_phase` would report them missing;
- a **state-based** scoreboard like `mem_sb` keeps a model of DUT state, `model[16]`; after reset the DUT's memory is all `00`, so the model must be too, or the next reads mismatch.

Observations are different. Transfers that *completed* before reset and still sit in the scoreboard's analysis FIFO are real, and must be checked, not thrown away:

```systemverilog
// snippet: mem_sb's reset handling (complete file in Make It Work)
virtual function void write_rst(mem_rst_e e);  // from agt.rst_ap, at the reset edge
  if (e == MEM_RST_ASSERTED) flush_on_reset();
endfunction

protected function void flush_on_reset();
  mem_item t;
  while (item_fifo.try_get(t)) check_item(t);  // completed before reset: still check
  foreach (model[i]) model[i] = '0;            // the spec's reset value, not "unknown"
  n_resets++;
  `uvm_info("SCB_RESET", "reset: expectations flushed, model cleared to 00", UVM_LOW)
endfunction
```

`write_rst()` is the second `write()` a scoreboard needs: `` `uvm_analysis_imp_decl(_rst) `` (Annex B.5.22) declares a class `uvm_analysis_imp_rst` whose `write()` calls `write_rst()` on its owner. For a queue-based scoreboard, the same function deletes the prediction queues and calls `flush()` on any FIFO of *predictions* (§12.2.8.2.6), counting what it threw away so that a reset that discards too much stays visible. Reset the model to what the **specification** says reset does, not to whatever the RTL happens to do.

### Choosing a reset strategy

There are two ways to organize the reaction to a mid-test reset.

| | Reset-aware `run_phase` threads (this lesson) | Run-time phase jumping |
|---|---|---|
| How | Drivers, monitors and scoreboards notice reset themselves (above); the test or a virtual sequence stops and restarts stimulus. `run_phase` never ends early. | On reset, `phase.jump(uvm_reset_phase::get())` ends the current run-time phase (say `main_phase`) and restarts the schedule at `reset_phase` (IEEE 1800.2-2020 §9.3.1.9.1; `uvm_domain::jump`, §9.4.2.4). |
| Who must cooperate | Every component, through its own reset handling | Every component that uses the run-time phases, which must re-run `reset_phase`, `configure_phase` and `main_phase` correctly |
| Drivers and monitors | Handle reset in `run_phase` | **Still** handle reset in `run_phase`: it runs in parallel to the run-time phases (§9.8.1.5) and a jump does not touch it |
| Sequences | Stopped explicitly (`kill()`, `stop_sequences()`) at a chosen moment | Killed with the jumping phase's processes (Annex F.2.5.2: "All processes related to phase are being killed"), wherever they were |
| Objections | The test's objection spans the reset | The jumping phase's objections are cleared (uvm-core 2020.3.1, `uvm_phase_hopper.svh`) |

**Misconception: "phase jumping is the standard reset technique."** Phase jumping is in the standard, but it is not how you make a bench reset-aware: it does nothing for the `run_phase` threads that actually touch the pins, it kills sequences at an arbitrary point (with the driver perhaps holding their item), and it works only if every component, including third-party verification IP (VIP), implements the run-time phases and can safely run them twice. The mechanics are in [I-UVM-1C](/curriculum/T2_Intermediate/I-UVM-1C_UVM_Phasing/index) (its expert item on domains, `sync` and phase jumps has the picture). This course's recommendation is reset-aware `run_phase` components plus a test-level restart, which works with any VIP that is itself reset-aware; use jumping only inside a bench whose components were all designed for it.

```systemverilog
// snippet: phase jumping on reset, for comparison only (this bench does not use it)
virtual task main_phase(uvm_phase phase);
  mem_wr_rd_seq seq = mem_wr_rd_seq::type_id::create("seq");
  phase.raise_objection(this);
  fork
    seq.start(env.agt.sqr);
    begin
      @(negedge rst_vif.rst_n);
      phase.jump(uvm_reset_phase::get());  // main ends now; schedule resumes at reset
    end
  join_any
  phase.drop_objection(this);
endtask
```

The jump is not immediate: `jump()` only sets flags, and the phase ends when the phaser next processes it (uvm-core logs `PH_JUMP` at `UVM_MEDIUM`). When it does, the thread running `seq.start()` is killed, so `seq` dies wherever it was. This snippet drops its own objection as soon as `jump()` returns; any objection still raised in the phase is cleared rather than dropped.

### The mid-test reset virtual sequence

In this bench the virtual sequence both causes the reset and restarts traffic, so it controls the order. The order is the whole point:

```systemverilog
// snippet: mem_reset_err_vseq::body (complete file in Make It Work)
fork
  traffic.start(sqr, this);           // a child: stop_sequences() and kill() reach it
join_none
repeat (rst_edge) @(rst_vif.cb);      // rst_edge = 24: the 235 ns edge
rst_vif.cb.rst_n <= 1'b0;             // sampled 0 from the next edge
repeat (2) @(rst_vif.cb);             // the driver releases its item at the first one
sqr.stop_sequences();                 // the sequencer back to idle: traffic is killed
@(rst_vif.cb);
rst_vif.cb.rst_n <= 1'b1;             // released after three edges in reset
errs.start(sqr, this);                // new sequence objects after reset
again.start(sqr, this);
```

`stop_sequences()` (IEEE 1800.2-2020 §15.3.2.14) "tells the sequencer to kill all sequences and child sequences currently operating on the sequencer, and remove all requests, locks, and responses that are currently queued". `kill()` (§14.2.5.11) does the same for one sequence and its children, on its default sequencer. **Predict** before you read the diagram: why does the virtual sequence wait until 255 ns, one edge *after* reset is first sampled, before calling `stop_sequences()`?

**Debrief.** At 245 ns the driver and the virtual sequence wake at the same clock edge, in an order the simulator chooses. In uvm-core 2020.3.1, `uvm_sequencer::stop_sequences()` also empties the request FIFO, which still holds the item the driver took (`uvm_sequencer.svh`). If it ran first at 245 ns, the driver's `item_done()` that follows would find nothing: `UVM_FATAL ... [SQRBADITMDN] Item_done() called with no outstanding requests.` Waiting one edge makes the order certain. Three more rules hold the scenario together:
- **New objects after reset.** `errs` and `again` are fresh sequence objects. Restarting the killed `traffic` would restart its body from the beginning, which is rarely what the scenario means, and uvm-core's own source calls reusing a sequence object "not recommended" (`uvm_sequence_base.svh`).
- **Children, not orphans.** `start(sqr, this)` makes each sequence a child of the virtual sequence, so `vseq.kill()` would stop all of them too (uvm-core's `m_kill()` kills every child).
- **Objections across reset.** The test raises its objection before starting the virtual sequence and drops it when the virtual sequence returns, so the run can never end during the reset. Never raise objections inside sequences you will kill: `kill()` drops the *automatic* objection (§14.2.4.4), but uvm-core's `stop_sequences()` does not drop it for a top-level sequence, and an objection raised by hand in a killed thread is never dropped; the run then ends at the timeout.

`kill()` versus `stop_sequences()`: use `kill()` on the sequences the scenario owns, and `stop_sequences()` when the sequencer as a whole must go back to idle, for example when other code may have started sequences on it. With `kill()`, the reset step of the same virtual sequence looks like this:

```systemverilog
// snippet: mem_reset_err_vseq::body with traffic.kill() instead of sqr.stop_sequences()
repeat (rst_edge) @(rst_vif.cb);      // the 235 ns edge
rst_vif.cb.rst_n <= 1'b0;             // sampled 0 from the next edge
@(rst_vif.cb);                        // 245 ns: the driver releases the read of 5 here too
traffic.kill();                       // traffic and its children only; the FIFO is untouched
repeat (2) @(rst_vif.cb);
rst_vif.cb.rst_n <= 1'b1;             // released at 265 ns, as before
errs.start(sqr, this);                // new sequence objects, as before
again.start(sqr, this);
```

`kill()` removes the sequence's queued requests and locks but does not empty the request FIFO (§14.2.5.11; uvm-core 2020.3.1 `uvm_sequencer_base.svh`), so the driver's `item_done()` finds its item whichever of the two runs first at 245 ns. That is why this variant may kill one edge earlier. A sequence started with no parent and no handle in the scenario cannot be reached this way; that is the case for `stop_sequences()`, after the driver has released its item.

**A reset agent instead of a raw interface.** This bench drives `rst_n` from the virtual sequence through a raw virtual interface, because it has one reset and one agent. Many production benches use a small reset agent instead: a driver for the reset pins, and reset sequences started on its sequencer like any other stimulus, so a virtual sequence coordinates reset with the same `start()` calls. Prefer the agent when the reset is reused across benches, when there are several reset domains, or when reset needs its own monitor and coverage.

### Injecting errors: three ways in

Injected errors need a knob in the stimulus. `mem_item` gets a random bit `par_err` with a **soft** default of 0 (`constraint c_par_ok { soft par_err == 0; }`), and `post_randomize()` sets `par = good_par() ^ par_err`, where `good_par()` returns `^{we, addr, wdata}`. Three mechanisms then set the knob, each at a different level:

| Mechanism | What changes | Best for | Code |
|---|---|---|---|
| **Error sequence** | A sequence sends chosen illegal items | Directed scenarios: exactly these errors, at these points, with checks around them | `mem_par_err_seq`: a bad-parity write to address 2, a read of address 2 (must still be `00`), a bad-parity read of address 3 |
| **Factory override** | Every `mem_item` the factory creates becomes an error-capable `mem_err_item` | Random error density, with no sequence edits, in sequences that randomize their items (`mem_rand_seq`); it does nothing where items are filled in by hand (`mem_wr_rd_seq::send()` never calls `randomize()`) | `mem_item::type_id::set_type_override(mem_err_item::get_type());` (§8.2.4.2.5) |
| **Driver callback** | The driver corrupts an item just before driving it | Errors at the pin level, below any sequence: every Nth request, or only on one agent instance | `uvm_callbacks#(mem_drv, mem_drv_cb)::add(env.agt.drv, flip);` (§10.7.2.3.1) |

The callback hook is one line in the driver, `` `uvm_do_callbacks(mem_drv, mem_drv_cb, pre_drive(this, req)) `` (Annex B.4.3), called after the reset check and before the drive. The mechanics of callbacks are [A-UVM-5](/curriculum/T3_Advanced/A-UVM-5_UVM_Callbacks/index)'s; here is the use:

```systemverilog
// snippet: in a test's start_of_simulation_phase (classes in Make It Work)
mem_par_flip_cb flip = mem_par_flip_cb::type_id::create("flip");
flip.every = 8;                                         // every 8th request
uvm_callbacks#(mem_drv, mem_drv_cb)::add(env.agt.drv, flip);
```

**Pitfall: a soft default that silently wins.** Suppose `mem_err_item` added `constraint c_inject { par_err dist {1 := 1, 0 := 7}; }`, a constraint with a *new* name. The base's `soft par_err == 0` does not conflict with it, because "nonzero distribution weights do not change the solution space" (IEEE 1800-2023 §18.5.3), and a soft constraint is discarded only when it conflicts (§18.5.13). So `par_err` stays 0 and no error is ever injected. `mem_err_item` therefore *replaces* the base constraint by giving its own the same name, `c_par_ok` (§18.5.2). Whatever mechanism you use, check from the log that errors were actually injected.

### Expected errors in the scoreboard and the checkers

An injected error touches two kinds of checking, and both must expect it:

- **The scoreboard predicts the error response.** `mem_sb` computes `exp_err = (t.par != t.good_par())` for every observed request, independently of how the error was injected. It reports `SCB_ERR_RSP` if the DUT's `err` differs from that prediction in either direction (a missed error and a spurious error are both DUT bugs), and a rejected request leaves the model unchanged. That is how the read of address 2 after the rejected write proves the write was really dropped. It counts `n_err_expected` and `n_err_seen`.
- **The protocol checker fires, correctly.** The monitor's parity check reports `` `uvm_error("MEM_PARITY", ...) `` on every request with bad parity. During injection that report is *expected*, but the check is right: on any other day, bad parity means a broken requester. Turning the check off for the injection test would also hide a requester that sends bad parity by accident. Instead, the test accounts for the expected reports with a narrow catcher.

**Accounting means three numbers agree** at the end of the test: the errors the test planned to inject (2), the bad-parity requests the scoreboard saw and saw rejected (`n_err_expected`, `n_err_seen`), and the reports the catcher demoted (`n_demoted`). If the checker missed an injected error, or a reset swallowed one, or the catcher demoted one too many, the counts disagree and the test reports `ERR_ACCOUNT`. When the number of injections is random (a callback or an override), the planned number is the injector's own count, read at the end of the test.

### Report catchers: demote only what you expect

```systemverilog
// snippet: the decision in mem_err_catcher::catch() (complete file in Make It Work)
virtual function action_e catch();
  if (get_severity() != UVM_ERROR || get_id() != catch_id)
    return THROW;                         // not ours: pass it on untouched
  if (n_demoted >= n_allowed())
    return THROW;                         // more than injected: a real failure
  n_demoted++;
  set_severity(UVM_INFO);                 // printed, not counted as an error
  set_message($sformatf("[expected %0d of %0d] %s", n_demoted, n_allowed(), get_message()));
  return THROW;                           // still in the log, for review
endfunction
```

A narrow catcher limits what it touches in three ways:
1. **One reporter.** The test attaches it to the monitor only: `uvm_report_cb::add(env.agt.mon, catcher)`. `uvm_report_cb` is the typedef `uvm_callbacks#(uvm_report_object, uvm_report_catcher)` (Annex D.4.3); with `null` instead of a component, the catcher would run on every report in the simulation.
2. **One severity and one ID.** `get_severity()` and `get_id()` (§6.6.3.2, §6.6.3.5) must be `UVM_ERROR` and `MEM_PARITY`.
3. **A count.** It demotes no more reports than the plan allows, `n_allowed()`, and counts what it demoted. With a fixed plan that is `expected`, set by the test before the run. When the number of injected errors is random, a fixed number cannot work: the catcher would demote the first `expected` reports and pass the rest on as errors, failing a correct DUT. The limit must then follow the injector's live count, `injector.n_injected` (see the density test in Make It Work).

It demotes with `set_severity(UVM_INFO)` (§6.6.4.1) and returns `THROW` (§6.6.5), so the report is still printed and reviewable. In uvm-core 2020.3.1, changing the severity also switches the action to the new severity's default (display, no count) unless the catcher calls `set_action()` itself (`uvm_report_catcher.svh`). Returning `CAUGHT` instead would drop the report silently: the server stops processing it, so it is neither printed nor counted (§6.5.1.2.14).

**Misconception: "demoting all errors during injection is fine."** It is the most dangerous line a test can contain. While it is active, a real DUT bug reports `UVM_ERROR`, the catcher demotes it with the expected ones, and the run passes. The broader the catcher (every ID, every reporter, no count), the more it hides, including the test's own accounting error. The same goes for `+uvm_set_action=...,UVM_ERROR,UVM_NO_ACTION`, which removes errors before they are even counted ([I-UVM-1D](/curriculum/T2_Intermediate/I-UVM-1D_Reporting_and_Run_Control/index)).

### Keeping real failures visible

A catcher, a flush and an injection knob are all code that can be wrong in a way that makes a run pass. Three habits keep real failures visible:

- **A negative control.** Run the same test on a DUT with a planted bug and require it to fail. `mem_dut`'s parameter `BUG = 1` writes the data of a bad-parity write anyway (it still raises `err`); the read of address 2 then returns `a5` instead of `00`, and the run must end with `UVM_ERROR : 1`. A test that passes on the mutant DUT is broken, whatever it reports on the good one.
- **Count what was caught.** The catcher counts its demotions, the test compares them with the plan, and uvm-core prints a catcher summary (`Number of demoted UVM_ERROR reports`) before the report summary whenever a catcher exists (`uvm_report_catcher.svh`). A regression script can require that number to equal the planned injections, from outside the simulation, where no catcher can reach.
- **Demote, never swallow.** A demoted report is still in the log, with its ID, at its time; a caught one is gone.

### Coverage: reset × state and error × response

A test that resets once, at one moment, proves the bench handles *that* reset. The verification plan (vplan) asks where in the protocol a reset can land and which error meets which response, and coverage records which of those cells the regression reached:

| Vplan item | Cross | Cells | How to close it |
|---|---|---|---|
| Reset meets every transfer state | what reset cut off (nothing pending, a write pending, a read pending) × whether a request was on the bus at the reset edge | 3 × 2 = 6 | randomize the virtual sequence's `rst_edge`; add back-to-back resets |
| Every error meets its correct response | request kind (read, write) × parity (good, bad) × DUT response (`err` 0 or 1), with the four "wrong response" cells (good parity flagged, bad parity not flagged, for reads and for writes) ignored, because those are DUT bugs the scoreboard reports | 4 | error sequences on reads and writes; the override or callback for density |

```systemverilog
// snippet: covergroups for the two vplan items (in a subscriber or in mem_sb)
typedef enum {RST_IDLE, RST_WR_PENDING, RST_RD_PENDING} mem_rst_ctx_e;

covergroup rst_cg with function sample(mem_rst_ctx_e ctx, bit req_on_bus);
  cp_ctx: coverpoint ctx;                  // what the reset cut off
  cp_req: coverpoint req_on_bus;           // a request on the bus at the reset edge
  ctx_x_req: cross cp_ctx, cp_req;         // 6 cells
endgroup

covergroup err_cg with function sample(bit we, bit bad_par, logic err);
  cp_we:  coverpoint we      { bins rd = {1'b0}; bins wr = {1'b1}; }
  cp_par: coverpoint bad_par { bins good = {1'b0}; bins bad = {1'b1}; }
  cp_err: coverpoint err     { bins none = {1'b0}; bins flagged = {1'b1}; }
  we_x_par_x_err: cross cp_we, cp_par, cp_err {
    // A wrong response is a bug for the scoreboard to report, not a goal.
    ignore_bins wrong_rsp = (binsof(cp_par.good) && binsof(cp_err.flagged)) ||
                            (binsof(cp_par.bad)  && binsof(cp_err.none));
  }
endgroup
```

`with function sample(...)` gives each covergroup its own sampling arguments (IEEE 1800-2023 §19.8.1); embedded covergroups are constructed in the class's `new()`. The monitor would sample `rst_cg` in its reset branch, at the first reset edge and before it clears `pending`:

```systemverilog
// snippet: in mem_mon::run_phase, inside if (!in_reset), before pending = null
rst_cg.sample(pending == null ? RST_IDLE : (pending.we ? RST_WR_PENDING : RST_RD_PENDING),
              vif.mon_cb.valid === 1'b1);
```

The scoreboard would sample `err_cg` for every request it checks. In this lesson's run, the reset lands with a read pending and a request on the bus, which is 1 of the 6 reset cells.

### Debugging: symptom, cause, fix

| Symptom in the log | Cause | Fix |
|---|---|---|
| `SCB_MISMATCH` on the first reads after a mid-test reset, on a correct DUT | expectations survived the reset: the model was not cleared, or predictions were not deleted | flush on the monitor's reset event, to the specification's reset values |
| `Get_next_item called twice without item_done or get in between` right after a reset | the driver dropped its item without `item_done()`, often through `disable fork` | release the item with `item_done()` when reset wins |
| `UVM_FATAL [SQRBADITMDN] Item_done() called with no outstanding requests.` | `stop_sequences()` emptied the request FIFO before the driver released its item (uvm-core) | let the driver release first; stop at a later edge, or `kill()` the owned sequences |
| `UVM_WARNING [SEQPRTZMB]` after a reset | the thread that called `start()` was killed (`disable fork`, a phase jump) while the sequence ran (uvm-core) | `kill()` the sequence before killing the thread |
| `PH_TIMEOUT` after a reset | an objection raised inside a killed thread, or a sequence that waits for a response its killed partner will never send | raise objections in the test around the whole scenario |
| `PH_TIMEOUT` after a reset, with a sequence blocked in `get_response()` | a pipelined driver dropped its outstanding items on reset without answering them | `put()` an aborted response for every outstanding item, or kill the waiting sequences before the restart |
| A random error test never logs a parity error | a soft default in the base item beats a `dist` with another name | replace the base constraint by name, or disable it |
| `ERR_ACCOUNT injected=2 demoted=1 ...` | the checker missed an injected error, or a reset aborted the injected request | check the monitor's parity check; keep injections away from resets, or count only accepted ones |
| `UVM_ERROR : 0`, but the catcher summary demoted more errors than were injected | the catcher is too broad and has demoted a real failure | narrow it: one reporter, one ID, a count |

### Recap

- Reset is a bench-wide event. The driver releases its item with `item_done()` and waits for release; the monitor discards partial transfers and publishes reset; the scoreboard checks what completed, then flushes what reset destroyed.
- Sample a synchronous reset through the clocking block; watch an asynchronous reset on the raw signal.
- Prefer reset-aware `run_phase` components and a test-level restart. Phase jumping restarts only the run-time phases, kills sequences wherever they are and clears objections.
- In the reset virtual sequence, let the driver release first, then `stop_sequences()` or `kill()`, then restart with new sequence objects; the test's objection spans it all.
- Inject errors with an error sequence (directed), a factory override (density, randomized items only) or a driver callback (pin level), and check that they were injected. When the count is random, account against the injector's live count.
- The scoreboard predicts error responses; the checker's reports are demoted by a catcher narrowed to one reporter, one ID and a count; the test compares the counts; a mutant DUT run proves real failures still fail.
- Cover reset × state and error × response.

```systemverilog
// compile: mem_dut.sv (file 1 of 5; replaces I-UVM-3C's version)
// 16 x 8-bit memory with a one-cycle request bus and a parity bit on every
// request. rdata and err are registered: they appear in the cycle after the
// edge that accepted the request.
module mem_dut #(
  parameter int BUG = 0           // 1: a bad-parity write is flagged but still written
) (
  input  logic       clk,
  input  logic       rst_n,       // synchronous, active low
  input  logic       valid,
  input  logic       we,
  input  logic [3:0] addr,
  input  logic [7:0] wdata,
  input  logic       par,         // even parity: must equal ^{we, addr, wdata}
  output logic [7:0] rdata,
  output logic       err          // 1: the request accepted last edge had bad parity
);
  timeunit 1ns; timeprecision 1ps;

  logic [7:0] mem [16];
  logic       par_ok;

  assign par_ok = (par == ^{we, addr, wdata});

  always_ff @(posedge clk) begin
    if (!rst_n) begin
      foreach (mem[i]) mem[i] <= '0;
      rdata <= '0;
      err   <= 1'b0;
    end else begin
      err <= valid && !par_ok;    // a bad request is answered with err ...
      if (valid && we && (par_ok || BUG == 1)) mem[addr] <= wdata;  // ... and ignored
      if (valid && !we && par_ok)              rdata <= mem[addr];
    end
  end
endmodule
```

```systemverilog
// compile: mem_item.svh (included by mem_pkg.sv)
class mem_item extends uvm_sequence_item;
  `uvm_object_utils(mem_item)

  rand bit       we;
  rand bit [3:0] addr;
  rand bit [7:0] wdata;
  rand bit       par_err;         // stimulus knob: 1 = send with bad parity
  bit            par;             // the parity bit on the bus
  logic    [7:0] rdata;           // response, filled in by the monitor
  logic          err;             // response, filled in by the monitor

  constraint c_par_ok { soft par_err == 0; }   // legal unless a test asks

  function new(string name = "mem_item");
    super.new(name);
  endfunction

  // The parity a correct requester sends: even parity over the request.
  function bit good_par();
    return ^{we, addr, wdata};
  endfunction

  function void post_randomize();
    par = good_par() ^ par_err;
  endfunction

  virtual function string convert2string();
    if (we) return $sformatf("WRITE addr=%h wdata=%h", addr, wdata);
    return $sformatf("READ  addr=%h rdata=%h", addr, rdata);
  endfunction
endclass

// For a factory override: about one request in eight gets bad parity. The
// constraint reuses the base's name, so it replaces the soft default.
class mem_err_item extends mem_item;
  `uvm_object_utils(mem_err_item)

  constraint c_par_ok { par_err dist {1'b1 := 1, 1'b0 := 7}; }

  function new(string name = "mem_err_item");
    super.new(name);
  endfunction
endclass
```

```systemverilog
// compile: mem_seqs.svh (included by mem_pkg.sv)
// Directed: write every address with its own pattern, then read every one back.
class mem_wr_rd_seq extends uvm_sequence #(mem_item);
  `uvm_object_utils(mem_wr_rd_seq)

  function new(string name = "mem_wr_rd_seq");
    super.new(name);
  endfunction

  virtual task body();
    for (int a = 0; a < 16; a++) send(1'b1, 4'(a), {4'(a), ~4'(a)}); // 0F ... F0
    for (int a = 0; a < 16; a++) send(1'b0, 4'(a), 8'h00);
  endtask

  // One item; bad_par = 1 sends it with wrong parity on purpose.
  protected task send(bit we, bit [3:0] addr, bit [7:0] wdata, bit bad_par = 1'b0);
    mem_item it = mem_item::type_id::create("it");
    start_item(it);
    it.we      = we;
    it.addr    = addr;
    it.wdata   = wdata;
    it.par_err = bad_par;
    it.par     = it.good_par() ^ bad_par;
    finish_item(it);
  endtask
endclass

// Random: num_items random reads and writes (post_randomize sets par).
class mem_rand_seq extends mem_wr_rd_seq;
  `uvm_object_utils(mem_rand_seq)

  int unsigned num_items = 40;

  function new(string name = "mem_rand_seq");
    super.new(name);
  endfunction

  virtual task body();
    repeat (num_items) begin
      mem_item it = mem_item::type_id::create("it");
      start_item(it);
      if (!it.randomize()) `uvm_fatal("RAND", "mem_item randomization failed")
      finish_item(it);
    end
  endtask
endclass

// Error sequence: exactly two parity errors, and a read that proves the
// rejected write changed nothing.
class mem_par_err_seq extends mem_wr_rd_seq;
  `uvm_object_utils(mem_par_err_seq)

  function new(string name = "mem_par_err_seq");
    super.new(name);
  endfunction

  virtual task body();
    send(1'b1, 4'h2, 8'ha5, 1'b1);   // bad parity: the DUT must drop this write
    send(1'b0, 4'h2, 8'h00);         // so address 2 still holds its reset value
    send(1'b0, 4'h3, 8'h00, 1'b1);   // bad parity on a read
  endtask
endclass
```

```systemverilog
// compile: mem_drv.svh (included by mem_pkg.sv)
typedef class mem_drv;

// The driver's hook for tests: called just before each request is driven.
virtual class mem_drv_cb extends uvm_callback;
  function new(string name = "mem_drv_cb");
    super.new(name);
  endfunction

  virtual function void pre_drive(mem_drv drv, mem_item req);
  endfunction
endclass

class mem_drv extends uvm_driver #(mem_item);
  `uvm_component_utils(mem_drv)
  `uvm_register_cb(mem_drv, mem_drv_cb)

  mem_cfg      cfg;                    // handed over by mem_agent
  int unsigned n_released;             // items given back because of a reset

  function new(string name, uvm_component parent);
    super.new(name, parent);
  endfunction

  virtual task run_phase(uvm_phase phase);
    virtual mem_if vif = cfg.vif;
    vif.drv_cb.valid <= 1'b0;          // idle the bus from the first edge
    wait_reset_released(vif);
    forever begin
      seq_item_port.get_next_item(req);
      if (vif.drv_cb.rst_n !== 1'b1) begin         // reset came while we waited
        release_item("before it was driven");
        wait_reset_released(vif);
        continue;
      end
      `uvm_do_callbacks(mem_drv, mem_drv_cb, pre_drive(this, req))
      vif.drv_cb.valid <= 1'b1;
      vif.drv_cb.we    <= req.we;
      vif.drv_cb.addr  <= req.addr;
      vif.drv_cb.wdata <= req.wdata;
      vif.drv_cb.par   <= req.par;
      @(vif.drv_cb);                               // the accept edge
      vif.drv_cb.valid <= 1'b0;                    // overridden if another item follows
      if (vif.drv_cb.rst_n !== 1'b1) begin         // reset won: not accepted
        release_item("reset at its accept edge");
        wait_reset_released(vif);
      end else begin
        seq_item_port.item_done();
      end
    end
  endtask

  // Wait for the first edge at which drv_cb samples rst_n as 1.
  protected task wait_reset_released(virtual mem_if vif);
    do @(vif.drv_cb); while (vif.drv_cb.rst_n !== 1'b1);
  endtask

  // Give the item back, so the sequencer is free; the test decides what
  // happens to the sequence that sent it.
  protected function void release_item(string why);
    n_released++;
    `uvm_info("DRV_RESET", $sformatf("released %s addr=%h: %s",
                                     req.we ? "WRITE" : "READ ", req.addr, why), UVM_LOW)
    seq_item_port.item_done();
  endfunction
endclass

// Pin-level injection: corrupt the parity of every Nth request.
class mem_par_flip_cb extends mem_drv_cb;
  `uvm_object_utils(mem_par_flip_cb)

  int unsigned every = 8;
  int unsigned n_seen, n_injected;

  function new(string name = "mem_par_flip_cb");
    super.new(name);
  endfunction

  virtual function void pre_drive(mem_drv drv, mem_item req);
    n_seen++;
    if (n_seen % every == 0 && !req.par_err) begin
      req.par_err = 1'b1;
      req.par     = ~req.par;
      n_injected++;
    end
  endfunction
endclass
```

```systemverilog
// compile: mem_mon.svh (included by mem_pkg.sv)
class mem_mon extends uvm_monitor;
  `uvm_component_utils(mem_mon)

  mem_cfg cfg;                             // handed over by mem_agent
  uvm_analysis_port #(mem_item)  ap;       // one new item per completed transfer
  uvm_analysis_port #(mem_rst_e) rst_ap;   // reset asserted, reset released
  protected mem_item pending;              // accepted last edge; response not yet seen
  int unsigned n_discarded;                // accepted transfers a reset cut off

  function new(string name, uvm_component parent);
    super.new(name, parent);
  endfunction

  virtual function void build_phase(uvm_phase phase);
    super.build_phase(phase);
    ap     = new("ap", this);
    rst_ap = new("rst_ap", this);
  endfunction

  virtual task run_phase(uvm_phase phase);
    virtual mem_if vif = cfg.vif;
    bit in_reset = 1;                      // the power-on reset is on at time 0
    forever begin
      @(vif.mon_cb);
      if (vif.mon_cb.rst_n !== 1'b1) begin
        if (!in_reset) begin               // the first edge of a new reset
          in_reset = 1;
          if (pending != null) begin
            n_discarded++;
            `uvm_info("MON_RESET", {"reset asserted: discarded ", describe(pending),
                                    " (no response yet)"}, UVM_LOW)
          end else begin
            `uvm_info("MON_RESET", "reset asserted", UVM_LOW)
          end
          rst_ap.write(MEM_RST_ASSERTED);  // subscribers flush in this call
        end
        pending = null;                    // a partial transfer is not a transfer
        continue;
      end
      if (in_reset) begin
        in_reset = 0;
        rst_ap.write(MEM_RST_RELEASED);
      end
      // The request accepted at the previous edge has its response now.
      if (pending != null) begin
        pending.rdata = vif.mon_cb.rdata;
        pending.err   = vif.mon_cb.err;
        ap.write(pending);
        pending = null;
      end
      if (vif.mon_cb.valid === 1'b1) begin
        mem_item t = mem_item::type_id::create("t");   // new object per transfer
        if ($isunknown({vif.mon_cb.we, vif.mon_cb.addr,
                        vif.mon_cb.wdata, vif.mon_cb.par}))
          `uvm_error("MON_X", "valid is 1 but the request has X or Z bits")
        t.we    = vif.mon_cb.we;
        t.addr  = vif.mon_cb.addr;
        t.wdata = vif.mon_cb.wdata;
        t.par   = vif.mon_cb.par;
        // Protocol check: every request carries even parity.
        if (t.par != t.good_par())
          `uvm_error("MEM_PARITY", $sformatf("bad parity on %s: par=%b, expected %b",
                                             describe(t), t.par, t.good_par()))
        pending = t;
      end
    end
  endtask

  protected function string describe(mem_item t);
    return $sformatf("%s addr=%h", t.we ? "WRITE" : "READ ", t.addr);
  endfunction

  // A request still waiting for its response means the run ended an edge early.
  virtual function void check_phase(uvm_phase phase);
    super.check_phase(phase);
    if (pending != null)
      `uvm_error("MON_INFLIGHT", {describe(pending), " never got its response"})
  endfunction
endclass
```

```systemverilog
// compile: mem_sb.svh (included by mem_pkg.sv)
class mem_sb extends uvm_scoreboard;
  `uvm_component_utils(mem_sb)

  uvm_analysis_export   #(mem_item)          item_export;  // agt.ap connects here
  uvm_analysis_imp_rst  #(mem_rst_e, mem_sb) rst_imp;      // agt.rst_ap: write_rst()
  uvm_tlm_analysis_fifo #(mem_item)          item_fifo;

  protected bit [7:0] model [16];        // what each address holds, per the spec
  int unsigned n_writes, n_reads, n_match, n_mismatch;
  int unsigned n_resets;                 // resets seen
  int unsigned n_err_expected;           // requests with bad parity
  int unsigned n_err_seen;               // err responses from the DUT

  function new(string name, uvm_component parent);
    super.new(name, parent);
  endfunction

  virtual function void build_phase(uvm_phase phase);
    super.build_phase(phase);
    item_export = new("item_export", this);
    rst_imp     = new("rst_imp", this);
    item_fifo   = new("item_fifo", this);
  endfunction

  virtual function void connect_phase(uvm_phase phase);
    super.connect_phase(phase);
    item_export.connect(item_fifo.analysis_export);
  endfunction

  virtual task run_phase(uvm_phase phase);
    mem_item t;
    forever begin
      item_fifo.get(t);
      check_item(t);
    end
  endtask

  // Called by the monitor (through agt.rst_ap) at the first edge of a reset.
  virtual function void write_rst(mem_rst_e e);
    if (e == MEM_RST_ASSERTED) flush_on_reset();
  endfunction

  protected function void flush_on_reset();
    mem_item t;
    while (item_fifo.try_get(t)) check_item(t); // completed before reset: still check
    foreach (model[i]) model[i] = '0;           // then forget what reset destroyed
    n_resets++;
    `uvm_info("SCB_RESET", "reset: expectations flushed, model cleared to 00", UVM_LOW)
  endfunction

  protected function void check_item(mem_item t);
    bit exp_err = (t.par != t.good_par());      // bad parity must be rejected
    if (exp_err) n_err_expected++;
    if (t.err === 1'b1) n_err_seen++;
    if (t.err !== exp_err) begin
      n_mismatch++;
      `uvm_error("SCB_ERR_RSP", $sformatf("%s par=%b: err=%b, expected err=%b",
                                          t.convert2string(), t.par, t.err, exp_err))
    end
    if (exp_err) return;                        // a rejected request changes nothing
    if (t.we) begin
      model[t.addr] = t.wdata;
      n_writes++;
      return;
    end
    n_reads++;
    if (t.rdata !== model[t.addr]) begin
      n_mismatch++;
      `uvm_error("SCB_MISMATCH", $sformatf("%s, expected rdata=%h",
                                           t.convert2string(), model[t.addr]))
    end else begin
      n_match++;
      `uvm_info("SCB_MATCH", t.convert2string(), UVM_HIGH)
    end
  endfunction

  virtual function void check_phase(uvm_phase phase);
    super.check_phase(phase);
    if (item_fifo.used() != 0)
      `uvm_error("SCB_PENDING", $sformatf("%0d items were never checked",
                                          item_fifo.used()))
    if (n_reads == 0)
      `uvm_error("SCB_NO_TRAFFIC", $sformatf(
        "no read was checked (%0d writes seen): this run proves nothing", n_writes))
  endfunction

  virtual function void report_phase(uvm_phase phase);
    super.report_phase(phase);
    `uvm_info("SCB_SUMMARY",
              $sformatf("SCB_SUMMARY matches=%0d mismatches=%0d pending=%0d",
                        n_match, n_mismatch, item_fifo.used()), UVM_NONE)
    `uvm_info("SCB_ACCOUNT", $sformatf("resets=%0d err_expected=%0d err_seen=%0d",
                                       n_resets, n_err_expected, n_err_seen), UVM_NONE)
  endfunction
endclass
```

### How to make your own bench reset-aware and injection-ready

1. **Write the reset rule into the protocol table:** which edges accept nothing, what the DUT's state becomes, and which responses an assertion aborts.
2. **Driver:** idle the bus, wait for release; after every accept edge, check the sampled reset; on reset, `item_done()` the held item, log it, wait for release.
3. **Monitor:** on the first reset edge, discard partial transfers and publish a reset event on a second analysis port; publish nothing during reset; for an asynchronous reset, watch the raw signal.
4. **Scoreboard:** add a `write_rst()` through `` `uvm_analysis_imp_decl(_rst) ``; check completed observations, then reset the model to the specification's values and delete pending predictions, counting them.
5. **Reset scenario:** a virtual sequence that applies reset, lets the driver release, then `stop_sequences()` or `kill()`, releases reset and starts *new* sequence objects; the test's objection spans it.
6. **Injection knob:** a `rand` error field with a soft default of "no error"; override that constraint *by name* in an error subclass.
7. **Predict error responses** in the scoreboard from what was observed, and count expected and seen errors.
8. **Catcher:** one ID, one reporter (`uvm_report_cb::add(component, catcher)`), a count, demote with `THROW`; attach it in `start_of_simulation_phase`.
9. **Account:** in the test's `check_phase`, compare planned, demoted, predicted and flagged. For random injection, the plan is the injector's live count, and the catcher's limit follows it.
10. **Negative control:** a DUT mutant that the test must fail on; and require the catcher summary to match the plan.

**Checklist before moving on:**
- [ ] The driver calls `item_done()` for an item that reset prevents from being accepted, and drives nothing until reset is released.
- [ ] The monitor discards a transfer whose response edge sees reset, and publishes reset to its subscribers.
- [ ] The scoreboard checks completed transfers, then resets its model to the specification's reset values on every reset.
- [ ] The reset virtual sequence stops sequences only after the driver has released its item, and restarts with new sequence objects.
- [ ] The test's objection spans the whole scenario, reset included; no objection is raised inside a sequence that may be killed.
- [ ] The log proves errors were injected (two `MEM_PARITY` reports), and the scoreboard predicted and saw both.
- [ ] The catcher is attached to one reporter, matches one ID and severity, and demotes at most the planned count.
- [ ] `ERR_ACCOUNT` compares the planned, demoted, predicted and flagged counts.
- [ ] In `mem_par_density_test`, the catcher's limit follows `flip.n_injected`, and `ERR_ACCOUNT` shows five equal non-zero counts.
- [ ] The run fails with `BUG = 1`, and passes with `BUG = 0`.
- [ ] You can explain why this bench does not use phase jumping for reset.

### Expert: what `kill()` and `stop_sequences()` do in uvm-core 2020.3.1

- **`stop_sequences()`** (IEEE 1800.2-2020 §15.3.2.14). In `uvm_sequencer_base.svh` it calls `kill_sequence()` for every sequence registered on the sequencer. `uvm_sequencer` (`uvm_sequencer.svh`) then clears its `get_next_item` bookkeeping and empties its request FIFO, logging "Sequences stopped. Removing request from sequencer fifo" if an item was there. A driver that later calls `item_done()` for that item gets `UVM_FATAL [SQRBADITMDN] Item_done() called with no outstanding requests.`
- **`kill()`** (§14.2.5.11). It removes the sequence's requests and locks from its default sequencer, calls `do_kill()` (§14.2.5.12, the user hook for cleanup), kills every child in `children_array`, then kills the process running `body()`. It does **not** empty the request FIFO, so a driver holding the sequence's item can still call `item_done()` safely afterwards.
- **`post_body()` and `post_start()`: standard versus implementation.** §14.2.5.11 says they "are executed" after a kill. In uvm-core 2020.3.1 they run inside the process that `kill()` terminates, and the source comment on `kill()` says they "will not be executed". Put cleanup in `do_kill()`, which both call.
- **Objections.** Both the standard (§14.2.4.4) and uvm-core drop a sequence's *automatic* phase objection when it is killed with `kill()`. uvm-core's `stop_sequences()` kills through `kill_sequence()` and `m_kill()`, which do not drop a top-level sequence's automatic objection (only children killed through `kill()` drop theirs), so the phase can hang: `kill()` such sequences, or keep objections in the test as this bench does. A `raise_objection()` written by hand in a killed thread is never dropped.
- **Process guards (uvm-core only).** If the process that called `start()` is killed while the sequence runs (by `disable fork` or a phase jump), `uvm_sequence_base.svh` reports `UVM_WARNING [SEQPRTZMB]` and calls `kill()` itself; if the process `start()` forked is killed, it reports `[SEQBDYZMB]`. Kill the sequence first, then the thread.

**Interview angle (try it first):** "Your reset test dies with `SQRBADITMDN` on one simulator and passes on another. Why?"

<details>
<summary>Model answer</summary>

A same-edge race between the driver's `item_done()` and `stop_sequences()`: the order of processes woken by one event is up to the simulator. Make the driver release first, by design.

### Expert: phase jumping as a reset strategy, in detail

- **What a jump does.** `uvm_phase::jump()` (§9.3.1.9.1) sets the target and the "end prematurely" flag; uvm-core says it "does not directly alter flow of control". The phaser then moves the phase to `UVM_PHASE_JUMPING`, in which "all processes related to phase are being killed" (Annex F.2.5.2), clears its objection, and schedules the target (`uvm_phase_hopper.svh`). `uvm_domain::jump()` (§9.4.2.4) jumps every active phase of a domain.
- **Errors you can meet (uvm-core).** A jump from a phase that is not running reports `JMPPHIDL`; a target that is neither a predecessor nor a successor reports `UVM_FATAL [PH_BADJUMP]` (`uvm_phase.svh`). The jump itself is logged as `PH_JUMP` at `UVM_MEDIUM`.
- **Re-entry.** After a backward jump, `reset_phase`, `configure_phase` and `main_phase` run again in every component of the domain. Each must recreate its sequences (a sequence object still running cannot be started again: uvm-core reports `SEQ_NOT_DONE`) and must not assume it runs once; `get_run_count()` (§9.3.1.4.2) tells a phase how many times it has executed.
- **What it does not touch.** `run_phase` (§9.8.1.5), and therefore every driver and monitor written the usual way, and every scoreboard flush. A jump-based bench still needs everything on this page, plus the jump.
- **When it fits.** A closed bench whose components were all designed for re-entry, where the run-time phases map onto real DUT stages (reset, configuration, traffic) and a reset should replay them. Even then, a power domain that resets alone is better modelled as its own domain ([I-UVM-1C](/curriculum/T2_Intermediate/I-UVM-1C_UVM_Phasing/index)) or with the power-aware techniques of [E-PWR-1](/curriculum/T4_Expert/E-PWR-1_Power_Aware_Verification/index).

**Interview angle (try it first):** "Name two things a phase jump to `reset_phase` does *not* do for you."

<details>
<summary>Model answer</summary>

It does not reset `run_phase` drivers and monitors, and it does not flush scoreboards; it also kills sequences at an arbitrary point.

</details>

### Expert: report catcher internals

- **Order and scope.** Catchers are callbacks (§6.6, §10.7). They run in registration order, `UVM_APPEND` by default (§10.7.2.3.1); a catcher added with `null` runs for every report object, one added to a component only for that component's reports. `callback_mode(0)` (§10.7.1.2.2) turns one off without removing it.
- **What they see.** Only reports issued through UVM. `$error` from a component, and the default action block of a failing SystemVerilog assertion, never reach the report server ([I-UVM-1D](/curriculum/T2_Intermediate/I-UVM-1D_Reporting_and_Run_Control/index)); to make those catchable, report them with `` `uvm_error `` in the assertion's action block.
- **Changing severity changes the action (uvm-core).** After each `catch()`, `process_all_report_catchers()` in `uvm_report_catcher.svh` replaces the action with the new severity's default if the severity changed, the action was still the old severity's default, and `set_action()` was not called. A demoted error therefore loses `UVM_COUNT` without any extra code; a catcher that promotes an `UVM_INFO` to `UVM_ERROR` gains it.
- **Reports from inside a catcher.** The catcher's own `uvm_report_error()` and friends "bypass any message catching callbacks" (§6.6.6.2), so a catcher cannot catch itself. `issue()` (§6.6.6.6) prints the current message immediately, even when the catcher then returns `CAUGHT`.
- **Counting.** uvm-core keeps static counts of demoted and caught fatals, errors and warnings, and prints them before the report summary once any catcher has been constructed (`uvm_report_catcher::summarize()`). `uvm_report_catcher::print_catcher()` and `debug_report_catcher()` are uvm-core extensions, not in IEEE 1800.2-2020.
- **Cost at scale (tool-dependent).** Every report passes every applicable catcher. Thousands of `UVM_HIGH` messages suppressed by verbosity never reach the server, but enabled messages do: keep catchers few and their tests cheap, string comparisons last.

**Interview angle (try it first):** "Why should an expected-error catcher return `THROW` after demoting, not `CAUGHT`?"

<details>
<summary>Model answer</summary>

A demoted report stays in the log with its ID and time, so a reviewer, the ID counts and a script can see what was excused; `CAUGHT` makes it vanish.

</details>

### Expert: reset at system scale (tool-dependent)

- **Several resets.** A chip has reset domains: a block can reset while its neighbours keep running. Each agent should watch the reset of the interface it sits on, not a global one, and scoreboards that span domains must flush only the expectations the resetting side owed. Reset-domain crossing analysis is [E-SOC-1](/curriculum/T4_Expert/E-SOC-1_SoC-Level_Verification_Strategies/index)'s topic.
- **Power-on X.** A 4-state variable starts at X (IEEE 1800-2023 §6.8). Until reset is applied, X on DUT outputs is legal; monitors that check for X must be gated by reset, as `mem_mon` is. Whether simulation starts registers at X, at 0 or at random values is a tool option (tool-dependent), and gate-level runs behave differently again.
- **Reset in the middle of an injected error.** If the reset aborts an injected request, the checker never fires and the scoreboard never predicts it: `ERR_ACCOUNT` then fails on a correct bench. Either keep injections away from resets, or count injections at the scoreboard (accepted requests only) rather than at the stimulus.

**Interview angle (try it first):** "Your reset test passes on RTL and fails at gate level with X on `rdata` right after reset. Where do you look?"

<details>
<summary>Model answer</summary>

Reset values and X-propagation of registers without reset at gate level; a monitor or scoreboard reading outputs the specification leaves undefined after reset.

</details>

<details>
<summary>Worked solution</summary>

1. **Verdicts.** Bench P, `BUG = 0`: **false failure** (the DUT is correct). Bench P, `BUG = 1`: right verdict (fail), wrong reason (it blames a stale `2d`, not the written `a5`). Bench Q, `BUG = 0`: right (pass). Bench Q, `BUG = 1`: **false pass**, a real bug and `UVM_ERROR : 0`.
2. **Mutants.**
   - **Bench P: the scoreboard is not flushed.** `flush_on_reset()` no longer clears `model` (for example, the `foreach (model[i]) model[i] = '0;` line was deleted), so the value written to address 2 before the reset (`{2, ~2}` = `2d`) survives. The read after reset returns the DUT's reset value `00` and mismatches. Pending expectations do not survive reset.
   - **Bench Q: the catcher is too broad.** Its `catch()` demotes every `UVM_ERROR` (no ID check and no limit; it still counts `n_demoted`), it is attached with `uvm_report_cb::add(null, catcher)`, and it no longer rewrites the message (no `[expected k of 2]` prefix). With the correct DUT only the two planned errors exist, so it looks fine; with the bug it demotes the real `SCB_MISMATCH`.
3. **Fixes.**

```systemverilog
// snippet: bench P, inside mem_sb::flush_on_reset()
foreach (model[i]) model[i] = '0;      // reset the model to the specification's values
```

```systemverilog
// snippet: bench Q, the narrow catch() and its registration
virtual function action_e catch();
  if (get_severity() != UVM_ERROR || get_id() != catch_id) return THROW;
  if (n_demoted >= n_allowed()) return THROW;
  n_demoted++;
  set_severity(UVM_INFO);
  set_message($sformatf("[expected %0d of %0d] %s", n_demoted, n_allowed(), get_message()));
  return THROW;
endfunction
// in the test's start_of_simulation_phase:
uvm_report_cb::add(env.agt.mon, catcher);   // the monitor only, not null
```

4. **Why 3 and 4.** In `check_phase` the test compared the counts when the catcher had demoted 3 reports (two `MEM_PARITY` and the `SCB_MISMATCH`), so it raised `ERR_ACCOUNT` as an error. That error went through the same over-broad catcher, which demoted it as well: the fourth demotion in uvm-core's catcher summary. A catcher with no reporter or ID limit can silence the very check meant to catch it.
5. **The regression rule.** Two rules, both outside the catcher's reach. The negative control: the `BUG = 1` run must end with a non-zero `UVM_ERROR` count. And the catcher summary: "Number of demoted UVM_ERROR reports" must equal the planned injections (2), checked by the regression script on the log. Either one fails bench Q.

</details>
