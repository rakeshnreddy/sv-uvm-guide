## Quick Take

- **What it is:** A **multi-agent topology** is the shape of a UVM environment for a design under test (DUT) with several interfaces. It has one **agent** per interface: active if the testbench drives it, passive if it only watches. Whole block environments are often nested inside a bigger one or repeated side by side, and around them sit a **virtual sequencer** that holds handles to the agents' sequencers, one **configuration object** tree that says what to build, and **scoreboards** that check results using more than one interface.
- **Why it matters:** The bugs live *between* interfaces: data that arrives before the DUT is configured, a mode change in the middle of traffic, an interrupt nobody answers. Multi-agent mistakes rarely show up as a clean mismatch. They show up as a test that never ends, a responder that never ran, or a pass that checked nothing.
- **The Analogy:** A railway junction run from a signal box. Each line (agent) runs its own trains (items); the timetable (the virtual sequence's `body()`) says which line moves when; signals (events, barriers, a sequencer `grab()`) hold trains until it is safe; trackside observers (passive agents) only watch and log. *Where it breaks:* nothing enforces the timetable except the statements you write in `body()`, the signal box itself (the virtual sequencer) gives no orders at all, and an observer's post has no trains: a passive agent has no sequencer, so its handle is null.

**You will be able to:**
1. Design a multi-agent environment for a DUT with a configuration port and data ports: choose active or passive for each agent, wire the virtual sequencer's handles, and reuse environments vertically (a block env nested in a subsystem env) and horizontally (several instances side by side).
2. Write a virtual sequence that configures before sending data, reconfigures in mid-stream at a safe point, and runs a background responder without blocking the end of the test.
3. Choose between `uvm_event`, `uvm_barrier`, a semaphore and sequencer `grab()`/`lock()` for a cross-agent rule, and predict the outcome of trigger/wait races.
4. Debug multi-agent hangs and silent passes from the log: a `forever` branch inside `fork…join`, a sequence started on a passive agent's null sequencer (with and without a parent), and objections held by background threads.
5. Configure the topology from the test through one environment configuration object, and check results across agents: place each check in a per-agent checker or a shared scoreboard, and make the shared scoreboard follow the configuration.

## Build Your Mental Model

**How to read this lesson.** The core path is the recap, the running example, one environment with many agents, configuring it from the test, reusing environments, ordering stimulus across agents and checking across agents. Practitioner depth sits between and after them: mid-stream reconfiguration, locking a sequencer, synchronization objects, where each check lives, and debugging. Make It Work builds the whole bench, and Push Further holds the expert corner cases.

**Words this lesson uses.** Each was taught earlier; here is the one-line version.
- **Agent:** a component that bundles a **sequencer** (queues items from sequences), a **driver** (turns items into pin activity) and a **monitor** (turns pin activity back into transactions) for one interface ([I-UVM-2A](/curriculum/T2_Intermediate/I-UVM-2A_Component_Roles/index)).
- **Active / passive agent:** an active agent (`UVM_ACTIVE`) builds all three; a passive agent (`UVM_PASSIVE`) builds only the monitor ([A-UVM-7](/curriculum/T3_Advanced/A-UVM-7_VIP_Construction/index)).
- **Analysis port:** the monitor's broadcast output; every connected subscriber's `write()` is called with each transaction ([I-UVM-2B](/curriculum/T2_Intermediate/I-UVM-2B_TLM_Connections/index)).
- **Virtual sequence:** a sequence that sends no items itself; its `body()` starts **child sequences** on the agents' sequencers. A **virtual sequencer** is a driverless sequencer that only holds those handles ([I-UVM-3B](/curriculum/T2_Intermediate/I-UVM-3B_Advanced_Sequencing_and_Layering/virtual-sequences)).
- **Configuration object:** a `uvm_object` that holds an agent's settings (mode, virtual interface, switches) and travels through the configuration database as one handle ([I-UVM-2C](/curriculum/T2_Intermediate/I-UVM-2C_Configuration_and_Resources/index)).
- **Phase:** one of the named steps UVM runs every component through, in order: `build_phase` creates children (top-down), `connect_phase` wires ports and handles, `run_phase` consumes simulation time, and the check and report phases run at the end ([I-UVM-1C](/curriculum/T2_Intermediate/I-UVM-1C_UVM_Phasing/index)).
- **Objection:** the vote that keeps a task phase such as `run_phase` alive; the phase ends when the last one is dropped ([I-UVM-1C](/curriculum/T2_Intermediate/I-UVM-1C_UVM_Phasing/index)).
- **Elaboration and time slot:** elaboration is the step before simulation in which the tool builds the design hierarchy and resolves connections; a time slot is all the activity at one simulation time ([F3C](/curriculum/T1_Foundational/F3C_Delta_Cycles_and_Race_Conditions/index)).
- **Parent and default sequencer:** a sequence started with `child.start(sqr, this)` has the calling sequence as its **parent**; the sequencer a sequence was started on is its **default sequencer** (for a virtual sequence, that is `v_sqr`).

### What I-UVM-3B already gave you

[Virtual Sequences and Sequencers](/curriculum/T2_Intermediate/I-UVM-3B_Advanced_Sequencing_and_Layering/virtual-sequences) and [The Virtual Sequencer](/curriculum/T2_Intermediate/I-UVM-3B_Advanced_Sequencing_and_Layering/uvm-virtual-sequencer) own the mechanics, so this lesson only recaps them. A child runs on the sequencer you pass to `child.start(sqr, this)`, and `start()` returns when the child's `body()` returns, so two `start()` calls in a row run one after the other. The handles reach the virtual sequence either from the test (`vseq.start(null)`) or from a virtual sequencer through the typed `p_sequencer` handle that `` `uvm_declare_p_sequencer `` declares (IEEE 1800.2-2020 Annex B.3.3). IEEE 1800.2-2020 defines no virtual-sequencer class; uvm-core 2020.3.1 ships `typedef uvm_sequencer #(uvm_sequence_item) uvm_virtual_sequencer;` (`uvm_sequencer.svh`), which you will meet in older code.

This lesson uses the virtual-sequencer style throughout, with type `soc_vsqr` and instance `v_sqr`, and spends its space on what I-UVM-3B does not cover: the topology around the virtual sequence, how it is configured, how its checking spans agents, and how it fails.

### The running example: one DUT, four interfaces

Every example on this page verifies the same small DUT, `dma_stream`, a streaming engine:
- **Configuration port.** An APB-style register bus: a write takes a **setup** cycle (`psel = 1`) and then an **access** cycle (`psel = 1`, `penable = 1`), and the register is written at the end of the access cycle when `pready = 1`. Two registers: `CTRL` at address 0x0 (bit 0 is `EN`, "accept data") and `MODE` at address 0x4 (bit 0: 0 passes data through, 1 inverts it). APB itself is taught in the AMBA track; this subset is all you need here.
- **Data in.** `din_valid` and `din`. The DUT accepts an item only while `CTRL.EN = 1` and **silently drops** anything sent while `EN = 0`.
- **Data out.** `dout_valid` and `dout`, two cycles after an item is accepted, with `MODE` applied when the item was accepted.
- **Interrupt.** `irq` rises after every fourth accepted item and stays high until the testbench pulses `irq_ack`.

| Interface (bus in `tb_top`) | Who drives it | Agent | Mode | Its handle in `v_sqr` |
|---|---|---|---|---|
| configuration (`apb_bus`) | the testbench | `apb_agt` | active | `apb_sqr` |
| data in (`data_bus`) | the testbench | `data_agt` | active | `data_sqr` |
| interrupt (`irq_bus`) | the DUT raises `irq`; the testbench answers with `irq_ack` | `irq_agt` (a **responder**) | active | `irq_sqr` |
| data out (`out_bus`) | the DUT | `out_agt` | passive | none: no sequencer |

A **responder** agent reacts to the DUT instead of starting traffic: its sequence runs for the whole test and each item it sends means "acknowledge the next interrupt". The names `cfg_seq`, `data_seq`, `irq_seq`, `cfg_done`, `apb_sqr`, `data_sqr` and `irq_sqr` match the interactive visual further down.

**What the picture shows.**
- **One class can be two agents.** `data_agt` and `out_agt` are both `stream_agent`, on two instances of the same interface type. The configuration object decides which one drives.
- **The env wires the handles.** In `connect_phase` the env copies each agent's sequencer handle into `v_sqr`: `v_sqr.data_sqr = data_agt.sqr;`. An agent written to the A-UVM-7 pattern does not create its sequencer when it is passive, so copying a passive agent's `sqr` copies `null`.
- **The virtual sequencer gives no orders.** It is a place to keep handles. Order comes from the statements in the virtual sequence's `body()`.

**The two mistakes everyone makes here.** Starting a sequence on a passive agent's handle (it is null; the symptom depends on the parent and is in the debugging table below), and leaving an agent active on an interface the DUT drives. On a net, two drivers resolve to X wherever their values disagree; on a variable, mixing a continuous driver (such as a DUT output port) with any other writer is an error, while two procedural writers are legal and the last write silently wins (IEEE 1800-2023 §6.5). Neither outcome is what you want.

### Configuring the topology from the test

A topology has knobs: which agents are active, how many data agents there are, whether the scoreboard is built. Put them all in **one environment configuration object** that holds one configuration object per agent. The test builds the tree and sets it once; the env takes it and hands each agent its own object at its own path; each agent copies `cfg.is_active` into `uvm_agent`'s public `is_active` member and reads it back with `get_is_active()`. (IEEE 1800.2-2020 §13.4.2.2 standardizes `get_is_active()` and the `is_active` configuration parameter; the public member is uvm-core 2020.3.1's implementation, in `uvm_agent.svh`. An agent that must stay portable overrides `get_is_active()` to return `cfg.is_active` instead.) The [I-UVM-2C worked example](/curriculum/T2_Intermediate/I-UVM-2C_Configuration_and_Resources/index) taught the per-agent object; this is the same idea one level up.

```systemverilog
// snippet: the environment configuration object (full version in Make It Work)
class soc_env_cfg extends uvm_object;
  `uvm_object_utils(soc_env_cfg)
  apb_cfg    apb_agt_cfg;          // one object per agent
  stream_cfg data_agt_cfg;
  stream_cfg out_agt_cfg;
  irq_cfg    irq_agt_cfg;
  bit        has_scoreboard = 1;   // topology switches live here too
  function new(string name = "soc_env_cfg");
    super.new(name);
  endfunction
endclass
```

The order of events at build time matters, because `build_phase` runs top-down: a parent's `build_phase` finishes before its children are built. Follow one agent's configuration from `tb_top` to the agent.

**Pitfalls.**
- **A missing `set()` and a missing object fail differently.** If no `set()` matches the agent's path, its `get()` returns 0 and the agent's guard stops the test in `build_phase` with `UVM_FATAL [NO_CFG]`. But if the env does call `set()` and the test simply never created that agent's object, `set()` stores a **null handle**: `get()` finds it and returns 1 with `cfg == null`. Without a further check, the next line, `is_active = cfg.is_active;`, dereferences null and the simulator stops with its own null-object error, which carries no UVM id and points at the agent, not at the test. So check both places: the env fatals on any null agent object before it calls `set()`, and each agent's guard tests `cfg == null` as well as the return value of `get()`. The Make It Work code does both. One environment object gives you one place to make that check. (In the Make It Work test, a forgotten `create()` would crash even earlier, at the test's own `get()` into `env_cfg.data_agt_cfg.vif`, for the same reason: a member of a null object.)
- **A path typo.** `set(this, "data_agent", ...)` for an agent named `data_agt` matches nothing, so the get fails the same way. uvm-core 2020.3.1 prints every set and get with `+UVM_CONFIG_DB_TRACE` (implementation, not 1800.2); I-UVM-2C has the full [debugging table](/curriculum/T2_Intermediate/I-UVM-2C_Configuration_and_Resources/index).
- **Setting after creating.** The env must call `set()` for an agent before it creates that agent. If it creates the agent first, the order still works today (the agent's `build_phase` runs later), but the moment someone moves a `get()` into a constructor it breaks. Set first, then create.

**An agent count from the configuration.** When the number of identical interfaces varies by DUT variant, keep an array of agent objects in the environment configuration and build the agents in a loop:

```systemverilog
// snippet: N data agents, named data_agt0, data_agt1, ... (env side)
stream_agent data_agt[];
// in build_phase, after getting cfg:
data_agt = new[cfg.num_data_agents];
foreach (data_agt[i]) begin
  string name = $sformatf("data_agt%0d", i);
  uvm_config_db#(stream_cfg)::set(this, name, "cfg", cfg.data_agt_cfg[i]);
  data_agt[i] = stream_agent::type_id::create(name, this);
end
```

The virtual interfaces need one instance per agent in `tb_top`. A select into an array of interface instances must be a constant expression (an **instance select**, IEEE 1800-2023 §23.6), so a `foreach` with a variable index cannot reach them. A `generate` loop can, because its loop variable (`genvar`) is a constant in each copy:

```systemverilog
// snippet: tb_top side; each generated block owns one interface instance
for (genvar i = 0; i < N_DATA; i++) begin : g_data
  stream_if bus (clk, rst_n);
  initial uvm_config_db#(virtual stream_if)::set(null, "uvm_test_top",
                                                 $sformatf("data_vif%0d", i), bus);
end
```

### Environments inside environments: block to subsystem

IEEE 1800.2-2020 §13.3 describes `uvm_env` as a container that "can be reused as a sub-environment in even larger system-level environments". That is **vertical reuse**: the environment you built for one block becomes a component of the subsystem environment, unchanged, and only its configuration differs. Suppose the subsystem connects block A's output straight to block B's input. Before you read on, predict which agent must change mode.

**Debrief.** Only B's `in_agt` changes mode: it becomes passive. At block level it drove B's input, but in the subsystem block A's output drives those wires, and a second driver on the same bus would fight it. As a passive agent it still monitors the bus and still feeds `b_scb`, and `blk_b_env.v_sqr`'s handle to its input sequencer is now null. A's `in_agt` stays active, because it still drives the subsystem's input, and both `out_agt`s were passive already.

**What changes, and what does not.**
- **Agents on internal interfaces become passive.** Nothing in `blk_b_env` changes except its configuration object (`in_agt_cfg.is_active = UVM_PASSIVE`). This is why the active/passive choice belongs in configuration, not in code.
- **Configuration nests too.** `sub_env_cfg` holds `blk_a_cfg` and `blk_b_cfg` (each a block environment object); `sub_env` sets each one at `"blk_a_env"` and `"blk_b_env"`, and each block env distributes its own agents' objects exactly as before. Every configuration path gets one level deeper, which is why paths should be relative to `this`, never absolute strings such as `"uvm_test_top.env.data_agt"`.
- **Block virtual sequences are reused as children.** A subsystem virtual sequence starts block A's virtual sequence on `p_sequencer.a_vsqr` with `this` as parent, so the block scenario runs unchanged. A block sequence that drives B's input can no longer run (its handle is null), which is the correct outcome.
- **Block scoreboards stay as internal checkers.** They now check each block's behaviour on internal buses that the subsystem test cannot see from the outside, and they localize failures. An end-to-end scoreboard from A's input to B's output can be added on top; the [E-SOC-1](/curriculum/T4_Expert/E-SOC-1_SoC-Level_Verification_Strategies/index) lesson covers that strategy at SoC scale.

Here is the subsystem env in code. `blk_env` is the block environment class (the same shape as `soc_env`), instantiated twice; `blk_env_cfg` is its configuration object, holding an `in_agt_cfg` and an `out_agt_cfg`; `blk_vsqr` is its virtual sequencer.

```systemverilog
// snippet: sub_env nests two copies of blk_env (vertical reuse)
class sub_env extends uvm_env;
  `uvm_component_utils(sub_env)
  sub_env_cfg cfg;                    // holds blk_env_cfg blk_a_cfg, blk_b_cfg

    super.new(name, parent);
  endfunction

    super.build_phase(phase);
    if (!uvm_config_db#(sub_env_cfg)::get(this, "", "cfg", cfg) || cfg == null ||
        cfg.blk_a_cfg == null || cfg.blk_b_cfg == null)
      `uvm_fatal("NO_CFG", "no complete sub_env_cfg at the env's path")
    // Block A drives B's input here: only B's configuration changes, not blk_env
    cfg.blk_b_cfg.in_agt_cfg.is_active = UVM_PASSIVE;
    uvm_config_db#(blk_env_cfg)::set(this, "blk_a_env", "cfg", cfg.blk_a_cfg);
    uvm_config_db#(blk_env_cfg)::set(this, "blk_b_env", "cfg", cfg.blk_b_cfg);
    blk_a_env = blk_env::type_id::create("blk_a_env", this);
    blk_b_env = blk_env::type_id::create("blk_b_env", this);
    v_sqr     = sub_vsqr::type_id::create("v_sqr", this);
  endfunction
  function void connect_phase(uvm_phase phase);
    v_sqr.a_vsqr = blk_a_env.v_sqr;   // block virtual sequencers, not agent ones
    v_sqr.b_vsqr = blk_b_env.v_sqr;
  endfunction
endclass

// in sub_vseq::body(): block A's own virtual sequence runs unchanged, as a child
a_seq.start(p_sequencer.a_vsqr, this);
```

Each `blk_env` then gets its `cfg` and sets `in_agt_cfg` and `out_agt_cfg` on its own agents with paths relative to `this`, exactly as `soc_env` does, so no block code changes.

**Pitfalls, with what the log shows.**
- **An internal agent left active.** B's input driver and block A both drive the internal bus: X on a net wherever they disagree, or a multiple-driver error on a variable, and B's scoreboard sees garbage.
- **An absolute configuration path.** A block env that sets `set(null, "uvm_test_top.env.in_agt", "cfg", …)` worked at block level. Nested, the agent is `uvm_test_top.env.blk_b_env.in_agt`, nothing matches, and the build stops with `UVM_FATAL [NO_CFG]` from `blk_b_env.in_agt`. Use `set(this, "in_agt", …)`.
- **The same path checked twice.** `b_scb` and a subsystem scoreboard both predict the internal bus with different expectations, and one bug produces two contradictory error streams.

```systemverilog
// snippet: dual_env builds one soc_env per channel
class dual_env extends uvm_env;
  `uvm_component_utils(dual_env)
  dual_env_cfg cfg;                 // holds soc_env_cfg ch_cfg[2]
  soc_env      ch[2];
  dual_vsqr    v_sqr;               // holds soc_vsqr ch_vsqr[2]

    super.new(name, parent);
  endfunction
  function void build_phase(uvm_phase phase);
    super.build_phase(phase);
    if (!uvm_config_db#(dual_env_cfg)::get(this, "", "cfg", cfg))
      `uvm_fatal("NO_CFG", "no dual_env_cfg at the env's path")
    foreach (ch[i]) begin
      string name = $sformatf("ch%0d", i);
      // exact path "ch0" or "ch1": never a wildcard such as "ch*"
      uvm_config_db#(soc_env_cfg)::set(this, name, "cfg", cfg.ch_cfg[i]);
      ch[i] = soc_env::type_id::create(name, this);
    end
    v_sqr = dual_vsqr::type_id::create("v_sqr", this);
  endfunction
  function void connect_phase(uvm_phase phase);
    foreach (ch[i]) v_sqr.ch_vsqr[i] = ch[i].v_sqr;
  endfunction
endclass
```

**What breaks when an environment is instantiated twice.** Code that was correct with one instance can quietly couple two of them:
- **A wildcard path.** `set(this, "ch*", "cfg", cfg.ch_cfg[0])` matches both instances, so `ch1` receives channel 0's virtual interfaces. Its active agents then drive channel 0's interfaces too (two UVM drivers writing the same signals, corrupting channel 0's traffic), and channel 1 is never exercised. Set each instance's object at its exact name.
- **A global event name.** If `soc_vseq` waited on `uvm_event_pool::get_global("cfg_done")`, both channels would share one event, and `ch1`'s data could start the moment `ch0` finished configuring. Keep events in the instance (in its configuration object or virtual sequencer), or prefix pool keys with `get_full_name()`.
- **A static variable.** A `static` counter or queue in a monitor or scoreboard class is shared by every instance of that class, so two channels' items mix. Use instance members.
- **A type override meant for one instance.** A type override replaces the class in both channels. To change only `ch1`, use an instance override on its path (IEEE 1800.2-2020 §8.3.1.4.1; the factory is taught in [I-UVM-1B](/curriculum/T2_Intermediate/I-UVM-1B_The_UVM_Factory/index)).
- **Reports that do not say which instance.** Use `` `uvm_error `` inside components, whose messages carry the full path (`uvm_test_top.env.ch1.scb`), rather than a global reporter.

The same rules make an agent or environment reusable in the next project: everything that differs between uses lives in the configuration object, nothing depends on a global name, and the class assumes nothing about how many copies of it exist.

### Ordering stimulus across agents

The DUT drops data sent before `CTRL.EN = 1`, so the virtual sequence must configure before it sends data, and it must keep the interrupt responder running the whole time without letting it hold up the end of the test. The minimal correct `body()`:

```systemverilog
// snippet: the core of soc_vseq::body() (full version in Make It Work)
fork                                          // background: its own fork...join_none
  irq_seq.start(p_sequencer.irq_sqr, this);   // runs forever
join_none
cfg_seq.start(p_sequencer.apb_sqr, this);     // returns after CTRL.EN = 1 is written
data_seq.start(p_sequencer.data_sqr, this);   // so no item can arrive before it
```

Two rules make this correct. First, `start()` returns only when the child's `body()` returns, and `dma_cfg_seq` returns after its last write completes, so sequential `start()` calls order the agents. Second, `fork…join` waits for **every** branch, `join_any` for the first and `join_none` for none (IEEE 1800-2023 §9.3.2), so a branch that never ends must never sit in a `join`.

### Reconfiguring in mid-stream

Real DUTs change mode while traffic flows: a new compression level, a new channel map. The safe pattern is **quiesce, reprogram, resume**: stop sending data at a point where nothing the change could affect is in flight, write the new settings, then continue. The scoreboard must follow the change too, which it does by watching the configuration monitor, not by being told by the sequence.

The **sequential form** is the one to reach for first. `data_seq.start()` returns after its last item has been sampled, so the next `cfg_seq.start()` is a safe point by construction:

```systemverilog
// snippet: sequential mid-stream reconfiguration inside soc_vseq::body()

cfg_seq.mode = 1'b1;                          // CTRL.EN = 0, MODE = 1, CTRL.EN = 1
cfg_seq.start(p_sequencer.apb_sqr, this);
data_seq = stream_seq::type_id::create("data_seq");
data_seq.start(p_sequencer.data_sqr, this);   // burst 2 runs with MODE = 1
```

### Locking an agent's sequencer from a virtual sequence

`lock()` and `grab()` give one sequence exclusive use of a sequencer: while it holds the lock, no other sequence's items are granted there. `lock()` waits its turn in the arbitration queue; `grab()` goes to the front of it (IEEE 1800.2-2020 §14.2.5.5, §14.2.5.6). The full arbitration rules are in [Sequence Arbitration](/curriculum/T2_Intermediate/I-UVM-3B_Advanced_Sequencing_and_Layering/sequence-arbitration); in a multi-agent bench, two details decide whether your lock does anything at all.

1. **With no argument, the lock goes to your own default sequencer.** A virtual sequence's default sequencer is `v_sqr`. `grab()` called in the virtual sequence therefore locks `v_sqr`, which grants no items, and the data traffic keeps flowing. Pass the agent's handle, or (better) do the grab in a child that runs on that agent's sequencer.
2. **A lock never blocks the holder's own descendants.** In uvm-core 2020.3.1, `uvm_sequencer_base::is_blocked()` lets through every sequence for which the lock holder is a parent, grandparent and so on (`is_child()`, §15.3.2.2). So if the virtual sequence started the background stream with `this` and then calls `grab(p_sequencer.data_sqr)`, the stream is its child and keeps running. The grab must be held by a sibling child: a small `quiesce_seq` on `data_sqr`.

```systemverilog
// snippet: a child that pauses other traffic on data_sqr while the vseq reconfigures
class quiesce_seq extends uvm_sequence #(stream_item);
  `uvm_object_utils(quiesce_seq)
  uvm_event paused, resume;                // set by the virtual sequence before start()
  function new(string name = "quiesce_seq");
    super.new(name);
  endfunction
  virtual task body();
    grab();                                // no argument: locks data_sqr, where it runs
    paused.trigger();
    resume.wait_trigger();                 // the vseq triggers resume after this waits
    ungrab();                              // before returning, or UVM_ERROR [SEQFINERR]
  endtask
endclass
```

**Semaphore or lock?** A SystemVerilog `semaphore` (IEEE 1800-2023 §15.3) only serializes the threads that call `get()` on it. Other sequences on the same sequencer know nothing about it and keep sending. Use a semaphore to share a testbench resource between your own threads; use `lock()`/`grab()` when the thing to protect is an agent's sequencer. And use neither just to make two agents take turns: serializing them in the testbench removes exactly the concurrency the DUT's own arbitration should be stressed with.

### Synchronization objects across agents

Sequences on different agents often need to wait for each other without being parent and child. UVM gives you named objects for this; [I-UVM-1C](/curriculum/T2_Intermediate/I-UVM-1C_UVM_Phasing/index) owns their semantics, and [I-UVM-5](/curriculum/T2_Intermediate/I-UVM-5_UVM_Container_Classes/index) the pools that share them by name. Here they are side by side, in multi-agent terms:

| Tool | What it blocks | Scope | Typical multi-agent use |
|---|---|---|---|
| `uvm_event` (§10.1) | callers of `wait_on`, `wait_trigger`, `wait_ptrigger` until a `trigger()` | whoever holds the handle (or the same key in a `uvm_event_pool`) | "configuration done", "interrupt seen", a monitor signalling a virtual sequence |
| `uvm_barrier` (§10.3) | each caller of `wait_for()` until *threshold* callers are waiting | whoever holds the handle | several agents' bring-up threads all ready before traffic starts |
| `semaphore` (IEEE 1800-2023 §15.3) | callers of `get()` until enough keys are returned | only the threads that use it | one shared testbench resource (a memory model, a file) |
| `lock()` / `grab()` (§14.2.5.5–§14.2.5.8) | other sequences' item requests on one sequencer | every sequence on that sequencer except the holder and its descendants | atomic register sequences, pausing traffic for a reconfiguration or an interrupt service |

**`uvm_event` is a state, not a pulse.** `trigger()` resumes every waiting process (§10.1.2.2.4) and turns the event **on**, and it stays on until `reset()` (§10.1.1.2.2). The three waits differ in what they do with a trigger that already happened:
- `wait_on()` returns at once if the event is on; otherwise it waits for the trigger (§10.1.1.2.2).
- `wait_trigger()` always waits for the **next** trigger. If it is called after the trigger, it waits for one that may never come (§10.1.1.2.4).
- `wait_ptrigger()` also accepts a trigger that happened earlier **in the same time slot**, and no earlier (§10.1.1.2.5).

  ]}
/>

**The rules this gives you.**
- Wait for a condition that may already be true with `wait_on()`; that is why the visual's `fork + uvm_event` variant uses it.
- Before reusing an event, `reset()` it, and do so when nobody is waiting on it. In uvm-core 2020.3.1, `reset()` with the default `wakeup = 0` replaces the event's internal SystemVerilog event, so a thread already blocked in `wait_trigger()` is never woken (IEEE 1800.2-2020 §10.1.1.2.8 only says that `wakeup = 1` activates such waiters first). Check `get_num_waiters()` (§10.1.1.2.10) or use `reset(1)`.
- A **monitor** is the right place to trigger a hardware-driven event: a passive agent cannot run a sequence, but its monitor (or a subscriber on its analysis port) can trigger a named event that a virtual sequence waits on. [Interrupt Handling](/curriculum/T2_Intermediate/I-UVM-3B_Advanced_Sequencing_and_Layering/interrupt-handling) builds the robust version, with a queue.

**`uvm_barrier` waits for a head count.** Every participant calls `wait_for()`; all of them are released when the number waiting reaches the threshold (§10.3.2.2). A barrier created with `new("sync")` and no threshold has threshold 0 (§10.3.2.1), so nothing ever blocks: set it with `set_threshold(3)` (§10.3.2.6) for three participants. If a participant is killed while waiting, call `cancel()` (§10.3.2.8) or lower the threshold, or the others wait for ever.

```systemverilog
// snippet: three agents' bring-up threads meet before traffic starts
uvm_barrier ready = new("ready");
ready.set_threshold(3);              // the default threshold is 0: nothing would block
fork
  begin cfg_seq.start(p_sequencer.apb_sqr, this);  ready.wait_for(); end
  begin link_up_seq.start(p_sequencer.data_sqr, this); ready.wait_for(); end
  begin irq_check_seq.start(p_sequencer.irq_sqr, this); ready.wait_for(); end
join                                 // all three return together
```

### Checking across agents

A **cross-agent scoreboard** predicts one interface's traffic from what it sees on several others. For `dma_stream` it needs three inputs: the configuration (to know `EN` and `MODE`), the data in (to predict), and the data out (to compare). Give it one analysis imp per input. The `` `uvm_analysis_imp_decl(SFX) `` macro (IEEE 1800.2-2020 Annex B.5.22) declares a new imp class whose `write()` calls your `write_SFX()` method, so one component can have three differently named write methods.

**Design rules for cross-agent checking.**
- **Follow the configuration from the bus, not from the test.** The scoreboard learns `MODE = 1` from the configuration monitor at the edge the write completes, so it is right even when someone else's sequence did the write.
- **Check ordering, not only data.** Data that arrives while `EN = 0` is dropped by the DUT, so a scoreboard that predicted it would report a MISSING item, which looks like a DUT bug. Not predicting it at all would hide a broken test. Reporting it as `ORDER` names the real cause: the stimulus broke the ordering rule. This is the check that catches the mutant test in Make It Work.
- **Do not infer order from arrival order within one time slot.** Two monitors that call `write()` at the same clock edge do so in an order the standard leaves open (IEEE 1800-2023 §4.7). If a `MODE` write and a data item can be sampled at the same edge, stamp each transaction with its sampling time and apply the configuration by time, or (as here) make the sequence guarantee they never coincide.
- **Account at the end of the test.** Anything still in `expected[$]` in `check_phase` is an error, and `report_phase` prints one summary line: `SCB_SUMMARY matches=N mismatches=0 pending=0`. [A-UVM-6](/curriculum/T3_Advanced/A-UVM-6_Scoreboards_and_Reference_Models/index) covers matching, ordering and draining in depth, and [A-UVM-4A](/curriculum/T3_Advanced/A-UVM-4A_RAL_Fundamentals/index) replaces the hand-written `en`/`mode` state with a register model and its predictor.

### Where each check lives: per-agent checkers and shared scoreboards

Not every check needs that. A rule about one interface's own protocol needs only that interface, so it belongs to the agent: in its interface as an assertion, or in its monitor. Before you read the table, decide where "APB never raises `penable` without a setup cycle first" should live.

| Where the check lives | What it checks | What it needs | It travels with | Example |
|---|---|---|---|---|
| **Per-agent checks:** assertions in the agent's interface (signal timing); the monitor or a subscriber on its analysis port (transaction rules) | one interface's protocol rules | that interface only | the agent (a VIP ships them) | APB setup cycle before every access (assertion); every transfer completes within a configured number of cycles (subscriber) |
| **Block (env) scoreboard** | the block's end-to-end behaviour | the block's monitors | the block env, into every bench that reuses it vertically | `soc_scoreboard` |
| **Per-instance scoreboard** | one copy of a repeated block | that instance's monitors | each instance in horizontal reuse | `ch0.scb`, `ch1.scb` |
| **Shared system scoreboard** | rules that span blocks or instances | monitors from several envs | the level where the rule exists | an end-to-end check from block A's input to block B's output; two channels sharing one output port |

**The rules behind the table.**
- **Put each check at the lowest level that has all the information it needs.** A protocol rule placed in a system scoreboard is lost the moment the agent is reused elsewhere; an end-to-end rule placed in an agent cannot see the other side.
- **Give every check one owner.** If `b_scb` and a subsystem scoreboard both predict the internal bus, they can disagree, and two error messages for one bug slow the debug. Decide which is the reference for each path, and switch the other off with a configuration bit.
- **Prefer one scoreboard per independent instance** over one shared scoreboard keyed by channel: the failures name the channel, and each instance is reusable alone. Use a **shared, keyed** scoreboard (an associative array of expected queues indexed by a channel or ID field) only when the DUT merges the streams, for example two input channels sharing one output port, because then only a component that sees both inputs can predict the merged output.
- **A per-agent checker does not replace the scoreboard.** It proves each interface is legal; it cannot prove the DUT computed the right data.

The Make It Work agents leave the per-agent checkers out to keep the code short; [A-UVM-7](/curriculum/T3_Advanced/A-UVM-7_VIP_Construction/index) shows how a VIP ships its own protocol checks with a switch to turn them off.

### When a multi-agent test hangs or passes silently

Most multi-agent failures announce themselves late: a watchdog fatal after every item matched, or no error at all. Read the log for these signatures.

| Symptom in the log | Cause | Fix |
|---|---|---|
| `UVM_FATAL [PH_TIMEOUT]` after every item matched | a `forever` branch (the responder) inside the same `fork…join` as the foreground threads, so `body()` never returns | start the responder in its own `fork…join_none` |
| `UVM_FATAL [SEQ] neither the item's sequencer nor dedicated sequencer has been supplied…` at the first `start_item()` | a child started on a passive agent's null handle **without** a parent; also with `this` when the virtual sequence itself was started with `start(null)` | null-check the handles at the top of `body()` |
| no message until `PH_TIMEOUT`; the responder or child never sent anything | a null handle **with** `this`, while the virtual sequence runs on `v_sqr`: uvm-core 2020.3.1 falls back to the parent's sequencer (`v_sqr`), which no driver ever pulls from, so `start_item()` waits for ever | the same null check: turn the hang into a `` `uvm_fatal `` |
| `UVM_FATAL [DCLPSQ] … Error casting p_sequencer` inside `start()` | the same fallback, when the child declares `` `uvm_declare_p_sequencer `` for its agent's sequencer type and receives `v_sqr` | the same null check |
| the test never ends; `+UVM_OBJECTION_TRACE` names a sequence | a background sequence with `set_automatic_phase_objection(1)` and a `forever` body (§14.2.4.4 NOTE), or a manual `raise_objection` in a thread that was killed before its drop. The automatic objection is raised only on the sequence's **starting phase**, so this applies to a default sequence or one given `set_starting_phase()` before `start()`; a child started from a virtual sequence has none, and its automatic objection does nothing | raise objections in the test or the top virtual sequence only, never in background sequences |
| the run ends at 0 ns, or the count check fails | the foreground work was put in `join_none` (or `join_any`), so `body()` returned early | link: the fork patterns in [I-UVM-3B](/curriculum/T2_Intermediate/I-UVM-3B_Advanced_Sequencing_and_Layering/uvm-virtual-sequencer) |
| a second wait returns immediately, before the second event | the `uvm_event` is still on from the first trigger | `reset()` it before re-arming, when nobody is waiting |
| other traffic still interleaves with your "exclusive" sequence | `grab()` with no argument in the virtual sequence (locks `v_sqr`), or the traffic is the grabber's own descendant | grab in a child that runs on the agent's sequencer |
| `UVM_ERROR [SEQFINERR]` | a sequence returned while it (or a descendant) still held a lock or grab | `ungrab()`/`unlock()` before `body()` returns |
| a simulator null-object error (no UVM id) in an agent's `build_phase` | the env called `set()` with an agent object the test never created, so `get()` returned 1 with a null handle | null-check every agent object in the env before `set()`, and test `cfg == null` in the agent's guard |
| `UVM_ERROR [ORDER]` (and `ORDER_SVA`) with no mismatches | data reached the DUT while `CTRL.EN = 0`: configuration and data were not ordered | order them in `body()`: sequential `start()` or an event with `wait_on()` |

**Tools that shorten the hunt.** `uvm_root::get().print_topology()` (Annex F.7.4.2) shows what was really built, so a passive agent's missing `sqr` is visible at time 0. uvm-core 2020.3.1 adds `+UVM_OBJECTION_TRACE` and `+UVM_PHASE_TRACE` (implementation, not 1800.2); `phase.get_objection().get_objectors()` (§10.5.1.5.1) lists who still objects. A short `set_timeout()` in the test (Annex F.7.3.3) turns a 9200 s wait into a quick fatal.

## Make It Work

### The complete bench

One file holds the DUT, three interface types, a package with every class, and `tb_top`. It is the M5 shape: a configuration agent and a data agent ordered by a virtual sequence, a mid-stream reconfiguration, a background responder that does not block the end of the test, a passive output agent, a cross-agent scoreboard with an ordering check, an ordering assertion, and a mutant test that must fail.

```systemverilog
// compile: dma_stream_tb.sv: the DUT, the interfaces, soc_pkg and tb_top
`timescale 1ns/1ps
`include "uvm_macros.svh"

// ======================================================================= DUT
module dma_stream (
  input  logic       clk,
  input  logic       rst_n,
  input  logic       psel,          // configuration port (APB-style subset)
  input  logic       penable,
  input  logic       pwrite,
  input  logic [3:0] paddr,
  input  logic [7:0] pwdata,
  output logic       pready,
  input  logic       din_valid,     // data in
  input  logic [7:0] din,
  output logic       dout_valid,    // data out, two cycles after acceptance
  output logic [7:0] dout,
  output logic       irq,           // after every 4th accepted item
  input  logic       irq_ack
);
  logic       ctrl_en;              // CTRL[0] at 0x0: accept data only when 1
  logic       mode;                 // MODE[0] at 0x4: 1 = invert the data
  logic       accept;
  logic [1:0] vld_q;
  logic [7:0] dat_q0, dat_q1;
  logic [1:0] acc_cnt;

  assign pready = 1'b1;             // no wait states
  assign accept = din_valid && ctrl_en;

  always_ff @(posedge clk or negedge rst_n) begin
    if (!rst_n) begin
      ctrl_en <= 1'b0;
      mode    <= 1'b0;
    end else if (psel && penable && pwrite) begin
      if (paddr == 4'h0) ctrl_en <= pwdata[0];
      if (paddr == 4'h4) mode    <= pwdata[0];
    end
  end

  // MODE is applied when an item is accepted; data sent while CTRL.EN = 0 is lost
  always_ff @(posedge clk or negedge rst_n) begin
    if (!rst_n) begin
      vld_q  <= 2'b00;
      dat_q0 <= 8'h00;
      dat_q1 <= 8'h00;
    end else begin
      vld_q  <= {vld_q[0], accept};
      dat_q0 <= mode ? ~din : din;
      dat_q1 <= dat_q0;
    end
  end
  assign dout_valid = vld_q[1];
  assign dout       = dat_q1;

  // irq rises after every 4th accepted item and stays high until irq_ack
  always_ff @(posedge clk or negedge rst_n) begin
    if (!rst_n) begin
      acc_cnt <= 2'd0;
      irq     <= 1'b0;
    end else begin
      if (accept) acc_cnt <= acc_cnt + 2'd1;
      if (accept && acc_cnt == 2'd3) irq <= 1'b1;
      else if (irq_ack)              irq <= 1'b0;
    end
  end
endmodule

        return;

      expected.push_back(mode ? ~t.data : t.data);

        n_mismatch++;

        return;
      end
      exp = expected.pop_front();
      if (t.data == exp) n_match++;
      else begin
        n_mismatch++;
        `uvm_error("MISMATCH", $sformatf("got 0x%02h, expected 0x%02h", t.data, exp))
      end
    endfunction
    function void check_phase(uvm_phase phase);
      if (expected.size() != 0)
        `uvm_error("PENDING", $sformatf("%0d outputs never arrived", expected.size()))
    endfunction
    function void report_phase(uvm_phase phase);
      `uvm_info("SCB_SUMMARY", $sformatf("matches=%0d mismatches=%0d pending=%0d",
                n_match, n_mismatch, expected.size()), UVM_NONE)

  class soc_vseq extends uvm_sequence;
    `uvm_object_utils(soc_vseq)
    `uvm_declare_p_sequencer(soc_vsqr)
    function new(string name = "soc_vseq");
      super.new(name);
    endfunction
    virtual task body();
      dma_cfg_seq       cfg_seq;
      stream_seq        data_seq;
      irq_responder_seq irq_seq;
      // 1. A passive agent has a null handle: fail now instead of hanging later
      if (p_sequencer.apb_sqr == null || p_sequencer.data_sqr == null ||
          p_sequencer.irq_sqr == null)
        `uvm_fatal("VSEQ", "soc_vseq needs apb_agt, data_agt and irq_agt active")
      // 2. The background responder: its own fork...join_none, never in a join
      irq_seq = irq_responder_seq::type_id::create("irq_seq");
      fork
        irq_seq.start(p_sequencer.irq_sqr, this);
      join_none
      // 3. Configure before any data: start() returns after the last write
      cfg_seq = dma_cfg_seq::type_id::create("cfg_seq");
      cfg_seq.mode = 1'b0;
      cfg_seq.start(p_sequencer.apb_sqr, this);
      // 4. Burst 1, MODE = 0
      data_seq = stream_seq::type_id::create("data_seq");
      data_seq.start(p_sequencer.data_sqr, this);
      // 5. Reconfigure at a safe point: every item of burst 1 has been sampled
      cfg_seq = dma_cfg_seq::type_id::create("cfg_seq");
      cfg_seq.mode = 1'b1;
      cfg_seq.start(p_sequencer.apb_sqr, this);
      // 6. Burst 2, MODE = 1
      data_seq = stream_seq::type_id::create("data_seq");
      data_seq.start(p_sequencer.data_sqr, this);
      // 7. Both interrupts answered? Then stop the responder ourselves
      wait (irq_seq.served == 2);
      irq_seq.kill();
    endtask
  endclass
```

### How to build any multi-agent environment

1. **List the DUT's interfaces** and, for each one, who drives it in this configuration. That answer is the agent's mode.
2. **Write one configuration object per agent** (mode, virtual interface, switches) and **one environment object** that holds them all, plus topology switches such as `has_scoreboard` or an agent count.
3. **Publish the virtual interfaces from `tb_top`** before `run_test()`; the test stores them in the objects and sets the environment object once.
4. **In the env, null-check every agent object, set each one at its agent's own path, then create the agent.** Agents check both `get()` and `cfg != null`, copy `cfg.is_active`, and build their sequencer and driver only when active.
5. **Wire the virtual sequencer in `connect_phase`**, accepting that a passive agent's handle is null, and null-check the handles at the top of every virtual sequence that needs them.
6. **Define the scoreboard's inputs and its state:** which monitor carries configuration, which carries inputs to predict, which carries outputs to compare, and the ordering rule it enforces.
7. **Write the virtual sequence's order** with sequential `start()` calls or events, and pick a safe point for every reconfiguration.
8. **Decide how background traffic runs and stops:** its own `fork…join_none`, no objections inside it, and an explicit `kill()` (or a cooperative stop) when the scenario is over.
9. **Decide the end of the test:** one objection around the top virtual sequence, a drain time that covers the DUT's latency, and a `set_timeout()` short enough that a hang fails fast.
10. **Write a mutant** that breaks your ordering rule, and prove your checks catch it.

**Checklist before moving on:**
- [ ] Every agent's mode follows from "who drives this interface here?", and the mode is set only in a configuration object.
- [ ] The env fatals on a null agent object before `set()`, and every agent's guard checks both `get()` and `cfg != null`, so a missing object or path fails with a named UVM fatal, never a bare null-object crash.
- [ ] `v_sqr`'s handles are assigned in `connect_phase`, and the virtual sequence fails fast with a clear `` `uvm_fatal `` on a null handle.
- [ ] Configuration completes before data in `body()`, and each reconfiguration happens at a point where its effect on in-flight data is defined.
- [ ] The responder sits in its own `fork…join_none`, raises no objection, and is stopped explicitly.
- [ ] The scoreboard follows the configuration from the configuration monitor and reports ORDER, not MISSING, for data sent while disabled.
- [ ] The mutant test fails with ORDER errors, and the real test ends with `SCB_SUMMARY matches=8 mismatches=0 pending=0` and no errors.

## Push Further

### Expert: what a null child sequencer really does

IEEE 1800.2-2020 §14.2.3.1 (`start`) and §14.1.2.5 (`get_sequencer`) do not say what happens when `start()` receives a null sequencer and a parent. uvm-core 2020.3.1 decides it in `uvm_sequence_item::set_item_context()`: `if (sequencer == null && m_parent_sequence != null) sequencer = m_parent_sequence.get_sequencer();`. So the symptom of starting a child on a passive agent's handle depends on two things:

| Child started with | Virtual sequence started with | Result (uvm-core 2020.3.1) |
|---|---|---|
| `start(null_handle)` | anything | `UVM_FATAL [SEQ]` at the child's first `start_item()` |
| `start(null_handle, this)` | `vseq.start(null)` | the parent's sequencer is null too: the same `[SEQ]` fatal |
| `start(null_handle, this)` | `vseq.start(env.v_sqr)` | the child runs on `v_sqr`; `start_item()` waits for a grant that only a driver's `get_next_item()` could produce, so it hangs until `PH_TIMEOUT` |
| the same, child declares `` `uvm_declare_p_sequencer(irq_sequencer) `` | `vseq.start(env.v_sqr)` | `UVM_FATAL [DCLPSQ]` inside `start()`, when the cast of `v_sqr` to the child's sequencer type fails (Annex B.3.3; `uvm_sequence_defines.svh`) |

The silent hang is the dangerous one, and it gets worse when the child was a background responder in `join_none`: if the test's own work finishes, the run phase ends normally and the test **passes** with a responder that never answered anything. The defence is the null check at the top of `body()`. [Virtual Sequences and Sequencers](/curriculum/T2_Intermediate/I-UVM-3B_Advanced_Sequencing_and_Layering/virtual-sequences) has the same rule from the sequence's side.

### Expert: lock and grab across a virtual sequence

- **Descendants pass.** uvm-core 2020.3.1 `uvm_sequencer_base::is_blocked()` returns 0 for any sequence whose ancestry reaches the lock holder (`is_child()`, §15.3.2.2, §15.3.2.8). A virtual sequence that grabs `data_sqr` therefore never pauses traffic it started with `this`; a sequence started with no parent is not a descendant of anything, so it waits like any other.
- **Nested holders block each other.** §15.3.2.9 notes that even when a sequence holds a lock, a child that also holds one still blocks it. If the reconfiguration child grabs a sequencer its parent has `lock()`ed, the parent's own items wait until the child releases.
- **Ending while holding.** When a sequence finishes while it or a descendant still has a lock or a queued request on a sequencer it used, uvm-core's `remove_sequence_from_queues()` reports `UVM_ERROR [SEQFINERR]` and removes them. `kill()` (§14.2.5.11) removes the killed sequence's locks, grabs and requests on its default sequencer without that error.
- **A grab is not pre-emption.** `grab()` is granted ahead of queued requests (§14.2.5.6), but an item the driver is already executing completes first. If the reconfiguration must happen at an exact item boundary, count items in the monitor and trigger from there.

**Interview angle:** "Your reconfiguration sequence grabs the data sequencer, and background traffic still interleaves. Name two causes." The grab was made by the traffic's ancestor, or with no argument on the virtual sequencer.

### Expert: `uvm_event` is a state, and its pool keys are typo-prone

- **On until reset.** §10.1.1.2.2 says that once the event has been triggered, it stays on until it is reset. Any loop that waits for "the next completion" with `wait_on()` must `reset()` between iterations, or the second wait returns on the first trigger.
- **What `reset()` does to waiters.** §10.1.1.2.8 says `reset(1)` activates the processes blocked in `wait_trigger()`/`wait_ptrigger()` before resetting. With the default `reset(0)`, uvm-core 2020.3.1 assigns a fresh SystemVerilog event to its internal `m_event`; a process already blocked on the old event is never resumed (an event's waiters are bound to the event object they waited on; compare IEEE 1800-2023 §15.5.5.1 on merged events). Reset only with no waiters, or use `reset(1)`.
- **Same-slot races.** `wait_ptrigger()` is built on the SystemVerilog `triggered` property, which persists only through the time slot of the trigger (IEEE 1800-2023 §15.5.3, uvm-core `uvm_event.svh`). It removes the race between a trigger and a wait in the same time slot; it does nothing for a wait that starts one cycle later. That case needs `wait_on()`.
- **Pools create on lookup.** `uvm_event_pool::get(key)` creates the event if no event has that key (§10.4.1.2.4). A monitor that triggers `"dma_done"` and a sequence that waits on `"dma_dn"` simply use two different events, with no warning, and the wait hangs. Put the key strings in a shared package as `localparam string` constants.
- **Debugging.** `get_num_waiters()` (§10.1.1.2.10) and `get_trigger_time()` (§10.1.1.2.6) tell you who is stuck and whether the trigger ever happened.

### Expert: barriers with changing membership

The barrier's threshold is a head count fixed in advance, so it breaks when the set of participants changes during the test.
- `new()` defaults the threshold to 0 (§10.3.2.1), and uvm-core's `wait_for()` returns as soon as the waiter count reaches the threshold, so an unset barrier never blocks.
- Auto-reset is on by default (§10.3.2.4): after a release, the next arrivals block again until the threshold is met again. Turn it off and later arrivals pass straight through until `reset()`.
- Lowering the threshold to fewer than the processes already waiting resets the barrier and releases them all (§10.3.2.6). That is how to shrink a group when an agent is disabled mid-test.
- A participant that is killed while waiting leaves the count one too high; call `cancel()` (§10.3.2.8) from whoever killed it.
- `reset()` defaults to `wakeup = 1` (§10.3.2.3), unlike `uvm_event::reset()`. Mixing up the two defaults is a common source of stranded threads.

### Expert: ending background traffic cleanly

- **What the language does.** `wait fork` waits for the current process's immediate children (IEEE 1800-2023 §9.6.1), so a `wait fork` after starting a `forever` responder never returns. `disable fork` kills all descendants of the calling process (§9.6.3), including sequence threads, without telling UVM.
- **What uvm-core does.** When the run phase ends, uvm-core kills the processes forked for it (`uvm_phase_hopper.svh`). `kill()` on a sequence is §14.2.5.11; in uvm-core 2020.3.1 its `m_kill()` also kills every child in `children_array` before the sequence itself, so killing a virtual sequence stops everything it started with `this`. `stop_sequences()` (§15.3.2.14) kills everything on one sequencer.
- **Process guards.** uvm-core 2020.3.1 adds a guard (not in 1800.2): if the process that called `start()` is killed while the sequence still runs, it reports `UVM_WARNING [SEQPRTZMB]` and kills the sequence; if `start()`'s own child process is killed, for example by an errant `disable fork`, it reports `[SEQBDYZMB]`. Whether the guard fires for a responder still running when the run phase ends was not confirmed in a simulator for this lesson: by source inspection it can, so the Make It Work bench stops its responder explicitly with `irq_seq.kill()`. Confirm your own tool's behaviour before relying on the phase-end kill.
- **Alternatives.** A responder can be the **default sequence** of its sequencer's run phase (§15.3.5, set through the resource database or `+uvm_set_default_sequence`, Annex G.2.9); uvm-core kills it when the phase ends. Or give it a cooperative stop: a `stop` flag it checks between items. Both are cleaner than `disable fork`.

### Expert: who may object

- **Never on a `forever` sequence.** §14.2.4.4 NOTE: do not set the automatic phase objection on a sequence whose body has a `forever` loop, "as the objection will never get dropped". Background responders must not object at all.
- **Only with a starting phase.** The automatic objection is raised on the sequence's **starting phase** (§14.2.4.4, §14.2.4.1). A default sequence gets one when its sequencer starts it for the phase; any other sequence has one only if you call `set_starting_phase(phase)` before `start()`. uvm-core 2020.3.1 `start()` raises only when `get_starting_phase()` is not null and does not copy the parent's phase, so a child started from a virtual sequence with `start(sqr, this)` raises nothing, whatever `set_automatic_phase_objection(1)` says. That is why the forever-sequence hang needs a default sequence or an explicit `set_starting_phase()`, and also why turning the automatic objection on in a child does not keep the phase alive for it.
- **Kills and objections.** uvm-core 2020.3.1 `kill()` drops the **automatic** phase objection if the killed sequence raised one. A **manual** `raise_objection()` inside a thread that is later killed (by `disable fork` or `kill()`) is never dropped, and the test runs into the timeout. Raise objections in the test or the top virtual sequence, around work that ends.
- **Draining.** The last outputs appear after the stimulus ends. `set_drain_time()` (§10.5.1.3.7) delays the end of the phase by a fixed time after the last drop; `phase_ready_to_end()` (§13.1.4.3.2) lets a component, such as a scoreboard with pending items, raise an objection again until it is satisfied. A fixed drain time is simpler; the callback scales to DUTs with variable latency.
- **Tracing.** `+UVM_OBJECTION_TRACE` and `display_objections()` are uvm-core 2020.3.1 implementation; `get_objectors()` (§10.5.1.5.1) is standard.

### Expert: configuration architecture at scale

- **One object or many entries.** One environment object per env is easier to audit, copy and randomize than dozens of scalar `uvm_config_db` settings, and it makes "every agent is configured" a single check. Wildcard settings matched by many components cost lookup time in big environments; [E-PERF-1](/curriculum/T4_Expert/E-PERF-1_UVM_Performance/index) measures that trade-off, so no numbers are quoted here.
- **Who wins on `is_active`.** §13.4.2.2 says the `is_active` configuration parameter of an agent may be set as `uvm_active_passive_enum` or as a string, which is what `+uvm_set_config_string=<path>,is_active,UVM_PASSIVE` (Annex G.2.8) provides. An agent that then copies `cfg.is_active` over the field silently ignores that command-line setting. Document which source your VIP honours, or make the config object read the field instead.
- **Audit the result.** `uvm_root::get().print_topology()` (Annex F.7.4.2) in `end_of_elaboration_phase` prints the tree that was really built; a regression can compare it with the intended topology.
- **Per-agent switches.** Coverage and checks enabled per agent (in the agent's object) let a subsystem test disable a block's checker on an interface that the subsystem scoreboard already covers, without editing either env.

### Expert: reuse at scale, vertical and horizontal

- **Instance count from configuration.** For a DUT with N identical channels, build `ch[i]` in a loop from a count in the environment object, publish the per-channel virtual interfaces from a `generate` loop in `tb_top` (instance selects must be constant, IEEE 1800-2023 §23.6), and size the top virtual sequencer's handle array from the same count. One number then controls the whole topology.
- **Independence is a property you test.** Start the same virtual sequence on every `ch_vsqr[i]` in parallel; per-instance scoreboards plus instance-qualified event names show at once whether any state leaks between instances (shared event keys, `static` members, wildcard configuration).
- **Instance overrides.** To make one instance differ (a mutant, a slower responder), use an instance override on that instance's path (§8.3.1.4.1) rather than a type override, which changes every instance.
- **Nested virtual sequencers or flat handles.** A subsystem virtual sequencer can hold the block virtual sequencers (as in the reuse diagram) or flat handles to every agent sequencer. Nested handles let block virtual sequences run unchanged as children; flat handles are simpler for scenarios that cut across blocks. Large benches usually keep both: block sequencers for reuse, a few flat handles for cross-block scenarios.
- **Register models compose too.** A block's register model is added to the subsystem model with `add_submap()` (IEEE 1800.2-2020 §18.2.3.5); [A-UVM-4A](/curriculum/T3_Advanced/A-UVM-4A_RAL_Fundamentals/index) and [A-UVM-4B](/curriculum/T3_Advanced/A-UVM-4B_Advanced_RAL_Techniques/index) cover the register layer.
- **Checks move inward.** At subsystem level, a block's input agent becomes passive and its scoreboard becomes a checker on an internal bus. That is valuable for localizing bugs, but it also means two checkers can disagree about the same traffic; decide which one is the reference for each path.
- **Strategy** at SoC scale (which block benches to keep, what to promote, when to switch to software-driven tests) is the subject of [E-SOC-1](/curriculum/T4_Expert/E-SOC-1_SoC-Level_Verification_Strategies/index).

### Kata 1: predict, then fix three planted bugs

This `body()` has three bugs. For each one, predict the log signature from the debugging table before you read the solution. Assume `soc_vseq` runs on `v_sqr`, and the test makes `irq_agt` passive.

```systemverilog
// snippet: a broken soc_vseq::body()
virtual task body();
  dma_cfg_seq       cfg_seq  = dma_cfg_seq::type_id::create("cfg_seq");
  stream_seq        data_seq = stream_seq::type_id::create("data_seq");
  irq_responder_seq irq_seq  = irq_responder_seq::type_id::create("irq_seq");
  uvm_event         cfg_done = new("cfg_done");
  fork
    begin
      cfg_seq.start(p_sequencer.apb_sqr, this);
      cfg_done.trigger();
    end
    begin
      #1us;                                       // stands for other work first
      cfg_done.wait_trigger();                    // bug A
      data_seq.start(p_sequencer.data_sqr, this);
    end
    irq_seq.start(p_sequencer.irq_sqr, this);     // bugs B and C
  join
endtask
```

<details>
<summary>Worked solution</summary>

- **Bug A: a missed trigger.** In the Make It Work timing, the three configuration writes finish at about 105 ns, long before the data branch reaches `wait_trigger()` at 1 us. The trigger is already past, so `wait_trigger()` waits for one that never comes: no data is ever sent, `join` never completes, and the run ends in `UVM_FATAL [PH_TIMEOUT]`. With a shorter delay the same code passes or fails depending on the APB timing, which is worse. Fix: `cfg_done.wait_on()`, which returns at once when the event is already on, and no delay.
- **Bug B: the responder in the `join`.** Even with A fixed, `join` waits for the `forever` responder: `UVM_FATAL [PH_TIMEOUT]` after every item matched. Fix: start it in its own `fork…join_none` before the foreground `fork`.
- **Bug C: a passive agent's null handle with `this`.** `p_sequencer.irq_sqr` is null, the vseq runs on `v_sqr`, so the responder falls back to `v_sqr` and hangs silently in `start_item()`. Once B is fixed (so nothing waits for it), the test can pass with no responder at all. Fix: the null check at the top of `body()`, which reports `UVM_FATAL [VSEQ]` and tells you to make `irq_agt` active.

You can check A and B in the visual above: `fork + uvm_event` is the corrected A, and `background in its own join_none` is the corrected B.

```systemverilog
// snippet: the fixed body()
virtual task body();
  dma_cfg_seq       cfg_seq  = dma_cfg_seq::type_id::create("cfg_seq");
  stream_seq        data_seq = stream_seq::type_id::create("data_seq");
  irq_responder_seq irq_seq  = irq_responder_seq::type_id::create("irq_seq");
  uvm_event         cfg_done = new("cfg_done");
  if (p_sequencer.irq_sqr == null)
    `uvm_fatal("VSEQ", "irq_agt is passive: no sequencer to answer interrupts")
  fork
    irq_seq.start(p_sequencer.irq_sqr, this);
  join_none
  fork
    begin
      cfg_seq.start(p_sequencer.apb_sqr, this);
      cfg_done.trigger();
    end
    begin
      cfg_done.wait_on();                         // returns at once if already on
      data_seq.start(p_sequencer.data_sqr, this);
    end
  join
  wait (irq_seq.served == 1);                     // 4 items: one interrupt to answer
  irq_seq.kill();                                 // stop the responder ourselves
endtask
```

</details>

### Kata 3 (expert): move the grab

A colleague's reconfiguration code is below. The background traffic `bg` keeps interleaving with the configuration writes. Explain why, and move the grab so the traffic pauses.

```systemverilog
// snippet: the colleague's version, inside soc_vseq::body()
fork
  bg.start(p_sequencer.data_sqr, this);     // background stream, runs for a while
join_none
#100ns;
grab(p_sequencer.data_sqr);                 // "pause the data path"
cfg_seq.start(p_sequencer.apb_sqr, this);
ungrab(p_sequencer.data_sqr);
```

<details>
<summary>Worked solution</summary>

`bg` was started with `this`, so it is a child of `soc_vseq`, and soc_vseq holds the grab. uvm-core's `is_blocked()` lets every descendant of the lock holder through, so `bg` is never blocked (the `#100ns` is a second smell: never use a delay for synchronization). The grab must be held by a sibling child that runs on `data_sqr`, the `quiesce_seq` from "Locking an agent's sequencer from a virtual sequence":

```systemverilog
// snippet: the fix
quiesce = quiesce_seq::type_id::create("quiesce");
quiesce.paused = new("paused");
quiesce.resume = new("resume");
fork
  quiesce.start(p_sequencer.data_sqr, this);  // grabs data_sqr, holds it until resume
join_none
quiesce.paused.wait_on();                     // the grab is held from here
cfg_seq.start(p_sequencer.apb_sqr, this);
quiesce.resume.trigger();                     // quiesce ungrabs and returns
```

`bg` is a sibling of `quiesce`, not its descendant, so its next request waits until the `ungrab()`. If `bg` had been started with no parent, the original grab would have worked, but then `kill()` on the virtual sequence would no longer stop it.

</details>
