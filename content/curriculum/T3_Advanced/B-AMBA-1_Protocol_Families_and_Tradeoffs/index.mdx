## Quick Take

- **What it is:** **AMBA** (Advanced Microcontroller Bus Architecture) is Arm's family of open specifications for the wires between blocks on one chip. A **system on chip (SoC)** is built from **IP blocks** (a CPU, a memory controller, a UART, a DMA engine), and each block talks to the rest through an **interface**: a defined set of signals plus rules for using them. AMBA gives you a menu of interfaces: **APB** for simple registers, **AHB** for a pipelined bus (the next transfer's address overlaps the current transfer's data), **AXI4** for high-throughput memory traffic, **AXI4-Lite** for registers on an AXI fabric, **AXI4-Stream** for data with no address, and **ACE** and **CHI** for systems whose caches must agree.
- **Why it matters:** The interface a block uses fixes its area, latency and concurrency. It also fixes your testbench (TB): which agent you build, how many threads its driver runs, which protocol rules your checkers enforce, whether your scoreboard can assume in-order completion, and what your coverage must hit. Pick the wrong interface and you pay twice, once in silicon and once in verification effort.
- **The Analogy:** Standard sockets and plugs. Any appliance with the right plug works in any matching socket, and an adapter (a **bridge**) lets one standard plug into another. *Where it breaks:* a socket standard only fixes the shape of the plug. AMBA also fixes timing, handshakes, ordering and error reporting, so a bridge must translate behaviour, not just rewire pins, and it adds latency. And one plug carries one thing, whereas an AXI interface carries five independent streams of information at once.

**You will be able to:**
1. Compare APB, AHB-Lite, AXI4, AXI4-Lite and AXI4-Stream on topology, channels or phases, bursts, outstanding transactions, ordering and typical use, and predict what appears on the bus for a given access.
2. Choose an interface for a described block, and justify the choice by what the block needs and what each alternative lacks or wastes.
3. Explain what an interconnect does (decode, arbitrate, route responses, return DECERR, bridge), and why a standard interface lets one verification IP (VIP) verify every block that uses it.
4. Place ACE, ACE-Lite and CHI in the family, and state what each adds to a verification plan.

### Why standard interfaces, and what an interconnect does

Without a standard, every pair of blocks that must talk needs custom glue logic. For *n* blocks that is up to about *n*² pairings, and each block becomes tied to its neighbours, so nothing can be reused in the next chip.

A standard fixes the interface once. The Arm AXI specification puts it precisely: AXI provides "a single interface definition" for the interfaces between a master and the interconnect, between a slave and the interconnect, and between a master and a slave (Arm IHI0022E §A1.3.2). Three terms from that sentence:

- A **master** starts transactions (a CPU, a DMA engine); a transaction is one complete request with its data and response, defined exactly in the vocabulary below. A **slave** responds to them (a memory controller, a register block). Later Arm issues rename these **manager** and **subordinate** (IHI0022H.b and IHI0033C, change history), and APB's latest issue says **requester** and **completer** (IHI0024E §1.1). This track uses master and slave, as in the issues it cites.
- An **interconnect** is the logic between masters and slaves. IHI0022E describes it as "equivalent to another device with symmetrical master and slave ports" (§A1.3.2). Its jobs:
  - **decode** each address against the address map and select the slave that owns it;
  - **arbitrate** when two masters want the same slave at once;
  - **route** each response back to the master that asked. On AXI every transaction carries an ID tag (the AXI section below covers IDs), and the interconnect appends the master's port number to it, so the slave sees a wider ID than the master sent (§A5.3.5);
  - **return DECERR** (decode error) when no slave owns the address; IHI0022E recommends a **default slave** that returns it (§A3.4.4);
  - **bridge** to other protocols, for example AXI to APB.
- How the interconnect is built inside is a design choice: IHI0022E lists shared address and data buses, a shared address bus with several data buses, and multilayer designs with many address and data buses (§A1.3.2). So "AXI is point to point" describes the *interface*, not the inside of the fabric.

**Why this matters for verification.** Because every AXI4 slave obeys the same interface rules, one AXI4 agent can verify every one of them. A **VIP** (verification IP) is such a reusable agent, plus its protocol checkers and coverage, packaged so other teams can drop it in ([A-UVM-7](/curriculum/T3_Advanced/A-UVM-7_VIP_Construction/index) builds one). At block level the agent is **active** and drives the block's port; at SoC level the same agent is **passive** and only watches an interconnect port. Block-level verification proves protocol compliance and function, so SoC tests can focus on connectivity, the address map and system scenarios ([E-SOC-1](/curriculum/T4_Expert/E-SOC-1_SoC-Level_Verification_Strategies/index)).

### Vocabulary for the whole AMBA track

IHI0022E §A1.4.2 defines three nested terms. Learn them exactly; every later module uses them.

- **Transaction:** the complete set of operations on the bus for one master request, for example "read 16 bytes from 0x100": the address, all the data and the response.
- **Burst:** the payload data of a transaction.
- **Beat** (or **transfer**): one data transfer of the burst. On a 32-bit data bus, one beat moves up to 4 bytes.

Four more terms:

- **Handshake:** how a sender and a receiver agree that information moved. AXI moves information on independent **channels** (each a group of wires carrying one kind of information, listed in the AXI section below), and each channel has a **VALID** signal (driven by the sender: "the information is valid") and a **READY** signal (driven by the receiver: "I can take it"); the information moves at a rising clock edge where both are high (IHI0022E §A1.3.1, §A3.2.1). [B-AMBA-2](/curriculum/T3_Advanced/B-AMBA-2_Protocol_Intuition_and_Memory_Hooks/index) builds the intuition and [B-AXI-1](/curriculum/T3_Advanced/B-AXI-1_AXI_Channel_Architecture/index) owns the rules.
- **Outstanding transaction:** one whose request has been accepted but whose last data or response has not yet returned. A master with several outstanding transactions hides memory latency by asking again before the first answer arrives.
- **Backpressure:** a receiver slowing a sender down, by holding READY low on AXI, PREADY low on APB, or HREADYOUT low on AHB (PREADY and HREADYOUT are the APB and AHB slaves' ready signals, covered in their sections below). On AXI any receiver can apply it, including a master that is not ready to accept read data; on APB and AHB only the slave can.
- **Response:** the status the slave returns: success, an error, or (on AXI) a decode error from the interconnect.

**A burst does not mean one address phase.** That depends on the protocol, and it is the first comparison this lesson makes. The waveform shows the AXI shape: one address handshake, then four beats. An AXI read uses two of AXI's five channels (the AXI section below lists all five): **AR** carries the address and the burst length, where ARLEN is the number of beats minus 1 (IHI0022E §A3.4.1), and **R** returns the data, with RLAST high on the final beat.

### The family, generation by generation

You will meet every generation in real chips, because IP lives for decades. Each row below is taken from the specifications' own release notes.

| AMBA generation | Protocols | Specification |
|---|---|---|
| AMBA 2 | AHB with request/grant arbitration inside the protocol (masters request the bus and an arbiter grants it to one); APB2 | IHI0011A, named by IHI0024C §1.2.1 (IHI0011A itself not checked here) |
| AMBA 3 | AXI3; APB3 (adds PREADY and PSLVERR) | IHI0022E Preface; IHI0024C §1.2 |
| AMBA 4 | AXI4, AXI4-Lite, ACE, ACE-Lite; AXI4-Stream | IHI0022E Preface; IHI0051A |
| AMBA 5 | AHB5; AXI5, AXI5-Lite, ACE5 and ACE5-Lite variants; CHI | IHI0033B.b; IHI0022G change history; IHI0050E.b |

Three more you will meet: **AHB-Lite** (IHI0033 issue A, 2006), **APB4** (adds PPROT, the protection attributes, and PSTRB, the write strobes; IHI0024C, 2010) and **APB5** (IHI0024 issue D, 2021). The issues checked here do not name an AMBA generation for them.

Two habits help. First, say the version: "AXI" alone is ambiguous, because AXI3 and AXI4 differ in burst length, write interleaving and locking (Push Further). Second, read the *issue* of the specification your IP was built to, because later issues add optional properties. AHB5 declares each new capability as a property that is False unless declared (IHI0033B.b §1.2), and AXI5 also declares its new capabilities as properties (IHI0022G §C1.1).

### APB: the register bus

**APB** (Advanced Peripheral Bus) "is not pipelined"; use it "to connect to low-bandwidth peripherals", and to "access the programmable control registers of peripheral devices"; "every transfer takes at least two cycles" (IHI0024C §1.1).

- **Mechanism:** PSEL selects the slave and PENABLE marks the second phase. A transfer goes IDLE → **SETUP** (PSEL high, PENABLE low, exactly one cycle) → **ACCESS** (PENABLE high) and stays in ACCESS until the slave drives PREADY high (§4.1). Each cycle with PREADY low is a **wait state**: it extends the transfer by one cycle (§3.3.2).
- **Data:** separate read and write data buses (PWDATA and PRDATA), up to 32 bits wide, which can never be active in the same transfer (§2.1.1).
- **Errors:** PSLVERR, optional, valid only in the last cycle of the transfer (§3.4).
- **Where it sits:** behind a bridge from AHB or AXI. Even the AHB specification says low-bandwidth peripherals "typically reside on the" APB (IHI0033B.b §1.1).

### AHB-Lite and AHB5: the pipelined bus

**AHB** is "suitable for high-performance synthesizable designs" (IHI0033B.b §1.1). IHI0033B.b defines two versions: **AHB-Lite** and **AHB5**, which adds optional properties such as Secure_Transfers and Exclusive_Transfers (§1.2). The word "AHB" in that specification means both.

**Structure.** A single-master AHB system needs only two pieces of interconnect logic (§1.1, §1.1.3):
- a **decoder**, which looks at the address and raises the select signal (HSELx) of the one slave involved;
- a **multiplexor**, which returns that slave's read data and response to the master.

The master's address, control and write data go to every slave; only the selected one acts.

**Separate data buses.** "Separate read and write data buses are required to implement an AHB system" (§6.1). A common misconception is that AHB has one multiplexed data channel that turns around between reads and writes; it does not.

**Phases and pipelining.** Every transfer has an **address phase** (one cycle, which a slave cannot ask to extend) and a **data phase** (one or more cycles) (§1.3). The two overlap: the next transfer's address phase happens during the current transfer's data phase. A slave that needs more time inserts **wait states** by driving HREADYOUT low; the multiplexor turns that into HREADY low, which also holds the next transfer's address phase, because that address phase overlaps the waiting data phase (§3.1). So at most one transfer is in its address phase and one in its data phase. That is pipelining, not many outstanding transactions.

**Bursts.** HBURST selects SINGLE, INCR (undefined length), INCR4/8/16 or WRAP4/8/16 (§3.5, Table 3-3). An incrementing (INCR) burst steps through sequential addresses. A wrapping (WRAP) burst wraps back to a lower address at a boundary equal to the number of beats times the transfer size, so a WRAP4 of words wraps at 16-byte boundaries (§3.5). HSIZE gives the transfer size: the bytes moved by each beat, for example Word for 4 bytes (§3.4, Table 3-2). Every beat still has its own address phase. The transfer type on HTRANS is NONSEQ for the first beat, then SEQ, with identical control and the previous address plus the transfer size, wrapping at the boundary for WRAP bursts (§3.2, Table 3-1). Predict how many address phases an INCR4 burst of words needs, then check the waveform.

Answer: four. Each beat has its own address phase: NONSEQ at edge 1, then SEQ at edges 2, 3 and 4, with the address rising by 4 bytes (one word) each time. Each beat's data arrives one edge after its address (edges 2 to 5), because each data phase overlaps the next address phase. HREADY stays 1, so there are no wait states. Compare the AXI waveform above: one address handshake for four beats.

**Responses.** HRESP is OKAY, or ERROR, which takes two cycles (§5.1, Table 5-1). AHB5 slaves with the Exclusive_Transfers property add HEXOKAY (§5.1, Chapter 8).

**Many masters.** AHB-Lite is single-master per bus. A multi-master system adds "an interconnect component that provides arbitration" (§1.1), and the specification leaves its design, single layer or multi-layer, out of scope (§1.1.3). The original AMBA 2 AHB put request/grant arbitration inside the protocol; that is the version older textbooks describe.

The AHB modules ([B-AHB-1](/curriculum/T3_Advanced/B-AHB-1_AHB_Design_Timing_Mechanics/index) onward) own wait-state timing and the 1KB rule for incrementing bursts.

### AXI3 and AXI4: independent channels

**AXI** (Advanced eXtensible Interface) is burst-based and defines five independent **channels** (IHI0022E §A1.3):

| Channel | Direction | Carries |
|---|---|---|
| AW, write address | master → slave | address and control for a write |
| W, write data | master → slave | write data, byte strobes (WSTRB), WLAST |
| B, write response | slave → master | one response for the whole write |
| AR, read address | master → slave | address and control for a read |
| R, read data | slave → master | read data, a response per beat, RLAST |

Each channel has its own VALID/READY handshake (§A1.3.1). Because the channels are independent, the protocol "permits address information to be issued ahead of the actual data transfer", "supports multiple outstanding transactions" and "supports out-of-order completion of transactions" (§A1.3). Only a few relationships are required: a write response follows the last write data beat, read data follows its address, and the handshake dependencies hold. Otherwise "write data can appear at an interface before the write address" (§A3.3).

- **Bursts:** AXI has three burst types (§A3.4.1). **INCR** steps through sequential addresses, for normal memory; **WRAP** wraps back to an aligned boundary, for cache-line accesses; **FIXED** repeats one address, for example to fill or empty a FIFO. AXI4 allows INCR bursts of 1 to 256 beats (1 to 16 in AXI3), FIXED bursts of 1 to 16 beats and WRAP bursts of exactly 2, 4, 8 or 16 beats, and no burst may cross a 4KB boundary (§A3.4.1). [B-AXI-2](/curriculum/T3_Advanced/B-AXI-2_AXI_Burst_Math/index) owns the burst arithmetic.
- **IDs and ordering:** each transaction carries an ID (AWID, ARID; BID and RID return it). Reads with the same ARID complete in order; reads with different ARIDs may complete in any order, and their data may interleave, meaning beats of one read can arrive between beats of another (§A5.3.1). Writes with the same AWID likewise complete in order (§A5.3). Reads and writes are not ordered against each other, "even if the ARID value of a read transaction is the same as the AWID value of a write transaction" (§A5.3.4). [B-AXI-3](/curriculum/T3_Advanced/B-AXI-3_AXI_Ordering_and_IDs/index) owns ordering.
- **Responses:** OKAY, EXOKAY (an **exclusive access**, AXI's read-then-conditional-write mechanism for semaphores, succeeded; [B-AXI-4](/curriculum/T3_Advanced/B-AXI-4_AXI_Expert_Features_Cache_Atomics/index) covers it), SLVERR (the access reached a slave, which reports an error) and DECERR (no slave at that address, typically from the interconnect). Reads carry a response on every beat; a write gets one response for the whole burst; and all data transfers must still happen after an error (§A3.4.4).

### AXI4-Lite: AXI channels for registers

**AXI4-Lite** is the AXI4 subset for simple register interfaces (IHI0022E §B1.1). It keeps the five channels and their handshakes, and removes everything a register access does not need. In the table, the prefix **Ax** stands for either address channel, so AxLEN means ARLEN or AWLEN, as the specification writes it (for example "AxLOCK indicates ARLOCK or AWLOCK", §A7.3). **AxPROT** carries protection attributes: privileged or unprivileged, Secure or Non-secure, instruction or data (§A4.7).

| AXI4-Lite… | Rule | Source |
|---|---|---|
| removes bursts | every transaction has burst length 1; there is no AxLEN, AxSIZE or AxBURST | §B1.1, Table B1-1 |
| uses the full bus | every access is the full data width, which must be 32 or 64 bits | §B1.1, §B1.1.2 |
| removes exclusive accesses | no AxLOCK; EXOKAY is never returned | §B1.1, §B1.1.1 |
| fixes memory attributes | no AxCACHE: every access is Non-modifiable, Non-bufferable, so no component may split or merge it and the response must come from the final destination | §B1.1, §B1.1.1; §A4.3.1, §A4.4 |
| removes IDs | so every transaction completes in order | §B1.1.4 |
| keeps outstanding transactions | a master may issue several; a slave can throttle them with READY | §B1.1.4 |
| keeps AxPROT and WSTRB | a slave may use, ignore or reject strobe patterns | Table B1-1, §B1.1.3 |

Signal count: AW (AWVALID, AWREADY, AWADDR, AWPROT), W (WVALID, WREADY, WDATA, WSTRB), B (BVALID, BREADY, BRESP), AR and R likewise (Table B1-1). Make It Work counts the wires.

Two misconceptions to retire now. "AXI4-Lite is AXI4 with fewer channels": no, it has all five. "AXI4-Lite supports short bursts": no, writing 16 consecutive words takes 16 separate transactions, each with its own AW, W and B.

### AXI4-Stream: data with no address

**AXI4-Stream** connects a master that generates data to a slave that receives it (IHI0051A §1.1). It has one channel and no concept of memory.

- **Signals:** only TVALID is mandatory (§3.1). TREADY and TDATA are optional but almost always present: a slave that can always accept data may omit TREADY, though Arm recommends keeping it (§3.1.1), and an interface may even have no TDATA payload (§3.1.5). The other optional signals qualify or route the data (Table 2-1): **TSTRB** marks each byte as a data byte or a position byte; **TKEEP** marks the bytes that are part of the stream (the others are null bytes that can be removed); **TLAST** marks a packet boundary; **TID** identifies one of several streams; **TDEST** carries routing information; and **TUSER** carries user-defined sideband information.
- **Handshake:** the same rule as AXI. A transfer happens when TVALID and TREADY are both high; a master must not wait for TREADY before asserting TVALID, and once TVALID is high it stays high until the transfer (§2.2.1).
- **No address, no read or write, no response.** TDEST is "routing information for the data stream", not a memory address (Table 2-1). Where the data lands in memory is decided by a receiving block such as a DMA engine.
- **Packets:** TLAST marks a packet boundary (§2.5). A packet "is similar to an AXI4 burst" (§1.1.2).
- **Ordering:** "all transfers remain ordered"; reordering is not permitted (§4.2).

Typical uses: video and DSP pipelines, packet processing, and the streaming side of a DMA engine. The misconception to retire: "AXI4-Stream carries addresses, just fewer of them". It carries none.

### Coherent protocols: ACE, ACE-Lite and CHI (placement only)

A **cache** keeps local copies of memory. When several masters have caches, the system must keep the copies consistent: this is **coherency**. A coherent interconnect can **snoop** a master's cache, meaning it asks the cache what it holds and tells it to clean or invalidate a line. Three AMBA protocols add this.

- **ACE** (AXI Coherency Extensions) is for masters with hardware-coherent caches, such as CPU clusters. It changes the existing channels and adds new ones (IHI0022E §C1.3):
  - extra signals on AR and AW (such as ARDOMAIN, ARSNOOP, ARBAR, AWDOMAIN, AWSNOOP, AWBAR, AWUNIQUE) and extra read response bits RRESP[3:2] (§C1.3.1). AxDOMAIN gives the transaction's shareability domain (the set of masters whose caches might hold a copy, so the interconnect knows which to snoop; §C1.6.1), AxSNOOP its coherent transaction type, and AxBAR marks a barrier transaction (§C2.1.1, §C2.1.2);
  - three snoop channels: **AC** (snoop address, *into* the master), **CR** (snoop response, out of it) and **CD** (snoop data, optional, out of it) (§C1.3.2);
  - the RACK and WACK acknowledge signals (§C1.3.3).
- **ACE-Lite** is for masters with *no* coherent cache that still need coherent access, such as an accelerator that reads buffers a CPU may hold **dirty** (the cache holds a newer value than memory). It is AXI4 plus the extra AR and AW signals only: no snoop channels, no RACK or WACK, no extra read response bits (§C11.1).
- **CHI** (Coherent Hub Interface, AMBA 5) is a different architecture for large systems. It is layered: a **protocol** layer of transactions, a **network** layer of packets with source and target node IDs, and a **link** layer of **flits** (flow-control units) with **link-layer credits** (IHI0050E.b §1.1.2, Table 1-1; §1.3). With credit-based flow control, a sender may send a flit only while it holds a credit from the receiver, and the receiver returns credits as its buffers free up, so it always has room for every flit it receives. Messages travel on separate request, response, snoop and data channels (REQ, RSP, SNP and DAT; §2.1, Table 2-1) between node types such as RN-F (a request node with a coherent cache), RN-I (I/O coherent, no cache) and HN-F (a home node that manages coherence) (§1.6).

What each adds to a verification plan:

| Protocol | The testbench gains |
|---|---|
| ACE | a snoop responder on AC, CR and CD; a model of each cache line's state; coherency checks across masters; coverage of snoop types and AR/AW domain, snoop and barrier fields |
| ACE-Lite | coherent request types on AR and AW only; checks that the data seen is coherent; no snoop responder |
| CHI | a flit-level VIP with link-layer credit flow control and node IDs; checking at the home nodes that order requests; a much larger scenario space |

Full depth is in [B-AMBA-F2](/curriculum/T3_Advanced/B-AMBA-F2_Future_Protocols_ACE_CHI/index).

### Comparing the family

| | APB | AHB-Lite | AXI4 | AXI4-Lite | AXI4-Stream |
|---|---|---|---|---|---|
| **Topology** | bridge to peripherals, one PSELx each | one master; decoder and multiplexor | point-to-point interface into any fabric | as AXI4 | master to slave; several streams can share wires (TID, TDEST) |
| **Channels or phases** | SETUP then ACCESS; separate PWDATA and PRDATA | overlapped address and data phases; separate HWDATA and HRDATA | five independent channels | five independent channels | one channel |
| **Bursts** | none | SINGLE, INCR, INCR4/8/16, WRAP4/8/16; an address phase per beat | INCR 1–256 beats, FIXED 1–16, WRAP 2/4/8/16; one address per burst | none (length 1) | none; TLAST marks packets |
| **Outstanding and IDs** | one transfer at a time, at least 2 cycles | one in address phase, one in data phase | many, tagged by ID | several, no IDs | nothing outstanding |
| **Ordering** | in order | in order | same ID in order; different IDs any order | in order | never reordered |
| **Responses** | PSLVERR (optional) | OKAY, ERROR (HEXOKAY in AHB5) | OKAY, EXOKAY, SLVERR, DECERR | OKAY, SLVERR, DECERR | none |
| **Byte strobes** | PSTRB (APB4) | none in IHI0033B.b | WSTRB | WSTRB | TKEEP, TSTRB (optional) |
| **Typical use** | control registers of low-bandwidth peripherals | memories and high-bandwidth peripherals in a single-master subsystem | DDR, DMA and other high-throughput paths | registers on an AXI fabric | video, DSP and packet pipelines |

ACE and ACE-Lite behave like AXI4 in every row, plus the coherency additions above. CHI does not fit these columns: it is packetized and credit-based (IHI0050E.b §1.1.2), so its transactions do not map onto them.

**Debrief.** The fit check works in two steps, and so should you. First it rules out every protocol that lacks something the block needs (an address, bursts, many transactions in flight, coherency). ### Design trade-offs and what each choice costs your testbench

Wires are only the visible cost. The real costs are:

- **Logic behind the wires:** ID tracking, outstanding-transaction buffers and reorder logic in AXI4 masters, slaves and interconnects; almost none in APB.
- **Latency per access:** an APB access through a bridge costs at least two APB cycles plus the bridge; that is irrelevant for registers written at boot and decisive for a memory path.
- **Concurrency:** among APB, AHB and AXI, only the AXI family lets reads and writes, and many transactions, proceed at once.
- **The neighbourhood:** if the SoC already has an AXI-to-APB bridge, a new peripheral on APB costs nothing extra in fabric.
- **Verification effort**, which you can predict from the protocol (engineering practice, not specified):

| | APB | AHB-Lite | AXI4-Lite | AXI4 | AXI4-Stream |
|---|---|---|---|---|---|
| **Driver** | one thread, one transfer at a time | one pipelined thread: next address during current data | one thread per channel, in order | one thread per channel plus ID bookkeeping | one thread |
| **Monitor** | sample when PSEL, PENABLE and PREADY are all 1 | pair each address phase with its data phase (the next HREADY-high edge) | match AW with W, and each with B, in order | match by ID; collect R beats per ID | collect transfers into packets at TLAST |
| **Checker families** | SETUP lasts one cycle; stable signals in ACCESS | HTRANS sequence; stable data under wait states | VALID held until handshake; stable payload | as Lite, plus burst rules, 4KB, WLAST count, ID rules | VALID held; stable payload; TLAST count preserved |
| **Scoreboard** | in order | in order | in order | one queue per ID | per packet, in order |
| **Coverage** | read/write, wait states, PSLVERR | burst types, wait states, ERROR | strobes, responses, backpressure | burst types and lengths, IDs, reordering, responses | packet lengths, TKEEP patterns, backpressure |

### Common misconceptions

1. **"AHB has a single multiplexed data channel."** Wrong: HWDATA and HRDATA are separate buses (IHI0033B.b §6.1). What the multiplexor selects is *which slave's* read data returns.
2. **"An AHB burst has one address phase."** Wrong: every beat has an address phase, NONSEQ then SEQ (§3.2). Only AXI sends one address per burst.
3. **"AXI4-Lite supports (short) bursts."** Wrong: every transaction is length 1 (IHI0022E §B1.1).
4. **"AXI4-Lite cannot have outstanding transactions."** Wrong: it can; it just has no IDs, so they complete in order (§B1.1.4).
5. **"AXI4-Stream carries addresses."** Wrong: it has none; TDEST is routing information (IHI0051A Table 2-1).
6. **"An AXI interconnect is always a full crossbar."** Wrong: the topology is a design choice (IHI0022E §A1.3.2).
7. **"Out of order means anything goes."** Wrong: reads with the same ARID must return in issue order, even when they target different slaves (§A5.3.1), and writes with the same AWID must complete in issue order (§A5.3).
8. **"AHB-Lite systems can only have one master."** Each AHB-Lite *bus* has one master; a multi-master system adds an arbitrating interconnect (IHI0033B.b §1.1, §1.1.3).

### Recap

- AMBA defines interfaces; the interconnect decodes, arbitrates, routes, returns DECERR and bridges.
- APB: registers, not pipelined, at least two cycles per transfer. AHB-Lite: pipelined, separate data buses, an address phase per beat. AXI4: five channels, one address per burst, IDs, many outstanding.
- AXI4-Lite: AXI4's channels for registers, length-1 transactions, no IDs. AXI4-Stream: data with no address.
- ACE adds snooping for cached masters; ACE-Lite gives coherent requests to uncached masters; CHI is a layered, credit-based network.
- Your protocol choice decides your agent, checkers, scoreboard model and coverage.

## Make It Work

### Worked example: choose the interface for three blocks

Apply the two-step method (strike what lacks a need, then prefer the fewest unused features) to three blocks.

| Block | Needs | Struck out (what it lacks) | Choice | Bigger options waste | Verification consequence |
|---|---|---|---|---|---|
| UART registers, written at boot, polled occasionally; an AXI-to-APB bridge exists | addresses only | AXI4-Stream (no address) | **APB** | AHB-Lite pipelining and bursts; AXI4-Lite's five channels; AXI4's IDs and bursts | one-thread APB agent, in-order scoreboard, register model on APB |
| DMA engine copying 4KB buffers from DDR, reading ahead while writing back | addresses, long bursts, many reads in flight, reads and writes at once | APB and AXI4-Lite (no bursts), AHB-Lite (at most one transfer in each phase, so no deep read-ahead and no read during a write), AXI4-Stream (no address) | **AXI4** | nothing: it uses all of it | AXI4 agent with per-channel threads, per-ID scoreboard, burst and 4KB checks |
| Video scaler feeding an encoder, one pixel group per clock, line markers | data every cycle, packet markers, no addresses | APB (at least two cycles per transfer); the AXI options could move data every clock but carry addresses the block never uses | **AXI4-Stream** | addresses, responses, reads | stream agent, packet scoreboard, TLAST and backpressure coverage |

These match the explorer's UART, DMA and Video scenarios.

### Debugging protocol and configuration mismatches

At this map level, many early failures are not DUT bugs but a testbench or VIP set up for the wrong protocol variant or width. Each row gives a symptom, its usual cause and the fix. The log messages are illustrative; real VIP messages are tool-dependent.

| What the log shows | Likely cause | Fix |
|---|---|---|
| The AXI checker flags a legal 32-beat INCR read: `ARLEN 31 exceeds the maximum of 15` | the VIP is set to AXI3, where every burst is 1 to 16 beats; AXI4 allows INCR bursts up to 256 (IHI0022E §A3.4.1) | set the VIP to AXI4 |
| A slave-side monitor rejects every response: `RID 0x23 does not fit in 4 bits` | the monitor uses the master's ID width, but the interconnect appended port bits (§A5.3.5) | give each slave-side monitor the slave-side width (Arm recommends 8 bits there, §A5.3.6) |
| The scoreboard reports `read returned out of order` for two reads with different ARIDs | the scoreboard keeps one in-order queue for everything; reads with different ARIDs may complete in any order (§A5.3.1) | keep one in-order queue per ID |
| A read of an unmapped address hangs until the test times out | the interconnect does not answer an address it cannot decode; that is a DUT bug, because it must return DECERR (§A3.4.4) | expect DECERR on every beat, and file the hang as a bug |
| A full AXI master never matches the responses of an AXI4-Lite register block | the Lite slave does not reflect IDs, which a full AXI master needs (§B1.2.1) | add ID reflection to the slave, or a conversion bridge |
| The register scoreboard flags a write that changed nothing | after conversion from full AXI, a write with every WSTRB bit low is legal, and suppressing it is "permitted but not required" (§B1.1.3) | predict no change for a write with no strobes set |

Protocol-level debugging (APB wait states, AHB HREADY stalls, a lost TLAST on a stream) belongs to the protocol modules: [B-APB-1](/curriculum/T3_Advanced/B-APB-1_APB_Protocol_and_Verification/index), the B-AHB modules and the B-AXI modules.

### How to choose an interface (steps)

1. **List the needs** of the block: memory-mapped addresses? Bursts? Many transactions in flight? Reads and writes at once? Coherency with other caches?
2. **Strike out** every protocol that lacks one of those needs.
3. **Prefer** the remaining protocol with the fewest features the block will never use.
4. **Check the neighbourhood:** which fabric the block sits on, and which bridge (with what latency) it would need.
5. **Write down the verification consequence:** the agent, the checker families, the scoreboard ordering model and the coverage axes.

- [ ] I can name a suitable protocol for a UART, a DMA engine, a video pipeline, a CPU cluster, a cacheless accelerator and a many-core mesh.

## Push Further

### Expert: AXI3 versus AXI4, what a VIP must be told

A VIP configured for the wrong AXI version flags legal traffic or misses illegal traffic. The differences (Arm IHI0022E):

- **Burst length:** AXI3 uses AxLEN[3:0] (1 to 16 beats); AXI4 uses AxLEN[7:0], with INCR up to 256 beats (§A3.4.1).
- **Write interleaving:** AXI3 slaves may accept interleaved write data tagged by WID. AXI4 removes write interleaving, and with it WID, "to reduce the pin-count of the interface" (§A5.4.1). An AXI3 master that interleaves must be set to an interleaving depth of 1 to work with AXI4 (§A5.4.2).
- **Locked transactions:** AXI4 removes them, because they complicate the interconnect and its QoS guarantees (§A7.3).
- **QoS and REGION:** AXI4 adds 4-bit AxQOS, a quality-of-service identifier that Arm recommends using as a priority, higher meaning more urgent (§A8.1.1), and optional 4-bit AxREGION (§A8.2.1).
- **Write response dependency:** AXI4 requires a slave to accept the write address before giving the write response. "An AXI3 slave that accepts all write data and provides a write response before accepting the address is not compliant with AXI4"; it needs a wrapper (§A3.3.2).

### Expert: AXI4-Lite inside a full AXI system

- **ID reflection:** an AXI master expects IDs back. An AXI4-Lite slave connected to a full AXI master must return the ID of each transaction with its response (§B1.2.1). A Lite slave with built-in ID reflection can connect directly, but only if the system guarantees it receives only Lite-subset traffic; Arm recommends reflecting AWID rather than WID so the logic works with AXI3 and AXI4 (§B1.2.2).
- **Conversion:** a bridge splits a burst into length-1 transactions and combines their write responses into one; "any error response is sticky" (§B1.3.1).
- **The all-strobes-low write:** after conversion from full AXI, a Lite slave can receive a write with every WSTRB bit low, and suppressing it is "permitted but not required" (§B1.1.3). A Lite slave model and its scoreboard must therefore accept a write that changes nothing.
- **64-bit Lite:** Arm expects most Lite components to be 32-bit, and "only components requiring 64-bit atomic accesses" to use 64 bits (§B1.1.2).

### Expert: interconnect topologies, IDs and errors

- **Topology:** shared address and data buses; shared address bus with multiple data buses; or multilayer. Address bandwidth is usually far below data bandwidth, so a shared address bus with several data buses is a common balance (§A1.3.2).
- **Register slices** (a pipeline register stage inserted in a channel): because each channel flows one way with no fixed relation to the others, a register slice can be inserted "at almost any point in any channel, at the cost of an additional cycle of latency" (§A1.3.3). A scoreboard that assumes fixed latency breaks when one is added.
- **ID widening:** the interconnect appends master-port bits to ARID and AWID, so slave-side IDs are wider (§A5.3.5). Arm recommends up to 4 ID bits at masters, up to 4 more for the port number, and 8 at slaves (§A5.3.6). A slave-side monitor must be configured with the wider width.
- **Ordering across slaves:** the interconnect must deliver same-ARID read data to the master in issue order even when the reads went to different slaves (§A5.3.1).
- **DECERR:** must come from the interconnect when it cannot decode the address, ideally through a default slave, and every beat of the burst must still be completed (§A3.4.4). A test of an unmapped address should expect the full number of R beats, each with DECERR.

### Expert: AHB-Lite, multi-master AHB and AHB5

- IHI0033B.b defines the interface between masters, interconnects and slaves; a single-master system needs only a decoder and multiplexor (§1.1, §1.1.3). Multi-master systems need an interconnect that arbitrates, and the specification gives no details of single-layer or multi-layer designs (§1.1.3). The multi-layer approach is described in a separate Arm document (DVI 0045), not checked here; the claim that a multi-layer interconnect isolates a slow slave from unrelated masters is engineering practice.
- AHB5 declares each new capability as a property that is False unless declared: Extended_Memory_Types, Secure_Transfers, Endian, Stable_Between_Clock, Exclusive_Transfers and Multi_Copy_Atomicity (§1.2). An AHB VIP needs these properties as configuration, exactly as an AXI VIP needs its version.
- The 2021 issue IHI0033C adds signal-width properties, write strobes, user-signal updates, signal-validity rules and parity protection, and renames master and slave to manager and subordinate (IHI0033C change history).

### Expert: AMBA 5 at awareness level (AXI5, atomics, APB5)

- **AXI5** "extends the capabilities of the AXI4 protocol", declaring each new capability as a property (IHI0022G §C1.1, Table C1-1). Issue F (2017) introduced the AXI5, AXI5-Lite, ACE5, ACE5-Lite, ACE5-LiteDVM and ACE5-LiteACP interfaces (IHI0022G change history).
- **Atomic transactions** (property Atomic_Transactions) send the operation to the data, so the data is unavailable to other agents for less time than with an exclusive-access sequence. There are four forms: AtomicStore, AtomicLoad, AtomicSwap and AtomicCompare; the slave returns data for every form except AtomicStore (IHI0022G §E1.1, §E1.1.1). They are signalled by AWATOP on the write address channel (Table C1-2) and are supported on AXI5, ACE5-Lite and ACE5-LiteDVM interfaces, not by ACE5 masters (§E1.1). One ID is used for the request, the write response and the read data (§E1.1.4), so a testbench must expect R-channel data in response to a *write-address* transaction. [B-AXI-4](/curriculum/T3_Advanced/B-AXI-4_AXI_Expert_Features_Cache_Atomics/index) covers atomics and exclusives.
- **APB5** (IHI0024 issue D, 2021) adds wake-up signalling, user signalling and parity protection; issue E (2023) adds optional Realm Management Extension support (IHI0024E Preface, "APB revisions").

### Expert: coherent protocols in verification

- ACE changes the existing AXI channels as well as adding snoop channels (IHI0022E §C1.3.1–§C1.3.3). So moving a CPU cluster from AXI4 to ACE changes the AR, AW and R monitors (new fields to decode and cover), not just the agent's channel list.
- An ACE-Lite master can issue all Non-shareable transactions but only a restricted set of Shareable ones, meaning transactions to locations that other masters' caches may hold (§C11.2), so an ACE-Lite VIP must constrain its stimulus to that set, and a checker must flag anything else.
- CHI moves verification to packets: flits, link-layer credits per hop and node IDs (IHI0050E.b §1.1.2, §1.3), with home nodes that serialize requests (§1.6). Commercial CHI and ACE VIP availability and features are tool-dependent.

### Expert: verification cost, build versus buy

Engineering practice, not specification. For APB and AXI4-Lite, many teams build their own agent: the protocol is small and the agent doubles as a teaching example. For AXI4 with full ordering checks, and certainly for ACE and CHI, teams usually license a commercial VIP, because the protocol checkers and coverage models are large and must track every specification issue. Whatever the source, a VIP is only as good as its configuration: version, data and ID widths, optional signals and declared properties (tool-dependent).

### Exercise: pick the protocol

For each block, write the needs, your choice, why not the runner-up, and the verification consequence. Then open the worked answer.

1. A 64-bit interrupt-controller register block on an AXI fabric with no APB bridge; the CPU needs 64-bit atomic register accesses.
2. An Ethernet MAC with control registers, a packet path between the MAC core and its DMA, and a DMA that writes packets to DDR.
3. A microcontroller with one CPU, flash, SRAM, timers and a UART.
4. A crypto accelerator with no cache that reads buffers CPUs may hold dirty, on a coherent interconnect.
5. An image filter between a camera interface and a scaler, one pixel group per clock, with an end-of-line marker.

<details>
<summary>Worked answers</summary>

1. **AXI4-Lite, 64-bit.** Needs: addresses and 64-bit atomic access on an AXI fabric. APB data buses are at most 32 bits (IHI0024C §2.1.1), and there is no bridge; AXI4-Lite's 64-bit option exists for exactly this (IHI0022E §B1.1.2). AXI4 would waste bursts and IDs. Consequence: an AXI4-Lite agent configured for 64-bit data; check that every access is full width.
2. **Three interfaces on one IP.** APB (or AXI4-Lite) for the registers, AXI4-Stream between the MAC core and its DMA (packets marked by TLAST), and AXI4 for the DMA master writing to DDR. Consequence: three agents, a packet scoreboard on the stream side and a per-ID scoreboard on the AXI4 side.
3. **AHB-Lite plus APB.** One master suits AHB-Lite's decoder-and-multiplexor structure, and memories are the most common AHB slaves; timers and the UART go on APB behind an AHB-to-APB bridge (IHI0033B.b §1.1). Consequence: an AHB-Lite agent with a pipelined driver, and an APB agent.
4. **ACE-Lite** (IHI0022E §C11.1). The accelerator has no cache to snoop, so ACE is wrong. On a non-coherent system the answer becomes AXI4 plus software cache maintenance. Consequence: constrain stimulus to ACE-Lite's permitted Shareable transactions (§C11.2) and check data coherency.
5. **AXI4-Stream**, with TLAST at the end of each line (IHI0051A §2.5). Marking start of frame on TUSER is a common convention, not part of the specification. Consequence: a stream agent; scoreboard per line; coverage of line lengths and backpressure.

</details>

### Kata: widen the IDs

In the wire-count unit, change every AXI4 ID field (AWID, BID, ARID, RID) from 4 to 8 bits. Predict the new AXI4 total before you recompute.

<details>
<summary>Worked solution</summary>

Four ID fields each gain 4 bits, so the total rises by 16: 214 + 16 = **230 wires**. This is not academic: the interconnect widens IDs on the slave side (IHI0022E §A5.3.5), and Arm recommends 8 ID bits at slaves (§A5.3.6). So a slave-side monitor in an SoC usually sees wider IDs than the master's agent.

</details>
