# AXI Expert Features: Cache, Prot, QoS & Atomics

While `AxADDR`, `AxLEN`, and `AxSIZE` define *where* and *how much* data to move, AXI includes several **sideband signals** that define *how* the interconnect and memory controllers should treat the transaction.

These "expert features" are critical for building complex, multi-core SoCs where security, caching, and atomic synchronization are required.

<QuickTake>
- **`AxCACHE` (Memory Type):** Tells interconnects and caches whether a transaction is bufferable, whether it may be modified (split, merged, prefetched), and how it may be allocated.
- **`AxPROT` (Protection):** Defines privilege (User vs. Privileged), security (Secure vs. Non-secure), and instruction vs. data access.
- **`AxQOS` (Quality of Service):** A 4-bit priority hint for interconnect arbitration and routing.
- **Exclusive Accesses (`AxLOCK`):** Enables atomic read-modify-write operations (like `LDREX`/`STREX` in ARM) across the bus. AXI4 removed AXI3's locked transactions (IHI0022E A7.3); the AXI5 atomic transactions are defined in later issues of the specification and are not covered here.
</QuickTake>

---

## 1. Memory Types (`AxCACHE[3:0]`)

Despite the name, `AxCACHE` is not just about caches. It defines the **memory attributes** of a transaction, telling the interconnect if it can buffer or combine the access.

| Bit | Name | Meaning |
|---|---|---|
| `[0]` | **Bufferable (B)** | If 1, the interconnect can issue a write response `BRESP` *before* the data reaches the final destination. |
| `[1]` | **Modifiable (AXI4)**, called Cacheable in AXI3 | If 1, the transaction may be modified: split, merged, prefetched, or widened with strobes. If 0 (Non-modifiable), it must not be split or merged, and its address, size, length, burst type, lock and protection must not change (A4.3.1). |
| `[2]` | **Read-allocate** | Allocation hint for reads. AXI4 updates its meaning (A4.3). |
| `[3]` | **Write-allocate** | Allocation hint for writes. AXI4 updates its meaning (A4.3). |

Ordering is a separate rule, not a bit: Non-modifiable transactions with the same ID to the same slave must stay ordered (A4.3.2). In AXI4 only the encodings in Table A4-5 of IHI0022E are legal; all other values are reserved.

### Common Use Cases

- **Device Non-bufferable (`AxCACHE = 4'b0000`):** used for peripheral registers. The write response must come from the final destination, reads must not be prefetched, writes must not be merged (A4.4.1).
- **Normal Non-cacheable Bufferable (`4'b0011`):** memory that may be buffered and modified but not cached.
- **Write-back, Read and Write-allocate (`4'b1111`):** normal cacheable DRAM. The interconnect and caches can optimize, prefetch, and buffer.

> [!WARNING]
> Setting `AxCACHE` to cacheable for a device register (like a UART FIFO) will cause catastrophic failures, as the CPU might read a stale cached value instead of popping the actual FIFO.

## 2. Protection & Security (`AxPROT[2:0]`)

`AxPROT` defines the access permissions for the transaction. Slaves (like memory controllers or peripheral bridges) use this to reject illegal accesses.

| Bit | Name | `0` Meaning | `1` Meaning |
|---|---|---|---|
| `[0]` | **Privilege** | Unprivileged (User mode) | Privileged (Kernel/Supervisor mode) |
| `[1]` | **Security** | Secure access (TrustZone) | Non-secure access |
| `[2]` | **Instruction/Data**| Data access | Instruction fetch |

### TrustZone & Security

Bit `[1]` is the cornerstone of ARM TrustZone hardware security.
- A **Non-secure** master (`AxPROT[1] = 1`) attempting to read a **Secure** memory region will be blocked by the slave or a firewall (TrustZone Address Space Controller), resulting in an `DECERR` (Decode Error) or `SLVERR` (Slave Error).
- Note the inverse logic: `0` means Secure, `1` means Non-secure.

## 3. Quality of Service (`AxQOS[3:0]`)

`AxQOS` was introduced in AXI4 to help interconnects prioritize traffic. It is a 4-bit value where a higher number indicates higher priority.

- **`4'b0000`**: Default, lowest priority.
- **`4'b1111`**: Highest priority.

### Why QoS?

In an SoC, a GPU fetching textures and a Display Controller fetching frame pixels both read from the same DRAM.
If the GPU dominates the bus, the Display Controller will starve, resulting in visual screen tearing (a missed VSYNC).
By assigning a higher `AxQOS` to the Display Controller, an interconnect that uses QoS will favor it in arbitration. Whether that is enough to meet the display's bandwidth depends on the interconnect, not on the protocol.

> [!NOTE]
> IHI0022E A8.1.1: "The protocol does not specify the exact use of the QoS identifier." It recommends using it as a priority, higher meaning more important, with `4'b0000` meaning the interface takes no part in any QoS scheme.

## 4. Exclusive Accesses (Atomics)

In a multi-core system, cores need a way to perform **atomic read-modify-write** operations (e.g., implementing semaphores or spinlocks).
If Core A reads a lock, modifies it, and writes it back, it must ensure Core B didn't modify it in the meantime.

AXI supports this using **Exclusive Accesses** via the `AxLOCK` signal.

### The Exclusive Access Flow

1. **Exclusive Read:** The master issues an `AR` transaction with `ARLOCK = 1`.
2. **Monitor Tracking:** The slave's exclusive monitor records the address and the `ARID` (IHI0022E A7.2.3). The spec recommends one monitor per exclusive-capable ID.
3. **Slave Response:** The slave returns the read data with `EXOKAY`. A slave **without** exclusive support answers `OKAY` instead; the master should treat that as "exclusive access not supported" and not attempt the write (A7.2.2).
4. **Master Modifies:** The master modifies the data locally.
5. **Exclusive Write:** The master issues an `AW` transaction to the *same address* with `AWLOCK = 1` and an `AWID` equal to the `ARID` of the exclusive read.
6. **Monitor Check:**
   - If the location is still monitored for that ID (no write has happened to it since the exclusive read), the slave updates memory and returns `EXOKAY`. The atomic operation **succeeded**, and that write ends any other ID's monitoring of the location.
   - Otherwise the slave does not update memory and returns `OKAY`. The atomic operation **failed**.
7. **Retry on Failure:** If the master sees `OKAY` instead of `EXOKAY` on its exclusive write, it must retry the entire read-modify-write sequence.

An exclusive write with no matching exclusive read is **not** a protocol error: it simply fails with `OKAY`. The real protocol restrictions are in A7.2.4, and breaking them makes the result UNPREDICTABLE:

- the number of bytes (size x length) is a power of 2, at most 128, and AXI4 allows at most 16 transfers;
- the address is aligned to that total number of bytes;
- the exclusive write uses the same address, ID, size, length and control signals as the exclusive read;
- `AxCACHE` must let the monitoring slave see the access (for example, not Cacheable).

### Global vs. Local Monitors

- **Local Monitor:** Sits close to the master (e.g., in the L1 cache). Handles exclusives that hit in the cache.
- **Global Monitor:** Sits at the interconnect or slave. Handles exclusives that miss the cache and go out to shared memory.

The monitor's state decides every answer. Predict each response, then switch between a per-ID monitor and a single shared monitor to see why the spec recommends one per ID.

## 5. Verification Strategy

Verifying expert features requires targeted test sequences:

### Cache & Protection VIP Support
Your AXI VIP must be able to inject illegal accesses (e.g., unprivileged write to a privileged-only register) and verify that the DUT responds with an `SLVERR` and does not update the internal state.

### Exclusive Access Sequences
To verify an exclusive monitor, you must create a virtual sequence that deliberately induces **collisions**:
1. Master 0 issues Exclusive Read.
2. Master 1 issues Exclusive Read to the same address.
3. Master 1 issues Exclusive Write (should succeed, receive `EXOKAY`).
4. Master 0 issues Exclusive Write (must fail, receive `OKAY`, memory unchanged).

```systemverilog
// [Protocol A7.2.4] the shape of every exclusive read (repeat for AW)
a_excl_shape: assert property (@(posedge ACLK) disable iff (!ARESETn)
  ARVALID && ARLOCK |->
    $onehot(((ARLEN + 1) << ARSIZE)) &&           // power of 2 bytes
    (((ARLEN + 1) << ARSIZE) <= 128) &&          // at most 128 bytes
    (ARLEN <= 15) &&                             // AXI4: at most 16 transfers
    ((ARADDR % ((ARLEN + 1) << ARSIZE)) == 0));  // aligned to the total

// [Not a protocol rule] an exclusive write with no earlier exclusive read is legal;
// it fails with OKAY. Check the expected EXOKAY/OKAY in the scoreboard instead.
```

### Coverage Plan

```systemverilog
covergroup axi_expert_cg @(posedge ACLK iff ARVALID && ARREADY);
  // AxPROT[0]: 1 = privileged; AxPROT[1]: 1 = Non-secure (IHI0022E Table A4-6)
  cp_prot: coverpoint ARPROT {
    bins secure_priv   = {3'b001};
    bins nonsec_priv   = {3'b011};
    bins secure_user   = {3'b000};
    bins nonsec_user   = {3'b010};
  }
  cp_cache: coverpoint ARCACHE {
    bins device_nb     = {4'b0000};   // Device Non-bufferable
    bins normal_nc_b   = {4'b0011};   // Normal Non-cacheable Bufferable
    bins wb_rwa        = {4'b1111};   // Write-back Read and Write-allocate
  }
  cp_lock: coverpoint ARLOCK {
    bins normal    = {0};
    bins exclusive = {1};
  }
  // Ensure we see exclusive accesses across different security states
  cx_lock_prot: cross cp_lock, cp_prot;
endgroup
```
