## Quick Take

- **What it is:** Besides *where* (AxADDR) and *how much* (AxLEN, AxSIZE), every AXI read and write request carries **attribute signals** that say *how* the system must treat it. "Ax" means "AR or AW": ARCACHE on reads, AWCACHE on writes.
- **The four attributes:** **AxCACHE** gives the **memory type**: may the transaction be buffered, merged, split, prefetched or answered by a cache? **AxPROT** gives the **access permissions**: privileged or not, Secure or Non-secure, instruction or data. **AxQOS** is a **priority hint** for arbiters. **AxLOCK** marks an **exclusive access**, the AXI building block for semaphores (Arm IHI0022E Chapters A4, A7 and A8).
- **Why it matters:** These few bits decide whether a status poll really reaches the peripheral, whether a firewall lets a Non-secure access touch Secure memory, whether a display gets its pixels on time, and whether a spinlock works. The classic bugs are silent: a register mapped as cacheable memory, an AxPROT bit with inverted polarity, an exclusive that fails forever, a verification plan that never sends anything but `AxCACHE = 4'b0000`.
- **The Analogy:** The attributes are labels on a parcel: "fragile, do not repack", "deliver to the addressee in person", "staff only", "express". *Where it breaks:* some labels bind every carrier on the route (Non-modifiable, the response point of Non-bufferable writes, AxPROT, which no carrier may change), while others are only hints a carrier may ignore (the allocate bits, QoS, the instruction bit). And "exclusive" is not a label on one parcel at all: it is a two-parcel agreement, a read and a later write, that the receiver may refuse.

**You will be able to:**
1. Decode AxCACHE, using the AXI4 bit names, into one of the twelve memory types, and predict what an interconnect may and may not do with the transaction: answer early, merge, split, prefetch, look it up in a cache, reorder it (IHI0022E §A4.3, §A4.4).
2. Choose AxPROT values for a scenario, remembering that AxPROT[1] = 1 means **Non-secure** (§A4.7).
3. Predict the response (EXOKAY or OKAY) and the memory effect of each step of an exclusive access sequence, check it against the exclusive restrictions, and explain why AXI4 removed locked transfers (§A7.2, §A7.3).
4. Explain AxQOS as a priority hint that never overrides the AXI ordering rules and never guarantees latency (§A8.1).
5. Plan the sequences, assertions and coverage for these attributes, and explain how an AXI5 atomic transaction differs from an exclusive pair (awareness; IHI0022L §A6.4).

Besides the prerequisite below, this lesson uses AxLEN and AxSIZE from [B-AXI-2 AXI Burst Math](/curriculum/T3_Advanced/B-AXI-2_AXI_Burst_Math/index), because an exclusive access has size rules.

## Build Your Mental Model

**How to read this lesson.** The core path is: the words, binding rules versus hints, AxCACHE bit by bit, the twelve memory types, the register pitfall, AxPROT, AxQOS and the exclusive-access flow. Each has a picture. Practitioner depth follows: the read/write ordering caveat (inside the memory-types section), the exclusive corner cases, locked transfers, monitors, how all this lives in a testbench and how to debug it. The expert layer, including AXI5 atomic transactions, is in Push Further.

### Words you need first

- **Master, slave, interconnect.** The master starts a transaction, the slave answers it, and the interconnect routes masters to slaves. IHI0022E, the issue this track cites, uses master and slave; later Arm issues (such as IHI0022L, cited for AXI5 below) say *manager* and *subordinate* for the same roles.
- **Final destination.** The slave that actually holds the location: the peripheral register or the memory.
- **Intermediate point.** Anything between the master and the final destination that may hold a transaction for a while: an interconnect **write buffer** (it accepts a write, answers it, and passes it on later) or a **system cache** (a cache in the interconnect or memory system, outside the processor).
- **Response codes** (IHI0022E §A3.4.4, Table A3-4). Every read beat carries RRESP and every write gets one BRESP: **OKAY** (`2'b00`, normal success, or a failed exclusive), **EXOKAY** (`2'b01`, exclusive success), **SLVERR** (`2'b10`, the slave reports an error) and **DECERR** (`2'b11`, no slave at that address, usually from the interconnect).
- **Prefetch** means reading a location before anyone asked for it; **merge** means combining several writes (or several reads) into one transaction; **allocate** means placing a line in a cache.
- **Device and Normal memory.** **Device** memory is peripherals and their registers: an access can have side effects, so every access must reach the device unchanged. **Normal** memory is RAM-like: depending on its exact type, the system may merge, split, prefetch or cache its accesses, because reading or writing it has no side effect. AXI4 splits each into several *memory types* (below).
- **Write-through and Write-back** are cache write policies. A **write-through** write updates any cached copy and also goes on to memory; a **write-back** write may stay in the cache, and memory is updated later, when the line is evicted.
- **Cacheable,** in AXI4 terms, means a Write-through or Write-back memory type: at least one of AxCACHE[3:2] is set (IHI0022E §A4.5). *Non-cacheable* means AxCACHE[3:2] = `2'b00`.
- **Privileged** and **Secure.** A processor runs code at different privilege levels (an operating-system kernel is privileged, an application is not). Processors with Arm TrustZone also run in a **Secure** or a **Non-secure** state; Secure memory holds keys and firmware that Non-secure software must never reach.
- **Semaphore, spinlock.** A shared variable that several masters update in a read-modify-write, for example "if the lock word is 0, write 1 to take it". The update must be **atomic**: no other master may write between the read and the write.
- **Arbiter.** The logic in an interconnect or memory controller that picks which of several waiting transactions goes next.
- **UNPREDICTABLE.** The specification's word for "no result is required": if a rule marked this way is broken, any outcome is allowed, so a checker must flag the cause rather than expect a particular response.
- **VIP.** Verification IP: a reusable, ready-made agent (driver, monitor, checks) for a protocol such as AXI.

### Binding rules and hints

Before decoding any bit, sort the attributes into two groups. Everything in this lesson follows from this table.

| Attribute | Binding or hint | Who acts on it | Source |
|---|---|---|---|
| AxCACHE[1] Modifiable | Binding: 0 forbids merging, splitting and changing the transaction | Interconnect, bridges, caches | §A4.3.1 |
| AxCACHE[0] Bufferable | Binding: 0 (with no allocate bit) makes the write response come from the final destination | Write buffers | Tables A4-3, A4-4 |
| AxCACHE[3:2] allocate bits | Binding for cache *lookup*; only a hint for *allocation* | System caches | §A4.3.3 |
| AxPROT | Binding: never changed on the way (§A4.3.1); the slave or a firewall decides what to allow | Slaves, firewalls | §A4.7 |
| AxPROT[2] instruction | A hint; not accurate in every case | Slaves (rarely) | §A4.7 |
| AxQOS | A hint; the protocol does not define its use | Arbiters | §A8.1.1 |
| AxLOCK exclusive | A request the slave may refuse: no support, or the location was written | Exclusive monitors | §A7.2 |

### AxCACHE bit by bit (AXI4 names)

AXI3 called the four AxCACHE bits Bufferable, Cacheable, Read-allocate and Write-allocate (IHI0022E Table A4-1). AXI4 renamed bit 1 to **Modifiable** (same function, better name) and redefined the two allocate bits, and it requires AXI4 components to use the new names (§A4.3, §A4.8). The allocate bits now mean different things on the two channels:

| Bit | ARCACHE (reads) | AWCACHE (writes) | Meaning |
|---|---|---|---|
| [0] | Bufferable | Bufferable | Writes with no allocate bit: 1 lets an intermediate point give the write response, 0 makes it come from the final destination. Reads: no effect on Device reads; for Normal Non-cacheable memory, 1 lets the data come from a write still on its way to the final destination. With an allocate bit set, on both channels the bit tells Write-back (1) from Write-through (0); a write of either kind may then be answered early, but a Write-through write must reach memory in a timely manner and a Write-back write need not reach it at all |
| [1] | Modifiable | Modifiable | 1: the transaction may be split, merged, widened or (reads) fetch more data than asked. 0: Non-modifiable, its shape must not change (a few exceptions, listed in Push Further) |
| [2] | **Allocate** | **Other Allocate** | Reads: "allocate this if you can". Writes: "a *read* or another master may already have allocated this location" |
| [3] | **Other Allocate** | **Allocate** | Reads: "a *write* or another master may already have allocated this location". Writes: "allocate this if you can" |

The rule that matters for correctness is the **lookup rule** (§A4.3.3): if AxCACHE[3:2] is not `2'b00`, the transaction **must be looked up in a cache**, because the location could be in one; if AxCACHE[3:2] is `2'b00`, it need not be, and a write must then go on to the final destination. Allocation itself stays a recommendation for performance.

**Pitfall: reading the AXI3 names.** In AXI4, ARCACHE[3] is not "write-allocate for reads". It says the location may hold data that a write or another master allocated, so the read must look in the cache to stay coherent with that write. A VIP or checker written from the AXI3 table decodes the allocate bits of cacheable encodings wrongly, and differently on each channel.

### The twelve memory types

AXI4 names twelve memory types (IHI0022E §A4.4, Table A4-5). Some have different preferred values on AR and AW, and some also accept the old AXI3 value (in brackets). **Every value not in the table is reserved.** A compact way to state the legal set: AxCACHE[1] = 1, or AxCACHE[3:2] = `2'b00`. That rule leaves exactly six reserved values: `4'b0100`, `4'b0101`, `4'b1000`, `4'b1001`, `4'b1100` and `4'b1101` (an allocate bit without Modifiable).

| Memory type | ARCACHE | AWCACHE |
|---|---|---|
| Device Non-bufferable | `0000` | `0000` |
| Device Bufferable | `0001` | `0001` |
| Normal Non-cacheable Non-bufferable | `0010` | `0010` |
| Normal Non-cacheable Bufferable | `0011` | `0011` |
| Write-through No-allocate | `1010` | `0110` |
| Write-through Read-allocate | `1110` (`0110`) | `0110` |
| Write-through Write-allocate | `1010` | `1110` (`1010`) |
| Write-through Read and Write-allocate | `1110` | `1110` |
| Write-back No-allocate | `1011` | `0111` |
| Write-back Read-allocate | `1111` (`0111`) | `0111` |
| Write-back Write-allocate | `1011` | `1111` (`1011`) |
| Write-back Read and Write-allocate | `1111` | `1111` |

Notice two things. First, the same type can have a different value on each channel (Write-through No-allocate is `1010` on AR but `0110` on AW), so a checker or coverage model needs one table per channel. Second, on AR the No-allocate and Write-allocate forms share a value: a read cannot express a write-allocation preference, and does not need to.

What each type allows is set by §A4.4.1:

| Memory type | Write response may come from | Read data may come from | Modifiable (merge, split, fetch more) | Cache lookup required | Same-ID ordering that must hold |
|---|---|---|---|---|---|
| Device Non-bufferable | final destination only | final destination only; no prefetch | no | no | all Non-modifiable transactions to the same slave |
| Device Bufferable | an intermediate point; the write must still reach the destination in a timely manner | final destination only; no prefetch | no | no | all Non-modifiable transactions to the same slave |
| Normal Non-cacheable Non-bufferable | final destination only | final destination only | yes (writes may merge) | no | reads and writes to overlapping addresses |
| Normal Non-cacheable Bufferable | an intermediate point; timely visibility | final destination, or a write still on its way there | yes | no | reads and writes to overlapping addresses |
| Write-through (any allocate) | an intermediate point; timely visibility | a cached copy; reads may be prefetched | yes | yes | reads and writes to overlapping addresses |
| Write-back (any allocate) | an intermediate point; need **not** ever reach the final destination | a cached copy; reads may be prefetched | yes | yes | reads and writes to overlapping addresses |

Between a read and a write, "ordered" has a catch for every type: the read and write channels are independent, so a read and a write are ordered only if the later one is issued after the earlier one has received its response (§A4.3.2 Note; [B-AXI-3](/curriculum/T3_Advanced/B-AXI-3_AXI_Ordering_and_IDs/index) teaches this in full). Device ordering holds between Bufferable and Non-bufferable transactions alike, for any addresses in the same slave; a component that cannot tell where one slave ends and the next begins must keep all same-ID Non-modifiable transactions on the same path in order (§A4.3.2).

**Predict first.** A master issues two writes, one after the other, to neighbouring bytes, both with `AWCACHE = 4'b0011`. May the interconnect merge them into one write, and may it answer them before they reach the memory? Decide, then use the picture.

**Debrief.** `4'b0011` is Normal Non-cacheable Bufferable. Modifiable = 1, so merging the two writes is allowed; Bufferable = 1 with no allocate bit, so the write buffer may answer both, provided it passes the writes on to the memory in a timely manner (§A4.4.1, §A4.6). With `4'b0001` (Device Bufferable) the early answer is still allowed, but the merge is not.

### Pitfall: a register mapped with the wrong AxCACHE

Peripheral registers often have **side effects**: reading a UART receive FIFO pops a byte, and reading a status register may clear its flags. They therefore need every read to reach the peripheral exactly once, in order. Only the **Device** types promise that: read data from the final destination, no prefetch, no merging, no change of shape (§A4.4.1).

If the same register is accessed as Normal memory, the system is allowed to break it. With Modifiable set, an interconnect may serve two polls from one fetch, or widen a read to neighbouring registers and pop a FIFO nobody asked for (§A4.3.1). With an allocate bit set, a system cache may answer from an old copy, and a polling loop never sees the flag change. None of this is a protocol violation: the master asked for Normal memory and got Normal behaviour. The processor's own caches are a separate matter, set by its memory-management attributes, not by AxCACHE.

So **register traffic uses Device memory**: `4'b0000` (Device Non-bufferable), or `4'b0001` (Device Bufferable) when an early write response is acceptable. For reads the two Device types behave identically (§A4.4.1 Note).

### AxPROT: who is asking

AxPROT has three independent bits (IHI0022E §A4.7, Table A4-6):

| Bit | 0 | 1 |
|---|---|---|
| AxPROT[0] | Unprivileged | Privileged |
| AxPROT[1] | **Secure** | **Non-secure** |
| AxPROT[2] | Data | Instruction |

- **Bit 1 is inverted from what people guess.** Asserting it marks the access as **Non-secure**, matching other Arm security signals. A VIP that drives `AxPROT[1] = 1` for "secure" gets every Secure access refused.
- **Privilege is only two levels on the bus.** A processor may have several privilege levels; how they map to AxPROT[0] is processor-specific (§A4.7 Note).
- **The instruction bit is a hint.** It cannot be exact (one burst may carry both instructions and data), and the specification recommends driving it 0 unless the access is known to be an instruction fetch.
- **No interconnect may change AxPROT,** not even for a Modifiable transaction (§A4.3.1).
- **What happens to a refused access is system policy.** AXI defines the encoding, not the reaction. A slave or a TrustZone firewall commonly answers SLVERR or DECERR; some return zeros and ignore writes (vendor-specific). Read the DUT's specification before writing the check.

**Predict first.** Give AxPROT for: (a) a Non-secure operating-system kernel reading a data buffer; (b) Secure boot firmware, running privileged, fetching its own instructions; (c) a Non-secure user application writing a frame. Write down all three before you open the answers.

### AxQOS: a priority hint

AXI4 adds a 4-bit QoS identifier on each address channel, ARQOS and AWQOS (IHI0022E §A8.1.1). The protocol does not define its exact use. The specification recommends using it as a priority, higher meaning more important, and `4'b0000` means the interface **takes no part in any QoS scheme**. A master that cannot produce QoS values must drive `4'b0000`, and an interconnect may overwrite a master's values from its own programmable registers (§A8.1.2).

The default system behaviour is simple: a component that has several transactions to choose from serves the higher QoS first, **but only where no AXI rule already fixes the order** (§A8.1.3). So the ordering rules win: a high-QoS read's data never returns before the data of an earlier read with the same ID.

Why bother? A display controller reads pixels at a fixed rate from a small buffer. If a GPU's bulk traffic delays those reads, the buffer underflows and the image glitches. Giving the display a higher QoS helps an arbiter that honours QoS to favour it, but whether that is *enough* depends on the interconnect, the memory controller and the traffic, not on AXI. **QoS is not a latency guarantee.** A bounded latency is an integration contract you specify and check at system level; [B-AXI-5](/curriculum/T3_Advanced/B-AXI-5_AXI_Pitfalls_Interconnect_Deadlocks/index) frames those liveness contracts.

### Exclusive access: the flow

A semaphore needs a read-modify-write that nobody can interrupt. AXI provides this without locking the bus: the **exclusive access** mechanism (IHI0022E §A7.2). The slave keeps an **exclusive monitor**, a small piece of hardware that remembers which location each ID is watching. The specification recommends one monitor unit per exclusive-capable ID (§A7.2.3).

1. **Exclusive read.** The master reads the location with `ARLOCK = 1`.
2. **The monitor starts watching.** The monitor records the address and the ARID. If the same ID later issues another exclusive read, the monitor moves to the new address; it watches only one address per ID (§A7.2.1).
3. **The read response.** A slave with exclusive support returns the data with **EXOKAY**. A slave **without** support returns **OKAY**; the master may treat that as "exclusives not supported here", and the specification recommends it does not attempt the write (§A7.2.2).
4. **Compute.** The master works out the new value locally.
5. **Exclusive write.** Only after the read has completed (§A7.2.2), the master writes the same address with `AWLOCK = 1`, an AWID equal to the ARID, and the same size, length and control signals (§A7.2.4).
6. **The monitor decides.**
   - Still watched for that ID (nobody wrote the location, and the monitor did not move): the slave **updates memory and answers EXOKAY**. This write is itself a write to the location, so it ends every other ID's watch on it.
   - Not watched any more: the slave **does not update memory and answers OKAY**. The exclusive failed (§A7.2.3).
7. **Software decides what next.** A failed exclusive usually makes software loop back to step 1. On Arm processors this is the LDREX/STREX pattern: LDREX is Arm's load-exclusive instruction and STREX its store-exclusive instruction, which reports whether the store succeeded; when they go out on the bus, they become the exclusive read and the exclusive write. The retry is the program's choice, not a protocol rule.

**Debrief.**
- **Race, monitor per ID:** both reads get EXOKAY; M0's write succeeds (EXOKAY) and, being a write to the location, ends M1's watch; M1's write then fails with OKAY. Exactly one of two racing masters wins, which is the whole point.
- **Race, one shared monitor:** M1's exclusive read takes the only monitor away from ID 0 although nobody wrote the location, so M0 fails and M1 wins. A single shared monitor is an implementation choice (§A7.2.3 only *recommends* a monitor per ID), and this is why it makes that recommendation: with a shared monitor, two masters that keep re-reading can keep failing each other.
- **No exclusive support:** the exclusive read returns OKAY, and if the master writes anyway, the write **is performed** and answered OKAY (§A7.2.5). An OKAY on an exclusive write therefore means "failed, not written" on a supporting slave but "written" on a non-supporting one: a scoreboard must know which slave it is talking to.
- **Debug: bad exclusive:** 3 beats of 4 bytes is 12 bytes, not a power of two, so the access breaks §A7.2.4 and its outcome is UNPREDICTABLE. A protocol checker must flag it; no response is "correct".
### Exclusive access: rules and corner cases

**The restrictions** (IHI0022E §A7.2.4). Breaking any of them makes the behaviour UNPREDICTABLE:
- the exclusive write has the same address, ID (AWID = ARID), burst size, burst length and control signals as the exclusive read;
- the total bytes (size × length) are a power of two: 1, 2, 4, 8, 16, 32, 64 or 128;
- the address is aligned to that total;
- AXI4 allows at most 16 transfers in an exclusive burst;
- AxCACHE must let the monitoring slave see the transaction: for example, an exclusive must not be Cacheable, or a cache could absorb it before the monitor sees it.

**What is *not* a violation.** An exclusive write with no earlier exclusive read on that ID is legal. On a supporting slave nothing is being watched for that ID, so it simply fails: OKAY, memory unchanged (§A7.2.3). Later issues of the specification name this case explicitly: IHI0022L §A6.3.4 lists "the Manager did not issue an exclusive read with the same attributes" among the reasons an exclusive write fails. A master may also abandon a pair after the read; the slave keeps watching the address until a new exclusive read from that ID moves the watch or a write to the location ends it (§A7.2.2, §A7.2.3).

**What a checker can assert.** The master must not start the write part of the pair until the read part is complete (§A7.2.2). That is observable at the pins and is checked in Make It Work.

**Spurious failures.** A monitor may watch more bytes than the access, up to 128 (call the watched block its **granule**), so a write to a *neighbouring* byte can fail an exclusive that nobody touched (§A7.2.4). Keep lock words apart from frequently written data.

**Interconnect changes.** An interconnect extends each master's ID with routing bits (§A5.3.5), so the ID the slave's monitor uses is the extended one: two masters that both drive ID 0 are different IDs at the slave, which is what keeps their watches apart. A Non-modifiable exclusive may even have AxSIZE and AxLEN changed by a component, provided the total bytes stay the same (§A4.3.1).

### AXI4 removed locked transfers

AXI3 had a second kind of atomic access, the **locked transfer**: the interconnect let only the locking master reach the slave region until an unlocking transaction completed (IHI0022E §A7.3). AXI4 dropped it, because few components need it and it badly complicates the interconnect and undermines QoS guarantees. The lock signal shrank from two bits to one:

| AXI3 AxLOCK[1:0] | Access | AXI4 AxLOCK | Access |
|---|---|---|---|
| `2'b00` | Normal | `1'b0` | Normal |
| `2'b01` | Exclusive | `1'b1` | Exclusive |
| `2'b10` | Locked | — | not supported |
| `2'b11` | Reserved | — | — |

When AXI3 traffic enters an AXI4 system, a locked access (`2'b10`) is converted to a **normal** access, and the converting component should be able to flag that it did so (§A7.4.1). Software that relied on a locked swap must change: the lock silently stops protecting anything. Exclusive accesses are the AXI4 replacement.

### Global and local monitors

Processor documentation talks about two monitors. These are Arm processor-architecture concepts, not part of IHI0022E (which only points to the Arm Architecture Reference Manual's monitor in §A7.2.3), so treat this as orientation:
- a **local monitor** inside the processor, defined by the Arm Architecture Reference Manual rather than by AXI; which accesses it alone handles depends on the memory's attributes there, so read the processor's documentation for that split;
- a **global monitor** in the interconnect or at the slave, which is the AXI exclusive monitor this lesson describes, handles exclusives that go out on the bus.

Exclusives to cacheable, coherent memory are resolved by the coherency protocol instead; they belong to [B-AMBA-F2 ACE and CHI](/curriculum/T3_Advanced/B-AMBA-F2_Future_Protocols_ACE_CHI/index).

### Pitfalls and misconceptions

1. **"AxPROT[1] = 1 means Secure."** Wrong: 1 means Non-secure (Table A4-6). The encoding matches other Arm security signals, where the asserted value is the less trusted one.
2. **"An exclusive write without a prior exclusive read is a protocol violation."** Wrong: it is legal and fails with OKAY on a supporting slave (§A7.2.3). Do not write an assertion for it; check the expected response in the scoreboard.
3. **"QoS guarantees latency."** Wrong: AXI only carries a priority hint whose use is up to the system, and the ordering rules override it (§A8.1.1, §A8.1.3).
4. **"Exclusives work on any memory type."** Wrong: the monitoring slave must see the access, so cacheable attributes break §A7.2.4.
5. **"Retry until EXOKAY."** Against a slave without exclusive support, the read never returns EXOKAY and the loop never ends; stop on an OKAY read (§A7.2.2).
6. **"The interconnect may adjust AxPROT like it adjusts AxLEN."** Wrong: AxPROT and AxLOCK are never changed (§A4.3.1).
7. **"OKAY on an exclusive write means nothing was written."** Only on a supporting slave; a non-supporting slave writes and answers OKAY (§A7.2.5).

### In a real testbench

- **The sequence item** carries `cache`, `prot`, `qos` and `lock` fields, constrained to the legal Table A4-5 values per channel. Register traffic (from a register-model adapter, see [A-UVM-4A](/curriculum/T3_Advanced/A-UVM-4A_RAL_Fundamentals/index)) should use a Device type; do not randomize AxCACHE freely on register accesses.
- **The driver** drives the fields unchanged, and a responder model for a slave needs an exclusive monitor if the real slave has one.
- **The monitor** records the attributes with each transaction and pairs exclusive reads and writes by ID.
- **The scoreboard** predicts each exclusive response and memory value with a reference model of the monitor, such as `excl_ref_model` in Make It Work. It must be told whether the slave supports exclusives and how many bytes its monitor watches.
- **Protocol assertions** check what is pin-observable: legal AxCACHE values, the exclusive shape, the write-after-read rule.
- **Coverage** records every legal memory type per channel, every AxPROT value, QoS bands, and every exclusive outcome.

// Both masters use AXI ID 0; the interconnect's ID extension (A5.3.5) makes

class excl_race_vseq extends uvm_sequence;
  `uvm_object_utils(excl_race_vseq)
  axi_sequencer m0_sqr, m1_sqr;   // the test sets these from m0_agent and m1_agent

  function new(string name = "excl_race_vseq");
    super.new(name);
  endfunction

  task excl(axi_sequencer sqr, bit is_write, bit [31:0] data);
    axi_item it = axi_item::type_id::create("it");
    start_item(it, -1, sqr);
    if (!it.randomize() with {lock == 1; id == 0; addr == 32'h1000; len == 0;
                              size == 3'd2; is_write == local::is_write;
                              data == local::data;})
      `uvm_fatal("RAND", "exclusive item failed to randomize")

  endtask

    excl(m1_sqr, 0, 0);   // M1 exclusive read:    expect EXOKAY

    excl(m1_sqr, 1, 2);   // M1 exclusive write 2: expect OKAY, memory stays 1
  endtask

|---|---|---|---|

| Exclusive write always OKAY, no other traffic to that word | AWID differs from ARID at the slave (routing); a same-ID exclusive read moved the monitor; a shared monitor taken by another master; a neighbour byte written inside the monitor's granule; cacheable AxCACHE so a cache absorbed the access | Compare AWID and ARID *at the slave port*; check AxCACHE; check the monitor policy and granule | §A7.2.1, §A7.2.3, §A7.2.4 |
| Exclusive write OKAY but memory changed | Slave without exclusive support | Check the exclusive read's response first | §A7.2.5 |
| Exclusive write EXOKAY but memory unchanged | Slave bug | File a DUT bug | §A7.2.3 |
| Status poll never sees the flag change, or a FIFO loses bytes | Register accessed as Normal or cacheable memory | Use a Device AxCACHE for registers | §A4.4.1 |

### Recap

| Signal | Remember |
|---|---|
| AxCACHE[0] Bufferable | No allocate bit: 1 lets an intermediate point answer a write; with an allocate bit: Write-back (1) or Write-through (0); Device reads unaffected |
| AxCACHE[1] Modifiable | 0 = Non-modifiable: no merge, split or change of shape (with listed exceptions) |
| AxCACHE[3:2] | Not `00` means the cache must be looked up; allocation is a hint; names differ per channel |
| Memory types | Twelve; registers use Device; six reserved values |
| AxPROT | [0] privileged, [1] **Non-secure**, [2] instruction (hint); never changed |
| AxQOS | Priority hint; `0000` = not participating; ordering rules win |
| AxLOCK | AXI4: 1 bit, exclusive only; locked transfers removed |
| Exclusive | Read then write, same ID and shape; EXOKAY success, OKAY failure or no support |

## Make It Work

### A reference model you can run

This plain SystemVerilog file models an AXI4 slave's exclusive monitor at transaction level and runs it through five scenarios: the visualizer's four situations and a shape check. The same class is what a scoreboard would call to predict exclusive responses.

```systemverilog
// compile
// excl_kata.sv: a transaction-level model of an AXI4 slave's exclusive monitor
// (Arm IHI0022E A7.2), run through five scenarios. Plain SystemVerilog, no UVM.
module tb_top;

  // RRESP/BRESP encodings used here (IHI0022E Table A3-4)
  typedef enum logic [1:0] {OKAY = 2'b00, EXOKAY = 2'b01} resp_e;

  class excl_ref_model;
    bit          supports_excl;      // 0 models a slave with no exclusive monitor
    bit [31:0]   mon_addr [int];     // per ID: the one address it watches (A7.2.1)
    int unsigned mem [bit [31:0]];   // word memory; a missing entry reads as 0

    function new(bit supports_excl);
      this.supports_excl = supports_excl;
    endfunction

    // A normal write: update memory and end every watch on the location (A7.2.3).
    function resp_e write(bit [31:0] addr, int unsigned data);
      int ids[$];
      mem[addr] = data;
      foreach (mon_addr[id]) if (mon_addr[id] == addr) ids.push_back(id);
      foreach (ids[i]) mon_addr.delete(ids[i]);  // never delete inside its own foreach
      return OKAY;
    endfunction

    function resp_e ex_read(int id, bit [31:0] addr);
      if (!supports_excl) return OKAY;   // no support: OKAY (A7.2.2)
      mon_addr[id] = addr;               // a newer same-ID read moves the watch (A7.2.1)
      return EXOKAY;
    endfunction

    function resp_e ex_write(int id, bit [31:0] addr, int unsigned data);
      if (!supports_excl) return write(addr, data);  // always written, OKAY (A7.2.5)
      if (mon_addr.exists(id) && mon_addr[id] == addr) begin
        void'(write(addr, data));        // success also ends every other watch
        return EXOKAY;
      end
      return OKAY;                       // failed: memory unchanged (A7.2.3)
    endfunction

    function int unsigned peek(bit [31:0] addr);
      return mem.exists(addr) ? mem[addr] : 0;
    endfunction

    // A7.2.4 shape rules; breaking one makes the result UNPREDICTABLE.
    function bit shape_ok(int unsigned beats, int unsigned bytes_per_beat,
                          bit [31:0] addr);
      int unsigned total;
      total = beats * bytes_per_beat;
      return ((total & (total - 1)) == 0) && (total <= 128) && (beats <= 16)
             && ((addr % total) == 0);
    endfunction
  endclass

  int unsigned pass_cnt, fail_cnt;

  function automatic void check_resp(string step, resp_e got, resp_e exp);
    $display("  %s -> %s", step, got.name());
    if (got == exp) pass_cnt++;
    else begin
      fail_cnt++;
      $error("%s: got %s, expected %s", step, got.name(), exp.name());
    end
  endfunction

  function automatic void check_mem(excl_ref_model m, int unsigned exp);
    int unsigned got;
    got = m.peek(32'h1000);
    $display("  memory[0x1000] = %0d", got);
    if (got == exp) pass_cnt++;
    else begin
      fail_cnt++;
      $error("memory[0x1000] = %0d, expected %0d", got, exp);
    end
  endfunction

  function automatic void check_shape(excl_ref_model m, int unsigned beats,
                                      int unsigned bytes, bit [31:0] addr,
                                      bit exp_ok);
    bit ok;
    ok = m.shape_ok(beats, bytes, addr);
    $display("  exclusive %0d x %0d bytes at 0x%0h -> %s", beats, bytes, addr,
             ok ? "legal" : "breaks A7.2.4 (UNPREDICTABLE)");
    if (ok == exp_ok) pass_cnt++;
    else begin
      fail_cnt++;
      $error("shape check disagrees with A7.2.4");
    end
  endfunction

  localparam bit [31:0] LOCK = 32'h1000;  // the lock word
  localparam int M0 = 0, M1 = 1;          // IDs as seen at the slave

  initial begin
    excl_ref_model m;

    $display("1. Uncontended");
    m = new(1);
    check_resp("M0 exclusive read", m.ex_read(M0, LOCK), EXOKAY);
    check_resp("M0 exclusive write 1", m.ex_write(M0, LOCK, 1), EXOKAY);
    check_mem(m, 1);

    $display("2. Intervening normal write");
    m = new(1);
    check_resp("M0 exclusive read", m.ex_read(M0, LOCK), EXOKAY);
    check_resp("M1 normal write 7", m.write(LOCK, 7), OKAY);
    check_resp("M0 exclusive write 1", m.ex_write(M0, LOCK, 1), OKAY);
    check_mem(m, 7);

    $display("3. Two masters race");
    m = new(1);
    check_resp("M0 exclusive read", m.ex_read(M0, LOCK), EXOKAY);
    check_resp("M1 exclusive read", m.ex_read(M1, LOCK), EXOKAY);
    check_resp("M0 exclusive write 1", m.ex_write(M0, LOCK, 1), EXOKAY);
    check_resp("M1 exclusive write 2", m.ex_write(M1, LOCK, 2), OKAY);
    check_mem(m, 1);

    // Software should stop after the OKAY read (A7.2.2); the write is
    // issued anyway to show what a slave without support does with it.
    $display("4. Slave without exclusive support");
    m = new(0);
    check_resp("M0 exclusive read", m.ex_read(M0, LOCK), OKAY);
    check_resp("M0 exclusive write 3", m.ex_write(M0, LOCK, 3), OKAY);
    check_mem(m, 3);

    $display("5. Exclusive shapes");
    check_shape(m, 1, 4, 32'h1000, 1);
    check_shape(m, 3, 4, 32'h1004, 0);

    $display("PASS=%0d FAIL=%0d", pass_cnt, fail_cnt);
    $finish;
  end
endmodule
```

**Expected output.** Traced by hand from the code and cross-checked against the course's exclusive-access model (the visualizer above); illustrative, not from a simulator run. Your simulator adds its own message at `$finish`.

```text
1. Uncontended
  M0 exclusive read -> EXOKAY
  M0 exclusive write 1 -> EXOKAY
  memory[0x1000] = 1
2. Intervening normal write
  M0 exclusive read -> EXOKAY
  M1 normal write 7 -> OKAY
  M0 exclusive write 1 -> OKAY
  memory[0x1000] = 7
3. Two masters race
  M0 exclusive read -> EXOKAY
  M1 exclusive read -> EXOKAY
  M0 exclusive write 1 -> EXOKAY
  M1 exclusive write 2 -> OKAY
  memory[0x1000] = 1
4. Slave without exclusive support
  M0 exclusive read -> OKAY
  M0 exclusive write 3 -> OKAY
  memory[0x1000] = 3
5. Exclusive shapes
  exclusive 1 x 4 bytes at 0x1000 -> legal
  exclusive 3 x 4 bytes at 0x1004 -> breaks A7.2.4 (UNPREDICTABLE)
PASS=17 FAIL=0
```

**Trace of scenario 3**, the one people get wrong:

| Step | `mon_addr` after the step | Response | `mem[0x1000]` |
|---|---|---|---|
| M0 exclusive read | ID 0 → 0x1000 | EXOKAY | 0 |
| M1 exclusive read | ID 0 → 0x1000, ID 1 → 0x1000 | EXOKAY | 0 |
| M0 exclusive write 1 | empty: the write ended both watches | EXOKAY | 1 |
| M1 exclusive write 2 | empty | OKAY | 1 |

**Simplification.** The model watches exactly one word per ID. A real monitor watches the bytes of the access and may watch up to 128 bytes, which adds the "neighbouring byte" failures of §A7.2.4.

**Run it.** Compile `excl_kata.sv` with `tb_top` as the top module in any simulator that supports SystemVerilog classes and associative arrays, and run it with no arguments. Class and associative-array support in open-source simulators varies by tool and version (tool-dependent).

### Pin-level checks and coverage

The reference model checks *responses*. Three rules are visible on the pins and belong in a protocol checker bound to the slave interface. Each property names the rule it checks.

```systemverilog
// snippet: add to a checker module that has the AXI4 signals as inputs and a
// parameter ID_W, the width of ARID, AWID and RID.

// [Protocol Table A4-5] only the legal memory-type encodings; the rest are reserved.
a_arcache_legal: assert property (@(posedge ACLK) disable iff (!ARESETn)
  ARVALID |-> (ARCACHE[1] || ARCACHE[3:2] == 2'b00));
a_awcache_legal: assert property (@(posedge ACLK) disable iff (!ARESETn)
  AWVALID |-> (AWCACHE[1] || AWCACHE[3:2] == 2'b00));

// [Protocol A7.2.4] the shape of every exclusive access, on both channels.
a_excl_shape_ar: assert property (@(posedge ACLK) disable iff (!ARESETn)
  ARVALID && ARLOCK |->
    $onehot(((ARLEN + 1) << ARSIZE)) &&           // power of 2 bytes
    (((ARLEN + 1) << ARSIZE) <= 128) &&          // at most 128 bytes
    (ARLEN <= 15) &&                             // AXI4: at most 16 transfers
    ((ARADDR % ((ARLEN + 1) << ARSIZE)) == 0));  // aligned to the total
a_excl_shape_aw: assert property (@(posedge ACLK) disable iff (!ARESETn)
  AWVALID && AWLOCK |->
    $onehot(((AWLEN + 1) << AWSIZE)) &&
    (((AWLEN + 1) << AWSIZE) <= 128) &&
    (AWLEN <= 15) &&
    ((AWADDR % ((AWLEN + 1) << AWSIZE)) == 0));

// [Protocol A7.2.2] the write of a pair starts only after its read completes.
int unsigned rd_issued [2**ID_W];  // AR handshakes per ID
int unsigned rd_done   [2**ID_W];  // RLAST handshakes per ID
int unsigned excl_tag  [2**ID_W];  // issue number of the latest exclusive read
bit          excl_seen [2**ID_W];  // an exclusive read was issued on this ID

always_ff @(posedge ACLK or negedge ARESETn)
  if (!ARESETn) begin
    rd_issued <= '{default: 0};
    rd_done   <= '{default: 0};
    excl_seen <= '{default: 0};
  end else begin
    if (ARVALID && ARREADY) begin
      rd_issued[ARID] <= rd_issued[ARID] + 1;
      if (ARLOCK) begin
        excl_tag[ARID]  <= rd_issued[ARID];  // its number in this ID's issue order
        excl_seen[ARID] <= 1'b1;
      end
    end
    if (RVALID && RREADY && RLAST) rd_done[RID] <= rd_done[RID] + 1;
  end

// Same-ID reads complete in order (A5.3.1), so read number excl_tag is complete
// once more than excl_tag reads on that ID have completed.
a_excl_wr_after_rd: assert property (@(posedge ACLK) disable iff (!ARESETn)
  AWVALID && AWLOCK && excl_seen[AWID] |-> rd_done[AWID] > excl_tag[AWID]);

// [Not a protocol rule] an exclusive write with no earlier exclusive read is
// legal and fails with OKAY: check the response in the scoreboard instead.
```

Three notes on these checks. The counters are separate arrays, so an AR handshake and an RLAST handshake for the same ID at the same edge both count. AXI4 write data carries no ID, so the checker sees the start of the write part only through AWVALID; W beats sent before their AW are not attributed. And `a_excl_shape_*` evaluates `(ARLEN + 1) << ARSIZE` in 32 bits, because the literal `1` is a 32-bit integer (IEEE 1800-2023 §11.6.1), so ARLEN = 255 cannot overflow it.

The coverage model samples each address handshake. Write a twin for AW with the AWCACHE values from Table A4-5, which differ.

```systemverilog
// snippet: read address channel attribute coverage (IHI0022E Tables A4-5, A4-6)
covergroup ar_attr_cg @(posedge ACLK iff (ARESETn && ARVALID && ARREADY));
  cp_cache: coverpoint ARCACHE {
    bins device_nb    = {4'b0000};
    bins device_b     = {4'b0001};
    bins normal_nc_nb = {4'b0010};
    bins normal_nc_b  = {4'b0011};
    // One bin per value ([]): a single bin over a value set would close as soon
    // as any one member was sent. On AR, No-allocate and Write-allocate share a
    // value, so 8 of these 10 bins cover all 12 memory types; the other two are
    // the legal AXI3 values 0110 and 0111.
    bins write_thru[] = {4'b1010, 4'b1110, 4'b0110};  // AR values, incl. AXI3 0110
    bins write_back[] = {4'b1011, 4'b1111, 4'b0111};  // AR values, incl. AXI3 0111
    illegal_bins reserved = {4'b0100, 4'b0101, 4'b1000, 4'b1001, 4'b1100, 4'b1101};
  }
  cp_prot: coverpoint ARPROT;          // automatic bins: all 8 values
  cp_qos: coverpoint ARQOS {
    bins none = {0};                   // not in any QoS scheme (A8.1.1)
    bins mid  = {[1:14]};
    bins max  = {15};
  }
  cp_lock: coverpoint ARLOCK { bins normal = {0}; bins exclusive = {1}; }
  x_lock_prot: cross cp_lock, cp_prot; // exclusives in every security state
endgroup
```

Exclusive *outcomes* (EXOKAY, OKAY-failed, OKAY on a non-supporting slave, an abandoned pair) are not visible on one channel; cover them in the scoreboard, where `excl_ref_model` knows which one each response was.

### How to verify the attributes of an AXI port

1. **Read the DUT's attribute contract.** Which memory types, AxPROT values and QoS values must it handle? Does it support exclusives, with which monitor policy and granule?
2. **Put the legal encodings in the item's constraints**, one table per channel, and keep register traffic on a Device type.
3. **Bind the pin-level checks**: legal AxCACHE, exclusive shape on AR and AW, and write-after-read.
4. **Build the exclusive reference model** (as in Make It Work) and connect it to the scoreboard, configured with the slave's support and monitor policy.
5. **Write directed exclusive scenarios**: uncontended, intervening write, race, unpaired write, abandoned pair, and a neighbour write inside the granule.
6. **Write AxPROT scenarios** against the DUT's permission rules, with the expected refusal response taken from the DUT specification.
7. **Check QoS under contention** if the DUT arbitrates: make two masters compete with different AxQOS values, check that a QoS-honouring arbiter prefers the higher value only where no ordering rule applies (same-ID data still returns in order, §A8.1.3), and measure latency against the integration contract, not against AXI.
8. **Check for legacy locked traffic** if an AXI3 master is attached: an AXI3 locked access (AxLOCK = `2'b10`) must arrive as a normal access (§A7.4.1), and no software flow may rely on it for mutual exclusion.
9. **Close coverage** per channel, then cross exclusive with AxPROT and with the memory types the DUT supports.

**Checklist before moving on:**
- [ ] I can decode any AxCACHE value on AR or AW into a memory type and say whether it may be answered early, merged or served from a cache.
- [ ] I can give AxPROT for a scenario without inverting bit 1.
- [ ] I can predict every response and memory value in the five scenarios above, and say what changes with a shared monitor.
- [ ] I can explain why AXI4 removed locked transfers and what happens to an AXI3 locked access in an AXI4 system.
- [ ] I can explain why a high QoS value guarantees neither latency nor overtaking.
- [ ] My plan separates pin-level assertions (legal values, shape, write after read) from scoreboard checks (exclusive responses and memory).

## Push Further

### Expert: what an interconnect may legally change

IHI0022E §A4.3.1 draws the line precisely.
- **Non-modifiable** (AxCACHE[1] = 0): the transaction must not be split or merged, and its address (and so AxREGION, the region signal described under *AxREGION and AxUSER* below), size, length, burst type, lock and protection are fixed (Table A4-2). AxCACHE may change only from Bufferable to Non-bufferable. The ID and QoS may change.
- **Exceptions:** a Non-modifiable burst longer than 16 beats may be split into shorter bursts with adapted addresses; a Non-modifiable exclusive may change AxSIZE and AxLEN if the total bytes stay the same; and downsizing to a bus narrower than AxSIZE forces modification (the component may flag it).
- **Modifiable:** a transaction may be split, merged, made to fetch more, or widened with strobes, and AxADDR, AxSIZE, AxLEN and AxBURST may change. AxLOCK and AxPROT never change. AxCACHE may change only in ways that do not reduce visibility.
- **Never, for any transaction:** a change that reaches into a different 4KB space, or splits a single-copy-atomic access (a block that must be updated all at once; see *single-copy and multi-copy atomicity* below) into several accesses.

So a checker that compares a transaction before and after an interconnect must allow the listed changes. Comparing every field one to one false-fires on a legal interconnect that splits a 256-beat Device INCR burst.

### Expert: buffering, early responses and proof of arrival

An intermediate buffer that answers early takes on obligations (§A4.6, §A6.5). A buffered write must still reach its destination in a timely manner, and merging new writes into it must not reset the drain timer; a forwarded Normal Non-cacheable read must not be served forever from a buffer, and re-reading must not reset that timeout either. The component that answered must also make the write visible to any later transaction to an overlapping address and, for Device memory, keep later same-ID transactions to the same slave in order.

How then does software know a Device Bufferable write has *arrived*? Follow it with a Device Non-bufferable write with the same ID to the same slave. The ordering rules force the earlier writes to reach the slave before the final one is answered from there, so its response proves all of them are visible (§A4.9.1). The guarantee covers only the same ID and the same slave.

### Expert: mismatched and changing memory attributes

Different masters may use different attributes for the same memory, within rules (§A4.5). All masters must agree on whether a region is cacheable: either all use AxCACHE[3:2] = `2'b00`, or all set at least one of those bits. Allocation hints may differ. A Normal Non-cacheable region may be accessed as Device, and a Bufferable region with non-bufferable transactions, because those only add guarantees. Changing a region's type, for example from Write-through to Normal Non-cacheable, needs a procedure: all masters stop, one performs any cache maintenance, then all restart with the new attributes (§A4.5.1). In a system testbench, a scoreboard that sees one master read cacheable data that another master just wrote as non-cacheable is looking at a break of the §A4.5 rule, which the specification says "must be obeyed" for functional correctness. It is a system-level rule: each interface on its own is legal, so no single-interface protocol checker can see it, and only a check that compares the attributes different masters use for the same region can.

### Expert: exclusive monitors in real systems

- **Policy.** One monitor per exclusive-capable ID (recommended), or fewer shared ones; a shared monitor makes legal but surprising failures and can stall two masters that keep retrying against each other.
- **Granule.** Monitoring up to 128 bytes is allowed and causes failures from neighbouring writes (§A7.2.4); software keeps lock words in their own granule.
- **IDs at the slave.** The monitor sees IDs after interconnect extension (§A5.3.5); two masters that use ARID 0 are different IDs at the slave.
- **Where exclusives are impossible.** AXI4-Lite has no exclusive accesses: AxLOCK is absent, EXOKAY is not supported and every access is Device Non-bufferable (`AxCACHE = 4'b0000`) (§B1.1). An exclusive routed to an AXI4-Lite slave through the specification's AXI-to-AXI4-Lite conversion therefore cannot succeed: the conversion discards AxLOCK, so every exclusive write fails with OKAY, never EXOKAY (§B1.3.1), and the write reaches the Lite slave as a normal write and is performed, as on any slave without exclusive support (§A7.2.5). [B-AMBA-1](/curriculum/T3_Advanced/B-AMBA-1_Protocol_Families_and_Tradeoffs/index) covers AXI4-Lite.
- **Issue E versus Issue L on mismatched pairs.** In IHI0022E, a write whose size, length, address, ID or control signals differ from the preceding exclusive read breaks §A7.2.4, so the result is UNPREDICTABLE and a checker flags it. IHI0022L softens this: if the signals of its Table A6.5 differ, the exclusive write *might fail* even though nobody wrote the location (§A6.3.3), and §A6.3.4 lists a missing exclusive read with the same attributes among the reasons a write finds its address unmonitored, which ends in OKAY with the location not written. So find out which issue your DUT's specification follows before you decide whether a mismatch is an assertion failure or an OKAY the scoreboard must accept.
- **Coherent exclusives** (cacheable memory with ACE or CHI) use a different mechanism; see [B-AMBA-F2](/curriculum/T3_Advanced/B-AMBA-F2_Future_Protocols_ACE_CHI/index).

### Expert: single-copy and multi-copy atomicity

Chapter A7 of IHI0022E starts before exclusives. The **single-copy atomicity size** is the smallest block a transaction updates atomically: no master may ever see a half-updated block (§A7.1). AXI4 does not fix the size; a system may have, say, a 32-bit group that includes peripherals and a 64-bit group of processor, DSP and memory controller, and every component on a communication path must support the size in use. A transaction never has a guarantee larger than the alignment of its start address, and byte strobes do not change the size. **Multi-copy atomicity** is a system property: all agents see writes to a location in the same order, and a write visible to one other agent is visible to all (§A7.1.1). It needs a single point of serialization per address and no forwarding buffers upstream of agents, and it is required in systems with ARMv8 processors, for their Store-Release instruction. For verification this means two things: a read-after-write check in [B-AXI-3](/curriculum/T3_Advanced/B-AXI-3_AXI_Ordering_and_IDs/index) may only expect whole atomic blocks, and an interconnect's early-forwarding buffers are a multi-copy-atomicity risk to review.

### Expert: AxREGION and AxUSER (awareness)

Two optional AXI4 signal groups complete the attribute set (§A8.2, §A8.3).
- **AxREGION** (4 bits) is produced by the interconnect's address decoder so that one physical slave interface can present up to sixteen logical interfaces, for example a data window and a register window. It must be constant within any 4KB space, it is fixed for Non-modifiable transactions (Table A4-2), and the slave must give a protocol-correct response to every value, even regions it does not implement. Same-ID responses to different regions must still come back in order.
- **xUSER** signals may exist on any channel, with an implementation-defined width. The specification recommends not using them, because their meaning is not defined and two components can disagree. If your interface has them, include them in the handshake stability checks and in the item.

### Expert: AXI5 atomic transactions (awareness)

AXI5 adds a second, different way to update memory atomically: the **atomic transaction**. Sources: Arm IHI0022L (Issue L, 2025) §A6.4; the Atomic_Transactions property dates from Issue F. Issue L uses the terms manager and subordinate.
- **What it is.** One transaction that carries an *operation* to the data: the manager sends address, operation and operand on AW and W; the subordinate (or an interconnect that supports atomics) reads the location, computes, stores the result, and answers. The whole written location is updated atomically.
- **Four forms** (§A6.4.1): **AtomicStore** (operation and operand; one B response, no data back), **AtomicLoad** (the same, but also returns the original value), **AtomicSwap** (writes the new value, returns the old) and **AtomicCompare** (sends a compare and a swap value; writes the swap value only if the location equals the compare value; returns the old value). Store and Load support eight operations: ADD, CLR, EOR, SET, SMAX, SMIN, UMAX and UMIN (§A6.4.2).
- **Signalling** (§A6.4.6). A 6-bit **AWATOP** field on the write address channel: `6'b000000` non-atomic, `6'b01exxx` AtomicStore, `6'b10exxx` AtomicLoad, `6'b110000` AtomicSwap, `6'b110001` AtomicCompare, where `e` (AWATOP[3]) selects big-endian arithmetic and `xxx` the operation. AWLOCK must be deasserted: an atomic transaction is never exclusive (§A6.4.5).
- **Sizes** (§A6.4.3). Store, Load and Swap send 1, 2, 4 or 8 bytes, with AWADDR aligned to that size and an INCR burst. Compare sends 2 to 32 bytes (both values) and receives half that.
- **Responses** (§A6.4.7, §A6.4.8). Load, Swap and Compare return the original data on the **read data channel**, with the same ID as the AW, as well as one B response. There is no failure code: to know whether a compare-and-swap took effect, software compares the returned old value with its compare value. A component without atomic support may answer with an error.
- **IDs** (§A6.4.4). An atomic's ID must be unique in flight: no other outstanding transaction may use it on the channels the atomic uses.
- **Support** (§A6.4.10). Optional, declared by the Atomic_Transactions property; a component that declares it must support every operation, size and endianness. An atomic must not be passed to a component without support; an interconnect without support must stop its managers issuing atomics. AXI5-Lite does not have atomics (Table B2.4).

**Verification impact.** A monitor that matches every R beat to an earlier AR breaks on atomics: R data now also answers an AW. The scoreboard needs an operation model (the eight operations, endianness, compare), the ID checker needs the unique-in-flight rule, and the exclusive monitor model does not predict an atomic's result; it only has to treat an atomic that changes a watched location as a write to that location (our reading of "until a write occurs to that location", IHI0022E §A7.2.3). The trade-off in one line: an exclusive pair needs no smart target but can fail and retry; an atomic never fails for contention and keeps the data busy for less time, but every component an atomic is passed to must support it (for Cacheable atomics an interconnect may perform the operation itself instead of passing it on, §A6.4.10).

### Kata: a shared monitor

**Given:** the `excl_ref_model` of Make It Work.

**Do:** add a mode `bit shared_monitor;` in which the slave has a single monitor for all IDs, as in the visualizer's "One shared monitor". Then, without running anything, predict the four responses and the final memory value of scenario 3 ("Two masters race") in that mode.

<details>
<summary>Worked solution</summary>

One line in `ex_read` makes the monitor single: before recording the new watch, forget every other one.

```systemverilog
// snippet: changes to excl_ref_model
bit shared_monitor;   // 1: one monitor for all IDs (allowed, not recommended, A7.2.3)

function resp_e ex_read(int id, bit [31:0] addr);
  if (!supports_excl) return OKAY;   // A7.2.2
  if (shared_monitor) mon_addr.delete();   // the single monitor moves to this ID
  mon_addr[id] = addr;                     // A7.2.1
  return EXOKAY;
endfunction
```

Scenario 3 with `shared_monitor = 1`:

| Step | `mon_addr` after | Response | `mem[0x1000]` |
|---|---|---|---|
| M0 exclusive read | ID 0 → 0x1000 | EXOKAY | 0 |
| M1 exclusive read | ID 1 → 0x1000 (ID 0 forgotten) | EXOKAY | 0 |
| M0 exclusive write 1 | ID 1 → 0x1000 | **OKAY** (not written) | 0 |
| M1 exclusive write 2 | empty | **EXOKAY** | 2 |

The result is still correct mutual exclusion (one winner), but the *later* reader wins, M0 fails although nobody wrote the word, and if both masters keep re-reading before writing, each read can cancel the other's watch indefinitely. The visualizer's race with "One shared monitor" shows M0's failure. In a scoreboard, the monitor policy is therefore a configuration of the reference model, never a hard-coded assumption.

</details>

### Debug challenge: the lock that never locks

A bring-up engineer sends you this monitor log from a two-master system. Software spins forever on its exclusive store.

```text
@1200ns AR  ARID=0x2 ARADDR=0x8000_0040 ARLOCK=1 ARLEN=0 ARSIZE=2 ARCACHE=4'b0011
@1260ns R   RID=0x2  RRESP=EXOKAY
@1270ns AW  AWID=0x5 AWADDR=0x8000_0060 AWLOCK=0 AWLEN=0 AWSIZE=2 AWCACHE=4'b0011
@1290ns B   BID=0x5  BRESP=OKAY
@1300ns AW  AWID=0x2 AWADDR=0x8000_0040 AWLOCK=1 AWLEN=0 AWSIZE=2 AWCACHE=4'b0011
@1340ns B   BID=0x2  BRESP=OKAY
... the same pattern repeats every 200 ns; nobody writes 0x8000_0040
```

The log was captured at the slave port. Name the most likely cause, the clause, and two ways to fix it before you open the answer.

<details>
<summary>Answer</summary>

The pair itself is legal: same ID, address and shape, a power-of-two size, aligned, non-cacheable (`4'b0011` has no allocate bit), and the write starts after the read completes. The clue is the other master's normal write (ID 5) to **0x8000_0060**, 32 bytes away and in the same 128-byte aligned block. It arrives at 1270 ns and completes at 1290 ns, inside every read-to-write window: after the exclusive read's data (1260 ns) and before the exclusive write (1300 ns). The slave's monitor watches a granule larger than the 4-byte access (up to 128 bytes is allowed), so that neighbouring write ends the watch and every exclusive store fails with OKAY (IHI0022E §A7.2.4). Because the other master writes on the same 200 ns rhythm, the retry loop never wins.

Fixes: move the lock word into its own monitor granule (for example its own 128-byte aligned block), or use a slave whose monitor watches only the accessed bytes. In the testbench, configure the reference model with the real granule so the scoreboard predicts these failures instead of flagging them. Before concluding, rule out the other suspects from the debugging table: AWID equal to ARID *at the slave* (it is), no same-ID exclusive read in between (there is none), and the monitor policy.

</details>
