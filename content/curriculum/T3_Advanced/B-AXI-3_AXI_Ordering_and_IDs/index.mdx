## Quick Take

- **What it is:** Every AXI request carries a **transaction ID** (AWID on writes, ARID on reads), and the slave copies it onto the response (BID, RID). An ID names an **ordering stream**. Transactions with one ID, in one direction (all reads, or all writes), complete in the order they were issued. Transactions with different IDs may complete in any order, and their read data may even interleave beat by beat (Arm IHI0022E §A5.1, §A5.3, §A5.3.1).
- **Why it matters:** An AXI master can have many transactions **outstanding** (issued but not finished) at once. Every monitor, scoreboard and interconnect check you write must accept every legal response order and flag only the illegal ones. A checker that expects "first in, first out" fails on correct hardware; a checker that accepts anything misses real data-corruption bugs.
- **The Analogy:** Supermarket checkout lanes. Customers in one lane leave in the order they joined; different lanes finish independently, so a quick customer in lane 2 can leave before a slow one who arrived earlier in lane 1. *Where it breaks:* reads and writes are two different shops, so the same lane number in each shop gives no order between them. And a read "lane" can hand over bags one at a time, interleaved with bags from other lanes, which no real checkout does.

**You will be able to:**
1. Predict which response and read-data orders are legal for outstanding transactions with the same and with different IDs, including interleaved read data.
2. Explain why AXI4 write data is never interleaved and always follows the write-address order, and what that means for a monitor.
3. Decide whether a read must return the data of an earlier write, and write the scoreboard's read-after-write policy.
4. Explain how an interconnect extends IDs, routes responses back, and keeps same-ID order across slaves.
5. Design ID-aware checking: place each ordering check in an assertion or in the scoreboard, and write a per-ID expected-queue model.

## Build Your Mental Model

**What you need from earlier lessons.** The five channels and the VALID/READY handshake from [B-AXI-1](/curriculum/T3_Advanced/B-AXI-1_AXI_Channel_Architecture/index); AxLEN, beats and RLAST from [B-AXI-2](/curriculum/T3_Advanced/B-AXI-2_AXI_Burst_Math/index); and keyed matching with one queue per key from [A-UVM-6](/curriculum/T3_Advanced/A-UVM-6_Scoreboards_and_Reference_Models/index).

**How to read this lesson.** The core path is four rules, each with a waveform: same ID in order, different IDs in any order, AXI4 write data in address order, and no order between reads and writes. Between them sit the two ideas the rules rely on (outstanding transactions and IDs) and, after them, the interconnect and where each check lives in a testbench. Device-versus-Normal memory and the full AXI4 ordering model are practitioner and expert depth; you can skip them on a first pass, because the four rules do not depend on them.

**Reading the waveforms.** Each waveform shows the value of every signal at numbered rising edges of the clock. A hatched bus value means nothing is being transferred on that bus at that edge (not an error). Markers above the waveform flag the edges to look at: ✓ a transfer the rules allow, ● a point to notice, ▼ a monitor action. Hover over a marker for its text; the caption carries the same information.

**Words you need first.**
- A **master** starts transactions (a CPU, a DMA engine); a **slave** answers them (a memory controller, a register block). IHI0022E uses these words; later Arm issues say **manager** and **subordinate** for the same roles. This track says master and slave.
- AXI has five **channels**: write address (AW), write data (W), write response (B), read address (AR) and read data (R). A **transfer** happens on a channel at a rising edge of the clock **ACLK** where its VALID and READY are both 1; that edge is the channel's **handshake** ([B-AXI-1](/curriculum/T3_Advanced/B-AXI-1_AXI_Channel_Architecture/index)).
- A **transaction** is one read or one write. It moves its data as a **burst** of AxLEN + 1 **beats** (one beat per data transfer), and the slave marks the last read beat with RLAST ([B-AXI-2](/curriculum/T3_Advanced/B-AXI-2_AXI_Burst_Math/index)). A write ends with one response on B, which carries BID and a response code BRESP, such as OKAY (success) or SLVERR (slave error) (§A3.4.4).
- A transaction is **issued** at its address handshake (AW or AR). It is **complete** when the master has its response: for a read, the last read beat; for a write, the write response on B. Sending all the write data does not complete a write (§A5.3.4).
- The **direction** of a transaction is read or write. **Issue order** is the order of one master's address handshakes in one direction.
- An **interconnect** is the fabric that connects several masters to several slaves and routes each request and response.
- In a testbench, a **monitor** watches the pins and turns handshakes into transaction objects, a **scoreboard** compares what was observed with what was expected ([A-UVM-6](/curriculum/T3_Advanced/A-UVM-6_Scoreboards_and_Reference_Models/index)), and an **assertion** is an SVA property checked on the pins every clock ([I-SV-4A](/curriculum/T2_Intermediate/I-SV-4A_SVA_Fundamentals/index)).

### Outstanding transactions

In AHB, one transfer at a time is in its data phase and transfers finish in order. AXI decouples requests from responses: a master can issue several read addresses on AR, one after another, before any read data comes back. Each such transaction is **outstanding** from its address handshake until it completes.

**Predict first.** A master issues three single-beat reads with ARIDs 0, 1 and 2, in that order. Must the read data come back in the order 0, 1, 2?

**Debrief.** No. The three reads have different IDs, so the slave may answer in any order (§A5.3), for example because ID 2 hit a fast buffer while ID 0 went to DRAM. Had all three used one ARID, only the order 0, 1, 2 would be legal. The rest of this lesson makes that difference precise.

**Why outstanding transactions exist.** One read to a memory with a 100-cycle latency, issued alone, leaves the R channel idle for 100 cycles. With several reads outstanding, their latencies overlap: while the first is still in the memory, the next ones are already queued behind it. Throughput then grows with the number outstanding until the R channel is full. *Push Further* turns this into a sizing estimate.

**Outstanding depth is a design parameter, not a protocol number.** IHI0022E sets no maximum. Each master decides how many transactions it issues before it must wait, and each slave decides how many it accepts: when it is full, it holds AWREADY or ARREADY low (backpressure). A slave also has a **read data reordering depth**: "the number of addresses pending in the slave that can be reordered". A slave that processes everything in order has a depth of one, the value "must be specified by the designer of the slave", and "there is no mechanism by which a master can determine" it (§A5.3.1). For verification, the consequence is direct: ordering bugs live at high outstanding depth, so your tests and coverage must reach the DUT's maximum.

### IDs on every channel

Each channel has its own ID signal (§A5.2, Table A5-1):

| Channel | ID signal | Driven by |
|---|---|---|
| Write address (AW) | AWID | master |
| Write data (W) | WID, **AXI3 only** | master |
| Write response (B) | BID | slave, copied from AWID |
| Read address (AR) | ARID | master |
| Read data (R) | RID | slave, copied from ARID |

"Slaves are required to reflect on the appropriate BID or RID response an AXI ID received from a master" (§A5.1 Note), and "the slave must ensure that the RID value of any returned data matches the ARID value of the address to which it is responding" (§A5.3.1). That is what lets a monitor match a response to its request.

IHI0022E describes the effect as one port acting as several: "a single physical port can support out-of-order transactions by acting as a number of logical ports, each of which handles its transactions in order" (§A5.1). Each ID is one such logical port.

**How wide is an ID?** The width "is IMPLEMENTATION DEFINED". The specification recommends up to 4 bits at a master, up to 4 more bits added by the interconnect for master-port numbers, and 8 bits of ID support at a slave (§A5.3.6). A master that needs only one ordered stream may tie its ID outputs to a constant such as 0, and then everything it issues is in order. **AXI4-Lite** has no IDs at all: "all transactions must be in order" (§B1.1.4; [B-AMBA-1](/curriculum/T3_Advanced/B-AMBA-1_Protocol_Families_and_Tradeoffs/index) covers AXI4-Lite).

### Rule 1: same ID, same direction, issue order

The exact rule (§A5.3, §A5.3.1, §A6.1):
- **Reads:** read data of transactions with the same ARID returns in the order the master issued the addresses. The beats of two same-ID reads are never mixed: all of the first read's beats come before any beat of the second.
- **Writes:** writes with the same AWID complete in issue order, so their B responses with that BID come back in AW order.
- **Only within one direction.** A read and a write are never ordered by sharing an ID value. That is Rule 4.

**Predict first.** Reads A and B both use ARID 3 and both have two beats. A was issued first. May B's first beat arrive between A's two beats?

**Debrief.** No. Same-ID beats never mix, so B0 cannot sit between A0 and A1, and B cannot return first either: the orders B0, B1, A0, A1 and A0, B0, A1, B1 are both illegal (§A5.3.1). Only the drawn order is legal. This is also what makes a monitor's job simple for one ID: every beat with RID 3 belongs to the **oldest** outstanding read with ARID 3.

**Pitfall: one slot per ID.** Rule 1 exists because several transactions with one ID can be outstanding at once, as A and B are here. A model that keeps a single entry per ID, such as `pending[id]`, overwrites A when B's address arrives. It then compares A's data with B's request, and finds no request at all when B's data arrives. Per-ID state must be a queue in issue order, as `exp_q[id][$]` is in *Make It Work* (§A5.3.1).

**Why masters use one ID.** One ID gives an in-order stream for free. A master reading several words from a FIFO-mapped peripheral register gives those reads one ARID, so the data comes back in the order it was requested. If a sequence of reads, or a sequence of writes, must complete in order, give them one ID. It does not order a read against a write; for that, see Rule 4.

**Pitfall: "same ID" is the ID at the slave.** Two masters that both use ARID 2 are *not* one stream. "Transactions from different masters have no ordering restrictions" (§A5.3), because the interconnect makes their IDs different (see the interconnect section below).

### Rule 2: different IDs, any order, and read data may interleave

"Transactions from the same master, but with different ID values, have no ordering restrictions. They can complete in any order" (§A5.3). This applies to reads and to writes. For reads it goes one step further: "read data of transactions with different ARID values can be interleaved" (§A5.3.1), that is, beats of two reads can alternate on R.

**Predict first.** Read A (ARID 1, two beats) is issued before read B (ARID 2, two beats). Is the R order B0, A0, B1, A1 legal?

**Debrief.** Yes. Overtaking and interleaving are both legal across IDs. So RLAST ends a burst *for its RID only*: a monitor must collect R beats per RID and must never assume a burst arrives in one piece.

**Why it exists.** A slave that receives reads for IDs 1 and 2 can return ID 2's data first if ID 2 hits in a cache while ID 1 misses and goes to DRAM. Without reordering, every slow transaction would block every fast one behind it.

**Pitfall: one queue for all IDs.** A scoreboard that keeps a single first-in, first-out queue for every read flags this legal waveform as an error. Keep one queue per ID ([A-UVM-6](/curriculum/T3_Advanced/A-UVM-6_Scoreboards_and_Reference_Models/index) teaches the keyed-queue pattern).

### Rule 3: AXI4 write data follows the write-address order

The W channel in AXI4 has **no ID**. "In AXI4, all write data for a transaction must be provided in consecutive transfers on the write data channel", and "all write data must be in the same order as the associated write addresses" (§A5.4, §A5.4.1). This holds "even if the write transactions have different AWID values, and even if they come from different masters" (§A5.3.2). So W beats are never interleaved across writes, whatever the AWIDs.

There is one twist a monitor must handle. AXI defines no timing relation between the AW and W channels, so "the write data can appear at an interface before the write address for the transaction" (§A3.3). The *order* of the bursts on W still follows the order of the addresses on AW; only the timing can lead.

**Predict first.** The master issues write X (AWID 0, two beats), then write Y (AWID 1, one beat). Is the W order Y0, X0, X1 legal, given that the IDs differ?

**Debrief.** No. Different AWIDs let the **B responses** of X and Y come back in any order (Rule 2), but they do not let the **data** reorder or interleave: W must carry all of X, then all of Y. Y0 before X0, or Y0 between X0 and X1, is illegal (§A5.4). The drawn waveform is legal, including X0 before X's AW and Y0 on the same edge as Y's AW (§A3.3). A monitor therefore keeps a queue of complete W bursts (ended by WLAST) and a queue of AW handshakes, and pairs them first with first, whichever arrives earlier. The kata solution in *Practice & Reinforce* builds this pairing.

**Pitfall: assuming AW comes first.** A monitor that treats W data with no AW yet as an error, or that pairs each W burst with the AW nearest in time, breaks on legal traffic like the waveform above. Pair by order, not by time.

**History: WID in AXI3.** AXI3 allowed **write data interleaving**: a slave could accept beats of writes with different IDs mixed together, identified by WID. AXI4 removed write data interleaving (§A5.4). That made WID redundant, and AXI4 removed the WID signals "to reduce the pin-count of the interface" (§A5.4.1). The specification also notes that most slave designs do not support write data interleaving (§A5.3.2 Note). *Push Further* covers the legacy rules.

### Rule 4: reads and writes are not ordered, even with one ID

"AXI has no ordering restrictions between read and write transactions. They can complete in any order, even if the ARID value of a read transaction is the same as the AWID value of a write transaction" (§A5.3.4). The AXI4 ordering model says why: "because the read and write address channels are independent", a master that needs an order between a read and a write "must wait to receive a response to the first transaction before issuing the second", and "if a master issues a transaction in one direction before it has received a response to an earlier transaction in the opposite direction then there are no ordering guarantees between the two transactions" (§A6.1).

**Memory types, briefly.** Every AW and AR request also carries an AxCACHE value (AWCACHE or ARCACHE). It marks the access as **Device** memory (peripherals, such as control registers) or **Normal** memory (RAM), and it says whether a write is **Bufferable**, which lets a buffer on the way (such as a write buffer in the interconnect) give the write response before the write reaches its destination (Table A4-3). *Device and Normal memory* below shows what the type changes, and [B-AXI-4](/curriculum/T3_Advanced/B-AXI-4_AXI_Expert_Features_Cache_Atomics/index) decodes AxCACHE bit by bit. For Rule 4 the type changes nothing: with Device or Normal memory alike, a read and a write are ordered only if the second is issued after the first has received its response (§A4.3.2 Note, §A6.1).

**What the slave must guarantee.** Rule 4 puts the burden of *creating* an order on the master. The slave has the matching obligation of *keeping* it: "any write transaction for which it has issued a response must be observed by any subsequent write or read transaction, regardless of the transaction IDs", and the same for reads it has answered (§A6.4). The AXI4 write-response rule says it plainly: "by issuing a write response, the slave takes responsibility for hazard checking the write transaction against all subsequent transactions" (§A3.3.1 Note).

**The scoreboard's read-after-write policy.** No pin-level assertion can check this, because it needs addresses, data and the order of events across channels. The scoreboard can. It needs one more term first. The **single-copy atomicity size** is "the minimum number of bytes that a transaction updates atomically" (§A7.1): no master may ever see half of such a block updated. A transaction larger than that size updates memory in blocks of at least that size, so another master can catch it half done, some blocks new and some old (§A7.1). [B-AXI-4](/curriculum/T3_Advanced/B-AXI-4_AXI_Expert_Features_Cache_Atomics/index) covers atomicity with exclusive accesses.

The policy has three cases for a read that overlaps a write's addresses:

| The read's AR handshake happened… | A legal read returns… | Source |
|---|---|---|
| after the write's B | this write's data, or the data of a later write to the same address that the slave has already observed (for example, another master's) | §A6.4 |
| before the write's B (the write is in flight) | old data, new data or, for a write larger than the single-copy atomicity size, a mix of the two in blocks of at least that size | §A5.3.4, §A6.1, §A7.1 |
| (no overlapping address) | unaffected: the two are independent | §A5.3.4 |

**Pitfall: "a B response means the write is visible everywhere".** A response from an intermediate component, such as a write buffer in the interconnect, "cannot guarantee ordering with respect to components that are downstream of the intermediate buffer" (§A6.1 Note). That component must itself make the write visible to later accesses to the same address (§A6.5). For a peripheral whose side effects matter, the master needs a response from the final destination; [B-AXI-4](/curriculum/T3_Advanced/B-AXI-4_AXI_Expert_Features_Cache_Atomics/index) shows how AxCACHE requests one.

### Device and Normal memory: what "in order" means at the slave

So far "in order" meant the order of **responses at the master**. The AXI4 ordering model also constrains the order in which same-ID transactions **arrive at the slave**, and that depends on the memory type in AxCACHE ([B-AXI-4](/curriculum/T3_Advanced/B-AXI-4_AXI_Expert_Features_Cache_Atomics/index) decodes AxCACHE):
- **Device memory** is AxCACHE = 0b0000 or 0b0001 (Table A4-5). Its transactions are Non-modifiable (AxCACHE[1] = 0): the interconnect may not split or merge them, with a few exceptions listed in §A4.3.1, and reads may not be prefetched (§A4.4.1). Peripherals use it.
- **Normal memory** is every other legal AxCACHE value (§A6.2 states it as AxCACHE[3:1] not 0b000). Memories use it.
- **Bufferable** is the AxCACHE[0] bit. For a Device write (AWCACHE[3:2] = 0b00) with this bit set, "the write response can be given from an intermediate point, but the write transaction is required to be made visible at the final destination in a timely manner" (Table A4-3, the AXI4 AWCACHE encoding; §A4.4.1, Device Bufferable). The AXI3 wording in §A4.2 says the same thing more loosely: any component may delay the transaction on its way. The pitfall in Rule 4 says what such an early response still guarantees.

For a master that issues several transactions **in the same direction with the same ID**, §A6.2 guarantees:

| Guarantee | Device memory | Normal memory, same or overlapping addresses | Normal memory, different addresses |
|---|---|---|---|
| Responses at the master in issue order | yes | yes | yes |
| Arrival at the slave in issue order | yes, to one slave, whatever the addresses | yes | no |
| Order guaranteed between a read and a write with that ID | only if the later one was issued after the earlier one's response | as for Device | as for Device |

Two addresses **overlap** when both transactions "access at least one byte in the same single-copy atomic address range" (§A6.2). For Device memory, A4.3.2 adds that the order holds for Non-modifiable transactions with one ID to one slave "irrespective of the address", and that when the boundary between slaves is unknown, the order must be kept for all such transactions "on the same path".

Two contrasting uses:
- **A peripheral command sequence** (write the address register, write the length register, write "go") uses one AWID and Device AxCACHE, so the three writes reach the peripheral in order without waiting for each B.
- **DRAM streaming** uses many IDs and Normal AxCACHE to non-overlapping addresses, so the memory controller may reorder freely for throughput.

### The interconnect: ID extension, routing and same-ID order across slaves

With several masters, two of them may use the same ID value. The interconnect makes them distinct: it "appends additional bits to the ARID, AWID and WID identifiers that are unique to that master port", so "the ID identifier at a slave interface is wider than the ID identifier at a master interface" (§A5.3.5). On the way back, it uses those extra bits of RID or BID "to determine which master port" the response is for, and removes them before passing the response on (§A5.3.5). Which bit positions the extra bits take is the interconnect's choice; this lesson puts them above the master's bits.

**A note on write order.** A B response carries only BID and BRESP (§A3.4.4). If two writes with one AWID both answer OKAY, a swap of their B responses is invisible at the pins: popping "the oldest write with this BID" accounts for responses but cannot detect the swap. Two checks cover what matters. Make the responses distinguishable, for example by aiming one write at an address that answers SLVERR, so that a swapped B shows the wrong BRESP. And check the effect end to end: two same-ID writes to overlapping addresses arrive and are observed in issue order (§A6.2, §A6.4), so a read issued after the last B must return the later write's data.

A pin-level checker for the first row looks like this:

```systemverilog
// snippet: inside module axi_order_checker, bound to one AXI interface. ID_W is the
// ID width at that interface, including any bits the interconnect added.
int unsigned rd_out [2**ID_W];  // per ID: AR handshakes minus RLAST handshakes
int unsigned wr_out [2**ID_W];  // per ID: AW handshakes minus B handshakes

always_ff @(posedge ACLK or negedge ARESETn) begin
  if (!ARESETn) begin
    foreach (rd_out[i]) rd_out[i] <= 0;
    foreach (wr_out[i]) wr_out[i] <= 0;
  end else begin
    // One net update per ID, so an AR and an RLAST for one ID on one edge cancel out.
    // A response for an ID whose count is 0 is the error flagged below; it must not
    // decrement, or the unsigned count would wrap and hide later errors for that ID.
    foreach (rd_out[i])
      rd_out[i] <= rd_out[i] + ((ARVALID && ARREADY && ARID == i) ? 1 : 0)
                             - ((RVALID && RREADY && RLAST && RID == i
                                 && rd_out[i] != 0) ? 1 : 0);
    foreach (wr_out[i])
      wr_out[i] <= wr_out[i] + ((AWVALID && AWREADY && AWID == i) ? 1 : 0)
                             - ((BVALID && BREADY && BID == i
                                 && wr_out[i] != 0) ? 1 : 0);
  end
end

// [Protocol A5.3.1] RID must match an outstanding ARID. RVALID can rise only after
// the AR handshake (A3.3.1), so the counter is already updated when it is sampled.
a_rid_known: assert property (@(posedge ACLK) disable iff (!ARESETn)
  RVALID |-> rd_out[RID] != 0);

// [Protocol A3.3.1, A6.4] BID must match an outstanding AWID. In AXI4, BVALID
// follows the AW handshake, so the counter is already updated.
a_bid_known: assert property (@(posedge ACLK) disable iff (!ARESETn)
  BVALID |-> wr_out[BID] != 0);
```

`|->` is overlapping implication (IEEE 1800-2023 §16.12.7): when the left side holds at an edge, the right side must hold at the same edge. `disable iff` turns the checks off during reset. The `!= 0` guard on each decrement matters because the counters are `int unsigned`: the whole update expression is then unsigned (§11.8.1), and 0 − 1 would wrap to 32'hFFFF_FFFF (§11.4.3). After such a wrap, stray responses for that ID would pass silently, and the next legal response after an AR would fail.

### Recap

| Rule | Scope | Guarantee | Source |
|---|---|---|---|
| Same ID, same direction | one master, one ID, reads or writes | responses in issue order; same-ID read beats never mix | §A5.3, §A5.3.1 |
| Different IDs | one master, across IDs | any order; read data may interleave | §A5.3, §A5.3.1 |
| AXI4 write data | all writes, all IDs, all masters | consecutive beats in AW order; no WID; W may lead AW in time | §A5.4, §A5.3.2, §A3.3 |
| Read and write | same ID or not | no order unless the later one is issued after the earlier one's response | §A5.3.4, §A6.1 |
| After a response | any ID | later reads and writes observe the answered write | §A6.4 |
| Device memory | same ID, one direction, one slave | also arrives at the slave in issue order | §A6.2, §A4.3.2 |
| Interconnect | across masters | appends master bits, routes by them, strips them; keeps same-ID order across slaves | §A5.3.5, §A5.3.1, §A6.3 |

## Make It Work

### A per-ID expected-queue model in plain SystemVerilog

This is the core of every AXI read-ordering checker, without UVM, so you can see every decision. It keeps one queue of outstanding reads per ARID, in issue order. Each R beat is checked against the **oldest** read with the same ID, because same-ID beats never mix (Rule 1) and other IDs may interleave freely (Rule 2). To keep the expected data simple, the model assumes every memory word holds its own address, so beat k of a read of 4-byte beats at address A must return A + 4k.

The code uses an associative array of queues (IEEE 1800-2023 §7.8, §7.10): `exp_q[id]` is the queue of reads for one ID, and `exp_q[id][0]` is the oldest. It creates each ID's entries explicitly before reading them, because reading a nonexistent associative-array entry issues a warning (§7.8.6).

```systemverilog
// compile
// Per-ID expected-queue model for AXI read ordering (plain SystemVerilog, no UVM).
// Expected data: every memory word holds its own address, so beat k of an INCR read
// of 4-byte beats at address A returns A + 4*k.
module tb_top;

  typedef struct {
    int unsigned addr;  // ARADDR
    int unsigned len;   // ARLEN: the read returns len + 1 beats
  } rd_t;

  class axi_order_model;
    rd_t         exp_q [int][$];  // per ARID: outstanding reads, oldest first
    int unsigned beat  [int];     // per RID: beats received for the oldest read
    bit          bad   [int];     // per RID: the oldest read already failed a check
    int unsigned pass_cnt, fail_cnt;

    // On each AR handshake. Same-ARID reads must return in this order (A5.3.1).
    function void on_ar(int id, int unsigned addr, int unsigned len);
      rd_t r;
      r.addr = addr;
      r.len  = len;
      if (!exp_q.exists(id)) begin  // create the per-ID state before reading it
        exp_q[id] = {};
        beat[id]  = 0;
        bad[id]   = 0;
      end
      exp_q[id].push_back(r);
    endfunction

    // On each R handshake. Other RIDs may interleave, so all state is per RID,
    // and a beat always belongs to the oldest outstanding read with its ID.
    function void on_r(int id, int unsigned data, bit last);
      rd_t         exp;
      int unsigned want;
      if (!exp_q.exists(id) || exp_q[id].size() == 0) begin
        $display("FAIL: RID=%0d has no outstanding read", id);
        fail_cnt++;
        return;
      end
      exp  = exp_q[id][0];
      want = exp.addr + 4 * beat[id];
      if (data != want) begin
        $display("FAIL: RID=%0d beat %0d: got 0x%0h, expected 0x%0h",
                 id, beat[id], data, want);
        fail_cnt++;
        bad[id] = 1;
      end
      beat[id]++;
      if (!last) return;
      if (beat[id] != exp.len + 1) begin  // RLAST must mark beat ARLEN + 1 (A3.4.1)
        $display("FAIL: RID=%0d RLAST on beat %0d of %0d", id, beat[id], exp.len + 1);
        fail_cnt++;
        bad[id] = 1;
      end
      if (!bad[id]) begin
        $display("PASS: RID=%0d read @0x%0h complete, beats=%0d",
                 id, exp.addr, beat[id]);
        pass_cnt++;
      end
      void'(exp_q[id].pop_front());  // the oldest read with this ID is finished
      beat[id] = 0;
      bad[id]  = 0;
    endfunction

    // At end of test, every outstanding read must have completed.
    function void report(string name);
      foreach (exp_q[id])
        if (exp_q[id].size() != 0) begin
          $display("FAIL: %0d read(s) with ARID=%0d never completed",
                   exp_q[id].size(), id);
          fail_cnt++;
        end
      $display("%s: PASS=%0d FAIL=%0d", name, pass_cnt, fail_cnt);
    endfunction
  endclass

  axi_order_model m;

  initial begin
    // Trace 1, legal: A (ARID 1, 2 beats), B (ARID 2, 2 beats), C (ARID 1, 1 beat).
    // B overtakes and interleaves with A (different IDs); C waits for A (same ID).
    m = new();
    m.on_ar(1, 'h100, 1);
    m.on_ar(2, 'h200, 1);
    m.on_ar(1, 'h300, 0);
    m.on_r(2, 'h200, 0);
    m.on_r(1, 'h100, 0);
    m.on_r(2, 'h204, 1);
    m.on_r(1, 'h104, 1);
    m.on_r(1, 'h300, 1);
    m.report("trace 1");

    // Trace 2, buggy DUT: C overtakes A with the same ID, a stray RID 4,
    // an early RLAST on ID 2, and an ID 5 read that never returns.
    m = new();
    m.on_ar(1, 'h100, 0);   // A
    m.on_ar(1, 'h300, 0);   // C
    m.on_ar(2, 'h400, 1);   // D, 2 beats
    m.on_ar(5, 'h500, 0);   // E
    m.on_r(1, 'h300, 1);    // C's data first: illegal for one ARID
    m.on_r(1, 'h100, 1);
    m.on_r(4, 'h0, 1);      // nobody issued ARID 4
    m.on_r(2, 'h400, 1);    // RLAST on the first of two beats
    m.report("trace 2");
    $finish;
  end
endmodule
```

### How to build ordering checks for your own DUT

1. Keep one queue of expected transactions per ID, per direction, filled in issue order from the AR (or AW) handshakes.
2. Collect R beats per RID. Compare each beat with the oldest read of that ID; never with "the next read overall".
3. On RLAST, check the beat count against ARLEN + 1, then pop that oldest entry.
4. Flag any RID or BID with no outstanding request, and report every request still outstanding at end of test.
5. Pair W bursts with AW handshakes in order, allowing W to arrive first.
6. Apply the read-after-write policy from Rule 4 with the AR and B times, and check same-ID write order end to end.
7. Cover what matters: the maximum outstanding depth, same-ID reuse, cross-ID overtaking and interleaving, and reads that overlap an in-flight write.

A coverage model for step 7, sampled by the model each time a read completes, with the values passed in as arguments (IEEE 1800-2023 §19.8.1):

```systemverilog
// snippet: declared in the model class; construct it in new() with rd_order_cg = new();
covergroup rd_order_cg with function sample(int unsigned depth, bit overtook,
                                            bit interleaved, bit id_reused);
  cp_depth: coverpoint depth {          // reads outstanding when this one completed
    bins one  = {1};
    bins few  = {[2:4]};
    bins many = {[5:$]};                // set the top bin to the DUT's maximum depth
  }
  cp_overtook:    coverpoint overtook;     // an older read with another ID still waited
  cp_interleaved: coverpoint interleaved;  // another RID's beat fell inside this burst
  cp_id_reused:   coverpoint id_reused;    // two or more reads with this ID outstanding
  x_depth_order:  cross cp_depth, cp_overtook;
endgroup
```

The kata model does not compute these arguments yet. At the RLAST of a read with ID `id`, before the pop, it can derive them like this:
- `depth`: the sum of `exp_q[k].size()` over every ID `k`.
- `overtook`: add an issue number `seq` to `rd_t`, set from a counter in `on_ar`. The read overtook another if some other ID's oldest read has a smaller `seq`.
- `interleaved`: count every R beat in one counter for the whole channel, and record its value at each read's first beat. The burst was interleaved if more beats passed on R since that point than the read itself has.
- `id_reused`: `exp_q[id].size() > 1`, that is, a younger read with the same ID was issued before this one completed.

Covergroups, coverpoints, bins and crosses are taught in [I-SV-3A](/curriculum/T2_Intermediate/I-SV-3A_Functional_Coverage_Fundamentals/index).

### Debugging ordering failures

| Symptom in the log | Likely cause | How to confirm and fix |
|---|---|---|
| `RID=3 has no outstanding read` | The DUT or interconnect returned an ID it never received (a bug in appending or stripping ID bits); the monitor missed the AR (wrong sampling edge); or the monitor uses the master's ID width at the slave port | Compare with the AR log at the same interface; check the ID width at each port |
| `RID=3 beat 0: got 0xB00, expected 0xA00` with two ARID 3 reads outstanding | The DUT returned the second same-ID read first: a same-ID ordering bug (§A5.3.1) | Confirm with the AR and R handshake times; it is a DUT bug, not a checker to relax |
| `RLAST on beat 1 of 2` | Early RLAST, a dropped beat, or two same-ID reads of different lengths returned in the wrong order | Check RLAST against ARLEN per ID; early termination is not allowed (§A3.4.1) |
| End of test: reads with ID 4 never completed | A hung slave, RREADY held low, or an interconnect still holding a younger read's data behind an older same-ID read to another slave | Print the outstanding table at end of test; check the READY signals |
| The scoreboard flags legal cross-ID reordering | One queue for all IDs | Use one queue per ID (A-UVM-6) |
| A data mismatch on the first of two same-ID reads, then `has no outstanding read` for the second | One slot per ID (such as `pending[id]`): the second request overwrote the first | Keep a queue per ID in issue order, as `exp_q[id][$]` does (§A5.3.1) |
| The monitor reports W data with no write address, or checks a write's data against the wrong address | The monitor assumes AW comes before W, or pairs each W burst with the AW nearest in time | Queue complete W bursts and pair them with AW handshakes in order, first with first (§A3.3, §A5.4) |
| A read returns old data after a write to the same address | Legal if the AR was issued before the write's B (§A5.3.4); a DUT bug if it was issued after it (§A6.4) | Compare the AR handshake time with the B handshake time |

**Checklist before moving on:**
- [ ] I can say which orders are legal for any pair of transactions, given their IDs and directions.
- [ ] My model collects beats per RID and compares them with the oldest read of that ID.
- [ ] It checks RLAST against ARLEN + 1 and flags unknown IDs and reads that never complete.
- [ ] My monitor pairs W bursts with AW handshakes in order, even when W arrives first (as `pair()` does in the kata solution under *Practice & Reinforce*).
- [ ] I know when a read must see a write, and my scoreboard policy says so explicitly.

The full UVM monitor and scoreboard built around this model are in [B-AXI-6](/curriculum/T3_Advanced/B-AXI-6_AXI_Verification_Performance/index).

## Push Further

### Expert: the full AXI4 ordering model (IHI0022E Chapter A6)

Chapter A6 defines the AXI4 ordering model in six sections. Its principles, for transactions with the same ID **in the same direction** (§A6.1, §A6.2): transactions to one peripheral arrive in issue order regardless of address, memory transactions to the same or overlapping addresses arrive in issue order, and responses come back in issue order. Across directions there is an order only if the master waited for the response (§A6.1), even to a peripheral (§A4.3.2 Note).

The parts that trip up experienced engineers:
- **The IDs include the interconnect's bits.** "The AXI IDs used for the ordering model include the infrastructure IDs", so "the ordering model applies independently to each master" (§A6.1 Note).
- **Responses from intermediate components.** A component that responds early (a write buffer, for example) must keep the ordering guarantees until the transaction reaches its destination (§A6.3), and must make the transaction visible to any later access to the same or an overlapping address (§A6.5).
- **Device is a superset of Normal.** "The ordering guarantees for access to Device memory are a superset of the guarantees for accesses to Normal memory", so marking a transaction Device never removes a guarantee (§A6.5).
- **Table A6-1 needs a gloss.** Its rows for *different* IDs and overlapping addresses say "ordering required". Read with §A6.4 and §A6.5, this expresses the observation obligation (a transaction that has been answered is observed by later ones, whatever the ID) and the rule that Device accesses to overlapping addresses behave like Normal ones "regardless of the ID values". It does not order *responses* across IDs, which §A5.3 leaves free. This gloss is our reading of the text, not a sentence of the specification. The same reading applies to A4.4.1, which says for every memory type that same-ID reads and writes (to the same slave for Device, to overlapping addresses for Normal) "must remain ordered": per §A6.1 and the A4.3.2 Note, an order between directions exists only once the master has waited for a response.
- **Ordered write observation.** An interface may declare the property Ordered_Write_Observation: two same-ID writes are then "observed by all other agents in the system in the same order that the transactions are issued". Without it, a producer that writes data to one peripheral and a flag to another must wait for the first write's BRESP before issuing the second (§A6.6).

*Expert: interview angles* below has an attempt-first question on this model.

### Expert: sizing outstanding depth and ID width

**A sizing estimate (a queueing model, not a rule of the specification).** Let L be the cycles from a read's AR handshake to its first R beat, and B the beats per burst, with one beat per cycle. Each read then occupies an outstanding slot for about L + B cycles, and to keep R busy the master must start one burst every B cycles. By Little's law (slots in use = arrival rate × time in system), it needs N ≥ (L + B) / B outstanding reads. For L = 100 and B = 16, N ≥ 7.25, so 8. If L is measured to the *last* beat instead, the estimate becomes N ≥ L / B; say which you mean.

**What the specification fixes.** Nothing about depth; only that the slave's read data reordering depth is static, set by its designer, and invisible to masters (§A5.3.1). So system integrators read it from the slave's documentation, and verification must cover the DUT's real maximum.

**ID width growth.** Recommended widths are up to 4 bits at a master, up to 4 more for master-port numbers, and 8 at a slave (§A5.3.6). Each level of cascaded interconnect appends its own bits, so a slave behind two levels sees the master's ID plus both sets of port bits. A slave whose ID ports are too narrow for that design is an integration bug that shows up as responses routed to the wrong master. A verification environment checks the ID width at each port against the topology.

### Expert: how interconnects keep same-ID order across slaves

IHI0022E requires the result (§A5.3.1, §A6.3), not the mechanism. Real interconnects use one of these strategies (implementation choices: **tool-dependent**, in the sense of interconnect IP, and documented by each vendor):
- **Single-slave rule (stall):** while an ID has transactions outstanding to one slave, a new transaction with that ID to another slave waits. It is cheap, but one slow slave blocks every later same-ID access (head-of-line blocking).
- **Reorder buffer:** forward everything and hold early responses until older same-ID ones have gone back. It is fast, but costs storage proportional to depth × burst length.
- **ID remapping:** an interconnect may rewrite IDs, for example to compress a wide ID space, but only if "the ordering requirements of the original ID values are maintained" (§A6.3). A remapper that gives two same-ID reads different IDs at the slave must restore their order on the way back.

For write data, the interconnect must forward W in address order (§A5.3.2). Because W carries no ID in AXI4, an interconnect that lets the address order seen at the slaves differ from the order in which it forwards write data can leave one slave waiting for data that is queued behind another slave's data, while that other path is itself blocked: a deadlock. [B-AXI-5](/curriculum/T3_Advanced/B-AXI-5_AXI_Pitfalls_Interconnect_Deadlocks/index) analyses this case.

### Expert: read-after-write checking at scale

Real scoreboards need four refinements of the Rule 4 policy:
- **Expected-value sets.** For a read that overlaps an in-flight write, keep the set of legal values per atomic block (old value, each in-flight write's value) and accept any member. For a read issued after B, the set shrinks to "this write or anything observed later" (§A6.4), which can still include another master's later write.
- **Single-copy atomicity.** A write larger than the single-copy atomicity size, even a single wide beat, may update memory in blocks of at least that size, so a concurrent read may see some blocks new and some old (§A7.1). And "a transaction never has an atomicity guarantee greater than the alignment of its start address" (§A7.1): a burst that is not aligned to the atomicity size has no guarantee at that size. A 64-bit group's burst that starts off an 8-byte boundary, for example, has no 64-bit guarantee.
- **Same-ID writes before a response.** A slave must make a Device write observed by any later Device write with the same ID, "even if a response has not yet been issued", and a Normal write by any later write with the same ID to the same or an overlapping address, even before its response (§A6.4). This is what makes the end-to-end check of same-ID writes work: two same-ID writes to overlapping addresses take effect in issue order, so one read after the *last* B is enough.
- **VIP policy knobs.** Commercial AXI VIP exposes read-after-write policies as configuration switches whose names and defaults differ by vendor: **tool-dependent**. Check what yours accepts before trusting a pass.

### Expert: AXI3 write interleaving, the legacy

AXI3 allowed a slave to accept interleaved write data with different AWIDs, identified by WID (§A5.3.3). The rules a legacy checker must still know:
- The **write data interleaving depth** is the number of addresses for which a slave can accept interleaved data, and no AXI component can discover it (§A5.3.3 Note).
- Data of writes with the same AWID is never interleaved, and the first data item of each transaction arrives in address order (§A5.3.3).
- An interleaving slave "must continuously accept interleaved write data" and never stall to change the order, to avoid deadlock (§A5.3.3).
- To work with AXI4, an AXI3 master that interleaves must be configured to an interleaving depth of 1, and an AXI3 component that needs WID can generate it from AWID (§A5.4.2).

### Debug challenge: legal or illegal?

These transactions are outstanding at one AXI4 slave interface, in issue order: read r1 (ARID 0, address 0x000), read r2 (ARID 1, 0x040), read r3 (ARID 0, 0x080), write w1 (AWID 2, 0x100, data 0x55). All reads are single-beat. Memory is Normal, every word initially holds its own address (as in *Make It Work*) except where written, and no other master is active. Then the log shows, in time order:

1. R with RID 1, data 0x040.
2. R with RID 0, data 0x080.
3. B with BID 2, OKAY.
4. R with RID 3.
5. After line 3, the master issues read r4 (ARID 5, 0x100). No other read with ARID 5 has been issued. R with RID 5 returns 0x100.

For each line, decide legal or illegal and name the rule.

<details>
<summary>Worked answers</summary>

1. **Legal.** r2 (ARID 1) may overtake r1 (ARID 0): different IDs (§A5.3). The data 0x040 is r2's own address, as expected.
2. **Illegal.** r1 and r3 share ARID 0 and r1 was issued first, so the first RID 0 data must be r1's (0x000), not r3's (0x080) (§A5.3.1). The per-ID model compares the beat with the oldest ARID 0 read and prints `FAIL: RID=0 beat 0: got 0x80, expected 0x0`. The check works only because the two addresses hold different data: had both words held the same value, the swap would be invisible at the pins, just like a swap of two same-ID OKAY responses.
3. **Legal.** The only outstanding write has AWID 2, so BID 2 completes it.
4. **Illegal.** No read with ARID 3 is outstanding: the slave must reflect the ARID it received (§A5.1, §A5.3.1). `a_rid_known` fires.
5. **Illegal, if r4 really was issued after B.** Nothing else with ARID 5 is outstanding, so this beat is r4's. The slave answered w1 before r4 was issued, so r4 must observe 0x55 (§A6.4); 0x100 is the stale value. Before calling it a DUT bug, confirm in the waveform that the AR handshake came after the B handshake; if it came before, 0x100 would be legal (§A5.3.4).

*Why r4 uses a fresh ID.* Had r4 used ARID 0, the line-5 beat would prove nothing about r4. After line 2 an older ARID 0 read is still outstanding, and by Rule 1 the next RID 0 beat belongs to that older read, not to r4. Judge a read-after-write result only once you know which read the beat belongs to.

</details>

### Kata extensions

Extend the Make It Work model, then write a trace that proves each extension works. Try each one before you open its solution.
- **W/AW pairing.** Add `on_aw(id, addr)` and `on_w(data)`. Queue whichever arrives first, and pair W data with AW handshakes first with first (Rule 3).
- **Writes.** Keep one queue per AWID of paired writes, add `on_b(id)`, flag unknown BIDs, and keep a shadow memory updated at each B.
- **Read-after-write policy.** On `on_ar`, record the value the read must see and which writes still had no B. On the read's data, accept the old value or the data of a write that had no B yet when the read was issued, and only the shadow value otherwise (the policy table in Rule 4).
- **Missing RLAST.** Flag beat ARLEN + 1 when it arrives without RLAST.

<details>
<summary>Worked solution: W/AW pairing, writes and the read-after-write policy</summary>

To keep the policy visible, this solution is a separate model for single-beat reads and writes. Merging it into the multi-beat read model is mechanical: give each beat its own address and apply the same check per beat.

```systemverilog
// compile
// Kata solution: W/AW pairing, writes and the read-after-write policy (plain SV).
// Simplified: single-beat reads and writes of one 4-byte word, each inside one
// single-copy atomic block (A7.1), so a read sees a word all old or all new.
// One master, and no two writes to one address in flight at once.
module tb_top;

  typedef struct {
    int          id;    // AWID
    int unsigned addr;
  } aw_t;

  typedef struct {
    int unsigned addr;
    int unsigned data;
    int unsigned b;     // 0 until its B arrives, then the B count at that moment
  } wr_t;

  typedef struct {
    int unsigned addr;
    int unsigned old;   // the value the read must see if no write is in flight
    int unsigned b_at;  // B responses seen when the read was issued
  } rd_t;

  class axi_raw_model;
    aw_t         aw_q [$];           // AW handshakes still waiting for their W data
    int unsigned w_q  [$];           // W data still waiting for its AW (A3.3)
    wr_t         wlog [$];           // every paired write, in AW order
    int          wr_q [int][$];      // per AWID: wlog indices waiting for B, oldest first
    rd_t         rd_q [int][$];      // per ARID: reads waiting for R, oldest first
    int unsigned mem  [int unsigned];  // shadow memory, updated at each B (A6.4)
    int unsigned b_cnt, pass_cnt, fail_cnt;

    // A word that no answered write has changed still holds its own address.
    function int unsigned mem_rd(int unsigned addr);
      return mem.exists(addr) ? mem[addr] : addr;
    endfunction

    // W data pairs with AW handshakes first with first, whichever came first (A5.4).
    function void pair();
      aw_t a;
      wr_t w;
      while (aw_q.size() != 0 && w_q.size() != 0) begin
        a      = aw_q.pop_front();
        w.addr = a.addr;
        w.data = w_q.pop_front();
        w.b    = 0;
        wlog.push_back(w);
        if (!wr_q.exists(a.id)) wr_q[a.id] = {};
        wr_q[a.id].push_back(wlog.size() - 1);
      end
    endfunction

    function void on_aw(int id, int unsigned addr);
      aw_t a;
      a.id   = id;
      a.addr = addr;
      aw_q.push_back(a);
      pair();
    endfunction

    function void on_w(int unsigned data);  // single beat, so WLAST is always 1
      w_q.push_back(data);
      pair();
    endfunction

    // Same-AWID writes complete in AW order (A5.3). From its B on, every later read
    // must observe the write (A6.4), so the shadow memory changes here, not at W.
    function void on_b(int id);
      int i;
      if (!wr_q.exists(id) || wr_q[id].size() == 0) begin
        $display("FAIL: BID=%0d has no outstanding write", id);
        fail_cnt++;
        return;
      end
      i = wr_q[id].pop_front();
      b_cnt++;
      wlog[i].b = b_cnt;
      mem[wlog[i].addr] = wlog[i].data;
    endfunction

    // Record, at the AR handshake, what the read may legally return.
    function void on_ar(int id, int unsigned addr);
      rd_t r;
      r.addr = addr;
      r.old  = mem_rd(addr);
      r.b_at = b_cnt;
      if (!rd_q.exists(id)) rd_q[id] = {};
      rd_q[id].push_back(r);
    endfunction

    // Legal data: the value at the AR, or the data of a write to this address that
    // had no B yet when the read was issued, because that write and the read are
    // unordered (A5.3.4, A6.1).
    function void on_r(int id, int unsigned data);
      rd_t r;
      wr_t hits [$];
      if (!rd_q.exists(id) || rd_q[id].size() == 0) begin
        $display("FAIL: RID=%0d has no outstanding read", id);
        fail_cnt++;
        return;
      end
      r    = rd_q[id].pop_front();  // single beat, so RLAST is always 1
      hits = wlog.find(w) with (w.addr == r.addr && w.data == data
                                && (w.b == 0 || w.b > r.b_at));
      if (data == r.old || hits.size() != 0) begin
        $display("PASS: RID=%0d @0x%0h got 0x%0h", id, r.addr, data);
        pass_cnt++;
      end else begin
        $display("FAIL: RID=%0d @0x%0h got 0x%0h, expected 0x%0h",
                 id, r.addr, data, r.old);
        fail_cnt++;
      end
    endfunction

    function void report(string name);
      foreach (rd_q[id])
        if (rd_q[id].size() != 0) begin
          $display("FAIL: %0d read(s) with ARID=%0d never completed",
                   rd_q[id].size(), id);
          fail_cnt++;
        end
      foreach (wr_q[id])
        if (wr_q[id].size() != 0) begin
          $display("FAIL: %0d write(s) with AWID=%0d never got B",
                   wr_q[id].size(), id);
          fail_cnt++;
        end
      if (aw_q.size() != 0 || w_q.size() != 0) begin
        $display("FAIL: %0d AW and %0d W left unpaired", aw_q.size(), w_q.size());
        fail_cnt++;
      end
      $display("%s: PASS=%0d FAIL=%0d", name, pass_cnt, fail_cnt);
    endfunction
  endclass

  axi_raw_model m;

  initial begin
    m = new();
    m.on_w('h42);       // write X's data arrives before its AW: legal (A3.3)
    m.on_aw(1, 'h100);  // X's AW pairs with the queued data; X is now in flight
    m.on_ar(1, 'h100);  // R1 is issued while X has no B
    m.on_r(1, 'h100);   // R1 returns the old value: legal (A5.3.4)
    m.on_b(1);          // X completes: the shadow memory now holds 0x42
    m.on_ar(2, 'h100);  // R2 is issued after X's B
    m.on_r(2, 'h100);   // R2 returns the old value: a DUT bug (A6.4)
    m.on_aw(3, 'h200);  // write Y: AW first this time
    m.on_w('h77);       // Y's data pairs with the queued AW
    m.on_ar(4, 'h200);  // R3 is issued while Y has no B
    m.on_r(4, 'h77);    // R3 already sees Y's data: also legal (A6.1)
    m.on_b(3);          // Y completes
    m.on_b(6);          // nobody issued AWID 6
    m.report("raw trace");
    $finish;
  end
endmodule
```

Expected output (illustrative: traced by hand from the code, not from a simulator run):

```text
PASS: RID=1 @0x100 got 0x100
FAIL: RID=2 @0x100 got 0x100, expected 0x42
PASS: RID=4 @0x200 got 0x77
FAIL: BID=6 has no outstanding write
raw trace: PASS=2 FAIL=2
```

How it maps to the policy table in Rule 4:
- R1 and R3 were issued before their write's B, so both the old value (R1) and the new value (R3) pass: the read and the write are unordered.
- R2 was issued after X's B, so only the shadow value 0x42 passes. The FAIL line names that value.
- `pair()` handles both timings of Rule 3: X's W came before its AW, and Y's AW before its W.
- The stray BID 6 is caught by the per-AWID queues, as the stray RID is in the read model.

A real scoreboard also needs the parts this solution leaves out: several masters (a later write by another master is also legal after B), multi-beat bursts, WSTRB, and pruning `wlog`.

</details>

<details>
<summary>Worked solution: missing RLAST</summary>

```systemverilog
// snippet: in on_r of the Make It Work model, right after beat[id]++;
if (!last && beat[id] == exp.len + 1) begin  // the final beat must carry RLAST (A3.2.2)
  $display("FAIL: RID=%0d beat %0d of %0d has no RLAST", id, beat[id], exp.len + 1);
  fail_cnt++;
  void'(exp_q[id].pop_front());  // end this read, so the next beat goes to the next one
  beat[id] = 0;
  bad[id]  = 0;
  return;
end
```

Without this check, a missing RLAST surfaces late: as a data mismatch on an extra beat, as a wrong beat count at the next RLAST, or only at end of test as a read that never completed. All three point away from the real cause.

</details>
