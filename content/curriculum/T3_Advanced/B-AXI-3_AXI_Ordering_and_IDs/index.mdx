# AXI Transaction Ordering & IDs

AXI's five-channel architecture decouples requests from responses.
This creates a powerful but complex ordering model: multiple transactions can be **outstanding** simultaneously, and responses can arrive **out of order**.

The **transaction ID** (`AxID`) is the mechanism that ties requests to responses and defines ordering guarantees.
Getting ID ordering wrong causes **data corruption** that is nearly impossible to debug from waveforms alone.

<QuickTake>
- **Outstanding transactions:** A master can issue multiple requests before any response arrives.
- **Transaction IDs:** `AWID`/`ARID` tag each request; `BID`/`RID` tag each response.
- **Same-ID ordering:** Responses with the **same ID** must arrive in the **same order** as the requests.
- **Different-ID freedom:** Responses with **different IDs** may arrive in **any order**.
- **Interleaving:** read data beats of different IDs may be interleaved; AXI4 write data is never interleaved.
- **Reads vs writes:** there is no ordering between reads and writes, even with the same ID.
</QuickTake>

---

## 1. Outstanding Transactions

In AHB, the next address overlaps the current data phase, but only one transfer is in its data phase at a time and transfers complete in order.
In AXI, a master can issue **multiple requests** on the address channel without waiting for responses.

```
Time →
AW:  [Req A]  [Req B]  [Req C]
B:                              [Resp A]  [Resp C]  [Resp B]
```

The number of outstanding transactions a master can issue is a design parameter, typically 2–16.
A slave that cannot buffer multiple requests applies backpressure on the address channel (`AxREADY = 0`).

### Why Outstanding Transactions Matter

Without outstanding transactions, every memory access would have a latency equal to the full round-trip time.
With 4 outstanding reads, a master can issue 4 read addresses back-to-back, effectively hiding the latency of the first 3 reads while the fourth is being processed.

> [!NOTE]
> The maximum number of outstanding transactions is not specified by the protocol — it's a design parameter of each master and slave.
> A verification environment must test at the maximum outstanding depth to find ordering bugs.

---

## 2. Transaction IDs

Every AXI address-channel transfer carries an ID:
- **AWID / ARID:** Tags the request
- **BID / RID:** Tags the response, matching it back to the request

IDs serve two purposes:
1. **Response routing:** The interconnect uses IDs to route responses back to the correct master.
2. **Ordering domains:** Same-ID transactions have ordering guarantees; different-ID transactions don't.

### ID Width

The ID width is a system-level parameter:
- Masters typically use 4–8 bit IDs
- The interconnect adds master-port bits, widening the ID at the slave port (IHI0022E A5.3.5 says it "appends" them; which bit positions they take is up to the interconnect)
- A slave sees wider IDs than the master originally issued

```
Master 0 issues ARID = 4'b0010
Master 1 issues ARID = 4'b0010

Interconnect adds a master-port bit (shown here above the master's bits):
  Slave sees ARID = 5'b0_0010 (from Master 0)
  Slave sees ARID = 5'b1_0010 (from Master 1)
```

## 3. Same-ID Ordering Rules

The AXI specification guarantees:

> **Transactions with the same ID from the same master must be completed in order.**

This means:
- If a master issues Read A (ID=3) then Read B (ID=3), the slave must return all of Read A's data before any of Read B's data. Their beats cannot be mixed.
- If a master issues Write A (ID=5) then Write B (ID=5), the slave must acknowledge Write A before Write B.

```
AR channel:  [Read A, ID=3]  [Read B, ID=3]
R channel:   [Data A, RID=3]  [Data B, RID=3]   ✓ LEGAL (in order)
R channel:   [Data B, RID=3]  [Data A, RID=3]   ✗ ILLEGAL (out of order)
```

### Why Same-ID Ordering?

Same-ID ordering gives masters a simple programming model: if you need sequential consistency for a sequence of accesses, use the same ID.
This is useful for:
- **Peripheral streams:** several outstanding reads from a FIFO-mapped register must come back in order.
- **Simple masters:** a master that uses one ID gets an in-order bus for free.

It does **not** order a read after a write, even when `ARID` equals `AWID` (IHI0022E A5.3.4). See section 5.

---

## 4. Different-ID Reordering

Transactions with **different IDs** have **no ordering guarantee**:

```
AR channel:  [Read A, ID=1]  [Read B, ID=2]
R channel:   [Data B, RID=2]  [Data A, RID=1]   ✓ LEGAL
```

This is the mechanism that enables **out-of-order completion**:
- A slave receives reads for IDs 1 and 2
- ID 2 hits the cache; ID 1 misses and goes to DRAM
- The slave returns ID 2's data first because it's ready first

Read data of different IDs may also be **interleaved** beat by beat (A5.3.1): `B0, A0, B1, A1` is legal when A and B have different IDs. A monitor must therefore collect R beats per `RID`, not assume a burst arrives in one piece. AXI4 write data is different: there is no `WID`, so the W beats of each write are consecutive and follow the order of the write addresses, whatever the AWIDs (A5.4).

### Performance Implications

Out-of-order completion dramatically improves throughput:
- Without reordering: every slow transaction blocks fast ones behind it
- With reordering: fast transactions complete immediately, slow ones don't block the pipeline

> [!IMPORTANT]
> **Masters that need strict ordering across different access streams must use the same ID.**
> Masters that want maximum throughput should use different IDs for independent access streams.

## 5. Read/Write Ordering

AXI has **no ordering guarantee between reads and writes**, even with the same ID, unless additional mechanisms are used.

### The Problem

```
AW channel:  [Write addr=0x100, data=0x42, AWID=1]
AR channel:  [Read  addr=0x100, ARID=1]
```

Even though both use ID=1, the spec does not guarantee the read will see the written value.
The write and read travel on **independent channels** and may arrive at the slave in any order.

### What the Spec Requires

IHI0022E A5.3.4: "AXI has no ordering restrictions between read and write transactions. They can complete in any order, even if the ARID value of a read transaction is the same as the AWID value of a write transaction." A master that needs one to see the other must wait for the earlier one to **complete** before it issues the later one:

- a write is complete when its **write response** (B) arrives; sending all the write data does not count;
- a read is complete when its **last read data beat** arrives.

This is an obligation on the master, so there is nothing to assert at the slave's pins. In a scoreboard, a read that overlaps an outstanding write to the same address may legally return either the old or the new data; decide that policy explicitly instead of flagging it as an error.

## 6. Interconnect ID Management

The AXI interconnect sits between masters and slaves and manages ID routing:

### ID Prepending

The interconnect adds master-port bits to the ID (A5.3.5), so IDs from different masters are unique at the slave port. Where the extra bits go is the interconnect's choice; this example puts them on top:

| Component | ID Width | Example |
|---|---|---|
| Master port | 4 bits | `AWID = 4'b0010` |
| Interconnect adds 2 source bits | 6 bits | `AWID = 6'b01_0010` |
| Slave port | 6 bits | Slave sees `6'b01_0010` |

The slave returns the full ID on the response channel. The interconnect strips the source bits to route the response back to the correct master.

### Interconnect Reordering Rules

The obligation is on the **responses the master receives**. A5.3.1: "The interconnect must ensure that the read data from a sequence of transactions with the same ARID value targeting different slaves is received by the master in the order in which it issued the addresses." Same-AWID write responses must likewise complete in issue order (A5.3).

```
Master 0: [Read A, ARID=1] -> Slave 0
Master 0: [Read B, ARID=1] -> Slave 1
Master 0 must receive all of A's data before B's. The interconnect can
stall B until A completes, or buffer B's data until A's has gone back.

Master 0: [Read A, ARID=1] -> Slave 0
Master 0: [Read B, ARID=2] -> Slave 0
B's data may arrive first, or interleaved with A's (different IDs).
```

For write data, an interconnect that merges writes from several masters into one slave "must ensure that it forwards the write data in address order" (A5.3.2).

## 7. Verification Strategy

### Scoreboard Design for ID-Based Ordering

The scoreboard keeps one queue of expected transactions per ID, collects read beats per `RID` (other IDs may interleave), and pops the **oldest** same-ID entry when a burst completes. A write response carries no address, so for writes the order itself is the check.

```systemverilog
typedef bit [63:0] data_t;

class axi_txn extends uvm_object;
  `uvm_object_utils(axi_txn)
  int unsigned id, len;   // AxID, AxLEN
  bit [31:0]   addr;
  data_t       data[];    // expected read data, filled by the reference model
  function new(string name = "axi_txn"); super.new(name); endfunction
endclass

class axi_order_scoreboard extends uvm_scoreboard;
  `uvm_component_utils(axi_order_scoreboard)

  axi_txn reads_by_id[int][$];   // in AR order, per ID (A5.3.1)
  axi_txn writes_by_id[int][$];  // in AW order, per ID (A5.3)
  data_t  rbeats_by_id[int][$];  // R beats collected until RLAST

  function new(string name, uvm_component parent); super.new(name, parent); endfunction

  function void on_ar(axi_txn t); reads_by_id[t.id].push_back(t);  endfunction
  function void on_aw(axi_txn t); writes_by_id[t.id].push_back(t); endfunction

  function void on_r_beat(int rid, data_t data, bit last);
    axi_txn exp;
    if (!reads_by_id.exists(rid) || reads_by_id[rid].size() == 0) begin
      `uvm_error("ORD", $sformatf("RID=%0d with no outstanding read", rid))
      return;
    end
    rbeats_by_id[rid].push_back(data);
    if (!last) return;
    exp = reads_by_id[rid].pop_front();          // oldest read with this ID
    if (rbeats_by_id[rid].size() != exp.len + 1)
      `uvm_error("ORD", $sformatf("RID=%0d: %0d beats, expected %0d", rid, rbeats_by_id[rid].size(), exp.len + 1))
    foreach (exp.data[i])
      if (i < rbeats_by_id[rid].size() && rbeats_by_id[rid][i] !== exp.data[i])
        `uvm_error("DATA", $sformatf("RID=%0d beat %0d: got %h, expected %h", rid, i, rbeats_by_id[rid][i], exp.data[i]))
    rbeats_by_id[rid].delete();
  endfunction

  function void on_b(int bid);
    if (!writes_by_id.exists(bid) || writes_by_id[bid].size() == 0)
      `uvm_error("ORD", $sformatf("BID=%0d with no outstanding write", bid))
    else
      void'(writes_by_id[bid].pop_front());    // completes the oldest write with this ID
  endfunction

  function void check_phase(uvm_phase phase);
    foreach (reads_by_id[id])
      if (reads_by_id[id].size()) `uvm_error("EOT", $sformatf("%0d reads with ID %0d never completed", reads_by_id[id].size(), id))
    foreach (writes_by_id[id])
      if (writes_by_id[id].size()) `uvm_error("EOT", $sformatf("%0d writes with ID %0d never completed", writes_by_id[id].size(), id))
  endfunction
endclass
```

If the data of a returned read matches the *second* outstanding read with that ID instead of the first, the beat-by-beat compare fails: that is how a same-ID reordering bug shows up.

### Key Assertions

At the pins, a checker can verify that every response ID belongs to an outstanding request. Same-ID order needs the expected data or address, so it lives in the scoreboard above.

```systemverilog
// outstanding_wr[id] / outstanding_rd[id]: AW (AR) handshakes minus B (RLAST)
// handshakes for each ID, maintained by the monitor.
a_bid_known: assert property (@(posedge ACLK) disable iff (!ARESETn)
  BVALID |-> outstanding_wr[BID] > 0);
a_rid_known: assert property (@(posedge ACLK) disable iff (!ARESETn)
  RVALID |-> outstanding_rd[RID] > 0);
```

### Coverage Plan

```systemverilog
covergroup axi_ordering_cg @(posedge ACLK iff BVALID && BREADY);
  // Outstanding depth when response arrives
  cp_outstanding: coverpoint outstanding_count {
    bins one   = {1};
    bins few   = {[2:4]};
    bins many  = {[5:8]};
    bins max   = {[9:$]};
  }

  // Response ordering
  cp_reordered: coverpoint response_was_reordered {
    bins in_order   = {0};
    bins reordered  = {1};
  }

  // Cross: reordering at high outstanding depth
  cx_depth_order: cross cp_outstanding, cp_reordered;
endgroup
```

## Summary

| Rule | Scope | Guarantee |
|---|---|---|
| Same-ID ordering | Per master, per ID | Responses arrive in request order |
| Different-ID freedom | Per master, across IDs | No ordering — may reorder freely |
| Read data interleaving | Different RIDs | Allowed; same-RID data is never mixed |
| Write data (AXI4) | All writes | Consecutive beats, in AW order, no WID |
| Read/Write independence | Same ID, different channels | No guarantee; wait for B (or the last R) first |
| Interconnect routing | Cross-master | IDs widened with source bits; per-ID ordering preserved |
