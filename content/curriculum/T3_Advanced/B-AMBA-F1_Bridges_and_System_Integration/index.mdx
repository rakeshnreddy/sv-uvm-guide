## Quick Take

- **What it is:** An **AHB↔AXI bridge** is a protocol converter: a **slave** on one bus (it answers transfers) and a **master** on the other (it starts transfers). AHB is a pipeline: one address and control bus plus separate write-data (`HWDATA`) and read-data (`HRDATA`) buses, where each transfer's address phase overlaps the previous transfer's data phase. AXI has five independent channels (AW, W, B, AR, R), each with its own VALID/READY handshake. The bridge reshapes every burst to the limits of the bus it sends on, and translates every response back.
- **Why it matters:** Most SoC paths between a CPU or DMA engine and its peripherals cross at least one bridge. Bridge bugs show up as corrupted data, lost errors or hangs, and they look like bugs in the master or the slave, so they are expensive to find late. The rules that decide what a bridge must do are spread over two specifications, and the most common mistake (splitting AHB bursts at 4KB) comes from mixing them up.
- **The Analogy:** A freight broker between a railway and a trucking firm. The railway (AHB) inspects each wagon as it passes while the paperwork for the next wagon is already being read. The trucking firm (AXI) receives the order, the cargo and the signed receipt separately. The broker repacks loads to each carrier's limits (at most 256 transfers per AXI burst; never across 1KB on AHB) and decides when to sign for a delivery: at once (posted) or only when the truck's receipt comes back (non-posted). *Where it breaks:* AHB has separate tracks for outbound and inbound freight (HWDATA and HRDATA), an AXI load can never be cancelled once announced, and the broker can delay a wagon only while unloading it (`HREADYOUT` in the data phase), never at the gate (the address phase).

**You will be able to:**
1. **Derive** whether and where a bridge must split or reshape a burst, and cite the rule that forces it: AHB→AXI for the AXI4 256-transfer limit, width conversion and the unknown length of an AHB INCR, never for 4KB; AXI→AHB at 1KB, and for FIXED, WRAP2, unaligned starts and sparse strobes.
2. **Map** responses and errors in both directions, and **justify** a posted or non-posted write policy by its error visibility, read-after-write ordering and latency.
3. **Plan** the verification of a bridge: protocol checks on both sides, a reference-model scoreboard, error injection, CDC and reset scenarios, and formal properties with the assumptions they need.
4. **Debug** common bridge bugs from a log or a waveform: a split off by one, `AWLEN` wrapping without the 256 cap, write data on the wrong burst or lanes, responses merged wrongly on split bursts, WRAP→INCR conversion, outstanding-queue overflow and channel-dependency deadlock, and the posted-write hazard.

## Build Your Mental Model

### Words you need first

- **Master and slave.** IHI0033B.b and IHI0022E, the issues this lesson cites, say *master* (starts transfers) and *slave* (answers them). Later Arm issues, such as IHI0033C, say *manager* and *subordinate* for the same two roles.
- **Transfer, beat and burst.** A **transfer** (or **beat**) moves one data item. A **burst** is a group of transfers that share one starting address and control set. AHB encodes the burst type in `HBURST`; AXI encodes the number of transfers as `AxLEN + 1` (`AxLEN` means `AWLEN` or `ARLEN`).
- **Address phase and data phase (AHB).** Each AHB transfer has a one-cycle **address phase** and a **data phase** of one or more cycles. The slave stretches the data phase by driving its `HREADYOUT` low; the interconnect returns the selected slave's `HREADYOUT` to everyone as `HREADY`. A transfer is accepted at a rising edge where `HREADY` is high and `HTRANS` is NONSEQ or SEQ (IHI0033B.b §1.3, §3.1).
- **Boundary rules.** An AHB master must not start an incrementing burst that crosses a **1KB** address boundary (IHI0033B.b §3.5). An AXI burst must not cross a **4KB** boundary (IHI0022E A3.4.1).
- **Posted and non-posted write.** A **posted** write is reported complete to the master as soon as the bridge has buffered it. A **non-posted** write is reported complete only when the far side has answered.
- **Reference model and scoreboard.** A **reference model** (or predictor) computes what the design under test (DUT) should do; a **scoreboard** compares that prediction with what the DUT did ([A-UVM-6](/curriculum/T3_Advanced/A-UVM-6_Scoreboards_and_Reference_Models/index)).
- **CDC.** A **clock domain crossing** is any signal that leaves logic clocked by one clock and is sampled by logic on another, unrelated clock.

### Where bridges sit

Real SoCs rarely use one bus. A high-bandwidth AXI fabric connects the CPU, DMA engines and DRAM; slower peripherals sit on AHB-Lite or APB. A bridge joins two of these buses, and it is always a slave on one and a master on the other.

This lesson covers the two AHB↔AXI directions. APB bridges follow the same idea with a simpler target; [B-APB-1](/curriculum/T3_Advanced/B-APB-1_APB_Protocol_and_Verification/index) covers how an APB error travels back through them.

### What differs between AHB and AXI

Every row of this table is a translation the bridge must do, and so a place where it can be wrong.

| Feature | AHB (IHI0033B.b) | AXI (IHI0022E) |
|---|---|---|
| Buses or channels | One address and control bus, plus separate `HWDATA` and `HRDATA` buses, pipelined (§3.1) | Five channels with independent handshakes: AW, W, B, AR, R (A3.2) |
| Flow control | Only the slave's `HREADYOUT`, and only in the data phase; "a slave cannot request that the address phase is extended" (§1.3) | VALID/READY on every channel (A3.2.1) |
| Outstanding transfers | One address phase overlapping one data phase | Many transactions; ordering by ID (A5.3) |
| Burst length known up front | Yes for SINGLE, INCR4/8/16, WRAP4/8/16; **no** for INCR, "incrementing burst of undefined length" (Table 3-3) | Always: `AxLEN + 1` transfers; INCR 1 to 256, all other types 1 to 16 (A3.4.1) |
| Boundary rule | No incrementing burst across 1KB (§3.5) | No burst across 4KB (A3.4.1) |
| Alignment | Every transfer aligned to its size (§3.5) | The first transfer may be unaligned (A3.4.3) |
| Write strobes | None in Issue B.b (Issue C adds an optional `HWSTRB`) | `WSTRB`, one bit per byte lane (A3.4.3) |
| Early termination | A master may cancel the rest of a burst after an ERROR (§3.5.2) | None: "No component can terminate a burst early" (A3.4.1) |
| Read response | `HRESP` per transfer, in its data phase; OKAY during wait states (§5.1.2) | `RRESP` per R beat (A3.4.4) |
| Write response | `HRESP` per transfer, in its data phase | One `BRESP` for the whole burst, after the last W transfer (A3.3.1, A3.4.4) |
| Error | One code, ERROR, always two cycles (§5.1.3) | SLVERR or DECERR (A3.4.4) |

The bridge also maps the control fields. For an AHB-to-AXI bridge:

| AXI field | Comes from (AHB) | Note |
|---|---|---|
| `AxADDR` | `HADDR` of the first transfer of each AXI burst | |
| `AxBURST`, `AxLEN` | `HBURST` and the transfer count | INCR4/8/16 give `AxLEN` 3/7/15; an AHB INCR has no count (see below) |
| `AxSIZE` | `HSIZE` | Smaller when the AXI bus is narrower (downsizing) |
| `AxCACHE[0]` (Bufferable) | `HPROT[2]` (Bufferable) | AHB Table 3-4; AXI A4.3 (Tables A4-3, A4-4) and Table A4-5 |
| `AxCACHE[1]` (Modifiable) | `HPROT[3]` (Modifiable) | Issue A of AHB called this bit Cacheable (§3.7) |
| `AxCACHE[3:2]` | `HPROT[6:4]` only if the AHB5 Extended_Memory_Types property is True | Otherwise a system choice |
| `AxPROT[0]` (Privileged) | `HPROT[1]` | A4.7 Table A4-6 |
| `AxPROT[1]` (Non-secure) | `HNONSEC` (AHB5 Secure_Transfers, §3.9) | Otherwise a system choice |
| `AxPROT[2]` (Instruction) | `!HPROT[0]` | `HPROT[0]` high means a data access |
| AW or AR | `HWRITE` | |

**The other direction.** An AXI-to-AHB bridge applies the same table backwards: `HPROT[0]` = `!AxPROT[2]`, `HPROT[1]` = `AxPROT[0]`, `HPROT[2]` = `AxCACHE[0]` and `HPROT[3]` = `AxCACHE[1]`. What the AHB side has no signal for is lost: `AxPROT[1]` needs the AHB5 `HNONSEC` signal, and the cache attributes in `AxCACHE[3:2]` have an AHB equivalent only with the AHB5 Extended_Memory_Types property (`HPROT[6:4]`, Tables 3-5 and 3-6). Both protocols also keep these fields fixed: `HPROT` must stay constant throughout a burst (§3.7), and no modification may change `AxPROT` (IHI0022E A4.3.1), so every piece of a split carries the same value.

**Pitfall: "AHB is one multiplexed channel."** It is not: AHB has separate write-data and read-data buses (§3.1). What it lacks is per-channel handshakes and outstanding transactions. A bridge model that serializes AHB reads and writes on "one channel" is modelling the wrong bus.

`HREADYOUT` is the bridge's only way to slow the AHB master down, and it works only in a data phase. "A slave cannot request that the address phase is extended" (IHI0033B.b §1.3), so whenever the bridge has no room, it must already be holding `HREADYOUT` low in the current data phase; then the master keeps the next address on the bus until the bridge raises `HREADYOUT` again. While it waits, the bridge drives `HRESP` OKAY (§5.1.2).

### AHB to AXI: what forces a split

**Never 4KB.** "Masters must not attempt to start an incrementing burst that crosses a 1KB address boundary" (IHI0033B.b §3.5). Every 4KB boundary is also a 1KB boundary, so a legal AHB incrementing burst stays inside one 4KB page, and so does any AXI burst made from it. An AHB burst that crosses 1KB is **illegal stimulus**: the bridge may assume it never arrives, and a checker on the AHB side must flag it. This is the per-transfer form of B-AHB-3's 1KB check, so it also covers an INCR of unknown length:

```systemverilog
// snippet: [Protocol IHI0033B.b §3.5] per-transfer form; covers undefined-length INCR
logic [31:0] burst_start;
always_ff @(posedge HCLK) if (HREADY && HTRANS == 2'b10) burst_start <= HADDR; // NONSEQ
a_ahb_no_1kb_cross: assert property (@(posedge HCLK) disable iff (!HRESETn)
  HREADY && HTRANS == 2'b11 && !(HBURST inside {3'b010, 3'b100, 3'b110}) // SEQ, not WRAP
  |-> HADDR[31:10] == burst_start[31:10]);
```

**The 256-transfer limit.** An AXI4 INCR burst carries at most 256 transfers (IHI0022E A3.4.1), because `AxLEN` is 8 bits. A fixed-length AHB burst has at most 16 transfers, and a legal incrementing burst stays inside 1KB, so it carries at most 1024 bytes: that is at most 256 transfers of 4 bytes. So the limit can force a split only when the AXI transfers are 1 or 2 bytes: an undefined-length INCR of bytes or halfwords, or a burst downsized onto a 1- or 2-byte AXI bus. For example, a byte-wide DMA streaming 1024 bytes becomes four AXI bursts of 256.

**The length nobody told the bridge.** `HBURST` = INCR means "incrementing burst of undefined length" (Table 3-3). The master can even pause with BUSY transfers and then end the burst with IDLE or NONSEQ (§3.5.1). So when the first transfer arrives, the bridge does not know what to put in `AWLEN` or `ARLEN`.

**Width conversion and WRAP.** When the AHB transfer is wider than the AXI bus, each AHB transfer becomes several AXI transfers of the bus width, and "when downsizing to a bus width narrower than that required by the transaction size, AxSIZE, the transaction must be modified" (IHI0022E A4.3.1 Note). INCR bursts just get longer. WRAP is harder. Both protocols wrap inside a block of `transfers × size` bytes, and AHB WRAP4/8/16 are legal AXI WRAP lengths, so a same-width bridge maps them one to one. But a WRAP16 of doublewords onto a 32-bit AXI bus would need a 32-transfer AXI WRAP, and AXI WRAP bursts stop at 16 (A3.4.1). The bridge sends the same bytes in the same order as INCR bursts:
- If the WRAP starts at the **wrap boundary** (the lowest address of the 128-byte block, A3.4.1), the bytes are already in increasing order: one AXI INCR of 32 word transfers. A WRAP16 of doublewords at 0x0100 becomes one INCR at 0x0100.
- Otherwise, two INCR bursts: from the start address to the top of the block, then from the wrap boundary up to the start. A WRAP16 of doublewords at 0x0140 becomes INCR16 of words at 0x0140 (bytes 0x0140 to 0x017F), then INCR16 at 0x0100 (bytes 0x0100 to 0x013F).

### AXI to AHB: what forces a split or a reshape

**Split at 1KB.** An AXI burst only has to stay inside 4KB (A3.4.1), so a legal AXI burst can cross a 1KB boundary, and the AHB side forbids that (§3.5). An AXI INCR16 of words at 0x03F0 is legal AXI (it ends at 0x042F), but it crosses 0x0400. The bridge issues an AHB INCR4 from 0x03F0, then the remaining 12 transfers from 0x0400, as an undefined-length INCR (or, by policy, INCR8 plus INCR4). [Make It Work](#make-it-work) builds this splitter as a complete, checked function.

**How many pieces at most?** An aligned AXI4 INCR of transfers of 4 bytes or less spans at most 1KB (256 × 4 bytes), so it crosses at most one 1KB boundary and splits into at most 2 AHB bursts. With 8-byte transfers it can span 2KB and needs up to 3; with 16-byte transfers, up to 4.

**Reshapes that have nothing to do with 1KB.** Some legal AXI bursts have no single AHB equivalent:
- **FIXED** (every transfer at the same address, A3.4.1): AHB has no fixed-address burst, so each transfer becomes its own SINGLE.
- **WRAP2**: AHB wraps only in 4, 8 or 16 transfers. A WRAP2 that starts at its wrap boundary is an INCR of 2; one that starts in the upper half becomes two SINGLEs in wrap order.
- **Unaligned start**: AXI's first transfer may be unaligned (A3.4.3), but every AHB transfer must be aligned to its size (§3.5). The bridge sends the first partial transfer as smaller aligned SINGLEs. An AXI INCR4 of words at 0x1001 becomes a byte SINGLE at 0x1001, a halfword SINGLE at 0x1002, then a 3-transfer INCR at 0x1004.
- **Sparse or all-zero `WSTRB`**: IHI0033B.b has no write strobes, so a write whose strobes do not cover whole aligned transfers must go out as narrower aligned transfers, and a transfer with all strobes low, which a master may use to "disable further writing" (A3.4.1), writes nothing and can be skipped.

### The two mistakes everyone makes

1. **"AHB bursts can cross 4KB, so an AHB-to-AXI bridge splits at 4KB."** Wrong twice: a legal AHB incrementing burst cannot even cross 1KB (§3.5), so a 4KB split never triggers on legal input, and a burst that does cross is illegal stimulus for a checker to flag, not something for the bridge to fix. The real AHB→AXI reasons are the 256 limit, width conversion and the unknown INCR length.
2. **"Every legal AXI burst is a legal AHB burst."** Wrong: AXI bursts may cross 1KB, start unaligned, use FIXED or WRAP2, and carry sparse strobes. Each needs a split or a reshape on the AHB side.

### Responses and errors, both directions

An **AHB-to-AXI bridge** receives AXI responses and must express them on AHB:

| AXI response | On AHB | Bridge action |
|---|---|---|
| OKAY (`2'b00`) | OKAY | Complete the data phase |
| EXOKAY (`2'b01`) | OKAY | Answers only an exclusive access, which an AHB-Lite bridge never issues. An AHB5 bridge with the Exclusive_Transfers property reports exclusive success on `HEXOKAY` (§8.3) |
| SLVERR (`2'b10`) | ERROR | Two-cycle ERROR on the data phase it belongs to: the failing read beat, or the last beat of a non-posted write |
| DECERR (`2'b11`) | ERROR | Same as SLVERR: AHB has only one error code |

**Reads.** AXI gives a response on every R beat, and "the required number of data transfers must be performed, even if an error is reported" (A3.4.4). So when `RRESP` is SLVERR on beat 2 of 4, the AXI slave still sends all four beats. The bridge must:
1. Accept every R beat, whatever the AHB side does next.
2. Give the AHB data phase of that beat a **two-cycle** ERROR: `HRESP` high with `HREADYOUT` low, then both high (§5.1.3). The first cycle gives the master time to cancel the next transfer, whose address is already on the bus.
3. Follow the master: it may cancel the rest of the burst by driving IDLE during the ERROR, or continue (§3.5.2). If it continues, each later beat gets its own `RRESP`. If it cancels, the bridge drops the R beats nobody asked for.

The read path that produces this waveform:

```systemverilog
// snippet: read path of an AHB-to-AXI bridge
//   data_phase : an accepted AHB read is in its data phase
//   rd_avail   : the R beat for that data phase is in the read buffer
//   rd_err     : its RRESP is SLVERR or DECERR (RRESP[1] == 1)
// The read buffer pops the beat at the edge where HREADY is high.
logic err2;  // high in the second ERROR cycle
always_ff @(posedge HCLK or negedge HRESETn)
  if (!HRESETn) err2 <= 1'b0;
  else          err2 <= !err2 && data_phase && rd_avail && rd_err;

// ERROR: first cycle HRESP=1 with HREADYOUT=0, second cycle both high.
assign HRESP     = err2 || (data_phase && rd_avail && rd_err);
// HREADYOUT is low while the beat is not there yet (with OKAY) and in ERROR cycle 1.
assign HREADYOUT = !data_phase || err2 || (rd_avail && !rd_err);
```

**Writes.** "For a write transaction, a single response is signaled for the entire burst, and not for each data transfer within the burst" (A3.4.4), and the slave sends it only after the last W transfer (A3.3.1). There is no "error on beat 3" of an AXI write. When the AHB master hears about a BRESP error depends on the posting policy below.

An **AXI-to-AHB bridge** has the reverse problem: an AHB slave answers each transfer, but AXI has one `BRESP` per write burst.
- **AHB ERROR on read transfer k** → `RRESP` = SLVERR on R beat k. The bridge still returns every R beat the AXI master asked for (A3.4.4). If it continues the AHB burst, each later beat carries its own AHB result; if it cancels, what the remaining beats carry is the bridge's documented policy (for example SLVERR on each).
- **AHB ERROR on any write transfer** → one `BRESP` = SLVERR for the burst, sent only after the bridge has accepted every W transfer (A3.3.1). Earlier AHB transfers already updated the slave: the error does not undo them.
- **SLVERR or DECERR?** AHB has one ERROR code, so which AXI code the bridge returns is a design policy. Document it, and make the scoreboard check it.

### Posted and non-posted writes

An AHB data phase completes as soon as the bridge takes the data, but the AXI write response arrives much later. So the bridge must decide what to do with the last AHB beat:

```text
AHB master -> bridge (AHB slave interface)
  1. Master drives HADDR, HTRANS=NONSEQ, HWRITE=1, HBURST=INCR4
  2. Bridge accepts each transfer and buffers its HWDATA

Bridge -> AXI slave (AXI master interface)
  3. Bridge drives AW (AWLEN=3) and the W transfers; WVALID never waits for AWREADY
  4. AXI slave returns one BRESP after the last W transfer

Bridge -> AHB master
  5. Non-posted: the bridge has held HREADYOUT low on the last data phase; it
     now completes it with OKAY, or with the two-cycle ERROR if BRESP is an error.
     Posted: every beat already completed with OKAY in step 2, so a BRESP error
     must be reported another way (interrupt, error status register).
```

|---|---|---|
| **Non-posted** | Only after `BRESP`: `HREADYOUT` is held low on the last data phase for the whole AXI round trip | Reported on that last beat as a two-cycle ERROR (§5.1.3). The earlier beats already completed with OKAY |

**What the protocols allow.** Both specifications tie early write responses to the bufferable attribute. On AHB, if `HPROT[4:3]` are both deasserted, `HPROT[2]` deasserted means "the write response must be given from the final destination" (IHI0033B.b Table 3-5). On AXI, Device Non-bufferable memory requires that "the write response must be obtained from the final destination" (IHI0022E A4.4.1), while the Bufferable types allow a response from an intermediate point. So a common policy is to post only writes marked Bufferable and keep the rest non-posted.

**The cost of non-posting.** A non-posted write keeps `HREADYOUT` low for the whole AXI round trip. IHI0033B.b recommends that a slave inserts no more than 16 wait states, "to prevent any single access locking the bus" (§5.1.2 Note): on a single-layer AHB bus, every other master waits too. This is a recommendation, not a rule, but a slow AXI path can make it a performance bug.

**The hidden cost of posting: read-after-write order.** The AHB master saw its write complete, so it may immediately read the same address. AHB requires that order to hold: for Device memory "all read and write transfers from the same master to the same slave must remain ordered" (§3.8.4), and for Normal memory, transfers "to addresses that overlap must remain ordered" (§3.8.5). AXI will not keep it for the bridge: "AXI has no ordering restrictions between read and write transactions", and a master "can only consider the earlier transaction is complete when … it receives the write response. Sending all of the write data for the transaction must not be taken as indicating completion" (IHI0022E A5.3.4).

### AXI handshake dependencies: the bridge's own deadlock

A bridge is an AXI master on one side or an AXI slave on the other, and both roles have handshake rules that exist only to prevent deadlock (IHI0022E A3.3.1):
- **As an AXI master** (AHB-to-AXI): "the master must not wait for the slave to assert AWREADY or WREADY before asserting AWVALID or WVALID". The Caution in A3.3.1 gives the exact bridge bug: "a master must not wait for AWREADY to be asserted before driving WVALID. A deadlock condition can occur if the slave is waiting for WVALID before asserting AWREADY."
- **As an AXI slave** (AXI-to-AHB): the slave *may* wait for AWVALID, WVALID or both before asserting AWREADY or WREADY, and it must send `BVALID` only after the last W transfer (A3.3.1). Write data may even arrive before its address (A3.3). The bridge must therefore never make one channel's READY wait for a completed handshake on the other channel while that channel waits for it in turn.

### Clocks and resets

**Synchronous bridges.** When both sides run on the same clock (or on clocks derived from one source with a known phase), the bridge is ordinary registered logic and needs no synchronizers.

**Asynchronous bridges.** When `HCLK` and `ACLK` are unrelated, every signal from one side is a clock domain crossing. The standard structure is an **asynchronous FIFO** per direction:
- The payload (address, data, response) is written into the FIFO memory in one domain and read in the other; it never passes through synchronizers.
- Only the FIFO **pointers** cross, in **Gray code** (one bit changes per step), through **two-flop synchronizers** (two flip-flops in a row in the receiving domain, which give a metastable first flop a cycle to settle). A pointer sampled mid-change is then either the old or the new value, never a mix.
- Low-rate control can use a **req/ack handshake**: only the req and ack levels are synchronized, and the payload register stays stable from req until ack returns.

**Pitfall: synchronizing VALID, READY and data bit by bit.** If `VALID`, `READY` and the payload bits each go through their own two-flop synchronizer, each bit can resolve a cycle apart, so the other domain can see `VALID` with half-updated data. A one-cycle `VALID` pulse from a faster clock can also be missed entirely, and a late `READY` can make the sender count one transfer as two. Carry each transfer as one unit, through an asynchronous FIFO or a full handshake.

**Resets.** The two sides have their own reset rules, and an asynchronous bridge usually has two reset domains:
- **AXI** (IHI0022E A3.1.2): `ARESETn` may be asserted asynchronously but is deasserted synchronously with `ACLK`. During reset a master drives `ARVALID`, `AWVALID` and `WVALID` low, and a slave drives `RVALID` and `BVALID` low; the earliest a master may raise a VALID is a rising `ACLK` edge after `ARESETn` is high.
- **AHB** (IHI0033B.b §7.1.2): `HRESETn` is asserted asynchronously and deasserted synchronously after a rising `HCLK` edge. During reset masters drive `HTRANS` IDLE and slaves drive `HREADYOUT` high.
- **One side resets with transfers in flight.** The bridge must keep the live side protocol-legal. It cannot abort an AXI burst it has started (A3.4.1): it must still send the remaining W transfers (with all strobes low) and accept every R beat. Which responses it then gives, and what it reports, is a design policy to document and test.

**Verifying CDC.** Simulation does not model metastability, so random clock ratios alone cannot prove a crossing safe. Use structural CDC analysis and, where the tool offers it, metastability injection (both **tool-dependent**), plus multi-clock simulation with several ratios and random phases, and reset tests per domain. CDC sign-off at SoC level is covered in [E-SOC-1](/curriculum/T4_Expert/E-SOC-1_SoC-Level_Verification_Strategies/index).

**What a CDC bug looks like in a bridge log.** The scoreboard reports a duplicated, lost or corrupted transfer, or the bench hangs, but only at some clock ratios or phases, and the failing seed does not fail again after an unrelated change. That pattern points at the crossing, not at the translation logic; the bug table below has the row. This lesson does not build an asynchronous FIFO as a worked example: its design (pointer width, full and empty generation) belongs with CDC sign-off in E-SOC-1, and a simulation of it cannot show metastability, so it would prove little here.

| Protocol checkers | AHB checker on the input (the 1KB rule flags illegal stimulus); AXI checker on the output | AXI checker on the input; AHB checker on the output, where the 1KB and alignment rules now check the bridge |

**The scoreboard compares bytes, not bursts.** A split, a downsize or a WRAP→INCR conversion changes the burst shape but never the bytes or their order. So the scoreboard should not predict the exact AXI bursts (that is the bridge's policy, checked separately). It should predict the byte stream: every AHB write beat becomes its bytes, every AXI W transfer becomes the bytes its strobes enable, and the two streams must match in order. The core, using two analysis imps declared with `` `uvm_analysis_imp_decl `` (uvm-core 2020.3.1, `src/macros/uvm_tlm_defines.svh`):

```systemverilog
// snippet: core of a bridge scoreboard (writes, AHB-to-AXI direction)
// ahb_item: one completed AHB beat (haddr, hsize, hwrite, hwdata).
// axi_wr_item: one AXI write burst rebuilt by the AXI monitor (awaddr, awsize,
// wdata[$], wstrb[$]); this bridge emits INCR bursts only.
`uvm_analysis_imp_decl(_ahb)
`uvm_analysis_imp_decl(_axi)

class bridge_sb extends uvm_scoreboard;
  `uvm_component_utils(bridge_sb)

  localparam int BUS_BYTES = 4;  // both buses 32 bits in this example

  uvm_analysis_imp_ahb #(ahb_item, bridge_sb)    ahb_export;
  uvm_analysis_imp_axi #(axi_wr_item, bridge_sb) axi_export;

  typedef struct { logic [31:0] addr; logic [7:0] data; } byte_t;
  byte_t       exp_q[$];          // bytes the AHB master wrote, in order
  int unsigned matches, mismatches;

  function new(string name, uvm_component parent);
    super.new(name, parent);
    ahb_export = new("ahb_export", this);
    axi_export = new("axi_export", this);
  endfunction

  // Predictor: each AHB write beat becomes its bytes, whatever the burst shape.
  function void write_ahb(ahb_item t);
    if (!t.hwrite) return;
    for (int i = 0; i < (1 << t.hsize); i++) begin
      logic [31:0] a = t.haddr + i;
      exp_q.push_back('{addr: a, data: t.hwdata[8 * (a % BUS_BYTES) +: 8]});
    end
  endfunction

  // Each AXI write burst: walk the INCR beat addresses and the enabled lanes.
  function void write_axi(axi_wr_item t);
    logic [31:0] aligned = (t.awaddr >> t.awsize) << t.awsize;
    foreach (t.wdata[k]) begin
      logic [31:0] beat = (k == 0) ? t.awaddr : aligned + (k << t.awsize);
      logic [31:0] base = beat - (beat % BUS_BYTES);  // bus-aligned address
      for (int lane = 0; lane < BUS_BYTES; lane++)
        if (t.wstrb[k][lane]) compare_byte(base + lane, t.wdata[k][8 * lane +: 8]);
    end
  endfunction

  function void compare_byte(logic [31:0] addr, logic [7:0] data);
    byte_t e;
    if (exp_q.size() == 0) begin
      mismatches++;
      `uvm_error("SCB", $sformatf("AXI wrote 0x%08h with no AHB byte pending", addr))
      return;
    end
    e = exp_q.pop_front();
    if (e.addr === addr && e.data === data) matches++;
    else begin
      mismatches++;
      `uvm_error("SCB", $sformatf("expected 0x%08h=%02h, AXI wrote 0x%08h=%02h",
                                  e.addr, e.data, addr, data))
    end
  endfunction

  function void check_phase(uvm_phase phase);
    if (exp_q.size() != 0)
      `uvm_error("SCB", $sformatf("%0d AHB bytes never reached AXI", exp_q.size()))
    `uvm_info("SCB", $sformatf("SCB_SUMMARY matches=%0d mismatches=%0d pending=%0d",
                               matches, mismatches, exp_q.size()), UVM_NONE)
  endfunction
endclass
```

Responses are checked beside the bytes, against the documented policy: for a non-posted bridge, the last AHB beat of a write ends with ERROR exactly when some `BRESP` of its AXI bursts was SLVERR or DECERR; for a posted bridge, it always ends with OKAY and the error register records the failure. Reads add an ordering check: the value the AHB master reads must be the one the reference memory holds after every write the master saw complete.

**Checks on each side.** Bind the AHB checker from [B-AHB-3](/curriculum/T3_Advanced/B-AHB-3_AHB_Verification/index) on the AHB port (the two-cycle ERROR, OKAY in waits, the 1KB rule as an input check) and the AXI checker from [B-AXI-6](/curriculum/T3_Advanced/B-AXI-6_AXI_Verification_Performance/index) on the AXI port (stable payload while VALID waits, `WLAST` on transfer `AxLEN + 1`, and the 4KB rule from [B-AXI-2](/curriculum/T3_Advanced/B-AXI-2_AXI_Burst_Math/index)). No passive assertion can see whether `WVALID` waits for `AWREADY`: on the wires, a bridge that waits looks like one that is merely slow. That A3.3.1 dependency is caught by an AXI slave mode that holds `AWREADY` low until it sees `WVALID`, plus `a_ahb_liveness` (below) or a test timeout. Tag each check **[Protocol]** when a specification rule forces it and **[Policy]** when it is this bridge's choice (posting, greedy splitting), so a failure tells the reader which document to open.

**Check the control fields too.** The mapping table above is the bridge's documented design, so its check is **[Policy]**; that every piece of a split keeps the same `AxPROT` is **[Protocol]** (A4.3.1). A short function in the scoreboard, called for every AXI burst with the AHB transfer that started it, is enough:

**Formal properties, in their correct forms.** Two properties that every bridge should carry, written for both simulation and formal:

```systemverilog
// snippet: bridge properties; the AHB side is clocked by HCLK, the AXI side by ACLK
function automatic bit crosses_4kb(logic [31:0] addr, logic [7:0] len, logic [2:0] size);
  logic [31:0] aligned = (addr >> size) << size;   // INCR: start from the aligned address
  return 32'(aligned[11:0]) + ((32'(len) + 1) << size) > 32'h1000;
endfunction

// [Protocol IHI0022E A3.4.1] no AXI INCR burst crosses 4KB (a safety net here)
a_aw_no_4kb: assert property (@(posedge ACLK) disable iff (!ARESETn)
  AWVALID && AWBURST == 2'b01 |-> !crosses_4kb(AWADDR, AWLEN, AWSIZE));
a_ar_no_4kb: assert property (@(posedge ACLK) disable iff (!ARESETn)
  ARVALID && ARBURST == 2'b01 |-> !crosses_4kb(ARADDR, ARLEN, ARSIZE));

// [Bridge obligation] the data phase of every transfer the bridge accepts ends
a_ahb_liveness: assert property (@(posedge HCLK) disable iff (!HRESETn)
  HSEL && HREADY && HTRANS[1] |=> s_eventually HREADYOUT);
```

`HSEL && HREADY && HTRANS[1]` is true exactly at the edge where the bridge accepts a transfer, `|=>` starts the check one edge later, in the transfer's data phase, and `s_eventually` (IEEE 1800-2023 §16.12.13) demands that `HREADYOUT` rise at some later edge. A strong property that is still pending when simulation ends has not been satisfied; how a simulator reports such an unfinished attempt (and whether it needs an option to do so) is **tool-dependent**. `|->` starts the consequent at the antecedent's end point (§16.12.7), and `s_eventually` holds if its operand holds "at a current or future clock tick" (§16.12.13). For a formal proof the environment needs **assumptions** (`assume property`, §16.14.2): the tool explores only input behaviour the assumptions allow, and in simulation an assumption is checked like an assertion. A bridge needs two kinds: the AHB master rules on the AHB port (best taken from an AHB master assertion IP used as assumptions, including the 1KB rule), and **fairness** on the AXI side, meaning the slave eventually raises its READY signals and eventually answers with `BVALID` and `RVALID`. Without fairness the tool proves nothing about liveness, because a slave that never answers is a legal counterexample.

**Debrief.** The rules of whatever drives the bridge's inputs become assumptions; the rules the bridge itself must follow become assertions. Liveness needs fairness because, without it, "the slave never answers" is a legal input and a counterexample to every liveness property. The snippet below adds two fairness assumptions on `ACLK`, for the read channels, and the two covers that show the proof is not vacuous:

```systemverilog
// snippet: assumptions and covers for a formal run (AHB-to-AXI direction)
// [tool-dependent] liveness assumptions need an engine that supports them.
// A slave may wait for ARVALID before ARREADY (A3.3.1), but not forever.
m_ar_fair: assume property (@(posedge ACLK) disable iff (!ARESETn)
  ARVALID |-> s_eventually ARREADY);
m_r_fair:  assume property (@(posedge ACLK) disable iff (!ARESETn)
  ARVALID && ARREADY |-> s_eventually RVALID);

// The antecedent of a_ahb_liveness must occur, or its proof says nothing.
c_ahb_accept: cover property (@(posedge HCLK) disable iff (!HRESETn)
  HSEL && HREADY && HTRANS[1]);
// A doubleword WRAP16 must be reachable; HSIZE <= 3'b010 would make it unreachable.
c_wrap16_dw: cover property (@(posedge HCLK) disable iff (!HRESETn)
  HSEL && HREADY && HTRANS == 2'b10 && HBURST == 3'b110 && HSIZE == 3'b011);
```

`cover property` (§16.14.3) counts the evaluation attempts in which the property succeeds; a formal tool searches for a trace in which it does. If a cover can never succeed, an assumption (or a bug) has removed that behaviour, and every assertion that depends on it passes without checking anything. Write-side fairness is subtler: a slave may legally wait for `WVALID` before it raises `AWREADY` (A3.3.1), so an unconditional `AWVALID |-> s_eventually AWREADY` forbids that slave, and with it the handshake deadlock you want to find. [Expert: formal verification of a bridge that converges](#expert-formal-verification-of-a-bridge-that-converges) shows a version that keeps it, and covers the rest.

**Coverage.** Cover the translation cases, not just the traffic: direction × burst type (SINGLE, INCR4/8/16, WRAP4/8/16, undefined INCR, AXI FIXED and WRAP2) × length class (1, 2 to 16, 17 to 256, more than 256) × size × boundary relation (inside, ends exactly at, crosses 1KB) × alignment × response (OKAY, SLVERR, DECERR, and their beat position) × posting × memory type (`HPROT[3:2]`, or `AxCACHE[1:0]` on the AXI side) × backpressure on each AXI channel. Every assertion's antecedent needs a `cover property` too, or a clean run may mean nothing was checked. A covergroup for the AXI-to-AHB direction, sampled once per AXI burst by the AXI monitor, shows the shape (IEEE 1800-2023 §19.3, §19.5, §19.6, §19.8.1):

```systemverilog
                                           logic [1:0] rel, logic [3:0] cache);
  cp_burst: coverpoint burst { bins fixed = {2'b00}; bins incr = {2'b01};

  cp_len:   coverpoint len   { bins one = {1}; bins upto16 = {[2:16]};

  cp_buf:   coverpoint cache[0] { bins nonbufferable = {0}; bins bufferable = {1}; }
```

The cross is where the splitter's bugs live: a 2-to-16 burst that ends exactly at a 1KB boundary is the off-by-one case, and a long burst that crosses is the case that must give two AHB bursts. A single transfer never crosses (even an unaligned one stays inside its own aligned block of `2**AxSIZE` bytes), so that cell is ignored rather than left as a hole.

### Common bridge bugs: symptom, cause, checker, fix

| Bug | Symptom in the log or waveform | Cause | Checker that catches it | Fix |
|---|---|---|---|---|
| Split off by one (AXI→AHB) | `a_ahb_no_1kb_cross` fires at the SEQ to 0x0400 of an AXI INCR16 from 0x03F0 | Room computed as `(next_1kb - a) / nbytes + 1`: 5 transfers from 0x03F0 instead of 4 | The AHB 1KB checker on the bridge's AHB master port; the Make It Work sweep | Room is `(next_1kb - a) / nbytes` with `a` aligned; keep the `+ 1` mutant in the regression |
| `AWLEN` wraps (AHB→AXI) | `AXI AW addr=0x00000400 AWLEN=43 (44 transfers)` then `WLAST on transfer 300` | No 256-transfer cap: 300 − 1 = 299 wraps to 43 in 8 bits | Per-burst W count against `AWLEN + 1` (the lab's TODO 2); a total-count check misses it | Cap each AXI burst at 256 transfers (A3.4.1) |
| Write data on the wrong burst or lanes | `WLAST` only on the last transfer of the whole request; or byte mismatches that start at a split point | W transfers counted against the request instead of each AW; narrow-transfer strobes taken from the burst start, not from each transfer's address | Per-burst `WLAST` check; byte scoreboard | One beat counter per AXI burst; lanes from each transfer's address (A3.4.3) |
| Responses merged wrongly on a split | AHB sees OKAY although the second AXI burst's `BRESP` was SLVERR | The bridge completed the AHB write after the first `BRESP` | Response-policy check in the scoreboard | Wait for every `BRESP` of the split and combine them |

| WRAP→INCR conversion | Byte-order mismatch on a downsized WRAP; second INCR at the top of the block | Second burst started at the wrong address, or with the wrong length | Byte scoreboard (order) | First INCR from the start to the top of the block; second from the wrap boundary (lowest address) for `(start − boundary) / size` transfers |
| Outstanding overflow or channel deadlock | Simulation hangs; `AWVALID` high, `WVALID` low, no progress | Queue overflow without READY backpressure, or W gated by `AWREADY` (A3.3.1) | `a_ahb_liveness`, a timeout, a slave that waits for `WVALID` | Backpressure with `AWREADY`/`ARREADY` only when full; never gate VALID on READY ([B-AXI-5](/curriculum/T3_Advanced/B-AXI-5_AXI_Pitfalls_Interconnect_Deadlocks/index)) |
| Posted-write hazard | Read returns old data only when AXI write latency is long | Read issued before the overlapping posted write's `BRESP` (A5.3.4) | Read check against the reference memory, with random AXI latency | Address hazard check against outstanding posted writes, or non-posted for that region |
| Control fields mapped wrongly (AHB→AXI) | A downstream access filter rejects ordinary data reads with DECERR, or Device writes get an early response from a buffer and a "write, then poll status" sequence reads stale status | `AxPROT[2]` copied from `HPROT[0]` instead of inverted, or `AxCACHE[0]` tied high instead of taken from `HPROT[2]` | `ctrl_map_ok` on every AXI burst; memory type × posting coverage | Map each field as in the table (A4.7 Table A4-6; IHI0033B.b Table 3-5) |
| Clock-domain crossing (async bridge) | Duplicated, lost or corrupted transfers, or a hang, only at some clock ratios or phases | Binary FIFO pointers synchronized bit by bit, or VALID, READY and data synchronized separately | Multi-ratio, random-phase regression with the byte scoreboard and liveness; structural CDC analysis (**tool-dependent**) | Gray-coded pointers through two-flop synchronizers, or a req/ack handshake with a stable payload |

### Recap

- **Split where the target protocol forces it; check the input against the source protocol's rules.** AHB→AXI: the 256 limit (only for 1- or 2-byte transfers), width conversion, and the unknown INCR length; never 4KB. AXI→AHB: 1KB, plus reshaping for FIXED, WRAP2, unaligned starts and strobes.
- **Responses:** AXI has one `BRESP` per write and an `RRESP` per read beat; AHB's ERROR is always two cycles. Posting hides write errors and breaks read-after-write order unless the bridge checks hazards.
- **Deadlock:** as an AXI master, never make `WVALID` wait for `AWREADY`.
- **Testbench:** the predictor uses the same rules, the scoreboard compares bytes rather than bursts, the checkers on both sides are tagged [Protocol] or [Policy], and the liveness property starts in the data phase.

## Make It Work

### Worked example: split an AXI INCR at 1KB, and check every split

This is the reference model an AXI-to-AHB bridge's predictor needs, as a complete non-UVM unit. `split_axi_incr` turns one AXI INCR burst into the AHB bursts the bridge should issue; `check_pieces` applies every AHB rule to the result; the `initial` block prints two worked cases and then sweeps every word-aligned burst in one 4KB page.

```systemverilog
// compile
// AXI-to-AHB splitter model with a self-checking sweep.
`timescale 1ns/1ps
module tb_top;

  // HBURST encodings, IHI0033B.b Table 3-3.
  localparam logic [2:0] SINGLE = 3'b000, INCR  = 3'b001,
                         INCR4  = 3'b011, INCR8 = 3'b101, INCR16 = 3'b111;

  typedef struct {
    logic [31:0] haddr;   // start address of this AHB burst
    logic [2:0]  hburst;
    int unsigned beats;   // NONSEQ + SEQ transfers
    int unsigned nbytes;  // bytes per transfer (2**HSIZE)
  } ahb_piece_t;

  function automatic logic [2:0] hburst_for(int unsigned beats);
    case (beats)
      1:       return SINGLE;
      4:       return INCR4;
      8:       return INCR8;
      16:      return INCR16;
      default: return INCR;   // undefined length; INCR4/8/16 + SINGLEs is another policy
    endcase
  endfunction

  function automatic string hburst_name(logic [2:0] hb);
    case (hb)
      SINGLE:  return "SINGLE";
      INCR4:   return "INCR4";
      INCR8:   return "INCR8";
      INCR16:  return "INCR16";
      default: return "INCR";
    endcase
  endfunction

  // Split one AXI INCR burst (AxADDR, len transfers of nbytes) into AHB bursts.
  // AXI: only the first transfer may be unaligned (IHI0022E A3.4.1, A3.4.3).
  // AHB: every transfer aligned, no incrementing burst across 1KB (IHI0033B.b 3.5).
  function automatic void split_axi_incr(input logic [31:0] axaddr,
                                         input int unsigned len,
                                         input int unsigned nbytes,
                                         ref ahb_piece_t q[$]);
    logic [31:0] a, aligned, last, room;
    int unsigned left, take, sz;
    q.delete();
    aligned = axaddr & ~32'(nbytes - 1);
    a       = axaddr;
    left    = len;
    if (axaddr != aligned) begin
      // Unaligned first transfer: send its bytes as aligned SINGLEs.
      last = aligned + nbytes - 1;
      while (a <= last) begin
        sz = nbytes;
        while (sz > 1 && ((a % sz) != 0 || a + sz - 1 > last)) sz = sz / 2;
        q.push_back('{haddr: a, hburst: SINGLE, beats: 1, nbytes: sz});
        a += sz;
      end
      left--;
    end
    while (left > 0) begin
      // a | 32'h3FF is the last byte of a's 1KB region, so adding 1 gives the next
      // 1KB boundary; room is the number of whole transfers that fit before it.
      room = ((a | 32'h3FF) + 1 - a) / nbytes;
      take = (left < room) ? left : room;
      q.push_back('{haddr: a, hburst: hburst_for(take), beats: take, nbytes: nbytes});
      a    += take * nbytes;
      left -= take;
    end
  endfunction

  // Count rule violations in q for the AXI burst it came from.
  function automatic int unsigned check_pieces(input logic [31:0] axaddr,
                                               input int unsigned len,
                                               input int unsigned nbytes,
                                               const ref ahb_piece_t q[$]);
    int unsigned errs;
    logic [31:0] next_addr, last_byte;
    errs      = 0;
    next_addr = axaddr;
    foreach (q[i]) begin
      last_byte = q[i].haddr + q[i].beats * q[i].nbytes - 1;
      if (q[i].haddr != next_addr)                    errs++;  // gap or overlap
      if (q[i].haddr % q[i].nbytes != 0)              errs++;  // AHB alignment
      if (last_byte[31:10] != q[i].haddr[31:10])      errs++;  // 1KB rule
      case (q[i].hburst)                                       // fixed lengths
        SINGLE: if (q[i].beats != 1)  errs++;
        INCR4:  if (q[i].beats != 4)  errs++;
        INCR8:  if (q[i].beats != 8)  errs++;
        INCR16: if (q[i].beats != 16) errs++;
        default: ;
      endcase
      next_addr = q[i].haddr + q[i].beats * q[i].nbytes;
    end
    // Every byte of the AXI burst sent exactly once.
    if (next_addr != (axaddr & ~32'(nbytes - 1)) + len * nbytes) errs++;
    return errs;
  endfunction

  task automatic show(input logic [31:0] axaddr, input int unsigned len,
                      input int unsigned nbytes);
    ahb_piece_t q[$];
    split_axi_incr(axaddr, len, nbytes, q);
    $display("AXI INCR, %0d x %0d B at 0x%08h -> %0d AHB bursts",
             len, nbytes, axaddr, q.size());
    foreach (q[i])
      $display("  AHB %0d: HADDR=0x%08h HBURST=%s size=%0d B transfers=%0d",
               i + 1, q[i].haddr, hburst_name(q[i].hburst), q[i].nbytes, q[i].beats);
  endtask

  initial begin
    ahb_piece_t  q[$];
    int unsigned pass_n, fail_n, most;
    show(32'h0000_03F0, 16, 4);   // legal AXI, crosses 0x0400
    show(32'h0000_1001, 4, 4);    // unaligned start

    pass_n = 0;
    fail_n = 0;
    most   = 0;
    for (int unsigned s = 0; s < 4096; s += 4)
      for (int unsigned n = 1; n <= 256 && s + n * 4 <= 4096; n++) begin
        split_axi_incr(s, n, 4, q);
        if (check_pieces(s, n, 4, q) == 0) pass_n++;
        else                               fail_n++;
        if (q.size() > most) most = q.size();
      end
    $display("Sweep: all word-aligned AXI INCRs of 1..256 transfers in one 4KB page");
    $display("  most AHB bursts for one AXI burst: %0d", most);
    $display("PASS=%0d FAIL=%0d", pass_n, fail_n);
    $finish;
  end

endmodule
```

### Prove it can fail

A check that never fails proves nothing. Change the room computation to `room = ((a | 32'h3FF) + 1 - a) / nbytes + 1;` (the off-by-one bug from the table above) and rerun. The 0x03F0 case now prints a 5-transfer first burst that ends at 0x0403, and the sweep reports a non-zero `FAIL` count (97 920 in the Python model), from the 1KB-rule and contiguity checks.

### How to use it in a bridge testbench

1. Make `split_axi_incr` the predictor's split model for the AXI-to-AHB direction, so the scoreboard knows which AHB bursts to expect if you also check the split policy.
2. Bind `a_ahb_no_1kb_cross` on the bridge's AHB **master** port: there it checks the bridge, not the stimulus.
3. Add `cover property` statements, or covergroup bins, for each piece type (SINGLE, INCR4/8/16, INCR) and for the 1-piece and 2-piece cases, so you know the sweep's cases also occur in the real bench.
4. Keep the off-by-one mutant as a regression test of the checker itself. The sweep runs word-aligned starts only, so before you add an unaligned-start mutant (one that uses `axaddr` instead of `aligned`), extend the sweep to unaligned starts or call `check_pieces` inside `show`; otherwise nothing would catch it.
5. Extend the model with FIXED and WRAP (see the kata below) before you trust it for those burst types.

**Checklist before moving on:**
- [ ] No AHB burst the model produces crosses 1KB, and the sweep prints `FAIL=0`.
- [ ] Every byte of the AXI burst appears exactly once, in order.
- [ ] The unaligned first transfer goes out as aligned SINGLEs.
- [ ] The INCR versus INCR4/8/16 choice is documented as policy, and the byte scoreboard does not depend on it.
- [ ] The off-by-one mutant makes the sweep fail.

## Push Further

### Expert: undefined-length INCR, the bridge cannot know the length

`HBURST` = INCR carries no length (IHI0033B.b Table 3-3), and the master may end it after a BUSY with NONSEQ or IDLE (§3.5.1). A bridge has four options, each with a cost:
- **Single-transfer AXI bursts** for every INCR transfer: always correct, slowest, and legal for any memory type.
- **Buffer writes** until the burst ends, the buffer fills, the 1KB region ends or 256 transfers are reached, then send one AXI burst: efficient, but it adds latency, and with a non-posted policy it holds `HREADYOUT` low longer.
- **Speculative read bursts** (fetch, say, a cache line): allowed only when the transfer is Modifiable or Normal memory. IHI0022E A4.3.1 allows a Modifiable read to "fetch more data than required", and IHI0033B.b §3.8.5 says "Reads can fetch more data than required" for Normal memory. For Device memory "reads must not be prefetched or performed speculatively" (§3.8.4), and A3.4.1 warns that discarding read data from a read-sensitive device such as a FIFO loses data.
- **Fixed chunks** (for example AXI INCR4 at a time), trimming the last chunk's surplus with all strobes low on writes (A3.4.1). Reads still face the speculation rule above.

The explorer assumes the bridge knows the length (its assumption 2), which is true only for the buffering policy. The prefetch question is one of the [interview angles](#interview-angles) below.

### Expert: early termination on AHB, none on AXI

An AHB master may cancel the rest of a burst after an ERROR (IHI0033B.b §3.5.2), and a multi-layer interconnect may also terminate a burst at a slave port; "slaves must be designed to work correctly if the burst is not completed" (§3.5.2). AXI has the opposite rule: "No component can terminate a burst early" (IHI0022E A3.4.1). So once an AHB-to-AXI bridge has issued `AWLEN` or `ARLEN`:
- for a write it must still send every announced W transfer, with all strobes low for the ones it has no data for ("the master can disable further writing by deasserting all the write strobes … the master must complete the remaining transfers");
- for a read it must accept every R beat and drop the unwanted ones ("the master can discard read data, but it must complete all transfers").

This is one more reason buffering policies matter: a bridge that issued a long `AWLEN` early pays for a cancelled AHB burst with padding transfers.

### Expert: what a bridge may change, by memory type

Both protocols restrict how a transfer may be reshaped, by memory type:
- **AXI** (IHI0022E A4.3.1): a Non-modifiable transaction (`AxCACHE[1]` = 0) "must not be split into multiple transactions or merged", and its address, size, length, burst type, lock and protection must not change (Table A4-2), with two exceptions: INCR bursts longer than 16 may be split, and downsizing "when downsizing to a bus width narrower than that required by the transaction size" forces a modification (Note). A Modifiable transaction may be split, merged, and widened with strobes, but no modification may move an access to a different 4KB space or split a single-copy-atomicity access (an access the system guarantees to perform as one indivisible update, A7.1).
- **AHB5** (IHI0033B.b §3.8.4): for Device memory a burst "is permitted to be broken into a number of smaller bursts" if the total number of NONSEQ and SEQ transfers is unchanged, `HSIZE` must not change, and writes must not be merged. Normal memory (§3.8.5) allows `HBURST` and `HSIZE` to change.

Two consequences. An AXI-to-AHB bridge must split a Non-modifiable AXI INCR16 that crosses 1KB, because AHB forbids the crossing; it keeps every transfer and its size, which is what §3.8.4 permits on the AHB side (this reading is the author's, combining the two rules). And a bridge may merge AHB SINGLEs into one AXI burst only for Modifiable transfers.

### Expert: posted writes, ordering and latency

- **AHB requires the order the bridge must keep:** same master to the same slave for Device memory (§3.8.4); overlapping addresses for Normal memory (§3.8.5).
- **AXI will not keep it before `BRESP`:** A5.3.4 says reads and writes "can complete in any order, even if the ARID value of a read transaction is the same as the AWID value of a write transaction", and completion means `BRESP`. A4.4.1 lists same-ID ordering for "read and write transactions" (to the same Device slave, or to overlapping Normal addresses), but the ordering model that defines it applies that order within one direction. Between a read and a write with the same ID, "a master must wait to receive a response to the first transaction before issuing the second transaction" (A6.1), and the Note in A4.3.2 says the same for Non-modifiable transactions. So the same ID gives no read-after-write order before `BRESP`. Wait for `BRESP`, or address-check the outstanding writes, as A5.3.4's Note suggests.
- **Posting in the AXI-to-AHB direction:** the bridge, now an AXI slave, may send an early `BRESP` only for Bufferable types; Device Non-bufferable and Normal Non-cacheable Non-bufferable writes need the response "obtained from the final destination" (A4.4.1). The AHB side then decides nothing: the bridge's posting decision follows the AXI-side memory type.
- **Latency budget:** a non-posted AHB write waits for the whole AXI round trip, often far beyond the 16-wait-state recommendation (§5.1.2 Note). Posted writes need a buffer deep enough for the AHB burst rate times the AXI round trip.
- **Posting is a promise, not just a shortcut:** a component that gives a write response before the final destination "must ensure visibility of the transaction" to later transactions to the same or overlapping address (A6.5), and a slave that has responded must make the write visible to every later read or write, whatever the IDs (A6.4). A posting AXI-to-AHB bridge therefore needs the same hazard check on its own read path.

### Expert: strobes, alignment and narrow transfers

IHI0033B.b has no write strobes at all, and every AHB transfer is aligned to its size (§3.5). IHI0033C adds an optional `HWSTRB`; a bridge to such an interface can pass sparse strobes through directly, but a bridge to an Issue B.b slave cannot. So an AXI-to-AHB bridge for Issue B.b must turn each AXI transfer's strobe pattern into whole aligned AHB transfers. `WSTRB` = `4'b0110` on a word at 0x1000 enables bytes 0x1001 and 0x1002; they cannot go out as one halfword, because 0x1001 is not halfword-aligned, so they become two byte transfers. `WSTRB` = `4'b1100` becomes one halfword at 0x1002. An all-zero strobe transfer is skipped. In the other direction, a narrow AHB transfer becomes a narrow AXI transfer whose strobes select the lanes of *that transfer's* address (IHI0022E A3.4.3): a byte at 0x0401 on a 32-bit bus uses `WSTRB` = `4'b0010`.

| `WSTRB` (lanes 3 to 0) on a word at 0x1000 | Bytes written | AHB transfers to an Issue B.b slave |
|---|---|---|
| `4'b1111` | 0x1000 to 0x1003 | one word at 0x1000 |
| `4'b1100` | 0x1002, 0x1003 | one halfword at 0x1002 |
| `4'b0110` | 0x1001, 0x1002 | a byte at 0x1001, then a byte at 0x1002 (no aligned halfword covers them) |
| `4'b0111` | 0x1000 to 0x1002 | a halfword at 0x1000, then a byte at 0x1002 |
| `4'b0000` | none | none: the transfer is skipped |

Once a write is split into several AHB transfers it is no longer a single access to the slave, so a sparse-strobe write can lose single-copy atomicity (A7.1). Flag such writes as a policy decision, and avoid them for Device memory.

### Expert: exclusive and locked accesses across a bridge

- **AXI to AHB-Lite:** AHB-Lite has no exclusive support, so the bridge answers an exclusive access with OKAY, which tells the master it failed or is not supported. "An exclusive write to a slave that does not support exclusive access always updates the memory location" (IHI0022E A7.2.5), so software that ignores the response corrupts its lock.
- **AXI to AHB5 with Exclusive_Transfers:** AHB5 exclusives "must have a single data transfer" and be SINGLE or INCR (IHI0033B.b §8.4), while an AXI exclusive may be a burst of up to 16 transfers and 128 bytes (A7.2.4). A Non-modifiable AXI exclusive may change `AxSIZE` and `AxLEN` if the total bytes stay the same (A4.3.1), but an AXI exclusive wider than one AHB transfer still cannot become one AHB5 exclusive. `HMASTER` must keep each AXI master's exclusive thread distinct (§8.3).
- **IDs:** "The ARID value of the exclusive read must match the AWID value of the exclusive write" (A7.2.4), so an AHB5-to-AXI bridge must map each `HMASTER` thread to a stable ID.
- **Locked transfers:** AHB `HMASTLOCK` (§3.3) has no AXI4 equivalent: "AXI4 does not support locked transactions" (A7.3). An AHB-to-AXI bridge cannot pass a locked sequence on as one.

### Expert: AXI ID assignment in an AHB-to-AXI bridge

AHB has no IDs, so the bridge chooses `AWID` and `ARID`, and the choice decides what AXI orders for it:
- **One fixed ID for everything:** same-ID writes complete in order and same-ID reads return in order (A5.3), so responses arrive in issue order, which makes the response mapper simple. Reads and writes are still unordered against each other: a read issued before an earlier write's `BRESP` has no order against it, whatever the IDs (A5.3.4, A6.1).
- **Separate IDs for reads and writes:** the same, but makes the read/write independence explicit; the hazard check is mandatory.
- **One ID per `HMASTER`** (AHB5 multi-master): keeps exclusive pairs and per-master order, at the cost of a reorder buffer if responses for different IDs return out of order.
- **Never different IDs for the pieces of one split read** unless the bridge reorders: read data for different `ARID`s "can arrive in any order" (A5.3.1), so the second AXI burst of a long AHB INCR read could return first and `HRDATA` would deliver its bytes early. Use one `ARID` for every piece, or a reorder buffer indexed by `RID`.

Interconnects append bits to `AWID` and `ARID` to identify the master port, and remove them from `BID` and `RID` before passing the response back (A5.3.5). So an AHB-to-AXI bridge, as a master, gets back exactly the IDs it sent. The wider IDs exist only at slave interfaces, which matters for an AXI-to-AHB bridge: as a slave, it must accept the full slave-side ID width and return each received `AWID` and `ARID` unchanged in `BID` and `RID`.

### Expert: reset domain crossing in a bridge

An asynchronous bridge has two reset domains, and resets that are asserted asynchronously but released synchronously to each side's clock (A3.1.2, §7.1.2). Three policies need explicit design and tests:
- **Release order:** each side's FIFO pointers must be reset together, or one side may see a stale pointer as data.
- **One side resets with transfers in flight:** the live AXI side must still complete any burst already announced (A3.4.1), with strobes low or read data dropped, and the bridge must decide what the reset AHB side sees when it comes back (usually nothing).
- **Responses owed across the reset:** a posted write whose `BRESP` arrives after the AHB side reset can only be logged.

Reset domain crossing analysis tools exist alongside CDC tools (**tool-dependent**). In simulation, assert each reset in the middle of every kind of burst and check that nothing is pending afterwards. [A-UVM-9](/curriculum/T3_Advanced/A-UVM-9_Reset_and_Error_Injection/index) builds reset-aware components.

### Expert: formal verification of a bridge that converges

A bridge suits formal well, because its rules are local and precise, but a naive setup proves too little or never finishes:
- **Assume-guarantee:** assume the protocol on the input side and the slave behaviour on the output side (`assume property`, IEEE 1800-2023 §16.14.2); assert the protocol on the output side and the slave obligations on the input side (§16.14.1). Use complete assertion IP, not a hand-picked subset.
- **Fairness for liveness:** assume the AXI slave eventually raises each READY, eventually sends `BVALID` once it has the address and the last W, and eventually sends `RVALID` after AR. Otherwise a slave that never answers is a counterexample to every liveness property.
- **Fairness that is too strong hides bugs too:** condition each fairness assumption only on what the slave may legally wait for. A slave may wait for `WVALID` before `AWREADY` (A3.3.1), so the write-address fairness should start only once write data has been offered:

  ```systemverilog
  // snippet: [tool-dependent] AW fairness that still allows a slave to wait for WVALID
  logic w_offered;  // WVALID seen since the last AW handshake
  always_ff @(posedge ACLK or negedge ARESETn)
    if (!ARESETn)                w_offered <= 1'b0;
    else if (AWVALID && AWREADY) w_offered <= 1'b0;
    else if (WVALID)             w_offered <= 1'b1;

  m_aw_fair: assume property (@(posedge ACLK) disable iff (!ARESETn)
    AWVALID && (WVALID || w_offered) |-> s_eventually AWREADY);
  ```

  Against a bridge whose `WVALID` waits for `AWREADY`, the antecedent never holds, so the tool may keep `AWREADY` low, and `a_ahb_liveness` fails as soon as the bridge can take no more AHB data: the deadlock is found. An unconditional `AWVALID |-> s_eventually AWREADY` would force `AWREADY` high and prove the deadlocking bridge live. The lab's `AXI_SLAVE_WAITS_FOR_W` slave uses the same `aw_gate` logic in simulation.
- **Over-constraint hides bugs:** an assumption such as `HSIZE <= 3'b010` ("transfers are at most a word") looks harmless, but it removes the 64-bit WRAP16 downsizing case, so the WRAP→INCR bug can never be reached. Every assumption needs a `cover property` (§16.14.3) on the behaviour it might exclude.
- **Data integrity with a tracked byte:** let the tool choose a symbolic address and data byte, written once on the AHB side; assert that the AXI side writes that byte to that address, exactly once and in order. That proves the transformation for every address, unlike a byte count, which passes with wrong data or a wrong address.
- **Convergence:** deep buffers, 256-transfer counters and asynchronous FIFOs make full proofs expensive. Reduce parameters (a shallower buffer, a smaller maximum length), prove bounded properties, and say which. How far a given engine gets is **tool-dependent**.

Formal remains a complement to simulation with a reference model: it proves the properties you wrote, under the assumptions you wrote. Methodology is in [E-INT-1](/curriculum/T4_Expert/E-INT-1_Integrating_UVM_with_Formal_Verification/index).

### Expert: performance and sizing

These are engineering trade-offs, not specification rules:
- **Write buffer depth** sets how long posted writes can run ahead of the AXI side; size it from the AHB burst rate and the worst AXI write round trip.
- **Outstanding queue** in an AXI-to-AHB bridge: AHB processes one transfer at a time, so a deep queue only absorbs bursts of AXI traffic; it never raises throughput above the AHB rate.
- **Read prefetch** for Normal memory saves AHB wait states but wastes AXI bandwidth when the master stops early.
- **Measure, do not guess:** use the latency and bandwidth method of [B-AXI-6](/curriculum/T3_Advanced/B-AXI-6_AXI_Verification_Performance/index) on both ports, and report AHB wait states per transfer against the §5.1.2 recommendation.

### Kata: plan the verification of a bridge

An asynchronous AXI-to-AHB bridge connects a CPU's AXI port (`ACLK`) to an AHB-Lite bus (`HCLK`, about a quarter of the `ACLK` rate) with two slaves:
- a UART, whose writes arrive with `AWCACHE` = `4'b0000` (Device Non-bufferable, IHI0022E Table A4-5);
- an SRAM, whose writes arrive with `AWCACHE` = `4'b0011` (Normal Non-cacheable Bufferable).

Write a short plan that answers these five questions, then compare it with the worked answer:
1. The posting policy for each region, and what each choice costs.
2. Two error-injection scenarios, and what the AXI master must see in each.
3. One CDC scenario and one reset scenario.
4. What the scoreboard compares, and what it deliberately does not compare.
5. For a formal run: one assumption and one cover property, and why each is needed.

<details>
<summary>Worked answer</summary>

**1. Posting.** The bridge is the AXI slave here, so "posting" means sending `BRESP` before the AHB slave has answered.
- **UART: non-posted.** Device Non-bufferable needs "the write response … obtained from the final destination" (A4.4.1), so `BVALID` waits until the AHB slave completes the last data phase. The cost is latency: every write includes the clock crossing and every AHB wait state, and the AXI master's outstanding writes back up. The gain: an AHB ERROR reaches `BRESP`.
- **SRAM: posting allowed.** A Bufferable write's response "can be obtained from an intermediate point" (A4.4.1), which hides the AHB latency. The cost: an AHB ERROR that arrives after the early `BRESP` can only be logged (status register or interrupt). And a slave that has responded must make the write visible to every later read or write (A6.4), so the bridge's read path needs a hazard check against buffered writes.
- Non-posted for both is also legal and simpler. Whatever you choose, write it down: the scoreboard checks responses against it.

**2. Error injection** (from the reactive AHB slave agent):
- ERROR on transfer 2 of a UART INCR4 write: one `BRESP` = SLVERR (or DECERR, by documented policy), after all four W transfers are accepted (A3.3.1, A3.4.4).
- ERROR on beat k of an SRAM read: `RRESP` = SLVERR on beat k, and every requested R beat is still returned (A3.4.4).
- A third worth adding: ERROR on a posted SRAM write. `BRESP` was already OKAY, so the error register must record it.

**3. CDC and reset.**
- **CDC:** run several clock ratios (for example `ACLK`:`HCLK` of 4:1, 1:1 and 1:3) with random phase and random AHB wait states, so the asynchronous FIFOs fill and drain. Back it with structural CDC analysis (**tool-dependent**), because simulation cannot show metastability.
- **Reset:** assert `HRESETn` in the middle of an AXI INCR16 write. The AXI side must still accept every W transfer and send one `BRESP`, as the documented reset policy says.

**4. Scoreboard.** Compare byte streams. For writes, compare the bytes each AXI W transfer's strobes enable with the bytes the AHB write transfers carry, in order. For reads, compare the bytes of the R beats with the `HRDATA` bytes the AHB slave returned. Do not compare burst shapes: the 1KB split, the FIXED and WRAP2 reshapes and unaligned starts change the shape, not the bytes. Check the split policy separately with `split_axi_incr` from Make It Work, and check the responses against the posting policy.

**5. Formal.** Assume fairness from the AHB slaves, and cover the case the splitter exists for:

```systemverilog
// snippet: [tool-dependent] fairness on the AHB side of an AXI-to-AHB bridge
m_hready_fair: assume property (@(posedge HCLK) disable iff (!HRESETn)
  !HREADY |-> s_eventually HREADY);
// The 1KB split must be reachable: an INCR16 of words whose aligned start is
// above 0x3C0 in its 1KB region crosses the boundary.
c_cross_1kb: cover property (@(posedge ACLK) disable iff (!ARESETn)
  AWVALID && AWREADY && AWBURST == 2'b01 && AWSIZE == 3'b010 &&
  AWLEN == 8'd15 && AWADDR[9:2] > 8'hF0);
```

- **Why the assumption:** without it, an AHB slave that holds `HREADY` low forever is a legal counterexample to every liveness property, such as "every AXI write gets its `BRESP`". It depends only on the slave's own wait, so it cannot hide a bridge bug.
- **Why the cover:** it shows that the crossing case is reachable under the AXI master assumptions. If it cannot be covered, those assumptions are over-constrained, and the 1KB assertion on the bridge's AHB port passes without ever checking a split.

</details>

```text
@ 130 AHB READ  0x00000100
@ 140 AXI AR  addr=0x00000100 ARID=1 ARLEN=0
@ 160 AXI R   data=0x00001111 RRESP=OKAY RLAST=1 RID=1
@ 170 AHB READ  0x00000100 -> HRDATA=0x00001111
@ 170 UVM_ERROR [SCB] read 0x00000100: expected 0x0000a5a5, got 0x00001111
@ 190 AXI B   BRESP=OKAY BID=0
```

Name the cause, the rule that allows the AXI behaviour, and two fixes.

<details>
<summary>Worked solution</summary>

**Cause.** The bridge posted the write (OKAY at 100) and then issued the read's AR at 140, before the write's BRESP at 190. The read completed first and returned the old value.

**Rule.** This bridge uses separate IDs (`AWID=0`, `ARID=1`), and transactions with different IDs have no ordering at all (IHI0022E A5.3). A shared ID would not have helped either: "AXI has no ordering restrictions between read and write transactions … even if the ARID value of a read transaction is the same as the AWID value of a write transaction" (A5.3.4), and the ordering model orders a read after a write only if the read is issued after the write's response (A6.1). A write is complete only when its BRESP arrives. Meanwhile AHB requires the master's read to see its own earlier write (§3.8.4, §3.8.5), so the bridge broke AHB ordering.

**Fixes.** (1) A hazard check: hold any AR whose address overlaps an outstanding posted write until that write's BRESP arrives. (2) Make the region non-posted, so the AHB write itself does not complete until BRESP. Then add the scenario (posted write, overlapping read, long write latency) and a coverage bin for it.

</details>
