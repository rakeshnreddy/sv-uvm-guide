# AHB↔AXI Bridges & System Integration

Real SoC designs rarely use a single bus protocol. A modern chip might have an AXI4 interconnect for high-performance masters (CPU, DMA, GPU) while using AHB-Lite for lower-bandwidth peripherals (UART, SPI, GPIO). **Protocol bridge IPs** sit between these domains, translating transactions from one protocol to another.

These bridges are deceptively complex — they must handle burst splitting, response mapping, flow control mismatches, and boundary rules that differ between protocols. Bridge bugs are some of the hardest to debug because they corrupt data silently or create deadlocks that appear to be in the master or slave, not the bridge itself.

<QuickTake>
- **Protocol Bridges** translate transactions between AHB and AXI, handling the fundamental asymmetry between a pipelined single-channel protocol and a decoupled five-channel protocol.
- **Burst Translation** is the hardest part, because the two protocols have different boundary rules: AHB incrementing bursts must not cross **1KB** (IHI0033B.b 3.5), AXI bursts must not cross **4KB** (IHI0022E A3.4.1).
- **AHB → AXI:** every 4KB boundary is also a 1KB boundary, so a legal AHB burst can never cross 4KB. The bridge splits only for the AXI 256-transfer limit (long undefined-length INCR) and for width conversion.
- **AXI → AHB:** a legal AXI burst may still cross 1KB, so the bridge **must split at 1KB**.
- **Formal Verification** is the gold standard for bridge correctness because the combinatorial space of burst types, sizes, and boundary conditions is too large for directed testing.
</QuickTake>

## 1. Why Protocol Bridges Exist

### The Two-Speed SoC

Modern SoCs are built with a hierarchy of interconnects:

| Layer | Protocol | Typical Masters | Typical Bandwidth |
|-------|----------|----------------|-------------------|
| High-Performance Fabric | AXI4 | CPU cores, DMA engines, GPU | 10+ GB/s |
| Peripheral Bus | AHB-Lite / APB | UART, SPI, I2C, GPIO, Timer | 100 MB/s |
| Configuration Bus | APB | Register access, debug | 10 MB/s |

A **bridge IP** connects these layers. The two most common bridges are:

1. **AHB-to-AXI Bridge** — An AHB master (e.g., a DMA engine on the peripheral bus) needs to access AXI memory space. The bridge converts AHB single-channel pipelined transfers into AXI five-channel transactions.
2. **AXI-to-AHB Bridge** — An AXI master (e.g., CPU) needs to access AHB peripherals. The bridge converts decoupled AXI transactions into sequential AHB pipelined transfers.

### Why Bridges Are Hard

The fundamental problem is **protocol asymmetry**:

| Feature | AHB | AXI |
|---------|-----|-----|
| Channels | 1 (shared address/data) | 5 (AW, W, B, AR, R) |
| Pipelining | Address phase overlaps with previous data phase | Fully decoupled — address and data are independent |
| Outstanding Transactions | 1 (inherently in-order) | Multiple per ID (out-of-order across IDs) |
| Burst Length | INCR4/8/16, WRAP4/8/16, or undefined-length INCR | INCR up to 256 transfers; FIXED up to 16; WRAP 2/4/8/16 |
| Boundary rule | Incrementing bursts must not cross 1KB (IHI0033B.b 3.5) | No burst may cross 4KB (IHI0022E A3.4.1) |
| Response Timing | Immediate (same cycle as data) | Decoupled (B channel fires after all W beats) |

Every row in this table is a potential source of bridge bugs.

### Block Diagram

An AHB-to-AXI bridge contains these key blocks:

1. **AHB Slave Interface** — Accepts AHB transactions from the AHB master.
2. **Address Decoder & Splitter** — Determines if the burst needs to be split (AXI 256-transfer limit, width conversion; 1KB in the AXI-to-AHB direction).
3. **Write Buffer** — Stores AHB write data beats until a complete AXI write burst can be issued.
4. **Read Buffer** — Stores AXI read response data until it can be returned to AHB.
5. **AXI Master Interface** — Issues AXI transactions downstream.
6. **Response Mapper** — Converts AXI response codes (OKAY, SLVERR, DECERR) to AHB response (OKAY, ERROR).

### Transaction Flow: AHB Write → AXI Write

```
AHB Master → Bridge AHB Slave Interface
  1. AHB master drives HADDR, HTRANS=NONSEQ, HWRITE=1, HBURST=INCR8
  2. Bridge accepts the address phase, starts collecting data beats
  3. Over the next 8 cycles, AHB master drives HWDATA for each beat
  4. Bridge buffers the data in its write buffer

Bridge Internal → AXI Master Interface
  5. Bridge issues AWVALID with translated burst parameters
  6. Bridge drives WVALID for each buffered data beat
  7. Bridge waits for BVALID on the B channel

Bridge → AHB Master
  8. Non-posted: the bridge has held HREADYOUT low on the last AHB data phase;
     it now completes that phase with OKAY, or with the two-cycle ERROR if
     BRESP is SLVERR or DECERR.
     Posted: the AHB beats all completed with OKAY in steps 2-4, so a BRESP
     error must be reported another way (interrupt, error register).
```

AHB completes each data phase as soon as the bridge takes the data, but AXI returns one write response for the whole burst after the last W transfer (IHI0022E A3.4.4). Step 8 is therefore a design choice, not a protocol rule:

| Write policy | When the AHB master sees the last beat complete | What happens to a SLVERR/DECERR in BRESP |
|---|---|---|
| **Non-posted** | Only after BRESP: the bridge holds `HREADYOUT` low on the last data phase for the whole AXI round trip | Reported on that last beat as a two-cycle ERROR (IHI0033B.b 5.1.3). The earlier beats already completed with OKAY. |
| **Posted** | As soon as the bridge buffers the data | Cannot be reported on the bus. The bridge must log it (interrupt, error status register) or the error is lost. |

Posting gives lower latency and frees the AHB bus sooner; non-posting keeps errors visible to the master that caused them. Many bridges post only writes marked Bufferable (`HPROT[2]`, IHI0033B.b 3.7), which maps to `AWCACHE[0]`, and keep the rest non-posted: for AXI Device Non-bufferable memory the write response must come from the final destination (IHI0022E A4.4.1). Whichever policy a bridge uses, document it, and make the scoreboard check that policy, because both are legal.

## 3. Burst Translation Rules

### AXI Burst Length Limits

AXI4 supports bursts up to 256 beats (`AWLEN = 255`). AHB-Lite supports:
- **INCR**: Undefined length (can be any number of beats)
- **INCR4/INCR8/INCR16**: Fixed length bursts of 4, 8, or 16 beats
- **WRAP4/WRAP8/WRAP16**: Wrapping bursts of 4, 8, or 16 beats

When an AHB master issues an INCR burst that would translate to more than 256 AXI transfers, the bridge must split it into multiple AXI transactions. Only an undefined-length INCR can do this, for example 1024 byte-wide transfers that fill one 1KB region.

### Boundary Rules in Each Direction

**AHB → AXI: no 4KB split is ever needed.** "Masters must not attempt to start an incrementing burst that crosses a 1KB address boundary" (IHI0033B.b 3.5). Every 4KB boundary is also a 1KB boundary, so a legal AHB incrementing burst stays inside one 4KB page, and so does the AXI burst made from it. An AHB burst that crosses 1KB is **illegal stimulus**: the bridge may assume it never arrives, and an AHB-side checker must flag it:

```systemverilog
// [Protocol IHI0033B.b 3.5] per-transfer check, so it also covers undefined-length INCR
logic [31:0] burst_start;
always_ff @(posedge HCLK) if (HREADY && HTRANS == 2'b10) burst_start <= HADDR; // NONSEQ
a_ahb_no_1kb_cross: assert property (@(posedge HCLK) disable iff (!HRESETn)
  HREADY && HTRANS == 2'b11 && !(HBURST inside {3'b010, 3'b100, 3'b110})     // SEQ, not WRAP
  |-> HADDR[31:10] == burst_start[31:10]);
```

**AXI → AHB: split at 1KB.** An AXI burst only has to stay inside 4KB. An AXI INCR16 of words at `0x03F0` is legal (it ends at `0x042F`), but it crosses `0x0400`. The bridge issues an AHB INCR4 from `0x03F0`, then the remaining 12 transfers from `0x0400` (as an undefined-length INCR, or INCR8 plus INCR4):

```systemverilog
// AXI-to-AHB bridge: split an AXI INCR burst at each 1KB boundary.
// Start from the aligned address: only the first AXI transfer may be unaligned,
// and AHB needs aligned transfers, so an unaligned first transfer goes out separately.
function automatic int unsigned beats_to_1kb(input logic [31:0] addr, input int unsigned nbytes);
  logic [31:0] next_1kb = (addr & ~32'h3FF) + 32'h400;
  return (next_1kb - addr) / nbytes;
endfunction

int unsigned remaining, n;
logic [31:0] cur;
remaining = beats_left;     // AXI transfers still to send
cur       = aligned_addr;   // address of the next aligned transfer
while (remaining > 0) begin
  n = (remaining < beats_to_1kb(cur, nbytes)) ? remaining : beats_to_1kb(cur, nbytes);
  issue_ahb_burst(cur, n);   // INCR4/8/16 when n is 4, 8 or 16; otherwise undefined-length INCR
  cur       += n * nbytes;
  remaining -= n;
end
```

### WRAP Burst Translation

Both protocols wrap at the same boundary, the burst's total size (beats x transfer size), and AHB WRAP4/8/16 are all legal AXI WRAP lengths. A same-width bridge maps them directly.

Width conversion is where WRAP gets hard. Downsizing an AHB WRAP16 of doublewords onto a 32-bit AXI bus would need a 32-transfer AXI WRAP, but AXI WRAP bursts stop at 16 (IHI0022E A3.4.1). The bridge sends the same bytes in the same order as two INCR bursts: from the start address up to the wrap boundary, then from the lower wrap address. Downsizing below the transfer size always forces such a modification (IHI0022E A4.3.1). In the other direction, an AXI WRAP2 has no AHB equivalent.

## 4. Response Mapping and Error Handling

### Response Code Translation

| AXI Response | AHB Response | Bridge Action |
|-------------|-------------|---------------|
| `OKAY (2'b00)` | `OKAY` | Pass through |
| `EXOKAY (2'b01)` | `OKAY` | AHB-Lite has no exclusive response. An AHB5 bridge with the Exclusive_Transfers property reports it on `HEXOKAY` (IHI0033B.b chapter 8). |
| `SLVERR (2'b10)` | `ERROR` | Two-cycle ERROR on the AHB data phase it belongs to: the failing read beat, or the last beat of a non-posted write |
| `DECERR (2'b11)` | `ERROR` | Same as SLVERR |

### The Error Termination Problem

AXI reads and writes report errors differently (IHI0022E A3.4.4):

- **Reads** carry a response on every R beat, so `SLVERR` on beat 3 of an 8-beat read is possible. The AXI slave still sends all 8 beats; the burst is not cut short.
- **Writes** get a single `BRESP` for the whole burst, after the last W transfer. There is no "error on beat 3" of an AXI write. When the AHB master sees the error depends on the posted or non-posted policy above.

For the read case, the bridge must:

1. Accept all 8 R beats from AXI, whatever the AHB side does.
2. Give the AHB data phase of beat 3 a **two-cycle** ERROR: `HRESP` high with `HREADYOUT` low, then both high (IHI0033B.b 5.1.3). A one-cycle ERROR is a protocol violation, and the master would see it too late to cancel the next transfer.
3. Then follow the AHB master: it may cancel the rest of the burst by driving IDLE, or continue (IHI0033B.b 3.5.2). If it continues, the bridge returns each later beat with that beat's own RRESP. If it cancels, the bridge discards the R beats nobody asked for.

```systemverilog
// Read path of an AHB-to-AXI bridge (sketch).
//   data_phase : an accepted AHB read is in its data phase
//   rd_avail   : the R beat for that data phase is in the read buffer
//   rd_err     : its RRESP is SLVERR or DECERR (RRESP[1] == 1)
// The buffer pops the beat at the edge where HREADY is high.
logic err2;  // high in the second ERROR cycle
always_ff @(posedge HCLK or negedge HRESETn)
  if (!HRESETn) err2 <= 1'b0;
  else          err2 <= !err2 && data_phase && rd_avail && rd_err;

// ERROR: first cycle HRESP=1 with HREADYOUT=0, second cycle both high.
assign HRESP     = err2 || (data_phase && rd_avail && rd_err);
// HREADYOUT is low while the beat is not there yet (with OKAY) and in the first ERROR cycle.
assign HREADYOUT = !data_phase || err2 || (rd_avail && !rd_err);
```

## 5. Reset and Clock Domain Crossing (CDC)

### Synchronous Bridges

If both the AHB and AXI domains share the same clock, the bridge is purely combinational/registered logic. This is the simpler case.

### Asynchronous Bridges (CDC)

When the AHB domain runs at a different clock frequency than the AXI domain, the bridge must include **Clock Domain Crossing (CDC)** structures:

1. **Async FIFOs** — For carrying address, data and responses across clock domains. The payload is written into the FIFO memory in one domain and read in the other.
2. **Gray-code pointers** — Only the FIFO pointers cross the boundary, through two-flop synchronizers. Gray code changes one bit per step, so a pointer sampled mid-change is either the old or the new value.
3. **Handshake synchronizers** — For low-rate control, a req/ack (four-phase or toggle) handshake: only the req and ack levels are synchronized, and the payload register stays stable from req until ack returns.
4. **Reset synchronization** — Both domains may have independent resets that must be properly sequenced.

Do **not** pass `VALID`, `READY`, or the payload bits through separate two-flop synchronizers. Each bit resolves independently and may land a cycle apart, so the other domain can see `VALID` with half-updated data. A one-cycle `VALID` pulse from a faster clock can also be missed completely, and a synchronized `READY` arrives late, so the sender may treat one transfer as two. Carry the whole transfer as one unit, through an async FIFO or a full handshake synchronizer.

### CDC Verification

CDC bugs are the most insidious bridge failures. They manifest as:
- **Data corruption** — Bits of a multi-bit value are sampled while they change, so the receiving domain sees a mix of old and new bits.
- **Lost transactions** — A VALID pulse is too short and missed by the receiving domain.
- **Deadlocks** — A READY signal from the other domain is never sampled.

Verification approaches:
1. **Formal CDC tools** (Cadence Conformal CDC, Synopsys SpyGlass CDC) — Structurally verify all crossings.
2. **Multi-clock simulation** — Run the bridge with intentionally mismatched clocks and random phase offsets.
3. **Reset sequencing tests** — Verify bridge behavior when one domain resets independently.

## 6. Formal Verification Strategy for Bridges

Formal verification is the **most effective** technique for bridge verification because:

1. **Exhaustive state coverage** — Formal explores all possible burst types, sizes, addresses, and boundary conditions.
2. **Equivalence checking** — You can prove that every AHB transaction maps to the correct AXI transaction(s).
3. **Deadlock detection** — Formal can prove that the bridge never enters a state where it stops making progress.

### Key Formal Properties

```systemverilog
// Property: Bridge must eventually complete every accepted AHB transaction
property p_bridge_liveness;
  @(posedge ACLK) disable iff (!ARESETn)
    (ahb_htrans == NONSEQ) |-> s_eventually (ahb_hready == 1);
endproperty

// Property: 4KB boundary is never violated on the AXI side.
// Only INCR can cross; start from the aligned address (IHI0022E A3.4.1).
property p_no_4kb_violation;
  logic [31:0] aligned;
  @(posedge ACLK) disable iff (!ARESETn)
    (AWVALID && AWBURST == 2'b01, aligned = (AWADDR >> AWSIZE) << AWSIZE) |->
      (aligned[11:0] + ((AWLEN + 1) << AWSIZE)) <= 32'h1000;
endproperty

// Property: Total data bytes in == total data bytes out
// (data integrity across the bridge)
property p_data_conservation;
  @(posedge ACLK) disable iff (!ARESETn)
    (bridge_state == IDLE && prev_state == COMPLETING) |->
      (total_ahb_bytes == total_axi_bytes);
endproperty
```

### Formal Constraints (Assumptions)

You must constrain the formal environment to only present legal inputs:

```systemverilog
// Assume AHB master follows protocol
assume property (@(posedge ACLK) disable iff (!ARESETn)
  (HTRANS == NONSEQ) |-> (HSIZE <= 3'b010));  // Max 4-byte transfers

// Assume the AHB master obeys IHI0033B.b 3.5: incrementing bursts stay inside 1KB
// (burst_start as in the AHB-side checker above)
assume property (@(posedge HCLK) disable iff (!HRESETn)
  HREADY && HTRANS == 2'b11 && !(HBURST inside {3'b010, 3'b100, 3'b110}) |->
    HADDR[31:10] == burst_start[31:10]);

// Assume AXI slave eventually responds
assume property (@(posedge ACLK) disable iff (!ARESETn)
  AWVALID |-> s_eventually AWREADY);
```

## 7. Common Bridge Bugs

### Bug 1: Off-by-One in Burst Splitting

In the AXI-to-AHB direction, the bridge calculates 3 transfers to the 1KB boundary but issues 4, so the AHB burst crosses 1KB. **Root cause:** using `>=` instead of `>` in the boundary comparison, or computing the distance from the unaligned start address instead of the aligned one.

### Bug 2: Write Data Misalignment

When splitting a burst, the bridge must ensure the `WSTRB` for the first beat of the second AXI burst is correct. If the original AHB transfer was unaligned, the strobe mask changes at the split point.

### Bug 3: Response Ordering on Split Bursts

If an AHB burst is split into two AXI bursts, the bridge receives two B-channel responses. It must wait for **both** before signaling completion to AHB. A common bug is returning OKAY after the first response, then receiving SLVERR on the second.

### Bug 4: WRAP-to-INCR Conversion Error

When downsizing turns a WRAP16 into more than 16 AXI transfers, the bridge must issue two INCR bursts. A common bug starts the second burst at the wrong address (it must be the lower wrap boundary) or gives it the wrong length (the bytes between the wrap boundary and the start address).

### Bug 5: Outstanding Transaction Overflow

An AXI-to-AHB bridge accepts multiple outstanding AXI transactions (different IDs) but AHB can only process one at a time. If the bridge's internal queue overflows, it must backpressure the AXI master by deasserting AWREADY/ARREADY — but must do so without creating a channel-dependency deadlock.

## 8. Verification Test Plan for Bridges

A comprehensive bridge verification plan must cover:

### Functional Scenarios
- Single-beat read/write (all sizes: byte, halfword, word)
- INCR bursts (all legal lengths)
- WRAP4, WRAP8, WRAP16 bursts
- AXI bursts that end exactly at a 1KB boundary, and ones that cross it (AXI-to-AHB split)
- Undefined-length AHB INCR bursts longer than 256 transfers
- WRAP bursts through a downsizing bridge
- Negative test: an AHB master that starts an incrementing burst across 1KB must trip the AHB-side checker
- Back-to-back bursts with no idle cycles
- Interleaved read and write traffic

### Error Injection
- AXI slave returns SLVERR on various beat positions
- AXI slave returns DECERR
- AXI slave stalls READY for extended periods
- AHB master issues bursts with maximum outstanding depth

### CDC Scenarios (for async bridges)
- Asymmetric clock ratios (2:1, 3:1, 7:3)
- Clock jitter injection
- Independent reset assertion on each domain
- Reset during mid-burst transfer

### Formal Properties
- Liveness: every accepted transaction eventually completes
- Safety: no 4KB boundary violations on the AXI side, no 1KB crossings on the AHB side
- Data integrity: bytes in == bytes out
- No deadlock: bridge always makes forward progress
