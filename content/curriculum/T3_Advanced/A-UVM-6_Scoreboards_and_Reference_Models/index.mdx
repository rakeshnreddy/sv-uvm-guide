## Quick Take
- **What it is:** A scoreboard is a passive verification component that collects transactions from monitors, predicts expected results through a reference model, and automatically compares DUT output against those predictions — transforming a testbench from "run and hope" into a self-checking machine.
- **Why it matters:** Without a scoreboard, catching a bug requires a human staring at waveforms comparing inputs to outputs. Scoreboards automate this comparison across millions of transactions, making bugs surface as `uvm_error` messages instead of invisible waveform anomalies.
- **The Standard:** IEEE 1800.2-2020 defines `uvm_scoreboard` (§13.6.1), a virtual class that extends `uvm_component` and adds no behavior. Extend it so tools and readers recognize the role; the matching, draining and end-of-test accounting are your code, built from `uvm_analysis_imp` and `uvm_tlm_analysis_fifo` (Clause 12).

## Build Your Mental Model

### The Scoreboard Architecture

Every production scoreboard follows this data flow:

```
Monitor → analysis_port → analysis_export → Scoreboard
                                                  ↓
                                           Reference Model
                                                  ↓
                                           Comparator Logic
                                                  ↓
                                         UVM_ERROR / UVM_INFO
```

The design separates three concerns:
1. **Collection** — The scoreboard receives transactions via TLM analysis ports. It never drives or monitors signals directly.
2. **Prediction** — A reference model computes the expected output from the input stimulus.
3. **Comparison** — A comparator checks the DUT's actual output against the reference model's predicted output.

### The Analysis FIFO Pattern

The recommended connection pattern uses `uvm_tlm_analysis_fifo` as a buffering adapter between the monitor's analysis port and the scoreboard's blocking get port:

```systemverilog
class my_scoreboard extends uvm_scoreboard;
  `uvm_component_utils(my_scoreboard)

  // Analysis FIFOs buffer transactions from monitors
  uvm_tlm_analysis_fifo #(my_transaction) input_fifo;
  uvm_tlm_analysis_fifo #(my_transaction) output_fifo;

  function new(string name, uvm_component parent);
    super.new(name, parent);
  endfunction

  function void build_phase(uvm_phase phase);
    super.build_phase(phase);
    input_fifo  = new("input_fifo", this);
    output_fifo = new("output_fifo", this);
  endfunction
endclass
```

In the environment's `connect_phase`, wire the monitor analysis ports to these FIFOs:

```systemverilog
function void connect_phase(uvm_phase phase);
  super.connect_phase(phase);
  // Input monitor → scoreboard input FIFO
  agent.input_monitor.ap.connect(scoreboard.input_fifo.analysis_export);
  // Output monitor → scoreboard output FIFO
  agent.output_monitor.ap.connect(scoreboard.output_fifo.analysis_export);
endfunction
```

> **Why use a FIFO?** A `uvm_analysis_imp` write callback is non-blocking and executes synchronously inside the monitor's `run_phase` context. If the scoreboard needs to do time-consuming comparison or wait for a corresponding output transaction, a FIFO decouples the timing — the scoreboard's `run_phase` can `get()` at its own pace. `uvm_tlm_analysis_fifo` is unbounded, so `write()` never blocks and never drops, but it stores the **handle** it is given, not a copy. A monitor that reuses one transaction object must publish a `clone()`, or every queued entry ends up showing the last transaction.

## Building a Transaction-Level Reference Model

The reference model is the golden behavioral specification of your DUT, implemented as pure SystemVerilog logic with no access to the RTL internals.

```systemverilog
class alu_reference_model;
  // Pure function: no side effects, no DUT access
  static function my_transaction predict(my_transaction input_txn);
    my_transaction expected = new();
    expected.copy(input_txn);

    case (input_txn.opcode)
      ADD:  expected.result = input_txn.operand_a + input_txn.operand_b;
      SUB:  expected.result = input_txn.operand_a - input_txn.operand_b;
      AND:  expected.result = input_txn.operand_a & input_txn.operand_b;
      OR:   expected.result = input_txn.operand_a | input_txn.operand_b;
      XOR:  expected.result = input_txn.operand_a ^ input_txn.operand_b;
      default: expected.result = '0;
    endcase

    return expected;
  endfunction
endclass
```

**Key principle:** The reference model should be simple enough that you trust it more than the RTL. If your reference model is as complex as the DUT, you've just duplicated the bug surface area.

## The Complete Scoreboard: Compare and Report

Combining the analysis FIFO pattern with the reference model, here is a complete self-checking scoreboard:

```systemverilog
class alu_scoreboard extends uvm_scoreboard;
  `uvm_component_utils(alu_scoreboard)

  uvm_tlm_analysis_fifo #(my_transaction) input_fifo;
  uvm_tlm_analysis_fifo #(my_transaction) output_fifo;

  int unsigned match_count;
  int unsigned mismatch_count;

  function new(string name, uvm_component parent);
    super.new(name, parent);
  endfunction

  function void build_phase(uvm_phase phase);
    super.build_phase(phase);
    input_fifo  = new("input_fifo", this);
    output_fifo = new("output_fifo", this);
    match_count    = 0;
    mismatch_count = 0;
  endfunction

  task run_phase(uvm_phase phase);
    my_transaction input_txn, output_txn, expected;

    forever begin
      // Wait for an input but leave it in the FIFO until its result arrives,
      // so check_phase can see an input whose output never came.
      input_fifo.peek(input_txn);
      output_fifo.get(output_txn);
      void'(input_fifo.try_get(input_txn));

      // Predict expected output
      expected = alu_reference_model::predict(input_txn);

      // Compare the field the output monitor fills (!== also flags X)
      if (output_txn.result !== expected.result) begin
        mismatch_count++;
        `uvm_error("SCOREBOARD",
          $sformatf("MISMATCH on txn #%0d: op=%s a=0x%0h b=0x%0h expected=0x%0h got=0x%0h",
            match_count + mismatch_count,
            input_txn.opcode.name(),
            input_txn.operand_a,
            input_txn.operand_b,
            expected.result,
            output_txn.result))
      end else begin
        match_count++;
        `uvm_info("SCOREBOARD",
          $sformatf("MATCH on txn #%0d: op=%s result=0x%0h",
            match_count,
            input_txn.opcode.name(),
            output_txn.result), UVM_HIGH)
      end
    end
  endtask

  // End-of-test accounting: anything left in a FIFO was never compared.
  function void check_phase(uvm_phase phase);
    super.check_phase(phase);
    if (!input_fifo.is_empty())
      `uvm_error("SCOREBOARD", $sformatf("%0d input(s) never produced an output", input_fifo.used()))
    if (!output_fifo.is_empty())
      `uvm_error("SCOREBOARD", $sformatf("%0d output(s) arrived with no input", output_fifo.used()))
    if (match_count + mismatch_count == 0)
      `uvm_error("SCOREBOARD", "No transactions compared: check monitor connections")
  endfunction

  function void report_phase(uvm_phase phase);
    `uvm_info("SCOREBOARD",
      $sformatf("\n========== Scoreboard Summary ==========\n  Matches:    %0d\n  Mismatches: %0d\n  Total:      %0d\n=========================================",
        match_count, mismatch_count, match_count + mismatch_count), UVM_LOW)

    if (mismatch_count > 0)
      `uvm_error("SCOREBOARD", $sformatf("%0d mismatches detected!", mismatch_count))
    else
      `uvm_info("SCOREBOARD", "All transactions matched — test PASSED", UVM_LOW)
  endfunction
endclass
```

> **Design note:** `check_phase` is not optional. If the DUT drops the last output, `run_phase` simply waits in `output_fifo.get()` until the phase ends, and no compare ever fails. Only the leftover input in `input_fifo` shows the bug. The same check catches a scoreboard that received zero transactions because of a broken connection.

## Handling Out-of-Order Transactions

In-order comparison assumes DUT output arrives in the same order as input. Pipelined or arbitrating designs may complete transactions out of order. AXI is the usual case: responses with **different** IDs may return in any order, but responses with the **same** ID must return in request order. That rule is a protocol requirement; how a particular DUT reorders across IDs is its design policy.

So the matching structure is **one ordered queue per ID**: an associative array of queues. The oldest prediction for an ID is the only legal partner for the next response with that ID.

A map with one slot per ID (`expected[id] = item`) is not enough. Two outstanding requests with the same ID are normal, and the second prediction overwrites the first.

```systemverilog
class ooo_scoreboard extends uvm_scoreboard;
  `uvm_component_utils(ooo_scoreboard)

  uvm_tlm_analysis_fifo #(my_transaction) input_fifo;
  uvm_tlm_analysis_fifo #(my_transaction) output_fifo;

  // One ordered queue per ID, oldest prediction first
  my_transaction expected_q[int unsigned][$];
  // Outputs that arrived before their prediction (the two threads race)
  my_transaction held_q[$];

  int unsigned match_count;
  int unsigned mismatch_count;

  function new(string name, uvm_component parent);
    super.new(name, parent);
  endfunction

  function void build_phase(uvm_phase phase);
    super.build_phase(phase);
    input_fifo  = new("input_fifo", this);
    output_fifo = new("output_fifo", this);
  endfunction

  task run_phase(uvm_phase phase);
    fork
      collect_inputs();
      compare_outputs();
    join
  endtask

  task collect_inputs();
    my_transaction txn;
    forever begin
      input_fifo.get(txn);
      expected_q[txn.id].push_back(alu_reference_model::predict(txn));
      retry_held(txn.id);
    end
  endtask

  task compare_outputs();
    my_transaction actual;
    forever begin
      output_fifo.get(actual);
      if (expected_q.exists(actual.id) && expected_q[actual.id].size() > 0)
        compare_pair(expected_q[actual.id].pop_front(), actual);
      else
        held_q.push_back(actual);  // maybe early; check_phase reports it if never matched
    end
  endtask

  // A prediction just arrived: an output with this ID may already be waiting.
  function void retry_held(int unsigned id);
    foreach (held_q[i]) begin
      if (held_q[i].id == id) begin
        compare_pair(expected_q[id].pop_front(), held_q[i]);
        held_q.delete(i);
        return;
      end
    end
  endfunction

  function void compare_pair(my_transaction exp, my_transaction act);
    if (act.result !== exp.result) begin
      mismatch_count++;
      `uvm_error("OOO_SCB", $sformatf("MISMATCH id=%0d: expected 0x%0h, got 0x%0h", act.id, exp.result, act.result))
    end else begin
      match_count++;
    end
  endfunction

  function void check_phase(uvm_phase phase);
    super.check_phase(phase);
    foreach (expected_q[id])
      if (expected_q[id].size() > 0)
        `uvm_error("OOO_SCB", $sformatf("id %0d: %0d expected transaction(s) never received", id, expected_q[id].size()))
    if (held_q.size() > 0)
      `uvm_error("OOO_SCB", $sformatf("%0d output(s) matched no prediction", held_q.size()))
  endfunction
endclass
```

**Key insights:**
- **The race.** `collect_inputs` and `compare_outputs` are separate threads. When an input and its output land in the same time step, the output thread can run first and find no prediction. Reporting "unexpected" at that moment would be a false error. Holding the output and retrying when the prediction arrives removes the race; `check_phase` reports anything still held.
- **Where the ID comes from.** Match on a field the DUT carries end to end (the AXI ID). A testbench-only sequence number works only if the DUT returns it.
- **End-of-test accounting.** `check_phase` catches dropped transactions (predictions never consumed) and extra ones (outputs never matched). Without it, both pass silently.

## Common Pitfalls

### 1. Comparing Objects by Reference Instead of Value

```systemverilog
// ❌ WRONG: compares handle identity (always fails for different objects)
if (actual_txn == expected_txn) ...

// ✅ CORRECT: uses uvm_object::compare() which calls do_compare()
if (actual_txn.compare(expected_txn)) ...
```

Every transaction class must implement `do_compare()` (or use the `` `uvm_field_* `` macros) for `compare()` to work correctly. If you rely on autopacked field macros, verify they cover all fields — a missing registration silently skips that field in comparisons. The opposite trap: `compare()` checks *every* registered field, so if the output monitor does not fill the operands, every compare fails. Compare the fields the output side really carries, or use a result-only item.

### 2. Scoreboard Receives Zero Transactions

A scoreboard connected to the wrong analysis port—or a monitor that never fires—reports zero mismatches and zero matches. This is a **false pass**.

**Mitigation:** In `report_phase`, assert that the total transaction count is greater than zero:

```systemverilog
if (match_count + mismatch_count == 0)
  `uvm_error("SCOREBOARD", "No transactions received — check monitor connections!")
```

### 3. Phase Ordering: Draining Until Idle

The `run_phase` ends when all objections are dropped. The test usually drops its objection when its sequence finishes, while responses are still inside the DUT. Writes that arrive after the phase ends never reach the scoreboard, so `check_phase` reports them as missing even though the DUT was right.

A fixed timer is a guess. An unconditional `#100ns` inside `phase_ready_to_end` is worse than it looks: UVM calls `phase_ready_to_end` again after every re-raise and drop, up to `max_ready_to_end_iterations` (20 by default in uvm-core `uvm_phase.svh`), so it adds about 2 µs to every test and still never checks that anything is pending.

Raise an objection only while work is outstanding, wait for it with a watchdog, and do it once:

```systemverilog
int unsigned outstanding;  // ++ when a prediction is stored, -- when it is matched
bit          drained;

function void phase_ready_to_end(uvm_phase phase);
  if (phase.get_name() != "run" || outstanding == 0 || drained) return;
  drained = 1;  // ready_to_end is called again after our drop
  phase.raise_objection(this, "scoreboard: responses outstanding");
  fork begin
    fork
      wait (outstanding == 0);  // a variable, so wait() has something to be sensitive to
      #(drain_timeout);         // watchdog: a dropped response must not hang the test
    join_any
    disable fork;
    phase.drop_objection(this, "scoreboard: idle or timed out");
  end join_none
endfunction
```

If the latency is bounded and known, `phase.get_objection().set_drain_time(this, 30ns)` in the test is a simpler alternative: after the last drop the phase waits that long, and a new raise cancels the end (`uvm_objection.svh`). The experiment above shows both rules and what each one misses.

### 4. Forgetting the `copy()` Before Mutation

When predicting, always `copy()` the input transaction before modifying it. Otherwise you corrupt the original transaction still held by the monitor or sequence:

```systemverilog
// ❌ WRONG: mutates the original transaction
expected = input_txn;
expected.result = input_txn.a + input_txn.b;

// ✅ CORRECT: work on an independent copy
expected = new();
expected.copy(input_txn);
expected.result = input_txn.a + input_txn.b;
```
