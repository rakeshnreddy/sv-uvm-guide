## Quick Take

- **What it is:** A **scoreboard** is the part of a testbench (TB) that decides, transaction by transaction, whether the design under test (DUT) did the right thing. It receives two streams: **expected items**, which a **reference model** computes from the inputs the DUT accepted, and **actual items**, which an output monitor observed. It pairs them, compares them by value, and at the end of the test counts everything that was never paired. IEEE 1800.2-2020 gives it a base class, `uvm_scoreboard` (§13.6), that adds no behaviour: every rule on this page is code you write.
- **Why it matters:** A scoreboard is how a regression of millions of transactions can say "fail" without anyone opening a waveform. It is also the easiest place in a UVM environment to build a bench that passes when it should fail: a scoreboard that compares handles instead of values, that saw zero transactions, that never looks at what was left over, or that stops waiting before the last response arrives prints "0 mismatches" just as happily as a correct one. This module is the gate of milestone M3: a reference-model scoreboard, in order and keyed, with end-of-test accounting.
- **The Analogy:** An exam marker with an answer key. The key is written from the questions each student actually received (prediction from what the input monitor saw, not from what the teacher meant to hand out). Each answer sheet is matched to its question by question number (the key), so sheets handed in out of order still meet the right answer. At the end, the marker counts questions with no answer and answer sheets with no question (accounting). *Where it breaks:* the person who wrote the key can misread a question in exactly the way the student did, so the marker approves a wrong answer (a **common-mode error**: the model and the DUT share one misreading of the specification). And real answers arrive late, so the marker must know when to stop waiting without a fixed timer: a rule this page builds from objections.

**You will be able to:**
1. **Design** a scoreboard for a DUT: place the predictor and its reference model, choose analysis imps (`` `uvm_analysis_imp_decl ``) or analysis FIFOs, and justify where prediction happens.
2. **Write** an in-order scoreboard and a keyed out-of-order scoreboard (one queue per key, safe when a key is reused) that compare by value with a checked `compare()`.
3. **Implement** end-of-test accounting: report missing and unexpected items in `check_phase`, fail a run with zero traffic, hold the run until outstanding items drain without a fixed delay, and print `SCB_SUMMARY matches=N mismatches=0 pending=0`.
4. **Debug** false passes and false failures caused by aliasing, monitor sampling time, items in flight at the end of the test, reset and expected errors.
5. **Choose** a reference-model style (a SystemVerilog model, a predictor component, or a DPI-C model) for a given DUT and team.

## Build Your Mental Model

You already know the pieces from Tier 2. A **monitor** watches the pins and publishes one transaction object per observed transfer through its **analysis port**, whose `write()` is a zero-time function call delivered to every connected subscriber ([I-UVM-2B](/curriculum/T2_Intermediate/I-UVM-2B_TLM_Connections/index)). The **run phase** ends when no **objection** (a component's "I am still busy" count on a phase) is raised, and afterwards `extract_phase`, `check_phase` and `report_phase` run in that order ([I-UVM-1C](/curriculum/T2_Intermediate/I-UVM-1C_UVM_Phasing/index)). `compare()` compares two objects field by field through a comparer policy ([I-UVM-4](/curriculum/T2_Intermediate/I-UVM-4_UVM_Policy_Classes/index)). [I-UVM-3C](/curriculum/T2_Intermediate/I-UVM-3C_First_Complete_Testbench/index) put them together in a single-agent bench whose scoreboard read one stream. This lesson is about everything that bench did not need: two streams, a reference model, ordering, waiting, and the ways a scoreboard lies.

Four words used throughout:
- **Expected item:** a transaction the reference model says the DUT should produce.
- **Actual item:** a transaction the output monitor saw the DUT produce.
- **Predictor:** the component that turns each observed input into an expected item by calling the reference model. (A **register predictor**, `uvm_reg_predictor`, is a different thing that updates a register model; see [A-UVM-4B](/curriculum/T3_Advanced/A-UVM-4B_Advanced_RAL_Techniques/index).)
- **Pending:** an expected item not yet matched, or an actual item not yet matched. At the end of a passing test, nothing is pending.

### Three jobs: observe, predict, compare and account

Every scoreboard does the same three jobs, whatever the protocol:
1. **Observe.** Two passive monitors watch the two sides of the DUT: one publishes each request the DUT **accepted**, the other each response it **produced**. The scoreboard never touches a signal.
2. **Predict.** A predictor feeds each accepted request to the reference model and publishes the expected item.
3. **Compare and account.** The scoreboard pairs each actual item with the right expected item, compares them by value, counts matches and mismatches, and at the end of the test reports anything still pending.

`uvm_scoreboard` is declared `virtual class uvm_scoreboard extends uvm_component` and adds no members (IEEE 1800.2-2020 §13.6.1). Extending it tells readers and tools what the component is for; it does not compare, store or report anything for you.

Three rules follow from the picture:
- **Predict from what the DUT accepted, not from what the stimulus intended.** The predictor subscribes to `in_mon`, not to the sequence or the driver. A request that was back-pressured, withdrawn or changed on its way to the pins is not what the DUT must answer; only the input monitor knows what it really accepted.
- **Predict early.** The expected item exists from the moment the request is accepted, before any response can arrive. That makes keyed matching, latency checks and "this response matches nothing" possible. Predicting late (computing the expected value only when the response arrives) works for a simple in-order stream, and nothing more.
- **The scoreboard lives in the env, never in an agent.** An agent is reusable verification IP for one interface ([A-UVM-7](/curriculum/T3_Advanced/A-UVM-7_VIP_Construction/index)); the scoreboard knows what this particular DUT computes, so it belongs to the environment that knows the DUT.

### Feeding the scoreboard: two imps or two FIFOs

A scoreboard has two inputs, and a class has only one method named `write`. [I-UVM-2B](/curriculum/T2_Intermediate/I-UVM-2B_TLM_Connections/index#two-input-scoreboards) showed the two standard ways round that. Here is how they apply to scoreboards.

**Form A: two imps with `` `uvm_analysis_imp_decl ``** (IEEE 1800.2-2020 Annex B.5.22). Each macro declares a new imp class whose `write()` calls a method with your suffix. The scoreboard's matching then runs inside those calls, in zero time:

```systemverilog
// snippet: form A, the form used in Make It Work
`uvm_analysis_imp_decl(_exp)   // declares uvm_analysis_imp_exp: write() calls write_exp()
`uvm_analysis_imp_decl(_act)   // declares uvm_analysis_imp_act: write() calls write_act()

class alu_scoreboard extends uvm_scoreboard;
  uvm_analysis_imp_exp #(alu_item, alu_scoreboard) exp_imp;   // from prd.ap
  uvm_analysis_imp_act #(alu_item, alu_scoreboard) act_imp;   // from out_mon.ap
  // write_exp() stores the prediction; write_act() pairs, compares and counts.
endclass
```

**Form B: two `uvm_tlm_analysis_fifo`s and a `run_phase` thread** (§12.2.8.3). Each FIFO accepts every `write()` at once (it is unbounded, and its `write()` is a `try_put` that always succeeds), and the scoreboard's own thread takes items out with `get()`, a task that may wait. The scoreboard exposes two `uvm_analysis_export`s and connects them to its private FIFOs, so the env never reaches inside it:

```systemverilog
// snippet: form B, used by the in-order scoreboard below and by the lab
uvm_analysis_export   #(alu_item) exp_export, act_export;  // the env connects here
uvm_tlm_analysis_fifo #(alu_item) exp_fifo,   act_fifo;    // private buffers
// connect_phase: exp_export.connect(exp_fifo.analysis_export);
//                act_export.connect(act_fifo.analysis_export);
```

| Choose | When |
|---|---|
| Form A, two imps | Every action is zero-time: store a prediction, look it up, compare, count. You need a **held queue** for an actual that arrives in the same time step as, but before, its prediction (traced below). |
| Form B, two FIFOs and a thread | A check must wait: for a sideband signal, a clock, a model that consumes time, or the other stream. Paired in-order FIFOs are race-free without a held queue; a design with **two** threads (one per FIFO) needs a held queue too. |

Both forms are legal and common; the visual later on this page and Make It Work use form A, and the lab uses form B, so you practise both. A graded wiring exercise, [scoreboard connector](/exercises/scoreboard-connector), drills the connections; it connects the env straight to the FIFOs' `analysis_export`s, which is legal, while this page prefers exports on the scoreboard so it can change how it buffers without touching the env.

**One rule for both forms: never modify what you receive.** `write()` hands the same handle to every subscriber, and "an implementation of the `write(T)` shall not modify the value passed to it" (§12.2.10.2). A scoreboard that changes a field of a received item corrupts what the coverage collector and every other subscriber see. Predict into a copy, and store items as received.

### The reference model: three styles

A **reference model** is an executable, transaction-level model of what the DUT must compute, written from the specification by someone other than the RTL designer. It is not the specification, and it is not "golden": that word is often used for it, but the model can share the RTL author's misreading (the common-mode error from the analogy). Its value comes from being simple enough to trust more than the RTL. If your model is as complex as the DUT, you have duplicated the bug surface.

| Style | What it is | Choose it when | Watch out for |
|---|---|---|---|
| **SystemVerilog function or class** | A pure function such as `alu_model(op, a, b)` in the package, called by the predictor | The behaviour is small, stateless, and owned by the verification team | Copying the RTL's structure instead of the specification's wording |
| **Predictor component** | A `uvm_subscriber` (§13.9) that receives observed inputs, keeps any state the model needs (a memory image, a sequence counter), calls the model, and publishes expected items on its own analysis port | The model has state, needs several inputs, or should be reusable and swappable by the factory | Keeping state in step with the DUT across reset (see False passes) |
| **DPI-C model** | An `import "DPI-C"` function or task that calls an existing C or C++ model, called from the predictor | Architects already maintain a bit-accurate model (a CPU instruction-set simulator, a codec, a DSP datapath) | Marshalling cost per call; a stateful C model must be called in DUT order; `pure` is legal only for a nonvoid function with only input arguments and no side effects (IEEE 1800-2023 §35.5.2) |

The two SystemVerilog styles combine in Make It Work: `alu_model()` is the model, `alu_predictor` is the component that calls it. A DPI-C variant would change one line of the predictor:

```systemverilog
// snippet: the same model through DPI-C. pure: a nonvoid function, inputs only,
// no side effects (IEEE 1800-2023 §35.5.2); use context if the C code calls
// exported SystemVerilog (§35.5.3).
import "DPI-C" pure function int unsigned alu_ref_c(input int unsigned op,
                                                    input int unsigned a,
                                                    input int unsigned b);
// in alu_predictor::write(): exp.result = 16'(alu_ref_c(t.op, t.a, t.b));
```

**An illegal input has no prediction.** If the model receives an opcode the specification does not define, it must say so (`'x`, or an error), never return a plausible value such as 0 that a broken DUT might also produce.

### When to predict, and when the monitors sample

The DUT in this lesson, `alu_pipe`, accepts one request per clock and returns its result two rising edges later, in request order, with the request's `tag` (a 4-bit label the DUT copies from input to output). Both monitors sample through the clocking block `mon_cb`, whose inputs are sampled just before each rising edge, as the DUT's own flip-flops see them (`default input #1step`; IEEE 1800-2023 §14.13).

**Predict before you look.** Requests arrive back to back at edges 1, 2 and 3. A bench with a single monitor reads `a`, `b` and `op` from the bus at the edge where it sees `valid_out` high, and publishes them with `result`. Which request's inputs does it pair with the first result? Decide, then read the waveform.

**What the waveform shows.** The single monitor pairs R1 with A3: by the time a result appears, the request bus has moved on. ### In-order matching and comparing by value

When the DUT answers every request in request order, the matching rule is simple: the oldest expected item is the only legal partner for the next actual item. Here is the form-B version, built on two FIFOs:

```systemverilog
// snippet: an in-order scoreboard (form B); alu_item is defined in Make It Work
class alu_inorder_sb extends uvm_scoreboard;
  `uvm_component_utils(alu_inorder_sb)

  uvm_analysis_export   #(alu_item) exp_export, act_export;
  uvm_tlm_analysis_fifo #(alu_item) exp_fifo,   act_fifo;
  int unsigned n_match, n_mismatch;

  function new(string name, uvm_component parent);
    super.new(name, parent);
  endfunction

  virtual function void build_phase(uvm_phase phase);
    super.build_phase(phase);
    exp_export = new("exp_export", this);
    act_export = new("act_export", this);
    exp_fifo   = new("exp_fifo", this);
    act_fifo   = new("act_fifo", this);
  endfunction

  virtual function void connect_phase(uvm_phase phase);
    super.connect_phase(phase);
    exp_export.connect(exp_fifo.analysis_export);
    act_export.connect(act_fifo.analysis_export);
  endfunction

  virtual task run_phase(uvm_phase phase);
    alu_item exp, act;
    forever begin
      exp_fifo.peek(exp);          // wait for a prediction, but leave it in the FIFO
      act_fifo.get(act);           // wait for the DUT's answer
      void'(exp_fifo.try_get(exp));  // only now consume the prediction
      if (exp.compare(act)) n_match++;                   // by value, result checked
      else begin
        n_mismatch++;
        `uvm_error("SCB/MISMATCH", $sformatf("expected %s, got tag=%0d result=%0d",
                   exp.convert2string(), act.tag, act.result))
      end
    end
  endtask

  // After run_phase: anything left in a FIFO was never compared.
  virtual function void check_phase(uvm_phase phase);
    super.check_phase(phase);
    if (exp_fifo.used() != 0)
      `uvm_error("SCB/MISSING", $sformatf("%0d predictions never answered",
                                          exp_fifo.used()))
    if (act_fifo.used() != 0)
      `uvm_error("SCB/UNEXPECTED", $sformatf("%0d results matched no prediction",
                                             act_fifo.used()))
    if (n_match + n_mismatch == 0)
      `uvm_error("SCB/NO_TRAFFIC", "no result was compared: this run proves nothing")
  endfunction
endclass
```

**Why `peek`, then `get`, then `try_get`.** If the thread took the prediction out first and then waited for an answer that never came, the prediction would sit in a local variable when `run_phase` ended and its thread was killed; `check_phase` would find both FIFOs empty and see nothing wrong. Peeking keeps the prediction in `exp_fifo` until its answer is in hand. Trace a DUT that drops the last of three responses:

| Event | `exp_fifo` | `act_fifo` | Thread | Counts |
|---|---|---|---|---|
| Predictions E1, E2, E3 arrive | E1 E2 E3 | empty | peeks E1, waits in `act_fifo.get()` | 0 / 0 |
| R1 arrives | E1 E2 E3 | R1 | gets R1, takes E1, compares: match; peeks E2 | 1 / 0 |
| R2 arrives | E2 E3 | R2 | gets R2, takes E2: match; peeks E3, waits | 2 / 0 |
| (R3 never comes) run_phase ends; the thread is killed | E3 | empty | killed in `get()` | 2 / 0 |
| `check_phase` | `used()` = 1 | 0 | | `SCB/MISSING`: 1 prediction never answered |

Without the `check_phase`, this run ends with two matches, zero mismatches and `UVM_ERROR : 0`: a false pass.

**Comparing by value.** `act == exp` on two class handles is true only when both refer to the **same object** (IEEE 1800-2023 §8.4, §11.4.5). An expected item and an actual item are always two objects, so `==` is always false for them, whatever their fields; `compare()` is what compares values (IEEE 1800.2-2020 §5.3.9.1). Four details decide whether `compare()` protects you:
- **Check its return value.** By default a miscompare is reported as a `UVM_INFO` message with ID `MISCMP`, at verbosity `UVM_LOW`, and only the first one is shown (§16.3.5.1–§16.3.5.3). `UVM_INFO` never fails a test: if you ignore the `bit` that `compare()` returns, the test passes with miscompares in its log.
- **Compare what the output side carries.** An actual item has a tag and a result, not the operands. `alu_item::do_compare()` therefore compares `tag` and `result` only. If your item uses the `` `uvm_field_* `` macros instead, flag input-only fields `UVM_NOCOMPARE` (Annex F.2.1.9), or every compare fails on fields the output monitor never fills.
- **Compare 4-state values with `!==` semantics.** `compare_field_int` uses case inequality, so an X on `result` is a miscompare; a hand-written `act.result != exp.result` would give X, which an `if` treats as false, and hide it.
- **Use your own comparer when you want detail.** Make It Work passes a scoreboard-owned `uvm_comparer` to `compare()` and puts `get_miscompares()` (§16.3.3.8) into its own `` `uvm_error ``.

### Out-of-order matching: one ordered queue per key

Pipelined, multi-bank or arbitrating DUTs can complete requests out of order. What is legal is the protocol's business; how a particular DUT uses that freedom is its design policy. AXI is the usual example: transactions with the **same** ID must complete in request order, and transactions with **different** IDs have no ordering restriction (Arm IHI0022E §A5.1); how deeply a slave reorders read data is a fixed property of its design (§A5.3.1). The scoreboard encodes the protocol rule, so it accepts every legal policy; a stricter promise in the DUT's own specification ("this block never reorders") is a separate check you can switch on.

So the matching structure is **one ordered queue per key**: an associative array of queues, `exp_q[tag][$]` (IEEE 1800-2023 §7.8, §7.10). A response with key *k* may only match the oldest pending prediction with key *k*. Three tempting alternatives each fail:
- **One queue for everything** raises false mismatches as soon as the DUT legally answers a later key first.
- **One slot per key** (`expected[id] = item`) overwrites a prediction when two requests with the same key are outstanding, which is normal in AXI: the first response is compared with the second prediction and the first prediction is lost.
- **Search any pending item that compares equal** never raises a false alarm, but lets a same-key reorder (a real protocol violation) pass, and costs a full search per response.

The key must be something the DUT carries from input to output: the AXI ID, a tag, an address. A sequence number that only the testbench knows works only if the DUT returns it. Here is the keyed matching in form A, exactly as the Make It Work scoreboard has it:

```systemverilog
// snippet: alu_scoreboard's matching (full class in Make It Work)
virtual function void write_exp(alu_item t);      // a prediction arrives
  foreach (held_q[i])
    if (held_q[i].tag == t.tag) begin             // its actual came first
      compare_pair(t, held_q[i]);
      held_q.delete(i);
      return;
    end
  exp_q[t.tag].push_back(t);                      // oldest first, per tag
  outstanding++;
  fork watch(t); join_none                        // per-item latency watchdog
endfunction

virtual function void write_act(alu_item t);      // an actual arrives
  if (!exp_q.exists(t.tag) || exp_q[t.tag].size() == 0) begin
    held_q.push_back(t);                          // early or extra: decide later
    return;
  end
  compare_pair(exp_q[t.tag].pop_front(), t);
  outstanding--;
endfunction
```

**The race the held queue removes.** Both `write` calls happen inside monitor threads. When a request and its response are observed in the **same time step** (a DUT with zero-cycle latency, or monitors on different clock phases), nothing in IEEE 1800-2023 says which monitor runs first. If the output monitor wins, `write_act()` finds no prediction yet. Reporting "unexpected" then would be a false error. Trace a response and its prediction for tag 3 that land in one time step, output first:

| Step (one time step) | `exp_q[3]` | `held_q` | What happens |
|---|---|---|---|
| `out_mon` writes actual, tag 3 | empty | `[act3]` | no prediction yet: held |
| `prd` writes expected, tag 3 | empty | `[act3]` | `write_exp()` finds `act3` in `held_q`: compare, match, remove |
| end of test, `check_phase` | empty | empty | nothing pending |

If the prediction never comes, the held actual is still in `held_q` at `check_phase`, which reports it as `SCB/UNEXPECTED`. That is also how an **extra** response is caught.

**Key reuse.** Because each key has a queue, two outstanding requests with the same key are fine: they are answered in order, and each response pops the oldest. The kata in Practice & Reinforce makes you watch a one-slot map fail on exactly that.

- "No drain" ends `run_phase` when the test drops its objection, before the last responses arrive, so `check_phase` reports correct responses as missing (setting 5). A drain time works only when the latency is known; waiting until idle works for any latency.

### End-of-test accounting and draining

A scoreboard's verdict is only as good as its last minute. Three questions must be answered after `run_phase` ends, in `check_phase`, the phase IEEE 1800.2-2020 provides for exactly this (§9.8.1.7):
1. **Missing:** is any prediction still unanswered? Each one is `SCB/MISSING`.
2. **Unexpected:** is any actual still unmatched? Each one is `SCB/UNEXPECTED`.
3. **Zero traffic:** was anything compared at all? If not, `SCB/NO_TRAFFIC`. Zero mismatches out of zero compares proves nothing: it is also what a scoreboard prints when its port was never connected or the run ended at 0 ns.

Then `report_phase` (§9.8.1.8) prints one line a regression script can grep, in this course's milestone format: `SCB_SUMMARY matches=N mismatches=M pending=P`, where pending counts the predictions never answered plus the actuals never matched. The scoreboard **reports**; the report server **decides**. Never print "TEST PASSED" from a scoreboard: it would print after another component's error, or after a `check_phase` error of your own. A run passes when the report summary shows `UVM_ERROR :    0` and `UVM_FATAL :    0` and the `SCB_SUMMARY` line has a non-zero match count and `mismatches=0 pending=0` ([I-UVM-1D](/curriculum/T2_Intermediate/I-UVM-1D_Reporting_and_Run_Control/index)).

**Draining: keep the run alive until the last response is in.** The test drops its objection when its sequence finishes, while the last responses are still inside the DUT. If `run_phase` ends then, those responses are never observed and `check_phase` reports correct work as missing. A fixed delay is a guess: too short tomorrow, wasted time today. Instead the scoreboard, the one component that knows what is outstanding, holds the phase itself through `phase_ready_to_end` (§13.1.4.3.2):

```systemverilog
// snippet: alu_scoreboard's drain (full class in Make It Work)
virtual function void phase_ready_to_end(uvm_phase phase);
  // Called for run and for every run-time phase: hold only run, and only once,
  // because UVM calls this again after our own drop.
  if (phase.get_name() != "run" || drained || outstanding == 0) return;
  drained = 1;
  phase.raise_objection(this, "scoreboard: responses outstanding");
  fork                                   // a function cannot wait: fork the wait
    begin
      fork
        wait (outstanding == 0);         // every prediction answered
        #(max_latency);                  // watchdog: a lost response must not hang
      join_any
      disable fork;
      if (outstanding != 0)
        `uvm_warning("SCB/DRAIN_TIMEOUT", "check_phase reports what is still pending")
      phase.drop_objection(this, "scoreboard: idle or timed out");
    end
  join_none
endfunction
```

Why each line is there:
- **When it is called.** UVM calls `phase_ready_to_end` on every component once all objections to the phase and its siblings have dropped. A component that still has work may raise the phase's objection there and must drop it when ready (§13.1.4.3.2). In uvm-core 2020.3.1 it is called for `run` and for each run-time phase, hence the `get_name()` guard; without it, a one-shot `drained` flag could be used up by an earlier run-time phase.
- **Why only once.** After the scoreboard's drop, UVM calls `phase_ready_to_end` again, up to `phase.get_max_ready_to_end_iterations()` times (§9.3.1.3.4; the default is 20, §9.3.1.3.5). The `drained` flag makes the second call return at once.
- **Why `fork ... join_none`.** `phase_ready_to_end` is a function, and a function may not wait, but it may start a background process with `fork ... join_none` (IEEE 1800-2023 §13.4.4).
- **Why `wait (outstanding == 0)` works.** A `wait` re-evaluates its condition only when an operand changes (§9.4.3). `outstanding` is a class member that `write_exp()` and `write_act()` update, so the wait wakes on the right event. `wait (exp_fifo.used() == 0)` would not be allowed: only non-virtual methods (and built-in methods of arrays and queues) may appear in an event expression (§9.4.2), and `used()` is virtual. That is why form A counts `outstanding` where a prediction enters the scoreboard.
- **Why the watchdog.** If a response is lost, `outstanding` never reaches 0. The watchdog drops the objection after `max_latency` with a warning, and `check_phase` then reports the missing item by name.
- **A deliberate exception.** This course's code style says objections are raised in tests and top sequences only. A scoreboard's bounded drain in `phase_ready_to_end` is the standard exception: the scoreboard is the only component that knows what is outstanding.

**The simpler alternative, when latency is fixed.** If the DUT's latency is bounded and known, the test can set a **drain time** on the phase's objection: `phase.get_objection().set_drain_time(this, 30ns)`. After the last drop, the phase waits that long before ending, and a new raise during the wait cancels it (§10.5.1.3.7). It is a guess dressed as a setting, so prefer waiting until idle whenever latency varies. Never put an unconditional `#100ns` inside `phase_ready_to_end`: UVM calls it again after each drop, so it adds up to 20 × 100 ns = 2 µs to every test and still never checks that anything was pending.

**Latency and timeouts: do not wait for the end to find a hang.** A response that never comes is reported by `check_phase`, but only at the end, and only if the run ends normally. Make It Work adds two run-time guards:
- **A per-item latency watchdog.** `write_exp()` forks `watch(t)`, which waits `max_latency` and reports `SCB/LATE` if that very object (compared with `==`, which is right here: the question is identity) is still queued. The error names the request and the time it went missing, while the run continues.
- **A global timeout.** The test calls `uvm_root::get().set_timeout(1ms)` (Annex F.7.3.3). If the run hangs, UVM ends it with `UVM_FATAL [PH_TIMEOUT]`. A fatal skips `check_phase` and `report_phase` entirely; in uvm-core 2020.3.1 the run ends through `uvm_root::die()`, which calls every component's `pre_abort()` first (§13.1.4.6). `alu_scoreboard::pre_abort()` prints its `SCB_SUMMARY` there, so even a killed run leaves its counts in the log.

### False passes and false failures

A **false pass** is a run that reports success although the DUT is wrong; a **false failure** is a run that reports errors although the DUT is right. Both waste time, but false passes ship bugs. Use this table as a debugging checklist: start from what the log shows.

| Symptom in the log | Likely cause | Fix |
|---|---|---|
| `SCB_SUMMARY matches=0 mismatches=0 pending=0`, `UVM_ERROR : 0` | Zero traffic: an unconnected analysis port, a monitor waiting on the wrong signal, a run that ended at 0 ns | Make zero compares an error (`SCB/NO_TRAFFIC`); then fix the connection or the objection |
| Clean log, but a known-bad DUT also passes | No leftover check: dropped responses and stuck predictions are never counted | `check_phase` reports `SCB/MISSING` and `SCB/UNEXPECTED`; prove it with a mutant (Make It Work) |
| `[MISCMP] Miscompare for ...` as `UVM_INFO`, yet `UVM_ERROR : 0` | The return value of `compare()` is ignored; a miscompare is only `UVM_INFO` by default | `if (!exp.compare(act, cmp))` raise `` `uvm_error ``; put `cmp.get_miscompares()` in the message |
| Every compare fails on fields the output never carries | `compare()` covers input-only fields | Compare only output fields in `do_compare`, or flag inputs `UVM_NOCOMPARE` |
| A burst of `SCB/MISMATCH` as soon as traffic overlaps, against a DUT the designers say is right | In-order matching on a DUT that legally reorders | Match per key, with one queue per key |
| Mismatches only when two requests share an ID | One slot per key overwrote a pending prediction | One queue per key |
| `SCB/MISSING` for the last few requests on a correct DUT | `run_phase` ended before they arrived: no drain, or a drain time shorter than the latency | Hold the phase in `phase_ready_to_end` until `outstanding == 0` |
| Every expected item shows the last transaction's data | A monitor reuses one object, and the scoreboard stored handles to it | The monitor creates a new item per transaction (below) |
| Results paired with the wrong inputs, but only under back-to-back traffic | One monitor samples inputs at the output edge, or samples raw signals on the wrong edge | One monitor per side, each sampling through a clocking block (the waveform above) |
| A burst of `SCB/MISSING` or `SCB/MISMATCH` right after a mid-test reset | Predictions for requests the reset discarded are still queued | Flush on reset and report the flushed items separately (below) |
| `SCB/MISMATCH` on every request a test injects as illegal on purpose | The model predicts the normal result for an illegal request | Predict the specified error response; never demote `SCB/*` errors for the whole test |

**Aliasing: one object, many handles.** An analysis FIFO, a queue and a `write()` all store or pass **handles**, never copies. A monitor that creates its item once, before its loop, and overwrites it for every transfer publishes the same object again and again; every handle the scoreboard stored then shows the last transfer's values. Try the model below: it is the same bug, with a plain queue in place of the analysis FIFO. **Predict** which line causes it before you click.

**What it showed, in UVM terms.** Only one `txn` object existed, so every stored handle pointed at it. In a UVM bench the rule has two halves: the **publisher** creates a new item for every transaction (`alu_in_mon` and `alu_out_mon` call `alu_item::type_id::create()` inside their loops) and never touches it after `write()`; the **subscriber** never modifies what it receives (§12.2.10.2) and predicts into a copy (`alu_predictor` calls `clone()`). [I-SV-1](/curriculum/T2_Intermediate/I-SV-1_OOP/copying-and-cloning) explains shallow and deep copies.

**Reset in the middle of a test (basic version).** When reset is asserted, the DUT discards the requests in flight, so their predictions will never be answered. Without care, `check_phase` reports them as missing on a correct DUT. The minimum a scoreboard needs is a flush, called when a reset monitor sees `rst_n` fall:

```systemverilog
// snippet: basic reset handling for alu_scoreboard (the full strategy,
// including when to stop predicting, is covered in A-UVM-9)
int unsigned n_flushed;
function void flush_on_reset();
  int unsigned flushed = outstanding + held_q.size();
  exp_q.delete();               // predictions the reset discarded
  held_q.delete();
  outstanding = 0;
  n_flushed += flushed;         // report these in the summary, never as MISSING
  `uvm_info("SCB/RESET", $sformatf("reset: %0d pending items flushed", flushed),
            UVM_LOW)
endfunction
```

A form-B scoreboard flushes its FIFOs with `flush()` (IEEE 1800.2-2020 §12.2.8.2.6). The per-item `watch()` processes of flushed items find nothing queued and stay silent.

**Expected errors (basic version).** When a test drives an illegal request on purpose and the specification says the DUT answers with an error response, the reference model predicts that error response, and the scoreboard compares as usual. The two shortcuts are both false passes waiting to happen: turning `SCB/MISMATCH` into a warning for the whole test hides every other bug in it, and skipping prediction for "error tests" leaves the error path unchecked. The full strategy (error catchers, demoting one expected message) is in [A-UVM-9: Reset Handling and Error Injection](/curriculum/T3_Advanced/A-UVM-9_Reset_and_Error_Injection/index).

### Recap

- A scoreboard observes two streams, predicts from what the DUT accepted, compares by value with a checked `compare()`, and accounts for everything at the end (objective 1).
- In order: the oldest prediction is the only legal partner. Out of order: one ordered queue per key that the DUT carries end to end, plus a held queue for actuals that beat their prediction (objective 2).
- `check_phase` reports `SCB/MISSING`, `SCB/UNEXPECTED` and `SCB/NO_TRAFFIC`; `report_phase` prints `SCB_SUMMARY`; the scoreboard holds `run_phase` in `phase_ready_to_end` until nothing is outstanding, with a watchdog, never a fixed delay (objective 3).
- False passes come from zero traffic, unchecked leftovers, ignored `compare()` results and aliasing; false failures from wrong ordering assumptions, monitors sampling at the wrong time, ending too early, reset and unpredicted errors (objective 4).
- The reference model is a SystemVerilog function, a predictor component, or a DPI-C call, chosen by state, ownership and existing models (objective 5).

## Make It Work

### The complete bench

The block below is one compile-ready file: the DUT, its interface, a package with every class, and `tb_top`. It is the bench in the architecture picture. Three `` `ifdef `` switches plant bugs in the DUT so you can prove the scoreboard fails when it should. The code has been checked by reading against IEEE 1800-2023 and uvm-core 2020.3.1; no simulator run is behind this page.

```systemverilog
// compile: alu_sb_tb.sv (DUT, interface, package and top in one file)
// Plant a bug with +define+MUT_DROP, +define+MUT_SUB or +define+MUT_EXTRA.

// ------------------------------------------------------------------ DUT
// Two-stage ALU: one request per clock; the result appears two rising edges
// later, in request order, with the request's tag.
module alu_pipe (
  input  logic        clk,
  input  logic        rst_n,      // synchronous, active low
  input  logic        valid_in,
  input  logic [3:0]  tag_in,     // returned unchanged with the result
  input  logic [1:0]  op,         // 0 ADD, 1 SUB, 2 MUL, 3 AND
  input  logic [7:0]  a,
  input  logic [7:0]  b,
  output logic        valid_out,
  output logic [3:0]  tag_out,
  output logic [15:0] result
);
  timeunit 1ns; timeprecision 1ps;

  logic        v1;
  logic [3:0]  tag1;
  logic [15:0] res1, f;
  logic [4:0]  n_acc;       // requests accepted so far (MUT_DROP uses it)
  logic        dup_done;    // MUT_EXTRA uses it

  always_comb begin
    unique case (op)
      2'd0:    f = a + b;            // 16-bit context keeps the carry
`ifdef MUT_SUB
      2'd1:    f = a + b;            // planted bug: SUB executes as ADD
`else
      2'd1:    f = a - b;            // wraps modulo 2**16
`endif
      2'd2:    f = a * b;
      2'd3:    f = {8'h00, a & b};
      default: f = 'x;               // op is X or Z
    endcase
  end

  always_ff @(posedge clk) begin
    if (!rst_n) begin
      v1        <= 1'b0;
      valid_out <= 1'b0;
      n_acc     <= '0;
      dup_done  <= 1'b0;
    end else begin
      // Stage 1: register the request and its result.
      v1   <= valid_in;
      tag1 <= tag_in;
      res1 <= f;
      if (valid_in) n_acc <= n_acc + 5'd1;
`ifdef MUT_DROP
      if (valid_in && n_acc == 5'd9) v1 <= 1'b0;   // planted bug: request 10 is lost
`endif
      // Stage 2: present the result; tag and result hold while idle.
      valid_out <= v1;
      if (v1) begin
        tag_out <= tag1;
        result  <= res1;
      end
`ifdef MUT_EXTRA
      // Planted bug: the first result followed by an idle cycle is sent twice.
      if (!v1 && valid_out && !dup_done) begin
        valid_out <= 1'b1;
        dup_done  <= 1'b1;
      end
`endif
    end
  end
endmodule

// ------------------------------------------------------------ interface
interface alu_if (input logic clk, input logic rst_n);
  timeunit 1ns; timeprecision 1ps;

  logic        valid_in;
  logic [3:0]  tag_in;
  logic [1:0]  op;
  logic [7:0]  a, b;
  logic        valid_out;
  logic [3:0]  tag_out;
  logic [15:0] result;

  // The driver's view: drives land just after the edge, so alu_pipe samples
  // them at the next one.
  clocking drv_cb @(posedge clk);
    default input #1step output #0;
    output valid_in, tag_in, op, a, b;
    input  rst_n;
  endclocking

  // The monitors' view: everything sampled just before the edge, as the
  // DUT's flip-flops see it.
  clocking mon_cb @(posedge clk);
    default input #1step;
    input valid_in, tag_in, op, a, b, valid_out, tag_out, result, rst_n;
  endclocking
endinterface

// -------------------------------------------------------------- package
package alu_pkg;
  timeunit 1ns; timeprecision 1ps;
  import uvm_pkg::*;
  `include "uvm_macros.svh"

  typedef enum logic [1:0] {ALU_ADD, ALU_SUB, ALU_MUL, ALU_AND} alu_op_e;

  // The reference model: what the specification says each operation returns.
  function automatic logic [15:0] alu_model(alu_op_e op,
                                            logic [7:0] a, logic [7:0] b);
    case (op)
      ALU_ADD: return 16'(a) + 16'(b);
      ALU_SUB: return 16'(a) - 16'(b);   // wraps modulo 2**16, as specified
      ALU_MUL: return 16'(a) * 16'(b);
      ALU_AND: return {8'h00, a & b};
      default: return 'x;                // an X opcode has no defined result
    endcase
  endfunction

  class alu_item extends uvm_sequence_item;
    `uvm_object_utils(alu_item)

    logic      [3:0]  tag;           // set by the sequence, returned by the DUT
    rand alu_op_e     op;
    rand logic [7:0]  a, b;
    logic      [15:0] result;        // predicted (expected) or observed (actual)
    int unsigned      idle_cycles;   // driver knob: idle cycles after this request

    function new(string name = "alu_item");
      super.new(name);
    endfunction

    virtual function void do_copy(uvm_object rhs);
      alu_item rhs_;
      super.do_copy(rhs);
      if (!$cast(rhs_, rhs)) `uvm_fatal("ITEM/COPY", "rhs is not an alu_item")
      tag    = rhs_.tag;
      op     = rhs_.op;
      a      = rhs_.a;
      b      = rhs_.b;
      result = rhs_.result;
    endfunction

    // Compare only what the output side carries: an actual has no op, a or b.
    virtual function bit do_compare(uvm_object rhs, uvm_comparer comparer);
      alu_item rhs_;
      if (!$cast(rhs_, rhs)) return 0;
      do_compare  = super.do_compare(rhs, comparer);
      do_compare &= comparer.compare_field_int("tag", tag, rhs_.tag, 4);
      do_compare &= comparer.compare_field_int("result", result, rhs_.result, 16);
    endfunction

    virtual function string convert2string();
      return $sformatf("tag=%0d %s a=%0d b=%0d result=%0d",
                       tag, op.name(), a, b, result);
    endfunction
  endclass

  class alu_seq extends uvm_sequence #(alu_item);
    `uvm_object_utils(alu_seq)

    int unsigned num_items = 20;

    function new(string name = "alu_seq");
      super.new(name);
    endfunction

    virtual task body();
      for (int unsigned i = 0; i < num_items; i++) begin
        alu_item it = alu_item::type_id::create("it");
        start_item(it);
        if (!it.randomize()) `uvm_fatal("RAND", "alu_item randomization failed")
        it.tag         = 4'(i);             // the DUT returns it: the match key
        it.idle_cycles = (i == 9) ? 1 : 0;  // one gap mid-stream, as real traffic has
        finish_item(it);
      end
    endtask
  endclass

  class alu_driver extends uvm_driver #(alu_item);
    `uvm_component_utils(alu_driver)

    virtual alu_if vif;

    function new(string name, uvm_component parent);
      super.new(name, parent);
    endfunction

    virtual function void build_phase(uvm_phase phase);
      super.build_phase(phase);
      if (!uvm_config_db#(virtual alu_if)::get(this, "", "vif", vif))
        `uvm_fatal("NOVIF", "virtual alu_if 'vif' is not set for the driver")
    endfunction

    virtual task run_phase(uvm_phase phase);
      vif.drv_cb.valid_in <= 1'b0;          // idle the bus from the first edge
      do @(vif.drv_cb); while (vif.drv_cb.rst_n !== 1'b1);
      forever begin
        seq_item_port.get_next_item(req);
        vif.drv_cb.valid_in <= 1'b1;
        vif.drv_cb.tag_in   <= req.tag;
        vif.drv_cb.op       <= req.op;
        vif.drv_cb.a        <= req.a;
        vif.drv_cb.b        <= req.b;
        @(vif.drv_cb);                      // alu_pipe accepts it at this edge
        vif.drv_cb.valid_in <= 1'b0;        // a following item overrides this
        repeat (req.idle_cycles) @(vif.drv_cb);
        seq_item_port.item_done();
      end
    endtask
  endclass

  // Publishes one new item for every request the DUT accepts.
  class alu_in_mon extends uvm_monitor;
    `uvm_component_utils(alu_in_mon)

    virtual alu_if vif;
    uvm_analysis_port #(alu_item) ap;

    function new(string name, uvm_component parent);
      super.new(name, parent);
    endfunction

    virtual function void build_phase(uvm_phase phase);
      super.build_phase(phase);
      ap = new("ap", this);
      if (!uvm_config_db#(virtual alu_if)::get(this, "", "vif", vif))
        `uvm_fatal("NOVIF", "virtual alu_if 'vif' is not set for in_mon")
    endfunction

    virtual task run_phase(uvm_phase phase);
      forever begin
        @(vif.mon_cb);
        if (vif.mon_cb.rst_n === 1'b1 && vif.mon_cb.valid_in === 1'b1) publish();
      end
    endtask

    protected function void publish();
      alu_item t = alu_item::type_id::create("t");   // a new object every time
      if ($isunknown({vif.mon_cb.tag_in, vif.mon_cb.op, vif.mon_cb.a, vif.mon_cb.b}))
        `uvm_error("MON/X", "valid_in is 1 but a request field is X or Z")
      t.tag = vif.mon_cb.tag_in;

    `uvm_component_utils(alu_predictor)

    virtual function void build_phase(uvm_phase phase);

    // Called inside in_mon's ap.write(), in the time step the request was
    // accepted, so the prediction exists before any result can arrive.
    virtual function void write(alu_item t);

      if (!$cast(exp, t.clone()))
        `uvm_fatal("PRD/CLONE", "clone() did not return an alu_item")
      exp.result = alu_model(t.op, t.a, t.b);   // t itself is never modified

  class alu_scoreboard extends uvm_scoreboard;
    `uvm_component_utils(alu_scoreboard)

    uvm_analysis_imp_exp #(alu_item, alu_scoreboard) exp_imp;   // from prd
    uvm_analysis_imp_act #(alu_item, alu_scoreboard) act_imp;   // from out_mon

    time max_latency = 100ns;      // the spec's bound plus margin: a knob, not a guess

    protected alu_item     exp_q[int unsigned][$];  // per tag, oldest first
    protected alu_item     held_q[$];     // actuals that arrived before a prediction
    protected uvm_comparer cmp;
    protected bit          drained;
    int unsigned outstanding;             // predictions not yet answered
    int unsigned n_match, n_mismatch;

    function new(string name, uvm_component parent);
      super.new(name, parent);
    endfunction

    virtual function void build_phase(uvm_phase phase);
      super.build_phase(phase);
      exp_imp = new("exp_imp", this);
      act_imp = new("act_imp", this);
      cmp = uvm_comparer::type_id::create("cmp");
      cmp.set_threshold(0);          // field-macro items would report every field
      cmp.set_verbosity(UVM_HIGH);   // SCB/MISMATCH below carries the detail
    endfunction

    // A prediction arrives (zero time, inside prd's ap.write()).
    virtual function void write_exp(alu_item t);
      foreach (held_q[i])
        if (held_q[i].tag == t.tag) begin    // its actual came first
          compare_pair(t, held_q[i]);
          held_q.delete(i);
          return;
        end
      exp_q[t.tag].push_back(t);
      outstanding++;
      fork watch(t); join_none               // per-item latency watchdog
    endfunction

    // An actual arrives (zero time, inside out_mon's ap.write()).
    virtual function void write_act(alu_item t);
      if (!exp_q.exists(t.tag) || exp_q[t.tag].size() == 0) begin
        held_q.push_back(t);                 // early or extra: check_phase decides
        return;
      end
      compare_pair(exp_q[t.tag].pop_front(), t);
      outstanding--;
    endfunction

    protected function void compare_pair(alu_item exp, alu_item act);
      if (exp.compare(act, cmp)) begin       // by value, and the result is checked
        n_match++;
        `uvm_info("SCB/MATCH", exp.convert2string(), UVM_HIGH)
      end else begin
        n_mismatch++;
        `uvm_error("SCB/MISMATCH", $sformatf("expected %s, got tag=%0d result=%0d; %s",
                   exp.convert2string(), act.tag, act.result, cmp.get_miscompares()))
      end
    endfunction

    // Reports a prediction that is still queued max_latency after it was made.
    protected task watch(alu_item e);
      #(max_latency);
      if (exp_q.exists(e.tag)) begin
        alu_item pend[$] = exp_q[e.tag];    // copy of the handles queued for e.tag
        foreach (pend[i])
          if (pend[i] == e)                  // == on handles: this very object
            `uvm_error("SCB/LATE", $sformatf("%s not answered within %0t",
                                             e.convert2string(), max_latency))
      end
    endtask

    virtual function void phase_ready_to_end(uvm_phase phase);
      // Called for run and for every run-time phase: hold only run, and only
      // once, because UVM calls this again after our own drop.
      if (phase.get_name() != "run" || drained || outstanding == 0) return;
      drained = 1;
      `uvm_info("SCB/DRAIN", $sformatf("holding run_phase: %0d outstanding",
                                       outstanding), UVM_MEDIUM)
      phase.raise_objection(this, "scoreboard: responses outstanding");
      fork
        begin
          fork
            wait (outstanding == 0);         // every prediction answered
            #(max_latency);                  // watchdog: a lost result must not hang
          join_any
          disable fork;
          if (outstanding != 0)
            `uvm_warning("SCB/DRAIN_TIMEOUT", $sformatf(
              "%0d outstanding after %0t; check_phase reports them",
              outstanding, max_latency))
          phase.drop_objection(this, "scoreboard: idle or timed out");
        end
      join_none
    endfunction

    // After run_phase: report everything that was never paired.
    virtual function void check_phase(uvm_phase phase);
      super.check_phase(phase);
      foreach (exp_q[tag, i])               // every key, every queued prediction
        `uvm_error("SCB/MISSING", {exp_q[tag][i].convert2string(),
                                   " was never answered"})
      foreach (held_q[i])
        `uvm_error("SCB/UNEXPECTED", $sformatf(
          "tag=%0d result=%0d matched no prediction", held_q[i].tag, held_q[i].result))
      if (n_match + n_mismatch == 0)
        `uvm_error("SCB/NO_TRAFFIC", "no result was compared: this run proves nothing")
    endfunction

    protected function string summary();
      return $sformatf("SCB_SUMMARY matches=%0d mismatches=%0d pending=%0d",
                       n_match, n_mismatch, outstanding + held_q.size());
    endfunction

    virtual function void report_phase(uvm_phase phase);
      super.report_phase(phase);
      `uvm_info("SCB_SUMMARY", summary(), UVM_NONE)
    endfunction

    // A fatal (PH_TIMEOUT, for one) skips check_phase and report_phase:
    // leave the counts in the log before the simulator stops.
    virtual function void pre_abort();
      `uvm_info("SCB_SUMMARY", {summary(), " (run aborted)"}, UVM_NONE)
    endfunction
  endclass
```

Operand values depend on the seed; the IDs, the times and the counts do not, except for `MUT_SUB`, whose number of mismatches is the number of SUB requests in your seed with `b` ≠ 0. Notice three things:
- **`MUT_DROP` is caught twice.** `SCB/LATE` names the lost request 100 ns after it was accepted, while the run continues; `SCB/MISSING` confirms it at the end. Because the scoreboard is keyed, the other 19 results still match: there is no cascade of mismatches after the lost one.
- **A SUB with `b = 0` is not caught by `MUT_SUB`.** `a - 0` equals `a + 0`, so a seed with few SUB requests, all with `b = 0`, would pass a buggy DUT. A mutant that does not fail tells you the stimulus is weak, not that the DUT is right: that is why coverage exists ([I-SV-3A](/curriculum/T2_Intermediate/I-SV-3A_Functional_Coverage_Fundamentals/index)).
- **`MUT_EXTRA` is caught only because the duplicate arrives while the run is alive.** An extra result that arrives after the scoreboard went idle and the phase ended is invisible to any end-of-test rule. Interface checkers ("a result with no request in flight") close that hole.

### Debug it: three logs, three causes

1. **Log:** `UVM_ERROR @ 335 ns: ... [SCB/MISSING] tag=9 ... was never answered`, after a `SCB/DRAIN_TIMEOUT` warning. **Cause:** the DUT lost the request (or the output monitor missed its result). **Next step:** find tag 9 on the waveform at the output: if `valid_out` never rose for it, it is a DUT bug; if it did, the output monitor's sampling condition is wrong.
2. **Log:** `UVM_INFO @ 115 ns: reporter [MISCMP] Miscompare for t.result: lhs = 'hb7 : rhs = 'hd9`, and later `UVM_ERROR :    0`. **Cause:** a scoreboard that calls `compare()` and ignores its return value; the default comparer reports miscompares as `UVM_INFO`. **Fix:** test the return value and raise `` `uvm_error ``, as `compare_pair()` does.
3. **Log:** `UVM_FATAL @ 1000000 ns: reporter [PH_TIMEOUT] Explicit timeout of 1000000 ns hit, indicating a probable testbench issue`, then `SCB_SUMMARY ... (run aborted)` and no other `SCB_SUMMARY`. **Cause:** something kept an objection raised forever, often a scoreboard drain with no watchdog. **What you learn from the log:** `check_phase` never ran, so the pending count in the aborted summary is the only accounting you get; that is why `pre_abort()` prints it.

### How to build a scoreboard

1. **Write the item and its `do_compare`.** Compare only the fields the output side carries; give the item `do_copy` so `clone()` works.
2. **Write two monitors.** Each samples its own side through a clocking block and creates a new item per transaction.
3. **Write the reference model and the predictor.** The predictor subscribes to the input monitor, clones, calls the model, and publishes the expected item.
4. **Choose the feeding form.** Two imps when every action is zero-time; two FIFOs and a thread when a check must wait.
5. **Write the matching.** In order: oldest first. Out of order: one queue per key, plus a held queue for actuals that arrive first.
6. **Compare by value** with a checked `compare()` and your own comparer; report `SCB/MISMATCH` with expected, actual and the comparer's detail.
7. **Account in `check_phase`:** `SCB/MISSING`, `SCB/UNEXPECTED`, `SCB/NO_TRAFFIC`.
8. **Drain in `phase_ready_to_end`** until nothing is outstanding, with a watchdog; add a per-item latency check and a global timeout.
9. **Print `SCB_SUMMARY`** in `report_phase` and in `pre_abort()`.
10. **Run the mutants.** Every one must fail with its own ID before you trust a clean run.

**Checklist before moving on:**
- [ ] Every item a monitor publishes, and every item the scoreboard stores, is a new object or a copy.
- [ ] The predictor takes its inputs from the input monitor, not from the sequence or the driver.
- [ ] The `compare()` result is checked and a miscompare raises `` `uvm_error ``.
- [ ] `check_phase` reports missing items, unexpected items and zero traffic.
- [ ] The test ends when the scoreboard is idle, never on a fixed delay, and a watchdog bounds the wait.
- [ ] `report_phase` prints `SCB_SUMMARY matches=N mismatches=M pending=P`, and nothing prints "PASSED".
- [ ] Each mutant fails with its own error ID.

## Push Further

### Expert: the end-of-test machinery, exactly

- **The iteration rule.** "If any objection is raised, when all objections to ending the given phase and siblings are dropped, another iteration of `phase_ready_to_end` is called", and the phase ends after at most `phase.get_max_ready_to_end_iterations()` iterations "regardless of whether a previous iteration lead to any objections being raised" (IEEE 1800.2-2020 §13.1.4.3.2). The default limit is 20 (§9.3.1.3.5); `set_max_ready_to_end_iterations()` changes it per phase (§9.3.1.3.3). A scoreboard that raises on every call without a once-only guard uses up the iterations and then the phase ends anyway, possibly with work pending.
- **When it is called.** uvm-core 2020.3.1 waits for the NBA region before each call (`uvm_phase_hopper.svh`), so every zero-time `write()` made in the time step of the last drop has already run: an item accepted at the very edge where the test drops its objection is already counted in `outstanding`.
- **Drain time interacts with the iterations.** A drain time set on the test applies each time the test's objection count reaches zero, including after the scoreboard's later drop, and a raise during the drain cancels it (§10.5.1.3.7).
- **What ending kills.** When `run_phase` ends, uvm-core kills the phase's processes (`uvm_phase_hopper.svh`), and `kill()` terminates every descendant process too (IEEE 1800-2023 §9.7). A monitor's late `write()` therefore never happens: the item is not "dropped by the scoreboard", it was never delivered.
- **Timeout and abort.** The default global timeout "is implementation specific" (Annex F.7.3.3); in uvm-core 2020.3.1 it is `` `UVM_DEFAULT_TIMEOUT ``, 9200 s (`uvm_global_defines.svh`, uvm-core impl.). The timeout raises `UVM_FATAL [PH_TIMEOUT]`; the fatal's exit action calls `pre_abort()` on every component, bottom-up (§13.1.4.6), then prints the report summary. `check_phase` and `report_phase` never run.
- **Interview angle:** "Your test ends at the right time in simulation A and 2 µs late in simulation B, with the same seed and code. Where do you look?" (A `phase_ready_to_end` that raises unconditionally with a delay, re-called up to 20 times; or a drain time hit repeatedly because something raises and drops in a loop.)

### Expert: configuring `compare()` for a scoreboard

- **The defaults are normative.** A new comparer shows at most one miscompare message (`show_max` 1, §16.3.5.1), at verbosity `UVM_LOW` (§16.3.5.2), with severity `UVM_INFO` (§16.3.5.3), and with a return threshold of 1 (§16.3.6), which lets `do_compare` "return as quickly as possible after the result ... reaches the threshold value, potentially skipping additional field comparisons".
- **Who honours the threshold.** In uvm-core 2020.3.1 the field macros stop comparing later fields once the result reaches the threshold (`uvm_comparer_defines.svh`); `compare_field_int` and the other `compare_field*` calls in a hand-written `do_compare` do not check it. `set_threshold(0)` asks for every field to be compared, which matters for field-macro items.
- **A null comparer means the shared default.** `compare(rhs)` with no comparer uses the default comparer policy and flushes it when the active object depth is 0 (§5.3.9.1). Changing the default comparer's severity to `UVM_ERROR` changes it for every `compare()` in the simulation, including library code: prefer a scoreboard-owned comparer, as `alu_scoreboard` does.
- **Reading the detail.** `get_miscompares()` returns the miscompare messages since the last flush, one per line (§16.3.3.8); `get_result()` returns their number (§16.3.3.9).
- **Tolerance.** A model with rounding (a DSP filter, floating point) needs a tolerant compare: override `do_compare` to compare within a bound, or compare a derived value; never weaken the compare by removing the field. [I-UVM-4](/curriculum/T2_Intermediate/I-UVM-4_UVM_Policy_Classes/index) shows both ways.
- **Interview angle:** "`compare()` returned 0, the log shows a `MISCMP` line, and the test passed. How?" (The return value was ignored and the default severity is `UVM_INFO`.)

### Expert: uvm-core's built-in comparators

- **They exist in uvm-core, not in the standard.** `uvm_in_order_class_comparator`, `uvm_in_order_built_in_comparator` and `uvm_algorithmic_comparator` live in uvm-core 2020.3.1 (`src/comps/uvm_in_order_comparator.svh`, `uvm_algorithmic_comparator.svh`); IEEE 1800.2-2020 does not define them, so treat them as uvm-core impl.
- **Why they are not a scoreboard.** On a mismatch the in-order comparator issues a `uvm_report_warning` ("Comparator Mismatch"), which does not fail a test unless you promote warnings; and nothing checks leftovers: its `flush()` only resets its counters. A dropped item and a mismatch both leave the run green.
- **When they are still useful.** As a quick in-order check inside a larger scoreboard, wrapped with your own `check_phase` and severity. In production benches, most teams write the matching themselves, as on this page.
- **Interview angle:** "Can you use `uvm_in_order_class_comparator` as your scoreboard?" (Only with your own accounting and severity on top; on its own it passes dropped items.)

### Expert: keyed matching at scale

- **Reading a missing key.** Reading a nonexistent entry of an associative array issues a warning and returns the default value (IEEE 1800-2023 §7.8.6), so guard reads with `exists()`, as `write_act()` does.
- **Writing a missing key.** An entry is allocated when it is the target of an assignment, an actual to a `ref` argument, or part of a read-modify-write such as an increment (§7.8.7). A queue method call on a missing key, `exp_q[k].push_back(t)`, is not named explicitly in §7.8.7; major simulators allocate the entry, but treat that as tool-dependent behaviour and keep the guarded read.
- **Memory.** Delete a key whose queue has emptied when the key space is large (addresses, 16-bit IDs); with 16 tags it does not matter.
- **The held queue is a linear search.** Its `foreach` is O(held). Bound it: hold an actual only within the race window (the same time step), timestamp it, and report anything older at once with its arrival time. An unbounded held queue also misreports an extra response: the next prediction with the same key claims it, so a `SCB/MISMATCH` is blamed on the wrong request and the real response later shows up as unexpected.
- **Search-any costs twice.** It is O(n) per response and lets same-key reorders through. Avoid it except for a genuinely unordered protocol.
- **Light records.** At very high transaction counts, storing a small struct (key, expected data, prediction time) instead of a full `uvm_object` per expected item saves allocation and memory. This is guidance to measure in your simulator, not a figure: profile first (tool-dependent).
- **Interview angle:** "Make a keyed scoreboard O(1) per transaction for 10 million transactions." (Associative array of queues, delete emptied keys, bounded held queue, per-key rather than per-item watchdogs, light records, no search-any.)

### Expert: protocol ordering versus DUT policy

- **The protocol rule.** AXI: transactions with the same ID complete in order; different IDs are unrestricted (Arm IHI0022E §A5.1). The read-data reordering depth is a static property of a slave's design (§A5.3.1).
- **The scoreboard checks the rule, not today's behaviour.** A scoreboard that assumes the current RTL's order (for example "always in order") false-fails the day the DUT starts using legal reordering, and a scoreboard that assumes nothing (search-any) misses same-ID violations. Encode the protocol rule; make a stricter promise from the DUT specification a separate, switchable check.
- **Time-local rules belong elsewhere.** "Same-ID responses never overtake" cannot be seen from handshakes alone: only the data shows which read came back, so a per-ID model or the scoreboard checks it, while interface assertions check what they can see, such as per-ID outstanding counts ([B-AXI-3](/curriculum/T3_Advanced/B-AXI-3_AXI_Ordering_and_IDs/index)). The scoreboard also checks end-to-end data. The AXI per-ID application is in [B-AXI-6](/curriculum/T3_Advanced/B-AXI-6_AXI_Verification_Performance/index), whose lab builds a per-ID read scoreboard keyed by ARID.
- **Interview angle:** "The designers changed the arbiter and now responses reorder across IDs. Your scoreboard fails. Is it a DUT bug?" (Only if a same-ID pair reordered or data is wrong; reordering across IDs is legal, so an in-order scoreboard was wrong all along.)

### Expert: reference-model independence and DPI-C

- **Common-mode errors.** A model written by the RTL author, or translated from the RTL, shares its misreadings, and the scoreboard then approves wrong behaviour. Mitigations: a different author working from the specification, directed tests whose expected values were computed by hand, a specification review of the model, and cross-checks against an architectural model where one exists.
- **DPI-C rules.** `pure` is legal only for a nonvoid function with no `output` or `inout` arguments, and promises no side effects, so a compiler may skip or reuse calls (IEEE 1800-2023 §35.5.2); a stateful model is never `pure`. A C model that calls exported SystemVerilog subroutines must be imported as `context` (§35.5.3).
- **State and order.** A stateful C model (a CPU simulator, a codec with history) must be called in exactly the order the DUT processes requests, from one place: the predictor component. Calling it from several monitors, or from the sequence, desynchronises it.
- **Cost.** Each DPI call marshals its arguments; for wide data, pass packed arrays or open arrays, and batch calls when the model allows (tool-dependent: measure).
- **Interview angle:** "When would you use a DPI-C reference model, and what can go wrong?" (When an architect-owned bit-accurate model exists; wrong `pure` on a stateful model, calls out of DUT order, model and RTL sharing a misreading, and debugging across two languages.)

### Expert: scoreboards across reset and injected errors

- **Reset.** On reset, stop treating discarded requests as missing: flush the expected queues, the held queue and any analysis FIFOs (`flush()`, IEEE 1800.2-2020 §12.2.8.2.6), and count the flushed items separately so a reset that discards too much is still visible. A predictor component with state (a memory image) must reset its state to what the specification says reset does, not to what the RTL happens to do.
- **When to stop predicting.** Requests accepted while reset is asserted are not requests; monitors that skip cycles with `rst_n` low (as `alu_in_mon` does) keep them out of the model.
- **Injected errors.** The reference model predicts the specified error response for an illegal input. Demoting one specific expected message with a report catcher (IEEE 1800.2-2020 §6.6) is a precise tool; demoting `SCB/*` for a whole test is a blindfold. The full strategy is in [A-UVM-9: Reset Handling and Error Injection](/curriculum/T3_Advanced/A-UVM-9_Reset_and_Error_Injection/index).
- **Interview angle:** "After a mid-test reset, your scoreboard reports 3 `SCB/MISSING`. The designers say the DUT is right. What do you change?" (Flush on reset and report flushed items separately; do not lengthen the drain or disable `check_phase`.)

### Expert: where checking belongs in a large environment

- **Assertions versus scoreboards.** Time-local interface rules (handshakes, stability, ordering on one interface) are assertions in the interface or VIP; end-to-end data correctness is the scoreboard. Do not reimplement protocol timing in a scoreboard.
- **Topologies.** One input split to N outputs: route each expected item to the scoreboard (or the queue) for its destination. N inputs merged into one output: keep one queue per source and match on a field that identifies the source. Crossbars combine both.
- **Knobs for reuse.** A subsystem scoreboard reused passively at SoC level needs configuration: matching mode, maximum latency, enable, which streams are present ([E-SOC-1](/curriculum/T4_Expert/E-SOC-1_SoC-Level_Verification_Strategies/index)).
- **Interview angle:** "Design the scoreboard for a 4×4 crossbar that reorders across sources and may drop packets by a QoS policy." (Per-destination scoreboards keyed by source and sequence; a model of the QoS policy that predicts which drops are legal; leftover accounting that separates legal drops from losses.)

### Kata: one slot per tag, then one queue per tag

A teammate wrote a keyed scoreboard with one slot per tag. It passes every test on `alu_pipe`, because the sequence numbers the tags 0 to 15 and no tag is ever outstanding twice. The DUT team now narrows the tag to 2 bits, and the sequence randomizes it, so requests with the same tag can be outstanding together.

```systemverilog
// snippet: the teammate's matching (form A); exp_by_tag replaces exp_q and held_q
alu_item exp_by_tag[int unsigned];               // ONE slot per tag

virtual function void write_exp(alu_item t);
  exp_by_tag[t.tag] = t;                         // overwrites a pending prediction
endfunction

virtual function void write_act(alu_item t);
  if (!exp_by_tag.exists(t.tag)) begin
    `uvm_error("SCB/UNEXPECTED", $sformatf("tag=%0d matched no prediction", t.tag))
    return;
  end
  compare_pair(exp_by_tag[t.tag], t);
  exp_by_tag.delete(t.tag);
endfunction
```

1. **Predict.** Requests A (tag 2), B (tag 2) and C (tag 0) are accepted at edges 1, 2 and 3; `alu_pipe` returns each result two edges later, correctly. Write down the scoreboard's messages, with the edge of each.
2. **Write** the fix: `write_exp()` and `write_act()` with one queue per tag, plus the `check_phase` lines it needs.
3. **Predict again** for your fix, first with the correct DUT, then with a DUT that swaps the two tag-2 results (B's result at edge 3, A's at edge 4).

<details>
<summary>Worked solution</summary>

**1. The one-slot version.** At edge 1 `exp_by_tag[2] = A`. At edge 2 `exp_by_tag[2] = B`: A's prediction is overwritten. At edge 3, A's result (tag 2) is compared with B's prediction: `SCB/MISMATCH` (unless A and B happen to give the same result), and slot 2 is deleted; C is predicted into slot 0 in the same time step. At edge 4, B's result (tag 2) finds no slot: `SCB/UNEXPECTED`. At edge 5, C's result matches. Two errors against a correct DUT: a false failure. If A and B give equal results, the first compare passes by luck, which is worse.

**2. The fix**, exactly the structure of `alu_scoreboard`:

```systemverilog
// snippet: one ordered queue per tag, plus a held queue
alu_item exp_q[int unsigned][$];
alu_item held_q[$];
int unsigned outstanding;

virtual function void write_exp(alu_item t);
  foreach (held_q[i])
    if (held_q[i].tag == t.tag) begin
      compare_pair(t, held_q[i]);
      held_q.delete(i);
      return;
    end
  exp_q[t.tag].push_back(t);
  outstanding++;
endfunction

virtual function void write_act(alu_item t);
  if (!exp_q.exists(t.tag) || exp_q[t.tag].size() == 0) begin
    held_q.push_back(t);
    return;
  end
  compare_pair(exp_q[t.tag].pop_front(), t);
  outstanding--;
endfunction

// in check_phase:
foreach (exp_q[tag, i])                       // every key, every queued prediction
  `uvm_error("SCB/MISSING", {exp_q[tag][i].convert2string(), " was never answered"})
foreach (held_q[i])
  `uvm_error("SCB/UNEXPECTED", $sformatf("tag=%0d matched no prediction", held_q[i].tag))
```

**3. The fixed version.** Correct DUT: `exp_q[2]` holds A, B after edge 2; edge 3 pops A for A's result (match), edge 4 pops B (match), edge 5 matches C; nothing pending, `SCB_SUMMARY matches=3 mismatches=0 pending=0`. Swapping DUT: at edge 3, B's result is compared with A's prediction (the oldest for tag 2): `SCB/MISMATCH`; at edge 4, A's result with B's prediction: `SCB/MISMATCH`. The same-tag reorder, which is a protocol violation, is caught. A "search any match" scoreboard would have passed it.

</details>
