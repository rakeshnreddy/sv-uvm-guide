## Quick Take
- **What it is:** A standardized mechanism for exposing safe extension points within a UVM component's main execution loop, allowing test-specific behavior injection without subclassing.
- **Why it matters:** Without callbacks, every test-specific tweak (error injection, delay insertion, scoring hooks) requires a factory override and a dedicated subclass. Callbacks let you append, prepend, or stack multiple independent extensions on a single component instance—and toggle them at runtime.
- **The Standard:** IEEE 1800.2-2020 §10.7 defines the `uvm_callback` base class (§10.7.1) and the `uvm_callbacks#(T,CB)` registration API (§10.7.2). The macros `` `uvm_register_cb `` and `` `uvm_do_callbacks `` are in Annex B.4, and the iterator class `uvm_callback_iter` is in Annex D.1 (clause numbers as tagged in the uvm-core 2020.3.1 sources).

## Build Your Mental Model

### The Three-Part Contract

Every callback scenario has exactly three participants:

1. **The callback interface** — a virtual class extending `uvm_callback` that declares hook methods (tasks or functions). The component developer writes this.
2. **The calling component** — registers the callback type with `` `uvm_register_cb `` and invokes hooks via `` `uvm_do_callbacks `` at chosen points in its execution loop.
3. **The test-specific implementation** — a concrete class extending the callback interface, overriding only the hooks it needs. The test writer creates and attaches this.

```systemverilog
// ──── Part 1: Callback interface (component developer) ────
typedef class my_driver;   // forward declaration: the hooks take a my_driver handle

virtual class my_driver_cb extends uvm_callback;
  // Called right before the driver wiggles pins
  virtual task pre_send(my_driver driver, ref packet pkt);
  endtask

  // Called right after driving completes
  virtual function void post_send(my_driver driver, const ref packet pkt);
  endfunction
endclass

// ──── Part 2: Calling component ────
class my_driver extends uvm_driver#(packet);
  `uvm_component_utils(my_driver)
  `uvm_register_cb(my_driver, my_driver_cb)

  function new(string name, uvm_component parent);
    super.new(name, parent);
  endfunction

  task run_phase(uvm_phase phase);
    packet pkt;
    forever begin
      seq_item_port.get_next_item(pkt);

      // Invoke all registered pre_send callbacks in order
      `uvm_do_callbacks(my_driver, my_driver_cb, pre_send(this, pkt))

      send_to_dut(pkt);

      // Invoke all registered post_send callbacks in order
      `uvm_do_callbacks(my_driver, my_driver_cb, post_send(this, pkt))

      seq_item_port.item_done();
    end
  endtask
endclass

// ──── Part 3: Test-specific callback ────
class inject_error_cb extends my_driver_cb;
  `uvm_object_utils(inject_error_cb)

  function new(string name = "inject_error_cb");
    super.new(name);
  endfunction

  virtual task pre_send(my_driver driver, ref packet pkt);
    `uvm_info("CB", "Injecting CRC error into packet", UVM_LOW)
    pkt.crc = ~pkt.crc;
  endtask
endclass
```

### Passing by Reference (`ref`) vs Handles

A transaction is a class object, so every hook receives a *handle*. The argument direction only decides what happens to that handle:
- **By value (default):** The hook gets a copy of the handle. It can still change the object's fields (`pkt.crc = ~pkt.crc` changes the packet the driver sends), but assigning a new object to `pkt` changes only the hook's local copy.
- **By `ref`:** The hook can also *replace the handle* in the driver's variable, substituting a different object.
- **By `const ref`:** The hook cannot reassign the handle, but it **can still modify the object's fields**. `const` protects the handle, not the object. A "read-only" observer hook is read-only by discipline only; if it must never disturb the driver, give it a `clone()`.

Choose deliberately: `ref` should be reserved for hooks that genuinely need object-swap power.

### Callback Lifecycle and the Iteration Queue

When `` `uvm_do_callbacks `` executes, it creates a `uvm_callback_iter` and walks **one queue**: the component's own instance queue if it has one, otherwise the type-wide queue for that `(component_type, callback_type)` pair. It runs the callbacks **in queue order** and skips any whose `callback_mode()` is off.

Key lifecycle rules (checked against `uvm_callback.svh` in uvm-core 2020.3.1):
- **Registration** uses `` `uvm_register_cb(comp_type, cb_type) `` inside the component class body. It declares that the pair is legal; it attaches nothing.
- **Attachment** uses `uvm_callbacks#(comp_type, cb_type)::add(comp_inst, cb_inst, ordering)`. The handle is read **when `add()` runs**. If it is `null`, the callback is registered **type-wide**: every instance of the type runs it, including ones created later. UVM builds top-down, so in any `build_phase` the components below you do not exist yet. Attach in `connect_phase`, `end_of_elaboration_phase` or `start_of_simulation_phase`, or at run time.
- **Order** follows the queue. `UVM_APPEND` (the default) adds at the back, `UVM_PREPEND` at the front. The first instance-specific `add()` creates the instance queue by **copying the type-wide queue**, then adds the new callback. A type-wide `add()` made later is appended to every existing instance queue as well.
- **Removal** uses `uvm_callbacks#(comp_type, cb_type)::delete(comp_inst, cb_inst)`; `delete(null, cb)` removes a type-wide callback from every queue.
- **Iteration** walks the live queue by index (`get_first`/`get_next`). There is no snapshot, so do not add or delete callbacks from inside a hook: a deleted entry shifts the queue and the next callback can be skipped.

Set the attachment point and the handle, predict which drivers corrupt their packets, then open the advanced options to see `UVM_PREPEND` and `callback_mode()` change the order a log callback sees.

## Managing Callbacks at Runtime

### Adding and Removing

```systemverilog
// In connect_phase or later: env.agent.driver exists now
// Add a callback to a specific driver instance
uvm_callbacks#(my_driver, my_driver_cb)::add(env.agent.driver, err_cb);

// Run it before every callback already in that driver's queue
uvm_callbacks#(my_driver, my_driver_cb)::add(env.agent.driver, dly_cb, UVM_PREPEND);

// Add a callback to ALL instances of my_driver (type-wide), on purpose
uvm_callbacks#(my_driver, my_driver_cb)::add(null, log_cb);

// Switch a callback off and on without removing it (affects every queue that holds it)
void'(err_cb.callback_mode(0));
void'(err_cb.callback_mode(1));

// Remove a specific callback from a specific instance
uvm_callbacks#(my_driver, my_driver_cb)::delete(env.agent.driver, err_cb);
```

> **Ordering rule:** Callbacks run in *queue order*. `UVM_APPEND` puts a callback at the back, `UVM_PREPEND` at the front. A driver's instance queue starts as a copy of the type-wide queue, so a type-wide `log_cb` registered first runs before an instance `err_cb` appended later, and logs the CRC before it is corrupted.

### Displaying Registered Callbacks

During debug, call `display()` (provided by the uvm-core reference implementation, not specified by IEEE 1800.2) to see all registered callbacks for a given type pair:

```systemverilog
// Print every callback attached to every my_driver instance
uvm_callbacks#(my_driver, my_driver_cb)::display();
```

This prints the callback queue order, instance name, and component path—essential for diagnosing "my callback is not firing" bugs.

## Callbacks vs Factory Overrides

The most common design question is: *Should I use a callback or a factory override?* They solve superficially similar problems but have fundamentally different architectural roles.

| Dimension | Factory Override | Callback |
|---|---|---|
| **Mechanism** | Replaces the *entire class* for a component or object | Appends/prepends behavior *around* existing logic |
| **Granularity** | One active override per type at any time | Multiple independent callbacks can be stacked |
| **Lifetime** | Set once during construction, persistent for the test | Can be added and removed dynamically at any phase |
| **Scope** | Structural—changes *what* the component *is* | Behavioral—changes *what the component does* at specific hooks |
| **Typical use** | Replacing a driver with a protocol variant, swapping the entire scoreboard | Injecting errors, adding delays, passive monitoring, per-test scoring hooks |
| **Overhead** | None at runtime (resolved at `create()` time) | Small per-invocation cost from `uvm_callback_iter` walking the queue |

**Rule of thumb:** If you need to *replace* the thing, use the factory. If you need to *augment* the thing (especially with multiple independent concerns), use callbacks.

## Debug & Failure Modes

### Common Pitfalls

1. **"My callback is not firing"**
   - Verify registration: did the component class declare `` `uvm_register_cb ``?
   - Verify attachment: did the test call `uvm_callbacks#(...)::add()` *before* the phase where the callback fires, and *after* the target component was built?
   - Verify type parameters: if `(T, CB)` was never paired with `` `uvm_register_cb ``, `add()` issues a `CBUNREG` warning. Read your warnings.
   - Verify `callback_mode()`: a disabled callback stays in the queue but is skipped.
   - Run `uvm_callbacks#(comp, cb)::display()` to inspect the queue.

2. **"My callback fires on every instance"**
   - The handle was `null` when `add()` ran, usually because the call sits in a `build_phase` and the target is built later. `add(null, cb)` is type-wide and issues no warning. Move the call to `connect_phase` or later.
   - In the test's `build_phase`, `env.agent.driver` is worse than null: `env.agent` itself is null, so reading `.driver` is a null-object access (IEEE 1800-2023 §8.4) and the simulation stops.

3. **Callback ordering surprises**
   - Callbacks execute in *queue order*, not alphabetical or priority order. Use `UVM_PREPEND` when a callback must run first, and remember that an instance queue starts as a copy of the type-wide queue at its first instance `add()`.

4. **Adding or deleting inside a hook**
   - Iteration walks the live queue by index. Deleting the current callback from inside its own hook shifts the queue, and the next callback in that pass can be skipped. Change the queue between invocations, or use `callback_mode()`.

5. **Performance in hot loops**
   - Each `` `uvm_do_callbacks `` invocation creates a `uvm_callback_iter` and walks the queue. In per-bit driver loops that run millions of times, this costs real CPU time. Profile before deploying callbacks in very tight loops.

### Debug Checklist

When a callback-related issue arises:
1. Call `uvm_callbacks#(T, CB)::display()` at the start of `run_phase`.
2. Add `uvm_info` traces inside callback hook methods to confirm they execute.
3. Verify the `ref`/value semantics: reassigning a by-value handle changes only the hook's copy; changing fields through any handle changes the shared object.
4. Check whether the callback was added to the correct *instance* or to `null` (all instances). A handle read during `build_phase` is usually still `null`.

## Push Further: Advanced Patterns

### Stacking Independent Concerns

One of the most powerful patterns is stacking multiple independent callbacks on the same component:

```systemverilog
// In the test's connect_phase (or end_of_elaboration_phase): every component exists
inject_error_cb err_cb = inject_error_cb::type_id::create("err_cb");
add_delay_cb    dly_cb = add_delay_cb::type_id::create("dly_cb");
scoreboard_cb   scb_cb = scoreboard_cb::type_id::create("scb_cb");

uvm_callbacks#(my_driver, my_driver_cb)::add(env.agent.driver, err_cb);
uvm_callbacks#(my_driver, my_driver_cb)::add(env.agent.driver, dly_cb);
uvm_callbacks#(my_driver, my_driver_cb)::add(env.agent.driver, scb_cb);

// All three fire in order at each `uvm_do_callbacks` invocation.
// Each is independently removable without affecting the others.
```

This composability is the key architectural advantage over factory overrides—you cannot cleanly stack three independent concerns using a single subclass chain.

### Dynamic Toggling During `run_phase`

Callbacks can be added and removed at any time, enabling scenario-based injection:

```systemverilog
task run_phase(uvm_phase phase);
  phase.raise_objection(this);

  // Run clean traffic first
  normal_seq.start(env.agent.sqr);

  // Now inject errors for the next batch
  uvm_callbacks#(my_driver, my_driver_cb)::add(env.agent.driver, err_cb);
  error_seq.start(env.agent.sqr);

  // Remove and run clean again
  uvm_callbacks#(my_driver, my_driver_cb)::delete(env.agent.driver, err_cb);
  recovery_seq.start(env.agent.sqr);

  phase.drop_objection(this);
endtask
```
