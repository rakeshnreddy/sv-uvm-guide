## Quick Take

- **What it is:** A **callback** is an object whose methods a component calls at fixed points in its own code. The component's author declares those methods, called **hooks**, in a subclass of `uvm_callback` (IEEE 1800.2-2020 §10.7.1) and calls them with the `` `uvm_do_callbacks `` macro (Annex B.4.3). A test attaches its own callback objects to one component, or to every component of a type, with `uvm_callbacks#(T,CB)::add` (§10.7.2.3.1).
- **Why it matters:** An error test often has to change what a driver does to one agent's traffic, without editing the driver, without touching the reused sequences, and with the change switched on and off during the run. Callbacks do exactly that: per instance, stackable (several independent concerns on one hook) and switchable. They are a common way for verification IP (VIP) to offer extension points, and they are one of the mechanisms you will use for error injection in the testbench milestones (M8). Other tools solve neighbouring problems: a factory override swaps a whole class, and a configuration knob or a sequence field changes values. This lesson shows when each one fits.
- **The Analogy:** A production line with sockets. The line's builder (the component's author) decides where the sockets are (the hooks). You plug tools (callback objects) into the sockets of one line, or of every line of that model, in front of or behind the tools already there, and you can switch a tool off without unplugging it. *Where it breaks:* a tool plugged in "before the line exists" does not fail; it silently goes onto every line of that model (`add(null, cb)`). And the tools work on the product itself (the transaction object), so their order changes the result.

**You will be able to:**
1. Write the three parts of a callback: a `uvm_callback` subclass with hook methods (§10.7.1), a component that registers it with `` `uvm_register_cb `` and calls it with `` `uvm_do_callbacks `` (Annex B.4), and a concrete callback attached with `uvm_callbacks#(T,CB)::add` (§10.7.2).
2. Predict which components run a callback, and in what order, from the `add()` calls: per-instance or type-wide (`add(null, cb)`), `UVM_APPEND` or `UVM_PREPEND`, and `callback_mode()`.
3. Choose between a callback and a factory override for an extension, and justify the choice: per-instance toggles, stacked concerns, vendor extension points, wholesale replacement, new item fields.
4. Debug a callback that never fires or fires everywhere (a null or too-early handle, `add_by_name` that matched nothing, a hook that is never reached, a `CBUNREG` warning, `callback_mode(0)`) using `display()`, `get_all()` and the log.
5. Explain what a hook can change when its transaction argument is passed by value, by `ref` or by `const ref` (IEEE 1800-2023 §13.5.2).

## Build Your Mental Model

**How to read this lesson.** The core path is the first four subsections: the problem, the three-part contract, what happens at a hook, and attaching a callback to the right component. Practitioner depth follows: queue order, run-time switching, hook arguments, callbacks versus the factory, and where callbacks live in a real testbench. Make It Work builds a complete two-agent error test and a debugging procedure; Push Further holds the expert corner cases.

A few terms from earlier lessons, in one line each. A **component** is a `uvm_component`: a long-lived testbench block with a place in the hierarchy, such as a driver ([I-UVM-1A](/curriculum/T2_Intermediate/I-UVM-1A_Components/index)). A **sequence item** is a transaction object that a sequence creates; the **driver** turns sequence items into pin activity, and the **sequencer** hands it those items ([I-UVM-2A](/curriculum/T2_Intermediate/I-UVM-2A_Component_Roles/index)). **Phases** are the fixed steps every component runs through: `build_phase` creates children, `connect_phase` wires them, and `run_phase` is where time passes ([I-UVM-1C](/curriculum/T2_Intermediate/I-UVM-1C_UVM_Phasing/index)). A **factory override** tells the factory to build a different class when someone asks for one ([I-UVM-1B](/curriculum/T2_Intermediate/I-UVM-1B_The_UVM_Factory/index)).

### The problem callbacks solve

Here is the running example of this lesson. An environment `env` holds two identical agents, `agt0` and `agt1`, and each agent's driver is a `my_driver`. The drivers send `packet` items, each with a data byte and a checksum byte, `crc` (a cyclic redundancy check, CRC). A test called `err_test` must corrupt the CRC of the packets that `agt0`'s driver sends to the design under test (DUT), and leave `agt1` clean. The driver comes from a VIP: you are not supposed to edit it.

You have several options, and each changes something different:

- **Subclass and override:** write `err_driver extends my_driver` and register a factory instance override for `env.agt0.drv`. This replaces the whole driver class for that instance, at build time.
- **A field or knob:** if the item already has an "inject error" field, an error sequence or a constrained item subclass can set it. This changes the stimulus, so it needs control over the sequences.
- **A hook:** if the driver's author left a hook just before the driver sends each packet, the test can plug a small object into it, for one driver only, and switch it off later.

The third option is a callback. It needs no new driver class and no change to the sequences, and several such objects can share one hook. Its limit is just as important: a callback can only act where the author put a hook.

### The three-part contract

Every callback involves three pieces of code, written by two different people:

1. **The callback base class** (the driver's author). A `virtual class` that extends `uvm_callback` and declares the hooks as **empty virtual methods**. "Empty, not `pure`" matters: each user callback overrides only the hooks it needs, and the rest do nothing (uvm-core 2020.3.1 documents this in `uvm_callback.svh`).
2. **The component that offers the hooks** (the driver's author). It declares the legal pairing with `` `uvm_register_cb(my_driver, drv_cb) `` and calls the hooks at chosen points with `` `uvm_do_callbacks ``.
3. **The concrete callback** (the test writer). A subclass of the base that overrides a hook, created in the test and attached with `uvm_callbacks#(my_driver, drv_cb)::add(...)`.

Here are the three parts in code. Names match the picture and the visualizers on this page.

```systemverilog
// snippet: the three parts (packet, the sequence item, has fields data and crc)
typedef class my_driver;  // drv_cb's hook names my_driver before it is declared

// Part 1: the callback base class, written by the driver's author
virtual class drv_cb extends uvm_callback;
  // Without this constructor, a subclass's super.new(name) does not compile:
  // the implicit new() of drv_cb takes no arguments (IEEE 1800-2023 §8.7, §8.17).
  function new(string name = "drv_cb");
    super.new(name);
  endfunction

  // Empty, not pure: a callback overrides only the hooks it needs.
  virtual task pre_send(my_driver drv, packet pkt);
  endtask
endclass

// Part 2: the component that offers the hook
class my_driver extends uvm_driver #(packet);
  `uvm_component_utils(my_driver)
  `uvm_register_cb(my_driver, drv_cb)  // declares the legal (my_driver, drv_cb) pair

  function new(string name, uvm_component parent);
    super.new(name, parent);
  endfunction

  task run_phase(uvm_phase phase);
    forever begin
      seq_item_port.get_next_item(req);
      // The hook: run pre_send on every enabled drv_cb in this driver's queue
      `uvm_do_callbacks(my_driver, drv_cb, pre_send(this, req))
      // ... drive req on the pins ...
      seq_item_port.item_done();
    end
  endtask
endclass

// Part 3: a concrete callback, written by the test writer
class crc_err_cb extends drv_cb;
  `uvm_object_utils(crc_err_cb)

  function new(string name = "crc_err_cb");
    super.new(name);
  endfunction

  virtual task pre_send(my_driver drv, packet pkt);
    pkt.crc = ~pkt.crc;  // pkt is a copy of the handle; the object is the driver's req
  endtask
endclass
```

And the attachment, in the test:

```systemverilog
// snippet: err_test::connect_phase; by now every component exists
err_cb = crc_err_cb::type_id::create("err_cb");
uvm_callbacks#(my_driver, drv_cb)::add(env.agt0.drv, err_cb);
```

Three details trip people up:

- **The base class needs its own constructor.** If `drv_cb` has no `new`, SystemVerilog gives it an implicit `new()` with **no** arguments, so `super.new(name)` in `crc_err_cb` is a compile error (IEEE 1800-2023 §8.7, §8.17).
- **`pure virtual` hooks force every callback to implement every hook.** That defeats the point of optional hooks, so declare them empty.
- **A task hook can only be called from a task.** `pre_send` is a task, so a `delay` callback can wait inside it; the driver calls it from `run_phase`, which is a task. A hook that must be called from a function must itself be a function.

### What happens at a hook: `` `uvm_do_callbacks `` and `uvm_callback_iter`

The macro is not magic. In uvm-core 2020.3.1 it expands to a loop over a **`uvm_callback_iter`**, the iterator class of Annex D.1. An **iterator** is an object that walks a queue one entry at a time:

```systemverilog
// snippet: what `uvm_do_callbacks(my_driver, drv_cb, pre_send(this, req)) expands to
// (uvm-core 2020.3.1, uvm_callback_defines.svh; trace lines removed)
begin
  uvm_callback_iter #(my_driver, drv_cb) iter = new(this);
  drv_cb cb = iter.first();    // first ENABLED drv_cb in this object's queue
  while (cb != null) begin
    cb.pre_send(this, req);
    cb = iter.next();          // next enabled drv_cb, by position in the live queue
  end
end
```

Read it slowly, because four rules hide in it:

1. **One queue per object.** The iterator walks the queue for `this`: the driver's own **instance queue** if it has one, otherwise the **type-wide queue** for `my_driver`.
2. **Queue order.** Callbacks run in the order they sit in that queue, not in the order you think of them.
3. **Enabled only.** `first()` and `next()` skip any callback whose `callback_mode()` is 0 (D.1.2.2, D.1.2.4).
4. **Type filter.** Only entries that are a `drv_cb` (or a subclass) are returned, because the iterator is typed on `CB`.

You can write the loop yourself when the macro does not fit, for example when every callback votes and the driver needs the combined answer. The same iterator also has `last()` and `prev()` for walking backwards, and `get_cb()` for the callback returned last (D.1.2.3, D.1.2.5, D.1.2.6). The static functions `get_first`, `get_next`, `get_last` and `get_prev` of `uvm_callbacks#(T,CB)` are the same walk without the facade (§10.7.2.4).

```systemverilog
// snippet: inside my_driver; drv_cb also declares
//   virtual function bit accept(my_driver drv, packet pkt); return 1; endfunction
function bit all_accept(packet pkt);
  uvm_callback_iter #(my_driver, drv_cb) it = new(this);
  bit ok = 1;
  for (drv_cb c = it.first(); c != null; c = it.next())
    ok &= c.accept(this, pkt);  // every enabled callback votes
  return ok;
endfunction
```

### Attaching a callback: one instance, every instance, or by name

You never construct `uvm_callbacks#(T,CB)`; you call its static functions. Its add/delete interface (§10.7.2.3) has these forms:

| Call | What it does |
|---|---|
| `add(obj, cb)` | Adds `cb` to `obj`'s instance queue, at the back (`UVM_APPEND`, the default). |
| `add(obj, cb, UVM_PREPEND)` | The same, at the front. |
| `add(null, cb)` | **Type-wide**: `cb` runs for every object of type `T`, including objects created later (§10.7.2.3.1). |
| `add_by_name("*.agt0.drv", cb, this)` | Searches the component tree, from `this`, for components whose full name matches the pattern, and adds `cb` to each match that is a `T` (§10.7.2.3.2). |
| `delete(obj, cb)` | Removes `cb` from `obj`'s queue. |
| `delete(null, cb)` | Removes `cb` from the type-wide queue and from every instance queue. |
| `delete_by_name("*.agt0.drv", cb, this)` | The by-name form of `delete` (§10.7.2.3.4). |

The second type parameter is optional for these calls, so `uvm_callbacks#(my_driver)::add(env.agt0.drv, err_cb)` means the same thing (§10.7.2.2.2). And `T` need not be a component: it can be any `uvm_object` derivative (§10.7.2.2.1), which is how UVM attaches callbacks to registers and fields.

Now the rule that causes most callback bugs. **The handle is read when `add()` runs.** If `env.agt0.drv` is still `null` at that moment, the call is `add(null, err_cb)`: a perfectly legal type-wide registration, with no warning. When is the handle null? UVM builds **top-down** (IEEE 1800.2-2020 §9.8.1.1): the test's `build_phase` creates `env`; then `env`'s `build_phase` creates `agt0` and `agt1`; then each agent's `build_phase` creates its driver. A component's children exist once its own `build_phase` has created them, but its grandchildren do not exist until the children's `build_phase` has run. By `connect_phase`, every component exists. So attach callbacks in `connect_phase`, `end_of_elaboration_phase` or `start_of_simulation_phase`, or later at run time.

`add_by_name` fails differently: it searches only the components that exist when it runs. If nothing matches, it warns `CBNOMTC` and registers nothing. If something matches that is not a `T` (the pattern `"*.agt0"` finds the agent, not the driver), it skips that match **without** a warning (uvm-core 2020.3.1, `add_by_name`).

**Predict first.** The explorer below starts with `add(env.agt0.drv, err_cb)` in `err_test.build_phase`. Before you change anything, write down what happens: only `agt0` corrupts, both corrupt, neither, or the simulation stops? Then move the call to `my_env.build_phase` (where the path becomes `agt0.drv`) and predict again, and then to `err_test.connect_phase`. Finally try `add_by_name` in a build phase.

What the three placements showed:

- **`err_test.build_phase`: the simulation stops.** `env` exists, but `env.agt0` is still null, so reading `env.agt0.drv` reads a member through a null handle. That is illegal; the standard says the result is indeterminate and an implementation may issue an error (IEEE 1800-2023 §8.4), and simulators typically stop with a null-object error.
- **`my_env.build_phase`: both drivers corrupt.** `agt0` exists, but its own `build_phase` has not run, so `agt0.drv` is null. Passing a null handle is legal, and it means type-wide.
- **`err_test.connect_phase`: only `agt0` corrupts.** The handle is the real driver, so `err_cb` goes into that driver's instance queue only.

The model follows uvm-core 2020.3.1 for one `(my_driver, drv_cb)` pair. It leaves out three things this lesson covers in Push Further: report catchers copied into new instance queues, `` `uvm_set_super_type ``, and `delete` on an object that has no queue.

### Queue order: APPEND, PREPEND and type-wide copies

The order rules, as uvm-core 2020.3.1 implements §10.7.2.3.1:

1. A component with no instance queue walks the type-wide queue.
2. The **first** instance `add()` for a component creates its instance queue by **copying the type-wide queue as it is at that moment**, then adds the new callback.
3. `UVM_APPEND` puts a callback at the back; `UVM_PREPEND` at the front, "ahead of previously added callbacks" (§10.7.2.3.1). A later `UVM_PREPEND` goes in front of an earlier one.
4. A **later** type-wide `add()` goes into the type-wide queue **and** into every instance queue that already exists, at the back or the front.

Trace this sequence of calls. `log_cb` prints the CRC it sees, `err_cb` inverts it, `dly_cb` waits, and `log2_cb` is a second logger.

| Step | Call, and where it runs | Type-wide queue | `agt0.drv` | `agt1.drv` |
|---|---|---|---|---|
| 1 | `add(null, log_cb)` in `base_test.build_phase` | log_cb | no queue: walks type-wide, log_cb | no queue: walks type-wide, log_cb |
| 2 | `add(env.agt0.drv, err_cb)` in `err_test.connect_phase` | log_cb | **created as a copy**, then append: log_cb, err_cb | log_cb (type-wide) |
| 3 | `add(env.agt0.drv, dly_cb, UVM_PREPEND)` | log_cb | dly_cb, log_cb, err_cb | log_cb (type-wide) |
| 4 | `add(null, log2_cb, UVM_PREPEND)` | log2_cb, log_cb | log2_cb, dly_cb, log_cb, err_cb | log2_cb, log_cb (type-wide) |

After step 3, `log_cb` on `agt0` runs **before** `err_cb`, so its log line shows the original CRC, a value the DUT never received. Add `log_cb` type-wide **after** step 2 instead, and it lands **behind** `err_cb` in `agt0`'s queue, so it logs the corrupted CRC. Same objects, different order, different log.

**Try it.** In the explorer above, place the `add()` in `err_test.connect_phase`, open "Show advanced", and predict which CRC `log_cb` prints on `agt0`'s first packet for each choice of "Type-wide log_cb registered in": `base_test build_phase` (step 1 of the table) or `start_of_simulation_phase` (after `err_cb`'s add). Then switch `err_cb` to `UVM_PREPEND` and predict again. The queue panel shows the final queues; the build-order list shows where each `add()` ran.

**Debrief.** With `log_cb` added in `base_test` `build_phase`, `log_cb` is ahead of `err_cb` in `agt0`'s queue and prints the original CRC, 0x5A. With `log_cb` added in `start_of_simulation_phase`, or with `err_cb` added with `UVM_PREPEND`, `err_cb` runs first and `log_cb` prints the corrupted CRC, 0xA5.

The rule to keep: **order is queue order, and queue order comes from when and how each `add()` ran**, not from which callback is "more important". If an order matters, make it explicit with the order of your `add()` calls or with `UVM_PREPEND`, and check it with `display()` (next subsections).

### Switching callbacks at run time

There are two ways to stop a callback:

| | `cb.callback_mode(0)` (§10.7.1.2.2) | `uvm_callbacks#(T,CB)::delete(obj, cb)` |
|---|---|---|
| What changes | A bit on the callback **object** | The callback is removed from **one queue** (or all, with `null`) |
| Scope | Every queue that holds this object | That queue only |
| Undo | `callback_mode(1)` | `add()` again, which puts it at the back or front, not where it was |
| Still listed by `get_all()` and `display()` | yes (`display()` shows `OFF`) | no |

`callback_mode(on)` returns the mode **before** the call, so `void'(err_cb.callback_mode(0));` discards it, and `is_enabled()` asks without changing anything (§10.7.1.2.3). Prefer `callback_mode` for "on for these items, off for those": the object keeps its place in every queue.

**Switch between items, never inside a hook.** The iterator walks the live queue by position. If a hook deletes a callback, the entries behind it move up one place and the next `next()` can skip one; if a hook prepends, the current callback can run again (uvm-core 2020.3.1 by source inspection). Changing `callback_mode` inside a hook is safe for the queue, but it only affects later lookups.

With a driver that calls `get_next_item` and then `item_done` **after** driving, the boundary between items is exact. In the Make It Work test, the sequence for `agt0`'s first two items returns only after the driver's `item_done` for item 2, and item 3 does not exist until the next sequence starts it, so a `callback_mode(0)` in between affects exactly items 3 and later. One more trap: **a callback object is shared state.** If one `err_cb` sits in two queues, or type-wide, its member variables (a counter, a flag) and its `callback_mode` are shared by every driver that runs it. A callback that "corrupts four items, then switches itself off" counts across all of them. Count per driver (key on the `drv` argument) or create one object per instance.

### Passing data into hooks: value, `ref` and `const ref`

- **By value** (the default, as in `pre_send` above): the hook gets a copy of the handle. `pkt.crc = ~pkt.crc` changes the packet the driver sends, because both handles point at one object. `pkt = new()` changes only the hook's copy.
- **By `ref`:** the hook works on the driver's variable itself, so `pkt = new()` makes the driver send a different object. Arguments passed by `ref` must have an **equivalent** type, with no casting (IEEE 1800-2023 §13.5.2), and `ref` is legal here because class methods are automatic (§8.6).
- **By `const ref`:** the hook cannot assign `pkt`; trying is a compile error (§13.5.2). But for a class handle only the handle is read-only: "The members of the object can be written" (§6.20.6). A "read-only" observer hook is read-only only by discipline. If an observer must never disturb the driver, give it a `clone()` ([I-SV-1: copying and cloning](/curriculum/T2_Intermediate/I-SV-1_OOP/copying-and-cloning)).

Use by value unless the hook genuinely has to substitute a different object; Push Further explains what substituting costs. ([F2D: tasks and functions](/curriculum/T1_Foundational/F2D_Reusable_Code_and_Parallelism/tasks-functions) introduced `ref` and `const ref` on arrays, where `const ref` does make the data read-only.)

### Callbacks or a factory override?

Both let a test change a component without editing it, so they are easy to confuse. They work at different levels:

| | Factory override | Callback |
|---|---|---|
| What it changes | **Which class** is built for a request (§8.3.1) | **What runs at a hook** the class already has |
| Granularity | One class per created object. A type override covers every instance; an instance override covers the paths that match its pattern, so different instances can get different classes (§8.3.1.4.1, §8.3.1.4.2) | Any number of callbacks per object, stacked in queue order |
| When it takes effect | At `create()`: register a component override before the parent's `build_phase` creates it. An object override registered at run time applies to every later `create()` of that type | Whenever `add()` runs; switchable with `callback_mode` during the run |
| Needs | A class you can extend, created through `type_id::create` | A hook the author provided |
| Cost | A lookup at every `create()` | An iterator walk at every hook call, even with an empty queue |

A common misconception says callbacks always replace overrides, or the other way round. They do not compete; they compose. A factory override can install a driver subclass that adds a new hook, and tests then attach callbacks to that hook. Choose by the scenario:

| Scenario | Choose | Why |
|---|---|---|
| Corrupt traffic on one agent, switched on and off during the test | Callback on that instance | Per instance, run-time switchable, no new class |
| Delay, corruption and logging, owned by different people, on one driver | Several callbacks | They stack; a single subclass would merge three concerns into one class |
| A vendor VIP with encrypted source that documents a callback class | Its callbacks | They are the extension point the vendor supports |
| Replace the protocol behaviour of a driver wholesale | Factory override | A hook cannot replace the whole `run_phase` |
| Every item needs a new field and constraint | Factory type override of the **item** type | Callbacks cannot add fields to a class |
| The behaviour you need has no hook | Subclass plus factory override, or ask the VIP owner for a hook | A callback can only act where a hook exists |

[I-UVM-1B](/curriculum/T2_Intermediate/I-UVM-1B_The_UVM_Factory/index) builds the factory version of this error injection, an `err_driver` installed at `env.agt0.drv` with an instance override; compare it with the Make It Work test below.

**When not to use a callback:** when the change is a property of the transaction (put it in the item and its constraints), when you need to replace the whole behaviour (use the factory), or when checking the DUT: a hook in a driver sees what the testbench intended to send, not what the DUT did, so checking belongs in monitors and scoreboards ([A-UVM-6](/curriculum/T3_Advanced/A-UVM-6_Scoreboards_and_Reference_Models/index)).

### Where callbacks live in a real testbench

- **Drivers:** a `pre_send` hook just before driving (corrupt, delay, drop) and a `post_send` hook after it (log, count). This is where error injection happens: the corruption must reach the DUT, and the checker must be told to expect it. Planning which errors to inject and how the scoreboard accounts for them is a planned T3 module on reset handling and error injection (A-UVM-9).
- **Monitors:** a hook after a transaction is captured and before it is written to the analysis port, for extra coverage sampling or protocol-specific logging. A monitor hook sees what really happened on the bus.

  ```systemverilog
  // snippet: inside a monitor's run_phase, after tr is fully captured
  `uvm_do_callbacks(my_monitor, mon_cb, post_capture(this, tr))
  ap.write(tr);
  ```

- **VIP extension points:** a VIP ([A-UVM-7](/curriculum/T3_Advanced/A-UVM-7_VIP_Construction/index)) documents its callback classes and hook order so that users never need its source.
- **UVM itself:** report catchers, objects that can intercept and change messages before they are printed, are callbacks (`uvm_report_catcher extends uvm_callback`, §6.6.1), and so are register callbacks (`uvm_reg_cbs`, §18.11, taught in [A-UVM-4B](/curriculum/T3_Advanced/A-UVM-4B_Advanced_RAL_Techniques/index)). Annex D.4 lists the typedefs UVM provides, such as `uvm_reg_cb` for `uvm_callbacks#(uvm_reg, uvm_reg_cbs)`. Everything on this page about `add(null, ...)` and queue order applies to them too.

### Pitfalls and misconceptions

| Mistake or belief | Why it is wrong |
|---|---|
| "`add(env.agt0.drv, cb)` in a `build_phase` attaches to that driver." | If the driver is not built yet, the handle is null and the call is type-wide; if a handle earlier on the path is null too, reading it stops the simulation (§8.4). |
| "Callbacks run in registration order." | They run in queue order. `UVM_PREPEND`, the copy of the type-wide queue and later type-wide adds all change it. |
| "`UVM_PREPEND` guarantees my callback runs first." | Only at that moment. A later `UVM_PREPEND` add, instance or type-wide, goes in front of it. |
| "A missing `` `uvm_register_cb `` stops the callback." | `add()` only warns `CBUNREG`; the callback is still queued and runs if the hook is called (Annex B.4.1 requires a warning; Push Further). |
| "`const ref` makes the transaction read-only." | It locks the handle; the object's fields can still be written (§6.20.6). |
| "`add_by_name` will find the driver whenever I call it." | It searches the components that exist at that moment, and silently skips matches that are not a `T`. |
| "Callbacks always replace factory overrides." | They act at different levels and compose; each fits different scenarios. |
| Adding or deleting callbacks inside a hook | The iterator walks the live queue; a callback can be skipped or run twice. |
| Checking the DUT from a driver callback | It sees the intended stimulus, not the DUT's behaviour. |
| A hook in a per-bit loop | Every hook call builds an iterator and walks a queue, even when nothing is attached. Hook once per transaction. |

### Recap

- Three parts: an empty-hook `uvm_callback` subclass with a constructor; a component with `` `uvm_register_cb `` and `` `uvm_do_callbacks ``; a concrete callback attached with `add()`.
- A hook walks one queue: the object's own, else the type-wide one, in queue order, enabled callbacks only.
- `add(null, cb)` is type-wide, and so is a handle that is still null. Attach in `connect_phase` or later.
- Order is queue order; check it with `display()`.
- `callback_mode(0/1)` switches an object in every queue; switch between items.
- A callback changes what runs at a hook; the factory changes which class exists. They compose.

## Make It Work

### A two-agent error test

This complete example is the running scenario of the page. Two agents run the same `my_driver`. `base_test` registers a logging callback **type-wide on purpose**, so every driver logs. `err_test` adds a CRC-corrupting callback to `agt0`'s driver only, checks that `agt1`'s driver did not get it, and switches it off after `agt0`'s second item. There is no DUT: the driver waits 10 ns to stand in for driving the pins, then logs what it drove. A real bench checks the CRC in a monitor and scoreboard ([A-UVM-6](/curriculum/T3_Advanced/A-UVM-6_Scoreboards_and_Reference_Models/index)). Each test starts a small sequence on each agent's sequencer ([I-UVM-3A](/curriculum/T2_Intermediate/I-UVM-3A_Fundamentals/index)) and raises an objection in `run_phase` to keep the phase open until the sequences finish ([I-UVM-1C](/curriculum/T2_Intermediate/I-UVM-1C_UVM_Phasing/index)).

```systemverilog
// compile
// File: cb_demo.sv. Run with +UVM_TESTNAME=err_test
`timescale 1ns/1ps
`include "uvm_macros.svh"

package cb_demo_pkg;
  import uvm_pkg::*;

  // ---------------------------------------------------------------- item
  class packet extends uvm_sequence_item;
    rand bit [7:0] data;
    bit [7:0]      crc;  // a toy "CRC" so the log can show corruption

    `uvm_object_utils(packet)

    function new(string name = "packet");
      super.new(name);
    endfunction

    function void post_randomize();
      crc = data ^ 8'hA5;
    endfunction
  endclass

  // ------------------------------------- part 1: the callback base class
  typedef class my_driver;

  virtual class drv_cb extends uvm_callback;
    function new(string name = "drv_cb");
      super.new(name);
    endfunction

    // Empty, not pure: callbacks override only the hooks they need.
    virtual task pre_send(my_driver drv, packet pkt);
    endtask
  endclass

  // ------------------------------- part 2: the component offering a hook
  class my_driver extends uvm_driver #(packet);
    `uvm_component_utils(my_driver)
    `uvm_register_cb(my_driver, drv_cb)

    function new(string name, uvm_component parent);
      super.new(name, parent);
    endfunction

    task run_phase(uvm_phase phase);
      forever begin
        seq_item_port.get_next_item(req);
        `uvm_do_callbacks(my_driver, drv_cb, pre_send(this, req))
        #10ns;  // stands in for driving the pins
        `uvm_info("DRV", $sformatf("drove data=%02h crc=%02h %s", req.data, req.crc,
                  (req.crc == (req.data ^ 8'hA5)) ? "crc ok" : "CRC CORRUPT"), UVM_LOW)
        seq_item_port.item_done();  // after driving: item boundaries are exact
      end
    endtask
  endclass

  // ------------------------------------------- sequence, agent and env
  class pkt_seq extends uvm_sequence #(packet);
    `uvm_object_utils(pkt_seq)
    int unsigned n_items = 2;

    function new(string name = "pkt_seq");
      super.new(name);
    endfunction

    task body();
      repeat (n_items) begin
        req = packet::type_id::create("req");
        start_item(req);
        if (!req.randomize()) `uvm_fatal("RAND", "packet randomization failed")
        finish_item(req);
      end
    endtask
  endclass

  class my_agent extends uvm_agent;
    `uvm_component_utils(my_agent)
    my_driver               drv;
    uvm_sequencer #(packet) sqr;

    function new(string name, uvm_component parent);
      super.new(name, parent);
    endfunction

    function void build_phase(uvm_phase phase);
      super.build_phase(phase);
      drv = my_driver::type_id::create("drv", this);
      sqr = uvm_sequencer#(packet)::type_id::create("sqr", this);
    endfunction

    function void connect_phase(uvm_phase phase);
      drv.seq_item_port.connect(sqr.seq_item_export);
    endfunction
  endclass

  class my_env extends uvm_env;
    `uvm_component_utils(my_env)
    my_agent agt0, agt1;

    function new(string name, uvm_component parent);
      super.new(name, parent);
    endfunction

    function void build_phase(uvm_phase phase);
      super.build_phase(phase);
      agt0 = my_agent::type_id::create("agt0", this);
      agt1 = my_agent::type_id::create("agt1", this);
    endfunction
  endclass

  // ---------------------------------- part 3: concrete callbacks (tests)
  class crc_err_cb extends drv_cb;
    `uvm_object_utils(crc_err_cb)

    function new(string name = "crc_err_cb");
      super.new(name);
    endfunction

    virtual task pre_send(my_driver drv, packet pkt);
      pkt.crc = ~pkt.crc;  // by-value handle: the write reaches the driver's req
    endtask
  endclass

  class crc_log_cb extends drv_cb;
    `uvm_object_utils(crc_log_cb)

    function new(string name = "crc_log_cb");
      super.new(name);
    endfunction

    virtual task pre_send(my_driver drv, packet pkt);
      // _context: report as the driver, so the log names the right agent
      `uvm_info_context("LOG", $sformatf("pre_send sees data=%02h crc=%02h",
                        pkt.data, pkt.crc), UVM_LOW, drv)
    endtask
  endclass

  // ---------------------------------------------------------------- tests
  class base_test extends uvm_test;
    `uvm_component_utils(base_test)
    my_env       env;
    crc_log_cb   log_cb;
    int unsigned n_items = 4;  // items per agent

    function new(string name, uvm_component parent);
      super.new(name, parent);
    endfunction

    function void build_phase(uvm_phase phase);
      super.build_phase(phase);
      env    = my_env::type_id::create("env", this);
      log_cb = crc_log_cb::type_id::create("log_cb");
      // null ON PURPOSE: type-wide, so every my_driver logs, even ones built later
      uvm_callbacks#(my_driver, drv_cb)::add(null, log_cb);
    endfunction

    task run_phase(uvm_phase phase);
      pkt_seq s0 = pkt_seq::type_id::create("s0");
      pkt_seq s1 = pkt_seq::type_id::create("s1");
      s0.n_items = n_items;
      s1.n_items = n_items;
      phase.raise_objection(this);
      fork
        s0.start(env.agt0.sqr);
        s1.start(env.agt1.sqr);
      join
      phase.drop_objection(this);
    endtask
  endclass

  class err_test extends base_test;
    `uvm_component_utils(err_test)
    crc_err_cb err_cb;

    function new(string name, uvm_component parent);
      super.new(name, parent);
    endfunction

    // By connect_phase every component exists: env.agt0.drv is the real driver.
    function void connect_phase(uvm_phase phase);
      super.connect_phase(phase);
      if (env.agt0.drv == null) `uvm_fatal("CBNULL", "env.agt0.drv is null")
      err_cb = crc_err_cb::type_id::create("err_cb");
      uvm_callbacks#(my_driver, drv_cb)::add(env.agt0.drv, err_cb);
    endfunction

    // Show every queue, and prove that agt1's driver did not get err_cb.
    function void end_of_elaboration_phase(uvm_phase phase);
      drv_cb cbs[$];
      super.end_of_elaboration_phase(phase);
      uvm_callbacks#(my_driver, drv_cb)::display();
      uvm_callbacks#(my_driver, drv_cb)::get_all(cbs, env.agt1.drv);
      foreach (cbs[i])
        if (cbs[i] == err_cb) `uvm_fatal("CBLEAK", "err_cb reached env.agt1.drv")
    endfunction

    task run_phase(uvm_phase phase);
      pkt_seq a = pkt_seq::type_id::create("a");  // agt0 items 1-2: errors on
      pkt_seq b = pkt_seq::type_id::create("b");  // agt0 items 3-4: errors off
      pkt_seq c = pkt_seq::type_id::create("c");  // agt1: 4 clean items
      c.n_items = 4;
      phase.raise_objection(this);
      fork
        begin
          a.start(env.agt0.sqr);
          // a.start() returned after item_done() of item 2, and item 3 does not
          // exist yet: an exact item boundary for this driver.
          void'(err_cb.callback_mode(0));
          b.start(env.agt0.sqr);
        end
        c.start(env.agt1.sqr);
      join
      phase.drop_objection(this);
    endtask
  endclass
endpackage

module tb_top;
  import uvm_pkg::*;
  import cb_demo_pkg::*;

  initial run_test();  // +UVM_TESTNAME=err_test (or base_test)
endmodule
```

- **`log_cb` logs the CRC before corruption** on `agt0` (`99`, then `66` on the pins), because it is ahead of `err_cb` in that queue. A log callback is a debugging aid, not a check.
- **No `CBUNREG`, `CBPREG` or `CBNOMTC` warnings**, and the `CBLEAK` guard did not fire.

With `+UVM_TESTNAME=base_test` both agents log and drive four clean items, and `display()` is not called.

The open-source Verilator flow has limited UVM support, so it is not a verified option for this example. **How to add a callback to a component and use it from a test:**

1. In the component's package, declare the callback base class: `virtual class ... extends uvm_callback`, with a `new(string name = ...)` that calls `super.new(name)`, and one empty virtual method per hook.
2. In the component, add `` `uvm_register_cb(<component>, <callback base>) `` and call each hook with `` `uvm_do_callbacks `` at the right point (a task hook only from a task).
3. In the test's package, extend the base and override only the hooks you need. Register it with `` `uvm_object_utils `` and give it a constructor.
4. In the test, create the callback with `::type_id::create`.
5. In `connect_phase` (or later), check that the handle is not null and call `add(handle, cb)`; use `add(null, cb)` only when you want every instance.
6. In `end_of_elaboration_phase`, print the queues with `display()`, and guard the intent with `get_all()`. `get_all()` also returns disabled callbacks (§10.7.2.5), so filter with `is_enabled()` if you mean "will run".
7. Switch the callback with `callback_mode(0/1)` between items, at a point where you know which items have been driven.

## Push Further

### Expert: what `` `uvm_register_cb `` really checks

In uvm-core 2020.3.1 the macro declares a static bit, `static local bit m_register_cb_<CB>`, whose initializer records the `(T, CB)` pair. Because the bit's name is built from `CB`, a **parameterized** callback type causes errors; use a `typedef` name instead (Annex B.4.1). The pair is checked only when someone adds or deletes: an unregistered pair makes `add()` warn `CBUNREG` (B.4.1 requires only a warning), and uvm-core then queues the callback anyway. Iteration never checks registration, so the callback runs. A team that wants this to fail loudly can promote the warning. The callback functions report through `uvm_root`, so set the override there, before any `add()` runs (§6.3.7):

```systemverilog
// snippet: in the test's build_phase, before any add()
uvm_root::get().set_report_severity_id_override(UVM_WARNING, "CBUNREG", UVM_ERROR);
```

This also promotes the delete-side `CBUNREG` ("cannot be removed"). An override set on the test or the env does nothing here, because those are not the reporting object (uvm-core 2020.3.1 by source inspection). `+uvm_set_severity` (Annex G.2.5) can do the same from the command line if its component pattern reaches `uvm_root`; confirm in the log that it took effect.

### Expert: callbacks on derived and factory-substituted components

Instance queues are keyed by the **object**, so a callback added with `add(env.agt0.drv, cb)` after build follows whatever class the factory built there. Two consequences:

- If a factory override installs a driver subclass whose `run_phase` does not call `` `uvm_do_callbacks ``, every callback on that driver goes silent, with no message. Subclass authors should call `super.run_phase` or keep the hook line.
- A hook names its `T` in the macro. If a subclass `my_err_driver` calls `` `uvm_do_callbacks(my_err_driver, drv_cb, ...) ``, type-wide callbacks registered through `uvm_callbacks#(my_driver, drv_cb)` do not reach it unless the subclass declares `` `uvm_set_super_type(my_err_driver, my_driver) `` (Annex B.4.2: "This allows for derived class objects to inherit type-wide callbacks that are registered with the base class"). An inherited `run_phase` that still names `my_driver` needs nothing extra.

uvm-core recommends a pattern for component authors: a **virtual method** per hook whose default body runs the callbacks (`uvm_callback.svh` class comment). Users can then extend by inheritance (override the method, call `super`) or by callbacks, and a subclass can disable the hook deliberately.

### Expert: veto hooks, other objects and manual iteration

`` `uvm_do_callbacks_exit_on(T, CB, METHOD, VAL) `` (B.4.5) calls a `bit` hook on each enabled callback and **returns** `VAL` from the enclosing function as soon as one callback returns `VAL`; if none does, it returns `1 - VAL` after the loop. It always returns, so it must be the last statement of a function that returns `bit`:

```systemverilog
// snippet: inside my_driver; drv_cb declares virtual function bit drop(my_driver d, packet p)
function bit any_drop(packet pkt);
  `uvm_do_callbacks_exit_on(my_driver, drv_cb, drop(this, pkt), 1)
endfunction
```

`` `uvm_do_obj_callbacks(T, CB, OBJ, METHOD) `` (B.4.4) runs the callbacks registered with another object, for example a sequence that runs its sequencer's callbacks; `` `uvm_do_obj_callbacks_exit_on `` (B.4.6) combines both. One macro gotcha: the expansion declares local variables named `iter` and `cb`, so an unqualified identifier `cb` or `iter` in the `METHOD` arguments binds to the macro's locals, not to your variable (uvm-core 2020.3.1, `uvm_callback_defines.svh`). A qualified name such as `vif.cb` is safe.

### Expert: queue internals in uvm-core 2020.3.1

These are implementation details found by reading `uvm_callback.svh`, not rules of IEEE 1800.2; confirm them on your simulator before you rely on them.

- **One global pool.** Every instance queue lives in one pool keyed by object, shared by all `(T, CB)` pairs; iteration filters entries by type. So `display()` for `(my_driver, drv_cb)` lists every callback in a driver's queue, including report catchers.
- **An instance add for another pair can hide type-wide callbacks.** The first instance add for an object seeds its queue with the type-wide report catchers and the type-wide queue of **that** add's `T`. If `log_cb` was added type-wide for `(my_driver, drv_cb)` and a colleague later adds a report catcher to `agt0.drv` with `uvm_report_cb::add(env.agt0.drv, demoter)`, `agt0.drv` now has a pool queue without `log_cb` and stops logging, while `agt1.drv` still logs.
- **An empty queue is re-seeded.** If an object's queue is empty when an instance `add()` runs, it is filled again from the type-wide queue, so a type-wide callback you deleted from that instance can come back.
- **`delete` on an object with no queue.** `delete(obj, cb)` for an object that never had an instance queue looks up a queue that does not exist and dereferences a null handle, where §10.7.2.3.3 expects a warning. Use `delete(null, cb)` for type-wide callbacks.
- **Live index.** `get_next` continues from a stored position in the current queue, which is why changing the queue inside a hook skips or repeats callbacks.

### Expert: `callback_mode()` corner cases

IEEE 1800.2-2020 §10.7.1.2.2 declares `function bit callback_mode(int on = -1)` but its prose says "The default value of on shall be 1". uvm-core follows the declaration: `-1` (or any value other than 0 and 1) only queries, and `is_enabled()` is implemented as `callback_mode()`. Do not rely on the default: always pass 0 or 1 to change the mode, and call `is_enabled()` to ask. The call returns the previous mode, which makes save-and-restore easy (`bit was = cb.callback_mode(0); ... void'(cb.callback_mode(was));`). The mode belongs to the object, so it affects every queue that holds it, including the type-wide one. With `UVM_CB_TRACE_ON`, every query also logs a trace line, because the iterator calls `callback_mode()` for each entry.

### Expert: item-accurate run-time toggling

"Errors on items 1 and 2 only" is exact only if you know where item boundaries are in the driver.

- **`get_next_item`, drive, `item_done`:** the sequence's `finish_item` returns only after `item_done`, and the next item cannot reach the hook until the sequence sends it. A toggle between two sequence calls, or after `finish_item` in the sequence, is exact (Make It Work).
- **`get()` or a pipelined driver:** `item_done` happens inside `get()`, so the sequence side and the driver both continue in the same time slot, and the standard leaves their order open (IEEE 1800-2023 §4.7). The boundary item races the toggle. A time-consuming hook earlier in the queue, such as a prepended delay, widens the window.
- **An `add()` at time 0 of `run_phase`** races the first item in the same way.

Patterns that avoid the race: count inside the callback (one object per driver), let the sequence set a field on the items it wants corrupted, or attach and switch before `run_phase` starts.

### Expert: `ref` hooks and sequence-item identity

A `ref` hook argument must have a type **equivalent** to the actual (IEEE 1800-2023 §13.5.2, "No casting shall be permitted"), so a generic hook declared with `ref uvm_sequence_item item` cannot be called with the driver's `req` of type `packet`. And when a hook swaps the object, three things break: the sequence still holds the original handle and never sees the new one; the new object lacks the sequence and transaction ids, so responses are misrouted unless the hook copies them with `set_id_info` (IEEE 1800.2-2020 §14.1.2.4); and any reference the sequence or a scoreboard kept now points at a stale object. Mutate in place (by value is enough), or clone for observers.

### Expert: cost at scale (tool-dependent)

In uvm-core 2020.3.1 every hook call constructs a `uvm_callback_iter`, does pool lookups for the object, and calls `$cast` and `callback_mode()` on each entry, even when no callback is registered. That is cheap per transaction and expensive per bit or per clock. Put hooks at transaction granularity, compile `UVM_CB_TRACE_ON` only for debug (it adds a message per add, delete and execution), and measure with your simulator's profiler before optimizing ([E-PERF-1](/curriculum/T4_Expert/E-PERF-1_UVM_Performance/index)). The actual cost depends on the tool.

### Expert: designing a VIP extension API

When you write a VIP, you choose how users extend it: configuration knobs (values), sequence-level control (stimulus), factory overrides (classes), virtual-method hooks (inheritance) and callbacks (stackable objects). A good callback API:

- names its hook points by protocol event (`pre_send`, `post_capture`), and documents the order in which they are called and what each may change;
- passes transactions by value unless substitution is a supported use, and says whether a hook may consume time;
- provides empty default hooks, a constructor in the base class and `` `uvm_register_cb `` for every component that calls them;
- pairs each hook with a virtual method, as uvm-core suggests, so users can choose inheritance or callbacks;
- states which hooks exist in monitors (observe) and which in drivers (modify).

UVM uses the same design for its own extension points: report catchers (§6.6.1; `uvm_report_cb`, D.4.3), register callbacks (§18.11; D.4.5), objection callbacks (D.4.2) and phase callbacks (D.4.1). Customizing methodology at this level is the subject of [E-CUST-1](/curriculum/T4_Expert/E-CUST-1_UVM_Methodology_Customization/index).

### Kata: stack and switch

**Objective:** stack two test callbacks on one driver, predict the queues, and make one of them switch itself off after a fixed number of items.

Start from the Make It Work bench.

1. Write `delay_cb`, a `drv_cb` whose `pre_send` waits a random 1 to 3 "cycles" of 10 ns.
2. Write `limited_err_cb`, a `crc_err_cb` that corrupts only its first 4 items and then switches itself off with `callback_mode(0)`.
3. Write `kata_test extends base_test`. In `connect_phase`, add `err_cb` (a `limited_err_cb`) to `env.agt0.drv`, then add `dly_cb` (a `delay_cb`) to the same driver with `UVM_PREPEND`. Run 6 items per agent, and call `display()` in `end_of_elaboration_phase`.
4. **Before you run it**, write down both drivers' queues in order, and the `display()` output.
5. **Acceptance:** exactly 4 `CRC CORRUPT` lines, all on `agt0`, for its first 4 items; 6 clean items on `agt1`; `display()` matches your prediction; no `CBUNREG`, `CBPREG` or `CBNOMTC` in the log.

<details>
<summary>Worked solution (try the kata first)</summary>

```systemverilog
// snippet: add to cb_demo_pkg after crc_log_cb; run with +UVM_TESTNAME=kata_test
class delay_cb extends drv_cb;
  `uvm_object_utils(delay_cb)
  int unsigned max_cycles = 3;

  function new(string name = "delay_cb");
    super.new(name);
  endfunction

  // A task hook may consume time: the driver waits here before driving.
  virtual task pre_send(my_driver drv, packet pkt);
    #($urandom_range(max_cycles, 1) * 10ns);
  endtask
endclass

class limited_err_cb extends crc_err_cb;
  `uvm_object_utils(limited_err_cb)
  int unsigned n_left = 4;  // shared by every queue that holds this object

  function new(string name = "limited_err_cb");
    super.new(name);
  endfunction

  virtual task pre_send(my_driver drv, packet pkt);
    super.pre_send(drv, pkt);  // corrupt this item
    n_left--;
    // Switching the mode inside the hook is safe: the queue does not change.
    if (n_left == 0) void'(callback_mode(0));
  endtask
endclass

class kata_test extends base_test;
  `uvm_component_utils(kata_test)
  limited_err_cb err_cb;
  delay_cb       dly_cb;

  function new(string name, uvm_component parent);
    super.new(name, parent);
    n_items = 6;
  endfunction

  function void connect_phase(uvm_phase phase);
    super.connect_phase(phase);
    err_cb = limited_err_cb::type_id::create("err_cb");
    dly_cb = delay_cb::type_id::create("dly_cb");
    uvm_callbacks#(my_driver, drv_cb)::add(env.agt0.drv, err_cb);
    uvm_callbacks#(my_driver, drv_cb)::add(env.agt0.drv, dly_cb, UVM_PREPEND);
  endfunction

  function void end_of_elaboration_phase(uvm_phase phase);
    super.end_of_elaboration_phase(phase);
    uvm_callbacks#(my_driver, drv_cb)::display();
  endfunction
endclass
```

**The prediction.** `agt0.drv`'s queue is created by the first instance add as a copy of the type-wide queue (`log_cb`), then `err_cb` is appended and `dly_cb` prepended: `dly_cb`, `log_cb`, `err_cb`. `agt1.drv` has no instance queue and walks the type-wide queue: `log_cb`. So `display()` prints (illustrative, by the uvm-core 2020.3.1 format):

```text
Registered callbacks for all instances of my_driver
---------------------------------------------------------------
log_cb   (*) on                         ON
dly_cb   uvm_test_top.env.agt0.drv on   ON
log_cb   uvm_test_top.env.agt0.drv on   ON
err_cb   uvm_test_top.env.agt0.drv on   ON
```

**Why it meets the acceptance.** `err_cb` corrupts items 1 to 4, and after the fourth it switches itself off, so `first()`/`next()` skip it for items 5 and 6. The count is exact because the decision is made inside the hook, where there is no race with a test thread. The counter is per object, so this works only because the object is on one driver; added type-wide or to both drivers, it would count both drivers' items together. `dly_cb` is first in the queue, so each `agt0` item waits 10 to 30 ns before `log_cb` and `err_cb` run, which spreads `agt0`'s lines out in time relative to `agt1`'s.
