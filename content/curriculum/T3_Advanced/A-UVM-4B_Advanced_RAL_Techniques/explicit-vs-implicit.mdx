## Quick Take

- **What it is:** A register model keeps a **mirrored value** for every register: what the testbench (TB) believes the design under test (DUT) holds. **Prediction** is the act of updating that mirror from an access. UVM gives you two ways to do it. **Implicit (auto) prediction**, `map.set_auto_predict(1)`, updates the mirror when the register model's own `read()` or `write()` finishes. **Explicit prediction** is a `uvm_reg_predictor` component fed by a bus monitor: it updates the mirror from every transfer seen on the bus, whoever started it (IEEE 1800.2-2020 §18.2.5.2, §19.3).
- **Why it matters:** Every register check compares the DUT with the mirror. If nothing predicts an access, or the wrong thing predicts it, the mirror silently drifts away from the DUT. You then get false failures (a correct DUT reported as wrong) or false passes (a check that compares stale values). By default neither form of prediction is switched on, so this is a choice every environment has to make.
- **The Analogy:** The mirror is your chequebook ledger and the DUT is your bank account. Implicit prediction records only the cheques *you* write. Explicit prediction reconciles every line of the bank statement, including direct debits made by someone else (firmware, a DMA engine). Passive prediction is reconciling the statement of an account you never write cheques on. *Where it breaks:* the bank also changes balances by itself, as hardware does when it sets a status bit, and no statement line shows it. No prediction mode can see that change; you have to read the register, call `predict()`, or mark the field as volatile.

**You will be able to:**
1. **Choose** implicit (auto) prediction, explicit prediction or passive prediction for a bus, from who can access the registers on that bus.
2. **Wire** an explicit predictor (`map`, `adapter`, `bus_in`) on the root map, with auto-predict off so that no access is predicted twice.
3. **Predict** the mirrored value after a register-model access, another initiator's access and a hardware change, under each prediction set-up.
4. **Debug** a stale or wrong mirror from its symptoms and log: a missing `connect()`, a null adapter, a sub-map, a wrong `bus2reg()`, `UVM_NOT_OK`, `provides_responses`, double prediction or a `predict()` race.
5. **Configure** passive checking with `set_check_on_read(1)`, and handle hardware-driven fields with `volatile` or `predict()` so that they cause no false mismatches.

## Build Your Mental Model

### The words this lesson builds on

[A-UVM-4A: RAL Fundamentals](/curriculum/T3_Advanced/A-UVM-4A_RAL_Fundamentals/index) built the register model. Here is the vocabulary this page uses, one line each:

- **Register model** (or RAL, the register abstraction layer): the `uvm_reg_block` object that describes the DUT's registers and fields.
- **Desired value** (`get()`): what the test wants a field to hold. **Mirrored value** (`get_mirrored_value()`): what the model believes the DUT holds. Neither one *is* the DUT.
- **Access policy**: the rule a field follows when written or read, such as RW (read-write), RO (read-only), W1C (write 1 to clear) or W1T (write 1 to toggle).
- **Address map** (`uvm_reg_map`): places registers at bus addresses. The **root map** is the top-most map, the one the bus actually sees (§18.2.4.1). In a one-level model, `default_map` is the root map.
- **Frontdoor access**: a real bus transfer. The map turns `write()` or `read()` into a bus **sequence item** with the **adapter** (`uvm_reg_adapter`), whose `reg2bus()` builds the item and whose `bus2reg()` turns a finished item back into a generic operation (§19.2.1). **Backdoor access**: reading or depositing the HDL signal directly, with no bus transfer; [Frontdoor vs. Backdoor Access](/curriculum/T3_Advanced/A-UVM-4B_Advanced_RAL_Techniques/frontdoor-vs-backdoor), the next lesson, covers it.
- **Bus monitor** and **analysis port**: the agent component that watches the pins and publishes one transaction object per observed transfer through its analysis port `ap` ([I-UVM-2B: TLM Connections](/curriculum/T2_Intermediate/I-UVM-2B_TLM_Connections/index)).

**Prediction** means updating the mirror (and the desired value) from an access, applying each field's access policy. The register calls its `do_predict()` method to do it. The question this page answers is: *who* calls it, and for *which* accesses?

### Three set-ups, and the default

| Set-up | How you turn it on | Who updates the mirror | Sees accesses the register model did not start? |
| --- | --- | --- | --- |
| **Implicit** (auto-predict) | `ral.default_map.set_auto_predict(1);` | The register itself, as its own `write()` or `read()` completes | No |
| **Explicit** | a `uvm_reg_predictor` with `map` and `adapter` set, and `agent.mon.ap.connect(predictor.bus_in);` | The predictor, for every transfer the monitor publishes | Yes |
| **Passive** | an explicit predictor on a bus that the register model never drives | The predictor only | Yes: it sees *only* other initiators |
| **Neither** (the default) | nothing | Nobody: frontdoor accesses leave the mirror alone | No |

The default is **neither**. `uvm_reg_map::new()` sets auto-predict to 0 (uvm-core 2020.3.1 `uvm_reg_map.svh`), §18.2.5.2 says auto-predict is off by default, and no predictor exists until you build one. In uvm-core 2020.3.1 even `mirror()` does not update the mirror through the frontdoor unless one of the two modes is active; the expert section below notes that the standard's text is not consistent on this point.

Two more things move the mirror without any prediction mode: `predict()`, which you call yourself, and `reset()`, which loads the reset values (§18.4.4.15, §18.4.4.5). In uvm-core 2020.3.1, backdoor `poke()` and `peek()` also update the mirror themselves; the next lesson covers them.

### Implicit (auto) prediction: the register predicts its own accesses

**Definition.** With `set_auto_predict(1)` on the root map, the register model "automatically updates its mirror ... immediately after any bus read or write operation via this map": before `write()` or `read()` returns, the register's predict method updates the mirrored value (§18.2.5.2). It covers every frontdoor access the register model starts through that map: `write()`, `read()`, `update()` (which calls `write()`) and `mirror()` (which reads through the same path as `read()`).

**What it predicts.**

- For a **write**, the value the test *asked* to write, passed through each field's policy. Writing `'hFFFF_FFFF` to a register whose upper bits are RO leaves those mirror bits unchanged.
- For a **read**, the data `bus2reg()` returned from the finished item, again through each field's policy. A read of an RC (read-to-clear) field predicts 0.
- Nothing, if the access ended with status `UVM_NOT_OK`: the register warns `PREDICT_NOK` "status UVM_NOT_OK; skip prediction." (uvm-core `uvm_reg.svh`).

**What it never sees.** Anything that does not go through this register model's `read()` and `write()`: firmware running on a CPU model, a DMA engine, another agent, or a plain bus sequence that bypasses the model. It also trusts the adapter round trip: it mirrors what you *asked* for, so a `reg2bus()` bug that corrupts write data shows up only when a later read is checked.

### Explicit prediction: a predictor on the bus monitor

**Definition.** `uvm_reg_predictor #(BUSTYPE)` is a component that "is used to update the register model's mirror values based on transactions explicitly observed on a physical bus" (§19.3). `BUSTYPE` is your bus item class. It has two ports and two handles you must set (§19.3.2):

| Member | Kind | What you do with it |
| --- | --- | --- |
| `bus_in` | analysis imp | connect the bus monitor's analysis port to it |
| `reg_ap` | analysis port | optional: publishes a `uvm_reg_item` for every predicted access, for a register scoreboard |
| `map` | `uvm_reg_map` handle | set it to the **root** map that decodes this bus's addresses |
| `adapter` | `uvm_reg_adapter` handle | set it to an adapter for this bus; the predictor only calls its `bus2reg()` |

**Purpose.** It sees every transfer on the bus, so the mirror follows firmware, DMA and other initiators as well as the register model's own accesses. That is why it is the normal choice for production environments.

**Wiring.** Five lines in the environment's `connect_phase`, after the predictor is created in `build_phase`; the second only restates the default, to make the choice visible. This excerpt is from the Make It Work example below:

```systemverilog
// snippet: demo_env::connect_phase, explicit prediction
ral.default_map.set_sequencer(agent.sqr, adapter);  // frontdoor path for RAL calls
ral.default_map.set_auto_predict(0);                // the default: nobody predicts twice
predictor.map     = ral.default_map;                // the root map decodes the address
predictor.adapter = adapter;                        // bus2reg() for each observed item
agent.mon.ap.connect(predictor.bus_in);             // the line that makes it explicit
```

**What each missing line does.** This is the core debugging knowledge for explicit prediction:

- **No `connect()`:** nothing reports an error. An analysis port may legally have no subscribers, so the predictor simply never runs and the mirror never moves.
- **No `predictor.adapter`:** the first observed transfer stops the run with `UVM_FATAL ... [REG/WRITE/NULL] write: adapter handle is null` (uvm-core `uvm_reg_predictor.svh`).
- **No `predictor.map`:** the first observed transfer dereferences a null handle inside the predictor's `write()`; the wording of the null-object error is tool-dependent.
- **No `set_sequencer()`:** the register model's own frontdoor calls cannot reach the bus, but the predictor still follows other initiators.
- **Auto-predict also on:** every register-model access is predicted twice (see [double prediction](#double-prediction-and-how-to-choose) below).

Three consequences to remember:

- **The mirror follows the bus, not the request.** The predictor mirrors the data the monitor saw, through the field policies. A `reg2bus()` bug that corrupts write data therefore shows up in the mirror at once.
- **Address decoding needs the root map and a locked model.** `get_reg_by_offset()` works only after `lock_model()` (§18.2.4.17); otherwise it reports `Cannot get register by offset: Block ral is not locked.` In uvm-core the address table lives only in the root map, so a predictor bound to a sub-map finds nothing.
- **Memories are never predicted** ("Memories can be large, so their accesses are not predicted", §19.3). Check memory contents by reading them back.

**Debrief.**

- Firmware traffic reaches the mirror only through the predictor. Auto-predict runs inside the register model's own `write()`, so it never sees a write it did not issue: the mirror stays at its reset value.
- With both paths on, the RW write to CTRL still looks right, because predicting `'h5` twice gives `'h5`. The W1T write does not: the LED toggles once in the DUT but twice in the mirror, so the mirror ends where it started.
- Open the **Debug** mode: the mirror never updates even though the DUT changes. Use the suspects to find the one line that is missing; the [debug table](#debugging-a-stale-mirror) below lists the rest.

### Passive prediction and check-on-read

**Passive prediction** is an explicit predictor on a bus that the register model never drives. A typical case is an SoC test in which firmware on a CPU model programs a block: the UVM environment has a passive agent (monitor only) on that bus, the register model, and a predictor. The mirror then follows what firmware does, and the test reads it with `get_mirrored_value()` instead of touching the bus.

A passive predictor becomes a **register checker** with one more line:

```systemverilog
// snippet: passive checking of firmware reads
ral.default_map.set_check_on_read(1);   // compare each observed read with the mirror
```

With check-on-read on, the predictor compares every observed **read** with the current mirror before it predicts, and reports a mismatch with the same `RegModel` error that `mirror(UVM_CHECK)` uses (§18.2.5.3, which calls the mode "useful when the register model is used passively"). The mirror is then updated from the read data whatever the result.

Two conditions make passive checking trustworthy:

- **Hardware-driven fields must be volatile.** A field configured with `volatile = 1` gets the compare policy `UVM_NO_CHECK` in `configure()` (uvm-core `uvm_reg_field.svh`), so it is skipped by the compare but still predicted. A status bit set by hardware and configured `volatile = 0` produces a mismatch on every firmware read that follows a hardware change: a false failure.
- **Writes must be predicted too.** Check-on-read only compares reads. The writes that firmware makes are predicted by the same predictor, which is what makes the later comparisons meaningful.

### Double prediction, and how to choose

**Double prediction** happens when auto-predict is on *and* a connected predictor watches the same bus. Each register-model access is then predicted once by the register and once by the predictor. The order is not fixed: the predictor runs when the monitor publishes, auto-predict runs when the item finishes. Either order gives the same result:

| Field policy | Prediction after one write of `v` | After two predictions | Visible? |
| --- | --- | --- | --- |
| RW | `v` | `v` | No |
| W1C | `mirror & ~v` | `mirror & ~v` | No |
| W1S | `mirror \| v` | `mirror \| v` | No |
| W1T | `mirror ^ v` | `mirror ^ v ^ v = mirror` | **Yes:** the toggle is undone |

So double prediction hides on most registers and breaks toggle fields, which makes it a classic late-found bug. The policy formulas are uvm-core 2020.3.1 `uvm_reg_field::XpredictX`, an internal method that applies a field's policy; never call it yourself.

**How to choose**, per bus:

1. **Can anything other than the register model access registers on this bus** (firmware, a DMA, another agent, a raw bus sequence)? Then use **explicit** prediction on that bus's monitor. This is the normal production set-up.
2. **Does the register model never drive this bus?** Then the predictor is **passive**; add `set_check_on_read(1)` if you want firmware reads checked.
3. **Is the register model the only initiator, and is there no monitor yet** (early bring-up)? Then **implicit** prediction is acceptable. Replace it with a predictor once the monitor exists.
4. **Never both on one map.** Turn auto-predict off whenever a predictor is connected.

### When the mirror goes stale

Each set-up has blind spots. A stale mirror is not a bug in itself; checking against a stale mirror is.

| What changed the DUT register | Implicit | Explicit | Passive | Remedy |
| --- | --- | --- | --- | --- |
| Register-model `write()`, `read()`, `update()`, `mirror()` through the map | predicted when the call completes | predicted when the monitor publishes | (no such accesses) | — |
| Firmware, DMA or a raw sequence on the same bus | **stale** | predicted | predicted | explicit prediction |
| An access on another bus port with no predictor | stale | stale | stale | a predictor on every bus port (see the module index for multiple maps) |
| The hardware itself: status bits, counters, interrupt flags | **stale** | **stale** | **stale** | read the register, call `predict()`, and make the field volatile |
| A DUT reset in the middle of a test | stale | stale | stale | `ral.reset()` (see the expert note on reset) |
| An access that ended with `UVM_NOT_OK` | not predicted | not predicted | not predicted | intended, but an error does not prove the register is unchanged: an APB write that gets an error may still have updated it (Arm IHI 0024C §3.4). Read the register back after the error (for example with `mirror()`) so prediction relearns it, or model the peripheral's documented behaviour ([B-APB-1](/curriculum/T3_Advanced/B-APB-1_APB_Protocol_and_Verification/index)) |
| Backdoor `poke()` or `peek()` | predicted by the call itself (uvm-core) | same; the monitor sees no bus traffic | same | none needed in uvm-core 2020.3.1 |

**Hardware changes, traced.** The hardware sets INT_STATUS.ERR (W1C) when the test programs an illegal mode, as in the Make It Work example. Explicit prediction is on:

| Step | DUT ERR | Mirrored ERR | What happened |
| --- | --- | --- | --- |
| 0. After reset | 0 | 0 | `ral.reset()` and the DUT reset agree |
| 1. `ral.ctrl.write(st, 'hD)` sets MODE = 3 | **1** | 0 | No access to INT_STATUS, so nothing predicts it: the mirror is stale |
| 2. `ral.int_status.mirror(st, UVM_CHECK)` | 1 | 1 | ERR is volatile (`UVM_NO_CHECK`), so no error; the predictor then learns 1 from the read. With `volatile = 0` this step reports a false mismatch |
| 3. `ral.int_status.write(st, 'h1)` | 0 | 0 | W1C: the predictor computes `1 & ~1 = 0`, matching the DUT |

**`predict()` versus volatile.** When the TB *knows* the hardware changed a field, for example because an interrupt line rose, it can tell the model with `predict()`. That is a **direct** prediction (`UVM_PREDICT_DIRECT`): the value is stored as is, with no policy applied (§17.2.2.8, §18.5.5.17). It is not "explicit prediction", which is the predictor component. Check the return value, because a prediction made while the register is in the middle of an access is refused:

```systemverilog
// snippet: in the env; vif.irq is an interrupt line (not part of the Make It Work bus)
task note_hw_error();
  forever begin
    @(posedge vif.irq);
    // predict() is refused while ral.int_status is being read or written
    // (is_busy(), §18.4.4.16), so let the access in flight finish first.
    while (ral.int_status.is_busy()) @(posedge vif.clk);
    if (!ral.int_status.predict(32'h1))
      `uvm_error("PREDICT", "ral.int_status.predict('h1) was refused")
  end
endtask
```

The busy test and the `predict()` call run with no time passing between them, so no access can start in between. This uses the register-level `predict()`, which leaves the mirror unchanged if it ever refuses. The field-level `ral.int_status.err.predict(1)` behaves differently in uvm-core 2020.3.1: it warns, returns 0 and *still* writes the mirror, which the access in flight can then overwrite (see the expert section). Use `predict()` only when the TB knows the exact new value, and make the field volatile in any case, so that a `mirror(UVM_CHECK)` between the hardware change and your prediction does not fail.

### Debugging a stale mirror

Start from the symptom. The messages are uvm-core 2020.3.1 formats; `...` stands for the file, line, time and reporter that your simulator prints.

| Symptom | Likely cause | Fix |
| --- | --- | --- |
| The DUT changes, the mirror never does, and the log is silent | Predictor not connected (`mon.ap` has no subscriber), or not built while auto-predict is off | Add `agent.mon.ap.connect(predictor.bus_in)`; check that the predictor was created |
| `UVM_FATAL ... [REG/WRITE/NULL] write: adapter handle is null` at the first transfer | `predictor.adapter` never set | Set it in `connect_phase` |
| Silent, but with `+UVM_VERBOSITY=UVM_FULL` every transfer logs `[REG_PREDICT_NOT_FOR_ME] Observed transaction does not target a register` | `predictor.map` is a sub-map, or `bus2reg()` returns the wrong address (for example a word address where the map uses byte addresses) | Bind the predictor to the root map; fix `rw.addr` in `bus2reg()` |
| `UVM_ERROR ... [RegModel] Cannot get register by offset: Block ral is not locked.` | `lock_model()` was not called after the model was built | End the block's `build()` with `lock_model()` |
| A W1T field flips back in the mirror; RW and W1C fields look fine | Double prediction: auto-predict on with a connected predictor | `set_auto_predict(0)` on the root map |
| `UVM_WARNING ... [PREDICT_NOK] status UVM_NOT_OK; skip prediction.` | The access ended `UVM_NOT_OK`, from the bus or from a wrong status mapping in `bus2reg()` | Intended for real errors; otherwise fix the status mapping |
| `read()` returns 0 or old data; mismatches appear only on reads | `provides_responses` does not match the driver: the driver returns read data only in a separate response, but the adapter says 0, so the map reads the request item (§19.2.1.2.3) | Set `provides_responses = 1`, or copy the data into the request item. With implicit prediction the mirror is wrong too; with explicit prediction only the returned value is |
| A `RegModel` mismatch right after a write, which passes when you check again later | The monitor publishes after `write()` returns, so the check compared with the old mirror | Make the driver finish after the monitor publishes, or wait for the prediction (see the expert section on timing) |
| `UVM_WARNING ... [RegModel] Trying to predict value of register 'ral.int_status' while it is being accessed` (or, field-level, `Trying to predict value of field 'err' while register 'ral.int_status' is being accessed`) | `predict()` called during an access to the same register | Wait until `is_busy()` is 0, call `predict()` and check its return value |
| False mismatches on status bits, counters or interrupt flags | Hardware-driven fields configured `volatile = 0` | Configure them `volatile = 1`; check them against your own expectation |

A mismatch itself always looks like this (uvm-core `uvm_reg.svh`), followed by one `UVM_INFO` line per mismatching field:

```text
UVM_ERROR ... [RegModel] Register "ral.ctrl" value read from DUT (0x0000000000000009) does not match mirrored value (0x0000000000000005) (valid bit mask = 0x00000000ffffffff)
UVM_INFO ... [RegModel] Field mode (ral.ctrl[3:2]) mismatch read=2'h2 mirrored=2'h1
```

The "valid bit mask" leaves out the fields that are not compared: fields whose compare policy is `UVM_NO_CHECK` (volatile fields get it from `configure()`, others from `set_compare(UVM_NO_CHECK)`, §18.5.5.15) and write-only fields.

## Make It Work

### One bench, four prediction set-ups

The example below is a complete UVM bench on a minimal register bus (not a standard protocol: one access per cycle, read data driven while `sel` is high). The DUT has three registers:

- **CTRL** at `'h00`: EN[0], IE[1] and MODE[3:2] are RW; bits [31:4] are RO and read 0.
- **INT_STATUS** at `'h08`: ERR[0] is W1C and is set by the **hardware** when CTRL.MODE is written with 3, an illegal mode.
- **GPIO** at `'h0C`: LED[3:0] is W1T.

The plusarg `+PRED=` selects the prediction set-up (it belongs to this example; it is not a UVM plusarg). The test makes four kinds of change and checks the mirror after each with `mirror(UVM_CHECK)`, which reads the DUT and reports a `RegModel` error if the mirror was stale:

1. a register-model write;
2. a raw bus write that bypasses the register model, standing in for firmware or a DMA;
3. a write to the W1T field;
4. a change made by the hardware itself, which no prediction mode can see.

// compile
// pred_demo.sv: run with +PRED=NONE, AUTO, EXPLICIT (the default) or BOTH.
`timescale 1ns/1ps
`include "uvm_macros.svh"

// A minimal register bus: one access per cycle, combinational read data.
interface rbus_if (input logic clk);
  logic        rst_n;
  logic        sel;
  logic        write;
  logic [7:0]  addr;
  logic [31:0] wdata;
  logic [31:0] rdata;

  // Inputs are sampled just before the edge; outputs change 1 ns after it.
  clocking drv_cb @(posedge clk);
    default input #1step output #1;
    output sel, write, addr, wdata;
    input  rdata;
  endclocking

  clocking mon_cb @(posedge clk);
    default input #1step;
    input sel, write, addr, wdata, rdata;
  endclocking
endinterface

// CTRL 'h00: EN[0] IE[1] MODE[3:2] RW, [31:4] read 0.
// INT_STATUS 'h08: ERR[0] W1C, set by hardware. GPIO 'h0C: LED[3:0] W1T.
module rdut (
  input  logic        clk,
  input  logic        rst_n,
  input  logic        sel,
  input  logic        write,
  input  logic [7:0]  addr,
  input  logic [31:0] wdata,
  output logic [31:0] rdata
);
  logic [3:0] ctrl_q;
  logic       err_q;
  logic [3:0] led_q;

  always_ff @(posedge clk or negedge rst_n) begin
    if (!rst_n) begin
      ctrl_q <= '0;
      err_q  <= 1'b0;
      led_q  <= '0;
    end else if (sel && write) begin
      case (addr)
        8'h00: begin
          ctrl_q <= wdata[3:0];
          if (wdata[3:2] == 2'b11) err_q <= 1'b1;  // illegal MODE: hardware flags it
        end
        8'h08:   if (wdata[0]) err_q <= 1'b0;       // W1C
        8'h0C:   led_q <= led_q ^ wdata[3:0];       // W1T
        default: ;
      endcase
    end
  end

  always_comb begin
    rdata = '0;
    if (sel && !write) begin
      case (addr)
        8'h00:   rdata = {28'h0, ctrl_q};
        8'h08:   rdata = {31'h0, err_q};
        8'h0C:   rdata = {28'h0, led_q};
        default: ;
      endcase
    end
  end
endmodule

    `uvm_object_utils(rbus_item)
    bit        write;
    bit [7:0]  addr;
    bit [31:0] data;  // write data, or the read data the driver captured

    function new(string name = "rbus_item");
      super.new(name);
    endfunction

    virtual function string convert2string();

  class rbus_driver extends uvm_driver #(rbus_item);
    `uvm_component_utils(rbus_driver)
    virtual rbus_if vif;

    endfunction

    task run_phase(uvm_phase phase);
      vif.drv_cb.sel <= 1'b0;
      wait (vif.rst_n === 1'b1);
      forever begin
        seq_item_port.get_next_item(req);
        @(vif.drv_cb);

        // predictor has updated the mirror) before write() or read() returns.
        @(vif.drv_cb);

      end
    endtask

### How to set up prediction in a new environment

1. **List the initiators on every bus** that reaches the register block: the register model, firmware, DMA engines, other agents.
2. **Pick a set-up per bus** with the four rules in [Double prediction, and how to choose](#double-prediction-and-how-to-choose).
3. **Build** the register model, call `lock_model()` at the end of its `build()`, and call `reset()`. Create one adapter and, for explicit or passive prediction, one `uvm_reg_predictor #(your_item)` per bus in `build_phase`.
4. **Wire** in `connect_phase`: `set_sequencer()` on the root map (active buses only), `predictor.map` = the root map, `predictor.adapter`, and `mon.ap.connect(predictor.bus_in)`. Leave auto-predict at 0.
5. **Check the monitor**: it publishes a new object for every transfer, reads included, with the read data filled in, and it publishes no later than the driver's `item_done()`.
6. **Mark hardware-driven fields volatile**, and add `predict()` calls only where the TB knows the exact new value.
7. **Prove it** with a firmware-style raw write followed by `mirror(UVM_CHECK)`, as in step 2 above, and a W1T write if the block has one.

**Checklist before moving on:**

- [ ] Every bus that can change a register has a connected predictor bound to the root map, or auto-predict is on and the register model is the only initiator on that bus.
- [ ] Auto-predict and a connected predictor are never active on the same map.
- [ ] The monitor publishes reads with their data, and publishes before the driver's `item_done()`.
- [ ] Hardware-driven fields are volatile; `predict()` calls wait for `is_busy()` to clear and check their return value.
- [ ] You can name, for each `+PRED` column above, which step fails and why.

## Push Further

### Expert: Where IEEE 1800.2-2020 and uvm-core 2020.3.1 disagree about prediction

The standard's text and the reference implementation differ in four places that touch this page. Teach and debug with the implementation, but write portable code that does not depend on either: when in doubt, read `get_mirrored_value()` after the call.

| Operation | IEEE 1800.2-2020 text | uvm-core 2020.3.1 (`uvm_reg.svh`, `uvm_reg_field.svh`) |
| --- | --- | --- |
| `poke()`, `peek()` | "This method is affected by the auto-prediction configuration value" (§18.4.4.11, §18.4.4.12) | always calls `do_predict()` after a successful backdoor access |
| `write()`, `read()` with `UVM_BACKDOOR` | "Auto-prediction ... shall determine how the mirror value is updated" (§18.4.4.9); read "is affected by the auto-prediction configuration value" (§18.4.4.10) | always predicts after a successful backdoor access |
| frontdoor `mirror()` | "The mirrored value is then updated using the uvm_reg::predict method" (§18.4.4.14), with no condition; yet §18.2.5.2 says reads do not update the mirror while auto-predict is off | predicts only through auto-predict or a predictor |
| field `predict()` while the register is busy | the method "does not allow an update of the mirror (or desired) values when the register containing this field is busy" (§18.5.5.17) | `uvm_reg_field::predict` warns, returns 0 and still writes the mirror and desired value; `uvm_reg::predict` refuses and returns 0 |

The last row is why the `predict()` snippet above waits for `is_busy()` to clear and uses the register-level call. With the field-level call, a refused prediction still lands, and the access in flight then overwrites it with its own prediction, so the mirror can end at either value. The backdoor rows are the subject of [Frontdoor vs. Backdoor Access](/curriculum/T3_Advanced/A-UVM-4B_Advanced_RAL_Techniques/frontdoor-vs-backdoor).

### Expert: Explicit prediction runs on the monitor's timing, not the RAL call's

A register-model `write()` returns when its bus item ends, which in uvm-core is the sequencer's `end_tr()` after the driver's `item_done()` (`uvm_reg_map.svh` waits on the item's `end` event). The predictor updates the mirror when the monitor publishes. Nothing ties the two together:

- If the driver calls `item_done()` **before** the monitor publishes (a pipelined bus where the driver finishes at the address phase, or a monitor that publishes at the end of a response phase), `write()` returns with the old mirror. A `mirror(UVM_CHECK)` or `update()` issued at once then works from the old value: a false mismatch, or an extra write.
- If both happen at the same clock edge, they run in the same **time slot** (one simulation time) in an order the scheduler chooses ([F3C: Delta Cycles and Race Conditions](/curriculum/T1_Foundational/F3C_Delta_Cycles_and_Race_Conditions/index)), so the result can change between simulators.

Remedies: let the driver finish after the monitor publishes, as the Make It Work driver does with its idle cycle; or have the test wait for the prediction, for example on an analysis FIFO connected to `predictor.reg_ap`. Auto-predict has no such gap, because it predicts inside `write()`. uvm-core's own `uvm_reg_single_access_seq` waits `#1` between its frontdoor write and the backdoor `mirror(UVM_CHECK)` that checks it (`sequences/uvm_reg_access_seq.svh`); the source does not say why, and letting a monitor-fed predictor catch up is the likely reason.

### Expert: Inside uvm_reg_predictor::write()

Details of uvm-core 2020.3.1 `uvm_reg_predictor.svh` that matter at scale:

- **Byte enables.** `rw.byte_en` is set to all ones before `bus2reg()` ("In case they forget to set byte_en"). If your adapter fills it, a field is predicted only when the byte holding its lowest bit is enabled (`uvm_reg_field::do_predict` returns early otherwise).
- **Wide registers.** A register wider than the bus is collected across beats, keyed by register. A beat to an address already collected raises `REG_PREDICT_COLLISION` and drops the partial item. An item still incomplete at the end of the test is reported by `check_phase` as `PENDING REG ITEMS` (§19.3.3.3).
- **`pre_predict()`** (§19.3.3.2) runs before the prediction; the standard says you may "change the value or redirect the target register". By source inspection, uvm-core 2020.3.1 applies a changed value but always predicts the register it looked up, so changing the item's target does not redirect the prediction.
- **Order of work for a complete item:** check-on-read (reads only, skipped for `UVM_NOT_OK`), `pre_predict()`, coverage sampling, `do_predict()` with the door `UVM_PREDICT`, the `REG_PREDICT` message at `UVM_HIGH`, then `reg_ap.write()`.
- **Indirect registers.** For a `uvm_reg_indirect_data` register, the `REG_PREDICT` message and check-on-read use `get_indirect_reg()`, the register selected by the index register, and the data register's `do_predict()` forwards the prediction to the selected register.
- **`flush()`** clears pending items, for example after a mid-test reset. It is marked `@uvm-contrib`: a uvm-core addition, not part of IEEE 1800.2-2020.

`reg_ap` makes the predictor a clean source for a **register scoreboard**: every observed access arrives as a `uvm_reg_item` already decoded to a register, with its kind and value. That is usually better than scattering `mirror(UVM_CHECK)` calls through tests ([A-UVM-6: Scoreboards and Reference Models](/curriculum/T3_Advanced/A-UVM-6_Scoreboards_and_Reference_Models/index)).

### Expert: The root map owns prediction

In uvm-core 2020.3.1 every prediction decision is taken at the root map, whichever map the access names:

- **Auto-predict** is read from the root map (`system_map.get_auto_predict()` in `uvm_reg::do_write` and `do_read`). `set_auto_predict()` on a sub-map is stored and ignored; unlike `set_check_on_read()`, which "specifies the check-on-read mode for this map and all of its submaps" (§18.2.5.3), it does not propagate.
- **The address table** that `get_reg_by_offset()` searches is built only in the root map when the model is locked, so `predictor.map` must be a root map.
- **One predictor per root map.** A register reachable from two buses has two root maps (one per bus interface, each created with `create_map()` in the top block), and each bus needs its own monitor, adapter and predictor. The module index covers multiple maps.

So the rule for hierarchical models is: `set_sequencer()`, `set_auto_predict()` and `predictor.map` all go on the root map.

### Expert: Reset and the mirror

A DUT reset in the middle of a test changes every register, and no access reports it. Call `ral.reset()` when the reset is applied: it "sets the mirror value of all registers in the block and sub-blocks to the reset value" without touching the DUT (§18.1.5.3). Also call `predictor.flush()` (uvm-core only, see above) so that a half-collected wide-register item does not survive the reset. Forgetting either gives false mismatches on the first check after reset. [A-UVM-9: Reset Handling and Error Injection](/curriculum/T3_Advanced/A-UVM-9_Reset_and_Error_Injection/index) owns this topic.
