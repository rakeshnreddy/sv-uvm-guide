## Quick Take

- **What it is:** the techniques that keep a register model's **mirror** (its copy of what each DUT register holds) equal to the real hardware while firmware, DMA (direct memory access) engines, hardware events and your own tests all touch the registers. When the copy and the hardware disagree, they also tell you why.
- **Why it matters:** a stale mirror produces false failures, and a wrongly updated mirror hides real bugs. Out of the box, `uvm_reg_map` updates the mirror after **no** bus access at all, so every environment has to choose how the mirror learns, and a wrong choice fails silently.
- **The Analogy:** the mirror is your chequebook ledger and the DUT is the bank account. Implicit (auto) prediction writes down only the cheques *you* write. Explicit prediction reconciles every line of the bank statement, including direct debits by others (firmware, a DMA engine). *Where it breaks:* the bank also changes balances by itself, as hardware-set status bits do, with no statement line. You only learn about those changes when you read the balance, or you agree in advance not to check that line (a volatile field). And no ledger keeps a copy of a whole memory: the register model does not mirror memories at all.

**You will be able to:**
1. Choose implicit (auto), explicit or passive prediction for an environment, and explain which accesses each one can see.
2. Predict the mirrored value after hardware-set bits, side-effect policies (W1C, W1T, RC), volatile fields and a double prediction.
3. Debug a mirror mismatch from its log with a fixed checklist: connection, monitor data, `bus2reg()`, map, adapter flags, field policy and double prediction.
4. Model a memory (`uvm_mem` and its allocation manager) and a register shared by several address maps, and state what the model tracks for each.
5. Extend the register layer with a user frontdoor (`uvm_reg_frontdoor`) or a register callback (`uvm_reg_cbs`), and turn on register coverage.

## Build Your Mental Model

### Words this page uses

[A-UVM-4A: RAL Fundamentals](/curriculum/T3_Advanced/A-UVM-4A_RAL_Fundamentals/index) teaches these terms in depth. Here is the one-line version of each.

| Term | Meaning on this page |
| --- | --- |
| **DUT** | The design under test: the hardware whose registers the model describes. |
| **Register model (RAL)** | The register abstraction layer: a tree of SystemVerilog objects, one per register block, register and field, that knows each register's address, fields, access policy and reset value (IEEE 1800.2-2020 Clause 18). |
| **Desired value** | What the test *wants* the register to hold. `set()` changes it; `update()` writes it to the DUT. |
| **Mirrored value (the mirror)** | What the model *believes* the DUT holds right now. `get_mirrored_value()` returns it. |
| **Access policy** | How a field reacts to reads and writes: RW (read-write), RO (read-only), W1C (write 1 to clear), W1T (write 1 to toggle), RC (cleared by a read), and so on. |
| **Volatile field** | A field the hardware may change without any access, such as a status bit or a counter. Marking it volatile tells `mirror(UVM_CHECK)` not to compare it. |
| **Address map (`uvm_reg_map`)** | The table that places registers at addresses on one bus, and knows which sequencer and adapter reach that bus. |
| **Adapter (`uvm_reg_adapter`)** | Converts a generic register operation into your bus's sequence item (`reg2bus()`) and back (`bus2reg()`). |
| **Frontdoor / backdoor** | A frontdoor access goes over the bus as a real transfer. A backdoor access reads or deposits the RTL signal directly through its HDL path (the signal's hierarchical name in the design), with no bus transfer. |
| **Monitor and analysis port** | The monitor watches the bus pins and publishes every transfer it sees through an analysis port (a broadcast output; see [I-UVM-2B: TLM Connections](/curriculum/T2_Intermediate/I-UVM-2B_TLM_Connections/index)). |
| **Sequencer, driver, sequence item** | The UVM stimulus path: a sequence hands sequence items to the sequencer, and the driver turns each item into pin activity (see [I-UVM-3A: Basic UVM Sequences and Items](/curriculum/T2_Intermediate/I-UVM-3A_Fundamentals/index)). |
| **`build_phase`, `connect_phase`** | The UVM phases in which components are created and then wired together (see [I-UVM-1C: UVM Phasing](/curriculum/T2_Intermediate/I-UVM-1C_UVM_Phasing/index)). |
| **Prediction** | Updating the mirror from an access, by applying each field's access policy to the old mirror and the data. |
| **Predictor (`uvm_reg_predictor`)** | The **register** predictor: a component that receives monitored transfers and predicts the mirror from them. It is not a scoreboard's reference model. |

### The mirror-correctness problem in one picture

The mirror is just a variable inside each field object. It changes only when something writes it:
- a **prediction** after a bus access;
- an explicit `predict()` call by your code;
- `reset()` on the model, which loads the reset values;
- a backdoor access: in uvm-core 2020.3.1, `peek()`, `poke()` and the backdoor forms of `read()` and `write()` all predict their own access (the [Frontdoor vs. Backdoor](/curriculum/T3_Advanced/A-UVM-4B_Advanced_RAL_Techniques/frontdoor-vs-backdoor) page covers what each one does and how the IEEE text words it).

For frontdoor traffic, the environment chooses one of three set-ups (IEEE 1800.2-2020 §18.2.5.2 and §19.3):

| Set-up | How you turn it on | What it sees |
| --- | --- | --- |
| **Implicit (auto) prediction** | `map.set_auto_predict(1)` | Only the accesses the register model itself starts (`read()`, `write()`, `mirror()`, `update()` through that map). The map predicts each one when it completes. |
| **Explicit prediction** | A `uvm_reg_predictor` whose `bus_in` is connected to the bus monitor's analysis port, with `predictor.map` and `predictor.adapter` set | Every transfer on the bus: register-model accesses, firmware, DMA, other agents. |
| **Passive prediction** | A predictor on a bus that the register model never drives | Everything that bus carries; the model only watches. |

A new `uvm_reg_map` starts with auto-predict **off** and no predictor exists, so nothing predicts frontdoor accesses until you choose (uvm-core 2020.3.1 `uvm_reg_map::new`; §18.2.5.2 also says "False (the default)"). Two mistakes cause most mirror bugs:
1. **Calling the wrong thing "explicit".** Explicit prediction is the predictor component fed by a monitor. Calling `predict()` by hand after each write is neither set-up; it is a manual patch.
2. **Turning on both.** Auto-predict does not switch a connected predictor off. With both, every access the model starts is predicted twice, which corrupts toggle (W1T) fields.

[Explicit vs. Implicit Prediction](/curriculum/T3_Advanced/A-UVM-4B_Advanced_RAL_Techniques/explicit-vs-implicit) wires each set-up step by step. Keep this picture in mind for the rest of the page:

### Fields the hardware changes: W1C, W1T, RC and volatile

Prediction applies each field's access policy to the old mirror and the access data. For most policies that gives the right answer. Some fields, though, change without any access, or change in ways a plain "store the data" rule would get wrong:

| Policy | What the DUT does | What the prediction does (uvm-core 2020.3.1 `uvm_reg_field::XpredictX` and `do_predict`) |
| --- | --- | --- |
| **W1C** (write 1 to clear) | A 1 in the write data clears the bit; a 0 leaves it | Write: mirror AND NOT data. When the *hardware* sets the bit, nothing is predicted until something reads it |
| **W1S** (write 1 to set) | A 1 sets the bit | Write: mirror OR data |
| **W1T** (write 1 to toggle) | A 1 flips the bit | Write: mirror XOR data, so predicting one write twice cancels it out |
| **RC** (clear on read) | A read returns the value, then clears it | A predicted frontdoor read sets the mirror to 0 |
| **Volatile** (any policy) | The hardware may change the value at any time | `configure(…, volatile = 1, …)` sets the field's compare mode to `UVM_NO_CHECK`. Prediction still runs; `mirror(UVM_CHECK)` simply skips the field |

**A traced example: a bit the hardware sets.** INT_STATUS.ERR is W1C, configured with `volatile = 0`, and an explicit predictor watches the bus. Read the table row by row and predict the mirror column before you look at it.

| Step | DUT ERR | Mirror ERR | What happened |
| --- | --- | --- | --- |
| Reset | 0 | 0 | `reset()` loaded the reset value |
| A bus write hits an unmapped address, and the DUT sets ERR | 1 | 0 | No register access, so nothing predicted ERR: the mirror is stale |
| `mirror(status, UVM_CHECK)` *now* | 1 | 1 | `mirror()` compares the old mirror (0) with the read value (1) and reports a `RegModel` error, a false failure. The predictor then learns 1 from the read |
| Instead: `read(status, v)` first | 1 | 1 | The predictor sees the read data and sets the mirror to 1 |
| `write(status, 1)` | 0 | 0 | W1C: 1 AND NOT 1 = 0 in both |
| `mirror(status, UVM_CHECK)` | 0 | 0 | Passes |

**What this means in a real testbench.**
- A field that hardware changes at times you **cannot** predict (an interrupt that can fire any cycle, a free-running counter) should be volatile. Check its value with a read and an expectation from your scoreboard, not with `mirror(UVM_CHECK)`.
- A field that hardware changes only on an event your test causes can stay checked (`volatile = 0`), as long as the test reads it before it checks it. The example in Make It Work does exactly this.
- To check a volatile field during a quiet window, call `set_compare(UVM_CHECK)` on it, run `mirror(UVM_CHECK)`, and restore `UVM_NO_CHECK` afterwards.
- No standard policy fits a bit that reads back 0 after you write 1 to it (a "GO" pulse). A register callback fixes its prediction; see [Extending the register layer](#extending-the-register-layer-user-frontdoors-and-register-callbacks).

### Adapter settings that move the mirror

[A-UVM-4A](/curriculum/T3_Advanced/A-UVM-4A_RAL_Fundamentals/index) builds the adapter. Four of its settings decide what the mirror receives, and each one fails quietly when it is wrong.

- **`provides_responses`** (§19.2.1.2.3) says whether the driver returns read data in a *separate* response item. When it is 1, the map waits for that response with `get_base_response()` and calls `bus2reg()` on it. When it is 0, the map calls `bus2reg()` on the request item, so the driver must write the read data into the request. A mismatch fails in one of two ways:
  - `provides_responses = 1` but the driver never sends a response: every `read()` and `write()` hangs.
  - `provides_responses = 0` but the driver returns data only through `put_response()`: `read()` returns whatever the request held (usually 0). An explicit predictor still learns the true value from the monitor, so a later `mirror(UVM_CHECK)` reports a mismatch that points at the adapter, not at the DUT.
- **`status` in `bus2reg()`.** Map your bus's error response to `UVM_NOT_OK`. A `UVM_NOT_OK` access is not predicted: uvm-core warns `PREDICT_NOK` "status UVM_NOT_OK; skip prediction." and the mirror keeps its old value. If `bus2reg()` always returns `UVM_IS_OK`, an access the DUT rejected moves the mirror anyway.
- **`supports_byte_enable`** (§19.2.1.2.2) says the bus can write single bytes. It matters when you write one field: `ral.ctrl.en.write(st, 1)`. The diagram below shows what uvm-core 2020.3.1 does.
- **`get_item()`** (§19.2.1.2.7) returns the `uvm_reg_item` being converted, so `reg2bus()` can read extra information that a test attached to the access (its `extension` argument).

Here "W1x" means the write-1 policies (W1C, W1S, W1T and their variants), and "W0x" the write-0 ones (W0C, W0S, W0T and their variants): uvm-core picks a neighbour value that leaves them unchanged.

### Memories: `uvm_mem` and the allocation manager

RAL models addressable memories with `uvm_mem` (§18.6). A memory has a size in locations, a width in bits and an access policy, but **no mirror**: the standard leaves it out "because of the potentially large data space", and `uvm_reg_predictor` never predicts a memory access. To check memory contents, read them back and compare, or let a scoreboard track what was written. Size, width and access are constructor arguments, so a memory is a small subclass:

```systemverilog
// snippet: a 1K x 32 memory in a block that has only a memory map
class sram_mem extends uvm_mem;
  `uvm_object_utils(sram_mem)
  function new(string name = "sram_mem");
    super.new(name, 1024, 32, "RW", UVM_NO_COVERAGE);   // 1K words x 32 bits
  endfunction
endclass

class sram_block extends uvm_reg_block;
  `uvm_object_utils(sram_block)
  sram_mem      sram;
  uvm_reg_map   mem_map;

  function new(string name = "sram_block");
    super.new(name, UVM_NO_COVERAGE);
  endfunction

  virtual function void build();
    sram = sram_mem::type_id::create("sram");
    sram.configure(this, "sram_q");   // parent block, optional HDL path
    mem_map = create_map("mem_map", 'h0, 4, UVM_LITTLE_ENDIAN);
    mem_map.add_mem(sram, 'h0000, "RW");
    lock_model();
  endfunction
endclass
```

Every access names an **offset**, which counts memory locations (words), not bytes (§18.6.5):

```systemverilog
// snippet: inside a sequence or test task
uvm_status_e   st;
uvm_reg_data_t rd;
uvm_reg_data_t burst[] = '{'h1, 'h2, 'h3, 'h4};
ral.sram.write(st, 'h10, 'hAB);          // location 16
ral.sram.read (st, 'h10, rd);            // compare rd yourself: there is no mirror
ral.sram.burst_write(st, 'h20, burst);   // locations 32 to 35
ral.sram.peek(st, 'h10, rd);             // backdoor, through the HDL path
```

The **memory allocation manager** (`uvm_mem_mam`, §18.12) hands out non-overlapping regions, like `malloc` and `free`, so that DMA tests can claim buffer space without collisions. Every `uvm_mem` builds one in `configure()`, available as its `mam` member. A region is accessed like a small memory of its own, with offsets relative to its start:

```systemverilog
// snippet: claim a DMA buffer, use it, give it back
uvm_mem_region r = ral.sram.mam.request_region(256);   // 256 bytes = 64 words
if (r == null) `uvm_fatal("MAM", "no free region of 64 words")
r.write(st, 0, 'h1234_5678);       // location r.get_start_offset() + 0
// ... program the DMA with the region's address ...
r.release_region();
```

### One register, several buses: multiple maps

A register is often reachable from two buses, for example a CPU configuration bus and a debug port. The model then has **one** register object with **one** mirror, and two address maps that both point at it. Each map places the register at its own address, with its own access **rights**:

```systemverilog
// snippet: soc_block::build(); one register, two maps
cfg_map = create_map("cfg_map", 'h0000, 4, UVM_LITTLE_ENDIAN);  // CPU bus
dbg_map = create_map("dbg_map", 'h1000, 4, UVM_LITTLE_ENDIAN);  // debug port
cfg_map.add_reg(ctrl, 'h00, "RW");
dbg_map.add_reg(ctrl, 'h00, "RO");   // the debug port may only read CTRL
lock_model();
```

Each bus with traffic needs its own sequencer, adapter and predictor, and each predictor is bound to its own map:

```systemverilog
// snippet: soc_env::connect_phase()
ral.cfg_map.set_sequencer(cpu_agent.sqr, cpu_adapter);
ral.dbg_map.set_sequencer(dbg_agent.sqr, dbg_adapter);
cpu_pred.map = ral.cfg_map;
cpu_pred.adapter = cpu_adapter;
dbg_pred.map = ral.dbg_map;
dbg_pred.adapter = dbg_adapter;
cpu_agent.mon.ap.connect(cpu_pred.bus_in);
dbg_agent.mon.ap.connect(dbg_pred.bus_in);
```

**Rules that keep a shared register right:**
- **Name the map on every frontdoor access**: `ral.ctrl.write(st, 'h1, UVM_FRONTDOOR, ral.cfg_map)`. IEEE 1800.2-2020 §18.4.4.9 says that for a frontdoor access to a register in more than one map, "an address map shall be specified". uvm-core 2020.3.1 does not stop you: with `map = null` it silently uses the block's default map, which is the first map created unless you call `set_default_map()`.
- **Rights change the policy seen through that map.** Through `dbg_map`, every writable field of CTRL behaves as RO, so a write through the debug port is predicted as "no change" (uvm-core `uvm_reg_field::get_access(map)`).
- **One mirror means one truth.** A write through `cfg_map`, predicted by `cpu_pred`, updates the same mirror that a later read through `dbg_map` compares against. A bus without a predictor is invisible to the model.
- **The root map owns the bus.** A map created with `create_map()` in the top block is a **root** map. A sub-block's map that you add to a parent map with `add_submap()` (§18.2.3.5) is not. In uvm-core 2020.3.1, accesses use the root map's sequencer and adapter, auto-predict is read from the root map (`set_auto_predict()` does not propagate to sub-maps), and a predictor needs the root map's address table. So call `set_sequencer()`, `set_auto_predict()` and set `predictor.map` on root maps only. A predictor bound to a sub-map finds no register at any address and stays silent (see the debugging table below).
- The built-in `uvm_reg_shared_access_seq` (Annex E.4) checks that a shared register reads the same through every map; see [Built-in RAL Sequences](/curriculum/T3_Advanced/A-UVM-4B_Advanced_RAL_Techniques/built-in-ral-sequences).

### Extending the register layer: user frontdoors and register callbacks

Sometimes the standard path is not enough: a register has no address of its own, or a field behaves in a way no access policy describes. UVM gives you two extension points, and neither needs a change to the library.

**A user frontdoor** (`uvm_reg_frontdoor`, §19.4.2) replaces the built-in "one bus transfer at this address" for one register in one map. It is a sequence: the register calls its `body()` with `rw_info`, a `uvm_reg_item` that holds the access kind, value and map, and `body()` performs the access however the hardware requires. The classic case is a table of registers reached through an INDEX register and a DATA register:

```systemverilog
// snippet: TBL[i] is reached by writing i to INDEX, then accessing DATA
class idx_data_fd extends uvm_reg_frontdoor;
  `uvm_object_utils(idx_data_fd)
  uvm_reg      idx, data;   // the two registers the bus really has
  int unsigned entry;       // which table entry this frontdoor reaches

  function new(string name = "idx_data_fd");
    super.new(name);
  endfunction

  virtual task body();
    uvm_status_e   st;
    uvm_reg_data_t v;
    idx.write(st, entry, UVM_FRONTDOOR, rw_info.get_map(), this);
    if (st == UVM_IS_OK) begin
      if (rw_info.get_kind() == UVM_WRITE)
        data.write(st, rw_info.get_value(0), UVM_FRONTDOOR, rw_info.get_map(), this);
      else begin
        data.read(st, v, UVM_FRONTDOOR, rw_info.get_map(), this);
        rw_info.set_value(v, 0);
      end
    end
    rw_info.set_status(st);
  endtask
endclass
```

```systemverilog
// snippet: in the block's build(), after idx, data and tbl[] are built
foreach (tbl[i]) begin
  idx_data_fd fd = idx_data_fd::type_id::create($sformatf("fd%0d", i));
  fd.idx   = idx;
  fd.data  = data;
  fd.entry = i;
  default_map.add_reg(tbl[i], 'h0, "RW", 1);  // unmapped: no address of its own
  tbl[i].set_frontdoor(fd, default_map);       // §18.4.5.2
end
```

What happens to the mirrors is the part that catches people. An explicit predictor sees only the INDEX and DATA transfers, so it predicts **INDEX and DATA**, never `tbl[i]`. The table entry's mirror moves only through auto-predict (uvm-core predicts the target register after the frontdoor's `body()` returns), through your own `predict()`, or by using `uvm_reg_indirect_data` (§18.7). That class packages this exact index/data pattern, and the predictor forwards its predictions to the indexed register. Write your own frontdoor for anything else that is not "one transfer at one address": an unlock key before a protected register, a mailbox, a serial side channel.

**A register callback** (`uvm_reg_cbs`, §18.11) hooks into every access of a field or register: `pre_write`, `post_write`, `pre_read`, `post_read`, and `post_predict` (§18.11.2.6), which runs after each read or write prediction and may change the predicted value through its `inout value` argument. Callback registration and ordering work as in [A-UVM-5: UVM Callbacks](/curriculum/T3_Advanced/A-UVM-5_UVM_Callbacks/index). The common use is a field that reads back differently from what you wrote, such as a GO bit that starts a job and always reads 0:

```systemverilog
// snippet: GO always reads 0, but no standard policy says so
class go_pulse_cb extends uvm_reg_cbs;
  `uvm_object_utils(go_pulse_cb)
  function new(string name = "go_pulse_cb");
    super.new(name);
  endfunction
  virtual function void post_predict(input uvm_reg_field  fld,
                                     input uvm_reg_data_t previous,
                                     inout uvm_reg_data_t value,
                                     input uvm_predict_e  kind,
                                     input uvm_door_e     path,
                                     input uvm_reg_map    map);
    if (kind == UVM_PREDICT_WRITE) value = 0;   // match what a read will return
  endfunction
endclass

// in the env's connect_phase, after the model is built
// (go_cb is a go_pulse_cb handle declared in the env):
go_cb = go_pulse_cb::type_id::create("go_cb");
uvm_reg_field_cb::add(ral.cmd.go, go_cb);   // typedef from Annex D.4.5.7
```

`post_predict` is the right hook because every prediction path (auto-predict, the predictor, a backdoor write) runs it. A `post_write` that calls `predict(0)` is fragile: with explicit prediction the monitor may publish *after* `write()` returns, and the predictor would then set GO back to 1. uvm-core also ships two ready callbacks, `uvm_reg_read_only_cbs::add(rg)` and `uvm_reg_write_only_cbs::add(rg)` (§18.11.4–§18.11.5), which turn a write to a read-only register (or a read of a write-only one) into a `UVM/REG/READONLY` (or `UVM/REG/WRTEONLY`) error with `UVM_NOT_OK`.

### Register coverage (awareness)

The register layer can measure functional coverage of the registers themselves: which bits were written and read, which addresses were accessed, and which field values occurred. The models are named by `uvm_coverage_model_e` (§17.2.2.9):

| Model | Measures |
| --- | --- |
| `UVM_CVR_REG_BITS` | Individual register bits written and read |
| `UVM_CVR_ADDR_MAP` | Individual register and memory addresses accessed |
| `UVM_CVR_FIELD_VALS` | Field values |
| `UVM_CVR_ALL` | All of the above |

Coverage is opt-in at two levels:

```systemverilog
// snippet: in the test's build_phase, BEFORE the env builds the model
uvm_reg::include_coverage("*", UVM_CVR_ALL);   // §18.4.7.1: which models to build

// snippet: in the env, after ral.build()
void'(ral.set_coverage(UVM_CVR_ALL));          // §18.1.4.5: start measuring
```

- `include_coverage()` (§18.4.7.1) only *requests* models. Each register asks for them when it is constructed, through `build_coverage()`, and builds its covergroups only if the request already exists. Called after the model is built, it changes nothing.
- Register generators write the covergroups for you, inside each register class (`has_coverage()`, `sample()`, `sample_values()`). The base classes contain none, so a hand-written model has no register coverage until you add it.
- Measurement is off until you call `set_coverage()`: uvm-core 2020.3.1 starts every register with measurement off. `set_coverage()` turns on only models that were built.
- In uvm-core 2020.3.1, `sample()` runs on each predicted access (from the predictor, or from auto-predict). Field values are sampled only when you call `sample_values()`, for example after a `mirror()` of the block.
- Register coverage tells you the *registers* were exercised. It does not replace functional coverage of what the design *did* with them (see [I-SV-3A: Functional Coverage Fundamentals](/curriculum/T2_Intermediate/I-SV-3A_Functional_Coverage_Fundamentals/index)).

| Symptom in the log | Likely cause | Fix |
| --- | --- | --- |
| The mirror never changes after frontdoor accesses; **no** predictor messages at all, even at `+UVM_VERBOSITY=UVM_HIGH` | Checkpoint 1: `mon.ap` is not connected to `predictor.bus_in`. An analysis port may legally have no subscriber, so UVM says nothing | Connect it in `connect_phase` |
| The mirror follows the test's own accesses but misses firmware or DMA writes | Auto-predict is on and no predictor is connected: implicit prediction sees only model-started accesses | Connect a predictor; set auto-predict back to 0 |
| `UVM_FATAL [REG/WRITE/NULL] write: adapter handle is null` at the first transfer | `predictor.adapter` was never set | Set it to the bus adapter |
| A null-handle crash inside the predictor at the first transfer | `predictor.map` was never set | Set it to the bus's root map |
| `REG_PREDICT` lines show values that differ from what `read()` returned | Checkpoint 2 or 3: the monitor publishes the wrong data (for example `wdata` for reads, or a value sampled after the edge), or `bus2reg()` copies the wrong field | Publish `rdata` for reads, sampled like the driver samples it; fix `bus2reg()` |
| Nothing is predicted; at `+UVM_VERBOSITY=UVM_FULL` every transfer logs `REG_PREDICT_NOT_FOR_ME` "Observed transaction does not target a register" | Checkpoint 4: `predictor.map` is a sub-map, or `bus2reg()` converts the address wrongly (byte vs word), or the map's base address differs from the bus's | Bind the predictor to the root map; compare the logged address with the register's address |
| `UVM_ERROR [RegModel] Cannot get register by offset: Block ral is not locked.` | Checkpoint 4: the model was never locked, so it has no address table | Call `lock_model()` at the end of the top block's `build()` |
| `UVM_WARNING [PREDICT_NOK] status UVM_NOT_OK; skip prediction.` | Checkpoint 5: `bus2reg()` reported an error response, so the access was not predicted | Correct if the DUT really rejected it; otherwise fix the status mapping |
| Only W1T fields (or other non-idempotent ones) mismatch, by exactly one toggle | Checkpoint 6: double prediction, auto-predict on next to a connected predictor | Set auto-predict to 0 |
| A hardware status field mismatches right after a hardware event | Checkpoint 5: a hardware-changed field with `volatile = 0`, checked before anything read it | Read it first, or make it volatile and check it against your scoreboard |
| `read()` returns 0 (or stale data) while the bus showed the right value | `provides_responses` does not match how the driver returns read data | Make the adapter flag and the driver agree |
| `UVM_ERROR [UVM/REG/READONLY] … is read-only. Cannot call write() method.` | A test wrote a register that the map aliases as read-only, or that has `uvm_reg_read_only_cbs` | Write the write-only alias, or do not write it |

### Recap: the mistakes that break mirrors

- Nothing is predicting: no predictor connected and auto-predict off (the default).
- Both are predicting: auto-predict on next to a predictor, so W1T fields toggle back.
- The predictor is fed wrong data: the monitor publishes the wrong value, or `bus2reg()` or `provides_responses` is wrong.
- The predictor looks in the wrong table: a sub-map, an unlocked model, or a wrong address conversion.
- The hardware changed a field that is not volatile, and the test checked it before reading it.
- A test expects a mirror for a memory (there is none), or for a register reached only through a user frontdoor (only auto-predict or `predict()` move it).

interface rb_if (input logic clk, input logic rst_n);
  logic        valid, write;
  logic [7:0]  addr;
  logic [31:0] wdata, rdata;

  // #1step samples the value just before the edge, so driver and monitor agree.
  clocking drv_cb @(posedge clk);
    default input #1step output #0;
    output valid, write, addr, wdata;
    input  rdata, rst_n;
  endclocking

  clocking mon_cb @(posedge clk);
    default input #1step;
    input valid, write, addr, wdata, rdata, rst_n;
  endclocking
endinterface

// ------------------------------------------------------------------------ the DUT
// 'h00 CTRL       EN[0] RW, LED[1] W1T
// 'h04 INT_STATUS ERR[0] W1C; hardware sets it when a write hits no register
// 'h08 CNT        [15:0] RO; counts clocks while EN = 1
module rb_regs (rb_if bus);
  logic        en, led, err;
  logic [15:0] cnt;
  wire         wr     = bus.valid && bus.write;
  wire         mapped = bus.addr inside {8'h00, 8'h04, 8'h08};

  always_ff @(posedge bus.clk or negedge bus.rst_n) begin
    if (!bus.rst_n) begin
      en  <= 1'b0;
      led <= 1'b0;
      err <= 1'b0;
      cnt <= '0;
    end else begin
      if (wr && bus.addr == 8'h00) begin
        en  <= bus.wdata[0];
        led <= led ^ bus.wdata[1];                 // write 1 to toggle
      end
      if (wr && bus.addr == 8'h04 && bus.wdata[0]) err <= 1'b0;  // write 1 to clear
      else if (wr && !mapped)                      err <= 1'b1;  // decode error
      if (en) cnt <= cnt + 16'd1;
    end

  always_comb begin
    case (bus.addr)
      8'h00:   bus.rdata = {30'd0, led, en};
      8'h04:   bus.rdata = {31'd0, err};
      8'h08:   bus.rdata = {16'd0, cnt};
      default: bus.rdata = '0;
    endcase
  end
endmodule

      vif.drv_cb.valid <= 1'b0;

        seq_item_port.get_next_item(req);
        vif.drv_cb.valid <= 1'b1;
        vif.drv_cb.write <= req.write;
        vif.drv_cb.addr  <= req.addr;
        vif.drv_cb.wdata <= req.data;
        @(vif.drv_cb);                         // the transfer happens at this edge
        if (!req.write) req.data = vif.drv_cb.rdata;
        vif.drv_cb.valid <= 1'b0;
        @(vif.drv_cb);                         // the monitor published one edge ago
        seq_item_port.item_done();
      end
    endtask

      env.ral.int_status.write(st, 'h1);
      check_ok(st, "int_status.write");

**Why those lines and times.**
- The clock has a 10 ns period with rising edges at 5, 15, 25 ns and so on. Reset is released at 20 ns, so the driver starts at the 25 ns edge and each access takes two edges: the transfer edge, then one idle edge.

**How to build an environment like this:**
1. Make the monitor publish a **new** item for every completed transfer, reads with their read data, sampled the same way the driver samples them (`#1step` here).
2. Write the adapter so that `reg2bus()` and `bus2reg()` are exact inverses, and set `provides_responses` and `supports_byte_enable` to match the driver and the bus.
3. In the register model, give each field its real policy, and decide per hardware-changed field: volatile (moves at any time) or checked after a read (moves only on events the test causes).
4. In `connect_phase`: `set_sequencer()` on the root map, leave auto-predict at 0, set `predictor.map` (the root map) and `predictor.adapter`, and connect `mon.ap` to `predictor.bus_in`.
5. In the test, read any hardware-changed field before you check it, and check every access's `status`.
6. Finish with `mirror(UVM_CHECK)` on each register (or on the block). The run must end with `UVM_ERROR :    0` and `UVM_FATAL :    0`.
7. Prove the checks can fail: try the three mutants in the kata under Practice & Reinforce.

**Checklist before moving on:**
- [ ] Your monitor publishes reads with their read data, and you can say at which edge it samples.
- [ ] Auto-predict is off wherever a predictor is connected, and every predictor is bound to a root map.
- [ ] Every hardware-changed field is either volatile or read before it is checked.
- [ ] Your adapter's `provides_responses` matches how your driver returns read data.
- [ ] Your test checks `status` after every access and ends with `mirror(UVM_CHECK)`.
- [ ] You can predict which check each kata mutant breaks, and why.

## Push Further

### Expert: inside `uvm_reg_predictor::write()`

The predictor is a short function, and knowing it line by line answers most "why did the mirror not move?" questions (uvm-core 2020.3.1 `src/reg/uvm_reg_predictor.svh`; IEEE 1800.2-2020 §19.3.2–§19.3.3):
1. It fatals with `REG/WRITE/NULL` if `adapter` is null, sets `rw.byte_en` to all ones "in case they forget", and calls `adapter.bus2reg(tr, rw)`.
2. It looks the address up with `map.get_reg_by_offset(rw.addr, rw.kind == UVM_READ)`. The lookup uses the root map's address table and needs a locked model (§18.2.4.17). The read flag matters for an RO and a WO register aliased at one address. Memories are never looked up, so memory traffic is never predicted.
3. If no register matches, it logs `REG_PREDICT_NOT_FOR_ME` at `UVM_FULL` and returns. At normal verbosity, a predictor that never matches is completely silent.
4. A register wider than the bus arrives as several transfers. The predictor collects one per bus word before predicting, raises `REG_PREDICT_COLLISION` if the same word arrives twice, and reports `PENDING REG ITEMS` in `check_phase` if a register is still incomplete at the end of the test (§19.3.3.3).
5. For a read with check-on-read enabled on the map, it compares the read data with the mirror (`do_check`) **before** predicting.
6. It calls `pre_predict(item)` (§19.3.3.2: "change the value or redirect the target register"), samples register coverage, and calls `do_predict(item, UVM_PREDICT_WRITE or UVM_PREDICT_READ)` with door `UVM_PREDICT`.
7. It logs `REG_PREDICT` at `UVM_HIGH` and publishes the item on `reg_ap` (§19.3.2.2), which is the clean place to attach a register scoreboard.

`flush()` clears pending multi-beat items after a reset; it is a uvm-core extension marked `@uvm-contrib`, not part of IEEE 1800.2-2020.

### Expert: passive checking with check-on-read

`map.set_check_on_read(1)` (§18.2.5.3) makes every observed read be compared with the mirror before it is predicted; the clause calls it "useful when the register model is used passively". With an explicit predictor on every bus, the register model becomes a passive register checker for firmware-driven SoC tests: firmware reads registers, and any read that disagrees with what the model predicted from earlier traffic is reported. Unlike `set_auto_predict()`, `set_check_on_read()` propagates to every sub-map.

Two uvm-core 2020.3.1 details that the clause does not state. First, a frontdoor read is checked only by a predictor or inside the auto-predict branch of `uvm_reg::do_read`. With neither, check-on-read checks nothing, and with both (already a wiring error) every mismatch is reported twice. Second, the check uses each field's compare mode, so volatile fields still need correct `volatile` settings, or the passive checker produces false failures on every interrupt.

### Expert: field access, byte enables and the neighbour-fill rule

The single-field diagram above is the core of `uvm_reg_field::is_indv_accessible()` (uvm-core 2020.3.1 `uvm_reg_field.svh`). The precise behaviour:
- A **backdoor** field access is always a whole-register access ("Individual BACKDOOR field access not available").
- The byte-enable check applies only when the root map has an adapter whose `supports_byte_enable` is 0. The "only field in its bus word" check then decides whether the neighbours' bits can be left out.
- When a field write becomes a register write, the other fields are filled from their **mirrored** values (RW-like policies), 0 (RO, RC, RS and the W1x family), or all ones (the W0x family). WC, WS, WCRS, WSRC, WOC and WOS neighbours cause a warning that the write "will cause unintended side effects".
- Compiling with `+define+UVM_REG_NO_INDIVIDUAL_FIELD_ACCESS` forces every field write to be a register write.

The interview angle: "Writing one field turned off an enable in the same register. Why?" The field write became a whole-register write, and the RW enable was filled from a stale mirror. W1C neighbours are written as 0, so they are not cleared by accident; RW neighbours get whatever the mirror says. Field writes are safe only on a correct mirror.

### Expert: aliased, indirect and FIFO registers

- **Aliases.** An RO register and a WO register may share one address. The map accepts that pair, adds `uvm_reg_read_only_cbs` and `uvm_reg_write_only_cbs` to them, and the predictor picks the right one by direction. Any other overlap warns that a register "maps to same address as register" (uvm-core `uvm_reg_map.svh`).
- **Indirect registers.** `uvm_reg_indirect_data` (§18.7) models a register array reached through an index register. It installs its own frontdoors on the array entries, and its `do_predict()` forwards predictions to the entry the index selects, so an explicit predictor *does* update the array.
- **FIFOs.** `uvm_reg_fifo` (§18.8) models a FIFO data register in which writes push and reads pop. Backdoor access is not supported, because no single deposit can set the FIFO's internal state.
- **Your own frontdoors** get none of this: the predictor sees only the transfers they make. Pair a user frontdoor with auto-predict, an explicit `predict()`, or a `pre_predict()` override that redirects the item.

### Expert: reset and the mirror

`reset()` on the block (§18.4.4.5 for a register) loads every field's reset value into the mirror and the desired value. It does not touch the DUT. When the DUT is reset in the middle of a test:
- call `ral.reset()` when the reset asserts, so the mirror matches the reset values;
- call `predictor.flush()` (uvm-core only) so no half-collected multi-beat register survives into the next phase;
- make sure no register access is in flight, or its completion will be predicted onto the reset mirror.

Without these steps, every `mirror(UVM_CHECK)` after the reset reports the pre-reset values as mismatches. Reset handling across the whole testbench is the topic of [A-UVM-9: Reset Handling and Error Injection](/curriculum/T3_Advanced/A-UVM-9_Reset_and_Error_Injection/index).

### Expert: methodology trade-offs at scale

- **Explicit prediction plus check-on-read on every bus** costs a monitor per bus but gives a passive checker for free. Auto-predict is acceptable only on a bus that the register model alone drives, and only before a monitor exists.
- **Backdoor for set-up, frontdoor for checks.** Backdoor accesses save simulation time in long configuration sequences; the frontdoor still has to be proved, by the access sequence or by targeted tests. [Frontdoor vs. Backdoor Access](/curriculum/T3_Advanced/A-UVM-4B_Advanced_RAL_Techniques/frontdoor-vs-backdoor) covers the side effects.
- **Run the built-in tests per IP, not per SoC.** Bit-bash makes several accesses per bit per map; at SoC scale run it on each block in isolation, with unsafe registers fenced off ([Built-in RAL Sequences](/curriculum/T3_Advanced/A-UVM-4B_Advanced_RAL_Techniques/built-in-ral-sequences)).
- **A register scoreboard on `reg_ap`** sees every predicted register access in one place. That is easier to maintain than `mirror(UVM_CHECK)` calls scattered through sequences, and it can apply design knowledge that no access policy captures.
- **The mirror is not a reference model.** It records what the bus did to the registers. Whether the design then *behaved* correctly belongs in your scoreboards ([A-UVM-6: Scoreboards and Reference Models](/curriculum/T3_Advanced/A-UVM-6_Scoreboards_and_Reference_Models/index)).

### Debug challenge: match the log to the cause

Each excerpt below comes from a different broken environment (illustrative, built from the uvm-core 2020.3.1 message formats). Name the cause before you open the answers.

1. `UVM_FATAL … [REG/WRITE/NULL] write: adapter handle is null`
2. With `+UVM_VERBOSITY=UVM_FULL`: `UVM_INFO … [REG_PREDICT_NOT_FOR_ME] Observed transaction does not target a register: …` on every transfer, including those to known register addresses.
3. `UVM_ERROR … [RegModel] Cannot get register by offset: Block ral is not locked.`
4. `UVM_WARNING … [PREDICT_NOK] status UVM_NOT_OK; skip prediction.` on every write to one register, while the DUT accepts the writes.
5. `UVM_ERROR … [RegModel] Register "ral.ctrl" value read from DUT (0x…03) does not match mirrored value (0x…01)` followed by `Field led … read=1'h1 mirrored=1'h0`, and no other field ever mismatches.

<details>
<summary>Answers</summary>

1. `predictor.adapter` was never set.
2. The predictor is bound to a sub-map, or `bus2reg()` converts the address wrongly (for example a byte address divided by 4). Compare the logged address with the register's offset.
3. The top block's `build()` never called `lock_model()`.
4. The adapter's `bus2reg()` maps that register's response (or every response) to `UVM_NOT_OK`. Check its status mapping against the bus specification.
5. Double prediction: auto-predict is on next to a connected predictor, and LED is the only W1T field.
</details>
