## Quick Take
- **What it is:** Techniques for bridging RAL into bus agents, keeping the mirror synchronized, and debugging mismatches.
- **Why it matters:** A register model is only as good as its mirror. The mirror changes only when something *predicts* an access, and UVM gives you two ways to do that. Pick the wrong one, or wire it wrong, and the mirror drifts silently.
- **The terms:** *Implicit* (auto) prediction is `map.set_auto_predict(1)`. *Explicit* prediction is a `uvm_reg_predictor` fed by a bus monitor. By default neither is active.
- **The Standard:** IEEE 1800.2-2020 Clause 18 (register model: `uvm_reg_map` 18.2, `uvm_reg` 18.4, `uvm_mem` 18.6, memory allocation manager 18.12) and Clause 19 (`uvm_reg_adapter` 19.2, `uvm_reg_predictor` 19.3, `uvm_reg_sequence` 19.4).

## Build Your Mental Model

### The Adapter Bridge
`uvm_reg_adapter` is the translator between generic `uvm_reg_bus_op` requests and your bus transaction item (e.g., `axi_item`). The map calls `reg2bus()` to build the item, and `bus2reg()` on the finished item (or on the response, when `provides_responses = 1`) to get the read data and status. A predictor calls the same `bus2reg()` on every item the monitor publishes.

### Predictors and the Mirror
Prediction keeps the RAL mirror aligned with the DUT. There are three set-ups:

| Mode | How you turn it on | Who updates the mirror | Sees firmware, DMA or other masters? | Typical failure |
| --- | --- | --- | --- | --- |
| **Implicit** (auto-predict) | `ral.default_map.set_auto_predict(1);` | `read()`/`write()` call `do_predict()` when their own access completes | No | Mirror misses every access the RAL did not start; it trusts the adapter's round trip |
| **Explicit** | `agent.mon.ap.connect(predictor.bus_in);` plus `predictor.map` and `predictor.adapter` | The `uvm_reg_predictor`, from every transfer the monitor sees | Yes | A missing `connect()` is silent; a null adapter is `UVM_FATAL REG/WRITE/NULL` |
| **Passive** | A predictor on a bus the RAL never drives | The predictor only | Yes | Same wiring risks as explicit |

Out of the box, `uvm_reg_map` starts with auto-predict **off** and no predictor exists, so frontdoor accesses do not update the mirror until you choose one. Backdoor `peek()` and `poke()` are different: they call `do_predict()` themselves.

## Adapter/Predictor/Mirror Debug Workflow
When the RAL mirror diverges from the DUT, use this deterministic workflow. The **Debug** tab of the visual above walks through the most common case.

1. **Was the access predicted at all?** With auto-predict off, only a connected `uvm_reg_predictor` updates the mirror. Check `agent.mon.ap.connect(predictor.bus_in)` in `connect_phase`; a missing connection produces no warning.
2. **Did the monitor publish the transfer?** Check the bus monitor's `ap` ([analysis port](/curriculum/T2_Intermediate/I-UVM-2B_TLM_Connections/index)) and that it publishes reads with their data.
3. **Did `bus2reg()` rebuild the operation?** Wrong `kind`, `addr` or `status` sends the prediction to the wrong register or skips it (`UVM_NOT_OK` is not predicted).
4. **Does the field's policy and volatility match the hardware?** The predictor applies the policy: an RO field ignores the written bits, W1C clears, RC clears on a read. A hardware-driven field configured `volatile = 0` produces false `mirror(UVM_CHECK)` mismatches.
5. **Is the access predicted twice?** Auto-predict plus a connected predictor predicts every RAL access twice. Toggle (W1T) fields end up back where they started.

> **Interview Pitfall:** A common interview question asks "My RAL mirror isn't updating after a bus write, why?". The most frequent architectural cause is simply forgetting to connect the bus monitor's [analysis port](/curriculum/T2_Intermediate/I-UVM-2B_TLM_Connections/index) to the `uvm_reg_predictor` in the `connect_phase`.

## Memories — `uvm_mem` (IEEE 1800.2-2020 §18.6)

RAL also models addressable memories via `uvm_mem`. Memories have **no mirror**: the model keeps their size, width, access and address, and `uvm_reg_predictor` does not predict memory accesses. Size, width and access are constructor arguments, so a memory is a small subclass:

```systemverilog
class sram_mem extends uvm_mem;
  `uvm_object_utils(sram_mem)
  function new(string name = "sram_mem");
    super.new(name, 1024, 32, "RW", UVM_NO_COVERAGE);   // 1K words x 32 bits
  endfunction
endclass

class sram_block extends uvm_reg_block;
  `uvm_object_utils(sram_block)
  sram_mem      sram;
  uvm_reg_map   mem_map;

  function new(string name = "sram_block");
    super.new(name, UVM_NO_COVERAGE);
  endfunction

  virtual function void build();
    sram = sram_mem::type_id::create("sram");
    sram.configure(this, "sram_q");   // parent block, optional HDL path
    mem_map = create_map("mem_map", 'h0, 4, UVM_LITTLE_ENDIAN);
    mem_map.add_mem(sram, 'h0000, "RW");
    lock_model();
  endfunction
endclass
```

**Memory allocation manager** (`uvm_mem_mam`, §18.12) tracks allocated regions so DMA tests can claim and release buffer space without address collisions. Every `uvm_mem` builds one in `configure()`, available as its `mam` member:

```systemverilog
uvm_mem_region r = ral.sram.mam.request_region(256);   // 256 BYTES = 64 32-bit words, random free offset
// ... program the DMA with r.get_start_offset() ...
r.release_region();
```

## Volatile and Special Access Policies

Not every field behaves like simple RW memory. Several access policies need care because **the hardware changes the field value behind the RAL's back**:

| Policy | Behavior | Mirror Implication |
| --- | --- | --- |
| **W1C** (Write-1-to-Clear) | Writing `1` to a bit clears it | The prediction for a write is mirror AND NOT data. When hardware *sets* the bit, nothing is predicted until a read, `peek()` or `predict()` |
| **W1S** (Write-1-to-Set) | Writing `1` to a bit sets it | The prediction is mirror OR data |
| **W1T** (Write-1-to-Toggle) | Writing `1` to a bit toggles it | The prediction is mirror XOR data, so a double prediction undoes it |
| **RC** (Read-to-Clear) | Reading the field clears it | A predicted frontdoor read sets the mirror to 0. `peek()` does not clear the hardware |
| **Volatile** | HW can change the value at any time | `configure(…, volatile = 1, …)` sets the compare mode to `UVM_NO_CHECK`, so `mirror(UVM_CHECK)` skips the field unless you call `set_compare(UVM_CHECK)` |

> **Gotcha:** If hardware sets a W1C status bit after your last access, the mirror is stale until the next read, `peek()` or `predict()`. If that field is configured `volatile = 0`, `mirror(UVM_CHECK)` reports a mismatch that is not a DUT bug. Configure hardware-driven fields as volatile, and check them by reading the value and comparing it with what your scoreboard expects.

## `set_auto_predict()` Strategy

Auto-predict is **off** by default (`uvm_reg_map::new` clears it). Turning it on makes `read()` and `write()` predict their own access when it completes. It does not disable or replace a predictor: if a predictor is also connected, the access is predicted twice.

| Mode | Pros | Cons |
| --- | --- | --- |
| Explicit (`uvm_reg_predictor`) | Sees every master on the bus; predicts what the bus really carried | Requires monitor, predictor and wiring |
| Implicit (auto-predict) | No predictor needed, fast bring-up | Blind to firmware, DMA and other masters; predicts the value it wrote rather than what the bus carried, so `reg2bus()` bugs stay hidden |

**When to use auto-predict:**
- Early bring-up, before a monitor exists.
- Production environments where the register model is the **only** initiator on that bus and the adapter round trip is trusted.
- Never together with a connected predictor on the same map.

```systemverilog
// Bring-up: the RAL is the only master and there is no monitor yet
cfg_map.set_auto_predict(1);

// Explicit prediction: leave auto-predict at 0 and wire the predictor
cfg_map.set_auto_predict(0);
predictor.map     = ral.cfg_map;
predictor.adapter = adapter;
axi_agt.monitor.ap.connect(predictor.bus_in);
```

## Multi-Map Concerns

When the same register is accessible from multiple bus interfaces (e.g., AXI config bus and APB debug port), there is still **one** register object and **one** mirror; every map references it. What each bus with traffic needs is its own:
- Adapter instance (different bus protocols).
- Predictor instance, with `predictor.map` set to **that bus's map** so it decodes that bus's addresses.
- Sequencer assignment (`set_sequencer` on each map).

A write through map A, predicted by A's predictor, updates the same mirror that a read through map B compares against. If one bus has no predictor, accesses on it are invisible to the model.

## Make It Work
1. **Instantiate Predictors:** Build the adapter and predictor in the `build_phase`.
2. **Connect the Flow:** In `connect_phase`, call `set_sequencer()` on each map, wire the bus monitor's `ap` into the predictor's `bus_in`, and assign `predictor.map` and `predictor.adapter`. Leave auto-predict at 0.
3. **Mirror responsibly:** Decide which registers need continuous mirroring; use backdoor `mirror()` or `peek()` where speed matters and HDL paths exist.
4. **Handle volatile fields:** Configure interrupt-status and other HW-modified fields as volatile. Check them by reading and comparing against your scoreboard's expectation, or temporarily with `set_compare(UVM_CHECK)`, rather than relying on `mirror(UVM_CHECK)`.

**Checklist before moving on:**
- [ ] You can define implicit and explicit prediction without mixing them up.
- [ ] You can systematically debug why a mirror fails to update, including the silent missing `connect()`.
- [ ] Your environment exposes the predictor so tests do not drill through component internals.
- [ ] You know when `set_auto_predict(1)` is appropriate and why it must not be combined with a predictor.
- [ ] You know how volatile, W1C, W1T and RC policies affect the mirror and the check.
