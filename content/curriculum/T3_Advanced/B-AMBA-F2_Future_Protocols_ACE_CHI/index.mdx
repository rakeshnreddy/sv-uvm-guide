## Quick Take

- **What it is:** **ACE** (AXI Coherency Extensions, AMBA 4) adds hardware cache coherency to AXI: extra signals on the AXI read and write channels, plus three snoop channels into every master that has a cache (Arm IHI0022E Part C). **CHI** (Coherent Hub Interface, AMBA 5) does the same job as a layered, packet-based protocol built for large interconnects such as rings and meshes (Arm IHI0050E.b).
- **Why it matters:** When several caches can hold copies of the same memory, the question is no longer only "is this interface legal?" but "do all the caches together still agree on the newest value?". No checker that looks at one interface can answer that. Coherency changes what your scoreboard models, what your assertions see and how you debug.
- **The Analogy:** A team shares one design document stored on a file server. Anyone may keep a read-only printout (a **Shared** copy). Only one person at a time may hold the editable copy (a **Unique** copy). Whoever has edited it and not yet uploaded owes the server an upload (a **Dirty** copy). A **snoop** is the coordinator saying "hand me your latest edits" or "shred your printout". *Where it breaks:* the unit is a cache line (a block of bytes, 64 bytes in CHI), not a document; copies are destroyed or downgraded, never updated in place; and a "clean" printout can still differ from the server when someone else owes the upload.

The folder name of this lesson says "Future Protocols". That is historical: ACE was first released in the AMBA AXI and ACE specification Issue D on 28 October 2011, and CHI Issue A on 12 June 2014, with the first public CHI issue (B) on 4 August 2017 (IHI0022H.c and IHI0050E.b change histories). Both are current AMBA protocols.

**You will be able to:**
1. Explain the coherency problem (a stale copy and a dirty copy of the same line) and how snoops through the interconnect solve it.
2. Trace a ReadShared and a store (CleanUnique, then WriteBack) through two caches' ACE states, naming the snoop, the CRRESP and RRESP[3:2] bits, the acknowledge, and who must update memory.
3. Compare CHI with ACE: node types, the four channels, credit-based (L-Credit) flow control and Direct Cache Transfer.
4. Design the outline of a coherency checker that sees every coherent port and enforces the global rules: a Unique copy is the only copy, at most one copy is Dirty, and read data matches a golden value.

## Build Your Mental Model

**How to read this lesson.** The core path is: the words, why AXI alone is not enough, the five ACE states, what ACE adds to an AXI port, one traced read and one traced store, CHI in one picture, and how coherency changes the checker. Each has a picture. The scope is the *concept* level: the encodings and the corner cases are there for reference, and the expert layer is in Push Further. Building a full coherency VIP is out of scope.

### Words you need first

- **Cache, cache line.** A cache is a small fast memory next to a processor that keeps copies of recently used memory. It stores data in fixed-size blocks called **cache lines** (often 64 bytes). Coherency is tracked per line, never per byte.
- **Load, store, hit, miss.** A processor *loads* (reads) and *stores* (writes). A **hit** means the line is already in the cache; a **miss** means it must be fetched.
- **Write-back cache.** A store updates only the cached copy; main memory is updated later, when the line is written back or evicted (removed to make room). Until then the cache holds the only up-to-date copy. This is why stale memory exists at all.
- **Master, interconnect, slave.** The master starts a transaction, the interconnect routes it and the slave answers. IHI0022E, the issue this track cites, uses master and slave. Later Arm issues (IHI0022H.b onwards) say *manager* and *subordinate*, and CHI says *Requester*, *Completer* and *Subordinate* for the same roles.
- **Shareable.** A memory location that the caches of several masters may hold. Only Shareable accesses need coherency.
- **Coherent.** "Regions of memory are coherent if writes to the same memory location by two components are observable in the same order by all components" (IHI0022E §C1.1; the same sentence opens IHI0050E.b §1.5). Hardware coherency removes the need for software to flush and invalidate caches by hand (**software cache maintenance**).
- **Snoop.** A request from the interconnect to a cached master asking it to look up a line in its cache and supply it, downgrade it or remove it.
- **Snoop filter.** An optional table in the interconnect that records which masters may hold each line, so it can skip snoops to masters that cannot have it.
- **Point of coherence (PoC).** "A point at which all agents that can access memory are guaranteed to see the same copy of a memory location"; in a typical CHI system it is the Home Node, defined below (IHI0050E.b §1.3). IHI0022E does not use the term; in an ACE system the coherent interconnect, which issues the snoops, plays that role.
- **DVM (Distributed Virtual Memory) messages.** Messages that keep address-translation caches (TLBs) in step across masters. This lesson only names them.

### Why AXI alone is not enough

Here is the classic failure. Read it, then predict before you look at the first picture.

1. CPU0 reads address `0x8000`; the line holding it is now in CPU0's cache.
2. CPU1 writes a new value, M1, to `0x8000`. Its write-back cache keeps M1; memory still holds the old value, M0.
3. A DMA engine (a master without a cache that copies buffers) reads `0x8000` through a plain AXI4 interconnect.

**Predict:** what value does the DMA read, and could the AXI4 interconnect have done anything about it?

**Debrief.** The DMA reads M0. The interconnect only routes addresses to slaves; it has no channel into CPU1's cache, so it cannot know that CPU1 holds a newer value. AXI ordering does not help either: ordering decides which of two transactions happens first, not whether a cache holds a newer copy. Without coherency, software must clean CPU1's cache (force the write-back) before starting the DMA.

Now the same system with ACE. Two things change. First, CPU1's store did not happen silently: CPU1 had to make its copy **Unique** (the only copy) first, which removed CPU0's copy, so CPU1 now holds the line **UD** (UniqueDirty: the only copy, and modified) and CPU0 holds nothing (**I**, Invalid). The next section defines these states, and you will trace this store later. Second, the DMA uses **ACE-Lite**, a version of the interface for masters without a coherent cache, and issues a **ReadOnce**: a coherent read of a snapshot it will not cache (IHI0022E §C1.4.2, §C11.1).

The interconnect sends its snoop to CPU1 on a new channel, **AC** (snoop address). CPU1 answers on **CR** (snoop response) with yes-or-no bits such as **DataTransfer** (the line follows) and **IsShared** (CPU1 keeps a copy), and sends the line itself on **CD** (snoop data). The section "What ACE adds to an AXI port" below defines all of them.

That is the whole idea of hardware coherency: before answering a Shareable access, the interconnect asks the caches that might hold the line. Everything else in this lesson is about *which* question it asks, *what* each cache must answer, and *who* owes memory the update.

**Pitfalls.**
- "The interconnect orders the write before the read, so the DMA sees M1." Ordering is not coherence: CPU1's store never left its cache.
- "Writes go straight to memory." Not in a write-back cache; that is the whole problem.
- "Coherency means memory is always up to date." Neither ACE nor CHI requires that. CHI says main memory "is only required to be updated before a copy of the memory location is no longer held in any cache" (IHI0050E.b §1.5.1).

### The five ACE cache states

ACE describes every cached copy with three yes-or-no characteristics (IHI0022E §C1.2.3):

- **Valid or Invalid:** is the line present in this cache?
- **Unique or Shared:** Unique means the line exists *only* in this cache. Shared means it *might* exist in other caches, "but this is not guaranteed".
- **Clean or Dirty:** Clean means "the cache does not have responsibility for updating main memory". Dirty means the line has been modified with respect to memory and *this* cache must make sure memory is eventually updated.

They combine into five states (Table C1-2):

| State | Name | Present only here? | Owes memory the update? | May store without telling anyone? |
|---|---|---|---|---|
| I | Invalid | not present | no | no (must first obtain the line) |
| UC | UniqueClean | yes | no | yes, and the line becomes UD |
| UD | UniqueDirty | yes | **yes** | yes |
| SC | SharedClean | maybe not | no | no: must notify other caches first |
| SD | SharedDirty | maybe not | **yes** | no: must notify other caches first |

The **cache state rules** that every coherent system must obey (§C1.2.3) give the two invariants your checker will enforce:

1. "A line in a Unique state must only be in one cache." So if any cache holds UC or UD, every other cache holds I. **(single writer)**
2. "A line that has been updated, relative to main memory, and is in more than one cache, must be in a Dirty state in only one cache." So at most one cache holds UD or SD. **(single owner)**

The other rules: a line in several caches is Shared in every one of them; a cache that obtains a new copy must make other holders treat the line as Shared; and a cache that discards its copy has no duty to inform the *other caches* that hold the line, so "Shared" may in fact mean "the only copy left". Discarding still has rules: a Dirty copy must first be written back or passed on, and in a system with a snoop filter a clean line is dropped with an Evict (see the eviction rules below).

**Pitfalls and misconceptions.**
- **"Clean means equal to memory."** No. SC means only that *this* cache does not owe the update; Table C1-2 says of SC "it is not known if the cache line is modified with respect to main memory". If another cache holds the line SD, the SC copy is newer than memory. A checker that compares SC data with memory fails falsely.
- **"SD means others hold copies."** SD *might* be shared. Shared is a permission ("tell others before you store"), not a head count.
- **"ACE is MOESI."** It is close: UD, UC, SD, SC and I correspond roughly to the textbook Modified, Exclusive, Owned, Shared and Invalid. But IHI0022E defines its own five states and says ACE can connect components that use MESI, ESI, MEI and MOESI (§C1.1.2). Use the ACE names when you talk about ACE.

### What ACE adds to an AXI port

ACE keeps the five AXI channels (AR, AW, W, R, B) and adds signals and channels (IHI0022E §C1.3, Tables C1-3 to C1-5):

| Where | Added | Direction | What it says |
|---|---|---|---|
| AR | ARSNOOP[3:0], ARDOMAIN[1:0], ARBAR[1:0] | master → interconnect | the coherent read type (for example ReadShared), the shareability domain, and whether it is a barrier |
| AW | AWSNOOP[2:0], AWDOMAIN[1:0], AWBAR[1:0], AWUNIQUE (required only by masters that support WriteEvict) | master → interconnect | the coherent write type (for example WriteBack), domain, barrier |
| R | RRESP[3:2]: PassDirty (bit 2), IsShared (bit 3) | interconnect → master | the state the reader must take, and whether it now owes memory the update |
| W, B | nothing new | — | — |
| AC (snoop address) | ACVALID, ACREADY, ACADDR, ACSNOOP[3:0], ACPROT[2:0] | interconnect → cached master | the snoop: address and type |
| CR (snoop response) | CRVALID, CRREADY, CRRESP[4:0] | cached master → interconnect | one response per snoop |
| CD (snoop data, optional) | CDVALID, CDREADY, CDDATA, CDLAST | cached master → interconnect | the cache line, when the response says data follows |
| acknowledges | RACK, WACK | master → interconnect | "I have finished this read" and "this write" |

**CRRESP bits** (Table C3-22): [0] DataTransfer (a line follows on CD), [1] Error, [2] PassDirty (the line was Dirty and the responsibility for writing it back is being handed over), [3] IsShared (the snooped cache keeps a copy), [4] WasUnique (the line was Unique before the snoop).

**Shareability domains** (§C1.6.1, Table C3-2) say *which* masters might hold a copy: AxDOMAIN `0b00` Non-shareable, `0b01` Inner Shareable, `0b10` Outer Shareable, `0b11` System. Only Inner and Outer Shareable accesses can cause snoops, and the interconnect snoops only the masters inside that domain: every coherent (snooped) read and write uses `0b01` or `0b10` (Tables C3-7, C3-8). Non-shareable and System accesses are non-snooping. System is the widest domain, but it holds no cached copies: a System-domain location "cannot be held in any cache" (§C3.1.1). A Device access must use System, and a Cacheable access must not (Table C3-2). Apart from barriers, only ReadNoSnoop and WriteNoSnoop may use it.

**ACE-Lite** (§C11.1) is for masters "that do not have hardware coherent caches", such as the DMA. It is AXI4 plus the AR and AW signals only: no AC, CR or CD channels, no RACK or WACK, and no extra RRESP bits. An ACE-Lite master can issue ReadOnce, WriteUnique and WriteLineUnique (snooped accesses that it does not cache), barriers and the cache maintenance transactions CleanShared, CleanInvalid and MakeInvalid (Tables C11-1, C11-2), but it is never snooped.

### Transactions and the snoops they cause

ACE names each coherent access by its purpose (§C1.4). You need the groups, not the encodings, at this level:

| Group | Transactions | Use |
|---|---|---|
| Non-snooping | ReadNoSnoop, WriteNoSnoop | Non-shareable or Device accesses (Device memory types are in [B-AXI-4](/curriculum/T3_Advanced/B-AXI-4_AXI_Expert_Features_Cache_Atomics/index)); no snoops |
| Coherent loads | ReadClean, ReadNotSharedDirty, ReadShared | fetch a line to cache; other holders may keep their copy (the three differ in the end states the reader accepts, below) |
| Coherent stores | ReadUnique, CleanUnique, MakeUnique | get a Unique line so the master may store |
| No cached copy kept | ReadOnce, WriteUnique, WriteLineUnique | snapshot reads and writes by masters that do not cache the line (ACE-Lite) |
| Memory update | WriteBack, WriteClean, WriteEvict, Evict | write a dirty line back (WriteBack, WriteClean), push a clean line to a lower-level cache (WriteEvict), or announce an eviction (Evict); *not snooped* |
| Cache maintenance | CleanShared, CleanInvalid, MakeInvalid | software-requested clean or invalidate of *other* caches |
| Barrier, DVM | barrier transactions; DVM messages | ordering guarantees; virtual-memory maintenance |

The three **load** transactions differ in what the reader can accept (§C4.5.3 to §C4.5.5):

- **ReadClean:** only a Clean line (UC or SC). It is "guaranteed not to pass responsibility for updating main memory to the initiating master", for example a master with a write-through cache (one that sends every store on to memory, so it never holds a dirty line).
- **ReadNotSharedDirty:** any state except SD.
- **ReadShared:** any state. This is the usual load of a write-back cache.

The three **store** transactions differ in what the master already has (§C1.4.2, §C1.3.4):

- **ReadUnique:** a partial-line store and the master holds no copy. It fetches the data and removes every other copy.
- **CleanUnique:** a partial-line store and the master already holds a copy (SC or SD). It fetches nothing; it removes every other copy, and any Dirty copy elsewhere is written to memory.
- **MakeUnique:** a *full*-line store. It fetches nothing and removes every other copy, because every byte is about to be overwritten. It "must only be used by an initiating master that is carrying out a full cache line store operation" (§C4.7.1).

The interconnect turns each request into a snoop. The recommended mapping (Table C5-1) is mostly one-to-one (ReadShared → ReadShared snoop, ReadOnce → ReadOnce snoop), with four you must remember: **CleanUnique → CleanInvalid snoop**, **MakeUnique → MakeInvalid snoop**, **WriteUnique → CleanInvalid snoop** and **WriteLineUnique → MakeInvalid snoop**. Only eight coherency snoop types may appear on AC: ReadOnce, ReadClean, ReadNotSharedDirty, ReadShared, ReadUnique, CleanInvalid, MakeInvalid and CleanShared (§C5.1.1). The only other ACSNOOP encodings are DVM Message and DVM Complete (Table C3-20).

What a snooped cache must do (Table C5-3):

| Snoop | Must transfer the line if Dirty | End state must be |
|---|---|---|
| ReadOnce | yes | any (no change required) |
| ReadClean, ReadNotSharedDirty, ReadShared | yes | Shared or Invalid |
| ReadUnique, CleanInvalid | yes | Invalid |
| CleanShared | yes | Clean or Invalid |
| MakeInvalid | **no** | Invalid |

**Pitfall: MakeInvalid discards dirty data.** A MakeInvalid snoop removes the copy "but it is not required to provide any data, even if the cache line is dirty" (§C1.4.4). That is correct only when the whole line is about to be overwritten. Software that uses MakeInvalid on a buffer it still needs loses the newest data, and the protocol does not stop it.

**Debrief.** The interconnect sends a ReadShared snoop, the recommended mapping (Table C5-1). A has a dirty line, so it must transfer it (Table C5-3). A then has three legal answers (Table C5-8), and B's state follows the RRESP[3:2] bits the interconnect gives it (Table C4-9; RRESP[3] is IsShared, RRESP[2] is PassDirty):

| A answers (CRRESP) | A ends | B gets RRESP[3:2] | B ends | Who owes memory |
|---|---|---|---|---|
| PassDirty=0, IsShared=1 | SD | 10 | SC | A |
| PassDirty=1, IsShared=1 | SC | 11 | SD | B |
| PassDirty=1, IsShared=0 | I | 01 | UD | B |

Rows 2 and 3 assume the interconnect passes the dirty line on to B. It may instead write the line to memory itself and give B PassDirty=0, so B ends SC or UC and memory becomes current. The interconnect must pass PassDirty on to the requester when a snoop response asserted it "and the interconnect has not generated a write transaction to update main memory" (§C6.4, Table C6-2). A checker must therefore take B's state from B's own RRESP, never predict it from A's CRRESP alone.

If dirty responsibility was handed over (PassDirty=1) but the requester cannot take it (ReadClean, for example), "the interconnect is responsible for writing back the dirty line to main memory" (§C1.4.2, §C3.7). Responsibility never disappears: one cache, or the interconnect, always owns it.

The read ends with **RACK**: B asserts it for one cycle, no earlier than the cycle after the last R handshake (the one with RLAST), and must not delay it to wait for another transaction (§C3.3). RACK tells the interconnect that the read has completed at B: after giving B a response for a line, the interconnect must not snoop B for that line until the RACK (or, for a write, the WACK) arrives (§C6.2).

**Debrief.**
- CleanUnique is snooped as **CleanInvalid** (Table C5-1). A dirty snooped copy must be supplied and the copy removed (§C1.4.4, Table C5-3); moving Dirty to Invalid requires PassDirty=1 (§C5.2, the rules after Table C5-4). The interconnect then "constructs the transaction to write the dirty cache line back to main memory" (§C1.3.4).
- The interconnect may give B permission to store only once earlier updates to memory are ordered (§C6.5.3); otherwise B's later WriteBack could overtake M1 and memory would end with the older value.
- B's response is a single R transfer with RRESP[3:2] = 00 and no valid data (§C3.2, §C4.6.1); B moves SC → UC (Table C4-13), and after the store a master "must be in the UniqueDirty state" (§C4.3.2).
- **WriteBack** is not snooped (§C1.4.3). B ends Invalid (Table C4-24) and acknowledges the write response with **WACK**, again one cycle, no earlier than the cycle after the B handshake (§C3.5).
- A clean line can be dropped with an **Evict** transaction (which carries no data and helps a snoop filter, §C1.4.3) or, if no snoop filter is used, silently.

**Pitfall: a partial store with no copy.** If B held nothing, CleanUnique would leave it Unique *without data*, and only a full-line store would be legal (§C4.6.1). For a partial store without a copy, use ReadUnique. For a full-line store, MakeUnique (snooped as MakeInvalid) skips the useless data fetch.

### CHI: the same job as a network protocol

CHI keeps the coherency ideas (the same Valid/Unique/Clean characteristics, the same snoop-then-respond pattern) but changes how messages travel. It splits the protocol into three **layers** (IHI0050E.b §1.1.2, Table 1-1): the **Protocol** layer (transactions, cache states), the **Network** layer (packets with source and target node IDs for routing) and the **Link** layer (flits and flow control between neighbours). A **flit** (flow control unit) is the smallest unit the link layer moves; in CHI every packet is exactly one flit (§1.3). A data message is 1 to 4 packets, because a 64-byte line needs 1, 2 or 4 flits on a 512-, 256- or 128-bit data channel (§1.3, §13.9.4).

**Nodes.** Components are classified by node type (§1.6):

| Node | Role |
|---|---|
| RN-F | Fully coherent Request Node: has a hardware-coherent cache and supports all snoops (a CPU cluster) |
| RN-D | IO coherent Request Node *with DVM support*: no coherent cache, receives DVM messages |
| RN-I | IO coherent Request Node: no coherent cache, no snoops (a DMA engine; the CHI counterpart of ACE-Lite) |
| HN-F | Fully coherent Home Node: the **Point of Coherence** (PoC) for its addresses, snoops the RN-Fs and is expected to be the **Point of Serialization** (PoS) that orders requests to the same address; *might* include a directory or snoop filter |
| HN-I | Non-coherent Home Node for IO addresses |
| MN | Miscellaneous Node: receives DVM operations and broadcasts them as snoops |
| SN-F, SN-I | Subordinate Nodes: SN-F for Normal memory, SN-I for peripherals or Normal memory |

**Channels.** There are four, each carrying one kind of flit (§13.4, Table 13-1): **REQ** (requests), **RSP** (responses without data, including snoop responses and CompAck), **SNP** (snoop requests, including DVM snoops) and **DAT** (anything with data). There is no fifth "misc" channel: link credits are signals, a DVM operation is a request on REQ (with its payload on DAT) that the MN broadcasts as a snoop on SNP (§8.1.1), and cache maintenance is an ordinary dataless request on REQ (Table 4-24).

**Credit-based flow control.** AXI and ACE move every beat with a VALID/READY handshake: the receiver can stall the sender in the same cycle. CHI's link layer uses **L-Credits** instead (§14.2.1). The receiver gives the transmitter one credit by pulsing that channel's **LCRDV** signal for one cycle; each flit the transmitter sends (FLITV high) consumes one credit; a receiver may hand out between 1 and 15 credits per channel and "must guarantee that it can accept all the flits for which it has issued L-Credits". A credit "cannot be used in the cycle it is received". There is no READY: a transmitter with no credit simply waits.

**Debrief.** The expected snoop for ReadShared is SnpSharedFwd (Table 4-24); the Home may also use SnpShared, SnpClean, SnpNotSharedDirty or their Fwd forms, but not an invalidating snoop such as SnpCleanInvalid, and a non-forwarding snoop cannot produce forwarded data (§4.4). So the answer to the prediction: RN-F1 sends the data straight to RN-F0, and the Home, not RN-F0, takes the duty to update memory, because RN-F1 passed it the dirty line (PD).

**Reading CHI message names.** CHI puts the states into the message names (§4.5.1, §4.5.3):

- **`CompData_X`:** read data that completes the request; the requester ends in state X. A `_PD` suffix (Pass Dirty) would mean the duty to update memory passes to the requester.
- **`SnpResp_X`** and **`SnpRespData_X`:** the snooped node's state *after* it responds is X. `Data` means it also sends the line to the Home, and `_PD` means it passes on the duty to update memory.
- **`..._Fwded_Y`:** the snooped node also forwarded the data to the requester, giving it state Y.
- **CompAck:** the requester's last message, "sent by the Requester on receipt of the completion response" (§4.5.4). Like RACK in ACE, it closes the transaction at the requester.

So `SnpRespData_SC_PD_Fwded_SC` reads: "I am now SC, here is the line, I pass you the dirty duty, and I forwarded an SC copy to the requester".

|---|---|---|

| Topology | not specified | topology-independent; crossbar, ring and mesh are examples (§1.2) |

**Misconception: "CHI is AXI with more signals."** It is not. CHI has no AXI channels, no READY signal and no per-channel handshake; it has layers, nodes, routed packets and credits.

### How coherency changes verification

An AXI checker asks local questions: is VALID stable until READY, does the burst stay inside 4KB, do responses with the same ID come back in order? Every one can be answered by watching one interface.

The coherency rules are **global**: "a Unique line is in only one cache" is a statement about *all* caches at once. A port checker on cache A sees A move to UD and finds nothing wrong; a port checker on cache B sees B move to SC and finds nothing wrong. Only a component that sees both ports can see that UD next to SC breaks the single-writer rule. That is the third misconception on this page: **coherency cannot be checked per interface.**

So a coherency checker has three parts:

1. **Passive monitors** on every coherent port, including ACE-Lite ports, and on the interconnect's memory port. Each reports only what it saw: requests, snoops, CRRESP and RRESP[3:2], RACK and WACK, memory writes, and the data. The model, not the monitor, decides what the responses mean.
2. **One line model** shared by all ports. For each line address it keeps the state of every cache (or, where the tables allow several end states, the set of legal ones), the newest value written (the **golden** value), what memory holds, and an "interconnect owes memory" flag. The flag is set when a snoop response passes a dirty line (PassDirty=1) and cleared when the requester takes the duty (its RRESP has PassDirty=1) or the memory write is seen.
3. **Global checks after every update:**
   - *safety* (nothing illegal ever happens): a Unique holder is the only valid copy; at most one Dirty holder; when no cache is Dirty and the interconnect owes nothing, memory equals the golden value; every read returns the golden value;
   - *liveness* (what must happen does happen): every AC snoop gets exactly one CR response, and every R or B response to an ACE master gets its RACK or WACK, within a time bound you choose as a policy;
   - *snoop filter, if there is one:* every cache that holds a valid copy is recorded in it. A missed holder is a stale read waiting to happen.

Where does the golden value come from? Not from the ACE port: a store to a Unique line causes no transaction at all (§C4.3.2). It must come from the master side, the CPU stimulus or a model of the cache. A checker that sees only the ports can check only data that leaves a cache, on CD, on R or in a write.

**Why not one big concurrent assertion?** A class-based scoreboard cannot hold concurrent assertions: they may appear only in always or initial procedures, modules, interfaces, programs, generate blocks and checkers (IEEE 1800-2023 §16.14), and their expressions "shall not reference non-static class properties or methods" (§16.6). Put the global check in a procedural function called after every observed change, and report with `` `uvm_error ``. Concurrent SVA (or formal) can express the same invariant over module-level state arrays, for example in a formal harness of a few caches and one line.

### Debugging coherency failures

| Symptom | Likely cause | Look first at |
|---|---|---|
| A CPU reads stale data after a DMA or a peer's write | a missing clean or invalidate, a non-snooped access (wrong AxDOMAIN), or ownership passed wrongly | the line's ownership timeline; the AxDOMAIN of the write |
| The checker reports "Unique copy coexists with another copy" | the interconnect chose a snoop that does not downgrade (for example ReadOnce for ReadShared), or a master ignored a snoop | the AC snoop type against Table C5-2, and the CRRESP |
| Memory holds an old value after all caches are Invalid | dirty data lost: PassDirty dropped, a MakeInvalid on a dirty line, or a write-back that the interconnect never issued | CRRESP.PassDirty on the last snoop; the interconnect's write-back |
| Hang under coherent stress | a snoop blocked behind the master's own reads, or a credit or retry that never returns | snoop channel stalls (ACE); LCRDV and PCrdGrant counts (CHI) |
| Directory or snoop filter disagrees with the caches | a lost Evict or snoop response | the snoop filter's view against the line model |

**The method:** do not start from a signal waveform. Print one **ownership timeline** per suspect line, one row per state change with the cause, for example `COH line=0x8000 t=1250ns cache=1 UD->SD snoop=ReadShared CRRESP=DT,IS`, find the first row that breaks a rule, and only then open the waveform for that transaction.

### Recap

- Coherency means all caches observe writes to a location in one order; without it, a write-back cache hides newer data from other masters (objective 1).
- ACE describes copies with Unique/Shared and Clean/Dirty; a Unique copy is the only copy, and at most one copy is Dirty. Clean does not mean "equal to memory".
- ACE adds AR/AW coherency signals, RRESP[3:2], the AC/CR/CD snoop channels and RACK/WACK to an AXI port; ACE-Lite adds only the AR/AW signals.
- Reads are snooped so the newest data comes back and the states follow CRRESP and RRESP[3:2]; stores first make the line Unique (ReadUnique, CleanUnique or MakeUnique), and dirty data always has exactly one owner, a cache or the interconnect (objective 2).
- CHI does the same job with layers, nodes (RN, HN, SN, MN), four credited channels and Direct Cache Transfer (objective 3).
- The checker is global: monitors on every port feed one line model that checks single writer, single owner and golden data (objective 4).

## Make It Work

### A runnable line model and checker

The example below is the heart of a coherency checker, stripped to one line and two caches so you can read it in one sitting. `coh_line_model` holds each cache's state, the golden value, what memory holds and the "interconnect owes memory" flag; `check_line()` is the global check. `tb_top` replays the two traces above as one story (every step legal; the values M0, M1 and M2 are `'hA0`, `'hA1` and `'hA2`), then one mutant in which the interconnect answered a ReadShared with a ReadOnce snoop, so A kept UD while B took SC. The checker must accept every legal step and reject the mutant.

```systemverilog
// compile
// One cache line, NCACHE caches: the global ACE rules of IHI0022E C1.2.3.
package coh_pkg;

  typedef enum logic [2:0] {ACE_I, ACE_UC, ACE_UD, ACE_SC, ACE_SD} ace_state_e;

  class coh_line_model #(int NCACHE = 2);
    ace_state_e  st[NCACHE];  // state of the line in each cache
    logic [31:0] golden;      // newest value written (one word stands in for the line)
    logic [31:0] memory;      // what main memory holds
    bit          ic_owes;     // a snoop passed dirty data that is not yet in memory
                              // or with a requester (updated from the monitors)

    function new(logic [31:0] init);
      foreach (st[n]) st[n] = ACE_I;
      golden  = init;
      memory  = init;
      ic_owes = 0;
    endfunction

    // Call after every observed state change. Returns 1 when the line is legal.
    function bit check_line(output string why);
      int unsigned valid_n = 0, unique_n = 0, dirty_n = 0;
      foreach (st[n]) begin
        if (st[n] != ACE_I)                valid_n++;
        if (st[n] inside {ACE_UC, ACE_UD}) unique_n++;
        if (st[n] inside {ACE_UD, ACE_SD}) dirty_n++;
      end
      why = "";
      // Single writer: a Unique copy must be the only valid copy.
      if (unique_n > 1 || (unique_n == 1 && valid_n > 1))
        why = "a Unique copy coexists with another copy (C1.2.3)";
      // Single owner: at most one cache owes memory the update.
      else if (dirty_n > 1)
        why = "more than one Dirty copy (C1.2.3)";
      // Nobody owes the update, so memory must already hold the newest value.
      else if (dirty_n == 0 && !ic_owes && memory != golden)
        why = "no cache is Dirty but memory is stale";
      return (why == "");
    endfunction

    // Every read, from any port, must return the newest value.
    function bit read_ok(logic [31:0] data);
      return (data == golden);
    endfunction
  endclass

endpackage

module tb_top;
  import coh_pkg::*;

  coh_line_model #(.NCACHE(2)) m;
  int pass_n = 0;
  int fail_n = 0;

  // Apply what the port monitors observed after one step, then run the global check.
  // expect_ok = 0 marks a step the checker must reject.
  function automatic void observe(string step, ace_state_e a, ace_state_e b,
                                  logic [31:0] mem, logic [31:0] newest, bit expect_ok);
    string why;
    string verdict;
    bit    ok;
    m.st[0] = a;
    m.st[1] = b;
    m.memory = mem;
    m.golden = newest;
    ok = m.check_line(why);
    if (ok) verdict = "ok";
    else    verdict = {"VIOLATION: ", why};
    if (ok == expect_ok) pass_n++;
    else                 fail_n++;
    $display("CHK %s | A=%s B=%s mem=%h newest=%h | %s",
             step, a.name(), b.name(), mem, newest, verdict);
  endfunction

  initial begin
    m = new(32'h0000_00A0);
    observe("0 start",                   ACE_I,  ACE_I,  32'hA0, 32'hA0, 1);
    observe("1 A ReadShared",            ACE_UC, ACE_I,  32'hA0, 32'hA0, 1);
    observe("2 A stores M1",             ACE_UD, ACE_I,  32'hA0, 32'hA1, 1);
    observe("3 B ReadShared",            ACE_SD, ACE_SC, 32'hA0, 32'hA1, 1);
    observe("4 B CleanUnique, store M2", ACE_I,  ACE_UD, 32'hA1, 32'hA2, 1);
    observe("5 B WriteBack",             ACE_I,  ACE_I,  32'hA2, 32'hA2, 1);
    // Any port reading the line now must see M2, the newest value.
    if (m.read_ok(32'hA2)) pass_n++;
    else                   fail_n++;
    // Mutant of step 3: a ReadOnce snoop leaves A UniqueDirty while B takes SC.
    observe("M ReadOnce snoop",          ACE_UD, ACE_SC, 32'hA0, 32'hA1, 0);
    $display("PASS=%0d FAIL=%0d", pass_n, fail_n);
    $finish;
  end

endmodule
```

Each `observe()` call applies one whole step, so `ic_owes` stays 0 here; a real monitor sets it between a snoop response and the requester's RRESP or the memory write. Each call counts as a pass when the checker's verdict matches the expectation, so the rejected mutant also counts as a pass; the `read_ok()` call after step 5 checks a read of the newest value.

### Where it lives in a UVM environment

In a real testbench, each port monitor publishes one transaction per observed request or snoop, carrying the responses it saw: RRESP[3:2] for the master's own reads, CRRESP for snoops. The checker turns them into each cache's new state using the tables (Table C4-9 for RRESP, Table C5-8 for CRRESP). Where a table allows more than one end state, for example RRESP 00 to a ReadShared without a snoop filter (I, UC or SC, Table C4-9), the model keeps the expected state for the system's configured snoop-filter policy, or the set of legal states (see "Snoop filters change what is legal" in Push Further). The `` `uvm_analysis_imp_decl `` macro creates one imp class per suffix, so one component can receive from several ports (IEEE 1800.2-2020 Annex B.5.22). `ace_obs_item` stands for your monitor's transaction class, with fields such as `addr`, `op` (a string naming the transaction), `is_read`, `end_state` (the state the model expects after the observed response) and `data`. A real checker keeps one model per line address, for example in an associative array keyed by address.

```systemverilog
// snippet: placement of the line model in a UVM scoreboard (uvm-core 2020.3.1)

`uvm_analysis_imp_decl(_port1)

  uvm_analysis_imp_port1 #(ace_obs_item, coh_checker) port1_imp;  // CPU1 ACE port
  uvm_analysis_imp_port2 #(ace_obs_item, coh_checker) port2_imp;  // DMA ACE-Lite port
  coh_line_model #(.NCACHE(2)) lines[logic [63:0]];               // one model per line

  function new(string name, uvm_component parent);
    super.new(name, parent);
    port0_imp = new("port0_imp", this);
    port1_imp = new("port1_imp", this);
    port2_imp = new("port2_imp", this);
  endfunction

  function void write_port0(ace_obs_item t); update_cache(0, t); endfunction
  function void write_port1(ace_obs_item t); update_cache(1, t); endfunction

  // The DMA has no cache: only its read data is checked.
  function void write_port2(ace_obs_item t);
    if (t.is_read && lines.exists(t.addr) && !lines[t.addr].read_ok(t.data))
      `uvm_error("COH", $sformatf("DMA read of line 0x%0h returned stale data", t.addr))
  endfunction

  function void update_cache(int cache, ace_obs_item t);
    string why;
    if (!lines.exists(t.addr)) lines[t.addr] = new(t.data);
    lines[t.addr].st[cache] = t.end_state;
    if (!lines[t.addr].check_line(why))
      `uvm_error("COH", $sformatf("line 0x%0h after %s on cache %0d: %s",
                                  t.addr, t.op, cache, why))
  endfunction

```

The snippet leaves out the golden-value, memory and `ic_owes` updates to stay short. The golden value comes from the master side (the CPU stimulus or a cache model), because a store to a Unique line is silent on the port; memory writes come from the memory-side monitor.

### How to build a coherency checker

1. List every port that can access Shareable memory, including ACE-Lite and non-coherent masters that share buffers with coherent ones, plus the interconnect's memory port.
2. Put a passive monitor on each and publish every request, snoop, CRRESP, RRESP[3:2], RACK, WACK and data beat, with a time stamp.
3. Keep one line model per line address: the state (or the set of legal states) in every cache, the golden value, the memory value and the "interconnect owes memory" flag.
4. Update the model from each observation, using the requester's RRESP[3:2] (Table C4-9) and the snoopee's CRRESP (Table C5-8), and take the golden value from the master side.
5. After every update, check single writer, single owner and "memory is current when nobody, cache or interconnect, owes it"; check every read against the golden value. Add the liveness checks (one CR per snoop; a RACK or WACK for every response, within your bound) and, if the system has a snoop filter, check that every valid holder is in it.
6. Cover start state × snoop type × response: every row of the tables you rely on, both RRESP outcomes, PassDirty set and clear.
7. Log an ownership timeline per line so a failure points to the first illegal step.

## Push Further

### Expert: snoop channel dependencies

The snoop channels have their own handshake dependencies (IHI0022E §C3.9, Figure C3-1). The interconnect must not wait for ACREADY before asserting ACVALID. The master must see the AC handshake (ACVALID and ACREADY) before asserting CRVALID or CDVALID, but must **not** wait for CRREADY or CDREADY before asserting CRVALID, or CDVALID when data is required. The interconnect may wait for CRVALID and CDVALID before raising either READY. A snoop port that waits for CRREADY first is a deadlock waiting to happen; an assertion bound to the snoop interface catches it locally, a coherency rule that a per-port checker *can* own.

### Expert: RACK, WACK and the snoop window

RACK and WACK are single-cycle pulses that the interconnect must accept in that cycle, asserted no earlier than the cycle after the last R handshake (RLAST) or the B handshake, and never delayed to wait for another transaction (§C3.3, §C3.5, §C6.2.1). They exist because a register or clock-domain crossing may sit between the interconnect and the master: the interconnect cannot assume the master has *applied* a response until the acknowledge arrives, and it "must use write acknowledge to ensure that a transaction to a master's snoop port is not issued until any preceding transaction from that master to the same address has completed" (§C3.5). The interconnect must not send a master a snoop to a line after giving it a response for that line until the RACK or WACK arrives, and must not give a response for a line while its snoop to that master for the same line awaits CRRESP (§C6.2). In a testbench, a snoop to line X issued to master M between M's response for X and M's acknowledge is an interconnect bug worth an assertion.

### Expert: a snoop that crosses a WriteBack

A master may be writing a dirty line back (WriteBack or WriteClean) when a snoop for that line arrives. Only one component may update memory at a time, so the snooped master must either answer with PassDirty deasserted and IsShared asserted (it passes neither the permission to store nor the duty to update memory), or delay the response until its write-back completes (§C5.2.3). When the response would pass the permission to store, all its memory-update writes must complete before the cycle of the CR response. This race (snoop arriving during a write-back) is a top coverage item for any coherent master, and a scoreboard that applies the snoop before the WriteBack predicts the wrong memory value. Apply the WriteBack's state change first, then the snoop's (the rule stated with Table C5-4).

### Expert: forward progress

ACE prevents deadlock with non-blocking rules (§C5.2.5). A master must complete any snoop, to any address, before any of its own AR-channel transactions (and its WriteUnique or WriteLineUnique) can be guaranteed to complete. It may make a snoop wait for its own WriteNoSnoop, WriteBack, WriteClean, WriteEvict or Evict; and if the snoop response could lead to a memory write or give another master permission to store, it must first complete any WriteBack, WriteClean or WriteEvict in progress for that line. The interconnect has matching rules (§C6.6.1). CHI states the same idea per channel: an RN-F must answer snoops "without creating any Protocol layer dependency on completion of outstanding requests" (§4.11.1), must make progress on inbound SNP without needing progress on outbound REQ, and must always sink inbound RSP and DAT (§13.4.1). In stress tests, a hang whose last activity is a snoop stuck behind the master's own read is the classic violation.

### Expert: overlapping stores and the CleanUnique race

When two masters try to store to the same Shareable line at the same time, the interconnect picks an order (§C1.3.4, "Overlapping store operations"). The loser sees the winner's snoop first and loses its copy. If the loser had issued CleanUnique for a partial store, its CleanUnique then completes with *no copy*: it may perform only a full-line store, or it must issue a new transaction to fetch the data, or write the partial line to memory without caching it (§C1.3.4; §C4.6.1: "If the cache line was in the Invalid state before the store operation, then the store must be a full cache line size"). A master that performs a partial store into a line it no longer holds corrupts data. Exclusive sequences add one more rule: a snooped line that is part of an exclusive sequence must remain valid in the snooped master for the read-type snoops of Table C5-8 (§C5.3), and CleanUnique may be used for exclusive accesses (§C4.6.1, Chapter C9). See [B-AXI-4](/curriculum/T3_Advanced/B-AXI-4_AXI_Expert_Features_Cache_Atomics/index) for exclusives on plain AXI.

### Expert: snoop filters change what is legal

A **snoop filter** tracks which lines each master holds, so the interconnect can skip useless snoops. Support is optional, and a master must state in its data sheet whether it supports one (§C4.2). The legal end states differ: for example, after a ReadShared with RRESP 00 the expected state is UC, legal states are UC or SC with a snoop filter, and I, UC or SC without one, because without a filter a clean line may be dropped silently (§C4.3, Table C4-9). A checker must be configured for the system's snoop-filter policy, or it will either miss lost-Evict bugs or flag legal silent evictions. CHI permits but does not require a snoop filter or directory, and lets the interconnect send snoops spontaneously, for example a SnpUnique or SnpCleanInvalid as "a backward invalidation from a snoop filter or interconnect cache" when a filter entry is evicted (IHI0050E.b §4.4). Snoop-filter capacity and the back-invalidation traffic it causes are a classic performance-verification topic (tool-dependent: measured with your interconnect's performance counters).

### Expert: CHI Request Retry and Protocol Credits

L-Credits only guarantee that the next hop accepts a flit. A Completer (a Home or a Subordinate) may still lack resources to take a request, so CHI adds **Request Retry** (§2.11). The first attempt is sent with AllowRetry asserted. A Completer that cannot accept it answers **RetryAck** with a **PCrdType**, records the requester, and later sends **PCrdGrant** (a Protocol Credit) when resources free up. The requester resends with AllowRetry deasserted and the granted PCrdType, and that attempt "is guaranteed to be accepted". Because responses can be reordered, a PCrdGrant may arrive **before** its RetryAck; the requester must remember the credit until the RetryAck arrives (§2.11). Up to 16 credit types let a Completer manage different resources separately. Snoops are not part of this mechanism: the snoop flit has no AllowRetry field (§13.9.3, Table 13-8). Verification targets: credit-type matching, retry storms, fairness between requesters, and every credit granted eventually used or returned.

### Expert: line size, partial and empty lines

ACE line size is a design-time choice per master: at least the larger of 16 bytes and the data-bus width, at most the smaller of 2048 bytes and 16 beats of the bus (§C3.1.5, Table C3-10), and most coherent transactions must be exactly one line (§C3.1.6). A coherency model must therefore be parameterized by line size, and the interconnect must agree with every master on it. CHI fixes the line at 64 bytes, aligned (§1.5.1), and adds two partial states: **UCE** (Unique, no valid bytes; must not supply data on a snoop) and **UDP** (Unique, some bytes dirty; must be merged with memory on eviction and must not be forwarded directly to a requester) (§4.1). A CHI model that tracks only the five ACE states cannot predict that a UDP line is never forwarded by DCT.

### Expert: methodology trade-offs

These are methodology choices, not protocol rules (tool-dependent where noted):
- **Commercial coherency VIP or in-house line model.** VIP brings the full transaction tables and protocol checks; an in-house model, like the one above, is small enough to understand and extend for your system's snoop-filter policy and caches. One option is to use VIP for port compliance and an in-house global model for the system rules.
- **Formal on a small abstraction.** A small model (a few caches, one line and a nondeterministic interconnect) lets a formal tool prove single writer and single owner exhaustively *for that abstraction* (see [E-INT-1](/curriculum/T4_Expert/E-INT-1_Integrating_UVM_with_Formal_Verification/index)). Use at least three caches, so that a requester plus two sharers is reachable: a bug such as an interconnect that, on CleanUnique, snoops only one of two sharers needs three. Argue symmetry before you claim the result for N caches; simulation then covers scale and performance.
- **What the protocol does not cover.** ACE and CHI guarantee coherence per location. Memory-ordering litmus tests (for example, whether two writes to different addresses are seen in order) belong to the processor architecture and the barrier rules, and are usually run as software tests on the full system (see [E-SOC-1](/curriculum/T4_Expert/E-SOC-1_SoC-Level_Verification_Strategies/index)).

**Debug variant (run 1, step 3).** A buggy interconnect sends a **ReadOnce** snoop instead of ReadShared, and A answers IsShared=1. What state is each cache in, which rule is broken, and which line of the Make It Work checker reports it?

<details>
<summary>Answer</summary>

A ReadOnce snoop requires no state change, so A may stay **UD** (§C1.4.2, Table C5-2), while B is told IsShared=1 and takes **SC**. A Unique line is now in two caches, which breaks "A line in a Unique state must only be in one cache" (§C1.2.3); it is also an illegal snoop choice, because a ReadShared request may be snooped only as ReadClean, ReadNotSharedDirty, ReadShared, ReadUnique or CleanInvalid (Table C5-2). In the checker, `unique_n == 1 && valid_n > 1` is true, so `check_line()` returns "a Unique copy coexists with another copy". The symptom in a real system comes later: A stores again silently (it believes it is Unique) and B keeps reading its stale SC copy.

</details>

### Design exercise: take the checker to CHI

Adapt `coh_line_model` to a CHI system with two RN-Fs and one RN-I behind one HN-F. Write a short answer to each question before you open the solution.

1. Which links do you monitor?
2. Where does each node's new state come from?
3. Why must the read-data check not assume that the data comes from the Home?
4. What must the state enum and the rules add?

<details>
<summary>Worked answer</summary>

1. **Every Request Node's link** (both RN-Fs and the RN-I, with their REQ, RSP, SNP and DAT channels), plus the HN-F's link to the SN-F, so the model sees memory writes. The RN-I is never snooped, but its writes change the golden value and its reads must return it.
2. **From the response names.** The requester takes the state in the Resp field of its CompData (or of RespSepData and DataSepResp): CompData_SC means SC, and a `_PD` suffix means it now owes memory (§4.5.1). A snooped RN-F reports its state *after* the response: SnpResp_SC_Fwded_SC means it keeps SC and forwarded an SC copy (§4.5.3).
3. **Because of DCT.** The snooped RN-F may send CompData straight to the requester (§1.7, §5.1.3); when it answers the Home with SnpRespFwded, which carries no data, the Home never sees the line. Check read data where it arrives, on the requester's DAT channel, whichever node sent it.
4. **UCE and UDP** (§4.1). Both are Unique, so the single-writer rule counts them; UDP is Dirty, so the single-owner rule counts it. UCE holds no valid bytes and UDP only some, so the golden-value check needs a valid flag per byte. A UCE or UDP holder must never forward data directly to the requester, so a forwarded CompData from one is a bug.

</details>

### Debug challenge: the vanishing write

A test runs a buffer through three steps: CPU0 writes the buffer (its lines end UD), then the DMA driver issues **MakeInvalid** on the buffer through the DMA's ACE-Lite port "to make sure the DMA sees fresh data", and the DMA reads it with ReadOnce. The DMA gets the values from before CPU0's writes, and the Make It Work checker reports "no cache is Dirty but memory is stale". Is the interconnect broken? What should the test or the software do instead?

<details>
<summary>Answer</summary>

The interconnect is behaving legally. A MakeInvalid snoop removes the copy "but it is not required to provide any data, even if the cache line is dirty" (§C1.4.4), so CPU0's dirty data is discarded and memory keeps the old values. The checker is right to flag it: after the MakeInvalid no cache owes the update, yet memory differs from the golden value. The software bug is using an invalidate where a clean was needed: use **CleanInvalid** (dirty data is written back, then the copies are removed) or **CleanShared** (written back, copies kept), or simply let the DMA's ReadOnce be snooped. If a test really intends to discard data with MakeInvalid, it must update the golden value to say so.

</details>
