## Quick Take

- **What it is:** Three ways to make random choices without writing a class, and the rules that decide which random numbers you get. `std::randomize()` randomizes ordinary variables in the current scope, `randcase` takes one weighted random branch, and `randsequence` builds a random stream of steps from a grammar (IEEE 1800-2023 §18.12, §18.16, §18.17). Behind all of them, and behind every `obj.randomize()`, sit **random number generators (RNGs)**: one per process and one per object, seeded in a fixed order. That arrangement is called **random stability** (§18.14).
- **Why it matters:** A constrained-random test is only useful if a failure can be replayed. A **seed** is the number that starts the random streams; give the simulator the same seed and the same code, and every random value repeats. Change the code, even by adding one harmless-looking `new()`, and some streams shift. The failing scenario may simply vanish, so a seed that now passes proves nothing. Knowing exactly which edits shift which streams is what lets you debug a random failure instead of chasing it.
- **The Analogy:** Every process holds a roll of pre-printed raffle tickets, and the seed decides what is printed on the roll. Each time the process creates an object or a child process, or calls `$urandom`, `std::randomize()`, `randcase` or `randsequence`, it tears off the next ticket. A new object uses its ticket to print its own private roll. Tear off one extra ticket early, and everyone served after that gets a different ticket, although nothing else changed. *Where it breaks:* a real roll cannot be rewound, but `get_randstate()` and `set_randstate()` can save and restore a generator exactly; and the numbers on these rolls look random, not 1, 2, 3, so you can only predict *which* values change, never the values themselves.

**You will be able to:**
1. **Choose** between a class `randomize()`, `std::randomize()`, `randcase` and `randsequence` for a stimulus task, and **write** each one with its result checked.
2. **Predict** the probability of each `randcase` branch and each `randsequence` stream from the weights, including zero, default and expression weights.
3. **Predict** which objects' and processes' random values change after a code edit (an extra `new()`, an extra `$urandom`, an extra `randomize()` call, a different process order), using the random-stability rules of §18.14.
4. **Debug** an irreproducible failure: replay it from its seed, explain why a seed does not reproduce a run once the code changes, and protect a stream with `srandom()`, process seeding or `get_randstate()`/`set_randstate()`.

This page adds the tools that live *outside* a class, then explains where every random number comes from.

### Four tools for random choices

A **random variable** is a variable the solver assigns; a **state variable** is one whose current value the solver treats as a constant. A **constraint** is a Boolean rule the random variables must satisfy. With those words, the four tools compare like this:

| You need | Use | Why |
|---|---|---|
| A transaction with fields, rules, inheritance and switchable constraints | a class and `obj.randomize()` (I-SV-2A) | Constraint blocks have names, so tests can override them in a derived class or turn them off with `constraint_mode()` |
| A few local values with a rule or two, such as a loop count or a delay | `std::randomize(v1, v2) with { … }` | No class to write; the variables become random for this one call (§18.12) |
| One of N actions, with fixed or computed odds | `randcase` | A weighted `case` statement: one draw, one branch (§18.16) |
| A structured stream: setup, a body of mixed steps, cleanup | `randsequence` | A grammar that the generator expands at random (§18.17) |

Rule of thumb: if anyone will ever want to change the rules from a test, put them in a class. The procedural tools are for local, throwaway choices.

### `std::randomize()`: randomize variables in the current scope

**What it is.** The **scope randomize function** gives random values to the variables you name, using the constraints in an optional `with` block (§18.12, §18.12.1). The named variables are the random variables of this one call; every other variable in the block is a state variable. It returns 1 on success and 0 when no legal combination exists, and it "behaves exactly the same as a class randomize method" apart from working on scope variables (§18.12), so check its result exactly as you would for `obj.randomize()`.

**The three forms:**

| Form | Random variables | Effect |
|---|---|---|
| `std::randomize(a, b)` | `a`, `b` | Any values of their types |
| `std::randomize(a, b) with { a < b; }` | `a`, `b` | Values that satisfy the block; other names in the block are state |
| `std::randomize() with { a < b; }` | none | Changes nothing; returns 1 only if every expression in the block is true now (§18.12) |

The last form is a **checker**: it tests the current values against the rules instead of generating new ones.

```systemverilog
// compile
module tb_top;
  initial begin
    int unsigned len;      // unsigned on purpose: see the first pitfall below
    bit [7:0]    addr;
    for (int i = 0; i < 3; i++) begin
      // len and addr are the random variables of this call only (§18.12.1)
      if (!std::randomize(len, addr) with {
            len inside {[64:1500]};
            addr < 8'h20;
            addr[1:0] == 2'b00;      // word aligned
          })
        $fatal(1, "std::randomize() failed");
      $display("len=%0d addr=0x%h", len, addr);
    end
    // No arguments: change nothing, only check the current values
    addr = 8'h21;
    if (!std::randomize() with { addr < 8'h20; })
      $display("checker: addr=0x%h breaks addr < 0x20", addr);
  end
endmodule
```

**Expected output** (illustrative, not from a simulator run; the three generated lines change with the seed and the simulator, the checker line does not):

```text
len=917 addr=0x0c
len=1301 addr=0x18
len=75 addr=0x04
checker: addr=0x21 breaks addr < 0x20
```

**Pitfalls.**
- **`int` is signed.** `int count; std::randomize(count) with { count < 10; }` is legal, but every value from −2,147,483,648 to 9 satisfies it, so almost every result is negative (§6.11.3). Random variables keep the signedness of their type. Declare `int unsigned`, or write `count inside {[0:9]}`.
- **Inside a class, write `std::` explicitly.** In a class method, an unqualified `randomize(x)` names the object's own `randomize()` method, whose arguments must be properties of that object (§18.11). A local variable there is an error, and a property name is randomized as one of the object's own variables, under the object's constraints and its RNG, which is rarely what you meant.
- **An unchecked call hides failures.** Calling it as a statement discards the result, and a tool only has to warn about that (§13.4.1). Write `if (!std::randomize(...)) $fatal(...)`, never `assert(std::randomize(...))`: switching assertions off would also remove the call (§20.11).

**Debugging.** Like a failing `obj.randomize()`, a failing call leaves the variables unchanged (§18.6.3, §18.12), so the symptom is a value that "never moves" or a stale value from the previous iteration. Print the variables and the state variables the `with` block reads, then test each expression with the no-argument checker form.

**In a real testbench.** In a UVM testbench, stimulus comes from sequences, objects whose `body()` task generates sequence items ([I-UVM-3A](/curriculum/T2_Intermediate/I-UVM-3A_Fundamentals/index)). Inside `body()` you often need a local count or delay: `std::randomize(n_items) with { n_items inside {[1:20]}; }` is shorter than a class. Anything a test might want to override belongs in a sequence item or configuration class instead, because a `with` block has no name to switch off or replace.

### `randcase`: one weighted random branch

**What it is.** `randcase` is a `case` statement whose items are **weights** instead of match values (§18.16). Each execution draws one random number and takes exactly one branch. A branch's probability is its weight divided by the sum of all weights.

```systemverilog
// compile
module tb_top;
  int unsigned hits[3];
  int unsigned w_err;            // a knob: 0 switches the error branch off
  initial begin
    w_err = 0;
    repeat (8000) begin
      randcase
        3     : hits[0]++;       // read
        1     : hits[1]++;       // write
        w_err : hits[2]++;       // error injection
      endcase
    end
    $display("read=%0d write=%0d err=%0d", hits[0], hits[1], hits[2]);
  end
endmodule
```

**Expected output** (illustrative; the read and write counts vary with the seed, but `err` is always 0 because a zero weight is never taken):

```text
read=6012 write=1988 err=0
```

**Predict first.** Set `w_err = 4`. What fraction of the 8000 iterations goes to each branch? And what happens if all three weights are 0? Write your answers down, then open the trace.

**Variants (§18.16).** A weight may be any non-negative integral expression, evaluated each time the `randcase` executes, so a weight can follow a configuration knob or a counter. A zero weight disables its branch. When every weight is zero, no branch runs and the tool may only warn, so a test whose knobs are all zero silently does nothing.

**Pitfalls.**
- Weights are relative, not percentages: `3` and `1` mean 75 % and 25 %, not 3 % and 1 %.
- Narrow weight expressions are computed in their own width and treated as unsigned (§18.16); the expert section shows how an 8-bit sum can wrap.

**In a real testbench.** A virtual sequence (a sequence that coordinates other sequences, taught in [I-UVM-3B](/curriculum/T2_Intermediate/I-UVM-3B_Advanced_Sequencing_and_Layering/index)) can use `randcase` to pick which traffic sequence to start next, with weights taken from a configuration object, and checks the all-zero case before entering the loop.

### `randsequence`: a random stream from a grammar

**What it is.** A **grammar** is a set of rules that says how a stream may be built. `randsequence` uses one to *generate* a random but legal stream, the reverse of what a parser does (§18.17). The vocabulary:

- a **production** is a named rule, such as `main : setup execute cleanup ;`;
- a **production list** is a sequence of items generated in order;
- `|` separates alternative production lists, and the generator picks one at random;
- `:=` gives an alternative a **weight**; an alternative without one has weight 1 (§18.17.1);
- a **terminal** is a production defined only by a **code block** `{ … }` of statements; a **nonterminal** is defined in terms of other productions.

```systemverilog
// compile
module tb_top;
  int n_rd, n_wr;
  initial begin
    repeat (4) begin
      randsequence (main)
        main    : setup execute cleanup ;
        setup   : reset | init ;                // equal weights: 1 and 1
        execute : read := 3 | write := 7 ;      // weights 3 and 7
        reset   : { $write("RESET "); } ;
        init    : { $write("INIT ");  } ;
        read    : { $write("READ ");  n_rd++; } ;
        write   : { $write("WRITE "); n_wr++; } ;
        cleanup : { $display("CLEAN"); } ;
      endsequence
    end
    $display("reads=%0d writes=%0d", n_rd, n_wr);
  end
endmodule
```

**More forms.** Real generators need more than fixed choices. Each form below is in §18.17:

| Form | Example | Meaning |
|---|---|---|
| Dynamic weight | `load := (n_load < 2 ? 3 : 0)` | Weights are evaluated each time their production is selected, so they can change during the stream (§18.17.1) |
| `if`/`else` | `op : if (depth < 2) push else pop ;` | Pick a production from a condition, not at random (§18.17.2) |
| `case` | `dev : case (sel) 0 : net ; default : mem ; endcase ;` | Pick by value; first match wins, `default` optional (§18.17.3) |
| `repeat` | `body : repeat ($urandom_range(2, 6)) op ;` | Generate a production the number of times the expression gives (§18.17.4) |
| `rand join` | `top : rand join s1 s2 ;` | Interleave two streams at random, keeping each stream's own order (§18.17.5) |
| `break` | `{ if (full) break; }` | Stop the whole `randsequence` (§18.17.6) |
| `return` | `{ if (skip) return; }` | Abort only the current production; generation continues with the next one (§18.17.6) |
| Values | `bit [7:0] value : { return $urandom; } ;` | A production can take arguments and return a value to the rule that used it (§18.17.7) |

A scope is **automatic** when the variables declared in it are created fresh each time it is entered and disappear when it is left (automatic lifetime, §6.21). `randsequence` creates an automatic scope, and each code block is its own automatic scope, so a variable declared in a code block starts again every time (§18.17). Use variables declared outside the `randsequence` for counts that must survive. Besides `repeat`, a recursive production (one that names itself) makes a grammar loop (§18.17). A `repeat` production cannot be cut short except by `break`, which ends the entire `randsequence` (§18.17.4).

**Pitfalls.**
- `break` and `return` are easy to swap: `break` ends everything, `return` skips the rest of one production.
- A `break` inside a loop statement *within* a code block exits that loop, not the `randsequence` (§18.17.6).
- Weights belong to alternatives: a weight on a production with no `|` has no effect (§18.17.1).

**In a real testbench.** Grammars suit streams whose *shape* matters: instruction streams for a processor (see [E-RISCV-1](/curriculum/T4_Expert/E-RISCV-1_RISC_V_Verification_Methodology/index)), packet sequences with headers and trailers, or reset-configure-traffic-drain scripts in a test. Each terminal's code block usually creates and randomizes a sequence item or starts a sequence, so the grammar decides the order and the item's constraints decide the fields.

### `$urandom` and `$urandom_range`: plain random numbers

`$urandom` returns a 32-bit unsigned random number; `$urandom_range(maxval, minval)` returns an unsigned value between the two limits, inclusive, and swaps them if `maxval` is the smaller one (§18.13.1, §18.13.2). Both draw from the calling process's RNG and are **thread stable**, which the next section explains. `$urandom` also takes an optional seed: `$urandom(254)` first reinitializes the generator with 254, then returns a value (§18.13.1). Because that generator is the calling process's RNG (§18.14.1), the call reseeds the whole process: everything the process creates or draws afterwards follows the new seed, and no longer depends on what came before it. The Verilog-era `$random` returns a *signed* number (§20.14.1) and is not in the random-stability list of §18.14, so prefer `$urandom` in new code.

### Random stability: who draws from which generator

Some definitions first:
- A **process** is one independently running piece of procedural code: an `initial` or `always` block, or a branch started by `fork` ([F2C](/curriculum/T1_Foundational/F2C_Procedural_Code_and_Flow_Control/index)). Clause 18 often calls it a **thread**. `initial` and `always` blocks are **static processes**; branches started by `fork` at run time are **dynamic** threads.
- An **RNG** is a deterministic generator: from the same starting value it returns the same sequence every time (§18.13.1). Its starting value is its **seed**.
- **Random stability** means that the RNGs are localized to processes and objects, so the values one of them returns do not depend on the others (§18.14).
- A **time slot** is everything the simulator does at one simulation time ([F3B](/curriculum/T1_Foundational/F3B_Scheduling_Regions/index)). Within a time slot, the order in which ready processes run is not specified (§4.7).

The rules, all from §18.14.1 to §18.14.3:

1. **Every object has its own RNG.** `obj.randomize()` draws only from `obj`'s RNG. Calls on one object never change the values of another.
2. **Every process has its own RNG.** `$urandom`, `$urandom_range`, `std::randomize()`, `randcase`, `randsequence` and the array method `shuffle()` draw from the RNG of the process that calls them.
3. **Creation takes a draw (hierarchical seeding).** When a process executes `new`, the new object's RNG is seeded with the **next value** of that process's RNG. When a process starts a dynamic thread with `fork`, the new thread is seeded the same way.
4. **Static processes are seeded at the start.** Each module instance, interface instance, program instance and package has an **initialization RNG**, seeded with the **default seed**; it seeds that scope's static processes and objects created by static declaration initializers. The default seed is implementation-dependent, which is why simulators take a seed on the command line.
5. **Process order does not matter.** The values a process gets do not depend on the order in which the simulator runs processes that already exist (§18.14.2).

Rows 4 and 5 are the answer to "why can adding one random call change later values?": a process-level call (`$urandom`, `std::randomize()`, `randcase`, `randsequence`, `shuffle()`) uses up a draw that a later `new` or `fork` would have received. Row 6 is the exception: `obj.randomize()` uses the object's own RNG, so it changes only that object. Two more cases complete the picture:

- **A shared object.** If two processes call `randomize()` on one object, they take turns drawing from that object's single RNG, so each process's values depend on which one runs first. This is the most common place where process order matters.
- **A shallow copy.** `a2 = new a;` copies `a`'s RNG state along with its fields (§8.12), so `a2` repeats `a`'s next values until one of them is reseeded. [I-SV-2A](/curriculum/T2_Intermediate/I-SV-2A_Constrained_Randomization_Fundamentals/index) covers what else a copy carries.

The rule to carry: **anything that creates an object or a thread, or draws from the process RNG (`$urandom`, `$urandom_range`, `std::randomize()`, `randcase`, `randsequence`, `shuffle()`), before existing work in the same process shifts everything created after it in that process.** A new `$display` shifts nothing, because it draws nothing. The LRM's own advice is to add new objects, threads and random calls *after* the existing ones (§18.14.1).

### Manual seeding: `srandom()`, process seeds and saved states

Sometimes a stream must stay fixed whatever else changes. Four tools do that (§18.13.1, §18.13.3–§18.13.5, §18.15):

| Method | On | Effect |
|---|---|---|
| `srandom(seed)` | an object, or a `process` handle | Reseeds that RNG |
| `get_randstate()` | an object, or a `process` handle | Returns the RNG's current state as a string |
| `set_randstate(state)` | an object, or a `process` handle | Restores a state that `get_randstate()` returned |
| `$urandom(seed)` | the calling process | Reseeds the calling process's RNG, then returns a value. Everything that process creates or draws afterwards follows the new seed; anything it did earlier is unaffected (§18.13.1) |

A `process` handle comes from `process::self()`, which returns the process that calls it ([I-SV-5](/curriculum/T2_Intermediate/I-SV-5_Synchronization_and_IPC/index) covers the `process` class, §9.7).

**Seed an object inside its own `new()`.** The LRM recommends it: once an object exists, nothing guarantees that its creator can reseed it before another process uses it, so it is best that objects self-seed in `new` (§18.14.3, §18.15). Note what self-seeding does *not* do. The `new` call has already taken a draw from the creating process, so a newly inserted object still shifts everything created after it, seeded or not. Self-seeding protects the object's *own* stream; to protect the others, seed *them*, or insert new objects last.

**Save and replay a state.** This complete example rewinds one object:

```systemverilog
// compile
module tb_top;
  class pkt;
    rand bit [31:0] data;
  endclass

  initial begin
    pkt        p;
    string     saved;
    bit [31:0] first, again;
    p = new();
    saved = p.get_randstate();          // snapshot before the call
    if (!p.randomize()) $fatal(1, "randomize() failed");
    first = p.data;
    p.set_randstate(saved);             // rewind this object's RNG
    if (!p.randomize()) $fatal(1, "randomize() failed");
    again = p.data;
    if (first == again) $display("replay MATCH");
    else                $display("replay DIFF");
  end
endmodule
```

**Expected output** (illustrative, traced by hand from §18.13.4 and §18.13.5; it does not depend on the seed):

```text
replay MATCH
```

The state string's length and format are implementation-dependent, and passing a string from a different implementation to `set_randstate()` is undefined (§18.13.4, §18.13.5). Use it within one simulator, for example to replay one interesting transaction many times.

### Seeds on the command line and in the log

IEEE 1800-2023 does not define how a seed is passed to a simulator, and it has no standard call that returns the seed the simulator used. The default seed is simply "implementation-dependent" (§18.14.1). Every simulator therefore has its own option, for example (tool-dependent; check your simulator's manual):

| Simulator | Option (tool-dependent) |
|---|---|
| Synopsys VCS | `+ntb_random_seed=1234` |
| Siemens Questa | `-sv_seed 1234` |
| Cadence Xcelium | `-svseed 1234` |

Good practice:
1. Let the regression script choose the seed, pass it with the simulator's option, and write it into the log header. Many simulators also report the seed they used in their own log (tool-dependent).
2. Store the seed with every failure, together with the code version, the simulator version and every plusarg.
3. To replay, rerun that exact combination. A seed is a starting point for *one* build of the code, not a name for a scenario.

[E-DBG-1](/curriculum/T4_Expert/E-DBG-1_Advanced_UVM_Debug_Methodologies/index) builds the regression and triage workflow on top of these rules.

### Debugging: symptom, cause, fix

| Symptom | Likely cause | Fix |
|---|---|---|
| A failing seed passes after you add debug code | The new code creates an object or thread, or draws a random number, before existing work, so later streams shifted | Rerun the old seed on the *old* code to debug; add debug objects after existing ones; run many seeds on the new code |
| The same seed gives different results on two runs | Something outside the RNGs changed: code, simulator version, plusargs, or an outside source such as wall-clock time or a C `rand()` called through the C interface, DPI ([I-SV-7](/curriculum/T2_Intermediate/I-SV-7_DPI_and_Foreign_Language_Interfaces/index)) | Put every input of the run under version control; remove outside entropy |
| One object's values changed although its code did not | It was created after an inserted `new`, `fork` or `$urandom` in the same process | Move the insertion after it, or self-seed the objects whose streams must stay fixed |
| `std::randomize()` keeps giving huge negative numbers | The variable is a signed `int` | Use `int unsigned` or an `inside` range |
| A `randcase` sometimes runs no branch | Every weight evaluated to zero | Check the knobs before the `randcase`, and report the all-zero case |
| A value never changes between iterations | The call failed and was not checked, so the old value stayed | Check every `randomize()` result |
| A `randsequence` stream ends too early, or runs on past the point where it should stop | `break` and `return` are swapped: `break` ends the whole `randsequence`, `return` only the current production; or a `break` sits inside a loop statement in a code block, so it exits only that loop (§18.17.6) | Use `break` to end the stream and `return` to skip the rest of one production; keep `break` out of loops in code blocks |
| A `randsequence` alternative never appears, or a weight seems to do nothing | A dynamic weight evaluates to 0 every time it is selected, or the weight is written on a production that has no alternatives (no vertical bar), where a weight has no meaning (§18.17.1) | Print the weight expressions when the production is selected; put the competing alternatives in one rule, separated by vertical bars |

### In a real testbench

- **Stimulus objects** (sequence items, transactions) use class constraints, so tests can layer and override them. The procedural tools fill the gaps: a count, a delay, a choice of sequence.
- **Seeds** come from the regression system and appear in every log header. Never seed from the time of day in a regression: the run could not be replayed.
- **UVM** reseeds its components and sequence items from their names (expert section below), which makes UVM benches much less sensitive to creation order than a plain class-based bench, but not immune.

### Recap

- `std::randomize()` randomizes named scope variables for one call; with no arguments it is a checker. Check the result, and remember `int` is signed.
- `randcase` takes one branch with probability weight/sum; a zero weight is never taken, and all-zero weights take no branch.
- `randsequence` expands a grammar; multiply the probabilities along a path. Weights are evaluated when their production is selected.
- Objects and processes each have an RNG. Creating an object or thread takes the next draw from the creating process. Adding work *early* shifts everything after it; adding it *last* shifts nothing.
- A seed reproduces a run only for the same code, simulator and arguments.

## Make It Work

### Worked example: prove which edits shift a seed

This bench turns the before/after table into a self-checking test. Instead of editing the code and rerunning the simulator five times, the task `run` replays one "test" from the same process seed with at most one edit switched on, and compares each object's first three values with the original version. The prediction function holds the answers from the table. The bench prints MATCH or DIFF, never the values themselves, so its output does not depend on the simulator.

```systemverilog
// compile
// Which code edits change which objects' random values? (IEEE 1800-2023 §18.14)
module tb_top;

  class pkt;
    rand bit [31:0] data;
    // seed == 0: keep the seed the creating process handed out.
    // seed != 0: self-seed, so this object's stream ignores creation order.
    function new(int unsigned seed = 0);
      if (seed != 0) this.srandom(seed);
    endfunction
  endclass

  typedef enum {BASELINE, REPLAY, EARLY_NEW, LATE_NEW, EXTRA_URANDOM,
                EXTRA_RANDOMIZE} edit_e;
  typedef bit [31:0] trace_t [3][3];   // [object: 0=a, 1=s, 2=b][draw 0..2]

  // One version of the "test": the same process seed, plus at most one edit.
  task automatic run(input edit_e edit, output trace_t t);
    process      p;
    pkt          a, s, b, x;
    int unsigned junk;
    p = process::self();
    p.srandom(1234);                     // plays the role of the command-line seed
    if (edit == EARLY_NEW) x = new();    // extra object BEFORE a
    a = new();                           // seed = next value of this process's RNG
    if (edit == EXTRA_URANDOM) junk = $urandom;  // one extra draw
    s = new(42);                         // takes a draw too, then self-seeds
    b = new();
    if (edit == LATE_NEW) x = new();     // extra object AFTER the others
    if (edit == EXTRA_RANDOMIZE) begin   // one extra call, on a only
      if (!a.randomize()) $fatal(1, "a.randomize() failed");
    end
    for (int i = 0; i < 3; i++) begin
      if (!a.randomize()) $fatal(1, "a.randomize() failed");
      if (!s.randomize()) $fatal(1, "s.randomize() failed");
      if (!b.randomize()) $fatal(1, "b.randomize() failed");
      t[0][i] = a.data;
      t[1][i] = s.data;
      t[2][i] = b.data;
    end
  endtask

  // 1 when object obj produced the same three values in both traces
  function automatic bit same(trace_t x, trace_t y, int obj);
    for (int i = 0; i < 3; i++)
      if (x[obj][i] != y[obj][i]) return 0;
    return 1;
  endfunction

  function automatic string tag(bit m);
    if (m) return "MATCH";
    return "DIFF";
  endfunction

  // The prediction from the random-stability rules, as {a, s, b}: 1 = MATCH
  function automatic bit [2:0] predicted(edit_e e);
    case (e)
      EARLY_NEW:       return 3'b010;
      EXTRA_URANDOM:   return 3'b110;
      EXTRA_RANDOMIZE: return 3'b011;
      default:         return 3'b111;    // REPLAY and LATE_NEW
    endcase
  endfunction

  initial begin
    trace_t   base, cur;
    edit_e    edits[5];
    bit [2:0] got;
    int       pass, fail;
    edits = '{REPLAY, EARLY_NEW, LATE_NEW, EXTRA_URANDOM, EXTRA_RANDOMIZE};
    run(BASELINE, base);
    foreach (edits[k]) begin
      run(edits[k], cur);
      got = {same(cur, base, 0), same(cur, base, 1), same(cur, base, 2)};
      $display("%s: a=%s s=%s b=%s", edits[k].name(), tag(got[2]), tag(got[1]),
               tag(got[0]));
      if (got == predicted(edits[k])) pass++;
      else begin
        fail++;
        $error("%s: pattern differs from the prediction", edits[k].name());
      end
    end
    $display("PASS=%0d FAIL=%0d", pass, fail);
  end

endmodule
```

**Expected output** (illustrative: traced by hand from §18.14.1–§18.14.3 and §18.15, not captured from a simulator run):

```text
REPLAY: a=MATCH s=MATCH b=MATCH
EARLY_NEW: a=DIFF s=MATCH b=DIFF
LATE_NEW: a=MATCH s=MATCH b=MATCH
EXTRA_URANDOM: a=MATCH s=MATCH b=DIFF
EXTRA_RANDOMIZE: a=DIFF s=MATCH b=MATCH
PASS=5 FAIL=0
```

Why this output is reliable on any simulator:
- Every MATCH follows from the standard: same seed, same order of draws, same values.
- A DIFF compares three 32-bit values from a differently seeded generator. A chance coincidence of all three has a probability of about 2⁻⁹⁶, so in practice DIFF is certain.
- `s` reseeds itself in `new()`, so it matches in every row, even in EARLY_NEW and EXTRA_URANDOM, where its own `new()` received a different draw.

**Run it.** Save the code as `tb_top.sv`, compile it with SystemVerilog enabled on any simulator that supports classes and the `process` class (for example on EDA Playground), and simulate `tb_top`. Run it with two different seeds: the output must not change. No open-source simulator has been checked with this example yet.

### How to keep a failing seed reproducible

1. **Record everything** with each failure: seed, code version, simulator and version, command line and plusargs.
2. **Replay before you edit.** Rerun the failing seed on the unchanged code and confirm the failure first.
3. **Debug with code that draws nothing,** such as `$display` calls and waveform dumps, or add new objects and threads *after* the existing ones.
4. **If you must restructure,** expect the seed to stop reproducing the failure. Find the scenario again (from the log, coverage or a directed test) instead of trusting the old seed.
5. **Fix, then rerun the old seed on the new code and many new seeds.** A passing old seed alone proves nothing, because its streams may have shifted away from the bug.
6. **Protect streams that must stay fixed** by seeding them in their constructors or from a known process seed.

**Checklist before moving on:**

- [ ] Every `std::randomize()` and `randomize()` result is checked with `if (!…)`, never `assert`.
- [ ] Random scope variables have the signedness and range you mean (`int unsigned` or `inside`).
- [ ] Every `randcase` has at least one weight that can be nonzero, or the all-zero case is reported.
- [ ] You can name which objects' values change for each edit in the before/after table, and why.
- [ ] New debug objects and threads are created after the existing ones, and the seed appears in the log header.

## Push Further

### Expert: UVM seeding in uvm-core 2020.3.1

UVM benches add their own reseeding on top of §18.14. The facts below are from the uvm-core 2020.3.1 reference implementation (uvm-core impl.; the IEEE 1800.2 clauses for the exact hashing are unverified):

- `uvm_object::reseed()` calls `srandom(uvm_create_random_seed(get_type_name(), get_full_name()))` when UVM seeding is on, which is the default (`uvm_object.svh`, `use_uvm_seeding = 1`).
- `uvm_component::new` calls `reseed()` once the component's name is set (`uvm_component.svh`).
- Each component's task-phase process, such as the one running `run_phase`, is reseeded with `uvm_create_random_seed(phase.get_type_name(), comp.get_full_name())` (`uvm_task_phase.svh`).
- Sequences and sequence items call `reseed()` in `set_item_context`, which `start`, `create_item` and `start_item` call (`uvm_sequence_item.svh`, `uvm_sequence_base.svh`).
- `uvm_create_random_seed` hashes the type name and the full name with `uvm_global_random_seed`, and adds a counter per name pair (`uvm_misc.svh`). `uvm_global_random_seed` is initialized with `$urandom` in the package, so it still follows the simulator seed.

Consequences: adding a component does not shift other components' run-phase streams; renaming a component or a sequence changes its own seed and the seeds of its items, because an item's full name includes the sequence path; a second item with the same type and full name advances the counter. A plain `new` of a non-UVM object, or of a `uvm_object` that is never started as an item, still uses the §18.14 rules: it shifts only objects created after it in the same process.

### Expert: seeds across simulators, versions and saved states

- The default seed is implementation-dependent (§18.14.1), and the LRM specifies no generator algorithm, only that the generator is deterministic (§18.13.1). The same seed therefore gives different values on different simulators: a seed is not portable.
- The `get_randstate()` string has an implementation-dependent format, and `set_randstate()` with a string from another implementation is undefined (§18.13.4, §18.13.5).
- A new simulator version may change how the solver picks among legal solutions (tool-dependent). Keep the simulator version with the seed, and expect a version upgrade to invalidate stored seeds.
- Static processes and static initializers are seeded from each scope's initialization RNG (§18.14.1). Exactly how a simulator derives distinct seeds for many instances of one module from the command-line seed is tool-dependent.

### Expert: weight arithmetic in `randcase` and `randsequence`

- **`randcase` widths (§18.16).** Each weight expression has its self-determined width, the sum is computed at the largest weight width, and each summand is treated as unsigned. With `bit [7:0] a, b;`, the weight `a + b` is computed in 8 bits, so `a = 200, b = 100` gives a weight of 44, not 300. A signed `byte` holding −1 does not act as zero: as an unsigned 8-bit summand it weighs 255. Cast weights to a wider type (`int'(a) + int'(b)`, or `32'(a) + 32'(b)`) when they come from narrow variables; each summand is still treated as unsigned.
- **Evaluation order (§18.16).** Each weight expression is evaluated at most once per execution, in an unspecified order, so weight expressions with side effects (a function that increments a counter) are a portability bug. A sum of weights wider than 32 bits may need several `$urandom_range()` draws.
- **`randsequence` weights (§18.17.1).** They are evaluated each time their production is selected, which makes self-adjusting grammars possible (the kata below uses it). A `repeat` production cannot be cut short; only `break` stops it, and `break` ends the whole `randsequence` (§18.17.4).

### Expert: grammars versus class constraints at scale

A `randsequence` and a constrained class answer different questions, and large instruction or packet generators usually combine them.
- **A grammar decides one choice at a time.** Each alternative is picked when its production is selected, from weights evaluated at that moment (§18.17.1); nothing looks ahead. A rule that spans several steps (no `LOAD` straight after a `STORE` to the same address) must be built from state variables read by weights and `if` productions (§18.17.2). A constraint over an array of items is solved for all items together (§18.5).
- **A grammar is a statement, not a class member.** A test cannot switch one production off by name the way it can call `constraint_mode()` on a named constraint block (§18.9) or override a constraint in a derived class (§18.5.2). To make a grammar configurable, drive its weights and conditions from configuration variables, or put the `randsequence` in a virtual method that a derived class can override.
- **A common split** (design practice, not a rule): the grammar fixes the *shape* of the stream (setup, body, drain; how many of each kind), and each terminal creates and randomizes an item whose class constraints fix the *fields*. Coverage then shows whether the weights reach the corners you need.

### Expert: shared objects and self-seeding

- Two processes calling `randomize()` on one shared object take turns drawing from that object's single RNG. Their values then depend on the order the scheduler runs them, which can differ between simulators (§4.7). Give each process its own object, or protect the shared one so that only one process randomizes it.
- After `new` returns, "there is no guarantee that the creating thread can change the object's random state before another thread accesses the object" (§18.14.3). That is why the LRM recommends seeding inside `new()`.
- Seeding one subtree's root process with `process::self().srandom(s)` fixes every object and thread it creates, whatever happens elsewhere, as long as the subtree itself is unchanged (§18.14.1 "manual seeding", §18.14.2 "hierarchical seeding").

### Kata 1 (predict): the seed drill

Process T0 (an `initial` block) runs this code, and nothing else in the simulation creates objects or draws random numbers. `C`'s branch is a dynamic thread, T1.

```systemverilog
// snippet
A = new();
fork
  begin                                 // T1, seeded when the fork runs
    C = new();
    repeat (3) if (!C.randomize()) $fatal(1, "C failed");
  end
join_none
B = new();
repeat (3) begin
  if (!A.randomize()) $fatal(1, "A failed");
  if (!B.randomize()) $fatal(1, "B failed");
end
```

For each edit, made on its own with the same seed, write down which of A, B and C produce different values. Then open the solution.

1. Insert `X = new();` before `A = new();`.
2. Insert `X = new();` after `B = new();`.
3. Insert `junk = $urandom;` between `join_none` and `B = new();`.
4. Add one extra `A.randomize()` before the loop.
5. Insert `#0;` before the `repeat (3)` loop, so that T1 may now run before T0's calls.
6. Make T1 also call `A.randomize()` in its loop. Then combine it with edit 5: what changes now?
7. Add `B.srandom(42);` right after `B = new();`. Then combine it with edit 1: which objects change now?

T0's RNG hands out draw 1 to A, draw 2 to the new thread T1, and draw 3 to B. C is created inside T1, so its seed comes from T1's RNG. In the original code T0 never blocks, so T0 finishes its whole loop before T1 runs.

### Kata 2 (write): an instruction-stream grammar

Write a `randsequence` that prints a stream of 4 to 8 instructions. Each instruction is `ALU` (weight 6), `LOAD` (weight 3) or `BRANCH` (weight 1). After two loads, `LOAD` must become impossible for the rest of the stream, and a `BRANCH` ends the stream at once. At the end, print how many instructions and loads were generated. Generate three streams.

Before you write it, answer two questions: how can the `LOAD` weight change in the middle of a stream, and should `BRANCH` use `break` or `return`?

<details className="my-4 rounded-xl border border-border/70 p-3">
<summary className="cursor-pointer font-semibold">Show the worked solution</summary>

The weight of `load` is an expression, and weights are evaluated each time their production is selected (§18.17.1), so it drops to 0 after the second load. `BRANCH` uses `break`, which ends the whole `randsequence`, including the remaining `repeat` iterations (§18.17.4, §18.17.6); `return` would only end the `branch` production and the stream would continue. The `randsequence` sits in its own task, so no loop statement encloses the code block that contains `break`.

```systemverilog
// compile
module tb_top;
  int n_load, n_instr;

  task automatic gen_stream();
    n_load  = 0;
    n_instr = 0;
    randsequence (stream)
      stream : repeat ($urandom_range(4, 8)) instr ;
      instr  : alu    := 6
             | load   := (n_load < 2 ? 3 : 0)   // re-evaluated at each selection
             | branch := 1 ;
      alu    : { $write("ALU ");    n_instr++; } ;
      load   : { $write("LOAD ");   n_instr++; n_load++; } ;
      branch : { $write("BRANCH "); n_instr++; break; } ;  // ends the stream
    endsequence
    $display("| %0d instructions, %0d loads", n_instr, n_load);
  endtask

  initial begin
    repeat (3) gen_stream();
  end
endmodule
```

**Expected output** (illustrative, one possible run; the streams change with the seed, but no line has more than two loads or more than eight instructions, and `BRANCH` is always last when it appears):

```text
ALU LOAD ALU BRANCH | 4 instructions, 1 loads
ALU ALU LOAD ALU LOAD ALU ALU | 7 instructions, 2 loads
LOAD ALU ALU ALU ALU | 5 instructions, 1 loads
```
