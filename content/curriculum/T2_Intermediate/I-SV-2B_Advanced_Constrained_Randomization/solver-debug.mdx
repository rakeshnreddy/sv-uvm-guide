## Quick Take

- **What it is:** A systematic way to find out why a `randomize()` call failed, or why it "worked" but never produced the values you needed. You confirm the failure, shrink the active constraints to the smallest set that still conflicts, check the usual non-obvious causes (signed and narrow arithmetic, inherited constraints, the solve orders the standard imposes), and then let the specification decide which rule is wrong (IEEE 1800-2023 §18.3, §18.6.3).
- **Why it matters:** A failed `randomize()` returns 0 and leaves the object holding its old values. Nothing stops the test unless your code checks the result, so a broken constraint can quietly send the same transaction thousands of times while the regression stays green. The opposite bug is just as quiet: a contradiction that makes one mode impossible never fails at all, it simply never generates that mode.
- **The Analogy:** Four colleagues try to book a meeting, and their calendars together leave no free slot. Removing any one person's calendar frees a slot, but that does not make that person the problem: everyone in the clash is a suspect, and the team's priorities decide who moves. *Where it breaks:* a calendar clash is the same every week, while a constraint set can fail on only some calls when the standard makes the solver pick some values first. And with constraints, the "priorities" are the written specification, not a negotiation.

**You will be able to:**
1. **Predict** what a failed `randomize()` returns and leaves in the object, and **decide** whether a value that never appears is a solver failure or a silent coverage hole.
2. **Debug** a failing `randomize()` by isolating a minimal conflicting set with `constraint_mode()`, `rand_mode()` and `randomize(null)`, and use the specification to decide which member is wrong.
3. **Diagnose** failures that are not plain contradictions: signed or narrow arithmetic, inherited or overridden constraints, and the implicit solve orders that make a call fail on only some calls.
4. **Write** randomization calls whose failures cannot pass silently, in plain SystemVerilog and in UVM sequences, and **explain** when a recorded seed still reproduces a failure after the code changed.

### Words you need on this page

You met most of these in [I-SV-2A](/curriculum/T2_Intermediate/I-SV-2A_Constrained_Randomization_Fundamentals/index) and the earlier pages of this module. One sentence each:

- A **random variable** is a class property declared `rand` or `randc`; `randomize()` gives it a new value.
- A **state variable** is any other variable a constraint reads. The solver treats its current value as a constant (§18.5.8).
- A **constraint block** is a named group of rules in a class, `constraint c_len { … }`. An **inline constraint** is the unnamed block after `randomize() with`.
- A constraint is **active** when the solver must honour it: its block is switched on with `constraint_mode()` (§18.9), or it is part of the current call's inline `with`.
- The **constraint solver** is the part of the simulator that picks values. IEEE 1800-2023 defines which results are legal, not the algorithm, so solvers differ between tools.
- A **legal combination** (a solution) is one set of values for all active random variables that makes every active constraint true. If there is none, the constraints are **infeasible**, or **over-constrained**.
- A **minimal conflicting set** is a group of active constraints that cannot all hold, where removing *any one* member leaves a set that can.
- A **coverage hole** is a value or scenario your stimulus never produces. **Functional coverage** is the measurement that finds holes; [I-SV-3A](/curriculum/T2_Intermediate/I-SV-3A_Functional_Coverage_Fundamentals/index), the next module, teaches it.
- A **seed** is the starting value of the simulator's random number generators (RNGs). The same seed with the same code repeats the same run.

### What a failed randomize() does

The standard's starting rule is strong: "If a solution exists, the constraint solver shall find it" (§18.3). A failure therefore means, in the normal case, that no legal combination exists for the active constraints of that call. When that happens (§18.6.2, §18.6.3):

- `randomize()` returns **0**;
- every random variable **keeps its previous value**; nothing is reset, zeroed or set to X;
- `pre_randomize()` has **already run**, because `randomize()` calls it before solving;
- `post_randomize()` is **not called**.

Here is that rule traced on the frame class from Make It Work, right after `new()`. The test asks for a `LONG` frame, which the class cannot produce:

| | `kind` | `len` | `payload.size()` | `pre_calls` | `post_calls` | return value |
|---|---|---|---|---|---|---|
| after `f = new();` | `SHORT` (enum default, value 0) | 0 | 0 | 0 | 0 | |

**The mistake everyone makes first** is not checking the return value. Only a checked call is safe:

```systemverilog
// snippet: plain SystemVerilog; a UVM version follows under "Failures you never see"
if (!f.randomize() with { kind == LONG; })
  $fatal(1, "RAND: frame randomize() failed for kind=LONG");
```

Three common forms hide the failure: `void'(f.randomize());` throws the result away on purpose; a bare `f.randomize();` statement does the same and only earns a compiler warning (§13.4.1); and `assert (f.randomize());` disappears completely when assertions are switched off (see [Failures you never see](#failures-you-never-see)).

### A failure or a coverage hole?

A contradiction does not always make `randomize()` fail. If the contradiction only rules out *some* values, the solver simply never picks them. The call succeeds every time, and the missing values form a coverage hole with no error message anywhere.

3. Now switch on `randomize() with { proto == IPV6; }`. What happens, and which constraints does the explorer list?

**Debrief.**

1. It never fails, and `proto` is **never** IPV6. IPV6 needs length 40, and 40 is not in the hardware list, so no legal pair contains IPV6. The solver picks among the pairs that remain.
2. 1/6. IPV4 owns one legal pair (length 32: the only listed length from 20 to 60); RAW owns five (any listed length). Every legal pair is equally likely (§18.5.9).
3. Every call fails. The inline constraint makes IPV6 mandatory, so the explorer lists a minimal conflicting set of three members: the inline `proto == IPV6`, the IPV6 length rule and the hardware list.

The explorer's feedback says the solver "never picks a value and then gives up". That is true *here*, where every constraint is solved together. It is not true everywhere: [When a solution exists but randomize() still fails](#when-a-solution-exists-but-randomize-still-fails) shows three cases where the standard makes the solver pick some values first.

Two lessons carry over to every testbench. First, forcing a value with an inline constraint is the fastest way to turn a hole into a failure you can debug. Second, the model has three members because its length rule mentions `length` directly. The lab packet at the end of this page routes the length through a payload, `payload.size() == length`, so its minimal set has **four** members.

### Finding the minimal conflicting set

When a call fails on every attempt, find the smallest set of active constraints that still conflicts. Every member of that set is a suspect. The solver cannot tell you which one is wrong; only the specification can.

Why insist on the *minimal* set? Because the obvious bisection misleads. If you switch blocks off one at a time until the call succeeds, the last block you switched off is **a** member of a conflict, not necessarily **the** wrong rule. Its partners are still in the class, and a second, independent conflict may still remain.

| Tool | What it does | Use it to | Watch out for |
|---|---|---|---|
| The simulator's failure report | Many simulators print the constraints, and often the variable values, involved in a failure | Get a first candidate set in seconds | The format, detail and options are tool-dependent; the standard requires no report |
| `obj.c_name.constraint_mode(0)` | The solver ignores that block on later calls (§18.9) | Remove one block at a time and see whether the call now succeeds | It works only on **named blocks**: an inline `with` constraint stays active until you edit the call |
| `obj.var.rand_mode(0)` | `var` becomes a state variable, so its **current value** is a constant (§18.8) | Pin a variable to a value the spec says is legal and see whether the rest can be solved | A frozen value can create a *new* conflict; freeze only at a value you have checked |
| `obj.randomize(null)` | Randomizes nothing and returns 1 only if every active constraint holds for the current values (§18.11.1) | Load values the spec calls legal and ask which block rejects them | Switch blocks on one at a time to name the guilty one |

Two more facts shorten the search:

- **Soft constraints never belong to a minimal conflicting set.** The solver discards a soft constraint that conflicts, and a call whose only conflicts involve soft constraints can never fail (§18.5.13, §18.5.13.1). Look only at hard constraints.
- **`randomize(v, w)` narrows the problem.** With arguments, only the named properties are random for that call and every other property is a state variable (§18.11). That lets you randomize one part of the object while the rest stays at values you trust.

The worked example in Make It Work applies the second and fourth tools to a frame class whose spec says LONG frames carry at least 9 bytes. Its results are the picture of this method.

3. Now switch on `y.rand_mode(0) with y = 4` and switch all blocks back on. **Predict** again: which blocks now conflict?

<ConstraintSolverHeatmapVisualizer initialScenario="debug" scenarios={["debug"]} />

**Debrief.**

1. It fails. `c_x` (`x > 3`) and `c_y` (`y > 2`) force `x + y` to be at least 7, and `c_sum` demands less than 6.
2. Switching off `c_sum`, `c_x` or `c_y` each makes the call succeed; switching off `c_odd` does not. The minimal conflicting set is `c_sum`, `c_x` and `c_y`. `c_odd` (`y % 2 == 1`) is innocent: odd values of `y` exist that fit everything else.
3. Now there are **two** separate conflicts. `y` is a state variable holding 4, so `c_odd` is simply false: a one-member conflict that did not exist before. And `c_sum` with `c_x` still conflicts (`x + 4 < 6` needs `x < 2`). Freezing a variable is a sharp tool: it turns an innocent block into a failing one if the frozen value is wrong. The visual names one minimal set at a time; when you fix one, look again.

### Signedness, width and 4-state traps

Some failures, and many "impossible" values that do appear, come from the expression rules of IEEE 1800-2023 Clause 11, which apply inside constraints unchanged.

**Signedness.** A random variable takes the signedness of its declared type: `byte`, `shortint`, `int`, `integer` and `longint` are **signed**; `bit` and `logic` vectors are **unsigned** (§6.11.3). The myth "random variables are unsigned" causes the classic bug:

Almost every legal value is negative: only 10 of about 2.1 billion are 0 to 9, and each legal value is equally likely (§18.5.9). Write `delay inside {[0:9]}`, or declare `rand int unsigned delay;` and bound it.

The opposite surprise comes from mixing. If any operand of an expression is unsigned, the expression is evaluated as unsigned (§11.8.1). So with `bit [31:0] max_delay = 10;` the constraint `delay < max_delay` compares unsigned values: a negative `delay` looks like a huge number and is excluded. The class works by accident, and it breaks the day someone changes `max_delay` to `int`.

**Predict before you click.** In the visual below, `i` is an `int` holding −1 and `w` is a `logic [31:0]` holding 1. Is `i < w` true or false? Then try the two fixes.

**Debrief.** `i < w` is **false**: `w` is unsigned, so the comparison is unsigned and −1 becomes 4,294,967,295. Inside a constraint the solver obeys exactly the same rule; it does not "know what you meant". The casts `$signed(w)` and `int'(w)` make the comparison signed again.

**Width.** Operands are sized by the expression rules of §11.6.1 before the solver sees them. In the standard's own example `class SimpleSum; rand bit [7:0] x, y, z; constraint c { z == x + y; }` (§18.6.1), every operand is 8 bits, so the sum wraps.

**Predict before you open the table.** Take `x = 200` and `y = 100`, all `bit [7:0]`. Which of `z == x + y`, `x + y < 300` and `x + y < 8'd44` accept this pair? Decide the width of each expression first.

The same applies to array reductions: `arr.sum()` has the element type unless you write `arr.sum() with (int'(item))` (§18.5.7.2). [Conditional and array constraints](/curriculum/T2_Intermediate/I-SV-2B_Advanced_Constrained_Randomization/advanced-constraints) covers reductions in depth.

**4-state values.** Constraints support only 2-state values: an `x` or `z` value, or a 4-state operator such as `===`, "shall result in an error" (§18.3). A `logic` configuration knob that nobody assigned still holds X, and a constraint that reads it fails with an error rather than a normal failure. Initialize knobs, or declare them as 2-state `bit`.

### Inherited and overridden constraints

A class inherits every constraint of its base class, and `randomize()` is virtual, so it uses the constraints of the **object**, whatever the type of the handle you call it through (§18.5.2). Two naming rules decide what is active:

- a derived-class constraint with the **same name** as a base-class constraint **replaces** it;
- a derived-class constraint with a **new name** is **added** to the inherited ones.

The standard warns about the consequence: "addition of constraints in derived classes can render seemingly simple constraints unsatisfiable" (§18.6.1). The classic version:

```systemverilog
// snippet
class pkt_item;
  rand bit [7:0] len;
  constraint c_len { len inside {[1:16]}; }
endclass

class jumbo_item extends pkt_item;
  constraint c_jumbo { len > 64; }             // new name: ADDED to c_len, never solvable
endclass

class jumbo_fixed extends pkt_item;
  constraint c_len { len inside {[65:255]}; }  // same name: REPLACES pkt_item::c_len
endclass
```

| A base-class handle produces "impossible" values | The object is a derived class (a UVM factory override, for example) whose constraints replace the base ones | Print the object's class, not the handle's; constraints follow the object |
| A soft default from the base class is ignored | A derived-class or inline soft constraint outranks it (§18.5.13.1) | Expected behaviour: later layers win; make the base rule hard if it must always hold |

[Controlling randomization](/curriculum/T2_Intermediate/I-SV-2B_Advanced_Constrained_Randomization/controlling-randomization) teaches overriding as a design tool; here it is a suspect to check.

### When a solution exists but randomize() still fails

The rule "if a solution exists, the solver shall find it" (§18.3) holds when all the constraints are solved together. Three rules of the standard split the solve into stages instead. A value chosen in an early stage becomes a constant for the later stages, and if that value leaves no solution, the call fails **although a legal combination exists**. The symptom is distinctive: the same call fails on a steady fraction of attempts, on every seed, with nothing changing between calls.

1. **Function calls in constraints.** Random variables used as function arguments are solved first, and the function's return value becomes a state variable. The standard says this "subdivides the solution space" and "can cause the overall constraints to fail" (§18.5.11).
2. **Array sizes before `foreach`.** If an array has both size constraints and `foreach` constraints, the sizes are solved first and the size acts as a state variable inside `foreach`. "This implicit ordering can cause the solver to fail in some situations" (§18.5.7.1).
3. **`randc` variables first.** Constraints that mix `rand` and `randc` variables are solved with the `randc` variables first, "and this can sometimes cause randomize() to fail" (§18.4.2).

Contrast two features that look similar but are safe: `solve a before b` "does not change the solution space and, therefore, cannot cause the solver to fail" (§18.5.9), and nonzero `dist` weights "cannot cause the solver to fail" either (§18.5.3).

The same contrast as a table. When you triage, read the last column first: only the first three rows can make a class that has a solution fail on a steady fraction of calls.

| Construct | Imposes an order? | Can it make `randomize()` fail? | Symptom in a regression |
|---|---|---|---|
| Random variable used as a function argument | **Yes**: the arguments are solved first, and the function's return value is a state variable for the rest (§18.5.11) | **Yes** | Fails on a steady fraction of calls (`staged_item` below: about 1 in 3) |
| Array size with `foreach` constraints | **Yes**: sizes first, then the size is a state variable inside `foreach` (§18.5.7.1) | **Yes** | Fails on a steady fraction of calls (the `d[]` example below: about 1 in 10) |
| `randc` and `rand` in one constraint | **Yes**: `randc` first (§18.4.2), also within each priority set that function arguments create (§18.5.11) | **Yes** | Fails on a steady fraction of calls |
| `solve a before b` | Orders the choice only; the solution space does not change (§18.5.9) | No | Only the odds move |
| `dist` with nonzero weights | No order (§18.5.3) | No, but see the note below | Only the odds move |
| `soft` | No order; a soft constraint that conflicts is discarded (§18.5.13) | No: a call whose only conflicts involve soft constraints never fails (§18.5.13.1) | A default silently does not hold |

**The `dist` note.** Values a `dist` does not list, and values whose total weight is zero, are excluded as if by a hard constraint (§18.5.3). So a `dist` can be a member of a minimal conflicting set; it just never splits the solve into stages.

The size case has the same shape:

```systemverilog
// snippet
rand bit [3:0] len;
rand bit [7:0] d[];
constraint c_d { len inside {[1:10]}; d.size() == len; foreach (d[i]) d[i] == i * 30; }
```

Stage 1 picks the size (`len` from 1 to 10) without looking at `foreach`. In stage 2, a size of 10 needs `d[9] == 270`, which an 8-bit element cannot hold, so about one call in ten fails, although sizes 1 to 9 always work. Some solvers may avoid such dead ends, but the standard allows the failure, so portable code must not rely on it (tool-dependent).

**Fixes, in order of preference.** Write the rule so it can be solved jointly (`x > y` instead of `x > limit(y)`). Otherwise, put the restriction on the early variable in a constraint that mentions only that variable, so stage 1 already respects it (`y inside {2, 4}`, or `len inside {[1:9]}`). Keep `randc` variables out of constraints shared with `rand` variables.

### Failures you never see

A failure that nobody reports is worse than one that stops the test. Three patterns hide failures:

- **An unchecked call.** `void'(obj.randomize())` or a bare statement call. Fix: test the return value and stop the test.
- **`assert (obj.randomize())`.** The call sits inside an immediate assertion. When assertions are switched off, with `$assertoff`, `$assertcontrol` or a simulator option, no new attempts start (§20.11), so the assertion's expression is not evaluated and `randomize()` is never called. The object silently keeps its old values. Fix: never put a call with side effects inside an assertion.
- **The `` `uvm_do `` family of UVM macros.** A **sequence** is the UVM class that generates **sequence items** (transactions); it hands each item to a **sequencer**, which passes it to a **driver** that drives the pins ([I-UVM-3A](/curriculum/T2_Intermediate/I-UVM-3A_Fundamentals/index) teaches the flow). In uvm-core 2020.3.1, `` `uvm_do_with(req, {…}) `` creates a new item, calls `start_item()`, randomizes it, and on failure only issues a **warning** with the ID `RNDFLD`. Then it calls `finish_item()` anyway, so the driver receives the newly created item with its initial field values.

**Predict, then check.** The constraints conflict on every call. For each form, decide whether `randomize()` runs at all, who reports the failure, and whether the test stops: `if (!obj.randomize()) $fatal(…);`, `void'(obj.randomize());`, a bare `obj.randomize();`, `assert (obj.randomize());` with assertions on and with them off, and `` `uvm_do_with ``.

### Reproducing a failure from its seed

Random stimulus is repeatable. Every module, thread and object has its own random number generator, and each one is seeded from its parent when it is created (§18.14.1). So the **same seed, the same code, the same simulator version and the same command-line options** give the same run. That is what lets you debug a failure from a regression log: rerun the test with the seed the log printed.

Change the code, and the promise is gone. Creating one extra object or thread early in a thread takes the next value from that thread's generator, so every object and thread created after it gets a different seed (§18.14.1). A failing seed that "passes" after an edit may only be generating different stimulus.

### Common pitfalls and misconceptions

- **"A failed `randomize()` leaves X, zeros or the solver's last attempt."** It leaves the previous values unchanged (§18.6.3). For a fresh object those are the declared defaults.
- **"`post_randomize()` can repair or relax the failed call."** It is not called when the call fails (§18.6.3), and even after a success it runs after the values are chosen, so it can only change state that the *next* call reads.
- **"The block I switched off last is the bug."** It is one member of a conflict. The spec decides which member is wrong.
- **"If IPV6 never appears, `randomize()` must be failing on IPV6 calls."** The solver weighs whole legal combinations; it does not pick `proto` first and then give up (§18.5.5, §18.5.9). An impossible branch is a coverage hole, not a failure.
- **"`rand` variables are unsigned."** They have the signedness of their type; `rand int` is signed (§6.11.3).
- **"Through a base-class handle only the base constraints apply."** `randomize()` is virtual; the object's constraints apply (§18.5.2).
- **"If a solution exists, `randomize()` never fails."** True only when everything is solved together; function arguments, array sizes and `randc` add stages that can fail (§18.4.2, §18.5.7.1, §18.5.11).
- **"The failing seed passes now, so the bug is fixed."** The edit may have changed the stimulus that seed produces.

## Make It Work

### Worked example: a frame that refuses to be LONG

This complete program runs the whole triage on one class. The spec excerpt says a frame carries 1 to 16 bytes, a LONG frame carries at least 9, and the receive buffer holds 16 bytes. One block was written from an old version of the spec. The test asks for a LONG frame and does four things:

1. makes the failure loud and prints what it left behind;
2. switches each named block off in turn (the inline `kind == LONG` stays on);
3. loads a frame the spec calls legal and asks each block, alone, whether it accepts it;
4. replaces the wrong block in a derived class and runs 1,000 checked calls through a base-class handle.

```systemverilog
// compile
package frame_pkg;
  // Spec excerpt (a made-up receive path, not a real protocol):
  //   S1. A frame carries 1 to 16 payload bytes; len holds that count.
  //   S2. A LONG frame carries at least 9 bytes.
  //   S3. The receive buffer holds up to 16 bytes.
  typedef enum bit {SHORT, LONG} kind_e;

  class frame;
    rand kind_e    kind;
    rand bit [4:0] len;                    // 5 bits, so 16 fits
    rand bit [7:0] payload[];
    int unsigned   pre_calls, post_calls;  // not rand: counters for the demo

    constraint c_len     { len inside {[1:16]}; }         // S1
    constraint c_payload { payload.size() == len; }       // S1
    constraint c_long    { (kind == LONG) -> len >= 9; }  // S2
    constraint c_buffer  { payload.size() <= 8; }         // BUG: S3 says 16

    function void pre_randomize();
      pre_calls++;
    endfunction

    function void post_randomize();
      post_calls++;
    endfunction
  endclass

  // The fix. In a real project you edit c_buffer in frame; the derived class
  // lets one file show both. Same name, so it replaces frame::c_buffer (§18.5.2).
  class frame_fixed extends frame;
    constraint c_buffer { payload.size() <= 16; }        // S3
  endclass
endpackage

module tb_top;
  import frame_pkg::*;

  string       names[4] = '{"c_len", "c_payload", "c_long", "c_buffer"};
  frame        f;
  frame        h;              // base-class handle for the fixed object
  frame_fixed  ff;
  bit          ok;
  int unsigned n_pass, n_fail, n_free_long;

  // constraint_mode() needs a block name, so map an index to each block.
  function automatic void set_block(frame fr, int unsigned i, bit on);
    case (i)
      0: fr.c_len.constraint_mode(on);
      1: fr.c_payload.constraint_mode(on);
      2: fr.c_long.constraint_mode(on);
      3: fr.c_buffer.constraint_mode(on);
    endcase
  endfunction

  // The spec's rules, checked procedurally and independently of the constraints.
  function automatic bit spec_ok(frame fr);
    return (fr.len inside {[1:16]}) && (fr.payload.size() == fr.len) &&
           (fr.kind != LONG || fr.len >= 9) && (fr.payload.size() <= 16);
  endfunction

  initial begin
    // Step 1: make the failure loud and look at what it leaves behind.
    f = new();
    ok = f.randomize() with { kind == LONG; };
    $display("STEP1 ok=%0d kind=%s len=%0d size=%0d pre_calls=%0d post_calls=%0d",
             ok, f.kind.name(), f.len, f.payload.size(), f.pre_calls, f.post_calls);

    // Step 2: switch off one named block at a time; the inline with stays on.
    for (int i = 0; i < 4; i++) begin
      set_block(f, i, 0);
      ok = f.randomize() with { kind == LONG; };
      $display("STEP2 %s off: ok=%0d", names[i], ok);
      set_block(f, i, 1);
    end

    // Step 3: which single block rejects a frame the spec calls legal?
    f.kind    = LONG;
    f.len     = 12;
    f.payload = new[12];
    for (int i = 0; i < 4; i++) begin
      f.constraint_mode(0);                // every block off ...
      set_block(f, i, 1);                  // ... except block i
      ok = f.randomize(null);              // checker: changes nothing (§18.11.1)
      $display("STEP3 %s alone accepts the spec-legal frame: %0d", names[i], ok);
    end
    f.constraint_mode(1);

    // Step 4: the fixed class, randomized through a base-class handle.
    ff = new();
    h  = ff;                               // randomize() is virtual (§18.5.2)
    for (int i = 0; i < 1000; i++) begin
      if (i % 2 == 0) begin
        if (!h.randomize() with { kind == LONG; })
          $fatal(1, "RAND: forced LONG failed on call %0d", i);
      end else begin
        if (!h.randomize())
          $fatal(1, "RAND: free call failed on call %0d", i);
        if (h.kind == LONG) n_free_long++;
      end
      if (spec_ok(h)) n_pass++;
      else            n_fail++;
    end
    $display("STEP4 unforced LONG frames seen: %s", (n_free_long > 0) ? "yes" : "no");
    $display("PASS=%0d FAIL=%0d", n_pass, n_fail);
  end
endmodule
```

### How to triage a failing randomize()

1. **Make it loud.** Check every `randomize()` result and stop with `$fatal` (or `` `uvm_fatal `` in UVM). Record the seed.
2. **Reproduce small.** Rerun the failing seed on the unchanged code. Then build a reproducer: one object, the failing call, the same state variables.
3. **Classify.** Fails on every call: a contradiction. Fails on a steady fraction of calls: suspect an implicit solve order. Never fails, but a value never appears: a coverage hole; force the missing value inline to turn it into a failure.
4. **Read the tool's report**, if your simulator prints one, as a first candidate set.
5. **Bisect named blocks** with `constraint_mode(0)` until you have a set where removing any one member succeeds. Remember the inline constraints, which you remove by editing the call.
6. **Check against the spec.** Load values the spec calls legal and use `randomize(null)` with one block on at a time, or freeze one variable with `rand_mode(0)`.
7. **Check the hidden causes:** signed types and mixed signedness, widths that wrap, X in a state variable, a derived class that added or replaced a block, function calls, array sizes and `randc`.
8. **Fix the rule the spec contradicts**, never the symptom. Remove every triage `constraint_mode()` and `rand_mode()` call, then run many seeds and confirm that the missing values now appear.

### Debugging table

| Symptom | Likely cause | Fix | What the log shows |
|---|---|---|---|
| The same item is sent again and again, or all fields are zero | `randomize()` fails and the result is ignored | Check the result; `$fatal` or `` `uvm_fatal `` on 0 | Possibly a solver diagnostic, otherwise nothing |
| A UVM test passes although its `` `uvm_do_with `` constraints conflict | `RNDFLD` is only a warning in uvm-core 2020.3.1 | Explicit `start_item`/`randomize`/`finish_item` with `` `uvm_fatal ``, or promote `RNDFLD` | `UVM_WARNING … [RNDFLD] Randomization failed in uvm_rand_send action` |
| Randomization stops happening when assertions are disabled | `assert (obj.randomize())` is not evaluated when assertions are off (§20.11) | Move the call out of the assertion | Nothing |
| One protocol or mode never appears; no failure | A contradiction makes that branch infeasible: a coverage hole | Force the value inline, then triage the failure | Nothing until coverage is measured |
| Fails on about 1 in N calls on every seed | Function argument, array size or `randc` solved first (§18.5.11, §18.5.7.1, §18.4.2) | Solve jointly, or constrain the early variable on its own | A solver diagnostic on some calls only |
| A length or delay is negative | `rand int` is signed (§6.11.3) | `inside {[lo:hi]}` or `int unsigned` with a bound | Values such as `-1834220012` |
| A sum constraint accepts values that add up to more than the bound | The expression is evaluated in a narrow width and wraps (§11.6.1, §18.5.7.2) | Widen with a cast or a 32-bit literal; `sum() with (int'(item))` | Plausible but wrong values |
| An error naming x or z in a constraint | A 4-state state variable holds X or Z (§18.3) | Initialize it, or make it `bit` | A tool-specific error message |
| A derived item always fails; the base item works | A new-named derived constraint was added, not replaced (§18.5.2) | Reuse the base block's name, or switch the base block off | A solver diagnostic naming both blocks |

## Push Further

### Expert: Tool solver reports, switches and timeouts

Everything in this item is **tool-dependent**; IEEE 1800-2023 defines which results are legal, not how a solver finds them.

- **Reports.** Most commercial simulators print a diagnostic when `randomize()` fails, often listing the constraints, and sometimes the variable values, involved. The format and level of detail differ, and so do the options that make reports more verbose. Find them in your simulator's user guide under constraint or randomization debug, and do not copy an option name from one tool to another.
- **Timeouts and resource limits.** "If a solution exists, the constraint solver shall find it" (§18.3) is a requirement on results. In practice, very large problems (long arrays with `foreach` and `unique`, wide multiplications, deep object graphs) can take a long time or hit a tool limit, and the tool may report giving up. That is a tool limitation, not an infeasible constraint set: check by shrinking the problem.
- **Making big problems cheap.** Randomize in stages: first the sizes and control fields with `randomize(len, kind)` (§18.11), then the payload. Precompute fields that need loops in `pre_randomize()` and switch them off with `rand_mode(0)`, because the solver would overwrite active random variables (§18.6.2, §18.8). Narrow the widths. These change what is solved, so they are portable.
- **What does not reliably help.** `solve…before` is defined only by its effect on the distribution (§18.5.9). Any speed-up it gives is a property of one tool. The same is true of how `dist` behaves when its variable is coupled to other variables.

What you can rely on in every simulator, and what you must look up in yours:

| Question | Portable: fixed by IEEE 1800-2023 | Tool-dependent |
|---|---|---|
| What a failed call does | Returns 0, keeps the old values, skips `post_randomize()` (§18.6.3) | Nothing |
| Which results are legal | Every active hard constraint holds, and a solution is found if one exists (§18.3) | How the solver searches for it |
| The failure report | No report is required | Whether one is printed, its format, which constraints and values it lists, and the options that make it more verbose |
| Time and size | The standard sets no limit | Timeouts, resource limits, and whether the tool says it gave up |
| Staging with `randomize(len, kind)` or `rand_mode(0)` | What is random in each call (§18.11, §18.8) | How much time it saves |
| `solve…before` | Only the distribution changes (§18.5.9) | Any speed-up |

### Expert: Silent failures in UVM flows

The uvm-core 2020.3.1 macros for sequences (IEEE 1800.2-2020 Annex B.3.1) are where most silent failures hide.

- `` `uvm_do(SEQ_OR_ITEM, …) `` expands to `` `uvm_create `` (which builds the item with `create_item()`) plus `` `uvm_rand_send ``. In uvm-core 2020.3.1, `` `uvm_rand_send `` calls `start_item()`, then `randomize() with` your constraints, then `finish_item()`. A failed randomization only executes `` `uvm_warning("RNDFLD", "Randomization failed in uvm_rand_send action") `` (`macros/uvm_sequence_defines.svh`). For an item from `` `uvm_do ``, the driver receives a just-created item; with `` `uvm_rand_send `` on a reused item, it receives the previous values.
- **Who reports it.** A sequence item reports through its sequencer's report handler: `uvm_get_report_object()` returns `m_sequencer`, or `uvm_root` when there is none (`seq/uvm_sequence_item.svh`). So an override must target the **sequencer**, not the test.
- **Promote it to an error** when you cannot edit the sequences:

```systemverilog
// snippet: in the test's end_of_elaboration_phase, after the env is built
env.agt.sqr.set_report_severity_id_override(UVM_WARNING, "RNDFLD", UVM_ERROR);
```

`set_report_severity_id_override` is IEEE 1800.2-2020 §6.3.7. From the command line, uvm-core 2020.3.1 accepts `+uvm_set_severity=<comp>,<id>,<current severity>,<new severity>`, for example `+uvm_set_severity=*,RNDFLD,UVM_WARNING,UVM_ERROR`; every component applies matching settings to itself when it is constructed (`base/uvm_component.svh`). uvm-core has no hierarchical (`_hier`) variant of the severity override.

### Expert: Reproducing a failure from its seed after the code changed

The plain-SystemVerilog rules are in §18.14: each object and thread is seeded from the next value of its creating thread's generator (§18.14.1), and object stability means that calls to one object's `randomize()` do not depend on other objects or on other random calls (§18.14.3). Two consequences for triage:

- **Self-seeding protects a stream.** An object that calls `srandom()` with a fixed or name-derived value in its own `new()` keeps its stream when other objects are added. The standard recommends seeding inside `new()`, because otherwise another thread may use the object before the creator reseeds it (§18.14.3). Seeding the *newly added* helper does not help: its `new` has already consumed the creator's next value.
- **UVM reseeds by name (uvm-core 2020.3.1 behaviour).** With UVM seeding on (the default), `uvm_component::new` calls `reseed()`; `uvm_task_phase` reseeds the process it starts for each component in a task phase (`run_phase` and the run-time phases) from the phase type and the component's full name; and `set_item_context()`, which `start()`, `create_item()` and `start_item()` call, reseeds sequences and items. The seed is a hash of the type name, the full name and a global seed taken from the simulator seed, plus a per-name counter (`base/uvm_misc.svh`). So adding a component does not shift the run-phase streams of existing components, while renaming a component or a sequence changes the seeds of everything below it, and a plain `new` of a non-UVM object still shifts later plain objects in the same thread. The IEEE 1800.2-2020 clause that specifies this is unverified here, so treat it as implementation behaviour.

The two seeding schemes side by side:

| What gets a seed | Plain SystemVerilog | uvm-core 2020.3.1 with UVM seeding on |
|---|---|---|
| A plain object (`new` of a non-UVM class) | The creating thread's next random value (§18.14.1) | The same: uvm-core does not reseed it |
| A component | The creating thread's next random value when its `new` runs | Reseeded in `uvm_component::new` from its type name and full name |
| A component's task-phase process (`run_phase` and the run-time phases) | Its parent thread's next random value | Reseeded from the phase type and the component's full name |
| A sequence or item | The creating thread's next random value | Reseeded in `set_item_context()` from its type name and full name |
| **Adding a component** | Shifts every object and thread created after it in the same thread | Leaves the run-phase streams of existing components unchanged |
| **Renaming a component or a sequence** | No effect: seeding follows creation order, not names | Changes its own seeds and the seeds of everything below it |

A disciplined workflow follows: replay the failing seed on the **old** code first and keep that log; minimize to a reproducer that does not depend on the seed (force the failing values inline, or load them and use `randomize(null)`); fix; then prove the fix with the reproducer plus a fresh batch of seeds, never with the old seed alone. Seeds do not transfer between simulators: the default seed and the generator state are implementation-dependent (§18.13.4, §18.14.1). [E-DBG-1](/curriculum/T4_Expert/E-DBG-1_Advanced_UVM_Debug_Methodologies/index) builds the regression workflow on top of this.

### Expert: State shared between objects

Some failures depend on what *another* object did earlier, which makes them look random:

- A **static** random variable is shared by all instances; every `randomize()` of any instance changes it (§18.6.3). Its `rand_mode` state is shared too (§18.8), and for `randc` so is the cyclic state (§18.4.2).
- A **static constraint block** is switched on or off for **all** instances by one `constraint_mode()` call (§18.5.10). A test that disables it "temporarily" for one object disables it everywhere until someone switches it back.
- `rand_mode(0)` on a `rand` class handle changes only the handle's mode, not the modes inside the object (§18.8). A nested object that "should be frozen" may still be randomized, or the reverse.
- A configuration object read by several items' constraints is ordinary shared state: if one test writes an illegal knob value, every item that reads it fails.

| Shared thing | What one call through one object changes | Clause |
|---|---|---|
| `static rand` variable | Its value and its `rand_mode` for every instance; for `randc`, the one cyclic sequence too | §18.6.3, §18.8, §18.4.2 |
| `static` constraint block | Its `constraint_mode` for every instance | §18.5.10 |
| `rand_mode(0)` on a `rand` class handle | Only the handle's own mode; the modes of the variables inside the object stay as they were | §18.8 |
| A configuration object that several items read | Every later `randomize()` whose constraints read the changed knob | ordinary shared state |

When a failure appears only after a particular earlier test step, print the static and shared state just before the failing call and compare it with a passing run.

### Debug challenge: the one-in-three failure

1. **Predict** how many of 300 calls fail, and why the number does not depend much on the seed.
2. Write a `tb_top` that makes 300 checked calls, counts the failures without stopping, and prints `FAILS=<n>`.
3. Fix the class two ways: once without the function, once keeping the function. After each fix, your bench should print `FAILS=0`.

```text
FAILS=97
```

**3. Two fixes.**

- **Without the function:** `constraint c_x { x > y; x < 6; }`. Now `x` and `y` are solved together, the only legal pairs have `y` = 2 or 4, and every call succeeds (§18.3).
- **Keeping the function:** restrict `y` in a constraint that mentions only `y`, so the first stage already respects it: `constraint c_y { y inside {2, 4}; }`. If 8 is a legal `y` in the spec, the function form cannot express the rule; drop the function.

In both cases, restore the checked call (`if (!s.randomize()) $fatal(...)`) once the experiment is over.
