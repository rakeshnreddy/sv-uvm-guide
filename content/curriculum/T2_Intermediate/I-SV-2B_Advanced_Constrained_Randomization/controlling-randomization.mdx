## Quick Take

- **What it is:** A class's constraints describe every legal transaction. This page covers the controls that change, *for a particular test or a particular call*, what `randomize()` does with that description, without editing the class: switching random variables off with `rand_mode()`, switching constraint blocks off with `constraint_mode()`, running your own code just before and after the solve with `pre_randomize()` and `post_randomize()`, replacing constraints in a derived class, and naming the variables one call may change with `randomize(v, w)` or none at all with `randomize(null)` (IEEE 1800-2023 §18.5.2, §18.6.2, §18.8–§18.11).
- **Why it matters:** One transaction class serves hundreds of tests. An error-injection test needs unaligned addresses, a directed test needs a fixed address with random lengths, a monitor needs to check an observed transaction against the same rules. Each control fits one of those jobs. Pick the wrong one and the call fails on every seed, a setting leaks into the next test, or a field silently stops being random.
- **The Analogy:** A mixing desk in front of a fixed band. `rand_mode(0)` freezes one channel's fader where it is; `constraint_mode(0)` bypasses one effects unit; `pre_randomize()` and `post_randomize()` are the sound check before the take and the mastering after it; a derived class swaps one effects unit for another with the same name. *Where it breaks:* a frozen fader in a real desk just stops moving. A frozen random variable becomes a **fixed value that every constraint must still accept**, so freezing it at a value a constraint forbids makes every call fail. Freezing never relaxes a rule.

**You will be able to:**
1. **Write** `rand_mode()` and `constraint_mode()` calls (set and query forms, on a whole object, one variable, one array element or a static block) and **predict** which later `randomize()` calls they affect.
2. **Predict** when `pre_randomize()` and `post_randomize()` run, on which objects, and whether a change made inside them affects the current call or the next one.
3. **Write** a derived class that replaces or adds constraints by name, and **predict** the active constraint set when the object is randomized through a base-class handle.
4. **Choose** among `constraint_mode()`, a derived-class override, `rand_mode()`, `randomize(v, w)` and inline `with` to aim one test's stimulus, and **write** `randomize(null)` as a constraint checker.
5. **Debug** control mistakes: a mode left switched off, a frozen variable that violates a constraint, an override that skips `super`, and a hook that changes the wrong call.

### Two words first: active and state

Every `randomize()` call works on a set of **active random variables** and a set of **active constraints**. The solver (the part of `randomize()` that searches for values) may change only the active random variables, and every value it returns must satisfy every active constraint.

Everything else that a constraint mentions is a **state variable**: the solver reads its current value and treats it as a constant. A class member declared without `rand` or `randc` is a state variable. So is a `rand` member that has been switched off (§18.5.8 step c, §18.8).

```systemverilog
// snippet
class bus_item;
  rand bit [15:0] addr;           // random variable: active by default
  rand bit [7:0]  len;            // random variable: active by default
  int unsigned    max_len = 16;   // state variable: read by c_len, never randomized

  constraint c_align { addr[1:0] == 2'b00; }        // a named constraint block
  constraint c_len   { len inside {[1:max_len]}; }
endclass
```

The same class as a picture. This page calls it **the two-sets picture**; every later section points back to it.

All random variables and all constraint blocks start **active** (§18.8, §18.9). Every control on this page changes one of the two sets: which variables are active, or which constraints are active.

### Switching variables off: rand_mode()

`rand_mode()` is a built-in method of every random variable, and of the object as a whole (§18.8). Calling it with `0` makes the variable **inactive**: it is "treated the same as if it had not been declared `rand` or `randc`", so the solver uses its current value as a constant. Calling it with `1` makes it active again.

| Call | Effect |
|---|---|
| `p.rand_mode(0);` | Every `rand` and `randc` variable in `p` becomes inactive (this form only exists as a `void` call) |
| `p.addr.rand_mode(0);` | Only `addr` becomes inactive |
| `p.data[3].rand_mode(0);` | Only element 3 of the unpacked array `data`; `p.data.rand_mode(0)` affects every element |
| `p.hdr.rand_mode(0);` where `hdr` is a `rand` class handle | Only the handle: the object `hdr` points to is no longer randomized with `p`, but the modes of the variables inside it do not change |
| `m = p.addr.rand_mode();` | Query: returns 1 if active, 0 if inactive. Only for a single variable, so select one element of an array |
| `p.max_len.rand_mode(0);` where `max_len` is not `rand` | Compile error: the name must be a `rand` or `randc` variable in the class hierarchy |

Two more rules from §18.8. The change applies to **subsequent** calls of `randomize()` (Table 18-3) and stays until you change it again. And if the variable is `static` (one copy shared by every object of the class), its mode is static too: switching it off in one object switches it off in all of them.

In the two-sets picture, `p.addr.rand_mode(0)` moves `addr` out of the lower box. It becomes a constant, like `max_len`, and `c_align` in the upper box still checks it.

```systemverilog
// snippet
p.addr = 16'h1000;          // choose the value first...
p.addr.rand_mode(0);        // ...then freeze it: addr is now a state variable
if (!p.randomize()) $fatal(1, "randomize() failed");   // len changes, addr stays 16'h1000
p.addr.rand_mode(1);        // restore it, or the next test inherits the frozen addr
```

**Predict:** suppose the first line were `p.addr = 16'h0001;` instead, so `addr` holds an unaligned value when it is frozen. What does every later `p.randomize()` return, and what happens to `len`?

**The classic mistake.** Freezing a variable does not loosen any constraint that mentions it. If `p.addr` still held `16'h0001` when you froze it, `c_align` would require `16'h0001 & 3 == 0`, which is false, and every call would return 0. Assign a legal value before freezing, as above.

Here `addr[1:0]` is `2'b01`, so `c_align` is false for that constant whatever the solver picks for `len`. Every call returns 0, and `addr` and `len` keep their old values (§18.8, §18.6.3). This is setup 3 of the experiment below, in miniature.

</details>

**Rule to keep:** freezing never loosens a constraint, so assign a legal value before you call `rand_mode(0)`.

### Switching constraint blocks off: constraint_mode()

`constraint_mode()` does the same for **named constraint blocks** (§18.9). An inactive block "is not considered by the `randomize()` method". In the two-sets picture, `p.c_align.constraint_mode(0)` takes `c_align` out of the upper box, and the lower box is unchanged.

| Call | Effect |
|---|---|
| `p.constraint_mode(0);` | Every constraint block in `p` becomes inactive (`void` form only) |
| `p.c_align.constraint_mode(0);` | Only `c_align`. The name can be any block in the class hierarchy, including one inherited from a base class |
| `m = p.c_align.constraint_mode();` | Query: 1 if active, 0 if inactive |
| `p.c_typo.constraint_mode(0);` | Compile error: no block of that name exists in the hierarchy |

What you cannot switch: a single expression inside a block (the whole block goes), and an inline `with` constraint, which has no name. That is why practitioners name blocks finely: one block per rule a test might want to drop.

The standard's own example of why this exists (§18.3) is error injection: a word-aligned bus item, and a test that must generate **unaligned** addresses.

```systemverilog
// snippet: after IEEE 1800-2023 §18.3, exercise_illegal
p.c_align.constraint_mode(0);                        // drop the alignment rule...
if (!p.randomize() with { addr[1:0] != 2'b00; })     // ...and ask for the opposite
  $fatal(1, "randomize() failed");
p.c_align.constraint_mode(1);                        // put it back for the next user
```

Without the first line, the inline constraint and `c_align` contradict each other and every call fails: an inline `with` constraint is **added** to the class's constraints (§18.7). It can narrow the legal set, never widen it.

**Static constraint blocks.** A block declared `static constraint` has one mode shared by every object of the class: "calls to `constraint_mode()` shall affect all instances of the specified constraint in all objects" (§18.5.10).

```systemverilog
// snippet
class word_item;
  rand bit [31:0] addr;
  static constraint c_word { addr[1:0] == 2'b00; }   // one mode for every word_item
endclass
```

**Debrief.**
- Setup 1 fails: `x > 3` and `y > 2` force `x + y` to be at least 7, but `c_sum` needs less than 6.
- Setup 2 succeeds with exactly one legal pair, `(4, 1)`: dropping a block **widens** the legal set.

Freezing **narrowed** the problem to one row (`y = 4`). The conflict list in the lab names only one of the two, because the lab marks one minimal conflict at a time (what a simulator reports, and how much at once, varies by tool): fix it, re-run, and the next one appears.
- Setup 4 removes the two conflicts one at a time. Dropping `c_x` clears the first, but is not enough, because `c_odd` still rejects the frozen 4. Dropping `c_odd` too clears the second and leaves `x` as 0 or 1.

</details>

The rule to keep: `constraint_mode(0)` removes rules; `rand_mode(0)` removes a degree of freedom and keeps every rule. Finding the smallest set of blocks that conflict is a debugging skill of its own, taught in [Solver Debug and Failure Triage](/curriculum/T2_Intermediate/I-SV-2B_Advanced_Constrained_Randomization/solver-debug).

### Dynamic constraint modification: the four levers

§18.10 lists four ways to change what randomization does while the simulation runs:

| Lever | What changes | Taught in |
|---|---|---|
| Implication and `if`/`else` constraints | A rule applies only when a condition holds | [Conditional and array constraints](/curriculum/T2_Intermediate/I-SV-2B_Advanced_Constrained_Randomization/advanced-constraints) |
| `constraint_mode()` | Whole blocks on or off | This page |
| `rand_mode()` | Variables on or off; off means "use the current value" | This page |
| `dist` weights | How often values are chosen (weights may be expressions) | [I-SV-2A](/curriculum/T2_Intermediate/I-SV-2A_Constrained_Randomization_Fundamentals/index) |

In practice a fifth pattern combines them: a **knob**, a state variable that a constraint reads. In `bus_item`, `c_len` reads `max_len` (the node outside both boxes in the two-sets picture); a test that sets `p.max_len = 4;` limits every later call to lengths 1 to 4, without touching a mode. Knobs are the usual way to pass test intent into an item; in UVM their values often come from the [configuration database](/curriculum/T2_Intermediate/I-UVM-2C_Configuration_and_Resources/index).

### pre_randomize() and post_randomize(): hooks around the solve

A **hook** is a method that some other code calls for you at a fixed point. Every class has two randomization hooks, both `function void` with no arguments, and both empty unless you override them (§18.6.2):

- `randomize()` calls `pre_randomize()` **first**, before it computes any value.
- After "the new random values are computed and assigned", it calls `post_randomize()`.
- If the solve fails, `randomize()` returns 0, the random variables keep their previous values, and `post_randomize()` is **not** called (§18.6.3). `pre_randomize()` has already run.

Use `pre_randomize()` to set preconditions: knobs, counters, the contents of a lookup table a constraint reads. Use `post_randomize()` for values the solver should not or cannot compute: checksums, CRCs, packed encodings, debug prints. This example counts the hook calls, so you can see the rule in the output.

```systemverilog
// compile
package frame_pkg;
  class frame;
    rand bit [7:0] len;
    rand bit [7:0] payload[];
    bit      [7:0] chk;            // XOR checksum (stand-in for a CRC): computed
    int unsigned   n_pre, n_post;  // hook call counters for this demo

    constraint c_len  { len inside {[1:32]}; }
    constraint c_size { payload.size() == len; }  // the solver sizes AND fills payload

    function void pre_randomize();
      n_pre++;                     // runs before every solve, even one that then fails
    endfunction

    function void post_randomize();
      n_post++;                    // runs only after a successful solve
      chk = 0;
      foreach (payload[i]) chk ^= payload[i];
    endfunction
  endclass
endpackage

module tb_top;
  import frame_pkg::*;
  frame     f;
  bit       ok;
  bit [7:0] old_len;

  initial begin
    f = new();
    if (!f.randomize()) $fatal(1, "frame randomize() failed");
    $display("call 1: pre=%0d post=%0d chk_matches=%0d",
             f.n_pre, f.n_post, f.chk == f.payload.xor());
    old_len = f.len;
    ok = f.randomize() with { len == 0; };   // contradicts c_len on purpose
    $display("call 2: ok=%0d pre=%0d post=%0d len_kept=%0d",
             ok, f.n_pre, f.n_post, f.len == old_len);
  end
endmodule
```

**Predict:** call 2 contradicts `c_len` on purpose. Write down its four values, `ok`, `pre`, `post` and `len_kept`, before you open the output.

<summary className="cursor-pointer font-semibold">Check against the hook timeline</summary>

| Change made in... | To... | Effect |
|---|---|---|
| `pre_randomize()` | a state variable or knob, such as `max_len` | This call: the solve has not started yet |

| `post_randomize()` | a `rand` variable, such as `len = 200;` | The value is replaced after the solve and **no constraint checks it**: you can produce an illegal item |

</details>

The third row is the misconception to unlearn: `post_randomize()` cannot change the constraints of the call that is running it. The fourth row is the anti-pattern this page has always warned about: deleting `payload` in `pre_randomize()` and refilling it in `post_randomize()` with fixed values such as `payload[i] = i`. That throws away the randomization, ignores every element constraint, and leaves payload coverage stuck on one pattern. Let the constraints size and fill the array; keep the hooks for what the solver cannot do.

**Overriding a hook in a derived class.** If a derived class does not define `pre_randomize()`, the inherited one runs automatically. If it **does** define one, the standard says the override "shall call" `super.pre_randomize()`; otherwise "their pre- and post-randomization processing steps shall be skipped" (§18.6.2). The same holds for `post_randomize()`. Nothing calls the base version for you once you have written your own.

```systemverilog
// snippet
class err_frame extends frame;
  function void post_randomize();
    super.post_randomize();      // keep the base steps: n_post++ and chk
    chk = ~chk;                  // then corrupt the checksum on purpose
  endfunction
endclass
```

### Replacing constraints in a derived class

Constraints are inherited like other class members (§18.5.2). The rules fit in three lines:

1. A derived class inherits **all** of its base class's constraints.
2. A constraint with the **same name** as an inherited one **replaces** it.
3. A constraint with a **new name** is **added**.

And one rule from polymorphism: "`randomize()` is virtual and therefore honors constraints of the object on which it was called, regardless of the data type of the object handle" (§18.5.2). Code that holds a base-class handle, such as a driver or a sequence, still gets the derived class's constraints.

```systemverilog
// snippet: the Make It Work example uses these two classes
class unaligned_item extends bus_item;
  constraint c_align { addr[1:0] != 2'b00; }   // same name: replaces bus_item::c_align
  constraint c_short { len <= 4; }             // new name: added to c_len and c_err
endclass
```

**The classic mistake.** Rule 2 is silent. A derived class that declares `constraint c_len { len > 100; }` meaning to *add* a rule actually *drops* the base `c_len`. No error, no warning; the base rule is gone. Choose new names for added rules, and when you do mean to replace one, say so in a comment (or with the `:extends` specifier in Push Further).

**Related forms.**
- A constraint can be declared as a **prototype** in the class (`constraint c_mode;` or `extern constraint c_mode;`) and defined later outside it as `constraint bus_item::c_mode { ... }` (§18.5.1). A derived prototype with an inherited name replaces the inherited constraint too.
- An abstract (`virtual`) class may declare a **pure constraint**, `pure constraint c_legal;`, which every non-abstract derived class must implement (§18.5.2). It is how a base class says "each protocol variant must define its own legality rule".
- A derived class's `soft` constraints outrank its base class's, and inline `soft` constraints outrank both (§18.5.13.1), so "the later layer wins" holds for soft defaults as well. [I-SV-2A's constraint-blocks page](/curriculum/T2_Intermediate/I-SV-2A_Constrained_Randomization_Fundamentals/constraint-blocks) covers soft priorities.

### Choosing the random variables for one call: randomize(v, w)

`randomize()` accepts a list of property names. For that call, **those names are the complete set of random variables**; every other variable in the object is a state variable (§18.11). It is the one-call equivalent of a set of `rand_mode()` calls, and it restores itself: the next plain `randomize()` uses the declared modes again.

The standard's example, class `CA`:

```systemverilog
// snippet: IEEE 1800-2023 §18.11
class CA;
  rand byte x, y;
  byte      v, w;                 // not rand
  constraint c1 { x < v && y > w; }
endclass
```

|---|---|---|

Notice the third row: `v` and `w` are not declared `rand`, yet the call randomizes them. The argument list can name **any** property. Three limits (§18.11):
- arguments are property names only, never expressions;
- a `local` member can be named only from code inside its own class;
- the call cannot turn a variable into `randc` or a `randc` into `rand`.

All active constraint blocks still apply, including those that mention only state variables. If a state variable already violates one, the call fails.

**Predict:** `a.x = 127;` then `ok = a.randomize(v, w);`. What is `ok`?

The call fails and `v` and `w` keep their values (§18.6.3). Naming the random variables in the call is conceptually the same as switching the others off with `rand_mode(0)` for that one call (§18.11), so every rule still applies to their current values.

</details>

### Checking instead of generating: randomize(null)

The special argument `null` means "no random variables for this call". Every member becomes a state variable, and `randomize()` turns into a **checker**: it changes nothing and "simply returns 1 if all constraints are satisfied and 0 otherwise" (§18.11.1). For `CA`, `success = a.randomize(null);` returns 1 exactly when `x < v && y > w` holds for the current values. A class that has no random variables at all behaves the same way on a plain `randomize()`.

This is how you reuse an item's rules as a check: load observed field values into an item and ask whether its constraints accept them. Push Further covers the design choices this raises.

## Make It Work

### Worked example: six ways to aim one item

This bench uses one `bus_item` class and one derived class, and aims them six ways. Every check counts outcomes instead of printing random values, so the expected output is the same on every simulator and every seed.

```systemverilog
// compile
package bus_pkg;
  class bus_item;
    rand bit [15:0] addr;
    rand bit [7:0]  len;
    bit             err;            // not rand: a state variable unless a call names it
    int unsigned    max_len = 16;   // knob: a state variable read by c_len

    constraint c_align { addr[1:0] == 2'b00; }     // word-aligned addresses
    constraint c_len   { len inside {[1:max_len]}; }
    constraint c_err   { err -> len == 1; }        // an error item is one beat long
  endclass

  // Same name replaces the base rule; a new name adds one (IEEE 1800-2023 §18.5.2).
  class unaligned_item extends bus_item;
    constraint c_align { addr[1:0] != 2'b00; }
    constraint c_short { len <= 4; }
  endclass
endpackage

module tb_top;
  import bus_pkg::*;

  bus_item       item;
  bus_item       h;               // base-class handle
  unaligned_item u;
  int            pass_n, fail_n;

  function automatic void check(string what, bit ok);
    if (ok) pass_n++;
    else begin
      fail_n++;
      $display("FAIL: %s", what);
    end
  endfunction

  initial begin
    int n_hit;
    bit ok;
    item = new();

    // 1. Error injection: drop the alignment block, ask for the opposite inline.
    item.c_align.constraint_mode(0);
    n_hit = 0;
    repeat (8) begin
      if (!item.randomize() with { addr[1:0] != 2'b00; }) $fatal(1, "way 1 failed");
      if (item.addr[1:0] != 2'b00) n_hit++;
    end
    item.c_align.constraint_mode(1);              // modes persist: switch it back on
    $display("constraint_mode + with : unaligned %0d/8, c_align on = %0d",
             n_hit, item.c_align.constraint_mode());
    check("way 1", n_hit == 8 && item.c_align.constraint_mode() == 1);

    // 2. A derived item, randomized through a base-class handle.
    u = new();
    h = u;                                        // randomize() is virtual
    n_hit = 0;
    repeat (8) begin
      if (!h.randomize()) $fatal(1, "way 2 failed");
      if (h.addr[1:0] != 2'b00 && h.len <= 4) n_hit++;
    end
    $display("override, base handle : unaligned and len<=4 %0d/8", n_hit);
    check("way 2", n_hit == 8);

    // 3. Hold addr fixed: give it a legal value, then make it a state variable.
    item.addr = 16'h1000;
    item.addr.rand_mode(0);
    n_hit = 0;
    repeat (8) begin
      if (!item.randomize()) $fatal(1, "way 3 failed");
      if (item.addr == 16'h1000) n_hit++;
    end
    $display("addr.rand_mode(0)      : addr held %0d/8, mode = %0d",
             n_hit, item.addr.rand_mode());
    check("way 3", n_hit == 8 && item.addr.rand_mode() == 0);
    item.addr.rand_mode(1);

    // 4. Only len is random for these calls; addr is state without touching its mode.
    item.addr = 16'h2000;
    n_hit = 0;
    repeat (8) begin
      if (!item.randomize(len)) $fatal(1, "way 4 failed");
      if (item.addr == 16'h2000 && item.len inside {[1:16]}) n_hit++;
    end
    $display("randomize(len)         : addr held %0d/8", n_hit);
    check("way 4", n_hit == 8);

    // 5. A non-rand member made random for one call; len = 5 is now state.
    item.len = 8'd5;
    ok = item.randomize(err);                     // c_err: err -> len == 1, so err = 0
    $display("randomize(err), len=5  : ok=%0d err=%0d", ok, item.err);
    check("way 5", ok && item.err == 0);

    // 6. Checker: nothing is random; the return value says whether the rules hold.
    item.addr = 16'h2001;
    ok = item.randomize(null);
    $display("randomize(null)        : addr=2001 -> %0d", ok);
    check("way 6a", !ok && item.addr == 16'h2001);
    item.addr = 16'h2000;
    ok = item.randomize(null);
    $display("randomize(null)        : addr=2000 -> %0d", ok);
    check("way 6b", ok);

    $display("PASS=%0d FAIL=%0d", pass_n, fail_n);
  end
endmodule
```

1. **Name the job.** Different values for one test? Different values for one call? Checking, not generating?
2. **Narrowing only, for one call** (a subset of what is already legal): use inline `with` in the sequence or test. It adds constraints for that call and leaves the class untouched.
3. **Going outside a rule** (error injection): switch the block off with `constraint_mode(0)` and add the opposite inline, or write a derived class that replaces the block by name and swap it in (in UVM, with a factory override).
4. **Holding a field fixed:** assign a legal value, then `rand_mode(0)`; or, for one call only, `randomize(<the other fields>)`.
5. **Changing a limit for many calls:** set a knob that a constraint reads, such as `max_len`.
6. **Restore what you changed** (`constraint_mode(1)`, `rand_mode(1)`) before the object goes back to shared code, or use a fresh object.
7. **Check every call:** `if (!obj.randomize(...)) $fatal(...)` outside UVM, `` `uvm_fatal `` or `` `uvm_error `` inside it.

### Debugging the controls

| Symptom | Likely cause | Fix |
|---|---|---|
| Every call fails right after a `rand_mode(0)` | The frozen value violates a constraint | Assign a legal value before freezing, or freeze a different variable |
| A later test is missing a whole category of values | A `constraint_mode(0)` or `rand_mode(0)` from an earlier test is still in effect (modes persist; a shallow copy made with `new` copies them too, §8.12) | Restore modes, or randomize a fresh object; query the mode to confirm |
| A derived item violates a base rule that "should" still apply | The derived class declared a block with the same name | Rename the derived block, or confirm the replacement was intended |
| A derived item's checksum or base fields are wrong | Its `pre_randomize()` or `post_randomize()` override does not call `super` | Call `super.pre_randomize()` / `super.post_randomize()` first |
| A value set in `pre_randomize()` is never seen | It was an active random variable; the solver overwrote it | Use a knob plus a constraint, or `rand_mode(0)`, or inline `with` |
| Items violate their own constraints | `post_randomize()` writes a `rand` variable | Compute only non-random, derived fields there |
| Inline `with` "should" allow a value but the call fails | Inline constraints are added, never relaxing a class constraint | Switch the conflicting block off, or override it |
| `constraint_mode` or `rand_mode` will not compile | Misspelled block name, or the variable is not `rand` | Use the declared name; `rand_mode()` works only on `rand`/`randc` variables |

### In a real testbench

- **Derived items swapped in by the factory.** In UVM (taught from [I-UVM-1A](/curriculum/T2_Intermediate/I-UVM-1A_Components/index) on) the item class extends `uvm_sequence_item` and is registered with the factory, and sequences create items with `type_id::create`. A test registers a type override so those calls return the derived item (an `unaligned_item` here), and every sequence starts producing unaligned addresses without being edited. [I-UVM-1B](/curriculum/T2_Intermediate/I-UVM-1B_The_UVM_Factory/index) teaches overrides.
- **Mode switches in sequences.** A sequence calls `req.c_align.constraint_mode(0);` before `req.randomize() with {...}`. UVM sequences usually create a new item per transaction, so the setting does not leak; a reused item keeps it. [I-UVM-3A](/curriculum/T2_Intermediate/I-UVM-3A_Fundamentals/index) shows the item flow.
- **Knobs from configuration.** A test puts a limit such as `max_len` in the configuration database; the sequence reads it and copies it into each item before randomizing.
- **`post_randomize()` in sequence items** computes CRCs, parity and packed fields, and calls `super.post_randomize()` when the base item has one.
- **When not to use these controls.** If every test needs the same change, change the class. Mode switches scattered across tests are hard to audit; prefer a named derived item or a knob that a reviewer can find.

## Push Further

### Expert: constraint layering for reuse

**Override specifiers.** Accidentally replacing a base constraint is common enough that IEEE 1800-2023 added specifiers for it (§18.5.2; grammar in Syntax 18-2 and Annex A.1.10: `[ static ] constraint [ dynamic_override_specifiers ] name { ... }`):

```systemverilog
// snippet: IEEE 1800-2023 specifiers; check your simulator's support first
class bus_item;
  rand bit [15:0] addr;
  constraint :initial c_align { addr[1:0] == 2'b00; }  // must not override anything
endclass

class unaligned_item extends bus_item;
  constraint :extends :final c_align { addr[1:0] != 2'b00; }  // must override; no more
endclass
```

| Specifier | Meaning | It is an error when... | Combines with |
|---|---|---|---|
| `:initial` | The constraint shall not be an override | It is used on an override (a constraint whose name a base class already declares) | `:final`; `:initial` and `:extends` are mutually exclusive |
| `:extends` | The constraint shall be an override | No base constraint has that name | `:final`; never with `:initial` |
| `:final` | No derived class may replace it | A derived class replaces it; or it is used on a pure constraint (footnote to Syntax 8-1) | Either of the others |

Two more rules:
- With a prototype and an external block, put the specifiers on both or on neither (§18.5.2).
- Specifiers are illegal on `static` constraints (Syntax 18-9 footnote, §18.5.10). A static prototype and its external block must both be `static`, and an override of a static pure constraint must match it.

Support for these 2023 specifiers varies by simulator and version (tool-dependent): try them in a small file before you adopt them.

**Choosing a layering mechanism.**

| Mechanism | Scope | Strength | Weakness |
|---|---|---|---|
| Knob read by a constraint | Every later call on that object | Visible, reviewable, cheap | Only changes what the class author anticipated |
| `constraint_mode()` | Every later call on that object | Can remove any named rule | Easy to leave off; scattered across tests |
| Inline `with` | One call | Local and obvious | Can only narrow, never relax |
| Derived class (plus factory override in UVM) | Every object of that type the factory creates | Can replace and add rules; reusable across tests | Silent replacement by name; one more class to maintain |
| `soft` defaults in the base class | Every call, until a higher layer contradicts them | Tests override without switching anything (§18.5.13.1) | Readers misread them as probabilities |

A common house style: the base item holds hard **legality** blocks (protocol rules, rarely switched off) and soft **shaping** defaults; tests narrow with inline `with` and knobs; error injection lives in named derived classes. That keeps every `constraint_mode(0)` in a handful of reviewed places.

### Expert: hooks and nested objects

A `rand` class handle makes the object it points to part of the same solve: the solver collects the **active random objects** recursively, starting from the object whose `randomize()` was called, and solves all their variables and constraints together (§18.4, §18.5.8). The hooks follow the same set: `randomize()` invokes `pre_randomize()` "on obj and also all of its random object members that are enabled", and likewise `post_randomize()` (§18.6.2).

```systemverilog
// snippet
class hdr_t;
  rand bit [3:0] kind;
  function void post_randomize();
    $display("hdr_t::post_randomize kind=%0d", kind);
  endfunction
endclass

class pkt;
  rand hdr_t hdr;                 // rand handle: hdr's object is solved with pkt
  function new();
    hdr = new();                  // randomize() never allocates objects (§18.4)
  endfunction
endclass
```

Consequences worth knowing:
- `p.randomize()` runs `hdr_t`'s hooks as well as `pkt`'s. The standard does not spell out the order between the container's hook and its members' hooks, so do not write code that depends on it.
- `p.hdr.rand_mode(0)` changes only the handle's mode (§18.8). For later `p.randomize()` calls, `hdr`'s object is no longer an active random object: its variables keep their values, its constraints are not applied, and its hooks are not called. `p.hdr.randomize()` still randomizes it normally, because the modes inside `hdr_t` were never touched.
- "Randomization shall not modify the actual object handle" (§18.4): a `rand` handle is never re-pointed or allocated. Allocate members in `new()`.
- A `static rand` variable is shared by all instances and changes in every instance on each `randomize()` (§18.6.3); its `rand_mode` is shared too (§18.8).
- `p2 = new p1;` (a shallow copy: a new object with the same property values) copies the random number generator (RNG) state, every `rand_mode` and `constraint_mode` setting and the `randc` cycle state (§8.12). The copy starts with the same switches as the original, which is either what you want or a leak.

### Expert: mode changes inside pre_randomize()

Can `pre_randomize()` switch a block off for the call that is running it? Tables 18-3 and 18-4 describe the effect of `rand_mode()` and `constraint_mode()` on "subsequent calls to the `randomize()` method", and §18.6.2 presents `pre_randomize()` as the place to "set preconditions before the object is randomized". The standard does not say explicitly whether a mode change made inside `pre_randomize()` applies to the call already in progress.

For portable code, call `constraint_mode()` and `rand_mode()` **before** `randomize()`, and set only knobs in `pre_randomize()`. Knobs are plain state variables; the solve has not started when `pre_randomize()` runs, so a knob set there applies to the current call by the ordinary rules of §18.6.2.

### Expert: randomize() as a checker

`randomize(null)` turns an item's constraints into an executable specification (§18.11.1). Three design questions decide whether that is useful:

1. **Which rules does the checker see?** Every active block, including shaping blocks a test added. Separate legality from shaping by name (`c_legal_*` versus `c_shape_*`) and switch the shaping blocks off on the checker's copy of the item.
2. **What does it report?** One bit. When it returns 0 you know the item is illegal, not which rule failed. Narrow it down by switching legality blocks off one at a time, as in [Solver Debug](/curriculum/T2_Intermediate/I-SV-2B_Advanced_Constrained_Randomization/solver-debug).
3. **What about soft constraints?** The standard says soft constraints "can only be specified on random variables" (§18.5.13.1), and in a `randomize(null)` call there are none. How a simulator treats a soft constraint that the current values violate in checker mode is not spelled out (tool-dependent). Keep checker classes free of `soft`, or switch those blocks off.

### Kata: illegal addresses three ways

Use the `bus_item` class from Make It Work. You need a test that sends unaligned addresses, without editing `bus_item`.

**Predict first.** For each approach below, write down: (1) does the call succeed, (2) are all addresses unaligned, (3) does the change affect other code that randomizes the same object or creates `bus_item` objects?

- (a) `item.c_align.constraint_mode(0);` then `item.randomize() with { addr[1:0] != 2'b00; }`, then `constraint_mode(1)`.
- (b) A derived class `unaligned_item` that redeclares `c_align`, randomized through a `bus_item` handle.
- (c) `item.randomize() with { addr[1:0] != 2'b00; }` with nothing else.

Then write all three in one `tb_top`, run each 8 times, count unaligned results, and print `PASS=<n> FAIL=<m>` with (c) expected to fail.

<details className="my-4 rounded-xl border border-border/70 p-3">
<summary className="cursor-pointer font-semibold">Show the worked solution</summary>

**Predictions.**
- (a) Succeeds; all unaligned. It affects only `item`, and only until `constraint_mode(1)` restores the block. Forgetting the restore would leak into the next user of `item`.
- (b) Succeeds; all unaligned. It affects only objects created as `unaligned_item`. In UVM a factory type override makes every `bus_item::type_id::create` return one, which is the point, and also the risk.
- (c) Fails on every call: the inline constraint is added to `c_align` and contradicts it (§18.7). The object keeps its previous values (§18.6.3).

```systemverilog
// compile: needs bus_pkg from Make It Work
module tb_top;
  import bus_pkg::*;
  bus_item       item, h;
  unaligned_item u;
  int            pass_n, fail_n, n_a, n_b, n_c_fail;

  initial begin
    item = new();
    u    = new();
    h    = u;

    item.c_align.constraint_mode(0);                       // (a)
    repeat (8) begin
      if (!item.randomize() with { addr[1:0] != 2'b00; }) $fatal(1, "(a) failed");
      if (item.addr[1:0] != 2'b00) n_a++;
    end
    item.c_align.constraint_mode(1);

    repeat (8) begin                                       // (b)
      if (!h.randomize()) $fatal(1, "(b) failed");
      if (h.addr[1:0] != 2'b00) n_b++;
    end

    repeat (8)                                             // (c): expected to fail
      if (!item.randomize() with { addr[1:0] != 2'b00; }) n_c_fail++;

    if (n_a == 8) pass_n++; else fail_n++;
    if (n_b == 8) pass_n++; else fail_n++;
    if (n_c_fail == 8) pass_n++; else fail_n++;
    $display("(a) %0d/8 (b) %0d/8 (c) failed %0d/8", n_a, n_b, n_c_fail);
    $display("PASS=%0d FAIL=%0d", pass_n, fail_n);
  end
endmodule
```
