## Quick Take

- **What it is:** The rest of IEEE 1800-2023 Clause 18 after [I-SV-2A](/curriculum/T2_Intermediate/I-SV-2A_Constrained_Randomization_Fundamentals/index). This module teaches four things. First, **conditional and array constraints**: rules that apply only in some cases (`->`, `if`/`else`) or to every element of an array (`foreach`, `size()`, `sum() with`, `unique`). Second, **run-time control**: switching variables and rules on and off, hooks that run around each call, and constraints replaced in a derived class. Third, **procedural randomization** outside classes (`std::randomize()`, `randcase`, `randsequence`). Fourth, **seeds**: why a run repeats, and why it stops repeating.
- **Why it matters:** Real protocol rules are conditional ("a wrapping burst has 2, 4, 8 or 16 beats") and per element ("no two outstanding tags are equal"). Every test needs to aim the same transaction class at a different corner without editing it. And a `randomize()` call that fails, or a failing seed that will not reproduce, can cost a team days. These skills turn the sequence items of milestone M2 into the shaped stimulus of milestone M4.
- **The Analogy:** A referee holds a rule book and judges each play against every rule at once, never reading the rules top to bottom. A rule that says "if it is a wrapping burst, it has a power-of-two length" can be satisfied by *not* being a wrapping burst. *Where it breaks:* IEEE 1800-2023 makes the referee read three chapters first: `randc` variables, array sizes, and the arguments of functions called in constraints. Those are decided before the rest, and that early decision can leave no legal answer even when one exists.

**You will be able to:**
1. **Predict** the legal values and the frequency of conditional constraints written with `->` and `if`/`else`, reading them as two-way Boolean rules rather than if-statements.
2. **Write** array constraints with `foreach`, `size()`, `sum() with`, `unique` and guards, and **predict** when array sizing or a function call makes `randomize()` fail.
3. **Configure** randomization at run time with `rand_mode()`, `constraint_mode()`, `pre_randomize()` and `post_randomize()`, a same-name constraint override in a derived class, and `randomize(null)`.
4. **Choose** between `std::randomize()`, `randcase` and `randsequence` for procedural stimulus, and write each one.
5. **Debug** a failing or irreproducible `randomize()`: isolate the conflicting constraints, check signedness and overridden constraints, and **explain** which code changes alter what a seed produces.

## Build Your Mental Model

**How to read this page.** This is the module's hub. The core path is the first three sections: the governing rule, what one `randomize()` call does, and the map of the four sub-lessons. Practitioner depth follows: how the pieces sit in a real testbench, and a symptom table for when an item goes wrong. Make It Work assembles one item that uses every technique of the module. Push Further holds the expert layer. Each sub-lesson then teaches its own topic in full.

**Words from I-SV-2A, in one line each.** A **random variable** is a class property declared `rand` or `randc`. A **constraint** is a Boolean expression over random variables, grouped in a named **constraint block**. The **solver** is the part of the simulator that finds values making every active constraint true. A **state variable** is any variable the solver may read but not change: the solver treats its current value as a constant. **Active** means switched on: every random variable and every constraint block starts active. This page also calls IEEE 1800-2023 the **LRM** (Language Reference Manual).

### The governing rule: one Boolean problem, solved together

Here is the smallest conditional constraint. Read `->` as "implies" (IEEE 1800-2023 §18.5.5).

```systemverilog
// snippet
class pair_item;
  rand bit       en;
  rand bit [1:0] v;
  constraint c_low { en -> v < 2; }  // implication: equivalent to !en || (v < 2)
endclass
```

**Predict before you read on.** On how many calls out of 300 is `en` equal to 1?

If you read the constraint like code ("pick `en`; if it is 1, then restrict `v`"), you would expect `en` to be 1 on about half the calls. The solver does not work that way. It looks at all eight `(en, v)` pairs, keeps those that make every constraint true, and picks one of the legal pairs, each with the same probability (§18.5.9). Trace it:

| `en` | `v` | `en -> v < 2` | Legal? |
|---|---|---|---|
| 0 | 0, 1, 2, 3 | true (the left side is false) | 4 legal pairs |
| 1 | 0, 1 | true | 2 legal pairs |
| 1 | 2, 3 | false | excluded |

Six pairs are legal and two of them have `en == 1`, so `en` is 1 on about 1 call in 3: about 100 of 300 calls, not 150.

Now call `randomize() with { v == 3; }`. Only `(0, 3)` is legal, so `en` is *forced to 0*. The rule pushed backward, from `v` to `en`. That is the governing rule of this whole module: **all active constraints form one Boolean problem, solved together, so every rule can constrain every variable it mentions.** An implication can be satisfied by making its left side false, and a narrow right side makes the left side rare. [Conditional and array constraints](/curriculum/T2_Intermediate/I-SV-2B_Advanced_Constrained_Randomization/advanced-constraints) teaches `->`, `if`/`else` and `foreach` on this model, with an interactive heatmap to experiment on.

**Two mistakes everyone makes first:**
- **Reading a constraint as a statement.** `en -> v < 2` is not "if `en`, then do something to `v`"; it is a fact that must hold. Nothing in a constraint block runs in order.
- **Expecting the implication to be checked after `en` is chosen.** The solver never "picks `en` and then fails". It only picks legal combinations, so the implication changes how often `en` is 1, not whether the call succeeds. The exceptions, where the standard does impose an order, are in [Expert: intermittent failures from LRM solve orders](#expert-intermittent-failures-from-lrm-solve-orders).

The same steps in words, with the clause for each:

1. **Hooks before.** `randomize()` first calls `pre_randomize()` on the object, then on every `rand` member object that is enabled (§18.6.2). A **hook** is a method the language calls for you; you override it to add your own steps.
2. **Collect the problem.** The solver gathers the active random variables and active constraints of the object and of every `rand` object member, which is how a constraint can reach into another object (a **global constraint**, §18.5.8). A variable switched off with `rand_mode(0)` becomes a state variable (§18.8). A block switched off with `constraint_mode(0)` is ignored (§18.9). Constraints from `randomize() with { … }` are added for this call only (§18.7).
3. **Solve.** All of it is one problem, solved together, with three exceptions that the standard orders: `randc` variables (§18.4.2), array sizes before the rules on elements (§18.5.7.1), and the arguments of functions called in constraints (§18.5.11). Each legal combination is equally likely unless `dist` or `solve…before` reshapes the odds (§18.5.3, §18.5.9).
4. **Success.** The solver assigns the new values, `post_randomize()` runs on the object and its enabled members, and the call returns 1 (§18.6.2).
5. **Failure.** The call returns 0. The random variables keep their previous values, and `post_randomize()` is not called; `pre_randomize()` has already run (§18.6.2, §18.6.3).

Steps 2 and 3 describe what the standard requires, not how a simulator implements it. Simulators use different solver engines (tool-dependent); the results they must produce are the same.

Three consequences follow, and each one is a classic mistake:
- **`post_randomize()` cannot fix this call.** It runs after the values are chosen. If it changes a knob that a constraint reads, only the *next* call sees the change.
- **An ignored return value hides a failure.** On failure, a newly created object still holds its default values, which look like data. Always write `if (!item.randomize()) $fatal(1, "…");`, as in I-SV-2A.
- **A rule you cannot see may be active.** A derived class can replace a base-class constraint of the same name (§18.5.2), and inline constraints add to the class rules. When a result surprises you, list every active constraint first.

### Run-time control in one table

You will meet five ways to change what a call produces without editing the class. The [controlling randomization](/curriculum/T2_Intermediate/I-SV-2B_Advanced_Constrained_Randomization/controlling-randomization) sub-lesson teaches each in depth.

| You want to… | Use | Effect | Clause |
|---|---|---|---|
| freeze one variable at its current value | `item.len.rand_mode(0);` | `len` becomes a state variable for later calls | §18.8 |
| switch off one rule | `item.c_len.constraint_mode(0);` | the solver ignores block `c_len` on later calls | §18.9 |
| add a rule for one call | `item.randomize() with { len > 4; }` | an extra constraint for this call only | §18.7 |
| replace a rule for a whole class of items | a derived class with a constraint of the **same name** | the derived block replaces the base block | §18.5.2 |
| check values without changing them | `item.randomize(null)` | returns 1 only if every active constraint holds now | §18.11.1 |

The fifth row is the **checker** form: no variable is random for that call, so `randomize()` only evaluates the constraints. Make It Work uses it to re-check every item.

### Practitioner: where these pieces live in a real testbench

In a UVM testbench, the class you randomize is a **sequence item**, a transaction that a **sequence** (a class that generates items) hands to a driver ([I-UVM-3A](/curriculum/T2_Intermediate/I-UVM-3A_Fundamentals/index)). The constraints of this module end up in four layers:

- **The item class holds the legal space.** Protocol rules (sizes, alignment, legal combinations) are named constraint blocks that are always active. Name every block: a test can switch off or replace only a named block.
- **The test aims the item.** It sets **knobs** (state variables that guarded constraints read), switches named blocks off, or swaps in a derived item class. In UVM the swap is a **factory override**, a registration that makes every `create` call build the derived class instead ([I-UVM-1B](/curriculum/T2_Intermediate/I-UVM-1B_The_UVM_Factory/index)).
- **The sequence narrows one call** with `randomize() with { … }` or `` `uvm_do_with ``. In uvm-core 2020.3.1 the `` `uvm_do `` macros report a failed `randomize()` only as a `UVM_WARNING` with id `RNDFLD` and still send the item, so a conflict there does not fail the test unless you promote that warning ([I-SV-2A](/curriculum/T2_Intermediate/I-SV-2A_Constrained_Randomization_Fundamentals/index#expert-randomization-failures-inside-uvm-macros) explains the macro).
- **The regression owns the seed.** A failing run is replayed with the same seed on the same code and the same simulator; [procedural randomization and seeds](/curriculum/T2_Intermediate/I-SV-2B_Advanced_Constrained_Randomization/randomization-methods) explains which edits break that, and [E-DBG-1](/curriculum/T4_Expert/E-DBG-1_Advanced_UVM_Debug_Methodologies/index) builds the regression workflow on it.

### When a randomized item goes wrong

Debugging starts from the symptom. Use this table to find the cause and the sub-lesson that fixes it.

| Symptom in the log | Likely cause | Where the fix is taught |
|---|---|---|
| `randomize()` returns 0 on every call | two or more active constraints contradict each other | [Solver debug](/curriculum/T2_Intermediate/I-SV-2B_Advanced_Constrained_Randomization/solver-debug): find the smallest conflicting set |
| `randomize()` returns 0 on some calls only, with nothing changed between calls | an order the standard imposes (array sizes, function arguments or `randc`) picked a dead end | [Expert: intermittent failures from LRM solve orders](#expert-intermittent-failures-from-lrm-solve-orders) |
| a value never appears in 10,000 calls, and nothing fails | an over-constraint removed it from the legal space: a coverage hole, not a failure | [Solver debug](/curriculum/T2_Intermediate/I-SV-2B_Advanced_Constrained_Randomization/solver-debug); measure with [I-SV-3A](/curriculum/T2_Intermediate/I-SV-3A_Functional_Coverage_Fundamentals/index) |
| a delay or length is negative | `rand int` is signed (§6.11.3), so `delay < 10` allows negative values | [Solver debug](/curriculum/T2_Intermediate/I-SV-2B_Advanced_Constrained_Randomization/solver-debug) |
| a `rand` dynamic array is never resized | no constraint on its `size()`, so `randomize()` keeps the old size (§18.4) | [Conditional and array constraints](/curriculum/T2_Intermediate/I-SV-2B_Advanced_Constrained_Randomization/advanced-constraints) |
| a base-class rule seems to be ignored | a derived class declared a constraint with the same name (§18.5.2) | [Controlling randomization](/curriculum/T2_Intermediate/I-SV-2B_Advanced_Constrained_Randomization/controlling-randomization) |
| the same seed gives different stimulus after a small code change | an object, thread or random call was added before existing ones, which shifts their seeds (§18.14.1) | [Procedural randomization and seeds](/curriculum/T2_Intermediate/I-SV-2B_Advanced_Constrained_Randomization/randomization-methods) |

- **Practitioner:** the item holds the legal space; tests aim it with knobs, `constraint_mode()`, derived classes or inline `with`; check every return value.

## Make It Work

### Worked example: one frame item, every technique

This example builds a frame for a made-up serial link: a frame kind plus a list of header options, each with a type code and a length. It uses one technique from each sub-lesson: an `if`/`else` rule, an implication that reads a knob, `foreach` with an index guard, `sum() with`, `unique`, a hook, a same-name override in a derived class, `randcase`, and `randomize(null)` as a checker. A procedural checker then re-checks every rule, so the constraints are never trusted to check themselves.

The package holds the item, the derived item and the checker:

```systemverilog
// compile
// frame_pkg.sv: the module's integrating example. Plain SystemVerilog, no UVM.
package frame_pkg;

  typedef enum bit [1:0] {DATA, ACK, PROBE} frame_kind_e;

  class frame_item;
    rand frame_kind_e kind;
    rand bit [2:0]    n_opt;           // number of header options
    rand bit [3:0]    opt_type[];      // one type code per option
    rand bit [7:0]    opt_len[];       // option lengths in bytes
    bit               allow_probe = 1; // test knob: a state variable, never random
    bit [7:0]         chk;             // XOR of the lengths: a stand-in for a CRC

    // Size rules. Array sizes are solved before element rules (§18.5.7.1).
    constraint c_size {
      n_opt inside {[1:7]};
      opt_type.size() == n_opt;
      opt_len.size()  == n_opt;
    }

    // if-else is two implications, and both are two-way Boolean rules,
    // not if-statements (§18.5.5, §18.5.6).
    constraint c_kind {
      if (kind == ACK) n_opt == 1;
      else             n_opt >= 2;
      !allow_probe -> (kind != PROBE);  // reads only the knob: a guard (§18.5.12)
    }

    // Element rules. The guard i > 0 keeps opt_len[i - 1] in bounds (§18.5.7.1).
    constraint c_opts {
      foreach (opt_len[i]) {
        opt_len[i] inside {[2:16]};
        opt_len[i] % 2 == 0;                      // whole 16-bit words
        if (i > 0) opt_len[i] <= opt_len[i - 1];  // longest option first
      }
      opt_len.sum() with (int'(item)) <= 40;  // int'() avoids an 8-bit sum (§18.5.7.2)
      unique {opt_type};                      // no option type twice (§18.5.4)
    }

    // Runs only after a successful solve (§18.6.2, §18.6.3).
    function void post_randomize();
      chk = opt_len.xor();
    endfunction
  endclass

  // A test-specific variant. The same name replaces the whole base c_kind
  // block, knob rule included; a new name adds a rule (§18.5.2).
  class probe_frame extends frame_item;
    constraint c_kind { kind == PROBE; n_opt >= 4; }
    constraint c_big  { opt_len.sum() with (int'(item)) >= 16; }
  endclass

  // Re-checks every rule with procedural code, independent of the constraints.
  // Returns "" for a legal item, otherwise the name of the broken rule.
  function automatic string check_item(frame_item it);
    probe_frame  pf;
    bit          is_probe;
    int unsigned total = 0;

    is_probe = $cast(pf, it);
    if (it.n_opt == 0) return "c_size n_opt";  // 3 bits, so 7 is the maximum anyway
    if (it.opt_type.size() != it.n_opt) return "c_size opt_type";
    if (it.opt_len.size() != it.n_opt)  return "c_size opt_len";
    if (is_probe) begin
      if (it.kind != PROBE || it.n_opt < 4) return "probe_frame c_kind";
    end else begin
      if (it.kind == ACK && it.n_opt != 1)     return "c_kind ACK";
      if (it.kind != ACK && it.n_opt < 2)      return "c_kind other";
      if (!it.allow_probe && it.kind == PROBE) return "c_kind knob";
    end
    foreach (it.opt_len[i]) begin
      if (it.opt_len[i] < 2 || it.opt_len[i] > 16) return "c_opts range";
      if (it.opt_len[i] % 2 != 0) return "c_opts even";
      if (i > 0 && it.opt_len[i] > it.opt_len[i - 1]) return "c_opts order";
      total += it.opt_len[i];
    end
    if (total > 40) return "c_opts sum";
    if (is_probe && total < 16) return "probe_frame c_big";
    foreach (it.opt_type[i])
      for (int j = i + 1; j < it.opt_type.size(); j++)
        if (it.opt_type[i] == it.opt_type[j]) return "c_opts unique";
    if (it.chk != it.opt_len.xor()) return "post_randomize";
    // The checker form: no variable is random, so it only evaluates every active
    // constraint against the current values (§18.11.1).
    if (!it.randomize(null)) return "randomize(null)";
    return "";
  endfunction

endpackage
```

The test module creates 1000 items, about one in four of them the derived class, and randomizes each through a base-class handle:

```systemverilog
// compile
// tb_top.sv: compile after frame_pkg.sv.
module tb_top;
  import frame_pkg::*;

  initial begin
    frame_item  item;
    probe_frame pf;
    string      why;
    int         n_pass, n_fail, n_probe_obj;
    int         n_kind[3];  // indexed by the frame_kind_e value

    for (int i = 0; i < 1000; i++) begin
      // randcase draws from this thread's generator: weights 3 to 1 (§18.16).
      randcase
        3: item = new();
        1: begin
          pf   = new();
          item = pf;                 // base handle, derived object
          n_probe_obj++;
        end
      endcase
      item.allow_probe = (i % 4 != 0);  // the knob: no PROBE on every fourth call

      // randomize() is virtual, so a derived object uses its own constraints
      // even through a base handle (§18.5.2).
      if (!item.randomize()) $fatal(1, "randomize() failed on call %0d", i);

      why = check_item(item);
      if (why == "") n_pass++;
      else begin
        n_fail++;
        $error("call %0d broke %s", i, why);
      end
      n_kind[item.kind]++;
    end

    $display("kinds: DATA=%0d ACK=%0d PROBE=%0d (probe_frame objects: %0d)",
             n_kind[DATA], n_kind[ACK], n_kind[PROBE], n_probe_obj);
    $display("PASS=%0d FAIL=%0d", n_pass, n_fail);
    $finish;
  end
endmodule
```

**Expected output** (illustrative, not from a simulator run). The `PASS` line is exact; the counts on the first line depend on the seed and on the simulator.

```text
kinds: DATA=418 ACK=72 PROBE=510 (probe_frame objects: 247)
PASS=1000 FAIL=0
```

**Reading the result.**
- **`PASS=1000 FAIL=0`** follows from the standard, whatever the seed: every element rule can hold for every option count the size stage can pick, so no call fails, and every item obeys every rule. If your run prints a `$fatal` or an `$error` line instead, you changed a rule; the rule name in the message tells you which.
- **About 250 `probe_frame` objects** because `randcase` picks the second branch with weight 1 of 4 (§18.16).
- **ACK is rare, and that is not a bug.** ACK allows one option count, while DATA and PROBE allow six each, and without `dist` or `solve…before` the solver favours no kind: it picks among legal combinations (§18.5.9). The exact share depends on how your simulator spreads its choices (see [Expert: what IEEE 1800-2023 leaves to the simulator](#expert-what-ieee-1800-2023-leaves-to-the-simulator)). A test that needs ACK must ask for it, with a knob, a `dist` (I-SV-2A) or an inline `with`; a coverpoint on `kind` shows the imbalance at once ([I-SV-3A](/curriculum/T2_Intermediate/I-SV-3A_Functional_Coverage_Fundamentals/index)).
- **`probe_frame` objects ignore the knob.** Their `c_kind` replaced the *whole* base `c_kind` block, including the line that reads `allow_probe`. Replacement works per block, not per line (§18.5.2). Put a rule that derived classes must keep in a block of its own.

### Run it

1. Put the two blocks in `frame_pkg.sv` and `tb_top.sv`.
2. Compile both files in one compilation, package first, with your simulator's SystemVerilog mode, and run `tb_top`.
3. Rerun with another seed. The `PASS` line must not change; the counts will. The seed option is simulator-specific (IEEE 1800 does not define one): check your simulator's documentation.
4. Open-source simulators support constrained randomization to different degrees (tool-dependent); this example was not checked on one.

### How to build a constrained item, step by step

1. **List the rules from the spec** in plain words, one per line, before writing any SystemVerilog.
2. **Give each rule a named constraint block**, grouped by what a test may want to switch off or replace (`c_size`, `c_kind`, `c_opts`). Unnamed rules cannot be switched off or overridden, and replacement takes a whole block.
3. **Write conditions as implications or `if`/`else`**, and predict how often each condition will hold: a narrow consequence makes its condition rare.
4. **Constrain every array size directly**, and make sure every element rule can hold for every legal size; sizes are decided first.
5. **Check widths**: cast with `int'()` inside `sum() with`, and use unsigned or bounded types for lengths and delays.
6. **Put test choices in knobs or derived classes**, never in edits to the shared item.
7. **Check every `randomize()` result**, and re-check the values with independent procedural code or `randomize(null)` while you develop the item.

## Push Further

### Expert: intermittent failures from LRM solve orders

The governing rule ("solved together") is the general rule of §18.3: when a solution exists, the solver finds one. IEEE 1800-2023 makes three exceptions. In each, some variables are decided first and become state variables for the rest, so an early choice can leave no solution even though another early choice would have worked.

| Order | What is decided first | The standard's warning | Clause |
|---|---|---|---|
| `randc` | `randc` variables, before `rand` variables | "this can sometimes cause randomize() to fail" | §18.4.2 |
| array sizes | `size()` of an array that also has `foreach` or reduction constraints | "This implicit ordering can cause the solver to fail in some situations" | §18.5.7.1, §18.5.7.2 |
| function arguments | random variables passed to a function called in a constraint | the "subdivision can cause the overall constraints to fail" | §18.5.11 |
| for contrast: `solve…before` | only the distribution changes | it "does not change the solution space and, therefore, cannot cause the solver to fail" | §18.5.9 |

**A traced size-first failure.**

```systemverilog
// snippet
rand bit [3:0] len;
rand bit [7:0] d[];
constraint c_len  { len inside {[1:10]}; }
constraint c_size { d.size() == len; }
constraint c_val  { foreach (d[i]) d[i] == i * 30; }  // last element: (len - 1) * 30
```

| Size chosen first | The element rule needs | Result |
|---|---|---|
| `len` = 1 … 9 | `d[len - 1]` = 0 … 240, which fits in 8 bits | success |
| `len` = 10 | `d[9]` = 270, which no 8-bit value equals | `randomize()` returns 0 |

If the size is picked uniformly from its 10 legal values, about one call in ten fails, although lengths 1–9 always work. Nothing is random about the bug: the size stage cannot see the element rules. The fix is to bound the size so that every element rule can hold (`len inside {[1:9]}`).

The signature of all three orders is a failure rate between 0 % and 100 % with nothing changed between calls. [Conditional and array constraints](/curriculum/T2_Intermediate/I-SV-2B_Advanced_Constrained_Randomization/advanced-constraints) shows how to remove each order, and [solver debug](/curriculum/T2_Intermediate/I-SV-2B_Advanced_Constrained_Randomization/solver-debug) turns the symptom into a triage procedure.

### Expert: what IEEE 1800-2023 leaves to the simulator

Clause 18 defines which results are legal and how they are distributed, not how a simulator finds them. Each item below is **tool-dependent**; the standard's own wording is cited where it exists.

| Question | What the standard says | Consequence |
|---|---|---|
| Which solver engine, how fast, and what it reports on failure | nothing: the clause defines results, not algorithms | run times, memory and failure messages differ between simulators; label any vendor option you document |
| Which other constraints join the array sizes in the first stage | §18.5.7.1 says size constraints are solved first; it does not list what else is solved with them | value frequencies, such as the kind counts in the worked example, can differ between simulators even when every result is legal |
| How often a function in a constraint is called | "an unspecified number of times (at least once) in an unspecified order" (§18.5.11) | a function that logs, counts or changes state behaves differently from tool to tool |
| The seed of a run | "The default seed is an implementation-dependent value" (§18.14.1); the saved generator state is an implementation-dependent string (§18.13.4) | a seed reproduces a run only on the same simulator, version and code; it does not transfer between tools |
| How to pass a seed on the command line | not defined by IEEE 1800 | every simulator names its own option; regression scripts must know the tool |

[Procedural randomization and seeds](/curriculum/T2_Intermediate/I-SV-2B_Advanced_Constrained_Randomization/randomization-methods) treats seeds across simulators in depth, and [conditional and array constraints](/curriculum/T2_Intermediate/I-SV-2B_Advanced_Constrained_Randomization/advanced-constraints) the performance of large array constraints.

### Kata: a storage write command

**Objective:** write an item with conditional, array and inherited constraints, predict its two traps, and prove it with a self-checking harness.

**Spec** (a made-up storage device):
- `mode` is `SEQ`, `SPLIT` or `TRIM`; `n_blk` (1 to 8) is the number of blocks; `blk_len[]` holds one length per block (`rand bit [7:0]`).
- R1: `blk_len` has `n_blk` elements.
- R2: `TRIM` uses exactly one block; `SPLIT` uses at most four.
- R3: every block is 4 to 64 bytes and a multiple of 4.
- R4: in `SEQ` mode, each block is longer than the one before.
- R5: the total of all blocks is at most 256 bytes.
- Then write `small_cmd`, a derived class that caps the total at 32 bytes by replacing R5's block.

**Predict first:**
1. Which rule needs an index guard, and why?
2. If you write R5 as `blk_len.sum() <= 256`, what goes wrong?
3. Does `small_cmd` ever fail? If it does, on which calls, and how do you fix it without weakening R4?

**Harness:** randomize 1000 `wr_cmd` and 1000 `small_cmd` objects, check every return value, re-check R1–R5 procedurally, and print `PASS=<n> FAIL=0`.

<details>
<summary>Worked solution (try the kata first)</summary>

```systemverilog
// compile
package wr_pkg;
  typedef enum bit [1:0] {SEQ, SPLIT, TRIM} wr_mode_e;

  class wr_cmd;
    rand wr_mode_e mode;
    rand bit [3:0] n_blk;
    rand bit [7:0] blk_len[];

    constraint c_size { n_blk inside {[1:8]}; blk_len.size() == n_blk; }  // R1
    constraint c_mode {                                                   // R2
      if (mode == TRIM)       n_blk == 1;
      else if (mode == SPLIT) n_blk <= 4;
    }
    constraint c_blk {                                                    // R3, R4
      foreach (blk_len[i]) {
        blk_len[i] inside {[4:64]};
        blk_len[i] % 4 == 0;
        if (i > 0) (mode == SEQ) -> (blk_len[i] > blk_len[i - 1]);
      }
    }
    constraint c_total { blk_len.sum() with (int'(item)) <= 256; }       // R5
  endclass

  class small_cmd extends wr_cmd;
    constraint c_total { blk_len.sum() with (int'(item)) <= 32; }  // replaces R5
    constraint c_small { (mode == SEQ) -> (n_blk <= 3); }         // keeps sizes feasible
  endclass
endpackage
```

1. **The index guard is R4.** It reads `blk_len[i - 1]`, which is out of bounds for `i = 0`. `if (i > 0)` involves only a loop variable, so it is a guard: no constraint is created for `i = 0` (§18.5.7.1, §18.5.12).
2. **`blk_len.sum() <= 256` constrains nothing.** Without `with`, the sum has the element type, `bit [7:0]` (§18.5.7.2), so it wraps and is always at most 255. A 300-byte command would pass. `with (int'(item))` sums at 32 bits.
3. **Without `c_small`, `small_cmd` fails on some SEQ calls.** Sizes are solved before the reduction (§18.5.7.2). Increasing multiples of 4 add up to at least 4 + 8 + 12 + 16 = 40 for four blocks, so any SEQ call whose size stage picks `n_blk` of 4 or more has no solution for the total of 32. If your simulator picks `(mode, n_blk)` uniformly in the size stage, that is 5 of the 13 legal pairs: roughly 38% of calls. `c_small` bounds the size directly, so every size the first stage can pick leaves a solution; three SEQ blocks need at least 4 + 8 + 12 = 24 bytes.

A harness in the style of the worked example (check every return value with `$fatal`, re-check each rule with procedural code, count) prints `PASS=1000 FAIL=0` for each class. Before you add `c_small`, the same harness stops on the first failing `small_cmd` call.

</details>
