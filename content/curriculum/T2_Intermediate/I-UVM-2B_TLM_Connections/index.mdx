## Quick Take
- **What it is:** Transaction-Level Modeling (TLM) is the UVM standard for moving objects between components without hardcoding pin wiggles.
- **Why it matters:** By decoupling *what* data is moving from *how* it's carried, you can swap drivers or scoreboards freely as long as they speak the same TLM contract.
- **The Analogy:** Think of TLM as pneumatic tubes in a pneumatic dispatch system. You define the tube shape (the TLM port) and drop the payload (the object); the infrastructure handles the delivery.

> **Retention Hook:** The port calls, the imp answers. `connect()` points from caller to implementer; the data may travel either way.

## Build Your Mental Model
### Three Types of TLM Connections
In typical UVM testbenches, you'll encounter three common TLM usage patterns:
1. **The Sequencer-Driver Handshake:** Bidirectional communication specifically designed for stimulus.
2. **Point-to-Point TLM (Put/Get/FIFO):** Used less frequently in modern environments, but standard blocking/non-blocking FIFO interfaces.
3. **The Analysis Fabric (Publish/Subscribe):** Used by monitors to fan-out data to 0-to-N listeners (scoreboards, coverage).

Three kinds of endpoint carry every connection:

| Symbol | Kind | Role | Example |
|---|---|---|---|
| ■ | **port** | Requires an interface: the caller. Calls `connect()`. | `drv.seq_item_port`, `scb.get_port` |
| ○ | **export** | Passes calls down to a child. Needs at least one imp below it. | `uvm_analysis_export` on a sub-env |
| ● | **imp** | Implements the methods. Always the end of a chain, never the caller of `connect()`. | `sqr.seq_item_export`, `fifo.analysis_export` |

Several handles named "export" are really imps: the sequencer's `seq_item_export`, a `uvm_subscriber`'s `analysis_export`, and the analysis FIFO's `analysis_export` and `get_export`.

### Sequencer ↔ Driver Handshake
Sequencers manage high-level intent, drivers translate that intent into pin-wiggles. Their protocol keeps stimulus moving.

```systemverilog
class my_driver extends uvm_driver#(my_txn);
  `uvm_component_utils(my_driver)

  function new(string name, uvm_component parent);
    super.new(name, parent);
  endfunction

  task run_phase(uvm_phase phase);

      seq_item_port.get_next_item(req); // Block until a sequence offers an item
      drive_transfer(req);              // Your task: translate to pins
      seq_item_port.item_done();        // Unblock the sequence's finish_item()
    end
  endtask
endclass

// In the agent's connect_phase: the driver's port is the caller
function void connect_phase(uvm_phase phase);
  drv.seq_item_port.connect(sqr.seq_item_export);
endfunction
```

### The Analysis Fabric (Publish/Subscribe)
Monitors reconstruct transactions and broadcast them. They use a `uvm_analysis_port`, and every connection from it must end at an imp that provides the `write()` function.

> **Connection rule:** An `analysis_port` may connect directly to an `analysis_imp`, or to an `analysis_export` that passes the calls down to an imp further inside a component. `uvm_subscriber::analysis_export` and `uvm_tlm_analysis_fifo::analysis_export` are themselves imps, so `ap.connect(cov.analysis_export)` is the everyday case. What is illegal is a chain that ends without an imp: an `analysis_export` must reach at least one imp by end of elaboration.

Watch one `ap.write(t)` below: predict when the monitor's next statement runs, then reorder the `connect()` calls and see whether the call order changes.

```systemverilog
// 1. The Broadcaster (Monitor)
class my_monitor extends uvm_monitor;
  `uvm_component_utils(my_monitor)
  uvm_analysis_port #(my_txn) ap;

  function new(string name, uvm_component parent);
    super.new(name, parent);
    ap = new("ap", this);
  endfunction

  task run_phase(uvm_phase phase);
    forever begin
      my_txn t = my_txn::type_id::create("t");  // a new item per transaction
      collect(t);                                // your task: sample the bus
      ap.write(t);                               // zero time: calls every subscriber's write()
    end
  endtask
endclass

// 2. The Subscriber (Scoreboard)
class my_scoreboard extends uvm_scoreboard;
  `uvm_component_utils(my_scoreboard)
  uvm_analysis_imp #(my_txn, my_scoreboard) item_imp;

  function new(string name, uvm_component parent);
    super.new(name, parent);
    item_imp = new("item_imp", this);
  endfunction

  // Must implement write(): a function, so it cannot wait
  virtual function void write(my_txn t);
    // compare t against the expected value; do not modify t
  endfunction
endclass

// 3. The Connection (Environment)
function void connect_phase(uvm_phase phase);
  agent.ap.connect(scb.item_imp);
endfunction
```

### One scoreboard, two inputs: `` `uvm_analysis_imp_decl ``

A class can have only one `write()` method, so a scoreboard with an expected stream and an actual stream needs two differently named write methods. The macro `` `uvm_analysis_imp_decl(SFX) `` declares an imp class whose `write()` calls `write<SFX>()` on your component:

```systemverilog
`uvm_analysis_imp_decl(_exp)
`uvm_analysis_imp_decl(_act)

class bridge_scoreboard extends uvm_scoreboard;
  `uvm_component_utils(bridge_scoreboard)
  uvm_analysis_imp_exp #(bus_item, bridge_scoreboard) exp_imp;
  uvm_analysis_imp_act #(pkt_item, bridge_scoreboard) act_imp;

  function new(string name, uvm_component parent);
    super.new(name, parent);
    exp_imp = new("exp_imp", this);
    act_imp = new("act_imp", this);
  endfunction

  function void write_exp(bus_item t);  /* predict and queue */  endfunction
  function void write_act(pkt_item t);  /* compare with queue */ endfunction
endclass

// env connect_phase
in_agt.ap.connect(scb.exp_imp);
out_agt.ap.connect(scb.act_imp);
```

## Decoupling the Scoreboard
`write()` is a **function**. An analysis port's `write()` calls each connected subscriber's `write()` one after another, inside the monitor's own process, all at the same simulation time. It has no buffer and no back-pressure: a subscriber cannot slow the monitor down, because a function cannot consume simulation time. A delay or a task call inside `write()` does not compile.

So when a subscriber needs to *wait* (for a DUT response, for the matching item on another stream, or for a clock), the waiting cannot live in `write()`. Insert a `uvm_tlm_analysis_fifo`:
1. The monitor's `analysis_port` connects to the FIFO's `analysis_export` (an imp). The FIFO's `write()` is a zero-time `try_put()` into an unbounded queue, so it always succeeds.
2. The scoreboard no longer implements `write()` for that stream. It runs a `forever` loop in its `run_phase`, calling `get()` (a task, which may block) through a `uvm_blocking_get_port` connected to the FIFO's `get_export`.
3. The queue now holds the backlog. Make sure it is empty before the test ends: keep an objection until the scoreboard is idle, or report leftovers in `check_phase`.

```systemverilog
class my_env extends uvm_env;
  `uvm_component_utils(my_env)
  my_agent                         agt;
  my_checker                       chk;      // has uvm_blocking_get_port #(my_txn) get_port
  uvm_tlm_analysis_fifo #(my_txn)  chk_fifo;

  function new(string name, uvm_component parent);
    super.new(name, parent);
  endfunction

  function void build_phase(uvm_phase phase);
    super.build_phase(phase);
    agt      = my_agent::type_id::create("agt", this);
    chk      = my_checker::type_id::create("chk", this);
    chk_fifo = new("chk_fifo", this);
  endfunction

  function void connect_phase(uvm_phase phase);
    agt.ap.connect(chk_fifo.analysis_export);
    chk.get_port.connect(chk_fifo.get_export);
  endfunction
endclass

// my_checker::run_phase
task run_phase(uvm_phase phase);
  my_txn t;
  forever begin
    get_port.get(t);          // blocks until the FIFO has an item
    wait_for_response(t);     // time-consuming work is legal here
    compare(t);
  end
endtask
```

## Make It Work
1. **Connect everything in `connect_phase`**: Ports exist after the `build_phase` completes. Bindings are resolved when `end_of_elaboration` starts; a `connect()` at or after that point is ignored with a "Late Connection" warning.
2. **Analysis Ports support 0-to-N connections**: You can wire an agent's `analysis_port` to an `analysis_imp` on a subscriber, a FIFO for a scoreboard, and a logger simultaneously. Most other ports (put, get, and exports) need at least one connection, or end of elaboration reports "connection count of 0 does not meet required minimum of 1" and stops the run.
3. **Use FIFOs when the consumer must wait**: Put a `uvm_tlm_analysis_fifo` in front of any subscriber that needs task context (waiting, pairing two streams, timing).
4. **Be careful with references**: Items passed via TLM are handles, and every subscriber receives the same object. Create a new item per transaction in the monitor, never modify an item inside `write()`, and `clone()` anything you need to change or store.
5. **Never rely on subscriber order**: The standard promises no order for the `write()` calls. (The reference implementation happens to call them sorted by the imps' full names, not in `connect()` order.)

## Interview Pitfalls
**Missing the `connect_phase` Hierarchy Rule:**
Connections cross one level of hierarchy at a time:
- **port → port goes up**: a child's port connects to its parent's port (`mon.ap.connect(ap)` inside the agent).
- **port → export or imp goes across**: between siblings, written in their common parent's `connect_phase` (`agt.ap.connect(scb.item_imp)` in the env).
- **export → export or imp goes down**: a parent's export connects to a child's export or imp (`analysis_export.connect(scb.item_imp)` inside a sub-env).

UVM checks these levels only as *warnings*, and only when `check_connection_relationships` is set; analysis ports skip the check. What it always enforces is direction: an imp can never call `connect()`, and an export can never connect to a port.

**Missing `item_done()`:**
Interviewers will present a testbench that runs exactly one transaction and hangs. If the driver loops but never calls `item_done()`, the sequence blocks forever waiting for acknowledgment.
