## Quick Take

- **What it is:** **Transaction-level modeling (TLM)** is how UVM components pass whole transaction objects to each other by calling methods such as `put()`, `get()` and `write()`, instead of driving signals. A component makes the call through a **port**; the call travels along `connect()` bindings, sometimes through an **export**, and ends at an **imp** in another component that implements the method. A **TLM FIFO** stores items between a producer and a consumer that run at different speeds (IEEE 1800.2-2020 §12.2).
- **Why it matters:** Ports keep components independent. A monitor publishes what it saw without knowing who listens, so the same agent works in a block-level bench and in a system-on-chip (SoC) bench. Most "silent scoreboard" and "test hangs" bugs in real benches are wiring bugs: a connection made backwards, a connection forgotten, a slow check in the wrong place, or one object shared by every listener.
- **The Analogy:** An office phone system. A port is a handset: it can only place calls. An imp is the desk that answers and does the work. An export is a reception desk that forwards calls to a desk further inside the building. The extensions are wired once before the office opens, in `connect_phase`, and tested at opening time, at the start of end of elaboration (both are UVM phases, the fixed steps every test runs through, from [I-UVM-1C](/curriculum/T2_Intermediate/I-UVM-1C_UVM_Phasing/index)). An analysis port is the office public-address system: one announcement reaches every speaker that is wired in, even none, and the announcer never waits for a listener. *Where it breaks:* a phone call carries a copy of your voice, but a TLM call passes a **handle** to one object, so every listener reads, and could scribble on, the same sheet of paper. And a TLM call has no transit time: `write()` reaches every listener at the same simulation time. Only a FIFO adds storage, like an in-tray between two desks.

> **Retention Hook:** The port calls, the imp answers. `connect()` points from the caller toward the implementer, one level of hierarchy at a time; the data may travel either way.

**You will be able to:**
1. Explain the roles of port, export and imp, write legal `connect()` calls (port to parent port, port to sibling export or imp, export to child export or imp), and predict whether a wiring mistake is a compile error, a UVM error at end of elaboration, or silently legal.
2. Predict what an analysis port's `write()` does (a zero-time function call to each of 0..N subscribers, all sharing one object, with no back-pressure, meaning no way for a subscriber to make the caller wait) and choose between a direct imp, `` `uvm_analysis_imp_decl `` and `uvm_tlm_analysis_fifo`.
3. Write a two-input scoreboard, with two imps or with two analysis FIFOs and a `get()` thread, that reports leftover items at the end of the test.
4. Use blocking and nonblocking put, get and peek ports with a `uvm_tlm_fifo`, and predict when `put()` and `get()` block for a given FIFO size.
5. Debug unconnected, reversed and over-connected ports from the end-of-elaboration log, and items modified after `write()`.

## Build Your Mental Model

### Why components talk through ports

From [I-UVM-2A](/curriculum/T2_Intermediate/I-UVM-2A_Component_Roles/index) you know the roles: a **monitor** turns pin activity into transaction objects, a **scoreboard** checks them, and a **coverage collector** records which values were seen. These are **components**: long-lived `uvm_component` objects arranged in a parent-child tree ([I-UVM-1A](/curriculum/T2_Intermediate/I-UVM-1A_Components/index)). A **transaction** (or **item**) is a short-lived `uvm_object` that holds one bus operation, and a variable that refers to an object is a **handle** ([I-SV-1](/curriculum/T2_Intermediate/I-SV-1_OOP/copying-and-cloning)).

The obvious way to pass an item is a direct call: the monitor holds a handle to the scoreboard and calls `scb.check(t)`. That welds the monitor to one scoreboard class. The agent can no longer be reused in a bench that has a different scoreboard, two scoreboards, or none. TLM puts a small object between the two sides. The monitor owns a port and calls `ap.write(t)`. Someone else, usually the parent environment, decides in `connect_phase` where that call goes.

Two phases from [I-UVM-1C](/curriculum/T2_Intermediate/I-UVM-1C_UVM_Phasing/index) matter here. In **`connect_phase`** every component wires its children together, after `build_phase` has created them all. At the start of **end of elaboration** (`end_of_elaboration_phase`, the phase after `connect_phase`) UVM **resolves** the bindings: it follows every chain of connections to the imps at its end and checks the counts. From then on the wiring is fixed.

This lesson is about the TLM-1 classes in §12.2, which every UVM bench uses. TLM-2 (§12.3), used mainly to connect SystemC models, appears only in [Push Further](#expert-tlm-2-in-one-page).

### The three endpoints: port, export, imp

Every connection is made of these three kinds of endpoint. The symbols match the diagrams and visuals on this site.

| Symbol | Kind | What it does | Who calls `connect()` | Examples |
|---|---|---|---|---|
| ■ | **port** | *Requires* an interface. The owning component calls methods through it. | A port calls `connect()` toward its provider. | `drv.seq_item_port`, `mon.ap`, `prod.put_port` |
| ○ | **export** | *Forwards* an interface. It lets an outside port reach an imp inside the component that owns it. | An export calls `connect()` toward the export or imp below it. | `uvm_analysis_export` on a scoreboard or sub-environment |
| ● | **imp** | *Implements* the interface. It calls the method of the component passed to its constructor. | Never. An imp is always the end of a chain. | `uvm_analysis_imp`, `fifo.put_export` |

Several handles named "export" are really imps, so read the class, not the name. The sequencer's `seq_item_export` is a `uvm_seq_item_pull_imp`. A `uvm_subscriber`'s `analysis_export` is a `uvm_analysis_imp`, and its instance name in logs is `analysis_imp`. A TLM FIFO's `put_export`, `get_export` and `analysis_export` are imps too (uvm-core 2020.3.1, `uvm_sequencer.svh`, `uvm_subscriber.svh`, `uvm_tlm_fifo_base.svh`).

**The methods.** All TLM-1 endpoints share one method set, declared in `uvm_tlm_if_base` (§12.2.4). Each port class enables a subset of it.

| Method | Kind | Behaviour | Port classes that provide it |
|---|---|---|---|
| `put(t)` | task | may block until the provider accepts `t` | `uvm_blocking_put_port`, `uvm_put_port` |
| `get(t)` | task | may block until an item is available, then removes it | `uvm_blocking_get_port`, `uvm_get_port`, `uvm_blocking_get_peek_port`, `uvm_get_peek_port` |
| `peek(t)` | task | like `get`, but leaves the item in place | `uvm_blocking_peek_port`, `uvm_peek_port`, `uvm_blocking_get_peek_port`, `uvm_get_peek_port` |
| `try_put(t)`, `try_get(t)`, `try_peek(t)` | function returning `bit` | never blocks; returns 0 if it could not complete | the `uvm_nonblocking_*` ports and the combined `uvm_put_port`, `uvm_get_port`, `uvm_peek_port`, `uvm_get_peek_port` |
| `can_put()`, `can_get()`, `can_peek()` | function returning `bit` | asks without doing anything | the same nonblocking and combined ports |
| `write(t)` | function | delivers `t` and returns at once | `uvm_analysis_port` |

The pattern is `uvm_<blocking_|nonblocking_|>` + `<put|get|peek|get_peek>` + `_port`, `_export` or `_imp`. A **task** may consume simulation time; a **function** returns in zero time and cannot wait (IEEE 1800-2023 §13.4). That one difference explains most of this lesson.

Because every TLM-1 port class extends `uvm_port_base #(uvm_tlm_if_base #(T,T))`, the compiler lets you call any of these methods through any port. Calling `peek()` through a `uvm_get_port` compiles, then reports `UVM_ERROR [peek] UVM TLM interface task not implemented` at run time (uvm-core 2020.3.1, `uvm_tlm_ifs.svh`, `uvm_ports.svh`). Pick the port class that names every method you call.

**Predict, then step.** The driver-to-sequencer link is the most common connection in UVM, and it shows the rule best. The driver's `seq_item_port` is a port and the sequencer's `seq_item_export` is an imp. Choose each `connect_phase` line below, predict which way the item travels and what happens, then step through it.

What the stepper showed:
- **Call direction is not data direction.** The driver's port *calls* `get_next_item(req)` into the sequencer, and the item comes *back* as the call's output argument. `connect()` always follows the call: requirer `.connect(` provider `)`.
- **Backwards is a run-time UVM error, not a compile error.** Both ends have the same type, so `sqr.seq_item_export.connect(drv.seq_item_port)` compiles. `connect()` itself refuses any call made on an imp, and the error stops the run at end of elaboration.
- **Some ports may stay unconnected.** `uvm_seq_item_pull_port` is built with a minimum of 0 connections (§15.2.2.1), so a forgotten driver connection is not caught at end of elaboration. You get only a `DRVCONNECT` warning, then a null-object error at the first `get_next_item()`.

That is all this lesson needs from the sequencer-driver link: it is a TLM pull connection like any other. The handshake itself (`get_next_item`, `item_done`, responses) belongs to [I-UVM-3A](/curriculum/T2_Intermediate/I-UVM-3A_Fundamentals/index), which comes two lessons later.

### Connection rules: one level at a time

`connect()` is called on the requiring side and given the providing side. Each call crosses at most one level of hierarchy, and each form has its place:

| Form | Direction | Written in | Example |
|---|---|---|---|
| port `.connect(` port `)` | **up**: child's port to its parent's port (promotion) | the parent's `connect_phase` | `mon.ap.connect(ap);` inside the agent |
| port `.connect(` export or imp `)` | **across**: between siblings | their common parent's `connect_phase` | `agt.ap.connect(scb.item_imp);` inside the env |
| export `.connect(` export or imp `)` | **down**: parent's export to its child's export or imp | the parent's `connect_phase` | `exp_export.connect(exp_fifo.analysis_export);` inside the scoreboard |

Two directions are always illegal and always reported: an imp calling `connect()`, and an export connecting to a port (uvm-core 2020.3.1, `uvm_port_base.svh`, `connect()`; §5.5.2.14). Type mismatches are caught even earlier: connecting a `uvm_analysis_port #(bus_item)` to an imp of another item type does not compile, because `connect()` takes an argument of the port's own base type.

**When connections are checked.** Make connections in `connect_phase`. At the start of end of elaboration, `resolve_bindings()` follows every chain to its imps and compares the number of imps reached with the endpoint's minimum and maximum (§5.5.2.15):

| Endpoint | Minimum imps | Maximum imps | Unconnected means |
|---|---|---|---|
| put, get and peek ports (and their exports) | 1 | 1 | `UVM_ERROR`, then the run stops |
| `uvm_analysis_port` | 0 | unbounded | legal: `write()` reaches nobody |
| `uvm_analysis_export` | 1 | unbounded | `UVM_ERROR`, then the run stops |
| `uvm_seq_item_pull_port` (driver) | 0 | 1 | legal at elaboration; fails at run time |
| any imp | 1 | 1 | an imp counts itself, so never an error |

Sources: uvm-core 2020.3.1, `uvm_tlm_imps.svh` (`UVM_PORT_COMMON`, `UVM_EXPORT_COMMON`, `UVM_IMP_COMMON`, `UVM_SEQ_PORT`) and `uvm_analysis_port.svh`.

A count error is reported as `UVM_ERROR [Connection Error]`. Right after resolving, `uvm_root` checks the error count and, if any `UVM_ERROR` has been reported so far, stops with `UVM_FATAL [BUILDERR] stopping due to build errors` before `run_phase` begins (uvm-core 2020.3.1, `uvm_root.svh`). A `connect()` made at or after end of elaboration is ignored with a `[Late Connection]` warning. `connect()` is also legal earlier, in the parent's `build_phase` after it creates the child, but only for ports the child created in its constructor, because the child's own `build_phase` has not run yet. `connect_phase` avoids that trap.

**The one-level rule is only a convention in practice.** uvm-core checks the up, across and down forms, but the resulting `[Connection Warning]` is switched off unless you enable it (see [Push Further](#expert-relationship-checks-are-off-by-default)), and analysis ports skip the check entirely. The rule still matters: it is what keeps each component's insides private.

**Silently legal: the reversed promotion.** Inside the agent, `ap.connect(mon.ap)` instead of `mon.ap.connect(ap)` passes every check. Both ends are ports, so there is no direction error; analysis ports skip the relationship check; and `mon.ap` now reaches 0 imps, which its minimum of 0 allows. The monitor's `write()` goes nowhere and the scoreboard reports zero errors. Only a check of how many items arrived catches it, which is why the worked example's scoreboard counts.

So for any wiring mistake, ask three questions in order:
1. Do the two ends have compatible types? If not: **compile error**.
2. Is the direction illegal (imp calls `connect()`, export connects to a port), the interface incomplete, or a count outside its limits? If so: a **UVM error**, reported when `connect()` runs or when the bindings are resolved, and the run stops with `BUILDERR` at the start of end of elaboration.
3. Otherwise it is **silently legal**, however wrong, and only the data flow reveals it.

### Point-to-point: put, get, peek and `uvm_tlm_fifo`

Some connections have exactly one producer and one consumer, which run at their own pace. A **predictor** (a component that computes the expected result) feeding a **reference model**, a model feeding a checker, and two threads inside one component are common examples. For these, put a **`uvm_tlm_fifo #(T)`** between them (§12.2.8.2). It is a `uvm_component` that wraps a SystemVerilog `mailbox` ([I-SV-5](/curriculum/T2_Intermediate/I-SV-5_Synchronization_and_IPC/mailboxes)), so the same blocking rules apply:

- `put()` blocks while the FIFO is full; `get()` and `peek()` block while it is empty.
- `try_put()` returns 0 instead of blocking when the FIFO is full; `try_get()` and `try_peek()` return 0 when it is empty.
- The constructor is `new(string name, uvm_component parent = null, int size = 1)`. **The default size is 1**, and size 0 means unbounded (uvm-core 2020.3.1, `uvm_tlm_fifos.svh`). This is the opposite of `mailbox::new()`, which is unbounded by default.
- `used()`, `is_empty()`, `is_full()` and `size()` tell you its state; `flush()` empties it.

The producer connects a put port to the FIFO's `put_export`, and the consumer connects a get port to its `get_export` (or `get_peek_export`, if it also peeks). Both are siblings of the FIFO, so both connections are "across" and are written in the parent:

```systemverilog
// snippet: one producer, one consumer, one FIFO in the parent env
// prod declares:  uvm_blocking_put_port #(bus_item) put_port;
// cons declares:  uvm_get_peek_port     #(bus_item) get_port;  // get, peek and try_*
uvm_tlm_fifo #(bus_item) f;

function void build_phase(uvm_phase phase);
  super.build_phase(phase);
  prod = bus_producer::type_id::create("prod", this);
  cons = bus_consumer::type_id::create("cons", this);
  f    = new("f", this);                       // size 1: the default
endfunction

function void connect_phase(uvm_phase phase);
  prod.put_port.connect(f.put_export);         // port -> sibling imp
  cons.get_port.connect(f.get_peek_export);    // port -> sibling imp
endfunction
```

**Nonblocking forms.** Use them when a component must not wait, for example to sample a FIFO once per clock, or inside a function:

```systemverilog
// snippet: a consumer that must not block (its port is a uvm_get_peek_port)
bus_item t;
if (get_port.try_get(t))                       // 1: got one; 0: FIFO was empty
  check_item(t);
if (!get_port.can_peek())                      // ask first, take nothing
  `uvm_info("CONS", "nothing waiting this cycle", UVM_HIGH)
```

**Where you meet it.** Inside agents, stimulus normally flows through the sequencer instead ([I-UVM-3A](/curriculum/T2_Intermediate/I-UVM-3A_Fundamentals/index)). Point-to-point FIFOs appear between analysis-side components: a predictor and a reference model, a model and its checker, or a transaction-level model of the design. Choose the size on purpose. Size 1 couples the two sides tightly; size 0 never blocks the producer but can grow without limit if the consumer stops.

### The analysis fabric: `write()` to 0..N subscribers

A monitor must never wait for its listeners, because the bus does not wait for the monitor. So monitors publish through a **`uvm_analysis_port`**, whose only method is a function:

- `ap.write(t)` calls the `write()` of every imp the port reaches, one after another, inside the monitor's own **process** (its running thread), at the same simulation time (§12.2.10.1).
- There may be **0, 1 or many subscribers**. With none, `write()` does nothing, and that is legal.
- There is **no buffer and no back-pressure**. Every subscriber's `write()` is a function, so none of them can consume time, and `ap.write(t)` returns, in zero simulation time, as soon as the last one returns.
- Every subscriber receives **the same handle `t`**, not a copy.

A **subscriber** is any component that receives `write()` calls. UVM provides a base class for the common case of one input, **`uvm_subscriber #(T)`** (§13.9). It already contains `analysis_export`, a `uvm_analysis_imp` whose instance name is `analysis_imp`, and declares `pure virtual function void write(T t)`, which you must implement. A coverage collector is the textbook subscriber. The covergroup syntax is from [I-SV-3A](/curriculum/T2_Intermediate/I-SV-3A_Functional_Coverage_Fundamentals/index).

```systemverilog
// snippet: the monitor publishes; a scoreboard and a coverage subscriber listen
// bus_monitor (from I-UVM-2A):
//   uvm_analysis_port #(bus_item) ap;
//   t = bus_item::type_id::create("t");  ap.write(t);   // a new t per transaction

class bus_scoreboard extends uvm_scoreboard;
  `uvm_component_utils(bus_scoreboard)
  uvm_analysis_imp #(bus_item, bus_scoreboard) item_imp;   // calls this->write()

  function new(string name, uvm_component parent);
    super.new(name, parent);
    item_imp = new("item_imp", this);                       // imps take their owner
  endfunction

  function void write(bus_item t);       // a function: it must return without waiting
    // compare t with the expected value; never modify t
  endfunction
endclass

class bus_cov extends uvm_subscriber #(bus_item);
  `uvm_component_utils(bus_cov)

  covergroup data_cg with function sample(bit [7:0] data);
    coverpoint data { bins low = {[8'h00:8'h7F]}; bins high = {[8'h80:8'hFF]}; }
  endgroup

  function new(string name, uvm_component parent);
    super.new(name, parent);
    data_cg = new();
  endfunction

  // Overrides uvm_subscriber's pure virtual write(T t). The argument must keep
  // the name t: overrides need identical argument names (IEEE 1800-2023 §8.20).
  function void write(bus_item t);
    data_cg.sample(t.data);
  endfunction
endclass

// bus_env::connect_phase: one port, two subscribers
agt.ap.connect(scb.item_imp);
agt.ap.connect(cov.analysis_export);     // analysis_export is an imp
```

What the trace showed:
- The monitor's next statement runs at 10 ns, **after all three `write()` calls have returned**. Nothing runs in parallel, and no simulation time passes.
- The order did not follow the `connect()` order. uvm-core stores the imps in an associative array indexed by full name and calls them in that (lexicographic) order, so `cov` runs before `log`, and `log` before `scb` (uvm-core 2020.3.1, `uvm_port_base.svh`; IEEE 1800-2023 §7.8.2). - With the bug ticked, `scb` reports a mismatch. `cov` ran first and changed the one shared object, so `log` and `scb` saw the cleared field. That is why the `uvm_analysis_imp` documentation says `write()` "must not modify the value passed to it" (uvm-core 2020.3.1, `uvm_analysis_port.svh`).

### One object, every subscriber: copy before you modify

Because `write()` passes a handle, the monitor and every subscriber refer to **one object**. Two rules follow.

**Rule 1: the publisher creates a new object for every transaction.** Here is what goes wrong when a monitor creates its item once, before the loop, and a scoreboard stores the handles it receives:

```systemverilog
// snippet: the bug, a monitor that reuses one object
bus_item t = bus_item::type_id::create("t");   // created once
forever begin
  @(vif.mon_cb iff vif.mon_cb.valid);
  t.data = vif.mon_cb.data;                    // overwrites the same object
  ap.write(t);                                 // scb does: exp_q.push_back(t);
end
```

Trace three transfers carrying data `11`, `22` and `33`:

| After `write` number | The one object `t` holds | `scb.exp_q` holds | What `scb` reads from `exp_q` |
|---|---|---|---|
| 1 | `data=11` | 1 handle to `t` | `11` |
| 2 | `data=22` | 2 handles to `t` | `22, 22` |
| 3 | `data=33` | 3 handles to `t` | `33, 33, 33` |

Every stored item equals the last one. Move `create` inside the loop and the queue holds three objects, `11, 22, 33`. The monitor code in [I-UVM-2A](/curriculum/T2_Intermediate/I-UVM-2A_Component_Roles/index) already does this.

**Rule 2: a subscriber that needs a changed version works on a copy.** A scoreboard that predicts the expected output, or a component that must edit a field, clones first:

```systemverilog
// snippet: predict on a copy, never on the received object
bus_item pred;
if (!$cast(pred, t.clone()))                   // clone() returns a uvm_object
  `uvm_fatal("SCB", "clone() did not return a bus_item")
pred.data = t.data + 8'd1;                     // t itself is unchanged
```

`clone()` needs the item to implement `do_copy()` (or field macros); [I-SV-1](/curriculum/T2_Intermediate/I-SV-1_OOP/copying-and-cloning) covers shallow and deep copies. Storing a received handle without copying is safe only while every publisher follows rule 1. A scoreboard that stores items for later can clone them as cheap insurance, which is what this site's code style asks for.

### Decoupling a slow subscriber with `uvm_tlm_analysis_fifo`

`write()` is a function, so a subscriber cannot wait inside it, directly or by calling a task: either is a compile error (IEEE 1800-2023 §13.4 a and b). Yet many checks must wait, for a response from the design under test (DUT), for the matching item on another stream, or for a clock edge.

**Predict.** A new subscriber, `chk`, must wait about 25 ns for the DUT's response before it can check each item, and the monitor writes an item every 10 ns. Where can that waiting go? Answer in the visual, then compare the three implementations and move the end of the test.

<AnalysisBroadcastVisualizer section="slow" />

**Debrief.** The waiting must live in a thread that `chk` owns, fed by a **`uvm_tlm_analysis_fifo #(T)`** (§12.2.8.3):
1. The monitor's analysis port connects to the FIFO's `analysis_export` (an imp). The FIFO is always unbounded, and its `write()` is `void'(try_put(t))`, which therefore always succeeds in zero time (uvm-core 2020.3.1, `uvm_tlm_fifos.svh`).
2. The subscriber no longer implements `write()`. Its `run_phase` loops on `get()`, a task that blocks until the FIFO holds an item, and may then wait as long as it needs.
3. The FIFO now holds the backlog, so the test must not end while it is non-empty. Keep the test's **objection** (the "still busy" vote from I-UVM-1C) raised until the checker is idle, and report anything left over in `check_phase`, the phase after `run_phase` that exists for end-of-test checks. The visual's 45 ns end showed the items that are silently lost otherwise.

| Choose | When |
|---|---|
| a direct `uvm_analysis_imp` (or `uvm_subscriber`) | the work fits in zero time: sampling coverage, logging, an in-order compare against a queue |
| `` `uvm_analysis_imp_decl `` | one component needs two or more zero-time `write` methods (next section) |
| `uvm_tlm_analysis_fifo` plus a `get()` thread | the subscriber must wait, or must pair items that arrive at different times |

### Two-input scoreboards

A scoreboard usually compares two streams: **expected** items (from the input-side monitor, through a predictor) and **actual** items (from the output-side monitor). A class has only one method named `write`, so two plain `uvm_analysis_imp #(bus_item, bus_scoreboard)` members would both call the same `write()`, and the scoreboard could not tell which stream an item came from. There are two standard fixes.

**Fix A: `` `uvm_analysis_imp_decl ``** (Annex B.5.22). `` `uvm_analysis_imp_decl(_exp) `` declares a new class, `uvm_analysis_imp_exp`, whose `write()` calls `write_exp()` on its owner. Invoke the macro outside any class, once per suffix in a given scope.

```systemverilog
// snippet: two inputs with imp_decl (the kata in Practice builds the full version)
`uvm_analysis_imp_decl(_exp)                 // declares class uvm_analysis_imp_exp
`uvm_analysis_imp_decl(_act)                 // declares class uvm_analysis_imp_act

class bridge_scoreboard extends uvm_scoreboard;
  `uvm_component_utils(bridge_scoreboard)
  uvm_analysis_imp_exp #(bus_item, bridge_scoreboard) exp_imp;   // calls write_exp()
  uvm_analysis_imp_act #(bus_item, bridge_scoreboard) act_imp;   // calls write_act()
  bus_item exp_q[$];
  // new(): exp_imp = new("exp_imp", this); act_imp = new("act_imp", this);
  function void write_exp(bus_item t);  /* queue a copy of t      */ endfunction
  function void write_act(bus_item t);  /* pop, compare and count */ endfunction
endclass

// bus_env::connect_phase
in_agt.ap.connect(scb.exp_imp);
out_agt.ap.connect(scb.act_imp);
```

**Fix B: two analysis FIFOs and a `get()` thread.** The scoreboard owns two `uvm_tlm_analysis_fifo`s and one `run_phase` loop that takes one item from each and compares them. The scoreboard can wait for whichever stream is late, and it can be given time-consuming checks later without rewiring. To keep its FIFOs private, the scoreboard exposes two `uvm_analysis_export`s and connects each **down** to its FIFO. uvm-core's own `uvm_sequencer` uses the same pattern: its `rsp_export` is an analysis export connected down to an internal analysis FIFO (uvm-core 2020.3.1, `uvm_sequencer_param_base.svh`). The Make It Work example builds this version completely.

**How to choose.** Start with Fix A when both streams arrive in order and every check is zero-time. Use Fix B when a check must wait, when items on the two streams arrive far apart, or when you expect the scoreboard to grow. Matching algorithms for out-of-order and keyed streams belong to [A-UVM-6](/curriculum/T3_Advanced/A-UVM-6_Scoreboards_and_Reference_Models/index).

**Pitfalls of `` `uvm_analysis_imp_decl ``:**
- It expands to a class declaration at the point where you invoke it. Invoke it at package or file scope, before the class that uses it, so that one declaration serves every component in the package.
- The same suffix invoked twice in one scope (one package, or `$unit`) declares the same class twice, which does not compile. Two verification IP (VIP) packages that each declare `_exp` are fine on their own, but a file that wildcard-imports both packages and then uses `uvm_analysis_imp_exp` meets an ambiguous name. Prefix suffixes with the component name (`_scb_exp`).
- Name the write methods after the suffix exactly: `_exp` needs `write_exp()`.

### Recap

- Ports call, imps implement, exports forward. `connect()` goes from the caller toward the implementer, one level at a time: up (port to port), across (port to export or imp), down (export to export or imp).
- Bindings are made in `connect_phase` and resolved at the start of end of elaboration. Count errors stop the run with `BUILDERR`; unconnected analysis ports, reversed analysis promotions and unconnected driver ports are silent there.
- `uvm_tlm_fifo` holds 1 item by default and gives back-pressure; `uvm_tlm_analysis_fifo` is unbounded and never blocks the writer.
- Analysis `write()` is a zero-time function call to 0..N subscribers in an order you must not rely on, and all of them share one object. Publish a new object per transaction and copy before you modify.
- A subscriber that must wait goes behind an analysis FIFO, and an end-of-test check proves its FIFO drained.

### Worked example: a transaction-level bench with every connection kind

// compile
// tlm_demo.sv: compile with the UVM 1800.2 library (uvm-core 2020.3.1), top tb_top.
`include "uvm_macros.svh"

package tlm_demo_pkg;
  timeunit 1ns; timeprecision 1ps;     // must precede every other package item
  import uvm_pkg::*;

  // ---------------------------------------------------------------- item
  class bus_item extends uvm_sequence_item;
    `uvm_object_utils(bus_item)
    bit [7:0] addr;
    bit [7:0] data;

    function new(string name = "bus_item");
      super.new(name);
    endfunction

    function void do_copy(uvm_object rhs);   // clone() relies on this
      bus_item rhs_;
      if (!$cast(rhs_, rhs)) `uvm_fatal("COPY", "do_copy: rhs is not a bus_item")
      super.do_copy(rhs);
      addr = rhs_.addr;
      data = rhs_.data;
    endfunction

    function bit do_compare(uvm_object rhs, uvm_comparer comparer);
      bus_item rhs_;
      if (!$cast(rhs_, rhs)) return 0;
      return super.do_compare(rhs, comparer) && addr == rhs_.addr && data == rhs_.data;
    endfunction

    function string convert2string();
      return $sformatf("addr=%02h data=%02h", addr, data);
    endfunction
  endclass

  // ------------------------------------------------------------ producer
  class item_producer extends uvm_component;
    `uvm_component_utils(item_producer)
    uvm_blocking_put_port #(bus_item) put_port;  // to the model, via req_fifo
    uvm_analysis_port     #(bus_item) ap;        // the expected stream

    function new(string name, uvm_component parent);
      super.new(name, parent);
    endfunction

    function void build_phase(uvm_phase phase);
      super.build_phase(phase);
      put_port = new("put_port", this);
      ap       = new("ap", this);
    endfunction

    // Called by the test. Returns once the last put() has been accepted.
    task send(int unsigned n);
      for (int unsigned i = 0; i < n; i++) begin
        bus_item t = bus_item::type_id::create($sformatf("t%0d", i)); // new each time
        t.addr = 8'(i);
        t.data = 8'(8'h30 * i);
        put_port.put(t);                 // blocks while req_fifo is full
        `uvm_info("PROD", $sformatf("put #%0d returned: %s", i, t.convert2string()),
                  UVM_LOW)
        ap.write(t);                     // publish exactly what was sent
      end
    endtask
  endclass

  // --------------------------------------------------------------- model
  // A transaction-level stand-in for the DUT: out.data = in.data + 1, 10 ns later.
  class item_model extends uvm_component;
    `uvm_component_utils(item_model)
    uvm_blocking_get_port #(bus_item) get_port;  // from req_fifo
    uvm_analysis_port     #(bus_item) ap;        // the actual stream

    function new(string name, uvm_component parent);
      super.new(name, parent);
    endfunction

    function void build_phase(uvm_phase phase);
      super.build_phase(phase);
      get_port = new("get_port", this);
      ap       = new("ap", this);
    endfunction

    task run_phase(uvm_phase phase);
      bus_item in_item, out_item;
      forever begin
        get_port.get(in_item);           // blocks while req_fifo is empty
        #10ns;                           // models the design's latency
        // in_item is also in the scoreboard's expected FIFO: work on a copy.
        if (!$cast(out_item, in_item.clone())) `uvm_fatal("MODEL", "clone failed")
        out_item.data = in_item.data + 8'd1;
        ap.write(out_item);
      end
    endtask
  endclass

  // ---------------------------------------------------------- scoreboard
  class bus_scoreboard extends uvm_scoreboard;
    `uvm_component_utils(bus_scoreboard)
    uvm_analysis_export   #(bus_item) exp_export;  // expected items enter here
    uvm_analysis_export   #(bus_item) act_export;  // actual items enter here
    uvm_tlm_analysis_fifo #(bus_item) exp_fifo;    // unbounded, never blocks a writer
    uvm_tlm_analysis_fifo #(bus_item) act_fifo;
    int unsigned matches, mismatches;

    function new(string name, uvm_component parent);
      super.new(name, parent);
    endfunction

    function void build_phase(uvm_phase phase);
      super.build_phase(phase);
      exp_export = new("exp_export", this);
      act_export = new("act_export", this);
      exp_fifo   = new("exp_fifo", this);
      act_fifo   = new("act_fifo", this);
    endfunction

    function void connect_phase(uvm_phase phase);
      exp_export.connect(exp_fifo.analysis_export);  // down: my export -> child imp
      act_export.connect(act_fifo.analysis_export);
    endfunction

    task run_phase(uvm_phase phase);
      bus_item exp_item, act_item, pred;
      forever begin
        exp_fifo.get(exp_item);          // the FIFOs are my children: call get() directly
        act_fifo.get(act_item);          // waits here until the model's result arrives
        if (!$cast(pred, exp_item.clone())) `uvm_fatal("SCB", "clone failed")
        pred.data = exp_item.data + 8'd1;   // the prediction, made on a copy
        if (act_item.compare(pred)) matches++;
        else begin
          mismatches++;
          `uvm_error("SCB_MISMATCH", $sformatf("expected %s, got %s",
                     pred.convert2string(), act_item.convert2string()))
        end
      end
    endtask

    // Lets the test wait until n pairs have been checked.
    task wait_checked(int unsigned n);
      wait (matches + mismatches >= n);
    endtask

    function void check_phase(uvm_phase phase);
      int unsigned pending = exp_fifo.used() + act_fifo.used();
      if (pending != 0)
        `uvm_error("SCB_PENDING", $sformatf("%0d items were never compared", pending))
      if (matches + mismatches == 0)
        `uvm_error("SCB_IDLE", "no item was checked: is every stream connected?")
      `uvm_info("SCB", $sformatf("SCB_SUMMARY matches=%0d mismatches=%0d pending=%0d",
                matches, mismatches, pending), UVM_LOW)
    endfunction
  endclass

  // ------------------------------------------------------------ coverage
  class bus_cov extends uvm_subscriber #(bus_item);
    `uvm_component_utils(bus_cov)

    covergroup data_cg with function sample(bit [7:0] data);
      coverpoint data { bins low = {[8'h00:8'h7F]}; bins high = {[8'h80:8'hFF]}; }
    endgroup

    function new(string name, uvm_component parent);
      super.new(name, parent);
      data_cg = new();
    endfunction

    function void write(bus_item t);     // argument name t, as in uvm_subscriber
      data_cg.sample(t.data);
    endfunction

    function void report_phase(uvm_phase phase);
      `uvm_info("COV", $sformatf("data_cg coverage = %0.1f%%", data_cg.get_coverage()),
                UVM_LOW)
    endfunction
  endclass

  // ----------------------------------------------------------------- env
  class tlm_env extends uvm_env;
    `uvm_component_utils(tlm_env)
    item_producer            prod;
    uvm_tlm_fifo #(bus_item) req_fifo;
    item_model               model;
    bus_scoreboard           scb;
    bus_cov                  cov;

    function new(string name, uvm_component parent);
      super.new(name, parent);
    endfunction

    function void build_phase(uvm_phase phase);
      super.build_phase(phase);
      prod     = item_producer::type_id::create("prod", this);
      req_fifo = new("req_fifo", this, 2);      // holds 2 items: back-pressure on prod
      model    = item_model::type_id::create("model", this);
      scb      = bus_scoreboard::type_id::create("scb", this);
      cov      = bus_cov::type_id::create("cov", this);
    endfunction

    function void connect_phase(uvm_phase phase);
      prod.put_port.connect(req_fifo.put_export);   // across: port -> sibling imp
      model.get_port.connect(req_fifo.get_export);  // across: port -> sibling imp
      prod.ap.connect(scb.exp_export);              // across: port -> sibling export
      model.ap.connect(scb.act_export);
      model.ap.connect(cov.analysis_export);        // a second subscriber on model.ap
    endfunction
  endclass

  // ---------------------------------------------------------------- test
  class tlm_test extends uvm_test;
    `uvm_component_utils(tlm_test)
    tlm_env env;

    function new(string name, uvm_component parent);
      super.new(name, parent);
    endfunction

    function void build_phase(uvm_phase phase);
      super.build_phase(phase);
      env = tlm_env::type_id::create("env", this);
    endfunction

    task run_phase(uvm_phase phase);
      phase.raise_objection(this);
      env.prod.send(6);          // in a real bench, sequences make stimulus (I-UVM-3A)
      env.scb.wait_checked(6);   // do not end the test while items are in flight
      phase.drop_objection(this);
    endtask
  endclass
endpackage

  import tlm_demo_pkg::*;

endmodule

### Break it on purpose

Each change below is one line. Predict the log first, then read the answer.

1. **The model modifies its input.** Replace the clone in `item_model` with `in_item.data = in_item.data + 8'd1; ap.write(in_item);`. The producer published the same object to `exp_fifo`, so by the time the scoreboard predicts, the "expected" item has already been incremented. The first error reads `UVM_ERROR … [SCB_MISMATCH] expected addr=00 data=02, got addr=00 data=01`, all six pairs mismatch, and the summary is `SCB_SUMMARY matches=0 mismatches=6 pending=0`. Nothing was wrong with the "design": the bug is a shared handle.
2. **A connection is forgotten.** Delete `exp_export.connect(exp_fifo.analysis_export);`. `scb.exp_export` reaches 0 imps against a minimum of 1, so end of elaboration reports `UVM_ERROR … [Connection Error] connection count of 0 does not meet required minimum of 1`, then `UVM_FATAL … [BUILDERR] stopping due to build errors`. No time passes.
3. **The FIFO is unbounded.** Change `new("req_fifo", this, 2)` to `new("req_fifo", this, 0)`. All six `put` lines now print at time 0, and the results are unchanged. Back-pressure only changes when the producer runs.
4. **The test does not wait.** Delete `env.scb.wait_checked(6);`. The objection drops at 30 ns, when `send()` returns, while at least three results are still in flight. `check_phase` reports `UVM_ERROR … [SCB_PENDING] … items were never compared`, and the summary shows fewer than 6 matches and a non-zero `pending`. The exact split depends on which processes the simulator runs first in the 30 ns time slot, which is one more reason never to end a test on a guess.

### How to wire a new connection

1. **Name the roles.** Which component calls (the requirer) and which implements (the provider)? Is it a broadcast (analysis), a one-to-one hand-off (put or get), or a pull from a sequencer?
2. **Pick the classes.** The caller declares a port that names every method it will call: `uvm_analysis_port`, `uvm_blocking_put_port`, `uvm_get_peek_port` and so on. The provider declares an imp, or uses a FIFO's imps, or a `uvm_subscriber`.
3. **Add a FIFO when the two sides run at different speeds:** `uvm_tlm_fifo` (choose its size) between a put port and a get port, `uvm_tlm_analysis_fifo` behind an analysis port.
4. **Construct** ports, exports and FIFOs with `new` in `build_phase` (or the constructor); components with `::type_id::create`.
5. **Connect in `connect_phase`** of the component that owns both ends: up in the child's parent, across in the common parent, down in the parent of the imp. Call `connect()` on the requiring side.
6. **Publish safely:** a new object per transaction; copy before modifying.
7. **Prove it at end of test:** count what each subscriber received, check that every analysis FIFO is empty in `check_phase`, and read the end-of-elaboration log for `Connection Error`.

### Debugging connections: symptom, cause, fix

| Symptom in the log | Cause | Fix |
|---|---|---|
| Compile error at a `connect()` line, about the argument type | the two ends carry different item types | use the same `T` on both ends, or add a converter component |
| `[Connection Error] connection count of 0 does not meet required minimum of 1`, then `[BUILDERR] stopping due to build errors` | a put, get or peek port, or an analysis export, was never connected | add the missing `connect()` in `connect_phase` |
| `[Connection Error] Cannot call an imp port's connect method. An imp is connected only to the component passed in its constructor. …` | the call is written backwards, from the imp | call `connect()` on the port: `port.connect(imp)` |
| `[Connection Error] Cannot connect exports to ports Try calling port.connect(export) instead. …` | an export was connected to a port | reverse it: `port.connect(export)` |
| `[Connection Error] … does not provide the complete interface required of this port …` | for example a get port connected to a FIFO's `put_export`; every TLM-1 port shares one base type, so it compiles. A reversed connection whose ends enable different method sets, such as `req_fifo.put_export.connect(prod.put_port)`, also lands here, because the interface is checked before the direction | connect a get port to `get_export` or `get_peek_export`, a put port to `put_export`; call `connect()` on the port |
| `[Connection Error] connection count of 2 exceeds maximum of 1` | a put or get port connected to two providers | keep one; to fan out, use an analysis port |
| `[Late Connection] Attempt to connect … at or after end_of_elaboration phase.  Ignoring.` (warning) | `connect()` in `end_of_elaboration_phase` or later | move it to `connect_phase` |
| `[peek] UVM TLM interface task not implemented` at run time | `peek()` called through a port class without peek, such as `uvm_get_port` | use `uvm_get_peek_port` or `uvm_blocking_get_peek_port` |
| `[DRVCONNECT] seq_item_port … has not been connected to a sequencer` (warning), then a null-object error at the first `get_next_item()` | the driver's pull port was never connected (minimum 0) | `drv.seq_item_port.connect(sqr.seq_item_export)` in the agent |
| Scoreboard silent: zero matches and zero errors | an analysis port with no subscriber, or a reversed promotion `ap.connect(mon.ap)`: both are legal | connect it; and make the scoreboard report `SCB_IDLE` when it checked nothing |
| Every stored item equals the last one | the publisher reused one object | create a new object per transaction |
| Expected and actual both "wrong" in the same way, or values change after they were checked | a subscriber or model modified a shared object | clone before modifying |
| `SCB_PENDING`, or items lost at the end | the test ended while an analysis FIFO still held items | keep the objection until the checker is idle; report `used()` in `check_phase` |

## Push Further

### Expert: binding resolution, sizes and BUILDERR

- Resolution happens in `uvm_root::phase_started()` for end of elaboration: `do_resolve_bindings()` calls `resolve_bindings()` on every port, which walks each port's providers recursively and collects the imps at the leaves (§5.5.2.15). Only after that do `size()` and `get_if()` return meaningful values (§5.5.2.12).
- The `BUILDERR` check counts **every** `UVM_ERROR` reported so far, not only connection errors. A `build_phase` that reports a `uvm_error`, for example for a failed configuration lookup, also stops the run here. That is deliberate: a bench that built wrongly should not run.
- The minimum and maximum come from constructor arguments. Every TLM-1 port and export constructor accepts `min_size` and `max_size`, so a port that should be allowed to stay unconnected can be built with `new("opt_port", this, 0)`. Use this sparingly: a missing connection then goes unreported.
- `uvm_analysis_port::write()` loops over the resolved imps, and before resolution `size()` is 0. An analysis `write()` called during `build_phase` or `connect_phase` therefore reaches nobody, silently.

Sources: IEEE 1800.2-2020 §5.5.2.12, §5.5.2.15; uvm-core 2020.3.1 `src/base/uvm_root.svh`, `src/base/uvm_port_base.svh`, `src/tlm1/uvm_analysis_port.svh`.

### Expert: relationship checks are off by default

- `connect()` always calls an internal relationship check that compares grandparents and parents to enforce the up, across and down forms. But each port's constructor sets the action for `Connection Warning` to `UVM_NO_ACTION` unless an integer configuration entry named `check_connection_relationships` exists for that port. The warnings are therefore invisible unless the test sets, before the env is built, `uvm_config_int::set(this, "*", "check_connection_relationships", 1);`.
- Ports of type `uvm_analysis_port` skip the check entirely, and so does any connection in which either side was created with a `null` parent.
- Consequence: an env that connects `env.agt.mon.ap` straight to `env.chk_env.scb.item_imp` works and stays silent. It also breaks encapsulation: the env now depends on the agent's and the checker's internal names, and replacing either with an implementation whose children have other names breaks the bench. Promote through the agent's `ap` and the sub-environment's export instead.
- Teams that enable the check in a regression smoke test catch these shortcuts early, at the cost of warnings from third-party VIP that takes them.

Sources: uvm-core 2020.3.1 `src/base/uvm_port_base.svh` (`new()`, `connect()`, `m_check_relationship()`); this switch is uvm-core implementation behaviour (IEEE 1800.2-2020 §5.5.2.1 defines the constructor).

### Expert: write() corner cases

- **Waiting inside a function.** IEEE 1800-2023 §13.4 forbids time-controlling statements and task calls in a function, but §13.4.4 allows `fork … join_none` there, and the forked block may contain anything legal in a task. A `write()` that forks a waiting thread per item compiles. It also creates one unmanaged process per transaction: nothing bounds how many run at once, nothing orders them, and no objection waits for them at the end of the test. An analysis FIFO and one `get()` thread give the same decoupling with a single, visible process.
- **Order.** uvm-core calls subscribers in lexicographic order of the imps' full names, because it iterates a string-indexed associative array (IEEE 1800-2023 §7.8.2). Renaming a component can therefore reorder subscribers. Code that works only in one order has a hidden dependency between subscribers.
- **Cost.** `write()` takes zero simulation time but real CPU time. A monitor with ten subscribers calls ten functions per transaction; a heavy subscriber slows every test that instantiates it, even when its results are not needed. Gate expensive subscribers with a configuration knob.
- **Re-entrancy.** A subscriber's `write()` may itself call `write()` on another analysis port. The nested calls also complete before the monitor's `write()` returns, so a cycle of analysis connections recurses until the simulator's stack runs out.

Sources: IEEE 1800-2023 §7.8.2, §13.4, §13.4.4; uvm-core 2020.3.1 `src/base/uvm_port_base.svh`, `src/tlm1/uvm_analysis_port.svh`. The CPU-cost and re-entrancy points are general practice.

### Expert: FIFO sizing, memory and end of test

- `uvm_tlm_fifo` defaults to `size = 1`; 0 means unbounded (§12.2.8.2). `uvm_tlm_analysis_fifo` calls `super.new(name, parent, 0)`, so it is always unbounded, and its `write()` is `void'(try_put(t))` (§12.2.8.3).
- An unbounded FIFO whose consumer has stopped grows for the rest of the test and keeps every queued object alive. A non-zero `used()` in `check_phase` is the cheapest leak detector you will ever write.
- `flush()` reports `UVM_ERROR "there are blocked gets preventing the flush"` if items remain while another process is blocked in `get()`. Flushing on reset therefore needs care: stop or kill the consumer first (A-UVM-9 covers reset handling).
- In uvm-core, `can_get()` returns 0 while another process is blocked in `get()`, even if an item is present, so two consumers on one FIFO may not see what they expect. Prefer one consumer per FIFO.
- Every `uvm_tlm_fifo` has two analysis ports, `put_ap` and `get_ap`, which publish each item put and each item taken. Connect a logger or a latency monitor to them without touching the producer or the consumer.

Sources: IEEE 1800.2-2020 §12.2.8.1, §12.2.8.2, §12.2.8.3; uvm-core 2020.3.1 `src/tlm1/uvm_tlm_fifos.svh`, `src/tlm1/uvm_tlm_fifo_base.svh`.

### Expert: inspecting connectivity

- `get_connected_to(list)` fills an associative array with the endpoints this port or export connects to, and `get_provided_to(list)` with the endpoints that connect to it (§5.5.2.9, §5.5.2.10). `size()` returns the number of imps reached, after resolution (§5.5.2.12). A scoreboard can assert in `end_of_elaboration_phase` that each of its exports reaches exactly the imps it expects.
- `debug_connected_to()` and `debug_provided_to()` print the whole fan-out or fan-in tree as text. They are uvm-core implementation features, marked as not part of IEEE 1800.2, and are meaningful only from end of elaboration on.
- Imps appear in these listings under their instance names: a subscriber's imp as `…cov.analysis_imp`, a FIFO's `get_export` as `…req_fifo.get_peek_export` (the alias's real object).
- `print_topology()` shows the component tree, with ports as children, but no connections. A clean topology printout proves nothing about wiring.

Sources: IEEE 1800.2-2020 §5.5.2.9, §5.5.2.10, §5.5.2.12; uvm-core 2020.3.1 `src/base/uvm_port_base.svh`, `src/comps/uvm_subscriber.svh`, `src/tlm1/uvm_tlm_fifo_base.svh`.

### Expert: TLM-2 in one page

- **What it is.** UVM also implements TLM-2.0 (§12.3), modelled on the SystemC standard. Its transaction is the **generic payload**, `uvm_tlm_generic_payload` (§12.3.4), a `uvm_sequence_item` with a 64-bit address, a command (read, write or ignore), a data byte array, a length, byte enables and a response status.
- **Sockets** (§12.3.5) replace port and imp pairs: an initiator socket connects to a target socket, for example `uvm_tlm_b_initiator_socket` to `uvm_tlm_b_target_socket`.
- **Transport calls** carry timing as an argument instead of consuming it. `b_transport(t, delay)` is a blocking task; `nb_transport_fw(t, phase, delay)` and `nb_transport_bw(t, phase, delay)` are functions that move a transaction through phases such as `BEGIN_REQ` and `END_RESP` and return `UVM_TLM_ACCEPTED`, `UVM_TLM_UPDATED` or `UVM_TLM_COMPLETED` (§12.3.2).
- **When you meet it.** Mostly at the boundary with SystemC or C++ virtual-platform models, and in some memory-mapped reference models. Ordinary UVM agents, scoreboards and coverage use TLM-1. [E-UVM-ML-1](/curriculum/T4_Expert/E-UVM-ML-1_Multi_Language_Verification/index) covers mixed-language connection.
- **Other TLM-1 channels** for completeness: `uvm_tlm_req_rsp_channel` (§12.2.9.1) pairs a request FIFO and a response FIFO, and `uvm_tlm_transport_channel` (§12.2.9.2) adds a blocking `transport(req, rsp)`.

Sources: IEEE 1800.2-2020 §12.2.9.1, §12.2.9.2, §12.3.2, §12.3.4, §12.3.5; uvm-core 2020.3.1 `src/tlm2/uvm_tlm2_generic_payload.svh`, `src/tlm2/uvm_tlm2_ifs.svh`, `src/tlm2/uvm_tlm2_sockets.svh`, `src/tlm1/uvm_tlm_req_rsp.svh`.

### Kata: a two-input scoreboard with `` `uvm_analysis_imp_decl ``

**Objective:** practise objectives 3 and 5 by turning the snippet from Build Your Mental Model into a working scoreboard, then into a two-FIFO version.

**Spec.** An in-order bridge copies every `bus_item` from its input bus to its output bus unchanged. `in_agt.ap` publishes what entered, and `out_agt.ap` what left. Write `bridge_scoreboard`:
1. Declare `exp_imp` and `act_imp` with `` `uvm_analysis_imp_decl(_exp) `` and `` `uvm_analysis_imp_decl(_act) ``.
2. `write_exp()` stores a copy of each expected item in a queue. `write_act()` pops the oldest expected item, compares it with the actual item, and counts matches and mismatches. An actual item with nothing expected is an error.
3. `check_phase` reports `SCB_SUMMARY matches=N mismatches=M pending=P`, an error if `pending` is not 0, and an error if nothing was checked.
4. Write the env's two `connect()` lines.
5. **Part two:** re-implement it with two `uvm_tlm_analysis_fifo`s behind `uvm_analysis_export`s and one `run_phase` loop, as in Make It Work. What does the second version allow that the first does not?

**Done when** a clean run of 5 items prints `SCB_SUMMARY matches=5 mismatches=0 pending=0` with `UVM_ERROR :    0`, and deleting `out_agt.ap.connect(scb.act_imp);` makes the scoreboard fail (pending 5) instead of passing.

<details>
<summary>Worked solution (try the kata first)</summary>

```systemverilog
// snippet: compiles inside tlm_demo_pkg, after bus_item
`uvm_analysis_imp_decl(_exp)            // package scope, before the class
`uvm_analysis_imp_decl(_act)

class bridge_scoreboard extends uvm_scoreboard;
  `uvm_component_utils(bridge_scoreboard)
  uvm_analysis_imp_exp #(bus_item, bridge_scoreboard) exp_imp;
  uvm_analysis_imp_act #(bus_item, bridge_scoreboard) act_imp;
  bus_item     exp_q[$];
  int unsigned matches, mismatches;

  function new(string name, uvm_component parent);
    super.new(name, parent);
  endfunction

  function void build_phase(uvm_phase phase);
    super.build_phase(phase);
    exp_imp = new("exp_imp", this);
    act_imp = new("act_imp", this);
  endfunction

  function void write_exp(bus_item t);
    bus_item c;
    if (!$cast(c, t.clone())) `uvm_fatal("SCB", "clone failed")
    exp_q.push_back(c);                   // store a copy: the publisher keeps t
  endfunction

  function void write_act(bus_item t);
    bus_item e;
    if (exp_q.size() == 0) begin
      `uvm_error("SCB_UNEXPECTED",
                 $sformatf("nothing expected, got %s", t.convert2string()))
      mismatches++;
      return;
    end
    e = exp_q.pop_front();
    if (t.compare(e)) matches++;
    else begin
      mismatches++;
      `uvm_error("SCB_MISMATCH", $sformatf("expected %s, got %s",
                 e.convert2string(), t.convert2string()))
    end
  endfunction

  function void check_phase(uvm_phase phase);
    int unsigned pending = exp_q.size();
    if (pending != 0)
      `uvm_error("SCB_PENDING", $sformatf("%0d expected items never arrived", pending))
    if (matches + mismatches == 0)
      `uvm_error("SCB_IDLE", "no item was checked: is act_imp connected?")
    `uvm_info("SCB", $sformatf("SCB_SUMMARY matches=%0d mismatches=%0d pending=%0d",
              matches, mismatches, pending), UVM_LOW)
  endfunction
endclass

// bus_env::connect_phase
// in_agt.ap.connect(scb.exp_imp);
// out_agt.ap.connect(scb.act_imp);
```

**Why it works.** Each imp class calls its own method, so the two streams stay apart. Both methods are zero-time functions, which is enough for an in-order compare: the expected item always arrives first, because the bridge cannot output an item before it receives it. With `out_agt.ap.connect(scb.act_imp)` deleted, the build is still clean (an analysis port may have no subscriber, and `act_imp` counts itself), but `check_phase` reports `SCB_PENDING` for 5 items and `SCB_IDLE`, so the test fails as it should.

**Part two.** The two-FIFO version is `bus_scoreboard` in Make It Work without the `+1` prediction. Its `run_phase` thread may wait, so it can later model latency, wait for a response or apply a timeout without rewiring the env. It also tolerates actual items that arrive before their expected partners, which the `imp_decl` version reports as unexpected.

</details>

### Debug challenge: read the log, find the line

Each symptom comes from the Make It Work bench with one line of `tlm_env::connect_phase` changed, deleted or added. Name the line and the fix before opening the answers.

1. `UVM_ERROR … uvm_test_top.env.cov.analysis_imp [Connection Error] Cannot call an imp port's connect method. … (You attempted to bind this imp to uvm_test_top.env.model.ap)`
2. `UVM_ERROR … uvm_test_top.env.model.get_port [Connection Error] uvm_test_top.env.req_fifo.put_export (of type uvm_put_imp) does not provide the complete interface required of this port (type uvm_blocking_get_port)`
3. A team-mate added a second FIFO, `log_fifo` (built like `req_fifo`), and one new line in `connect_phase`. The log shows `UVM_ERROR … uvm_test_top.env.prod.put_port [Connection Error] connection count of 2 exceeds maximum of 1`.
4. The end-of-elaboration log is clean. All six `PROD` lines print by 30 ns, then nothing happens until the run is killed by the phase timeout.

<details>
<summary>Answers (try first)</summary>

1. `cov.analysis_export.connect(model.ap);`: the call was written from the imp (the reporter's name, `cov.analysis_imp`, is the instance name of `uvm_subscriber`'s `analysis_export`). Imps never call `connect()`. Fix: `model.ap.connect(cov.analysis_export);`. The build stops with `BUILDERR`. Reversing a *put* connection, `req_fifo.put_export.connect(prod.put_port)`, gives a different first message: `connect()` checks the interface before the direction, and a `uvm_blocking_put_port` lacks the nonblocking half that the `uvm_put_imp` requires, so the log reads `… prod.put_port (of type uvm_blocking_put_port) does not provide the complete interface required of this port (type uvm_put_imp)` (uvm-core 2020.3.1, `uvm_port_base.svh`, `connect()`).
2. `model.get_port.connect(req_fifo.put_export);`: a get port connected to a put imp. It compiles because all TLM-1 endpoints share one base type, and the interface check inside `connect()` catches it. Because that `connect()` was refused, `model.get_port` also reaches 0 imps, so a second `connection count of 0` error follows at end of elaboration. Fix: `model.get_port.connect(req_fifo.get_export);`.
3. `prod.put_port.connect(log_fifo.put_export);` was added, so `prod.put_port` now reaches two imps. A put port reaches exactly one provider. Fix: remove the line; to send the same items to a logger as well, connect the logger to `prod.ap` (an analysis port fans out) or to `req_fifo.put_ap`.
4. `model.ap.connect(scb.act_export);` is missing. The build stays clean: `model.ap` is an analysis port (minimum 0), and `scb.act_export` still reaches its own `act_fifo.analysis_export`, so its count is 1. At run time the scoreboard waits forever in `act_fifo.get()`, so `wait_checked(6)` never returns and the objection is never dropped. The default phase timeout (9200 s, `UVM_DEFAULT_TIMEOUT` in uvm-core) finally ends the run with a `UVM_FATAL`, and `check_phase` never runs. Fix: restore the connection. To fail faster, give the test a shorter timeout (I-UVM-1C).

</details>
