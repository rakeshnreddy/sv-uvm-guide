## Quick Take
- **What it is:** Constrained randomization lets you describe legal stimulus space with constraints so the solver generates thousands of intelligent variations automatically.
- **Why it matters:** Directed tests miss combinations; constrained random exploration paired with coverage exposes subtle corner cases and shrinks bug escape risk.
- **The Analogy:** It’s a programmable dice tower—tell it “only roll sums of 7 where die1 > die2,” and it feeds you every valid combo, not noise.

> **Tip:** Always pair constraints with coverage goals—random stimulus without measurement is aimless wandering.
> *SystemVerilog Constrained Randomization is formally defined in **IEEE 1800-2023, Clause 18**.*

### Random Variables & Constraint Blocks
<InteractiveCode>
```systemverilog
class Packet;
  rand bit        is_read;
  rand bit [7:0]  length;
  rand bit [3:0]  opcode;
  rand byte       payload[];

  // Hard constraints define legal space
  constraint legal_length { length inside {[8:16], [64:96]}; }
  constraint payload_size { payload.size() == length; }

  // Distribution biases interesting cases
  constraint opcode_dist {
    opcode dist { 4'h0 := 10, [4'h1:4'h3] :/ 70, [4'h8:4'hF] :/ 20 };
  }

  // Relational constraint
  constraint read_defaults { if (is_read) length == 8; }

  function void post_randomize();
    $display("Packet(opcode=%0h len=%0d is_read=%0b)", opcode, length, is_read);
  endfunction
endclass

program demo;
  initial begin
    Packet pkt = new();
    repeat (3) begin
      if (!pkt.randomize())
        $fatal(1, "Randomization failed");
    end
    // Inline constraint for targeted scenario
    void'(pkt.randomize() with { opcode == 4'hF; length == 16; });
  end
endprogram
```
</InteractiveCode>

### Reading `dist` weights

`opcode_dist` does two jobs (IEEE 1800-2023 §18.5.3). It **restricts** `opcode` to the listed values, and it **weights** them.

- `:=` gives the weight to *every value* of a range. `[4'h1:4'h3] := 70` would weigh 3 × 70 = 210.
- `:/` gives the weight to the *range as a whole*. `[4'h1:4'h3] :/ 70` weighs 70 in total, about 23.3 per value.
- Weights are ratios. Divide by the total weight, here 10 + 70 + 20 = 100.

So `opcode` is `0` on 10% of calls, each of `1`–`3` on about 23.3%, and each of `8`–`F` on 2.5%. Values `4`–`7` are not listed, so they **never** occur: `dist` is also a membership constraint. Nonzero weights never make `randomize()` fail, but the membership part can.

### See the solution space

Picture every combination of the random variables as a grid. Constraints cross out cells, then `randomize()` picks **one legal cell, uniformly** (§18.5.9). It does not pick each variable on its own. Before each reveal, commit to a number for `P(x == 0)`.

Try the scenarios in order:

1. **Coupled variables** with `c_sum` on. `x == 0` pairs with 8 legal `y` values, while `x == 7` pairs with only one. Predict, then switch on `c_order`: the legal cells stay the same and only the odds change.
2. **Implication.** `(x == 0) -> (y == 0)` is the Boolean `!(x == 0) || (y == 0)`. Switch on `c_hi` and watch the right-hand side rule out `x == 0`.
3. **dist := vs :/.** Flip the operator, then add `c_big` and see a `dist` membership conflict.
4. **soft priority.** A lone `soft` constraint holds on 100% of calls, not "usually".
5. **Debug a failure.** Find the smallest set of constraints that conflict. Is `c_odd` guilty?

Then run 1,000 calls and compare the sampled bars with the exact ones. A satisfiable problem never fails; the sample only wobbles around the exact value.

### Constraint Patterns
- **Relational:** guard dependent variables with `if...else` or `->`. Both sides constrain each other (§18.5.5).
- **Ordering:** `solve addr before data;` changes the odds, never the legal set. `addr` is drawn uniformly over its legal values first, then `data` (§18.5.9). It is never needed for correctness.
- **Soft defaults:** `soft length == 32;` holds on **every** call unless a hard constraint or a higher-priority soft constraint contradicts it. Then it is dropped entirely (§18.5.13). It is a priority, not a probability.

**Predict before you read on:** in this class, how often is `is_secure` equal to 1?

<InteractiveCode>
```systemverilog
class Config;
  rand bit       is_secure;
  rand bit [1:0] burst_len;

  constraint burst_rules {
    soft burst_len == 2'b10;           // default burst = 4 beats
    if (is_secure) burst_len == 2'b01; // secure mode shortens bursts
  }
  constraint order { solve is_secure before burst_len; }
endclass
```
</InteractiveCode>

<details>
<summary>Reveal the answer</summary>

**Never.** The pair `is_secure = 0, burst_len = 2'b10` satisfies everything, so nothing contradicts the soft default and the solver keeps it on every call. Keeping it forces `burst_len == 2'b10`, and the `if` then forces `is_secure = 0`. The `solve…before` cannot help: it reshapes the odds over the legal set, and the legal set contains only `is_secure = 0`. Scope the default to the case it belongs to:

<InteractiveCode>
```systemverilog
class Config;
  rand bit       is_secure;
  rand bit [1:0] burst_len;

  constraint burst_rules {
    is_secure  -> burst_len == 2'b01;       // secure mode shortens bursts
    !is_secure -> soft burst_len == 2'b10;  // the default applies only when not secure
  }
endclass
```
</InteractiveCode>

Now `is_secure` is 1 on half the calls, with no ordering constraint needed.

</details>

## Make It Work
1. **Model legality:** Translate protocol rules into constraints—illegal stimulus wastes regression time.
2. **Layer distributions:** Bias randomization toward risky scenarios (e.g., error opcodes) while still covering the space.
3. **Validate success:** Always check `randomize()` return value and log failures with an actionable message.
4. **Measure:** Pair random stimulus with functional coverage to confirm constraint intent is met.

**Checklist before moving on:**
- [ ] You can explain the difference between `rand` and `randc`.
- [ ] You can write relational and distribution constraints that reflect spec rules.
- [ ] You confirm randomize success and understand how to debug failures.

## Push Further
- Keep relations between random fields in constraints (for example `payload.size() == len`). Use `post_randomize()` only for derived, non-random fields such as a CRC.
- Create constraint mode toggles (`constraint_mode(0)`) for reusable classes in different scenarios.
- Explore `randomize() with` blocks in sequences to target coverage holes without new classes.
