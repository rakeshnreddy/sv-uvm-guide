## Quick Take

- **What it is:** A **sequence item** (`uvm_sequence_item`) is an object that holds the data of one transaction, such as one bus read or write. A **sequence** (`uvm_sequence`) is an object whose `body()` task creates items and hands them out one at a time. A **sequencer** (`uvm_sequencer`) is the component that decides which sequence may send next, and a **driver** (`uvm_driver`) is the component that pulls each item from the sequencer and turns it into activity on the design under test (DUT). The four of them together carry out the **sequence–sequencer–driver handshake**.
- **Why it matters:** Sequences separate *what* to send from *how* to send it. One driver can serve hundreds of tests, each of which only picks or writes sequences. Every stimulus you write in UVM from now on goes through this handshake, and its two classic bugs, a missing `item_done()` and a response that cannot be routed, stop whole regressions.
- **The Analogy:** The item is a letter, the sequence is the person who writes it, the driver is the mail carrier, and the sequencer is the post-office counter. The carrier asks the counter for the next letter, and the counter picks which waiting writer is served. *Where it breaks:* a real counter stockpiles letters, but a UVM sequencer holds at most one item for its driver. The writer also stands at the counter until the carrier reports delivery (`item_done()`), so a writer can never run ahead of the carrier.

**You will be able to:**
1. Write a `uvm_sequence_item` with `rand` fields, constraints and `do_copy`, `do_compare` and `convert2string`, and predict what `clone()` and `compare()` do with each field.
2. Write a sequence `body()` with `start_item`, a checked `randomize()` and `finish_item`, say what each call blocks on, and expand `` `uvm_do `` and `` `uvm_do_with `` into those calls.
3. Write a driver loop with `get_next_item` and `item_done`, choose `try_next_item` or `get` and `put` when they fit, and predict the hang when `item_done` is missing.
4. Return responses with `set_id_info` plus `item_done(rsp)` or `put_response`, and collect them with `get_response`.
5. Start a sequence from a test on the right sequencer, with the end of test handled by objections around `start()` or by `set_starting_phase` plus `set_automatic_phase_objection`.

> **Remember:** `start_item`, `finish_item` and `get_next_item` block. `item_done` never blocks: it is a function, and calling it is what lets `finish_item` return.

### Who does what: item, sequence, sequencer, driver

The driver *pulls* work. Its `seq_item_port` is a port connected to the sequencer's `seq_item_export`, and the driver calls `get_next_item()` through it whenever it is ready for the next transfer. The sequencer then chooses one of the sequences that are waiting to send, which is called **arbitration**, and passes that sequence's item to the driver. Nothing moves until the driver asks.

| Role | Class | Is a | Job |
| --- | --- | --- | --- |
| Item | `bus_item extends uvm_sequence_item` | object | Holds one transfer's fields; knows how to copy, compare and print itself |

The test reaches the sequencer through the hierarchy (`env.agt.sqr`) and starts sequences on it.

### The sequence item

A **sequence item** is a class that extends `uvm_sequence_item` (IEEE 1800.2-2020 §14.1). It holds the fields of one transaction, declared `rand` so that `randomize()` can choose them, plus constraints that keep the choices legal ([I-SV-2A](/curriculum/T2_Intermediate/I-SV-2A_Constrained_Randomization_Fundamentals/index)). It is an object, so you create a new one for every transaction.

Scoreboards and drivers also need to copy, compare and print items. `uvm_object` gives every item the methods `copy()`, `clone()`, `compare()`, `print()` and `convert2string()` (§5.3.6.4, §5.3.8, §5.3.9). Your class tells them about its fields in one of two ways.

**Way 1: field macros.** Each `` `uvm_field_* `` macro registers one field, and the library then copies, compares and prints it for you.

```systemverilog
// snippet: the shortest correct item, with field macros
typedef enum bit {BUS_READ, BUS_WRITE} bus_op_e;  // declared before the macros use it

class bus_item extends uvm_sequence_item;
  rand bus_op_e   op;
  rand bit [7:0]  addr;
  rand bit [31:0] data;

  constraint c_word_aligned { addr[1:0] == 2'b00; }

  `uvm_object_utils_begin(bus_item)
    `uvm_field_enum(bus_op_e, op, UVM_ALL_ON)
    `uvm_field_int(addr, UVM_ALL_ON | UVM_HEX)
    `uvm_field_int(data, UVM_ALL_ON | UVM_HEX)
  `uvm_object_utils_end

  function new(string name = "bus_item");
    super.new(name);
  endfunction
endclass
```

**Way 2: hand-written methods.** You override `do_copy()` and `do_compare()`, the hooks that `copy()` and `compare()` call, and `convert2string()`. This is the version used in Make It Work. It is longer, but every line is visible, it is easy to debug, and it avoids the field automation that runs on every copy and compare.

```systemverilog
// snippet: the same item with hand-written methods (in a package that imports uvm_pkg)
class bus_item extends uvm_sequence_item;
  rand bus_op_e   op;
  rand bit [7:0]  addr;
  rand bit [31:0] data;

  constraint c_word_aligned { addr[1:0] == 2'b00; }

  `uvm_object_utils(bus_item)

  function new(string name = "bus_item");
    super.new(name);
  endfunction

  virtual function void do_copy(uvm_object rhs);
    bus_item rhs_;
    super.do_copy(rhs);                  // let the base classes copy their state first
    if (!$cast(rhs_, rhs)) begin
      `uvm_fatal("BUS_ITEM/COPY", "do_copy: rhs is not a bus_item")
      return;
    end
    op   = rhs_.op;
    addr = rhs_.addr;
    data = rhs_.data;
  endfunction

  virtual function bit do_compare(uvm_object rhs, uvm_comparer comparer);
    bus_item rhs_;
    if (!$cast(rhs_, rhs)) return 0;     // a different type never matches
    return super.do_compare(rhs, comparer) &&
           op == rhs_.op && addr == rhs_.addr && data == rhs_.data;
  endfunction

  virtual function string convert2string();
    return $sformatf("%s addr=0x%02h data=0x%08h", op.name(), addr, data);
  endfunction
endclass
```

How the calls fit together in uvm-core 2020.3.1:
- `clone()` creates a new object of the same type and calls `copy()` on it.
- `copy(rhs)` runs the field macros first, then your `do_copy(rhs)`.
- `compare(rhs)` runs the field macros first, then your `do_compare(rhs, comparer)`; it returns 1 only if both agree.
- `convert2string()` returns `""` unless you override it. Use it in log messages: one line per item is easier to read than `sprint()`'s table.

The two ways can be mixed. A field that is in a field macro *and* in `do_copy` is simply copied twice. The details of printers, comparers and copier policies belong to [I-UVM-4](/curriculum/T2_Intermediate/I-UVM-4_UVM_Policy_Classes/index).

**Predict, then check: what does `clone()` copy?** Suppose `bus_item` gains two more members that the hand-written methods above do not mention: `byte payload[$]` (a queue) and `bus_cfg cfg` (a handle to a configuration object). Predict the clone's values and the `compare()` result for each row before you read the table.

| Member | How the class handles it | `orig` | `clone` after `$cast(c, orig.clone())` | Does `orig.compare(c)` check it? |
| --- | --- | --- | --- | --- |
| `addr` | copied in `do_copy`, compared in `do_compare` | `8'h34` | `8'h34` | yes |
| `payload[$]` | in neither method, no field macro | `'{1, 2, 3}` | empty queue | no: `compare()` still returns 1 |
| `cfg` | `do_copy` assigns `cfg = rhs_.cfg;` | handle to object A | handle to the **same** object A | only if `do_compare` checks it |
| `cfg` | `` `uvm_field_object(cfg, UVM_ALL_ON) `` | handle to object A | handle to a **new** object, a copy of A | yes, field by field |
| `cfg` | `` `uvm_field_object(cfg, UVM_ALL_ON | UVM_REFERENCE) `` | handle to object A | handle to the same object A | yes, by handle |

What the table shows:
- **Queues and dynamic arrays are values in SystemVerilog.** Copying one copies its elements; nothing is ever shared. The real danger is the opposite: a field nobody registered is not copied at all, and `compare()` ignores it, so a scoreboard reports a match although the data differ.
- **Class handles are references.** Assigning a handle copies the reference, so the original and the clone share one object (a *shallow* copy). Write `cfg = rhs_.cfg.clone()` (with a `$cast`) if each item needs its own copy.
- **Every field must appear somewhere**: in a field macro, or in both `do_copy` and `do_compare`.

**Pitfalls and how to spot them.**
- *An unregistered field.* Symptom: the scoreboard says "match" while waveforms differ. Print both items with `convert2string()` and compare by eye; then add the field.
- *A missing `super.do_copy(rhs)`.* The base classes' state is not copied. Always call `super` first.
- *A missing `$cast` check.* Copying from the wrong type then reads null fields. Check the cast as above.

### The handshake: sequence ↔ sequencer ↔ driver

The whole handshake comes down to one question: who blocks where. A sequence runs its `body()` task, and every item goes through two blocking calls on the sequence side and one blocking call on the driver side:
- `start_item(req)` asks the sequencer for permission and **blocks until the sequencer grants it**. The grant comes when the driver asks for an item and this sequence wins arbitration.
- Between the two calls you randomize the item. This is **late randomization**: the values are chosen at the last moment, when the sequence knows it will send next.
- `finish_item(req)` puts the item into the sequencer's **request FIFO** (a first-in, first-out queue with room for one item) and **blocks until the driver calls `item_done()`**.
- On the driver side, `get_next_item(req)` **blocks until a granted sequence has sent an item**, and `item_done()` reports that the item is finished. `item_done()` is a function, so it never blocks.

**What the explorer showed.**

- The sequencer never holds a second item: its request FIFO has room for one, and the next grant only happens when the driver calls `get_next_item()` again.
- `item_done()` returns at once. Its only job is to remove the item from the FIFO and wake the sequence.

The same handshake as code. Both classes are complete; Make It Work grows them into a runnable testbench (a read-back sequence, and a driver that also returns responses).

```systemverilog
// snippet: the sequence (inside a package that imports uvm_pkg)
class bus_write_seq extends uvm_sequence #(bus_item);
  `uvm_object_utils(bus_write_seq)

  function new(string name = "bus_write_seq");
    super.new(name);
  endfunction

  virtual task body();
    repeat (5) begin
      req = bus_item::type_id::create("req");  // a new object for every transfer
      start_item(req);                          // blocks until the sequencer grants us
      if (!req.randomize() with { op == BUS_WRITE; })
        `uvm_fatal("RAND", "bus_item randomization failed")
      finish_item(req);                         // blocks until the driver's item_done()
    end
  endtask
endclass
```

```systemverilog
// snippet: the driver loop (a pin-level drive_transfer() is in I-UVM-3C)
class bus_driver extends uvm_driver #(bus_item);
  `uvm_component_utils(bus_driver)

  function new(string name, uvm_component parent);
    super.new(name, parent);
  endfunction

  virtual task run_phase(uvm_phase phase);
    forever begin
      seq_item_port.get_next_item(req);  // blocks until a granted sequence sends an item
      drive_transfer(req);               // consumes simulation time
      seq_item_port.item_done();         // lets that sequence's finish_item() return
    end
  endtask

  virtual task drive_transfer(bus_item t);
    #10ns;                               // placeholder for the bus cycles of one transfer
  endtask
endclass
```

`req` is not declared in either class: `uvm_sequence #(REQ, RSP)` and `uvm_driver #(REQ, RSP)` both declare members `REQ req;` and `RSP rsp;` for you to use. Note the **checked randomization**: `randomize()` returns 0 when the constraints cannot be met, and an unchecked call would send whatever the item held before.

What each call does in uvm-core 2020.3.1 (`uvm_sequence_base.svh`, `uvm_sequencer.svh`):

| Call | Side | Blocks until | What it really does |
| --- | --- | --- | --- |
| `start_item(req)` | sequence | the sequencer grants this sequence | `wait_for_grant()` queues a request; arbitration runs when the driver asks for an item; then `pre_do(1)` |
| `req.randomize()` | sequence | does not block | late randomization, after the grant |
| `finish_item(req)` | sequence | the driver calls `item_done()` (or `get()`) for this item | `mid_do(req)`; `send_request()` puts the item in the request FIFO; `wait_for_item_done()`; `post_do(req)` |
| `get_next_item(req)` | driver | a granted sequence has sent an item | arbitrates if nothing is requested yet, then *peeks* the item: it stays in the FIFO |
| `item_done()` | driver | does not block (a function) | removes the item from the FIFO and wakes that sequence's `finish_item()` |

**The classic mistake: a missing `item_done()`.** The driver drives the item and loops straight back to `get_next_item()`. The item is still in the FIFO, so `get_next_item()` does not block. It reports `UVM_ERROR … Get_next_item called twice without item_done or get in between` and returns the **same** item again. The driver re-drives it forever, the sequence never leaves `finish_item()`, and the test ends only at the **phase timeout**, the time limit UVM puts on a run (see [I-UVM-1D](/curriculum/T2_Intermediate/I-UVM-1D_Reporting_and_Run_Control/index)). Fix: exactly one `item_done()` for every `get_next_item()`.

**Debugging the handshake: symptom → cause → fix.**

| Symptom in the log | Cause | Fix |
| --- | --- | --- |
| `Get_next_item called twice without item_done or get in between`, the same item driven again and again | `item_done()` missing, or two `get_next_item()` calls before one `item_done()` | One `get_next_item()`, one `item_done()` per item |
| `UVM_FATAL … [SQRBADITMDN] Item_done() called with no outstanding requests` | `item_done()` without a matching `get_next_item()`, for example called twice | Remove the extra call |
| `UVM_WARNING … [DRVCONNECT] seq_item_port … has not been connected to a sequencer`, then nothing is driven | The agent's `connect_phase` never connected the port | `drv.seq_item_port.connect(sqr.seq_item_export);` |
| `UVM_FATAL … [SEQNOTITM] attempting to start a sequence using start_item()` | A sequence was passed to `start_item()` | Start sequences with `start()` (below) |
| `UVM_FATAL … [RAND] bus_item randomization failed` | The inline constraints contradict the class constraints | Fix the constraints; never send an unrandomized item |
| Nothing at all after time 0; the test ends at once | No objection keeps `run_phase` alive | See "Starting a sequence from a test" |

The first warning to look for when a driver never receives items is `DRVCONNECT`: `uvm_driver` prints it at the end of elaboration when its `seq_item_port` is unconnected.

### Responses: data back from the driver

Sometimes the sequence needs data back: the value a read returned, or a status. The driver sends a **response**, an item of the response type, and the sequence collects it.

A sequencer can serve many sequences at once, so every item carries two ids that the sequencer uses to find the right sequence:
- `sequence_id` identifies the sequence on this sequencer;
- `transaction_id` identifies the item within that sequence.

`send_request()` (inside `finish_item`) writes both ids into the request. A response you create is new, so its ids are unset (`-1`); `rsp.set_id_info(req)` copies them from the request (§14.1.2.4). Even `req.clone()` does not copy them, because `copy()` does not copy the ids.

```systemverilog
// snippet: driver side, inside the forever loop
seq_item_port.get_next_item(req);
drive_transfer(req);
rsp = bus_item::type_id::create("rsp");
rsp.set_id_info(req);                 // without this, the sequencer cannot route rsp
rsp.op   = req.op;
rsp.addr = req.addr;
rsp.data = read_data;                 // whatever the transfer returned
seq_item_port.item_done(rsp);         // completes req and sends rsp
// Alternative: seq_item_port.item_done(); then seq_item_port.put_response(rsp);
```

```systemverilog
// snippet: sequence side, inside body()
start_item(req);
if (!req.randomize() with { op == BUS_READ; })
  `uvm_fatal("RAND", "bus_item randomization failed")
finish_item(req);
get_response(rsp);                    // blocks until a response for this sequence arrives
// or: get_response(rsp, req.get_transaction_id());  waits for this request's response
```

`item_done(rsp)` is one zero-time function call: it completes the request, then queues the response, and only after it returns can the waiting `finish_item()` resume. So by the time `finish_item()` returns, the response is already waiting and `get_response()` returns at once.

**What the explorer showed, and the rules behind it** (uvm-core 2020.3.1):
- **No `set_id_info`** → `UVM_FATAL … [SQRPUT] Driver put a response with null sequence_id`. The sequencer never guesses where a response belongs.
- **Responses never collected** → each sequence queues at most 8 responses (`get_response_queue_depth()`, §14.2.7.6). Further responses are **dropped silently**, unless the sequence called `set_response_queue_error_report_enabled(1)` (§14.2.7.5). Worse, a later `get_response()` returns the oldest response, which may belong to an earlier item.
- **Waiting for a response nobody sends** → the sequence hangs in `get_response()`, and the driver idles in `get_next_item()`.
- **A response for a sequence that has already finished** → `UVM_WARNING … Dropping response for sequence N, sequence not found`.

The discipline that avoids all four: decide per sequence whether its driver responds. If it does, collect a response after **every** item; if only some items get responses, collect those by `transaction_id`. Calling both `item_done(rsp)` and `put_response(rsp)` sends two responses for one request.

### Starting a sequence from a test

A sequence runs when something calls its `start()` task with the sequencer to run on (§14.2.3.1):

```systemverilog
// snippet: the full signature
virtual task start(uvm_sequencer_base sequencer,
                   uvm_sequence_base  parent_sequence = null,
                   int                this_priority   = -1,
                   bit                call_pre_post   = 1);
```

- `sequencer`: the sequencer the items go to, for example `env.agt.sqr`. The test can name it because the environment has been built by the time `run_phase` starts.
- `parent_sequence`: `null` for a sequence started by a test (a **root** sequence); `this` when one sequence starts another.
- `this_priority`: `-1` means "the default": 100 for a root sequence, the parent's priority for a child. It only matters for arbitration modes that use priority ([Sequencer Arbitration](/curriculum/T2_Intermediate/I-UVM-3B_Advanced_Sequencing_and_Layering/sequence-arbitration)).
- `call_pre_post`: 1 runs the `pre_body()` and `post_body()` hooks around `body()`.

`start()` is blocking: it returns when `body()` and the hooks have finished, which for our sequences means after the last `item_done()`.

**Keeping the test alive.** `run_phase` is a task phase: it ends as soon as no component holds an **objection**, a counter that says "I am still busy" ([I-UVM-1C](/curriculum/T2_Intermediate/I-UVM-1C_UVM_Phasing/index)). If nobody raises one, `run_phase` ends at time 0 and every sequence and driver loop is killed with it. There are two correct patterns.

**Pattern A: the test objects around `start()`.** This is the simplest and the one Make It Work uses.

```systemverilog
// snippet: bus_test::run_phase
virtual task run_phase(uvm_phase phase);
  bus_rw_seq seq = bus_rw_seq::type_id::create("seq");
  phase.raise_objection(this, "bus_rw_seq running");
  seq.start(env.agt.sqr);             // returns after the last item_done()
  phase.drop_objection(this, "bus_rw_seq finished");
endtask
```

A sequence can read its starting phase with `get_starting_phase()` (§14.2.4.1). It returns `null` when nobody set one, and the automatic objection then raises nothing. If you raise and drop objections by hand inside a sequence, do it in `pre_start()` and `post_start()`, which always run, and check for `null` first.

**Pitfalls.**
- *Automatic objection without a starting phase.* `set_automatic_phase_objection(1)` alone raises nothing, so `run_phase` ends at 0 ns and no item is driven. There is no error message: the log just ends with the report summary.
- *A driver that objects.* A driver's `forever` loop never finishes. Raising once at the top of the driver's `run_phase` means the test never ends; raising and dropping around each item lets the count reach 0 between items. Objections belong to the test or to the top sequence, which know when the stimulus is finished.
- *A `#` delay to "let the sequence finish".* The objection pattern already waits for exactly as long as the sequence runs.

### Practitioner depth: hooks and nested sequences

A sequence's `body()` can start other sequences, which lets you build big stimulus from small reusable pieces: a `bus_rw_seq` that runs a `bus_write_seq` and then a `bus_read_seq`, for example.

```systemverilog
// snippet: a parent sequence that runs two children on its own sequencer
virtual task body();
  bus_write_seq wr = bus_write_seq::type_id::create("wr");
  bus_read_seq  rd = bus_read_seq::type_id::create("rd");
  wr.start(m_sequencer, this);   // child of this sequence: same sequencer, our priority
  rd.start(m_sequencer, this);
endtask
```

`m_sequencer` is the sequencer this sequence was started on; `get_sequencer()` returns the same handle.

`start()` wraps `body()` in **hooks**, empty virtual tasks and functions you may override. The order, from `uvm_sequence_base::start()` (§14.2.3):
1. `pre_start()` always runs.
2. `pre_body()` runs only when `call_pre_post` is 1.
3. If a parent was passed: the parent's `pre_do(0)` and `mid_do(this)`.
4. `body()`.
5. If a parent was passed: the parent's `post_do(this)`.
6. `post_body()` runs only when `call_pre_post` is 1.
7. `post_start()` always runs.

### Practitioner depth: sequencer and driver types

The sequencer, the driver and the sequence are all parameterized by the request type `REQ` and the response type `RSP`, and `RSP` defaults to `REQ`:

```systemverilog
// snippet
typedef uvm_sequencer #(bus_item) bus_sequencer;             // REQ = RSP = bus_item
class bus_driver extends uvm_driver #(bus_item); /* ... */ endclass
class bus_rw_seq extends uvm_sequence #(bus_item); /* ... */ endclass

// With a separate response class, all three must agree:
//   uvm_sequencer #(bus_item, bus_rsp), uvm_driver #(bus_item, bus_rsp),
//   uvm_sequence #(bus_item, bus_rsp)
```

- `uvm_sequencer #(REQ, RSP)` (§15.5) provides `seq_item_export`. Most agents need no sequencer subclass at all, only the `typedef`.
- `uvm_driver #(REQ, RSP)` (§13.7) provides `seq_item_port`, a second port `rsp_port` (an analysis port, connected to the sequencer's `rsp_export`, for drivers that publish responses), and the members `req` and `rsp`.
- The port and export types include `REQ` and `RSP`, so a driver and a sequencer with different item types cannot be connected: the mismatch is a compile error at the `connect()` line.
- The agent connects them in `connect_phase` with `drv.seq_item_port.connect(sqr.seq_item_export);`. The pull port is a special TLM port ([I-UVM-2B](/curriculum/T2_Intermediate/I-UVM-2B_TLM_Connections/index)).

### Practitioner depth: driver styles

`get_next_item` with `item_done` is the default, and it is right for most drivers. Two other styles exist for specific needs (§15.2.1.2):

| Style | Calls | When `finish_item()` returns | Use it when |
| --- | --- | --- | --- |
| Pull, then complete | `get_next_item(req)`, drive, `item_done()` or `item_done(rsp)` | after the drive, at `item_done()` | almost always: the sequence knows the item has been driven |
| Poll | `try_next_item(req)`; if `req == null`, drive an idle cycle; otherwise drive and `item_done()` | after the drive | the bus needs something every cycle (idle cycles) even when no sequence has work |
| Take | `get(req)`, drive, optionally `put(rsp)` | as soon as `get()` returns, **before** the drive | the driver queues items itself, for example a pipelined bus |

`try_next_item(req)` does not wait for a sequence to appear. It waits only inside the current **time slot**, the set of events at one simulation time ([F3B](/curriculum/T1_Foundational/F3B_Scheduling_Regions/index)): one `wait_for_sequences()` call by default, which lasts a few **delta cycles**, zero-time scheduling steps ([F3C](/curriculum/T1_Foundational/F3C_Delta_Cycles_and_Race_Conditions/index)). If no sequence has offered an item by then, it returns `null`. No simulation time passes.

```systemverilog
// snippet: a polling driver that drives idle cycles
forever begin
  seq_item_port.try_next_item(req);
  if (req == null) begin
    drive_idle_cycle();              // must consume time, or the loop never advances
  end else begin
    drive_transfer(req);
    seq_item_port.item_done();
  end
end
```

`get(req)` calls `item_done()` for you before it returns, so the sequence is released while the driver is still working. A response then goes back with `put(rsp)`, which does the same as `put_response(rsp)`.

### Practitioner depth: the `` `uvm_do `` macros

The `` `uvm_do `` family hides the calls you have just learned. IEEE 1800.2 defines one form with optional arguments (Annex B.3.1.4): `` `uvm_do(SEQ_OR_ITEM, SEQR, PRIORITY, CONSTRAINTS) ``. The older `` `uvm_do_with(req, { … }) `` still compiles in uvm-core 2020.3.1, but it comes from the library's deprecated macro file and is not in IEEE 1800.2.

For an item, `` `uvm_do_with(req, { op == BUS_WRITE; }) `` (or `` `uvm_do(req, , , { op == BUS_WRITE; }) ``, where empty arguments take their defaults) expands to:
1. `` `uvm_create(req) ``: `create_item()` builds the item through the factory and sets its sequencer.
2. `start_item(req)`: wait for the grant.
3. `req.randomize() with { op == BUS_WRITE; }`: on failure it prints only the warning `RNDFLD` and **still sends the item**, with the values it held before the call (a failed `randomize()` changes nothing, IEEE 1800-2023 §18.6.3).
4. `finish_item(req)`: send it and wait for `item_done()`.

For a child sequence, `` `uvm_do(child) `` creates and randomizes the child, then calls `child.start(sequencer, this, priority, 0)`. The final `0` is `call_pre_post`, so the child's `pre_body()` and `post_body()` do not run.

The rest of the family: `` `uvm_create `` only creates; `` `uvm_send `` sends what you created without randomizing; `` `uvm_rand_send `` randomizes and sends (B.3.1.1 to B.3.1.3).

| | Explicit calls | `` `uvm_do `` family |
| --- | --- | --- |
| Lines of code | more | fewer |
| A failed `randomize()` | your check stops the test | a warning, and the item is sent anyway |
| Code between grant and send | anything you write | only the inline constraints |
| Hooks of a child sequence | your choice of `call_pre_post` | `pre_body`/`post_body` skipped |

This course writes the explicit calls, because they show where the sequence blocks and they fail loudly. You will still meet the macros in legacy code and interviews.

### Recap: the mistakes everyone makes once

| Mistake | What happens | Fix |
| --- | --- | --- |
| No `item_done()` | `Get_next_item called twice…`, the same item driven forever, the sequence stuck in `finish_item()` | One `item_done()` per `get_next_item()` |
| Response without `set_id_info(req)` | `SQRPUT` fatal | `rsp.set_id_info(req)` before `item_done(rsp)` |
| Responses never collected | silent drop after 8; later `get_response()` returns stale responses | Collect after every item, or by `transaction_id` |
| Unchecked `randomize()` | an unrandomized item is sent | `if (!req.randomize() …)` followed by `` `uvm_fatal `` |
| Unregistered item field | not copied, not compared: false matches | Field macro, or `do_copy` plus `do_compare` |
| Automatic objection without a starting phase | test ends at 0 ns, no error | `set_starting_phase(phase)` first |
| Objections in the driver | test never ends, or ends between items | Object in the test or the top sequence |

## Make It Work

### A sequence that writes, reads back and checks

This example puts the whole lesson in one file: an item with hand-written methods, a sequence that writes four random words and reads each one back through responses, a driver, an agent, an environment, a test that objects around `start()`, and `tb_top`.

The driver has no pins. It plays the memory itself, so the example needs no interface and no DUT, and it takes 10 ns per transfer to stand in for real bus cycles. [I-UVM-3C](/curriculum/T2_Intermediate/I-UVM-3C_First_Complete_Testbench/index) replaces it with a pin-level driver and a real DUT.

**Run it.** Compile uvm-core 2020.3.1 (or your simulator's built-in UVM library) together with this file, with `tb_top` as the top module, and run. `run_test("bus_test")` names the test, so no plusarg is needed; `+UVM_TESTNAME=bus_test` would override it (Annex G.2.1). The exact compile and run switches are tool-dependent. No simulator was available to the course authors, so the code was checked by reading it against IEEE 1800-2023 and the uvm-core 2020.3.1 source.

```systemverilog
// compile
// tb_top.sv: the package and the top module in one file
`include "uvm_macros.svh"

package bus_pkg;
  timeunit 1ns;
  timeprecision 1ps;

  import uvm_pkg::*;

  typedef enum bit {BUS_READ, BUS_WRITE} bus_op_e;

  // One bus transfer. The driver also uses this class for responses.
  class bus_item extends uvm_sequence_item;
    rand bus_op_e   op;
    rand bit [7:0]  addr;
    rand bit [31:0] data;   // write data; in a response, the data read

    constraint c_word_aligned { addr[1:0] == 2'b00; }

    `uvm_object_utils(bus_item)

    function new(string name = "bus_item");
      super.new(name);
    endfunction

    virtual function void do_copy(uvm_object rhs);
      bus_item rhs_;
      super.do_copy(rhs);
      if (!$cast(rhs_, rhs)) begin
        `uvm_fatal("BUS_ITEM/COPY", "do_copy: rhs is not a bus_item")
        return;
      end
      op   = rhs_.op;
      addr = rhs_.addr;
      data = rhs_.data;
    endfunction

    virtual function bit do_compare(uvm_object rhs, uvm_comparer comparer);
      bus_item rhs_;
      if (!$cast(rhs_, rhs)) return 0;
      return super.do_compare(rhs, comparer) &&
             op == rhs_.op && addr == rhs_.addr && data == rhs_.data;
    endfunction

    virtual function string convert2string();
      return $sformatf("%s addr=0x%02h data=0x%08h", op.name(), addr, data);
    endfunction
  endclass

  // Writes n_pairs random words, then reads each address back and checks it.
  class bus_rw_seq extends uvm_sequence #(bus_item);
    `uvm_object_utils(bus_rw_seq)

    int unsigned n_pairs = 4;

    function new(string name = "bus_rw_seq");
      super.new(name);
    endfunction

    virtual task body();
      bit [31:0]   expected [bit [7:0]];  // address -> last data written there
      bit [7:0]    written [$];           // addresses in write order
      int unsigned n_ok;

      // Writes. The driver answers every item, so collect every response.
      repeat (n_pairs) begin
        req = bus_item::type_id::create("req");
        start_item(req);
        if (!req.randomize() with { op == BUS_WRITE; })
          `uvm_fatal("RAND", "write item failed to randomize")
        finish_item(req);
        get_response(rsp);
        expected[req.addr] = req.data;
        written.push_back(req.addr);
      end

      // Reads: one per written address, checked against the expected data.
      foreach (written[i]) begin
        bit [7:0] rd_addr = written[i];
        req = bus_item::type_id::create("req");
        start_item(req);
        // local:: resolves rd_addr here, not in bus_item (IEEE 1800-2023 §18.7.1)
        if (!req.randomize() with { op == BUS_READ; addr == local::rd_addr; })
          `uvm_fatal("RAND", "read item failed to randomize")
        finish_item(req);
        get_response(rsp);
        if (rsp.data != expected[rd_addr])
          `uvm_error("RD_MISMATCH", $sformatf("addr=0x%02h got 0x%08h, expected 0x%08h",
                                                rd_addr, rsp.data, expected[rd_addr]))
        else begin
          n_ok++;
          `uvm_info("RD_OK", rsp.convert2string(), UVM_LOW)
        end
      end

      `uvm_info("SEQ_DONE", $sformatf("%0d of %0d reads matched", n_ok, written.size()),
                UVM_LOW)
    endtask
  endclass

  // A driver with no pins: it models the memory itself.
  class bus_driver extends uvm_driver #(bus_item);
    `uvm_component_utils(bus_driver)

    protected bit [31:0] mem [bit [7:0]];

    function new(string name, uvm_component parent);
      super.new(name, parent);
    endfunction

    virtual task run_phase(uvm_phase phase);
      forever begin
        seq_item_port.get_next_item(req);  // blocks until a sequence sends an item
        #10ns;                             // stands in for the bus cycles of one transfer
        rsp = bus_item::type_id::create("rsp");
        rsp.set_id_info(req);              // copy sequence_id and transaction_id
        rsp.op   = req.op;
        rsp.addr = req.addr;
        if (req.op == BUS_WRITE) begin
          mem[req.addr] = req.data;
          rsp.data      = req.data;
        end else begin
          rsp.data = mem.exists(req.addr) ? mem[req.addr] : '0;
        end
        `uvm_info("DRV", rsp.convert2string(), UVM_MEDIUM)
        seq_item_port.item_done(rsp);      // completes req and returns rsp
      end
    endtask
  endclass

  typedef uvm_sequencer #(bus_item) bus_sequencer;

  class bus_agent extends uvm_agent;
    `uvm_component_utils(bus_agent)

    bus_sequencer sqr;
    bus_driver    drv;

    function new(string name, uvm_component parent);
      super.new(name, parent);
    endfunction

    // Always active in this lesson; I-UVM-2A adds the is_active check.
    virtual function void build_phase(uvm_phase phase);
      super.build_phase(phase);
      sqr = bus_sequencer::type_id::create("sqr", this);
      drv = bus_driver::type_id::create("drv", this);
    endfunction

    virtual function void connect_phase(uvm_phase phase);
      drv.seq_item_port.connect(sqr.seq_item_export);
    endfunction
  endclass

  class bus_env extends uvm_env;
    `uvm_component_utils(bus_env)

    bus_agent agt;

    function new(string name, uvm_component parent);
      super.new(name, parent);
    endfunction

    virtual function void build_phase(uvm_phase phase);
      super.build_phase(phase);
      agt = bus_agent::type_id::create("agt", this);
    endfunction
  endclass

  class bus_test extends uvm_test;
    `uvm_component_utils(bus_test)

    bus_env env;

    function new(string name, uvm_component parent);
      super.new(name, parent);
    endfunction

    virtual function void build_phase(uvm_phase phase);
      super.build_phase(phase);
      env = bus_env::type_id::create("env", this);

    endtask
```

### How to build it yourself

1. **Write the item.** Declare the fields `rand`, add constraints, register with `` `uvm_object_utils ``, and write `do_copy`, `do_compare` and `convert2string` (or field macros).
2. **Write the sequence.** Extend `uvm_sequence #(bus_item)`, give it a constructor with a default name, and in `body()` repeat: create, `start_item`, checked `randomize()`, `finish_item`, and `get_response` if the driver responds.
3. **Write the driver loop.** One `get_next_item()` and exactly one `item_done()` per item. Build each response with `set_id_info(req)`.
4. **Declare the sequencer** with a `typedef`, then build both in an agent and connect `seq_item_port` to `seq_item_export` in `connect_phase`.
5. **Start the sequence in the test** on `env.agt.sqr`, inside an objection (pattern A) or with the automatic objection (pattern B).
6. **Run, then read the log**: one `DRV` line per item, one `RD_OK` per read, and `UVM_ERROR :    0`.

### Break it on purpose: four debugging drills

Make one change at a time, predict the log, then run (or reason it through with the explorer).

1. **Delete `seq_item_port.item_done(rsp);`.** Every 10 ns the driver logs `Get_next_item called twice without item_done or get in between` and drives W1 again. The sequence stays in `finish_item(W1)` until the phase timeout ends the test with a fatal (timeouts are in [I-UVM-1D](/curriculum/T2_Intermediate/I-UVM-1D_Reporting_and_Run_Control/index)).
2. **Delete `rsp.set_id_info(req);`.** At 10 ns: `UVM_FATAL … [SQRPUT] Driver put a response with null sequence_id`.
3. **Replace pattern A with `seq.set_automatic_phase_objection(1); seq.start(env.agt.sqr);`, without `set_starting_phase(phase)`.** The run ends at time 0 with no `DRV` lines and no error, only the report summary.
4. **Delete `get_response(rsp);` from the write loop only.** Usually the test still passes, for the wrong reason: each read's `get_response()` pops the oldest response, which is a *write's* response, and its data happen to equal the data written to the same address. If two writes hit the same address, a read gets the wrong write's data and `RD_MISMATCH` fires. Guard against this by collecting every response, or with `get_response(rsp, req.get_transaction_id())`, or by checking `rsp.op == BUS_READ`.

**Checklist before moving on:**
- [ ] I can say what `start_item`, `finish_item`, `get_next_item` and `item_done` each wait for.
- [ ] Every field of my item is copied and compared, by a field macro or by `do_copy` and `do_compare`.
- [ ] Every `randomize()` call is checked.
- [ ] My driver calls exactly one `item_done()` per `get_next_item()`, and every response has `set_id_info(req)`.
- [ ] My sequence collects every response its driver sends.
- [ ] My test keeps `run_phase` alive with an objection around `start()`, or gives the sequence a starting phase before turning on the automatic objection.
- [ ] My driver raises no objections.

## Push Further

### Expert: What start() really does

Read `uvm_sequence_base::start()` in uvm-core 2020.3.1 (`src/seq/uvm_sequence_base.svh`; IEEE 1800.2-2020 §14.2.3.1) and these details fall out:
- **One run at a time.** A sequence object holds a one-key semaphore while it runs. Calling `start()` on an object that is still running is `UVM_FATAL [SEQ_NOT_DONE] Sequence … already started`. Starting the same object again *after* it finished is legal, but most teams create a new object per start so that no state carries over.
- **Priority.** A priority below `-1` is the fatal `SEQPRI`. `-1` becomes 100 for a root sequence and the parent's priority for a child.
- **A clean response queue.** `start()` calls `clear_response_queue()` first, so responses left from an earlier run are discarded.
- **Delta cycles between hooks.** `start()` forks a process and puts a `#0` before the automatic objection and `pre_start()`, before `pre_body()`, `body()`, `post_body()` and `post_start()`, and after `body()`. Code that depends on the exact order of other zero-time processes can see a different order than it expects.
- **The automatic objection** is raised after that first `#0`, before `pre_start()`, and dropped after `post_start()`.
- **A killed sequence.** If something kills the process that runs `body()` without calling `kill()`, for example an errant `disable fork`, `start()` reports `SEQBDYZMB` and kills the sequence properly.

### Expert: Driver-side corner cases

All from uvm-core 2020.3.1 (`uvm_sequencer.svh`, `uvm_sequencer_param_base.svh`; §15.2.1.2):
- **`try_next_item` and time.** It waits `wait_for_sequences()` (by default to the NBA region of the current time slot) up to `m_wait_for_sequences_count` times, which is 1 unless the sequencer's `wait_for_sequences_count` resource is set (uvm-core impl.). A sequence that consumes time between `start_item()` and `finish_item()` makes `try_next_item` report `TRY_NEXT_BLOCKED` and return `null`, even though the sequence won arbitration. Never put delays between the two calls.
- **One FIFO slot.** The request FIFO holds one item. If two processes call `get_next_item()` on one port, the second item cannot be stored and `send_request` stops the test with `SQRSNDREQGNI` ("Concurrent calls to get_next_item() not supported").
- **No current item with `get()`.** `get_current_item()` (§14.3.3.2) returns the item between `get_next_item`/`peek` and `item_done`/`get`. A driver that only calls `get()` never has a current item.
- **`peek()` then `get()`.** `peek()` (§15.2.1.2.7) returns the item without completing it, and a later `get()` or `item_done()` completes it. This is how a driver can look at an item before deciding to accept it.

### Expert: Response routing internals

- **Where the ids come from.** `send_request` assigns a `transaction_id` when the item still has `-1`, and always writes the sequence's `sequence_id` for this sequencer. `set_id_info` copies both (§14.1.2.4). A request object that is sent twice keeps its first `transaction_id`, which is one more reason to create a new item per transfer.
- **`SQRPUT` is not universal.** The null-id check in `uvm_sequencer_param_base::put_response` is compiled out when the vendor define `CDNS_NO_SQR_CHK_SEQ_ID` is set; the response is then dropped without a message (tool-dependent).
- **The standard and the code disagree on overflow reporting.** The source comment says overflow errors are reported by default, but the flag `response_queue_error_report_enabled` starts at 0, so uvm-core 2020.3.1 drops silently until you call `set_response_queue_error_report_enabled(1)` (§14.2.7.5). `set_response_queue_depth(-1)` makes the queue unbounded (§14.2.7.7), at the cost of memory if nobody collects.
- **`get_response(rsp, tid)`** waits until a response with that `transaction_id` arrives and leaves other responses in the queue. A related trap: `wait_for_item_done(tid)` for an item that has already completed waits forever, because it missed the notification.
- **Out-of-order responses.** For drivers that answer in a different order than requests arrived, a sequence can turn on `use_response_handler(1)` and override `response_handler()` (§14.2.7.1); that is taught in [the I-UVM-3B handshake lesson](/curriculum/T2_Intermediate/I-UVM-3B_Advanced_Sequencing_and_Layering/sequencer-driver-handshake).

### Expert: Starting phase and default sequences

- **The starting phase locks on first read.** `get_starting_phase()` locks the value, and a later `set_starting_phase()` reports `UVM/SEQ/SP/SET` and is ignored (`uvm_sequence_base.svh`). The legacy public member `starting_phase` (marked `@uvm-compat` in uvm-core 2020.3.1) still compiles; writing it after the lock reports `UVM/SEQ/SP/GET` on the next read. Use the methods in new code.
- **Default sequences.** A sequencer starts a **default sequence** in each task phase when a resource named `default_sequence` is set for the scope `<sequencer path>.<phase>_phase`, for example `uvm_test_top.env.agt.sqr.main_phase`; the value is a sequence type wrapper or a sequence object (`uvm_sequencer_base::start_phase_sequence`; the configuration database that holds such resources is taught in [I-UVM-2C](/curriculum/T2_Intermediate/I-UVM-2C_Configuration_and_Resources/index)). From the command line, without touching the test: `+uvm_set_default_sequence=uvm_test_top.env.agt.sqr,main_phase,bus_rw_seq` (Annex G.2.9). The phase field needs the `_phase` suffix.
- **A default sequence does not object by itself.** `start_phase_sequence` sets the starting phase, randomizes the sequence and starts it, but raises nothing. The sequence must turn on the automatic objection (for example in its constructor) or raise through `get_starting_phase()`, or the phase ends at once.
- **Why many teams avoid default sequences:** the stimulus is invisible in the test code, and a misspelt scope fails silently. Starting sequences explicitly in the test, as this lesson does, is easier to read and debug.

### Expert: Randomization corner cases

- **Name capture in inline constraints.** In `req.randomize() with { addr == addr; }`, both names resolve to the item's own `addr`, so the constraint is always true. Unqualified names are looked up in the item first; `local::addr` forces the caller's variable (IEEE 1800-2023 §18.7.1).
- **Macros do not fail loudly.** `` `uvm_do `` and `` `uvm_rand_send `` print the warning `RNDFLD` and continue when randomization fails.
- **Switching randomization off.** `set_randomize_enabled(0)` (§14.2.2.3) stops `` `uvm_do `` (and default-sequence start-up) from randomizing a child sequence that you configured by hand. The legacy bit `do_not_randomize` does the same in old code (`@uvm-compat`).
- **Sequences can be randomized too.** A sequence with `rand` members, such as a `rand int unsigned n_items` with a constraint, can be randomized before `start()`; the kata below uses this.

### Expert: Performance and object lifetime

- **A new item per transfer.** Monitors, scoreboards and response queues may keep the handle you sent. Reusing one object for every transfer makes all of them see the latest values. Allocation is cheap compared with debugging that.
- **Field macros cost run time.** In uvm-core 2020.3.1 every `copy()`, `compare()`, `print()` and `record()` walks the field macros through `do_execute_op` before calling your `do_*` hook. Hand-written methods skip that walk. How much it matters depends on the simulator and the item size; measure before rewriting (the profiling method is in [E-PERF-1](/curriculum/T4_Expert/E-PERF-1_UVM_Performance/index)).
- **Transaction recording.** Sequencers record every item by default when recording is enabled; `disable_auto_item_recording()` (§15.2.1.2.10) turns that off for a busy sequencer. Whether recording costs anything depends on the tool's recorder (tool-dependent).
- **Responses are memory.** An unbounded response queue (`set_response_queue_depth(-1)`) that nobody drains grows for the whole test.

### Kata: N randomized items with response checking

**Task.** Starting from the Make It Work file:
1. Write `bus_burst_check_seq`, a sequence with `rand int unsigned n_items` constrained to 1 to 16. For each item it writes a random word, immediately reads it back, and checks the read data. Use `get_response(rsp, req.get_transaction_id())` for both responses.
2. In `bus_test`, randomize the sequence (checked), then start it with **pattern B**: a starting phase and the automatic objection, and no objection in the test.
3. Predict the log for `n_items = 3`: how many `DRV` lines, how many check lines, and the time of the last line.

**Acceptance:** one check line per item, `UVM_ERROR :    0`, and the run ends when the sequence ends.

<details>
<summary>Worked solution (try it first)</summary>

```systemverilog
// snippet: add to bus_pkg, after bus_driver
class bus_burst_check_seq extends uvm_sequence #(bus_item);
  `uvm_object_utils(bus_burst_check_seq)

  rand int unsigned n_items;
  constraint c_n { n_items inside {[1:16]}; }

  function new(string name = "bus_burst_check_seq");
    super.new(name);
  endfunction

  virtual task body();
    repeat (n_items) begin
      bit [7:0]  wr_addr;
      bit [31:0] wr_data;

      req = bus_item::type_id::create("req");
      start_item(req);
      if (!req.randomize() with { op == BUS_WRITE; })
        `uvm_fatal("RAND", "write item failed to randomize")
      finish_item(req);
      get_response(rsp, req.get_transaction_id());   // the write's own response
      wr_addr = req.addr;
      wr_data = req.data;

      req = bus_item::type_id::create("req");
      start_item(req);
      if (!req.randomize() with { op == BUS_READ; addr == local::wr_addr; })
        `uvm_fatal("RAND", "read item failed to randomize")
      finish_item(req);
      get_response(rsp, req.get_transaction_id());   // the read's own response
      if (rsp.data != wr_data)
        `uvm_error("CHK", $sformatf("addr=0x%02h read 0x%08h, wrote 0x%08h",
                                    wr_addr, rsp.data, wr_data))
      else
        `uvm_info("CHK", {"match: ", rsp.convert2string()}, UVM_LOW)
    end
  endtask
endclass
```

```systemverilog
// snippet: bus_test::run_phase with pattern B
virtual task run_phase(uvm_phase phase);
  bus_burst_check_seq seq = bus_burst_check_seq::type_id::create("seq");
  if (!seq.randomize() with { n_items == 3; })
    `uvm_fatal("RAND", "sequence failed to randomize")
  seq.set_starting_phase(phase);
  seq.set_automatic_phase_objection(1);
  seq.start(env.agt.sqr);
endtask
```

**Prediction for `n_items = 3`:** six `DRV` lines (W, R, W, R, W, R) at 10, 20, 30, 40, 50 and 60 ns; three `CHK … match` lines at 20, 40 and 60 ns; the run ends at 60 ns.

**Why it works:** the driver answers every item, and the sequence collects every response by its own `transaction_id`, so no response is left in the queue and none can be taken by the wrong check. `local::wr_addr` makes the read use the sequence's variable, not the item's own `addr`.

**Mutations to try:** delete `seq.set_starting_phase(phase);` (the run ends at 0 ns); delete `rsp.set_id_info(req);` in the driver (`SQRPUT` at 10 ns); delete `item_done(rsp)` (`Get_next_item called twice…` every 10 ns).
