## Quick Take
- **What it is:** `uvm_sequence_item` models the transaction data. `uvm_sequence` holds the procedural code that creates items and hands them, one at a time, to the driver through the sequencer.
- **Why it matters:** Sequencing separates the *what* from the *how*. You can reuse the "memory read" sequence across fifty tests without rewriting the driver that wiggles the pins.
- **The analogy:** The `sequence_item` is the letter. The `sequence` is the writer. The `driver` is the mail carrier. The `sequencer` is the post-office counter: the carrier asks for the next letter, and the counter decides which waiting writer is served. Nothing is stockpiled; a letter is only taken when the carrier asks.

> **Retention hook:** Two blocking pairs, one on each side. The sequence calls `start_item` then `finish_item`. The driver calls `get_next_item` then `item_done`. `finish_item` returns only when `item_done` is called.

## Build Your Mental Model
### The payload: `uvm_sequence_item` (IEEE 1800.2 clause 14.1)
A sequence item holds randomizable fields, constraints, and the copy, compare and print behaviour that scoreboards rely on. Declare a type before you use it: the enum `typedef` comes first, then the field macros that refer to it.

<InteractiveCode>
```systemverilog
class mem_item extends uvm_sequence_item;
  typedef enum { READ, WRITE } op_t;   // declared before the macros use it

  rand bit [31:0] addr;
  rand bit [31:0] data;
  rand op_t       op;

  constraint c_addr_align { addr % 4 == 0; }

  // Register fields for print, copy, compare
  `uvm_object_utils_begin(mem_item)
    `uvm_field_int(addr, UVM_ALL_ON | UVM_HEX)
    `uvm_field_int(data, UVM_ALL_ON | UVM_HEX)
    `uvm_field_enum(op_t, op, UVM_ALL_ON)
  `uvm_object_utils_end

  function new(string name = "mem_item");
    super.new(name);
  endfunction

  // A field that is neither registered above nor handled in do_copy()/do_compare()
  // is NOT copied by clone() and NOT checked by compare().
endclass
```
</InteractiveCode>

### The handshake: sequence ↔ sequencer ↔ driver
A sequence runs its `body()` task. Each item goes through two blocking calls on the sequence side, and two on the driver side. The sequencer sits between them and only grants a request when the driver asks for work.

Pick **Clean handshake**, predict where the sequence is while the driver is busy, then step through. Both code panels highlight the line each side is executing. Then try the **Bug** scenarios.

The same two classes, written out:

```systemverilog
// THE SEQUENCE
class my_simple_sequence extends uvm_sequence #(mem_item);
  `uvm_object_utils(my_simple_sequence)

  function new(string name = "my_simple_sequence");
    super.new(name);
  endfunction

  virtual task body();
    repeat (5) begin
      req = mem_item::type_id::create("req");
      start_item(req);                       // blocks until the sequencer grants this request
      if (!req.randomize() with { op == WRITE; })
        `uvm_error("RAND", "mem_item randomization failed")
      finish_item(req);                      // blocks until the driver calls item_done()
    end
  endtask
endclass

// THE DRIVER
class my_driver extends uvm_driver #(mem_item);
  `uvm_component_utils(my_driver)

  virtual mem_if vif;                        // set in build_phase (see I-UVM-2A)

  function new(string name, uvm_component parent);
    super.new(name, parent);
  endfunction

  virtual task run_phase(uvm_phase phase);
    forever begin
      seq_item_port.get_next_item(req);      // blocks until a sequence is granted
      drive_transfer(req);                   // pin-level work, consumes time
      seq_item_port.item_done();             // lets finish_item() return
    end
  endtask

  virtual task drive_transfer(mem_item t);
    @(vif.drv_cb);
    vif.drv_cb.addr  <= t.addr;
    vif.drv_cb.wdata <= t.data;
    vif.drv_cb.we    <= (t.op == mem_item::WRITE);
  endtask
endclass
```

What each call does in uvm-core 2020.3.1:

| Call | Side | Blocks until | What it really does |
| --- | --- | --- | --- |
| `start_item(req)` | sequence | the sequencer grants the request | `wait_for_grant()` queues a request; arbitration runs when the driver calls `get_next_item()`; then `pre_do(1)` |
| `req.randomize()` | sequence | does not block | late randomization: after the grant, so constraints can use the latest state |
| `finish_item(req)` | sequence | the driver calls `item_done()` | `mid_do(req)`, `send_request()` puts the item in the request FIFO, `wait_for_item_done()`, `post_do(req)` |
| `get_next_item(req)` | driver | an item is in the request FIFO | arbitrates if nothing is requested yet, then *peeks* the item (it stays in the FIFO) |
| `item_done()` | driver | does not block | removes the item from the FIFO and wakes the sequence's `finish_item()` |

### Breaking down `` `uvm_do ``
`` `uvm_do `` hides the same calls. In IEEE 1800.2 it has one form with optional arguments: `` `uvm_do(SEQ_OR_ITEM, SEQR, PRIORITY, CONSTRAINTS) ``. The older `` `uvm_do_with(req, {...}) `` still compiles in uvm-core 2020.3.1, but it comes from the library's deprecated macro file.

For an item, `` `uvm_do(req) `` does:
1. `` `uvm_create `` → `create_item()`: create the item and set its sequencer.
2. `start_item(req)`: wait for the grant.
3. `req.randomize()`: on failure it only prints the warning `RNDFLD` and **still sends the item**.
4. `finish_item(req)`: send it and wait for `item_done()`.

For a child *sequence*, `` `uvm_do(child) `` randomizes the child and then calls `child.start(sequencer, this, priority, 0)`. The last argument `0` means `pre_body()` and `post_body()` of the child are skipped. The explorer further down shows this.

## Make It Work
1. **Define the item:** extend `uvm_sequence_item`, declare types first, register fields, add constraints.
2. **Define the sequence:** extend `uvm_sequence #(mem_item)`, give it a constructor, and write `body()` with `start_item`/`finish_item` (or `` `uvm_do ``).
3. **Define the driver loop:** one `get_next_item()` and exactly one `item_done()` per item.
4. **Start the sequence from the test, inside an objection.** `start()` is a blocking task that returns after the last `item_done()`. Without the objection, `run_phase` ends at 0 ns and nothing is driven.

```systemverilog
class mem_test extends uvm_test;
  `uvm_component_utils(mem_test)
  mem_env env;

  function new(string name, uvm_component parent);
    super.new(name, parent);
  endfunction

  function void build_phase(uvm_phase phase);
    super.build_phase(phase);
    env = mem_env::type_id::create("env", this);
  endfunction

  task run_phase(uvm_phase phase);
    my_simple_sequence seq = my_simple_sequence::type_id::create("seq");
    phase.raise_objection(this);
    seq.start(env.agt.sqr);            // returns after the 5th item_done()
    phase.drop_objection(this);
  endtask
endclass
```

## Push Further
- **Responses.** A driver can answer with `seq_item_port.item_done(rsp)`, after `rsp.set_id_info(req)`. The sequence collects it with `get_response(rsp)`. Each sequence keeps at most 8 uncollected responses by default; the 9th is dropped. The handshake explorer has a scenario for each of these.
- **Polling drivers.** `try_next_item(req)` returns `null` instead of blocking, for drivers that must drive idle cycles when no sequence has work.
- **Priority.** `seq.start(sqr, null, 300)` sets a priority. It only matters when the sequencer uses a priority-aware arbitration mode; see [Sequencer Arbitration](/curriculum/T2_Intermediate/I-UVM-3B_Advanced_Sequencing_and_Layering/sequence-arbitration).
- **Several agents at once.** Virtual sequences start sequences on several agent sequencers; see I-UVM-3B.

## Explore Nested Sequence Execution

A sequence's `body()` can start other sequences. `start()` wraps each `body()` in hooks, and which hooks run depends on how the child is started. <UvmSequenceHierarchyVisualizer />

The rules the explorer applies, from `uvm_sequence_base::start()`:
- `pre_start()` and `post_start()` always run.
- `pre_body()` and `post_body()` run only when the fourth argument of `start()`, `call_pre_post`, is 1 (its default). `` `uvm_do `` passes 0.
- When a parent is passed, the parent's `pre_do(0)` and `mid_do(child)` run just before the child's `body()`, and `post_do(child)` right after it.
- A child started with `child.start(m_sequencer)` has no parent. It is not covered by the parent's `lock()`, so a locked parent deadlocks it. Tick **Debug: top_seq calls lock() first** to see it.

## Interview Pitfalls
**The silently skipped field.**
Interviewers show an item with `rand byte payload[$];` that is not in the field macros and has no `do_copy()`/`do_compare()`. "What happens when the scoreboard compares the original with a `clone()`?" SystemVerilog queues and dynamic arrays are copied by value, so there is no shared pointer. The real problem: `clone()` never copies the unregistered field, so the clone's `payload` is empty, and `compare()` ignores the field and reports a match. Register every field, or copy and compare it yourself. Class-handle members are the case that is copied shallowly unless you deep-copy them.

**The missing `item_done()`.**
If the driver loops without calling `item_done()`, its next `get_next_item()` reports `UVM_ERROR … Get_next_item called twice without item_done or get in between` and returns the **same** item again. The driver re-drives that item forever while the sequence stays blocked in `finish_item()`. The test only ends at the phase timeout.

**The response nobody can route.**
`rsp = mem_item::type_id::create("rsp"); seq_item_port.item_done(rsp);` without `rsp.set_id_info(req)` stops the test with `UVM_FATAL [SQRPUT] Driver put a response with null sequence_id`.
