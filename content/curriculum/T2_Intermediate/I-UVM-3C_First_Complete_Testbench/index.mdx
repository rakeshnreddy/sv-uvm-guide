## Quick Take

- **What it is:** A complete UVM testbench (TB) for one small design under test (DUT): a top module that makes the clock, the reset, the DUT and its interface, and starts UVM; a package of classes (an item, two sequences, a driver, a monitor, an agent with its configuration object, a scoreboard, a coverage subscriber, an environment and two tests); and a log that ends with a verdict. Every piece was taught on its own in I-UVM-1A to I-UVM-3A. This lesson assembles them into one bench that compiles, runs, checks itself and can be debugged from its log (IEEE 1800.2-2020 §13, §14, Annex C.4, Annex F.7).
- **Why it matters:** This bench is the shape of every UVM environment you will meet, and it is the gate of Tier 2 (milestone M2, and the seed of M3). The hard part is no longer any single class: it is the joins between them. A virtual interface that never arrives, an objection nobody raises, an analysis port nobody connects, a driver that forgets `item_done()`: each one gives a bench that compiles cleanly and then hangs, ends at 0 ns, or "passes" having checked nothing. You learn to make the bench prove it ran, and to read those four failures straight from the log.
- **The Analogy:** A new restaurant's opening night. The building (`tb_top`) supplies power and the street address (clock, reset, the interface). The manager (the test) hands each station its instructions (the configuration object) and decides the menu (which sequence runs). The kitchen line (the agent) takes orders (sequence items), cooks them (the driver), and a runner (the monitor) reports every plate that actually left the pass. The inspector (the scoreboard) checks every plate against the recipe and, at closing, counts the plates that never arrived. *Where it breaks:* a real inspector who saw no plates would notice that the kitchen never opened; a scoreboard reports "0 mismatches" happily unless you make it count, and a real restaurant does not close itself the moment nobody is holding the door (UVM's run phase does, unless someone raises an objection).

**You will be able to:**
1. **Write** the top module: a clock and a reset, the DUT, an interface with clocking blocks, a `uvm_config_db` set of the virtual interface, and `run_test()`.
2. **Write** the test, env and agent (with a configuration object that selects active or passive), the driver, monitor and sequencer, a sequence, and a scoreboard fed through `uvm_tlm_analysis_fifo` with `check_phase` accounting; and **organize** them in a package compiled in the right order.
3. **Run** two tests from the command line, one of them changing the stimulus through a factory override, and **predict** the key lines of each log.
4. **Diagnose** the four classic bring-up failures from their logs: a null virtual interface, an objection never raised or never dropped, an unconnected analysis port, and a missing `item_done()`.
5. **Reuse** the same agent, unchanged, as a passive agent in a second environment and **check** the topology and the scoreboard count (the M2 seed).

## Build Your Mental Model

### Words you need first

Each term was taught in an earlier lesson; this list is a reminder, with the link to go back to.

- **Component:** a long-lived UVM object in the testbench tree (test, env, agent, driver, monitor, sequencer, scoreboard), created in `build_phase` with `::type_id::create(name, parent)` ([I-UVM-1A](/curriculum/T2_Intermediate/I-UVM-1A_Components/index)).
- **Phase:** a step every component goes through in a fixed order: `build_phase` (create children, top-down), `connect_phase` (connect ports), `end_of_elaboration_phase`, `run_phase` (the only one that takes simulation time), then `check_phase` and `report_phase` (bottom-up, at the end) ([I-UVM-1C](/curriculum/T2_Intermediate/I-UVM-1C_UVM_Phasing/index)).
- **Objection:** a counter on a task phase. `run_phase` lasts while at least one component holds an objection, and ends as soon as none does ([I-UVM-1C](/curriculum/T2_Intermediate/I-UVM-1C_UVM_Phasing/index)).
- **Sequence item, sequence, sequencer, driver:** the item is one unit of stimulus; a sequence creates items; the sequencer hands them, one at a time, to the driver, which turns each into pin activity and then calls `item_done()` ([I-UVM-3A](/curriculum/T2_Intermediate/I-UVM-3A_Fundamentals/index)).
- **Monitor and analysis port:** the monitor watches the pins and publishes one new item per observed transfer with `ap.write(t)`; every connected subscriber receives the same handle. A **subscriber** (`uvm_subscriber`) is a component with a built-in analysis export, `analysis_export`, whose `write()` function you implement; a coverage collector is the usual example. **Promoting** a port means connecting a child's port to a port of the same kind on its parent, so that the parent's users see one port on its boundary ([I-UVM-2A](/curriculum/T2_Intermediate/I-UVM-2A_Component_Roles/index), [I-UVM-2B](/curriculum/T2_Intermediate/I-UVM-2B_TLM_Connections/index)).
- **Analysis FIFO:** `uvm_tlm_analysis_fifo #(T)`, an unbounded buffer whose `analysis_export` accepts `write()` calls and whose `get()` hands the items, in order, to a thread that may wait ([I-UVM-2B](/curriculum/T2_Intermediate/I-UVM-2B_TLM_Connections/index)).
- **Virtual interface:** a class variable that holds a handle to an interface instance in the module hierarchy, so class code can reach the pins ([F4B](/curriculum/T1_Foundational/F4B_Interfaces_and_Modports/index)). A **clocking block** inside the interface defines when those pins are sampled and driven relative to a clock edge ([F4C](/curriculum/T1_Foundational/F4C_Clocking_Blocks/index)).
- **Elaboration, time slot, regions:** elaboration is the step in which the tool builds the design hierarchy (modules, interfaces, their instances) before simulation time 0. A time slot is all the activity at one simulation time, processed in ordered regions; this lesson names three: Active (where `always_ff` and class code run), NBA (where nonblocking assignments update) and Re-NBA (where clocking-block drives update) ([F3B](/curriculum/T1_Foundational/F3B_Scheduling_Regions/index)).
- **Configuration database:** `uvm_config_db#(T)`, a typed store keyed by a path in the component tree; `set()` publishes, `get()` fetches ([I-UVM-2C](/curriculum/T2_Intermediate/I-UVM-2C_Configuration_and_Resources/index)).
- **Factory and override:** `::type_id::create()` asks the factory for an object; a **type override** makes it return a derived class instead ([I-UVM-1B](/curriculum/T2_Intermediate/I-UVM-1B_The_UVM_Factory/index)).
- **Report summary:** the block UVM prints at the end of every run with the count of `UVM_INFO`, `UVM_WARNING`, `UVM_ERROR` and `UVM_FATAL` messages; a run passes only if errors and fatals are both 0 and the bench proves it checked something ([I-UVM-1D](/curriculum/T2_Intermediate/I-UVM-1D_Reporting_and_Run_Control/index)).

**Debrief.** The stimulus comes from `seq`, an object, not a component: it is created and started by the test in `run_phase`. Only `drv` touches the DUT's inputs, and only `mon` reads the pins on behalf of the checkers. The driver finds `mem_if0` through `cfg`, never through a hierarchical path: `tb_top` publishes the handle, the test copies it into the configuration object, and the agent passes the same object to its children. The scoreboard sits in the env, beside the agent, because it judges the DUT, not the protocol. The names in the picture are exactly the names in the code below.

Seven ideas make this bench work. The rest of this section takes them one at a time: the DUT and its protocol; files and compile order; `tb_top`; the agent and its configuration; the driver and monitor; the scoreboard and its accounting; and the end of the test. Then come the two tests, the four bring-up failures and the passive reuse.

### The DUT and its protocol

Write a bench from the specification, not from the RTL. The DUT, `mem_dut`, is a 16-entry, 8-bit memory with a one-cycle request bus:

| Signal | Direction | Meaning |
|---|---|---|
| `clk` | input | Everything happens on its rising edge. |
| `rst_n` | input | Synchronous reset, active low: every location and `rdata` become 0. |
| `valid` | input | A request is present this cycle. The DUT accepts it at the rising edge where `valid` is 1; there is no back-pressure. |
| `we` | input | 1: write `wdata` to `addr`. 0: read `addr`. |
| `addr` | input, 4 bits | The location. |
| `wdata` | input, 8 bits | The data to write. |
| `rdata` | output, 8 bits | The data of a read, valid in the cycle **after** the edge that accepted the read, and held until the next read. |

The last row is the one that shapes the bench: a write is complete at the edge that accepts it, but a read's data appears one edge later. The monitor has to remember the read until its data arrives, and the test must not end before that edge.

The waveform shows the boundary between the smoke test's writes and its reads. Each value is the one **sampled at that rising edge**, which is exactly what the monitor's clocking block sees (input skew `#1step`: the value just before the edge, the same value the DUT's flip-flops capture). Edge 0 is the rising edge at 175 ns and edge 5 the one at 225 ns.

### Files, packages and compile order

A UVM bench is many files, but only four compile units. Two kinds of code live in different places:

- **Design elements** (modules and interfaces) live outside any package. An interface is not a class; it is instantiated in `tb_top`, and classes reach it only through a virtual interface.
- **Classes** live in one package, here `mem_pkg`. Each class sits in its own `.svh` file, and `mem_pkg.sv` pulls them in with `` `include `` in dependency order. `` `include `` pastes the file's text where the directive stands (IEEE 1800-2023 §22.4), so the package compiles as if it were one long file.

| Order | File | Contains | Needs before it |
|---|---|---|---|
| 1 | `mem_dut.sv` | module `mem_dut` | nothing |
| 2 | `mem_if.sv` | interface `mem_if` with `drv_cb` and `mon_cb` | nothing (it must precede the package that names `virtual mem_if`) |
| — | uvm-core 2020.3.1 | `uvm_pkg` (often precompiled by your simulator) | nothing |
| 3 | `mem_pkg.sv` | package `mem_pkg`, which includes `mem_item.svh`, `mem_cfg.svh`, `mem_seqs.svh`, `mem_drv.svh`, `mem_mon.svh`, `mem_cov.svh`, `mem_agent.svh`, `mem_sb.svh`, `mem_env.svh`, `mem_tests.svh` | `uvm_pkg`, `mem_if` |
| 4 | `tb_top.sv` | module `tb_top` | `mem_pkg`, `mem_if`, `mem_dut` |

**Trace the include order** inside `mem_pkg`: `mem_item` first, because every other class names it; `mem_cfg` next, because the driver, monitor and agent hold one; the sequences; then the driver, monitor and coverage subscriber; the agent, which declares handles of those three; the scoreboard; the env, which declares an agent and a scoreboard; and the tests last, because they name the env, the configuration and the sequences. A class must be declared before it is used as a type in the same compilation unit; `typedef class` is the forward declaration for the rare case of two classes that need each other (§8.27).

**Pitfalls.**
- *An interface inside the package.* A package may declare types, nets, variables, tasks, functions, sequences, properties and checkers (§26.2), not interfaces or modules. Keep `mem_if.sv` separate.
- *Include order backwards.* If `mem_agent.svh` comes before `mem_drv.svh`, the compiler stops in `mem_agent.svh`: `mem_drv` is not yet a type. The error points at the agent, not at the include list.
- *A class file compiled on its own as well as included.* The class then exists twice, once in `mem_pkg` and once in the compilation-unit scope, and a handle of one is not a handle of the other. Compile only `mem_pkg.sv`; list the `.svh` files only through an include path.

### `tb_top`: clock, reset, interface, `run_test()`

`tb_top` is the only module the bench needs. It does five things, and the order inside its last `initial` block matters:

```systemverilog
// snippet: the heart of tb_top.sv (complete file in Make It Work)
mem_if  mem_if0 (.clk(clk), .rst_n(rst_n));         // the pins, bundled
mem_dut dut (.clk(clk), .rst_n(rst_n), .valid(mem_if0.valid), .we(mem_if0.we),
             .addr(mem_if0.addr), .wdata(mem_if0.wdata), .rdata(mem_if0.rdata));

initial begin
  clk = 1'b0;
  forever #5 clk = ~clk;            // rising edges at 5, 15, 25 ns ...
end

initial begin
  rst_n = 1'b0;
  repeat (2) @(posedge clk);
  rst_n <= 1'b1;                    // nonblocking: the flops at this edge still see 0
end

initial begin
  uvm_config_db#(virtual mem_if)::set(null, "uvm_test_top", "vif", mem_if0);
  run_test("mem_smoke_test");       // +UVM_TESTNAME on the command line wins
end
```

- **Clock and reset.** A 10 ns clock and two reset edges. Reset is released with a nonblocking assignment at a rising edge, so the DUT's flip-flops at that edge (15 ns) still read 0 and the first edge with reset inactive is 25 ns. A blocking release at the same edge would race with them ([F3C](/curriculum/T1_Foundational/F3C_Delta_Cycles_and_Race_Conditions/index)).
- **The set comes before `run_test()`.** `run_test()` builds the test and runs every phase, and by default ends the simulation with `$finish` when the run is over, so it never returns to the next line. The test reads the virtual interface in its `build_phase`, so the handle must already be in the database. A `set()` written after `run_test()` in the same block is never reached.
- **The scope `"uvm_test_top"`.** With a `null` context the second argument is the whole path (Annex C.4.2.2.1). `uvm_test_top` is the name `run_test()` gives the test, so exactly the test can `get()` it. The test then hands the handle on inside the configuration object; nothing below the test reads `"vif"`.

**Misconception: "setting the vif from the test by a hierarchical reference is the same thing."** It looks equivalent: `cfg.vif = tb_top.mem_if0;` in the test would give the same handle. It is not:
- The test lives in `mem_pkg`, and an item in a package may not refer to the design hierarchy (IEEE 1800-2023 §26.2: "Items within packages shall not have hierarchical references to identifiers except those created within the package or made visible by import of another package"). The line does not compile.
- Even in code outside a package, the test would then work only under a top module named `tb_top` with an instance named `mem_if0`. In Make It Work the same package runs under a second top, `tb_sys_top`; a hard-coded path would break it. The module that owns the instance publishes it; classes stay independent of where the pins live.

### The agent and its configuration object

An agent needs several settings: the virtual interface, whether it is active, and whether it builds coverage. Instead of three `set()`/`get()` pairs, the test fills one **configuration object** and publishes it once (the pattern from [I-UVM-2C](/curriculum/T2_Intermediate/I-UVM-2C_Configuration_and_Resources/index)):

```systemverilog
// snippet: mem_cfg (complete file in Make It Work)
class mem_cfg extends uvm_object;
  `uvm_object_utils(mem_cfg)
  virtual mem_if          vif;                     // from tb_top, via the test
  uvm_active_passive_enum is_active = UVM_ACTIVE;  // UVM_PASSIVE: monitor only
  bit                     coverage_enable = 1;     // build the coverage subscriber
  // ... constructor
endclass
```

The agent does four things in `build_phase`, in this order:
1. Gets `cfg` (`uvm_config_db#(mem_cfg)::get(this, "", "cfg", cfg)`), and stops with `` `uvm_fatal `` if it is missing or its `vif` is `null`. One check here protects the driver and the monitor.
2. Copies `cfg.is_active` into its own `is_active`, the field `get_is_active()` returns (IEEE 1800.2-2020 §13.4.2.2). `uvm_agent` itself builds nothing; it only stores the setting.
3. Always creates the monitor (and the coverage subscriber when `cfg.coverage_enable` is 1).
4. Creates the sequencer and driver only when `get_is_active()` returns `UVM_ACTIVE`.

Right after creating each child, the agent hands it the same `cfg` handle (`mon.cfg = cfg;`). That works because a child's `build_phase` runs after its parent's `build_phase` has returned. In `connect_phase` the agent connects `drv.seq_item_port` to `sqr.seq_item_export` (active only), promotes `mon.ap` to its own `ap`, and connects `mon.ap` to the coverage subscriber. The env then sees one port on the agent's boundary and never reaches inside it ([I-UVM-2B](/curriculum/T2_Intermediate/I-UVM-2B_TLM_Connections/index), one level at a time).

**Pitfall: a driver that is built anyway.** If the agent created the driver without checking `get_is_active()`, a passive agent would drive the bus too, fighting the real source of the traffic. The guard is not optional.

### Driver and monitor: one transfer each

The **driver** turns one item into one request:

```systemverilog
// snippet: mem_drv::run_phase (complete file in Make It Work)
vif.drv_cb.valid <= 1'b0;                       // idle the bus from the first edge
do @(vif.drv_cb); while (vif.drv_cb.rst_n !== 1'b1);
forever begin
  seq_item_port.get_next_item(req);
  vif.drv_cb.valid <= 1'b1;
  vif.drv_cb.we    <= req.we;
  vif.drv_cb.addr  <= req.addr;
  vif.drv_cb.wdata <= req.wdata;
  @(vif.drv_cb);                                // the DUT accepts it at this edge
  vif.drv_cb.valid <= 1'b0;                     // overridden if another item follows
  seq_item_port.item_done();
end
```

A drive through a clocking block with output skew `#0` lands in the Re-NBA region of the edge's time slot, after the DUT's flip-flops have sampled that edge (IEEE 1800-2023 §14.16), so the DUT sees it at the next edge. A drive made between edges takes effect as if made at the next clocking event. When two drives to the same clocking output mature in the same slot, the last one wins (§14.16.2). That is why the bus stays busy with back-to-back items: `valid <= 0` after one item is overridden by `valid <= 1` for the next item in the same slot.

**Trace the start, and predict first.** Reset is released with `rst_n <= 1'b1` at the 15 ns edge, and the driver waits until `drv_cb` samples `rst_n` as 1. At which rising edge does the driver leave its reset loop and drive the first request (a write of `0F` to address 0), and at which edge does the DUT accept it? Commit to two times, then read the waveform. As before, each value is the one sampled at that rising edge.

**Debrief.** The driver drives at 25 ns, and the DUT accepts at 35 ns: one edge between the drive and the accept, every time, because a zero-skew clocking drive matures after the flip-flops of its own edge have sampled. The same one-edge offset explains every time in this lesson's logs: item `k` of the smoke test is accepted at 35 + 10k ns.

The **monitor** watches every edge, creates a **new** item for every transfer, and publishes it. Writes are complete at once; a read waits one edge for its data:

```systemverilog
// snippet: the core of mem_mon::run_phase (complete file in Make It Work)
@(vif.mon_cb);
if (rd_pending != null) begin                   // the read accepted one edge ago
  rd_pending.rdata = vif.mon_cb.rdata;          // its data is here now
  ap.write(rd_pending);
  rd_pending = null;
end
if (vif.mon_cb.valid === 1'b1) begin
  mem_item t = mem_item::type_id::create("t");  // new object per transfer
  t.we   = vif.mon_cb.we;
  t.addr = vif.mon_cb.addr;
  if (t.we) begin
    t.wdata = vif.mon_cb.wdata;
    ap.write(t);
  end else begin
    rd_pending = t;
  end
end
```

- **Why `#1step` for every input here.** `mon_cb` samples every signal just before the edge: the values the DUT's flip-flops used at that edge. Everything that qualifies a transfer (`valid`, `we`, `addr`, `wdata`) must be seen this way. With an input skew of `#0`, the monitor would see a value *after* the edge's nonblocking updates (§14.4, §14.13) and mix "before" and "after" in one transaction. This bench also reads `rdata` with `#1step`, one edge after the read was accepted, which is why the monitor holds the read in `rd_pending`.
- **The one exception, and this module's lab.** A result that the DUT registers at the *same* edge as the request may be sampled with `#0` at that edge, because `#0` sees it after the update. The lab's FIFO samples its `dout` that way. Its earlier version broke because it also sampled the `full` and `empty` flags with `#0`: the flags qualify the transfer, so they need `#1step`. The rule, from the expert item on monitor sampling skew in [I-UVM-2A](/curriculum/T2_Intermediate/I-UVM-2A_Component_Roles/index): `#1step` for whatever decides whether a transfer happened; `#0` only for a same-edge registered result.
- **Why a new item each time.** Subscribers receive the handle, not a copy. Reusing one object would let the next transfer overwrite an item the scoreboard has not read yet.
- **Why `rdata` is `logic`.** The item's `rdata` field is 4-state, so an X from the DUT reaches the scoreboard and fails the compare, instead of silently turning into 0.

- **Why a FIFO between the port and the checker.** An analysis port's `write()` is a function: it cannot wait. The analysis FIFO accepts every `write()` at once (it is unbounded, IEEE 1800.2-2020 §12.2.8.3) and the scoreboard's own `run_phase` thread takes items out with `get()`, which may block. This scoreboard never needs to wait, but the shape is the one every scoreboard grows into: when a check must wait for a later item, a clock or a model, only a thread can do it.
- **Why an export on the scoreboard.** The env connects `agt.ap` to `sb.item_export`, a `uvm_analysis_export` that `mem_sb` connects to its FIFO. The env never reaches inside the scoreboard, and the scoreboard can change how it buffers without touching the env.
- **Compare with `!==`.** `t.rdata !== model[t.addr]` treats X and Z as values, so an X on `rdata` fails ([F2E](/curriculum/T1_Foundational/F2E_First_Self_Checking_Testbench/index)).

**Accounting in `check_phase`.** `check_phase` runs after `run_phase` has ended, bottom-up (IEEE 1800.2-2020 §9.8.1.7). It is the place to ask "did I check everything, and did I check anything?":
- `item_fifo.used()` (§12.2.8.2.3) must be 0. Items still in the FIFO were observed but never judged.
- `n_reads` must not be 0. A scoreboard that checked no read has proved nothing about the DUT, whatever its mismatch count says.

**Misconception: "a scoreboard that saw zero transactions passed."** `0 mismatches` is also what a scoreboard prints when its port was never connected, the run ended at 0 ns, or the stimulus never reached the DUT. That is why `mem_sb` raises `SCB_NO_TRAFFIC` as an error. `report_phase` then prints one line a regression script can grep, in this course's milestone format:

```text
SCB_SUMMARY matches=16 mismatches=0 pending=0
```

The scoreboard reports; the report server decides. A run passes when the summary shows `UVM_ERROR :    0` and `UVM_FATAL :    0` **and** the `SCB_SUMMARY` line is present with a non-zero match count. Never print "TEST PASSED" from a component: it would print even after another component's error.

### Ending the test: objections and drain time

**Misconception: "the run ends when the sequence ends."** It does not, in either direction. `run_phase` ends when no objection is raised, whatever any thread is doing ([I-UVM-1C](/curriculum/T2_Intermediate/I-UVM-1C_UVM_Phasing/index)):
- With **no objection**, `run_phase` ends in the first time slot: the sequence, driver and monitor threads are killed at 0 ns, and the log shows the report phase at 0 ns.
- With an objection that is **never dropped**, `run_phase` never ends on its own; the global timeout ends the run with a fatal.
- With the objection dropped **the moment the sequence returns**, the run ends one edge too early for this DUT: the last read's data arrives at the next edge.

The test therefore raises an objection before anything consumes time, starts the sequence, and drops the objection when the sequence returns, with a **drain time** of two clocks on the test (`phase.get_objection().set_drain_time(this, 20ns)`, §10.5.1.3.7). After the drop, the phase waits the drain time before it ends, which covers the read-data latency. The monitor's `check_phase` proves it: a read still waiting for data at the end raises `MON_INFLIGHT`.

### Two tests and a factory override

Both tests are compiled into every run; the command line picks one. `run_test()` creates the test named by `+UVM_TESTNAME` if it is present, and otherwise the one named in its argument (Annex F.7.3.1, G.2.1). Every test is created with the instance name `uvm_test_top`, which is why the configuration paths start there.

- **`mem_smoke_test`** builds the configuration and the env, and in `run_phase` creates its stimulus through the factory: `mem_wr_rd_seq::type_id::create("seq")`. The directed sequence writes every address with a different pattern, then reads every address back.
- **`mem_rand_test`** extends `mem_smoke_test` and adds one line to `build_phase`:

```systemverilog
// snippet: mem_rand_test::build_phase
mem_wr_rd_seq::type_id::set_type_override(mem_rand_seq::get_type());
super.build_phase(phase);
```

`set_type_override` (IEEE 1800.2-2020 §8.2.4.2.5) tells the factory: whenever anyone asks for a `mem_wr_rd_seq`, return a `mem_rand_seq`. The inherited `run_phase` still asks for a `mem_wr_rd_seq`, and gets 40 random reads and writes instead. `mem_rand_seq` must extend `mem_wr_rd_seq`, because the handle that receives it is a `mem_wr_rd_seq`. The proof is in the log: the test prints `seq.get_type_name()`, which reads `mem_rand_seq` in the second test.

The same override can come from the command line without a new test class: `+UVM_TESTNAME=mem_smoke_test +uvm_set_type_override=mem_wr_rd_seq,mem_rand_seq` (Annex G.2.7). A test class is still the better home for an override you will rerun: it is reviewed, versioned and named in the regression list.

**Pitfall: creating the sequence with `new()`.** `mem_wr_rd_seq seq = new("seq");` bypasses the factory, so the override silently does nothing: the second test runs the directed sequence. Every object you might want to replace is created with `::type_id::create`.

Four details make the signatures reliable:
- **A fatal skips the checking phases.** `PH_TIMEOUT` and `NOVIF` end the run through uvm-core's `die()`, which runs `pre_abort()` and prints the report summary but never runs `check_phase` or `report_phase` (`uvm_root.svh`). A log without `SCB_SUMMARY` is never a pass.
- **Failure 3 is silent by design.** `uvm_analysis_port` requires zero connections, and the end-of-elaboration check reports only ports and exports below their minimum (or above their maximum) connection count. Compare: if `mem_sb` forgot its *own* line, `item_export.connect(item_fifo.analysis_export)`, the export (which needs at least one connection) fails loudly at 0 ns: `UVM_ERROR @ 0 ns: uvm_test_top.env.sb.item_export [Connection Error] connection count of 0 does not meet required minimum of 1`, then `UVM_FATAL @ 0 ns: reporter [BUILDERR] stopping due to build errors`. Coverage at 100% next to a scoreboard with no traffic is the giveaway: the monitor ran, the scoreboard was never told.
- **Failure 4 floods the log.** One error per clock until the timeout. Add `+UVM_MAX_QUIT_COUNT=5` (Annex G.2.6) while you debug: the run stops after five errors, and the summary says `Quit count reached!`.
- **A null handle that slips past the check** (a driver that reads its own `vif` and forgets to test the `get()` result) is a simulator error, not a UVM message: using a null virtual interface "shall result in a fatal run-time error" (IEEE 1800-2023 §25.9), and the message points at the driver line, far from the missing `set()`. Check every required `get()` and stop with `` `uvm_fatal ``.

### Recap

- `tb_top` owns the pins: clock, reset with a nonblocking release, the DUT, the interface, the `set()` of the virtual interface, then `run_test()`.
- Interfaces outside the package; classes in one package, included in dependency order; compile DUT, interface, `uvm_pkg`, package, top.
- The test fills one configuration object per agent; the agent builds from it (monitor always, sequencer and driver only when active) and hands it to its children.
- The driver drives through `drv_cb`; the monitor samples through `mon_cb` with `#1step`, builds a new item per transfer, and holds a read until its data arrives.
- The scoreboard takes items from an analysis FIFO in its own thread, and its `check_phase` fails the run if anything is pending or nothing was checked; `SCB_SUMMARY` is the grep line.
- The test's objection, with a drain time for the read latency, decides when the run ends. A fatal skips `check_phase` and `report_phase`.
- The four failures have four signatures: `NOVIF` at 0 ns; everything at 0 ns or a `PH_TIMEOUT`; `SCB_NO_TRAFFIC` beside full coverage; `Get_next_item called twice` every clock.

```systemverilog
// compile: mem_dut.sv (file 1 of 4)
// 16 x 8-bit memory with a one-cycle request bus. Read data is registered:
// it appears in the cycle after the edge that accepted the read.
module mem_dut #(
  parameter int BUG = 0                // 1: reads ignore addr[3] (a planted bug)
) (
  input  logic       clk,
  input  logic       rst_n,            // synchronous, active low
  input  logic       valid,            // a request this cycle
  input  logic       we,               // 1: write, 0: read
  input  logic [3:0] addr,
  input  logic [7:0] wdata,
  output logic [7:0] rdata
);
  timeunit 1ns; timeprecision 1ps;

  logic [7:0] mem [16];
  logic [3:0] rd_addr;

  // The planted bug aliases addresses 8 to 15 onto 0 to 7, for reads only.
  assign rd_addr = (BUG == 1) ? {1'b0, addr[2:0]} : addr;

  always_ff @(posedge clk) begin
    if (!rst_n) begin
      foreach (mem[i]) mem[i] <= '0;
      rdata <= '0;
    end else if (valid && we) begin
      mem[addr] <= wdata;
    end else if (valid && !we) begin
      rdata <= mem[rd_addr];
    end
  end
endmodule
```

```systemverilog
// compile: mem_if.sv (file 2 of 4; outside the package, because it is not a class)
interface mem_if (input logic clk, input logic rst_n);
  timeunit 1ns; timeprecision 1ps;

  // Request signals are nets, so the same interface also works when RTL, not
  // the driver, drives them (the passive bench). rdata is driven by the DUT only.
  wire        valid;
  wire        we;
  wire  [3:0] addr;
  wire  [7:0] wdata;
  logic [7:0] rdata;

  // The driver's view: drives land just after the edge (Re-NBA region), so the
  // DUT samples them at the next edge.
  clocking drv_cb @(posedge clk);
    default input #1step output #0;
    output valid, we, addr, wdata;
    input  rst_n;
  endclocking

  // The monitor's view: inputs only, sampled just before the edge (#1step),
  // the same values the DUT's flip-flops capture at that edge.
  clocking mon_cb @(posedge clk);
    default input #1step;
    input valid, we, addr, wdata, rdata, rst_n;
  endclocking
endinterface
```

```systemverilog
// compile: mem_seqs.svh (included by mem_pkg.sv)
// Directed: write every address with its own pattern, then read every one back.
class mem_wr_rd_seq extends uvm_sequence #(mem_item);
  `uvm_object_utils(mem_wr_rd_seq)

  function new(string name = "mem_wr_rd_seq");
    super.new(name);
  endfunction

  virtual task body();
    for (int a = 0; a < 16; a++) send(1'b1, 4'(a), {4'(a), ~4'(a)}); // 0F ... F0
    for (int a = 0; a < 16; a++) send(1'b0, 4'(a), 8'h00);
  endtask

  // One item: create it, wait for the driver (start_item), fill it in, and
  // hand it over (finish_item returns after the driver's item_done).
  protected task send(bit we, bit [3:0] addr, bit [7:0] wdata);
    mem_item it = mem_item::type_id::create("it");
    start_item(it);
    it.we    = we;
    it.addr  = addr;
    it.wdata = wdata;
    finish_item(it);
  endtask
endclass

// Random: num_items random reads and writes. mem_rand_test makes the factory
// return this class wherever a mem_wr_rd_seq is requested.
class mem_rand_seq extends mem_wr_rd_seq;
  `uvm_object_utils(mem_rand_seq)

  int unsigned num_items = 40;

  function new(string name = "mem_rand_seq");
    super.new(name);
  endfunction

  virtual task body();

      mem_item it = mem_item::type_id::create("it");
      start_item(it);
      if (!it.randomize()) `uvm_fatal("RAND", "mem_item randomization failed")
```

```systemverilog
// compile: mem_drv.svh (included by mem_pkg.sv)
class mem_drv extends uvm_driver #(mem_item);
  `uvm_component_utils(mem_drv)

  mem_cfg cfg;                          // handed over by mem_agent

  function new(string name, uvm_component parent);
    super.new(name, parent);
  endfunction

  virtual task run_phase(uvm_phase phase);
    virtual mem_if vif = cfg.vif;
    vif.drv_cb.valid <= 1'b0;           // idle the bus from the first edge
    do @(vif.drv_cb); while (vif.drv_cb.rst_n !== 1'b1);
    forever begin
      seq_item_port.get_next_item(req);
      vif.drv_cb.valid <= 1'b1;
      vif.drv_cb.we    <= req.we;
      vif.drv_cb.addr  <= req.addr;
      vif.drv_cb.wdata <= req.wdata;
      @(vif.drv_cb);                    // the DUT accepts the request at this edge
      vif.drv_cb.valid <= 1'b0;         // a following item overrides this drive
      seq_item_port.item_done();        // releases finish_item() in the sequence
    end
  endtask
endclass
```

```systemverilog
// compile: mem_mon.svh (included by mem_pkg.sv)
class mem_mon extends uvm_monitor;
  `uvm_component_utils(mem_mon)

  mem_cfg cfg;                            // handed over by mem_agent
  uvm_analysis_port #(mem_item) ap;       // one new item per observed transfer
  protected mem_item rd_pending;          // a read accepted, its data not yet seen

  function new(string name, uvm_component parent);
    super.new(name, parent);
  endfunction

  virtual function void build_phase(uvm_phase phase);
    super.build_phase(phase);
    ap = new("ap", this);
  endfunction

  virtual task run_phase(uvm_phase phase);
    virtual mem_if vif = cfg.vif;
    forever begin
      @(vif.mon_cb);
      if (vif.mon_cb.rst_n !== 1'b1) begin
        rd_pending = null;                // reset cancels a read in flight
        continue;
      end
      // The read accepted at the previous edge has its data now.
      if (rd_pending != null) begin
        rd_pending.rdata = vif.mon_cb.rdata;
        ap.write(rd_pending);
        rd_pending = null;
      end
      if (vif.mon_cb.valid === 1'b1) begin
        mem_item t = mem_item::type_id::create("t");
        if ($isunknown({vif.mon_cb.we, vif.mon_cb.addr}))
          `uvm_error("MON_X", "valid is 1 but we or addr is X or Z")
        t.we   = vif.mon_cb.we;
        t.addr = vif.mon_cb.addr;
        if (t.we) begin
          t.wdata = vif.mon_cb.wdata;
          ap.write(t);                    // a write is complete at once
        end else begin
          rd_pending = t;                 // its data arrives one edge later
        end
      end
    end
  endtask

  // A read still waiting for its data means the run ended one edge too early.
  virtual function void check_phase(uvm_phase phase);
    super.check_phase(phase);
    if (rd_pending != null)
      `uvm_error("MON_INFLIGHT", $sformatf("read of addr %h never got its data",
                                           rd_pending.addr))
  endfunction
endclass
```

```systemverilog
// compile: mem_agent.svh (included by mem_pkg.sv)
class mem_agent extends uvm_agent;
  `uvm_component_utils(mem_agent)

  mem_cfg cfg;
  mem_sqr sqr;
  mem_drv drv;
  mem_mon mon;
  mem_cov cov;
  uvm_analysis_port #(mem_item) ap;       // the monitor's stream, at the boundary

  function new(string name, uvm_component parent);
    super.new(name, parent);
  endfunction

  virtual function void build_phase(uvm_phase phase);
    super.build_phase(phase);
    if (!uvm_config_db#(mem_cfg)::get(this, "", "cfg", cfg))
      `uvm_fatal("NOCFG", {"no mem_cfg set for ", get_full_name()})
    if (cfg.vif == null)
      `uvm_fatal("NOVIF", {"mem_cfg.vif is null for ", get_full_name()})
    is_active = cfg.is_active;            // get_is_active() returns this from now on
    ap  = new("ap", this);
    mon = mem_mon::type_id::create("mon", this);
    mon.cfg = cfg;
    if (cfg.coverage_enable)
      cov = mem_cov::type_id::create("cov", this);
    if (get_is_active() == UVM_ACTIVE) begin
      sqr = mem_sqr::type_id::create("sqr", this);
      drv = mem_drv::type_id::create("drv", this);
      drv.cfg = cfg;
    end
  endfunction

  virtual function void connect_phase(uvm_phase phase);
    super.connect_phase(phase);
    mon.ap.connect(ap);                   // promote: the env sees agt.ap only
    if (cov != null)
      mon.ap.connect(cov.analysis_export);
    if (get_is_active() == UVM_ACTIVE)
      drv.seq_item_port.connect(sqr.seq_item_export);
  endfunction
endclass
```

```systemverilog
// compile: mem_sb.svh (included by mem_pkg.sv)
class mem_sb extends uvm_scoreboard;
  `uvm_component_utils(mem_sb)

  uvm_analysis_export   #(mem_item) item_export;  // the env connects agt.ap here
  uvm_tlm_analysis_fifo #(mem_item) item_fifo;    // buffers items for run_phase

  protected bit [7:0] model [16];   // reference model: what each address holds
  int unsigned n_writes, n_reads, n_match, n_mismatch;

  function new(string name, uvm_component parent);
    super.new(name, parent);
  endfunction

  virtual function void build_phase(uvm_phase phase);
    super.build_phase(phase);
    item_export = new("item_export", this);
    item_fifo   = new("item_fifo", this);
  endfunction

  virtual function void connect_phase(uvm_phase phase);
    super.connect_phase(phase);
    item_export.connect(item_fifo.analysis_export);
  endfunction

  virtual task run_phase(uvm_phase phase);
    mem_item t;
    forever begin
      item_fifo.get(t);                   // waits until the monitor publishes
      check_item(t);
    end
  endtask

  protected function void check_item(mem_item t);
    if (t.we) begin
      model[t.addr] = t.wdata;            // predict: later reads return wdata
      n_writes++;
      return;
    end
    n_reads++;
    if (t.rdata !== model[t.addr]) begin
      n_mismatch++;
      `uvm_error("SCB_MISMATCH", $sformatf("%s, expected rdata=%h",
                                           t.convert2string(), model[t.addr]))
    end else begin
      n_match++;
      `uvm_info("SCB_MATCH", t.convert2string(), UVM_HIGH)
    end
  endfunction

  // After run_phase: did we judge everything we saw, and did we judge anything?
  virtual function void check_phase(uvm_phase phase);
    super.check_phase(phase);
    if (item_fifo.used() != 0)
      `uvm_error("SCB_PENDING", $sformatf("%0d items were never checked",
                                          item_fifo.used()))
    if (n_reads == 0)
      `uvm_error("SCB_NO_TRAFFIC", $sformatf(
        "no read was checked (%0d writes seen): this run proves nothing", n_writes))
  endfunction

  virtual function void report_phase(uvm_phase phase);
    super.report_phase(phase);
    `uvm_info("SCB_SUMMARY",
              $sformatf("SCB_SUMMARY matches=%0d mismatches=%0d pending=%0d",
                        n_match, n_mismatch, item_fifo.used()), UVM_NONE)
  endfunction
endclass
```

```systemverilog
// compile: tb_top.sv (file 4 of 4)
module tb_top;
  timeunit 1ns; timeprecision 1ps;
  import uvm_pkg::*;
  `include "uvm_macros.svh"
  import mem_pkg::*;        // some tools elaborate only packages that are referenced

  logic clk;
  logic rst_n;

  mem_if  mem_if0 (.clk(clk), .rst_n(rst_n));
  mem_dut #(.BUG(0)) dut (.clk(clk), .rst_n(rst_n), .valid(mem_if0.valid),
                          .we(mem_if0.we), .addr(mem_if0.addr),
                          .wdata(mem_if0.wdata), .rdata(mem_if0.rdata));

  initial begin
    clk = 1'b0;
    forever #5 clk = ~clk;              // rising edges at 5, 15, 25 ns ...
  end

  initial begin
    rst_n = 1'b0;
    repeat (2) @(posedge clk);
    rst_n <= 1'b1;                      // nonblocking: the flops at 15 ns still see 0
  end

  initial begin
    $timeformat(-9, 0, " ns", 0);       // %t in the log reads "35 ns"
    // Publish the interface first: the test reads it in build_phase.
    uvm_config_db#(virtual mem_if)::set(null, "uvm_test_top", "vif", mem_if0);
    run_test("mem_smoke_test");         // +UVM_TESTNAME=<test> overrides this
  end
endmodule
```

### Run it

The steps are tool-neutral; switches differ between simulators, so check your tool's UVM documentation.

1. **Point the compiler at uvm-core 2020.3.1.** Many simulators ship a precompiled UVM library selected with one switch (tool-dependent). Otherwise compile the library's `src/uvm_pkg.sv` with `src` on the include path, together with its DPI file `src/dpi/uvm_dpi.cc`, or define `UVM_NO_DPI` to compile without the C side (uvm-core then reads `+UVM_TESTNAME` with `$value$plusargs` and loses some features).
2. **Use one time unit everywhere.** Every file of this bench declares `timeunit 1ns; timeprecision 1ps;`, but `uvm_pkg` declares none, and IEEE 1800-2023 §3.14.2.3 makes it an error for some design elements to specify a time unit while others do not. Give the compile a default time unit and precision of 1 ns / 1 ps with your tool's switch, so that uvm-core gets the same unit. It matters beyond legality: `set_drain_time(this, 20ns)` and `set_timeout(1ms)` pass `time` values that uvm-core waits on in its own time unit (see the expert item on time units in [I-UVM-1C](/curriculum/T2_Intermediate/I-UVM-1C_UVM_Phasing/index)).
3. **Compile in order** with the bench's directory on the include path: `mem_dut.sv`, `mem_if.sv`, `mem_pkg.sv`, `tb_top.sv`. Elaborate with `tb_top` as the top module.
4. **Run each test** by name:

```bash
# Generic shape; <sim> stands for your simulator's run command.
<sim> ... +UVM_TESTNAME=mem_smoke_test
<sim> ... +UVM_TESTNAME=mem_rand_test       # add your tool's seed switch to vary it
```

Open-source simulators' UVM support is limited and changes between releases; whether this bench runs on one is tool-dependent, and this page does not claim it.

### The same agent, passive, in a second bench

```systemverilog
// compile: mem_traffic_gen.sv (an RTL stand-in for the block that will drive mem_dut)
// After reset: 16 back-to-back writes (address a gets {a, ~a}), then 16 reads.
module mem_traffic_gen (
  input  logic       clk,
  input  logic       rst_n,
  output logic       valid,
  output logic       we,
  output logic [3:0] addr,
  output logic [7:0] wdata
);
  timeunit 1ns; timeprecision 1ps;

  logic [5:0] step;                     // 0-15 write, 16-31 read, 32 done

  always_ff @(posedge clk) begin
    if (!rst_n)             step <= '0;
    else if (step != 6'd32) step <= step + 6'd1;
  end

  assign valid = rst_n && (step != 6'd32);
  assign we    = !step[4];
  assign addr  = step[3:0];
  assign wdata = {step[3:0], ~step[3:0]};
endmodule
```

### How to build your own first bench

1. **Write the DUT's protocol down** as a table: which edge accepts a request, when results are valid, what reset does. Every later decision (clocking skews, the monitor's state, the drain time) comes from it.
2. **Write the interface** with a driver clocking block and a monitor clocking block. Use nets for signals that another source may drive in a passive bench.
3. **Write the item**, then the **configuration object** (`vif`, `is_active`, knobs), then one directed **sequence**.
4. **Write the driver** (drive through `drv_cb`, one `item_done()` per item) and the **monitor** (sample through `mon_cb`, a new item per transfer, state for anything that completes later).
5. **Write the agent:** get the configuration, set `is_active`, build the monitor always and the sequencer and driver only when active, hand `cfg` to the children, connect, promote the analysis port.
6. **Write the scoreboard:** an export, an analysis FIFO, a `run_phase` thread, a model, counters, `check_phase` for pending items and zero traffic, and one `SCB_SUMMARY` line.
7. **Write the env** (build and connect), **the test** (configuration, timeout, topology, objection with drain, sequence created through the factory), and **`tb_top`** (clock, reset, DUT, interface, `set()` then `run_test()`).
8. **Organize and compile:** the package with includes in dependency order; compile DUT, interface, `uvm_pkg`, package, top.
9. **Run, then break it:** check the verdict lines, plant a DUT bug and see the scoreboard catch it, then remove the bug.
10. **Add a second test** that changes only what it must (an override or a configuration field) and prove from the log that it did.

**Checklist before moving on:**
- [ ] `tb_top` publishes `virtual mem_if` before `run_test()`, and no class names `tb_top` in a hierarchical path.
- [ ] Interfaces are outside the package; the package includes its files in dependency order; the four units compile in order.
- [ ] The agent builds its sequencer and driver only when `get_is_active()` returns `UVM_ACTIVE`, and every required `get()` is checked.
- [ ] The monitor samples through its clocking block with `#1step` and creates a new item for every transfer.
- [ ] The scoreboard's `check_phase` fails a run with pending items or no checked transaction, and `report_phase` prints `SCB_SUMMARY`.
- [ ] The test raises its objection before anything consumes time, drops it after the sequence, and covers the DUT's latency with a drain time.
- [ ] Both tests run from the command line, and the log proves which sequence ran.
- [ ] You have seen the bench fail on a planted bug and pass without it.
- [ ] You can name the failure behind each of the four bring-up signatures.
- [ ] The second bench runs the same agent passive, with no driver in the topology and a matching scoreboard count.

## Push Further

### Expert: compilation units, packages and include order

- **What `` `include `` really does.** It pastes text (IEEE 1800-2023 §22.4). The package is then one long scope, so declaration order inside it is the include order. A class used as a type before its declaration is an error unless forward-declared with `typedef class` (§8.27).
- **Why one package and not `$unit`.** Declarations outside any module or package go into the compilation-unit scope, `$unit` (§3.12.1). Whether two files share one `$unit` depends on whether the tool compiles them together, which is a tool switch. Two copies of the same class in two compilation units are two different types, and a handle of one cannot hold an object of the other. A package is one named scope, compiled once, imported everywhere: the type identity problem disappears.
- **What a package may not contain.** Packages hold types, data, tasks, functions and similar declarations, may not contain hierarchical references to the design, and may not refer to items in `$unit` (§26.2). Interfaces and modules are design elements and stay outside.
- **Import is not elaboration.** `import mem_pkg::*;` makes names visible; it does not create anything. Whether a compiled but unreferenced package is elaborated (and so registers its classes with the factory) is tool-dependent, which is why `tb_top` imports `mem_pkg` even though it names none of its classes.
- **Interview angle:** "Two engineers each include `my_item.svh` in their own package. What breaks, and how do you fix it?" (Two distinct `my_item` types; a `uvm_config_db#(my_item)` set by one package's code is invisible to a `get()` compiled in the other. Put shared types in one package that both import.)

### Expert: what `run_test()` does with the command line

- **Test selection.** If `+UVM_TESTNAME` is present, `run_test()` creates that test through the factory by name; otherwise it uses its argument (IEEE 1800.2-2020 Annex F.7.3.1, G.2.1). If several `+UVM_TESTNAME` arguments are given, the first is used and a warning is issued (G.2.1).
- **The names in the errors** (uvm-core 2020.3.1, `uvm_root.svh`): a name the factory does not know gives `UVM_FATAL [INVTST] Requested test from command line +UVM_TESTNAME=<name> not found.` A run with no test at all gives `[NOCOMP]`. Calling `run_test()` twice gives `[TTINST]`. Registering the test with `` `uvm_component_utils `` is what makes the name known.
- **When the command line is applied.** uvm-core applies `+uvm_set_type_override` and the other `+uvm_set_*` arguments in `uvm_root`'s own `build_phase`, which runs before the test's (`uvm_root.svh`), so a command-line override is in place before any component or sequence is created. It then logs `UVM_CMDLINE_PROC` with the override applied.
- **Interview angle:** "Why do regressions select tests with `+UVM_TESTNAME` instead of recompiling with a different `run_test()` argument?" (One compiled image runs every test; the command line, not the source, records which test ran.)

### Expert: when the run really ends, and what a fatal skips

- **Normal end.** After the last objection drops and every drain time has passed, `run_phase` ends, its threads are killed (IEEE 1800.2-2020 §9.6, §10.5.1), and `extract_phase`, `check_phase`, `report_phase` and `final_phase` run (§9.8.1). `run_test()` then prints the report summary and, by default, calls `$finish`.
- **Fatal end.** A `UVM_FATAL` (including `PH_TIMEOUT`, `NOVIF` and a reached quit count) calls `uvm_root::die()` in uvm-core 2020.3.1, which runs `pre_abort()` on every component and prints the summary, then calls `$finish` (`uvm_root.svh`). `check_phase` and `report_phase` never run. Override `pre_abort()` in the scoreboard to print the pending count when a run is killed.
- **The default timeout** is 9200 s (`` `UVM_DEFAULT_TIMEOUT ``, `uvm_global_defines.svh`), and its fatal says "Default timeout"; after `set_timeout()` it says "Explicit timeout" (`uvm_phase_hopper.svh`). `set_timeout()` must be called before `run_phase` starts (Annex F.7.3.3).
- **Drain time versus `phase_ready_to_end`.** A drain time is right when the leftover work has a known bound (one read latency here). When it does not, the component that knows (usually the scoreboard) raises an objection from `phase_ready_to_end` and drops it when its expected items have arrived ([I-UVM-1C](/curriculum/T2_Intermediate/I-UVM-1C_UVM_Phasing/index), [A-UVM-6](/curriculum/T3_Advanced/A-UVM-6_Scoreboards_and_Reference_Models/index)).
- **Interview angle:** "A regression job's log ends with `PH_TIMEOUT` and the report summary shows `UVM_ERROR : 0`. Is it a pass?" (No: a fatal is a failure, and the checking phases never ran.)

### Expert: why the virtual interface travels through the configuration database

- **Packages cannot see the design.** Classes in a package cannot use hierarchical references (IEEE 1800-2023 §26.2), so the only way in is a value passed at run time. The configuration database is UVM's standard carrier (IEEE 1800.2-2020 Annex C.4.2).
- **The type is part of the key.** A `set()` of `virtual mem_if` is invisible to a `get()` of `virtual mem_if.some_modport`: a modport is part of a virtual interface's type (IEEE 1800-2023 §25.9), and the database matches types exactly ([I-UVM-2C](/curriculum/T2_Intermediate/I-UVM-2C_Configuration_and_Resources/index)).
- **One handle per instance, scoped narrowly.** Setting the handle for `"uvm_test_top"` and passing it on in `cfg` means a second interface instance (a second agent) can never pick up the wrong one through a wildcard. A `set(null, "*", "vif", ...)` matches every component and is how two agents end up watching the same bus.
- **A null virtual interface** is a fatal run-time error when used (§25.9). The error appears at the first use, often in `run_phase`, far from the missing `set()`; a checked `get()` moves the report to time 0 and names the cause.
- **Interview angle:** "Why not make the virtual interface a static member of a global class and assign it from `tb_top`?" (It works for one instance, but it hard-wires one interface to every user, defeats per-instance configuration and passive reuse, and hides the dependency from the tree.)

### Expert: the analysis FIFO at scale

- **It is unbounded** (IEEE 1800.2-2020 §12.2.8.3). If the scoreboard thread falls behind, or never runs, the FIFO keeps growing; nothing blocks the monitor and nothing warns. `used()` (§12.2.8.2.3) in `check_phase` catches leftovers at the end, but not memory growth during a long run.
- **It stores handles, not copies.** The monitor must create a new item per transfer. A monitor that reuses one object fills the FIFO with N handles to the same item, and every check sees the last transfer's values.
- **Imps versus FIFOs.** A scoreboard whose checks are all zero-time can implement `write()` directly through `` `uvm_analysis_imp_decl `` and skip the FIFO; one that must wait needs the FIFO and a thread. The FIFO also gives you `used()` and `is_empty()` for free accounting ([A-UVM-6](/curriculum/T3_Advanced/A-UVM-6_Scoreboards_and_Reference_Models/index) compares the forms).
- **Cost at scale** (tool-dependent): every published item is an object allocation, and every subscriber connected to a port adds a call per transfer. On a high-rate interface, measure before adding subscribers; keep the coverage subscriber switchable (`coverage_enable`) as this agent does.

### Expert: the same agent on both sides of a hierarchy

- **Passive is a build-time decision.** `uvm_agent` reads `is_active` in its `build_phase` (IEEE 1800.2-2020 §13.4.2.2; uvm-core also accepts integer and string settings for it). Changing `cfg.is_active` after the build changes nothing.
- **Nets make the interface reusable.** A clocking-block output on a net adds a driver that stays `'z` until the first synchronous drive (IEEE 1800-2023 §14.16); on a variable, an output clocking signal and a continuous driver from RTL cannot coexist (see the expert item on one interface type on both sides of the DUT in [I-UVM-2A](/curriculum/T2_Intermediate/I-UVM-2A_Component_Roles/index)).
- **End of test without a sequence.** A passive bench has no stimulus of its own to wait for. This page's second test waits on the bus going idle, which works because the stand-in sends one burst; a real subsystem test ends on its own active stimulus, and the passive agents simply keep watching ([A-UVM-8](/curriculum/T3_Advanced/A-UVM-8_Multi_Agent_Topologies/index)).
- **Interview angle:** "Your passive agent at chip level reports zero transactions. List three causes in order of likelihood." (The `vif` points at the wrong instance; the monitor waits for a reset or clock that is now different at chip level; the agent's analysis port is not connected in the new env.)

### Kata 1 (guided): a third test through the factory

**Objective:** add a test that changes only the stimulus, run it, and predict its summary before you look.

**The task:** write `mem_pairs_seq`, which extends `mem_wr_rd_seq` and, for every address `a` from 0 to 15, writes `{a, ~a}` and immediately reads `a` back. Write `mem_pairs_test`, which extends `mem_smoke_test` and overrides `mem_wr_rd_seq` with `mem_pairs_seq`. Add both to the package (where?), run with `+UVM_TESTNAME=mem_pairs_test`, and predict: the `TEST` line, the `SCB_SUMMARY` line, and the time of the last report.

<details>
<summary>Hint</summary>

The sequence can reuse the protected `send()` task it inherits. The 32 items are still back to back, so the timing is the same as the smoke test's except for which item is a read.

</details>

<details>
<summary>Worked solution</summary>

```systemverilog
// compile: add to mem_seqs.svh, after mem_rand_seq
class mem_pairs_seq extends mem_wr_rd_seq;
  `uvm_object_utils(mem_pairs_seq)

  function new(string name = "mem_pairs_seq");
    super.new(name);
  endfunction

  virtual task body();
    for (int a = 0; a < 16; a++) begin
      send(1'b1, 4'(a), {4'(a), ~4'(a)});
      send(1'b0, 4'(a), 8'h00);          // read back at once
    end
  endtask
endclass
```

```systemverilog
// compile: add to mem_tests.svh, after mem_rand_test
class mem_pairs_test extends mem_smoke_test;
  `uvm_component_utils(mem_pairs_test)

  function new(string name, uvm_component parent);
    super.new(name, parent);
  endfunction

  virtual function void build_phase(uvm_phase phase);
    mem_wr_rd_seq::type_id::set_type_override(mem_pairs_seq::get_type());
    super.build_phase(phase);
  endfunction
endclass
```

Expected lines:

```text
UVM_INFO @ 0 ns: uvm_test_top [TEST] starting mem_pairs_seq
UVM_INFO @ 365 ns: uvm_test_top.env.sb [SCB_SUMMARY] SCB_SUMMARY matches=16 mismatches=0 pending=0
```

Item `k` is still accepted at 35 + 10k ns, so the last read (item 31, address F) is accepted at 345 ns, its data is published at 355 ns, and the drain ends the run at 365 ns. Each read follows its write by one edge: the write to address `a` is accepted at one edge and the read at the next, and the DUT's write has updated the location by then, so every read matches. The new classes go after the classes they extend, because the package compiles in include order.

**Reflect:** what does `mem_pairs_test` report with `.BUG(1)`? Trace it before you read on. In the pairs order, addresses 0 to 7 are written (and read back correctly) before any of 8 to F is read. Each read of an address from 8 to F then returns the location eight below it, which holds `0f` to `78`, while the model expects `87` to `f0`: `matches=8 mismatches=8`, the same verdict as the smoke test, reached through a different order.

</details>

### Kata 2 (debug): four logs, four bugs

Each excerpt below comes from this bench with one line changed. Name the failure, the missing or wrong line, and the fix, before you open the answer.

1. `UVM_FATAL @ 0 ns: uvm_test_top [NOVIF] virtual mem_if 'vif' not found: set it in tb_top before run_test()`, then the report summary.
2. `UVM_INFO @ 0 ns: uvm_test_top [TEST] starting mem_wr_rd_seq`, then at 0 ns: `[SCB_NO_TRAFFIC]`, `COV_SUMMARY ... 0.0%`, `SCB_SUMMARY matches=0 mismatches=0 pending=0`.
3. A run that ends at 365 ns with `COV_SUMMARY ... 100.0%`, then `[SCB_NO_TRAFFIC] no read was checked (0 writes seen)`.
4. `UVM_ERROR @ 35 ns: uvm_test_top.env.agt.sqr [uvm_test_top.env.agt.sqr] Get_next_item called twice without item_done or get in between`, repeated every 10 ns, then `UVM_FATAL @ 1000000 ns: reporter [PH_TIMEOUT] Explicit timeout of 1000000 ns hit, indicating a probable testbench issue`.

<details>
<summary>Answers</summary>

1. **Null virtual interface.** The `set()` in `tb_top` is missing, placed after `run_test()`, or uses another type or scope. Fix: `uvm_config_db#(virtual mem_if)::set(null, "uvm_test_top", "vif", mem_if0);` before `run_test()`.
2. **Objection never raised.** Everything happens at 0 ns: `run_phase` ended in its first time slot and killed the sequence. Fix: `phase.raise_objection(this, ...)` before `seq.start()`, and `drop_objection` after it.
3. **Unconnected analysis port.** The run ended normally and the monitor ran (coverage is full), but the scoreboard received nothing: `agt.ap.connect(sb.item_export);` is missing in `mem_env::connect_phase`. Nothing reports it except the zero-traffic check.
4. **Missing `item_done()`.** The driver loops back to `get_next_item()` without `seq_item_port.item_done()`. The sequence is stuck in `finish_item()`, the objection is never dropped, and the timeout fires. Fix: one `item_done()` after the item is on the pins.

</details>
