## Quick Take

- **What it is:** UVM's **reporting** system turns every message a testbench (TB) prints into a **report**: a message with a **severity** (`UVM_INFO`, `UVM_WARNING`, `UVM_ERROR` or `UVM_FATAL`), an **ID** (a short tag such as `"MISMATCH"`), and, for information messages, a **verbosity** (how much detail it is). One central **report server** counts every report it handles, by severity and by ID, and prints those counts in the **report summary** at the end of the run (IEEE 1800.2-2020 Clause 6). **Run control** is how you start, steer and stop a run: choosing the test with `+UVM_TESTNAME`, setting verbosity and actions with **plusargs** (command-line options that start with `+`), and bounding the run with a timeout or a maximum error count (Annex F.7, Annex G).
- **Why it matters:** Every UVM milestone on this site, and every industrial regression, decides pass or fail from the report summary: `UVM_ERROR :    0` and `UVM_FATAL :    0`. If you do not know what those counts include, you will ship false passes: a run that checked nothing, an assertion that failed with `$error` that UVM never saw, or errors switched off from the command line.
- **The Analogy:** A building's fire-alarm system. Each room's detector (a component) reports to one central panel (the report server), which logs and counts every alarm; each room has its own sensitivity dial (verbosity), and the inspector signs the building off by reading the panel's log (the summary). *Where it breaks:* the sensitivity dial in UVM only hides routine information messages, never warnings or errors; a separate bell wired straight to the street (`$error`) rings without ever reaching the panel; and a panel showing zero alarms in a building with no detectors installed proves nothing.

**You will be able to:**
1. **Write** `` `uvm_info ``, `` `uvm_warning ``, `` `uvm_error `` and `` `uvm_fatal `` with meaningful IDs, and **predict** which information messages print at a given verbosity.
2. **Decide** pass or fail from a report summary's severity counts, and **recognize** a zero-activity run that only looks like a pass.
3. **Configure** a run: select the test with `+UVM_TESTNAME`, and set verbosity, actions and severities from the command line (`+UVM_VERBOSITY`, `+uvm_set_verbosity`, `+uvm_set_action`, `+uvm_set_severity`) and in code (`set_report_*`).
4. **Bound** a run with `set_timeout`, `+UVM_TIMEOUT` (uvm-core only) and `+UVM_MAX_QUIT_COUNT`, and **predict** what the log shows when each one ends it.
5. **Explain** why `$display`, `$error` and an assertion's default `$error` do not change UVM's counts, and **route** them into UVM reporting.

## Build Your Mental Model

**How to read this lesson.** The core path is the first four sections: the message macros, verbosity, where a report goes, and reading the summary. Practitioner depth follows: actions and counts, command-line control, ending a run, and messages UVM never sees. Make It Work gives you one test you can run three ways and judge each log. Push Further holds the expert corner cases.

A few words you already know, in one line each:

- A **component** is an object of a class derived from `uvm_component`; components form a tree that lives for the whole run ([I-UVM-1A](/curriculum/T2_Intermediate/I-UVM-1A_Components/index)). Every component is also a `uvm_report_object`, which is why it can print UVM messages under its own name.
- The **test** is the component at the top of your tree. UVM creates it by name through the **factory** ([I-UVM-1B](/curriculum/T2_Intermediate/I-UVM-1B_The_UVM_Factory/index)) and names the instance `uvm_test_top`. Above it sits **`uvm_root`**, UVM's own top-level component; `uvm_root::get()` returns it (older code uses the compatibility variable `uvm_top`).
- A **phase** is one named step of the run (`build_phase`, `run_phase`, `check_phase`, `report_phase` and so on). An **objection** keeps `run_phase` open until the test is finished ([I-UVM-1C](/curriculum/T2_Intermediate/I-UVM-1C_UVM_Phasing/index)).
- **`$display`** and the **severity tasks** `$info`, `$warning`, `$error` and `$fatal` are plain SystemVerilog printing ([F2D](/curriculum/T1_Foundational/F2D_Reusable_Code_and_Parallelism/index)).
- A **regression** is a script that runs many tests and seeds and marks each one pass or fail, usually by reading its log.

### The four message macros

You report from UVM code with four macros (IEEE 1800.2-2020 Annex B.1.1):

```systemverilog
// snippet: inside any component method
// Detail for debugging:
`uvm_info("CHK", $sformatf("check %0d passed", n), UVM_HIGH)
// Suspicious, but the run can still be valid:
`uvm_warning("CFG", "timeout_cycles not set, using 100")
// A check failed:
`uvm_error("MISMATCH", $sformatf("expected %0d, got %0d", e, a))
// The run cannot continue:
`uvm_fatal("NO_VIF", "virtual interface not found")
```

- The **first argument is the ID**. It is a free string that you choose (§6.2.4.2). It appears in brackets in the log, the summary counts messages per ID, and every control knob in this lesson can target one ID. Use one short, stable, upper-case ID per kind of event (`MISMATCH`, `NO_CHECKS`), not a new ID per message.
- The **second argument is the message text**: one string, so build it with `$sformatf`.
- Only `` `uvm_info `` takes a **third argument, the verbosity**: `UVM_NONE` (0), `UVM_LOW` (100), `UVM_MEDIUM` (200), `UVM_HIGH` (300), `UVM_FULL` (400) (Annex F.2.2.4). uvm-core 2020.3.1 adds `UVM_DEBUG` (500). A higher number means "more detailed, print less often".
- The macros add the source file and line for you (`` `__FILE__ ``, `` `__LINE__ ``) and skip all the string formatting when the message would be filtered anyway (B.1).

What each severity means, and what UVM does with it by default (§6.3, Annex F.2.2.1):

| Severity | Meaning | Default action |
|---|---|---|
| `UVM_INFO` | Information: progress, detail | print it |
| `UVM_WARNING` | A potential problem; the run continues | print it |
| `UVM_ERROR` | A real problem: a check failed; the run continues | print it and add 1 to the quit counter |
| `UVM_FATAL` | Cannot continue | print it and end the simulation |

An **action** is what UVM does with a report; the next sections explain each one. Notice what the table says about pass and fail: a `UVM_ERROR` does not stop the run. The run continues so you see every failure, and the verdict comes at the end from the counts.

**Read one log line.** Every UVM message has the same layout (uvm-core 2020.3.1 `uvm_report_server.svh`, `compose_report_message`):

```text
UVM_ERROR report_tb.sv(28) @ 30: uvm_test_top.chk [MISMATCH] check 3: expected 33, got 34
|         |                |     |                |          |
severity  file(line)       time  report object    ID         message text
```

This is run B's error from Make It Work; line 28 is where the macro call starts. The report object is the full hierarchical name of the component that issued the message. Messages that UVM itself issues from outside any component show the name `reporter`, which is `uvm_root`'s report handler.

**Why not `$display`?** A `$display` line has no severity, no ID and no verbosity: you cannot filter it, count it, send it to a file or turn it into a failure, and the report summary never sees it. Inside UVM code, always use the macros (spine §5.2 rule 10).

### Verbosity: which information messages print

Each report object has a **maximum verbosity**, `UVM_MEDIUM` by default. An `` `uvm_info `` prints only if its verbosity is **less than or equal to** that maximum (§6.3.3.2 `uvm_report_enabled`, §6.3.4.3). Here is a traced example with the four messages above, at three settings:

| Message | `UVM_LOW` setting | `UVM_MEDIUM` (default) | `UVM_HIGH` setting |
|---|---|---|---|
| `` `uvm_info("CHK", …, UVM_HIGH) `` | hidden (300 > 100) | hidden (300 > 200) | **printed** |
| `` `uvm_warning("CFG", …) `` | **printed** | **printed** | **printed** |
| `` `uvm_error("MISMATCH", …) `` | **printed** | **printed** | **printed** |
| `` `uvm_fatal("NO_VIF", …) `` | **printed** | **printed** | **printed** |

**Verbosity never hides a warning, an error or a fatal.** The macros issue them at `UVM_NONE` (0), the lowest standard level, which every standard setting allows (B.1.1.2–B.1.1.4; §6.3.3.3: "Verbosity is ignored for warnings, errors, and fatals"). So `+UVM_VERBOSITY=UVM_LOW` makes a log quieter, but it can never make a failing test pass. Turning errors off needs a different knob, the action, and that is exactly why actions deserve suspicion when you read someone else's run script.

The precise rule (§6.4.3.1): a verbosity set for a (severity, ID) pair wins over one set for an ID, which wins over the report object's maximum verbosity. So you can raise one ID in one component to `UVM_HIGH` while the rest of the TB stays quiet. That is the everyday debugging move, and Kata 2 practises it.

A **filtered message is not counted**: it never reaches the report server. A message hidden by verbosity appears neither in the log nor in the summary.

### Where a report goes: object, handler, server

Four classes make up the machinery (§6.1–§6.5):

- **`uvm_report_message`** (§6.2): one report as an object, carrying its severity, ID, text, verbosity, file, line and the action chosen for it.
- **`uvm_report_object`** (§6.3): the class every component extends. It owns the `` `uvm_* `` calls and the `set_report_*` configuration methods.
- **`uvm_report_handler`** (§6.4): each report object has its own handler, which stores that object's settings: maximum verbosity, actions, files and severity overrides.
- **`uvm_report_server`** (§6.5): one server for the whole run. It counts, prints, writes files, and prints the summary at the end.

**Debrief.** The answer to the prediction is "nowhere": the error passes the verbosity check because the macro issues it at `UVM_NONE`. Only two things after that step can remove an error from the counts: an action of `UVM_NO_ACTION`, and a **report catcher**, a callback object that can inspect, change or swallow a report inside the server before it is counted (§6.6). Catchers are a powerful debugging and error-injection tool; you will write one in [E-DBG-1](/curriculum/T4_Expert/E-DBG-1_Advanced_UVM_Debug_Methodologies/index). For now, remember that they exist and that a catcher in a TB can change what the summary says.

### Reading the summary and deciding pass or fail

When all phases have finished, `run_test` calls `report_summarize()` on the report server and then `$finish` (Annex F.7.3.1 steps k–m). The summary looks like this (layout from uvm-core 2020.3.1 `uvm_report_server.svh`):

```text
UVM_INFO @ 40: reporter [UVM/REPORT/SERVER]
--- UVM Report Summary ---

** Report counts by severity
UVM_INFO :    4
UVM_WARNING :    1
UVM_ERROR :    0
UVM_FATAL :    0
** Report counts by id
[CFG_DEFAULT]     1
[CHK_DONE]     1
[RNTST]     1
[UVM/RELNOTES]     1
[VERDICT]     1
```

- **Report counts by severity**: how many reports of each severity the server handled (§6.5.1.2.6 `get_severity_count`). Filtered `` `uvm_info `` messages are not in these counts.
- **Report counts by id**: the same reports, by ID, in alphabetical order. This is your index: it tells you which kinds of event happened and how often. `RNTST` ("Running test …") and `UVM/RELNOTES` (the release-notes banner) are UVM's own messages.
- **Quit count** lines appear above the severity counts only when a maximum quit count is set (later in this lesson).

**The pass/fail rule.** A run passes only if all four of these hold:

| # | Condition | What it catches |
|---|---|---|
| 1 | The summary is present | a crash or a simulator kill before UVM finished |
| 2 | `UVM_ERROR :    0` and `UVM_FATAL :    0` | failed checks, timeouts, missing tests |
| 3 | Proof that checks ran: a scoreboard or checker count above zero | a **zero-activity run**, where nothing was compared, so nothing could fail |
| 4 | No simulator-format error lines (from `$error`, assertions or the tool itself) | failures UVM never saw |

Condition 3 is the one beginners skip. **`UVM_ERROR : 0` proves that no check failed, not that any check ran.** A test that ended at time 0, a sequence that never started, or a monitor that never saw a transaction all produce a perfect-looking summary. Two defences, and real TBs use both: each checker raises a `` `uvm_error `` in its `check_phase` when it compared nothing (Make It Work does this), and the regression script looks for a positive count line (`checks=4`, `matched=120`).

Warnings do not fail a run by default. Many teams add "`UVM_WARNING : 0`, or every warning ID is on an approved list" to the rule. That is a project policy, not a UVM rule.

**A verdict in the test.** A test can print its own one-line verdict from the server's counts in `report_phase` (§6.5.1.2.18 `get_server`, §6.5.1.2.6):

```systemverilog
// snippet: the verdict used in Make It Work
function void report_phase(uvm_phase phase);
  uvm_report_server svr = uvm_report_server::get_server();
  int failures = svr.get_severity_count(UVM_ERROR) + svr.get_severity_count(UVM_FATAL);
  if (failures == 0) begin
    `uvm_info("VERDICT", "TEST PASSED", UVM_NONE)
  end else begin
    `uvm_info("VERDICT", $sformatf("TEST FAILED: %0d error(s)", failures), UVM_NONE)
  end
endfunction
```

The line is convenient for humans, but it is not the contract. A `UVM_FATAL` ends the run before `report_phase` (next sections), so a fatal run has **no** verdict line at all, and a script that only searches for `TEST FAILED` would pass it. Scripts must check the summary.

### Actions: display, log, count, exit, stop

An **action** is a set of flags telling the report server what to do with a report (Annex F.2.2.2). You combine them with `|`:

| Action | What the server does |
|---|---|
| `UVM_DISPLAY` | prints the report to standard output |
| `UVM_LOG` | writes it to the file descriptor configured for it |
| `UVM_COUNT` | adds 1 to the **quit counter**; the run ends when the counter reaches the maximum quit count |
| `UVM_EXIT` | ends the run at once: `uvm_root::die()` prints the summary and calls `$finish` (F.7.3.2) |
| `UVM_STOP` | calls `$stop`, pausing the simulator in interactive mode (useful while debugging) |
| `UVM_NO_ACTION` | nothing: the report is dropped before it is counted |

`UVM_RM_RECORD` (send the report to the transaction recorder) also exists; recording is [I-UVM-6](/curriculum/T2_Intermediate/I-UVM-6_UVM_Recording_Classes/index)'s topic.

The handler chooses an action per report: an action set for a (severity, ID) pair wins over one set for an ID, which wins over one set for a severity (§6.4.4.1). The defaults are the table in the first section: info and warning display; error displays and counts; fatal displays and exits (§6.3).

Two facts about counting surprise almost everyone, and both come straight from uvm-core 2020.3.1 (`uvm_report_server.svh`, `process_report_message` and `execute_report_message`):

- **Every report the server executes is counted in the summary, whatever its action.** Removing `UVM_DISPLAY` hides an error from the screen, but `UVM_ERROR` still counts it. Removing `UVM_COUNT` only stops the error feeding the quit counter.
- **`UVM_NO_ACTION` removes a report before counting.** `+uvm_set_action=uvm_test_top.*,_ALL_,UVM_ERROR,UVM_NO_ACTION` on a regression command line turns every error below the test into nothing, and the run "passes". Treat that string as a red flag in any review.

**Experiment.** The explorer below runs a small error-injection test, `crc_inject_test`, on a model of this pipeline. Its sequence corrupts the CRC (a checksum) of packets 2 and 4 on purpose, so the monitor reports two *expected* `CRC` errors; packet 5 then exposes a *real* DUT bug through a `SCB` error; and an interface assertion fails with `$error`. Leave the **Report catcher** knob on `none`: catchers are [E-DBG-1](/curriculum/T4_Expert/E-DBG-1_Advanced_UVM_Debug_Methodologies/index)'s topic. Before each change, **predict the `UVM_ERROR` count**:

1. **Defaults.** How many of the four error-looking messages are counted?
2. **`+UVM_VERBOSITY=UVM_LOW`.** Does the error count change?
3. **Errors: `UVM_DISPLAY` only** (`UVM_COUNT` removed, with a quit limit of 2). Does the count drop?
4. **`+UVM_MAX_QUIT_COUNT=2`.** Which error is never issued?
5. **`UVM_NO_ACTION` on errors.** What verdict does the summary give, and is it true?

**Debrief.**
1. Three: the two `CRC` errors and the `SCB` mismatch. The `$error` is printed by the simulator but never counted (see "Messages UVM never sees" below).
2. No. `UVM_LOW` hides the `UVM_MEDIUM` and `UVM_HIGH` information lines only; the count stays 3.
3. No, still 3. Without `UVM_COUNT` the quit counter never moves, so the run is not stopped either.
4. The real bug. The second `CRC` error reaches the limit at 150 ns, the server adds `UVM_EXIT`, and the run ends before packet 5: the test fails, but for the wrong reason, and the real bug is invisible in this log.
5. "Passed", with `UVM_ERROR :    0`, and it is false: every error was dropped before counting, the real bug included. The `$error` fired too, and the summary cannot show it.

**File logging.** `UVM_LOG` writes a report to a file, but only to a file you open and attach yourself: the default file handle is 0, which means "no file", even when `UVM_LOG` is set (§6.3 item d, §6.3.6.2). A common use is a separate errors file:

```systemverilog
// snippet: in sum_test (Make It Work), after build_phase has created the tree
UVM_FILE err_log;

function void start_of_simulation_phase(uvm_phase phase);
  err_log = $fopen("errors.log", "w");
  // Errors from this component and everything below it: screen, file and count.
  set_report_severity_file_hier(UVM_ERROR, err_log);
  set_report_severity_action_hier(UVM_ERROR, UVM_DISPLAY | UVM_LOG | UVM_COUNT);
endfunction

function void final_phase(uvm_phase phase);
  $fclose(err_log);
endfunction
```

The `_hier` forms (Annex D.2.2) apply the setting to this component and every component **that exists at the time of the call**, so call them after `build_phase`. Set the file and the action together: a file without `UVM_LOG` writes nothing, and `UVM_LOG` without a file writes nothing. Files can be set per severity, ID or (severity, ID) pair, with the same precedence as actions (§6.4.5.1). You open and close the file; UVM does not (§6.4.5.2).

### Controlling reports from code and from the command line

Every report setting has a code form, called on a component (§6.3.4–§6.3.7, Annex D.2.2), and most have a plusarg form (Annex G.2). Plusargs let you change a run without recompiling.

| You want to | In code (on a component) | On the command line |
|---|---|---|
| choose the test | `run_test("name")` in the top module | `+UVM_TESTNAME=<name>` (G.2.1) |
| set verbosity for the whole TB | `uvm_root::get().set_report_verbosity_level_hier(UVM_HIGH)` | `+UVM_VERBOSITY=UVM_HIGH` (G.2.2) |
| set verbosity for one component or ID | `set_report_verbosity_level(…)`, `set_report_id_verbosity("CHK", UVM_HIGH)` | `+uvm_set_verbosity=<comp>,<id>,<verbosity>,<phase>` (G.2.3) |
| change an action | `set_report_severity_action`, `set_report_id_action`, `set_report_severity_id_action` (§6.3.5.2) | `+uvm_set_action=<comp>,<id>,<severity>,<action>` (G.2.4) |
| change a severity | `set_report_severity_override`, `set_report_severity_id_override` (§6.3.7) | `+uvm_set_severity=<comp>,<id>,<old>,<new>` (G.2.5) |
| stop after N errors | `uvm_report_server::get_server().set_max_quit_count(N)` (§6.5.1.2.3) | `+UVM_MAX_QUIT_COUNT=<N>,<YES or NO>` (G.2.6) |
| bound simulated time | `uvm_root::get().set_timeout(1ms, 1)` (F.7.3.3) | `+UVM_TIMEOUT=<integer>,<YES or NO>` (uvm-core only) |

How to write the lower-case `+uvm_set_*` plusargs (uvm-core 2020.3.1 `uvm_cmdline_report.svh`, `uvm_component.svh`):

- `<comp>` is a full hierarchical name, and may contain the wildcards `*` and `?`. `uvm_test_top.env.*` matches everything below `env` but **not** `env` itself.
- `<id>` is one ID, or `_ALL_` for every ID. IDs cannot contain wildcards (G.2.3).
- `<severity>` in `+uvm_set_action` and `<old>` in `+uvm_set_severity` may be `_ALL_` as well.
- `<action>` is `UVM_NO_ACTION` or flags joined with `|`, for example `UVM_DISPLAY|UVM_COUNT|UVM_STOP`. Quote it in your shell, because `|` is a shell pipe.
- `<phase>` in `+uvm_set_verbosity` is a phase name without `_phase`: `build` applies the setting as the component is constructed, `run` when its `run_phase` starts. The form `…,time,<t>` applies it at simulation time `t`.
- In `+UVM_MAX_QUIT_COUNT` and `+UVM_TIMEOUT` the `,YES` or `,NO` field may be left off; uvm-core then treats it as `YES`.
- Upper-case plusargs (`+UVM_TESTNAME`, `+UVM_VERBOSITY`, `+UVM_MAX_QUIT_COUNT`) take one value: if you give several, the first wins and UVM warns. Lower-case ones may be repeated (G.1).
- A setting whose `<comp>` pattern matches no component is reported as `UVM_WARNING … [INVLCMDARGS] … never took effect`. A badly formed setting is ignored with the same ID. Search for that ID whenever a plusarg "does nothing".

Examples you will use all the time:

```bash
# Tool-dependent: <simulate> stands for your simulator's run command.
<simulate> tb_top +UVM_TESTNAME=sum_bug_test               # run another test
<simulate> tb_top +UVM_VERBOSITY=UVM_LOW                   # quieter log
<simulate> tb_top '+uvm_set_verbosity=uvm_test_top.chk,CHK,UVM_HIGH,build'
<simulate> tb_top '+uvm_set_severity=uvm_test_top,CFG_DEFAULT,UVM_WARNING,UVM_INFO'
<simulate> tb_top \
  '+uvm_set_action=uvm_test_top.chk,MISMATCH,UVM_ERROR,UVM_DISPLAY|UVM_COUNT|UVM_STOP'
```

The last line pauses the simulator at the first mismatch, so you can inspect signals interactively, without editing code.

**`+UVM_TESTNAME` wins.** In `run_test(test_name)`, if `+UVM_TESTNAME=<name>` is on the command line, UVM creates that test, and the argument is used only when no plusarg is given (F.7.3.1 steps d–e). So `run_test("sum_test")` in `tb_top` is just a default: one compiled image runs every registered test. If the name matches no registered class, the run ends at once with `UVM_FATAL … [INVTST] Requested test from command line +UVM_TESTNAME=… not found.` Check the spelling and the `` `uvm_component_utils `` line.

**A severity override changes what a report *is*.** `+uvm_set_severity` (or `set_report_severity_id_override`) changes the severity in the handler, before the action is chosen, so a warning demoted to `UVM_INFO` is printed, counted and acted on as an info message (uvm-core `uvm_report_handler.svh`). Use it for a *known, reviewed* warning, by ID, never for a whole severity. There is no `_hier` form of the severity override (Annex D.2.2 lists none): in code you call it on each component, or you use the plusarg with a wildcard.

**Your own plusargs.** UVM's command-line processor reads any plusarg, not only UVM's own (G.1). Make It Work reads `+NUM_ITEMS=<n>`:

```systemverilog
// snippet: G.1.2 get_inst, G.1.4.1 get_arg_value
uvm_cmdline_processor clp = uvm_cmdline_processor::get_inst();
string value;
if (clp.get_arg_value("+NUM_ITEMS=", value) > 0) num_items = value.atoi();
```

`get_arg_value` returns how many arguments matched and gives you the text after the first match; `get_arg_values` returns all of them. The SystemVerilog `$value$plusargs` from [F2D](/curriculum/T1_Foundational/F2D_Reusable_Code_and_Parallelism/index) works too. Other UVM plusargs belong to other lessons: `+uvm_set_type_override` and `+uvm_set_inst_override` (G.2.7, [I-UVM-1B](/curriculum/T2_Intermediate/I-UVM-1B_The_UVM_Factory/index)), `+uvm_set_config_int` and `+uvm_set_config_string` (G.2.8, [I-UVM-2C](/curriculum/T2_Intermediate/I-UVM-2C_Configuration_and_Resources/index)), and `+uvm_set_default_sequence` (G.2.9, [I-UVM-3A](/curriculum/T2_Intermediate/I-UVM-3A_Fundamentals/index)).

### Ending a run: normally, by timeout, or by quit count

Apart from a crash, a simulator kill or a SystemVerilog `$fatal`, a UVM run ends in one of two ways (Annex F.7.3):

- **Normally.** All phases finish; `run_test` calls `report_summarize()` and then `$finish`. `check_phase` and `report_phase` ran, so checker and verdict lines are in the log.
- **Through `die()`.** A report with the `UVM_EXIT` action (every `UVM_FATAL` by default, or the error that reaches the quit limit) calls `uvm_root::die()`, which calls `pre_abort()` on every component, prints the summary and calls `$finish` (F.7.3.2). **No further phases run**: no `check_phase`, no `report_phase`, no verdict line.

Three knobs bound a run so that a broken test cannot run forever or bury the first failure:

- **`set_timeout(time, overridable)`** (F.7.3.3) sets the maximum simulation time. When it is reached, UVM reports `UVM_FATAL … [PH_TIMEOUT] Explicit timeout of … hit, indicating a probable testbench issue`, which ends the run through `die()`. Without a call the limit is implementation specific: 9200 s in uvm-core (`` `UVM_DEFAULT_TIMEOUT ``), and the message then says "Default timeout". Set it in the test's `build_phase`. [I-UVM-1C](/curriculum/T2_Intermediate/I-UVM-1C_UVM_Phasing/index) covers where hangs come from and the time-unit trap.
- **`+UVM_TIMEOUT=<integer>,<YES or NO>`** sets the same limit from the command line. It is **uvm-core only**: IEEE 1800.2-2020 does not define it. The integer is in `uvm_pkg`'s time unit (tool-dependent), and `NO` stops the test's own `set_timeout` from replacing it.
- **`+UVM_MAX_QUIT_COUNT=<N>,<YES or NO>`** (G.2.6) ends the run when the quit counter reaches N. Each report whose action includes `UVM_COUNT` (every `UVM_ERROR` by default) adds 1, and the report that reaches N gets `UVM_EXIT` added. The summary then starts with `Quit count reached!` and `Quit count :     N of     N`. The default maximum is 0, which means "never stop on a count" (uvm-core `uvm_report_server.svh`). `NO` makes the value final: a later `set_max_quit_count` in code is ignored.

### Messages UVM never sees: `$display`, `$error` and assertions

The report server counts only reports that go through UVM. Everything else is invisible to the summary:

- **`$display`** prints a line. It has no severity, so there is nothing to count.
- **`$error`, `$warning`, `$fatal`** are SystemVerilog severity tasks (IEEE 1800-2023 §20.10). The **simulator** prints them, in its own format; they never enter the UVM report server. A `$error` inside a component does not change `UVM_ERROR`. (`$fatal` ends the simulation with `$finish` immediately, also without a UVM summary.)
- **Assertions.** An `assert` statement with no `else` clause calls `$error` when it fails (IEEE 1800-2023 §16.3, §20.10). So a SystemVerilog Assertion (SVA) in an interface can fail a thousand times while the UVM summary says `UVM_ERROR :    0`.

To route a failure into UVM, call a UVM macro in the fail action. Outside a class, the macros use the global report functions, which report through `uvm_root` (Annex F.3.2.1), so the interface needs only the import and the include:

```systemverilog
// snippet: an interface whose assertion is counted by UVM
`include "uvm_macros.svh"
interface sum_if (input logic clk);
  import uvm_pkg::*;
  logic valid, ready;

  // Once valid is high it must stay high until ready (a handshake rule).
  a_hold: assert property (@(posedge clk) valid && !ready |=> valid)
    else `uvm_error("SUM_IF_SVA", "valid dropped before ready")
endinterface
```

The message shows `reporter` as its source, so put the interface's identity in the ID or the text. Verification IP (VIP) interfaces add an enable knob so that error-injection tests can switch the checks off, and tests can also control assertions with `$assertoff`: both are in [A-UVM-7](/curriculum/T3_Advanced/A-UVM-7_VIP_Construction/index). Until every check reports through UVM, condition 4 of the pass/fail rule (no simulator-format error lines) is your safety net, so regression scripts search the whole log, not only the summary.

### Recap

- Four macros, one ID each; only `` `uvm_info `` has a verbosity, and verbosity never hides warnings, errors or fatals.
- Report object (settings and calls) → its handler (override, action, file) → one server (catchers, count, display, log, quit, exit) → one summary at the end.
- Pass = summary present, `UVM_ERROR` and `UVM_FATAL` both 0, a positive check count, and no simulator-format errors.
- The server counts every report it executes; only `UVM_NO_ACTION` and catchers remove a report from the counts.
- `+UVM_TESTNAME` beats `run_test("…")`; `+uvm_set_*` targets components and IDs; `INVLCMDARGS` means a setting did nothing.
- A fatal, a timeout or a reached quit count ends the run through `die()`: no `check_phase`, no `report_phase`.
- `$display`, `$error` and default assertion failures are invisible to UVM; route them with the macros.

## Make It Work

### One test, three runs, three verdicts

This complete example has no design under test (DUT). A small checker component, `sum_checker`, stands in for a DUT and its scoreboard: the test hands it pairs of numbers, it "computes" their sum, and it compares the result with the expected sum. A second test, `sum_bug_test`, injects a wrong result on the third check. The test reads a project plusarg, `+NUM_ITEMS`, and prints its own verdict from the report server's counts.

```systemverilog
// compile
// report_tb.sv: compile together with uvm-core 2020.3.1.
`timescale 1ns/1ps

package report_pkg;
  import uvm_pkg::*;
  `include "uvm_macros.svh"

  // Stands in for a DUT and its checker: it "computes" a + b, with an optional
  // injected bug, and compares the result with the expected sum.
  class sum_checker extends uvm_component;
    `uvm_component_utils(sum_checker)
    int unsigned checks;   // results compared so far
    int unsigned bug_at;   // corrupt this result (0 = never)

    function new(string name, uvm_component parent);
      super.new(name, parent);
    endfunction

    function void check_sum(int unsigned a, int unsigned b);
      int unsigned actual;
      checks++;
      actual = (checks == bug_at) ? a + b + 1 : a + b;  // the "DUT"
      // Debug detail: hidden at the default verbosity, UVM_MEDIUM.
      `uvm_info("CHK", $sformatf("check %0d: %0d + %0d = %0d", checks, a, b, actual),
                UVM_HIGH)
      if (actual != a + b) begin
        `uvm_error("MISMATCH",
                   $sformatf("check %0d: expected %0d, got %0d", checks, a + b, actual))
      end
    endfunction

    // A run that compared nothing proves nothing, so make it fail.
    function void check_phase(uvm_phase phase);
      if (checks == 0) begin
        `uvm_error("NO_CHECKS", "no result was compared")
      end
    endfunction

    // Positive evidence for the log reader: how many checks ran.
    function void report_phase(uvm_phase phase);
      `uvm_info("CHK_DONE", $sformatf("checks=%0d", checks), UVM_LOW)
    endfunction
  endclass

  class sum_test extends uvm_test;
    `uvm_component_utils(sum_test)
    sum_checker  chk;
    int unsigned num_items = 4;

    function new(string name, uvm_component parent);
      super.new(name, parent);
    endfunction

    function void build_phase(uvm_phase phase);
      uvm_cmdline_processor clp;
      string value;
      super.build_phase(phase);
      chk = sum_checker::type_id::create("chk", this);
      // A project plusarg, read through UVM's command-line processor (G.1).
      clp = uvm_cmdline_processor::get_inst();
      if (clp.get_arg_value("+NUM_ITEMS=", value) > 0) begin
        num_items = value.atoi();
      end else begin
        `uvm_warning("CFG_DEFAULT",
                     $sformatf("+NUM_ITEMS not set, using %0d", num_items))
      end
      // Bound a hang: the run may not pass 1 us of simulated time (F.7.3.3).
      uvm_root::get().set_timeout(1us, 1);
    endfunction

    task run_phase(uvm_phase phase);
      phase.raise_objection(this, "checking sums");
      for (int unsigned i = 1; i <= num_items; i++) begin
        #10ns;
        chk.check_sum(i, 10 * i);
      end
      phase.drop_objection(this, "sums checked");
    endtask

    // A human-readable verdict. Scripts must still read the summary:
    // a UVM_FATAL ends the run before this phase.
    function void report_phase(uvm_phase phase);
      uvm_report_server svr = uvm_report_server::get_server();
      int failures = svr.get_severity_count(UVM_ERROR)
                     + svr.get_severity_count(UVM_FATAL);
      if (failures == 0) begin
        `uvm_info("VERDICT", "TEST PASSED", UVM_NONE)
      end else begin
        `uvm_info("VERDICT", $sformatf("TEST FAILED: %0d error(s)", failures), UVM_NONE)
      end
    endfunction
  endclass

  // The same test with a DUT bug on the third result.
  class sum_bug_test extends sum_test;
    `uvm_component_utils(sum_bug_test)

    function new(string name, uvm_component parent);
      super.new(name, parent);
    endfunction

    function void build_phase(uvm_phase phase);
      super.build_phase(phase);
      chk.bug_at = 3;
    endfunction
  endclass
endpackage

module tb_top;
  import uvm_pkg::*;
  import report_pkg::*;

  // Only a default: +UVM_TESTNAME=<name> on the command line wins (F.7.3.1).
  initial run_test("sum_test");
endmodule
```

### How to make a UVM run judgeable

1. **Report through the macros only**, with one stable ID per kind of event: `` `uvm_error `` for a failed check, `` `uvm_fatal `` only when the run cannot continue, `` `uvm_warning `` for "suspicious but not wrong", `` `uvm_info `` with a deliberate verbosity for everything else.
2. **Give every checker a zero-activity guard** in `check_phase`, and print a positive count in `report_phase` (`checks=`, `matched=`).
3. **Set a timeout** in the test's `build_phase`, and keep `run_test("<default test>")` in `tb_top` so `+UVM_TESTNAME` can choose any test.
4. **Route assertions and legacy checks into UVM** with `` `uvm_error `` in their fail actions.
5. **Decide pass or fail in the script** from the summary (present, `UVM_ERROR` = 0, `UVM_FATAL` = 0), a positive check count, and no simulator-format error lines.
6. **Debug with plusargs, not edits**: `+uvm_set_verbosity` on one component and ID, `+UVM_MAX_QUIT_COUNT=1` to stop at the first error, `UVM_STOP` to pause there. Search for `INVLCMDARGS` when a setting seems ignored.

**Checklist before moving on:**
- [ ] I can say which of `` `uvm_info(…, UVM_HIGH) ``, `` `uvm_warning `` and `` `uvm_error `` print at `UVM_LOW`, and why.
- [ ] I can judge runs A, B and C with the four-condition rule and name the first failure in each failing run.
- [ ] I can write the plusarg that raises one ID's verbosity in one component, and the one that demotes one known warning.
- [ ] I can explain why `+UVM_MAX_QUIT_COUNT=1` removes the verdict line from run B.
- [ ] I can explain why a `$error` or an assertion with no `else` clause leaves `UVM_ERROR :    0`, and fix it.
- [ ] My checkers fail a run that compared nothing.

## Push Further

### Expert: what the counters really count

The standard describes `UVM_COUNT` as incrementing the quit counter (Annex F.2.2.2) and `get_severity_count` as "the count of already passed messages" (§6.5.1.2.6). uvm-core 2020.3.1 makes the split exact (`uvm_report_server.svh`):

- `process_report_message` runs the catchers, returns early on `CAUGHT`, then returns early if the action is `UVM_NO_ACTION`. Those reports are never counted.
- `execute_report_message` first increments the severity count and the ID count for **every** report it receives, and only then looks at the action flags. `UVM_COUNT` increments the quit counter only when the maximum quit count is non-zero, and adds `UVM_EXIT` when the count is reached.
- The macros also check the action before building the message (`` `uvm_report_begin ``): a report whose action is `UVM_NO_ACTION` is not even formatted.

Consequences: an error with action `UVM_DISPLAY` only, or `UVM_LOG` only, still makes the run fail on the summary; an error with `UVM_NO_ACTION` or caught by a catcher does not; and a demoted error is counted at its new severity. The LRM text of §6.5.1.2.3 calls these "UVM_QUIT actions"; the enumeration value is `UVM_COUNT`.

### Expert: when command-line report settings take effect

The standard defines what each plusarg means (Annex G.2) but not exactly when it is applied. In uvm-core 2020.3.1:

- `+UVM_VERBOSITY` is read during UVM's initialization, before the test exists, and applied to `uvm_root` and everything below it (`uvm_root::m_check_verbosity`, which calls `set_report_verbosity_level_hier`). Each new component copies its parent's verbosity in its constructor.
- `+uvm_set_verbosity` (phase `build`), `+uvm_set_action` and `+uvm_set_severity` are applied **in each component's constructor** (`uvm_component::new` calls `m_set_cl_msg_args`). So a `set_report_*` call in that component's `build_phase` or later, in code, **replaces** the command-line setting. If a plusarg seems ignored, look for code that sets the same thing.
- A `+uvm_set_verbosity` with another phase name is applied when that phase starts in that component; the `time` form is applied by a thread in `uvm_root`.
- `+UVM_TIMEOUT` and `+UVM_MAX_QUIT_COUNT` are applied in `uvm_root::build_phase`, which runs before the test's `build_phase` (top-down). With `YES` or no second field the test can still change them; with `NO` the test's `set_timeout` or `set_max_quit_count` is ignored with an info message (`NOTIMOUTOVR`, `NOMAXQUITOVR`).
- Unused `+uvm_set_action` and `+uvm_set_severity` settings are reported as `INVLCMDARGS` warnings when `run_phase` starts; unused `+uvm_set_verbosity` settings at the end of `run_test`. Both are `UVM_WARNING`s, so they show in the counts.
- `+UVM_DUMP_REPORT_ARGS` prints a table of every reporting plusarg and which components it reached (uvm-core only).

### Expert: the exit status is not the verdict

Tool-dependent. UVM ends every run, passing or failing, with `$finish`: after the summary in `run_test` (F.7.3.1 step m) and in `die()` (F.7.3.2 step f). A `UVM_FATAL` is a UVM report, not a call to `$fatal`. IEEE 1800-2023 §20.2 defines `$finish`'s argument only as a diagnostics level and says nothing about the process exit status. So whether a simulator returns a non-zero status for a run with `UVM_ERROR :    3` depends on the tool and its options. Regression flows therefore parse the log. A robust parser:

- requires the `--- UVM Report Summary ---` block (a missing summary means a crash, a kill or a `$fatal`);
- extracts `UVM_ERROR` and `UVM_FATAL` with anchored patterns such as `^UVM_ERROR :\s+(\d+)$`, not a bare search for "UVM_ERROR", which also matches message lines;
- requires a positive check count from each checker;
- fails on the simulator's own error format, which is tool-dependent;
- records the first `UVM_ERROR` or `UVM_FATAL` line as the failure signature, so failures can be grouped (failure bucketing, [E-DBG-1](/curriculum/T4_Expert/E-DBG-1_Advanced_UVM_Debug_Methodologies/index)).

### Expert: the cost of messages at scale

Messages are not free. Each `` `uvm_info `` costs a verbosity lookup even when filtered, and a displayed one costs string formatting and output, which in a long SoC regression can dominate simulation time. The macros already skip the `$sformatf` when the message is filtered (B.1). For expensive debug work that is not a single message, such as printing a large object or computing a checksum only for a trace, guard it yourself:

```systemverilog
// snippet: §6.3.3.2 uvm_report_enabled
if (uvm_report_enabled(UVM_FULL, UVM_INFO, "PKT_DUMP")) begin
  `uvm_info("PKT_DUMP", pkt.sprint(), UVM_FULL)
end
```

Scale rules that experienced teams follow: regressions run at `UVM_LOW` (or `UVM_NONE`), debug reruns raise one component and one ID, nothing per-transaction is `UVM_LOW` or below, and per-cycle messages are `UVM_FULL` or `UVM_DEBUG`. The ID counts in the summary are your profiler: an ID with a count of 2 million is a performance bug. [E-PERF-1](/curriculum/T4_Expert/E-PERF-1_UVM_Performance/index) measures this.

### Expert: customizing the server and the message format

The report server is replaceable. `uvm_report_server::set_server(new_server)` installs a different server and copies the existing severity and ID counts into it (§6.5.1.2.19). Extending `uvm_default_report_server` (§6.5.2) and overriding `compose_report_message` (§6.5.1.2.15) changes the line format, for example to add a test name or a seed for log aggregation; overriding `report_summarize` adds lines to the summary. uvm-core also offers `show_verbosity` and `show_terminator` flags on its default server (uvm-core only). Do this once, in a company base test or package, so every log keeps one parseable format; changing the summary layout breaks every regression parser that reads it. Report catchers, which change individual messages rather than the format, are [E-DBG-1](/curriculum/T4_Expert/E-DBG-1_Advanced_UVM_Debug_Methodologies/index)'s topic, and methodology-wide customization is [E-CUST-1](/curriculum/T4_Expert/E-CUST-1_UVM_Methodology_Customization/index)'s.

Nothing is demoted: `uvm_test_top.*` matches the test's children (here `chk`), not the test that issues the warning, so the line still reads `UVM_WARNING @ 0: uvm_test_top [CFG_DEFAULT] …` and `UVM_WARNING :    1`. Because the pattern matched `chk`, UVM counts the setting as used and prints no `INVLCMDARGS` warning: the only symptom is that nothing changed. In a TB where the pattern matched no component at all, UVM would add `UVM_WARNING … [INVLCMDARGS] … never took effect due to a mismatching component pattern` at the start of `run_phase`. Lesson: a wildcard ending in `.*` never includes the component named before it.
4. In the test, for example at the start of `build_phase` before the warning can be issued: `set_report_severity_id_override(UVM_WARNING, "CFG_DEFAULT", UVM_INFO);` (§6.3.7). Code applied in `build_phase` runs after the constructor, so it would also replace any command-line setting for the same report.

</details>
