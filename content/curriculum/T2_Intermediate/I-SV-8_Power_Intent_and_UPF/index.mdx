## Quick Take

- **What it is:** **Power intent** says which parts of a chip can be powered down, how their supplies are switched, and what protects the logic that stays on. **IEEE 1801**, the **Unified Power Format (UPF)**, writes it as a separate file of Tcl commands that sits beside your unchanged register-transfer-level (RTL) code. A power-aware simulator, synthesis, equivalence checking and place and route all read the same UPF (IEEE 1801-2018 §1.3).
- **Why it matters:** RTL never loses power on its own. A simulation of plain RTL keeps every register alive, so a block that is switched off at the wrong moment, a missing clamp, or a lost register value stays invisible until silicon. Load the UPF and the same simulation shows those bugs as X values in the logic that stays on.
- **The Analogy:** The RTL is a building's floor plan; the UPF is its electrical plan. It has circuit breakers (power switches), a fuse at every doorway so a dark room's wiring cannot feed junk into the lit rooms (isolation), a battery backup for one filing cabinet (retention), an emergency-lighting circuit that never goes off (always-on logic), and transformers between rooms wired for different voltages (level shifters). *Where it breaks:* a dark room keeps its furniture. A powered-down block in simulation loses everything: every register becomes X. And when the lights come back, nothing returns by itself until a reset or a restore puts values back.

**You will be able to:**
1. Explain why power intent is written in a UPF side file, and how a simulator and the implementation tools apply it to RTL that never changes.
2. Write IEEE 1801 power intent for a two-domain design: power domains, supply ports, nets and sets, a power switch, and isolation, retention and level-shifter strategies.
3. Predict what a power-aware simulator shows at power-down and power-up: corrupted state (X for 4-state types, a default value for 2-state types), isolation clamps, and retention save and restore.
4. Define power states and legal transitions, and derive the verification scenarios they imply.
5. Choose a safe power-down and power-up order, and explain the bug that each wrong order causes.

## Build Your Mental Model

**How to read this lesson.** The core path is the first five subsections: two descriptions of one chip, the edition, power domains, the supply network, and what the simulator does when power goes away. Practitioner depth follows: the three strategies (isolation, retention, level shifting), power states, sequencing and the pitfalls. Make It Work builds one complete two-domain example, and Push Further holds the expert corner cases. This lesson is an elective at the end of Tier 2; [E-PWR-1](/curriculum/T4_Expert/E-PWR-1_Power_Aware_Verification/index) builds power-aware UVM verification on top of it.

A few words you need first, in one line each:
- **RTL**: the synthesizable SystemVerilog that describes the design's logic (modules, `always_ff` flops, assignments).
- **4-state and 2-state types**: a `logic` bit can be 0, 1, X or Z; a `bit` can only be 0 or 1 ([F2A](/curriculum/T1_Foundational/F2A_Core_Data_Types/index)). X means "unknown".
- **Instance path and scope**: `u_cpu` is an instance inside `soc_top`; `u_cpu/ctx_reg` names a register inside it. UPF writes hierarchy with `/` and is always read relative to a **scope**, a point in the hierarchy ([F4A](/curriculum/T1_Foundational/F4A_Modules_and_Packages/index)).
- **Tcl**: the scripting language most chip tools use. A UPF file is a list of Tcl commands; you only need to read and write the commands themselves.
- **PMU**: the **power-management unit**, ordinary RTL that never powers down and drives the control signals (isolate, save, power off, reset, restore) in the right order.
- **Implementation tools**: **synthesis** turns RTL into a **netlist** (a circuit of library gates); **equivalence checking** proves that two versions of a design compute the same thing; **place and route** lays the netlist out on silicon.
- **Gated clock**: a clock that a control signal can stop, so the logic it drives stops changing. An **asynchronous reset** acts as soon as it is asserted, without waiting for a clock edge.

### Two descriptions of one chip: logical intent and power intent

IEEE 1801-2018 §1.3 describes UPF files as "part of the design source": together with the hardware description they describe the whole design, the HDL giving the **logical intent** and the UPF the **power intent**. The RTL says what the logic computes. The UPF says which supply powers each part, how those supplies switch, and which protection cells sit at the boundaries. Neither file edits the other.

**Misconception: "loading the UPF changes my RTL."** It does not. The simulator reads the UPF beside the RTL and applies power behaviour itself: it corrupts a domain when its supply turns off, drives clamp values at isolated boundaries, and copies retained registers in and out. Synthesis is the first tool that adds real isolation, retention and level-shifter cells, and it adds them to the netlist it writes, not to your source. The flip side matters too: **without** the UPF, the simulator never powers anything down, so a plain RTL simulation can pass while the power sequence is broken.

UPF also supports **successive refinement** (§4.9): an early UPF may contain only power domains and supply sets, and later files add the supply wiring and implementation detail. §1.3 says it directly: for RTL power-aware simulation, the UPF "might only contain abstract models such as power domains and supply sets". This lesson writes the full network anyway, because seeing every supply makes the simulator's behaviour easier to predict.

### Which edition this lesson uses

UPF has changed a lot, and tools differ in which edition they read by default. Here is the history, from the IEEE 1801 working group's own timeline:

| Name | Standard | Year | What changed, in one line |
|---|---|---|---|
| UPF 1.0 | Accellera UPF | 2007 | The first version; donated to IEEE |
| UPF 2.0 | IEEE 1801-2009 | 2009 | Supply sets, `add_power_state`, refinement |
| UPF 2.1 | IEEE 1801-2013 | 2013 | Power state tables marked legacy; split isolation and retention control commands deprecated |
| UPF 2.2 | IEEE 1801a-2014 | 2014 | Amendment |
| UPF 3.0 | IEEE 1801-2015 | 2015 | Power states overhauled; predefined `ON` and `OFF` states for supply sets |
| UPF 3.1 | IEEE 1801-2018 | 2018 | Simulation-control commands; clarified semantics |
| UPF 4.0 | IEEE 1801-2024 | 2024 | Value conversion methods, virtual supplies, new retention conditions |

**This lesson's rule.** Command names and clause numbers come from **IEEE 1801-2018** (UPF 3.1), checked against its table of contents (published by IEC as IEC 61523-4:2023). Option spellings come from worked examples by the 1801 working group and the 2013 Accellera tutorial, because the clause bodies were not available to check. IEEE 1801-2024 (UPF 4.0) is the current edition and is free through the IEEE GET program; its working group lists none of this lesson's commands as removed. Every UPF file starts with `upf_version`, which tells the tool which syntax the following commands use:

```tcl
upf_version 3.1   ;# IEEE 1801-2018 syntax; check which version strings your tool accepts
```

If you meet `set_isolation_control`, `set_retention_control`, `create_pst` or `set_domain_supply_net` in an older file, that file is UPF 1.0 or 2.x style. Push Further explains what happened to them.

### Power domains and always-on logic

A **power domain** is a group of design instances that share the same primary supply, so they power up and down together. Every instance belongs to exactly one domain. `create_power_domain` (1801-2018 §6.20) makes one:

```tcl
# scope: soc_top
create_power_domain PD_TOP -include_scope      ;# soc_top and all not placed elsewhere
create_power_domain PD_CPU -elements {u_cpu}   ;# the CPU instance and everything below it
```

- `-elements {…}` lists instances (relative to the current scope) that belong to the domain, together with everything below them.
- `-include_scope` puts the current scope itself in the domain. Here `PD_TOP` gets `soc_top` and every child not claimed by another domain.
- A more specific `-elements` entry wins: the 2013 Accellera tutorial puts `P1` in one domain and `P1/M1` in another. That is how you carve an **always-on island** out of a switchable block.

**Always-on logic** is logic that must keep working while its neighbours are off: the PMU, a wake-up interrupt detector, a real-time clock. You make it always on by putting it in a domain whose primary supply never switches. Suppose the CPU has a small wake-up detector `u_cpu/u_wake` that must keep listening while the rest of the CPU is off:

```tcl
# snippet: an always-on island inside the switchable CPU (scope: soc_top)
create_power_domain PD_WAKE -elements {u_cpu/u_wake}
associate_supply_set SS_AON -handle PD_WAKE.primary      ;# never switched
# Its inputs that come from the rest of PD_CPU go X when PD_CPU is off: isolate them.
set_isolation iso_wake -domain PD_WAKE -applies_to inputs -source SS_CPU \
  -isolation_supply_set SS_AON -clamp_value 0 \
  -isolation_signal cpu_iso_en -isolation_sense high
```

The second half is the part people forget. The island keeps running, so anything it reads from the switched part of the CPU turns to X when that part powers down. Those inputs need isolation too (`-source SS_CPU` picks only the inputs driven from the switched supply). The supply-set commands are explained in the next subsection.

### The supply network: ports, nets, a switch and supply sets

Power has to reach each domain, and UPF describes the path with four kinds of object:

| Object | Command (1801-2018) | What it is |
|---|---|---|
| **Supply port** | `create_supply_port` (§6.25) | A connection point for power, like a pad on the chip boundary. The testbench drives top-level supply ports. |
| **Supply net** | `create_supply_net` (§6.24), `connect_supply_net` (§6.14) | A wire that carries a supply from a port or a switch to its loads. |
| **Power switch** | `create_power_switch` (§6.22) | A switch with an input supply, an output supply and a control signal from the design. When on, its output carries its input; when off, its output is OFF. |
| **Supply set** | `create_supply_set` (§6.26), `associate_supply_set` (§6.10) | A named bundle of supply functions, at least `power` and `ground` (also `nwell` and `pwell` where needed). Each domain has a **supply-set handle** such as `PD_CPU.primary`, a slot you fill by associating a supply set with it. |

A supply-set handle is a UPF name, not a SystemVerilog class handle. `PD_CPU.primary` simply means "the supply set that powers PD_CPU".

Each supply carries a **supply state** and a voltage. The states are `FULL_ON`, `PARTIAL_ON`, `OFF` and `UNDETERMINED`, and UPF writes a supply value as `{FULL_ON 0.8}` (state, then volts). Simulation follows these values through switches to every domain.

**One fact causes many wrong examples: a switch does not change voltage.** It connects or disconnects its input. If the CPU runs at 0.8 V while the rest of the chip runs at 1.2 V, the 0.8 V must enter the chip on its own supply port (or come from a regulator model), and the switch must take that 0.8 V supply as its input. Switching the 1.2 V supply and calling the result "0.8 V" gives a power state that can never be true.

Here is the supply network for the example, step by step (the full file is in Make It Work):

```tcl
# scope: soc_top. A supply port can be used wherever a supply net is expected.
create_supply_port VDD    -direction in      ;# 1.2 V pad: always-on logic
create_supply_port VDD_LV -direction in      ;# 0.8 V pad: the CPU's own voltage
create_supply_port VSS    -direction in      ;# ground
create_supply_net  VDD_CPU                   ;# the switched 0.8 V supply

create_power_switch psw_cpu \
  -input_supply_port  {vin  VDD_LV} \
  -output_supply_port {vout VDD_CPU} \
  -control_port       {ctrl cpu_pwr_en} \
  -on_state           {on_s vin {ctrl}} \
  -off_state          {off_s {!ctrl}}

create_supply_set SS_AON -function {power VDD}     -function {ground VSS}
create_supply_set SS_RET -function {power VDD_LV}  -function {ground VSS}
create_supply_set SS_CPU -function {power VDD_CPU} -function {ground VSS}
associate_supply_set SS_AON -handle PD_TOP.primary
associate_supply_set SS_CPU -handle PD_CPU.primary
```

- `-control_port {ctrl cpu_pwr_en}` names the switch's control port and the design net that drives it: the PMU output `cpu_pwr_en`. The UPF reads an RTL signal; the RTL never sees the switch.
- `-on_state {on_s vin {ctrl}}` says: when `ctrl` is 1, the output carries input `vin`. `-off_state {off_s {!ctrl}}` says: when `ctrl` is 0, the output is off. A real switch often also has an acknowledge output (`-ack_port`) that the PMU waits for before going on.
- `SS_RET` is an always-on 0.8 V set for the retention cells inside the CPU; Retention below uses it.
- When the supply ports and the supply nets have different names, `connect_supply_net` joins them, for example `connect_supply_net VDD_AON -ports {VDD}` after `create_supply_net VDD_AON`.

**The testbench powers the chip.** Nothing drives a supply port until the testbench does. A power-aware simulator provides a SystemVerilog package named `UPF` (the HDL interface of 1801-2018 §11.2) with functions such as `supply_on(path, volts)` and `supply_off(path)`. The 2013 Accellera tutorial uses them as `result = supply_on("Sub/VDD", 1.0);`. What an undriven supply port does is tool-dependent, so drive every one at time 0.

### What the simulator does at power-down and power-up

This is the heart of power-aware simulation, and the rules are short. When a domain's primary supply set goes to a state whose **simstate** (simulation state, explained under Power states) is `CORRUPT`, the simulator **corrupts** the domain (1801-2018 §9.5 defines simstate simulation):

1. Every register and latch in the domain, and every signal driven from inside it, takes a corrupted value: **X** for 4-state types such as `logic`. A 2-state type such as `bit` cannot hold X, so it reads a default value instead, typically 0, the 2-state default of IEEE 1800-2023 Table 6-7 (the exact choice is tool-dependent).
2. The domain's processes stop responding while it is off, so nothing inside can "fix" the X.
3. **Power returning restores nothing.** Registers stay X until something writes them: a reset, a retention restore, or a normal clocked load.
4. Outputs that are isolated read the **clamp** value while isolation is on. Outputs that are not isolated carry X into whatever reads them.

Two words to keep apart: **corruption** is what happens *inside* the off domain (values become X); **X-propagation** is what happens next, when that X travels into logic that is still on.

Here is the example traced through one power cycle. `ctx_reg` (context) is retained; `scratch` is not. Both outputs are isolated with clamp value 0.

| Signal (type) | Running | Power off (isolation on) | Power back on | After domain reset | After restore | After isolation release |
|---|---|---|---|---|---|---|
| `ctx_reg` (`logic [7:0]`, retained) | `A5` | X | X | `00` | `A5` | `A5` |
| `scratch` (`logic [7:0]`) | `3C` | X | X | `00` | `00` | `00` |
| `cpu_data_out` as `u_top` sees it | `A5` | `00` (clamp) | `00` | `00` | `00` | `A5` |
| `cpu_scr_out` as `u_top` sees it | `3C` | `00` (clamp) | `00` | `00` | `00` | `00` |

**Misconception: "a powered-down block's outputs read 0."** Only *isolated* outputs read their clamp, and the clamp can be 0 or 1 (or Z, or a latched value). An output with no isolation reads X in a 4-state simulation. Worse, a 2-state output reads 0, which looks like a clean, idle signal, so a missing isolation cell can hide behind a `bit` type.

**Predict, then check.** The model below powers `PD_CPU` down and up one PMU action per step. Choose **"Power off before isolation"** and, before you press play, write down the first step at which the always-on side (`top_out`) shows X. Then do the same for **"Release isolation before restore"** and **"Save after power-off"**.

**What the model showed.**
- *Power off before isolation:* X reaches the always-on side at step 2, the instant power drops, because the clamp is not on yet. The context still comes back, because it was saved while powered.
- *Release isolation before restore:* the context comes back, but X reaches the always-on side at step 5, the moment the clamp is lifted while `ctx` is still X.
- *Save after power-off:* the retention element saves X, the restore copies X back, and X reaches the always-on side at step 6.
- *Isolate, save, off, on, restore, release:* clean. Only the clamp or `A5` ever reaches the always-on side.

### Isolation strategies

An **isolation strategy** (`set_isolation`, 1801-2018 §6.45; simulation semantics in §9.8) puts an **isolation cell** on selected ports of a domain boundary. While the isolation signal is active, the cell ignores its input and drives a fixed **clamp value**. It protects the *receiving* side from a source that is off.

```tcl
set_isolation iso_cpu -domain PD_CPU -applies_to outputs \
  -isolation_supply_set SS_AON -clamp_value 0 \
  -isolation_signal cpu_iso_en -isolation_sense high -location parent
```

| Option | Values you will meet | What to choose |
|---|---|---|
| `-domain` | the domain whose boundary is isolated | the domain that switches off |
| `-applies_to` | `inputs`, `outputs`, `both` | Always write it: the default has differed between editions. Outputs of a switchable domain are the usual case. |
| `-elements`, `-source`, `-sink`, `-diff_supply_only` | port lists and supply filters | Narrow the strategy, e.g. `-source SS_CPU` for only the ports driven from the switched supply |
| `-clamp_value` | `0`, `1`, `Z`, `latch` | The value the receiver treats as idle: 0 for an active-high request, **1** for an active-low reset or request. `latch` holds the last value. |
| `-isolation_signal`, `-isolation_sense` | a design net; `high` or `low` | The PMU output that enables isolation, and which level means "isolate" |
| `-isolation_supply_set` | a supply set | An **always-on** set. The cell must stay powered while the source is off. |
| `-location` | `self`, `other`, `parent`, `fanout` (3.x syntax) | Where the cell goes. `parent` puts it on the parent side of the boundary, in always-on logic. |

The isolation cell, as the simulator models it:

| Isolation enable (`cpu_iso_en`) | Isolation supply | Cell output seen by `u_top` |
|---|---|---|
| inactive (0) | on | the input (X if the source domain is off) |
| active (1) | on | the clamp value (here 0) |
| X | on | X: an unknown enable gives an unknown output |
| any | off | corrupted: the cell itself has no power |

The last two rows are why the **isolation supply must be always-on** and why the **isolation enable must never be X**. An isolation cell powered from the switched supply dies together with the logic it should protect.

### Retention strategies

A **retention strategy** (`set_retention`, 1801-2018 §6.50; simulation in §9.7) keeps selected registers alive through a power-down. Picture each retained register with a small shadow storage element, often called a balloon latch, powered from an always-on retention supply:

- a **save** event copies the register into its shadow;
- the register itself is corrupted at power-off like everything else, while the shadow keeps its value;
- a **restore** event copies the shadow back into the register after power returns.

```tcl
set_retention ret_cpu -domain PD_CPU -elements {u_cpu/ctx_reg} \
  -retention_supply_set SS_RET \
  -save_signal {cpu_save high} -restore_signal {cpu_restore high}
```

- `-elements {u_cpu/ctx_reg}` chooses *which* registers are retained. Always write it. Without it, the strategy applies to the domain's state elements in general, not to the one register you meant to keep.
- `-save_signal {net sense}` and `-restore_signal {net sense}` name the PMU outputs. The sense is `high` or `low` for a level-sensitive control, or `posedge` or `negedge` for an edge-sensitive one.
- `-retention_supply_set` names the shadow's supply, here the always-on 0.8 V set `SS_RET`. This spelling appears in the 2013 tutorial; check it against the edition your tool reads.
- For a level-sensitive save signal, the 1801-2024 working group defines the save event as the trailing edge of the pulse; check your edition's §9.7 if your design depends on it. With the domain clock stopped before the save, the register cannot change during the pulse, so the saved value is the same either way. That is one reason the sequence below stops the clock first.

What the shadow saves depends on *when* you save:

Three ways to lose the value, each one a real bug:
- **Save after power-off:** the register is already X, so the shadow saves X.
- **Restore before power-on:** there is no powered register to restore into; it stays X.
- **Reset after restore:** the reset overwrites the restored value with the reset value. Reset first, then restore. Push Further covers what happens when reset and restore overlap.

**Misconception: "isolation and retention are interchangeable."** They solve different problems on different sides of the boundary. Isolation protects the *always-on receivers* from X while the source is off; it keeps nothing. Retention keeps *selected state inside* the switched domain for after power-up; it protects nobody while the domain is off. A domain that is switched off normally needs isolation on its outputs, and retention only if some of its state must survive. `-clamp_value latch` holds an output's last value at the boundary; it does not retain the register behind it.

### Level shifters

When two domains run at different voltages, a signal crossing between them needs a **level shifter**: a 0.8 V high may not read as a reliable 1 at 1.2 V, and a 1.2 V signal can overstress 0.8 V logic. A **level-shifter strategy** (`set_level_shifter`, 1801-2018 §6.46) says where shifters are required; the implementation tools insert the cells.

```tcl
set_level_shifter ls_cpu -domain PD_CPU -applies_to both -rule both -location self
```

- `-applies_to inputs|outputs|both` and `-rule low_to_high|high_to_low|both` select the crossings; `-threshold` sets the voltage difference below which no shifter is needed.
- The strategy needs both voltages, which come from the power states (next subsection): `SS_AON` at 1.2 V and `SS_CPU` at 0.8 V.
- In RTL simulation a level shifter is mostly invisible: values pass through unchanged. 1801-2018 §9.9 defines its simulation semantics, but most level-shifter bugs (missing, redundant or wrongly placed shifters) are found by static checking tools, not by simulation (tool-dependent).

### Power states, simstates and legal transitions

So far the simulator has followed the supplies. **Power states** give names to the combinations you care about, tell the simulator how to behave in each one, and tell the verification team which combinations and changes are legal. There are three layers, plus the simstate that each supply-set state carries:

| Layer | Example | Written with |
|---|---|---|
| Supply value of a port or net | `VDD_CPU` is `{FULL_ON 0.8}` or `OFF` | the switch, and `supply_on`/`supply_off` from the testbench |
| Power state of a **supply set** | `SS_CPU` is `ON` when power is `{FULL_ON 0.8}` and ground is `{FULL_ON 0.0}` | `add_power_state SS_CPU -supply` with `-supply_expr` |
| Power state of a **domain** (or a whole system) | `PD_CPU` is `RUN` when its primary set is `ON` | `add_power_state PD_CPU -domain` with `-logic_expr` |
| **Simstate** of the current supply-set state | `NORMAL` when `ON`, `CORRUPT` when `OFF` | `-simstate` on the supply-set state |

`add_power_state` (1801-2018 §6.5) defines them. Since 1801-2015 every supply set has predefined `ON` and `OFF` states, and you complete them with their supply expressions and voltages. The 1801 working group's own 2025 examples write them as below; if your tool reports that `ON` already exists, it expects the `-update` option (tool-dependent):

```tcl
add_power_state SS_CPU -supply \
  -state {ON  -simstate NORMAL \
          -supply_expr {power == {FULL_ON 0.8} && ground == {FULL_ON 0.0}}} \
  -state {OFF -supply_expr {power == OFF || ground == OFF} -simstate CORRUPT}
add_power_state PD_CPU -domain \
  -state {RUN   -logic_expr {primary == ON}} \
  -state {RET   -logic_expr {primary == OFF && SS_RET == ON}}
```

A **simstate** (§4.8) tells the simulator how much of the logic still works in a state. `NORMAL` means full behaviour and `CORRUPT` means everything is corrupted, as in the rules above. The editions since 1801-2013 also define intermediate simstates for reduced-voltage states, which corrupt only when the logic is used or changes: `CORRUPT_ON_ACTIVITY`, `CORRUPT_STATE_ON_ACTIVITY`, `CORRUPT_ON_CHANGE` and `CORRUPT_STATE_ON_CHANGE`. A low-voltage "standby" is not a special UPF state: it is a state you name yourself and give one of these simstates. A state can also be marked `-illegal`, so a tool can flag the design if it is ever entered.

**Legal transitions.** Once the states exist, the next question is which *changes* between them are allowed. 1801-2018 has a command for this, `add_state_transition` (§6.7); its options are not shown here because they were not checked, and tool support varies. Whatever you write in the UPF, the verification plan needs the same list. Take a CPU domain whose retention supply can also be switched off for a deeper sleep:

Each state and each arrow becomes a scenario in the verification plan:

| Item | Scenario | What the testbench checks |
|---|---|---|
| RUN → RET → RUN | sleep with retention, then wake | no X into PD_TOP; `ctx_reg` back to its saved value; non-retained state at reset values |
| RUN → OFF → RUN | full power-down, then cold wake | no X into PD_TOP; everything at reset values; no restore expected |
| RET → OFF | deep sleep from retention | the retained value is gone; the next wake must use reset, not restore |
| OFF → RET (illegal) | negative test | the PMU refuses it, or an assertion flags it |
| each state | state coverage | every state is reached, and each legal arrow is taken at least once |

Coding these checks and the coverage in a UVM testbench is the job of [E-PWR-1](/curriculum/T4_Expert/E-PWR-1_Power_Aware_Verification/index).

**Power state tables (PSTs) are legacy.** Older UPF lists legal supply combinations in a table: `create_pst` names supply *ports or nets*, and `add_pst_state` gives one row of *port states* (declared with `add_port_state`). The PST was marked legacy in 1801-2013, and §6.23 of 1801-2018 still lists it as legacy. Its job was static analysis, such as deciding where isolation and level shifters are needed. It does not drive power-aware simulation: the simulator follows the supply values and the simstates of the current power states. You will meet PSTs in older IP; do not start new UPF with them.

### Power-down and power-up sequencing

The PMU must drive the controls in an order that never lets X escape and never loses retained state. For a domain with isolation, retention, a gated clock and an asynchronous domain reset, the safe order is:

**Power down:** stop the domain clock → isolate → save → power off.

**Power up:** power on (and wait for the switch's acknowledge, where there is one) → reset the domain → restore → restart the clock → release isolation.

Each of these wrong orders produces a specific bug:

| Wrong order | What the simulator shows | In silicon |
|---|---|---|
| Power off before isolate | X reaches `u_top` at power-off | floating inputs, short-circuit current, corrupted always-on state |
| Isolate and power off on the same clock edge | no guaranteed order; an assertion such as "isolation was on in the cycle before power dropped" fails | a race between two control paths |
| Save after power off | the shadow saves X; `ctx_reg` is X after restore | lost context |
| Restore before power on | nothing to restore into; `ctx_reg` stays X | lost context |
| Reset after restore | `ctx_reg` ends at its reset value, not `A5` | lost context, often silently |
| No domain reset after power-up | `scratch` stays X; X reaches `u_top` at release | random state at wake-up |
| Release isolation before restore | X (or the reset value) reaches `u_top` until the restore | a glitch on the always-on side |
| Clock running during save | the register may change during the save | saved value one cycle stale or new |

**Reset while the clock is stopped.** In this sequence the domain is reset while its clock is still gated. A synchronous reset (`always_ff @(posedge clk)` that checks the reset) would never see a clock edge, and the registers would stay X. Either make the domain reset **asynchronous**, as the Make It Work CPU does, or turn the clock on for the reset window and say so in the PMU specification.

### Pitfalls and misconceptions

| Pitfall | Why it is wrong | Fix |
|---|---|---|
| "UPF edits the RTL" | The RTL is unchanged; the tools apply the UPF beside it | Keep power logic out of the RTL; read the tool's power report instead |
| "Powered-down outputs read 0" | Only isolated outputs read their clamp; others read X (or a 2-state default) | Isolate every output of a switchable domain that feeds always-on logic |
| "Isolation and retention are the same thing" | Isolation protects receivers; retention keeps selected state | Use isolation on the boundary, retention on the registers that must survive |
| "The power state table drives simulation" | PSTs are legacy and serve static analysis | Use `add_power_state` with simstates |
| Isolation cells on the switched supply | The cell dies with the source and drives X | `-isolation_supply_set` names an always-on set |
| PMU outputs X at time 0 | An X isolation enable gives X; an X switch control leaves the supply undetermined | Decode PMU controls from registers reset by an always-on power-on reset |
| Always-on island fed by switched logic | Its inputs go X when the neighbour powers down | Isolate the island's inputs with `-applies_to inputs -source` |
| `bit` (2-state) signals on a domain boundary | Corruption shows up as 0, which looks valid | Use `logic` on power-domain boundaries |
| Supply ports never driven | The default state of an undriven supply is tool-dependent | Drive every top-level supply port from the testbench at time 0 |
| A switch "converts" 1.2 V to 0.8 V | A switch passes its input through | Bring each voltage in on its own supply port |
| No `-applies_to` or no `-elements` | Defaults differ between editions and cover more or less than you meant | Write both explicitly |

### Recap

- The RTL holds the logical intent and the UPF the power intent; the RTL never changes, and without the UPF nothing ever powers down.
- Domains group logic by primary supply. Supply ports, nets, a switch and supply sets bring power to each domain, and the testbench drives the ports.
- When a supply turns off, the domain is corrupted (X, or a default for 2-state types), and nothing comes back by itself at power-up.
- Isolation clamps outputs for the always-on receivers; retention saves selected registers; level shifters bridge voltages.
- Power states name the supply combinations and their simstates; legal transitions become verification scenarios.
- Order: stop clock, isolate, save, off … on, reset, restore, clock on, release.

## Make It Work

### A two-domain SoC under power intent

This example puts the whole lesson in four files: the RTL, a testbench, the UPF, and the testbench lines that drive the supplies. The RTL and testbench are plain IEEE 1800-2023 SystemVerilog and run on any simulator **without** the UPF. That first run proves the point of objective 1: the same RTL, simulated with and without power intent, behaves differently.

**`soc_top.sv`** holds the always-on PMU, the switchable CPU, the always-on consumer `u_top`, and `soc_top`, which wires them together.

```systemverilog
// compile: soc_top.sv (compile together with tb_top.sv)
`timescale 1ns/1ps

// PD_TOP: the power-management unit (PMU). One step per always-on clock edge.
module pmu (
  input  logic clk, por_n, sleep_req, wake_req,
  output logic cpu_clk_en, cpu_iso_en, cpu_save, cpu_pwr_en, cpu_rst_n, cpu_restore
);
  typedef enum logic [3:0] {
    RUN, CLK_OFF, ISO_ON, SAVE, SAVED, OFF,
    PWR_ON, RST_ON, RST_OFF, RESTORE, RESTORED, CLK_ON
  } step_t;
  step_t step;

  always_ff @(posedge clk or negedge por_n)
    if (!por_n) step <= RUN;
    else case (step)
      RUN:     if (sleep_req) step <= CLK_OFF;
      OFF:     if (wake_req)  step <= PWR_ON;
      default: step <= step.next();   // CLK_ON.next() wraps back to RUN
    endcase

  // Every control is decoded from the registered step, so after the always-on
  // power-on reset none of them is ever X (an X enable would leak X).
  always_comb begin
    cpu_clk_en  = !(step inside {[CLK_OFF:RESTORED]});
    cpu_iso_en  =   step inside {[ISO_ON:CLK_ON]};
    cpu_save    = (step == SAVE);
    cpu_pwr_en  = (step != OFF);
    cpu_rst_n   = por_n && (step != RST_ON);  // chip reset also resets PD_CPU
    cpu_restore = (step == RESTORE);
  end
endmodule

// PD_CPU: the switchable CPU. Nothing in it knows that it can lose power.
module cpu_core (
  input  logic       clk,       // gated clock from PD_TOP
  input  logic       rst_n,     // domain reset from the PMU
  input  logic       load,
  input  logic [7:0] ctx_in,
  input  logic [7:0] scratch_in,
  output logic [7:0] data_out,
  output logic [7:0] scr_out
);
  logic [7:0] ctx_reg;   // context: the UPF retains it (ret_cpu)
  logic [7:0] scratch;   // working state: not retained

  // Asynchronous reset: it must work while the clock is stopped, which is
  // exactly when the PMU resets the domain after power-up.
  always_ff @(posedge clk or negedge rst_n)
    if (!rst_n) begin
      ctx_reg <= '0;
      scratch <= '0;
    end else if (load) begin
      ctx_reg <= ctx_in;
      scratch <= scratch_in;
    end

  assign data_out = ctx_reg;
  assign scr_out  = scratch;
endmodule

// PD_TOP: always-on logic that consumes the CPU outputs.
module top_logic (
  input logic       clk, por_n,
  input logic [7:0] cpu_data, cpu_scr
);
  logic [7:0] ctx_seen, scr_seen;

  always_ff @(posedge clk or negedge por_n)
    if (!por_n) begin
      ctx_seen <= '0;
      scr_seen <= '0;
    end else begin
      ctx_seen <= cpu_data;
      scr_seen <= cpu_scr;
    end
endmodule

module soc_top (
  input logic       clk, por_n, sleep_req, wake_req, load,
  input logic [7:0] ctx_in, scratch_in
);
  logic       cpu_clk_en, cpu_iso_en, cpu_save, cpu_pwr_en, cpu_rst_n, cpu_restore;
  logic       clk_en_q, cpu_clk;
  logic [7:0] cpu_data_out, cpu_scr_out;

  // cpu_save, cpu_restore and cpu_pwr_en have no RTL reader: the UPF uses them.
  pmu u_pmu (.clk, .por_n, .sleep_req, .wake_req, .cpu_clk_en, .cpu_iso_en,
             .cpu_save, .cpu_pwr_en, .cpu_rst_n, .cpu_restore);

  // Clock gate (always on). The latch follows cpu_clk_en only while clk is
  // low, so cpu_clk cannot glitch: the RTL model of a clock-gating cell.
  always_latch if (!clk) clk_en_q <= cpu_clk_en;
  assign cpu_clk = clk & clk_en_q;

  cpu_core u_cpu (.clk(cpu_clk), .rst_n(cpu_rst_n), .load, .ctx_in, .scratch_in,
                  .data_out(cpu_data_out), .scr_out(cpu_scr_out));

  top_logic u_top (.clk, .por_n, .cpu_data(cpu_data_out), .cpu_scr(cpu_scr_out));
endmodule
```

**`tb_top.sv`** loads `A5` and `3C`, asks for one sleep and one wake, and prints a line whenever the PMU enters a new step. Stimulus goes through a clocking block, so it changes after the design has sampled each clock edge ([F4C](/curriculum/T1_Foundational/F4C_Clocking_Blocks/index)).

```systemverilog
// compile: tb_top.sv (compile together with soc_top.sv)
`timescale 1ns/1ps

module tb_top;
  logic       clk = 1'b0;
  logic       por_n;
  logic       sleep_req = 1'b0, wake_req = 1'b0, load = 1'b0;
  logic [7:0] ctx_in = '0, scratch_in = '0;

  always #5 clk = ~clk;   // always-on clock: rising edges at 5, 15, 25 ... ns

  default clocking cb @(posedge clk);
    output sleep_req, wake_req, load, ctx_in, scratch_in;
  endclocking

  soc_top u_soc (.clk, .por_n, .sleep_req, .wake_req, .load, .ctx_in, .scratch_in);

  // $strobe prints at the end of the time slot, after every update (§21.2.2).
  always @(u_soc.u_pmu.step)
    if (por_n)
      $strobe("%0d %s pwr_en=%b iso_en=%b ctx_reg=%h scratch=%h | u_top sees %h %h",
              $time, u_soc.u_pmu.step.name(), u_soc.cpu_pwr_en, u_soc.cpu_iso_en,
              u_soc.u_cpu.ctx_reg, u_soc.u_cpu.scratch,
              u_soc.u_top.cpu_data, u_soc.u_top.cpu_scr);

  initial begin
    por_n = 1'b0;                     // always-on power-on reset
    repeat (2) @(negedge clk);
    por_n = 1'b1;                     // released on a falling edge, away from sampling
    ##1;
    cb.ctx_in <= 8'hA5;
    cb.scratch_in <= 8'h3C;
    cb.load <= 1'b1;
    ##1 cb.load <= 1'b0;
    $strobe("%0d loaded ctx_reg=%h scratch=%h | u_top sees %h %h", $time,
            u_soc.u_cpu.ctx_reg, u_soc.u_cpu.scratch,
            u_soc.u_top.cpu_data, u_soc.u_top.cpu_scr);
    ##2 cb.sleep_req <= 1'b1;         // ask the PMU to power PD_CPU down ...
    ##1 cb.sleep_req <= 1'b0;
    ##8 cb.wake_req <= 1'b1;          // ... and, later, to wake it up
    ##1 cb.wake_req <= 1'b0;
    ##8 $finish;
  end
endmodule
```

**`power_intent.upf`** is the power intent for `soc_top`. Every command is in the IEEE 1801-2018 command list; the option forms follow the 1801 working group's and the 2013 Accellera tutorial's examples.

```tcl
# power_intent.upf: power intent for soc_top (apply it at the instance tb_top.u_soc)
```

### How to write power intent for a new block

1. **List the domains.** Which instances switch off together? Which logic must stay on (PMU, wake detectors)? Write `create_power_domain` for each, with explicit `-elements`.
2. **Build the supply network.** One supply port per voltage, a switch per switchable domain fed from the right voltage, and supply sets with `power` and `ground`.
3. **Associate a supply set with every domain's primary handle.** An unpowered domain is a bug that looks like "everything X".
4. **Add isolation** on every output of a switchable domain that feeds logic that stays on, with an explicit `-applies_to`, an always-on `-isolation_supply_set`, and a clamp equal to the receiver's idle value.
5. **Add retention** only for the registers that must survive, with explicit `-elements` and an always-on retention supply.
6. **Add level shifters** wherever voltages differ.
7. **Write the power states**, with voltages and simstates, and list the legal transitions.
8. **Write the PMU order down** (clock, isolate, save, off … on, reset, restore, clock, release) and make the PMU's controls reset to safe values.
9. **Simulate with the supplies driven,** read the tool's power report, then check the log against your expected-behaviour table.

### Symptom, cause and fix

| Symptom in a power-aware run | Likely cause | Fix |
|---|---|---|
| Everything X from time 0, before any power event | a supply port is never driven, or a domain has no primary supply set | drive every supply port at time 0; associate a set with every `.primary` handle |
| X reaches `u_top` right after reset, before any power event | an isolation enable or switch control is X: PMU outputs not reset | decode PMU controls from registers reset by the always-on power-on reset |
| X reaches `u_top` at power-off | isolation missing, enabled in the same cycle as power-off, or the strategy matched other ports (`-applies_to`, `-elements`) | isolate at least one cycle earlier; check the tool's isolation report |
| X from the isolation cell itself while the domain is off | the isolation supply is the switched set | use an always-on `-isolation_supply_set` |
| `ctx_reg` X after wake | saved after power-off, restored before power-on, restore never pulsed, or retention supply switched | save while powered; restore after power-on; always-on retention supply |
| `ctx_reg` at its reset value after wake | reset applied after (or during) the restore | reset first, then restore |
| `scratch` X after wake, and X at release | no domain reset after power-up, or a synchronous reset while the clock is gated | asynchronous domain reset, or clock on for the reset window |
| X in an always-on island while its neighbour is off | the island's inputs from switched logic are not isolated | `set_isolation … -applies_to inputs -source <switched set>` on the island |
| The tool rejects `set_isolation_control` | deprecated UPF 1.0 split command in a `upf_version 3.1` file | merge the control options into `set_isolation` |

**Checklist before moving on:**
- [ ] The UPF states its edition with `upf_version`, and no deprecated split commands remain.
- [ ] Every domain has a primary supply set, and every supply port is driven by the testbench.
- [ ] Each voltage enters on its own supply port; no switch is expected to change voltage.
- [ ] Every switched domain's outputs are isolated, with an explicit `-applies_to` and an always-on isolation supply.
- [ ] Retention names its `-elements` and uses an always-on retention supply.
- [ ] PMU control outputs reset to safe values from an always-on reset.
- [ ] The power-down and power-up order is written down, and the domain reset works with the clock stopped.

## Push Further

### Expert: editions, legacy commands and mixed-version IP

- **History that interview questions turn on.** The UPF 1.0 split commands `set_isolation_control` and `set_retention_control` were already **deprecated** in IEEE 1801-2013 (§6.42 and §6.50 of that edition), and `create_pst`, `add_pst_state`, `add_port_state` and `set_domain_supply_net` were already **legacy**. In 1801-2018 the split commands are gone from the command list (clause 6), and the PST commands and `set_domain_supply_net` remain as legacy (§6.4, §6.6, §6.23, §6.43; Annex D lists the replacements).
- **1801-2024 (UPF 4.0)** lists as legacy or deprecated the `-domain` option of `create_supply_net`, `create_supply_port` and `create_power_switch`, the value conversion table commands, and `set_retention`'s `-save_condition`, `-restore_condition` and `-retention_condition` (1801 working group, DVCon 2025). That is why this lesson's supply commands carry no `-domain`.
- **`upf_version` is per file, semantics are per design** (Bhargava, Siemens, secondary source). Each UPF file can declare its syntax, but a tool applies one edition's semantics to the whole design. An SoC that loads an old IP file therefore gets the new semantics for that IP's commands, whatever its file says. Migrate IP UPF rather than relying on the tool's compatibility mode.
- **CPF**, the Si2 Common Power Format, is the other power format you may meet in older flows; the 1801 working group cites contributions from CPF 2.0 and 2.1 into IEEE 1801.

### Expert: simstates, current power state and partial corruption

- A supply set or domain can satisfy several power-state definitions at once. From UPF 3.0 the standard defines one **current power state** per object, and the simstate of the current state drives simulation (Bhargava, secondary source; IEEE 1801-2018 §4.7, §4.8 and §9.3–§9.6 cover the normative rules). UPF 3.0 also predefines `UNDEFINED` and `ERROR` states for every object, and `ON` and `OFF` for supply sets.
- The intermediate simstates model reduced-voltage operation. In summary, `CORRUPT_ON_ACTIVITY` and `CORRUPT_ON_CHANGE` corrupt logic when its inputs are active or its outputs change, and the `CORRUPT_STATE_ON_ACTIVITY` and `CORRUPT_STATE_ON_CHANGE` variants apply the same idea to sequential state only; §4.8 has the exact rules. Use them for low-voltage states in which the domain is powered but cannot switch reliably.
- **Refining states.** `add_power_state … -update` adds to or changes an existing definition. Marschner and Biggs (Mentor and Arm, DVCon) recommend refining by deriving new, mutually exclusive sub-states instead of editing existing ones, so that no other state's meaning changes underneath it.

### Expert: corruption corner cases

- **2-state hiding.** A `bit`, `int` or `byte` cannot be X, so a corrupted 2-state signal reads a default value (0 under IEEE 1800-2023 Table 6-7; the exact choice is tool-dependent). Power-domain boundaries should be 4-state.
- **X on a switch control.** An X or Z control leaves the switch output undetermined; tools report the supply as `UNDETERMINED` or as an error (tool-dependent). A PMU that comes out of reset late can corrupt a domain at time 0.
- **Retention supply loss.** If the retention supply itself drops, the shadow is lost too, and the next restore brings back garbage: that is the RET → OFF transition.
- **Initial blocks are not replayed.** An `initial` block runs once, at time 0. A behavioural ROM or PLL model whose contents come from an `initial` block stays X after its domain powers back up. 1801-2018 adds `sim_replay_control` (§6.57) to replay selected initial blocks when a domain returns to `NORMAL`; tool support varies.

### Expert: retention in detail, reset and restore together

- **Reset during restore.** If the domain reset and the restore overlap, the result depends on the retention cell. 1801-2018 does not let you say which cell you have; 1801-2024 adds `-async_set_reset_effect` with the values `ignored`, `retained_value` and `output_value` to describe what a set or reset does during the restore period (1801 working group, DVCon 2025). Until your flow uses it, keep reset and restore strictly ordered and add an assertion that they never overlap.
- **Clock conditions.** Many retention cells need the clock held low at the save and restore events. 1801-2024 expresses this with `-save_event_condition`, `-restore_event_condition`, `-restore_period_condition` and `-powerdown_period_condition`, for example `-save_event_condition {!UPF_GENERIC_CLOCK}`; these replace the legacy `-save_condition` family.
- **Edge-sensitive controls.** A single retention pin often saves on one edge and restores on the other: `-save_signal {RET posedge} -restore_signal {RET negedge}` (here `RET` is a control signal, not the RET power state), as in the 2013 tutorial and the 1801-2024 working group examples.

### Expert: successive refinement and IP reuse

- **Constraint, configuration and implementation UPF** (§4.9): an IP ships a constraint UPF (domains, supply sets, which ports need isolation) that the SoC configures (which supplies, which control nets) and implementation refines (cells and wiring). §1.3 explicitly allows RTL simulation with only abstract domains and supply sets.
- **Applying IP UPF:** `load_upf ip.upf -scope u_ip` (§6.33) runs an IP's file at its instance. `set_scope` (§6.52) and `set_design_top` (§6.42) set where commands apply. The SoC file then associates its own supply sets with the IP's, for example `associate_supply_set {SS_SOC_AON u_ip/SS_IP_AON}` as in the 1801 working group's 2025 examples.
- **1801-2024 refinable macros:** an IP marked with `set_design_attributes -models . -is_refinable_macro true` keeps its verified UPF untouched, and the SoC applies only the changes it is allowed to make through `load_upf … -implementation`.

### Expert: simulation-control commands (UPF 3.1)

IEEE 1801-2018 added three commands for problems every power-aware testbench hits (§6.55–§6.57; behaviour summarized from Bhargava, secondary source; support is tool-dependent):
- `sim_assertion_control` keeps assertions inside a powered-down domain from firing on corrupted signals: suspend, kill or reset them while their domain is off.
- `sim_corruption_control` changes which elements are corrupted, for example to exclude a behavioural model.
- `sim_replay_control` replays selected `initial` blocks at power-up.

Before UPF 3.1 the same effects needed tool-specific switches or `$assertcontrol` in the testbench; prefer the standard commands where your tool supports them.

### Expert: static and dynamic power verification

Two kinds of tool check power intent, and you need both (tool-dependent):
- **Static checkers** read the RTL or netlist with the UPF, with no stimulus. They find missing, redundant or wrongly supplied isolation cells and level shifters, crossings between domains in incompatible states, and strategies that match nothing.
- **Power-aware simulation** finds what depends on time and order: the PMU sequence, retention timing, reset after wake-up, and X reaching always-on logic. No static tool can tell you that the PMU drops power one cycle before isolation.

### Kata 2: write the UPF

**Objective:** write IEEE 1801 power intent from a specification (objective 2).

Write the UPF for this block, at the scope of its top module `chip`:
- `u_dsp` is switchable and runs at 0.9 V from its own supply port; everything else (`chip` and `u_ctrl`) is always on at 1.1 V;
- the switch is controlled by `dsp_pwr_en`; isolation is enabled by `dsp_iso_n`, which is **active low**;
- every output of `u_dsp` is isolated in the parent; the receivers treat `1` as idle on all of them;
- `u_dsp/coeff_reg` must survive a power-down; save on the rising edge of `dsp_ret` and restore on its falling edge;
- one level-shifter strategy covers all crossings;
- the DSP domain has power states `ACTIVE` and `SLEEP`.

<details>
<summary>Worked solution (try the kata first)</summary>

```tcl
upf_version 3.1
create_power_domain PD_CHIP -include_scope
create_power_domain PD_DSP  -elements {u_dsp}

create_supply_port VDD    -direction in      ;# 1.1 V
create_supply_port VDD_LV -direction in      ;# 0.9 V
create_supply_port VSS    -direction in
create_supply_net  VDD_DSP
create_power_switch psw_dsp \
  -input_supply_port  {vin  VDD_LV} \
  -output_supply_port {vout VDD_DSP} \
  -control_port       {ctrl dsp_pwr_en} \
  -on_state           {on_s vin {ctrl}} \
  -off_state          {off_s {!ctrl}}

create_supply_set SS_AON -function {power VDD}     -function {ground VSS}
create_supply_set SS_RET -function {power VDD_LV}  -function {ground VSS}
create_supply_set SS_DSP -function {power VDD_DSP} -function {ground VSS}
associate_supply_set SS_AON -handle PD_CHIP.primary
associate_supply_set SS_DSP -handle PD_DSP.primary

set_isolation iso_dsp -domain PD_DSP -applies_to outputs \
  -isolation_supply_set SS_AON -clamp_value 1 \
  -isolation_signal dsp_iso_n -isolation_sense low -location parent
set_retention ret_dsp -domain PD_DSP -elements {u_dsp/coeff_reg} \
  -retention_supply_set SS_RET \
  -save_signal {dsp_ret posedge} -restore_signal {dsp_ret negedge}
set_level_shifter ls_dsp -domain PD_DSP -applies_to both -rule both -location self

add_power_state SS_AON -supply \
  -state {ON  -simstate NORMAL \
          -supply_expr {power == {FULL_ON 1.1} && ground == {FULL_ON 0.0}}}
add_power_state SS_RET -supply \
  -state {ON  -simstate NORMAL \
          -supply_expr {power == {FULL_ON 0.9} && ground == {FULL_ON 0.0}}}
add_power_state SS_DSP -supply \
  -state {ON  -simstate NORMAL \
          -supply_expr {power == {FULL_ON 0.9} && ground == {FULL_ON 0.0}}} \
  -state {OFF -supply_expr {power == OFF || ground == OFF} -simstate CORRUPT}
add_power_state PD_DSP -domain \
  -state {ACTIVE -logic_expr {primary == ON}} \
  -state {SLEEP  -logic_expr {primary == OFF && SS_RET == ON}}
```

Common mistakes, and why each one fails:
- **Switching the 1.1 V supply** and declaring `SS_DSP` at 0.9 V: the `ON` state can never be true, because a switch does not change voltage.
- **No `associate_supply_set` for `PD_DSP.primary`:** the domain has no defined primary supply, which shows up as X from time 0.
- **`-isolation_sense high`:** `dsp_iso_n` is active low, so the cells would clamp while the DSP runs and pass X while it is off.
- **`-clamp_value 0`:** the receivers treat 1 as idle, so 0 would look like an active request during sleep.
- **No `-applies_to` or no `-elements`:** the defaults cover more or less than the specification says.
- **`-retention_supply_set SS_DSP`:** the shadow would lose power with the domain.

</details>

### Kata 3: scenarios from a transition table

**Objective:** derive the verification scenarios that a set of power states implies (objective 4).

A GPU domain has three states: `ON` (full voltage), `LOW` (reduced voltage, simstate `CORRUPT_STATE_ON_CHANGE`) and `OFF`. The legal transitions are ON ↔ LOW, ON → OFF and OFF → ON. The domain has no retention. List the scenarios a verification plan needs, with what each one checks.

<details>
<summary>Worked solution (try the kata first)</summary>

| Scenario | Kind | What to check |
|---|---|---|
| ON → LOW → ON | positive | the clock is held (or slowed) so no state changes while in LOW; GPU state is intact back in ON |
| LOW with a clock edge | negative behaviour | any register that changes in LOW is corrupted (`CORRUPT_STATE_ON_CHANGE`): the PMU must stop the clock before LOW |
| ON → OFF → ON | positive | isolation before off; X never reaches the always-on side; everything at reset values after wake; no restore expected |
| LOW → OFF | illegal (not listed) | negative test: the PMU refuses it or goes through ON first; an assertion flags a direct LOW → OFF |
| OFF → LOW | illegal (not listed) | negative test, as above |
| each state reached, each legal arrow taken | coverage | transition coverage on the domain state, with illegal arcs as illegal bins |

The two illegal arcs come from the transitions that are *not* in the list. The simstate `CORRUPT_STATE_ON_CHANGE` adds a scenario of its own: LOW is safe only if no state changes while the voltage is reduced. The coverage and assertions themselves are written in [E-PWR-1](/curriculum/T4_Expert/E-PWR-1_Power_Aware_Verification/index).

</details>

### Visualizer challenge

Go back to the PowerDomainVisualizer and choose **Build your own**.

1. Find a sequence that leaks X into the always-on side but still brings `ctx` back as `A5`. Name the single swap from the safe order that causes it.
2. Find a sequence that loses `ctx` (it never comes back as `A5`) and ends with isolation released. Explain why X then reaches the always-on side in this model, and what the Make It Work PMU, which resets the domain after power-on, would show at the release instead.

<details>
<summary>Answer</summary>

1. Swap "restore" and "release": isolation drops while `ctx` is still X, so X leaks at the release, and the restore one step later brings `A5` back. Swapping "isolate" and "release" also works: isolation is off at power-off, so X leaks at the power-off step and stays on the always-on side through power-on, until the restore; the save happened while powered so the restore brings `A5` back, and the sequence ends isolated. A literal swap of "isolate" and "power off" does *not* work: it also moves the save after power-off (power off, save, isolate, ...), so the shadow saves X and `ctx` is lost. The **Power off before isolation** preset keeps the save first; it moves power-off earlier rather than swapping two steps. These are the only two single swaps that leak X and still restore `A5`.
2. Swap "save" and "power off" (the save copies X), or "restore" and "power on" (the restore has no powered register to write). The model has no reset, so a lost `ctx` stays X, and releasing isolation while powered passes that X to the always-on side. (A sequence that never releases isolation, such as isolate, power off, save, power on, restore, loses `ctx` without leaking: the clamp hides the X, but the always-on side never sees the CPU again.) In the Make It Work PMU the domain reset writes `00` after power-on. If the restore never brings anything back (restore before power-on), `u_top` sees the reset value `00` at the release, a wrong value but not X, as in kata 1. If the save happened after power-off, the restore copies X over the reset value, and X still leaks.

</details>
