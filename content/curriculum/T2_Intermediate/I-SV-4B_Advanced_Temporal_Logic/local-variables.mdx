## Quick Take

- **What it is:** A **local variable** is a variable you declare inside a named `sequence` or `property` (IEEE 1800-2023 §16.10). Every evaluation attempt of the assertion gets its own fresh copy. The attempt stores a value in it when part of the sequence matches, and compares against it later in the same attempt.
- **Why it matters:** Data-integrity checks say "the byte that went in is the byte that comes out". The value is known at one clock tick and checked at a later one, often after a delay that varies, and often while other transfers are still in flight. `$past` needs a fixed delay, and a module-level variable is overwritten by the next transfer. A local variable gives each transfer its own private copy.
- **The Analogy:** A parcel tag. Each parcel that enters the warehouse gets its own tag that records what is inside; at the exit, you compare the parcel with its own tag. A second parcel gets a second tag, so tags never overwrite each other. *Where it breaks:* the tag exists only inside the attempt, so nobody outside can read it, not even the assertion's own failure message. And a tag does not tell you which parcel leaving the warehouse is yours: when several are in flight, you must also number them, which this page calls a **ticket**.

**You will be able to:**
1. Predict, for overlapping attempts, which value each attempt captures in its local variable and on which edge each comparison happens and with what result.
2. Write data-integrity properties with local variables, for fixed and for variable latency, using `[->1] ##0` to check on the handshake tick and a ticket when several transfers are in flight.
3. Apply the rules for declaring, assigning and referencing local variables, and report a captured value with a subroutine call attached to a sequence (§16.11).
4. Debug a failing data check from its log and trace: a shared module-level variable, a `[->1]` that pairs the wrong transfer, `##1` where `##0` was meant, or a bare sequence asserted without an implication.

This page assumes [I-SV-4A: SVA Fundamentals](/curriculum/T2_Intermediate/I-SV-4A_SVA_Fundamentals/index) and the repetition operators from the [module overview](/curriculum/T2_Intermediate/I-SV-4B_Advanced_Temporal_Logic/index).

### Words this page uses

- **Attempt.** A concurrent assertion starts a new evaluation, an **attempt**, at every tick of its leading clock (§16.14.5). Many attempts can be alive at once.
- **Sampled value.** Assertions read every signal as it was just before the clock edge, in the **Preponed** region, the first region of the time slot (§16.5.1). Assignments made at the edge itself are not seen until the next edge. [F3B: Scheduling Regions](/curriculum/T1_Foundational/F3B_Scheduling_Regions/index) shows the regions in order.
- **Antecedent and consequent.** In `a |-> b`, the left side `a` is the antecedent and the right side `b` the consequent. The consequent is checked only when the antecedent matches; when it does not, the attempt is a **vacuous success**, a pass that checked nothing (§16.12.7, §16.14.8).
- **Match, end point.** A sequence matches over a run of ticks; the tick where the match ends is its end point.
- **Handshake, transfer, in flight.** A transfer happens on a **handshake**, the tick where valid (and ready, if the interface has one) are both high. A transfer is **in flight** between its input handshake and its output handshake.

### The problem: a value you need later

Suppose a pipeline returns every input byte unchanged, exactly two clock ticks later. `$past`, from I-SV-4A, can express it:

```systemverilog
// snippet
// Fixed latency: $past looks back a constant number of ticks (§16.9.3).
a_fixed: assert property (@(posedge clk) disable iff (!rst_n)
  in_vld |-> ##2 (out_data == $past(in_data, 2)));
```

This works because the delay is a constant: the tick count of `$past` must be an elaboration-time constant (§16.9.3). Make the latency vary, as it does in a FIFO, a cache or a bus that can stall, and `$past(in_data, N)` has no single N to use. The standard motivates local variables with exactly this case: a pipeline whose latency varies needs a variable that belongs to one transaction check, lives as long as that check, and does not collide with checks of other transactions that overlap it (§16.10).

A local variable is that variable. Here is the same fixed-latency rule written with one:

```systemverilog
// snippet
property p_fixed_latency;
  logic [7:0] v;                                  // 1. declare: one copy per attempt
  @(posedge clk) disable iff (!rst_n)
    (in_vld, v = in_data) |-> ##2 (out_data == v); // 2. assign, 3. compare
endproperty

a_fixed_latency: assert property (p_fixed_latency)
  else $error("output byte differs from the byte that went in 2 ticks earlier");
```

Read it in three steps:

1. **Declare.** `logic [7:0] v;` sits after the `property` header and before the clock. It needs an explicit data type (§16.10).
2. **Assign.** `(in_vld, v = in_data)` is a **match item**: when the expression before the comma matches, the assignments after it run, in order (§16.10). Here that happens on every edge where `in_vld` is sampled high, and `v` takes the sampled value of `in_data` at that edge.
3. **Compare.** Two ticks later, `out_data == v` uses the value this attempt stored. On edges where `in_vld` is low, the antecedent does not match, nothing is stored, and the attempt is a vacuous success.

The standard's own example is the same shape with a pipeline that takes five cycles and adds one: `(valid_in, x = pipe_in) |-> ##5 (pipe_out1 == (x+1))` (§16.10).

### Mistake 1: a module-level variable

The most common first attempt stores the input in an ordinary variable of the module, then compares against it in the assertion:

```systemverilog
// snippet
logic [7:0] last_data;                       // ONE variable for the whole module
always_ff @(posedge clk) if (in_vld) last_data <= in_data;

a_shared: assert property (@(posedge clk) disable iff (!rst_n)
  in_vld |-> ##2 (out_data == last_data));   // compares with whatever is stored now
```

**Why it fails.** `last_data` is one variable, so the input at edge 2 overwrites the value A1 still needs. The check passes for isolated transfers and fails only when transfers overlap, which is exactly when the design is busiest. That is the misconception to drop: *local variables are not shared between attempts; module variables are*. If you ever do need state shared across attempts, such as a running count, that is the job of a module-level variable written by procedural code, as the ticket counters later on this page are.

### Variable latency: wait with `[->1]`, check with `##0`

When the output can come any number of ticks later, wait for the output handshake instead of counting ticks. Two operators from the module overview do this:

- **Goto repetition** `out_vld[->1]` waits through any number of ticks with `out_vld` low and ends exactly on the first tick where `out_vld` is high (§16.9.2).
- **`##0`** joins two sequences so that the second starts on the same tick where the first ends (§16.7). `##1` starts it one tick later.

```systemverilog
// snippet
property p_var_latency;
  logic [7:0] v;
  @(posedge clk) disable iff (!rst_n)
    (in_vld, v = in_data) |=> out_vld[->1] ##0 (out_data == v);
endproperty
```

Read it as: "when a byte enters, from the next tick wait for the first `out_vld`, and on that same tick `out_data` must equal the stored byte." **Predict:** in the trace below, on which edge does each version compare `out_data`?

**Mistake 2: `##1` where `##0` was meant.** `##0` does not wait a cycle in a singly clocked sequence: it starts the second sequence on the same clock tick where the first one ends (§16.7). Writing `##1` after `[->1]` checks the data one tick after the handshake, which fails on a correct design whose output moves on at once. Crossing clocks changes this rule, see [Multiclock Assertions](/curriculum/T2_Intermediate/I-SV-4B_Advanced_Temporal_Logic/multi-clocking).

**A related slip: `[=1]` instead of `[->1]`.** Nonconsecutive repetition `out_vld[=1]` is `out_vld[->1] ##1 !out_vld[*0:$]` (Annex F.3.4.2.3): it can end on the handshake tick *or on any later tick before the next `out_vld`*. With `[=1] ##0`, a wrong value on the handshake tick passes if the right value shows up on one of those later ticks. The two operators are not interchangeable here; use `[->1]`.

### Mistake 3: asserting a bare sequence

```systemverilog
// snippet
property p_bare;                  // WRONG: no implication
  logic [7:0] v;
  @(posedge clk) (in_vld, v = in_data) ##2 (out_data == v);
endproperty
a_bare: assert property (p_bare);
```

An attempt starts on every edge, and in `assert property` a sequence used as the whole property must match from that attempt's start (§16.12.2). On an edge where `in_vld` is low, the very first tick already shows that the sequence cannot match, so the attempt **fails**. It is not a vacuous success: vacuity comes only from an implication whose antecedent does not match. A bare sequence therefore fails on every idle edge. Put the trigger in an antecedent: `(in_vld, v = in_data) |-> ##2 (out_data == v)`.

### Transfers in flight: the pairing bug and the ticket

`p_var_latency` is right when only one transfer can be in flight. Now let the design accept new data while older data is still inside, as any FIFO or pipeline does. The trace below comes from the Make It Work bench: an in-order FIFO whose output side has a ready signal, `out_rdy`, so a transfer leaves on a tick where `out_vld && out_rdy`. Four bytes, T0 to T3, enter at edges 2, 3, 5 and 6 and leave, in order, at edges 4, 7, 8 and 9. The FIFO has a planted bug: it stores T2 (C3) as C2.

First, the obvious property:

```systemverilog
// snippet
// WRONG with several transfers in flight: pairs each input with the NEXT output.
(in_vld, exp_data = in_data) |=> (out_vld && out_rdy)[->1] ##0 (out_data == exp_data);
```

**What went wrong.** Each attempt is private, so this is not Mistake 1. The problem is *which* handshake each attempt waits for. T1's goto starts at edge 4 and ends at the first output handshake it sees, which belongs to T0, the older transfer still in flight. The property is wrong even on a perfect design: remove the planted bug and the same three attempts still fail.

**The fix: a ticket.** Count the transfers on each side with two counters in the bench. When a byte enters, capture the input count as its ticket; the byte's output is the handshake where the output count equals that ticket.

```systemverilog
// snippet
logic [7:0] in_cnt, out_cnt;          // modelling code, not part of the DUT
always_ff @(posedge clk or negedge rst_n)
  if (!rst_n) begin
    in_cnt  <= '0;
    out_cnt <= '0;
  end else begin
    if (in_vld)             in_cnt  <= in_cnt  + 1'b1;   // transfers accepted
    if (out_vld && out_rdy) out_cnt <= out_cnt + 1'b1;   // transfers delivered
  end

property p_in_order_data;
  logic [7:0] tkt;                    // this transfer's place in the stream
  logic [7:0] exp_data;               // the byte it must come out with
  @(posedge clk) disable iff (!rst_n)
    (in_vld, tkt = in_cnt, exp_data = in_data)
      |=> (out_vld && out_rdy && out_cnt == tkt)[->1] ##0 (out_data == exp_data);
endproperty
```

The sampled `in_cnt` at a transfer's input edge is the number of transfers accepted before it, and the sampled `out_cnt` at an output handshake is the number delivered before it. In an in-order design, transfer k enters when `in_cnt` is k and leaves when `out_cnt` is k. A local variable can appear inside the Boolean of a goto repetition, as `tkt` does here, like any other variable in an expression (§16.10). The 8-bit counters wrap, which is safe while fewer than 256 transfers are in flight.

A reset then clears the counters and disables every attempt in flight together. ### Seeing the captured value: subroutine calls on match

A failing data check is far easier to debug when the log shows what the attempt stored. The action block cannot show it: a local variable is not visible in the context that instantiates its sequence or property (§16.10), and the assertion statement is that context. Hierarchical names such as `p_in_order_data.exp_data` are illegal too (§16.10).

Instead, attach a call to a subsequence, in the same comma list as the assignments (§16.11):

```systemverilog
// snippet
(in_vld, tkt = in_cnt, exp_data = in_data)
  |=> ((out_vld && out_rdy && out_cnt == tkt)[->1], show_pair(tkt, exp_data, out_data))
      ##0 (out_data == exp_data);
```

The rules, each from §16.11:

- **What you may call:** tasks, void functions, their class-method forms, and system tasks such as `$display`.
- **When it runs:** at every end point of the subsequence it is attached to, so here once per pairing, on a pass or a fail alike. Calls in one list run in list order.
- **Where it runs:** scheduled in the **Reactive** region, like an action block. The Reactive region comes after the Observed region, where assertions are evaluated (§4.4.2.5, §4.4.2.6, §16.14.1; regions in [F3B](/curriculum/T1_Foundational/F3B_Scheduling_Regions/index)). The assertion never waits for the call and receives nothing back.
- **Which values it sees:** arguments are passed by value (or by `ref`/`const ref`). By-value arguments use sampled values, the same ones the match used, so `out_data` prints as the assertion saw it. A local variable that has been assigned by that point may be an argument, and must then be passed by value.
- **Where it is illegal:** on a subsequence that can match empty, the same rule as for assignments.

### Rules and restrictions

| Rule | Legal | Illegal | Why | Source |
|---|---|---|---|---|
| Declare inside a named `sequence` or `property`, with an explicit type | `property p; logic [7:0] v; …` | a declaration inside an inline `assert property (…)` | The inline form has no place for declarations; name the property first | §16.10, §16.12 |
| Assign before you reference | `(a, v = d) ##1 (b == v)` | `a ##1 (b == v)` with `v` never assigned | A local variable has no default value; it starts unassigned | §16.10 |
| Attach assignments and calls only to a subsequence that cannot match empty | `(a ##1 b[*0:1], x = e)` | `a ##1 (b[*0:1], x = e)` | An empty match has no tick at which to perform the assignment | §16.10, §16.11 |
| Goto and nonconsecutive repetition take only a Boolean | `(b[->1], v = d)` | `(b, v = d)[->1]` | `[->]` and `[=]` apply to an expression; a parenthesised sequence with match items allows only `[*]` | §16.9.2 (Syntax 16-6) |
| Match items may change only local variables | `(a, n++)` with `n` a local variable already assigned | `(a, cnt++)` with `cnt` a module variable | Assertion expressions must have no side effects on design or bench state | §16.6 |
| Not in a disable condition | `disable iff (!rst_n)` | `disable iff (v == 0)` | The disable condition is evaluated with current values and applies to all attempts at once, so there is no single attempt's copy to read | §16.12 |
| Not in a sampled-value function or a clocking event | `$stable(out_data)` | `$past(v)`, `@(posedge v)` | A sampled-value function samples its argument at earlier clock ticks, and a clocking event decides when attempts run; a local variable exists only inside one attempt | §16.9.3, §16.10 |
| Not visible outside the property | a §16.11 call that prints `v` | `v` in the action block; `p.v` from elsewhere | The variable exists only inside the attempt | §16.10 |

Two more facts complete the picture. The **sampled value of a local variable is its current value** (§16.5.1): a comparison sees the value the attempt itself assigned, not a Preponed copy. And a declaration may carry an initializer, `logic [7:0] v = in_data;`; it runs when the attempt begins, in the Observed region, with the sampled values of that time slot (§16.10).

### More ways to assign: several assignments and accumulation

A match-item list may hold several assignments, performed left to right, and a later one may use an earlier one: `(b[->1], x = e, y = x && f)` (§16.10). Assignments may use `+=`, `++` and the other C operators on local variables (§16.6), and repeating a parenthesised match item accumulates. This property checks that a reported `total` equals the sum of the four data beats that follow a `start`:

```systemverilog
// snippet
property p_burst_sum;
  logic [15:0] sum;
  @(posedge clk) disable iff (!rst_n)
    (start, sum = 0) ##1 (beat[->1], sum += data)[*4] |=> (total == sum);
endproperty
```

Each iteration of `[*4]` waits for the next `beat` and adds that tick's `data`, the pattern of the standard's `(a[->1], x += data)[*4]` (§16.10). A traced attempt, with `start` at edge 1:

| Edge | `start` | `beat` | `data` | What happens | `sum` after |
|---|---|---|---|---|---|
| 1 | 1 | 0 | – | `(start, sum = 0)` matches; the attempt continues | 0x0000 |
| 2 | 0 | 1 | 0x10 | first `beat[->1]` ends; `sum += 0x10` | 0x0010 |
| 3 | 0 | 1 | 0x20 | second | 0x0030 |
| 4 | 0 | 0 | – | waiting; nothing assigned | 0x0030 |
| 5 | 0 | 1 | 0x30 | third | 0x0060 |
| 6 | 0 | 1 | 0x40 | fourth: the antecedent matches | 0x00A0 |
| 7 | – | – | – | `\|=>`: `total` must be 0x00A0 | 0x00A0 |

### Debugging data checks

| Symptom | Likely cause | Fix |
|---|---|---|
| Fails on every edge where nothing happens | A bare sequence asserted (Mistake 3) | Put the trigger in an antecedent: `\|->` or `\|=>` |
| Fails only when transfers overlap, and the expected value belongs to a newer transfer | A module-level variable shared by all attempts (Mistake 1) | Declare the value as a local variable |
| Fails only when transfers overlap, and the actual value belongs to an older transfer | `[->1]` paired the wrong output | Add a ticket, or a per-ID ticket for out-of-order designs |
| Fails one tick after a correct handshake | `##1` after `[->1]` (Mistake 2) | Use `##0` |
| Passes although the data was wrong on the handshake tick | `[=1]` instead of `[->1]`, or the comparison is outside the waited-for tick | Use `[->1] ##0 (check)` |
| Compile error about a local variable | Referenced before assignment, used in `disable iff`, `$past` or the action block, or attached to an empty-matching subsequence | Apply the rules table above; the exact message is tool-dependent |
| Failures start right after a mid-test reset | Ticket counters reset by a different signal than the `disable iff` | Reset counters and assertion together |
| No failure for a transfer that never came out | `[->1]` waits forever and the attempt is still open when simulation ends, which is not a failure for `assert property` (§16.12.2) | Bound the wait (the Kata shows how); the module overview explains weak and strong |

Error messages differ between simulators. Read them for the assertion name and the time, then reproduce the attempt by hand on the waveform as this page does.

### Local variables in real testbenches

- **Where the check lives.** Data-integrity assertions sit in the interface of the agent that watches the bus, or in a checker attached with `bind` without editing the RTL ([I-SV-4C](/curriculum/T2_Intermediate/I-SV-4C_Checkers/index)). The ticket counters go next to them, never in the design.
- **When to use one.** In-order data paths where a short rule describes the expected output: FIFOs, pipelines, bridges that pass data through, request/response pairs. One property covers every overlap pattern the stimulus produces.
- **When not to.** Out-of-order completion with many IDs, transformations that need a real reference model, or checks that must compare whole transactions: use a scoreboard ([A-UVM-6](/curriculum/T3_Advanced/A-UVM-6_Scoreboards_and_Reference_Models/index)). Many benches use both: the assertion catches the cycle where data went wrong, and the scoreboard checks the end-to-end result.
- **In a UVM bench.** The assertion still reports with `$error`; routing interface assertion failures into the UVM report is covered in [A-UVM-7](/curriculum/T3_Advanced/A-UVM-7_VIP_Construction/index).

## Make It Work

### An in-order FIFO with variable latency

The bench below is the trace from the pairing pictures. `pipe_fifo` is an in-order FIFO; the bench decides when to take data, so the latency varies from 2 to 4 ticks. Its parameter `CORRUPT` plants a bug: the write with that index (counting from 0) is stored with bit 0 flipped. The assertion checks every byte with a ticket and prints each pairing through an attached call.

```systemverilog
// compile
// In-order FIFO, 8 deep. No full flag: this bench never has more than 4 words inside.
module pipe_fifo #(parameter int CORRUPT = -1) (  // write index to damage; -1: none
  input  logic       clk, rst_n,
  input  logic       in_vld,
  input  logic [7:0] in_data,
  output logic       out_vld,
  input  logic       out_rdy,
  output logic [7:0] out_data
);
  timeunit 1ns; timeprecision 1ns;

  logic [7:0] mem [8];
  logic [2:0] wr_ptr, rd_ptr;
  logic [3:0] count;
  int         n_wr;                       // writes so far; used only by the planted bug

  assign out_vld  = (count != 0);
  assign out_data = mem[rd_ptr];

  always_ff @(posedge clk or negedge rst_n)
    if (!rst_n) begin
      wr_ptr <= '0;
      rd_ptr <= '0;
      count  <= '0;
      n_wr   <= 0;
    end else begin
      if (in_vld) begin
        // planted bug: one write is stored with bit 0 flipped
        mem[wr_ptr] <= (n_wr == CORRUPT) ? (in_data ^ 8'h01) : in_data;
        wr_ptr      <= wr_ptr + 1'b1;
        n_wr        <= n_wr + 1;
      end
      if (out_vld && out_rdy) rd_ptr <= rd_ptr + 1'b1;
      case ({in_vld, out_vld && out_rdy})
        2'b10:   count <= count + 1'b1;
        2'b01:   count <= count - 1'b1;
        default: ;                        // none, or one in and one out
      endcase
    end
endmodule

module tb_top;
  timeunit 1ns; timeprecision 1ns;

  logic       clk = 1'b0, rst_n = 1'b0;
  logic       in_vld = 1'b0, out_rdy = 1'b0, out_vld;
  logic [7:0] in_data = '0, out_data;
  int         n_pairs, n_fail;

  always #5 clk = ~clk;                   // rising edge n at 10n + 5 ns

  pipe_fifo #(.CORRUPT(2)) dut (.*);      // damage the third write (C3 is stored as C2)

  clocking cb @(posedge clk);             // the bench drives only through cb
    output rst_n, in_vld, in_data, out_rdy;
  endclocking

  // Ticket counters: modelling code next to the assertion, reset like its disable iff
  logic [7:0] in_cnt, out_cnt;
  always_ff @(posedge clk or negedge rst_n)
    if (!rst_n) begin
      in_cnt  <= '0;
      out_cnt <= '0;
    end else begin
      if (in_vld)             in_cnt  <= in_cnt  + 1'b1;
      if (out_vld && out_rdy) out_cnt <= out_cnt + 1'b1;
    end

  // Called by the assertion at each pairing (§16.11): runs in the Reactive region,
  // and its by-value arguments carry this attempt's values.
  function automatic void show_pair(logic [7:0] tkt, logic [7:0] exp_data,
                                    logic [7:0] got);
    n_pairs++;
    $display("[%0t] pair ticket %0d: expected %h, got %h", $time, tkt, exp_data, got);
  endfunction

  property p_in_order_data;
    logic [7:0] tkt;                      // this transfer's place in the stream
    logic [7:0] exp_data;                 // the byte it must come out with
    @(posedge clk) disable iff (!rst_n)
      (in_vld, tkt = in_cnt, exp_data = in_data)
        |=> ((out_vld && out_rdy && out_cnt == tkt)[->1],
             show_pair(tkt, exp_data, out_data))
            ##0 (out_data == exp_data);
  endproperty

  a_in_order_data: assert property (p_in_order_data)
    else begin
      n_fail++;
      $error("[%0t] a_in_order_data: data changed in flight", $time);
    end

  // Proves the interesting case happened: a byte entered while another was inside
  c_accept_while_busy: cover property (@(posedge clk) disable iff (!rst_n)
    in_vld && (in_cnt != out_cnt));

  initial begin
    repeat (2) @(cb);                     // reset is sampled low at edges 0 and 1
    cb.rst_n   <= 1'b1;                   // each drive is sampled at the next edge
    cb.in_vld  <= 1'b1;
    cb.in_data <= 8'hA1;                  // T0 enters at edge 2
    @(cb);
    cb.in_data <= 8'hB2;                  // T1 enters at edge 3, while T0 is inside
    @(cb);
    cb.in_vld  <= 1'b0;
    cb.out_rdy <= 1'b1;                   // edge 4: take T0 (latency 2)
    @(cb);
    cb.in_vld  <= 1'b1;
    cb.in_data <= 8'hC3;                  // T2 enters at edge 5
    cb.out_rdy <= 1'b0;                   // stall the output: T1 waits
    @(cb);
    cb.in_data <= 8'hD4;                  // T3 enters at edge 6
    @(cb);
    cb.in_vld  <= 1'b0;
    cb.out_rdy <= 1'b1;                   // edges 7, 8, 9: take T1, T2, T3
    repeat (3) @(cb);
    cb.out_rdy <= 1'b0;
    repeat (2) @(cb);                     // edge 11 (115 ns): every attempt is done
    $display("[%0t] PASS=%0d FAIL=%0d", $time, n_pairs - n_fail, n_fail);
    $finish;
  end
endmodule
```

Both modules use a 1 ns time unit and precision, so `%0t` prints whole nanoseconds. Support for local variables in open-source simulators varies and was not verified for this page; no simulator was run, and the log below was traced by hand from the rules on this page.

### Break it on purpose

1. **Remove the ticket.** In the consequent, replace `(out_vld && out_rdy && out_cnt == tkt)` with `(out_vld && out_rdy)` and rerun. **Predict** before you run: the attempts now pair with the next handshake, as in the pairing-bug picture.

   ```text
   [45] pair ticket 0: expected a1, got a1
   [45] pair ticket 1: expected b2, got a1
   Error: [45] a_in_order_data: data changed in flight
   [75] pair ticket 2: expected c3, got b2
   [75] pair ticket 3: expected d4, got b2
   Error: [75] a_in_order_data: data changed in flight
   Error: [75] a_in_order_data: data changed in flight
   [115] PASS=1 FAIL=3
   ```

   (Illustrative; lines with the same time may appear in a different order.) Three failures, and the log blames the wrong transfers. Now also set `.CORRUPT(-1)`: the same three failures remain, which proves the property, not the FIFO, is wrong.

2. **Fix the FIFO instead.** Restore the ticket and set `.CORRUPT(-1)`. All four pairings pass and the last line becomes `[115] PASS=4 FAIL=0`.

3. **Swap `##0` for `##1`.** Restore everything, then change `##0 (out_data == exp_data)` to `##1 (out_data == exp_data)`. **Predict** which pairings fail. (T0 is compared at edge 5, where `out_data` already shows B2, so it fails; work out the other three yourself, then check against the trace table.)

### How to write a data-integrity property

1. **Write the rule in one English sentence**, naming the input event, the output event and the data relation: "every byte accepted on the input leaves the output unchanged, in order".
2. **Pick the capture point** and make it the antecedent, with the assignments in a match item: `(in_vld, exp_data = in_data)`.
3. **Pick the waiting operator.** Fixed latency: `##N`. Variable latency, one transfer at a time: `out_hs[->1]`. Several in flight, in order: add a ticket counter and wait for `(out_hs && out_cnt == tkt)[->1]`.
4. **Compare on the handshake tick with `##0`**, and write the relation exactly as the design's specification states it (unchanged, plus one, a CRC).
5. **Report what was captured** with an attached call when a failure needs context; keep the failure message true for every way the property can fail.
6. **Cover the interesting case** (overlap, back-to-back, maximum depth), so a pass means the check really ran.
7. **Bound the wait** if a missing output must fail during the run (the Kata below shows how).

**Checklist before moving on:**

- [ ] I can say, for two overlapping attempts, which value each one stores and on which edge each compares.
- [ ] My local variables are declared in a named property with explicit types, and assigned in a match item before they are used.
- [ ] My consequent compares with `##0` on the tick where the goto repetition ends.
- [ ] With more than one transfer in flight, each attempt waits for its own transfer by ticket (or ID).
- [ ] My trigger is in an antecedent, never a bare sequence.
- [ ] No local variable appears in `disable iff`, `$past`/`$stable`, a clocking event or an action block; I print captured values with a §16.11 call.
- [ ] I ran the bench, matched the log line by line to the trace table, and broke it on purpose at least once.

## Push Further

### Expert: One attempt can fork into several threads

An antecedent with a range can match more than once from one start. For each match, the consequent is evaluated separately (§16.12.7), and the evaluation behaves as if it forked one thread per match, each carrying the local-variable values assigned on its own path (§16.10; a range such as `##[1:3]` is defined as an `or` of its alternatives, §16.7). In

```systemverilog
// snippet
(req ##[1:3] (gnt, id = gnt_id)) |=> (rsp && rsp_id == id)
```

a `gnt` on two of the three ticks gives two threads with two `id` values, and *both* consequents must pass. If only the first grant counts, keep one thread with `first_match`, which accepts match items inside its parentheses: `first_match(req ##[1:3] (gnt, id = gnt_id))` (§16.9.8). Interview angle: "Why did one request produce two failure messages?"

### Expert: Flow rules for `or`, `and` and `intersect`

A local variable keeps its value through a plain chain of `##` and repetitions. Through `or`, `and` and `intersect` it may not, because the two operands are evaluated like parallel threads (§16.10; the precise conditions are in Annex F.5.4):

- **Sibling threads cannot see each other's assignments.** `(a ##1 (b, x = data) ##1 c) or (d ##1 (e == x))` is illegal: the right operand reads an `x` that only the left one assigns.
- **After `or`**, a variable is usable only if every operand leaves it assigned. Each matching operand continues as its own thread with its own value.
- **After `and` and `intersect`**, a variable assigned in only one operand flows out; one assigned in both is blocked, and becomes unassigned, because the two threads merge into one and cannot agree on a value.

A variable that does not flow out becomes unassigned, and referencing it before it is assigned again is illegal (§16.10).

### Expert: Local variable formal arguments

A named sequence can return a captured value to its caller through a **local variable formal argument**, declared with `local` and a direction: `sequence s_cap(local output logic [7:0] lv); …` (§16.8.2). Directions `input`, `inout` and `output` are allowed for sequences; a named property's local formal arguments must be `input` (§16.12.19). This lets an assertion library offer reusable "capture" sequences. Another way is an untyped formal argument bound to a whole local variable of the caller, which the sequence assigns (§16.10).

### Expert: Two leading clocks give two copies

In a multiclock property, a declaration initializer runs at the first tick of the property's leading clock at or after the attempt begins. If one named property has two distinct leading clocks, for example an `and` of two subproperties clocked by `clk1` and `clk2`, the standard creates a separate copy of the local variable per leading clock, each initialized at its own clock's tick (§16.13.7). The two copies can hold different values, so do not expect them to agree. Clock crossing itself is taught in [Multiclock Assertions](/curriculum/T2_Intermediate/I-SV-4B_Advanced_Temporal_Logic/multi-clocking).

### Expert: Measure latency in time, inside the assertion

To bound latency in nanoseconds rather than ticks, capture the time in a local variable: `(count == 0, l_t = $realtime) ##1 (count == 7)[->1] |-> $realtime - l_t < 50.5` (§16.6). The standard warns against the alternative, capturing time in procedural code and comparing it in the assertion: the procedure sees current values and the assertion sees sampled ones, so the two readings belong to different ticks and the measured interval is off by a clock period.

### Expert: Per-ID tickets, cost, and the scoreboard boundary

- **Out-of-order by ID.** Protocols such as AXI keep order only among transfers with the same ID ([B-AXI-3](/curriculum/T3_Advanced/B-AXI-3_AXI_Ordering_and_IDs/index)). Keep one counter per ID and capture the ID too: `(in_vld, id = in_id, tkt = in_cnt[in_id], d = in_data) |=> (out_vld && out_id == id && out_cnt[id] == tkt)[->1] ##0 (out_data == d)`. A local variable may index an array like any other variable (§16.10).
- **Cost (tool-dependent).** Every open attempt keeps its own copies alive until it finishes, so a property with an unbounded wait on a busy interface can hold thousands of attempts. The standard also notes that an attempt indexing a large dynamic structure with a local variable may force the tool to sample the whole structure (§16.6). Measure with your simulator's assertion profiling before you scale a check up.
- **The boundary.** When the expected output needs a model (reordering, transformation, dropped or merged transfers), write a scoreboard ([A-UVM-6](/curriculum/T3_Advanced/A-UVM-6_Scoreboards_and_Reference_Models/index)). Formal tools accept local variables too; how much each one costs the proof is tool-dependent ([E-INT-1](/curriculum/T4_Expert/E-INT-1_Integrating_UVM_with_Formal_Verification/index)).

### Kata: four transfers in flight, with a bounded wait

**Objective:** write a ticket check whose wait is bounded, so a missing or wrong response fails during the run.

**Interface** (one clock `clk`, active-low reset `rst_n`): requests `req_vld`, `req_rdy`, `req_data[7:0]`; responses `rsp_vld`, `rsp_data[7:0]`, with no ready on the response side. **Rule:** responses come back in order, each 1 to 8 ticks after its request handshake, carrying `req_data + 1`. Up to 4 requests may be outstanding.

**Trace for task 3:** request handshakes at edges 1 (`req_data` 10), 2 (20) and 3 (30); `rsp_vld` high at edges 4 (`rsp_data` 11), 6 (21) and 9 (30), low elsewhere.

**Tasks:**
1. Write the ticket counters `req_cnt` and `rsp_cnt`, and a property that captures a ticket and the expected byte at each request handshake.
2. Make the wait bounded: the response must arrive within 8 ticks, and a wrong byte must fail on the tick it arrives.
3. Predict, on the trace above, which request fails and on which edge.
4. Add a `cover property` that proves the bench reached 4 outstanding requests.
5. A teammate writes the consequent as `|-> ##[1:8] (rsp_vld && rsp_cnt == tkt && rsp_data == exp_data + 8'd1)`. Does it catch the same bug, and on which edge?

<details>
<summary>Reveal the worked solution</summary>

**1 and 2.** Count handshakes on each side, and replace the unbounded `[->1]` with "no response of mine for 0 to 7 ticks, then my response, correct":

```systemverilog
// snippet
logic [7:0] req_cnt, rsp_cnt;
always_ff @(posedge clk or negedge rst_n)
  if (!rst_n) begin
    req_cnt <= '0;
    rsp_cnt <= '0;
  end else begin
    if (req_vld && req_rdy) req_cnt <= req_cnt + 1'b1;
    if (rsp_vld)            rsp_cnt <= rsp_cnt + 1'b1;
  end

property p_rsp_data;
  logic [7:0] tkt, exp_data;
  @(posedge clk) disable iff (!rst_n)
    (req_vld && req_rdy, tkt = req_cnt, exp_data = req_data)
      |=> (!(rsp_vld && rsp_cnt == tkt))[*0:7]
          ##1 (rsp_vld && rsp_cnt == tkt && rsp_data == exp_data + 8'd1);
endproperty
a_rsp_data: assert property (p_rsp_data)
  else $error("response missing within 8 ticks, or wrong data");
```

`|=>` starts the consequent one tick after the request, and `[*0:7] ##1` places the response 1 to 8 ticks after it. The repetition cannot step over a tick where this ticket's response is present, so the attempt ends on its own response: a wrong byte fails there, and a missing response fails 8 ticks after the request. `exp_data + 8'd1` is computed in 8 bits in this comparison, so FF + 1 wraps to 00 like the design. The failure message names both causes, because the property fails for either.

**3.** Tickets: edge 1 gets 0, edge 2 gets 1, edge 3 gets 2. `rsp_cnt` is 0 at edge 4, 1 at edge 6 and 2 at edge 9. Requests 0 and 1 pass at edges 4 (11 = 10 + 1) and 6 (21 = 20 + 1). Request 2's response arrives at edge 9, six ticks after its request, carrying 30 instead of 31: **it fails at edge 9**.

**4.**

```systemverilog
// snippet
c_four_outstanding: cover property (@(posedge clk) disable iff (!rst_n)
  (req_cnt - rsp_cnt) == 8'd4);
```

The subtraction is done in 8 bits here, so it stays correct when the counters wrap.

**5.** It catches the bug, but later. With tickets there is exactly one tick with `rsp_vld && rsp_cnt == tkt`, so a wrong byte means no tick in the window can match, and the attempt fails only when the window closes: edges 4 to 11 for the request at edge 3, so **at edge 11**, two ticks after the bad response. The `[*0:7] ##1` form points at the guilty tick, which is why it is preferred for debug.
