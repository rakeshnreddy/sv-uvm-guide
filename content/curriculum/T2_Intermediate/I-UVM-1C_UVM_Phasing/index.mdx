## Quick Take
- **What it is:** UVM phasing defines the sequence of build, run, and cleanup steps each component follows. Objections, events, and barriers control when phases end or when threads sync.
- **Why it matters:** Consistent phasing keeps agents, scoreboards, and tests synchronized—no component starts driving before everything is connected.
- **The Analogy:** Think of phases as a rehearsal schedule: setup, sound check, showtime, encore. Objections are the stage manager holding the curtain until performers finish.

> **Retention Hook:** Say “build → connect → run → report” and picture objections as the brake pedal on `run_phase`.

## Build Your Mental Model
### Three Buckets of Phases
Phases fall into predictable groups (Clause 9 of the IEEE 1800.2-2020 LRM):
- **Build-time (functions, zero time):** `build` runs top-down, because a parent's `build_phase` creates its children. `connect`, `end_of_elaboration` and `start_of_simulation` run bottom-up: every child finishes before its parent.
- **Run-time (tasks):** `run_phase` starts in every component at once. Beside it, the `uvm` schedule steps through 12 runtime phases (`pre_reset` … `post_shutdown`), and all components move through them together.
- **Cleanup (functions, zero time):** `extract`, `check` and `report` run bottom-up; `final` runs top-down, like `build`.

"Top-down" and "bottom-up" are depth-first walks of the tree, not level-by-level sweeps. Click any phase in the map for its rule and a minimal example. Then predict the call order for a function phase and step through it, or switch to the second experiment to see how `run_phase` and the runtime phases share time.

### Objection Flow
A task phase ends when every objection raised in it has dropped, after any drain time. If nothing has raised an objection by the end of the phase's first time step, UVM ends the phase at once and kills its threads. The test owns the objection around its stimulus:

<InteractiveCode>
```systemverilog
class my_test extends uvm_test;
  `uvm_component_utils(my_test)
  my_env env;

  function new(string name, uvm_component parent);
    super.new(name, parent);
  endfunction

  function void build_phase(uvm_phase phase);
    super.build_phase(phase);
    env = my_env::type_id::create("env", this);
  endfunction

  task run_phase(uvm_phase phase);
    my_seq seq = my_seq::type_id::create("seq");
    phase.raise_objection(this, "stimulus running");
    seq.start(env.agt.sqr);
    phase.drop_objection(this, "stimulus done");
  endtask
endclass
```
</InteractiveCode>

**Why the driver does not object:** a driver loops `forever` (`get_next_item`, drive, `item_done`) and never knows when the test is finished, so it would never drop. The test decides when stimulus is done. When `run_phase` ends, UVM kills the driver's loop for you.

**Drain time is not a hang safety net.** It only delays the end of a phase *after* the count reaches zero, so transactions still in flight can reach the scoreboard. Set it on the phase's objection, `phase.get_objection().set_drain_time(this, 50ns);` (there is no static `set_drain_time`). A raise during the drain cancels it. For a forgotten drop, the safety net is the global timeout: `uvm_root::get().set_timeout(2ms);` or `+UVM_TIMEOUT=<value>,<YES|NO>` on the command line. When it expires before `run_phase` can end, UVM issues `UVM_FATAL [PH_TIMEOUT]` and no `check_phase` or `report_phase` runs. The default is 9200 s, so set a realistic value.

**phase_ready_to_end:** once every objection has dropped (and the drain has passed), UVM calls `phase_ready_to_end(phase)` on every component. A component with unfinished work, such as a scoreboard still waiting for responses, can raise an objection there and drop it later. UVM then asks again, at most 20 times by default.

## Advanced Mechanics

### 🔥 Critical: `run_phase` Concurrency with Runtime Sub-Phases

> **Senior/Staff Interview Trap:** `run_phase` and the runtime sub-phases (`pre_reset_phase`, `reset_phase`, `configure_phase`, `main_phase`, `shutdown_phase`, etc.) execute **concurrently in parallel domains**, not sequentially.

This is the most commonly misunderstood aspect of UVM phasing. Here is what actually happens at runtime (IEEE 1800.2-2020 §9.4 and §9.8; in uvm-core, `uvm_domain::get_common_domain()` adds the `uvm` domain `.with_phase(run)`):

1. **`run_phase`** executes in the **common domain** — it is a single task-based phase shared by all components.
2. **Runtime sub-phases** (`pre_reset_phase` through `post_shutdown_phase`) execute in the **`uvm` domain** — they proceed sequentially within their domain, but the entire domain runs **in parallel** with `run_phase`.
3. **Both must complete** (all objections dropped in both domains) before cleanup phases (`extract_phase`, `check_phase`, `report_phase`) begin. `run_phase` itself cannot end before the schedule has finished, even when nothing objects in it.

<InteractiveCode>
```systemverilog
// COMMON FAILURE: Raising objection only in run_phase
// does NOT keep main_phase alive — they are independent!
class my_test extends uvm_test;
  `uvm_component_utils(my_test)
  my_env env;
  // new() and build_phase() as in the test above

  // This objection keeps run_phase alive...
  task run_phase(uvm_phase phase);
    phase.raise_objection(this, "run_phase work");
    #1us;
    phase.drop_objection(this);
  endtask

  // ...but main_phase has its OWN objection count.
  // Without the raise below, main_phase ends at once and kills seq.
  task main_phase(uvm_phase phase);
    my_seq seq = my_seq::type_id::create("seq");
    phase.raise_objection(this, "main_phase work");
    seq.start(env.agt.sqr);
    phase.drop_objection(this);
  endtask
endclass
```
</InteractiveCode>

**Common failure modes:**
- **Hanging simulation:** `run_phase` raises an objection but never drops it. Even if all sub-phases complete, `run_phase` never finishes; only the global timeout ends the run, with `UVM_FATAL [PH_TIMEOUT]` (after 9200 s if you never set one).
- **Premature end:** A sub-phase ends immediately because no component raised an objection in that specific sub-phase, even though `run_phase` is still active. Stimulus that was intended to run during `main_phase` never executes.
- **Phase confusion:** An engineer implements logic in both `run_phase` and `main_phase` expecting them to execute sequentially — instead, they race.

**Best practice:** Choose one approach consistently across your environment:
- **Option A (recommended for most teams):** Use only `run_phase` for all runtime work. Ignore the sub-phases entirely.
- **Option B (structured environments):** Use only the runtime sub-phases (`reset_phase`, `configure_phase`, `main_phase`, `shutdown_phase`). Leave `run_phase` empty (do NOT raise objections in it).
- **Never mix both** unless you fully understand the parallel domain semantics.

### Domains and Phase Jumping
Phases execute in a **domain**. The *common* domain holds `build` through `final`, including `run_phase`. The 12 runtime phases belong to the **`uvm`** domain, whose schedule runs beside `run_phase`. Every component starts in the `uvm` domain, so all of them step through the runtime phases together. With `set_domain()` you can move a subset of components (say, a second clock domain's agents) into their own domain, whose runtime phases are then not synchronized with the rest unless you call `sync()`.

A runtime phase can **jump** with `phase.jump(<target>::get())`. The usual reason is a mid-test reset: from `main_phase`, jump back to `reset_phase` so the whole schedule replays reset, configure and main. Jump to a phase in the same schedule; jumping from `run_phase` into the runtime schedule is not the intended use. Jumps are advanced and are not modelled in the visuals on this page.

### uvm_event and uvm_barrier (Clause 10)
Beyond phase objections, you often need cross-component signaling:
- **`uvm_event`**: A simple trigger/wait synchronization. One process calls `trigger()` and another waits with `wait_trigger()`.
- **`uvm_barrier`**: Blocks progress until a specified number of processes reach it via `wait_for()`. The barrier then "opens" and all waiting processes continue simultaneously.

## Interview Pitfalls
**The `build_phase` vs `connect_phase` Mix-Up:**
If you try to call `<port>.connect(<export>)` inside the `build_phase`, you will face null pointer exceptions. `build_phase` builds from the top-down, meaning peer components might not exist yet when you try to connect them. Always wait for `connect_phase` (which resolves bottom-up) to wire ports.

**The Test That Ends at 0 ns:**
"My test passes, but nothing was driven." Nobody raised an objection in `run_phase` (or in the runtime phase that starts the stimulus) during its first time step. Raising after a delay is too late: the phase has already ended and killed the thread. Run with `+UVM_OBJECTION_TRACE` and `+UVM_PHASE_TRACE` to see it.

**The Hanging Simulation:**
"My test says time 0 and never finishes."
1. Did you raise an objection but never drop it? Then the run ends only at the timeout, with `UVM_FATAL [PH_TIMEOUT]`.
2. Did you forget to consume time in a `run_phase` loop? If you raise an objection and enter a loop without `#` delays or `@(posedge clk)`, simulation time freezes and even the timeout cannot fire.
