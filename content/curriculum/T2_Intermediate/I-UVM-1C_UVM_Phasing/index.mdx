## Quick Take

- **What it is:** A **phase** is one named step of a UVM run. UVM calls the method with that step's name (`build_phase`, `connect_phase`, `run_phase` and so on) on every component in the testbench (TB), in a fixed order and direction. This is **phasing**. The steps before and after `run_phase` are functions that take no simulation time. `run_phase` and twelve **run-time phases** beside it are tasks that do take time, and each of those ends only when its **objections**, the "not finished yet" flags that components raise and drop, have all dropped (IEEE 1800.2-2020 §9.8, §10.5).
- **Why it matters:** Phasing guarantees that every component exists before anything is connected, and that everything is connected before time starts. Most UVM end-of-test bugs are phasing bugs: a test that "passes" at 0 ns having checked nothing, a test that hangs until a timeout, and a last transaction that never reaches the scoreboard. You can predict and fix all three once you know the rules on this page.
- **The Analogy:** A theatre production. The set is built (build), cables are run between rooms (connect), the dress rehearsal checks everything (end_of_elaboration, start_of_simulation), the show is performed (run), then the reviews are written (extract, check, report) and the set is struck (final). Objections are performers telling the stage manager "do not drop the curtain yet". *Where it breaks:* in UVM a second, twelve-scene programme (the run-time phases) plays on another stage at the same time as the show, and the curtain falls only when both stages are done. A performer who never says "done" holds the curtain forever: only a timeout ends that show, as a failure. And the curtain falls on performers in mid-line: threads still running when a phase ends are killed.

**You will be able to:**
1. **Predict** the call order and direction of the common phases for a component tree: `build` and `final` top-down; `connect`, `end_of_elaboration`, `start_of_simulation`, `extract`, `check` and `report` bottom-up; `run` a task phase.
2. **Explain** how `run_phase` runs in parallel with the twelve run-time phases, and **predict** when each of them ends.
3. **Write** end-of-test control in the test (raise before anything consumes time, drop after the stimulus) with `set_drain_time` and `phase_ready_to_end` for in-flight traffic, and **predict** when `run_phase` ends.
4. **Debug** a test that ends at 0 ns or hangs, using `set_timeout`/`+UVM_TIMEOUT`, `+UVM_OBJECTION_TRACE`, `+UVM_PHASE_TRACE` and `display_objections`.
5. **Write** `uvm_event` and `uvm_barrier` synchronization that is independent of phases, and **explain** why custom domains and phase jumps are advanced and hazardous.

## Build Your Mental Model

**How to read this lesson.** The core path is the first five sections: why phases exist, the common phases, `run_phase` beside the run-time phases, objections, and ending cleanly. Practitioner depth follows: debugging, synchronizing threads with `uvm_event` and `uvm_barrier`, and the pitfalls. Make It Work turns it into a test you can run and break on purpose, and Push Further holds the expert corner cases.

A few words you already know from earlier lessons, in one line each:

- A **component** is an object of a class derived from `uvm_component`. Components form a tree that lives for the whole run ([I-UVM-1A](/curriculum/T2_Intermediate/I-UVM-1A_Components/index)). The test object is the root you write, and UVM names it `uvm_test_top`. Above it sits `uvm_top`, UVM's own top-level component.
- A **function** returns without consuming simulation time, while a **task** may wait (`#10ns`, `@(posedge clk)`).
- A **thread** (or process) is one independently running piece of procedural code, such as one branch of a `fork` ([F2C](/curriculum/T1_Foundational/F2C_Procedural_Code_and_Flow_Control/index)).
- A **time slot** is everything the simulator does at one simulation time. The **NBA region** is the step inside it where nonblocking assignments update ([F3B](/curriculum/T1_Foundational/F3B_Scheduling_Regions/index)).

### Why a testbench needs phases

A UVM TB is a tree of components: a test, an environment (**env**) and, inside it, components that drive the design's pins (a **driver**), watch them (a **monitor**) and check results (a **scoreboard**). [I-UVM-2A](/curriculum/T2_Intermediate/I-UVM-2A_Component_Roles/index) teaches each role; on this page they are just names in a tree.

Three things must happen in a strict order. First, build the tree: a parent can create its children only after it exists itself. Second, connect the components: a connection needs both ends to exist. Third, run in simulation time, and only afterwards collect and judge the results. If each component did these things whenever it liked, a driver could start before its connection existed.

UVM therefore owns the schedule. Every component inherits one method per phase (the **phasing interface**, IEEE 1800.2-2020 §13.1.4). Almost all of them do nothing by default, and you override only the ones you need. UVM calls each one on every component at the right moment. You never call a phase method yourself.

### The common phases: order, direction and purpose

The nine **common phases** run in this order on every component (§9.8.1). "All of the phases before `uvm_run_phase` shall execute at simulation time 0" (§9.8.1). They, and the phases after `run_phase`, are **function phases**: zero-time functions that cannot wait (§9.5, §9.7). `run_phase` is a task, the only common phase that consumes time. The phases after it (extract, check, report and final) run when `run_phase` ends, at whatever simulation time that is.

| # | Phase method | Kind | Direction | Typical work |
|---|---|---|---|---|
| 1 | `build_phase` | function | top-down | Create children with `type_id::create(name, this)`; read configuration |
| 2 | `connect_phase` | function | bottom-up | Connect ports and set handles between components |
| 3 | `end_of_elaboration_phase` | function | bottom-up | Last structural adjustments; print the topology |
| 4 | `start_of_simulation_phase` | function | bottom-up | Print configuration and banners, just before time starts |
| 5 | `run_phase` | task | all components in parallel | Drive stimulus, monitor pins, check: everything that takes time |
| 6 | `extract_phase` | function | bottom-up | Collect results, such as items still waiting in a scoreboard |
| 7 | `check_phase` | function | bottom-up | Judge them: report an error for anything left over |
| 8 | `report_phase` | function | bottom-up | Print summaries |
| 9 | `final_phase` | function | top-down | Close files; last actions before the simulation ends |

What the directions mean:

- **Top-down** means a parent before its children (§9.7). `build_phase` must work this way: the parent's `build_phase` is what creates the children, so they cannot be visited first.
- **Bottom-up** means every child (and its whole subtree) before its parent (§9.5). By the time a parent runs `connect_phase`, everything below it is connected.
- The standard requires only children before parents for bottom-up phases (§9.5) and parents before children for top-down ones (§9.7). **In uvm-core 2020.3.1 both are depth-first walks**, not level-by-level sweeps: it finishes one branch of the tree before it starts the next (`uvm_bottomup_phase.svh`, `uvm_topdown_phase.svh`).
- **Siblings** (children of the same parent) are visited in instance-name order in uvm-core 2020.3.1, because it stores children in an array indexed by name. The standard does not promise this, so never write code that depends on sibling order.

Here is a traced example for one tree. The env's `build_phase` creates `scb` first and `agt` second, but name order decides the visit order:

```text
uvm_test_top
└── env
    ├── agt          (children: drv, mon)
    └── scb

build_phase   (top-down):  uvm_test_top, env, agt, drv, mon, scb
connect_phase (bottom-up): drv, mon, agt, scb, env, uvm_test_top
final_phase   (top-down):  uvm_test_top, env, agt, drv, mon, scb
```

**Pitfall: connecting in `build_phase`.** A parent's `build_phase` runs before its children's `build_phase`, so a port or handle that a child creates in its own `build_phase` does not exist yet. Calling `connect()` on it from the parent's `build_phase` dereferences a null handle. In `connect_phase` every `build_phase` in the tree has finished, so both ends exist. The bottom-up direction is not what makes it safe; finishing the build is.

### `run_phase` and the twelve run-time phases

Beside `run_phase`, UVM runs a second schedule of twelve task phases, the **run-time phases** (§9.8.2). They run one after another, in this order:

```text
pre_reset → reset → post_reset → pre_configure → configure → post_configure
→ pre_main → main → post_main → pre_shutdown → shutdown → post_shutdown
```

`run_phase` "runs in parallel to the run-time phases" (§9.8.1.5). Both start after `start_of_simulation_phase`, and `extract_phase` starts only after both have ended. A **domain** is a named group of phases that advance together. The common phases belong to the **common** domain, the twelve run-time phases to the **uvm** domain, and every component is in both by default (§13.1.4.4.1). So all components step through `reset`, then `configure`, then `main` together: `configure_phase` starts for everyone when the last component's `reset_phase` work is done.

The rule that surprises people: **`run_phase` cannot end before the schedule ends.** `run_phase` and `post_shutdown_phase` share a successor (`extract_phase`), which makes them **sibling phases**. Phase advancement "is delayed until all predecessors of the common successor are ready to proceed" (§9.6). So `run_phase` stays open, even with no objection of its own, until `post_shutdown_phase` is done. In the other direction, `post_shutdown_phase` cannot end while `run_phase` still has an objection.

Open the visualizer above again and switch the experiment to **run_phase ∥ uvm schedule**. **Predict** the answer to "Runtime phases only" (nobody objects in `run_phase`; the schedule has work until 470 ns) before you check it, then try "Objection only in run_phase".

**What the experiment showed.**
- "Runtime phases only": `run_phase` ends with `post_shutdown`, at 470 ns, although nothing objected in it. A driver looping in `run_phase` therefore keeps running through every run-time phase.
- "Objection only in run_phase": `main_phase` ends at once, because an objection keeps alive only the phase it was raised in. Code started in `main_phase` without an objection there is killed at once.
- The timeline draws the `post_shutdown` bar ending at its own idle time. In uvm-core it stays open until `run_phase`'s objections have dropped too (§9.6), so read only the `main_phase` answer from that drawing.

**Two ways to organize the run.** Pick one place for objections per environment:

- **Run-phase style (the most common).** The test raises and drops its objection in `run_phase`. The run-time phases are unused, and each one passes at time 0 with no objections, except `post_shutdown_phase`, which stays open beside `run_phase` until `run_phase`'s objections drop.
- **Run-time-phase style.** The test (or a top-level sequence) raises its objections in `reset_phase`, `configure_phase`, `main_phase` and `shutdown_phase`, so that reset, register setup and traffic are separate steps. Drivers and monitors **still loop in `run_phase`, without objections**. A driver loop placed in `main_phase` would be killed when `main_phase` ends.

Mixing both is legal, but then you must reason about sibling phases to predict the end. That is exactly the kind of question interviewers ask.

### Objections: who keeps a task phase alive

An **objection** is a counter attached to one task phase (§10.5.1, §9.3.1.7). Raising it says "do not end this phase yet"; dropping it says "I am done":

```systemverilog
// snippet: inside any task phase method
phase.raise_objection(this, "sending 4 requests");  // count defaults to 1
// ... work that takes time ...
phase.drop_objection(this, "requests sent");
```

- The first argument names who objects, almost always `this`. The description string appears in traces, so make it say why.
- An optional third argument raises or drops several at once (`count`, default 1; §9.3.1.7.2–3).
- Each task phase has its own objection object, and `phase.get_objection()` returns it (§9.3.1.7.1). uvm-core names it after the phase: `run_objection`, `main_objection` and so on.

**Count and total.** Raises **propagate** up the component tree. For each component the objection keeps a **count**, the objections that component raised itself, and a **total**, its count plus every descendant's (§10.5.1.5.3–4). A raise by `uvm_test_top.env.scb` adds 1 to the totals of `env`, `uvm_test_top` and `uvm_top`. The phase is ready to end when `uvm_top`'s total is zero.

**Who should object.** The component that knows when the work is finished: the **test**, around its stimulus, or (from [I-UVM-3A](/curriculum/T2_Intermediate/I-UVM-3A_Fundamentals/index)) the top-level **sequence** that generates it. A driver must not object. It loops `forever`, takes the next transaction, drives it, and waits for the next one; it never knows that the test is over, so it would never drop. When `run_phase` ends, UVM kills the driver's loop for you. A scoreboard may raise a *temporary* objection while it waits for a response it knows is coming, as the next section shows.

**How a task phase ends.** This is what uvm-core 2020.3.1 does for each task phase (`uvm_phase_hopper.svh`), and it implements §9.6 and §13.1.4.3.2:

1. UVM calls the phase task on every component, each in its own thread.
2. It waits for the NBA region of that first time slot, so that any `raise_objection` executed before the first statement that consumes time is seen.
3. If an objection has been raised, it waits until every objection has dropped and every drain time has passed (next section). If none has, it stops waiting for a first raise. With `+UVM_PHASE_TRACE` the log says "No objections raised, skipping phase".
4. It waits until its sibling phases also have no outstanding objections.
5. It calls `phase_ready_to_end(phase)` on every component. If a component raises an objection there, UVM goes back to step 3 and later asks again.
6. The phase ends. Threads still running in it "are forcibly and immediately killed" (§9.6), including everything they forked.

Two consequences decide most end-of-test bugs:

- **Raise before anything consumes time.** If `run_phase` has no objection at the step-2 check and the schedule is idle, step 4 passes at once and the phase ends in the same time slot. A `raise_objection` placed after `#10ns` never executes: the thread is killed first. The test "passes" at 0 ns having checked nothing.
- **Returning from the task does not end the phase.** If the test's `run_phase` returns at 100 ns but the scoreboard still objects until 300 ns, the phase ends at 300 ns. The opposite also holds: a task still running does not hold a phase open. Only objections do.

**Traced example: counts and totals.** This is the run of the Make It Work test below. The test raises at 0 ns and drops at 40 ns with a 10 ns drain time set on `uvm_test_top`. The scoreboard, `env.scb`, re-raises from `phase_ready_to_end` because two responses are still in flight, and drops at 65 ns. Each cell shows count/total for the `run_objection`; a dash means the component holds nothing.

| Time | What happens | `env.scb` | `env` | `uvm_test_top` | `uvm_top` |
|---|---|---|---|---|---|
| 0 ns | The test raises 1 | – | – | 1/1 | 0/1 |

### Ending cleanly: drain time, `phase_ready_to_end` and the timeout

Dropping the objection the moment the last stimulus is sent usually ends the phase too early. A response can still be travelling through the design, and the scoreboard would never see it. UVM gives you three tools. Only the third one deals with a hang.

**1. Drain time: a fixed grace period** (§10.5.1.3.7).

```systemverilog
// snippet: in the test's run_phase, before the drop
phase.get_objection().set_drain_time(this, 10ns);
```

- The drain is "the amount of time between the last remaining objection being dropped and the `all_dropped` callback". It starts each time this object's total reaches zero, and a new raise during the drain cancels it.
- `uvm_phase` has no `set_drain_time`; the method belongs to the phase's objection, which `get_objection()` returns.
- A drain time is a guess: long enough for today's latency, and either wasted or too short tomorrow.

**2. `phase_ready_to_end`: hold the phase while real work is pending** (§13.1.4.3.2). UVM calls this function on every component once all objections to the phase and its siblings have dropped. A component with unfinished work raises the objection there and drops it when the work is done:

```systemverilog
// snippet: in the scoreboard
function void phase_ready_to_end(uvm_phase phase);
  // Called for every task phase, not only run: act only on run.
  if (phase.get_name() != "run" || pending == 0) return;
  phase.raise_objection(this, "responses in flight");
  // A function cannot wait, so fork the wait and return at once.
  fork
    begin
      wait (pending == 0);
      phase.drop_objection(this, "all responses in");
    end
  join_none
endfunction
```

- It is a function, so it cannot wait. `fork ... join_none` is allowed in a function (IEEE 1800-2023 §13.4.4) and does the waiting in a new thread.
- It is called for `run_phase` and for each of the twelve run-time phases, so check `phase.get_name()`.
- After the new objection drops, UVM calls `phase_ready_to_end` again. To stop endless loops, it gives up after 20 rounds by default (§9.3.1.3.3–6).

**3. The timeout: the only end for a hang** (F.7.3.3).

```systemverilog
// snippet: in the test's build_phase, before run_phase starts
uvm_root::get().set_timeout(10us, 1);
```

- `run_phase` "starts a global timeout counter thread" (§9.8.1.5). If simulation time reaches the timeout before `run_phase` ends, UVM reports `UVM_FATAL [PH_TIMEOUT]`, prints the report summary and stops. `extract_phase`, `check_phase` and `report_phase` do not run.
- The value is the maximum absolute simulation time. Set it before `run_phase` starts, for example in the test's `build_phase` (§9.8.1.5). uvm-core reads it once, just after `run_phase` starts.
- The second argument, `overridable`, defaults to 1. With 0, later `set_timeout` calls have no effect.
- If nobody sets it, the default "is implementation specific" (F.7.3.3). In uvm-core it is `` `UVM_DEFAULT_TIMEOUT ``, 9200 s of simulated time, so always set a realistic value.
- From the command line, `+UVM_TIMEOUT=<integer>,<YES|NO>` sets it (uvm-core impl., not in IEEE 1800.2-2020). Push Further explains its units and the `NO` option.

**Drain time is not a hang safety net.** It starts only when a count reaches zero. If an objection is never dropped, the count never reaches zero, the drain never starts, and only the timeout ends the run.

### Debugging end-of-test problems: symptom, cause, fix

Two **plusargs** (command-line arguments that start with `+`) and one method show you what the objections are doing. All three are uvm-core 2020.3.1 implementation features, not part of IEEE 1800.2-2020.

- **`+UVM_OBJECTION_TRACE`** logs every raise, drop and `all_dropped` with ID `OBJTN_TRC`, with the count and total. The object that raised or dropped prints one form; each ancestor prints an "added … to its total" or "subtracted … from its total" form (`uvm_objection.svh`).
- **`+UVM_PHASE_TRACE`** logs phase state changes: "Starting phase", "No objections raised, skipping phase" (ID `PH/TRC/SKIP`) and "Completed phase". When the timeout fires, it also prints the outstanding objections.
- **`phase.get_objection().display_objections()`** prints a table of who holds the objection right now, with ID `UVM/OBJ/DISPLAY`. Call it from a debug thread shortly before your timeout fires (the sample below calls it at 900 ns against a 1 µs timeout).

Illustrative lines in the uvm-core formats, taken from three different runs on this page: the Make It Work test with `+UVM_OBJECTION_TRACE`, its "raise too late" variant with `+UVM_PHASE_TRACE`, and Kata 1 with a `display_objections()` call at 900 ns (before its 1 µs timeout; at exactly 1 µs the `PH_TIMEOUT` fatal could end the simulation first). Your simulator adds file and line numbers and prints times in its own units.

```text
UVM_INFO @ 0: run_objection [OBJTN_TRC] Object uvm_test_top raised 1 run_objection objection(s) (sending 4 requests): count=1  total=1
UVM_INFO @ 0: run_objection [OBJTN_TRC] Object uvm_top added 1 run_objection objection(s) to its total (raised from source object uvm_test_top, sending 4 requests): count=0  total=1

UVM_INFO @ 0: reporter [PH/TRC/SKIP] Phase 'common.run' (id=…) No objections raised, skipping phase

UVM_INFO @ 900: run_objection [UVM/OBJ/DISPLAY] The total objection count is 1
---------------------------------------------------------
Source  Total
Count   Count   Object
---------------------------------------------------------
0       1        uvm_top
0       1          uvm_test_top
0       1            env
1       1              drv
---------------------------------------------------------
```

In the table, **Source Count** is the objections that object raised itself and **Total Count** includes its descendants: here `drv` alone holds the phase open.

| Symptom in the log | Cause | Fix |
|---|---|---|
| The run ends at 0 ns, `UVM_ERROR : 0`, but nothing was driven or checked. `PH/TRC/SKIP` for `common.run`. | Nobody raised an objection before the first check: no raise at all, or a raise after a delay. | Raise in the test before the first statement that consumes time; drop after the stimulus. |
| Stimulus written in `main_phase` never appears; `run_phase` has an objection. | Objections belong to one phase. `main_phase` had none, so it ended at once and killed its threads. | Raise in `main_phase` too, or move the stimulus to `run_phase`. |
| `UVM_FATAL [PH_TIMEOUT]`, simulation time advanced, no check or report output. | An objection was never dropped. The trace shows its owner with count 1. | Drop on every path, including error paths. Move objections out of drivers and monitors. |
| Simulation time stops advancing and the job never finishes. | A loop that never consumes time, such as a `forever` with no delay or event control. The timeout cannot fire because time does not advance. | Add the missing wait (`@(posedge clk)`). A wall-clock limit on the job is the only safety net. |
| The last transaction or two never reach the scoreboard; `check_phase` reports leftovers. | The phase ended at the drop, and the response threads were killed. | Use `phase_ready_to_end` in the scoreboard, or a drain time. |

The hands-on part of this section is in Practice & Reinforce: a hang-triage simulator and a kata built on the Make It Work test.

### Synchronizing threads outside phases: `uvm_event` and `uvm_barrier`

Objections decide when a *phase* ends. Sometimes threads in different components must agree on a moment *inside* a phase: "the configuration is written, start traffic", or "all three agents have finished reset, go together". UVM wraps SystemVerilog's `event` for this (§10.1, §10.3). These objects do not touch objections and do not end phases.

**`uvm_event`: one thread says "now".** Components usually share one by name through the global **event pool**, a table of events indexed by string (`uvm_event_pool`, §10.4.1, taught in [I-UVM-5](/curriculum/T2_Intermediate/I-UVM-5_UVM_Container_Classes/index)):

```systemverilog
// snippet: two components share the event "cfg_done" by name
// In the component that writes the configuration (a task phase):
uvm_event cfg_done = uvm_event_pool::get_global("cfg_done");
// ... program the design ...
cfg_done.trigger();          // optional data: trigger(obj)

// In the component that waits for it:
uvm_event cfg_done = uvm_event_pool::get_global("cfg_done");
cfg_done.wait_ptrigger();    // safe even if trigger() ran earlier in this time slot
```

| Method | Returns when | Clause |
|---|---|---|
| `wait_trigger()` | the next `trigger()`. It is `@` on the wrapped event, so it misses a trigger earlier in the same time slot. | §10.1.1.2.4 |
| `wait_ptrigger()` | at once if the event was triggered earlier in this time slot, otherwise the next trigger | §10.1.1.2.5 |
| `wait_on()` | at once if the event is "on" (triggered and not reset since), otherwise the first trigger | §10.1.1.2.2 |
| `wait_off()` | when `reset()` turns the event off (at once if it is already off) | §10.1.1.2.3 |
| `trigger(data)` | — wakes every waiter, turns the event on and stores the optional data | §10.1.2.2.4 |
| `reset(wakeup)` | — turns the event off; with `wakeup = 1` it first wakes the waiters | §10.1.1.2.8 |

The race behind `wait_trigger()` is the SystemVerilog race you met in [I-SV-5: Events](/curriculum/T2_Intermediate/I-SV-5_Synchronization_and_IPC/events). The visualizer below models the plain `event` that `uvm_event` wraps: `wait_trigger()` behaves like `@(done)` and `wait_ptrigger()` like `wait (done.triggered)`. **Predict**: with `->` and `@(done)`, does the consumer always wake? Then flip the scheduler order.

**What it showed.** With `@(done)` the consumer wakes only if the scheduler happens to run it first. The triggered state lasts until the end of the time slot, so `wait (done.triggered)` always wakes. That is why `wait_ptrigger()` is the safe default when the trigger and the wait may fall in the same time slot, and `wait_on()` when the waiter may arrive later still. Replacing `@` with `wait_trigger()` fixes nothing.

**`uvm_barrier`: wait until N threads arrive.** Each thread calls `wait_for()`. The barrier blocks them until the number waiting reaches its **threshold**, then releases them all (§10.3.2):

```systemverilog
// snippet: three agents finish reset at different times, then start together
uvm_barrier bar = uvm_barrier::type_id::create("bar");
bar.set_threshold(3);   // the default threshold is 0: nothing would ever block
// ... in each of the three threads:
bar.wait_for();
```

Barrier methods: `set_threshold(n)` (§10.3.2.6; lowering it below the number already waiting releases them, and uvm-core also releases them when it equals that number), `set_auto_reset(0)` to let later callers pass straight through once the threshold is reached (§10.3.2.4; default 1), `reset()` (§10.3.2.3) and `cancel()` for a waiter that was killed (§10.3.2.8).

**Pitfalls.**
- `uvm_barrier` created with no threshold, or with `new("bar")`, has threshold 0, so `wait_for()` never blocks (§10.3.2.1).
- `wait_trigger()` loses a trigger from the same time slot; use `wait_ptrigger()` or `wait_on()`.
- `wait_on()` stays satisfied until `reset()`. If you reuse an event for a second round, reset it, or the second wait returns at once.
- In uvm-core, `reset()` without `wakeup` strands threads that are already waiting (see I-SV-5 Events, Push Further).
- Do not use events to end a test. A test that waits on an event in `run_phase` still needs its objection, or it never waits at all.

### Domains and phase jumps, in one paragraph

You have met the two default domains. `set_domain()` can move a subtree of components into a domain of their own (§13.1.4.4.1). In uvm-core 2020.3.1 that domain's run-time phases then advance independently of the uvm domain's, because `set_domain` never calls `sync()`. The standard's wording points the other way ("By default, all uvm_components … using the run-time schedule are synchronized", §9.8), so do not rely on either default: call `sync()` or `unsync()` explicitly (§9.3.1.8.1, §9.3.1.8.2). A running phase can also **jump** to an earlier or later phase of its schedule with `phase.jump(...)` (§9.3.1.9.1), for example from `main_phase` back to `reset_phase` after a mid-test reset. Both break the simple "everyone together, in order" picture this page is built on. A jump kills the threads of the phase it leaves, sequences included. That is why most teams avoid both, and why they are expert material: see Push Further, [E-CUST-1](/curriculum/T4_Expert/E-CUST-1_UVM_Methodology_Customization/index) for custom phases, and the A-UVM tier for reset strategy.

### Recap

- The phases before `run_phase` run at time 0, and the phases after it run when `run_phase` ends; all of them are zero-time functions. `build` and `final` are top-down; everything else is bottom-up. In uvm-core both are depth-first walks with siblings in name order (the standard requires only parents-first or children-first; do not rely on the rest).
- `run_phase` runs beside the twelve run-time phases and cannot end before `post_shutdown` ends. Objections belong to one phase.
- A task phase ends when the objection totals of it and its siblings are zero after drain time and `phase_ready_to_end`; then its threads are killed. Returning from the task does not end it.
- The test (or a top sequence) owns the objection and raises it before anything consumes time. Drivers never object.
- Drain time and `phase_ready_to_end` protect in-flight traffic; only `set_timeout` (or `+UVM_TIMEOUT`) ends a hang, with `UVM_FATAL [PH_TIMEOUT]`.
- `uvm_event` and `uvm_barrier` synchronize threads inside a phase; they never end one.

## Make It Work

### A test that ends exactly when its last response arrives

A small component, `toy_bus`, stands in for a DUT and its monitor: each request takes 10 ns to send, and its response reaches the scoreboard 25 ns later.       super.build_phase(phase);

    endfunction

    function void connect_phase(uvm_phase phase);
      `uvm_info("PHASE", "connect", UVM_LOW)
    endfunction

    function void final_phase(uvm_phase phase);
      `uvm_info("PHASE", "final", UVM_LOW)
    endfunction
  endclass

  class toy_scoreboard extends logged_component;
    `uvm_component_utils(toy_scoreboard)
    int pending;   // requests sent whose response has not arrived yet
    int matched;

    function new(string name, uvm_component parent);
      super.new(name, parent);
    endfunction

    function void expect_response(int id);
      pending++;
    endfunction

    function void write_response(int id);
      pending--;
      matched++;
      `uvm_info("SCB", $sformatf("response %0d checked", id), UVM_MEDIUM)
    endfunction

    // Called once every run_phase objection has dropped (after the drain).
    function void phase_ready_to_end(uvm_phase phase);
      // Called for every task phase: only run_phase matters here.
      if (phase.get_name() != "run" || pending == 0) return;
      phase.raise_objection(this, "responses in flight");
      fork   // a function cannot wait, so the wait runs in its own thread
        begin
          wait (pending == 0);
          phase.drop_objection(this, "all responses in");
        end
      join_none
    endfunction

    function void check_phase(uvm_phase phase);
      if (pending != 0)
        `uvm_error("SCB", $sformatf("%0d responses never arrived", pending))
    endfunction

    function void report_phase(uvm_phase phase);
      `uvm_info("SCB", $sformatf("matched=%0d pending=%0d", matched, pending), UVM_LOW)
    endfunction
  endclass

  // Stands in for a DUT and its monitor: 10 ns per request, 25 ns latency.
  class toy_bus extends logged_component;
    `uvm_component_utils(toy_bus)
    toy_scoreboard scb;   // set by the env in connect_phase

    function new(string name, uvm_component parent);
      super.new(name, parent);
    endfunction

    task send(int id);
      scb.expect_response(id);
      #10ns;
      fork   // the response arrives later, while the next request is sent
        begin
          #25ns;
          scb.write_response(id);
        end
      join_none
    endtask
  endclass

    toy_bus        bus;
    toy_scoreboard scb;

    endfunction

    endfunction

      super.connect_phase(phase);

      bus.scb = scb;
    endfunction

      super.build_phase(phase);
      `uvm_info("PHASE", "build", UVM_LOW)

      // Before run_phase starts: a hang now ends at 10 us, not 9200 s.
      uvm_root::get().set_timeout(10us, 1);
    endfunction

    function void connect_phase(uvm_phase phase);
      `uvm_info("PHASE", "connect", UVM_LOW)
    endfunction

      // Raise before anything consumes time, or the phase ends at 0 ns.
      phase.raise_objection(this, "sending 4 requests");
      phase.get_objection().set_drain_time(this, 10ns);
      for (int id = 0; id < 4; id++) env.bus.send(id);
      phase.drop_objection(this, "requests sent");
    endtask

    function void final_phase(uvm_phase phase);
      `uvm_info("PHASE", "final", UVM_LOW)
    endfunction

  import phasing_pkg::*;

Make one change at a time, predict the log, then run it:

| Change | What you should see |
|---|---|
| Delete the scoreboard's `phase_ready_to_end` | `run_phase` ends at 50 ns. The response threads (forked inside the test's `run_phase`) are killed, so responses 2 and 3 never arrive: `UVM_ERROR … [SCB] 2 responses never arrived` and `matched=2 pending=2`. |
| Delete `phase.drop_objection` in the test | The run reaches 10 µs and ends with `UVM_FATAL … [PH_TIMEOUT] Explicit timeout of … hit, indicating a probable testbench issue`. No `check_phase`, `report_phase` or `final` lines. |
| Put `#5ns;` before `raise_objection` | The run ends at 0 ns with `matched=0 pending=0` and `UVM_ERROR :    0`: a false pass. `+UVM_PHASE_TRACE` shows `[PH/TRC/SKIP] Phase 'common.run' … No objections raised, skipping phase`. |
| Delete the drop **and** move the `set_timeout` call to after the first `send` in `run_phase` | The watchdog started with the 9200 s default before the call, so the hang now runs to 9200 s of simulated time. Set the timeout before `run_phase` starts. |

### How to write end-of-test control

1. **Set the timeout first**, in the test's `build_phase`: `uvm_root::get().set_timeout(<max run time>, 1);`.
2. **Raise in the test** (or, from I-UVM-3A, in the top sequence) as the first statement of the task phase that runs the stimulus. Give it a description.
3. **Run the stimulus**, then **drop** with a description. Drop on every path, including error paths.
4. **Protect in-flight traffic**: prefer `phase_ready_to_end` in the scoreboard, which waits for the real responses; fall back to a drain time when nothing can tell you what is pending.
5. **Keep drivers and monitors in `run_phase` with no objections.** Choose the run-phase or the run-time-phase style once per environment.
6. **Debug** with `+UVM_OBJECTION_TRACE` (who holds what), `+UVM_PHASE_TRACE` (which phases were skipped), and `display_objections()` (a snapshot).

**Checklist before moving on:**
- [ ] I can write the build, connect and final print order for a tree I have not seen before.
- [ ] I can say when `run_phase` ends if only `main_phase` objects, and what happens to a driver loop in `run_phase`.
- [ ] My test raises before any delay and drops on every path; no driver or monitor raises an objection.
- [ ] I can explain why the Make It Work run ends at 75 ns, not 40 or 50 ns.
- [ ] My regressions set a timeout before `run_phase` starts, and I know what `PH_TIMEOUT` and `PH/TRC/SKIP` mean in a log.
- [ ] I use `wait_ptrigger()` or `wait_on()` rather than `wait_trigger()` when a trigger may come first, and I set a barrier's threshold.

## Push Further

### Expert: when UVM looks for the first objection

The standard says how a phase ends (§9.6, §13.1.4.3.2) but not exactly when an implementation first checks for objections. In uvm-core 2020.3.1, `uvm_phase_hopper::execute_phase` forks the phase tasks, then calls `uvm_wait_for_nba_region()` and only then reads `get_objection_total`. So:

- A raise after `#0` still counts: `#0` moves the thread to the Inactive region, which runs before the NBA region of the same time slot. (If uvm-core is compiled with `UVM_NO_WAIT_FOR_NBA` defined, it waits a fixed number of `#0` delays instead, so even this depends on the build.)
- A raise after `#1ps`, `@(posedge clk)` or any wait for a later time slot does not count in an idle run: the phase has already ended and killed the thread.
- Beside an active schedule, `run_phase` stays open until `post_shutdown_phase` ends. A raise on `run_phase` made before then still counts, because each `phase_ready_to_end` round checks every sibling again (`uvm_phase::wait_for_self_and_siblings_to_drop`). If the test's `run_phase` raises at 10 ns and drops at 510 ns while `main_phase` objects until 300 ns, `run_phase` ends at 510 ns.
- `phase_ready_to_end` is called even after "No objections raised, skipping phase", so a component can hold open, from there, a phase that nobody objected to.

Teach and code to "raise before the first statement that can consume time". It works in every implementation.

### Expert: timeout mechanics and the `+UVM_TIMEOUT` plusarg

- **Normative part** (F.7.3.3, §9.8.1.5): `set_timeout(time timeout, bit overridable = 1)`; the value is "the maximum absolute simulation time"; it must be set "prior to `uvm_run_phase` starting"; with `overridable = 0` "any future calls to `set_timeout` have no effect"; the default is implementation specific.
- **uvm-core 2020.3.1** (`uvm_root.svh`, `uvm_phase_hopper.svh`):
  - The default is `` `UVM_DEFAULT_TIMEOUT `` = 9200 s, and the fatal then says "Default timeout"; after `set_timeout` it says "Explicit timeout".
  - `+UVM_TIMEOUT=<integer>,<YES|NO>` is applied in `uvm_root::build_phase`, which runs before the test's `build_phase` (top-down). With `YES` (or nothing after the comma) the test's own `set_timeout` then replaces it. With `NO` the test's call is ignored with an info message `NOTIMOUTOVR`, so the command line wins.
  - The value is parsed with `$sscanf("%d,%s")`: give a bare integer. `+UVM_TIMEOUT=2ms` parses as 2, which gives an almost immediate `PH_TIMEOUT` (derived from the source, not run).
  - The watchdog reads the value once, just after `run_phase` starts, and runs only in `run_phase`. It bounds hangs in the run-time phases too, because `run_phase` waits for the schedule. If the value is 0 at that moment, the watchdog waits for a non-zero value, so `set_timeout(0)` disables it.
  - With `+UVM_PHASE_TRACE`, the timeout also prints each phase's outstanding objections before the fatal.

### Expert: time units of `set_timeout` and `set_drain_time`

Tool-dependent. `set_timeout(10us)` and `set_drain_time(this, 10ns)` pass a `time` value. A time literal "is interpreted as a realtime value scaled to the current time unit" (IEEE 1800-2023 §5.8), the time unit of the code that calls the method. uvm-core then waits with `#(value)` inside `uvm_pkg`, so the number is read again in `uvm_pkg`'s time unit. If your TB and `uvm_pkg` are compiled with different time units, the timeout and drain time are scaled wrongly, by a factor of 1000 for ns against ps. `+UVM_TIMEOUT`'s integer is in `uvm_pkg`'s unit. Compile uvm-core and the TB with the same time unit and precision, and print `$time` at the first drain or timeout to confirm.

### Expert: domains, `sync` and phase jumps

- **Jumps** (§9.3.1.9.1, §9.4.2.4). `phase.jump(target)` needs a target among the current phase's predecessors or successors; otherwise uvm-core reports `PH_BADJUMP` and stops. "All active phases that share phase as a common successor or predecessor shall also be affected." `uvm_domain::jump` jumps all active phases of a domain.
- **Hazards.** A jump kills the threads of the phase it leaves, including a sequence that was in the middle of an item, and clears that phase's objections (uvm-core `cleanup_phase`). Drivers and monitors in `run_phase` do not restart; they must notice the reset themselves. Scoreboards must flush expected items, or they report false mismatches. Reset handling is usually designed with explicit reset-aware components instead (A-UVM tier).
- **Domains** (§13.1.4.4.1, §9.3.1.8). `set_domain(dom)` moves a component and, by default, its subtree into `dom`, which receives its own copy of the twelve run-time phases. uvm-core does not synchronize it with the uvm domain, although §9.8 says components on the run-time schedule are synchronized by default, so call `sync` or `unsync` explicitly rather than rely on either default. Both start after `start_of_simulation` and both must finish before `extract`, but in between they drift unless you call `dom.sync(uvm_domain::get_uvm_domain())` for all phases, or `sync(target, phase, with_phase)` for one. `unsync` removes a link (§9.3.1.8.2). A use case: two clock domains whose resets end at different times.
- Custom phases are taught in [E-CUST-1](/curriculum/T4_Expert/E-CUST-1_UVM_Methodology_Customization/index).

### Expert: objections at scale

- Every raise and drop walks up the hierarchy to `uvm_top` and may trigger callbacks (`raised`, `dropped`, `all_dropped`; §10.5.1.4). Raising per transaction in a deep, busy environment costs simulation time. Raise once per test or per top sequence.
- `set_propagate_mode(0)` (§10.5.1.3.2) sends raises and drops straight to `uvm_top` instead of through each ancestor. It cannot be changed while the objection is raised or draining.
- A top sequence can own the objection: `set_automatic_phase_objection(1)` raises before `pre_start` and drops after `post_start` (§14.2.4.3–4), and `get_starting_phase()` gives the phase to object to (§14.2.4.1). The standard warns against it for a sequence with a `forever` loop, which would never drop. I-UVM-3A teaches it.
- Performance profiling of objections belongs to [E-PERF-1](/curriculum/T4_Expert/E-PERF-1_UVM_Performance/index).
