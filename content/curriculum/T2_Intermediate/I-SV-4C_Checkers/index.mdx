## Quick Take

- **What it is:** A **checker** is a SystemVerilog design element made to hold verification code: assertions, covers, covergroups and the small amount of modelling code they need (IEEE 1800-2023 Clause 17). **`bind`** is a statement that inserts an instance of a checker, module, interface or program into an existing module or interface from outside that unit's source code (§23.11). The tool does the insertion at **elaboration**, the step after compilation in which it builds the design hierarchy (the tree of instances, such as `tb_top.u_tx`), computes parameter values and connects ports (§3.12).
- **Why it matters:** The RTL (register-transfer-level design code) you must check is often locked: another team owns it, it is third-party IP, or it is under change control. Inline assertions need an edit to that source every time a check changes. A checker packages the checks once, and `bind` attaches it to every instance of a module, to a chosen list of instances, or to one instance, while the RTL files stay untouched. The same checker can then travel to the next project, and to **formal verification**, where a tool proves a property for every legal input sequence instead of simulating chosen ones.
- **The Analogy:** `bind` is a heart-monitor patch. You stick it on the patient's skin and read the vital signs without surgery. *Where it breaks:* the patient's "body" does change. After elaboration each target holds a new instance with its own hierarchical path, coverage and assertion-control scope. And a patch cannot hurt the patient, but a bound unit can: a bound module, or a checker with an output argument, can write to the design's variables. A bind is non-intrusive only if you keep it that way.

**You will be able to:**
1. Write a `checker` with formal arguments, assertions, a cover and a checker variable, instantiate it, and explain what a checker may not contain.
2. Write `bind` for a module type, an instance list and a single instance path, and predict the hierarchical path of every bound instance.
3. Choose among a checker, a bound module or interface, and assertions written inline or in an interface for a reuse scenario, and justify the choice.
4. Debug bind failures: names resolved in the target scope, connections to internal signals, name clashes, parameterized targets and missing clocks.

### The problem: checks that belong inside locked RTL

The running example is a small first-in, first-out buffer (FIFO). Its RTL is locked, and the bench uses three instances of it with different depths:

```systemverilog
// snippet: the locked RTL's ports (the full file is in Make It Work)
module fifo #(parameter int DEPTH = 4) (
  input  logic       clk, rst_n, wr_en, rd_en,
  input  logic [7:0] din,
  output logic [7:0] dout,
  output logic       full, empty
);
```

Three rules should hold on every instance: no write while `full`, no read while `empty`, and `full` and `empty` must agree with the number of items actually stored. You also want proof that each FIFO was filled and drained at least once. Where can those checks live?

- **Inline in `fifo`.** They see everything, but you may not edit the file.
- **In `tb_top`, beside each instance.** You must wire `full` and `empty` out to `tb_top`, repeat the checks per instance, and copy each `DEPTH` by hand. Internal signals stay out of reach unless you write hierarchical references.
- **In an interface that the agent uses** (the testbench unit that drives and monitors one bus). It sees only the interface's signals, never the FIFO's internals.
- **In a separate unit that the tool inserts into every `fifo` instance.** It sees every name inside each instance, gets each instance's own `DEPTH`, and needs no RTL edit. That separate unit is a checker, and the insertion is `bind`.

### The checker construct

A **checker** is declared between `checker` and `endchecker`. Its **formal arguments** are the names it uses for the values it watches, and an instance supplies an **actual argument** for each one (§17.2, §17.3). Here is the first version of the FIFO checker, declared in a package so that every bind file can name it:

```systemverilog
// compile
// fifo_chk_pkg.sv, first version: a package makes the checker visible to every bind file
package fifo_chk_pkg;
  timeunit 1ns; timeprecision 1ns;

  checker fifo_chk (
    input logic clk,                         // a direction needs an explicit type
    input logic rst_n, wr_en, rd_en, full, empty,
    input int   depth = 4                // no parameters in a checker: pass constants in
  );
    default clocking @(posedge clk); endclocking   // a package has no clock to inherit
    default disable iff (!rst_n);

    a_no_write_when_full: assert property (full |-> !wr_en)
      else $error("[%0t] write while full (depth %0d)", $time, depth);
    a_no_read_when_empty: assert property (empty |-> !rd_en)
      else $error("[%0t] read while empty", $time);
    c_fill_then_drain: cover property ($rose(full) ##[1:$] empty)
      $info("[%0t] filled and drained (depth %0d)", $time, depth);
  endchecker
endpackage
```

Read it in four parts:

1. **Formal arguments** (§17.2). Each may have a direction, `input` or `output`; with none, it copies the previous argument's direction, and the first one defaults to `input`. A formal with an explicit direction must also have an explicit type. The type may be anything legal for a property argument: `logic`, `int`, `event`, `sequence`, `property`, or nothing at all (**untyped**, which takes the type of whatever is connected). An input may have a **default value**, as `depth = 4` does, and an input may never be modified inside the checker. An `output` may not be untyped, a sequence or a property.
2. **Clock and reset.** `default clocking` and `default disable iff` give every assertion in the checker its clock and reset, exactly as in a module (I-SV-4A). They are declared inside the checker because this checker lives in a package, and a package cannot declare either one.
3. **Assertions and a cover.** These are the concurrent assertions you already know (§16.14). They sample their signals in the Preponed region, at the start of each clock edge's time slot.
4. **No parameters, no nets.** A checker is connected through its formal arguments, not module-style ports with parameters, and it can declare neither parameters nor nets. The depth arrives as an ordinary input argument.

**What a checker may contain.** The checker body is everything except the assertions' action blocks. It is deliberately smaller than a module:

| May contain | May not contain |
|---|---|
| `let`, sequence, property and function declarations (§17.2) | task declarations (only functions are listed in §17.2) |
| deferred and concurrent assertions, assumptions and covers; immediate assertions inside its procedures (§17.2, §17.5) | nets of any kind (§17.7) |
| checker variables, with continuous assignments to them (§17.7, §17.7.1) | module, interface or program instances or declarations (§17.2) |
| `always_comb`, `always_latch` and `always_ff` procedures (§17.5) | a plain `always` procedure (§17.5) |
| `initial` holding only `let`, assertions and an event control (§17.5) | assignments in `initial`, such as `initial cnt = 0;` (§17.7.1) |
| `final` procedures, with anything a module's `final` may hold (§17.5) | `parameter` or `localparam` items, and `#(...)` on an instance (§17.2, Annex A.1.8) |
| covergroup declarations and instances, outside any procedure (§17.6) | covergroups declared or created inside a procedure (§17.6) |
| other checker declarations and instances, generate blocks (§17.2) | blocking assignments in `always_ff` (§17.7.1) |

**A checker is not a module.** The table is the whole difference. A module can instantiate submodules, declare nets and parameters, and run arbitrary `always` code; a checker cannot. In exchange, a checker accepts sequences, properties and events as arguments, infers its clock from where it is placed (later in this section), and can hold **free variables** for formal verification (Push Further). If you need anything from the right-hand column, use a bound module or interface instead.

### Checker variables and sampled procedures

Variables declared in a checker body are **checker variables** (§17.7). They are static, and you initialize them in their declaration, never in an `initial` procedure. They let a checker model state that the assertions need. Here the checker counts the items it expects the FIFO to hold, so it can check the flags:

```systemverilog
// snippet: added inside fifo_chk; the complete package is in Make It Work
int level = 0;                                 // initialize here, never in initial
always_ff @(posedge clk)                       // only <= is allowed in always_ff
  if (!rst_n) level <= 0;
  else        level <= level + int'(wr_en && !full) - int'(rd_en && !empty);

a_flags_match_level: assert property (
  (full == (level == depth)) && (empty == (level == 0)))
  else $error("[%0t] full/empty disagree with the expected level", $time);
```

Two rules make this work (§17.5, §17.7.3):

- In a checker's `always_ff`, every expression except the event control reads the **sampled** value: the value from the Preponed region, the same snapshot the assertions use. So `level` is computed from the same values that the assertions see, and it can never race with the RTL's flops.
- The nonblocking assignment to `level` lands in the **Re-NBA** region, late in the time slot, after the RTL's own NBA updates. The assertions sample `level` at the next edge, together with the flags the RTL computed at this edge.

`always_comb` and `always_latch` in a checker read **current** values instead, and they are the only checker `always` procedures that may use blocking assignments (§17.5). (F3B names all the regions: [F3B: Scheduling Regions](/curriculum/T1_Foundational/F3B_Scheduling_Regions/index).)

What the waveform shows:

- **Edges 0 and 1:** `rst_n` is 0, so `default disable iff (!rst_n)` disables every attempt; the unknown flags before the first reset edge cannot cause a failure.
- **Edge 4:** `full` (which became 1 just after edge 3) and `wr_en` are both 1 in the same sample, so `full |-> !wr_en` fails. The RTL ignores that write, so `level` stays at 2 and `a_flags_match_level` keeps passing: the checker's model and the RTL agree that the third item was dropped.
- **Edge 7:** the cover's attempt started at edge 4, where `$rose(full)` was true, and `empty` is 1 for the first time since then at edge 7. A `cover property` counts at most one success per attempt (§16.14.3), so the message prints once.
- **`level` changes in the same column as the flags**, by design. Like the RTL's internal count, it is updated just after each edge (in Re-NBA rather than NBA) and sampled at the next edge, so `a_flags_match_level` always compares values from the same cycle.

### Instantiating a checker directly

You can instantiate a checker wherever a concurrent assertion may appear (§17.3, §16.14): in a module, an interface, a program, a generate block or another checker. Connections work like module ports: by position, by name (`.full(tx_full)`), implicitly by name (`.full`) or by wildcard (`.*`). Written directly in `tb_top`, the checker for one FIFO looks like this:

```systemverilog
// snippet: a static checker instance written in tb_top, with no bind
logic tx_full, tx_empty;                  // u_tx's flags must now be wired out
fifo #(.DEPTH(2)) u_tx (.clk, .rst_n, .wr_en, .rd_en, .din, .dout(),
                        .full(tx_full), .empty(tx_empty));
fifo_chk_pkg::fifo_chk u_tx_chk (.clk, .rst_n, .wr_en, .rd_en,
                                 .full(tx_full), .empty(tx_empty), .depth(2));
```

It works, and its path is `tb_top.u_tx_chk`. But every instance needs its own copy, the depth is typed twice, and the checker can only see what `tb_top` can see. That is the gap `bind` closes.

Two placement rules (§17.3):

- A checker written outside any procedure is a **static checker instance**: its assertions run at every clock tick for the whole simulation.
- A checker written inside procedural code, such as an `always` block, is a **procedural checker instance**. Its assertions are queued when the code reaches the instance, like the procedural assertions in I-SV-4A. A checker may not be instantiated inside a `fork`…`join` block or inside a procedure of another checker.

### Where a checker gets its clock and reset

A checker inherits `default clocking` and `default disable iff` from the scope where it is **declared**, not from where it is used (§17.2). A checker declared inside a module that has a default clock gets that clock. A checker declared in a package inherits nothing, because a package can declare neither default (Annex A.1.11). That is why `fifo_chk` declares its own from its `clk` and `rst_n` formals.

The other option is **context inference** (§17.4). Give a formal the default value `$inferred_clock` or `$inferred_disable`, and the default is replaced by the clock and the disable condition in force **at the point where the checker is instantiated** (§16.14.7):

```systemverilog
// snippet: declared in fifo_chk_pkg; clock and reset come from the instantiation point
checker data_stable_chk (valid, ready, data,           // untyped: any width fits
                         event clk = $inferred_clock,
                         logic rst = $inferred_disable);
  a_hold: assert property (@clk disable iff (rst) valid && !ready |=> $stable(data))
    else $error("[%0t] data changed while stalled (%0d bits)", $time, $bits(data));
endchecker
```

Three rules come with it (§16.14.7):

- If there is no clock at the instantiation point, `$inferred_clock` is an **error**. Connect the clock explicitly instead: `.clk(posedge clk)`.
- If no `default disable iff` covers the instantiation point, `$inferred_disable` returns `1'b0`, so the assertion is **never** disabled. During reset, that means false failures.
- Explicit connections always win over the defaults.

The locked `fifo` declares no default clocking, so binding `data_stable_chk` into it without `.clk(...)` is an elaboration error. Make It Work's debugging table lists the fix.

### bind: one statement, three forms

`bind` has the shape *where* + *what*: a target, then an ordinary instantiation of a checker, module, interface or program (§23.11). It is a statement, not a compiler directive (there is no backtick), and it may be written in a module, in an interface or at **compilation-unit scope**, the space outside every module in a file (§23.11). Teams usually collect binds in one file, such as `fifo_binds.sv`.

```systemverilog
// snippet: the three forms, for the bench in Make It Work
// 1. Module form: every instance of fifo, designwide, gets u_chk.
bind fifo fifo_chk_pkg::fifo_chk u_chk (
  .clk, .rst_n, .wr_en, .rd_en, .full, .empty, .depth(DEPTH));

// 2. Module : instance-list form: only the listed instances of fifo get u_cov.
bind fifo : tb_top.u_rx, tb_top.u_tx fifo_chk_pkg::fifo_state_cov u_cov (
  .clk, .rst_n, .full, .empty);

// 3. Instance form: exactly one instance gets u_log (a bound module, not a checker).
bind tb_top.u_dbg fifo_logger u_log (.clk, .wr_en, .full, .din);
```

The rules behind all three forms (§23.11):

- **Each target receives the instance as if it were typed at the very end of the target's source.** The bound instance's path is the target instance's path plus the instance name: `tb_top.u_tx.u_chk`.
- **Every actual argument and parameter is looked up inside the target**, from the target's point of view, never where the `bind` is written. `DEPTH` is each `fifo`'s own parameter, and `wr_en` is the `fifo`'s port, even if `tb_top` also has a signal called `wr_en`.
- **The module form reaches every instance of the module in the whole design**, including instances deep inside other modules and in generate blocks.
- **The instance-list form** names the module and then the instances of it to use; **the instance form** names one instance path.
- **The target must be a module or an interface**, or an instance of one. Into an interface you may bind only interfaces or checkers.

For the bench in Make It Work the result is:

| `fifo` instance | Gets | From |
|---|---|---|
| `tb_top.u_rx` (DEPTH 4) | `tb_top.u_rx.u_chk`, `tb_top.u_rx.u_cov` | module form, instance list |
| `tb_top.u_tx` (DEPTH 2) | `tb_top.u_tx.u_chk`, `tb_top.u_tx.u_cov` | module form, instance list |
| `tb_top.u_dbg` (DEPTH 8) | `tb_top.u_dbg.u_chk`, `tb_top.u_dbg.u_log` | module form, instance form |

**Classic mistake: "binding to a module type affects one instance."** The module form has no notion of "the first" or "this file's" instance. It reaches every instance of `fifo` designwide, which is what you want for protocol rules and exactly what you do not want for an expensive debug checker. Use the instance list or the instance form to narrow it.

### Predict the bind, then check it

The explorer below uses a different design, so you can test the rules rather than recall the table above. `tb_top.dut` (a `soc` module) contains two `ahb_slave` instances, `u_slave_0` and `u_slave_1`, and one `spi_ctrl`. Each `ahb_slave` already contains a FIFO called `u_fifo`. The checker `ahb_protocol_chk` has three formals, connected to the slave's `clk_i`, `rst_ni` and `addr_i`.

For each of the four bind forms, **predict the full path of every `chk_inst` before you reveal the hierarchy.** That path is what you will type into waveform viewers, `$assertoff` calls and coverage exclusions.

Debrief, scenario by scenario:

- **Every `ahb_slave`:** both `tb_top.dut.u_slave_0.chk_inst` and `tb_top.dut.u_slave_1.chk_inst`. `u_spi` gets nothing, because it is a `spi_ctrl`, not an `ahb_slave`.
- **Listed instances:** only `tb_top.dut.u_slave_1.chk_inst`. Each instance in the list must be an instance of the named module.
- **One instance path:** only `tb_top.dut.u_slave_0.chk_inst`.
- **Two binds, same name:** an elaboration error. A bound instance name may not clash with any name already in the target, including a name added by another bind (§23.11). Rename one of them, for example `cov_inst`.
- **The distractor `tb_top.chk_inst` is never right.** Where the `bind` is written decides nothing about where the instance goes. A bind may be written in a module, an interface or at compilation-unit scope (§23.11), and the instance always lands inside its target.

### Where a bound checker's names come from

A bound checker uses names from three different places, and most bind bugs come from mixing them up:

1. **Actual arguments** in the bind's port list resolve **in the target** (§23.11). `.wr_en` means the `fifo`'s `wr_en`; `.depth(DEPTH)` means the `fifo`'s `DEPTH`. You may also pass an expression or a relative hierarchical name that the target can see, such as `.data(u_ram.q)`.
2. **Names inside the checker body** that are neither formals nor the checker's own declarations resolve in the scope where the checker is **declared** (§17.2), here the package. A bound checker does not see the target's signals just because it sits inside the target: its body sees only its formals and its own declarations, plus what its declaration scope can see.
3. **`$inferred_clock` and `$inferred_disable` defaults** resolve at the **instantiation point** (§16.14.7). For a bound checker, that point is the end of the target scope, so they pick up the target's default clocking and default disable, if it has any.

Two consequences:

- **Name the checker by its package:** `fifo_chk_pkg::fifo_chk`. Declarations in the compilation-unit scope (`$unit`, the space outside every module) are not visible in a bind statement (§23.11), and the RTL usually does not import your verification package. A package-scoped name works from anywhere, provided the package is compiled first: the standard requires a package to be compiled before anything that refers to it (§3.12, §26.3). The bind file itself may come before or after the RTL, because targets are resolved at elaboration.
- **Never hide a design signal inside the checker body.** `assert property (rst_n |-> …)` inside a package checker, with `rst_n` not a formal, looks in the package, not in the `fifo`. Make every design signal a formal and connect it in the bind.

### Parameterized and generated targets

**Parameters.** A checker cannot take `#(...)`, so pass the target's parameter as an input argument: `.depth(DEPTH)` resolves `DEPTH` inside each target, so `u_rx` gets 4, `u_tx` 2 and `u_dbg` 8 from one bind statement. For data whose width depends on a parameter, use **untyped** formals, as `data_stable_chk` does: an untyped formal takes the width of its actual, and `$bits(data)` reports it. When a check genuinely needs a parameter or a type parameter (for example to size a `generate` loop or instantiate a submodule), bind a **module** instead: modules take `#(...)`, and its parameter values also resolve in the target.

**Generate scopes** (awareness; generate blocks are taught in [I-SV-6](/curriculum/T2_Intermediate/I-SV-6_Compiler_Directives_and_Generates/index)). A generate block is code the tool repeats or selects at elaboration, and a named generate loop gives each copy an indexed name:

```systemverilog
// snippet: locked RTL that builds one fifo per lane in a named generate loop
module lanes (input logic clk, rst_n);
  for (genvar i = 0; i < 4; i++) begin : g_lane
    fifo #(.DEPTH(4)) u_fifo (.clk, .rst_n, .wr_en(), .rd_en(), .din(),
                              .dout(), .full(), .empty());
  end
endmodule

// The module form already reaches tb_top.dut.g_lane[0].u_fifo … g_lane[3].u_fifo.
// The instance form can pick one lane with a constant index:
bind tb_top.dut.g_lane[2].u_fifo fifo_chk_pkg::fifo_state_cov u_cov (
  .clk, .rst_n, .full, .empty);
```

- A bind target path may contain constant indices into generate blocks (Annex A.9.3 `hierarchical_identifier`).
- Give every generate block you want to target a name. An unnamed block has no name that can be used in a hierarchical path; tools show it as `genblk<n>` (§27.6), but that name is for external tools, not for your bind file.
- To attach one checker per port or lane, I-SV-6 binds a **wrapper module** that contains its own generate loop, with one `bind` to the RTL module. Never write `bind` inside a generate loop to do it: every iteration would add the same instance name to the same target.

### Choosing where assertions live

| Container | What it can see | Parameters | Use when | Avoid when |
|---|---|---|---|---|
| Inline in the RTL module | everything in the module | yes | you own the RTL and the rule is a design invariant the designer should see fail | the RTL is locked or third-party, or the check is testbench policy |
| In an interface ([F4B](/curriculum/T1_Foundational/F4B_Interfaces_and_Modports/index)) | only the interface's signals | yes | pin-level protocol rules that should travel with an agent (VIP: verification IP) | you need internal design state |
| Checker, bound or instantiated | every name its bind actuals reach | no: pass constants as arguments | reusable assertion libraries, formal reuse, internal signals of locked RTL | you need module instances, nets, parameters or a plain `always`, or your tools support checkers poorly |
| Bound module | the same, plus anything a module can declare | yes | a check needs a submodule, a generate loop sized by a parameter, or file I/O | a checker would do: a module can also drive design signals by mistake |
| Bound interface | the same | yes | the target is an interface, or a UVM monitor needs a virtual interface onto internal signals | plain assertions are all you need |

A good default: protocol rules at the pins go in the agent's interface; internal-signal checks for locked RTL go in a checker in a package, attached with one bind file; anything the table's checker row forbids goes in a bound module.

### Assertion libraries

The standard names the intended use of checkers directly: "verification library units", and building blocks for the abstract models used in formal verification (§17.1). A library checker is written once, without knowing where it will be used, so it takes every signal as a formal, often untyped, and takes its clock and reset from `$inferred_clock` and `$inferred_disable` defaults. The standard's own example, `assert_window1` in §17.9, has exactly that shape. You will meet two kinds of library in practice: Accellera's Open Verification Library (OVL), whose elements are instantiated like modules, and vendor assertion IP for standard protocols, whose form and licensing are tool-dependent. Before you adopt one, check how it reports failures and how it expects to be bound.

### Common mistakes

1. **"`bind` edits or recompiles the target's source."** It does neither. The file is untouched; the instance exists only in the elaborated design, so changing a bind needs a new elaboration, not an RTL edit.
2. **"A checker can contain anything a module can."** It cannot: no nets, no module instances, no tasks, no plain `always`, no parameters (the table above).
3. **"Binding to a module type affects one instance."** It affects every instance designwide.
4. **Writing actuals with the bench's names.** `.wr_en(tx_wr)` fails if the target has no `tx_wr`. Worse, if the target happens to have a signal with the bench's name, the bind silently connects to the target's signal.
5. **`initial level = 0;` in a checker.** Assigning a checker variable in `initial` is illegal (§17.7.1); initialize it in its declaration.
6. **Expecting a package checker to inherit a clock.** It inherits nothing; declare `default clocking` inside it, or use `$inferred_clock` and accept the error when the target has no clock.

### Recap

- A checker is a restricted, verification-only container: formals instead of ports, no parameters, nets or module instances, sampled `always_ff`, and assertions, covers and covergroups.
- `bind` inserts an instance into a module or interface at elaboration, as if it were written at the end of the target; the target's source never changes.
- Three forms: a module (every instance, designwide), a module with an instance list, or one instance path. The bound path is always the target path plus the instance name.
- Bind actuals resolve in the target; the checker body resolves free names where it is declared; inferred clock and disable resolve at the instantiation point.
- Pass parameters as arguments, name the checker by its package, and choose a bound module when a checker's restrictions get in the way.

## Make It Work

### Worked example: one checker on every FIFO, coverage on two, a logger on one

The bench has five files. The RTL is never edited; everything else attaches to it through one bind file. The stimulus drives the same writes into three FIFOs of depth 4, 2 and 8, and the third write is one too many for the depth-2 FIFO only.

**File 1, `fifo.sv`: the locked RTL.**

```systemverilog
// compile
// fifo.sv: locked RTL. Nothing below may be edited for verification.
module fifo #(parameter int DEPTH = 4) (
  input  logic       clk, rst_n, wr_en, rd_en,
  input  logic [7:0] din,
  output logic [7:0] dout,
  output logic       full, empty
);
  timeunit 1ns; timeprecision 1ns;

  localparam int AW = (DEPTH > 1) ? $clog2(DEPTH) : 1;
  logic [7:0]    mem [DEPTH];
  logic [AW-1:0] wptr, rptr;
  logic [AW:0]   count;
  logic          do_wr, do_rd;

  assign do_wr = wr_en && !full;     // a write while full is dropped
  assign do_rd = rd_en && !empty;    // a read while empty is dropped
  assign full  = (count == DEPTH);
  assign empty = (count == 0);
  assign dout  = mem[rptr];

  always_ff @(posedge clk or negedge rst_n) begin
    if (!rst_n) begin
      wptr <= '0; rptr <= '0; count <= '0;
    end else begin
      if (do_wr) begin
        mem[wptr] <= din;
        wptr      <= (wptr == DEPTH - 1) ? '0 : wptr + 1'b1;
      end
      if (do_rd) rptr <= (rptr == DEPTH - 1) ? '0 : rptr + 1'b1;
      count <= count + do_wr - do_rd;
    end
  end
endmodule
```

**File 2, `fifo_chk_pkg.sv`: the checkers.** `fifo_chk` is the first version plus the `level` model; `fifo_state_cov` is coverage only.

```systemverilog
// compile
// fifo_chk_pkg.sv: compile this file before any file that names its checkers
package fifo_chk_pkg;
  timeunit 1ns; timeprecision 1ns;

  // Protocol and flag checks for one fifo instance.
  checker fifo_chk (
    input logic clk,
    input logic rst_n, wr_en, rd_en, full, empty,
    input int   depth = 4                    // no parameters in a checker
  );
    default clocking @(posedge clk); endclocking
    default disable iff (!rst_n);

    int level = 0;                           // items this checker expects to be stored
    always_ff @(posedge clk)                 // reads sampled values, updates in Re-NBA
      if (!rst_n) level <= 0;
      else        level <= level + int'(wr_en && !full) - int'(rd_en && !empty);

    a_no_write_when_full: assert property (full |-> !wr_en)
      else $error("[%0t] write while full (depth %0d)", $time, depth);
    a_no_read_when_empty: assert property (empty |-> !rd_en)
      else $error("[%0t] read while empty", $time);
    a_flags_match_level: assert property (
      (full == (level == depth)) && (empty == (level == 0)))
      else $error("[%0t] full/empty disagree with the expected level", $time);
    c_fill_then_drain: cover property ($rose(full) ##[1:$] empty)
      $info("[%0t] filled and drained (depth %0d)", $time, depth);
  endchecker

  // Which flag states did this instance reach? Covergroups sit outside procedures.
  checker fifo_state_cov (input logic clk, rst_n, full, empty);
    covergroup cg_state @(posedge clk);
      option.per_instance = 1;
      cp_state: coverpoint {full, empty} iff (rst_n) {
        bins is_empty = {2'b01};
        bins partial  = {2'b00};
        bins is_full  = {2'b10};
      }
    endgroup
    cg_state cg = new();
  endchecker
endpackage
```

**File 3, `fifo_logger.sv`: a bound module.** It uses a plain `always` procedure, which a checker may not contain, so it has to be a module. `%m` prints the logger's own hierarchical path.

```systemverilog
// compile
// fifo_logger.sv: debug logging for one instance; a checker may not use a plain always
module fifo_logger (input logic clk, wr_en, full, input logic [7:0] din);
  timeunit 1ns; timeprecision 1ns;
  // Runs in the Active region at the edge, before the RTL's NBA updates,
  // so it sees the same wr_en, full and din as the fifo's flops.
  always @(posedge clk)
    if (wr_en && !full) $display("[%0t] %m: write %h", $time, din);
endmodule
```

**File 4, `fifo_binds.sv`: every bind in one place.**

```systemverilog
// compile
// fifo_binds.sv: compilation-unit scope. Every actual is looked up inside each target.

// Module form: every fifo in the design, each with its own DEPTH.
bind fifo fifo_chk_pkg::fifo_chk u_chk (
  .clk, .rst_n, .wr_en, .rd_en, .full, .empty, .depth(DEPTH));

// Instance-list form: state coverage on the two traffic FIFOs only.
bind fifo : tb_top.u_rx, tb_top.u_tx fifo_chk_pkg::fifo_state_cov u_cov (
  .clk, .rst_n, .full, .empty);

// Instance form: the logger on the debug FIFO only.
bind tb_top.u_dbg fifo_logger u_log (.clk, .wr_en, .full, .din);
```

**File 5, `tb_top.sv`: the bench.**

```systemverilog
// compile
// tb_top.sv: one stimulus drives three FIFOs of different depths.
module tb_top;
  timeunit 1ns; timeprecision 1ns;

  logic       clk   = 1'b0;
  logic       rst_n = 1'b0;
  logic       wr_en = 1'b0;
  logic       rd_en = 1'b0;
  logic [7:0] din   = '0;

  always #5 clk = ~clk;                 // rising edges at 5, 15, 25 ... ns

  // Drive DUT inputs only through this clocking block (F4C): each drive lands
  // just after an edge, and every flop and assertion samples it at the next one.
  default clocking cb @(posedge clk);
    output rst_n, wr_en, rd_en, din;
  endclocking

  // full and empty are left open: the bound checkers read them inside each fifo.
  fifo #(.DEPTH(4)) u_rx  (.clk, .rst_n, .wr_en, .rd_en, .din,
                           .dout(), .full(), .empty());
  fifo #(.DEPTH(2)) u_tx  (.clk, .rst_n, .wr_en, .rd_en, .din,
                           .dout(), .full(), .empty());
  fifo #(.DEPTH(8)) u_dbg (.clk, .rst_n, .wr_en, .rd_en, .din,
                           .dout(), .full(), .empty());

  initial begin
    ##2 cb.rst_n <= 1'b1;               // leave reset just after the 2nd edge (15 ns)
    for (int i = 0; i < 3; i++) begin   // three writes: one too many for u_tx
      cb.wr_en <= 1'b1;
      cb.din   <= 8'hA0 + 8'(i);
      ##1;
    end
    cb.wr_en <= 1'b0;
    cb.rd_en <= 1'b1;                   // two reads empty u_tx again
    ##2 cb.rd_en <= 1'b0;
    ##2 $display("[%0t] stimulus done", $time);
    $finish;
  end
endmodule
```

**Run it.** Compile the package first, then the other four files in any order, and elaborate with `tb_top` as the top module. With most simulators that is one command of the form `<simulator> fifo_chk_pkg.sv fifo.sv fifo_logger.sv fifo_binds.sv tb_top.sv` with `tb_top` as top. Checker, covergroup-in-checker and `bind` support differs between tools, so try this bench before you rely on these features (Push Further).

**Expected output** (illustrative, traced by hand; no simulator was run). Each tool adds its own prefix to `$error` and `$info` lines, normally with the assertion's full path, shown here in braces:

```text
[25] tb_top.u_dbg.u_log: write a0
[35] tb_top.u_dbg.u_log: write a1
[45] tb_top.u_dbg.u_log: write a2
{error prefix, tb_top.u_tx.u_chk.a_no_write_when_full} [45] write while full (depth 2)
{info prefix, tb_top.u_tx.u_chk.c_fill_then_drain} [75] filled and drained (depth 2)
[85] stimulus done
```

The coverage report (format tool-dependent) shows all three bins of `tb_top.u_tx.u_cov.cg` hit, and `is_full` of `tb_top.u_rx.u_cov.cg` missed: `u_rx` never held more than three items. There is no `u_cov` under `u_dbg`, because the instance list did not name it. The cover `c_fill_then_drain` matched only under `tb_top.u_tx.u_chk`.

How to read it:

- **One bind, three behaviours.** The module form put `u_chk` in all three FIFOs, and each got its own `depth` (4, 2 and 8) from its own `DEPTH`. Only `u_tx` holds two items, so only its checker fails, at 45 ns: the same edge 4 you predicted on the waveform.
- **The 45 ns lines come in a fixed order.** The logger's `$display` runs in the Active region of the edge; the assertion's fail statement runs later in the same time slot, in the Reactive region (§16.14.1).
- **The coverage tells you what was never tested.** `u_rx` was never full, so its `is_full` bin and its cover are empty. A stimulus change is needed before anyone can claim the full-FIFO behaviour of the depth-4 FIFO is verified.
- **`tb_top` never connected `full` or `empty`**, and the checkers still read them. That is the bound checker's view from inside each instance.

### How to attach a checker with bind

1. **Write the checks as a checker in a package.** Make every design signal a formal, pass parameters as input arguments, and declare `default clocking` and `default disable iff` inside the checker (or use `$inferred_clock` and `$inferred_disable` defaults and always connect them explicitly).
2. **Pick the form.** Module form for rules every instance must obey; instance list or instance form for expensive or instance-specific checks.
3. **Connect by the target's names.** Prefer explicit `.formal(actual)` or `.name` connections: `.name` is an error when the target has no such name (§23.3.2.3), while `.*` silently uses a formal's default (§23.3.2.4).
4. **Compile the package first**, then elaborate, and list the bound paths in the tool's hierarchy view. Each should be `target path` + `.` + `instance name`.
5. **Prove the checker is alive.** Inject one bug that must fail (here, one write too many) and check that a cover fires on a normal run. A checker that has never failed and never covered anything is not evidence of anything.

### Debugging bind failures

| Symptom | Likely cause | Fix |
|---|---|---|
| Elaboration error: a name in the bind's port list is not found, for example `tx_wr` | Actuals resolve in the target (§23.11); the target calls it `wr_en`, or the signal lives in a submodule | Use the target's name; for a submodule signal pass a relative path the target can see (`.data(u_ram.q)`) or bind to the submodule instead |
| Elaboration error: the checker name is not found in the bind | The checker is declared in `$unit` or in a package the target does not import; `$unit` is not visible in a bind (§23.11) | Declare it in a package, write `pkg::name`, and compile the package first (§3.12) |
| Elaboration error: an instance name already exists | Two binds add the same name to one target, the RTL already uses it, or the bind sits inside a module that is instantiated twice (§23.11) | Give each bind a unique name; keep binds at compilation-unit scope or in a module instantiated once |
| Syntax error at `#(` on a checker instance | Checkers have no parameters (§17.2) | Pass the value as an input argument: `.depth(DEPTH)` |
| Elaboration error: no clock can be inferred | A formal defaults to `$inferred_clock` and the target has no default clocking (§16.14.7) | Connect it: `.clk(posedge clk)`, or give the checker its own `default clocking` from a clock formal |
| Assertions fail during reset | `$inferred_disable` returned `1'b0` because the target has no `default disable iff` (§16.14.7), or `.*` left a reset formal at its default because the target's reset has another name (§23.3.2.4) | Connect the reset explicitly; prefer `.name` or explicit connections to `.*` |
| Elaboration error when binding into an interface | Only interfaces and checkers can be bound into an interface (§23.11) | Bind a checker or an interface, or bind to a module instead |
| Elaboration error: target is inside a bound instance | A bind may not reach underneath another bound instance (§23.11) | Bind into the original target scope |
| The checker never fails and never covers | It is not bound where you think (wrong list or path), its assertions are turned off, or every attempt is vacuous | Find its path in the hierarchy view, add a cover on the trigger, inject a bug |

**Checklist before moving on:**
- [ ] Every design signal the checker uses is a formal, and every formal is connected by the target's name.
- [ ] The checker has no `#(...)`, no nets, no plain `always` and no assignment in `initial`.
- [ ] The checker is declared in a package, named as `pkg::name` in every bind, and the package compiles first.
- [ ] You can write down the full path of every bound instance before elaborating, and the hierarchy view agrees.
- [ ] Each checker has failed once on an injected bug, and its cover has fired on a normal run.
- [ ] Clock and reset are connected explicitly or declared inside the checker, so no assertion runs during reset.

## Push Further

### Expert: Checker scheduling and sampled procedures

Inside a checker, constructs that react to changes (clocking events, continuous assignments) and all blocking statements run in the **Reactive** region, like a program block; nonblocking assignments to checker variables update in **Re-NBA**, after the Reactive and Re-Inactive regions have emptied (§17.7.3). Four consequences:

- `always_ff @clk a <= s.triggered;` works in a checker. The sequence's `triggered` value is set in the Observed region, and the checker reads it later, in Reactive. Read in the Active region, it would always be `1'b0` (§17.7.3).
- §17.7.3 names clocking events among the change-sensitive constructs it schedules in the Reactive region. A covergroup clocked with `@(posedge clk)` inside a checker can therefore sample values that the design already updated at that edge, not the Preponed snapshot the assertions use. Simulators differ in how closely they follow this (tool-dependent), so `fifo_state_cov` in Make It Work only makes claims that hold either way. When the exact sample point matters, give the covergroup a custom `sample()` with arguments and call it from a sequence match item, as the second §17.6 example does: by-value arguments of a match-item call carry sampled values (§16.11).
- A covergroup's `sample()` called from a sequence match item runs in Reactive, before the checker's NBAs, so it sees the **old** value of a checker variable (§17.6). Pass the value as a `sample()` argument when you need a particular one.
- A checker's output arguments behave as continuous assignments to their actuals, executed in Reactive (§17.3). Design code that reads such an output on the same edge sees the value from the previous edge.

Source: IEEE 1800-2023 §16.11, §17.3, §17.5, §17.6, §17.7.3; covergroup sample timing in simulators is tool-dependent.

### Expert: Free variables, assume sets and formal

A checker variable declared `rand` is a **free variable**: a value no code assigns, which a formal tool treats as "any value allowed by the assumptions" and a simulator randomizes (§17.7). `rand const` holds one nondeterministic value for the whole run. The standard's own example checks that every bit of two 64-bit buses matches, using one symbolic index:

```systemverilog
// snippet: in formal, idx stands for every index at once; in simulation, one random index
checker same_bits (bit [63:0] a, b, event clk);
  rand const bit [5:0] idx;
  a1: assert property (@clk a[idx] == b[idx]);
endchecker
```

The checker's `assume` statements that mention its active free variables form its **assume set**. A simulator solves the assume set at each of its clock events, before the Observed region, to pick values for the free variables (§17.7.2); there is no `randomize()` call, and a solution that leads to a later "dead end" still counts as a solution. This is why §17.1 calls checkers building blocks for "abstract auxiliary models" in formal verification: the same checker drives a symbolic model in formal and a random one in simulation. [E-INT-1](/curriculum/T4_Expert/E-INT-1_Integrating_UVM_with_Formal_Verification/index) uses bound checkers this way.

Source: IEEE 1800-2023 §17.1, §17.7, §17.7.1, §17.7.2.

### Expert: Bind corner cases from §23.11

- **No bind underneath a bound instance.** A bind may not target a scope inside another bind's instance.
- **Interface targets** accept only interface or checker instances.
- **An instance path that is also a module name** binds only the instance.
- **Bind order does not matter**: a tool may elaborate the bind statements in a scope in any order.
- **`$unit` is invisible** in a bind statement. Wildcard imports already made into the target are visible, but a bind cannot cause a new wildcard import.
- **Type parameters** overridden in a bind must name a type visible and matching in both the bind's scope and the target's.
- **Hierarchical references to a bound instance's parameters** are not constant expressions outside it, so they cannot size types or drive generate conditions.
- **A bind inside a module that is instantiated twice** adds the same instance name twice to each target: an error. Keep binds at compilation-unit scope or in a single-instance module.

Source: IEEE 1800-2023 §23.11.

### Expert: Wildcard connections, defaults and inferred context

With `.*`, a formal whose name does not exist in the instantiating scope silently takes its **default value** (§23.3.2.4); checker connections follow the module-port rules (§17.3). Combine that with a reset formal declared as `logic rst = $inferred_disable` and a target whose reset is called `rst_ni`: the formal is not connected, the default applies, and `$inferred_disable` returns `1'b0` when the target has no `default disable iff` (§16.14.7). The assertion is then never disabled, and nothing warns you. The `.name` form would have reported an error instead (§23.3.2.3). Library checkers make this trap common, because their formals all have defaults. Rule of thumb for bind files: explicit or `.name` connections, never a bare `.*`.

Source: IEEE 1800-2023 §16.14.7, §17.3, §23.3.2.3, §23.3.2.4.

### Expert: Keeping a bound checker non-intrusive

Non-intrusive is a discipline, not a guarantee of the language:

- A checker's output argument must be connected to a variable or net, and it is written by an implicit continuous assignment in Reactive (§17.3). Bound into RTL and connected to an RTL variable, it writes into the design, and it can create a second driver.
- A bound module can do anything a module can, including `force` statements and drives on design signals.
- Even a pure checker changes the elaborated design: it adds instance paths, coverage items and scopes that `$assertoff` and waveform tools see. Code-coverage and hierarchy-comparison flows see the extra instances; whether and how to exclude them is tool-dependent.

Keep bound units observation-only, and route any result to the testbench through reporting, not through output arguments connected to RTL.

Source: IEEE 1800-2023 §17.3, §23.11; tool-dependent for flow integration.

### Expert: Controlling and reporting bound assertions

Bound assertions are controlled by their **module hierarchy** paths, not UVM component paths. `$assertoff(0, tb_top.u_tx)` turns off every assertion in `u_tx` and everything below it, bound checkers included; the first argument 0 means "all levels below" (§20.11). A test that injects a deliberate protocol error can switch off just the affected instance this way and switch it back on with `$asserton`. In a UVM bench, assertion failures from bound checkers reach the log through `$error`; routing them into UVM's report server, so they count in the end-of-test summary, belongs to [A-UVM-7](/curriculum/T3_Advanced/A-UVM-7_VIP_Construction/index).

Source: IEEE 1800-2023 §20.11.

### Expert: Tool support and portability

Tool-dependent. Simulators and formal tools differ in their checker support: free variables and assume-set randomization, procedural checker instances, covergroups inside checkers, untyped and `sequence` formals, and how bound paths appear in reports. Some teams standardize on bound modules and interfaces for portability and keep checkers for formal-only models; others ship checker libraries and test them on every tool in the flow. Whichever you choose, add a one-page smoke test (this lesson's bench is a good start) to the project's tool qualification, and check how each tool names a failing assertion inside a bound checker before you write triage scripts that parse it.

### Kata: bind a handshake checker everywhere, then selectively

A new SoC, `tb_top.dut` (module `soc`), contains four instances of the locked `fifo` from Make It Work: `u_rx` (DEPTH 4), `u_tx` (DEPTH 2), `u_dma` (DEPTH 16) and `u_dbg` (DEPTH 8). Using the package from Make It Work plus `data_stable_chk` from Build Your Mental Model (added to the same package):

1. Bind `fifo_chk` to **every** `fifo`, and write down all four paths before you elaborate.
2. Bind `data_stable_chk` to **every** `fifo` as a handshake check: while the FIFO is not empty and no read happens, `dout` must hold its value. Remember that `fifo` has no default clocking and no default disable.
3. Bind `fifo_state_cov` only to `u_rx` and `u_tx`.
4. Bind `fifo_logger` only to `u_dbg`.
5. Predict what happens if you also add `bind fifo fifo_chk_pkg::fifo_state_cov u_chk (.clk, .rst_n, .full, .empty);`.

<details>
<summary>Reveal the worked solution</summary>

```systemverilog
// compile
// soc_binds.sv: compilation-unit scope; fifo_chk_pkg is compiled first.

// 1. Every fifo: tb_top.dut.u_rx.u_chk, .u_tx.u_chk, .u_dma.u_chk, .u_dbg.u_chk
bind fifo fifo_chk_pkg::fifo_chk u_chk (
  .clk, .rst_n, .wr_en, .rd_en, .full, .empty, .depth(DEPTH));

// 2. Every fifo. fifo has no default clocking or default disable iff, so both
//    inferred defaults must be overridden: the clock would be an error, and
//    the disable would be 1'b0 (never disabled).
bind fifo fifo_chk_pkg::data_stable_chk u_hold (
  .valid(!empty), .ready(rd_en), .data(dout),
  .clk(posedge clk), .rst(!rst_n));

// 3. Only the two traffic FIFOs.
bind fifo : tb_top.dut.u_rx, tb_top.dut.u_tx fifo_chk_pkg::fifo_state_cov u_cov (
  .clk, .rst_n, .full, .empty);

// 4. Only the debug FIFO.
bind tb_top.dut.u_dbg fifo_logger u_log (.clk, .wr_en, .full, .din);
```

**Why the handshake check holds on this RTL.** While the FIFO holds at least one item and no read happens, `rptr` does not move. A write in that cycle goes to `mem[wptr]`, and `wptr` differs from `rptr` whenever the FIFO is neither empty nor full (when it is full, no write happens at all). So `dout = mem[rptr]` keeps its value, and `a_hold` passes. If you remove the `!empty` guard, a write into an empty FIFO lands at `rptr` and changes `dout`, and the check fails on correct RTL: a reminder to write the condition the design actually promises.

**Step 5 prediction.** Elaboration error in every `fifo` instance: step 1 already added a name `u_chk` to each target, and a bound instance name may not clash with a name in the target, including names added by other binds (§23.11). Rename the new instance, for example `u_cov_all`; then `u_rx` and `u_tx` hold both `u_cov` and `u_cov_all`, which is legal but duplicates coverage.

**Paths after steps 1 to 4:**

| Instance | Bound instances |
|---|---|
| `tb_top.dut.u_rx` | `u_chk`, `u_hold`, `u_cov` |
| `tb_top.dut.u_tx` | `u_chk`, `u_hold`, `u_cov` |
| `tb_top.dut.u_dma` | `u_chk`, `u_hold` |
| `tb_top.dut.u_dbg` | `u_chk`, `u_hold`, `u_log` |

### Debug drill: four symptoms

For each symptom, name the cause and the fix before you open the answers.

1. `bind fifo fifo_chk u_chk (...)` fails: `fifo_chk` not found. The checker is declared at the top of `fifo_chk.sv`, outside any package.
2. A bound checker with `logic rst = $inferred_disable` reports failures on every edge during reset.
3. `bind fifo : tb_top.u_rx, tb_top.u_spi fifo_chk_pkg::fifo_chk u_chk (...)` fails, although both paths exist.
4. After a merge, the bind file has two `u_chk` binds for `fifo`, one for `fifo_chk` and one for a new coverage checker. Elaboration fails.

<details>
<summary>Reveal the answers</summary>

1. The checker is in the compilation-unit scope (`$unit`), whose declarations are not visible in a bind statement (§23.11). Move it into a package, write `fifo_chk_pkg::fifo_chk`, and compile the package first.
2. The target `fifo` has no `default disable iff`, so `$inferred_disable` returned `1'b0` (§16.14.7) and the assertions are never disabled. Connect `.rst(!rst_n)`.
3. `tb_top.u_spi` is not an instance of `fifo`. Every path in the instance list must be an instance of the named module (§23.11). Bind `u_spi` with its own statement, or drop it.
4. Two binds add the same instance name to each `fifo` (§23.11). Give the coverage checker its own name, such as `u_cov`.

</details>
