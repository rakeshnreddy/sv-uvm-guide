## Quick Take
- **Why it exists:** text logs are a poor way to debug long bus transactions. Recording writes each UVM transaction — its start time, end time and field values — into a transaction database, so a waveform viewer can draw it next to the RTL signals.
- **`uvm_recorder`**: The policy object that receives a transaction's fields. Your `do_record()` (or the field macros) calls it, for example through `` `uvm_record_field ``.
- **`uvm_tr_stream`**: A channel of transactions, like one row in the viewer. A component opens one stream per stream name.
- **`uvm_tr_database`**: The backend that stores everything. The UVM library's default writes a text file (`tr_db.log`); simulators plug in their own database so transactions appear in the waveform tool.
- **The rule that bites:** recording is **off by default**. Until it is enabled on the component, `begin_tr()` returns 0 and nothing is recorded.

## Build Your Mental Model

Think of a UVM transaction as a cargo box filled with items (data fields). The `uvm_recorder` acts as a packing slip generator, noting down every item in the box. The `uvm_tr_stream` is the conveyor belt that moves this specific type of box, and the `uvm_tr_database` is the warehouse where all boxes are stored and cataloged for later inspection.

When a `uvm_driver` starts executing a transaction, it tells the warehouse, "I'm starting a new box now." When it finishes, it says, "I'm done with this box" — and only then is the packing slip written. So the recorded field values are the values **at `end_tr()`**: a read's response data, filled in during the drive, is captured.

Three conditions must all hold for a transaction to appear with its fields:

1. Recording is **enabled** on the component that calls `begin_tr()`.
2. Something tells `record()` **what to write**: field macros or a `do_record()`.
3. The component calls **`end_tr()`**, which records the fields and closes the transaction.

## Make It Work: Recording in Practice

To leverage recording effectively, you need to enable it, instrument the transaction, and instrument the component processing it.

### Step 0: Enable Recording on the Component

A component's `recording_detail` starts at `UVM_NONE`, so `get_recording_enabled()` returns 0. Enable it explicitly:

```sv
// IEEE 1800.2: in the component itself (or on it, from the test)
function void build_phase(uvm_phase phase);
  super.build_phase(phase);
  set_recording_enabled(1);
endfunction

// uvm-core library behaviour (also UVM 1.2 style): set recording_detail
// before the component is built, e.g. in the test's build_phase
uvm_config_db#(int)::set(this, "env.agt.*", "recording_detail", UVM_FULL);
```

The component reads `recording_detail` when it is constructed and when its `build_phase` applies configuration. A `config_db::set` made later (for example in `run_phase`) is never read.

### Step 1: Implement `do_record` in the Transaction

Just like `do_print` or `do_copy`, your transaction must define what fields are important to record by overriding the `do_record` method. This method receives a `uvm_recorder` object.

```sv
class axi_transfer extends uvm_sequence_item;
  rand bit [31:0] addr;
  rand bit [31:0] data;
  rand bit        is_read;

  `uvm_object_utils(axi_transfer)

  function new(string name = "axi_transfer");
    super.new(name);
  endfunction

  virtual function void do_record(uvm_recorder recorder);
    super.do_record(recorder);
    // The macros use the argument named 'recorder'
    `uvm_record_field("ADDR", addr)
    `uvm_record_field("DATA", data)
    `uvm_record_string("CMD", (is_read ? "READ" : "WRITE"))
  endfunction
endclass
```

If the class registers its fields with `` `uvm_field_* `` macros instead, `record()` writes them for you; do not record the same field in both places.

### Step 2: Demarcate the Transaction in the Component

In the component that executes or observes the transaction (like a driver or monitor), you must mark when the transaction begins and ends in simulation time. The base `uvm_component` provides the `begin_tr()` and `end_tr()` methods for this purpose. `accept_tr()` can be called before `begin_tr()` to mark when the component took ownership.

```sv
class axi_driver extends uvm_driver #(axi_transfer);
  // ... constructor and registration ...

  virtual task run_phase(uvm_phase phase);
    forever begin
      seq_item_port.get_next_item(req);

      // Start recording on stream "axi_driver_stream".
      // Returns 0 (and records nothing) while recording is disabled.
      void'(begin_tr(req, "axi_driver_stream"));

      // Drive physical signals (consume simulation time)
      drive_transaction(req);

      // Record the fields (calls req.record → do_record) and close the transaction.
      end_tr(req);

      seq_item_port.item_done();
    end
  endtask
endclass
```

> [!TIP]
> The UVM library only needs recording enabled on the component. To see the transactions in your waveform tool, the simulator must also connect its own `uvm_tr_database`; each vendor documents its own switch for that. Without it, uvm-core's default database writes a text file.

## Push Further: Telemetry and Structured Debug

Transaction recording bridges the gap between pure UVM logic and structured debug. While `uvm_info` statements are interspersed linearly in a text log, recorded transactions have rigid start/end times and hierarchical relationships.

This allows EDA tools to correlate a high-level `uvm_sequence_item` directly with the toggling of wires on a physical interface. When a sequence item has a parent sequence, `begin_tr()` links the two recorders (`uvm_parent_child_link`), so tools can show a parent transaction containing its children. The **Advanced UVM Debug Methodologies** module combines recording with report control to make large failures explainable.
