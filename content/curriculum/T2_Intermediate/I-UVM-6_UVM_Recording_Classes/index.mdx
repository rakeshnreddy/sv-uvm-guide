## Quick Take

- **What it is:** **Transaction recording** writes each transaction a component handles (its name, its start and end times, and its field values) into a **transaction database**, a store of timed records that a waveform viewer can draw as rows of boxes next to the signals. IEEE 1800.2-2020 defines the pieces: the database (`uvm_tr_database`, §7.1), **streams** that group records (`uvm_tr_stream`, §7.2), one **recorder** per record (`uvm_recorder`, §16.4), **links** between records (§7.3), and the component calls that drive them: `begin_tr`, `end_tr`, `record_error_tr` and `record_event_tr` (§13.1.7).
- **Why it matters:** A bus transfer that spans ten clocks is ten lines of text in a log, and you have to match them to the waveform by hand. A recorded transaction is one box on the waveform, aligned with the signals that carried it, showing its fields and the sequence that caused it. That is often the fastest way to see *which* transaction a failure belongs to.
- **The rule that bites:** recording is **off by default** on every component (§13.1.7.14). Until you enable it, `begin_tr` returns 0, opens nothing, and the database stays empty, however carefully you wrote `do_record`.
- **The Analogy:** A warehouse ledger. Each dock (a component) has its own pages in the shared ledger (its streams). When a dock starts handling a package (`begin_tr`), it opens a new line; when the package leaves (`end_tr`), it writes the package's contents on that line and closes it. A line can point to another ("this package belongs to that order": a parent/child link). *Where it breaks:* the ledger is switched off at every dock until someone switches it on; the contents are copied from the package at the moment it leaves, not as items go in; and the ledger's format belongs to the simulator, not to UVM.

**You will be able to:**
1. Explain the recording architecture (database, streams, recorders, attributes and links) and what a component's `begin_tr` and `end_tr` do to it.
2. Predict when nothing, or the wrong values, will be recorded: recording never enabled or enabled too late, nothing telling `record()` what to write, fields changed before `end_tr`, `end_tr` never called.
3. Write `do_record` and component `begin_tr`/`end_tr`/`record_error_tr`/`record_event_tr` calls that produce useful records with parent/child links, and control the sequencer's automatic item recording.
4. Choose what to record in long regressions, trading recording cost against debug value.

## Build Your Mental Model

**How to read this lesson.** The core path runs from why recording exists, through the architecture picture, to turning recording on and what `begin_tr`/`end_tr` write, then lets you test your predictions in the explorer. Practitioner depth follows: automatic recording by the sequencer, parent/child links, error and event records, the two kinds of database, and a table of common mistakes. Make It Work builds a complete recorded agent and reads its database line by line. Push Further holds the expert layer.

Words this lesson leans on, all from earlier lessons:
- A **transaction** is one complete operation, such as one bus write, held in an object. A **sequence item** is a transaction class derived from `uvm_sequence_item` that a **sequence** (a class that generates items) sends through a **sequencer** to a **driver**, which drives it onto the pins; a **monitor** watches the pins and builds a new transaction for each transfer it sees ([I-UVM-2A](/curriculum/T2_Intermediate/I-UVM-2A_Component_Roles/index)).
- `uvm_sequence_item` derives from `uvm_transaction` (§5.4), which carries begin and end times. That is why every sequence item can be recorded.
- A **policy** is a helper object that `print()`, `compare()` or `record()` passes to your `do_*` method. `record()` passes a `uvm_recorder`, and your `do_record()` writes fields into it ([I-UVM-4](/curriculum/T2_Intermediate/I-UVM-4_UVM_Policy_Classes/index)).
- **Phases** such as `build_phase` and `run_phase` are the fixed steps every component runs; `build_phase` creates children top-down, so a parent's `build_phase` runs before its children exist ([I-UVM-1C](/curriculum/T2_Intermediate/I-UVM-1C_UVM_Phasing/index)). `uvm_config_db` passes values from a parent to the components below it ([I-UVM-2C](/curriculum/T2_Intermediate/I-UVM-2C_Configuration_and_Resources/index)).
- A **waveform viewer** is the simulator's tool for drawing signals over time. Whether it can also draw transactions, and how you switch that on, depends on the simulator: this lesson labels such details **tool-dependent**.

### Why record transactions, and why recording does not replace logging

A report message such as `` `uvm_info `` writes one line of text at one instant. A recorded transaction is different in three ways:

| | Report message (`` `uvm_info ``, `` `uvm_error ``) | Recorded transaction |
|---|---|---|
| Time | one instant | a begin time and an end time |
| Content | a formatted string | typed fields (name, value, width, radix) |
| Relations | none | links to other records, such as the sequence that created an item |
| Where you read it | the log file | the transaction database, usually drawn in the waveform viewer |
| Decides pass or fail | yes: the report server counts errors | **no**: nothing counts records |

The last row is the misconception to avoid: **recording does not replace logging.** A test passes or fails on its report counts ([I-UVM-1D](/curriculum/T2_Intermediate/I-UVM-1D_Reporting_and_Run_Control/index)). Even an error record written with `record_error_tr` is invisible to the report server, so a monitor that sees a protocol error still reports it with `` `uvm_error `` and may *also* mark it in the database.

### The recording architecture: database, streams, recorders, links

Four kinds of object hold a recording. Each is an abstract class in the standard, and the database implementation supplies the concrete subclasses.

- **`uvm_tr_database`** (§7.1) is the store. Every component asks for one through `get_tr_database()` (§13.1.7.12), which by default returns the core service's default database (§13.1.7.11, F.4.1.4.6). In uvm-core 2020.3.1 that default is `uvm_text_tr_database`, which writes a text file named `tr_db.log`. Simulators supply their own database class so that the viewer can draw the records (tool-dependent).
- **`uvm_tr_stream`** (§7.2) is a named group of records, which a viewer usually draws as one row. A component opens one stream per stream name you pass it (`get_tr_stream`, §13.1.7.9), and the stream's **scope** is the component's full name. So `begin_tr(req, "drv")` in `uvm_test_top.env.agt.drv` writes to stream `drv` with scope `uvm_test_top.env.agt.drv`.
- **`uvm_recorder`** (§16.4) is two things at once: one **record** (one transaction) inside a stream, and the **policy** that writes the object's fields into that record. A stream creates it with `open_recorder` (§7.2.5.1). Each field becomes an **attribute** written with `record_field_int`, `record_string` and their siblings (§16.4.6).
- **Links** (§7.3) connect two records: `uvm_parent_child_link` (§7.3.2), `uvm_cause_effect_link` (§7.3.3) and `uvm_related_link` (§7.3.4), stored by `establish_link` (§7.1.5).

Every recorder has an integer **handle** (§16.4.5.1), a number that names the record. `begin_tr` returns it, and 0 means "nothing was opened".

### Turning recording on

Every component has a recording switch. **It is off until you turn it on** (§13.1.7.14: "If `set_recording_enabled` … has never been called for this component, the default is 0"). There are three ways to turn it on:

```systemverilog
// snippet: three ways to enable recording, from the test
// 1. One component (IEEE 1800.2 §13.1.7.13)
env.agt.drv.set_recording_enabled(1);

// 2. A component and everything below it (IEEE 1800.2 D.2.3)
env.agt.set_recording_enabled_hier(1);

// 3. uvm-core only: a "recording_detail" setting that the component reads
//    when it is created. Set it before the parent's build_phase creates it.
uvm_config_db#(int)::set(this, "env.agt.drv", "recording_detail", UVM_FULL);
```

Calls 1 and 2 work at any time after the component exists; in a test, `end_of_elaboration_phase` (the phase that runs after every component has been built and connected) is the natural place. Way 3 is **uvm-core behaviour**, not part of IEEE 1800.2. uvm-core keeps the switch in a member called `recording_detail` (default `UVM_NONE`, which means off) and reads a configuration setting of that name **only in the component's constructor** in its default configuration mode. A setting made after the component was created is never read, not even by its own `build_phase` (see the expert note on configuration mode). The command-line form, `+uvm_set_config_int=uvm_test_top.env.agt.drv,recording_detail,1` (G.2.8), works the same way.

**What "on" changes.** With recording off, `begin_tr` still sets the transaction's begin time and triggers its events, but it opens no recorder and returns 0, and `end_tr` writes nothing (§13.1.7.3, §13.1.7.5).

### What a component records, and when

A component brackets each transaction it handles with three calls from §13.1.7:

- **`accept_tr(tr)`** (§13.1.7.1), optional: marks when the component took the transaction. It sets the accept time and records nothing.
- **`begin_tr(tr, stream_name, label, desc, begin_time, parent_handle)`** (§13.1.7.3): marks the start. If recording is on, it opens a recorder on the stream `stream_name` (default `"main"`). **No fields are recorded at this time.** It returns the recorder's handle, or 0.
- **`end_tr(tr, end_time, free_handle)`** (§13.1.7.5): marks the end. If recording is on, it calls `tr.record(recorder)`, which writes the fields, then closes the recorder and (by default, `free_handle = 1`) frees it.

So the recorded values are the values **at `end_tr`**. Trace one READ through a driver to see why that matters. The driver fills `rdata` from the bus during the read.

| Time | Driver calls | `req.rdata` | Database (recording on) |
|---|---|---|---|
| 10 ns | `begin_tr(req, "drv")` returns 7 | 0 | record 7 opened at 10 ns, no fields yet |
| 10–30 ns | drives the read, samples the bus | `'h3c` from 30 ns | nothing |
| 30 ns | `end_tr(req)` | `'h3c` | `record()` writes `rdata = 3c` and the other fields; record 7 closed at 30 ns |
| 31 ns | `req.rdata = 0;` (a bug: reusing the item) | 0 | nothing: record 7 is already closed |

Two mistakes follow directly. If you never call `end_tr`, the record stays open and holds no fields. If you change a field *after* `end_tr`, the record keeps the old value; if you change it *before* `end_tr` (for example a response field filled late), the record shows the new one.

> **Who may call `begin_tr`?** Any component that produces or consumes the transaction: a driver, a monitor, a scoreboard, and the sequencer itself (next sections). `uvm_component::begin_tr` calls the transaction's own `uvm_transaction::begin_tr` (§5.4.2.4) to set its times; you do not call the transaction's method yourself. One transaction can be recorded by several components, each on its own stream.

### Telling the recorder what to write

`end_tr` calls `record()`, and `record()` writes only what the class tells it to: the fields registered with `` `uvm_field_* `` macros, then whatever your `do_record()` writes (§5.3.7). With neither, the record has times but no fields. In `do_record`, use the recording macros of Annex B.2.3:

```systemverilog
// snippet: do_record with the recording macros (IEEE 1800.2 B.2.3)
virtual function void do_record(uvm_recorder recorder);
  super.do_record(recorder);
  `uvm_record_int("addr", addr, $bits(addr), UVM_HEX)   // B.2.3.2
  `uvm_record_int("data", data, $bits(data), UVM_HEX)
  `uvm_record_string("kind", kind.name())                // B.2.3.3
endfunction
```

The macros expand to calls on the argument named `recorder` (`recorder.record_field_int`, `recorder.record_string`, §16.4.6), so keep that argument name. Prefer `` `uvm_record_int `` for integral fields: `` `uvm_record_field `` (B.2.3.6) passes the value through `record_generic` (§16.4.6.7), and uvm-core turns it into a `%p` string, so the text database loses its width and radix. Do not record the same field from both a field macro and `do_record`, or it appears twice.

### Sequences, items and automatic recording

The sequencer is a component too, so it can record. When its recording is on, it records two kinds of thing without any code from you:

- **Sequences.** A sequence's `start()` asks its sequencer to `begin_tr` the sequence; `end_tr` follows when the sequence finishes. A sequence started directly by the test (a **root sequence**) goes on a stream named after the sequence; a child sequence goes on its root sequence's stream, linked to its parent.
- **Items, by default.** IEEE 1800.2 calls this **automatic item recording** (§15.3.2.22): each item is recorded around the driver's `get_next_item` and `item_done`. uvm-core 2020.3.1 does it inside the sequence's `start_item`, right after the **grant** (the moment the sequencer lets this sequence send its item, because the driver has asked for one), and in `finish_item` after `item_done`. The records go on the root sequence's stream, with the label `"Transactions"`.

If your driver *also* calls `begin_tr`/`end_tr` on the items, and the sequencer's recording is on, every item is recorded **twice**: once on the sequencer's stream with the handshake times, and once on the driver's stream with the drive times. A driver that records items itself therefore turns automatic recording off, and IEEE 1800.2 says when: `disable_auto_item_recording()` "needs to be called prior to the driver initiating its first request for an item" (§15.2.1, §15.2.1.2.10). Once disabled, it cannot be re-enabled.

### Parent/child links

A **parent/child link** says "this record is part of that one", so a viewer can show a sequence containing its items. Records get one in three ways:

1. **The sequencer links them itself.** A child sequence's record, and an automatically recorded item's record, are linked to their parent sequence's record.
2. **A component's `begin_tr` looks up the parent sequence (uvm-core only).** If you pass no `parent_handle` and the transaction is a sequence item, uvm-core uses the record of the item's parent sequence. The header of `uvm_component::begin_tr` calls this "an added feature" beyond the standard. It works **only if that sequence was itself recorded**, which means the *sequencer's* recording is on. Enable recording on the driver alone, and the driver's records have no parent link.
3. **You pass `parent_handle` explicitly** (§13.1.7.3): `begin_tr(rsp, "drv", "", "", 0, req_handle)` links `rsp`'s record under the record whose handle is `req_handle`. This works in any implementation, as long as that handle is still valid: the parent record must not have been freed yet (uvm-core reports `ILLHNDL` for a handle that no longer names a recorder).

A monitor builds new transaction objects from the pins, so they have no parent sequence and get no automatic link. That is correct: the monitor reports what happened on the bus, not who asked for it.

### Error and event records

Two more component calls write a **zero-length record**, one whose begin and end times are the same, onto a stream (§13.1.7.7, §13.1.7.8):

```systemverilog
// snippet: marking an error and an event on the monitor's stream
void'(record_error_tr("mon", tr, "parity_error"));   // type "Error"; tr's fields
void'(record_event_tr("mon", null, "reset_released")); // type "Event"; no fields
```

The arguments are the stream name, an optional object whose fields are recorded (`info`, through its `do_record`), a label (defaults `"error_tr"` and `"event_tr"`), a description, a time (0 means now) and `keep_active`. With `keep_active = 0` (the default) the record is closed at once; with 1 the call returns a handle you can link to. A viewer can show these as markers on the stream, so a protocol error sits right on the transaction row where it happened. Remember the logging rule: an error record does not fail the test. Report the error with `` `uvm_error `` as well.

### Databases: the text file or the simulator's

- **uvm-core's default, `uvm_text_tr_database`** (uvm-core impl.), writes every stream, record, attribute and link as a line of text in `tr_db.log` in the run directory. It needs no tool support, so it is how you check recording code with any simulator. You read it in Make It Work.
- **A simulator's database** (tool-dependent) writes records into the simulator's own waveform database, so the viewer draws them as transaction rows. Each vendor documents its own switch for this; it may replace the default database for the whole run. The UVM code on this page does not change.

### Common mistakes

| Mistake | What you see | Why |
|---|---|---|
| Recording never enabled | empty stream; `begin_tr` returns 0 | off by default (§13.1.7.14) |
| `recording_detail` set after the component was created | empty stream | uvm-core reads it only in the constructor |
| No field macros and no `do_record` | records with times but no fields | `record()` has nothing to write |
| `end_tr` never called | records that never close, with no fields | fields are written in `end_tr` |
| A field changed after `end_tr` | old value in the record | the record was closed |
| Driver records items, automatic recording still on | every item twice, on two streams | the sequencer records them too |
| Only the driver's recording enabled | no parent links | the parent sequence was never recorded |
| `` `uvm_record_field `` on integral fields | values as strings, no radix (text database) | it records `%p` through `record_generic` |
| Recording used instead of `` `uvm_error `` | a failure that passes | nothing counts records |

### Recap

- The database holds streams, streams hold one recorder per transaction, recorders hold attributes, and links connect recorders.
- Recording is off on every component until `set_recording_enabled(1)`, `set_recording_enabled_hier(1)`, or (uvm-core) a `recording_detail` setting made before the component is created.
- `begin_tr` opens a record with no fields; `end_tr` writes the fields and closes it.
- `record()` writes only what field macros and `do_record` tell it to.
- A driver that records items calls `disable_auto_item_recording()` before its first `get_next_item`; automatic parent links need the sequence to be recorded.
- `record_error_tr` and `record_event_tr` add zero-length markers; they do not replace reports.

## Make It Work

### A recorded agent: sequencer, driver and monitor on three streams

The example is a one-agent testbench on a tiny bus: `valid` is high for one clock per transfer, and `parity` makes `{addr, data, parity}` even. The test enables recording on the whole agent and injects one parity error on purpose. Because that error is expected, the test applies a **severity override** that turns the monitor's `PARITY` error reports into info messages ([I-UVM-1D](/curriculum/T2_Intermediate/I-UVM-1D_Reporting_and_Run_Control/index)). It also sets a **drain time**, extra time the run phase keeps going after the last objection is dropped ([I-UVM-1C](/curriculum/T2_Intermediate/I-UVM-1C_UVM_Phasing/index)), so the monitor can close its last record. Values are fixed rather than random so that the logs below are reproducible. Save it as `tb_top.sv`.

```systemverilog
// compile
`timescale 1ns/1ps
`include "uvm_macros.svh"

interface bus_if (input logic clk);
  logic       rst_n;
  logic       valid;
  logic [7:0] addr;
  logic [7:0] data;
  logic       parity;  // even parity over addr and data

  clocking drv_cb @(posedge clk);
    output valid, addr, data, parity;
  endclocking

  clocking mon_cb @(posedge clk);
    input rst_n, valid, addr, data, parity;
  endclocking
endinterface

package rec_pkg;
  import uvm_pkg::*;
  `include "uvm_macros.svh"

  class bus_item extends uvm_sequence_item;
    rand bit [7:0] addr;
    rand bit [7:0] data;
    bit            bad_parity;  // 1: the parity bit on the bus is wrong

    `uvm_object_utils(bus_item)

    function new(string name = "bus_item");
      super.new(name);
    endfunction

    // record() calls this inside end_tr: it decides what a record carries.
    virtual function void do_record(uvm_recorder recorder);
      super.do_record(recorder);
      `uvm_record_int("addr", addr, 8, UVM_HEX)
      `uvm_record_int("data", data, 8, UVM_HEX)
      `uvm_record_int("bad_parity", bad_parity, 1, UVM_BIN)
    endfunction

    virtual function string convert2string();
      return $sformatf("addr='h%02h data='h%02h", addr, data);
    endfunction
  endclass

  class bus_seq extends uvm_sequence #(bus_item);
    `uvm_object_utils(bus_seq)

    function new(string name = "bus_seq");
      super.new(name);
    endfunction

    task body();
      for (int i = 0; i < 3; i++) begin
        // Named items make the records easy to find: item0, item1, item2.
        req = bus_item::type_id::create($sformatf("item%0d", i));
        start_item(req);
        req.addr       = 8'h10 + 8'(i * 4);
        req.data       = 8'ha0 + 8'(i);
        req.bad_parity = (i == 2);  // inject one parity error on purpose
        finish_item(req);
      end
    endtask
  endclass

  class bus_driver extends uvm_driver #(bus_item);
    `uvm_component_utils(bus_driver)
    virtual bus_if vif;

    function new(string name, uvm_component parent);
      super.new(name, parent);
    endfunction

    function void build_phase(uvm_phase phase);
      super.build_phase(phase);
      if (!uvm_config_db#(virtual bus_if)::get(this, "", "vif", vif))
        `uvm_fatal("NOVIF", "bus_driver: vif not set")
    endfunction

    task run_phase(uvm_phase phase);
      // This driver records items itself, so the sequencer must not record
      // them too. The call must come before the first get_next_item.
      seq_item_port.disable_auto_item_recording();
      vif.drv_cb.valid <= 1'b0;
      wait (vif.rst_n === 1'b1);
      forever begin
        seq_item_port.get_next_item(req);
        @(vif.drv_cb);
        void'(begin_tr(req, "drv"));  // opens a record: times only, no fields
        vif.drv_cb.valid  <= 1'b1;
        vif.drv_cb.addr   <= req.addr;
        vif.drv_cb.data   <= req.data;
        vif.drv_cb.parity <= ^{req.addr, req.data} ^ req.bad_parity;
        @(vif.drv_cb);
        vif.drv_cb.valid  <= 1'b0;
        end_tr(req);                  // writes the fields, closes the record
        seq_item_port.item_done();
      end
    endtask
  endclass

  class bus_monitor extends uvm_monitor;
    `uvm_component_utils(bus_monitor)
    virtual bus_if vif;
    uvm_analysis_port #(bus_item) ap;

    function new(string name, uvm_component parent);
      super.new(name, parent);
    endfunction

    function void build_phase(uvm_phase phase);
      super.build_phase(phase);
      ap = new("ap", this);
      if (!uvm_config_db#(virtual bus_if)::get(this, "", "vif", vif))
        `uvm_fatal("NOVIF", "bus_monitor: vif not set")
    endfunction

    task run_phase(uvm_phase phase);
      bus_item tr;  // the transfer whose record is open, or null
      do @(vif.mon_cb); while (vif.mon_cb.rst_n !== 1'b1);
      void'(record_event_tr("mon", null, "reset_released"));
      forever begin
        @(vif.mon_cb);
        // Close the record opened one clock ago. Each monitor record spans
        // the clock after the edge where the transfer was sampled.
        if (tr != null) begin
          end_tr(tr);
          tr = null;
        end
        if (vif.mon_cb.valid === 1'b1) begin
          tr = bus_item::type_id::create("mon_item");  // new object per transfer
          tr.addr       = vif.mon_cb.addr;
          tr.data       = vif.mon_cb.data;
          tr.bad_parity = ((^{tr.addr, tr.data}) != vif.mon_cb.parity);
          void'(begin_tr(tr, "mon"));
          if (tr.bad_parity) begin
            // The report decides pass/fail; the error record marks the spot.
            `uvm_error("PARITY", {"parity error: ", tr.convert2string()})
            void'(record_error_tr("mon", tr, "parity_error"));
          end
          ap.write(tr);
        end
      end
    endtask
  endclass
```

### Read the database

Each line kind comes from uvm-core's text backend (`uvm_text_tr_stream.svh`, `uvm_text_recorder` in `uvm_recorder.svh`, `uvm_text_tr_database.svh`):

| Line | Written by | In this run |
|---|---|---|
| `CREATE_STREAM` | the first `begin_tr`, `record_error_tr` or `record_event_tr` on a stream name | three streams: `seq` (sequencer), `mon`, `drv` |
| `OPEN_RECORDER` | `begin_tr` (and the error and event calls) | `TIME` is the record's begin time; `TYPE` is `Begin_End, Link` when the record has a parent, `Begin_No_Parent, Link` otherwise, or `Error`/`Event` |
| `LINK ... RELATION=child` | a parent/child link | `TXH1` is the parent (the sequence, handle 2), `TXH2` the child |
| `SET_ATTR` | `record()` inside `end_tr`, or a `label` argument | written at the end time (`@35`), not the begin time: the fields are recorded in `end_tr` |
| `CLOSE_RECORDER`, `FREE_RECORDER` | `end_tr` with the default `free_handle = 1` | |

Now trace what the run shows:

1. **The sequence is recorded from 0 to 75 ns** on stream `seq`, because the sequencer's recording is on. Its record holds only `inst_id`, because `bus_seq` records no fields.
2. **Each item appears once, on `drv`**, from the edge where it is driven (25 ns) to the next edge (35 ns), with a `LINK` to the sequence. No item appears on stream `seq`, because the driver disabled automatic item recording.
3. **The monitor's records trail the driver's by one clock** (35 to 45 ns for the first transfer): it samples a transfer at the edge after it was driven, and closes the record one clock later. That offset is sampling, not a bug.
4. **The monitor's records have no `LINK`**: a monitor builds new objects with no parent sequence.
5. **The parity error is a zero-length `Error` record** at 75 ns on stream `mon`, carrying the transfer's fields. The report summary still shows `UVM_ERROR :    0` only because the test demoted that one ID; without the demotion the test would fail, as it should.

### How to add recording to an agent

1. In each item class, write `do_record` with `` `uvm_record_int `` and `` `uvm_record_string `` (or register the fields with field macros, not both).
2. In the driver, decide who records items. If the driver does, call `seq_item_port.disable_auto_item_recording()` at the start of `run_phase`, before the first `get_next_item`, and bracket each item with `begin_tr(req, "drv")` when it starts on the pins and `end_tr(req)` after the last field (including any response data) is filled.
3. In the monitor, bracket each new transaction with `begin_tr(tr, "mon")`/`end_tr(tr)`, and mark protocol errors with `record_error_tr` **as well as** `` `uvm_error ``.
4. In the test, enable recording only where you need it: `set_recording_enabled_hier(1)` on the agent in `end_of_elaboration_phase`, ideally behind a configuration knob that is off by default.
5. Make sure the run does not end with records open: give the last transaction time to close (a drain time, or end the test from the monitor's side).
6. Run once with uvm-core's text database and read `tr_db.log` before relying on the viewer.

| Symptom | Likely cause | Fix |
|---|---|---|

| Same, although a `recording_detail` setting exists | the setting was made after the component was created, or its path does not match | set it before the parent's `build_phase` creates the component; print the path; or call `set_recording_enabled` |
| Records have times but no fields | no field macros and no `do_record` | add `do_record` with the recording macros |
| A response field shows its old value | `end_tr` was called before the field was filled | move `end_tr` after the last assignment |

## Push Further

### Expert: choosing what to record in long regressions

Recording costs simulation time (a call into the database for every record and attribute) and disk space, and the cost grows with traffic. How much depends on the simulator and its database: **tool-dependent**, so measure it with your simulator's profiler rather than trusting a rule of thumb. The trade-off is against debug value, which is high only when someone will open the database. A sound policy:

- **Off by default in regressions.** Thousands of passing seeds produce databases nobody reads. Make recording a test knob (a configuration field or your own plusarg) that defaults to 0.
- **On for reruns of failing seeds**, and then only for the agents near the failure: `set_recording_enabled_hier(1)` on one agent, not on `uvm_test_top`. In uvm-core, `+uvm_set_config_int=uvm_test_top.env.agt.*,recording_detail,1` (G.2.8) does the same from the command line, because the agent's children are created after the command-line settings are applied.
- **Record transactions, not internals.** Record the fields a person will look at on the waveform; leave out large arrays and derived values that the viewer can show from signals.
- **Close and free promptly.** Keep the default `free_handle = 1` in `end_tr` unless you need the handle later (for a link). An unfreed recorder stays in uvm-core's static handle table, so its memory is never reclaimed (§13.1.7.5, §16.4.4.3; `uvm_recorder.svh`).
- **Watch the stream count.** A sequencer opens one stream per root-sequence name, so a test that starts thousands of uniquely named root sequences (`$sformatf("seq_%0d", i)`) creates thousands of streams. Reuse names, or record the sequences on fewer agents.

### Expert: automatic item recording, pipelined drivers and the "end" event

IEEE 1800.2 places automatic item recording around `get_next_item` and `item_done` (§15.3.2.22); uvm-core 2020.3.1 does it in `start_item` after the grant and in `finish_item` after `item_done`. Either way it marks the handshake, not the time the item spends on the pins. For a simple in-order driver the two are close; for a **pipelined** driver, which calls `item_done` as soon as the address phase is accepted and finishes the data phase later, the automatic record ends too early. §15.2.1 gives the rule: such a driver calls `disable_auto_item_recording()` before its first request and calls `begin_tr`/`end_tr` itself at the right moments. A sequence that must wait until the item has really finished waits on the item's `"end"` event (`get_event_pool()`, §5.4.2.13), which `end_tr` triggers. uvm-core also accepts a compile-time define, `UVM_DISABLE_AUTO_ITEM_RECORDING`, that turns automatic item recording off globally (uvm-core impl.).

### Expert: component-level versus transaction-level recording

Everything on this page is **component-level** recording (§13.1.7): the component owns the streams and decides. A `uvm_transaction` can also record itself: `enable_recording(stream)` (§5.4.2.9) points it at a stream, and its own `begin_tr`/`end_tr` then open and close records there. The two differ in when fields are written. §5.4.2.4 says the transaction-level `begin_tr` records the current property values at begin; uvm-core 2020.3.1 records them only in `end_tr`, like the component path. Label any code that depends on begin-time values as implementation-dependent. Component-level recording is the norm in UVM testbenches because the test can switch it per component.

### Expert: links beyond parent/child

§7.3 defines three link classes, each created with a static `get_link(lhs, rhs)` and stored with the database's `establish_link` (§7.1.5): `uvm_parent_child_link` (§7.3.2, containment), `uvm_cause_effect_link` (§7.3.3, "this caused that", for example a request and its response) and `uvm_related_link` (§7.3.4). You need the recorders, which you get from handles with `uvm_recorder::get_recorder_from_handle` (§16.4.5.2). Two uvm-core facts to know: the automatic parent lookup in `begin_tr` is a uvm-core addition, and **the text database writes `LINK` lines only for parent/child and related links**; it drops a cause/effect link silently (`uvm_text_tr_database::do_establish_link`). A simulator's database may keep all three (tool-dependent). Where portability matters, pass `parent_handle` to `begin_tr` explicitly.

### Expert: when uvm-core reads recording_detail

uvm-core 2020.3.1 compiles `uvm_component::apply_config_settings` in `CONFIG_CHECK_NAMES` mode by default (`uvm_global_defines.svh`; the source calls it "a divergence from 1800.2", and `DEVIATIONS.md` item 3 explains it). In that mode `build_phase` applies only the names reported by field macros, and `uvm_component` reports none, so the `recording_detail` setting is read only by the constructor's own lookup. Compiled with `+define+UVM_COMPONENT_CONFIG_MODE_DEFAULT=CONFIG_STRICT`, `build_phase` applies it as well. The portable rule is simple: call `set_recording_enabled`, which IEEE 1800.2 defines and which works whenever you call it.

### Expert: error and event records ignore the enable (uvm-core)

In uvm-core 2020.3.1, `record_error_tr` and `record_event_tr` open their stream and write the record **without checking `get_recording_enabled()`** (`uvm_component.svh`), so they appear in `tr_db.log` even on a component whose recording is off. §13.1.7.7 and §13.1.7.8 do not state an enable condition either. If error markers must stay out of disabled runs, guard the calls with `if (get_recording_enabled())`.

### Expert: the database plumbing

- **Per component:** `set_tr_database(db)` (§13.1.7.11) makes one component record into a different database; `get_tr_database()` (§13.1.7.12) returns it.
- **For the run:** `uvm_coreservice_t::get().set_default_tr_database(db)` (F.4.1.4.7) changes the default for components that have not asked yet. This is the hook a simulator's database uses.
- **A custom database** extends `uvm_tr_database` and implements its protected `do_*` methods (§7.1.6), with matching `uvm_tr_stream` and `uvm_recorder` subclasses, for example to write records to a file format your own tools read.
- **`` `uvm_record_attribute ``** (B.2.3.1) hides a tool-specific attribute call. A recorder whose `use_record_attribute()` returns 1 (§16.4.6.8) routes the recording macros through it; the default returns 0. uvm-core maps the macro to a simulator system task only under a vendor-specific define (tool-dependent).

### Expert: uvm-core text database details

- **Append mode.** `uvm_text_tr_database` opens `tr_db.log` with `$fopen(..., "a+")`, so reruns in one directory pile up in one file.
- **File name.** `set_file_name("my_tr.log")` changes it, but only before the database opens (the first record); afterwards uvm-core warns `UVM/TXT_DB/SET_AFTER_OPEN` and ignores the call. Cast the default database to `uvm_text_tr_database` in the test's `build_phase` to call it.
- **Line kinds:** `CREATE_STREAM`, `CLOSE_STREAM`, `FREE_STREAM`, `OPEN_RECORDER`, `SET_ATTR`, `CLOSE_RECORDER`, `FREE_RECORDER` and `LINK`. These names are uvm-core's, not the standard's; scripts that parse them are tied to uvm-core.
- **`inst_id`.** Each record starts with an `inst_id` attribute, the object's instance id, because recorders record ids by default (`set_id_enabled`, §16.4.2.2).

### Kata: record an agent and read its database

Take the Make It Work testbench (or your own one-agent bench) and do the following.

1. Enable recording on the agent from the test, in the phase where every component exists.
2. Record driver items on stream `drv`, with the automatic parent-sequence link, and with no duplicate copies on the sequencer's stream.
3. Record monitor transactions on their own stream `mon`.
4. Mark a parity error with `record_error_tr`, and keep the `` `uvm_error `` report.
5. Run with uvm-core's text database and answer from `tr_db.log`:
   - (a) How many streams are there, and which component owns each?
   - (b) Which record is the child of which?
   - (c) At what time were the attributes of `item0` written, and why that time?
   - (d) What changes in the file if you remove the `disable_auto_item_recording()` call?
   - (e) What changes if you enable recording on `env.agt.drv` and `env.agt.mon` only?

<details className="my-4 rounded-xl border border-border/70 p-3">
<summary className="cursor-pointer font-semibold">Show the worked solution</summary>

1. In `end_of_elaboration_phase`: `env.agt.set_recording_enabled_hier(1);`. The agent's sequencer, driver and monitor all exist by then.
2. In the driver's `run_phase`, call `seq_item_port.disable_auto_item_recording();` first, then `begin_tr(req, "drv")` when the item starts on the pins and `end_tr(req)` after the drive. The parent link is automatic in uvm-core because the sequencer's recording is on, so it records the sequence.
3. In the monitor: `begin_tr(tr, "mon")` when a transfer is seen, `end_tr(tr)` when its record should close (one clock later in the example).
4. Next to the `` `uvm_error ``: `void'(record_error_tr("mon", tr, "parity_error"));`.
5. Answers, from the example's file:
   - (a) Three: `seq` (scope `...agt.sqr`), `mon` (`...agt.mon`) and `drv` (`...agt.drv`). Each `CREATE_STREAM` line names the scope.
   - (b) Each `item` record on `drv` is the child of the `seq` record: `LINK ... TXH1:2 TXH2:6 RELATION=child`, where handle 2 is the sequence. Monitor records and the `Error` record have no links.
   - (c) At 35 ns, the `@35` on its `SET_ATTR` lines, although the record began at 25 ns: fields are written inside `end_tr`.
   - (d) Each item also appears on stream `seq`, with the label attribute `Transactions` and the handshake times (from the grant in `start_item` to the return of `finish_item` in uvm-core), linked to the sequence.
   - (e) Stream `seq` disappears, and the `drv` records lose their `LINK` lines: with the sequencer's recording off, the sequence is never recorded, so there is no parent record. The `mon` records are unchanged.

### Debug challenge: three broken configurations

Each configuration below breaks the example in one way. Name the cause from the symptom alone, then check your answer.

1. The test calls `uvm_config_db#(int)::set(this, "env.agt.*", "recording_detail", 1);` in its `run_phase`, and deletes the `set_recording_enabled_hier` call. Symptom: `tr_db.log` holds only the `reset_released` event and the `parity_error` record.
2. The driver is changed to call `end_tr(req)` before it fills a new response field `req.status` from the bus. Symptom: `status` is always 0 in the records, but correct in the scoreboard.
3. The `disable_auto_item_recording()` call is moved to just after the first `get_next_item`. Symptom: on stream `seq`, an `item0` record opens and never closes, with no fields; on `drv`, all three items look normal.

<details className="my-4 rounded-xl border border-border/70 p-3">
<summary className="cursor-pointer font-semibold">Show the worked solution</summary>

1. The setting is made after every component was created, and uvm-core reads `recording_detail` only in the constructor, so recording stays off. The two records that do appear come from `record_event_tr` and `record_error_tr`, which uvm-core writes without checking the enable. Fix: `set_recording_enabled_hier(1)` in `end_of_elaboration_phase`, or the `set` in the test's `build_phase`.
2. The fields are written inside `end_tr`, so a field filled afterwards is never recorded. The scoreboard sees the final object because it receives the handle. Fix: call `end_tr` after the last field is filled.
3. Automatic item recording was still on when `start_item` was granted for `item0`, so the sequencer opened a record for it. By the time `finish_item` checked again, recording had been disabled, so the sequencer never called `end_tr` and the record stayed open (uvm-core `start_item`/`finish_item`). The standard requires the call before the driver's first request (§15.2.1). Fix: call it first in `run_phase`.

</details>
