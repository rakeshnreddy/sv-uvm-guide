## Quick Take

- **What it is:** In [I-SV-3A](/curriculum/T2_Intermediate/I-SV-3A_Functional_Coverage_Fundamentals/index) you wrote covergroups. This module turns them into a **closure process**. Each coverage item carries the ID of the verification-plan row it measures, the testbench reads coverage while it runs, and every **hole** (a bin hit fewer than `option.at_least` times, 1 by default) is explained and acted on until the plan's goals are met within a budget of seeds or transactions.
- **Why it matters:** Coverage is the evidence that the planned scenarios *happened*. Checks (a scoreboard compare, an assertion) are the evidence that the design behaved *correctly* in them. A project signs off only when both are complete for every plan row. Milestone M4 (a coverage-driven environment with a closure loop) is gated on this module, and the classic escapes happen exactly where people confuse the two, or exclude a hole to reach a number.
- **The Analogy:** A flight-test campaign. The test plan lists the manoeuvres; the flight log (coverage) records which ones were flown; the instruments and the inspector (checks) decide whether the aircraft behaved. *Where it breaks:* a test pilot can be ordered to fly a manoeuvre, but random stimulus cannot. You change probabilities or write a directed test, and some manoeuvres are impossible on this aircraft (unreachable) or forbidden by the rules (illegal).

**You will be able to:**
1. **Explain** why a covered plan row is not a verified one, and **decide** whether a row is closed from its coverage items and its checks.
2. **Design** where each piece of a closure-capable testbench lives (collector, checker, stimulus, stop decision), and **justify** ending stimulus at the coverage goal or the budget without skipping a single check.
3. **Write** a run-time closure loop that samples once per checked transaction, polls `get_inst_coverage(covered, total)` and switches a stimulus knob when a cross stops growing, and **predict** why `get_coverage()` is the wrong call for that poll.
4. **Classify** a coverage hole as forbidden, unreachable, under-stimulated or unobserved, and **choose** the matching action.
5. **Predict** whether a seed or transaction budget can close a rare bin, using P(hit) = 1 − (1 − p)^N, and **choose** between more seeds and steering.

## Build Your Mental Model

**How to read this page.** The core path is the first four sections: the words, the evidence rule, the loop, and where each piece lives. Make It Work assembles them into one self-checking bench that steers itself. Push Further holds the expert corner cases; the sub-lessons hold the depth.

### The words this module uses

You met covergroups, coverpoints, crosses and bins in I-SV-3A. Six more words carry this module:

| Term | Meaning |
|---|---|
| **Verification plan (vplan)** | The document that lists what must be verified: each feature, the scenarios that exercise it, how correctness is checked, and the coverage goal. "Vplan" after first use. |
| **Plan row** | One line of the vplan with a stable ID, such as `ALU-4`: "every operation with `a` at each edge value". |
| **Coverage item** | A coverpoint or a cross. Items carry options such as `option.comment` and `option.goal`; individual bins do not (IEEE 1800-2023 §19.7, Table 19-2). |
| **Check** | Code that compares what the design under test (DUT) did with what it should do: a scoreboard compare against a **reference model** (code that computes the expected result), or an assertion. |
| **Hole** | A bin whose hit count is below `option.at_least` (default 1), so it does not count as covered (Table 19-1). |
| **Closure** | The state where every plan row has met its coverage goal *and* its checks ran on those scenarios without failing, or where each remaining hole carries a reviewed, written justification. |

Four more appear in the loop. A **seed** is the number that starts the simulator's random generator, so a new seed is a new random run of the same test ([I-SV-2B](/curriculum/T2_Intermediate/I-SV-2B_Advanced_Constrained_Randomization/randomization-methods)). A **regression** is a batch of such runs whose coverage your tool merges into one report. **Steering** means changing the stimulus on purpose (weights, a mode, a directed test) to reach a hole. A **budget** is the number of seeds or transactions you can afford to spend.

### Coverage measures, checks verify

A covergroup counts sampled values into bins (§19.5) and computes its percentage from covered bins and weights (§19.11). Nothing in that computation knows what the right answer was. **Coverage records that a scenario was observed; only a check can say whether the design got it right.** If a covergroup samples the DUT's inputs, a wrong result changes nothing; if it samples outputs, a wrong result is counted exactly like a right one.

Read the picture as a 2×2: is the scenario covered, and was it checked?

**The pairing rule.** Every scenario row in the vplan has at least one coverage item *and* at least one check. A check-only row, such as "the result always matches the reference model", has no coverage item of its own: it names the scenario rows whose coverage shows which inputs reached the check. This is the plan this whole module uses:

| Row | Scenario or rule | Coverage item | Check |
|---|---|---|---|
| ALU-1 | every operation (ADD, SUB, MUL, DIV, AND, OR, XOR) | `cp_op` | ALU-6 compare |
| ALU-2 | `a` at its edge values 0 and `8'hFF` | `cp_a` | ALU-6 compare |
| ALU-3 | `b` at its edge values | `cp_b` (lab) | ALU-6 compare |
| ALU-4 | every operation with each edge of `a` | `x_op_a` | ALU-6 compare |
| ALU-5 | DIV with `b == 0` is forbidden by the spec | `illegal_bins` in `x_op_b` (lab) | the constraint, plus a forbidden-input check |
| ALU-6 | the result `y` always equals the reference model | none: exercised by ALU-1 to ALU-5 | `y !== alu_model(...)` in `tb_top` |

**A traced example.** Suppose the DUT has a bug: SUB computes `b - a` instead of `a - b`. The covergroup samples `op` and `a` (inputs), so it counts the same bins whether the result is right or wrong:

| # | op | a | b | DUT `y` (bug: b − a) | `alu_model` | ALU-6 check | Bins hit |
|---|---|---|---|---|---|---|---|
| 1 | SUB | `8'h00` | `8'h05` | `8'h05` | `8'hFB` | **FAIL** | `ops[SUB]`, `zero`, ⟨SUB, zero⟩ |
| 2 | ADD | `8'hFF` | `8'h01` | `8'h00` | `8'h00` | pass | `ops[ADD]`, `max`, ⟨ADD, max⟩ |
| 3 | SUB | `8'hFF` | `8'hFF` | `8'h00` | `8'h00` | pass | `ops[SUB]`, `max`, ⟨SUB, max⟩ |
| 4 | SUB | `8'h10` | `8'h03` | `8'hF3` | `8'h0D` | **FAIL** | `ops[SUB]` only (`a` is in no bin) |

After four transactions coverage is the same with or without the bug: `cp_op` 2/7, `cp_a` 2/2, `x_op_a` 3/14. Only the check column knows. Row 3 shows the other half of the rule: a check catches a bug only with data that exposes it (`a == b` hides this one), which is why the plan pairs checks with coverage of interesting values.

**`illegal_bins` is not a checker.** An illegal bin raises a run-time error when its covergroup instance samples a forbidden value (§19.5.6). It sees only the values that covergroup samples, only while the covergroup exists and is sampled, and its error is a simulator error, not a UVM report. Behaviour after `stop()` or a tool's coverage-off switch is tool-dependent. Use it as a second line of defence beside a constraint and a real check, never instead of them.

**Pitfalls.**
- *"100% coverage, so the design is verified."* Coverage has no expected values (§19.11). The SUB bug above leaves every number unchanged.
- *"The scoreboard reported zero mismatches, so the row is closed."* Zero comparisons also produce zero mismatches. A row closes when its coverage shows the scenarios reached the check and the check passed them.
- *"Exclude the empty bin and the row is done."* An exclusion removes a bin from the denominator; the scenario still never ran. That is acceptable only for a forbidden or unreachable scenario, with a written reason.

**Debugging the evidence.** When a row looks closed but a bug escaped, read the log for two signatures: the check's own pass count (did it ever compare this scenario?) and the coverage per plan row (did the scenario happen?). A row with high coverage and a check count of zero is the false-confidence quadrant. A planted bug that changes no `FAIL` count means the check cannot see it.

**In a real testbench.** The scoreboard and assertions own correctness, the coverage collector owns "did it happen", and the vplan pairs them row by row. Sign-off reviews both lists, plus code coverage (introduced in F1B; how it complements functional coverage is in [The Coverage Closure Loop](/curriculum/T2_Intermediate/I-SV-3B_Advanced_Functional_Coverage/closure-workflow)). Interviewers ask this as "you hit 100% coverage and a bug escaped: how?". Push Further lists the answers.

Each step has a page:
- **Plan and model** (the top row): every coverage item carries its row's ID, so a report reads row by row. Depth: [Linking Coverage to the Plan](/curriculum/T2_Intermediate/I-SV-3B_Advanced_Functional_Coverage/linking-coverage).
- **Read**: the testbench can query coverage while it runs (`get_inst_coverage()`, `get_coverage()`, §19.8), and a regression's results are merged into one database by your tool. Depth: [Coverage APIs](/curriculum/T2_Intermediate/I-SV-3B_Advanced_Functional_Coverage/coverage-apis).
- **Classify and act**: every hole falls into one of four classes, and the class decides the action. Depth: [The Coverage Closure Loop](/curriculum/T2_Intermediate/I-SV-3B_Advanced_Functional_Coverage/closure-workflow).

**The four hole classes** (core summary; the closure page has the full method, waivers and a debugging table):

| Class | What it means | Action |
|---|---|---|
| **Forbidden** | The spec says it must never happen (ALU-5: DIV with `b == 0`) | `illegal_bins`, the constraint that prevents it, and a check. Never `ignore_bins`. |
| **Unreachable** | Legal in the spec, impossible in this design or configuration | A justified exclusion or waiver, with the reason and a reviewer recorded |
| **Under-stimulated** | Legal and reachable, but rare or never generated (a constraint bug gives probability 0) | Fix the constraint, bias the stimulus, or write a directed test |
| **Unobserved** | It happened, but coverage missed it (the collector was not fed, sampled the wrong value, or was stopped) | Fix the collector or the sampling, not the stimulus |

**Budgets: why "more seeds" is not a plan.** If one sample hits a bin with probability p, the chance that N samples hit it at least once is P = 1 − (1 − p)^N. The average wait, 1/p samples, gives only about 63%; a 95% chance needs about 3/p (exactly ln 20 / p for small p). A probability-0 bin never closes. With the ALU, one operation with `a == 0` has p ≈ 1/1792 when `a` is uniform, and about 1/28 when half of the `a` values are steered to the two edges:

| Per-sample probability p | Hit within 500 | Within 1,500 | Samples for 95% |
|---|---|---|---|
| ≈ 1/1792 (uniform `a`) | 24.4% | 56.7% | ≈ 5,370 |
| ≈ 1/28 (steered `a`) | ≈ 100% | ≈ 100% | ≈ 83 |

All 14 cells of `x_op_a` must close, which is harder still: at 1/1792 per cell, 1,500 samples close all 14 with probability 0.035%, and a 95% chance needs about 10,050; steered to 1/28, about 155 samples give 95%. When the 95% figure is larger than your budget, steer.

Two rules follow from the picture. The collector samples each transaction exactly once, after the transaction exists, and does not decide anything. And the stop decision belongs to the code that can see the checks: a collector that calls `$finish` at 100% ends the simulation at once (§20.2), so in-flight transactions are never compared and, in UVM, the check and report phases never run.

### Mistakes everyone makes

1. **"100% functional coverage means the design is verified."** It means every planned scenario was sampled at least `at_least` times. Correctness comes only from checks mapped to the same rows.
2. **"`get_coverage()` returns this collector's coverage."** It returns the **type** coverage: by default the weighted average over every instance of that covergroup type (§19.8, §19.11.3). For one collector's number, call `get_inst_coverage()`.
3. **"Closure means running more seeds."** More seeds never close a probability-0 bin and close a rare one only slowly (3/p for 95%). Classify first; steer when the budget is too small.
4. **"Excluding a bin is as good as covering it."** An exclusion removes the bin from the denominator; the scenario still never ran. Exclude only forbidden or unreachable scenarios, with a recorded reason.

## Make It Work

### A closure loop that checks every transaction

This bench puts every core idea of the module into one file. It randomizes ALU transactions, checks each result against a reference model (ALU-6), samples coverage once per checked transaction, polls the `x_op_a` cross every 50 transactions, switches on a steering knob when the cross stops growing, and stops creating stimulus when every coverage item reaches its goal or the budget of 1,500 transactions is spent. The report prints one line per plan row, reading the plan ID from each item's `option.comment`.

```systemverilog
// compile
// alu_closure.sv: one file. Top level: tb_top.
package alu_pkg;
  typedef enum bit [2:0] {ADD, SUB, MUL, DIV, AND, OR, XOR} op_t;

  // Reference model for plan row ALU-6: what the spec says y must be.
  function automatic bit [7:0] alu_model(op_t op, bit [7:0] a, bit [7:0] b);
    case (op)
      ADD:     return a + b;
      SUB:     return a - b;
      MUL:     return a * b;   // low byte of the product
      DIV:     return a / b;   // b == 0 never gets here: ALU-5 forbids it
      AND:     return a & b;
      OR:      return a | b;
      default: return a ^ b;   // XOR
    endcase
  endfunction

  class alu_txn;
    rand op_t      op;
    rand bit [7:0] a;
    rand bit [7:0] b;
    bit            corner_mode;  // not rand: the test sets it to steer a

    // ALU-5: the spec forbids divide by zero, so the generator never sends it.
    constraint c_spec { op == DIV -> b != 8'h00; }
    // The steering knob: in corner mode, a is 0 or 8'hFF half of the time.
    constraint c_corner {
      if (corner_mode) a dist {8'h00 := 1, 8'hFF := 1, [8'h01:8'hFE] :/ 2};
    }
  endclass

  // Coverage collector: one covergroup, one plan ID per item.
  class alu_cov;
    op_t      op;
    bit [7:0] a;

    covergroup cg;
      option.per_instance = 1;  // keep and report this instance's numbers
      cp_op: coverpoint op {
        option.comment = "ALU-1";
        bins ops[] = {ADD, SUB, MUL, DIV, AND, OR, XOR};
      }
      cp_a: coverpoint a {
        option.comment = "ALU-2";
        bins zero = {8'h00};
        bins max  = {8'hFF};
      }
      x_op_a: cross cp_op, cp_a {
        option.comment = "ALU-4";
      }
    endgroup

    function new(string name);
      cg = new();
      cg.set_inst_name(name);
    endfunction

    // Called once per checked transaction: copy the fields, sample once.
    function void write(alu_txn t);
      op = t.op;
      a  = t.a;
      cg.sample();
    endfunction
  endclass
endpackage

module alu
  import alu_pkg::*;
(
  input  op_t        op,
  input  logic [7:0] a,
  input  logic [7:0] b,
  output logic [7:0] y
);
  always_comb begin
    case (op)
      ADD:     y = a + b;
      SUB:     y = a - b;
      MUL:     y = a * b;
      DIV:     y = a / b;
      AND:     y = a & b;
      OR:      y = a | b;
      default: y = a ^ b;
    endcase
  end
endmodule

module tb_top;
  timeunit 1ns;
  timeprecision 1ns;
  import alu_pkg::*;

  localparam int BUDGET = 1500;  // most transactions this test may spend
  localparam int POLL   = 50;    // read coverage every POLL transactions

  op_t        op;
  logic [7:0] a, b, y;
  alu dut (.op(op), .a(a), .b(b), .y(y));

  alu_cov cov;
  bit     corner_mode;
  int     n_items, n_pass, n_fail;

  initial begin
    alu_txn t;
    int     covered, total, last_covered;

    cov = new("tb_top.cov");
    last_covered = -1;
    while (n_items < BUDGET) begin
      t = new();
      t.corner_mode = corner_mode;
      if (!t.randomize()) $fatal(1, "alu_txn randomize() failed");

      // The ALU is combinational and has no clock: drive, wait 1 ns, compare.
      op <= t.op;
      a  <= t.a;
      b  <= t.b;
      #1;
      if (y !== alu_model(t.op, t.a, t.b)) begin  // ALU-6: the check
        n_fail++;
        $error("ALU-6 mismatch: %s a=%0h b=%0h y=%0h", t.op.name(), t.a, t.b, y);
      end else begin
        n_pass++;
      end
      cov.write(t);  // sampled after it was checked, never instead of it
      n_items++;

      if (n_items % POLL == 0) begin
        void'(cov.cg.x_op_a.get_inst_coverage(covered, total));
        if (!corner_mode && covered == last_covered) begin
          corner_mode = 1;
          $display("STEER at item %0d: x_op_a stuck at %0d/%0d, corner_mode on",
                   n_items, covered, total);
        end
        last_covered = covered;
        // Every item at its goal: stop new stimulus. Nothing is in flight,
        // because each transaction was checked before the next one began.
        if (cov.cg.get_inst_coverage() >= cov.cg.option.goal) break;
      end
    end

    void'(cov.cg.cp_op.get_inst_coverage(covered, total));
    $display("COV %s cp_op %0d/%0d", cov.cg.cp_op.option.comment, covered, total);
    void'(cov.cg.cp_a.get_inst_coverage(covered, total));
    $display("COV %s cp_a %0d/%0d", cov.cg.cp_a.option.comment, covered, total);
    void'(cov.cg.x_op_a.get_inst_coverage(covered, total));
    $display("COV %s x_op_a %0d/%0d", cov.cg.x_op_a.option.comment, covered, total);
    $display("COV total %0.2f%% after %0d of %0d items",
             cov.cg.get_inst_coverage(), n_items, BUDGET);
    $display("PASS=%0d FAIL=%0d", n_pass, n_fail);
    $finish;
  end
endmodule
```

**Expected output.** This log is illustrative: it was worked out by hand from the probabilities on this page, not captured from a simulator run. The item where steering starts and the item where the loop stops depend on your simulator's random seed; the shape does not. Your simulator adds its own banner and a `$finish` message.

```text
STEER at item 100: x_op_a stuck at 0/14, corner_mode on
COV ALU-1 cp_op 7/7
COV ALU-2 cp_a 2/2
COV ALU-4 x_op_a 14/14
COV total 100.00% after 250 of 1500 items
PASS=250 FAIL=0
```

Why each line looks the way it does:

- **`STEER at item 100`.** With `a` uniform, one cell of `x_op_a` has p ≈ 1/1792, so all 14 cells together get a new hit about once every 128 transactions. Between two polls 50 transactions apart, no new cell is the most likely outcome (about 68%). The first poll only records a baseline; the second sees no growth and steers.
- **`7/7` and `2/2`.** `cp_op` has seven explicit bins, each with p ≈ 1/7; `cp_a` has two. Both close early. Values of `a` outside 0 and `8'hFF` fall in no bin and are simply not counted.
- **`x_op_a 14/14` after about 150 more items.** In corner mode each cell has p ≈ 1/7 × 1/4 = 1/28, and 14 such cells need about 91 samples on average and 155 for a 95% chance. The loop checks the goal only at each poll, so it stops at a multiple of 50.
- **`PASS=250 FAIL=0`.** Every transaction was checked before it was sampled, so the pass count equals the item count. Stopping the stimulus skipped no check.
- **`total 100.00%`.** The covergroup's instance coverage is the average of its three items, weight 1 each (§19.11), and the loop compares it with `option.goal` using `>=`, never `== 100.0`.

**Run it.** Save the code as `alu_closure.sv` and compile it with any simulator that supports IEEE 1800-2023 functional coverage (Clause 19); `tb_top` is the top level. Covergroup support in open-source simulators is partial or absent, and this example was not run on one (tool-dependent).

**See the check do its job.** Change the DUT's SUB line to `y = b - a;` and rerun with the same seed. Every `COV` line is unchanged, and `FAIL` counts the SUB transactions whose operands differ. That is the evidence rule from Build Your Mental Model, in your own log.

### How to build a closure loop for your own design

1. **Write the plan rows first.** Give each a stable ID, the scenario, the check that judges it and the goal. Pair every scenario row with a check (the pairing rule).
2. **Build the collector from the rows.** One coverage item per row, `option.comment` set to the row ID *on the item* (a covergroup-level comment is not a default for coverpoints and crosses, §19.7), and `option.per_instance = 1` so each instance is reported.
3. **Feed it once per transaction, after the check.** Never sample from two places, and never sample instead of checking.
4. **Poll the instance number of the item you steer**, with `get_inst_coverage(covered, total)` every N transactions. Use `get_coverage()` only when you want the type number over all instances.
5. **Steer with a knob, not by editing the plan.** A mode bit, `constraint_mode()` or a directed sequence; check that the knob's constraint cannot conflict with the spec constraints.
6. **Stop the stimulus, not the simulation.** End at the goal (`>=` the item's or group's `option.goal`) or at the budget, let every check finish, print the report per plan row and the pass/fail counts, then `$finish` from the top.
7. **Plant a bug** in the DUT and confirm that `FAIL` moves while coverage does not.

### Debugging the loop

| Symptom | Likely cause | Fix |
|---|---|---|
| Every `COV` line is `0/N` although transactions ran | The collector is never constructed or never fed: `cov.write(t)` is missing or on a branch that does not run | Construct the collector before the loop; call `write(t)` for every transaction |
| The run ends at the first poll with 100% coverage and very few items | The goal compare reads the wrong number, for example a different covergroup's `get_coverage()`, or the items have weight 0 | Poll this instance's `get_inst_coverage()` and check every item's weight |
| `STEER` prints, but the cross keeps growing at the uniform rate | The knob is set on the old handle before `t = new()`, so every new object starts with `corner_mode = 0` | Set the knob on the new object, after `new()` |
| The cross is still stuck after steering | One cell has probability 0: a constraint excludes it, or the spec forbids it | Classify the hole: fix the constraint, or move the cell to `illegal_bins` with a check |
| The log ends with coverage numbers but no `PASS`/`FAIL` line | Something called `$finish` early, for example a collector reaching 100% | Only `tb_top` (or, in UVM, the objection mechanism) ends the test |
| `FAIL` is 0 even with a planted bug | The check never runs on that path, or compares a value with itself | Count checks per plan row and plant a bug for each check |

**Checklist before moving on:**
- [ ] I can explain why the SUB bug leaves every coverage number unchanged, and which column of the log does change.
- [ ] Every scenario row in my plan has a coverage item and a check; my check-only rows name the scenario rows that exercise them.
- [ ] My collector samples once per transaction, after the check, and never ends the simulation.
- [ ] I can read an item's `covered/total` with `get_inst_coverage(covered, total)` and say why `get_coverage()` could hide a hole in one instance.
- [ ] I can name the four hole classes and the action for each.
- [ ] I can compute the chance that N samples hit a bin of probability p, and I know about how many samples a 95% chance needs.

## Push Further

These items are for working engineers and interview preparation. The core path above does not depend on them.

### Expert: what a coverage number can and cannot prove

- **The standard's wording versus its mechanism.** §19.2 describes functional coverage as measuring whether scenarios "have been observed, validated, and tested", but the mechanism it then defines only counts sampled values into bins (§19.5) and computes percentages from covered bins and weights (§19.11). Argue from the mechanism: no clause of Clause 19 compares a value with an expected one.
- **Coverage collected with the checks off.** A regression that disables a scoreboard for speed, or an assertion with `$assertoff` (§20.11), still reports full coverage. Sign-off tooling should show, per plan row, whether the paired check was enabled in the runs that produced the coverage (tool-dependent).
- **Vacuous checks.** An implication whose antecedent never matches passes vacuously, and a scoreboard that never received a transaction reports zero mismatches. Pair each check with a count of how often it compared something, and cover the antecedent ([I-SV-4A](/curriculum/T2_Intermediate/I-SV-4A_SVA_Fundamentals/index) teaches `cover property`).
- **Illegal bins take precedence, and report outside UVM.** An illegal value errors even when another bin also contains it (§19.5.6), and an illegal cross product errors even when it is also ignored or inside another cross bin (§19.6.3). That error comes from the simulator, not from `` `uvm_error ``, so a regression gated only on `UVM_ERROR : 0` can pass with illegal-bin hits. Gate on the tool's error count as well, or mirror the condition in a check that reports through UVM. Message text and exit status are tool-dependent.

### Expert: stopping at the goal without losing checks

- **`$finish` is immediate.** It "causes the simulator to exit and pass control back to the host operating system" (§20.2). `final` procedures still run (§9.2.3), but they cannot drain transactions still in flight, so a pipelined DUT's last results are never compared.
- **In UVM it also skips the summary.** In uvm-core 2020.3.1, `uvm_root::run_test()` calls `report_summarize()` only after all phases have run (`uvm_root.svh`); a `$finish` from a component during the run phase skips extract, check, report and final (IEEE 1800.2-2020 §9.8.1) and the report summary that regressions grade on. End the stimulus instead: the test or top sequence drops its objection at the goal, and the scoreboard's end-of-test checks run in the check phase.
- **Compare with `>=`.** `get_inst_coverage()` returns a `real`; comparing it with `== 100.0` is fragile, and `option.goal` may be set below 100. Use `>= option.goal` of the item or the group you care about.
- **Polling cost.** Each query asks the simulator to compute coverage over every bin of the item. Poll every N transactions, not every cycle; how much a query costs is tool-dependent.

### Expert: steering is feedback, and `dist` is only a request

- **What `dist` guarantees.** "Absent any other constraints", the probability of each item is proportional to its weight; when other constraints make the weights unsatisfiable, "implementations are only required to satisfy the constraints" (§18.5.3). This page's `c_corner` touches only `a`, which no other constraint mentions, so the ratio holds. When a steering weight interacts with a spec constraint (as `b`'s weights interact with `c_spec` in the lab), measure the result with coverage; do not assume the arithmetic.
- **Steering changes the random stream.** Each object's generator is seeded from the thread that creates it (§18.14.1). Switching a knob, adding a constraint or adding one `randomize()` call changes the values of every later transaction, so a seed reproduces a failure only with the same code. Record the code version with the seed, and expect coverage merged across a steering change to contain stimulus that can no longer occur ([I-SV-2B Randomization Methods](/curriculum/T2_Intermediate/I-SV-2B_Advanced_Constrained_Randomization/randomization-methods)).
- **Plateau rules are heuristics.** "No new bins in the last N transactions" is a common trigger, not a standard one. A rule that triggers too early wastes the uniform phase's broad exploration; one that triggers too late wastes budget. Tune N with the per-sample probability of your rarest legal cell.
- **When random steering is the wrong tool.** A cell that needs a long, ordered sequence of events is better reached with a directed sequence, a `cover property` with formal reachability ([E-INT-1](/curriculum/T4_Expert/E-INT-1_Integrating_UVM_with_Formal_Verification/index)), or a portable-stimulus scenario ([E-PSS-1](/curriculum/T4_Expert/E-PSS-1_Portable_Stimulus_Standard/index)).

### Expert: code coverage beside functional coverage

IEEE 1800-2023 names the two families of coverage metric (§19.2): code coverage, extracted automatically from the design code, and functional coverage, written by people from the specification. Its coverage API requires at least statement, toggle, FSM (states and transitions) and assertion coverage (§40.2.1, defined in §40.2.2); branch and condition coverage are defined by each tool. The two families answer different questions. A code-coverage hole is RTL that nothing exercised, which usually means a missing plan row or dead code; a functional hole is a planned scenario that never ran, which can hide behind 100% code coverage. Sign-off reviews both. The method, with exclusions and merging, is in [The Coverage Closure Loop](/curriculum/T2_Intermediate/I-SV-3B_Advanced_Functional_Coverage/closure-workflow).

### Kata: add plan row ALU-3 and steer `b`

Extend the Make It Work bench with plan row ALU-3 (`b` at its edge values 0 and `8'hFF`).

1. Add a coverpoint `cp_b` to `cg` with bins `zero` and `max` and its plan ID, and add `b` to the collector's fields and `write()`. Print its `COV` line.
2. **Predict before you run.** `a` is irrelevant to `b`, but `c_spec` is not. With the solver choosing uniformly among legal combinations of `op`, `a` and `b` (IEEE 1800-2023 §18.5.9), what is the probability of `b == 0` on one transaction, and what is the chance that `cp_b.zero` is hit within 500 transactions?
3. Change the steering so that `corner_mode` also aims `b` at its edges, and explain why `c_spec` still holds.
4. Run several seeds. Accept your solution when every run prints `cp_b 2/2`, `FAIL=0`, and never generates DIV with `b == 0`.

<summary>Worked solution (try the kata first)</summary>

**Step 1.** The collector changes; everything else in the bench stays the same.

```systemverilog
// snippet: replaces class alu_cov inside package alu_pkg of alu_closure.sv
class alu_cov;
  op_t      op;
  bit [7:0] a;
  bit [7:0] b;

  covergroup cg;
    option.per_instance = 1;
    cp_op: coverpoint op {
      option.comment = "ALU-1";
      bins ops[] = {ADD, SUB, MUL, DIV, AND, OR, XOR};
    }
    cp_a: coverpoint a {
      option.comment = "ALU-2";
      bins zero = {8'h00};
      bins max  = {8'hFF};
    }
    cp_b: coverpoint b {
      option.comment = "ALU-3";
      bins zero = {8'h00};
      bins max  = {8'hFF};
    }
    x_op_a: cross cp_op, cp_a {
      option.comment = "ALU-4";
    }
  endgroup

  function new(string name);
    cg = new();
    cg.set_inst_name(name);
  endfunction

  function void write(alu_txn t);
    op = t.op;
    a  = t.a;
    b  = t.b;
    cg.sample();
  endfunction
endclass
```

In `tb_top`, add the report line after the `cp_a` line:

```systemverilog
// snippet: inside the report section of tb_top's initial block
void'(cov.cg.cp_b.get_inst_coverage(covered, total));
$display("COV %s cp_b %0d/%0d", cov.cg.cp_b.option.comment, covered, total);
```

**Step 2.** There are 7 × 256 × 256 = 458,752 combinations of `op`, `a` and `b`. `c_spec` removes the 256 with DIV and `b == 0` (one for every `a`), leaving 458,496 legal ones, all equally likely (§18.5.9). `b == 0` is legal for the six other operations: 6 × 256 = 1,536 combinations. So P(`b == 0`) = 1,536 / 458,496 = 6/1791 ≈ 1/299, not 1/256. Within 500 transactions, P(hit) = 1 − (1 − 6/1791)^500 ≈ 81%; a 95% chance needs about 893 transactions. `b == 8'hFF` has p = 7/1791 ≈ 1/256 (86% within 500). Both bins of `cp_b` close within 500 transactions only about 70% of the time, so without steering the loop usually runs past the point where `x_op_a` closed.

**Step 3.** Steer both inputs in corner mode:

```systemverilog
// snippet: replaces constraint c_corner in class alu_txn
constraint c_corner {
  if (corner_mode) {
    a dist {8'h00 := 1, 8'hFF := 1, [8'h01:8'hFE] :/ 2};
    b dist {8'h00 := 1, 8'hFF := 1, [8'h01:8'hFE] :/ 2};
  }
}
```

`c_spec` still holds because a `dist` never overrides a hard constraint: when the weights cannot all be satisfied, "implementations are only required to satisfy the constraints" (§18.5.3). A solver that multiplies the weights and removes the forbidden combinations gives P(`b == 0`) = (6/7 × 1/4) / (1 − 1/28) = 2/9, but the standard guarantees the weights' ratio only "absent any other constraints", so treat 2/9 as an estimate and let coverage confirm it.

**Step 4.** In corner mode both `cp_b` bins have p ≈ 1/4 or more, so they close within a few dozen transactions of steering. `c_spec` guarantees that DIV with `b == 0` is never generated, and the ALU-6 check still runs on every transaction, so `FAIL=0` remains the evidence that the results were right.
