## Quick Take

- **What it is:** A **verification plan** (vplan after this first use) is the list of things the design must be shown to do. Each line of it, a **plan row**, has an ID such as `ALU-4`. Linking coverage to the plan means three things: every row names the **coverage items** (coverpoints and crosses) that show its scenario happened and the **check** that shows the design behaved correctly; every coverage item carries its row's ID in `option.comment`, so the ID appears in the coverage report; and every covergroup instance has a stable name, so each lane's numbers can be read and merged (IEEE 1800-2023 §19.7, Table 19-1).
- **Why it matters:** A coverage report full of percentages answers "how much ran?" but not "which requirement is still open?". With IDs on the items, a reviewer reads the report row by row. With a check named on every row, nobody mistakes "it ran" for "it worked": coverage counts the values it sampled and never looks at whether the result was right (§19.5, §19.11).
- **The Analogy:** A road-trip checklist where every landmark has a line number, and you write that number next to each photo you take. At the end, you can tell which lines have a photo. *Where it breaks:* a photo proves you were at the landmark, not that it was the right landmark or that it was open. In verification, that second question is answered only by the checks. Also, one photo can serve two lines, and one line may need several photos, so the map from rows to items is many-to-many.

**You will be able to:**
1. **Write** a plan table in which every scenario row names its coverage items, its check and its goal, and **find** orphan rows (no item or no check) and orphan items (counted, but no row).
2. **Write** plan IDs into a coverage model at the right level: `option.comment` on each coverpoint and cross, `type_option.comment` for type-level reports, and never on a bin.
3. **Configure** `option.per_instance` and stable, hierarchy-derived instance names so that each lane's rows can be read separately and line up across tests.
4. **Decide** from a coverage report and the check results whether a plan row is closed, and **explain** why 100 % coverage on its own proves nothing about correctness.

You need [I-SV-3A Functional Coverage Fundamentals](/curriculum/T2_Intermediate/I-SV-3A_Functional_Coverage_Fundamentals/index) (covergroups, coverpoints, bins, crosses, `illegal_bins`, `sample()`) and its [coverage options page](/curriculum/T2_Intermediate/I-SV-3A_Functional_Coverage_Fundamentals/coverage-options) (`option`, `type_option`, `weight`, `per_instance`). The plan-row fields come from [F1B: From spec to plan](/curriculum/T1_Foundational/F1B_The_Verification_Mindset/index#from-spec-to-plan). This is the first of three pages after the [module overview](/curriculum/T2_Intermediate/I-SV-3B_Advanced_Functional_Coverage/index); the next two cover run-time queries and the closure loop.

## Build Your Mental Model

### Words you need first

- **Plan row:** one line of the vplan. In F1B it has five fields: feature, scenario, check, coverage item and method. This page adds two more: an **ID** (such as `ALU-4`) and a **goal** (the coverage percentage, or the check result, that closes the row).
- **Coverage item:** a coverpoint or a cross. Items are the things that get a coverage percentage of their own (§19.11). Bins are inside items and have no percentage of their own.
- **Check:** code that decides pass or fail: a compare against a **reference model** (a second, independent description of what the design should do), an assertion, or a scoreboard.
- **Type and instance:** the covergroup definition is a **type**; each object you create from it with `new()` is an **instance**. A bench with two ALU lanes (two copies of the ALU, each with its own collector) has one type and two instances.
- **Coverage database and report:** at the end of a run the simulator saves coverage into a file (the database) and can print a report from it. The file format is tool-specific. Combining the databases of many runs into one is called **merging**, and it is also tool-specific.
- **Traceability:** being able to follow a link in both directions: from a plan row to the items and checks that close it, and from any item in the report back to its row.

### What a plan row holds

Here is the plan for the 8-bit ALU used throughout this module. It has seven operations (`ADD`, `SUB`, `MUL`, `DIV`, `AND`, `OR`, `XOR`) and two operands, `a` and `b`.

| ID | Feature | Scenario | Coverage item | Check | Goal |
|---|---|---|---|---|---|
| ALU-1 | Every operation works | Each of the 7 operations is applied | `cp_op` | result compare | 100 % and 0 mismatches |
| ALU-2 | Operand `a` edge values | `a` is `8'h00` and `8'hFF` | `cp_a` | result compare | 100 % and 0 mismatches |
| ALU-3 | Operand `b` edge values | `b` is `8'h00` and `8'hFF` | `cp_b` | result compare | 100 % and 0 mismatches |
| ALU-4 | Every operation at each `a` edge | 7 operations × 2 edges | `x_op_a` | result compare | 100 % and 0 mismatches |
| ALU-5 | Divide by zero is forbidden by the spec | Never sent | `x_op_b` illegal bin `div_by_zero` | input check, plus the stimulus rule | Never seen |
| ALU-6 | Every result matches the reference model | Check-only row: exercised by ALU-1 to ALU-4 | none of its own | result compare: `y` against `alu_model()` | 0 mismatches |

Three rules turn this table into something you can trust:

1. **Every scenario row names at least one coverage item and at least one check.** ALU-1 to ALU-4 all point at the result compare: the coverage proves the scenario ran, the compare proves the result was right.
2. **A check-only row names the scenario rows whose coverage exercises it.** ALU-6 has no coverage item of its own; it is exercised exactly as far as ALU-1 to ALU-4 are covered.
3. **Every coverage item that counts traces to a row.** An item with no row is an **orphan item**: it moves the score without being evidence for anything. Either give it a row, or give it `option.weight = 0` if it only exists to feed a cross or to guard a forbidden case (ALU-5's `x_op_b`). A scenario row with no item or no check is an **orphan row**: it can never close honestly. (A check-only row such as ALU-6 is not an orphan, because rule 2 ties it to the scenario rows that exercise it.)

Forbidden behaviour (ALU-5) is a row too. It gets an `illegal_bins` in the model, a constraint that stops the stimulus from producing it, and a check. You will see why the check is needed further down.

### Putting plan IDs into the model

`option.comment` is an option string that the standard saves "in the coverage database and included in the coverage report" (Table 19-1). You may set it at three levels: covergroup, coverpoint and cross (Table 19-2). Bins have no options at all.

The rule that catches everyone: **a comment set at covergroup level is not copied down to the coverpoints and crosses.** The standard says that `weight`, `goal`, `comment` and `per_instance` set at covergroup level "do not act as default values to the lower syntactic levels" (§19.7). So this puts the ID on the covergroup instance only, and every item row in the report has an empty comment:

```systemverilog
// snippet: the classic mistake
covergroup cg with function sample(op_t op, bit [7:0] a);
  option.comment = "ALU-1 ALU-2 ALU-4";   // labels the instance, not the items
  cp_op:  coverpoint op;
  cp_a:   coverpoint a { bins zero = {8'h00}; bins max = {8'hFF}; }
  x_op_a: cross cp_op, cp_a;
endgroup
```

Put each ID inside the item that closes its row:

```systemverilog
// snippet: one ID per item
covergroup cg with function sample(op_t op, bit [7:0] a);
  cp_op: coverpoint op {
    option.comment = "ALU-1";
  }
  cp_a: coverpoint a {
    option.comment = "ALU-2";
    bins zero = {8'h00};
    bins max  = {8'hFF};
  }
  x_op_a: cross cp_op, cp_a {
    option.comment = "ALU-4";
  }
endgroup
```

Where each option is allowed, for the options this page uses (Table 19-2 for `option`, Table 19-4 for `type_option`):

| Option | Covergroup | Coverpoint | Cross | Bin |
|---|---|---|---|---|
| `option.comment` | yes (not inherited) | yes | yes | no |
| `type_option.comment` | yes (not inherited) | yes | yes | no |
| `option.name` | yes | no | no | no |
| `option.per_instance` | yes, in the definition only | no | no | no |
| `option.weight` | yes (not inherited) | yes | yes | no |

**`option.comment` or `type_option.comment`?**
- `option.comment` belongs to an instance. It is reported with that instance's data, which the tool is required to save only when `option.per_instance = 1` (Table 19-1).
- `type_option.comment` belongs to the type, so it appears with the cumulative (type) numbers. Type options are written with constant expressions, so every instance has the same value (§19.7.1).
- If your team reads per-instance reports, `option.comment` on each item is enough. If it reads only the cumulative report, put the ID in `type_option.comment` on each item as well.

**When a row is finer than an item.** Because bins have no options, a row that covers just one value of a coverpoint cannot carry its ID on that bin. You have two choices: split it into its own coverpoint (`cp_a_max: coverpoint a { option.comment = "ALU-2b"; bins max = {8'hFF}; }`), or name the bin after the row (`bins alu_2b_max = {8'hFF};`) and let the item's comment list the parent row. Some plan tools can link individual bins; that is a tool feature, not part of the standard.

### Naming instances so rows line up

A bench with two ALU lanes has two instances of the same covergroup. Two settings decide whether you can tell them apart in the report.

- **`option.per_instance = 1`** tells the tool to save and report this instance's coverage, separately from the type total. When it is 0 (the default), "implementations are not required to save instance-specific information" (Table 19-1). It can be set only inside the covergroup definition (§19.7).
- **An explicit instance name.** If you do not name an instance, "a unique name for each instance is automatically generated by the tool" (Table 19-1). Nothing in the standard keeps those generated names the same between two tests, two tool versions or two orders of construction. Set the name yourself with `cg.set_inst_name("...")` (Table 19-5) or by assigning `cg.option.name`, and derive the string from the place in the bench hierarchy, for example `"tb_top.dut1"`.

Why the hierarchy? A **regression** is a large batch of tests and seeds run together. When a regression merges the databases of many tests, rows that should be combined are matched by name (how exactly is tool-specific). A name built from the hierarchy is the same in every test that builds the same bench, so lane 1's rows from test A land on lane 1's rows from test B.

A common slip in the reverse direction: reading `cg.get_coverage()` to see one lane. `get_coverage()` returns **type** coverage, across every instance; the lane's own number is `cg.get_inst_coverage()` (§19.8). The [next page](/curriculum/T2_Intermediate/I-SV-3B_Advanced_Functional_Coverage/coverage-apis) shows how the two are computed.

### A reusable collector

A **collector** is a small class that owns the covergroup, receives one call per observed transaction and samples once per call. The ALU collector puts the pieces together.

```systemverilog
// snippet: the full version is in Make It Work
class alu_cov;
  string name;

  covergroup cg with function sample(op_t op, bit [7:0] a, bit [7:0] b);
    option.per_instance = 1;                  // save this lane's numbers
    type_option.comment = "ALU vplan rev 3";  // labels the type only
    cp_op: coverpoint op { option.comment = "ALU-1"; /* bins */ }
    // ... cp_a (ALU-2), cp_b (ALU-3), x_op_a (ALU-4), x_op_b (ALU-5)
  endgroup

  function new(string name);
    this.name = name;
    cg = new();                // an embedded covergroup is built in new()
    cg.set_inst_name(name);    // stable, hierarchy-derived
  endfunction

  function void write(op_t op, bit [7:0] a, bit [7:0] b);
    cg.sample(op, a, b);       // exactly one sample per transaction
  endfunction
endclass
```

Three choices in it are deliberate:
- **No clocking event.** The covergroup samples only when `write()` calls `cg.sample()`, so nothing is counted on idle cycles and nothing is counted twice.
- **Built in `new()`.** A covergroup declared inside a class is an **embedded covergroup**. It must be created by assigning `cg = new()` in the class constructor, or it is never created and samples nothing (§19.4).
- **No virtual interface.** The collector receives values; it never reads signals. In UVM the same class becomes a `uvm_subscriber`, whose `write()` is called by a monitor's analysis port ([I-UVM-2A Component Roles](/curriculum/T2_Intermediate/I-UVM-2A_Component_Roles/index), [I-UVM-2B TLM Connections](/curriculum/T2_Intermediate/I-UVM-2B_TLM_Connections/index)).

### Coverage measures, checks verify

This is the idea the whole page rests on. A bin's count goes up when a sampled value falls in it (§19.5). The percentage is computed from covered bins and weights only (§19.11; Table 19-1, `at_least`). Nothing in that computation compares a result with an expected value. A wrong result is counted exactly like a right one.

So a plan row closes only when both halves are true:

| Coverage of the row's items | The row's check | What you can claim |
|---|---|---|
| At goal | Ran, 0 failures | **Closed**: the scenario happened and the design did the right thing |
| At goal | Missing, disabled or failing | **Not closed**: false confidence, the most dangerous cell |
| Below goal | Ran, 0 failures | **Not closed**: the check passed, but on too few scenarios |
| Below goal | Missing | **Not closed**: a blind spot |

The [module overview](/curriculum/T2_Intermediate/I-SV-3B_Advanced_Functional_Coverage/index) draws this as a 2 × 2 picture.

**`illegal_bins` is not a checker.** ALU-5's `div_by_zero` bin issues a run-time error when a sampled value matches it (§19.5.6, §19.6.3). But it fires only when its covergroup instance exists and samples that value, and the error is a simulator message, not a UVM report or a test-bench failure count. A regression that only counts its own failures can pass with illegal-bin errors in the log. That is why ALU-5 also has an input check in the bench that counts the forbidden case itself. What happens to illegal bins after `stop()` or under a tool's coverage-off switch is tool-dependent.

### Pitfalls and how to debug them

| Symptom in the report or log | Cause | Fix |
|---|---|---|
| The covergroup shows an ID, every item row has an empty comment | The ID was set only at covergroup level; it is not inherited (§19.7) | Put `option.comment` inside each coverpoint and cross |
| Only one set of numbers for the ALU, though there are two lanes | `option.per_instance` is 0, so instance data need not be saved | Set `option.per_instance = 1` in the definition |
| Instance rows called something like `cg`, `cg_1`, and merged rows do not line up between tests | Tool-generated names | `set_inst_name()` with a hierarchy-derived string |
| IDs appear in per-instance reports but not in the cumulative report | IDs only in `option.comment` | Also set `type_option.comment` on each item |
| The compiler rejects an option inside a `bins` line (message wording varies by tool) | Bins have no options (Table 19-2) | Move the ID to the item, or encode the row in the bin name |
| The total is lower than every row suggests | An orphan item with weight 1 is part of the average | Give the item a row, or `option.weight = 0` if it only feeds a cross or guards a forbidden case |
| A row is at 100 %, yet a bug in that scenario escaped | The row has no check, or its check is disabled | Name a check on every scenario row; print the check counts next to the coverage |
| Simulator log has an illegal-bin error, the bench prints PASS | `illegal_bins` is not counted by the bench | Mirror the forbidden condition in a check that counts as a failure |

## Make It Work

### Worked example: a two-lane ALU with a traced plan report

The bench has two copies of a combinational ALU (`dut0`, `dut1`), one collector per lane, a result compare against a reference model (ALU-6), and an input check for the forbidden case (ALU-5). Lane 0 gets 14 transactions that cover every scenario row. Lane 1 gets only the first 7, so it never sees `a == 8'hFF`. At the end, each collector prints one line per plan-linked item, reading the ID back from the model through `cg.<item>.option.comment` (`option` is a built-in member of every covergroup, coverpoint and cross, §19.10).

```systemverilog
// compile: alu_pkg.sv
package alu_pkg;
  typedef enum bit [2:0] {ADD, SUB, MUL, DIV, AND, OR, XOR} op_t;

  // Reference model for ALU-6. Divide by zero never reaches it (ALU-5).
  function automatic bit [7:0] alu_model(op_t op, bit [7:0] a, bit [7:0] b);
    case (op)
      ADD:     return a + b;
      SUB:     return a - b;
      MUL:     return a * b;
      DIV:     return a / b;
      AND:     return a & b;
      OR:      return a | b;
      default: return a ^ b;   // XOR
    endcase
  endfunction

  // Coverage for one ALU lane. Every item carries the plan row it closes.
  class alu_cov;
    string name;

    covergroup cg with function sample(op_t op, bit [7:0] a, bit [7:0] b);
      option.per_instance = 1;                  // save this lane's numbers
      type_option.comment = "ALU vplan rev 3";  // labels the type only

      cp_op: coverpoint op {
        option.comment = "ALU-1";
        bins ops[] = {ADD, SUB, MUL, DIV, AND, OR, XOR};
      }
      cp_a: coverpoint a {
        option.comment = "ALU-2";
        bins zero = {8'h00};
        bins max  = {8'hFF};
      }
      cp_b: coverpoint b {
        option.comment = "ALU-3";
        bins zero = {8'h00};
        bins max  = {8'hFF};
      }
      x_op_a: cross cp_op, cp_a {
        option.comment = "ALU-4";
      }
      // Guards ALU-5 only. Its 13 legal bins belong to no plan row,
      // so weight 0 keeps them out of the score.
      x_op_b: cross cp_op, cp_b {
        option.comment = "ALU-5";
        option.weight  = 0;
        illegal_bins div_by_zero = binsof(cp_op) intersect {DIV} &&
                                   binsof(cp_b.zero);
      }
    endgroup

    function new(string name);
      this.name = name;
      cg = new();
      cg.set_inst_name(name);
    endfunction

    // One call per observed transaction; a UVM subscriber's write() does this job.
    function void write(op_t op, bit [7:0] a, bit [7:0] b);
      cg.sample(op, a, b);
    endfunction

    function void show_item(string id, string item, int c, int t);
      $display("COV %s %s %s %0d/%0d", name, id, item, c, t);
    endfunction

    // On a coverpoint or cross, get_inst_coverage(c, t) returns the true
    // numerator and denominator of that item's percentage (IEEE 1800-2023 19.8).
    function void report();
      int c, t;
      void'(cg.cp_op.get_inst_coverage(c, t));
      show_item(cg.cp_op.option.comment, "cp_op", c, t);
      void'(cg.cp_a.get_inst_coverage(c, t));
      show_item(cg.cp_a.option.comment, "cp_a", c, t);
      void'(cg.cp_b.get_inst_coverage(c, t));
      show_item(cg.cp_b.option.comment, "cp_b", c, t);
      void'(cg.x_op_a.get_inst_coverage(c, t));
```

```systemverilog
module tb_top;
  timeunit 1ns;
  timeprecision 1ps;
  import alu_pkg::*;

  op_t        op [2];
  logic [7:0] a [2], b [2], y [2];

  alu dut0 (.op(op[0]), .a(a[0]), .b(b[0]), .y(y[0]));
  alu dut1 (.op(op[1]), .a(a[1]), .b(b[1]), .y(y[1]));

  alu_cov cov [2];
  int pass_count, fail_count, illegal_inputs;

  // ALU-5 stimulus rule: DIV always gets b = 8'hFF; other ops alternate 00/FF.
  function automatic bit [7:0] b_for(op_t o, int i);
    return (o == DIV || i % 2 == 1) ? 8'hFF : 8'h00;
  endfunction

  // Apply one transaction to lane p, check it, then sample coverage.
  // The ALU is combinational with no clock, so there is no clock edge to race;
  // a clocked DUT would be driven through a clocking block (F4C).
  task automatic apply(int p, op_t o, bit [7:0] av, bit [7:0] bv);
    op[p] = o;
    a[p]  = av;
    b[p]  = bv;
    #1;
    if (o == DIV && bv == 8'h00) begin          // ALU-5 input check
      illegal_inputs++;
      $error("ALU-5 lane %0d: DIV by zero sent", p);
    end
    if (y[p] === alu_model(o, av, bv)) pass_count++;   // ALU-6 result compare
    else begin
      fail_count++;
      $error("ALU-6 lane %0d: %s a=%h b=%h y=%h", p, o.name(), av, bv, y[p]);
    end
    cov[p].write(o, av, bv);
  endtask

  initial begin
    cov[0] = new("tb_top.dut0");   // names follow the bench hierarchy
    cov[1] = new("tb_top.dut1");
    for (int i = 0; i < 14; i++)    // lane 0: a = 00 for 7 items, then FF
      apply(0, op_t'(i % 7), (i < 7) ? 8'h00 : 8'hFF, b_for(op_t'(i % 7), i));
    for (int i = 0; i < 7; i++)     // lane 1: a = 00 only
      apply(1, op_t'(i % 7), 8'h00, b_for(op_t'(i % 7), i));
    cov[0].report();
    cov[1].report();
    $display("CHK ALU-5 illegal_inputs=%0d", illegal_inputs);
    $display("CHK ALU-6 compares=%0d mismatches=%0d",
             pass_count + fail_count, fail_count);
    $display("PASS=%0d FAIL=%0d", pass_count, fail_count + illegal_inputs);
    $finish;
  end
endmodule
```

### How to link a block's coverage to its plan

1. **Start from the plan, not the covergroup.** Write the table: ID, feature, scenario, coverage item, check, goal. Mark forbidden rows and check-only rows.
2. **Check the table for orphans.** Every scenario row needs an item and a check; every check-only row names the rows that exercise it.
3. **Write one item per row, or one row per item.** Put `option.comment = "<ID>"` inside each coverpoint and cross. Add `type_option.comment` if anyone reads cumulative reports.
4. **Give leftover items a job.** An item that only feeds a cross or guards a forbidden row gets `option.weight = 0` and a comment saying why.
5. **Map forbidden rows three ways:** `illegal_bins` in the model, a constraint in the stimulus, and a check that counts the case as a failure.
6. **Name every instance.** `option.per_instance = 1` in the definition, and `set_inst_name()` with a hierarchy-derived string in the constructor.
7. **Print the evidence together.** Report each item's `covered/total` with its ID, then the check counts, so one log shows both halves of every row.
8. **Close rows, not percentages.** A row is closed only when its items are at goal and its check ran with zero failures.

**Checklist before moving on:**
- [ ] Every scenario row in my plan names at least one coverage item and one check.
- [ ] Every coverpoint and cross has its own `option.comment`; none relies on a covergroup-level comment.
- [ ] No bin carries an option; finer rows have their own item or a bin named after the row.
- [ ] Every item with nonzero weight traces to a plan row.
- [ ] `option.per_instance = 1` is set in the definition, and every instance has a hierarchy-derived name.
- [ ] Forbidden rows have an illegal bin, a constraint and a counting check.

## Push Further

### Expert: plans in tools, and what the standard guarantees

- **What IEEE 1800-2023 guarantees:** `option.comment` and `type_option.comment` are "saved in the coverage database and included in the coverage report" (Table 19-1, Table 19-3). That is all. Filtering a report by comment, linking a plan spreadsheet to coverage paths, annotating a plan with live percentages, and linking individual bins are features of each vendor's plan tool (tool-dependent).
- **Executable plans** (tool-dependent): many flows keep the vplan in a structured format that names, for each row, coverage paths (such as `tb_top.dut1.x_op_a`), assertions and tests. The tool then computes each row's status from the merged database. Hierarchy-derived instance names are what make those paths stable.
- **UCIS** (Unified Coverage Interoperability Standard, Accellera, version 1.0, June 2012) is an API plus an XML interchange format for reading and writing coverage data across tools. It is not a database file format; "UCDB" is the name of one vendor's database. Scripts built on UCIS can read comments and instance names, but how a tool maps covergroups into UCIS objects is tool-dependent.
- **Interview angle:** "How do you prove the plan is closed?" A strong answer says: per row, coverage at goal *and* the mapped check ran with zero failures, on a merged database whose instance names line up, with every exclusion reviewed.

### Expert: per-instance IDs and option timing

- **Per-instance comments.** Instance options can be set from covergroup arguments (§19.7 shows `option.comment = instComment;` with `instComment` passed to `new`) or assigned procedurally after the instance exists, such as `cov.cg.cp_op.option.comment = "ALU-1 lane 1";` (§19.7: "Other instance-specific options can be assigned procedurally after a covergroup has been instantiated").
- **What cannot vary per instance.** `per_instance` and `get_inst_coverage` "can only be set in the covergroup definition" (§19.7). Type options use constant expressions, so "different instances of a covergroup cannot assign different values to type options" (§19.7.1). A type-level ID is therefore one string for every lane.
- **Embedded covergroups have an anonymous type** (§19.4). For the ALU collector there is no type name to write `cg_t::type_option.comment = ...` with; set type options in the definition. The `::` form applies to covergroups declared outside a class.
- **Option evaluation time.** Option assignments in the definition are evaluated when the covergroup is instantiated (§19.7), so an option that reads a class member sees its value at the moment `cg = new()` runs in the constructor.

### Expert: reusing a coverage model across derived classes

- **Embedded covergroup inheritance** (§19.4.1): `covergroup extends cg; ... endgroup` in a derived class adds or overrides coverpoints, crosses and options of the base class's covergroup. The derived covergroup replaces the base one for every reference to the name.
- **Traceability consequences.**
  - A derived coverpoint with the same name as a base coverpoint replaces it in the coverage computation, so its plan ID must be declared again in the derived item.
  - Base options that are not overridden still apply.
  - "For the purposes of `get_coverage()`, a derived covergroup and its base covergroup are separate types" (§19.4.1), so a plan row fed by both needs both types summed in the plan tool.
- **Covergroup arguments** let each instance build different bins (the §19.8 example builds 2 and 4 bins from arguments). Rows that depend on such arguments should say which configuration they need, or one lane's bins can silently differ from another's.

### Expert: traceability under change

These are methodology practices, not language rules:
- **Version the link.** Put the plan revision in `type_option.comment` (as the example does with "ALU vplan rev 3") so a report says which plan it was measured against.
- **Audit both directions on every spec change.** Orphan rows (a new requirement with no item or check) and orphan items (a removed requirement whose item still counts) both distort the number. A small script that compares the plan's ID list with the IDs printed by `report()` catches both.
- **Re-baseline instead of mixing.** Merging databases measured against different coverage models or stimulus versions can mix bins that no longer mean the same thing. How a tool merges changed models is tool-dependent; many teams start a fresh baseline when the model changes.

### Kata: trace a FIFO plan

| ID | Feature | Scenario |
|---|---|---|
| FIFO-1 | Every occupancy level is reached | `count` takes each value 0 to 4 |
| FIFO-2 | Push while full is dropped and flags overflow | `push` when `count == 4` |
| FIFO-3 | Pop while empty is forbidden by the spec | `pop` when `count == 0` |
| FIFO-4 | Push and pop together keep the level | `push` and `pop` in one cycle at levels 1 to 3 |
| FIFO-5 | Data leave in the order they entered | Check-only row |
| FIFO-6 | Pop alone at every non-empty level | `pop` without `push` at levels 1 to 4 |

<summary className="cursor-pointer font-semibold">Show the worked solution</summary>

```systemverilog
// snippet: one item per row; IDs on the items
covergroup fifo_cg with function sample(bit push, bit pop, int unsigned count);
  option.per_instance = 1;
  cp_level: coverpoint count {
    option.comment = "FIFO-1";
    bins level[] = {[0:4]};
  }
  cp_push_full: coverpoint (push && count == 4) {
    option.comment = "FIFO-2";
    bins seen = {1};
  }
  // Forbidden: guards FIFO-3 only, so it must not count toward the score.
  cp_pop_empty: coverpoint (pop && count == 0) {
    option.comment = "FIFO-3";
    option.weight  = 0;
    illegal_bins seen = {1};
  }
  cp_both: coverpoint count iff (push && pop) {
    option.comment = "FIFO-4";
    bins level[] = {[1:3]};
  }
  cp_pop_only: coverpoint count iff (pop && !push) {
    option.comment = "FIFO-6";
    bins level[] = {[1:4]};
  }
endgroup
```

| ID | Coverage item | Check | Goal |
|---|---|---|---|
| FIFO-1 | `cp_level` (5 bins) | Occupancy model: `count` matches a counter in the bench | 100 %, 0 mismatches |
| FIFO-2 | `cp_push_full` | Overflow flag is 1, `count` stays 4, stored data unchanged | 100 %, 0 failures |
| FIFO-3 | `cp_pop_empty` illegal bin, weight 0 | Stimulus constraint, plus a check that counts any pop at level 0 as a failure | Never seen |
| FIFO-4 | `cp_both` (3 bins) | `count` unchanged after the cycle; scoreboard order check | 100 %, 0 failures |
| FIFO-5 | none (check-only) | Scoreboard: each popped word equals the oldest pushed word | 0 mismatches; exercised by FIFO-1, FIFO-2, FIFO-4 and FIFO-6 |
| FIFO-6 | `cp_pop_only` (4 bins) | `count` drops by 1; scoreboard order check | 100 %, 0 failures |

**Why these choices.**
- Each ID is inside its own coverpoint, because a covergroup-level comment would not reach the items (§19.7).
- `cp_pop_empty` has weight 0: its only bin is illegal, so it has nothing to count, and it exists only to guard FIFO-3. The bench check is still needed, because the illegal bin produces a simulator error, not a failure the bench counts.
- A coverpoint on an expression such as `(push && count == 4)` turns one scenario into one item, so the row and the item match one-to-one.
- FIFO-5 is exercised exactly as far as the rows that move data are covered. If FIFO-4 were at 1 of 3 bins, the order check would have been tried on fewer simultaneous push-and-pop levels than the plan asks for, even with 0 mismatches.

</details>
