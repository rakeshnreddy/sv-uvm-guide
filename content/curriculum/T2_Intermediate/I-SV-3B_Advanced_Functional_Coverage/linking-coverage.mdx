  ## Level 1: Why Link Coverage?
  *IEEE 1800-2023, Clause 19.7: Specifying coverage options*

  A verification plan (V-Plan) lists the features the design must support. Linking **covergroups** to plan items proves that each requirement has been exercised in simulation.

  **The Analogy:** Imagine a checklist for a road trip. Each time you visit a landmark, you tick it off. Coverage-to-V-Plan linkage is that checklist for verification.

  ## Level 2: Practical Method

  ### Tagging Covergroups

  Use options to embed plan information:

  <InteractiveCode>
  ```systemverilog
  covergroup cg_mode @(posedge clk);
    option.comment = "VPLAN-5.2"; // link to plan item
    cp_mode: coverpoint mode;
  endgroup
  ```
  </InteractiveCode>

  A reusable collector wraps the covergroup in a class. It samples once per observed transaction, keeps each instance's data separately, and names each instance after the plan item and the channel it watches:

  ```systemverilog
typedef enum bit [1:0] {IDLE, NORMAL, TURBO} mode_t;

class mode_coverage;
  localparam string PLAN_ID = "VPLAN-5.2";

  covergroup cg_mode with function sample(mode_t mode);
    option.per_instance = 1;   // save this instance's data in the database
    option.comment      = PLAN_ID;
    cp_mode: coverpoint mode;
  endgroup

  function new(string inst_name);
    cg_mode = new();
    cg_mode.set_inst_name({PLAN_ID, "::", inst_name});
  endfunction

  // Called once per observed transaction, for example by a monitor.
  function void write(mode_t mode);
    cg_mode.sample(mode);
  endfunction
endclass
  ```

  Create one collector per channel, `mode_coverage chan0_cov = new("chan0");`, and every instance carries the plan ID in both its comment and its instance name. The covergroup has no clocking event, so the only samples are the `write()` calls: nothing is counted twice, and nothing depends on a virtual interface that may not exist yet when the constructor runs.

  In UVM (from I-UVM-2B on) the same class becomes a `uvm_subscriber`, and its `write()` receives transactions from a monitor's analysis port. See [analysis components](/curriculum/T2_Intermediate/I-UVM-2B_TLM_Connections/index#monitors-scoreboards-and-the-analysis-fabric) for how transactions reach these covergroups.

  Reports can then filter coverage by `option.comment`, giving traceability back to the V-Plan. When holes appear, adjust stimulus using [Constrained Randomization](/curriculum/T2_Intermediate/I-SV-2A_Constrained_Randomization_Fundamentals/index).

  ## Level 3: Expert Insights

  **Tool integration:** UCIS/UCDB databases preserve `option.comment` and instance names. Feed them into your coverage-report scripts or dashboards so coverage badges line up with the plan hierarchy automatically.

  **Granularity:** Tag the bin level when requirements are nuanced—e.g., `illegal_bins` for forbidden modes vs. `bins` for required ones. Traceability works best when the V-Plan mirrors this structure.

  **Process guardrails:** Schedule periodic coverage reviews with the plan owners. Any time a requirement changes, update both the plan YAML and the covergroup options together so the linkage never drifts.
