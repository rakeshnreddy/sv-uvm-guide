## Quick Take

- **What it is:** In UVM, "layering" means two different things. **Sequence layering** builds big stimulus from small sequences: an **atomic sequence** sends one transaction, and a **scenario sequence** starts several atomic sequences to make a meaningful pattern, such as "program eight registers". **Protocol layering** carries one protocol's items inside another protocol's items, for example packets carried inside frames. A **translation sequence** turns each upper-layer item into one or more lower-layer items, and a **layered monitor** turns the lower-layer items back into upper-layer items.
- **Why it matters:** Scenario sequences survive protocol changes, because only the atomic sequences touch the item fields. Protocol layering lets you send upper-layer traffic through an agent you already have, without writing a new driver, and lets the checks and coverage speak the upper layer's language.
- **The Analogy:** Letters, mail bags and a sorting office. A writer (the upper sequence) hands a letter to a counter (the upper sequencer). A clerk (the translation sequence) takes it, puts it in a mail bag (a lower-layer frame) and hands the bag to the van driver (the lower-layer driver). At the far end, someone opens the bags and rebuilds the letters (the layered monitor). *Where it breaks:* this clerk tells the writer "delivered" only after the van has delivered the bag, so the writer cannot run ahead of the van; real post offices give no such guarantee. And here one long letter may be cut across several bags (fragmentation), which real mail never does.

**The analogy at a glance** (the UVM names are the ones this page builds):

| Post office | Protocol layering | Where the analogy breaks |
| --- | --- | --- |
| Writer | Upper sequence (`ip_burst_seq`) | |
| Counter | Upper sequencer with no driver (`ip_sqr`) | |
| Clerk | Translation sequence (`xlate`) | The clerk says "delivered" only after the van has delivered the bag |
| Mail bag | Lower-layer item (`eth_frame`) | One long letter may be cut across several bags (fragmentation) |
| Van driver | Lower-layer driver (`eth_agt.drv`) | |
| Opening the bags at the far end | Layered monitor (`ip_mon`) | |

**You will be able to:**
1. Explain the two meanings of layering in UVM, and choose the one a stimulus problem needs.
2. Write a scenario sequence that starts atomic children with `start(m_sequencer, this)` and constrains them correctly with `local::`.
3. Write a translation sequence that pulls items from a driverless upper sequencer and sends lower-layer items, and predict when the upper sequence's `finish_item()` returns.
4. Write a layered monitor that rebuilds upper-layer items from lower-layer items, and decide which layer each check and coverage model belongs to.
5. Debug a layered stack that never sends, that runs ahead of the wire, or whose upper layer loses packets.

## Build Your Mental Model

Every subsection before the one marked *Practitioner depth* is the core path; read them in order. The practitioner subsection and Make It Work add what you need for daily work, and the expert layer is in Push Further.

This lesson builds on terms from earlier lessons:
- A **sequence item** is one transaction object; a **sequence** is an object whose `body()` task sends items; a **sequencer** is the component that grants one waiting sequence at a time (choosing among them is **arbitration**); a **driver** is the component that pulls each item and drives it. `start_item()` waits for the grant, and `finish_item()` waits until the driver calls `item_done()` ([I-UVM-3A](/curriculum/T2_Intermediate/I-UVM-3A_Fundamentals/index), and in more depth [The Sequencer-Driver Handshake](/curriculum/T2_Intermediate/I-UVM-3B_Advanced_Sequencing_and_Layering/sequencer-driver-handshake)).
- `m_sequencer` is a member of every sequence: the sequencer the sequence was started on.
- A **phase** is one of the fixed steps UVM runs on every component. Time passes in the **run phase** (`run_phase`), which lasts as long as some component has an **objection** raised; tests raise one before their stimulus and drop it afterwards ([I-UVM-1C](/curriculum/T2_Intermediate/I-UVM-1C_UVM_Phasing/index)).
- A **lock** (`lock()`) gives one sequence, and its children, exclusive use of a sequencer until `unlock()` ([Sequence Arbitration](/curriculum/T2_Intermediate/I-UVM-3B_Advanced_Sequencing_and_Layering/sequence-arbitration)).
- An **analysis port** broadcasts a transaction with `write()` to every connected **subscriber**, a component that implements `write()` ([I-UVM-2B](/curriculum/T2_Intermediate/I-UVM-2B_TLM_Connections/index)).
- The **upper layer** is the protocol your test thinks in (packets, commands). The **lower layer** is the protocol the agent actually drives (frames, bus transfers).

### Two meanings of "layering"

The word appears in job interviews, in the manuals of **verification IP** (VIP: a ready-made, reusable agent for a protocol) and in code reviews with two meanings. Keep them apart, because they solve different problems with different mechanisms.

| | Sequence layering | Protocol layering |
| --- | --- | --- |
| Problem it solves | Writing the same transaction patterns again and again | Testing a protocol that rides on top of the one your agent drives |
| What is layered | Sequences of the **same** item type | Item types of **different** protocols |
| Mechanism | A parent sequence starts child sequences: `child.start(m_sequencer, this)` | A translation sequence pulls upper items from an upper sequencer and sends lower items |
| Sequencers involved | One | Two: an upper sequencer with no driver, and the lower agent's sequencer |
| Where it lives | A sequence package next to the agent | A layering environment (or layering agent) around the lower agent |
| On this page | `bus_write_atomic_seq` inside `bus_burst_scenario_seq` | `ip_packet` items carried in `eth_frame` items |

The protocol-layering column gets its picture in "Protocol layering: the translation sequence" below. Here is the sequence-layering column: everything stays on one agent.

**How to choose.** If the test needs the same protocol at a higher level of abstraction ("program eight registers" instead of eight writes), use sequence layering. If the test needs a different protocol that travels inside the one your agent drives (packets inside frames, register commands inside a serial link), use protocol layering. Both can be combined: an upper-layer scenario sequence runs on the upper sequencer of a protocol layer.

There is a third use of the word. The top of a sequence stack is often a **virtual sequence**, a sequence that starts children on several agents' sequencers, for example configuration first and data second. That is the next lesson, [Virtual Sequences and Sequencers](/curriculum/T2_Intermediate/I-UVM-3B_Advanced_Sequencing_and_Layering/virtual-sequences); nothing on this page needs it.

### Sequence layering: atomic and scenario sequences

An **atomic sequence** sends exactly one item and exposes the fields a caller may want to choose. A **scenario sequence** composes atomic sequences into a pattern, here eight writes to consecutive word addresses. Both use the `bus_item` and the bus agent from [I-UVM-3A](/curriculum/T2_Intermediate/I-UVM-3A_Fundamentals/index): `op` is `BUS_READ` or `BUS_WRITE`, `addr` is 8 bits and word aligned, and `data` is 32 bits.

```systemverilog
// snippet: add to bus_pkg from I-UVM-3A (bus_item, BUS_WRITE)

// Atomic layer: one write. The caller chooses addr and data by randomizing
// this sequence (or by setting the fields) before start().
class bus_write_atomic_seq extends uvm_sequence #(bus_item);
  `uvm_object_utils(bus_write_atomic_seq)

  rand bit [7:0]  addr;
  rand bit [31:0] data;
  constraint c_word_aligned { addr[1:0] == 2'b00; }  // bus_item requires it too

  function new(string name = "bus_write_atomic_seq");
    super.new(name);
  endfunction

  virtual task body();
    req = bus_item::type_id::create("req");   // create before start_item
    start_item(req);
    // local:: makes addr and data mean this sequence's fields (IEEE 1800-2023 §18.7.1)
    if (!req.randomize() with { op == BUS_WRITE;
                                addr == local::addr;
                                data == local::data; })
      `uvm_fatal("RAND", "bus_item failed to randomize")
    finish_item(req);
  endtask
endclass

// Scenario layer: eight atomic writes at consecutive word addresses.
class bus_burst_scenario_seq extends uvm_sequence #(bus_item);
  `uvm_object_utils(bus_burst_scenario_seq)

  rand bit [7:0] base_addr;
  constraint c_base { base_addr[1:0] == 2'b00; base_addr <= 8'hE0; }  // 8 words fit

  function new(string name = "bus_burst_scenario_seq");
    super.new(name);
  endfunction

  virtual task body();
    bus_write_atomic_seq wr;
    for (int idx = 0; idx < 8; idx++) begin
      wr = bus_write_atomic_seq::type_id::create($sformatf("wr%0d", idx));
      if (!wr.randomize() with { addr == local::base_addr + local::idx * 4; })
        `uvm_fatal("RAND", "atomic write failed to randomize")
      wr.start(m_sequencer, this);   // same sequencer; this sequence is the parent
    end
  endtask
endclass
```

A test starts the scenario like any sequence, for example `burst.start(env.agt.sqr)` inside an objection. The scenario never touches a `bus_item`: if the bus later gains a byte-enable field, only `bus_write_atomic_seq` changes.

**What `wr.start(m_sequencer, this)` gives the child.** The first argument is the sequencer, the second is the **parent sequence** (IEEE 1800.2-2020 §14.2.3.1):
- **The same sequencer.** `m_sequencer` is the sequencer the scenario runs on, so the child's items go to the same driver.
- **The parent's priority.** A child started with the default priority takes its parent's priority; a sequence with no parent (a **root sequence**) gets 100.
- **The parent's hooks.** The parent's `pre_do()`, `mid_do()` and `post_do()` run for the child's execution, so a parent can watch or adjust what its children do.
- **A nested name.** The child's full name becomes `<parent full name>.wr3`, which tells you in the log which scenario sent an item.
- **The parent's lock.** If the parent holds a `lock()` on the sequencer, its children can still send; any other sequence waits (uvm-core 2020.3.1 `uvm_sequencer_base::is_blocked()`, which exempts children of the lock holder).

The same five points side by side, against a child started with no parent argument (a root sequence):

| Inside the scenario's `body()` | `wr.start(m_sequencer, this)` | `wr.start(m_sequencer)` |
| --- | --- | --- |
| Sequencer the child's items go to | `m_sequencer`, the scenario's | `m_sequencer`, the scenario's |
| Child's priority (default argument) | The parent's priority | 100 |
| The scenario's `pre_do()`, `mid_do()`, `post_do()` | Run for the child | Not run: the child has no parent |
| Child's full name | `<parent full name>.wr3` | `<sequencer full name>.wr3` |
| Scenario holds a `lock()` | The child is exempt and sends | The child is blocked; the scenario waits in `wr.start()` forever |

Sources: IEEE 1800.2-2020 §14.2.3.1 for the parent, priority and hooks; uvm-core 2020.3.1 `uvm_sequence_item::get_full_name()` for the names and `uvm_sequencer_base::is_blocked()` for the lock.

### Traced example: what `local::` changes

Inside `req.randomize() with { … }`, an unqualified name is looked up in the object being randomized first, and only then in the code that called `randomize()` (IEEE 1800-2023 §18.7.1). `bus_item` and `bus_write_atomic_seq` both have a field called `addr`, so the plain name always means the item's field. `local::` skips the item and means the caller's scope.

Suppose the atomic sequence was randomized with `addr = 8'h40`. Each row is a different way to write the `addr` part of the inline constraint:

| Constraint inside `bus_write_atomic_seq::body()` | Left side binds to | Right side binds to | `req.addr` after `randomize()` |
| --- | --- | --- | --- |
| `addr == addr` | `req.addr` | `req.addr` | any aligned address, for example `8'hB4`: the constraint is always true |
| `this.addr == addr` | `req.addr` (`this` means the randomized object) | `req.addr` | any aligned address |
| `addr == local::addr` | `req.addr` | the sequence's `addr` | `8'h40` |
| `addr == local::this.addr` | `req.addr` | the sequence's `addr` | `8'h40` |

The first two rows compile, run and pass every check you did not write: the sequence's field is silently ignored. That is why the checklist below asks for `local::` on every name that means a sequence field.

### Pitfalls of sequence layering

| Mistake | What you see | Fix |
| --- | --- | --- |
| **Forgetting to create the item.** `req` starts as `null` | `start_item(null)` stops the test with `UVM_FATAL [NULLITM] attempting to start a null item from sequence …` | Create a new item for every transfer |
| **Starting a child without `this` inside a locked parent.** The scenario calls `lock()` and then `wr.start(m_sequencer)` (no parent), so `wr` is a root sequence and is blocked by the lock | No error: the scenario waits inside `wr.start()` forever | Pass `this`, or do not lock |
| **Ignoring a failed child randomization** | If `wr.randomize()` fails, `addr` and `data` keep their old values (zero for a new object) and the write goes to the wrong place | Check the result and stop with `` `uvm_fatal `` |
| **Starting the same child object twice at once.** A sequence object can run only once at a time | A second `start()` while it runs is `UVM_FATAL [SEQ_NOT_DONE]` | Create a new child per start, as the loop does |

### Protocol layering: the translation sequence

Now the second meaning. The running example is a simplified IP-over-Ethernet stack. The field names are made up for teaching, not the real IPv4 or Ethernet formats:
- `ip_packet` (upper layer) has an `id` and 1 to 16 bytes of `data`;
- `eth_frame` (lower layer) has an `ethertype` (`16'h0800` marks an IP payload), a `more` bit (1 when more frames of the same packet follow), and a `payload` byte queue.

You already have an Ethernet agent: `eth_agt`, with its sequencer `eth_agt.sqr` and driver `eth_agt.drv`. You want tests to send IP packets without knowing about frames. Three pieces do it, and none of them is a new driver:
1. **An upper sequencer with no driver**, `ip_sqr`, of type `uvm_sequencer #(ip_packet)`. Ordinary IP sequences run on it, exactly as they would on an agent's sequencer. Nothing is connected to its `seq_item_export`; uvm-core 2020.3.1 does not report that as an error.
2. **A translation sequence**, `xlate` of class `ip_to_eth_seq`, which runs **on the Ethernet sequencer** and plays the IP layer's driver. A `uvm_sequencer` implements the driver-side methods itself (`get_next_item`, `item_done`, `get`; IEEE 1800.2-2020 §15.5.2.3 to §15.5.2.6); a driver's `seq_item_port` normally just forwards to them. So the translation sequence can call `ip_sqr.get_next_item(pkt)` through a plain handle.
3. **A layered monitor**, `ip_mon`, which subscribes to the Ethernet side and rebuilds packets (next subsection).

The heart of the translation sequence is a loop that behaves like a driver on one side and like a sequence on the other:

```systemverilog
// snippet: the body() of ip_to_eth_seq (the complete class is in Make It Work)
forever begin
  ip_sqr.get_next_item(pkt);         // driver side of the IP layer: wait for a packet
  frm = eth_frame::type_id::create("frm");
  start_item(frm);                   // sequence side of the Ethernet layer
  frm.ethertype = 16'h0800;
  frm.more      = 0;                 // one frame per packet in this version
  frm.payload   = pkt.to_bytes();
  finish_item(frm);                  // returns after eth_agt.drv calls item_done()
  ip_sqr.item_done();                // only now does the IP finish_item() return
end
```

**What the diagram shows.**
- The IP sequence's `finish_item()` returns at 10 ns, when the frame has been driven. Because the translation sequence calls `ip_sqr.item_done()` *after* its own `finish_item(frm)`, the upper layer keeps the meaning it has on any agent: "the driver has finished with my item". (IEEE 1800.2-2020 §14.2.6.3 notes that `finish_item()` returning means the driver signalled completion, not necessarily that all its processing is done; here the loopback driver signals after driving.)
- The upper sequencer's grant still comes from a "driver" asking, exactly as in the handshake you know. The only difference is that the asker is a sequence.
- The frames are ordinary Ethernet items. If other Ethernet sequences run on `eth_agt.sqr` at the same time, the translation sequence's frames are arbitrated against theirs ([Sequence Arbitration](/curriculum/T2_Intermediate/I-UVM-3B_Advanced_Sequencing_and_Layering/sequence-arbitration)).

**Pitfalls of the translation sequence.**
- **Calling `ip_sqr.item_done()` too early**, for example right after `get_next_item()`. The IP sequence's `finish_item()` then returns before the frame is driven, so the upper layer runs ahead of the wire, and a test that drops its objection when the IP sequence ends can end before the last frame is sent. Make It Work shows the log.
- **Using `ip_sqr.get(pkt)` instead of `get_next_item()`.** `get()` calls `item_done()` immediately (uvm-core 2020.3.1 `uvm_sequencer::get()`; §15.5.2.6), which is the same early completion.
- **Sharing one payload between frames.** Build each frame's `payload` from the packet's bytes; never keep one frame object and refill it, because subscribers may still hold the handle you published.

### Where the translation sequence lives, and how it ends

If every test had to start `xlate`, every test would also have to know about Ethernet. So the **layering environment** (`layer_env` here) builds `ip_sqr`, and its `run_phase` creates `xlate`, gives it the `ip_sqr` handle and starts it on `eth_agt.sqr`. Tests only start IP sequences on `env.ip_sqr`. Some VIPs package the same pieces as a **layering agent**: an agent whose sequencer is the upper sequencer and whose "driver" side is the translation sequence.

The translation sequence's `body()` is a `forever` loop, so it never ends by itself. Two consequences:
- **It does not keep the test alive.** Only objections do ([I-UVM-1C](/curriculum/T2_Intermediate/I-UVM-1C_UVM_Phasing/index)). The test raises an objection around its IP sequences; when it drops it, the run phase may end even though `xlate` is still running.
- **Stop it on purpose.** When the run phase ends, UVM kills the processes it started for the phase (a **process** is one running thread of SystemVerilog code, such as a component's `run_phase` task and everything it is waiting in). Rather than leave the translation sequence to be killed that way, stop it explicitly once the test is finished: `layer_env` calls `xlate.kill()` (IEEE 1800.2-2020 §14.2.5.11) from `phase_ready_to_end()` (§13.1.4.3.2), which UVM calls on every component when all run-phase objections have been dropped. Push Further explains why this matters in uvm-core 2020.3.1.

### The way back up: layered monitors

Checks and coverage must use what was actually sent, not what a sequence intended: a sequence knows what it *tried*, which can differ from what happened (a dropped, reordered or corrupted frame). So the upper layer gets its own monitor, fed by the lower layer.

`ip_mon` is a subscriber of Ethernet frames. For every frame with `ethertype == 16'h0800` it appends the payload bytes to a buffer; when a frame with `more == 0` arrives, it builds a **new** `ip_packet` object from the buffer and writes it to its own analysis port `ap`. The IP scoreboard and IP coverage subscribe to `ip_mon.ap`, while Ethernet-level checks and coverage stay on the Ethernet monitor. In a pin-level agent, the Ethernet frames come from the Ethernet monitor; in the Make It Work example, which has no pins, the loopback driver publishes each frame it finishes on `wire_ap` instead.

Each layer's checks look at that layer's rules:

| Layer | Its checks look at | Its coverage | Its checkers subscribe to |
| --- | --- | --- | --- |
| **Lower layer** (Ethernet) | Frame format, `ethertype`, payload length | Frame-level (see "Checking and coverage per layer" in Push Further) | The Ethernet monitor (in Make It Work, the loopback driver's `wire_ap`) |
| **Upper layer** (IP) | Every packet arrives once, in order, with the right contents | Packet-level coverage (sizes, ids, sequences of packet types) | `ip_mon.ap` |

**Find the bug yourself.** Why does `ip_mon` build a new object for every packet? A new object per rebuilt packet matters: an analysis port passes handles, and a subscriber such as a `uvm_tlm_analysis_fifo` stores the handle it receives without copying it. If `ip_mon` reused one packet object, every stored entry would change when the next packet arrives ([I-UVM-2B](/curriculum/T2_Intermediate/I-UVM-2B_TLM_Connections/index) shows this bug).

### Practitioner depth: debugging a layered stack

| Symptom in the log | Cause | Fix |
| --- | --- | --- |
| No Ethernet frames at all; the IP sequence never returns from `start_item()`; the run ends with `UVM_FATAL … [PH_TIMEOUT] Default timeout of … hit, indicating a probable testbench issue` | Nobody started the translation sequence, so nothing calls `get_next_item()` on `ip_sqr` and its arbitration never grants | Start `xlate` in the layering environment's `run_phase`, with `xlate.ip_sqr` set first |
| `UVM_FATAL [XLATE] ip_sqr was not set before start()` (the example's own check) or a null-handle error from the simulator | `xlate.ip_sqr` was never assigned | Assign it before `xlate.start()` |
| The IP sequence logs "delivered" before the matching frame is driven; the test ends early and the IP scoreboard reports a missing packet | `ip_sqr.item_done()` is called before the frame's `finish_item()` returns, or `ip_sqr.get()` is used | Call `ip_sqr.item_done()` after the last frame for the packet |
| Frames are driven but the IP scoreboard sees nothing and reports a count error in `check_phase` | The lower layer's analysis port is not connected to the layered monitor | Connect it in the environment's `connect_phase` |
| After a mid-test restart of the layer, `Get_next_item called twice without item_done or get in between`, and an old packet is sent again | The translation sequence was killed between `get_next_item()` and `item_done()`, leaving `ip_sqr`'s handshake open | Reset both sequencers first; see "Reset and restart of a layered stack" in Push Further |
| Stored packets in a scoreboard queue all show the latest values | The layered monitor reuses one packet object | Create a new `ip_packet` per rebuilt packet |

### Recap

- **Sequence layering:** atomic sequences send one item; scenario sequences start them with `child.start(m_sequencer, this)`; every name that means a sequence field inside `randomize() with` gets `local::`.
- **Protocol layering:** an upper sequencer with no driver, a translation sequence on the lower sequencer that calls `get_next_item()` and `item_done()` on the upper sequencer, and a layered monitor that rebuilds upper items for upper-layer checks and coverage.
- **Timing:** the upper `finish_item()` returns when the translation sequence calls `item_done()`; call it after the last lower item, so it still means "delivered".
- **Ownership:** the layering environment starts the translation sequence and stops it at the end of the test; tests only start upper-layer sequences.

## Make It Work

### A layered IP-over-Ethernet stack with no DUT

This example builds the stack from the diagram: `ip_packet` and `eth_frame`; a loopback Ethernet driver that takes 10 ns per frame and publishes each finished frame on `wire_ap`; the Ethernet agent; the driverless `ip_sqr`; the translation sequence; the layered monitor `ip_mon`; an IP scoreboard that checks that packets arrive once and in order; the layering environment; an IP sequence that knows nothing about Ethernet; a test; and `tb_top`.

**Run it.** Compile uvm-core 2020.3.1 (or your simulator's built-in UVM library) together with this file, with `tb_top` as the top module, and run. `run_test("layer_test")` names the test. The exact compile and run switches are tool-dependent. No simulator was available to the course authors, so the code was checked by reading it against IEEE 1800-2023 and the uvm-core 2020.3.1 source, and the output below is illustrative.

```systemverilog
// compile
// tb_top.sv: a layered IP-over-Ethernet stack (simplified formats, no DUT)
`include "uvm_macros.svh"

package layer_pkg;
  timeunit 1ns;
  timeprecision 1ps;

  import uvm_pkg::*;

  typedef byte unsigned bytes_t[$];

  // Upper layer: a simplified packet (not the real IPv4 header format).
  class ip_packet extends uvm_sequence_item;
    rand bit [7:0]     id;
    rand byte unsigned data[];

    constraint c_len { data.size() inside {[1:16]}; }

    `uvm_object_utils(ip_packet)

    function new(string name = "ip_packet");
      super.new(name);
    endfunction

    // Wire format: id, length, then the data bytes.
    function bytes_t to_bytes();
      bytes_t b;
      b.push_back(id);
      b.push_back(8'(data.size()));
      foreach (data[i]) b.push_back(data[i]);
      return b;
    endfunction

    function void from_bytes(bytes_t b);
      id   = b[0];
      data = new[b[1]];
      foreach (data[i]) data[i] = b[i + 2];
    endfunction

    virtual function string convert2string();
      return $sformatf("id=%0d len=%0d", id, data.size());
    endfunction
  endclass

  // Lower layer: a simplified frame (not the real Ethernet frame format).
  class eth_frame extends uvm_sequence_item;
    bit [15:0] ethertype;  // 16'h0800: the payload is (part of) an ip_packet
    bit        more;       // 1: more frames of the same packet follow
    bytes_t    payload;

    `uvm_object_utils(eth_frame)

    function new(string name = "eth_frame");
      super.new(name);
    endfunction

    virtual function string convert2string();
      return $sformatf("type=0x%04h more=%0b bytes=%0d",
                       ethertype, more, payload.size());
    endfunction
  endclass

  typedef uvm_sequencer #(ip_packet) ip_sequencer;   // upper layer: no driver
  typedef uvm_sequencer #(eth_frame) eth_sequencer;

  // Loopback driver: no pins. Each frame takes 10 ns. It publishes every
  // finished frame on wire_ap, standing in for a pin-level Ethernet monitor.
  class eth_driver extends uvm_driver #(eth_frame);
    `uvm_component_utils(eth_driver)

    uvm_analysis_port #(eth_frame) wire_ap;

    function new(string name, uvm_component parent);
      super.new(name, parent);
    endfunction

    virtual function void build_phase(uvm_phase phase);
      super.build_phase(phase);
      wire_ap = new("wire_ap", this);
    endfunction

    virtual task run_phase(uvm_phase phase);
      forever begin
        seq_item_port.get_next_item(req);
        #10ns;                                  // "drive" the frame
        `uvm_info("DRV", req.convert2string(), UVM_LOW)
        wire_ap.write(req);                     // what went on the wire
        seq_item_port.item_done();
      end
    endtask
  endclass

  class eth_agent extends uvm_agent;
    `uvm_component_utils(eth_agent)

    eth_sequencer sqr;
    eth_driver    drv;

    function new(string name, uvm_component parent);
      super.new(name, parent);
    endfunction

    virtual function void build_phase(uvm_phase phase);
      super.build_phase(phase);
      sqr = eth_sequencer::type_id::create("sqr", this);
      drv = eth_driver::type_id::create("drv", this);
    endfunction

    virtual function void connect_phase(uvm_phase phase);
      drv.seq_item_port.connect(sqr.seq_item_export);
    endfunction
  endclass

  // Plays the IP layer's driver: pulls each packet from ip_sqr and sends it
  // as one frame on the Ethernet sequencer it was started on.
  class ip_to_eth_seq extends uvm_sequence #(eth_frame);
    `uvm_object_utils(ip_to_eth_seq)

    ip_sequencer ip_sqr;   // the upper sequencer; set by layer_env before start()

    function new(string name = "ip_to_eth_seq");
      super.new(name);
    endfunction

    virtual task body();
      ip_packet pkt;
      eth_frame frm;
      if (ip_sqr == null)
        `uvm_fatal("XLATE", "ip_sqr was not set before start()")
      forever begin
        ip_sqr.get_next_item(pkt);              // wait for the next IP packet
        frm = eth_frame::type_id::create("frm");
        start_item(frm);                        // wait for the Ethernet grant
        frm.ethertype = 16'h0800;
        frm.more      = 0;                      // 1:1 here: one frame per packet
        frm.payload   = pkt.to_bytes();
        finish_item(frm);                       // returns after the frame is driven
        ip_sqr.item_done();                     // releases the IP finish_item()
      end
    endtask
  endclass

  // Layered monitor: rebuilds IP packets from the frames seen on the wire.
  class ip_monitor extends uvm_subscriber #(eth_frame);
    `uvm_component_utils(ip_monitor)

    uvm_analysis_port #(ip_packet) ap;
    bytes_t pending;   // bytes of a packet whose last frame has not arrived

    function new(string name, uvm_component parent);
      super.new(name, parent);
    endfunction

    virtual function void build_phase(uvm_phase phase);
      super.build_phase(phase);
      ap = new("ap", this);
    endfunction

    virtual function void write(eth_frame t);
      ip_packet pkt;
      if (t.ethertype != 16'h0800) return;    // not an IP frame
      pending = {pending, t.payload};
      if (t.more) return;                     // wait for the last frame
      if (pending.size() < 2 || pending.size() != pending[1] + 2)
        `uvm_error("IP_MON", $sformatf("malformed packet: %0d bytes", pending.size()))
      else begin
        pkt = ip_packet::type_id::create("pkt");   // a new object per packet
        pkt.from_bytes(pending);
        ap.write(pkt);
      end
      pending.delete();
    endfunction
  endclass

  // Upper-layer check: every packet arrives exactly once, in order.
  class ip_scoreboard extends uvm_subscriber #(ip_packet);
    `uvm_component_utils(ip_scoreboard)

    int unsigned n_expected;   // set by the test
    int unsigned n_seen;

    function new(string name, uvm_component parent);
      super.new(name, parent);
    endfunction

    virtual function void write(ip_packet t);
      if (t.id != n_seen)
        `uvm_error("IP_SB", $sformatf("expected id=%0d, got %s",
                                      n_seen, t.convert2string()))
      else
        `uvm_info("IP_SB", {"in order: ", t.convert2string()}, UVM_LOW)
      n_seen++;
    endfunction

    virtual function void check_phase(uvm_phase phase);
      super.check_phase(phase);
      if (n_seen != n_expected)
        `uvm_error("IP_SB", $sformatf("expected %0d packets, saw %0d",
                                      n_expected, n_seen))
      else
        `uvm_info("IP_SB", $sformatf("%0d of %0d packets received",
                                     n_seen, n_expected), UVM_LOW)
    endfunction
  endclass

  // The layering environment: tests see only ip_sqr.
  class layer_env extends uvm_env;
    `uvm_component_utils(layer_env)

    eth_agent     eth_agt;
    ip_sequencer  ip_sqr;
    ip_monitor    ip_mon;
    ip_scoreboard ip_sb;
    ip_to_eth_seq xlate;

    function new(string name, uvm_component parent);
      super.new(name, parent);
    endfunction

    virtual function void build_phase(uvm_phase phase);
      super.build_phase(phase);
      eth_agt = eth_agent::type_id::create("eth_agt", this);
      ip_sqr  = ip_sequencer::type_id::create("ip_sqr", this);
      ip_mon  = ip_monitor::type_id::create("ip_mon", this);
      ip_sb   = ip_scoreboard::type_id::create("ip_sb", this);
    endfunction

    virtual function void connect_phase(uvm_phase phase);
      eth_agt.drv.wire_ap.connect(ip_mon.analysis_export);
      ip_mon.ap.connect(ip_sb.analysis_export);
    endfunction

    // The layer runs for the whole test, so no test has to start it.
    virtual task run_phase(uvm_phase phase);
      xlate = ip_to_eth_seq::type_id::create("xlate");
      xlate.ip_sqr = ip_sqr;
      xlate.start(eth_agt.sqr);   // never returns: body() is a forever loop
    endtask

    // All run-phase objections are dropped: stop the endless layer cleanly
    // instead of leaving it to be killed with the phase's processes.
    virtual function void phase_ready_to_end(uvm_phase phase);
      super.phase_ready_to_end(phase);
      if (phase.get_name() == "run" && xlate != null)
        xlate.kill();
    endfunction
  endclass

  // Upper-layer stimulus: knows nothing about frames.
  class ip_burst_seq extends uvm_sequence #(ip_packet);
    `uvm_object_utils(ip_burst_seq)

    int unsigned n_pkts = 3;

    function new(string name = "ip_burst_seq");
      super.new(name);
    endfunction

    virtual task body();
      for (int i = 0; i < n_pkts; i++) begin
        req = ip_packet::type_id::create("req");
        start_item(req);
        if (!req.randomize() with { id == local::i; })
          `uvm_fatal("RAND", "ip_packet failed to randomize")
        finish_item(req);   // returns when xlate calls ip_sqr.item_done()
        `uvm_info("IP_SEQ", $sformatf("packet %0d delivered", req.id), UVM_LOW)
      end
    endtask
  endclass

  class layer_test extends uvm_test;
    `uvm_component_utils(layer_test)

    layer_env env;

    function new(string name, uvm_component parent);
      super.new(name, parent);
    endfunction

    virtual function void build_phase(uvm_phase phase);
      super.build_phase(phase);
      env = layer_env::type_id::create("env", this);
    endfunction

    virtual task run_phase(uvm_phase phase);
      ip_burst_seq seq = ip_burst_seq::type_id::create("seq");
      env.ip_sb.n_expected = seq.n_pkts;
      phase.raise_objection(this, "IP traffic running");
      seq.start(env.ip_sqr);              // the upper sequencer, not eth_agt.sqr
      phase.drop_objection(this, "IP traffic done");
    endtask
  endclass
endpackage

module tb_top;
  timeunit 1ns;
  timeprecision 1ps;

  import uvm_pkg::*;
  import layer_pkg::*;

  initial run_test("layer_test");
endmodule
```

2. **Declare the upper sequencer** with a `typedef` of `uvm_sequencer #(upper_item)`. Do not give it a driver.
3. **Write the translation sequence** as a `uvm_sequence #(lower_item)` with a handle to the upper sequencer. In a `forever` loop: `get_next_item()` on the upper sequencer, send one or more lower items with `start_item()`/`finish_item()`, then `item_done()` on the upper sequencer.
4. **Write the layered monitor** as a subscriber of the lower layer that publishes a new upper item on its own analysis port whenever one is complete.
5. **Build the layering environment:** the lower agent, the upper sequencer, the layered monitor and the upper checks. Connect the analysis ports in `connect_phase`.
6. **Start the translation sequence in the environment's `run_phase`**, after setting its upper-sequencer handle, and stop it in `phase_ready_to_end()` for the run phase.

## Push Further

### Expert: Layering through a pull port

Instead of giving the translation sequence a handle to the upper sequencer, a layering agent can give a component a `uvm_seq_item_pull_port #(ip_packet)` (IEEE 1800.2-2020 §15.2.2.1) and connect it to `ip_sqr.seq_item_export` in `connect_phase`, exactly as a driver would. The translation sequence then calls `get_next_item()` and `item_done()` through that port.
- **What you gain:** the connection is made and type-checked like any TLM connection (a port with the wrong item type does not compile), and the layering looks like a normal agent to anyone reading the topology.
- **What to watch:** `uvm_seq_item_pull_port` has a default `min_size` of 0, so an unconnected port is not an error (uvm-core 2020.3.1 `uvm_sqr_connections.svh`). UVM then reports nothing when it resolves the connections, and the port's interface handle stays null: in uvm-core 2020.3.1, `uvm_port_base::resolve_bindings()` sets it only when the port has at least one connection, and the port's `get_next_item()` simply calls through that handle. Construct it with `min_size` 1, `new("ip_port", this, 1)`, if you want the error `connection count of 0 does not meet required minimum of 1` when UVM resolves the port connections, before the run phase, instead of a null-handle error from the simulator at the first `get_next_item()` at run time.

| | Plain handle (`xlate.ip_sqr = ip_sqr`) | Pull port, default `min_size` 0 | Pull port, `min_size` 1 |
| --- | --- | --- | --- |
| How it is connected | Assigned before `xlate.start()` | `connect()` to `ip_sqr.seq_item_export` in `connect_phase` | The same |
| Item type checked | At compile time, by the handle's declared type (`ip_sequencer`) | At compile time, by the port's parameter | At compile time |
| If nobody connects it | A null handle: the example's `XLATE` fatal, or the simulator's null-handle error at run time | No UVM message at elaboration; the first `get_next_item()` through the port dereferences a null interface handle, a simulator null-handle error at run time (uvm-core 2020.3.1 `uvm_port_base`: the handle is set only when the port has a connection) | Error `connection count of 0 does not meet required minimum of 1` before the run phase |

### Expert: One-to-many and many-to-one translation

- **Fragmentation (one upper item, several lower items).** Send every fragment, then call `ip_sqr.item_done()` once, after the last one. The upper `finish_item()` then still means "the whole packet was sent". The kata below builds this.
- **Aggregation (several upper items, one lower item).** The upper sequencer lets its "driver" hold only one item at a time: a second `get_next_item()` before `item_done()` logs `Get_next_item called twice without item_done or get in between` and returns the same item again (uvm-core 2020.3.1 `uvm_sequencer::get_next_item()`). To pack several packets into one frame, the translation sequence must complete each packet (`item_done()`, or `get()`) before pulling the next, and only then send the frame. The upper `finish_item()` therefore no longer means "delivered", and an upper sequence that ends after its last `finish_item()` can let the test end before the frame is sent. Keep an objection, or a flush of the partial frame, until the lower layer has caught up.

| | Fragmentation | Aggregation |
| --- | --- | --- |
| Items | One upper item, several lower items | Several upper items, one lower item |
| When the upper item is completed | `ip_sqr.item_done()` once, after the last fragment's `finish_item()` returns | `item_done()` (or `get()`) for each packet before pulling the next, so before the frame is sent |
| What the upper `finish_item()` returning means | The whole packet was sent | Only that the translation sequence has taken the packet: not "delivered" |
| End-of-test risk | None beyond the 1:1 case | The test can end before the frame is sent |
| Mitigation | Nothing extra | Keep an objection, or flush the partial frame, until the lower layer has caught up |

Why aggregation cannot simply hold several packets open: the upper sequencer allows one outstanding item. See the rule you just read (a second `get_next_item()` before `item_done()`) happen in the driver-side version of that mistake below; the same rule applies when the "driver" is a translation sequence.

### Expert: Responses across layers

### Expert: Reset and restart of a layered stack

A mid-test reset that kills the translation sequence between `ip_sqr.get_next_item()` and `ip_sqr.item_done()` leaves `ip_sqr` believing its "driver" still holds an item. The restarted translation sequence's first `get_next_item()` then logs `Get_next_item called twice without item_done or get in between` and is handed the old packet again, because it is still at the head of `ip_sqr`'s request FIFO.

Reset both layers before restarting: `ip_sqr.stop_sequences()` and `eth_agt.sqr.stop_sequences()` (IEEE 1800.2-2020 §15.3.2.14). In uvm-core 2020.3.1, `uvm_sequencer::stop_sequences()` kills every sequence registered on that sequencer, clears the "item outstanding" flags and flushes the request FIFO. The translation sequence is registered on the Ethernet sequencer, so the second call stops it; the first stops the IP sequences. Then restart the translation sequence and let the test restart its upper traffic.

The state of `ip_sqr` just before the new translation sequence starts, in uvm-core 2020.3.1:

| `ip_sqr` state | Kill `xlate` only | `stop_sequences()` on `ip_sqr` and `eth_agt.sqr` |
| --- | --- | --- |
| "Item outstanding" flag (set by `get_next_item()`, cleared by `item_done()`) | Still set | Cleared |
| Request FIFO | The old packet is still at its head | Flushed |
| Sequences registered on it | The IP sequences still run | Killed |
| The new translation sequence's first `get_next_item()` | Logs `Get_next_item called twice without item_done or get in between` and returns the old packet | Waits for a new packet |

### Expert: Ending the test with an endless layer

Why does `layer_env` kill `xlate` itself? Reading the uvm-core 2020.3.1 source (not confirmed by a simulation run): `start()` creates a process guard that watches the process that called it, and the guard's watcher runs in a thread started by `run_test()`, outside the run phase. When the run phase ends, UVM kills the phase's processes, including the one that called `xlate.start()`. The guard then fires, reports `UVM_WARNING [SEQPRTZMB] The parent process that called start() on sequence … was terminated without killing the sequence`, and kills the sequence (`uvm_sequence_base.svh`, `process_guard_triggered()`). Calling `xlate.kill()` first ends the sequence normally, and `kill()` clears the guard. This is uvm-core implementation behaviour, not part of IEEE 1800.2-2020; other UVM libraries may report nothing in either case (tool-dependent).

The same applies to every endless background sequence: responders, translation layers, interrupt service sequences. Stop them when the stimulus is finished, before the phase ends.

### Expert: Several upper protocols on one lower agent

A real link often carries more than one upper protocol, for example IP packets and control messages. Give each upper protocol its own upper sequencer, its own translation sequence and its own layered monitor (which filters by a type field such as `ethertype`). All the translation sequences run on the same lower sequencer, so their frames are **arbitrated** there like any other sequences. Under the default `UVM_SEQ_ARB_FIFO` mode, requests are granted in arrival order and priority is ignored; `UVM_SEQ_ARB_WEIGHTED` grants randomly by weight, so a higher priority wins more often but not always; only the `STRICT` modes always grant the highest priority first (IEEE 1800.2-2020 Annex F.2.4.1). If one protocol must never be delayed by another, the arbitration mode is part of your layering design ([Sequence Arbitration](/curriculum/T2_Intermediate/I-UVM-3B_Advanced_Sequencing_and_Layering/sequence-arbitration)).

### Expert: Checking and coverage per layer

Give each layer a monitor, a scoreboard for that layer's rules and its own coverage. Lower-layer coverage answers "did we exercise frame lengths, back-to-back frames and the `more` bit?"; upper-layer coverage answers "did we exercise packet sizes, ids and packet sequences?". Comparing upper items end to end (sent by the test against rebuilt by the monitor) catches bugs in the translation sequence and in the monitor alike, so one of them must be written from the protocol specification, not from the other. A full predictor and scoreboard design is in [A-UVM-6](/curriculum/T3_Advanced/A-UVM-6_Scoreboards_and_Reference_Models/index), and packaging the layer as reusable VIP is in [A-UVM-7](/curriculum/T3_Advanced/A-UVM-7_VIP_Construction/index).

### Kata: a fragmenting translation sequence

**Task.** Starting from the Make It Work file:
1. Change `ip_to_eth_seq` so that each frame carries at most 4 payload bytes. Set `more = 1` on every frame of a packet except the last.
2. Call `ip_sqr.item_done()` only after the last frame of the packet.
3. Do not change `ip_monitor`: it already rebuilds a packet from several frames.
4. Predict the log for one packet with `len=5`: how many `DRV` lines, their `more` values, and when `packet 0 delivered` appears.

**Acceptance:** every `DRV` line has `bytes` of 4 or less, `IP_SB` reports every packet in order, and `UVM_ERROR :    0`.

<details>
<summary>Worked solution (try it first)</summary>

```systemverilog
// snippet: replaces ip_to_eth_seq in layer_pkg
class ip_to_eth_seq extends uvm_sequence #(eth_frame);
  `uvm_object_utils(ip_to_eth_seq)

  ip_sequencer ip_sqr;
  int unsigned max_bytes = 4;   // payload bytes per frame

  function new(string name = "ip_to_eth_seq");
    super.new(name);
  endfunction

  virtual task body();
    ip_packet pkt;
    eth_frame frm;
    bytes_t   bytes;
    if (ip_sqr == null)
      `uvm_fatal("XLATE", "ip_sqr was not set before start()")
    forever begin
      ip_sqr.get_next_item(pkt);
      bytes = pkt.to_bytes();
      while (bytes.size() > 0) begin
        frm = eth_frame::type_id::create("frm");
        start_item(frm);
        frm.ethertype = 16'h0800;
        for (int k = 0; k < max_bytes && bytes.size() > 0; k++)
          frm.payload.push_back(bytes.pop_front());
        frm.more = (bytes.size() > 0);   // more fragments follow
        finish_item(frm);
      end
      ip_sqr.item_done();   // after the last fragment: the packet is delivered
    end
  endtask
endclass
```

**Prediction for one packet with `len=5`:** the packet is 7 bytes (id, length, 5 data bytes), so two frames: `more=1 bytes=4` at 10 ns and `more=0 bytes=3` at 20 ns. `ip_mon` publishes the packet when the second frame arrives, so `IP_SB in order: id=0 len=5` and then `packet 0 delivered` both appear at 20 ns.

### Debug challenge: the IP test that never sends a frame

A colleague's layered test produces this log and nothing else before the fatal (illustrative; the reporter and the timeout value are shown as `…`):

```text
UVM_INFO @ 0: reporter [RNTST] Running test layer_test...
UVM_FATAL … [PH_TIMEOUT] Default timeout of … hit, indicating a probable testbench issue
```

Their `layer_env::run_phase` is:

```systemverilog
// snippet: the colleague's layer_env::run_phase
virtual task run_phase(uvm_phase phase);
  xlate = ip_to_eth_seq::type_id::create("xlate");
  xlate.ip_sqr = ip_sqr;
  xlate.start(ip_sqr);
endtask
```

Before you open the answer: which sequencer is `xlate` running on, who calls `get_next_item()` on `ip_sqr`, and why is there no fatal message from `start_item()`?

<details>
<summary>Answer</summary>

`xlate` was started on `ip_sqr` instead of `eth_agt.sqr`. It calls `ip_sqr.get_next_item(pkt)`, gets the first packet, and then calls `start_item(frm)` **on `ip_sqr`**, because that is its `m_sequencer`. That request needs a grant on `ip_sqr`, and the only "driver" of `ip_sqr` is `xlate` itself, which is now waiting inside `start_item()`. Nothing is wrong with any handle, so there is no fatal: the stack is a silent deadlock until the phase timeout. Meanwhile `eth_agt.drv` waits forever in `get_next_item()`, so no `DRV` line appears.
