## Quick Take

- **What it is:** A **sequence library** is a sequence (`uvm_sequence_library`, IEEE 1800.2-2020 §14.4) that holds a list of sequence *types*, its **members**. When you start it like any other sequence, it picks members by its **selection mode**, creates a fresh member object for each pick, and runs it on its own sequencer, a given number of times.
- **Why it matters:** One `start()` call runs a random mix of every scenario you have registered, and a new scenario joins the mix by registering itself, without anyone editing the test. That makes a library a cheap way to get broad, seed-driven regression stimulus from sequences you already wrote.
- **The Analogy:** A library is a playlist on shuffle. RAND is shuffle with repeats, RANDC plays every song once before any repeats, ITEM ignores the songs and plays random notes, and USER is your own DJ rule. *Where it breaks:* a playlist stores recordings, but a library stores song *types* and records a brand-new song (a new, freshly randomized sequence object) every time it plays one. And it plays one song at a time on one speaker: a library never runs two members at once or drives two sequencers.

**You will be able to:**
1. Write a `uvm_sequence_library` subtype, register member sequences with it, and run it from a test or as a phase default sequence.
2. Predict which members, and how many, a library runs for each selection mode and count setting.
3. Bias a library's mix with a USER-mode `select_sequence()`, and explain why registering a type twice is not a portable way to do it.
4. Debug the common library failures from the log: `SEQLIB/NOSEQS`, a count that is ignored, the ITEM-mode fallback, and member hooks that never run.
5. Decide when a library is the right tool, and how its members share the sequencer with other sequences, compared with a virtual sequence or a directed test.

### What a sequence library is

Suppose you have three scenario sequences for a memory interface: a write, a read and a write to an unmapped address. A regression test should run a random mix of them. Without a library you write the loop yourself:

```systemverilog
// snippet: the loop a library writes for you (inside some sequence's body())
repeat (n) begin
  uvm_sequence_base s;
  case ($urandom_range(2))
    0: s = wr_seq::type_id::create("wr");
    1: s = rd_seq::type_id::create("rd");
    2: s = err_seq::type_id::create("err");
  endcase
  if (!s.randomize()) `uvm_fatal("RAND", "member randomization failed")
  s.start(m_sequencer, this);
end
```

This works, but every new scenario means editing the `case`, and every team writes the loop slightly differently. A `uvm_sequence_library` is that loop, written once, with an *open* member list (§14.4):

- It **is a sequence**: `uvm_sequence_library #(REQ, RSP)` extends `uvm_sequence #(REQ, RSP)` (§14.4.1), so you create it with the factory and run it with `start()`.
- It holds a queue of member **types**. Members join by registering, from their own class or from code, so the library class never names them.
- When started, it runs `sequence_count` picks. For each pick it chooses an index into the member queue by its **selection mode**, creates a new member with the factory, randomizes it and starts it on the library's sequencer.

**Where it lives in a testbench.** A library usually sits next to the agent's sequences, in the agent's or the environment's package. A test, or the sequencer's default-sequence setting, starts it on one agent's sequencer. It is the "random mix of known scenarios" layer, between the individual scenario sequences below it and the test above it.

### Registering members

A library subtype needs two macros and, in uvm-core 2020.3.1, one call in its constructor:

```systemverilog
// snippet: a library subtype (uvm-core 2020.3.1)
class mem_seq_lib extends uvm_sequence_library #(mem_item);
  `uvm_object_utils(mem_seq_lib)
  `uvm_sequence_library_utils(mem_seq_lib)

  function new(string name = "mem_seq_lib");
    super.new(name);
    init_sequence_library();   // copy the registered types into this object
  endfunction
endclass
```

- `` `uvm_sequence_library_utils(mem_seq_lib) `` gives the subtype its own **static** member list (a static class variable is one variable shared by every object of the class), plus the functions that fill it (Annex B.3.2.2).
- `init_sequence_library()` copies that static list into this object's own queue, `sequences`. In uvm-core 2020.3.1 the subtype's constructor must call it. The standard's own example constructor (§14.4.2) calls only `super.new(name)`; code copied from it compiles, but the library is empty and reports `SEQLIB/NOSEQS` when started.

There are three ways to add a member. The first runs during **static initialization**: the step, before any `initial` or `always` procedure starts, in which the simulator gives every static variable its declared initial value (IEEE 1800-2023 §10.5).

| Way | Code | Who sees it | When it takes effect |
| --- | --- | --- | --- |
| Static, from the member's class | `` `uvm_add_to_seq_lib(wr_seq, mem_seq_lib) `` inside `wr_seq` (Annex B.3.2.1) | every `mem_seq_lib` | during static initialization, before any `initial` procedure runs, so before `run_test()` |
| Static, from code | `mem_seq_lib::add_typewide_sequence(wr_seq::get_type())`, or `add_typewide_sequences(q)` for a queue (§14.4.5.1, §14.4.5.2) | every `mem_seq_lib` built **afterwards** | at the call; libraries already constructed are not changed |
| One instance | `lib.add_sequence(wr_seq::get_type())`, or `lib.add_sequences(q)` (§14.4.5.3, §14.4.5.4) | this `lib` only | at the call; do it after `create()` and before `start()` |

The macro expands to a static `bit` whose initializer calls the library's registration function, which is why it runs before the test starts. A member class can use the macro several times with *different* libraries, joining each of them, but only once per member and library pair (B.3.2.1). The standard says every registration function silently ignores a type that is already registered (§14.4.5.1 to §14.4.5.4). `remove_sequence()`, `get_sequences()` and `get_sequence(idx)` (§14.4.5.5, §14.4.5.6, §14.4.4.10) inspect or edit an instance's list.

### Selection modes and counts

A library has three public fields that decide what it runs (uvm-core 2020.3.1 exposes them as fields; the standard's accessors are in Push Further):

| Field | Meaning | Default |
| --- | --- | --- |
| `selection_mode` | how the next member is chosen: `UVM_SEQ_LIB_RAND`, `UVM_SEQ_LIB_RANDC`, `UVM_SEQ_LIB_ITEM` or `UVM_SEQ_LIB_USER` (Annex F.2.4.3) | `UVM_SEQ_LIB_RAND` (§14.4.4.1) |
| `min_random_count`, `max_random_count` | the range that `sequence_count` is constrained to | 10 and 10 (§14.4.4.2, §14.4.4.3) |
| `sequence_count` | how many picks one `start()` makes; a `rand` field constrained inside `[min_random_count:max_random_count]` | 10 (§14.4.4.6) |

The four modes:

| `selection_mode` | What one pick does |
| --- | --- |
| `UVM_SEQ_LIB_RAND` | Randomizes `select_rand`, constrained to a valid index (§14.4.4.7). Repeats are allowed, and a member may never be picked in a short run. |
| `UVM_SEQ_LIB_RANDC` | Uses `randc bit [15:0] select_randc`, constrained to a valid index (§14.4.4.8). A `randc` variable walks through a random permutation of its legal values before repeating any (IEEE 1800-2023 §18.4.2), so with N members every N consecutive picks run each member once. |
| `UVM_SEQ_LIB_ITEM` | Runs no members at all: each pick creates and randomizes one item of the library's request type (`mem_item` here) and sends it (§14.4). |
| `UVM_SEQ_LIB_USER` | Calls `select_sequence(max)`, which returns the index of the next member, from 0 to `max` (§14.4.4.9). The default returns 0, 1, 2… and wraps: plain **round robin** by index. Override it to write your own rule. |

**The count only changes when the library is randomized.** `min_random_count` and `max_random_count` feed a constraint on `sequence_count`, and constraints act only when something calls `randomize()`. If you set them and then call `start()` without `randomize()`, the library runs `sequence_count` at its initial value, 10. Either call `lib.randomize()` (and check the result), or set `lib.sequence_count` directly and skip randomization.

**Predict first.** A library has three members whose indexes are A = 0, B = 1 and C = 2, and `sequence_count = 5`. Before you read the table, write down what each mode can run, and in particular: with `UVM_SEQ_LIB_USER` and no override, which five indexes?

| Pick | RAND (one possible run) | RANDC (one possible run) | ITEM | USER, default `select_sequence()` |
| --- | --- | --- | --- | --- |
| 1 | B | C | one `mem_item` | index 0 (A) |
| 2 | A | A | one `mem_item` | index 1 (B) |
| 3 | B | B | one `mem_item` | index 2 (C) |
| 4 | C | B | one `mem_item` | index 0 (A) |
| 5 | A | A | one `mem_item` | index 1 (B) |

**What the table shows.**
- RAND ran B twice and C only once. Nothing stops a member from running zero times in a short run.
- RANDC ran picks 1 to 3 as one full permutation (C, A, B); picks 4 and 5 are the first two of a new permutation. With 5 picks and 3 members, two members run twice and one runs once; you cannot predict which.
- ITEM ran five items and no member sequences: your scenarios do not run at all in this mode.
- USER without an override is deterministic *by index*. Which member sits at which index follows registration order, and the order of static initialization across classes is not defined by IEEE 1800-2023 (§10.5 requires only that it happens before any `initial` or `always` procedure starts). So "A B C A B" is right only if you know A registered first.

The details that matter, each checked against the uvm-core 2020.3.1 `body()` and `execute()` in `uvm_sequence_library.svh`:

1. **A fresh member each pick.** The factory creates the member by type, so a factory type override on `wr_seq` changes what the library runs ([I-UVM-1B](/curriculum/T2_Intermediate/I-UVM-1B_The_UVM_Factory/index)). Each member is named `<type>:<n>`, where `n` counts every member run so far: `rd_seq:1`, `err_seq:2`, `wr_seq:3`.
2. **The member is randomized,** unless its `set_randomize_enabled(0)` was called (§14.2.2.2). A failed randomization is only a warning, `UVM_WARNING [RNDFLD] Randomization failed in uvm_rand_send action`, and the member still runs with whatever values its `rand` fields had.
3. **It starts with the library as parent, priority -1 and `call_pre_post = 0`**, exactly what `` `uvm_rand_send `` does (Annex B.3.1.3, §14.2.3.1). So the member inherits the library's priority, runs as the library's child, and its `pre_body()` and `post_body()` never run. `pre_start()` and `post_start()` always run.
4. **One member at a time.** The next pick starts only after the member's `start()` returns. A library never runs two members concurrently.
5. **Log lines** (all from `uvm_sequence_library.svh`): `SEQLIB/START` and `SEQLIB/END` at `UVM_LOW`; `SEQLIB/DSTRB`, a count per member type, at `UVM_HIGH`; `SEQLIB/EXEC` (one line per pick) and `SEQLIB/SPRINT` (a table of the library) at `UVM_FULL`.

**Pitfall: an objection in `pre_body()`.** An **objection** is the counter that keeps a phase running until it drops to zero ([I-UVM-1C](/curriculum/T2_Intermediate/I-UVM-1C_UVM_Phasing/index)). A sequence that raises its objection in `pre_body()` works when a test starts it, and silently raises nothing when it runs inside a library. Put objection code in `pre_start()` and `post_start()`, which run in every start style ([I-UVM-3A](/curriculum/T2_Intermediate/I-UVM-3A_Fundamentals/index#practitioner-depth-hooks-and-nested-sequences) shows the same trap with `` `uvm_do ``).

### Running a library: from a test or as a default sequence

**From a test** (the pattern Make It Work uses): create the library, set its fields, randomize it, and start it inside an objection, exactly like any sequence ([I-UVM-3A](/curriculum/T2_Intermediate/I-UVM-3A_Fundamentals/index#starting-a-sequence-from-a-test)).

```systemverilog
// snippet: lib_test::run_phase
virtual task run_phase(uvm_phase phase);
  mem_seq_lib lib = mem_seq_lib::type_id::create("lib");
  lib.selection_mode   = UVM_SEQ_LIB_RANDC;
  lib.min_random_count = 6;
  lib.max_random_count = 6;
  if (!lib.randomize()) `uvm_fatal("RAND", "mem_seq_lib randomization failed")
  phase.raise_objection(this, "mem_seq_lib running");
  lib.start(agt.sqr);
  phase.drop_objection(this, "mem_seq_lib finished");
endtask
```

Variants you will meet:
- `lib.set_starting_phase(phase)` before `start()` names the phase in the `SEQLIB/START` line, and in uvm-core 2020.3.1 the library then raises and drops an objection on that phase itself, around its whole run.
- `lib.start(agt.sqr, null, 300)` gives the library, and therefore every member, priority 300. That matters only under a priority-aware arbitration mode (next section).
- For ITEM mode, call `lib.set_sequencer(agt.sqr)` before `lib.randomize()`. The reason is in the debugging section.

**As a phase default sequence.** A sequencer can start a **default sequence** by itself when a run-time phase begins. You name the sequence type in a resource called `default_sequence`, scoped to the sequencer's full name plus the phase (§15.3.5); I-UVM-3A's [default sequences](/curriculum/T2_Intermediate/I-UVM-3A_Fundamentals/index#expert-starting-phase-and-default-sequences) item shows the mechanism. The command-line form needs no test code (Annex G.2.9):

```text
+uvm_set_default_sequence=uvm_test_top.agt.sqr,main_phase,mem_seq_lib
```

When `main_phase` starts, the sequencer creates `mem_seq_lib` with the factory, sets its sequencer and starting phase, randomizes it and starts it (§15.3.5). Two library-specific facts make this work well:
- The library is randomized, so `sequence_count` lands in `[min_random_count:max_random_count]`. Set those, and the mode, in the library's constructor, or with the uvm-core knobs in Push Further.
- In uvm-core 2020.3.1 the library raises an objection on its starting phase, so `main_phase` stays alive until the library ends. A plain sequence used as a default sequence does not object by itself.

Use the full sequencer path (`uvm_test_top.agt.sqr`) and the `_phase` suffix; a wrong scope starts nothing and reports no error. The test must not also start the same library in `run_phase`, or two copies run.

### Libraries and arbitration

Selection and arbitration are different layers, and the page title puts them side by side because people confuse them.

- **Selection** (`selection_mode`) decides *which member the library runs next*. It happens inside the library, one member at a time.
- **Arbitration** (`set_arbitration()`, IEEE 1800.2-2020 §15.3.2.19) decides *whose item the sequencer grants next* when several sequences are waiting at the same sequencer ([Sequencer Arbitration](/curriculum/T2_Intermediate/I-UVM-3B_Advanced_Sequencing_and_Layering/sequence-arbitration)).

So arbitration only matters when something *else* runs on the same sequencer as the library, for example a background traffic sequence. Then the library's current member competes with it like any sequence:
- **Priority.** Members inherit the library's priority (point 3 above). The default mode, `UVM_SEQ_ARB_FIFO`, ignores priority. Under `UVM_SEQ_ARB_WEIGHTED`, priority is a weight, not a rank: a member with priority 300 against a sequence with priority 100 wins about three grants in four, not all of them.
- **Locks.** Members are children of the library. If a sequence calls `lock()` and then starts the library with itself as parent, `lib.start(m_sequencer, this)`, every member is a descendant of the lock holder and is not blocked by the lock, while other sequences are (§14.2.5.5, §15.3.2.2). A member that calls `lock()` or `grab()` itself holds it only until that member unlocks or ends.

Picking a selection mode never changes arbitration, and `set_arbitration()` never changes which member a library picks.

### Biasing the mix

There is no per-member weight in a library. To make `err_seq` run three times as often as each other member, override `select_sequence()` and use USER mode:

```systemverilog
// snippet: in mem_seq_lib; used only when selection_mode == UVM_SEQ_LIB_USER
virtual function int unsigned select_sequence(int unsigned max);
  int unsigned w[$];
  int unsigned total, pick;
  foreach (sequences[i])                          // weight per member type
    w.push_back(sequences[i].get_type_name() == "err_seq" ? 3 : 1);
  foreach (w[i]) total += w[i];
  pick = $urandom_range(total - 1);
  foreach (w[i]) begin
    if (pick < w[i]) return i;                    // an index from 0 to max
    pick -= w[i];
  end
  return 0;
endfunction
```

It weights by **type name**, not by index, because registration order is not defined. `max` is the last valid index (`sequences.size() - 1`); returning anything larger is an error (`SEQLIB/USER_FAIL`). With three members the weights are 3, 1, 1, so `err_seq` gets about 60% of the picks. Confirm the result with `SEQLIB/DSTRB` at `UVM_HIGH`.

**Registering a type twice is not a way to bias.** The standard ignores a repeated registration (§14.4.5.1 to §14.4.5.4), and the macro may be used only once per member and library pair (B.3.2.1); a second `` `uvm_add_to_seq_lib(err_seq, mem_seq_lib) `` in the same class does not even compile, because it declares the same static variable twice. uvm-core 2020.3.1 happens to keep a duplicate made with `add_typewide_sequence()` on a library subtype (Push Further explains why), which does skew RAND, but that is an accident of one implementation. Use USER mode, or a constraint on `select_rand` (Push Further).

### Debugging a library from its log

Raise the verbosity first: `+UVM_VERBOSITY=UVM_HIGH` shows `SEQLIB/DSTRB`, and `UVM_FULL` adds one `SEQLIB/EXEC` line per pick and a `SEQLIB/SPRINT` table that lists the library's members. `lib.print()` prints the same table at any time.

| Symptom in the log | Cause | Fix |
| --- | --- | --- |
| `UVM_ERROR [SEQLIB/NOSEQS] Sequence library does not contain any sequences. Did you forget to call init_sequence_library() in the constructor?` | The subtype's constructor does not call `init_sequence_library()`, or no member registered with this library type (the macro names another library, or the member's class is not compiled into the build) | Add the call; check the macro's second argument; print the library to see its list |
| `SEQLIB/START … 10 iterations` although you set min = max = 3 | The library was started without `randomize()`, so `sequence_count` kept its initial value 10 | Call `lib.randomize()` and check it, or set `lib.sequence_count = 3` |
| `UVM_ERROR [SEQLIB/VIRT_SEQ] selection_mode cannot be UVM_SEQ_LIB_ITEM when running as a virtual sequence. Using UVM_SEQ_LIB_RAND mode` | ITEM mode, and the library was randomized before it had a sequencer: uvm-core checks the mode in `pre_randomize()` | `lib.set_sequencer(agt.sqr)` before `lib.randomize()` |
| `UVM_FATAL [SEQLIB/VIRT_SEQ] Sequence library 'm_sequencer' handle is null …` | The library was started with a null sequencer, for example from a `p_sequencer` field that was never set | Start it on a real sequencer handle |
| `UVM_ERROR [SEQLIB/MIN_GT_MAX]` | `min_random_count` is larger than `max_random_count`; uvm-core sets min to max | Fix the two values |
| `UVM_WARNING [SEQLIB/MAX_ZERO]` and nothing runs | `max_random_count` is 0 | Set a non-zero maximum |
| `UVM_ERROR [SEQLIB/BASE_ITEM]` | ITEM mode on a library declared with the base `uvm_sequence_item` as its request type | Parameterize the library with your item type, or use another mode |
| `UVM_ERROR [SEQLIB/USER_FAIL] User sequence selection out of range`, then an item instead of a member | Your `select_sequence()` returned an index larger than `max` | Return a value from 0 to `max` |
| `UVM_WARNING [RNDFLD] Randomization failed in uvm_rand_send action` | A member's constraints failed; it runs anyway with stale field values | Fix the member's constraints |
| A member's `pre_body()` work never happens | Members start with `call_pre_post = 0` | Move the work to `pre_start()` |
| `lib.randomize()` fails | An inline constraint such as `with { sequence_count == 20; }` conflicts with the built-in `[min:max]` constraint | Set `max_random_count` instead, or set `sequence_count` directly |

All message texts are from uvm-core 2020.3.1 (`uvm_sequence_library.svh`, and `uvm_sequence_defines.svh` for `RNDFLD`).

### When not to use a library

A library is good at one thing: an unordered random mix of independent scenarios on one sequencer. Use something else when:
- **Scenarios must overlap in time**, for example traffic on two agents at once. A library runs one member at a time on one sequencer; use a [virtual sequence](/curriculum/T2_Intermediate/I-UVM-3B_Advanced_Sequencing_and_Layering/virtual-sequences) that forks sub-sequences.
- **Order matters**, such as "configure, then send data". The library has no notion of dependencies; a virtual sequence or a layered sequence ([Layered Sequences](/curriculum/T2_Intermediate/I-UVM-3B_Advanced_Sequencing_and_Layering/layered-sequences)) encodes the order.
- **You are closing a specific coverage hole.** Blind random selection may take many seeds to reach it; a directed or tightly constrained sequence gets there at once.
- **There are only two or three variants of one scenario.** A single sequence with a `rand` kind field and a `case` is simpler to read and debug.
- **The scenario mix must be portable across simulation, emulation and post-silicon, or generated from a model.** That is what [E-PSS-1: Portable Stimulus](/curriculum/T4_Expert/E-PSS-1_Portable_Stimulus_Standard/index) is for.

### Recap: the mistakes everyone makes once

1. Forgetting `init_sequence_library()` in the constructor: the library is empty (`SEQLIB/NOSEQS`).
2. Setting `min_random_count` and `max_random_count` but never randomizing: 10 picks run.
3. Expecting RAND to run every member: only RANDC guarantees that, and only per full cycle of N picks.
4. Expecting a member's `pre_body()` to run: members start with `call_pre_post = 0`.
5. Registering a member twice to bias the mix: use a USER-mode `select_sequence()`.
6. Confusing `selection_mode` with sequencer arbitration: the first chooses the next member, the second chooses between competing sequences.

## Make It Work

### A library of three memory scenarios

This file builds a library with three members and runs it in RANDC mode for six picks. It also shows the hook trap: every member logs from `pre_start()` and from `pre_body()`, and only the first appears.

The driver has no pins. It logs each item and takes 10 ns per transfer to stand in for real bus cycles, so the example needs no interface and no DUT, as in [I-UVM-3A](/curriculum/T2_Intermediate/I-UVM-3A_Fundamentals/index). The memory map in this example is addresses `0x00` to `0xef`; `err_seq` writes to `0xff`, which a real design would reject.

**Run it.** Compile uvm-core 2020.3.1 (or your simulator's built-in UVM library) together with this file, with `tb_top` as the top module, and run. Add `+UVM_VERBOSITY=UVM_HIGH` to see the `SEQLIB/DSTRB` line. The exact compile and run switches are tool-dependent. No simulator was available to the course authors, so the code was checked by reading it against IEEE 1800-2023 and the uvm-core 2020.3.1 source.

    endfunction

    endfunction

  endclass

      start_item(it);

  endclass

**How to read it.**
- **Six picks, two of each.** Picks 1 to 3 (`rd`, `err`, `wr`) are one RANDC cycle and picks 4 to 6 (`wr`, `err`, `rd`) are the next; each cycle contains every member once (IEEE 1800-2023 §18.4.2). Your order will differ, but every run of this test prints two of each.
- **No `pre_body` lines.** Every member logs from `pre_start()` and never from `pre_body()`, because the library starts members with `call_pre_post = 0`.
- **"unknown phase".** The test started the library without a starting phase. Call `lib.set_starting_phase(phase)` first and the lines read `in run phase` and `in phase run`.
- **Names.** Messages from a member show the library's path then the member's name, `lib.wr_seq:3`; the number counts all members run so far, not runs of that type.
- **Timing.** One item per member and 10 ns per item: the sixth item completes at 60 ns, and the library ends in the same time slot.

### How to build it yourself

1. **Write the library subtype.** Extend `uvm_sequence_library #(your_item)`, add `` `uvm_object_utils `` and `` `uvm_sequence_library_utils `` with the subtype's name, and call `init_sequence_library()` after `super.new(name)`.
2. **Write the members as ordinary sequences.** Give each a complete `body()` and any `rand` knobs the library should randomize. Put objection or setup code in `pre_start()`, never in `pre_body()`.
3. **Register each member** with `` `uvm_add_to_seq_lib(member, library) `` in its class, which must come after the library's declaration. Or register from code with `add_typewide_sequence()` before the library is created, or with `lib.add_sequence()` on one instance.
4. **Choose the mode and the count** in the test (or in the library's constructor): `selection_mode`, `min_random_count`, `max_random_count`.
5. **Randomize, check, then start** inside an objection. For ITEM mode, `set_sequencer()` before `randomize()`.
6. **Read the log**: `SEQLIB/START` states the count and the mode; at `UVM_HIGH`, `SEQLIB/DSTRB` states what ran.

**Checklist before moving on:**
- [ ] My library subtype has both macros and calls `init_sequence_library()` in its constructor.
- [ ] Every member registers with the right library type, and its class is compiled into the build.
- [ ] I randomize the library (and check the result) whenever I rely on `min_random_count` and `max_random_count`, or I set `sequence_count` directly.
- [ ] I can predict what each selection mode runs for a given count, and I know USER mode is round robin by index unless I override `select_sequence()`.
- [ ] No member depends on `pre_body()` or `post_body()`.
- [ ] I bias the mix with a USER-mode `select_sequence()`, never by registering a type twice.
- [ ] I can find `SEQLIB/START`, `SEQLIB/END` and `SEQLIB/DSTRB` in my log and say what each tells me.

## Push Further

### Expert: IEEE 1800.2-2020 versus uvm-core 2020.3.1

Code written from the standard's text alone does not always compile, or behave the same, on uvm-core 2020.3.1. Every difference below was observed in the uvm-core 2020.3.1 source (`src/seq/uvm_sequence_library.svh`, `src/macros/uvm_sequence_defines.svh`); none is listed in its `DEVIATIONS.md`.

| Topic | IEEE 1800.2-2020 | uvm-core 2020.3.1 |
| --- | --- | --- |
| Mode and counts | Accessors `get/set_selection_mode`, `get/set_min_random_count`, `get/set_max_random_count`, `get_num_sequences_executed` (§14.4.4.1 to §14.4.4.4) | None of these methods exist; you write the public fields `selection_mode`, `min_random_count` and `max_random_count`. `sequences_executed` is protected |
| Constructor | The §14.4.2 example calls only `super.new(name)` | The subtype must call `init_sequence_library()`, or the library is empty |
| Duplicate registration | Silently ignored (§14.4.5.1 to §14.4.5.4) | `add_sequence()` ignores it. On a subtype made with `` `uvm_sequence_library_utils ``, `add_typewide_sequence()` checks for duplicates in the *base* class's static list, not the subtype's, so a second registration of the same type is kept and RAND picks it twice as often |
| `remove_sequence()` | Removing a statically registered type updates every instance; a warning if the type is not registered (§14.4.5.5) | Removes the first match from this instance only, with no warning |
| USER default | Returns 0, incrementing, wrapping back to 0 (§14.4.4.9) | Returns 0 to `max` inclusive, then wraps. The counter is not reset between starts, so a second `start()` of the same object continues where the first stopped |
| Objection | Not specified | `body()` raises and drops an objection on the library's starting phase, if it has one |
| Default-sequence knobs | Not in the standard | `pre_randomize()` reads `default_sequence.*` resources and a `uvm_sequence_library_cfg` (next item) |

To keep code portable, touch the library's fields in one place, for example a helper function in your library base class, so a later implementation that follows the standard's accessors needs one edit.

### Expert: libraries as phase default sequences

Default sequences are the regression use the library class was designed around: a test, or just a command line, names the library for a sequencer and phase, and the library runs a random mix there.

- **How it starts.** When the phase starts, the sequencer looks up `default_sequence` in the scope `<sequencer full name>.<phase>_phase`, creates the sequence with the factory, sets its sequencer and starting phase, randomizes it unless randomization is disabled, and starts it (§15.3.5; uvm-core `uvm_sequencer_base::start_phase_sequence`). `+uvm_set_default_sequence=<seqr>,<phase>,<type>` sets that resource from the command line (Annex G.2.9). uvm-core sets that resource from `uvm_root`, whose full name is empty, so `<seqr>` must be the sequencer's full name, `uvm_test_top.agt.sqr`, not `agt.sqr`.
- **Configuring it without test code** (uvm-core 2020.3.1 only; the names do not appear in IEEE 1800.2-2020). The library's `pre_randomize()` looks, in the same `<sequencer>.<phase>_phase` scope of the configuration database ([I-UVM-2C](/curriculum/T2_Intermediate/I-UVM-2C_Configuration_and_Resources/index)), for either a `uvm_sequence_library_cfg` object named `default_sequence.config`, which carries a mode, a minimum and a maximum, or the three separate resources `default_sequence.selection_mode` (type `uvm_sequence_lib_mode`), `default_sequence.min_random_count` and `default_sequence.max_random_count` (type `int unsigned`). The knobs are read in `pre_randomize()`, or at the start of `body()` when randomization is disabled with `set_randomize_enabled(0)`; the default-sequence path randomizes the library, so they always apply there. A library that a test starts without randomizing never reads them.
- **Ending.** The library objects on its starting phase (uvm-core), so the phase waits for it. If the phase is ended anyway, for example by a phase jump, a default sequence that is still running is killed (§15.3.5).
- **Trade-off.** Default sequences hide the stimulus from the test code, and a misspelt scope starts nothing without an error. Many teams therefore start libraries explicitly in a test and keep default sequences for regression scripts that vary stimulus from the command line.

### Expert: randomness, reproducibility and measurement

- **Which generator.** RAND and RANDC picks call `randomize(select_rand)` or `randomize(select_randc)` on the library object, so they use the library's own random generator (IEEE 1800-2023 §18.14.3, object stability). Each member is reseeded from its name when the library sets its context (uvm-core `set_item_context()`), and member names include the run counter, so a given seed reproduces the same mix on one simulator.
- **What breaks reproducibility.** Adding, removing or reordering members shifts the indexes, so the same seed picks different members. Registration order follows static initialization, which IEEE 1800-2023 does not order across classes (§10.5), so it can change with file order, compile options or the simulator (tool-dependent). If an exact order matters, register in the library's constructor with `add_sequences()` and a queue in a fixed order, instead of the macros.
- **RANDC draws first.** uvm-core's RANDC branch draws all `sequence_count` indexes into a queue, then runs them; RAND, ITEM and USER pick one, run it, then pick the next. A RANDC run therefore cannot react to what earlier members did. The `randc` permutation is recomputed whenever the constraints on it change (§18.4.2), which is why each `start()` begins a fresh cycle: `body()` switches the index constraint on before the loop.
- **Inline control.** `randomize(select_rand)` makes `select_rand` the only random variable for that call; every other field is a state variable whose constraints must still hold (§18.11). An extension that adds a constraint linking its own fields to `select_rand` can therefore make a pick fail with `SEQLIB/RAND_FAIL`.
- **Measuring the mix.** `SEQLIB/DSTRB` (UVM_HIGH) prints how many times each type ran in that `start()`. For coverage across a regression, override `post_do(uvm_sequence_item this_item)` in the library: the library is every member's parent, so `post_do()` runs after each member's `body()` (§14.2.3.1), and `this_item.get_type_name()` tells you which one.

### Expert: biasing and coverage-driven selection

- **Constraints on `select_rand`.** The standard allows extensions to add constraints to `select_rand` and `select_randc` (§14.4.4.7, §14.4.4.8). Keep any index you need in a state variable, computed once after construction with `get_sequence(i)` (§14.4.4.10), rather than calling functions inside the constraint. An exclusion such as `select_rand != skip_idx` is simple; per-member weights are clearer in a USER-mode `select_sequence()`, as shown in the mental model.
- **Coverage-driven selection.** A USER-mode `select_sequence()` can read coverage your environment collects, such as which members have already hit their goals, and pick an uncovered one. Keep that logic deterministic per seed and log every decision, or failures become hard to reproduce.
- **Factory overrides as a bias.** Because members are created by the factory every pick, a test can replace one member with a variant (`wr_seq` with a burst version) by a type override, without touching the library ([I-UVM-1B](/curriculum/T2_Intermediate/I-UVM-1B_The_UVM_Factory/index)). An override of the request type also changes what ITEM mode sends.

### Expert: choosing between a library, a virtual sequence and PSS

| Need | Library | Randomized virtual sequence | PSS |
| --- | --- | --- | --- |
| Random mix of independent scenarios on one sequencer | Best fit: one `start()` | Possible, but you write the loop | Overkill |
| Concurrency across agents | No: one member at a time, one sequencer | Yes: `fork` sub-sequences on several sequencers | Yes, scheduled by the tool |
| Ordering and dependencies | No | Yes, written in `body()` | Yes, declared as a model |
| Adding a scenario | The new sequence registers itself | Edit the virtual sequence | Edit the model |
| Reuse beyond simulation | No | No | Yes (emulation, post-silicon) |

A library can also be built from virtual sequences: parameterize it with `uvm_sequence_item`, register virtual sequences as members, and start it on a virtual sequencer handle. It then picks one coordinated scenario at a time; ITEM mode is not available there (`SEQLIB/BASE_ITEM`). See [Virtual Sequences](/curriculum/T2_Intermediate/I-UVM-3B_Advanced_Sequencing_and_Layering/virtual-sequences) and [E-PSS-1](/curriculum/T4_Expert/E-PSS-1_Portable_Stimulus_Standard/index).

### Kata: build and bias a library

**Task.** Start from the Make It Work file.
1. **Predict, then run.** Change `min_random_count` and `max_random_count` to 9. Predict the `SEQLIB/DSTRB` counts.
2. **Bias.** Add a USER-mode `select_sequence()` to `mem_seq_lib` that runs `err_seq` three times as often as each other member. Change the test to `UVM_SEQ_LIB_USER` with a count of 50, run with `+UVM_VERBOSITY=UVM_HIGH`, and predict the counts before you look.
3. **Break it.** Remove the `select_sequence()` override but keep USER mode. Predict the counts again.

<details>
<summary>Worked solution</summary>

1. **Nine picks in RANDC** are three full cycles, so `SEQLIB/DSTRB` shows 3 for each of `err_seq`, `rd_seq` and `wr_seq`.
2. **The override** is the one from the mental model, added to `mem_seq_lib`:

```systemverilog
// snippet: add to class mem_seq_lib
virtual function int unsigned select_sequence(int unsigned max);
  int unsigned w[$];
  int unsigned total, pick;
  foreach (sequences[i])
    w.push_back(sequences[i].get_type_name() == "err_seq" ? 3 : 1);
  foreach (w[i]) total += w[i];
  pick = $urandom_range(total - 1);
  foreach (w[i]) begin
    if (pick < w[i]) return i;
    pick -= w[i];
  end
  return 0;
endfunction
```

and in `lib_test::run_phase`:

```systemverilog
// snippet: replaces the three field assignments in lib_test::run_phase
lib.selection_mode   = UVM_SEQ_LIB_USER;
lib.min_random_count = 50;
lib.max_random_count = 50;
```

The weights are 3, 1 and 1 out of 5, so expect about 30 `err_seq` and about 10 each of `rd_seq` and `wr_seq`, for example `'{"err_seq":31, "rd_seq":9, "wr_seq":10}` (illustrative; the exact numbers depend on the seed, and the total is always 50).

3. **Without the override**, USER mode is round robin by index: 50 picks over 3 members give 17, 17 and 16. The two members at indexes 0 and 1 get 17 each; which members those are depends on registration order, which is not defined.

**How to check yourself.** The `SEQLIB/START` line must say `50 iterations in mode UVM_SEQ_LIB_USER`. If it says 10, the library was not randomized; if it says `UVM_SEQ_LIB_RAND`, the mode assignment did not happen before `randomize()`.

</details>

### Debug challenge: three library logs

Each log comes from a variation of the Make It Work test. Name the cause and the fix before you open the answer.

**Log A**
```text
UVM_ERROR … @ 0: uvm_test_top.agt.sqr@@lib [SEQLIB/NOSEQS] Sequence library does not contain any sequences. Did you forget to call init_sequence_library() in the constructor?
```

**Log B** (the test sets `min_random_count = 3` and `max_random_count = 3`)
```text
UVM_INFO … @ 0: uvm_test_top.agt.sqr@@lib [SEQLIB/START] Starting sequence library mem_seq_lib in unknown phase: 10 iterations in mode UVM_SEQ_LIB_RANDC
```

**Log C** (the test sets `selection_mode = UVM_SEQ_LIB_ITEM`)
```text
UVM_ERROR … @ 0: reporter@@lib [SEQLIB/VIRT_SEQ] selection_mode cannot be UVM_SEQ_LIB_ITEM when running as a virtual sequence. Using UVM_SEQ_LIB_RAND mode
UVM_INFO … @ 0: uvm_test_top.agt.sqr@@lib [SEQLIB/START] Starting sequence library mem_seq_lib in unknown phase: 6 iterations in mode UVM_SEQ_LIB_RAND
```

<details>
<summary>Answers</summary>

- **Log A.** `mem_seq_lib::new()` lost its `init_sequence_library()` call, so the object's member list is empty. If the call is there, check that each member's macro names `mem_seq_lib` and that the member classes are compiled. Fix: call `init_sequence_library()` after `super.new(name)`.
- **Log B.** The test deleted `lib.randomize()`, so `sequence_count` kept its initial value 10. Fix: randomize the library and check the result, or set `lib.sequence_count = 3`.
- **Log C.** `lib.randomize()` ran before the library had a sequencer. uvm-core checks ITEM mode in `pre_randomize()`, found `m_sequencer` null and switched to RAND, so members ran instead of items. The first line shows `reporter@@lib` instead of `uvm_test_top.agt.sqr@@lib` because a sequence that has no sequencer yet reports through the top of the hierarchy: one more clue that the sequencer was missing. Fix: `lib.set_sequencer(agt.sqr)` before `lib.randomize()`.

</details>
