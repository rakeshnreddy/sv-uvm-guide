## Quick Take

- **What it is:** In [I-UVM-3A](/curriculum/T2_Intermediate/I-UVM-3A_Fundamentals/index) one sequence fed one driver through one sequencer. Real tests are busier. Several sequences compete for one driver, and stimulus on one agent must happen before, during or after stimulus on another. **Advanced sequencing** is the set of UVM tools for both problems: arbitration modes and priority, `lock()` and `grab()`, sequence libraries, layering, virtual sequences, the interrupt pattern and the response handler. This page is the map of the module. It teaches the two decisions every advanced test makes, gives you the core rule for each, and then sends you to the eight sub-lessons that take each tool to full depth.
- **Why it matters:** As a testbench (TB) grows from one block to a subsystem, a single `` `uvm_do `` loop on one agent no longer describes the test. The bugs change too. Data reaches the design under test (DUT) before its configuration, a background stream starves an urgent one, an interrupt is serviced late, or the test ends while stimulus is still running. Most of these print no error at all. Knowing which tool controls which decision is what lets you write such tests on purpose and debug them quickly.
- **The Analogy:** Think of each agent as an airport with one runway. The driver is the runway, the sequencer is the control tower, and each sequence is an airline asking the tower for a slot. The tower's rule (the arbitration mode) decides who flies next, and priority is a number written on each request. `lock()` books a block of consecutive slots; `grab()` is an emergency block booking, served before any ordinary block booking that is still waiting. A virtual sequence is the airline operations centre that tells several airports what to do and in which order, and a virtual sequencer is only that centre's phone book. *Where it breaks:* a real tower clears planes on its own schedule, but a UVM sequencer chooses only when its driver asks for the next item. A block booking never expires by itself: a `lock()` lasts until `unlock()`, and other sequences wait silently while it is held. And the phone book never schedules anything: the virtual sequencer decides no order at all.

**You will be able to:**
1. **Choose** the tool for a stimulus requirement (arbitration mode and priority, `lock()`, `grab()`, a sequence library, layering, a virtual sequence, the interrupt pattern or the response handler), and say whether it controls the order inside one sequencer or the order across sequencers.
2. **Predict** which waiting request a sequencer grants under the default FIFO mode, under `UVM_SEQ_ARB_WEIGHTED` and `UVM_SEQ_ARB_STRICT_FIFO`, and when locks and grabs are waiting.
3. **Write** a virtual sequence that runs configuration before data on two agents, with the sequencer handles assigned by the test or taken from a virtual sequencer.
4. **Predict** when each item is driven for sequential `start()` calls, `fork…join` and `fork…join_none` in a virtual sequence, including how `join_none` lets the test end before the stimulus does.
5. **Diagnose** a stuck, starved or misordered stimulus run from its first symptom, and name the sub-lesson whose triage fixes it.

This page teaches you to choose each tool and to predict its effect. Across the module's lessons you will also write layered stimulus ([Layered Sequences and Protocol Layering](/curriculum/T2_Intermediate/I-UVM-3B_Advanced_Sequencing_and_Layering/layered-sequences)) and a sequence library ([Sequence Libraries & Arbitration Control](/curriculum/T2_Intermediate/I-UVM-3B_Advanced_Sequencing_and_Layering/sequence-libraries)), write a sequence that waits with `is_relevant()` ([Sequence Arbitration and Priority](/curriculum/T2_Intermediate/I-UVM-3B_Advanced_Sequencing_and_Layering/sequence-arbitration)), and collect out-of-order responses with `use_response_handler()` and debug the four hang signatures ([The Sequencer-Driver Handshake](/curriculum/T2_Intermediate/I-UVM-3B_Advanced_Sequencing_and_Layering/sequencer-driver-handshake)).

### Recap from I-UVM-3A: one sequence, one sequencer, one driver

Five terms carry the whole module, so here they are again in one place:

- A **sequence item** (`uvm_sequence_item`) holds the data of one transaction, such as one bus write.
- A **sequence** (`uvm_sequence`) is an object whose `body()` task creates items and sends them, one at a time, with `start_item()` and `finish_item()`.
- A **sequencer** (`uvm_sequencer`) is the component that passes items from sequences to one driver. When several sequences want to send at once, it chooses which one goes next. That choice is called **arbitration**.
- A **driver** (`uvm_driver`) is the component that pulls the next item with `get_next_item()`, turns it into pin activity, and reports completion with `item_done()`.
- An **agent** groups one sequencer, one driver and one monitor for one interface ([I-UVM-2A](/curriculum/T2_Intermediate/I-UVM-2A_Component_Roles/index)).

The handshake you learned in I-UVM-3A has one property that matters on every page of this module: **a sequence waits inside `start_item()` until the sequencer grants it, and the sequencer only grants when its driver asks for work.** A test starts a sequence with `seq.start(sqr)`. That call returns only when the sequence's `body()` has finished. Keep both facts in mind; everything below builds on them.

### Two decisions every advanced test makes

Every question in this module is one of two questions:

1. **Inside one sequencer:** several sequences are waiting to send on the same driver. Which one goes next? The *sequencer* decides, using its arbitration mode, the requests' priorities, and any `lock()` or `grab()` in force.
2. **Across sequencers:** stimulus on one agent must happen before, during or after stimulus on another. Who enforces that order? No sequencer can, because each one only sees its own requests. The order comes from *your code*: the `body()` of a **virtual sequence** that starts sequences on several sequencers.

Keep the two apart and most confusion in this module disappears. A priority never orders two agents; a virtual sequence never decides which of two sequences on the same sequencer goes first. The next two subsections give the core rule for each decision.

### Inside one sequencer: who is granted next

Picture three sequences sharing the data agent's sequencer: a background stream, a burst that must not be split, and an interrupt service sequence. Each one has called `start_item()` and is waiting in the sequencer's **arbitration queue**: the sequencer's list of waiting requests, oldest first.

The rules, in the order the sequencer applies them:

1. **Locks and grabs filter first.** While a sequence holds a `lock()` or a `grab()` on the sequencer, only that sequence (and, in uvm-core 2020.3.1, its child sequences) can be granted; every other request waits. Both are exclusive until they are released with `unlock()` or `ungrab()`. They differ in where the request enters the arbitration queue: a lock request at the back, a grab request at the front (IEEE 1800.2-2020 §14.2.5.5, §14.2.5.6). So **when a lock and a grab are both waiting, the grab is served first.** Use `grab()` when your intent is to pre-empt other traffic (an interrupt), and `lock()` when you only need your items kept together. If the holding sequence ends without releasing, uvm-core 2020.3.1 removes the lock and reports `UVM_ERROR [SEQFINERR]`.

   *Standard versus uvm-core:* when nothing is held, the standard's wording says a lock "is arbitrated the same as any other request" and waits for earlier requests (§14.2.5.5). uvm-core 2020.3.1, the reference implementation, grants an unblocked lock at once, ahead of older item requests, just like a grab (`grant_queued_locks()` in `uvm_sequencer_base.svh`). Do not write tests that depend on either reading.
2. **Then the arbitration mode chooses** among the unblocked requests. Set it on the sequencer with `set_arbitration()` (§15.3.2.19). There are six modes (Annex F.2.4.1):
   - `UVM_SEQ_ARB_FIFO`, **the default**: the oldest request wins, and **priority is ignored**.
   - `UVM_SEQ_ARB_WEIGHTED`: a random pick in which each request's chance is proportional to its priority.
   - `UVM_SEQ_ARB_RANDOM`: a random pick that ignores priority.
   - `UVM_SEQ_ARB_STRICT_FIFO`: the highest priority wins; ties go to the oldest.
   - `UVM_SEQ_ARB_STRICT_RANDOM`: the highest priority wins; ties are broken at random.
   - `UVM_SEQ_ARB_USER`: your sequencer's `user_priority_arbitration()` decides (§15.3.2.3).
3. **Priority** is an integer attached to a sequence. A sequence started with no parent gets 100 by default, and a child gets its parent's priority (§14.2.3.1). Pass another value as the third argument of `start()`, as in `isr.start(sqr, null, 300)`. Use values of 1 or more.

Now apply the rules. In this traced example the three requests arrived in the order `bg_seq`, `burst_seq`, `isr_seq`, with the priorities in the picture, and nobody holds a lock unless the row says so:

| Situation | Next grant | Why |
|---|---|---|
| `UVM_SEQ_ARB_FIFO` (the default) | `bg_seq` | Oldest request; the 300 on `isr_seq` is ignored |
| `UVM_SEQ_ARB_STRICT_FIFO` | `isr_seq` | Highest priority |
| `UVM_SEQ_ARB_WEIGHTED` | random: `bg_seq` 20 %, `burst_seq` 20 %, `isr_seq` 60 % | Chance = priority ÷ sum = 100, 100 and 300 out of 500 |
| `UVM_SEQ_ARB_RANDOM` | random, one third each | Priority ignored |
| `burst_seq` holds a `lock()`, any mode | `burst_seq` | The others are blocked until it calls `unlock()` |
| Suppose instead that, while `burst_seq` holds a lock, `bg_seq` calls `lock()` and then `isr_seq` calls `grab()`; `burst_seq` then calls `unlock()` | `isr_seq` gets the sequencer | Both requests were blocked by the held lock; the grab waits at the front of the queue, so it is granted before the earlier lock request (§14.2.5.6). The standard and uvm-core 2020.3.1 agree here |

Two misconceptions to drop now. **`UVM_SEQ_ARB_WEIGHTED` is not strict priority**: `isr_seq` loses two times in five. If the urgent sequence must win whenever it is waiting, use `UVM_SEQ_ARB_STRICT_FIFO`, or `grab()`. And **`grab()` is not just another name for `lock()`**: both give exclusive access until released, but when a lock and a grab are both waiting, the grab is served first, as in the last row. Choose by intent: `grab()` to pre-empt, `lock()` to keep a burst together. The [Sequence Arbitration and Priority](/curriculum/T2_Intermediate/I-UVM-3B_Advanced_Sequencing_and_Layering/sequence-arbitration) lesson owns these rules in full, with a sandbox that replays each case grant by grant.

### Across sequencers: virtual sequences

A **virtual sequence** is a sequence whose `body()` sends no items of its own. Instead it starts other sequences, each on the sequencer of the agent it targets, and the order of those `start()` calls in its code *is* the cross-agent order. Because `start()` returns only after the child's `body()` has finished, a plain sequence of calls is already an ordering rule.

**Practitioner note: handshake order is not pin order.** `start()` returns when the driver has called `item_done()` for the child's last item, so "the configuration sequence returned" means "the configuration is applied" only if the driver calls `item_done()` after the transfer has really completed. Three common cases break that link while the sequence-level order still looks right:
- a driver that pulls items with `get()`, which completes the handshake at once, before anything is driven;
- a **pipelined driver**, one that accepts the next item before the previous one has finished on the bus;
- a DUT that needs a **write response** (an acknowledgement it returns after a write) or **settling time** (time after a write before the new setting takes effect).

The bench's ordering check should therefore watch completed transfers, as the driver's check in Make It Work does. [Virtual Sequences and Sequencers](/curriculum/T2_Intermediate/I-UVM-3B_Advanced_Sequencing_and_Layering/virtual-sequences#expert-handshake-order-is-not-pin-order) takes this further.

The virtual sequence needs handles to the agents' sequencers. There are two common, supported ways to provide them:

- **From the test.** The virtual sequence declares two sequencer handles; the test assigns them from the environment and calls `vseq.start(null)`. The `null` says the virtual sequence runs on no sequencer, which is fine because it never sends an item itself. Make It Work uses this form.
- **From a virtual sequencer.** A **virtual sequencer** is a sequencer with no driver whose only job is to hold the agents' sequencer handles. The environment fills them in its `connect_phase`. The virtual sequence is started on it, `vseq.start(env.vsqr)`, and reads the handles through a typed `p_sequencer` handle that the `` `uvm_declare_p_sequencer `` macro declares (IEEE 1800.2-2020 Annex B.3.3).

```systemverilog
// snippet: the same virtual sequence, with its handles taken from a virtual sequencer.
// Assumes bus_sqr and top_vseq from Make It Work; env.connect_phase sets
// vsqr.cfg_sqr = cfg_agt.sqr and vsqr.data_sqr = data_agt.sqr.
class two_agent_vsqr extends uvm_sequencer;     // REQ defaults to uvm_sequence_item
  `uvm_component_utils(two_agent_vsqr)
  bus_sqr cfg_sqr;
  bus_sqr data_sqr;
  function new(string name, uvm_component parent);
    super.new(name, parent);
  endfunction
endclass

class top_vseq_vsqr extends top_vseq;
  `uvm_object_utils(top_vseq_vsqr)
  `uvm_declare_p_sequencer(two_agent_vsqr)   // p_sequencer: a two_agent_vsqr handle
  function new(string name = "top_vseq_vsqr");
    super.new(name);
  endfunction
  virtual task body();
    cfg_sqr  = p_sequencer.cfg_sqr;          // copy the handles, then run the same body
    data_sqr = p_sequencer.data_sqr;
    super.body();
  endtask
endclass
```

The virtual sequencer is a convenience, not a scheduler. IEEE 1800.2-2020 does not define a virtual sequencer class at all; it is a usage pattern, and uvm-core 2020.3.1 only adds the name `uvm_virtual_sequencer` as a typedef of `uvm_sequencer #(uvm_sequence_item)`. **The virtual sequencer does not decide the order of your sub-sequences.** They run on the agents' sequencers, so the virtual sequencer never arbitrates between them; the order is exactly what `body()` says. [Virtual Sequences and Sequencers](/curriculum/T2_Intermediate/I-UVM-3B_Advanced_Sequencing_and_Layering/virtual-sequences) owns the virtual sequence itself; [Virtual Sequencer: Handles, p_sequencer and Dispatch](/curriculum/T2_Intermediate/I-UVM-3B_Advanced_Sequencing_and_Layering/uvm-virtual-sequencer) owns the virtual sequencer, its wiring and `p_sequencer` in depth.

### Dispatch timing: sequential, fork…join and fork…join_none

A virtual sequence orders agents with three shapes of code. They come from [F2C](/curriculum/T1_Foundational/F2C_Procedural_Code_and_Flow_Control/index): statements in a `begin…end` run one after another; a `fork…join` starts each statement as a separate **process** (a thread) and waits for all of them; a `fork…join_none` starts them and continues at once without waiting.

Trace them with the Make It Work bench. The configuration driver takes 10 ns per item and the data driver 4 ns. `ctrl` writes CTRL (1 item), `thr` writes two threshold registers (2 items) and `data` writes three data words (3 items). Each cell shows the times at which the driver finishes each item:

| `body()` shape | `ctrl` (cfg) | `data` (data) | `thr` (cfg) | `body()` returns | What happens |
|---|---|---|---|---|---|
| A. `ctrl`; `data`; `thr`, all sequential | 10 | 14, 18, 22 | 32, 42 | 42 ns | Correct, but the cfg agent idles while data runs |
| B. `ctrl`; then `fork data; thr; join` (Make It Work) | 10 | 14, 18, 22 | 20, 30 | 30 ns | Correct and faster: the two agents overlap after configuration |
| C. `fork ctrl; join_none`; then `data`; then `thr` | 10 | **4, 8**, 12 | 22, 32 | 32 ns | Data at 4 and 8 ns arrives before CTRL is enabled: two ordering errors |
| D. `ctrl`; then `fork data; thr; join_none` | 10 | — | — | **10 ns** | `body()` returns as soon as the fork starts, the test ends at 10 ns, and the forked sequences are killed before any of their items completes |

Read the table twice:

- **Order across agents is code order.** B is right because `ctrl.start()` returns before the `fork` begins. C breaks the rule even though `ctrl` is written first: `join_none` lets `data` start at time 0.
- **`fork…join_none` does not keep the test alive.** The test raised an **objection** around `vseq.start()`. An objection keeps the **run phase**, the part of the test in which simulation time advances, from ending until every raised objection is dropped ([I-UVM-1C](/curriculum/T2_Intermediate/I-UVM-1C_UVM_Phasing/index)). In D, `start()` returns at 10 ns, the test drops its objection, the run phase ends, and UVM kills every thread still running in it, including the two forked sequences. Nothing reports an error unless your test counts what was driven, which is why Make It Work does.

[Virtual Sequences and Sequencers](/curriculum/T2_Intermediate/I-UVM-3B_Advanced_Sequencing_and_Layering/virtual-sequences#running-work-in-parallel-the-fork-patterns) teaches these patterns in full, including `fork…join_any` and how to stop background children cleanly. [Virtual Sequencer: Handles, p_sequencer and Dispatch](/curriculum/T2_Intermediate/I-UVM-3B_Advanced_Sequencing_and_Layering/uvm-virtual-sequencer) replays three of them (one after another, `fork…join` and `fork…join_none`) in an interactive timeline.

Both are introduced here only by what they decide; their lessons cover them in full.

### Recap

- Two decisions: **inside one sequencer** (the sequencer decides, by locks, grabs, mode and priority) and **across sequencers** (your virtual sequence's code decides).
- The default mode, `UVM_SEQ_ARB_FIFO`, ignores priority. `UVM_SEQ_ARB_WEIGHTED` is random by weight, not strict. `lock()` and `grab()` are both exclusive until released; a waiting grab is served before a waiting lock, so grab to pre-empt and lock to keep a burst together.
- `start()` returns when the child is done, so sequential calls are an ordering rule. `fork…join_none` does not wait, and it does not keep the test alive.
- The virtual sequencer only holds handles. It never orders anything.
- Read the first symptom to find where the flow stopped: in `start_item()` (starvation), in `finish_item()` (handshake), or before `start()` returned (cut short).

## Make It Work

### A virtual sequence that configures before it sends data

This complete bench has two agents of the same type and no DUT: each driver only prints its items and waits a fixed time, standing in for pin activity. A static bit in the driver plays the DUT's CTRL.enable register and reports an ordering error if anything other than CTRL is written before enable is set. The test checks at the end that every planned item was driven, so a run that is cut short fails too.

```systemverilog
// compile
// tb.sv: a two-agent bench with no DUT. The drivers print instead of driving pins.
`include "uvm_macros.svh"

package two_agent_pkg;
  timeunit 1ns; timeprecision 1ns;
  import uvm_pkg::*;
  `include "uvm_macros.svh"

  localparam bit [7:0] CTRL_ADDR = 8'h00;   // bit 0 of CTRL enables the DUT

  class bus_item extends uvm_sequence_item;
    rand bit [7:0]  addr;
    rand bit [31:0] data;
    `uvm_object_utils(bus_item)
    function new(string name = "bus_item");
      super.new(name);
    endfunction
    virtual function string convert2string();
      return $sformatf("addr=0x%02h data=0x%08h", addr, data);
    endfunction
  endclass

  typedef uvm_sequencer #(bus_item) bus_sqr;

  class bus_drv extends uvm_driver #(bus_item);
    `uvm_component_utils(bus_drv)
    static bit   ctrl_enabled;    // plays the DUT's CTRL.enable; shared by both agents
    time         item_time = 10ns;
    int unsigned n_driven;
    function new(string name, uvm_component parent);
      super.new(name, parent);
    endfunction
    virtual task run_phase(uvm_phase phase);
      forever begin
        seq_item_port.get_next_item(req);
        #item_time;                         // the time the transfer takes on the bus
        `uvm_info("DRV", req.convert2string(), UVM_LOW)
        if (req.addr == CTRL_ADDR)
          ctrl_enabled = req.data[0];
        else if (!ctrl_enabled)                   // the DUT ignores writes until enabled
          `uvm_error("ORDER", $sformatf("write to 0x%02h before CTRL.enable", req.addr))
        n_driven++;
        seq_item_port.item_done();
      end
    endtask
  endclass

  class bus_agent extends uvm_agent;              // always active in this example
    `uvm_component_utils(bus_agent)
    bus_sqr sqr;
    bus_drv drv;
    time    item_time = 10ns;               // set by the env before build_phase runs
    function new(string name, uvm_component parent);
      super.new(name, parent);
    endfunction
    virtual function void build_phase(uvm_phase phase);
      super.build_phase(phase);
      sqr = bus_sqr::type_id::create("sqr", this);
      drv = bus_drv::type_id::create("drv", this);
      drv.item_time = item_time;
    endfunction
    virtual function void connect_phase(uvm_phase phase);
      drv.seq_item_port.connect(sqr.seq_item_export);
    endfunction
  endclass

  // Writes n words at base_addr, base_addr+4, ... Fixed values keep the log predictable;
  // a real test would randomize them.
  class bus_write_seq extends uvm_sequence #(bus_item);
    `uvm_object_utils(bus_write_seq)
    bit [7:0]    base_addr;
    bit [31:0]   base_data;
    int unsigned n = 1;
    function new(string name = "bus_write_seq");
      super.new(name);
    endfunction
    virtual task body();
      for (int i = 0; i < n; i++) begin
        req = bus_item::type_id::create($sformatf("req%0d", i));
        start_item(req);
        req.addr = base_addr + 8'(4 * i);
        req.data = base_data + i;
        finish_item(req);
      end
    endtask
  endclass

  // The virtual sequence: it sends no items itself, it orders the agents.
  class top_vseq extends uvm_sequence;
    `uvm_object_utils(top_vseq)
    bus_sqr cfg_sqr;                              // assigned before start()
    bus_sqr data_sqr;
    function new(string name = "top_vseq");
      super.new(name);
    endfunction
    virtual task body();
      bus_write_seq ctrl = bus_write_seq::type_id::create("ctrl");
      bus_write_seq thr  = bus_write_seq::type_id::create("thr");
      bus_write_seq data = bus_write_seq::type_id::create("data");
      if (cfg_sqr == null || data_sqr == null)
        `uvm_fatal("VSEQ", "sequencer handles not set: assign them before start()")
      ctrl.base_addr = 8'h00; ctrl.base_data = 32'h1;  ctrl.n = 1;
      thr.base_addr  = 8'h04; thr.base_data  = 32'h10; thr.n  = 2;
      data.base_addr = 8'h40; data.base_data = 32'hA0; data.n = 3;
      // Rule: configuration first. start() returns only when ctrl's body() is done.
      ctrl.start(cfg_sqr, this);
      // Then data and the rest of the configuration overlap. join waits for both,
      // so the test cannot end while either is still running.
      fork
        data.start(data_sqr, this);
        thr.start(cfg_sqr, this);
      join
    endtask
  endclass

  class two_agent_env extends uvm_env;
    `uvm_component_utils(two_agent_env)
    bus_agent cfg_agt;
    bus_agent data_agt;
    function new(string name, uvm_component parent);
      super.new(name, parent);
    endfunction
    virtual function void build_phase(uvm_phase phase);
      super.build_phase(phase);
      cfg_agt  = bus_agent::type_id::create("cfg_agt", this);
      data_agt = bus_agent::type_id::create("data_agt", this);
      data_agt.item_time = 4ns;                   // the data bus is faster
    endfunction
  endclass

  class two_agent_test extends uvm_test;
    `uvm_component_utils(two_agent_test)
    two_agent_env env;
    function new(string name, uvm_component parent);
      super.new(name, parent);
    endfunction
    virtual function void build_phase(uvm_phase phase);
      super.build_phase(phase);
      env = two_agent_env::type_id::create("env", this);
    endfunction
    virtual task run_phase(uvm_phase phase);
      top_vseq vseq = top_vseq::type_id::create("vseq");
      vseq.cfg_sqr  = env.cfg_agt.sqr;      // handles from the test: no virtual sequencer
      vseq.data_sqr = env.data_agt.sqr;
      phase.raise_objection(this);
      vseq.start(null);                     // null: the virtual sequence sends no items
      phase.drop_objection(this);
    endtask
    virtual function void check_phase(uvm_phase phase);
      if (env.cfg_agt.drv.n_driven != 3)
        `uvm_error("COUNT", $sformatf("cfg_agt drove %0d of 3 items",
                                      env.cfg_agt.drv.n_driven))
      if (env.data_agt.drv.n_driven != 3)
        `uvm_error("COUNT", $sformatf("data_agt drove %0d of 3 items",
                                      env.data_agt.drv.n_driven))
    endfunction
  endclass
endpackage
```

### How to build a virtual sequence yourself

1. **List the ordering rules first,** in words: "CTRL before anything else", "thresholds and data may overlap", "the test ends when both are done".
2. **Write one ordinary sequence per agent-level job** (`ctrl`, `thr`, `data`). Keep each one ignorant of the other agents.
3. **Write the virtual sequence:** declare one handle per target sequencer, fail fast with `` `uvm_fatal `` if a handle is null, and in `body()` express each rule as code: sequential `start()` for "before", `fork…join` for "overlap, then wait".
4. **Start each child on its own sequencer with the virtual sequence as parent:** `child.start(target_sqr, this)`. The parent argument makes the child a child for naming, priority and locks.
5. **Give the virtual sequence its handles,** from the test as here or from a virtual sequencer, and start it under an objection: `vseq.start(null)` or `vseq.start(env.vsqr)`.
6. **Make the bench prove the order and the amount:** an ordering check that fires on a violation, and a count of what was driven, checked in `check_phase`.

**Checklist before moving on:**
- [ ] Every "before" rule is a sequential `start()` call, never a delay and never a priority.
- [ ] Every `fork` in the virtual sequence ends in `join`, or in `join_none` followed by a deliberate `wait fork` or `kill()`.
- [ ] Each child is started on the sequencer of the agent it targets, with `this` as its parent.
- [ ] The virtual sequence checks its handles before using them.
- [ ] The test raises an objection around `vseq.start()`, and nothing else is needed to keep the stimulus alive.
- [ ] The bench counts what it drove, so a run that is cut short fails instead of passing quietly.

### Break it on purpose

1. **Configuration in the background.** Replace `ctrl.start(cfg_sqr, this);` with `fork ctrl.start(cfg_sqr, this); join_none` and replace the final `fork…join` with two sequential calls, `data.start(data_sqr, this);` then `thr.start(cfg_sqr, this);`.
2. **Children in the background.** Restore the original, then change the final `join` to `join_none`.

## Push Further

### Expert: where the two decisions meet

- **A `fork` in a virtual sequence feeds one sequencer's queue.** If two children forked by a virtual sequence target the *same* sequencer, the virtual sequence decides only that both start; from then on the sequencer's arbitration interleaves their items. To keep one child's items together, that child takes `lock()` or `grab()` on the sequencer.
- **Same-time requests have no defined order.** Two children forked in the same time slot (at the same simulation time) reach the sequencer's queue in an order IEEE 1800-2023 leaves open (§9.3.2 says the forked statements run concurrently; §4.7 lets a simulator run same-time processes in any order). Under the default FIFO mode, the first grant can therefore differ between simulators. When the first grant matters, serialize the two `start()` calls, or give the requests different priorities under `UVM_SEQ_ARB_STRICT_FIFO`.
- **Locks from a virtual sequence must name the sequencer.** A virtual sequence started with `start(null)` has no default sequencer, and §14.2.5.5 requires a fatal message when `lock()` gets no sequencer and none is set. Write `lock(data_sqr)` … `unlock(data_sqr)`, or `grab(data_sqr)`. Sequences started with the locking sequence as their parent are not blocked by its lock in uvm-core 2020.3.1 (`is_blocked()` exempts children through `is_child()`, `uvm_sequencer_base.svh`), so the virtual sequence's own children get through. [Virtual Sequences and Sequencers](/curriculum/T2_Intermediate/I-UVM-3B_Advanced_Sequencing_and_Layering/virtual-sequences#expert-locking-an-agent-from-a-virtual-sequence) works through an example.

### Expert: IEEE 1800.2-2020 versus uvm-core 2020.3.1 in sequencing

The standard and the reference implementation differ in several places this module touches. Each difference below was observed in the uvm-core 2020.3.1 source; none is listed in its `DEVIATIONS.md`. Code that depends on either side is not portable between UVM libraries (tool-dependent).

| Topic | IEEE 1800.2-2020 says | uvm-core 2020.3.1 does | Taught in |
|---|---|---|---|
| When a lock is granted | "A lock request is arbitrated the same as any other request" and is granted after all previously arbitrated requests complete (§14.2.5.5) | `grant_queued_locks()` grants the first unblocked lock request at once, ahead of older item requests (`uvm_sequencer_base.svh`) | [Sequence Arbitration and Priority](/curriculum/T2_Intermediate/I-UVM-3B_Advanced_Sequencing_and_Layering/sequence-arbitration#expert-when-is-a-lock-granted-the-standard-and-uvm-core) |
| Several waiting grabs | A grab "is put in front of the arbitration queue" (§14.2.5.6) | Each new grab is pushed to the very front, so a later grab is served before an earlier waiting one; a source comment marks this as a known gap | [Sequence Arbitration and Priority](/curriculum/T2_Intermediate/I-UVM-3B_Advanced_Sequencing_and_Layering/sequence-arbitration#expert-when-is-a-lock-granted-the-standard-and-uvm-core) |

### Expert: ending a test that has background stimulus

Row D of the dispatch table is what happens when `join_none` meets objections. When a task phase ends, uvm-core 2020.3.1 "forcibly and immediately" kills every thread still running in it (`uvm_task_phase.svh`, `uvm_phase_hopper.svh`), and IEEE 1800-2023 §9.7 says killing a process also kills the processes it created. Choose how background stimulus ends instead of letting the phase decide:

- **Wait for it.** End the virtual sequence's `body()` with `wait fork`, which blocks until every immediate child process of the calling thread has finished (IEEE 1800-2023 §9.6.1). Use it when the background work is finite.
- **Stop it on purpose.** For a `forever` background sequence, call `bg.kill()` before `body()` returns. `kill()` removes the sequence's requests, locks and grabs from its sequencer (IEEE 1800.2-2020 §14.2.5.11), and in uvm-core 2020.3.1 it also clears the process guard, so no `SEQPRTZMB` warning appears.
- **Let in-flight items finish.** A drain time delays the end of the phase after the last objection drops: `phase.get_objection().set_drain_time(this, 100ns)` (§9.3.1.7.1, §10.5.1.3.7). It is a margin, not a guarantee; prefer the two options above.
- **Object from the sequence itself.** `set_automatic_phase_objection(1)` makes a sequence raise and drop the starting phase's objection around its own execution (§14.2.4.4). The standard's own note warns against it for a sequence with a `forever` loop, because the objection never drops.

### Expert: choosing between a library, a virtual sequence and a scenario model

- **A sequence library** (§14.4) varies *which* scenario runs on one sequencer. It knows nothing about other agents and cannot express "A must happen before B".
- **A virtual sequence** expresses order across agents directly in code. It scales by composition: a top virtual sequence can start lower virtual sequences, each owning one subsystem. Its weakness is that every legal ordering you want to explore must be written, or randomized, by hand.
- **A scenario model** in the Accellera Portable Test and Stimulus Standard (PSS) describes actions and their legal orderings once, and a tool generates many valid orderings, including into UVM sequences. Use it when the number of legal cross-agent orderings outgrows hand-written virtual sequences. [E-PSS-1](/curriculum/T4_Expert/E-PSS-1_Portable_Stimulus_Standard/index) covers it; how a given tool maps PSS onto UVM sequences is tool-dependent.

### Kata: plan the stimulus for a two-agent DUT

**Goal:** choose a tool for each requirement and justify it by the decision it controls. This is the planning step you do before writing any sequence.

A DMA block has a register agent (`reg_agt`) and a memory-side data agent (`mem_agt`). Its test plan says:

1. Program the channel registers before any data moves.
2. Background memory traffic runs during the whole test, at a low share of the bus.
3. A descriptor update is a read-modify-write of three register items that must not be interleaved.
4. When the DMA raises its interrupt, service it next on the register agent, ahead of queued register traffic.
5. Nightly runs pick a random mix of six transfer scenarios on `mem_agt`.
6. The test must end only when the transfers are done, and the background traffic must stop cleanly.

For each requirement, write the tool, whether it acts inside one sequencer or across sequencers, and the lesson that teaches it.

<details>
<summary>Worked solution</summary>

| # | Tool | Decision | Lesson |
|---|---|---|---|
| 1 | Virtual sequence: `prog.start(reg_sqr, this);` before the data `fork` | Across sequencers | Virtual Sequences and Sequencers |
| 2 | A background sequence started in the virtual sequence, with a lower priority than the transfers and `UVM_SEQ_ARB_WEIGHTED` on `mem_agt`'s sequencer, if the transfers share that sequencer | Inside one sequencer (its share); across (when it starts) | Sequence Arbitration and Priority; Virtual Sequences and Sequencers |
| 3 | `lock(reg_sqr)` … `unlock(reg_sqr)` around the three items: exclusive, without competing with the interrupt's `grab()` | Inside one sequencer | Sequence Arbitration and Priority |
| 4 | A monitor event wakes a service sequence, which calls `grab()` on the register sequencer and `ungrab()` when done | Across (the event); inside (the grab) | Interrupt-Driven Stimulus |
| 5 | A `uvm_sequence_library` on `mem_agt` with the six scenarios registered, in `UVM_SEQ_LIB_RAND` or `UVM_SEQ_LIB_RANDC` mode | Which sequence runs on one sequencer | Sequence Libraries |
| 6 | `fork … join` for the transfers; for the `forever` background sequence, `bg.kill()` before `body()` returns; the test's objection around `vseq.start()` | Across sequencers (end of test) | Virtual Sequences and Sequencers; Push Further above |

Common wrong answers:

- **Priority for requirement 1:** priority cannot order two agents.
- **`grab()` for requirement 3:** it keeps the items together, but it states the wrong intent. If the interrupt service of requirement 4 is waiting for the same sequencer, a waiting lock is sure to yield to its grab, while a second grab competes with it. Use `grab()` only to pre-empt.
- **WEIGHTED or a large priority for requirement 4:** "next" must be certain, so use `grab()`, or `UVM_SEQ_ARB_STRICT_FIFO` with a higher priority.
- **`join_none` with nothing after it for requirement 6:** the test would end and kill the transfers early.
