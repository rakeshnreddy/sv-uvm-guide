## Quick Take

- **What it is:** A **virtual sequence** is a UVM sequence that drives no items of its own. Its `body()` starts ordinary sequences (its **child sequences**) on the sequencers of several **agents**, and the order of the statements in that `body()` decides which agent works when. It needs handles to those agent sequencers, which it gets in one of two ways: the test copies them into the sequence and starts it with `vseq.start(null)`, or the sequence runs on a **virtual sequencer**, a driverless component that holds the handles.
- **Why it matters:** Real designs have several interfaces that must work together. A typical rule is "write the configuration registers over the slow register bus before any packet arrives on the fast data bus". Each bus has its own agent, and no agent knows the others exist. The virtual sequence is the one place where cross-agent order is written down, so it is where ordering bugs are made and fixed.
- **The Analogy:** A virtual sequence is a conductor's score, the agent sequencers are the musicians, and a virtual sequencer is the podium the score sits on. The score says who plays when; each musician plays only its own instrument. *Where it breaks:* the podium gives no cues, so all the timing comes from the score (`body()`); a score can be played with no podium at all (`start(null)`); and between the score's cues each musician also takes requests from other players (its own [arbitration](/curriculum/T2_Intermediate/I-UVM-3B_Advanced_Sequencing_and_Layering/sequence-arbitration)), which the score cannot see.

**You will be able to:**
1. Explain what a virtual sequence does and why neither a virtual sequencer nor the agent sequencers decide the order of traffic across agents.
2. Write a virtual sequence that runs configuration before data on two agent sequencers, start it from a test on a null sequencer or on a virtual sequencer, and keep the run phase alive with an objection.
3. Predict when each agent's first item starts and when `body()` returns for sequential `start()` calls, `fork…join`, `fork…join_any` and `fork…join_none`, and choose the pattern a stated dependency needs.
4. Debug a virtual sequence from its symptom: `UVM_FATAL [SEQ]`, a silent hang until the run-phase timeout, a test that ends at 0 ns, a test that never ends, and `UVM_FATAL [SQRSNDREQCAST]`.

This lesson builds on sequences, `start(sqr, parent)` and the two objection patterns from [I-UVM-3A](/curriculum/T2_Intermediate/I-UVM-3A_Fundamentals/index); what `start_item()`, `finish_item()` and `item_done()` block on, from [The Sequencer-Driver Handshake](/curriculum/T2_Intermediate/I-UVM-3B_Advanced_Sequencing_and_Layering/sequencer-driver-handshake); and `fork…join`, `join_any`, `join_none`, `wait fork` and `disable fork` from [F2C](/curriculum/T1_Foundational/F2C_Procedural_Code_and_Flow_Control/index).

### The problem: one test, several agents

Recall the pieces from [I-UVM-2A](/curriculum/T2_Intermediate/I-UVM-2A_Component_Roles/index) and [I-UVM-3A](/curriculum/T2_Intermediate/I-UVM-3A_Fundamentals/index). An **agent** bundles everything for one interface: a **sequencer**, which queues and grants **sequence items** (items for short); a **driver**, which pulls each item from the sequencer and wiggles the pins; and a monitor. A **sequence** generates items in its `body()` task and runs on exactly one sequencer, the one passed to its `start()`.

This lesson's running example has two agents:

| Agent | Sequencer handle | Driver (called this in the diagrams) | Item | Sequence | Time per item |
|---|---|---|---|---|---|
| `cfg_agt` (register bus) | `cfg_agt.sqr`, type `cfg_sequencer` | `cfg_agt.drv`, type `cfg_driver` (`cfg_drv`) | `cfg_item` | `cfg_seq`: 2 register writes, C1 and C2 | 20 ns |
| `data_agt` (data bus) | `data_agt.sqr`, type `data_sequencer` | `data_agt.drv`, type `data_driver` (`data_drv`) | `data_item` | `data_seq`: 3 payloads, D1 to D3 | 10 ns |

The rule: **no data item may start before both configuration writes have completed.** `cfg_seq` cannot enforce that, because it only knows `cfg_sqr`. `data_seq` cannot either. Something above both agents has to say "this, then that".

### A virtual sequence starts sequences; it sends no items

A **virtual sequence** is a class derived from `uvm_sequence` (IEEE 1800.2-2020 §14.3) whose `body()` calls `start()` on other sequences, its **children**, and never calls `start_item()` itself. Each child runs on the sequencer passed to its `start()` call and sends its items through that agent's sequencer and driver as usual. The virtual sequence is called *virtual* because it has no physical interface of its own: it coordinates sequences that do.

Two facts follow, and juniors get both wrong:
- **Items never pass through the virtual sequence.** There is no TLM connection from a virtual sequence (or a virtual sequencer) to any agent. It holds plain class **handles** (references) to the agent sequencers and hands them to `start()`.
- **Only `body()` decides the order across agents.** Each agent sequencer grants items only among the sequences running on *it*; it has no idea another agent exists.

- The two architectures differ only in *who supplies the handles*: the env (into a virtual sequencer) or the test (into the sequence). The order still comes from `body()` in both.

### Why two `start()` calls in a row give an order

`start()` is a blocking task (§14.2.3.1). It runs the child's `pre_start()`, `pre_body()`, `body()`, `post_body()` and `post_start()` (the two `*_body()` hooks only when its `call_pre_post` argument is 1, the default), and returns only when all of them have finished. A child's `body()` finishes after its last `finish_item()` returns, and `finish_item()` returns only when the driver calls `item_done()` for that item (§14.2.6.3). So in `soc_vseq`, `d.start()` cannot begin until the configuration driver has called `item_done()` for C2.

Notice what the guarantee is: *the configuration handshakes have completed*. That equals "the DUT is configured" only if the configuration driver calls `item_done()` after the write has really finished on the bus. Push Further returns to this ("handshake order is not pin order").

### Who keeps the test alive

The **run phase** (`run_phase`) is a task phase that ends as soon as no component holds an **objection**, a counter that says "I am still busy" ([I-UVM-1C](/curriculum/T2_Intermediate/I-UVM-1C_UVM_Phasing/index)). A virtual sequence is usually the top of the stimulus, so it is what the objection must cover. Use one of the two patterns you met in I-UVM-3A:

- **The test objects around `vseq.start()`**, as in the walkthrough. Simple and explicit.
- **The virtual sequence objects for itself:** `vseq.set_starting_phase(phase); vseq.set_automatic_phase_objection(1);` before `vseq.start(...)` (§14.2.4.2, §14.2.4.4). `start()` then raises an objection before `pre_start()` and drops it after `post_start()`.

The rule is the same whichever way the handles arrive: `set_automatic_phase_objection(1)` raises nothing unless `set_starting_phase()` was called, because `get_starting_phase()` returns null otherwise (§14.2.4.1). Starting the sequence on a virtual sequencer does not supply a starting phase.

**Children never object.** `cfg_seq` and `data_seq` run inside `vseq.start()`, which is already covered. A child that raises its own objection only adds noise, and a forever-running child that raises one keeps the test alive for ever.

### Running work in parallel: the fork patterns

Sequential `start()` calls are the right tool for "this, then that". When two agents should work *at the same time*, `body()` uses SystemVerilog's parallel blocks (IEEE 1800-2023 §9.3.2). Each branch of a `fork` runs as its own **process** (a thread of execution); the keyword after the branches decides when the parent continues:

| Pattern in `body()` | When `body()` continues | Use it for | Risk |
|---|---|---|---|
| `c.start(...); d.start(...);` | after each child finishes, one at a time | "configure, then send data" | none: it is the safe default |
| `fork c.start(...); d.start(...); join` | when **every** branch has finished | independent traffic that must all complete | it does not order the branches; a branch that never ends hangs `body()` |
| `fork … join_any` | when **the first** branch finishes; the others keep running | a race against a watchdog | the losers keep running; stopping them with `disable fork` can kill more than you meant |
| `fork … join_none` | **at once**; the branches start when the parent next blocks (§9.3.2) | background traffic that the end of the test does not depend on | if nothing waits, `body()` returns, the test drops its objection and the run phase ends |

**What the waveforms showed.**
- **One after another** is the only pattern that meets the rule: D1 starts at 40 ns, `body()` returns at 70 ns.
- **`fork…join` runs the agents in parallel; it does not order them.** D1 runs at 0 ns. The run passes silently unless a checker looks at the order, which is why the [Coordinated Attack lab](/curriculum/T2_Intermediate/I-UVM-3B_Advanced_Sequencing_and_Layering/coordinated-attack-lab) adds one. `body()` returns when the longer branch (configuration) ends, at 40 ns.
- **`fork…join_none` with nothing waiting ends the test.** `vseq.start()` returns at 0 ns, so the test carries on at 0 ns (the Make It Work bench prints its `TEST` line then), drops its objection, and the run phase ends and kills the children. The children do start at 0 ns and the drivers may even print `start C1` and `start D1`; no item completes.
- **`fork…join_any`** (not drawn) would return at 30 ns, when `data_seq` finishes first, while C2 is still being written. If `body()` then returns, the run ends at 30 ns in the middle of C2.

**Patterns you will write in real virtual sequences.** Each fragment is a `body()` of `soc_vseq` or an extension of it; `bg` is an endless background sequence (for example a responder that answers the DUT's requests for ever) on some agent sequencer `rsp_sqr`.

```systemverilog
// snippet: configure, then run two independent streams together
c.start(cfg_sqr, this);              // phase 1: in order
fork                                 // phase 2: both streams, both must finish
  d.start(data_sqr, this);
  s.start(cfg_sqr, this);            // s: a second cfg_seq object, e.g. status reads
join
```

```systemverilog
// snippet: a background responder alongside an ordered foreground
fork
  bg.start(rsp_sqr, this);           // never ends on its own
join_none
c.start(cfg_sqr, this);              // the foreground is still in order
d.start(data_sqr, this);
bg.kill();                           // stop it on purpose before body() returns
```

```systemverilog
// snippet: a watchdog race, isolated so disable fork kills only this race
fork begin                           // isolation: the race's own parent process
  fork
    d.start(data_sqr, this);
    begin #1us; `uvm_fatal("VSEQ_TO", "data_seq still running after 1 us") end
  join_any
  disable fork;                      // kills the timer; d has already finished
end join
```

```systemverilog
// snippet: N copies in parallel, one sequence object and one handle per branch
data_seq ds[4];                      // data_sqrs[4]: four data sequencer handles
foreach (ds[i]) begin
  ds[i] = data_seq::type_id::create($sformatf("ds%0d", i));
  fork
    automatic int k = i;             // per-branch copy, set before the branch spawns
    ds[k].start(data_sqrs[k], this);
  join_none
end
wait fork;                           // waits for every immediate child process
```

Why each detail is there:
- **`bg.kill()`** stops the background sequence explicitly (§14.2.5.11). Without it, the run phase kills the process that started `bg` when the objection drops, and uvm-core 2020.3.1 reacts with a warning (see Push Further).
- **The isolation wrapper `fork begin … end join`.** `disable fork` terminates *every* descendant of the calling process (§9.6.3), not just the branches of the last fork. Without the wrapper it would also kill `bg` and any other child started earlier in the same `body()`.
- **`automatic int k = i`.** Branches of a `join_none` start only after the loop has moved on, so a branch that read `i` directly would see a later value. A variable declared at the top of the `fork` is initialized each time execution enters the fork, before its branch is spawned, which gives every branch its own copy (§9.3.2 uses exactly this idiom).
- **`wait fork`** waits for every *immediate* child process of the caller (§9.6.1), including an endless `bg` forked earlier. Use it only when every child forked so far in this process is meant to finish, or isolate the forks you want to wait for with `fork begin … end join`.

To see these process rules step by step, replay the *timeout-disable-fork* and *wait-fork* scenarios of the fork visualizer in [F2C: Waiting for and cleaning up threads](/curriculum/T1_Foundational/F2C_Procedural_Code_and_Flow_Control/index#waiting-for-and-cleaning-up-threads). Map them onto a virtual sequence like this: `bg.start()` is an endless immediate child process of `body()`, exactly like the background monitor there, so `disable fork` without a wrapper kills it and `wait fork` waits for it for ever.

### Where the handles come from: a null sequencer or a virtual sequencer

So far the test copied the handles into the sequence. The other standard style puts them in a **virtual sequencer**: a `uvm_sequencer` component with no driver, built by the env next to the agents, whose handle fields the env assigns in `connect_phase`. The virtual sequence then runs *on* that component, and reaches the handles through a typed handle called `p_sequencer`, which the `` `uvm_declare_p_sequencer(soc_vsqr) `` macro declares and casts when the sequence starts (Annex B.3.3). The body is the same; only the handle expressions and the `start()` argument change:

```systemverilog
// snippet: the same body() when soc_vseq runs on a virtual sequencer soc_vsqr
virtual task body();
  cfg_seq  c = cfg_seq::type_id::create("c");
  data_seq d = data_seq::type_id::create("d");
  c.start(p_sequencer.cfg_sqr, this);   // handles now live in soc_vsqr
  d.start(p_sequencer.data_sqr, this);
endtask

// in the test: no handle copying; start on the virtual sequencer
vseq.start(env.vsqr);
```

The [next lesson, the virtual sequencer](/curriculum/T2_Intermediate/I-UVM-3B_Advanced_Sequencing_and_Layering/uvm-virtual-sequencer), builds `soc_vsqr`, explains `p_sequencer` and the macro in full, and compares the alternatives. What matters here is how the choice changes the *sequence*:

| | `vseq.start(null)`, handles set by the test | `vseq.start(env.vsqr)`, handles in a virtual sequencer |
|---|---|---|
| Who assigns the handles | every test that starts the sequence | the env, once, in `connect_phase` |
| Extra component | none | a virtual sequencer per env |
| `p_sequencer` | not used (with `start(null)` it would be null) | the way `body()` reaches the handles |
| A child started with a null handle and `this` as parent | `UVM_FATAL [SEQ]` at its first `start_item()` | a silent hang (next section) |
| Transaction recording and the sequence's full name | not recorded; the name is just `vseq` | recorded on the virtual sequencer; the name includes its path |
| Objections | the test objects, or `set_starting_phase()` plus the automatic objection | the same rules: starting on a sequencer supplies no starting phase |

Both styles are in wide use; teams usually pick one per project and keep it.

### What `start()` does with a null handle

A forgotten handle assignment is the most common virtual-sequence bug, and its symptom depends on the parent. When `start(sequencer, parent)` begins, it calls `set_item_context()` (§14.1.2.2). In uvm-core 2020.3.1, if `sequencer` is null *and* a parent was given, the child takes **the parent's sequencer** instead (`uvm_sequence_item.svh`, `set_item_context()`).

Without a parent (`d.start(null_handle)`) both styles give the `UVM_FATAL [SEQ]` of style 1. The hang of style 2 is the dangerous one: nothing is printed until the run-phase timeout, which the standard leaves implementation specific (Annex F.7.3.3) and uvm-core 2020.3.1 sets to 9200 s of simulated time (`UVM_DEFAULT_TIMEOUT` in `uvm_global_defines.svh`), unless the test sets a shorter one with `uvm_root::get().set_timeout()` in its `build_phase`. The cheap defence is a null check at the top of `body()`, as Make It Work shows.

### Pitfalls and misconceptions

- **"The virtual sequencer decides which agent goes first."** It holds handles and nothing else; it has no scheduling logic. The order is the statement order in `body()`.
- **"`fork…join` makes the children run in order."** It runs them in parallel and waits for all. Two `start()` calls without a fork are the ordered form.
- **"`fork…join_none` keeps the test alive until the children finish."** It returns at once. The objection covers `vseq.start()`, which returns as soon as `body()` does.
- **"Items flow through the virtual sequencer."** Items go from each child to the sequencer passed to its `start()`. A virtual sequencer has no TLM connection to the agents.
- **"`set_automatic_phase_objection(1)` is enough."** Without `set_starting_phase(phase)` it raises nothing, and the run phase ends at 0 ns with no error.
- **Reusing one sequence object in two parallel branches.** A sequence object can run only once at a time; the second `start()` stops with `UVM_FATAL [SEQ_NOT_DONE] … already started` (uvm-core 2020.3.1). Create one object per branch.
- **A child on the wrong agent.** `cfg_seq` started on `data_sqr` compiles, because `start()` takes any `uvm_sequencer_base`, but the first `finish_item()` fails with `UVM_FATAL [SQRSNDREQCAST] send_request failed to cast sequence item` (uvm-core 2020.3.1, `uvm_sequencer_param_base.svh`).

### Debugging: symptom, cause, fix

| What you see | Likely cause | Fix |
|---|---|---|
| `UVM_FATAL [SEQ] neither the item's sequencer nor dedicated sequencer has been supplied to start item in vseq.d` | a child handle is null and the parent has no sequencer (or no parent was passed) | assign the handle; add a null check at the top of `body()` |
| nothing for a long time, then `UVM_FATAL [PH_TIMEOUT]`; the child never gets past `start_item()` | a child handle is null, `this` was passed as parent, and the parent runs on a virtual sequencer | assign the handle in `connect_phase`; add a null check; set a short timeout while debugging |
| the `TEST` line appears too early (at 0 ns, or before the last item), with few driver lines, and the run ends right after it | `fork…join_none` (`TEST` at 0 ns) or `fork…join_any` (`TEST` when the first branch ends) in `body()`, with nothing waiting for the rest | wait for the work that matters: `fork…join`, or sequential `start()` calls |
| the run ends at 0 ns with no `TEST` line and no error; at most a `start` line from each driver | no objection around `vseq.start()`; or `set_automatic_phase_objection(1)` without `set_starting_phase(phase)` | raise and drop an objection in the test, or call `set_starting_phase(phase)` before `start()` |
| every item checks out, but the test never ends | an endless child inside `fork…join`, or `wait fork` that also waits for an endless child | start endless children with `join_none` and stop them with `kill()`; isolate the forks you wait for |
| data appears on the bus before configuration has finished | the children are in a `fork…join`; or the configuration driver calls `item_done()` before the write has completed | start them one after another; fix the driver (Push Further) |
| `UVM_FATAL [SQRSNDREQCAST] send_request failed to cast sequence item` | a child was started on another agent's sequencer | pass the sequencer whose item type matches the child |
| `UVM_FATAL [SEQ_NOT_DONE] Sequence … already started` | one sequence object started twice while still running | create a new object per branch |

Two habits make these quick to find: name every child after its role (`"c"`, `"d"`), so the full names in the log (`vseq.d`) point at the guilty line; and log one line per phase of `body()` at `UVM_MEDIUM` verbosity ([I-UVM-1D](/curriculum/T2_Intermediate/I-UVM-1D_Reporting_and_Run_Control/index)).

### Where virtual sequences live in a real testbench

- **One top virtual sequence per test.** The test creates it, sets its knobs (counts, modes) and handles, and starts it inside the objection. The test itself stays short.
- **Virtual sequences start other virtual sequences.** A subsystem-level virtual sequence starts block-level virtual sequences as children (`blk.start(null, this)` after copying the handles down), so block scenarios are reused unchanged at subsystem level. Passing `this` keeps the hierarchy in names and lets `kill()` on the top sequence stop everything below it.
- **A base virtual sequence holds the handles.** Projects that use the `start(null)` style usually write one `base_vseq` with the handle fields and one helper that copies them from the env; every scenario extends it.
- **When not to use one.** A test that drives a single agent does not need a virtual sequence; start the agent sequence directly. Cross-agent *checking* (for example "no data before configuration") belongs in a scoreboard or checker, not in the virtual sequence; [A-UVM-8](/curriculum/T3_Advanced/A-UVM-8_Multi_Agent_Topologies/index) builds both into a multi-agent environment.

### Recap

- A virtual sequence starts child sequences on agent sequencers and sends no items itself; each child's items go to the sequencer passed to its `start()`.
- `start()` blocks until the child has finished, so two calls in a row give an order; `fork…join` gives parallelism, not order; `fork…join_none` with nothing waiting ends the test.
- The handles come from the test (`vseq.start(null)`) or from a virtual sequencer (`p_sequencer`, next lesson). The order comes from `body()` in both.
- The test, or the virtual sequence with a starting phase, owns the objection; children never object.
- A null child handle gives `UVM_FATAL [SEQ]`, or a silent hang when `this` is the parent and the parent runs on a virtual sequencer.

### How to build one yourself

1. **List the agents and the dependency.** Write the rule in one sentence ("no data before both configuration writes complete") and name each agent's sequencer and the sequence that runs on it.
2. **Write or reuse one sequence per agent.** Each must work on its own when started on its agent's sequencer. A virtual sequence only coordinates them.
3. **Write the virtual sequence.** Extend `uvm_sequence`, register it with `` `uvm_object_utils ``, add one handle field per agent sequencer (or use a virtual sequencer, next lesson), and check the handles at the top of `body()`.
4. **Express each dependency in `body()`.** "Then" is two `start()` calls in a row; "at the same time, and both must finish" is `fork…join`; "in the background" is `fork…join_none` plus an explicit `kill()` before `body()` returns.
5. **Pass `this` as the parent** of every child, so priorities, names and `kill()` follow the hierarchy.
6. **Start it from the test** inside an objection, after copying the handles (or on the virtual sequencer).
7. **Check the order in the log**, then make a checker enforce it so a regression catches a change ([Coordinated Attack lab](/curriculum/T2_Intermediate/I-UVM-3B_Advanced_Sequencing_and_Layering/coordinated-attack-lab)).

## Push Further

### Expert: the parent fallback inside `start()`

IEEE 1800.2-2020 §14.2.3.1 says only that `start()` runs the sequence on the given sequencer, with the given parent. uvm-core 2020.3.1 makes the null case concrete: `start()` calls `set_item_context(parent_sequence, sequencer)` (§14.1.2.2), and `set_item_context()` replaces a null `sequencer` with `m_parent_sequence.get_sequencer()` when a parent exists (`uvm_sequence_item.svh`). Consequences:
- A child started with a null handle and `this` as parent, inside a sequence that runs on a *real* agent sequencer, silently runs on that sequencer, the same result as the explicit `child.start(m_sequencer, this)` taught in [I-UVM-3A](/curriculum/T2_Intermediate/I-UVM-3A_Fundamentals/index).
- Inside a virtual sequence running on a virtual sequencer, the same call queues the child's request on a sequencer no driver ever pulls from. Arbitration runs only when a driver asks for an item ([Sequence Arbitration](/curriculum/T2_Intermediate/I-UVM-3B_Advanced_Sequencing_and_Layering/sequence-arbitration)), so `start_item()` waits until `UVM_FATAL [PH_TIMEOUT]`.
- A nested *virtual* sequence started with `blk.start(null, this)` inherits the parent's virtual sequencer, which is usually what you want: `p_sequencer` then works in the child too.

**Interview angle:** "Why does the same forgotten handle crash one testbench and hang another?" The answer is the parent's sequencer.

### Expert: what `start(null)` changes, and what it does not

Reading `start()` in uvm-core 2020.3.1 (`uvm_sequence_base.svh`):
- **Recording.** `begin_tr()` and `end_tr()` run only when `m_sequencer` is non-null, so a virtual sequence started with `start(null)` produces no transaction record of its own. Its children, which have real sequencers, are still recorded ([I-UVM-6](/curriculum/T2_Intermediate/I-UVM-6_UVM_Recording_Classes/index) covers recording).
- **Names.** `get_full_name()` prefixes the sequencer's path only when there is a sequencer and no parent, so the sequence is plain `vseq` and its children `vseq.c` and `vseq.d`. Messages and debug dumps are less self-locating; name your sequences well.
- **`p_sequencer`.** The `` `uvm_declare_p_sequencer `` cast of a null `m_sequencer` succeeds (casting null is legal, IEEE 1800-2023 §8.16), so there is no `DCLPSQ` error; `p_sequencer.cfg_sqr` then fails at run time as a null-handle access reported by the simulator, not by UVM.
- **Locks.** `lock()` and `grab()` with no argument act on `m_sequencer`; with `start(null)` that is null, and uvm-core stops with `UVM_FATAL [LOCKSEQR]` or `UVM_FATAL [GRAB]` (next item).
- **Not the objection.** `set_automatic_phase_objection(1)` behaves the same in both styles: it needs `set_starting_phase()` (§14.2.4.1–§14.2.4.4). Only a default sequence started by the sequencer gets a starting phase automatically.

### Expert: locking an agent from a virtual sequence

To keep other traffic off an agent while a multi-item scenario runs, the virtual sequence must name the agent sequencer: `lock(cfg_sqr)` … `unlock(cfg_sqr)` (§14.2.5.5, §14.2.5.7), or `grab(cfg_sqr)` … `ungrab(cfg_sqr)` (§14.2.5.6, §14.2.5.8).
- **With no argument**, `lock()` targets the virtual sequence's own sequencer: a virtual sequencer, where it blocks nothing useful, or null after `start(null)`, where uvm-core stops with `UVM_FATAL [LOCKSEQR] Null m_sequencer reference`.
- **Children must be started with `this` as parent.** A sequencer blocks every request whose sequence is neither the lock holder nor one of its descendants (`is_blocked()` and `is_child()` in `uvm_sequencer_base.svh`). A child started without a parent is *not* a descendant, so it waits behind its own parent's lock while the parent waits in `c.start()`: a deadlock that ends only at `PH_TIMEOUT`.
- When locks and grabs are granted relative to queued requests is taught, with the uvm-core details, in [Sequence Arbitration](/curriculum/T2_Intermediate/I-UVM-3B_Advanced_Sequencing_and_Layering/sequence-arbitration).

### Expert: handshake order is not pin order

Sequential `start()` calls order *handshakes*: `d.start()` begins after the configuration driver's last `item_done()` (§14.2.6.3). That is "the DUT is configured" only if three things hold:
- **The driver calls `item_done()` after the transfer is complete.** A driver that uses `get()` instead of `get_next_item()` completes the handshake as soon as it takes the item ([The Sequencer-Driver Handshake](/curriculum/T2_Intermediate/I-UVM-3B_Advanced_Sequencing_and_Layering/sequencer-driver-handshake)); a pipelined driver calls `item_done()` when it accepts the next request, not when the write's response returns.
- **The write takes effect at once in the DUT.** Some configuration needs a response, a settling time or a "ready" status bit. Then `cfg_seq` must wait for it (read the status back, or collect the response) before its `body()` ends.
- **The checker watches the pins, not the sequences.** An ordering checker fed by the sequences passes even when the bus reordered the transfers. Feed it from the monitors, as the [Coordinated Attack lab](/curriculum/T2_Intermediate/I-UVM-3B_Advanced_Sequencing_and_Layering/coordinated-attack-lab) does.

**Interview angle:** "The ordering check passes, but the DUT still drops the first packet. Where do you look?" At what `item_done()` means in the configuration driver, and at what the checker observes.

### Expert: stopping parallel and background children cleanly

- **The library's own guards.** uvm-core 2020.3.1 wraps every `start()` in a process guard. If the process that called `start()` is killed while the sequence still runs (for example by the end of the run phase, or by a `disable fork`), it reports `UVM_WARNING [SEQPRTZMB]` and calls `kill()`; if the sequence's `body()` process itself is killed, `start()` reports `UVM_WARNING [SEQBDYZMB]` (`uvm_sequence_base.svh`). These are uvm-core behaviour, not IEEE 1800.2, and the end-of-run case is read from the source, not confirmed in simulation: check what your simulator prints.
- **Stop on purpose.** Call `bg.kill()` (§14.2.5.11) or, to clear a whole sequencer, `sqr.stop_sequences()` (§15.3.2.14) before `body()` returns and before the objection drops. A sequence that was started with `this` as parent is also killed when its parent is.
- **Mid-item kills.** The two ways of stopping a sequence leave the driver in different states, so the driver's rule differs (uvm-core 2020.3.1, `uvm_sequencer_base.svh`, `uvm_sequencer.svh`):
  - after `seq.kill()`, the item the driver holds stays in the sequencer's request FIFO and the sequencer still expects `item_done()`. The driver must finish or cut short the item and call `item_done()` as usual; any response it sends is dropped with a warning, because the sequence is gone. Skipping `item_done()` here makes the next `get_next_item()` report "Get_next_item called twice" and return the same stale item again.
  - after `sqr.stop_sequences()`, the sequencer also empties its request FIFO, so the driver must abandon the item *without* calling `item_done()`; calling it fires `UVM_FATAL [SQRBADITMDN]`.
  The handshake lesson's "killed and stopped sequences" item and the arbitration lesson's "locks, killed processes and cleanup" item cover the details.
- **`disable fork` versus `kill()`.** `disable fork` ends processes (IEEE 1800-2023 §9.6.3); `kill()` ends a sequence and removes its requests and locks from the sequencer. Prefer `kill()` for sequences, and keep any `disable fork` inside an isolation wrapper.

### Expert: virtual sequences at scale

- **Vertical reuse.** Block-level virtual sequences become children of subsystem- and SoC-level ones. Keep them free of test-specific handles: pass handles down from the parent (a helper in a base class), or run them on a virtual sequencer whose handles the env sets. Starting them with `this` as parent inherits the parent's priority (§14.2.3.1), which matters when several scenarios share an agent.
- **Knobs, not copies.** Give the virtual sequence `rand` fields (counts, modes, which agents take part) with constraints, randomize it in the test before `start()` (check the result), and write one scenario family instead of ten near-copies.
- **Ownership of order versus checking.** The virtual sequence *creates* the intended order; a checker *proves* it. Keep them separate, so a broken sequence cannot hide its own bug ([A-UVM-8](/curriculum/T3_Advanced/A-UVM-8_Multi_Agent_Topologies/index)).
- **Factory overrides.** Create every child through `::type_id::create()`, so a test can replace `data_seq` with an error-injecting variant without touching the virtual sequence ([I-UVM-1B](/curriculum/T2_Intermediate/I-UVM-1B_The_UVM_Factory/index)).

### Kata: configure, then two streams with a watchdog

**Goal:** extend the Make It Work bench (objectives 2 and 3).

**Requirements:**
1. Write `soc_vseq2`, which extends `soc_vseq` and overrides `body()`.
2. Phase 1: run `cfg_seq` on `cfg_sqr`, as before.
3. Phase 2: run `data_seq` on `data_sqr` and a second `cfg_seq` object `s` (standing for status reads) on `cfg_sqr` at the same time. `body()` returns only when both have finished.
4. Guard phase 2 with a watchdog: if it has not finished within 100 ns, stop with `` `uvm_fatal("VSEQ_TO", …) ``. The watchdog must not kill anything outside phase 2.
5. Change the test to create `soc_vseq2` (keep the handle copying).
6. **Predict before you run:** the start time of every item and the time of the `TEST` line.

<details>
<summary>Worked solution</summary>

```systemverilog
// snippet: add to soc_pkg after soc_vseq, and create soc_vseq2 in soc_test
class soc_vseq2 extends soc_vseq;
  `uvm_object_utils(soc_vseq2)

  function new(string name = "soc_vseq2");
    super.new(name);
  endfunction

  virtual task body();
    cfg_seq  c = cfg_seq::type_id::create("c");
    cfg_seq  s = cfg_seq::type_id::create("s");    // a second object, not c again
    data_seq d = data_seq::type_id::create("d");
    if (cfg_sqr == null || data_sqr == null)
      `uvm_fatal("VSEQ_HANDLES", "set cfg_sqr and data_sqr before start()")

    c.start(cfg_sqr, this);                        // phase 1: in order

    fork begin                                     // isolation for disable fork
      fork
        begin                                      // phase 2: both must finish
          fork
            d.start(data_sqr, this);
            s.start(cfg_sqr, this);
          join
        end
        begin                                      // watchdog
          #100ns;
          `uvm_fatal("VSEQ_TO", "phase 2 still running after 100 ns")
        end
      join_any
      disable fork;                                // kills the watchdog only
    end join
  endtask
endclass
```

In `soc_test::run_phase`, write `soc_vseq2 vseq = soc_vseq2::type_id::create("vseq");`. The handle fields are inherited, so the copying lines stay the same.

**Predicted log** (illustrative): C1 at 0, C2 at 20; then at 40 both D1 and s's first item (named C1 again, because `cfg_seq` names its items C1 and C2); D2 at 50, D3 at 60; s's C2 at 60; `TEST` at 80 ns. Phase 2 ends at 80 ns, when `s` finishes (40 + 2 × 20), well inside the 100 ns watchdog, which `disable fork` then kills.

**Why the shape.** The inner `fork…join` is the "both must finish" rule. The `join_any` races it against the watchdog. The outer `fork begin … end join` gives `disable fork` its own parent process, so it can only reach the watchdog and phase 2, never a background sequence started earlier in `body()` (IEEE 1800-2023 §9.6.3). Using `c` again for the status reads instead of a new `s` would fail with `UVM_FATAL [SEQ_NOT_DONE]` only if `c` were still running; creating a new object keeps the two runs independent and clearly named in the log.
