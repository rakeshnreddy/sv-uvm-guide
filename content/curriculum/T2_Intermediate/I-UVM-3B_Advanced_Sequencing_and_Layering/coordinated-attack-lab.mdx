  ## Introduction

  The DUT has a slow configuration interface (`cfg_agent`) and a fast data interface (`data_agent`). It silently drops any data that arrives before configuration is complete. You will write the virtual sequence, wire its sequencer handles, and start it from the test so that **no data item is driven before the last configuration item has completed**.

  ## Objectives

  1. Declare a typed `p_sequencer` for the virtual sequencer.
  2. Create the configuration and data sequences.
  3. Start them so the order requirement holds, and justify the choice of sequential calls over `fork … join`.
  4. Assign the virtual sequencer's handles in the env's `connect_phase`.
  5. Start the virtual sequence from the test inside an objection.

  ## Conclusion

  The virtual sequencer only gives the sequence handles. The order of traffic across agents comes entirely from how `body()` calls `start()`. Sequential calls order; `fork … join` overlaps; `fork … join_none` needs a later `wait fork`.
