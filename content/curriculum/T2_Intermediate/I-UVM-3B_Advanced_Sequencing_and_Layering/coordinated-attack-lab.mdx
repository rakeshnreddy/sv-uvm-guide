## Quick Take

- **What it is:** The capstone exercise of I-UVM-3B. A design under test (DUT) has a slow configuration port and a fast data port. You write the one **virtual sequence** (a sequence that sends no items itself and starts other sequences on several agents' sequencers) that drives a whole scenario: configure the DUT, send messages through a **translation layer**, keep background traffic running, and service the interrupt the DUT raises halfway through. A self-checking bench tells you whether you got it right, and five broken versions (**mutants**) show you what each mistake looks like in a log.
- **Why it matters:** Each sub-lesson of this module taught one tool on its own. Real tests use them together, and most of the bugs live where they meet: data that overtakes configuration, an interrupt service that is interleaved with other traffic, a test that ends while stimulus is still running, or one that never ends. None of these prints an error unless the bench checks for it. This lab is the guided pre-lab for milestone M5 (a multi-agent environment with virtual sequences).
- **The Analogy:** A stage manager calling a show from a script. The stage manager (the virtual sequence) tells the lighting desk (the configuration agent) and the sound desk (the data agent) what to do, strictly in script order: house lights up before the music starts. An assistant (the translation sequence) turns each line of the script into the individual sound cues. When the fire alarm goes off (the interrupt), the duty electrician takes over the lighting desk for two cues in a row (`grab()`), and the show waits until the alarm is reset. *Where it breaks:* a stage manager watches a clock, but a virtual sequence orders things only by waiting for one step to *finish* before starting the next. A desk operator in UVM (the driver) takes the next cue only when it asks for one. And taking over the desk never interrupts a cue that is already running.

**You will be able to:**
1. **Write** a virtual sequence with a typed `p_sequencer` that configures the DUT before any data is sent, then runs background polling, a layered message stream and an interrupt service together, and ends with nothing left running.
2. **Predict** when each access completes on each port, for the working virtual sequence and for a mutant, from how `start()` blocks, how `fork…join` behaves, when the layer calls `item_done()`, and what `grab()` blocks.
3. **Write** an interrupt service sequence that uses `grab()` and `ungrab()` so that its STATUS read and its clear reach the driver back to back, and **explain** what changes with `lock()`, with a priority, or with no grab at all.
4. **Configure** the bench: assign the virtual sequencer's handles in `connect_phase`, and start the virtual sequence from the test inside an objection, with a timeout so that a hang fails quickly.
5. **Debug** a broken run from its log: say which self-check fired (ORDER, ATOMIC, COUNT or the timeout) and which line of the virtual sequence caused it.

This lab combines five sub-lessons. If one of them is new to you, read it first: [Virtual Sequences and Sequencers](/curriculum/T2_Intermediate/I-UVM-3B_Advanced_Sequencing_and_Layering/virtual-sequences) (`p_sequencer`), [Dispatch Order](/curriculum/T2_Intermediate/I-UVM-3B_Advanced_Sequencing_and_Layering/uvm-virtual-sequencer) (`fork…join` shapes), [Layered Sequences](/curriculum/T2_Intermediate/I-UVM-3B_Advanced_Sequencing_and_Layering/layered-sequences) (translation sequences), [Sequence Arbitration](/curriculum/T2_Intermediate/I-UVM-3B_Advanced_Sequencing_and_Layering/sequence-arbitration) (`grab()` and `lock()`) and [Interrupt Handling](/curriculum/T2_Intermediate/I-UVM-3B_Advanced_Sequencing_and_Layering/interrupt-handling).

### Words this lab uses

Every term below is taught in full elsewhere; here is each one in a sentence.

- A **sequence item** (item) holds one transaction, such as one register write. A **sequence** is an object whose `body()` task sends items with `start_item()` and `finish_item()`. A **sequencer** passes items from sequences to one **driver**, which pulls each one with `get_next_item()` and reports it finished with `item_done()`. An **agent** groups one sequencer, one driver and (usually) one monitor for one port ([I-UVM-3A](/curriculum/T2_Intermediate/I-UVM-3A_Fundamentals/index), [I-UVM-2A](/curriculum/T2_Intermediate/I-UVM-2A_Component_Roles/index)).
- `seq.start(sqr, parent)` runs a sequence on sequencer `sqr` and **returns only when the sequence's `body()` has finished**. Passing the calling sequence as `parent` (usually `this`) makes the new sequence its **child** (IEEE 1800.2-2020 §14.2.3.1).
- `finish_item()` returns when the driver calls `item_done()` for that item. When several sequences wait on one sequencer, the sequencer chooses which goes next: that choice is **arbitration**, and the default mode grants requests in arrival order ([Sequence Arbitration](/curriculum/T2_Intermediate/I-UVM-3B_Advanced_Sequencing_and_Layering/sequence-arbitration)).
- A **virtual sequencer** is a sequencer with no driver that only holds handles to the agents' sequencers. A sequence declares a typed handle to it, `p_sequencer`, with the `` `uvm_declare_p_sequencer `` macro (Annex B.3.3) ([Virtual Sequences and Sequencers](/curriculum/T2_Intermediate/I-UVM-3B_Advanced_Sequencing_and_Layering/virtual-sequences)).
- A **translation sequence** (or **layer**) runs on a lower agent's sequencer, pulls upper-layer items from a sequencer that has no driver, and sends each one as lower-layer items ([Layered Sequences](/curriculum/T2_Intermediate/I-UVM-3B_Advanced_Sequencing_and_Layering/layered-sequences)).
- `grab()` asks a sequencer for exclusive use, ahead of every waiting request; `ungrab()` gives it back. While a sequence holds a grab, only that sequence and its children are granted (§14.2.5.6, §14.2.5.8).
- An **interrupt** is a signal the DUT raises to ask for attention; the **interrupt service** is the stimulus that answers it. Here the DUT's interrupt line is a `uvm_event` called `irq`: `trigger()` turns it on, `reset()` turns it off, `wait_on()` waits until it is on and `wait_off()` until it is off (§10.1.1.2).
- A **write-1-to-clear** (W1C) register bit is cleared by writing 1 to it.
- An **objection** keeps the **run phase** (the part of the test in which simulation time passes) alive; the run phase ends when every raised objection is dropped, and UVM then kills every process still running in it ([I-UVM-1C](/curriculum/T2_Intermediate/I-UVM-1C_UVM_Phasing/index)).
- An **analysis port** broadcasts a transaction to every connected **analysis imp** with `write()`. The bench's checker receives transactions this way ([I-UVM-2B](/curriculum/T2_Intermediate/I-UVM-2B_TLM_Connections/index)).
- A **process** is one thread of execution; `fork` starts several. `fork…join` waits for all of them, `fork…join_none` waits for none (IEEE 1800-2023 §9.3.2; [F2C](/curriculum/T1_Foundational/F2C_Procedural_Code_and_Flow_Control/index)).

### The scenario: what the DUT requires

The DUT is a small message engine with two ports. There is no RTL in this lab: each driver plays the DUT behind its port, so you can follow every event by reading the code.

- **Configuration port** (`cfg_agt`, 10 ns per access). Three registers: `CTRL` (bit 0 enables the data path), `STATUS` (bit 0 means "a message had a bad destination"; write 1 to clear) and `STATS` (a counter that test software reads now and then).
- **Data port** (`data_agt`, 4 ns per beat). A **message** goes over it as one header beat (the destination and the length) and then one payload beat per data word.

The test must satisfy five requirements. Each one is a job for a different tool from this module:

| # | Requirement | Tool | Taught in |
|---|---|---|---|
| R1 | No data beat before the CTRL write has completed | Sequential `start()` calls in the virtual sequence | [Virtual Sequences](/curriculum/T2_Intermediate/I-UVM-3B_Advanced_Sequencing_and_Layering/virtual-sequences) |
| R2 | The test thinks in messages, not beats | A translation sequence on the data sequencer | [Layered Sequences](/curriculum/T2_Intermediate/I-UVM-3B_Advanced_Sequencing_and_Layering/layered-sequences) |
| R3 | Background polling of `STATS` runs during the traffic | `fork…join` in the virtual sequence | [Dispatch Order](/curriculum/T2_Intermediate/I-UVM-3B_Advanced_Sequencing_and_Layering/uvm-virtual-sequencer) |
| R4 | When the interrupt fires, read `STATUS` and clear it, back to back, with no poll in between | An interrupt branch, and `grab()` in the service sequence | [Interrupt Handling](/curriculum/T2_Intermediate/I-UVM-3B_Advanced_Sequencing_and_Layering/interrupt-handling), [Sequence Arbitration](/curriculum/T2_Intermediate/I-UVM-3B_Advanced_Sequencing_and_Layering/sequence-arbitration) |
| R5 | The test ends when everything planned was driven, with nothing left running | `join`, an objection, and `kill()` for the endless layer | [Dispatch Order](/curriculum/T2_Intermediate/I-UVM-3B_Advanced_Sequencing_and_Layering/uvm-virtual-sequencer) |

One more DUT behaviour ties the ports together. The second message goes to destination `4'hF`, which does not exist. When the DUT accepts that header it raises its interrupt and **stalls the data port** until software clears `STATUS`. So if nobody services the interrupt, the rest of the traffic never moves.

**What the diagram shows.**
- **No sequencer decides the order across ports.** `vsqr` is only a box of handles; nothing runs through it. Configuration comes before data only because of the order of statements in `coordinated_vseq`'s `body()`. That is the first misconception this module set out to remove: *the virtual sequencer does not decide sub-sequence order.*
- **One sequencer does decide something:** `cfg_agt.sqr` is shared by three sequences (`ctrl`, `poll`, `isr`), so its arbitration, and any grab, decides which of them goes next on the configuration port.
- **The data port has one sequence on it, the layer.** Tests never send beats; they send messages on `msg_sqr`, and `xlate` turns each message into beats.
- **The checker watches completed accesses**, published by the drivers, not what the sequences intended.

### Core idea 1: order across agents comes from `body()`

`start()` returns only when the child's `body()` has finished, and the child's last `finish_item()` returns only when the driver has called `item_done()` (§14.2.3.1, §14.2.6.3). So two statements in a row are already an ordering rule:

```systemverilog
// snippet: R1 in the solution's body(). The data path cannot start before CTRL completes.
ctrl.start(p_sequencer.cfg_sqr, this);   // returns at 10 ns, after CTRL's item_done()
fork
  msgs.start(p_sequencer.msg_sqr, this); // so the first beat is driven from 10 ns on
  // ... the other branches
join
```

**Pitfalls.**
- **"The virtual sequencer will sort it out."** It cannot: it never sees the items. If you write the CTRL write inside the same `fork` as the traffic, both start at 0 ns and the first data beat completes at 4 ns, before CTRL (mutant M1 in the kata).
- **"Handshake order is pin order."** It is only if the driver calls `item_done()` after the transfer has really finished. A driver that pulls with `get()` (which completes the handshake at once), or a pipelined driver, lets `ctrl.start()` return before the write reaches the DUT. This bench's drivers call `item_done()` after driving, and Push Further explains how to check this in a real bench.

### Core idea 2: three jobs at once, and nothing left running

After configuration, three jobs overlap: the background poll, the message traffic, and a branch that waits for the interrupt and services it. `fork…join` starts all three and waits until **all three** have finished (IEEE 1800-2023 §9.3.2), so `body()` cannot return while any of them is still running. That matters because the test drops its objection as soon as `body()` returns, and the run phase then kills everything still running.

The layer is different: `xlate`'s `body()` is a `forever` loop, so it never finishes. If it were inside the `join`, the `join` would never complete. It therefore starts in its own `fork…join_none`, which returns at once, and the virtual sequence stops it with `xlate.kill()` once the other three jobs are done (§14.2.5.11). `kill()` removes the layer's requests from its sequencer and ends its `body()` cleanly, so nothing is left for the end of the run phase to kill.

**Pitfalls.**
- **"`fork…join_none` keeps the test alive."** It does the opposite: `body()` carries on at once, returns, and the test ends at that moment (mutant M3). Only objections keep the run phase alive.
- **`wait fork` instead of `kill()`.** `wait fork` waits for every immediate child process of the caller (IEEE 1800-2023 §9.6.1), and the endless layer is one of them, so it would wait forever.
- **An interrupt branch that waits for an interrupt that never comes** keeps the `join` open until the timeout. This test expects exactly one interrupt; a test with zero or several needs the queue pattern from [Interrupt Handling](/curriculum/T2_Intermediate/I-UVM-3B_Advanced_Sequencing_and_Layering/interrupt-handling) (Push Further compares them).

### Core idea 3: the layer keeps "delivered" honest

`xlate` plays the driver of `msg_sqr`: it calls `msg_sqr.get_next_item(m)`, sends the header beat and the payload beats on the data port with `start_item()` and `finish_item()`, and only then calls `msg_sqr.item_done()`. So the message sequence's `finish_item()` returns when the **last beat of that message has been driven**, exactly as it would on an agent with a real driver.

**Predict.** The bad-destination message's header completes at 26 ns, and its one payload beat cannot start until the interrupt is cleared. When does `msgs`'s `finish_item()` for that message return? (The trace below gives the answer: 54 ns, after the payload beat, not 26 ns after the header.)

**Pitfall.** Calling `msg_sqr.item_done()` right after `get_next_item()` makes the message sequence run ahead of the wire, so a test that ends when `msgs` returns can end with beats unsent ([Layered Sequences](/curriculum/T2_Intermediate/I-UVM-3B_Advanced_Sequencing_and_Layering/layered-sequences) shows the log).

### Core idea 4: the interrupt service jumps the queue with `grab()`

The interrupt branch of `body()` waits with `p_sequencer.irq.wait_on()`. `wait_on()` returns at once if the event is already on, so it cannot miss an interrupt that fired before the branch began waiting (§10.1.1.2.2). Then it starts `isr` on the configuration sequencer. `isr` calls `grab()`, reads `STATUS`, writes 1 to clear it and calls `ungrab()`.

Why the grab? The poll keeps a request waiting on the same sequencer almost all the time. Without the grab, the default arbitration (`UVM_SEQ_ARB_FIFO`) grants the oldest request, and after the service's STATUS read completes, the poll's next read is older than the service's clear. A poll read would land between the read and the clear, which breaks R4. With the grab, the poll's requests are blocked until `ungrab()`, while the service's own items are not.

**What the diagram shows.**
- `grab()` returns at 26 ns, but the configuration driver is still busy until 30 ns. **A grab wins the next grant; it never aborts an access already on the port.**
- `poll` is blocked because it is not `isr` and not a child of `isr`. `isr`'s own items are never blocked by its own grab.
- The interrupt line is the only link between the two ports: the data driver raises it, the configuration driver clears it, and the data driver waits for it to go off.

**Pitfalls.**
- **Priority instead of a grab.** The default `UVM_SEQ_ARB_FIFO` mode ignores priority. `UVM_SEQ_ARB_WEIGHTED` treats priority as a random weight, so a high priority makes the service *likely*, not certain, to win each grant; it also does nothing to keep the read and the clear together. Only a lock or a grab makes the two accesses atomic.
- **Forgetting `ungrab()`.** uvm-core 2020.3.1 removes the grab when `isr`'s `start()` finishes and reports `UVM_ERROR [SEQFINERR]`. Until then every other sequence on the sequencer starves. Here `isr` ends right after the clear, so the cost is the error message; in a longer service routine it is a silent stall.
- **`lock()` versus `grab()`.** In this bench they behave the same, because nothing else holds or waits for a lock. They differ when another lock is held or waiting: a grab goes to the front of the queue (§14.2.5.6). Push Further has the details.

### Core idea 5: the bench proves it

`atk_checker` receives every completed access from both drivers. Each driver publishes an access **after** it completes, just before `item_done()`, so the checker sees what really happened on the port. The checker enforces three rules, each with its own message ID:

| Rule | Check | Catches |
|---|---|---|
| `ORDER` | A data beat arrives while CTRL.enable has not yet been written | Configuration overtaken by data (R1) |
| `ATOMIC` | Between a STATUS read and the STATUS clear, any other configuration access arrives | An interleaved interrupt service (R4) |
| `COUNT` | In `check_phase`: 8 configuration accesses, 8 data beats and 1 clear were seen | A test that ended early, or stimulus that never ran (R5) |

`ORDER` and `ATOMIC` catch the wrong thing happening; `COUNT` catches the right thing *not* happening. A bench with only the first two passes a test that ends at 10 ns having driven nothing, because nothing ever broke a rule. Hangs are caught by a fourth, built-in check: the test calls `uvm_root::get().set_timeout(1us)` (Annex F.7.3.3), so a hang ends with `UVM_FATAL [PH_TIMEOUT]` at 1 µs instead of at the much longer default.

(3) `msgs.start()` returns at 66 ns, but the test ends at 80 ns: the `join` waits for the slowest branch, the poll. Counts: 1 + 5 + 2 = 8 configuration accesses, 3 + 2 + 3 = 8 beats, 1 clear, so `COUNT` is silent.

### Practitioner depth: reading a failing run

Read a failing log in this order: first *which check fired*, then *at what time*, then *what the other port was doing at that time*.

| First symptom | Likely cause | Fix |
|---|---|---|
| `UVM_ERROR [ORDER]` at 4 ns or soon after | Configuration was started inside the same `fork` as the traffic, or with `fork…join_none` | Make `ctrl.start()` a plain statement before the `fork` |
| `UVM_ERROR [ATOMIC]` naming a `RD addr=0x08` access | The service sequence does not grab, or grabs a different sequencer than the one it runs on | `grab()` and `ungrab()` around the two accesses, on `cfg_agt.sqr` |
| The run ends at 10 ns; `UVM_ERROR [COUNT]` with almost nothing seen | `body()` returned early: `fork…join_none`, or a forgotten `fork` in the test | End the three-branch `fork` with `join` |
| `UVM_ERROR [COUNT] … cfg=0/8 beats=0/8` at 0 ns | The test never started the virtual sequence, or never raised an objection | Start it in `run_phase` between `raise_objection()` and `drop_objection()` |
| Data stops after the bad header, the poll finishes, then `UVM_FATAL [PH_TIMEOUT]` | Nobody services the interrupt, so the data port stays stalled and `msgs` never returns | Add the interrupt branch to the `fork` |
| `UVM_FATAL [PH_TIMEOUT]` with no data beats at all, and no `UVM_FATAL [SEQ]` | A sequencer handle is null and the child was started with `this` as parent, so it fell back to `vsqr`, which has no driver (uvm-core impl.) | Assign every `vsqr` handle in `connect_phase` |
| `UVM_ERROR [SEQFINERR]` at 50 ns, timeline otherwise correct | `isr` returned without `ungrab()` | Call `ungrab()` before `body()` ends |

### Recap

- **Order across agents** is the order of statements in the virtual sequence's `body()`. The virtual sequencer only holds handles.
- **Overlap** is `fork…join`: it starts the branches and waits for all of them, so `body()` cannot return early. An endless layer goes in its own `fork…join_none` and is stopped with `kill()`.
- **The layer** calls `item_done()` on the upper sequencer after the last beat, so "message sent" means "every beat driven".
- **The interrupt service** waits with `wait_on()`, then `grab()`s the configuration sequencer so that its read and clear are back to back; `ungrab()` lets the poll resume.
- **The bench proves it** with ORDER, ATOMIC and COUNT checks on completed accesses, plus a short timeout for hangs.

## Push Further

### Expert: handshake order is not pin order

Every ordering guarantee in this lab rests on one fact: `finish_item()` returns when the driver calls `item_done()`. IEEE 1800.2-2020 §14.2.6.3 notes that this "does not strictly indicate that the driver has completed all processing of the request". Three real drivers break the link between handshake order and pin order:
- a driver that pulls with `get()`, which completes the handshake as soon as it takes the item (§15.5.2.6);
- a pipelined driver, which calls `item_done()` when it has *issued* an access and sends responses later ([The Sequencer-Driver Handshake](/curriculum/T2_Intermediate/I-UVM-3B_Advanced_Sequencing_and_Layering/sequencer-driver-handshake));
- a DUT that needs a write response or settling time before the new configuration takes effect.

In each case `ctrl.start()` returns early and the virtual sequence looks correct while the DUT still drops data. That is why this bench's checker watches **completed transfers**, and why a real bench takes them from a pin-level monitor, not from the driver ([A-UVM-7](/curriculum/T3_Advanced/A-UVM-7_VIP_Construction/index)). If your configuration must be *applied* before data, wait for the evidence: a write response, or a read-back of CTRL, before you start the data path.

### Expert: lock() or grab() for the interrupt service

Replace `grab()` and `ungrab()` with `lock()` and `unlock()` and this bench behaves identically under uvm-core 2020.3.1: `m_lock_req()` grants the first unblocked lock request in the queue at once, so the lock is granted at 26 ns just like the grab (`uvm_sequencer_base.svh`, `grant_queued_locks()`). The standard words it differently: "A lock is granted after all previously arbitrated requests are completed" (§14.2.5.5). Read literally, the lock would wait for poll's in-flight read and be granted at 30 ns, which still gives the same order here (tool-dependent). The two calls differ in a case this bench does not have: when another sequence already holds a lock, waiting grabs are granted before waiting locks, because a grab request is put at the front of the arbitration queue (§14.2.5.6). So:
- use `grab()` for an interrupt service that must go next even if other sequences are queued for a lock;
- use `lock()` for an atomic burst that may wait its turn;
- neither aborts the access already on the port, so the worst-case service latency includes one full access of whatever was running.

The arbitration sandbox on [Sequence Arbitration](/curriculum/T2_Intermediate/I-UVM-3B_Advanced_Sequencing_and_Layering/sequence-arbitration) has a "grab vs lock" scenario that shows the difference.

### Expert: ending a test that has an endless layer

Three ways to stop `xlate`, and what each costs:
- **`kill()` from the virtual sequence (this lab).** The layer's lifetime is visible in one `body()`. `kill()` removes the sequence's requests and locks from its sequencer and ends its `body()` (§14.2.5.11). Kill only when the layer is idle; here it is waiting in `get_next_item()` with no beat outstanding, because `msgs` has returned. (§14.2.5.11 says `post_body()` and `post_start()` then run; uvm-core 2020.3.1 does not run them, so put no clean-up there: tool-dependent.)
- **The layering environment owns the layer** and kills it from `phase_ready_to_end()` (§13.1.4.3.2), as [Layered Sequences](/curriculum/T2_Intermediate/I-UVM-3B_Advanced_Sequencing_and_Layering/layered-sequences) does. Better for reusable VIP: tests never see the layer.
- **Let the end of the run phase kill it.** Reading the uvm-core 2020.3.1 source (not confirmed by a simulator run), the process guard that `start()` creates should then report `UVM_WARNING [SEQPRTZMB]` and kill the sequence (`uvm_sequence_base.svh`, `process_guard_triggered()`). That is uvm-core behaviour, not IEEE 1800.2; avoid relying on it either way.

Never use `wait fork` to wait for the other branches while the layer runs: it waits for every immediate child process (IEEE 1800-2023 §9.6.1), the layer included. If you need `join_none` for several finite jobs, wrap them as `fork begin … end join` so that only they are waited for.

### Expert: interrupt delivery: a level event versus a queue

The bench models the interrupt line as a `uvm_event` used as a **level**: `trigger()` turns it on and it stays on until `reset()` (§10.1.1.2.2, §10.1.1.2.8). That is why the interrupt branch uses `wait_on()`, which returns at once if the line is already on, and the data driver uses `wait_off()`.

`wait_trigger()` would be a mistake here: it waits for the *next* trigger, so it misses one that fired before the call (§10.1.1.2.4 warns about the same-time race too). The level form has its own limit. Two interrupts that arrive while the first is still pending turn the line on only once, so a single `wait_on()` services one of them. A test with several interrupts needs a loop that reads `STATUS` until no bit is pending, or a queue of interrupt transactions from a monitor (`uvm_tlm_analysis_fifo`, §12.2.8.3), as [Interrupt Handling](/curriculum/T2_Intermediate/I-UVM-3B_Advanced_Sequencing_and_Layering/interrupt-handling) builds. In a real bench the line is a DUT pin, and an interrupt monitor turns its rising edges into transactions; reaching into a shared event, as this lab does, is a teaching shortcut.

### Expert: handles from the test, and the parent fallback

The same lab works without a virtual sequencer. Give `coordinated_vseq` its own `cfg_sqr`, `data_sqr`, `msg_sqr` and `irq` fields, let the test assign them from `env`, and call `vseq.start(null)` ([Virtual Sequences and Sequencers](/curriculum/T2_Intermediate/I-UVM-3B_Advanced_Sequencing_and_Layering/virtual-sequences) compares the two styles). `p_sequencer` is then null, so every handle must come from the test.

Either way, watch what a **null handle** does. With no parent, `seq.start(null)` followed by `start_item()` stops the test with `UVM_FATAL [SEQ] neither the item's sequencer nor dedicated sequencer has been supplied…`. With `this` as the parent, uvm-core 2020.3.1 `set_item_context()` silently takes the **parent's** sequencer instead (`uvm_sequence_item.svh`; uvm-core impl.). Forget `vsqr.data_sqr = data_agt.sqr;` and `xlate` runs on `vsqr`, which has no driver: no fatal message, no beats, and a `PH_TIMEOUT` at 1 µs. A one-line guard at the top of `body()`, `` if (p_sequencer.data_sqr == null) `uvm_fatal("VSEQ", "data_sqr not set") ``, turns the hang into a clear message.

### Extension kata: mid-stream reconfiguration

Milestone M5 asks for a virtual sequence that also handles a **reconfiguration in the middle of the traffic**. Change the lab so that:
1. messages 0 and 1 are sent first; then
2. the data path is disabled (`CTRL = 0`) and re-enabled (`CTRL = 1`), standing in for a real settings change; then
3. message 2 is sent.

Extend the checker so that `ORDER` also fires for a beat that arrives while CTRL.enable is 0, and update `COUNT` (the configuration port now carries 10 accesses). Predict: can a data beat of message 1 still be on the port when `CTRL = 0` is written?

<details>
<summary>Worked solution</summary>

```systemverilog
// snippet: new sequences, the changed body() and the changed checker lines
class reconfig_seq extends cfg_base_seq;
  `uvm_object_utils(reconfig_seq)
  function new(string name = "reconfig_seq");
    super.new(name);
  endfunction
  virtual task body();
    bus_item t;
    access(1, CTRL, 32'h0, t);            // disable the data path
    access(1, CTRL, 32'h1, t);            // re-enable it with the new settings
  endtask
endclass

class msg_batch_seq extends msg_seq;      // reuses msg_seq's send() task
  `uvm_object_utils(msg_batch_seq)
  bit second;                             // 0: messages 0 and 1; 1: message 2
  function new(string name = "msg_batch_seq");
    super.new(name);
  endfunction
  virtual task body();
    if (!second) begin
      send(4'h1, 2, 32'hA0);
      send(4'hF, 1, 32'hB0);
    end
    else
      send(4'h2, 2, 32'hC0);
  endtask
endclass

// coordinated_vseq::body(), with batch1, batch2 (second = 1) and reconfig created
// like the other children: only the data branch of the fork changes.
fork
  poll.start(p_sequencer.cfg_sqr, this);
  begin                                   // the data path, in three ordered steps
    batch1.start(p_sequencer.msg_sqr, this);    // returns after its last beat
    reconfig.start(p_sequencer.cfg_sqr, this);  // no beat can be in flight now
    batch2.start(p_sequencer.msg_sqr, this);
  end
  begin
    p_sequencer.irq.wait_on();
    isr.start(p_sequencer.cfg_sqr, this);
  end
join
xlate.kill();

// atk_checker::write_cfg(): track enable in both directions
if (t.write && t.addr == CTRL)
  enabled = t.data[0];
// atk_checker::check_phase(): expect cfg=10 instead of 8
```

**Prediction:** no. `batch1.start()` returns only when the layer calls `msg_sqr.item_done()` for message 1, which happens after message 1's last beat has completed (54 ns in the original trace). The reconfiguration starts after that, so no beat can overlap it, and `batch2` starts only after `CTRL = 1` has completed. The poll still shares the configuration port, so a poll read may land between `CTRL = 0` and `CTRL = 1`; that is harmless, because the rule concerns data beats.

**Why it works:** the same rule as R1, applied in the middle of the run. Sequential `start()` calls in one branch order the data path against the configuration path; the other branches keep overlapping.
