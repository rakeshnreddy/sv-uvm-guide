## Quick Take

- **What it is:** The **handshake** is the set of calls through which a **sequence** (the object that creates stimulus) hands **sequence items** (items) to a **driver** (the component that turns items into pin activity), with the **sequencer** (the component that decides which sequence sends next) in between. [I-UVM-3A](/curriculum/T2_Intermediate/I-UVM-3A_Fundamentals/index) taught the basic loop. This page goes one level down: what each driver call does exactly in uvm-core 2020.3.1, how a **response** (an item the driver sends back) finds the sequence that asked for it, how a **pipelined** driver (one that accepts the next item before the previous one is answered) returns responses **out of order**, and how to read a hang from the log.
- **Why it matters:** Most "the test hangs until the timeout" bugs are one handshake rule broken on one side: a missing `item_done()`, a response without ids, a sequence waiting for a response that never comes, or a response that was dropped. Each has its own signature in the log. Engineers who know the signatures fix these in minutes; everyone else adds `$display` calls for a day.
- **The Analogy:** A restaurant kitchen with a ticket rail. A waiter (the sequence) clips an order ticket (the item) on the rail (the sequencer's one-slot request FIFO). The cook (the driver) takes it, cooks, and rings it out (`item_done()`), and only then is the waiter released. A plate (the response) goes back to the table printed on the ticket (`sequence_id`) and is matched by the order number (`transaction_id`). *Where it breaks:* a real rail holds many tickets, but a UVM sequencer holds one item for its driver. A plate with no table number is not guessed at: the kitchen stops (`SQRPUT`). And a busy table that never collects its plates does not get a stack of them on the floor: after eight, new plates go in the bin, silently in uvm-core 2020.3.1.

**You will be able to:**
1. Predict, for `get_next_item()`, `try_next_item()`, `peek()` and `get()`, when the call returns, when the sequence's `finish_item()` returns, and what a second call before `item_done()` does.
2. Write a driver that returns responses with `item_done(rsp)`, `put_response()`, `put()` or `rsp_port.write()`, each routed by `set_id_info()`.
3. Write a sequence that collects pipelined, out-of-order responses with `use_response_handler(1)` and `response_handler()`, or with `get_response(rsp, transaction_id)` and a response queue deep enough for every outstanding request.
4. Debug a sequencer-driver hang from its log signature and the sequencer's state (`get_current_item()`, `last_req()`, `convert2string()`), and fix it.

### Recap: who blocks where

You know this loop from [I-UVM-3A](/curriculum/T2_Intermediate/I-UVM-3A_Fundamentals/index#the-handshake-sequence--sequencer--driver). In one paragraph: the sequence waits inside `start_item()` (in `wait_for_grant()`) until the sequencer **grants** it, that is, picks it as the next sender (this choice is called **arbitration**). The sequencer makes that choice only when the driver asks for work by calling `get_next_item()`, `try_next_item()`, `get()` or `peek()`. The sequence then randomizes the item and calls `finish_item()`, which puts the item in the sequencer's **request FIFO**, a buffer that holds exactly one item, and waits. The driver's call returns that item. In the default style, `finish_item()` returns only when the driver calls `item_done()`.

| Call | Who calls it | Blocks? | What it waits for |
| --- | --- | --- | --- |
| `start_item(req)` | sequence | yes | a grant, which needs a driver request |
| `finish_item(req)` | sequence | yes | the driver's `item_done()` (directly, or inside `get()`) |
| `get_next_item(req)` | driver | yes | a granted sequence to send an item |
| `item_done()` | driver | no, it is a function | nothing: it completes the item and wakes `finish_item()` |
| `get_response(rsp)` | sequence | yes | a response in this sequence's response queue |

Two consequences carry the rest of this page. A sequence can never run ahead of its driver, because `finish_item()` waits. And every wait in the table has a partner call on the other side: if the partner never happens, that side hangs, usually without any message.

### The four driver calls compared

A driver can fetch an item in four ways (IEEE 1800.2-2020 §15.5.2.3 to §15.5.2.7). [I-UVM-3A](/curriculum/T2_Intermediate/I-UVM-3A_Fundamentals/index#practitioner-depth-driver-styles) showed when to choose each style. Here is what each one does, call by call, in uvm-core 2020.3.1 (`uvm_sequencer.svh`, `uvm_sequencer_param_base.svh`):

| Call | Waits for an item? | Item stays in the request FIFO? | Sequence's `finish_item()` returns | A second fetch before `item_done()` |
| --- | --- | --- | --- | --- |
| `get_next_item(req)` | yes, as long as it takes | yes, until `item_done()` | at `item_done()` | `get_next_item()` again: returns the same item and reports `UVM_ERROR` "Get_next_item called twice…" |
| `try_next_item(req)` | only until the NBA region of the current time slot; no simulation time passes | yes, if it returned one | at `item_done()` | `try_next_item()` again: reports `UVM_ERROR` "get_next_item/try_next_item called twice…" and returns at once |
| `peek(req)` | yes | yes, until `item_done()` or `get()` | at `item_done()` or `get()` | `peek()` again: returns the same item, no message (§15.5.2.7) |
| `get(req)` | yes | no: `get()` calls `item_done()` itself before it returns | when `get()` returns, **before** the driver drives the item | `get()` again: a normal fetch of the next item |

Three rules fall out of the table:
- **Only `get()` completes the item for you.** After `get()`, never call `item_done()`: there is no outstanding item, and uvm-core stops with `UVM_FATAL [SQRBADITMDN] Item_done() called with no outstanding requests`.
- **"The sequence waits while the driver drives" is true only for the first three calls.** With `get()`, the sequence is released as soon as the driver takes the item, so it must wait for a response if it needs the result. This is exactly what makes `get()` the natural call for pipelined drivers.
- **`try_next_item()` never waits for a sequence to start.** It gives sequences that already asked for a grant one NBA region (one `wait_for_sequences()` call) to send an item, then returns `null`.

**Pitfalls.**
- **A "look-ahead" with two `get_next_item()` calls does not look ahead.** The second item cannot exist yet, because the sequence is still inside `finish_item()` for the first. You get the first item twice and an error.
- **A polling loop that does not consume time** (`try_next_item()` returns `null` and the loop calls it again at once) never lets time advance. The idle branch must wait for a clock.
- **`has_do_available()`** (§15.3.2.17) answers "is a request waiting right now that could be granted?", meaning one not blocked by another sequence's `lock()` and not excluded by its own `is_relevant()` ([Sequencer Arbitration](/curriculum/T2_Intermediate/I-UVM-3B_Advanced_Sequencing_and_Layering/sequence-arbitration) covers both). It does not wait for the NBA region, so it misses a sequence that calls `start_item()` later in the same time slot, before the NBA region, which `try_next_item()` would still serve. Use `try_next_item()` itself as the test, and `has_do_available()` only as a hint.

### How a response finds its sequence

A **response** is an item the driver sends back to the sequence that asked, for example the data of a read. Many sequences may share one sequencer, so the response must carry an address. Every item carries two ids:
- **`sequence_id`** identifies the sequence on this sequencer. `send_request()`, inside `finish_item()`, writes it into the request.
- **`transaction_id`** numbers the requests of one sequence: 1, 2, 3 and so on. In uvm-core 2020.3.1, `send_request()` assigns it only when the item still has the value -1, the value of a newly created item (`uvm_sequencer_param_base.svh`).

The driver creates a new response object, whose ids are -1, and copies both ids from the request with `rsp.set_id_info(req)` (§14.1.2.4). The sequencer then looks up the sequence by `sequence_id` and hands the response over. The ids are the only routing information: the sequencer never guesses from timing or order.

There are four ways for a driver to send a response, listed in §15.4.3.1. All four end in the same sequencer function, `put_response()`:

| Driver call | Kind | When to use it | Connection it needs |
| --- | --- | --- | --- |
| `seq_item_port.item_done(rsp)` | function | `get_next_item()` drivers that answer when they complete the item | `seq_item_port` (always connected) |
| `seq_item_port.put_response(rsp)` | function | a response after `item_done()`, or several responses for one request | `seq_item_port` |
| `seq_item_port.put(rsp)` | task that never blocks (§15.2.1.2.8) | `get()` drivers: the usual call in pipelined drivers | `seq_item_port` |
| `rsp_port.write(rsp)` | function (analysis port) | a separate response thread or a monitor that sees the response | `drv.rsp_port.connect(sqr.rsp_export)` in `connect_phase` (§13.7.2.2) |

**Rules and pitfalls.**
- **One response path per response.** `item_done(rsp)` followed by `put_response(rsp)` sends the same response twice. The second copy waits in the queue, and the next `get_response()` returns it instead of the answer to the next request.
- **`item_done(rsp)` delivers the response before `finish_item()` can resume.** So with the queue, `get_response()` right after `finish_item()` returns at once. With a handler, the handler runs *before* `finish_item()` returns, a timing detail that matters in Make It Work.
- **A cloned request still needs `set_id_info()`.** I-UVM-3A showed that `copy()` does not copy the ids. A response built with `req.clone()` therefore also has -1 ids.
- **The response type must match.** The sequence's `put_response()` casts to its `RSP` type, and a response of another type stops the test with `UVM_FATAL [PUTRSP] Failure to cast response in put_response` (uvm-core `uvm_sequence.svh`). The handler path skips that cast, so a handler must `$cast` and check for itself.

### The response queue and how it overflows

Each sequence keeps its own **response queue**. `get_response(rsp)` takes the oldest response, and `get_response(rsp, tid)` waits for the response whose `transaction_id` is `tid` and leaves the others where they are (§14.3.3.3). The queue holds at most 8 responses by default (§14.2.7.7); `set_response_queue_depth(-1)` makes it unbounded, at the cost of memory if nobody collects.

What happens to the ninth uncollected response differs between the standard and the implementation:
- IEEE 1800.2-2020 §14.2.7.4 and §14.2.7.5 say an overflow generates an error by default.
- uvm-core 2020.3.1 declares the enable bit without initializing it, so it starts at 0 (`uvm_sequence_base.svh`). The response is **dropped silently** unless the sequence calls `set_response_queue_error_report_enabled(1)`, which then reports `UVM_ERROR` "Response queue overflow, response was dropped".

The visual's **Bug: responses never collected** scenario shows the silent version. Now combine it with collection by id. A pipelined sequence that sends many requests first and collects by `transaction_id` afterwards can lose exactly the response it later waits for: once 8 responses for other ids sit in the queue, the next ones are dropped, and `get_response(rsp, tid)` for a dropped id waits forever. The kata in Practice & Reinforce traces this case step by step. The cure is a depth of at least the number of outstanding responses, collecting while you send, or the response handler.

### Pipelined drivers and out-of-order responses

A **pipelined** bus accepts a new request before it has answered the previous one: AXI, PCIe and most memory interfaces work like this. The driver for such a bus must take the next item while earlier ones are still outstanding, so it uses `get()` (or `get_next_item()` plus an immediate `item_done()`), keeps the requests itself, and answers later with `put(rsp)`. If the target may answer in a different order than it was asked, the responses arrive **out of order**.

A sequence has two ways to collect them:
- **By id with `get_response(rsp, tid)`**: record each request's `transaction_id` after `finish_item()`, then wait for each one. Simple, but every outstanding response must fit in the queue (previous section).
- **With a response handler** (§14.2.7.1 to §14.2.7.3): call `use_response_handler(1)` before the first request. From then on, the sequencer calls the sequence's `response_handler(uvm_sequence_item response)` function for every response, and nothing goes into the queue. The handler matches each response by `get_transaction_id()`.

**Pitfalls.**
- **Handler on, then `get_response()`: the sequence hangs.** With the bit set, responses never reach the queue, so `get_response()` waits forever. Choose one method per sequence.
- **The handler is a function, and it runs in the driver's thread.** The sequencer calls it inside the driver's `put()` or `item_done()`. It cannot wait, and slow work in it slows the driver. Record, check and count; if something must wait, push the response into a queue that `body()` services.
- **`body()` must not return while responses are outstanding.** When a sequence ends, the sequencer forgets its `sequence_id`, and a late response is dropped with `UVM_WARNING [Sequencer] Dropping response for sequence N, sequence not found. Probable cause: sequence exited or has been killed`. End `body()` with a wait for the last response.
- **Create a new item for every request.** A reused request object keeps the `transaction_id` it got the first time, because `send_request()` assigns one only to an item whose id is still -1 (uvm-core). Worse, with `get()` the sequence re-randomizes the very object the driver is still holding.
- **Record what the handler needs before it can run.** With a `get()` driver, the handler runs long after `finish_item()` returns. With an `item_done(rsp)` driver, it runs *inside* `item_done()`, before `finish_item()` returns, so anything you record after `finish_item()` is too late.

### Hang signatures and triage

A **hang** means simulation time keeps advancing (or the phase sits waiting) while no side makes progress, until the **phase timeout** ends the run. In uvm-core 2020.3.1 the default timeout is 9200 s of simulation time, reported as `UVM_FATAL [PH_TIMEOUT] Default timeout of 9200s hit, indicating a probable testbench issue`; a test that calls `uvm_root::get().set_timeout(...)` (Annex F.7.3.3) gets "Explicit timeout of … hit" sooner.

| Symptom | Likely cause | What the log shows |
| --- | --- | --- |
| Sequence stuck in `finish_item()`; driver drives the same item again and again | `item_done()` missing | `UVM_ERROR` "Get_next_item called twice without item_done or get in between", once per loop. Its message id is the sequencer's full name, so search for the text. |
| Every item driven twice | two `get_next_item()` calls per loop | the same error, once per item |
| Polling driver gets `null` although a sequence is running | the sequence consumes time between `start_item()` and `finish_item()` | `UVM_ERROR [TRY_NEXT_BLOCKED] try_next_item: the selected sequence '…' did not produce an item within 1 wait_for_sequences call…` |
| Test stops at the driver's response | response without `rsp.set_id_info(req)`, or a null response | `UVM_FATAL [SQRPUT] Driver put a response with null sequence_id` (or `…a null response`) |
| Test stops with `PUTRSP` | the driver's response type is not the sequence's `RSP` | `UVM_FATAL [PUTRSP] Failure to cast response in put_response` |
| Sequence stuck in `get_response()`; driver idle | the driver never responds to this item, or the sequence turned on the response handler | nothing |
| Sequence stuck in `get_response(rsp, tid)` with many requests outstanding | the response for `tid` was dropped because the queue was full | nothing, unless overflow reporting is enabled |
| Responses missing, test still passes or mismatches later | more than 8 uncollected responses | nothing in uvm-core by default |
| `UVM_WARNING [Sequencer] Dropping response for sequence N, sequence not found` | the sequence ended (or was killed) before its response arrived | that warning |
| `UVM_FATAL [SQRBADITMDN]` | `item_done()` with no outstanding item: after `get()`, twice in a row, or after the sequencer was stopped | "Item_done() called with no outstanding requests. Each call to item_done() must be paired with a previous call to get_next_item()." |
| `UVM_FATAL [SQRSNDREQGNI]` | two driver threads fetching from one sequencer at once | "Concurrent calls to get_next_item() not supported…". Depending on timing the second thread can get the "called twice" error instead. |
| Sequence never leaves `start_item()`; nothing in the log | no driver is asking (the driver is on another sequencer, or stuck elsewhere), or another sequence holds a `lock()` or `grab()` | nothing. See [Sequencer Arbitration](/curriculum/T2_Intermediate/I-UVM-3B_Advanced_Sequencing_and_Layering/sequence-arbitration) for locks. |
| Driver's `seq_item_port` unconnected | the agent's `connect_phase` forgot the connection | `UVM_WARNING [DRVCONNECT]` at end of elaboration, then a null-handle error from your simulator at the driver's first fetch (the text depends on the tool) |
| `start_item()` stops the test at once | the item handle is null (not created) | `UVM_FATAL [NULLITM] attempting to start a null item from sequence '…'` (uvm-core; §14.2.6.2 requires an error) |

**The four-step triage procedure.**
1. **Find the blocked side.** Is the sequence in `start_item()`, `finish_item()` or `get_response()`? Is the driver in a fetch call, or inside its own pin-level code (for example waiting for a ready signal the DUT never raises)? A log line in the driver after the fetch and before `item_done()` answers the second question.
2. **Read the log for the signature.** Match it against the table. No message at all points to the silent rows: a missing response, a dropped response, a lock, or a driver stuck in its own code.
3. **Probe the sequencer.** `sqr.get_current_item()` (§15.4.1) returns the item the driver holds between `get_next_item()` or `peek()` and `item_done()`, and `null` otherwise (always `null` for a `get()` driver). `sqr.last_req()` and `sqr.last_rsp()` (§15.4.2, §15.4.3.2) show the last request sent and the last response received. `sqr.convert2string()` prints the waiting requests and the lock list as index/sequence-id pairs, not names, so print `seq.get_sequence_id()` from your sequences to map them.
4. **Fix the side that broke the rule,** then rerun with a short explicit timeout so a regression of the fix fails fast.

### Recap

- `get_next_item()`, `try_next_item()` and `peek()` leave the item in the one-slot FIFO until `item_done()`; `get()` completes it at once, so the sequence runs ahead and must wait for a response.
- A response finds its sequence only through `sequence_id`, and its request through `transaction_id`. `set_id_info()` copies both. All four response paths end in the same routing function.
- The response queue holds 8 by default and, in uvm-core 2020.3.1, drops silently. Collect every response, size the queue, or use a response handler.
- A response handler replaces the queue: never mix it with `get_response()`, never block in it, and never let `body()` end before the last response.
- Find the blocked side first, then read the signature, then probe the sequencer.

## Make It Work

### An out-of-order read bench

This complete bench has a driver that takes two reads with `get()`, waits 10 ns to model the target's latency, and answers the newer read first. The sequence sends four reads and checks every response in a response handler.

```systemverilog
// compile
`timescale 1ns/1ps
`include "uvm_macros.svh"

package ooo_pkg;
  import uvm_pkg::*;

  class rd_item extends uvm_sequence_item;
    `uvm_object_utils(rd_item)

    rand bit [7:0] addr;
    bit [31:0]     data;  // filled in by the target, carried back in the response

    function new(string name = "rd_item");
      super.new(name);
    endfunction

    virtual function string convert2string();
      return $sformatf("addr=0x%02h data=0x%08h", addr, data);
    endfunction
  endclass

  typedef uvm_sequencer #(rd_item) rd_sqr;

  // Takes reads two at a time and answers the newest first, like a target
  // that reorders. get() completes each item at once (it calls item_done()
  // itself), so the sequence can send the second read while the first is
  // still outstanding.
  class ooo_driver extends uvm_driver #(rd_item);
    `uvm_component_utils(ooo_driver)

    function new(string name, uvm_component parent);
      super.new(name, parent);
    endfunction

    virtual task run_phase(uvm_phase phase);
      rd_item pending[$];
      rd_item req_n;
      rd_item rsp_n;
      forever begin
        repeat (2) begin
          seq_item_port.get(req);
          `uvm_info("DRV", $sformatf("took tid=%0d addr=0x%02h",
                    req.get_transaction_id(), req.addr), UVM_LOW)
          pending.push_back(req);
        end
        #10ns;  // models the target's read latency, not a synchronization delay
        while (pending.size() > 0) begin
          req_n = pending.pop_back();  // newest first: out of order
          rsp_n = rd_item::type_id::create("rsp_n");
          rsp_n.set_id_info(req_n);    // copies sequence_id and transaction_id
          rsp_n.addr = req_n.addr;
          rsp_n.data = 32'h1000 + req_n.addr;
          seq_item_port.put(rsp_n);    // never blocks; routed like put_response()
        end
      end
    endtask
  endclass

  class ooo_read_seq extends uvm_sequence #(rd_item);
    `uvm_object_utils(ooo_read_seq)

    int unsigned n_reads = 4;
    int unsigned n_rsp;
    bit [31:0]   expected[int];  // expected data, keyed by transaction_id

    function new(string name = "ooo_read_seq");
      super.new(name);
    endfunction

    virtual task body();
      rd_item rd;
      use_response_handler(1);  // responses go to response_handler(), not the queue
      repeat (n_reads) begin
        rd = rd_item::type_id::create("rd");  // new item per read: its own transaction_id
        start_item(rd);
        if (!rd.randomize())
          `uvm_fatal("RAND", "rd randomization failed")
        finish_item(rd);  // with a get() driver, returns when the driver takes rd
        // send_request() inside finish_item() has assigned the transaction_id
        expected[rd.get_transaction_id()] = 32'h1000 + rd.addr;
      end
      wait (n_rsp == n_reads);  // body() must not end while reads are outstanding
    endtask

    // Called by the sequencer, in the driver's thread, once per response.
    virtual function void response_handler(uvm_sequence_item response);
      rd_item rsp_rd;
      int     tid;
      if (!$cast(rsp_rd, response))
        `uvm_fatal("RSPTYPE", "response is not an rd_item")
      tid = rsp_rd.get_transaction_id();
      if (!expected.exists(tid))
        `uvm_error("RSPID", $sformatf("unexpected response tid=%0d", tid))
      else if (rsp_rd.data != expected[tid])
        `uvm_error("RSPDATA", $sformatf("tid=%0d data=0x%08h, expected 0x%08h",
                   tid, rsp_rd.data, expected[tid]))
      else
        `uvm_info("RSP", $sformatf("tid=%0d %s", tid, rsp_rd.convert2string()),
                  UVM_LOW)
      expected.delete(tid);
      n_rsp++;
    endfunction
  endclass

  class ooo_test extends uvm_test;
    `uvm_component_utils(ooo_test)

    rd_sqr     sqr;
    ooo_driver drv;

    function new(string name, uvm_component parent);
      super.new(name, parent);
    endfunction

    virtual function void build_phase(uvm_phase phase);
      super.build_phase(phase);
      sqr = rd_sqr::type_id::create("sqr", this);
      drv = ooo_driver::type_id::create("drv", this);
      uvm_root::get().set_timeout(1us);  // end a hung run early (default: 9200 s)
    endfunction

    virtual function void connect_phase(uvm_phase phase);
      super.connect_phase(phase);
      drv.seq_item_port.connect(sqr.seq_item_export);
    endfunction

    virtual task run_phase(uvm_phase phase);
      ooo_read_seq seq;
      seq = ooo_read_seq::type_id::create("seq");
      phase.raise_objection(this);  // the test owns the end of test
      seq.start(sqr);
      phase.drop_objection(this);
    endtask
  endclass
endpackage

module tb_top;
  import uvm_pkg::*;
  import ooo_pkg::*;

  initial run_test("ooo_test");
endmodule
```

### Break it on purpose

Make each change, predict the log, then run.
1. **Delete `use_response_handler(1);`.** The responses go to the queue instead (4 fit easily), `response_handler()` is never called, and `n_rsp` stays 0. `body()` waits forever and the run ends with `UVM_FATAL [PH_TIMEOUT] Explicit timeout of … hit`. No other message.
2. **Keep the handler and replace the final `wait` with `repeat (n_reads) get_response(rsp);`.** The handler still checks every response, but `get_response()` waits for a queue that stays empty: the same timeout.
3. **Move `rd = rd_item::type_id::create("rd");` above the `repeat`.** One object is reused, so it keeps transaction id 1 for all four reads, and the driver's `pending` queue holds two handles to the same object. Each pair of responses comes back as tid 1 twice: the first matches, and the second gives `UVM_ERROR [RSPID] unexpected response tid=1`, once at 10 ns and once at 20 ns.
4. **Delete `rsp_n.set_id_info(req_n);`.** At 10 ns the first `put()` stops the test with `UVM_FATAL [SQRPUT] Driver put a response with null sequence_id`.
5. **Delete the final `wait`.** `body()` ends right after the fourth `finish_item()` returns at 10 ns. The test drops its objection, the run phase ends, and the driver is stopped before it answers reads 3 and 4. Only two `RSP` lines appear and the report is clean: two reads were never checked, which is worse than a failure. If something keeps the phase alive, for example `phase.get_objection().set_drain_time(this, 50ns);` before the drop, the driver does answer at 20 ns and both responses are dropped with `UVM_WARNING [Sequencer] Dropping response for sequence …, sequence not found`.

### How to build a pipelined responder yourself

1. **Decide the response contract.** Which requests get a response, how many, and can they come back out of order? Write it down next to the driver.
2. **Fetch with `get()`** when the driver must hold several requests; keep them in a queue owned by the driver, and never call `item_done()` after `get()`.
3. **Build each response as a new object** of the sequence's `RSP` type, call `rsp.set_id_info(req)` with the matching request, fill the data, and send it with `put(rsp)` (or `rsp_port.write(rsp)` from a separate thread connected to `rsp_export`).
4. **In the sequence, choose one collection method:** `use_response_handler(1)` plus `response_handler()`, or `get_response(rsp, tid)` with `set_response_queue_depth()` at least the number of outstanding requests.
5. **Create a new item per request,** and record what the response check needs at a point where it is guaranteed to exist before the response can arrive.
6. **End `body()` only after the last response,** for example with `wait (n_rsp == n_reads)`.
7. **Set a short explicit timeout** in the test, and turn on `set_response_queue_error_report_enabled(1)` in sequences that use the queue, so silent failures become loud.

**Checklist before moving on:**
- [ ] I can say, for each of `get_next_item()`, `try_next_item()`, `peek()` and `get()`, when the sequence's `finish_item()` returns.
- [ ] Every `get_next_item()` or non-null `try_next_item()` in my drivers has exactly one `item_done()`, and no `get()` is followed by `item_done()`.
- [ ] Every response is a new object with `set_id_info(req)`, sent by exactly one path.
- [ ] Each sequence either collects every response, or uses a response handler, never both.
- [ ] Sequences that collect by id have a queue deep enough for every outstanding response.
- [ ] No `body()` returns while its responses are outstanding.
- [ ] I can find the blocked side of a hang from the log and from `get_current_item()`, `last_req()` and `convert2string()`.

## Push Further

### Expert: the call matrix inside uvm-core 2020.3.1

The driver-facing calls share two flags in `uvm_sequencer`: `sequence_item_requested` (an item has been fetched and not completed) and `get_next_item_called` (it was fetched with `get_next_item()` or `try_next_item()`). Reading the code (`uvm_sequencer.svh`, `m_safe_select_item()` in `uvm_sequencer_param_base.svh`) gives these less obvious results:
- **`get_next_item()` then `get()`** returns the same item and completes it, with no message: `get()` only arbitrates when no item is outstanding.
- **`peek()` then `get_next_item()`** also returns the same item without an error, because the "called twice" check looks only at `get_next_item_called`, which `peek()` does not set.
- **`get_next_item()` then `try_next_item()`** reports "get_next_item/try_next_item called twice without item_done or get in between" and returns at once without arbitrating.
- **The request FIFO holds one item.** If two threads fetch at once, the second granted sequence cannot store its item and `send_request()` stops with `SQRSNDREQGNI`. A pipelined driver therefore fetches from one thread only and hands items to other threads itself.
- **`try_next_item()`** waits `wait_for_sequences_count` NBA regions, both before choosing and after granting; the count is 1 unless the sequencer's `wait_for_sequences_count` resource is set, a uvm-core feature (`@uvm-accellera` in `uvm_sequencer_base.svh`) that stacked sequencers need.

IEEE 1800.2-2020 specifies the observable steps of each call (§15.5.2.3 to §15.5.2.7) but not these flags, so treat the combinations above as uvm-core behaviour, not as portable rules.

### Expert: IEEE 1800.2-2020 versus uvm-core 2020.3.1 on responses

| Topic | IEEE 1800.2-2020 | uvm-core 2020.3.1 (observed in the source) |
| --- | --- | --- |
| Response queue overflow | an error by default (§14.2.7.4, §14.2.7.5) | silent: the enable bit starts at 0 (`uvm_sequence_base.svh`) |
| Depth set below the current count | "An implementation shall generate an error message" (§14.2.7.7) | no check in `set_response_queue_depth()` |
| Response with no ids | `item_done()` requires `set_id_info()` (§15.5.2.5) | `UVM_FATAL [SQRPUT]`, except when the vendor define `CDNS_NO_SQR_CHK_SEQ_ID` is set: then the response is dropped without a message (tool-dependent) |
| Null item in `start_item()` | an error message (§14.2.6.2) | `UVM_FATAL [NULLITM]` |
| Overflow error text in the class comment | — | the comment says an error is reported by default, contradicting the code |

None of these differences is listed in the uvm-core release's deviations file, so do not call them "documented deviations". The practical rule: turn on `set_response_queue_error_report_enabled(1)` yourself in any sequence that relies on the queue.

### Expert: pipelined driver architecture

Real pipelined drivers, for AXI-like buses with several outstanding transactions, usually have three threads:
- a **fetch thread** that calls `get(req)` whenever the bus can accept another request and puts `req` into a request queue;
- a **request-phase thread** that drives address phases from that queue;
- a **response-phase thread** that observes responses on the bus, finds the matching request (for AXI by its bus ID, which is not the UVM `transaction_id`), builds the response with `set_id_info()` and sends it with `put()` or `rsp_port.write()`.

The fetch thread is the only caller of `get()`, which avoids `SQRSNDREQGNI`. The bus-ID-to-request map lives in the driver, because the UVM ids say nothing about bus ordering rules; [B-AXI-3](/curriculum/T3_Advanced/B-AXI-3_AXI_Ordering_and_IDs/index) explains those. Back-pressure comes from how often the fetch thread calls `get()`: while it does not call, no sequence is granted. For reusable components the same structure appears in [A-UVM-7](/curriculum/T3_Advanced/A-UVM-7_VIP_Construction/index).

### Expert: killed and stopped sequences

- **`kill()`** (§14.2.5.11) removes a sequence's requests and locks from the sequencer. The standard says `post_body()` and `post_start()` then run; uvm-core kills the process that would run them, so they do not (`uvm_sequence_base.svh`, `m_kill()`).
- **`sqr.stop_sequences()`** (§15.3.2.14) kills every sequence on the sequencer and, in uvm-core, also empties the request FIFO with the message "Sequences stopped. Removing request from sequencer fifo". A driver that was in the middle of an item and then calls `item_done()` hits `UVM_FATAL [SQRBADITMDN]`, because the item is gone. Reset handling that stops sequences must also make the driver abandon its current item without calling `item_done()`.
- **Late responses** for a killed or finished sequence are dropped with the "Dropping response … sequence not found" warning, because the sequencer unregisters the sequence id when the sequence exits (`remove_sequence_from_queues()` in `uvm_sequencer_base.svh`).

### Expert: hang triage at regression scale

- **Timeouts.** §F.7.3.3 leaves the default timeout implementation specific; uvm-core uses 9200 s. Set an explicit one with `uvm_root::get().set_timeout(...)`, or with the uvm-core plusarg `+UVM_TIMEOUT=<integer>,<YES or NO>` (not in Annex G). The plusarg value is read with `%d`, so it is a plain count of time units: `+UVM_TIMEOUT=10us,NO` is read as 10, not 10 µs, and the `NO` after it is lost (`uvm_root.svh`). A `time` value is a plain number scaled to the time unit of the code that wrote it, and `uvm_pkg` delays by that number in its own time unit, so compile your code and `uvm_pkg` with the same timescale.
- **Who still objects.** uvm-core's `+UVM_OBJECTION_TRACE` (also not in Annex G) logs every raise and drop, which shows which component or sequence keeps the phase alive.
- **Probes in a timeout hook.** A test can print `get_current_item()`, `last_req()`, `last_rsp()` and `convert2string()` for each sequencer from `pre_abort()` (§13.1.4.6), which is called on every component when a message with the `UVM_EXIT` action, such as the timeout fatal, ends the run; one log line per sequencer then tells you the blocked side without rerunning.
- **Method.** [E-DBG-1](/curriculum/T4_Expert/E-DBG-1_Advanced_UVM_Debug_Methodologies/index) turns this into a full debug methodology, and its [hang lab](/curriculum/T4_Expert/E-DBG-1_Advanced_UVM_Debug_Methodologies/hang-lab) practises it.

### Kata: collect by transaction_id, and watch the queue overflow

Rewrite `ooo_read_seq` from Make It Work so it does **not** use a response handler. It sends 12 reads first, recording each `transaction_id` in a queue `tids`, then collects them in request order with `get_response(rsp, tid)` and checks the data. Keep `ooo_driver` unchanged.

1. **Predict** with the default response queue depth of 8: which `get_response()` call blocks forever, and what is logged?
2. **Fix** it two different ways.

<details>
<summary>Worked solution</summary>

The driver answers in pairs every 10 ns, newest first, and the sequence only collects after its twelfth `finish_item()` returns, at 50 ns. Trace the response queue:

| Time | Driver | Response queue (tids, oldest first) | Note |
| --- | --- | --- | --- |
| 0 ns | takes tids 1, 2 | empty | |
| 10 ns | answers 2, 1; takes 3, 4 | 2 1 | |
| 20 ns | answers 4, 3; takes 5, 6 | 2 1 4 3 | |
| 30 ns | answers 6, 5; takes 7, 8 | 2 1 4 3 6 5 | |
| 40 ns | answers 8, 7; takes 9, 10 | 2 1 4 3 6 5 8 7 | full: 8 entries |
| 50 ns | answers 10, 9; takes 11, 12 | 2 1 4 3 6 5 8 7 | 10 and 9 dropped, no message |
| 50 ns | sequence collects tids 1 to 8 | empty | each found by id |
| 50 ns | sequence calls `get_response(rsp, 9)` | empty | waits |
| 60 ns | answers 12, 11 | 12 11 | no 9: waits forever |

So `get_response(rsp, 9)` blocks forever and the run ends at the phase timeout with nothing else in the log. With `set_response_queue_error_report_enabled(1)` you would also see two `UVM_ERROR` "Response queue overflow, response was dropped" lines at 50 ns.

```systemverilog
// snippet: body() of the by-id version, with fix 1 applied
virtual task body();
  rd_item rd;
  int     tids[$];
  set_response_queue_depth(-1);             // fix 1: room for every outstanding response
  set_response_queue_error_report_enabled(1); // make any future overflow loud
  repeat (12) begin
    rd = rd_item::type_id::create("rd");
    start_item(rd);
    if (!rd.randomize())
      `uvm_fatal("RAND", "rd randomization failed")
    finish_item(rd);
    tids.push_back(rd.get_transaction_id());
    expected[rd.get_transaction_id()] = 32'h1000 + rd.addr;
  end
  foreach (tids[i]) begin
    get_response(rsp, tids[i]);             // rsp is uvm_sequence's built-in RSP handle
    if (rsp.data != expected[tids[i]])
      `uvm_error("RSPDATA", $sformatf("tid=%0d data=0x%08h", tids[i], rsp.data))
  end
endtask
```

**Fix 2:** keep the default depth and collect while sending, for example by forking a collector thread at the start of `body()` that calls `get_response(rsp)` twelve times and checks each response by its id against `expected`, then `wait fork` before `body()` returns. Using the response handler from Make It Work is the third option.
