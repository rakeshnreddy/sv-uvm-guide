  ## Elevator Pitch

  When several sequences run on one sequencer, each `start_item()` puts a request in the sequencer's arbitration queue. Every time the driver asks for an item, the sequencer picks one request. The arbitration mode, the sequence priorities, and any `lock()` or `grab()` decide which. Get it wrong and you see starvation or hangs that look like DUT bugs.

  ## When Arbitration Happens

  Three facts explain most surprises (all from `uvm_sequencer_base` in uvm-core 2020.3.1):

  1. **Only when the driver asks.** The choice is made inside the driver's `get_next_item()`, after every request made in the same time step has been queued. While the driver is busy, nothing is granted.
  2. **Only among requests already queued.** A sequence that starts later, or is still inside `finish_item()` for its previous item, is not a candidate, whatever its priority.
  3. **Locks filter first.** Requests from sequences blocked by another sequence's `lock()` or `grab()` are removed before the mode's rule is applied, in every mode.

  ## The Arbitration Modes

  Set the mode with `set_arbitration()`. The default is `UVM_SEQ_ARB_FIFO`.

  | Mode | Rule (among unblocked requests) | Priority used? |
  | --- | --- | --- |
  | `UVM_SEQ_ARB_FIFO` | the oldest request | no |
  | `UVM_SEQ_ARB_WEIGHTED` | random; chance = priority ÷ sum of the waiting priorities | yes, as a weight |
  | `UVM_SEQ_ARB_RANDOM` | uniformly random | no |
  | `UVM_SEQ_ARB_STRICT_FIFO` | the oldest request among those with the highest priority | yes, strictly |
  | `UVM_SEQ_ARB_STRICT_RANDOM` | uniformly random among those with the highest priority | yes, strictly |
  | `UVM_SEQ_ARB_USER` | your `user_priority_arbitration()` override returns the choice | your rule |

  `STRICT_FIFO` does not mean "strict order across locks": it means *priority first, FIFO among equals*. A lower-priority sequence can starve under either STRICT mode while higher-priority traffic keeps arriving. UVM 1.1 spelled these names `SEQ_ARB_*`; uvm-core 2020.3.1 defines only the `UVM_SEQ_ARB_*` names.

  ```systemverilog
  class my_sequencer extends uvm_sequencer #(my_item);
    `uvm_component_utils(my_sequencer)

    function new(string name, uvm_component parent);
      super.new(name, parent);
    endfunction

    function void build_phase(uvm_phase phase);
      super.build_phase(phase);
      set_arbitration(UVM_SEQ_ARB_WEIGHTED);
    endfunction
  endclass

  // In the test: priorities are passed to start()
  fork
    bulk_seq.start(env.agt.sqr, null, 100);
    urgent_seq.start(env.agt.sqr, null, 300);   // 3× the chance under WEIGHTED
  join
  ```

  **Setting priority.** A root sequence started with no priority argument gets 100. `start()` overwrites the priority, so `seq.set_priority(300)` *before* `seq.start(sqr)` has no effect. Pass the priority as the third argument of `start()`, or call `set_priority()` inside `body()`. A single item can also carry its own priority: `start_item(req, 500)`.

  ## Locks vs. Grabs vs. Priority

  | Tool | What it does in uvm-core 2020.3.1 | Use it for | Watch out for |
  | --- | --- | --- | --- |
  | `lock()` / `unlock()` | Queues a lock request at the back of the arbitration queue. It is granted as soon as no other sequence holds a lock or grab. From then on, every other sequence's requests are blocked until `unlock()`. | Short atomic bursts (program a register, then read it back). | The lock is held until `unlock()`, even while you queue nothing. If `body()` returns still holding it, UVM removes it with `UVM_ERROR [SEQFINERR]`, after everyone else has starved. |
  | `grab()` / `ungrab()` | Same as `lock()`, but the request goes to the **front** of the queue, so it is granted before any lock or grab that is already waiting. | Urgent stimulus, such as an interrupt service routine. | It only jumps the queue; it cannot take the sequencer from a sequence that already holds a lock. |
  | priority | Weights (`WEIGHTED`) or ranks (`STRICT_*`) the waiting requests. | Biasing traffic without exclusivity. | Ignored by `FIFO` and `RANDOM`. |

  The library's own comment on `lock()` says a lock request is "arbitrated the same as any other request". The code (`grant_queued_locks()`) grants it as soon as nothing blocks it, even ahead of older item requests. The sandbox follows the code.

  A child sequence started *with* its parent (`child.start(sqr, this)` or `` `uvm_do ``) is not blocked by its parent's lock. A sequence started without a parent (`child.start(sqr)`) is, which deadlocks a locked parent.

  ## Throttling Without Stalling the Driver

  A common need: a sequence must not send while the DUT has no credits. Wait *before* `start_item()`, so the sequence has no request queued and the sequencer serves other sequences meanwhile.

  ```systemverilog
  class credit_sensitive_seq extends uvm_sequence #(my_item);
    `uvm_object_utils(credit_sensitive_seq)

    credit_monitor credits;    // handle set by whoever starts the sequence

    function new(string name = "credit_sensitive_seq");
      super.new(name);
    endfunction

    virtual task body();
      repeat (20) begin
        wait (credits.available > 0);              // no request queued while waiting
        req = my_item::type_id::create("req");
        start_item(req);
        if (!req.randomize() with { opcode inside { READ, WRITE }; })
          `uvm_error("RAND", "randomization failed")
        finish_item(req);
      end
    endtask
  endclass
  ```

  Two things that do **not** work:
  - Waiting *after* `start_item()` returns. The sequence has been granted, the driver is blocked in `get_next_item()` waiting for this item, and nobody else can be served: you stall the driver.
  - Using `mid_do()` to refuse an item. `mid_do()` is a `void` function that runs inside `finish_item()`, after the grant. It cannot veto or delay anything.

  For a sequence that should stay queued but be skipped until it is ready, override `is_relevant()` (return 0 while not ready) together with `wait_for_relevant()` (a task that returns when it may be ready again). UVM requires both.

  ## Debugging Starvation

  - Print the sequencer state: `` `uvm_info("ARB", env.agt.sqr.convert2string(), UVM_LOW) `` shows the arbitration queue and the lock list.
  - Ask directly: `sqr.is_blocked(seq)`, `sqr.has_lock(seq)`, `sqr.current_grabber()`.
  - Look for `UVM_ERROR [SEQFINERR]` (a sequence ended while still holding a lock) and `UVM_ERROR [SQRUNL]` (`unlock()` without a lock).
  - Put `lock()`/`unlock()` in the same task, with nothing that can block forever in between. SystemVerilog has no exceptions or `finally`; a `disable` or a killed process skips the `unlock()`.
  - Run some regressions with a random mode (`WEIGHTED` or `RANDOM`) to expose ordering assumptions.

  ## Checklist

  - [ ] Can you describe when to choose `lock()` versus `grab()`?
  - [ ] Do you know which arbitration mode your sequencer uses, and whether it reads priority?
  - [ ] Is every `lock()` paired with an `unlock()` on every path through `body()`?
  - [ ] Is a global timeout set, so starvation ends with a fatal instead of a hang?
