## Quick Take

- **What it is:** When two or more sequences run on the same sequencer at the same time, each `start_item()` call puts a **request** into the sequencer's **arbitration queue**. **Arbitration** is the sequencer's choice of which waiting request the driver serves next. Four things decide it: the **arbitration mode** (one of six, set with `set_arbitration()`), the **priority** of each request, any **`lock()`** or **`grab()`** that reserves the sequencer for one sequence, and an optional **`is_relevant()`** check that lets a sequence sit out a round (IEEE 1800.2-2020 §14.2.5, §15.3.2).
- **Why it matters:** Real agents are shared. Background traffic, register programming and an interrupt routine all want the same driver. If you cannot predict who wins, you get a sequence that never runs (**starvation**), a "back-to-back" burst that other traffic splits in half, or a silent hang that looks like a design bug.
- **The Analogy:** The sequencer is an air-traffic control tower with one runway, the driver. Sequences are aircraft that radio in to ask for a slot. The arbitration mode is the tower's rule for picking the next aircraft; priority is how urgent each one claims to be. `lock()` books a block of consecutive slots, and `grab()` is an emergency booking that jumps to the head of the line. *Where it breaks:* the tower clears an aircraft only when the runway asks for the next one, it ignores aircraft that have not radioed in yet, and a block booking never expires by itself: if the owner forgets to release it, the runway sits idle.

**You will be able to:**
1. Predict which request the sequencer grants under each of the six arbitration modes, given the priorities and the queue order.
2. Choose between priority, `lock()` and `grab()` for a scenario, and predict the grant order when locks and grabs wait together.
3. Write a sequence that waits for a resource without stalling the driver: wait before `start_item()`, or use `is_relevant()` with `wait_for_relevant()`.
4. Debug starvation and deadlock (an unreleased lock, an unparented child under a locked parent, a priority that has no effect) from the sequencer state and the log.

**Before you start:** read [The Sequencer-Driver Handshake](/curriculum/T2_Intermediate/I-UVM-3B_Advanced_Sequencing_and_Layering/sequencer-driver-handshake), the previous lesson, for what blocks where. From [I-UVM-3A](/curriculum/T2_Intermediate/I-UVM-3A_Fundamentals/index) you need `start(sqr, parent, priority)`, `start_item()`/`finish_item()` and nested sequences.

### The words you need

You met most of these in I-UVM-3A; here they are in one place, with the meaning this lesson relies on.

| Term | Meaning here |
|---|---|
| **sequence item** (item) | The `uvm_sequence_item` object a sequence hands to the driver, one transaction at a time. |
| **sequence** | A `uvm_sequence` object whose `body()` task creates and sends items. Several sequences can run on one sequencer at once, each in its own process (thread). |
| **sequencer** | The `uvm_sequencer` component between the sequences and the driver. It holds the arbitration queue and decides which sequence's item goes next. |
| **driver** | The `uvm_driver` component that pulls items with `seq_item_port.get_next_item()` and drives them onto the pins. One item at a time. |
| **request** | An entry in the arbitration queue. `start_item()` adds an **item request**; `lock()` and `grab()` add a **lock request**. |
| **grant** | The sequencer's decision for one request. For an item request, `start_item()` returns; for a lock request, `lock()` or `grab()` returns. |
| **root sequence**, **child sequence** | A sequence started with no parent (`seq.start(sqr)`) is a root. One started with a parent (`seq.start(sqr, this)` or `` `uvm_do ``) is that parent's child. |
| **priority** | An integer attached to each request. Higher means more important, but only some modes look at it. |
| **starvation** | A sequence that is ready but is never granted, because the rule always prefers someone else. |

### When the sequencer arbitrates

A sequence waits inside `start_item()` (which calls the sequencer's `wait_for_grant()`). The sequencer makes the choice when the driver asks for work: `get_next_item()`, `try_next_item()`, `get()` or `peek()` (§15.2.1.2). Three facts explain most surprises:

1. **Only when the driver asks.** No item request is granted while the driver is busy with the previous item. In uvm-core 2020.3.1, the reference implementation of IEEE 1800.2, the sequencer also waits for one nonblocking-assignment (NBA) region of the current time slot before it chooses (`uvm_wait_for_nba_region()`), so requests made earlier in the same time slot are counted. (A **time slot** is everything the simulator does at one simulation time; the NBA region is one of its ordered steps, see [F3B Scheduling Regions](/curriculum/T1_Foundational/F3B_Scheduling_Regions/index).) A request made after that point waits for the next choice.
2. **Only among requests already queued.** A sequence that starts later, or is still inside `finish_item()` for its previous item, is not a candidate, whatever its priority.
3. **Filters first, then the rule.** The sequencer removes requests from sequences blocked by another sequence's lock, and requests whose sequence says `is_relevant() == 0`. The mode's rule picks among the rest.

Lock requests are the exception to fact 1. In uvm-core 2020.3.1 a `lock()` or `grab()` is granted as soon as no other lock blocks it, even while the driver is busy. The standard words this differently ("A lock request is arbitrated the same as any other request", §14.2.5.5); [Expert: when is a lock granted?](#expert-when-is-a-lock-granted-the-standard-and-uvm-core) compares the two.

**Predict first.** Two sequences are waiting: `bulk_seq` with priority 100 queued first, then `urgent_seq` with priority 300. The driver calls `get_next_item()`. Who is granted under the default mode, and who under `UVM_SEQ_ARB_STRICT_FIFO`? Decide, then read the diagram.

### The six arbitration modes

Set the mode with `set_arbitration()` and read it back with `get_arbitration()` (§15.3.2.19, §15.3.2.18). The type is the enum `uvm_sequencer_arb_mode` (Annex F.2.4.1). If you never set it, the mode is `UVM_SEQ_ARB_FIFO` (§15.3.2.18).

| Mode | Rule, among the unblocked and relevant item requests | Priority used? |
| --- | --- | --- |
| `UVM_SEQ_ARB_FIFO` | the oldest request | no |
| `UVM_SEQ_ARB_WEIGHTED` | random; chance = its priority ÷ the sum of the waiting priorities | yes, as a weight |
| `UVM_SEQ_ARB_RANDOM` | uniformly random | no |
| `UVM_SEQ_ARB_STRICT_FIFO` | the oldest request among those with the highest priority | yes, strictly |
| `UVM_SEQ_ARB_STRICT_RANDOM` | uniformly random among those with the highest priority | yes, strictly |
| `UVM_SEQ_ARB_USER` | whatever your override of `user_priority_arbitration()` returns (§15.3.2.3) | your rule |

The rules above are how uvm-core 2020.3.1 implements them (`m_choose_next_request()` in `uvm_sequencer_base.svh`); the standard's one-line definitions in F.2.4.1 agree. Read the table as two questions: *is priority ignored, a weight, or a rank?* and *how are ties broken: by age or at random?*

**Worked example: WEIGHTED is odds, not order.** Under `UVM_SEQ_ARB_WEIGHTED`, A (priority 100) and B (priority 300) are waiting. The sum is 400, so B wins this grant with probability 300 ÷ 400 = 75 % and A with 25 %. Over many grants B gets about three of every four, but A is never locked out. That is the main difference from `STRICT_FIFO`, where B wins every time both are waiting and A can starve.

```systemverilog
// snippet: set the mode once, before any sequence starts on this sequencer
class bus_sequencer extends uvm_sequencer #(bus_item);
  `uvm_component_utils(bus_sequencer)

  function new(string name, uvm_component parent);
    super.new(name, parent);
  endfunction

  function void build_phase(uvm_phase phase);
    super.build_phase(phase);
    set_arbitration(UVM_SEQ_ARB_WEIGHTED);   // priorities now act as weights
  endfunction
endclass
```

You can also call `env.agt.sqr.set_arbitration(...)` from the test before it starts the sequences. UVM 1.1 spelled these names `SEQ_ARB_*`; uvm-core 2020.3.1 defines only the `UVM_SEQ_ARB_*` names, so old code needs renaming.

### Priority

A sequence's priority comes from `start()`, and each item request copies it:

- **From `start()`.** The third argument of `start(sqr, parent, this_priority)` sets it. With the default `-1`, a root sequence gets **100** and a child gets its parent's priority (§14.2.3.1, §14.2.5.2).
- **Into each request.** `start_item(item, set_priority)` queues the request with `set_priority` if you pass one (≥ 0), otherwise with the sequence's current `get_priority()` (§14.2.6.2). The value is captured when the request is queued.
- **Changing it.** `set_priority()` inside `body()` affects the *next* `start_item()`, not a request already waiting. In uvm-core 2020.3.1, `start()` assigns the priority when it begins, so `seq.set_priority(300)` *before* `seq.start(sqr)` is overwritten: pass the value as `start(sqr, null, 300)` instead.
- **Legal values.** Use values ≥ 1 (§14.2.5.2: "value shall be >= 1"). uvm-core 2020.3.1 stops the run with `UVM_FATAL [SEQITEMPRI]` when it reads a request priority of 0 or below.
- **Who reads it.** Only `WEIGHTED`, `STRICT_FIFO`, `STRICT_RANDOM`, and a `USER` rule that chooses to. `FIFO` and `RANDOM` ignore it entirely.

```systemverilog
// snippet: three ways to raise priority
// in the test: the whole sequence, from start()
urgent.start(env.agt.sqr, null, 300);

// inside a sequence's body(): one item only
start_item(req, 500);   // this request only; later ones use get_priority()

// inside a sequence's body(): from now on
set_priority(300);      // affects the next start_item(), not a queued one
```

**The classic mistake.** "I set priority 500 and nothing changed." Check, in order: the mode (FIFO and RANDOM ignore priority), *when* the priority was set (before `start()` it is overwritten), and whether a lock is blocking the sequence (filters come before the rule).

### lock() and grab()

Priority only *biases* each single grant: between two of your items, another sequence can still win. When a burst must reach the driver back to back, with nothing in between, the sequence reserves the sequencer.

- **`lock()`** asks for exclusive use of a sequencer. Once it is granted, every other sequence's requests are blocked until the holder calls `unlock()` (§14.2.5.5, §14.2.5.7).
- **`grab()`** asks for the same exclusive use, but its request goes to the **front** of the arbitration queue, ahead of every waiting request, including waiting locks (§14.2.5.6). `ungrab()` releases it (§14.2.5.8).

**Syntax and variants.** Both are tasks on the sequence, and both release methods are functions:

```systemverilog
// snippet: the signatures (uvm_sequence_base, IEEE 1800.2-2020 §14.2.5.5-§14.2.5.10)
task lock (uvm_sequencer_base sequencer = null);   // returns when the lock is granted
task grab (uvm_sequencer_base sequencer = null);   // returns when the grab is granted
function void unlock (uvm_sequencer_base sequencer = null);
function void ungrab (uvm_sequencer_base sequencer = null);   // same as unlock()
function bit is_blocked ();   // 1 if another sequence's lock blocks this one
function bit has_lock ();     // 1 if this sequence holds a lock on its sequencer
```

With no argument they act on the sequence's own sequencer, the one it was started on. A **virtual sequence** (one that starts sequences on other agents' sequencers and runs on a virtual sequencer or on `null`) must name the real sequencer: `grab(p_sequencer.data_sqr)` and later `ungrab(p_sequencer.data_sqr)`. Here `p_sequencer` is the virtual sequence's typed handle to its virtual sequencer, which holds `data_sqr`; [Virtual Sequences](/curriculum/T2_Intermediate/I-UVM-3B_Advanced_Sequencing_and_Layering/virtual-sequences) builds both. With no argument and no sequencer, the standard requires a fatal message (§14.2.5.5); uvm-core reports `UVM_FATAL [LOCKSEQR]` for `lock()` and `UVM_FATAL [GRAB]` for `grab()`. The sequencer offers matching queries: `sqr.is_grabbed()`, `sqr.current_grabber()`, `sqr.is_blocked(seq)` and `sqr.has_lock(seq)` (§15.3.2.8, §15.3.2.9, §15.3.2.15, §15.3.2.16).

| Tool | What it does (uvm-core 2020.3.1) | Use it for | Watch out for |
| --- | --- | --- | --- |
| `lock()` / `unlock()` | Queues a lock request at the back of the queue. It is granted as soon as no other sequence holds a lock or grab. From then on, every other sequence's requests are blocked until `unlock()`. | Short atomic bursts: program a register, then read it back. | The lock is held until `unlock()`, even while the holder queues nothing. If the holder's `start()` finishes still holding it, the sequencer removes it then, with `UVM_ERROR [SEQFINERR]`, after everyone else has starved. |
| `grab()` / `ungrab()` | Same as `lock()`, but the request goes to the **front** of the queue, so it is granted before any lock or grab that is already waiting. | Urgent stimulus, such as an interrupt service routine. | It jumps the queue; it cannot take the sequencer away from a sequence that already holds a lock. |
| priority | Weights (`WEIGHTED`) or ranks (`STRICT_*`) the waiting item requests. | Biasing traffic without exclusivity. | Ignored by `FIFO` and `RANDOM`; never makes a burst atomic. |

**Who is *not* blocked by a lock.** The holder itself, and its **children** at any depth: sequences started with the holder as their parent (`child.start(sqr, this)` or `` `uvm_do(child) ``). The sequencer checks this with `is_child()` (§15.3.2.2), which walks the parent chain. A sequence started *without* the parent argument (`child.start(sqr)`) is a new root, so the parent's own lock blocks it. The parent then waits inside `child.start()` for a child that can never be granted: a **deadlock**, with no error message.

Two rules fall out of the diagram. Release with the **same sequencer argument** you locked with: a bare `ungrab()` in `irq_vseq` acts on its own (virtual) sequencer, reports `UVM_WARNING [SQRUNL]`, and leaves `data_sqr` grabbed. And keep the lock and the release in the **same task**, with nothing between them that can block forever.

### Waiting for a resource: is_relevant() and wait_for_relevant()

Some sequences may only send when the design under test (DUT) can accept: it has free buffer credits, or a mode is configured. Such a sequence can stay in the queue but **sit out** each choice until it is ready.

- **`is_relevant()`** is a virtual function of the sequence. The default returns 1. At every choice the sequencer calls it on the queued, unblocked item requests it considers (in FIFO mode it stops at the first relevant one); a request whose sequence returns 0 is skipped this time (§14.2.5.3).
- **`wait_for_relevant()`** is a virtual task. When *no* request can be granted and some are only waiting because they are not relevant, the sequencer calls `wait_for_relevant()` on each of those sequences and chooses again as soon as one returns, or as soon as the queue changes (§14.2.5.4; uvm-core `m_wait_for_available_sequence()`).
- **The rule:** if you override `is_relevant()`, you must also override `wait_for_relevant()` (§14.2.5.4: the sequence "shall also supply a wait_for_relevant method"). uvm-core enforces it with `UVM_FATAL [RELMSM] is_relevant() was implemented without defining wait_for_relevant()`.

```systemverilog
// snippet: a credit-gated sequence; credit_pool is a plain class shared with the test
class credit_pool;
  int credits;                     // the testbench adds credits as the DUT frees space
endclass

class credit_seq extends burst_seq;
  `uvm_object_utils(credit_seq)
  credit_pool pool;                // set by whoever starts the sequence

  function new(string name = "credit_seq");
    super.new(name);
  endfunction

  // Called at every arbitration: cheap, no side effects, no waiting.
  virtual function bit is_relevant();
    return pool.credits > 0;
  endfunction

  // Called only when nothing can be granted: return once a credit exists.
  virtual task wait_for_relevant();
    wait (pool.credits > 0);
  endtask

  virtual task body();
    repeat (n) begin
      req = bus_item::type_id::create("req");
      start_item(req);             // granted only while is_relevant() is 1
      pool.credits--;              // spend the credit that made us relevant
      if (!req.randomize()) `uvm_fatal("RAND", "bus_item randomize failed")
      req.src = get_name();
      finish_item(req);
    end
  endtask
endclass
```

**Which one to use.** Waiting before `start_item()` is simpler, but the check can go stale: the request may wait behind others while their items use up the credits, and the item is then sent anyway. `is_relevant()` is evaluated at every choice, so it gates at grant time. Use the early wait when only this sequence spends the resource; use `is_relevant()` when several sequences compete for it.

**Two hooks that do not throttle.** `pre_do()` is a task, but it runs *after* the grant (§14.2.6.2), so waiting there stalls the driver just like waiting after `start_item()`. `mid_do()` is a `void` function that runs inside `finish_item()`; it cannot delay or refuse anything.

### Debugging starvation and deadlock

A blocked request never prints anything: arbitration problems look like silence. Work from the symptom.

| Symptom | Likely cause | Probe | Fix |
| --- | --- | --- | --- |
| One sequence never runs while others do | `STRICT_*` mode and a higher-priority stream that never pauses | `sqr.get_arbitration()`; the priorities passed to `start()` | Use `WEIGHTED`, lower the stream's priority, or let it pause |
| All traffic stops; no errors; the driver idles in `get_next_item()` | A lock or grab that is never released while its holder is still running | `sqr.is_grabbed()`, `sqr.current_grabber().get_full_name()` | Pair every `lock()` with `unlock()` in the same task, on every path |
| Hang right after a parent calls `lock()` | A child started without a parent: `child.start(m_sequencer)` | `child.is_blocked()` returns 1 | Start it as `child.start(m_sequencer, this)` or with `` `uvm_do `` |
| `UVM_ERROR [SEQFINERR] Parent sequence '…' should not finish before locks from itself and descedent sequences are removed.` | A sequence's `start()` finished while it, or a child, still held a lock | The two sequence names in the message | Add the missing `unlock()`/`ungrab()` (the log line keeps uvm-core's spelling "descedent") |
| `UVM_WARNING [SQRUNL] Sequence '…' called ungrab / unlock, but didn't have lock` | `unlock()` called twice, by another sequence object, or on the wrong sequencer | `sqr.has_lock(seq)` on the sequencer you meant | Release with the same sequence and the same sequencer argument |
| Priority "has no effect" | `FIFO` or `RANDOM` mode, or `set_priority()` before `start()` | `get_arbitration()`, `seq.get_priority()` inside `body()` | Pick a priority-aware mode; pass the priority to `start()` |
| `UVM_FATAL [SEQITEMPRI] Sequence item from … has illegal priority: 0` | A priority of 0 or below, read by `WEIGHTED` or `STRICT_*` | The `start()` or `start_item()` arguments | Use priorities ≥ 1 |
| `UVM_FATAL [RELMSM]` or `[SEQRELEVANTLOOP]` | `is_relevant()` without `wait_for_relevant()`, or a `wait_for_relevant()` that returns at once | The sequence's two overrides | Override both; make `wait_for_relevant()` wait on the real condition |

`sqr.convert2string()` prints the queue and the lock list as numbers, `-- arb i/id/type: 0/2/SEQ_TYPE_REQ …` and `-- lock_list i/id: 0/3`, where *id* is the sequence id on that sequencer (uvm-core `uvm_sequencer_base.svh`). Map an id to a name with `seq.get_sequence_id()` in each candidate's log, or print `current_grabber().get_full_name()` directly. If nothing ends the hang, uvm-core stops at its default phase timeout of 9200 s (`UVM_DEFAULT_TIMEOUT`) with `UVM_FATAL [PH_TIMEOUT]`; set `uvm_root::get().set_timeout(...)` in the test to end such runs much sooner (IEEE 1800.2-2020 F.7.3.3 leaves the default to the implementation). The [E-DBG-1 hang lab](/curriculum/T4_Expert/E-DBG-1_Advanced_UVM_Debug_Methodologies/hang-lab) practises the full triage.

### Recap

- The sequencer chooses only when the driver asks, only among queued requests, after dropping blocked and not-relevant ones.
- `FIFO` (the default) and `RANDOM` ignore priority; `WEIGHTED` treats it as odds; `STRICT_*` as rank, which can starve.
- A sequence's priority comes from `start()` (100 for a root, the parent's for a child) and is copied into each request at `start_item()`.
- `lock()` and `grab()` reserve the sequencer until released; the holder and its children are exempt. A grab queues at the front; neither takes the sequencer from a current holder.
- Wait for resources before `start_item()` or with `is_relevant()` plus `wait_for_relevant()`, never after the grant.
- Arbitration bugs are silent: probe the mode, `is_grabbed()`, `current_grabber()` and the log ids.

## Push Further

### Expert: when is a lock granted? The standard and uvm-core

IEEE 1800.2-2020 §14.2.5.5 says: "A lock request is arbitrated the same as any other request. A lock is granted after all previously arbitrated requests are completed and no other locks or grabs are blocking this sequence." §15.3.2.10 repeats it for the sequencer's `lock()`.

What uvm-core 2020.3.1 does, as observed in `uvm_sequencer_base.svh` (`m_lock_req()`, `grant_queued_locks()`): `lock()` pushes the lock request to the back of the queue, then immediately grants the first lock request in the queue that is not blocked. With no other lock held, the lock is granted at once, ahead of older item requests, even while the driver is busy. Lock requests are also granted from `unlock()`, `item_done()`, `send_request()` and every arbitration. `DEVIATIONS.md` in the release does not list this; treat it as **tool-dependent**: other implementations may make the lock wait for earlier requests.

Two more source observations:

- **Grabs among grabs.** `grab()` uses `push_front`, so a later grab is queued ahead of an earlier waiting grab. The source marks this with "Missing: grabs get arbitrated behind other grabs".
- **Nested locks.** A second `lock()` by the holder is granted at once and adds a second entry to the lock list. `unlock()` removes one entry, so `lock(); lock(); unlock();` still blocks everyone else. §14.2.5.7 says unlock "removes any locks obtained by this sequence".

Write tests that hold under both readings: take the lock before you queue competing traffic, and test pre-emption with scenarios such as "a lock and a grab both wait behind a held lock", where every reading gives the same answer.

### Expert: custom arbitration with UVM_SEQ_ARB_USER

Set `UVM_SEQ_ARB_USER` and override `user_priority_arbitration()` in a sequencer subclass (§15.3.2.3). The argument `avail_sequences` holds **indexes into the arbitration queue** of the requests that are unblocked and relevant; `get_arbitration_sequence(index)` returns the sequence behind an index (§15.3.2.4). The override must return one of those indexes. In uvm-core 2020.3.1 anything else stops the run with `UVM_FATAL [Sequencer] Error in User arbitration, sequence N not available`.

```systemverilog
// snippet: "strict LIFO": highest sequence priority wins, the newest request breaks ties
class lifo_sequencer extends uvm_sequencer #(bus_item);
  `uvm_component_utils(lifo_sequencer)

  function new(string name, uvm_component parent);
    super.new(name, parent);
    set_arbitration(UVM_SEQ_ARB_USER);
  endfunction

  virtual function int user_priority_arbitration(int avail_sequences[$]);
    int best = avail_sequences[0];
    foreach (avail_sequences[i]) begin
      int idx = avail_sequences[i];
      // avail_sequences is in queue order, so >= keeps the newest of equal priority
      if (get_arbitration_sequence(idx).get_priority() >=
          get_arbitration_sequence(best).get_priority())
        best = idx;
    end
    return best;
  endfunction
endclass
```

A traced decision: the queue holds `0: bulk (100)`, `1: credit_seq (200)` whose `is_relevant()` returns 0, `2: urgent_a (300)` and `3: urgent_b (300)`. `avail_sequences` is `{0, 2, 3}`: the not-relevant request is filtered out before your function is called. The loop keeps 0, then 2 (300 ≥ 100), then 3 (300 ≥ 300), and returns 3, so `urgent_b` is granted.

Two cautions. This override reads the *sequence's* current priority, not the priority captured in each request; `get_arbitration_sequence()` gives no access to the latter. And §15.3.2.3 says the function "is called even if there is only one sequence available", but uvm-core 2020.3.1 returns early with 0 or 1 candidates without calling it, so do not count calls to track state such as round-robin history (tool-dependent).

### Expert: priority values, inheritance and capture

- **The standard is inconsistent about 0.** §14.2.3.1 allows "a non-negative value of `this_priority`", while §14.2.5.2 says the value "shall be >= 1". Use values ≥ 1.
- **What uvm-core 2020.3.1 checks.** `start()` stops with `UVM_FATAL [SEQPRI]` for a priority below -1. A priority of 0 is accepted there, but because `start_item()` copies the priority into the request, the request then has priority 0, and `UVM_FATAL [SEQITEMPRI]` fires as soon as a `WEIGHTED` or `STRICT_*` choice with two or more candidates reads it. A priority-0 sequence can therefore pass silently under FIFO and fail when someone changes the mode.
- **Inheritance.** A child started with the default priority takes its parent's (§14.2.3.1). A library or virtual sequence started at 300 therefore runs all its children at 300, unless they pass their own value.
- **Capture.** §14.2.5.2 says a changed priority is used "the next time that it arbitrates". In practice the request already holds its own copy from `start_item()`, so `set_priority()` reaches only requests queued afterwards.

### Expert: fairness, randomness and reproducibility

- **Starvation by design.** `STRICT_FIFO` and `STRICT_RANDOM` never grant a lower priority while a higher one waits. A background stream at priority 200 that never pauses starves everything at 100. Use `WEIGHTED` when every stream must make progress.
- **Where the random draws come from.** `WEIGHTED`, `RANDOM` and `STRICT_RANDOM` call `$urandom_range()` (IEEE 1800-2023 §18.13.2) inside the arbitration code, which runs in the thread that called `get_next_item()`: the driver's. By random stability (§18.14, §18.14.2), a change in how many random numbers that thread draws, for example a driver that starts randomizing delays, changes every later arbitration pick for the same seed.
- **Same-time starts.** Sequences started at the same simulation time queue in an order the simulator chooses (IEEE 1800-2023 §4.7). Under FIFO that order decides the first grant. When a test depends on it, stagger the starts (as Make It Work does with `#1ns`) or start sequentially.
- **Regression strategy.** Run some seeds with `WEIGHTED` or `RANDOM` to flush out stimulus that silently assumes one ordering, and record the mode in the log.

### Expert: locks, killed processes and cleanup

A lock belongs to the **sequence object**, not to a thread. SystemVerilog has no exceptions or `finally` block, so a `disable` statement, a `disable fork` or a killed process can skip the `unlock()`.

- If only an inner thread of `body()` dies, the lock stays in place until the sequence's `start()` finishes, which removes it with `SEQFINERR`.
- In uvm-core 2020.3.1, if the process that called `start()` is killed, a process guard reports `UVM_WARNING [SEQPRTZMB]` and calls `kill()`; if `body()`'s own process is killed (an errant `disable fork`), `start()` reports `UVM_WARNING [SEQBDYZMB]` and calls `kill()`. Lock requests whose calling process died are removed with `UVM_ERROR [SEQLCKZMB]`. These guards are uvm-core features, not part of IEEE 1800.2.
- `kill()` (§14.2.5.11) and `sqr.stop_sequences()` (§15.3.2.14) remove the sequence's requests and locks, including its children's. §14.2.5.11 says `post_body()` and `post_start()` then run; uvm-core 2020.3.1 kills the process that would run them, so they do not (tool-dependent). Never put the `unlock()` in `post_body()` as a safety net.

### Kata: credits without stalling

**Goal:** write `credit_seq` (objective 3) and predict its grant times.

**Setup.** Start from Make It Work. Remove `urgent` and `isr`, give `bulk` `n = 2`, keep the default FIFO mode, and add a `credit_pool` with `credits = 1`. Start `credit_seq` (`n = 2`) at 1 ns on the same sequencer, and let the test do `#35ns pool.credits++;`.

**Requirements:**
1. `credit_seq` stays queued while it has no credit, and other traffic keeps flowing.
2. It spends one credit per item, and never sends an item without one.
3. Before you run anything, write down the time and source of every grant.

<details>
<summary>Worked solution (try the kata first)</summary>

The class is the `credit_seq` shown in "Waiting for a resource" above: `is_relevant()` returns `pool.credits > 0`, `wait_for_relevant()` does `wait (pool.credits > 0)`, and `body()` decrements `pool.credits` right after `start_item()` returns. The test side:

```systemverilog
// snippet: the kata's run_phase body (FIFO mode, from the Make It Work test)
credit_pool pool = new();
burst_seq   bulk = burst_seq::type_id::create("bulk");
credit_seq  cs   = credit_seq::type_id::create("cs");
pool.credits = 1;
bulk.n = 2;
cs.n   = 2;
cs.pool = pool;
phase.raise_objection(this);
fork
  bulk.start(sqr);
  begin #1ns; cs.start(sqr); end
  begin #35ns; pool.credits++; end      // the DUT frees one buffer
join
phase.drop_objection(this);
```

Declare `pool`, `bulk` and `cs` at the top of `run_phase`, before any statement. The grant order, traced through uvm-core 2020.3.1:

| Time | Waiting | Credits | Grant | Why |
|---|---|---|---|---|
| 0 | bulk | 1 | bulk | only candidate |
| 10 | cs (since 1 ns), bulk (since 10 ns) | 1 | cs | oldest and relevant; credits drop to 0 |
| 20 | bulk, cs (not relevant) | 0 | bulk | cs is skipped; bulk's last item |
| 30 | cs (not relevant) | 0 | none | the sequencer calls `cs.wait_for_relevant()`; the driver waits |
| 35 | cs | 1 | cs | the credit arrives, `wait_for_relevant()` returns, the sequencer chooses again |

The run ends at 45 ns. The driver sat idle from 30 to 35 ns only because nothing could legally go.

**Extension.** Give bulk `n = 4` and predict again. The correct `credit_seq` is skipped at 30 ns, so bulk runs at 30 ns; cs takes its second item at 40 ns and the run ends at 60 ns. A version that waits for the credit *after* `start_item()` is granted at 30 ns with no credit, holds the driver idle until 35 ns while bulk is ready, and the run ends at 65 ns.
