## Quick Take

- **What it is:** The **Universal Verification Methodology (UVM)** is a standard base class library for building testbenches in SystemVerilog. IEEE 1800.2-2020 defines it as "a set of application programming interfaces (APIs) that defines a base class library (BCL)" (§1.1), and Accellera's **uvm-core 2020.3.1** is the reference implementation you compile with your bench. This lesson takes the layered, class-based testbench (TB) you can already write and shows which part of it each UVM mechanism replaces.
- **Why it matters:** A hand-built class bench works for one block and one engineer. When the project grows (more tests, a second team, reuse at subsystem or SoC level), the same few limits appear in every bench: hard-coded construction, settings passed through constructor chains, end-of-test rules invented per bench, consumers wired point to point, stimulus welded into the environment, and a home-made pass/fail line. Each UVM mechanism removes one of those limits. Without that map, UVM looks like ceremony; with it, every base class has a reason.
- **The Analogy:** UVM is the standard pipe fittings and building code of testbench construction. Any plumber can work on any house, and a part made for one house fits the next. *Where it breaks:* the building code does not build the house. UVM gives you no checks, reference models or coverage for your design under test (DUT); you still write those (the register layer's built-in checks are the one exception). And a garden shed does not need a building code: a small bench that will never be reused may be better off without UVM.

**You will be able to:**
1. **Draw** a layered class-based SystemVerilog testbench for a FIFO (transaction, generator, driver, monitor, scoreboard, coverage, environment, test) and state each layer's job and how it is connected (handle, mailbox, virtual interface).
2. **Explain**, for each of the factory, phasing, the configuration database, TLM, sequences and reporting, which limit of the layered bench it removes and what new failure mode it brings.
3. **Map** each layer to its UVM base class (`uvm_sequence_item`, `uvm_sequence`, `uvm_sequencer`, `uvm_driver`, `uvm_monitor`, `uvm_agent`, `uvm_scoreboard`, `uvm_env`, `uvm_test`).
4. **Decide** whether UVM is worth its overhead for a given block or project, and justify the decision.
5. **Compare** the IEEE 1800.2-2020 standard with the uvm-core reference implementation, and place both in UVM's history.

### The layered testbench you can already build

In the SystemVerilog half of this tier you met every piece of a **layered testbench**: classes and handles ([I-SV-1](/curriculum/T2_Intermediate/I-SV-1_OOP/index)), constrained-random transactions ([I-SV-2A](/curriculum/T2_Intermediate/I-SV-2A_Constrained_Randomization_Fundamentals/index)), covergroups ([I-SV-3A](/curriculum/T2_Intermediate/I-SV-3A_Functional_Coverage_Fundamentals/index)), mailboxes and threads ([I-SV-5](/curriculum/T2_Intermediate/I-SV-5_Synchronization_and_IPC/index)), and interfaces with clocking blocks ([F4C](/curriculum/T1_Foundational/F4C_Clocking_Blocks/index)). Put together, they give each job in the bench its own class:

| Layer (instance in Make It Work) | Class | Single job | Talks to the next layer through |
|---|---|---|---|
| Transaction | `fifo_txn` | One FIFO operation as data: `op` (WRITE or READ), `data`, and `accepted` (filled in by the monitor) | It *is* the message |
| Generator (`gen`) | `fifo_gen` | Creates a new randomized `fifo_txn` for every item | Bounded mailbox `gen2drv` (bound 1) |
| Driver (`drv`) | `fifo_drv` | Turns one transaction per clock into pin activity | Virtual interface `vif`, through the clocking block `drv_cb` |
| Monitor (`mon`) | `fifo_mon` | Turns pin activity back into transactions; never drives | `vif.mon_cb` in, mailboxes `mon2sb` and `mon2cov` out |
| Scoreboard (`sb`) | `fifo_sb` | Predicts with a reference model (a queue) and compares | Reads `mon2sb` |
| Coverage (`cov`) | `fifo_cov` | Samples a covergroup on what really happened | Reads `mon2cov` |
| Environment (`env`) | `fifo_env` | Builds the layers, connects them, starts them, decides when the test is over | Holds a handle to every layer |
| Test (`test`) | `fifo_test` | Reads the knob `n` from `+N=`, builds the env, prints the verdict | Constructor arguments |

The key property is **one job per class**: the driver knows the pins but not what to send, the generator knows what to send but not the pins, and the scoreboard never looks at the pins at all. Follow one transaction through the picture below, from `gen` to `sb`.

**Predict before you read on.** Using only the picture, answer three questions: (1) if the FIFO's data width changes from 8 to 16 bits, which classes change? (2) If a second FIFO is added to the chip, which classes are copied or edited? (3) If one test needs a driver that corrupts data on purpose, which classes change?

**Debrief.** (1) The transaction, the interface and everything that declares `bit [7:0]`: a width change ripples through the bench, which is why real benches parameterize types. (2) Almost everything below the test: `fifo_env` builds exactly one set of layers with `new`, so a second FIFO means a second set of handles, mailboxes and constructor calls, or a copied environment. (3) `fifo_env`, because the line `drv = new(vif, gen2drv);` names the concrete class, plus `fifo_test`, which must pass a knob to choose the new driver. Questions 2 and 3 are where the hand-built bench strains; that is the subject of the next subsection.

**Two mistakes everyone makes in this bench**, and you must not carry into UVM:
- **Reusing one transaction handle.** A mailbox carries *handles*, not copies (IEEE 1800-2023 §15.4). If the generator or monitor calls `new` once and then refills the same object, the receiver sees values that were overwritten after they were sent. Create a new object for every item, as `fifo_gen.run` and `fifo_mon.publish` do. The full story is in [I-SV-5: Mailboxes](/curriculum/T2_Intermediate/I-SV-5_Synchronization_and_IPC/mailboxes).
- **Driving the DUT with blocking assignments at the clock edge.** The bench and the DUT wake on the same edge, and the simulator may run them in any order (§4.7), so the drive races the flops (§4.8). Drive through a clocking block (`vif.drv_cb.wr_en <= 1'b1`) and sample through one (`vif.mon_cb`), as in [F4C](/curriculum/T1_Foundational/F4C_Clocking_Blocks/index). UVM does not fix this for you: a UVM driver still drives through a clocking block.

### Where the layered bench strains

Nothing in the Make It Work bench is wrong. It is race-free, self-checking and passes with zero mismatches. Its limits appear only when the bench has to grow. Here are the six, each shown in the bench's own code.

**1. Construction is hard-coded.** `fifo_env` names every concrete class:

```systemverilog
// snippet: fifo_env::new
gen = new(gen2drv, n, depth);
drv = new(vif, gen2drv);   // to use err_drv in one test you must edit this line
mon = new(vif, mon2sb, mon2cov);
```

To substitute an error-injecting driver, a slower monitor or a mock scoreboard in one test, you edit the environment, or add a knob and an `if` for every variant.

**2. Settings travel through constructor chains.** The virtual interface, `DEPTH` and the knob `n` go from `tb_top` to `fifo_test`, then to `fifo_env`, then to each layer. Every new setting adds an argument to every constructor on its path, and a deeper hierarchy makes the chain longer.

**3. Build, connect, run and end of test are ordered by hand.** `fifo_env::new` builds and connects in one step (the mailboxes are passed into constructors), and `fifo_env::run` starts every thread and then decides by counting when the test is over:

```systemverilog
// snippet: fifo_env::run
fork
  sb.run(gen.n_total);       // the test ends when the scoreboard has seen n_total items
  begin
    repeat (4 * gen.n_total + 100) @(vif.mon_cb);   // a hand-made watchdog
    timed_out = 1'b1;
  end
join_any
```

A second environment needs its own counting rule. Two environments in one bench must agree on who decides the end, and a rule like `#10000 $finish` cuts off transactions still in flight.

**4. Consumers are wired point to point.** The monitor owns one mailbox per consumer (`mon2sb`, `mon2cov`). Adding a protocol checker means editing the monitor's constructor and its `publish` function, and the environment.

**5. Stimulus is welded into the environment.** `fifo_gen` is one random loop followed by drain reads. A directed corner case, a different traffic mix or a reused stimulus library means a new generator class and an edit to `fifo_env` to construct it.

**6. Messages and the verdict are home-made.** The bench reports with `$display` and `$error`, and `fifo_test` computes `PASS=… FAIL=…` from the scoreboard's own counters. An `$error` from the bound assertion module `fifo_sva` is *not* in that count: the bench can print `FAIL=0` while an assertion failed. There is also no standard way to make the log quieter or louder.

**What this adds up to: copy-paste reuse.** At subsystem or SoC level the FIFO is written by RTL, not by your driver. To reuse your monitor, scoreboard and coverage there, without the generator and driver, you copy `fifo_env`, delete the stimulus half and re-wire the rest. Two copies then drift apart. This is the "reuse problem" UVM was built for.

**Debugging the layered bench (symptom, cause, fix).** These are the failures you will see in this kind of bench; Make It Work turns three of them into a debug challenge.

| Symptom in the log | Cause | Fix |
|---|---|---|
| Mismatches start where a read completes on the same edge as a new write, then continue; `pending` is not 0 | One transaction handle reused: the write overwrote an object still in a mailbox | `new` per item in the generator and the monitor |
| Every read mismatches; the "actual" value is always the previous read's data | The monitor captures `rd_data` at the edge where `rd_en` was sampled, ignoring the DUT's one-cycle read latency | Remember the accepted read and capture `rd_data` at the next edge |
| `mismatches=0` but `pending` is not 0, or fewer items than expected | The test ended before the scoreboard drained (a fixed delay, or ending when the generator returns) | End when the scoreboard has seen every item, with a watchdog |
| `TIMEOUT` and the bench hangs at a `get` | A layer never started, or a bounded mailbox has no reader | Check every `fork` branch is started; check mailbox bounds |
| Results change when files are reordered or the tool changes | Blocking drives or unclocked samples at the active edge | Drive through `drv_cb`, sample through `mon_cb` |

### Six UVM mechanisms and the pain each removes

Each limit above has one standard answer. The table is the summary; the notes after it show what you will write and the new mistake each mechanism brings, because no mechanism is free.

| 1. Hard-coded `new` of concrete classes | **Factory**: create by type, substitute by override | `fifo_drv::type_id::create("drv", this)`, and in one test `fifo_drv::type_id::set_type_override(err_drv::get_type())` | IEEE 1800.2-2020 Clause 8 (§8.2.3.2.4, §8.2.3.2.5) | [I-UVM-1B](/curriculum/T2_Intermediate/I-UVM-1B_The_UVM_Factory/index) |

| 3. Hand-ordered build, connect and run; end of test by counting | **Phasing** and **objections** | `build_phase`, `connect_phase`, `run_phase`, `check_phase`, `report_phase`; `phase.raise_objection(this)` and `drop_objection` around the stimulus | §9.8, §9.3.1.7, §10.5 | [I-UVM-1C](/curriculum/T2_Intermediate/I-UVM-1C_UVM_Phasing/index) |

| 5. | 6. `$display`, `$error` and a home-made verdict | **Reporting** | `` `uvm_info ``, `` `uvm_error ``, `` `uvm_fatal ``; the report server counts every severity and prints the summary | Clause 6, Annex B.1 | [I-UVM-1D](/curriculum/T2_Intermediate/I-UVM-1D_Reporting_and_Run_Control/index) |

**Factory.** Components ask the factory for a type instead of calling `new`, so a test can substitute a subclass without touching the environment:

```systemverilog
// snippet: fifo_agent::build_phase asks the factory, not new()
drv = fifo_drv::type_id::create("drv", this);

// snippet: err_test::build_phase, before the environment is built
fifo_drv::type_id::set_type_override(err_drv::get_type());   // err_drv extends fifo_drv
super.build_phase(phase);                                    // the base test builds env
```

The override applies to every later request for `fifo_drv` "provided no instance override applies", and the original type "shall be a super class of the override_type" (§8.2.3.2.5). *New failure mode:* an override registered after the component was created, or for a type nobody requests, does nothing, and no error tells you so.

**Configuration database.** `tb_top` publishes the virtual interface once; each component that needs it reads it by name:

```systemverilog
// snippet: tb_top, before run_test()
uvm_config_db#(virtual fifo_if)::set(null, "uvm_test_top.env.agt*", "vif", bus);

// snippet: fifo_drv::build_phase
if (!uvm_config_db#(virtual fifo_if)::get(this, "", "vif", vif))
  `uvm_fatal("NOVIF", "no virtual interface set for this driver")
```

Nothing between `tb_top` and the driver changes when a setting is added (Annex C.4.2.2.1, C.4.2.2.2). *New failure mode:* `get` returns 0 when the path or the field name does not match. Ignore the return value and the vif stays `null` until the first access fails.

**Phasing and objections.** Every component implements the same phase methods, and the library calls them in a fixed order: `build_phase` top-down, then `connect_phase`, `end_of_elaboration_phase` and `start_of_simulation_phase`, all at time 0, then `run_phase`, then `extract_phase`, `check_phase`, `report_phase` and `final_phase` (§9.8.1). The run phase ends when every objection has been dropped, not when a task returns (§13.1.4.1.5):

```systemverilog
// snippet: fifo_test::run_phase
phase.raise_objection(this);
seq.start(env.agt.sqr);
phase.drop_objection(this);
```

*What phasing does not do:* it orders construction and connection, but every component's `run_phase` runs concurrently (§9.6), so run-time races against the DUT are still prevented by clocking blocks, not by UVM. *New failure modes:* forget to raise and the run phase ends at time 0 with no traffic, which can look like a pass; forget to drop and the test hangs until a timeout.

**TLM analysis ports.** The monitor publishes once; any number of subscribers listen:

```systemverilog
// snippet: fifo_mon
uvm_analysis_port #(fifo_item) ap;   // built in build_phase: ap = new("ap", this);
ap.write(t);                         // in run_phase, once per observed item

// snippet: fifo_env::connect_phase
agt.mon.ap.connect(sb.item_imp);         // an analysis imp the scoreboard declares
agt.mon.ap.connect(cov.analysis_export); // uvm_subscriber's built-in imp
```

`write` "Sends the specified value to all connected interfaces" (§12.2.10.1.4): it calls each subscriber's `write` function in turn, in zero time. Adding a checker adds one `connect` line in the environment; the monitor is not edited. *New failure mode:* an analysis port with nothing connected is legal, so a scoreboard that was never connected receives nothing and reports no mismatches. A good scoreboard checks in `check_phase` that it saw traffic.

**Sequences.** The generator becomes a sequence object that runs on the agent's sequencer; the driver pulls items:

```systemverilog
// snippet
class fifo_rand_seq extends uvm_sequence #(fifo_item);
  `uvm_object_utils(fifo_rand_seq)
  int unsigned n = 1000;

  function new(string name = "fifo_rand_seq");
    super.new(name);
  endfunction

  task body();
    repeat (n) begin
      req = fifo_item::type_id::create("req");
      start_item(req);
      if (!req.randomize()) `uvm_fatal("RAND", "fifo_item randomize failed")
      finish_item(req);
    end
  endtask
endclass
```

A sequence runs on any sequencer for `fifo_item`; `start` takes "the sequencer on which to run this sequence" (§14.2.3.1), and the driver pulls through `seq_item_port` (§13.7.2.1). Tests choose, combine and layer sequences without editing the environment. *New failure mode:* a driver that never calls `item_done` leaves `finish_item` waiting forever.

**Reporting.** Every message goes through the report server, which filters by verbosity, counts each severity, and prints a summary at the end:

```systemverilog
// snippet: fifo_sb::write
`uvm_error("SCB", $sformatf("read %02h, expected %02h", t.data, exp))
```

Pass or fail becomes "no `UVM_ERROR` and no `UVM_FATAL` in the report summary", which every UVM bench shares (§6.5.1.2.6 `get_severity_count`). *New failure mode:* a plain `$error`, such as one in an assertion's action block, bypasses the report server and is missing from those counts.

The same agent class serves block level and SoC level with one configuration setting, which is exactly the copy of `fifo_env` the hand-built bench needed.

Two more facts about the shape of a UVM bench, which [I-UVM-1A](/curriculum/T2_Intermediate/I-UVM-1A_Components/index) develops:
- **Components** (test, env, agent, sequencer, driver, monitor, scoreboard, subscriber) are "quasi-static objects that exist throughout simulation" and form a hierarchy, while **transactions** "are transient in nature" (§5.1). - Every component is created in a parent's `build_phase` with `::type_id::create(name, this)`, never with `new`, so the factory can substitute it and the hierarchy knows its name.

- **UVM is a library and an API standard.** IEEE 1800.2-2020 specifies the classes and their behaviour (§1.1); uvm-core is Accellera's reference implementation. All of UVM is exported through `uvm_pkg` (§1.4.5): a UVM file starts with `import uvm_pkg::*;` and `` `include "uvm_macros.svh" ``.
- **It is not a language or a simulator feature.** Every UVM class is ordinary SystemVerilog built on classes, parameterized classes, virtual interfaces and mailbox-like queues you already know. Many simulators ship a precompiled copy for convenience (tool-dependent), but it is still compiled SystemVerilog.
- **It does not make simulation faster.** It adds objects, phases, factory lookups, configuration lookups and message filtering on top of the same scheduler. Its payoff is engineering time, reuse and consistency, not simulation speed. See Expert: what UVM costs.
- **It does not verify your design for you.** `uvm_scoreboard` is only "the base class for user-defined scoreboards" (§13.6); the reference model, the comparison and the covergroups are your code, written with SystemVerilog's own randomization and coverage (IEEE 1800-2023 Clauses 18 and 19). The register layer is the one exception: a `mirror` with checking reports mismatches (§18.1.5.6) and Annex E supplies built-in register test sequences ([A-UVM-4A](/curriculum/T3_Advanced/A-UVM-4A_RAL_Fundamentals/index)).

### Where UVM came from

UVM did not appear from nothing; it standardized what several vendor libraries had already proven. The IEEE 1800.2-2020 Introduction (informative) gives the lineage: UVM "is built on the Open Verification Methodology (OVM), which combined the Advanced Verification Methodology (AVM) with the Universal Reuse Methodology (URM) and concepts from the e Reuse Methodology (eRM)", and it "also infuses concepts and code from the Verification Methodology Manual (VMM)". Its TLM facilities are based on the OSCI SystemC TLM work, though not an exact copy.

Three facts to keep straight, because interviewers and older material get them wrong:
- **The first IEEE UVM standard is IEEE 1800.2-2017**, not 2020. IEEE 1800.2-2020 is its revision ("Revision of IEEE Std 1800.2-2017"), and it is the edition this course follows.
- **"UVM 1.2" is a pre-IEEE Accellera release.** Code written for it mostly runs on uvm-core, and uvm-core marks the leftovers it still supports as `@uvm-compat` (Expert: the standard and the implementation).
- **The standard and the implementation are different documents.** The standard says what a class must do; uvm-core is one implementation of it, with some features the standard does not define. This course labels those "uvm-core impl.".

### When UVM is worth it, and when it is not

UVM is the usual choice for simulation benches that will be reused or shared, but "usual" is not "always". Weigh these criteria for a given block:

| Criterion | Points toward UVM | Points toward a plain SV bench or formal |
|---|---|---|
| Reuse horizon | The block, its agent or its env will be reused at subsystem or SoC level, or on the next chip | One-off block, no reuse planned |
| Team | Several engineers, several sites, people joining mid-project | One or two engineers |
| VIP | You must integrate bought or in-house verification IP, which is commonly delivered as UVM agents | No external VIP |
| Regression scale | Many tests and seeds, tests chosen on the command line, consistent pass/fail across a farm | A handful of directed tests |
| Protocol complexity | Layered or multi-interface protocols, virtual sequences across agents | One simple interface |
| Alternative methods | Simulation is the main method | Formal can prove most properties of a small, control-heavy block ([E-INT-1](/curriculum/T4_Expert/E-INT-1_Integrating_UVM_with_Formal_Verification/index)) |
| Tools | Your simulator supports UVM fully (tool-dependent: check your vendor's documentation) | Your flow lacks full class-based SystemVerilog support (tool-dependent) |

**Three worked decisions.**
1. **A 200-line CRC block**, two engineers, a stable spec, formal available, no reuse planned. Formal for the properties plus a small self-checking class bench for end-to-end data is enough. UVM's structure would cost more than it saves here.
2. **A single-protocol subsystem** (a DMA engine with one bus interface) that the SoC team will reuse. UVM: the bus agent will be reused passively at SoC level, and tests will be selected and combined in regressions.
3. **SoC integration** of a dozen IP blocks, each with an existing UVM agent. UVM without question: the passive agents, scoreboards and register models come from the block teams, and virtual sequences coordinate them ([A-UVM-8](/curriculum/T3_Advanced/A-UVM-8_Multi_Agent_Topologies/index)).

Two misconceptions to retire: "every bench needs UVM" (scenario 1 does not) and "UVM is chosen for simulation speed" (it is chosen for reuse and consistency, at some run-time cost).

### Recap

- A layered class bench gives each job its own class: transaction, generator, driver, monitor, scoreboard, coverage, environment, test, connected by mailboxes and a virtual interface with clocking blocks.
- It strains at scale in six places: hard-coded construction, constructor-chain configuration, hand-ordered phases and end of test, point-to-point consumers, welded-in stimulus, and a home-made verdict. Together they force copy-paste reuse.
- Six UVM mechanisms remove them, each with its own new failure mode: the factory, the configuration database, phasing with objections, TLM analysis ports, sequences on a sequencer, and reporting; the agent packages them for active or passive reuse.
- Each layer has a UVM base class; the sequence and the agent are the two genuinely new shapes.
- UVM is an IEEE 1800.2-2020 API with the uvm-core reference implementation: a SystemVerilog library, not a language, not faster, and not a substitute for your own checks, models and coverage. It is worth its overhead when reuse, team size, VIP and regression scale demand it.

## Make It Work

### The bridge bench: a layered FIFO testbench in plain SystemVerilog

This is the bench every picture above is drawn from, and the **bridge capstone** of the SystemVerilog half of the tier. It is race-free (clocking blocks), self-checking (a reference queue in the scoreboard), measures coverage, and binds assertions to the DUT. Read it once as a whole, then find each of the six limits in it.

The five design units are in one listing, separated by file comments. Compile them in the order shown: the interface must be known before the package that declares `virtual fifo_if`.

```systemverilog
// compile
// ---------------------------------------------------------------- sync_fifo.sv
// DUT: synchronous FIFO, registered read (rd_data is valid one cycle after a
// read is accepted). DEPTH must be a power of two.
module sync_fifo #(parameter int WIDTH = 8, parameter int DEPTH = 8) (
  input  logic             clk,
  input  logic             rst_n,
  input  logic             wr_en,
  input  logic [WIDTH-1:0] wr_data,
  input  logic             rd_en,
  output logic [WIDTH-1:0] rd_data,
  output logic             full,
  output logic             empty
);
  localparam int AW = $clog2(DEPTH);
  logic [WIDTH-1:0] mem [DEPTH];
  logic [AW:0]      wptr, rptr;     // the extra bit tells full from empty

  assign full  = (wptr[AW] != rptr[AW]) && (wptr[AW-1:0] == rptr[AW-1:0]);
  assign empty = (wptr == rptr);

  always_ff @(posedge clk or negedge rst_n) begin
    if (!rst_n) begin
      wptr    <= '0;
      rptr    <= '0;
      rd_data <= '0;
    end else begin
      if (wr_en && !full) begin
        mem[wptr[AW-1:0]] <= wr_data;
        wptr              <= wptr + 1'b1;
      end
      if (rd_en && !empty) begin
        rd_data <= mem[rptr[AW-1:0]];
        rptr    <= rptr + 1'b1;
      end
    end
  end
endmodule

// ------------------------------------------------------------------ fifo_if.sv
interface fifo_if (input logic clk);
  logic       rst_n;
  logic       wr_en, rd_en;
  logic [7:0] wr_data, rd_data;
  logic       full, empty;

  // Driver view: drives land in Re-NBA, after the DUT's flops sampled the edge.
  clocking drv_cb @(posedge clk);
    output wr_en, wr_data, rd_en;
  endclocking

  // Monitor view: every input is the value from just before the edge (1step).
  clocking mon_cb @(posedge clk);
    input rst_n, wr_en, wr_data, rd_en, rd_data, full, empty;
  endclocking
endinterface

// ----------------------------------------------------------------- fifo_sva.sv
// Flag assertions, kept out of the design file and bound in from tb_top.
module fifo_sva (input logic clk, rst_n, wr_en, rd_en, full, empty);
  a_not_full_and_empty: assert property (
    @(posedge clk) disable iff (!rst_n) !(full && empty))
    else $error("SVA a_not_full_and_empty failed");
  a_write_fills: assert property (
    @(posedge clk) disable iff (!rst_n) (wr_en && !rd_en && empty) |=> !empty)
    else $error("SVA a_write_fills failed");
  a_read_frees: assert property (
    @(posedge clk) disable iff (!rst_n) (rd_en && !wr_en && full) |=> !full)
    else $error("SVA a_read_frees failed");
endmodule

// ------------------------------------------------------------- fifo_tb_pkg.sv
package fifo_tb_pkg;

  typedef enum bit {WRITE, READ} fifo_op_e;

  // Transaction: one requested operation, or one observed transfer.
  class fifo_txn;
    rand fifo_op_e op;
    rand bit [7:0] data;
    bit            accepted;   // monitor only: 0 if the DUT ignored the request

    constraint c_op   { op dist {WRITE := 1, READ := 1}; }
    constraint c_data { data dist {8'h00 := 1, 8'hFF := 1, [8'h01:8'hFE] :/ 8}; }

    function fifo_txn copy();
      fifo_txn c = new();
      c.op       = op;
      c.data     = data;
      c.accepted = accepted;
      return c;
    endfunction

    function string convert2string();
      return $sformatf("%s data=%02h accepted=%0b", op.name(), data, accepted);
    endfunction
  endclass

  // Generator: n_random random items, then DEPTH reads to drain the FIFO.
  class fifo_gen;
    mailbox #(fifo_txn) gen2drv;
    int unsigned        n_random, n_total;

    function new(mailbox #(fifo_txn) gen2drv, int unsigned n_random,
                 int unsigned depth);
      this.gen2drv  = gen2drv;
      this.n_random = n_random;
      n_total       = n_random + depth;
    endfunction

    task run();
      fifo_txn t;
      for (int unsigned i = 0; i < n_total; i++) begin
        t = new();                // a new object for every item
        if (i < n_random) begin
          if (!t.randomize()) $fatal(1, "fifo_gen: randomize failed");
        end else begin
          if (!t.randomize() with { op == READ; })
            $fatal(1, "fifo_gen: randomize failed");
        end
        gen2drv.put(t);           // bound 1: blocks until the driver takes the last one
      end
    endtask
  endclass

  // Driver: one item per clock; idle while in reset or when nothing is ready.
  class fifo_drv;
    virtual fifo_if     vif;
    mailbox #(fifo_txn) gen2drv;

    function new(virtual fifo_if vif, mailbox #(fifo_txn) gen2drv);
      this.vif     = vif;
      this.gen2drv = gen2drv;
    endfunction

    task run();
      fifo_txn t;
      forever begin
        @(vif.drv_cb);
        if (vif.rst_n === 1'b1 && gen2drv.try_get(t) > 0) begin
          vif.drv_cb.wr_en   <= (t.op == WRITE);
          vif.drv_cb.rd_en   <= (t.op == READ);
          vif.drv_cb.wr_data <= t.data;
        end else begin
          vif.drv_cb.wr_en <= 1'b0;
          vif.drv_cb.rd_en <= 1'b0;
        end
      end
    endtask
  endclass

  // Monitor: one transaction per requested operation, accepted or not.
  class fifo_mon;
    virtual fifo_if     vif;
    mailbox #(fifo_txn) mon2sb, mon2cov;   // one mailbox per consumer

    function new(virtual fifo_if vif, mailbox #(fifo_txn) mon2sb,
                 mailbox #(fifo_txn) mon2cov);
      this.vif     = vif;
      this.mon2sb  = mon2sb;
      this.mon2cov = mon2cov;
    endfunction

    task run();
      bit rd_pending;
      forever begin
        @(vif.mon_cb);
        if (vif.mon_cb.rst_n !== 1'b1) begin
          rd_pending = 1'b0;
          continue;
        end
        // A read accepted at the previous edge: rd_data now holds its value.
        if (rd_pending) publish(READ, vif.mon_cb.rd_data, 1'b1);
        rd_pending = 1'b0;
        // What the DUT saw at this edge: the same pre-edge values its flops used.
        if (vif.mon_cb.wr_en) publish(WRITE, vif.mon_cb.wr_data, !vif.mon_cb.full);
        if (vif.mon_cb.rd_en) begin
          if (vif.mon_cb.empty) publish(READ, 8'h00, 1'b0);
          else rd_pending = 1'b1;
        end
      end
    endtask

    function void publish(fifo_op_e op, bit [7:0] data, bit accepted);
      fifo_txn t = new();               // a new object per observation
      t.op       = op;
      t.data     = data;
      t.accepted = accepted;
      void'(mon2sb.try_put(t));         // unbounded mailboxes are never full
      void'(mon2cov.try_put(t.copy())); // each consumer owns its object
    endfunction
  endclass

  // Scoreboard: a queue is the reference model of the FIFO.
  class fifo_sb;
    mailbox #(fifo_txn) mon2sb;
    int unsigned        depth;
    bit [7:0]           model[$];
    int unsigned        n_seen, matches, mismatches;

    function new(mailbox #(fifo_txn) mon2sb, int unsigned depth);
      this.mon2sb = mon2sb;
      this.depth  = depth;
    endfunction

    task run(int unsigned expected);   // returns after `expected` observations
      fifo_txn t;
      repeat (expected) begin
        mon2sb.get(t);
        n_seen++;
        check(t);
      end
    endtask

    function void check(fifo_txn t);
      bit [7:0] exp;
      bit       ok;
      if (t.op == WRITE) begin
        ok = (t.accepted == (model.size() < depth));  // accepted exactly when not full
        if (ok && t.accepted) model.push_back(t.data);
      end else if (!t.accepted) begin
        ok = (model.size() == 0);                     // rejected exactly when empty
      end else if (model.size() == 0) begin
        ok = 1'b0;                                    // data from an empty FIFO
      end else begin
        exp = model.pop_front();
        ok  = (t.data == exp);
      end
      if (ok) matches++;
      else begin
        mismatches++;
        $error("SCB mismatch: %s (expected %02h, model size %0d)",
               t.convert2string(), exp, model.size());
      end
    endfunction
  endclass

  // Coverage: what the DUT really did, including writes when full and reads when empty.
  class fifo_cov;
    mailbox #(fifo_txn) mon2cov;
    fifo_txn            t;

    covergroup cg;
      cp_op:    coverpoint t.op;
      cp_acc:   coverpoint t.accepted;
      x_op_acc: cross cp_op, cp_acc;
      cp_data:  coverpoint t.data iff (t.op == WRITE && t.accepted) {
        bins zero = {8'h00};
        bins mid  = {[8'h01:8'hFE]};
        bins max  = {8'hFF};
      }
    endgroup

    function new(mailbox #(fifo_txn) mon2cov);
      this.mon2cov = mon2cov;
      cg = new();
    endfunction

    task run();
      forever begin
        mon2cov.get(t);
        cg.sample();
      end
    endtask
  endclass

  // Environment: builds, connects and starts every layer, and decides the end.
  class fifo_env;
    virtual fifo_if     vif;
    mailbox #(fifo_txn) gen2drv, mon2sb, mon2cov;
    fifo_gen            gen;
    fifo_drv            drv;
    fifo_mon            mon;
    fifo_sb             sb;
    fifo_cov            cov;
    bit                 timed_out;

    function new(virtual fifo_if vif, int unsigned depth, int unsigned n);
      this.vif = vif;
      gen2drv  = new(1);              // bounded: the generator runs one item ahead
      mon2sb   = new();
      mon2cov  = new();
      gen = new(gen2drv, n, depth);   // every concrete class is named here
      drv = new(vif, gen2drv);
      mon = new(vif, mon2sb, mon2cov);
      sb  = new(mon2sb, depth);
      cov = new(mon2cov);
    endfunction

    task run();
      fork                            // start every layer
        gen.run();
        drv.run();
        mon.run();
        cov.run();
      join_none
      fork                            // end of test, decided by hand
        sb.run(gen.n_total);
        begin
          repeat (4 * gen.n_total + 100) @(vif.mon_cb);
          timed_out = 1'b1;
          $error("TIMEOUT: scoreboard saw %0d of %0d items", sb.n_seen, gen.n_total);
        end
      join_any
      repeat (2) @(vif.mon_cb);       // let fifo_cov sample the last item
      disable fork;                   // stop the forever loops and the watchdog
    endtask

    function void report();
      $display("SCB_SUMMARY matches=%0d mismatches=%0d pending=%0d",
               sb.matches, sb.mismatches, sb.model.size());
      $display("COVERAGE fifo_cov.cg = %0.1f%%", cov.cg.get_coverage());
    endfunction
  endclass

  // Test: reads the knob, builds the env, prints the verdict.
  class fifo_test;
    fifo_env     env;
    int unsigned n;

    function new(virtual fifo_if vif, int unsigned depth);
      if (!$value$plusargs("N=%d", n)) n = 1000;
      env = new(vif, depth, n);
    endfunction

    task run();
      int unsigned fails;
      env.run();
      env.report();
      fails = env.sb.mismatches + env.sb.model.size() + env.timed_out;
      $display("PASS=%0d FAIL=%0d", env.sb.matches, fails);
    endtask
  endclass

endpackage
```

### Debug challenge: three mutants

Each mutant is a small edit to the bench above. Predict the symptom in the log before you open the answer.

**Mutant 1.** In `fifo_mon::publish`, the monitor allocates one object in its constructor and reuses it: `t.op = op; t.data = data; …` with no `new`.

<details>
<summary>Symptom, cause and fix</summary>

**Symptom:** the first mismatch appears at an edge where a read completes and a new write arrives together (a READ followed immediately by a WRITE). From then on reads keep mismatching, and `pending` is not 0 at the end. **Cause:** at that edge `publish` runs twice before the scoreboard's thread resumes. Both mailbox entries hold the same handle, so the scoreboard sees the WRITE twice and never sees the READ: the model gains an extra entry, skips a pop, and is off by one from then on. **Fix:** `fifo_txn t = new();` in every call, as in the listing. The same rule applies to UVM monitors, which create a new item before every `ap.write`.
</details>

**Mutant 2.** The monitor ignores the read latency: `if (vif.mon_cb.rd_en && !vif.mon_cb.empty) publish(READ, vif.mon_cb.rd_data, 1'b1);` at the edge where it sees `rd_en`.

<details>
<summary>Symptom, cause and fix</summary>

**Symptom:** almost every accepted read mismatches, and the reported data is always the *previous* read's value (or `00` for the first read after reset). **Cause:** `rd_data` is a flop that updates at the edge that accepts the read; `mon_cb` samples the value from just before that edge (§14.13), which is the previous read's data. **Fix:** remember the accepted read and capture `rd_data` one edge later, as `rd_pending` does. A clocking block removes races, not the DUT's latency: the monitor must model the protocol's timing.
</details>

**Mutant 3.** `fifo_env::run` ends the test when the generator returns: `sb.run(gen.n_total)` moves into the `join_none` group, and `gen.run()` takes its place in the `join_any`.

<details>
<summary>Symptom, cause and fix</summary>

**Symptom:** `SCB_SUMMARY` shows `mismatches=0` but `matches` a little below 1008. If the unchecked items were reads that would have emptied the model, `pending` is not 0 and the verdict is `FAIL`; if not, the bench prints `FAIL=0` after checking fewer items than it sent, a **false pass**. **Cause:** `gen.run()` returns as soon as its last `put` succeeds, which is before the driver drives the last item and before the last read data appears; the two extra clocks are not always enough. **Fix:** end when the scoreboard has seen every item, with a watchdog, and make the verdict also check that the scoreboard saw as many items as were sent. In UVM this is the objection raised by the test around the sequence, plus the scoreboard's own checks in `check_phase` ([I-UVM-1C](/curriculum/T2_Intermediate/I-UVM-1C_UVM_Phasing/index)).
</details>

## Push Further

### Expert: the standard and the implementation

IEEE 1800.2-2020 defines an API, not source code. Several of its rules matter in practice:
- **Inheritance is not exact.** "Class declarations shown in this document … do not imply class A and class B are adjacent in the inheritance tree; implementations are free to have other classes between A and B" (§1.4.3). uvm-core, for example, inserts `uvm_sequencer_param_base` between `uvm_sequencer_base` and `uvm_sequencer`. Code that depends on such an intermediate class is not portable.
- **Order is not guaranteed.** "An implementation … may choose any operation order or sorting order for 'equivalent data' objects", so output "may differ between implementations" (§1.4.4). Do not write checks that depend on the order in which equivalent components or settings are visited.
- **Random stability is limited.** APIs that run user code "are not guaranteed to be random stable" (§1.4.6).
- **uvm-core adds features the standard does not define.** Examples (uvm-core impl.): the plusargs `+UVM_TIMEOUT`, `+UVM_OBJECTION_TRACE`, `+UVM_PHASE_TRACE` and `+UVM_CONFIG_DB_TRACE`; `uvm_root::set_enable_print_topology`; and the methods `check_config_usage` and `print_config`. Annex G.2 lists the plusargs the standard does define, such as `+UVM_TESTNAME` and `+UVM_VERBOSITY`.
- **uvm-core keeps compatibility shims**, marked `@uvm-compat` in its source: the global `uvm_top` ("Provided for compatibility with 1.2", `uvm_root.svh`) and the OVM-style `build()`, `connect()` and `run()` methods (`uvm_component.svh`, where `uvm_component::build_phase` simply calls `build()`). The standard spells the root `uvm_root::get()`.
- **uvm-core deliberately diverges in one default.** Its automatic configuration mode defaults to `CONFIG_CHECK_NAMES`, which its source calls "a divergence from 1800.2, however the performance increase is drastic"; compiling with `+define+UVM_COMPONENT_CONFIG_MODE_DEFAULT=CONFIG_STRICT` restores the standard behaviour (`uvm_global_defines.svh`).

*Practical rule:* write to the standard, and label every uvm-core-only feature you use, so the bench survives a different implementation or a newer uvm-core release.

### Expert: what UVM costs and how to measure it

UVM's benefits are paid for in simulation time and memory, and the costs scale with how you use it:
- **Objects and phases.** Every component is an object in a hierarchy, and every phase visits every component.
- **Factory and configuration lookups.** `create` consults the override tables; `uvm_config_db::get` searches the resource pool. uvm-core's own default above exists because automatic configuration was expensive enough to change the standard behaviour.
- **Field automation.** The standard itself warns that the `uvm_field_*` macros "may not be as run-time efficient nor as flexible as direct implementations of the do_* methods" (Annex B.2.2 NOTE).
- **Messages.** The report macros check the verbosity and action "before any string formatting is performed" (Annex B.1), so a filtered `` `uvm_info `` is cheap. Formatting done outside the macros, such as a `$sformatf` stored in a variable first or a plain `$display`, is paid on every call, and hot loops make that visible.
- **Transaction traffic.** A new object per item, analysis fan-out and recording all allocate memory.

This page gives no speed figures on purpose: they depend on the simulator, the bench and the switches. Measure with your simulator's profiler before and after a change (tool-dependent), and see [E-PERF-1](/curriculum/T4_Expert/E-PERF-1_UVM_Performance/index) for the techniques.

### Expert: choosing a methodology for a block, a subsystem or an SoC

The decision is rarely "UVM or nothing" for a whole chip; it is made per level and per block.
- **Block level.** Small control blocks are often better served by formal plus a light bench ([E-INT-1](/curriculum/T4_Expert/E-INT-1_Integrating_UVM_with_Formal_Verification/index)). Datapath-heavy or protocol blocks benefit from UVM because their agents are reused later.
- **Subsystem and SoC.** UVM's value peaks here: passive agents from block benches, register models, virtual sequences, and VIP that is commonly delivered as UVM agents ([A-UVM-7](/curriculum/T3_Advanced/A-UVM-7_VIP_Construction/index)).
- **Emulation and acceleration.** Testbench code that must run with an emulator needs synthesizable transactors and a split between the timed and untimed sides ([E-EMU-1](/curriculum/T4_Expert/E-EMU-1_Emulation_Aware_Verification/index)); a UVM bench needs restructuring for it.
- **Python and multi-language flows.** Teams also build benches in Python (cocotb, pyuvm) or mix languages ([E-PYUVM-1](/curriculum/T4_Expert/E-PYUVM-1_Python_Based_Verification/index), [E-UVM-ML-1](/curriculum/T4_Expert/E-UVM-ML-1_Multi_Language_Verification/index)). Simulator and open-source tool support for full UVM varies: tool-dependent, so check it before committing.

A staff-level answer names the reuse plan, the people and the tools before it names a library.

### Expert: migrating a legacy bench to UVM

A mature hand-built bench is rarely rewritten in one step. Migrate layer by layer, keeping the bench green after each step:
1. **Keep what is already right:** the transaction (extend `uvm_sequence_item` and add a constructor `new(string name = "fifo_item")`), the reference model inside the scoreboard, the covergroups, the interface and its clocking blocks, and the bound assertions.
2. **Wrap, then replace, the plumbing:** the generator becomes a sequence; the generator-to-driver mailbox becomes `seq_item_port` and a sequencer; monitor mailboxes become one analysis port; the vif moves to the configuration database; the counting end of test becomes an objection in the test.
3. **Route every error through the report server**, including assertion action blocks, so the summary is the single verdict.
4. **Check the deprecation list.** Annex H lists constructs that have been deprecated from UVM or are under consideration for deprecation; uvm-core's `@uvm-compat` shims help old code compile but are not part of the standard.

Old UVM 1.2 or OVM code follows the same path: compile it against uvm-core, then remove its reliance on `@uvm-compat` features one at a time.

### Kata: predict the cost of a change request

For each change request, list the classes you would edit in the Make It Work bench, then name the UVM mechanism that would avoid most of those edits. Write your answers before opening the solution.

1. Swap in a driver that drops every tenth write.
2. Add a second coverage collector for a new metric.
3. Reuse the monitor, scoreboard and coverage at SoC level, where RTL drives the FIFO.
4. Set the number of items from the command line.
5. End the test exactly when the scoreboard has checked everything, in a bench that has two environments.
6. Make the log quiet except for errors.

<details>
<summary>Worked solution</summary>

| # | Hand-built: classes edited | UVM mechanism | UVM: what changes |
|---|---|---|---|
| 1 | New `fifo_drv` subclass; `fifo_env` (the `new` line or a knob); `fifo_test` | Factory | New subclass plus one `set_type_override` in a new test |
| 2 | `fifo_mon` (third mailbox, constructor, `publish`); `fifo_env` | TLM analysis port | New subscriber built in the env and one `connect` line; monitor untouched |
| 3 | A copy of `fifo_env` without `gen` and `drv`, or knobs through `fifo_env` and `fifo_test` | Agent with `is_active` from the configuration database | One configuration setting; the agent and env classes are unchanged |
| 4 | Nothing: `n` is already a `+N=` knob, but it is threaded through two constructors | Configuration database | The test reads it once and sets it; or `+uvm_set_config_int` (Annex G.2.8) |
| 5 | Both envs' `run` tasks and the test, to agree on who decides the end | Phasing with objections | Each top sequence or test raises and drops; the run phase ends when all are dropped |
| 6 | Every `$display` call | Reporting | `+UVM_VERBOSITY=UVM_LOW` or a verbosity setting; no code edits |

Item 4 is the honest exception: a well-written hand-built bench can already take command-line knobs. What it cannot do without edits is deliver them to a component deep in the hierarchy.
</details>

### Kata: the bridge capstone

Build the Make It Work bench yourself, from an empty file, on your simulator. **Acceptance:** zero mismatches over at least 1,000 random items, `pending=0`, coverage of at least 90%, the three bound assertions passing, and `PASS=<n> FAIL=0`. Then:
1. Inject each of the three mutants and confirm the symptom you predicted.
2. Make one change the bench cannot express cleanly (for example, the driver that drops every tenth write in one test only) and record every file you had to edit. Keep that list: you will redo the same change with a factory override in [I-UVM-1B](/curriculum/T2_Intermediate/I-UVM-1B_The_UVM_Factory/index).

<details>
<summary>Self-check list for the capstone</summary>

- The interface has two clocking blocks, and no class touches a DUT input outside `drv_cb`.
- The generator and the monitor call `new` for every item.
- The monitor captures read data one edge after the accepted `rd_en`.
- The scoreboard checks rejected writes and reads too, so a broken `full` or `empty` flag is caught.
- The end of test waits for the scoreboard, with a watchdog that reports a timeout.
- The verdict counts mismatches, pending items and the timeout. Note that it still cannot see `fifo_sva`'s `$error`: that is limit 6.
</details>
