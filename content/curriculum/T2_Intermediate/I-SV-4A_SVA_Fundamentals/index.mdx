## Quick Take
- **What it is:** SystemVerilog Assertions (SVA) describe how signals must behave over clock cycles. A simulator or a formal tool checks the description on every cycle and flags violations.
- **Why it matters:** Assertions catch protocol bugs on the cycle they happen, shrink debug time, and document the contract between blocks.
- **The rule you will use every day:** a concurrent assertion starts a new **attempt** at every tick of its clock (§16.14.5). Each attempt reads values **sampled just before the edge** (§16.5.1) and ends as a pass, a fail, a vacuous success, or a disabled attempt.
- **The Analogy:** Think of SVA as highway patrol. Sequences spot patterns like "car stops at red"; properties turn them into laws; an `assert` issues a ticket when a driver misbehaves; a `cover` proves the patrol ever saw a car.

> **Retention Hook:** "Sequence = pattern, Property = rule, Assert = enforce, Cover = evidence."
> *SystemVerilog Assertions are formally defined in **IEEE 1800-2023, Clause 16**.*

## Build Your Mental Model
### Traffic Rules for Signals
How do you guarantee that an `ack` follows a `req` within three cycles? Assertions turn such timing rules into executable checks. Immediate assertions are quick checkpoints inside procedural code; concurrent assertions sit beside the design and check every clock tick.

### Immediate vs. Concurrent Assertions
Immediate assertions execute once, exactly where they are written, on the current values. Concurrent assertions are evaluated at each tick of their clock, in the Observed region, on sampled values (§16.5). Use concurrent assertions for protocol rules.

### Assertions read the past
At each clock edge, a concurrent assertion uses the value every signal had **just before** the edge: its Preponed sample (§16.5.1). A flop output that changes on edge 2 is still 0 when the assertion samples it at edge 2, and is first seen as 1 at edge 3. This is the same time-slot ladder you met in [F3C](/curriculum/T1_Foundational/F3C_Delta_Cycles_and_Race_Conditions/index): the assertion samples in Preponed, evaluates in Observed, and runs its action block in Reactive. Because it never reads values written on the same edge, it is immune to the Active-region races from that lesson.

### From sequence to assertion
A `sequence` names a pattern, a `property` turns it into a rule with a clock, and `assert` or `cover` puts the rule to work. Note which statement covers what: the cover statement watches the *sequence*, not the implication.

<InteractiveCode>
```systemverilog
// Sequence: the pattern (req, then ack on the next tick)
sequence s_req_then_ack;
  req ##1 ack;
endsequence

// Property: the rule. Only attempts that see req are checked.
property p_req_implies_ack;
  @(posedge clk) disable iff (!rst_n)
    req |-> s_req_then_ack;   // equivalent to: req |=> ack
endproperty

a_req_ack: assert property (p_req_implies_ack)
  else $error("Request not acknowledged in one cycle");

// Coverage evidence: cover the sequence itself, not the implication
c_req_ack: cover property (@(posedge clk) disable iff (!rst_n) s_req_then_ack);
```
</InteractiveCode>

### Temporal Operators at a Glance
- `##1` delays by exactly one tick; `##[1:3]` accepts any delay from one to three ticks; `##[1:$]` has no upper bound.
- `|->` (overlapping implication) starts the consequent on the edge where the antecedent matched. `|=>` (non-overlapping) starts it on the next edge. `a |=> b` means the same as `a |-> ##1 b` (§16.12.7).
- Repetition (`[*N]`, `[->N]`, `[=N]`) and the conditions `throughout` and `within` are covered in [I-SV-4B](/curriculum/T2_Intermediate/I-SV-4B_Advanced_Temporal_Logic/index).

### Every edge starts an attempt
Each attempt is evaluated on its own, and each one ends in one of five ways:

| Result | When | What the tool does |
|---|---|---|
| Pass ✓ | The property held from this start edge | Runs the pass action, counts a real success |
| Fail ✕ | A finite prefix proved it cannot hold | Runs the fail action (`$error` by default) |
| Vacuous success ○ | An implication whose antecedent did not match | Not considered a pass or a failure (§16.14.8) |
| Pending … | Still running when the simulation stops | In `assert property` a sequence is weak, so this is not a failure (§16.12.2) |
| Disabled ⊘ | `disable iff` was true while the attempt was in flight | Neither pass nor fail; no action block runs (§16.12, §16.14.1) |

The most common beginner bug follows directly from this table. A property that is just a sequence, such as `req ##2 ack`, has no antecedent, so every attempt must match `req` at its own start edge. It **fails on every idle edge** where `req` is 0. It is never vacuous (§16.14.8 a). Write `req |-> ##2 ack` when the check should start only after a request.

### Sampled-value functions
These functions compare **sampled** values at consecutive ticks of the assertion clock (§16.9.3):

| Function | True when |
|---|---|
| `$rose(e)` | the LSB of `e` changed to 1 since the previous tick |
| `$fell(e)` | the LSB of `e` changed to 0 since the previous tick |
| `$stable(e)` | `e` did not change since the previous tick |
| `$changed(e)` | `e` changed since the previous tick |
| `$past(e, N)` | returns `e` as sampled N ticks earlier (N defaults to 1 and must be at least 1) |
| `$sampled(e)` | returns the sampled value of `e` (redundant inside an assertion) |

Two corner cases matter in real benches:
- **The first tick.** At or before the first clock tick there is no previous sample, so these functions compare against the *default sampled value*: X for a `logic` signal (§16.5.1, §16.9.3). A `req` that starts at 1 therefore gives `$rose(req)` true at the first tick, and an active-low `rst_n` that starts at 0 gives `$fell(rst_n)` true there.
- **Too few ticks for `$past`.** If fewer than N ticks have happened, `$past(e, N)` returns the default sampled value (§16.9.3), X for `logic`. A check like `q == $past(d)` then sees an unknown at the first tick, and an unknown condition counts as false (§16.6). The same function looks straight back into the reset period on the first edge after reset. Guard it with `!$past(rst) |-> ...` (the lab's third debug case).

### Vacuity
An implication `a |-> b` whose antecedent `a` does not match succeeds **vacuously**: nothing about `b` was checked. The standard calls it a success, but says an assertion with a vacuous success "is not considered a pass or a failure" (§16.14.8). A sequence used as a property is never vacuous (§16.14.8 a).

Vacuity hides bugs. An antecedent with the wrong polarity, or one that the stimulus never produces, makes an assertion that can never fail. Three habits catch this:
- Read the vacuous count in the assertion report, not just the failure count.
- Cover the trigger: `cover property (@(posedge clk) req && rst_n);` stays at zero if the antecedent never happens.
- Cover sequences, not implications. For `cover property`, tools report attempts, successes and vacuous successes separately (§16.14.3), and an implication can be "covered" without its trigger ever firing.

### disable iff
`disable iff (expr)` attaches a reset condition to a property (§16.12):
- If the condition is true at any time between the start of an attempt and its end, that attempt is **disabled**. It reports neither a pass nor a failure, and its action block does not run (§16.14.1). Attempts that start while the condition is true are disabled too.
- The condition uses **current** values, not sampled values (§16.12), so an asynchronous reset aborts attempts in flight as soon as it changes. Write `disable iff ($sampled(rst))` if you want the sampled value (§16.9.3).
- A sampled-value function such as `$past` inside the condition needs an explicit clocking event, and `disable iff` cannot be nested (§16.12).
- `default disable iff !rst_n;` in a module, interface or program applies one condition to every concurrent assertion in that scope (§16.15).

### assume and cover
The same property can be used three ways (§16.2):
- `assert property (p)` states an obligation on the design. A failure is reported.
- `assume property (p)` states an assumption about the environment. Formal tools use it to constrain inputs; simulators check it and report a failure like an assertion (§16.14.2). Put protocol rules for DUT *inputs* here.
- `cover property (p)` and `cover sequence (s)` collect evidence that a behavior happened. `cover property` counts at most one success per attempt; `cover sequence` counts every match (§16.14.3).

## Make It Work
1. **Identify intent:** Translate protocol rules or handshake timing into short English statements ("after a request, ack within three cycles").
2. **Name the trigger:** The condition that starts the check becomes the antecedent. Never assert a bare sequence for a conditional rule.
3. **Pick the timing:** Use `|->` when the consequent starts on the trigger's edge and `|=>` when it starts on the next edge.
4. **Handle reset:** Add `disable iff (!rst_n)` (or a `default disable iff`), and guard `$past` after reset.
5. **Prove it can fire:** Add a `cover` on the antecedent or on the full sequence, and check the vacuous count.
6. **Enforce and observe:** Place the assertion in an interface, a bind file, or a checker so the DUT source stays untouched.

**Checklist before moving on:**
- [ ] You can predict, for any edge, whether an attempt passes, fails, is vacuous, pending or disabled.
- [ ] You can explain why `req ##2 ack` fails on idle cycles and `req |-> ##2 ack` does not.
- [ ] You can choose `|->` or `|=>` to express timing intent.
- [ ] You can explain why `$rose` fires one edge after a flop output changes.

## Push Further
- **Coverage evidence:** Pair every important assertion with a `cover` of its trigger or of the full sequence. A green assertion with zero real passes is a hole, not a success.
- **Formal verification:** The same SVA feeds formal tools. They try to prove that a property can never fail, using `assume` properties as constraints on the inputs.
- **Reusable checkers:** Named sequences and properties can be declared in packages (§16.12). The `assert property` statements themselves go in modules, interfaces, programs, generate blocks, checkers or procedures (§16.14). Bind them to the DUT so its source stays untouched (I-SV-4C).
- **Memory trick:** Sequence = pattern, Property = rule, Assert = enforce, Assume = constrain, Cover = evidence.
