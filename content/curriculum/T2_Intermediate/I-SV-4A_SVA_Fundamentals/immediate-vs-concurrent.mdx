## Quick Take

- **What it is:** An **assertion** is a statement that checks a condition your design under test (DUT) or testbench (TB) must meet and reports when it does not. SystemVerilog has two families (IEEE 1800-2023 §16.2). An **immediate assertion** is a procedural statement: it checks its condition on the values variables hold at the moment the statement runs (§16.3). It comes in two modes. A **simple immediate assertion** reports at once; a **deferred immediate assertion** (`assert #0` or `assert final`) checks at once but holds its report until later in the same time slot (§16.4). A **concurrent assertion** checks a **property**, a rule about how signals behave over clock ticks, at each tick of a clock, using values sampled just before the tick (§16.5).
- **Why it matters:** The kinds differ in three things: when they check, which values they read, and when they report. Pick the wrong one and you get false failures from values that are still settling, error messages that print values the check never used, or a check that cannot say "within three cycles" at all. Every real bench mixes all of them, so you need to know which one each check calls for.
- **The Analogy:** Three ways to inspect a shelf that a clerk is restocking. The simple immediate inspector glances at the shelf and writes a ticket on the spot, even if the clerk is halfway through. The deferred inspector writes the ticket in pencil and files it only if the shelf still looks wrong when the clerk steps back; every new glance erases the pencil note. The concurrent inspector is a camera that photographs the shelf just before each scheduled bell and judges only the photos. *Where it breaks:* the deferred inspector waits only until the end of the current time slot, never across clock cycles, and "the clerk steps back" is a precise scheduling region (Observed or Postponed), not a judgment call. The camera also misses anything that happens and is undone between two bells.

**You will be able to:**
1. Choose between a simple immediate, an observed deferred (`assert #0`), a final deferred (`assert final`) and a concurrent assertion for a given check, and justify the choice.
2. Predict, for a procedure that runs more than once in one time slot, how many reports each kind prints and in which scheduling region each report is printed.
3. Write legal action blocks for each kind with severity tasks (`$fatal`, `$error`, `$warning`, `$info`), and place deferred assertions in procedures or at module level.
4. Debug a false, missing or misleading assertion report by tracing it to its cause: a glitch, an unknown (X) value, a Reactive-region change, or an action block that reads current values.

## Build Your Mental Model

**How to read this lesson.** The core path is the first six sections: the three questions, the region refresher, simple immediate assertions, the glitch, deferred assertions and concurrent assertions. Then come the ladder picture that puts them side by side, action blocks, choosing a kind and debugging. The [module overview](/curriculum/T2_Intermediate/I-SV-4A_SVA_Fundamentals/index) teaches the temporal side of concurrent assertions (sequences, `|->` and `|=>`, vacuity, `disable iff`, `assume` and `cover`); this lesson does not repeat it.

A few words you will meet on every line. A **procedure** is a block of procedural code such as an `initial`, `always`, `always_comb` or `always_ff` block ([F2C](/curriculum/T1_Foundational/F2C_Procedural_Code_and_Flow_Control/index)). A **process** is one running thread of a procedure; each procedure is one process. A **time slot** is everything the simulator does at one simulation time, and it is split into ordered **regions** such as Preponed, Active, Observed, Reactive and Postponed ([F3B](/curriculum/T1_Foundational/F3B_Scheduling_Regions/index)). An **action block** is the code an assertion runs when it passes (the **pass statement**) or fails (the **fail statement**, written after `else`).

### Three questions decide the kind

Every assertion answers three questions differently: **when does it check, which values does it read, and when does it report?**

| Kind | Syntax | Checks when | Reads which values | Reports (runs its action block) |
|---|---|---|---|---|
| Simple immediate | `assert (expr)` | Each time procedural code reaches it | Current values, at that moment | At once, in the same region (§16.3) |
| Observed deferred | `assert #0 (expr)` | Each time procedural code reaches it | Current values, at that moment | Later in the same time slot: the report matures in Observed and runs in Reactive, unless the process runs again first (§16.4.1) |
| Final deferred | `assert final (expr)` | Each time procedural code reaches it | Current values, at that moment | At the end of the time slot: matures and runs in Postponed, unless the process runs again first (§16.4.1) |
| Concurrent | `assert property (@(posedge clk) expr)` | At each tick of its clock | **Sampled** values: the values from just before the tick (Preponed, §16.5.1) | Checked in Observed; action block runs in Reactive (§16.5, §16.14.1) |

Deferred assertions are still immediate assertions: they are procedural statements that read current values. Only the *report* is deferred (§16.4). That one difference is what the rest of this lesson unpacks.

### Simple immediate assertions

A **simple immediate assertion** is a test of an expression, performed when the statement is executed in procedural code (§16.3). The expression is read exactly like the condition of an `if`: if it evaluates to `0`, `x` or `z` it is false and the assertion **fails**; otherwise it **passes**. The pass and fail statements run immediately after the check. If you leave out the `else` clause, the tool calls `$error` for you on a failure (§16.3).

There are three forms, all usable wherever a procedural statement is legal: in `initial` and `always` procedures, tasks, functions and class methods (§16.3).

```systemverilog
// snippet
// [label:] assert (expression) [pass_statement] [else fail_statement]
a_aligned:  assert (addr[1:0] == 2'b00) else $error("addr %h not aligned", addr);
// assume: a requirement on the environment; a simulator can check it like an assert
a_legal_op: assume (opcode inside {ADD, SUB}) else $error("illegal opcode");
// cover: counts how often the expression was evaluated and how often it was true
c_full:     cover (fifo_full) $info("FIFO reached full");
```

The **label** (`a_aligned:`) creates a named block around the statement, so the hierarchical name in the message (`%m`) names the assertion, and assertion-control tasks can target it (§16.3, §20.11). Label every assertion you write.

Here is a simple immediate assertion where it belongs: in procedural testbench code, checking a value at one moment. The action block of a simple immediate assertion can be any statement, including a `begin`-`end` block.

```systemverilog
// snippet
class simple_sb;
  int unsigned expected_q[$];

  function void check(int unsigned actual);
    int unsigned exp_val;
    // Guard the pop: an empty queue means the DUT produced an unexpected output
    a_not_empty: assert (expected_q.size() > 0)
      else begin
        $error("unexpected output %0d: nothing was expected", actual);
        return;
      end
    exp_val = expected_q.pop_front();
    a_match: assert (actual == exp_val)
      else $error("mismatch: expected %0d, got %0d", exp_val, actual);
  endfunction
endclass
```

**Mistakes everyone makes with simple immediate assertions:**

- **Forgetting that X is false.** In a clocked procedure, `assert (!(addr[1:0]))` fails on every edge while `addr` is still `x` during reset, because `!(2'bxx)` is `x`, and `x` counts as false (§16.3). Gate the check with the reset (`if (rst_n) assert (...)`), or check `!$isunknown(addr)` first ($isunknown is true when any bit is `x` or `z`, §20.9).
- **Racing with the testbench.** It reads current values, so in an `always @(posedge clk)` it can see a value a testbench wrote with a blocking assignment on the same edge, or not, depending on process order. That is the read-write race from [F3C](/curriculum/T1_Foundational/F3C_Delta_Cycles_and_Race_Conditions/index). Concurrent assertions avoid it by reading sampled values.
- **Hiding work inside the expression.** Never write `assert (item.randomize())`. When assertions are switched off, for example with `$assertoff` or a simulator option, the check is not executed and the randomization silently stops happening. Call `randomize()` in an `if` and report the failure there.
- **Trusting it inside logic that settles.** If the procedure runs several times in one time slot while its inputs settle, a simple immediate assertion reports every transient failure. That is the next section.

### Watch a simple assertion misfire: the glitch

A procedure that waits on its inputs, such as `always @(a or b)` or `always_comb`, runs again every time one of them changes. Inside one time slot the inputs can change one after another, a **delta cycle** apart: one more trip of the scheduler back to the Active region at the same simulation time ([F3C](/curriculum/T1_Foundational/F3C_Delta_Cycles_and_Race_Conditions/index)). In between, the procedure sees a mix of new and old values that the design never intends to hold. A short-lived wrong value like this is a **glitch**.

```systemverilog
// compile
`timescale 1ns/1ps
module tb_top;
  logic a = 1'b0;
  logic b = 1'b0;   // rule: b always equals a

  always @(a or b) begin : chk
    a1: assert (a == b)       else $error("a1 simple: a=%0b b=%0b", a, b);
    a2: assert #0 (a == b)    else $error("a2 observed deferred: a=%0b b=%0b", a, b);
    a3: assert final (a == b) else $error("a3 final deferred: a=%0b b=%0b", a, b);
  end

  initial begin
    #10 a = 1'b1;
    #0  b = 1'b1;   // b follows a one Inactive pass later, same time slot (§4.4.2.3)
    #10 $finish;
  end
endmodule
```

**Predict first.** At 10 ns, how many error lines do `a1`, `a2` and `a3` each print? Write down three numbers before you read the trace.

Here is the time slot at 10 ns, step by step. `a1`, `a2` and `a3` all check the same condition; they differ only in when they report.

| Step | Region | What happens | `a` | `b` | `a1` simple | `a2` `#0` | `a3` `final` |
|---|---|---|---|---|---|---|---|
| 1 | Active | `initial` runs `a = 1'b1`, which wakes `chk`; `initial` reaches `#0` and suspends | 1 | 0 | | | |
| 2 | Active | `chk` resumes from its event control and runs all three checks | 1 | 0 | **fails, prints now** | fail report queued | fail report queued |
| 3 | Inactive, then Active | `initial` resumes and runs `b = 1'b1`, which wakes `chk` again | 1 | 1 | | | |
| 4 | Active | `chk` resumes from its event control: a **flush point**, so both pending reports are thrown away. The checks run again | 1 | 1 | passes | pass queued | pass queued |
| 5 | Observed, Reactive | `a2`'s pending pass matures; it has no pass statement, so nothing prints | 1 | 1 | | done | |
| 6 | Postponed | `a3`'s pending pass matures; nothing prints | 1 | 1 | | | done |

**Debrief.** The answer is 1, 0, 0. Only `a1` prints, at 10 ns, with `a=1 b=0`: a failure on values that existed for one delta cycle. `a2` and `a3` also failed in step 2, but they only *queued* their reports, and the queue was cleared when `chk` ran again in step 4. Most learners guess that the queue is cleared when the procedure suspends; it is cleared when the procedure **resumes** (§16.4.2). That is the whole idea of a deferred assertion.

### Deferred assertions: `assert #0` and `assert final`

A **deferred assertion** evaluates its expression the moment the statement is reached, exactly like a simple one. The difference is in reporting (§16.4, §16.4.1):

1. **Queue, do not report.** Instead of running the action block, the tool places the action-block call (or `$error`, if there is no `else` and the check failed) on a **deferred assertion report queue** that belongs to the current process. The queued call is a **pending report**. Arguments passed by value are evaluated now, so the report keeps the values the check saw.
2. **Flush on re-run.** When the process reaches a **flush point**, its queue is cleared and the pending reports never run. The three flush points are (§16.4.2):
   - the process resumes after waiting on an event control (`@`) or a `wait` statement;
   - an `always_comb` or `always_latch` resumes because one of its inputs changed;
   - the outermost scope of the process is disabled with `disable`.
3. **Mature and report.** A pending report that survives **matures**: it is confirmed and can no longer be flushed.
   - **Observed deferred** (`#0`): matures in the **Observed** region; its call runs in the **Reactive** region.
   - **In the Postponed region** a pending report of an `assert final` (a **final deferred** assertion) matures, and its call runs there too.

The syntax adds `#0` or `final` after the keyword, and works for `assert`, `assume` and `cover` (§16.4):

```systemverilog
// snippet
a_obs: assert #0 (a == b) else $error("a_obs: a=%0b b=%0b", a, b);
a_fin: assert final (a == b) else $error("a_fin: a=%0b b=%0b", a, b);
m_in:  assume #0 (!(rd_en && wr_en));   // no else: $error on failure
c_hit: cover final (hit && !miss);      // counts only settled values
```

**Action-block rules for deferred assertions** (§16.4):

- The pass statement and the fail statement must each be **a single subroutine call**: a task, a task method, a void function, a void function method or a system task such as `$error`. A `begin`-`end` block is not a subroutine call, so it is illegal here.
- Postponed forbids writing any variable or net (§4.4.2.9). An `assert final` action runs in that region, so its subroutine must be legal there (§16.4): it may print, but it must not update a counter or a flag. Use `#0` when the action has to change state.
- Arguments passed by value are evaluated when the check runs. Arguments passed by `ref` or `const ref` read their current values when the report finally runs (Reactive for `#0`, Postponed for `final`).

```systemverilog
// snippet
a_ok1: assert #0 (x) else $error("x low");             // legal: one system-task call
a_ok2: assert #0 (x) else log_fail("a_ok2", x);        // legal: one void-function call
// a_bad1: assert #0 (x) else begin $error("x"); n++; end   // illegal: begin-end
// a_bad2: assert #0 (x) else n++;                          // illegal: not a call
```

**Static deferred assertions.** A deferred assertion may also sit directly in a module, interface or checker, outside any procedure. It is then treated as if it were inside its own `always_comb` (§16.4.3), so it is checked at time zero and whenever an input changes, and glitches are flushed for you. This is the cleanest way to state a combinational rule:

```systemverilog
// snippet
module arb_checks(input logic [3:0] grant);
  // At most one grant at a time. $onehot0 counts only bits that are 1 (§20.9),
  // so an all-X grant passes: add a separate X check if X must be caught.
  a_grant_1hot0: assert #0 ($onehot0(grant))
    else $error("more than one grant: %b", grant);
  a_grant_known: assert #0 (!$isunknown(grant))
    else $error("grant has X or Z bits: %b", grant);
endmodule
```

Two more rules complete the picture. `disable a_obs;` cancels that assertion's pending reports, and disabling the outermost block of the procedure flushes its whole queue (§16.4.4). And a deferred assertion inside a function belongs to whichever process called the function, so two `always_comb` blocks that call the same function keep separate queues (§16.4.5).

**Where deferral stops helping.** Deferral filters glitches caused by the *order* in which procedures run within one pass of the Active region. It does not filter changes made after the report has matured. If code in the Reactive region (a program block, or a clocking-block drive in Re-NBA) changes an input after Observed, an `assert #0` report has already matured and prints. A report of `assert final` is not due until the last region of the time slot, so the re-run flushes it (§16.4.1). Push Further shows the standard's example.

### Concurrent assertions: checked at the clock, on sampled values

A **concurrent assertion** describes behaviour over clock ticks. A **clock tick** is a time slot in which the assertion's clocking event, such as `@(posedge clk)`, occurs (§16.5). Written outside procedural code, in a module, interface or program (§16.14.5) or in a checker (Clause 17), it starts a new **evaluation attempt** at every tick of its leading clock (§16.14.5). That is called a **static concurrent assertion**.

```systemverilog
// snippet
a_conc: assert property (@(posedge clk) a == b)
  else $error("a_conc: sampled a=%0b b=%0b", $sampled(a), $sampled(b));
```

Four rules define how it sees the design:

- **Sampled values.** Each expression uses its **sampled value**: the value in the Preponed region of that time slot, before anything in the slot changed (§16.5.1). A flop output written on this edge is still its old value; the new value is first seen at the next tick. At time 0 the sampled value is the **default sampled value**: a static variable's declaration initializer if it has one, otherwise the type's default, which is `x` for `logic` (§16.5.1).
- **Two exceptions.** The clocking event and a `disable iff` condition use current values, not sampled ones (§16.5). The module overview explains what that means for reset.
- **Regions.** The assertion is evaluated in the Observed region (§16.5), and its pass and fail statements run in the Reactive region (§16.14.1). A disabled attempt runs neither.
- **One clean clock.** The clocking event should change once per time slot; a glitching clock gives undefined behaviour (§16.5).

**Where the clock comes from.** In this lesson every concurrent assertion writes its clock. A clock can also come from the property or sequence it instantiates, from the enclosing procedure, or from a `default clocking` block (§16.16, §14.12); the [module overview](/curriculum/T2_Intermediate/I-SV-4A_SVA_Fundamentals/index) teaches those rules.

**Procedural concurrent assertions.** You can also write `assert property` inside an `always` or `initial` procedure. It is then a **procedural concurrent assertion**: reaching the statement does not check anything; it places a pending instance on the process's **procedural assertion queue**. Pending instances mature in Observed and start an attempt at once if this time slot is a tick of their clock, otherwise at the next tick; the same three flush points clear the queue (§16.14.6, §16.14.6.2). If the procedure has exactly one clean event control such as `@(posedge clk)`, the clock is inferred from it (§16.14.6). Push Further compares this queue with the deferred one; the module overview works through its traps.

**Where concurrent assertions live.** Concurrent assertion expressions cannot reference non-static class members (§16.6), so concurrent assertions live in modules, interfaces, programs and checkers, typically in the interface that an agent's virtual interface points to. Simulators reject `assert property` inside class methods (tool behaviour); a class uses immediate assertions or UVM reporting instead.

**Debrief.** Read the columns left to right and the trade-off appears. Each kind moves its decision later in the time slot, so it sees more settled values. The simple assertion decides in Active, as soon as its procedure runs, and so it sees glitches. `#0` decides in Observed, after the Active region set has settled for that pass, and `final` decides last of all, at the end of the time slot. The concurrent assertion is different in kind: it checks in Observed but on the Preponed photo, so it never sees anything that happened in this slot, glitch or not.

### Action blocks and severity tasks

The action block decides what a pass or a failure *does*. Its full form is `[pass_statement] [else fail_statement]` (§16.3):

- **Pass statement:** runs when the check passes. Usually omitted. For a concurrent assertion it also runs on a vacuous success by default (§20.11; see the module overview for vacuity).
- **Fail statement:** runs when the check fails. If you omit `else`, the tool calls `$error` (§16.3, §16.14.1).
- **What it may contain:** any procedural statement for simple immediate and concurrent assertions (a concurrent action block must not contain another concurrent assertion, §16.14.1); exactly one subroutine call each for deferred assertions (§16.4).

The **severity tasks** report a failure at a chosen severity (§20.10). All four take an optional `$display`-style message, and every message the tool prints includes the file name and line number, the hierarchical scope and the simulation time:

| Task | Meaning | Typical use in an action block |
|---|---|---|
| `$fatal(finish_number, "msg", ...)` | Run-time fatal error; calls `$finish` and ends the simulation. `finish_number` (0, 1 or 2) sets how much diagnostic information `$finish` prints | A broken invariant after which nothing else is trustworthy, such as a corrupted memory model |
| `$error("msg", ...)` | Run-time error; the simulation continues | Every protocol or data rule; it is also the default |
| `$warning("msg", ...)` | Run-time warning | A suspicious but legal condition, such as a long stall |
| `$info("msg", ...)` | Message of no specific severity | Pass statements and coverage notes |

**Print the values the check used.** Each kind sees different values in its action block:

- **Simple immediate:** the action runs at once, so `a` and `b` in the message are the values just checked.
- **Deferred:** arguments passed by value are captured when the check runs, so `$error("a=%0b", a)` prints the checked value even though it runs later. An argument passed by `ref` is read only when the call finally runs, so it can show a value the check never saw.
- **Concurrent:** the action block runs in Reactive with **current** values, which can differ from the sampled values the check used. Print `$sampled(a)` instead of `a` (§16.9.3).

The standard's own example shows the concurrent trap (§16.9.3); the [module overview](/curriculum/T2_Intermediate/I-SV-4A_SVA_Fundamentals/index) traces it as a table. Both assertions below fail at the same edge; only one tells you why.

```systemverilog
// snippet
a1_bad: assert property (@(posedge clk) a == b)
  else $error("a1_bad: a=%0b b=%0b", a, b);                       // current values
a2_ok:  assert property (@(posedge clk) a == b)
  else $error("a2_ok: a=%0b b=%0b", $sampled(a), $sampled(b));    // checked values
```

### Choosing the kind

| You want to check | Use | Why |
|---|---|---|
| A value at one moment in testbench procedural code: a scoreboard compare, a function argument range | Simple immediate (or `` `uvm_error `` in UVM classes) | Runs exactly where the code runs; allowed in class methods; the values are already final when the code reaches it |
| A combinational rule on design signals: one-hot grants, mutually exclusive enables, a decoder output | Static `assert #0` in the module or interface, or `assert #0` inside the `always_comb` | Checks every change but ignores ordering glitches within the Active region |
| The same rule, when Reactive-region code (a program block or clocking-block drives) can also change its inputs in the same time slot | `assert final` | Only the values at the very end of the time slot count; the action may only print |
| A rule tied to clock edges or spanning cycles: a handshake, a latency bound, data stable while stalled | Concurrent `assert property` | Sampled values are race-free, and only concurrent assertions have temporal operators such as `##` |
| A combinational rule that only matters at the active clock edge | Concurrent, for example `@(posedge clk) $onehot(grant)` | Ignores everything between edges, including real short pulses: be sure that is what you want |

**When not to use an assertion.** Do not put work with side effects in an assertion expression, and do not use assertions for checks that must count toward the test's pass/fail verdict in a UVM bench unless that routing is in place.

### Debugging assertion reports

| Symptom in the log | Likely cause | Fix |
|---|---|---|
| A simple immediate assertion fails once, at a time when the waveform shows the signals agree | A glitch: the procedure ran on half-updated values in the same time slot | Make it `assert #0`, or `assert final` |
| An `assert #0` prints a failure at a time when the settled values are legal, only in tests where a program block or a clocking-block drive changes the inputs | The input changed after Observed, so the failure had already matured | `assert final` |
| A concurrent failure message prints values that satisfy the check (`a=0 b=0` for `a == b`) | The action block printed current values in Reactive | Print `$sampled(a)` and `$sampled(b)` |
| An immediate assertion fails on every clock during reset | An `x` in the expression counts as false | Gate it with reset, or check `!$isunknown(...)` first |
| Compile error on a deferred assertion's action block | A `begin`-`end` block or a statement that is not a subroutine call | Put the work in a void function and call that one function |
| Error about writing a variable in Postponed, or a counter that never moves | An `assert final` action writes a variable | Only print from `final`; count with `#0` |
| A concurrent assertion never catches a bad pulse the waveform shows | The pulse started and ended between two clock ticks, so no sample ever saw it | Use a deferred immediate assertion for a combinational rule |
| Error: no clock for `assert property` inside an `always_comb` | No clock can be inferred from `always_comb` and there is no default clocking | Write the clock in the assertion, or use a deferred immediate assertion |

### Recap

- Immediate assertions are procedural: they check current values whenever the code reaches them. Simple ones report at once; deferred ones queue their report and drop it if the process runs again.
- `assert #0` reports in Reactive after maturing in Observed; the Postponed region is where `assert final` matures and reports, so it survives Reactive-region changes. Deferred action blocks are one subroutine call; `final` actions must not write variables.
- Concurrent assertions check at clock ticks, in Observed, on sampled (Preponed) values, and run their action blocks in Reactive with current values, so print `$sampled(...)`.
- Choose by the question: one moment in TB code (simple), a combinational rule (deferred), a clocked or temporal rule (concurrent).

## Make It Work

### All four kinds on one bench

This bench checks one rule, "b always equals a", with all four kinds at once. It contains a glitch at 10 ns and a real bug from 20 ns to 30 ns. The concurrent assertion is clocked by a free-running clock whose rising edges fall at 5, 15, 25 and 35 ns.

```systemverilog
// compile
`timescale 1ns/1ps
module tb_top;
  logic clk = 1'b0;
  logic a   = 1'b0;
  logic b   = 1'b0;   // rule: b always equals a

  always #5 clk = ~clk;   // rising edges at 5, 15, 25, 35 ns

  // The three immediate kinds run every time a or b changes.
  always @(a or b) begin : chk
    a_simple: assert (a == b)
      else $error("a_simple: a=%0b b=%0b", a, b);
    // Deferred: by-value arguments are captured now, printed later
    a_obs:    assert #0 (a == b)
      else $error("a_obs: a=%0b b=%0b", a, b);
    a_fin:    assert final (a == b)
      else $error("a_fin: a=%0b b=%0b", a, b);
  end

  // Concurrent: one attempt per rising edge, on Preponed samples.
  // The action block runs in Reactive, so print what was sampled.
  a_conc: assert property (@(posedge clk) a == b)
    else $error("a_conc: sampled a=%0b b=%0b", $sampled(a), $sampled(b));

  initial begin
    #10 a = 1'b1;   // 10 ns: a glitch, b follows in the same time slot
    #0  b = 1'b1;
    #10 a = 1'b0;   // 20 ns: a real bug, b lags behind by 10 ns
    #10 b = 1'b0;   // 30 ns: b catches up
    #10 $finish;    // 40 ns
  end
endmodule
```

ERROR  20 ns  tb_top.chk.a_fin     a_fin: a=0 b=1

Read it against the rules:

- **10 ns:** only `a_simple` reports. The deferred failures were flushed when `chk` ran again with `b = 1`, and 10 ns is not a clock edge.
- **20 ns:** nothing changes `a` or `b` again in this time slot, so no flush happens. `a_simple` prints in Active, `a_obs` in Reactive and `a_fin` in Postponed: same time stamp, three regions, in that order.
- **25 ns:** the concurrent assertion sees the bug at the first rising edge after it started, on the Preponed samples `a = 0`, `b = 1`. The edges at 5, 15 and 35 ns sample equal values and pass silently.

### How to choose and write an assertion

1. **State the rule in one sentence**, and note whether it is about one moment ("b equals a"), about a clock edge ("at each edge, grant is one-hot") or about several cycles ("ack within 3 cycles").
2. **Pick the kind** with the decision table: procedural TB check, combinational rule, or clocked or temporal rule.
3. **Place it.** Simple immediate: in the procedure or method that has the value. Deferred: at module or interface level as a static deferred assertion, or inside the `always_comb`. Concurrent: in the interface or module, outside procedures, with an explicit clock.
4. **Label it** (`a_<rule>:`) so the message names it and `$assertoff` can target it.
5. **Write the action block** with a severity task. For deferred assertions keep it to one call, and only print from `final`. For concurrent assertions print `$sampled(...)` values.
6. **Guard reset and X**: gate with reset, or add a `!$isunknown(...)` check.
7. **Break it on purpose** and confirm it reports. Then confirm it stays silent on a glitch.

**Break it on purpose.** Make three one-line changes, one at a time, and predict the log before each run:

- Delete `#0 ` from the second line of the `initial` block, so `b = 1'b1;` runs right after `a = 1'b1;`. On typical simulators `chk` then runs once, after both changes, and `a_simple` no longer prints at 10 ns: the glitch came from the `#0`. (The standard lets a simulator switch to `chk` between the two statements, §4.7, so this is not guaranteed; the `#0` version is.)
- Change `a_obs` to `assert (a == b)`. It now prints at 10 ns as well, exactly like `a_simple`.
- In `a_conc`, print `a, b` instead of `$sampled(a), $sampled(b)`. At 25 ns it still prints `a=0 b=1` here, because nothing changes `a` or `b` at 25 ns. Current and sampled values differ only when something writes the signals on the clock edge, as in the `a1_bad` waveform above.

**Checklist before moving on:**
- [ ] You can say, for each of the four kinds, when it checks, which values it reads and in which region it reports.
- [ ] You can trace the glitch at 10 ns and explain why only `a_simple` prints.
- [ ] You can explain why `a_obs`, `a_fin` and `a_simple` all print at 20 ns, in three different regions.
- [ ] You can write a legal deferred action block and explain why a `final` action must not write a variable.
- [ ] You print `$sampled(...)` in concurrent action blocks, and you know why.

## Push Further

### Expert: Observed or final when Reactive code changes the inputs

Deferral protects against glitches that come from the order of procedural execution, but not against loops between regions (§16.4.1). The standard's example (§16.4.2) has a DUT with a static `assert #0 (!(a & c))` and a static `assert final (!(a & c))`, where `a` is driven by a program block. A program block runs in the Reactive region set. In the time slot where `a` and `c` are both 1:

- Both assertions fail in Active and queue their reports.
- The `#0` report matures in Observed, so its failure is printed in Reactive.
- Still in Reactive, the program sets `a = 0`. That starts another pass through Active, where the implied `always_comb` runs again: a flush point. For `#0` the flush comes too late; the new evaluation passes, so the log shows **both a fail and a pass** at one time stamp.
- The `final` report has not matured yet, so it is flushed. Only the settled pass is reported in Postponed.

Clocking-block output drives land in Re-NBA (§14.16), also after Observed. So a combinational check on DUT inputs that a UVM driver writes through a clocking block should use `assert final`, as long as its action only prints.

### Expert: Deferred arguments and functions are evaluated on every failure

A deferred assertion queues the *call*, but it evaluates by-value arguments, including function calls, every time it queues one (§16.4). In the standard's example, `$error("...", error_type(opcode))` calls `error_type()` on every failing evaluation, even when the report is later flushed, so any side effect or nested assertion in that function fires on glitches anyway (§16.4.2). Three related corner cases:

- **Short-circuit hides results.** In `a = b || f(c);`, a deferred assertion inside `f` is never reached when `b` settles to 1, so after the flush nothing at all is reported for that time slot (§16.4.2). Use `|`, which evaluates both operands, if every evaluation must be checked.
- **One function, many queues.** A deferred assertion inside a function belongs to the process that called it. Two `always_comb` blocks calling the same function flush independently, so one can report a failure while the other passes (§16.4.5).
- **`ref` arguments read late.** A `ref` or `const ref` argument reads its current value in Reactive (`#0`) or Postponed (`final`), not the value that failed. Passing an automatic or dynamic variable to a `ref` formal is an error (§16.4).

### Expert: Two queues per process

A process can own two queues at once, and they follow the same flush rules but different maturity rules:

| | Deferred report queue (§16.4.1) | Procedural assertion queue (§16.14.6) |
|---|---|---|
| What is queued | A pending *report*: the action-block call, with its by-value arguments | A pending *instance* of a concurrent assertion, with its `const'` and automatic values |
| When it was checked | Already, when the statement was reached | Not yet: no check happens when the statement is reached |
| Flush points | Resume from `@` or `wait`; `always_comb`/`always_latch` re-trigger; `disable` of the outermost scope (§16.4.2) | The same three (§16.14.6.2) |
| Maturity | Observed (`#0`) or Postponed (`final`); the call then runs | Observed; an evaluation attempt starts at once if this time slot is a tick of its clock, otherwise at its next tick |
| After maturity | The report runs; nothing can cancel it | The attempt runs to completion; `disable` no longer affects it (§16.14.6.4) |

Both resist glitches from the order of procedural execution and neither resists Reactive-to-Active loops (§16.4.1, §16.14.6.3). `$assertoff` leaves both queues alone, so already-queued entries may still mature; `$assertkill` flushes both (§20.11). The traps that belong to procedural concurrent assertions alone, clock inference in an `always_ff` with asynchronous reset, `if` conditions read on current values and static loop variables, are worked through in the module overview's Push Further.

### Expert: Silencing one kind with `$assertcontrol`

`$assertoff`, `$asserton` and `$assertkill` act on all four kinds in this lesson: `$assertoff(levels, scope)` is defined as `$assertcontrol(4, 15, 7, levels, scope)` (§20.11; the module overview covers them for concurrent assertions). The second argument is an **assertion_type** mask (Table 20-6): 1 concurrent, 2 simple immediate, 4 observed deferred, 8 final deferred, 16 `expect`, and 32, 64 and 128 for `unique`, `unique0` and `priority` violation reports. So you can switch off only the deferred checks of one block during a known-noisy reset sequence:

```systemverilog
// snippet
initial begin
  $assertcontrol(4, 12, 7, 0, tb_top.dut);  // Off: observed + final deferred, all levels
  wait (tb_top.rst_n === 1'b1);
  $assertcontrol(3, 12, 7, 0, tb_top.dut);  // On again
end
```

Off and Kill differ for deferred assertions (§20.11). **Off** (control_type 4) stops new checks, but reports already queued are not flushed and may still mature and print. **Kill** (control_type 5), for the assertions it selects, also flushes pending deferred reports and pending procedural assertion instances that have not matured, and aborts concurrent attempts in flight.

### Kata: tame a glitchy one-hot checker

An arbiter hands the grant from requester 0 to requester 1 in two steps within one time slot. Your checker must report real double grants but stay silent on the hand-over.

```systemverilog
// compile
`timescale 1ns/1ps
module tb_top;
  logic [3:0] grant = 4'b0001;   // requester 0 holds the grant

  always_comb begin : chk
    a_1hot: assert ($onehot(grant))
      else $error("a_1hot: grant=%b", grant);
  end

  initial begin
    #10 grant[0] = 1'b0;     // hand-over step 1: release requester 0
    #0  grant[1] = 1'b1;     // hand-over step 2: grant requester 1, same time slot
    #10 grant    = 4'b0011;  // a real bug: two grants
    #10 grant    = 4'b0100;
    #10 $finish;
  end
endmodule
```

1. **Predict:** how many `a_1hot` errors does this print, and at which times?
2. **Fix:** change one token so only the real bug reports. How many errors now, and in which region is the message printed?
3. **Extend:** suppose step 2 of the hand-over is made by a program block (Reactive region) instead of the `initial`. Does your fix still stay silent at 10 ns? If not, what do you change, and what may its action block no longer do?

<details>
<summary>Reveal the worked solution</summary>

1. **Two errors.** At time 0 the `always_comb` runs once and passes (`0001`). At 10 ns, step 1 makes `grant = 4'b0000`; `chk` runs at once (an `always_comb` is sensitive to the expressions in its immediate assertions, §9.2.2.2.2) and `a_1hot` fails with `grant=0000`. Step 2 makes `0010` and the re-run passes. At 20 ns, `0011` fails. At 30 ns, `0100` passes.
2. **Write `assert #0`.** At 10 ns the failure is queued, then flushed when the `always_comb` re-runs on step 2 (§16.4.2). At 20 ns nothing re-runs `chk`, so the failure matures in Observed and is printed in Reactive. One error, `a_1hot: grant=0011` at 20 ns. The `$error` arguments are passed by value, so they keep the failing value (§16.4).

   ```systemverilog
   // snippet
   a_1hot: assert #0 ($onehot(grant))
     else $error("a_1hot: grant=%b", grant);
   ```

3. **No.** Step 2 now happens in Reactive, after the 10 ns failure has matured in Observed, so `assert #0` prints the false failure (and the re-run then passes, §16.4.1). Use `assert final`: the re-run reaches its flush point before the end of the time slot, so only the settled value is reported. Its action must be callable in Postponed, so it may print but must not write any variable (§16.4, §4.4.2.9).

</details>
