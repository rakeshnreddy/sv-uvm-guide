## Quick Take

- **What it is:** A UVM testbench (TB) is a tree of **components**, each with one standard role. The **test** configures the bench and starts the traffic. The **env** holds everything that belongs to one design under test (DUT). One **agent** per DUT interface groups the parts that talk to that interface: a **sequencer** and a **driver** that send traffic, and a **monitor** that watches it. A **scoreboard** checks the DUT's results and a **coverage subscriber** records what was exercised, both beside the agents in the env (IEEE 1800.2-2020 §13.2–§13.9, §15.5).
- **Why it matters:** Standard roles let you reuse an agent unchanged. The same agent class drives an interface in a block-level bench and only watches it, as a **passive** agent, when that interface is driven by real hardware at chip level. Only the env's wiring and the test's settings change. Put a job in the wrong role and reuse breaks: a scoreboard inside an agent cannot see the other interface it must compare against, and a driver left in a "passive" agent fights the DUT for the bus.
- **The Analogy:** A film shoot. The test is the director, who picks the cast and calls "action". The env is the soundstage. Each agent is a camera crew assigned to one set: an operator who moves the scenery on cue (the driver, fed by the sequencer) and a camera that records it (the monitor). The editor (the scoreboard) compares footage from several cameras against the script. *Where it breaks:* a real camera crew can be told to "stand still"; a passive agent instead never hires the operator at all, because an idle driver would still be standing on the set. And a camera never edits film: a monitor only records, it never drives.

> **Retention Hook:** An active agent is sequencer + driver + monitor. A passive agent is the monitor alone. Checking lives beside the agents, never inside them.

**You will be able to:**
1. **Assign** each testbench responsibility (stimulus, arbitration, pin driving, observation, data checking, coverage, configuration, orchestration) to its UVM role, and justify why the scoreboard sits in the env rather than in an agent.
2. **Write** an agent that always builds its monitor, builds its sequencer and driver only when `get_is_active()` returns `UVM_ACTIVE`, and connects `drv.seq_item_port` to `sqr.seq_item_export` under the same test.
3. **Write** a monitor that samples a valid/ready bus through a clocking block, creates a new item for every transfer and publishes it on an analysis port.
4. **Write** an env that builds an active input agent, a passive output agent, a scoreboard and a coverage subscriber and connects them, and **predict** its `print_topology` listing for any `is_active` setting.
5. **Debug** the classic agent bugs from their symptoms: a missing `super.build_phase`, a missing `get_is_active()` guard, a mistargeted `is_active` setting and a reused monitor item.

## Build Your Mental Model

### Words you need first

You met most of these in the prerequisites. This lesson leans on all of them, so here they are in one place.

- A **component** is a `uvm_component`: created once, during the **build phase**, with a name and a parent, and kept for the whole simulation. Components form a tree, and each has a full name such as `uvm_test_top.env.in_agt.drv` ([I-UVM-1A](/curriculum/T2_Intermediate/I-UVM-1A_Components/index)).
- An **object** is a `uvm_object` with no parent: it is created, passed around and dropped. Transactions, sequences and configuration objects are objects.
- A **phase** is one step of the run that every component executes in a fixed order. This lesson uses four: `build_phase` creates children, top-down; `connect_phase` wires them together, bottom-up; `end_of_elaboration_phase` runs once the tree is complete; and the `run_phase` task is where simulation time passes ([I-UVM-1C](/curriculum/T2_Intermediate/I-UVM-1C_UVM_Phasing/index)).
- `type_id::create("name", this)` asks the **factory** to build a child, so a test can later substitute a derived class ([I-UVM-1B](/curriculum/T2_Intermediate/I-UVM-1B_The_UVM_Factory/index)).
- A **transaction** is one complete exchange on an interface, written as an object. A **sequence item** (or just **item**) is a transaction that travels from a sequence to a driver; it extends `uvm_sequence_item` (§14.1).
- A **virtual interface** (`vif` in code) is a handle that lets class code reach an interface instance. A **clocking block** (`drv_cb`, `mon_cb`) samples and drives that interface's signals at a clock edge without races ([F4C](/curriculum/T1_Foundational/F4C_Clocking_Blocks/index)).

Two connection mechanisms appear here as **labelled previews**. A **port** is a typed connection point on a component; one component calls methods through it, and the component at the other end implements them. Ports are joined with `connect()` in `connect_phase`. The end that implements the methods is an **imp** (short for implementation); an **export** carries a connection through a component's boundary toward an imp inside it. Despite its name, a sequencer's `seq_item_export` is an imp. An **analysis port** is a component's outlet: `ap.write(t)` hands the handle `t` to every component connected to it ([I-UVM-2B](/curriculum/T2_Intermediate/I-UVM-2B_TLM_Connections/index) owns the details). The **configuration database**, `uvm_config_db`, is a lookup table where a test or `tb_top` leaves a value under a path and a name, and a component retrieves it ([I-UVM-2C](/curriculum/T2_Intermediate/I-UVM-2C_Configuration_and_Resources/index) owns the details).

### The bench is a tree of roles

Start from the jobs a testbench must do, not from the class names. Each job has exactly one standard owner:

| Responsibility | Role | Base class | Component or object | Where it lives |
|---|---|---|---|---|
| Decide what traffic to send (**stimulus**) | sequence | `uvm_sequence #(REQ)` | object | started by the test on a sequencer |
| Carry one unit of traffic | sequence item | `uvm_sequence_item` | object | flows sequence → sequencer → driver |
| Choose which sequence's item goes next (**arbitration**) and hand it to the driver | sequencer | `uvm_sequencer #(REQ)` | component | active agent |
| Turn an item into signal activity (**pin driving**) | driver | `uvm_driver #(REQ)` | component | active agent |
| Turn signal activity back into transactions (**observation**) | monitor | `uvm_monitor` | component | every agent |
| Package one interface's sequencer, driver and monitor for reuse | agent | `uvm_agent` | component | env |
| Compare what the DUT did with what it should have done (**data checking**) | scoreboard | `uvm_scoreboard` | component | env |
| Record which values and scenarios occurred (**coverage**) | coverage subscriber | `uvm_subscriber #(T)` | component | env (or an agent, behind an on/off knob) |
| Hold the agents and checkers for one DUT (**integration**) | env | `uvm_env` | component | under the test |
| Choose settings and start the traffic (**configuration and orchestration**) | test | `uvm_test` | component | the root of the tree, named `uvm_test_top` |
| Carry one agent's settings in one place | configuration object (preview) | `uvm_object` | object | set by the test, read by the agent |

Two roles you will meet later fit the same pattern. A **virtual sequencer** in the env coordinates sequences across several agents ([I-UVM-3B](/curriculum/T2_Intermediate/I-UVM-3B_Advanced_Sequencing_and_Layering/index)). A **reference model** or predictor inside the scoreboard computes expected results ([A-UVM-6](/curriculum/T3_Advanced/A-UVM-6_Scoreboards_and_Reference_Models/index)).

The bus in this lesson is a **valid/ready bus**: the sender raises `valid` with a byte on `data`; the receiver raises `ready` when it can accept; a **transfer** happens at each rising clock edge where both are sampled as 1. The DUT, `incr_dut`, accepts a byte on its input bus and, one clock later, offers that byte plus 1 on its output bus. Every name in the picture below is the name used in the code on this page.

Three things in the picture are worth saying out loud:

- **The test chooses the shape.** One `bus_agent` class appears twice. The test, not the agent, decides that `out_agt` is passive.
- **Agents are per interface.** Each agent sees exactly one `bus_if` instance. That is what makes it reusable: it never needs to know what else is in the bench.
- **Checking sits beside the agents.** `scb` needs both the input stream and the output stream, so it can only live where both are visible: the env.

**Pitfall: the scoreboard inside the agent.** It looks tidy to give each agent its own scoreboard. But an agent sees one interface, and a data check such as "every byte that went in comes out, plus 1, in order" needs two. Worse, at chip level the same agent class is reused passive on many interfaces, and every instance would carry a scoreboard that can compare nothing. Keep protocol checks of one interface (the monitor's job) separate from data checks across interfaces (the scoreboard's job).

**Pitfall: thinking sequences are components.** Sequences and items are objects. They are not in the tree, they have no `build_phase`, and the factory creates them with `create("name")`, without a parent. A sequence borrows a sequencer while it runs.

### Active and passive agents

An agent is **active** when it drives its interface and **passive** when it only watches. The agent decides what to build from one setting, `is_active`, of type `uvm_active_passive_enum` (values `UVM_ACTIVE` and `UVM_PASSIVE`, Annex F.2.1.7):

- `uvm_agent` itself builds nothing. It declares `is_active`, with the default `UVM_ACTIVE`, and its `build_phase` looks up a configuration setting named `"is_active"` for this agent and copies it in (uvm-core 2020.3.1 `uvm_agent.svh`).
- `get_is_active()` returns the result (§13.4.2.2).
- **Your** agent's `build_phase` calls `super.build_phase(phase)` first, then creates the monitor always, and the sequencer and driver only when `get_is_active()` returns `UVM_ACTIVE`.
- **Your** agent's `connect_phase` connects the driver to the sequencer under the same test, because in passive mode both handles are `null`.

```systemverilog
// snippet: the agent (it is part of bus_pkg in Make It Work)
class bus_agent extends uvm_agent;
  `uvm_component_utils(bus_agent)

  bus_sequencer sqr;
  bus_driver    drv;
  bus_monitor   mon;
  uvm_analysis_port #(bus_item) ap;   // the agent's outlet: the env connects here

  function new(string name, uvm_component parent);
    super.new(name, parent);
  endfunction

  function void build_phase(uvm_phase phase);
    super.build_phase(phase);         // uvm_agent reads the "is_active" setting here
    ap  = new("ap", this);
    mon = bus_monitor::type_id::create("mon", this);   // always: observing is never wrong
    if (get_is_active() == UVM_ACTIVE) begin
      sqr = bus_sequencer::type_id::create("sqr", this);
      drv = bus_driver::type_id::create("drv", this);
    end
  endfunction

  function void connect_phase(uvm_phase phase);
    mon.ap.connect(ap);               // promote the monitor's port to the agent boundary
    if (get_is_active() == UVM_ACTIVE)  // the same test as build: drv and sqr may be null
      drv.seq_item_port.connect(sqr.seq_item_export);
  endfunction
endclass
```

The test chooses the mode per agent instance. It must do so before the agent's `build_phase` runs, and since build runs top-down, the test's own `build_phase`, before it creates the env, is the natural place:

```systemverilog
// snippet: bus_test::build_phase
uvm_config_db#(uvm_active_passive_enum)::set(this, "env.out_agt", "is_active",
                                              UVM_PASSIVE);
env = bus_env::type_id::create("env", this);
```

The path `"env.out_agt"` is relative to the test, so it names exactly one agent, `uvm_test_top.env.out_agt`. `in_agt` gets no setting and keeps the default, `UVM_ACTIVE`.

**Predict first.** In the visual below, `in_agt` drives the DUT's input bus and `out_agt` watches its output bus. Before you touch anything, answer its question: which children does `out_agt` build when the test sets it to `UVM_PASSIVE`? Then flip each agent's mode, and inject the two classic bugs one at a time.

**What you should have seen.**
- **Passive means not built.** With `out_agt` passive, only `mon` (and the agent's `ap`) exist. The "idle driver" answer is the most common wrong one: an idle driver still runs its `run_phase` and drives idle values onto signals the DUT owns.
- **Skipping `super.build_phase` silently undoes the setting.** Nothing reads `is_active`, so it stays at its default, `UVM_ACTIVE`, and `out_agt` builds a sequencer and a driver for a bus the DUT drives.
- **A missing guard fails in `connect_phase`, not later.** In passive mode `drv` is `null`, and `drv.seq_item_port` dereferences it: the simulator reports a null-object access and stops.
- The visual leaves out the coverage subscriber `cov` and the sequence; the full-bench picture above shows them.

**Pitfalls, with the reason each is wrong:**
- **"A passive agent keeps its sequencer so tests can still start sequences on it."** A sequencer with no driver accepts items that nobody ever takes. A passive agent builds neither, so `env.out_agt.sqr` is `null`. A sequence started on it runs its body and stops at its first `start_item` with `UVM_FATAL [SEQ] neither the item's sequencer nor dedicated sequencer has been supplied to start item` (uvm-core `uvm_sequence_base.svh`).
- **"I can decide active or passive in the agent's constructor."** In the constructor, `build_phase` has not run, so `get_is_active()` still returns the default, `UVM_ACTIVE`. Ask only from `build_phase` on, after `super.build_phase`.
- **"Any path that contains the agent works."** A setting on `"env.out_agent"` (a typo), or one made after the env was already built, matches nothing or arrives too late. The agent then stays active, silently. The debugging section below shows how to catch it.

### The driver's loop (a preview of I-UVM-3A)

A **driver** turns items into signal activity. It extends `uvm_driver #(bus_item)`, which gives it a `seq_item_port` (a port that pulls items from the sequencer) and a handle `req` for the current item (§13.7). Its `run_phase` is one endless loop with a fixed shape: get the next item, drive it, report it done. The handshake behind `get_next_item` and `item_done` is owned by [I-UVM-3A](/curriculum/T2_Intermediate/I-UVM-3A_Fundamentals/index); here you need only the shape.

```systemverilog
// snippet: bus_driver::run_phase (the full class is in Make It Work)
task run_phase(uvm_phase phase);
  vif.drv_cb.valid <= 1'b0;                   // idle until the first item
  wait (vif.rst_n === 1'b1);
  forever begin
    seq_item_port.get_next_item(req);        // blocks until a sequence offers an item
    @(vif.drv_cb);
    vif.drv_cb.valid <= 1'b1;                 // synchronous drives (F4C)
    vif.drv_cb.data  <= req.data;
    do @(vif.drv_cb); while (vif.drv_cb.ready !== 1'b1);   // DUT accepted it
    vif.drv_cb.valid <= 1'b0;
    seq_item_port.item_done();               // the sequence may send the next one
  end
endtask
```

Three rules for drivers, each with its reason:
- **A driver never raises an objection.** Objections decide when the test may end; that is the test's or the top sequence's call ([I-UVM-1C](/curriculum/T2_Intermediate/I-UVM-1C_UVM_Phasing/index)). A driver's loop never finishes, so an objection raised there would never drop.
- **A driver drives only through its clocking block**, so its drives never race the DUT's sampling ([F4C](/curriculum/T1_Foundational/F4C_Clocking_Blocks/index)).
- **A driver does not check results.** If it compared what it sent with what came back, the check would vanish in passive mode, exactly where chip-level benches need it.

### The monitor: sample, build a new item, publish

A **monitor** watches one interface and turns signal activity into transactions. It extends `uvm_monitor`, which adds nothing to `uvm_component` except its role (§13.5): everything a monitor does, you write. Its loop has three steps:

1. **Sample** the bus once per clock edge through `mon_cb`, a clocking block with only inputs. With the default input skew, `#1step`, every signal is read as it was just before the edge, the same values the DUT's flops capture at that edge (IEEE 1800-2023 §14.4, §14.13).
2. **Build a new item** whenever the samples show a complete transfer: here, `valid` and `ready` both 1.
3. **Publish** the item with `ap.write(t)`. This is a labelled preview of analysis ports: `write` is a function, so it returns in zero time, and every connected component receives the same handle ([I-UVM-2B](/curriculum/T2_Intermediate/I-UVM-2B_TLM_Connections/index)).

```systemverilog
// snippet: the monitor (it is part of bus_pkg in Make It Work)
class bus_monitor extends uvm_monitor;
  `uvm_component_utils(bus_monitor)

  virtual bus_if vif;
  uvm_analysis_port #(bus_item) ap;

  function new(string name, uvm_component parent);
    super.new(name, parent);
  endfunction

  function void build_phase(uvm_phase phase);
    super.build_phase(phase);
    ap = new("ap", this);
    // Preview of I-UVM-2C: tb_top left this agent's interface handle under "vif".
    if (!uvm_config_db#(virtual bus_if)::get(this, "", "vif", vif))
      `uvm_fatal("NOVIF", "bus_monitor: no virtual interface set for 'vif'")
  endfunction

  task run_phase(uvm_phase phase);
    bus_item t;
    forever begin
      @(vif.mon_cb);                                   // once per rising edge
      if (vif.mon_cb.rst_n !== 1'b1) continue;         // ignore samples taken in reset
      if (vif.mon_cb.valid === 1'b1 && vif.mon_cb.ready === 1'b1) begin
        t = bus_item::type_id::create("t");            // a NEW object for every transfer
        t.data = vif.mon_cb.data;
        ap.write(t);
      end
    end
  endtask
endclass
```

Notice two things. At edge 2, `in_if.data` still reads 10, but `in_if.valid` is 0, so no transfer happens: data without `valid` means nothing. And `out_if.data` still reads 11 at edge 3 while `out_if.valid` is 0: the monitor must look at the qualifier, not at whether the data changed.

**Why a new item every time.** `ap.write(t)` passes a handle, not a copy. If the monitor creates `t` once and only overwrites its fields, every component that stored a handle holds the same object. Trace it for a subscriber that keeps every item it receives in a queue, `bus_item seen_q[$]`, after three transfers A (10), B (20) and C (7F):

| Step | Monitor does | The one object's `data` | `seen_q` holds | What the subscriber sees |
|---|---|---|---|---|
| build | `t = create("t")` once | X | (empty) | (nothing) |
| transfer A | `t.data = 10; ap.write(t)` | 10 | 1 handle to the object | 10 |
| transfer B | `t.data = 20; ap.write(t)` | 20 | 2 handles, same object | 20, 20 |
| transfer C | `t.data = 7F; ap.write(t)` | 7F | 3 handles, same object | 7F, 7F, 7F |

Every stored "item" now reads 7F. A scoreboard built this way reports every comparison against the last transfer, and the bug looks like a DUT bug. Creating a new object per transfer gives each receiver its own snapshot. (The receiving side has its own rule, copy before you modify, which [I-UVM-2B](/curriculum/T2_Intermediate/I-UVM-2B_TLM_Connections/index) covers.)

**Monitors never drive.** `mon_cb` declares only inputs, so the monitor has no way to change a signal; a monitor bug cannot disturb the DUT. That is also what makes a passive agent safe: it is a monitor and nothing else.

### The env: build and connect

The **env** creates the agents and checkers in `build_phase` and wires them in `connect_phase`. Wiring comes after building because every handle must exist before it is connected; `connect_phase` runs only after every component's `build_phase` has finished ([I-UVM-1C](/curriculum/T2_Intermediate/I-UVM-1C_UVM_Phasing/index)).

```systemverilog

  `uvm_component_utils(bus_env)

  bus_agent      in_agt;   // drives the DUT's input bus (active by default)
  bus_agent      out_agt;  // watches the DUT's output bus (the test makes it passive)
  bus_scoreboard scb;
  bus_coverage   cov;

  function new(string name, uvm_component parent);
    super.new(name, parent);
  endfunction

  function void build_phase(uvm_phase phase);
    super.build_phase(phase);
    in_agt  = bus_agent::type_id::create("in_agt", this);
    out_agt = bus_agent::type_id::create("out_agt", this);
    scb     = bus_scoreboard::type_id::create("scb", this);
    cov     = bus_coverage::type_id::create("cov", this);
  endfunction

  function void connect_phase(uvm_phase phase);
    in_agt.ap.connect(scb.exp_imp);           // what went in: scb predicts from it
    out_agt.ap.connect(scb.act_imp);          // what came out: compared with it
    out_agt.ap.connect(cov.analysis_export);  // coverage of the DUT's output values
  endfunction
endclass
```

The scoreboard has two inputs, `exp_imp` and `act_imp`, so it can tell the two streams apart. They are **imps**, the end points of an analysis connection, declared with the `` `uvm_analysis_imp_decl `` macro; this is a labelled preview of [I-UVM-2B](/curriculum/T2_Intermediate/I-UVM-2B_TLM_Connections/index), which teaches the macro. The coverage subscriber needs no such macro: `uvm_subscriber #(T)` already provides one input, `analysis_export`, and requires you to write one function, `write(T t)` (§13.9).

**Predict.** With the test setting shown earlier, which children does `env.out_agt` have? Write your answer, then check it against the topology listing in Make It Work.

**A wiring pitfall that hides itself.** Each agent must get *its own* interface. If `tb_top` hands one handle to every path, for example `set(null, "*", "vif", in_if)`, `out_agt`'s monitor watches the input bus. The scoreboard then compares the input stream with predictions made from the same stream. In this bench every comparison fails, because the DUT adds 1. With a DUT whose output should equal its input, every comparison would *pass*, and a broken DUT would ship. Set each agent's interface on its own path.

### The configuration object (preview)

Real agents have more than one setting: the interface handle, active or passive, whether the monitor runs protocol checks, whether coverage is collected. Setting each one separately through the configuration database means several names and paths that can each be mistyped. The usual practice is one **configuration object** per agent instance: a `uvm_object` that holds every setting, created and filled by the test, and read once by the agent. [I-UVM-2C](/curriculum/T2_Intermediate/I-UVM-2C_Configuration_and_Resources/index) owns the database mechanics and [A-UVM-7](/curriculum/T3_Advanced/A-UVM-7_VIP_Construction/index) owns configuration objects for reusable verification IP (VIP); this is the shape only.

### Debugging agents: symptom, cause, fix

| Symptom | Cause | Fix |
|---|---|---|
| A "passive" agent has `drv` and `sqr` in the topology listing; `out_if.valid` shows X whenever the DUT drives it to 1; the scoreboard never sees an output and the run ends only at `UVM_FATAL [PH_TIMEOUT]` | The agent's `build_phase` does not call `super.build_phase`, so `is_active` keeps its default. The unwanted driver drives `valid` to 0 against the DUT's 1 | Call `super.build_phase(phase)` first in every component's `build_phase` |
| The same symptoms, although `super.build_phase` is called | The `is_active` setting never matched: a mistyped path, a set made after the env was built, or a set from the wrong component | Fix the path or move the set before `create("env", this)`; then confirm with the listing or the check in the next row |
| You want to catch either of the two rows above before any traffic runs | — | In the test's `end_of_elaboration_phase`, compare `env.out_agt.get_is_active()` with what you intended and raise `` `uvm_error `` if they differ; or read the `print_topology` listing |
| The simulator stops in `connect_phase` with a null-object access in `bus_agent` | `drv.seq_item_port.connect(...)` runs without the `get_is_active()` guard in a passive agent | Guard the connection with the same test used in `build_phase` |
| `UVM_WARNING [DRVCONNECT] seq_item_port (a uvm_seq_item_pull_port in uvm_driver) has not been connected to a sequencer` | An active agent built `drv` but never connected it (uvm-core `uvm_driver::end_of_elaboration_phase`) | Add `drv.seq_item_port.connect(sqr.seq_item_export)` in the agent's `connect_phase` |
| Every stored item, or every scoreboard comparison, shows the data of the last transfer | The monitor creates one item and reuses it for every transfer | `create` a new item inside the loop, once per transfer |
| `UVM_FATAL [NOVIF]` at time 0 | No interface handle was set on a path that matches this component | Set the handle in `tb_top` before `run_test()`, on the agent's path |
| Every scoreboard comparison fails, or passes suspiciously, and the "outputs" arrive at input timing | Both agents received the same interface handle | Give each agent its own `vif`, set on its own path |

### Recap

- Each testbench job has one standard owner. Sequences and items are objects; everything in the tree is a component.
- An agent packages one interface. It always builds its monitor, and builds a sequencer and a driver only when `get_is_active()` returns `UVM_ACTIVE`; it guards its `connect_phase` with the same test.
- `uvm_agent` reads the `is_active` setting in its own `build_phase`, so your agent must call `super.build_phase` first, and the test must set it before the agent builds.
- A monitor samples through an input-only clocking block, creates a new item per transfer, and publishes it on an analysis port. It never drives.
- The env builds agents, a scoreboard and subscribers, and connects them. Checking that spans interfaces lives in the env, never inside an agent.

## Make It Work

### A complete bench: one agent class, two shapes

The example below is the whole bench from the picture at the top of the page: `incr_dut`, two instances of `bus_if`, and the package `bus_pkg` with an item, a sequence, the driver, monitor, agent, scoreboard, coverage subscriber, env and test. The sequence is a preview of [I-UVM-3A](/curriculum/T2_Intermediate/I-UVM-3A_Fundamentals/index); read it as "send these four bytes". The test makes `out_agt` passive, prints the topology at the end of elaboration, sends four bytes, and ends when the scoreboard has compared all four.

```systemverilog
// compile
// -----------------------------------------------------------------
// The interface. The signals an agent drives are nets (wire), not
// variables: on out_if the DUT drives valid and data, and a variable
// may not be both continuously driven and a clocking-block output
// (IEEE 1800-2023 §14.16.2). See "Expert: one interface type on both
// sides of the DUT".
// -----------------------------------------------------------------
interface bus_if (input logic clk, input logic rst_n);
  wire       valid;
  wire       ready;
  wire [7:0] data;

  clocking drv_cb @(posedge clk);       // the driver's view
    default input #1step output #0;
    output valid, data;
    input  ready;
  endclocking

  clocking mon_cb @(posedge clk);       // the monitor's view: inputs only
    default input #1step;
    input valid, ready, data, rst_n;
  endclocking
endinterface

// -----------------------------------------------------------------
// The DUT: one register stage that adds 1 to every byte.
// -----------------------------------------------------------------
module incr_dut (
  input  logic       clk,
  input  logic       rst_n,
  input  logic       in_valid,
  output logic       in_ready,
  input  logic [7:0] in_data,
  output logic       out_valid,
  input  logic       out_ready,
  output logic [7:0] out_data
);
  // Accept a new byte whenever the stage is empty or its byte is leaving.
  assign in_ready = !out_valid || out_ready;

  always_ff @(posedge clk or negedge rst_n) begin
    if (!rst_n) begin
      out_valid <= 1'b0;
    end else if (in_ready) begin
      out_valid <= in_valid;
      out_data  <= in_data + 8'd1;
    end
  end
endmodule

// The UVM package.

package bus_pkg;
  import uvm_pkg::*;
  `include "uvm_macros.svh"

  class bus_item extends uvm_sequence_item;
    `uvm_object_utils(bus_item)
    rand logic [7:0] data;

    function new(string name = "bus_item");
      super.new(name);
    endfunction

    function string convert2string();
      return $sformatf("data=%02h", data);
    endfunction
  endclass

  // The sequencer needs no new code: the library class does the routing.
  typedef uvm_sequencer #(bus_item) bus_sequencer;

  // Preview of I-UVM-3A: send four fixed bytes.
  class bus_seq extends uvm_sequence #(bus_item);
    `uvm_object_utils(bus_seq)
    logic [7:0] values[4] = '{8'h10, 8'h20, 8'h7F, 8'hFF};

    function new(string name = "bus_seq");
      super.new(name);
    endfunction

    task body();
      foreach (values[i]) begin
        req = bus_item::type_id::create("req");
        start_item(req);
        req.data = values[i];
        finish_item(req);
      end
    endtask
  endclass

  class bus_driver extends uvm_driver #(bus_item);
    `uvm_component_utils(bus_driver)
    virtual bus_if vif;

    function new(string name, uvm_component parent);
      super.new(name, parent);
    endfunction

    function void build_phase(uvm_phase phase);
      super.build_phase(phase);
      if (!uvm_config_db#(virtual bus_if)::get(this, "", "vif", vif))
        `uvm_fatal("NOVIF", "bus_driver: no virtual interface set for 'vif'")
    endfunction

    task run_phase(uvm_phase phase);
      vif.drv_cb.valid <= 1'b0;                 // idle until the first item
      wait (vif.rst_n === 1'b1);
      forever begin
        seq_item_port.get_next_item(req);
        @(vif.drv_cb);
        vif.drv_cb.valid <= 1'b1;
        vif.drv_cb.data  <= req.data;
        do @(vif.drv_cb); while (vif.drv_cb.ready !== 1'b1);
        vif.drv_cb.valid <= 1'b0;
        seq_item_port.item_done();
      end
    endtask
  endclass

  class bus_monitor extends uvm_monitor;
    `uvm_component_utils(bus_monitor)
    virtual bus_if vif;
    uvm_analysis_port #(bus_item) ap;

    function new(string name, uvm_component parent);
      super.new(name, parent);
    endfunction

    function void build_phase(uvm_phase phase);
      super.build_phase(phase);
      ap = new("ap", this);
      if (!uvm_config_db#(virtual bus_if)::get(this, "", "vif", vif))
        `uvm_fatal("NOVIF", "bus_monitor: no virtual interface set for 'vif'")
    endfunction

    task run_phase(uvm_phase phase);
      bus_item t;
      forever begin
        @(vif.mon_cb);
        if (vif.mon_cb.rst_n !== 1'b1) continue;
        if (vif.mon_cb.valid === 1'b1 && vif.mon_cb.ready === 1'b1) begin
          t = bus_item::type_id::create("t");   // a new object per transfer
          t.data = vif.mon_cb.data;
          ap.write(t);
        end
      end
    endtask
  endclass

  class bus_agent extends uvm_agent;
    `uvm_component_utils(bus_agent)

    bus_driver    drv;
    bus_monitor   mon;

    endfunction

      ap  = new("ap", this);

        drv = bus_driver::type_id::create("drv", this);
      end

      mon.ap.connect(ap);
      if (get_is_active() == UVM_ACTIVE)
        drv.seq_item_port.connect(sqr.seq_item_export);
    endfunction
  endclass

  // Preview of I-UVM-2B: two analysis inputs on one scoreboard.
  `uvm_analysis_imp_decl(_exp)
  `uvm_analysis_imp_decl(_act)

  class bus_scoreboard extends uvm_scoreboard;
    `uvm_component_utils(bus_scoreboard)
    uvm_analysis_imp_exp #(bus_item, bus_scoreboard) exp_imp;
    uvm_analysis_imp_act #(bus_item, bus_scoreboard) act_imp;

    logic [7:0]  expected_q[$];   // predicted output bytes, oldest first
    int unsigned compared;
    int unsigned mismatches;

    function new(string name, uvm_component parent);
      super.new(name, parent);
    endfunction

    function void build_phase(uvm_phase phase);
      super.build_phase(phase);
      exp_imp = new("exp_imp", this);
      act_imp = new("act_imp", this);
    endfunction

    // From in_agt: predict. Only the byte is stored, never the handle.
    function void write_exp(bus_item t);
      expected_q.push_back(t.data + 8'd1);
    endfunction

    // From out_agt: compare with the oldest prediction.
    function void write_act(bus_item t);
      logic [7:0] exp_data;
      compared++;
      if (expected_q.size() == 0) begin
        mismatches++;
        `uvm_error("SCB", $sformatf("unexpected output %02h", t.data))
        return;
      end
      exp_data = expected_q.pop_front();
      if (t.data === exp_data) begin
        `uvm_info("SCB", $sformatf("match %02h", t.data), UVM_MEDIUM)
      end else begin
        mismatches++;
        `uvm_error("SCB", $sformatf("expected %02h, got %02h", exp_data, t.data))
      end
    endfunction

    function void check_phase(uvm_phase phase);
      super.check_phase(phase);
      if (expected_q.size() != 0)
        `uvm_error("SCB", $sformatf("%0d predicted bytes never came out",
                                    expected_q.size()))
    endfunction

    function void report_phase(uvm_phase phase);
      super.report_phase(phase);
      `uvm_info("SCB_SUMMARY", $sformatf("matches=%0d mismatches=%0d pending=%0d",
                compared - mismatches, mismatches, expected_q.size()), UVM_NONE)
    endfunction
  endclass

  class bus_coverage extends uvm_subscriber #(bus_item);
    `uvm_component_utils(bus_coverage)
    logic [7:0] data;

    covergroup data_cg;
      coverpoint data {
        bins zero = {8'h00};
        bins low  = {[8'h01:8'h7F]};
        bins high = {[8'h80:8'hFF]};
      }
    endgroup

    function new(string name, uvm_component parent);
      super.new(name, parent);
      data_cg = new();                          // an embedded covergroup is built in new
    endfunction

    // The argument must be named t, as in uvm_subscriber (IEEE 1800-2023 §8.20).
    function void write(bus_item t);
      data = t.data;
      data_cg.sample();
    endfunction

    function void report_phase(uvm_phase phase);
      super.report_phase(phase);
      `uvm_info("COV", $sformatf("output data coverage = %0.1f%%",
                                 data_cg.get_coverage()), UVM_LOW)
    endfunction
  endclass

module tb_top;
  timeunit 1ns;
  timeprecision 1ps;
  import uvm_pkg::*;
  import bus_pkg::*;
  `include "uvm_macros.svh"

  logic clk = 1'b0;      // initialized in its declaration: no process sees an edge at 0
  logic rst_n;

  always #5 clk = ~clk;

  bus_if in_if  (.clk, .rst_n);
  bus_if out_if (.clk, .rst_n);

  // No block sits after the DUT in this bench: its output is always accepted.
  assign out_if.ready = 1'b1;

  incr_dut dut (
    .clk, .rst_n,
    .in_valid (in_if.valid),  .in_ready (in_if.ready),  .in_data (in_if.data),
    .out_valid(out_if.valid), .out_ready(out_if.ready), .out_data(out_if.data)
  );

  initial begin
    rst_n = 1'b0;
    repeat (2) @(negedge clk);
    rst_n = 1'b1;          // released on a falling edge, away from the sampling edge
  end

  initial begin
    // One handle per agent, each on its own path (preview of I-UVM-2C).
    uvm_config_db#(virtual bus_if)::set(null, "uvm_test_top.env.in_agt.*", "vif",
                                        in_if);
    uvm_config_db#(virtual bus_if)::set(null, "uvm_test_top.env.out_agt.*", "vif",
                                        out_if);
    run_test("bus_test");
  end
endmodule
```

### How to build an agent-based bench

1. **List the DUT's interfaces.** Give each one an interface type with a driver clocking block and an input-only monitor clocking block.
2. **Decide each agent's mode.** An interface the bench must drive gets an active agent; one the DUT (or other hardware) drives gets a passive agent.
3. **Write the item, then the driver and the monitor** for each interface type: the driver loops on `get_next_item` / drive / `item_done`; the monitor samples through `mon_cb`, creates a new item per transfer, and publishes it.
4. **Write the agent:** `super.build_phase` first; always the monitor and `ap`; sequencer and driver under `get_is_active() == UVM_ACTIVE`; the driver connection under the same test.
5. **Write the env:** create the agents, the scoreboard and the subscribers in `build_phase`; connect each agent's `ap` in `connect_phase`.
6. **Write the test:** set each agent's mode (or its configuration object) before creating the env; print the topology at the end of elaboration while you develop.
7. **Write `tb_top`:** instantiate the DUT and one interface per bus, set each interface handle on its own agent's path, then call `run_test()`.
8. **Run, then break it on purpose:** check the listing and the scoreboard summary, then remove a `super.build_phase` or a `connect` and make sure the bench notices.

**Checklist before moving on:**
- [ ] I can say which role owns stimulus, arbitration, pin driving, observation, data checking, coverage, configuration and orchestration.
- [ ] My agent calls `super.build_phase(phase)` before calling `get_is_active()`.
- [ ] My agent builds the sequencer and driver, and connects them, only under `get_is_active() == UVM_ACTIVE`.
- [ ] My monitor reads only through an input-only clocking block and creates a new item for every transfer.
- [ ] No scoreboard lives inside an agent; every cross-interface check is in the env.
- [ ] Each agent receives its own interface handle, on its own path.
- [ ] I can predict the `print_topology` listing for any combination of `is_active` settings, and I know it does not show connections.

## Push Further

### Expert: what the base classes really add

Most component base classes add a role and nothing else. Knowing exactly what each one provides tells you what you must write yourself. All from the uvm-core 2020.3.1 sources (`src/comps/*.svh`, `src/seq/uvm_sequencer*.svh`), with the 1800.2-2020 clause from each class's annotation:

| Class | Clause | What it adds to `uvm_component` |
|---|---|---|
| `uvm_test` | §13.2.1 | Nothing but the role: a `virtual class` with a constructor |
| `uvm_env` | §13.3.1 | Nothing but the role |
| `uvm_agent` | §13.4.1 | The field `is_active` (default `UVM_ACTIVE`), a `build_phase` that reads the `"is_active"` setting, and the virtual function `get_is_active()` (§13.4.2.2). It builds no children |
| `uvm_monitor` | §13.5.1 | Nothing but the role. No analysis port: you declare `ap` yourself |
| `uvm_scoreboard` | §13.6.1 | Nothing but the role |
| `uvm_driver #(REQ,RSP)` | §13.7.1 | `seq_item_port` (constructed in `new`), `rsp_port`, the handles `req` and `rsp`, and the `DRVCONNECT` warning at end of elaboration when `seq_item_port` has no connection |
| `uvm_push_driver #(REQ,RSP)` | §13.8.1 | The opposite direction: a `req_export` through which items are *pushed* in by a `put` call, which you implement. Rare in practice |
| `uvm_subscriber #(T)` | §13.9.1 | `analysis_export`, an imp whose instance name is `"analysis_imp"`, and the pure virtual function `write(T t)` (§13.9.3.2) that you must implement |
| `uvm_sequencer #(REQ,RSP)` | §15.5.1 | `seq_item_export` (an imp, `uvm_seq_item_pull_imp`), `rsp_export`, and all the arbitration machinery. You almost never extend it: a `typedef` is enough |

Two consequences. First, deriving from `uvm_monitor` rather than `uvm_component` changes no behaviour, but it states intent, and tools and reports that filter by type can use it. Second, because `uvm_test`, `uvm_env`, `uvm_agent`, `uvm_monitor`, `uvm_scoreboard` and `uvm_subscriber` are `virtual class`es, you cannot create them directly; you always extend them.

### Expert: how `is_active` is really read

`uvm_agent::build_phase` does not call `uvm_config_db::get`. It searches the **resource pool**, the store that `uvm_config_db` writes into, for entries named `"is_active"` that match the agent's full name, in precedence order, and reads the first one it can convert (uvm-core `uvm_agent.svh`, macro `` `uvm_resource_enum_read `` in `uvm_resource_defines.svh`). It accepts:
- `uvm_active_passive_enum`;
- a `string` that names a value, such as `"UVM_PASSIVE"`;
- a bit vector as wide as the enum, `uvm_integral_t`, `uvm_bitstream_t`, `int` or `int unsigned`.

IEEE 1800.2-2020 §13.4.2.2 requires only the first two: the enum, plus a string so that the command line can override it. The integral forms are what uvm-core 2020.3.1 adds, so treat them as implementation behaviour.

So `uvm_config_db#(int)::set(this, "env.out_agt", "is_active", 0)` also makes `out_agt` passive, even though [I-UVM-2C](/curriculum/T2_Intermediate/I-UVM-2C_Configuration_and_Resources/index) teaches that a `get` matches only the exact type that was set: this field is the exception. A set with any other type, for example `uvm_config_db#(logic)` or `#(byte)`, is silently ignored and the agent stays active. The command line works too, because `+uvm_set_config_string` and `+uvm_set_config_int` (Annex G.2.8) create string and integer settings: `+uvm_set_config_string=uvm_test_top.env.out_agt,is_active,UVM_PASSIVE` is the portable form, and `+uvm_set_config_int=uvm_test_top.env.out_agt,is_active,0` also works in uvm-core.

Timing rules follow from where the read happens. A setting made after the agent's `build_phase` has run changes nothing. Calling `get_is_active()` from the constructor returns the default. And `get_is_active()` is virtual: an agent may override it, for example to return `cfg.is_active`. If you do, make sure `cfg` is fetched before the first call, or the override dereferences a `null` handle. The copy pattern shown in the configuration-object preview avoids that trap and keeps one answer for everyone.

### Expert: monitor sampling skew

A monitor's clocking block decides *which* value of each signal it sees at an edge. (A **time slot** is all the activity at one simulation time; the standard divides it into ordered regions, among them Preponed, Active, NBA and Observed, as [F3B](/curriculum/T1_Foundational/F3B_Scheduling_Regions/index) teaches.)
- `#1step` (the default input skew) samples the value the signal had at the end of the previous time slot, just before the edge (IEEE 1800-2023 §14.4).
- An explicit `#0` input skew samples in the Observed region of the edge's time slot, after the design's nonblocking assignments for that edge have updated (§14.4, §14.13).

Mixing the two views in one transaction misclassifies transfers. A monitor that reads a FIFO's `full` flag with `#0` sees the flag *after* the write that filled the FIFO, and decides that write was refused. Use `#1step` for everything that qualifies a transfer (`valid`, `ready`, flags, the data being written), the same values the DUT's flops captured. Take a registered result one edge later, or through a separate input with `#0` when the protocol defines it as available in the same cycle. Experiment with both skews in F4C's skew visualizer ([F4C](/curriculum/T1_Foundational/F4C_Clocking_Blocks/index)).

### Expert: one interface type on both sides of the DUT

A reusable agent comes with one interface type, and a passive agent watches an instance of that type that something else drives. That has a legality consequence that catches many first VIPs (§14.16, §14.16.2):
- When the signal is a **variable** (for example `logic valid;`) and it appears as an `output` of a clocking block, it is illegal to also drive it with a continuous assignment (§14.16.2). Connecting a variable to a DUT output port implies exactly such a continuous assignment (§23.3.3.2). So `bus_if` with variables cannot legally sit on the DUT's *output* bus, even if its `drv_cb` is never used. How a simulator reports the violation is tool-dependent.
- When the signal is a **net** (for example `wire valid;`), each clocking-block output creates its own driver on the net. That driver starts at `'z` and has no effect until the first synchronous drive, so the DUT's driver wins until a driver actually drives.

That is why `bus_if` declares `valid`, `ready` and `data` as `wire`. It also explains the X in "Prove the checks can fail": once the unwanted driver in `out_agt` drives `valid` to 0, its driver and the DUT's resolve to X whenever the DUT drives 1.

### Expert: where protocol checks and coverage live

This is methodology, not a rule of the standard (`uvm_monitor` imposes nothing):
- **Protocol checks of one interface** ("`data` must not change while `valid` is high and `ready` is low") need cycle-level visibility. Put them in the monitor, behind a `checks_enable` knob, or as SystemVerilog Assertions (SVA) bound to the interface ([I-SV-4C](/curriculum/T2_Intermediate/I-SV-4C_Checkers/index)). A scoreboard sees transactions, not cycles, so it cannot make these checks.
- **Data checks across interfaces** belong in the env-level scoreboard.
- **Coverage** belongs in subscribers, or in the monitor behind a `coverage_enable` knob. Agent-level coverage travels with the agent into every bench that reuses it, which is often what a VIP wants; data coverage that relates several interfaces belongs in the env.

The knobs matter at chip level. The same passive agent may appear on dozens of interfaces, and its checks and coverage must be switchable per instance.

### Expert: reuse at chip level, reactive agents and scale

- **Chip-level reuse.** Agents on interfaces that become internal at chip level are reused passive: their monitors keep checking and covering traffic that real blocks now drive. Agents on the chip's own pins stay active, because the bench still drives those pins ([A-UVM-8](/curriculum/T3_Advanced/A-UVM-8_Multi_Agent_Topologies/index) builds such topologies).
- **Reactive agents.** A responder, the agent that plays a slave or memory, is active, but what it drives depends on what its monitor observes: it answers requests instead of starting them. It is still one agent class with the same build rules ([A-UVM-7](/curriculum/T3_Advanced/A-UVM-7_VIP_Construction/index)).
- **Scale.** Each component costs memory and each running `run_phase` costs simulation time per edge, but none of it advances simulated time. How much a large passive topology slows a run is tool-dependent; measure it rather than guess.

### Expert: checking topology in regression

The cheapest guard against "the agent was silently active" is a check in the test's `end_of_elaboration_phase`, when the tree is complete and nothing has run yet:

```systemverilog
// snippet: in bus_test
function void end_of_elaboration_phase(uvm_phase phase);
  super.end_of_elaboration_phase(phase);
  if (env.out_agt.get_is_active() != UVM_PASSIVE)
    `uvm_error("TOPO", "env.out_agt should be passive but is active")
endfunction
```

`print_topology` (IEEE 1800.2-2020 F.7.4.2; listing format from uvm-core 2020.3.1) is the human view of the same thing. Call it through `uvm_root::get()`; the global `uvm_top` still works but is a UVM 1.2 compatibility name in uvm-core. It prints components and ports, never connections. For connections, ask a port after end of elaboration: `get_connected_to()` and `get_provided_to()` (§5.5.2.9, §5.5.2.10) fill a list, and `debug_connected_to()` prints one (uvm-core implementation only, not in 1800.2). `uvm_root::set_enable_print_topology(1)` prints the listing automatically after end of elaboration (also uvm-core only).

### Kata 2 (debug): a broken DUT that passes

A teammate made three changes to the Make It Work bench, one at a time, and the last run passed:

1. To prove the bench catches bugs, the DUT now passes byte 7F through unchanged: `out_data <= (in_data == 8'h7F) ? in_data : in_data + 8'd1;`.
2. The monitor "saves an allocation" by creating its item once:

```systemverilog
// snippet: the changed bus_monitor::run_phase
task run_phase(uvm_phase phase);
  bus_item t = bus_item::type_id::create("t");   // changed: created once
  forever begin
    @(vif.mon_cb);
    if (vif.mon_cb.rst_n !== 1'b1) continue;
    if (vif.mon_cb.valid === 1'b1 && vif.mon_cb.ready === 1'b1) begin
      t.data = vif.mon_cb.data;
      ap.write(t);
    end
  end
endtask
```

3. The scoreboard now keeps every item it receives and compares the two queues at the end:

```systemverilog
// snippet: the changed parts of bus_scoreboard
bus_item in_q[$];
bus_item out_q[$];

function void write_exp(bus_item t);
  in_q.push_back(t);
endfunction

function void write_act(bus_item t);
  out_q.push_back(t);
  compared++;                         // the test still waits on this count
endfunction

function void check_phase(uvm_phase phase);
  super.check_phase(phase);
  foreach (out_q[i]) begin
    logic [7:0] exp_data;
    exp_data = in_q[i].data + 8'd1;   // 8 bits: FF + 1 wraps to 00
    if (out_q[i].data !== exp_data) begin
      mismatches++;
      `uvm_error("SCB", $sformatf("item %0d: expected %02h, got %02h",
                                  i, exp_data, out_q[i].data))
    end
  end
endfunction
```

The log ends with `SCB_SUMMARY matches=4 mismatches=0 pending=0` and `UVM_ERROR :    0`.

1. Trace what `in_q` and `out_q` hold when `check_phase` runs.
2. Explain why a broken DUT passed.
3. Fix the bench in one line.
4. The original Make It Work scoreboard would have caught the DUT bug even with the changed monitor. Why?

<details className="my-4 rounded-xl border border-border/70 p-3">
<summary className="cursor-pointer font-semibold">Show the worked solution</summary>

1. Each monitor instance now owns exactly one object. `in_q` holds four handles to `in_agt.mon`'s object, whose `data` was last set to FF. `out_q` holds four handles to `out_agt.mon`'s object, whose `data` was last set to 00 (the DUT produced 11, 21, 7F and 00).

| After the transfer of | `in_agt.mon`'s object | `out_agt.mon`'s object | `in_q` | `out_q` |
|---|---|---|---|---|
| 10 in, 11 out | 10 | 11 | 1 handle | 1 handle |
| 20 in, 21 out | 20 | 21 | 2 handles, one object | 2 handles, one object |
| 7F in, 7F out (the bug) | 7F | 7F | 3 handles | 3 handles |
| FF in, 00 out | FF | 00 | 4 handles | 4 handles |

2. `check_phase` runs after the last transfer, so all four comparisons read the same two objects: is 00 equal to FF + 1, wrapped to 8 bits? Yes, four times. The faulty output, 7F where 80 was due, lived in `out_agt.mon`'s object only from 85 to 105 ns; by the time anything looked, it had been overwritten.
3. Move the `create` into the `if` block, so each transfer gets a new object: `t = bus_item::type_id::create("t");` just before `t.data = vif.mon_cb.data;`. With that fix the same scoreboard reports `item 2: expected 80, got 7f` and one mismatch.
4. The original scoreboard used the data at the moment it arrived: `write_exp` stored the predicted *byte*, `t.data + 1`, and `write_act` compared `t.data` at once, before the monitor could overwrite it. Storing values, or copies, is the scoreboard's defence. Creating a new item per transfer removes the cause, and is the monitor's duty because it cannot know how its subscribers will use the handle.

</details>
