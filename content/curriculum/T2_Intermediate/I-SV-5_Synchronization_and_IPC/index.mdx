## Quick Take

- **What it is:** A testbench (TB) is a team of processes that run at the same simulation time: a generator and a driver, a monitor and a scoreboard, requesters, responders and a watchdog. **Synchronization** is how they cooperate. IEEE 1800-2023 gives you four tools for it. A **named event** says "it happened", a **mailbox** hands over data in order, and a **semaphore** shares a limited resource by handing out keys (Clause 15). A **`process` handle** lets one thread check on, wait for or stop another (§9.7). This page frames the module; three sub-lessons then take events, mailboxes and semaphores to full depth.
- **Why it matters:** Most testbench hangs are synchronization bugs: a trigger nobody heard, a key nobody returned, two threads each waiting for the other. They rarely print an error. A bench whose threads are all blocked can simply stop early (§9.6.1), and a race between processes that run at the same time can pass on one simulator and hang on another (§4.7). This page shows you how to pick a tool that cannot fail that way, and how to find the culprit when a bench stops anyway.
- **The Analogy:** A workshop. A bell (an event) tells whoever is listening that a job is ready. An in-tray with a fixed number of slots (a bounded mailbox) passes jobs along in order; when it is full, the sender waits. A key cabinet (a semaphore) decides who may use the one lathe. The foreman's staff list (process handles) lets them check on, wait for or send home one particular worker. *Where it breaks:* a bell rung while nobody listens is simply lost, and SystemVerilog only adds a light that stays on until simulation time moves (`.triggered`). The keys carry no names, so anyone may return a key they never took. And a worker sent home with a key in their pocket keeps it forever, because `kill()` returns nothing.

**You will be able to:**
1. **Choose** an event, a mailbox, a semaphore, a `process` handle or, between UVM components, a TLM FIFO for a coordination need, and justify the choice by what the tool passes, what it remembers and when it blocks.
2. **Write** the producer/consumer, request/response and resource-arbitration patterns from these tools, and predict when each thread blocks.
3. **Control** individual threads with `process` handles (`self`, `status`, `kill`, `await`), building on the fork and join you learned in F2C.
4. **Diagnose** a deadlock, a lost wake-up, a leaked key or starvation from a stuck bench's symptoms by drawing its wait-for graph, and **fix** it with a lock order, by releasing before you wait, or with a timeout that reports and cleans up.

## Build Your Mental Model

### Threads that must cooperate

Every `initial` block, and every branch of a `fork`, is a **process**, also called a thread. It runs its statements in order and can stop at a delay, an event control or a blocking method call. Processes that are ready at the same simulation time may run in any order (§4.7). So "B runs after A" is never something you can assume. You make it true with a tool that blocks the waiting thread until the other one acts.

Threads cooperate for three reasons, and sometimes one thread must control another:

- **Signal:** one thread tells others that something happened, such as reset released or stimulus finished. Only the moment matters.
- **Transfer:** a transaction must get from one thread to another, in order and without loss: generator to driver, monitor to scoreboard.
- **Share:** a bus, a reference model or a pool of request slots may be used by only one thread, or by N threads, at a time.
- **Control:** you must check on, wait for or stop one particular thread, for example a driver that is stuck past its deadline.

If you did the first look at interprocess communication in [F2D: Interprocess Communication](/curriculum/T1_Foundational/F2D_Reusable_Code_and_Parallelism/ipc), you have seen the three Clause 15 tools at work. This module takes them to full depth:

### Recap from F2C: threads start, end and get stopped

You need four rules from [F2C: Procedural Code and Flow Control](/curriculum/T1_Foundational/F2C_Procedural_Code_and_Flow_Control/index), which owns them and lets you watch them in its fork-join visualizer:

- `join` waits for every child, `join_any` for the first, and `join_none` for none. The children start only once the parent blocks or ends (§9.3.2).
- `wait fork` waits for the calling process's immediate children only (§9.6.1).
- `disable fork` kills every descendant of the calling process, including threads it forked earlier (§9.6.3). `disable` with a block name ends every process that is running that block (§9.6.2).
- For a timeout, give the race its own parent, so that `disable fork` cannot reach anything else: `fork begin fork … join_any; disable fork; end join`.

Those rules act on groups of threads. This module adds the `process` handle, which acts on exactly one.

Before you commit, check two properties, because they decide which bugs you can get: what the tool **remembers** when nobody is waiting, and when it **blocks**.

| Tool | Remembers when nobody waits | Blocks the caller when | Classic bug |
|---|---|---|---|
| Named event: `-> ev`, `@ev`, `wait (ev.triggered)` | Almost nothing: a `->` with no waiter is gone (§15.5.2), and `ev.triggered` lasts only until time advances (§15.5.3) | `@ev`: until the next trigger | The trigger runs before the wait in the same time slot, and the waiter sleeps forever |
| `mailbox #(T)` | Every message, in order, until someone takes it (§15.4.3) | `get()`: the mailbox is empty (§15.4.5). `put()`: a bounded mailbox is full (§15.4.3) | One transaction object reused for every `put()`, so all queued handles point to one object |
| `semaphore` | The key count. `new()` with no argument starts with **0** keys (§15.3.1) | `get(n)`: fewer than n keys are free (§15.3.3) | A path out of the critical section skips `put()`, and the key is gone |
| `process` handle | The thread's state: `FINISHED`, `RUNNING`, `WAITING`, `SUSPENDED` or `KILLED` (§9.7) | `await()`: until that thread ends | Using the handle before the child has run, while it is still `null` |
| `uvm_tlm_fifo #(T)` (UVM) | Like the `mailbox #(T)` it contains | `get()`: empty. `put()`: full, and the default depth is 1 | Expecting a deep queue: at depth 1 the putter waits for every get |

Three rules of thumb follow from that table:

- **If the waiter might arrive late, the tool must remember.** Use a mailbox, a semaphore created with 0 keys (each `put(1)` is banked until a `get(1)` takes it, §15.3.1–§15.3.3), or a flag you `wait` on. A bare event cannot do it.
- **If data moves, the data is the signal.** A mailbox `get()` returns exactly when the item arrives, so you do not need a separate event.
- **Between UVM components, connect TLM ports** instead of passing mailbox or event handles around. A `uvm_tlm_fifo` is a component that holds a `mailbox #(T)` behind exports such as `put_export` and `get_peek_export`. A `uvm_tlm_analysis_fifo` is unbounded, so the analysis `write()` that feeds it never blocks (IEEE 1800.2-2020 §12.2.8.2–§12.2.8.3). [I-UVM-2B: TLM Connections](/curriculum/T2_Intermediate/I-UVM-2B_TLM_Connections/index) teaches them.

**Producer/consumer: a mailbox between two speeds.** One thread makes items and another uses them, at different rates. The mailbox absorbs the difference, and it blocks whichever side gets too far ahead.

```systemverilog
// snippet: the two ends of req_mbx
mailbox #(int) req_mbx = new(2);    // bounded: at most 2 requests wait here

req_mbx.put(10 * id);               // producer: blocks only while 2 requests are queued
req_mbx.get(req);                   // consumer: blocks while the mailbox is empty
```

- Bound the mailbox where you want **back-pressure**, as from a generator to a driver. Never let it block a thread that must keep sampling, such as a monitor that feeds a scoreboard. Make that one unbounded, or use `try_put()` and report an error when it returns 0.
- When the message is a class handle, create a new object for every `put()`: the mailbox stores the handle, not a copy. The [Mailboxes](/curriculum/T2_Intermediate/I-SV-5_Synchronization_and_IPC/mailboxes) page builds the full generator → driver pipeline.

**Request/response: a channel out and a channel back.** A requester sends a request and waits for its own answer.

```systemverilog
// snippet: one reply mailbox per requester, so replies cannot cross
mailbox #(int) rsp_mbx[2];          // rsp_mbx[id] carries the replies for requester id

req_mbx.put(10 * id);               // the request names its sender
rsp_mbx[id].get(rsp);               // wait for my reply, not anyone's
```

- **Route the reply.** Give each requester its own reply mailbox, or put an id in the reply and dispatch it. If two requesters `get()` from one shared reply mailbox, each takes whichever reply is at the head.
- **Use a mailbox, not an event, for the reply.** A reply mailbox keeps the answer if it arrives before the requester starts to wait, but a `->` that runs first is lost.
- **Never hold a resource the responder needs while you wait for the reply.** Make It Work breaks this rule on purpose, so you can watch the deadlock it causes.

**Resource arbitration: a semaphore in front of a shared resource.** Several threads share something that only one, or only N, may use at a time.

```systemverilog
// snippet: one key means one bus owner
semaphore bus = new(1);

bus.get(1);                         // wait for the key; blocked callers queue in order
// drive the bus
bus.put(1);                         // the one exit point of the critical section
```

- Blocked callers are served first-in first-out, in the order they arrived (§15.3.3). Two callers that arrive in the same time slot can still arrive in either order (§4.7).
- **Credits** use the same tool with more keys. `semaphore credits = new(4);` lets four requests be outstanding: each request takes `credits.get(1)`, and whichever thread handles the reply returns it with `credits.put(1)`. Any thread may return a key (§15.3.2).
- Keys carry no owner, so nothing checks that the right thread returns them. Make every path out of the critical section call `put()`, and record the owner yourself when you debug. The [Semaphores](/curriculum/T2_Intermediate/I-SV-5_Synchronization_and_IPC/semaphores) page covers multi-key requests and leaks.

### Process handles: one thread under remote control

**What it is.** `process` is a built-in class, declared final so that it cannot be extended (§9.7). You never create one yourself: the simulator makes a `process` object for every process it spawns, and calling `new` on the class is an error. `process::self()` returns a handle to the process that calls it.

**What it solves.** `wait fork` and `disable fork` act on groups chosen by structure: all children, or all descendants. A handle acts on exactly one thread, wherever it sits in the tree. Through it you can read the thread's state, wait for it to end, or stop it and everything it forked, without touching its siblings.

| Method | Kind | What it does (§9.7) |
|---|---|---|
| `process::self()` | static function | Returns a handle to the calling process |
| `status()` | function | Returns `FINISHED`, `RUNNING` (not in a blocking statement), `WAITING` (in a blocking statement), `SUSPENDED` or `KILLED` (ended by `kill()` or `disable`) |
| `kill()` | function | Ends the process and all its descendants: every process it forked, and every process those forked in turn. All of them end before `kill()` returns |
| `await()` | task | Blocks until the process ends, normally or by `kill()`. Calling it on yourself is an error |
| `suspend()`, `resume()` | functions | Pause and restart a process. A process suspended while it waits ignores the event or delay it was waiting for until it is resumed |
| `srandom()`, `get_randstate()`, `set_randstate()` | functions | Seed, save and restore the thread's random-number generator (§18.13.3–§18.13.5) |

**How to capture a handle.** The child publishes its own handle, and the parent waits for it before using it.

```systemverilog
// snippet: publish, wait, then use
process worker;                     // declared where the parent can read it

initial begin
  fork
    begin
      worker = process::self();     // the child's first statement
      // the child's work
    end
  join_none
  wait (worker != null);            // the child starts only once this process blocks
  // worker.status(), worker.await() and worker.kill() are safe from here on
end
```

**Pitfalls.**

- **`process p = process::self();` inside an `initial` block does not compile.** Variables declared in a module's `initial` block are static, and a static declaration with an initializer there needs an explicit `static` or `automatic` (§6.21). Declare `process p;` and assign it as a statement. An `automatic` local would compile, but the parent could not read it.
- **Using the handle too early.** Right after `fork … join_none` the child has not run yet (§9.3.2), so the handle is still `null` and `p.kill()` is a null-handle access. Always `wait (p != null)` first.
- **Expecting `kill()` to clean up.** It ends threads. It does not return their keys, finish a half-driven transfer or take back what they put into a mailbox. Restore that state yourself after a kill.
- **Calling `await()` on yourself.** It is an error, because a process cannot wait for its own end (§9.7).
- **Reaching for `disable fork` when you meant one thread.** `disable fork` also kills every other thread the caller forked; `kill()` on the right handle does not.

**Debugging.** A null-handle access at `p.status()` or `p.kill()` means that the parent did not wait for the child to publish its handle. Keys that never come back after a timeout mean that the killed thread was holding them. And a thread that ended normally while `kill()` was running reads `FINISHED`, not `KILLED`, because the two can race (§9.7), so treat both as "terminated".

**In a real bench.** A watchdog reads `status()` to report which threads are stuck. A per-transaction timeout can kill only its own helper thread instead of calling `disable fork`. A reset handler can stop a driver's thread and then restore the keys it held. In UVM, phases and objections decide when most threads end ([I-UVM-1C: UVM Phasing](/curriculum/T2_Intermediate/I-UVM-1C_UVM_Phasing/index)), so raw handles appear mainly in drivers, monitors and timeouts.

### Deadlock, lost wake-ups and starvation: read the wait-for graph

When a bench stops making progress, list every blocked thread and ask two questions about each one: **what is it blocked on**, and **who could release it**? Then draw a **wait-for graph**:

1. Draw each blocked thread, and each resource it waits for: a semaphore, a mailbox or an event.
2. Draw an arrow from each thread to the resource it waits for.
3. Draw an arrow from each resource to the thread that would have to act: the holder of the key, the only thread that puts into the mailbox, or the thread that triggers the event.

Here is the opposite-order deadlock from F2D's first look, redrawn this way.

```systemverilog
// snippet: two threads take two semaphores in opposite orders
semaphore s1 = new(1), s2 = new(1);

initial begin : proc_a
  s1.get(1);
  #5 s2.get(1);                     // proc_b holds s2
  s2.put(1);
  s1.put(1);
end

initial begin : proc_b
  s2.get(1);
  #5 s1.get(1);                     // proc_a holds s1
  s1.put(1);
  s2.put(1);
end
```

**Predict before you look at the graph:** at 5 ns, which key does each process hold, and which key does it wait for? Draw the four arrows yourself, then compare.

Now read the graph's **shape**. Each shape names a different bug and points to a different fix.

| Shape of the graph | Name | What happened | Fix |
|---|---|---|---|
| The arrows close into a loop | **Deadlock** | Each thread on the loop holds what the next one needs | One global acquisition order; never hold a key while you wait for another thread |
| An arrow ends at a thread that has finished, has been killed, or has already done what you wait for | **Lost wake-up** or **leaked key** | The release was skipped, or it happened before the wait began | One exit point that always releases; restore keys after a kill; wait on something that remembers |
| No loop, and the releaser is alive and running, but the waiter keeps losing | **Starvation** | An unfair policy passes the waiter over again and again | Round-robin or aging; block instead of polling |
| Threads keep running, but nothing completes | **Livelock**, or a zero-delay loop | Threads retry or spin forever | Randomized back-off; make every loop iteration wait for something |

**Why deadlock happens.** Four conditions must all hold at once (Coffman, Elphick and Shoshani, 1971):

- **mutual exclusion**: a key can be held by only one thread;
- **hold and wait**: a thread holds one key while it waits for another;
- **no preemption**: nothing takes a key back from its holder;
- **circular wait**: the loop in the graph.

Break any one of them and deadlock is impossible. In a bench you usually break one of the last three:

- **A lock order breaks circular wait.** Rank every shared resource, and make every thread acquire in rising rank. Here, both threads take `s1` first, then `s2`.
- **Releasing before you wait breaks hold and wait.** Return a key before you wait for a reply, an event or anything else another thread must produce. When the resources are interchangeable, take them all at once with `get(n)` on one counting semaphore, which waits until n keys are free together (§15.3.3).
- **Release and retry** gives up instead of waiting. `try_get()` the second key, and if it returns 0, put back the first key, wait a random delay and try again. If both threads back off by the same delay, they can collide forever (livelock), so randomize the delay.

**A timeout detects a hang; it does not cure it.** It turns a silent hang into a reported failure:

```systemverilog
// snippet: wait for a reply, but give up after budget_ns
task automatic get_reply(input int id, input int unsigned budget_ns,
                         output int rsp, output bit ok);
  ok = 0;
  fork begin                        // own parent: disable fork stays inside
    fork
      begin
        rsp_mbx[id].get(rsp);
        ok = 1;
      end
      #(budget_ns);                 // the budget runs out
    join_any
    disable fork;                   // stop the loser: the timer or the blocked get()
  end join
endtask
```

The cause is still there after the timeout fires, and whatever the timed-out thread holds stays held. If it holds a key, return the key in the timeout path, or the next `get()` hangs instead. A reply that arrives in the same time slot as the deadline races with the timer (§4.7), so give budgets a wide margin.

**Starvation has no loop.** The bench makes progress, but one waiting thread is passed over again and again. A common cause is a server that always looks at its high-priority queue first. Suppose a responder serves one request every 10 ns, a fast producer adds a new request H*k* to `hi_mbx` at `10k − 5` ns, and `lo_mbx` has held one request, L0, since 0 ns:

| Service at | "hi first" serves | L0 still waiting? | Round-robin serves | L0 still waiting? |
|---|---|---|---|---|
| 10 ns | H1 | yes | H1 (hi's turn) | yes |
| 20 ns | H2 | yes | L0 (lo's turn) | no |
| 30 ns | H3 | yes | H2 | no |
| 40 ns | H4 | yes | H3 | no |

With "hi first", L0 waits for as long as the fast producer runs. There are other causes too:

- A thread that polls with `try_get()` while other threads wait in `get()` can keep losing. Each returned key lets a waiting `get()` proceed (§15.3.2), so the poller finds a key free only if it happens to look while nobody is queued.
- A multi-key request can be overtaken by smaller ones if your simulator lets later requests go first. The standard does not say whether it may, so this is tool-dependent.

The fix is fairer arbitration, never a lock order.

**Triage a stuck bench by its symptom.** Whatever the shape, the run either ends early with no error, because nothing is left to do (§9.6.1), or hangs until a watchdog or a time limit stops it, because a clock keeps time moving. Then use the symptom:

| Symptom in the log or the watchdog report | Shape | Usual cause | Confirm and fix | Deep dive |
|---|---|---|---|---|
| A thread stuck in `@ev`; the trigger's own line printed earlier in the same time slot, or before the wait began | Arrow to an event that already fired | `->` ran before `@` | Print `$time` before the wait and at the trigger. Wait on `ev.triggered` (same time slot only), or carry the fact in a mailbox, a 0-key semaphore or a flag | [Events](/curriculum/T2_Intermediate/I-SV-5_Synchronization_and_IPC/events) |
| Threads stuck in `get()` on one semaphore; the recorded owner is a call that has returned, or a killed thread | Arrow to a dead holder | An early `return`, a `disable` or a `kill()` skipped `put()` | Count the gets and puts on every path. Use one exit point, and put keys back after a kill | [Semaphores](/curriculum/T2_Intermediate/I-SV-5_Synchronization_and_IPC/semaphores) and the lab below |
| Two or more threads stuck, each holding what the next needs | Loop | Opposite acquisition orders, or a key held while waiting for a reply | Draw the graph from the report. Use one global order, and release before you wait | Make It Work below |
| A consumer stuck in `get()` on an empty mailbox while its producer is `FINISHED` or `KILLED` | Arrow to a dead producer | Fewer items were sent than expected, or the producer was killed | Count items on both sides, and agree on a count or an end marker | [Mailboxes](/curriculum/T2_Intermediate/I-SV-5_Synchronization_and_IPC/mailboxes) |
| A producer stuck in `put()` on a full bounded mailbox | Arrow to a stuck consumer, often part of a loop | The consumer is itself waiting for the producer, as in a burst of requests | Collect replies in their own thread, or size the channel for the burst | The kata below |
| Time stops advancing, a line repeats, memory grows | No graph: a zero-delay loop | `forever wait (ev.triggered)`, or a `forever` producer feeding an unbounded mailbox with no delay | Make every loop iteration wait for something | [Events](/curriculum/T2_Intermediate/I-SV-5_Synchronization_and_IPC/events) |
| Every thread progresses except one | No loop, live releaser | Fixed priority, or polling against blocked waiters | Round-robin, aging, or blocking instead of polling | This page |

### Recap

- A thread can never assume that another has already run. Make the order true with a tool that blocks the waiter.
- Choose by what must pass: data in order is a mailbox (a TLM FIFO between UVM components), a turn or a count is a semaphore, control of one thread is a `process` handle, and only "it happened" is an event.
- Producer/consumer, request/response and arbitration cover almost every coordination. Route replies, and never hold a key while you wait for another thread.
- Capture a handle as the child's first statement, and wait for it before you use it. `kill()` ends a thread and everything it forked, but gives back nothing that it held.
- A stuck bench is a graph. A loop is a deadlock, an arrow to a dead thread is a lost wake-up or a leak, and no loop with a waiter that keeps losing is starvation.

## Make It Work

### A request/response bench with a watchdog that names the stuck thread

This bench combines the three patterns and the `process` handle. Two requesters share one bus with a responder. Each requester takes the bus key, puts one request into `req_mbx`, drives it for 4 ns, returns the key, and only then waits for its reply on its own mailbox. The responder takes each request, needs the bus for 2 ns to send the reply, and puts the reply on the requester's mailbox. `main` waits for both requesters with `await()`, and a watchdog reports and cleans up if they never finish.

```systemverilog
// compile
module tb_top;
  timeunit 1ns; timeprecision 1ns;

  semaphore      bus     = new(1);  // arbitration: one key, so one bus owner at a time
  mailbox #(int) req_mbx = new(2);  // producer/consumer: at most 2 requests wait here
  mailbox #(int) rsp_mbx[2];        // request/response: one reply mailbox per requester

  process worker[3];                // 0 and 1: requesters; 2: responder
  string  doing[3];                 // what each thread is blocked on, for the watchdog
  string  bus_owner = "nobody";     // a semaphore does not record who holds its key
  int     replies, fails;

  task automatic take_bus(int me, string who);
    doing[me] = "bus.get";
    bus.get(1);
    bus_owner = who;
    $display("[%0t] %s owns the bus", $time, who);
  endtask

  task automatic give_bus();
    bus_owner = "nobody";
    bus.put(1);
  endtask

  // Sends one request, then waits for the matching reply on its own mailbox.
  task automatic requester(int id, int unsigned start_ns);
    string me = $sformatf("requester %0d", id);
    int rsp;
    worker[id] = process::self();           // publish the handle first
    #(start_ns);                            // staggered start: see the notes below
    take_bus(id, me);
    req_mbx.put(10 * id);                   // the request names its sender
    #4;                                     // drive the request on the bus
    give_bus();                             // release the key BEFORE waiting
    doing[id] = "rsp_mbx.get";
    rsp_mbx[id].get(rsp);
    $display("[%0t] %s got reply %0d", $time, me, rsp);
    if (rsp == 10 * id + 100) replies++;
    else fails++;
    doing[id] = "finished";
  endtask

  // Serves requests in arrival order; it needs the bus to send each reply.
  task automatic responder();
    int req;
    worker[2] = process::self();
    forever begin
      doing[2] = "req_mbx.get";
      req_mbx.get(req);
      take_bus(2, "responder");
      #2;                                   // drive the reply on the bus
      give_bus();
      rsp_mbx[req / 10].put(req + 100);     // route the reply to its requester
    end
  endtask

  initial begin : main
    foreach (rsp_mbx[i]) rsp_mbx[i] = new(1);
    fork
      requester(0, 1);
      requester(1, 9);
      responder();
    join_none
    foreach (worker[i]) wait (worker[i] != null);  // children run once main blocks
    worker[0].await();                      // the responder never ends: await requesters
    worker[1].await();
    $display("[%0t] PASS=%0d FAIL=%0d", $time, replies, fails);
    if (fails != 0) $fatal(1, "test failed");
    $finish;
  end

  initial begin : watchdog
    process::state s;
    #100;
    fails++;                                // reaching the deadline is a failure
    $display("[%0t] WATCHDOG: no result after 100 ns, bus owner: %s", $time, bus_owner);
    foreach (worker[i]) begin
      s = worker[i].status();
      $display("[%0t]   worker %0d is %s in %s", $time, i, s.name(), doing[i]);
    end
    foreach (worker[i])                     // releases main's await() calls
      if (worker[i].status() != process::FINISHED) worker[i].kill();
  end
endmodule
```

**Run it.** Save the code as `tb_top.sv` and run it with `tb_top` as the top module on any simulator that supports IEEE 1800-2023 semaphores, mailboxes and the `process` class. No library is needed. Support for the `process` methods in open-source simulators varies, so check your tool's documentation first.

**Expected output** (illustrative: traced by hand from §9.3.2, §9.7, §15.3 and §15.4, not captured from a simulator; your simulator then prints its own `$finish` message):

```text
[1] requester 0 owns the bus
[5] responder owns the bus
[7] requester 0 got reply 100
[9] requester 1 owns the bus
[13] responder owns the bus
[15] requester 1 got reply 110
[15] PASS=2 FAIL=0
```

Why each line is where it is:

- At 1 ns requester 0 takes the free key and sends request 0. The responder takes the request at once, then blocks in `bus.get(1)`.
- At 5 ns requester 0 returns the key. A process waiting for a key proceeds once enough keys are returned (§15.3.2), so the responder's `bus.get(1)` returns. Requester 0 then blocks in `rsp_mbx[0].get()`.
- At 7 ns the responder returns the key and puts reply 100, which wakes requester 0.
- Requester 1 starts at 9 ns, when the bus is free, and repeats the round trip. The staggered start is deliberate. Two `bus.get(1)` calls in the same time slot reach the semaphore's queue in an order that the standard leaves open (§4.7, §15.3.3), so the log could differ between simulators.

**How to build a bench like this:**

1. Name every thread and every shared object, and give each object one job: `req_mbx` carries requests, `rsp_mbx[id]` carries one requester's replies, and the `bus` key says who may drive.
2. Publish each thread's handle as its first statement, and wait for the handles before you use them.
3. Keep critical sections short: take the key, drive, return the key, and only then wait for anything else.
4. Record the debug state that the tools do not keep for you: what each thread is blocked on (`doing`) and who holds the key (`bus_owner`).
5. End the test from a thread that awaits the threads that must finish. Give the run a watchdog that reports each thread's status, kills the stuck ones and counts a failure.
6. Print one summary line, and fail the run with `$fatal` when anything failed.

### Break it: hold the bus while you wait

Move the release of the bus key below the reply wait in `requester`:

```systemverilog
// snippet: replaces the lines from "#4;" to the reply get() in requester
    #4;                                     // drive the request on the bus
    doing[id] = "rsp_mbx.get (holding the bus)";
    rsp_mbx[id].get(rsp);                   // waits for a reply that needs the bus
    give_bus();                             // BUG: key returned only after the reply
```

**Predict before you read on:** which threads finish, and what does the watchdog print at 100 ns?

**Expected output** (illustrative, as above; your simulator then prints its own `$fatal` message, "test failed"):

**Checklist before moving on:**

- [ ] Each shared object has one job, and its name says what it carries.
- [ ] No thread holds a key while it waits for a reply, an event or a key of lower rank.
- [ ] Every path out of a critical section returns the key.
- [ ] Every handle is published as its thread's first statement, and waited for before use.
- [ ] A watchdog reports what each thread is blocked on and fails the test, and the run ends with a `PASS=… FAIL=…` line.
- [ ] From the broken run's watchdog report alone, you can draw its wait-for graph.

## Push Further

### Expert: kill(), await() and suspend() corner cases

- `kill()` ends the target and all its descendants before it returns, but the target may finish normally while `kill()` runs (§9.7, citing §4.7). Read the result as "terminated": `FINISHED` or `KILLED`.
- Calling `kill()` on a process that is already `FINISHED` or `KILLED` still kills its live descendants (§9.7). That is a quick way to clean up everything a finished thread left running.
- `await()` returns when the process ends normally or is killed, and calling it on the current process is an error (§9.7).
- `suspend()` on a waiting process desensitizes it to the event, wait condition or delay it is blocked on (§9.7). After `resume()`, a `wait` condition that is now true, or a delay that has expired, lets it continue at once, but an event trigger that happened while it was suspended is not seen.
- A function may kill, suspend or resume another process, or kill its own (§13.4, rule c), but it may not suspend its own process (§9.7). `await()` is a task, so a function cannot call it.
- `kill()`, `await()`, `suspend()` and `resume()` are restricted to processes created by an `initial` procedure, an `always` procedure or a `fork` block in one of them (§9.7).
- `status()` also reads `KILLED` after a `disable` (§9.7).

### Expert: a deadlocked bench can end quietly

- Simulation automatically terminates when there is no further activity of any kind (§9.6.1). When every thread is blocked and nothing is scheduled, the run ends at the time of the last activity, with no message.
- A free-running clock or a watchdog timer keeps time moving, so the same bug becomes a hang that lasts until the watchdog or a tool limit stops it.
- If the bench uses `program` blocks, simulation also ends when all of them finish, whatever their child processes are doing (§9.6.1). A deadlocked child of a program is abandoned silently.
- So "no errors in the log" is not a pass. End every test with one summary line, and make the watchdog call `$fatal`, which ends the run with an error code (§20.10). Make your regression scripts treat a missing summary line as a failure; how depends on your scripts and simulator (tool-dependent).

### Expert: choosing disable fork, disable by name or kill() in reusable code

Consider a per-transaction timeout in a driver task that several threads may call at once:

- `disable fork` follows the dynamic process tree: it kills every descendant of the caller, including threads forked long before (§9.6.3). Use it only inside an isolation wrapper, `fork begin … end join`.
- `disable` with a block or task name uses the static name: it ends every process executing that block, including other threads' calls of the same task (§9.6.2, §9.6.3). Avoid it in reusable code.
- `kill()` on a captured handle ends exactly one thread and its descendants (§9.7). It is the most precise tool, at the cost of publishing the handle first.

### Expert: deadlock theory and the SystemVerilog traps

- **With counting semaphores, a loop is necessary but not sufficient.** When a resource has several keys, a thread outside the loop may return one and break it. With one key per resource, a loop is a deadlock. This is general concurrency theory (Coffman, Elphick and Shoshani, 1971), not a SystemVerilog rule.
- **Latent deadlock.** Put two `get()` calls with no delay between them, in opposite orders, in two threads. Simulators usually run a thread until it blocks, so each thread takes both keys in one go and the code passes. But §4.7 lets a simulator suspend a process between statements, so a conforming simulator may deadlock on the same code. "It passed on every simulator we tried" proves nothing: fix the order.
- **Self-deadlock.** A semaphore has no owner, so a thread that calls `get(1)` on a one-key semaphore whose key it already holds blocks forever, and nothing reports it (§15.3.3). Part 1 of the lab ends this way after a leak.
- **Mixed loops.** A loop can run through different tools. In Make It Work it runs from a thread through a mailbox to the responder, and through a semaphore back again. The method is the same: follow "waits for" to the resource, then "only released by" to the thread.

### Expert: fairness, what the standard guarantees and what it leaves open

- **Guaranteed.** Semaphore waiters (§15.3.3) and mailbox `get()` waiters (§15.4.5) are served first-in first-out, in the order in which they arrived. When a `put()` returns enough keys, a waiting process proceeds (§15.3.2).
- **Not guaranteed.** Both clauses say that FIFO does not guarantee the order in which processes arrive at the queue, and processes that call `get()` in the same time slot run in any order (§4.7). The order in which blocked `put()` callers of a full mailbox resume is not stated (§15.4.3). Nor does the standard say whether a later, smaller multi-key request may be served before a blocked larger one, so that is tool-dependent. The course's visualizers make one documented choice, and simulators may differ.
- **Consequence.** Build the fairness you rely on into your own code: round-robin or aging in servers, and for multi-key requests a one-key "gate" in front of the counting semaphore, `gate.get(1); credits.get(n); gate.put(1);`. Requests then take their credits strictly in arrival order. The price is head-of-line blocking, and the gate is deadlock-free only if no thread asks for more credits while it already holds some, so take everything you need in one `get(n)`.

### Expert: debug threads change the random stream

- Each thread has its own random-number generator. A thread created by `fork` is seeded with the next random value from its parent's generator, which the standard calls hierarchical seeding (§18.14.1). That is why `$urandom` values in one thread do not depend on the order in which threads run (§18.14.2).
- The catch: creating a thread consumes the next value from its parent's generator. Add a debug thread before the others, and every thread forked after it gets a different seed, so a seed-dependent hang can vanish when you add instrumentation.
- Pin the stream of a thread that must stay reproducible by seeding it at its start: `p = process::self(); p.srandom(seed);` (§18.13.3, §9.7). Add new debug threads after the threads whose behaviour you want to keep, as §18.14.1 advises for any new thread.

### Expert: from these tools to UVM

- `uvm_tlm_fifo #(T)` holds a `local mailbox #(T)`, and its constructor's `size` argument defaults to 1. `uvm_tlm_analysis_fifo` passes size 0, so it is unbounded, and its `write()` calls `try_put()`, which therefore always succeeds (uvm-core 2020.3.1 `src/tlm1/uvm_tlm_fifos.svh`; IEEE 1800.2-2020 §12.2.8.2–§12.2.8.3). See [I-UVM-2B: TLM Connections](/curriculum/T2_Intermediate/I-UVM-2B_TLM_Connections/index).
- `uvm_event` keeps an "on" state that `trigger()` sets and `reset()` clears. Its `wait_trigger()` is a plain `@` on the underlying event, so it has the same race as `@ev` when trigger and wait share a time slot. `wait_ptrigger()` (the `.triggered` form) and `wait_on()` avoid it (uvm-core 2020.3.1 `src/base/uvm_event.svh`; IEEE 1800.2-2020 §10.1). See [I-UVM-1C: UVM Phasing](/curriculum/T2_Intermediate/I-UVM-1C_UVM_Phasing/index).
- Several sequences share one driver through the sequencer's arbitration, and `lock()` or `grab()` gives one sequence exclusive access (IEEE 1800.2-2020 §14.2.5.5–§14.2.5.6). See [I-UVM-3B: Sequence Arbitration](/curriculum/T2_Intermediate/I-UVM-3B_Advanced_Sequencing_and_Layering/sequence-arbitration).
- Objections, not a watchdog alone, decide when a UVM test ends ([I-UVM-1C](/curriculum/T2_Intermediate/I-UVM-1C_UVM_Phasing/index)).

### Kata: the burst that never finishes

**Goal:** predict a deadlock between two bounded mailboxes, draw its wait-for graph, and fix it without making either mailbox bigger.

```systemverilog
// compile
module tb_top;
  timeunit 1ns; timeprecision 1ns;

  mailbox #(int) req_mbx = new(1);
  mailbox #(int) rsp_mbx = new(1);

  // Sends a burst of four requests, then collects the four replies.
  task automatic requester();
    int rsp, fails;
    for (int n = 0; n < 4; n++) req_mbx.put(n);
    for (int n = 0; n < 4; n++) begin
      rsp_mbx.get(rsp);
      $display("[%0t] reply %0d", $time, rsp);
      if (rsp != n + 100) fails++;
    end
    $display("[%0t] PASS=%0d FAIL=%0d", $time, 4 - fails, fails);
  endtask

  task automatic responder();
    int req;
    forever begin
      req_mbx.get(req);
      #2;                                   // work on the request
      rsp_mbx.put(req + 100);
    end
  endtask

  initial begin
    fork
      requester();
      responder();
    join_none
  end
endmodule
```

1. **Predict:** what does the run print, and when does it end?
2. **Draw** the wait-for graph at the moment the bench stops.
3. **Fix** it so that all four replies arrive, without changing either `new(1)`.
4. **Explain** why `new(2)` on both mailboxes would only move the problem.

<details>
<summary>Worked solution</summary>

**1. Prediction.** Nothing prints, and the run ends quietly at 4 ns. (Illustrative: traced by hand from §15.4.3 and §15.4.5.)

- At 0 ns the responder takes request 0, so request 1 fits in `req_mbx`; the requester then blocks trying to put request 2.
- At 2 ns the responder puts reply 100, which fills `rsp_mbx`, and takes request 1, which lets request 2 in. The requester now blocks trying to put request 3.
- At 4 ns the responder tries to put reply 101 into the full `rsp_mbx`, and blocks. Nobody can move and nothing is scheduled, so simulation ends (§9.6.1). The requester never reached its reply loop, so no line printed.

**2. Wait-for graph.** The requester waits in `put()` on the full `req_mbx`, which only the responder empties. The responder waits in `put()` on the full `rsp_mbx`, which only the requester empties. Requester → `req_mbx` → responder → `rsp_mbx` → requester: a loop, so a deadlock between two bounded channels.

**3. Fix.** Collect the replies in their own thread, so that sending and receiving overlap:

```systemverilog
// snippet: requester() with a separate reply collector
  task automatic requester();
    int rsp, fails;
    fork
      for (int n = 0; n < 4; n++) req_mbx.put(n);      // sender
      for (int n = 0; n < 4; n++) begin                // collector
        rsp_mbx.get(rsp);
        $display("[%0t] reply %0d", $time, rsp);
        if (rsp != n + 100) fails++;
      end
    join
    $display("[%0t] PASS=%0d FAIL=%0d", $time, 4 - fails, fails);
  endtask
```

Expected output (illustrative, traced as above):

```text
[2] reply 100
[4] reply 101
[6] reply 102
[8] reply 103
[8] PASS=4 FAIL=0
```

An unbounded `rsp_mbx` would also remove the loop, because the responder could never block on it, but memory then grows with the size of the burst.

**4. Bigger mailboxes only move the limit.** The pair can absorb one queued request, one request in service and one queued reply. A burst larger than that deadlocks. With `new(2)` on both mailboxes, a burst of five passes and a burst of six deadlocks again. Splitting sending from receiving removes the loop for any burst size.

</details>
