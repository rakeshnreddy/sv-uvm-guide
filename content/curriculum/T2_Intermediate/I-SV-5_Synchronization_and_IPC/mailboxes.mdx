## Quick Take

- **What it is:** A **mailbox** is a built-in SystemVerilog class that passes messages from one process to another in first-in, first-out (FIFO) order (IEEE 1800-2023 §15.4, §15.4.3). `put()` adds a message and `get()` removes the oldest one. Both calls suspend the calling process when they cannot complete: `get()` while the mailbox is empty, and `put()` while a **bounded** mailbox is full.
- **Why it matters:** A class-based testbench is a set of threads that run at different speeds: a generator, a driver, a monitor and a scoreboard. Mailboxes are the channels between them. Choose the wrong depth and the generator races ahead, or the monitor stalls and misses bus traffic. Put one object into a mailbox twice and the driver sends repeated data that still looks plausible in the log.
- **The Analogy:** An in-tray with N slots on a colleague's desk. You drop forms in and your colleague takes the oldest one out; when the tray is full you wait, and when it is empty they wait. *Where it breaks:* a mailbox of class handles holds references to forms, not photocopies, so if you keep editing a form after dropping it in, your colleague reads your latest edits. And an unbounded tray, made with `new()`, never fills, so nobody ever waits for room.

**You will be able to:**
1. Predict when `put()`, `get()`, `peek()` and their `try_` forms wait, and what each `try_` call returns, for empty, full, bounded and unbounded mailboxes.
2. Choose the type and the depth of each testbench channel (typed or typeless, bounded or unbounded), and say when a UVM `uvm_tlm_fifo` replaces a mailbox.
3. Write a generator → bounded, typed mailbox → driver pipeline with backpressure, plus a monitor → scoreboard path that never blocks the monitor.
4. Debug the shared-handle bug, where queued messages show repeated or later values, and fix it with a new object or a copy per message.

## Build Your Mental Model

### Why threads need a mailbox

A class-based testbench starts its components as separate processes, usually with `fork … join_none` ([F2C](/curriculum/T1_Foundational/F2C_Procedural_Code_and_Flow_Control/index)). A **generator** creates transactions, a **driver** turns each one into pin activity, a **monitor** turns pin activity back into transactions, and a **scoreboard** checks them. These processes run at different speeds. The driver can take the next transaction only when the bus is free, and the scoreboard can check only what the monitor has seen.

Without a channel you would share a queue and poll it, for example with `while (q.size() == 0) #1;`. Polling wakes the consumer every interval even when there is nothing to do, delays every hand-off by up to one interval, and gives you no way to slow a fast producer down. A mailbox fixes all three. A consumer that calls `get()` on an empty mailbox is suspended and resumes by itself when a message arrives. A producer that calls `put()` on a full bounded mailbox is suspended until there is room. That automatic slowing of the producer is called **backpressure**.

Read the picture top to bottom:

- Messages enter at the tail and leave from the head in strict FIFO order (§15.4.3). The next `get()` takes `t0`.
- A **bounded** mailbox, created with `new(N)`, is full when it holds N messages. Then `put()` suspends the caller until a `get()` frees a slot (§15.4, §15.4.3).
- An **unbounded** mailbox, created with `new()`, is never full, so `put()` never waits (§15.4.1).
- `get()` and `peek()` suspend the caller while the mailbox is empty (§15.4.5, §15.4.7).
- A suspended process resumes **by itself**, in the time slot where room or a message appears. Nobody polls.

### Your first mailbox: predict, then watch

This complete example has one producer and one consumer. The consumer takes a message every 10 ns; the producer tries to send four at once.

```systemverilog
// compile
module tb_top;
  timeunit 1ns; timeprecision 1ns;

  mailbox #(int) mbx = new(2);          // bounded: at most 2 messages wait inside

  initial begin : producer
    for (int i = 0; i < 4; i++) begin
      mbx.put(i);                       // waits while mbx already holds 2 messages
      $display("[%0t] sent %0d", $time, i);
    end
  end

  initial begin : consumer
    int v;
    repeat (4) begin
      #10 mbx.get(v);                   // waits while mbx is empty
      $display("[%0t] got %0d", $time, v);
    end
  end
endmodule
```

**Predict before you look:** at what time does the producer print `sent 2`? Write your answer down. Then predict again for `new(1)` and for `new()`.

**What the runs showed:**

- With `new(2)`, messages 0 and 1 fill the mailbox at 0 ns and `put(2)` suspends the producer. The consumer's first `get()` at 10 ns frees a slot, and the producer resumes by itself in the same time slot: `sent 2` prints at 10 ns (§15.4.3).
- With `new(1)`, every `put()` waits for the previous message to be taken: `sent 1` prints at 10 ns and `sent 2` at 20 ns.
- With `new()`, `put()` never waits. All four `sent` lines print at 0 ns, and the messages pile up until the consumer drains them (§15.4.1).
- Now use the sandbox under the scripted run. Make **consumer 1** and then **consumer 2** call `get(v)` on the empty mailbox, then click `put(1)`: consumer 1, the first to wait, receives the message (§15.4.5). Repeat with `peek(v)`: the message is copied and stays in the mailbox.

### Every method, and exactly what it returns

A mailbox has eight methods, declared in Annex G.4 of the standard. The three tasks can wait; the functions never do.

| Method (Annex G.4) | Waits? | What it returns or does |
|---|---|---|
| `task put(T message)` | while a bounded mailbox is full; never if unbounded | adds the message at the tail (§15.4.3) |
| `function int try_put(T message)` | never | a positive integer when the message was stored; 0 when the mailbox was full and nothing was stored (§15.4.4) |
| `task get(ref T message)` | while the mailbox is empty | removes the oldest message into the variable; in a typeless mailbox, a type mismatch is a run-time error (§15.4.5) |
| `function int try_get(ref T message)` | never | positive: the oldest message was removed into the variable; 0: empty; negative: type mismatch, nothing removed (§15.4.6) |
| `task peek(ref T message)` | while the mailbox is empty | copies the oldest message into the variable and leaves it queued; type mismatch: run-time error (§15.4.7) |
| `function int try_peek(ref T message)` | never | positive: copied; 0: empty; negative: type mismatch (§15.4.8) |
| `function int num()` | never | the number of messages right now, valid only until the next `put()` or `get()` by any process (§15.4.2) |
| `function new(int bound = 0)` | never | creates the mailbox: bound 0, the default, is unbounded; a positive bound is the capacity; a negative bound is illegal (§15.4.1) |

Three rules follow from the table:

- **Test a `try_` result with `> 0`.** The standard promises a positive integer on success, not the value 1, and a negative result is a failure that `if (m.try_get(v))` would take for success.
- **Nothing is ever overwritten.** No call replaces or drops a stored message. On a full mailbox, `put()` waits and `try_put()` returns 0.
- **Inside a function, only the functions are available.** A function cannot call a task (§13.4), so function code can use `try_put()`, `try_get()`, `try_peek()` and `num()`, but not `put()`, `get()` or `peek()`. You will meet this in UVM, where an analysis `write()` method is a function.

### A mailbox carries handles, not objects

A message can be any **singular** value, meaning one value or one handle: an `int`, a packed struct or, most often, a class handle (§15.4.3). For a class, `put(t)` stores a copy of the **handle** held in `t`, not a copy of the object it refers to (§8.12). If the producer reuses one object, every queued message refers to that one object, and the consumer reads whatever the producer wrote last.

```systemverilog
// compile
module tb_top;
  timeunit 1ns; timeprecision 1ns;

  class txn;
    int unsigned id;
    bit [7:0]    data;
  endclass

  mailbox #(txn) gen2drv = new();       // unbounded: all three puts finish at 0 ns

  initial begin : generator
    txn t;
    t = new();                          // BUG: one object for all three messages
    for (int i = 0; i < 3; i++) begin
      t.id   = i;
      t.data = 8'hA0 + 8'(i);
      gen2drv.put(t);                   // queues a copy of the handle, not of the object
    end
  end

  initial begin : driver
    txn d;
    #1;                                 // let the generator finish first, so the output
                                        // does not depend on process order
    repeat (3) begin
      gen2drv.get(d);
      $display("drv got id=%0d data=%h", d.id, d.data);
    end
  end
endmodule
```

**Expected output** (illustrative):

```text
drv got id=2 data=a2
drv got id=2 data=a2
drv got id=2 data=a2
```

The trace shows why. `txn@1` names the first `txn` object created, as in the I-SV-1 handle visualizer.

| After this step | `t` refers to | `txn@1` holds | Messages queued in `gen2drv` |
|---|---|---|---|
| `t = new();` | `txn@1` | id=0, data=00 | none |
| i = 0: write the fields, `put(t)` | `txn@1` | id=0, data=a0 | `txn@1` |
| i = 1: write the fields, `put(t)` | `txn@1` | id=1, data=a1 | `txn@1`, `txn@1` |
| i = 2: write the fields, `put(t)` | `txn@1` | id=2, data=a2 | `txn@1`, `txn@1`, `txn@1` |
| at 1 ns: three `get(d)` calls | | id=2, data=a2 | each `get()` returns `txn@1` |

**The fix:** create the object inside the loop, so that each message refers to its own object. The driver then prints ids 0, 1 and 2 with data a0, a1 and a2.

```systemverilog
// snippet: the generator loop above, fixed
for (int i = 0; i < 3; i++) begin
  t      = new();                       // one object per message
  t.id   = i;
  t.data = 8'hA0 + 8'(i);
  gen2drv.put(t);
end
```

If a producer must keep its own object, for example a template it edits between items, put a copy instead. `c = new t;` makes a shallow copy (§8.12), which is enough when the class holds only values; a class with nested handles needs a deep copy ([I-SV-1: Copying and Cloning](/curriculum/T2_Intermediate/I-SV-1_OOP/copying-and-cloning)).

The same bug runs the other way. A consumer that keeps a received handle, such as a scoreboard that stores expected items, sees every later change made through another handle to that object. The rule for every channel is: **producers send a new object for each message, and consumers that keep a message copy it first.** The [I-SV-1 module page](/curriculum/T2_Intermediate/I-SV-1_OOP/index) has a debugging challenge with the queue version of this bug.

That is the core of mailboxes. The rest of this section is practitioner depth: the depth and type of each channel, the ordering guarantees, the UVM equivalent, and debugging.

### Bounded or unbounded: where backpressure belongs

`new()` and `new(0)` create an unbounded mailbox; `new(N)` with a positive N holds at most N messages (§15.4.1). A mailbox variable is a class handle, so it is `null` until `new` runs. Calling a mailbox method through a null handle is illegal, its result is indeterminate, and simulators may report a null-object error at that line (§8.4).

The right depth depends on the direction of the channel:

| Channel | Depth | Why |
|---|---|---|
| generator → driver | bounded and small, `new(1)` or `new(2)` | Backpressure: the generator stays one or two items ahead of the driver, so it never floods memory and creates each item close to the time it is driven. |
| monitor → scoreboard | unbounded, `new()` | The bus does not wait. A monitor suspended in `put()` stops sampling and misses transactions. |
| generator or predictor → scoreboard (expected items) | unbounded, `new()` | Whoever produces the expected values must not stall behind a slow checker. |

Two traps:

- **Do not build your own backpressure** with `try_put()` plus `wait (mbx.num() < N)`. `put()` already waits for room (§15.4.3), and `num()` is only a snapshot (§15.4.2). Worse, the standard requires an expression that calls a method to be re-evaluated when data members that the method reads change (§9.4.2), but it does not describe a mailbox's internals, so whether such a wait ever wakes is tool-dependent.
- **An unbounded mailbox has no memory limit.** Queued handles keep their objects reachable, so the objects cannot be reclaimed while they wait (§8.29). A `forever` generator with no delay that feeds an unbounded mailbox never waits at all: it is a zero-delay loop, simulation time stops advancing, and whether the driver ever gets to run depends on the simulator (§4.7).

> [!TIP]
> Keep the bound in a named parameter, such as `GEN_DEPTH`. The mailbox has no method that reports its bound (Annex G.4), so the parameter is the only place your end-of-test checks and debug prints can read it from.

### Typed or typeless (§15.4.9)

A mailbox comes in two kinds:

- **Parameterized (typed):** `mailbox #(txn) m;` carries one type. The compiler checks that every argument of `put`, `try_put`, `get`, `try_get`, `peek` and `try_peek` has a type equivalent to `txn`, so mismatches are compile errors (§15.4.9).
- **Typeless:** `mailbox m;` is the default `mailbox #(dynamic_type)`. One mailbox can carry any singular type: it records the type of each message and checks it at run time (§15.4.5, §15.4.9).

The same calls behave differently in the two kinds. The variables are `int i = 5;`, `int x;` and `string s;`. Row 1 puts one message, and rows 2 to 4 are three separate alternatives, each starting with that message as the only one in the mailbox:

| Step | Typeless: `mailbox m = new();` | Typed: `mailbox #(int) m = new();` |
|---|---|---|
| `m.put(i);` | stores 5 and records its type, `int` (§15.4.5) | stores 5 |
| `m.get(s);` | compiles; a run-time error when the call executes (§15.4.5) | compile error: `s` is not an `int` (§15.4.9) |
| `r = m.try_get(s);` | compiles; `r` is negative and nothing is removed (§15.4.6) | compile error |
| `m.get(x);` | `x` becomes 5 | `x` becomes 5 |

The rows put an `int` variable on purpose. A typeless mailbox checks the type that `put()` recorded, so put a variable of the type your consumer reads. The standard calls an unsized decimal literal such as `5` a signed integer (§5.7.1) without naming its exact type, so do not rely on how a typeless mailbox records one.

Use typed mailboxes in testbench code. A typeless mailbox moves type errors from the compiler to the middle of a long run, and its negative `try_get()` results are easy to mistake for success. When one channel must carry several kinds of transaction, a typed `mailbox #(base_txn)` with a class hierarchy is clearer (Push Further shows how to read it back).

Every message must be **singular**: one value or one handle (§15.4.3). An unpacked struct, union or array is not singular (Annex P), so it cannot be a message. Send a class handle, the usual choice, or a packed struct. Whether a particular simulator rejects an unpacked struct is tool-dependent, so do not rely on either outcome.

### Who gets the next message?

- **One producer, one consumer:** messages come out in exactly the order they went in (§15.4.3).
- **Several producers:** messages are stored in the order in which their `put()` calls complete. Two producers that put in the same time slot are ordered by the scheduler, which the standard leaves open (§4.7), so the order can differ between simulators. If the consumer needs the source or the order, carry it in the transaction, as an id or a timestamp, or give each producer its own mailbox.
- **Several consumers waiting in `get()`:** the mailbox keeps waiting processes in the order they arrived, and the first to arrive receives the next message (§15.4.5). The standard does not say which of two `get()` calls in the same time slot arrives first. In the picture, `c1` has waited since 10 ns, so it is ahead of `c2`.
- **Each message goes to exactly one `get()`:** several consumers share the work; they do not each receive a copy. For broadcast, give each consumer its own mailbox, or in UVM use an analysis port ([I-UVM-2B](/curriculum/T2_Intermediate/I-UVM-2B_TLM_Connections/index)). Only `peek()` lets several processes see the same message, and for a class they all see the same handle.

Never let a result depend on which of several equal waiters is served first. If the order matters, make it explicit, with one mailbox per consumer or a single thread that hands out the work.

### Mailbox or `uvm_tlm_fifo`?

In UVM, components normally do not share mailbox handles. They talk through TLM ports, and the channel between a producer and a consumer is a `uvm_tlm_fifo`, a UVM component that wraps a mailbox. [I-UVM-2B](/curriculum/T2_Intermediate/I-UVM-2B_TLM_Connections/index) teaches the connections; this table shows how the two compare.

| | SystemVerilog `mailbox #(T)` | UVM `uvm_tlm_fifo #(T)` |
|---|---|---|
| What it is | a built-in class in the `std` package (§15.2) | a `uvm_component` that wraps a `mailbox #(T)` |
| Default depth | `new()` is unbounded | the constructor's `size` defaults to 1, so it is bounded; `size` 0 means unbounded |
| How the two ends reach it | both ends hold the same handle | each end connects a port to `put_export` or `get_peek_export` |
| Non-blocking calls return | `int`: positive, 0 or negative | `bit`: 1 or 0; `can_put()`, `can_get()` and `can_peek()` ask first |
| Inspecting it | `num()` | `used()`, `size()`, `is_empty()`, `is_full()` |
| Emptying it | no method; drain with `try_get()` | `flush()` |
| Watching its traffic | not built in | the `put_ap` and `get_ap` analysis ports publish every put and get |
| Monitor-side form | `new()` | `uvm_tlm_analysis_fifo #(T)`: unbounded, written through its `analysis_export` |

Sources: IEEE 1800.2-2020 §12.2.8.2 and §12.2.8.3; uvm-core 2020.3.1 `src/tlm1/uvm_tlm_fifos.svh` and `src/tlm1/uvm_tlm_fifo_base.svh`.

Use mailboxes in a plain SystemVerilog testbench, like this module's examples and the layered bench of [I-SV-9](/curriculum/T2_Intermediate/I-SV-9_Why_UVM/index). Between UVM components, use a TLM FIFO with a port on each side, so that neither component needs a handle to the other. A mailbox is still a reasonable choice between two threads inside one component. The trap when porting: a `uvm_tlm_fifo` built with default arguments holds one item, whereas `new()` gave you an unbounded mailbox.

### Failure modes: leaks and backpressure

Mailbox bugs show up as a hang, a quiet early end, repeated data or missed transactions. Find the row that matches your log.

| What you see | Likely cause | How to confirm | Fix |
|---|---|---|---|
| The driver repeats values or drives later items first; the scoreboard reports mismatches | One object queued several times: the shared handle | At the consumer, compare each handle with the previous one: `if (t == prev) $error(...)` | Create a new object per message, or put a copy |
| The log stops at one timestamp, memory grows, the driver is silent | A `forever` producer with no delay feeding an unbounded mailbox: a zero-delay loop | Time never advances in the log | Bound the mailbox, or pace the producer |
| The run ends quietly with fewer items than expected, or the watchdog fires | A consumer waits forever in `get()`: the producer finished or was killed, or the two ends hold different mailboxes | At the end, print `num()`; check that both ends hold the same handle, for example `gen.gen2drv == drv.gen2drv` | Create each mailbox once and pass the same handle to both ends; end the test on a count and add a watchdog |
| The producer is stuck in `put()`; the monitor misses bus transactions | A bounded mailbox whose consumer is slow, stopped or killed | The producer's last log line comes just before a `put()` | Unbounded mailboxes on observation paths; keep consumers alive |
| Two threads both stuck in `put()`, for example a requester and a responder; the run ends quietly or the watchdog fires | A loop of bounded mailboxes: each thread waits for room in a mailbox that only the other thread empties | Draw who waits for whom: each arrow leads to the thread that would have to call `get()` | Collect replies in their own thread, or size the mailboxes for the largest burst; the kata on the [module page](/curriculum/T2_Intermediate/I-SV-5_Synchronization_and_IPC/index) walks through one |
| A run-time type error at a `get()`, or `try_get()` returns a negative value | A typeless mailbox carrying another type | The error names the `get()` line | Use `mailbox #(T)` |
| A null-object error at the first `put()` or `get()` | The mailbox was declared but never created | The handle is `null` at that line | Call `new` before starting the threads |
| Memory grows steadily over a long test | An unbounded mailbox whose consumer fell behind or stopped; queued objects stay reachable (§8.29) | `num()` keeps rising | Find the stalled consumer; check `num() == 0` at the end of the test |

When every process is suspended and nothing else is scheduled, simulation simply ends (§9.6.1), often with no error, which can look like a pass. A free-running clock or a watchdog turns the same bug into a hang that the watchdog reports. That is why every test should end on a condition, print a summary line, and have a `$fatal` watchdog.

### Recap

- A mailbox is a FIFO channel between processes: `mailbox #(txn) m = new(N);` holds at most N messages, and `new()` is unbounded.
- `put()` waits only while a bounded mailbox is full; `get()` and `peek()` wait while it is empty; the `try_` functions never wait and return a positive value, 0 or, for `try_get()` and `try_peek()`, a negative value on a type mismatch.
- A mailbox stores handles. Create a new object, or a copy, for every message.
- Bound the stimulus path for backpressure; never let a monitor block.
- Messages are FIFO, and processes waiting in `get()` are served in arrival order, but the standard leaves the order of same-time arrivals and of waiting `put()` callers open.

### Worked example: mailbox plumbing for a layered bench

```systemverilog
// compile
`timescale 1ns/1ns

// The bus that the driver drives and the monitor watches. There is no DUT yet:
// the monitor sees what the driver drove one clock earlier.
interface bus_if (input logic clk);
  logic       valid = 1'b0;
  logic [7:0] data  = '0;

  clocking drv_cb @(posedge clk);   // default output skew #0: drives land in Re-NBA
    output valid, data;
  endclocking

  clocking mon_cb @(posedge clk);   // default input skew #1step: values before the edge
    input valid, data;
  endclocking
endinterface

package tb_pkg;
  class txn;
    int unsigned id;
    bit [7:0]    data;

    function txn copy();            // shallow is enough: txn holds no handles
      txn c = new();
      c.id   = id;
      c.data = data;
      return c;
    endfunction
  endclass

  class generator;
    mailbox #(txn) gen2drv, gen2scb;
    int unsigned   n;

    function new(mailbox #(txn) gen2drv, mailbox #(txn) gen2scb, int unsigned n);
      this.gen2drv = gen2drv;
      this.gen2scb = gen2scb;
      this.n       = n;
    endfunction

    task run();
      txn t;
      for (int unsigned i = 0; i < n; i++) begin
        t      = new();               // a new object for every message
        t.id   = i;
        t.data = 8'hA0 + 8'(i);       // a real generator randomizes here (I-SV-2A)
        gen2drv.put(t);               // waits while gen2drv is full: backpressure
        gen2scb.put(t.copy());        // the scoreboard keeps its own snapshot
        $display("[%0t] gen: put id=%0d", $time, t.id);
      end
    endtask
  endclass

  class driver;
    virtual bus_if vif;
    mailbox #(txn) gen2drv;

    function new(virtual bus_if vif, mailbox #(txn) gen2drv);
      this.vif     = vif;
      this.gen2drv = gen2drv;
    endfunction

    task run();
      txn t;
      forever begin
        gen2drv.get(t);               // waits while there is nothing to drive
        @(vif.drv_cb);
        vif.drv_cb.valid <= 1'b1;
        vif.drv_cb.data  <= t.data;
        $display("[%0t] drv: drive id=%0d data=%h", $time, t.id, t.data);
        @(vif.drv_cb);
        vif.drv_cb.valid <= 1'b0;     // one idle cycle between items
      end
    endtask
  endclass

  class monitor;
    virtual bus_if vif;
    mailbox #(txn) mon2scb;

    function new(virtual bus_if vif, mailbox #(txn) mon2scb);
      this.vif     = vif;
      this.mon2scb = mon2scb;
    endfunction

    task run();
      txn a;
      forever begin
        @(vif.mon_cb);
        if (vif.mon_cb.valid) begin
          a      = new();             // a new object for every observed item
          a.data = vif.mon_cb.data;
          mon2scb.put(a);             // unbounded: never waits, so no beat is missed
        end
      end
    endtask
  endclass

  class scoreboard;
    mailbox #(txn) gen2scb, mon2scb;
    int unsigned   matches, mismatches;

    function new(mailbox #(txn) gen2scb, mailbox #(txn) mon2scb);
      this.gen2scb = gen2scb;
      this.mon2scb = mon2scb;
    endfunction

    task run();
      txn a, e;
      forever begin
        mon2scb.get(a);                    // waits for the next observed item
        // Expected snapshots always arrive first in this bench, so 0 here
        // means an extra, unexpected item.
        if (gen2scb.try_get(e) > 0) begin
          if (a.data == e.data) matches++;
          else begin
            mismatches++;
            $error("[%0t] SCB: id=%0d expected data=%h, saw %h",
                   $time, e.id, e.data, a.data);
          end
        end else begin
          mismatches++;
          $error("[%0t] SCB: saw data=%h with no expected item", $time, a.data);
        end
      end
    endtask
  endclass
endpackage

module tb_top;
  import tb_pkg::*;

  localparam int unsigned N_ITEMS = 5;

  logic clk = 1'b0;
  always #5 clk = ~clk;               // rising edges at 5, 15, 25, ... ns

  bus_if bus (.clk(clk));

  mailbox #(txn) gen2drv, gen2scb, mon2scb;
  generator  gen;
  driver     drv;
  monitor    mon;
  scoreboard scb;

  initial begin
    // Create each mailbox once, then hand the same handle to both of its ends.
    gen2drv = new(2);                 // bounded: the generator stays close to the driver
    gen2scb = new();                  // unbounded: expected snapshots
    mon2scb = new();                  // unbounded: a monitor must never wait
    gen = new(gen2drv, gen2scb, N_ITEMS);
    drv = new(bus, gen2drv);
    mon = new(bus, mon2scb);
    scb = new(gen2scb, mon2scb);

    fork
      gen.run();
      drv.run();
      mon.run();
      scb.run();
    join_none

    wait (scb.matches + scb.mismatches == N_ITEMS);
    $display("[%0t] SCB_SUMMARY matches=%0d mismatches=%0d pending=%0d",
             $time, scb.matches, scb.mismatches, gen2scb.num());
    $display("[%0t] PASS=%0d FAIL=%0d", $time, scb.matches, scb.mismatches);
    $finish;
  end

  initial begin
    #1000;
    $fatal(1, "WATCHDOG: fewer than %0d items checked", N_ITEMS);
  end
endmodule
```

**Run it.** Save the block as one file, for example `tb_top.sv`, and compile and run it with a simulator that supports SystemVerilog classes, mailboxes, interfaces and clocking blocks; `tb_top` is the top module. The command line is tool-dependent, and your simulator may add its own banner and a note when `$finish` runs.

**What to notice:**

- `gen: put id=2` prints at 0 ns although `gen2drv` can hold only two messages. The driver took id 0 at 0 ns and is waiting for the first clock edge, so three `put()` calls complete before the generator has to wait.
- `put id=3` completes at 15 ns and `put id=4` at 35 ns, each in the time slot where the driver takes the next item. That is backpressure, with no polling anywhere.
- Each item is driven at one rising edge and observed at the next: the monitor's clocking block samples the value from just before the edge (§14.13), and the drive landed in the Re-NBA region of the previous edge (§14.16).
- The test ends on a condition, five items checked, not on a delay. `pending=0` comes from `gen2scb.num()` and proves no expected item was left over. The watchdog fires only if something hangs.

| Time (ns) | What happens | `gen2drv` afterwards, oldest first | Generator |
|---|---|---|---|
| 0 | `put()` ids 0 and 1 fill the mailbox; the driver's `get()` takes id 0, so `put()` id 2 completes; `put()` id 3 must wait | 1, 2 | waiting in `put()` with id 3 |
| 5 | first rising edge: the driver drives id 0 | 1, 2 | waiting |

At 15 ns and 35 ns the scoreboard's error and the generator's line share a time slot, so they may print in the other order (§4.7).

**Why the driver drives id 3 first.** At 0 ns the generator writes ids 0, 1, 2 and 3 into the same object before its fourth `put()` suspends it. When the first clock edge arrives at 5 ns, the driver's handle refers to that object, which now holds id 3. From then on the driver always reads whatever the generator wrote last, so id 4 repeats. The scoreboard's snapshots, taken with `copy()`, are still correct, so it reports four mismatches and one accidental match. The symptom depends on timing; the cause, one object, does not. Restore the `new()` inside the loop and the clean log returns.

### How to add a channel to a bench

1. Make the transaction a class, so that a handle is the message, and give it a `copy()` method.
2. Declare the mailbox typed: `mailbox #(txn)`.
3. Choose the depth by direction: a small bound on stimulus paths toward a driver; unbounded for anything a monitor writes or anything a scoreboard reads as expected values.
4. Create the mailbox once, in the code that builds the bench, and pass the same handle to the producer's and the consumer's constructors.
5. In the producer, create a new object for each message, or put a copy.
6. In the consumer, wait in `get()`. Do not poll `num()` or loop on `try_get()` with a delay.
7. Start every `run()` task with `fork … join_none`, end the test on a condition such as "N items checked", add a `$fatal` watchdog, and print a summary line.

**Checklist before moving on:**
- [ ] Every mailbox is typed, for example `mailbox #(txn)`.
- [ ] The generator → driver mailbox is bounded and the monitor → scoreboard mailbox is unbounded.
- [ ] Each mailbox is created once, and both of its ends hold the same handle.
- [ ] Every message is a new object or a copy, and nothing modifies an object after putting it.
- [ ] Consumers wait in `get()`; nothing polls `num()`.
- [ ] Every `try_` result is tested with `> 0`.
- [ ] The test ends on a condition, has a `$fatal` watchdog, and prints `SCB_SUMMARY` and `PASS`/`FAIL` lines.

## Push Further

### Expert: wake-up order the standard leaves open

- The standard fixes FIFO order for messages (§15.4.3) and keeps processes waiting in `get()` in their arrival order (§15.4.5). It does not fix the order in which processes **reach** the waiting queue: two `get()` calls in one time slot are ordered by the scheduler (§4.7).
- For producers suspended in `put()` on a full mailbox, the standard states no order at all. When a slot frees, which waiting producer completes first is tool-dependent. The visual on this page serves them first come, first served, and lists that choice among its modelling assumptions.
- One message can release several processes waiting in `peek()`, because the message stays queued; a waiting `get()`, if there is one, then removes it. As long as a message remains, every process blocked in `peek()` or `get()` is released, and a process still waiting once no message remains keeps waiting (§15.4.7). So whether a `peek()` waiter sees a message can depend on whether a `get()` waiter ahead of it took it first.
- Design consequence: fair or ordered service between equal waiters is not a mailbox feature. Build it explicitly, with one mailbox per consumer or a dispatcher thread.

Sources: IEEE 1800-2023 §4.7, §15.4.3, §15.4.5, §15.4.7; the order of waiting `put()` callers is tool-dependent.

### Expert: the three results of try_get and try_peek

- `try_get()` and `try_peek()` return a positive integer on success, 0 when the mailbox is empty, and a negative integer when the message's type is not equivalent to the variable's type (§15.4.6, §15.4.8). `try_put()` returns a positive integer or 0 (§15.4.4).
- `if (m.try_get(x))` treats the negative mismatch result as success, and the code then uses an `x` that was never written. Write `if (m.try_get(x) > 0)`. In a typed mailbox the compiler rules mismatches out (§15.4.9), one more reason to type every mailbox.
- Draining a typeless mailbox with `while (m.try_get(x) > 0);` stops at the first message of another type and leaves the rest queued.
- Functions, including UVM's analysis `write()` methods, cannot call tasks (§13.4), so they can use only the `try_` methods and `num()`. On an unbounded mailbox `try_put()` always succeeds, which is how `uvm_tlm_analysis_fifo::write()` stores every item without waiting (uvm-core 2020.3.1, `uvm_tlm_fifos.svh`).

Sources: IEEE 1800-2023 §13.4, §15.4.4, §15.4.6, §15.4.8, §15.4.9; uvm-core 2020.3.1 `src/tlm1/uvm_tlm_fifos.svh`.

### Expert: singular messages, ref arguments and class hierarchies

- A message must be singular (§15.4.3), and the Annex G.4 prototype names the default type parameter `dynamic_singular_type`. Unpacked structs, unions and arrays are not singular (Annex P).
- `get()`, `peek()`, `try_get()` and `try_peek()` take a `ref` argument, and an argument passed by reference must have a type equivalent to the formal, with no casting (§13.5.2). A `mailbox #(base_txn)` that carries objects of derived classes is therefore read into a `base_txn` handle and then `$cast` to the derived type (§6.24.2); passing a derived-class variable to `get()` does not compile. [I-SV-1: Polymorphism Pitfalls](/curriculum/T2_Intermediate/I-SV-1_OOP/polymorphism-pitfalls) covers the cast.
- `peek()` on a class message gives every peeking process the same handle, so they all share one object: the aliasing rule again.

Sources: IEEE 1800-2023 §6.24.2, §13.5.2, §15.4.3 to §15.4.8, Annex G.4, Annex P.

### Expert: extending the built-in mailbox class

- `mailbox` is a class in the built-in `std` package, so you can extend it, and user code may declare its own `mailbox` in another scope; the built-in one stays reachable as `std::mailbox` (§15.2, §26.7).
- The Annex G.4 prototype declares none of the methods `virtual`. A subclass that adds its own `put()`, for example to count messages or track a high-water mark, is called only through a handle of the subclass type. Code that holds a plain `mailbox #(T)` handle still calls the built-in `put()` (§8.14, §8.20).
- For statistics, wrapping is often simpler than extending: a small class that owns a mailbox and forwards `put()` and `get()` controls every access point.

Sources: IEEE 1800-2023 §8.14, §8.20, §15.2, §26.7, Annex G.4.

### Expert: num() snapshots, draining and waiting without taking

- `num()` is exact only until the next `put()` or `get()` by any process (§15.4.2). Use it for end-of-test accounting and debug prints, never to decide whether a `put()` or `get()` will wait.
- There is no method that empties a mailbox or reports its bound (Annex G.4). On a reset, drain it with `while (m.try_get(x) > 0);` and keep the bound in a parameter.
- To wait until a message exists without taking it, call `peek()`: it blocks while the mailbox is empty and leaves the message for the real consumer (§15.4.7). A `wait (m.num() > 0)` may never wake: the standard requires re-evaluation when data members that the method reads change (§9.4.2), but it does not describe a mailbox's internals, so the behaviour is tool-dependent.

Sources: IEEE 1800-2023 §9.4.2, §15.4.2, §15.4.7, Annex G.4.

### Expert: memory, polling and zero-time producers

- A queued handle keeps its object reachable, so automatic memory management cannot reclaim it (§8.29). An unbounded mailbox whose consumer has stopped grows for the rest of the test; the `pending=0` field of an end-of-test summary, read with `num()`, catches it.
- Polling with `try_get()` and a `#1` delay in a loop wakes the process at every interval even when there is nothing to do, and adds up to one interval of latency to each hand-off; a blocking `get()` costs nothing while it waits. This is general practice, not a rule of the standard.
- A `forever` producer with no blocking statement that feeds an unbounded mailbox is a zero-delay loop: simulation time never advances, and whether any other process runs is up to the simulator (§4.7). Whether a tool detects the loop and stops is tool-dependent.

Sources: IEEE 1800-2023 §4.7, §8.29; the polling cost is general practice.

### Kata: a bounded channel that knows when to stop

**Objective:** expose the shared-handle bug, fix it, and stop a driver cleanly once its generator has finished, using the isolated timeout idiom from [F2C](/curriculum/T1_Foundational/F2C_Procedural_Code_and_Flow_Control/index).

**Starter.** It compiles, and it has both bugs.

```systemverilog
// compile
module tb_top;
  timeunit 1ns; timeprecision 1ns;

  class txn;
    int unsigned id;
  endclass

  mailbox #(txn) gen2drv = new(2);

  initial begin : generator
    txn t;
    t = new();                          // reused for every message (task 2)
    for (int i = 0; i < 4; i++) begin
      t.id = i;
      gen2drv.put(t);
    end
  end

  initial begin : driver
    txn t;
    forever begin
      gen2drv.get(t);                   // waits forever after the last item (task 3)
      #20 $display("[%0t] drv: drove id=%0d", $time, t.id);
    end
  end

  initial begin : watchdog
    #1000 $fatal(1, "WATCHDOG: the driver never stopped");
  end
endmodule
```

**Tasks:**
1. Predict the starter's log, then run it or trace it by hand. Explain why every line shows `id=3`, and why the run ends with the watchdog at 1000 ns.
2. Fix the generator so that each message is its own object.
3. Write `task automatic get_with_timeout(output txn t, input int unsigned budget_ns, output bit ok);` with the isolated `fork begin fork … join_any; disable fork; end join` idiom. Make the driver stop when 50 ns pass without an item, print a `PASS=` and `FAIL=` line, and call `$finish`.
4. Add an aliasing check to the driver: report an error when the same handle arrives twice in a row.

**Done when:**
- the driver prints ids 0, 1, 2 and 3 in order, at 20, 40, 60 and 80 ns;
- no aliasing error is reported;
- exactly one timeout line appears, at 130 ns, after the last item;
- the run ends with `PASS=4 FAIL=0` and `$finish`, not with the watchdog.

<details>
<summary>Worked solution (try the kata first)</summary>

**Task 1.** The starter prints `id=3` four times, at 20, 40, 60 and 80 ns, and then the watchdog's `$fatal` ends the run at 1000 ns. At 0 ns the generator writes ids 0 to 3 into its one object: two messages fit in `gen2drv` and the driver takes a third, so the fourth `put()` suspends it only after `t.id` is already 3. Each `$display` runs 20 ns after a `get()`, when the object holds 3. After the last item the driver waits in `get()` forever, and only the watchdog's pending delay keeps the simulation alive; without it the run would end quietly (§9.6.1).

**Tasks 2 to 4:**

```systemverilog
// compile
module tb_top;
  timeunit 1ns; timeprecision 1ns;

  class txn;
    int unsigned id;
  endclass

  mailbox #(txn) gen2drv = new(2);

  // Wait at most budget_ns for an item. ok is 1 when an item arrived.
  task automatic get_with_timeout(output txn t, input int unsigned budget_ns,
                                  output bit ok);
    ok = 1'b0;
    fork begin                          // isolation: disable fork reaches only these two
      fork
        begin
          gen2drv.get(t);
          ok = 1'b1;
        end
        #(budget_ns);
      join_any
      disable fork;
    end join
  endtask

  initial begin : generator
    txn t;
    for (int i = 0; i < 4; i++) begin
      t    = new();                     // fix: a new object for every message
      t.id = i;
      gen2drv.put(t);
    end
  end

  initial begin : driver
    txn t, prev;
    bit ok;
    int unsigned n_items, n_errors;
    forever begin
      get_with_timeout(t, 50, ok);
      if (!ok) break;                   // 50 ns without an item: the generator is done
      if (t == prev) begin              // the same object twice means aliasing
        n_errors++;
        $error("[%0t] drv: the same txn object arrived twice", $time);
      end
      prev = t;
      #20 $display("[%0t] drv: drove id=%0d", $time, t.id);
      n_items++;
    end
    $display("[%0t] drv: no item for 50 ns, stopping", $time);
    $display("[%0t] PASS=%0d FAIL=%0d", $time, n_items - n_errors, n_errors);
    $finish;
  end

  initial begin : watchdog
    #1000 $fatal(1, "WATCHDOG: the driver never stopped");
  end
endmodule
```

**Expected output** (illustrative):

```text
[20] drv: drove id=0
[40] drv: drove id=1
[60] drv: drove id=2
[80] drv: drove id=3
[130] drv: no item for 50 ns, stopping
[130] PASS=4 FAIL=0
```

**Why it works:**
- Comparing handles with `==` tests whether two variables refer to the same object (§8.4), so the aliasing check needs no knowledge of the fields. Run it without the task 2 fix and it reports an error at 20 ns.
- `disable fork` ends every descendant of the calling process (§9.6.3). The outer `fork begin … end join` gives the race its own parent, so the `disable fork` cannot reach other threads that the driver might own.
- The 50 ns budget is longer than the longest gap between items (20 ns), so the timeout fires only after the generator has really stopped. If an item and the timeout could land in the same time slot, which branch of `join_any` finishes first would depend on process order (§4.7).
