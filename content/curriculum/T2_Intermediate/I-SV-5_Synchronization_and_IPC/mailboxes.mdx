  ## Level 1: The Big Idea
  *IEEE 1800-2023, Clause 15.4: Mailboxes*

  A **mailbox** is a built-in message queue. One process `put`s an item into the mailbox while another `get`s it out. It's like dropping a letter into a box for someone else to pick up later.

  ## Level 2: Practical Usage

  ### Basic Operations

  | Call | Blocking? | Use it when |
  | --- | --- | --- |
  | `put(item)` | Blocks while a bounded mailbox is full | Backpressure producer threads until consumers catch up. |
  | `try_put(item)` | Never; returns 0 if full and stores nothing | Drop low-priority work instead of stalling. |
  | `get(item)` | Blocks until something arrives | Classic producer/consumer handshakes. |
  | `try_get(item)` | Never; returns 0 if empty (negative on a type mismatch) | Check for work without blocking a monitor. |
  | `peek(item)` | Blocks until something arrives; copies without removing | Look at the next transaction while leaving it queued. |
  | `try_peek(item)` | Never; returns 0 if empty | Look ahead without blocking. |
  | `num()` | Instant | Inspect queue depth; the value is stale after the next put or get by any process (§15.4.2). |

  Blocked callers are woken first-in first-out (IEEE 1800-2023 §15.4.5). Predict when the producer gets past a full mailbox, then drive a producer and two consumers yourself — and watch who receives the first message when both consumers are waiting.

  ```systemverilog
  typedef struct { int id; bit [7:0] data; } packet_t;
  mailbox #(packet_t) mbx = new(4); // depth-limited queue

  task automatic produce_packet(int id);
    packet_t p = '{id: id, data: $urandom_range(0, 255)};
    mbx.put(p);   // blocks while 4 packets are queued: this IS the backpressure
  endtask

  task automatic produce_optional(int id);   // low-priority traffic
    packet_t p = '{id: id, data: 8'hFF};
    if (!mbx.try_put(p))
      $display("[%0t] dropped optional packet %0d: mailbox full", $time, id);
  endtask

  initial begin
    for (int idx = 0; idx < 8; idx++) begin
      produce_packet(idx);
    end
  end

  initial begin
    packet_t pkt;
    forever begin
      mbx.get(pkt);
      $display("[%0t] Consumer saw id=%0d depth=%0d", $time, pkt.id, mbx.num());
    end
  end
  ```

  ## Failure Modes: Leaks and Backpressure

  **The Infinite Queue (Memory Leak):** 
  Calling `new()` with no arguments creates an unbounded (infinite) mailbox. If your producer thread (e.g., a fast transaction generator) pushes items faster than your consumer thread (e.g., a slow APB driver) can pull them, the mailbox will grow infinitely. This will eventually exhaust the simulator's memory and crash the process. 
  
  **The Fix (Backpressure):** Always use bounded mailboxes `new(DEPTH)` for driver queues. When the mailbox is full, the producer's `put()` will naturally block, creating *backpressure* that forces the generator to wait for the hardware to catch up. Do not build your own backpressure with `try_put` plus `wait (mbx.num() < DEPTH)`: `put()` already waits for room. Worse, the wait's only operand is the `mbx` handle, which never changes; whether a simulator re-evaluates a method call like `mbx.num()` when the mailbox's contents change is tool-dependent, so this pattern can hang.

  **The Shared Handle:** For class objects, `put(tr)` stores the **handle**, not a copy. A producer that reuses one object — `tr.randomize(); mbx.put(tr);` in a loop — fills the mailbox with several handles to the same object, and the consumer sees only the last values. Call `tr = new();` (or copy the object) before every `put()`.

  **Mailboxes vs. TLM/FIFOs:** 
  In modern UVM environments, raw SystemVerilog mailboxes are rarely used. UVM’s `uvm_tlm_fifo` wraps a mailbox with analysis ports, standard reset control, and comprehensive blocking/non-blocking APIs. You should transition to TLM FIFOs when bridging IPC into UVM testbench architecture.

  **One-to-one only:** Mailboxes always deliver each message to a single consumer. When you need broadcast semantics, rely on [analysis ports](/curriculum/T2_Intermediate/I-UVM-2B_TLM_Connections/index#monitors-scoreboards-and-the-analysis-fabric) or register callbacks.
