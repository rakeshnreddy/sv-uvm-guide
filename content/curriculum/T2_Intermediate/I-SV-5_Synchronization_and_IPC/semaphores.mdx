## Quick Take

- **What it is:** A **semaphore** is a built-in SystemVerilog class that hands out keys from a bucket (IEEE 1800-2023 §15.3). A process takes keys with `get()` before it touches a shared resource and returns them with `put()` afterwards. When the bucket holds too few keys, `get()` makes the process wait, and the process resumes by itself as soon as another process returns enough keys.
- **Why it matters:** Testbench threads share things that only one of them, or only a few, may use at a time: a bus model, a memory port, the requests a target can accept. Without a semaphore, two threads drive the same signals in the same time slot and the damage looks like a design bug. With one, three new bugs become possible: a key that is never returned, two threads that each hold the key the other needs, and a thread that never gets a turn. None of them prints an error by itself. The test stops early, hangs, or quietly never finishes part of its work.
- **The Analogy:** A key cabinet outside a workshop with one machine. You take the key to use the machine; if the cabinet is empty, you join the queue at the door; when you hang the key back, the person at the front of the queue takes it. *Where it breaks:* the keys carry no names, so anyone can hang a key back, even one they never took, and the cabinet can end up holding more keys than it started with. A worker sent home mid-job (a killed process) takes the key along, and nobody notices. And the queue protects only the people already standing in it.

**You will be able to:**
1. Predict the key count and the process that runs next after any sequence of `new`, `get`, `put` and `try_get` calls, including `new()` with no argument, a multi-key `get(n)` and a `put()` that raises the count above its starting value.
2. Write mutual exclusion for a shared bus driver and a credit limit with a multi-key semaphore, with every exit path returning its keys and an end-of-test check that proves it.
3. Debug a leaked key, from an early exit or a killed holder, starting from its symptom in the log.
4. Diagnose a lock-order deadlock between two semaphores from its symptoms, and fix it with one acquisition order or an all-or-nothing acquire.
5. Explain which wake-up order the standard guarantees to semaphore waiters and which it leaves open, and fix a waiter that starves.

## Build Your Mental Model

### A semaphore is a bucket of keys

The standard describes a semaphore as a bucket of keys (§15.3). `new(n)` creates the bucket with n keys. A process calls `get(1)` to take a key before it uses the shared resource, and `put(1)` to return it afterwards. If the bucket is empty, `get(1)` **blocks**: the process stops at that line and joins a waiting queue. It resumes by itself when a key comes back. Nobody polls.

The code between a process's `get()` and its `put()` is its **critical section**. With one key, at most one process can be inside its critical section at any moment; that guarantee is called **mutual exclusion**. With n keys, at most n processes can be inside at once.

`semaphore` is a class (§15.2), so a `semaphore` variable holds a **handle** to the object, as in [I-SV-1](/curriculum/T2_Intermediate/I-SV-1_OOP/index). Every process that uses the same handle shares the same bucket. Declare it with its initializer at module scope, `semaphore bus_lock = new(1);`, and the object exists before any `initial` procedure starts (§6.8).

The example the picture freezes: three masters share one bus through one task.

```systemverilog
// compile
module tb_top;
  timeunit 1ns; timeprecision 1ns;

  semaphore bus_lock = new(1);          // one key: one master on the bus at a time

  // automatic: each concurrent call gets its own copy of who
  task automatic use_bus(string who);
    bus_lock.get(1);                    // take the key, or wait in line for it
    $display("[%0t] %s drives the bus", $time, who);
    #10;                                // the critical section lasts 10 ns
    $display("[%0t] %s releases the bus", $time, who);
    bus_lock.put(1);                    // return the key: the oldest waiter takes it
  endtask

  initial begin
    fork
      use_bus("A");
      begin #2; use_bus("B"); end       // asks at 2 ns, while A holds the key
      begin #4; use_bus("C"); end       // asks at 4 ns, and queues behind B
    join
    $display("[%0t] all done", $time);
  end
endmodule
```

**Expected output** (illustrative: traced by hand from §15.3.2–§15.3.3, not from a simulator run):

```text
[0] A drives the bus
[10] A releases the bus
[10] B drives the bus
[20] B releases the bus
[20] C drives the bus
[30] C releases the bus
[30] all done
```

Read the log against the rules. B asks at 2 ns while A holds the key, so B waits; C asks at 4 ns and queues behind B. When A calls `put(1)` at 10 ns, B, the oldest waiter, takes the key and resumes by itself. Each "releases" line prints before `put(1)`, so the next "drives" line can never come first, and the three transfers never overlap.

### The four methods and their key counts

The class has exactly four methods (Annex G.3):

| Call | Prototype | What happens to the count | Blocks? |
|---|---|---|---|
| `new(n)` | `function new(int keyCount = 0);` | The bucket starts with n keys. **`new()` alone starts with 0.** | Never |
| `get(n)` | `task get(int keyCount = 1);` | Takes n keys in one step, once n keys are free at the same time (§15.3.3). | Until n keys are free |
| `put(n)` | `function void put(int keyCount = 1);` | Adds n keys, with no upper limit. A waiting process whose request now fits continues (§15.3.2). | Never |
| `try_get(n)` | `function int try_get(int keyCount = 1);` | Takes n keys and returns a positive value, or takes nothing and returns 0 (§15.3.4). | Never |

Rules to carry into every bench, each with the mistake it prevents:

- **`new()` is an empty bucket.** The default count is 0 (§15.3.1), while `get()` and `put()` default to one key. A lock created with `new()` blocks its very first `get(1)`, and the bench stalls unless some process happens to call `put()` first. Write `new(1)`.
- **`put()` can push the count above where it started** (§15.3.1). The standard gives keys no owner: §15.3.2 lets any process call `put()`, with no check that it ever took a key. A stray second `put(1)` therefore creates an extra key, and two processes can then be inside a one-key critical section together.
- **`try_get()` never waits, and never joins the queue** (§15.3.4). Check its result. Code that ignores a 0 and uses the resource anyway has no protection, and its later `put(1)` adds a key nobody took.
- **Negative counts are errors.** `get(-1)` and `put(-1)` are errors; `try_get(-1)` returns 0 and is an error too (§15.3.2–§15.3.4).
- **Nothing reads the count.** There is no method that returns how many keys are free (Annex G.3). Make It Work shows how to check the count at the end of a test with `try_get()` and `put()`.
- **`get()` is a task; `put()` and `try_get()` are functions.** A function cannot call `get()` directly (§13.4), but it can return keys or try for them.

### Mistake 1: the leaked key

A **leaked key** is a key that a process took and never returned. With a one-key lock, every later `get()` then waits forever; with more keys, the bucket is one key short for the rest of the run. SystemVerilog has no exceptions and no `finally` block (Annex B reserves no `try`, `catch` or `finally` keyword), so nothing ever returns a key on your behalf. The usual ways out of a critical section without `put()`:

- **An early exit** in the code between `get()` and `put()`: a `return`, a `break` or an error path that skips the rest. A `return` inside a task that the critical section *calls* ends only that task (§12.8), and the caller still reaches its `put()`.
- **The holder is stopped.** `p.kill()`, `disable fork` and `disable` of a block or task end the code that would have called `put()` (§9.6.2, §9.6.3, §9.7). The [module overview](/curriculum/T2_Intermediate/I-SV-5_Synchronization_and_IPC/index) shows how a `process` handle reaches and kills another thread.
- **The holder never gets there.** It waits inside the critical section for something that never comes, such as a response or an event, and keeps the key while it waits.

```systemverilog
// snippet: broken: the error path leaves with the key
bus_lock.get(1);
if (pkt.bad) return;                    // skips put(1): the key is gone for good
drive(pkt);
bus_lock.put(1);
```

```systemverilog
// snippet: fixed: one exit after get(1), whatever happens inside
bus_lock.get(1);
if (!pkt.bad) drive(pkt);               // the error path skips the work, not the put
bus_lock.put(1);
```

The model reruns the whole test and checks three things: no process is left blocked, two senders never share the bus, and the bus ends with all its keys.

### Mistake 2: the lock-order deadlock

A **deadlock** is a set of processes in which each waits for something only another member of the set can provide, so none of them can ever continue. With semaphores, the classic case is **lock-order inversion**: two processes need the same two semaphores and take them in opposite orders.

```systemverilog
// compile
module tb_top;
  timeunit 1ns; timeprecision 1ns;

  semaphore s1 = new(1);                // guards resource 1, say the bus
  semaphore s2 = new(1);                // guards resource 2, say a memory port

  initial begin : proc_a                // takes s1, then s2
    s1.get(1);
    $display("[%0t] proc_a holds s1, wants s2", $time);
    #1;
    s2.get(1);                          // waits forever: proc_b holds s2
    $display("[%0t] proc_a holds s1 and s2", $time);
    s2.put(1);
    s1.put(1);
  end

  initial begin : proc_b                // takes s2, then s1: the opposite order
    s2.get(1);
    $display("[%0t] proc_b holds s2, wants s1", $time);
    #1;
    s1.get(1);                          // waits forever: proc_a holds s1
    $display("[%0t] proc_b holds s1 and s2", $time);
    s1.put(1);
    s2.put(1);
  end
endmodule
```

**Expected output** (illustrative; the two lines may print in either order, because both initial procedures start at 0 ns and the standard leaves their order open, §9.2, §4.7):

```text
[0] proc_a holds s1, wants s2
[0] proc_b holds s2, wants s1
```

Nothing else prints. At 1 ns both processes block, nothing is left to run, and the simulation ends by itself with no error (§9.6.1).

**Symptoms.** Each process printed that it holds one semaphore and wants the other, and nothing follows. No error appears. With nothing else scheduled, the run ends at 1 ns; with a free-running clock or a watchdog, it runs on until the watchdog fires.

**Fixes**, best first:

1. **One global order.** Every process that needs both semaphores takes s1 before s2. Whoever gets s1 first also gets s2; the other waits for s1 while holding nothing, so no cycle can form.

   ```systemverilog
   // snippet: the fix: proc_b now takes s1 first, like proc_a
   initial begin : proc_b
     s1.get(1);                          // one global order: s1, then s2
     #1;
     s2.get(1);
     $display("[%0t] proc_b holds s1 and s2", $time);
     s2.put(1);                          // any release order is safe
     s1.put(1);
   end
   ```

2. **All or nothing.** When no fixed order is possible, for example because the resources are picked at run time, take the first key, try the second with `try_get()`, and if that fails, give the first one back and retry after a random pause.

   ```systemverilog
   // snippet: take both keys or neither, then retry after a random pause
   task automatic get_both(semaphore first, semaphore second);
     forever begin
       first.get(1);
       if (second.try_get(1)) return;    // got both: done
       first.put(1);                     // give back what you hold...
       #($urandom_range(5, 1));          // ...and retry after a random pause
     end
   endtask
   ```

   Without the random pause, two processes that back off for equal times can keep colliding forever. That is a **livelock**: both keep running, and neither makes progress.

3. **One counting semaphore**, when the resources are interchangeable. With `semaphore ports = new(2);`, a process that needs two calls `ports.get(2)`, which takes both keys in one step, so nobody ever holds one key while waiting for another.

**Not fixes:**
- `s2 = new(2)`: proc_b gets in, but two processes can now hold s2 at once, so s2 no longer protects anything.
- Killing one process: the deadlock ends, but the killed process's key is never returned (§9.7), so the next user of that semaphore hangs instead.
- `try_get()` in a loop while still holding the other key: the process spins, and its partner stays blocked.

**A deadlock can hide.** Delete both `#1` delays and the run usually passes, because each process takes both keys before the other one starts. But the standard lets a simulator suspend a process between any two statements (§4.7), so the opposite orders can still deadlock on a conforming simulator. A passing run proves nothing here: fix the order.

### Multi-key semaphores: counting and credits

The sections above are the core. The ones below add practitioner depth; read this one before Make It Work, which uses credits.

A semaphore with n keys counts n interchangeable things: n channels, n buffer slots, n requests a target can accept. Each user takes as many keys as it needs and gives back the same number.

**`get(n)` is all or nothing.** It waits until n keys are free at the same time and then takes them in one step (§15.3.3), as the get(2) program above showed. Two `get(1)` calls are not the same thing. With `new(2)`, two processes that each call `get(1)` twice can each end up holding one key and waiting forever for a second.

**Credits.** A **credit** is a key that stands for permission to have one request outstanding. The requester takes one before each request, and whoever finishes the request returns it. That is often a different process, such as the one that receives the response, and it is legal because keys have no owner.

```systemverilog
// snippet: credits limit how many requests are outstanding
semaphore credits = new(4);             // the target can queue 4 requests

task automatic send_request(int unsigned id);
  credits.get(1);                       // waits while 4 requests are outstanding
  issue(id);                            // drive the request (not shown)
endtask

task automatic on_response(int unsigned id);   // runs in the response process
  retire(id);                           // check the response (not shown)
  credits.put(1);                       // a different process returns the credit
endtask
```

Two rules keep credits honest. Return a credit on every path, including a request that the target refuses, because no response will come to return it. And never wait for a credit while holding a lock that the returning process needs (Interview angles). Make It Work builds a bench that follows both rules.

### Who gets the key next: FIFO, fairness and starvation

**What the standard guarantees.** The waiting queue is first-in first-out (FIFO): processes blocked in `get()` are served in the order in which they arrived (§15.3.3).

**What it leaves open.** The same clause says the FIFO rule does not decide the order in which processes reach the queue; it only keeps the order in which they arrived. In practice:

- **Same-slot arrivals.** If two processes call `get()` in the same time slot, the scheduler decides which one arrives first (§4.7).
- **`try_get()` has no place in line.** It never waits, so it never queues (§15.3.4). A task that polls with `try_get()` while other processes wait in `get()` can be passed over forever.
- **Small requests overtaking a large one.** The text of `get()` says it takes the keys whenever enough are free. Whether a later `get(1)` may do that while an older `get(2)` is still waiting is not spelled out. The course model allows it; a simulator may instead queue the `get(1)` behind the `get(2)`. This is tool-dependent.
- **Hand-off.** Whether the keys that `put()` returns are reserved for the woken waiter before it runs is not spelled out either (Push Further).

**Starvation** is what an unfair order can cause: one process waits indefinitely while the others keep running. (In a deadlock, by contrast, nobody in the cycle runs.) Here a flush that needs both channels competes with two workers that each use one channel at a time.

```systemverilog
// compile
module tb_top;
  timeunit 1ns; timeprecision 1ns;

  semaphore chans = new(2);             // two identical channels
  bit stop;                             // ends the workers after about 100 ns

  // A worker uses one channel for 10 ns, then asks again at once.
  task automatic worker();
    while (!stop) begin
      chans.get(1);
      #10;
      chans.put(1);
    end
  endtask

  initial begin
    fork
      worker();                         // W0 starts at 0 ns
      begin #5; worker(); end           // W1 starts at 5 ns
      begin
        #2;
        chans.get(2);                   // the flush needs both channels at once
        $display("[%0t] flush got both channels", $time);
        chans.put(2);
      end
      begin #103; stop = 1; end
    join
  end
endmodule
```

Trace it on the course model, which lets a smaller request take free keys past a waiting larger one:

| t (ns) | What happens | Free keys after | flush |
|---|---|---|---|
| 0 | W0 takes a key | 1 | — |
| 2 | flush asks for 2; only 1 is free | 1 | waiting |
| 5 | W1 takes the free key | 0 | waiting |
| 10 | W0 returns its key, then takes one again at once | 1, then 0 | waiting: never 2 free |
| 15 | W1 returns its key, then takes one again | 1, then 0 | waiting |
| … | the pattern repeats every 5 ns | 0 or 1 | waiting |
| 103 | `stop` is set | 0 | waiting |
| 105 | W1 returns its key and leaves | 1 | waiting |
| 110 | W0 returns its key and leaves | 2, then 0 | gets both keys |

**Expected output** (illustrative, course model):

```text
[110] flush got both channels
```

On the course model the flush waited 108 ns and ran only because the workers stopped; with `forever` loops it would never run. On a simulator that queues a new `get()` behind an older waiter, W1's `get(1)` at 5 ns waits behind the flush, and the line reads `[10] flush got both channels` instead. You can watch the course-model behaviour in the sandbox of the semaphore lab above: choose `new(2)`, click A `get(1)`, B `get(2)`, C `get(1)`, then repeat A `put(1)`, A `get(1)`, C `put(1)`, C `get(1)`. B stays first in the queue and never wakes, because the bucket never holds two keys at once.

**Fix it on every simulator** by making the small users step aside while a large request waits:

```systemverilog
// snippet: a gate that lets a waiting flush in first
bit flush_pending;                      // workers take no new keys while it is set

task automatic worker();
  while (!stop) begin
    wait (!flush_pending);              // step aside for a waiting flush
    chans.get(1);
    #10;
    chans.put(1);
  end
endtask

// in the flush branch:
//   flush_pending = 1;  chans.get(2);  flush_pending = 0;
```

Once `flush_pending` is set at 2 ns, no worker starts a new `get(1)`, so the bucket fills as soon as W0 returns its key, and the line reads `[10] flush got both channels` on any simulator. Other fixes, by cause: a polling task should wait in `get()`, so that the FIFO queue covers it; keep critical sections short; and when the order of service matters, for example round-robin between masters, do not leave it to a semaphore. Let one arbiter process grant the requests in the order you choose.

### Diagnosing a hang from its symptoms

Synchronization bugs rarely print an error. Read the log for what is missing, then confirm the cause before you change code.

| Symptom in the log | Likely cause | How to confirm | Fix |
|---|---|---|---|
| The last "granted" line has no matching "released"; later requesters stop in `get()` | Leaked key: an early exit, a kill or a stuck callee between `get()` and `put()` | Log every `get()` and `put()` with the process name; at the end, `try_get(N)` fails | One exit after `get()`; restore keys where processes are killed |
| Two "holds X, wants Y" lines, then nothing | Lock-order deadlock | Draw the wait-for graph: the arrows close a cycle | One global order, or all or nothing |
| One process never gets the resource while the others keep running | Starvation | Count grants per process; look for `try_get()` polling, or a large request behind small ones | Wait in `get()`; gate new requests; use an arbiter when order matters |
| A process stops in `get()` while it already holds the only key | Self-deadlock: a nested `get()` on a semaphore that is not re-entrant | The same process logs "granted" and then blocks on the same semaphore | Take the key once, at the outermost level (Push Further) |
| Two holders at once, and no hang | Surplus key: a second `put()`, or a `put()` by a process that never took a key | At the end, `try_get(N + 1)` succeeds | One `put()` per `get()` (Kata 2) |
| A waiter is stuck at `@ev`, but the trigger line printed earlier in the same time slot | Lost event | Print `$time` before the wait and after the trigger | `wait (ev.triggered)`; see [Events](/curriculum/T2_Intermediate/I-SV-5_Synchronization_and_IPC/events) |
| A consumer is stuck in `get()` on an empty mailbox | The producer finished, was killed, or never started | Count `put()` and `get()` calls per mailbox | See [Mailboxes](/curriculum/T2_Intermediate/I-SV-5_Synchronization_and_IPC/mailboxes) |
| A producer is stuck in `put()` on a full mailbox | The consumer was killed, for example by `disable fork`, or stalled | Check which process should have called `get()` | See [Mailboxes](/curriculum/T2_Intermediate/I-SV-5_Synchronization_and_IPC/mailboxes) |
| Simulation time stops advancing while memory grows | A zero-delay loop writing an unbounded mailbox | Time is stuck at one value in every message | Bound the mailbox or add timing; see [Mailboxes](/curriculum/T2_Intermediate/I-SV-5_Synchronization_and_IPC/mailboxes) |

**Quiet end or hang?** Simulation ends by itself when no activity of any kind remains (§9.6.1). A bench with no clock and no watchdog therefore ends quietly at its last activity, often with no error, which can look like a pass. A free-running clock or a watchdog keeps the run alive, so the same bug becomes a hang that ends only when the watchdog fires. In a UVM test, a blocked process that keeps an objection raised holds the run phase open until the global timeout ends it ([I-UVM-1C](/curriculum/T2_Intermediate/I-UVM-1C_UVM_Phasing/index)).

**Make the log point at the culprit.** Give every test a watchdog that ends with `$fatal`, print a PASS/FAIL line only after the last expected step, and name every wait:

```systemverilog
// snippet: name every wait, so a hang points at its semaphore
task automatic get_logged(semaphore sem, string sem_name, string who, int n = 1);
  $display("[%0t] %s waits for %0d key(s) of %s", $time, who, n, sem_name);
  sem.get(n);
  $display("[%0t] %s got %0d key(s) of %s", $time, who, n, sem_name);
endtask
```

After a hang, the last "waits for" line with no matching "got" line names every blocked process and the semaphore it waits on.

### Semaphores in real testbenches

- **Where they belong.** A bus model, memory port or shared interface that several bench threads drive: wrap every access in one task with `get()` and `put()`. A limit on outstanding requests: credits. A pool of identical resources: one key per resource.
- **Where they do not.** To pass data, use a mailbox. To say "it happened now", use an event. To impose an order of service, use an arbiter: a semaphore serves only its waiters, in arrival order, and promises nothing else.
- **In UVM.** Inside one agent, the sequencer already decides which sequence's item goes to the driver next, and a sequence that needs exclusive use calls `lock()` or `grab()` ([Sequence arbitration](/curriculum/T2_Intermediate/I-UVM-3B_Advanced_Sequencing_and_Layering/sequence-arbitration)). Semaphores remain the tool for resources that no sequencer owns. UVM itself uses one: the register model gives every register a one-key semaphore, so that concurrent `read()`, `write()`, `mirror()`, `peek()` and `poke()` calls on one register run one at a time (uvm-core 2020.3.1 implementation, `src/reg/uvm_reg.svh`).

## Make It Work

### Two masters share one bus driver

This bench has the parts of a real shared-bus driver, in plain SystemVerilog:

- `bus_lock = new(1)` guards the bus, so the two masters' transfers never overlap;
- `credits = new(2)` allows at most two requests outstanding at the target, and the target's response process returns each credit;
- the target refuses request 11, an early-exit path that must still return both keys;
- an end-of-test check proves that each semaphore holds exactly its starting keys, and a watchdog with `$fatal` turns any leak into a loud failure.

Every process takes `credits` before `bus_lock`. That one order is what keeps the bench free of deadlock (Mistake 2, and Interview angles).

```systemverilog
// compile
module tb_top;
  timeunit 1ns; timeprecision 1ns;

  semaphore bus_lock = new(1);          // one key: one master on the bus at a time
  semaphore credits  = new(2);          // two keys: at most two requests outstanding

  int unsigned busy, collisions, completed, nacks;
  int unsigned pass_count, fail_count;

  // The target refuses request 11: a stand-in for any early-exit path.
  function automatic bit target_refuses(int unsigned id);
    return id == 11;
  endfunction

  // The shared bus driver: exactly one exit after get(1), so the key always returns.
  task automatic drive_on_bus(string who, int unsigned id, int unsigned xfer_ns,
                              output bit ok);
    bus_lock.get(1);                    // wait in line for the bus
    busy++;
    if (busy > 1) collisions++;         // proves mutual exclusion
    $display("[%0t] %s: bus granted, req %0d", $time, who, id);
    ok = !target_refuses(id);
    if (ok) #(xfer_ns);                 // data phase
    else    nacks++;                    // refused: no data phase
    busy--;
    $display("[%0t] %s: req %0d %s, bus released", $time, who, id,
             ok ? "done" : "NACK");
    bus_lock.put(1);                    // the single exit: every path gets here
  endtask

  // The target answers 25 ns after a transfer and returns the credit itself.
  task automatic respond(int unsigned id);
    #25;
    $display("[%0t] target: req %0d response, credit returned", $time, id);
    completed++;
    credits.put(1);                     // a different process returns the key
  endtask

  task automatic master(string who, int unsigned first_id, int unsigned n,
                        int unsigned xfer_ns);
    for (int unsigned i = 0; i < n; i++) begin
      bit ok;
      credits.get(1);                   // always credits first, then the bus
      drive_on_bus(who, first_id + i, xfer_ns, ok);
      if (ok) begin
        fork
          automatic int unsigned id = first_id + i;  // copy now: the child runs later
          respond(id);
        join_none
      end else begin
        credits.put(1);                 // refused: no response will return it
      end
    end
  endtask

  // Returns 1 when sem holds exactly n free keys, and leaves the count unchanged.
  function automatic bit holds_exactly(semaphore sem, int n);
    if (!sem.try_get(n)) return 0;      // fewer than n: a key leaked
    if (sem.try_get(1)) begin           // more than n: a key was returned twice
      sem.put(n + 1);
      return 0;
    end
    sem.put(n);
    return 1;
  endfunction

  function automatic void check(bit ok, string what);
    if (ok) pass_count++;
    else begin
      fail_count++;
      $error("CHECK FAILED: %s", what);
    end
  endfunction

  initial begin
    fork
      master("A", 1, 3, 10);            // req 1..3, 10 ns transfers
      begin #4; master("B", 10, 2, 6); end  // req 10..11, 6 ns transfers
    join
    credits.get(2);                     // drain: wait until both credits are back
    credits.put(2);
    check(collisions == 0, "never two masters on the bus");
    check(holds_exactly(bus_lock, 1), "bus_lock ends with exactly 1 key");
    check(holds_exactly(credits, 2), "credits ends with exactly 2 keys");
    check(completed + nacks == 5, "every request completed or was refused");
    $display("[%0t] PASS=%0d FAIL=%0d", $time, pass_count, fail_count);
    $finish;
  end

  initial begin                         // a leaked key ends the run here, loudly
    #1000;
    $fatal(1, "WATCHDOG at %0t: a process is still blocked in get()", $time);
  end
endmodule
```

Compiled on its own, the design's only time unit and precision is 1 ns, so `%0t` prints whole nanoseconds (§20.4.3 gives the `%t` defaults). No simulator was run for this page, so the log below was traced by hand from the rules on this page.

**Trace the keys.** Read this table next to the log. "Waiting" lists the processes blocked on each semaphore, oldest first.

| t (ns) | What happens | `credits` free | `bus_lock` free | Waiting |
|---|---|---|---|---|
| 0 | A takes a credit and the bus; drives req 1 | 1 | 0 | — |
| 4 | B takes the last credit and asks for the bus | 0 | 0 | B on `bus_lock` |
| 10 | A releases the bus, so the key goes to B. A asks for a credit | 0 | 0 | A on `credits` |
| 16 | B releases the bus and asks for a credit | 0 | 1 | A, B on `credits` |
| 35 | `respond(1)` returns a credit; it goes to A, first in line. A takes the bus | 0 | 0 | B on `credits` |
| 41 | `respond(10)` returns a credit to B. B asks for the bus | 0 | 0 | B on `bus_lock` |
| 45 | A releases the bus to B and asks for a credit. B is refused, releases the bus and returns its own credit, which goes to A. A takes the bus | 0 | 0 | — |
| 55 | A releases the bus. The test's `credits.get(2)` starts to wait | 0 | 1 | test on `credits` |
| 70 | `respond(2)` returns a credit: one is not enough for `get(2)` | 1 | 1 | test on `credits` |
| 80 | `respond(3)` returns the second; the drain succeeds, then the checks run | 2 | 1 | — |

Three things to notice:
- At 10 ns A has just freed the bus but must wait anyway: both credits are out. Between 16 and 35 ns the bus sits idle, because the credit limit, not the bus, throttles A.
- At 35 ns the returned credit goes to A, not B. A has been waiting since 10 ns and B only since 16 ns (§15.3.3).
- At 45 ns request 11 is refused. B still releases the bus through the same exit and returns its own credit, which lets A start request 3 at once.

### Break it on purpose

Replace the single exit with an early return on the refusal path:

```systemverilog
// snippet: the bug: an early exit inside drive_on_bus
ok = !target_refuses(id);
if (!ok) begin
  nacks++;
  busy--;
  return;                               // leaves while still holding the bus key
end
#(xfer_ns);
```

**Expected output** (illustrative; the first six lines are unchanged):

```text
[41] target: req 10 response, credit returned
[45] A: req 2 done, bus released
[45] B: bus granted, req 11
[70] target: req 2 response, credit returned
WATCHDOG at 1000: a process is still blocked in get()
```

The last line follows the tool's own fatal-error header, which names the file, line, scope and time (§20.10). Read the log the way you would in a regression:

1. B's grant for request 11 has no matching "bus released" line: B is the holder.
2. B still returned its credit, so A took it and is now blocked in `bus_lock.get(1)`. Request 3 never starts, and no PASS line appears.
3. Remove the watchdog and the run ends quietly at 70 ns instead, with no error at all: the last response was the last activity (§9.6.1).

### How to add a semaphore to a testbench

1. **Name the shared thing and how many users it can serve at once.** Create one semaphore for it with exactly that many keys: `new(1)` for a lock, `new(N)` for N credits or N channels. Never rely on `new()` alone.
2. **Put `get()` and `put()` in one task** that every user calls, so the pair appears in exactly one place.
3. **Hold the key only as long as the resource is busy:** take it just before the first shared signal changes, and return it as soon as the resource is idle again.
4. **Give the task one exit after `get()`.** Use a status flag instead of `return`, and never kill or disable a process that may hold a key.
5. **Write down one acquisition order** for any process that needs two semaphores (here: `credits`, then `bus_lock`) and keep it everywhere.
6. **Return credits** from the process that finishes the request, and from the requester on every path where no response will come.
7. **At the end of the test,** drain counting semaphores with `get(N)` then `put(N)`, and check that each semaphore holds exactly its starting keys: `try_get(N)` must succeed and `try_get(1)` must then fail.
8. **Keep a watchdog** that ends with `$fatal`, and print the PASS/FAIL line only after the last check, so a hang is never mistaken for a pass.

**Checklist before moving on:**
- [ ] Every `get()` has exactly one `put()` on every path, including error and refusal paths.
- [ ] Nothing can return from, disable or kill a process between its `get()` and its `put()`, or the code that kills it restores the keys.
- [ ] Every process that needs two semaphores takes them in the same order.
- [ ] Credits come back from the responder, or from the requester when no response will come.
- [ ] The end-of-test check catches both a missing key and a surplus key.
- [ ] No `try_get()` result is ignored.
- [ ] The watchdog ends with `$fatal`, and a passing run prints `PASS=<n> FAIL=0`.

## Push Further

### Expert: What FIFO leaves open

The FIFO rule of §15.3.3 leaves gaps that every implementation must fill somehow: the course model fills them one way, and your simulator may fill them another. Three are worth knowing, and all three are **tool-dependent**:

- **Hand-off or barging.** §15.3.2 says a waiting process shall continue once enough keys are returned, but not whether those keys are reserved for it before it runs. If they are not, a process that calls `put(1)` and then `get(1)` again in the same time slot can take its own key straight back ("barging"), and a tight `forever` loop of `get(1)`, work, `put(1)` can starve every waiter. The course model hands the keys to the woken waiter inside `put()`, so it cannot show this.
- **Head-of-line blocking.** Whether a `get(2)` at the head of the queue holds back a later `get(1)` that would fit, new or already waiting, is not spelled out. The course model lets every request that fits proceed, oldest waiter first, which is why the flush example starves on it.
- **Same-slot arrivals.** Two `get()` calls in one time slot reach the queue in scheduler order (§4.7).

Write code whose correctness and progress depend on none of these. If other processes must get a turn, do not `put()` and `get()` the same semaphore back to back in one time slot; gate new requests while a large one waits; and use an explicit arbiter when the order of service matters.

### Expert: Key counts at the edges

- **A negative start.** The starting count may be negative, and keys must climb above zero before `get()` or `try_get()` can take any (§15.3.1). `new(1 - N)` therefore lets one `get(1)` through after N `put(1)` calls. `new(0)` followed by `get(N)` says the same thing more clearly.
- **Negative arguments** are errors: `get(-1)` and `put(-1)` report one, and `try_get(-1)` returns 0 and reports one (§15.3.2–§15.3.4).
- **Functions and final procedures.** `put()` and `try_get()` are functions and `get()` is a task (Annex G.3), so only `put()` and `try_get()` can appear in a function or in a `final` procedure, which allows only the statements a function allows (§13.4, §9.2.3). That makes a `final` procedure a natural home for the exact-count check. Final procedures run when simulation ends, before any callback that reports the end (§9.2.3), and the standard names two ways to end: a `$finish`, including the one that `$fatal` makes implicitly (§20.10), and an event queue with nothing left in it (§9.6.1; `cbEndOfSimulation` in §38.36.3). Read together, these clauses mean a `final` check also reports on a run that stopped quietly.
- **The exact-count check** has two halves: `try_get(N)` must succeed (no leak) and `try_get(1)` must then fail (no surplus). Checking only the first half misses the extra key a double `put()` creates.

### Expert: Keys survive a kill, so reset must restore them

`p.kill()`, `disable fork` and `disable` stop a process without running the rest of its code (§9.6.2, §9.6.3, §9.7), and there is no `try`/`finally` to run cleanup. A mid-test reset that kills driver threads therefore also deletes the keys they held. Two patterns work:

- **Account for holdings.** Each holder records what it took, for example in a per-process count. After the kill, the reset code puts back exactly what the killed processes held.
- **Rebuild once everyone is gone.** Kill every process that uses the semaphore, then assign a fresh object: `bus_lock = new(1);`. Do it only after the kills. A process still blocked in the old object's `get()` keeps waiting on that old object, which nobody will ever `put()` to again.

uvm-core shows both the cost and the cure. Its register model records which process holds a register's key; when a later access finds that holder KILLED, it reports a `UVM/REG/ZOMBIE` error saying the register is locked for good, and then waits like any other caller (task `XatomicX`). The register's `reset()` function puts the key back, with a comment that a thread may have been killed during an access: it calls `void'(m_atomic.try_get(1))` and then `m_atomic.put(1)`, so the count ends at exactly one whether or not the key was missing (uvm-core 2020.3.1 implementation, `src/reg/uvm_reg.svh`). A reset handler that calls the register model's `reset()` therefore repairs those keys too; your own semaphores need the same treatment.

### Expert: Ownership and re-entry are your job

A semaphore does not know who holds its keys, so it cannot stop two classic mistakes:

- **Self-deadlock.** A process that holds the only key and calls `get(1)` again, for example from a nested task, waits forever for its own key.
- **Stray release.** A `put(1)` from a process that holds nothing adds a key.

When you need those guarantees, wrap the semaphore. uvm-core does exactly this for every register: it records the holder with `process::self()`, lets the holder re-enter with a counter instead of a second `get()`, and releases with `void'(m_atomic.try_get(1))` before `m_atomic.put(1)`, so the count can never exceed one (uvm-core 2020.3.1 implementation, `XatomicX`). The same pattern as a small class:

```systemverilog
// snippet: a lock that knows its owner (the pattern of uvm_reg's XatomicX)
class owned_lock;
  local semaphore key = new(1);
  local process   owner;                // null while the lock is free
  local int       depth;                // extra lock() calls by the owner

  task lock();
    process me = process::self();
    if (owner == me) begin              // re-entry: never a second get()
      depth++;
      return;
    end
    if (owner != null && owner.status() inside {process::FINISHED, process::KILLED})
      $error("lock held by a process that has ended: restore it in the reset code");
    key.get(1);
    owner = me;
  endtask

  function void unlock();
    if (owner != process::self()) begin // only the holder may release
      $error("unlock() by a process that does not hold the lock");
      return;
    end
    if (depth > 0) begin
      depth--;
      return;
    end
    owner = null;
    void'(key.try_get(1));              // clamp: the count can never exceed 1
    key.put(1);
  endfunction
endclass
```

`unlock()` can be a function because `try_get()` and `put()` are functions; `lock()` must be a task because it calls `get()`. The ended-holder check goes one step beyond `XatomicX`, which checks only for KILLED: a holder that FINISHED without calling `unlock()` has leaked the key just as surely, and `kill()` can race with normal completion, so a killed holder may even read FINISHED (§9.7).

### Expert: Deadlock conditions and system-scale cycles

General concurrency theory (not part of IEEE 1800; Coffman, Elphick and Shoshani, 1971) names four conditions that must all hold for a deadlock: mutual exclusion, hold and wait, no preemption, and a circular wait. Each fix on this page breaks one of them. A global order breaks the circular wait. One `get(n)` on a counting semaphore breaks hold and wait. `try_get()` with release and back-off gives up the hold voluntarily, at the risk of livelock. Mutual exclusion is the reason the semaphore exists, so it stays.

**A loop is proof only with one key per semaphore.** When a semaphore has several keys, a loop in the wait-for graph is necessary for a deadlock but not sufficient: another holder of the same semaphore, outside the loop, may still return a key and break it. Before you call a counting-semaphore hang a deadlock, follow the arrows from every holder of every semaphore in the loop: if any of them can still run and return a key, the loop can still break.

The same reasoning scales up. AXI interconnects deadlock when the dependencies between channels form a cycle, and the simulator in [B-AXI-5](/curriculum/T3_Advanced/B-AXI-5_AXI_Pitfalls_Interconnect_Deadlocks/index) draws that dependency graph with the cycle highlighted. When someone asks you to show that a design cannot deadlock, show the global order or the broken condition, not a passing regression: a latent deadlock can pass on every simulator you try (§4.7).

### Expert: Semaphore or sequencer lock in UVM

Inside one agent, the sequencer already serializes items to its driver, and a sequence that needs exclusive use of that driver calls `lock()` or `grab()` on the sequencer (IEEE 1800.2-2020 §14.2.5.5, §14.2.5.6; see [Sequence arbitration](/curriculum/T2_Intermediate/I-UVM-3B_Advanced_Sequencing_and_Layering/sequence-arbitration)). A semaphore inside such a driver adds nothing the sequencer does not already do. Use a semaphore when several drivers or threads, possibly in different agents, share something that no sequencer owns: a bus model, a memory model's port, a shared interface. The leak, deadlock and starvation rules on this page apply there unchanged. In a UVM test the same bugs usually surface as a run that ends only at its global timeout ([I-UVM-1C](/curriculum/T2_Intermediate/I-UVM-1C_UVM_Phasing/index)).

### Kata 1 (guided): untangle a lock-order deadlock

**Objective:** reproduce a lock-order deadlock, read it from the log, and fix it with one global order.

```systemverilog
// compile
module tb_top;
  timeunit 1ns; timeprecision 1ns;

  semaphore bus_lock = new(1);
  semaphore mem_lock = new(1);
  int unsigned copies;

  // Copies a block from memory onto the bus: memory port first, then the bus.
  task automatic dma_copy(int unsigned id);
    mem_lock.get(1);
    #3;                                 // read the source block
    bus_lock.get(1);
    $display("[%0t] dma copy %0d on the bus", $time, id);
    #5;
    bus_lock.put(1);
    mem_lock.put(1);
    copies++;
  endtask

  // Fills memory from the bus: the bus first, then the memory port.
  task automatic cpu_fill(int unsigned id);
    bus_lock.get(1);
    #2;                                 // fetch the data from the bus
    mem_lock.get(1);
    $display("[%0t] cpu fill %0d into memory", $time, id);
    #5;
    mem_lock.put(1);
    bus_lock.put(1);
    copies++;
  endtask

  initial begin
    fork
      dma_copy(1);
      begin #1; cpu_fill(2); end
    join
    $display("[%0t] PASS=%0d FAIL=%0d", $time, copies, 2 - copies);
    $finish;
  end

  initial begin
    #200;
    $fatal(1, "WATCHDOG at %0t: copies=%0d, a process is stuck in get()", $time, copies);
  end
endmodule
```

1. Before running anything, predict the log. Which lines print, and when does the run end?

3. Fix the deadlock by changing only one task, so that both tasks use one global order.
4. Confirm that both copy lines print, the run ends with `PASS=2 FAIL=0`, and the watchdog stays silent.

```text
[3] dma copy 1 on the bus
[10] cpu fill 2 into memory
[15] PASS=2 FAIL=0
```

**Reflect.** `cpu_fill` now holds the memory port during its bus fetch, a little longer than it needs. That is the usual price of a global order: some resources are held earlier than strictly necessary, in exchange for a bench that cannot deadlock.

</details>

### Kata 2 (debug challenge): the bus that lets two masters in

**Objective:** find a surplus key, the mirror image of a leaked key.

```systemverilog
// compile
module tb_top;
  timeunit 1ns; timeprecision 1ns;

  semaphore bus_lock = new(1);
  int unsigned busy, collisions;

  task automatic send(string who, int unsigned id);
    bus_lock.get(1);
    busy++;
    if (busy > 1) begin
      collisions++;
      $display("[%0t] COLLISION: %s req %0d shares the bus", $time, who, id);
    end
    if (id == 2) begin                  // the target rejects request 2
      $display("[%0t] %s req %0d rejected", $time, who, id);
      bus_lock.put(1);                  // "make sure the key goes back"
    end else begin
      #10;                              // transfer
    end
    busy--;
    bus_lock.put(1);
  endtask

  initial begin
    fork
      begin send("A", 1); send("A", 2); send("A", 3); end
      begin #15; send("B", 7); end
    join
    if (bus_lock.try_get(2)) begin      // more than one key left?
      $display("[%0t] bus_lock holds 2 keys: one put() too many", $time);
      bus_lock.put(2);
    end
    $display("[%0t] collisions=%0d", $time, collisions);
  end
endmodule
```

**Tasks:**
1. Predict the log before you read the solution.
2. Find the line that creates the extra key.
3. Fix it without adding a second exit.
4. Explain why this bug never hangs, while its mirror image, a missing `put()`, does.

<details>
<summary>Reveal the worked solution</summary>

**Prediction** (illustrative, traced by hand):

```text
[10] A req 2 rejected
[15] COLLISION: B req 7 shares the bus
[25] bus_lock holds 2 keys: one put() too many
[25] collisions=1
```

At 10 ns `send(2)` takes one key and returns two, once in the rejection branch and once at the shared exit, so the bucket now holds 2 keys (§15.3.1). `send(3)` takes one key at 10 ns, and at 15 ns B takes the other while A is still on the bus.

**Fix.** Delete the `bus_lock.put(1)` in the rejection branch. The single `put(1)` at the end already serves both paths:

```systemverilog
// snippet: the rejection path skips the transfer, not the shared exit
if (id == 2) begin
  $display("[%0t] %s req %0d rejected", $time, who, id);
end else begin
  #10;                                  // transfer
end
busy--;
bus_lock.put(1);                        // the only put(1): exactly one per get(1)
```

**Expected output after the fix** (illustrative): B now waits for A's key and runs from 20 to 30 ns.

```text
[10] A req 2 rejected
[30] collisions=0
```

**Why it never hangs.** A surplus key makes `get()` succeed more often, never less, so it cannot cause a hang; instead, mutual exclusion silently breaks. A missing `put()` does the opposite. That is why the end-of-test check tests both directions: `try_get(N)` must succeed and `try_get(1)` must then fail.

</details>
