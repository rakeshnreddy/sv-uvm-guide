  ## Level 1: The Big Idea
  *IEEE 1800-2023, Clause 15.5: Events*

  An **event** is a simple synchronization object. One process can signal an event, and another can wait for it. It's like ringing a doorbell and waiting for someone to answer.

  ## Level 2: Practical Usage

  ### Declaring and Triggering

  -   Declare an event: `event done;`
  -   Trigger: `-> done;` unblocks every process that is **already** waiting on `@done`. A process that reaches `@done` later in the same time step misses it (IEEE 1800-2023 §15.5.2).
  -   Nonblocking trigger: `->> done;` does not trigger now. It schedules the trigger for the NBA region of the current time step (§15.5.1), so processes that reach `@done` during that time step's Active region are already waiting when it fires. It does **not** make the event persistent.
  -   Persistent state: `done.triggered` is true from the trigger until simulation time advances (§15.5.3). `wait(done.triggered);` therefore succeeds whether it runs before or after the trigger in the same time step.
  -   Wait for it: `@done;` for the next trigger, or `wait(done.triggered);` when the trigger may come first in the same time step.

  <InteractiveCode>
  ```systemverilog
  event start, done;

  initial begin
    // Producer thread
    repeat (3) begin
      #10 -> start;          // fire the start event
      @done;                 // wait for acknowledgement
    end
  end

  initial begin
    // Consumer thread
    forever begin
      @start;
      $display("Start seen at %0t", $time);
      #2 -> done;            // safe: the producer has been waiting at @done since t = 10
    end
  end

  initial begin
    // Listener that wakes at t = 12, the same time step as the first "-> done"
    #12 wait (done.triggered);   // passes whether it runs before or after the trigger (§15.5.3)
    // "#12 @done;" here would race with the consumer and could miss it (§15.5.2)
    $display("First completion observed at %0t", $time);
  end
  ```
  </InteractiveCode>

  ## Failure Mode: Lost Event Pulses
  
  **The `->` race:** Events do not queue triggers. If a producer executes `-> done` before the consumer reaches `@done` in the same time step, the consumer misses it and waits for the next trigger, possibly forever (§15.5.2). The standard does not fix the order of processes that wake at the same time, so this code can pass on one simulator and hang on another.

  **Two fixes, for two different reasons:**
  - Wait on the persistent state: `wait(done.triggered)` succeeds whether the trigger came before or after it in the same time step (§15.5.3).
  - Trigger later in the time step: `->> done` fires in the NBA region (§15.5.1), after every process running in that time step's Active region has had the chance to reach `@done`. It is not persistent: a process that only starts waiting after the NBA region can still miss it.

  You can also keep a `bit done_seen` flag, or use `uvm_event`, which counts triggers.

  **The real `.triggered` trap: a zero-delay loop.** Because `done.triggered` stays true for the whole time step, a loop such as `forever begin wait(done.triggered); count++; end` passes the wait again and again without letting time advance — the simulation hangs at that time. Try the *forever wait(done.triggered)* variant above. Inside loops, wait with `@done`, or make sure every iteration advances time.

  **Ordering constraints:** `wait_order(e1, e2)` (or the array form) asserts that events arrive in a given sequence—perfect for handshake protocols. Pair with assertions so violations show up in logs.

  **Leveraging `triggered`:** The built-in `event.triggered` state is true for the remainder of the time step after a trigger. Use `wait(event.triggered)` for a one-shot wait when the trigger and the wait may happen in the same time step.

  **Bridging to UVM:** `uvm_event` adds `wait_on()`, `wait_off()`, callbacks, and a `trigger_cnt`. Manage them through an `uvm_event_pool` so components can look up events by name without hard-coded handles. See [analysis components](/curriculum/T2_Intermediate/I-UVM-2B_TLM_Connections#monitors-scoreboards-and-the-analysis-fabric) for how that integrates with monitors.
