## Quick Take

- **What it is:** A **named event** is a variable of type `event`. It holds a **handle** to a **synchronization object** that one process **triggers** (`-> done;`) and other processes **wait on** (`@(done);` or `wait (done.triggered);`). An event carries no data and keeps no count. It only says "now" (IEEE 1800-2023 §6.17, §15.5).
- **Why it matters:** Generators, drivers, monitors and checkers run as separate processes, and they must agree on *when* something happened: reset finished, an item was sent, the test may end. Events are the lightest way to say so, and the easiest to get subtly wrong. A trigger that fires an instant before its waiter starts waiting is lost, even when both happen at the same simulation time (the same **time slot**). The test then hangs or ends early, and the same code can pass on one simulator and fail on another (§4.7).
- **The Analogy:** A doorbell. Pressing it (`->`) alerts everyone already standing at the door (`@`), and someone who arrives a moment later hears nothing. SystemVerilog adds a light next to the bell that stays on for the rest of that moment (`.triggered`). *Where it breaks:* the light goes out as soon as simulation time advances, so it never tells a later visitor that the bell rang earlier. And an event variable is not the bell but a name for it: two names can share one bell, and moving a name to another bell does not move the people already waiting at the old one.

**You will be able to:**
1. **Predict** whether a waiting process wakes for `->` versus `->>`, and for `@(ev)` versus `wait (ev.triggered)`, when the trigger and the wait fall in the same time slot.
2. **Diagnose** a lost trigger and a zero-delay `.triggered` loop from their symptoms, and fix each one.
3. **Write** a race-free handshake that passes events to tasks and stores them in a class.
4. **Predict** which processes wake after event variables are assigned (merged) or set to `null`.
5. **Write** an ordering check with `wait_order`, and predict where it succeeds or fails for a given trigger order.

## Build Your Mental Model

### Why threads need to say "now"

A testbench (TB) is many processes running at once: an `initial` block that applies reset, a driver loop, a monitor loop, a checker. Most of the time they run independently. At a few moments one of them must tell the others that something has happened: "reset is done, start driving", "the item was sent, make the next one", "the last check passed, end the test".

A shared variable could carry that news, but every reader would have to keep checking it. A **named event** is the built-in alternative. Waiting processes sleep until the event is triggered, and one trigger wakes them all (§15.5). The next lesson adds mailboxes, for news that carries data, and the one after that adds semaphores, for sharing a resource.

### A named event is a handle to a synchronization object

An `event` variable holds no data. It holds a handle to a **synchronization object**, which keeps two things (§6.17, §15.5):

- a **waiting queue**: the processes currently blocked on the event;
- a **triggered state**: set when the event is triggered, and cleared when simulation time advances.

```systemverilog
// snippet
event done;              // a new synchronization object (the default, §6.8 Table 6-7)
event done_too = done;   // a second name for the same object
event empty = null;      // a name that refers to no object at all
```

Because an event is a handle, it behaves like a class handle: assigning one event variable to another makes both names refer to one object. That matters later on this page.

### Trigger with `->`, wait with `@`

- `-> done;` **triggers** the event. It wakes every process waiting on `done` at that moment, and the triggering process carries on with its next statement (§15.5.1).
- `@(done);`, or `@done;`, **waits**. It blocks the calling process until the next trigger (§15.5.2).

The trigger itself is instantaneous and is not stored. The standard compares it to a clock edge that clocks a flip-flop: you see its effect, but you cannot test the edge afterwards (§15.5.1). Only the triggered state, covered below, outlasts it.

Here is the minimal correct use. The consumer starts waiting at t = 0, and the producer triggers at t = 10 ns:

```systemverilog
// compile
module tb_top;
  timeunit 1ns; timeprecision 1ns;

  event done;                        // one synchronization object

  initial begin : consumer
    $display("[%0t] consumer: waiting for done", $time);
    @(done);                         // blocks until the next trigger
    $display("[%0t] consumer: woke", $time);
  end

  initial begin : producer
    #10;                             // the consumer has been waiting since t = 0
    $display("[%0t] producer: -> done", $time);
    -> done;                         // wakes every process waiting on done now
  end
endmodule
```

**Expected output** (illustrative: traced by hand against IEEE 1800-2023, not captured from a simulator). The two lines at t = 10 ns can appear only in this order, because the consumer cannot print before the trigger that wakes it:

```text
[0] consumer: waiting for done
[10] producer: -> done
[10] consumer: woke
```

This works because of one rule: **the wait started before the trigger.** The rest of this page is about what happens when nothing guarantees that.

### Same time slot: the scheduler decides who wins

Now give both processes the same delay: the producer runs `#10 -> done;` and the consumer runs `#10 @(done);`. Both become ready at t = 10 ns in the Active region of the same time slot, which is all the work the simulator does at one simulation time. (Review [F3B: Scheduling Regions](/curriculum/T1_Foundational/F3B_Scheduling_Regions/index) if the regions are new.) The standard lets the simulator run the two processes in either order (§4.7), and `@` catches only triggers that happen after it started waiting (§15.5.2).

**What the four variants showed:**

- **`->` with `@(done)`** is the only race. The model finds two outcomes across the legal orders: if the producer runs first, the consumer stays blocked (§15.5.2).
- **`->` with `wait (done.triggered)`** wakes in every order, because the triggered state is still 1 when a late waiter arrives (§15.5.3).
- **`->>` with `@(done)`** wakes in every order, because the trigger moves to the NBA region, after the consumer is already waiting (§15.5.1).
- **`forever wait (done.triggered)`** wakes and then never stops: the wait passes again and again at t = 10 ns, and time never advances.

The next two sections explain the two fixes and the trap in the fourth variant.

### The triggered state lasts until time advances

Every event has a built-in method, `triggered()`, that returns 1 if the event has been triggered **in the current time slot** and 0 otherwise (§15.5.3, which calls the time slot a "time step"). The trigger sets the state, and it stays set until simulation time advances.

So `wait (done.triggered);` succeeds whether it runs before the trigger or after it in the same time slot (§15.5.3). It turns the edge-like trigger into a level that lasts for the rest of the time slot. Use it for **one-shot waits** whose trigger may already have happened at this time.

It has two limits:

- **It does not remember across time.** A process that reaches `wait (done.triggered);` at t = 11 ns, for a trigger at t = 10 ns, blocks until the next trigger.
- **In a loop it can spin.** `forever begin wait (done.triggered); n++; end` passes the wait, increments, and passes it again, all at the same time, because the state stays 1 until time advances. Time never moves: a **zero-delay loop**. Inside loops, wait with `@(done)`, or make every iteration advance time.

> [!WARNING]
> `wait (done);` without `.triggered` does not wait for a trigger. An event used as a condition is a handle test: 1 if the variable refers to an object, 0 if it is `null` (§15.5.5.3). For any normal event it passes at once.

### `->>`: trigger later in the same time slot

The **nonblocking trigger** `->> done;` does not trigger now. Like a nonblocking assignment, it schedules an update, and that update triggers the event in the **NBA region** of the current time slot (§15.5.1). The NBA region runs only after the Active and Inactive regions are empty (§4.4.2.3, §4.4.2.4). So every process that reaches `@(done)` in the Active region before the NBA region runs is already waiting when the trigger fires. Until then, `done.triggered` still reads 0, because the event has not been triggered yet (§15.5.3).

> [!IMPORTANT]
> `->>` does **not** make the event persistent. It moves one trigger to a later region of the same time slot. A process that starts waiting after the trigger has fired, for example in a later time slot, still misses it. And a process that is woken by the same NBA region, such as one waiting on a signal that a nonblocking assignment updates at this time, runs in the same batch as the trigger. It can catch the trigger or miss it, so the race is back (§4.5, §4.7).

Which fix to choose:

- Change the **waiter** to `wait (ev.triggered)` when one process must not miss a trigger that may already have happened at this time.
- Change the **trigger** to `->> ev` when you own the producer and want every waiter that arms before the NBA region to be covered, without editing each waiter.
- Change the **design** when a waiter might arrive in a later time slot. Keep the news in state, such as a flag or a counter, or send it through a [mailbox](/curriculum/T2_Intermediate/I-SV-5_Synchronization_and_IPC/mailboxes).

### Choosing a wait

| You need to… | Use | Why |
|---|---|---|
| wake on every trigger, inside a loop | `@(ev)` | it waits for the next trigger each time; a trigger that fires while the loop body is still running is missed |
| wait once, when the trigger may already have fired at this time | `wait (ev.triggered)` | the triggered state lasts until time advances (§15.5.3) |
| make your trigger safe for waiters that arm before the NBA region | `->> ev` | it fires in the NBA region (§15.5.1) |
| know that something happened at an earlier time | a flag, a counter or a mailbox | an event forgets as soon as time advances |
| check that several events happen in a given order | `wait_order` | covered below (§15.5.4) |

### Event variables are handles: assignment, merging and `null`

**Assignment.** `done_too = done;` copies the handle, not the object, so both names now refer to one synchronization object. The standard calls this **merging**: a trigger through either name wakes processes waiting through either name (§15.5.5, §15.5.5.1).

**Merging affects only later waits.** The assignment changes which object the name refers to from now on. A process that is already blocked on the name stays in the waiting queue of the object it blocked on, and the standard says it shall never unblock (§15.5.5.1). In the example below, no name refers to that old object any more, so nothing could trigger it anyway. This example is adapted from the one in the standard:

```systemverilog
// compile
module tb_top;                   // adapted from the example in §15.5.5.1
  timeunit 1ns; timeprecision 1ns;

  event E1, E2;                  // two names, two objects: call them A and B

  initial begin : T1
    @(E2);                       // t = 0: T1 joins the waiting queue of B
    $display("[%0t] T1 woke", $time);
  end

  initial begin : T2
    @(E1);                       // t = 0: T2 joins the waiting queue of A
    $display("[%0t] T2 woke", $time);
  end

  initial begin : T3
    #5 E2 = E1;                  // E2 now names A; B still holds T1
    #5 -> E2;                    // t = 10: triggers A
  end
endmodule
```

| Time | Statement | `E1` refers to | `E2` refers to | Queue of A | Queue of B |
|---|---|---|---|---|---|
| 0 | declarations | A | B | empty | empty |
| 0 | T1 runs `@(E2)` | A | B | empty | T1 |
| 0 | T2 runs `@(E1)` | A | B | T2 | T1 |
| 5 | T3 runs `E2 = E1` | A | **A** | T2 | T1 |
| 10 | T3 runs `-> E2` | A | A | empty: T2 wakes | T1, forever |

**Expected output** (illustrative: traced by hand against IEEE 1800-2023). The run prints one line, then ends at t = 10 ns with T1 still blocked and no error (§9.6.1):

```text
[10] T2 woke
```

The fix is to merge **before** any process waits, for example before the processes are forked. The same rule applies to the class properties and task arguments in the next section.

**`null`.** Assigning `null` breaks the link between the variable and its object (§15.5.5.2). Triggering a `null` event does nothing. Waiting on one, with `@` or with `wait (e.triggered)`, is undefined: it may block forever or not at all, and a simulator may warn (§15.5.5.2).

**Comparison.** You can compare events with `==`, `!=`, `===` and `!==`, against another event or against `null`, and you can test an event as a Boolean (§15.5.5.3). That is how you check a suspected merge problem:

```systemverilog
// snippet
if (E1 == E2) $display("E1 and E2 name the same object");
if (E2 == null) $fatal(1, "E2 refers to no synchronization object");
```

### Passing events to tasks and storing them in classes

**Task arguments.** An `event` argument receives a copy of the caller's handle, so the task triggers and waits on the caller's synchronization object. The standard's own example passes an event to a task that triggers it (§15.5.3).

**Class properties.** Constructing an object initializes each property (§8.7), and an event's default value is a new synchronization object (§6.8 Table 6-7). So every object gets its *own* events. Two components see the same event only if they share one object, or if one of them merges its property with the other's handle before anyone waits.

This excerpt from the Make It Work example below shows both. The constructor merges the class's events with the testbench's before any process can wait on them:

```systemverilog
// snippet: excerpt from the Make It Work example
event req, ack;                          // tb_top's events

class requester;
  event req, ack;                        // new objects for every requester...
  function new(event req, event ack);
    this.req = req;                      // ...merged with the caller's at once
    this.ack = ack;
  endfunction
endclass

// Arguments copy the caller's handles, so this task shares tb_top's objects.
task automatic responder(event req, event ack);
  forever begin
    @(req);                              // armed since the previous ack: no race
    $display("[%0t] responder: req seen", $time);
    #2;
    $display("[%0t] responder: -> ack", $time);
    -> ack;
  end
endtask
```

Two mistakes to avoid:

- **Reversing the assignment.** `req = this.req;` in the constructor re-points the *argument*, which is a local copy, and leaves the class with a private object that nobody else waits on. Kata 2 below is this bug.
- **Re-pointing after the waits start.** Assigning a different event to a property while a process is blocked on the old one strands that process, as in the merge example above (§15.5.5.1).

### Checking order with `wait_order`

`wait_order` blocks until the listed events have triggered in the listed order, left to right. It **fails** as soon as an event that is still awaited triggers out of order (§15.5.4). It takes an action block, much like an immediate assertion:

```systemverilog
// snippet: three forms (§15.5.4)
bit ok;
wait_order (a, b, c);                    // a failure calls $error by default
wait_order (a, b, c) else $error("[%0t] a, b, c out of order", $time);
wait_order (a, b, c) ok = 1; else ok = 0;  // record the result, report nothing
```

An `else` clause replaces the default error. An `else` that only calls `$display` prints a message but generates no error, so an out-of-order run can still end clean. Report failures with `$error`, or count them.

Here is how `wait_order (a, b, c)` reacts to six trigger orders, each trigger in its own time slot:

| Triggers, in time order | Result | Rule (§15.5.4) |
|---|---|---|
| a, b, c | succeeds at c | the listed order |
| a, a, b, c | succeeds at c | an event already seen may trigger again |
| a, b, a, c | succeeds at c | the same rule: a was already seen |
| a, c | fails at c | c triggered while b was still awaited |
| b | fails at b | b triggered while a was still awaited |
| a, b, then nothing | still waiting | `wait_order` has no timeout |

Three pitfalls:

- **No timeout.** If an awaited event never fires, the process waits forever. Run the check in a forked thread with a timer, using the isolated `disable fork` pattern from [F2C](/curriculum/T1_Foundational/F2C_Procedural_Code_and_Flow_Control/index).
- **Only the first event can be satisfied by its triggered state** (§15.5.4). The others must trigger while the construct is waiting.
- **Same-time triggers.** If two listed events can fire in the same time slot from different processes, their order is the scheduler's choice (§4.7), and so is the verdict.

`wait_order` checks the order of events that testbench processes trigger. For the order of **signals**, cycle by cycle, write a concurrent assertion instead ([I-SV-4A](/curriculum/T2_Intermediate/I-SV-4A_SVA_Fundamentals/index)).

### Debugging events: symptom, cause, fix

| Symptom in the log | Likely cause | How to confirm | Fix |
|---|---|---|---|
| The run ends early with no error, and a "waiting" line is the last thing one process printed. With a clock or a watchdog running, the run hangs until the watchdog fires instead. | A lost trigger: `->` ran earlier in the same time slot than `@` (§15.5.2). With nothing else scheduled, simulation simply stops (§9.6.1). | Print `$time` and a tag just before the wait and just before the trigger. The same time, with the trigger first, confirms it. | `wait (ev.triggered)` for a one-shot wait, `->>` at the trigger, or arm the wait earlier by design. |
| Simulation time stops, one log line or counter repeats at the same time, and the simulator stays busy. | A loop whose only blocking statement is `wait (ev.triggered)`. | Find the loop that never advances time after the first trigger. | `@(ev)` inside loops, or advance time in every iteration. |
| `wait (ev)` never seems to wait. | It tests the handle, not the trigger (§15.5.5.3). | Read the condition: it has no `.triggered`. | `@(ev)` or `wait (ev.triggered)`. |
| A trigger runs and the names match, but the waiter never wakes. | The two sides refer to different objects: a property was never merged, an assignment ran after the wait started, or each object has its own event. | Compare handles, for example `if (rq.req != req) $error("not merged");` (§15.5.5.3). | Merge before any process waits, or share one object. |
| `-> ev` has no effect. | `ev` is `null` (§15.5.5.2). | `if (ev == null) $fatal(1, "null event");` | Give the variable an object before use. |
| `wait_order` reports a run-time error. | An awaited event triggered out of order (§15.5.4). | Use the error's time, and print every trigger with `$time`. | Fix the order at its source, or fix the check if it is wrong. |
| A process sits in `wait_order` forever. | An awaited event never fires. | A watchdog shows where it stopped. | Add a timeout around the check. |

### Where events belong in a real testbench

Good uses:

- one-time milestones: reset done, configuration loaded, the generator finished;
- handshakes between two TB threads, such as a generator waiting for a driver's "item done";
- sampling triggers: a covergroup can sample on a named event, as in `covergroup cg @(sample_ev);` (§19.3);
- a monitor telling a checker that a time window has closed.

Poor uses:

- **Passing data.** An event carries none, so use a [mailbox](/curriculum/T2_Intermediate/I-SV-5_Synchronization_and_IPC/mailboxes).
- **Counting occurrences.** Triggers are not queued. Two triggers in one time slot can wake a looping waiter once or twice, depending on process order (§4.7).
- **Ordering signals cycle by cycle.** Use SystemVerilog Assertions ([I-SV-4A](/curriculum/T2_Intermediate/I-SV-4A_SVA_Fundamentals/index)).
- **Components in a UVM environment.** Use `uvm_event` and `uvm_barrier` ([I-UVM-1C](/curriculum/T2_Intermediate/I-UVM-1C_UVM_Phasing/index)) or analysis ports ([I-UVM-2B](/curriculum/T2_Intermediate/I-UVM-2B_TLM_Connections/index)). The race rules on this page still apply to `uvm_event`.

Best practice: arm waits before triggers by design; use `wait (ev.triggered)` for one-shot waits that may race; keep `@(ev)` for repeated waits in loops; merge or share event handles before forking; and end every test with a watchdog and a summary line.

**Interview angle.** Expect "Why can `@` miss a trigger, and what are two fixes and their limits?" at every level, and "Why did switching to `uvm_event` not fix it?" at senior level. Try both under Push Further before you read the answers.

## Make It Work

### A request and acknowledge handshake that cannot lose a trigger

Three processes share one handshake made of two events, `req` and `ack`:

- a `requester` object sends three requests. It **stores the events** as class properties, merged with the testbench's in its constructor;
- a `responder` task answers each request 2 ns later. It **receives the events** as task arguments;
- a `check_order` task checks with `wait_order` that every `ack` follows a `req`, and counts the results.

A watchdog ends a stuck run with `$fatal`, and a `final` procedure prints the summary line when the simulation ends (§9.2.3).

```systemverilog
// compile
module tb_top;
  timeunit 1ns; timeprecision 1ns;

  localparam int N = 3;
  localparam bit SPURIOUS_ACK = 1'b0;    // second run: set to 1'b1

  event req, ack;                        // the handshake, shared by every process
  int in_order, out_of_order;            // written only by check_order

  // Events stored in a class. Construction gives req and ack new objects
  // (§8.7); the constructor merges them with the caller's before anyone waits.
  class requester;
    event req, ack;

    function new(event req, event ack);
      this.req = req;
      this.ack = ack;
    endfunction

    task run(int n);
      for (int i = 0; i < n; i++) begin
        #10;                             // the responder is already waiting at @(req)
        $display("[%0t] requester: -> req %0d", $time, i);
        -> req;
        wait (ack.triggered);            // still passes if ack fires in this time slot
        $display("[%0t] requester: ack %0d received", $time, i);
      end
    endtask
  endclass

  // Events passed to tasks: each argument copies a handle, so the task
  // triggers and waits on the caller's synchronization objects.
  task automatic responder(event req, event ack);
    forever begin
      @(req);                            // armed since the previous ack: no race
      $display("[%0t] responder: req seen", $time);
      #2;
      $display("[%0t] responder: -> ack", $time);
      -> ack;
    end
  endtask

  task automatic check_order(event first, event second);
    forever begin
      wait_order (first, second)
        in_order++;
      else begin
        out_of_order++;
        $error("[%0t] handshake out of order: ack without req", $time);
      end
    end
  endtask

  requester rq;

  initial begin : stimulus
    rq = new(req, ack);
    fork
      rq.run(N);
      begin
        #1000;
        $fatal(1, "[%0t] watchdog: the handshake is stuck", $time);
      end
    join_any
    disable fork;                        // stop the watchdog
  end

  initial responder(req, ack);
  initial check_order(req, ack);

  initial begin : bug_injector
    if (SPURIOUS_ACK) begin
      #28;
      $display("[%0t] bug: -> ack with no req", $time);
      -> ack;
    end
  end

  // Runs once, at the end of simulation (§9.2.3).
  final $display("PASS=%0d FAIL=%0d", in_order, out_of_order + (N - in_order));
endmodule
```

**Expected output** (illustrative: traced by hand against IEEE 1800-2023, not captured from a simulator). After the last acknowledgement nothing else is scheduled, so the simulation ends at t = 36 ns (§9.6.1) and the `final` procedure prints the summary:

```text
[10] requester: -> req 0
[10] responder: req seen
[12] responder: -> ack
[12] requester: ack 0 received
[22] requester: -> req 1
[22] responder: req seen
[24] responder: -> ack
[24] requester: ack 1 received
[34] requester: -> req 2
[34] responder: req seen
[36] responder: -> ack
[36] requester: ack 2 received
PASS=3 FAIL=0
```

**Second run: inject the bug.** Set `SPURIOUS_ACK` to `1'b1`. At t = 28 ns a buggy responder fires `ack` with no request. Only `check_order` is waiting on `ack` at that moment, so only it reacts. The other lines do not change. The `Error:` prefix stands for the simulator's own format, which adds the file, the line, the scope and the simulation time (§20.10):

```text
...
[24] requester: ack 1 received
[28] bug: -> ack with no req
Error: [28] handshake out of order: ack without req
[34] requester: -> req 2
...
PASS=3 FAIL=1
```

Why no trigger can be lost, and why the log order is fixed:

- The responder is armed at `@(req)` from t = 0, and again right after each `ack`, 10 ns before the next request.
- The requester waits with `wait (ack.triggered)`, which would still work if a faster responder acknowledged in the same time slot.
- `check_order` restarts in time slots in which `req` did not fire, so a stale `req` never satisfies a new round (see the `wait_order` expert note).
- Every line printed at one time comes either from the process that triggers, before its trigger, or from a process woken by that trigger, after it.

**Run it.** Save the code as `tb_top.sv`. Compile it with SystemVerilog enabled on any simulator that supports classes and `wait_order`, for example on EDA Playground, and simulate the top module `tb_top`. No open-source simulator has been checked with this example yet.

### How to build an event handshake

1. **Declare the events where both sides can see them**: at module scope, in one shared object, or as handles passed to constructors and tasks.
2. **Merge before anyone waits.** Assign class properties from the caller's handles in the constructor, before any process can wait on them.
3. **For every `@(ev)`, ask: can the trigger fire earlier in the same time slot?** If it can, use `wait (ev.triggered)` for a one-shot wait, or trigger with `->>`.
4. **Inside loops, wait with `@(ev)`**, or advance time in every iteration.
5. **Check the order with `wait_order`** in a process that runs for the whole test, and count or report every failure.
6. **End with a watchdog and a summary line** that fails when expected work is missing.

**Checklist before moving on:**

- [ ] Every `@(ev)` is armed before its trigger can fire, or the wait uses `ev.triggered`, or the trigger uses `->>`.
- [ ] No loop waits on `ev.triggered` without advancing time.
- [ ] Event properties and arguments are merged before any process waits on them.
- [ ] Order checks report through `$error` or a counter, and the run ends with a summary line and a `$fatal` watchdog.

## Push Further

### Expert: `->>` with a delay or event control

The full syntax is `->> [delay_or_event_control] ev;` (§15.5.1, Syntax 15-1). The control can be a delay, an event control, or `repeat (n)` followed by an event control (Annex A.6.5). The statement never blocks. When the delay expires or the event occurs, the trigger lands in the NBA region of that time slot (§15.5.1):

```systemverilog
// snippet
->> #5 window_closed;                 // NBA region of the time slot 5 ns from now
->> @(posedge clk) sampled;           // NBA region of the next posedge clk
->> repeat (2) @(posedge clk) done;   // NBA region of the second posedge clk
```

It behaves like an intra-assignment delay on a nonblocking assignment: the current process schedules the trigger and moves on.

**Program blocks (tool-dependent).** Nonblocking assignments made from the Reactive region set update in the Re-NBA region (§4.4.2.8), but §15.5.1 names only the NBA region for `->>`. The standard does not say where a `->>` executed in a `program` block triggers, so do not build on the difference.

### Expert: how waits on events are re-evaluated

- **The fall of the triggered state wakes nothing.** A wait on `ev.triggered` is re-evaluated only when an operand changes, such as the event being triggered. The change from 1 to 0 at the end of the time slot does not affect anything waiting on it (§15.5.3).
- **Event arrays.** `-> evs[i];` triggers one element, because the trigger syntax allows a select (§15.5.1). But changing the index of a named event array inside an event control is not a trigger: a process in `@(evs[i])` does not wake because `i` changed (§15.5.1).
- **`null` handles.** `e.triggered` returns 0 on a `null` event (§15.5.3), yet waiting on a `null` event is undefined (§15.5.5.2). Guard shared handles with `if (e == null)` before waiting on them.
- **Handle tests.** An event used as a condition says nothing about triggers (§15.5.5.3), so `wait (ev)` and `if (ev)` only check that a handle is not `null`.

### Expert: `wait_order` corner cases

- **First-event persistence.** Only the first listed event can be satisfied by its triggered state (§15.5.4). If `a` fired earlier in this time slot, `wait_order (a, b)` starts as if it had already seen `a`.
- **Restarting in a loop.** A checker that loops on `wait_order (req, ack)` restarts in the time slot in which `ack` fired. If `req` also fired in that time slot, the new round accepts that old `req`, by the first-event rule above. Keep the events of one round in different time slots, as the Make It Work example does, or restart only after time has advanced.
- **Repeats.** Events already seen may trigger again without failing the construct (§15.5.4).
- **No timeout.** Wrap the check in a timer when an event may never come; `disable fork` in an isolated wrapper ends a forked check (F2C).
- **Reporting.** An `else` branch replaces the default `$error` (§15.5.4, §20.10). A branch that only calls `$display` keeps failures out of the error count.
- **Same-time triggers.** Two listed events triggered by different processes in one time slot reach the construct in scheduler order (§4.7), so the verdict can differ between simulators.

### Expert: races that differ between simulators

§4.7 names two sources of nondeterminism. Processes that are ready in the Active (or Reactive) region run in any order. And code without a timing control does not have to run as one event: a simulator may suspend a process part-way through it, so other processes can run in between.

So a same-time-slot `->`/`@` pair can pass on one simulator, fail on another, and change with file order or unrelated edits. Passing on every simulator you tried proves nothing: fix the design by arming the wait first, waiting on the state, or using `->>`.

Interleaving also means `data = 42; -> data_ready;` is not atomic: other processes may run between the two statements (§4.7). A waiter still sees the new data, because nothing can wake it on `data_ready` before the trigger. So update the data first, then trigger.

**Tool-dependent:** what you see when a process loops without advancing time. A `wait` whose condition is already true does not block (§9.4.3), so the loop never hands control back to the scheduler, and the standard does not say what happens next. Expect simulation time to freeze while the simulator stays busy, until a tool-specific limit or your job's wall-clock timeout ends the run. Give every regression job a wall-clock timeout.

### Expert: from `event` to `uvm_event`

[I-UVM-1C](/curriculum/T2_Intermediate/I-UVM-1C_UVM_Phasing/index) teaches `uvm_event`. Here is how it maps onto this page (IEEE 1800.2-2020 §10.1; uvm-core 2020.3.1 `src/base/uvm_event.svh`):

- `uvm_event_base` wraps a SystemVerilog `event` and adds a persistent **on** bit. `trigger()` sets it (§10.1.2.2.4) and `reset()` clears it (§10.1.1.2.8).
- `wait_trigger()` (§10.1.1.2.4) is `@` on the wrapped event, so it has the same race when the trigger and the wait share a time slot. The comment in the uvm-core source says so.
- `wait_ptrigger()` (§10.1.1.2.5) checks the triggered state first: it is the `wait (ev.triggered)` form.
- `wait_on()` (§10.1.1.2.2) returns at once while the event is on, which lasts across time until `reset()`.
- It does not count or queue triggers.
- **`reset()` and waiting processes (uvm-core impl.).** In uvm-core 2020.3.1, `reset()` points the wrapped event at a new synchronization object (`m_event = e;`). A process still blocked in `wait_trigger()` or `wait_ptrigger()` stays on the old object, like T1 in the merge example above, and never wakes. `reset(1)` triggers the waiting processes first (§10.1.1.2.8).

So replacing `@(ev)` with `wait_trigger()` does not fix a race. `wait_ptrigger()` fixes it within a time slot, and `wait_on()` across time. UVM components can also look events up by name in a `uvm_event_pool` (§10.4.1) instead of sharing handles directly.

### Kata 1 (guided): make a zero-time handshake race-free, two ways

**Starter code.** The producer and the consumer meet at time 0:

```systemverilog
// compile
module tb_top;
  timeunit 1ns; timeprecision 1ns;

  event data_ready;
  int data;

  initial begin : producer
    data = 42;
    -> data_ready;                     // t = 0
  end

  initial begin : consumer
    @(data_ready);                     // t = 0: may already be too late
    $display("[%0t] consumer got %0d", $time, data);
  end
endmodule
```

**Tasks:**

1. Predict every output this code can legally produce.
2. Fix it by editing **only the consumer**. State one limit of your fix.
3. Undo that, and fix it by editing **only the producer**. State one limit of this fix.
4. Three consumers, written by three engineers, wait on `data_ready`. Which fix do you prefer, and why?
5. Stretch: the producer now sends 42, 43 and 44 at t = 0, 10 and 20 ns, and the consumer receives them in a loop. Which trigger and which wait do you use?

<details className="my-4 rounded-xl border border-border/70 p-3">
<summary className="cursor-pointer font-semibold">Show the worked solution</summary>

1. **Two outputs.** If the consumer runs first, it prints `[0] consumer got 42`. If the producer runs first, the trigger is lost (§15.5.2): nothing prints, and the simulation ends at time 0 with the consumer blocked and no error (§9.6.1).
2. **Consumer only:** `wait (data_ready.triggered);`. It passes in either order, because the triggered state lasts until time advances (§15.5.3). *Limit:* it covers only the same time slot, and inside a loop it spins.
3. **Producer only:** `->> data_ready;`. The trigger moves to the NBA region of time 0, after the consumer has started waiting (§15.5.1). *Limit:* it is not persistent, so a consumer that starts waiting after the trigger has fired, for example in a later time slot, still misses it.
4. **The producer fix.** One change covers every consumer that starts waiting before the NBA region, so nobody has to remember the rule. If a consumer might be late by more than a time slot, neither fix is enough: keep the news in state, or use a mailbox.
5. **`->>` at the producer and `@` in the loop.** A `wait (data_ready.triggered)` loop would spin at time 0 after the first value. The loop version:

```systemverilog
// compile
module tb_top;
  timeunit 1ns; timeprecision 1ns;

  event data_ready;
  int data;

  initial begin : producer
    for (int i = 0; i < 3; i++) begin
      data = 42 + i;
      ->> data_ready;                  // NBA region: every Active waiter is armed
      #10;
    end
  end

  initial begin : consumer
    forever begin
      @(data_ready);                   // @ in a loop: one wake per trigger
      $display("[%0t] consumer got %0d", $time, data);
    end
  end
endmodule
```

Expected output (illustrative, traced by hand):

```text
[0] consumer got 42
[10] consumer got 43
[20] consumer got 44
```

### Kata 2 (debug): the watchdog fires

A teammate changed two lines in the Make It Work example. Now the run prints the first request, nothing more until the watchdog, and a failing summary. As before, `Fatal:` stands for the simulator's own message format:

```systemverilog
// snippet: the changed constructor in class requester
function new(event req, event ack);
  req = this.req;                      // changed
  ack = this.ack;                      // changed
endfunction
```

```text
[10] requester: -> req 0
Fatal: [1000] watchdog: the handshake is stuck
PASS=0 FAIL=3
```

1. At t = 1000 ns, which processes are blocked, and on which synchronization objects?
2. Prove your diagnosis with one line of code in the `stimulus` block.
3. Fix it.

<details className="my-4 rounded-xl border border-border/70 p-3">
<summary className="cursor-pointer font-semibold">Show the worked solution</summary>

1. The changed lines assign to the **arguments**, which are local copies of the caller's handles, so the properties keep the objects they received at construction (§8.7; §6.8 Table 6-7). The requester's `-> req` at t = 10 ns triggers its private object, which nobody waits on. So:
   - the requester is blocked in `wait (ack.triggered)` on its private `ack` object;
   - the responder is blocked in `@(req)` on `tb_top`'s `req` object;
   - `check_order` is blocked in `wait_order`, waiting for `tb_top`'s `req`.

   At t = 1000 ns the watchdog calls `$fatal`, which ends the simulation (§20.10), and the `final` procedure reports `PASS=0 FAIL=3`.
2. After `rq = new(req, ack);`, add `if (rq.req != req) $error("rq.req is not merged with req");`. Events can be compared with `!=` (§15.5.5.3), and this one fires.
3. Assign the properties from the arguments, before any process waits:

```systemverilog
// snippet
function new(event req, event ack);
  this.req = req;
  this.ack = ack;
endfunction
```
