## Quick Take
- **What it is:** A **class** is a type that bundles data and methods. `new` creates an **object** of that class. A class variable never holds the object itself: it holds a **handle** that refers to the object, or `null`.
- **Why it matters:** UVM is built from classes. Most OOP bugs in a testbench are handle bugs: two names for one object, a copy that still shares a nested object, a scoreboard that stores an item the monitor later overwrites, or a call through a handle that was never constructed.
- **The picture to keep:** **a handle is an arrow, not the box.** Assignment copies the arrow. `new` builds a box. When no arrow reaches a box any more, SystemVerilog reclaims it for you.
- **The Analogy:** A handle is a house address written on a card. Copying the card gives you two cards and still one house. Repainting the house through either card changes the one house.

> **Note:** Mastering OOP is the gatekeeper skill between procedural benches and professional-grade UVM environments.
> *SystemVerilog OOP is formally defined in **IEEE 1800-2023, Clause 8: Classes**.*

### Before you start
- Tier 1 only previewed a class. This module is where classes, objects and handles are taught properly, so you do not need prior OOP experience.

## Build Your Mental Model

### A handle is an arrow, not the box

Three rules explain almost every handle bug you will meet:

1. Declaring `packet p1;` creates a variable that holds a handle. Its initial value is `null`; no object exists yet (§8.4, §8.12).
2. `p1 = new;` allocates an object, initializes its properties, then runs the constructor (§8.7). Only then does `p1` refer to something.
3. `p2 = p1;` copies the handle. There is still one object, now reachable through two names (§8.12).

### Classes and objects: blueprint, object, handle
<InteractiveCode>
```systemverilog
// Blueprint for a reusable transaction
class BasePacket;
  rand bit [31:0] addr;
  rand bit [31:0] data;

  function void print();
    $display("Packet addr=0x%h data=0x%h", addr, data);
  endfunction
endclass

module demo;
  BasePacket pkt1, pkt2;   // two handles, both null

  initial begin
    pkt1 = new();          // one object
    pkt2 = pkt1;           // still one object, two names
    void'(pkt1.randomize());
    pkt2.print();          // prints the values pkt1 just randomized
  end
endmodule
```
</InteractiveCode>

Declare the handle first and call `new` as a statement. Writing `BasePacket p = new();` inside an `initial` block of an ordinary module or program is illegal: a static variable with an initializer needs an explicit `static` or `automatic` keyword (§6.21). With `static`, the `new` runs only once at time zero, which surprises people inside loops.

### Static members: one box for the whole class

A `static` property exists once per class, not once per object, and it exists before any object is created (§8.9). Every handle, and the class scope `packet::count`, names the same storage. A `static` method behaves like an ordinary subroutine scoped inside the class: it has no `this`, can only touch static members, and cannot be virtual (§8.10).

<InteractiveCode>
```systemverilog
class packet;
  static int count = 0;   // shared by every packet (§8.9)
  int id;

  function new();
    count++;              // runs once per new, never for a shallow copy
    id = count;
  endfunction

  static function int created();  // no object needed (§8.10)
    return count;
  endfunction
endclass

module demo;
  packet a, b, c;
  initial begin
    a = new;
    b = new;
    c = new a;            // shallow copy: the constructor does not run (§8.12)
    $display("%0d %0d %0d", packet::count, packet::created(), c.id);  // 2 2 1
  end
endmodule
```
</InteractiveCode>

You already rely on this in UVM: `my_driver::type_id::create("drv", this)` calls a static function of a registry class, without any object in hand.

### Object lifetime and null handles

- **Lifetime is automatic.** An object lives as long as some handle in an active scope can reach it, directly or through other objects. When none can, it becomes unreachable and is eligible for reclamation (§8.29). There is no `delete` or `free` for class objects.
- **Null is the default.** Every class variable starts as `null`. Test with `if (h == null)` (§8.4).
- **Calling through null is illegal.** Touching a non-static member or calling a virtual method through a null handle is illegal; the result is indeterminate and simulators stop with a null-object access error (§8.4). Static members stay reachable through a null handle.
- **Where null handles come from in a testbench:** a missing `new` or `type_id::create`, a `uvm_config_db::get` that found nothing, or a `$cast` called as a function whose return value was ignored.

```systemverilog
if (cfg == null)
  $fatal(1, "cfg was never constructed or never set in config_db");
```

The 2023 standard also adds `weak_reference#(T)` (§8.30), a reference that does not keep its object alive. Check that your simulator supports it before you use it.

### Encapsulation: guard the internals
<InteractiveCode>
```systemverilog
class CrcPacket;
  rand bit [7:0] payload;
  local bit [3:0] crc;

  function void calculate_crc();
    crc = ^payload; // toy CRC
  endfunction

  function bit [3:0] get_crc();
    return crc;
  endfunction
endclass
```
</InteractiveCode>
Encapsulation hides implementation details (`crc`) while exposing intent (`calculate_crc`, `get_crc`). `local` members are visible only inside the class; `protected` members are also visible to subclasses (§8.18). This prevents careless external writes and keeps APIs clean.

### Inheritance and polymorphism: specialize without rewriting
<InteractiveCode>
```systemverilog
class BasePacket;
  virtual function void pack();
    $display("[BasePacket] generic packing");
  endfunction
endclass

class EthernetPacket extends BasePacket;
  rand bit [47:0] dst_mac;

  function void pack();   // still virtual: inherited from BasePacket (§8.20)
    $display("[EthernetPacket] packing MAC=%h", dst_mac);
  endfunction
endclass

class UsbPacket extends BasePacket;
  function void pack();
    $display("[UsbPacket] packing USB framing");
  endfunction
endclass

class GenericDriver;
  task run(BasePacket pkt);
    pkt.pack(); // resolves to the object's implementation
  endtask
endclass
```
</InteractiveCode>
A single `GenericDriver` talks to any `BasePacket` descendant, exactly as UVM drivers use `uvm_sequence_item` handles.

Which `pack()` runs depends on two things you can see in the code: the handle's declared class and whether the method is `virtual`. Try a `base_txn` handle holding a `bad_crc_txn` object, predict, then make `describe()` non-virtual and predict again.

### Forward declarations with `typedef class`

Two classes that refer to each other need a forward declaration, because a class name must be known before a variable of that type is declared (§8.27). You will also need one when `include` order puts a user before the definition.

```systemverilog
typedef class scoreboard;   // "scoreboard is a class, defined later"

class monitor;
  scoreboard sb;            // legal thanks to the forward declaration
endclass

class scoreboard;
  monitor mon;
endclass
```

The keyword `class` in `typedef class scoreboard;` is optional documentation: `typedef scoreboard;` means the same (§8.27).

### Interface classes: one class, several roles

A class can extend only one base class, but it can **implement** any number of interface classes (§8.26). An interface class contains only pure virtual methods, types and parameters, and every implementation must be a virtual method.

```systemverilog
interface class has_crc;
  pure virtual function bit check_crc();
endclass

interface class printable;
  pure virtual function string to_string();
endclass

class base_txn;
  int addr;
endclass

class crc_txn extends base_txn implements has_crc, printable;
  bit [7:0] crc;
  virtual function bit check_crc();      return (crc == 8'h5a); endfunction
  virtual function string to_string();   return $sformatf("addr=%0h crc=%0h", addr, crc); endfunction
endclass
```

A `printable` handle can refer to any object whose class implements `printable`, regardless of its base class. Converting it back to `crc_txn` needs `$cast`, checked at run time (§8.16).

## Make It Work
1. **Define your transactions:** Start with a base class containing shared fields, methods, and automation (`rand`, `constraint`, `copy`/`compare`).
2. **Specialize via inheritance:** Create derived packet classes for protocol-specific fields. Override virtual methods (for example `pack` or `convert2string`).
3. **Drive polymorphically:** Use base-class handles (`BasePacket pkt_h`) across sequencers, drivers, and scoreboards to minimize coupling.
4. **Instrument with encapsulation:** Expose intent methods (`start_transfer`) while protecting internals with `local`/`protected` members.
5. **Decide who owns each object:** Whoever stores an item it did not create stores a copy, and whoever publishes an item never modifies it afterwards.

### Debug it: the scoreboard whose expected items change

This is the most common handle bug in real testbenches. Read the symptom, select the line that causes it, then try fixes; the model reruns the monitor and the scoreboard reads the stored items back.

## Push Further
- Implement factory overrides (UVM `type_id::create`) to swap derived packets at runtime.
- Explore abstract classes and pure virtual methods for defining protocol templates ([Parameterized and Abstract Classes](./parameterized-classes)).
- IEEE 1800-2023 adds the method specifiers `:initial`, `:extends` and `:final` (§8.20), which let the compiler catch an accidental override or a missing one. Check simulator support before using them.
- Profile simulation performance when using deep inheritance hierarchies, and know when composition is cleaner.
