## Quick Take

- **What it is:** SystemVerilog has three operations that all look like "copy", and they copy different amounts. `p2 = p1` copies only the **handle**, the reference to an object. `p2 = new p1` builds a second object and copies its properties, but any object it refers to is still shared: a **shallow copy** (IEEE 1800-2023 §8.12). A **deep copy** duplicates the nested objects too. The language has no built-in deep copy, so you write it yourself as a `copy()` method, plus a `clone()` method that creates the new object and copies into it.
- **Why it matters:** Testbench components pass handles, not objects. A scoreboard that stores a handle to an object the producer later reuses, or a copy that still shares a nested header, sees its stored expected data change without any error message. These bugs make tests fail for no visible reason, or, worse, pass when they should fail.
- **The Analogy:** Photocopying a folder gives you new pages you can scribble on freely. But a sticky note in the folder saying "the header is in drawer 3" is photocopied too, and both notes still point at the same drawer: change what is in the drawer and both folders see it. A deep copy also copies drawer 3's contents into a new drawer 4 and updates the copied note to point there. *Where it breaks:* a folder never changes its kind when you copy it, but an object reached through a base-class handle can be a subclass object, and a `clone()` written in the base class quietly builds the wrong kind of object unless it is `virtual`.

## Build Your Mental Model

This page uses three ideas from earlier lessons. A **class** describes an object's properties and methods; `new` builds an **object** and returns a **handle**, which a class variable holds ([I-SV-1 overview](/curriculum/T2_Intermediate/I-SV-1_OOP/index)). A **virtual** method called through a base-class handle runs the version in the object's own class, and `$cast` safely converts a base-class handle into a subclass handle ([Polymorphism Pitfalls and Type Casting](/curriculum/T2_Intermediate/I-SV-1_OOP/polymorphism-pitfalls)).

### Three things that look like "copy"

Every example on this page uses the same two classes, so you can compare them directly: a `packet` with an `int id`, a queue of values `int data[$]` and a **nested object**, `header hdr`, which is a handle to a second object of class `header`. A `header` holds one `int len`.

| You write | New `packet` objects | New `header` objects | What the two `packet` handles share afterwards |
|---|---|---|---|
| `p2 = p1;` | none | none | everything: `p1` and `p2` name the same object |
| `p2 = new p1;` | one | none | the `header`: both `hdr` handles refer to one object |
| `p2 = new; p2.copy(p1);` (your deep copy) | one | one (built by `p2 = new`) | nothing |
| `p2 = p1.clone();` (your clone) | one, of `p1`'s real class | one | nothing |

The rest of this section takes each row in turn. The core path is the first five subsections; the UVM subsection and the pitfalls table are practitioner depth.

The **heap** is the memory where objects live. The visual below draws each handle as an arrow and each object as a box, and generates its code from the same model that draws the boxes. Its `packet` class is the one on this page, plus a `static int count` that only the `static-count` scenario uses.

**What the four scenarios showed:**
- **`aliasing`:** `p2 = p1` copied an arrow. There was still one `packet` box, so a write through `p2` was visible through `p1`.
- **`shallow-copy`:** `new p1` copied the box but not the inner arrow's target. `p2` got its own `id` and its own `data` queue, but its `hdr` arrow pointed at `p1`'s `header`, so `p2.hdr.len = 9` changed `p1.hdr.len` too.
- **`deep-copy`:** only `copy()` left two `header` boxes, so a write through `p3` could not reach `p1`.
- **`static-count`:** three `packet` boxes exist after `p3 = new p1`, but `packet::count` reads 2: a shallow copy runs no constructor (rule 2 below, §8.12), and `count` is one variable for the whole class, not a field in each box (§8.9).

### Assignment copies the handle

Assigning one class variable to another copies the handle, never the object (§8.12). Afterwards both variables refer to one object, so this is not a copy at all; it is a second name. The [I-SV-1 overview](/curriculum/T2_Intermediate/I-SV-1_OOP/index) covers this in depth; here is the one-line reminder, as code.

```systemverilog
// compile
module tb_top;
  class packet;
    int id;
  endclass

  initial begin
    packet p1, p2;
    p1 = new;
    p2 = p1;                        // copies the handle: one object, two names
    p2.id = 7;
    $display("p1.id=%0d", p1.id);   // the write through p2 is visible through p1
  end
endmodule
```

**Expected output** (traced by hand from §8.12, not from a simulator run):

```text
p1.id=7
```

### Shallow copy: `p2 = new p1`

`new` followed by an expression that refers to an object makes a **shallow copy** (§8.12). The standard defines exactly what happens:

1. **A new object of the source object's class is allocated.** If `p1` is a `packet` handle that holds a subclass object, the copy is a subclass object too.
2. **No constructor runs, and no declaration initializer runs.** `header hdr = new;` in the class does **not** build a new `header` for the copy, and a counter incremented in `new()` does not count shallow copies.
3. **Every property is copied as a value.** An `int`, a `string`, a queue of `int` and a dynamic array of `int` are values: assigning an array copies each element (§7.6), so the copy gets its own queue. The internal state used by randomization is copied too (see [Push Further](#expert-what-else-a-shallow-copy-copies)).
4. **A class-handle property is copied as a handle.** The object it refers to is not duplicated, so both objects now share it. This applies to every object a class refers to: a nested transaction, a mailbox, a semaphore.
5. **A queue or array of handles gets its own container, holding the same handles.** The container is a value, so it is copied; its elements are handles, so the objects behind them are shared. (The next subsection shows this.)

Two syntax rules: `new p1` may appear only on the right of an assignment or in a declaration, and the expression after `new` must refer to an object (Syntax 8-2). A typed constructor call (`packet::new`, §8.8) cannot be used for a shallow copy (§8.12).

```systemverilog
// compile
module tb_top;
  class header;
    int len = 4;
  endclass

  class packet;
    int    id;
    int    data[$] = {1, 2};    // a queue of values
    header hdr = new;           // a nested object: the property holds a handle
  endclass

  initial begin
    packet p1, p2;
    p1 = new;
    p1.id = 5;
    p2 = new p1;                // shallow copy: no constructor, no initializers
    p2.id = 6;                  // p2's own int
    p2.data.push_back(3);       // p2's own queue: its elements were copied
    p2.hdr.len = 9;             // p1.hdr and p2.hdr are ONE header object
    $display("p1: id=%0d data=%p hdr.len=%0d", p1.id, p1.data, p1.hdr.len);
    $display("p2: id=%0d data=%p hdr.len=%0d", p2.id, p2.data, p2.hdr.len);
  end
endmodule
```

**Predict first.** Write down both lines before you open the output. In particular: what do `p1.data` and `p1.hdr.len` hold after the last two writes through `p2`? Rules 3 and 4 decide.

**When a shallow copy is enough.** If a class holds only values (integers, strings, queues and arrays of values), `new h` is a complete copy. The moment it holds a handle to an object you might change, it is not.

A deep copy of such a queue copies each element's contents into a new object, as the next subsection shows.

### Deep copy: write your own `copy()`

A **deep copy** duplicates an object together with every object it refers to, so the copy shares nothing with the original. SystemVerilog has no built-in deep copy; §8.12 says that custom code is typically needed, and shows the convention used everywhere: a method `copy()` that copies its argument **into the object it is called on**.

The rules for a correct `copy()`:
- **Copy contents, never handles.** For a nested object, call its own `copy()`: `hdr.copy(rhs.hdr)`. Writing `hdr = rhs.hdr;` turns that field back into a shallow copy.
- **Handle `null` on both sides.** If the source's handle is `null`, make the copy's handle `null`. If the copy has no nested object yet, build one before copying into it. Reject a `null` source outright, because there is nothing to copy.
- **Copy every level.** Each nested class has its own `copy()`, and each `copy()` calls the next one down.

This example matches the visual's `deep-copy` scenario line for line.

```systemverilog
// compile
module tb_top;
  class header;
    int len = 4;

    function void copy(header rhs);
      len = rhs.len;
    endfunction
  endclass

  class packet;
    int    id;
    int    data[$] = {1, 2};
    header hdr = new;

    // Deep copy: fill THIS object from rhs; share nothing with it.
    function void copy(packet rhs);
      if (rhs == null) $fatal(1, "packet::copy: null rhs");
      id   = rhs.id;
      data = rhs.data;                    // a queue of values: elements copied (§7.6)
      if (rhs.hdr == null) hdr = null;    // nothing to copy: mirror the null
      else begin
        if (hdr == null) hdr = new;       // make sure this object owns a header
        hdr.copy(rhs.hdr);                // copy the contents, not the handle
      end
    endfunction
  endclass

  initial begin
    packet p1, p3;
    p1 = new;
    p1.hdr.len = 9;
    p3 = new;                             // runs hdr = new: header@2 belongs to p3
    p3.copy(p1);                          // copies len 9 INTO header@2
    p3.hdr.len = 2;                       // changes only header@2
    $display("p1.hdr.len=%0d p3.hdr.len=%0d same=%0d", p1.hdr.len, p3.hdr.len,
             p1.hdr == p3.hdr);
  end
endmodule
```

```text

```

`$fatal` (§20.10) stops the run with a message. That is this page's choice for a broken call; UVM's `copy()` reports an error and returns instead (see [How UVM splits the same job](#how-uvm-splits-the-same-job)).

**A queue of handles, copied deeply.** Rebuild the queue and give each element its own object:

```systemverilog
// snippet: a deep copy() for the burst class above
function void copy(burst rhs);
  header h;
  if (rhs == null) $fatal(1, "burst::copy: null rhs");
  beats.delete();                       // drop this object's old beats
  foreach (rhs.beats[i]) begin
    h = null;
    if (rhs.beats[i] != null) begin
      h = new;                          // a header owned by this burst
      h.copy(rhs.beats[i]);             // contents, not the handle
    end
    beats.push_back(h);                 // a null beat stays null
  end
endfunction
```

### Comparing copies: `==` asks "the same object?"

Once you can make copies, you need to check them. `==` and `!=` on two class handles compare the **handles** (§11.4.5): they ask whether both refer to the same object, never whether the objects hold equal values. So a scoreboard that writes `if (exp == act)` reports a mismatch for two distinct objects with identical contents, and reports a match whenever it compares a handle with itself, for example two stored handles to one reused object.

To compare by value, write a `compare()` method next to `copy()`. It returns 1 when every property matches, comparing nested objects by their contents, and is null-safe. You will write one in [Make It Work](#make-it-work). Debugging hint: when printing two items that "should" match, print the handles' equality too (`exp == act`); a 1 means you are comparing an object with itself.

### `clone()`: a copy that keeps the object's real class

`copy()` fills an object that already exists, so the caller must build the right kind of object first. When code holds only a base-class handle, as a generator holding a "template" `packet` does, it does not know the object's real class. **`clone()`** solves this: it builds a new object of the right class and copies into it, and the caller just writes `q = p.clone();`.

For `clone()` to build the right class through a base-class handle, three things must hold:
- **`clone()` is virtual, and every subclass overrides it** to construct an object of its own class. A call through a `packet` handle then runs the version in the object's class (§8.20).
- **`copy()` is virtual too,** so that copying through a base-class handle copies the whole object, subclass fields included.
- **The subclass `copy()` keeps the base-class argument type and uses `$cast`.** An override must have the same argument types as the method it overrides (§8.20), so `crc_packet::copy` still takes a `packet rhs`. It checks with `$cast` that `rhs` really holds a `crc_packet`, calls `super.copy(rhs)` for the base part, and then copies its own fields.

```systemverilog
// compile
module tb_top;
  class header;
    int len = 4;
    function void copy(header rhs);
      len = rhs.len;
    endfunction
  endclass

  class packet;
    int    id;
    header hdr = new;

    virtual function void copy(packet rhs);
      if (rhs == null) $fatal(1, "packet::copy: null rhs");
      id = rhs.id;
      if (rhs.hdr == null) hdr = null;
      else begin
        if (hdr == null) hdr = new;
        hdr.copy(rhs.hdr);
      end
    endfunction

    virtual function packet clone();
      packet c = new;     // class methods are automatic (§8.6): a new object per call
      c.copy(this);
      return c;
    endfunction
  endclass

  class crc_packet extends packet;
    bit [7:0] crc;

    virtual function void copy(packet rhs);   // same argument type as packet::copy
      crc_packet r;
      if (!$cast(r, rhs))                      // check first, before changing anything
        $fatal(1, "crc_packet::copy: rhs is null or not a crc_packet");
      super.copy(rhs);                         // the base part: id and hdr
      crc = r.crc;                             // then this class's part
    endfunction

    virtual function packet clone();          // may also return crc_packet (§8.20)
      crc_packet c = new;                      // build an object of THIS class
      c.copy(this);                            // virtual: runs crc_packet::copy
      return c;
    endfunction
  endclass

  initial begin
    packet     p, q;
    crc_packet orig, back;
    orig = new;
    orig.id = 3;
    orig.crc = 8'h5a;
    orig.hdr.len = 7;
    p = orig;                       // a base-class handle to a subclass object
    q = p.clone();                  // virtual: runs crc_packet::clone
    if (!$cast(back, q)) $fatal(1, "clone lost the subclass");
    $display("back: id=%0d crc=%h hdr.len=%0d same_hdr=%0d",
             back.id, back.crc, back.hdr.len, back.hdr == orig.hdr);
  end
endmodule
```

**Expected output** (traced by hand):

```text
back: id=3 crc=5a hdr.len=7 same_hdr=0
```

**What goes wrong without each piece:**
- **`clone()` not virtual:** `p.clone()` runs `packet::clone`, which builds a plain `packet`. The `crc` field is lost and `$cast(back, q)` returns 0. No error is reported unless you check that `$cast`.
- **A subclass that does not override `clone()`:** it inherits `packet::clone`, so it is cloned as a plain `packet` even though `clone()` is virtual.
- **A forgotten `super.copy(rhs)`:** the base part (`id`, `hdr`) keeps the new object's default values.
- **An unchecked `$cast`:** if `rhs` is not a `crc_packet`, `r` stays `null` and `r.crc` is a null-handle access. Call `$cast` as a function inside `if (...)`. Called as a task, a failing `$cast` is a run-time error instead of a 0 (§6.24.2).

### How UVM splits the same job

You meet the same pattern again in UVM, which comes later in this course: every UVM transaction class (a **sequence item**) derives from the library's base class `uvm_object`. UVM keeps the idea but splits `clone()` and `copy()` differently, so that you override only one small method. In uvm-core 2020.3.1 (`uvm_object.svh`, `uvm_copier.svh`):
- **`clone()`** is virtual but written once, in `uvm_object`: it calls `create(get_name())` and then `copy(this)`. You do not override it.
- **`create()`** builds an object of your class. The `` `uvm_object_utils `` macro, which every UVM object class uses, generates it for you, so `clone()` builds the right class without a per-class override.
- **`copy()`** is **not** virtual. It reports `` `uvm_error("OBJ/COPY", …) `` and returns if `rhs` is `null`, then passes the work to a copier policy object, whose `copy_object()` copies any fields registered with **field macros** (the `` `uvm_field_* `` macros, which automate copying, comparing and printing) and then calls your **`do_copy()`**.
- **`do_copy()`** is the virtual hook you override. Call `super.do_copy(rhs)` first, then `$cast` and copy your fields (IEEE 1800.2-2020 §5.3.8.2).

### Common pitfalls, and how they show up

These are the copy bugs that reach real testbenches. A **monitor** is the component that watches the pins of the design under test (DUT) and publishes each observed transaction; a **scoreboard** stores expected transactions and compares each observed one against them.

| Symptom in the log | Cause | Fix |
|---|---|---|
| Every stored item shows the last values written; a "mismatch" for all but the last one | A producer reuses one object and the consumer stores its handle (`exp_q.push_back(t)`) | Producers build a new object per transaction; a consumer that keeps an item stores `t.clone()` |
| Stored items have correct `id`s but every nested field (a header, a payload object) shows the latest value | A shallow copy (`new t`) or `hdr = rhs.hdr` inside `copy()` | Deep-copy nested objects with their own `copy()` |
| A cloned subclass item loses its extra fields, or `$cast` back to the subclass fails | `clone()` not virtual, or a subclass did not override it | Make `clone()` virtual; override it in every subclass that adds fields |
| A copied item has default base fields (id 0, a fresh header) | A subclass `copy()` without `super.copy(rhs)` | Call `super.copy(rhs)` in every override |
| A null-object error inside `copy()` | Unchecked `$cast`, or no null check on `rhs` or a nested handle | `if (!$cast(...))`, and handle null on both sides |
| A scoreboard flags equal items as mismatches, or never flags a corrupted one | `exp == act` compares handles (§11.4.5) | Compare by value with `compare()` |
| A transaction sent through a mailbox changes after it is sent | The mailbox holds the handle, and the sender keeps editing the object | Send a new object or a clone each time ([I-SV-5 Mailboxes](/curriculum/T2_Intermediate/I-SV-5_Synchronization_and_IPC/mailboxes)) |

- `=` copies a handle; `new h` copies one object and shares everything it refers to; only your `copy()` and `clone()` copy as deep as you write them.
- A queue of values is copied by `new h`; a queue of handles is copied as handles.
- `copy()` copies contents into objects the copy owns, and handles `null` on both sides.
- `clone()` and `copy()` are virtual; each subclass overrides both, keeps the base argument type, checks `$cast` and calls `super.copy`.
- Anything that keeps an item it did not create stores a copy; anything that publishes an item never changes it afterwards.

## Make It Work

### Worked example: a generator that clones before it stores

This is the copy-before-store pattern every testbench needs. A **generator** is the testbench component that creates stimulus transactions. This one keeps a single **template** object, changes it for each transaction, and stores a clone of it in `sent`, the list a scoreboard would use as its expected items. The template is a `crc_packet` held through a `packet` handle, so only a virtual `clone()` keeps its class.

```systemverilog
// compile
module tb_top;

  class header;
    int len = 4;

    function void copy(header rhs);
      len = rhs.len;
    endfunction
  endclass

  class packet;
    int    id;
    header hdr = new;

    virtual function void copy(packet rhs);
      if (rhs == null) $fatal(1, "packet::copy: null rhs");
      id = rhs.id;
      if (rhs.hdr == null) hdr = null;
      else begin
        if (hdr == null) hdr = new;
        hdr.copy(rhs.hdr);                    // contents, not the handle
      end
    endfunction

    virtual function packet clone();
      packet c = new;
      c.copy(this);
      return c;
    endfunction

    // Compare by value: == on two handles only asks "the same object?"
    virtual function bit compare(packet rhs);
      if (rhs == null) return 0;
      if (id != rhs.id) return 0;
      if ((hdr == null) != (rhs.hdr == null)) return 0;
      if (hdr != null && hdr.len != rhs.hdr.len) return 0;
      return 1;
    endfunction

    virtual function string convert2string();
      if (hdr == null) return $sformatf("id=%0d hdr=null", id);
      return $sformatf("id=%0d len=%0d", id, hdr.len);
    endfunction
  endclass

  class crc_packet extends packet;
    bit [7:0] crc;

    virtual function void copy(packet rhs);
      crc_packet r;
      if (!$cast(r, rhs))
        $fatal(1, "crc_packet::copy: rhs is null or not a crc_packet");
      super.copy(rhs);
      crc = r.crc;
    endfunction

    virtual function packet clone();
      crc_packet c = new;
      c.copy(this);
      return c;
    endfunction

    virtual function bit compare(packet rhs);
      crc_packet r;
      if (!$cast(r, rhs)) return 0;           // a plain packet never equals a crc_packet
      return super.compare(rhs) && crc == r.crc;
    endfunction

    virtual function string convert2string();
      return $sformatf("%s crc=%h", super.convert2string(), crc);
    endfunction
  endclass

  class generator;
    packet tmpl;        // ONE template object, changed for every transaction
    packet sent[$];     // what a scoreboard would keep as expected items

    function new(packet tmpl);
      this.tmpl = tmpl;
    endfunction

    function void send(int id);
      packet c;
      tmpl.id = id;
      tmpl.hdr.len++;           // the template changes every time
      c = tmpl.clone();         // copy before store
      sent.push_back(c);
    endfunction
  endclass

  initial begin
    crc_packet proto, exp;
    generator  gen;
    int        n_match, n_mismatch;

    proto = new;
    proto.crc = 8'h5a;
    gen = new(proto);           // the generator sees the template as a packet

    gen.send(1);
    gen.send(2);
    gen.send(3);

    foreach (gen.sent[i]) $display("sent[%0d] %s", i, gen.sent[i].convert2string());

    // Rebuild what each send() should have stored, and compare by value.
    foreach (gen.sent[i]) begin
      exp = new;
      exp.id      = i + 1;
      exp.hdr.len = 5 + i;      // len starts at 4 and send() increments it first
      exp.crc     = 8'h5a;
      if (exp.compare(gen.sent[i])) n_match++;   // exp's class decides which compare runs
      else begin
        n_mismatch++;
        $display("MISMATCH [%0d] exp %s, got %s", i, exp.convert2string(),
                 gen.sent[i].convert2string());
      end
    end
    $display("SCB_SUMMARY matches=%0d mismatches=%0d pending=0", n_match, n_mismatch);
  end
endmodule
```

**Expected output** (traced by hand against §8.12 and §8.20; no simulator was run for this page):

```text

sent[1] id=2 len=6 crc=5a
sent[2] id=3 len=7 crc=5a
SCB_SUMMARY matches=3 mismatches=0 pending=0
```

**Why it works.** Each `send()` runs `tmpl.clone()` through a `packet` handle. The virtual call reaches `crc_packet::clone`, which builds a new `crc_packet` with its own `header` and copies the template's current `id`, `len` and `crc` into it. Later changes to the template cannot reach the stored clones. The check calls `exp.compare(...)` on the **expected** item, whose class is `crc_packet`, so a stored item that lost its subclass fails the `$cast` and is reported.

### How to add copy support to a class

1. **List the properties** and sort them: values (integers, strings, queues and arrays of values) and handles (nested objects, queues of handles, shared resources such as mailboxes).
2. **Decide ownership for each handle.** A part of the item (a header, a payload object) is deep-copied; a shared resource or a back-pointer to a parent is copied as a handle on purpose, with a comment saying why.
3. **Write `copy(rhs)`:** reject a `null` `rhs`; assign the values; for each owned nested object, mirror `null`, build an object if this one has none, and call its `copy()`; for a queue of handles, rebuild it element by element.
4. **Write `clone()`:** construct an object of this class, call `copy(this)` on it, return it. Make both methods virtual.
5. **In each subclass,** override both. In `copy()`, keep the base argument type, check `$cast` first, call `super.copy(rhs)`, then copy the new fields. In `clone()`, construct the subclass.
6. **Add `compare()` and `convert2string()`** with the same structure, so that checks compare by value and logs show contents.
7. **Prove it is deep:** clone an object, change every nested field of the clone, and check that the original is unchanged.

## Push Further

### Expert: what else a shallow copy copies

§8.12 lists more than the properties you declared:
- **Randomization state is copied.** The object's random number generator (RNG) state, each variable's `rand_mode`, each constraint's `constraint_mode` and the cyclic state of `randc` variables all go to the copy. Because each object has its own RNG (§18.14.3), a copy and its source start from the same RNG state, so with the same constraints their next `randomize()` calls should pick the same values. A clone built with `new` and `copy()` gets a fresh RNG seeded from the creating thread instead (§18.14.3), and `copy()` does not move the RNG state. [I-SV-2A](/curriculum/T2_Intermediate/I-SV-2A_Constrained_Randomization_Fundamentals/index) teaches randomization.
- **An embedded covergroup is not shared but dropped.** A covergroup declared inside a class (§19.4, taught in [I-SV-3A](/curriculum/T2_Intermediate/I-SV-3A_Functional_Coverage_Fundamentals/index)) gets a `null` handle in the copy, so the copy's properties are not covered, and calling `sample()` on the copy's covergroup is a null-handle access (§8.12 step 2 and its NOTE).
- **Instance constants are copied.** A shallow copy runs no constructor and copies every property, so it duplicates an instance constant such as a unique id (§8.19). A clone built with `new` gets a fresh one from its constructor, and its `copy()` cannot assign it, because an instance constant can be assigned only once, in the constructor (§8.19).
- **The class follows the object.** `base3 = new base2`, where `base2` is a base-class handle to a subclass object, creates a subclass object (§8.12). That is why Break 1 above still stored `crc_packet` objects.

The same facts side by side, for a shallow copy and for a clone built with `new` and `copy()`:

| | `p2 = new p1` (shallow copy) | `p2 = p1.clone()` (`new`, then `copy()`) |
|---|---|---|
| Constructor and declaration initializers | Not run (§8.12) | Run once, by `new` (§8.7) |
| RNG state | Copied, so both objects start from the same RNG state (§8.12) | A fresh RNG, seeded from the thread that creates the object (§18.14.3); `copy()` does not move it |
| `rand_mode`, `constraint_mode`, `randc` cycle | Copied (§8.12) | The new object's own: every random variable and constraint starts active (§18.8, §18.9); assigning values in `copy()` does not change them |
| Embedded covergroup | `null` in the copy, so the copy's properties are not covered (§8.12, §19.4) | Built by the constructor, if `new()` builds it; only `new()` may assign it (§19.4) |
| Instance constant (`const int uid;`) | Copied with the other properties (§8.12, §8.19) | Assigned once, in the constructor; `copy()` cannot assign it (§8.19) |
| Class of the new object | The source object's class (§8.12) | The class whose `clone()` ran: the object's own class only if `clone()` is virtual and overridden (§8.20) |

### Expert: override rules that shape `copy()` and `clone()`

- **Argument types must match.** A virtual override must have matching argument types, identical argument names, qualifiers and directions (§8.20). `crc_packet::copy(crc_packet rhs)` is therefore not an override of `packet::copy(packet rhs)`; it is an error. That rule is why the subclass takes `packet rhs` and uses `$cast`.
- **The return type may be narrower.** A virtual function override may return a derived class of the base return type (§8.20). `virtual function crc_packet clone();` in `crc_packet` is legal and saves callers who hold a `crc_packet` handle a `$cast`. Calls through a `packet` handle still see a `packet` return type.
- **`local` members of the other object are visible.** Inside a class, `rhs.secret` is legal even when `secret` is `local`, because local access is per class, not per object (§8.18). `copy()` and `compare()` need no getters.
- **Let the compiler check the overrides (IEEE 1800-2023).** `virtual function :extends void copy(packet rhs);` declares that the method must override a virtual base method, so a misspelled name or a changed argument list becomes a compile error instead of a silent new method. `:final` stops further overrides (§8.20). Support for these 2023 specifiers is tool-dependent: check your simulator before using them.

### Expert: deep copies of linked and shared structures

- **Back-pointers.** If an item holds a handle to its parent (for example `burst parent` in each beat) and `copy()` deep-copies that handle too, the copy recurses: the parent copies the beat, which copies the parent, and so on. Copy back-pointers as handles, or set them to the new parent after copying the children.
- **Shared sub-objects.** If two properties refer to one object (a beat in both `beats[$]` and `last_beat`), a naive deep copy makes two objects where there was one, and the copy no longer has the original's shape. Copy the shared object once, then point both properties at the copy.
- **How UVM handles it.** uvm-core 2020.3.1's `uvm_copier::copy_object` records which pairs of objects it has started and finished copying, and refuses to copy an object whose recursion policy is `UVM_REFERENCE`, reporting `UVM_COPY_POLICY` (`uvm_copier.svh`). A field macro flagged `UVM_REFERENCE` copies only that handle, without following it (`uvm_object_defines.svh`).

### Expert: ownership, cost and where copies belong

- **One rule for every channel:** the creator of an object publishes it and never changes it afterwards; any consumer that keeps an object it did not create stores a copy. Mailboxes ([I-SV-5](/curriculum/T2_Intermediate/I-SV-5_Synchronization_and_IPC/mailboxes)) and UVM analysis ports ([I-UVM-2B](/curriculum/T2_Intermediate/I-UVM-2B_TLM_Connections/index)) pass handles, so this rule is the only thing that keeps items intact.
- **Copy at one end, not both.** If monitors build a new object per transaction, the scoreboard does not need to clone what it receives, unless another subscriber may change it. Teams usually pick one convention for a whole testbench and review against it.
- **Cost.** A deep copy of a large payload (thousands of bytes, or many nested objects) costs time and memory on every transaction. How much depends on the simulator: measure with your tool's profiler before optimizing (tool-dependent). Sharing read-only data, such as a configuration object, is legitimate when the owner guarantees it never changes.

### Expert: why UVM separates `copy()` from `do_copy()`

In uvm-core 2020.3.1 `copy()` is non-virtual and owns the policy: the null check (`OBJ/COPY`), choosing a copier (`get_default_copier()` when none is passed), flushing it for a new top-level copy, and calling `copy_object`, which runs field automation (`do_execute_op`) and then your `do_copy()` (`uvm_object.svh`, `uvm_copier.svh`; IEEE 1800.2-2020 §5.3.8.1). Making `copy()` non-virtual means no user class can skip those steps; making `do_copy()` the only virtual hook means each class writes only its own fields. The same split appears in `compare()`/`do_compare()`, `print()`/`do_print()` and the other `uvm_object` operations, which [I-UVM-4](/curriculum/T2_Intermediate/I-UVM-4_UVM_Policy_Classes/index) covers as policy classes.

### Kata: four bugs in one clone

**Objective:** find and fix four copy and clone bugs, predicting the log after each fix.

**Starter.** It compiles and runs, and it has four bugs, marked A to D only in the solution.

```systemverilog
// compile
module tb_top;
  class header;
    int len = 4;
    function void copy(header rhs);
      len = rhs.len;
    endfunction
  endclass

  class packet;
    int    id;
    header hdr = new;

    virtual function void copy(packet rhs);
      id  = rhs.id;
      hdr = rhs.hdr;
    endfunction

    function packet clone();
      packet c = new;
      c.copy(this);
      return c;
    endfunction
  endclass

  class crc_packet extends packet;
    bit [7:0] crc;

    virtual function void copy(packet rhs);
      crc_packet r;
      void'($cast(r, rhs));
      crc = r.crc;
    endfunction

    virtual function packet clone();
      crc_packet c = new;
      c.copy(this);
      return c;
    endfunction
  endclass

  initial begin
    crc_packet orig, back;
    packet     p, q;
    orig = new;
    orig.id = 3;
    orig.crc = 8'h5a;
    orig.hdr.len = 7;
    p = orig;
    q = p.clone();
    $display("cast_ok=%0d id=%0d", $cast(back, q), q.id);
    q.hdr.len = 1;
    $display("orig.hdr.len=%0d", orig.hdr.len);
  end
endmodule
```

**Tasks:**
1. Predict the starter's two log lines, and explain each value with a heap drawing.
2. Fix the bug that makes `cast_ok` 0, and predict the new log. Explain why `id` changes.
3. Fix the bug that the new `id` reveals, and predict again. Explain why `orig.hdr.len` changes back.
4. Fix the last visible bug. Then find the fourth bug, which this test never triggers, by declaring `crc_packet x; packet y;` at the top of the initial block, adding `x = new; y = new; x.copy(y);` at its end, and predicting what happens.

**Done when:** the log reads `cast_ok=1 id=3` and `orig.hdr.len=7`, and `x.copy(y)` stops with a clear message that names the problem.

<details>
<summary>Worked solution (try the kata first)</summary>

**Task 1.** The starter prints:

```text
cast_ok=0 id=3
orig.hdr.len=1
```

**Bug B:** `packet::clone` is not virtual, so `p.clone()` runs `packet::clone` and builds a plain `packet`; the `$cast` fails. Its `copy()` call is virtual but the new object is a `packet`, so `packet::copy` runs. It copies `id` (3) and, through **bug A** (`hdr = rhs.hdr`), the header handle, so `q.hdr.len = 1` writes `orig`'s header.

**Task 2.** Make `packet::clone` virtual. Now `crc_packet::clone` runs and the log is:

```text
cast_ok=1 id=0
orig.hdr.len=7
```

`crc_packet::copy` never calls `super.copy(rhs)` (**bug D**), so `id` keeps its default 0, and `packet::copy`, the home of bug A, never runs: the clone keeps the header its own `hdr = new` built.

**Task 3.** Add `super.copy(rhs);`. Now `packet::copy` runs, `id` is 3, and bug A shares the header again:

```text
cast_ok=1 id=3
orig.hdr.len=1
```

**Task 4.** Replace `hdr = rhs.hdr;` with a null-safe deep copy. The log becomes `cast_ok=1 id=3` and `orig.hdr.len=7`. **Bug C** is `void'($cast(r, rhs));`: it throws away the result. When `rhs` holds a plain `packet`, as in `x.copy(y)`, the cast fails, `r` stays `null`, and `r.crc` is a null-handle access, reported however your simulator reports one (tool-dependent wording). Check the result and stop with a message first.

```systemverilog
// snippet: the fixed methods
// in packet:
virtual function void copy(packet rhs);
  if (rhs == null) $fatal(1, "packet::copy: null rhs");
  id = rhs.id;
  if (rhs.hdr == null) hdr = null;
  else begin
    if (hdr == null) hdr = new;
    hdr.copy(rhs.hdr);                  // bug A fixed: contents, not the handle
  end
endfunction

virtual function packet clone();        // bug B fixed: virtual
  packet c = new;
  c.copy(this);
  return c;
endfunction

// in crc_packet:
virtual function void copy(packet rhs);
  crc_packet r;
  if (!$cast(r, rhs))                   // bug C fixed: the result is checked
    $fatal(1, "crc_packet::copy: rhs is null or not a crc_packet");
  super.copy(rhs);                      // bug D fixed: copy the base part
  crc = r.crc;
endfunction
```

With these fixes, `x.copy(y)` stops at the `$fatal` with its message instead of a null-handle access.
