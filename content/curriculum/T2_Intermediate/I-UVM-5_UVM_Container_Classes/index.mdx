## Quick Take
- **What it is:** `uvm_pool` and `uvm_queue` are UVM container classes that wrap a native associative array and a native SV queue in a `uvm_object`, so the container can be passed by handle, created through the factory, and shared through a global singleton.
- **Why it matters:** Choosing the wrong container wastes simulation performance or forces manual boilerplate. Knowing when UVM containers add value versus when native SV is simpler prevents over-engineering.
- **The gotchas:** `uvm_pool::get()` of a missing key **inserts** a default entry. `uvm_queue` cannot `insert()` at `size()`. Neither container implements `compare()`, so two different containers always "match".
- **The Analogy:** UVM containers are like a shared locker with a nameplate: anyone who knows the name can open it. Native SV containers are your own backpack — faster and simpler, but nobody else can reach in.

> **Signal:** If you are passing the same queue between components by copying it, or inventing a global singleton class to share a lookup table, a UVM container may help.

## Build Your Mental Model

### The Two UVM Containers

UVM provides two general-purpose container classes, plus specializations of `uvm_pool` such as `uvm_event_pool`, `uvm_barrier_pool` and `uvm_object_string_pool`. Both extend `uvm_object`, so they can be created through the factory — but they implement only part of the policy interface:

| Container | Native SV Equivalent | Key Difference |
| --- | --- | --- |
| `uvm_pool #(KEY,T)` | `T aa[KEY]` | Passed by handle; one global singleton per specialization via `get_global_pool()`; type-safe |
| `uvm_queue #(T)` | `T q[$]` | Passed by handle; `wait_until_not_empty()`; one global singleton per specialization via `get_global_queue()` |

| Policy operation | `uvm_pool` | `uvm_queue` |
| --- | --- | --- |
| `copy()` | yes — shallow: class handles are shared | yes — shallow |
| `print()` | yes, lists every value | **no** — prints only the header |
| `compare()` | **no** — always returns 1 | **no** — always returns 1 |
| `convert2string()` | no | yes (`%p` format) |

> **IEEE 1800.2-2020 reference:** §11.2 (`uvm_pool`), §11.3 (`uvm_queue`), §10.4.1 (`uvm_event_pool`). Behaviour above checked against the uvm-core 2020.3.1 reference implementation.

### `uvm_pool` — A Shared, Type-Safe Map

`uvm_pool #(KEY,T)` is a parameterized associative array inside a class. Its static `get_global_pool()` returns one singleton **per specialization**: `uvm_pool #(string,int)` and `uvm_pool #(string,bit)` are two different pools.

```systemverilog
// Store a value from a monitor
uvm_pool #(string, int)::get_global_pool().add("error_count", err_cnt);

// Read it in the scoreboard — no handle-passing needed
if (uvm_pool #(string, int)::get_global_pool().exists("error_count"))
  errors = uvm_pool #(string, int)::get_global_pool().get("error_count");
```

**The `get()` trap:** for a missing key, `get()` stores the default value of `T` and returns it — `0` for an `int`, `null` for a class handle — and `num()` grows by one. Use `exists()` first when absence means something.

**When to use `uvm_pool`:**
- Sharing metadata across components that don't have direct TLM connections (event counters, status flags, configuration tokens)
- Building registries or lookup tables that multiple agents read

**When NOT to use it:**
- For high-frequency data (transactions) — use TLM ports instead
- When you need ordering guarantees beyond key order — pools are maps

### `uvm_queue` — A Queue You Can Pass by Handle

`uvm_queue #(T)` wraps a native SV queue (`T queue[$]`) with `push_back`, `push_front`, `pop_front`, `pop_back`, `get`, `insert`, `delete` and `size`. It is stricter than a native queue: `get(i)`, `insert(i, x)` and `delete(i)` with an index out of range only warn (`QUEUEGET`, `QUEUEINS`, `QUEUEDEL`) and do nothing — and `insert(size(), x)` counts as out of range.

```systemverilog
function void log_packet(my_packet pkt);
  uvm_queue #(my_packet) pkt_log;
  my_packet first;

  pkt_log = uvm_queue #(my_packet)::get_global_queue();
  pkt_log.push_back(pkt);
  first = pkt_log.get(0);
  `uvm_info("LOG", $sformatf("Logged %0d packets", pkt_log.size()), UVM_MEDIUM)
  `uvm_info("LOG", pkt_log.convert2string(), UVM_HIGH)   // print() would show no elements
endfunction
```

**When to use `uvm_queue`:**
- When one queue must be shared by handle between components (or through `config_db` as a `uvm_object`)
- When a consumer should block until data arrives (`wait_until_not_empty()`)

**When NOT to use it:**
- For local iteration — native `T q[$]` is faster and has the array methods (`sort`, `find`, `unique`, `sum`)
- When you need `compare()` or `print()` of the contents — neither is implemented

### Native SV: When Simpler Is Better

Most production testbenches use native SV structures for the majority of their container needs:

```systemverilog
// Associative array — keys iterate in order (string keys: lexicographic)
int error_map[string];
my_packet pkt_q[$];
my_packet matches[$];

error_map["crc"] = 0;
error_map["timeout"] = 3;

pkt_q.push_back(pkt);
pkt_q.sort() with (item.addr);                    // sorts in place; returns nothing
matches = pkt_q.find() with (item.addr > 'h1000); // returns a new queue
```

> **Key insight:** native SV arrays have `sort`, `find`, `unique`, `min`, `max`, `sum` and `reverse` built in. The ordering methods (`sort`, `rsort`, `reverse`, `shuffle`) are `void` functions that reorder the array in place. `uvm_queue` has none of these methods.

## Make It Work

1. **Default to native SV.** Start with `int map[string]` and `pkt q[$]`. Only switch to UVM containers when you need to share the container by handle or through a global singleton.
2. **Use `uvm_pool` for cross-component metadata.** Error counters, test-phase flags, and configuration tokens are good candidates. Guard reads with `exists()`.
3. **Avoid `uvm_pool` for transactions.** TLM analysis ports are the right mechanism for moving structured data between components.
4. **Use `uvm_event_pool` for named events.** `uvm_event_pool::get_global("name")` creates the event on first use, so the producer and consumer need no agreed start-up order.
5. **Never rely on container `compare()` or `print()`.** Compare element by element yourself, and log a `uvm_queue` with `convert2string()`.

**Checklist before moving on:**
- [ ] You know the two UVM container classes and their native SV equivalents.
- [ ] You can predict what `get()` does for a missing key in `uvm_pool` and in `uvm_event_pool`.
- [ ] You can explain why native SV queues have richer array methods than `uvm_queue`.
- [ ] You know which policy operations each container implements.

## Push Further: Sharing Events Between Agents

A common pattern uses the global event pool as a coordination point between independent agents:

```systemverilog
// In agent A's sequence: announce that the DMA finished
uvm_event_pool::get_global("dma_done").trigger();

// In agent B's sequence: wait for it
uvm_event_pool::get_global("dma_done").wait_on();
```

`uvm_event_pool` is `uvm_object_string_pool #(uvm_event #(uvm_object))`, whose `get()` creates a missing event. A plain `uvm_pool #(string, uvm_event)` would return `null` for a key nobody added.

> **Caution:** `wait_trigger()` only sees triggers that happen after it starts waiting. If agent B might arrive late, use `wait_on()` (returns at once if the event is already on) or `wait_ptrigger()` (also sees a trigger earlier in the same time step). The string key couples the agents: a misspelled name silently creates a second event. Define the key names in a shared package.
