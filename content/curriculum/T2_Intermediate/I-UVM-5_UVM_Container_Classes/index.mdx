## Quick Take

- **What it is:** UVM has two general container classes. `uvm_pool #(KEY,T)` wraps a native associative array, and `uvm_queue #(T)` wraps a native queue, each inside a `uvm_object` (IEEE 1800.2-2020 §11.2, §11.3). Because the container is now an object, components can share it by **handle** (a reference to one object), pass it through `uvm_config_db`, create it with the factory, or reach one **global singleton** of it. Two specializations of the pool, `uvm_event_pool` and `uvm_barrier_pool` (§10.4), hand out named events and barriers and create them on first use.
- **Why it matters:** Most testbench data belongs in native SystemVerilog containers, which are simpler and come with array methods. The UVM containers earn their place in two jobs: sharing one container object between components, and sharing a named event or barrier between agents that have no other connection. They also hide traps that cause silent bugs: `get()` of a missing key *adds* that key, `compare()` returns 1 whatever two containers hold, and a barrier taken from the pool starts with a threshold of 0, so it blocks nobody.
- **The Analogy:** A native container is your backpack: fast, private, and copied whenever you hand it over. A UVM container is a locker in a shared hallway: anyone holding the key (a handle) opens the same locker, and the event pool is a row of lockers labelled by name. *Where it breaks:* the "global" locker is not chosen by name. There is exactly one per type specialization, so every piece of code that uses `uvm_pool #(string,int)`, including a vendor's **verification IP** (VIP: a ready-made, usually third-party, set of agents for a protocol), opens the same one. And a native array declared in a package is shared too; what the UVM container really adds is a handle you can pass and a factory that can create it.

**You will be able to:**
1. Choose native containers or `uvm_pool`/`uvm_queue` for a sharing scenario (a handle passed through `uvm_config_db`, a global singleton, factory creation), and justify the choice.
2. Predict what `uvm_pool` and `uvm_queue` calls do: `get()` of a missing key, `exists`/`delete`/`num`, out-of-range `get`/`insert`/`delete`, and which global instance a specialization returns.
3. Write code that shares a named event or barrier between components with `uvm_event_pool`/`uvm_barrier_pool`, including the threshold a pool-created barrier needs.
4. Explain and debug what the containers do not do (no content compare, shallow copy, no `uvm_queue` print) and the hangs, false passes and null-handle errors that follow.

## Build Your Mental Model

**How to read this lesson.** The core path runs from native containers to `uvm_pool`, its global singleton, `uvm_queue`, and the event and barrier pools, then lets you test your predictions in the explorer. Practitioner depth follows: what the containers do not do, and a decision table. Make It Work builds a complete testbench that uses all four classes, then breaks it on purpose and gives a debugging table. Push Further holds the expert corner cases.

Three words this lesson leans on, all from earlier lessons:
- A **parameterized class** takes types as parameters; a **specialization** is the class with its parameters filled in, such as `uvm_pool #(string,int)`. Each specialization is a separate type ([I-SV-1: Parameterized Classes](/curriculum/T2_Intermediate/I-SV-1_OOP/parameterized-classes)).
- A **static** method belongs to the class rather than to one object, so you call it with `::` and no handle, as in `uvm_pool #(string,int)::get_global_pool()`.
- The **factory** creates objects by type with `::type_id::create` ([I-UVM-1B](/curriculum/T2_Intermediate/I-UVM-1B_The_UVM_Factory/index)), and `uvm_config_db` hands a value or a handle from a parent to the components below it ([I-UVM-2C](/curriculum/T2_Intermediate/I-UVM-2C_Configuration_and_Resources/index)).

### Start from what you already have: native containers

[F2B](/curriculum/T1_Foundational/F2B_Dynamic_Structures/index) taught the native containers: an associative array such as `int err_map[string]` and a queue such as `int q[$]`. They are variables, not objects. Assigning one to another, or passing one to a function without `ref`, makes a **copy**:

```systemverilog
// snippet: a native queue is copied on assignment
int q_a[$] = '{1, 2};
int q_b[$];
q_b = q_a;          // q_b is a new queue that holds 1, 2
q_b.push_back(3);   // q_a still holds 1, 2
```

A `uvm_queue` is an object, so assignment copies the *handle* and both names reach one queue:

```systemverilog
// snippet: a uvm_queue is shared on assignment, because it is an object
uvm_queue #(int) qa, qb;
qa = uvm_queue #(int)::type_id::create("qa");
qb = qa;            // qa and qb are two handles to one object
qb.push_back(3);    // qa.size() is now 1
```

So when two components need *the same* container, you have three options: make the native container a member of an object you already share (for example a configuration object), declare it at package scope where every importer sees it, or use a UVM container and share its handle. The rest of this section is about the third option and when it is worth it.

### `uvm_pool #(KEY,T)`: a keyed table behind a handle

`uvm_pool #(KEY,T)` holds a protected associative array `T pool[KEY]` (§11.2.1; the defaults are `KEY = int` and `T = uvm_void`). You reach the entries only through methods:

| Method | What it does | Clause |
|---|---|---|
| `new(name)` | creates an empty pool; prefer `uvm_pool #(KEY,T)::type_id::create(name)` | §11.2.2.1 |
| `add(key, item)` | stores `item`, overwriting any entry at `key` | §11.2.2.5 |
| `get(key)` | returns the entry; **if `key` is missing, first stores the default value of `T` at `key`** | §11.2.2.4 |
| `exists(key)` | 1 if `key` is present, 0 otherwise; never adds anything | §11.2.2.8 |
| `num()` | number of keys stored | §11.2.2.6 |
| `delete(key)` | removes `key`; there is no "delete everything" form | §11.2.2.7 |
| `first(key)`, `last(key)`, `next(key)`, `prev(key)` | walk the keys in key order; each returns 0 when there is nothing to move to | §11.2.2.9–§11.2.2.12 |
| `get_global_pool()`, `get_global(key)` | static: the one global pool of this specialization, and `get(key)` on it | §11.2.2.2–§11.2.2.3 |

**The `get()` trap, traced.** This is the call that surprises nearly everyone. Read the code, predict the right-hand columns, then check:

```systemverilog
// snippet: inside a class method
uvm_pool #(string, int) err_pool;
int n;
err_pool = uvm_pool #(string, int)::type_id::create("err_pool");
err_pool.add("crc", 2);                                    // step 1
n = err_pool.get("timeout");                               // step 2
if (err_pool.exists("parity")) n = err_pool.get("parity"); // step 3
err_pool.delete("parity");                                 // step 4
```

| Step | Pool contents after the step | `num()` | `n` | Log |
|---|---|---|---|---|
| 1 `add("crc", 2)` | `crc: 2` | 1 | 0 | — |
| 2 `get("timeout")` | `crc: 2`, **`timeout: 0`** | **2** | 0 | nothing: no warning |
| 3 `exists("parity")` | unchanged (`exists` returned 0, so `get` was skipped) | 2 | 0 | — |
| 4 `delete("parity")` | unchanged | 2 | 0 | `UVM_WARNING … [POOLDEL]` (uvm-core) |

Step 2 is the trap. A native associative array behaves the other way round, which is why the habit from F2B misleads you:

| Action | Native `int aa[string]` | `uvm_pool #(string,int)` |
|---|---|---|
| Read a missing key | returns the default (0) and **adds nothing**; IEEE 1800-2023 §7.8.6 says a warning shall be issued | `get()` returns the default **and adds the key**, with no warning (§11.2.2.4) |
| Delete a missing key | no effect and no warning (IEEE 1800-2023 §7.9.2) | no effect; uvm-core warns `POOLDEL` (the standard does not require a warning) |
| The default value | from IEEE 1800-2023 Table 7-1 (§7.4.5) | the same table: `0` for 2-state types such as `int`, `'x` for 4-state types such as `logic`, `null` for a class handle, `""` for a `string` |
| Walk the entries | `foreach`, or `first`/`next` | `first`/`next` only: a pool is an object, so `foreach` and the array methods do not apply |

Two rules follow:
- **When absence means something, ask `exists()` before `get()`.** Otherwise every probe adds a phantom entry, `num()` grows, and a later `first`/`next` walk lists keys nobody added.
- **When absence means zero, the insertion is harmless and even handy.** `counts.add(k, counts.get(k) + 1);` counts occurrences without any `exists()` check, because the first `get(k)` stores and returns 0.

### Global singletons: one per specialization

A **singleton** is a class that keeps exactly one shared instance. `uvm_pool` keeps a static handle, and `get_global_pool()` creates the pool on its first call and returns that same object on every later call (§11.2.2.2). `get_global(key)` is shorthand for `get_global_pool().get(key)` (§11.2.2.3), so it has the same insertion behaviour. `uvm_queue` has the matching `get_global_queue()` and `get_global(index)` (§11.3.2.2, §11.3.2.3).

```systemverilog
// snippet: two components that never exchanged a handle share one counter table
// In the monitor:
uvm_pool #(string, int)::get_global_pool().add("parity_err", 1);
// In the scoreboard, any time later:
if (uvm_pool #(string, int)::get_global_pool().exists("parity_err")) ...
```

The catch is the word *one*. The singleton belongs to the **specialization**, not to your testbench or to a name you choose:

- A `typedef uvm_pool #(string,int) my_pool_t;` does not give you a private global: a typedef is another name for the same specialization.
- The safer default is an **instance**: create the pool in the test or env with `type_id::create`, and pass its handle down through `uvm_config_db`. The sharing is then limited to the components you chose, and two tests in one regression cannot leak state through it. Make It Work does exactly this.
- A native array at package scope (`int error_map[string];` in a shared package) is just as global and needs no handle at all. Both are global mutable state; prefer an explicit owner.

### `uvm_queue #(T)`: a queue behind a handle

`uvm_queue #(T)` holds a protected native queue `T queue[$]` (§11.3.1) behind these methods:

| Method | What it does | Clause |
|---|---|---|
| `push_back(x)`, `push_front(x)` | add at the back or front | §11.3.2.10–§11.3.2.11 |
| `pop_front()`, `pop_back()` | remove and return the first or last item | §11.3.2.8–§11.3.2.9 |
| `get(i)` | return item `i` without removing it | §11.3.2.4 |
| `insert(i, x)` | insert before item `i` | §11.3.2.6 |
| `delete(i)` | remove item `i`; with no argument (`i = -1`) remove everything | §11.3.2.7 |
| `size()` | number of items | §11.3.2.5 |
| `wait_until_not_empty()` | task: returns at once if the queue holds an item, otherwise blocks until one is added | §11.3.2.12 |
| `get_global_queue()`, `get_global(i)` | static: the one global queue of this specialization | §11.3.2.2–§11.3.2.3 |

It is **stricter than a native queue** at the edges. An index equal to or greater than `size()` is rejected: the call warns and changes nothing (§11.3.2.4, §11.3.2.6). uvm-core also rejects a negative index, except the `-1` that means "everything" for `delete`.

| Call on a queue holding `'{5, 9}` | Native `int q[$]` | `uvm_queue #(int)` |
|---|---|---|
| `insert(2, 7)`, index equal to `size()` | appends: `'{5, 9, 7}` (IEEE 1800-2023 §7.10.2.2) | ignored, `QUEUEINS` warning, still `'{5, 9}` (§11.3.2.6) |
| `get(5)` / `q[5]` | default value (0) | default value (0) and a `QUEUEGET` warning (§11.3.2.4) |
| `delete(5)` | no effect | no effect, `QUEUEDEL` warning (uvm-core) |
| `insert(0, 7)` on an **empty** queue | `'{7}` | ignored: 0 is not less than `size()`, so use `push_back` |

**`wait_until_not_empty()` waits; it does not take.** With one consumer, `wait_until_not_empty(); x = q.pop_front();` is fine. With two consumers, both can wake for the same item, and the second `pop_front()` finds an empty queue and returns the default (`null` for a class). IEEE 1800.2 §11.3.2.8 says an implementation shall warn in that case; uvm-core simply calls the native `pop_front`, for which IEEE 1800-2023 §7.10.2.4 says only that a warning *may* be issued, so whether you see anything is tool-dependent. For a blocking hand-off from producer to consumer, use a mailbox ([I-SV-5: Mailboxes](/curriculum/T2_Intermediate/I-SV-5_Synchronization_and_IPC/mailboxes)) or a `uvm_tlm_fifo` ([I-UVM-2B](/curriculum/T2_Intermediate/I-UVM-2B_TLM_Connections/index)): their `get` waits *and* removes in one step.

`uvm_queue` also has none of the native array methods (`sort`, `find`, `unique`, `sum` and the rest), and `foreach` does not work on it. Walk it with `for (int i = 0; i < q.size(); i++)` and `q.get(i)`.

### Named synchronization objects: `uvm_event_pool` and `uvm_barrier_pool`

[I-UVM-1C](/curriculum/T2_Intermediate/I-UVM-1C_UVM_Phasing/index) taught the two objects themselves: a `uvm_event` lets one thread announce "now" to any number of waiters, and a `uvm_barrier` blocks threads until a set number of them, its **threshold**, have arrived. The problem this lesson solves is *finding* the same object from two agents that share no handle.

The event and barrier pools are pools keyed by `string`, with one change that matters: **their `get()` creates the object** when the key is missing, instead of storing `null` (§10.4.1.2.4, §10.4.2.2.4). So the producer and the consumer can each call `get_global("cfg_done")` in any order and both receive the same, real event.

```systemverilog
// snippet: two agents share one event by name
// Producer (for example, the configuration agent's sequence):
uvm_event cfg_done = uvm_event_pool::get_global("cfg_done");
// ... program the design ...
cfg_done.trigger();

// Consumer (for example, the data agent's sequence):
uvm_event cfg_done = uvm_event_pool::get_global("cfg_done");
cfg_done.wait_on();   // returns at once if cfg_done was already triggered
```

A plain `uvm_pool #(string, uvm_event)` does not do this. Its `get()` stores and returns the default value of a class handle, `null`, and the following `.trigger()` stops the run with a null-object access.

**Late waiters.** Which wait you choose decides whether an agent that arrives after the trigger proceeds or hangs. The diagram uses the names from Make It Work: `data_b` starts waiting 100 ns after the trigger.

| Wait | Returns | Use when |
|---|---|---|
| `wait_trigger()` | at the next `trigger()` (§10.1.1.2.4) | the waiter is certainly waiting before the trigger |
| `wait_ptrigger()` | also if the trigger happened earlier at the same simulation time (§10.1.1.2.5) | the trigger and the wait can fall at the same time |
| `wait_on()` | at once if the event is on, that is, triggered and not reset since (§10.1.1.2.2) | the waiter may arrive any time later: the usual choice for "configuration is done" |

**Barriers from the pool start at threshold 0.** `uvm_barrier_pool::get(key)` builds the barrier with `new(key)`, and the default threshold of a new barrier is 0 (§10.3.2.1). With threshold 0, the first `wait_for()` already meets the threshold, so it returns at once and nobody ever waits. Set the threshold with `set_threshold(n)` (§10.3.2.6) **before** the first waiter can arrive, for example in `build_phase`:

```systemverilog
// snippet: three parties must all arrive before any continues
// In the test's build_phase, before any run_phase thread exists:
uvm_barrier_pool::get_global("traffic_done").set_threshold(3);
// In each of the three parties, in run_phase:
uvm_barrier_pool::get_global("traffic_done").wait_for();
```

Trace the waiter count for Make It Work's barrier, first with the threshold set, then without it:

| When | Call | Waiters after the call | Threshold | Result |
|---|---|---|---|---|
| build | `get_global("traffic_done")` | 0 | **0** | the pool creates the barrier |
| build | `set_threshold(3)` | 0 | 3 | — |
| 0 ns | test: `wait_for()` | 1 | 3 | blocks |
| 120 ns | `data_a`: `wait_for()` | 2 | 3 | blocks |
| 220 ns | `data_b`: `wait_for()` | 3, then 0 | 3 | all three released; with auto-reset on (the default, §10.3.2.4) the count returns to 0 |
| *without `set_threshold`:* 0 ns | test: `wait_for()` | 1, then 0 | 0 | returns at once: the test drops its objection at 0 ns and "passes" with no traffic |

**Keys are strings, so spell them once.** A misspelled key does not fail: `get_global("cfg_dn")` quietly creates a second event that nobody triggers. Define every key as a constant in a shared package (`localparam string CFG_DONE = "cfg_done";`) so that a typo becomes a compile error.

### What the containers do not do

Both classes extend `uvm_object`, so `copy()`, `print()`, `compare()` and the other policy operations from [I-UVM-4](/curriculum/T2_Intermediate/I-UVM-4_UVM_Policy_Classes/index) are callable on them. But each operation only does what the class implements, and these classes implement little. Checked against uvm-core 2020.3.1 (`uvm_pool.svh`, `uvm_queue.svh`):

| Operation | `uvm_pool #(KEY,T)` | `uvm_queue #(T)` |
|---|---|---|
| `copy()` | **shallow**: the array is copied, but class handles in it are shared | **shallow**, the same way |
| `print()` | lists the values; uvm-core labels every row `[-key0--]`, so the keys do not appear | **header only**: no items |
| `convert2string()` | not implemented (empty string) | `$sformatf("%p", queue)`, for example `'{5, 9}` |
| `compare()` | **returns 1 whatever the contents** | **returns 1 whatever the contents** |
| `pack()`, `record()` | nothing about the contents | nothing about the contents |

Three consequences:
- **Equal-looking is not equal.** `q1.compare(q2)` returns 1 for two `uvm_queue #(int)` objects holding `'{5, 9}` and `'{1}`: there are no field macros and no `do_compare`, so nothing is compared. A scoreboard that trusts it passes every test. Compare the contents yourself:

  ```systemverilog
  // snippet: compare two queues item by item
  function automatic bit same_items(uvm_queue #(int) a, uvm_queue #(int) b);
    if (a.size() != b.size()) return 0;
    for (int i = 0; i < a.size(); i++)
      if (a.get(i) != b.get(i)) return 0;
    return 1;
  endfunction
  ```

- **A copy shares the objects.** After `q2.copy(q1)` on a `uvm_queue #(my_item)`, `q2` has its own list, so `q2.push_back(x)` leaves `q1` alone. But `q2.get(0)` and `q1.get(0)` are the same `my_item` object: change one and the other changes. Push Further shows the deep-copy idiom.
- **Not faster.** A UVM container is the same native container plus a virtual method call on every access, so it is never a speed upgrade, and you lose the array methods. Choose it for sharing, never for performance.

### Choosing a container

| Situation | Choose | Why |
|---|---|---|
| A list or table used inside one component (expected items in a scoreboard, a sparse memory model) | native queue or associative array | array methods, no call overhead, no sharing needed |
| Transactions moving between components | an analysis port or other TLM connection ([I-UVM-2B](/curriculum/T2_Intermediate/I-UVM-2B_TLM_Connections/index)) | ordering, fan-out, and a new object per transaction |
| A producer hands items to a consumer that must block until one arrives | mailbox or `uvm_tlm_fifo` | `get` waits and removes in one step |
| One table or list shared by a few components you build | a `uvm_pool`/`uvm_queue` **instance** created in the test or env and passed through `uvm_config_db` | shared by handle, scope you control, factory-creatable |
| Data that is part of an agent's configuration | a native container inside the configuration object | travels with the configuration you already pass |
| "Configuration is done, start traffic" between agents | `uvm_event_pool::get_global(KEY)` with `wait_on()` | created on first use; order-independent |
| "Wait until all N agents finish reset" | `uvm_barrier_pool::get_global(KEY)` with `set_threshold(N)` set first | created on first use; threshold must be set before the first `wait_for()` |
| A table every part of the bench must reach, with no owner | global pool or package-scope native array, with the keys defined in one package | both are global mutable state; use sparingly |

### Recap

- `uvm_pool` and `uvm_queue` are native containers behind a handle. Use them to share one container object; use native containers for everything else.
- `uvm_pool::get()` adds a missing key with the default value; `exists()` does not. Event and barrier pools create the object instead.
- The global singleton is one per specialization, shared with every other user of that type. Prefer an instance passed through `uvm_config_db`.
- `uvm_queue` rejects every index outside `0` to `size()-1`, including `insert(size(), x)`. `wait_until_not_empty()` does not remove the item.
- Neither container compares its contents, copies deeply, or (for `uvm_queue`) prints its items.
- Late waiters use `wait_on()`. Pool barriers need `set_threshold(n)` before anyone waits. Keys belong in constants.

## Make It Work

### A configuration handshake with shared containers

This complete testbench has no design under test (DUT): the containers are testbench plumbing, so three small components stand in for agents.
- `cfg_agt` "programs the design" for 100 ns, fills a shared `uvm_queue` with the addresses it configured, and triggers the pooled event `cfg_done`.
- `data_a` and `data_b` wait for `cfg_done` with `wait_on()`, send one write per address and count their writes in a shared `uvm_pool`. `data_b` is busy until 200 ns, so it arrives after the trigger.
- The test creates both containers, passes them down through `uvm_config_db`, sets the barrier threshold, and keeps an **objection** raised (while any objection is raised, `run_phase` does not end; see [I-UVM-1C](/curriculum/T2_Intermediate/I-UVM-1C_UVM_Phasing/index)) until all three parties reach the `traffic_done` barrier. `check_phase` and `report_phase` read the counters safely.

// container_tb.sv: compile together with uvm-core 2020.3.1.
`timescale 1ns/1ps

package container_pkg;
  import uvm_pkg::*;
  `include "uvm_macros.svh"

  // Every shared name in one place: a misspelled key becomes a compile
  // error instead of a silent second event.
  localparam string CFG_DONE     = "cfg_done";
  localparam string TRAFFIC_DONE = "traffic_done";

  typedef uvm_queue #(int)        addr_queue_t;  // filled once, read by many
  typedef uvm_pool #(string, int) count_pool_t;  // writes per agent

  // Stands in for the agent that programs the DUT's registers.
  class cfg_agent extends uvm_component;
    `uvm_component_utils(cfg_agent)
    addr_queue_t addr_q;

    function new(string name, uvm_component parent);
      super.new(name, parent);
    endfunction

    function void build_phase(uvm_phase phase);
      super.build_phase(phase);
      if (!uvm_config_db #(addr_queue_t)::get(this, "", "addr_q", addr_q))
        `uvm_fatal("NOQ", "addr_q was not set")
    endfunction

    task run_phase(uvm_phase phase);
      uvm_event cfg_done = uvm_event_pool::get_global(CFG_DONE);
      #100ns;   // stands in for the time it takes to program the design
      addr_q.push_back('h1000);
      addr_q.push_back('h2000);
      `uvm_info("CFG", $sformatf("configured, addr_q = %s",
                                 addr_q.convert2string()), UVM_LOW)
      cfg_done.trigger();
    endtask
  endclass

  // Stands in for an agent that may only send traffic after configuration.
  class data_agent extends uvm_component;
    `uvm_component_utils(data_agent)
    addr_queue_t addr_q;
    count_pool_t counts;
    time         start_delay;   // the test makes data_b arrive late on purpose

    function new(string name, uvm_component parent);
      super.new(name, parent);
    endfunction

    function void build_phase(uvm_phase phase);
      super.build_phase(phase);
      if (!uvm_config_db #(addr_queue_t)::get(this, "", "addr_q", addr_q))
        `uvm_fatal("NOQ", "addr_q was not set")
      if (!uvm_config_db #(count_pool_t)::get(this, "", "counts", counts))
        `uvm_fatal("NOPOOL", "counts was not set")
    endfunction

    task run_phase(uvm_phase phase);
      uvm_event   cfg_done = uvm_event_pool::get_global(CFG_DONE);
      uvm_barrier done_bar = uvm_barrier_pool::get_global(TRAFFIC_DONE);
      if (start_delay > 0) #(start_delay);   // busy with something else
      cfg_done.wait_on();   // returns at once if cfg_done already fired
      for (int i = 0; i < addr_q.size(); i++) begin
        #10ns;   // stands in for one bus write
        `uvm_info("DATA", $sformatf("write to 'h%0h", addr_q.get(i)), UVM_HIGH)
        // The first get() of our name inserts 0, so counting needs no exists()
        counts.add(get_name(), counts.get(get_name()) + 1);
      end
      `uvm_info("DATA", $sformatf("sent %0d writes", counts.get(get_name())), UVM_LOW)
      done_bar.wait_for();
    endtask
  endclass

  class container_test extends uvm_test;
    `uvm_component_utils(container_test)
    cfg_agent    cfg_agt;
    data_agent   data_a, data_b;
    addr_queue_t addr_q;
    count_pool_t counts;

    function new(string name, uvm_component parent);
      super.new(name, parent);
    endfunction

    function void build_phase(uvm_phase phase);
      super.build_phase(phase);
      // Instances, not globals: only the components we choose can see them.
      addr_q = addr_queue_t::type_id::create("addr_q");
      counts = count_pool_t::type_id::create("counts");
      uvm_config_db #(addr_queue_t)::set(this, "*", "addr_q", addr_q);
      uvm_config_db #(count_pool_t)::set(this, "data_*", "counts", counts);
      // A pool-created barrier starts at threshold 0: set it before anyone waits.
      uvm_barrier_pool::get_global(TRAFFIC_DONE).set_threshold(3);  // 2 agents + test
      cfg_agt = cfg_agent::type_id::create("cfg_agt", this);
      data_a  = data_agent::type_id::create("data_a", this);
      data_b  = data_agent::type_id::create("data_b", this);
      data_b.start_delay = 200ns;
    endfunction

    task run_phase(uvm_phase phase);
      phase.raise_objection(this);
      uvm_barrier_pool::get_global(TRAFFIC_DONE).wait_for();
      phase.drop_objection(this);
    endtask

    function void check_phase(uvm_phase phase);
      string names[2] = '{"data_a", "data_b"};
      foreach (names[i]) begin
        // exists() first: get() alone would add a missing name to the pool
        if (!counts.exists(names[i]) || counts.get(names[i]) != addr_q.size())
          `uvm_error("COUNTS", $sformatf("%s did not send %0d writes",
                                         names[i], addr_q.size()))
      end
    endfunction

    function void report_phase(uvm_phase phase);
      string key;
      if (counts.first(key)) begin
        do begin
          `uvm_info("COUNTS", $sformatf("%s = %0d", key, counts.get(key)), UVM_LOW)
        end while (counts.next(key));
      end
      `uvm_info("COUNTS", $sformatf("num() = %0d", counts.num()), UVM_LOW)
    endfunction
  endclass
endpackage

module tb_top;
  import uvm_pkg::*;
  import container_pkg::*;
  initial run_test("container_test");
endmodule

### Debug it: symptom, cause, fix

| Symptom in the log | Likely cause | Fix |
|---|---|---|
| Null-object access at `.trigger()` or `.wait_*()` | a plain `uvm_pool` of events or barriers returned `null` | use `uvm_event_pool` / `uvm_barrier_pool` |
| A waiter never wakes; the run ends in `PH_TIMEOUT` | the waiter used `wait_trigger()` after the trigger, or the two sides spell the key differently | use `wait_on()`; define keys as constants; print the pool to see every key (below) |
| The test ends at 0 ns and passes; barrier waiters return at once | the barrier's threshold is still 0 | call `set_threshold(n)` in `build_phase`, before any `wait_for()` |
| `num()` is larger than expected; a walk lists keys nobody added | `get()` on missing keys | `exists()` before `get()` |
| `UVM_WARNING [POOLDEL]` | `delete()` of a key that is not there | check `exists()`, or treat the warning as a sign of a wrong key |
| `UVM_WARNING [QUEUEINS]`, `[QUEUEGET]` or `[QUEUEDEL]` | an index outside `0` to `size()-1`, often `insert(size(), x)` | `push_back`/`push_front`; check `size()` |
| `print()` of a `uvm_queue` shows no items; a pool's print shows no keys | the containers have little or no `do_print` | log with `convert2string()` (queue) or walk with `first`/`next` (pool) |
| `compare()` returns 1 although the contents differ | the containers do not compare contents | compare item by item |
| Two agents, or your bench and a vendor's VIP, corrupt each other's counters | both use the global pool of the same specialization | pass an instance through `uvm_config_db`; at least prefix keys |
| Changing an item through a copy changes the original | `copy()` is shallow | clone each item (Push Further) |
| With two consumers, one `pop_front()` returns `null` or 0 | `wait_until_not_empty()` woke both | use a mailbox or `uvm_tlm_fifo` |

To see every key in an event or barrier pool, print it: `uvm_event_pool::get_global_pool().print();`. In uvm-core the event and barrier pools print one row per key, such as `[cfg_dn]` and `[cfg_done]` side by side, which exposes a misspelling at once. (A plain `uvm_pool` prints its values without the keys, so walk it with `first`/`next` instead.)

### How to share data and synchronization between components

1. **Default to native containers.** Keep data local to the component that owns it; move transactions with TLM.
2. **Need one container in several components?** Create a `uvm_pool`/`uvm_queue` instance in the test or env with `type_id::create`, `uvm_config_db #(T)::set` it for exactly the components that need it, and `get` it in their `build_phase`, with a `uvm_fatal` if it is missing.
3. **Read safely.** Use `exists()` before `get()` whenever a missing key means something; use `push_back` rather than `insert(size(), x)`.
4. **Need a named "now" or "all here"?** Put the key in a package constant, use `uvm_event_pool::get_global(KEY)` with `wait_on()` for late waiters, or `uvm_barrier_pool::get_global(KEY)` with `set_threshold(n)` in `build_phase`.
5. **Check and report by content.** Compare item by item, log with `convert2string()` or a `first`/`next` walk, and make `check_phase` fail if the expected entries are missing.

**Checklist before moving on:**
- [ ] I can say, for a given sharing need, whether a native container, a container instance through `uvm_config_db`, a global pool or a TLM connection fits, and why.
- [ ] I can predict `num()` after `get()` of a missing key, and what `insert(size(), x)` does to a `uvm_queue`.
- [ ] I can share an event between two components with `uvm_event_pool::get_global` and choose `wait_on()` for a late waiter.
- [ ] I set the threshold of a pool barrier before the first `wait_for()`, and I know what happens if I forget.
- [ ] I never trust `compare()`, `copy()` or `print()` of a container for its contents.

## Push Further

### Expert: one global instance per specialization, and what to use instead

In uvm-core 2020.3.1, `uvm_pool` declares `static protected this_type m_global_pool;` and `get_global_pool()` creates it on first call (`uvm_pool.svh`; §11.2.2.2 "Returns the singleton global pool for the item type T"). A static member of a parameterized class exists once per specialization (IEEE 1800-2023 §8.25: "Each specialization of a class has a separate set of static member variables"), so the scope of "global" is the type, not your testbench. Every library, VIP and test in the simulation that names `uvm_pool #(string,int)` shares it, and it lives, with every key anyone added, until the simulation ends.

- A `typedef` is the same specialization, so it shares the global.
- A subclass inherits the base's static `get_global_pool()`, which returns the *base* global. It gets a private global only if it redeclares the static handle and the static methods, which is exactly what uvm-core's `uvm_object_string_pool` does for the event and barrier pools.
- A package-scope native array is equally global. Both are global mutable state; the pool adds only handle passing and factory creation.

Staff-level answer to "where should shared state live?": with an owner. The env or test creates the instance and passes it down with `uvm_config_db`; global pools are for genuinely global names, with keys defined in one package and prefixed by the owner.

### Expert: the standard and uvm-core declare the synchronization pools differently

IEEE 1800.2-2020 declares `class uvm_event_pool extends uvm_pool #(string,uvm_event#(uvm_object))` (§10.4.1.1) and `class uvm_barrier_pool extends uvm_pool #(string,uvm_barrier)` (§10.4.2.1). uvm-core 2020.3.1 implements both as typedefs of a helper class: `typedef uvm_object_string_pool #(uvm_event#(uvm_object)) uvm_event_pool;` and `typedef uvm_object_string_pool #(uvm_barrier) uvm_barrier_pool;` (`uvm_pool.svh`). `uvm_object_string_pool` is marked `@uvm-compat` (kept for UVM 1.2 code) and is not part of IEEE 1800.2-2020, so code that names it is not portable; name `uvm_event_pool` and `uvm_barrier_pool` instead.

Two consequences in uvm-core:
- `uvm_event_pool::get_global_pool()` and `uvm_pool #(string, uvm_event#(uvm_object))::get_global_pool()` return **different** objects, because the helper class redeclares the static handle.
- §10.4.1's overview says the event pool contains `begin`, `accept` and `end` events by default. That describes the event pool *inside each* `uvm_transaction`: in uvm-core, `accept_tr()`, `begin_tr()` and `end_tr()` fetch those three events from the transaction's own pool by name, which creates them on first use (`uvm_transaction.svh`). A pool you get from `uvm_event_pool::get_global_pool()` or create yourself starts empty in uvm-core.

### Expert: shallow copy and the deep-copy idiom

uvm-core's `do_copy` for both containers is one assignment: `pool = p.pool;` or `queue = p.queue;` (`uvm_pool.svh`, `uvm_queue.svh`). Assigning a native array copies its elements, and for class-typed elements an element is a handle, so the copy shares every object: the same handle-copying that IEEE 1800-2023 §8.12 describes for a shallow copy of a class. If the copy must be independent, clone each element:

```systemverilog
// snippet: deep copy of a uvm_queue of uvm_objects
function automatic uvm_queue #(my_item) deep_copy(uvm_queue #(my_item) src);
  uvm_queue #(my_item) dst = uvm_queue #(my_item)::type_id::create("dst");
  for (int i = 0; i < src.size(); i++) begin
    my_item it;
    if (!$cast(it, src.get(i).clone()))
      `uvm_fatal("CLONE", "clone() returned the wrong type")
    dst.push_back(it);
  end
  return dst;
endfunction
```

`clone()` is `create()` plus `copy()`, so each item is only as deep as *its* `do_copy` or field macros make it ([I-UVM-4](/curriculum/T2_Intermediate/I-UVM-4_UVM_Policy_Classes/index)). A scoreboard that stores items from a monitor should clone them on entry for the same reason.

### Expert: compare() returns 1, and when it does not

Neither container registers fields or overrides `do_compare`, so `compare()` of two containers of the **same** specialization returns 1 whatever they hold. Two **different** specializations do miscompare in uvm-core, but only on type: the comparer's type check (§16.3.4.2, on by default) compares `get_object_type()`, which differs per specialization. Because both classes declare their type name with `` `uvm_type_name_decl("uvm_pool") `` and `("uvm_queue")`, `get_type_name()` is the same string for every specialization, and uvm-core's message reads "get_object_type() for … does not match get_object_type() for …" rather than naming the two types (`uvm_comparer.svh`). Either way, no element is ever compared.

### Expert: factory registration of parameterized containers

Both classes register with `` `uvm_object_param_utils `` (uvm-core source). IEEE 1800.2-2020 B.2.1.2 says the param variants "do not supply a type name when registering the object with the factory. As such, name-based lookup with the factory for parameterized classes is not possible." So `uvm_pool #(string,int)::type_id::create("counts")` and type overrides by type work, but creating or overriding a pool by the string name "uvm_pool" does not. If a project wants to override its shared table type from the command line, wrap it in a non-parameterized subclass registered with `` `uvm_object_utils ``.

### Expert: memory and performance at scale (tool-dependent)

- **Probes grow memory.** Every `get()` of a missing key adds an entry that lives until `delete(key)`; a monitor that probes a pool per transaction with fresh keys leaks for the whole run. `num()` in `report_phase` is a cheap leak check.
- **No clear-all for pools.** `uvm_pool::delete` needs a key (§11.2.2.7). To empty a pool, walk and delete each key, or drop the handle and create a new instance.
- **Calls, not speed.** Each access is a virtual method call around the same native container. The cost difference against a native container is tool-dependent and usually small next to the rest of a UVM bench, so measure with your simulator's profiler before arguing either way. Never pick a UVM container for speed.

### Kata: an "end of configuration" event between two agents

The configuration agent runs `cfg_seq`, which writes the design's registers. The data agent runs `traffic_seq`, which must not send its first item before configuration is complete. The two agents share no handle, and the test may start `traffic_seq` before or after `cfg_seq` finishes.

1. Write the lines that `cfg_seq::body()` and `traffic_seq::body()` need, using `uvm_event_pool::get_global`, so that the order of starting does not matter.
2. **Predict:** you change the wait to `wait_trigger()`, and the test starts `traffic_seq` 50 ns after `cfg_seq` has finished. What happens, and what does the log end with?
3. Extend it: three agents each run a reset sequence, and no traffic may start until all three have finished. Use `uvm_barrier_pool`. Who sets the threshold, and when?

<details className="my-4 rounded-xl border border-border/70 p-3">
<summary className="cursor-pointer font-semibold">Show the worked solution</summary>

1. Put the key in a package, then fetch the event by name on both sides:

   ```systemverilog
   // snippet: kata solution, part 1
   package keys_pkg;
     localparam string CFG_DONE   = "cfg_done";
     localparam string RESET_DONE = "reset_done";
   endpackage

   // In cfg_seq:
   task body();
     uvm_event cfg_done = uvm_event_pool::get_global(keys_pkg::CFG_DONE);
     // ... register writes ...
     cfg_done.trigger();
   endtask

   // In traffic_seq:
   task body();
     uvm_event cfg_done = uvm_event_pool::get_global(keys_pkg::CFG_DONE);
     cfg_done.wait_on();   // returns at once if configuration already finished
     // ... start_item / finish_item loop ...
   endtask
   ```

   Whichever side calls `get_global` first creates the event; the other receives the same object.

2. `traffic_seq` waits for a second `trigger()` that never comes. No item is ever sent, the objection that keeps the test alive is never dropped, and the run ends with `UVM_FATAL … [PH_TIMEOUT]` (default 9200 s in uvm-core, or your test's `set_timeout`). `wait_on()` avoids it because the event stays on. If configuration can happen again later in the test (after a mid-test reset, say), call `cfg_done.reset()` when reconfiguration starts, or the next `wait_on()` returns at once on the old trigger.

3. The test sets the threshold in `build_phase`, because the reset sequences may reach the barrier at time 0 and a threshold set later would race them:

   ```systemverilog
   // snippet: kata solution, part 3
   // container test, build_phase:
   uvm_barrier_pool::get_global(keys_pkg::RESET_DONE).set_threshold(3);
   // at the end of each agent's reset sequence body():
   uvm_barrier_pool::get_global(keys_pkg::RESET_DONE).wait_for();
   ```

   If the test also waits at the barrier, the threshold is 4. Without `set_threshold`, the barrier's threshold is 0 and every `wait_for()` returns at once.

</details>

### Debug challenge: the agent that never started

A test hangs until `PH_TIMEOUT`. The data agent's sequence calls `uvm_event_pool::get_global("cfg_dn").wait_on();`, and the configuration agent's sequence calls `uvm_event_pool::get_global("cfg_done").trigger();` at 100 ns. Nothing in the log mentions an error before the timeout.

1. Why is there no error message?
2. Which one line, added in the test's `report_phase` (or just before the timeout with a short `set_timeout`), shows the cause?
3. How do you make this class of bug impossible?

<details className="my-4 rounded-xl border border-border/70 p-3">
<summary className="cursor-pointer font-semibold">Show the worked solution</summary>

1. Nothing is wrong as far as UVM is concerned: `get_global("cfg_dn")` created a second, legal event, and waiting on an event that is never triggered is legal too.
2. `uvm_event_pool::get_global_pool().print();` In uvm-core the event pool prints one row per key, so `[cfg_dn]` and `[cfg_done]` appear side by side, and `num()` is 2 where you expected 1. (Printing is uvm-core behaviour; the standard does not specify the format.)
3. Define the key once as a package constant (`localparam string CFG_DONE = "cfg_done";`) and use only the constant. A typo in a constant's name is a compile error; a typo in a string literal is a silent second event.

</details>
