## Quick Take

- **What it is:** The **Direct Programming Interface (DPI)** lets SystemVerilog call functions and tasks written in C, called **imports**, and lets that C code call SystemVerilog functions and tasks back, called **exports**. IEEE 1800-2023 Clause 35 defines the SystemVerilog side, Annex H the C side, and Annex I the header `svdpi.h` that every simulator ships.
- **Why it matters:** Verification teams already own C and C++ code: reference models (CRC, ECC, codecs, instruction-set simulators), firmware and stimulus generators. DPI calls them like ordinary SystemVerilog functions, and the standard says the interface itself adds "no intrinsic overhead" (§35.2.1). The price is discipline: the SystemVerilog compiler never sees your C code, so nothing checks that the two sides agree.
- **The Analogy:** DPI is a border crossing. Every value that crosses is declared at customs (the import or export declaration) and repacked into the other side's format (C types, `svLogicVecVal`). *Where it breaks:* two countries go about their business at the same time, and DPI never does. A crossing is a call: the caller waits until it returns, and simulation time moves only inside an exported SystemVerilog task that waits.

**You will be able to:**
1. Write `import "DPI-C"` and `export "DPI-C"` declarations for functions and tasks, with matching C prototypes for 4-state `svLogicVecVal` vectors, strings and open arrays.
2. Choose `pure`, `context` or neither for an import, and explain what each one permits and costs.
3. Predict when simulation time passes across a DPI call, and write a `context` import task that waits through an exported task and honours the disable protocol.
4. Debug a mismatched prototype, C code that keeps a pointer to SystemVerilog-owned memory, a missing `context`, an export called in the wrong scope and a library that does not load, from their symptoms.
5. Implement a C reference model as a shared library, load it with the recommended `-sv_lib` switch and call it from a self-checking checker.

**You also need:** basic C (pointers, `malloc` and `free`, compiling a shared library). The section on disabled calls uses `fork … join_any` and `disable fork` from [F2C: Procedural Code and Flow Control](/curriculum/T1_Foundational/F2C_Procedural_Code_and_Flow_Control/index).

## Build Your Mental Model

The first eight subsections are the core path; read them in order. Subsections that start with *Practitioner depth* add the rules you need for daily work. The expert layer is in Push Further.

### Two layers and one boundary

DPI has two layers (§35.3). The **SystemVerilog layer** (Clause 35) is what you write in `.sv` files: import and export declarations, and ordinary calls. The **C layer** (Annex H) fixes how every SystemVerilog value looks in C and provides helper functions, all declared in `svdpi.h` (Annex I).

Neither compiler is required to analyze the other language (§35.2). The SystemVerilog compiler trusts your import declaration, the C compiler trusts your C prototype, and nothing compares the two. The standard calls this the **WYSIWYG principle**, "what you specify is what you get" (§35.6.1.1): C receives each argument exactly as the declaration specifies it, and no compiler converts between that declaration and your C prototype. Making them match is your job.

Two more rules shape everything on this page:

- **One thread of control.** DPI has no synchronization of its own. The only interaction is data passed in calls and control passed by calls (§35.2.1). When SystemVerilog calls C, the SystemVerilog caller waits; when C calls back, C waits. DPI never runs your C code alongside SystemVerilog.
- **Global linkage names.** Every import resolves to a C symbol, and every export defines one, in a single global name space (§35.4). By default the symbol is the SystemVerilog name. It must be a legal C identifier, and one name means one C symbol with one signature everywhere: there is no overloading.

### Your first import: calling C from SystemVerilog

The smallest complete DPI program is one import, one C function and one call:

```systemverilog
// compile: tb_top.sv; build add.c into a shared library (see Run it, below)
module tb_top;
  // The declaration is the whole contract: name, result type and argument types
  import "DPI-C" function int c_add(input int a, input int b);

  initial begin
    $display("c_add(2, 3) = %0d", c_add(2, 3));
    $finish;
  end
endmodule
```

```c
/* add.c */
#include "svdpi.h"

/* int inputs are small values, so they arrive by value (H.8.7) */
int c_add(int a, int b) {
  return a + b;
}
```

Expected output (illustrative, derived from the code; the simulator's own `$finish` message follows it):

```text
c_add(2, 3) = 5
```

An import declaration defines a SystemVerilog function whose body lives in C (§35.5.4). You call it exactly like a native function, with positional or named arguments (§35.6). The C function's name is the import's linkage name, `c_add`, and its parameters follow the type rules in the next subsection.

**The two mistakes everyone makes:**
1. **The C prototype does not match the import.** The SystemVerilog compiler cannot see your C code and the C compiler cannot see your import, so both accept a mismatch. If the import says `input logic [31:0] v` and the C code says `int v`, C reads a pointer as if it were a number. Check every parameter against the type table, or let your tool generate the prototypes (Push Further).
2. **C calls back into SystemVerilog from an import that is not `context`.** It compiles, then behaves unpredictably or crashes (§35.5.1.3). Any import whose C body calls an export, or a VPI routine, must be declared `context`.

### Types across the boundary

Each argument has two descriptions that must agree: the SystemVerilog formal in the declaration and the C parameter. Annex H fixes the C side for every permitted type (§35.5.6) and every direction:

- **Small values** are `byte`, `shortint`, `int`, `longint`, `real`, `shortreal`, `chandle`, `string`, and scalar `bit` and `logic`. As inputs they are passed **by value** (H.8.7).
- **Every other input** (packed vectors, structs, sized unpacked arrays) arrives **by reference**, as a pointer to `const` data (H.8.4, H.8.7).
- **Every output and inout** arrives as a pointer (H.8.8).
- **Open arrays**, declared with `[]`, arrive as a `const svOpenArrayHandle` in every direction (H.8.6).
- **Function results** must be small values (§35.5.5). Return anything wider through an `output` argument.

| SystemVerilog formal | C parameter for an input | C parameter for an output or inout | Function result? |
|---|---|---|---|
| `byte` / `byte unsigned` | `char` / `unsigned char` | `char*` / `unsigned char*` | yes |
| `shortint` / `shortint unsigned` | `short int` / `unsigned short` | `short int*` / `unsigned short*` | yes |
| `int` / `int unsigned` | `int` / `unsigned int` | `int*` / `unsigned int*` | yes |
| `longint` / `longint unsigned` | `long long` / `unsigned long long` | `long long*` / `unsigned long long*` | yes |
| `real` / `shortreal` | `double` / `float` | `double*` / `float*` | yes |
| `chandle` | `void*` | `void**` | yes |
| `string` | `const char*` | `const char**` | yes |
| `bit` (scalar) | `svBit`: 0 or 1 | `svBit*` | yes |
| `logic` (scalar) | `svLogic`: `sv_0`, `sv_1`, `sv_z` (2), `sv_x` (3) | `svLogic*` | yes |
| packed 2-state: `bit [N-1:0]`, packed `struct` of `bit` | `const svBitVecVal*` | `svBitVecVal*` | no |
| packed 4-state: `logic [N-1:0]`, `integer`, `time` | `const svLogicVecVal*` | `svLogicVecVal*` | no |
| `enum` | as its base type; names do not reach C | as its base type | if the base type is small |
| unpacked `struct` | `const S*`, matching C `struct S` | `S*` | no |
| sized unpacked array, `int a [8]` | `const int*`, C indices 0 to 7 | `int*` | no |
| open array, `int a []` | `const svOpenArrayHandle` | `const svOpenArrayHandle` | no; imports only |

The table follows Table H.1 and the unsigned rule after it (H.7.4), H.7.3 (enums, `integer`, `time`), H.7.6 to H.7.8, H.8.4 to H.8.9, and Annex I for the scalar codes. An unpacked struct's layout is implementation dependent but normally matches the C compiler (§35.5.6).

Two traps hide in that table:

- `logic [7:0]` and `bit [7:0]` are **different C types**. The 4-state form carries a second 32-bit word (`bval`) for every 32 bits, so C code written for one silently misreads the other.
- `byte unsigned` arrives by value as `unsigned char`, but `bit [7:0]` arrives by reference as `const svBitVecVal*` (H.7.4). Same eight bits, different C parameter.

Inputs are read-only: C must not change an input argument (§35.5.1.2), which is why Annex H gives every input a `const` qualifier (H.8.7). For pointers the `const` matters. For small values passed by value it does not: C ignores a top-level `const` when it compares prototypes, so `int a` and `const int a` declare the same parameter.

Some types cannot cross at all. Class handles cannot be passed, `ref` arguments are not allowed (Syntax 35-1, note 27), and only the types listed in §35.5.6 are permitted, so events and virtual interfaces stay on the SystemVerilog side.

### Exports: calling SystemVerilog from C

An **export** makes a SystemVerilog function or task callable from C. C sees it as an ordinary C function with the same prototype rules as an import (H.8.2):

```systemverilog
// snippet: inside a module
export "DPI-C" function sv_now;            // C sees the symbol sv_now
function automatic longint sv_now();
  return $time;                            // in this module's time unit
endfunction

// Its C body calls sv_now, so this import must be context (§35.5.1.3)
import "DPI-C" context function void c_log(input int value);
```

```c
/* snippet: log.c */
#include <stdio.h>
#include "svdpi.h"

extern long long sv_now(void);   /* the export: longint result -> long long */

void c_log(int value) {
  printf("[t=%lld] value=%d\n", sv_now(), value);
}
```

The rules for exports (§35.7, §35.8, H.8.2, H.9):

- Declare the export in the scope that defines the subroutine, once per subroutine. The export declaration and the definition may come in either order (§35.7).
- **Class methods cannot be exported** (§35.7). Export a subroutine of a module, interface, program or package instead.
- Exports follow the import type rules, but they cannot take open arrays (§35.5.6.1, H.8.2), and dynamic-array formals are erroneous (§35.5.6).
- Every exported function is a context function (§35.7). C may call an export only from inside a `context` import's call chain. From a call chain without the context property its behaviour is undefined (H.9). From code outside any import call chain, such as a VPI callback, it is simulator-defined and beyond the DPI specification (§35.5.3).
- An **exported task** may consume time. Its C prototype returns `int`: 1 if it returns because a disable stopped the import's thread, otherwise 0 (§35.8, §35.9). Only an imported **task** declared `context` may call an exported task. An imported function never may, just as a SystemVerilog function cannot enable a task (§35.8).

A practical note on logging: `printf` writes to the C program's standard output, which a simulator may buffer separately from its own log. `vpi_printf` writes to the simulator's output and log file (Table 36-9) and may be called even from an import that is not `context` (H.9.5).

### pure, context or neither

A qualifier is a promise about the C body. The compiler cannot check it, but it optimizes and instruments every call as if the promise were true (§35.5.1).

| Qualifier | What the C body may do | Effect on calls | Use it for |
|---|---|---|---|
| `pure` (non-void functions with no `output` or `inout` only) | Compute from its inputs. No I/O, no static or global data, nothing with side effects. | Calls may be removed, or replaced by an earlier result for the same inputs (§35.5.2) | Stateless models: CRC, parity, ECC syndromes |
| none | Use its own arguments; keep C-side state; write files (§35.5.1.3) | Ordinary calls; never a barrier to optimization (§35.5.3) | Self-contained C with side effects |
| `context` | All of the above, plus call exports, VPI routines and the `svdpi.h` scope functions (§35.5.3) | Each call is instrumented and is a barrier to optimization (§35.5.3) | C that calls back into SystemVerilog |

```systemverilog
// snippet: one import of each kind
import "DPI-C" pure function int unsigned crc32_step(input int unsigned crc,
                                                    input int unsigned word);
import "DPI-C" function void c_log_line(input string line);  // appends to a C-side file
import "DPI-C" context task c_send_words(input int n);       // calls an exported task
```

Choose in this order:
1. Does the C body call an export, a VPI routine, or `svGetScope`/`svSetScope`? Use `context`. If it calls an exported **task**, the import must also be a **task** (§35.8).
2. Otherwise, is it a non-void function whose result depends only on its inputs, with no I/O and no static data? You may add `pure` for speed.
3. Otherwise, use no qualifier.

An imported task can never be `pure` (§35.5.1.3). Do not add `context` just in case: every context call is instrumented and blocks optimizations, so the simulation can slow down (§35.5.1.3).

### Time: one side runs at a time

DPI calls follow the same timing rules as SystemVerilog subroutines:

- An imported **function** completes instantly and consumes zero simulation time (§35.5.1.1).
- An imported **task** also takes zero time, unless its C code calls an exported task that executes a delay, an event control or a `wait` (§35.5.1.5). Only a `context` import task may make that call (§35.8).
- While C code runs, no SystemVerilog process runs and time does not move. A C call that blocks on a socket for ten seconds of wall-clock time freezes the whole simulation for those ten seconds, whether it was imported as a function or as a task.
- When an exported task waits, the C stack frame stays suspended inside the call. The simulator runs other processes and advances time, and the export finally returns into C at the new time.

The worked example in Make It Work uses this pattern. A C traffic model sends words through an exported task, and the clock edges happen inside that task:

```systemverilog
// snippet (from the worked example)
export "DPI-C" task sv_send_word;
task automatic sv_send_word(input int unsigned w);  // automatic: one w per caller
  cb.valid <= 1'b1;
  cb.word  <= w;
  @(cb);              // time passes here, in SystemVerilog
  cb.valid <= 1'b0;
endtask

import "DPI-C" context task c_send_words(input int n);
```

```c
/* snippet (from traffic.c in the worked example) */
extern int sv_send_word(unsigned int w);   /* exported task: returns 1 if disabled */

int c_send_words(int n) {                  /* import task: int result for §35.9 */
  static const unsigned int words[2] = { 0x00000001u, 0xDEADBEEFu };
  for (int i = 0; i < n && i < 2; i++) {
    if (sv_send_word(words[i]))
      return 1;                            /* disabled: acknowledge at once */
  }
  return 0;
}
```

**Why `automatic`:** several SystemVerilog threads can be inside the same import task at once, each suspended in its own export call (§35.5.1.5). An `automatic` exported task gives each call its own variables; a static task would share them.

### Predict, then check: the DPI boundary explorer

The explorer below is a deterministic model of Clause 35 and Annex H. Part 1 shows how one argument crosses; part 2 judges import and export pairs as legal, a compile error, or code that compiles but is illegal or undefined when it runs. Commit to an answer before you reveal each one:

1. **Part 1:** choose the type `bit [7:0]` with direction *input*. Is the C parameter `unsigned char` or something else? Then try `logic [31:0]` with direction *output / inout*.
2. **Part 1:** choose `int x[]`. Which C type arrives, and how would you loop over it?

4. **Part 2:** compare *export, no context* with *export, with context*. Which one can crash?
5. **Part 2:** *function calls exported task*, *context task waits in SV* and *pure with a counter*. Where does time pass, and what silently goes missing?

What the explorer showed:

- **Three kinds of verdict.** A *compile error* means the declaration itself breaks a rule the SystemVerilog compiler checks: a `pure` task (§35.5.1.3) or a vector result (§35.5.5). *Compiles, but illegal or undefined* means the C body breaks a rule nobody checks: an export called from a non-`context` import, an exported task called from an imported function, or a `pure` function with side effects. Expect no error message for those; expect wrong results or a crash.
- **Same width, different crossing.** `bit [7:0]` arrives by reference as `const svBitVecVal*` in a 32-bit chunk, not as `unsigned char`. Of the 8-bit types, only `byte` and `byte unsigned` arrive by value.
- **Time passes only in one scenario**, *context task waits in SV*, and only inside the exported task. Every function call, and every task that does not call a waiting export, takes zero simulation time.
- **One thing the explorer leaves out.** Its *context task waits in SV* C code ignores the value `sv_wait_cycles` returns. Real code must check it, `if (sv_wait_cycles(5)) return 1;`, so that a disabled caller is acknowledged (§35.9). The section on disabled calls below explains why.

### Memory: who owns what, and for how long

SystemVerilog and C allocate memory separately, and each side frees only what it allocated (§35.5.1.4). Four rules follow:

1. **Anything SystemVerilog passes by reference is valid only during the call.** That covers strings, packed vectors, structs and arrays. C may assume nothing about their lifetime; to keep a value, copy it into memory that C owns (H.8.4, H.8.10).
2. **C never frees SystemVerilog's memory** (§35.5.1.4, H.8.10). Freeing the `const char*` of an `input string` can corrupt the simulator's heap.
3. **SystemVerilog never frees memory it gets from C.** A string that C returns, or writes to an `output string`, must still be valid when the call returns: point at static or C-owned heap storage, never at a local array on the C stack (H.8.10).
4. **C objects that live across calls travel as a `chandle`.** C allocates the object, SystemVerilog stores the handle, and SystemVerilog calls another import that frees it. The standard describes exactly this pattern (§35.5.1.4).

The classic mistake keeps SystemVerilog's pointer:

```c
/* snippet: BAD */
static const char* g_name;                 /* points into SystemVerilog memory */

void c_set_name(const char* name) {
  g_name = name;                           /* not guaranteed after the call returns */
}
```

The fix copies the characters into memory that C owns, and frees the previous copy:

```c
/* snippet: GOOD */
#include <stdlib.h>
#include <string.h>

static char* g_name;                       /* C-owned copy */

void c_set_name(const char* name) {
  char* copy = malloc(strlen(name) + 1);
  if (copy == NULL) return;
  strcpy(copy, name);
  free(g_name);                            /* free(NULL) is allowed */
  g_name = copy;
}
```

For a C object that must survive between calls, hand SystemVerilog a `chandle` and an explicit free function:

```systemverilog
// snippet: the chandle pattern
import "DPI-C" function chandle c_model_new(input int seed);
import "DPI-C" function int     c_model_next(input chandle model);
import "DPI-C" function void    c_model_free(input chandle model);
import "DPI-C" function string  c_model_name();  // C returns static text
```

### Declaration and calling rules

*Practitioner depth.* Import and export declarations may appear in a module, interface, program, package, compilation-unit scope or generate scope (H.9.2). They cannot appear inside a class, so put imports in a package and call them from class methods. An import declaration defines a SystemVerilog subroutine in its scope, so the same name can be imported only once per scope (§35.5.4).

The linkage name can differ from the SystemVerilog name, and one C function can stand behind several SystemVerilog names with different default arguments (§35.2.1, §35.4, §35.5.4):

```systemverilog
// snippet: SystemVerilog name crc_seed_step, C symbol crc32_step
import "DPI-C" pure crc32_step = function int unsigned crc_seed_step(
  input int unsigned crc = 32'hFFFF_FFFF,    // default: may be omitted at the call
  input int unsigned word);

// called by name, using the default seed
initial $display("%h", crc_seed_step(.word(32'h0000_0001)));  // 66074786
```

Every declaration of one linkage name, in any scope, must have exactly the same signature: result type, argument types and directions, ranges, the `pure` or `context` property and the `"DPI-C"` string (§35.5.4). Only argument names and default values may differ. Always write `"DPI-C"`: the older `"DPI"` string is deprecated, and a tool must give a warning or an error for it (§35.5.4).

Calls behave as if arguments were copied (§35.6.1):

- **Inputs are copied in.** C sees a `const` value or a `const` pointer and must not modify it (§35.5.1.2).
- **Outputs are copied out.** Their initial value in C is undetermined, so C should write every output it is given (§35.5.1.2).
- **Inouts are both.** C may read the initial value of an inout argument.
- **Coercion happens on the SystemVerilog side.** If an actual argument's type differs from the formal, for example a `logic [15:0]` passed to an `int`, SystemVerilog creates a temporary of the formal's type; C always receives exactly the declared type (§35.6.1, §35.6.1.1).
- **Output changes appear after the call.** Values written to outputs propagate, and wake processes waiting on them, only when the C call returns (§35.6.2).

### 4-state vectors in C

*Practitioner depth.* A packed vector crosses in **canonical form**: an array of 32-bit chunks, with chunk `[0]` holding bits 31:0, chunk `[1]` bits 63:32, and so on (H.7.7). A 2-state vector uses `svBitVecVal`, one 32-bit word per chunk. A 4-state vector uses `svLogicVecVal`, two words per chunk named `aval` and `bval`; the type is equivalent to VPI's `s_vpi_vecval` (H.7.7), whose bit encoding is given in Figure 38-8 (§38.15). `SV_PACKED_DATA_NELEMS(width)` gives the number of chunks (Annex I).

| `aval` bit | `bval` bit | Logic value |
|---|---|---|
| 0 | 0 | 0 |
| 1 | 0 | 1 |
| 0 | 1 | Z |
| 1 | 1 | X |

The last chunk usually has unused bits. Their contents are undetermined, and C must mask them, or sign-extend them for signed values, before using the chunk (H.7.7). Ranges are normalized first, so `logic [39:0]`, `logic [0:39]` and `logic [47:8]` all reach C as bits 39 down to 0 (H.7.6).

This C function reads a 40-bit 4-state value, reports X or Z bits, and otherwise returns the value through an `output longint`:

```systemverilog
// snippet
import "DPI-C" function int c_read40(input logic [39:0] v, output longint value);

logic [39:0] addr = 40'h12_3456_789A;
longint      a;

initial begin
  if (c_read40(addr, a)) $display("addr = %0h", a);       // addr = 123456789a
  addr[3] = 1'bx;
  if (!c_read40(addr, a)) $display("addr has X or Z bits");
end
```

```c
/* snippet: read40.c */
#include "svdpi.h"

/* logic [39:0] is SV_PACKED_DATA_NELEMS(40) == 2 chunks: v[0] holds bits 31:0,
   the low 8 bits of v[1] hold bits 39:32, the rest of v[1] is undetermined. */
int c_read40(const svLogicVecVal* v, long long* value) {
  unsigned int hi_a = SV_GET_UNSIGNED_BITS(v[1].aval, 8);
  unsigned int hi_b = SV_GET_UNSIGNED_BITS(v[1].bval, 8);
  *value = 0;                              /* write every output (§35.5.1.2) */
  if (v[0].bval != 0 || hi_b != 0)
    return 0;                              /* some bit is X or Z: its bval is 1 */
  *value = ((long long)hi_a << 32) | v[0].aval;
  return 1;
}
```

### Open arrays

*Practitioner depth.* An **open array** formal leaves a dimension unsized with `[]`, so one C routine accepts arrays of any size (§35.5.6.1). C receives a handle, never a raw pointer, and reads it through `svdpi.h` functions (H.8.6, H.12):

```systemverilog
// snippet
import "DPI-C" function int unsigned c_crc32_words(input int unsigned data []);

int unsigned w [1:2] = '{32'h0000_0001, 32'hDEAD_BEEF};
initial $display("CRC-32 = %h", c_crc32_words(w));       // CRC-32 = 929660f4
```

```c
/* snippet: words.c (crc32_step is the model from Make It Work) */
#include <stddef.h>
#include "svdpi.h"

unsigned int crc32_step(unsigned int crc, unsigned int word);

unsigned int c_crc32_words(const svOpenArrayHandle data) {
  unsigned int crc = 0xFFFFFFFFu;
  for (int i = svLow(data, 1); i <= svHigh(data, 1); i++) {  /* SV indices */
    const unsigned int* p = (const unsigned int*)svGetArrElemPtr1(data, i);
    if (p == NULL) return 0;               /* never dereference NULL (H.12.4) */
    crc = crc32_step(crc, *p);
  }
  return ~crc;
}
```

A traced call with the actual argument `w`, declared `int unsigned w [1:2]`:

| C call | Result | Why |
|---|---|---|
| `svLow(data, 1)`, `svHigh(data, 1)` | 1, 2 | Unpacked dimensions keep the actual argument's own range (H.12.1, H.12.2) |
| `svSize(data, 1)` | 2 | Number of elements in dimension 1 |
| `svGetArrElemPtr1(data, 1)` | points at `w[1]`, `0x00000001` | Accessors take SystemVerilog indices, not 0-based ones (H.12) |
| `svGetArrElemPtr1(data, 2)` | points at `w[2]`, `0xDEADBEEF` | Same rule |
| `svGetArrElemPtr1(data, 0)` | `NULL` | Index outside the range (H.12.4) |
| return value | `929660f4` | The same CRC-32 as the worked example |

The rules for open arrays:

- Dimension 0 is the packed part; dimensions 1 and up are the unpacked ones (H.12.2).
- Pointer access (`svGetArrElemPtr1`, `svGetArrayPtr`) works only when the elements are laid out as in C. For scalar or packed elements, such as `bit [7:0] b []`, the layout is implementation dependent and the pointer functions may return `NULL` (H.12.4). Copy each element in canonical form instead, with `svGetBitArrElem1VecVal` or `svGetLogicArrElem1VecVal`, and write back with the matching `svPut` function (H.12.5).
- For an `output` or `inout` open array, C may write only as many elements as the actual argument holds; writing more is undefined (H.12). Use `svSize`.
- A dynamic array can be passed to an open-array formal under the same rules as for a native subroutine (§35.6.1.1, §7.7).
- Exports cannot take open arrays (§35.5.6.1).
- There is no `svGetIntElement` or similar helper. If a function is not declared in Annex I, it does not exist.

### Scope and context

*Practitioner depth.* A `context` import knows where it was declared. Each call carries the instance scope that contains the import declaration, for example `tb_top` (§35.5.3). That scope decides which exports C can call directly: only exports defined in that same scope. To reach an export in another instance, C switches scope first:

```systemverilog
// snippet: one exported task per bus_bfm instance
interface bus_bfm (input logic clk);
  logic [7:0] data;
  clocking cb @(posedge clk);
    output data;
  endclocking

  export "DPI-C" task bfm_write;           // every instance exports bfm_write
  task automatic bfm_write(input byte unsigned d);
    cb.data <= d;
    @(cb);
  endtask
endinterface

module tb_top;
  logic clk = 1'b0;
  always #5 clk = ~clk;

  bus_bfm u_bfm0 (.clk);
  bus_bfm u_bfm1 (.clk);

  import "DPI-C" context task c_firmware(input string bfm_path);

  initial begin
    c_firmware("tb_top.u_bfm1");
    $finish;
  end
endmodule
```

```c
/* snippet: firmware.c */
#include <stddef.h>
#include "svdpi.h"

extern int bfm_write(unsigned char d);     /* exported by every bus_bfm instance */

int c_firmware(const char* bfm_path) {
  svScope target = svGetScopeFromName(bfm_path);  /* NULL if no such instance */
  if (target == NULL) return 0;
  svScope caller = svSetScope(target);     /* returns the previous scope */
  if (bfm_write(0xA5))
    return 1;                              /* disabled: acknowledge (§35.9) */
  svSetScope(caller);
  return 0;
}
```

The scope functions (H.9.3, Annex I) work only inside a `context` call chain; anywhere else their behaviour is undefined (H.9):

- `svGetScope()`: the current scope, which is the import's declaration scope unless `svSetScope` changed it.
- `svSetScope(scope)`: selects the scope for the export calls that follow, and returns the previous scope.
- `svGetScopeFromName(name)`: the scope of a module, interface, program or generate instance, given its full name; `NULL` for a name it does not recognize.
- `svGetNameFromScope(scope)`: the full name of a scope, for messages.
- `svPutUserData` and `svGetUserData`: attach C data to a scope, which gives one C model object per SystemVerilog instance (Push Further).

### When a DPI call is disabled

*Practitioner depth.* A `disable` statement can terminate a thread while it is inside an import call chain: `disable fork` after a timeout, or `disable` of a named block that encloses the call (§9.6.2, §9.6.3). An import enters the **disabled state** only at one moment, when an export it called returns (§35.9). The **disable protocol** then lets C clean up (close files, free memory) before it unwinds:

- **(a)** An exported task returns 1 when it returns because of a disable, and 0 otherwise. The simulator guarantees this.
- **(b)** An imported task that returns because of a disable returns 1, and 0 otherwise.
- **(c)** An imported function in the disabled state calls `svAckDisabledState()` before it returns.
- **(d)** Once disabled, the import makes no further export calls.

Items (b) to (d) are the C programmer's job, simulators check them, and breaking one is a fatal simulation error (§35.9). `svIsDisabledState()` tells C whether its thread is in the disabled state (Annex I).

A disabled call does not finish its work, so do not trust its results: after an import returns because of a disable, the values of its `output` and `inout` arguments, and a function's result, are undefined (§35.9).

```systemverilog
// snippet: give the C traffic model at most 15 ns
fork
  c_send_words(2);
  #15;
join_any
disable fork;   // kills c_send_words if it is still waiting inside sv_send_word
```

The recommended switches (J.3, J.4):

- `-sv_lib <path without extension>` loads one library. The simulator appends the platform's extension, such as `.so`. Repeat the switch for more libraries.
- `-sv_root <directory>` is prefixed to every relative path that follows it.

### DPI, VPI or the old PLI?

*Practitioner depth.* SystemVerilog has two C interfaces, and you will meet the names of a third in older code:

| Interface | What it is | Use it for |
|---|---|---|
| DPI (Clause 35) | Direct calls between SystemVerilog and C with typed arguments | Reference models, firmware models, C libraries |
| VPI (Clauses 36 to 38) | The third generation of the PLI: a C library that walks the elaborated design, reads and writes objects by name and registers callbacks (§36.2) | Tools: signal access by name at run time, value-change callbacks, user-defined system tasks |
| TF and ACC routines | The first and second generations of the PLI | Nothing new: deprecated by IEEE 1364-2005 and not part of IEEE 1800 (§36.2, Annex C.2.1) |

A `context` import may call VPI routines (§35.5.3). uvm-core's register backdoor does exactly that (Push Further).

### Pitfalls and debugging

Message texts depend on the simulator, so the first column names what you will see rather than an exact message.

| What you see | Likely cause | Fix |
|---|---|---|
| The simulator cannot load the library, or reports an undefined or unresolved symbol | Library not loaded: no `-sv_lib`, a wrong path, or the extension included (J.4); or a C++ name without `extern "C"` (§35.5.1.6) | Load it with `-sv_lib <path without extension>`; give C++ functions C linkage |
| Wrong values or a crash on the first call | The C prototype does not match the import: by value versus by pointer, `long` for `longint`, `int` for a `logic` vector | Check every parameter against the type table, or include a prototype header your tool generates |
| A crash or nonsense only when C calls back into SystemVerilog | The import is not `context` (§35.5.1.3) | Declare it `context`; an import that calls an exported task must be a `context` task |
| An error that the export does not exist in a scope | The export lives in another instance than the import's declaration scope (§35.5.3) | `svSetScope(svGetScopeFromName(...))` before the call |
| A print, file write or counter in C silently goes missing | The import is `pure` (§35.5.2) | Remove `pure` |
| A string that turns into garbage later, or a crash inside `free` | C kept or freed SystemVerilog's pointer (H.8.10, §35.5.1.4) | Copy the data; free only what C allocated |
| A string that C returned, or wrote to an `output string`, arrives as garbage | C pointed it at a local array on its own stack, which is gone when the call returns (H.8.10) | Point it at static text or C-owned heap memory |
| Comparisons on wide vectors fail on some runs or tools only | Unused bits of the last chunk not masked (H.7.7) | `SV_GET_UNSIGNED_BITS`, for `aval` and `bval` |
| Memory corruption after a call with an output open array | C wrote past the actual argument's size (H.12) | Bound every write with `svSize` |
| A fatal error right after a timeout's `disable fork` | C ignored an export's return value of 1 and called another export (§35.9) | Return 1 at once when an export returns 1 |
| The whole simulation freezes and time stops | C blocks on I/O or loops without returning | Poll without blocking; wait inside an exported task |
| A warning or error naming the `"DPI"` string | Deprecated spec string (§35.5.4) | Write `"DPI-C"` |

- An import is a SystemVerilog subroutine whose body is a C symbol; an export is a SystemVerilog subroutine C can call.
- Nothing checks that the C prototype matches the declaration. Small values travel by value, everything else by pointer or handle, and `logic` vectors are `svLogicVecVal` chunks with `aval` and `bval`.
- `pure` lets the compiler drop calls; `context` lets C call back and costs optimization; most imports need neither.
- Functions take zero time. Time passes only inside an exported task called from a `context` import task, and C must answer a disable by returning 1.
- Each side frees only its own memory, and nothing passed by reference outlives the call.

## Make It Work

### A C reference model checks a CRC block

You will build a small self-checking testbench from three files. The design under test (DUT), `crc_dut`, computes one CRC-32 step per accepted 32-bit word. `crc_checker` watches the pins and predicts every result with a `pure` C reference model. A C traffic model, `c_send_words`, sends the words through an exported task, so simulation time passes inside SystemVerilog while C waits.

```systemverilog
// compile: tb_top.sv, together with crc_model.c and traffic.c (see Run it)
`timescale 1ns/1ps

package crc_dpi_pkg;
  // The result depends only on the inputs, with no C state and no I/O,
  // so the import may be pure (§35.5.2).
  import "DPI-C" pure function int unsigned crc32_step(input int unsigned crc,
                                                      input int unsigned word);
endpackage

// DUT: one CRC-32 step (reflected polynomial 32'hEDB8_8320) per accepted word
module crc_dut (
  input  logic        clk,
  input  logic        rst_n,
  input  logic        valid,
  input  logic [31:0] word,
  output logic [31:0] crc
);
  function automatic logic [31:0] step(input logic [31:0] c, input logic [31:0] w);
    logic [31:0] r;
    r = c;
    for (int b = 0; b < 32; b++)
      r = (r >> 1) ^ ((r[0] ^ w[b]) ? 32'hEDB8_8320 : 32'h0);
`ifdef CRC_BUG
    r[7] = ~r[7];  // injected design bug: the checker must catch it
`endif
    return r;
  endfunction

  always_ff @(posedge clk or negedge rst_n)
    if (!rst_n)     crc <= 32'hFFFF_FFFF;
    else if (valid) crc <= step(crc, word);
endmodule

// Passive checker: predicts each result with the C model and compares
module crc_checker (
  input logic        clk,
  input logic        rst_n,
  input logic        valid,
  input logic [31:0] word,
  input logic [31:0] crc
);
  import crc_dpi_pkg::*;

  int unsigned expected;   // C-model register value after the words seen so far
  bit          check_due;  // the DUT accepted a word at the previous edge
  int          pass_n;
  int          fail_n;

  // Inputs are sampled just before each edge (default #1step), so the
  // checker never races the DUT's nonblocking updates on the same edge.
  clocking mon_cb @(posedge clk);
    input rst_n, valid, word, crc;
  endclocking

  always @(mon_cb) begin
    if (check_due) begin
      if (mon_cb.crc === expected) pass_n++;
      else begin
        fail_n++;
        $error("crc_checker: DUT crc=%h, C model=%h", mon_cb.crc, expected);
      end
    end
    check_due = 1'b0;
    if (!mon_cb.rst_n) expected = 32'hFFFF_FFFF;
    else if (mon_cb.valid) begin
      expected  = crc32_step(expected, mon_cb.word);  // pure C reference model
      check_due = 1'b1;
    end
  end
endmodule

module tb_top;
  logic        clk   = 1'b0;
  logic        rst_n = 1'b0;
  logic        valid = 1'b0;
  logic [31:0] word  = '0;
  logic [31:0] crc;

  always #5 clk = ~clk;  // rising edges at 5, 15, 25, ... ns

  crc_dut     u_dut (.clk, .rst_n, .valid, .word, .crc);
  crc_checker u_chk (.clk, .rst_n, .valid, .word, .crc);

  // Drive DUT inputs only through a clocking block: the #0 output skew puts
  // new values in Re-NBA, after the DUT has sampled this edge (§14.16).
  clocking cb @(posedge clk);
    output rst_n, valid, word;
  endclocking

  // Exported task: simulation time passes in here, never in C
  export "DPI-C" task sv_send_word;
  task automatic sv_send_word(input int unsigned w);
    cb.valid <= 1'b1;
    cb.word  <= w;
    @(cb);              // the DUT accepts w at this edge
    cb.valid <= 1'b0;   // a back-to-back call drives 1 again in the same step
  endtask

  // A context import task may call the exported task above (§35.8)
  import "DPI-C" context task c_send_words(input int n);

  initial begin
    repeat (2) @(cb);   // reset is low at the edges at 5 and 15 ns
    cb.rst_n <= 1'b1;
    @(cb);              // t = 25 ns
    c_send_words(2);    // returns at t = 45 ns, two clock edges later
    repeat (2) @(cb);   // let the checker compare the last result
    $display("t=%0d ns crc register=%h CRC-32=%h", $time, crc, ~crc);
    $display("PASS=%0d FAIL=%0d", u_chk.pass_n, u_chk.fail_n);
    $finish;
  end
endmodule
```

```c
/* crc_model.c: the pure reference model */
#include "svdpi.h"

/* One CRC-32 step over the 32 bits of word, least significant bit first.
   No static state and no I/O: exactly what the pure import promises. */
unsigned int crc32_step(unsigned int crc, unsigned int word) {
  for (int b = 0; b < 32; b++) {
    unsigned int bit = (word >> b) & 1u;
    crc = (crc >> 1) ^ (0xEDB88320u & (0u - ((crc ^ bit) & 1u)));
  }
  return crc;
}
```

```c
/* traffic.c: a tiny C traffic model that sends words through the export */
#include "svdpi.h"

/* The exported SystemVerilog task, seen from C: returns 1 if the calling
   SystemVerilog thread was disabled while it waited, else 0 (§35.8, §35.9). */
extern int sv_send_word(unsigned int w);

/* Context import task: its int result is the disable acknowledgement. */
int c_send_words(int n) {
  static const unsigned int words[2] = { 0x00000001u, 0xDEADBEEFu };
  for (int i = 0; i < n && i < 2; i++) {
    if (sv_send_word(words[i]))
      return 1;     /* disabled: return 1 at once, call no more exports */
  }
  return 0;
}
```

### How to build it yourself

1. **Write the C model and test it without a simulator.** Bugs are far cheaper to find here than in a simulation log. One step from the reset value must give `66074786`, and its inverse, `99f8b879`, is the standard CRC-32 of the bytes `01 00 00 00`:

```c
/* test_model.c: gcc -I"$SIM_INCLUDE" -o test_model test_model.c crc_model.c */
#include <stdio.h>

unsigned int crc32_step(unsigned int crc, unsigned int word);

int main(void) {
  unsigned int r = crc32_step(0xFFFFFFFFu, 0x00000001u);
  printf("%08x %08x\n", r, ~r);            /* expect: 66074786 99f8b879 */
  return r == 0x66074786u ? 0 : 1;
}
```

2. **Declare the import in a package** and pick the qualifier: the model has no state and no I/O, so `pure` is allowed.
3. **Check the prototypes.** Compare each C parameter with the type table, or include the prototype header your simulator can generate from the declarations (tool-dependent; see Push Further).
4. **Write the export and the `context` import task** for anything that must wait. Make the exported task `automatic`, and make C check every exported task's return value.
5. **Build the shared library** with `-shared -fPIC` and the simulator's include directory.
6. **Compile, elaborate and run** with `-sv_lib libcrc_model`.
7. **Read the log** for `PASS=2 FAIL=0`, then **prove that the checker can fail**: rebuild the SystemVerilog with `CRC_BUG` defined.

### Variations to try

- **Inject the bug.** With `CRC_BUG` defined, the checker reports two mismatches. Your simulator wraps each `$error` message in its own text, which names the severity, the file and line, the scope `tb_top.u_chk` and the time (§20.10). Below, `<error at 45 ns>` stands in for that tool-specific part:

- **Send three words.** Add `0x12345678u` to `words` in `traffic.c`, raise the array size and the loop bound from 2 to 3, and call `c_send_words(3)`. ## Push Further

### Expert: Context call chains and per-instance C state

A **DPI import call chain** starts when SystemVerilog calls an import and lasts until that call returns, including any exports C calls in between (§35.5.3). Its context follows strict rules:

- A call to a `context` import starts the chain's context at the import's instance scope. `svSetScope` changes it. When an export returns into C, the context reverts to its value when the export was called.
- Each import call takes the context property of the import it calls, and the property is never promoted: a non-`context` import called further down the chain, for example from an exported SystemVerilog function, is still non-`context`. The context characteristic adheres to the call chain, not to the C code, so the same C function can run in both context and non-context chains.
- Jumping out of an export with `setjmp`/`longjmp`, so that it never returns normally to its import, gives undefined results (§35.5.3, H.9.2).

Because the context identifies the calling instance, a C model can keep one object per SystemVerilog instance with `svPutUserData` and `svGetUserData` (H.9.3). The key must be unique across all C code in the simulation; the standard recommends the address of a static C function or variable:

```c
/* snippet: one model object per instance that calls c_model_step.
   SV: import "DPI-C" context function int c_model_step(input int in); */
#include <stdlib.h>
#include "svdpi.h"

typedef struct { unsigned int state; } model_t;
static int model_key;                      /* its address is the unique key */

int c_model_step(int in) {
  svScope me = svGetScope();               /* the instance that made this call */
  model_t* m = (model_t*)svGetUserData(me, &model_key);
  if (m == NULL) {                         /* first call from this instance */
    m = calloc(1, sizeof *m);
    if (m == NULL) return -1;
    if (svPutUserData(me, &model_key, m) != 0) {
      free(m);
      return -1;
    }
  }
  m->state += (unsigned int)in;
  return (int)m->state;
}
```

For debug messages, `svGetCallerInfo` returns the SystemVerilog file and line of the import call when the tool provides it (Annex I). One quirk of the standard: the H.9.4 example calls `svGetScopeByName`, which `svdpi.h` does not declare. The real function is `svGetScopeFromName` (Annex I).

### Expert: Reentrancy, C threads and blocking

**Reentrancy.** When an import task waits inside an exported task, another SystemVerilog thread can call the same import, so the same C code can be active in several threads at once (§35.5.1.5). Keep per-call state in local variables or per-instance objects, not in C statics, and call only thread-safe library functions.

**C threads.** A C library may start its own threads, but DPI defines nothing for them. The standard calls DPI use from outside an import call chain simulator-defined and beyond the DPI specification, with a VPI callback as its example (§35.5.3); a thread that your own C code starts is not covered at all. Exports called from a chain without the context property behave in undefined ways (H.9). The portable design keeps worker threads inside C: they fill a lock-protected queue, and SystemVerilog drains it through a `context` import that it polls, for example once per clock.

**Blocking.** The simulator stops while C runs, because DPI transfers control and never runs the two sides at once (§35.2.1). A blocking `recv`, `sleep` or long computation freezes simulation time and every other process. Make socket or pipe access non-blocking, and let time pass in an exported task between polls.

### Expert: Disabling imported functions, and cleanup

Imported **functions** follow the disable protocol too (§35.9 c, d). A function cannot wait, so it can enter the disabled state only if an exported function it calls executes a `disable` of a block that encloses the import call. For native code, IEEE 1800-2023 §9.6.2 makes exactly that undefined: a `disable` inside a function that disables a block or task that called the function. So never design for this path, but code for it defensively. An imported function in the disabled state must make no further export calls, and it must call `svAckDisabledState()` before it returns. `svIsDisabledState()` lets shared helper code test the state.

The protocol exists so that C can clean up before it unwinds: close files, free heap memory, release VPI handles (§35.9). Write cleanup once, call it on both the normal and the disabled path, and test the disabled path deliberately; the kata below does.

One corner case catches people out. If a `disable` statement targets the exported task itself, rather than the import's thread or a block around it, the import is not in the disabled state: the export returns 0, `svIsDisabledState()` returns 0, and C carries on normally (§35.9). Only a disable that targets the import itself, or a parent that encloses the call, puts the import into the disabled state.

### Expert: C++ models and shared-library hygiene

DPI uses C linkage, and exceptions must never cross the boundary (§35.5.1.6). Wrap every C++ entry point:

```cpp
// snippet: crc_model.cpp
extern "C" unsigned int crc32_step(unsigned int crc, unsigned int word) {
  try {
    return model::step(crc, word);   // C++ code that may throw
  } catch (...) {
    return 0u;                       // never let an exception reach SystemVerilog
  }
}
```

`svdpi.h` wraps its own declarations in `extern "C"` (Annex I), but your functions need it too. Annex J.4 warns about two more traps in shared libraries: C++ global objects and static initializers depend on the run-time environment at load time, and two libraries that reference different versions of the same third-party library can interfere. Keep DPI libraries small, link third-party code deliberately, and give every library a version function that the testbench checks at time 0.

### Expert: Performance at scale

- **Context costs.** Each call to a `context` import is a barrier to compiler optimization (§35.5.3, H.6.5). Use it only where C really calls back.
- **Pure helps.** The compiler may skip or reuse `pure` calls (§35.5.2), which pays off for repeated calls with the same inputs.
- **Sized beats open.** A sized array formal is passed by reference "with no overhead"; an open array is passed by handle with some overhead (H.12.1). For large open arrays in C layout, `svGetArrayPtr` plus `memcpy` avoids a call per element (H.12.4, H.12.9).
- **Cross less often.** Every crossing has a cost. Send one call per transaction, not one per clock or per bit. How large the cost is depends on the tool, so measure it with your simulator's profiler.
- **Read time directly.** A `context` import can call `svGetTime`, `svGetTimeUnit` and `svGetTimePrecision` instead of calling an export just to read `$time` (H.13).

### Expert: DPI inside a UVM environment

- **Where the declarations go.** Imports cannot sit inside a class (H.9.2 lists the legal scopes), so put them in a package next to your environment code and call them from class methods, such as a predictor's `write` method.
- **Calling objects from C.** Class methods cannot be exported (§35.7), and class handles cannot cross (Syntax 35-1, note 27). The usual bridge is a package-level exported function that takes an integer id, finds the object in a package-level table and calls its method. C calls it through a `context` import declared in the same package, so the export is in the import's own scope and needs no `svSetScope` (§35.5.3).
- **uvm-core's own DPI** (uvm-core impl.). `src/dpi/uvm_hdl.svh` declares `context` imports such as `uvm_hdl_deposit`, `uvm_hdl_read`, `uvm_hdl_force` and `uvm_hdl_release`, on values of type `uvm_hdl_data_t`, a `logic [UVM_HDL_MAX_WIDTH-1:0]` that defaults to 1024 bits. `uvm_reg::backdoor_read_func` and `uvm_reg::backdoor_write` call them (`src/reg/uvm_reg.svh`). Their C side, for example `src/dpi/uvm_hdl_questa.c`, finds signals with VPI (`vpi_handle_by_name`) and writes them with `vpi_put_value`, which is why the imports are `context`. Defining `UVM_NO_DPI` also defines `UVM_HDL_NO_DPI`, `UVM_REGEX_NO_DPI` and `UVM_CMDLINE_NO_DPI` (`src/dpi/uvm_dpi.svh`), which compiles out uvm-core's DPI.
- **Reference models.** A C model behind a `pure` or plain import is the predictor half of a scoreboard; [A-UVM-6](/curriculum/T3_Advanced/A-UVM-6_Scoreboards_and_Reference_Models/index) covers the scoreboard architecture around it.

### Expert: Standard quirks and tool-dependent behaviour

- **Prototype headers** (tool-dependent). Most simulators can write a C header with the exact prototypes your declarations need; include it so that the C compiler checks you. Verilator, for example, writes it with `--dpi-hdr-only`. Look up your tool's option.
- **Compiling C through the simulator** (tool-dependent). Some tools accept `.c` files on their command line and build the library themselves. Verilator, for example, takes C and C++ files on its command line (with `--exe`) and has no `-sv_lib`.
- **A contradiction in the standard.** The import examples in §35.5.4 include `function bit [15:0] getStimulus()`, but §35.5.5 allows only small values as results. The H.9.4 example's `function integer MapID` breaks the same rule, because `integer` is a 4-state packed type (H.7.3). Follow §35.5.5: whether a tool accepts such results is tool-dependent, and portable code returns vectors through `output` arguments.
- **A broken helper macro.** `SV_GET_SIGNED_BITS(VALUE, N)` in Annex I tests bit `N` instead of the sign bit `N-1`, so do not use it; mask with `SV_GET_UNSIGNED_BITS` and sign-extend by hand. `SV_MASK(N)` shifts `-1` left, which ISO C leaves undefined for negative values; mainstream compilers produce the expected mask, but a strict checker may flag it.
- **`char` signedness.** Table H.1 maps `byte` to plain `char`, and C leaves it to the platform whether `char` is signed. On platforms where it is unsigned (Arm Linux, for example), cast to `signed char` before arithmetic on a `byte`.

### Expert: VPI and the PLI family

The **Programming Language Interface (PLI)** has had three generations: TF routines, ACC routines and **VPI**, the Verification Procedural Interface (§36.2). IEEE 1364-2005 deprecated the TF and ACC routines, and IEEE 1800 does not include them (§36.2, Annex C.2.1). VPI's object model is in Clause 37 and its routines in Clause 38: for example `vpi_handle_by_name` (§38.21), `vpi_get_value` (§38.15), `vpi_put_value` (§38.34) and `vpi_register_cb` for value-change callbacks (§38.36).

DPI and VPI differ in where they run. A DPI import runs in the scope of its declaration, like a native subroutine; a VPI routine works in the context of its system-task call site (H.9.1). Inside a DPI import:

- VPI calls need a `context` import, except the output routines `vpi_printf`, `vpi_vprintf` and `vpi_flush`, the `vpi_mcd_*` file routines and `vpi_get_vlog_info`, which do not touch the design (H.9.5).
- An import is not a system task, so `vpi_handle(vpiSysTfCall, NULL)` is an error and system-task callbacks are not available (H.9.5).
- A `vpiHandle` and an `svOpenArrayHandle` are unrelated and cannot be swapped (H.9.5).

Choose DPI for typed calls into models. Choose VPI when C must discover or watch the design: look up any signal by name at run time, react to value changes, or implement a `$` system task.

### Kata P7: a firmware poll with a timeout

**Objective:** write a `context` import task that waits in SystemVerilog, predict when it returns, and prove that it survives a timeout without breaking the disable protocol.

Start from this bench:

```systemverilog
// snippet: kata starter; it compiles once you add the three TODO items
`timescale 1ns/1ps

module tb_top;
  logic clk = 1'b0;
  bit   ready;            // a status bit the firmware model polls
  int   polls;

  always #5 clk = ~clk;   // rising edges at 5, 15, 25, ... ns
  initial #62 ready = 1'b1;  // the status becomes ready between two edges

  // TODO 1: export a task sv_wait_clks(input int n) that waits n rising edges
  // TODO 2: export a function sv_ready() that returns ready
  // TODO 3: import a context task c_poll_ready(input int max_polls, output int polls)

  initial begin
    repeat (3) @(posedge clk);  // t = 25 ns
    c_poll_ready(10, polls);
    $display("t=%0d polls=%0d", $time, polls);
    $finish;
  end
endmodule
```

**Requirements:**
1. Write `c_poll_ready` in C. Each poll waits two clock edges through `sv_wait_clks(2)`, checking its return value, then reads `sv_ready()`. Stop at the first ready poll and write the poll count to `polls`, or write -1 after `max_polls` failed polls.
2. **Predict** the printed line before you run it.
3. **Add a timeout.** Replace the call with the block below, and predict the printed time and whether any error appears:

```systemverilog
// snippet: replaces the c_poll_ready call
fork
  c_poll_ready(10, polls);
  #33;                  // timeout
join_any
disable fork;
$display("t=%0d after timeout", $time);
```

4. **Break it on purpose.** Make the C code ignore the return value of `sv_wait_clks` and keep polling. Predict what the simulator does after the timeout.

If you have no simulator, write your predicted logs first, then compare them with the solution.

<details>
<summary>Worked solution (attempt the kata first)</summary>

The SystemVerilog additions replace the three TODO lines:

```systemverilog
// snippet: inside tb_top
export "DPI-C" task sv_wait_clks;
task automatic sv_wait_clks(input int n);   // automatic: several threads may wait here
  repeat (n) @(posedge clk);
endtask

export "DPI-C" function sv_ready;
function automatic bit sv_ready();
  return ready;
endfunction

import "DPI-C" context task c_poll_ready(input int max_polls, output int polls);
```

```c
/* poll.c */
#include "svdpi.h"

extern int   sv_wait_clks(int n);   /* exported task: 1 if this thread was disabled */
extern svBit sv_ready(void);        /* exported function: a bit result is an svBit */

int c_poll_ready(int max_polls, int* polls) {
  *polls = -1;                      /* outputs start undetermined: always write them */
  for (int i = 1; i <= max_polls; i++) {
    if (sv_wait_clks(2))
      return 1;                     /* disabled: acknowledge, no more exports */
    if (sv_ready()) {
      *polls = i;
      return 0;
    }
  }
  return 0;
}
```

**Prediction 1.** The call starts at 25 ns. Poll 1 waits for the edges at 35 and 45 ns and reads `ready` = 0. Poll 2 waits for 55 and 65 ns and reads `ready` = 1, because it rose at 62 ns. The log shows `t=65 polls=2`.

**Prediction 2.** The timeout branch finishes at 58 ns, first, so `join_any` returns and `disable fork` disables the polling thread while it waits for the edge at 65 ns. `sv_wait_clks` returns 1, C returns 1 at once, and the log shows `t=58 after timeout` with no error. Do not read `polls` after a disable: the call did not complete.

**Prediction 3.** After the disable, the broken C code calls another export. That breaks protocol item (d), and the simulator stops with a fatal error (§35.9). The message text is tool-specific.

**Reflect:** why must `sv_wait_clks` be `automatic`? Because two firmware threads polling different status bits would be inside it at the same time (§35.5.1.5), and a static task would share `n` between them.

### Debug challenge: five broken DPI pairs

For each pair, write down the symptom you expect and the fix before you open the answers.

1. `import "DPI-C" function int c_sum(input int a, input int b);` with C `int c_sum(const int* a, const int* b) { return *a + *b; }`
2. `import "DPI-C" function void c_check(input int v);` whose C body calls the exported function `sv_now()`.
3. `import "DPI-C" function void c_set_name(input string name);` whose C body saves `name` in a static pointer that a later call prints.
4. `import "DPI-C" function bit c_top_all_ones(input logic [39:0] v);` with C `svBit c_top_all_ones(const svLogicVecVal* v) { return v[1].aval == 0xFFu; }`
5. A C++ file defines `int c_model_step(int in)` without `extern "C"`, and the library is loaded with `-sv_lib`.

<details>
<summary>Answers (write your predictions first)</summary>

1. **Wrong values or a crash on the first call.** `int` inputs are small values passed by value (H.8.7), so C dereferences the two integer values as if they were addresses. Fix: `int c_sum(int a, int b)`.
2. **Unpredictable behaviour or a crash, perhaps only in some benches.** An import whose C body calls an export shall be `context` (§35.5.1.3). Fix: `import "DPI-C" context function void c_check(input int v);`.
3. **Garbage or a crash in the later call, and no error at the first one.** The pointer is valid only during the call (H.8.10). Fix: copy the characters into memory C allocates, and free the old copy.
4. **The result changes between runs or tools.** The upper 24 bits of `v[1]` are undetermined (H.7.7), and X or Z bits are ignored. Fix: `return SV_GET_UNSIGNED_BITS(v[1].aval, 8) == 0xFFu && SV_GET_UNSIGNED_BITS(v[1].bval, 8) == 0u;`.
5. **The library loads, but the symbol `c_model_step` is undefined.** C++ mangled the name (§35.5.1.6). Fix: `extern "C" int c_model_step(int in)`.

</details>
