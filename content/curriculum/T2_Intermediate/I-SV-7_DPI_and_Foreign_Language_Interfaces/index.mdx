## Quick Take
- **What it is:** The Direct Programming Interface (DPI) is a standardized boundary (IEEE 1800-2023 Clause 35 and Annex H) that lets SystemVerilog call C functions and C code call back into SystemVerilog — without the complexity of the older VPI/PLI interfaces.
- **Why it matters:** Real verification environments need to model firmware, run reference algorithms, talk to external tools, or reuse legacy C checkers. DPI provides a clean, typed, zero-PLI-overhead way to do this.
- **The Analogy:** Think of DPI as a customs checkpoint at a national border. Both countries (SV and C) operate freely inside their own territory, but any goods (data) crossing the border must go through customs (type marshaling) and follow the treaty rules (calling conventions).

> **Signal:** If you find yourself writing a complex algorithm in SystemVerilog that already exists in C, or if your testbench must coordinate with a software model, DPI is the right tool.

## Build Your Mental Model

### DPI Import: Calling C from SystemVerilog

The most common DPI use case is importing a C function so SystemVerilog can call it.

```systemverilog
// Declaration in SV: tells the compiler about the C function
import "DPI-C" function int c_crc32(input int unsigned data[], input int len);

module crc_demo;
  int unsigned payload[] = '{32'h0000_0001, 32'hDEAD_BEEF};
  initial $display("golden CRC = %h", c_crc32(payload, payload.size()));
endmodule
```

The corresponding C implementation:

```c
// crc32.c: compiled separately, linked as a shared library
#include <stdint.h>
#include "svdpi.h"

/* Reflected CRC-32 over every bit of every 32-bit word, LSB first. */
int c_crc32(const svOpenArrayHandle data, int len) {
    uint32_t crc = 0xFFFFFFFFu;
    for (int i = svLow(data, 1); i <= svHigh(data, 1); i++) {        /* SV indices */
        uint32_t word = *(const uint32_t*)svGetArrElemPtr1(data, i); /* int elements are C-compatible */
        for (int b = 0; b < 32; b++) {
            uint32_t bit = (word >> b) & 1u;
            crc = (crc >> 1) ^ (0xEDB88320u & (0u - ((crc ^ bit) & 1u)));
        }
    }
    (void)len;   /* svSize(data, 1) returns the same element count */
    return (int)~crc;
}
```

An open (unsized) array always arrives as a `const svOpenArrayHandle`. Read it with the svdpi.h query functions (`svLow`, `svHigh`, `svSize`) and accessors such as `svGetArrElemPtr1` (Annex H.12). There is no `svGetIntElement`.

### DPI Export: Calling SystemVerilog from C

You can also export SV functions so C can call back into the simulation:

```systemverilog
// Export declaration: makes this SV function visible to C
export "DPI-C" function sv_get_sim_time;

function longint sv_get_sim_time();
  return $time;
endfunction

// The import whose C body calls the export MUST be context (§35.5.1.3)
import "DPI-C" context function void my_c_checker(input int value);
```

```c
#include <stdio.h>
#include "svdpi.h"
extern long long sv_get_sim_time(void);   /* exported from SV */

void my_c_checker(int value) {
    long long t = sv_get_sim_time();
    printf("[%lld] Checking value: %d\n", t, value);
}
```

> **Caution:** An import that calls exported subroutines (or VPI) shall be declared `context`; without it the call has no proper SystemVerilog scope and the behaviour is unpredictable, often a crash (§35.5.1.3). Exported *tasks* are stricter: only a `context` imported *task* may call them, never an imported function (§35.8). Write C++ implementations with `extern "C"` linkage.

### Function Qualifiers: `pure`, `context`, and Standard

Predict the C type for a few SystemVerilog types first, then judge each import/export pair: legal, a compile error, or legal-looking code that is illegal or undefined at run time. The explorer is a deterministic model of Clause 35 and Annex H.

<DPIBoundaryInspector />

The qualifier you choose has major performance and capability implications:

| Qualifier | May touch SV data or call exports? | May call exported tasks? | Optimization | Use when… |
|---|---|---|---|---|
| `pure` (functions only) | ❌ No | ❌ No | Calls may be removed or reused | Non-void, no output/inout args, result depends only on inputs, no side effects (§35.5.2) |
| `context` | ✅ Yes | Only if the import is a **task** (§35.8) | Each call is an optimization barrier | C calls exported subroutines or VPI (§35.5.3) |
| *(none)* | ❌ Only its own arguments | ❌ No | Normal | C does self-contained work; side effects such as file I/O are allowed (§35.5.1.3) |

```systemverilog
// Pure: safe to inline, result depends only on inputs
import "DPI-C" pure function int c_parity(input int data);

// Context: needs to read SV signals via VPI or call SV functions
import "DPI-C" context function void c_monitor_check();

// Standard (default): no qualifier needed
import "DPI-C" function int c_add(input int a, input int b);
```

> **Performance tip:** Mark a function `pure` only when it truly has no side effects. The compiler may eliminate or reuse calls, so a `pure` function that prints, writes a file, or counts calls can silently lose those effects (§35.5.2).

## Type Marshaling: Crossing the Border

The core DPI challenge is mapping SystemVerilog's 4-state types to C's 2-state types.

| SystemVerilog type | C type (input) | C type (output / inout) | Notes |
|---|---|---|---|
| `byte` | `char` | `char*` | 8-bit, 2-state |
| `shortint` | `short int` | `short int*` | 16-bit |
| `int` | `int` | `int*` | 32-bit, 2-state |
| `longint` | `long long` | `long long*` | 64-bit |
| `real` / `shortreal` | `double` / `float` | `double*` / `float*` | IEEE 754 |
| `chandle` | `void*` | `void**` | Opaque C pointer that SV stores and passes back |
| `string` | `const char*` | `const char**` | Do not free or keep it; copy if needed (H.8.10) |
| `bit` (scalar) | `svBit` | `svBit*` | unsigned char: 0 or 1 |
| `logic` (scalar) | `svLogic` | `svLogic*` | `sv_0`, `sv_1`, `sv_z` = 2, `sv_x` = 3 |
| `bit [N:0]` | `const svBitVecVal*` | `svBitVecVal*` | Packed 2-state vector, 32-bit chunks |
| `logic [N:0]` | `const svLogicVecVal*` | `svLogicVecVal*` | Packed 4-state vector (aval/bval pairs) |
| `int arr[]` (open array) | `const svOpenArrayHandle` | `const svOpenArrayHandle` | Always a handle; use `svLow`/`svHigh`/`svGetArrElemPtr1` |

Small inputs (the basic types, scalar `bit`/`logic`, `chandle`, `string`) are passed by value; every other input arrives by `const` reference, and every output or inout arrives by pointer (H.8.7, H.8.8). Only small types can be function results: `function logic [31:0] f()` is not a legal DPI import; return wide values through an `output` argument (§35.5.5).

### The 4-State Problem

`logic` values can be `0`, `1`, `X`, or `Z`. C has no concept of `X`/`Z`. The DPI represents `logic` vectors using `svLogicVecVal` — a struct with two members:

```c
typedef struct {
    uint32_t aval;  // value bits
    uint32_t bval;  // X/Z indicator bits
} svLogicVecVal;
// bval=0, aval=0 → logic 0
// bval=0, aval=1 → logic 1
// bval=1, aval=1 → logic X
// bval=1, aval=0 → logic Z
```

> **Pitfall:** If you pass a `logic` signal that contains `X` to a C function expecting a simple `int`, the `X` information is silently lost. Always use `bit` types on the SV side when the C function cannot handle `X`/`Z`.

## Memory Ownership & Lifetime

**Rule:** The caller owns the memory.

- When SV calls C: SV allocates the argument data. The C function must **not** free it or store pointers to it beyond the function return.
- When C calls exported SV: C owns the arguments. The SV function must not store references to C-allocated strings or arrays.
- **Dynamic allocation in C:** If C `malloc`s memory and returns a pointer, that memory will leak unless you provide an explicit `c_free()` import for SV to call later.

```c
// BAD: storing a pointer to SV-owned data
static const char* cached_name = NULL;
void c_set_name(const char* name) {
    cached_name = name;  // DANGER: SV may reclaim this memory!
}

// GOOD: copy the data if you need it beyond the call
void c_set_name(const char* name) {
    cached_name = strdup(name);  // owned by C, must be freed later
}
```

## Blocking Behavior: Functions vs Tasks

- **`import "DPI-C" function`** executes in **zero simulation time**, like any SystemVerilog function (§35.5.1.1). The simulator waits until the C code returns.
- **`import "DPI-C" task`** can consume simulation time, but only in one way: its C code calls an **exported SystemVerilog task** that executes a delay, event control or `wait` (§35.5.1.5). To call that export, the import must be declared `context` (§35.8). Without such a call, an imported task also takes zero simulation time.
- C code that **blocks on I/O or computes for a long time freezes the whole simulator**, whether it is imported as a function or a task. `$time` does not move and no other SystemVerilog process runs until the C code returns.

```systemverilog
// Zero-time function: fast computation only
import "DPI-C" function int c_compute_hash(input int data);

// Time passes only inside the exported SV task that C calls
export "DPI-C" task sv_wait_cycles;
task sv_wait_cycles(int n); repeat (n) @(posedge clk); endtask
import "DPI-C" context task c_wait_for_firmware_ack(output int status);
```

```c
extern int sv_wait_cycles(int n);          /* exported SV task */
int c_wait_for_firmware_ack(int* status) {
    while (!fw_ack_ready()) {              /* non-blocking poll of the firmware model */
        sv_wait_cycles(10);                /* let simulation time advance in SV */
    }
    *status = fw_ack_value();
    return 0;                              /* 0 = not disabled (§35.9) */
}
```

> **Warning:** A C call that takes 500 ms of wall-clock time holds the simulator for those 500 ms, task or not. If C must wait for something, poll without blocking and let time pass by calling an exported task that waits, as above.

## Build & Link Workflow

DPI requires compiling C code into a shared library and telling the simulator where to find it.

```bash
# 1. Compile the C code into a shared library
# -I takes the directory that contains svdpi.h (your simulator's include dir)
gcc -shared -fPIC -o libmydpi.so crc32.c -I${VCS_HOME}/include

# 2. Run simulation with the library
# VCS
vcs -sverilog -LDFLAGS "-L. -lmydpi" top.sv
# Questa
vlog top.sv && vsim -sv_lib libmydpi top

# 3. Or use the built-in DPI compilation flow
# VCS auto-compile
vcs -sverilog top.sv crc32.c
```

> **Pitfall:** Forgetting `-sv_lib` or `-LDFLAGS` at link time is the #1 DPI build failure. The error message is typically `"undefined symbol: c_crc32"` — which looks like a C linker error, not a SystemVerilog issue.

## Common Failure Modes & Debug

| Symptom | Likely Cause | Fix |
|---|---|---|
| `undefined symbol` at runtime | Missing `-sv_lib` or library not on `LD_LIBRARY_PATH` | Add correct linker flags |
| Segmentation fault | C prototype does not match the import (e.g., `int` where SV passes `const svLogicVecVal*`), open-array misuse, or an export called from a non-`context` import | Check the C prototype against the type table; declare imports that call exports `context` |
| Simulation hang | C code blocks or loops (function and task alike) | Make the C side non-blocking; let time pass in an exported SV task called from a `context` import task |
| Corrupted return values | Incorrect `svLogicVecVal` packing | Verify `aval`/`bval` encoding |
| Memory leak | C allocates, SV never frees | Add explicit `c_free()` import |
| Stack overflow | Deep C recursion from context function | Increase simulator stack or restructure |

## Make It Work

1. **Start with a plain import.** Add `pure` only for side-effect-free functions, and `context` only when the C code calls back into SystemVerilog.
2. **Match types exactly** — consult the type table above and always check the `svdpi.h` header.
3. **Test the C code independently** — write a standalone `main()` that exercises your C function before integrating with the simulator.
4. **Version your shared libraries** — include a `c_get_version()` function so the SV side can assert the expected library version at `$time 0`.

**Checklist before moving on:**
- [ ] You understand the difference between `import` and `export`.
- [ ] You can choose between `pure`, `context`, and standard qualifiers.
- [ ] You know that simulation time can pass during a DPI call only inside an exported SV task called from a `context` import task.
- [ ] You know that `logic` marshals as `svLogicVecVal` (4-state) and `bit` as `svBitVecVal` (2-state).

## Push Further: VPI and PLI

DPI is the modern interface, but two older APIs still exist:

- **VPI (Verilog Procedural Interface, IEEE 1364-2005 §27):** A callback-driven API that lets C code traverse the simulation hierarchy, register value-change callbacks, and read/write signals by name. Much more powerful than DPI but significantly more complex and slower.
- **PLI (Programming Language Interface):** The original Verilog-95 foreign interface. Fully deprecated in favor of VPI. Avoid in new code.

**When to use VPI over DPI:**
- You need to **discover signals by name** at runtime (e.g., a generic coverage monitor).
- You need **value-change callbacks** — DPI has no equivalent.
- You need to **traverse the design hierarchy** programmatically.

Most modern workflows use DPI for performance-critical paths and VPI only for tool/infrastructure code.
