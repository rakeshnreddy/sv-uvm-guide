## Quick Take
- **What it is:** The UVM factory is a centralized registry where types are recorded so tests can substitute concrete implementations (overrides) at runtime.
- **Why it matters:** Overrides enable A/B testing, negative fault injection, and mock instrumentation without editing the environment that instantiates the components.
- **The Analogy:** Think of the factory as a casting director—register every actor, then swap who plays the role on the day of the shoot without rewriting the script.

> **Retention Hook:** “Register, override, then create.” Every class registers; the test registers its overrides; only `create()` calls made after that see them.

## Build Your Mental Model
### Registration & Creation Rules (IEEE 1800.2-2020 Clause 8)
Every class you want to override, and every class you override it with, must register with the factory. Every object you want the factory to be able to swap must be constructed through `type_id::create()`.

<InteractiveCode>
```systemverilog
class base_driver extends uvm_driver#(seq_item);
  `uvm_component_utils(base_driver) // 1. Register
  function new(string name, uvm_component parent);
    super.new(name, parent);
  endfunction
endclass

class mock_driver extends base_driver;
  `uvm_component_utils(mock_driver) // 1. Register the alternative
  function new(string name, uvm_component parent);
    super.new(name, parent);
  endfunction
endclass

class my_env extends uvm_env;
  `uvm_component_utils(my_env)
  base_driver drv;
  function new(string name, uvm_component parent);
    super.new(name, parent);
  endfunction

  function void build_phase(uvm_phase phase);
    super.build_phase(phase);
    // 2. Create using factory, not `new()`
    drv = base_driver::type_id::create("drv", this); 
  endfunction
endclass
```
</InteractiveCode>

Two ways to lose the factory:
- **Calling `new()` directly.** The factory is never asked, so no override can apply to that object.
- **Skipping the registration macro** (`uvm_component_utils` / `uvm_object_utils`). The class has no proxy of its own. `get_type()` is a static member, so it resolves to the nearest registered parent's proxy, and an override *to* that class quietly becomes "parent → parent". A class with no registered ancestor has no `get_type()` at all and does not compile.

### Type vs. Instance Overrides
- **Type overrides** replace *every* creation of a specified class with another class, unless an instance override applies.
- **Instance overrides** target creations whose full path matches a pattern. The path the factory compares is `{parent's full name}.{name}` from the `create()` call.
- With `this` as the third argument, `set_inst_override` prefixes your string with the caller's full name: `"env.drv"` from the test becomes `uvm_test_top.env.drv`. Without it, the string is used as an absolute path.
- In the path, `*` matches any run of characters (dots included) and `?` matches one character. A path with neither must match exactly.

<InteractiveCode>
```systemverilog
class my_test extends uvm_test;
  `uvm_component_utils(my_test)
  my_env env;
  function new(string name, uvm_component parent);
    super.new(name, parent);
  endfunction

  function void build_phase(uvm_phase phase);
    super.build_phase(phase);

    // 3. Global swap: every base_driver becomes a mock_driver
    base_driver::type_id::set_type_override(mock_driver::get_type());

    // OR Instance swap: only uvm_test_top.env.drv is swapped
    // base_driver::type_id::set_inst_override(mock_driver::get_type(), "env.drv", this);

    // Register overrides before the components they affect are created.
    env = my_env::type_id::create("env", this);
  endfunction
endclass
```
</InteractiveCode>

## Make It Work
1. **Centralize overrides:** Collect factory policy in base tests or configuration modules.
2. **Prefer handles over strings:** Use `<type>::get_type()` (e.g. `mock_driver::get_type()`) for compile-time safety instead of `set_type_override_by_name`.
3. **Instrument debugging:** Call `uvm_factory::get().print()` and `uvm_root::get().print_topology()` in `end_of_elaboration_phase`. The first lists every registered override; the second shows the class each component actually became.
4. **Register before you create:** `create()` asks the factory at the moment it runs. An override registered later changes only later `create()` calls.

## Advanced Factory Dynamics
### Override Precedence
The rules below are those of `uvm_default_factory::find_override_by_type` (IEEE 1800.2-2020 §8.3.1.7.1). They were checked against the uvm-core 2020.3.1 source.
1. **Instance overrides are checked before type overrides.** This holds even when the type override was registered first.
2. **Among instance overrides, the first registered match wins.** Neither the most specific path nor the component that registered it matters. Register specific overrides before general ones.
3. **There is one type override per original type.** A new `set_type_override` replaces it (`replace` defaults to 1). With `replace = 0`, the existing override stays and the new call is ignored.
4. **Overrides chain.** If `base_driver → mock_driver` and `mock_driver → err_driver` are both registered, a request for `base_driver` builds `err_driver`. The factory repeats the lookup, instance overrides first, for each new type.
5. **Timing matters.** Overrides affect only `create()` calls made after they are registered. Build runs top-down, so an override set in the test's `build_phase` after `env` is created still reaches the drivers, but not `env` itself.
6. **`type_id::create` checks the result.** It `$cast`s the object to the requested class. An override class that does not extend the original gives `UVM_FATAL [FCTTYP]`.

### uvm_root and uvm_report_server Interplay
Advanced environments often override the core UVM reporting mechanism. Because `uvm_report_server` is a global object, you can't use standard component overrides. Instead, you register your custom server globally with `uvm_report_server::set_server(...)` to control testbench-wide logging formats. `uvm_root` (`uvm_top`) implicitly oversees this global state and hierarchy.

## Interview Pitfalls
**The `new()` Keyword Trap:**
Interviewers will often ask you to debug a testbench where an override isn't taking effect. Always look for the `new()` keyword. If a component is instantiated via `new("name", this);`, the factory is completely bypassed!

**The Base Class Fallback:**
You override `base_driver` with `mock_driver`, but `mock_driver` is missing `uvm_component_utils`. What happens?
- There is no fatal error. `mock_driver::get_type()` is inherited, so it returns `base_driver`'s proxy. The call becomes `base_driver → base_driver`.
- The factory prints a `TYPDUP` warning ("Original and override type arguments are identical") and keeps building `base_driver`.
- If the class has no registered ancestor at all, `get_type()` does not exist and the code does not compile.
- With `set_type_override_by_name` and a misspelled or unregistered override name, `create()` reports `UVM_ERROR [TYPNTF]` ("Cannot resolve override ... not registered with the factory") and gets no class back from the factory.
