## Quick Take

- **What it is:** **AI-driven verification** applies **machine learning (ML)**, programs that learn patterns from data instead of following hand-written rules, and **large language models (LLMs)**, ML models trained on text and code that generate text from a prompt, to verification work. ML is used to steer stimulus toward coverage holes, pick which tests to run, and group regression failures by cause. LLMs are used to draft assertions (**SVA**, SystemVerilog Assertions), UVM sequences and coverage code from a written specification.
- **Why it matters:** Constrained-random coverage closes quickly at first and then crawls, and every extra simulation costs compute. ML can cut that tail for some holes and not at all for others. LLM drafts are fast, but an assertion that compiles can still check the wrong thing, or nothing at all. The main risk is **false confidence**: a green result that proves nothing.
- **The Analogy:** A fast, confident intern. The intern produces useful drafts quickly; you review every line, and the intern never signs the tape-out form. *Where it breaks:* a human intern learns from your review and says "I don't know" when unsure. An LLM rarely flags its own uncertainty, usually does not learn from your correction in the next session, and may give a different answer to the same prompt tomorrow.

**You will be able to:**
1. Explain why constrained-random coverage curves flatten (uniform solving, the coupon-collector tail, rare and unreachable bins), and which holes coverage-directed generation, reinforcement learning, evolutionary search and learned test selection can and cannot close.
2. Evaluate a vendor or research claim: what is measured, to which coverage target, against which baseline and compute, on which designs, and how reproducibly; flag unsupported ROI (return on investment) figures.
3. Debug LLM-generated SVA and UVM sequences for semantic errors (sampling and history, vacuity, cycle off-by-one, wrong implication, over-specification, invented APIs) using the I-SV-4A/4B rules, and add the covers that prove a check ran.
4. Decide where AI fits in a verification flow, which checks and human sign-offs stay mandatory, and which data, privacy and reproducibility controls the flow needs.

## Build Your Mental Model

**How to read this lesson.** The core path is the first four sections: why coverage flattens, what ML can and cannot do for closure, what is established and what is emerging, and LLMs as drafting tools. Practitioner depth follows: reviewing AI-generated SVA and sequences, evaluating claims, and where AI fits in a flow, with a debugging table. Make It Work reviews and repairs one LLM-drafted checker on a small FIFO. Push Further holds the expert layer.

A few terms from the prerequisites, restated in one line each:
- A **coverage bin** is one value or range you want to see at least once; a **cross** counts combinations of bins ([I-SV-3A](/curriculum/T2_Intermediate/I-SV-3A_Functional_Coverage_Fundamentals/index)). **Coverage closure** is the work of getting every bin that matters hit, or justifiably excluded ([I-SV-3B](/curriculum/T2_Intermediate/I-SV-3B_Advanced_Functional_Coverage/closure-workflow)).
- **Constrained-random** stimulus is random values that obey your constraints. A **seed** is the number that fixes the random choices of one run, so the same seed and the same code reproduce the same run ([I-SV-2B](/curriculum/T2_Intermediate/I-SV-2B_Advanced_Constrained_Randomization/randomization-methods)).
- A **regression** is the large set of tests and seeds you run repeatedly, typically every night, to catch new failures, on the **design under test (DUT)** and its testbench. **Continuous integration (CI)** is the automated system that reruns builds and checks on every change.
- The **verification plan (vplan)** lists the features to verify and how each is checked and covered; it is the basis of sign-off. A **formal** tool proves a property for all input sequences instead of simulating some of them ([E-INT-1](/curriculum/T4_Expert/E-INT-1_Integrating_UVM_with_Formal_Verification/index)).
- In SVA, the **antecedent** is the left side of an implication (`|->` or `|=>`) and the **consequent** is the right side. An attempt whose antecedent does not match succeeds **vacuously**: it passes without checking anything ([I-SV-4A](/curriculum/T2_Intermediate/I-SV-4A_SVA_Fundamentals/index), IEEE 1800-2023 §16.14.8).

### Why constrained-random coverage flattens

**The mechanism.** The constraint solver is not lazy or biased. IEEE 1800-2023 §18.5.9 requires it to give "a uniform value distribution over legal value combinations", and an unconstrained `rand` variable is uniform over its range (§18.4.1). Coverage still slows down, for four reasons:

1. **The coupon-collector tail.** Random samples repeat bins. When most bins are covered, almost every new sample lands in a bin you already have. With *n* equally likely bins, the average number of samples to hit all of them is *n* × H(*n*), where H(*n*) = 1 + 1/2 + … + 1/*n* is the *n*-th harmonic number. For 100 bins that is about 519 samples, and the last 10 bins cost more than the first 90 (calculated in Make It Work).
2. **Rare bins.** Uniform values do not mean uniform bins. A bin that a sample hits with probability *p* takes about 1/*p* samples on average. If one cross cell is hit once in 200 samples, it alone costs about 200 samples; once in 20,000, about 20,000.
3. **Deep states.** Some bins need a sequence of several transactions in a specific order (fill a FIFO, then a read and a write in the same cycle). Their probability is roughly the product of each step's probability, so it falls fast.
4. **Unreachable bins.** A bin with probability 0 under your constraints is never hit, by any number of seeds. Either the constraint is wrong or the bin should be excluded; only the specification can say which.

Published work on test selection says random tests "tend to repeatedly exercise the same design logic" (Masamba, Eder and Blackmore, 2022). That observation is right. The cause is the four points above, not a defect in the solver.

**Debrief.** The coupon-collector estimate assumes equally likely bins, and this stimulus breaks that assumption. The rarest bin sets the pace: the curve climbs fast, then flattens while the run waits for one rare cell. Switch the stimulus to **constrained (hole)** and predict again: one cell now has probability 0, and the run never closes. Those two shapes, *rare* and *unreachable*, are the whole story of the long tail, and they behave very differently under ML.

**Pitfalls.**
- "The solver keeps generating the same values." It is uniform over legal combinations (§18.5.9); look at bin probabilities, not at the solver.
- "Run more seeds" for a bin at 0%. First check whether the bin can be generated at all (I-SV-3B's [closure workflow](/curriculum/T2_Intermediate/I-SV-3B_Advanced_Functional_Coverage/closure-workflow) shows how).

### What ML can and cannot do for closure

Every ML closure technique sits in the same loop: run tests, read the coverage database, learn something, change what you run next. They differ in what they learn and what they are allowed to change.

The four families, in plain words:

- **Coverage-directed test generation (CDG)** closes a feedback loop from coverage back to the generator's knobs. A **knob** is any setting that shapes stimulus: a `dist` weight, a constraint mode, a sequence choice. Fine and Ziv (IBM, DAC 2003) learned the relation between knobs and coverage with Bayesian networks (probabilistic models of how variables depend on each other); Ioannides and Eder (ACM TODAES 2012) review the ML methods used for CDG since then.
- **Reinforcement learning (RL)** learns a **policy**, a rule for choosing the next action (here, the next knob setting or sequence), by trial and error, guided by a **reward** (here, new bins hit). It must balance **exploration**, trying settings it knows little about, against **exploitation**, reusing settings that paid off. RL for stimulus is a research approach, not a standard product feature.
- **Evolutionary (genetic) search** keeps a population of knob settings, scores each by the new coverage it produced (its **fitness**), keeps the best, and combines and mutates them into the next population. Ioannides and Eder's review covers genetic-algorithm CDG.
- **Learned test selection** is **supervised learning**: a **classifier**, a model trained on labelled examples, predicts whether a candidate test will hit uncovered bins. You generate many candidate tests cheaply, describe each by **features** of its stimulus (operation mix, address ranges, burst lengths), simulate only those the classifier ranks highest, and retrain on the results (Masamba, Eder and Blackmore, IEEE AITest 2022). The features describe the stimulus. A seed number is not a feature: it has no learnable relation to coverage. What you *can* do with known seeds is re-rank them from their recorded history, because random stability (I-SV-2B) makes a known seed reproduce the same run.

**What all four can do:** shift probability toward bins that are *rare but reachable*, and avoid re-running tests that add nothing. **What none of them can do:** hit a bin with probability 0, notice that a bin is missing from the coverage model, or decide whether an empty bin is legal. That is the second misconception this lesson targets: *ML closure does not replace the coverage model*. The model only optimizes against the coverage model you give it, and 100% of a wrong model is still wrong.

**Predict, then try.** A regression is stuck because a constraint makes one cross cell impossible. Read the spec the challenge shows you, and decide which fix is right *before* you choose one. Then switch the spec and decide again.

<CoverageCrossExplorerVisualizer mode="closure" />

**Debrief.** "Run 10× more samples" never works: the cell has probability 0, and no optimizer, however clever, samples it. When the spec forbids the combination, `illegal_bins` is right; when the spec allows it, the constraint is the bug. Both answers come from the specification, which is why the coverage model, the constraints and waivers stay with engineers.

**Pitfalls.**
- Letting a tool's suggestion add `ignore_bins` without a spec reference. Coverage closes and a real hole disappears.
- Training test selection on coverage only. A selector that maximizes coverage can drop the very tests that find bugs; keep a random **control slice** (a fixed share of unselected random tests) in every regression.

### LLMs as drafting tools

An LLM generates the most likely continuation of its **prompt**, the text you give it. It has no simulator inside it: it has not run your design, and it has not checked its output against IEEE 1800-2023. A **hallucination** is fluent output that is false: a method that does not exist, a plusarg nothing reads, a clause number that is wrong.

LLMs draft some things well: boilerplate (class skeletons, `uvm_component_utils` registration, port declarations), first-cut assertions for simple single-cycle rules, coverpoint lists from a register table. They fail in predictable ways, and the review sections below are organized around this failure catalogue:

1. **Compiles but wrong:** the property checks something other than the spec (the count instead of the data).
2. **Vacuity:** the antecedent never matches, so every attempt passes vacuously (§16.14.8).
3. **Cycle off-by-one:** `|->` where `|=>` was meant, or `##2` where the spec meant "within two cycles".
4. **Sampling and history:** `$past` across reset, current values printed in an action block (§16.9.3).
5. **Wrong implication:** a bare sequence used as a property, so idle cycles fail.
6. **Over-specification:** the property forbids legal behaviour the spec allows (a read in the same cycle).
7. **Width and type traps:** a counter too narrow to hold the value the property compares against.
8. **Invented APIs:** methods, macros, plusargs or system functions that do not exist in IEEE 1800-2023 or uvm-core 2020.3.1.

Items 1 to 7 compile cleanly. That is the first misconception this lesson targets: *an AI-generated assertion is not correct because it compiles*. Only item 8 is caught by the compiler, and only if the invented name is not an existing name used wrongly.

**A worked review.** A designer asked an LLM for SVA from this spec: "When the FIFO is full, a write must not cause data corruption. The FIFO count should not exceed MAX_DEPTH." It returned:

```systemverilog
// snippet: LLM draft, shown for review (do not copy)
property p_fifo_count_bounded;
  @(posedge clk) disable iff (!rst_n)
  (fifo_count <= MAX_DEPTH);
endproperty

assert property (p_fifo_count_bounded)
  else $error("FIFO count exceeded MAX_DEPTH: %0d", fifo_count);

property p_full_write_no_corrupt;
  @(posedge clk) disable iff (!rst_n)
  (fifo_full && write_en) |-> ##1 (fifo_count == $past(fifo_count));
endproperty

assert property (p_full_write_no_corrupt)
  else $error("Write to full FIFO corrupted count");
```

It compiles. Review it against the spec:

1. **Wrong target.** The spec talks about *data* corruption; the second property looks only at the count. A full-FIFO write that overwrites a stored entry, without changing the count, passes.
2. **Over-specification.** On a FIFO that serves a read while it is full, the same cycle's read legally drops the count from 4 to 3. The property fails on a correct design. The waveform below shows it.
3. **Sampling in the action block.** The first message prints `fifo_count`, the current value when the action block runs in the **Reactive region** (the part of the time step that runs after the design's updates for that edge, §16.14.1), not the sampled value the assertion used (§16.9.3's `a1_bad` example, §16.14.1). Print `$sampled(fifo_count)`.
4. **No cover.** Nothing shows that "full and write" ever happened in the test. If it never did, the second assertion is green and has checked nothing (§16.14.8). Add `cover property` on the antecedent.
5. **Width trap.** If `fifo_count` is declared with `$clog2(MAX_DEPTH)` bits, it cannot represent `MAX_DEPTH`, and `fifo_count <= MAX_DEPTH` can never fail.
6. Here `|-> ##1 (...)` checks the same edge as `|=> (...)`: §16.12.7 defines `|=>` as a one-tick delay after the antecedent's match. That is style, not a bug; use `|=>` for readability.

### Reviewing AI-generated SVA

Review an AI-drafted assertion exactly as you would review a colleague's, with a fixed checklist. Each item names the rule it rests on:

1. **Restate the intent** in one sentence from the spec, then read the property aloud and compare. If they differ, stop.
2. **Timing.** Overlapping `|->` checks the consequent on the antecedent's last edge; non-overlapping `|=>` checks it one edge later (§16.12.7). `##2` is exact; `##[1:2]` is a window.
3. **Property shape.** A bare sequence used as a property must match from *every* attempt, so idle cycles fail (§16.12.2); conditional rules need an implication.
4. **Sampling and history.** Assertions use sampled values (§16.5.1). `$past` looks back one clock tick regardless of reset; guard the first cycle after reset with `!$past(rst)` in the antecedent. Print `$sampled(...)` in action blocks (§16.9.3).
5. **Disable condition.** `disable iff` uses current, not sampled, values (§16.9.3 notes that "the disable condition by default is not sampled"), and its polarity must match the reset's.
6. **Reachability.** Add `cover property` on the antecedent and confirm it is hit; zero failures with zero covers proves nothing (§16.14.3, §16.14.8).
7. **Widths and types.** Can each signal represent every value the property compares against?
8. **Against the spec, not the RTL.** Does the property forbid something the spec allows (over-specification) or allow something it forbids? Is it checking control when the spec is about data?

Finish with a **mutation test**: deliberately break the design (or the trace) in the way the assertion should catch, and confirm it fires. An assertion that never fires on any mutant has not been shown to check anything.

### Reviewing AI-generated UVM sequences

Sequences fail review in different ways from assertions: the code runs, stimulus flows, and the defect shows up as a hang, a crash, a silent skip or a wrong check. Review an LLM-drafted sequence against the code standards you already apply:

- **Randomization is checked.** ``if (!req.randomize() with {...}) `uvm_fatal(...)``, never `assert(req.randomize())`. Assertion control can switch assertion evaluation off (`$assertoff`, or a simulator switch). IEEE 1800-2023 §20.11 says that while assertions are off "No new attempts will be started", so the immediate assertion is not evaluated and the `randomize()` call inside it never runs.
- **The handshake is complete:** `start_item(req)`, then randomize or set fields, then `finish_item(req)` ([I-UVM-3A](/curriculum/T2_Intermediate/I-UVM-3A_Fundamentals/index)). `finish_item` returns only after the driver calls `item_done()`.
- **No `#delay` for synchronization.** Wait for the event you need (the return of `finish_item`, or `get_response`), not for a guessed time.
- **Objections belong in the test or a top-level sequence.** `starting_phase` is a compatibility variable in uvm-core 2020.3.1 (marked "@uvm-compat" in `uvm_sequence_base.svh`) and stays null unless something sets it, such as the default-sequence mechanism; a test that calls `seq.start(sqr)` does not; IEEE 1800.2-2020 provides `get_starting_phase()` and `set_automatic_phase_objection()` (§14.2.4).
- **Every API exists.** Check each method against the uvm-core 2020.3.1 source or the IEEE 1800.2-2020 class reference. Methods that sound right, such as a `compare_and_report` on a sequence item, are a classic hallucination.
- **Ambiguities are resolved, not guessed.** "Consecutive addresses" on a byte-addressed 32-bit bus usually means a step of 4, not 1. Ask, then record the answer in the spec.

### Evaluating vendor and research claims

A speed-up claim is a ratio, and a ratio is meaningless without its denominator. Before you budget for a tool or quote a paper, fill in this **claim scorecard**:

| Question | Why it matters |
|---|---|
| What metric? (coverage, compute hours, wall-clock, engineer time, bugs found) | "Productivity" can mean any of them |

**Data, privacy and reproducibility controls.** These are practice guidance, not a standard; your company's policy decides the details.
- **What leaves the building.** RTL, specifications, logs and waveforms are confidential and may be export-controlled. Use only deployments your company has approved (an enterprise contract or an on-premises model), and know their retention terms. Never paste unreleased RTL into a public chatbot.
- **Reproducibility.** LLM output can differ between two identical requests, even at **temperature** 0 (the setting meant to make output deterministic), because inference servers batch requests and some computations are not batch-invariant (H. He, Thinking Machines Lab, "Defeating Nondeterminism in LLM Inference", September 2025). So commit the *reviewed artifact* as source, record its provenance, and never regenerate collateral inside CI.
- **For learned generators,** log the seed, the policy or model version and the knob settings of every run, or you cannot reproduce a failure the model found.

### Practitioner depth: debugging an AI-assisted flow

| Symptom | Likely cause | Fix |
|---|---|---|
| A bug escapes that a full regression would have caught | Test selection learned "covers new bins", not "finds bugs" | Keep a random control slice in every run and a periodic full regression |
| Hundreds of AI assertions, zero failures, ever | Vacuous attempts, or checks that cannot fail | Read the vacuous and cover counts; cover each antecedent; mutation-test |
| Coverage reached 100% overnight | Bins were excluded or the model was edited | Diff the coverage model; every exclusion needs a spec reference and a human approver |
| The same prompt gives different assertions this week | LLM nondeterminism, or a model update | Commit the reviewed artifact; record model id and prompt; do not regenerate |
| Compile error: unknown method or macro in LLM code | Invented API | Check the name against uvm-core 2020.3.1 or IEEE 1800-2023; write it by hand |
| A failure from the ML generator cannot be reproduced | Seed or policy version not logged | Log both for every run; rerun with the same versions |
| An LLM root-cause explanation sounds right but the fix does not hold | A plausible hypothesis was treated as a confirmed cause | Confirm with a directed test before fixing ([E-DBG-1](/curriculum/T4_Expert/E-DBG-1_Advanced_UVM_Debug_Methodologies/effective-debug)) |

### Recap

- Coverage flattens because of the coupon-collector tail, rare bins and unreachable bins, not because the solver repeats itself (§18.5.9).
- ML can shift effort toward rare, reachable bins and drop redundant tests. It cannot reach a probability-0 bin or fix a wrong coverage model.
- CDG, signature triage and failure clustering have a long published record; LLM drafting is emerging. Label vendor features as vendor claims, with a date.
- An assertion that compiles can be wrong, over-specified or vacuous. Review against the spec with a checklist, cover the antecedent, mutation-test.
- A speed-up without a target, baseline and design set is a hypothesis, not a fact.
- AI drafts, ranks, clusters and suggests; humans own the plan, the checks, waivers and sign-off, inside an approved data boundary, with provenance recorded.

## Make It Work

### Worked example: review and repair an LLM-drafted FIFO checker

The bench below has three parts: a 4-entry FIFO (`fifo4`) that drops a write when it is full and serves a read whenever it is not empty; a checker module (`fifo_props`) bound into the FIFO (a `bind` directive instantiates a module inside every instance of a target module without editing the target's source, IEEE 1800-2023 §23.11), holding the LLM's draft and the reviewed assertions; and `tb_top`, which drives a directed scenario through a clocking block and checks the data with a small queue model. Define the macro `LLM_DRAFT` to include the draft assertions.

```systemverilog
// compile
`timescale 1ns/1ns

// A FIFO that drops a write when full. DEPTH must be a power of two so that
// the pointers wrap naturally.
module fifo4 #(parameter int DEPTH = 4, parameter int W = 8) (
  input  logic                   clk,
  input  logic                   rst_n,
  input  logic                   write_en,
  input  logic                   read_en,
  input  logic [W-1:0]           wdata,
  output logic [W-1:0]           rdata,
  output logic                   fifo_full,
  output logic                   fifo_empty,
  output logic [$clog2(DEPTH):0] fifo_count   // one bit wider so DEPTH fits
);
  logic [W-1:0]             mem [DEPTH];
  logic [$clog2(DEPTH)-1:0] wr_ptr, rd_ptr;
  wire do_write = write_en && !fifo_full;
  wire do_read  = read_en  && !fifo_empty;

  always_ff @(posedge clk or negedge rst_n) begin
    if (!rst_n) begin
      wr_ptr     <= '0;
      rd_ptr     <= '0;
      fifo_count <= '0;
    end else begin
      if (do_write) begin
        mem[wr_ptr] <= wdata;
        wr_ptr      <= wr_ptr + 1'b1;
      end
      if (do_read) rd_ptr <= rd_ptr + 1'b1;
      case ({do_write, do_read})
        2'b10:   fifo_count <= fifo_count + 1'b1;
        2'b01:   fifo_count <= fifo_count - 1'b1;
        default: ;  // both or neither: the count is unchanged
      endcase
    end
  end

  assign rdata      = mem[rd_ptr];
  assign fifo_full  = (fifo_count == DEPTH);
  assign fifo_empty = (fifo_count == 0);
endmodule

// Checker bound into fifo4: sees the FIFO's ports and its internal wr_ptr.
module fifo_props #(parameter int DEPTH = 4) (
  input logic                     clk,
  input logic                     rst_n,
  input logic                     write_en,
  input logic                     read_en,
  input logic                     fifo_full,
  input logic [$clog2(DEPTH):0]   fifo_count,
  input logic [$clog2(DEPTH)-1:0] wr_ptr
);
`ifdef LLM_DRAFT
  // The LLM's draft, kept so the review finding can be reproduced.
  a_llm_count_bounded: assert property (@(posedge clk) disable iff (!rst_n)
    fifo_count <= DEPTH)
    else $error("FIFO count exceeded MAX_DEPTH: %0d", fifo_count);

  a_llm_full_write: assert property (@(posedge clk) disable iff (!rst_n)
    (fifo_full && write_en) |-> ##1 (fifo_count == $past(fifo_count)))
    else $error("Write to full FIFO corrupted count");
`endif

  // Reviewed: the count can never exceed DEPTH (fifo_count is wide enough to fail).
  a_count_bounded: assert property (@(posedge clk) disable iff (!rst_n)
    fifo_count <= DEPTH)
    else $error("count %0d > DEPTH", $sampled(fifo_count));

  // Reviewed: a write to a full FIFO with no read is dropped, so neither the
  // count nor the write pointer moves.
  a_full_write_dropped: assert property (@(posedge clk) disable iff (!rst_n)
    fifo_full && write_en && !read_en |=> $stable(fifo_count) && $stable(wr_ptr))
    else $error("full write not dropped: count %0d, wr_ptr %0d",
                $sampled(fifo_count), $sampled(wr_ptr));

  // Reviewed: full, write and read together: the read is served, the write dropped.
  a_full_write_read: assert property (@(posedge clk) disable iff (!rst_n)
    fifo_full && write_en && read_en |=>
      fifo_count == $past(fifo_count) - 1 && $stable(wr_ptr))
    else $error("full write+read: count %0d", $sampled(fifo_count));

  // Covers prove that each antecedent actually happened in this test.
  c_full_write_read: cover property (@(posedge clk) disable iff (!rst_n)
    fifo_full && write_en && read_en)
    $display("%0t COVER c_full_write_read: full, write and read in one cycle", $time);

  c_full_write_no_read: cover property (@(posedge clk) disable iff (!rst_n)
    fifo_full && write_en && !read_en)
    $display("%0t COVER c_full_write_no_read: write to a full FIFO, no read", $time);
endmodule

module tb_top;
  logic       clk = 1'b0;
  logic       rst_n = 1'b0;
  logic       write_en = 1'b0;
  logic       read_en = 1'b0;
  logic [7:0] wdata = '0;
  logic [7:0] rdata;
  logic       fifo_full, fifo_empty;
  logic [2:0] fifo_count;

  always #5 clk = ~clk;  // rising edges at 5, 15, 25, ... ns

  fifo4 #(.DEPTH(4), .W(8)) dut (.*);

  // Parameters and ports of a bind are resolved in the target (fifo4) scope.
  bind fifo4 fifo_props #(.DEPTH(DEPTH)) u_props (.*);

  // Drive DUT inputs 1 ns after each edge; sample just before it.
  clocking cb @(posedge clk);
    default input #1step output #1;
    output rst_n, write_en, read_en, wdata;
  endclocking

  clocking mon_cb @(posedge clk);
    default input #1step;
    input rst_n, write_en, read_en, wdata, rdata, fifo_full, fifo_empty;
  endclocking

  // Data check: a queue model of the same rules. The assertions above check
  // control; only this checks that the right data comes out in order.
  logic [7:0] model_q[$];
  int         matches, mismatches;

  always @(mon_cb) begin
    if (mon_cb.rst_n) begin
      if (mon_cb.read_en && !mon_cb.fifo_empty) begin
        logic [7:0] expected;
        expected = model_q.pop_front();
        if (mon_cb.rdata === expected) matches++;
        else begin
          mismatches++;
          $error("read 0x%0h, expected 0x%0h", mon_cb.rdata, expected);
        end
      end
      if (mon_cb.write_en && !mon_cb.fifo_full) model_q.push_back(mon_cb.wdata);
    end
  end

  initial begin
    repeat (2) @(cb);
    cb.rst_n <= 1'b1;
    for (int i = 0; i < 4; i++) begin       // fill the FIFO
      cb.write_en <= 1'b1;
      cb.wdata    <= 8'hA0 + 8'(i);
      @(cb);
    end
    cb.read_en <= 1'b1;                      // full: write and read together
    cb.wdata   <= 8'hEE;                     // this write must be dropped
    @(cb);
    cb.read_en <= 1'b0;                      // refill to full
    cb.wdata   <= 8'hA4;
    @(cb);
    cb.wdata   <= 8'hFF;                     // full, no read: must be dropped
    @(cb);
    cb.write_en <= 1'b0;                     // drain
    cb.read_en  <= 1'b1;
    repeat (4) @(cb);
    cb.read_en <= 1'b0;
    repeat (2) @(cb);
    $display("PASS=%0d FAIL=%0d", matches, mismatches);
    $finish;
  end
endmodule
```

**Trace the key edges** (the TimingDiagram above shows edges 6 to 10):

| Edge (time) | Sampled inputs | What the FIFO does | Draft `a_llm_full_write` | Reviewed assertions |
|---|---|---|---|---|
| 6 (55 ns) | count 3, write A3 | stores A3, count 4, full | antecedent false | nothing starts |
| 7 (65 ns) | full, write EE, read | drops EE, serves A0, count 3 | attempt starts | `a_full_write_read` starts; cover hit |
| 8 (75 ns) | count 3, write A4 | stores A4, count 4, full | **fails: 3 is not 4** | `a_full_write_read` passes (3 = 4 − 1) |
| 9 (85 ns) | full, write FF, no read | drops FF, count 4 | attempt starts | `a_full_write_dropped` starts; cover hit |
| 10 (95 ns) | count 4, read | serves A1 | passes | `a_full_write_dropped` passes |

The reads at edges 7, 10, 11, 12 and 13 return A0, A1, A2, A3 and A4, so the queue model counts 5 matches. Neither dropped value (EE, FF) ever comes out. The draft's failure at 75 ns is on a correct design: that is the over-specification finding, reproduced.

**What this bench still does not prove.** The assertions check control (count and pointer), and the queue model checks data only for this one directed scenario. Full data integrity under random traffic belongs to a scoreboard ([A-UVM-6](/curriculum/T3_Advanced/A-UVM-6_Scoreboards_and_Reference_Models/index)) or to a formal check; with a formal tool you would prove the reviewed properties for all input sequences, a tool-dependent step covered in [E-INT-1](/curriculum/T4_Expert/E-INT-1_Integrating_UVM_with_Formal_Verification/index).

### A closure calculator for the claim chart

This Python script produced the chart's numbers. It is a real run (Python 3.13.4).

```python
"""Expected random samples to cover k of n equally likely coverage bins."""


def expected_samples(n: int, k: int) -> float:
    # While i bins are covered, a new sample hits a new bin with probability (n - i) / n,
    # so that step takes n / (n - i) samples on average. Sum the steps.
    return sum(n / (n - i) for i in range(k))


N = 100
print(f"{'target':>7} {'random':>8} {'no-repeat':>9} {'ratio':>6}")
for k in (50, 80, 90, 95, 99, 100):
    rnd = expected_samples(N, k)
    print(f"{k:>6}% {rnd:>8.1f} {k:>9} {rnd / k:>5.2f}x")

# One rare bin: hit with probability p per sample. On average it takes 1 / p samples.
for p in (1 / 200, 1 / 2000):
    print(f"rare bin p={p:.5f}: about {1 / p:.0f} samples on average")
```

### How to review AI-generated verification code

1. **Write the intent first.** One sentence per check, from the specification, before you read the AI output.
2. **Compile it.** This catches invented APIs and syntax errors only; it proves nothing about meaning.
3. **Walk the SVA checklist** (timing, shape, sampling and history, disable, reachability, widths, spec versus RTL) or the sequence checklist (checked randomization, complete handshake, no delays, objections, real APIs, resolved ambiguities).
4. **Add a cover** for every antecedent and every interesting scenario.
5. **Run a directed scenario** that exercises the rule, including the legal corner cases the spec allows (here, a read while full).
6. **Mutation-test.** Break the design in the way the check should catch (for example, let the FIFO accept a write when full) and confirm the check fires.
7. **Commit the reviewed version** as ordinary source, with the model, prompt and date in the commit message. Never regenerate it in CI.

**Checklist before moving on:**
- [ ] I can explain why the draft fails at 75 ns on a correct design, and which spec case it over-specifies.
- [ ] Every assertion I accept has a cover on its antecedent that was hit in at least one test.
- [ ] Action-block messages print `$sampled(...)` values.
- [ ] Every counter in a property is wide enough to hold every value it is compared with.
- [ ] I have checked data, not only control, somewhere in the bench.
- [ ] I can compute the expected samples for a coverage target and explain why the speed-up ratio depends on it.
- [ ] I know which AI artifacts in my flow are committed with provenance, and where the human gates are.

## Push Further

### Expert: The arithmetic of closure

The solver's guarantee is about values, not bins: §18.5.9 makes every legal value combination equally likely, and a `dist` constraint reshapes that distribution on purpose (§18.5.3). Bin probabilities follow from both and from your bin definitions. Three regimes follow:
- **Equally likely bins:** about *n* × H(*n*) samples to close *n* bins (519 for 100), and reaching *k* of them costs *n*(H(*n*) − H(*n* − *k*)).
- **Unequal bins:** closure waits for the rarest bin, at about 1/*p*_min samples. Biasing (`dist`, constraint modes) and every ML method in this lesson work by raising *p*_min.
- **Probability 0:** no method helps; the fix is a constraint change or a spec-backed exclusion.

A staff-level consequence: when you plan compute for closure, estimate the rarest reachable bin's probability from the constraints, not from yesterday's curve. Sources: IEEE 1800-2023 §18.4.1, §18.5.3, §18.5.9; the calculation in Make It Work; the coverage model behind the explorer above ("coupon collector with unequal probabilities").

### Expert: Reading a speed-up claim

Reduce every claim to the scorecard, then compute what it would mean for you. "Up to N×" is a best case. A ratio quoted at 100% closure looks larger than the same method at your real sign-off target, which may exclude waived bins (the chart above: 2.51× at 90% versus 5.19× at 100% for the same pair of generators). Check whether the baseline was tuned and given the same compute, whether training runs are counted as cost, and whether the designs resemble yours. Then run the pilot described above: frozen RTL, equal compute, several runs, the median and spread, and a random control slice. Worked vendor example: the VSO.ai page's "Up to 10x Verification Productivity Boost" (accessed 11 October 2026; vendor claim, no stated target or baseline). Source: the computed values above; the vendor page as cited.

### Expert: Learned test selection done right

Masamba, Eder and Blackmore (IEEE AITest 2022) describe the pattern: randomly generate many tests, use **supervised learning from coverage feedback** to select the most effective subset, and simulate only that subset. The design choices that decide whether it works:
- **Features** must come from the stimulus (or the knob settings), which exist before simulation. A seed number carries no learnable signal.
- **Labels** come from coverage you already measured; the model is only as good as the coverage model it learned from.
- **Drift:** an RTL change can change which tests matter. Retrain on recent runs and keep the random control slice to detect drift.
- **Reuse of known seeds** is legitimate because of random stability (I-SV-2B): a recorded seed reproduces its run, so it can be re-ranked from history.

For the wider family, Fine and Ziv (DAC 2003) used Bayesian networks to direct generation toward cross-product coverage holes, and Ioannides and Eder (ACM TODAES 17(1), 2012) review CDG methods including genetic algorithms. Sources as cited.

### Expert: Failure clustering beyond signatures

Signature bucketing groups runs by a normalized first error message ([E-DBG-1](/curriculum/T4_Expert/E-DBG-1_Advanced_UVM_Debug_Methodologies/effective-debug)). It fails in two directions: one root cause can produce several messages (a checker fires in different places), and one message can hide several causes (a generic timeout). Failure clustering treats triage as a data-mining problem: describe each failure by features (message, failing checker, time, the components and signals involved) and cluster them, as Poulos and Veneris do for RTL regression failures (ITC 2014). Commercial tools offer ML-based triage (Cadence Verisium AutoTriage, announced September 2022, per the vendor's description). Practice that keeps it honest: debug at least one run from every cluster, review a sample of each cluster's members, and treat "new cluster" as a signal to look. Sources: Poulos and Veneris 2014; the Verisium announcement (vendor, tool-dependent).

### Expert: Benchmarking LLM assertion generators

A pass rate for "the generated SVA compiles" says almost nothing. FVEval (Kang et al., NVIDIA, arXiv 2410.23299, 2024) evaluates LLMs on formal-verification tasks at several levels, from natural language to SVA up to suggesting assertions directly from RTL, using both expert-written and synthetic test cases. When you evaluate a generator yourself, separate four measures: syntax (it compiles); functional match (equivalence with a reference assertion, checked by a formal tool where you have one, tool-dependent); reachability (each antecedent covered); and **bug detection** (each assertion fires on a mutant it should catch). Also beware **benchmark contamination**: a model may have seen a public benchmark's answers during training. Sources: FVEval as cited; mutation testing and formal equivalence are tool-dependent.

### Expert: Reproducibility and provenance

Treat generated collateral like code from an outside contributor: reviewed, committed, attributable. Record the model name and version, the full prompt, the parameters and the date; keep the reviewed result, not the prompt, as the source of truth. Do not regenerate in CI: LLM inference can be nondeterministic even at temperature 0 because inference kernels are not always batch-invariant (H. He, "Defeating Nondeterminism in LLM Inference", Thinking Machines Lab, September 2025), and hosted models are updated. For learned stimulus, log the seed, the policy or model version and the knob values per run, so that any failure the model finds can be rerun exactly. Sources: He 2025; the rest is tool-dependent practice.

### Expert: Data and IP boundaries

Tool-dependent and policy-dependent; the questions to answer before any AI tool sees project data: Which data classes may it see (RTL, specifications, logs, waveforms, coverage databases)? Where does it run (vendor cloud, enterprise tenancy, on-premises)? What does the provider retain, and for how long? Is the data export-controlled? Can prompts or outputs be used to train the provider's models? Who approved it? Teams that cannot answer these in writing should limit AI use to public, non-proprietary material. This is practice guidance, not a standard.

### Expert: AI tools in safety-related flows

In automotive flows, ISO 26262-8 clause 11 ("Confidence in the use of software tools") asks you to classify each tool by its **tool impact** (TI: can its error introduce or hide a fault?) and its **tool error detection** (TD: how likely is such an error to be caught?), which together give a **tool confidence level** (TCL) and the qualification it needs. An AI tool that drafts assertions has high impact if its output is trusted; independent review, covers, mutation tests and formal checks raise the detection level. This summary is from secondary sources; read the clause itself before you rely on it.

### Review exercise: six AI-drafted checks with seeded bugs

For each item, write down (a) what is wrong and which rule it breaks, (b) the fix, and (c) the cover you would add, before you open the solution. Items 1 to 4 match the four debug cases of the SVA trace lab above: predict in the lab first, then compare.

1. **Spec:** "ack is high exactly two cycles after every req." **Draft:** `assert property (@(posedge clk) req ##2 ack);`
2. **Spec:** "ack is high in the cycle after req." **Draft:** `assert property (@(posedge clk) req |-> ack);`
3. **Spec:** "q is d delayed by one cycle; q is 0 while rst is 1." **Draft:** `assert property (@(posedge clk) disable iff (rst) q == $past(d));`
4. **Spec:** "After reset (rst_n active low), every req gets ack on the next cycle." Assume req is never driven during reset. **Draft:** `assert property (@(posedge clk) req && !rst_n |=> ack);`
5. **Spec:** "When the FIFO is full, a write must not cause data corruption." **Draft:** the `p_full_write_no_corrupt` property from the worked review above.
6. **Spec (test plan):** "10 writes to consecutive word addresses from 0x1000, then read them all back and check the data." `bus_item` has `rand bit write; rand bit [31:0] addr, data;` and the driver writes read data back into the item before `item_done()`. **Draft:**

```systemverilog
// snippet: LLM draft, shown for review (do not copy)
class wr_rd_seq extends uvm_sequence #(bus_item);
  `uvm_object_utils(wr_rd_seq)

  function new(string name = "wr_rd_seq");
    super.new(name);
  endfunction

  task body();
    bit [31:0] wdata[10];
    starting_phase.raise_objection(this);
    for (int i = 0; i < 10; i++) begin
      req = bus_item::type_id::create("req");
      assert(req.randomize() with { write == 1; addr == 32'h1000 + i; });
      wdata[i] = req.data;
      start_item(req);
      finish_item(req);
    end
    for (int i = 0; i < 10; i++) begin
      req = bus_item::type_id::create("req");
      req.write = 0;
      req.addr  = 32'h1000 + i;
      start_item(req);
      finish_item(req);
      #10ns;
      if (!req.compare_and_report(wdata[i]))
        `uvm_error("SEQ", "read data mismatch")
    end
    starting_phase.drop_objection(this);
  endtask
endclass
```

<details>
<summary>Worked solutions</summary>

1. **Wrong implication (bare sequence).** As a property, a sequence must match from every attempt, and a new attempt starts at every clock edge (§16.12.2, §16.14.5), so every edge without req fails. **Fix:** `req |-> ##2 ack`. **Cover:** `cover property (@(posedge clk) req ##2 ack);`
2. **Cycle off-by-one.** `|->` checks ack on the same edge as req; the spec says the next cycle (§16.12.7). **Fix:** `req |=> ack`. **Cover:** `cover property (@(posedge clk) req);`
3. **Sampling and history across reset.** At the first edge after reset, q still holds its reset value 0, but `$past(d)` is d sampled during reset. Whenever d was nonzero during reset, a correct flop fails once. **Fix:** `disable iff (rst) !$past(rst) |-> q == $past(d)`. Do not put `$past` in the `disable iff` condition: it uses current values. **Cover:** `cover property (@(posedge clk) disable iff (rst) !$past(rst) && d);`
4. **Vacuity.** `req && !rst_n` can only match during reset, when req is never driven, so every attempt is vacuous (§16.14.8). **Fix:** `req && rst_n |=> ack`. **Cover:** `cover property (@(posedge clk) req && rst_n);` A cover count of zero would have exposed the draft immediately.
5. **Over-specification and wrong target.** It checks the count, not the data, and it fails when a legal read happens in the same cycle. **Fix:** the reviewed `a_full_write_dropped` and `a_full_write_read` from Make It Work, plus a data check (a scoreboard or the queue model). **Covers:** `c_full_write_read` and `c_full_write_no_read`.
6. **Six defects in the sequence:**
   - `starting_phase.raise_objection(this)`: `starting_phase` is a compatibility variable in uvm-core 2020.3.1 and is null when the test calls `seq.start(sqr)`, so this is a null-handle access. Objections belong in the test or a top-level sequence: use `get_starting_phase()` with a null check, or `set_automatic_phase_objection(1)` (IEEE 1800.2-2020 §14.2.4). Here, simply raise and drop in the test.
   - `assert(req.randomize() ...)`: silently skipped when assertion evaluation is switched off (§20.11). Use ``if (!req.randomize() with {...}) `uvm_fatal(...)``.
   - `32'h1000 + i`: "consecutive word addresses" on a byte-addressed 32-bit bus step by 4. The draft guessed; confirm with the spec owner.
   - Randomizing before `start_item`: legal, but randomize after `start_item` so the item reflects the state at the moment the sequencer grants it ([I-UVM-3A](/curriculum/T2_Intermediate/I-UVM-3A_Fundamentals/index)).
   - `#10ns`: `finish_item` already returns after the driver's `item_done()`, when the read data is in the item. The delay is a guess.
   - `compare_and_report`: no such method exists in uvm-core 2020.3.1. Compare the field directly.

   A reviewed `body()`:

```systemverilog
// snippet: reviewed body() for wr_rd_seq (objections are raised in the test)

  bit [31:0] wdata[10];
  for (int i = 0; i < 10; i++) begin
    req = bus_item::type_id::create($sformatf("wr%0d", i));
    start_item(req);
    if (!req.randomize() with { write == 1; addr == 32'h1000 + 4 * i; })
      `uvm_fatal("RAND", "write item randomization failed")
    finish_item(req);
    wdata[i] = req.data;
  end
  for (int i = 0; i < 10; i++) begin
    req = bus_item::type_id::create($sformatf("rd%0d", i));
    start_item(req);
    if (!req.randomize() with { write == 0; addr == 32'h1000 + 4 * i; })
      `uvm_fatal("RAND", "read item randomization failed")
    finish_item(req);  // returns after item_done(): req.data holds the read data
    if (req.data !== wdata[i])
      `uvm_error("SEQ", $sformatf("addr 0x%0h: read 0x%0h, wrote 0x%0h",
                                  req.addr, req.data, wdata[i]))
  end
endtask
```

A good pilot plan names: one RTL and testbench tag held fixed; the real sign-off target (often below 100% after reviewed waivers); identical machine budgets for both flows; at least several independent runs per flow; coverage-versus-compute curves with median and spread; a random control slice inside the ML flow (for example a fixed share of unselected tests) to detect escaped bugs; and the cost of training runs and adoption time counted against the gain.
