## Quick Take

- **What it is:** Processor verification checks that every instruction the core **retires** (finishes and commits) changes the programmer-visible state exactly as the RISC-V specification says: the integer registers, the program counter, the control and status registers and memory. It does this across random programs, privilege modes, exceptions and interrupts. Four tools do the work: a **program generator** that writes random but legal assembly programs, an **instruction set simulator** (ISS) that runs the same program as a reference, **ISA coverage** that measures what the programs exercised, and **formal checks** on a retirement port called RVFI.
- **Why it matters:** If you build or modify a RISC-V core, its correctness is your job: the open specification gives you no verified implementation. Typical escapes hide in instruction decode, register forwarding (handing a result straight to the next instruction before it reaches the register file), traps, interrupts and control registers. A green compare means nothing if the compare cannot see a hung core or an interrupt the reference never heard about.
- **The Analogy:** Two accountants book the same transactions. A **post-run compare** checks the two ledgers at year end; a **lock-step compare** checks each entry the moment it is booked. *Where it breaks:* some entries cannot be recomputed by the second accountant, such as the bank's interest or the time of day. For a core these are cycle counters and the moment an interrupt arrives. The testbench must copy them from the first ledger to the second, or every ledger disagrees.

**You will be able to:**
1. **Explain** why verifying a processor differs from verifying a peripheral: architectural state checked at retirement, privilege modes, synchronous exceptions versus asynchronous interrupts, and the sources of nondeterminism.
2. **Configure** a riscv-dv test with documented testlist keys, `gen_opts` options and directed streams, and **read** an ISA coverage model (a riscv-isac CGF file or an ACT4 SystemVerilog covergroup) to find what a regression did not exercise.
3. **Write** a post-run trace compare that reports the first divergence and fails on truncated, extra or empty traces.
4. **Plan and debug** a lock-step compare: which events the testbench must forward to the ISS, which values it must override, and how to diagnose a mismatch caused by a missed interrupt or a counter read.
5. **Explain** what RVFI exposes and what a riscv-formal pass guarantees, and **choose** formal or simulation for a given processor bug class.

## Build Your Mental Model

This lesson uses one tiny RV32I program throughout. It is short enough to trace by hand, and every compare on the page runs on it.

| # | Address | Instruction | Encoding | Effect |
|---|---|---|---|---|
| 0 | `0x100` | `addi x1, x0, 5` | `0x00500093` | x1 = 5 |
| 1 | `0x104` | `addi x2, x0, 7` | `0x00700113` | x2 = 7 |
| 2 | `0x108` | `add x3, x1, x2` | `0x002081B3` | x3 = 12 |
| 3 | `0x10C` | `sw x3, 0(x0)` | `0x00302023` | memory word at address 0 = 12 |
| 4 | `0x110` | `lw x4, 0(x0)` | `0x00002203` | x4 = 12 |
| 5 | `0x114` | `addi x0, x0, 0` | `0x00000013` | no effect (the canonical `nop`) |

The memory map is a toy: RAM starts at address 0, so the store and load use address 0. That choice matters later, because one classic compare bug skips any store to address 0.

### Words you need first

Each term is used on the rest of the page, so each gets one plain sentence here.

- **ISA (instruction set architecture):** the contract between software and hardware: the instructions, their encodings, the registers and what each instruction does to them. RISC-V's base 32-bit integer ISA, **RV32I**, has 40 instructions; extensions add more, such as **M** (multiply and divide) and **C** (16-bit compressed encodings). An **ISA string** such as `rv32imc` names the base and extensions a core implements.
- **Core:** the processor design under test (DUT), in RTL.
- **Architectural state:** everything the ISA lets software see: the integer registers `x0` to `x31` (`x0` always reads 0), the program counter (`pc`), the **CSRs** (control and status registers, such as `mstatus` with the global interrupt enable MIE, `mip` with the pending-interrupt bits, the trap registers `mcause` and `mepc`, and the cycle counter `mcycle`) and memory.
- **Microarchitectural state:** everything else inside the core, such as pipeline registers, caches and branch predictors. It is invisible to software, so the reference model does not have it and it cannot be compared directly.
- **Retire:** an instruction retires when it has finished and its results are committed to architectural state. Retirement is the moment a processor testbench compares, because it is the only moment the RTL and the specification agree on what "done" means.
- **Trap:** a transfer of control to a handler. A **synchronous exception** is caused by the instruction itself (an illegal encoding, a misaligned access the core does not support, an `ecall`). An **interrupt** is **asynchronous**: something outside the program (a timer, an external line, a debug request) asks for attention between instructions. When a trap is taken into machine mode, `mepc` holds the address of the interrupted or faulting instruction, and the top bit of `mcause` says whether it was an interrupt.
- **Privilege modes:** RISC-V defines machine (M), supervisor (S) and user (U) mode. Each trap and each return (`mret`) can change mode, and what an instruction may do depends on the mode.
- **ISS (instruction set simulator):** a program that executes RISC-V instructions one at a time and updates a model of architectural state. It is **instruction-accurate, not cycle-accurate**: it knows what each instruction does, not how long it takes. Spike and Sail are the common open-source ISSes.
- **ELF:** the binary file a compiler or assembler produces; the testbench loads it into the core's memory model and the ISS loads the same file.

### What makes a processor different

You have verified peripherals in earlier modules: a transaction goes in, a transaction comes out, a scoreboard compares them against a reference model. A core breaks that picture in four ways.

| Dimension | Peripheral (UART, DMA, FIFO) | RISC-V core |
|---|---|---|
| Stimulus | Transactions on its ports | A **program** in memory; the core fetches its own stimulus |
| What you compare | Output transactions | Architectural state after each **retirement** |
| Reference model | A transaction-level model you write | An ISS, configured to match the core's ISA string and options |
| Control flow | Set by the testbench | Set by the program, and changed by traps and interrupts the testbench injects |
| Nondeterminism | Usually ordering between ports | Cycle counters, interrupt arrival time, implementation-defined choices |

The last row is the one that breaks naive testbenches. An ISS reproduces only what the ISA fully determines. Four kinds of value are not fully determined:
1. **Cycle and performance counters.** `mcycle` counts clock cycles of the RTL; an instruction-accurate ISS has no cycles to count.
2. **Interrupt and debug-request arrival.** The testbench raises them at some clock edge; the ISS runs no clock and cannot know which instruction boundary they landed on.
3. **Implementation-defined behaviour.** The ISA leaves some choices to the implementation, for example whether a misaligned load is handled in hardware or traps. The ISS must be configured to make the same choice.
4. **External responses.** A bus error on a load is decided by the memory system, not by the program.

**Classic mistake: comparing the PC only.** A PC-only compare passes a core that computes `add` wrongly, because a wrong sum does not change where the next instruction is fetched. **Classic mistake: comparing per clock cycle.** The RTL may take one cycle or forty for the same instruction, and the ISS has no cycles. The only shared timeline is the sequence of retirements.

### The processor verification loop

The loop has five steps: generate a program, build it, run it on the ISS and on the RTL, compare, and measure coverage. The open-source riscv-dv flow automates the first steps; your core's own flow owns the RTL side.

As a text list: the testlist's options drive the generator (`gen`), which writes an assembly program; `gcc_compile` turns it into an ELF; `iss_sim` runs the ELF on one or more ISSes and writes trace CSV files; `iss_cmp` compares two ISS traces; the separate `cov` command builds coverage from a trace. Your core flow loads the same ELF into the RTL simulation and compares the RTL against the ISS, either after the run or in lock-step.

### Generating programs with riscv-dv

**riscv-dv** is an open-source instruction generator written in SystemVerilog and UVM, started by Google and now hosted by CHIPS Alliance. It writes random RISC-V assembly programs that are legal by default: illegal instructions and HINT instructions (encodings reserved as hints, which execute as no-ops) appear only when you ask for them. Its `run.py` script reads a **testlist**, a YAML file (a plain-text format for lists and key-value pairs) in which each entry names a test and its options. Many options are **plusargs**: `+name=value` strings on the simulator command line, which SystemVerilog code reads at run time (with `$value$plusargs`, or through UVM's command-line processor, as riscv-dv does).

The testlist keys are documented in the header of every riscv-dv target testlist. `run.py` looks up the generator-side keys by name; keys such as `rtl_test`, `sim_opts` and `compare_opts` are carried for your core's own flow to read. No script validates the keys, so **a key nobody reads is silently ignored**.

| Key | What it does |
|---|---|
| `test` | Name of this test |
| `description` | Free text |
| `gen_test` | The generator's UVM test, for example `riscv_instr_base_test` |
| `gen_opts` | Generator options, as `+name=value` plusargs (table below) |
| `iterations` | How many programs to generate, each with its own seed |
| `rtl_test` | The RTL test name, passed to your core flow |
| `sim_opts` | Simulation options. `run.py` does not read this per-test key (it has its own `--sim_opts` for the generator run), so your core flow uses it for the RTL simulation: `riscv_full_interrupt_test` passes `+enable_irq_seq=1` to ask the bench for interrupts |
| `compare_opts` | Options for the RTL-vs-ISS compare, for example `+compare_final_value_only=1` |
| `no_iss`, `no_post_compare` | Skip the ISS run or the post-run compare |
| `cmp_opts`, `gcc_opts` | Generator compile options and gcc options |
| `asm_tests` | Hand-written assembly tests to run instead of generated ones |

Here is a real entry from riscv-dv's `yaml/base_testlist.yaml`, traced option by option. The defaults come from riscv-dv's runtime-options table in `docs/source/configuration.rst`.

```yaml
- test: riscv_arithmetic_basic_test
  description: >
    Arithmetic instruction test, no load/store/branch instructions
  gen_opts: >
    +instr_cnt=10000
    +num_of_sub_program=0
    +directed_instr_0=riscv_int_numeric_corner_stream,4
    +no_fence=1
    +no_data_page=1
    +no_branch_jump=1
    +boot_mode=m
    +no_csr_instr=1
  iterations: 2
  gen_test: riscv_instr_base_test
  rtl_test: core_base_test
```

| Option | Default | Effect in this test |
|---|---|---|
| `+instr_cnt=10000` | 200 | 10,000 instructions per program |
| `+num_of_sub_program=0` | 5 | No sub-programs, so no calls and returns |
| `+directed_instr_0=riscv_int_numeric_corner_stream,4` | none | Inserts the numeric-corner stream about 4 times per 1000 instructions |
| `+no_fence=1` | 0 | No `fence` instructions |
| `+no_data_page=1` | 0 | No data pages are generated (this test has no loads or stores) |
| `+no_branch_jump=1` | 0 | No branches or jumps |
| `+boot_mode=m` | m | Start in machine mode |
| `+no_csr_instr=1` | 0 | No CSR instructions |
| `iterations: 2` | none | Two programs, two seeds (`run.py --iterations` overrides it) |

Three levers control what a program contains:
1. **`gen_opts` plusargs** remove or add classes of instruction and behaviour (the table above, plus options such as `+illegal_instr_ratio`, `+hint_instr_ratio`, `+enable_interrupt` and `+disable_compressed_instr`).
2. **Directed streams** splice hand-designed instruction sequences into the random program: `+directed_instr_<n>=<stream class>,<insertions per 1000 instructions>`. riscv-dv ships streams such as `riscv_int_numeric_corner_stream`, `riscv_hazard_instr_stream`, `riscv_load_store_rand_instr_stream` and `riscv_jal_instr`, and you can add your own.
3. **The target's `riscv_core_setting.sv`** says what the core supports: `XLEN`, `supported_isa` (for example `RV32I`, `RV32M`), `supported_privileged_mode` and `unsupported_instr`. The generator never emits an instruction outside it.

A custom entry follows the same pattern. This one keeps the arithmetic focus and adds a hazard stream:

```yaml
- test: my_arith_hazard_test
  description: >
    Arithmetic program with numeric corner values and register hazards
  gen_test: riscv_instr_base_test
  gen_opts: >
    +instr_cnt=5000
    +num_of_sub_program=0
    +directed_instr_0=riscv_int_numeric_corner_stream,4
    +directed_instr_1=riscv_hazard_instr_stream,10
    +no_fence=1
    +no_branch_jump=1
    +boot_mode=m
  iterations: 4
  rtl_test: core_base_test
```

**Misconception: "random instruction streams need no constraints."** Fill a memory with random 32-bit words and call it a program, and you get a poor test. Many words decode to illegal or reserved encodings, so the core spends its time in the illegal-instruction handler. Random branches and jumps leave the program. Random loads and stores hit unmapped addresses. Nothing guarantees the program ever ends. A generator like riscv-dv exists to make every instruction legal by construction, keep branches inside the program, point loads and stores at real data pages, reserve registers for the stack and the handlers, and end every program the same way.

**Pitfall: an invented key passes silently.** A key such as `dist:` with per-instruction weights is not a riscv-dv testlist key. Nothing reads it, and your "distribution" never reaches the generator. The same happens to `+num_of_tests` placed in `gen_opts`: `run.py` already passes `+num_of_tests` (computed from `iterations`) before your `gen_opts`, and the generator reads the first match. Use `iterations` to set the count.

**Debugging: "my run never produces a MUL."** Check, in order: the `--isa` you passed to `run.py` (or the target) includes `m`; `supported_isa` in `riscv_core_setting.sv` lists `RV32M`; `unsupported_instr` does not exclude it; no `gen_opts` removes it. Then open the generated `.S` file and search for `mul`: the program is the ground truth.

### ISA coverage: what did the programs exercise?

**ISA coverage** measures which instructions, operand patterns and value corners the programs actually executed. It is functional coverage (see [I-SV-3A](/curriculum/T2_Intermediate/I-SV-3A_Functional_Coverage_Fundamentals/index)) sampled at retirement. Three tools produce it.

1. **riscv-isac** reads an ISS trace and a coverage file written in **CGF (Cover Group Format)**, a YAML format. Status: the repository is **archived** (it now lives under `riscvarchive/riscv-isac`). It still documents the format many teams use.
2. **ACT4**, the framework of the RISC-V Architectural Certification Tests, replaced the deprecated RISCOF tool. Its coverpoints are generated SystemVerilog covergroups.
3. **riscv-dv's `cov` command** builds functional coverage from a trace CSV.

A small CGF covergroup for `add`, using only the node types and variables the CGF specification defines (`op_comb` uses register numbers `rs1`, `rs2`, `rd`; `val_comb` uses `rs1_val`, `rs2_val`, `imm_val`, `ea_align`):

```yaml
add_cg:
  config:
    - check ISA:=regex(.*I.*)
  mnemonics:
    add: 0
  rd:
    x0: 0
    x3: 0
  op_comb:
    'rs1 == rs2 == rd': 0
    'rs1 == rd or rs2 == rd': 0
  val_comb:
    'rs1_val == 0': 0
    'rs1_val == rs2_val': 0
  cross_comb:
    '[add : ?] :: [a=rd : ?] :: [? : rs1==a or rs2==a]': 0
```

The `cross_comb` line reads: an `add`, then any instruction; remember the `add`'s `rd` as `a`; the second instruction reads `a`. That is a read-after-write (**RAW**) hazard: an instruction that needs a value the previous one has just produced, which is exactly where forwarding bugs live.

Run on the lesson's program, only instruction 2 is an `add` (`add x3, x1, x2` with `x1 = 5`, `x2 = 7`):

| Coverpoint | Hit? | Why |
|---|---|---|
| `mnemonics: add` | 1 | Instruction 2 |
| `rd: x0` | 0 | No `add` writes `x0` |
| `rd: x3` | 1 | Instruction 2 |
| `op_comb: rs1 == rs2 == rd` | 0 | `x1`, `x2`, `x3` are all different |
| `op_comb: rs1 == rd or rs2 == rd` | 0 | Same reason |
| `val_comb: rs1_val == 0` | 0 | `rs1_val` is 5 |
| `val_comb: rs1_val == rs2_val` | 0 | 5 and 7 |
| `cross_comb` RAW | 1 | Instruction 3, `sw x3, 0(x0)`, reads `x3` as `rs2` |

Three of eight coverpoints are hit, and the five holes tell you what to generate next. *Predict:* which coverpoints would a single extra instruction `add x0, x5, x5` hit, if `x5` holds 0? (Answer: the holes `rd: x0`, `rs1_val == 0` and `rs1_val == rs2_val`, plus `mnemonics: add` again; not `rs1 == rs2 == rd`, because `rd` is `x0`, not `x5`.)

The ACT4 covergroup for the same instruction is plain SystemVerilog. An excerpt from `coverpoints/unpriv/I_coverage.svh` in the `riscv-arch-test` repository (`act4` branch):

```systemverilog
// snippet: simplified excerpt of a generated ACT4 covergroup (riscv-arch-test, act4 branch; RV32 bins only)
covergroup I_add_cg with function sample(ins_t ins);
  cp_rs1_edges : coverpoint unsigned'(ins.current.rs1_val) iff (ins.trap == 0) {
    bins zero  = {0};
    bins one   = {32'b00000000000000000000000000000001};
    bins ones  = {32'b11111111111111111111111111111111};
    // ... further edge values (min, max, and their neighbours)
  }
endgroup
```

Two details carry over to any processor coverage model. The `iff (ins.trap == 0)` guard means a trapping instruction never counts as exercising `add`. And `sample(ins_t ins)` takes one retired instruction, the same unit the compare uses.

**Pitfall: coverage from an ISS trace measures the program, not the RTL.** It tells you what the stimulus asked for. If the RTL silently dropped an instruction, the ISS trace still shows it. riscv-isac's own documentation warns that coverage from Spike traces is inaccurate, because Spike does not log instructions that trap, and recommends Sail. Sample coverage from the RTL's retirement port when you want to know what the core did.

**Pitfall: certification tests are not verification.** The ACT4 README states that the architectural tests "are not verification tests". They are self-checking ELFs whose expected results Sail computes, which your own testbench runs. They show that common behaviour matches the specification; they do not hunt for your pipeline's bugs.

### Comparing against an ISS after the run

The simplest compare is **post-run**: run the program on the RTL and log every retirement; run it on the ISS and log every retirement; compare the two logs afterwards. It needs no connection between the simulator and the ISS, which is why riscv-dv's flow starts with it.

Here is the classic mistake, in the shape many first attempts take, written in Python:

```python
# snippet: the naive compare (do not use)
for i, (r, s) in enumerate(zip(rtl, iss)):  # zip() stops at the shorter list
    if r.pc != s.pc:
        return f"#{i}: pc"
    if r.rd != 0 and r.rd_wdata != s.rd_wdata:  # never checks rd itself
        return f"#{i}: rd_wdata"
    if r.mem_addr and r.mem_wdata != s.mem_wdata:  # skips address 0
        return f"#{i}: mem_wdata"
return None  # None means PASS
```

*Predict before you read on:* the RTL hangs after instruction 2. Its trace has three entries; the ISS trace has six. What does this compare report?

It reports **PASS**. `zip()` stops at the shorter list, so the three missing retirements are never examined. That is misconception 1: a `zip()`-style compare is not sufficient. The table traces seven injected bugs through the naive compare and the robust compare you build in Make It Work, from a real run (CPython 3.13.4):

| RTL trace | Naive compare | Robust compare |
|---|---|---|
| Clean | PASS | PASS (6 matched) |
| Truncated after 3 (hang) | **PASS** | FAIL: length mismatch, RTL 3, ISS 6 |
| One extra retirement | **PASS** | FAIL: length mismatch, RTL 7, ISS 6 |
| Empty | **PASS** | FAIL: empty trace |
| `add` writes `x4` instead of `x3` | **PASS** | FAIL at #2: `rd` |
| Store to address 0 writes 11 | **PASS** | FAIL at #3: `mem_wdata` |
| Store goes to address 4 | **PASS** | FAIL at #3: `mem_addr` |
| `nop` reports `x0` written with 5 | **PASS** | FAIL at #5: `rd_wdata` |

The rules a robust post-run compare follows:
1. Compare **every** architectural effect of each retirement: `pc`, the instruction word, the trap flag, `rd` and its value (expecting 0 when `rd` is `x0`), and for stores the address, the byte mask and the masked data.
2. Report the **first** divergence. Everything after it is a consequence.
3. **Count.** Fail on an empty trace, and fail when the RTL retired fewer or more instructions than the reference. Missing outputs are found only by counting; this is the same end-of-test accounting you met in [A-UVM-6](/curriculum/T3_Advanced/A-UVM-6_Scoreboards_and_Reference_Models/index).
4. Print the number matched, so "PASS, 0 matched" can never look like success.

**What riscv-dv's own compare checks.** riscv-dv's `scripts/instr_trace_compare.py` compares the sequence of **integer-register updates** in two trace CSVs: it skips instructions that write no register, never compares stores directly (a bad store shows up only if a later load reads it back), and counts leftover register-writing entries as mismatches. Its `iss_cmp` step in `run.py` compares two ISSes. Know this before you trust a green result from it; the robust compare above is your own, stricter design.

**The limit of any post-run compare: interrupts.** The ISS runs the ELF alone. If the testbench raised a timer interrupt after instruction 2, the RTL trace continues in the interrupt handler while the ISS trace continues with instruction 3. The compare fails at the first handler instruction, and nothing in the logs says it was not a bug. riscv-dv's interrupt and debug tests therefore set `compare_opts: +compare_final_value_only=1`, which gives up comparing instruction by instruction (see Push Further for what that does in riscv-dv's script today). The fix is the next section.

### Lock-step step-and-compare

**Step-and-compare**, also called **lock-step co-simulation**, keeps the ISS running alongside the RTL simulation and compares at each retirement, while the simulation runs. The testbench calls the ISS through DPI (see [I-SV-7](/curriculum/T2_Intermediate/I-SV-7_DPI_and_Foreign_Language_Interfaces/index)): one **step** per retired instruction. Because the testbench sees the interrupt lines, it can tell the ISS about an interrupt before the step that needs it. That is what a post-run compare can never do.

The open-source Ibex core's UVM environment is a complete, public example. Its co-simulation documentation says the system runs an ISS (Spike) "in lockstep" with the core, and that interrupts, debug requests and memory errors observed in the RTL simulation are "forwarded to the ISS so the ISS and RTL remain in sync". Its DPI interface (`dv/cosim/cosim_dpi.svh`) includes these calls:

| DPI call | What it tells the ISS |
|---|---|
| `riscv_cosim_set_mip(handle, pre_mip, post_mip)` | Which interrupts are pending (the `mip` CSR) |
| `riscv_cosim_set_nmi`, `riscv_cosim_set_debug_req` | A non-maskable interrupt or a debug request |
| `riscv_cosim_set_mcycle(handle, mcycle)` | The RTL's cycle count, which the ISS cannot model |
| `riscv_cosim_notify_dside_access(...)` | A data-side memory access the RTL made, including any bus error |
| `riscv_cosim_step(handle, write_reg, write_reg_data, pc, sync_trap, suppress_reg_write)` | Execute one instruction and check it against what the RTL retired; returns 0 on mismatch |

How a step works, per the Ibex documentation: for a retired instruction, `step` executes one ISS instruction and checks the PC and the register write. For an instruction that raised a synchronous trap, it checks that the ISS traps on the same instruction. And **if an interrupt is pending when `step` is called, the ISS takes it first**, expecting the checked instruction to be the first instruction of the handler.

**Misconception: "the ISS compare handles asynchronous interrupts automatically."** It cannot. The ISS executes the program; nothing in the program says when the timer fired. The testbench observes the interrupt lines and must forward their state before the step, in the right priority order when several events coincide (Ibex calls `set_debug_req`, then `set_nmi`, then `set_nmi_int`, then `set_mip`). Forget it, and the first mismatch lands on the first handler instruction, every time.

**Pitfall: a hang produces no mismatch.** Lock-step compares only what retires. A core that stops retiring generates no steps, so the scoreboard never complains. End-of-test accounting is still required: a cycle timeout that is fatal, an end-of-test handshake from the program, and a check at the end that the scoreboard compared a sensible number of instructions. Ibex's base test, for example, waits for a `TEST_RESULT` handshake written by the program, with a cycle timeout that ends in `uvm_fatal` "TEST TIMEOUT!!", and its scoreboard prints "Co-simulation matched N instructions" in `final_phase`.

**Debugging a lock-step mismatch:** look at the first mismatch only, and ask three questions. Is it the first instruction after an interrupt, an NMI or a debug request (forwarding)? Does it read a counter or another CSR the ISS cannot model (override)? Does it follow a load or store that saw a bus error, or a misaligned access (notification, or ISS configuration)? Only when all three answers are no is it time to suspect the RTL.

### RVFI and riscv-formal

**RVFI (RISC-V Formal Interface)** is a set of output signals a core provides, usually only in verification builds, that describe each retired instruction. It was defined for the riscv-formal framework, and simulation benches use it too: Ibex's monitor reads an extended RVFI. The specification lives in `docs/source/rvfi.rst` of the `YosysHQ/riscv-formal` repository.

| Group | Signals | Rule worth remembering |
|---|---|---|
| Metadata | `rvfi_valid`, `rvfi_order`, `rvfi_insn`, `rvfi_trap`, `rvfi_halt`, `rvfi_intr`, `rvfi_mode`, `rvfi_ixl` | All other signals are meaningful only when `rvfi_valid` is 1; `rvfi_order` is the instruction index, with no index used twice and no gaps |
| Integer registers | `rvfi_rs1_addr`, `rvfi_rs2_addr`, `rvfi_rs1_rdata`, `rvfi_rs2_rdata`, `rvfi_rd_addr`, `rvfi_rd_wdata` | `rvfi_rd_wdata` must be zero when `rd` is zero; `rvfi_rd_addr` is zero for an instruction that writes no register |
| Program counter | `rvfi_pc_rdata`, `rvfi_pc_wdata` | The address of this instruction, and of the next one |
| Memory | `rvfi_mem_addr`, `rvfi_mem_rmask`, `rvfi_mem_wmask`, `rvfi_mem_rdata`, `rvfi_mem_wdata` | The masks say which bytes are valid |
| CSRs (optional) | `rvfi_csr_<name>_rmask`, `_wmask`, `_rdata`, `_wdata` | One group per traced CSR |

Two metadata rules matter most for a compare. `rvfi_trap` is set for an instruction that raised a synchronous trap, such as an illegal encoding. `rvfi_intr` is set for "the first instruction that is part of a trap handler", that is, an instruction whose `rvfi_pc_rdata` does not match the previous instruction's `rvfi_pc_wdata`. For a compressed instruction, `rvfi_insn` holds the 16-bit word with the upper bits zero.

**riscv-formal** is a framework that checks a core's RVFI output against a formal model of the ISA, using SymbiYosys, an open-source formal verification flow. You write a wrapper that instantiates your core with RVFI outputs and a `checks.cfg` file; its `genchecks.py` script generates the checks. The main kinds:

| Check | What it proves about the RVFI trace |
|---|---|
| `insn` (one per instruction and channel) | The retired instruction's register, PC and memory effects match the ISA model |
| `reg` | Values read from the register file match what was last written |
| `pc_fwd`, `pc_bwd` | Consecutive instructions agree on the PC |
| `causal`, `causal_mem`, `causal_io` | Retirement order respects register and memory dependencies |
| `liveness` | The core does not freeze (unless it retired a halting instruction) |
| `unique` | No two retirements share an `rvfi_order` |
| `cover` | Chosen states are reachable, used to pick the depths for the other checks |

**What a pass means.** The checks `genchecks.py` generates are **bounded model checks** by default (configuration `mode`, which also accepts `prove`): each check explores every input sequence up to a configured `[depth]` from reset. A pass in `bmc` mode means no violation within that depth, not "correct for all programs". And riscv-formal states its own limit for multiply and divide: they are beyond practical model checkers, so with `RISCV_FORMAL_ALTOPS` the core implements stand-in operations (an add or subtract, then an XOR with a fixed mask). That checks the forwarding and control around the M unit, not the multiplier itself.

An illustrative SVA version of one `insn`-style check, written by hand for this lesson. It is not riscv-formal source: riscv-formal generates its checks per instruction and writes them with immediate assertions for tool compatibility.

```systemverilog
// snippet: illustrative ADD check on an RVFI port (RV32, one channel)
wire is_add = rvfi_insn[6:0] == 7'b0110011 && rvfi_insn[14:12] == 3'b000
           && rvfi_insn[31:25] == 7'b0000000;

a_add_effects: assert property (@(posedge clk) disable iff (!rst_n)
  rvfi_valid && is_add && !rvfi_trap |->
    rvfi_rd_addr == rvfi_insn[11:7] &&
    rvfi_rd_wdata == ((rvfi_insn[11:7] == 5'd0) ? 32'd0
                                                : rvfi_rs1_rdata + rvfi_rs2_rdata) &&
    rvfi_pc_wdata == rvfi_pc_rdata + 32'd4);
```

The `rd == 0` arm is the point. Write the obvious `rvfi_rd_wdata == rvfi_rs1_rdata + rvfi_rs2_rdata` and the property fails on `add x0, x1, x2` whenever the sum is nonzero, because RVFI requires `rvfi_rd_wdata` to be zero when `rd` is `x0`. The overlapping implication `|->` (IEEE 1800-2023 §16.12.7) checks the consequent in the same cycle as the retirement.

**Choosing the engine.** Formal and simulation find different bugs, so plan both (the general method is in [E-INT-1](/curriculum/T4_Expert/E-INT-1_Integrating_UVM_with_Formal_Verification/index)).

| Bug class | Better engine | Why |
|---|---|---|
| A forwarding path wrong only for one rare back-to-back pair | Formal (`insn`, `reg`, `causal`) | Every pair within the depth is explored |
| Two retirements with the same `rvfi_order`, or a stall that never ends | Formal (`unique`, `liveness`) | Crisp per-cycle properties |
| A multiplier returning a wrong product | Simulation with an ISS | ALTOPS replaces the product in formal |
| A bug that needs an OS boot, a deep cache state or thousands of instructions to reach | Simulation (or emulation) | Far beyond any practical depth |
| Interrupt arriving during a multi-cycle divide | Both: formal for the local interaction, simulation for the system flow | Each covers the other's blind spot |

### Common pitfalls and misconceptions

| Belief | Why it is wrong | Instead |
|---|---|---|
| "A `zip()`-style compare is enough." | It stops at the shorter trace, so hangs and truncations pass | Check lengths, emptiness and every field; report the first divergence |
| "Random instruction streams need no constraints." | Raw random words hit illegal encodings, leave the program and touch unmapped memory | Use a generator that is legal by construction, and steer it with documented options |
| "The ISS compare handles interrupts automatically." | The ISS cannot see the testbench's interrupt lines | Forward interrupt, NMI and debug state before each step |
| "A clean lock-step run means the test passed." | A hung core retires nothing and produces no mismatch | Fatal cycle timeout, end-of-test handshake, matched-instruction count |
| "The ISS defaults match my core." | ISA string, privilege modes and the misaligned-access policy are configuration | Configure the ISS from the same source as the core (for Spike: `--isa`, `--priv`, `--misaligned`) |
| "A riscv-formal pass means the core is ISA-correct." | Default checks are bounded, and ALTOPS replaces multiply and divide | Report the mode and depth, and verify the M unit in simulation |
| "Coverage from the ISS trace is coverage of the core." | It measures the program; Spike omits trapping instructions | Sample coverage at the RTL retirement port |

### Recap

- A processor testbench compares **architectural state at retirement**, never cycles and never microarchitecture.
- riscv-dv makes **legal** random programs. Steer it with documented testlist keys, `gen_opts` and directed streams; unknown keys are ignored silently.
- ISA coverage (CGF, ACT4 covergroups, riscv-dv `cov`) shows the holes; sample it where the RTL retires.
- A post-run compare must **count** and check every field; it cannot follow interrupts.
- Lock-step steps the ISS once per retirement and needs the testbench to **forward** asynchronous events and **override** counters. It still needs a timeout, because a hang produces no mismatch.
- RVFI is the retirement port for both simulation and formal. A riscv-formal pass is bounded by default and does not cover the real multiplier under ALTOPS.

## Make It Work

### Worked example: a trace compare that cannot be fooled

This complete Python script holds the lesson's program as an ISS trace, injects seven bugs into copies of it, and runs both the naive compare and a robust one on each. Each `Retire` record holds the fields an RVFI monitor reports for one retirement.

```python
# compile: complete Python 3.8+ script, standard library only
from dataclasses import dataclass, replace
from typing import List, Optional


@dataclass(frozen=True)
class Retire:
    """One retired instruction: the fields an RVFI monitor reports."""
    pc: int
    insn: int
    rd: int = 0         # destination register number (0: none, or x0)
    rd_wdata: int = 0   # value written to rd
    trap: bool = False  # this instruction raised a synchronous trap
    mem_addr: int = 0
    mem_wmask: int = 0  # store byte enables; 0 means "not a store"
    mem_wdata: int = 0


def naive_compare(rtl: List[Retire], iss: List[Retire]) -> Optional[str]:
    """The classic mistake. Returns None for PASS."""
    for i, (r, s) in enumerate(zip(rtl, iss)):  # stops at the shorter trace
        if r.pc != s.pc:
            return f"#{i}: pc"
        if r.rd != 0 and r.rd_wdata != s.rd_wdata:  # never checks rd itself
            return f"#{i}: rd_wdata"
        if r.mem_addr and r.mem_wdata != s.mem_wdata:  # skips address 0
            return f"#{i}: mem_wdata"
    return None


def store_bytes(data: int, mask: int) -> int:
    """Keep only the bytes the store's byte-enable mask marks valid."""
    keep = 0
    for b in range(4):
        if mask >> b & 1:
            keep |= 0xFF << (8 * b)
    return data & keep


def robust_compare(rtl: List[Retire], iss: List[Retire]) -> Optional[str]:
    """Report the first divergence; never pass a short, long or empty trace."""
    if not rtl or not iss:
        return f"empty trace: RTL retired {len(rtl)}, ISS retired {len(iss)}"
    for i, (r, s) in enumerate(zip(rtl, iss)):
        exp_wdata = 0 if s.rd == 0 else s.rd_wdata  # x0 always reads 0
        checks = [("pc", r.pc, s.pc), ("insn", r.insn, s.insn),
                  ("trap", r.trap, s.trap), ("rd", r.rd, s.rd),
                  ("rd_wdata", r.rd_wdata, exp_wdata),
                  ("mem_wmask", r.mem_wmask, s.mem_wmask)]
        if s.mem_wmask:  # a store: check where it went and what it wrote
            checks += [("mem_addr", r.mem_addr, s.mem_addr),
                       ("mem_wdata", store_bytes(r.mem_wdata, r.mem_wmask),
                        store_bytes(s.mem_wdata, s.mem_wmask))]
        for field, got, exp in checks:
            if got != exp:
                return (f"first divergence at #{i} (pc 0x{s.pc:x}): {field} "
                        f"RTL=0x{int(got):x} ISS=0x{int(exp):x}")
    if len(rtl) != len(iss):
        return (f"length mismatch: RTL retired {len(rtl)}, "
                f"ISS retired {len(iss)}")
    return None


# ISS (reference) trace of the lesson's 6-instruction program.
ISS = [
    Retire(0x100, 0x00500093, rd=1, rd_wdata=5),   # addi x1, x0, 5
    Retire(0x104, 0x00700113, rd=2, rd_wdata=7),   # addi x2, x0, 7
    Retire(0x108, 0x002081B3, rd=3, rd_wdata=12),  # add  x3, x1, x2
    Retire(0x10C, 0x00302023, mem_addr=0x0, mem_wmask=0xF,
           mem_wdata=12),                          # sw   x3, 0(x0)
    Retire(0x110, 0x00002203, rd=4, rd_wdata=12),  # lw   x4, 0(x0)
    Retire(0x114, 0x00000013),                     # addi x0, x0, 0 (nop)
]


def mutate(i: int, **fields) -> List[Retire]:
    """Copy the ISS trace and inject one RTL bug at retirement i."""
    t = list(ISS)
    t[i] = replace(t[i], **fields)
    return t


CASES = [
    ("clean", list(ISS)),
    ("truncated (hang)", ISS[:3]),
    ("extra retirement", ISS + [Retire(0x118, 0x00000013)]),
    ("empty RTL trace", []),
    ("wrong rd", mutate(2, rd=4)),
    ("store to 0, bad data", mutate(3, mem_wdata=11)),
    ("store to wrong addr", mutate(3, mem_addr=0x4)),
    ("x0 written nonzero", mutate(5, rd_wdata=5)),
]

if __name__ == "__main__":
    caught = 0
    for name, rtl in CASES:
        naive = "PASS" if naive_compare(rtl, ISS) is None else "FAIL"
        result = robust_compare(rtl, ISS)
        caught += result is not None
        robust = f"PASS ({len(rtl)} matched)" if result is None else "FAIL"
        print(f"{name:<21} naive: {naive}   robust: {robust}")
        if result:
            print(f"    {result}")
    print(f"robust compare caught {caught} of {len(CASES) - 1} injected bugs")
```

Notice the order inside `robust_compare`: it compares the common prefix field by field first, and checks the lengths last. A trace that diverges and is also short reports the divergence, which is the earlier and more useful fact.

### The same checks in lock-step: a UVM scoreboard hook

In a real bench the compare runs inside the simulation. This scoreboard follows the Ibex pattern, with a subset of Ibex's calls (the full order is in Push Further). It receives one `rvfi_item` per retirement from the RVFI monitor, forwards events, overrides the cycle counter, steps the ISS and counts. The DPI functions come from Ibex's `dv/cosim/cosim_dpi.svh` (lowRISC/ibex master, fetched 2026-10-11); the ISS behind them is Spike, built from lowRISC's `ibex_cosim` branch.

```systemverilog
// snippet: lock-step hook modelled on Ibex's ibex_cosim_scoreboard (subset of its calls)
`include "uvm_macros.svh"
import uvm_pkg::*;
`include "cosim_dpi.svh"  // Ibex DPI imports: riscv_cosim_step, riscv_cosim_set_mip, ...

class rvfi_item extends uvm_sequence_item;
  bit        irq_only;        // interrupt notification only, nothing retired
  bit [31:0] pc;
  bit [4:0]  rd_addr;
  bit [31:0] rd_wdata;
  bit        trap;            // this instruction raised a synchronous trap
  bit        rf_wr_suppress;  // register write suppressed
  bit        debug_req, nmi, nmi_int;
  bit [31:0] pre_mip, post_mip;
  bit [63:0] mcycle;
  `uvm_object_utils(rvfi_item)
  function new(string name = "rvfi_item");
    super.new(name);
  endfunction
endclass

class rv_cosim_scb extends uvm_scoreboard;
  `uvm_component_utils(rv_cosim_scb)
  // The env connects: mon.ap.connect(scb.rvfi_fifo.analysis_export);
  uvm_tlm_analysis_fifo #(rvfi_item) rvfi_fifo;
  chandle      cosim_handle;  // set by the env; Ibex creates it with spike_cosim_init
  int unsigned n_checked;

  function new(string name, uvm_component parent);
    super.new(name, parent);
  endfunction

  function void build_phase(uvm_phase phase);
    super.build_phase(phase);
    rvfi_fifo = new("rvfi_fifo", this);
  endfunction

  task run_phase(uvm_phase phase);
    rvfi_item t;
    forever begin
      rvfi_fifo.get(t);
      if (t.irq_only) begin
        // An interrupt changed between retirements: update the ISS, check nothing.
        riscv_cosim_set_nmi(cosim_handle, t.nmi);
        riscv_cosim_set_nmi_int(cosim_handle, t.nmi_int);
        riscv_cosim_set_mip(cosim_handle, t.pre_mip, t.pre_mip);
        continue;
      end
      // Forward asynchronous events BEFORE the step, in priority order.
      riscv_cosim_set_debug_req(cosim_handle, t.debug_req);
      riscv_cosim_set_nmi(cosim_handle, t.nmi);
      riscv_cosim_set_nmi_int(cosim_handle, t.nmi_int);
      riscv_cosim_set_mip(cosim_handle, t.pre_mip, t.post_mip);
      // Override what an instruction-accurate ISS cannot know.
      riscv_cosim_set_mcycle(cosim_handle, t.mcycle);
      if (!riscv_cosim_step(cosim_handle, t.rd_addr, t.rd_wdata, t.pc,
                            t.trap, t.rf_wr_suppress))
        `uvm_fatal("COSIM", $sformatf("mismatch at pc 0x%08h: %s", t.pc,
                                      cosim_errors()))
      n_checked++;
    end
  endtask

  function string cosim_errors();
    string s;
    for (int i = 0; i < riscv_cosim_get_num_errors(cosim_handle); i++)
      s = {s, riscv_cosim_get_error(cosim_handle, i), "\n"};
    riscv_cosim_clear_errors(cosim_handle);
    return s;
  endfunction

  function void check_phase(uvm_phase phase);
    // A hung core retires nothing and causes no mismatch: count instead.
    if (n_checked == 0)
      `uvm_error("COSIM", "no retired instruction was compared")
  endfunction

  function void report_phase(uvm_phase phase);
    `uvm_info("COSIM", $sformatf("matched %0d instructions", n_checked), UVM_LOW)
  endfunction
endclass
```

What the code is for, line by line:
- The `irq_only` branch handles an interrupt that changed while nothing retired. Ibex's RVFI reports such events in order with the retirements, so the ISS can prioritise interrupts that arrive close together.
- The forwarding calls come before `riscv_cosim_step`, because the ISS takes any pending interrupt at the start of the step.
- `riscv_cosim_set_mcycle` copies the RTL's cycle count into the ISS, so a `csrr` of `mcycle` compares equal.
- `check_phase` turns "nothing compared" into an error. It complements, and does not replace, the test's fatal cycle timeout.

### How-to: set up an ISS compare for a new core

1. **Pin every tool version.** Record the riscv-dv, ISS and toolchain commits in the regression log. Tool behaviour changes between commits.
2. **Make the ISS configuration match the core**, from the same source of truth as the RTL parameters. riscv-dv runs Spike as `spike --log-commits --isa=<variant> --priv=<priv> --misaligned -l <elf>` (from `yaml/iss.yaml`): the ISA string, the privilege modes and the misaligned-access policy are the usual sources of false mismatches.
3. **Describe the core to the generator:** copy a target directory, edit `riscv_core_setting.sv`, and run with `--custom_target <dir> --isa <isa> --mabi <mabi>`.
4. **Generate and build:** `run --test <test> --iss spike --steps gen,gcc_compile` (or let `--steps` default to all).
5. **Run the ISS and the RTL** on the same ELF. Give the RTL a fatal cycle timeout and an end-of-test detector.
6. **Compare:** post-run for tests without asynchronous events; lock-step for interrupt, debug and bus-error tests.
7. **Collect coverage** from the RTL retirement port, and merge it across seeds.
8. **Triage the first divergence only**, with the table below.

| Symptom | Likely cause | Fix |
|---|---|---|
| Mismatch at the first instruction of a handler | Interrupt, NMI or debug request not forwarded | Forward its state before the step |
| A `csrr` of `mcycle` or a performance counter mismatches every run | The ISS cannot model cycles | Override the counter before the step, or keep counter reads out of compared tests |
| Test times out with no mismatch | The core hung; nothing retired | Fatal cycle timeout, end-of-test handshake, matched count |
| Illegal-instruction trap in the ISS only | ISS ISA string differs from the core | Generate the ISS options from the core configuration |
| Misaligned load traps on one side only | Misaligned policy differs | Match the ISS option (Spike `--misaligned`) to the core |
| Load value mismatch after a bus error | The ISS did not know about the error | Notify the access and its error before the step |
| Post-run compare reports PASS with 0 matched | The compare compared nothing | Fail on zero matched; check which compare mode ran |

## Push Further

### Expert: Lock-step co-simulation in a production UVM bench

Ibex's `ibex_cosim_scoreboard` (lowRISC/ibex master, `dv/uvm/core_ibex/common/ibex_cosim_agent/ibex_cosim_scoreboard.sv`, fetched 2026-10-11) extends `uvm_scoreboard` and reads RVFI items from a `uvm_tlm_analysis_fifo`. Before each step it calls, in this order: `riscv_cosim_set_debug_req`, `riscv_cosim_set_nmi`, `riscv_cosim_set_nmi_int`, `riscv_cosim_set_mip(pre_mip, post_mip)`, `riscv_cosim_set_mcycle`, `riscv_cosim_set_csr` for each of ten `mhpmcounter` registers and their high halves, and `riscv_cosim_set_ic_scr_key_valid`; then `riscv_cosim_step(rd_addr, rd_wdata, pc, trap, rf_wr_suppress)`. The source comment explains the order: debug, NMI and normal interrupts must be handled "with the correct priority when they occur together". On a mismatch it calls `uvm_fatal`, unless the configuration's `relax_cosim_check` downgrades it to `uvm_info`. Separate threads notify every data-side access and instruction-fetch bus errors. The co-simulation documentation states that only VCS is supported as the simulator, though no VCS-specific feature is needed (tool-dependent).

### Expert: A nondeterminism policy: forward, override, notify, exclude

Every value the ISS cannot derive from the program needs one of four treatments, decided once per bench and written in the verification plan (source: Ibex `doc/03_reference/cosim.rst`, sections "Trap Handling", "Interrupts and Debug Requests", "Memory Access Checking and Bus Errors").

| Treatment | Applies to | Mechanism in Ibex |
|---|---|---|
| Forward | Interrupt lines, NMI, debug request | `set_mip`, `set_nmi`, `set_debug_req` before the step; interrupt-only RVFI items between retirements |
| Override | `mcycle`, performance counters | RVFI was extended with `rvfi_ext` signals, and the values are written into the ISS before the step |
| Notify | Data-side accesses and their bus errors | `notify_dside_access` before the ISS performs the access |
| Exclude | Speculative instruction fetches | Not compared directly; only fetch errors that cause a fault are notified (`set_iside_error`) |

The documentation also notes that a co-simulated Spike "doesn't produce matching performance counters", so software that dumps counters must be built with that dump disabled. Anything you exclude is unverified by the compare; cover it with assertions or a dedicated test.

### Expert: Post-run versus lock-step, and what riscv-dv's compare actually does

Post-run needs no DPI integration and works with any ISS that writes a log; lock-step finds the first divergence while the simulation is still running and can follow asynchronous events. riscv-dv's interrupt and debug tests (`riscv_full_interrupt_test` and others in `yaml/base_testlist.yaml`) set `+compare_final_value_only=1`. In `scripts/instr_trace_compare.py` at riscv-dv master (fetched 2026-10-11), that option turns off the in-order compare, and the final-value compare it should select is a commented-out TODO. The script then reports `[PASSED]: 0 matched`. Read the matched count of every compare you rely on, and treat zero as a failure. Cores with their own lock-step bench (Ibex) do not depend on this path.

### Expert: What a riscv-formal pass guarantees

From `docs/source/procedure.rst` (YosysHQ/riscv-formal main, fetched 2026-10-11): the tests "might be set up as bounded model checks or as unbounded verification tasks"; checks generated by `genchecks.py` are bounded model checks run with SymbiYosys; the configuration's `mode` accepts `bmc` or `prove` and defaults to `bmc`; each check's bound comes from the `[depth]` section. So state results as "insn checks pass to depth N in bmc mode", never as "ISA-compliant". Three further limits: under `RISCV_FORMAL_ALTOPS` the M-extension results are stand-in operations (`rvfi.rst`, "Alternative arithmetic operations"); the README calls the project "work in progress" with interfaces "likely to change"; and properties are written as immediate assertions "for maximal compatibility with other tools", so running them in a commercial formal tool is possible but tool-dependent.

### Expert: Multi-retire cores and reordered retirement

RVFI has `NRET` channels, one per instruction a core can retire in a cycle; if two retirements in one cycle write the same register, the higher channel wins. Retirement may even be reordered "as long as causality is preserved" (`rvfi.rst`). A trace compare that assumes one retirement per cycle, in program order, breaks on such cores. Sort by `rvfi_order` before comparing, and decide how to treat same-cycle writes to one register. riscv-dv's `instr_trace_compare.py` has an out-of-order mode for cores that commit several instructions per cycle, but at master it is a commented-out TODO. Speculative cores add a rollback interface (`rvfi_rollback_valid`, `rvfi_rollback_order`) that invalidates earlier packets, so a monitor must buffer until a retirement can no longer be rolled back.

### Expert: Trusting ISA coverage

Three questions decide whether a coverage number means anything. Where was it sampled (an ISS trace measures the program; the RTL retirement port measures the core)? Which ISS produced the trace (riscv-isac's quickstart warns that Spike omits trapping instructions and recommends Sail)? And does a trapping instruction count (ACT4 covergroups guard each coverpoint with `iff (ins.trap == 0)`)? Also remember that riscv-isac is archived, so new projects increasingly write coverage as SystemVerilog covergroups, the form ACT4 generates, and sample them from a UVM subscriber on the RVFI monitor.

### Expert: Generator realities in riscv-dv

Read the generator before you trust a distribution. In `src/isa/riscv_instr.sv`, `get_rand_instr` picks uniformly among the allowed instruction names, so the mix of categories follows how many mnemonics each category has unless directed streams shift it. `+dist_control_mode` and `+dist_<category>` options are parsed in `riscv_instr_gen_config.sv` and copied into the stream's `category_dist`, but the random-instruction call in `riscv_instr_stream.sv` passes no distribution argument (riscv-dv master, fetched 2026-10-11), so do not rely on them without checking your pinned commit. riscv-dv's README requires a simulator with "SystemVerilog and UVM 1.2" support; whether it runs on uvm-core 2020.3.1 is tool-dependent.

### Expert: The verification-interface landscape

RVFI is the retirement interface riscv-formal defines. **RVVI** (RISC-V Verification Interface, `riscv-verification/RVVI`) is a draft open standard for lock-step processor DV, which its README describes as "a superset of RVFI": RVVI-TRACE (version 1.7, SystemVerilog) for the core's trace, RVVI-API (version 1.37, C/C++ with a DPI wrapper) for the reference model, and RVVI-VVP for virtual peripherals such as interrupt generators. The README lists Synopsys ImperasDV and the OpenHW Group's CV32E40X verification as users. Choosing RVVI over a home-grown interface buys reusable reference-model and coverage components; choosing RVFI keeps the formal flow open.

# snippet: add to the worked example's script
END_PC = 0x114  # address of the program's last instruction


def accounted_compare(rtl, iss, end_pc):
    """robust_compare, plus: the reference itself must reach the end."""
    if iss and iss[-1].pc != end_pc:
        return (f"reference did not finish: last ISS pc 0x{iss[-1].pc:x}, "

In a riscv-dv flow the real end marker is the program's end-of-test code (the `test_done` section ends in `ecall` and then `write_tohost`), so check that the ISS log reaches it.

Part C: probably not an RTL bug. The ISS never heard about the interrupt, so any post-run compare diverges at the handler's first instruction. Either run interrupt tests in lock-step with the interrupt forwarded before the step, or fall back to a weaker end-state check and accept that it cannot locate a bug. The `mcause` value `0x80000007` (interrupt bit set, code 7, machine timer) confirms the cause.

### Kata 2: an interrupt-injection test plan

Write the test plan for the interrupt logic of an RV32 core with machine mode only, three local interrupts (machine external, software and timer), an NMI and a debug request, and a lock-step bench. Fill in a table with one row per scenario: interrupt source, timing point, what the bench forwards and when, what you check, and the coverage cross that proves you ran it. Include at least: an interrupt during a multi-cycle divide; one between a taken branch and its target; one while `mstatus.MIE` is 0 that becomes taken when software sets it; two interrupts pending at once; an interrupt in the same cycle as a synchronous exception; and a debug request together with an interrupt.

<details>
<summary>Worked solution</summary>

| Scenario | Timing point | Forward (before the step) | Check | Coverage |
|---|---|---|---|---|
| Timer interrupt during `div` | While the divide is in progress | `set_mip` with MTIP | Handler entry; `mepc` is the `div` (if the core abandons it) or the next instruction; `mcause = 0x80000007` | interrupt × instruction category |
| External interrupt after a taken branch | Between the branch and its target | `set_mip` with MEIP | `mepc` = branch target, not branch + 4 | interrupt × previous instruction was a taken branch |
| Pending while `mstatus.MIE = 0` | Raised, then software sets MIE | `set_mip` each retirement it stays pending | No trap before the `csrs` that sets MIE; trap right after | MIE 0 then 1 × source |
| Two at once | MEIP and MTIP in the same cycle | `set_mip` with both bits | External taken first (M-mode priority is MEI, MSI, MTI) | pending pair × taken source |
| Interrupt with a synchronous exception | Same cycle as an illegal instruction | `set_mip`; the trap flag goes in the step | The core and the ISS agree on which trap is taken first | sync cause × interrupt source |
| Debug request plus interrupt | Same cycle | `set_debug_req`, then `set_mip` (Ibex order: debug, NMI, NMI_INT, mip) | Core and ISS enter the same handler; the forwarding order lets the ISS apply the core's priority | debug × interrupt |
| NMI | Any point, including inside a handler | `set_nmi` | NMI vector entered whatever the interrupt-enable bits; `mepc` is the interrupted instruction | NMI × handler nesting |

Also plan the end: every test ends with a fatal cycle timeout and an end-of-test handshake, and `mret` returns are checked against `mepc`. Sources: the M-mode interrupt priority order is in the privileged specification's "Machine Interrupt (mip and mie) Registers" section; the forwarding order is Ibex's (`ibex_cosim_scoreboard.sv`).

</details>

### Debug challenge: the counter that never matches

A colleague's lock-step log shows `UVM_FATAL ... mismatch at pc 0x00000a44` in every test that calls a timing routine. The instruction at `0xa44` is `csrr a0, mcycle`. They have opened an RTL bug against the CSR file. What do you tell them, and what do you change?

<details>
<summary>Worked solution</summary>

`mcycle` counts clock cycles of the RTL; the ISS is instruction-accurate and has no clock, so its value can never match by itself. It is not an RTL bug. Copy the RTL's value into the ISS before each step (`riscv_cosim_set_mcycle` in the Ibex DPI), do the same for performance counters (`riscv_cosim_set_csr`), or keep counter reads out of compared tests. Check the counters' own behaviour separately, with assertions or a directed test.

</details>
