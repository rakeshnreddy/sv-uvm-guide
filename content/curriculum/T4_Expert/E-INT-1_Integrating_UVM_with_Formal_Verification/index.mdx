## Quick Take
- **What it is:** A partnership between UVM simulation and formal tools using shared assertions, interface assumptions, and coverage targets.
- **Why it matters:** Simulation finds deep data-path bugs; formal proves corner-case safety. Together they close gaps faster than either technique alone.
- **The Analogy:** Imagine mission control (UVM) running real-time rehearsals while a mathematical twin (formal) proves the mission profile safe under every scenario.

> **Signal:** When UVM tests add endless directed scenarios to hit corner cases, formal proofs can slash effort if assertions already exist.

## Build Your Mental Model

### Assertions as the bridge

SystemVerilog Assertions (SVA) become the common artefact: `assert` in simulation, `prove` in formal, `cover` for reachability/coverage. The **same property library** serves both flows—no duplicate specification, no semantic drift.

  (input logic clk, rst_n, push, pop,
   input logic [$clog2(DEPTH):0] count,
   input logic full, empty);

  // Safety property
  property p_full_is_correct;
    @(posedge clk) disable iff (!rst_n)
      (count == DEPTH) |-> full;
  endproperty
  assert property (p_full_is_correct);

  // Assumption: constrains formal, checked in simulation
  property p_legal_transactions;
    @(posedge clk) disable iff (!rst_n)
      !(push && full) && !(pop && empty);
  endproperty
  assume property (p_legal_transactions);

## Formal Harness Architecture

Building a formal testbench from an existing UVM environment requires stripping the RTL down to a small cone of logic and replacing UVM agents with formal assumptions.

### From UVM env to formal harness

| UVM Component | Formal Equivalent | Notes |
|---|---|---|
| Driver + Sequencer | Free inputs + `assume` properties | Assumptions written from the interface specification replace constrained stimulus; formal explores every input they allow |
| Monitor | Not needed | Formal engines observe all signals natively |
| Scoreboard | `assert` properties | Correctness is expressed as SVA, not procedural checks |
| Coverage | `cover` properties | Reachability proofs replace sampling-based coverage |
| Config/Factory | Parameters | Formal harnesses are statically parameterized |

### Building the harness step by step

1. **Isolate the DUT block** — formal scales best on small blocks with a well-defined interface and shallow state. Extract the block you want to prove.
2. **Declare free inputs** — inputs left undriven become unconstrained; the formal engine explores all possible values.
3. **Add assumptions** — restrict free inputs to what the interface specification (or the upstream block) guarantees. If the interface already has protocol assertions, reuse those properties as `assume`. Sequence constraints can suggest rules, but they are not equivalent to assumptions (see below).
4. **Assert safety properties** — these are the same properties your UVM assertions check in simulation.
5. **Add cover properties** — verify that interesting states are reachable under your assumptions.
6. **Bind the property module** — use `bind` so the same checkers attach in both simulation and formal without modifying the DUT.

> ⚠️ **Over-constraining is the #1 formal pitfall.** If your assumptions are tighter than what the real environment produces, the formal engine cannot find real bugs. Audit each assumption against the interface specification, not against the UVM driver: a driver can be wrong too, and copying its habits imports testbench bugs into the proof. Add a `cover` for each behaviour an assumption must still allow.

## Assumption Alignment

### Constraints and assumptions: related, not equivalent

A sequence-item constraint and a formal assumption can describe the same rule, but they act at different times and on different data. Before you read the explanation, predict which of the three constraints below would be safe to turn into an assumption:

<InteractiveCode
  language="systemverilog"
  fileName="constraint_vs_assumption.sv"
  code={`// UVM sequence item: stimulus for ONE transaction, solved before it is driven
class fifo_txn extends uvm_sequence_item;
  rand bit push, pop;
  bit      full_seen, empty_seen; // copied in by the sequence before randomize()

  constraint c_legal {
    full_seen  -> !push;          // the flags as the sequence last saw them
    empty_seen -> !pop;
  }
  constraint c_one_op { !(push && pop); } // this test's choice, not an interface rule
endclass

// Interface rule: evaluated at every clock edge, on the live signals
property a_legal_push;
  @(posedge clk) disable iff (!rst_n)
    full |-> !push;
endproperty
assume property (a_legal_push);

property a_legal_pop;
  @(posedge clk) disable iff (!rst_n)
    empty |-> !pop;
endproperty
assume property (a_legal_pop);`}
  explanationSteps={[
    { target: "6-9", title: "Constraint: decided once per item", explanation: "`c_legal` is solved when the sequence calls `randomize()`. The flags hold whatever the sequence copied in at that moment, and the item may reach the pins cycles later, after `full` has changed. The rule it hints at is real; the constraint cannot enforce it per cycle." },
    { target: "10", title: "Test intent, not a rule", explanation: "`c_one_op` shapes this test's traffic. As an assumption it would forbid simultaneous push and pop, and every bug that needs both would become unreachable: an over-constraint." },
    { target: "13-24", title: "Assumption: applies at every clock", explanation: "The rule comes from the interface specification and holds on the live signals at every edge, however late an item is driven. Simulation checks the same `assume` like an assertion (IEEE 1800-2023 §16.14.2), so a testbench that breaks it is reported." }
  ]}
/>

Constraints can inspire assumptions, but they are not automatically equivalent:
- Constraints are solved per transaction, ahead of time; they cannot see cycle-level DUT state.
- Drivers implement protocol rules (handshakes, timing) that never appear in any constraint.
- Many constraints express test intent (biases, narrowed ranges) that would over-constrain a proof.

So write assumptions from the interface specification, per clock, on the signals at the DUT boundary. The best source is the interface's own protocol assertions: the same properties are asserted where the DUT drives a signal and assumed where the environment drives it.

### Common assumption pitfalls

| Pitfall | Symptom | Fix |
|---|---|---|
| **Over-constraining** | Everything proves, but bugs exist in silicon | Audit each assumption against the interface specification; add a `cover` for each behaviour it must still allow |
| **Under-constraining** | Spurious CEX: the trace uses an input sequence the real environment never produces | Add the missing assumption from the specification; replay the CEX in simulation to confirm |
| **Vacuous proofs** | Property passes but antecedent is never true | Add a cover property for the antecedent; verify reachability |
| **Assumption/assertion confusion** | Properties accidentally assumed instead of asserted | Review property directives; use linting tools |

## Counterexample Replay

When a formal engine finds a counterexample trace, that trace is a witness **relative to your assumptions**: a real bug if every input in it is legal, or a missing assumption if it is not. Replaying it in UVM, where the same `assume` properties are checked like assertions (IEEE 1800-2023 §16.14.2), tells you which. Converting a genuine one into a directed UVM test closes the formal→simulation feedback loop.

### The replay workflow

1. **Export the CEX** — formal tools produce VCD, FSDB, or waveform databases. Extract signal values per cycle.
2. **Build a directed sequence** — create a UVM sequence that replays the exact input values from the CEX trace. This works only if the driver applies one item per clock with the trace's timing; otherwise drive the trace values directly from a small directed testbench.
3. **Run in UVM** — execute the directed sequence in your full UVM environment to reproduce the bug with full scoreboard and coverage instrumentation.
4. **Debug with waveforms** — use the familiar simulation debug flow to root-cause the failure.
5. **Verify the fix** — re-run formal to confirm the property now proves, then add the CEX-derived test to your regression suite as a permanent guard.

## Workflow Alignment

### Plan and map
Link requirements to both UVM scenarios and formal proof goals; track progress in a shared dashboard.

### Share rules, not constraints
Keep interface rules as properties in one library: assumed by formal, checked by simulation. Use sequence constraints only as a prompt for which rules to write, never as a mechanical translation.

### Swap drivers
Replace expensive UVM drivers with lightweight formal stubs when building formal harnesses; reuse monitors for scoreboarding.

### Handshake results
Feed proven properties back into UVM (waive unreachable coverage bins) and use formal counterexamples as directed UVM seeds.

## Make It Work
1. **Property library:** Store assertions in reusable packages with consistent naming; annotate each with owner and coverage intent.
2. **Unified run scripts:** Provide make/CI targets that run UVM regressions and formal proofs using shared config files (JSON/TOML).
3. **Result exchange:** Automate export of formal counterexamples to VCD/FSDB for UVM replay; import UVM coverage to identify assertions needing refinement.
4. **Governance:** Define approval checkpoints—e.g., a feature closes only when directed UVM test, coverage, and formal proof all pass.

**Checklist before moving on:**
- [ ] Assertions live in one library consumed by both simulation and formal flows.
- [ ] Formal assumptions come from the interface specification, and simulation checks the same properties.
- [ ] Counterexample-to-testcase scripts exist.
- [ ] Dashboards track both formal proof depth and UVM coverage.

## Push Further
- **Coverage unification:** Merge formal `cover` hits into your UVM coverage database to show complete progress.
- **Formal smoke tests:** Add short bounded proofs to CI so critical properties break builds immediately.
- **Proof planning:** Categorize properties by difficulty and schedule compute resources accordingly.
- **Training:** Run joint UVM+formal debug workshops so teams can interpret counterexamples and waveform evidence quickly.
- **Portable Stimulus:** See [PSS: Portable Stimulus](/curriculum/T4_Expert/E-SOC-1_SoC-Level_Verification_Strategies/pss) for how intent-based test descriptions extend across simulation, emulation, and silicon.
