## Quick Take

- **What it is:** One library of SystemVerilog Assertions (SVA), bound to the design under test (DUT) and read by two engines. A **simulator** checks the properties on the stimulus your UVM testbench happens to run. A **formal tool** reads the same RTL and properties and analyses *every* input sequence that the `assume` properties allow, starting from reset, so it either proves a property or returns a **counterexample** (CEX): a trace from reset that makes it fail.
- **Why it matters:** Formal reaches corner cases that random stimulus rarely hits, such as "four pushes in a row, then check the flag". Simulation reaches deep, multi-block and software-driven scenarios, and it checks that the formal assumptions hold in the real environment. Each engine covers the other's blind spot only if both use the same properties and the assumptions are honest.
- **The Analogy:** Formal is a building inspector who checks every room on the floor plan; simulation is a fire drill run in the real building. *Where it breaks:* the inspector trusts the plan. A room left off the plan is never inspected (an **over-constraining** assumption hides a bug), and a door drawn by mistake creates hazards that do not exist (an **under-constraining** assumption gives a spurious counterexample). The fire drill, unlike the inspector, only visits the rooms people happen to walk through.

**You will be able to:**
1. **Explain** what `assert`, `assume`, `cover` and `restrict` mean to a simulator and to a formal tool, and **predict** how adding or removing an assumption changes a proof result.
2. **Build** a formal harness from an interface checker: bind it to the DUT, assume the inputs the environment drives, assert and cover the outputs, and add covers that expose over-constraint.
3. **Explain** why a sequence-item constraint is not an assumption, and **diagnose** over-constraint (vacuous proofs, unreachable covers) and under-constraint (spurious counterexamples).
4. **Triage** a counterexample against the interface specification, **replay** it in UVM, and **decide** whether it is a design bug or an assumption gap.
5. **Plan** a hybrid flow: **choose** which properties go to formal and which to simulation, and report each result as proven, bounded to depth N, counterexample, covered or unreachable.

## Build Your Mental Model

This lesson uses one small design throughout: the control block of a 4-entry FIFO. It has two inputs, `push` and `pop`, driven by whoever uses the FIFO (the **environment**), and three outputs computed by the DUT: an occupancy `count`, and the flags `full` and `empty`. The storage array is left out because no property here needs it. The same design runs inside the `FormalVsSimulationVisualizer` further down, so every number on this page can be checked there.

### What formal verification does

Start with words you already know from simulation and add five new ones.

- The DUT's **state** is the value of all its flip-flops; here, `count` (and, in the buggy version, a registered `full`). After reset the state is known: `count == 0`.
- A **free input** is an input the formal tool may set to any value at every clock edge. Here `push` and `pop` are free: they are input ports of the block the tool analyses.
- A **reachable state** is a state that some sequence of input values can lead to from reset. Simulation visits the reachable states its stimulus happens to drive through; formal reasons about all of them.
- A **proof** of an assertion means: no input sequence the assumptions allow, starting from reset, makes it fail.
- A **counterexample (CEX)** is a trace (input values and sampled outputs, edge by edge from reset) that obeys every assumption in force and makes an assertion fail. A **witness** is the same kind of trace for a `cover`: it shows the covered behaviour happening.

Formal tools look only at the logic that can affect a property, its **cone of influence**: the signals in the property plus everything that feeds them, back to the free inputs. The tool computes the cone; you choose the block boundary.

The picture below shows the whole reachable-state space of the FIFO counter under the interface contract "never push while full, never pop while empty". Formal explores this graph from reset, along every edge the assumptions allow. The second row shows what happens when someone adds a wrong assumption that forbids pushing into the last free slot: the edge into `count = 4` disappears, and with it every behaviour that needs a full FIFO.

Two consequences follow, and the rest of the lesson builds on them:
- **A proof is only as good as its assumptions.** Formal proves "no failure in the states I can reach". If an assumption cuts away states the real environment can reach, the proof says nothing about them.
- **A counterexample is relative to the assumptions.** If the assumptions are too loose, formal can reach states the real environment never produces, and the CEX describes a situation that cannot happen.

Formal does not replace simulation. It works best on blocks of modest size with deep corner cases; it struggles with large datapaths and long end-to-end flows. Choosing between the two is the last section of this lesson. For the general choice of verification methods, see [F1B: The Verification Mindset](/curriculum/T1_Foundational/F1B_The_Verification_Mindset/index).

### One property library, two engines

The design is checked by one property module, `fifo_props`, attached to the DUT with `bind`. You met `bind` in [I-SV-4C](/curriculum/T2_Intermediate/I-SV-4C_Checkers/index): it instantiates a module, interface, program or checker inside a target module without editing the target's source (IEEE 1800-2023 §23.11). Both engines elaborate the same bound module, so they check the same lines.

```systemverilog
// snippet: the heart of fifo_props (the full file is in Make It Work)
default clocking @(posedge clk); endclocking
default disable iff (!rst_n);

// The interface contract: what the environment promises
a_no_push_when_full: assume property (!(push && full));
a_no_pop_when_empty: assume property (!(pop && empty));

// Obligations on the DUT
p_count_in_range:    assert property (count <= DEPTH);
p_full_is_correct:   assert property ((count == DEPTH) |-> full);

// Behaviour the assumptions must still allow
c_reach_depth:       cover  property (count == DEPTH);
c_push_pop:          cover  property (push && pop);
```

Every statement has a **label** (`a_no_push_when_full:`). The label gives the assertion a hierarchical name, such as `tb_top.dut.u_fifo_props.p_full_is_correct`, which reports, assertion-control tasks and formal-tool commands can refer to. Unlabelled assertions get a tool-chosen name, which is harder to track. The names used here are the names the visualizer uses.

The same line means different things to the two engines. IEEE 1800-2023 §16.2 lists four kinds of concurrent assertion statement:

| Statement | What a simulator does | What a formal tool does | Clause |
|---|---|---|---|
| `assert property` | Evaluates an attempt at every clock edge; on failure runs the `else` action, or calls `$error` if there is none | Treats it as a **proof obligation**: reports proven, a CEX, or a bounded or undetermined result | §16.14.1, §16.2 |
| `assume property` | **Checks it and reports a failure, just like an assertion.** It does not stop your UVM driver from breaking it | Treats it as a **hypothesis**: explores only traces that satisfy it and never checks it ("there is no obligation to verify that the assumed properties hold") | §16.14.2 |
| `cover property` | Counts attempts, successes, and successes that were vacuous | Searches for a witness trace: **covered** at some edge, or **unreachable** | §16.14.3 |
| `restrict property` | **Ignores it.** It is not checked and has no action block | Constrains the analysis exactly like `assume` | §16.14.4 |

Read the `assume` row twice, because the two most common misunderstandings live there. In simulation an `assume` is a check: if your testbench pushes while `full` is 1, the simulator reports `a_no_push_when_full` failing (some tools can also generate stimulus from assumptions; that is tool-dependent). In formal an `assume` is a filter on the inputs: the tool never tries a trace that breaks it, so it can never report it failing.

`restrict` exists for constraints that are deliberately *not* true of the environment, such as analysing one operating mode per formal run. The standard's example restricts an ALU's control bit to "add" for one session and to "subtract" in another (§16.14.4):

```systemverilog
// snippet: one formal session analyses addition only; simulation is unaffected
r_add_only: restrict property (@(posedge clk) ctr == '0);
```

If you wrote this as an `assume`, every simulation that exercised subtraction would report a failure.

**Where properties can live.** Concurrent assertions belong in modules, interfaces and programs (§16.14.5), in checkers (Clause 17), and inside `always` or `initial` procedures as procedural concurrent assertions (§16.14.6). They cannot do useful work in a class: expressions in a concurrent assertion "shall not reference non-static class properties or methods" (§16.6). That is why a UVM monitor or scoreboard, which are classes, cannot be part of a formal harness. Formal tools also read only synthesizable RTL plus SVA; which constructs each tool accepts is tool-dependent.

**One library does not mean identical semantics.** The standard itself warns that tools using cycle-based evaluation can behave differently from event-based simulation in some scenarios (§16.2). X values, the initial state before reset, delays and `initial` blocks in the RTL are the usual sources of difference; the Push Further item [Where simulation and formal disagree](#expert-where-simulation-and-formal-disagree) lists them.

**Classic mistake: assuming a DUT output.** An `assume` on a signal the DUT drives, such as `assume property ((count == DEPTH) |-> full)`, tells formal to ignore every trace in which the DUT gets `full` wrong. The matching assertion then "proves", and the bug is hidden. Rule: assume only signals the environment drives; assert the signals the DUT drives.

### Reading a formal result: bounded and full proofs

A formal run returns one status per property. Exact names differ by tool (tool-dependent), but the meanings are these:

| Status | Meaning | Is it a proof? |
|---|---|---|
| **Proven** | No allowed input sequence from reset violates the assertion, at any depth | Yes, relative to the assumptions |
| **Bounded to depth N** | No violation in any allowed sequence through edge N; nothing is known beyond | No |
| **Counterexample at edge k** | A concrete trace from reset, obeying every assumption, fails at edge k | It disproves the property, relative to the assumptions |
| **Covered at edge k** | A witness trace reaches the cover at edge k | It shows the behaviour is reachable |
| **Unreachable** | No allowed sequence ever reaches the cover | It shows the behaviour is impossible under the assumptions |
| **Undetermined** | The tool ran out of time or memory | No |

This lesson counts edges from 0, the first rising clock edge after reset is released, and uses the values sampled at each edge (§16.5.1). A **bounded run to depth N** checks every allowed input sequence through edge N. Tools count from 0 or from 1 and call the bound "depth", "cycles" or "steps" (tool-dependent), so check the convention before you compare numbers.

Bounded runs are often all a tool can finish on a large design, and they are useful: they find shallow bugs fast. But a bounded pass is not a proof. The timing diagram shows why, with the late-flag bug you will meet in the visualizer: `full` is a register that copies `count == DEPTH` one edge late.

Notice the warning sign in the bounded run: the cover `c_reach_depth` was not reached within the bound. A bound that never fills the FIFO cannot test anything about a full FIFO. A practical rule follows: **choose a bound at least as deep as your deepest cover**. That rule is a heuristic, not a guarantee. Only a full proof, or a bound at least as deep as the longest shortest path to any reachable state (the design's sequential depth), covers every reachable state.

### Building a harness: what carries over from the UVM environment

A **formal harness** is the formal tool's equivalent of a testbench: the DUT, the assumptions on its inputs, the assertions and covers on its outputs, and any small modelling code they need. You do not translate the UVM environment class by class. Most of it is class code, which a formal tool cannot read (§16.6), and most of it is not needed: formal supplies its own stimulus and reads every signal directly. What carries over is the properties.

| UVM part | In the formal harness | Why |
|---|---|---|
| Sequencer, sequences, driver | Free inputs, filtered by `assume` properties written from the interface specification | Formal generates its own stimulus; the assumptions say what is legal |
| Monitor | Not carried over. Its protocol rules, if they are SVA in the interface or a checker, carry over as bound assertions | The tool reads signals directly; a class cannot hold a useful concurrent assertion (§16.6) |
| Scoreboard | Assertions on outputs, plus a small auxiliary model where the check needs memory (see [Symbolic data](#expert-symbolic-data-with-constant-free-variables)) | Transaction-level checks must be re-expressed on signals |
| Covergroups | `cover property` statements for the scenarios that matter | They complement sampled coverage; they do not replace it |
| Configuration, factory | Parameters | The harness is elaborated once, statically |

**How to build one, step by step:**
1. **Choose the block boundary.** Pick a block with a well-defined interface and modest state: a FIFO controller, an arbiter, a protocol FSM. Make its inputs the input ports of the top the formal tool reads, so they are free. (Whether an undriven internal signal is treated as free is tool-dependent; ports are not.)
2. **State reset.** Tell the tool which signal is the reset and its active level; the analysis starts from the reset state. The command is tool-dependent.
3. **Assume the environment's rules**, written per clock from the interface specification. The best source is the interface's own protocol checker (next paragraph). Never copy sequence constraints mechanically (next section).
4. **Assert the DUT's obligations** on its outputs: the same properties simulation checks.
5. **Cover what the assumptions must still allow**: one cover per assumption for a behaviour it must not forbid, plus a cover for the **antecedent** of each implication (its left-hand side, the condition that must hold before the check applies).
6. **Bind** the property module to the DUT, passing parameters through: `bind fifo fifo_props #(.DEPTH(DEPTH)) u_fifo_props (.*);`. Parameters and ports in a bind resolve in the target's scope (§23.11), so `DEPTH` means the FIFO's own `DEPTH`. A hard-coded `#(.DEPTH(8))` would silently check the wrong depth on a FIFO of any other size.

**One rule, two directives.** An interface rule constrains whoever drives the signal. When you verify the FIFO, the environment drives `push`, so the rule is an assumption. When you verify the block that *produces* `push`, the same rule is an obligation on that block. Write the rule once and choose the directive by parameter:

```systemverilog
// compile
module fifo_push_rule_chk #(parameter bit ASSUME_IT = 1'b1) (
  input logic clk, rst_n, push, full
);
  default clocking @(posedge clk); endclocking
  default disable iff (!rst_n);
  // Assume where the environment drives push (the FIFO's harness);
  // assert where the block under test drives it (the producer's harness).
  if (ASSUME_IT) begin : g_env_drives
    a_no_push_when_full: assume property (!(push && full));
  end else begin : g_dut_drives
    a_no_push_when_full: assert property (!(push && full));
  end
endmodule
```

Proving a block under an assumption, then proving that assumption as an assertion on the block that drives the signal, is called **assume-guarantee** reasoning. The same properties can also live in a `checker` instead of a module; you can bind a checker too (§23.11), and you need a checker when the harness uses free variables (Push Further).

In summary:
- Constraints are solved per item, ahead of time; they cannot see the DUT's state at the edge where the item is applied.
- Drivers implement protocol timing (handshakes, idle cycles) that appears in no constraint.
- Many constraints are test intent: biases, narrowed ranges, "one operation at a time". As assumptions they over-constrain the proof.
- A `dist` bias inside an `assume` only steers random simulation. In formal, "the properties that are assumed shall hold in the same way with or without biasing", and in an `assert` or `cover` a `dist` is treated like `inside` with the weights ignored (§16.14.2). Test biases never belong in assumptions.

Checker **free variables** (checker variables declared `rand`, which formal treats as "any value the assumptions allow") are the closest SystemVerilog gets to "constraints inside the harness": a simulator re-solves the checker's assumptions at each of their clock events, with no `randomize()` call, whereas class constraints are solved only when `randomize()` is called (§17.7.2). See [I-SV-4C: free variables](/curriculum/T2_Intermediate/I-SV-4C_Checkers/index#expert-free-variables-assume-sets-and-formal).

So write assumptions from the **interface specification**, per clock, on the signals at the DUT boundary. Constraints are only a prompt for which rules to look up. Audit each assumption against the specification, not against the UVM driver: a driver can be wrong too, and copying its habits imports testbench bugs into the proof. See [I-SV-2A](/curriculum/T2_Intermediate/I-SV-2A_Constrained_Randomization_Fundamentals/index) if you need a refresher on how constraints are solved.

### Over-constraint, vacuity and sanity covers

An assumption that forbids something the real environment does is an **over-constraint**. Formal then never looks at those behaviours, and properties that depend on them prove for the wrong reason.

The sharpest form is a **vacuous proof**. An implication such as `(count == DEPTH) |-> full` succeeds trivially, without checking `full`, at every edge where its left side (the **antecedent**) is false (§16.12.7). Such a success is **vacuous**: per §16.14.8 it "is not considered a pass or a failure". If an over-constraint makes `count == DEPTH` unreachable, every attempt is vacuous and the tool still says "proven". Some tools flag vacuous proofs; many do not by default (tool-dependent). You need your own detector, and covers are that detector:

1. **Cover each antecedent**, as its own property: `c_reach_depth: cover property (count == DEPTH);`. If it is unreachable, the implication is proven only vacuously. Do not rely on covering the implication itself: a `cover property` of an implication can count vacuous successes (§16.14.3 lists "succeeded because of vacuity" as a separate count), so cover the antecedent.
2. **Give each assumption a cover** for a behaviour it must still allow. For example, `c_push_pop: cover property (push && pop);` goes unreachable the moment someone assumes "one operation at a time".
3. **Read the covers before the assertions.** An unreachable cover, or every assertion proving almost instantly, means over-constraint or contradictory assumptions (assumptions that no trace can satisfy, which empty the input space so everything proves).
4. **Let simulation audit the assumptions.** Because a simulator checks every `assume` (§16.14.2), a legal random environment that does something an assumption forbids reports it. In the visualizer's model, with the correct RTL, the over-tight `a_never_fill` fails at edge 14 of random seed 1.

For cover statements, know one more distinction. `cover sequence` reports *every* match per evaluation attempt, while `cover property` counts at most one success per attempt (§16.14.3). Use `cover sequence` when you want to know how many ways a scenario completed.

### Under-constraint and counterexample triage

The opposite mistake is a **missing** assumption, or **under-constraint**. Formal then explores input sequences the real environment never produces and can return a **spurious counterexample**: a real trace of the RTL that can never occur in the product.

| Pitfall | Symptom | Fix |
|---|---|---|
| Over-constraint | Everything proves, often quickly; a cover is unreachable; a bug later appears in simulation or silicon | Find the assumption the specification does not support; remove or relax it; re-check the covers |
| Under-constraint | A CEX whose trace uses an input the specification forbids | Add the missing rule as an assumption, from the specification; re-run formal: the CEX must disappear |
| Vacuous proof | An implication proves but its antecedent cover is unreachable | Same as over-constraint, or fix a wrong antecedent, a `disable iff` that is always true, or the wrong clock |
| Assume on a DUT output | The matching assertion proves; the bug is hidden | Assume only environment-driven signals; assert DUT-driven ones |

So every counterexample needs **triage**: deciding whether it shows a design bug or an assumption gap. The decision is made against the **specification**, not against the assumptions, because a CEX satisfies every assumption formal used: those same assumptions cannot fire on it. The rule:

1. **Check every environment-driven input in the trace against the interface specification.** Read the trace edge by edge, or replay it in simulation with an *independent* input-side checker bound: the interface's complete protocol checker or VIP assertions on the signals the environment drives.
2. **If an input is illegal, the CEX is spurious.** Add the missing rule as an assumption and re-run formal. Replaying the old trace with the new assumption bound shows it firing at the illegal input.
3. **If every input is legal, it is a design bug.** Output-side checks (the scoreboard, assertions on DUT outputs) failing on legal inputs confirm it. They never make a CEX spurious: they check the DUT, not the stimulus.
4. **If the replay does not reproduce the failure**, you have a reproduction problem (reset alignment, X, driver timing), not a verdict. Fix the replay first.

Replaying the CEX in UVM with *only the same* `fifo_props` bound tells you that it reproduces, not that it is a bug. The visualizer can classify its counterexamples because its replay environment binds the **full interface contract**, even when the formal run had an assumption switched off. That contract checker plays the role of step 1's independent input-side checker.

**Debrief, run B (correct RTL, `a_no_push_when_full` off).** Formal reports `p_count_in_range` failing at edge 5. The trace pushes at edges 0 to 4; at edge 4 `count` is 4 and `full` is 1, and the push overflows the counter to 5. Pushing while full breaks the specification, so the CEX is spurious: the replay's contract checker reports `a_no_push_when_full` failing at edge 4. Restore the assumption; nothing in the RTL changes.

**Debrief, run C (late-flag RTL, contract).** Formal reports `p_full_is_correct` failing at edge 4: four legal pushes, then `count == 4` with `full == 0`. It also reports `p_count_in_range` failing at edge 5: at edge 4 the stale `full` still reads 0, so a fifth push is *legal* by the contract, and the counter overflows. Every input obeys the specification, so this is a design bug.

**Debrief, the simulation panel.** With the late-flag RTL and the contract, random seed 1 fails `p_full_is_correct` at edge 15, while seed 2 never fills the FIFO in 16 edges and passes. Formal found the bug at edge 4 whatever the seed. That is the case for formal in one sentence: it does not depend on stimulus luck.

### Choosing formal or simulation, and reporting results

A hybrid plan assigns each property, and each verification-plan feature, to the engine that can close it.

| Choose | When the logic is | Examples |
|---|---|---|
| Formal first | Control-dominated, a small interface, deep corner cases, properties that are easy to state | FIFO control and flags, arbiters (one-hot grant, bounded wait), FSMs, handshakes, credit counters, interrupt masking |
| Simulation first | Large datapaths, long end-to-end flows across many blocks, software-driven scenarios, performance | A pixel filter compared with a C model over a frame, a DMA throughput test, boot code |
| Both | Interface protocols | The same protocol checker is proven on each block in formal and checked in every simulation |

Formal results and simulation results are reported per property and traced to the verification plan:

| Property | Feature | Engine | Status | Assumptions (spec source) | Covers | Owner |
|---|---|---|---|---|---|---|
| `p_full_is_correct` | FIFO flags | formal | proven | `a_no_push_when_full`, `a_no_pop_when_empty` (FIFO spec, interface rules) | `c_reach_depth` covered at 4 | block owner |
| `p_count_in_range` | no overflow | formal | proven | as above | `c_push_pop` covered at 1 | block owner |
| `p_data_order` | data integrity | simulation | 0 failures in the nightly regression | none (scoreboard) | covergroup bins 100% | DV owner |

Each line names its depth when the result is bounded ("bounded to 30"), and each assumption names the specification clause it comes from and whether any regression ever violated it. Reviewers can then see exactly what "proven" rests on.

**Share rules, not constraints.** Keep interface rules as properties in one library: assumed by formal where the environment drives, asserted where a DUT drives, and checked by every simulation. Sequence constraints stay in the testbench as test intent.

### Recap

- One bound property library serves both engines; `assume` is a check in simulation and a hypothesis in formal, and `restrict` is ignored by simulators (objective 1).
- A harness keeps only SVA: free inputs filtered by assumptions from the specification, assertions and covers on outputs, bound with parameters passed through (objective 2).
- Constraints are solved per item and often encode test intent; assumptions hold at every edge on live signals. Over-constraint shows up as vacuous proofs and unreachable covers, under-constraint as spurious counterexamples (objective 3).
- Triage every CEX against the specification; the assumptions formal used cannot fire on its own trace (objective 4).
- Give each property to the engine that can close it, and report status, depth and assumptions per property; a bounded pass is not a proof (objective 5).

## Make It Work

### Worked example: FIFO flags, one checker, two engines

Three files. `fifo.sv` is the DUT, with a parameter that switches in the late-flag bug. `fifo_props.sv` is the shared property module and its bind. `fifo_tb.sv` is a small UVM bench that replays a formal counterexample.

```systemverilog
// compile
// fifo.sv: the control block of a FIFO (occupancy counter and flags)
module fifo #(
  parameter int DEPTH     = 4,
  parameter bit LATE_FULL = 1'b0  // 1 = the bug: full is registered, one edge late
) (
  input  logic                   clk, rst_n, push, pop,
  output logic [$clog2(DEPTH):0] count,
  output logic                   full, empty
);
  // The interface contract forbids push while full and pop while empty,
  // so the counter is deliberately unguarded: an illegal input overflows it.
  always_ff @(posedge clk or negedge rst_n)
    if (!rst_n) count <= '0;
    else        count <= count + push - pop;

  if (LATE_FULL) begin : g_late_full
    always_ff @(posedge clk or negedge rst_n)  // BUG: copies count one edge late
      if (!rst_n) full <= 1'b0;
      else        full <= (count == DEPTH);
  end else begin : g_full
    assign full = (count == DEPTH);
  end

  assign empty = (count == 0);
endmodule
```

```systemverilog
// compile
// fifo_props.sv: one property library for simulation and formal
module fifo_props #(
  parameter int DEPTH          = 4,
  parameter bit OVER_CONSTRAIN = 1'b0  // 1 adds a_never_fill: a deliberate mistake
) (
  input logic                   clk, rst_n, push, pop, full, empty,
  input logic [$clog2(DEPTH):0] count
);
`ifdef FIFO_PROPS_UVM  // defined only by the simulation compile
  import uvm_pkg::*;
  // Failures reach the UVM report server, so they count in the summary.
  `define FIFO_FAIL(msg) uvm_report_error("FIFO_PROPS", msg)
`else
  `define FIFO_FAIL(msg) $error(msg)
`endif

  default clocking @(posedge clk); endclocking
  default disable iff (!rst_n);

  // Interface contract (FIFO spec): the environment never pushes while full
  // and never pops while empty. Assumed here, because the environment drives
  // push and pop; simulation checks them on every edge.
  a_no_push_when_full: assume property (!(push && full))
    else `FIFO_FAIL("a_no_push_when_full: push while full");
  a_no_pop_when_empty: assume property (!(pop && empty))
    else `FIFO_FAIL("a_no_pop_when_empty: pop while empty");

  // Obligations on the DUT's outputs.
  p_count_in_range: assert property (count <= DEPTH)
    else `FIFO_FAIL("p_count_in_range: count > DEPTH");
  p_full_is_correct: assert property ((count == DEPTH) |-> full)
    else `FIFO_FAIL("p_full_is_correct: count == DEPTH but full == 0");

  // Sanity covers: the antecedent above, and push with pop together.
  c_reach_depth: cover property (count == DEPTH);
  c_push_pop:    cover property (push && pop);

  // A wrong assumption, kept here only to demonstrate over-constraint.
  if (OVER_CONSTRAIN) begin : g_over
    a_never_fill: assume property (!(push && count == DEPTH - 1));
  end
endmodule

// One bind for both flows. DEPTH and every port resolve in fifo's scope.
bind fifo fifo_props #(.DEPTH(DEPTH)) u_fifo_props (.*);
```

The simulation side drives the DUT through a clocking block and replays the run-C counterexample: `p_full_is_correct` failing at edge 4. The replay sequence is the pattern the visualizer generates from a trace: copy the trace's `push` and `pop` columns into arrays, and send one item per clock.

```systemverilog
// compile
// fifo_tb.sv: a minimal UVM bench that replays a formal counterexample
interface fifo_if (input logic clk);
  logic       rst_n, push, pop, full, empty;
  logic [2:0] count;  // $clog2(DEPTH) + 1 bits for DEPTH = 4
  clocking cb @(posedge clk);
    output push, pop;
    input  full, empty, count;
  endclocking
endinterface

package fifo_tb_pkg;
  import uvm_pkg::*;
  `include "uvm_macros.svh"

  class fifo_item extends uvm_sequence_item;
    rand bit push, pop;
    bit      full_seen, empty_seen;
    constraint c_legal { full_seen -> !push; empty_seen -> !pop; }
    `uvm_object_utils(fifo_item)
    function new(string name = "fifo_item");
      super.new(name);
    endfunction
  endclass

  class cex_replay_seq extends uvm_sequence #(fifo_item);
    `uvm_object_utils(cex_replay_seq)
    // Inputs copied from the formal trace (run C, p_full_is_correct), edges 0..3
    bit push_v[4] = '{1, 1, 1, 1};
    bit pop_v[4]  = '{0, 0, 0, 0};
    function new(string name = "cex_replay_seq");
      super.new(name);
    endfunction
    task body();
      foreach (push_v[i]) begin
        req = fifo_item::type_id::create($sformatf("cex_%0d", i));
        start_item(req);
        req.push = push_v[i];  // assigned, not randomized: c_legal is NOT applied,
        req.pop  = pop_v[i];   // so the trace is replayed exactly as formal found it
        finish_item(req);
      end
    endtask
  endclass

  class fifo_drv extends uvm_driver #(fifo_item);
    `uvm_component_utils(fifo_drv)
    virtual fifo_if vif;
    function new(string name, uvm_component parent);
      super.new(name, parent);
    endfunction
    function void build_phase(uvm_phase phase);
      super.build_phase(phase);
      if (!uvm_config_db#(virtual fifo_if)::get(this, "", "vif", vif))
        `uvm_fatal("NOVIF", "virtual interface not set")
    endfunction
    task run_phase(uvm_phase phase);
      @(vif.cb);
      vif.cb.push <= 1'b0;  // idle before reset is released
      vif.cb.pop  <= 1'b0;
      wait (vif.rst_n === 1'b1);
      forever begin
        @(vif.cb);
        seq_item_port.try_next_item(req);
        if (req != null) begin  // one item per clock edge, as in the trace
          vif.cb.push <= req.push;
          vif.cb.pop  <= req.pop;
          seq_item_port.item_done();
        end else begin          // nothing to send: idle, never repeat a push
          vif.cb.push <= 1'b0;
          vif.cb.pop  <= 1'b0;
        end
      end
    endtask
  endclass

  class fifo_cex_replay_test extends uvm_test;
    `uvm_component_utils(fifo_cex_replay_test)
    uvm_sequencer #(fifo_item) sqr;
    fifo_drv                   drv;
    virtual fifo_if            vif;
    function new(string name, uvm_component parent);
      super.new(name, parent);
    endfunction
    function void build_phase(uvm_phase phase);
      super.build_phase(phase);
      sqr = uvm_sequencer#(fifo_item)::type_id::create("sqr", this);
      drv = fifo_drv::type_id::create("drv", this);
      if (!uvm_config_db#(virtual fifo_if)::get(this, "", "vif", vif))
        `uvm_fatal("NOVIF", "virtual interface not set")
    endfunction
    function void connect_phase(uvm_phase phase);
      drv.seq_item_port.connect(sqr.seq_item_export);
    endfunction
    task run_phase(uvm_phase phase);
      cex_replay_seq seq = cex_replay_seq::type_id::create("seq");
      phase.raise_objection(this);
      seq.start(sqr);
      repeat (3) @(vif.cb);  // let the edges after the last push be sampled
      `uvm_info("CEX", "replayed 4 items from the run-C trace", UVM_LOW)
      phase.drop_objection(this);
    endtask
  endclass
endpackage

module tb_top;
  timeunit 1ns; timeprecision 1ps;
  import uvm_pkg::*;
  import fifo_tb_pkg::*;

  logic clk = 1'b0;
  always #5 clk = ~clk;

  fifo_if vif (clk);

  fifo #(.DEPTH(4), .LATE_FULL(1'b1)) dut (
    .clk(clk), .rst_n(vif.rst_n), .push(vif.push), .pop(vif.pop),
    .count(vif.count), .full(vif.full), .empty(vif.empty)
  );

  initial begin
    vif.rst_n = 1'b0;
    repeat (2) @(posedge clk);
    vif.rst_n <= 1'b1;
  end

  initial begin
    uvm_config_db#(virtual fifo_if)::set(null, "uvm_test_top*", "vif", vif);
    run_test("fifo_cex_replay_test");
  end
endmodule
```

### How-to: from first proof to a regression test

1. **Run formal with the contract only.** Read the covers first: every cover must be reached before any "proven" means anything.
2. **Read each status**: proven, bounded to N (not a proof), CEX at edge k, covered, unreachable, undetermined.
3. **Triage each CEX against the specification** before touching the RTL: is every environment-driven input legal at every edge?
4. **If an input is illegal**: add the missing rule as an assumption, from the specification, and re-run. The CEX must disappear, and every cover must still be reached.
5. **If every input is legal**: replay the trace in UVM. Copy the `push`/`pop` columns into arrays, assign rather than randomize, drive one item per clock, and count edges from the first replayed item. Confirm the same property fails at the same edge.
6. **Fix the RTL, re-prove**, and add the replay test to the regression. It must fail before the fix, pass after, and its failure must count in the regression's pass/fail.

### Debugging formal results

| Symptom | Likely cause | Fix |
|---|---|---|
| Everything proves almost instantly | Over-constraint; contradictory assumptions; a `disable iff` stuck true; the wrong clock or reset polarity; or a genuinely easy property | Check the covers; drop assumptions one at a time and watch which proofs change; check reset and clock declarations |
| A cover is unreachable | An assumption forbids it, or the cover is written wrongly | Find the assumption (remove each in turn); check it against the specification |
| A CEX has an illegal input | Under-constraint | Add the rule from the specification as an assumption; re-run |
| The CEX does not reproduce in simulation | Reset or initial-state differences; X values; the driver does not apply one item per clock; `randomize()` changed the replayed values | Align reset and edge 0; assign item fields instead of randomizing; check the driver's timing |
| A result is "bounded" or "undetermined" | The proof does not converge | See [Bounded proofs, induction and convergence](#expert-bounded-proofs-induction-and-convergence) |
| The replay fails but the regression passes | Assertion failures do not reach the UVM report summary | Route them to UVM reporting, or fail the regression on simulator assertion errors |

### In a real project

- **Property library:** interface rules live in one checker per interface, versioned with the interface, assumed or asserted by parameter.
- **Two run targets:** the same bind file feeds the formal run and the simulation compile; CI runs a short formal job (bounded proofs and covers) on every change and full proofs nightly.
- **Result exchange:** every CEX the team accepts as a design bug becomes a replay test; every assumption added after triage cites the specification clause it encodes.
- **Governance:** a feature closes only when its properties are proven (or bounded to an agreed depth), its covers are reached, and its simulation coverage is met.

**Checklist before moving on:**
- [ ] Every assumption is on a signal the DUT does not drive, and cites the specification.
- [ ] Every assumption has a cover for a behaviour it must still allow, and every cover is reached.
- [ ] Every proven implication has a covered antecedent.
- [ ] Each CEX was checked against the specification before the RTL was touched.
- [ ] The replay test fails before the fix, passes after, and its failure counts in the regression.
- [ ] Results are reported per property with status, depth and assumptions.

## Push Further

### Expert: What each directive means to each engine

- **`assume` in simulation is a check, not a generator** (§16.14.2). A failing assumption in simulation means either the testbench broke the interface rule or the assumption is wrong; both are worth knowing. Some tools can drive random simulation from assumptions; that is tool-dependent.
- **`dist` in assumptions** biases random simulation only. Formal treats the assumption as if the weights were absent, and in an `assert` or `cover` the `dist` acts like `inside` (§16.14.2).
- **Weak and strong sequences.** A bare sequence used as a property is weak in `assert` and `assume` and strong elsewhere, including `cover` (§16.12.2). So in `assert property (req |-> ##[1:$] ack)` the consequent is weak: the assertion cannot fail at the end of a simulation in which `ack` never came. Use `s_eventually` (§16.12.13) or a bounded `##[1:N]` when the obligation must bite. In a `cover`, the same bare sequence is strong and counts only completed matches.
- **Cover counting.** `cover property` records attempts, successes (at most one per attempt) and successes because of vacuity; `cover sequence` records every match per attempt (§16.14.3). Disabled evaluations are not counted as successes.
- **Case splits with `restrict`** (§16.14.4) need care: two sessions that restrict a signal to 0 and to 1 at every edge together cover only traces where the signal is constant. That is complete for a static mode bit, but not for a signal that can change during a trace.

### Expert: Bounded proofs, induction and convergence

Engines, option names and result labels are tool-dependent; the ideas are general.
- **Bounded model checking** unrolls the design N edges from reset and searches for a violation. It finds shallow bugs fast and returns short traces, often the shortest (tool-dependent), but it proves nothing beyond N.
- **Full proofs** need an argument that covers every reachable state. One common technique is **k-induction**: show that the property holding for k consecutive edges implies it holds at the next. Induction can fail on *unreachable* states, so engineers add **helper assertions** (invariants such as `count <= DEPTH` for a property about `full`) that rule those states out; each helper must itself be proven.
- **Convergence aids:** smaller parameters (prove DEPTH 4, argue the RTL is parameter-generic), case splits with `restrict`, and assume-guarantee decomposition. **Cut points and black boxes** replace logic with free signals. That over-approximates the design, which can cause spurious CEXs, and the black-boxed logic itself is not verified at all. A cover reached on the over-approximated design may be unreachable in the real one, so abstraction can hide over-constraint and dead code. Assumptions, by contrast, *remove* behaviour and can hide bugs.
- **CI practice:** a short bounded job on every change catches regressions in minutes; full proofs run nightly. Report bounded results with their depth, never as "proven".

### Expert: Symbolic data with constant free variables

A scoreboard checks data for the values the test happened to send. Formal can check data integrity for *every* value at once with a **constant free variable**: a checker variable declared `rand const`, which holds one nondeterministic value for the whole trace (§17.7). The standard's `data_legal` checker records "a value that went in" and asserts the same value comes out:

```systemverilog
// snippet: the data-integrity pattern of IEEE 1800-2023 §17.7 (abridged)
rand const bit [$bits(in_data)-1:0] mem_data;
sequence transaction;
  start_ev && (in_data == mem_data) ##1 end_ev[->1];
endsequence
a1: assert property (@clock transaction |-> out_data == mem_data);
```

Because `mem_data` can be any value, formal checks the transfer for every possible data value. A simulator randomizes `mem_data` once instead (§17.7.2), so in simulation it checks only the transactions whose data happen to match. The standard's representative-bit example (one symbolic bit index instead of a 64-bit compare) is "equivalent in formal verification" but "not equivalent in simulation". This is how the scoreboard's job moves into a formal harness, and it is why harnesses use the `checker` construct: free variables exist only in checkers. Syntax: [I-SV-4C](/curriculum/T2_Intermediate/I-SV-4C_Checkers/index#expert-free-variables-assume-sets-and-formal).

### Expert: Liveness, fairness and bounded response

"Every request is eventually granted" is a **liveness** property, for example `req |-> s_eventually gnt` (§16.12.13). Simulation can never prove it, because a finite run cannot show that something never happens; it can only fail to see it. Formal can, and a liveness CEX is a **lasso**: a prefix followed by a loop that repeats forever without the grant (presentation tool-dependent). Liveness proofs usually need **fairness** assumptions about the environment, such as "the requester eventually releases the bus", and each one is a claim to audit like any other assumption. The practical alternative is a **bounded-response** safety property, `req |-> ##[1:8] gnt`: it states the real requirement (a latency budget), has finite counterexamples, and works the same way in simulation.

### Expert: Where simulation and formal disagree

The standard notes that cycle-based evaluation can differ from event-based simulation (§16.2). Each of these can make a counterexample fail to replay, or a simulation failure fail to appear in formal:
- **X values.** In an assertion, X counts as false (§16.6). Many formal tools treat X sources as free 0/1 values instead of propagating X (tool-dependent).
- **Initial state.** Formal starts from the declared reset; registers without reset may be free. A simulator starts them at X or at an initializer (tool-dependent).
- **Delays, `initial` blocks and `$random` in RTL** are ignored or rejected by formal tools (tool-dependent).
- **Action blocks** run in simulation; formal tools ignore them (tool-dependent).
- **Free checker variables** are re-solved at each assume-set clock event in simulation (§17.7.2), but range over all legal values in formal.

### Expert: Assume-guarantee and keeping formal-only constraints out of simulation

Every assumption is a debt. Pay it by **discharging** it: prove the same property as an assertion on the block that drives the signal (the `ASSUME_IT` checker above), or rely on every simulation regression checking it, since simulators check assumptions (§16.14.2). An undischarged wrong assumption silently weakens every proof that uses it. Watch for **circular** assume-guarantee: block A's proof assumes what B guarantees, and B's proof assumes what A guarantees; naive circular reasoning can be unsound, so tools that support it impose conditions (tool-dependent).

Some constraints are deliberately formal-only: case splits, reduced modes, convergence restrictions. Keep them from failing simulations in one of three ways: write them as `restrict` (§16.14.4), which simulators ignore; switch them off in simulation with assertion control (`$assertcontrol` and `$assertoff`, §20.11); or compile them only for formal with a define your flow sets (tool-dependent naming). Prefer `restrict`: the intent is visible in the code.

### Expert: Formal apps (awareness)

Formal tools package common jobs as **apps**: automated flows that need little or no property writing. Names, features and availability are tool-dependent; the categories are widespread:
- **Connectivity checking:** proves that signals are connected as a specification table says (SoC pin muxing, interrupt wiring).
- **Coverage unreachability:** proves that some simulation coverage items can never be hit, so they can be excluded with evidence instead of by opinion.
- **Sequential equivalence:** proves that two versions of a design (before and after clock gating, retiming or a bug fix) behave the same at their outputs.
- **X-propagation:** looks for X values that can reach outputs or control logic from uninitialized or unknown sources.
- **Register (CSR) checking:** proves register access behaviour (reset values, access policies) from a register description.
- **Security and data-propagation:** proves that a secret cannot reach a given output, or only through approved paths.
- **Automatic checks:** generated properties for FSM reachability, deadlock, dead code and arithmetic overflow.

Each app proves something specific under its own assumptions; read its report with the same triage discipline as a hand-written proof.

### Expert: Signing off a hybrid flow

Sign-off asks two questions: did every property get the result it needs, and are the properties enough?
- **Per property:** status (proven, bounded to N, CEX open, CEX closed by an added assumption, undetermined), mapped to verification-plan features, with the assumptions and their specification sources.
- **Per assumption:** its source, whether it was discharged (proven elsewhere), and whether any simulation regression ever violated it.
- **Are the assertions enough?** Tools offer **formal coverage** metrics (tool-dependent): which logic lies in the cone of influence of the proven assertions, which logic a proof actually depended on, and **mutation** checks that change the design and ask whether some assertion fails. Logic no assertion depends on is unverified, however green the proofs.
- **Merging with simulation coverage:** some flows merge formal results into the simulation coverage database (tool-dependent). Merge only with the rules agreed up front: a cover proved unreachable may exclude a bin; a bounded result may not.

**Tasks:**

2. Write the per-clock assumptions for `fifo_props`.
3. Add one cover per behaviour the assumptions must still allow: push and pop together, a full FIFO, and a push into the last free slot.
4. Predict which covers become unreachable if `c_one_op` were assumed, and which if `a_never_fill` were added.

<summary>Worked solution</summary>

`a_never_fill` forbids pushing when `count` is 3, so the FIFO can never fill. `c_reach_depth` (the antecedent of `p_full_is_correct`) is unreachable, so that proof is vacuous. `c_push_pop` is still covered, which shows the over-constraint is specific to filling, not a global contradiction. Remove `a_never_fill` (bind with `OVER_CONSTRAIN = 1'b0`): formal reports `p_full_is_correct` failing at edge 4 (count = 4, full = 0) and `p_count_in_range` failing at edge 5 (a fifth, contract-legal push overflows the counter), with `c_reach_depth` covered at edge 4. Other causes of a too-fast proof to rule out: contradictory assumptions, a `disable iff` stuck true, the wrong clock or reset polarity, or a property that really is easy.

</details>

### Exercise: write the replay

Formal returned this trace for `p_full_is_correct` (run C). Write the `push_v`/`pop_v` arrays and the `body()` loop of `cex_replay_seq`, and predict what the simulation reports and when.

| Edge | 0 | 1 | 2 | 3 | 4 |
|---|---|---|---|---|---|
| `push` | 1 | 1 | 1 | 1 | 0 |
| `pop` | 0 | 0 | 0 | 0 | 0 |
| `count` | 0 | 1 | 2 | 3 | 4 |
| `full` | 0 | 0 | 0 | 0 | 0 |

<details>
<summary>Worked solution</summary>

Drive the inputs of edges 0 to 3; edge 4 is where the failure is sampled, and the driver idles there.

```systemverilog
// snippet: inside cex_replay_seq
bit push_v[4] = '{1, 1, 1, 1};
bit pop_v[4]  = '{0, 0, 0, 0};

task body();
  foreach (push_v[i]) begin
    req = fifo_item::type_id::create($sformatf("cex_%0d", i));
    start_item(req);
    req.push = push_v[i];  // assigned, not randomized
    req.pop  = pop_v[i];
    finish_item(req);
  end
endtask
```

Prediction: `p_full_is_correct` fails 4 edges after the first replayed push, with `count == 4` and `full == 0`, exactly as in formal. If you randomized the items instead, `c_legal` could change the values and the trace would not replay. The driver must apply one item per clock and idle afterwards; a driver that keeps the last push asserted would overflow the FIFO and add a `p_count_in_range` failure the trace never had.

</details>
