## Quick Take

- **What it is:** **cocotb** is a Python library for writing testbenches: your test is a set of Python coroutines that a Python interpreter, embedded *inside* the running HDL simulator, resumes whenever a simulator event you asked for happens. **pyuvm** is the most-used part of UVM (IEEE 1800.2-2020) written in Python on top of cocotb: components, phases, the factory, `ConfigDB`, TLM ports and sequences.
- **Why it matters:** Many teams already keep their reference models, data generators and analysis scripts in Python, and Python tests run without recompiling the bench. cocotb also runs on open-source simulators such as Icarus Verilog and Verilator, which makes continuous integration (CI) cheap. The price is a different execution model, a different (smaller) UVM, and a speed cost you must understand to control.
- **The Analogy:** A cocotb test is an operator who works *inside* a machine and may only act when a bell rings: each `await` names the bell. *Where it breaks:* while the operator works, the whole machine is frozen, so a slow operator means a slow simulation; and the operator cannot see anything that happens between bells, so choosing the wrong bell means reading the wrong value.

**Versions on this page.** cocotb **2.1.0** (released 2026-08-30) and pyuvm **5.0.0** (2026-08-31, which requires `cocotb>=1.6.0,<3.0`), both on Python 3.9 or later. cocotb 2.0 removed or renamed several 1.x APIs, so most cocotb code you find online needs changes; the [migration traps](#expert-cocotb-1x-to-2x-migration-traps) are listed in Push Further.

**You will be able to:**
1. Write a cocotb 2.x test with a clock, a reset that respects the interface rules, and a driver and monitor that complete each valid/ready handshake and drop VALID right after it.
2. Explain how cocotb runs (an interpreter embedded in the simulator, resumed by VPI, VHPI or FLI callbacks), predict what a coroutine reads and when its writes reach the design after each trigger, and explain what makes Python benches slow.
3. Map a SystemVerilog UVM agent to pyuvm 5.0 (factory, phases, `ConfigDB`, TLM, sequences, objections) and name where pyuvm differs.
4. Choose Python (cocotb or pyuvm), SystemVerilog UVM or a hybrid for a project, and justify the choice with skills, ecosystem, performance and tool support.

### Words you need first

- **Design under test (DUT):** the HDL module the testbench (TB) checks. Here it is always simulated by the HDL simulator, never by Python.
- **Coroutine:** a Python function defined with `async def`. It can pause at an `await` and be resumed later, keeping its local variables. It is the Python counterpart of a SystemVerilog `task` that consumes time.
- **`await`:** "pause this coroutine until that thing is done". `await RisingEdge(dut.clk)` pauses until the clock rises; `await drv.write(5)` pauses until another coroutine finishes.
- **Trigger:** a cocotb object you can `await` that stands for a simulator event: `RisingEdge(sig)`, `FallingEdge(sig)`, `ValueChange(sig)`, `Timer(10, unit="ns")`, `ReadWrite()`, `ReadOnly()`, `NextTimeStep()`, and `ClockCycles(sig, n)`, which counts edges.
- **Task:** a coroutine that runs on its own, started with `cocotb.start_soon(coro)`. It is the counterpart of a process started by `fork … join_none`.
- **VPI, VHPI, FLI:** C interfaces through which a program attached to a simulator reads and writes signals and asks to be called back. **VPI** is part of IEEE 1800-2023 (Clauses 36 to 38) and is the current form of SystemVerilog's **PLI** (Programming Language Interface, the family of C interfaces Clause 36 introduces), **VHPI** is the VHDL equivalent, and **FLI** is a proprietary Siemens interface for VHDL in Questa and ModelSim.
- **Callback:** a C function the simulator calls when an event happens, such as a value change, a delay expiring or a scheduling point. The callback **reason** names the event, for example `cbValueChange` or `cbReadOnlySynch`.
- **GPI:** cocotb's own C++ layer that hides the differences between VPI, VHPI and FLI.
- **Time step:** cocotb's name for everything the simulator does at one simulation time. IEEE 1800-2023 calls it a **time slot** (§4.4). This page says "time slot" in its own voice and keeps "time step" only inside cocotb's phase names (such as "End of time step") and quotes.
- **Deposit:** cocotb's default way to write a signal, `dut.push.value = 1`. If HDL code also drives that signal, the HDL value wins at its next update.
- **`dut` handle:** the Python object for the top-level HDL instance. `dut.push` is a handle for the signal `push`; `.value` reads or writes it.

### Where your Python runs: inside the simulator

The common wrong picture is a Python program in one process talking to a simulator in another, or worse, a DUT "converted to Python". Neither is true. cocotb's own description: "A Python interpreter is embedded into the running simulator process to provide a Python execution environment" (cocotb 2.1 docs, *How does cocotb work?*). The simulator loads cocotb's GPI library through VPI, VHPI or FLI, and the library starts Python. The DUT is compiled and simulated exactly as it would be for a SystemVerilog bench.

Every `await` on a trigger becomes a callback registration. When the event happens, the simulator calls the GPI, the GPI wakes cocotb's scheduler, and the scheduler resumes every coroutine waiting on that trigger. Python then runs until each of those coroutines reaches its next `await`, and only then does control go back to the simulator.

**Predict first.** While your coroutine runs a slow Python loop (say, a large NumPy computation), does simulated time move on without it?

**Debrief.** No: simulated time is frozen until your Python returns to an `await`. That is also why a Python debugger breakpoint (`breakpoint()`) freezes the whole simulation, and why the cost of a Python bench grows with how often Python is woken and how long it runs each time. The DUT itself always runs at full simulator speed.

**Where this lives in a real flow.** You compile the DUT with the simulator as usual; cocotb's Makefiles or Python runner add the GPI library to the simulator's command line and point it at your test module. In the simplest flow there is no SystemVerilog `tb_top`: the HDL top level *is* the DUT, and Python drives its ports.

### What you read and write after each trigger (the timing model)

Because Python runs at callback points, *which* trigger you awaited decides what you see. cocotb 2.1 splits a time slot (cocotb says "time step") into five phases (cocotb docs, *The Timing Model*):

1. **Beginning of time step:** where `Timer` and `NextTimeStep` return, before any HDL has run.
2. **HDL evaluation:** the simulator runs `always` blocks and continuous assignments. Python is not running.
3. **Values Change:** where `RisingEdge`, `FallingEdge` and `ValueChange` return. The signal you waited on has its new value, but "no HDL that reacts to that value change will have executed".
4. **Values Settle:** where `ReadWrite` returns. An **evaluation cycle** is one pass in which the simulator runs every piece of HDL triggered by the latest value changes; at Values Settle that pass has finished, and you may still write (a write starts another pass).
5. **End of time step:** where `ReadOnly` returns. All values are final, and writing is an error.

Two consequences shape every cocotb driver and monitor:

- **Reads after `RisingEdge`:** cocotb's docs say it directly: after `await RisingEdge(dut.clk)`, "the output of the flip-flop will remain the previous value". You see the values the flops *used* at this edge, not the values they produce.
- **Writes after `RisingEdge`:** with cocotb's default settings, a deposit made in the Values Change phase is not applied at once. cocotb queues it and applies it at the start of the next ReadWrite callback (cocotb 2.1 `handle.py`, `_schedule_write`). By then the flops clocked by this edge have already sampled their inputs, so **the DUT sees your write at the next rising edge**, exactly like a nonblocking drive (`<=`) in a SystemVerilog bench.

The table maps each trigger to the VPI callback reason cocotb registers (cocotb v2.1.0 `src/cocotb/share/lib/gpi/vpi/VpiCbHdl.cpp`) and to the region IEEE 1800-2023 §4.10 Table 4-1 assigns that reason; regions are the ordered stages of a time slot taught in [F3B](/curriculum/T1_Foundational/F3B_Scheduling_Regions/index), and the PLI regions (Pre-Active, Pre-NBA, Post-NBA) are the points between them where C callbacks may run (§4.4.3). Value-change callbacks have no row in Table 4-1: they fire when the value changes, wherever that happens.

| You `await` | cocotb phase | VPI callback reason | Table 4-1 region | A read returns | A write (default settings) |
|---|---|---|---|---|---|
| `Timer(t, unit=…)` | Beginning of time step | `cbAfterDelay` | Pre-Active | values left by the previous time slot | queued; applied at this time slot's ReadWrite point |
| `NextTimeStep()` | Beginning of time step | `cbNextSimTime` | Pre-Active | same as `Timer` | same as `Timer` |
| `RisingEdge(s)`, `FallingEdge(s)`, `ValueChange(s)` | Values Change | `cbValueChange` | none (fires on the change) | `s` is new; anything that depends on `s` is still old | queued; logic clocked by this edge does not see it |
| `ReadWrite()` | Values Settle | `cbReadWriteSynch` | Pre-NBA or Post-NBA (around the nonblocking-assignment region) | settled values | applied at once; may start another evaluation cycle |
| `ReadOnly()` | End of time step | `cbReadOnlySynch` | Postponed | the values the time slot ends with | `RuntimeError` |

**Verilator is different (tool-dependent).** Verilator is cycle-based: it cannot stop in the middle of evaluating a time slot, so cocotb handles edge triggers after the evaluation ends, "as if the value change triggers all have an implicit `await ReadWrite()` after them" (cocotb docs, *Differences in Verilator*). After `await RisingEdge(dut.clk)` on Verilator you see the flops' *new* outputs. A monitor that reads right after `RisingEdge` therefore sees every handshake one cycle off on one of the two kinds of simulator. The portable fix is in [Monitoring a portable way](#monitoring-a-portable-way).

### Coroutines and tasks versus fork and join

A coroutine runs only when someone awaits it or starts it as a Task. The cocotb test itself is a coroutine marked with `@cocotb.test()`; it ends when that coroutine returns, and at that point cocotb **cancels every Task still running** (cocotb 2.0 release notes, PR 4574). Concurrency in cocotb is cooperative: exactly one coroutine runs at a time, and it keeps running until its next `await`.

| SystemVerilog ([F2C](/curriculum/T1_Foundational/F2C_Procedural_Code_and_Flow_Control/index)) | cocotb 2.1 | Notes |
|---|---|---|
| call a time-consuming task: `drive(x);` | `await drive(x)` | the caller waits |
| `fork p(); join_none` | `task = cocotb.start_soon(p())` | `start_soon` runs `p` at the next scheduling point, not immediately |
| `fork a(); b(); join` | `await gather(a(), b())` | `gather` is new in 2.1 (PR 5165) |
| `fork a(); b(); join_any` | `await select(a(), b())` | `select` cancels the coroutines that did not finish; passing Tasks to `First` is deprecated in 2.1 (PR 5206), and `First` is for triggers |
| `disable fork` (one process) | `task.cancel()` | throws `CancelledError` into the Task |
| `wait fork` | `await task` for each Task, or a `TaskManager` (2.1, a helper that starts a group of Tasks and waits for all of them) | `Join(task)` is deprecated; await the Task itself |
| `@(posedge clk)` | `await RisingEdge(dut.clk)` | see the timing model above |
| `#10ns` | `await Timer(10, unit="ns")` | `unit` was `units` before 2.0 |

**Pitfall.** A Task that is still mid-transfer when the test returns is cancelled, silently from your point of view. Wait for the last transfer to be observed before the test returns (Make It Work waits two clock cycles after the last read for exactly this reason).

### Driving a valid/ready interface

Most on-chip interfaces move data with a **valid/ready handshake**. The source raises **VALID** when it offers data; the destination raises **READY** when it can take it. In AXI, "Transfer occurs only when both the VALID and READY signals are HIGH", and "Once VALID is asserted it must remain asserted until the handshake occurs, at a rising clock edge at which VALID and READY are both asserted" (Arm IHI0022E §A3.2.1). Read the second rule carefully: VALID must stay up *until its handshake edge*, and no longer if the source has nothing more to send. **Every** rising edge with both signals HIGH is a new transfer.

The FIFO you will drive in Make It Work follows the same rule with other names: `push` is VALID for writes, `pop` is VALID for reads, and `!full` and `!empty` play READY. A push happens at each rising edge with `push && !full`.

**Use the explorer.** Open the scenario **Back-to-back**: VALID stays HIGH while three addresses are queued, and you can click READY cells. **Predict first:** at which edge does the third address (0x3000) transfer? Then open **Debug: dropped VALID** and find the edge where the source breaks the rule in the other direction.

**Debrief.** In Back-to-back, READY is HIGH at edges 1, 2 and 4, so the three addresses transfer at edges 1, 2 and 4: one transfer per edge with both signals HIGH. Holding VALID HIGH is correct *only because there are three addresses to send*. If the source had one address and kept VALID HIGH, edges 2 and 4 would deliver two more copies of it. In the dropped-VALID trace, at edge 3 the source lowers VALID while AWREADY is still 0, before any handshake edge, which §A3.2.1 forbids.

**The classic Python mistake.** A widespread pattern holds AWVALID (write-address VALID) and WVALID until the write response `BVALID` arrives:

```python
# snippet -- WRONG: holds AWVALID and WVALID until the write response
dut.s_axi_awvalid.value = 1
dut.s_axi_wvalid.value = 1
while not dut.s_axi_bvalid.value:
    await RisingEdge(dut.clk)
dut.s_axi_awvalid.value = 0
dut.s_axi_wvalid.value = 0
```

**The pattern that is always right.** Drive VALID just after a rising edge. Before the next rising edge, look at READY in its settled state; after that edge, if READY was HIGH the transfer happened, so lower VALID (or present the next item). In cocotb that is:

```python
# snippet -- one handshake; enter just after a rising edge
valid.value = 1
while True:
    await FallingEdge(dut.clk)
    await ReadOnly()             # READY is settled for the next rising edge
    ready = bool(ready_sig.value)
    await RisingEdge(dut.clk)    # the edge that samples VALID
    if ready:
        break                    # transferred at this edge
valid.value = 0                  # drop VALID after its handshake
```

Reading READY at the falling edge, rather than right after `RisingEdge`, works on event-driven simulators and on Verilator alike, as long as READY is stable from the falling edge to the next rising edge. That holds for a registered READY, and also for a READY that is combinational from VALID and registered state: VALID was applied just after the rising edge, so READY has settled long before the falling edge. It fails only if READY can change in the second half of the cycle (for example, negedge logic, or another driver that writes at the falling edge); then sample it later, for example with `await ReadWrite()` after the edge, as in the cocotb docs' combinational-reaction example.

**Reset.** Arm IHI0022E §A3.1.2 requires a master to drive ARVALID, AWVALID and WVALID LOW during reset, and allows them HIGH at the earliest "at a rising ACLK edge after ARESETn is HIGH". The same discipline protects any DUT: drive every input to a known value at time 0, hold reset for a few edges, release it by writing right after a rising edge (so the release is synchronous), and start traffic one edge later.

### Monitoring a portable way

A monitor must decide, once per cycle, whether a transfer happened and with which data. The safest point in cocotb is the **end of the falling-edge time slot** (cocotb's End of time step phase): `await FallingEdge(dut.clk)` then `await ReadOnly()`. There, every input the drivers wrote after the last rising edge has settled, and so have the DUT's outputs, so you read exactly what the flops will use at the next rising edge, on any simulator.

For the FIFO: at each falling edge the monitor records a push if `push && !full`, and remembers whether a pop will happen (`pop && !empty`). `dout` is registered by the pop, so the popped word is visible at the *next* falling edge. The monitor in the I-UVM-3C capstone lab (`uvm-mini-capstone`) solves the same problem differently: its clocking block reads `dout` with an `input #0` skew at the pop edge itself, in the Observed region after the nonblocking update. cocotb has no clocking blocks, so the Python monitor waits for the next falling edge instead.

**Predict first.** In Make It Work the driver issues write `00`, read, write `A5`, write `5A`, read, read, write `11`, one per cycle. The read accepted at edge 5 pops `A5`. At which edge is `A5` first on `dout`, and at which falling edge does the monitor check it?

### pyuvm: the same structure in Python

pyuvm keeps UVM's architecture: tests, environments, agents, drivers, monitors, scoreboards, sequences and TLM connections, with UVM's class names. It does not keep SystemVerilog's syntax, and it implements, in its README's words, "the most-often used parts of the IEEE 1800.2 standard". Code does not move between the two by copy and paste: you port it, class by class.

| SystemVerilog UVM (uvm-core 2020.3.1) | pyuvm 5.0 | What is different |
|---|---|---|
| `` `uvm_component_utils(my_drv) `` | nothing | every class derived from `uvm_void` registers itself with the factory |
| `my_drv::type_id::create("drv", this)` | `MyDrv.create("drv", self)` | `create` is a class method; there is no `type_id` |
| `function new(string name, uvm_component parent)` | `__init__(self, name, parent)` (usually inherited) | |
| `function void build_phase(uvm_phase phase)` | `def build_phase(self):` | no `phase` argument |
| `task run_phase(uvm_phase phase)` | `async def run_phase(self):` | a coroutine; time passes only at `await` |
| run-time phases (`reset_phase` … `shutdown_phase`) | not provided | pyuvm runs only the common phases (build to final) |
| `phase.raise_objection(this)` | `self.raise_objection()` | a component method; no drain time |
| `uvm_config_db#(T)::set(this, "env.agt", "vif", vif)` | `ConfigDB().set(self, "env.agt", "DUT", cocotb.top)` | one untyped database; you usually store the `dut` handle, not a virtual interface |
| `uvm_config_db#(T)::get(...)` returns 0, then `` `uvm_fatal `` | `ConfigDB().get(self, "", "DUT")` | raises `UVMConfigItemNotFound` unless you pass a default |

| `uvm_subscriber #(T)` with `write(T t)` | `uvm_subscriber` with `def write(self, t):` | |

**Debrief.** `finish_item` returns only after the driver calls `item_done()`. pyuvm keeps that order: its `finish_item` waits on the item's `finish_condition` event, which `item_done()` sets. Two differences matter in practice. In pyuvm every blocking call is visibly awaited (`await self.start_item(item)`, `item = await self.seq_item_port.get_next_item()`), while `item_done()` is a plain call. And a driver that forgets `item_done()` does not see SystemVerilog's "Get_next_item called twice" error: its next `get_next_item()` raises `UVMSequenceError: You must call item_done() before calling get_next_item again`.

**Misconception: "pyuvm is SystemVerilog UVM in Python, so code ports line for line."** It ports *idea for idea*. You will rewrite every class, lose run-time phases, sequencer arbitration, `lock`/`grab`, field automation and the constraint solver, and gain Python's libraries, plain methods for compare and print, and no macros. SystemVerilog verification IP (VIP), the ready-made agents vendors sell for standard protocols, cannot be imported into a pyuvm bench.

### What Python costs, and why

There is no fixed slowdown factor for a Python bench; anyone who quotes one without a benchmark is guessing. The cost follows from the execution model: every trigger that fires calls into Python, and every signal access crosses the GPI. A useful model is:

**Python cost per simulated cycle ≈ (number of trigger wake-ups per cycle × Python work per wake-up) + signal reads and writes per cycle.**

The DUT's own simulation cost is unchanged. A large DUT with a thin Python bench (a few wake-ups per transaction) loses little; a small DUT with five coroutines each waking on every edge and reading twenty signals may spend most of its time in Python. Push Further lists the levers. The rule for daily work: **measure** (cocotb reports simulated time and wall-clock time per test) before and after a change.

### Choosing Python, SystemVerilog UVM or a hybrid

Separate verified facts from judgement. The facts:

| Question | SystemVerilog UVM | cocotb / pyuvm |
|---|---|---|
| Which simulators run it? | Any simulator with full IEEE 1800-2023 class support and a UVM library; open-source support is limited | Icarus Verilog 11.0+, Verilator 5.036+, VCS (VPI only), Questa, ModelSim, Xcelium, Incisive, Riviera-PRO, Active-HDL, GHDL, NVC, DSim and others (cocotb Simulator Support) |
| Constrained random | built into the language (IEEE 1800-2023 Clause 18) | Python `random`; pyvsc or cocotb-coverage add constraints (third-party) |
| Functional coverage | covergroups (Clause 19), merged by the vendor's tools | cocotb-coverage or pyvsc (third-party); merging with vendor coverage databases is tool-dependent |
| Assertions (SVA) | in the HDL | the same SVA in the HDL; SVA does not depend on the bench language |
| Standard | IEEE 1800.2-2020, with the uvm-core reference implementation | pyuvm implements "the most-often used parts" of 1800.2 |
| Ready-made VIP | commercial and open SystemVerilog VIP | community packages, for example cocotbext-axi 0.1.28 for AXI and AXI-Lite (third-party) |
| Speed | no language boundary | a GPI crossing per wake-up and per signal access |

The judgement, which you must make per project:

- **Python fits** when the reference model or stimulus already lives in Python (signal processing, machine-learning accelerators), when the team writes Python better than SystemVerilog, when open-source CI matters, and for block-level benches where wake-ups per cycle stay low.
- **SystemVerilog UVM fits** when the project depends on commercial VIP, run-time phases, sequencer arbitration, a mature register layer, or an established methodology team; and for large system-on-chip (SoC) benches where simulation throughput dominates cost. Emulation and acceleration flows are tool-dependent for both; check what your emulator vendor supports.
- **A hybrid fits** when an SV UVM bench needs a Python model: the bench calls Python through a DPI-C layer that embeds an interpreter. pyuvm plays no part in that path.

### Pitfalls

| Pitfall | Why it is wrong | Fix |
|---|---|---|
| Holding VALID until a response arrives | every edge with VALID and READY HIGH is a transfer (IHI0022E §A3.2.1) | drop VALID right after its handshake edge |
| Reading flop outputs right after `RisingEdge` | you see the old value on event-driven simulators and the new one on Verilator | sample at `FallingEdge` + `ReadOnly`, or add `ReadOnly` and reason about which edge you see |
| Starting the clock high | `RisingEdge` may fire on the X→1 transition at time 0 (cocotb warns that "many simulators" do this); reset release can race the first edge | `clock.start(start_high=False)` as in cocotb's own `simple_dff` example |
| Leaving inputs undriven before reset | `bool()` or `int()` of an X raises `ValueError` in your monitor, and the DUT may latch X | drive every input at time 0 |
| Relying on `logger.error` to fail a test | cocotb and pyuvm fail a test only on an exception | `assert`, or raise |
| Returning from the test while a transfer is in flight | Tasks are cancelled at test end | wait for the monitor to observe the last transfer |
| Expecting SV UVM features in pyuvm | pyuvm implements a subset | check the mapping table before porting |

### Debugging: symptom, cause, fix

| Symptom (what the log shows) | Cause | Fix |
|---|---|---|
| `ImportError: cannot import name 'TestFailure' from 'cocotb.result'` | cocotb 2.0 removed `TestFailure` (PR 4960) | `assert cond, "message"` |
| `DeprecationWarning: The 'units' argument has been renamed to 'unit'.` | 1.x keyword on `Clock` or `Timer` | rename to `unit=`; the code still runs |
| `ValueError: Cannot convert Logic('X') to bool` | reading an undriven or unreset signal | drive inputs and assert reset at time 0; check `.value.is_resolvable` |
| `RuntimeError: Attempting settings a value during the ReadOnly phase.` (sic) | a write after `await ReadOnly()` | await an edge or `Timer` before writing |
| every handshake one cycle late on Verilator only | reads right after `RisingEdge` | sample at `FallingEdge` + `ReadOnly` |
| `UVMConfigItemNotFound` | no `ConfigDB().set` for that key and path, or a wrong context | set it in the test's `build_phase`, or pass a default to `get` |
| `UVMSequenceError: You must call item_done() before calling get_next_item again` | the driver skipped `item_done()` | call `self.seq_item_port.item_done()` after each item |
| `AttributeError: 'FifoAgent' object has no attribute 'is_active'` | the agent's `build_phase` did not call `super().build_phase()` | call it first; it reads `is_active` from `ConfigDB` |
| warning `You did not call self.raise_objection() in any run_phase` and the test ends at once | no objection | raise one in the test's `run_phase` and drop it at the end |
| errors in the log but the test passed | logging is not a verdict | `assert` in `check_phase` (pyuvm) or at the end of the test (cocotb) |
| the test never ends (a sequence or monitor waits forever) | an event that never comes; there is no UVM-style global timeout | give the test a limit: `@cocotb.test(timeout_time=50, timeout_unit="us")`, or the same arguments to `@pyuvm.test()` |

**Waveforms.** With the Makefile flow, `make SIM=icarus WAVES=1` makes Icarus write `sim_build/packet_fifo.fst` (FST is a compressed waveform format; open it in GTKWave or Surfer); Verilator takes its trace options through `EXTRA_ARGS`, and other simulators use their own switches (cocotb Simulator Support). **Logs.** `cocotb.log` is a standard Python logger, so `cocotb.log.setLevel(logging.DEBUG)` shows more detail; pyuvm components log through `self.logger`.

### Recap

- cocotb runs **inside** the simulator: an embedded interpreter, resumed by VPI, VHPI or FLI callbacks; simulated time stops while Python runs.
- The trigger you await decides what you read: old flop outputs after `RisingEdge` on event-driven simulators, settled values at `ReadWrite` and `ReadOnly`. A default write after `RisingEdge` reaches the DUT at the next rising edge.
- A Task is `fork … join_none`; awaiting is a blocking call; Tasks are cancelled at test end.
- One transfer per edge with VALID and READY HIGH: drop VALID after its handshake. Sample monitors at `FallingEdge` + `ReadOnly` for portability.
- pyuvm keeps UVM's structure but not its syntax or all its features: `create()` without `type_id`, common phases only, `ConfigDB` that raises, a FIFO sequencer, logging that does not fail tests.
- Python's cost is wake-ups and signal accesses per cycle: measure, do not assume.

### The DUT

This is the capstone lab's DUT, extracted to its own file. Two edits keep it friendly to every simulator cocotb supports: `mem` uses an explicit range, and `case` replaces `unique case` (the two branches are already exclusive, so behaviour is identical).

```systemverilog
// compile -- packet_fifo.sv: the I-UVM-3C capstone lab DUT, standalone
// push is accepted at a rising edge only when !full, pop only when !empty.
// dout is registered: the popped word appears just after the pop edge.
module packet_fifo #(
  parameter int DEPTH = 4,
  parameter int WIDTH = 8
) (
  input  logic                       clk,
  input  logic                       rst_n,
  input  logic                       push,
  input  logic                       pop,
  input  logic [WIDTH-1:0]           din,
  output logic [WIDTH-1:0]           dout,
  output logic                       full,
  output logic                       empty,
  output logic [$clog2(DEPTH+1)-1:0] level
);
  localparam int PTR_W = $clog2(DEPTH);

  logic [WIDTH-1:0] mem [0:DEPTH-1];
  logic [PTR_W-1:0] rd_ptr;
  logic [PTR_W-1:0] wr_ptr;
  logic [$clog2(DEPTH+1)-1:0] count;

  assign full  = (count == DEPTH);
  assign empty = (count == 0);
  assign level = count;

  function automatic logic [PTR_W-1:0] bump(input logic [PTR_W-1:0] ptr);
    return (ptr == DEPTH-1) ? '0 : ptr + 1'b1;
  endfunction

  always_ff @(posedge clk or negedge rst_n) begin
    if (!rst_n) begin
      rd_ptr <= '0;
      wr_ptr <= '0;
      count  <= '0;
      dout   <= '0;
    end else begin
      if (push && !full) begin
        mem[wr_ptr] <= din;
        wr_ptr <= bump(wr_ptr);
      end
      if (pop && !empty) begin
`ifdef INJECT_FIFO_BUG
        // Planted bug: skips a word when the head is 8'hA5 and more follow.
        if (mem[rd_ptr] == 8'hA5 && count > 1)
          dout <= mem[bump(rd_ptr)];
        else
          dout <= mem[rd_ptr];
`else
        dout <= mem[rd_ptr];
`endif
        rd_ptr <= bump(rd_ptr);
      end
      case ({push && !full, pop && !empty})
        2'b10:   count <= count + 1'b1;
        2'b01:   count <= count - 1'b1;
        default: count <= count;
      endcase
    end
  end
endmodule
```

### The cocotb test

```python
# compile -- test_fifo.py: cocotb 2.1 test for packet_fifo (Python 3.9+)
from collections import deque

import cocotb
from cocotb.clock import Clock
from cocotb.triggers import ClockCycles, FallingEdge, ReadOnly, RisingEdge

# The capstone's traffic: (operation, data); None means a read.
SEQUENCE = [
    ("W", 0x00), ("R", None),
    ("W", 0xA5), ("W", 0x5A), ("R", None), ("R", None),
    ("W", 0x11), ("W", 0x22), ("W", 0x33), ("W", 0x44),
    ("R", None), ("R", None), ("R", None), ("R", None),
]


class FifoDriver:
    """Drives one request at a time. Call its methods just after a rising edge."""

    def __init__(self, dut):
        self.dut = dut

    async def _handshake(self, valid, stall):
        # valid is push or pop (VALID); READY is "not full" or "not empty".
        valid.value = 1
        while True:
            await FallingEdge(self.dut.clk)
            await ReadOnly()                  # flags are settled for the next edge
            ready = not stall.value
            await RisingEdge(self.dut.clk)    # the edge that samples valid
            if ready:
                break                         # one transfer happened at this edge
        valid.value = 0                       # drop VALID after its handshake

    async def write(self, data):
        self.dut.din.value = data
        await self._handshake(self.dut.push, self.dut.full)

    async def read(self):
        await self._handshake(self.dut.pop, self.dut.empty)


class Scoreboard:
    """Reference model: a deque stands in for the FIFO."""

    def __init__(self):
        self.model = deque()
        self.matches = 0
        self.mismatches = 0

    def push(self, data):
        self.model.append(data)

    def check_pop(self, observed):
        if not self.model:
            self.mismatches += 1
            cocotb.log.error("SCB_UNDERFLOW popped 0x%02x from an empty model", observed)
            return
        expected = self.model.popleft()
        if observed == expected:
            self.matches += 1
        else:
            self.mismatches += 1
            cocotb.log.error(
                "SCB_MISMATCH expected 0x%02x observed 0x%02x", expected, observed
            )


async def monitor(dut, sb):
    """Samples once per cycle at the end of the falling-edge time slot."""
    pop_pending = False
    while True:
        await FallingEdge(dut.clk)
        await ReadOnly()
        if dut.rst_n.value != 1:
            pop_pending = False
            continue
        if pop_pending:                       # dout was loaded at the last rising edge
            sb.check_pop(int(dut.dout.value))
        # These are the values the DUT uses at the next rising edge.
        pop_pending = bool(dut.pop.value) and not dut.empty.value
        if dut.push.value == 1 and not dut.full.value:
            sb.push(int(dut.din.value))


@cocotb.test()
async def test_fifo_scoreboard(dut):
    """Same traffic as the I-UVM-3C capstone lab: 7 writes, 7 reads."""
    # Known inputs and reset asserted before the first edge: no X reaches the DUT.
    dut.push.value = 0
    dut.pop.value = 0
    dut.din.value = 0
    dut.rst_n.value = 0
    # Start low so the first rising edge is a clean 0 -> 1 at 5 ns.
    Clock(dut.clk, 10, unit="ns").start(start_high=False)
    await ClockCycles(dut.clk, 2)             # rising edges at 5 ns and 15 ns
    dut.rst_n.value = 1                       # written after an edge: synchronous release

    sb = Scoreboard()
    cocotb.start_soon(monitor(dut, sb))       # runs alongside, like fork ... join_none
    drv = FifoDriver(dut)
    await RisingEdge(dut.clk)                 # 25 ns: first edge with rst_n = 1

    for op, data in SEQUENCE:
        if op == "W":
            await drv.write(data)
        else:
            await drv.read()

    await ClockCycles(dut.clk, 2)             # let the monitor check the last pop
    pending = len(sb.model)
    cocotb.log.info(
        "SCB_SUMMARY matches=%d mismatches=%d pending=%d",
        sb.matches, sb.mismatches, pending,
    )
    assert sb.matches > 0, "no read was checked: this run proves nothing"
    assert sb.mismatches == 0 and pending == 0, "scoreboard found errors"
```

Notice what is *not* there: no `TestFailure`, no `units=`, no `.integer`, no `dut._log`. Those are cocotb 1.x idioms.

```makefile
ifeq ($(INJECT_BUG),1)
  COMPILE_ARGS += -DINJECT_FIFO_BUG
endif

# Verilator stops on warnings by default, and the DUT compares a 3-bit count
# with the 32-bit parameter DEPTH (a width warning). Keep warnings non-fatal.
ifeq ($(SIM),verilator)
  EXTRA_ARGS += -Wno-fatal
endif

include $(shell cocotb-config --makefiles)/Makefile.sim
```

### The same bench in pyuvm 5.0

Now the architecture of [I-UVM-3C](/curriculum/T2_Intermediate/I-UVM-3C_First_Complete_Testbench/index) and its capstone lab, in Python.

**Try it first.** Before you read the code, port the lab's `fifo_driver` and `fifo_monitor` yourself, using the mapping table in [pyuvm: the same structure in Python](#pyuvm-the-same-structure-in-python). Then compare with the code below. Check four things: `create` without `type_id`; an awaited `get_next_item()`; a plain, not awaited, `item_done()`; and sampling at `FallingEdge` + `ReadOnly`, where the lab uses a clocking block.

Save the file next to the Makefile and run `make SIM=icarus COCOTB_TEST_MODULES=test_fifo_uvm`.

```python
# compile -- test_fifo_uvm.py: the I-UVM-3C capstone lab environment in pyuvm 5.0
from collections import deque

import cocotb
import pyuvm
from cocotb.clock import Clock
from cocotb.triggers import ClockCycles, FallingEdge, ReadOnly, RisingEdge
from pyuvm import (ConfigDB, uvm_active_passive_enum, uvm_agent, uvm_analysis_port,
                   uvm_driver, uvm_env, uvm_get_port, uvm_monitor, uvm_scoreboard,
                   uvm_sequence, uvm_sequence_item, uvm_sequencer, uvm_test,
                   uvm_tlm_analysis_fifo)

SEQUENCE = [
    ("W", 0x00), ("R", 0),
    ("W", 0xA5), ("W", 0x5A), ("R", 0), ("R", 0),
    ("W", 0x11), ("W", 0x22), ("W", 0x33), ("W", 0x44),
    ("R", 0), ("R", 0), ("R", 0), ("R", 0),
]


class FifoItem(uvm_sequence_item):
    def __init__(self, name="fifo_item", op="W", data=0):
        super().__init__(name)
        self.op = op          # "W" write (push) or "R" read (pop)
        self.data = data

    def __str__(self):        # plays the role of convert2string()
        return f"{self.get_name()}: op={self.op} data=0x{self.data:02x}"


class FifoCapstoneSeq(uvm_sequence):
    async def body(self):
        for op, data in SEQUENCE:
            item = FifoItem.create(f"{op}_{data:02x}")   # factory, no type_id
            await self.start_item(item)
            item.op, item.data = op, data
            await self.finish_item(item)                # returns after item_done()


class FifoDriver(uvm_driver):
    def build_phase(self):
        self.dut = ConfigDB().get(self, "", "DUT")      # raises if missing

    async def run_phase(self):
        while True:
            item = await self.seq_item_port.get_next_item()
            if item.op == "W":
                self.dut.din.value = item.data
                await self.handshake(self.dut.push, self.dut.full)
            else:
                await self.handshake(self.dut.pop, self.dut.empty)
            self.seq_item_port.item_done()

    async def handshake(self, valid, stall):
        # An item may arrive at any time: align to an edge before driving.
        await RisingEdge(self.dut.clk)
        valid.value = 1
        while True:
            await FallingEdge(self.dut.clk)
            await ReadOnly()
            ready = not stall.value
            await RisingEdge(self.dut.clk)
            if ready:
                break
        valid.value = 0


class FifoMonitor(uvm_monitor):
    def build_phase(self):
        self.ap = uvm_analysis_port("ap", self)
        self.dut = ConfigDB().get(self, "", "DUT")

    def publish(self, op, data):
        item = FifoItem.create("observed")              # a new object per transfer
        item.op, item.data = op, data
        self.ap.write(item)

    async def run_phase(self):
        dut = self.dut
        pop_pending = False
        while True:
            await FallingEdge(dut.clk)
            await ReadOnly()
            if dut.rst_n.value != 1:
                pop_pending = False
                continue
            if pop_pending:
                self.publish("R", int(dut.dout.value))
            pop_pending = bool(dut.pop.value) and not dut.empty.value
            if dut.push.value == 1 and not dut.full.value:
                self.publish("W", int(dut.din.value))


class FifoScoreboard(uvm_scoreboard):
    def build_phase(self):
        self.fifo = uvm_tlm_analysis_fifo("fifo", self)
        self.get_port = uvm_get_port("get_port", self)
        self.analysis_export = self.fifo.analysis_export  # the env connects here
        self.model = deque()
        self.matches = 0
        self.mismatches = 0

    def connect_phase(self):
        self.get_port.connect(self.fifo.get_export)

    async def run_phase(self):
        while True:
            item = await self.get_port.get()
            if item.op == "W":
                self.model.append(item.data)
            elif not self.model:
                self.mismatches += 1
                self.logger.error(f"SCB_UNDERFLOW popped 0x{item.data:02x}")
            else:
                expected = self.model.popleft()
                if item.data == expected:
                    self.matches += 1
                else:
                    self.mismatches += 1
                    self.logger.error(
                        f"SCB_MISMATCH expected 0x{expected:02x} "
                        f"observed 0x{item.data:02x}"
                    )

    def check_phase(self):
        pending = len(self.model) + self.fifo.used()
        self.logger.info(f"SCB_SUMMARY matches={self.matches} "
                         f"mismatches={self.mismatches} pending={pending}")
        # A logged error does not fail a cocotb test; an exception does.
        assert self.matches > 0, "no read was checked: this run proves nothing"
        assert self.mismatches == 0 and pending == 0, "scoreboard found errors"


class FifoAgent(uvm_agent):
    def build_phase(self):
        super().build_phase()      # reads is_active from ConfigDB (default UVM_ACTIVE)
        self.monitor = FifoMonitor.create("monitor", self)
        if self.get_is_active() == uvm_active_passive_enum.UVM_ACTIVE:
            self.sequencer = uvm_sequencer.create("sequencer", self)
            self.driver = FifoDriver.create("driver", self)

    def connect_phase(self):
        if self.get_is_active() == uvm_active_passive_enum.UVM_ACTIVE:
            self.driver.seq_item_port.connect(self.sequencer.seq_item_export)


class FifoEnv(uvm_env):
    def build_phase(self):
        self.agent = FifoAgent.create("agent", self)
        self.sb = FifoScoreboard.create("sb", self)

    def connect_phase(self):
        self.agent.monitor.ap.connect(self.sb.analysis_export)


@pyuvm.test()
class FifoTest(uvm_test):
    def build_phase(self):
        # The SV bench sets a virtual interface in tb_top; here the DUT handle.
        ConfigDB().set(None, "*", "DUT", cocotb.top)
        self.env = FifoEnv.create("env", self)

    async def run_phase(self):
        self.raise_objection()
        dut = cocotb.top
        dut.push.value = 0
        dut.pop.value = 0
        dut.din.value = 0
        dut.rst_n.value = 0
        Clock(dut.clk, 10, unit="ns").start(start_high=False)
        await ClockCycles(dut.clk, 2)
        dut.rst_n.value = 1
        seq = FifoCapstoneSeq.create("seq")
        await seq.start(self.env.agent.sequencer)
        await ClockCycles(dut.clk, 2)   # let the monitor publish the last pop
        self.drop_objection()
```

### How to build a cocotb bench for your own block

1. **Pin versions.** Install `cocotb==2.1.*` (and `pyuvm==5.0.*` if you use it); record them in `requirements.txt`.
2. **List the DUT's handshakes.** For each interface name VALID, READY and payload, and when each is sampled.
3. **Start the clock low** and drive every input to a known value at time 0, with reset asserted.
4. **Release reset right after a rising edge**, then wait one more edge before traffic.
5. **Write the driver** with the handshake pattern: drive after a rising edge, check READY at `FallingEdge` + `ReadOnly`, drop VALID after the handshake edge.
6. **Write the monitor** at `FallingEdge` + `ReadOnly`, publishing one record per transfer, with any registered response one cycle later.
7. **Write a reference model** in Python and compare in the scoreboard; count matches, mismatches and pending items.
8. **End with assertions**, not log messages, and wait for the last transfer to be observed before the test returns.
9. **Prove the bench can fail:** plant a bug (a `define` or a mutant) and check that the test fails with the error you expect.
10. **Run it on two simulators** if you can (for example Icarus and Verilator): differences point at timing-model assumptions.

**Checklist before moving on:**
- [ ] Your test imports nothing from `cocotb.result` and uses `unit=`, `cocotb.log` and `.to_unsigned()` or `int()`.
- [ ] The clock starts low, and every input is driven before the first edge.
- [ ] Reset is released by a write made just after a rising edge.
- [ ] Each VALID drops right after its handshake edge, and back-to-back transfers keep VALID HIGH only because there is more to send.
- [ ] The monitor samples at `FallingEdge` + `ReadOnly` and handles the one-cycle delay of registered outputs.
- [ ] The test fails through `assert`, and fails on the planted bug.
- [ ] You can say, for each pyuvm class you wrote, which SV UVM class it replaces and what differs.
- [ ] You can explain why simulated time stops while a breakpoint holds Python.

## Push Further

### Expert: where cocotb triggers land in the SystemVerilog scheduler

cocotb's VPI layer registers one callback reason per trigger (cocotb v2.1.0, `src/cocotb/share/lib/gpi/vpi/VpiCbHdl.cpp`): `ValueChange`, `RisingEdge` and `FallingEdge` use `cbValueChange`; `Timer` uses `cbAfterDelay`; `ReadWrite` uses `cbReadWriteSynch`; `ReadOnly` uses `cbReadOnlySynch`; `NextTimeStep` uses `cbNextSimTime`. IEEE 1800-2023 §4.10 Table 4-1 places `cbAfterDelay` and `cbNextSimTime` in **Pre-Active**, `cbReadWriteSynch` in **Pre-NBA or Post-NBA**, and `cbReadOnlySynch` in **Postponed**. The PLI regions themselves are defined in §4.4.3.

Three consequences for experts:

- **`cbValueChange` has no row in Table 4-1.** A value-change callback fires when the value changes, in whichever region performs that update (for a flop output, the NBA region; for a clock written by cocotb, the point where cocotb applies the write). Do not assign `RisingEdge` a region; assign it a *cause*.
- **"Pre-NBA or Post-NBA" is a real ambiguity.** At a `ReadWrite` callback, NBA updates of the current evaluation cycle may or may not have happened, depending on the simulator. cocotb's model hides this by saying all HDL "will have executed" at Values Settle; if your bench depends on the difference, it is not portable.
- **`cbReadOnlySynch` is in Postponed** (§4.4.3.10), the same region where `$monitor` and `$strobe` print (§4.4.2.9). That is why cocotb refuses writes there: in Postponed "it is illegal to write values to any net or variable" (§4.4.2.9).

[F3B's PLI and VPI callback regions](/curriculum/T1_Foundational/F3B_Scheduling_Regions/index#expert-pli-and-vpi-callback-regions) lists the whole table; this item settles the cocotb mapping that F3B labels tool-dependent.

**Interview angle.** "A cocotb driver writes `valid` right after `RisingEdge`. Can the DUT see it at the same edge?" With default settings, no: the write is applied at the next `cbReadWriteSynch`, after the flops have sampled. With `COCOTB_TRUST_INERTIAL_WRITES`, cocotb passes the write straight to the simulator as an **inertial write** (cocotb's VPI layer deposits with `vpi_put_value()` and the `vpiInertialDelay` flag at zero delay, IEEE 1800-2023 §38.34; when that update lands is up to the simulator) instead of queuing it, and the answer depends on the simulator (next item).

### Expert: simulator differences (tool-dependent)

All of this is tool-dependent; the source is cocotb 2.1's *Simulator Support* and *Timing Model* pages.

- **Verilator** (5.036+) is cycle-based: edge triggers behave as if followed by `await ReadWrite()`. It also enables `COCOTB_TRUST_INERTIAL_WRITES` by default (as do GHDL and NVC), and cocotb 2.0 reimplemented its evaluation loop for "behavior more consistent with event-based simulators". Verilator also needs `--public-flat-rw` (cocotb's makefile passes it) for signals to be visible.
- **VCS** is supported through VPI only, not VHPI, so VHDL top levels need another simulator.
- **Questa** can reach VHDL through the proprietary FLI or through VHPI; cocotb defaults to FLI for backward compatibility. From Questa 2025.2 cocotb's makefiles choose the newer `qrun` flow.
- **Signal visibility.** Whether `dut.u_core.some_reg` is reachable depends on the simulator's debug-access options; commercial simulators often hide internals unless you enable access at compile time. Names that are not valid Python identifiers are reached with `dut["name"]`.
- **Minimum versions** published by cocotb 2.1: Icarus 11.0+, Verilator 5.036+, NVC 1.19.1+, DSim 2025+.

**Practice.** Run the same test on two simulators in CI. A monitor bug of the "one cycle late on Verilator" kind shows up immediately.

### Expert: performance, what Python costs and how to cut it

Cost grows with Python wake-ups and GPI crossings per simulated cycle; the DUT's own cost is unchanged. Levers, roughly in order of payoff:

1. **Fewer wake-ups.** Wait for the event you need (`await RisingEdge(dut.valid)`, `ClockCycles(clk, n)`) instead of waking every cycle to poll. Combine coroutines that wake on the same edge.
2. **Fewer signal accesses.** Read a bus once into a local variable; do not read twenty signals per edge if two decide whether anything happened.
3. **A C++ clock.** `Clock(..., impl="gpi")` uses `cocotb.simulator.cpp_clock`, "a C++ clock generator implementation with higher performance due to less handshaking between Python and the GPI" (cocotb 2.0 release notes, PR 3983). If you leave `impl` out (the documented `'auto'` choice), `Clock` uses the C++ clock exactly when `COCOTB_TRUST_INERTIAL_WRITES` is enabled (the default for Verilator, GHDL and NVC), where it behaves identically, and the Python clock otherwise (cocotb 2.1 `clock.py`, `Makefile.inc`).
4. **Trusted inertial writes.** `COCOTB_TRUST_INERTIAL_WRITES=1` skips the extra `ReadWrite` callback that applies queued writes, which "can lead to noticeable performance improvements"; cocotb's docs also warn that "Not all simulators handle inertial writes properly, so use with caution" (cocotb 2.1 docs, environment variables).
5. **Move cycle-level work into HDL.** Write the pin-level bus-functional model (BFM) in SystemVerilog and exchange whole transactions with Python, so Python wakes once per transaction, not once per cycle.
6. **Measure.** cocotb's regression summary reports simulated time and real time per test; profile Python with standard tools (`cProfile`) when the ratio is poor.

Staff-level framing: the question is never "Python or not" but "how many times per cycle does control cross the language boundary, and could it cross once per transaction instead?"

### Expert: cocotb 1.x to 2.x migration traps

From cocotb's *Upgrading to cocotb 2.0* guide and the 2.0.0 and 2.1.0 release notes. Some changes break code; others only warn.

| 1.x code | cocotb 2.x | Effect |
|---|---|---|
| `from cocotb.result import TestFailure` | `assert cond, msg` | **breaks**: removed (PR 4960) |
| `cocotb.fork(coro)` | `cocotb.start_soon(coro)` | **breaks**: removed (PR 3425) |
| `BinaryValue`, `.value` returning `BinaryValue` | `LogicArray` (vectors) and `Logic` (one bit) | **breaks**: removed (PR 3634) |
| `@cocotb.coroutine` generator coroutines | `async def` | **breaks**: removed (PR 3509) |
| `dut._log.info(...)` | `cocotb.log.info(...)` | handle loggers were made private |
| `Clock(..., units="ns")`, `Timer(..., units="ns")` | `unit="ns"` | warns (PR 4455) |
| `.value.integer` | `.value.to_unsigned()` or `int(...)` | warns (PR 3792) |
| `MODULE`, `TOPLEVEL` | `COCOTB_TEST_MODULES`, `COCOTB_TOPLEVEL` | warns (PR 3644) |
| `await cocotb.start(coro)` | `cocotb.start_soon(coro)` | warns (PR 4397) |
| `await Join(task)` | `await task` | warns (PR 4084) |
| `await First(task_a, task_b)`, `await Combine(task_a, task_b)` | `await select(a(), b())`, `await gather(a(), b())` | warns in 2.1 (PR 5206); `First` and `Combine` still take triggers |
| `cocotb.start_soon(clock.start())` | `clock.start()` | still legal (`start()` now returns a Task), just redundant |

One more change has no warning at all: cocotb 2.1 "Reimplemented the scheduler. Exact scheduling order may have changed" (PR 4717). A bench that depended on which of two coroutines woken by the same trigger runs first was already racy; 2.1 may expose it. The fix is the same as for a SystemVerilog race ([F3C](/curriculum/T1_Foundational/F3C_Delta_Cycles_and_Race_Conditions/index)): remove the dependence on order.

### Expert: hybrid flows

Three different things are often confused:

- **cocotb next to an SV bench.** cocotb attaches to the simulation through VPI and touches *signals*. It can share a simulation with SystemVerilog code, but it does not call SystemVerilog tasks or UVM objects.
- **SV calling Python.** A SystemVerilog bench calls Python through DPI-C ([I-SV-7](/curriculum/T2_Intermediate/I-SV-7_DPI_and_Foreign_Language_Interfaces/index)): an `import "DPI-C"` function in C that embeds an interpreter with the Python C API. PyHDL-IF (third-party; 0.2.1 on PyPI) packages such a layer; its README (GitHub, fvutils/pyhdl-if) states that it can "invoke Python methods from SystemVerilog".
- **pyuvm** is a pure-Python UVM on top of cocotb. It is involved in neither path above; it cannot host an SV UVM agent, and an SV UVM bench cannot instantiate a pyuvm component.

A common, low-risk hybrid: keep the SV UVM environment and VIP, and call a NumPy reference model from the scoreboard through DPI-C, one call per transaction. Whether two embedded interpreters (cocotb's and a DPI layer's) can coexist in one simulator process is tool- and library-dependent; do not assume it.

### Expert: protocol libraries and randomization in Python (third-party)

- **cocotbext-axi** (0.1.28, third-party) provides AXI, AXI-Lite and AXI-Stream masters, slaves and RAM models for cocotb. Using a maintained protocol model is the practitioner's answer to the duplicate-write bug above; review its handshake behaviour once, as you would any VIP.
- **Constrained random.** Python's `random` covers uniform choices. pyvsc (Verification Stimulus and Coverage) and cocotb-coverage 2.0 (which requires `cocotb>=2.0`) add constraint solving and functional coverage. They are not part of cocotb or pyuvm, and their coverage databases are separate from your simulator's.
- **Seeds.** cocotb seeds Python's `random` from `COCOTB_RANDOM_SEED` (1.x: `RANDOM_SEED`, now deprecated), or from the time if it is unset, and logs `Seeding Python random module with <seed>` at start-up; rerun a failure with the same seed to reproduce it.

### Kata: finish porting the capstone to pyuvm

**Goal.** The pyuvm bench in Make It Work covers the capstone lab's agent, sequence and scoreboard. The SystemVerilog capstone also has a coverage subscriber (`fifo_coverage`) and sequences built for a factory override (`fifo_base_seq`, `fifo_capstone_seq`). Add both, then answer one debugging question. The level bins below are a simplified stand-in for the capstone's operation-by-depth cross, chosen so the solution stays short.

1. **Coverage.** Extend `FifoItem` with `level` (the FIFO's `level` output sampled with the other signals). Add `FifoCoverage(uvm_subscriber)` connected to the monitor's `ap`. It records the `level` at which each push and each pop was accepted, and in `check_phase` reports `COV_SUMMARY push_levels=a/4 pop_levels=b/4` and fails if either is below 4 (pushes can be accepted at levels 0 to 3; pops at 1 to 4).
2. **Factory override.** Split the sequence: `FifoBaseSeq` writes `0x11` and reads it back; `FifoCapstoneSeq(FifoBaseSeq)` runs the full traffic. The base test starts `FifoBaseSeq.create("seq")`; a second test, `FifoCapstoneTest(FifoTest)`, overrides the type in its `build_phase`.
3. **Debug.** Predict what happens if `FifoAgent.build_phase` omits `super().build_phase()`.

**Acceptance.** `FifoCapstoneTest` prints `SCB_SUMMARY matches=7 mismatches=0 pending=0` and `COV_SUMMARY push_levels=4/4 pop_levels=4/4` on the clean DUT, and fails with one `SCB_MISMATCH` with `INJECT_BUG=1`. `FifoTest` alone passes the scoreboard but fails coverage (one push at level 0, one pop at level 1).

<summary>Worked solution</summary>

```python
# snippet -- changes to test_fifo_uvm.py (pyuvm 5.0)
from pyuvm import uvm_factory, uvm_subscriber


class FifoItem(uvm_sequence_item):
    def __init__(self, name="fifo_item", op="W", data=0, level=0):
        super().__init__(name)
        self.op, self.data, self.level = op, data, level


# In FifoMonitor: sample level with the other signals, before the edge.
#   pop_level = 0                      (before the while loop)
#   level = int(dut.level.value)
#   if pop_pending: self.publish("R", int(dut.dout.value), pop_level)
#   pop_pending = bool(dut.pop.value) and not dut.empty.value
#   pop_level = level
#   if dut.push.value == 1 and not dut.full.value:
#       self.publish("W", int(dut.din.value), level)
# and publish(self, op, data, level) also sets item.level = level.


class FifoCoverage(uvm_subscriber):
    def build_phase(self):
        self.push_levels = set()
        self.pop_levels = set()

    def write(self, item):
        (self.push_levels if item.op == "W" else self.pop_levels).add(item.level)

    def check_phase(self):
        pushes = len(self.push_levels & {0, 1, 2, 3})
        pops = len(self.pop_levels & {1, 2, 3, 4})
        self.logger.info(f"COV_SUMMARY push_levels={pushes}/4 pop_levels={pops}/4")
        assert pushes == 4 and pops == 4, "coverage holes"


class FifoBaseSeq(uvm_sequence):
    async def send(self, op, data):
        item = FifoItem.create(f"{op}_{data:02x}")
        await self.start_item(item)
        item.op, item.data = op, data
        await self.finish_item(item)

    async def body(self):
        await self.send("W", 0x11)
        await self.send("R", 0)


class FifoCapstoneSeq(FifoBaseSeq):
    async def body(self):
        for op, data in SEQUENCE:
            await self.send(op, data)


# In FifoEnv:
#   build_phase:   self.cov = FifoCoverage.create("cov", self)
#   connect_phase: self.agent.monitor.ap.connect(self.cov.analysis_export)
# In FifoTest.run_phase: seq = FifoBaseSeq.create("seq")


@pyuvm.test()
class FifoCapstoneTest(FifoTest):
    def build_phase(self):
        uvm_factory().set_type_override_by_type(FifoBaseSeq, FifoCapstoneSeq)
        super().build_phase()
```

**Why the levels are complete.** With the capstone traffic, pushes are accepted at levels 0, 0, 1, 0, 1, 2 and 3, and pops at 1, 2, 1, 4, 3, 2 and 1: all four bins of each. `FifoBaseSeq` alone reaches only push level 0 and pop level 1, which is why the coverage check fails `FifoTest`.

**Why the monitor keeps `pop_level`.** The pop is decided at one falling edge and its data published at the next; by then `level` has changed, so the level must be saved when the decision is made.

**Debug answer.** `uvm_agent.build_phase` is what sets `self.is_active` (it reads `is_active` from `ConfigDB`, defaulting to `UVM_ACTIVE`). Without the `super()` call, `self.get_is_active()` raises `AttributeError: 'FifoAgent' object has no attribute 'is_active'` during build, at time 0, and the test fails before any simulated time passes. In SystemVerilog the same omission is silent: `is_active` keeps its default `UVM_ACTIVE`, so the bug only shows when someone tries to make the agent passive.

### Debug challenge: the slave got two writes

A colleague's AXI4-Lite test (the snippet under [Driving a valid/ready interface](#driving-a-validready-interface)) passes on one slave and fails on another with "unexpected write to 0x00". The failing slave raises AWREADY at edges 2 and 4, and BVALID first at edge 5.

1. At which edges do write-address transfers happen?
2. Why does the test pass on the other slave?
3. Rewrite the write so that it is correct on every slave.

<details>
<summary>Answer</summary>

1. At edges 2 and 4: AWVALID is HIGH from edge 1 to edge 5, and both edges have AWREADY HIGH (IHI0022E §A3.2.1).
2. The other slave keeps AWREADY LOW after the first address until it has sent the response, so only one edge has both signals HIGH. The test was relying on a slave's choice that the protocol does not require.
3. Handle each channel separately: raise AWVALID, wait for its handshake edge with the pattern from Build Your Mental Model, and lower it; do the same for WVALID; then hold BREADY and wait for the edge with BVALID and BREADY HIGH, and check that BRESP is `0` (OKAY). Or use a maintained model such as cocotbext-axi's AXI-Lite master.
