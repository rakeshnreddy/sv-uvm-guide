## Quick Take

- **What it is:** A **methodology layer** is a thin, versioned package of base classes, helpers, conventions and checks that every block team builds its testbench (TB) on. It sits on top of an **unmodified, pinned** copy of the UVM library: uvm-core 2020.3.1, the Accellera reference implementation of IEEE 1800.2-2020. You customize UVM through the extension points the standard already gives you (base classes, factory overrides, callbacks, configuration objects, the report server, phase callbacks, default sequences). A **custom phase**, a new step added to UVM's phase schedule, is a rare, last-resort part of the layer.
- **Why it matters:** Without a layer, each block team reinvents configuration plumbing, log formats and pass/fail rules, and an SoC team inherits ten incompatible benches. With a **fork** of uvm-core (a copy whose sources your team edits), you can no longer upgrade, share verification IP (VIP) built against the stock library, or file a bug report anyone else can reproduce. The layer gives you the consistency without the fork.
- **The Analogy:** A company style guide plus a shared helper library on top of a language's standard library. You add helpers and rules; you never edit the standard library itself. *Where it breaks:* some UVM customizations are not opt-in helpers. A custom phase, a new phase domain or a replaced report server changes behaviour for **every** component in the simulation, including VIP that has never heard of your project, which is closer to patching the language runtime than adding a library. That is why those three need the strongest justification.

**You will be able to:**
1. **Design** a project base layer (role bases for drivers and monitors, an item base, a sequence base, a base test, a configuration helper and reporting conventions) on an unmodified uvm-core, and **justify** each addition.
2. **Choose** the UVM extension point (factory override, callback, configuration object, report server or catcher, phase callback, default sequence) that meets a team requirement without forking uvm-core.
3. **Implement** a custom run-time phase (a `uvm_task_phase` with `exec_task`, inserted with `uvm_phase::add`), **predict** where and when it runs, and **explain** why most teams avoid custom phases.
4. **Define** governance: coding guidelines, lint rules, an honest CI gate, and a pinned uvm-core version.
5. **Diagnose** methodology drift (phase misordering, bypassed bases, version drift) from phase traces, factory and topology prints, and lint output.

## Build Your Mental Model

**How to read this lesson.** The core path is four sections: customize without forking, the project base layer, custom phases (with the visualizer), and when not to add a custom phase. Practitioner depth follows: where a new phase lands in the schedule, governance and CI gates, and diagnosing methodology drift. Make It Work builds a complete custom-phase test you can run and break, and Push Further holds the expert corner cases.

Words this page uses, in one line each (each links to where it is taught in full):

- A **component** is an object of a class derived from `uvm_component`; components form a tree that lives for the whole run ([I-UVM-1A](/curriculum/T2_Intermediate/I-UVM-1A_Components/index)).
- A **phase** is one named step of a UVM run, such as `build_phase` or `run_phase`, that UVM calls on every component. The twelve **run-time phases** (`pre_reset_phase` … `post_shutdown_phase`) are tasks that run one after another *beside* `run_phase`. An **objection** is a component's "not finished yet" flag: a task phase ends when every objection to it has been dropped ([I-UVM-1C](/curriculum/T2_Intermediate/I-UVM-1C_UVM_Phasing/index)).
- A **schedule** is a graph of phase nodes that says which phase follows which. A **domain** is a group of components that move through one schedule together. Every component starts in the `uvm` domain, whose schedule (`uvm_sched` in uvm-core) holds the twelve run-time phases; the separate `common` domain holds `build` … `final`.
- The **factory** creates objects by type so a test can swap in a derived type, an **override** ([I-UVM-1B](/curriculum/T2_Intermediate/I-UVM-1B_The_UVM_Factory/index)). A **callback** is a hook object that a component calls at a point its author chose ([A-UVM-5](/curriculum/T3_Advanced/A-UVM-5_UVM_Callbacks/index)). The **configuration database** (`uvm_config_db`) passes settings down the tree by path ([I-UVM-2C](/curriculum/T2_Intermediate/I-UVM-2C_Configuration_and_Resources/index)).
- **Forking a library** means copying its sources into your project and editing them. It has nothing to do with the SystemVerilog `fork` statement, which this page also uses.

### Customize without forking

A methodology layer answers one question for a team: "where does project-specific behaviour live?" The answer must never be "inside uvm-core". UVM was designed to be extended from the outside, and IEEE 1800.2-2020 standardizes each extension point. Pick the point by the requirement, not by habit:

| Team requirement | Extension point (no fork) | Standard | Taught in |
|---|---|---|---|
| Every block driver gets the project config and the same hooks | A role base class: `proj_driver #(REQ) extends uvm_driver #(REQ)` | §13.7; IEEE 1800-2023 §8.13 | this lesson |
| One test swaps a component or item type | Factory type or instance override | §8.3.1.4.1–8.3.1.4.2 | [I-UVM-1B](/curriculum/T2_Intermediate/I-UVM-1B_The_UVM_Factory/index) |
| Add behaviour at a point a VIP author exposed (error injection, coverage) | Callbacks | §10.7 | [A-UVM-5](/curriculum/T3_Advanced/A-UVM-5_UVM_Callbacks/index) |
| Per-test knobs read by many components | A configuration object through the configuration database | Annex C.4 | [I-UVM-2C](/curriculum/T2_Intermediate/I-UVM-2C_Configuration_and_Resources/index) |
| One log-line format for the whole project | Extend `uvm_default_report_server`, override `compose_report_message`, install with `uvm_report_server::set_server` | §6.5.2, §6.5.1.2.15, §6.5.1.2.19 | [I-UVM-1D](/curriculum/T2_Intermediate/I-UVM-1D_Reporting_and_Run_Control/index) and below |
| Demote or promote one known message | A report catcher | §6.6 | [E-DBG-1](/curriculum/T4_Expert/E-DBG-1_Advanced_UVM_Debug_Methodologies/index) |
| Run project code when any phase starts or ends | `phase_started` / `phase_ended` in the base class | §13.1.4.3.1, §13.1.4.3.3 | this lesson |
| Start a sequence automatically in a phase | A default sequence | §15.3.5, Annex G.2.9 | [I-UVM-3A](/curriculum/T2_Intermediate/I-UVM-3A_Fundamentals/index) |
| Change how objects print, compare or copy | Policy classes (`uvm_printer`, `uvm_comparer`, `uvm_copier`) | §16.2, §16.3, §16.6 | [I-UVM-4](/curriculum/T2_Intermediate/I-UVM-4_UVM_Policy_Classes/index) |
| A step that no existing phase or sequence can express | A custom phase (rare) | §9.3.1.1.1, §9.3.1.6.1, §9.6 | this lesson |

Every row is a way to *add* code that UVM calls. None of them edits uvm-core. Before you read on, look at the diagram and find where each row of the table plugs in.

**Misconception: "forking uvm-core is acceptable for team conventions."** It looks cheap: one edited line in `uvm_report_server.svh` and every log has your format. The bill comes later:

- **No clean upgrade.** Every uvm-core release must be re-merged by hand, so teams stop upgrading, and bug fixes never arrive.
- **VIP mismatch.** Commercial and in-house VIP is compiled and qualified against stock uvm-core. Behaviour it relies on may no longer hold in your copy.
- **Unreproducible bugs.** A bug report against "uvm-core plus our patches" cannot be reproduced by the tool vendor, the VIP vendor or Accellera.
- **Hidden behaviour.** New engineers read the standard and the public source and get a different answer from your simulation.

If you find a real bug in uvm-core, report it upstream and work around it in your layer (for example with a derived class and a factory override) until the fix ships.

### The project base layer

A **base layer** is the set of classes your block teams extend instead of the raw UVM classes. Each class earns its place by removing a decision that every team would otherwise make differently. SystemVerilog has **single inheritance**: "each class is derived from a single base class" (IEEE 1800-2023 §8.13). So the layer is a set of **per-role** bases, one beside each UVM role class, not one project root above everything. A class derived from a `proj_component extends uvm_component` root could never also be a `uvm_driver`, and would lose the driver's `seq_item_port` (§13.7.2.1).

```systemverilog
// snippet: proj_pkg, the project layer (inside a package that imports uvm_pkg)
class proj_config extends uvm_object;
  `uvm_object_utils(proj_config)
  bit    enable_coverage = 1;
  bit    enable_security_checks;
  string firmware_image;

  function new(string name = "proj_config");
    super.new(name);
  endfunction
endclass

// One lookup for every component: one key, one failure message that names the culprit.
class proj_cfg_util;
  static function proj_config get(uvm_component c);
    proj_config cfg;
    if (!uvm_config_db #(proj_config)::get(c, "", "proj_cfg", cfg))
      `uvm_fatal("PROJ/NO_CFG", {"proj_config missing for ", c.get_full_name(),
                                 ": set it in proj_base_test"})
    return cfg;
  endfunction
endclass

// Drivers: keep uvm_driver (and its seq_item_port), add the config and a policy hook.
class proj_driver #(type REQ = uvm_sequence_item) extends uvm_driver #(REQ);
  `uvm_component_param_utils(proj_driver #(REQ))
  proj_config cfg;

  function new(string name, uvm_component parent);
    super.new(name, parent);
  endfunction

  function void build_phase(uvm_phase phase);
    super.build_phase(phase);
    cfg = proj_cfg_util::get(this);
  endfunction

  // Block teams override this hook instead of editing the base.
  virtual function void apply_project_policy();
  endfunction

  function void end_of_elaboration_phase(uvm_phase phase);
    super.end_of_elaboration_phase(phase);
    `uvm_info("PROJ/BASE", {"proj_driver base active in ", get_full_name()}, UVM_HIGH)
    apply_project_policy();
  endfunction
endclass

// Monitors: keep the uvm_monitor type (§13.5) and declare the analysis port here,
// because uvm_monitor itself declares no port.
class proj_monitor #(type T = uvm_sequence_item) extends uvm_monitor;
  `uvm_component_param_utils(proj_monitor #(T))
  proj_config cfg;
  uvm_analysis_port #(T) ap;

  function new(string name, uvm_component parent);
    super.new(name, parent);
    ap = new("ap", this);
  endfunction

  function void build_phase(uvm_phase phase);
    super.build_phase(phase);
    cfg = proj_cfg_util::get(this);
  endfunction
endclass

// Items: one error-injection flag and one log format for every protocol.
class proj_item extends uvm_sequence_item;
  `uvm_object_utils(proj_item)
  bit inject_error;   // set by error tests, read by drivers and scoreboards

  function new(string name = "proj_item");
    super.new(name);
  endfunction

  // Convention: block items override convert2string() with their fields;
  // the base adds the common prefix so every log line parses the same way.
  function string to_log();
    return $sformatf("[%s%s] %s", get_type_name(), inject_error ? " ERR" : "",
                     convert2string());
  endfunction
endclass

// Sequences: a typed handle to the project config without each sequence looking it up.
class proj_base_seq #(type REQ = proj_item) extends uvm_sequence #(REQ);
  `uvm_object_param_utils(proj_base_seq #(REQ))
  proj_config cfg;

  function new(string name = "proj_base_seq");
    super.new(name);
  endfunction

  virtual task pre_start();
    if (cfg == null && get_sequencer() != null)
      cfg = proj_cfg_util::get(get_sequencer());
  endtask
endclass

// Tests: version pin, timeout, config object and report conventions, written once.
class proj_base_test extends uvm_test;
  `uvm_component_utils(proj_base_test)
  localparam string PINNED_UVM = "Accellera:1800.2:UVM:2020.3.1";
  proj_config cfg;

  function new(string name, uvm_component parent);
    super.new(name, parent);
  endfunction

  function void build_phase(uvm_phase phase);
    super.build_phase(phase);
    if (UVM_VERSION_STRING != PINNED_UVM)
      `uvm_fatal("PROJ/UVM_VERSION", {"compiled against ", UVM_VERSION_STRING,
                                      "; proj_pkg is pinned to ", PINNED_UVM})
    uvm_root::get().set_timeout(10ms);   // a hang ends as a UVM_FATAL, not a killed job
    cfg = proj_config::type_id::create("cfg");
    set_knobs(cfg);
    uvm_config_db #(proj_config)::set(this, "*", "proj_cfg", cfg);
  endfunction

  // Derived tests override this instead of rewriting build_phase.
  virtual function void set_knobs(proj_config cfg);
  endfunction
endclass
```

Before you read the justification table, cover it and say, for each class, which decision it takes away from a block team.

| Addition | What it removes from every block team | Why it is shaped this way |
|---|---|---|
| `proj_config` | Inventing knob names and where they live | One object, set once by the base test, read by everyone |
| `proj_cfg_util::get` | Twenty slightly different `uvm_config_db::get` calls with silent failures | One key and a fatal that names the component whose lookup failed |
| `proj_driver #(REQ)` | Re-fetching config and forgetting project hooks | Keeps `uvm_driver` so `seq_item_port` still exists; the hook runs from `end_of_elaboration_phase` |
| `proj_monitor #(T)` | Choosing the analysis port's name and type | Keeps the `uvm_monitor` type, which lets tools and code tell monitors apart (§13.5); the port is declared here because `uvm_monitor` has none |
| `proj_item` | Ad-hoc error flags and log formats per protocol | Scoreboards and log parsers see the same prefix everywhere |
| `proj_base_seq #(REQ)` | Each sequence finding its own config | Uses `get_sequencer()` (a component) as the lookup context |
| `proj_base_test` | Forgetting the timeout, the version check or the config | Each rule is written once and inherited; `set_knobs` is the only thing a test writes |

**Reporting conventions** belong in the layer too, written as rules rather than code ([I-UVM-1D](/curriculum/T2_Intermediate/I-UVM-1D_Reporting_and_Run_Control/index) teaches the mechanisms):

- **ID taxonomy:** `<BLOCK>/<TOPIC>`, for example `APB/PROTOCOL` or `PROJ/NO_CFG`, so one `+uvm_set_action` or catcher can target a whole family.
- **Verbosity policy:** nothing per-transaction at `UVM_LOW` or below; regressions run at `UVM_LOW`; debug reruns raise one component and one ID.
- **One line format:** if the project needs extra fields in every line, change the format once in a project report server, never by editing uvm-core:

```systemverilog
// snippet: proj_pkg, one log-line format for the whole project
class proj_report_server extends uvm_default_report_server;
  string test_name = "unknown";

  function new(string name = "proj_report_server");
    super.new(name);
  endfunction

  // Append, never prepend: regression parsers anchor on the leading severity.
  virtual function string compose_report_message(uvm_report_message report_message,
                                                 string report_object_name = "");
    return {super.compose_report_message(report_message, report_object_name),
            " [test=", test_name, "]"};
  endfunction
endclass

// In proj_base_test::build_phase, once per run:
//   proj_report_server srv = new();
//   srv.test_name = get_type_name();
//   uvm_report_server::set_server(srv);   // copies the existing counts (§6.5.1.2.19)
```

`uvm_report_server` itself is a virtual class whose methods are pure virtual (§6.5.1.1, §6.5.1.2.15), so you extend `uvm_default_report_server`, which "provides a full implementation" (§6.5.2), and override only what you change.

**Pitfalls in base classes**, each with why it bites:

- **A forgotten `super.<phase>()`.** If a block driver overrides `end_of_elaboration_phase` without calling `super.end_of_elaboration_phase(phase)`, the base's `apply_project_policy()` call never runs, silently. Make it a lint rule (Governance, below).
- **A hook named like a phase.** A method called `post_configure()` in a component is easily confused with the run-time phase `post_configure_phase` (§9.8.2.6). Name hooks by intent: `apply_project_policy`.
- **Parameterized bases have no factory name.** Classes registered with `` `uvm_component_param_utils `` or `` `uvm_object_param_utils `` are registered without a type name, so name-based lookup (`create_component_by_name`, or `+uvm_set_type_override`, Annex G.2.7) cannot find them; use type-based overrides (uvm-core `uvm_object_defines.svh`, the comment above the B.2.1.3 macros).
- **Abstract bases.** A `virtual class` base with `pure virtual` hooks must use `` `uvm_component_abstract_param_utils `` (B.2.1.3), because the factory cannot construct a virtual class. The kata at the end of this page uses one.
- **Bases that hide cost.** A base whose `run_phase` calls `uvm_config_db::get` per transaction, or formats messages that are then filtered, multiplies that cost by every block in the SoC. Look up configuration in `build_phase`; [E-PERF-1](/curriculum/T4_Expert/E-PERF-1_UVM_Performance/index) measures the rest.

**Where it lives in a real TB.** `proj_pkg` is compiled once per project, after `uvm_pkg` and before any block package, and every block package imports it. **When not to add a base:** if a behaviour is optional per test (error injection, extra coverage), a callback or an override is better than a base-class method that every component carries.

### Custom phases: the mechanism

The standard explicitly allows new phases: "Users and implementations may add run-time phases before or after any of these specified phases" (IEEE 1800.2-2020 §9.8.2). §9.3.1.1.1 gives the recipe. A custom **task phase** (one that may consume simulation time) needs exactly three parts:

1. **A phase class, instantiated once.** Extend `uvm_task_phase` (§9.6) and provide a static `get()` that always returns the same object. The standard calls this object the phase **IMP** (implementation): "instantiated once as a singleton IMP … and one or more times as nodes in a graph" (§9.2.1). Give it a `protected` constructor, as uvm-core does for every built-in phase, so nobody can create a second one.
2. **An `exec_task` override.** For every component in the phase's domain, UVM forks one call to `exec_task(comp, phase)` (§9.6, §9.3.1.5.2). That proxy is the only path by which your component's *task* code runs in the new phase, and the inherited `exec_task` is empty. Your override casts `comp` to the class that has the method and calls it.
3. **One `add()` call on the container that holds the anchor.** `uvm_phase::add(phase, with_phase, after_phase, before_phase, …)` (§9.3.1.6.1) creates a new **schedule node** that refers to the IMP and links it into the graph. The anchors "shall already exist in the schedule or domain" you call `add()` on.

```systemverilog
// snippet: the three parts (the complete, compilable file is in Make It Work)
typedef class soc_env;   // forward declaration: exec_task only needs a handle type

class load_fw_phase_c extends uvm_task_phase;
  local static load_fw_phase_c m_inst;

  protected function new(string name = "load_fw");   // 1. only get() constructs it
    super.new(name);
  endfunction

  static function load_fw_phase_c get();
    if (m_inst == null) m_inst = new();
    return m_inst;
  endfunction

  // 2. Forked once per component in the domain; only soc_env has work to do.
  virtual task exec_task(uvm_component comp, uvm_phase phase);
    soc_env env;
    if ($cast(env, comp)) env.load_fw_phase(phase);
  endtask
endclass

// 3. In the test's build_phase, before any run-time phase starts.
//    get_uvm_schedule() is uvm-core impl. (not in IEEE 1800.2-2020; see Push Further).
uvm_domain::get_uvm_schedule().add(load_fw_phase_c::get(),
                                   .after_phase(uvm_reset_phase::get()));
```

**IMP versus node.** `get()` always returns the same IMP, but every `add()` builds a *new* node that points to it (uvm-core `uvm_phase.svh`, `add()`). Two `add()` calls therefore put two `load_fw` nodes in the schedule, and the phase runs twice. Register once, from one place. A static "already added" bit in the test is the usual guard; the danger is an `add()` placed in a class that has several instances (an env or an agent), or reached from two code paths. (A second *test* is not the danger: one simulation runs one test.)

**Classic mistake: no `exec_task`.** The class compiles, `add()` succeeds, the phase starts and ends at once, and nothing in `soc_env` runs. UVM never calls a component method because its *name* matches the phase (`load_fw_phase`); only your `exec_task` makes that call. The built-in phases work the same way: `uvm_main_phase` has an `exec_task` that calls `comp.main_phase(phase)`.

**Why `typedef class soc_env;` is enough here, but not everywhere.** A forward typedef (IEEE 1800-2023 §8.27) lets `exec_task` declare a handle, `$cast` to it and call a method through it before `soc_env` is defined. It does not let other code use `soc_env::type_id` before the definition: selecting a type with `::` through an incomplete forward type is illegal (§6.18, whose own example is `C::T x; // illegal`). So define `soc_env` before any class that calls `soc_env::type_id::create`, as Make It Work does.

**What the model showed, and why:**

1. **`PH_BAD_ADD` during `build_phase`.** `add()` looks up its anchor with `find(..., stay_in_scope = 1)`, which searches only "this phase's schedule and domain" (§9.3.1.4.4). The common domain holds `build` … `final`; `reset` lives in the `uvm` domain's schedule, so it is not found: `UVM_FATAL [PH_BAD_ADD] cannot find after_phase 'reset' within node 'common'`.
2. **Its own slot, in series:** `reset → load_fw → post_reset`. With only `after_phase`, `add()` moves `reset`'s successors to the new node, so `post_reset` now waits for `load_fw`.
3. **A parallel branch.** `reset` and `configure` are not neighbours (`post_reset` and `pre_configure` lie between them), so `add()` creates a branch from `reset` to `configure` beside the existing phases. `post_reset` starts when `reset` ends, at the same time as `load_fw`, and `configure` waits for both paths.
4. **A parallel branch beside `main`,** sharing `main`'s predecessor and successor. `post_main` cannot start until `load_fw` ends too.
5. **It runs, but calls nothing.** The phase starts, nobody raises an objection, it ends at once, and `soc_env.load_fw_phase` never runs. In a real log the only evidence is a phase-trace line saying the phase was skipped (Diagnosing drift, below).
6. **Legal on the common domain, fatal on the uvm schedule.** `extract` lives in the common domain, so the second form fails with `PH_BAD_ADD`. The first form runs, but in a dangerous place: after `run_phase` ended, its threads were killed (drivers and monitors stopped), `extract_phase` has already collected results, and uvm-core's timeout watchdog guards only `run_phase` (F.7.3.3 applies the timeout "in uvm_run_phase"), so a hang there is never timed out.

### Where a new phase lands

`add()` takes at most one *predecessor* argument (`with_phase`, `after_phase` or `start_with_phase`) and at most one *successor* argument (`with_phase`, `before_phase` or `end_with_phase`) (§9.3.1.6.1). The rules you need in practice, all derived from uvm-core's `add()`:

| Call | Result | Who waits for whom |
|---|---|---|
| `.after_phase(A)` | Series: `A → new → (A's old successors)` | Everything after `A` now waits for `new` |
| `.before_phase(B)` | Series: `(B's old predecessors) → new → B` | `B` waits for `new` |
| `.after_phase(A), .before_phase(B)` with `A`, `B` neighbours | Series between them | as above |
| `.after_phase(A), .before_phase(B)` with phases between them | Parallel branch from `A` to `B` | `B` waits for both paths |
| `.with_phase(C)` | Parallel with `C`, same predecessors and successors | `C`'s successors wait for both |
| no anchor | Appended at the end of the container | the container's end waits for it |

uvm-core also refuses an after/before pair in the wrong order (`PH_BAD_ADD … is not before phase …`) and two predecessor arguments at once.

**Edit the schedule in `build_phase`.** The run-time phases start after `start_of_simulation_phase` (§9.8.2), so a schedule edited during `build_phase` is complete before any of them begins. Registering from the test's `build_phase` (or a static function it calls) also gives one obvious owner.

**Time can pass in a phase nobody objects to.** "If two (or more) phases … share a common successor … phase advancement is delayed until all predecessors of the common successor are ready" (§9.6). In setting 3 above, `pre_configure` has nothing to do, yet it cannot finish into `configure` until `load_fw` has ended, so it stays open for 20 ns with no objection. This is the same rule that keeps `run_phase` open until `post_shutdown_phase` ends.

**A task phase must not share a successor with a function phase.** §9.6: "A task phase shall not share a successor with a topdown_phase or bottomup_phase, as that setup could try to make the topdown_phase or bottomup_phase consume time." For example, `get_common_domain().add(my_task_phase_c::get(), .with_phase(uvm_extract_phase::get()))` makes a time-consuming phase run beside the zero-time `extract` and share its successor `check`. uvm-core's `add()` does not check for this, so nothing warns you; treat it as a review rule.

### When not to add a custom phase

**Misconception: "custom phases are the standard way to add reset or configuration steps."** They are legal and standardized, but most teams avoid them, for concrete reasons:

- **Global reach.** The new node runs for every component in its domain, and forks one `exec_task` per component (§9.6), including third-party VIP that has no code for it.
- **Ownership.** The schedule is shared, global state. Two block teams that each add "their" phase interact in ways neither designed.
- **Jumps re-run it.** A phase jump back to `reset` (§9.3.1.9.1) re-runs every phase after it, including your custom one, so its work must be safe to repeat.
- **Portability.** The usual insertion calls (`get_uvm_schedule()`, `get_common_domain()`) are uvm-core implementation, not IEEE 1800.2-2020 API.
- **Separate domains do not see it.** A VIP placed in its own domain gets a fresh copy of the run-time schedule without your phase (Push Further).
- **The existing phases already exist for this.** Twelve run-time phases leave room for almost any ordering need.

Choose the mechanism by the requirement:

| Requirement | Preferred mechanism | Why |
|---|---|---|
| Wait for PLL lock after reset | `post_reset_phase` in the env, or the first step of the top virtual sequence | An existing phase with exactly this meaning |
| Load firmware before registers are programmed | `pre_configure_phase` or `configure_phase` work, or a step of the top virtual sequence | Same ordering, no new node |
| Several components must reach a checkpoint together | `uvm_event` or `uvm_barrier` ([I-UVM-1C](/curriculum/T2_Intermediate/I-UVM-1C_UVM_Phasing/index)) | Synchronizes exactly the components involved |
| Per-test ordering of stimulus | The top virtual sequence ([I-UVM-3B](/curriculum/T2_Intermediate/I-UVM-3B_Advanced_Sequencing_and_Layering/index)) | Tests own stimulus, not the schedule |
| A VIP needs its own reset and configure cadence | A separate domain (Push Further) | Isolates the VIP instead of changing everyone's schedule |
| A project-wide step that every component must take part in, which no existing phase names, and that a sequence cannot express | A custom phase, owned by the methodology team, added once by `proj_base_test` | The rare case the mechanism exists for |

Reset strategy in depth (reset-aware drivers, mid-test reset) is taught in [A-UVM-9](/curriculum/T3_Advanced/A-UVM-9_Reset_and_Error_Injection/index); this lesson only needs the decision above.

### Governance: guidelines, lint, CI gates, pinned versions

**Governance** is how the layer stays the layer: written rules, automatic checks that enforce them, and a release process for `proj_pkg`. Four parts:

1. **Coding guidelines.** A short document with the rules from this page: extend the project bases, register with the `` `uvm_*_utils `` macros, look up configuration in `build_phase`, objections only in tests or top sequences, report only through the UVM macros with `<BLOCK>/<TOPIC>` IDs, custom phases only from the methodology team.
2. **Lint rules.** Text checks that run on every merge request. Make each one precise, or teams learn to ignore it:

   | Rule | What it catches | Scope |
   |---|---|---|
   | `extends uvm_driver` or `extends uvm_monitor` outside `proj_pkg` | A bypassed base | Block code only: `proj_pkg` itself, scoreboards (`uvm_scoreboard`) and helpers (`uvm_component`) legitimately extend UVM classes |
   | An override of `*_phase` with no `super.` call in its body | A base hook that never runs | All components |
   | `uvm_config_db` `get` inside `run_phase` or a task it calls | Per-transaction lookups | All components |
   | `raise_objection` in a driver or monitor | Objections owned by the wrong component | Drivers, monitors |
   | `$display`, `$error` in UVM classes | Messages the report server never counts | All UVM code |
   | `uvm_domain::get_uvm_schedule().add` or `get_common_domain().add` outside `proj_pkg` | Unowned custom phases | All code |
   | `return CAUGHT` in a report catcher without a narrow ID and message match, or a type-wide `uvm_report_cb::add(null, …)` | A catcher that can hide real errors from the counts | Catcher code; the narrow catchers of reviewed error-injection tests are exempt by name |
   | `UVM_NO_ACTION` for `UVM_ERROR` or `UVM_FATAL`, or a `+uvm_set_severity` that demotes them | Errors removed before they are counted | Regression command lines and run scripts |

3. **An honest CI gate.** A run passes only if **all** of these hold, each for a reason ([I-UVM-1D](/curriculum/T2_Intermediate/I-UVM-1D_Reporting_and_Run_Control/index) and [E-DBG-1](/curriculum/T4_Expert/E-DBG-1_Advanced_UVM_Debug_Methodologies/index) show the failures each one catches). Six of them are E-DBG-1's gate rules written as pass conditions; the exit status is the one this page adds:
   - the `--- UVM Report Summary ---` block is present (a missing summary means a crash, a kill or a `$fatal`);
   - `UVM_ERROR :    0` and `UVM_FATAL :    0` in that summary, matched with anchored patterns;
   - no assertion failures and no simulator-format errors anywhere in the log, because an SVA or `$error` failure does not enter the UVM counts;
   - the simulator exit status is 0: a non-zero status always fails, but 0 alone proves nothing, since UVM ends passing and failing runs alike with `$finish`;
   - an activity floor: every checker reports a positive count (for example `matched > 0`), and the log names the test that was meant to run;
   - the catcher summary shows no caught or demoted errors, unless the test is on a reviewed list of error-injection tests that check their own counts: a caught report ends processing before it is counted (§6.5.1.2.14), and a demoted one is counted at its new severity. This check needs the run at `UVM_LOW` or above, as the verbosity policy sets: uvm-core prints the catcher summary at `UVM_LOW` (uvm-core impl.: `uvm_report_catcher::summarize`), so at `UVM_NONE` it is absent even when a catcher caught errors, and the check proves nothing;
   - the command line sets no `UVM_NO_ACTION` for `UVM_ERROR` or `UVM_FATAL`, and the log holds no `INVLCMDARGS` warning (uvm-core impl.: a `+uvm_set_*` setting that was malformed or never took effect), because a report whose action is `UVM_NO_ACTION` is dropped before it is counted (§6.5.1.2.14).
4. **A pinned uvm-core version.** Every project compiles against one uvm-core release, and the base test proves it at run time by comparing `uvm_pkg::UVM_VERSION_STRING` with the pinned string, as `proj_base_test` does above. The parameter is standard (IEEE 1800.2-2020 B.7.2); only its *value* is implementation-defined, and uvm-core 2020.3.1 gives `"Accellera:1800.2:UVM:2020.3.1"` (`src/base/uvm_version.svh`). `proj_pkg` itself is versioned too: breaking changes to a base class bump its major version and ship with a migration note.

### Diagnosing methodology drift

**Methodology drift** is the slow divergence between what the layer says and what the benches do. It has three common forms, and each leaves evidence you can collect in one run. The trace plusargs below are uvm-core implementation (none of them is in IEEE 1800.2-2020); `print_topology` (F.7.4.2) and the factory `print` (§8.3.1.7.5) are standard.

| Symptom | Evidence to collect | Cause | Fix |
|---|---|---|---|
| `load_fw` work never happens; `configure_phase` complains | `+UVM_PHASE_TRACE`: `load_fw` starts and is skipped in the same time slot | No `exec_task`, or its `$cast` targets the wrong class | Add or fix `exec_task` |
| `UVM_FATAL [PH_BAD_ADD]` at time 0 | The message names the container it searched (`within node 'common'`) | Anchor and container do not match | Call `add()` on the container that holds the anchor |
| A custom phase runs twice | Two `load_fw` start lines in the phase trace; a counter shows 2 | `add()` called twice | Register once, from the test |
| One block ignores project settings; its config errors appear late | The `PROJ/BASE` lines (at `UVM_HIGH`) list every component built on a base; compare them with `print_topology()`. Lint finds the source line | A bypassed base (`extends uvm_driver` directly) | Migrate the class to `proj_driver`; keep the lint rule on |
| An override "does nothing" | `uvm_factory::get().print()` shows the override registered, but the topology shows the original type | The component was created with `new` instead of `type_id::create`, or created before the override was set | Create through the factory; set overrides before the parent's `build_phase` creates the child |
| Behaviour changes after a tool or library update | The `PROJ/UVM_VERSION` fatal, or the version string in the log header differs from last week's | Version drift | Restore the pinned release, or upgrade deliberately with a regression |
| A knob is set but ignored | `+UVM_CONFIG_DB_TRACE`, or `check_config_usage()` in `report_phase` (both uvm-core impl.) | Wrong path or key | Fix the path or key |

A traced log excerpt for the first row (uvm-core 2020.3.1 message IDs and texts; the `UVM_INFO` prefix is shortened to the time, and the full phase names and instance ids are illustrative):

```text
@ 50 [PH/TRC/STRT] Phase 'uvm.uvm_sched.load_fw' (id=…) Starting phase
@ 50 [PH/TRC/SKIP] Phase 'uvm.uvm_sched.load_fw' (id=…)
     No objections raised, skipping phase
@ 50 [PH/TRC/STRT] Phase 'uvm.uvm_sched.post_reset' (id=…) Starting phase
```

`load_fw` starts and is skipped at the same time as `reset` ends: the phase exists, but nothing in it objected. With a working `exec_task` you would see `PH/TRC/DONE` for `load_fw` 20 ns later instead.

### Recap

- Customize UVM through its extension points; never edit uvm-core. Pick the point by the requirement.
- The base layer is one base per UVM role (single inheritance), plus a config helper, an item base, a sequence base and a base test, each removing one decision from block teams.
- A custom task phase is three parts: a singleton IMP with a protected constructor, an `exec_task` proxy, and one `add()` on the container that holds the anchor. Without `exec_task` it runs and does nothing.
- `.after_phase` alone splices in series; non-adjacent anchors or `with_phase` make a parallel branch. The wrong container gives `PH_BAD_ADD`.
- Most needs fit an existing run-time phase, a sequence or a synchronization object. Custom phases are owned by the methodology team.
- Governance is guidelines, precise lint rules, an honest CI gate and a pinned uvm-core version checked at run time.

## Make It Work

### A custom phase you can run

This complete file adds a `load_fw` phase between `reset` and `post_reset`, checks the uvm-core version, sets a timeout, and proves in `check_phase` that the firmware was loaded exactly once. It is the same design as the lab, written as a package plus `tb_top`.

```systemverilog
// compile
`include "uvm_macros.svh"

package soc_pkg;
  timeunit 1ns;
  timeprecision 1ps;
  import uvm_pkg::*;

  typedef class soc_env;

  // Part 1: the phase IMP. One object, shared by every node that refers to it.
  class load_fw_phase_c extends uvm_task_phase;
    local static load_fw_phase_c m_inst;

    protected function new(string name = "load_fw");
      super.new(name);
    endfunction

    static function load_fw_phase_c get();
      if (m_inst == null) m_inst = new();
      return m_inst;
    endfunction

    // Part 2: the proxy. Forked once per component in the domain.
    virtual task exec_task(uvm_component comp, uvm_phase phase);
      soc_env env;
      if ($cast(env, comp)) env.load_fw_phase(phase);
    endtask
  endclass

  // soc_env is defined before base_test, which uses soc_env::type_id (§6.18).
  class soc_env extends uvm_env;
    `uvm_component_utils(soc_env)
    bit          reset_done;
    int unsigned fw_loads;

    function new(string name, uvm_component parent);
      super.new(name, parent);
    endfunction

    task reset_phase(uvm_phase phase);
      phase.raise_objection(this);
      `uvm_info("ORDER", "reset", UVM_LOW)
      #50ns;
      reset_done = 1;
      phase.drop_objection(this);
    endtask

    // Called only through load_fw_phase_c::exec_task.
    task load_fw_phase(uvm_phase phase);
      phase.raise_objection(this);
      if (!reset_done) `uvm_error("ORDER", "load_fw ran before reset finished")
      `uvm_info("ORDER", "load_fw", UVM_LOW)
      #20ns;   // stands in for a backdoor load of the firmware image
      fw_loads++;
      phase.drop_objection(this);
    endtask

    task configure_phase(uvm_phase phase);
      phase.raise_objection(this);
      if (fw_loads == 0) `uvm_error("ORDER", "configure ran before firmware was loaded")
      `uvm_info("ORDER", "configure", UVM_LOW)
      #10ns;
      phase.drop_objection(this);
    endtask

    function void check_phase(uvm_phase phase);
      super.check_phase(phase);
      if (fw_loads != 1)
        `uvm_error("FW", $sformatf("firmware loaded %0d times, expected 1", fw_loads))
    endfunction
  endclass

  class base_test extends uvm_test;
    `uvm_component_utils(base_test)
    localparam string PINNED_UVM = "Accellera:1800.2:UVM:2020.3.1";
    static bit load_fw_added;   // one add() per simulation: each add() makes a node
    soc_env env;

    function new(string name, uvm_component parent);
      super.new(name, parent);
    endfunction

    function void build_phase(uvm_phase phase);
      super.build_phase(phase);
      if (UVM_VERSION_STRING != PINNED_UVM)
        `uvm_fatal("VERSION", {"compiled against ", UVM_VERSION_STRING,
                               ", pinned ", PINNED_UVM})
      `uvm_info("VERSION", UVM_VERSION_STRING, UVM_LOW)
      // Compile uvm_pkg with the same time unit as this package (see I-UVM-1C).
      uvm_root::get().set_timeout(1ms);
      // Part 3: reset lives in the uvm schedule, so the new phase goes there.
      // get_uvm_schedule() is uvm-core impl.; Push Further shows the standard route.
      if (!load_fw_added) begin
        uvm_domain::get_uvm_schedule().add(load_fw_phase_c::get(),
                                           .after_phase(uvm_reset_phase::get()));
        load_fw_added = 1;
      end
      env = soc_env::type_id::create("env", this);
    endfunction
  endclass
endpackage

module tb_top;
  timeunit 1ns;        // every design element in the unit declares the same time
  timeprecision 1ps;   // unit; mixing declared and undeclared is an error (§3.14.2.3)
  import uvm_pkg::*;
  import soc_pkg::*;
  initial run_test("base_test");
endmodule
```

**Expected output** (illustrative: derived by tracing the phase rules above through uvm-core 2020.3.1, not captured from a simulator; the message prefix and the printed time units depend on your simulator and on how `uvm_pkg` was compiled):

```text
UVM_INFO @ 0: uvm_test_top [VERSION] Accellera:1800.2:UVM:2020.3.1
UVM_INFO @ 0: uvm_test_top.env [ORDER] reset
UVM_INFO @ 50: uvm_test_top.env [ORDER] load_fw
UVM_INFO @ 70: uvm_test_top.env [ORDER] configure

--- UVM Report Summary ---
...
```

`reset` objects for 50 ns, `load_fw` for 20 ns and `configure` for 10 ns. `post_reset` and `pre_configure` have no objections and end in the time slot they start, so `configure` starts at 70 ns. `main_phase` through `post_shutdown_phase` follow at 80 ns with no objections, `run_phase` ends with them, and `check_phase` finds `fw_loads == 1`.

**Run it.** Compile uvm-core 2020.3.1 (its `src/uvm_pkg.sv`, with `src` on the include path) and then this file, elaborate `tb_top`, and run. The test name is fixed by `run_test("base_test")`, so no `+UVM_TESTNAME` is needed. Add `+UVM_PHASE_TRACE` (uvm-core impl.) to see the schedule. Simulator switches are tool-specific; UVM support in open-source simulators is still limited, so use a commercial simulator or check your tool's UVM status first.

| Delete `exec_task` from `load_fw_phase_c` | `configure` at 50 ns with `UVM_ERROR [ORDER] configure ran before firmware was loaded`, then `UVM_ERROR [FW] firmware loaded 0 times, expected 1` | The node runs, nobody objects, it ends at 50 ns |
| Call `add()` on `uvm_domain::get_common_domain()` | `UVM_FATAL [PH_BAD_ADD] cannot find after_phase 'reset' within node 'common'` at time 0, during `build_phase` | The common domain cannot see `reset` |

| Remove the `load_fw_added` guard and call `add()` twice | `load_fw` at 50 and 70 ns, `configure` at 90 ns, `UVM_ERROR [FW] firmware loaded 2 times` | Each `add()` makes a node; the second is spliced right after `reset`, before the first |
| Move `class base_test` above `class soc_env` | A compile error on `soc_env::type_id` in a conforming tool (some tools accept it) | `soc_env` is still an incomplete forward type there (IEEE 1800-2023 §6.18) |

### How to add a custom phase (when you must)

1. **Justify it.** Check the "When not to add a custom phase" table. Write down why no existing phase, sequence or `uvm_event` works.
2. **Write the IMP:** extend `uvm_task_phase` (or `uvm_topdown_phase` / `uvm_bottomup_phase` for a zero-time step), add `local static` `m_inst`, a `protected` constructor and a static `get()`.
3. **Write the proxy:** override `exec_task` (or `exec_func`) to `$cast` the component and call a method with a distinct name.
4. **Pick the container that holds the anchor:** run-time anchors live in the `uvm` schedule; `build` … `final` live in the common domain. Avoid anchors after `run_phase` unless the step needs no drivers or monitors.
5. **Register once,** from the test's `build_phase` or a static function in `proj_pkg`, guarded by a static bit.
6. **Make the work idempotent,** because a jump back to `reset` runs it again.
7. **Prove it:** run with `+UVM_PHASE_TRACE`, read the start and end times of your phase, and keep a counter checked in `check_phase`.

**Checklist before moving on:**
- [ ] I can map five team requirements to an extension point from the table, without editing uvm-core.
- [ ] My phase class has a `protected` constructor, a static `get()` and an `exec_task` that casts to the right component.
- [ ] I can say which container holds `reset`, `configure`, `main` and `extract`, and predict `PH_BAD_ADD` for a mismatch.
- [ ] I can predict the start times of `post_reset` and `configure` for a series splice and for a parallel branch.
- [ ] I can explain why a second `add()` runs the phase twice, and where the guard belongs.
- [ ] I can name two existing mechanisms that would replace a proposed `pll_lock` phase.
- [ ] I can list the seven conditions of an honest CI gate and say what each one catches, including the two that catch errors hidden before counting.

## Push Further

### Expert: standard API versus uvm-core API for phase insertion

`uvm_domain::get_uvm_schedule()`, `get_common_domain()` and `get_uvm_domain()` are used in almost every custom-phase example, but none is in IEEE 1800.2-2020: §9.4.2 defines only `new`, `get_domains`, `add_uvm_phases` and `jump`, and uvm-core marks the three as non-standard (no `@uvm-ieee` tag in `uvm_domain.svh`). `set_phase_imp` is marked `@uvm-compat`. A standard-only route exists:

```systemverilog
// snippet: standard API only (§9.4.2.2, §9.3.1.6.1)
uvm_domain doms[string];
uvm_domain::get_domains(doms);   // always has doms["common"] and doms["uvm"]
doms["uvm"].add(load_fw_phase_c::get(), .after_phase(uvm_reset_phase::get()));
```

§9.3.1.6.1 allows `add` on a domain node, and §9.4.2.2 says `domains["uvm"]` "contains the UVM run-time phases". In uvm-core, `find` from the `uvm` domain node descends into its schedule because that schedule belongs to the same domain (`m_find_successor`). This route was traced through the source but not run: confirm the splice with `+UVM_PHASE_TRACE`. Two more standard details: §9.3.1.6.4 declares `get_schedule` as returning `string` while describing a node, which looks like an erratum (uvm-core returns `uvm_phase`), so prefer `get_parent()` (§9.3.1.6.2) in portable code; and `add()` also takes `start_with_phase` and `end_with_phase`, which align a new phase with the start or end of an existing one (§9.3.1.6.1).

### Expert: custom phases and separate domains

`set_domain(dom)` (§13.1.4.4.1) moves a component, and by default its subtree, into another domain, and calls `define_domain(dom)` (§13.1.4.4.3), whose default "adds a copy of the uvm phasing schedule to the given domain". In uvm-core that copy is built fresh with `add_uvm_phases` (`uvm_component.svh`, `define_domain`), so it does **not** contain a phase you added to `get_uvm_schedule()`. uvm-core's task-phase traversal also runs a node only for components whose domain is the node's domain or the common domain (`uvm_task_phase.svh`, `traverse`). Consequences:

- A VIP that an integrator places in its own domain silently skips your `load_fw` phase.
- To give a domain its own custom phase, add it to that domain's schedule, once, after the domain is defined:

```systemverilog
// snippet: integrator env's build_phase, after vip_env is created
// (vip_dom is a uvm_domain member of the env)
vip_dom = new("vip");                     // §9.4.2.1: names must be unique
vip_env.set_domain(vip_dom);              // builds vip_dom's own run-time schedule
vip_dom.find(uvm_reset_phase::get()).get_parent()
       .add(vip_cal_phase_c::get(), .after_phase(uvm_reset_phase::get()));
```

- Do not put such an `add()` inside an overridden `define_domain`: `set_domain` calls `define_domain` on every component it reaches, so the phase would be added once per component.
- Components created after `set_domain` inherit their parent's domain (uvm-core `uvm_component::new`). Whether the new domain runs in lockstep with `uvm` is a separate decision: `sync` and `unsync` (§9.3.1.8.1–9.3.1.8.2), taught in [I-UVM-1C](/curriculum/T2_Intermediate/I-UVM-1C_UVM_Phasing/index).

(The `vip_cal_phase_c` class is written exactly like `load_fw_phase_c`. Traced through uvm-core, not run.)

### Expert: jumps re-run custom phases

`phase.jump(target)` (§9.3.1.9.1) ends the current phase prematurely and continues the schedule from `target`; `uvm_domain::jump` (§9.4.2.4) does it for every active phase of a domain. A jump from `main` back to `reset` re-runs `reset`, then your spliced `load_fw`, then everything after it. In Make It Work, `fw_loads` would reach 2 and `check_phase` would fail. Write custom-phase work to be **idempotent** (safe to repeat): reload the image deliberately and reset the counter in `reset_phase`, or count per reset epoch. Also, threads still running when a phase ends are killed ("any remaining forked … exec_task threads are forcibly and immediately killed", §9.6), so a `load_fw_phase` that forks a background thread loses it when the phase ends.

### Expert: typed proxies, phase callbacks and default sequences

- **Typed proxies.** For a phase that calls methods of an extended component class, the standard recommends a parameterized proxy: "extend the base … phase class with parameterized component class context … to create a specialized proxy" (§9.3.1.1.1 c). In practice, `class load_fw_phase_t #(type T = soc_env) extends load_fw_phase_c` whose `exec_task` casts to `T` lets one phase serve several env types without editing it.
- **Phase callbacks.** `phase_started(phase)` and `phase_ended(phase)` (§13.1.4.3.1, §13.1.4.3.3) fire for custom phases too, for every component in the domain. A project base can use them for timing or logging without each block knowing the phase exists: compare `phase.get_name()` with `"load_fw"`.
- **Default sequences.** A default sequence can target any phase of a sequencer (§15.3.5). Its scope is the sequencer path plus the phase, as in the standard's own example `"path.to.sequencer.main_phase"` (G.2.9); uvm-core looks it up at `<sequencer full name>.<phase name>_phase` (`uvm_sequencer_base.svh`), so a firmware sequence for the custom phase is set at `"env.agt.sqr.load_fw_phase"` relative to the test.

### Expert: enforcing the base layer at run time

Lint finds bypassed bases in source; a run-time check finds them in the elaborated tree, including classes generated by scripts. An **interface class** (IEEE 1800-2023 §8.26) works as a marker that any project base can implement in addition to its single base class, and a handle can be `$cast` to it (§8.26.5):

```systemverilog
// snippet: proj_pkg
interface class proj_conformant;
  pure virtual function string proj_base_name();
endclass

// proj_monitor now also implements the marker:
//   class proj_monitor #(type T = uvm_sequence_item) extends uvm_monitor
//     implements proj_conformant;
//     virtual function string proj_base_name(); return "proj_monitor"; endfunction

// In proj_base_test:
function void end_of_elaboration_phase(uvm_phase phase);
  uvm_component comps[$];
  super.end_of_elaboration_phase(phase);
  uvm_root::get().find_all("*", comps);    // F.7.4.1
  foreach (comps[i]) begin
    uvm_monitor     mon;
    proj_conformant pc;
    if ($cast(mon, comps[i]) && !$cast(pc, comps[i]))
      `uvm_error("PROJ/BASE", {comps[i].get_full_name(), " bypasses proj_monitor"})
  end
endfunction
```

The limit is instructive: this works for roles with a non-parameterized UVM base (`uvm_monitor`, `uvm_scoreboard`, `uvm_agent`, `uvm_env`). Drivers have no common non-parameterized base below `uvm_component` (`uvm_driver #(REQ, RSP)` is parameterized, §13.7.1), so the driver rule stays a lint rule. Exempt third-party VIP by path.

### Expert: pinning and upgrading uvm-core

- **Run time:** compare `uvm_pkg::UVM_VERSION_STRING` (B.7.2) with the pinned string and fatal on a mismatch, as `proj_base_test` does. Its value is implementation-defined, so pin the exact string of your release.
- **Compile time:** `` `UVM_VERSION `` is `2020` (B.7.1), and the version ladder defines `` `UVM_VERSION_POST_2017 `` (B.7.3) for code that must also compile on IEEE 1800.2-2017 libraries. uvm-core adds finer defines such as `` `UVM_VERSION_POST_2020_2_0 `` (uvm-core only). Do not rely on the legacy `` `UVM_MINOR_REV ``: in the 2020.3.1 tag it reads `3.0` (`uvm_version_defines.svh`), not the release you might expect.
- **Upgrades** are a project: build the new uvm-core beside the old, run the example-environment regression on both, read the release notes for behaviour changes (deprecated `@uvm-compat` APIs especially), then move the pin in one commit. Fixes you need go upstream; your layer carries a workaround until they ship.

### Expert: the cost of a methodology layer

Tool-dependent in magnitude, standard in mechanism. Each task phase forks one `exec_task` per component in its domain (§9.6), even for components that do nothing in it, so a custom phase in an SoC with thousands of components costs thousands of short-lived threads per run. Base classes multiply every per-component cost: a `uvm_config_db::get` in a run-time loop, string formatting in a hook that is called per item, or a `+UVM_OBJECTION_TRACE`-style audit trail left on in regressions (uvm-core impl., very verbose). Measure before and after any base-class change on the largest environment, with CPU time measured outside the simulator. [E-PERF-1](/curriculum/T4_Expert/E-PERF-1_UVM_Performance/index) teaches the measurement.

### Kata: a base driver with reset hooks

Objective 1 in code. The project wants every block driver to behave the same way around reset: outputs idle while reset is asserted, items driven only after reset is released, and a clean stop when reset asserts in the middle of a test. Here is an abstract base that adds the reset contract on top of `proj_driver` (so it keeps the config and the policy hook); a block team supplies the four hooks. The base adds no reset rule of its own: it packages the reviewed single-thread pattern of [A-UVM-9's reset-aware driver](/curriculum/T3_Advanced/A-UVM-9_Reset_and_Error_Injection/index#the-reset-aware-driver), in which one thread reads the sampled reset at each edge of an item, so that "accepted" and "reset" are decided once, with no `fork` to race.

```systemverilog
// snippet: kata starter, part of proj_pkg
virtual class proj_reset_driver #(type REQ = uvm_sequence_item) extends proj_driver #(REQ);
  `uvm_component_abstract_param_utils(proj_reset_driver #(REQ))

  function new(string name, uvm_component parent);
    super.new(name, parent);
  endfunction

  // The contract: four hooks every block driver implements.
  pure virtual task wait_reset_released();   // first edge that samples reset released
  pure virtual function bit in_reset();      // reset as sampled at the latest edge
  pure virtual task drive_item(REQ item);    // returns at the accept edge, or on reset
  pure virtual task idle_outputs();

  // One thread (A-UVM-9): reset is read at the item's edges, never raced against it.
  task run_phase(uvm_phase phase);
    REQ item;
    super.run_phase(phase);
    idle_outputs();
    wait_reset_released();
    forever begin
      seq_item_port.get_next_item(item);
      if (!in_reset()) drive_item(item);
      if (in_reset()) begin
        // TODO 2: reset came before this item's accept edge; the item is still pending.
        idle_outputs();
        wait_reset_released();
      end else begin
        seq_item_port.item_done();
      end
    end
  endtask
endclass
```

1. **Write `apb_driver`** on top of this base for an `apb_if` with `pclk`, `presetn` (active low), `psel`, `penable`, `pwrite`, `paddr`, `pwdata` and a clocking block `drv_cb`, driving an `apb_item` with `addr`, `data` and `write`. Keep the protocol minimal: one setup cycle, one access cycle. `drive_item` returns at the access (accept) edge, or straight after the setup edge if that edge sampled reset asserted.
2. **Decide and implement** what happens to an item taken but not finished when reset asserts (the `TODO 2` branch). Calling `get_next_item` again without `item_done` is an error, and the sequence that sent the item stays blocked in `finish_item` until `item_done` is called.
3. **Predict** what a run shows if you skip step 2 and reset asserts once in the middle of an item.

**Step 2 first, because it belongs in the base.** An item that reset cut short is *abandoned*: give it back with `item_done()` exactly as an accepted item, so the sequence's `finish_item` returns, and count it so the abandonment is visible:

```systemverilog
// snippet: proj_reset_driver::run_phase with TODO 2 done
protected int unsigned n_abandoned;   // items taken but cut short by reset

task run_phase(uvm_phase phase);
  REQ item;
  super.run_phase(phase);
  idle_outputs();
  wait_reset_released();
  forever begin
    seq_item_port.get_next_item(item);
    if (!in_reset()) drive_item(item);
    if (in_reset()) begin
      n_abandoned++;
      `uvm_info("PROJ/RESET", "item abandoned by reset", UVM_MEDIUM)
    end
    // Accepted or abandoned: give the item back, so finish_item returns.
    // Sequences check their own status or the reset epoch.
    seq_item_port.item_done();
    if (in_reset()) begin
      idle_outputs();
      wait_reset_released();
    end
  end
endtask
```

Putting this in the base is the point of the kata: every block driver inherits one reviewed reset behaviour instead of forty variants. **Why one thread:** `in_reset()` reads the value the clocking block sampled at the edge `drive_item` has just returned from, so acceptance is decided once, as a DUT that samples reset on its clock decides it. A base that forked the drive loop against a reset watcher would wake both branches at the same clocking event, in an order the simulator chooses, and its `disable fork` could land inside `get_next_item()` (A-UVM-9 explains both). This base fits a reset the driver can sample on a running clock, as `apb_driver` does. For a DUT with an asynchronous reset whose clock may stop, give the project a second base on [A-UVM-9's asynchronous-reset driver](/curriculum/T3_Advanced/A-UVM-9_Reset_and_Error_Injection/index#an-asynchronous-reset-is-watched-outside-the-clocking-block): `get_next_item()` outside the fork, only the drive raced against the raw reset, and `item_done()` whether the item was accepted or abandoned.

**Step 1, the block driver:**

```systemverilog
// snippet: block code, extends the project base
class apb_driver extends proj_reset_driver #(apb_item);
  `uvm_component_utils(apb_driver)
  virtual apb_if vif;

  function new(string name, uvm_component parent);
    super.new(name, parent);
  endfunction

  function void build_phase(uvm_phase phase);
    super.build_phase(phase);
    if (!uvm_config_db #(virtual apb_if)::get(this, "", "vif", vif))
      `uvm_fatal("APB/NO_VIF", "virtual apb_if not set")
  endfunction

  virtual task wait_reset_released();
    @(vif.drv_cb iff vif.drv_cb.presetn === 1'b1);
  endtask

  // The value drv_cb sampled at the latest edge: what a synchronous DUT acts on.
  virtual function bit in_reset();
    return vif.drv_cb.presetn !== 1'b1;
  endfunction

  virtual task idle_outputs();
    vif.drv_cb.psel    <= 1'b0;
    vif.drv_cb.penable <= 1'b0;
  endtask

  virtual task drive_item(apb_item item);
    vif.drv_cb.psel    <= 1'b1;      // setup cycle
    vif.drv_cb.penable <= 1'b0;
    vif.drv_cb.pwrite  <= item.write;
    vif.drv_cb.paddr   <= item.addr;
    vif.drv_cb.pwdata  <= item.data;
    @(vif.drv_cb);
    if (in_reset()) return;          // reset at the setup edge: the base idles the bus
    vif.drv_cb.penable <= 1'b1;      // access cycle
    @(vif.drv_cb);                   // the accept edge; the base reads in_reset() here
    vif.drv_cb.psel    <= 1'b0;
    vif.drv_cb.penable <= 1'b0;
  endtask
endclass
```

(`presetn` must be an `input` of `drv_cb` and the bus signals its `output`s. This minimal driver ignores `PREADY` wait states; real APB timing, with wait states, is taught in [B-APB-1](/curriculum/T3_Advanced/B-APB-1_APB_Protocol_and_Verification/index).) `apb_driver` is a concrete class, so it uses `` `uvm_component_utils ``, while the abstract base uses the abstract macro.

**Step 3, without the fix:** reset is sampled at the item's setup or accept edge, `drive_item` returns, and the base idles the bus and waits for release without calling `item_done`. The sequence that sent the item stays blocked in `finish_item` for the whole reset. When reset is released, the loop calls `get_next_item` again while the first item is still outstanding. uvm-core's sequencer reports `Get_next_item called twice without item_done or get in between` as a `UVM_ERROR` (`uvm_sequencer.svh`) and, because the item is still at the head of its request FIFO, hands the driver the *same* item again (`uvm_sequencer_param_base.svh`, `m_safe_select_item`). So the run shows one `UVM_ERROR` and the item driven twice, once cut short by reset and once complete, which a scoreboard may also flag as a duplicate. (Traced through the uvm-core source, not run.)

</details>
