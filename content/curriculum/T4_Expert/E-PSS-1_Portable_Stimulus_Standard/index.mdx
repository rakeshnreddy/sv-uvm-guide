## Quick Take
- **What it is:** The Portable Test and Stimulus Standard (PSS) is an Accellera standard (version 2.1 was approved in October 2023 and version 3.0 in August 2024). It is a declarative language for expressing *test intent* — the abstract scenario logic — independently of any particular execution platform.
- **Why it matters:** Modern verification teams must run the same test scenarios on RTL simulation, FPGA prototypes, emulation platforms, and post-silicon validation. Without PSS, each target requires hand-porting of test logic, a quadratic maintenance burden that fragments coverage metrics and introduces target-specific bugs.
- **Industry context:** Several EDA vendors ship commercial PSS tools, and open-source front ends exist (for example the ANTLR-based `pssparser` from the PSSTools project). Tools differ in which PSS version and which targets they support, so check before you rely on a feature.

## The Portability Problem PSS Solves

Consider a memory subsystem verification scenario that must check read-after-write coherency. Without PSS, you write:

| Target | What you write | Effort |
|---|---|---|
| **RTL Simulation** | A UVM virtual sequence calling read/write sequences on an AXI agent | ~200 lines SV |
| **FPGA Prototype** | A C test using memory-mapped register writes from an embedded processor | ~150 lines C |
| **Emulation** | A transaction-level acceleration (TLA) sequence with emulator-specific APIs | ~180 lines SV |
| **Post-Silicon** | A bare-metal firmware test running on the real chip via JTAG | ~120 lines C |

That is **four separate implementations** of the same logical test, each with independent bugs and maintenance costs. PSS replaces all four with a single declarative specification that a compiler translates to each target.

## PSS Language Fundamentals

### Actions, Components, and Activity Graphs

PSS programs are built from four core concepts:

1. **Components** — reusable containers for actions, pools and resources (memory subsystems, DMA engines, processors).
2. **Actions** — test operations. Their inputs and outputs are *flow objects*: a `buffer` (the producer completes before the consumer starts), a `stream` (producer and consumer run in parallel) or a `state`. Actions claim *resources* with `lock` (exclusive) or `share`.
3. **Activities** — the scenario: which actions run, in sequence or in `parallel`. The tool completes whatever the activity leaves out.
4. **Exec blocks** — `exec body C = """..."""` and `exec body SV = """..."""` templates that say how an action is realised on each target.

```pss
// Accellera PSS: two actions linked by a buffer flow object
buffer mem_buf_s {
  rand bit[32] addr;
  rand bit[32] data;
  constraint { addr in [0x1000..0x1FFC]; addr % 4 == 0; } // aligned, one 4 KB region
}

component mem_subsys_c {
  pool mem_buf_s buf_p;   // where mem_buf_s objects are exchanged
  bind buf_p *;

  action write_a {
    output mem_buf_s out_buf;
    exec body C  = """ mem_write32({{out_buf.addr}}, {{out_buf.data}}); """;
    exec body SV = """
      wr = mem_wr_seq::type_id::create("wr");
      wr.addr = {{out_buf.addr}}; wr.data = {{out_buf.data}};
      wr.start(m_sequencer);
    """;
  }

  action read_check_a {
    input mem_buf_s in_buf;
    // Bare metal has no scoreboard, so the C template checks the data itself.
    exec body C  = """ if (mem_read32({{in_buf.addr}}) != {{in_buf.data}}) test_fail(); """;
    // In UVM the scoreboard checks every monitored read, so the SV template only reads.
    exec body SV = """
      rd = mem_rd_seq::type_id::create("rd");
      rd.addr = {{in_buf.addr}};
      rd.start(m_sequencer);
    """;
  }
}
```

### Activity Graphs: Declarative Test Flow

The activity block defines the test scenario's execution order:

```pss
component pss_top {
  mem_subsys_c mem;

  action raw_coherency_test {
    activity {
      do mem_subsys_c::write_a;      // produces a mem_buf_s
      do mem_subsys_c::read_check_a; // its input binds to that buffer
    }
  }
}
```

No constraint links the two addresses: the read's input buffer *is* the write's output buffer, so address and data flow through the binding. The activity says **what** must happen and **in which order**; the `exec` blocks say **how** each action runs on each target; the tool picks the schedule, the bindings and the values.

## Data Constraints in PSS

PSS constraints look like SystemVerilog constraints, but weighting and defaults work differently. Notice where each kind of bias lives:

```pss
component mem_c {
  action burst_write {
    rand bit[8] len;
    constraint len in [1..16];
    // dist is a separate directive (PSS 2.1 and later), not an operator inside an expression
    constraint len_bias { dist len in [1 := 10, 4 := 30, 8..16 :/ 60]; }
  }
  action single_write { }
  action read_verify  { }

  action stress_test {
    rand int num_iterations;
    constraint num_iterations in [100..10000];
    // default: holds unless a containing or derived context overrides it
    // (constraint default s.num_iterations == 5000;) or removes it (default disable)
    constraint default num_iterations == 1000;

    activity {
      repeat (num_iterations) {
        select {                  // a weighted choice, made again on every iteration
          [70]: do burst_write;
          [30]: do single_write;
        }
        do read_verify;
      }
    }
  }
}
```

Key differences from SV constraints:
- In SystemVerilog, `x dist {...}` is itself a constraint: a set-membership test plus weights (IEEE 1800-2023 §18.5.3). In PSS, `dist x in [...];` is a directive that biases the solver. When a constraint disagrees, the constraint wins and the solve does not fail.
- There is no `soft` keyword in the PSS 3.0 grammar. A `default` value constraint (`constraint default x == 1000;`) fixes a value until an enclosing or derived context overrides it with its own `default`, or removes it with `default disable x;`. A plain constraint that disagrees with an active default is a contradiction, not an override.
- Weighted choices between *actions* belong in the activity: `select` branches with a `[weight]`, re-drawn on every pass of the `repeat`. A `dist` on a field of `stress_test` would be solved once for the whole test.
- Constraints can relate fields of different actions, flow objects and resources, so the tool solves the whole scenario at once.

## Compiling PSS to SystemVerilog UVM Sequences

When targeting RTL simulation, a PSS tool typically generates a UVM sequence (or virtual sequence) whose body:
1. Runs the actions in the schedule the tool solved, including any it inferred.
2. Expands each action's `exec body SV` template (usually starting a UVM sequence on the right sequencer) with the solved values filled in.
3. Leaves checking to the UVM environment: the scoreboard already compares monitored traffic against its reference model.

The exact mapping (a sequence per action, a virtual sequence per scenario, or calls into a runtime library) is tool-dependent.

### Side-by-Side: PSS vs Generated UVM

```pss
// ── PSS Source (inside component pss_top, as above) ──
action raw_coherency_test {
  activity {
    do mem_subsys_c::write_a;
    do mem_subsys_c::read_check_a;
  }
}
```

The generated UVM equivalent (simplified; the values are the ones the tool solved):

```systemverilog
// ── Generated UVM Sequence ──
class raw_coherency_test_seq extends uvm_sequence #(uvm_sequence_item);
  `uvm_object_utils(raw_coherency_test_seq)

  mem_wr_seq wr;
  mem_rd_seq rd;

  function new(string name = "raw_coherency_test_seq");
    super.new(name);
  endfunction

  task body();
    // Step 1: write_a (its exec body SV, solved values filled in)
    wr = mem_wr_seq::type_id::create("wr");
    wr.addr = 32'h0000_1A3C; wr.data = 32'h5E2D_19A7;
    wr.start(m_sequencer);

    // Step 2: read_check_a reads the same buffer, so the same address
    rd = mem_rd_seq::type_id::create("rd");
    rd.addr = 32'h0000_1A3C;
    rd.start(m_sequencer);

    // No compare here: the scoreboard checks every monitored read
    // against its reference memory, whoever started it.
  endtask
endclass
```

## Compiling PSS to C for Bare-Metal Firmware Tests

When targeting post-silicon or an embedded processor, the tool expands each action's `exec body C` template instead:

```c
// ── Generated C Bare-Metal Test (simplified) ──
#include "mem_subsystem_api.h"   // mem_write32(), mem_read32(), test_fail()

void raw_coherency_test(void) {
    // write_a: its exec body C, with the solved buffer values filled in
    mem_write32(0x00001A3C, 0x5E2D19A7);

    // read_check_a: it reads the same buffer, so the same address and data
    if (mem_read32(0x00001A3C) != 0x5E2D19A7) test_fail();
}
```

Both outputs come from the same PSS model: the UVM version starts sequences from the `exec body SV` templates, the C version calls the functions in the `exec body C` templates. Change a constraint once and both targets change. Here the values were solved when the test was generated; some tools instead emit code that solves on the target at run time.

## Tool Ecosystem

Commercial PSS tools come from several EDA vendors, and open-source parsers exist for syntax checking and research. Rather than trusting a feature list, ask each tool:

| Question | Why it matters |
|---|---|
| Which PSS version does it accept (2.1, 3.0)? | Features such as the `dist` directive or 3.0 behavioral coverage may be missing |
| Which targets can it generate (SV/UVM, C, others)? | Portability only pays off for the targets you actually run |
| Does it solve values at generation time or on the target? | Pre-solved tests are reproducible; run-time solving needs a solver on the target |
| How much does it infer? | Inferred actions and bindings are where PSS saves the most work, and where tools differ most |

PSS pays off when the same scenario has to run on more than one execution target. How many targets justify the cost depends on your team and tools; there is no standard threshold.

## Hands-On Example: Memory Test with Portability Comparison

Here is a complete PSS model for a memory stress test. Before reading it, predict: which actions may run at the same time on the same memory region?

```pss
component mem_test_suite {
  // Two 4 KB regions. A resource is claimed with lock or share; it is never an input.
  resource mem_region_r { }
  pool [2] mem_region_r region_p;        // instance_id 0 and 1
  bind region_p *;

  // What the writer hands to the reader: a buffer flow object.
  buffer burst_s {
    rand int     region_id;
    rand bit[32] start_addr;
    rand bit[32] burst_len;
    constraint start_addr % 4 == 0;
    constraint burst_len in [1..16];
  }
  pool burst_s burst_p;
  bind burst_p *;

  action write_burst {
    lock   mem_region_r region;          // exclusive while it writes
    output burst_s      burst;
    constraint {
      burst.region_id == region.instance_id;
      burst.start_addr >= 0x1000 * (region.instance_id + 1);
      burst.start_addr + burst.burst_len * 4 <= 0x1000 * (region.instance_id + 2);
    }
  }

  action read_verify_burst {
    share  mem_region_r region;          // readers may overlap; a writer may not
    input  burst_s      burst;           // the burst some write_burst produced
    constraint region.instance_id == burst.region_id;
  }

  action mem_stress {
    activity {
      repeat (100) {
        wb:  do write_burst;
        rvb: do read_verify_burst;
        bind wb.burst rvb.burst;         // read back exactly this iteration's burst
      }
    }
  }
}
```

What each piece guarantees:
- **`lock` / `share`:** a `write_burst` holds its region exclusively, so nothing else that claims that region runs alongside it. Two `read_verify_burst` actions may share one region. With a pool of two regions, two writers can still run in parallel on different instances.
- **The buffer:** `burst_s` carries the address, length and region from the writer to the reader. The explicit `bind` pins each read to the write of the same iteration; without it, the tool may pick any earlier `write_burst` output.
- **`in`, not `inside`:** PSS writes set membership as `burst_len in [1..16]`.
- **Labels, not `as`:** `wb: do write_burst;` names a traversal so later statements can refer to `wb`.

A tool can lower this one model to a UVM virtual sequence for RTL simulation, a C test for an embedded core or post-silicon, or both. How much code that becomes, and whether values are solved before the run or on the target, depends on the tool.
