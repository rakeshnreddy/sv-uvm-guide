## Quick Take

- **What it is:** The **Portable Test and Stimulus Standard (PSS)** is a language for writing **test intent**: what a scenario must do (write a buffer, then read it back while a DMA copy runs), kept separate from how each platform does it. It is published by **Accellera**, an industry standards body. Version 2.1 was approved in October 2023 and version 3.0, the current release, in August 2024. PSS has no IEEE number.
- **Why it matters:** A system-on-chip (SoC) runs the same scenarios on RTL simulation, emulation, FPGA prototypes and the finished chip (post-silicon). Written by hand, that is one test per scenario per platform, and every change is made four times. With PSS you write one scenario model; a tool binds the pieces together, adds missing setup actions, schedules around shared hardware and emits a UVM sequence or a C test from the same model. You still write, once per action and platform, the small code template that performs it.
- **The Analogy:** A PSS model is a trip itinerary handed to a travel agent. The itinerary says which cities, in which order (the activity). The agent (the PSS tool) adds the connecting flights you left out (inferred actions), makes sure two travellers never get the same hotel room (resource locks) and prints each airline's ticket in that airline's format (the `exec` templates). *Where it breaks:* the agent cannot invent an airline. Every action needs a hand-written realization for every platform, and nothing gets checked unless a template or your UVM scoreboard checks it.

**You will be able to:**
1. Write a PSS model with components, pools, atomic and compound actions, an activity (sequence, `parallel`, `schedule`, `select`, `repeat`) and data constraints (`in`, `dist`, `default`).
2. Choose buffer, stream or state flow objects and `lock` or `share` resource claims for a scenario, and predict which actions the tool infers, which may run at the same time, and when no legal scenario exists.
3. Explain how one model becomes a UVM virtual sequence and a bare-metal C test through `exec` templates, and name what stays hand-written.
4. Debug common modelling errors: a resource declared as an `input`, a missing `bind`, a `default` that contradicts a constraint, parallel locks that exceed the pool, and an SV template that does not compile.
5. Decide whether PSS adds value over UVM virtual sequences for a given project, and justify the decision.

### Intent versus realization: what the tool writes and what you write

Take one scenario: write a word to memory and read it back (read-after-write). Without PSS, a team that runs on four platforms writes it four times:

| Platform | What you write by hand (illustrative) |
|---|---|
| RTL simulation | A UVM virtual sequence that starts write and read sequences on a memory agent |
| Emulation | A transaction-level sequence or software test for the emulator's interface |
| FPGA prototype | A C test that writes and reads memory-mapped addresses from an embedded processor |
| Post-silicon | A bare-metal C test: C code that runs directly on the chip's processor, with no operating system |

Each copy has its own bugs, and a change to the address map is made four times. (The **design under test**, DUT, is the same in every row; only the code that drives it changes.) PSS replaces the four *scenario descriptions* with one model. It does **not** replace the code that touches each platform: every action keeps a small template per platform, and your UVM environment and C hardware-abstraction layer (HAL, the C functions such as `mem_write32()` that hide register addresses) stay exactly as they are.

**What the picture shows.** The words "generated" and "hand-written" are the whole story of adoption. The tool writes the scenario layer: which action runs when, with which values. You write, once, the realization layer: the per-platform template inside each action and the environment those templates call.

**The two mistakes everyone makes here.**
- *"PSS replaces UVM."* It does not. The generated UVM code is a sequence that starts your sequences; the agents, scoreboard and coverage are still yours.
- *"PSS is IEEE 2401" (or P2851).* PSS is an Accellera standard with no IEEE number. IEEE 2401-2019 is a format for chip-package-board design data, and IEEE 2851-2023 is a functional-safety data format. Cite PSS as "Accellera PSS 3.0 (2024)".

**Versions.** 1.0 (2018), 2.0 (2021), 2.1 (October 2023, which added `dist` weights) and 3.0 (August 2024, which added behavioral coverage). A 3.1 draft went to public review in 2026; until Accellera approves it, 3.0 is the standard. Tools differ in which version they accept, so check before you rely on a feature.

### The vocabulary in one small model

Read these terms once; the model below uses every one of them.

- A **component** is a reusable block of the system (a memory subsystem, a DMA engine). It owns actions and pools. Components form a tree whose root is called `pss_top` by default (§9.4.1).
- An **action** is one test operation, such as "write memory". An **atomic** action is realized by `exec body` templates; a **compound** action contains an activity built from other actions (§10).
- An **activity** is the scenario inside a compound action: which actions are **traversed** (executed as part of the scenario), in what order (§12).
- A **flow object** is data one action hands to another: a `buffer`, `stream` or `state` (§13). An action declares it as an `input` or `output`.
- A **resource** is something an action needs for its whole execution, such as a DMA channel. Actions claim it with `lock` or `share`, never as an input (§14).
- A **pool** is where objects of one type are exchanged or held. Every flow-object exchange and every resource claim goes through a pool (§15). A **static bind directive**, such as `bind buf_p *;`, says which actions use which pool.
- The **PSS tool** (the processing tool, in the standard's words) reads the model, completes what the activity leaves open, picks random values with its **solver**, and generates target code.

The minimal correct model. It is complete: a tool given `raw_test_a` as the root action can generate both targets from it.

```pss
// A complete PSS model: write a word, then read the same word back
buffer mem_buf_s {                      // flow object: data one action hands to another
  rand bit[32] addr;
  rand bit[32] data;
  constraint { addr in [0x1000..0x2FFC]; addr % 4 == 0; }   // aligned, two 4KB regions
}

component mem_subsys_c {
  pool mem_buf_s buf_p;                 // where mem_buf_s objects are exchanged
  bind buf_p *;                         // every action in this component uses buf_p

  action write_a {                      // atomic: realized by its exec body templates
    output mem_buf_s out_buf;
    exec body C = """ mem_write32({{out_buf.addr}}, {{out_buf.data}}); """;
    exec body SV = """
      begin
        mem_wr_seq wr = mem_wr_seq::type_id::create("wr");
        wr.addr = {{out_buf.addr}};
        wr.data = {{out_buf.data}};
        wr.start(p_sequencer.mem_sqr, this);
      end
    """;
  }

  action read_check_a {
    input mem_buf_s in_buf;
    // Bare metal has no scoreboard, so the C template checks the data itself.
    exec body C = """
      if (mem_read32({{in_buf.addr}}) != {{in_buf.data}})
        test_fail("read-after-write mismatch");
    """;
    // In UVM the scoreboard checks every monitored read, so the SV template only reads.
    exec body SV = """
      begin
        mem_rd_seq rd = mem_rd_seq::type_id::create("rd");
        rd.addr = {{in_buf.addr}};
        rd.start(p_sequencer.mem_sqr, this);
      end
    """;
  }
}

component pss_top {                     // the default root component (§9.4.1)
  mem_subsys_c mem;

  action raw_test_a {                   // compound: its body is an activity
    activity {
      w1: do mem_subsys_c::write_a;     // labelled traversal: w1 names this write
      r1: do mem_subsys_c::read_check_a;
      bind w1.out_buf r1.in_buf;        // the read consumes exactly w1's buffer
    }
  }
}
```

Three syntax points that trip SystemVerilog engineers: set membership is `in` (§8.5.9), not `inside`; widths are written `bit[32]` (the `bit[31:0]` form is deprecated, §7.2.1); and a traversal is named with a label, `w1: do write_a;` (§12.3.1), because PSS has no `do write_a as w1` form (`as` exists only for package import aliases).

### Actions and their exec templates

An atomic action says *how* it runs on each platform with **target-template exec blocks**: `exec body C = """..."""` and `exec body SV = """..."""` (§22.1, §22.5). The triple-quoted string is foreign code. The tool pastes it **verbatim** into the generated test, in schedule order, after replacing each `{{expression}}` with the solved value; this `{{ }}` notation is called **mustache** (§22.5.3). The language identifiers C, CPP and SV are the ones the standard reserves (§22.5.1).

Three consequences follow directly from "pasted verbatim":

- **Wrap SystemVerilog declarations in `begin … end`.** The tool pastes several templates into one task body. Without the wrapper, the second action's `mem_wr_seq wr = …` lands after statements of the first, and declares `wr` a second time in the same scope; both are compile errors in SystemVerilog.
- **Values arrive as decimal text.** Mustache prints a `bit` field as unsigned decimal and an `int` as signed decimal (§22.5.3.2). A solved address of `0x1040` appears in the generated code as `4160`, which is legal in both C and SystemVerilog.
- **The tool does not check your template.** A typo in a template becomes a compile error in the generated file, not a PSS error. Only scalar fields can be referenced in mustache (§22.5.3).

Templates are one of three realization mechanisms. The other two are **imported functions**, where a PSS function declaration is bound to an existing C or SystemVerilog API (§22.4; the same idea as DPI in [I-SV-7](/curriculum/T2_Intermediate/I-SV-7_DPI_and_Foreign_Language_Interfaces/index)), and target-template functions (§22.6). Besides `body`, an action can carry `exec header` (for example a C `#include`) and `exec declaration` templates (§22.1.2).

### Activities: the scenario

An activity lists **action traversals**. Statements run in sequence unless you say otherwise (§12.3). These are the statements you will use:

| Statement | Meaning | PSS 3.0 |
|---|---|---|
| `w1: do T;` | Traverse an action of type `T`; the label `w1` names it | §12.3.1 |
| `bind w1.out_buf r1.in_buf;` | Both fields reference the same flow object | §12.9 |
| `parallel { A B }` | Branches start together; no branch may wait for another | §12.3.4 |
| `schedule { A B }` | The tool picks any legal order, sequential or overlapping | §12.3.5 |
| `sequence { A B }` (or just braces) | A then B, as a group, for example one branch of a `parallel` | §12.3.3 |
| `select { [70]: A; [30]: B; }` | Pick one branch per evaluation, by weight and optional guard; at least two branches | §12.4.4 |
| `repeat (n) A` | Run `A` n times in sequence; `n` may be a random field | §12.4.1 |
| `foreach`, `if`-`else`, `match`, `repeat … while` | Data-driven loops and branches | §12.4 |

**Two pitfalls.**
- **`schedule` is not `parallel`.** `parallel` forbids any dependency between branches. `schedule` lets the tool add whatever ordering the rules need, including running everything one after the other (§12.3.5.1).
- **A buffer cannot cross `parallel` branches.** If branch 1's action inputs a buffer that branch 2's action outputs, the reader must wait for the writer, which `parallel` forbids, so the activity is illegal (§12.3.4.2). Keep a producer and its consumer in the same branch, as `w0` and `r0` are.

### Flow objects: buffer, stream and state

Each kind of flow object carries data *and* a timing rule. Choose the kind by the timing your hardware has.

| Kind | Models | Producers and consumers | Timing rule |
|---|---|---|---|
| `buffer` | Data left in memory | Exactly one producer, any number of consumers | A consumer starts after the producer completes (§13.1.1) |
| `stream` | Data in flight on a bus or link | Exactly one producer and exactly one consumer | Both start at the same time (§13.2.1) |
| `state` | The current value of something, such as a configuration | One object per pool at any time; `initial` marks the reset state | A writer never overlaps any reader or writer; readers may overlap (§13.3.1) |

A buffer is the `mem_buf_s` you have already seen. A stream and a state look like this:

```pss
// stream: producer and consumer run together, like a sender and a receiver
stream pkt_s { rand bit[16] len; }

enum mode_e { LOW_POWER, NORMAL }

// state: one current configuration; writers and readers are ordered by the tool
state cfg_s { rand mode_e mode; }

component nic_c {
  pool pkt_s link_p;  bind link_p *;
  pool cfg_s cfg_p;   bind cfg_p *;

  action send_a      { output pkt_s out_pkt; }
  action receive_a   { input  pkt_s in_pkt; }
  action configure_a { output cfg_s new_cfg; }
  action transfer_a {
    input cfg_s cur_cfg;
    constraint !cur_cfg.initial;          // never run on the reset configuration
    constraint cur_cfg.mode == mode_e::NORMAL;
  }
}
```

The three timing rules, drawn. Each column is one step of scenario time and a high level means the action is executing; these are scheduling pictures, not clocked waveforms.

**Binding and inference.** An activity is a *partial* specification. If you leave an input unbound, the tool must complete the scenario: it binds the input to a suitable producer that is traversed, or it **infers** (adds) a producer action that the activity never mentions, and if no completion exists it reports an error (§17.1). Inference can chain: an inferred action may itself need an inferred producer. When every input is explicitly bound to traversed actions, the tool may not add actions at all.

That is why `raw_test_a` says `bind w1.out_buf r1.in_buf;`. Without it, the read may consume the output of any earlier write, including one the tool inferred, and your "read back what I wrote" check reads some other address. Explicit binds are only legal between fields bound to the same pool (§12.9.1).

### Resources: lock and share

A resource is something an action holds for its whole execution: a DMA channel, a processor core, a memory region. You declare `resource mem_region_r { }`, size its pool with `pool [2] mem_region_r region_p;` (the size defaults to 1, §15.1), and every instance gets a built-in `instance_id` from 0 to size − 1 (§14.1.1). An action claims an instance in one of two modes (§14.2.1):

- `lock`: no other action may use that instance while the locking action executes.
- `share`: no other action may *lock* that instance while the sharing action executes; other sharers are fine.

The tool picks which instance each claim gets. Two actions that overlap in time on the same instance are legal only if both share.

**The classic mistake: a resource as an input.** `input mem_region_r region;` does not compile, because `input` and `output` accept only buffer, stream and state types (§13.4.1). Data flows; resources are claimed. Write `lock mem_region_r region;` or `share mem_region_r region;`.

**Not the UVM sequencer's lock.** [Sequencer `lock()` and `grab()`](/curriculum/T2_Intermediate/I-UVM-3B_Advanced_Sequencing_and_Layering/sequence-arbitration) are run-time arbitration requests inside one sequencer. A PSS `lock` is a rule the tool satisfies *when it builds the scenario*, before anything runs. If no assignment of instances works, there is no test to run, and the tool tells you at generation time.

**`schedule` versus `parallel` with one region.** Take the `mem_stress_a` activity pictured earlier (two branches, `w0` then `r0`, and `w1` then `r1`) and shrink the region pool to `pool [1]`. Every action now claims region 0: the writes lock it and the reads share it. Under `parallel`, both branches must start together, so `w0` and `w1` would hold the same lock at once, and no legal scenario exists. Under `schedule`, the tool may order the actions, and one legal order is this:

- **Scenario 1** needs nothing new: the traversed `write_a` completes before the read, so it can supply the buffer. The visualizer always binds to it; a real tool may also bind the input to an inferred producer unless you pin it with `bind` (§17.1).

Four simplifications in the visualizer, so do not copy them into a real model:
- Its SV templates start sequences on `m_sequencer` to stay short. In a virtual sequence you use `p_sequencer.mem_sqr`, as on this page.
- Its source writes widths as `bit[31:0]`. Prefer `bit[32]`; the range form is deprecated (§7.2.1).
- Its generated code shows solved values in hex, such as `0x00001A3C`. A real tool prints a `bit` field as unsigned decimal, `6716` (§22.5.3.2).
- Its generator wraps each SV template in `begin : label … end` for you. A real tool pastes templates verbatim (§22.5), so your templates must carry their own `begin … end`, as `write_a` and `read_check_a` do on this page.

### Data constraints: `in`, `dist` and `default`

PSS constraints look like SystemVerilog constraints, but weighting and defaults work differently. Notice where each kind of bias lives:

```pss
component mem_c {
  action burst_write {
    rand bit[8] len;
    constraint len in [1..16];
    // dist is a separate directive (PSS 2.1 and later), not an operator in an expression
    constraint len_bias { dist len in [1 := 10, 4 := 30, 8..16 :/ 60]; }
  }
  action single_write { }
  action read_verify  { }

  action stress_test {
    rand int num_iterations;
    constraint num_iterations in [100..10000];
    // default: holds unless a containing or derived context overrides it
    // (constraint default s.num_iterations == 5000;) or removes it (default disable)
    constraint default num_iterations == 1000;

    activity {
      repeat (num_iterations) {
        select {                  // a weighted choice, made again on every iteration
          [70]: do burst_write;
          [30]: do single_write;
        }
        do read_verify;
      }
    }
  }
}
```

Key differences from SystemVerilog constraints:
- **`dist` is a directive, and it excludes unlisted values.** In SystemVerilog, `x dist {...}` is itself a constraint: a set-membership test plus weights (IEEE 1800-2023 §18.5.3). In PSS, `dist x in [...];` is a separate directive (§16.1.11). Unless a constraint conflicts, the value must fall inside the `dist` list, with probability proportional to its weight; so in `burst_write`, 2, 3, 5, 6 and 7 never occur. If a constraint does conflict, the constraint wins and the solve does not fail.
- **No `soft`; use `default`.** There is no `soft` keyword in PSS 3.0 (§4.4). A `default` value constraint (`constraint default x == 1000;`) fixes a value until a containing or derived context overrides it with its own `default`, or removes it with `default disable x;` (§16.1.10). A plain constraint that disagrees with an active default is a contradiction, not an override. Compare SystemVerilog `soft`, which simply yields to hard constraints (IEEE 1800-2023 §18.5.13; [I-SV-2A](/curriculum/T2_Intermediate/I-SV-2A_Constrained_Randomization_Fundamentals/constraint-blocks)). A `default` may only be applied to a `rand` field.
- **Weighted choices between actions belong in the activity.** `select` branches with a `[weight]` are drawn again on every pass of the `repeat` (§12.4.4). A `dist` on a field of `stress_test` would be solved once for the whole test.
- **Constraints can relate fields of different actions**, flow objects and resources. Values are chosen as each action is traversed, but the tool looks ahead over the rest of the activity, so an early choice never strands a later constraint (§16.4.9).

### From model to UVM and to C

What a tool produces for simulation is tool-dependent, but the common shape follows from the template rules:

1. The tool solves the scenario: the schedule, the bindings, any inferred actions, the resource instances and the values.
2. For UVM it emits a sequence, typically a **virtual sequence** that runs on your virtual sequencer, whose `body()` contains each scheduled action's `exec body SV` template in order, with `fork … join` for `parallel` branches. The templates start your existing sequences on real sequencers through `p_sequencer` (declared by `` `uvm_declare_p_sequencer ``).
3. For bare metal it emits a C function made of the `exec body C` templates, plus any `exec header C` text.

**Where checking lives.** A template can check (the C `read_check_a` compares the read data, because bare metal has no scoreboard), or it can leave checking to your UVM **scoreboard** ([A-UVM-6](/curriculum/T3_Advanced/A-UVM-6_Scoreboards_and_Reference_Models/index)), which compares every monitored read against a reference memory whoever started it. This page's SV templates only read. The lab uses the other pattern, a self-checking SV template. Both are legitimate; pick one per environment so a read is not checked twice by different rules.

**What stays hand-written.** The `exec` templates (or imported functions) for every action and platform; the UVM sequences, agents, scoreboard and coverage they rely on; the virtual sequencer; and the C HAL. The tool writes only the scenario layer, the part that changes from test to test.

**Generated values: before the run or on the target?** The listings in Make It Work assume values were solved when the test was generated, so the code contains constants. Some tool flows instead generate code once per model and solve on the target at run time (§22.8 lists the flows). Ask your tool which it does.

### When PSS adds value, and when it does not

PSS is a cost: a tool licence, a new language, a realization layer someone must own, and debugging through generated code. It pays when the scenario layer is the expensive part.

| Question | Favours UVM virtual sequences | Favours PSS |
|---|---|---|
| How many platforms run the scenarios? | One (simulation) | Several: simulation, emulation, prototype, silicon |
| How much concurrency must be legal and varied? | A few hand-written `fork … join` blocks | Many combinations constrained by shared resources |
| How long are setup chains? | Short and fixed | Many prerequisites that inference can fill in |
| Who owns per-platform realization? | Nobody needs to | A named owner for each platform's templates or HAL |
| How will failures be debugged? | In code you wrote | Through generated code: keep the tool's schedule report with every failing seed |

**Two worked decisions.**
- *A block-level team with one simulation target, an existing UVM environment and a dozen scenarios.* Use virtual sequences. PSS adds a tool and a layer without removing a platform.
- *An SoC team whose use-case library (boot, DMA under load, low-power entry) must run in simulation, on an emulator and on first silicon.* PSS pays: one scenario library, three realizations written once, and the tool explores concurrency that hand-written tests would leave untested.

**The tool landscape.** Commercial PSS tools include Cadence Perspec System Verifier, Siemens EDA Questa inFact, Synopsys VC Portable Stimulus and Breker Verification Systems' Trek family (TrekGen, TrekUVM, TrekSoC, TrekSoC-Si). Their public launch announcements (2018) cover PSS 1.0; check each vendor for 2.1 and 3.0 support. The open-source PSSTools `pssparser` is a parser useful for checking syntax, not a generator. PSS 3.0 defines one input language, the DSL used on this page (§1.2); some early tools also advertised a C++ input format, so check what your tool accepts. Ask any tool:

| Question | Why it matters |
|---|---|
| Which PSS version does it accept (2.1, 3.0, the 3.1 draft)? | `dist` needs 2.1; behavioral coverage needs 3.0 |
| Which targets does it generate (SV/UVM, C, others)? | Portability pays only for the targets you run |
| Does it solve before the run or on the target? | Pre-solved tests are reproducible; run-time solving needs a solver on the target |
| How much does it infer, and can you see why? | Inference saves the most work and is where tools differ most |

### Pitfalls and misconceptions

- **"PSS replaces UVM."** It generates scenario-level code that runs on your UVM environment.
- **"PSS is an IEEE standard."** It is Accellera's, with no IEEE number.
- **A resource as an `input`.** Resources are claimed with `lock` or `share` (§13.4.1, §14.2).
- **`schedule` used as if it meant `parallel`.** `schedule` may serialize everything (§12.3.5).
- **An unbound input when several producers exist.** The tool may bind or infer something you did not intend (§17.1); add `bind`.
- **A pool too small for parallel locks.** No legal scenario (§12.3.4, §14.2.1).
- **SV templates without `begin … end`.** The generated SystemVerilog does not compile (§22.5).
- **`dist` read as SystemVerilog `soft`.** Unlisted values are excluded, not just rare (§16.1.11).

### Recap

- PSS is Accellera's language for test intent; the tool writes the scenario layer and you write the realization layer once.
- Components own actions and pools; `bind` directives connect pools to actions.
- Atomic actions carry `exec` templates that are pasted verbatim with decimal values; compound actions carry activities.
- Activities order traversals with sequence, `parallel`, `schedule`, `select` and `repeat`; explicit `bind` pins which object an action consumes.
- Buffers, streams and states differ in timing; resources are claimed, never passed.
- PSS pays when many platforms or resource-constrained concurrency make the scenario layer expensive.

## Make It Work

### A complete model: two writers, two readers, two regions

The scenario: in each round, two write-then-read pairs run in parallel, each in its own 4KB memory region, and every read checks the word its own write produced. The number of rounds is random with a default of 2. **Predict before you read the generated code:** in round 1, can both writes use region 0? What would change with `pool [1]`?

```pss
// compile (Accellera PSS 3.0; checked against the standard by reading, not by a tool)
buffer mem_buf_s {
  rand bit[32] addr;
  rand bit[32] data;
  constraint { addr in [0x1000..0x2FFC]; addr % 4 == 0; }
}

resource mem_region_r { }               // one 4KB memory region

component mem_subsys_c {
  pool mem_buf_s buf_p;
  bind buf_p *;
  pool [2] mem_region_r region_p;       // instance_id 0: 0x1000-0x1FFC, 1: 0x2000-0x2FFC
  bind region_p *;

  action write_a {
    lock   mem_region_r region;         // nothing else uses this region while it writes
    output mem_buf_s    out_buf;
    constraint {
      out_buf.addr >= 0x1000 * (region.instance_id + 1);
      out_buf.addr <  0x1000 * (region.instance_id + 2);
    }
    exec body C = """ mem_write32({{out_buf.addr}}, {{out_buf.data}}); """;
    exec body SV = """
      begin
        mem_wr_seq wr = mem_wr_seq::type_id::create("wr");
        wr.addr = {{out_buf.addr}};
        wr.data = {{out_buf.data}};
        wr.start(p_sequencer.mem_sqr, this);
      end
    """;
  }

  action read_check_a {
    share  mem_region_r region;         // readers may overlap; a writer may not
    input  mem_buf_s    in_buf;
    constraint {
      in_buf.addr >= 0x1000 * (region.instance_id + 1);
      in_buf.addr <  0x1000 * (region.instance_id + 2);
    }
    exec body C = """
      if (mem_read32({{in_buf.addr}}) != {{in_buf.data}})
        test_fail("read-after-write mismatch");
    """;
    exec body SV = """
      begin
        mem_rd_seq rd = mem_rd_seq::type_id::create("rd");
        rd.addr = {{in_buf.addr}};
        rd.start(p_sequencer.mem_sqr, this);
      end
    """;
  }
}

component pss_top {
  mem_subsys_c mem;

  action mem_stress_a {
    rand bit[8] rounds;
    constraint rounds in [1..8];
    constraint default rounds == 2;     // a containing test may set its own default
    exec header C = """ #include "mem_test_platform.h" """;

    activity {
      repeat (rounds) {
        parallel {
          sequence {
            w0: do mem_subsys_c::write_a;
            r0: do mem_subsys_c::read_check_a;
            bind w0.out_buf r0.in_buf;
          }
          sequence {
            w1: do mem_subsys_c::write_a;
            r1: do mem_subsys_c::read_check_a;
            bind w1.out_buf r1.in_buf;
          }
        }
      }
    }
  }
}
```

What each piece guarantees:
- **The two locks force two regions.** `w0` and `w1` start together and each locks a region for its whole execution, so they must get different instances. With `pool [1]` they cannot, and the tool reports that no legal scenario exists.
- **The read follows its write's region.** Both actions tie the address to `region.instance_id`, and the `bind` makes them the same buffer, so `r0` shares exactly the region `w0` locked.
- **Nothing is inferred.** Every input is explicitly bound to a traversed action, so the tool may not add actions (§17.1).

### How to build a PSS scenario

1. **List the actions and the data they exchange.** Each operation the hardware can do is an action; each piece of data passed between them is a flow object.
2. **Pick a flow-object kind for each exchange.** Data left in memory is a buffer, data in flight is a stream, a mode or configuration is a state.
3. **Model shared hardware as resources** and size each pool to the number of real instances. Claim with `lock` for exclusive use and `share` otherwise.
4. **Write the activity**, then add `bind` for every exchange whose producer matters to the check.
5. **Write the `exec` templates** for each platform: wrap SystemVerilog in `begin … end`, start real sequences through `p_sequencer`, and decide where checking lives.
6. **Generate, then read the resolved schedule before you run it**: which actions were inferred, which instances were assigned, which values were chosen.
7. **Run on each platform** and keep the seed and schedule report with every failure.

### Debugging a PSS model

| Symptom | Likely cause | Fix |
|---|---|---|
| The tool rejects `input dma_chan_r chan;` | A resource used as an input (§13.4.1) | `lock` or `share` it (§14.2) |
| "No legal scenario" or a solve failure | A plain constraint contradicts an active `default` (§16.1.10); parallel locks exceed the pool (§12.3.4, §14.2.1); no pool bound for an input | Override with `constraint default …` or `default disable`; enlarge the pool or use `schedule`; add the static `bind` |
| Unexpected extra actions in the schedule | Inference completed an unbound input (§17.1) | Add explicit `bind`s; use an `atomic` block (§12.3.7) to keep inferred actions out of a region |
| The read checks the wrong address | The input was bound to a different producer | Add `bind w.out_buf r.in_buf;` |
| Generated SystemVerilog does not compile | Template declarations outside `begin … end`, or a template typo (templates are not checked, §22.5) | Wrap every SV template; compile one generated test early |
| C and UVM runs disagree | The two templates of an action do different things | Review each action's templates side by side |
| The UVM test hangs in `start_item` | A child sequence was started on the virtual sequencer, which has no driver | Start children on `p_sequencer.<real sequencer>` |

## Push Further

### Expert: inference, binding and determinism

When bindings are left implicit, the tool completes the scenario by binding to traversed actions or by inferring new ones, and it may choose randomly or by policy, including coverage goals (§17.1). Only when every required input is explicitly bound to traversed actions is it forbidden to add actions. Inference chains until a producer needs nothing more, or a tool limit is hit and an error is reported; the informative Annex E describes how candidates are considered. Explicit binds must also respect pools: both fields must be statically bound to the same pool instance (§12.9.1), and a field and its pool must be of exactly the same type, not a base or derived type (§15.3.1).

Two tools for control. An **`atomic { }` block** (§12.3.7) keeps inferred actions and resource-driven reordering from slipping between the actions it contains; inferred actions are never inside an atomic set. **Hierarchical binding** (§12.10) lets a compound action delegate its own input or output to a sub-action with `bind`; the outer action's boundary then sets the timing, so an input buffer must be ready before the compound action's whole activity begins.

*Interview angle:* "Your read-after-write test sometimes reads an address no traversed write produced. Why?" Because the input was unbound and the tool inferred or chose another producer; pin it with `bind`.

### Expert: parallel, schedule and join specifiers

`parallel` (§12.3.4) gives a synchronized start and forbids any scheduling dependency between branches, so any binding or lock that would force one branch to wait for another makes the activity illegal. `schedule` (§12.3.5) requires all its statements to execute in any order that satisfies the other rules; sequential orders are valid. Both accept **join specifiers** (§12.3.6): `join_branch(label, …)` continues after the named branches, `join_select(n)` after n randomly chosen branches, `join_none` immediately, and `join_first(n)` after the first n to complete at run time.

*Predict:* two lockers on a `pool [1]` resource. Under `parallel` there is no legal scenario; under `schedule` the tool serializes them. The same model with `pool [2]` is legal under both.

### Expert: when values are chosen, and the limits of the solver

Random fields are chosen as the activity is traversed, with **relationship lookahead** over constraints from the rest of the traversal, including inferred actions, bindings and scheduling (§16.4.9), and across sub-actions (§16.4.10). The solve-side exec kinds run in a defined order: `pre_solve` before solving, `post_solve` after, `pre_body` before code is generated for the body (§22.1.2). Values assigned by an `exec body` are checked against the constraints only after the block completes; a conflict is illegal and the tool does not backtrack (§16.4.13). Practical rule: compute derived values in `post_solve`, and never assign a constrained field from target code.

### Expert: PSS `default` and `dist` versus SystemVerilog `soft` and `dist`

A PSS `default` is an equality that holds until it is disabled or replaced by another default. Precedence: a higher-level containing context beats a lower one, a derived type beats its base, and a later declaration beats an earlier one in the same type (§16.1.10 d). A default on an aggregate applies to all its random scalar fields, and defaults may not be conditioned on non-constant expressions. SystemVerilog `soft` (IEEE 1800-2023 §18.5.13) is resolved by priority among soft constraints and always yields to hard ones; it never causes a contradiction.

PSS `dist` (§16.1.11) is a directive: constraints take priority over it, and with several `dist` directives on overlapping expressions the resulting distribution is undefined. SystemVerilog `dist` (IEEE 1800-2023 §18.5.3) is a constraint whose set membership is hard. Porting a SystemVerilog constraint set to PSS line by line therefore changes behaviour in both directions. PSS 3.0 has no `soft`; a 3.1 draft is in public review, so check your tool's version before assuming either way.

### Expert: realization flows and exec kinds

PSS 3.0 defines three mapping mechanisms: imported functions bound to a foreign API (§22.4), target-template functions (§22.6) and target-template exec blocks (§22.5). It also defines three flows: no target code generation (the test calls existing APIs directly), per-model generation and per-test generation (§22.8, Tables 25 and 26). Not every mechanism works in every flow: target-template exec blocks need generated code, and `exec header` and `declaration` may only be templates (§22.1.2). The target exec kinds are `body`, `run_start`, `run_end`, `header` and `declaration`; `run_start` and `run_end` are restricted to pre-generation flows. Whether a given tool solves before the run or on the target is **tool-dependent**.

*Architecture consequence:* if you need on-target randomization on silicon, design the realization around imported functions into your HAL, not around pasted templates with constants.

### Expert: coverage in PSS

PSS 3.0 has two kinds of coverage. **Data coverage** uses covergroups on PSS fields (Clause 18), typically measured on the generation side. **Behavioral coverage**, new in 3.0, uses `cover` statements and `monitor` declarations that describe an action order to observe in the executed scenarios (Clause 19). Neither replaces your UVM functional coverage of DUT behaviour. How much a tool automates, for example generating scenarios until a cover target is hit, is **tool-dependent**.

### Expert: PSS versus UVM virtual sequences at scale

Methodology trade-offs, not standard rules:
- **Integration.** Generate against one virtual sequencer type per environment, start children on real sequencers through `p_sequencer`, raise objections in the test (not in generated code), and regenerate per seed rather than editing generated files.
- **Ownership.** The realization layer is a product: one owner per platform, reviewed like VIP. Templates that drift apart between C and SV produce "passes in simulation, fails on silicon" reports that are really model bugs.
- **Debug.** Archive the tool's resolved schedule with every failing run. Without it, a failure in generated code cannot be traced back to the action and constraint that produced it.
- **Cost model.** PSS reduces work in proportion to scenarios × platforms; it adds a fixed cost (tool, training, realization). With one platform, the multiplier is 1.
- **Versions and tools (tool-dependent).** Tools support different versions and input formats; public announcements of the main commercial tools date from PSS 1.0. Pin the version in your flow and test a feature before you design around it.

### Kata: fix the model

This model has six errors. Find each one, fix it, and name the rule it breaks, before you open the answer.

```pss
resource chan_r { }
buffer data_s { rand bit[32] addr; }

component dma_c {
  pool [1] chan_r chan_p;
  bind chan_p *;
  pool data_s data_p;
  bind data_p *;

  action load_a {
    output data_s dst;
    constraint dst.addr inside [0x0..0xFF];
  }

  action copy_a {
    input chan_r ch;
    input data_s src;
    rand bit[8] n;
    rand bit[8] burst;
    constraint soft n == 4;
    constraint burst dist { 4 := 80, 8 := 20 };
  }

  action two_copies_a {
    activity {
      do load_a as l1;
      parallel {
        c1: do copy_a;
        c2: do copy_a;
      }
    }
  }
}
```

<details>
<summary>Answer: the six fixes</summary>

1. `input chan_r ch;` becomes `lock chan_r ch;`. A resource is claimed, never an input (§13.4.1, §14.2.1).
2. `do load_a as l1;` becomes `l1: do load_a;`. A traversal is named with a label (§12.3.1); `as` exists only for package import aliases.
3. `dst.addr inside [0x0..0xFF]` becomes `dst.addr in [0x0..0xFF]`. PSS set membership is `in` (§8.5.9).
4. `constraint soft n == 4;` becomes `constraint default n == 4;`. PSS 3.0 has no `soft` (§4.4); a `default` on a `rand` field is the nearest equivalent, but a conflicting plain constraint is a contradiction (§16.1.10).
5. `constraint burst dist { 4 := 80, 8 := 20 };` becomes `constraint dist burst in [4 := 80, 8 := 20];`. The PSS distribution is a directive with square brackets (§16.1.11).
6. `c1` and `c2` both lock a channel under `parallel` from a pool of one, so there is no legal scenario. Use `pool [2] chan_r chan_p;`, or replace `parallel` with `schedule` if the copies may run one after the other (§12.3.4, §12.3.5, §14.2.1).

Also note what is *not* an error: both copies input `src` without a `bind`, and `l1`'s buffer may feed both, because a buffer may be the input of any number of actions (§13.1.1). Add `bind l1.dst c1.src;` and `bind l1.dst c2.src;` if the copies must use that buffer and nothing the tool infers.

</details>
