## Quick Take

- **What it is:** A measurement-first method for making UVM simulations and regressions faster. You **measure** a run with the right clock, **profile** it to see which code consumed the CPU time, **fix** the few costly habits the profile points at, and **measure again** to prove the gain. At regression scale you also **plan throughput**: how many simulations run at once, which tests run when, and how long the whole set takes.
- **Why it matters:** Simulator licences, slots on the compute farm (the shared pool of machines that runs simulations) and engineers' waiting time are finite. A nightly regression that spills into the working day delays every bug fix. Folklore fixes waste that time: "add an analysis FIFO for parallelism" or "just lower the verbosity" often change nothing, and some "optimizations", such as reusing one transaction object, make the testbench (TB) silently wrong.
- **The Analogy:** A racing pit crew with a stopwatch. Nobody changes the tyre routine until the stopwatch shows which step is slow, and after the change they time it again. *Where it breaks:* a pit crew gets faster by adding people who work in parallel, but one simulation runs its processes one at a time (IEEE 1800-2023 §4.5), so extra threads or FIFOs inside one simulation add work, not speed. And a simulation has three different clocks, only two of which can ever show a speed-up.

**You will be able to:**
1. **Measure** a UVM run correctly: choose CPU, wall-clock or simulated time, fix the seed and build, repeat runs, and label illustrative numbers.
2. **Read** a profile and attribute time to the design under test (DUT), the testbench and UVM-library hotspots (configuration lookups, message formatting, objection churn, recording, object creation, coverage sampling).
3. **Apply** targeted fixes (cache lookups, guard messages, raise and drop once, turn off recording, waves and tracing in regressions) and **measure** the gain.
4. **Explain** why analysis FIFOs, polling loops and `#0` do or do not cost time, using the scheduler rules from F3B and F3C without re-deriving them.
5. **Plan** regression throughput: compile once and run many, run parallel jobs within licence and queue limits, and select tests.

## Build Your Mental Model

**How to read this lesson.** The core path is the first five sections: the three clocks, reading a profile, the UVM hotspots, why decoupling is not parallelism, and the scheduler costs. Regression throughput is practitioner depth. Make It Work gives you one bench with four seeded costs that you measure and remove one at a time. Push Further holds the expert material: what happens inside the UVM library, noise in timing, and the levers that only your simulator has.

Words you will meet, in one line each (the links go to where each is taught):

- A **process** is an `initial` or `always` block, a branch of a `fork`, or a UVM phase task such as `run_phase`. The simulator runs one process at a time and switches when the running process waits ([F3A](/curriculum/T1_Foundational/F3A_Simulation_Semantics/index)).
- A **time slot** is everything the simulator does at one simulation time; a **delta cycle** is one more pass through its regions without advancing time ([F3B](/curriculum/T1_Foundational/F3B_Scheduling_Regions/index), [F3C](/curriculum/T1_Foundational/F3C_Delta_Cycles_and_Race_Conditions/index)).
- An **objection** keeps a run-time phase open; you **raise** and **drop** it ([I-UVM-1C](/curriculum/T2_Intermediate/I-UVM-1C_UVM_Phasing/index)).
- The **configuration database** (`uvm_config_db`) stores values by scope and field name for components to `get` ([I-UVM-2C](/curriculum/T2_Intermediate/I-UVM-2C_Configuration_and_Resources/index)).
- An **analysis port** broadcasts each transaction to its subscribers by calling their `write()` ([I-UVM-2B](/curriculum/T2_Intermediate/I-UVM-2B_TLM_Connections/index)).
- The **report macros** (`` `uvm_info `` and friends) and **verbosity** decide which messages print ([I-UVM-1D](/curriculum/T2_Intermediate/I-UVM-1D_Reporting_and_Run_Control/index)).
- A **scoreboard** checks the DUT's output against expected values ([A-UVM-6](/curriculum/T3_Advanced/A-UVM-6_Scoreboards_and_Reference_Models/index)).
- A **hot path** is code that runs once per transaction or once per clock. Code that runs once per test (such as `build_phase`) is almost never worth optimizing.
- A **regression** is a script that runs many tests, each with one or more random **seeds** (the number that fixes the random choices), and marks each run pass or fail. A **licence** is the right to run one simulation at a time; a site has a fixed number.
- A **profiler** is a simulator feature that reports where CPU time went, per function, task, class method or module. Its output is a **profile**. How you turn it on and how its report looks are tool-dependent.

### Three clocks: measure before you change anything

Every simulation run has three different clocks, and mixing them up is the most common measurement mistake.

| Clock | What it measures | Where you read it | Does a performance fix change it? |
|---|---|---|---|
| **Simulated time** | Time inside the model: `$time`, the `@ 20035` in a UVM log line | the simulator (IEEE 1800-2023 §20.3) | **No.** The same code with the same seed reaches the same `$time` |
| **CPU time** | Seconds of processor work the operating system charged to the simulator process | outside the simulator, e.g. `user` + `sys` from `/usr/bin/time -p` | **Yes.** This is what an optimization reduces |
| **Wall-clock time** | Elapsed real time from start to finish | outside the simulator, e.g. `real` from `/usr/bin/time -p`, or the regression system | **Yes**, but it also includes waiting for a licence, disk, the network and other jobs on the same machine |

The key rule: **a pure performance fix leaves simulated time and every result unchanged, and reduces CPU time.** If `$time` at the end or the scoreboard's counts change, you changed the test's behaviour, not just its speed. That is a bug until proven otherwise.

**The measurement protocol.** Use it every time you claim a speed-up:

1. **Same build, same seed, same plusargs** (command-line options that start with `+`). Compile once and run both versions from the same image where you can, with a plusarg that selects the variant, or rebuild with the same compile options.
2. **One change at a time**, so you know which change earned the gain.
3. **Repeat each run 3 to 5 times and take the median.** CPU time varies from run to run, especially on a shared machine.
4. **Record the tool name and version, the host, and the compile options.** Debug options that keep every signal visible can change the speed of the whole run (tool-dependent).
5. **Check that the results did not change:** the same report summary, the same scoreboard counts, the same coverage.
6. **Label every number.** A number from a run carries the tool, version and host; anything else is "illustrative".

Here is what a correct before-and-after record looks like, for the bench in Make It Work. The first three rows are exact: they follow from the code. The time rows are yours to fill in, because CPU time depends on the simulator, its version and the machine.

| | Run A: baseline | Run B: `+FIX_SB` (one change) |
|---|---|---|
| `$time` at the end (simulated) | 20035 ns | 20035 ns (must not change) |
| `SCB_SUMMARY` | `matches=2000 mismatches=0 pending=0` | identical (must not change) |
| `PERF_SUMMARY cmp=` (scoreboard comparisons) | 1999000 | 2000 |
| CPU time, median of 3 (`user` + `sys`) | your measurement | your measurement |
| Wall-clock time, median of 3 (`real`) | your measurement | your measurement |

Read the table from top to bottom: the behaviour rows match, the work row drops by three orders of magnitude, and only then do the time rows mean anything.

**Pitfalls.**
- **Printing `$time` as "run time".** It is simulated time; an optimization cannot change it. A lab that prints `wall_time=%0t` from `$time` measures nothing.
- **Comparing runs with different seeds.** A different seed is a different test: different stimulus, a different number of transactions, a different run length.
- **One run each.** A small difference between two single runs on a shared machine is often noise: compare it with the spread of repeated runs.
- **Changing two things at once.** You cannot tell which one helped, or whether one of them made things worse.

**Debugging a vanished speed-up.** Symptom: the fix was fast on your machine, but the regression is not faster. Usual causes: the regression runs a different compile mode or different plusargs; wall-clock time is dominated by licence or queue waits, not CPU; or the fixed code is not on the hot path in the tests the regression runs. Compare the two command lines first, then CPU time rather than wall-clock time.

**In a real project.** Teams keep a small performance baseline in continuous integration: a few fixed tests and seeds whose CPU time is recorded on every library or TB change, so a slowdown is caught on the day it is introduced. In interviews, "how would you prove your change made the regression faster?" is a standard question, and this protocol is the answer.

### Reading a profile

A profile lists locations (functions, tasks, class methods, modules) with three numbers that matter:

- **Self time:** CPU time spent in that location's own code, not in the routines it calls.
- **Total time** (also called inclusive time): self time plus everything it called.
- **Calls:** how many times it ran. Calls are often the most useful column, because they are exact and they tell you *why* a location is expensive.

Then **attribute** every row to one of four owners:

- **DUT:** the register-transfer level (RTL) modules you are verifying;
- **TB:** your own classes, interfaces and modules;
- **UVM library:** classes and functions in `uvm_pkg`;
- **simulator kernel and I/O:** scheduling, clocking blocks, waveform dumping and file output (how the tool names these is tool-dependent).

The rule that saves most time: **UVM-library time is almost always caused by how your TB calls the library.** When a library routine dominates, look at its callers and its call count, not at the library.

**Pitfalls.** Sorting by total time and fixing the top row: `uvm_pkg::run_test` or your test's `run_phase` always has nearly 100% total time, because everything runs under it. Sort by self time, then use calls to find the cause. And do not trust a profile of a run that is too short to matter: profile a run long enough to reach steady state.

**Debugging.** Symptom: "the profile says 60% is in `uvm_pkg`". Cause: per-item calls into the library from your code. Fix: list the library rows with the largest call counts, find their callers (most profilers can show a call tree; tool-dependent), and move those calls out of the hot path.

### UVM hotspots and their fixes

These are the costly habits that profiles of UVM benches keep finding. Each row names the mechanism (in uvm-core 2020.3.1, the Accellera reference implementation of IEEE 1800.2-2020), what the profile shows, the fix, and how to prove it.

| Hotspot | Why it costs | What the profile shows | Fix | How to verify |
|---|---|---|---|---|
| 1. Message formatted outside the guard | A direct `uvm_report_info(id, $sformatf(...), v)` builds the string, then filters it | `$sformatf`, `convert2string` or `sprint` called once per item with no matching log lines | `` `uvm_info ``, or `uvm_report_enabled` around expensive work | the formatting call count drops to 0 at regression verbosity |
| 2. `uvm_config_db::get` per item | Each `get` scans every entry with that field name and matches its scope | `lookup_name`, `uvm_is_match` called per item | read once in `build_phase`; or `get` a configuration object handle once | `get` count = 1 per component |
| 3. Objection raised and dropped per item | Each raise and drop updates every ancestor; a drop to zero starts a background drain (the wait, in uvm-core a separate process, that runs before the count is passed up) | `uvm_objection::m_raise`, `m_drop` at a multiple of the item count (one per hierarchy level) | raise once in the test or the top sequence | raises = 1 per test |
| 4. Transaction recording left on | Each recorded item opens a recorder and records every field | `begin_tr`, recorder and stream routines per item | recording off in regressions; on for debug reruns | the recording routines leave the profile |
| 5. Throwaway objects | Creating, copying, cloning or printing objects that nobody stores | `create_object_by_type`, `copy`, `clone`, `sprint` call counts above one per item | copy only what you store; keep `sprint()` out of hot paths unless guarded | those counts drop to what the design needs |
| 6. Field automation in hot `copy`/`compare` | The `` `uvm_field_* `` macros route every field through a policy object at run time; `copy()` runs that walk and *then* `do_copy` (same for `compare`) | `do_execute_op` and policy-class routines | take the fields out of the macro path for that operation (no field macros, or flag them `UVM_NOCOPY` and `UVM_NOCOMPARE`), then hand-write `do_copy`/`do_compare` | copy and compare results unchanged; gain is tool-dependent: measure it |
| 7. Coverage sampled too often | Sampling every clock instead of every transaction | covergroup sample routines at the clock rate | sample per transaction, gate with `iff`, `stop()` unused groups | sample count = transaction count |
| 8. Your own algorithms | Searching a queue for every item: N items cost N² comparisons | your scoreboard's `write` or check function dominates self time | an associative array keyed by the match field | the comparison count grows with N, not N² |

#### Hotspot 1: formatting a message nobody will see

This is the hotspot behind a common misconception: "a direct `uvm_report_info(..., $sformatf(...))` is as cheap as the guarded macro when the message is filtered". It is not, and the reason is when the string is built.

- The **`` `uvm_info `` macro** expands, in uvm-core, to a block that first asks the report object whether the message is enabled (its verbosity and action) and calls `uvm_report_info` only if it is (uvm-core `src/macros/uvm_message_defines.svh`, `` `uvm_report_begin ``; IEEE 1800.2-2020 B.1.1.1). The message argument, including any `$sformatf`, is never evaluated when the message is filtered.
- A **direct call** to `uvm_report_info(id, msg, verbosity)` is an ordinary function call (IEEE 1800.2-2020 §6.3.3.3). SystemVerilog evaluates every argument before the call, so `msg` is formatted first; the verbosity check happens inside, after the work is done (uvm-core `uvm_report_object.svh`, `uvm_report`).
- **`uvm_report_enabled(verbosity, severity, id)`** returns whether a message with that verbosity, severity and ID would be shown (§6.3.3.2). Use it to guard any expensive work that is not a single message: a payload dump, a checksum, a `sprint()` of a large object.

Traced over 1000 transactions with the component at `UVM_LOW` (or the default `UVM_MEDIUM`) and each message at `UVM_HIGH`:

| Code in the monitor | Verbosity checked | Message built at `UVM_LOW`? | Formatting calls for 1000 items |
|---|---|---|---|
| `` `uvm_info("MON", t.convert2string(), UVM_HIGH) `` | before the message is built | no | 0 |
| `uvm_report_info("MON", t.convert2string(), UVM_HIGH);` | after the message is built | **yes, then discarded** | 1000 |
| `if (uvm_report_enabled(UVM_HIGH, UVM_INFO, "MON")) dump_payload(t);` | before the work | no | 0 |

```systemverilog
// snippet: inside a monitor's run_phase loop
// Cheap when filtered: the macro checks verbosity before building the string.
`uvm_info("MON", t.convert2string(), UVM_HIGH)

// Costly when filtered: convert2string() runs first, then the call discards it.
uvm_report_info("MON", t.convert2string(), UVM_HIGH);

// Guard any expensive debug work, not only one message (§6.3.3.2).
if (uvm_report_enabled(UVM_HIGH, UVM_INFO, "MON")) begin
  dump_payload(t);  // walks a large payload; never runs at regression verbosity
end
```

**The classic mistake** is to believe that `+UVM_VERBOSITY=UVM_LOW` makes every message free. It hides them all, but it removes the formatting cost only for guarded ones. `$display` is never filtered at all. **Symptom in a profile:** `$sformatf`, `convert2string` or `sprint` near the top with call counts equal to the item count, while the log shows none of those messages. **Real testbench:** per-transaction detail belongs at `UVM_HIGH` or above, written with the macros; [I-UVM-1D](/curriculum/T2_Intermediate/I-UVM-1D_Reporting_and_Run_Control/index) covers the verbosity rules themselves.

The answer is 21: one `uvm_is_match` per entry with that field name and type (the function is IEEE 1800.2-2020 F.3.3.1; that `get` uses `lookup_name`, C.2.4.4.1, is how uvm-core implements it). In a real system-on-chip (SoC) TB, common field names such as `vif`, `cfg` or `is_active` are set for dozens of scopes, so the scan is long.

**Fix.** Read the value once, in `build_phase`, into a member variable. If the value must be able to change during the run, do not poll the database: either `get` a **configuration object** (a class handle) once, so every later change to its fields is visible through the handle, or wait for a change in a separate thread with `uvm_config_db#(T)::wait_modified` (C.4.2.2.4). **Pitfall:** "it's only one line" is exactly why it survives code review. **Debugging:** `+UVM_CONFIG_DB_TRACE` (uvm-core only, not in IEEE 1800.2-2020) prints one line per `get`, so a per-item lookup floods the log; that is a debugging switch, never a regression setting.

    { from: "bg", to: "obj", label: "drain for mon: all_dropped(), then m_drop at env (1 to 0)" },

    { from: "bg", to: "obj", label: "drain for env: all_dropped(), m_drop at uvm_test_top, uvm_root" },
    { kind: "divider", from: "mon", label: "next item: the whole chain again" }

**What it showed.** Four counts change on the raise (four `m_raise` calls) and four on the drop (four `m_drop` calls), and the drop starts two background drain processes, one for each level whose count reaches zero. None of that does useful work: the test's own objection already keeps the phase open.

IEEE 1800.2-2020 §10.5.1.3.3 and §10.5.1.3.4 require the propagation up the hierarchy; the background drain process is how uvm-core implements a drop that reaches zero (`uvm_objection.svh`, `m_drop`, `m_execute_scheduled_forks`, `m_forked_drain`).

**Fix.** Raise one objection for the whole stimulus, in the test or in the top-level sequence, and never in drivers or monitors. A top-level sequence can do it with `set_automatic_phase_objection(1)` (§14.2.4.4), which raises the objection before `pre_start` and drops it after `post_start`, so it spans the whole sequence, `body()` included; the standard's own NOTE warns never to use it for a sequence whose `body()` loops `forever`, because the objection would never drop. **Pitfall:** "the monitor must keep the test alive while it is busy". A monitor's `write()` takes no simulation time, so there is nothing to keep alive; if the test ends too early, the fix is in the test (wait for the expected count, or set a drain time, an extra delay after the last drop before the phase ends, taught in [I-UVM-1C](/curriculum/T2_Intermediate/I-UVM-1C_UVM_Phasing/index)), not a per-item objection. **Debugging:** `+UVM_OBJECTION_TRACE` (uvm-core only) prints every raise and drop; thousands of lines from one monitor are the symptom.

#### Practitioner hotspots 4 to 8

**4. Recording.** Transaction recording writes every recorded item, with its fields, to a database a waveform viewer can show. It is off by default: `get_recording_enabled()` returns 0 unless `set_recording_enabled(1)` was called (IEEE 1800.2-2020 §13.1.7.13, §13.1.7.14). It gets turned on by a base test that sets uvm-core's `recording_detail` configuration field (uvm-core only), or by a simulator switch (tool-dependent), and then each sequence item started on a sequencer is recorded automatically unless `disable_auto_item_recording()` was called (§15.2.1.2.10). Recording is a debugging aid: off in regressions, on for the rerun of a failing seed. [I-UVM-6](/curriculum/T2_Intermediate/I-UVM-6_UVM_Recording_Classes/index) explains the recording classes.

**5. Throwaway objects.** `type_id::create` costs a factory override search plus the constructor (uvm-core `uvm_factory.svh`, `create_object_by_type` calls `find_override_by_type`). That cost is worth paying for every object you keep: **a monitor must create a new transaction for every observation**, because subscribers and analysis FIFOs store handles, not copies (IEEE 1800-2023 §8.12: assigning a handle copies the handle, not the object). What you remove are objects nobody keeps: a `clone()` before every compare in a scoreboard that does not store the item, a `copy()` into a temporary, or an unguarded `sprint()`. Replacing `type_id::create` with `new` to save the lookup breaks factory overrides; do it only where a profile shows the factory dominating, and never for objects a test may want to override.

**6. Field automation.** The `` `uvm_field_* `` macros implement `do_execute_op` (IEEE 1800.2-2020 B.2.1.1, §5.3.13): every `copy`, `compare`, `print`, `pack` and `record` walks the registered fields through a policy object at run time. That is convenient and usually affordable. When a profile shows `copy` or `compare` of one item type near the top, hand-written `do_copy` and `do_compare` for that type are the fix, but only if the macro path stops doing the same work: `copy()` first runs `do_execute_op` (the field-macro walk) and then calls `do_copy`, and `compare()` does the same with `do_compare` (§5.3.8.1; uvm-core `uvm_copier.svh`, `copy_object`). Adding hand-written methods while keeping `UVM_ALL_ON` fields does every field twice, which is slower. So either drop the field macros for that type (`` `uvm_object_utils `` plus hand-written `do_copy`, `do_compare` and `convert2string`), or keep them for printing and flag the fields `UVM_ALL_ON | UVM_NOCOPY | UVM_NOCOMPARE`. The gain is tool-dependent, so measure it, and check that copies and compares give the same results ([I-UVM-4](/curriculum/T2_Intermediate/I-UVM-4_UVM_Policy_Classes/index) covers the policy classes).

**7. Coverage sampling.** A covergroup sampled on every clock edge costs one sample per clock, and it also samples idle cycles, which inflates hit counts. Sample per transaction, in the subscriber's `write()`; gate clocked sampling with `iff (valid)`; and `stop()` covergroups the current test does not need (IEEE 1800-2023 §19.8, Table 19-5). Never switch off coverage that the verification plan needs, to save time: that coverage is the point of the run. [I-SV-3A](/curriculum/T2_Intermediate/I-SV-3A_Functional_Coverage_Fundamentals/index) teaches covergroups.

**8. Your own algorithms.** A scoreboard that searches a queue for every incoming item does N² work over N items. An associative array keyed by the field you match on (an id, an address) makes each match one lookup. This is ordinary data-structure work, but in a TB-bound bench it is often the largest single row in the profile.

### Decoupling is not parallelism

A common misconception says the opposite: "putting an analysis FIFO between the monitor and the scoreboard makes the scoreboard run in parallel and speeds up the simulation". Start with what `ap.write(t)` really does.

The visualizer below runs one analysis-port broadcast. **Before you press play, predict:** when does the monitor's next statement run, relative to the three subscribers' `write()` functions? Then step through the call trace.

<AnalysisBroadcastVisualizer section="trace" />

**What it showed.** `ap.write(t)` is a loop of ordinary function calls inside the monitor's own process (IEEE 1800.2-2020 §12.2.10.1.4 defines it as sending the value to every connected interface). Each subscriber's `write()` runs to completion, one after another, at one simulation time; nothing is forked. The visualizer models simulation time and call order. It does not model CPU time, so here is the CPU question in words.

**Predict:** the coverage subscriber and the logger each spend some CPU in their `write()`. You put a `uvm_tlm_analysis_fifo` in front of each and move their work into `run_phase` loops that `get()` from the FIFO. What happens to the total CPU time of the run?

**Answer: about the same, or slightly more.** The FIFO's `write()` is a zero-time `try_put` of the handle into an unbounded mailbox (uvm-core `uvm_tlm_fifos.svh`; IEEE 1800.2-2020 §12.2.8.3 defines the analysis FIFO as an unbounded `uvm_tlm_fifo` with a `write` interface). The subscriber's `get()` loop then does exactly the same work, later, in another process of the *same* simulation. The scheduler still executes one event at a time (IEEE 1800-2023 §4.5), so the work is moved, not shared out, and the mailbox and the extra process add a little bookkeeping. And because the FIFO stores the handle, a monitor that reuses its transaction object now corrupts every queued item.

**When a FIFO is right.** Use an analysis FIFO when a subscriber must *wait for simulation time*, for example a checker that compares each request with a response that arrives cycles later: a function cannot wait, a `get()` loop can. Switch the visualizer above to its **Slow subscriber** view to see that case. A FIFO is a decoupling tool for time, never a speed tool. If one subscriber's `write()` is CPU-heavy, make that `write()` cheaper: that is hotspots 5 to 8.

**Pitfall in reviews:** "the monitor is blocked while the scoreboard checks". It is blocked for CPU time only, never for simulation time: the next bus cycle is not missed, because simulated time does not advance during a function call.

### Scheduler costs, without re-teaching scheduling

[F3B](/curriculum/T1_Foundational/F3B_Scheduling_Regions/index) and [F3C](/curriculum/T1_Foundational/F3C_Delta_Cycles_and_Race_Conditions/index) taught the regions and delta cycles. For performance you need one consequence of them: **every time a process resumes, and every extra pass through the regions, costs CPU time, while simulated time stands still.** Three habits create needless resumptions.

**Polling.** Here are three ways for a driver task to wait until `ready` is 1:

```systemverilog
// snippet: three ways to wait for ready inside a driver task
// (a) Time-step poll: resumes every 1 ns, so ten times per 10 ns clock period.
while (!vif.ready) #1ns;

// (b) Clocked poll: resumes at every rising edge until it sees ready = 1.
while (!vif.ready) @(posedge vif.clk);

// (c) Event control with iff (IEEE 1800-2023 §9.4.2.3): the process resumes only
//     at the rising edge where ready is 1.
@(posedge vif.clk iff vif.ready);
```

**Predict:** `ready` rises just after edge 4. How many times does each form resume its process?

Two cautions keep this honest. First, (b) and (c) are not identical: (b) does not wait at all if `ready` is already 1, while (c) always waits for at least one edge. Choose the behaviour you need first, then the cheaper way to write it. Second, `wait (vif.ready)` (§9.4.3) also resumes once, but when `ready` *changes*, which is not necessarily on a clock edge, so it is not a drop-in replacement for a clocked poll in a driver. In a real driver, read through a clocking block: `@(vif.cb iff vif.cb.ready);` ([F4C](/curriculum/T1_Foundational/F4C_Clocking_Blocks/index)). How much CPU the saved resumptions are worth is tool-dependent; on a bench with many agents they add up. **In a profile,** polling shows as a driver or monitor task whose resumption or call count follows the clock or the time step rather than the transaction count (how a profiler reports process resumptions is tool-dependent).

**`#0`.** An explicit `#0` suspends the process and reschedules it in the Inactive region of the same time slot, so it runs again only on the next Inactive-to-Active pass (IEEE 1800-2023 §4.4.2.3). That is an extra pass for every `#0` executed, and `#0` is usually a workaround that hides an ordering bug instead of fixing it ([F3C](/curriculum/T1_Foundational/F3C_Delta_Cycles_and_Race_Conditions/index)). Remove it, and fix the race with nonblocking assignments or a clocking block.

**Loops that never wait.** A loop with no timing control, such as `while (!done);`, never lets another process run. If `done` is set by another process, it never will be: simulated time stops and the simulator uses 100% CPU. That is a hang, not a slow test. The other zero-time hang is feedback that keeps scheduling events in the same time slot, such as a combinational loop.

**A common misconception.** "Mixing `=` and `<=` causes infinite delta loops." It does not: mixing them causes **races** (results that depend on process order) and simulation/synthesis mismatches. Infinite zero-time activity comes from zero-delay feedback or a loop with no timing control, as above.

### Regression throughput

One fast simulation is not the goal; a regression that finishes in time is. Five practices decide that.

1. **Compile and elaborate once, run many.** Building the simulation image can take longer than a short test. Build one image, then select the test with `+UVM_TESTNAME=<test>` (IEEE 1800.2-2020 G.2.1), the seed with your simulator's seed option (tool-dependent), and knobs with plusargs: `$value$plusargs` (IEEE 1800-2023 §21.6) or `+uvm_set_config_int` (G.2.8).
2. **Parallel jobs are bounded by the scarcest resource:** jobs = min(licences, cores, queue slots, memory ÷ memory per job). The licence count is usually the limit.
3. **Estimate the wall-clock time.** For tests of similar length, wall time ≈ ⌈tests ÷ jobs⌉ × time per test. Worked example, with invented numbers: 400 tests of about 20 minutes each, 50 licences and 200 cores give 50 jobs, so ⌈400 ÷ 50⌉ = 8 rounds × 20 min ≈ 160 minutes. The cores do not help, because licences run out first. When test lengths vary, start the longest tests first.
4. **Select tests by purpose.** A short smoke set on every commit, the full set nightly, and long or rare seeds weekly. Many tools can rank tests by the coverage each adds, to build a smaller set that reaches the same coverage (tool-dependent).
5. **Fail fast, and debug in a rerun.** Stop runs that cannot pass: `+UVM_MAX_QUIT_COUNT` (G.2.6) ends a run after a number of errors, and `set_timeout` (F.7.3.3) bounds a hung one. Turn on waves, recording and higher verbosity only when you rerun the failing seed.

**What may be switched off for speed, and what may not.** Safe to switch off in regressions: waveform dumping, transaction recording, debug-level messages (`UVM_HIGH` and above), and tracing plusargs such as `+UVM_OBJECTION_TRACE` and `+UVM_CONFIG_DB_TRACE` (uvm-core only). Never switched off to save time: scoreboards, protocol assertions, the error checks, and the coverage the verification plan needs. A regression that runs fast because it stopped checking reports false passes. If you dump waves at all, scope them (`$dumpvars` with a level and a scope, IEEE 1800-2023 §21.7.1.2) rather than dumping everything.

### Recap

- Measure CPU or wall-clock time outside the simulator; `$time` never shows a speed-up. Same build and seed, one change, median of several runs, every number labelled.
- Read a profile by self time and call count, attribute rows to DUT, TB, UVM library and kernel, and chase library time back to the TB line that causes it.
- The core UVM hotspots are message formatting outside the guard, configuration lookups per item, and objections per item. Recording, throwaway objects, field automation, coverage sampling and your own algorithms follow.
- An analysis FIFO moves work into another process of the same simulation. It adds no parallelism; use it when a subscriber must wait for time.
- Every needless process resumption costs CPU: prefer event controls with `iff` to polling, remove `#0`, and never loop without a timing control.
- Regression throughput: compile once, run many; jobs are bounded by licences and other limits; turn debug aids on only for reruns; never turn checks off for speed.

## Make It Work

### Measure and fix a slow monitor and scoreboard

The bench below has a tiny DUT, `pkt_src`, that sends one packet per clock with an incrementing `id` and `data = 8'(id * 7 + 3)`. A monitor publishes each packet; a scoreboard checks `data` and that no `id` repeats. Four costs from this lesson are seeded in it, each with its fix behind a plusarg, so **one compiled image** gives you every variant:

| Plusarg | Seeded cost (without the plusarg) | Fix (with the plusarg) |
|---|---|---|
| `+FIX_MSG` | monitor: direct `uvm_report_info` formats every item | `` `uvm_info `` macro |
| `+FIX_CFG` | monitor: `uvm_config_db::get` on every item, 21 `max_id` entries to scan | one `get` in `build_phase` |
| `+FIX_OBJ` | monitor: raise and drop an objection per item | only the test's single objection |
| `+FIX_SB` | scoreboard: duplicate check searches every earlier item | associative array keyed by `id` |

Wall-clock seconds depend on the tool, so the bench also **counts its own costly operations**: string formatting (`fmt`), configuration lookups (`cfg_get`), objection raises (`raises`) and scoreboard comparisons (`cmp`). Those counts are exact and deterministic, which makes them gradable; CPU time is what you measure.

```systemverilog
// compile
// perf_tb.sv: one file. Compile once; select each fix with +FIX_* plusargs.
`include "uvm_macros.svh"

interface stream_if (input logic clk);
  timeunit 1ns; timeprecision 1ps;
  logic        valid;
  logic [15:0] id;
  logic [7:0]  data;
  clocking mon_cb @(posedge clk);
    input valid, id, data;  // sampled just before each rising edge
  endclocking
endinterface

// The DUT: sends N_PKTS packets, one per clock, then goes idle.
module pkt_src #(parameter int unsigned N_PKTS = 2000) (
  input  logic        clk,
  input  logic        rst_n,
  output logic        valid,
  output logic [15:0] id,
  output logic [7:0]  data
);
  timeunit 1ns; timeprecision 1ps;
  logic [15:0] next_id;
  always_ff @(posedge clk or negedge rst_n) begin
    if (!rst_n) begin
      valid   <= 1'b0;
      id      <= '0;
      data    <= '0;
      next_id <= '0;
    end else if (next_id < N_PKTS) begin
      valid   <= 1'b1;
      id      <= next_id;
      data    <= 8'(next_id * 7 + 3);
      next_id <= next_id + 16'd1;
    end else begin
      valid   <= 1'b0;
    end
  end
endmodule

package perf_pkg;
  timeunit 1ns; timeprecision 1ps;  // every design element declares its own (§3.14.2.3)
  import uvm_pkg::*;

  localparam int unsigned N_ITEMS = 2000;

  // Operation counters: exact and repeatable, unlike CPU time.
  int unsigned n_fmt, n_cfg_get, n_raise, n_cmp;

  function automatic void raise_counted(uvm_phase phase, uvm_object obj);
    n_raise++;
    phase.raise_objection(obj);
  endfunction

  class pkt_item extends uvm_sequence_item;
    bit [15:0] id;
    bit [7:0]  data;
    `uvm_object_utils(pkt_item)
    function new(string name = "pkt_item");
      super.new(name);
    endfunction
    virtual function string convert2string();
      n_fmt++;  // every message about an item is built here
      return $sformatf("id=%0d data=0x%02h", id, data);
    endfunction
  endclass

  class pkt_mon extends uvm_monitor;
    `uvm_component_utils(pkt_mon)
    virtual stream_if vif;
    uvm_analysis_port #(pkt_item) ap;
    int max_id;
    bit fix_msg, fix_cfg, fix_obj;

    function new(string name, uvm_component parent);
      super.new(name, parent);
    endfunction

    function void build_phase(uvm_phase phase);
      super.build_phase(phase);
      ap = new("ap", this);
      if (!uvm_config_db#(virtual stream_if)::get(this, "", "vif", vif))
        `uvm_fatal("NO_VIF", "virtual interface not found")
      fix_msg = $test$plusargs("FIX_MSG");
      fix_cfg = $test$plusargs("FIX_CFG");
      fix_obj = $test$plusargs("FIX_OBJ");
      if (fix_cfg && !get_max_id())  // FIX 2: one lookup, before the run
        `uvm_fatal("NO_CFG", "max_id not set")
    endfunction

    // Every lookup of max_id goes through here, so the bench can count them.
    function bit get_max_id();
      n_cfg_get++;
      return uvm_config_db#(int)::get(this, "", "max_id", max_id);
    endfunction

    task run_phase(uvm_phase phase);
      pkt_item t;
      forever begin
        @(vif.mon_cb);
        if (vif.mon_cb.valid !== 1'b1) continue;
        if (!fix_obj) raise_counted(phase, this);   // COST 3: objection per item
        t = pkt_item::type_id::create("t");         // a new item every time
        t.id   = vif.mon_cb.id;
        t.data = vif.mon_cb.data;
        if (!fix_cfg && !get_max_id())               // COST 2: lookup per item
          `uvm_fatal("NO_CFG", "max_id not set")
        if (t.id > max_id)
          `uvm_error("ID_RANGE", $sformatf("id %0d above max_id %0d", t.id, max_id))
        if (fix_msg) begin
          `uvm_info("MON", t.convert2string(), UVM_HIGH)  // FIX 1: built only if shown
        end else begin
          uvm_report_info("MON", t.convert2string(), UVM_HIGH);  // COST 1: always built
        end
        ap.write(t);
        if (!fix_obj) phase.drop_objection(this);
      end
    endtask
  endclass

  class pkt_sb extends uvm_scoreboard;
    `uvm_component_utils(pkt_sb)
    uvm_analysis_imp #(pkt_item, pkt_sb) item_imp;
    int unsigned seen, matched, mismatched;
    bit fix_sb;
    pkt_item history_q[$];       // COST 4: every earlier item, searched linearly
    bit      id_seen[bit [15:0]];  // FIX 4: ids seen, looked up by key

    function new(string name, uvm_component parent);
      super.new(name, parent);
    endfunction

    function void build_phase(uvm_phase phase);
      super.build_phase(phase);
      item_imp = new("item_imp", this);
      fix_sb = $test$plusargs("FIX_SB");
    endfunction

    // N items cost N*(N-1)/2 comparisons. Stores handles, so it needs new items.
    function bit check_dup_slow(pkt_item t);
      check_dup_slow = 1'b0;
      foreach (history_q[i]) begin
        n_cmp++;
        if (history_q[i].id == t.id) check_dup_slow = 1'b1;
      end
      history_q.push_back(t);
    endfunction

    // One lookup per item. Stores the id value, not the handle.
    function bit check_dup_fast(pkt_item t);
      n_cmp++;
      check_dup_fast = id_seen.exists(t.id);
      id_seen[t.id] = 1'b1;
    endfunction

    function void write(pkt_item t);
      bit [7:0] exp_data;
      seen++;
      if (fix_sb ? check_dup_fast(t) : check_dup_slow(t))
        `uvm_error("DUP_ID", $sformatf("id %0d seen twice", t.id))
      exp_data = 8'(t.id * 7 + 3);  // reference model
      if (t.data === exp_data) begin
        matched++;
      end else begin
        mismatched++;
        `uvm_error("MISMATCH", $sformatf("%s, expected data=0x%02h",
                                         t.convert2string(), exp_data))
      end
    endfunction

    function void check_phase(uvm_phase phase);
      super.check_phase(phase);
      if (seen != N_ITEMS)
        `uvm_error("COUNT", $sformatf("expected %0d items, saw %0d", N_ITEMS, seen))
    endfunction

    function void report_phase(uvm_phase phase);
      super.report_phase(phase);
      `uvm_info("SCB_SUMMARY", $sformatf("matches=%0d mismatches=%0d pending=%0d",
                matched, mismatched, (seen < N_ITEMS) ? N_ITEMS - seen : 0), UVM_NONE)
    endfunction
  endclass

  class perf_env extends uvm_env;
    `uvm_component_utils(perf_env)
    pkt_mon mon;
    pkt_sb  sb;
    function new(string name, uvm_component parent);
      super.new(name, parent);
    endfunction
    function void build_phase(uvm_phase phase);
      super.build_phase(phase);
      mon = pkt_mon::type_id::create("mon", this);
      sb  = pkt_sb::type_id::create("sb", this);
    endfunction
    function void connect_phase(uvm_phase phase);
      mon.ap.connect(sb.item_imp);
    endfunction
  endclass

  class perf_test extends uvm_test;
    `uvm_component_utils(perf_test)
    perf_env env;
    virtual stream_if vif;
    function new(string name, uvm_component parent);
      super.new(name, parent);
    endfunction

    function void build_phase(uvm_phase phase);
      super.build_phase(phase);
      // Twenty other blocks of a bigger TB set their own max_id. Every get of
      // max_id scans all 21 entries, whichever one it finally returns.
      for (int i = 0; i < 20; i++)
        uvm_config_db#(int)::set(this, $sformatf("env.blk%0d.*", i), "max_id", 0);
      uvm_config_db#(int)::set(this, "env.mon", "max_id", N_ITEMS - 1);
      if (!uvm_config_db#(virtual stream_if)::get(this, "", "vif", vif))
        `uvm_fatal("NO_VIF", "virtual interface not found")
      env = perf_env::type_id::create("env", this);
    endfunction

    task run_phase(uvm_phase phase);
      raise_counted(phase, this);  // the one objection the run needs
      // Two edges of reset, N_ITEMS packets, and a margin after the last one.
      repeat (N_ITEMS + 4) @(vif.mon_cb);
      phase.drop_objection(this);
    endtask

    function void report_phase(uvm_phase phase);
      super.report_phase(phase);
      `uvm_info("PERF_SUMMARY", $sformatf(
                "items=%0d fmt=%0d cfg_get=%0d raises=%0d cmp=%0d",
                env.sb.seen, n_fmt, n_cfg_get, n_raise, n_cmp), UVM_NONE)
    endfunction
  endclass
endpackage

module tb_top;
  timeunit 1ns; timeprecision 1ps;
  import uvm_pkg::*;
  import perf_pkg::*;

  logic clk;
  logic rst_n;
  stream_if sif (.clk(clk));
  pkt_src #(.N_PKTS(N_ITEMS)) dut (
    .clk(clk), .rst_n(rst_n), .valid(sif.valid), .id(sif.id), .data(sif.data)
  );

  initial clk = 1'b0;
  always #5ns clk = ~clk;

  initial begin
    rst_n = 1'b0;
    #12ns rst_n = 1'b1;  // released between edges, so it cannot race the flops
  end

  initial begin
    uvm_config_db#(virtual stream_if)::set(null, "uvm_test_top*", "vif", sif);
    run_test("perf_test");
  end
endmodule
```

**How to use it.**

1. **Baseline.** Run with no plusargs three times. Record the median CPU time (`user` + `sys`), and the `PERF_SUMMARY` and `SCB_SUMMARY` lines.
2. **Profile** one baseline run with your simulator's profiler (tool-dependent; see its user guide). Attribute the top rows to DUT, TB, UVM library and kernel, and match each counter to the row it explains, as in the profile walkthrough.
3. **Predict** which single fix saves the most CPU time, from the counts alone. (At 2000 items, which counter is largest?)
4. **Add one fix at a time**, in the order your profile and your prediction suggest (the table below shows one possible order). Re-measure each with the same seed and image, three runs each.
5. **Check the results did not change:** `SCB_SUMMARY`, `UVM_ERROR :    0` and the end time must be identical in every row.
6. **Fill in the table** and compute each step's saving as a percentage of the baseline. Label it with the tool, version and host.

## Push Further

### Expert: timing noise and fair comparisons

*Methodology; the numbers involved are tool- and machine-dependent.* On a shared compute farm, the same run can vary from one run to the next because of other jobs on the host, CPU frequency scaling, the file system and memory pressure. Compare **medians** of 3 to 5 runs, and compare on the same host type with the same tool version and compile options. Treat a difference smaller than the spread between repeated runs as no difference. For a change that matters (a UVM library upgrade, a new base class), measure a small fixed set of tests and seeds and keep the history, so the next slowdown is caught on the day it appears. When the wall-clock time of a regression changes but the CPU time does not, the cause is outside the simulation: licences, queue, storage or network.

### Expert: inside an objection raise and drop

IEEE 1800.2-2020 §10.5.1.3.3 and §10.5.1.3.4 require a raise or drop to update the source's counts and to call `raised`/`dropped` for every component up the hierarchy. In uvm-core 2020.3.1 (`src/base/uvm_objection.svh`), `m_raise` and `m_drop` update per-object associative arrays at each level through `m_propagate`. A drop that takes an object's total to zero does not propagate at once: it schedules a context that the static `m_execute_scheduled_forks` task forks into an `m_forked_drain` process, which waits for any drain time, calls `all_dropped`, waits for its callbacks, and only then propagates to the parent. A re-raise during a drain kills that process. So per-item objections cost work at every level plus process creation, all in zero simulated time.

`set_propagate_mode(0)` (§10.5.1.3.2) skips the intermediate levels: a raise or drop updates only the source and the top. It can be changed only while no objection is raised or draining, and it removes the per-level `raised`/`dropped` callbacks that some benches rely on, so it is a niche tool. The real fix is architectural: one objection per test or per top-level sequence. `set_automatic_phase_objection(1)` (§14.2.4.4) does that for a sequence started with a starting phase (§14.2.4.1), with the NOTE that a `forever` body never drops it.

### Expert: what a configuration lookup really costs

`uvm_config_db#(T)::get` (IEEE 1800.2-2020 C.4.2.2.2) in uvm-core 2020.3.1 (`uvm_config_db_implementation.svh`) builds the caller's full path, calls `uvm_resource_pool::lookup_name` (C.2.4.4.1), which walks every resource stored under that field name and, for each one of the requested type, calls `uvm_is_match` (F.3.3.1) on its scope (the type is checked first, so entries of another type cost only that check), then calls `get_highest_precedence` on the matches and `read`s the winner. The cost grows with the number of entries that share the field name, not with the number that match. Wildcard scopes are glob patterns that uvm-core converts to regular expressions for matching, so many wildcard `set` calls make every `get` of that name slower.

Two more uvm-core details (not in the standard): `read` records an audit entry when auditing is on, which is the default; `uvm_resource_options::turn_off_auditing()` switches it off for the whole database, at the price of losing the audit trail that `print_config` and configuration debugging use. And `+UVM_CONFIG_DB_TRACE` prints one line per `set` and `get`. Better than tuning the database is not hitting it in the hot path: cache values in `build_phase`, or pass one configuration object per agent, so the hot path reads class members.

### Expert: field automation versus hand-written methods

The `` `uvm_field_* `` macros implement `do_execute_op` (IEEE 1800.2-2020 B.2.1.1, §5.3.13). Every `copy`, `compare`, `print`, `pack`, `unpack` and `record` then visits each registered field through a policy object (`uvm_copier`, `uvm_comparer` and so on, Clause 16), with a check of the field's flags for that operation. Hand-written `do_copy` and `do_compare` (§5.3.8.2, §5.3.9.2) are not an alternative path that bypasses this: `copy()` and `compare()` always call `do_execute_op` first and then the `do_` hook (§5.3.8.1, §16.6.4.1; uvm-core `uvm_copier.svh` `copy_object`, `uvm_comparer.svh` `compare_object`). They save time only when the macro path no longer does that operation. The standard itself notes that field macros may be less run-time efficient than direct `do_*` implementations (B.2.2, NOTE). The usual staff-level answer is: keep the macros for convenience; for item types a profile shows near the top, typically in high-rate scoreboards, either drop the field macros and hand-write `do_copy`, `do_compare` and `convert2string`, or keep the macros for printing with `UVM_NOCOPY | UVM_NOCOMPARE` on every field and hand-write `do_copy` and `do_compare`. The size of the gain is tool-dependent; claims of a fixed speed-up factor have no source.

### Expert: coverage, constraints and register-model scale

- **Coverage.** `sample()` cost grows with the number of coverpoints and cross bins evaluated. Sample per transaction; use `stop()` and `start()` (IEEE 1800-2023 §19.8, Table 19-5) to disable covergroups a test does not target; avoid crosses whose bins the plan never reviews. Coverage options such as per-instance coverage (`option.per_instance`) also cost memory (tool-dependent).
- **Constraints.** Randomize once per item, and keep constraints the solver can propagate easily. `solve…before` leaves the set of legal value combinations unchanged and changes only their probabilities (§18.5.9); any effect on solver speed is solver-specific, so it is not a performance rule. Most simulators have a constraint profiler (tool-dependent). [I-SV-2B](/curriculum/T2_Intermediate/I-SV-2B_Advanced_Constrained_Randomization/index) covers solver behaviour.
- **Register models.** A large `uvm_reg_block` with built-in coverage models costs build time and memory. `uvm_reg::include_coverage` (IEEE 1800.2-2020 §18.4.7.1) selects which coverage models are built, by scope, before the model is built ([A-UVM-4A](/curriculum/T3_Advanced/A-UVM-4A_RAL_Fundamentals/index)).

### Expert: simulator levers you cannot see in the code

*All tool-dependent: check your simulator's user guide for names and effects.*
- **Debug visibility.** Options that keep every signal and variable visible for waveforms or interactive debug often disable optimizations. Regressions usually build with less visibility than debug builds; profile the build the regression actually uses.
- **Multi-core and partitioned simulation.** Some simulators can spread the design over several cores or machines. That is the tool's parallelism, not something a FIFO in your TB creates, and it pays off mostly for large designs; a TB-bound bench gains little.
- **Waveform dumping.** A simulator's own waveform format is usually faster to write and smaller than VCD (IEEE 1800-2023 §21.7). Scope dumps to the signals you need and start them at the time window of interest.
- **Save and restore.** Many simulators can checkpoint after a long reset or boot sequence and start many tests from it.
- **Emulation.** When even an optimized simulation is too slow, for example running software on a full SoC, the answer is hardware acceleration: [E-EMU-1](/curriculum/T4_Expert/E-EMU-1_Emulation_Aware_Verification/index).

### Kata: guard an expensive debug dump

A monitor for a packet bus computes a byte-by-byte dump of each packet's payload, for debugging, and prints it at `UVM_FULL`:

```systemverilog
// snippet: inside the monitor's run_phase, once per packet
string dump;
dump = payload_hex(pkt);   // loops over up to 4096 payload bytes
`uvm_info("PKT_DUMP", dump, UVM_FULL)
```

1. At regression verbosity (`UVM_LOW`), does `payload_hex` run? Why?
2. Rewrite the snippet so that `payload_hex` runs only when the message will be shown.
3. How would you prove, with a counter rather than a stopwatch, that your change works?

<details className="my-4 rounded-xl border border-border/70 p-3">
<summary className="cursor-pointer font-semibold">Show the worked solution</summary>

1. **Yes, for every packet.** `payload_hex(pkt)` is called in an ordinary assignment statement before the macro; the macro's guard protects only its own message argument. So the expensive loop runs and its result is then filtered.
2. Guard the work with `uvm_report_enabled` (IEEE 1800.2-2020 §6.3.3.2), using the same verbosity, severity and ID as the message:

```systemverilog
// snippet: the dump is built only when PKT_DUMP at UVM_FULL would be shown
if (uvm_report_enabled(UVM_FULL, UVM_INFO, "PKT_DUMP")) begin
  `uvm_info("PKT_DUMP", payload_hex(pkt), UVM_FULL)
end
```

   Passing `payload_hex(pkt)` straight into the macro also works for this one message, because the macro evaluates its message argument only when enabled. The explicit guard is clearer when the debug work is more than one message.
3. Increment a package counter inside `payload_hex`, as the Make It Work bench does in `convert2string`, and print it in `report_phase`. At `UVM_LOW` it must be 0; with `+uvm_set_verbosity=<monitor path>,PKT_DUMP,UVM_FULL,build` it must equal the packet count. The simulated time and the scoreboard summary must be identical in both runs.

</details>

### Debug challenge: the monitor that reuses its item

A colleague "optimizes" the Make It Work monitor: `t` becomes a class member, created once in `build_phase` instead of once per packet, and the local declaration and the `type_id::create` line in `run_phase` are deleted. Run without `+FIX_SB`.

1. Predict the report summary's `UVM_ERROR` count and which ID the errors carry.
2. Explain why. Which line of the scoreboard turns the reuse into errors?
3. With `+FIX_SB` the errors disappear. Does that make the optimization safe?

<details className="my-4 rounded-xl border border-border/70 p-3">
<summary className="cursor-pointer font-semibold">Show the worked solution</summary>

1. `UVM_ERROR : 1999`, all with ID `DUP_ID` (every packet except the first). `SCB_SUMMARY` still shows `matches=2000`, because the data check runs on the current values as soon as each packet arrives.
2. `ap.write(t)` passes the handle, and `history_q.push_back(t)` stores the handle (IEEE 1800-2023 §8.12). All 2000 entries point to the one object, which always holds the newest `id`, so from the second packet on, `history_q[i].id == t.id` is true for every entry.
3. **No.** With `+FIX_SB` the scoreboard stores the `id` *value* in `id_seen`, so this particular check no longer sees the aliasing. But any component that keeps items, such as an analysis FIFO, a scoreboard's expected queue ([A-UVM-6](/curriculum/T3_Advanced/A-UVM-6_Scoreboards_and_Reference_Models/index)) or a coverage collector that samples later, would silently see wrong values. The rule stands: a monitor publishes a new object per transaction. The creation cost is one of the few costs you always pay.

</details>

### Exercise: plan a nightly regression

Illustrative numbers. Your site has 120 simulator licences, a farm queue that gives your team 80 job slots, and machines with enough memory for any number of jobs. The nightly list has 600 tests: 450 take about 10 minutes, 120 about 25 minutes and 30 about 40 minutes.

1. What bounds the number of jobs in flight, and what is it?
2. Estimate the wall-clock time of the regression.
3. In which order should the tests start, and why?
4. The team wants results by 07:00 and the regression starts at 05:00. Name two changes that help without switching off any check.

<details className="my-4 rounded-xl border border-border/70 p-3">
<summary className="cursor-pointer font-semibold">Show the worked solution</summary>

1. Jobs = min(licences, slots, memory) = min(120, 80, no limit) = **80**. The queue, not the licence count, is the limit here; 40 licences sit idle.
2. Total work = 450 × 10 + 120 × 25 + 30 × 40 = 4500 + 3000 + 1200 = 8700 job-minutes. Spread over 80 jobs, that is about 8700 ÷ 80 ≈ 109 minutes, if the jobs are packed well. The longest test (40 minutes) is far shorter than that, so good packing is possible: about **1 hour 50 minutes**, plus compile time and queue waits.
3. **Longest first.** If the 40-minute tests start last, the regression ends with a few jobs running while the rest of the farm is idle. Starting them first lets the short tests fill the gaps.
4. Any two of: ask for more queue slots (up to 120 would use every licence, about 73 minutes); profile the 40-minute tests and fix their hotspots; move rare long seeds to the weekly run, ranking tests by the coverage they add (tool-dependent); make sure waves, recording and debug verbosity are off. Never turn off scoreboards, assertions or plan coverage.

</details>
