## Quick Take

- **What it is:** A repeatable method for turning a red regression into a root cause. You **triage** (find each run's first failure, give it a signature, group runs by signature), **reproduce** one failure exactly, **isolate** it in time, place and stimulus, form a **hypothesis** that predicts something you have not seen yet, **confirm** it with a directed test, and only then fix the bug and **lock in** the fix as a regression check.
- **Why it matters:** A large UVM regression can produce hundreds of failing runs overnight, each with thousands of log lines. Without a method, engineers read the last error, add prints until the failure disappears, and "fix" symptoms. With one, a single root cause is debugged once, every step can be checked by someone else, and the fix comes with proof.
- **The Analogy:** An air-accident investigator. They start from the first thing that went wrong, not the wreckage. They recreate the exact conditions, rule out causes one at a time with tests that could prove them wrong, and only then issue the fix and a new rule so it cannot happen again. *Where it breaks:* a simulation is deterministic, so with the same build and seed you can replay the "accident" as often as you like and stop it at any instant, which no investigator can do. But the replay is exact only while nothing in its recipe changes, and a careless debug edit is a change.

**You will be able to:**
1. **Diagnose** how a UVM run ended and find its first failure, separating it from the errors it caused.
2. **Write** a normalized failure signature, use it to bucket a regression's failures, and **choose** which bucket to debug first.
3. **Plan** an exact reproduction (same test, seed, build, simulator version and plusargs), and **predict** whether a debug edit keeps the seed's stimulus.
4. **Debug** a reproduced failure by isolating it in time, place and stimulus, and write a hypothesis that predicts something you have not yet observed.
5. **Design** a directed test that confirms or refutes the hypothesis, then shrink the failure and lock the fix in as a regression check.

**How to read this lesson.** The core path is the loop picture, the first failure, signatures and buckets, and exact reproduction. The [module overview](/curriculum/T4_Expert/E-DBG-1_Advanced_UVM_Debug_Methodologies/index) owns [verdict honesty](/curriculum/T4_Expert/E-DBG-1_Advanced_UVM_Debug_Methodologies/index#honest-verdicts-what-uvm_error--0-does-and-does-not-prove), report catchers and tracing switches; this page uses them and links back.

A few words in one line each:

- A **regression** is a script that runs many tests, each with many random **seeds**, and marks every run pass or fail from its log.
- A **seed** is the number that starts the simulator's random number generators (RNGs). The same seed with the same build repeats every random value (IEEE 1800-2023 §18.13.1).
- A **build** is one compiled image of the testbench (TB) and the design under test (DUT): the source revision plus every compile option and define.
- A **plusarg** is a run-time command-line option that starts with `+`, such as `+UVM_TESTNAME=<test>`; code reads it without a rebuild (IEEE 1800-2023 §21.6; IEEE 1800.2-2020 Annex G).
- The **driver** turns sequence items into pin activity, the **monitor** turns pin activity back into transactions, and the **scoreboard** compares them with the expected values of a **reference model** ([A-UVM-6](/curriculum/T3_Advanced/A-UVM-6_Scoreboards_and_Reference_Models/index)).
- A UVM **log line** has the form `SEVERITY file(line) @ time: reporter [ID] message`, and the run ends with a **report summary** of counts by severity and by ID ([I-UVM-1D](/curriculum/T2_Intermediate/I-UVM-1D_Reporting_and_Run_Control/index)). The logs on this page omit `file(line)` to keep lines short.

The two mistakes everyone makes at first are skipping step 2 (debugging a run you cannot replay) and jumping from step 3 to step 6 (fixing what you *think* is wrong). One more rule the picture does not draw: if step 2 fails, because the run will not fail again, you go back and check the recipe of the run (Step 2 below), not on to a different seed. The rest of this section takes the steps in order.

### Step 1a: find the first failure

The **first failure** of a run is its earliest `UVM_ERROR` or `UVM_FATAL` in simulation time. In one log file, time never goes backwards, so it is the first such line in the file. Debug it first, because later errors are usually **consequences** of it, a **cascade**: a scoreboard whose expected-data queue slipped by one item reports every following item as wrong, and a stuck handshake ends, much later, in a timeout.

**A worked log.** Read this log of a failing DMA (direct memory access) test, whose agent drives and monitors an AXI bus, and decide which line to debug. Times are in ps. `RVALID` and `RREADY` are the AXI read-data handshake signals; you only need to know that the monitor checks their protocol.

```text
UVM_INFO @ 0: reporter [RNTST] Running test dma_rand_test...
UVM_WARNING @ 1205: uvm_test_top.env.axi_agt.mon [AXI_PROTO] RVALID dropped before RREADY: id=0x3
UVM_ERROR @ 1215: uvm_test_top.env.scb [MISMATCH] read data wrong: exp=0xa5 act=0x00 pkt=9
UVM_ERROR @ 1325: uvm_test_top.env.scb [MISMATCH] read data wrong: exp=0x17 act=0xa5 pkt=10
UVM_ERROR @ 1435: uvm_test_top.env.scb [MISMATCH] read data wrong: exp=0x3e act=0x17 pkt=11
UVM_ERROR @ 52000: uvm_test_top.env.scb [ORPHAN] 3 expected items were never compared
UVM_FATAL @ 1000000: reporter [PH_TIMEOUT] Explicit timeout of 1000000 hit, indicating a probable testbench issue
```

| Time | Line | Role | Why |
|---|---|---|---|
| 1205 | `AXI_PROTO` warning | the **lead** | The monitor saw a protocol violation on the same read, 10 ps before the first error. Not a failure by itself, but read it with the first failure. |
| 1215 | `MISMATCH` pkt 9 | **first failure** | Earliest error. Debug this one. |
| 1325, 1435 | `MISMATCH` pkt 10, 11 | consequence | Each `act` equals the previous `exp`: the scoreboard's queue is one item behind, so these errors repeat the first one. |
| 52000 | `ORPHAN` | consequence | Expected items left over at the end, from the same slip. |
| 1000000 | `PH_TIMEOUT` | consequence | The run never finished. Something stayed blocked after the bad read; [Hang Triage](/curriculum/T4_Expert/E-DBG-1_Advanced_UVM_Debug_Methodologies/hang-lab) teaches that triage. |

So the rule is: start at the first `UVM_ERROR` or `UVM_FATAL`, then read the few lines **before** it for warnings about the same transaction. The summary's `UVM_FATAL :    1` and the timeout are the loudest lines in this log, and the least useful.

**Classify how the run ended** before you debug anything, because the ending decides where you look:

| How the log ends | What it means | First move |
|---|---|---|
| Report summary with `UVM_ERROR` greater than 0, no fatal | The run completed; checks failed | Debug the first error |
| `UVM_FATAL … [PH_TIMEOUT]` | Something kept `run_phase` open until the timeout (Annex F.7.3.3) | First error before it, if any; otherwise hang triage |
| `Quit count reached!` in the summary | The run stopped early at `+UVM_MAX_QUIT_COUNT` (Annex G.2.6) | The last counted error is the Nth error, not the first; read from the top |
| `UVM_FATAL … [BUILDERR]` at end of elaboration | Errors were reported during build, so UVM stopped before simulation (Annex F.7.3.6) | The first build-time `UVM_ERROR`, such as a missing configuration |
| No report summary at all | A crash, a `$fatal`, a simulator error or a killed job (tool-dependent) | The simulator's own messages at the end of the log |
| Summary with no errors, but nothing was checked | A zero-activity run, not a pass | [Verdict honesty](/curriculum/T4_Expert/E-DBG-1_Advanced_UVM_Debug_Methodologies/index#honest-verdicts-what-uvm_error--0-does-and-does-not-prove) on the module overview |

**Pitfalls.** Searching the log for the text "error" finds lines such as `UVM_INFO … error_inject=0` before the real failure; match the severity at the start of the line instead. A long run killed by the regression's wall-clock limit has no summary and looks like a crash; check the job status first.

### Step 1b: failure signatures and buckets

A **failure signature** is the first failure with everything run-specific removed, so that two runs with the same root cause produce the same string. A **bucket** is the set of failing runs that share a signature. You debug one run per bucket, not one per failing test.

Build a signature from the first-failure line:

1. Keep the **severity** and the **ID**. If the ID is the reporter's own full name, replace it with `{PATH}`. uvm-core 2020.3.1 does this for some of its own errors: the sequencer's "Get_next_item called twice" error uses `get_full_name()` as its ID (`uvm_sequencer.svh`).
2. Keep the **reporter path**, but replace array indices: `agt[3]` and `agt[0]` are the same component type with the same bug.
3. In the **message text**, replace hex values with `{H}` and decimal numbers with `{N}`.
4. Drop the time and the `file(line)`.
5. **Reorder** the result as `SEVERITY [ID] path: message`, so that sorted signatures group by ID.

**Traced example.** One raw line, step by step:

| Step | Result |
|---|---|
| Raw | `UVM_ERROR /proj/tb/axi_mon.sv(212) @ 5000: uvm_test_top.env.agt[3].mon [AXI_PROTO] RVALID dropped before RREADY: id='h3` |
| Drop time and file | `UVM_ERROR uvm_test_top.env.agt[3].mon [AXI_PROTO] RVALID dropped before RREADY: id='h3` |
| Normalize indices | `UVM_ERROR uvm_test_top.env.agt[N].mon [AXI_PROTO] …` |
| Normalize values | `UVM_ERROR uvm_test_top.env.agt[N].mon [AXI_PROTO] RVALID dropped before RREADY: id={H}` |
| Reorder | `UVM_ERROR [AXI_PROTO] uvm_test_top.env.agt[N].mon: RVALID dropped before RREADY: id={H}` |

The script below applies these rules to every log of a regression and prints one line per bucket, largest first. It is a sketch for your regression flow; real flows add the test name, seed and build to each entry.

```python
import re
import sys
from collections import defaultdict

# severity, optional file(line), time, reporter path, [ID], message.
# The ID pattern is non-greedy so that an ID such as [env.agt[0].sqr] still matches.
LINE = re.compile(r"^(UVM_ERROR|UVM_FATAL) (?:\S+\(\d+\) )?@ ?\d+: (\S+) \[(.+?)\] (.*)$")

def signature(sev, path, ident, msg):
    if ident == path:                       # some UVM IDs are the reporter's own path
        ident = "{PATH}"
    path = re.sub(r"\[\d+\]", "[N]", path)  # agt[3] and agt[0] are the same bug
    msg = re.sub(r"\b0x[0-9a-fA-F_]+|'h[0-9a-fA-F_]+", "{H}", msg)
    msg = re.sub(r"\b\d+\b", "{N}", msg)
    return f"{sev} [{ident}] {path}: {msg}"

def first_failure(log):
    with open(log) as f:
        for line in f:
            m = LINE.match(line.rstrip("\n"))
            if m:
                return signature(*m.groups())
    return "NO_UVM_ERROR_OR_FATAL"          # judge this run by other evidence

buckets = defaultdict(list)
for log in sys.argv[1:]:
    buckets[first_failure(log)].append(log)
for sig, logs in sorted(buckets.items(), key=lambda kv: -len(kv[1])):
    print(f"{len(logs)}  {sig}  {' '.join(logs)}")
```

The summary line `UVM_ERROR :    3` does not match the pattern, because it has no `@ time:`; only message lines do. Runs with no UVM error still need the checks on the module overview (simulator-format errors, zero activity), which this sketch does not do.

**Choosing which bucket to debug first.** Prefer, in order: a signature that is **new** since the last good regression; the bucket that blocks the most tests; and, within a bucket, the run whose first failure comes **earliest in simulation time**, because it is the cheapest to rerun.

**Pitfalls.**
- *Too fine:* leaving indices, addresses or path-like IDs in the signature splits one bug into many buckets.
- *Too coarse:* keeping only the ID merges different bugs. `MISMATCH` from two scoreboards is two signatures, which is why the reporter path stays in.
- *Bucketing by test name:* one test can hit three bugs, and one bug can fail ten tests. Bucket by signature, then check one run per bucket really is the bug the bucket claims; a signature is a strong hint, not a proof.
- *Messages that put variable data first* (`"0x3c != 0x3d in pkt 17 read data"`) still normalize, but messages that print a variable-length list do not. Write messages with constant text first and `key=value` fields last.

The **reproduction contract**: rerun the same test, the same seed, the **same build**, the same simulator version and the same plusargs. Each part matters:

- **Seed.** IEEE 1800-2023 leaves the default seed implementation-dependent (§18.14.1) and defines no call that returns it, so the regression script must choose the seed, pass it with the simulator's own option, and write it in the log header. [I-SV-2B](/curriculum/T2_Intermediate/I-SV-2B_Advanced_Constrained_Randomization/randomization-methods) lists those options and the seeding rules.
- **Build.** Random values are handed out in the order the code asks for them (§18.14.1), so changed TB code can change which values the failing transaction receives. Keep the failing build (or its revision and compile options) with every failure.
- **Simulator version.** The standard fixes the generator algorithm only for `$random` and the `$dist_*` functions (§20.14, Annex N). For `$urandom`, `randomize()` and the solver it requires only that the same seed gives the same sequence (§18.13.1). A seed is therefore not portable between simulators, and a new version may choose differently (tool-dependent).
- **Plusargs.** A plusarg can change the test, the number of items, a configuration knob or a factory override. Copy the failing command line, do not retype it.

**Misconception: "The same seed reproduces the failure after I rebuild with my changes."** Not necessarily. If the seed passes on your new build, you have learned only that *this build with this seed* passes. The rebuild may have moved the failing stimulus to another transaction, or away entirely. Go back to the archived failing build, confirm it still fails, and add visibility with plusargs on *that* build.

**Debugging the reproduction.** If the archived build with the same seed and command line does *not* fail again, the run is not deterministic. Look for a race between processes (IEEE 1800-2023 §4.7, §4.8; [F3C](/curriculum/T1_Foundational/F3C_Delta_Cycles_and_Race_Conditions/index)), C code called through the DPI that reads the clock or uninitialized memory, input files that changed, or simulator options that differ (tool-dependent). Push Further covers flaky failures at scale.

### Will my debug edit keep the seed?

Once a failure reproduces, you add visibility. Some ways of adding it leave the random streams alone, and some move them. The rules underneath are in IEEE 1800-2023 §18.14 and, for UVM, IEEE 1800.2-2020 §1.4.6, §6.2.2.2 and Annex F.4.1.4.26. [I-SV-2B](/curriculum/T2_Intermediate/I-SV-2B_Advanced_Constrained_Randomization/randomization-methods) teaches the mechanism; here is what it means for debug edits.

Two kinds of random stream matter. Each **process** (a thread such as a component's `run_phase`) has its own generator, and draws such as `$urandom` or `new` take its next value in order (IEEE 1800-2023 §18.14.1, §18.14.2). Each **object** has its own generator too, which `randomize()` uses (§18.14.3), and UVM seeds objects by type and full name (Annex F.4.1.4.26). In uvm-core 2020.3.1, `start_item` reseeds every sequence item from its type, its full name and a per-name count (`uvm_sequence_base.svh`, `set_item_context` in `uvm_sequence_item.svh`, `uvm_create_random_seed` in `uvm_misc.svh`). So an edit in the driver can move the driver's own later draws, such as random idle gaps, but not the field values of the items it receives.

**Predict first.** For each debug edit below, on seed 42, decide whether the stimulus stays the same, then open the answers.

1. Add `+uvm_set_verbosity`, `+uvm_set_action` or `+UVM_MAX_QUIT_COUNT` to the command line (no rebuild).
2. Turn on the simulator's waveform dump (no rebuild).
3. Add `` `uvm_info("DRV", $sformatf("a=%0h", req.a), UVM_HIGH) `` to the driver and rebuild.
4. Add `` `uvm_info("DRV", req.sprint(), UVM_HIGH) `` to the driver, rebuild, and run at `UVM_HIGH`.
5. Add a coverage subscriber component.
6. Add a `$urandom` or `std::randomize()` call, a `new` or a `fork` in the driver's `run_phase`.
7. Rename a sequence, or start an extra item of the same type and name earlier (for example another `create("req")` in the same sequence).

| Debug edit (same seed) | Same stimulus? | Why |
|---|---|---|
| 1. Verbosity, action or quit-count plusargs | yes | No TB code changes. uvm-core 2020.3.1 also saves and restores the random state while it applies the verbosity and action settings (`m_set_cl_msg_args` in `uvm_component.svh`); the quit count is applied by `uvm_root` and only sets a report-server limit |
| 2. Waveform dump | yes | Dumping draws no random values |
| 3. Field-only message | yes | Report messages preserve the random state of the calling thread (IEEE 1800.2-2020 §6.2.2.2), and `$sformatf` draws nothing |
| 4. `sprint()` message | **not guaranteed** | `sprint()` runs user code (`do_print`), which §1.4.6 does not guarantee to be random stable. uvm-core's printer can also create element objects with `new` in the driver's thread (`uvm_printer.svh`), which moves that thread's later draws. Items' field values do not move in uvm-core (reseeded by name), so on a driver with no random draws of its own, such as the one in Make It Work, nothing changes; on a driver with random delays, the timing does |
| 5. Coverage subscriber | yes, for other components | UVM seeds components by type and full name, not by creation order (Annex F.4.1.4.26), and uvm-core reseeds every component's phase processes by name. Only later draws in the *same* `build_phase` call that created it can shift |
| 6. A draw, `new` or `fork` in the driver | **no**, for that driver's draws | Each takes the next value from the thread's generator, so every later draw in that thread moves (§18.14.1, §18.14.2): random delays, `$urandom` choices, objects created after it |
| 7. Renamed sequence, extra item with the same name | **no**, for those items | In uvm-core their seeds come from type, full name and a per-name count (`uvm_misc.svh`), so the rename, or every later item with that name, gets new values |

</details>

The safe habit: **debug with plusargs and waveforms on the unchanged build first.** When you must edit code, keep message arguments free of object creation and random calls, rebuild, and check that the failure still happens at the same transaction (the driver's log line for it should be identical) before trusting anything else.

### Step 3: isolate in time, place and stimulus

**Isolating** means narrowing the failure until only a few candidate causes remain. Narrow three things:

1. **Time.** You know the time of the first failure. Raise visibility only for a window before it: the `time` form of `+uvm_set_verbosity` (Annex G.2.3) raises verbosity from a given time, and `+UVM_MAX_QUIT_COUNT=1` (G.2.6) stops the run at the first counted error, so the log ends at your failure. The time value is in UVM's time unit, which is tool-dependent, so check one run before relying on it. A waveform dump of the same window shows the pins. Start it *before* the failure: `$dumpvars` begins recording only at the end of the time unit in which it is called (IEEE 1800-2023 §21.7.1.3), so a dump started by the error itself cannot show the cause.
2. **Place.** Decide which part of the bench is wrong. In a scoreboard mismatch there are only three suspects: the **TB plumbing** (the driver drove something other than the item, or the monitor recorded something other than the pins), the **reference model** (the scoreboard's expected value is wrong), or the **DUT**. Compare the probes in the picture below.
3. **Stimulus.** Find what is special about the failing transaction: its fields, the transactions just before it, the configuration. Passing transactions in the same log are evidence too.

**Pitfall: isolating by editing.** Commenting out agents or constraints to "see if it still fails" changes the stimulus (previous section). Narrow with plusargs, the time window and the waveform first; change code only to *test* a hypothesis, in a new directed test.

### Step 4: hypothesize; step 5: confirm

A **hypothesis** is a specific claim about the cause that **predicts an observation you have not made yet**. A good one can be proved wrong by one run. "The adder is flaky" and "something is wrong in the scoreboard" predict nothing, so no run can refute them, and they lead to random edits.

| Hypothesis | Testable? | What it predicts |
|---|---|---|
| "The adder is flaky." | no | Nothing specific |
| "Overflow is broken." | weakly | Every item with `a + b > 255` fails; one passing overflow item in the log refutes it |
| "The DUT saturates only above 256, so it fails exactly when `a + b == 256`." | yes | (128, 128) fails; (127, 128) and (128, 129) pass; every past failure has `a + b == 256` |

**Confirming** means running the prediction, ideally in a small **directed test** (a test whose stimulus you choose rather than randomize) that would *fail* if the hypothesis were wrong. Check the prediction against evidence you already have, too: every failure in the bucket should fit it. A hypothesis that survives both is confirmed; one that fails either is refuted, and you go back to isolating. Never skip to a fix on an unconfirmed hypothesis, because a "fix" that makes one seed pass may only have moved the stimulus away from the bug.

### Shrink and lock in

**Shrinking** makes a reproduced failure smaller and faster while it still fails: fewer transactions, fewer active agents, a shorter run. Shrink **from the end**. Cutting transactions *after* the first failure leaves every earlier random draw untouched, so the failing transaction stays the same. Removing transactions *before* it, or disabling an agent that draws random values, changes what later draws produce, so recheck that the same failure still happens after every cut.

**Traced example.** On the Make It Work bench, the failing seed of run 1 fails at item 57 (counting from 0), at 1165 ns. Every item is created with the same name, `req`, so in uvm-core item *k* receives the seed for the *k*-th use of that name.

| Shrink | Items generated | The item that failed (old item 57) | Same failure? |
|---|---|---|---|
| None: the full run | 0 to 199 | the 58th item created: `a=0x9c b=0x64` | yes, at 1165 ns |
| `+NUM_ITEMS=60`: cut after the failure | 0 to 59 | still the 58th item created, so the same seed and the same values | yes, at 1165 ns ([Run 2](/curriculum/T4_Expert/E-DBG-1_Advanced_UVM_Debug_Methodologies/effective-debug#walking-the-loop-on-this-bench) in Make It Work shows the log) |
| First 50 items never generated | old items 50 to 199 | now only the 8th item created, so it receives the seed old item 7 got, and different values | probably not: that item no longer gets `0x9c, 0x64` |

**Locking in** turns the confirmed cause into a check that runs in every regression from now on:

- the directed test from step 5, which fails on the old build and passes on the fixed one;
- a coverage point on the condition, so the random tests show they reach it ([I-SV-3A](/curriculum/T2_Intermediate/I-SV-3A_Functional_Coverage_Fundamentals/index)); or an assertion, when the rule is about signals;
- a rerun of the whole bucket and many new seeds on the fixed build.

A passing rerun of the old seed on the fixed build counts as evidence only if the stimulus did not move: compare its driver lines with the failing run's.

### Debugging the method itself

| Symptom | Likely cause | Fix |
|---|---|---|
| The failing seed passes after your rebuild | The rebuild changed the stimulus | Rerun on the archived failing build; add visibility with plusargs |
| Same build, same seed, same command line, different result | Nondeterminism: a race, DPI code reading the clock or uninitialized memory, a changed input file, different simulator options | Run it twice more to confirm; then hunt the race ([F3C](/curriculum/T1_Foundational/F3C_Delta_Cycles_and_Race_Conditions/index)) or the external input |
| The failure vanishes at `UVM_HIGH` and returns at `UVM_LOW` | A message argument runs code that draws random values or creates objects (`sprint()`) in a thread whose later draws matter, such as a driver with random delays | Use field-only messages, or raise verbosity only for IDs whose messages draw nothing |
| One bug fills ten buckets | Signature too fine: indices, addresses or path IDs not normalized | Add normalization rules |
| One bucket hides two different bugs | Signature too coarse | Keep the reporter path; split by a message field |
| The fix makes the seed pass, then the bug escapes | The hypothesis was never confirmed; the fix moved the stimulus | Confirm with a directed test that failed before the fix |

### In a real regression flow

Nightly regressions run thousands of tests. A triage script records, for every failing run, the first-failure line, the normalized signature, the test, seed, build and full command line. It groups runs into buckets and marks each bucket **new** or **known** against the last good regression. Engineers then take one bucket each, reproduce one run on the archived build, and work the loop. The fix lands together with its directed test, and the bucket stays open until a full regression on the fixed build no longer shows the signature. Teams that skip this end up debugging the same root cause several times under different test names.

### Recap

- The first failure is the earliest `UVM_ERROR` or `UVM_FATAL`; later errors are usually its consequences. Classify the ending before you debug.
- A signature is the first failure with indices, values, times and path-like IDs normalized. Bucket by signature, not by test name.
- Reproduce with the same test, seed, build, simulator version and plusargs. A seed is not a scenario.
- Plusargs and waveforms keep the stimulus; code edits may not. Check that the failing transaction is unchanged after any rebuild.
- Isolate by time, place and stimulus; a hypothesis must predict something new; confirm it with a directed test before you fix.
- Shrink from the end, then lock the fix in with the directed test, coverage and a fresh regression.

## Make It Work

### Worked example: a saturating adder that fails on half the seeds

The DUT is an 8-bit **saturating adder**: `y` is `a + b`, or `0xff` when the sum does not fit in 8 bits. It has a planted bug that makes it fail only for some random values, as real bugs do. The bench is a minimal UVM environment (a real bench would wrap `sqr`, `drv` and `mon` in an agent). It contains the three things this lesson needs: a reproduction line in the log, error messages that normalize well, and a directed test that the factory can swap in.

```systemverilog
// compile
`timescale 1ns/1ps

interface add_if (input logic clk);
  logic       valid = 1'b0;  // qualifies a and b for the monitor
  logic [7:0] a, b;
  logic [7:0] y;             // registered: shows the result one clock later
  clocking cb @(posedge clk);       // driver view
    default input #1step output #1;
    output valid, a, b;
  endclocking
  clocking mon_cb @(posedge clk);   // monitor view: values just before each edge
    default input #1step;
    input valid, a, b, y;
  endclocking
endinterface

// 8-bit saturating adder with a planted boundary bug.
module sat_add (input  logic       clk,
                input  logic [7:0] a, b,
                output logic [7:0] y);
  logic [8:0] sum;
  always_comb sum = a + b;                     // 9-bit context keeps the carry
  always_ff @(posedge clk)
    y <= (sum > 9'd256) ? 8'hFF : sum[7:0];    // BUG: the limit should be 9'd255
endmodule

package add_pkg;
  import uvm_pkg::*;
  `include "uvm_macros.svh"

  class add_item extends uvm_sequence_item;
    `uvm_object_utils(add_item)
    rand bit [7:0] a, b;
    logic    [7:0] y;        // observed result; 4-state so an X shows in the compare
    function new(string name = "add_item");
      super.new(name);
    endfunction
    function string convert2string();
      return $sformatf("a=0x%02h b=0x%02h", a, b);
    endfunction
  endclass

  class add_seq extends uvm_sequence #(add_item);
    `uvm_object_utils(add_seq)
    int unsigned n_items = 200;
    function new(string name = "add_seq");
      super.new(name);
    endfunction
    task body();
      repeat (n_items) begin
        req = add_item::type_id::create("req");
        start_item(req);
        if (!req.randomize()) `uvm_fatal("RAND", "add_item randomize failed")
        finish_item(req);
      end
    endtask
  endclass

  // Directed stimulus that tests the hypothesis "fails exactly when a + b == 256".
  class add_boundary_seq extends add_seq;
    `uvm_object_utils(add_boundary_seq)
    function new(string name = "add_boundary_seq");
      super.new(name);
    endfunction
    task body();
      bit [7:0] a_vals[5] = '{8'd127, 8'd128, 8'd128, 8'd255, 8'd1};
      bit [7:0] b_vals[5] = '{8'd128, 8'd128, 8'd129, 8'd1, 8'd255};
      foreach (a_vals[i]) begin    // sums: 255, 256, 257, 256, 256
        req = add_item::type_id::create("req");
        start_item(req);
        req.a = a_vals[i];
        req.b = b_vals[i];
        finish_item(req);
      end
    endtask
  endclass

  class add_driver extends uvm_driver #(add_item);
    `uvm_component_utils(add_driver)
    virtual add_if vif;
    function new(string name, uvm_component parent);
      super.new(name, parent);
    endfunction
    function void build_phase(uvm_phase phase);
      if (!uvm_config_db#(virtual add_if)::get(this, "", "vif", vif))
        `uvm_fatal("NO_VIF", "add_if not set for the driver")
    endfunction
    task run_phase(uvm_phase phase);
      forever begin
        seq_item_port.get_next_item(req);
        @(vif.cb);
        vif.cb.valid <= 1'b1;
        vif.cb.a     <= req.a;
        vif.cb.b     <= req.b;
        // Probe 1: what was driven. Field-only text, so it draws no random values.
        `uvm_info("DRV", $sformatf("drive %s", req.convert2string()), UVM_HIGH)
        @(vif.cb);
        vif.cb.valid <= 1'b0;      // one item every two clocks keeps the monitor simple
        seq_item_port.item_done();
      end
    endtask
  endclass

  class add_monitor extends uvm_monitor;
    `uvm_component_utils(add_monitor)
    virtual add_if vif;
    uvm_analysis_port #(add_item) ap;
    function new(string name, uvm_component parent);
      super.new(name, parent);
      ap = new("ap", this);
    endfunction
    function void build_phase(uvm_phase phase);
      if (!uvm_config_db#(virtual add_if)::get(this, "", "vif", vif))
        `uvm_fatal("NO_VIF", "add_if not set for the monitor")
    endfunction
    task run_phase(uvm_phase phase);
      add_item t;
      forever begin
        @(vif.mon_cb);
        if (vif.mon_cb.valid === 1'b1) begin
          t = add_item::type_id::create("t");   // a new object per transaction
          t.a = vif.mon_cb.a;
          t.b = vif.mon_cb.b;
          @(vif.mon_cb);                        // y is registered: one edge later
          t.y = vif.mon_cb.y;
          ap.write(t);
        end
      end
    endtask
  endclass

  class add_scb extends uvm_subscriber #(add_item);
    `uvm_component_utils(add_scb)
    int unsigned n_match, n_mismatch;
    function new(string name, uvm_component parent);
      super.new(name, parent);
    endfunction
    function void write(add_item t);
      bit [8:0] sum      = t.a + t.b;            // reference model, from the spec
      bit [7:0] expected = (sum > 9'd255) ? 8'hFF : sum[7:0];
      if (t.y !== expected) begin
        n_mismatch++;
        // Constant text first, key=value fields last: easy to normalize.
        `uvm_error("MISMATCH", $sformatf("sat_add result wrong: exp=0x%02h act=0x%02h %s",
                   expected, t.y, t.convert2string()))
      end
      else begin
        n_match++;
        `uvm_info("CHK", $sformatf("ok %s y=0x%02h", t.convert2string(), t.y), UVM_HIGH)
      end
    endfunction
    function void check_phase(uvm_phase phase);
      if (n_match + n_mismatch == 0)
        `uvm_error("NO_CHECKS", "the scoreboard compared nothing")
    endfunction
    function void report_phase(uvm_phase phase);
      `uvm_info("SCB_SUMMARY",
                $sformatf("matches=%0d mismatches=%0d", n_match, n_mismatch), UVM_LOW)
    endfunction
  endclass

  class add_env extends uvm_env;
    `uvm_component_utils(add_env)
    uvm_sequencer #(add_item) sqr;
    add_driver                drv;
    add_monitor               mon;
    add_scb                   scb;
    function new(string name, uvm_component parent);
      super.new(name, parent);
    endfunction
    function void build_phase(uvm_phase phase);
      sqr = uvm_sequencer#(add_item)::type_id::create("sqr", this);
      drv = add_driver::type_id::create("drv", this);
      mon = add_monitor::type_id::create("mon", this);
      scb = add_scb::type_id::create("scb", this);
    endfunction
    function void connect_phase(uvm_phase phase);
      drv.seq_item_port.connect(sqr.seq_item_export);
      mon.ap.connect(scb.analysis_export);
    endfunction
  endclass

  class add_rand_test extends uvm_test;
    `uvm_component_utils(add_rand_test)
    add_env      env;
    int unsigned n_items;
    function new(string name, uvm_component parent);
      super.new(name, parent);
    endfunction
    function void build_phase(uvm_phase phase);
      env = add_env::type_id::create("env", this);
      // +NUM_ITEMS=<n> shrinks a run without a rebuild (IEEE 1800-2023 §21.6).
      if (!$value$plusargs("NUM_ITEMS=%d", n_items)) n_items = 200;
      // Safety net for hangs. UVM applies this value in uvm_pkg's time unit (see "Run it").
      uvm_root::get().set_timeout(1ms, 1);
    endfunction
    function void start_of_simulation_phase(uvm_phase phase);
      uvm_cmdline_processor clp = uvm_cmdline_processor::get_inst();
      string args[$];
      string cmd;
      clp.get_args(args);
      foreach (args[i]) cmd = {cmd, " ", args[i]};
      // What a rerun needs that the TB can see; the script logs the seed and build.
      `uvm_info("REPRO", $sformatf("test=%s n_items=%0d cmdline:%s",
                get_type_name(), n_items, cmd), UVM_NONE)
    endfunction
    task run_phase(uvm_phase phase);
      add_seq seq;
      phase.raise_objection(this);
      seq = add_seq::type_id::create("seq");
      seq.n_items = n_items;
      seq.start(env.sqr);
      #20ns;   // two clocks: let the monitor deliver the last result
      phase.drop_objection(this);
    endtask
  endclass

  // The lock-in test: same bench, directed stimulus, chosen with +UVM_TESTNAME.
  class add_boundary_test extends add_rand_test;
    `uvm_component_utils(add_boundary_test)
    function new(string name, uvm_component parent);
      super.new(name, parent);
    endfunction
    function void build_phase(uvm_phase phase);
      add_seq::type_id::set_type_override(add_boundary_seq::get_type());
      super.build_phase(phase);
    endfunction
  endclass
endpackage

module tb_top;
  import uvm_pkg::*;
  import add_pkg::*;       // makes sure the test classes are elaborated and registered

  logic clk;
  initial clk = 1'b0;
  always #5ns clk = ~clk;

  add_if  aif (.clk(clk));
  sat_add dut (.clk(clk), .a(aif.a), .b(aif.b), .y(aif.y));

  initial begin
    uvm_config_db#(virtual add_if)::set(null, "uvm_test_top.env.*", "vif", aif);
    run_test("add_rand_test");
  end
endmodule
```

**Run it.** Compile the file with your simulator's UVM library (uvm-core 2020.3.1 or the simulator's built-in UVM, with `+incdir` pointing at `uvm_macros.svh`), with `tb_top` as the top module. Run with `+UVM_TESTNAME=add_rand_test` or `+UVM_TESTNAME=add_boundary_test`, and pass a seed with your simulator's seed option (tool-dependent). The regression script should print that seed and the build revision in the log header. Compile `uvm_pkg` with the same 1 ns time unit as this file (with your simulator's default-timescale option, for example): the standard leaves the time unit of `uvm_pkg` unspecified (IEEE 1800.2-2020 §1.4.5), and UVM applies time values passed to it, such as the `set_timeout(1ms)` argument, and prints `@ time`, in that unit. With a 1 ps unit the timeout would fire at 1 µs, before item 57, and the logs below would print times in ps.

**Why only some seeds fail.** 255 of the 65,536 possible (a, b) pairs sum to exactly 256. With uniform random values, each item has about a 0.39% chance to hit one, so a 200-item run fails on roughly 54% of seeds (1 − (65281/65536)²⁰⁰ ≈ 0.54). A regression of this test is red about half the time, with different item numbers each time.

### How to debug a regression failure, step by step

1. **Classify each failing run's ending** (completed with errors, timeout, quit count, build error, no summary, zero activity).
2. **Extract the first failure** of each run and **normalize** it into a signature.
3. **Bucket** by signature; mark buckets new or known; pick one bucket and, inside it, the run that fails earliest.
4. **Reproduce** that run on its archived build with its exact command line, and see it fail.
5. **Shrink from the end** (`+NUM_ITEMS`, a shorter test) and recheck that the same transaction still fails.
6. **Isolate** with plusargs: one component and one ID at a time, `+UVM_MAX_QUIT_COUNT=1`, a time window, a waveform of that window. Split TB plumbing, model and DUT with the probes.
7. **Write a hypothesis** that predicts an observation you have not made, and check it against every failure in the bucket.
8. **Confirm** with a directed test that fails if the hypothesis is right and the bug is present.
9. **Fix**, then **lock in**: the directed test joins the regression, add coverage or an assertion, rerun the bucket and many new seeds.
10. **Write it down**: signature, root cause, fix and test, so the next person who sees the signature starts at the answer.

**Checklist before moving on:**
- [ ] I can find the first failure in a log with a cascade and a timeout, and say why the timeout is not it.
- [ ] I can turn a first-failure line into a normalized signature, including a path-like ID.
- [ ] I can list the five parts of a reproduction, and explain why a passing seed on a new build proves little.
- [ ] I can say which debug edits keep a seed's stimulus and which may move it.
- [ ] I can split a scoreboard mismatch into TB plumbing, model or DUT with the four probes.

## Push Further

### Expert: what UVM promises about random stability, and what it does not

IEEE 1800.2-2020 §1.4.6 is short: "Any APIs that result in user code being executed are not guaranteed to be random stable. All other APIs are guaranteed to be random stable, unless otherwise specified." The consequences for debugging:

- **Stable by the standard.** Report messages: `new_report_message` "will preserve the random stability of the calling thread" (§6.2.2.2), and the macros build messages with it. Name-based seeding: with UVM seeding enabled (the default), "UVM-based objects are seeded based on their type and full hierarchical name rather than allocation order" (Annex F.4.1.4.26; `reseed`, §5.3.3.3).
- **Not guaranteed, because user code runs.** `print()` and `sprint()` (they call your `do_print`), `convert2string`, `copy` and `compare` hooks, report catchers' `catch()` and callbacks. If yours create objects or draw random values, enabling them shifts streams.
- **What uvm-core 2020.3.1 adds (implementation, not standard):** `uvm_component::new` calls `reseed()`; before every phase callback, each component's phase process is reseeded from the phase type and the component's full name (`uvm_topdown_phase.svh`, `uvm_bottomup_phase.svh`, `uvm_task_phase.svh`); sequences and items are reseeded in `set_item_context` (`uvm_sequence_item.svh`); resource lookups, transaction recording and command-line message settings save and restore the caller's random state (`uvm_resource_pool.svh`, `uvm_recorder.svh`, `uvm_component.svh`). The damage of one extra `new` is therefore limited to later draws in the same component's same phase call.
- **The seeds still follow the simulator seed.** uvm-core hashes the names with `uvm_global_random_seed`, which the package initializes with `$urandom`, so a different simulator seed gives different UVM streams (`uvm_misc.svh`).

Staff-level angle: if a team must add instrumentation to a long-lived regression without invalidating its stored seeds, every debug hook must be stream-neutral: field-only messages, and no `new`, `fork` or random call in a TB thread. Self-seeding a new debug object in its constructor (IEEE 1800-2023 §18.14.3) protects only that object's own stream; its `new` still takes a draw from the creating thread. Verify by diffing the driver logs of one seed before and after the change.

### Expert: comparing runs: two seeds, two builds and bisecting

- **Two seeds, one build.** Different seeds produce different stimulus from the first random draw, so there is no meaningful "first divergence" between a passing and a failing seed. What the comparison *can* show is correlation: which stimulus features every failing seed has and no passing seed has (here, a sum of exactly 256). Coverage from both sets answers that faster than log diffs.
- **One seed, two builds.** When a failure appears after a code change, run the same seed on the last good build and the first bad one. If the change did not alter the TB's random draws or their order (for example an RTL-only change in a TB whose draws do not depend on DUT responses), the stimulus is identical and the first differing *monitor* transaction is where behaviour diverged. Diff the *driver* streams first: if they already differ from item 0, the stimulus moved, and the comparison means nothing. This follows from the ordering rule in IEEE 1800-2023 §18.14.1; reactive TBs, whose draws depend on DUT timing, can shift even on RTL-only changes.
- **Bisecting revisions.** Once a *directed* test reproduces the bug, its stimulus does not depend on the seed, so you can search the revision history for the commit that introduced it, for example with `git bisect run` and a script that runs the test (tool-dependent: your version-control system and simulator).

### Expert: triage at scale: new, known and flaky failures

Methodology; the tooling is tool-dependent.

- **New versus known.** Keep a database of signatures with their bug IDs. A regression report then shows new signatures first. A known signature with a sudden jump in count is also news: a fix may have regressed.
- **Flaky failures.** Rerun each new signature once on the same build, seed and command line. A run that does not repeat is nondeterministic, and that is a bug in itself: a race (IEEE 1800-2023 §4.7, §4.8), DPI code that reads the clock or uninitialized memory, or an input that changed. Never mark it "flaky" and move on; a nondeterministic bench cannot reproduce the next real bug either.
- **Expected failures and waivers.** While an RTL fix is pending, a team may waive one known signature. The waiver must be narrow (severity, ID, path and message pattern), counted, tied to a bug ID and removed with the fix; a report catcher that demotes every `MISMATCH` is not a waiver, it is a blindfold. The module overview shows the narrow, counted catcher.
- **Budgets.** At thousands of runs, triage cost matters more than simulation cost: record the signature, seed, build and command line automatically; cap reruns per signature; and prefer one deep debug of the earliest-failing run per bucket over shallow looks at many.

```bash
<sim> +UVM_TESTNAME=dma_rand_test <seed option> 1001 +UVM_MAX_QUIT_COUNT=1 \
  +uvm_set_verbosity=uvm_test_top.env.scb,_ALL_,UVM_HIGH,build
```

### Kata 2 (hypothesis): predict, then confirm

Use the Make It Work bench, on the buggy build.

1. Before running anything, predict which of these pairs fail: (0x00, 0xff), (0x80, 0x80), (0x40, 0xc0), (0x81, 0x80), (0xff, 0xff).
2. Write the `a_vals` and `b_vals` arrays of a directed sequence that tests your prediction, and give the expected `SCB_SUMMARY` line.
3. A colleague "fixes" the DUT by deleting `sum` and writing `y <= (a + b > 8'd255) ? 8'hFF : a + b;`. Predict what `add_boundary_test` reports now, and why.

<details className="my-4 rounded-xl border border-border/70 p-3">
<summary className="cursor-pointer font-semibold">Show the worked solution</summary>

1. Sums: 0x00 + 0xff = 255 (pass), 0x80 + 0x80 = 256 (**fail**), 0x40 + 0xc0 = 256 (**fail**), 0x81 + 0x80 = 257 (pass), 0xff + 0xff = 510 (pass, saturates). Two failures.
2. `a_vals = '{8'h00, 8'h80, 8'h40, 8'h81, 8'hff}` and `b_vals = '{8'hff, 8'h80, 8'hc0, 8'h80, 8'hff}`, with two `MISMATCH` errors and `SCB_SUMMARY matches=3 mismatches=2`. If you see a different count, the hypothesis is refuted: go back to isolating.
3. Every overflowing pair now fails. In `a + b > 8'd255` both operands of `>` are 8 bits wide, so `a + b` is evaluated in 8 bits and the carry is lost (IEEE 1800-2023 §11.6.1); the comparison is never true and nothing saturates. The boundary test reports four mismatches out of five (only the sum of 255 passes): the directed test caught a bad fix, which is exactly what locking in is for.

</details>
