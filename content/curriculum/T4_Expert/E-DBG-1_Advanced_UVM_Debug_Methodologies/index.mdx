## Quick Take
- **What it is:** A debugging playbook — report control (verbosity, actions, report catchers), tracing switches, transaction recording, selective waveforms and reproducible seeds — to tame large UVM environments.
- **Why it matters:** Scale brings opaque failures. Long SoC simulations or massive block-level regressions require rich, automated debug hooks to keep the signal-to-noise ratio high under tight schedules.
- **The rule that bites:** a test's pass/fail verdict is only as honest as its report configuration. A catcher that swallows every error, or `UVM_NO_ACTION` on errors, turns a failing run into a passing one — and `$error` from an assertion never reaches the UVM report server at all.
- **The Analogy:** Think of an airliner flight recorder: every test run should leave breadcrumbs that explain what the bench did and why, *before* you ever open a waveform viewer.

> **Signal:** When triage meetings begin with “rerun with more logs,” your methodology needs stronger built-in instrumentation.

## Build Your Mental Model

### 1. Structured Logging
Standard `uvm_info` is often treated as a dumping ground. Professional environments treat logs as machine-readable telemetry.
- **Standardize IDs:** Use consistent IDs (`ENV`, `DRV`, `SEQ`, `SCB`, `CFG`). Actions, verbosity and catchers all select messages by ID.
- **Correlation IDs:** Stamp sequence IDs, transaction handles, and timestamps into every message so logs join up clearly with coverage holes and scoreboard discrepancies.
- **Two separate knobs:** **verbosity** decides whether a `UVM_INFO` is issued at all (warnings, errors and fatals are never filtered by verbosity); the **action** decides what an issued message does — display, log to a file, count toward the quit limit, exit.
- **Change them without recompiling:** `+UVM_VERBOSITY=UVM_HIGH` sets every component; `+uvm_set_verbosity=<comp>,<id>,<verbosity>,<phase>` targets one; `+uvm_set_action=<comp>,<id>,<severity>,<action>` and `+uvm_set_severity=<comp>,<id>,<old>,<new>` change actions and severities. The procedural equivalents (`set_report_id_action_hier()`, `set_report_severity_override()`, …) need a code change in the test.

### 2. The Report Pipeline
Every `` `uvm_error `` travels the same path: the component's verbosity filter (`UVM_INFO` only), its report handler (severity overrides, then the action lookup: severity+ID beats ID beats severity), the **report catchers**, and finally the report server, which counts every message it executes, prints it, and exits on `UVM_EXIT` or when `+UVM_MAX_QUIT_COUNT` is reached.

### 3. Beyond Reports: a Debug Event Bus
Some teams also broadcast significant events (`reset_done`, `scb_mismatch`, `watchdog`) on an analysis port or `uvm_event_pool` channel that a dedicated debug component subscribes to. That component can start a waveform dump, add trace metadata, or stop the run, without rewiring drivers or monitors. It complements, not replaces, the report pipeline: errors still go through `` `uvm_error `` so they are counted.

### 4. Selective Waveform Capture
Indiscriminately dumping waveforms for a 20-hour SoC regression is impossible. You must gate waveform dumping behind triggers.
- **Trigger-Driven Dumps:** Use a report catcher (it sees every message) or the debug component to react to errors or watchdog timeouts, and *then* fire vendor-specific waveform APIs (e.g., `$fsdbDumpvarsByFile`).
- **Ring Buffers:** Keep the last N microseconds of history in memory and flush to disk only when a trigger fires, capturing the lead-up to the failure without the terabytes of idle traffic.
- **Transaction recording:** enable recording on the agents you care about (see [I-UVM-6](/curriculum/T2_Intermediate/I-UVM-6_UVM_Recording_Classes/index)) so the viewer shows transactions next to the signals.

### 5. Trace Metadata Pipeline
- Emit JSON or NDJSON trace files mapping the test name to key lifecycle events (e.g., reset done, handshake stalled, scoreboard mismatch).
- Post-process these traces into dashboards so regression reports show high-level failure breadcrumbs before anyone opens a log file.

## Make It Work

### Write a narrow report catcher

```systemverilog
class crc_demoter extends uvm_report_catcher;
  `uvm_object_utils(crc_demoter)
  int unsigned demoted;

  function new(string name = "crc_demoter");
    super.new(name);
  endfunction

  virtual function action_e catch();
    if (get_severity() == UVM_ERROR && get_id() == "CRC" &&
        uvm_is_match("*bad CRC*", get_message())) begin
      set_severity(UVM_INFO);   // INFO's default action: display, no count
      demoted++;
    end
    return THROW;               // CAUGHT would hide the message entirely
  endfunction
endclass

class crc_inject_test extends base_test;
  `uvm_component_utils(crc_inject_test)
  crc_demoter demoter;

  function new(string name, uvm_component parent);
    super.new(name, parent);
  endfunction

  function void build_phase(uvm_phase phase);
    super.build_phase(phase);
    demoter = crc_demoter::type_id::create("demoter");
    uvm_report_cb::add(null, demoter);   // null: attach to every report object
  endfunction

  function void report_phase(uvm_phase phase);
    if (demoter.demoted != 2)
      `uvm_error("TEST", $sformatf("expected 2 injected CRC errors, saw %0d", demoter.demoted))
  endfunction
endclass
```

The last check matters: if the injection stops working, a catcher alone would quietly pass the test.

### Debug switches to know by heart

| Switch | What it does |
| --- | --- |
| `+UVM_TESTNAME=<test>` | Selects the test run by `run_test()` |
| `+UVM_VERBOSITY=<level>` | Sets the verbosity of every component |
| `+uvm_set_verbosity=<comp>,<id>,<level>,<phase>` | Verbosity for matching components and IDs (`_ALL_` for every ID) |
| `+uvm_set_action=<comp>,<id>,<severity>,<action>` | Action for matching messages, e.g. `UVM_DISPLAY\|UVM_LOG` |
| `+uvm_set_severity=<comp>,<id>,<old>,<new>` | Severity override for matching messages |
| `+UVM_MAX_QUIT_COUNT=<n>,<YES\|NO>` | Exit after `n` counted errors (default 0: never) |
| `+UVM_TIMEOUT=<time>,<YES\|NO>` | Run-phase timeout; expiry is the `PH_TIMEOUT` fatal |
| `+UVM_OBJECTION_TRACE` | Logs every raise and drop (`OBJTN_TRC`) |
| `+UVM_PHASE_TRACE` | Logs phase transitions |
| `+UVM_CONFIG_DB_TRACE` | Logs every `config_db` set and get |

From code: `uvm_top.print_topology()` prints the component tree, `uvm_factory::get().print()` lists overrides, and `check_config_usage()` reports configuration that was set but never read.

### Reproduce with the same seed

1. Every regression run gets an explicit seed on the simulator command line (the option is tool-specific, for example `+ntb_random_seed=<n>`, `-sv_seed <n>` or `-svseed <n>`), and the regression script prints that seed in the log header.
2. A failure is reproduced by rerunning **the same test, seed and code**. Prefer command-line visibility (`+uvm_set_verbosity`, traces, dumps) over code edits.
3. Random stability (IEEE 1800-2023 §18.14) keeps each thread's and object's random sequence independent of the others, but it is not magic: a new thread or a new object created with `new` takes the next value from its parent thread's generator (§18.14.1). Adding or reordering threads, objects or `randomize()` calls — even extra report messages, which UVM builds as objects — can change what a seed produces. After adding visibility, confirm the failure still reproduces.

## Push Further: Triage Playbook

When an overnight regression turns red, follow this playbook rather than randomly adding displays:

1. **Classify the ending:** a `UVM_ERROR`/`UVM_FATAL` count, a `PH_TIMEOUT` fatal (a hang — see the [Hang Lab](/curriculum/T4_Expert/E-DBG-1_Advanced_UVM_Debug_Methodologies/hang-lab)), or a suspiciously short run (no objection raised).
2. **Bucket by signature:** group failures by the first error's ID and message pattern, not by test name, so one root cause is debugged once.
3. **Reproduce exactly:** rerun one failure with the same test and seed, then add verbosity for the IDs involved with `+uvm_set_verbosity`, and `+UVM_OBJECTION_TRACE` for hangs.
4. **Open targeted waveforms:** use the triggered dump or transaction recording for the window around the first error, rather than the full-run database.
5. **Shrink:** once it reproduces, trim the test duration or bypass unrelated subsystems until it fails in under a minute.
