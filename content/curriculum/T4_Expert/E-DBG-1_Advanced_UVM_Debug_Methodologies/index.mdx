## Quick Take

- **What it is:** a method for debugging large UVM environments without guessing. It has five parts: checking that a run's **verdict** (its pass or fail result) is honest; **report catchers**, small callback objects that can inspect and change UVM messages; **traces and prints** that UVM can switch on from the command line; a **debug event bus** that broadcasts significant events to debug components; and a **regression flow** that keeps every failure reproducible. A **regression** is a script that runs many tests, each with many random seeds, and marks each run pass or fail.
- **Why it matters:** at scale, the expensive failures are not the ones that crash. They are the green regression that hid a bug, the failing run nobody can reproduce, and the 20-hour simulation whose waveform starts one microsecond too late. Each of these has a specific, teachable cause, and each has a fix you build into the testbench (TB) before you need it.
- **The rule that bites:** a verdict is only as honest as its report configuration. A catcher that swallows every error, or `UVM_NO_ACTION` on errors, turns a failing run into a passing one; an assertion that fails with `$error` never reaches UVM's counts at all; and a run that checked nothing reports zero errors.
- **The Analogy:** an airliner's flight recorder and the investigators who read it. Every run should leave enough evidence to explain what the bench did, *before* anyone opens a waveform viewer. *Where it breaks:* a flight recorder is passive and records everything, all the time. UVM's debug hooks are selective: you choose what to record, a recording started *after* an event holds nothing about its cause, and some hooks (catchers and actions) can change the verdict itself, which no flight recorder can do.

**You will be able to:**
1. **Decide** whether a UVM run's verdict is honest (actions, catchers, `$error` and assertion control outside UVM, zero-activity runs) and **write** the regression gate that enforces it.
2. **Write** a narrow `uvm_report_catcher` that demotes only expected errors (THROW vs CAUGHT), counts them and fails the test when the count is wrong, and **control** verbosity, actions, severities and the quit count from the command line.
3. **Choose** the trace or print (configuration database, factory, topology, objection, phase, heartbeat) that answers a given debug question, and **read** its output.
4. **Design** a debug event bus, and **plan** a selective waveform window and transaction recording for a long run.
5. **Plan** a regression flow that keeps every failure reproducible and groupable: what each run must log, the gate, and the triage loop that follows a red result.

## Build Your Mental Model

**How to read this page.** The core path is the first two sections: honest verdicts and report catchers. Practitioner depth follows: command-line control, choosing a trace, the debug event bus, selective waveforms and recording, and the regression loop. Push Further holds the expert corner cases.

Words this page uses, each in one line:

- The **design under test (DUT)** is the RTL the TB checks; a **scoreboard** or checker compares what the DUT did with what it should have done ([A-UVM-6](/curriculum/T3_Advanced/A-UVM-6_Scoreboards_and_Reference_Models/index)).
- A **report** is one UVM message: a severity (`UVM_INFO`, `UVM_WARNING`, `UVM_ERROR`, `UVM_FATAL`), an ID such as `"CRC"`, and text. Every component is a **report object**; each has a **report handler** holding its settings; one **report server** counts every report and prints the **report summary** at the end ([I-UVM-1D](/curriculum/T2_Intermediate/I-UVM-1D_Reporting_and_Run_Control/index)).
- An **action** says what the server does with a report: display it, log it, count it toward the quit limit, exit, or nothing (`UVM_NO_ACTION`). **Verbosity** only decides whether a `UVM_INFO` is issued.
- A **plusarg** is a simulator command-line option that starts with `+`, such as `+UVM_TESTNAME=crc_inject_test`.
- An **objection** keeps a phase such as `run_phase` open; a **phase** is one named step of a UVM run ([I-UVM-1C](/curriculum/T2_Intermediate/I-UVM-1C_UVM_Phasing/index)).
- A **seed** is the number that starts the simulator's random number generators; the same seed on the same build gives the same random stimulus ([I-SV-2B](/curriculum/T2_Intermediate/I-SV-2B_Advanced_Constrained_Randomization/randomization-methods)).
- A **waveform dump** is a file of signal value changes that a viewer draws; **VCD** (value change dump) is the format the SystemVerilog standard defines (IEEE 1800-2023 §21.7). **Transaction recording** stores whole transactions in a database the viewer shows beside the signals ([I-UVM-6](/curriculum/T2_Intermediate/I-UVM-6_UVM_Recording_Classes/index)).
- An **analysis port** broadcasts an object to every connected **subscriber** by calling its `write()` function ([I-UVM-2B](/curriculum/T2_Intermediate/I-UVM-2B_TLM_Connections/index)).
- **CI** (continuous integration) is the automation that runs a regression on every code change and blocks the change if the regression fails.

### Honest verdicts: what `UVM_ERROR : 0` does and does not prove

A UVM run's **verdict** comes from the report summary: it passes when the summary is present, `UVM_ERROR :    0` and `UVM_FATAL :    0`, a checker proves it compared something, and the log has no simulator-format errors ([I-UVM-1D](/curriculum/T2_Intermediate/I-UVM-1D_Reporting_and_Run_Control/index) teaches this four-condition rule). The counts come from `get_severity_count` on the report server (IEEE 1800.2-2020 §6.5.1.2.6). At the scale of a regression, the question is no longer "did this run pass?" but "**can I trust that it passed?**"

Four mechanisms make a verdict lie. Learn them as a checklist:

| # | How the verdict lies | What happens | Where the evidence is |
|---|---|---|---|
| 1 | **Errors removed before counting** | A catcher returns CAUGHT, or an action is `UVM_NO_ACTION`. The server ends processing before it counts (§6.5.1.2.14 steps a and b). With the macros it is worse: `` `uvm_error `` checks the action *before building the message*, so a `UVM_NO_ACTION` error is never even created and no catcher or audit can see it (uvm-core 2020.3.1 `uvm_message_defines.svh`, `` `uvm_report_begin ``). | The run's command line (`UVM_NO_ACTION`), the catcher summary (`Number of caught UVM_ERROR reports`) |
| 2 | **Failures UVM never saw** | `$error` is a SystemVerilog severity task: the simulator prints it, UVM never counts it (IEEE 1800-2023 §20.10). A failing assertion with no `else` clause calls `$error`. `$assertoff` or `$assertcontrol` (§20.11) can switch assertions off entirely. | Simulator-format error lines (their format is tool-dependent), assertion-control calls in the test |
| 3 | **Zero activity** | Nothing raised an objection, so `run_phase` ended at once; or a sequence never started; or the monitor was not connected. Nothing was compared, so nothing could fail. | `+UVM_PHASE_TRACE` prints `No objections raised, skipping phase` (uvm-core); the scoreboard's count line says `0 compares` |
| 4 | **An early end hides the real failure** | A fatal, a reached quit count or a timeout ends the run through `die()` before later phases run. The run fails, but the first visible failure may not be the root cause, and `check_phase` checks never ran. | `Quit count reached!` in the summary; a `PH_TIMEOUT` fatal |

Mechanisms 1 to 3 produce false passes. Mechanism 4 produces a true fail with a misleading signature. A **signature** is the short, normalized text that identifies a failure (its severity, ID and message with numbers stripped), used to group failures.

In [I-UVM-1D](/curriculum/T2_Intermediate/I-UVM-1D_Reporting_and_Run_Control/index) you left the catcher knob at `none`. 1. **Demote the injected CRC errors.**
2. **Catch every error.**

**Debrief.**
1. **One error, and the verdict is honest.** The two `CRC` errors are demoted to `UVM_INFO` and still printed, so they are counted as information. The real `SCB` mismatch is counted, and the run fails for the right reason. The `$error` is still invisible to UVM, so the gate must scan for it.
2. **Zero errors, and the verdict is a lie.** The catcher returns CAUGHT for every `UVM_ERROR`, including the real bug. The catcher summary would show `Number of caught UVM_ERROR reports   :    3`, which is the evidence a gate can check.
3. **Zero errors, and the verdict is a lie.** The errors are dropped before counting and, because the macros check the action first, never even built. Nothing in the summary shows it; only the command line does.

**Read the generated code for the Demote preset.** It attaches the catcher to the one component that reports the injected errors, `uvm_report_cb::add(env.agt.mon, catcher)`, in `connect_phase`, and the catcher counts its demotions so that `check_phase` can fail the test when the count is not the expected 2. **The gate that enforces it.** A regression script, not a human, decides each run's verdict, so honesty must be written into the script. A good **CI gate** fails a run when any of these hold:

1. The `--- UVM Report Summary ---` block is missing (crash, kill or `$fatal`).
2. `UVM_ERROR` or `UVM_FATAL` is above 0 (read with anchored patterns such as `^UVM_ERROR :\s+(\d+)$`).
3. A checker's count line is missing or zero (`SCB_SUMMARY: 0 compares`).
4. The log contains simulator-format error lines (tool-dependent patterns).
5. The catcher summary shows caught or demoted errors and the test is not on a reviewed list of error-injection tests that check their own counts.
6. The run's command line contains `UVM_NO_ACTION` for errors, or the log contains an `INVLCMDARGS` warning (a plusarg that never took effect).

**Debugging the gate itself.** Symptom: the simulator printed `Error:` lines, yet the summary says `UVM_ERROR :    0` and the run was marked green. Cause: the gate checked only the summary (mechanism 2). Fix: add rule 4, and route assertion failures into UVM with `` `uvm_error `` in their fail action ([I-UVM-1D](/curriculum/T2_Intermediate/I-UVM-1D_Reporting_and_Run_Control/index) shows how).

### Report catchers: narrow, counted, audited

A **report catcher** is an object of a class derived from `uvm_report_catcher` (§6.6). It is a **callback**, an object whose method a UVM class calls at a fixed point in its own code (§10.7): you register it with `uvm_report_cb::add(obj, catcher)` (`uvm_report_cb` is the callbacks type for report objects, Annex D.4.3), and the report server calls its `catch()` method for every report from that object.

**Purpose.** Some tests *must* produce errors: an error-injection test corrupts a CRC on purpose and expects the monitor to complain. Without a catcher those expected errors fail the test; with a careless catcher, real errors pass. A good catcher **demotes** only the errors the test injected, keeps them visible, and **counts** them so the test can fail if the count is wrong.

**Mechanism** (§6.6, §6.5.1.2.14):
- `catch()` runs inside the server, after the report handler has applied any severity override (`+uvm_set_severity`) and chosen the action. A catcher therefore sees the *overridden* severity.
- Catchers run in registration order. A catcher registered with `add(null, c)` is **type-wide**: it sees reports from every report object. One registered with `add(obj, c)` sees only that object's reports (§10.7.2.3.1).
- Inside `catch()`, the `get_*` methods read the current report (§6.6.3): `get_severity`, `get_id`, `get_message`, `get_verbosity`, `get_action`, `get_client` (the report object). The protected `set_*` methods change it, and later catchers see the change (§6.6.4): `set_severity`, `set_id`, `set_message`, `set_verbosity`, `set_action`, `set_context`.
- `catch()` returns **THROW**, which passes the (possibly changed) report on to the next catcher and then to the server, or **CAUGHT**, which ends processing at once: no later catcher runs, and the report is neither printed nor counted (§6.6.5, §6.5.1.2.14 a).
- The catcher class keeps counts of demoted and caught warnings, errors and fatals, and the server prints them before the report summary (§6.6 overview).

Now follow one injected error through a catcher. **Predict first:** if `crc_demoter` calls `set_severity(UVM_INFO)` but not `set_action()`, will the demoted report still be counted toward the quit limit?

**Debrief.** No. In uvm-core 2020.3.1, when a catcher changes the severity without calling `set_action()`, and the action was still the old severity's default, the server switches it to the new severity's default action (`uvm_report_catcher.svh`, `process_all_report_catchers`). `UVM_INFO`'s default is `UVM_DISPLAY`, so the demoted report is printed and counted under `UVM_INFO`, and it no longer feeds the quit counter. Call `set_action()` yourself if you want something else.

**Pitfalls, and why each is wrong:**
- **The catch-all.** `if (get_severity() == UVM_ERROR) return CAUGHT;` hides every error, the real bug included. A catcher must match severity *and* ID *and* message.
- **Demoting without counting.** If the injection stops working (a refactored sequence no longer corrupts the CRC), a catcher alone lets the test pass while it tests nothing. Count demotions and check the count in `check_phase`.
- **Registering too early.** Build is top-down (§9.8.1.1): in the test's `build_phase`, `env.chk` does not exist yet. `uvm_report_cb::add(env.chk, demoter)` then passes `null`, and the catcher silently becomes type-wide. Register on a specific component in `connect_phase` or later.
- **Attaching to the wrong object.** A sequence reports through its sequencer (§14.1.3), so a catcher for a sequence's errors must be attached to the sequencer, not the driver.
- **Returning neither THROW nor CAUGHT.** uvm-core reports `RPTCTHR` ("must return THROW or CAUGHT").

**Real testbench use.** Error-injection tests (see [A-UVM-9](/curriculum/T3_Advanced/A-UVM-9_Reset_and_Error_Injection/index)), and temporary waivers for a known, filed DUT bug, each with an owner and an expiry. Not for silencing noisy warnings: fix their source, or demote one ID with `+uvm_set_severity`.

### Command-line control: the debug subset

[I-UVM-1D](/curriculum/T2_Intermediate/I-UVM-1D_Reporting_and_Run_Control/index) teaches every reporting plusarg. These are the forms you will reach for while debugging (Annex G.2):

| Need | Plusarg | Note |
|---|---|---|
| More detail from one component and ID | `+uvm_set_verbosity=uvm_test_top.env.scb,SCB,UVM_HIGH,build` | G.2.3; `_ALL_` for every ID; IDs cannot use wildcards |
| More detail only near a known failure time | `+uvm_set_verbosity=uvm_test_top.env.*,_ALL_,UVM_FULL,time,3000` | G.2.3 `time` form; uvm-core waits that many units of `uvm_pkg`'s time unit, which is tool-dependent |
| Pause at the first mismatch, interactively | `'+uvm_set_action=uvm_test_top.env.scb,SCB,UVM_ERROR,UVM_DISPLAY\|UVM_COUNT\|UVM_STOP'` | G.2.4; quote it, because `\|` is a shell pipe |
| Demote one reviewed warning | `+uvm_set_severity=uvm_test_top.env.agt.drv,CFG,UVM_WARNING,UVM_INFO` | G.2.5; one ID, never a whole severity |
| Stop at the first error | `+UVM_MAX_QUIT_COUNT=1` | G.2.6; the log then ends at the first failure |

If a plusarg seems to do nothing, search the log for `INVLCMDARGS` (uvm-core): the component pattern matched nothing, or the setting was malformed. Code that calls `set_report_*` after construction also replaces a command-line setting.

### Choosing the right trace

UVM can explain itself, but each trace answers one question. Pick by the question, not by habit, and know whether the tool is in the standard or only in uvm-core (the Accellera reference implementation, which other libraries may not match).

| Question | Tool | Standard? | What to look for |
|---|---|---|---|
| Did my configuration arrive? | `+UVM_CONFIG_DB_TRACE` | uvm-core | `CFGDB/SET` and `CFGDB/GET` lines; `= null (failed lookup)`. Printed at `UVM_LOW`, so hidden at `+UVM_VERBOSITY=UVM_NONE` |
| Was every setting read? | `check_config_usage()` | uvm-core (compatibility API) | `CFGNRD` lines list settings written but never read |
| Which class was really built? | `uvm_factory::get().print()` | §8.3.1.7.5 | the `Type Overrides` and `Instance Overrides` tables |
| Which class *would* be built here? | `find_override_by_type(type, path)` | §8.3.1.7.1 | returns the override wrapper; uvm-core also has `debug_create_by_type`, which prints the search |
| Is the tree what I think? | `uvm_root::get().print_topology()` in `end_of_elaboration_phase` | F.7.4.2 | names, types and nesting; call it after build, never at the end of a `build_phase` |
| Who is holding the phase open? | `+UVM_OBJECTION_TRACE` | uvm-core | `OBJTN_TRC` lines: a `raised` with no matching `dropped` |
| The same, from code | `phase.get_objection().get_objectors(list)` | §9.3.1.7.1, §10.5.1.5.1 | the queue of objects still objecting; uvm-core's `display_objections()` prints a table |
| Did the phase run at all? | `+UVM_PHASE_TRACE` | uvm-core | `No objections raised, skipping phase`; at a timeout, which phases still have objections |
| Is a component still making progress, long before the timeout? | `uvm_heartbeat` | §10.6 | a fatal `HBFAIL` (uvm-core message ID) naming the component that was silent in the last window |

A **heartbeat** (`uvm_heartbeat`, §10.6) watches a list of components: each must raise or drop a heartbeat objection in every window between two triggers of an event, or the heartbeat reports a failure. It finds a stalled agent within one window instead of at the global timeout. Setting one up, and the window rules, are in [hang triage](/curriculum/T4_Expert/E-DBG-1_Advanced_UVM_Debug_Methodologies/hang-lab).

**Reading the output: three traced excerpts.** The lines below follow the message formats in the uvm-core 2020.3.1 source; they are illustrative, not captured from a simulator. Real lines also carry a file name and line number, and the `(type …)` text is formatted by your simulator.

A configuration miss (`+UVM_CONFIG_DB_TRACE`):

```text
UVM_INFO @ 0 ns: reporter [CFGDB/SET] Configuration scope='uvm_test_top.env.agt*' name='cfg' (type agt_cfg) set by uvm_test_top = (agt_cfg) ...
UVM_INFO @ 0 ns: reporter [CFGDB/GET] Configuration scope='uvm_test_top.env.agent' name='cfg' (type agt_cfg) read accessor=uvm_test_top.env.agent = null (failed lookup)
```

What to look for: compare the `GET` scope with the `SET` scope character by character. Here the component is named `agent`, but the setting targets `agt*`.

A hang (`+UVM_OBJECTION_TRACE`):

```text
UVM_INFO @ 0 ns: run_objection [OBJTN_TRC] Object uvm_test_top raised 1 objection(s) (send 500 beats): count=1  total=1
UVM_INFO @ 0 ns: run_objection [OBJTN_TRC] Object uvm_top added 1 objection(s) to its total (raised from source object uvm_test_top, send 500 beats): count=0  total=1
```

What to look for: the last `raised` line with no later `dropped` line from the same object. Here the test raised and never dropped, so whatever the test waits on is stuck.

The tree (`print_topology()` in `end_of_elaboration_phase`):

```text
UVM_INFO @ 0 ns: reporter [UVMTOP] UVM testbench topology:
----------------------------------------------
Name           Type             Size  Value
----------------------------------------------
uvm_test_top   crc_inject_test  -     @335
  env          crc_env          -     @348
    chk        pkt_checker      -     @357
----------------------------------------------
```

What to look for: missing components (a `create` that never ran) and wrong types (an override that did or did not apply). The `@` numbers are object handles and vary from run to run.

### A debug event bus

A **debug event bus** is a component with one analysis port on which any component can publish a small **debug event** (a tag such as `"WATCHDOG_TIMEOUT"`, a detail string and a time). Debug components subscribe to it. It lets a debug action, such as opening a waveform window, adding trace metadata or writing a structured log line, react to *what happened* without rewiring drivers, monitors or scoreboards.

**Mechanism.** The bus is an ordinary analysis port (§12.2.10): `publish()` builds an event object and calls `ap.write(evt)`, which calls every subscriber's `write()` in turn, in zero time, in the publisher's process. A subscriber is a `uvm_subscriber #(debug_event)` (§13.9), which provides the `analysis_export` to connect to.

```systemverilog
// snippet: the event bus of the debug-waveform-trigger lab (names match the lab)
class debug_event extends uvm_object;
  `uvm_object_utils(debug_event)
  string tag;          // what happened, e.g. "WATCHDOG_TIMEOUT"
  string detail;
  time   last_ok_ns;   // the last time the bus made progress
  function new(string name = "debug_event");
    super.new(name);
  endfunction
endclass

class debug_event_bus extends uvm_component;
  `uvm_component_utils(debug_event_bus)
  uvm_analysis_port #(debug_event) ap;
  function new(string name, uvm_component parent);
    super.new(name, parent);
    ap = new("ap", this);
  endfunction
  function void publish(string tag, string detail, time last_ok_ns);
    debug_event evt = debug_event::type_id::create("evt");
    evt.tag        = tag;
    evt.detail     = detail;
    evt.last_ok_ns = last_ok_ns;
    `uvm_info("BUS", $sformatf("Broadcasting %s: %s", tag, detail), UVM_LOW)
    ap.write(evt);   // every subscriber's write() runs now
  endfunction
endclass

// In the subscriber: no hierarchical reference to tb_top, so it can live in a package.
virtual function void write(debug_event t);
  if (t.tag == "WATCHDOG_TIMEOUT") dump_now.trigger();   // a uvm_event shared by name
endfunction
```

**Pitfalls, and why each is wrong:**
- **Using the bus instead of `` `uvm_error ``.** The bus is for debug actions; it is not a reporting channel. A failure must still be reported with `` `uvm_error `` or `` `uvm_fatal `` so the server counts it.
- **Blocking in `write()`.** `write()` is a function, so it cannot wait. Anything that takes time (open a window *later*, wait for a quiet bus) belongs in a task the subscriber starts, or in a process that waits on a `uvm_event`.
- **Calling `$dumpvars(0, tb_top)` from a class.** It compiles only while the class sits outside any package. Items in a package cannot make hierarchical references (IEEE 1800-2023 §26.2), and real benches keep classes in packages. Share a named event instead: `uvm_event_pool::get_global("dump_now")` returns the same `uvm_event` to every caller that uses that key (IEEE 1800.2-2020 §10.4.1.2.3), so the subscriber triggers it and an `initial` block in `tb_top` waits on it.

**Real testbench use.** Typical events are reset done, a watchdog timeout, a first scoreboard mismatch and an interrupt storm. Typical subscribers open a waveform window, raise verbosity for one agent, or append one JSON line per event to a file for dashboards.

### Selective waveforms and transaction recording

Dumping every signal for every run of a long regression costs more disk space and simulation time than most teams can spend, so waveforms are captured selectively. The standard's VCD tasks are `$dumpfile` (file name), `$dumpvars` (what to dump), `$dumpoff` and `$dumpon` (pause and resume), `$dumplimit` (a cap on file size, in bytes) and `$dumpflush` (IEEE 1800-2023 §21.7.1.1–§21.7.1.6). One rule decides how you use them:

> Executing `$dumpvars` "causes the value change dumping to start at the end of the current simulation time unit" (IEEE 1800-2023 §21.7.1.3).

So **a dump started by a trigger records only what happens after the trigger.** By the time a watchdog fires, the cause of the stall is in the past, and no standard task can recover it. The standard method is a **two-run window**:

1. **Run 1 (the regression run)** dumps nothing. When the watchdog fires, a debug subscriber logs the time of the last good activity, `T`.
2. **Run 2 (the debug rerun)** uses the same test, seed and build, plus `+DUMP_START=<T - margin>`. An `initial` block in `tb_top` reads it with `$value$plusargs` (§21.6), waits until then, and calls `$dumpfile` and `$dumpvars`. The window now contains the cause.

**Single-run alternatives are tool-dependent.** Some simulators can keep recent history in memory and write it out on a trigger, or dump in their own database formats (FSDB, WLF, SHM) with richer controls. These are vendor features outside IEEE 1800-2023: check your tool's documentation, and label them as such in team scripts. `$dumplimit` caps the file size; it does not choose a time window.

**Transaction recording** shows whole transactions next to the signals ([I-UVM-6](/curriculum/T2_Intermediate/I-UVM-6_UVM_Recording_Classes/index) teaches the classes; its "Try it: why is my stream empty?" explorer pictures streams, recorders and the enable switches). For a debug rerun:
- Enable recording on the agents on the failing path only: `env.agt.set_recording_enabled_hier(1)` (Annex D.2.3; it calls `set_recording_enabled`, §13.1.7.13, on the component and its children). It reaches only the children that exist when you call it, so call it in `connect_phase` or `end_of_elaboration_phase`, not in the parent's `build_phase`.
- A sequencer records the items it handles automatically unless `disable_auto_item_recording()` is called (§15.2.1.2.10–§15.2.1.2.11); drivers and monitors bracket their own transactions with `begin_tr` and `end_tr`.
- To relate transactions across agents (a request and its response, a bus write and the register it updated), use the standard links: `uvm_tr_database::establish_link` with `uvm_related_link`, `uvm_parent_child_link` or `uvm_cause_effect_link` (§7.1.5, §7.3). How a viewer draws those links is tool-dependent.

### The regression loop: from a red result to a locked-in fix

A regression is only useful if every red result can be turned into a fix quickly. That depends on decisions made *before* the failure:

**What every run must log** (in the log header or the regression database):
- the test name and the **seed** (the seed option itself is tool-specific, for example `+ntb_random_seed=<n>`, `-sv_seed <n>` or `-svseed <n>`, so the script records the value it passed);
- the **build** identity: the source revision and the compile options;
- the simulator name and version;
- the full run command line, including every plusarg.

**Why the build matters as much as the seed.** The seed only starts the random number generators. Random stability (IEEE 1800-2023 §18.14) makes each thread's and each object's random sequence depend on the order in which threads and objects are created, so a code change, even an added debug print that creates objects, can shift what the same seed produces. "Seed 42 passes after my rebuild" does not mean the bug is gone; it may mean seed 42 no longer reaches it. Reproduce on the archived original build first. The [systematic debug lesson](/curriculum/T4_Expert/E-DBG-1_Advanced_UVM_Debug_Methodologies/effective-debug) explains exactly what keeps UVM's random streams stable and what breaks them.

- **Gate:** the honest-verdict rules above, run by the regression script on every log.
- **Triage, reproduce, debug, fix:** the [systematic debug lesson](/curriculum/T4_Expert/E-DBG-1_Advanced_UVM_Debug_Methodologies/effective-debug) teaches each step: finding the *first* `UVM_ERROR` or `UVM_FATAL`, normalizing it into a signature and grouping runs into buckets (with a kata), the exact-reproduction contract, isolating the failure with command-line visibility, and confirming a hypothesis before fixing.
- **Hangs:** a `PH_TIMEOUT` fatal, or a heartbeat failure, goes to [hang triage](/curriculum/T4_Expert/E-DBG-1_Advanced_UVM_Debug_Methodologies/hang-lab).

### Recap

- `UVM_ERROR : 0` proves no counted check failed. It does not prove that errors were counted, that UVM saw every failure, or that anything was checked. Four mechanisms make a verdict lie; a CI gate checks for all of them.
- A catcher runs inside the server after the handler; it sees the overridden severity. Match severity, ID and message; return THROW; count what you demote; check the count; register on a component that exists.
- Pick the trace by the question. `+UVM_*_TRACE` plusargs, `display_objections` and `check_config_usage` are uvm-core features; `get_objectors`, `find_override_by_type`, factory `print` and `print_topology` are in the standard.
- A debug event bus is an analysis port for debug actions, not for errors. Dump control lives in `tb_top`, reached through a named `uvm_event`.
- A dump started by a trigger records only what follows it. Rerun the same seed and build with a window that opens before the cause.
- Log seed, build, tool version and plusargs for every run, because the same seed on a different build is a different test.

## Make It Work

### Worked example: an error-injection test with an honest verdict

This complete file is a small error-injection test. `pkt_checker` stands in for a monitor's CRC check; the test corrupts packets 2 and 4 on purpose; `crc_demoter` demotes exactly those errors; and the test checks in `check_phase` that it demoted exactly two. The checker also refuses to pass a run in which it checked nothing.

```systemverilog
// compile: one file; top module tb_top; uvm-core 2020.3.1
`include "uvm_macros.svh"

package crc_demo_pkg;
  timeunit 1ns; timeprecision 1ps;
  import uvm_pkg::*;

  // Stands in for a monitor's CRC check; a real one would sample a bus.
  class pkt_checker extends uvm_component;
    `uvm_component_utils(pkt_checker)
    int unsigned checked;   // read by the zero-activity guard

    function new(string name, uvm_component parent);
      super.new(name, parent);
    endfunction

    function void check_pkt(int unsigned id, bit crc_ok);
      checked++;
      if (!crc_ok) begin
        `uvm_error("CRC", $sformatf("bad CRC on pkt %0d", id))
      end
    endfunction

    // Zero activity is a failure, not a pass.
    function void check_phase(uvm_phase phase);
      if (checked == 0) begin
        `uvm_error("NO_CHECKS", "no packet was checked")
      end
    endfunction

    function void report_phase(uvm_phase phase);
      `uvm_info("CHK_DONE", $sformatf("checked=%0d", checked), UVM_NONE)
    endfunction
  endclass

  class crc_env extends uvm_env;
    `uvm_component_utils(crc_env)
    pkt_checker chk;

    function new(string name, uvm_component parent);
      super.new(name, parent);
    endfunction

    function void build_phase(uvm_phase phase);
      super.build_phase(phase);
      chk = pkt_checker::type_id::create("chk", this);
    endfunction
  endclass

  // Demotes only the CRC errors this test injects on purpose.
  class crc_demoter extends uvm_report_catcher;
    `uvm_object_utils(crc_demoter)
    int unsigned demoted;

    function new(string name = "crc_demoter");
      super.new(name);
    endfunction

    virtual function action_e catch();
      if (get_severity() == UVM_ERROR && get_id() == "CRC" &&
          uvm_is_match("bad CRC on pkt*", get_message())) begin
        set_severity(UVM_INFO);   // still printed and counted, as UVM_INFO
        demoted++;
      end
      return THROW;               // CAUGHT would hide it from the log and counts
    endfunction
  endclass

  class crc_inject_test extends uvm_test;
    `uvm_component_utils(crc_inject_test)
    localparam int unsigned EXPECTED_BAD = 2;
    crc_env     env;
    crc_demoter demoter;

    function new(string name, uvm_component parent);
      super.new(name, parent);
    endfunction

    function void build_phase(uvm_phase phase);
      super.build_phase(phase);
      env     = crc_env::type_id::create("env", this);
      demoter = crc_demoter::type_id::create("demoter");
    endfunction

    // env.chk exists only after env's build_phase (build is top-down).
    // In build_phase it is still null, and add(null, ...) would make the
    // catcher type-wide: it would see every component's reports.
    function void connect_phase(uvm_phase phase);
      uvm_report_cb::add(env.chk, demoter);
    endfunction

    task run_phase(uvm_phase phase);
      phase.raise_objection(this, "checking 5 packets");
      for (int unsigned id = 1; id <= 5; id++) begin
        #10ns;
        env.chk.check_pkt(id, !(id == 2 || id == 4));   // 2 and 4 are corrupted
      end
      phase.drop_objection(this, "all packets checked");
    endtask

    // Accounting: if the injection silently stops, the test must fail.
    function void check_phase(uvm_phase phase);
      if (demoter.demoted != EXPECTED_BAD) begin
        `uvm_error("CRC_ACCT", $sformatf("expected %0d injected CRC errors, demoted %0d",
                                         EXPECTED_BAD, demoter.demoted))
      end else begin
        `uvm_info("CRC_ACCT", $sformatf("demoted %0d of %0d expected CRC errors",
                                        demoter.demoted, EXPECTED_BAD), UVM_NONE)
      end
    endfunction
  endclass
endpackage

module tb_top;
  timeunit 1ns; timeprecision 1ps;
  import uvm_pkg::*;
  import crc_demo_pkg::*;

  initial begin
    $timeformat(-9, 0, " ns", 0);   // UVM then prints times as "20 ns"
    run_test("crc_inject_test");
  end
endmodule
```

**Expected output** (illustrative: traced by hand against the uvm-core 2020.3.1 source, not captured from a simulator; file names, line numbers and the release-notes banner are omitted):

Read it the way a gate would: the summary is present, `UVM_ERROR` and `UVM_FATAL` are 0, `checked=5` proves work was done, the two `CRC` lines appear as `UVM_INFO` (demoted, still visible), and `CRC_ACCT` confirms the count. The `CRC_ACCT` line comes before `CHK_DONE` because `check_phase` runs before `report_phase`.

**Break it on purpose.** Predict each result before you run it:

| Change | What the log shows |
|---|---|
| Corrupt packet 5 as well (`id == 2 \|\| id == 4 \|\| id == 5`) | Three `CRC` lines as `UVM_INFO`, then `UVM_ERROR … [CRC_ACCT] expected 2 injected CRC errors, demoted 3`, and `UVM_ERROR :    1`. The pattern matched an error the test did not inject; the accounting caught it. |
| Stop the injection (pass `1'b1` for every packet) | No `CRC` lines; `[CRC_ACCT] expected 2 injected CRC errors, demoted 0`; the test fails because it no longer tests what it claims. |
| Replace the demoter's body with `return (get_severity() == UVM_ERROR) ? CAUGHT : THROW;` | No `CRC` lines at all; the catcher summary shows `Number of caught UVM_ERROR reports   :    2`; `CRC_ACCT` reports `demoted 0` and fails the run. Without the accounting, this catch-all would have passed. |
| Run with `+UVM_VERBOSITY=UVM_NONE` | The run still passes, but `RNTST` and the whole catcher summary disappear: uvm-core issues that summary at `UVM_LOW`. A gate that reads the catcher summary must run at `UVM_LOW` or above. |
| Move `uvm_report_cb::add(env.chk, demoter)` into `build_phase` | The same passing log, because only `chk` reports `CRC` here. But the catcher is now type-wide (`env.chk` was `null`), so in a full bench it would also demote `CRC` errors from every other component. |

### How to write an error-injection test with an honest verdict

1. **List the expected errors** the test will cause: severity, ID, message pattern and count.
2. **Write a catcher that matches all three** (severity, ID, message) and demotes with `set_severity(UVM_INFO)`, returning THROW so the report stays visible.
3. **Count every demotion** in the catcher.
4. **Register on the reporting component**, not `null`, in `connect_phase` or later, when that component exists. For a sequence's errors, register on its sequencer.
5. **Check the count in `check_phase`** and raise `` `uvm_error `` on any mismatch, too few or too many.
6. **Keep a zero-activity guard** in the checker, so a test that stimulated nothing cannot pass.
7. **Audit once:** run the test with `+UVM_VERBOSITY=UVM_LOW` and read the catcher summary; uvm-core also offers `uvm_report_catcher::print_catcher()`, which lists the registered catchers.
8. **Put the test on the gate's reviewed list** of tests allowed to show demoted errors.

**Checklist before moving on:**
- [ ] I can name the four ways a verdict lies and the log evidence for each.
- [ ] I can predict the `UVM_ERROR` count for the catch-all, demote and `UVM_NO_ACTION` configurations, and say which verdicts are honest.
- [ ] My catcher matches severity, ID and message, returns THROW, and counts.
- [ ] My test fails when the injected-error count is wrong in either direction.
- [ ] I register catchers on components that exist, and I know why `add(null, …)` is type-wide.
- [ ] I can pick the trace that answers "did my configuration arrive?", "who holds the phase open?" and "which class was built?".
- [ ] I can explain why a trigger-started dump misses the cause and how a rerun window fixes it.
- [ ] My regression logs the test, seed, build, tool version and command line of every run.

## Push Further

### Expert: Catcher corner cases

- **The severity override comes first.** The handler applies `+uvm_set_severity` or `set_report_severity_id_override` before the server runs the catchers (uvm-core `uvm_report_handler.svh`, `process_report_message`). A catcher that tests `get_severity() == UVM_ERROR` will not match an error already overridden to `UVM_WARNING`.
- **Order and stopping.** Catchers run in registration order (`UVM_APPEND` by default, `UVM_PREPEND` to go first, §10.7.2.3.1). CAUGHT ends processing at once, so later catchers never see the report (§6.5.1.2.14 a). A disabled catcher (`callback_mode(0)`, §10.7.1.2.2) is skipped.
- **Issuing from a catcher.** `issue()` emits the current report immediately, even if `catch()` then returns CAUGHT; the standard notes that issuing "updates the report_server stats, possibly multiple times if the message is not CAUGHT" (§6.6.6.6), so a THROW after `issue()` counts the report twice. Reports a catcher issues itself with its protected `uvm_report_*` methods bypass all catchers (§6.6.6.1–§6.6.6.5).
- **What catchers never see.** Reports filtered by verbosity, reports whose action is `UVM_NO_ACTION` when issued through the macros (the macro checks first), `$display` and `$error`. A catcher does see a `UVM_NO_ACTION` report issued through the `uvm_report_*` functions, because only the server drops it, after the catchers.
- **Auditing catchers.** uvm-core's `uvm_report_catcher::debug_report_catcher(1)` makes every CAUGHT behave like THROW, so you can see what the catchers are hiding; bit 1 (`debug_report_catcher(2)`) stops catchers from modifying reports. Both are uvm-core implementation features (tagged `@uvm-accellera`), not in IEEE 1800.2-2020.

### Expert: Waveform and recording budgets

- **The `$dumpvars` rules.** All `$dumpvars` calls in a run must execute at the same simulation time (§21.7.1.2), so you cannot add scopes later in the run. `$dumpoff` writes a checkpoint in which every dumped variable is `x`, and `$dumpon` writes their current values (§21.7.1.3). A window that pauses and resumes therefore shows `x` in the gap, not stale values.
- **One dump per run, chosen up front.** A practical budget: regressions dump nothing; a failing signature gets one rerun with a window of a few microseconds before the last good activity; recording is enabled only on the agents on the failing path. Disk and run-time costs vary too much between tools and designs to quote figures; measure your own.
- **Dump scope.** `$dumpvars(1, tb_top.u_dut.u_axi_bridge)` limits depth and scope; levels and scopes are standard (§21.7.1.2). Whether interface instances and class objects appear in a VCD is tool-dependent: VCD is defined for variables in module scopes.
- **Recording knobs.** uvm-core reads a component's `recording_detail` setting from the configuration database in the component's constructor, so it must be set before that component is created; `set_recording_enabled` (§13.1.7.13) is the standard switch. Reports can be sent to the recorder too, with the `UVM_RM_RECORD` action (Annex F.2.2.2).
- **Tool-dependent capture.** Vendor database formats, in-memory history buffers and viewer-side transaction correlation are outside the standards. Treat them as tool features, wrap them in `tb_top` behind a plusarg, and keep the standard VCD path working so the method survives a tool change.

### Expert: Gating a regression honestly at scale

Methodology practice; no standard defines regression management.
- **Gate as code, versioned with the TB.** The rules from Build Your Mental Model live in one script, reviewed like RTL. A change to the log format (a custom report server, [E-CUST-1](/curriculum/T4_Expert/E-CUST-1_UVM_Methodology_Customization/index)) must change the parser in the same commit, or the gate silently stops matching.
- **Check the inputs, not only the outputs.** Mechanism 1 leaves no trace in the summary when it uses `UVM_NO_ACTION`, so lint what can hide failures before the run: regression command lines (`UVM_NO_ACTION` or `+uvm_set_severity` on errors), catcher code in review (`return CAUGHT` without a narrow match, `uvm_report_cb::add(null, …)`), and `$assertoff` or `$assertcontrol` calls in tests.
- **Require positive evidence per checker, by ID.** Each scoreboard prints one count line with a stable ID; the gate keeps, per test, the list of checker IDs it expects. A scoreboard that was removed or never built then fails the run, instead of contributing nothing to a clean summary.
- **Keep the evidence visible.** uvm-core prints the catcher summary at `UVM_LOW`, `RNTST` at `UVM_LOW` and the `CFGDB` trace at `UVM_LOW`; a regression run at `UVM_NONE` hides all three. Either run regressions at `UVM_LOW` or have error-injection tests print their own accounting line at `UVM_NONE`, as `CRC_ACCT` does.
- **Record the recipe.** IEEE 1800-2023 defines no system function that returns the seed given on the simulator command line, so the regression script records the value it passed, with the build revision, compile options, tool version and full command line.
- **New, known and flaky failures, waivers and rerun budgets** belong to triage, after the gate: see "Expert: triage at scale" in the [systematic debug lesson](/curriculum/T4_Expert/E-DBG-1_Advanced_UVM_Debug_Methodologies/effective-debug).

### Kata: is this verdict honest?

Each item below is one run from a nightly regression: the relevant part of its command line and log. All five were marked **PASS** by an old gate that only checked `UVM_ERROR :    0` and `UVM_FATAL :    0`. For each one, decide whether the pass is honest, name the mechanism if it is not, and write the gate rule that would have caught it.

**Run A**

```text
cmd: +UVM_TESTNAME=dma_test +ntb_random_seed=17 '+uvm_set_action=uvm_test_top.env.*,_ALL_,UVM_ERROR,UVM_NO_ACTION'
UVM_INFO @ 98210 ns: uvm_test_top.env.scb [SCB_SUMMARY] 812 compares, 0 mismatches
UVM_ERROR :    0
UVM_FATAL :    0
```

**Run B**

```text
cmd: +UVM_TESTNAME=irq_test +ntb_random_seed=5
UVM_INFO @ 40110 ns: uvm_test_top.env.scb [SCB_SUMMARY] 230 compares, 0 mismatches
Number of demoted UVM_ERROR reports  :    0
Number of caught UVM_ERROR reports   :   14
UVM_ERROR :    0
UVM_FATAL :    0
```

**Run C**

```text
cmd: +UVM_TESTNAME=burst_test +ntb_random_seed=88
Error: assertion tb_top.bus_if.a_hold failed at 3215 ns   (simulator format; varies by tool)
UVM_INFO @ 50020 ns: uvm_test_top.env.scb [SCB_SUMMARY] 401 compares, 0 mismatches
UVM_ERROR :    0
UVM_FATAL :    0
```

**Run D**

```text
cmd: +UVM_TESTNAME=smoke_test +ntb_random_seed=3 +UVM_PHASE_TRACE
UVM_INFO @ 0 ns: reporter [PH/TRC/SKIP] Phase 'common.run' (id=…) No objections raised, skipping phase
UVM_INFO @ 0 ns: uvm_test_top.env.scb [SCB_SUMMARY] 0 compares, 0 mismatches
UVM_ERROR :    0
UVM_FATAL :    0
```

**Run E**

```text
cmd: +UVM_TESTNAME=crc_inject_test +ntb_random_seed=61
UVM_INFO @ 50 ns: uvm_test_top [CRC_ACCT] demoted 2 of 2 expected CRC errors
UVM_INFO @ 50 ns: uvm_test_top.env.chk [CHK_DONE] checked=5
Number of demoted UVM_ERROR reports  :    2
Number of caught UVM_ERROR reports   :    0
UVM_ERROR :    0
UVM_FATAL :    0
```

<details className="my-4 rounded-xl border border-border/70 p-3">
<summary className="cursor-pointer font-semibold">Show the worked solution</summary>

1. **Run A: not honest (mechanism 1, errors removed before counting).** `UVM_NO_ACTION` on every error below the test means any mismatch would have been dropped before counting; through the macros it would never even have been built, so even `0 mismatches` is the scoreboard's own counter, not proof. Gate rule: fail any regression command line containing `UVM_NO_ACTION` for `UVM_ERROR` or `UVM_FATAL`.
2. **Run B: not honest (mechanism 1, a catcher).** Fourteen errors were caught and none demoted: a catcher returned CAUGHT, so the errors vanished from the log and the counts. `irq_test` is not an error-injection test, and nothing accounts for them. Gate rule: fail when the catcher summary shows caught or demoted errors and the test is not on the reviewed list. Then find the catcher with `print_catcher()` or rerun with `debug_report_catcher(1)` (both uvm-core).
3. **Run C: not honest (mechanism 2, a failure UVM never saw).** An assertion failed with the simulator's `$error`, which UVM never counts. Gate rule: fail on simulator-format error lines (a tool-specific pattern). TB fix: report assertion failures with `` `uvm_error `` in the action block. Its first failure, at 3215 ns, is the signature to bucket on.
4. **Run D: not honest (mechanism 3, zero activity).** No objection was raised, so `run_phase` was skipped and the scoreboard compared nothing. Gate rule: require a positive count line (`SCB_SUMMARY` with compares above 0). TB fix: raise an objection in the test or its top sequence, and give the scoreboard a zero-activity guard that raises `` `uvm_error `` in `check_phase`.
5. **Run E: honest.** The demotions are accounted for (`demoted 2 of 2`), nothing was caught, work was done (`checked=5`), and `crc_inject_test` is on the reviewed list of tests allowed to demote. It passes under every rule.

</details>
