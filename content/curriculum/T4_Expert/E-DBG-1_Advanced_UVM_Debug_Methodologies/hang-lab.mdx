## Quick Take

- **What it is:** A **hang** is a UVM run whose `run_phase` never ends on its own: something keeps the phase open, nothing makes progress, and only the **phase timeout** stops the run with `UVM_FATAL [PH_TIMEOUT]` (or a heartbeat or watchdog, if you configured one). **Hang triage** is the method for finding the one component that owns the hang: read how the run ended, find who still holds the run-phase objection, then follow what each blocked process is waiting for until the chain ends.
- **Why it matters:** A hang wastes a whole regression slot, prints no useful error, and kills `check_phase` and `report_phase`, so the scoreboard never tells you anything. The usual reflexes (a longer timeout, a drain time, more `$display` calls) never fix it. Engineers who follow the wait-for chain find the owner in minutes. A **heartbeat** (an activity check, explained below) and a hang dump make the next hang fail fast and explain itself.
- **The Analogy:** A road jam. The timeout is the traffic report at midnight saying the road is still closed. To clear it, you walk from the front of the queue (whoever still holds the objection) to whatever it is waiting for, and so on, until you find a broken-down truck (an objection nobody will drop), a missing ferry (a get that no producer will ever satisfy), or two lorries blocking each other at a junction (a deadlock). *Where it breaks:* in a testbench (TB) the jam is perfectly repeatable with the same seed and build, so you can rerun it with more visibility. A road jam is not repeatable. Also, a UVM run can look healthy when the road was simply empty: a run that ends at 0 ns is not a jam, but it is not a pass either.

**You will be able to:**
1. **Diagnose** a hang from its evidence: how the run ended, who still holds the run-phase objection (`+UVM_OBJECTION_TRACE`, `get_objectors()`, `display_objections()`) and where each process waits, and name the component that owns it.
2. **Classify** a hang by where its wait-for chain ends (an objection never dropped, a get that no producer will satisfy, or a deadlocked handshake), and **choose** the fix in the owning component instead of a longer timeout or a drain time.
3. **Configure** a run timeout and a `uvm_heartbeat`, and **predict** what each one detects and when.
4. **Distinguish** a hang from a zero-activity run that only looks like a pass.

## Build Your Mental Model

**How to read this page.** The core path is the first four sections: what a hang is, the three places to look, the wait-for chain, and the three hang families. Practitioner depth follows: reading each kind of evidence, heartbeats, the zero-activity run, and a drill on the hang model. Make It Work gives you one bench with three switchable hangs and a debug kit, and walks you through diagnosing each one. Push Further holds the expert corner cases.

A few words this page uses, in one line each (most come from earlier lessons):

- A **phase** is one named step of a UVM run. `run_phase` is the one that consumes simulation time. An **objection** is a counter that keeps a task phase open: a component **raises** it to say "I am still busy" and **drops** it when done, and the phase ends when the total count falls to zero ([I-UVM-1C](/curriculum/T2_Intermediate/I-UVM-1C_UVM_Phasing/index)).
- The **phase timeout** is set with `uvm_root::get().set_timeout(t)`. It is an absolute simulation time: if `run_phase` is still open at time `t`, UVM reports `UVM_FATAL [PH_TIMEOUT]` (IEEE 1800.2-2020 Annex F.7.3.3).
- A **process** is one thread of execution: an `initial` block, a branch of a `fork`, or a component's `run_phase` task. A process is **blocked** when it waits for an event, a value or a call that has not happened yet.
- The **sequencer–driver handshake** is the call pairing `get_next_item()` / `item_done()` between a driver and the sequencer, with the sequence waiting in `start_item()` and `finish_item()` ([I-UVM-3A](/curriculum/T2_Intermediate/I-UVM-3A_Fundamentals/index), in depth in [Sequencer-Driver Handshake](/curriculum/T2_Intermediate/I-UVM-3B_Advanced_Sequencing_and_Layering/sequencer-driver-handshake)).
- A **TLM FIFO** (`uvm_tlm_analysis_fifo`) stores transactions between a producer that writes and a consumer whose `get()` blocks until an entry exists ([I-UVM-2B](/curriculum/T2_Intermediate/I-UVM-2B_TLM_Connections/index)).
- A **report catcher** is a callback that sees each UVM message before the report server acts on it ([E-DBG-1 index](/curriculum/T4_Expert/E-DBG-1_Advanced_UVM_Debug_Methodologies/index)).
- The **design under test (DUT)** is the RTL the TB drives. A **regression** runs many tests with many random **seeds** (the starting value of the random generators); the same seed on the same build reproduces a run exactly ([Systematic Debug](/curriculum/T4_Expert/E-DBG-1_Advanced_UVM_Debug_Methodologies/effective-debug)).
- **Drain time** is an extra delay a phase waits after its objection total reaches zero, before it ends (§10.5.1.3.7). A **plusarg** is a `+NAME` or `+NAME=value` option on the simulator command line.
- **uvm-core 2020.3.1** is the Accellera reference implementation of IEEE 1800.2-2020. Features marked "uvm-core only" exist in that library but not in the standard, so another UVM library may differ.

### What a hang is, and what it is not

`run_phase` ends when every run-phase objection has been dropped (IEEE 1800.2-2020 §9.8.1.5, §10.5). So a run that never ends has, by definition, **at least one objection that is still raised**. The objection itself is rarely the bug. It is held by a component that is waiting for something, and that something is waiting for something else.

There are three ways a run can end badly, and they need different tools:

| How the run ended | What it means | First tool |
|---|---|---|
| `UVM_FATAL [PH_TIMEOUT] Explicit timeout of … hit` | A hang: an objection was still raised when simulation time reached the timeout. `check_phase` and `report_phase` never ran. | Objection evidence (who holds it), then process evidence (what it waits for) |
| `UVM_FATAL [HBFAIL] Did not recieve an update of …` | A **heartbeat** found a component silent for a whole window, long before the timeout. (The misspelling is in the uvm-core message; search for it as printed.) | The same evidence, sooner |
| Simulation time stops advancing and the job never finishes | A loop that never consumes time. Not a UVM hang: the timeout cannot fire, because it is a delay that needs time to advance. | The simulator's interactive stop or a job time limit (tool-dependent), then the loop |

And one way a run can end too *well*: **the zero-activity run**. If nobody raises an objection before `run_phase` first checks, the phase ends at 0 ns, kills the stimulus, and the summary shows `UVM_ERROR :    0`. That is not a hang and not a pass. This page treats it as the opposite failure.

### The three places to look

Every hang diagnosis collects the same three pieces of evidence, in this order:

1. **How did it end?** `PH_TIMEOUT`, `HBFAIL`, or no end at all. The time of the end and the last messages before it.
2. **Who holds the objection?** The components or sequences whose count is still above zero. `+UVM_OBJECTION_TRACE` logs every raise and drop as it happens. `get_objectors()` (§10.5.1.5.1) returns the list in code, and `display_objections()` prints it as a table (uvm-core 2020.3.1 only).
3. **Where does each process wait?** For each holder, and for whatever it waits for: is it blocked in `finish_item()`, in a FIFO `get()`, in `@(vif.cb iff ...)`, or not blocked at all? The sequencer, the FIFOs and the ports can all be asked.

Evidence 2 names the **holder**. Evidence 3 takes you from the holder to the **owner**: the component whose code must change.

### Follow the wait-for chain

The **wait-for chain** is the list you get by starting at the holder and repeatedly asking "what is this process waiting for, and who would provide it?". You stop when the answer is one of three things:

| The chain ends at… | Hang family | Typical owner and fix |
|---|---|---|
| a holder that is **not waiting for anything it needs**: it finished, looped past its drop, or runs forever by design | **objection never dropped** | the holder: drop on every path, or never raise in a process that runs forever |
| a **partner that will never act**: a producer that is not connected or never writes, a driver that never calls `item_done()`, a lock that is never released | **blocked get** (a missing partner) | the partner, or the connection to it |
| **the process you started from**: A waits for B, and B waits for A | **deadlocked handshake** | the side that broke the protocol's dependency rule |

The rule that saves the most time: **the holder is usually the victim, not the owner.** A scoreboard holding an objection while it waits in `act_fifo.get()` is doing exactly what it should. The bug is wherever the actual transactions stopped.

**Two mistakes everyone makes.**
- **Fixing the holder.** Adding `phase.drop_objection()` to the scoreboard in family 2 ends the run, but the scoreboard then reports nothing for transactions it never received. The run "passes" with the real bug (the missing connection) still there.
- **Fixing the clock.** A longer timeout produces the same hang later. A drain time only starts once the objection total reaches zero, which is exactly what never happens (§10.5.1.3.7). Neither changes the chain.

### Reading the evidence: how the run ended

The timeout fatal looks like this in uvm-core 2020.3.1 (`uvm_phase_hopper.svh`):

```text
UVM_FATAL @ 2000 ns: reporter [PH_TIMEOUT] Explicit timeout of 2000 ns hit, indicating a probable testbench issue
```

- **"Explicit"** means the test called `set_timeout()`; **"Default"** means nobody did, and uvm-core used its default of 9200 s of simulated time. Set an explicit, realistic timeout in your base test, before `run_phase` starts (§9.8.1.5: the value applies if set "prior to `uvm_run_phase` starting").
- The timeout is a *bound*, not a diagnosis. Its time tells you only how long you waited.
- Rerun with **`+UVM_PHASE_TRACE`** (uvm-core only) and, just before the fatal, uvm-core prints each phase with outstanding objections and their counts.

Look at the last *meaningful* message before the end, not the last line. A scoreboard error at 45 ns followed by 1955 ns of silence is the start of the story.

### Reading the evidence: who holds the objection

**`+UVM_OBJECTION_TRACE`** (uvm-core only, not in IEEE 1800.2-2020) logs every raise and drop with ID `OBJTN_TRC`. The lines below are illustrative, in the uvm-core format, from the Make It Work bench run with `+HANG=1` (file and line numbers removed; the exact drop time depends on arbitration order):

```text
UVM_INFO @ 0 ns: run_objection [OBJTN_TRC] Object uvm_test_top raised 1 run_objection objection(s) (stimulus): count=1  total=1
UVM_INFO @ 0 ns: run_objection [OBJTN_TRC] Object uvm_test_top.env.agt.sqr.poll_seq raised 1 run_objection objection(s) (automatic phase objection): count=1  total=1
UVM_INFO @ 495 ns: run_objection [OBJTN_TRC] Object uvm_test_top dropped 1 run_objection objection(s) (stimulus done): count=0  total=1
```

How to read it:
- **`count`** is the object's own raises minus drops; **`total`** includes its children. The **holder** is an object whose `count` stays above zero.
- Read the last line closely: the test's own `count` is 0, but its `total` stays at 1 (2 if `scb` is mid-compare at that moment), because `poll_seq` below it still holds. A sequence's objection propagates through its sequencer, the agent and the env up to the test (uvm-core passes it to the sequence's sequencer as its parent). A `total` that will not reach zero at the top is the signature of a holder further down.
- The text in parentheses is the description argument of `raise_objection` and `drop_objection`. Always pass one: it is the only way to tell "pending compare" from "stimulus" in a long log.
- The real log also has a line for each parent the raise propagates through ("added 1 … to its total"). They are omitted here; filter on `raised`/`dropped` and on your own descriptions.
- A component that raises and drops on every transaction shows up with count 1 in some snapshots: for the part of every transaction between its raise and its drop. That is a **transient** holder. The **stuck** holder is the one with a raise and no later drop.

**In code**, `phase.get_objection().get_objectors(list)` fills a queue with the objects that raised and have not dropped (IEEE 1800.2-2020 §10.5.1.5.1; `get_objection()` is §9.3.1.7.1). One uvm-core caveat: it lists every object that still has an entry in its count table, and an entry whose own count is 0 is removed only once that object's total reaches 0. So the test, after its drop in the trace above, is still listed while `poll_seq` holds below it. Filter the list with `get_objection_count(obj) > 0` (§10.5.1.5.3, the object's own count) to keep only the real holders. `phase.get_objection().display_objections()` prints the same information as a Source/Total table (uvm-core). Use them from a debug thread, or from a report catcher at the timeout, as the Make It Work bench does.

### Reading the evidence: where each process waits

UVM does not print where your processes are blocked, so you ask the components:

| Question | How to ask | Standard? |
|---|---|---|
| Is a sequence holding the sequencer? | `sqr.is_grabbed()`, `sqr.current_grabber()` | §15.3.2.15, §15.3.2.16 |
| Which item does the driver hold between `get_next_item()` and `item_done()`? | `sqr.get_current_item()` | §15.4.1 |
| Is a FIFO empty, or filling up with nobody reading? | `fifo.used()` | §12.2.8.2.3 |
| Is a port connected at all? | `port.size()` (after end of elaboration) | §5.5.2.12 |
| Who is connected to what? | `port.debug_connected_to()` | uvm-core only |
| Where is *my* process? | a **breadcrumb**: a string each component updates before every blocking call, printed on demand | your own code |

Breadcrumbs are the cheapest instrument you can add. One line before each blocking call (`note(this, "act_fifo.get()")`) turns "the scoreboard holds the objection" into "the scoreboard has been waiting in `act_fifo.get()` since 45 ns". The Make It Work bench prints them automatically when a hang is detected.

Two silent traps to know:
- **An unconnected analysis port is silent.** uvm-core constructs `uvm_analysis_port` with a minimum of zero connections, so a missing `connect()` in `connect_phase` gives no error and no warning. `write()` simply goes nowhere. Check `ap.size()` in `end_of_elaboration_phase` for every analysis port your checkers depend on.
- **`uvm_tlm_analysis_fifo` is unbounded** (§12.2.8.3), so a FIFO whose consumer is stuck never blocks its producer. A growing `exp_fifo.used()` next to an empty `act_fifo.used()` is the classic family-2 picture.

### The three families, in detail

**Family 1: an objection never dropped.** The holder raised and will never drop. Common causes:
- an early `return` or `continue` on an error path that skips the drop;
- a sequence with `set_automatic_phase_objection(1)` whose `body()` contains a `forever` loop. the standard warns against exactly this, because "the objection will never get dropped" (§14.2.4.4, NOTE);
- a raise in a component that runs forever (a driver or monitor loop) with the drop after the loop.

*Signature:* `OBJTN_TRC` shows a raise with no later drop by that object; the holder is not blocked on anything that belongs to the stimulus. Traffic may even keep flowing. *Fix:* in the holder.

**Family 2: a blocked get (a missing partner).** The holder is blocked in a call whose partner will never act. Common causes:
- a FIFO or analysis connection that was never made, or a monitor that watches the wrong interface;
- a driver that never calls `item_done()`, so the sequence waits in `finish_item()` forever (the sequencer also reports "Get_next_item called twice without item_done or get in between" when the driver loops);
- a sequence waiting in `get_response()` for a response the driver never sends;
- a `grab()` or `lock()` that is never released, so other sequences wait in `start_item()` forever.

*Signature:* the holder is blocked in a get or wait; one step down the chain, the partner is idle, unconnected or busy elsewhere. Usually no error at all. *Fix:* in the partner or the connection. [Sequencer-Driver Handshake](/curriculum/T2_Intermediate/I-UVM-3B_Advanced_Sequencing_and_Layering/sequencer-driver-handshake) lists every handshake signature.

**Family 3: a deadlocked handshake.** Two parties each wait for the other to move first. In a TB the classic case is a pin-level handshake whose dependency rule is broken: a driver that waits for `READY` before raising `VALID`, facing a design under test (DUT) that is allowed to wait for `VALID` before raising `READY`. AXI states the rule for every channel: the sender's VALID must not depend on the receiver's READY, while the receiver may wait for VALID before it raises READY. The specification states that the dependency rules exist "To prevent a deadlock situation" (Arm IHI0022E §A3.3.1).

*Signature:* time advances, the clock runs, both handshake signals stay low, there are no errors, and the driver's breadcrumb says it is waiting for the DUT. *Fix:* in the side that broke the dependency rule, which is usually the driver.

The waveforms make the difference visible. In both, `values[k]` is the value sampled at rising edge k, and the DUT raises `in_ready` for one cycle after it samples `in_valid` high.

A circular wait can also form entirely inside UVM: two virtual sequences that `lock()` two sequencers in opposite orders. Push Further covers it.

### Heartbeats: catch a silent component early

A timeout must be longer than your longest legal test, so a hang at 10 µs in a test with a 10 ms timeout wastes 99.9 % of the slot. A **heartbeat** (`uvm_heartbeat`, IEEE 1800.2-2020 §10.6) is an activity check instead: the watched components raise or drop a dedicated **heartbeat objection** (a **beat**) in every **window** between two triggers of a `uvm_event`. Which components must beat depends on the **mode**: in `UVM_ALL_ACTIVE`, the mode used on this page, every watched component must beat at least once per window (the other modes follow below). If the condition fails for a window, the heartbeat reports a fatal with ID `HBFAIL` that names the silent component.

The API, all in §10.6.2:

```systemverilog
// snippet: the heartbeat set-up in pkt_env (full code in Make It Work)
hb_obj = new("hb_obj");             // a dedicated objection, not the phase's
hb     = new("hb", this, hb_obj);   // cntxt = env: beats must flow through env
hb_e   = new("hb_e");               // uvm_event#(uvm_object): its triggers delimit windows
// in run_phase:
void'(hb.set_mode(UVM_ALL_ACTIVE)); // every watched component must beat in each window
hb.set_heartbeat(hb_e, watched);    // watched is a queue: uvm_component watched[$]
// the watched component, once per unit of progress:
hb_obj.raise_objection(this);
hb_obj.drop_objection(this);
```

- **Modes** (§10.6, §10.6.2.2): `UVM_ALL_ACTIVE` (every watched component must beat in each window), `UVM_ANY_ACTIVE` (at least one), `UVM_ONE_ACTIVE` (exactly one, for example one of two redundant paths). The default mode, `UVM_NO_HB_MODE`, checks nothing, so always call `set_mode`.
- **`set_heartbeat`** starts monitoring immediately (§10.6.2.3). `start` and `stop` (§10.6.2.6, §10.6.2.7) control it later; to change the event, `stop()` first, then `start(new_event)`.
- **Call `stop()` when stimulus ends**, before the components legitimately go quiet, or a normal end of test trips `HBFAIL`.

Two details from the uvm-core 2020.3.1 implementation (`uvm_heartbeat.svh`) decide *when* it fires. **The first trigger is not checked**: it only opens the first window. And a beat counts only if the raise or drop **propagates through the context component** given to `new()`, so the watched components must sit below it. Predict before you read on: with triggers every 100 ns from time 0 and a scoreboard that never compares anything, at what time does `HBFAIL` appear?

**Debrief.** With triggers at 100, 200, 300 ns and a scoreboard that never compares, `HBFAIL` fires at **200 ns**: the trigger at 100 ns opens the first window and checks nothing, and the trigger at 200 ns checks it. A heartbeat therefore detects silence within two windows at most. Choose a window longer than the longest *legal* gap in activity (reset, a long configuration phase, a low-power period), and watch the component whose progress you care about. In Make It Work the heartbeat watches the scoreboard, because a stalled monitor, an unconnected FIFO and a deadlocked driver all end in the same symptom: no compares.

What a heartbeat cannot see: a component that keeps beating while the run never ends. In family 1, traffic keeps flowing and the scoreboard keeps comparing; only the objection evidence finds it.

### The opposite failure: a run that ends at 0 ns

If no objection is raised before UVM first checks the run phase, `run_phase` ends at 0 ns and kills every process in it, including the sequence that should have run. With `+UVM_PHASE_TRACE`, uvm-core prints "No objections raised, skipping phase" (ID `PH/TRC/SKIP`). The summary shows `UVM_ERROR :    0` and `UVM_FATAL :    0`.

It is the mirror image of a hang: a hang has an objection that is never dropped, this run has none at all. Both are failures of objection ownership, and both are invisible to the error counts. Guard against both in your base test: a timeout for the first, and a scoreboard that reports a `uvm_error` in `check_phase` when it compared nothing (`matches == 0`) for the second. [I-UVM-1D](/curriculum/T2_Intermediate/I-UVM-1D_Reporting_and_Run_Control/index) teaches the pass/fail rule that catches it.

|---|---|---|---|---|
| Same packet, over and over | `uvm_test_top` (waiting for `main_seq`) | `main_seq` in `finish_item()`, waiting for an `item_done()` the driver never calls | blocked get (missing partner call) | driver: call `item_done()` after driving |

| Stimulus stops after the interrupt | `uvm_test_top` (waiting for `main_seq`) | `main_seq` in `start_item()`; the grant is held by `irq_seq`, which is alive and never calls `ungrab()` | blocked get (a lock never released) | `irq_seq`: `ungrab()` after the ISR item |
| The test passes in 0 ns | nobody | — | not a hang: zero activity | test: raise before `seq.start()`, drop after |

One wrong fix in the model is a drain time, `phase.get_objection().set_drain_time(this, 100ns)` (§9.3.1.7.1, §10.5.1.3.7). Drain time starts only after the objection count reaches zero, so it cannot fix a count that never gets there. Older code may write the same call through `phase.phase_done`, a UVM 1.2 handle that IEEE 1800.2 does not define.

### Recap

- A hang is a run whose `run_phase` objection never reaches zero; `PH_TIMEOUT` bounds it, it never explains it.
- Collect three pieces of evidence in order: how it ended, who holds the objection, where each process waits.
- Follow the wait-for chain from the holder. It ends at the holder (objection never dropped), at a partner that will never act (blocked get), or back at the start (deadlock). Fix the owner, not the holder.
- A heartbeat catches silence within two windows; it cannot catch a component that stays busy for ever.
- A run that ends at 0 ns with no errors is the opposite failure, not a pass.

## Make It Work

### One bench, three hangs, one debug kit

The bench below drives 8 items through a one-stage pipeline DUT and checks every output against its input. A plusarg, `+HANG=<n>`, injects one of the three hang families:

| `+HANG=` | Bug injected | Family |
|---|---|---|
| 0 (default) | none: the run passes | — |
| 1 | the test also starts `poll_seq`, a background sequence with a `forever` body and an automatic phase objection | objection never dropped |
| 2 | `pkt_env` skips the connection from `out_mon` to the scoreboard's `act_fifo` | blocked get |
| 3 | the driver waits for `in_ready` before raising `in_valid` | deadlocked handshake |

- **breadcrumbs**: `note()` records, per component, what it is about to wait for;

// compile: hang_triage_tb.sv (IEEE 1800-2023, uvm-core 2020.3.1, one file)
`timescale 1ns/1ps

interface pkt_if (input logic clk);
  logic       rst_n;
  logic       in_valid, in_ready;
  logic [7:0] in_data;
  logic       out_valid;
  logic [7:0] out_data;
  clocking cb @(posedge clk);     // driver: in_ready sampled 1step before the edge
    output in_valid, in_data;
    input  in_ready;
  endclocking
  clocking mon_cb @(posedge clk); // monitors only sample
    input in_valid, in_ready, in_data, out_valid, out_data;
  endclocking
endinterface

module pkt_pipe (
  input  logic       clk, rst_n,
  input  logic       in_valid,
  input  logic [7:0] in_data,
  output logic       in_ready,
  output logic       out_valid,
  output logic [7:0] out_data
);
  // A receiver may wait for VALID before raising READY (Arm IHI0022E §A3.3.1
  // states this for AXI): in_ready is high for one cycle per accepted beat.
  always_ff @(posedge clk or negedge rst_n)
    if (!rst_n) begin
      in_ready  <= 1'b0;
      out_valid <= 1'b0;
      out_data  <= '0;
    end else begin
      in_ready  <= in_valid && !in_ready;
      out_valid <= in_valid && in_ready;  // a beat was accepted at this edge
      out_data  <= in_data;
    end
endmodule

package hang_pkg;
  import uvm_pkg::*;
  `include "uvm_macros.svh"

  // +HANG=<n> selects the injected bug (0 = none).
  function automatic int hang_mode();
    int m = 0;
    void'($value$plusargs("HANG=%d", m));
    return m;
  endfunction

  // Breadcrumbs: what each component is about to wait for.
  string where_now[string];
  function automatic void note(uvm_component c, string s);
    where_now[c.get_full_name()] = s;
  endfunction

  class pkt_item extends uvm_sequence_item;
    `uvm_object_utils(pkt_item)
    rand bit [7:0] data;
    function new(string name = "pkt_item");
      super.new(name);
    endfunction
  endclass

  class main_seq extends uvm_sequence #(pkt_item);
    `uvm_object_utils(main_seq)
    function new(string name = "main_seq");
      super.new(name);
    endfunction
    task body();
      repeat (8) begin
        req = pkt_item::type_id::create("req");
        start_item(req);
        if (!req.randomize()) `uvm_fatal("RAND", "pkt_item randomize failed")
        finish_item(req);
      end
    endtask
  endclass

  // A background "status poll" that is meant to run until the phase ends.
  class poll_seq extends uvm_sequence #(pkt_item);
    `uvm_object_utils(poll_seq)
    function new(string name = "poll_seq");
      super.new(name);
    endfunction
    task body();
      forever begin
        req = pkt_item::type_id::create("req");
        start_item(req);
        if (!req.randomize()) `uvm_fatal("RAND", "pkt_item randomize failed")
        finish_item(req);
      end
    endtask
  endclass

  class pkt_drv extends uvm_driver #(pkt_item);
    `uvm_component_utils(pkt_drv)
    virtual pkt_if vif;
    function new(string name, uvm_component parent);
      super.new(name, parent);
    endfunction
    function void build_phase(uvm_phase phase);
      if (!uvm_config_db#(virtual pkt_if)::get(this, "", "vif", vif))
        `uvm_fatal("NOVIF", "pkt_if not found in uvm_config_db")
    endfunction
    task run_phase(uvm_phase phase);
      vif.cb.in_valid <= 1'b0;
      wait (vif.rst_n === 1'b1);
      forever begin
        note(this, "idle in get_next_item()");
        seq_item_port.get_next_item(req);
        note(this, {"driving ", req.get_full_name()});
        @(vif.cb);                          // drive only at a clock edge
        if (hang_mode() == 3) begin
          note(this, {"waiting for in_ready before raising in_valid: ",
                      req.get_full_name()});
          @(vif.cb iff vif.cb.in_ready);    // BUG 3: VALID waits for READY
        end
        vif.cb.in_valid <= 1'b1;
        vif.cb.in_data  <= req.data;
        @(vif.cb iff vif.cb.in_ready);      // hold VALID until the DUT accepts
        vif.cb.in_valid <= 1'b0;
        seq_item_port.item_done();
      end
    endtask
  endclass

  class pkt_mon extends uvm_monitor;
    `uvm_component_utils(pkt_mon)
    virtual pkt_if vif;
    bit watch_out;                          // 0: accepted input beats, 1: output beats
    uvm_analysis_port #(pkt_item) ap;
    function new(string name, uvm_component parent);
      super.new(name, parent);
      ap = new("ap", this);
    endfunction
    function void build_phase(uvm_phase phase);
      if (!uvm_config_db#(virtual pkt_if)::get(this, "", "vif", vif))
        `uvm_fatal("NOVIF", "pkt_if not found in uvm_config_db")
    endfunction
    task run_phase(uvm_phase phase);
      forever begin
        @(vif.mon_cb);
        if (!watch_out && vif.mon_cb.in_valid && vif.mon_cb.in_ready)
          publish(vif.mon_cb.in_data);
        if (watch_out && vif.mon_cb.out_valid)
          publish(vif.mon_cb.out_data);
      end
    endtask
    function void publish(bit [7:0] d);
      pkt_item t = pkt_item::type_id::create("t");   // a new object per beat
      t.data = d;
      ap.write(t);
    endfunction
  endclass

  class pkt_scb extends uvm_scoreboard;
    `uvm_component_utils(pkt_scb)
    uvm_tlm_analysis_fifo #(pkt_item) exp_fifo, act_fifo;
    uvm_objection hb_obj;                   // set by pkt_env; the heartbeat watches it
    int unsigned matches, mismatches;
    function new(string name, uvm_component parent);
      super.new(name, parent);
    endfunction
    function void build_phase(uvm_phase phase);
      exp_fifo = new("exp_fifo", this);
      act_fifo = new("act_fifo", this);
    endfunction
    task run_phase(uvm_phase phase);
      pkt_item exp, act;
      forever begin
        note(this, "exp_fifo.get()");
        exp_fifo.get(exp);
        phase.raise_objection(this, "compare pending");  // hold the phase for in-flight beats
        note(this, "act_fifo.get()");
        act_fifo.get(act);
        if (exp.data == act.data) matches++;
        else begin
          mismatches++;
          `uvm_error("SCB", $sformatf("exp 'h%0h act 'h%0h", exp.data, act.data))
        end
        hb_obj.raise_objection(this);        // one heartbeat per compare
        hb_obj.drop_objection(this);
        phase.drop_objection(this, "compare done");   // reached on every path
      end
    endtask
    function void report_phase(uvm_phase phase);
      `uvm_info("SCB_SUMMARY", $sformatf("matches=%0d mismatches=%0d pending=%0d",
                matches, mismatches, exp_fifo.used()), UVM_NONE)
    endfunction
  endclass

  class pkt_agent extends uvm_agent;
    `uvm_component_utils(pkt_agent)
    uvm_sequencer #(pkt_item) sqr;
    pkt_drv drv;
    pkt_mon mon;
    function new(string name, uvm_component parent);
      super.new(name, parent);
    endfunction
    function void build_phase(uvm_phase phase);
      sqr = uvm_sequencer#(pkt_item)::type_id::create("sqr", this);
      drv = pkt_drv::type_id::create("drv", this);
      mon = pkt_mon::type_id::create("mon", this);
    endfunction
    function void connect_phase(uvm_phase phase);
      drv.seq_item_port.connect(sqr.seq_item_export);
    endfunction
  endclass

  class pkt_env extends uvm_env;
    `uvm_component_utils(pkt_env)
    pkt_agent agt;
    pkt_mon   out_mon;
    pkt_scb   scb;
    uvm_objection hb_obj;
    uvm_heartbeat hb;
    uvm_event #(uvm_object) hb_e;
    time hb_window = 100ns;                 // longer than the longest legal gap
    function new(string name, uvm_component parent);
      super.new(name, parent);
    endfunction
    function void build_phase(uvm_phase phase);
      agt     = pkt_agent::type_id::create("agt", this);
      out_mon = pkt_mon::type_id::create("out_mon", this);
      out_mon.watch_out = 1;
      scb     = pkt_scb::type_id::create("scb", this);
      hb_obj  = new("hb_obj");
      hb      = new("hb", this, hb_obj);    // cntxt = env: scb's beats pass through env
      hb_e    = new("hb_e");
    endfunction
    function void connect_phase(uvm_phase phase);
      agt.mon.ap.connect(scb.exp_fifo.analysis_export);
      if (hang_mode() != 2)                 // BUG 2 skips this connection
        out_mon.ap.connect(scb.act_fifo.analysis_export);
      scb.hb_obj = hb_obj;
    endfunction
    task run_phase(uvm_phase phase);
      uvm_component watched[$];
      watched.push_back(scb);
      void'(hb.set_mode(UVM_ALL_ACTIVE));
      hb.set_heartbeat(hb_e, watched);      // monitoring starts now
      forever begin
        #(hb_window);
        hb_e.trigger();                     // the first trigger only opens a window
      end
    endtask
  endclass

  // On PH_TIMEOUT or HBFAIL, print who holds the run objection and every
  // breadcrumb, then THROW: the fatal must still end the run and be counted.
  class hang_dump_catcher extends uvm_report_catcher;
    uvm_phase run_ph;                       // set by the test in run_phase
    function new(string name = "hang_dump_catcher");
      super.new(name);
    endfunction
    function action_e catch();
      if (get_severity() == UVM_FATAL && run_ph != null &&
          (get_id() == "PH_TIMEOUT" || get_id() == "HBFAIL")) begin
        uvm_object holders[$];
        uvm_objection run_obj = run_ph.get_objection();
        run_obj.get_objectors(holders);
        foreach (holders[i])
          if (run_obj.get_objection_count(holders[i]) > 0)  // own count: real holders only
            `uvm_info("HANG_DUMP", {"holds run_objection: ", holders[i].get_full_name()},
                      UVM_NONE)
        foreach (where_now[c])
          `uvm_info("HANG_DUMP", {c, " : ", where_now[c]}, UVM_NONE)
      end
      return THROW;
    endfunction
  endclass

  class hang_test extends uvm_test;
    `uvm_component_utils(hang_test)
    pkt_env env;
    hang_dump_catcher dump;
    function new(string name, uvm_component parent);
      super.new(name, parent);
    endfunction
    function void build_phase(uvm_phase phase);
      env = pkt_env::type_id::create("env", this);
      uvm_root::get().set_timeout(2us, 1);  // before run_phase starts (§9.8.1.5)
      dump = new("dump");
      uvm_report_cb::add(null, dump);       // null: every report object
    endfunction
    task run_phase(uvm_phase phase);
      main_seq seq = main_seq::type_id::create("main_seq");
      dump.run_ph = phase;
      phase.raise_objection(this, "stimulus");
      if (hang_mode() == 1) begin
        poll_seq poll = poll_seq::type_id::create("poll_seq");
        poll.set_starting_phase(phase);
        poll.set_automatic_phase_objection(1);  // BUG 1: forever body never drops
        fork
          poll.start(env.agt.sqr);
        join_none
      end
      seq.start(env.agt.sqr);
      env.hb.stop();                        // stimulus done: quiet is now legal
      phase.drop_objection(this, "stimulus done");
    endtask
  endclass
endpackage

### Guided exercise: diagnose each hang

Work through the three hangs in order. For each one, first **predict** from the table of bugs what the evidence will show, then read the evidence (the expected output above, or your own run), apply the method from Build Your Mental Model, and only then open the worked solution.

**The method, in five steps:**
1. **Ending.** Which fatal, at what time? `HBFAIL` names a silent component; `PH_TIMEOUT` names nothing.
2. **Holders.** Who still holds the run objection? Which holders are stuck and which are transient? (`+UVM_OBJECTION_TRACE` separates them.)
3. **Waits.** For each stuck holder, where does it wait (breadcrumb, sequencer, FIFO), and who would satisfy that wait?
4. **Chain end.** Follow step 3 until the chain ends at the holder, at a partner that will never act, or back at the start. That names the family and the owner.
5. **Fix and prove.** Change the owner, rerun the same seed and build, and check that the run ends on its own with the expected `SCB_SUMMARY`.

### How to triage any hang

1. **Never debug a hang at the default timeout.** Set an explicit, realistic `set_timeout()` in the base test's `build_phase`, so every hang fails fast and says "Explicit".
2. **Read the ending,** then the last meaningful message before it, not the last line.
3. **Rerun the same seed on the same build** with `+UVM_OBJECTION_TRACE` and `+UVM_PHASE_TRACE`. Plusargs need no rebuild, so the failure still reproduces exactly.
4. **Separate stuck holders from transient ones** by their raise and drop history.
5. **Follow the wait-for chain** from each stuck holder using breadcrumbs, `is_grabbed()`/`current_grabber()`, `get_current_item()`, `fifo.used()` and `port.size()`, until it ends.
6. **Name the family and the owner,** fix the owner, and rerun to prove the run now ends on its own with positive evidence of work.
7. **Lock it in:** add the check that would have caught it at elaboration or within one heartbeat window (a connection check, a heartbeat, a drop on every path).

**Checklist before moving on:**
- [ ] I can say which of `PH_TIMEOUT`, `HBFAIL` or a time-stopped job a log shows, and what each one means.
- [ ] I can find the stuck holder in an `OBJTN_TRC` log and tell it from a transient one.
- [ ] I can follow a wait-for chain from the holder to the owner, and name the family it ends in.
- [ ] I can explain why a longer timeout and a drain time never fix a hang.
- [ ] I can set up a `uvm_heartbeat` with a dedicated objection, a context above the watched component, a mode, and a `stop()` at the end of stimulus, and predict when it fires.
- [ ] I can tell a run that ended at 0 ns from a hang, and explain why neither is a pass.

## Push Further

### Expert: timeout, heartbeat or protocol watchdog

Three detectors, three different questions:

| Detector | Question it answers | Fires after | Blind spot |
|---|---|---|---|
| `set_timeout` (F.7.3.3, §9.8.1.5) | Did the whole run end by absolute time T? | T, whatever happened | Any hang shorter than T wastes the rest of T; useless while time is stopped |
| `uvm_heartbeat` (§10.6) | Did each watched component make progress in every window? | at most two windows of silence | A component that stays busy for ever (family 1); legal quiet periods longer than a window |
| A protocol watchdog (your own checker) | Did *this* transaction complete within N cycles? | N cycles after the stuck request | Only the protocol it watches |

Corner cases worth knowing:
- `set_timeout` must be set before `run_phase` starts (§9.8.1.5). In uvm-core 2020.3.1 the watchdog reads the value once, when `run_phase` starts, so a call from inside `run_phase` does not move a watchdog that is already counting.
- In uvm-core the first heartbeat trigger only opens a window, so worst-case detection is two windows. Beats count only if the heartbeat objection propagates through the context component (`uvm_heartbeat.svh`, `raised()` compares against the context). Any component below the context that raises `hb_obj` is added to the watched set from then on, and in `UVM_ALL_ACTIVE` mode it must keep beating in every later window (uvm-core implementation).
- `HBFAIL` is a fatal, so `check_phase` and `report_phase` do not run. If you want a report from the scoreboard on a heartbeat failure, have the hang dump print the scoreboard's counters.
- A heartbeat beat is an objection raise and drop that propagates up the hierarchy and runs callbacks. Beat once per transaction at most; on a busy, deep environment, beat once per N transactions.
- At SoC scale, a protocol watchdog per interface usually gives the earliest and most specific failure; the heartbeat is the generic safety net, and the timeout the last resort.

### Expert: deadlocks by design rules

Circular waits come from rules about who may wait for whom. Design them out:
- **Pin handshakes.** Arm IHI0022E §A3.3.1: the sender's VALID must not depend on the receiver's READY; the receiver may wait for VALID. The specification gives a cross-channel example too: a master must not wait for AWREADY before driving WVALID, because a slave may wait for WVALID before asserting AWREADY. A driver or a reactive responder that waits for the other side first can deadlock with any legal partner. Write VIP drivers so that every wait is on the partner's response, never on its permission to start.
- **Lock order across sequencers.** `lock()` returns only once the lock is granted (§14.2.5.5). If virtual sequence A locks `sqr_x` then `sqr_y`, while B locks `sqr_y` then `sqr_x`, each can end up holding one sequencer and waiting for the other. The evidence: no errors, `is_grabbed()` is 1 on both sequencers and `current_grabber()` names a different sequence on each. The fix is a global lock order (always `x` before `y`), or one coordinating sequence that owns both locks.
- **Request–response loops in the TB.** A sequence that waits for a response before sending the request that would trigger it, or a scoreboard that waits for a predictor which waits for the scoreboard's output, closes a loop entirely in software. Draw the wait-for chain at design review, not at 2 a.m.
- [B-AXI-5](/curriculum/T3_Advanced/B-AXI-5_AXI_Pitfalls_Interconnect_Deadlocks/index) and [B-AHB-2](/curriculum/T3_Advanced/B-AHB-2_AHB_Pitfalls_and_Deadlocks/index) cover protocol-level deadlocks in interconnects.

### Expert: hangs the watchdog cannot see

- **Zero-time loops.** In uvm-core 2020.3.1 the timeout watchdog is a `#` delay (`uvm_phase_hopper.svh`). A `forever` loop with no delay or event control, or two processes that keep waking each other in the same time slot, stop simulation time, so the watchdog never fires and no heartbeat trigger arrives either. Only the simulator's interactive stop, an iteration limit, or a wall-clock limit on the job ends it. All of those are tool-dependent or flow-dependent. Find the loop from the simulator's process or call stack when you stop it.
- **A combinational loop in the DUT** can oscillate in zero time in the same way. How it is reported (an iteration-limit error, a hang) is tool-dependent.
- **A hang before `run_phase`.** `build_phase` and `connect_phase` are functions and cannot block, so a hang before `run_phase` is usually a zero-time loop in one of them, or in an `initial` block before `run_test()`.
- **A deadlock that resolves itself** at the timeout is still a deadlock. If a test "passes" only because a driver times out its own wait and drops the item, the deadlock has become a silent loss of stimulus. Count such events and report them as errors.

### Expert: hang triage at regression scale

- **Signatures for hangs.** A hang's useful signature is not `PH_TIMEOUT` (every hang has it), but the stuck holder plus its breadcrumb or objection description, for example `PH_TIMEOUT | uvm_test_top.env.agt.sqr.poll_seq | automatic phase objection`. The hang dump prints exactly what a regression script needs to bucket hangs by owner. [Systematic Debug](/curriculum/T4_Expert/E-DBG-1_Advanced_UVM_Debug_Methodologies/effective-debug) teaches signatures and bucketing.
- **The catcher must THROW.** The hang dump returns `THROW`, so the fatal is still printed, counted and ends the run. A catcher that returned `CAUGHT` on `PH_TIMEOUT` would stop processing of the message (§6.5.1.2.14 a): nothing printed, nothing counted, no exit. In uvm-core the timeout branch of `run_phase` then simply finishes, so the run phase ends at the timeout, the later phases run, and the test can end with `UVM_FATAL :    0`: a hang turned into a green result. That is the "catcher that demotes errors is a fix" misconception in its most dangerous form.
- **Messages from inside a catcher** bypass catchers (`uvm_report_catcher::uvm_report_info`, §6.6.6), so the dump cannot recurse.
- **Rebuilds and reproduction.** A hang that vanishes after you rebuild with extra instrumentation has not been fixed: the rebuild can change the random draws (IEEE 1800-2023 §18.14.1 ties each thread's random sequence to its creation order). Rerun the same seed on the original build with plusarg-only visibility (`+UVM_OBJECTION_TRACE`, `+UVM_PHASE_TRACE`, `+uvm_set_verbosity`), and keep debug kits like this page's compiled into every build, switched by plusargs.

### Kata: name the family from the evidence

Three new hangs, from three different benches. For each one, name the stuck holder, follow the chain, name the family and the owner, and say what you would change. Write your answers down before you open the solution.

1. **Bench A.** `PH_TIMEOUT` at 5 ms. `OBJTN_TRC` shows `uvm_test_top` raised "stimulus" at 0 ns and never dropped. The driver's breadcrumb, since 200 ns: `idle in get_next_item()`. The sequence's code ends with `finish_item(req); get_response(rsp);`. The driver calls `item_done()` with no argument and never calls `put_response()`.
2. **Bench B.** `PH_TIMEOUT` at 5 ms. `OBJTN_TRC` shows `uvm_test_top.env.scb` raised "check" at 3.2 µs and never dropped; a `UVM_ERROR [SCB] length mismatch` was printed at 3.2 µs. The scoreboard's breadcrumb is `exp_fifo.get()`.
3. **Bench C.** `PH_TIMEOUT` at 5 ms, no errors. The virtual sequence `vseq_a` holds a run objection, and so does `vseq_b`. `sqr_x.is_grabbed()` is 1 and `sqr_x.current_grabber()` is `vseq_a`; `sqr_y.is_grabbed()` is 1 and `sqr_y.current_grabber()` is `vseq_b`. Both drivers are idle in `get_next_item()`.

1. **Bench A: blocked get (a missing partner).** Holder: the test, waiting for its sequence. The sequence waits in `get_response()`; the partner that should act is the driver, which completed the item with `item_done()` but never sent a response. The driver, idle and waiting for the next item, will never act. Owner: the driver (if the protocol has responses) or the sequence (if it does not). Fix: in the driver, `rsp.set_id_info(req); seq_item_port.item_done(rsp);`, or delete the `get_response()` call. [Sequencer-Driver Handshake](/curriculum/T2_Intermediate/I-UVM-3B_Advanced_Sequencing_and_Layering/sequencer-driver-handshake) lists this signature.
2. **Bench B: objection never dropped.** Holder: `scb`, and it is not blocked on its partner: its breadcrumb is `exp_fifo.get()`, the *top* of its loop. It raised "check", hit the length-mismatch error, and went back to the top of the loop without dropping: an early `continue` or `return` on the error path. Owner: the scoreboard. Fix: drop on every path, for example by moving the drop before the error report or into a single exit point. The breadcrumb is what proves it is not a blocked get: a blocked scoreboard would be in `act_fifo.get()`.
3. **Bench C: deadlock (lock order).** Holders: both virtual sequences. `vseq_a` holds `sqr_x` and, by its code, waits in `lock(sqr_y)`; `vseq_b` holds `sqr_y` and waits in `lock(sqr_x)`. The chain loops: a waits for b, b waits for a. Owner: the virtual sequences' design. Fix: every sequence takes locks in one global order (`sqr_x` before `sqr_y`), or one coordinating sequence owns both locks.
