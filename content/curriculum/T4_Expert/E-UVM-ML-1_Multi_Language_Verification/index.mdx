## Quick Take

- **What it is:** **Multi-language verification** means running models and verification components written in different languages (SystemVerilog and UVM, C or C++, SystemC, sometimes *e*) in one simulation, so that they exchange transactions. There are three ways across the **language boundary**: call C or C++ functions through **DPI**, connect a SystemC model's transaction-level sockets through a **bridge** library, or run a separate program and **co-simulate** over a link. UVM's own transaction-level interface for that boundary is **UVM TLM-2**: the **generic payload**, `b_transport` and `nb_transport`, and **sockets** (IEEE 1800.2-2020 §12.3).
- **Why it matters:** Architecture teams often deliver SystemC models, and algorithm teams deliver C++. Reusing one of those as the **reference model** behind your scoreboard (milestone M3) saves writing a second model that can drift from the first, and a model written by another team exposes ambiguous specifications. The price is a boundary that you have to choose, build and debug, plus libraries whose origin and support status you must check before you depend on them.
- **The Analogy:** A container port. The generic payload is the standard shipping container that fits every ship; sockets are the berths; a bridge library is the customs office that unpacks a SystemC container and repacks it as a SystemVerilog one. *Where it breaks:* two real ports share one calendar, but two simulation kernels each keep their own clock and their own working days (phases). Someone must decide whose clock counts and who announces the end of the day (end of test), and the container does not carry the clock with it: timing travels as a separate annotation.

**You will be able to:**
1. Choose DPI, a TLM-2 bridge or co-simulation to connect a C/C++ or SystemC model to a UVM bench, and justify the choice by model type, time ownership, tool support and cost.
2. Write a blocking UVM TLM-2 transport between an initiator socket and a target socket with the generic payload, and predict the phases and return values of a non-blocking transport (IEEE 1800.2-2020 §12.3).
3. Explain how a bridge (UVM Connect, UVM-ML OA) registers, connects and converts transactions and coordinates phases, and state each library's origin, support status and limits from dated sources.
4. Plan a mixed-language bench (time and end-of-test ownership, conversion points, build flow) and debug a failed connection or a garbled transaction.

## Build Your Mental Model

**How to read this lesson.** The core path is the first three sections: the three ways across a boundary, UVM TLM-2 in one page, and how UVM TLM-2 differs from SystemC's. Practitioner depth follows: how a bridge connects the two sides, time and end of test, planning, and debugging. Make It Work builds a bench you can run with only a SystemVerilog simulator and a C++ compiler, and Push Further holds the expert layer.

This lesson assumes two prerequisites. From [I-SV-7](/curriculum/T2_Intermediate/I-SV-7_DPI_and_Foreign_Language_Interfaces/index) you know DPI: an `import "DPI-C"` declaration lets SystemVerilog call a C function, and an imported function runs in zero simulated time. From [I-UVM-2B](/curriculum/T2_Intermediate/I-UVM-2B_TLM_Connections/index) you know TLM-1: ports, exports and imps, connected in `connect_phase`. A **reference model** is code that computes what the design under test (DUT) should produce, so that a scoreboard can compare ([A-UVM-6](/curriculum/T3_Advanced/A-UVM-6_Scoreboards_and_Reference_Models/index)).

### Three ways across a language boundary

A **language boundary** is any point where a call or a transaction passes from SystemVerilog to code compiled from another language. Each side has its own types, its own memory, and possibly its own **simulation kernel**: the scheduler that runs processes and advances simulated time. How much of that the two sides share decides which connection you need.

Two more terms first:
- **SystemC** is a C++ class library with its own event-driven simulation kernel, used to model hardware and systems; it is standardized as IEEE 1666. Its **TLM-2.0** part (transaction-level modelling) defines how models exchange memory-mapped transactions through sockets. TLM-1 and TLM-2.0 have been part of IEEE 1666 since 1666-2011, and the current revision is IEEE 1666-2023.
- **Co-simulation** means two separately running simulators or programs, for example an instruction-set simulator (**ISS**) or a model running as its own process, that exchange data and synchronize time over a link.

**Option 1: DPI.** You wrap the model in C-linkage functions and import them (I-SV-7). It is part of the SystemVerilog standard (IEEE 1800-2023 Clause 35), it needs no extra library, and it is the cheapest crossing. Its limits come from the same rules: an imported function completes in zero simulated time (§35.5.1.1), there are no sockets or phases, and the C side has no processes of its own that the simulator schedules. A C++ exception must never escape the wrapper (§35.5.1.6).

**Option 2: a TLM-level bridge.** The model is a SystemC module with TLM-2.0 sockets and its own SystemC processes. A simulator that supports SystemC runs its kernel next to the SystemVerilog one, and a bridge library connects a UVM socket to the SystemC socket and converts each transaction between the two languages' payload classes. The bridge libraries are not IEEE standards; each is **implementation-specific** (later in this section).

**Option 3: co-simulation.** The model runs as its own program, or in another simulator, and a proxy component in the bench exchanges messages with it. Both sides keep their own notion of time, so the link must synchronize them. For simulation co-simulation the link is project- or tool-specific; emulators are the exception, with Accellera SCE-MI defining the host link ([E-EMU-1](/curriculum/T4_Expert/E-EMU-1_Emulation_Aware_Verification/index)). Note that an ISS can also be built as a library and stepped through DPI, as in [E-RISCV-1](/curriculum/T4_Expert/E-RISCV-1_RISC_V_Verification_Methodology/index): then it is option 1, not option 3.

**Can I get away with DPI alone?** That is the first question to ask, and the answer depends on the model, not on taste.

| Situation | Languages | Usual choice |
|---|---|---|
| Algorithm check: a C++ codec, CRC or math model computes expected output per transaction | SV + C/C++ | DPI from the predictor. The model is a function of its inputs and owns no time. |
| Architecture model reuse: a SystemC TLM-2.0 model of a controller or interconnect, with its own threads and sockets | SV + SystemC | A bridge, so the model's sockets and processes run unchanged in the SystemC kernel. |
| Legacy verification IP: an existing *e* or SystemC verification component joins a new UVM bench | SV + *e* or SystemC | A bridge that also coordinates hierarchy and phases (UVM-ML OA supports *e*; UVM Connect does not). |
| A separate executable, another simulator, or hardware in the loop | SV + anything | Co-simulation over a link, or DPI to a library build of the same program. |

The decision in full:

| Question | DPI | TLM-level bridge | Co-simulation |
|---|---|---|---|
| What shape is the model? | Functions, untimed | SystemC module with sockets and processes | Separate program, ISS or simulator |
| Who owns time? | SystemVerilog only; C runs in zero time | Both kernels, in one simulation run (tool-dependent) | Each side; the link synchronizes them |
| What is standard? | IEEE 1800-2023 Clause 35 | UVM TLM-2 (1800.2 §12.3) and SystemC TLM-2.0 (IEEE 1666) at the ends; the bridge is a library | Project- or tool-specific |
| Hierarchy, configuration, phases | None | UVM-ML OA: unified hierarchy, configuration and phase coordination; UVM Connect: a command interface for phases and objections | You build them |
| Cost | Lowest crossing cost and tool needs | Needs a simulator with SystemC support and a bridge; measure the crossing cost | Highest integration and debug cost |
| Debug | One process; C debugger attaches to the simulator | Two languages in one process; library trace commands (tool-dependent) | Two processes, two logs |

**The classic mistakes.**
- *"DPI is always sufficient."* For a function-shaped model, yes. For a SystemC model with its own threads and sockets, DPI alone means writing your own glue: Cadence's 2018 comparison had to hand-write a global `extern "C"` function that built a SystemC payload, located the module with `sc_find_object`, and called its socket, plus a `friend` declaration in the model. The bridge exists to remove that glue.
- *"Use DPI with C threads and callbacks."* DPI defines nothing for threads that your C code starts. The standard calls DPI scope and export use from outside an import call chain "simulator defined" and beyond the DPI specification (§35.5.3). The portable pattern keeps worker threads inside C behind a queue that a `context` import polls; see [I-SV-7, Expert: Reentrancy, C threads and blocking](/curriculum/T2_Intermediate/I-SV-7_DPI_and_Foreign_Language_Interfaces/index#expert-reentrancy-c-threads-and-blocking).

### UVM TLM-2 in one page

TLM-1 ([I-UVM-2B](/curriculum/T2_Intermediate/I-UVM-2B_TLM_Connections/index)) moves any transaction type in one direction. **UVM TLM-2** (IEEE 1800.2-2020 §12.3) is the memory-mapped variant, modelled on SystemC's TLM-2.0. It is what you meet at a SystemC boundary, because a bridge connects a UVM TLM-2 socket to a SystemC TLM-2.0 socket. Four ideas make it up.

**1. The generic payload** (`uvm_tlm_generic_payload`, short name `uvm_tlm_gp`, §12.3.4.2) is one transaction class for any memory-mapped read or write. It `extends uvm_sequence_item`, so you can randomize it and send it through sequencers too. Use its accessor methods rather than the `m_` member variables, which exist for constraints (§12.3.4.2.6).

| Attribute | Accessors | Rule (1800.2 §12.3.4.2.7 to §12.3.4.2.14) |
|---|---|---|
| command | `set_command`, `set_write`, `set_read`, `get_command` | `UVM_TLM_READ_COMMAND`, `UVM_TLM_WRITE_COMMAND` or `UVM_TLM_IGNORE_COMMAND` (§12.3.4.1.1). Set by the initiator only. |
| address | `set_address`, `get_address` | 64-bit start address. A target that cannot use it returns `UVM_TLM_ADDRESS_ERROR_RESPONSE`. |
| data | `set_data`, `get_data` | A `byte unsigned` dynamic array. The initiator supplies it, also for a read; the target overwrites it only for a read. |
| data length | `set_data_length`, `get_data_length` | Number of bytes to transfer. Never 0; to move nothing, use the ignore command. |
| byte enables | `set_byte_enable`, `set_byte_enable_length` | `8'hFF` enables a byte, `8'h00` disables it. An empty array means byte enables are not used. |
| streaming width | `set_streaming_width` | Bytes per beat for a stream to one address; 0 means no streaming. |
| response status | `set_response_status`, `is_response_ok`, `get_response_string` | The initiator sets `UVM_TLM_INCOMPLETE_RESPONSE`; the target replaces it with OK or one of five errors (§12.3.4.1.2). |
| extensions | `set_extension`, `get_extension` | Extra attributes in classes derived from `uvm_tlm_extension` (§12.3.4.5). |

The response status rule is the one that catches people. `UVM_TLM_INCOMPLETE_RESPONSE` means "never reached a target", and the target "shall be responsible" for replacing it before `b_transport` returns (§12.3.4.2.11). The constructor sets that default (uvm-core 2020.3.1, `uvm_tlm2_generic_payload.svh`).

**2. Sockets** (§12.3.5) replace port and imp pairs. A socket "is like a port or export", derived from the same `uvm_port_base`, but it carries both a forward and a backward path. Each socket has three attributes, which give eight classes: **initiator** or **target** (who starts the transaction), **blocking** or **non-blocking** (which transport it carries), and **terminator** or **pass-through** (ends the path, or carries it across a hierarchy boundary). An initiator socket connects to a target socket, never the reverse, and you never call `connect` on a target terminator socket (§12.3.5.1.4).

| You want | Initiator side | Target side | The target class implements |
|---|---|---|---|
| Blocking | `uvm_tlm_b_initiator_socket #(T)` | `uvm_tlm_b_target_socket #(IMP, T)` | `task b_transport(T t, uvm_tlm_time delay)` |
| Non-blocking | `uvm_tlm_nb_initiator_socket #(IMP, T, P)` | `uvm_tlm_nb_target_socket #(IMP, T, P)` | target: `nb_transport_fw`; initiator: `nb_transport_bw` |

`T` defaults to `uvm_tlm_generic_payload` and `P` to `uvm_tlm_phase_e`. Construct sockets with `new` in `build_phase`, like any port. The `imp` argument of a target socket defaults to the parent component (§12.3.5.1.3).

**3. Blocking transport.** `b_transport(t, delay)` executes the whole transaction in one task call (§12.3.2.2.3). The call marks the transaction's first timing point and the return marks its last. The **timing annotation** `delay` "allows the timing points to be offset from the simulation times at which the task call and return are executed". So a target can report "this took 10 ns" by adding to `delay` and return at once, without waiting. This is the **loosely-timed (LT)** style: a model reports its latency instead of spending it. `delay` is a `uvm_tlm_time` object, a class with `incr`, `decr`, `get_realtime` and `get_abstime` (`typedef uvm_time uvm_tlm_time`, §5.6), so the target's change is visible to the caller.

**4. Non-blocking transport** spreads one transaction over several calls, `nb_transport_fw` from initiator to target and `nb_transport_bw` back, each carrying a **TLM phase** (`BEGIN_REQ`, `END_REQ`, `BEGIN_RESP`, `END_RESP`, §12.3.3.1) and returning a **sync value**: `UVM_TLM_ACCEPTED`, `UVM_TLM_UPDATED` or `UVM_TLM_COMPLETED` (§12.3.3.2). A TLM phase is a step in one transaction's protocol; it has nothing to do with UVM phases such as `run_phase`. Push Further walks through it; the blocking form is what most reference models use.

**What the diagram shows.** The call and return happen at 0 ns, and so does the DPI call inside it (§35.5.1.1). The annotation is not a wait: `b_transport` may consume time if the target chooses to wait, but this one does not. The caller decides what to do with the 10 ns. This client waits it out, so its log lines are 10 ns apart. A faster, **temporally decoupled** client would keep adding annotations and synchronize later.

**The classic mistakes.**
- *Reading the annotation as a delay that already happened.* It is an offset from the call time (§12.3.2.2.3), and somebody must still act on it.
- *Forgetting the response status.* If the target never calls `set_response_status`, the client sees `INCOMPLETE` even though the data moved. Always check `is_response_ok()` after `b_transport` returns.
- *Data length larger than the data array.* The payload's `do_pack` raises a fatal error when the array is shorter than the length (§12.3.4.2.4), and a target that indexes the array blindly goes out of range. Check both before use.
- *Passing a `null` delay.* uvm-core reports `UVM/TLM/NULLDELAY` and drops the call (uvm-core impl., `uvm_tlm2_imps.svh`). Create a `uvm_tlm_time` for every call or reuse one deliberately.
- *Expecting read data to appear in your own array.* `set_data` copies the array into the payload (dynamic-array assignment copies, IEEE 1800-2023 §7.6), so read data arrives only in the payload's copy: call `get_data` after the call returns. SystemC differs here; see the next section.

The initiator may reuse one payload object across calls (§12.3.2.2.3), but then it must reset the status and every attribute it relies on before each call.

### UVM TLM-2 is not SystemC TLM-2.0

IEEE 1800.2-2020 says that UVM's TLM facilities "are based on what was developed by Open SystemC Initiative (OSCI) for SystemC, though they are not an exact replication or re-implementation of the SystemC TLM library" (Introduction). So a UVM socket cannot be bound straight to a SystemC socket: they are different classes in different languages, with different time types. A bridge converts.

| | UVM TLM-2 (IEEE 1800.2-2020 §12.3) | SystemC TLM-2.0 (IEEE 1666; awareness level) |
|---|---|---|
| Payload class | `uvm_tlm_generic_payload`, a `uvm_sequence_item` | `tlm::tlm_generic_payload`, a plain C++ class |
| Data | A dynamic array inside the payload; `set_data` copies | A pointer to memory the initiator owns (`set_data_ptr`); the target writes through it |
| Time | `uvm_tlm_time`, a class handle | `sc_time`, passed by reference |
| Interface methods | `b_transport`, `nb_transport_fw`, `nb_transport_bw` only (`uvm_tlm_if`, §12.3.2) | The same three, plus direct memory interface (DMI) and debug transport |
| Enum names | `UVM_TLM_OK_RESPONSE`, `BEGIN_REQ`, `UVM_TLM_ACCEPTED` | `tlm::TLM_OK_RESPONSE`, `tlm::BEGIN_REQ`, `tlm::TLM_ACCEPTED` |
| Kernel | The SystemVerilog scheduler | The SystemC kernel |

SystemC TLM-2.0 also names two **coding styles**: **loosely-timed (LT)**, which uses `b_transport` with timing annotations and suits fast reference models, and **approximately-timed (AT)**, which uses `nb_transport` phases to model pipelining and contention. A reference model handed to a verification team is usually LT, which is why the blocking path is the one to master first. (This lesson cites no IEEE 1666 clause numbers: they were not verified for it.)

UVM keeps a DMI *hint* in the payload (`set_dmi_allowed`, §12.3.4.2.34) but has no DMI interface. A SystemC model that relies on DMI for speed falls back to normal transport across a UVM bridge, or the bridge must handle it: check the library's documentation.

### Practitioner depth: how a bridge connects the two sides

Every TLM bridge does the same four jobs: it **registers** sockets on both sides, **connects** each pair, **converts** each transaction between the two payload classes, and lets the two sides agree on **phases** and end of test. The libraries differ in how. Everything in this section is **implementation-specific**: it describes libraries, not IEEE standards, and each item names its source and version.

**UVM Connect (UVMC).** A library from Mentor Graphics, now Siemens EDA, introduced in February 2012 and distributed as open source under the Apache 2.0 licence; the 2.2 release was also posted to Accellera's contributions file area. The latest release whose notes were checked for this lesson is 2.3.2 (November 2019); its notes say the kit is intended to work with Questa, VCS and IUS and has not been verified on other simulators. It provides TLM-1 and TLM-2 connections and object passing between SystemC and SystemVerilog, built on DPI-C. It is *not* a Synopsys product, a misattribution that still circulates.
- *Connect:* SystemVerilog calls `uvmc_tlm #(T, CVRT)::connect(port, "lookup")`; SystemC calls `uvmc_connect(port, "lookup")` (or `uvmc_connect<CVRT>`). **Lookup strings** are global across both languages; two registered ports with the same string are connected.
- *When:* "just before UVM's end_of_elaboration phase", and transactions are blocked until UVM reaches `run_phase`. An incompatible pair, or a registered port with no match, is an error during elaboration.
- *Convert:* converters for the TLM generic payload are predefined; other transaction types need a converter class, the `CVRT` parameter.
- *Phases:* the **UVM Command API** lets SystemC code (from an `SC_THREAD`) wait for a UVM phase (`uvmc_wait_for_phase`), raise and drop objections (`uvmc_raise_objection`, `uvmc_drop_objection`), and set configuration. The SystemVerilog side must call `uvmc_init` for the commands to work.
- *Not covered:* *e* (Cadence 2018 notes this).

**UVM-ML Open Architecture (UVM-ML OA).** A library originally developed by Cadence Design Systems and AMD, open source since 2012, distributed through Accellera's community downloads and shipped inside Cadence Xcelium installations (Cadence, DVCon Europe 2018). It joins **frameworks** (UVM-SV, UVM-SystemC, UVM-*e*) through **adapters** to a central **backplane**, a hub that knows the whole topology. Its listed features are TLM-1 and TLM-2 communication (including analysis ports in recent releases), coordinated bring-up and phase synchronization, a **unified hierarchy** (a SystemC component instantiated under a UVM-SV component), multi-language configuration created in the top framework and propagated to the others, and multi-language sequence layering. It is not an Accellera standard. The latest release used in published work found for this lesson is 1.9 (both 2018 papers; reference and user guides dated December 2017), and Accellera's Multi-Language Working Group page described the group as "currently inactive" when checked on 11 October 2026.
- *Run:* `import uvm_ml::*;` after `uvm_pkg` and the macros, then start the test with `uvm_ml_run_test(tops)` instead of `run_test()`.
- *Register:* SystemVerilog sockets in `phase_ended()` of the build phase with `uvm_ml::ml_tlm2#()::register(sock)`; SystemC sockets with `ML_TLM2_REGISTER_TARGET(...)`, which returns the socket's full path.
- *Connect:* in `connect_phase`, `void'(uvm_ml::connect(sock.get_full_name(), "<SystemC path>"))`. A call from a time-0 `initial` block runs before the components exist and connects nothing.
- *Convert:* objects are serialized with packing routines, usually from the UVM field macros; the registration order must match on both sides, and `uvm_ml::set_type_match("sv:...", "sc:...")` pairs classes whose names differ.

**Vendor interfaces.** Simulator vendors also ship their own SystemC–SystemVerilog transaction interfaces, for example the VCS TLI described in a Doulos SNUG 2012 paper. Their APIs differ from both libraries above: use the vendor's manual.

**UVM-SystemC is not a bridge.** UVM-SystemC is UVM written *in* SystemC by Accellera's SystemC verification group (reference implementation on GitHub, Apache 2.0, release 1.0-beta6 on 1 July 2024). It lets you write UVM-style components in C++; connecting them to a SystemVerilog bench still needs a bridge. Its components take one constructor argument, a `uvm_component_name`, and its `uvm_analysis_imp<T, IMP>` is a member constructed with `(name, this)`, not a base class.

### Practitioner depth: time, phases and end of test across languages

A mixed bench has two schedulers. Three questions decide whether it behaves.

1. **Who owns time?** With DPI, only SystemVerilog does. With a SystemC bridge, both kernels advance one simulated time inside one simulator; how they interleave is tool-dependent. Timing annotations let an LT model report latency without forcing either kernel to stop.
2. **Which phases are coordinated?** UVM-ML OA coordinates bring-up and phases so that "components are configured then created, and ports are created then connected" (Cadence 2018). Synchronizing the UVM **run-time sub-phases** (`reset_phase` through `shutdown_phase`) with another framework is a different matter: HPE reported it "not supported" up to UVM-ML OA 1.8 and supported in 1.9 only on Cadence Xcelium, and built its own objection-based synchronizer (Pertuit et al., DVCon US 2018). Whether an objection raised on one side holds `run_phase` on the other is a property of the library, its version and the simulator. Check the release notes and test it; do not assume it.
3. **Who ends the test?** UVM ends `run_phase` when the last objection drops ([I-UVM-1C](/curriculum/T2_Intermediate/I-UVM-1C_UVM_Phasing/index)). If the SystemC model is still working and nothing on its behalf holds an objection, the SystemVerilog side can end the test under it.

### Practitioner depth: planning a mixed-language bench

Before writing code, write the plan down. It is short, and every line prevents a class of bug.

| Plan item | Decide | Example for a SystemC LT reference model |
|---|---|---|
| Boundary | Where transactions cross, and in which type | Predictor → generic payload → model's target socket |
| Option and library | DPI, which bridge and version, or co-simulation | UVMC 2.3.x on the team's simulator, checked in the release notes |
| Time owner | Whose clock counts, and how annotations are used | SystemVerilog; the model annotates latency, the predictor ignores it |
| End-of-test owner | Who holds the last objection | The test; every `b_transport` returns before it drops |
| Conversion points | Payload converters, field order, byte order | Predefined GP converter; data bytes little-endian on both sides |
| Build flow | Compilers, libraries, link order, versions | SystemC built by the simulator's flow; model library version printed at time 0 |
| Debug plan | Trace switches, logs, how to correlate them | Library trace on; both sides log a transaction id |
| Fallback | What runs if the bridge is unavailable on a tool | A DPI wrapper around the same model, kept compiling |

### Practitioner depth: debugging a mixed-language bench

| Symptom | Likely cause | Fix |
|---|---|---|
| `Connection Error`: "connection count of 0 does not meet required minimum of 1" for a socket | A pure-SV socket was never connected, or a bridge connection did not happen | Check the `connect` call. With UVMC, compare lookup strings character by character; with UVM-ML OA, check registration in `phase_ended` of build and the SystemC path |
| Elaboration error from the bridge about an unmatched or incompatible port | Lookup strings differ, or the payload or interface types differ on the two sides | Same string, same transaction type, compatible directions; message text is library-dependent |
| Status `INCOMPLETE` after `b_transport` returns | The target never set the response status, or the transaction never reached a target | Set the status on every path in the target; check `is_response_ok()` in the initiator |
| Fields arrive scrambled or shifted | Byte order or field order differs between the two sides' packing | Write one packing convention down and test it with a known pattern; see Expert: Data conversion |
| The test ends while the SystemC model is busy | No objection covers the model's work | Make the SV side wait for responses, or raise objections from SystemC through the bridge |
| Simulation freezes | A C or C++ call blocks (a socket read, a lock, an endless loop): while C runs, no SystemVerilog process runs | Make C calls non-blocking; let time pass in SystemVerilog between polls (I-SV-7) |
| The simulator crashes inside the model | A C++ exception crossed the DPI boundary (undefined behaviour, §35.5.1.6), or a pointer outlived its call | Catch everything in the `extern "C"` wrapper; copy pass-by-reference data you keep (Annex H.8.4) |

### Recap

- Three options: **DPI** for function-shaped models, a **bridge** for SystemC TLM-2.0 models with sockets and processes, **co-simulation** for separate programs. Start by asking whether DPI is enough.
- **UVM TLM-2** (§12.3): the generic payload with its status rule, sockets with three attributes, `b_transport` with a timing annotation that is not a wait, and `nb_transport` with phases and sync values.
- UVM TLM-2 is modelled on SystemC TLM-2.0 but "not an exact replication": a bridge converts payloads and time.
- **UVM Connect** (Mentor, now Siemens EDA; Apache 2.0) and **UVM-ML OA** (Cadence and AMD; last verified release 1.9) are libraries, not standards. Their support differs by simulator and version.
- Plan time ownership and end-of-test ownership first; most mixed-bench bugs are a missing connection, a packing mismatch or an orphaned objection.

## Make It Work

### Worked example: one C++ reference model behind a UVM TLM-2 target

This bench needs only a SystemVerilog simulator with UVM and DPI, and a C++ compiler. A C++ reference model, a small register space, sits behind an `extern "C"` wrapper. A UVM component, `ref_mem_target`, owns a blocking target socket and calls the model through DPI inside `b_transport`. A second component, `ref_client`, sends generic payloads through an initiator socket. There is no DUT: the point is the boundary. Because the model already sits behind a TLM-2 target socket, Part C can replace that target by a SystemC model without touching the client.

```cpp
// compile: ref_mem.cpp, built into a shared library (see "Run it")
#include <cstdint>
#include <map>
#include <stdexcept>

namespace {
// The reference model: a sparse 4 KB register space owned by C++.
class RefMem {
 public:
  void write(uint32_t addr, uint32_t data) { check(addr); mem_[addr] = data; }
  uint32_t read(uint32_t addr) const {
    check(addr);
    auto it = mem_.find(addr);
    return it == mem_.end() ? 0u : it->second;
  }

 private:
  static void check(uint32_t addr) {
    if (addr >= 0x1000u) throw std::out_of_range("address outside model");
  }
  std::map<uint32_t, uint32_t> mem_;
};

RefMem g_model;  // one model per simulation (see Expert: Debugging at scale)
}  // namespace

// C linkage at the boundary; no exception may cross it (IEEE 1800-2023 §35.5.1.6).
extern "C" int ref_mem_write(unsigned int addr, unsigned int data) {
  try {
    g_model.write(addr, data);
    return 0;
  } catch (...) {
    return 1;
  }
}

// An output argument of type int unsigned arrives as unsigned int* (Annex H).
extern "C" int ref_mem_read(unsigned int addr, unsigned int* data) {
  try {
    *data = g_model.read(addr);
    return 0;
  } catch (...) {
    *data = 0u;  // always write outputs: their initial value is undetermined
    return 1;
  }
}
```

```systemverilog
// compile: tb_top.sv (UVM 1800.2 library, plus the ref_mem shared library)
`timescale 1ns/1ps

package mlx_pkg;
  import uvm_pkg::*;
  `include "uvm_macros.svh"

  // Not pure: the model keeps state between calls (§35.5.2).
  import "DPI-C" function int ref_mem_write(input int unsigned addr,
                                            input int unsigned data);
  import "DPI-C" function int ref_mem_read(input  int unsigned addr,
                                           output int unsigned data);

  // Target: the only class that knows a C++ model sits behind the socket.
  class ref_mem_target extends uvm_component;
    `uvm_component_utils(ref_mem_target)

    uvm_tlm_b_target_socket #(ref_mem_target) sock;

    function new(string name, uvm_component parent);
      super.new(name, parent);
    endfunction

    function void build_phase(uvm_phase phase);
      super.build_phase(phase);
      sock = new("sock", this);  // imp defaults to the parent: this class
    endfunction

    // Called through sock. No simulated time passes in here: the model's
    // latency is reported through the annotation instead (loosely timed).
    task b_transport(uvm_tlm_generic_payload t, uvm_tlm_time delay);
      byte unsigned bytes[];
      bit [31:0]    addr, word;
      int           err;

      t.get_data(bytes);
      if (t.get_byte_enable_length() != 0) begin
        t.set_response_status(UVM_TLM_BYTE_ENABLE_ERROR_RESPONSE);
        return;
      end
      if (t.get_data_length() != 4 || bytes.size() < 4) begin
        t.set_response_status(UVM_TLM_GENERIC_ERROR_RESPONSE);
        return;
      end

      addr = 32'(t.get_address());
      err  = 0;
      case (t.get_command())
        UVM_TLM_WRITE_COMMAND: begin
          for (int i = 0; i < 4; i++) word[8*i +: 8] = bytes[i];  // little-endian
          err = ref_mem_write(addr, word);
        end
        UVM_TLM_READ_COMMAND: begin
          err = ref_mem_read(addr, word);
          for (int i = 0; i < 4; i++) bytes[i] = word[8*i +: 8];
          t.set_data(bytes);  // set_data copies the array into the payload
        end
        default: ;  // UVM_TLM_IGNORE_COMMAND: nothing to execute
      endcase

      delay.incr(10ns, 1ns);  // the model's latency: an annotation, not a wait
      t.set_response_status(err == 0 ? UVM_TLM_OK_RESPONSE
                                     : UVM_TLM_ADDRESS_ERROR_RESPONSE);
    endtask
  endclass

  // Initiator: builds one generic payload per access and checks its status.
  class ref_client extends uvm_component;
    `uvm_component_utils(ref_client)

    uvm_tlm_b_initiator_socket #() sock;

    function new(string name, uvm_component parent);
      super.new(name, parent);
    endfunction

    function void build_phase(uvm_phase phase);
      super.build_phase(phase);
      sock = new("sock", this);
    endfunction

    task access(uvm_tlm_command_e cmd, bit [31:0] addr,
                inout bit [31:0] word, output bit ok);
      uvm_tlm_generic_payload gp;
      uvm_tlm_time            delay;
      byte unsigned           bytes[];

      gp    = uvm_tlm_generic_payload::type_id::create("gp");
      delay = new("delay");
      bytes = new[4];
      for (int i = 0; i < 4; i++) bytes[i] = word[8*i +: 8];  // little-endian

      gp.set_command(cmd);
      gp.set_address(addr);
      gp.set_data(bytes);
      gp.set_data_length(4);
      gp.set_streaming_width(4);
      gp.set_byte_enable_length(0);                         // no byte enables
      gp.set_response_status(UVM_TLM_INCOMPLETE_RESPONSE);  // §12.3.4.2.11

      sock.b_transport(gp, delay);

      ok = gp.is_response_ok();
      gp.get_data(bytes);  // read data lives in the payload's own copy
      for (int i = 0; i < 4; i++) word[8*i +: 8] = bytes[i];
      `uvm_info("CLIENT", $sformatf("%s addr=0x%0h data=0x%08h status=%s delay=%0.0f ns",
                cmd.name(), addr, word, gp.get_response_string(),
                delay.get_abstime(1.0e-9)), UVM_LOW)
      #(delay.get_realtime(1ns));  // honour the annotation before the next access
    endtask
  endclass

  class mlx_env extends uvm_env;
    `uvm_component_utils(mlx_env)

    ref_client     client;
    ref_mem_target target;

    function new(string name, uvm_component parent);
      super.new(name, parent);
    endfunction

    function void build_phase(uvm_phase phase);
      super.build_phase(phase);
      client = ref_client::type_id::create("client", this);
      target = ref_mem_target::type_id::create("target", this);
    endfunction

    function void connect_phase(uvm_phase phase);
      client.sock.connect(target.sock);  // initiator socket -> target socket
    endfunction
  endclass

  class mlx_test extends uvm_test;
    `uvm_component_utils(mlx_test)

    mlx_env env;
    int     pass_count, fail_count;

    function new(string name, uvm_component parent);
      super.new(name, parent);
    endfunction

    function void build_phase(uvm_phase phase);
      super.build_phase(phase);
      env = mlx_env::type_id::create("env", this);
    endfunction

    // Not named check(): uvm_component already has a virtual check() (OVM compatibility).
    function void expect_true(string what, bit cond);
      if (cond) pass_count++;
      else begin
        fail_count++;
        `uvm_error("TEST", {"check failed: ", what})
      end
    endfunction

    task run_phase(uvm_phase phase);
      bit [31:0] word;
      bit        ok;

      phase.raise_objection(this);
      word = 32'hCAFE_F00D;
      env.client.access(UVM_TLM_WRITE_COMMAND, 32'h10, word, ok);
      expect_true("write 0x10 status", ok);

      word = '0;
      env.client.access(UVM_TLM_READ_COMMAND, 32'h10, word, ok);
      expect_true("read 0x10 returns the written word", ok && word == 32'hCAFE_F00D);

      word = '0;  // outside the model: the target must report an error
      env.client.access(UVM_TLM_READ_COMMAND, 32'h2000, word, ok);
      expect_true("read 0x2000 reports an error status", !ok);

      `uvm_info("TEST", $sformatf("PASS=%0d FAIL=%0d", pass_count, fail_count),
                UVM_NONE)
      phase.drop_objection(this);
    endtask
  endclass
endpackage

module tb_top;
  import uvm_pkg::*;
  import mlx_pkg::*;

  initial run_test("mlx_test");
endmodule
```

### How to integrate a model in another language

1. **Classify the model**: function-shaped C/C++ (DPI), SystemC with sockets and processes (bridge), or a separate program (co-simulation).
2. **Write the plan** (time owner, end-of-test owner, conversion points, build flow) before any code.
3. **Wrap the model.** For DPI: `extern "C"` entry points that catch every exception and always write their outputs. For a bridge: keep the model's own sockets.
4. **Put a TLM-2 target socket in front of it** on the SystemVerilog side, even for DPI, so a later swap to SystemC touches one class.
5. **Fix the packing convention**: byte order of the data array, field order of any extension, written down and shared by both sides.
6. **Connect** in `connect_phase` (pure SV or UVM-ML OA) or by lookup string (UVMC), then run one transaction with a known pattern and print both sides.
7. **Check every status** with `is_response_ok()`, and add a negative test that must return an error.
8. **Decide end of test**: the test drops its objection only after the last `b_transport` returns, or the other side holds objections through the bridge.
9. **Measure** the crossing cost on your simulator before scaling up, and record the library and simulator versions in the log.

**Checklist before moving on:**
- [ ] I can say which of DPI, a bridge or co-simulation fits a given model, and why.
- [ ] My initiator sets command, address, data, length, streaming width, byte-enable length and `UVM_TLM_INCOMPLETE_RESPONSE` before every call.
- [ ] My target sets the response status on every path, including errors.
- [ ] I read the timing annotation as an offset, and I chose what my initiator does with it.
- [ ] My C++ entry points use C linkage, catch every exception and always write outputs.
- [ ] I can name the origin, licence and latest checked release of UVM Connect and UVM-ML OA, and I know neither is an IEEE or Accellera standard.
- [ ] I know who ends the test in my bench, and what keeps the other language's work covered.

### Expert: Non-blocking transport across a boundary

A call to `nb_transport` "always represents a phase transition", while its return may or may not: `UVM_TLM_ACCEPTED` means "no change on this call", `UVM_TLM_UPDATED` means the callee moved the phase and wrote it into the `ref` phase argument, and `UVM_TLM_COMPLETED` is an optional shortcut that ends the transaction (IEEE 1800.2-2020 §12.3.2, §12.3.3.2). The phase belongs to the hop, not to the payload, so it can differ at each hop. The target implements `nb_transport_fw`; the initiator implements `nb_transport_bw` (§12.3.2.2.1, §12.3.2.2.2).

**Across a language boundary**, each of those calls is a crossing, so the four-phase path costs at least four crossings where `b_transport` costs one, and every backward call needs the bridge to route the SystemC target's `nb_transport_bw` back into SystemVerilog. The target must set the response status before it sends `BEGIN_RESP` or returns `UVM_TLM_COMPLETED` (§12.3.4.2.11). Use non-blocking transport across a boundary only when the model really is approximately-timed and you need its pipelining; for a reference model, prefer blocking LT transport.

### Expert: Data conversion, byte order and packing

Every bridge converts, and conversion is where silent bugs live.

- **Generic payloads.** UVMC predefines the converter. UVM-ML OA serializes objects with packing routines, normally from the UVM field macros, and requires the field registration order to match on both sides (Cadence 2018 §V). `uvm_tlm_generic_payload::do_pack` packs address, command, data length, DMI hint, data, status, byte-enable length, byte enables and streaming width, in that order, and does **not** pack extensions by default (§12.3.4.2.4).
- **Extensions.** A GP extension must exist in both languages. With UVM-ML OA, class names must match or be paired with `uvm_ml::set_type_match("sv:vip_transfer_gp_ext", "sc:transfer_gp_ext")` (Cadence 2018 Example 10).
- **The data array.** 1800.2 leaves byte order to you: "use a consistent mechanism to both fill the payload data array and later extract data from it" (§12.3.4.2.9). The worked example chose little-endian on both sides.
- **Packed structs over DPI.** The first member of a packed struct is the most significant (IEEE 1800-2023 §7.2.1), and DPI passes it as the canonical `svBitVecVal` array whose first element holds the 32 least significant bits (Annex H.7.7). A C struct declares its first member at the lowest address. Copy one onto the other and the fields come out reversed.

A traced example. SystemVerilog passes `typedef struct packed { bit [7:0] opcode; bit [23:0] addr; } cmd_t;` with `opcode = 8'h5A` and `addr = 24'h001234` to an import `function void send_cmd(input cmd_t c)`, which C receives as `const svBitVecVal* c`.

| Step | Value | Why |
|---|---|---|
| SV packed vector | `32'h5A00_1234` | `opcode` is the first member, so bits [31:24] (§7.2.1) |
| C sees `c[0]` | `0x5A001234` | Element 0 holds bits [31:0] (Annex H.7.7; compare Annex H.11.3, where struct `{a, b, c}` with only `a` set prints 4) |
| Wrong: `memcpy(&s, c, 4)` into `struct { uint8_t opcode; uint8_t addr[3]; }` on a little-endian host | `opcode = 0x34`, `addr = {0x12, 0x00, 0x5A}` | The lowest-addressed byte of `c[0]` is bits [7:0], which belong to `addr` |
| Right: shift and mask | `opcode = (c[0] >> 24) & 0xFF = 0x5A`; `addr = c[0] & 0xFFFFFF = 0x001234` | Field positions come from the SV declaration, not from C's memory layout |

The rule: convert field by field with shifts and masks, and test the converter with a pattern whose every field differs.

### Expert: Time and phase alignment

- **Time resolution.** `uvm_tlm_time` keeps a resolution, 1 ps by default; uvm-core's source comment recommends setting it to the SystemC resolution when co-simulating (uvm-core 2020.3.1, `uvm_tlm_time.svh`). The standard's names for the setter differ from uvm-core's (§5.6.2.2 lists `set_default_time_resolution`, uvm-core implements `set_time_resolution`), so check your library before calling it.
- **Common phases.** UVM-ML OA coordinates bring-up and phase order (Cadence 2018 §I).
- **Run-time sub-phases.** UVM-ML OA synchronization of run-time sub-phases with another framework: not supported up to 1.8; supported in 1.9 for Cadence on Xcelium only; HPE built a simulator-agnostic synchronizer that holds an objection from the SV side until the *e* side lets the phase advance (Pertuit et al., DVCon US 2018).
- **UVMC.** SystemC participates in UVM phasing through the Command API (`uvmc_wait_for_phase`, `uvmc_raise_objection`, `uvmc_drop_objection`), which needs `uvmc_init` on the SV side (UVMC documentation).
- **`run_phase` objections across languages** in UVM-ML OA: not verified for this lesson. Treat it as tool-dependent, read the release notes and write a test that ends while the model is busy.

### Expert: Support status and portability

Dated facts, checked for this lesson; re-check before you commit a project to any of them.

| Library | Origin and licence | Latest release checked | Simulators named by the source | Status |
|---|---|---|---|---|
| UVM Connect (UVMC) | Mentor Graphics, now Siemens EDA; Apache 2.0; introduced 2012 | 2.3.2, November 2019 (release notes) | Questa, VCS, IUS: "intended to work with all three"; others not verified | Documentation and kits on Verification Academy |

The misconception to drop: *frameworks behave the same on every simulator.* The sources above say otherwise, and a bench that depends on a feature such as cross-language run-time phase synchronization needs re-qualification when it changes simulator or library version. A useful insurance policy is to keep a DPI fallback compiling for function-shaped models.

### Expert: Performance of language crossings

The only published measurement found for this lesson compares the same bench two ways: UVM-ML at 167 MB and 0.6 s net CPU time against hand-written DPI-C at 146 MB and 0.4 s, with the DPI version reported as more complex to write (Cadence, DVCon Europe 2018 §VII). One small bench is not a rule: the crossing cost is **tool-dependent**, so measure it with your simulator's profiler before scaling up. The levers are the same everywhere: fewer crossings per transaction (blocking transport over four-phase non-blocking), batching several items into one payload where the model allows it, and keeping converters cheap (no string formatting in the hot path).

### Expert: Debugging a mixed-language bench at scale

- **List the connections.** UVM-ML OA can trace registrations from SystemC with `uvm_ml_execute_command("uvm_ml_trace_register -on")`; Cadence 2018 also lists Xcelium Tcl commands to stop after connect and print connections and type matches (tool-dependent). With UVMC, log every lookup string on both sides.
- **Correlate two logs.** Give every transaction an id in an extension or in the data, and print it on both sides with simulation time.
- **Isolate the model.** Keep the DPI path or a pure-SV stand-in target compiling, so you can tell a model bug from a bridge bug.
- **Per-instance state.** A C++ global like `g_model` is one model per simulation. Two targets that each need a model need a handle (`chandle`) per instance or a `context` import with per-scope data ([I-SV-7, Expert: Context call chains](/curriculum/T2_Intermediate/I-SV-7_DPI_and_Foreign_Language_Interfaces/index#expert-context-call-chains-and-per-instance-c-state)).
- **Exceptions and memory.** No exception may cross a DPI boundary (§35.5.1.6); never keep pointers to pass-by-reference arguments after the call (Annex H.8.4); each side frees only its own memory (§35.5.1.4).

### Kata: one model, two integrations

**Task.** Take the C++ `RefMem` model from Make It Work and integrate it twice.
1. **DPI only.** Write a predictor, a `uvm_subscriber #(bus_item)` whose `write` calls `ref_mem_write` or `ref_mem_read` directly, where `bus_item` has fields `bit write; bit [31:0] addr, data;`. Report a mismatch with `` `uvm_error ``.
2. **Behind a TLM-2 target.** Change the predictor to build a generic payload from each `bus_item` and send it through a `uvm_tlm_b_initiator_socket #()` to `ref_mem_target`. Check `is_response_ok()`.
3. **Sketch the SystemC swap** with UVM Connect: which lines change, and which stay.
4. **Compare** the two in a table: time ownership, conversion, tool needs, debug path, and the run time of 10,000 transactions on your simulator.

<details>
<summary>Worked solution</summary>

Step 1, the DPI predictor (the imports are those of `mlx_pkg`):

```systemverilog
// snippet: DPI-only predictor (bus_item is your monitor's transaction class)
class ref_mem_predictor extends uvm_subscriber #(bus_item);
  `uvm_component_utils(ref_mem_predictor)

  function new(string name, uvm_component parent);
    super.new(name, parent);
  endfunction

  function void write(bus_item t);
    bit [31:0] expected;
    if (t.write) begin
      if (ref_mem_write(t.addr, t.data) != 0)
        `uvm_error("PRED", $sformatf("model rejected write to 0x%0h", t.addr))
    end
    else begin
      void'(ref_mem_read(t.addr, expected));
      if (expected != t.data)
        `uvm_error("PRED", $sformatf("read 0x%0h: DUT 0x%08h, model 0x%08h",
                                     t.addr, t.data, expected))
    end
  endfunction
endclass
```

`write` is a function, so it can call the imported *functions*, which complete in zero time (§35.5.1.1).

Step 2. `write` cannot call `b_transport`, which is a task. Put a `uvm_tlm_analysis_fifo #(bus_item)` between the monitor and the predictor, and give the predictor a `run_phase` that does `fifo.get(t)`, builds a payload exactly as `ref_client::access` does, calls `sock.b_transport(gp, delay)`, and compares `get_data` against `t.data` for reads. The predictor no longer knows what is behind the socket; only `ref_mem_target` calls DPI.

Step 3. Only `mlx_env::connect_phase` changes on the SystemVerilog side: `uvmc_tlm #()::connect(pred.sock, "ref_mem")` replaces `pred.sock.connect(target.sock)`, and `ref_mem_target` is no longer created. On the SystemC side, `sc_main` builds the model and calls `uvmc_connect(model.sock, "ref_mem")`. The predictor code is unchanged, which is the payoff of step 2.

### Debug challenge: four broken bridges

For each, name the symptom you would see, the cause and the fix before you open the answer.

1. UVMC: the SV side registers `"ref_mem"`, the SC side `"ref_mem "` (trailing space).
2. UVM-ML OA: `uvm_ml::connect(...)` is called from an `initial` block in `tb_top` at time 0.
3. The initiator sets `set_data_length(8)` but passes a 4-byte data array.
4. The C++ model throws `std::out_of_range` and the wrapper has no `try`/`catch`.

<details>
<summary>Answers</summary>

1. **Symptom:** an elaboration error for an unmatched registered port, or an unconnected-socket error. **Cause:** lookup strings must match exactly and are global. **Fix:** share the string as one constant, and log it on both sides.
2. **Symptom:** the connection is missing and the first transport fails. **Cause:** at time 0 the components do not exist yet; UVM-ML OA expects registration in `phase_ended` of build and `connect` in `connect_phase`. **Fix:** move both calls into the environment, per Cadence 2018 Examples 4 and 7.
3. **Symptom:** a fatal error from `do_pack` when a bridge serializes the payload, or an out-of-range array access in a target that trusts the length. **Cause:** the length must not exceed the data array (§12.3.4.2.4). **Fix:** set the length from `bytes.size()`, and make targets check both.
4. **Symptom:** a crash or undefined behaviour inside the simulator. **Cause:** an exception crossed the DPI boundary (§35.5.1.6). **Fix:** catch everything in the `extern "C"` wrapper and return an error code that the target turns into an error status.

</details>
