## Quick Take

- **What it is:** **SoC-level verification** checks what only exists once separately verified blocks are joined into a system on chip (SoC): address decode, interrupt routing, resets that cross blocks, power states, firmware-driven flows, interconnect ordering and security. It is a **strategy** (who checks what, at which level, with which evidence) plus a **testbench** that reuses the block teams' verification components instead of rewriting them.
- **Why it matters:** Every block can pass its own regression while the chip still fails: an interrupt wired to the wrong core, a DMA write that the interconnect sends to the wrong memory, a reset that leaves one block mid-transfer. Those bugs belong to no block team, so unless the SoC strategy names an owner and a check for them, nobody looks.
- **The Analogy:** A city grid. Each neighbourhood (block) was inspected on its own; the city plan (SoC strategy) covers what joins them: roads (the interconnect), the power grid (power and reset), traffic lights (arbitration) and the emergency services (interrupts and error responses). *Where it breaks:* real neighbourhoods are independent, but SoC blocks are not; a shared clock, reset or bus couples them, so a fault in one "neighbourhood" can appear as a symptom in another. And unlike a city, the SoC plan must also decide which old inspectors (block checks) still have a job.

**You will be able to:**
1. Write a staff-level SoC verification strategy: scope split, test layers, reuse plan, checkers, coverage goals traced from features, regression tiers, sign-off gates and a risk register.
2. Configure reused block environments for the SoC (an environment of environments; passive where an on-chip master drives an interface, active where the bench still drives it) and adapt their checks so they still prove something.
3. Plan firmware and testbench co-operation: mailbox handshakes turned into events, image loading, and a SoC register model with explicit prediction on every bus (auto-predict cannot see firmware).
4. Plan system-level reset, error, power, concurrency and CDC/RDC scenarios, with the liveness properties and coverage that prove them.
5. Define regression tiers, the triage flow and the closure gates that must pass before sign-off.

## Build Your Mental Model

**How to read this lesson.** The core path is: what changes from block to SoC, the verification plan, reusing environments, active and passive agents, keeping block checks useful, and firmware with the testbench. Practitioner depth follows: the SoC register model, the interconnect and liveness, system scenarios (including CDC/RDC), coverage closure, regression and sign-off, and debugging. Make It Work builds a small SoC bench you can compile, and Push Further holds the expert layer.

**Words this lesson uses.** Each is defined here in one line, with the lesson that teaches it in full.
- **Design under test (DUT):** the hardware being verified. At SoC level the DUT is the whole chip, or a **subsystem** (a group of blocks that work together, such as a DMA engine, its interconnect and a memory controller).
- **Interconnect:** the on-chip network of buses and switches that routes each request from a **master** (a component that starts transfers, such as a CPU or DMA engine) to a **slave** (a component that answers them, such as a memory or a peripheral's registers). This lesson uses the master/slave terms of Arm IHI0022E; later Arm issues say manager/subordinate.
- **AXI and APB:** two of Arm's AMBA bus protocols. AXI is the high-performance bus with separate address, data and response channels and a transaction **ID** on each transfer; APB is the simple register bus ([B-AXI-1](/curriculum/T3_Advanced/B-AXI-1_AXI_Channel_Architecture/index)). **DECERR** is the AXI "decode error" response an interconnect returns for an address that no slave owns.
- **Firmware:** the software the SoC's own processor runs during the test, compiled into an **image** (a memory file) that is loaded before the processor starts.
- **Verification IP (VIP):** a reusable package of verification components for one interface or protocol, usually an **agent** plus its configuration ([A-UVM-7](/curriculum/T3_Advanced/A-UVM-7_VIP_Construction/index)).
- **Agent:** a UVM component that bundles a **sequencer** (queues items from sequences), a **driver** (turns items into pin activity) and a **monitor** (turns pin activity back into transactions) for one interface ([I-UVM-2A](/curriculum/T2_Intermediate/I-UVM-2A_Component_Roles/index)). An **active** agent (`UVM_ACTIVE`) builds all three; a **passive** agent (`UVM_PASSIVE`) builds only the monitor side.
- **Scoreboard and analysis port:** a scoreboard compares what the DUT did with what it should have done; it receives transactions from monitors through **analysis ports**, which broadcast each transaction to every connected subscriber's `write()` ([I-UVM-2B](/curriculum/T2_Intermediate/I-UVM-2B_TLM_Connections/index)).
- **Virtual sequence:** a sequence that sends no items itself but starts child sequences on several agents' sequencers, usually through a **virtual sequencer** that holds their handles ([I-UVM-3B](/curriculum/T2_Intermediate/I-UVM-3B_Advanced_Sequencing_and_Layering/virtual-sequences)).
- **Environment (env):** a `uvm_env` that holds agents, scoreboards and other checkers for one block or system ([I-UVM-2A](/curriculum/T2_Intermediate/I-UVM-2A_Component_Roles/index)).
- **Phase:** one of the named steps UVM runs every component through, in order: `build_phase` creates children, `connect_phase` wires them, `run_phase` consumes simulation time, then the check and report phases ([I-UVM-1C](/curriculum/T2_Intermediate/I-UVM-1C_UVM_Phasing/index)).
- **Objection and `uvm_event`:** an objection is the vote that keeps a time-consuming phase alive until it is dropped; a `uvm_event` is a UVM object one process triggers and others wait on ([I-UVM-1C](/curriculum/T2_Intermediate/I-UVM-1C_UVM_Phasing/index), [A-UVM-8](/curriculum/T3_Advanced/A-UVM-8_Multi_Agent_Topologies/index)).
- **Clocking block and assertion:** a clocking block samples and drives interface signals at a defined clock edge ([F4C](/curriculum/T1_Foundational/F4C_Clocking_Blocks/index)); a concurrent assertion checks a property on every clock edge and reports when it fails ([I-SV-4A](/curriculum/T2_Intermediate/I-SV-4A_SVA_Fundamentals/index)).
- **Plusarg:** a `+name` or `+name=value` argument on the simulator command line that the bench can read at run time.
- **Configuration database:** the UVM store a parent uses to pass settings to a child by its instance path, used here as `uvm_config_db` ([I-UVM-2C](/curriculum/T2_Intermediate/I-UVM-2C_Configuration_and_Resources/index)).
- **Register model (RAL), mirrored value, predictor:** the register model is a class model of the DUT's registers; its **mirrored value** is what it believes each register holds; a **register predictor** (`uvm_reg_predictor`) updates the mirror from bus transfers a monitor saw, using an **adapter** that turns bus items into register operations and back; a **frontdoor** access reaches a register through real bus transfers, and a **backdoor** access reads or writes its storage directly through its HDL path, with no bus cycle ([A-UVM-4A](/curriculum/T3_Advanced/A-UVM-4A_RAL_Fundamentals/index), [A-UVM-4B](/curriculum/T3_Advanced/A-UVM-4B_Advanced_RAL_Techniques/explicit-vs-implicit)).
- **Liveness:** the promise that something good *eventually* happens (every accepted request gets a response); its opposite, **safety**, promises that something bad *never* happens ([E-INT-1](/curriculum/T4_Expert/E-INT-1_Integrating_UVM_with_Formal_Verification/index)).
- **CDC / RDC:** a **clock-domain crossing** is a signal that leaves logic clocked by one clock and is captured by logic on an unrelated clock; a **reset-domain crossing** is the same idea for logic reset by different resets.
- **Verification plan (vplan):** the document that lists features and, for each one, the scenarios, checks and coverage that prove it. Each row carries a priority; this lesson uses the common project convention **P0** (must work for the chip to ship) and **P1** (should work; a gap needs an agreed waiver) ([F1B](/curriculum/T1_Foundational/F1B_The_Verification_Mindset/index)).
- **Regression and sign-off:** a regression is the automated run of many tests and random seeds; **sign-off** is the decision, backed by agreed evidence, that verification is complete enough to build the chip.

### What changes from block to SoC

A block team verifies one block through its own ports. Its bench drives every input, models every neighbour and checks every output. At SoC level most of those neighbours are now real: a CPU running firmware drives the block's register port, a real interconnect carries its memory traffic, and a real interrupt controller receives its interrupt. The bugs that remain are the ones that only exist **between** blocks.

**Bugs that only exist after integration:**
- **Connectivity:** an interrupt line, clock enable, reset or pin-multiplexer output wired to the wrong place. Each block is correct; the wiring between them is not.
- **Address map and decode:** a master reaches the wrong slave, or an unmapped address hangs instead of returning an error.
- **System flows:** boot, firmware configuration, DMA descriptor chains, interrupt handling end to end.
- **Shared resources:** arbitration between masters, ordering through the interconnect, quality of service (QoS: which traffic class gets bandwidth first).
- **Resets, power and clocks:** one block reset while another is mid-transfer, a power domain switched off while traffic is in flight, a signal crossing clock domains without a synchronizer.
- **Security:** a non-secure master reaching protected registers.

**Test layers.** No single bench catches all of this, so the strategy assigns each class of bug to the cheapest layer that can see it. Before you read the caption, predict: which layer is the *first* that can see a wrong interrupt wire between two blocks?

**What the SoC layer adds.** The processor model, firmware, the interconnect checks, system scenarios and system coverage. What it does *not* do is re-verify each block's internals: the block layer already did that more cheaply and with more control. That leads to the first classic mistake.

> **Misconception: "SoC closure is the union of block coverage."** Merging every block's 100% coverage proves each block was exercised *by its own bench*. It says nothing about whether the CPU ever reached the crypto block, or whether a DMA error response ever reached firmware. SoC closure needs system goals collected at SoC level. "SoC coverage and closure" below shows the difference in a picture.

**Connectivity checking.** Top-level wiring is usually checked apart from functional tests: by a formal connectivity check that proves each listed connection (source pin to destination pin, under a condition such as a pin-multiplexer setting) from a spreadsheet of intended connections, or by simulation tests that toggle each source and watch each destination. Which tool does this, and how the spreadsheet is written, is tool-dependent. The strategy only has to say who owns the connection list and how it is proven.

**Choosing the processor model.** The firmware needs something to run on.

| CPU model | Speed | Fidelity | Firmware debug | Use it for |
|---|---|---|---|---|
| RTL core | slowest | exact: real pipeline, caches, bus timing | waveforms, plus a trace of executed instructions if the core provides one | final SoC regressions, boot, timing-sensitive flows |
| Instruction-set simulator (ISS) | fast | executes the right instructions, but bus timing is approximate | software debugger | firmware bring-up, long flows |
| Bus-functional model (BFM) | fastest | issues the bus cycles a test lists; no instructions at all | none needed | early integration, interconnect tests, this lesson's example |

Many projects use all three over time. The strategy states which model each test layer uses and what each one cannot prove (a BFM never finds a bug in the core's own bus interface).

### From features to checks: the verification plan

A strategy is only reviewable if every promise in it can be traced. The **verification plan** does that: each **feature** from the specification becomes one or more **scenarios** (what the tests make happen), each scenario has a **check** (what decides pass or fail) and **coverage** (the evidence that the scenario really happened), and each of those is linked to regression results. This chain is called **traceability**.

### Reusing environments: an environment of environments

IEEE 1800.2-2020 §13.3 says a `uvm_env` "can be reused as a sub-environment in even larger system-level environments". That is the core reuse move at SoC level: the block team's whole environment (agent, scoreboard, coverage) becomes a child of the SoC environment, unchanged, and only its configuration differs. Engineers call the result an **environment of environments** (env of envs). [A-UVM-8](/curriculum/T3_Advanced/A-UVM-8_Multi_Agent_Topologies/index) teaches the nesting mechanics (configuration objects one level deeper, virtual sequencers of virtual sequencers); this lesson applies them at SoC scale.

**What changes, and what does not.**
- **The block environment's code is reused, not rewritten.** `spi_blk_env` and its agent come from the block team's package; the settings they receive from above differ. Where a reused check must change, the change is a recorded decision: Make It Work adapts one scoreboard line, and "Keeping block checks useful at SoC" explains why.
- **Every configuration path gets one level deeper.** At block level the agent was `env.spi_agent`; nested, it is `env.spi_env.spi_agent`. A block environment that used absolute paths (`"uvm_test_top.env.spi_agent"`) breaks here, which is why paths must be relative to `this`.
- **Block virtual sequences become children,** started on the block's virtual sequencer from a SoC virtual sequence, exactly as in [A-UVM-8](/curriculum/T3_Advanced/A-UVM-8_Multi_Agent_Topologies/index). A block sequence that targets an agent that is now passive can no longer run: its sequencer handle is null.
- **SoC-only components are added beside the reused ones,** never inside them: here the mailbox decoder; in a real SoC also interconnect scoreboards, interrupt checkers and system coverage.

### Active and passive reuse

At block level the SPI block team's agent is **active**: its sequencer and driver play the CPU, writing the block's registers over its APB register port. (APB is Arm's simple register bus: each transfer has a **setup** cycle with `psel = 1`, then an **access** cycle with `psel = 1` and `penable = 1`; it is taught in the AMBA track.) In the SoC the real CPU drives that port. If the agent stays active and a block sequence runs, two masters drive one bus.

What that looks like depends on how the interface signals are declared (IEEE 1800-2023 §6.5):
- **Nets** (`wire`) resolve multiple drivers: where the CPU and the driver disagree, the signal becomes `X`. That is visible, so this lesson's interface uses nets and an assertion that fails on `X`.
- **Variables** (`logic` written procedurally) take the **last write**: no `X`, no error, just silently corrupted transfers. This is the dangerous case.
- Mixing a continuous assignment and procedural writes on one variable is illegal, so that case fails at compile or elaboration time.

The fix is to reuse the agent **passive**. The visual below shows the SPI agent at block level and at SoC level. Predict which parts of the agent exist after `build_phase` in passive mode, then switch levels and try breaking the agent.

**What the visual showed.**
- **Passive means never built, not built-but-idle.** The agent's `build_phase` creates the sequencer and driver only inside `if (get_is_active() == UVM_ACTIVE)`. In passive mode those handles stay null, so there is nothing to "switch off".
- **Break 1: no `super.build_phase(phase)`.** The base class `uvm_agent` reads the `"is_active"` setting in its own `build_phase` (uvm-core 2020.3.1 `uvm_agent.svh`). A derived agent that skips `super.build_phase` never reads it, stays at the default `UVM_ACTIVE`, and fights the CPU.
- **Break 2: an unguarded `connect_phase`.** `driver.seq_item_port.connect(...)` reads a member of a null handle. IEEE 1800-2023 §8.4 makes that access illegal, and simulators stop with a null-object-access error during `connect_phase`, at time 0 (the visual calls this stopping at elaboration). The connect must repeat the same `get_is_active()` guard.
- **Names.** The visual's path is `"env.spi_agent"` and its class is `spi_agent`. In Make It Work the agent is one level deeper (`"env.spi_env.spi_agent"`) and its class is `spi_apb_agent`, because it is the SPI block's agent for its APB register port. The visual's "pins" are, in this lesson's bench, the APB register-port signals that the CPU drives.

**How the mode reaches the agent.** `uvm_agent` itself builds no children. It only reads `is_active`; *your* agent's `build_phase` must contain the guard, and its `connect_phase` must repeat it. IEEE 1800.2-2020 §13.4.2.2 says the parameter is set as a `uvm_active_passive_enum` and also accepts a string, so the command line can override it (Annex G.2.8):

```systemverilog
// snippet: soc_test::build_phase, an exact path relative to the test
uvm_config_db#(uvm_active_passive_enum)::set(this, "env.spi_env.spi_agent",
                                             "is_active", UVM_PASSIVE);
```

```bash
# the same setting from the command line (component path, field, value)
+uvm_set_config_string=uvm_test_top.env.spi_env.spi_agent,is_active,UVM_PASSIVE
```

A VIP that keeps the mode in its own configuration object ([A-UVM-7](/curriculum/T3_Advanced/A-UVM-7_VIP_Construction/index)) is switched through that object instead; it should still copy the mode into `is_active` so `get_is_active()` stays the one answer.

**Prove the build, do not assume it.** Call `uvm_root::get().print_topology()` (Annex F.7.4.2) in `end_of_elaboration_phase`: a passive agent shows a monitor and no driver or sequencer. Better still, make the check automatic: the Make It Work test fails with `UVM_FATAL [MODE]` if `get_is_active()` is not `UVM_PASSIVE`.

**Active where the bench still drives.** Passive is not the SoC default; it is the answer to "who drives this interface here?". An agent goes passive where an on-chip master now drives the interface. It stays **active** where the bench still plays the other side, typically for devices outside the chip.

| Interface in the SoC | Who drives it in the SoC test | Agent mode | Why |
|---|---|---|---|
| SPI block's APB register port | the CPU (firmware) | passive | the CPU is a real master now |
| SPI pins to an off-chip flash | the SPI block drives the clock and commands; the flash answers | active (a responder playing the flash) | no on-chip model of the flash exists, so the bench must answer |
| UART pins to a terminal | the chip transmits; the terminal transmits back | active on receive, monitor on transmit | the bench plays the terminal |
| DMA engine's AXI master port | the DMA engine | passive | the DUT is the master |
| PCIe link | the chip and an off-chip link partner | active (the bench plays the link partner) | the partner is off chip |

`is_active` is set per instance path, so each agent gets the mode its interface needs, and the same VIP class can even be passive on one instance and active on another:

```systemverilog
// snippet: soc_test::build_phase, two agents, two modes
// the CPU drives the APB port, so the register-port agent only watches
uvm_config_db#(uvm_active_passive_enum)::set(this, "env.spi_env.spi_agent",
                                             "is_active", UVM_PASSIVE);
// no on-chip flash model exists, so the bench plays the flash on the SPI pins
uvm_config_db#(uvm_active_passive_enum)::set(this, "env.flash_env.flash_agent",
                                             "is_active", UVM_ACTIVE);
```

This is also why a wildcard such as `set(this, "*.spi_agent", ...)` is risky: it would make every instance called `spi_agent` passive, including one that must stay active.

**Pitfall: a block sequence on a passive agent.** A SoC virtual sequence copied from a block test may still run `spi_seq.start(p_sequencer.spi_sqr)`. With the agent passive, that handle is null. `start(null)` itself is legal; uvm-core 2020.3.1 reports `UVM_FATAL [SEQ]` "neither the item's sequencer nor dedicated sequencer has been supplied to start item" at the sequence's first `start_item()` (`uvm_sequence_base.svh`). With a parent sequence the symptom can instead be a silent hang; [A-UVM-8's debugging table](/curriculum/T3_Advanced/A-UVM-8_Multi_Agent_Topologies/index) lists every case.

### Keeping block checks useful at SoC

> **Misconception: "block scoreboards transfer to SoC unchanged."** A block scoreboard was written for a world where the bench drove every input and knew every expected value. At SoC level some of those assumptions are false, and a scoreboard that silently checks the wrong thing is worse than none.

What changes, check by check:
- **Where expected values come from.** At block level a scoreboard often took its expectation from the sequence that sent the item. At SoC the firmware sends it, so the expectation must come from what a **monitor observed** at the block's input. Make It Work's `spi_reg_scb` is written that way: it builds its shadow of the registers from observed writes, so it works whether a sequence or firmware drove the bus.
- **What traffic the monitor sees.** A monitor on a shared bus also sees other blocks' traffic. Make It Work's scoreboard needs one adapted line: it ignores addresses outside the SPI block's window, because the same bus carries the mailbox.
- **IDs change through the interconnect.** An AXI interconnect appends bits identifying the master port to `ARID`, `AWID` and `WID`, so "the ID identifier at a slave interface is wider" than at the master (IHI0022E §A5.3.5). A block scoreboard that matches a slave-side response against a master-side request by raw ID reports every response as unmatched. Correlate at the master side, or strip the port bits before matching.
- **Unmapped addresses get an error, not silence.** "If the interconnect cannot successfully decode a slave access, it must return the DECERR response" (§A3.4.4), usually from a default slave. A block scoreboard never saw DECERR; a SoC scoreboard must expect it for every hole in the address map.
- **Other masters change ordering and contents.** Memory a block wrote can be overwritten by another master before the block reads it back. A memory scoreboard at SoC must know which master owns which region, or check per master.
- **Security attributes start to matter.** `AxPROT` carries the access permissions (§A4.7); a security controller may refuse a transfer the block bench always allowed.

**The decision per scoreboard.** For every reused check, the strategy records one of three decisions and an owner: **keep** (still valid as is, often as an internal checker that localizes failures), **adapt** (new expectation source, address filter or ID mapping) or **disable** (the check now duplicates a better SoC check, or its assumptions no longer hold). A check that is kept must prove it ran: the bench counts what each enabled monitor saw and compares the count with what the test expected. That count is project-specific code, distinct from `uvm_heartbeat` (IEEE 1800.2-2020 §10.6), which checks that components keep raising an objection within a time window.

**Interrupts need their own check.** Firmware *uses* interrupts; the bench must *check* them. An interrupt monitor records each interrupt line's rising edge, an expected-interrupt model in the scoreboard predicts which source should fire for each event (a DMA completion, an error response), and the check compares the two and cross-checks the status register firmware reads. "The firmware handled an interrupt" is not evidence that the *right* interrupt reached the *right* core.

### Firmware and the testbench

In a SoC test two programs run at once: the firmware on the CPU and the UVM testbench. Neither can call the other, so they co-operate through the hardware, under a written **firmware–testbench contract**.

**Loading the image.** The firmware image is loaded into the memory the CPU boots from before reset is released, usually with `$readmemh` (IEEE 1800-2023 §21.4) on the memory model's array, or with a register-model backdoor write to a `uvm_mem`. Log the image's file name and a hash of it, so a failure can be tied to the exact firmware build. Choosing the image at run time with a plusarg read by `$value$plusargs` (§21.6) avoids recompiling the bench for each firmware test.

**The mailbox.** Firmware reports progress by writing agreed codes to an agreed address, the **mailbox** (a spare register or a reserved word of memory). A bus monitor sees the write, and a decoder turns each code into an event the test can wait on. The contract fixes:
- the mailbox address and every code (BOOT_DONE, FW_PASS, FW_FAIL with a reason, PRINT for log messages);
- who writes and who reads each code;
- what the test waits for, and its timeout;
- what the scoreboards do during boot (usually: nothing is checked until BOOT_DONE).

Keep the addresses and codes in one package that both the firmware build and the testbench use, so the two sides cannot drift apart. Make It Work's `soc_map_pkg` plays that role.

**Events, and the race in waiting for them.** The decoder triggers a `uvm_event` taken from the global event pool with `uvm_event_pool::get_global("fw_boot_done")` (IEEE 1800.2-2020 §10.4.1.2.3); any component that asks for the same name gets the same event. The test must not miss it:
- `wait_trigger()` (§10.1.1.2.4) waits for the **next** trigger. If the trigger already happened, it "does not return until the next trigger, which may never occur".
- `wait_on()` (§10.1.1.2.2) waits for the event to be **on**: "If the event has already been triggered, this task returns immediately." For a one-time milestone such as BOOT_DONE, use `wait_on()`.

### The SoC register model and its prediction limits

At block level a test often reads and writes registers through the register model, and the model keeps its **mirror** up to date by **auto-prediction**: `set_auto_predict(1)` on a map makes the model call `predict()` after each `uvm_reg::write()` or `uvm_reg::read()` it starts through that map (IEEE 1800.2-2020 §18.2.5.2). At SoC level most register traffic comes from firmware, which never calls the model.

> **Misconception: "auto-predict keeps the mirror right when firmware writes."** Auto-prediction only sees accesses the register model itself started. A firmware write to CTRL leaves the mirror at its old value. Only an **explicit** `uvm_reg_predictor` connected to a monitor on that bus (§19.3) sees it.

Three more facts trip people up:
- `get()` returns the **desired** value (what the model wants to write next, §18.4.4.1), not the DUT's value; `get_mirrored_value()` returns the mirror (§18.4.4.3). Polling `get()` for a firmware write never sees it.
- One predictor holds one map (`map`, §19.3.2.3) and one adapter, and finds registers by offset in that map (uvm-core 2020.3.1 `uvm_reg_predictor.svh`). Every bus that can write registers needs its own monitor, adapter and predictor: the CPU's bus, a debug port, a second processor.
- "Memories can be large, so their accesses are not predicted" (§19.3): a `uvm_mem` has no mirror to update.

Predict before the caption: the debug port writes CTRL, and a test sequence also writes it with `ctrl.write()` through the model, with auto-predict on and both predictors connected. Which paths update the mirror, and how many times is the sequence's write predicted?

### Liveness: failures that should not wait for a timeout

A lost response at SoC level often shows up only as a test that hangs until the global timeout, hours later, with no clue where. A **liveness property** names the promise (every accepted write gets a response) so a failure points at the broken promise instead. In the strategy, each property gets four things: its **trigger** (when the obligation starts), its **obligation**, its **failure meaning** (what bug a failure indicates) and its **owner**.

Typical SoC liveness properties:
- every accepted request eventually receives data, a completion or an error response;
- no legal backpressure state makes two channels wait on each other for ever (a channel-dependency cycle; see [B-AXI-5](/curriculum/T3_Advanced/B-AXI-5_AXI_Pitfalls_Interconnect_Deadlocks/index));
- a reset asserted during traffic eventually returns the fabric to idle;
- an enabled interrupt eventually reaches its target or its status register;
- a denied access never causes a side effect in the protected slave (a safety property, listed here because it is reviewed with the others).

**Weak, strong and bounded.** In an `assert property`, a sequence written without `strong` is evaluated as **weak** (IEEE 1800-2023 §16.12.2). A weak sequence fails only when a finite stretch of the trace proves it cannot match, and `##[1:$]` can always still match later, so this assertion can **never fail** in simulation, however long the response is missing:

```systemverilog
// snippet: AXI write channel, one write outstanding at a time
// Weak: never fails in a finite simulation (§16.12.2)
a_bresp_weak: assert property (@(posedge aclk) disable iff (!aresetn)
  (wvalid && wready && wlast) |-> ##[1:$] bvalid);

// Bounded: a safety check that simulation can fail; 8 is a project budget
a_bresp_bounded: assert property (@(posedge aclk) disable iff (!aresetn)
  (wvalid && wready && wlast) |-> ##[1:8] bvalid)
  else `uvm_error("LIVE_B", "no BVALID within 8 cycles of the last W beat")

// Strong: true liveness, for formal (§16.12.13); see Push Further
a_bresp_live: assert property (@(posedge aclk) disable iff (!aresetn)
  (wvalid && wready && wlast) |-> s_eventually bvalid);
```

The trigger is the **last write-data beat**, not the address: an AXI slave "must wait for both WVALID and WREADY to be asserted before asserting BVALID" and also for `WLAST` (IHI0022E §A3.3.1). Measuring from the address would blame the slave for a missing data beat, which is a master or bench bug. Count the edges in the waveform before you read the caption.

### System scenarios: reset, errors, power, concurrency and CDC/RDC

These are the scenarios no block bench can run, because they span blocks. The strategy lists each with its stimulus, its check and the coverage that proves it ran.

**CDC and RDC awareness.** Clock- and reset-domain crossings are signed off mainly by **structural analysis**, not by functional coverage. A CDC tool reads the RTL, finds every signal that crosses from one clock domain to another, and checks that each crossing has an approved **synchronizer**. A flip-flop that samples an input changing too close to its clock edge can go **metastable**: its output hovers between 0 and 1 for a while before settling. A synchronizer gives it time to settle: for a single bit, typically two flip-flops in the receiving domain; for a bus, a handshake or a FIFO whose pointers are Gray-coded (they change one bit at a time). An RDC check does the same for flip-flops whose asynchronous reset can change their output while a flip-flop in another reset domain, which is not being reset, captures it.

What the SoC strategy needs from you is awareness, not the tool flow:
- Functional tests with random clock ratios exercise crossing logic, but an RTL simulation **shows no metastability** unless the tool injects it (tool-dependent), so passing tests prove nothing about a missing synchronizer.
- The CDC/RDC report, its waivers and their reviewer are sign-off items in the strategy, owned by the design or a CDC specialist.
- IP from other teams can come with abstract CDC/RDC models so the SoC run does not re-analyse every block; Accellera approved a standard for such abstractions in 2026 (see References).
- [B-AMBA-F1](/curriculum/T3_Advanced/B-AMBA-F1_Bridges_and_System_Integration/index) shows a bridge that crosses clock domains, which is where many SoC crossings live.

### SoC coverage and closure

**Coverage closure** means every planned coverage goal is hit, or **waived** (excluded on purpose) with a written reason, and every hole has been analysed ([I-SV-3B closure workflow](/curriculum/T2_Intermediate/I-SV-3B_Advanced_Functional_Coverage/closure-workflow)). At SoC level the goals are system goals:
- master × slave × response (including decode errors and security denials);
- interrupt source × target core × priority;
- reset source × traffic class;
- power state × traffic class;
- master × privilege × region × response for security;
- traffic profile × latency bucket for QoS.

**From goal to code.** A system goal becomes a covergroup in the SoC-only checker that sees the outcome, here the routing scoreboard `route_scb`, sampled once per completed response. Each waiver becomes an `ignore_bins` with its reason beside it, so the review of the waiver and the code stay together. [I-SV-3A](/curriculum/T2_Intermediate/I-SV-3A_Functional_Coverage_Fundamentals/index) teaches the covergroup syntax.

```systemverilog
// snippet: inside class route_scb (IEEE 1800-2023 §19.4, §19.6.2, §19.8.1)
typedef enum {CPU, DMA, DBG}        master_e;
typedef enum {DDR, SRAM, SPI, HOLE} target_e;

covergroup cg_route with function sample(master_e m, target_e t);
  cp_master: coverpoint m;                // one automatic bin per enum value
  cp_target: coverpoint t;
  x_route:   cross cp_master, cp_target {
    // waived: the address map gives the DMA no route to SPI (reviewer: SoC lead)
    ignore_bins dma_spi  = binsof(cp_master) intersect {DMA} &&
                           binsof(cp_target) intersect {SPI};
    // waived: the debug decoder cannot produce an unmapped address
    ignore_bins dbg_hole = binsof(cp_master) intersect {DBG} &&
                           binsof(cp_target) intersect {HOLE};
  }
endgroup

function new(string name, uvm_component parent);
  super.new(name, parent);
  cg_route = new();                       // only new() may assign it (§19.4)
endfunction

// in the response check, once per completed response:
//   cg_route.sample(master_of(rsp), target_of(rsp));
```

A response coverpoint (OKAY, SLVERR, DECERR) crossed with these two gives the full master × target × response goal from the list above.

**Practitioner rules.**
- Close block coverage in block regressions. At SoC, collect only the goals that need the SoC.
- Every waiver states why the cell is unreachable or irrelevant, and someone other than the author approves it.
- Code coverage (statement, branch, toggle) at SoC level is mostly used for **toggle coverage of top-level connections**, which overlaps the connectivity check.
- Do not chase block-internal states that the system cannot reach from firmware: that spends regression time on holes that will be waived anyway.

### Regression, triage and sign-off gates

A SoC simulation can take hours, so not every test can run on every change. The strategy defines **tiers**; the run times below are illustrative project policy, not industry figures.

| Tier | When | Content | Gate (example policy) |
|---|---|---|---|
| Smoke | every change (pull request) | boot to BOOT_DONE, one transfer per master, every passive monitor sees traffic | no error or fatal; every enabled monitor active |
| Nightly | every night | randomized firmware tests, resets, interrupts, errors, many seeds | no new P0/P1 failure; coverage does not drop |
| Weekly stress | every week | heavy backpressure, long random runs, concurrency | no deadlock, no unexplained timeout |
| Sign-off | at the milestone | the whole vplan, formal proofs, power and reset scenarios | all closure gates below met |

**Triage by first divergence.** When a test fails, the first question is *where did reality first differ from expectation*, not "which block is broken". A scoreboard mismatch is a symptom; its cause can be the RTL, the reference model, the test's intent, the firmware, the UVM infrastructure or the tool. Each failure therefore carries an **evidence package**: random seed, RTL version hash, firmware image hash, testbench version hash, plusargs, the failing transaction and a window of bus traffic around it, and a waveform trigger. From that package a script or a person sorts the failure into an **owner bucket**. [E-DBG-1](/curriculum/T4_Expert/E-DBG-1_Advanced_UVM_Debug_Methodologies/index) teaches the regression loop and honest pass/fail verdicts in depth.

**Closure gates** are the conditions that must all hold before sign-off. The numbers are project policy that the strategy states and the review agrees; there is no universal threshold. A typical set:
- every P0 and P1 vplan row closed: check linked, coverage hit or waived with an approved reason;
- no open P0/P1 failures, and every known failure bucketed with an owner;
- every liveness and security property proven in formal or covered by an agreed bounded check, with counterexamples closed;
- the CDC/RDC report clean or waived by its reviewer;
- the last N nightly regressions (N set by policy) without a new failure or coverage drop;
- the risk register reviewed, each open risk accepted by a named owner.

### The staff-level strategy artifact

A staff-level SoC plan is a reviewable engineering document, not a list of tests. It must make ownership, observability and sign-off evidence explicit enough that block teams, firmware, formal and SoC verification can execute it without interpreting it differently.

| Strategy area | Staff-level question | Evidence expected at review |
|---|---|---|
| Scope split and test layers | Which bugs remain block-owned, and which only appear at subsystem or SoC scope? | Block/subsystem/SoC responsibility matrix; processor model per layer |
| Traceability | Can every feature be followed to a check and to coverage? | vplan with feature, scenario, check, coverage and owner per row |
| Reuse plan | Which environments are nested, and which agents are active, passive or disabled? | Per-interface mode table, build audit (`print_topology()` or an automatic mode check), monitor activity counts |
| Checkers | Which block scoreboards are kept, adapted or disabled, and what is new at SoC? | Per-scoreboard decision and owner; interconnect, interrupt and security checks |
| Firmware contract | How do firmware and the bench synchronize, and how is the mirror kept right? | Mailbox map and codes, events and timeouts, one predictor per bus |
| Coverage model | Which scenarios prove system behaviour instead of repeating block coverage? | Master × slave × response, interrupt routing, security, reset, power and QoS crosses |
| Formal and liveness | Which failures should never wait for a regression timeout? | Liveness and safety properties with trigger, obligation, failure meaning and owner |
| Regression and triage | What runs when, and how does a failure reach its owner? | Tiers, evidence package, buckets |
| Sign-off | What exactly must be true to stop? | Closure gates with owners |
| Risks | What can still invalidate the schedule after the tests are green? | Risk register with owner, mitigation and exit criteria |

**The risk register,** reviewed weekly before sign-off:

| Risk | Mitigation | Exit criteria |
|---|---|---|
| Passive VIP is connected but not observing traffic | per-monitor activity counts checked in `check_phase`; build audit | every enabled passive monitor sees the expected smoke-tier traffic |
| Firmware boot instability hides RTL failures | firmware phase codes in the mailbox; a separate firmware bucket | boot failures reproduce and are separated from RTL checks |
| Interconnect deadlock appears only under rare backpressure | formal liveness plus weekly backpressure stress | no open liveness counterexample or stress timeout |
| Coverage chases unreachable block states | system-level coverage review and waiver policy | every waived bin has a reachability reason and a reviewer |
| Failure artifacts do not identify an owner | mandatory evidence-package schema in CI | P0/P1 failures are bucketed without a rerun |

### Pitfalls and misconceptions

- *"SoC closure is the union of block coverage."* Block coverage shows each block was exercised by its own bench, not that the system flows happened. Close system goals at SoC.
- *"Block scoreboards transfer unchanged."* Expectation sources, visible traffic, IDs and error responses all change at SoC. Decide keep, adapt or disable per scoreboard.
- *"Auto-predict keeps the mirror right when firmware writes."* It only sees accesses the model started. Put an explicit predictor on every bus that writes registers.
- *"Every agent becomes passive at SoC."* Only where an on-chip master now drives. Off-chip devices still need active responders.
- *"A passive monitor that reports nothing means nothing happened."* It may be connected to the wrong interface. Count what it saw and compare with what the test expected.
- *"A liveness assertion with `##[1:$]` will catch a lost response."* In `assert property` it is weak and never fails in simulation.
- *"Random clock ratios prove CDC."* RTL simulation shows no metastability; CDC is signed off structurally.

### Debugging at SoC: symptom, cause, fix

| Symptom in the log | Likely cause | Fix |
|---|---|---|
| `print_topology()` shows a driver and sequencer under a reused agent, or `UVM_FATAL [MODE]` | the `is_active` setting never reached the agent: wrong path, a wildcard that missed, or the agent skips `super.build_phase` | use the exact relative path; check with `+UVM_CONFIG_DB_TRACE` (uvm-core 2020.3.1 plusarg, not in 1800.2); restore `super.build_phase` |
| `X` on bus control signals; a protocol assertion fails from the first transfer | an agent left active drives the same nets as the CPU | make the agent passive; remove the block sequence from the SoC test |
| `UVM_FATAL [SEQ]` "neither the item's sequencer nor dedicated sequencer has been supplied" | a block sequence started on a passive agent's null sequencer | do not start it, or null-check handles at the top of the virtual sequence |
| A monitor count of 0, or a count lower than the firmware contract | the monitor's virtual interface points at the wrong instance, or the monitor sits on a bus this test does not use | check where `tb_top` set `"vif"` and the path it used; compare counts with the contract |
| The register mirror never changes after firmware writes | no predictor on the bus firmware used; only auto-predict is on | add a monitor, adapter and predictor for that bus |
| Every response unmatched in a reused AXI scoreboard | slave-side IDs carry the interconnect's port bits (IHI0022E §A5.3.5) | correlate at the master side or strip the port bits |
| The test hangs after boot, or a firmware watchdog error | a missed trigger (`wait_trigger()` after the trigger), or firmware never booted (image not loaded, wrong path) | use `wait_on()`; check the image hash and the mailbox codes in the log |
| An error-injection test fails on its own expected errors | expected errors are not demoted and counted | a report catcher that demotes only the expected IDs and counts them ([A-UVM-9](/curriculum/T3_Advanced/A-UVM-9_Reset_and_Error_Injection/index)) |

### Recap

- SoC verification targets bugs between blocks; each layer reuses the one below and adds only what it alone can see.
- A vplan traces every feature to scenarios, checks and coverage; a hit bin without a check proves nothing.
- Block environments are nested unchanged; only their configuration changes. Agents are passive where an on-chip master drives, active where the bench still drives.
- Reused checks are kept, adapted or disabled by decision, and every kept monitor proves it saw traffic.
- Firmware and the bench meet through a mailbox contract and events; use `wait_on()` for milestones.
- Only explicit predictors see firmware register traffic: one per bus.
- Liveness needs strong properties in formal and bounded checks in simulation; CDC/RDC needs structural analysis.
- Closure is system coverage plus gates stated as project policy, not merged block coverage.

## Make It Work

### The complete example

One file holds a tiny SoC and its testbench. The SoC (`mini_soc`) has a CPU model that runs a short "firmware" as APB bus cycles (a bus-functional model, as in "Choosing the processor model"), the SPI block's register port (`spi_regs`) and a mailbox register. The testbench reuses the SPI block team's environment unchanged inside `soc_env`, makes its agent passive, adds a SoC-only mailbox decoder, waits on firmware milestones with `wait_on()`, audits the build and checks that the passive monitor saw exactly the traffic the firmware contract promises. The names match the `soc_env` diagram above.

```systemverilog
// compile: soc_spi_tb.sv: the firmware contract, the bus, the mini SoC, the TB
`timescale 1ns/1ps
`include "uvm_macros.svh"

// =============================================== the firmware-testbench contract
// One package for addresses and codes, shared by the firmware build and the bench.
package soc_map_pkg;
  localparam logic [11:0] SPI_CTRL   = 12'h000;
  localparam logic [11:0] SPI_TXDATA = 12'h004;
  localparam logic [11:0] MAILBOX    = 12'h100;
  localparam logic [31:0] BOOT_DONE  = 32'h0000_0001;
  localparam logic [31:0] FW_PASS    = 32'h0000_0002;
  localparam logic [31:0] FW_FAIL    = 32'h0000_00FF;
  localparam int unsigned FW_APB_TRANSFERS = 5;   // the boot firmware's bus transfers
endpackage

// ======================================================================= the bus
// Nets, not variables: two drivers that disagree resolve to X, which an assertion
// can see. A clocking output that is never written stays 'z (IEEE 1800-2023 §14.16),
// so a passive agent cannot disturb the bus.
interface apb_if (input logic clk, input logic rst_n);
  wire        psel, penable, pwrite, pready;
  wire [11:0] paddr;
  wire [31:0] pwdata, prdata;
  clocking drv_cb @(posedge clk);                 // used only when the agent is active
    default input #1step output #1;
    output psel, penable, pwrite, paddr, pwdata;
    input  pready, prdata;
  endclocking
  clocking mon_cb @(posedge clk);
    default input #1step;
    input psel, penable, pwrite, paddr, pwdata, pready, prdata;
  endclocking
endinterface

// =================================================================== the mini SoC
// The SPI block's register port: CTRL and TXDATA, no wait states.
module spi_regs
  import soc_map_pkg::*;
(
  input  logic        clk,
  input  logic        rst_n,
  input  logic        psel,
  input  logic        penable,
  input  logic        pwrite,
  input  logic [11:0] paddr,
  input  logic [31:0] pwdata,
  output logic [31:0] prdata
);
  logic [31:0] ctrl, txdata;
  always_ff @(posedge clk or negedge rst_n) begin
    if (!rst_n) begin
      ctrl   <= '0;
      txdata <= '0;
    end else if (psel && penable && pwrite) begin
      if (paddr == SPI_CTRL)   ctrl   <= pwdata;
      if (paddr == SPI_TXDATA) txdata <= pwdata;
    end
  end
  always_comb prdata = (paddr == SPI_CTRL)   ? ctrl   :
                       (paddr == SPI_TXDATA) ? txdata : '0;
endmodule

// The SoC: a CPU bus-functional model running the boot "firmware", the SPI block
// and a mailbox register at 0x100. The bus is inside the SoC; the interface port
// is the point where the testbench watches it.
module mini_soc
  import soc_map_pkg::*;
(
  apb_if bus
);
  logic        cpu_psel, cpu_penable, cpu_pwrite;
  logic [11:0] cpu_paddr;
  logic [31:0] cpu_pwdata, spi_rdata, mailbox_q;

  assign bus.psel    = cpu_psel;                  // the CPU is the only master
  assign bus.penable = cpu_penable;
  assign bus.pwrite  = cpu_pwrite;
  assign bus.paddr   = cpu_paddr;
  assign bus.pwdata  = cpu_pwdata;
  assign bus.pready  = 1'b1;                      // no wait states
  assign bus.prdata  = bus.paddr[8] ? mailbox_q : spi_rdata;

  spi_regs u_spi (
    .clk    (bus.clk),
    .rst_n  (bus.rst_n),
    .psel   (bus.psel && !bus.paddr[8]),          // 0x000-0x0FF is the SPI block
    .penable(bus.penable),
    .pwrite (bus.pwrite),
    .paddr  (bus.paddr),
    .pwdata (bus.pwdata),
    .prdata (spi_rdata)
  );

  always_ff @(posedge bus.clk or negedge bus.rst_n) begin
    if (!bus.rst_n) mailbox_q <= '0;
    else if (bus.psel && bus.penable && bus.pwrite && bus.paddr == MAILBOX)
      mailbox_q <= bus.pwdata;
  end

  // One APB write: a setup cycle (psel = 1), then an access cycle (penable = 1).
  task automatic apb_write(input logic [11:0] addr, input logic [31:0] data);
    @(posedge bus.clk);
    cpu_psel <= 1'b1;  cpu_penable <= 1'b0;  cpu_pwrite <= 1'b1;
    cpu_paddr <= addr; cpu_pwdata <= data;
    @(posedge bus.clk);
    cpu_penable <= 1'b1;
    @(posedge bus.clk);                           // pready = 1: completes at this edge
    cpu_psel <= 1'b0;  cpu_penable <= 1'b0;
  endtask

  task automatic apb_read(input logic [11:0] addr, output logic [31:0] data);
    @(posedge bus.clk);
    cpu_psel <= 1'b1;  cpu_penable <= 1'b0;  cpu_pwrite <= 1'b0;
    cpu_paddr <= addr;
    @(posedge bus.clk);
    cpu_penable <= 1'b1;
    @(posedge bus.clk);
    data = bus.prdata;                            // stable: no write is in progress
    cpu_psel <= 1'b0;  cpu_penable <= 1'b0;
  endtask

  // The boot firmware, reduced to the bus transfers it makes (5 of them).
  initial begin : firmware
    logic [31:0] rd;
    cpu_psel = 1'b0;  cpu_penable = 1'b0;  cpu_pwrite = 1'b0;
    cpu_paddr = '0;   cpu_pwdata = '0;
    @(posedge bus.rst_n);
    apb_write(MAILBOX, BOOT_DONE);                // 1: boot code finished
    apb_write(SPI_CTRL, 32'h9);                   // 2: enable the SPI block
    apb_read (SPI_CTRL, rd);                      // 3: firmware's own read-back
    apb_write(SPI_TXDATA, 32'hA5);                // 4: first byte to send
    apb_write(MAILBOX, (rd == 32'h9) ? FW_PASS : FW_FAIL);   // 5: verdict
  end
endmodule

// ============================================================= the UVM testbench
package soc_spi_pkg;
  import uvm_pkg::*;
  import soc_map_pkg::*;
  `include "uvm_macros.svh"

  // ------- the SPI block team's VIP and environment (reused; one SoC adaptation marked)
  class apb_item extends uvm_sequence_item;
    rand bit        write;
    rand bit [11:0] addr;
    rand bit [31:0] data;
    `uvm_object_utils_begin(apb_item)

      `uvm_field_int(data,  UVM_ALL_ON)
    `uvm_object_utils_end
    function new(string name = "apb_item");
      super.new(name);
    endfunction
    function string convert2string();
      return $sformatf("%s addr=0x%03h data=0x%08h", write ? "WR" : "RD", addr, data);
    endfunction
  endclass

  class apb_driver extends uvm_driver #(apb_item);
    `uvm_component_utils(apb_driver)
    virtual apb_if vif;
    function new(string name, uvm_component parent);
      super.new(name, parent);
    endfunction
    function void build_phase(uvm_phase phase);
      super.build_phase(phase);
      if (!uvm_config_db#(virtual apb_if)::get(this, "", "vif", vif))
        `uvm_fatal("NO_VIF", "apb_driver: no virtual interface")
    endfunction
    task run_phase(uvm_phase phase);
      forever begin
        seq_item_port.get_next_item(req);
        @(vif.drv_cb);
        vif.drv_cb.psel    <= 1'b1;               // setup cycle
        vif.drv_cb.penable <= 1'b0;
        vif.drv_cb.pwrite  <= req.write;
        vif.drv_cb.paddr   <= req.addr;
        vif.drv_cb.pwdata  <= req.data;

        vif.drv_cb.penable <= 1'b1;               // access cycle

        while (!vif.drv_cb.pready) @(vif.drv_cb);

        vif.drv_cb.psel    <= 1'b0;
        vif.drv_cb.penable <= 1'b0;
        seq_item_port.item_done();

    endtask

  class spi_reg_scb extends uvm_subscriber #(apb_item);
    `uvm_component_utils(spi_reg_scb)
    bit [31:0]   shadow [bit [11:0]];
    int unsigned n_match, n_mismatch;
    function new(string name, uvm_component parent);
      super.new(name, parent);
    endfunction
    function void write(apb_item t);
      if (t.addr[8]) return;                      // adapted for SoC: not SPI's window
      if (t.write) shadow[t.addr] = t.data;

        bit [31:0] exp = shadow.exists(t.addr) ? shadow[t.addr] : '0;  // reset 0
        if (t.data == exp) n_match++;
        else begin
          n_mismatch++;
          `uvm_error("SPI_SCB", $sformatf("read 0x%03h: got 0x%08h, expected 0x%08h",
                                          t.addr, t.data, exp))
        end
      end
    endfunction
    function void report_phase(uvm_phase phase);
      `uvm_info("SCB_SUMMARY", $sformatf("matches=%0d mismatches=%0d pending=0",
                                         n_match, n_mismatch), UVM_LOW)
    endfunction
```

### How to bring a block environment into the SoC

1. **List every interface of the SoC DUT** and, for each, who drives it in the SoC test. That answer is each agent's mode: passive where an on-chip master drives, active where the bench plays an off-chip device.
2. **Nest the block environments unchanged** inside the SoC environment, and set each agent's mode with an exact path relative to the test (or through the block's configuration object).
3. **Audit the build** in `end_of_elaboration_phase`: an automatic mode check plus `print_topology()`.
4. **Decide keep, adapt or disable for every reused check**, with an owner, and adapt expectation sources to come from monitors.
5. **Write the firmware contract** in one shared package: mailbox address, codes, events, timeouts, and what is checked during boot.
6. **Decode the mailbox into events** and wait on milestones with `wait_on()`, inside a watchdog.
7. **Add one register predictor per bus** that can write registers, and turn auto-predict off where explicit predictors exist.
8. **Add SoC-only checks:** interconnect routing, interrupts, security and the liveness properties, each with an owner.
9. **Prove every monitor saw the traffic the test promised** in `check_phase`.
10. **Write the mutants** (agent left active, wrong `vif` path, wrong transfer count) and prove each one fails with a named message.

### Worked strategy: one page for the DMA subsystem

The planned M8 code capstone verifies a DMA subsystem: a DMA engine with an APB register port and an AXI master port, an AXI interconnect with an AXI-to-APB bridge in front of that register port, an SRAM and a DDR controller model, and a completion interrupt to the CPU. At subsystem level the CPU is a bus-functional model with its own AXI master port into the interconnect, running firmware-style bus scripts. Through the interconnect it reaches both the DMA's registers (via the bridge) and the SRAM. A one-page strategy for it, in the shape of the artifact table:

| Area | Decision |
|---|---|
| Scope | Block team owns DMA descriptor parsing and AXI protocol corner cases. Subsystem owns routing, ordering through the interconnect, completion interrupts, resets during transfers and error responses. |
| Test layers | Block TB (DMA alone, AXI slave responder); subsystem TB (this one: DMA plus interconnect plus memory models, with a CPU BFM on its own AXI master port); SoC TB later with the RTL CPU running driver firmware. |
| Reuse | `dma_blk_env` nested unchanged. Its APB agent goes passive, because the CPU BFM now drives the register port through the bridge (at block level the agent played the CPU). Its AXI responder is disabled, because real memory models answer. Its AXI monitor stays on the DMA's master port. The interrupt line gets a monitor only. |
| Checkers | Keep the descriptor scoreboard, adapted to build its expectations from monitored traffic (the APB register writes and the CPU's descriptor writes to SRAM) instead of from block sequences; add a memory scoreboard per region, a routing scoreboard on the interconnect, and an interrupt checker. |
| Register prediction | One predictor on the APB monitor; auto-predict off. Descriptor memory is a `uvm_mem`, so it is checked by backdoor reads, not prediction. |
| Liveness | Every accepted AXI request gets a response (bounded in simulation, strong in formal); every enabled completion raises the interrupt within a budget. |
| Scenarios | Reset during a burst; DECERR on a descriptor pointing into a hole; back-to-back descriptors; two channels competing for DDR. |
| Coverage | Descriptor type × target region × response; reset × transfer phase; interrupt × channel. |
| Regression and gates | Smoke: one transfer per channel; nightly: random descriptors over many seeds; sign-off: all P0/P1 rows closed, liveness proven, no open failure. |
| Risks | The interconnect model lags the RTL; descriptor-memory backdoor paths change with the netlist. |

## Push Further

### Expert: liveness in simulation versus formal

In `assert property` an unqualified sequence is weak (IEEE 1800-2023 §16.12.2), so `req |-> ##[1:$] resp` can never fail on a finite trace. `strong(...)` and `s_eventually` (§16.12.13) make the obligation strong: in formal, a counterexample is an infinite path (a loop) on which the response never comes, which is exactly the deadlock you want to find. In simulation, a strong obligation still pending when the run ends is reported in a tool-dependent way: some simulators report it as a failure at the end of simulation, some only in a coverage or "incomplete" report. Do not rely on that report for sign-off. The working pattern is a pair: the strong property for formal, and a bounded `##[1:MAX]` safety version for simulation, where `MAX` is a budget the architecture can justify. A bounded property that is too tight fails on legal congestion; one that is too loose detects nothing within the test length. Formal liveness proofs also need **fairness** assumptions (for example, that every slave behind the interconnect eventually asserts its `READY` signals), or the tool finds trivial counterexamples where the environment simply stalls; [E-INT-1](/curriculum/T4_Expert/E-INT-1_Integrating_UVM_with_Formal_Verification/index) covers writing those assumptions.

### Expert: SoC register models and prediction at scale

- **One predictor, one map.** `uvm_reg_predictor` holds one `map` and one `adapter` and looks registers up by offset in that map (IEEE 1800.2-2020 §19.3.2.3; uvm-core 2020.3.1 `uvm_reg_predictor.svh`). A register reachable from three buses needs three predictors, each bound to the map that describes that bus's addresses.
- **Bridges translate addresses.** If a monitor sits behind a bridge that remaps addresses, its predictor must use a map with the remapped offsets, or prediction silently finds no register.
- **Memories.** "Memories can be large, so their accesses are not predicted" (§19.3). Firmware-visible memory is checked by a memory scoreboard or by backdoor reads, never by the mirror.
- **Backdoor writes and the mirror.** IEEE 1800.2-2020 §18.4.4.11 says `poke()` "is affected by the auto-prediction configuration", but uvm-core 2020.3.1 (`uvm_reg.svh`) calls `do_predict` after every `poke()` regardless. Write code that does not depend on the difference: after a backdoor load, call `predict()` or `mirror()` explicitly.
- **The two defaults of §18.2.5.2.** The clause says both that "the default value of on shall be 1" and that "when on is False (the default)" bus traffic does not update the mirror. uvm-core resolves it: the *argument* of `set_auto_predict()` defaults to 1, and the *map's mode* starts at 0. Calling `set_auto_predict()` with no argument turns it on.
- **Volatile and side-effect registers.** Clear-on-read and hardware-updated status fields cannot be predicted from bus traffic alone; mark them volatile and check them with a scoreboard that knows the hardware events.

### Expert: firmware and testbench synchronization races

- `uvm_event::wait_trigger()` misses a trigger that happened earlier in time, and §10.1.1.2.4 notes a race even within one time slot (the "same delta"). `wait_ptrigger()` (§10.1.1.2.5) avoids the same-slot race but still needs the trigger to be in the current time slot. For milestones, `wait_on()` (§10.1.1.2.2) is the robust choice; call `reset()` on the event only if the milestone can legitimately happen twice (for example, a warm reboot), and then only from a point where no waiter can miss the next trigger.
- Event pool keys are plain strings: a typo (`"fw_boot_dn"`) silently creates a second event that nobody triggers. Keep the keys in the shared contract package.
- Firmware time is long: a test should log firmware milestones with their simulation time and the image hash, so a slow boot can be told apart from a hang.
- If the bench must *drive* firmware decisions (inject an interrupt "when firmware reaches state X"), synchronize on the mailbox code for state X, never on a fixed delay that a firmware change will break.

### Expert: what block checks need at the interconnect

- **ID widening.** The interconnect appends master-port bits to `ARID`, `AWID` and `WID`, so slave-side IDs are wider (IHI0022E §A5.3.5). A routing scoreboard needs the interconnect's port numbering, or it correlates by address and order at each master instead.
- **DECERR from a default slave.** The specification recommends routing undecodable accesses to a default slave that answers DECERR, and requires all data transfers of the transaction to complete even so (§A3.4.4). A scoreboard must expect the full data phase of a failed burst, not an early stop.
- **Security.** `AxPROT` carries privileged, secure and instruction attributes (§A4.7). A security policy scoreboard predicts allow or deny per master × privilege × region, and the security liveness property becomes a safety property: a denied access never reaches the protected slave.
- **Ownership.** Each reused check gets one owner who signs the keep, adapt or disable decision. Duplicated checks with different expectations produce two contradictory error streams for one bug, which slows triage more than a missing check.

### Expert: CDC and RDC sign-off (tool-dependent)

Structural CDC tools classify crossings (single-bit control, multi-bit data, handshakes, FIFOs), check synchronizer structures and **reconvergence** (two separately synchronized signals that recombine and can arrive one cycle apart), and report glitch-prone combinational logic before a synchronizer. RDC analysis finds asynchronous resets that can corrupt a capture in another reset domain. Formal tools can then prove protocol rules on handshakes. Metastability-injection simulation, where the tool randomly delays a synchronizer's output by a cycle, is a vendor feature; its name, switches and coverage differ per tool. For integration, Accellera's Standard for IP Abstraction for Clock and Reset Domain Crossing Integration 1.0 (approved in 2026) defines how an IP provider describes its crossings so the SoC analysis need not re-read the IP's RTL. The strategy's job is to name the owner of the CDC/RDC report, the waiver reviewer, and the gate.

### Expert: the cost of one SoC simulation (tool-dependent)

A single SoC test can spend most of its time booting. Common tactics, all tool-dependent in how they are switched on:
- **Checkpoint and restore:** save the simulation state after boot and restore it for each test, so boot runs once per regression rather than once per test.
- **Swap firmware without recompiling:** pass the image name as a plusarg, read it with `$value$plusargs` (IEEE 1800-2023 §21.6) and load it with `$readmemh` (§21.4).
- **Separate compilation and partitioning:** compile stable IP once and reuse the compiled library across bench changes.
- **Log volume:** a SoC log with every monitor at full verbosity is too large to read; set verbosity per component from the command line (`+uvm_set_verbosity`, IEEE 1800.2-2020 Annex G.2.3) and keep transfer-level prints at `UVM_HIGH`.
- **Faster CPU models** for long firmware flows (an ISS or BFM, with the RTL core reserved for the tests that need it).

### Expert: scaling out to emulation and portable tests (methodology)

Tests that run for millions of cycles (operating-system boot, performance runs) move to emulation or FPGA prototypes. The bench must change for that. It splits into two tops: everything timed (the clock and reset generators, and the pin-level parts of drivers and monitors, rewritten as BFMs) moves into the HDL-side top, which is compiled into the emulator with the DUT. The host-side (HVL) testbench of classes (sequences, driver and monitor proxies, scoreboards, coverage) becomes untimed: no `#` delays, no clock waits and no polling of DUT signals, because each one is a synchronization point between the host and the emulator. The two sides talk in whole transactions, and checks must tolerate reduced visibility inside the emulator; [E-EMU-1](/curriculum/T4_Expert/E-EMU-1_Emulation_Aware_Verification/index) covers the split and its coding rules. Writing one scenario once and running it in simulation, on the emulator and on silicon is what the Portable Test and Stimulus Standard is for; [the PSS bridge page](/curriculum/T4_Expert/E-SOC-1_SoC-Level_Verification_Strategies/pss) shows where it fits in this strategy and [E-PSS-1](/curriculum/T4_Expert/E-PSS-1_Portable_Stimulus_Standard/index) teaches the language.

### Expert: regression economics and closure gates (methodology)

- **Flaky tests** (pass or fail on the same seed and hashes) destroy trust in every gate. Quarantine them with an owner and a deadline instead of rerunning until green.
- **Seeds and reproducibility:** a failure is only actionable if its seed, hashes and plusargs reproduce it; random stability rules are in [I-SV-2B](/curriculum/T2_Intermediate/I-SV-2B_Advanced_Constrained_Randomization/randomization-methods).
- **First-failure signatures:** bucket failures by the first error message and its component, so 200 failures from one bug count as one bucket ([E-DBG-1](/curriculum/T4_Expert/E-DBG-1_Advanced_UVM_Debug_Methodologies/index)).
- **Coverage per hour:** rank tests by the new coverage they add per CPU hour and retire those that add nothing, but keep a fixed set of directed tests that guard known bugs.
- **Gates are policy.** Numbers such as "N clean nightlies" are agreed by the project and written in the strategy; there is no standard threshold, and claims of one should be treated as unverified.
