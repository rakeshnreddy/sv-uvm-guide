## Quick Take

- **What it is:** An **emulator** is a machine that runs a compiled hardware copy of your design in special-purpose hardware: arrays of custom processors, custom chips or FPGAs. It is much faster than simulating the design in software on an ordinary computer, the **host** (or workstation). **Emulation-aware verification** is the set of testbench changes that let a UVM bench keep up with it. The timed part of the bench, which wiggles the pins every clock, moves into the emulator next to the design under test (DUT). The untimed UVM part (sequences, scoreboard, coverage) stays on the host. The two parts then talk in whole transactions instead of stopping each other on every clock edge.
- **Why it matters:** Boot, firmware and long-traffic tests need billions of clock cycles, which no simulator finishes in a working day. How a bench is written decides how much of the emulator's speed you actually get. Mentor reported co-emulation running 60× to 491× faster than simulation on six designs of 1 to 34 million gates (DVCon US 2011, Table 1). Synopsys's customer table shows 1.5× to 80× when the bench still talks to the emulator signal by signal, against 25× to 2091× when it talks in transactions (DVCon US 2019). Both are vendor-authored figures. The gap between those two ranges is what this lesson teaches.
- **The Analogy:** A factory floor (the emulator) and its head office (the host). If the office phones the floor before every hand movement, the machines spend most of the day waiting for the phone. If the office sends whole work orders, the floor runs flat out between orders, and the office only hears back when an order is done. *Where it breaks:* while the office is still writing the next order, the floor stands still. In the standard co-emulation models, hardware time is frozen while host code runs (SCE-MI 2.4 §4.4.4), so a slow office slows the floor even when it never phones. And the office cannot watch every machine all the time: seeing inside the emulator costs capacity, speed or storage.

**You will be able to:**
1. **Explain** why per-cycle synchronization between a host testbench and an emulated DUT limits throughput, and **predict** how many synchronization points a pin-level driver and a split driver need for one burst.
2. **Refactor** a UVM driver and monitor into BFM interfaces in an HDL-side top and untimed proxy classes in an HVL-side top, with fixed-size packed types and converters for the data that crosses.
3. **Apply** the coding rules for each side (an untimed HVL side, the HDL side's synthesizable subset, clocks and resets in the HDL top, the SCE-MI 2 argument types and calling rules) and **debug** a co-emulation run that compiles badly or barely speeds up.
4. **Choose** debug-visibility options (full-visibility capture, probes, triggers and capture windows, in-emulation assertions, reproduction in simulation) for a failure, and **state** what each one costs.
5. **Compare** simulation, emulation and FPGA prototyping for a verification goal, quoting vendor claims with their source and date.

## Build Your Mental Model

### Words you need first

This lesson builds on agents, virtual interfaces and the configuration database from [A-UVM-8](/curriculum/T3_Advanced/A-UVM-8_Multi_Agent_Topologies/index), on DPI from [I-SV-7](/curriculum/T2_Intermediate/I-SV-7_DPI_and_Foreign_Language_Interfaces/index), and on measuring where a bench spends its time from [E-PERF-1](/curriculum/T4_Expert/E-PERF-1_UVM_Performance/index). A few new words come up on every page of emulation documentation, so here they are in one place.

| Term | Plain meaning |
|---|---|
| **synthesizable** | Code a compiler can turn into hardware: flops, gates and memories. A class object or a `#10` delay is not; an `always_ff` block is. Emulator compilers accept more than ASIC synthesis does, and *how much* more is tool-dependent. |
| **host** | The ordinary computer that runs the simulator and the UVM classes. |
| **HDL side** | Everything that runs in the emulator: the DUT plus the timed testbench code next to it. HDL means hardware description language. |
| **HVL side** | Everything that stays on the host: the class-based, untimed part of the bench. HVL means hardware verification language. |
| **BFM** (bus functional model), also **transactor** | Code that turns a transaction into clocked pin activity, or pin activity back into a transaction. In this lesson it is an **interface** that holds the protocol's signals plus the tasks and functions that drive and sample them. |
| **proxy** | The class that stands in for a BFM on the HVL side. It keeps the UVM driver's or monitor's place in the agent, but touches no pins: it only *calls* its BFM. |
| **synchronization point** | A moment where the host and the emulator must agree on time before either can go on: every clock edge, delay or signal change the host code waits on, and every call across the boundary. |
| **gates** (MG, BG) | Capacity in equivalent logic gates: millions (MG) or billions (BG). Vendors quote capacity this way. |

### Three ways to run a design, and four ways to use an emulator

You can run the same RTL in three kinds of engine.

- **RTL simulation.** A simulator runs the design as software on the host. You get every language feature, 4-state values (X and Z) and any waveform you ask for, but a big SoC runs very slowly.
- **Emulation.** The design is compiled into an emulator. The three main product families are built very differently, and the differences matter for this lesson:
  - **Cadence Palladium** uses custom Cadence emulation processors (Palladium Z3, announced 2024-04-18, quoted at 16 million to 48 billion gates).
  - **Siemens Veloce Strato CS** uses Siemens' purpose-built Crystal accelerator chip (announced 2024-02-20).
  - **Synopsys ZeBu** uses commercial FPGAs: ZeBu EP1 used Xilinx Virtex UltraScale+ VU19P devices and was quoted at "10 MHz" and up to 2 billion gates (2021-05-13); ZeBu-200 uses AMD Versal Premium VP1902 devices (2025-02-13).
- **FPGA prototyping.** The design is placed and routed onto FPGA boards, mainly so software teams can run real software on it early. Examples: Cadence Protium X3 (AMD VP1902, 2024-04-18), Siemens Veloce Primo CS and proFPGA CS (AMD VP1902, 2024-02-20), and Synopsys HAPS-200 (quoted at "up to 10s of MHz", 2025-02-13).

Every number above is a vendor claim with the date it was made. Product generations change every few years, so date any figure you repeat.

An emulator can be used in several **use modes**. A speed-up figure means nothing until you know which one it was measured in.

| Use mode | What runs on the host | What runs in the emulator | How they talk |
|---|---|---|---|
| **Signal-level acceleration** (simulation acceleration) | the unmodified UVM bench, drivers and monitors included | the DUT | pin values, every time the host code waits on a clock or a signal |
| **Transaction-based acceleration** (co-emulation, co-modeling) | the untimed UVM part: sequences, proxies, scoreboard, coverage | the DUT plus the BFMs | calls that carry whole transactions |
| **In-circuit emulation** (ICE) | run control and debug only | the DUT, wired through **speed bridges** to real devices | real interface traffic, rate-adapted |
| **Standalone** | nothing but run control | the DUT plus a fully synthesizable testbench | none during the run |

A **speed bridge** (Cadence SpeedBridge; Synopsys calls them ZeBu Speed Adapters) is hardware that connects the slowly running emulated design to a real device running at full speed, such as a PCIe link, by buffering and rate-adapting its traffic (Cadence, 2013-07-29; Synopsys, 2021-05-13). It is not the link between the emulator and your UVM bench. This lesson is about the second row, co-emulation, because that is where a UVM bench lives.

The engines also differ in ways a speed number hides. Here they are side by side, in qualitative terms.

| | RTL simulation | Emulation | FPGA prototyping |
|---|---|---|---|
| **Speed** | slowest; falls as the design grows | far faster; how much depends on the use mode and the bench (figures in Quick Take) | usually the fastest of the three, built for running software |
| **Turnaround after an RTL change** | a recompile, minutes for most blocks | an emulator compile; Cadence quotes "10 billion gates in under 10 hours" for Palladium Z2 (2021-04-05) | FPGA place and route, usually the longest |
| **Debug visibility** | any signal you choose to dump; dumping costs run time and disk | depends on the platform: full-visibility capture on some, chosen probes on others | depends on the platform; generally less than emulation |
| **Value system** | 4-state (X and Z propagate) | usually 2-state; X and Z are coerced | 2-state |
| **Typical goal** | block and subsystem verification; all detailed debug | SoC tests, OS boot, firmware, long traffic, power and performance runs | software development and system validation |

The value-system row needs one more sentence. SCE-MI 2.4 §5.6.1.3.1 says that when the hardware side supports only 2 states, an X arriving from the software side is coerced to 1 and a Z to 0, and warns that a model using 4-state types may then give results that differ from a 4-state simulator. A reset or initialization bug that shows up as X in simulation can be silent on an emulator.

**Misconception: "the emulators are interchangeable."** They are not. A processor-based emulator, a custom-chip emulator and an FPGA-based emulator differ in compile turnaround, run speed, capacity and how much you can see. A methodology tuned for one, such as a vendor's transactor pragmas or debug flow, does not carry over unchanged to another.

### Why an unmodified bench gains little speed

Start with the bench you already know. Its driver reaches the DUT's pins through a **virtual interface** (a class handle to an interface instance, IEEE 1800-2023 §25.9) and times every drive and sample with the interface's **clocking block** ([F4C](/curriculum/T1_Foundational/F4C_Clocking_Blocks/index)). Here is a correct pin-level driver task for an AXI write burst with a fixed length of four beats. It follows the VALID/READY rule: a transfer happens on a rising clock edge where both VALID and READY are high (Arm IHI0022E §A3.2.1; see [B-AXI-1](/curriculum/T3_Advanced/B-AXI-1_AXI_Channel_Architecture/index)).

```systemverilog
// snippet: a pin-level driver task (class axi_wr_driver, simulation only).
// AWSIZE, AWBURST, AWID and WSTRB are left out: the slave assumes full-width INCR.
task drive_burst(axi_wr_item req);
  @(vif.drv_cb);                                  // align to a clock edge
  vif.drv_cb.awaddr  <= req.addr;
  vif.drv_cb.awlen   <= 8'd3;                     // 4 beats
  vif.drv_cb.awvalid <= 1'b1;
  do @(vif.drv_cb); while (!vif.drv_cb.awready);  // AW handshake
  vif.drv_cb.awvalid <= 1'b0;
  for (int i = 0; i < 4; i++) begin
    // Drive beat i in the same time step as beat i-1's handshake: no idle edge.
    vif.drv_cb.wdata  <= req.data[i];
    vif.drv_cb.wlast  <= (i == 3);
    vif.drv_cb.wvalid <= 1'b1;
    do @(vif.drv_cb); while (!vif.drv_cb.wready); // beat i handshake
  end
  vif.drv_cb.wvalid <= 1'b0;
  vif.drv_cb.wlast  <= 1'b0;
  vif.drv_cb.bready <= 1'b1;
  do @(vif.drv_cb); while (!vif.drv_cb.bvalid);   // B handshake
  vif.drv_cb.bready <= 1'b0;
endtask
```

Two details make this correct. A clocking-block input such as `vif.drv_cb.wready` is the value sampled just *before* the edge (default input skew `1step`, IEEE 1800-2023 §14.3), which is exactly what a flop in the DUT sees. And a drive such as `vif.drv_cb.wdata <= …` executed right after `@(vif.drv_cb)` changes the signal in the Re-NBA region of that same time step (§14.16), so the next beat appears straight after the edge that accepted the previous one.

**Classic mistake: the extra edge per beat.** A very common version puts an `@(posedge vif.aclk)` at the *top* of the beat loop and then waits for WREADY. After beat 0's handshake, that extra wait spends one more edge with WVALID still high and WDATA still holding beat 0, so a slave that keeps WREADY high accepts beat 0 twice. Trace it with WREADY held at 1:

| Edge | WVALID | WDATA on the bus | What the slave does |
|---|---|---|---|
| n | 1 | D0 | accepts D0 (handshake of beat 0) |
| n+1 | 1 | D0 (the loop-top wait, nothing re-driven) | accepts D0 **again** |
| n+2 | 1 | D1 | accepts D1 |
| n+3 | 1 | D1 | accepts D1 **again** |

Four beats become seven transfers, and WLAST arrives on the wrong count. The fix is the one above: drive the next beat in the same time step as the previous handshake.

Now put that driver on the host and the DUT in an emulator. The host and the emulator are two separate machines with separate notions of time. Each time the driver executes `@(vif.drv_cb)`, the host must tell the emulator "run until the next edge", and the emulator must report back the sampled READY before the host can decide what to drive next. That round trip is a **synchronization point**, and while one side works the other waits. Synopsys's guidance for signal-level acceleration puts it bluntly: when host code advances time, "HW needs to sync with SW every event clock" (DVCon US 2019).

**Predict first.** Use the DUT model from Make It Work: it accepts AW at once, stalls the first W beat for one cycle, and returns B on the edge after the last beat. How many times does `drive_burst` wait for an emulator edge in one burst? And if the whole task moved into the emulator so the host made one call per burst, how many calls would there be? Write both numbers down, then read the diagram.

**Debrief.** The driver waits 8 times: one alignment edge, one for the AW handshake, five for the W channel (four beats plus one stall) and one for B. With the burst moved into the emulator the host makes **one** call, and all eight edges run at emulator speed. A real burst with more beats or more stalls has proportionally more round trips, and the monitor, which waits on every edge, adds one per clock on top. That is why the signal-based rows in Synopsys's table sit at 1.5× to 80× while the transaction-based rows reach 25× to 2091×.

**Misconception: "a standard UVM bench runs unmodified on an emulator at emulator speed."** It usually *runs*: in signal-level acceleration the tool keeps the bench on the host and exchanges pin values. It just gains little, because the bench's own waits set the pace. The speed comes from moving the waits into the emulator, which is the split below.

### The split: a BFM in the HDL top, an untimed proxy in the HVL top

The method that makes one bench run well in both simulation and co-emulation has three steps (van der Schoot et al., DVCon US 2011 §4):

1. Use **two top-level modules**. `hdl_top` holds everything that must run in the emulator: the DUT, the clock and reset generators, and the BFMs. `hvl_top` holds everything else and calls `run_test()`.
2. Move every timed line of the driver and the monitor into **BFM interfaces** under `hdl_top`. A BFM is an `interface`, not a module, so the HVL side can still reach it through a virtual interface handle.
3. Make the driver and the monitor **proxies**: they keep their place in the UVM agent, but reach their BFMs only by calling the BFMs' tasks and functions (IEEE 1800-2023 §25.7). No class reads or writes a pin.

**The driver BFM.** All the clocked code of `drive_burst` moves, almost unchanged, into a task inside the BFM interface. The task takes the whole burst as one fixed-size packed argument. The full interface is in Make It Work; this is its heart:

```systemverilog
// snippet: inside interface axi_wr_bfm (HDL side)
task automatic write_burst(input axi_wr_burst_t burst);
  @(drv_cb);
  drv_cb.awaddr  <= burst.addr;
  drv_cb.awlen   <= 8'(BEATS - 1);
  drv_cb.awvalid <= 1'b1;
  do @(drv_cb); while (!drv_cb.awready);
  drv_cb.awvalid <= 1'b0;
  for (int i = 0; i < BEATS; i++) begin
    drv_cb.wdata  <= burst.data[i];
    drv_cb.wlast  <= (i == BEATS - 1);
    drv_cb.wvalid <= 1'b1;
    do @(drv_cb); while (!drv_cb.wready);
  end
  drv_cb.wvalid <= 1'b0;
  drv_cb.wlast  <= 1'b0;
  drv_cb.bready <= 1'b1;
  do @(drv_cb); while (!drv_cb.bvalid);
  drv_cb.bready <= 1'b0;
endtask
```

**The driver proxy.** What is left in the class is the part that was never timed: get an item, convert it, call the BFM, report done.

```systemverilog
  bfm.wait_for_reset();                 // the BFM counts the clocks, not the class
  forever begin
    seq_item_port.get_next_item(req);
    sent_ap.write(req);                 // expected stream for the scoreboard
    bfm.write_burst(req.to_packed());   // one call: all edges run in the emulator
```

**The monitor pushes instead of pulling.** A monitor proxy that called a BFM task such as `bfm.wait_for_burst()` in a loop would make the host start and wait for every burst. It is better for the monitor BFM to watch the pins on its own and *push* each completed burst to its proxy (DVCon US 2011 §4.3.2). To do that, the BFM holds a handle to its proxy, a **back-pointer**: the proxy writes `bfm.proxy = this;` through its virtual interface, and the BFM calls `proxy.burst_seen(b)` at the end of each burst. `burst_seen` is a `void` function, so it consumes no time. Calls from the HDL side to the HVL side must be functions, never time-consuming tasks, because only the HDL side has clocks (DVCon US 2011, footnote to §4.3.2).

**Debrief against your prediction.** Eight host round trips became one call and one return, plus one one-way call from the monitor. Some tools go further and dispatch one-way void calls without even stopping the emulator clocks (Veloce TBX, DVCon US 2011 §4.3.2). That is a tool-dependent extension: in the standard SCE-MI 2 models, hardware time is frozen while the software side is called (SCE-MI 2.4 §4.4.4).

**The rules for the HVL side.** The HVL side must be **untimed**: no `#` delays, no waits on clocks (`@(posedge vif.aclk)`, `@(vif.drv_cb)`), no waits on DUT signals (`wait (vif.done)`), and no polling of HDL signals (DVCon US 2011 §3). Waits on *abstract* events are fine. A UVM driver blocking in `get_next_item`, a proxy waiting on a class event, a test waiting for the scoreboard's count: none of these advance hardware time. SCE-MI's own proxy example waits on an event after each call (SCE-MI 2.4 §4.7.9.3.1).

**What moves and what stays.**
- BFMs are statically elaborated with `hdl_top`, so they cannot be created by the UVM factory or configured through `uvm_config_db`. The proxies can, and they control their BFMs by calls (DVCon US 2011 §5).
- Only fixed-size, packed data crosses the boundary. A class handle or a dynamic array cannot be an argument to a BFM task that becomes hardware. Each item therefore gets a pair of **converters**: `to_packed()` turns the class into a packed struct, `from_packed()` turns it back (DVCon US 2011 §4.3.1 recommends one converter per transaction type).
- Where the virtual interface handles come from varies by tool. This lesson's example sets them from `hvl_top` with the hierarchical names `hdl_top.drv_bfm` and `hdl_top.mon_bfm`, the only cross-references between the tops. Some emulation flows want the binding written inside `hdl_top` with a tool pragma instead. Check your tool's documentation.

**One portability trap in the standard.** It is tempting to give the BFM interface a port of the pin interface type, as the 2011 paper's samples do (`interface fpu_monitor_bfm(fpu_pin_if fpu_pins)`). IEEE 1800-2023 §25.9 makes that illegal as soon as you declare a virtual interface of the BFM's type: "it shall be illegal to use an interface containing those references in the declaration of a virtual interface." Give BFMs plain signal ports, or declare the signals inside the BFM itself, as Make It Work does.

**Packing order across the boundary.** A packed struct is just a bit vector with named fields, and "the first member specified is the most significant" (IEEE 1800-2023 §7.2.1). On the C side of a DPI call it arrives as a canonical bit-vector array, least significant word first. SCE-MI 2.4 §5.6.1.3.3 traces exactly this example:

| | SystemVerilog side | C side, naive | C side, correct |
|---|---|---|---|
| Declaration | `typedef struct packed { byte unsigned idNum; int unsigned value; } TransactionType;` | `struct { unsigned char idNum; unsigned value; };` | `struct { unsigned value; unsigned char idNum; };` (order reversed) |
| Bit layout | bits 39:32 = `idNum`, bits 31:0 = `value` | first member at the lowest address | first member at the lowest address |
| What C reads for `{ idNum = 1, value = 32'hbeefcafe }` | | `idNum` gets the low byte of `value` (`8'hfe`), and `value` reads the word that holds `idNum` (1 in its low byte) | `value = 32'hbeefcafe`, `idNum = 1` |

The naive C struct is also padded after its byte field, so even the widths do not line up. The portable fix is to reverse the field order on the C side, as the standard shows, or to pack the fields explicitly with `svPutPartselBit` and `svGetPartselBit`. A UVM-to-BFM converter in pure SystemVerilog, like the one in Make It Work, does not have this problem, because both ends use the same packed type.

**Pitfalls of the split.**
- A `#` delay, clock wait or DUT-signal wait left in a proxy: the bench still works in simulation, but in co-emulation every such wait is a synchronization point.
- An HDL-to-HVL call that is a task, or a function that calls a task: the HDL side cannot wait for the host to consume time.
- A dynamic array, queue, class handle or non-constant string as a BFM argument: the emulator compiler rejects it, or the tool falls back to slow signal-level communication.
- A class that reads a DUT signal through a virtual interface "just for a check": that is a cross-boundary access on every read.

### How the two sides talk: SCE-MI 2

The **Standard Co-Emulation Modeling Interface** (SCE-MI) is the Accellera standard for connecting HDL code running in an emulator or simulator to software models running on a host. The current release is SCE-MI 2.4 (November 2016). It defines three interfaces, each a use model of its own (SCE-MI 2.4 Clause 4):

- **Function-based:** a subset of SystemVerilog DPI. "The function call itself is the transaction" (§4.7.4).
- **Pipe-based:** one-way **transaction pipes** for streaming (§4.8).
- **Macro-based:** the message-passing interface from SCE-MI 1.1, with explicit clock control (§4.1).

**Myth to unlearn: "DPI cannot cross into the emulated design."** It is the other way round. In the function-based interface, DPI *is* the emulator transport. The synthesizable HDL-side transactor **calls** imported functions whose bodies are on the host, and **implements** exported functions that the host calls (§4.7.3, "Define a function in one language, call it from the other"). The emulator compiler maps those calls onto the link between emulator and host. What is restricted is the subset:
- **Argument types** (§5.6.1.3, Table 5.3): C-compatible integer types (`byte` to `longint`, signed or unsigned), `bit`, packed one-dimensional and multi-dimensional arrays of `bit` and `logic`, and packed structs. A `string` is allowed only for `import "DPI-C"` functions, that is from the HDL side to C, and only as a constant (§5.6.1.3.2). Class handles, dynamic arrays, queues and `chandle` arguments on the HDL side are not in the subset.
- **Time:** DPI functions always execute in zero time. SCE-MI supports DPI tasks too, but "No DPI imported task calls … can be time consuming" (§5.6.2.1).
- **Nesting:** two levels are required: the HDL side calls an import, which calls an export, which returns. Deeper chains are undefined in SCE-MI 2 (§5.6.2.3).
- **Many messages per time step:** several calls in the same time step are allowed and must be supported (§5.6.2.2, §4.9.8).
- **Frozen time:** in the function- and pipe-based models, "time on the HW side is frozen implicitly when the SW side is called" (§4.4.4).

**SV-Connect** is the part of SCE-MI 2 for SystemVerilog HVL benches like yours (§4.7.9, §5.6.3). The HVL side and the HDL side both declare DPI functions, and a thin C layer between them, which vendors are encouraged to generate automatically (§4.7.9.2.1), relays each call. HVL-side function names carry a prefix (default `svc`) and an extra first `chandle` argument naming the HDL scope (§5.6.3.1.1, §5.6.3.1.3). And SV-Connect is defined for **functions only**: a long operation is started by an inbound (HVL-to-HDL) function call and announced finished by a later outbound (HDL-to-HVL) call (§5.6.3.1.4). Expert: Standard SCE-MI 2 calls versus vendor BFM tasks, under Push Further, shows that pattern.

**Pipes** are for streams. A producer calls `send` and a consumer calls `receive`; input pipes carry data from the host to the HDL side, output pipes the other way. In **deferred visibility** mode a pipe may buffer elements, and the consumer sees them only when the pipe fills or is flushed. In **immediate visibility** mode the consumer sees each element the next time it gets control. A **flush** guarantees the writer that the reader has consumed what was sent (§4.8.1). Buffering lets many items share one synchronization.

Mentor's paper describes its remote calls as "inspired by" the SCE-MI 2 function model, with "extensions … most notably task calls in the workstation to emulator direction in which use of time-consuming/multi-cycle processing elements is allowed" (DVCon US 2011 §4.3). Synopsys documents a similar style for ZeBu, where UVM drivers and monitors call methods on BFM interfaces running in ZeBu (DVCon US 2019). The pattern simulates on any IEEE 1800-2023 simulator, which is why the lesson teaches it, but which emulators accept it, and with which pragmas, is tool-dependent.

### Practitioner depth: emulation-friendly coding rules

Each rule below has a reason, a symptom you will see if it is broken, and a fix. "Tool-dependent" means the rule's details differ between emulators, so check your tool's documentation.

| Rule | Why | Symptom if broken | Fix |
|---|---|---|---|
| The HVL side is untimed: no `#`, no clock or DUT-signal waits, no polling | each one is a synchronization point (DVCon US 2011 §3) | low speed-up; the profile shows synchronization dominating | move the wait into a BFM task, or have the BFM push an event by a void call |
| HDL-to-HVL calls are functions, preferably `void` | clocks exist only on the HDL side (DVCon US 2011 §4.3.2 footnote) | compile error, or the emulator stops for every call | make the callback a function; let the proxy do any waiting on HVL events |
| Only Table 5.3 types cross: integers, `bit`, packed arrays, packed structs | the SCE-MI 2 subset is what emulators synthesize (§5.6.1.3) | compile error, or a fall-back to slow communication | add packed types and `to_packed()`/`from_packed()` converters |
| HDL-side code stays within the tool's synthesizable subset | it must become hardware | emulator compile errors | tool-dependent: Veloce TBX documents implicit state machines, initial and final blocks, `wait`, named events and system tasks (DVCon US 2011 §4.1); ZeBu documents behavioral compilation of clocking blocks, `fork`/`join` and `wait` (DVCon US 2019) |
| Clocks and resets come from generators in `hdl_top` | an HVL clock is a synchronization on every edge (DVCon US 2019, "Moving clocks from SW to HW") | very low speed; host CPU busy toggling a clock | move the generators into `hdl_top`; some tools want a pragma, such as TBX's `// tbx clkgen` (DVCon US 2011, Sample A.1) |
| Keep one timescale across the project | the finest HDL precision sets the event-clock granularity: `#1` at 1ns/1ns on the host against 1ns/1fs in hardware gives "1,000,000 synchronization points" (DVCon US 2019) | unexplained slowness after a file with a fine `timeprecision` is added | one project-wide timescale, checked in simulation first |
| Covergroups live on the HVL side | DVCon US 2011 §5: synthesis "does not readily handle" covergroups | compile error or lost coverage | sample in the proxy, or in a subscriber of its analysis port; hardware coverage is tool-dependent (ZeBu documents an option for it, DVCon US 2019) |
| Protocol assertions can stay in the BFM or DUT | assertion synthesis exists on some platforms (TBX, DVCon US 2011 §5; ZeBu `assertion_synthesis`, DVCon US 2019) | assertions silently absent if not enabled | tool-dependent: enable assertion synthesis, or keep the checks in simulation runs |
| Report from the proxies, not from HDL code | whether `$display` in HDL code is accepted is tool-dependent (TBX synthesizes system tasks), and every HDL-side message is an HDL-to-HVL transfer | slow runs with heavy logging | pass status to the proxy and report there with `` `uvm_info `` |
| Expect 2-state behaviour | X and Z are coerced on 2-state engines (SCE-MI 2.4 §5.6.1.3.1) | a reset or initialization bug passes on the emulator but fails in simulation | keep X and reset checks in simulation runs of the same bench |

### Practitioner depth: getting software and data into the emulated design

The boot and firmware tests that justify an emulator need a program image in the DUT's memories before the processor comes out of reset. Loading it through the bus, one write per word, would cost a synchronization per word. Instead, emulation flows load memories directly, a **backdoor** load. SCE-MI 2.4 defines a C-side backdoor memory API, the direct memory interface (`scemi_mem_` calls), and a register access API (§4.11). Vendor flows add their own: Synopsys shows host code loading a memory inside ZeBu with `$readmemh` on the hardware hierarchy, and a run-time `memory -read|-write` command (DVCon US 2019). The same deck warns against "100k's" of individual backdoor accesses from the host, which are slow; load whole images instead. Exact commands are tool-dependent.

### Practitioner depth: what you can see inside an emulator

**Misconception: "emulation gives full waveform visibility for free."** Nothing gives it for free. Even in simulation, dumping waveforms costs run time and disk, which is why you dump selectively ([E-DBG-1](/curriculum/T4_Expert/E-DBG-1_Advanced_UVM_Debug_Methodologies/index)). On an emulator the options and their costs depend on the platform:

- **Full-visibility capture.** Cadence markets FullVision on Palladium and Protium, which captures all design signals without recompiling for each new set (Cadence product material). Siemens describes Veloce Strato CS as "maintaining full visibility" (2024-02-20). Capture still has a cost: the depth of the capture window, run speed while capturing, and host storage.
- **Probes and dump types.** On ZeBu, signals for waveform capture are grouped into value sets and dumped with dump types such as FWC, QIWC and dynamic probes, and some debug actions must be enabled when the design is compiled: forcing a hardware signal needs `zforce`, depositing needs `zinject`, and reading or breaking on a hardware signal needs `probe_signals` (DVCon US 2019). Each enabled feature costs compile work and capacity.
- **Triggers and capture windows.** You rarely capture a whole run of billions of cycles. You run to a **trigger**, such as an assertion failure, a signal value or a cycle count, and keep a window of cycles around it. Synopsys's own guidance: "Full vision is usually only achievable with a short run", so "run till first point of failure" (DVCon US 2019).
- **In-emulation assertions.** Assertions synthesized into the emulator watch every cycle at full speed and make ideal triggers, where the tool supports assertion synthesis.
- **Reproduction in simulation.** Once you know roughly when and where a failure happens, the same single-source bench can reproduce it in simulation with full 4-state visibility.

A workable flow for a failure deep in a long run:
1. Find the failure cheaply: an in-emulation assertion, a scoreboard error with a cycle count, or a bisection over check points.
2. Rerun with a trigger and a capture window placed just before the failure.
3. Read the captured window; force or deposit values only if the platform enabled it at compile time.
4. Reproduce in simulation with the same bench, starting from the closest point you can reach (a shorter test, or a saved state where the tool supports it), to get 4-state visibility and step-by-step debug.

### Practitioner depth: debugging a slow or broken co-emulation run

| Symptom | Likely cause | Fix |
|---|---|---|
| Speed-up of only a few times; the profiler shows synchronization or host time dominating | `#` delays, clock waits or HDL-signal polling left in proxies; an HVL clock generator | move waits into BFM tasks; move generators into `hdl_top` |
| Slower than expected after a "harmless" change | a new file with a finer `timeprecision`, which multiplies event-clock synchronizations | one project-wide timescale |
| Speed-up flat even with BFMs | the monitor BFM is pulled by its proxy (a call per burst *and* a wait), or HDL-to-HVL callbacks are tasks | push with a `void` function through a back-pointer |
| Host CPU at 100 %, emulator mostly idle | heavy HVL work per transaction: solver, logging, scoreboard (hardware time is frozen meanwhile, §4.4.4) | profile the host side ([E-PERF-1](/curriculum/T4_Expert/E-PERF-1_UVM_Performance/index)); lower verbosity; batch with pipes |
| Emulator compile fails in a BFM | a non-synthesizable construct for this tool, or a class type the BFM uses but does not import from a package | rewrite within the tool's subset; import the proxy's package into the BFM |
| Fields arrive garbled | packing-order mismatch between a packed struct and a C struct, or a converter that packs in the wrong order | one packed type on both ends, or reverse the C field order (§5.6.1.3.3) |
| Hang: the run stops advancing | a BFM waiting for a READY that never comes, with no timeout in hardware; or an HVL proxy waiting on an event the BFM never triggers | add a cycle-count timeout inside the BFM and report it through the proxy |
| Passes on the emulator, fails in simulation | 2-state coercion hides X (§5.6.1.3.1) | fix the reset or initialization bug; keep X checks in simulation |

Profilers that count synchronizations are tool-dependent. Synopsys documents VCS's `-simprofile` for finding `#` delays on the host and `-simxl=profile` for a communication profile of a simulation-acceleration run (DVCon US 2019).

### Recap: the mistakes everyone makes

- Expecting an unmodified bench to run at emulator speed. It runs, but its own waits set the pace.
- Leaving `#` delays, clock waits or DUT-signal polling in proxies after the split.
- Calling HVL tasks from the HDL side. Callbacks must be functions.
- Passing class handles, dynamic arrays or strings across the boundary instead of packed types.
- Treating "DPI does not cross into the emulator" as a rule. DPI is the standard transport, within a subset.
- Assuming full visibility is free, or that every emulator offers it the same way.
- Comparing speed-ups without asking which use mode and which bench produced them.

## Make It Work

### Worked example: an AXI write agent split for co-emulation

This is one complete file. It compiles on an IEEE 1800-2023 simulator with uvm-core 2020.3.1 and runs there as an ordinary simulation, which is how you prove the split is correct before an emulator compile. The protocol is an AXI4 write subset: fixed four-beat INCR bursts of 32-bit data, no AWSIZE, AWBURST, AWID or WSTRB, and the AW handshake before the first W beat. The DUT is a small synthesizable write-only memory that stalls the first W beat by one cycle.

Two notes on the code style. The usual convention of a single top module named `tb_top` does not apply here: co-emulation needs two tops, `hdl_top` and `hvl_top`, and the virtual interface handles are set in `hvl_top` before `run_test()`. And the BFMs use time-consuming tasks called from the HVL side, which is the vendor-extension style explained in "How the two sides talk"; tool pragmas, which differ by emulator, are left out.

```systemverilog
// compile
// axi_wr_split.sv: one file. Compile order matters: the package, then the
// interfaces that import it, then the DUT and the two tops.
`timescale 1ns/1ns
`include "uvm_macros.svh"

package axi_wr_pkg;
  import uvm_pkg::*;

  localparam int BEATS = 4;                  // every burst: AWLEN = BEATS-1

  // The only data that crosses HVL <-> HDL: fixed-size, 2-state, packed.
  typedef struct packed {
    bit [31:0]            addr;
    bit [BEATS-1:0][31:0] data;              // data[0] is the first beat
    bit [1:0]             resp;              // BRESP (unused on the way in)
  } axi_wr_burst_t;

  `uvm_analysis_imp_decl(_exp)
  `uvm_analysis_imp_decl(_obs)

  class axi_wr_item extends uvm_sequence_item;
    rand bit [31:0] addr;
    rand bit [31:0] data [BEATS];
    bit      [1:0]  resp;                    // 0 = OKAY, the expected response

    // 16-byte aligned inside a 256-byte slave: a burst never crosses 4KB.
    constraint c_addr { addr[3:0] == 4'h0; addr < 32'h100; }

    `uvm_object_utils(axi_wr_item)

    function new(string name = "axi_wr_item");
      super.new(name);
    endfunction

    // Converters: the only code that knows the packed layout.
    function axi_wr_burst_t to_packed();
      axi_wr_burst_t b;
      b.addr = addr;
      foreach (data[i]) b.data[i] = data[i];
      b.resp = resp;
      return b;
    endfunction

    function void from_packed(axi_wr_burst_t b);
      addr = b.addr;
      foreach (data[i]) data[i] = b.data[i];
      resp = b.resp;
    endfunction

    virtual function void do_copy(uvm_object rhs);
      axi_wr_item that;
      super.do_copy(rhs);
      if (!$cast(that, rhs)) `uvm_fatal("COPY", "not an axi_wr_item")
      addr = that.addr;
      data = that.data;
      resp = that.resp;
    endfunction

    virtual function bit do_compare(uvm_object rhs, uvm_comparer comparer);
      axi_wr_item that;
      if (!$cast(that, rhs)) return 0;
      return super.do_compare(rhs, comparer) && addr == that.addr &&
             data == that.data && resp == that.resp;
    endfunction

    virtual function string convert2string();
      return $sformatf("addr=%h data=%h %h %h %h resp=%0d",
                       addr, data[0], data[1], data[2], data[3], resp);
    endfunction
  endclass

      super.new(name);
    endfunction

    task body();
      repeat (n) begin
        req = axi_wr_item::type_id::create("req");
        start_item(req);
        if (!req.randomize()) `uvm_fatal("RAND", "axi_wr_item randomize failed")
        finish_item(req);
      end
    endtask
  endclass

  // Driver proxy: untimed. Every clocked line lives in axi_wr_bfm.
  class axi_wr_driver extends uvm_driver #(axi_wr_item);
    `uvm_component_utils(axi_wr_driver)
    virtual axi_wr_bfm bfm;
    uvm_analysis_port #(axi_wr_item) sent_ap;  // what was sent: expected stream

    function void build_phase(uvm_phase phase);

      expected.push_back(c);

    function void write_obs(axi_wr_item t);
      axi_wr_item e;
      observed++;
      if (expected.size() == 0) begin
        mismatches++;
        `uvm_error("SCB", {"unexpected burst: ", t.convert2string()})
      end else begin
        e = expected.pop_front();
        if (e.compare(t)) matches++;
        else begin
          mismatches++;
          `uvm_error("SCB", {"expected ", e.convert2string(),
                             " got ", t.convert2string()})
        end
      end
      -> burst_observed;
    endfunction

    function void check_phase(uvm_phase phase);
      super.check_phase(phase);
      `uvm_info("SCB", $sformatf("SCB_SUMMARY matches=%0d mismatches=%0d pending=%0d",
                                 matches, mismatches, expected.size()), UVM_NONE)
      if (expected.size() != 0)
        `uvm_error("SCB", "bursts were sent but never observed")
    endfunction

// Driver BFM: the AXI write signals, a clocking block and the clocked tasks.
// Plain signal ports (no interface ports), so a virtual interface may name it.
interface axi_wr_bfm (
  input  logic        aclk, aresetn,
  output logic [31:0] awaddr,
  output logic [7:0]  awlen,
  output logic        awvalid,
  input  logic        awready,
  output logic [31:0] wdata,
  output logic        wlast, wvalid,
  input  logic        wready,
  input  logic [1:0]  bresp,
  input  logic        bvalid,
  output logic        bready
);
  import axi_wr_pkg::*;

  // Default skews: inputs sampled just before the edge, outputs driven at it.
  clocking drv_cb @(posedge aclk);
    output awaddr, awlen, awvalid, wdata, wlast, wvalid, bready;
    input  awready, wready, bresp, bvalid;
  endclocking

  task automatic wait_for_reset();
    drv_cb.awvalid <= 1'b0;
    drv_cb.wvalid  <= 1'b0;
    drv_cb.wlast   <= 1'b0;
    drv_cb.bready  <= 1'b0;
    wait (aresetn == 1'b1);
    @(drv_cb);
  endtask

  task automatic write_burst(input axi_wr_burst_t burst);
    @(drv_cb);
    drv_cb.awaddr  <= burst.addr;
    drv_cb.awlen   <= 8'(BEATS - 1);
    drv_cb.awvalid <= 1'b1;
    do @(drv_cb); while (!drv_cb.awready);    // AW handshake
    drv_cb.awvalid <= 1'b0;
    for (int i = 0; i < BEATS; i++) begin
      drv_cb.wdata  <= burst.data[i];          // next beat right after the last
      drv_cb.wlast  <= (i == BEATS - 1);
      drv_cb.wvalid <= 1'b1;
      do @(drv_cb); while (!drv_cb.wready);   // beat i handshake
    end
    drv_cb.wvalid <= 1'b0;
    drv_cb.wlast  <= 1'b0;
    drv_cb.bready <= 1'b1;
    do @(drv_cb); while (!drv_cb.bvalid);     // B handshake
    drv_cb.bready <= 1'b0;
  endtask
endinterface

// Monitor BFM: watches the same signals and pushes each completed burst.
interface axi_wr_mon_bfm (
  input logic        aclk, aresetn,
  input logic [31:0] awaddr,
  input logic [7:0]  awlen,
  input logic        awvalid, awready,
  input logic [31:0] wdata,
  input logic        wlast, wvalid, wready,
  input logic [1:0]  bresp,
  input logic        bvalid, bready
);
  import axi_wr_pkg::*;

  axi_wr_monitor proxy;                        // set by the proxy: the back-pointer

  clocking mon_cb @(posedge aclk);
    input awaddr, awvalid, awready, wdata, wvalid, wready, bresp, bvalid, bready;
  endclocking

  initial begin : observe
    axi_wr_burst_t b;
    wait (proxy != null);
    wait (aresetn == 1'b1);
    forever begin
      do @(mon_cb); while (!(mon_cb.awvalid && mon_cb.awready));
      b.addr = mon_cb.awaddr;
      for (int i = 0; i < BEATS; i++) begin
        do @(mon_cb); while (!(mon_cb.wvalid && mon_cb.wready));
        b.data[i] = mon_cb.wdata;
      end
      do @(mon_cb); while (!(mon_cb.bvalid && mon_cb.bready));
      b.resp = mon_cb.bresp;
      proxy.burst_seen(b);                     // one-way void call to the HVL side
    end
  end
endinterface

// DUT: a write-only memory with one wait state on the first W beat.
// It ends a burst on WLAST and ignores AWLEN.
module axi_wr_mem (
  input  logic        aclk, aresetn,
  input  logic [31:0] awaddr,
  input  logic [7:0]  awlen,
  input  logic        awvalid,
  output logic        awready,
  input  logic [31:0] wdata,
  input  logic        wlast, wvalid,
  output logic        wready,
  output logic [1:0]  bresp,
  output logic        bvalid,
  input  logic        bready
);
  typedef enum logic [1:0] {IDLE, STALL, DATA, RESP} state_e;
  state_e      state;
  logic [5:0]  widx;                           // word index of the next beat
  logic [31:0] mem [64];

  assign awready = (state == IDLE);
  assign wready  = (state == DATA);
  assign bvalid  = (state == RESP);
  assign bresp   = 2'b00;                      // always OKAY

  always_ff @(posedge aclk or negedge aresetn) begin
    if (!aresetn) begin
      state <= IDLE;
      widx  <= '0;
    end else begin
      case (state)
        IDLE:    if (awvalid) begin
                   widx  <= awaddr[7:2];
                   state <= STALL;
                 end
        STALL:   state <= DATA;                // the one wait state
        DATA:    if (wvalid) begin
                   widx <= widx + 6'd1;
                   if (wlast) state <= RESP;
                 end
        RESP:    if (bready) state <= IDLE;
        default: state <= IDLE;
      endcase
    end
  end

  always_ff @(posedge aclk)
    if (state == DATA && wvalid) mem[widx] <= wdata;
endmodule
```

### How to split an agent, step by step

1. **Find the timed code.** In the driver and monitor, mark every line with `@`, `#`, `wait`, `##` or a read of a virtual-interface signal.
2. **Create the BFM interfaces.** One for driving, one for monitoring. Give them the protocol signals as plain ports (or as their own signals), a clocking block, and tasks that hold all the marked lines.
3. **Define the packed types.** One packed struct per transaction kind that crosses, built only from the Table 5.3 types. Add `to_packed()` and `from_packed()` to the item.
4. **Reduce the driver to a proxy.** It gets items, converts them, calls one BFM task per item, and reports done.
5. **Make the monitor push.** Give the monitor BFM a back-pointer to its proxy, set it in the proxy's `connect_phase`, and call a `void` function on the proxy for each completed transaction.
6. **Move clocks and resets** into `hdl_top`, with the DUT and the BFM instances.
7. **Hand over the handles.** In `hvl_top` (or wherever your tool wants the binding), set the virtual interface handles with `uvm_config_db` before `run_test()`.
8. **Prove it in simulation.** Run the same test and seed before and after the split; the scoreboard results and coverage must match.
9. **Audit the HVL side.** Search every class for `#`, clock waits, DUT-signal waits and polling loops. Event waits and blocking TLM calls may stay.

- [ ] I can count the synchronization points of a pin-level driver for one transaction, and say why the split version needs one call.

## Push Further

### Expert: Standard SCE-MI 2 calls versus vendor BFM tasks

The worked example calls a time-consuming task, `write_burst`, from the HVL side. Standard SV-Connect does not allow that: it "is defined for functions only", and a time-consuming operation is started by an inbound function and completed by an outbound function (SCE-MI 2.4 §5.6.3.1.4); DPI tasks must not consume time (§5.6.2.1). The same split in that style looks like this:

```systemverilog
// snippet: function-only handshake in the SCE-MI 2 style (shown with virtual-
// interface calls for readability; real SV-Connect uses DPI import/export pairs).
// HDL side, inside the BFM:
//   function void start_burst(input axi_wr_burst_t b);   // inbound, zero time
//     pending = b;  go = 1'b1;                           // an FSM picks it up
//   endfunction
//   ... at the B handshake: proxy.burst_done(bresp);      // outbound, void
// HVL side, in the driver proxy:
event done_ev;
function void burst_done(bit [1:0] bresp);   // called from the HDL side
  -> done_ev;
endfunction
task run_phase(uvm_phase phase);
  forever begin
    seq_item_port.get_next_item(req);
    bfm.start_burst(req.to_packed());        // returns at once
    @(done_ev);                              // an abstract event: allowed
    seq_item_port.item_done();
  end
endtask
```

Trade-offs to weigh at staff level:
- **Portability.** The function-only style follows the standard's rules; the task style depends on a vendor's extension, but reads exactly like the simulation driver it replaced (DVCon US 2011 §4.3).
- **Hardware design.** With functions only, the BFM's protocol logic must be an explicit state machine started by a flag; with tasks, the emulator compiler infers that state machine for you (implicit FSMs, DVCon US 2011 §2).
- **Interface ports.** The 2011 samples give BFM interfaces a pin-interface port, which IEEE 1800-2023 §25.9 forbids for any interface named by a virtual interface. Some tools accept it; standard-clean code does not need it.

### Expert: SCE-MI pipes and batching

Function calls are strictly reactive: one call, one return. For streams, SCE-MI 2 adds **transaction pipes** (SCE-MI 2.4 §4.8). They are unidirectional and named by the HDL endpoint's hierarchical path; both ends call into the pipe, one with `send` and one with `receive`. In **deferred visibility** mode the infrastructure may absorb elements on non-blocking sends and the consumer sees them only "until the pipe either fills or is flushed"; in **immediate visibility** mode the consumer sees each element the next time it gets control (§4.8.1). Batching is the whole point: many transactions share one synchronization. The price is latency and a harder end-of-test, because data can sit in a buffer: flush before you check, or your scoreboard reports pending items. Pipes also support variable-length messages with an end-of-message mark (§4.8.8) and multiple transactions in zero time (§4.8.8.1.3). A design that streams packets one way (video frames, network traffic) fits pipes; a register-access protocol that needs each response before the next request fits function calls.

### Expert: Throughput engineering

A useful mental model, illustrative rather than any vendor's formula: run time ≈ (emulated cycles ÷ emulator clock rate) + (number of synchronizations × (link latency + host work per synchronization)). Every technique in this lesson attacks one term:
- **Fewer synchronizations:** BFM tasks instead of pin waits; monitor pushes instead of pulls; pipes for streams. Synopsys's guidance is to "initiate all actions from HW as much as you can" and to keep the host side free of scheduling (DVCon US 2019).
- **Less host work per synchronization:** hardware time is frozen while the host side runs (SCE-MI 2.4 §4.4.4), so the constraint solver, `uvm_info` formatting and scoreboard searches all show up as emulator idle time. Profile the host side as in [E-PERF-1](/curriculum/T4_Expert/E-PERF-1_UVM_Performance/index).
- **No accidental synchronizations:** the timescale granularity trap (one `#1` at a coarse unit against a femtosecond hardware precision gives a million synchronization points, DVCon US 2019).
- **Tool-dependent optimizations:** Veloce TBX can dispatch one-way void calls without stopping the clocks (DVCon US 2011 §4.3.2). Synopsys reports that repeated `repeat (N) @(posedge clk)` waits on the host can be optimized "under the hood" in simulation acceleration, and that rarely changing signals can stay signal-level because only changes are communicated (DVCon US 2019). Measure before you rewrite.

Once synchronization is gone, the emulator's clock rate is the ceiling. That is when a bench is "emulation-bound", and only a faster platform, a smaller design partition, or fewer cycles per test help.

### Expert: Choosing a platform and use mode

Choose by the goal, then check the claims:
- **Debug turns per day** depend on compile turnaround. It differs by architecture: FPGA-based systems must run FPGA place and route, custom-silicon emulators have their own compilers. Vendors quote figures such as "10 billion gates in under 10 hours" (Cadence, Palladium Z2, 2021-04-05); treat them as claims for the vendor's chosen design.
- **Capacity** claims change with every generation: Palladium Z3 is quoted at 16 MG to 48 BG (2024-04-18), ZeBu EP1 at up to 2 BG (2021-05-13). Ask for the figure on a design like yours.
- **Speed** claims depend on the use mode. ZeBu EP1 was marketed at "10 MHz" and HAPS-200 at "up to 10s of MHz"; neither tells you what your co-emulation bench will reach.
- **Real interfaces:** in-circuit emulation with speed bridges exercises real devices and real software stacks; transaction-based "virtual" targets on the host are easier to control, reproduce and share. Teams often use both.
- **Hand-off to prototyping:** when the RTL is stable and the goal is running software at speed, FPGA prototyping takes over, with less visibility and longer compiles.
- **Scenario reuse:** a scenario described once can be targeted at simulation and emulation alike; see [E-PSS-1](/curriculum/T4_Expert/E-PSS-1_Portable_Stimulus_Standard/index).

### Expert: Debug at emulation scale

- **Capture strategy is a budget.** Full-visibility platforms still cost capture depth and host storage; probe-based flows also cost compile-time planning. Synopsys's own advice is to bring a design up "in the shortest running test available", because "full vision is usually only achievable with a short run" (DVCon US 2019).
- **Enable control early.** On ZeBu, forcing a hardware signal from the run-time shell requires `zforce` in the compile setup, depositing requires `zinject`, and watching or breaking on a hardware signal requires `probe_signals` (DVCon US 2019). Deciding this after the failure costs a recompile.
- **Triggers from assertions.** Synthesized assertions turn the emulator into its own logic analyzer: they watch every cycle and give you a precise trigger for the capture window.
- **Reproduce in simulation.** The single-source bench is the strongest debug tool you have. Reach the failure with a shorter test or a saved state, where the tool supports it, and debug there with 4-state values. Remember that a mismatch between the two may be 2-state coercion rather than a bug in either (SCE-MI 2.4 §5.6.1.3.1).
- **Backdoor access** (SCE-MI 2.4 §4.11) lets C code read and write memories and registers at one instant, which is how you check a firmware image or dump a buffer without a bus transaction.

### Expert: One bench for simulation and emulation

The goal of the dual-top method is a **single source** that runs in both, "without the use of hooks like compile-time or run-time switches that would disable entire branches of code" (DVCon US 2011 §3). Practical consequences:
- **Topology is static on the HDL side.** BFMs are elaborated with `hdl_top`; use a shared parameter package and conditional or loop `generate` blocks to instantiate the right number, and let the HVL side's dynamic proxies decide which ones are active (DVCon US 2011 §5). An `` `ifdef EMULATION `` that swaps whole drivers is two code bases.
- **The factory and `uvm_config_db` reach proxies, not BFMs.** Type overrides of a driver proxy work as usual; an override cannot change a BFM.
- **Coverage stays in classes**, assertions may go into hardware where the tool synthesizes them.
- **X checking stays in simulation.** Emulators are usually 2-state, so reset and initialization checks that rely on X need simulation runs of the same bench.
- **Prove equivalence regularly.** A nightly simulation run of the split bench with fixed seeds catches a proxy that has quietly grown a `#` delay.

### Kata: split a pin-level stream driver

Start from this single-top driver for a simple valid/ready byte stream: the DUT accepts a byte at an edge where `valid` and `ready` are both 1.

```systemverilog
// snippet: the starting point (one top, pin-level driver)
interface strm_if (input logic clk, input logic rst_n);
  logic       valid, ready;
  logic [7:0] data;
  clocking cb @(posedge clk);
    output valid, data;
    input  ready;
  endclocking
endinterface

class strm_item extends uvm_sequence_item;
  rand bit [7:0]    data;
  rand int unsigned gap;                     // idle cycles before the byte
  constraint c_gap { gap < 4; }
  `uvm_object_utils(strm_item)
  function new(string name = "strm_item"); super.new(name); endfunction
endclass

class strm_driver extends uvm_driver #(strm_item);
  `uvm_component_utils(strm_driver)
  virtual strm_if vif;
  // new() and a build_phase that gets vif are omitted
  task run_phase(uvm_phase phase);
    vif.cb.valid <= 1'b0;
    @(vif.cb iff vif.rst_n);
    forever begin
      seq_item_port.get_next_item(req);
      repeat (req.gap) @(vif.cb);
      vif.cb.valid <= 1'b1;
      vif.cb.data  <= req.data;
      do @(vif.cb); while (!vif.cb.ready);
      vif.cb.valid <= 1'b0;
      seq_item_port.item_done();
    end
  endtask
endclass
```

1. Predict: for an item with `gap = 2` and a DUT that holds `ready` low for one cycle, how many synchronization points does the pin-level driver spend on that item?
2. Write `strm_bfm`, an interface with the stream signals as its own ports, a clocking block, and the tasks `wait_reset()` and `send(input bit [7:0] data, input int unsigned gap)`.
3. Reduce `strm_driver` to a proxy whose `run_phase` contains no `@`, `#` or `wait`.
4. Write `hdl_top` (clock, reset, DUT, `strm_bfm`) and `hvl_top` (sets the virtual interface, calls `run_test()`).
5. Self-check: list every argument that crosses the boundary and confirm it is in Table 5.3.

<details>
<summary>Worked solution</summary>

1. **Four** waits on that item: `repeat (2)` waits twice, then the `do … while` loop waits once at the stalled edge and once at the accepting edge. The split version makes one call.

2. and 3.

```systemverilog
// snippet: the split (package and DUT omitted)
interface strm_bfm (
  input  logic       clk, rst_n,
  output logic       valid,
  output logic [7:0] data,
  input  logic       ready
);
  clocking cb @(posedge clk);
    output valid, data;
    input  ready;
  endclocking

  task automatic wait_reset();
    cb.valid <= 1'b0;
    wait (rst_n == 1'b1);
    @(cb);
  endtask

  task automatic send(input bit [7:0] d, input int unsigned gap);
    repeat (gap) @(cb);                      // idle cycles run in hardware
    cb.valid <= 1'b1;
    cb.data  <= d;
    do @(cb); while (!cb.ready);
    cb.valid <= 1'b0;
  endtask
endinterface

class strm_driver extends uvm_driver #(strm_item);
  `uvm_component_utils(strm_driver)
  virtual strm_bfm bfm;                      // got from uvm_config_db in build_phase
  function new(string name, uvm_component parent); super.new(name, parent); endfunction
  task run_phase(uvm_phase phase);
    bfm.wait_reset();
    forever begin
      seq_item_port.get_next_item(req);
      bfm.send(req.data, req.gap);           // one call per item
      seq_item_port.item_done();
    end
  endtask
endclass
```

4.

```systemverilog
// snippet: the two tops (strm_dut is your DUT with ports clk, rst_n, valid, data, ready)
module hdl_top;
  logic clk, rst_n, valid, ready;
  logic [7:0] data;
  initial begin clk = 1'b0; forever #5 clk = ~clk; end
  initial begin rst_n = 1'b0; repeat (4) @(negedge clk); rst_n = 1'b1; end
  strm_bfm bfm (.*);
  strm_dut dut (.*);
endmodule

module hvl_top;
  import uvm_pkg::*;
  initial begin
    uvm_config_db#(virtual strm_bfm)::set(null, "uvm_test_top.*", "bfm", hdl_top.bfm);
    run_test();
  end
endmodule
```

5. `d` is `bit [7:0]`, a packed array of `bit`; `gap` is `int unsigned`, a C-compatible integer type. Both are in Table 5.3. Note that `wait_reset()` and `send()` are time-consuming tasks called from the HVL side, so this split relies on the vendor-extension style; a function-only version would start the send with a function and report completion through a `void` callback.

### Debug challenge: five emulation killers

A colleague "split" an agent, but the emulator compile fails and, after a workaround, the run is barely faster. Find all five problems and give each fix.

```systemverilog
// snippet: the colleague's proxies (pkt_bfm and pkt_mon_bfm are HDL-side BFMs)
class pkt_driver extends uvm_driver #(pkt_item);
  virtual pkt_bfm bfm;
  task run_phase(uvm_phase phase);
    forever begin
      seq_item_port.get_next_item(req);
      #10ns;                                         // (A) "settle time"
      while (!bfm.ready_for_next) @(posedge bfm.clk); // (B)
      bfm.send(req.payload, req.get_name());         // (C) payload is byte payload[]
      seq_item_port.item_done();                     // (D) send's 2nd arg is a string
    end
  endtask
endclass

class pkt_monitor extends uvm_monitor;
  virtual pkt_mon_bfm bfm;
  uvm_analysis_port #(pkt_item) ap;
  // Called by pkt_mon_bfm for every packet: proxy.collect(p);
  task collect(pkt_packed_t p);                      // (E)
    pkt_item t = pkt_item::type_id::create("t");
    @(posedge bfm.clk);                              // "let the bus settle"
    t.from_packed(p);
    ap.write(t);
  endtask
endclass
```

<details>
<summary>Answers</summary>

- **(A) `#10ns` in the driver proxy.** A time advance on the HVL side, so a synchronization per item, and with a fine hardware precision possibly many more. Fix: remove it; if the protocol needs idle cycles, give `send` a cycle-count argument and wait in the BFM.
- **(B) Polling `bfm.ready_for_next` every clock.** A synchronization on every edge it loops over. Fix: wait inside the BFM (`send` waits for ready itself), or have the BFM push a `void` notification that the proxy waits for as an event.
- **(C) `byte payload[]` across the boundary.** Dynamic arrays are not in the SCE-MI 2 subset (Table 5.3), and the emulator compiler cannot build hardware for them. Fix: a fixed-size packed array with a length field, one call per beat, or an input pipe for variable-length data (§4.8.8).
- **(D) A `string` from HVL to HDL.** SCE-MI 2 allows strings only for `import "DPI-C"` functions (HDL to C), and only constant ones (§5.6.1.3.2). Fix: send a numeric id, or drop the name; report names from the proxy.
- **(E) The monitor BFM calls a task, and the task waits on a clock.** HDL-to-HVL calls must be functions, and the HVL side must not wait on clocks. Fix: make it `function void collect(pkt_packed_t p)`, with no clock wait; any settling belongs in the BFM before it calls.

(A), (B) and (E) make the run slow; (C), (D) and (E) are what break the emulator compile.

</details>
