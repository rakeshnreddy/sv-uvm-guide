**Expert (absent).** Push Further is four practice bullets. Add these `### Expert:` subsections, with the sources I verified:
1. **Time zero.** `initial` and `always` start in no implied order (§9.2). Declaration initialisers run before any procedure and create no event (§6.8, §10.5).
   - So `initial reset_n = 0;` can be missed by `always_ff @(posedge clk or negedge reset_n)`, and the page's own InteractiveCode ends with `q_out` = 0 or x depending on the simulator.
   - Fix: `reset_n <= 0;`. The LRM's own `forever` clock example initialises its clocks with `<=` (§12.7.6).
   - Within a process, the simulator may interleave other processes (§4.7).
2. **NBA ordering.**
   - Nonblocking updates happen in execution order, so `a <= 0; a <= 1;` leaves `a` = 1 (§4.6 b, §10.4.2).
   - `<=` with an intra-assignment delay schedules the update in a later time slot (§4.4.2.4).
   - Statements in one begin-end run in source order (§4.6 a). Races come from separate processes.
3. **Fork corner cases** (§9.3.2, §12.8).
   - Variables declared at the top of a fork are initialised before any child is spawned. That is why `automatic int k = i;` in the fork works while the same declaration inside a child `begin` does not; in the LRM's own example `m` reads 4.
   - `return` inside a fork is a compile error.
   - Inside `join_any`/`join_none`, formal `ref` arguments may only initialise fork-local variables unless they are `ref static`.
   - `break`/`continue` cannot control a loop outside the fork (§12.8).
4. **`disable` in depth.**
   - Disabling a task or block ends all its activations, automatic tasks included (§9.6.2).
   - A disabled loop-body block acts like `continue`. A block that is not executing is unaffected.
   - The outputs, pending NBAs and procedural continuous assignments of a disabled task are unspecified (§9.6.2).
   - `disable fork` also reaches descendants of children that have already finished (§9.6.3).
   - `process::kill()` likewise kills all descendants (§9.7). I-SV-5 owns the `process` class, so link to it.
5. **Thread hygiene at scale and in UVM.**
   - Every timer you do not kill stays a live process until it expires. The memory and run-time cost is tool-dependent; label it as such.
   - `wait fork` waits for every immediate child, monitors included (§9.6.1).
   - uvm-core 2020.3.1 uses the same guard idiom: `fork begin // guard … fork … join_any; disable fork; end join // guard` (`uvm_phase_hopper.svh:493-603`, `execute_phase`).
   - uvm-core also kills every task-phase thread when the phase ends (`uvm_task_phase.svh` header comment; `cleanup_phase` calls `m_phase_proc.kill()`, `uvm_phase_hopper.svh:677-692`). So a component's `forever` loop needs no cleanup, but a per-transaction timer inside a driver still does.
6. **Violation reporting** (flow-control page).
   - The check runs when the statement executes. The report matures in the Observed region, and is dropped if the procedure runs again first, which makes it immune to zero-delay glitches (§12.4.2.1, §12.5.3.1).
   - Severity and wording are tool-specific.
   - To silence the report during reset, use `$assertcontrol` or `$assertoff` with assertion_type 32 (unique), 64 (unique0) or 128 (priority) (§20.11, Table 20-6). Adding a `default` instead hides real bugs.
7. **X and the case family** (flow-control).
   - `casez`/`casex` treat don't-cares in the selector as well as in the items (§12.5.1).
   - `case inside` is asymmetric: x/z in an item are wildcards, x/z in the selector are not (§12.5.4, §11.4.6).
   - `unique casex` with selector `2'b1x` and items `2'b10`, `2'b11` reports an overlap.
   - How synthesis reads `unique`/`priority`, and how it treats `full_case`/`parallel_case` pragmas, is tool-dependent: label it.
8. **Loop corner cases** (flow-control).
   - A for-loop variable declared in the header is automatic, in an implicit block, and an x/z condition ends the loop (§12.7.1).
   - `repeat` evaluates its count once and runs zero times for a negative, x or z count (§12.7.2).
   - `foreach` loop variables are read-only, and resizing the array during the loop is undefined (§12.7.3).
   - `forever` with no timing control is a zero-delay infinite loop (§12.7.6).
   - `break` in a multi-dimensional `foreach` leaves the whole loop (§12.8).
9. **Interview angles** (staff level, attempt-first). Each must name its clause:
   - "Your timeout works with one transaction and loses responses with two in flight. Why?"
   - "Why do four forked senders all send id 4? Give two fixes."
   - "When does `wait fork` hang, and how do you wait for a bounded set of threads?"
   - "A `unique case` violation appears only at time 0. Bug or noise? How do you keep the check?"
   - "`casex` vs `case inside` with an x selector?"
   - "Can `break` inside a fork end the enclosing loop?"
