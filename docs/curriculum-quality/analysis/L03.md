### Depth ladder

**Practitioner (partial).** To add:
- **Queues.** `q[$]`, slices `q[a:b]` (a > b gives `{}`, a < 0 means `q[0:b]`, b > `$` means `q[a:$]`, x/z bounds give `{}`), and `q[$+1]` writes (legal). An invalid write is ignored with a required warning. `q = {q, x}` and `q = q[1:$]` give the same value as the methods, but they outdate references (§7.10.1, §7.10.3, §7.10.4).
- **Associative arrays.**
  - A `first()/next()` traversal loop (§7.9.4–§7.9.6).
  - Key types and their ordering (§7.8.1–§7.8.5).
  - Literals with a default (§7.9.11).
  - Allocation rules (§7.8.7).
  - Assignment and argument restrictions (§7.9.9, §7.9.10).
  - `delete(k)` of a missing key is silent (§7.9.2).
- **Methods.** The iterator argument, `item.index` (§7.12.4), `sort() with (item.field)` (§7.12.2), and `map()` labelled as 2023 with tool support varying (§7.12.5).
- **Query functions.** §20.7 and §20.7.1.
- **Array arguments.** By value vs `ref`/`const ref` (§7.7, §13.5.2).
- **A complete worked example.** The plain-SV tracker and sparse memory model, with expected output and a traced table.
- **A debugging table:** symptom → cause → fix → what the log shows.
- **When not to use each structure.**
  - A queue polled with `wait` vs a mailbox (F2D/ipc; IEEE 1800-2023 §15.4).
  - A dynamic array grown one element at a time (use a queue).
  - A string-keyed table where an enum key would catch typos.

**Expert (thin, not in `### Expert:` form).** Today there are five corner cases, a performance table, four Push Further bullets and four interview answers. Missing items:
1. **Ordering you can rely on.**
   - Strings sort lexicographically (§7.8.2). Integral keys sort numerically, signed or unsigned (§7.8.4).
   - Class-handle keys are "deterministic but arbitrary" (§7.8.3). User-defined keys without relational operators may vary "even between successive runs" (§7.8.5).
   - Locators traverse in an unspecified order (§7.12.1), and `unique()` order is unrelated to the array.
   - `min()`/`max()` return one element on ties (§7.12.1). §7.12.2 does not state that `sort()` is stable.
   - To keep logs reproducible, key by ID or sort the keys before printing. The actual orders are tool-dependent.
2. **Traversal and allocation corner cases.**
   - An index variable narrower than the key type makes `first()` return −1 and truncates. The LRM example: `byte ix` with key 1000 gives 232 (§7.9.8).
   - A wildcard `[*]` array cannot be used with `foreach`, with `first/next/last/prev`, or with index-returning methods (§7.8.1, §7.9.4–§7.9.7).
   - `a[k]++` and `ref` actuals allocate (§7.8.7).
   - A default does not change `exists()` or `num()` (§7.9.11).
   - x/z keys are invalid (§7.8.4, §7.8.6).
3. **Stale references and hidden copies.**
   - `new[]` outdates every reference to the array's elements (§7.5.1).
   - Queue methods keep references to the elements that survive; whole-queue assignment outdates all of them (§7.10.3).
   - Passing by value copies every array kind (§7.7).
   - `ref` needs an automatic subroutine and an equivalent type, so a queue cannot bind to `ref int a[]` (§13.5.2, §6.22.2(e)).
4. **Result types and widths.**
   - A reduction returns the element type or the `with` type (§7.12.3).
   - `sum() with (item > 4)` is 1 bit wide (§11.4.4), so three matches print 1.
   - Reductions over struct arrays need a `with`.
   - Index locators return `int`, or the key type for an associative array (§7.12.1).
   - The element type of `map()` is the self-determined type of the `with` expression (§7.12.5).
5. **Memory and performance at scale.** All implementation-dependent, so label it.
   - Keep the current table.
   - Containers of class handles keep objects alive (§8.29). 2023 `weak_reference` with `get_id()` keys avoids strong references (§8.30.5); tool support varies.
   - Delete per-ID queues when they empty.
   - `find*` is a linear scan on every call.
   - Do not pass large queues by value.
6. **The same structures inside UVM.**
   - `uvm_pool#(KEY,T)` is "a class-based dynamic associative array" (IEEE 1800.2-2020 §11.2).
   - Its `get()` allocates a missing key with the Table 7-1 value (§11.2.2.4), unlike a native read (IEEE 1800-2023 §7.8.6). This is where "phantom entries" come from.
   - uvm-core 2020.3.1 `uvm_resource_pool` keeps `rtab[string]` and `ttab[uvm_resource_base]`: associative arrays of resource queues keyed by name and by type handle.
7. **Staff-level interview angles.** See Assessment plan.

**## Make It Work**
- **### Worked example: an expected tracker and a sparse memory model in plain SV.**
  - The example: an associative array of queues, `exists()` before any read, a key deleted when its queue empties, a sparse memory with a warning-free read, and a `final` leftover report.
  - The outline below must compile on the CI simulator. Name the tool if the output comes from a real run.

  ```systemverilog
  // compile
  module tb_top;
    bit [31:0]   exp_by_id [int][$];   // expected data per ID, oldest first
    logic [31:0] mem [bit [31:0]];     // sparse memory: only written addresses exist
    int n_pass, n_fail;

    function automatic void add_expected(int id, bit [31:0] data);
      exp_by_id[id].push_back(data);   // first use allocates the key (§7.8.7)
    endfunction

    function automatic void check_actual(int id, bit [31:0] data);
      bit [31:0] expected;
      // exists() first: reading a missing key warns and returns an empty queue
      if (!exp_by_id.exists(id) || exp_by_id[id].size() == 0) begin
        $error("UNEXPECTED id=%0d data=%h", id, data);
        n_fail++;
        return;
      end
      expected = exp_by_id[id].pop_front();   // order must hold within one ID
      if (expected != data) begin
        $error("MISMATCH id=%0d exp=%h act=%h", id, expected, data);
        n_fail++;
      end else n_pass++;
      if (exp_by_id[id].size() == 0) exp_by_id.delete(id);  // num() = pending IDs
    endfunction

    function automatic logic [31:0] mem_read(bit [31:0] addr);
      return mem.exists(addr) ? mem[addr] : 'x;  // no warning for unwritten addresses
    endfunction

    initial begin
      add_expected(1, 32'hA1); add_expected(2, 32'hB1);
      add_expected(1, 32'hA2); add_expected(3, 32'hC1);
      check_actual(2, 32'hB1);   // legal: another ID overtakes ID 1
      check_actual(1, 32'hA2);   // DUT bug: ID 1 answered out of order
      check_actual(1, 32'hA1);
      // ID 3 never answers, so it stays pending
      mem[32'h1000] = 32'hDEAD_BEEF;
      $display("mem[1000]=%h mem[2000]=%h", mem_read(32'h1000), mem_read(32'h2000));
    end

    final begin
      foreach (exp_by_id[id])
        $display("PENDING id=%0d count=%0d", id, exp_by_id[id].size());
      $display("PASS=%0d FAIL=%0d PENDING_IDS=%0d", n_pass, n_fail, exp_by_id.num());
    end
  endmodule
  ```

  - Expected output (illustrative): two tool-specific `$error` lines for the MISMATCHes, then `mem[1000]=deadbeef mem[2000]=xxxxxxxx`, `PENDING id=3 count=1` and `PASS=1 FAIL=2 PENDING_IDS=1`.
  - Note: `exp_by_id[id].push_back()` on a new key relies on §7.8.7's read-modify-write allocation. A portable alternative is `if (!exp_by_id.exists(id)) exp_by_id[id] = {};`.
- **Traced table** (step → call → `exp_by_id` after → result):
  1. `add_expected(1, A1)` → `{1:[A1]}`.
  2. `add_expected(2, B1)` → `{1:[A1], 2:[B1]}`.
  3. `add_expected(1, A2)` → `{1:[A1,A2], 2:[B1]}`.
  4. `add_expected(3, C1)` → `{1:[A1,A2], 2:[B1], 3:[C1]}`.
  5. `check_actual(2, B1)` → `{1:[A1,A2], 3:[C1]}`: match, key 2 deleted.
  6. `check_actual(1, A2)` → `{1:[A2], 3:[C1]}`: MISMATCH, expected A1.
  7. `check_actual(1, A1)` → `{3:[C1]}`: MISMATCH, expected A2; key 1 deleted.
  8. `final` → PENDING id 3.
- **How-to (numbered):**
  1. Push the expected item when the request is seen.
  2. On a response, check `exists()` before reading.
  3. `pop_front` within the ID.
  4. Delete the key when its queue empties.
  5. Report the leftovers at the end.
  6. Make the bench prove it can fail (the swap above).
