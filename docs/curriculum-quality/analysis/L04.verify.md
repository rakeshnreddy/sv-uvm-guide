## Completeness and depth gaps the analyst missed

**Must-cover depth** (spine: "timing controls #, @, wait (§9.4)", "block statements and named blocks (§9.3)", flow control §12.5)
1. **Intra-assignment timing controls (§9.4.5).**
   - Forms: `a = #5 b;`, `q <= #1 d;` and `a <= repeat (n) @(posedge clk) d;`. The right side is evaluated now and assigned later.
   - Teach the LRM's race-free swap `fork a = #5 b; b = #5 a; join`.
   - This grounds Expert item 2 ("`<=` with an intra-assignment delay").
2. **Event expressions (§9.4.2, §9.4.2.1).**
   - `or` and `,` are synonyms, and `edge` means either edge.
   - An edge event is detected only on the LSB of a vector.
   - A change in an operand that does not change the expression's value is no event.
3. **What creates a process (§9.5).** Procedures, each statement of a fork, and dynamic processes. This is why `begin…end` cannot isolate `disable fork`. Cite it in the blocks H3 and in f2c-5.
4. **Block names and lifetime (§9.3.4, §6.21).**
   - A named block is a hierarchy scope.
   - Variables in a module's procedural blocks are static by default, and a declaration with an initializer needs explicit `automatic` or `static` (the LRM's `top_illegal` example).
   - That is why the fork-in-loop fix is `automatic int k = i;`, and why `int k = i;` does not compile there.
5. **Constant case expression (§12.5.2).** `unique case (1'b1)` one-hot decoding, which is also the form of the §12.5.3.1 glitch example. flow-control.mdx:72 says unique is "great for one-hot decoders" but never shows how.

**Expert layer**
6. **`final` corner cases (§9.2.3).**
   - Final procedures run as function calls from one process, in an arbitrary but deterministic order.
   - "No remaining scheduled events shall execute after all final procedures have executed", so anything a `final` schedules for later, such as a `$strobe`, never runs: print with `$display`. An NBA inside `final` is also outside §13.4.4's provision (the calling thread is not created by an initial or always procedure). Whether a tool errors or ignores it is unverified: label it tool-dependent.
   - `$finish` inside `final` ends the run at once.
   - Final procedures run on `$finish`. That they do not run on `$stop` is an inference from §20.2 (`$stop` only suspends); label it as such.
7. **No nonblocking writes to automatic variables (§6.21).** Once drivers are `task automatic` (spine rule 7), `<=` to a task-local variable is illegal; `<=` to module or interface signals is fine.
8. **Sensitivity differences (§9.2.2.2.1 vs §9.4.2.2).** `always_comb` leaves variables written in the block out of its sensitivity list. `always @*` includes them: the LRM's Example 2 lists `tmp1` and `tmp2`.
9. **Multiple processes (§12.4.2.2, §12.5.3.2).** Violation reports from a check inside a function called by several processes are queued per process.
10. **Evaluation order (§12.5.3).** Unique and unique0 items may be evaluated and compared in any order, and side effects in item expressions make the result nondeterministic.
11. **Interview angle on pragmas** (fixes the thin answer at flow-control.mdx:205).
    - `unique` checks overlap and no-match; `unique0` checks overlap only, so it is the closer analogue of a lone `parallel_case`.
    - IEEE 1800 does not define the pragmas, and how synthesis maps any of them is tool-dependent: label it.
    - Say "violation report", not "warning".

**Concept table**
12. Two "yes" cells should be "partial":
    - **"disable fork … isolated timeout", worked example.** The idiom uses an undeclared `rsp_seen`, assumes a 1 ns unit and has no expected output (L04-F2C-25).
    - **"initial / always / final", mechanism.** The §9.2.2.1 deadlock and the §9.2.3 rules are missing, as the report's own must-cover row says.
