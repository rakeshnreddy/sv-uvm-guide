**Expert (absent; 260-263 is three loose bullets).** Add, each as `### Expert:`:
1. **IEEE 1800.2-2020 text vs uvm-core 2020.3.1.**
   - `peek`/`poke`: §18.4.4.11–12 say they are "affected by the auto-prediction configuration". uvm-core calls `do_predict` unconditionally after the access (`uvm_reg.svh` `poke` ~2696, `peek` ~2765) and skips it only when status is not `UVM_IS_OK` (`do_predict`, `uvm_reg.svh:1637-1660`, warning `PREDICT_NOK`). Portable code may call `predict()` after `poke()`; it is harmless in uvm-core.
   - `mirror()`: §18.4.4.14 says the mirror "is then updated using the uvm_reg::predict method". uvm-core's frontdoor path predicts only when auto-predict is on (`uvm_reg.svh` `do_read`, `if (system_map.get_auto_predict())`); the backdoor path always predicts.
   - Policies: §18.5.4.6 lists 26 (a–z, including `NOACCESS`). uvm-core pre-defines 25 (`uvm_reg_field.svh:740-764`), and `configure(…, "NOACCESS", …)` reports "not defined. Setting to RW" (`uvm_reg_field.svh:477-481`).
   - Volatility: volatile ⇒ `UVM_NO_CHECK` is uvm-core (`uvm_reg_field.svh:466`). §18.5.3.2 says nothing about it, and §18.5.4.10 says only that the mirror "cannot be trusted".
   - `needs_update`: §18.5.5.8 says TRUE "if the field is writable and … needs to be updated". uvm-core also returns 1 for every writable volatile field (`uvm_reg_field.svh:1386-1392`).
2. **Map rights vs field access.**
   - §18.2.3.3: field access depends on both the field policy and the register's rights in that map. `get_access(map)` (`uvm_reg_field.svh:571-680`) maps W1C/RW/W1S… to RO under `"RO"` rights, and RW/WRC/WRS to WO under `"WO"` rights.
   - The frontdoor does not refuse a write through an RO map (`uvm_reg.svh` `do_write`); prediction uses the reduced access.
   - Overlapping RO and WO registers at one address are allowed (`uvm_reg_map.svh:715-723`).
   - Use the debug port as the legitimate case for `"RO"`.
3. **Bus width, byte addressing and endianness.** §18.1.2.3, §17.2.2.4; `uvm_reg_map.svh` `get_physical_addresses_to_map`, 1420-1446.
   - A 64-bit register on a 4-byte map is two accesses. `UVM_LITTLE_ENDIAN` puts the least-significant word at the lower address; `UVM_BIG_ENDIAN` puts the most-significant word there.
   - `UVM_LITTLE_FIFO`/`UVM_BIG_FIFO` reuse one address. `UVM_NO_ENDIAN` errors with `UVM/REG/MAPNOENDIANESS` for wider-than-bus registers.
   - `byte_addressing = 0` makes offsets count words.
   - Big-endian maps byte-swap the data (`perform_accesses`).
4. **Hierarchical models.**
   - Sub-block `configure(parent, hdl_path)` (§18.1.2.2); `add_submap` (§18.2.3.5); `set_base_addr` re-initializes a locked model's address map (§18.2.3.9; `uvm_reg_map.svh:1273-1284`).
   - Only the **root** map's sequencer and adapter are used (`get_sequencer`, `uvm_reg_map.svh:1077-1084`; `do_write` uses `get_root_map()`).
   - Root block names must be unique (`UVM/REG/DUPLROOT`, `uvm_reg_block.svh` `lock_model`).
5. **Backdoor write vs poke; HDL path forms.**
   - `write(…, UVM_BACKDOOR)` reads the register, applies each field's policy through `XpredictX`, deposits the result, and needs rights RW/WO (§18.4.4.9 "mimicked"; `uvm_reg.svh` `do_write` backdoor branch). `read(…, UVM_BACKDOOR)` writes back RC/RS side effects and masks WO fields. `poke` deposits the raw value.
   - Missing HDL path: a backdoor `read`/`write` falls back to the frontdoor with a warning ("No backdoor access available … Using frontdoor instead.", `uvm_reg.svh:2461-2467`), while `peek`/`poke` error.
   - Path forms: `add_hdl_path_slice` for per-field flops (§18.4.2.2, §18.4.6.5); `set_hdl_path_root` overrides ancestors (§18.1.6.11); the `kind` argument ("RTL", "GATE").
6. **Tool-dependent backdoor behaviour** (label it as such).
   - `uvm_hdl` is implemented per simulator (`src/dpi/uvm_hdl_questa.c`, `uvm_hdl_vcs.c`, `uvm_hdl_xcelium.c`, §19.6). The error `UVM/DPI/HDL_SET` "set: unable to locate hdl path (…) Either the name is incorrect, or you may not have PLI/ACC visibility to that name" means the path is wrong or the tool needs read/write visibility flags.
   - `+define+UVM_HDL_NO_DPI` compiles the backdoor off (`uvm_hdl.svh:71`, 148).
   - Vendor flag names: section unverified.
7. **Width limits and performance.**
   - `UVM_REG_DATA_WIDTH` and `UVM_REG_ADDR_WIDTH` default to 64 (`src/macros/uvm_reg_defines.svh:45-59`). `lock_model` fatals with "Register model requires that UVM_REG_DATA_WIDTH be defined as N or greater" (`uvm_reg_block.svh:1331`).
   - `+UVM_ENABLE_REG_LOOKUP_CACHE` / `set_reg_lookup_cache` (uvm-core impl., `uvm_reg_block.svh:1096-1119`) speeds up offset lookups in large models.
   - `uvm_mem` is not mirrored and not factory-registered, because of its constructor (§18.6).
8. **Concurrency.**
   - Each register access holds a per-register semaphore (`XatomicX`).
   - `set()` while the register is busy warns `UVM/FLD/SET/BSY` (`uvm_reg_field.svh:1179-1183`); `predict()` while busy fails.
   - `reset()` puts the semaphore back and clears busy for threads killed mid-access (§18.4.4.5; `uvm_reg.svh:1708-1720`). This is essential for mid-test reset (proposed A-UVM-9).
9. **Methodology trade-offs.**
   - Generated vs hand-written models.
   - Committing generated code vs generating at build time with a pinned generator.
   - Who builds and owns the model (env vs test).
   - Handing the model to sequences (env handle, config_db, or `uvm_reg_sequence::model`).
   - The adapter path vs a layered register sequencer (`set_sequencer` without an adapter → `uvm_reg_item`s on a register sequencer with `uvm_reg_sequence` as the translator, §19.4.1; `REG_NO_ADAPT`, `uvm_reg_map.svh:993-997`).
   - Customizing generated models without editing: factory type overrides, `uvm_reg_cbs` (A-UVM-4B).
10. **Staff-level interview angles** (attempt-first): listed under the target outline.
