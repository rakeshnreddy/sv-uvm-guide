## Completeness and depth gaps the analyst missed

Spot-check of the analyst's tables:
- Every "no" and "partial" in the must-cover table and the C1-C8 checklist is accurate. The page has no `barrier`, `reconfig`, `grab()` code, `Push Further`, `Make It Work`, `<BeforeYouStart />` or `<NextLesson />`.
- The visual's reset modes do sit behind an un-introduced "Show advanced" toggle (`MultiAgentCoordinationVisualizer.tsx:228-263`).
- No item marked covered is overstated.

Gaps to add to the target outline:
1. **No-argument `grab()`/`lock()` in a virtual sequence** (V03). This is a core pitfall of the must-cover item, not only an expert one.
2. **`uvm_event::reset()` semantics** (V02). Expert 3 should say: "`reset(0)` strands current `wait_trigger` waiters (uvm-core; IEEE 1800-2023 §15.5.5.1)". The "a second wait returns at once" debug row should use the fix "`reset()` when `get_num_waiters() == 0`, or `reset(1)`".
3. **The objection nuance for Expert 6 and L31-A8-07.**
   - uvm-core `kill()` drops the **automatic** phase objection (`uvm_sequence_base.svh` `kill`, the `m_safe_drop_starting_phase` calls).
   - A **manual** `raise_objection` inside a thread that is killed is never dropped.
   - The page should teach both, so learners do not conclude "every kill leaks an objection".
4. **The null-handle symptom depends on the virtual sequence's own sequencer.** The fallback takes the parent's sequencer, so:
   - with the handles-in-the-sequence style (`vseq.start(null)`, I-UVM-3B `virtual-sequences.mdx:100`), a child started on a null handle with `this` still hits `UVM_FATAL [SEQ]`;
   - only with a virtual sequence running on `v_sqr` does it hang.

   Add this to the debugging table row and to quiz Q3's explanation (uvm-core `set_item_context`).
5. **Nested locks (expert, optional).** §15.3.2.9 notes that a sequence holding a lock is still blocked while a child also holds one. This matters when the reconfiguration child grabs while its parent holds a `lock()` on the same sequencer.
6. **Pictures for practitioner concepts.** Sequential mid-stream reconfiguration (burst → drain → reprogram `MODE` → burst; objective 2, M5) has no picture in the outline; only the concurrent grab form gets a `SequenceDiagram`. Add a `<TimingDiagram>` with `MODE`, `din_valid`, `dout` and the scoreboard's expected mode, or a traced example.
