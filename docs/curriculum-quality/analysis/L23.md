*Handshake page*
1. **Response routing and the two ids.**
   - `set_id_info()` copies `sequence_id` and `transaction_id` (§14.1.2.4).
   - `send_request()` assigns a `transaction_id` only when it is -1, so a reused item keeps its first id (`uvm_sequencer_param_base.svh` 317-318).
   - The sequencer routes by `sequence_id`. A response for a sequence that has ended gives `UVM_WARNING [Sequencer] Dropping response for sequence N, sequence not found` (371).
   - `get_response(rsp, transaction_id)` (§14.3.3.3).
2. **IEEE 1800.2-2020 vs uvm-core 2020.3.1 on responses.**
   - The standard reports a queue overflow by default (§14.2.7.4, §14.2.7.5, §14.3.3.3). uvm-core initializes the enable bit to 0 (`uvm_sequence_base.svh` 174), so drops are silent.
   - §14.2.7.7 requires an error when the depth is set below the current count; uvm-core's `set_response_queue_depth()` does not check (1264-1266).
   - Tool-dependent: the `SQRPUT` check is compiled out when the vendor define `CDNS_NO_SQR_CHK_SEQ_ID` is set (`uvm_sequencer_param_base.svh` 352).
3. **Pipelined and multi-threaded drivers.**
   - `get()` is `get_next_item()` plus `item_done()` (§15.2.1.2.6), so `finish_item()` returns before the item is driven. Responses then go through `put()`, `put_response()` or `rsp_port.write()` (§15.2.1.2.8-9, §13.7.2.2, §15.4.3.1).
   - Two threads fetching at once gives `UVM_FATAL [SQRSNDREQGNI]`, because the request FIFO holds one item (`uvm_sequencer_param_base.svh` 261, 327-329).
   - `try_next_item()` waits `wait_for_sequences_count` NBA regions and reports `TRY_NEXT_BLOCKED` (`uvm_sequencer.svh` 238-310). The count is uvm-core only (`@uvm-accellera`), set through the config DB, and needed for stacked sequencers.
   - Coordinate with I-UVM-3A, whose plan (L22) also lists driver styles.
4. **Killed and stopped sequences.**
   - `kill()` (§14.2.5.11) and `stop_sequences()` (§15.3.2.14) remove a sequence's requests and locks.
   - §14.2.5.11 says `post_body`/`post_start` run after a kill; uvm-core kills the process that would run them (`uvm_sequence_base.svh` 933-989). Label the difference.
   - uvm-core process guards (`uvm_process_guard`, `@uvm-contrib`) report `SEQPRTZMB`/`SEQBDYZMB` and kill an orphaned sequence. `SEQREQZMB`/`SEQLCKZMB` report requests whose process died (`uvm_sequencer_base.svh` 599, 675).
5. **Hang triage at scale.**
   - `set_timeout()` (F.7.3.3: the default is implementation specific). uvm-core uses `UVM_DEFAULT_TIMEOUT` = 9200 s and ends with `PH_TIMEOUT` (`uvm_phase_hopper.svh` 587-589).
   - `+UVM_TIMEOUT=<integer>,<YES or NO>` (uvm-core impl.; the value is a count of time units).
   - `+UVM_OBJECTION_TRACE` (uvm-core impl.).
   - Sequencer probes: `get_current_item()`, `last_req()`, `last_rsp()` (§15.4.1, §15.4.2, §15.4.3.2), and `convert2string()`.
   - Link E-DBG-1.
6. **Interview angles** (attempt-first): see the target outline.

*Arbitration page*
1. **`lock()` in the standard and in uvm-core.**
   - §14.2.5.5: "A lock request is arbitrated the same as any other request. A lock is granted after all previously arbitrated requests are completed…"
   - uvm-core grants an unblocked lock at once (`m_lock_req` → `grant_queued_locks()`, `uvm_sequencer_base.svh` 1146-1157), ahead of older item requests.
   - A later `grab()` goes in front of an earlier waiting grab (`push_front`; the source notes "Missing: grabs get arbitrated behind other grabs", 1150).
   - Tool-dependent. Write tests that hold whichever reading applies: take the lock before queuing competing traffic.
2. **Custom arbitration with `UVM_SEQ_ARB_USER`.**
   - `user_priority_arbitration(avail_sequences)` receives indexes into the arbitration queue; `get_arbitration_sequence(i)` gives the sequence (§15.3.2.3, §15.3.2.4).
   - Returning anything else is a fatal ("Error in User arbitration", 798).
   - uvm-core returns early with 0 or 1 candidates (709-715), although §15.3.2.3 says the function "is called even if there is only one sequence available".
   - Example: round robin by sequence id, or oldest-first with ageing.
3. **Priority values and inheritance.**
   - Default 100 for a root sequence; a child takes its parent's priority (`start()`, `uvm_sequence_base.svh` 320-339; §14.2.5.2).
   - §14.2.5.2 says the value shall be ≥ 1. uvm-core fatals on an item priority ≤ 0 (`SEQITEMPRI`) and a sequence priority < 0 (`SEQDEFPRI`), so 0 is accepted for sequences (893-913).
   - An item priority overrides the sequence's.
4. **Fairness, starvation and randomness.**
   - STRICT modes starve lower priorities.
   - WEIGHTED and RANDOM draw with `$urandom_range` in the arbitration thread (IEEE 1800-2023 §18.14 random stability).
   - The sequencer waits for one NBA region before choosing (`uvm_wait_for_nba_region`, uvm-core impl.). The queue order of simultaneous starts is simulator-dependent.
   - Run regressions across modes.
5. **Locks, killed processes and process guards** (L23-3B-39).
6. **Interview angles.**

*Libraries page*
1. **The IEEE 1800.2 API vs uvm-core 2020.3.1.**
   - The standard's accessors `get/set_selection_mode`, `get/set_min_random_count`, `get/set_max_random_count` and `get_num_sequences_executed` (§14.4.4.1-§14.4.4.4) do not exist in uvm-core 2020.3.1. A grep of the whole release finds none. uvm-core exposes the public fields instead.
   - uvm-core requires `init_sequence_library()` in the subtype constructor (its own `SEQLIB/NOSEQS` text says so), while the §14.4.2 example constructor only calls `super.new(name)`.
   - Code written from the standard's text does not compile on uvm-core.
2. **Libraries as phase default sequences.**
   - Set `default_sequence` to the library type in the scope `<sqr>.<phase>_phase`, or use `+uvm_set_default_sequence` (G.2.9). The library then raises an objection on its starting phase (`uvm_sequence_library.svh` 707).
   - `pre_randomize()` reads the `default_sequence.selection_mode`, `default_sequence.min_random_count` and `default_sequence.max_random_count` knobs, or a `uvm_sequence_library_cfg` under `default_sequence.config` (611-642). These are uvm-core only; the class and the names do not appear in 1800.2-2020.
3. **Randomness and reproducibility.**
   - RANDC precomputes the whole run list before executing any member (body, RANDC branch).
   - It relies on the randc permutation being recomputed when the constraint changes (IEEE 1800-2023 §18.4.2: "recomputed whenever the constraints change on that variable").
   - Members are created by the factory each time, so type overrides apply.
4. **Biasing and coverage-driven selection.**
   - `UVM_SEQ_LIB_USER` with a weight per type.
   - A `dist` on `select_rand` in an extension (§14.4.4.7), only with indexes looked up through `get_sequence(i)`: static registration order is not defined.
   - Read `seqs_distrib` (`SEQLIB/DSTRB`, UVM_HIGH) per regression.
5. **When not to use a library.**
   - Members run one at a time on one sequencer; concurrent traffic needs several sequences or a virtual sequence.
   - A null sequencer is a fatal (`SEQLIB/VIRT_SEQ`, 691).
   - ITEM mode needs a sequencer of `REQ` (672).
   - Trade-offs against a randomized virtual sequence and PSS (link E-PSS-1).
6. **Interview angles.**

**`## Quick Take`**
- What it is, then why it matters: most "the test hangs at the timeout" bugs are a handshake rule broken on one side.
- **The Analogy:** a kitchen ticket rail.
  - A ticket (item) stays on the rail (request FIFO) until the cook rings it out (`item_done()`).
  - A plate (response) goes back to the table printed on the ticket (`sequence_id`), matched by order number (`transaction_id`).
  - *Where it breaks:* the rail holds one ticket, and a plate with no table number is not guessed; the kitchen stops (`SQRPUT`).
- Objectives; `<BeforeYouStart />`.

1. `### Recap: who blocks where`

   - `<AnimatedUvmSequenceDriverHandshakeDiagram initialPreset="missing_item_done" />`.

   - Debrief: a 5-row mapping preset → blocked side → log line → fix, which feeds the triage table below.
3. `### How a response finds its sequence`
   - `set_id_info()` copies two ids; `send_request()` assigns `transaction_id`; the sequencer looks up the sequence by `sequence_id`; then the queue or the handler.
   - Picture: `<SequenceDiagram>` "Response routing".
   - Pitfalls: no ids → `SQRPUT`; a reused item → repeated `transaction_id`; a late response → "Dropping response…".
4. `### Four ways to return a response`
   - Table: `item_done(rsp)`, `put_response(rsp)`, `put(rsp)`, `rsp_port.write(rsp)`, each with when to use it and the connection it needs.
   - Rule: one response per request unless the protocol defines more; never both `item_done(rsp)` and `put_response(rsp)` for one response.
5. `### Collecting responses`
   - `get_response(rsp)`, `get_response(rsp, tid)`.
   - Depth 8, `set_response_queue_depth(-1)`, the silent drop in uvm-core (L23-3B-36).
   - Picture: the visual's "Responses" and "Bug: responses never collected" presets.
6. `### Pipelined drivers and out-of-order responses`
   - The driver takes items with `get()` (or `get_next_item()` + `item_done()`) and answers later with `put()`.
   - The sequence calls `use_response_handler(1)` and overrides `response_handler()`, matching `get_transaction_id()`. Alternative: one thread per request calling `get_response(rsp, tid)`.
   - Picture: `<SequenceDiagram>` "Out-of-order responses".
   - Pitfalls:
     - handler on + `get_response()` → hang;
     - the handler is a function and must not block;
     - `body()` must wait for all responses before returning;
     - one new item per request.
7. `### Polling drivers`
   - `try_next_item()` returns null when nothing is ready in the current time step; `has_do_available()`.
   - Idle-cycle drivers; `get()` vs `get_next_item()`.
8. `### Hang signatures and triage`

  virtual function int unsigned select_sequence(int unsigned max);
