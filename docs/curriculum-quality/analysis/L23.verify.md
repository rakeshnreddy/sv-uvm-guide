## Completeness and depth gaps the analyst missed

**Practitioner and expert items not in the analysis:**
1. Nested-lock counting (V03) and the sequencer argument of `lock()`/`grab()` (V02). Both feed the card's must-cover "interrupt-driven stimulus (events plus `grab`)", whose virtual-sequence form needs `grab(sqr)`.
2. The request priority is captured at `start_item()`, and the standard is inconsistent about priority 0 (adjusted -06).
3. Libraries: uvm-core keeps a duplicate typewide registration on a macro subtype (adjusted -03).
4. Libraries: `remove_sequence()`. Per §14.4.5.5, removing a statically registered type updates every instance and warns if the type is absent. uvm-core removes only the first match from this instance, without a warning (`uvm_sequence_library.svh` 457-468). Add it to the libraries expert table.
5. Libraries: four logs belong in the debug list:
   - `SEQLIB/MIN_GT_MAX`;
   - `SEQLIB/MAX_ZERO`;
   - `SEQLIB/BASE_ITEM` (ITEM mode with REQ equal to `uvm_sequence_item`);
   - `SEQLIB/USER_FAIL`: an out-of-range `select_sequence()` result runs a REQ item instead of a member (`uvm_sequence_library.svh` 646, 656, 667, 773).
6. Responses collected by id overflow the queue (V04).
7. `DEVIATIONS.md` (2020.3.1) lists only two register-layer items and `apply_config_settings`. None of the sequencing differences in the analysis is documented there. Label them "observed in the uvm-core 2020.3.1 source", never "documented deviation".
8. In uvm-core, `has_do_available()` also counts a waiting lock request from an unblocked sequence (1335-1344). Mention it only if the polling-driver section uses `has_do_available()` to decide whether to call `get_next_item()`.
