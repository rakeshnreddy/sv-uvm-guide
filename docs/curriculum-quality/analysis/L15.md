**Expert: absent.** Add these `### Expert:` subsections (sources verified):
1. **Sampling corner cases:**
   - at time 0 every sampled value is its default sampled value (§16.5.1);
   - X→1 is a posedge (§9.4.2, Table 9-2), and whether a time-0 edge starts an attempt is tool-dependent;
   - a glitching clock is undefined (§16.5);
   - a clock expression uses current values while the same variable inside the assertion is sampled (§16.5.2);
   - `$rose` ≡ `$past(b) !== 1 && b === 1`, and `$stable` uses `===` (Annex F.3.4.4);
   - a clocking-block input used in an assertion must have `#1step` sampling (§16.5.1, §16.18);
   - a static loop variable in a procedural concurrent assertion checks the last index (§16.14.6.1).
2. **`disable iff` timing and reset strategy:**
   - the window runs from the attempt's start (Observed, inclusive) to its end (inclusive) (§16.12);
   - a reset asserted or released by a flop at edge k takes effect for the attempt at edge k itself (derived from §16.12 and §16.5.1);
   - the `$sampled(rst)` trade-off (§16.9.3);
   - `default disable iff` scope: nested declarations but not instances, cancelled only by `disable iff (1'b0)` (§16.15);
   - a comparison of disable iff, an antecedent guard, `$assertoff` and `$assertkill`.
3. **Vacuity, statistics and pass actions:**
   - the nonvacuity rules for `if`, implication and `disable iff` (§16.14.8 g, h, ag);
   - cover counters exclude disabled attempts (§16.14.3);
   - the pass action runs on vacuous success by default, and VacuousOff/`$assertvacuousoff` stops it without changing statistics (§20.11);
   - whether a tool reports an implication cover as "covered" through vacuous successes is tool-dependent; label it so.
4. **Glitches: deferred vs procedural concurrent assertions:**
   - `#0` can still glitch through Reactive→Active loops, while `final` cannot (§16.4.1);
   - procedural concurrent assertions mature in Observed and are flushed at flush points (§16.14.6, §16.14.6.2, §16.14.6.3).
   - The sub-lesson holds the details.
5. **Assertion control at scale:**
   - `$assertcontrol` control types (Lock, Unlock, On, Off, Kill, PassOff, FailOff, VacuousOff);
   - the assertion_type and directive_type masks (Tables 20-6 and 20-7), with `$assertoff` ≡ `$assertcontrol(4, 15, 7, …)`;
   - Off does not touch attempts in flight, while Kill aborts them and flushes pending deferred reports (§20.11).
6. **Performance and methodology:**
   - an attempt starts at every tick (§16.14.5);
   - long or unbounded windows keep many attempts alive (tool-dependent cost);
   - bounded waits, because pending attempts are not failures in `assert` (§16.12.2);
   - the copy cost of large dynamic structures (§16.6 note);
   - placement: interface vs bind vs checker vs inline;
   - SVA vs scoreboard;
   - formal reuse: `assume` constrains formal inputs and is checked in simulation (§16.2, §16.14.2), while `restrict` is formal-only (§16.14.4).
7. **Interview angles,** attempt-first. See the [assessment plan](#assessment-plan).

```systemverilog
  initial begin
    #10 a = 1'b1;
    #0  b = 1'b1;   // b follows a one Inactive pass later in the same time step (§4.4.2.3)
    #10 $finish;
  end
endmodule
```

   At t=10, `chk` runs with a=1, b=0. a1 reports a failure at once; a2 and a3 queue pending reports. In the next Inactive→Active pass, `b = 1` resumes `chk`. Resuming after an event control is a flush point (§16.4.2), so both pending reports are cleared and all three checks pass. The expected output is exactly one error (a1) at time 10. That follows from the reference algorithm (§4.4.2.3, §16.4.2); confirm it on a simulator or label it illustrative.
3. `### Deferred assertions: assert #0 and assert final` (§16.4, §16.4.1):
   - the expression is evaluated now and the report is deferred;
   - there is one report queue per process; the flush points are listed in §16.4.2;
   - an observed deferred report matures in Observed and its call runs in Reactive; a final deferred report matures and runs in Postponed;
   - each pass or fail statement is a single subroutine call;
   - by-value arguments are evaluated at once;
   - a final deferred call must be legal in Postponed;
   - deferred `assume` and `cover` exist;
   - static deferred assertions at module level behave as if inside an `always_comb` (§16.4.3);
   - `disable` of the assertion or of the procedure's outermost scope clears pending reports (§16.4.4).
4. `### Concurrent assertions, in one paragraph`: clocked, sampled, one attempt per tick; static vs procedural (§16.14.5, §16.14.6); link back to the index.
5. `### Picture`: V1 (the TimeSlotTraceVisualizer "assertion-kinds" scenario, or the static region ladder), with the prediction "how many reports does each assertion print?" and a debrief.
6. `### Choosing the kind`: a decision table.
   - A combinational invariant in an `always_comb` uses `assert #0` (or `final` when Reactive code may change inputs).
   - A procedural check in a TB class uses a simple immediate assertion.
   - A rule over clock cycles uses a concurrent assertion.
   - A check of an X-free bus at each edge uses a concurrent assertion with `!$isunknown`.
   - Pitfalls: a `#1` in `always_comb` is illegal (§9.2.2.2.2), and a `begin … end` in a deferred action block is illegal (§16.4).
