## Completeness and depth gaps the analyst missed

1. **The VIP sequence API (V06).** No subsection, concept row or picture covers the sequences a VIP ships. A VIP's sequences are how test writers use it.
2. **The coverage model (V07).** It is a core concept with no subsection and no picture. Add it to the list in -11 and to the Visual coverage table.
3. **Objections in the responder (V05).** A responder whose reactive sequence holds an objection hangs the test; this is a classic bug. Add it to the responder concept's pitfalls and debugging.
4. **Reset ordering of `item_done()` and `stop_sequences()` (V01).** This is a standard expert corner case. As written, Expert item 4 would teach a race.
5. **Which setting decides `is_active` (V03).** It is only in Expert item 5. It belongs in the core pitfall recap, because it causes exactly the SoC contention bug this lesson exists to prevent.
6. **Item design for a VIP with both roles (practitioner).**
   - The responder randomizes "only the response fields" (L30.md:221). That needs an item with separate request and response fields, using separate constraint blocks or `rand_mode`.
   - The self-test scoreboard needs `do_compare` and `convert2string`.
   - No concept row treats the item as the VIP's data API.
7. **Drivers that use `get()`.**
   - §14.2.6.3's NOTE says `finish_item` returns when the driver signals done "either explicitly via item_done … or implicitly via a call to get".
   - So "a forgotten `item_done` hangs `finish_item`" applies only to drivers that use `get_next_item`. Say so in Expert item 4, quiz 5 and Request 5.
