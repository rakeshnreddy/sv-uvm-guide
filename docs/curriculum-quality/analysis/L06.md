**`## Quick Take`**
- **What it is:** a SystemVerilog simulation is a discrete-event model (§4.3). Processes wake on events, and time jumps to the next non-empty time slot only when the current one is empty (§4.4). Every `#d` is a number interpreted in its module's time unit and rounded to its precision (§3.14).
- **Why it matters:** off-by-1000 delays, misleading log times and compile errors from missing time units are among the first bugs a new bench hits. Zero-time iterations explain why two prints "at the same time" show different values.
- **The Analogy:** a to-do list sorted by due time. You finish everything due now, including new items they create for now, then jump straight to the next due time without ticking through empty minutes. *Where it breaks:* "now" has ordered regions (F3B), and items in the same region may be done in any order (F3C).
- **You will be able to:** see Objectives.
- **Before you start:** F2C (procedures, `#`/`@`, `=` vs `<=`) and F2D (`$display`, format specifiers, `$finish`), linked.

**`## Make It Work`**
- **Worked example** (`// compile`): two modules with different units.
  ```systemverilog
  // compile
  module slow_gen;
    timeunit 10ns; timeprecision 1ns;
    initial begin
      #1.55 $display("slow: $time=%0d $realtime=%0.2f t=%0t", $time, $realtime, $realtime);
      #1.55 $display("slow: $time=%0d $realtime=%0.2f t=%0t", $time, $realtime, $realtime);
    end
  endmodule

  module tb_top;
    timeunit 1ns; timeprecision 100ps;
    slow_gen u_slow ();
    initial begin
      $timeformat(-9, 1, " ns", 0);   // every %t in the design prints ns with 1 decimal
      $printtimescale;                // this module
      $printtimescale(u_slow);        // the instance
      $printtimescale($root);         // global precision (simulation time unit)
      #1.55 $display("tb:   $time=%0d $realtime=%0.2f t=%0t", $time, $realtime, $realtime);
    end
  endmodule
  ```
  Expected output. Label it illustrative unless it was run, and say that the instance-name format of `$printtimescale` is tool-dependent:
  ```text
  Time scale of (tb_top) is 1ns / 100ps
  Time scale of (tb_top.u_slow) is 10ns / 1ns
  Time scale of ($root) is 100ps / 100ps
  tb:   $time=2 $realtime=1.60 t=1.6 ns
  slow: $time=2 $realtime=1.60 t=16.0 ns
  slow: $time=3 $realtime=3.20 t=32.0 ns
  ```
  (15.5 ns rounds to 16 ns and 1.55 ns to 1.6 ns, per §3.14.1. `$time` is an integer in each module's own unit, per §20.3.1.)
- **How-to:**
  1. Declare `timeunit`/`timeprecision` in every module, interface, program and package.
  2. Call `$timeformat` once at time 0 in `tb_top`.
  3. Use time literals (`#5ns`) in shared code.
  4. Print with `%t`, never with raw `$time`, in logs.
  5. Check `$printtimescale($root)` when logs look wrong.

**`## Make It Work`**
- **Worked example: one time slot, every region.** A complete unit: a `module tb_top` and a `program tb_prog`, each declaring `timeunit 1ns; timeprecision 1ns;` (§3.14.2.3). It contains:

  2. **Time-0 races.**
     - "There shall be no implied order of execution between initial and always procedures" (§9.2).
     - Declaration initializers run before procedures start (§6.8).
     - `always_comb` runs once at time 0, after all procedures start (§9.2.2.2), "whereas always @* waits until a change occurs" (§9.2.2.2.2).
  3. **The LRM's own race (§4.8).** `assign p = q; initial begin q = 1; #1 q = 0; $display(p); end` may print 1 or 0, because evaluation and update events interleave. There is no clock: the race is between the `initial` and the continuous-assignment process (§4.7 interleaving).
  4. **Derived and NBA-generated clocks.**
     - A clock produced by an NBA (for example a divide-by-2 flop) changes while the same-slot NBA batch is applied. §4.5 moves the NBA events into Active, where "E = any event from region" lets a woken capture flop run before or after the data flop's update.

     - A clock generated with `<=` in the TB orders against NBA data drives only by execution order: a race.
     - §24.4: "clocks driven by nonblocking assignments" are why programs run in Reactive.
  5. **Write-write races and single-writer checks.**
     - Two processes doing `x <= …` on one edge: the last NBA executed wins (§4.6), and process order is free (§4.7).
     - With `always_ff` it is illegal: "shall not be assigned by any other process" (§9.2.2.4 referring to §9.2.2.2).
  6. **Event races.** `->e` before `@e` leaves the waiter blocked (§15.5.2). `wait (e.triggered)` fixes it, because the triggered state "persists throughout the time step" (§15.5.3).

     - `@(posedge clk)` then a `cb.x` read races the clocking block's own update; wait on `@(cb)` (§14.13).

- **New** `### A race you can run` (`// compile`, before the debug challenge):
  ```systemverilog
  // compile
  module tb_top;
    timeunit 1ns; timeprecision 1ns;

    logic       clk = 0;
    logic [7:0] din = 8'd3;
    logic [7:0] q;
    logic [7:0] expected[$];
    int         pass_n = 0, fail_n = 0;

    always #5 clk = ~clk;

    // DUT flop: reads din in Active, writes q in NBA
    always_ff @(posedge clk) q <= din;

    // Driver: records din's pre-edge value, then changes din
    initial begin
      for (int i = 4; i < 8; i++) begin
        @(posedge clk);
        expected.push_back(din);  // only this process writes din, so this is the pre-edge value
        din = i;                  // BUG: blocking write in Active races the flop's read
        // din <= i;              // FIX: write lands in NBA, after every flop has read din
      end
      @(negedge clk);
      #1 $finish;
    end

    // Checker: compares at the falling edge, when nothing else changes
    initial forever begin
      @(negedge clk);
      if (expected.size() > 0) begin
        if (q === expected.pop_front()) pass_n++;
        else                            fail_n++;
      end
    end

    final $display("PASS=%0d FAIL=%0d", pass_n, fail_n);
  endmodule
  ```
  **Expected output:**
  - With the fix: `PASS=4 FAIL=0`.
  - With the bug: `PASS=4 FAIL=0` if the simulator runs the flop first, or `PASS=0 FAIL=4` if it runs the driver first. Any mix is also legal, because the order may differ from edge to edge (§4.7). Which one appears is tool-dependent, and swapping the order of the `always_ff` and the driver `initial` may flip it.
  - State whether the log came from a named simulator run or is illustrative.
- **How-to:**
  1. Run it.
  2. Swap the process order and run again.
  3. Apply the `<=` fix.
  4. Rerun both orders.
  5. (After F4C) replace the drive with a clocking block.

### Objectives

**You will be able to:**
1. Trace one clock edge through the time slot's iterations (delta cycles) and predict every variable's final value.
2. Identify a race (two processes on the same event whose result depends on their order, §4.7–§4.8), and prove it by exploring all legal orders.
3. Debug testbench races (blocking drives at the active edge, `#0` workarounds, reads of signals driven by blocking RTL), and choose a hardware-faithful fix.
4. Write race-free code: flops with `<=`, and testbench drives with `<=` today and through a clocking block from F4C (Re-NBA drives, Preponed samples).
