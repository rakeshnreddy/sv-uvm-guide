**Headline findings.**
1. **Every audit defect in E-RISCV-1 is still present.** One of them meets this program's S1 definition: the `zip()` trace compare hides bugs.
   - My run shows the lesson's compare passing three broken traces:
     - a trace truncated after 3 of 5 instructions;
     - a write to the wrong register with the right value;
     - a store to address 0 with wrong data.
   - The invented `dist:` testlist key is still there, and `run.py` silently ignores unknown keys.
2. **E-RISCV-1 defines step-and-compare wrongly.** It calls step-and-compare a post-simulation trace diff. Industry usage, and the Ibex and CORE-V benches, mean lock-step comparison at each retirement, with interrupts, debug requests and counters forwarded to the ISS. The page never mentions asynchronous events, which are the card's misconception 3.
3. **E-RISCV-1's tool landscape is stale.**
   - riscv-isac is archived, and RISCOF has been replaced by the ACT4 framework, whose coverpoints are SystemVerilog covergroups.
   - The CGF example is structurally invalid.
   - The riscv-formal link points at a repository not updated since 2022.
   - Interrupt injection is credited to riscv-dv, but the testbench does it.
4. **E-AI-1 still presents Cadence Cerebrus as a verification ML tool** (a must-cover failure flagged by the audit). It makes unsourced ROI claims in its opening, while objective 2 asks learners to detect exactly such claims.
5. **E-AI-1's only worked example is an LLM-generated FIFO assertion, shown without critique.** The assertion:
   - checks the count instead of the data;
   - false-fails when a read coincides with a write-when-full;
   - prints a non-sampled value in its action block.

   This is the failure the module should teach learners to catch.
6. **Neither page follows the template.** Neither has an objectives block, a picture a learner can use, a hands-on element, a quiz aimed at the card's misconceptions, or an expert layer. Both need a rewrite.

- **Expert: absent.** Add these `### Expert:` items, each with the source given:
  1. **Lock-step co-simulation in a production UVM bench.** Ibex's `ibex_cosim_scoreboard extends uvm_scoreboard`:
     - it calls `riscv_cosim_set_debug_req`, `_set_nmi`, `_set_nmi_int`, `_set_mip(pre_mip, post_mip)`, `_set_mcycle`, `_set_csr` (mhpmcounters) and then `riscv_cosim_step(...)`, in that order, so that debug, NMI and interrupt priority is right;
     - it handles `irq_only` RVFI items (interrupt notifications that are not tied to a retirement);
     - it reports `uvm_fatal` on mismatch unless `relax_cosim_check` is set.

     Source: `ibex_cosim_scoreboard.sv:116-176` @654ac71; `cosim.rst` ("Interrupts and Debug Requests").
  2. **Nondeterminism policy: forward, override, notify, or exclude.**
     - Forward: `mip`, debug request, NMI.
     - Override: `mcycle` and performance counters. The Ibex docs note that Spike "doesn't produce matching performance counters" and that RVFI was extended with `rvfi_ext` signals such as `mcycle`.
     - Notify: data-side accesses and bus errors.
     - Exclude: speculative instruction-side fetches, which cannot be compared directly.

     Source: `cosim.rst` sections "Trap Handling", "Interrupts and Debug Requests", "Memory Access Checking and Bus Errors".
  3. **Post-run vs lock-step trade-offs.**
     - Post-run needs no DPI integration, but it cannot follow asynchronous events. riscv-dv's interrupt and debug tests fall back to `+compare_final_value_only=1` (`base_testlist.yaml:162-174`) and so lose the location of the bug.
     - Lock-step finds the first divergence immediately, but needs event forwarding.
     - Both still need end-of-test accounting: a hung core simply stops retiring and produces no mismatch. Fix it with a retirement watchdog, the TEST_RESULT handshake and a retired-instruction count (`core_ibex_base_test.sv:323-370`; Ibex prints "Co-simulation matched %d instructions" in `final_phase`, `ibex_cosim_scoreboard.sv:343-350`).
  4. **What a riscv-formal pass guarantees.**
     - The checks are bounded to a configured `[depth]` (procedure.rst).
     - Check list: `insn`, `reg`, `pc_fwd`/`pc_bwd`, `causal`/`causal_mem`/`causal_io`, `liveness`, `unique`, `cover`, bus and CSR checks.
     - `RISCV_FORMAL_ALTOPS` replaces MUL/DIV with alternative operations (rvfi.rst), so the real multiplier datapath is not checked by the `insn` checks.
     - The rollback interface supports speculative cores.
     - Retirement may be reordered if causality holds.
     - The flow is SymbiYosys with immediate assertions "for maximal compatibility" (README). Running it under a commercial tool is tool-dependent.
  5. **Trusting ISA coverage.**
     - Coverage sampled from an ISS trace measures the program, not the RTL.
     - The riscv-isac quickstart warns that Spike traces omit trapping instructions and advises Sail.
     - ACT4 covergroups guard their coverpoints with `iff (ins.trap == 0)` and sample from a SystemVerilog harness.
  6. **Generator realities in riscv-dv.**
     - `get_rand_instr` picks uniformly among allowed mnemonics (`riscv_instr.sv:181-240`). The category mix therefore follows how many mnemonics each category has, unless directed streams are added.
     - `+dist_control_mode`/`+dist_<category>` are parsed (`riscv_instr_gen_config.sv:675-697`), but I found no consumer of `category_dist` in instruction selection at @0d71c2b (`riscv_instr_stream.sv:203-215`). Verify on the pinned commit before teaching them.
     - riscv-dv requires a simulator with "UVM 1.2" support (README). Compatibility with uvm-core 2020.3.1 is tool-dependent.
  7. **The verification-interface landscape.**
     - RVFI is the formal and trace interface.
     - RVVI (TRACE v1.7, API v1.37, VVP) is "a superset of RVFI" for lock-step DV, used by ImperasDV (Synopsys) (RVVI README).
     - ACT4 certification tests are not the same thing as verification: they are self-checking ELFs with Sail-computed signatures, and the user's testbench runs them (arch-test README).
  8. **Interview angles (attempt-first).**
     - "Your trace compare passes but the core hung at instruction 1,203. Why, and how do you prevent it?"
     - "A timer interrupt causes a lock-step mismatch at the first handler instruction. What did the TB forget?"
     - "`csrr x5, mcycle` mismatches every run. Is it an RTL bug?"
     - "What does a riscv-formal pass at depth 20 guarantee?"
     - "Why can ISA coverage from Spike logs over-report?"
     - "How do you bias riscv-dv toward M-extension corner cases without inventing options?"

**## Quick Take**
- **What it is.** Processor DV checks that every *retired* instruction changes architectural state (registers, PC, CSRs, memory) exactly as the ISA specifies, across random programs, privilege modes, traps and interrupts. The tools are:
  - a program generator;
  - an ISS compared at retirement;
  - ISA coverage;
  - formal checks on a retirement interface (RVFI).
- **Why it matters.** The correctness of a custom core is the implementer's job. The classic escapes are in decode, forwarding, traps, interrupts and CSRs. A green compare means nothing if the compare cannot see truncation or interrupts.
- **The Analogy.** Two accountants book the same transactions. The *post-run* compare checks the two ledgers at year end; *lock-step* checks each entry as it is posted. *Where it breaks:* some entries (bank interest, timestamps, i.e. counters and interrupt arrival) cannot be recomputed by the second accountant. They must be copied from the first, or every ledger disagrees.

     - Where biasing, RL or GA help: rare-but-reachable bins.
     - Where they cannot: unreachable bins and a missing coverage model (misconception 2).

     - "Up to" means best case.

**## Quick Take**
- **What it is.** Machine learning (RL, evolutionary search, supervised test selection) and LLMs applied to stimulus, regression ranking, coverage analysis and drafting assertions and sequences.
- **Why it matters.** Random closure has a long tail that costs compute. LLM drafts are fast, but a compiling assertion can be wrong or vacuous. False confidence is the risk.
- **The Analogy.** A fast, confident intern. Useful drafts, every line reviewed, never signs the tape-out form. *Where it breaks:* an intern learns from review and says "I don't know"; an LLM may give a different answer to the same prompt tomorrow and rarely flags uncertainty.

### Hands-on plan

- **Review exercise: five LLM-drafted assertions** (obj 3; the card's hands-on). For each: the spec, the LLM's SVA, a "what is wrong (rule)" field, a fix, and the cover to add. Worked solutions in `<details>`.
  1. **Wrong implication (bare sequence).**
     - Spec: "ack two cycles after req".
     - LLM: `req ##2 ack`.
     - Fix: `req |-> ##2 ack`.
     - The visualizer debug case "bare-sequence" uses this pair.
  2. **Cycle off-by-one.**
     - Spec: "ack on the next cycle".
     - LLM: `req |-> ack`.
     - Fix: `req |=> ack`.
     - Visualizer case "overlap-vs-next".
  3. **Sampling and history.**
     - Spec: "q is d delayed one cycle; q is 0 in reset".
     - LLM: `disable iff (rst) q == $past(d)`.
     - Fix: `disable iff (rst) !$past(rst) |-> q == $past(d)`.
     - Visualizer case "past-reset".
  4. **Vacuity.**
     - Spec: "after reset, every req gets ack next cycle".
     - LLM: `req && !rst_n |=> ack`.
     - Fix: `req && rst_n |=> ack`, plus `cover property (req && rst_n)`.
     - Visualizer case "dead-antecedent".
  5. **Over-specification and wrong target.** The FIFO assertion (AI:126), with the TimingDiagram and the corrected checker from Make It Work.
