### Depth ladder

**index.mdx.**
- **Core: present.** It has the arrow-and-box model, statics, null and lifetime, encapsulation, inheritance, the recap card, and two good predict quiz items. It needs objectives, an analogy limit, and debriefs.
- **Practitioner: partial.**
  - Present: a bug-mode visual, five Make It Work bullets and a checklist.
  - Missing: a complete example with an expected log, a how-to, symptom → cause → fix for null handles, `extern`, `::` and the vif handle.
- **Expert: absent.** Push Further (`:269-273`) is four bullets. One is out of scope (factory overrides, I-UVM-1B) and one is vague ("Profile simulation performance…"). Add these as `### Expert:` subsections:
  1. **Null handles: what the standard guarantees and what tools do.**
     - Access to non-static members or virtual methods through null is illegal; the result is indeterminate and "implementations may issue an error" (§8.4).
     - Static members stay legal through null. §8.9's own example reads `p.fileID` through an unconstructed `p`.
     - *Tool-dependent:* most implementations pass `this` implicitly, so a non-virtual method called through null runs until it touches a property (dave_59, Verification Academy forum). So the error line can be inside the method, not at the call.
     - Contrast: a null virtual interface "shall result in a fatal run-time error" (§25.9).
  2. **Reachability, garbage collection and weak references.**
     - Strongly reachable, weakly reachable and unreachable (§8.29). A pending nonblocking assignment to a non-static member keeps the object alive (§8.29).
     - `weak_reference#(T)`: `new(referent)`, `get()`, `clear()`, `static get_id()` (§8.30, Annex G.7).
     - Garbage-collection timing is implementation-dependent; do not rely on when weak references clear (§8.30, the NOTE under `get()`). Tool support varies.
  3. **Static initialization, singletons and the UVM registry.**
     - Static initializers, including static class members, run before any `initial` or `always` (§6.8). §6.8 states no order among them, so do not depend on one.
     - Initialized static variables in procedural blocks need an explicit `static` (§6.21).
     - A static method is not the same as a `task static` (§8.10). Class methods are always automatic (§8.6).
     - Singleton: a `protected` constructor (§8.7) plus a static `get()`. uvm-core does exactly this: `uvm_root` declares `extern protected function new ();` and `extern static function uvm_root get();` (`uvm_root.svh`).
     - `uvm_component_registry::get()` builds its instance lazily in a function-local `static this_type m_inst`, and `create` is a `static function` (`uvm_registry.svh`).
  4. **Override control in IEEE 1800-2023.**
     - `:initial`, `:extends` and `:final` on methods (§8.20; Annex A `dynamic_override_specifiers`). `:final` is illegal on a pure virtual method or a pure constraint (Syntax 8-1 footnote 8), and the specifiers are legal only on methods of non-interface classes (footnote 25).
     - `class :final` (§8.13).
     - Specifiers go on the `extern` prototype, not on the out-of-block body (§8.24).
     - `:extends` catches a misspelled override that would otherwise silently become a new method.
     - Tool support varies.
  5. **Interface classes, abstract classes or parameterized classes?**
     - Rules: `implements` several interface classes (§8.26); casting between them (§8.26.5); name conflicts and diamonds (§8.26.6, §8.26.6.3); partial implementation in a `virtual` class (§8.26.7).
     - Trade-off: a role shared across unrelated hierarchies, vs shared state and code, vs type-generic containers (link parameterized-classes).
  6. **Object churn, memory and ownership at scale.**
     - New object per transaction vs reuse plus copy.
     - Unbounded queues, associative arrays and mailboxes of handles keep every object reachable (§8.29). That is the usual cause of memory that grows with simulation time.
     - Measure with the simulator's profiler (tool-dependent, no figures).
  7. **Interview angles** (attempt-first):
     - "What happens when you call a method through a null handle?"
     - "Why can a static method not be virtual?"
     - "Two classes reference each other: how does it compile?"
     - "How does `type_id::create` work with no object?"
     - "What keeps an object alive?"
     - "Class vs module vs struct?"

**constructors.mdx.**
- **Core: present.** The three-step order list, `this`, `super`, and the pitfalls are correct. It needs a picture of the order.
- **Practitioner: partial.** It has two complete programs, but no expected output, no how-to, no checklist, no `const`, and no testbench conventions.
- **Expert: one item only** (the virtual call in a constructor, `:110`). Add these as `### Expert:` subsections:
  1. **Initialization-order corner cases.**
     - The §8.7 C/D example: after `D d = new;`, c1=1, c2=2, d1=4, d2=2 and d3=6, and c3 is **undefined**, because `super.new(d3)` is evaluated before d3 is initialized.
     - "The value of a property prior to its initialization shall be undefined" (§8.7). Simulators usually show the type default; label that tool-dependent.
     - Virtual calls from a base constructor run the override (§8.17 NOTE 2, §8.20). C++ behaves differently; SystemVerilog does not follow it.
  2. **Constructor qualifiers.**
     - `local` or `protected`, never `static` or `virtual` (§8.7).
     - A `local` constructor makes the class inextensible (§8.17 NOTE 1).
     - Singleton pattern; `uvm_root` is the real-world example.
     - `new` is a nonblocking function (§8.7, §13.4), so it cannot wait for time.
  3. **2023 `default` constructor arguments.**
     - `class A extends Base(default);`, `function new(int size, default);`, `super.new(default)` (§8.17).
     - Rules: subclasses only; at most once; no name clashes with the base arguments; an argument written after `default` defaults to input `logic`.
     - Tool support varies.
  4. **`extends Base(args)` vs `super.new(args)`.** With arguments in the `extends` clause, "the subclass constructor shall not contain a `super.new()` call" (§8.17). Use the clause for constant arguments and `super.new` for computed ones.
  5. **Typed constructor calls.** `C c = D::new;` constructs a D (§8.8). A parameterized form exists: `E #(.T(byte))::new(.x_init(5))` (§8.8). A typed constructor call cannot be used for a shallow copy (§8.12).
  6. **UVM constructor conventions.**
     - `uvm_object_utils` generates a `create()` that calls `new()` or `new(name)` (`uvm_object_defines.svh`). `type_id::create` for components calls `new(name, parent)` (`uvm_registry.svh`).
     - So a UVM class's constructor must keep exactly those signatures; an extra required argument fails to compile.
     - Child components are built in `build_phase`, not `new` (methodology; owned by I-UVM-1C, forward link only).
  7. **Interview angles:**
     - "What runs first when you construct a derived object?"
     - "Why does omitting `super.new` sometimes compile?"
     - "Can a constructor be virtual?"
     - "What does a virtual call in a base constructor do in SystemVerilog vs C++?"

**copying-and-cloning.mdx.**
- **Core: present and strong.** It covers handle copy, the four shallow-copy rules, deep copy, a compilable virtual `clone()`, and the shared-mailbox IQP.
- **Practitioner: partial.**
  - There is no Make It Work: no kata, no expected log for the deep copy, no debugging flow.
  - The UVM transfer statement is inaccurate.
- **Expert: absent.** Add these as `### Expert:` subsections:
  1. **What a shallow copy really copies (§8.12).**
     - The new object has the source object's class, even through a base handle (the §8.12 `base3 = new base2` example).
     - The RNG state, `rand_mode`, `constraint_mode` and the randc cyclic state are copied. So the copy and its source give the same next `randomize()` results; this follows from §8.12 with §18.14 object stability.
     - An embedded covergroup's handle is set to **null** in the copy ("the properties of the new object are not covered"). Calling `cg.sample()` on the copy is a null access.
  2. **Deep-copy design.**
     - Arrays or queues of handles need a per-element copy or clone (§7.6 copies the handles).
     - Shared sub-objects get duplicated.
     - An instance constant cannot be assigned in `copy()`, only in `new` (§8.19).
     - Inside the class, `rhs.local_member` is accessible (§8.18), so `copy`/`compare` need no getters.
  3. **Two clone patterns.**
     - Override `clone()` in each class (this page), or write it once and call a virtual `create()` (UVM).
     - A covariant return type is legal (§8.20: "a derived class type of the return type").
     - Run the `$cast` before copying, so the copy fails fast.
     - `:final` (2023, §8.20) on copy wrappers; tool support varies.
  4. **How UVM factors it.** In uvm-core 2020.3.1:
     - `clone()` is virtual and implemented once as `create(get_name())` followed by `copy(this)`.
     - `copy()` is non-virtual. It reports `OBJ/COPY` on a null `rhs` and calls your virtual `do_copy()` through the default `uvm_copier`.
     - `compare()`/`do_compare()` follow the same split. `convert2string()` is virtual.
     - Forward link to I-UVM-1A (spine gap G16).
  5. **Ownership and cost.**
     - The creator publishes and never mutates; a consumer that keeps an object stores a copy.
     - Deep copies of large payloads cost time and memory; measure, don't guess (tool-dependent).
     - Mailboxes and analysis paths pass handles. Link I-SV-5 mailboxes; I-UVM-2B for `write()`.
  6. **Interview angles:**
     - "What exactly does `p2 = new p1` copy?"
     - "Why did my scoreboard's expected queue change?"
     - "How do you clone through a base handle?"
     - "What happens to an embedded covergroup in a shallow copy?"
     - "Why does UVM have both `copy` and `do_copy`?"

```systemverilog
// compile
// A value-only transaction, a reused producer object, and a scoreboard
// that owns copies. No UVM.
class txn;
  static int unsigned created;          // one counter for the class (§8.9)
  local int unsigned id;                // only txn's methods touch it (§8.18)
  bit [7:0] data;

  function new(bit [7:0] data = 0);
    created++;
    id = created;
    this.data = data;                   // this.data is the property (§8.11)
  endfunction

  function int unsigned get_id();
    return id;
  endfunction
endclass

class scoreboard;
  local txn expected[$];                // copies this scoreboard owns
  local int unsigned matches, mismatches;

  // The producer may reuse its object after this call, so keep a copy.
  function void add_expected(txn t);
    txn c;
    c = new t;                          // shallow copy suffices: values only (§8.12)
    expected.push_back(c);
  endfunction

  function void check(bit [7:0] actual);
    txn e;
    if (expected.size() == 0) begin
      mismatches++;
      $error("SCB: unexpected output %02h", actual);
      return;
    end
    e = expected.pop_front();
    if (e.data === actual) matches++;
    else begin
      mismatches++;
      $error("SCB: item %0d expected %02h, got %02h", e.get_id(), e.data, actual);
    end
  endfunction

  function void report();
    $display("SCB_SUMMARY matches=%0d mismatches=%0d pending=%0d",
             matches, mismatches, expected.size());
  endfunction
endclass

module tb_top;
  scoreboard sb;
  txn        t;                         // one producer object, reused
  bit [7:0]  samples[4] = '{8'h11, 8'h22, 8'h33, 8'h44};

  initial begin
    sb = new;
    t  = new;
    foreach (samples[i]) begin
      t.data = samples[i];
      sb.add_expected(t);
    end
    foreach (samples[i]) sb.check(samples[i]);  // the "DUT" echoes its input
    sb.report();
    $display("txn::created=%0d", txn::created);
  end
endmodule
```


**`## Make It Work`**

Complete example:

```systemverilog
// compile
// Construction order across three classes, with an instance constant.
class base_item;
  static int unsigned count;            // objects constructed so far (§8.9)
  const int unsigned id;                // instance constant: set once, in new (§8.19)
  string name;

  function new(string name = "base_item");
    count++;
    id = count;                         // the only legal assignment to id
    this.name = name;
    $display("base_item::new  name=%s id=%0d", this.name, id);
  endfunction
endclass

class bus_item extends base_item;
  bit [31:0] addr = 32'h100;            // set after base_item::new returns (§8.7)

  function new(string name = "bus_item");
    super.new(name);                    // must be first (§8.15, §8.17)
    $display("bus_item::new   addr=%0h", addr);
  endfunction
endclass

class crc_item extends bus_item;
  bit [7:0] crc = 8'h5a;

  function new(string name = "crc_item");
    super.new(name);
    $display("crc_item::new   crc=%0h", crc);
  endfunction
endclass

module tb_top;
  crc_item c;
  initial begin
    c = new("pkt0");
    $display("id=%0d name=%s count=%0d", c.id, c.name, base_item::count);
  end
endmodule
```
