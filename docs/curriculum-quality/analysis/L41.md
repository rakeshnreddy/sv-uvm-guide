**Headline findings.**
1. **E-CUST-1's custom-phase mechanics are now correct.**
   - I checked them against uvm-core: the `exec_task` proxy, `add()` on the uvm schedule, the serial vs parallel splice, `PH_BAD_ADD` from the common domain, and the run-only timeout watchdog. The audit's F-CUST-01..05 are fixed.
   - What remains wrong in the main example: `base_test` calls `soc_env::type_id::create` while `soc_env` is still only a forward typedef. IEEE 1800-2023 §6.18 makes that illegal. The fix is to reorder the classes.
2. **E-CUST-1 leaves out half its card.**
   - It never explains why most teams avoid custom phases, and it even proposes linting for "missing custom phases".
   - It never says what "without forking" means or which UVM extension points make forking unnecessary.
   - It defines no CI gate and no uvm-core version pin, and it has no quiz, no kata and no expert layer.
3. **E-PERF-1 teaches the card's misconception 2 as fact.** "Decouple with FIFOs … to exploit parallelism" (L63) is wrong. An analysis FIFO moves the subscriber's work into another process of the same simulation (`try_put` of a handle), and the scheduler still executes one event at a time (§4.5). The page also never teaches the UVM hotspots its card lists, and it re-teaches scheduling regions, which are out of scope.
4. **`uvm-performance-1` cannot run and measures the wrong thing.**
   - The README is built on the same FIFO misconception and points to files and `make` targets that do not exist.
   - The starter has no import, no test and no objection, so 0 packets run.
   - The solution prints simulated time (`$time`) as `wall_time`, and simulated time cannot change when code gets faster.
5. **The custom-phase lab is now sound.** It contains `exec_task`, it uses the right schedule, and its expected log matches the solution (traced: reset 0, load_fw 50, configure 70, main 80 ns). It needs only minor additions.
6. **New in this analysis.** Three insertion APIs used everywhere (`get_uvm_schedule`, `get_common_domain`, `get_uvm_domain`) are uvm-core implementation, not IEEE 1800.2-2020 (§9.4.2 defines only `new`, `get_domains`, `add_uvm_phases`, `jump`). In addition, §9.3.1.6.4 declares `get_schedule` as returning `string` while describing a node, which looks like an erratum. Neither lesson nor visual labels the APIs.

### Depth ladder

- **Core: partly present.** The base-class rationale and the three-part custom-phase recipe are clear. Missing:
  - the objectives block, prerequisites, and an analogy with its limits;
  - the extension-point map that makes forking unnecessary;
  - "when not to add a custom phase";
  - a debrief of the visual.
- **Practitioner: partly present.** Present: the per-role bases, the config helper, PH_BAD_ADD, phases after `extract`. Missing:
  - item, sequence and test bases;
  - reporting conventions (ID taxonomy, verbosity policy, an optional custom server);
  - a complete worked example with expected output;
  - CI gate rules and uvm-core pinning;
  - a drift-diagnosis how-to (symptom → evidence → fix);
  - the kata.
- **Expert: absent.** "Push Further: Governance at Scale" is management advice. Add, each as `### Expert:`:
  1. **Custom domains for VIP and multi-clock subsystems.** `uvm_domain::new` (§9.4.2.1), `add_uvm_phases` (§9.4.2.3), `set_domain` and `define_domain` (§13.1.4.4.1, §13.1.4.4.3), `sync`/`unsync` (§9.3.1.8.1–9.3.1.8.2). A VIP can carry its own schedule without touching the global one.
  2. **Jumps re-run custom phases.** `jump` (§9.3.1.9.1) and a domain jump (§9.4.2.4) back to `reset` re-execute every phase up to the jump source, including a spliced `load_fw`, so `exec_task` work must be idempotent. Leftover threads are killed when a phase completes (§9.6).
  3. **Parallel branches and sibling waits.** An after/before pair with phases between them, or `with_phase`, creates a branch. Phases that share a successor wait for each other, so time can pass in a phase that nobody objects to (§9.6). "A task phase shall not share a successor with a topdown_phase or bottomup_phase" (§9.6), so a custom task phase added `.with_phase(uvm_extract_phase::get())` on the common domain is illegal. uvm-core's `add()` (L764-1027) does not check for this, so nothing warns you.
  4. **Standard vs implementation API.**
     - `get_common_domain()`, `get_uvm_domain()` and `get_uvm_schedule()` are uvm-core only (no clause in §9.4.2). `set_phase_imp` is marked `@uvm-compat`.
     - The standard-only route is `uvm_domain::get_domains(doms)` (§9.4.2.2), then `doms["uvm"].find(uvm_reset_phase::get())` (§9.3.1.4.4), then `.get_parent()` (§9.3.1.6.2), then `.add(...)`.
     - §9.3.1.6.4 declares `get_schedule` as returning `string` while describing a node. uvm-core returns `uvm_phase`, so prefer `get_parent()` for portability.
  5. **Typed phase proxies, phase callbacks and default sequences.**
     - The standard's recipe for a phase that calls methods of an extended component is a parameterized proxy class (§9.3.1.1.1 c).
     - `phase_started`/`phase_ended` (§13.1.4.3) also fire for custom phases.
     - Default sequences apply to any phase (§15.3.5). In uvm-core the scope is `<sequencer>.<phase>_phase`, e.g. `env.agt.sqr.load_fw_phase` (`uvm_sequencer_base.svh` L164).
  6. **Cost of a methodology layer.** Each task phase forks one `exec_task` per component in its domain (§9.6). Base classes that call `uvm_config_db::get` in run-time loops, or that do heavy work in constructors, cost every block. Link E-PERF-1.
  7. **Pinning and upgrading uvm-core.** Check `uvm_pkg::UVM_VERSION_STRING` (`"Accellera:1800.2:UVM:2020.3.1"`, `src/base/uvm_version.svh` L40-44). Do not rely on `` `UVM_MINOR_REV ``: it reads `3.0` in the 2020.3.1 tag (`uvm_version_defines.svh`). Keep a deprecation policy for the project package, and send fixes upstream instead of patching locally.
  8. **Interview angles** (attempt-first `InterviewQuestionPlayground`):
     - "The team wants a `load_fw` phase: argue for and against, and propose the alternative."
     - "Your custom phase never calls your env: what is missing?"
     - "Where does `.after_phase(reset), .before_phase(configure)` put a phase, and how would you prove it?"
     - "A third-party VIP must not take part in your custom phase: how?"
     - "How do you guarantee every block driver uses the project base?"
     - "How do you make a CI verdict honest?"
