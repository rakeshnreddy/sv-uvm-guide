*polymorphism-pitfalls, each as `### Expert:`:*
1. **Default arguments on virtual overrides.** Move the existing text, then add:
   - §13.5.3: "the compiler shall insert their corresponding values";
   - §8.26.8: interface-class method defaults are constant expressions with the same value in every implementing class;
   - simulator behaviour for differing defaults is tool-dependent (unverified), so keep defaults identical.
2. **Override specifiers, IEEE 1800-2023.**
   - `:initial`: the method shall not be a virtual override; it is an error on an override.
   - `:extends`: the method shall be a virtual override; it implies virtual.
   - `:final`: no further overrides; it does not make the method virtual, and it is illegal on `pure virtual`.
   - `initial` and `extends` are mutually exclusive. Out-of-block definitions do not repeat specifiers (§8.20 Example 3, §8.24). The specifiers are legal only "inside a non-interface class scope" (Annex A, A.10 BNF clarifications, note 25).
   - `class :final` forbids extension (§8.13).
   - Label tool support as "check your simulator".
3. **Exactly when `$cast` succeeds** (§8.16, three cases):
   - assignment-compatible;
   - cast-compatible with a run-time check, including an interface-class source (§8.26.5, sideways casts between interface classes);
   - the literal `null`.
   - It "shall fail" for types that are not cast compatible, "even if the source expression evaluates to null".
   - The function form never issues a compile-time or run-time error. The task form gets no compiler type check (§6.24.2).
   - A null-valued handle *variable* of a superclass type is not spelled out: guard with `if (src != null)` (tool-dependent, unverified).
4. **Virtual introduced mid-hierarchy** (§8.20: a virtual method may override a non-virtual one). Calls through the base handle stay static; calls through the subclass handle and below dispatch. Use the explorer's advanced mode with a prediction.
5. **How UVM uses dispatch and casts** (uvm-core 2020.3.1):
   - `virtual class uvm_object` with `virtual clone`/`do_copy`;
   - the factory proxy's virtual `create_component` and `$cast(create, obj)` → `FCTTYP`;
   - `randomize()` is virtual and honours the object's constraints whatever the handle type (§18.5.2).
6. **Design trade-offs.**
   - Inheritance + `virtual` vs interface classes (§8.26) vs callbacks (A-UVM-5) vs factory overrides (I-UVM-1B).
   - Why VIP authors mark hooks `virtual` and public APIs `:final`.
   - Composition over deep hierarchies.
   - No performance figures (none are sourced); point to E-PERF-1 for measurement.
7. **Interview angles**, attempt-first; see the Assessment plan.

*parameterized-classes, each as `### Expert:`:*
1. **Specialization identity** (§8.25 rules a/b with §6.22.1).
   - `fifo`, `fifo#()`, `fifo#(int, 4)` and `fifo#(int, 2+2)` are one type.
   - `int` matches `bit signed [31:0]` (rule e).
   - `int` does not match `integer` (2-state vs 4-state) or `bit [31:0]` (signedness).
2. **Where the class is declared decides how many generic classes exist** (§8.25).
   - A generic class in a package gives one set of specializations system-wide.
   - In a module, program or interface, *each instance* of that scope creates a unique generic class.
   - Put classes in packages.
3. **`::` and names inside a parameterized class** (§8.25, §8.25.1, §8.5).
   - Inside the class, `C::x` means the current specialization.
   - The bare name `C` *not* followed by `::` "shall denote the default specialization", even inside the class. That is why uvm-core declares `typedef … this_type`.
   - A type parameter cannot be reached through a handle (`v.T` is illegal, §8.5).
   - A value parameter read through a handle is not a constant expression (§8.5, §8.25.1).
4. **Out-of-block (`extern`) methods of parameterized classes** (§8.24, §8.25.1). The return type needs the class scope: `function C::T C::f();`. Inside an out-of-block declaration, `C::` implies no specialization (the §8.25.1 example prints "2 10").
5. **Inheriting from parameterized classes and from a type parameter** (§8.25 D1–D4): `extends C`, `extends C#(integer)`, `extends C#(P)` and `extends P` (a mixin), which "shall resolve to a class type after elaboration". Sharing statics across specializations through a non-parameterized base (§8.25).
6. **Abstract-class corner cases** (§8.21).
   - Any class may be extended into an abstract class that re-declares methods `pure virtual`.
   - An abstract class's constructor runs only through constructor chaining.
   - A virtual method with an empty body is callable and is not pure (§8.21 NOTE: it "Will return 'x" for `integer`).
   - `pure constraint` is an error in a non-abstract class (§18.5.2).
   - The LRM's own §8.20 Example 3 declares `pure virtual function void f3();` inside a plain `class base;`, while §8.21's normative text attaches pure virtual methods to abstract classes. Tool behaviour for a pure virtual method in a non-virtual class varies (unverified), so always declare the class `virtual` (the page's :82 already advises this).
7. **How UVM combines both** (uvm-core 2020.3.1):
   - `virtual class uvm_object_wrapper` (pure virtual `get_type_name`) is the abstract proxy.
   - `uvm_component_registry #(T, Tname)` holds one singleton per specialization (`static this_type m_inst` inside `get()`) and registers it through `uvm_registry_common`'s `local static bit m__initialized=__deferred_init();`.
   - `` `uvm_component_param_utils(T) `` gives `typedef uvm_component_registry #(T) type_id;` with no name string. Name-versus-type lookup belongs to I-UVM-1B.
   - `virtual class uvm_sequence #(REQ, RSP)` is abstract and parameterized.
   - `uvm_sequence_base::body()` is deliberately *not* pure: it warns "Body definition undefined". This is the trade-off between compile-time enforcement and backward-compatible defaults.
   - `uvm_config_db#(T)` looks resources up with `uvm_resource#(T)::get_type()`.
8. **Trade-offs and scale.**
   - Parameterize by type (type safety, no casts, one elaboration per specialization) or store polymorphic base handles (one type, `$cast` at the edges, run-time flexibility).
   - Many specializations increase elaboration work (tool-dependent; no figures).
   - Parameterized interfaces and virtual-interface typedefs for VIP are G25 (A-UVM-7, link only).
9. **Interview angles**, attempt-first; see the Assessment plan.

`## Quick Take`
- **What it is:** a base-class handle can hold any subclass object. A `virtual` method call runs the body of the object's class; a non-virtual call runs the body the handle's class sees; `$cast` turns a handle back into a subclass handle, checked at run time.
- **Why it matters:** UVM passes base handles everywhere (`uvm_sequence_item`, `uvm_object`, `uvm_component`). A missing `virtual`, a redeclared property or an unchecked `$cast` runs the wrong code or reads the wrong field *without any error*.
- **The Analogy:** a universal remote labelled with the base model. Only the buttons on the label work, which is what compiles. A `virtual` button asks the TV actually connected what to do; a plain button always does the label's action. *Where it breaks:* remotes have no fields. Properties never dispatch; they always come from the handle's class.
- **You will be able to:** the four objectives in the Objectives section.

- **Worked example** (sketch; reviewers compile-check). The class names match the explorer:

  ```systemverilog
  // compile
  package txn_pkg;
    class base_txn;
      virtual function string describe(); return "base_txn"; endfunction
      function string kind(); return "base"; endfunction   // non-virtual on purpose
    endclass

    class crc_txn extends base_txn;
      bit [7:0] crc = 8'h5a;
      virtual function string describe(); return "crc_txn"; endfunction
      function string kind(); return "crc"; endfunction    // hides base_txn::kind
    endclass

    class bad_crc_txn extends crc_txn;
      virtual function string describe(); return "bad_crc_txn"; endfunction
      function void corrupt(); crc = ~crc; endfunction     // only bad_crc_txn has it
    endclass
  endpackage

  module tb_top;
    import txn_pkg::*;
    base_txn    h;
    base_txn    q[$];
    crc_txn     c;
    bad_crc_txn bad;

    initial begin
      h = new;             q.push_back(h);
      h = crc_txn::new();  q.push_back(h);  // typed constructor call (§8.8)
      bad = new;           bad.corrupt();
      q.push_back(bad);                     // upcast: always legal (§8.16)

      foreach (q[i]) begin
        if ($cast(c, q[i]))                 // function form: 0 on failure (§6.24.2)
          $display("q[%0d] %s kind=%s crc=%h", i, q[i].describe(), q[i].kind(), c.crc);
        else
          $display("q[%0d] %s kind=%s no crc", i, q[i].describe(), q[i].kind());
      end
    end
  endmodule
  ```

    ```text
    q[0] base_txn kind=base no crc
    q[1] crc_txn kind=base crc=5a
    q[2] bad_crc_txn kind=base crc=a5
    ```

    - Typed constructor calls are legal only on the right of an assignment or declaration (A.2.4 `class_new`), so `q.push_back(crc_txn::new())` would not be. Do not write that.
    - Declare handles at module scope, because an initializer inside `initial` needs `static`/`automatic` (§6.21).

  1. Declare the method `virtual` at the root of the hierarchy (`:initial` there where supported).

  4. Downcast only where you need subclass members, with `if (!$cast(dst, src)) $fatal(1, …)` (or `` `uvm_fatal ``) printing the actual type.
  5. Never redeclare a base property.

`## Make It Work`
- **Worked example** (sketch; reviewers compile-check). It mirrors `uvm_object_wrapper`/`uvm_component_registry` in uvm-core:
  ```systemverilog
  // compile
  package reg_pkg;
    virtual class base_obj;                    // what the registry builds
      pure virtual function string get_type_name();
    endclass

    virtual class object_wrapper;              // abstract proxy (uvm_object_wrapper's role)
      pure virtual function base_obj create_object();
      pure virtual function string   get_type_name();
    endclass

    // T has no default, so there is no default specialization (§8.25).
    class registry #(type T, string TNAME = "<unknown>") extends object_wrapper;
      // The bare name "registry" (not before ::) would mean the default
      // specialization (§8.25), which does not exist here: name this one.
      typedef registry #(T, TNAME) this_type;

      static int created;                      // one counter per specialization

      static function this_type get();
        static this_type m_inst;               // one singleton per specialization
        if (m_inst == null) m_inst = new();
        return m_inst;
      endfunction

      virtual function base_obj create_object();
        T obj = new();
        created++;
        return obj;
      endfunction

      virtual function string get_type_name();
        return TNAME;
      endfunction
    endclass

    class txn extends base_obj;
      typedef registry #(txn, "txn") type_id;          // the UVM idiom, by hand
      virtual function string get_type_name(); return "txn"; endfunction
    endclass

    class err_txn extends txn;
      typedef registry #(err_txn, "err_txn") type_id;
      virtual function string get_type_name(); return "err_txn"; endfunction
    endclass
  endpackage

  module tb_top;
    import reg_pkg::*;
    object_wrapper w[$];
    base_obj       o;

    initial begin
      w.push_back(txn::type_id::get());
      w.push_back(err_txn::type_id::get());
      w.push_back(txn::type_id::get());        // the same txn singleton again
      foreach (w[i]) begin
        o = w[i].create_object();              // virtual: the specialization decides
        $display("%s built a %s", w[i].get_type_name(), o.get_type_name());
      end
      $display("txn=%0d err_txn=%0d same_proxy=%0b",
               txn::type_id::created, err_txn::type_id::created, w[0] == w[2]);
    end
  endmodule
  ```
  - Expected output (illustrative):
    ```text
    txn built a txn
    err_txn built a err_txn
    txn built a txn
    txn=2 err_txn=1 same_proxy=1
    ```
- **How-to (numbered):**
  1. Put generic classes in a package.
  2. Give parameters defaults only when a sensible default specialization exists.
  3. Typedef each specialization you use more than once.
  4. Reach statics with `C#(…)::x` or the typedef.
  5. Make extension points `pure virtual` in a `virtual class`.
- **`### Debugging parameterized and abstract classes`:**

  | Symptom | Cause | Fix |
  |---|---|---|
  | Illegal assignment between two `fifo` handles | Different specializations, e.g. `int` vs `integer` (§8.25, §6.22.1) | One typedef per specialization, in a package |
  | Static counter reads 0 | Another specialization's static (§8.25) | Read the specialization you created; share through a non-parameterized base |
  | `C::x` does not compile | Unadorned name before `::` is legal only inside the class (§8.25.1) | `C#()::x` or a typedef |
  | `D d;` does not compile | A parameter has no default (§8.25) | Supply it |
  | Assignment or `$cast` fails between "the same" class from two module instances | Class declared in a module: each instance creates a new generic class (§8.25) | Move it to a package |
  | "Cannot construct" error | `new` on a `virtual class` (§8.21) | Construct a concrete subclass |
  | "Does not implement" error | Pure virtual method left unimplemented, or the signature differs (§8.21, §8.20) | Implement with the identical signature |
  | UVM: `uvm_config_db#(bit [31:0])::get` fails after `uvm_config_db#(int)::set` | Typed lookup `uvm_resource#(T)::get_type()` (uvm-core); `int` ≠ `bit [31:0]` (§6.22.1) | Use one type on both sides (I-UVM-2C) |
