**Headline findings.**
1. **The counterexample triage rule is wrong (S1).** L157 says that replaying a counterexample (CEX) in UVM, "where the same `assume` properties are checked", tells a design bug from a missing assumption. A formal engine only produces traces that satisfy every assumption it used (§16.14.2: an assumption is "a hypothesis"; §16.2: "formal tools use the information to generate input stimulus"). Those same assumptions therefore cannot fire on the replay. A learner who follows L157 classifies every CEX as a design bug, which is the card's misconception 1. The visualizer models the correct rule: its replay checks the complete interface contract, not just the assumptions formal used (`src/lib/formal-fifo-model.ts:413-414`).

With all three assumptions on, the exhaustive search finds a CEX at edge 7. The "overflow" is impossible (the counter is guarded), the cover was reachable before the "fix", and the fix turns the assertion into a tautology.

- **Expert: absent.** L236-241 are generic bullets with no sources. Add each item as `### Expert: <topic>`:
  1. **What each directive means to each engine.**
     - Simulators check `assume` like an assertion; formal treats it as a hypothesis (§16.14.2).
     - `restrict` is "not verified in simulation and has no action block"; use it for case splits (§16.14.4, the `ctr == '0` ALU example).
     - `dist` in an `assume` biases random simulation; in `assert` or `cover` it is equivalent to `inside` and the weights are ignored (§16.14.2).
     - Cover results count vacuous successes (§16.14.3); nonvacuous evaluation is defined in §16.14.8.
     - Sequence properties are weak in `assert`/`assume` and strong in `cover` (§16.12.2).
  2. **Bounded proofs, induction and convergence** (engine names and result labels are tool-dependent; label them so).
     - A bounded result to depth N means no CEX of length ≤ N from reset; a full proof covers every reachable state.
     - Choose N beyond the depth of your deepest cover.
     - Convergence aids: helper assertions (invariants), cut points and black boxes (these add behaviours, so they can cause spurious CEXs but never hide bugs), smaller parameters, case splits with `restrict`, and assume-guarantee decomposition. Contrast with assumptions, which remove behaviours and can hide bugs.
  3. **Symbolic data with constant free variables.**
     - The `rand const` checker variable and the `data_legal` checker (§17.7) check end-to-end data integrity for every data value at once.
     - The representative-bit example, and the LRM's note that the two forms "are not equivalent in simulation" (§17.7).
     - Simulation randomizes free variables instead (§17.7.2).
     - This is how a scoreboard's job is done in formal.
  4. **Liveness, fairness and bounded-response checks.**
     - `s_eventually` (§16.12.13); fairness assumptions on the environment; lasso-shaped counterexamples (tool-dependent).
     - A bounded-response safety property (`##[1:N]`) as the practical alternative.
     - Why simulation cannot prove liveness.
  5. **Where simulation and formal semantics diverge** (§16.2 says cycle-based evaluation can differ from event-based evaluation). Each of these breaks a CEX replay:
     - X treated as a free 0/1 vs X propagation (tool-dependent);
     - uninitialized state and reset specification (tool-dependent);
     - `#` delays, `initial` blocks and `$random` in the RTL (tool-dependent);
     - action blocks ignored by formal tools (tool-dependent);
     - free checker variables solved per clock in simulation (§17.7.2).
  6. **Assume-guarantee and discharging assumptions.**
     - The same interface property is asserted where the DUT drives and assumed where the environment drives (L144, expanded with code).
     - Prove the assumption as an assertion on the upstream block, or rely on simulation checking it in every regression (§16.14.2).
     - Contradictory assumptions empty the input space and make everything prove.
  7. **Formal apps (awareness; names and features are tool-dependent).** Connectivity checking, coverage unreachability analysis, sequential equivalence, X-propagation, register (CSR) checks, security or data-propagation checks, and auto-generated FSM and deadlock checks: what each proves and what it needs.
  8. **Planning and reporting a hybrid sign-off.**
     - Per-property status (proven, bounded to N, CEX open, CEX waived with the added assumption, undetermined), mapped to verification-plan features.
     - Assumptions listed with their spec source and whether regressions ever violated them.
     - Formal results merged into the coverage database (tool-dependent).
  9. **Interview angles** (attempt-first `InterviewQuestionPlayground`; see Assessment plan). Align with the bank items `sva-formal-overconstraint` and `sva-staff-formal-strategy` (`content/interview-questions/sva-formal.json`), and with G29's list of formal methodology topics (cut points, black-boxing, abstraction, k-induction, proof depth, formal coverage).
