**Headline findings.**
1. **I-SV-8 teaches a mix of UPF 1.0 and UPF 2.x that no single edition accepts, and states no edition.**
   - The split commands `set_isolation_control` and `set_retention_control` do not exist in IEEE 1801-2018 clause 6.
   - `set_domain_supply_net`, `create_pst` and `add_pst_state` are legacy in 1801-2018.
   - The file still declares `upf_version 2.1`.
2. **I-SV-8's power-state section is wrong.**
   - It says the simulator learns legal states from a PST. UPF 1.0 §6.10 gives a PST "no simulation semantics".
   - Its PST code builds the table over supply *sets* and `add_power_state` state names. A PST takes supply nets or ports and their port states.
3. **I-SV-8's "complete" UPF example would leave every domain unpowered under UPF 1.0 semantics.** It creates supply nets but no supply port, so no net has a path to a supply pad (UPF 1.0 §5.1.1). It also has no retention, no level shifter and no power state, and its supply sets are never associated with a domain.
4. **E-PWR-1 states a wrong UVM model (S1).** At L164 it says PH_TIMEOUT "only guards run_phase, so a hang in … main_phase may never be timed out".
   - The run phase starts the global timeout (§9.8.1.5).
   - The run phase cannot end until the run-time schedule ends: run and post_shutdown share extract as their successor (§9.6; uvm-core `wait_for_self_and_siblings_to_drop`).
   - So a hang in main_phase does end in `UVM_FATAL [PH_TIMEOUT]` (9200 s by default in uvm-core 2020.3.1).
5. **Both pages fall short of the template.** Both have an explicit H1, no template H2s, no objectives, no quiz and no expert layer.
   - I-SV-8 has no deck, no picture and no Next link, and calls E-PWR-1 "coming soon".
   - E-PWR-1's deck mostly repeats I-SV-8 content and tests none of the card's misconceptions.
6. **E-PWR-1's UVM mechanics are mostly right and worth keeping.** These claims check against uvm-core 2020.3.1 and 1800.2-2020: the power-aware driver pattern, `stop_sequences()` vs `kill()`, the SQRBADITMDN ordering rule, and "callbacks do not abort sequences". The gaps are elsewhere:
   - no power-cycle virtual sequence in code, and no reset or clock steps in the recipe;
   - no scoreboard flush or accounting;
   - no restore-before-release assertion; the second property has no `assert`;
   - coverage without transitions;
   - no "wake-up before reset" symptom.
7. **The lab cannot show its own bug.** It has no DUT, no UPF and no model, and the bug lasts zero simulation time. Even the "correct" wake-up never resets the domain.

3. **Corruption corner cases.**
   - 2-state signals corrupt to 0 and hide the bug (UPF 1.0 §5.1.1; Table 6-7).

   - A retention-supply loss resets both the register and the shadow (§5.3).

4. **Successive refinement and IP reuse.**

6. **Static vs dynamic power verification.**

**## Quick Take**
- **What it is:** IEEE 1801, the Unified Power Format (UPF): a Tcl side file that says which supply powers each part of the unchanged RTL, how supplies switch, and what protects the logic that stays on.
- **Why it matters:** RTL alone never powers anything down, so isolation, retention and sequencing bugs stay invisible until silicon. With the UPF loaded, the same simulation shows them.
- **The Analogy:** the RTL is a building's floor plan; the UPF is its electrical plan. It has circuit breakers (power switches), fuses at each doorway so a dark room's wiring cannot feed junk into lit rooms (isolation), a UPS for one cabinet (retention) and emergency lighting (always-on logic). *Where it breaks:* a breaker just cuts power, but a simulator *corrupts* the room, so every register becomes X (or 0 for 2-state types). Nothing comes back when power returns until reset or restore.

**## Make It Work**
- **Worked example: a two-domain SoC under power intent.**
  - `soc_top.sv` (`// compile`, with stub modules): a PMU with always-on reset `por_n` and outputs `cpu_pwr_en`, `cpu_iso_en`, `cpu_save`, `cpu_restore`, `cpu_rst_n`; `cpu_core` with `ctx_reg` (8'hA5, retained) and `scratch` (8'h3C, not retained); `top_logic`. Use the visualizer's names.
  - `power_intent.upf` (`tcl` fence). Required content, with notes:

```tcl
# power_intent.upf: IEEE 1801-2018 (UPF 3.1) command forms; apply at the scope of soc_top
upf_version 3.1                                  ;# check the version string your tool accepts
create_power_domain PD_TOP -include_scope        ;# everything not listed elsewhere: always on
create_power_domain PD_CPU -elements {u_cpu}
create_supply_port VDD                           ;# supply pads the testbench drives
create_supply_port VSS
create_supply_net  VDD     -domain PD_TOP        ;# -domain: legacy or deprecated in 1801-2024
create_supply_net  VSS     -domain PD_TOP
create_supply_net  VDD_CPU -domain PD_TOP
connect_supply_net VDD -ports {VDD}
connect_supply_net VSS -ports {VSS}
create_power_switch psw_cpu -domain PD_CPU \
  -input_supply_port {vin VDD} -output_supply_port {vout VDD_CPU} \
  -control_port {ctrl u_pmu/cpu_pwr_en} \
  -on_state {on_s vin {ctrl}} -off_state {off_s {!ctrl}}
create_supply_set SS_AON -function {power VDD}     -function {ground VSS}
create_supply_set SS_CPU -function {power VDD_CPU} -function {ground VSS}
associate_supply_set SS_AON -handle PD_TOP.primary
associate_supply_set SS_CPU -handle PD_CPU.primary
set_isolation iso_cpu -domain PD_CPU -applies_to outputs -clamp_value 0 \
  -isolation_supply_set SS_AON \
  -isolation_signal u_pmu/cpu_iso_en -isolation_sense high -location parent
set_retention ret_cpu -domain PD_CPU -elements {u_cpu/ctx_reg} \
  -retention_supply_set SS_AON \
  -save_signal {u_pmu/cpu_save high} -restore_signal {u_pmu/cpu_restore high}
set_level_shifter ls_cpu -domain PD_CPU -applies_to outputs -rule low_to_high -location parent
add_power_state SS_CPU -supply \
  -state {ON  -supply_expr {power == {FULL_ON 0.8} && ground == {FULL_ON 0.0}} -simstate NORMAL} \
  -state {OFF -supply_expr {power == OFF} -simstate CORRUPT}
add_power_state PD_CPU -domain \
  -state {RUN -logic_expr {SS_CPU == ON}} \
  -state {OFF -logic_expr {SS_CPU == OFF}}
```

- **Debugging table** (symptom → cause → fix):

  | Symptom | Cause |

**## Quick Take**
- **What it is:** running functional tests while the power intent is live, so domains really switch off, corrupt and wake. The UVM environment has to drive those power events and stay correct through them.
- **Why it matters:** a testbench that ignores power events either hangs (drivers waiting on a dead domain), floods the log with false mismatches, or hides real X leaks and lost state.
- **The Analogy:** an airport closing a runway for maintenance. Stop new departures (quiesce), divert or cancel flights already rolling (abort and flush, and count them), and reopen only when lights and radar are back and checked (reset and restore before release). *Where it breaks:* cancelled flights are announced; a powered-down domain gives no notice, so the bench must learn of the event from the PMU or a power monitor.
