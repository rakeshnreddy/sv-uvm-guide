**Expert: missing.** There is no `## Push Further`. Add these items, each verified as noted:

1. **Expert: where interface-assertion messages go, and how to control them.**
   - `` `uvm_error `` calls `` `uvm_report_begin ``, which uses the global `uvm_get_report_object()`. In an interface that function returns `uvm_root` (F.3.2.1; `uvm_globals.svh:72-79`), and the message goes out through the global `uvm_report_error` (F.3.2.3, B.1.1.3; `uvm_message_defines.svh:130-135, 188-191`).
   - Consequences: the message carries no instance path, so add `%m` to the text. `set_report_*` calls on the env or agent do not reach it. Control it on `uvm_root::get()` (§6.3.5.2) or with a catcher by ID and count (§6.6), as proposed A-UVM-9 does for expected errors.
   - A disabled attempt runs no action block (§16.14.1).
   - Compare a per-instance `checks_enable` bit in `disable iff` with `$assertoff/$asserton/$assertkill`, `$assertfailoff` and `$assertcontrol` (§20.11). The bit can be set from the VIP cfg. The system tasks take hierarchical scopes, so they belong in `tb_top`.
   - Tool-dependent: some simulators can fold SVA failures or `$error` into their exit status. Label this unverified and never rely on it for UVM pass/fail.
2. **Expert: parameterized VIPs and the virtual-interface type.**
   - The interface type includes its actual parameter values and any selected modport. Set and get must name the identical specialization, or `get()` returns 0 with no message (§25.9; I-UVM-2C:107-114). Declare `typedef virtual apb_if #(AW, DW) vif_t;` once inside the parameterized cfg or agent.
   - Parameterized classes must use `` `uvm_component_param_utils ``/`` `uvm_object_param_utils ``. These register no type name, so name-based factory lookup is impossible (B.2.1.3; `uvm_registry.svh:57` default name `"<unknown>"`). As a result, `+uvm_set_type_override` by name (G.2.7) cannot target them; use `set_type_override_by_type` (§8.3.1.4.2).
   - Trade-off: carry the parameters through every class, or use a max-width interface with a run-time `data_width` in cfg (one type; the monitor masks unused lanes). A third option is an abstract BFM API in the package, implemented by a class inside the interface and passed as a class handle; this is a methodology pattern, not a standard clause.
3. **Expert: nets or variables in a multi-role interface.**
   - A `logic` variable allows one continuous driver (a port connection counts) and no mix of continuous and procedural or clocking writes (§6.5).
   - On a `wire`, a clocking-block output creates a driver that stays `'z` until the first synchronous drive (§14.16). The same interface can therefore be driven by the VIP in one role and by the DUT in another.
   - Tool-dependent: some tools flag a clocking output on a continuously driven variable even if it is never driven.
   - Observation-only SoC hookup can use `bind` (§23.11) or one-way assigns. An interface that contains hierarchical references cannot be used for a virtual interface (§25.9), so a bound interface takes its signals through ports.
4. **Expert: reset inside the VIP (agent mechanics only; strategy belongs to proposed A-UVM-9).**
   - Read asynchronous reset outside the clocking block (`preset_n` is already in the modports at :137-138).
   - `disable fork` kills every child of the calling process, so isolate the fork.
   - Release the in-flight item with `item_done()`, or the sequence's `finish_item` never returns (`uvm_sequence_base.svh:1107-1108`).
   - The test or virtual sequence flushes the sequencer with `stop_sequences()` (§15.3.2.14) and `kill`/`do_kill` (§14.2.5.11-.12).
   - The monitor discards partial transfers, and the responder drops PREADY/PSLVERR.
5. **Expert: configuration API design.**
   - One cfg object versus scalar knobs (misconception 3): one typed `get`, a randomizable and printable object, and defaults in one place, versus silent failures on a typo or type mismatch.
   - Mode source of truth: copying `cfg.is_active` into uvm-core's `is_active` member (`uvm_agent.svh:52`, not in the standard) versus overriding the virtual `get_is_active()` ("An agent developer may override this behavior", §13.4.2.2). Also document the precedence when a test uses the standard `"is_active"` entry or `+uvm_set_config_string=<path>,is_active,UVM_PASSIVE` (§13.4.2.2 example).
   - Sub-configs for an env of envs (link A-UVM-8).
   - Debug with `+UVM_CONFIG_DB_TRACE` (`uvm_config_db.svh:291`) and `check_config_usage()` (`uvm_component.svh:750`), both labelled uvm-core impl.
6. **Expert: versioning, compatibility and release qualification.**
   - `` `UVM_VERSION ``, `UVM_VERSION_STRING` and the `` `UVM_VERSION_POST_2017 `` ladder (B.7.1-B.7.3) support conditional compilation. uvm-core 2020.3.1 defines `UVM_VERSION 2020` and `UVM_VERSION_POST_2017` … `_2020_2_0` (`uvm_version_defines.svh:40-55`), and `UVM_VERSION_STRING = "Accellera:1800.2:UVM:2020.3.1"` (`uvm_version.svh:40`). `uvm_revision_string()` is uvm-core impl.
   - Give the package a VIP version parameter and print it in `start_of_simulation_phase`.
   - Keep semantic versions, a changelog and a compatibility matrix: simulators, UVM versions, and the APB issue (IHI0024C, or a later issue once it is verified).
   - Qualify each release with a self-test regression:
     - loopback traffic;
     - error injection that proves every assertion fires and is counted;
     - closure of the VIP's own covergroups;
     - a `print_topology` golden (F.7.4.2).
7. **Expert: evaluating third-party VIP (staff checklist).**
   - Protocol issue and feature list.
   - vif type, parameters and modports.
   - Config API (objects, paths, defaults).
   - Item and sequencer types, and base sequences: a foreign item type fails at `finish_item` with `UVM_FATAL SQRSNDREQCAST` (`uvm_sequencer_param_base.svh:322`).
   - Extension points (callbacks: A-UVM-5; factory).
   - Report IDs, and whether its checkers report through UVM.
   - Coverage model and sampling cost.
   - Encrypted source and debug visibility.
   - Licensing in CI: a checkout failure is an infrastructure error, never a pass.
   - UVM and simulator support, and self-test evidence.
8. **Expert: passive VIPs at SoC scale (performance; tool-dependent, measure with E-PERF-1).**
   - Costs grow with: per-transfer object creation, analysis fan-out, coverage sampling, transaction recording and assertion attempts across dozens of interfaces.
   - Gate them from cfg, and do `config_db` lookups once in `build_phase`.
   - Give no numbers unless measured.
9. **Expert: interview angles (attempt-first, `InterviewQuestionPlayground`).**
   - "Make one agent active at block level and passive at SoC level without editing it."
   - "The waveform shows an APB violation flagged by an interface assertion, yet the regression passed. Why?"
   - "A parameterized VIP's driver hits a null vif. What do you check first?"
   - "Design an APB responder whose wait states and errors come from sequences."
   - "What is in your VIP release checklist?"
   - "How do you evaluate a vendor VIP before committing a project to it?"

- **Files.**
