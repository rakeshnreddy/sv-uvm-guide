### Depth ladder

- **Core: present.**
  - Quick Take, the cost visual, the ECO table and the carousel give a junior the idea and the picture.
  - Add one short "Two mistakes everyone makes" paragraph: "every silicon fix needs a full respin" and "verification is overhead you can cut when the schedule slips". These are card misconceptions 1 and 2.
- **Practitioner: thin.** "Deeper Understanding" (`F1A:97-114`) is a list. Add:
  - a worked decision example, four late bugs → four fixes (Make It Work below);
  - a numbered "triage a late bug" procedure;
  - escape analysis;
  - what sign-off weighs;
  - the WRG 2022 data with sources.
- **Expert: absent.** Add these `### Expert:` subsections. The heading text must start with "Expert:" to feed the expert index (`src/lib/heading-slug.ts`, `isExpertHeading`).
  1. **Expert: Designing for fixability.**
     - Spare cells and ECO-friendly logic placed before tape-out.
     - Defeature ("chicken") bits and firmware or microcode patch paths.
     - Trade-offs: area, the cost of verifying the defeatured paths, and the security of patch paths.
     - Label all of this as industry practice; no standard defines it.
  2. **Expert: Reading the industry data.** WRG 2022:
     - about 1:1 mean peak verification-to-design headcount, with 5-to-1 "not unusual" for processors;
     - design engineers spend 49% of their time on verification (Foster, Part 8, 12 Dec 2022);
     - "only about 24 percent" of projects reached first-silicon success;
     - "logic or functional flaws" remain the leading cause of respins;
     - design errors lead functional flaws, with changing, incorrect or incomplete specifications "a common theme" (Part 12, 9 Jan 2023);
     - the study had n = 980 and a ±3.7% margin of error (trend-report page).
     Caveats: self-reported survey data, and mean peak headcount is not effort.
  3. **Expert: Sign-off is a judgement, not a number.**
     - Inputs: the reviewed plan, functional and code coverage with reviewed exclusions, regression pass rate, a falling bug-discovery rate, open-bug review and risk acceptance.
     - Labelled as common practice.
  4. **Expert: Shift-left trade-offs.**
     - Verifying unstable RTL wastes effort.
     - Formal on blocks is cheap early.
     - Emulation has capacity and cost limits; FPGA prototypes have clocking and visibility limits.
     - Virtual prototypes let software start early. All of this is tool- and project-dependent.
  5. **Interview angles.** Attempt first, staff level:
     - "Tape-out in 6 weeks, coverage 92%, three open medium bugs: do you tape out?"
     - "How do you decide whether a late bug is ECO-able?"
     - "Estimate verification effort for a new block."
     - Keep the existing respin and edge-vs-corner questions as junior items.

  1. **Expert: `$onehot` and X.**

     - The LRM gives a "known" one-hot `let` using `$countbits(myvec,'x,'z) == 0` (§20.9). Use `!$isunknown(state)` when X must fail.

     - An implication with no antecedent match succeeds (§16.12.7). Vacuous success counts as neither pass nor failure (§16.14.8).
     - `cover property` reports "number of times succeeded because of vacuity" (§16.14.3).
     - `$assertvacuousoff` and `$assertnonvacuouson` control reporting (§20.11).
     - How tools report vacuous passes is tool-dependent (label it).

     - "For formal analysis, there is no obligation to verify that the assumed properties hold" (§16.14.2).

**## Make It Work**
- `### Worked example: plan the counter, then prove the check can fail`.
- Step 1: a plan table for the bug-hunt counter, five rows: reset, increment, wrap 7 → 0, reset mid-count, X-free output.
- Step 2: a complete bench, labelled **preview**: "read it now; you will write your own in F2E. Syntax arrives in F2A–F2D". It must compile under IEEE 1800-2023. This version was checked by inspection and with a cycle model; the lead's CI should compile it (TRUST-1).

```systemverilog
// compile
`timescale 1ns/1ps

module up_counter #(parameter int WRAP_AT = 7) (  // set WRAP_AT = 6 to inject the bug
  input  logic       clk,
  input  logic       rst,      // synchronous, active-high
  output logic [2:0] count
);
  always_ff @(posedge clk) begin
    if (rst)                   count <= '0;
    else if (count == WRAP_AT) count <= '0;
    else                       count <= count + 3'd1;
  end
endmodule

module tb_top;
  logic       clk = 1'b0;
  logic       rst = 1'b1;
  logic [2:0] count;
  logic [2:0] expected;          // reference model: what the spec says count should be
  int         pass_cnt = 0;
  int         fail_cnt = 0;

  up_counter #(.WRAP_AT(7)) dut (.clk(clk), .rst(rst), .count(count));

  always #5 clk = ~clk;

  initial begin
    @(posedge clk);              // the DUT samples rst = 1 at this edge
    rst <= 1'b0;                 // nonblocking: released after the edge, so no race
    expected = 3'd0;
    repeat (20) begin
      @(negedge clk);            // check mid-cycle, when count is stable
      if (count !== expected) begin  // !== so an X can never pass
        fail_cnt++;
        $error("count=%0d expected=%0d", count, expected);
      end else begin
        pass_cnt++;
      end
      expected = expected + 3'd1;    // a 3-bit add wraps 7 -> 0, as the spec says
    end
    $display("PASS=%0d FAIL=%0d", pass_cnt, fail_cnt);
    $finish;
  end
endmodule
```

- **Expected output** (illustrative; the `$error` prefix is tool-dependent): `PASS=20 FAIL=0`.
- **Mutant** (`WRAP_AT(6)`): 13 `$error` lines, the first at 80 ns, `count=0 expected=7`; then `PASS=7 FAIL=13`. Both results come from the cycle model.
- Numbered how-to:
  1. Write the plan row.
  2. Write the check against a model.
  3. Run it and see PASS.
  4. Inject the bug and see FAIL.
  5. Revert.
  6. Record which plan row caught it.
- "Run it": compile both modules with any IEEE 1800 simulator, with `tb_top` as the top. The open-source option is unverified, so the lead decides whether to name one.
- **Checklist before moving on:**
  - `- [ ]` Every plan row has a check and a coverage item.
  - `- [ ]` I have seen my check fail on a mutant.
  - `- [ ]` I compare with `!==`.
  - `- [ ]` I can name the three ways a check never fails.

**## Make It Work**
- `### Worked example: bring a legacy Verilog file into a SystemVerilog bench`.
- Two `// compile` files, checked by inspection and hand-traced; the lead's CI should compile them.

```systemverilog
// compile
// legacy_cnt.v: legal IEEE 1364-2001 Verilog. 'logic' is an ordinary name there.
`timescale 1ns/1ps
`begin_keywords "1364-2001"
module legacy_cnt (clk, rst, logic);
  input        clk;
  input        rst;
  output [7:0] logic;
  reg    [7:0] logic;

  always @(posedge clk)
    if (rst) logic <= 8'd0;
    else     logic <= logic + 8'd1;
endmodule
`end_keywords
```

```systemverilog
// compile
// tb_top.sv: compiled with the default SystemVerilog keywords.
`timescale 1ns/1ps
module tb_top;
  logic       clk = 1'b0;
  logic       rst = 1'b1;
  logic [7:0] q;

  // .logic(q) would be a syntax error here: logic is a keyword in SystemVerilog.
  // An escaped identifier names the port; the space before '(' ends it.
  legacy_cnt u_cnt (.clk(clk), .rst(rst), .\logic (q));

  always #5 clk = ~clk;

  initial begin
    @(posedge clk);              // reset is sampled at this edge
    rst <= 1'b0;                 // nonblocking: released after the edge, so no race
    repeat (3) @(posedge clk);   // three increments
    @(negedge clk);
    $display("q=%0d", q);
    $finish;
  end
endmodule
```

- **Expected output:** `q=3`.
- Notes:
  - Both files carry `` `timescale ``, because §3.14.2.3 makes it an error for some design elements to have a time unit and others not.
  - Without the `` `begin_keywords `` pair, `legacy_cnt.v` fails under SystemVerilog keywords: the §22.14 example.
- Numbered how-to: identify the clashing identifiers → wrap the legacy file → connect by escaped name or by position → rerun.
- "Run it": compile both files with any IEEE 1800 simulator, with `tb_top` as the top. The open-source option is unverified.
