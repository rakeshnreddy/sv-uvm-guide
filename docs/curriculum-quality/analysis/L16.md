**Expert: absent.** No `### Expert:` subsection on any page. Add, with verified sources:
- **Weak vs strong and what a finite run can report:** sequence properties are weak in `assert`/`assume` and strong in `cover` (§16.12.2); strong operators need the clock to tick enough (§16.12.15); the four outcomes Holds strongly / Holds / Pending / Fails (§16.12.21, F.5.3.2); end-of-simulation reporting of pending strong obligations is tool-dependent (label it).
- **`not` switches strength:** `not a ##1 b` in an assertion fails if the clock stops after `a`; write `not strong(a ##1 b)` (§16.12.3, the standard's own example).
- **Safety vs liveness:** a failure of `s_eventually a` cannot be identified at a finite time (§16.12.15), so simulation can never report it as a failure mid-run; bound it or move it to formal (E-INT-1).
- **Abort properties vs `disable iff`:** `accept_on`/`reject_on` use sampled values and make the property true/false; `sync_*` act only at clock ticks; `disable iff` uses current values and makes the attempt disabled (§16.12.14, §16.12).
- **`expect`** in procedural code: a blocking wait on one property evaluation, first evaluation at the next clocking event, `$error` if no else clause (§16.17).
- **Multiclock legality:** only `##1`/`##0` may join differently clocked sequences; maximal singly clocked subsequences must not admit an empty match (§16.13.1); an assertion needs a unique semantic leading clock (§16.16.1); a named property with two leading clocks gets a separate local-variable copy per leading clock (§16.13.7); end points across clocks use `.triggered`/`.matched` (§16.13.5–§16.13.6).
- **Local variables:** flow rules and "unassigned" after a subsequence (§16.10, F.5.4); local-variable formal arguments (§16.8.2, awareness).
- **Performance (tool-dependent, label it):** every attempt of an unbounded range or `[*0:$]` antecedent stays alive until it resolves, so assertion-heavy benches slow down; bound windows, use `first_match`, avoid unbounded antecedents.
- **Staff-level interview angles (attempt-first IQPs):** in-order data integrity with several transfers in flight; why `s_eventually` never fails in simulation; `not a ##1 b` vs `not strong(a ##1 b)`; why `##2` cannot cross clocks; when `first_match` changes a result.

2. Which lets quiet ticks pass before `done`: `ack[->2] ##1 done` or `ack[=2] ##1 done`? — `[=2]`, because it is `ack[->2] ##1 !ack[*0:$]` (Annex F.3.4.2.3); `[->2]` needs `done` on the next tick.

7. Two requests overlap: is the local variable shared? — No: each attempt gets its own copy, created and removed with the attempt (§16.10).
8. Where may a local variable not appear? — In `disable iff` (§16.12), sampled-value function arguments (§16.9.3), clocking events, or a hierarchical reference (§16.10).
9. In `@(posedge w) a |=> @(posedge r) b`, which `r` edge checks `b`? — The nearest `posedge r` strictly after the `w` tick; with `|->` a coincident `r` tick is used if there is one (§16.13.2).
10. Which operators may join differently clocked sequences? — Only `##1` and `##0` (§16.13.1).
11. An `assert property` attempt of `req |=> ##[1:$] ack` is open at `$finish`: failure? — No; sequences are weak in assert and assume (§16.12.2). Bound the wait to get a failure during the run.
12. `not a ##1 b` vs `not strong(a ##1 b)`? — `not` switches strength; the first fails if the clock stops right after `a`, so write the second for "never a then b" (§16.12.3).

Key: error, there is no inferred clock at the instantiation point (§16.14.7); connect the clock. Distractors: it uses the clock of `tb_top`; it uses the package's clock; it never evaluates but reports nothing.

**Flashcards.** New deck `content/flashcards/I-SV-4C_Checkers.json` (ids `i-sv-4c-1` …):
1. Does `bind` edit or recompile the target's source? — No: it is processed at elaboration and inserts an instance as if written at the end of the target scope (§23.11).
2. `bind fifo fifo_chk u_chk (.*);` — which instances get `u_chk`? — Every instance of `fifo`, designwide (§23.11).
3. How do you limit a bind to two of five instances? — `bind fifo : inst_a, inst_b fifo_chk u_chk (…);` (§23.11).
4. Where are names in a bind's port list resolved? — In the target scope, from the target instance's point of view (§23.11).
5. Two binds put `u_chk` into the same module: result? — Elaboration error; a bound name may not clash with any name in the target, including other binds' names (§23.11).
6. Which procedures may a checker contain? — `initial`, `always_comb`, `always_latch`, `always_ff`, `final`; no plain `always`; a checker `initial` holds only assertions, `let` and an event control (§17.5).
7. Can a checker declare nets or instantiate a module? — No: nets are illegal (§17.7), and modules, interfaces and programs cannot be declared or instantiated in it (§17.2).
8. A package checker bound into RTL: whose default clocking does its body use? — Its declaration scope's (§17.2); use `$inferred_clock`/`$inferred_disable` defaults or pass the clock (§16.14.7, §17.4).
9. How do you give a bound checker the target's `DEPTH`? — As an argument, `.depth(DEPTH)`, resolved in the target; checkers have no parameter ports (§17.2–§17.3).
10. What does a checker `always_ff` read? — Sampled values, except the event-control variables (§17.5); its NBAs update in Re-NBA (§17.7.3).
11. What can be bound into an interface? — Only interface or checker instances (§23.11).
