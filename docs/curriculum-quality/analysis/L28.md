- **Expert: missing.** :189-232 "Push Further: Advanced Patterns" holds two practitioner patterns, with no `### Expert:` items and no interview angles. Add these items, each verified as noted:
  1. **What `` `uvm_register_cb `` really checks.**
     - The macro declares `static local bit m_register_cb_<CB>`. B.4.1 says a parameterized CB type causes errors, so use a typedef.
     - An unregistered pair only warns (`CBUNREG`, `uvm_callback.svh:745`). `add()` still queues the callback (`:752-831`), and iteration never checks registration (`:991-1005`).
     - Promote `CBUNREG` to an error with a severity override (§6.3.7) or `+uvm_set_severity` (G.2.5).
  2. **Derived and factory-substituted components.**
     - `` `uvm_set_super_type `` (B.4.2) lets a derived type inherit the base type's type-wide callbacks. In uvm-core this matters when the hook is invoked with T = the derived type (`m_add_tw_cbs` propagates to `m_derived_types`, `uvm_callback.svh:316-322`).
     - Instance queues are keyed by the object, so instance callbacks follow a factory-substituted driver.
     - A subclass whose `run_phase` drops the `` `uvm_do_callbacks `` line silences every callback.
  3. **Veto hooks and other contexts.**
     - `` `uvm_do_callbacks_exit_on ``/`` `uvm_do_obj_callbacks_exit_on `` (B.4.5/B.4.6) return on the first callback that returns VAL. They are legal only inside functions returning `bit`.
     - `` `uvm_do_obj_callbacks `` (B.4.4) runs another object's callbacks, for example a sequencer's from a sequence.
     - Use a manual `uvm_callback_iter` loop (D.1.2) when results must be combined or walked backwards.
     - B.4.3 calls METHOD "a function signature". uvm-core's expansion (`cb.METHOD;`, `uvm_callback_defines.svh:177-186`) also accepts task hooks when the macro sits in a task.
  4. **Queue internals and modification hazards (uvm-core 2020.3.1 impl., by source inspection).**
     - All instance queues live in one global pool keyed by object (`uvm_callback.svh:112`). They are shared across callback types and filtered by `$cast` at iteration.
     - An instance queue that is empty when `add()` runs is re-seeded from the type-wide queue (`:788-799`), so a type-wide callback deleted from that instance can come back.
     - `delete(obj, cb)` on an object that never had an instance queue calls `m_cb_find(null, …)`, which calls `q.size()` on a null handle (`:901-902`, `:261-262`). That is an illegal null access (IEEE 1800-2023 §8.4), where §10.7.2.3.3 expects a warning. Confirm on a simulator before teaching it.
     - Deleting inside a hook skips the next callback. Prepending inside a hook re-runs the current one (live index, `:1059`).
  5. **`callback_mode()` corner cases.**
     - §10.7.1.2.2 declares `int on = -1`, yet its prose says "The default value of on shall be 1". uvm-core treats −1 as a query (`:1387-1407`), and `is_enabled()` calls `callback_mode()` (`:1414`).
     - Always pass 0 or 1. Query with `is_enabled()` (§10.7.1.2.3). The mode is per object, so it affects every queue that holds the callback, and the call returns the previous mode.
  6. **Item-accurate run-time toggling.**
     - With `get_next_item … item_done` after driving, the boundary between items is exact.
     - With `get()` or a pipelined driver, `finish_item` returns before the hook runs, so the boundary item races the toggle.
     - Time-consuming task hooks widen the window. An `add()` at time 0 of `run_phase` races the first item.
     - Patterns that avoid this: count inside the callback, toggle from the sequence at item boundaries, or attach before `run_phase`.
  7. **`ref` hooks and transaction identity.**
     - `ref` actuals need equivalent types, with no casting (§13.5.2), so a derived-class variable cannot be passed to `ref base_item`.
     - Swapping `req` through `ref` hides the new object from the sequence, and it breaks `set_id_info` (§14.1.2.4) and response routing unless the ids are copied.
     - Mutate in place, or clone for observers.
  8. **Cost at scale.**
     - Each invocation allocates a `uvm_callback_iter`, does pool `exists`/`get` lookups and a `$cast` plus `callback_mode()` per entry, even when no callback is registered (`uvm_callback_defines.svh:177-186`, `uvm_callback.svh:964-1005`).
     - Put hooks per transaction, not per bit. Profile with your simulator (tool-dependent; link E-PERF-1).
     - `UVM_CB_TRACE_ON` adds a message per add, delete and execution, so compile it only for debug.
  9. **Designing a VIP extension API.**
     - Choose between callbacks, virtual-method hooks, configuration knobs, sequence-level error injection and factory overrides.
     - uvm-core recommends virtual-method hooks whose default implementation runs the callbacks, so users can choose inheritance or callbacks (`uvm_callback.svh:538-548`).
     - Document the hook order and argument directions.
     - UVM itself is built on callbacks: report catchers (§6.6.1, typedefs D.4.3/D.4.4), register callbacks (`uvm_reg_cbs` §18.11, D.4.5), objection and phase callbacks (D.4.1/D.4.2).
  10. **Interview angles** (attempt-first): see the Target outline.

**`## Quick Take`**
- **What it is:** A callback is an object, a subclass of `uvm_callback` (IEEE 1800.2-2020 §10.7.1), whose hook methods a component calls at fixed points with `` `uvm_do_callbacks `` (B.4.3). A test attaches it to one instance, or to every instance of a type, with `uvm_callbacks#(T,CB)::add` (§10.7.2.3.1).
- **Why it matters:** per-instance, stackable, switchable extensions without editing or subclassing the component. This is a common way for VIP to expose extension points, and a standard mechanism for M8 error injection.
- **The Analogy:** sockets on a production line.
  - The line's owner (the component developer) decides where the sockets are (hook points).
  - You plug tools (callback objects) into the sockets of one line or of every line, in front of or behind the tools already there.
  - You can switch a tool off without unplugging it.
  - *Where it breaks:* a tool plugged in "before the line exists" does not fail; it silently goes onto every line of that type (`add(null, cb)`). Tools can also change the product itself (the transaction object), so their order changes the outcome.

| a-uvm-5-8 | value / `ref` / `const ref` | By value: a copy of the handle, and field writes still reach the object. `ref`: the hook can replace the driver's handle. `const ref`: no handle change, but fields can still be written. |
| a-uvm-5-9 | `display()` vs `get_all()` | `display()` is uvm-core impl. and prints the name, `(*)` or the path, and ON/OFF. `get_all()` (§10.7.2.5) fills a queue for self-checks. |
| a-uvm-5-10 | `add_by_name` | Components must already exist, otherwise `CBNOMTC` and nothing is registered. |
| a-uvm-5-11 | Callbacks vs factory (merges cards 3 and 4) | Callbacks: per-instance, stackable, switchable, only where hooks exist. Factory: replace a class or add fields. They compose. |
| a-uvm-5-12 | `` `uvm_do_callbacks_exit_on `` | It returns on the first callback that returns VAL (veto or drop). Use it only inside a function returning `bit`. |

Card 7 is dropped or rewritten as a use-case card that says "corrupt stimulus before the DUT; the checker must expect it" (L28-AUVM5-21).

## Cross-cutting observations

1. **Spine card wording (A-UVM-5 "Debug a callback that never fires").** "missing `` `uvm_register_cb ``" is not a never-fires cause in uvm-core 2020.3.1:
   - `add()` warns `CBUNREG` and still queues the callback (`uvm_callback.svh:717-831`), and B.4.1 requires only a warning.
   - Suggested card text: "missing `` `uvm_register_cb `` (`CBUNREG` warning; the callback still runs)".
   - Add two never-fires causes: "hook never reached (a subclass omits `` `uvm_do_callbacks ``)" and "`add_by_name` before build (`CBNOMTC`)".
   - Misconception 1's parenthetical, "(the handle is null, so it becomes type-wide)", is right for a direct child such as the lab's `env.drv`, or for `agt0.drv` read in `my_env.build_phase`. It is wrong for the card's own example `env.agent.drv` in the **test's** `build_phase`. There `env.agent` is itself null, so the read is an illegal null access (IEEE 1800-2023 §8.4; simulators typically stop), not a type-wide add. The lesson (:165-166) and the visualizer (`test-build` preset) already teach this distinction. Suggested card text: "`add(env.drv, cb)` in the test's `build_phase`, or `add(agt0.drv, cb)` in the env's `build_phase`, attaches to that driver (the handle is still null, so it becomes type-wide; one level deeper, the access itself fails)".
