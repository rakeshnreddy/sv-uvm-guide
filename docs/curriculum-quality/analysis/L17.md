*Index (process control):*
- X1. `kill()` ends the process and all its descendants, and finishes before it returns. Calling `kill()` on a FINISHED or KILLED process still kills its live descendants (§9.7).
- X2. Other §9.7 rules:
  - Calling `await()` on the current process is an error.
  - `suspend()` on a WAITING process desensitizes it to the event, wait or delay it is blocked on. A suspended waiter therefore misses triggers.
  - A function may kill, suspend or resume another process (§13.4, rule c), but may not suspend itself.
  - `status()` also reports KILLED after `disable` (§9.6.2).
- X3. **A deadlocked bench often ends quietly instead of hanging.** "Simulation automatically terminates when there is no further activity of any kind", and when all program blocks finish regardless of their child processes (§9.6.1, §24.7). A free-running clock or a watchdog turns the same bug into a hang. Practice: always print a summary line, and give the watchdog `$fatal`.
- X4. **Choosing a stop mechanism for reusable code:**
  - `disable fork` follows the caller's dynamic process tree (§9.6.3);
  - `disable <block>` uses the static name and ends every activation (§9.6.2);
  - `p.kill()` ends exactly one handle's subtree (§9.7).
- X5. **Per-process random stability.** `process::self().srandom(seed)`, `get_randstate()`/`set_randstate()` (§9.7 prototype), and thread-stable `$urandom` (§18.14.2, whose example uses `process pvar; pvar = process::self; pvar.srandom(100);`).

*Events:*
- X6. **Delayed and event-controlled `->>`.** The syntax is `->> [delay_or_event_control] ev;`, for example `->> #5 ev;` or `->> @(posedge clk) ev;`. It creates the NBA-region update when the delay expires or the event occurs (§15.5.1).
- X7. **`->>` from `program` code is unspecified.** §15.5.1 names only "the nonblocking assignment region". §4.4.2.8 sends nonblocking assignments made from the reactive region set to Re-NBA, but the standard does not say whether `->>` follows that rule. Label it tool-dependent (unverified).
- X8. **Events are handles (§6.17):**
  - `event b = a;` aliases one synchronization object.
  - Assigning one event variable to another *after* a process is already blocked leaves that process waiting on the old object forever (§15.5.5.1, LRM example with T1/T2/T3).
  - With a `null` event, `->` has no effect and waiting is undefined (§15.5.5.2).
  - Only `==`, `!=`, `===`, `!==` and a Boolean test are allowed on events (§15.5.5.3).
  - Events can be passed to tasks (§15.5.3 example).
- X9. **Wait re-evaluation.** A wait on `ev.triggered` is re-evaluated only when an operand changes. The 1→0 change at the end of the time step does not affect waiters (§15.5.3). `wait(ev)` without `.triggered` tests the handle, which is true for any non-null event (§15.5.5.3), so it returns at once.
- X10. **`wait_order` corner cases (§15.5.4):**
  - Only the first listed event can be satisfied by the persistent triggered state.
  - An event already seen in order may repeat without failing.
  - Without an `else` clause, a failure calls `$error`.
  - There is no timeout. Wrap it in `fork … join_any` with a timer when the events may never arrive.
- X11. **Tool-dependent behaviour:**
  - The order of processes that wake at the same time is unspecified (§4.7). A same-slot `->`/`@` race can pass on one simulator and hang on another.
  - Whether a simulator stops a zero-delay loop with an iteration-limit error or simply spins is tool-specific. Label it; do not name tools unless verified.
- X12. **`uvm_event` as a pointer only; I-UVM-1C owns it.** All of the following are verified in uvm-core `uvm_event.svh`:
  - `trigger()` sets a persistent `on` bit that stays until `reset()` (`:366-392`).
  - `wait_on()` returns at once if `on` is set (§10.1.1.2.2).
  - `wait_ptrigger()` is the `.triggered` form (§10.1.1.2.5).
  - `wait_trigger()` has the same same-delta race as `@` (§10.1.1.2.4; source comment at `:128-132`).
  - There is no trigger counter.

*Mailboxes:*
- X13. **Typeless vs parameterized (§15.4.9).** The default `mailbox` is `mailbox #(dynamic_type)`, so type mismatches surface only at run time:
  - `get`/`peek` with a mismatched type raise a run-time error (§15.4.5, §15.4.7);
  - `try_get`/`try_peek` return a negative value (§15.4.6, §15.4.8);
  - `mailbox #(T)` catches the mismatch at compile time.
- X14. **Waking order:**
  - One `put()` can unblock several processes waiting in `peek()` (§15.4.7).
  - The `get` waiting queue is FIFO (§15.4.5).
  - The standard does not state an order for blocked `put()` callers. That is tool-dependent, and the visual's FIFO is a modelling assumption (`sv-process-model.ts:40-42`).
- X15. **`num()` and bounds.** `num()` is valid only until the next `put` or `get` by any process (§15.4.2), so never gate a `put` or `get` on it. A negative bound is illegal (§15.4.1).
- X16. **Mailbox is a built-in class in the `std` package (§15.2).** It can be extended, for example as a counting mailbox for statistics, and stays reachable as `std::mailbox` when user code reuses the name.
- X17. **Bounded or unbounded depends on direction.**
  - Generator→driver wants back-pressure: bounded.
  - Monitor→scoreboard must never block the monitor, or the monitor misses bus activity: unbounded, or `try_put` with an error.
  - UVM mirrors this. `uvm_tlm_fifo` defaults to size 1 and wraps `local mailbox #(T) m` (uvm-core `uvm_tlm_fifos.svh:65,81`). `uvm_tlm_analysis_fifo` is unbounded (`:248-249`).
- X18. **Scale.**
  - A queued handle keeps its object alive (§8.29), so unbounded mailboxes of large transactions grow memory.
  - Polling with `try_get` plus `#1` adds scheduler activity that a blocking `get()` does not. This is general practice; no LRM source.

*Semaphores:*
- X19. **Key counts (§15.3.1–§15.3.4):**
  - `new()` creates **0 keys**, so the first `get()` blocks forever.
  - The initial count may be negative.
  - `put()` may push the count above the initial value.
  - Negative arguments are errors, and `try_get(-n)` returns 0.
- X20. **There is no method to read the key count.** The Annex G.3 prototype has only `new`, `put`, `get` and `try_get`. The end-of-test leak check is therefore `if (!s.try_get(N)) $error(...); else s.put(N);`.
- X21. **Multi-key ordering.** The waiting queue is FIFO and arrival order is preserved (§15.3.3). The standard does not say whether a later, smaller request may be served while the head waiter needs more keys. That is tool-dependent. The course visual serves any waiter whose request fits, and this is a labelled assumption (`sv-process-model.ts:43-45`, `:650-668`).
- X22. **Deadlock theory** (general concurrency knowledge; label it as such). The four conditions are mutual exclusion, hold-and-wait, no preemption and circular wait.
  - Break circular wait with one global acquisition order.
  - Break hold-and-wait with `get(n)` on one counting semaphore when the resources are interchangeable.
  - "`try_get`, release, back off" can livelock if both sides back off symmetrically.
- X23. **Keys and kill/reset.** `disable`, `disable fork` and `kill()` never return held keys. SystemVerilog has no cleanup construct: Annex B Table B.1 has no `try`, `catch`, `finally` or `throw`. Reset handlers must restore the count. Link the proposed A-UVM-9.
- X24. **UVM alternative.** Sequencer `lock()`/`grab()` gives a sequence exclusive access (IEEE 1800.2-2020 §14.2.5.5, §14.2.5.6). Link I-UVM-3B/`sequence-arbitration`.

*Index (process control)*

- **P1 (predict, objective 4).** A worker publishes `p = process::self()` and then runs `#20`. The parent runs `wait (p != null); #5;` and prints `p.status()`.
  - Key: WAITING.
  - Distractors:
    - RUNNING ("alive means running");
    - FINISHED;
    - SUSPENDED (confuses blocking with suspension).
- **P2 (predict, objective 4).** The worker forked two grandchildren with `join_none`. The parent calls `p.kill()`.
  - Key: the worker and both grandchildren die (§9.7).
  - Distractors:
    - only the worker (transfers `wait fork`'s immediate-children rule);
    - the worker and immediate children only;
    - nothing, because `join_none` children are detached.
- **P3 (debug, objective 4).** `fork begin p = process::self(); … end join_none; p.kill();` fails with a null-handle error.
  - Key: the child has not run yet (§9.3.2); add `wait (p != null)`.
  - Distractors:
    - `process` objects must be created with `new` (illegal, §9.7);
    - call `await()` first;
    - use `disable fork` instead (it would kill other children too).
- **P4 (debug, objectives 3 and 4).** A killed driver held the bus key.
  - Key: the key is lost; the next `get()` blocks forever.
  - Distractors:
    - `kill()` returns held keys;
    - the semaphore detects dead holders;
    - the next `get()` raises an error.

*Events*

- **E1 (predict, objective 1; misconception 2).** `-> done` and `@done` in two processes that both wake at t = 10.
  - Key: it depends on which runs first (§4.7, §15.5.2).
  - Distractors:
    - always wakes (`@` catches an earlier same-slot trigger);
    - never wakes;
    - compile error.
- **E2 (predict, objective 1; misconception 1).** At t = 10, P runs `->> done`. B runs `@done` at t = 10 in the Active region. C runs `@done` at t = 12.
  - Key: B wakes, C does not.
  - Distractors:
    - both wake because `->>` keeps the event triggered;
    - neither, because `->>` fires at the next time step;
    - only C.
- **E3 (debug, objective 5).** `forever begin wait(done.triggered); n++; end` hangs at one time.
  - Key: `.triggered` stays 1 for the whole time step, so the loop never advances time; use `@done`.
  - Distractors:
    - `wait` misses triggers;
    - `n` overflows;
    - `.triggered` is illegal in `wait`.
- **E4 (predict, objective 1).** Which wait succeeds whether the trigger came before or after it in the same slot?
  - Key: `wait(ev.triggered)`.
  - Distractors:
    - `wait(ev)` (legal, but returns at once for any non-null event);
    - `@ev`;
    - `@(ev.triggered)`.
- **E5 (predict, must-cover).** `wait_order(a, b, c);` sees a, then c.
  - Key: fails at c with a run-time error (default `$error`, §15.5.4).
  - Distractors:
    - keeps waiting for b and c;
    - passes once b arrives later;
    - returns silently.

*Mailboxes*

- **M1 (predict, objective 2; misconception 3).** `mailbox #(int) m = new(2);` The producer puts 0, 1, 2 at t = 0. The consumer's first `get` is at t = 10.
  - Key: `put(2)` blocks until t = 10.
  - Distractors:
    - `put(2)` overwrites 0;
    - `put(2)` is dropped and returns 0;
    - the mailbox grows to 3.
- **M2 (predict, objective 2).** `ok = m.try_put(x)` on a full mailbox.
  - Key: returns 0 and stores nothing (§15.4.4).
  - Distractors:
    - blocks;
    - returns 1 and overwrites the oldest;
    - returns −1.
- **M3 (debug, objective 2).** `tr = new; repeat (3) begin void'(tr.randomize()); mbx.put(tr); end`. The driver sees three identical items.
  - Key: one object, three handles; `new` per item or put a copy.
  - Distractors:
    - the mailbox copies objects (misconception);
    - `randomize()` failed silently;
    - the mailbox is LIFO.
- **M4 (choose, objective 2).** What depth for monitor→scoreboard?
  - Key: unbounded, or `try_put` plus an error, because a blocked monitor misses transactions.
  - Distractors:
    - `new(1)` for back-pressure (overgeneralized rule);
    - a semaphore;
    - an event.
- **M5 (predict, objective 2).** A typeless mailbox: `put(5)`, then `get(s)` into a `string`.
  - Key: run-time error (§15.4.5); with `mailbox #(int)` the compiler rejects it.
  - Distractors:
    - `s = "5"`;
    - blocks forever;
    - returns 0.

*Semaphores*

- **S1 (predict, objective 3).** `semaphore s = new(); s.get();`
  - Key: blocks forever (0 keys, §15.3.1).
  - Distractors:
    - takes the default single key;
    - compile error;
    - returns at once.
- **S2 (predict, objective 3).** One key is held by A. B waits from t = 2, C from t = 4. A puts at t = 10.
  - Key: B (FIFO, §15.3.3).
  - Distractors:
    - C (LIFO);
    - both;
    - unspecified.
- **S3 (debug, objective 3; misconception 4).** An early `return` skips `put`.
  - Key: the next `get` blocks; the bench ends quietly or the watchdog fires.
  - Distractors:
    - harmless because the task ended;
    - SystemVerilog returns keys at task exit;
    - the blocked `get` reports an error.
- **S4 (diagnose, objective 5).** A runs `get(s1)` then `get(s2)`; B runs `get(s2)` then `get(s1)`. Both are stuck, and no error is printed.
  - Key: a circular wait; make both acquire s1 then s2.
  - Distractors:
    - `s2 = new(2)` (it masks the bug and breaks exclusion);
    - `disable fork` on B;
    - B uses `try_get(s1)` in a retry loop without releasing s2 (A stays blocked, B spins).
- **S5 (predict, objective 3).** `s = new(3)`; A takes `get(2)`, then B calls `get(2)`; later `put(4)`.
  - Key: B waits until at least 1 key returns, and `put(4)` is legal and the count grows (§15.3.1).
  - Distractors:
    - `put` beyond the initial count is an error;
    - the count caps at 3;
    - B takes the last key and waits for one more.

**What it teaches today.** One semaphore key leak. The producer returns early on `data == 5` without `put(1)`, so the consumer blocks in `get(1)` and the 500 ns watchdog ends the run.

This matches the lesson's key-leak material (`semaphores.mdx:52-57`) and the `MailboxSemaphoreGame` debug mode. By inspection the SystemVerilog is legal:
- `for (int i …)` variables are automatic (§6.21);
- `return` sits in a task, not in a `fork` (§9.3.2);
- static tasks with one caller each are legal.
