**Expert: absent.** `index.mdx:195-198` has three bullets. Add these `### Expert:` sections, each with its source:
1. **`dist` corner cases** (§18.5.3, 1800-2023 text):
   - A value listed in several items adds the weights.
   - A zero weight excludes a value only when no other item gives it a nonzero weight.
   - A range weight applies to the range as a whole, even when other constraints exclude some of its values. The LRM's own example: `x > 101; x dist {[100:102]:=1, 103:=1}` gives 102 : 103 = 3 : 1. Label tool support as unverified and check it on your simulator.
   - Items with no weight default to `:= 1`.
   - Weights are unsigned integral expressions.
   - `default :/ w` covers every value not listed elsewhere. It must use `:/`, at most once. Check tool support.
   - `dist` is illegal on `randc` and needs at least one `rand` variable.
   - Real ranges must use `:/`.
   - When a `dist` variable is coupled to other variables, "implementations are only required to satisfy the constraints", so the distributions are tool-dependent.
2. **Soft priorities across layers:**
   - The ranking (§18.5.13.1): later in the same construct; extern prototype order; derived class over superclass; inline over class; contained objects lower, ordered by handle declaration; `foreach` by iteration order.
   - The solver's conceptual model, and "if a call to randomize() only involves soft constraints, the call can never fail".
   - `soft` is illegal on `randc`.
   - `disable soft x` (§18.5.13.2), and the trap in its B1/B3 example: an earlier `soft x == 5` makes a later `soft x dist {5, 8}` always yield 5.
3. **`randc` internals** (§18.4.2):
   - The permutation is recomputed when the constraints on the variable change, or when no remaining value fits.
   - `randc` is solved first, which "can sometimes cause randomize() to fail".
   - Implementations may limit the width, but not below 8 bits.
   - A `static` variable shares one cycle across all instances. §18.6.3: a static rand variable "is changed in every class instance", including items a scoreboard has stored.
   - UVM consequence: a new item per transaction never cycles.
4. **When `randomize()` fails although a legal combination exists:** `randc` first (§18.4.2); sizes before `foreach` (§18.5.7.1: "can cause the solver to fail"); function-argument ordering (§18.5.11). Link I-SV-2B solver-debug.
5. **Inline name resolution in depth** (§18.7, §18.7.1):
   - An unrestricted block resolves names in the object's class first, then in the calling scope.
   - `this.` and `super.` bind to the object's class.
   - Dotted names resolve downward first.
   - A restricted block `with (id_list)` binds only the listed names into the object.
   - `local::` forces the calling scope, including `local::this`.
6. **Randomization in UVM macros.** In uvm-core 2020.3.1 (`uvm_sequence_defines.svh`; IEEE 1800.2-2020 B.3.1.3/B.3.1.4), `` `uvm_rand_send `` and `` `uvm_do `` turn a failed `randomize() with CONSTRAINTS` into `` `uvm_warning("RNDFLD", "Randomization failed in uvm_rand_send action") `` and still call `finish_item`. The stale item goes to the driver. Prefer the explicit pattern with `` `uvm_fatal ``. Link I-UVM-3A, which already teaches RNDFLD at `index.mdx:121`.
7. **Language limits and 1800-2023 additions:**
   - Constraints are 2-state: x/z values and `===`/`!==` are illegal (§18.3).
   - Rand enums take only their named constants, but enum members of packed structs and unions do not (§18.4).
   - `rand real` (§18.4.1 example), with `randc` illegal on real.
   - Tolerance ranges `[A +/- B]` and `[A +%- B]` (§11.4.13).
   - Say the revision in which each feature arrived is unverified, and that tool support varies.
8. **Solver performance at scale (tool-dependent, no figures):** keep variables narrow; avoid wide `*`, `/` and `%`; bound sizes; randomize once per item; use `solve…before` only for distribution; profile with the simulator's tools.
9. **Interview angles (attempt-first).** Keep the two existing IQPs and add questions on:
   - P(x == 0) under `x + y < 8`;
   - the range-weight rule;
   - `len == len`;
   - `randc` in UVM items;
   - why `assert(randomize())` is a bug;
   - the soft-`dist` trap.

**`## Quick Take`**
- **What it is:**
  - A random variable (`rand`/`randc`) is a class property that `randomize()` assigns.
  - Constraints are Boolean rules over those variables.
  - The simulator's constraint solver returns one combination that satisfies them all.
- **Why it matters:** directed tests miss combinations, and this is how M2 sequence items and M4 stimulus shaping work.
- **The Analogy:**
  - Constraints are a stencil laid over the grid of every possible value combination. Each `randomize()` throws one dart that lands in an open hole, every hole equally likely.
  - `dist` and `solve…before` change where darts tend to land, never which holes are open.
  - *Where it breaks:* a real solver does not list the holes. When `dist` variables are coupled, tools may differ (§18.5.3). `randc` remembers earlier darts.
- **You will be able to:** 1–5 (Objectives section).
- **Before you start:** the links in the Objectives section.

`### Worked example: a constrained-random bus item`. A complete unit tagged `// compile`. The sketch below was checked by inspection, not compiled. The author must run it on a simulator, wrap lines over 90 columns, and replace the illustrative log with a real one, naming the simulator and version.

```systemverilog
// compile
module tb_top;
  typedef enum bit [1:0] {READ, WRITE, ATOMIC} op_e;

  class bus_item;
    rand  op_e       op;
    rand  bit [31:0] addr;
    rand  bit [7:0]  len;
    rand  byte       data[];
    randc bit [3:0]  tag;                                   // one permutation per object
    constraint c_align { addr[1:0] == 2'b00; }              // word aligned
    constraint c_len   { len inside {[1:16]}; }             // bounds the array size
    constraint c_size  { data.size() == len; }
    constraint c_mode  { op dist { READ := 6, WRITE := 3, ATOMIC := 1 }; }
    constraint c_def   { soft len == 4; }                   // a test may override it
    extern constraint c_map;                                // body after the class
  endclass

  // Out-of-body block: same scope, after the class (IEEE 1800-2023 §18.5.1)
  constraint bus_item::c_map { addr inside {[32'h0000_1000 : 32'h0000_1FFF]}; }

  int pass, fail;
  int op_count[3];

  function automatic void check(bus_item t);
    if (t.addr[1:0] == 2'b00 && t.addr inside {[32'h1000 : 32'h1FFF]} &&
        t.len inside {[1:16]} && t.data.size() == t.len) pass++;
    else begin
      fail++;
      $display("FAIL addr=%h len=%0d size=%0d", t.addr, t.len, t.data.size());
    end
  endfunction

  // The argument is also called len: local:: makes the constraint use the argument.
  task automatic send_len(bus_item t, bit [7:0] len);
    if (!t.randomize() with { len == local::len; })
      $fatal(1, "RAND: randomize() failed for len=%0d", len);
    check(t);
  endtask

  initial begin
    bus_item t, a;
    bit [7:0] old_len;
    bit seen[16];
    int n_len4, distinct;
    t = new();
    repeat (1000) begin
      if (!t.randomize()) $fatal(1, "RAND: randomize() failed");
      check(t);
      op_count[t.op]++;
      if (t.len == 4) n_len4++;
    end
    $display("op READ=%0d WRITE=%0d ATOMIC=%0d of 1000",
             op_count[READ], op_count[WRITE], op_count[ATOMIC]);
    $display("len==4 on %0d of 1000 calls", n_len4);
    send_len(t, 9);
    $display("send_len(9): len=%0d", t.len);
    old_len = t.len;
    if (!t.randomize() with { len == 0; })                  // c_len forbids 0
      $display("EXPECTED_FAIL randomize()=0, len kept %0d (was %0d)", t.len, old_len);
    a = new();                                              // randc: per-object cycle
    repeat (16) begin
      if (!a.randomize()) $fatal(1, "RAND: randomize() failed");
      if (!seen[a.tag]) begin seen[a.tag] = 1; distinct++; end
    end
    $display("randc tag: %0d distinct values in 16 calls", distinct);
    $display("PASS=%0d FAIL=%0d", pass, fail);
    $finish;
  end
endmodule
```

**Optional NEW visualizer, `RandcCycleVisualizer` (P2).** No existing visual covers it: `constraint-solver-model.ts:46` says `randc` is not modelled.
- **Rules:**
  - Each object holds a permutation of the variable's legal values. Each `randomize()` returns the next value.
  - At the end of a cycle, a new random permutation starts.
  - When the constraints on the variable change (an inline `with`, or `constraint_mode`), the permutation is recomputed over the new legal set.
  - A `static randc` variable shares one permutation across all instances.
  - `randc` is solved before `rand` variables, so a coupled constraint can fail.
- **Scenarios:**
  1. one object, 2-bit;
  2. two objects;
  3. a constraint change mid-cycle;
  4. `static randc`;
  5. UVM style, a new item per call;
  6. coupling that fails.
- **Predictions:** "what values can the next call return?"; "can `a` and `b` return the same value on the same call?"; "after 4 new items, how many distinct values are guaranteed?" (only 1).
