**Expert: missing (no Push Further).** Add these `### Expert:` items. Every number below is verified in PSS 3.0 unless marked.

1. **Inference and determinism.**
   - §17.1: when bindings are left implicit, the tool may complete them by binding to traversed actions or by inferring new ones; when every required input is explicitly bound to traversed actions, it may not add actions.
   - Annex E (informative): the inferencing candidate list prefers explicitly traversed actions.
   - §12.3.7: `atomic { }` blocks stop interference from inference and resource scheduling. The 2.1 release notes list this as a 2.1 addition (limiting how inferred actions affect an activity region).
   - Interview angle: "your read-after-write test sometimes reads an address no traversed write produced: why?"
2. **Scheduling semantics.**
   - §12.3.4 `parallel`: synchronized start, no cross-branch dependencies. A buffer binding across branches makes the activity illegal (§12.3.4.2).
   - §12.3.5 `schedule`: the tool picks any legal order.
   - §12.3.6 join specifiers: `join_branch`, `join_select`, `join_none`, `join_first`.
   - Predict: two lockers with `pool [1]` are an error under `parallel` and serialized under `schedule`.
3. **Randomization order and exec blocks.**
   - §12.3.1.1 b: traversal steps pre_solve → random values → post_solve → pre_body → body → activity.
   - §16.4.9: values are chosen at traversal with "relationship lookahead".
   - §17 intro: the tool does not backtrack across exec blocks, so `post_solve` assignments can cause unsatisfied-constraint errors.
4. **`default` vs SystemVerilog `soft`; PSS `dist` vs SV `dist`.**
   - §16.1.10 a, d: a default is an equality until disabled. Precedence runs containing context > derived type > later in the same type.
   - IEEE 1800-2023 §18.5.13: a `soft` constraint yields to hard constraints.
   - §16.1.11: values outside the `dist` list are excluded unless a constraint forces them, and `:/` divides the weight across a range.
   - IEEE 1800-2023 §18.5.3: SV `dist` is a set-membership constraint plus weights.
5. **Realization flows and mapping mechanisms.**
   - §22.4 imported functions, §22.5 target-template exec blocks, §22.6 target-template functions.
   - §22.8 Tables 25 and 26: no target code generation, per-model generation, per-test generation, and which exec kinds each supports.
   - §22.1.2 exec kinds: `header`, `declaration`, `run_start`, `run_end`, `pre_solve`, `post_solve`, `pre_body`, `body`, `init_down`, `init_up`.
   - Annex D.5: SystemVerilog type bindings.
   - Tool-dependent, and must be labelled so: pre-generated vs on-target solving.
6. **Coverage.** §18 data coverage (covergroups); §19 behavioral coverage (`cover`, `monitor`), new in 3.0.
7. **Versions and tools.**
   - Versions: 2.0 (2021-04), 2.1 (2023-10), 3.0 (2024-08); 3.1 in public review (draft 2026-08-28).
   - Tool-dependent: version support, and whether `soft` exists. The `pssparser` grammar cites "PSS 3.1 B.14 / 13.1.12" for `soft`; this is not verified against the draft.
   - Tools: Cadence Perspec System Verifier, Siemens Questa inFact, Synopsys VC Portable Stimulus, Breker Trek5; open source: PSSTools `pssparser`.
8. **PSS vs UVM virtual sequences: architecture trade-offs.**
   - When PSS pays: many platforms; resource-aware concurrency the tool must solve; inference of setup chains; SoC use-case libraries.
   - When it does not: single-target block-level simulation; no owner for the realization layer; debugging through generated code; licence cost.
   - Integration: run the generated sequence on a virtual sequencer, raise objections in the test, regenerate for each seed.
9. **Staff-level interview questions (attempt-first):**
   - Why can't a resource be an input?
   - `parallel` vs `schedule` with a pool of one?
   - `default` vs `soft` when composing scenarios?
   - What stays hand-written and who owns it?
   - When would you not use PSS?

**## Quick Take**
- **What it is:** Accellera PSS is a language for test *intent*, kept separate from each platform's *realization*.
  - Versions: 2.1 (October 2023), 3.0 (August 2024, current), 3.1 in public review (2026).
  - It is an Accellera standard with no IEEE number. IEEE 2401 and 2851 are unrelated standards.
- **Why it matters:** SoC scenarios rerun on simulation, emulation, prototypes and silicon. One rewrite per test per platform multiplies effort. PSS keeps one scenario model, lets a tool infer setup actions and schedule around shared resources, and needs one realization per action per platform.
- **The Analogy:** an itinerary and a travel agent.
  - The itinerary is the activity.
  - The agent (the tool) adds the connecting flights (inferred actions), stops two guests getting the same room (lock/share) and prints tickets in each airline's format (exec blocks).
  - Where it breaks: the agent cannot invent an airline. Every action needs a hand-written realization per platform, and nothing gets checked unless an exec block or the scoreboard checks it.
- **You will be able to:** the five objectives below.
- **Before you start:** A-UVM-8; I-UVM-3B virtual sequences; I-SV-2A constraint blocks (`dist`, `soft`, for contrast).

- **The SequenceDiagram** (row 9).
- **How-to steps:**
  1. List the actions and the data they exchange.
  2. Choose a flow-object kind per exchange.
  3. Model shared resources and pool sizes.
  4. Write the activity, then pin critical bindings with `bind`.
  5. Write the exec templates per target.
  6. Generate and read the resolved schedule before running.
  7. Run on each target.
