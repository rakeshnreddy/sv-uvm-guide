## Completeness and depth gaps the analyst missed

**Practitioner and expert items**

1. **An instance add for another type pair hides type-wide callbacks.** This is uvm-core impl., found by source inspection; confirm it on a simulator before teaching it.
   - All instance queues live in one pool keyed by object (`uvm_callback.svh:112`). `m_get_q` uses an object's pool entry whichever type pair created it (`:964-975`), and filters the entries by `$cast` (`:998`).
   - An instance add for another pair seeds the new queue with only two type-wide queues: the report-object one and the one for its own T (`:781-809`).
   - Example:
     - `base_test.build_phase` calls `uvm_callbacks#(my_driver, drv_cb)::add(null, log_cb)`.
     - Later a test adds a report catcher to one driver with `uvm_report_cb::add(env.agt0.drv, demoter)`.
     - `agt0.drv` now has a pool queue without `log_cb`, so it silently stops running it. `agt1.drv` still runs it.
     - If the type-wide add comes after the catcher, `m_add_tw_cbs` adds it to that queue (`:292-315`).
   - `display()` lists every entry of a T object's pool queue with no CB filter (`:415-460`), so the catcher appears in `uvm_callbacks#(my_driver, drv_cb)::display()` output.
   - Where it goes: expert item 4, the never-fires table, and an interview angle: "A type-wide error callback stops on one driver after a colleague adds a report catcher to that driver. Why?"
2. **Where callback messages come from.**
   - `CBUNREG`, `CBPREG`, `CBNOMTC` and `CBTPREG` go through the global report functions (`uvm_globals.svh:156-169`) to `uvm_root`, whose report handler is named `reporter` (`uvm_root.svh:390-393`).
   - So the log shows `reporter [CBUNREG] …`, and catchers or severity overrides must target `uvm_root` (V04).
   - The debug table's "what the log shows" column needs this.
3. **Two silent or ambiguous debug cases.** `CBUNREG` covers three different cases (V03), and `add_by_name` skips non-T matches without a warning (V05). Both belong in the symptom → cause → fix table.
4. **`get_all()` returns disabled callbacks too.**
   - §10.7.2.5 says "whether they are enabled or disabled", and `uvm_callback.svh:1105-1143` has no `callback_mode` check. Iteration skips disabled callbacks.
   - A self-check meaning "will run" must filter with `is_enabled()`.
   - Add this to card a-uvm-5-9 and to step 6 of the Make It Work how-to.
5. **The end of test cuts off the last check.** Any checker that observes the last injected item, whether an assertion, a monitor or a scoreboard, needs a drain time or extra cycles (L28-LAB-V01). This belongs in Make It Work if the author adds a checker, and in the hand-off to planned A-UVM-9.
6. **Stateful callbacks are shared.**
   - A callback object added type-wide or to several components shares its members (counters, flags) and its `callback_mode` across all of them.
   - For "count inside the callback" (the kata and expert item 6), count per `drv` argument or attach one object per instance.
   - This is a practitioner pitfall.
7. **Macro-local names.**
   - `` `uvm_do_callbacks `` expands to a block that declares `iter` and `cb` (`uvm_callback_defines.svh:177-186`). They hide same-named identifiers in the METHOD arguments.
   - Spine §5.1 names clocking blocks `cb`. `vif.cb` is safe because it is qualified; a bare member called `cb` is not.
   - This is an expert gotcha.
