     - A6.1–A6.6 and Table A6-1;
     - "A response from an intermediate AXI component cannot guarantee ordering with respect to components that are downstream" (A6.1 note);
     - response before final destination (A6.5);
     - Device guarantees are a superset of Normal (A6.5);
     - the Ordered_Write_Observation property and producer/consumer ordering (A6.6).

     - A Little's-law estimate, labelled as a model and not a spec rule.
     - Read data reordering depth is "a static value that must be specified by the designer of the slave", with "no mechanism" for the master to learn it (A5.3.1).
     - ID width recommendations: up to 4 bits at a master, up to 4 more for interconnect port numbers, 8 at a slave (A5.3.6).
     - ID growth through cascaded interconnects.
  3. **How interconnects keep same-ID order across slaves.** Each strategy is labelled as an implementation choice:
     - stall a target change, at a head-of-line cost;
     - reorder buffers;
     - ID remapping, where "any manipulation of the AXI ID values … must ensure that the ordering requirements of the original ID values are maintained" (A6.3).

     Write data must be forwarded in address order when masters are merged (A5.3.2), which leads to the W-ordering deadlock in B-AXI-5.
  4. **Read-after-write checking at scale.**
     - A6.4 slave obligations, including Device writes that must be observed by later same-ID Device writes even before a response.
     - Single-copy atomicity: a read overlapping an in-flight multi-beat write can see a mix of old and new data at atomic-unit granularity (A7.1).
     - Expected-value sets in the scoreboard.
     - VIP "RAW policy" knobs are vendor-specific; label them as such.
  5. **AXI3 legacy (A5.3.3, A5.4.2).**
     - Write interleaving depth.
     - The first data item of each write arrives in address order.
     - Same-AWID data is never interleaved.
     - An interleaving slave must keep accepting data.
     - An AXI3 master must be set to depth 1 for AXI4.
     - Bridges generate WID from AWID.
  6. **Staff-level interview angles**, attempt-first (see Target outline).

**`## Quick Take`**
- **What it is:** an AXI ID (AWID or ARID, reflected on BID or RID) names an ordering stream. Transactions with one ID in one direction complete in issue order. Different IDs may complete in any order, and their read data may interleave.
- **Why it matters:** every AXI monitor, scoreboard and interconnect check must accept all legal orders and flag only the illegal ones.
- **The Analogy:** supermarket checkout lanes. Customers in one lane leave in the order they joined; different lanes finish independently. *Where it breaks:* reads and writes are two different shops, so the same lane number gives no order between them. Also, a read lane may hand over bags one at a time, interleaved with other lanes.
- **You will be able to:** the five objectives below.
- **Before you start:** B-AXI-1, B-AXI-2, A-UVM-6 (links in Navigation).

- **How-to:** five numbered steps:

- **Debugging table:**

| Symptom (log line) | Likely cause | Fix |
|---|---|---|
| `RID=3 with no outstanding read` | DUT or interconnect returned an ID it never received (an extend or strip bug); the monitor missed the AR (wrong sampling edge); or the monitor uses the master's ID width at the slave port | Compare with the AR log at the same interface; check the ID width at each port |
| `RID=3 beat 0: got B…, expected A…` with two same-ID reads outstanding | Same-ID reordering in the DUT (A5.3.1) | DUT bug; confirm with AR and R timestamps |
| `RLAST after 1 beats, expected 2` | Early RLAST, a dropped beat, or two same-ID bursts of different lengths returned out of order | Check RLAST against ARLEN per ID |
| End of test: reads with ID 4 never completed | Slave hang, RREADY held low, or the interconnect holding B behind A for same-ID order to another slave | Inspect the outstanding table at the end of test; check the READYs |
| Scoreboard flags legal cross-ID reordering | One FIFO for all IDs | Per-ID queues (A-UVM-6) |
| Read returns old data after a write to the same address | Legal if the AR was issued before the write's B (A5.3.4); a DUT bug if issued after it (A6.4) | Compare the AR issue time with the B time |

### Hands-on plan

**1. Kata (this is Make It Work): a per-ID expected-queue model in plain SV.** The block below is checked by inspection against IEEE 1800-2023:
- associative-array allocation on `++` is §7.8.7;
- `pop_front` and `push_back` are §7.10.2.4 and §7.10.2.7;
- short-circuit `||` is §11.3.5 and §11.4.7.

It has no delays, so it needs no timescale.

```systemverilog
// compile
module tb_top;
  class axi_order_model;
    int unsigned exp_beats [int][$];  // AxLEN+1 of each outstanding read, AR order, per ID
    int unsigned got [int];           // beats seen for the oldest read of each ID
    int unsigned pass_cnt, fail_cnt;

    function void on_ar(int id, int unsigned len);
      exp_beats[id].push_back(len + 1);
    endfunction

    function void on_r(int id, bit last);
      if (!exp_beats.exists(id) || exp_beats[id].size() == 0) begin
        $display("FAIL: RID=%0d with no outstanding read", id);  // A5.3.1
        fail_cnt++;
        return;
      end
      got[id]++;                          // same-ID beats never mix, so they belong to the oldest read
      if (!last) return;
      if (got[id] != exp_beats[id][0]) begin
        $display("FAIL: RID=%0d RLAST after %0d beats, expected %0d", id, got[id], exp_beats[id][0]);
        fail_cnt++;
      end else begin
        $display("PASS: RID=%0d burst complete (%0d beats)", id, got[id]);
        pass_cnt++;
      end
      void'(exp_beats[id].pop_front());   // the oldest read with this ID is done
      got[id] = 0;
    endfunction
  endclass

  axi_order_model m;

  initial begin
    // Trace 1 (legal): A (ID 1, 2 beats), B (ID 2, 2 beats), C (ID 1, 1 beat); B interleaves with A
    m = new();
    m.on_ar(1, 1); m.on_ar(2, 1); m.on_ar(1, 0);
    m.on_r(2, 0); m.on_r(1, 0); m.on_r(2, 1); m.on_r(1, 1); m.on_r(1, 1);
    $display("trace 1: PASS=%0d FAIL=%0d", m.pass_cnt, m.fail_cnt);
    // Trace 2 (DUT bug): C's single beat returns before A's two beats (same ID)
    m = new();
    m.on_ar(1, 1); m.on_ar(1, 0);
    m.on_r(1, 1); m.on_r(1, 0); m.on_r(1, 1);
    $display("trace 2: PASS=%0d FAIL=%0d", m.pass_cnt, m.fail_cnt);
  end
endmodule
```

**`## Push Further`.** The seven `### Expert:` items in the Depth ladder.

- **`### Expert: AXI5 atomic transactions (awareness)`.** Every AXI5 statement must be checked against IHI0022 Issue H or later before it is published; the issue and section numbers are unverified.
  - AXI5 adds atomic transactions, in which the master sends the operation and its data and the target performs the read-modify-write. The four types are AtomicStore, AtomicLoad, AtomicSwap and AtomicCompare (secondary source: Synopsys). AtomicStore and AtomicLoad each support eight operations.

  - **Verification impact:** a monitor that matches every R beat to an AR must also accept R data for atomic AW transactions. The scoreboard needs an operation model. ID-use rules for atomics must be checked in the spec.

### Hands-on plan

**1. Kata (Make It Work): exclusive pairs with expected responses.**
- **Form:** a `// compile` plain-SV `tb_top` holding a class `excl_ref_model`. Members:
  - `bit supports_excl`;
  - `bit [31:0] mon_addr [int]` (one monitored address per ID, A7.2.3);
  - `int unsigned mem [bit [31:0]]`.
- **Methods:**
  - `ex_read(id, addr)` returns OKAY if exclusives are unsupported (A7.2.2). Otherwise it records the address for the ID and returns EXOKAY; a newer same-ID read moves the monitor (A7.2.1).
  - `ex_write(id, addr, data)`:
    - without support, it writes memory and returns OKAY (A7.2.5);
    - if the address is monitored for this ID, it writes, clears every monitor on that address, and returns EXOKAY;
    - otherwise it returns OKAY without writing (A7.2.3).
  - `write(addr, data)` writes memory and clears every monitor on that address.
  - `check_shape(len, size, addr)` flags A7.2.4 violations.

  - Collect the IDs to delete first, then delete them; do not delete from the associative array inside its own `foreach`.
