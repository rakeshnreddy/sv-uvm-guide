**Expert: absent.** Add these `### Expert:` subsections.

1. **What a null child sequencer really does.**
   - With a parent, uvm-core `set_item_context()` substitutes the parent's sequencer (`src/seq/uvm_sequence_item.svh`, tagged §14.1.2.2). The LRM text of §14.1.2.2 does not specify the fallback, so label it "uvm-core 2020.3.1".
   - On a virtual sequencer, `start_item()` then waits forever, because item grants happen only when a driver pulls (`uvm_sequencer_param_base::m_safe_select_item`).
   - If the child declares `` `uvm_declare_p_sequencer ``, `UVM_FATAL [DCLPSQ]` fires at `start()` (Annex B.3.3; `src/macros/uvm_sequence_defines.svh`).
   - With no parent, `UVM_FATAL [SEQ]` fires at the first `start_item()` (`uvm_sequence_base.svh`).
   - Add defensive null checks in the virtual sequence.
2. **Lock and grab across a virtual sequence.**
   - §14.2.5.5–§14.2.5.8 and §15.3.2.10–§15.3.2.11 define lock and grab. A grab goes to the front of the queue.
   - uvm-core `is_blocked()` exempts every descendant of the lock holder via `is_child()` (§15.3.2.2, §15.3.2.8; `uvm_sequencer_base.svh`):
     - a virtual sequence that grabs `data_sqr` does **not** pause its own children, including background traffic it started with `this`;
     - a child started without a parent waits behind its own parent's grab;
     - to pause sibling traffic, the reconfiguration or interrupt-service child must hold the grab itself.
   - Returning from `body()` while holding a lock, or while descendants still queue on a sequencer the sequence locked, gives `UVM_ERROR [SEQFINERR]` (`remove_sequence_from_queues`).
3. **`uvm_event` is a state, not a pulse.**
   - `on` stays set until `reset()` (§10.1.1.2.2, §10.1.1.2.8).
   - The `wait_trigger` race (§10.1.1.2.4) versus `wait_ptrigger` (§10.1.1.2.5), which persists only within the time slot. It is built on the SystemVerilog `triggered` property (IEEE 1800-2023 §15.5.3).
   - `reset(1)` wakes only `wait_trigger`/`wait_ptrigger` waiters (§10.1.1.2.8).
   - Trigger data (§10.1.2.2.4–§10.1.2.2.5).
   - Pool keys: `uvm_event_pool::get` creates a missing event (§10.4.1.2.4), so a typo in a key silently creates a second event. Put key names in a shared package.
   - `get_num_waiters()` (§10.1.1.2.10) for debug.
4. **Barriers with changing membership.**
   - The threshold defaults to 0, so nothing blocks (§10.3.2.1).
   - `set_auto_reset` (§10.3.2.4).
   - Lowering the threshold below the number of waiters releases all of them (§10.3.2.6).
   - `cancel()` when a participant is killed (§10.3.2.8).
   - `reset(wakeup = 1)` is the default (§10.3.2.3). Mid-test reset is owned by proposed A-UVM-9 (link as text).
5. **Ending background traffic cleanly.**
   - `kill()` terminates all descendants (IEEE 1800-2023 §9.7). `wait fork` waits for immediate children, including a `forever` responder (§9.6.1). `disable fork` kills every descendant (§9.6.3).
   - uvm-core kills the phase processes in `cleanup_phase`, after `UVM_PHASE_ENDED` (`uvm_phase_hopper.svh`).
   - uvm-core 2020.3.1 process guards (`@uvm-contrib`, not in 1800.2): when the process that called `start()` is killed, the library reports `UVM_WARNING [SEQPRTZMB]` (or `[SEQBDYZMB]`) and kills the sequence (`uvm_sequence_base.svh`, `uvm_process_guard_base.svh`). By source inspection this also fires for a background responder still running when the run phase ends. Confirm in a simulator before the page states it as fact.
   - The clean alternatives:
     - a default sequence on the responder's sequencer, killed through `kill()` when the phase ends (§15.3.5; `uvm_task_phase.svh` at `UVM_PHASE_ENDED`);
     - `seq.kill()`, which also kills children started with `this` (§14.2.5.11);
     - `stop_sequences()` (§15.3.2.14);
     - a cooperative stop event.
6. **Who may object.**
   - Never use the automatic phase objection on a `forever` sequence: §14.2.4.4 NOTE says it is never dropped.
   - An objection raised in a thread that is later killed is never dropped.
   - Drain time (§10.5.1.3.7) versus `phase_ready_to_end` (§13.1.4.3.2).
   - Debug with `+UVM_OBJECTION_TRACE` and `display_objections()` (both uvm-core impl., `uvm_objection.svh`) or `get_objectors()` (§10.5.1.5.1).
7. **Ordering between monitors in one time step.** Two monitors that `write()` at the same edge do so in a nondeterministic order (IEEE 1800-2023 §4.7). A scoreboard must not infer config-before-data from arrival order. Stamp items with the sampling cycle, or sample both on one clocking event.
8. **Configuration architecture and scale.**
   - One env config object versus many scalar `uvm_config_db` entries. The lookup cost of wildcard entries is qualitative only, so link E-PERF-1 and quote no numbers.
   - `is_active` precedence: a VIP that copies `cfg.is_active` overrides a `+uvm_set_config_string=<agent>,is_active,UVM_PASSIVE` command-line setting, which §13.4.2.2 says the agent supports.
   - Arrays of agents. The per-instance vifs are set from a `generate` loop, because an instance select needs a constant expression (IEEE 1800-2023 Clause 23, hierarchical names; sub-clause unverified in the text extract).
   - Per-agent coverage and check switches.
   - `print_topology()` to audit what was built (Annex F.7.4.2).
9. **Vertical reuse at scale.**
   - An env "can be reused as a sub-environment" (§13.3).
   - Nested virtual sequencers versus flat handles; reuse block virtual sequences by starting them on the block virtual sequencers as children.
   - Internal agents become passive.
   - Keep block scoreboards as checkers on internal interfaces, or replace them end-to-end.
   - Register models compose with `add_submap` (§18.2.3.5; link A-UVM-4A).
   - `uvm_config_db` paths change when you nest.
   - Link E-SOC-1 for strategy.
10. **Interview angles (attempt-first).**
    1. Design the environment for a DMA engine with an APB slave config port, an AXI master data port and an IRQ output. Expected answer: an APB **master** agent, an AXI **slave** responder agent with a memory model, a passive IRQ monitor, a register model with an explicit predictor, a reference model, and a scoreboard keyed per channel (the corrected roles of G29-UVM-04).
    2. "Every item matched, but the job hit the watchdog."
    3. "The regression passed, but the interrupt responder never ran." Answer: a null handle plus the parent fallback plus `join_none`.
    4. "Stop a `forever` responder without warnings."
    5. "Why can't a semaphore stop another component's sequence on the same sequencer?"
    6. "An intermittent config-after-data error on one simulator only" (§4.7).

**`## Quick Take`**
- **What it is:** an environment with one agent per DUT interface, some active and some passive, often nested sub-environments, a virtual sequencer, a configuration-object tree, and scoreboards that see more than one interface.
- **Why it matters:** the bugs live between interfaces: data before configuration, reconfiguration mid-stream, interrupt timing. Multi-agent mistakes show up as hangs and silent passes, not mismatches.
- **The Analogy:** a railway junction run from a signal box. Each line (agent) runs its own trains; the timetable (the virtual sequence's `body()`) decides who goes when; signals (events, barriers, grabs) hold trains; platform observers (passive agents) only watch. *Where it breaks:* nothing enforces the timetable except the code in `body()`, and a passive "line" has no trains at all (its sequencer handle is null).
- **You will be able to:** the five objectives below.
- `<BeforeYouStart />`, plus one sentence: "Uses A-UVM-6 (scoreboards), I-UVM-1C (objections, `uvm_event`, `uvm_barrier`) and I-UVM-5 (`uvm_event_pool`)."

## Cross-cutting observations

1. **`uvm_event` has no trigger counter.** `I-SV-5_Synchronization_and_IPC/events.mdx:73` says "`uvm_event`, which counts triggers", and `:81` lists a "`trigger_cnt`". Neither IEEE 1800.2-2020 §10.1 nor uvm-core 2020.3.1 `src/base/uvm_event.svh` has a trigger count. The only counter is `get_num_waiters()` (§10.1.1.2.10). Forward to the I-SV-5 group.
2. **Null handle with a parent.** The fallback to the parent's sequencer (uvm-core `set_item_context`) is owned by I-UVM-3B (L24 cross-cutting 2). A-UVM-8 must apply it to passive agents and link `virtual-sequences`. Both pages should use the same wording and the same two-column table (without parent / with `this`).
3. **Lock ownership follows the parent chain.** uvm-core `is_blocked()` lets descendants of the lock holder through. So a virtual sequence's own `grab()` does not pause its own children, including background traffic it started with `this`. This also affects I-UVM-3B `sequence-arbitration` and `interrupt-handling` (L23, L24) wherever a virtual sequence grabs. The ISR or reconfiguration child should hold the grab.
4. **Process guards in uvm-core 2020.3.1** (`@uvm-contrib`: `SEQPRTZMB`, `SEQBDYZMB`). By source inspection they fire when the process that called `start()` is killed, including at the end of the run phase for background sequences. This touches every lesson that shows background sequences, `disable fork` near sequences, or the visual's restart snippet (`vseq-coordination-model.ts:628`, `disable fork;`): F2C, I-SV-5, I-UVM-3B, A-UVM-8, E-DBG-1 and proposed A-UVM-9. It needs one simulator confirmation (same as L24 request 7). Until then, lessons should label it "uvm-core 2020.3.1, by source inspection".
5. **One naming scheme.**
