## Completeness and depth gaps the analyst missed

1. **E-EMU-1, 2-state emulation and X handling (expert and practitioner).** The concept table, the rules table and the expert items never mention that emulators run 2-state. Add three things: X/Z coercion at the boundary, reset and initialization differences against 4-state simulation, and the need to keep X-checking in simulation, with SCE-MI 2.4 §5.6.1.3.1 as the source. Put a row in "emulation-friendly coding rules" and a line in "One bench for simulation and emulation".
2. **Both pages, packing order at the boundary has no picture.** Garbled fields are in both debug tables, yet no visual shows why. SCE-MI 2.4 §5.6.1.3.3 gives the canonical example: in SV the first member of a packed struct is the most significant, while in a C struct it comes first in memory, so the field order must be reversed. Add a traced example (struct, bit layout, C view), shared by E-EMU-1 (converter) and E-UVM-ML-1 (data conversion expert item).
3. **E-EMU-1, getting software and data into the emulated design.** Boot and firmware tests, the page's own motivation, depend on preloading DUT memories (backdoor load of firmware or images). This is tool-dependent, and I did not verify a primary source. If it is covered, include it as a labelled, tool-dependent practitioner item, or name it explicitly as out of scope.

However, "Emulation-friendly coding rules: Mechanism partial" hides that the page's mechanism statements for timescale, clocks, DPI and `$display` are all wrong (EMU-08, EMU-09). ## Notes for the implementation author

1. **Keep two layers apart in E-EMU-1:** what SCE-MI 2 standardizes, and what vendors add. The standard covers DPI functions and zero-time tasks, pipes, frozen HW time while the SW side runs, the Table 5.3 types, and two-level nesting. TBX adds time-consuming HVL→HDL BFM tasks through virtual interfaces and one-way void calls that do not stop the clocks. The worked example uses the TBX-style virtual-interface pattern (DVCon 2011), which is fine and simulates anywhere, but label it a vendor-supported methodology "inspired by" SCE-MI 2 (EMU-02, EMU-V01).
2. **Use one synchronization model on the whole page** (EMU-V02): one host synchronization per HVL time advance or HDL-signal wait. Derive the predict number from the snippet you actually show, and say it in the explanation.
3. **The corrected pin-level driver is now an S1 fix** (EMU-07). Show the beat sequence in a small trace table or the `<TimingDiagram>`, so the duplicate-beat bug and its fix are visible, not just described.
4. **Do not write "`$display` is not synthesizable"** anywhere, quiz included. Write "tool-dependent; every HDL-side message is an HDL→HVL transfer that costs throughput; portable code reports from proxies or assertion action blocks".
5. **HVL-side rule wording** (EMU-V07): forbid `#`, clock and DUT-signal waits, and polling. Do not forbid every `@` or `wait`.
