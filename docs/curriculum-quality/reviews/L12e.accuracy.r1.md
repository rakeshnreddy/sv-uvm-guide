## Findings

### S3

**A1. `` `uvm_do_with `` is presented as the standard macro; it is a uvm-core deprecated-file macro, not IEEE 1800.2-2020.**
- Where: solver-debug.mdx:280, :283-284 (SequenceDiagram title and caption), :523, :555, Q8 (:712), card sd-11, debugging table, References :830-831.
- Problem: the page's main UVM example is `` `uvm_do_with(req, {…}) ``, and :555 introduces the discussion as "The uvm-core 2020.3.1 macros for sequences (IEEE 1800.2-2020 Annex B.3.1)". Annex B.3.1 defines only `uvm_create`, `uvm_send`, `uvm_rand_send` and `uvm_do` (with a `CONSTRAINTS` argument). In uvm-core 2020.3.1, `uvm_do_with` lives in `src/deprecated/macros/uvm_sequence_defines.svh:69-70` and expands to `` `uvm_do(SEQ_OR_ITEM, get_sequencer(), -1, CONSTRAINTS) ``. The behaviour the page describes is correct; the provenance is not stated, and learners may conclude `uvm_do_with` is standard 1800.2.
- Fix: one sentence at :280 or :557: "`` `uvm_do_with `` is a uvm-core convenience kept in `deprecated/macros/uvm_sequence_defines.svh`; IEEE 1800.2-2020 defines the same action as `` `uvm_do(req, , , { … }) `` (Annex B.3.1.4). Both expand to `` `uvm_create `` plus `` `uvm_rand_send ``." Add `deprecated/macros/uvm_sequence_defines.svh` to the uvm-core references at :831.
- Source: `uvm_lrm.txt` B.3.1.1-B.3.1.4 (0 hits for `uvm_do_with`); uvm-core 2020.3.1 `src/deprecated/macros/uvm_sequence_defines.svh:69-70`, `src/uvm_macros.svh:95`, `src/macros/uvm_sequence_defines.svh:110-114`.

### S4

**A2. Module RNGs are not "seeded from their parent".**
- Where: :320 "Every module, thread and object has its own random number generator, and each one is seeded from its parent when it is created (§18.14.1)."
- Problem: §18.14.1 gives each module instance, interface, program and package an initialization RNG "seeded with the default seed", an implementation-dependent value; only dynamic threads and objects are seeded from the parent thread (static processes from the initialization RNG).
- Fix: "Every module instance has an initialization RNG seeded from the simulation's seed; every thread and object has its own RNG, seeded from its creating thread when it is created (§18.14.1)."
- Source: IEEE 1800-2023 §18.14.1 (Initialization RNG, Thread stability, Object stability bullets).

**A3. "two failing calls" undercounts the calls that return 0 in the worked example.**
- Where: :480 "Your simulator will also print its own diagnostics for the two failing calls (STEP1 and `c_len off`)".
- Problem: STEP3's `randomize(null)` with only `c_buffer` on also returns 0, and some simulators report a failing checker call the same way.
- Fix: "…for the calls that return 0 (STEP1, `c_len off`, and possibly the `c_buffer` check in STEP3); their wording is tool-dependent." Similarly, the debug-challenge Expected output (:788-792) can note that the simulator may also print a diagnostic for each failing call.
- Source: §18.11.1 (a checker returns 0 when a constraint fails); tool behaviour is tool-dependent.

**A4. The 4-state sentence states a runtime outcome more firmly than the standard does.**
- Where: :178 "a constraint that reads it fails with an error rather than a normal failure"; debugging table :529.
- Problem: §18.3 says 4-state values or operators in constraints "are illegal and shall result in an error". It does not say when (compile time or at the call) or what `randomize()` returns; tools differ for a state variable that holds X at run time.
- Fix: "the standard makes it an error (§18.3); when and how a tool reports it is tool-dependent." The debugging-table row already says "A tool-specific error message".
- Source: IEEE 1800-2023 §18.3.

**A5. Q7's stem uses a declaration with an initializer in an unspecified procedural context.**
- Where: :701 "A test does pkt_item p; jumbo_item j = new(); p = j;".
- Problem: if read as code inside an `initial` block of a module, `jumbo_item j = new();` is an implicitly static variable with an initializer, which §6.21 forbids without `static`/`automatic`. The rewrite fixed the same pattern elsewhere (L12-2B-30).
- Fix: "A test declares pkt_item p and jumbo_item j, then does j = new(); p = j; and calls p.randomize()."
- Source: IEEE 1800-2023 §6.21.

**A6. "switching to another simulator: no" is stronger than the standard.**
- Where: :330.
- Problem: the standard makes the default seed and generator implementation-dependent; it does not guarantee different stimulus, only no guarantee of the same stimulus.
- Fix: "not guaranteed (in practice, no)".
- Source: IEEE 1800-2023 §18.14.1, §18.13.4-§18.13.5.
