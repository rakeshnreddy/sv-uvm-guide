## Findings

### S3

1. **Line 160, and the diagram edges at lines 151-153: `iss_sim` does not write trace CSVs.**
   - **Problem.** The prose says "`iss_sim` runs the ELF on one or more ISSes and writes trace CSV files", and the diagram labels the `iss_sim` → `iss_cmp` and `iss_sim` → `cov` edges "trace CSV". In `run.py` at master, `iss_sim` writes each ISS's commit log (`<iss>_sim/<test>_<i>.log`). `iss_cmp` → `compare_iss_log` converts the two logs to CSV (`process_spike_sim_log` etc.) and then calls `compare_trace_csv`. It returns without comparing anything unless exactly two ISSes were given.
   - **Fix.** Write: "`iss_sim` runs the ELF on each ISS and writes its log; `iss_cmp` (exactly two ISSes) converts both logs to trace CSVs and compares them". Relabel the two edges "ISS log".
   - **Source.** riscv-dv `run.py` `iss_sim`, `iss_cmp`, `compare_iss_log` (master, 2026-10-11 copy).

2. **Line 349: the description of what `instr_trace_compare.py` checks is incomplete in a way that matters for this lesson.**
   - **Problem.** The page says the script "counts leftover register-writing entries as mismatches". Only leftovers in the **second** CSV are counted. When the second trace ends, the in-order loop breaks (`if trace_2_index == len(instr_trace_2): break`), so extra entries in the first trace are never reported. That is the "extra retirement" blind spot this lesson teaches. The script also skips register writes that do not change the register's value (`check_update_gpr` returns 0 when `rd_val` equals the stored value), not only instructions that write no register.
   - **Fix.** Write: "it compares only register writes that change a register's value, never compares stores directly, and counts leftover entries in the second trace only; extra entries in the first trace pass unnoticed".
   - **Source.** riscv-dv `scripts/instr_trace_compare.py` `compare_trace_csv` and `check_update_gpr` (master).

### S4

3. **Lines 166, 176 and 179: the `sim_opts` and `cmp_opts` descriptions differ from the header the page cites, without saying so.**
   - **Problem.** The page says the keys "are documented in the header of every riscv-dv target testlist" and that `run.py` "looks up the generator-side keys by name". But the header defines `cmp_opts` and `sim_opts` as options "passed to the instruction generator", while `run.py` at master reads only the command-line `--cmp_opts`/`--sim_opts`, never the per-test keys. The page's `sim_opts` row ("read by your core flow") matches actual use in Ibex (`+enable_irq_seq=1`) but contradicts the header.
   - **Fix.** Add one clause: "the header calls `cmp_opts`/`sim_opts` generator options, but `run.py` uses only its `--cmp_opts`/`--sim_opts` arguments; per-test `sim_opts` is read by core flows such as Ibex's".
   - **Source.** `target/rv32imc/testlist.yaml` header; `run.py` (`do_compile`, `do_simulate`, `parse_args`).

4. **Line 794: the `+compare_final_value_only` effect needs one qualifier.**
   - **Problem.** `run.py`'s `iss_cmp` never reads `compare_opts`. It calls `compare_trace_csv` with the defaults. So the "[PASSED]: 0 matched" outcome happens only when a core flow passes the option to `instr_trace_compare.py` as `--compare_final_value_only 1`. The claim about the script itself is correct.
   - **Fix.** Add "when your core flow passes it to the script".
   - **Source.** `run.py` `compare_iss_log`; `instr_trace_compare.py` `main`.

5. **Line 740: the illustrative log line has the wrong time.**
   - **Problem.** `UVM_INFO @ 0: ... matched 10000 instructions` comes from `report_phase`, which runs at the end-of-simulation time, not at time 0. The block is labelled illustrative, but the time is still wrong.
   - **Fix.** Use a non-zero end time, for example `@ 412870`.
   - **Source.** IEEE 1800.2-2020 §9.8 (common phases: `report_phase` runs after the run-time phases); uvm-core 2020.3.1 `uvm_common_phases.svh`.

6. **Lines 1001-1017 (Kata 1 Part A): the "real run" output does not match what the page's snippet produces.**
   - **Problem.** The snippet defines only `A`, `B` and `C`. The case labels ("A wrong load data" and so on) and the 24-character name column in the output come from the author's own driver (`L48a/kata1.py` uses `{name:<24}`). With the worked script's `{name:<21}` format, the C line prints with no padding.
   - **Fix.** Show the three `CASES` entries with their labels, and either paste the output produced at width 21 or say that the column was widened.
   - **Source.** I re-ran the page's script with the snippet added.
