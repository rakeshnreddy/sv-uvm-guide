## Findings

### S3-1. Objective 1's "choose a sequence" is never tested
- **Where:** `built-in-ral-sequences.mdx:18` (objective 1); quiz items Q1 (:871), Q7 (:937) and Q11 (:981), all tagged `objective: 1`.
- **Problem:** Objective 1 is "Choose the Annex E sequence that answers a given question about a block … and state what it needs". The three quiz items tagged with it test only the second half: a fresh reset, unsafe registers and an idle DUT. No quiz item asks the learner to pick a sequence for a question. Only the second interview item (SoC strategy, :842) touches the choice. "Choose" is the verb the objective is measured by.
- **Fix:** Add one quiz item tagged `objective: 1`. Example stem: "A register is reachable from both the APB and the AXI map, and you suspect the two decoders disagree. Which built-in sequence answers that?" Key: `uvm_reg_mem_shared_access_seq` (E.4). Distractors: bit-bash (one map at a time, so it never compares across maps); the access test (frontdoor against backdoor, not map against map); the HDL-path check (no bus access). Alternatively, reword Q1 so that it asks for a choice.
- **Source checked:** spine §5.4 ("every objective is exercised … add `objective: <n>`"); plan §4 item 5; catalogue at :91-100.

### S3-2. The access test has no worked example with expected output
- **Where:** `:168-215` (access test); Make It Work `:362-743`.
- **Problem:** The access test is a core-path concept (:28 names it as the fifth core section), and the spine objective says to *run* it. It has a definition, purpose, mechanism, picture, pitfalls and debugging. It fails checklist item 5, though: no example on the page runs `uvm_reg_access_seq` and shows its log. The learner never sees the "Verifying access of register '…' in map '…' ..." line, which the page tells them to count (:315, :736, :825, interview 1 at :836). They also never see the legitimate "has only RO fields … skipping" warning, which is the reason the catcher matches the message text and not the ID (:806). Make It Work follows the analysis outline (E.1 then E.2), so this is S3 and not S2.
- **Fix:** Add a kata step 4, or a short "Extend it" under Make It Work. Give the bench HDL paths: `ral.add_hdl_path("tb_top.dut")` in the env, `CTRL.add_hdl_path_slice("mode", 0, 4)` and `("en", 4, 1)`, and `BOOT.add_hdl_path_slice("spare", 8, 8)` (link frontdoor-vs-backdoor for the API). Then start `uvm_reg_access_seq` and show the expected log: "Verifying access of register 'ral.CTRL' …"; the VERSION warning "has only RO fields … skipping"; then BOOT, if PINS is given a path or excluded with `NO_REG_ACCESS_TEST`. The bench already has auto-predict, so CTRL passes. Optionally add a mutant that removes `set_auto_predict(1)` and reproduces debug Log C.
- **Source checked:** README concept completeness checklist item 5; uvm-core 2020.3.1 `uvm_reg_access_seq.svh:154-156` (the "Verifying access" message), `:139` (RO-only skip) and `:288-291` (no-backdoor skip).

### S3-3. The `#1` in the access test is shown but never explained, and the debugging row misses the late-predictor cause
- **Where:** `:188` (the `#1` divider in the SequenceDiagram); `:206`; the Debugging table at `:324`; Q4's distractor at `:909`.
- **Problem:** The analysis asked the page to mention the `#1` the sequence waits between its frontdoor write and its backdoor check (L27-4B-05; L27.md Expert 3). The page draws it, and Q4 uses it as a distractor, but the prose never says what it is or why it matters to the learner. The Debugging row "mismatch right after the frontdoor write, on every register" gives a single cause: no prediction path. With *explicit* prediction, a monitor that publishes the transfer more than one time unit after `item_done()` gives the same symptom while the predictor is connected. A learner who has checked the connection then has nowhere to go.
- **Fix:** Add one sentence after :206. In uvm-core, the sequence waits `#1` after the frontdoor write before the backdoor check. The source gives no reason; letting a monitor-fed predictor catch up is the likely one. The delay's real length depends on the time unit `uvm_pkg` was compiled with (tool-dependent). An explicit predictor whose monitor publishes later still sees the old mirror. Add the cause "explicit predictor updates the mirror too late (monitor publishes after the `#1`)" to the :324 row, with the fix "publish at transfer completion" and a link to explicit-vs-implicit.
- **Source checked:** uvm-core 2020.3.1 `uvm_reg_access_seq.svh:160-169` (`write(~v, UVM_FRONTDOOR)`, `#1;`, `mirror(UVM_CHECK, UVM_BACKDOOR)`); L27.md depth-ladder Expert 3; L27-4B-05.

### S4-1. The kata step-3 log description is incomplete
- **Where:** `:1052`.
- **Problem:** The text says the log shows `[START_SEQ]` for `smoke`, then "the same 'Verifying' lines as before". `uvm_reg_mem_built_in_seq` creates its children as `reg_hw_reset_seq` and `reg_bit_bash_seq` and starts them with itself as parent. The log therefore also contains a `[STARTING_SEQ]` line for each child, and the report context changes (for example `smoke.reg_hw_reset_seq`), so the lines are not literally the same.
- **Fix:** Say "a `[STARTING_SEQ]` line for each child sequence (`reg_hw_reset_seq`, `reg_bit_bash_seq`), then the same Verifying messages under `smoke.…`, each test followed by `[FINISH_SEQ]`".
- **Source checked:** uvm-core `uvm_reg_mem_built_in_seq.svh:82-103`.
