## Findings

### S2

**F1. S2 randomization-methods.mdx:743, :758 - Kata 1 edit 6's key says "A becomes order-dependent", but in the kata's program the order is fixed by the standard.**
- *Problem.* T1 is spawned with `join_none`, and "processes spawned by a fork-join block shall not start executing until the parent process is blocked or terminates" (§9.3.2). T0 contains no blocking statement, so with edit 6 alone T0 runs all three `A.randomize()` calls first and T1 then takes A's 4th to 6th values. T0's A values, B and C are unchanged, and nothing is order-dependent. The key teaches nondeterminism where none exists, and a learner who reasons correctly from §9.3.2 is marked wrong. (Edit 5's own prompt, "so that T1 may now run before T0's calls", relies on the same rule, so the two rows contradict each other.)
- *Fix.* Either (a) change the key for edit 6 to "nothing that existed changes: T1 cannot start until T0 terminates (§9.3.2), so T0 still gets A's first three values and T1 gets the next three", and add a combined edit "5 + 6: T1 now runs first at the `#0` and takes A's first three values, so T0's A values change, deterministically"; or (b) rewrite edit 6 so that both processes really interleave on A at a point where the LRM leaves the order open (for example both resume from `@(posedge clk)` in the same time slot) and keep "order-dependent (§4.7)". Keep the general shared-object bullet (line 303) and the expert item (line 558), which are correct.
- *Source checked.* IEEE 1800-2023 §9.3.2 (Table 9-1 and the sentence after it), §18.14.3, §4.7.

### S3

**F2. S3 randomization-methods.mdx:21, :594-613 - The "Choose" half of objective 1 is never tested or exercised.**
- *Problem.* Objective 1 is "Choose between a class `randomize()`, `std::randomize()`, `randcase` and `randsequence` … and write each one". Q1 and Q2 test `std::randomize()` pitfalls (signedness, name lookup), and Kata 2 writes a grammar, but no quiz item or exercise asks the learner to pick a tool for a task. The "Four tools" table (lines 38-45) is the only place the choice appears.
- *Fix.* Add one `objective: 1` question, for example: "A test must be able to switch off the 'aligned address' rule for one error test; the rule currently sits in a `std::randomize() with` block inside a sequence body. What should you do?" Key: move it into a named constraint in the item class (tests can override or `constraint_mode(0)` it). Distractors: "use randcase to skip the rule sometimes", "use randsequence", "add a second `with` block". Alternatively a three-scenario matching item (loop count / weighted action / structured stream).
- *Source checked.* README §Target lesson 2 ("every objective must be exercised"); spine §5.4 Coverage.

**F3. S3 randomization-methods.mdx:254, :310-316 - The seed argument of `$urandom` (§18.13.1) is missing from both the `$urandom` section and the manual-seeding tools.**
- *Problem.* §18.13.1 defines `$urandom [ (int seed) ]`; the LRM's own example uses `$urandom(254)` to "initialize the generator". The page says manual seeding has "three tools" and never mentions this form, so the syntax-and-variants item is incomplete and a learner meeting `$urandom(seed)` in legacy code cannot predict that it reseeds the calling process's RNG, which shifts everything that process creates afterwards.
- *Fix.* Add the form to the `$urandom` paragraph and a fourth row to the manual-seeding table ("`$urandom(seed)` | the calling process | seeds the process RNG, then returns a value"), with the stability consequence.
- *Source checked.* IEEE 1800-2023 §18.13.1 (syntax and example).

**F4. S3 randomization-methods.mdx:297, :306 - "One extra randomize() call" (must-cover) is shown only for `obj.randomize()` and `$urandom`; the case of an extra `std::randomize()`, `randcase` or `randsequence` is left to inference.**
- *Problem.* The spine's must-cover item is "why adding one `randomize()` call can change later values". The before/after table and the rule to carry show `$urandom` ("draws a plain random number"), and rule 2 lists `std::randomize()` among process-RNG users, but nothing states the direct consequence: an extra `std::randomize()` (a "randomize call") or an extra `randcase` shifts every object and thread created after it in that process, unlike an extra `obj.randomize()`. A junior is unlikely to file `std::randomize()` under "a plain random number".
- *Fix.* Add one table row ("Insert one `std::randomize(n)` between `a` and `s`" → same/same/changes, rules 2 and 3) or reword the rule to carry: "…or draws from the process RNG (`$urandom`, `std::randomize()`, `randcase`, `randsequence`, `shuffle()`)…". Optionally mirror it in card 11.
- *Source checked.* §18.14.1, §18.14.2; spine card I-SV-2B must-cover; L12-2B-08.

**F5. S3 randomization-methods.mdx:373-382 - The debugging table has no `randsequence` row.**
- *Problem.* Checklist item 8 (debugging) for `randsequence` relies only on the pitfalls list (lines 245-248). The common symptoms, a stream that ends too early (a `break` where `return` was meant), a stream that continues after a terminal meant to end it (`return` instead of `break`), and a weighted alternative that never appears (its dynamic weight is always 0, or the weight sits on a production with no `|`), have no symptom → cause → fix row.
- *Fix.* Add two rows: "Stream stops after one production / continues past the end marker → `break` vs `return` swapped (§18.17.6)"; "An alternative never appears → its weight expression is 0 when selected, or the weight is on a production without `|` (§18.17.1)".
- *Source checked.* README §Concept completeness checklist item 8; §18.17.1, §18.17.6.
