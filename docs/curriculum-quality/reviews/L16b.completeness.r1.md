## Findings

### S3-1 Break it 3 has no answer, and its last case falls outside the trace table
- **Where:** `local-variables.mdx:568`; trace table `:538-547`.
- **Problem:** The learner is told to work out T1–T3 under `##1` "then check against the trace table". The table stops at edge 9, but T3's comparison under `##1` lands on edge 10 (`out_vld` 0, `out_data` X from unwritten `mem[4]`). The result there depends on an X comparison, which the page never teaches. Break it 1 gives a predicted log; Break it 3 gives none, so a junior cannot check their answer.
- **Fix:** Add an edge-10 row to the trace table (`out_vld` 0, `out_rdy` 0, `out_data` X). Add the predicted log in a `<details>`: the four `show_pair` lines are unchanged, because the call is attached to the goto and still runs on each handshake. Errors follow at 55, 85, 95 and 105 ns, then `[115] PASS=0 FAIL=4`. State in one line that `X == D4` gives X, which a concurrent assertion treats as false, so T3 fails.
- **Source:** my own trace of the bench; IEEE 1800-2023 §16.6 (an expression that evaluates to X or Z is false in an assertion; accuracy reviewer to confirm the clause wording).

### S3-2 The kata solution relies on an empty-repetition rule nobody teaches
- **Where:** `local-variables.mdx:787-794`.
- **Problem:** `(!hit)[*0:7] ##1 (hit && ok)` is described as placing the response "1 to 8 ticks after" the request. That is true only because, with zero repetitions, `empty ##1 s` is defined as `##0 s` (§16.9.2.1). Neither this page nor the index core path states that rule; the index only says `[*0]` "matches without consuming a tick" (`index.mdx:52`) and gives the `##0` case (`:107`). A junior reads `##1` as one more tick and gets 2 to 9 ticks, so the window, the "fails 8 ticks after the request" claim and task 3 all look wrong to them.
- **Fix:** Add one sentence after the code: "With zero repetitions, `##1` joins an empty match, which the standard defines as `##0` (§16.9.2.1). So the response may arrive on the first tick of the consequent, one tick after the request." Optionally add the 0-, 1- and 7-repetition cases as a three-row table.
- **Source:** IEEE 1800-2023 §16.9.2.1; `index.mdx:52`, `:107`.

### S4-1 Q3's key can be guessed from its length

### S4-2 Card 8 names abort conditions, but the page body never does
- **Where:** deck `isv4b-lv-8`; rules table `local-variables.mdx:307`.
- **Problem:** The card says a local variable may not appear in an abort condition (§16.12.14). The page states this only in the reference list (`:823`), not in the rules it teaches, so the card tests something the lesson does not teach (spine §5.6: no card goes beyond or contradicts the page).
- **Fix:** In the "Not in a disable condition" row, add "or an abort condition (`accept_on`, `reject_on` and their sync forms, §16.12.14)", with the same reason.
- **Source:** spine §5.6; IEEE 1800-2023 §16.12.14 (as cited by the author).
