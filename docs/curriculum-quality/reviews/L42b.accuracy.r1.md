## Findings

### 1. S2: `effective-debug.mdx:801-811` (quiz Q6), and `:220`

**Problem.** The Q6 stem uses the Make It Work bench: seed 42 fails at item 57, and the options use `uvm_test_top.env.drv`, `DRV` and `req.a`. The key says that `` `uvm_info("DRV", req.sprint(), UVM_HIGH) `` is the change "most likely to make it stop failing at item 57", because the printer's `new` changes "later random draws in that thread".

On this bench that cannot happen:
- `add_driver::run_phase` makes no random draws.
- Every item is created and randomized in `add_seq::body`. `start_item` calls `set_item_context`, which calls `reseed()` (uvm-core `uvm_sequence_base.svh:1066`, `uvm_sequence_item.svh:143`). Each item's RNG is therefore set from its type, its full name and a per-name count, and nothing in the driver's thread reaches it.
- `add_item` has no `do_print` and no field macros, so `sprint()` runs only uvm-core printer code. Its only effect is to create printer elements in the driver's thread.

None of the four options can move item 57. The page's own Expert 1 (`:695`, "limited to later draws in the same component's same phase call") and the Q9 explanation say the same thing. The item therefore teaches the over-broad form of the DBG-02 misconception: that a debug print in one component shifts stimulus another component's sequence generates. That is the scope the verifier corrected.

The key is the "least wrong" option, because it is the only edit that §1.4.6 does not guarantee to be stable. But the outcome the stem asks about is false.

The predict table row at `:220` answers "**maybe not**" for the same edit, in a table whose rows (`:219`) refer to this bench's `DRV` and `req.a`. On this bench the stimulus is unchanged.

**Fix.** Choose one:
- Make the premise explicit, for example: "the driver also waits a random idle gap (`$urandom_range(0,3)` clocks) after each item, and the failure depends on the gap." The question then asks which edit can change those gaps. The feedback says that the items keep their values (uvm-core reseeds started items by name) while the driver's own later draws move.
- Reword the stem to ask which edit is *not guaranteed* to be stream-neutral (§1.4.6), without claiming that item 57 changes.

At `:220`, add: "only that driver's later draws (for example random delays) move; items randomized in a sequence after `start_item` are reseeded by name (uvm-core), so on this bench the stimulus is unchanged." Optionally, qualify the "Debugging the method itself" row at `:294` the same way: the vanishing failure must depend on draws in the thread that runs the message.

**Sources.** 1800.2 §1.4.6, §14.1.2.2, F.4.1.4.26; uvm-core `uvm_sequence_base.svh:1066`, `uvm_sequence_item.svh:127-143`, `uvm_object.svh:813-819`, `uvm_misc.svh:189-219`, `uvm_printer.svh:1144-1150`; IEEE 1800-2023 §18.14.1, §18.14.3.

### 2. S3: `effective-debug.mdx:513`, `:528-529`, `:599`, and the run 1 and run 3 expected logs

**Problem.** The bench passes `20ns` to `set_drain_time` and `1ms` to `set_timeout` from a package compiled under `` `timescale 1ns/1ps ``. These arrive as `time` values 20 and 1,000,000, and uvm-core applies them as delays inside `uvm_pkg` (the drain through `` `uvm_delay `` in `uvm_objection.svh`). 1800.2 §1.4.5 says UVM requires no specific time unit for `uvm_pkg`.

If `uvm_pkg` is compiled with a 1 ps unit:
- the drain becomes 20 ps, so the last item's check at 4005 ns is never made: run 1 would show 199 compares, and run 3 `mismatches=2`;
- the timeout becomes 1 µs, so run 1 would end in `PH_TIMEOUT` at 1000 ns, before item 57.

The comment "Two clocks of drain let the monitor deliver the last result" holds only when `uvm_pkg`'s unit is 1 ns. The page already says, at `:231`, that UVM's time unit is tool-dependent, but the bench relies on it silently.

**Fix.** In "Run it" (`:568`), add one sentence: compile `uvm_pkg` with the same 1 ns time unit (put `uvm_pkg` after the `` `timescale `` in one compilation unit, or use the simulator's default-timescale option), because drain and timeout values are delays in `uvm_pkg`'s time unit (1800.2 §1.4.5). Alternatively, end the test without depending on time units: wait until the scoreboard has seen `n_items` results before dropping the objection.

**Sources.** 1800.2 §1.4.5, §10.5.1.3.7, F.7.3.3; uvm-core `uvm_objection.svh` (drain delay); IEEE 1800-2023 §3.14.2.3.

### 3. S3: `effective-debug.mdx:780-788` (quiz Q4)

**Problem.** The stem's paths are `uvm_test_top.env.agt0.sqr` and so on: 16 agents with numbered instance names. The key says that replacing the ID with `{PATH}` "and normalize the path indices" merges the 16 buckets into one.

The page's rule 2 (`:115`) and the sketch (`:141`) normalize only bracketed array indices (`agt[3]` becomes `agt[N]`). The reporter path stays in the signature, so `agt0` … `agt15` stay distinct and the taught rules give 16 buckets. I ran the sketch on `agt0`, `agt1` and `agt15` logs and got three separate buckets.

**Fix.** Use `agt[0]` … `agt[15]` in the stem. Or extend rule 2 and the sketch to numbered instance names, for example `re.sub(r"(?<=[A-Za-z_])\d+(?=\.|$)", "N", path)` applied to each path segment, and say so in the key. Card `e-dbg-1-ed-5` is worded generally and is correct for array-indexed agents, so it needs no change unless the rule is extended.

**Sources.** The page's own rules (`:114-117`, `:141`); the sketch, executed.
