## Findings

### S2

**F1, S2. advanced-constraints.mdx:480-492, 544, 555, 560: the DMA bench's "exact" PASS line rests on a size-step partition the LRM does not define.**
- **Problem.** `c_mode` ties `n_chunks` to `mode`, and through `if (mode == COPY) total inside {[64:256]}` also to `total`. None of these constraints references array elements.
  - §18.5.7.1 says only that "the size constraints are solved first and the iterative constraints next". It does not say which other variables join that first step.
  - Suppose a solver puts every non-element constraint connected to the size into the first step. Then it can pick `n_chunks = 1, mode = COPY, total = 200`, or `FILL` with `total = 900`, before it sees `chunk[i] <= 64`. That call fails and `$fatal` fires.
  - The page asserts that only "the `PASS=1000 FAIL=0` line is exact" and that "neither implicit order can strand the solver". It also tells learners to "Accept the run when the last line is `PASS=1000 FAIL=0` on every seed".
  - This contradicts the page's own kata debrief (:883), which correctly says "tools may partition that step differently".
- **Fix.** Keep `total` out of the size step by stating the COPY range on the reduction:
  - Write `if (mode == COPY) chunk.sum() with (int'(item)) inside {[64:256]};` and keep `c_total` as is.
  - Now only `mode` can join `n_chunks` in step 1. Every `(n_chunks, mode)` pair is feasible for every `width`: n = 1 with COPY gives chunk = 64, which every unit divides.
  - The PASS line is then exact under any partition. The `legal()` check needs no change.
  - Alternatively, qualify the claim the way the kata does. That is weaker, because the acceptance criterion would no longer be guaranteed.
- **Source.** IEEE 1800-2023 §18.5.7.1, §18.5.7.2, §18.5.11; the page's own :883.

### S3

**F2, S3. advanced-constraints.mdx:606 (and IQP 1, :643): the "practical signature" of an implicit order is overstated.**
- **Problem.** The page says "a failure rate between 0 % and 100 % with no `soft` constraint involved" identifies an implicit order. Two things are wrong with that:
  - Intermittent failures with identical constraint code also come from state variables that change between calls: configuration knobs, a `busy_ids` queue like the one this page recommends at :280, or values left by a previous call. Per-call inline `with` constraints do the same.
  - Soft constraints never cause failures (§18.5.13), so "no `soft` constraint involved" does not discriminate between causes.
- **Fix.** Write: "with the same constraints and the same state-variable values on every call (no changing knobs, busy lists or inline `with`)". Drop the `soft` clause. In IQP 1's stem, add "and no state variable or inline constraint changes between calls".
- **Source.** §18.5.8 step c (state variables used as constants); §18.5.13; §18.7.

### S4

**F3, S4. advanced-constraints.mdx:325: the "Guard evaluates to" column says ERROR for the unguarded `v < next.v;`.**
- **Problem.** That row has no guard. The constraint itself hits an evaluation error (the SList "will fail on the last element" text in §18.5.12).
- **Fix.** Write "(no guard) evaluation error" in that cell.
- **Source.** §18.5.12.

**F4, S4. advanced-constraints.mdx:788-789, 817, 821: the kata names a class property `size` next to `data.size()`.**
- **Problem.** The code is legal. However, L12-2B-43 and spine §5.2 #5 ask to avoid a `size` property beside an array's `size()`, and the author log reports -43 as fully resolved.
- **Fix.** Rename the property to `bsize` or `beat_size` in the table, the rules, the solution and `legal()`.
- **Source.** analysis L12-2B-43; spine §5.2 #5.

**F5, S4. advanced-constraints.mdx:92: "Writing `=` instead of `==`… assignments… are not allowed in constraints (§18.5)".**
- **Problem.** §18.5 names only `++` and `--` as examples. A bare `a = b` in a constraint is not an expression statement, so the usual result is a syntax error.
- **Fix.** "…`=` is not an expression here, so the compiler rejects it; operators with side effects such as `++` and `--` are not allowed either (§18.5)."
- **Source.** §18.5 restrictions; Syntax 18-2.

**F6, S4. advanced-constraints.mdx:581: "Compare the group size with 2 to the power of the width" is too coarse.**
- **Problem.** When members are also limited by `inside` or ranges, the pigeonhole bound is the number of values the members may still take, not 2^width.
- **Fix.** "Compare the group size with the number of values each member can still take (2^width when unconstrained)."
- **Source.** §18.5.4.
