## Findings

### F1. S3: the order of the prediction steps contradicts the debrief

- **Where:** `index.mdx:155` and `index.mdx:171-177`.
- **Problem:** The page says to "try each of these": `set_recording_enabled(1)`, then "config_db in run_phase", then "no record code", then clearing "The driver calls end_tr". The explorer keeps every control's state between clicks.
  - A learner who follows the list in order still has "config_db in run_phase" selected when choosing "no record code". The explorer then shows **nothing**, but debrief item 3 says "three boxes with times but no fields".
  - Clearing end_tr next also shows nothing, but debrief item 4 says "three boxes that never close".
  - The debrief also lists the outcomes in a different order from the steps; item 5 is the `set_recording_enabled(1)` case.
- **Fix:** Give each step the state it needs, and order the debrief the same way. For example: "(1) default; (2) choose `set_recording_enabled(1)`; (3) choose 'config_db in run_phase'; (4) go back to `set_recording_enabled(1)` and choose 'no record code'; (5) choose `do_record()` again and clear 'The driver calls end_tr'." Then reorder the `<ol>` to match: default, enabled (rdata appears), run_phase, no record code, no end_tr.
- **Source checked:** `src/components/visuals/TransactionRecordingVisualizer.tsx:129` (`update` merges a patch into the existing setup); `src/lib/uvm-recording-model.ts:126-150` (when not enabled, nothing is pushed whatever `impl` or `callEndTr` is).

### F3. S3: the architecture diagram draws the error and event records inside the `mon_item` recorder

- **Where:** `index.mdx:78`.
- **Problem:** Node `r_mon` is labelled "recorder: mon_item" with the sublabel "plus Error, Event records". That reads as if the Error and Event records live inside the `mon_item` record. They are separate, zero-length recorders on stream `mon`, with their own handles: TXH:4 for `reset_released` and TXH:13 for `parity_error` in the excerpt at lines 540 and 561, against TXH:7 for `mon_item`. Since the diagram's stated job is "one recorder per transaction", this is a wrong picture of that one point.
- **Fix:** Either option works.
  - Change the sublabel to "one per transfer" and add a caption sentence: "Error and event records are separate zero-length recorders on the same stream."
  - Or give the container `rowSpan: 3` and add a node in the `mon` column: `{ id: "r_err", label: "recorder: parity_error", sublabel: "type Error, zero length", kind: "generic", col: 2, row: 3 }`, with a structural edge `s_mon → r_err`. This also needs re-running the layout.
- **Source checked:** the page's own excerpt (lines 540-543, 553, 561-568); IEEE 1800.2 §13.1.7.7 and §13.1.7.8 as the page quotes them; uvm-core `uvm_component.svh` `record_error_tr`/`record_event_tr`, which open their own recorder.

### F4. S3: the default legend labels the parent/child link "causal"

- **Where:** `index.mdx:87`, with the diagram's default legend.
- **Problem:** The parent/child link is drawn with edge style `causal`. Because edges exist, the kit shows its default legend, "- - causal / call order". The page itself contrasts `uvm_parent_child_link` with `uvm_cause_effect_link` (lines 61 and 650; the text database drops cause/effect links). A legend that calls the parent/child arrow "causal" invites exactly that confusion. The caption does say "the dashed arrow is a parent/child link", but it disagrees with the legend printed just above it. The legend also lists port glyphs (■ ○ ● ◆) that the diagram does not use.
- **Fix:** Add `legend={false}` to the `<ArchitectureDiagram>`; the prop exists in `DiagramKit.tsx:40`, and no ports are used. Keep the caption's explanation of the dashed arrow. Optionally, label the edge "parent/child link".
- **Source checked:** `src/components/visual-system/BlockDiagram.tsx:123-128, 408-416`; `src/components/mdx/DiagramKit.tsx:38-57`.

### F5. S4: the sequence diagram is titled for `item0` but shows the order of a later item

- **Where:** `index.mdx:193-220`.
- **Problem:** The diagram names `item0` (message 9) but draws `get_next_item(req)` before `start_item(req)`. In the Make It Work run:
  - `item0`'s `start_item` is called at 0 ns and blocks;
  - the driver's first `get_next_item` comes at 22 ns, after it waits for reset;
  - the grant follows that request.
  
  The order drawn is the one for item1 and item2, where the driver asks again straight after `item_done`. The recording semantics are unaffected, and the note "granted…" is correct.
- **Fix:** Either option works.
  - Move `start_item(req)` above `get_next_item`, with the note "start_item blocks until the driver asks for an item".
  - Or keep the order and change "item0" to "item1" in message 9 and the caption.
- **Source checked:** the Make It Work code (lines 336-346, 366-370, 507-510); uvm-core `uvm_sequence_base.svh:1077`.

### F8. S4: a kit-level readability note at 390 px (for the lead)

- **Where:** `index.mdx:65-89`.
- **Problem:** The architecture grid is 634 px wide, and `ArchitectureDiagram` passes `minWidth = min(width, 360)`. At a 390 px viewport the SVG is therefore scaled to about 0.55. The 11.5 px labels and 9.5 px sublabels render at roughly 6 px and 5 px. This is kit behaviour, not the author's.
- **Fix:** Lead option: raise `minWidth` for grids of three or more columns so the figure scrolls horizontally instead (its wrapper already has `overflow-x-auto`). Or the author could set `cellWidth={130}` to shrink the grid, but the labels may then need re-checking.
