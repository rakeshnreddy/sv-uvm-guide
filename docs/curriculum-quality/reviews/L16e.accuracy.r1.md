## Findings

### S3

1. **S3 `content/curriculum/labs/assertions/README.md:177` (Hint 4): the remedy contradicts the symptom and the LRM.** Hint 4 says that if "both covers stay at 0", the cause may be covering an implication instead of a sequence. But the pass statement of `cover property` "shall be executed once for each successful evaluation attempt" (§16.14.3), and vacuous successes count as successes unless `$assertvacuousoff` is used (§20.11 VacuousOff). An implication therefore drives the counter *up*, on every idle edge, and never holds it at 0. README:112 and `solution/hs_slice_sva.sv:93-94` say exactly that. Fix: keep only the missing-increment cause under "stay at 0", and move the implication point to a separate hint, for example "**c_stall_then_ready counts far more than 1.** You covered an implication; it succeeds vacuously on every edge without a stall. Cover the sequence `(out_valid && !out_ready) ##1 (out_valid && out_ready)`." (Source: IEEE 1800-2023 §16.14.3, §20.11.)
2. **S3 (cross-scope, already lead request 3) `content/curriculum/T2_Intermediate/I-SV-4B_Advanced_Temporal_Logic/index.mdx:717` and `local-variables.mdx:814`: both describe `assertions-1` as a pipeline data-integrity lab with local variables.** After this rewrite that is false: the lab is a one-word valid/ready slice with no local variables. These pages are outside L16e's scope. Fix: L16a/L16b reword the sentences to "a local-variable pipeline lab is planned" with no id, or drop them. If 4B gets its own lab, give it a new id. (Source: the rewritten `lab.json` and README.)
3. **S3 (lead request 1) `src/generated/lab-registry.ts:170-…` is stale.** It still holds the old title, the old description and the deleted `lab1_data_integrity/*` asset paths. Anything that renders this lab's assets from the registry would point at files that no longer exist. Fix: run `node scripts/generate-lab-registry.mjs` before merge. (Source: grep of the registry; `git status` shows the deletions.)
