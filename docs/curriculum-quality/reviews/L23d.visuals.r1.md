## Findings

### F1 (S3) No picture for selection versus arbitration
- **Where:** `sequence-libraries.mdx:235-246` ("Libraries and arbitration").
- **Problem:** The page title, which is e2e-pinned, names arbitration, and the analysis lists "selection = arbitration" as a library misconception, but the two-layer distinction (library picks the next member internally; the sequencer arbitrates between the current member and other sequences) is told in bullets only. The start diagram's note "priority is the library's" covers priority inheritance, not the competition at the sequencer.
- **Fix:** Add a small `<SequenceDiagram>` or `<ArchitectureDiagram>`: `lib` (with a "selection_mode picks wr_seq:3" self/note) and a `bg_seq` both sending `start_item` to `agt.sqr`, a note at the sequencer "arbitration (FIFO / WEIGHTED) grants one", and a caption that says neither setting affects the other. Optional for this round; not a blocker.
- **Source checked:** plan §4 item 6; the author log "Pictures" table (row "libraries and arbitration: text + code").

### F2 (S4) Reading prompt says "dashed arrows" for a solid arrow
- **Where:** `sequence-libraries.mdx:93`.
- **Problem:** "Follow the dashed arrows from the members to the static list, from the static list into one library object, and from there to the sequencer." The last arrow, `lib` → `sqr`, has `style: "data"`, which the kit draws solid with a filled head (`BlockDiagram.tsx` `edgeStyleProps.data`), and `drv` → `sqr` is dotted (`control`).
- **Fix:** "Follow the dashed arrows from the members to the static list and from the static list into one library object, then the solid arrow to the sequencer."
- **Source checked:** `src/components/visual-system/BlockDiagram.tsx` lines 124-129.

### F3 (S4) `lib.sequences` node carries the SEQ role tag
- **Where:** `sequence-libraries.mdx:103`.
- **Problem:** The node labelled `lib.sequences` (a queue of type handles) has `kind: "sequence"`, so the kit prints the tag "SEQ" next to it, which reads as "this is a sequence object" right after the text stresses that the list holds types, not objects.
- **Fix:** Either label the node as the object, `label: "lib (mem_seq_lib)"`, `sublabel: "sequences[$]: this object's copy; add_sequence() edits only this"`, keeping `kind: "sequence"`; or keep the label and use `kind: "generic"` like the static-list node.
- **Source checked:** `BlockDiagram.tsx` `nodeKindTags` (lines 26-43); page text lines 35 and 118.

### F4 (S4) `finish_item` return omitted in the start diagram
- **Where:** `sequence-libraries.mdx:180-183`.
- **Problem:** After `item_done()` the diagram goes straight to "member start() returns"; the step in which `finish_item` returns to the member (and the member's `body()` ends) is implicit.
- **Fix:** Insert `{ kind: "return", from: "sqr", to: "mem", label: "finish_item returns" }` after the `item_done()` message. Labels still fit (22-character limit for adjacent lifelines).
- **Source checked:** uvm-core 2020.3.1 `uvm_sequence_base.svh` `finish_item`/`wait_for_item_done`; the Make It Work member `body()`s (lines 393-399).
