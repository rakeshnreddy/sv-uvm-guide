## Findings

### S3-1: UVMC converter rule is overstated for the SystemVerilog side
- **Where:** index.mdx:217.
- **Problem:** "converters for the TLM generic payload are predefined; other transaction types need a converter class, the `CVRT` parameter." The UVMC README says the opposite for SV: "In SV, you do not need to specify a converter for transaction types that extend uvm_object and implement the do_pack and do_unpack methods." A learner would write SV converter classes that they do not need.
- **Fix:** "Converters for the generic payload are predefined. In SV, any `uvm_object` with `do_pack`/`do_unpack` uses the default converter; other types, and user types on the SystemC side, need a converter class (the `CVRT` parameter)."
- **Source:** UVMC 2.3.2 connections README.

### S3-2: UVMC "latest release" status omits the 2.3.3 release
- **Where:** index.mdx:214, :706 (and :273 and :575 say "2.3.x").
- **Problem:** The page dates the status to "2.3.2 (November 2019)" as the latest release whose notes were checked. Verification Academy also hosts a "UVM Connect 2.3.3 Kit", which "adds better support for the semantics of the TLM-2.0 base protocol and how it is used in the context of 4-phase transactions". The wording is technically hedged, but the dated status table and the checklist item ("latest checked release", :638) will teach 2.3.2 as current. The 2.3.3 change also bears on the page's non-blocking advice (:668).
- **Fix:** Add "a 2.3.3 kit (TLM-2.0 base-protocol and 4-phase improvements) is also posted on Verification Academy; its date and simulator list were not checked". Keep 2.3.2 as the release whose notes were read.
- **Source:** verificationacademy.com resource "UVM Connect 2.3.3 Kit"; UVMC 2.3.2 RELEASE_NOTES.

### S3-3: Quiz Q6 feedback reverses the UVM-ML OA and Accellera WG relationship; :224 overstates the time-0 failure mode
- **Where:** index.mdx:828, :224 and debug-challenge answer 2 (:943).
- **Problem (a):** The Q6 distractor feedback says "UVM-ML OA came out of an Accellera working group that is now inactive". Cadence 2018 §I says the library, developed by Cadence and AMD, "were the base for the Accellera UVM-ML Open Architecture (OA) working group". The library came first, so the feedback contradicts :221 and card 2.
- **Problem (b):** :224 says a time-0 `initial` connect "runs before the components exist and connects nothing". With the page's own form, `client.sock.get_full_name()`, at time 0 `client` is null, so the call is a null-handle dereference, not a silent no-op. No source documents a silent "connects nothing" outcome.
- **Fix (a):** "UVM-ML OA was the basis for an Accellera working group that is now inactive."
- **Fix (b):** "…runs before the components and sockets exist: the handle is null, or the socket is not yet registered, so the connection cannot be made (the exact failure is library- and tool-dependent)." Reword answer 2's symptom to match.
- **Source:** Cadence 2018 §I and §IV (Examples 4 and 7); IEEE 1800-2023 §8 (null handle access).

### S4-3: Paraphrase shown as a quotation
- **Where:** index.mdx:645.
- **Problem:** `UVM_TLM_ACCEPTED` means "no change on this call", in quotation marks. The LRM text is "The transaction has been accepted", plus §12.3.2's "ACCEPTED versus UPDATED" choice. The phrase is a paraphrase.
- **Fix:** Drop the quotation marks, or quote §12.3.3.2.
- **Source:** 1800.2-2020 §12.3.2, §12.3.3.2.

### S4-4: Run-time sub-phase span named inexactly
- **Where:** index.mdx:236, :835, :840.
- **Problem:** "`reset_phase` through `shutdown_phase`" / "from reset_phase to shutdown_phase". The UVM run-time schedule runs from `pre_reset_phase` to `post_shutdown_phase` (12 phases).
- **Fix:** "`pre_reset_phase` through `post_shutdown_phase`", or "the run-time phases (reset, configure, main, shutdown and their pre/post phases)".
- **Source:** IEEE 1800.2-2020 §9.8 (UVM run-time phases).

### S4-5: UVMC matching description leaves out hierarchical-name registration and the fatal severity
- **Where:** index.mdx:215-216, Q8 (:849, :851), debug answer 1 (:942).
- **Problem (a):** The README says UVMC registers the port's hierarchical name and the lookup string, and either can match. The page says only the lookup string is registered. Q8's distractor ("falls back to matching the ports' hierarchical names") is still wrong here, because the names differ, but its feedback implies hierarchical names never take part.
- **Problem (b):** The README also says an unmatched connection "will produce a fatal error". The page says "an error".
- **Fix:** At :215, add "(the port's hierarchical name is registered too, but SV and SC paths rarely match, so use a lookup string)". Change "error" to "fatal error per the UVMC docs; exact text library-dependent". Adjust Q8 option 0's feedback to "Hierarchical names are registered too, but here they differ, and so do the lookup strings."
- **Source:** UVMC 2.3.2 connections README.

### S4-6: Kata step 3 says "only connect_phase changes", but build changes too
- **Where:** index.mdx:916.
- **Problem:** "Only `mlx_env::connect_phase` changes … and `ref_mem_target` is no longer created". Not creating the target is a `build_phase` change.
- **Fix:** "Only `mlx_env` changes on the SV side: `connect_phase` calls `uvmc_tlm #()::connect(...)`, and `build_phase` no longer creates `ref_mem_target`."
- **Source:** the page's own bench (:479-487).
