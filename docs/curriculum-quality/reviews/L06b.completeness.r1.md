## Findings

### S2-1 · `index.mdx:49` (also :19, :51, :76, :161-:162, :197-:198, :293; deck f3b-5, f3b-8) — "checker" is never defined and means something else in earlier lessons

- **Problem.** The page says "blocking statements in checkers" run in Reactive and that `<=` from "program and checker code" lands in Re-NBA (Recap :293). It never says this means the IEEE `checker … endchecker` construct (Clause 17). Earlier lessons define "checker" the other way: F1B :32 defines a checker as "code that compares the DUT's actual output with the expected value" and explicitly says it is *not* the `checker` construct; F2E :19, :83 and :364 build "the checker" as a module `always @(posedge clk)` procedure. A junior who applies this page's rule to that checker predicts Reactive and Re-NBA for code that runs in the active set. The ambiguity teaches a wrong placement, and objective 2 tests placement.
- **Fix.** On first use (:49, or in a short primer before the region table) write: "Here **checker** means the SystemVerilog `checker … endchecker` construct for packaging assertions and modelling code (§17; [I-SV-4C](/curriculum/T2_Intermediate/I-SV-4C_Checkers/index)), not a testbench's checking code such as F2E's `always` checker, which is module code and runs in the active set." Then say "`checker` construct" or "`checker` code" at :19, :51, :76, :161-:162, :197-:198, :293, and in f3b-5 and f3b-8.
- **Source checked.** IEEE 1800-2023 §4.4.2.6, §17.7.3; F1B :32; F2E :19, :83, :364.

### S2-2 · `index.mdx:49`, :149, :191-:196, :273-:276, :332-:339 — the page never defines a program block, yet objective 5 and the worked example depend on it

- **Problem.** Program code appears in the region table (:49), the visualizer debrief (:149), the construct tables (:195-:196), the §24.4 argument (:273-:276) and the worked example's nested `program tb_prog` (:332). Show three lines (`program tb_prog; initial begin … end endprogram`). Link F4C.
- **Source checked.** IEEE 1800-2023 §24.3, §24.3.1; F2C :219; F3A :163; F4C :13.
