## Findings

### S2-1: hang-lab.mdx:160, the trace line for the test's drop is wrong

**Problem.** The `OBJTN_TRC` line for the drop reads:

`Object uvm_test_top dropped 1 run_objection objection(s) (stimulus done): count=0  total=0`

In uvm-core, `poll_seq`'s raise propagates up `sqr → agt → env → uvm_test_top`. So `m_total_count[uvm_test_top]` still holds `poll_seq`'s 1, plus `scb`'s 1 if a compare is in flight. `m_drop` subtracts the test's own count and then reports the remaining total. The real line therefore ends `count=0  total=1` (or `total=2`).

As printed, `total=0` says that nothing below the test holds the objection. That contradicts:
- the page's own reading rule at line 164 ("total includes its children");
- the family-1 point that the total never reaches zero.

A learner who trusts this line concludes that nobody holds the objection.

**Fix.**
- Print `count=0  total=1`.
- Add a sentence: the test's own count is 0, but its total stays at 1 or more, because `poll_seq` below it still holds the objection. That is the family-1 signature.

**Source.** uvm-core `uvm_objection.svh`: `m_raise` 380–400 (total incremented at every level), `m_propagate`, `m_drop` 650–656 (subtract, then `m_report`), `m_report` 191–206 (`_total = m_total_count[obj]`).

### S2-2: hang-lab.mdx:727–730 and :788 (also :169 and card 9), the `+HANG=1` hang dump omits a holder

**Problem.** The expected output for `+HANG=1` lists two "holds run_objection" lines, `poll_seq` and `scb`. Worked solution step 2 says "The dump names `poll_seq` and `scb`".

In uvm-core, `get_objectors()` pushes every key of `m_source_count`. A key whose count has fallen to 0 is deleted only in `m_forked_drop`, once the object's *total* reaches zero. The test dropped at about 500 ns, but its total never reaches zero, because `poll_seq` below it still holds. So `m_source_count[uvm_test_top]` stays at 0, and the dump also prints:

`holds run_objection: uvm_test_top`

A learner who runs the bench sees a third "holder" that the page says is not there. This happens in exactly the family the exercise teaches.

The page's description at :169 and card 9 ("every object whose count is still raised") matches §10.5.1.5.1 ("raised an objection, but have not dropped it"), but uvm-core does not behave that way.

**Fix.**
- In `hang_dump_catcher`, filter the holders: `if (run_ph.get_objection().get_objection_count(holders[i]) > 0)` (§10.5.1.5.3). The expected output and step 2 then become correct.
- Add one line at :169 (and in card 9): uvm-core's `get_objectors()` can also return an object whose own count has dropped to 0 while a descendant still holds, so check `get_objection_count()`.
- Alternative: keep the catcher as it is, add the `uvm_test_top` line to the expected output, and explain it in step 2.

**Source.** uvm-core `uvm_objection.svh` 1049–1056 (`get_objectors`), 886–893 (deletion only in `m_forked_drop`), 664–675 (no fork while total ≠ 0), 1133–1147 (`get_objection_count` returns the source count); 1800.2 §10.5.1.5.1, §10.5.1.5.3. The repo's own `uvm-hang-model.ts` "stuck-objection" feedback notes the same parent-with-count-0 effect for `display_objections()`.

### S3-2: hang-lab.mdx:952, quiz Q4 distractor 1 uses a port that has no minimum

**Problem.** The feedback says a minimum of one connection is "true for ports with a minimum size of 1, such as a driver's seq_item_port". In uvm-core, `uvm_seq_item_pull_port` defaults to `min_size=0` ("it can be left unconnected"), and `uvm_driver` builds `seq_item_port` with the defaults. So an unconnected `seq_item_port` raises no end-of-elaboration error either.

**Fix.** Use an example that does have a minimum of 1, such as a `uvm_blocking_get_port` (standard TLM ports default to `min_size=1`), or drop the example.

**Source.** uvm-core `uvm_sqr_connections.svh:50`, `uvm_tlm_imps.svh:202` (`int min_size=0`), `uvm_driver.svh:94`, `uvm_ports.svh:89` (`min_size=1`).
