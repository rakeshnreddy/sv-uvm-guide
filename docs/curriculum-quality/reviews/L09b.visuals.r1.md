## Findings

### S2-1. The sequence diagram clips its root-class steps (constructors.mdx:151-152)

- **Problem.** Two self-messages sit on `base_item::new`, the rightmost lifeline:
  - "root class: id and name get default values";
  - "body: count++, id = count, name = \"pkt0\"".
  
  `layoutSequence` puts the lifeline at x = 565 in a 650-wide viewBox. Self-message text starts at x + 42 = 607 and wraps at 24 characters, so each line is about 19–23 monospace characters (about 120–145 px at 10.5 px). The lines therefore end at about x = 740–770, past the viewBox. An inline `<svg>` has `overflow: hidden`, so only about 40 px of each label is drawn: roughly "4. ro" and "5. bo".
  
  These two steps are what the debrief at :163 asks the learner to read ("Work happens only on the way back up, one whole class at a time, root first"), and :262 names this diagram as *the* picture of chaining. On every viewport, the drawing hides the step that proves the base runs completely first. The kit's width (`SEQ_PAD_X*2 + SEQ_BOX_W + (n-1)*colW`) leaves no room for self labels on the last lifeline.
- **Fix (author, in scope).** Change the six initializer and body steps (:151, :152, :154, :155, :157, :158) from `kind: "self"` to `kind: "note"` with the same `from`. A note is drawn inside the lifeline's own column: for `base` it spans x ≈ 506–624, wraps at about 16 characters on up to 4 lines, and fits the viewBox. This also fixes S3-1. Re-check by running the messages through `layoutSequence`, or by viewing the page at 390 px and at desktop width.
- **Optional lead item (kit).** `layoutSequence` should widen `width` when a self-message sits on the last lifeline (about +170 px), or wrap self labels to the space left. The kit's own doc example (`visual-language.md` §9, `drv` self-call on the last lifeline) has the same latent clip.
- **Sources checked.** `src/components/visual-system/diagram-layout.ts:270-331` (lifeline x, `wrapLabel(m.label, 24, 3)`, width formula); `SequenceDiagram.tsx` (self text at `x + 42`, `viewBox 0 0 ${width}`); computed layout output (base lifeline x = 565, width = 650, no problems).

### S3-1. The text alternative calls initializers and bodies "self-calls" (constructors.mdx:151-158)

- **Problem.** The "Steps as text" list, which is the accessible equivalent, renders each self-message as "<participant> calls itself: …". The page's diagram therefore reads:
  - "4. base_item::new calls itself: root class: id and name get default values";
  - "7. bus_item::new calls itself: initializer: addr = 32'h100".
  
  A screen-reader learner hears that the constructor calls itself, a recursion that does not happen. The drawn self-loop arrows suggest a method call in the same way. Initializers and the rest of the body are not calls.
- **Fix.** The S2-1 fix: `kind: "note"` renders as "Note over base_item::new: …" and draws a box, not an arrow.
- **Source checked.** `diagram-layout.ts:314` (`text: \`${step}. ${nameOf(m.from)} calls itself: ${m.label}\``).

### S4-1. The page cites a `this.name = name;` pattern that the diagram does not show (constructors.mdx:197 and :152)

- **Problem.** :197 says "every `this.name = name;` in the sequence diagram is the same pattern", but the diagram's label is `name = "pkt0"`. The label also leaves out that `base_item::new` prints its line, which is the first line of the Make It Work log (:347).
- **Fix.** Relabel the base body step "body: count++, id = count, this.name = name (\"pkt0\"), prints", or reword :197 to "the `this.name = name;` in `base_item::new`".
- **Source checked.** Make It Work code, :343-348.
