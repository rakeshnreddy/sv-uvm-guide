## Findings

### S3-1: Objective 2's "write" is never produced by the learner
- **Where:** `index.mdx:25` (objective 2) and `index.mdx:1329-1334` (kata tasks)
- **Problem:** Objective 2 asks the learner to write a requester driver, a monitor and the protocol assertions. The page shows complete code for all three in Make It Work, which §5.4 accepts as exercise. But in the kata the learner writes a completer, a sequence and a subscriber. They mutate the driver; they never write a driver change, monitor logic or an assertion themselves. The quiz tests only the debug half of the objective (Q6, Q7).
- **Fix:** Add one small production task to the kata, with its solution in the `<details>` block. Either of these would do:
  - "write the read-direction counterpart of `a_resp_known`";
  - "write an assertion that `PWDATA` is stable on write wait states only, and say why `a_wait_hold` already implies it".
  - Better still: "turn `apb_driver` into the zero-idle driver from Push Further and show `c_back_to_back` is hit". This exercises the driver.
- **Source checked:** spine §5.4 (coverage); spine card objective 2; README depth ladder (the practitioner layer needs a complete worked example the learner can reproduce).

### S3-2: The APB4 `PSTRB` sparse write has no picture
- **Where:** `index.mdx:158-164`
- **Problem:** `PSTRB` and sparse writes are a core concept for objectives 3 and 4. They are explained only in prose and tables. The sparse write appears just as a log line (`Expected output`, line 1050) and in a prose trace (line 1073). The README requires a waveform, a diagram or a traced example for every core concept. The kit TimingDiagram used elsewhere would show it well: the write of `AAAABBBB` with `PSTRB 0011` to `DATA`, then the register value per byte lane.
- **Fix:** Add a short TimingDiagram, or a byte-lane table traced from the worked example, to the APB4 section. Show `PSTRB = 0011`, `PWDATA = AAAABBBB`, `DATA` before (`12345678`) and after (`1234BBBB`). Ask a predict question first ("which bytes change?") and debrief after. Link it from the adapter's `bus2reg()` decision 2.
- **Source checked:** README §Visuals ("every core concept has a picture"); plan §1.2.
