## New findings

### 1. S3: `effective-debug.mdx:594` (and the run 1 and run 3 expected logs at `:602-623`, `:675-685`)

**Problem.** "Run it" says that UVM "prints `@ time`, in that unit" (the unit of `uvm_pkg`), and that with a 1 ps unit "the logs below would print times in ps". That implies that with a 1 ns unit they print ns, as in the logs (`@ 1165`, `@ 4015`, `@ 45`).

uvm-core does not work that way. It builds the field with `$swrite(time_str, "%0t", $realtime)` (`uvm_report_server.svh:891`). `%t` reports in the `$timeformat` units, and by default those are "the smallest time precision argument of all the `` `timescale `` compiler directives" (IEEE 1800-2023 §20.4.3, Table 20-3). This file's `` `timescale 1ns/1ps `` makes that 1 ps or finer, whatever the unit of `uvm_pkg`. On the bench as written, a conforming simulator therefore prints `@ 1165000`, not `@ 1165`.

The logs are labelled illustrative and say "your simulator's times may be printed in another unit" (`:600`, `:673`), so a learner is warned. But the stated mechanism is wrong, and it points the learner at the wrong knob.

**Fix.** Use one of these:
- Add `$timeformat(-9, 0, "", 0);` as the first statement of `tb_top`'s `initial` block, so the logs really print ns. Then reword: "UVM prints `@ time` with `%0t`, which uses the `$timeformat` units: by default the smallest time precision in the design (1 ps here; IEEE 1800-2023 §20.4.3), so `tb_top` sets ns."
- Or keep the code and change the sentence to: "UVM applies time values passed to it, such as the `set_timeout(1ms)` argument, in the time unit of `uvm_pkg`. It prints `@ time` with `%t`, whose default unit is the smallest time precision in the design (1 ps with this file), so a simulator may print 1165000 where the logs below show 1165 ns."

**Source checked.** uvm-core `uvm_report_server.svh:820,891`; IEEE 1800-2023 §20.4.3, Table 20-3, and §3.14.3; IEEE 1800.2-2020 §1.4.5.

### 2. S4: `effective-debug.mdx:748` (Interview angle 1, feedback on option B)

**Problem.** "A UVM message does not change simulation time or process order in a way that fixes races" is too strong. IEEE 1800-2023 §4.7 leaves the execution order of processes in one region to the implementation. A rebuild that adds statements can change which order a simulator picks, so print-sensitive races ("Heisenbugs") do happen. The option is still wrong for the right reason: nothing shows a race yet, and the archived build must be rerun first.

**Fix.** Write: "Possible in principle (a rebuild can change the order a simulator runs racing processes, IEEE 1800-2023 §4.7), but nothing points to a race yet, and a moved stimulus is more likely. Rerun the archived build before forming any hypothesis."

**Source checked.** IEEE 1800-2023 §4.7, §4.8.
