## Findings

### S2

**F1. S2 · index.mdx:357–361, 664–674, 810–829, 1093–1114, 1208–1259 · Objective 3 is only partly exercised: the override and callback mechanisms are never run, and the page gives no way to account for errors whose count is random.**

The page has three gaps here:
- **The two mechanisms are never run.** The table recommends the factory override for "random error density across existing tests, with no sequence edits" and the callback for "every Nth request". `mem_err_item` and `mem_par_flip_cb` are defined, but no test uses them, and there is no log for either.
- **The catcher cannot serve them.** The only accounting scheme on the page is `mem_err_catcher.expected = N_INJECT`, a constant known before the run. With density injection the count is random. The catcher would demote the first `expected` reports and THROW the rest, and the run would fail on a correct DUT. Nothing tells the learner how to account in that case.
- **The override silently does nothing in the directed sequences.** `mem_wr_rd_seq::send()` (:693–702) creates the item through the factory but never calls `randomize()`; it sets `par_err` and `par` by hand. So the override injects nothing in `mem_smoke_test`. The claim "across existing tests, with no sequence edits" holds only for sequences that randomize, such as `mem_rand_seq`.

Objective 3 reads "Inject errors with an error sequence, a factory override and a driver callback, and **account** for the expected errors". Only the first mechanism is exercised with accounting. Q6 tests only the override's soft-constraint pitfall.

*Fix:*
- Add a short complete test, for example `mem_par_density_test extends mem_reset_err_test` or `mem_smoke_test`, that runs `mem_rand_seq` with `mem_par_flip_cb` (or the `mem_err_item` override).
- Make the catcher's limit follow the injector's live count. For example, the catcher holds a handle to `flip` and demotes only while `n_demoted < flip.n_injected`. That works because `pre_drive()` increments before the monitor reports at the accept edge. Alternatively, leave the limit open and compare at `check_phase`.
- Make `check_phase` compare `flip.n_injected == catcher.n_demoted == sb.n_err_expected == sb.n_err_seen`, and show the expected `ERR_ACCOUNT` line.
- Add one sentence to the table row: the override affects only items that are randomized after creation (`mem_rand_seq`, not `mem_wr_rd_seq::send`).
- Optionally add a quiz item or a kata task on accounting for random-count injection.

*Source checked:* spine card objective 3; README "every objective must be exercised"; page code at the lines cited.

### S3

**F2. S3 · index.mdx:1485–1587 (quiz) · The key is guessable by length.**

In 8 of 9 questions the correct option is the longest, often by a wide margin: Q4 191 characters against at most 98; Q5 167 against 78; Q9 94 against 52; Q6 105 against 80. Q8 is the only exception. Spine §5.5 requires that the answer not be guessable. "Pick the longest" is a known test-wiseness cue, and it weakens retrieval practice. The two InterviewQuestionPlayground items show the same pattern.

*Fix:*
- Shorten the keys (move the "why" into `feedback`), or lengthen the distractors with plausible detail, so the correct option is the longest in no more than about a third of the items.
- Vary the key position too; today the keys sit at positions 2, 2, 3, 4, 1, 2, 2, 4, 3.

*Source:* spine §5.5; option lengths measured from the quiz block.

**F3. S3 · index.mdx:288–351, 1133–1152 · `kill()` has no code form.**

The brief and objective 2 name `kill()` (§14.2.5.11) beside `stop_sequences()`. The page says when to prefer `kill()` (:351), and the expert item explains its internals (:1423). But no snippet shows the reset virtual sequence using `traffic.kill()`, so items 4 (syntax and variants) and 5 (worked example) of the completeness checklist are missing for this concept. A learner told to "`kill()` the sequences the scenario owns" never sees where the call goes, or that it can run at the 245 ns edge because it does not flush the request FIFO.

*Fix:* add a 6–8 line `// snippet` variant of `mem_reset_err_vseq::body()` that replaces `sqr.stop_sequences()` with `traffic.kill()`, with one comment on why the timing constraint differs. Optionally add a checklist line.

*Source:* IEEE 1800.2-2020 §14.2.5.11; page :351 and :1423.

**F4. S3 · index.mdx:145–177, 206–223 · Two driver variants a practitioner meets are not covered.**

- **Driver for an asynchronous reset.** The must-cover "asynchronous reset outside clocking blocks" is taught for the monitor and for assertions only. The driver shown is synchronous-only: it learns about reset at `@(vif.drv_cb)`. With a gated clock, it can sit at that edge through a whole reset and then see `rst_n` already released. Name what an async-reset driver does: watch `negedge rst_n` on the raw signal, abandon the item with `item_done()`, and idle the bus. One paragraph or a 10-line snippet next to the monitor's would complete the must-cover.
- **Pipelined driver, or a driver whose sequences use responses.** The page covers a single-item driver. A driver that holds several items (`get()` plus `put()`), or sequences that call `get_response()`, also need a rule on reset. For example: release or `put` an aborted response for every outstanding item, or rely on `kill()` and `stop_sequences()` to clear responses. One sentence and a debugging-table row would do.

*Source:* spine card must-cover; README completeness checklist item 4 (variants).
