## Findings

### A1. S3: `coverage-apis.mdx:523`, auto-bin overlap rule overgeneralized

- **Problem:** The page says "Two instances with different `auto_bin_max` have differently named bins, so nothing overlaps." This is false in general.
  - §19.5.3 sets N = MIN(2^M, `auto_bin_max`), and N is the enum cardinality for an enum coverpoint. Bins are named `auto[value]` or `auto[low:high]`.
  - So two instances of an enum coverpoint, or of an integral coverpoint whose `auto_bin_max` values are both ≥ 2^M, have identical bins that overlap completely. For example, `bit [7:0] a` with `auto_bin_max` 256 and 300.
  - Bin widths can also coincide on most bins when 2^M is not divisible by N, because the last bin takes the remainder. For example, with 8 bits, N = 100 and N = 120 both give width-2 bins `auto[0:1]` … up to the shorter set's last full bin.
  - Only the LRM's `ga` case (64 vs 32 on 8 bits) is guaranteed disjoint.
- **Fix:** "Automatic bins are named by their value range (§19.5.3), so bins overlap only where two instances produce the same range. In the §19.11.3 example (`auto_bin_max` 64 and 32 on an 8-bit coverpoint) no range coincides, so the type has 96 cumulative bins. An enum coverpoint, or any `auto_bin_max` at or above 2^M, gives every instance the same bins."
- **Source:** IEEE 1800-2023 §19.5.3, §19.11.3 (`ga` example).

### A2. S4: `coverage-apis.mdx:689` (Q6 explanation), also `:289` (rule 2), causal wording reversed

- **Problem:** The page says "run_test() prints the report summary only after the phases finish, so a $finish from a component skips the check and report phases." The phases are skipped because `$finish` exits at once (§20.2), not because of where `run_test()` prints the summary. The summary placement explains why no summary appears. Rule 2 at :289 has the same "because" link.
- **Fix:** "$finish exits at once (§20.2), so the extract, check and report phases never run; and since run_test() prints the report summary only after the phases finish, no summary prints either."
- **Source:** IEEE 1800-2023 §20.2; IEEE 1800.2-2020 §9.8.1; uvm-core 2020.3.1 `uvm_root.svh` (via L14.verify.md).

### A3. S4: `coverage-apis.mdx:206` and Q5 feedback at `:676`, per-instance scope of `stop()` stated as an LRM rule

- **Problem:** The page says "§19.8 does not make start() and stop() static, so lane0.cg.stop() acts on lane0's instance." The conclusion is almost certainly right. However, the LRM only says that `get_coverage()` is static and never states the scope of `start()`/`stop()`, so this is an inference.
- **Fix:** Add "(the LRM marks only get_coverage() as static; acting per instance is the natural reading and what tools do, so confirm on yours)". Alternatively, soften "acts on" to "is called on".
- **Source:** IEEE 1800-2023 §19.8, Table 19-5.
