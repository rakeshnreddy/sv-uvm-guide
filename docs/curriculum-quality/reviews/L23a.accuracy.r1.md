## Verified correct (no change needed)

- **Arbitration rules and the traced table.**
  - FIFO is the default and ignores priority (F.2.4.1; §15.3.2.18; `m_choose_next_request()` 687-688). STRICT_FIFO and STRICT_RANDOM behave as the page says.
  - WEIGHTED draws `$urandom_range(sum-1,0)` over the priorities, so 100/100/300 gives 20/20/60 % and Q3's 100/300 gives 25/75 %.
  - RANDOM ignores priority. There are six modes in total.
  - Root priority is 100 and a child takes its parent's (§14.2.3.1; `start()` 320-333).
- **Lock and grab.**
  - Row 6 and Q4 give a grab granted before the earlier waiting lock (`push_front` plus `grant_queued_locks()` choosing the first unblocked lock request; §14.2.5.6). This matches both readings.
  - Children are exempt in uvm-core (`is_blocked()`/`is_child()`).
  - `SEQFINERR` is raised on a normal finish while a lock is held (1264).
  - A virtual sequence must name the sequencer; §14.2.5.5 requires a fatal message otherwise.
- **Dispatch timing.** I traced rows A–D through `start()`, driver delays of 10 ns and 4 ns, and the one-slot request FIFO:
  - A: 10; 14, 18, 22; 32, 42.
  - B: 10; 14, 18, 22; 20, 30.
  - C: 10; 4, 8, 12; 22, 32, with two `ORDER` errors at 4 ns and 8 ns.
  - D: ends at 10 ns, and the drivers complete no further item.

  Q6's key (42 ns) and the Make It Work log match row B.
- **Break-it 2.** The phase kills the run-phase process tree (`uvm_phase_hopper.svh` 690; IEEE 1800-2023 §9.7). The process guards are forked from `run_test()` outside the phase (`uvm_root.svh` 507-512), so they survive, and each fires `SEQPRTZMB` for `vseq.data` and `vseq.thr` (`get_full_name()` through the parent). Both count errors follow.
- **Make It Work code.** It is legal and uses declared names throughout:
  - `req` is declared in `uvm_driver` and `uvm_sequence`.
  - `` `uvm_error ``/`` `uvm_fatal `` expand to `begin … end`, so the unbraced `if`/`else` is safe.
  - `timeunit` in a package and a module is legal.
  - `extends uvm_sequencer` and `extends uvm_sequence` use the default parameters.
  - `` `uvm_declare_p_sequencer `` declares `p_sequencer` and casts in `m_set_p_sequencer()`.
  - `vseq.start(null)` is a valid call.
  - The `RNTST` text matches `uvm_root.svh` 595.
- **Expert table rows.** Each row checks against the cited standard text and the uvm-core source:
  - `user_priority_arbitration` is skipped with a single candidate (713-714), although §15.3.2.3 says it is called "even if there is only one".
  - The response-queue error bit defaults to 0 (174 has no initializer; `put_base_response()` 1289-1298), while §14.2.7.4 and §14.2.7.5 make the error the default, with depth 8.
  - The library uses public `selection_mode`/`min_random_count`/`max_random_count` and has no `set_selection_mode()`. `init_sequence_library()` is documented as required in each subtype.
  - `kill()` skips `post_body`/`post_start` in uvm-core, against §14.2.5.11.
  - `uvm_virtual_sequencer` is a typedef.
  - `SEQPRTZMB`/`SEQBDYZMB` come from the process guards.
- **Ending a test with background stimulus.** `wait fork` waits for immediate children (§9.6.1). A `kill()` clears the guard through `clean_exit_sequence()`, so no `SEQPRTZMB` appears. The drain-time call has the right signature (§10.5.1.3.7), and the `forever` note in §14.2.4.4 is cited correctly.
- **Interview items, Q2–Q7 and Q9, and cards 1–10, 12, 13, 15 and 16.** All are correct.

## Re-run check (same round, same inputs)

The orchestrator asked for this review to be run again. `index.mdx` (mtime 00:53) and the deck (00:50) have not changed since the findings above were written. I re-checked the deciding evidence directly:

- **A1/A2 confirmed (S2).** uvm-core 2020.3.1 `uvm_sequencer.svh` 218-232: `get_next_item()` reports the error whenever `get_next_item_called == 1`, then calls `m_safe_select_item()`. In `uvm_sequencer_param_base.svh` 508-546, `sequence_item_requested` is still 1, so arbitration is skipped and `m_req_fifo.peek()` returns the same item. Only `item_done()` (315-336) clears both flags. A driver loop without `item_done()` therefore re-drives the same item and logs the error once per pass. It is never "one error, then silence". The sibling handshake page (:58, :212, :510, :635) teaches the repeating form, so index Q8, triage row :242 and card `iuvm3b-14` contradict it.
- **A3 confirmed (S3).** `m_lock_req()` pushes a lock to the back (1144-1146), and `grant_queued_locks()` (593-616) then grants the first unblocked `SEQ_TYPE_LOCK` request at once. In Q1's scenario (no lock held), `lock()` and `grab()` act the same in uvm-core. The key is still the better answer by §14.2.5.5.
- **Row 6 and Q4 confirmed correct.** A grab is `push_front`, a lock is `push_back`, and both are `SEQ_TYPE_LOCK`. On `unlock()`, `grant_queued_locks()` takes the first unblocked one, which is the grab.
- **A5 confirmed (S4).** In Annex F.2.4.3, `UVM_SEQ_LIB_ITEM` "Emits only items, no sequence execution", and §14.4.4 says "no sequences are executed".
- **A6 confirmed (S4).** §14.2.5.4 says a sequence that defines `is_relevant` "shall also supply a wait_for_relevant method".
- **Also confirmed:**
