## Findings

### S3

1. **`immediate-vs-concurrent.mdx:491` (and the lead sentence at `:462`).**
   - **Problem:** "Both resist glitches from the order of procedural execution and neither resists Reactive-to-Active loops (§16.4.1, §16.14.6.3)." That is false for the deferred column as the table defines it, which includes `final`. §16.4.1 says "Due to their execution in the non-iterative Postponed region, final deferred assertions are not vulnerable to the potential glitch behavior previously described for observed deferred assertions." It also contradicts the page itself (`:192`, `:467`, kata step 3). Line 462 has the same gap: "Deferral protects against glitches … but not against loops between regions (§16.4.1)" is true only of observed deferral.
   - **Fix:** At `:491`, write "Both resist glitches from the order of procedural execution. Against Reactive-to-Active loops, observed deferred reports and procedural assertion instances are not protected (§16.4.1, §16.14.6.3); final deferred reports are, because they mature in Postponed." At `:462`, write "Observed deferral protects … but not against loops between regions; final deferral does (§16.4.1)."
   - **Source:** IEEE 1800-2023 §16.4.1 (last paragraph), §16.14.6.3.

### S4

2. **`immediate-vs-concurrent.mdx:489`.**
   - **Problem:** In the procedural column, "The attempt runs to completion; `disable` no longer affects it (§16.14.6.4)". The `disable` half is right. "Runs to completion" is not: `$assertkill` aborts currently executing attempts (§20.11 Kill), and a `disable iff` can still disable it.
   - **Fix:** "`disable` no longer affects it (§16.14.6.4); `$assertkill` or the assertion's `disable iff` can still end it."
   - **Source:** §16.14.6.4; §20.11 (Kill); §16.12.

3. **`immediate-vs-concurrent.mdx:213`.**
   - **Problem:** "If the procedure has exactly one clean event control such as `@(posedge clk)`, the clock is inferred from it." This understates §16.14.6 a-c. The procedure must be `always` or `initial` (including `always_ff`), with no blocking timing control and exactly one event control. Exactly one event expression must qualify, and its signal must not be used elsewhere in the body (r3: `posedge reset` is not inferred because `reset` is referenced).
   - **Fix:** "If the procedure has no delays and exactly one event control, and the clock signal is not used elsewhere in its body, the clock is inferred from that event control (§16.14.6); the module overview gives the full rule." Optional: the page already links the overview's expert item.
   - **Source:** §16.14.6 requirements a-c, examples r2, r3, r4.

4. **`immediate-vs-concurrent.mdx:555`** (quiz Q1, first distractor feedback).
   - **Problem:** "simulators reject assert property in class methods" is stated as fact here. The page body labels it as tool behaviour (`:215`), and the LRM has no such rule: §16.6 forbids only non-static class properties and methods in the expressions.
   - **Fix:** Add "(tool behaviour)" after "class methods".
   - **Source:** §16.6; L15-4A-05 labelling requirement.

5. **`immediate-vs-concurrent.mdx:50`.**
   - **Problem:** "only concurrent assertions and clocking-block inputs read it [Preponed]" is too absolute. Sampled value functions (`$sampled`, `$past`, `$rose` and others) used in procedural code also return Preponed-based sampled values (§16.9.3), and checker `always_ff` variables are sampled too (§16.5.1).
   - **Fix:** "chiefly concurrent assertions, sampled-value functions such as `$sampled`, and clocking-block inputs read it."
   - **Source:** §16.5.1 (first paragraph), §16.9.3.

6. **`immediate-vs-concurrent.mdx:29`.**
   - **Problem:** "each procedure is one process". A `fork` inside a procedure creates further processes (§9.3.2), and flush points and report queues are per *process* (§16.4.1). The simplification could mislead a learner who puts deferred assertions inside forked branches.
   - **Fix:** "each procedure starts one process (a `fork` inside it starts more)."
   - **Source:** §9.3.2, §16.4.1.
