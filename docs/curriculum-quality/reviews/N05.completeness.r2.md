**C2-2. S3 · index.mdx:1511 (with :1172, :1181, :425, :1539–1542) · The page says how to account for errors injected by the factory override, but the catcher it ships cannot take that path, and no code shows it.**

The page says "a callback that only counts items with `par_err` set plays the role of `flip`". Two things block this:
- `mem_err_catcher.injector` is typed `mem_par_flip_cb` (:1172), so a separate counting callback cannot be assigned to it.
- `mem_par_flip_cb` counts only its own flips. It skips items whose `par_err` is already set (:897).

A learner who follows How-to step 9 for the override therefore has to redesign the catcher, with no example. The override is the one mechanism of objective 3 that is never run in a test. Q6 tests only its soft-constraint pitfall, which is enough for the "exercised" rule but leaves this gap. The override is also the only mechanism whose count is truly random (see C2-3).

*Fix (smallest):* make `mem_par_flip_cb` count every bad-parity item it drives:

```systemverilog
if (req.par_err) n_injected++;
else if (every != 0 && n_seen % every == 0) begin ... n_injected++; end
```

Add `flip.every = 0` as "count only". Then show a 6–8 line `mem_par_override_test extends mem_rand_test` that sets the `mem_err_item` override and attaches this counter with `catcher.injector = flip`, and add one sentence on its expected `ERR_ACCOUNT` line.

*Alternative:* give `mem_drv_cb` a virtual `n_injected()` and type `injector` as `mem_drv_cb`.

*Source:* spine card objective 3; README "every objective must be exercised"; page code at the lines cited.

**C2-3. S3 · index.mdx:1341–1343, 1494, 467, 1726 · The density example cannot show why a live count is needed, because its count is fixed.**

- The test says "the number of injected errors is known only as the run goes" (:1342).
- The catcher text says "when the number of injected errors is random, a fixed number cannot work" (:467).
- But `every = 8` with `num_items = 40` always injects exactly 5. Q7's own stem works this out ("every 8th of 40 random items, so 5 errors", :1726).

A junior will ask why not just set `expected = 5`. In Q7 the colleague's `expected = 4` then reads as an arithmetic slip, not as a flaw in the method. So the example does not motivate the technique objective 3 teaches.

*Fix (choose one):*
- Make the callback's injection random, for example `int unsigned pct = 12;` and `if ($urandom_range(99) < pct)`, so the count varies with the seed. Update the log to "injected=<k>", and reword Q7 to a seed where 5 were injected against a hand-set 4.
- Or keep `every = 8` and say plainly that the count is predictable here, but the live count stays right when `num_items`, `every`, a mid-run reset or a random mechanism (the override, C2-2) changes it. Then remove "known only as the run goes".

*Source:* page code :783, :888, :1357; spine card objective 3 ("account for expected errors").
