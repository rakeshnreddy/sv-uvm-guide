## Findings

### S3-1. The AXI write channels are used on the core path without being introduced
- **Where:** `index.mdx:42`, `:192-247`, `:266`; Q2 `:1062-1070`; the debug challenge `:1269-1280`.
- **Problem:** The handshake section uses AWVALID, AWADDR, AWREADY, WVALID, WREADY, BVALID, BREADY, ARVALID, "the W transfer" and "the B transfer". Only AWVALID ("write-address VALID") and BVALID ("the write response") get a gloss. The section never says that an AXI write uses three independent channels, AW (address), W (data) and B (response), each with its own VALID/READY pair. That point first appears inside Q2's feedback ("The AW and W channels handshake independently"). The manifest prerequisites are only I-UVM-3A and I-UVM-2B, and `:42` says "Everything else is defined below". A learner who takes this elective without the AMBA track meets the TimingDiagrams and the debug challenge without the channel model they rest on.
- **Fix:** Before `:192`, add two sentences: "An AXI write uses three channels, each with its own VALID/READY pair: AW carries the address (AWADDR, AWVALID, AWREADY), W the data (WDATA, WVALID, WREADY), and B the slave's response (BRESP, BVALID, BREADY), which the slave sends after both the address and the data have transferred. Reads use AR and R the same way." At `:42`, add "Recommended: [B-AXI-1](/curriculum/T3_Advanced/B-AXI-1_AXI_Channel_Architecture/index) for the full channel rules."
- **Source checked:** IHI0022E §A3.2.1 and §A3.3.1 (the B response follows both the AW and W handshakes); the manifest prerequisites; the README tone rule ("define jargon before using it"); the analysis "Before you start" recommendation (B-AXI-1).

### S3-2. Why back-to-back VALID stays HIGH in the cocotb driver is never explained
- **Where:** `index.mdx:560-578` (`_handshake`, `write`, `read`), `:641-645`; it is relied on at `:276-286` (push is 1 at edges 3 and 4) and at `:717` ("each of the 14 operations takes one cycle"); checklist `:934`.
- **Problem:** `_handshake` ends with `valid.value = 0`, and the loop immediately calls the next `write`, which sets `valid.value = 1`, with no `await` in between. A junior who has just learned "drop VALID after its handshake" expects VALID to glitch low, or to lose a cycle, between back-to-back pushes. Yet the TimingDiagram shows push HIGH across edges 3 and 4, and the timing derivation counts one cycle per operation. The page never names the rule that makes this work. With default settings, cocotb queues deposits keyed by handle, and "Only the last scheduled write to a particular handle in a timestep is performed" (cocotb v2.1.0 `handle.py`, the `_write_calls` comment). So the 0 is replaced by the 1 before it is ever applied. The checklist item at `:934` ("keep VALID HIGH only because there is more to send") asserts the behaviour without the mechanism.
- **Fix:** After the code block at `:655` (or in "Where the times come from" at `:717`), add: "Back-to-back writes keep `push` HIGH even though `_handshake` writes 0 and the next `write` writes 1: both writes happen in the same Values Change phase, and cocotb applies only the last write to each signal in a time slot (cocotb 2.1 `handle.py`). With `COCOTB_TRUST_INERTIAL_WRITES` (the Verilator default), both go to the simulator as zero-delay inertial writes, and the later one replaces the earlier." Ask the accuracy reviewer to confirm the wording of the trusted-inertial case before it is added. Optionally add the same point to the Words entry for **Deposit** at `:55`.
- **Source checked:** cocotb v2.1.0 `src/cocotb/handle.py` (`_write_calls` dict and `_schedule_write`: `_write_calls.pop(handle, None)` and then reinsert); this page `:105`, `:276-297`, `:717`.

### S3-4. The coroutine mapping lacks the IPC primitives a ported SV agent uses
- **Where:** `index.mdx:150-159` (the SV ↔ cocotb table).
- **Problem:** Item 4 of the concept checklist (syntax and variants the learner will meet) is partial for "coroutines and tasks". The table maps `fork`/`join`, `disable fork` and `wait fork`, but not SystemVerilog events, semaphores and mailboxes (I-SV-5). These are what a practitioner meets when porting a hand-written SV agent or reading cocotbext code. cocotb 2.1 provides all three: `Event` (`set()`, `await e.wait()`), `Lock` (`async with lock:`), and `cocotb.queue.Queue` (`await q.put(x)`, `x = await q.get()`). The table also omits `with_timeout`, the per-call counterpart of a `fork … join_any` timeout race.
- **Fix:** Add four rows:
  - `-> e` / `@e` → `e.set()` / `await e.wait()` (`Event`);
  - `semaphore` `get`/`put` → `async with lock:` (`Lock`);
  - `mailbox` `put`/`get` → `await q.put(x)` / `await q.get()` (`cocotb.queue.Queue`);
  - a timeout race → `await with_timeout(coro, 1, "us")`.

  Link I-SV-5 in the header cell next to F2C. Ask the accuracy reviewer to confirm the `with_timeout` signature in 2.1 before it is added.
- **Source checked:** cocotb v2.1.0 `src/cocotb/triggers.py` `__all__` (it includes `Event`, `Lock` and `with_timeout`); `src/cocotb/queue.py` (`Queue`, `AbstractQueue.put`/`get`, both `async`); plan §1.3 (I-SV-5 owns IPC).
