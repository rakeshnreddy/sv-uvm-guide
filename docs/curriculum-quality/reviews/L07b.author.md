## Requests for the lead

1. **InterfaceSignalFlow model vs §25.9.2.** With the handle type `virtual simple_bus_if` (no modport), the model reports `vif.cb.valid <= 1` as legal. §25.9.2 says dot access to a clocking block through a virtual interface "only works for interfaces with no modports", and `simple_bus_if` declares modports. Many tools accept it, so the rule is tool-dependent in practice. Either:
   - model the standard's rule as a compile error with a tool-dependent note; or
   - add an assumption line to the visual.

   The page directs learners only to the presets, which avoid this case. F4C states the §25.9.2 rule too.
2. **ModportExplorer limits line (optional component text).** "It does not stop two modules on the same master view from both driving" should add: unless a writer is `always_ff` or `always_comb` (§9.2.2.2, §9.2.2.4). It could also say that types and parameters stay visible (§25.10). The page's own debrief already qualifies both.
3. **E2E pin.** `F4_lessons.spec.ts` uses `getByText('Modport Explorer')`, and the page keeps exactly one occurrence, in body text. No spec change is needed, but scoping it to `getByTestId('lesson-content')`, as for F4C, would make it robust.
