## Findings

### F1 (S3) solver-debug.mdx:299: the SequenceDiagram's last step is clipped

- **Problem.** `{ kind: "self", from: "drv", label: "drives req on the pins" }` sits on the last participant. The kit draws self-call text from the lifeline x + 42. The drv lifeline is at x = 20 + 65 + 2·150 = 385, but the viewBox is only 470 wide. The text "8. drives req on the pins" (about 25 monospace characters at 10.5 px, roughly 158 px) runs from 427 to about 585. Everything after "8. dri…" is clipped by the SVG edge. The step is still in the "Steps as text" list, but the drawing loses it.
- **Fix.** Replace it with a note centred on the driver: `{ kind: "note", from: "drv", label: "drives req on the pins" }`. A note's box is lifeline ± 59, so it wraps inside the column. Alternatively, drop the step and add "(driven on the pins)" to the return label on line 298. Do not just widen `columnWidth`, because the last column stays at the right edge.
- **Source checked.** `src/components/visual-system/diagram-layout.ts:243-245` (SEQ_PAD_X 20, SEQ_BOX_W 130), `:297-316` (note and self geometry), `:330` (width); `SequenceDiagram.tsx:114-130` (self text at `x + 42`, prefix added).

### F2 (S3) solver-debug.mdx:212-213: ArchitectureDiagram labels overflow their nodes

- **Problem.** The default node is 150 px wide, and labels render in 11.5 px semibold monospace (about 6.9 px per character):
  - "active: c_len (jumbo_fixed)" has 27 characters (about 186 px). It spills about 18 px past each side of its box and reaches the right edge of the 610-px viewBox.
  - "active: c_len + c_jumbo" has 23 characters (about 159 px). It also crosses its border.

  The kit does not wrap node labels.
- **Fix.** Shorten the labels and move "active" into the title, which already says "Which constraints are active…":
  - setA: label `c_len + c_jumbo`, sublabel `no len fits: returns 0`;
  - setB: label `c_len (replaced)`, sublabel `len 65..255: returns 1`.

  Alternatively, pass `cellWidth={200}`, at the cost of a smaller scale on phones.
- **Source checked.** `diagram-layout.ts:96-99` (cellW 150, gapX 64, OUTER_MARGIN 16 at `:71`); `BlockDiagram.tsx:290-302` (centred label at `text-[11.5px]`, sublabel at `text-[9.5px]`).

### F5 (S4) solver-debug.mdx:261-270: the size-first failure has only a prose trace

- **Problem.** The function-order case gets a two-stage table (lines 256-259). The size-first case, which has the same shape, is explained only in prose.
- **Fix.** Add a matching two-row stage table:
  - Stage 1: `len` is chosen from 1..10, each value with probability 1/10, ignoring `foreach`.
  - Stage 2: `d[i] == i * 30` holds for `len` ≤ 9; for `len = 10`, `d[9] == 270` cannot fit in 8 bits, so `randomize()` returns 0.
- **Lead note.** The model already computes size-first failure rates (`tests/lib/constraint-solver-model.test.ts`, "§18.5.7.1 … element constraints that cannot hold for the chosen size make randomize() fail", `failureProbability` 2/6). The optional model-backed scenario the author requested (lead request 4) therefore needs only a component scenario, not new model work.
- **Source checked.** Page lines 256-270; `tests/lib/constraint-solver-model.test.ts` §18.5.7.1 block.
