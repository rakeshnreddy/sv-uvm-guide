## Code traced by hand

No simulator is available (plan §6). I traced each block myself against §9.3.2, §9.7, §15.3 and §15.4, independently of the author's scheduler model.

- **Make It Work (working).** Lines `[1]`, `[5]`, `[7]`, `[9]`, `[13]`, `[15] … reply 110` and `[15] PASS=2 FAIL=0` match the page. Same-time line pairs are causally ordered. `req_mbx` (bound 2) never fills, and `rsp == 10*id + 100` holds for both requesters.
- **Break it.** At 1 ns requester 0 takes the key. The responder takes request 0 and blocks in `bus.get`. From 5 ns requester 0 waits in `rsp_mbx[0].get` while it holds the key. Requester 1 queues at 9 ns. At 100 ns the watchdog prints the bus owner and three WAITING lines with the `doing[]` strings shown, kills all three, and `main` prints `[100] PASS=0 FAIL=1`. The status table and the wait-for graph match.
- **Quiz Q3 variant (both requesters at 1 ns).** I traced the key-queue order "r0 before the responder": the run passes at 13 ns, so it agrees with the key ("either one", and both pass).
- **Kata.** The starter deadlocks at 4 ns with nothing printed. The collector fix prints replies at 2, 4, 6 and 8 ns, then `[8] PASS=4 FAIL=0`. The capacity claim holds: with `new(1)` a burst of 3 passes and 4 deadlocks; with `new(2)` a burst of 5 passes and 6 deadlocks.
- **Lab, starter.** Part 1 prints sends at 30 and 65 ns, reads at 45 and 80 ns, and the drop at 100 ns. From 110 ns the sender (item 3) is blocked, and the receiver (read 2) has been blocked since 95 ns. The holder is `sender (item 2)`. The report comes at 300 ns, and without the watchdogs the last activity is at 110 ns (§9.6.1). Part 2 starts at 300 ns: the mover holds A and waits for B (302 ns), the auditor holds B and waits for A (303 ns), and the report comes at 400 ns with the holder lines in r-order. The run ends `PASS=0 FAIL=2` and calls `$fatal`. All of this matches the README.
- **Lab, one fix.** Part 1 passes at 185 ns (sends 0, 1, 3, 4; five reads). Part 2 deadlocks at 187–188 ns and reports at 285 ns. This matches the README.
- **Lab, both fixes.** Part 2 lines at 189, 193, 199, 203, 209 and 213 ns, then `[217] PART 2 PASS` and `[217] PASS=2 FAIL=0`. This matches the README. The checks are sound: two keys on either table cause a collision, so check 2 fails; a retry loop that keeps the first key times out, so check 1 fails; `keys_back()` catches a missing key and a surplus key.
- **Syntax by inspection.** The following are all legal:
  - `process::state s; … s.name()`;
  - `foreach (worker[i]) wait (worker[i] != null)`, which is the §9.7 `do_n_way` idiom;
  - an output formal passed to `get(ref …)` inside `fork … join_any` (§9.3.2 forbids only `ref` formals there);
  - `#(budget_ns);` as a fork branch;
  - `bit finished = 0;` in an automatic task;
  - a module-level `string res_name[3] = '{…}`;
  - `return` in a task;
  - `try_get` and `put` called from functions.

  Every name used is declared. The solution's `if/else` plus a single `give_key(BUS)` is correct.

| S4 | `index.mdx:356` | "Each returned key lets a waiting `get()` proceed (§15.3.2), so the poller finds a key free only if it happens to look while nobody is queued." The standard says only that a waiting process "shall execute if enough keys have been returned". It does not say that the key is reserved for that waiter, so it does not rule out a `try_get()` in the same time slot (between the `put()` and the waiter resuming) winning the key. "Only if" is stronger than the clause. This is the same kind of over-reading that the author already reworded at two other places. | Soften it: "…so a returned key usually goes to a queued `get()` first, and the poller tends to lose.
