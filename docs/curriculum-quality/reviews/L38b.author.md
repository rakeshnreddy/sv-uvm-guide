### The S2: `WRONG_RID` (accuracy finding 1)

The reviewer was right. The responder popped the wrong-RID read, but the monitor kept it at the head of `open_q[ID]`, so the next read with that ID was misattributed. The documented `SCB_PENDING`, `[EOT] 39 of 40` and `pending=1` needed no later read with that ID, which is about 0.02% of seeds. Of the two fixes offered, I took (b), which makes the documented log true. The mutant exists to show end-of-test accounting, and a cascade would hide that.

- **Code (page and `testbench.sv`, identical).** `rd_req_t` gains `bit bad_rid`, and the responder counts `n_accepted` in `accept_ar()`. `inject_wrong_rid(cur)` runs in `next_beat` before the head is read. It marks `pend[cur][0].bad_rid` only when `n_accepted == cfg.n_reads` (the last AR has been accepted), `pend[cur].size() == 1` and `sent == 0`. Every beat of that read then drives `RID = cur ^ 8`. A single-beat requirement would have left the mutant unfired in about 59% of runs, so the length condition is gone.
- **Why it always fires.** The last accepted read Z becomes the only read of its ID with `sent == 0`, and the test waits for every read (`n_pending == 0`, or the 2,000-cycle timeout). So Z, or an earlier last-of-its-ID read, qualifies before the run ends.
- **Trace.** Each beat of the chosen read V raises `UNEXPECTED_R`, and `on_r_valid` returns silently. V stays in `open_q[ID]`, but no later read has that ID. The checker's counters stay balanced, because V's AR and RLAST are both counted, and the master's `outstanding` count is not affected. The test then times out and warns `[EOT] 1 read(s) still open after 2000 cycles`. In `check_phase`, bottom-up, the scoreboard reports `SCB_PENDING` and then the test reports `[EOT] 39 of 40 reads compared`. The run ends with `SCB_SUMMARY matches=39 mismatches=0 pending=1`. The expected log now adds "one `UNEXPECTED_R` for each beat".
- **Teaching.** A paragraph under the mutant table explains why the mutant is timed this way and shows the cascade it avoids. A new debugging row reads: one `UNEXPECTED_R`, then `SCB_MISMATCH`/`RLAST` on later reads of one ID, so debug the first error. Card 15 tests the same cascade. The README's step 4 explains it too.
