## Findings

### S3-1: Family 3 diagram marks the legal DUT as faulty
- **Where:** `hang-lab.mdx:125` (node `dut`, `state: "error"`).
- **Problem:** the drawing gives the DUT the same error state as the driver. But the page says the DUT is legal and the driver owns the deadlock (lines 209 and 820, quiz Q3 feedback: "The DUT's behaviour is legal for a receiver"). The picture works against the lesson's main point, "fix the owner": a learner reading only the diagram sees two culprits.
- **Fix:** remove `state: "error"` from `dut` (or use `state: "active"`) and keep `drv` as `error`. Optionally change the DUT sublabel to `"waits in_valid (legal)"`.
- **Source:** Arm IHI0022E §A3.3.1 as cited on the page; page lines 209 and 820.

### S3-2: the bench diagram cannot show the evidence for hang 3
- **Where:** `hang-lab.mdx:366–373` (bench `edges`).
- **Problem:** the drawing shows only `drv → dut (in_valid, in_data)` and `dut → out_mon`. Two connections are missing:
  - `in_ready` coming back to the driver, which is the signal that `+HANG=3` waits on (line 494);
  - the input monitor `mon` sampling `in_valid`, `in_ready` and `in_data` (lines 520–522).

  The hang 3 solution relies on both: "scb never received even an expected beat … nothing was ever accepted at the DUT's input". Without them, a learner cannot trace on the picture why `exp_fifo` stays empty. The rule that a diagram matches the code's connections and directions is only partly met.
- **Fix:** add `{ from: "dut", to: "drv", style: "data", label: "in_ready" }` (a `via` may be needed to keep it apart from the existing `drv → dut` edge) and `{ from: "dut", to: "mon", style: "data", label: "in_valid, in_ready, in_data (sampled)" }`. Re-run the kit layout to confirm there are no overlaps.
- **Source:** bench code, lines 386–392, 494–498 and 518–525.

### S4-1: the sequencer's `seq_item_export` is an imp, not an export
- **Where:** `hang-lab.mdx:360`, `kind: "export"`.
- **Fix:** use `kind: "imp"`. uvm-core declares `uvm_seq_item_pull_imp #(REQ, RSP, this_type) seq_item_export;`.
- **Source:** uvm-core 2020.3.1 `src/seq/uvm_sequencer.svh:93`.

### S4-2: the missing connection is drawn like a real one
- **Where:** `hang-lab.mdx:114` (`fifo → mon.ap`, label "no connection") and `:369`.
- **Problem:** `GridEdge` has no `state` field, so the missing connection draws as an ordinary dashed causal arrow, and only its label says otherwise.
- **Fix:** make the label stronger, for example "NOT connected (ap.size() = 0)". Optionally, ask the lead to expose `state` on `GridEdge` (the primitive's `DiagramEdge` already supports `error` and `dim`).
- **Source:** `diagram-layout.ts:38–47`, `BlockDiagram.tsx:76–88`.

### S4-3: deadlock waveform markers are tied to single edges
- **Where:** `hang-lab.mdx:238–241`.
- **Problem:** the markers put "driver waiting" at edge 1 and "DUT waiting" at edge 3, but both conditions hold at every edge.
- **Fix:** use one `highlights` span over edges 0–5 (or one marker), so the picture doesn't suggest the two waits happen at different times.
- **Source:** bench lines 491–495; DUT line 411.

### S4-4: the zero-activity section has no picture or pointer
- **Where:** `hang-lab.mdx:295–299`.
- **Problem:** objective 4 has no picture in its own section. The drill's "The test passes in 0 ns" scenario covers it, with a prediction and a debrief.
- **Fix:** add one sentence: "You will see this run in the drill below (scenario 4: The test passes in 0 ns)."
- **Source:** README §Visuals ("every core concept has a picture"); `uvm-hang-model.ts:581`.

### S4-5: the hand-written prerequisites differ from the manifest
- **Where:** `hang-lab.mdx:1053`.
- **Problem:** the line lists I-UVM-1C and the I-UVM-3B handshake. `<BeforeYouStart />` shows the manifest list: I-UVM-6, I-UVM-1C and A-UVM-6. The convention is common (about 80 pages), so this is minor.
- **Fix:** rename the line to "Background for this page", or align it with the manifest.
- **Source:** `content/curriculum/curriculum.manifest.json` (E-DBG-1 prerequisites).

### S4-6: the heartbeat diagram shows a different case from the prediction it follows
- **Where:** `hang-lab.mdx:270–291` (prediction prompt, `SequenceDiagram`, debrief).
- **Problem:** the prompt asks about a scoreboard that *never* compares (answer: `HBFAIL` at trigger 2, 200 ns). The diagram that comes straight after shows a scoreboard that beats once in window 1 and then stops, so `HBFAIL` comes at trigger 3. A learner who checks the prediction against the picture may read "trigger 3, 300 ns". The diagram also matches neither bench case: in `+HANG=2` and `+HANG=3` the scoreboard never beats.
- **Fix:** either remove the window-1 beat so the diagram shows the predicted case (trigger 2 reports `HBFAIL`), or add one sentence to the caption: "This shows a component that beat once and then stalled; for one that never beats, trigger 2 already reports."
- **Source:** page lines 270, 274 and 291; uvm-core 2020.3.1 `uvm_heartbeat.svh` (the first trigger only opens a window).
