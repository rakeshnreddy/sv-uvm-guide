| 1 | **S2** | soc-ral-firmware-prediction (rubric and model answer, point 1) | The answer says "Two separate model facts explain it", and the first is that `get()` returns the desired value while `get_mirrored_value()` returns the model's belief about the DUT. The rubric makes this the first thing a strong answer must say. In this scenario it explains nothing. The standard says "Unless set to a different value using uvm_reg::set, the desired value and the mirrored value are identical" (§18.4.4.1). `predict()` "updates the mirrored and desired value" (§18.4.4.15), and uvm-core's `do_predict` writes `m_desired` and `m_mirrored` together. So without a predictor, `get_mirrored_value()` also returns 0x0. With an explicit predictor, `get()` also returns 0x1. The key rewards a non-causal reason, and a candidate who "fixes" the test by switching to `get_mirrored_value()` still sees 0x0. | Make missing prediction the single cause: nothing updated the model when firmware wrote, because auto-predict covers only model-initiated accesses (§18.2.5.2). Demote the get/get_mirrored_value point to a side note, for example: "`get()` returns the desired value; unless `set()` was called it equals the mirror (§18.4.4.1), and prediction updates both (§18.4.4.15), so switching to `get_mirrored_value()` alone would still show 0x0. Prefer `get_mirrored_value()` when checking the DUT, because `set()` can make the two differ." Update the rubric to match, and add a common mistake: "Thinking `get_mirrored_value()` would have shown 0x1 without a predictor." | 1800.2-2020 §18.4.4.1, §18.4.4.15, §18.2.5.2; uvm-core `uvm_reg_field.svh` `do_predict` (`m_mirrored = field_val; m_desired = field_val;`) |
