## Findings

### A-1 (S3) Loop detection claim for uvm-core is not borne out by the source

- **Where:** `index.mdx:700`, "(§8.3.1.5; uvm-core reports `OVRDLOOP`)".
- **Problem:** The standard part is right (§8.3.1.5: a loop is an error, and the class that formed the loop is returned). The uvm-core claim is not. In 2020.3.1, `OVRDLOOP` is checked only against the `override_info` queue that is passed to `m_find_override_by_type`. The public `find_override_by_type` creates a new, empty local queue on every call (`uvm_factory.svh`, `find_override_by_type`: `uvm_factory_override override_info[$]; return m_find_override_by_type(...)`). `m_find_override_by_type` follows a chain by calling that public method again (`override = find_override_by_type(override, full_inst_path);`). So a type-based loop such as `A→B` with `B→A` is never matched against earlier entries. By inspection, it recurses without bound until the simulator fails, and it never prints `OVRDLOOP`. The by-name path also reaches the by-type recursion. No simulator was available, so this was confirmed by reading the code only.
- **Fix:** Drop "uvm-core reports `OVRDLOOP`". Write instead: "The standard requires an error (§8.3.1.5). In uvm-core 2020.3.1, each step of the chain starts a fresh history, so a loop of type overrides may recurse until the simulator fails instead of printing `OVRDLOOP`: never register one." Alternatively, keep only the standard's statement.
- **Source:** uvm-core 2020.3.1 `src/base/uvm_factory.svh`, `find_override_by_type` and `m_find_override_by_type` (the `OVRDLOOP` check and the recursive call); IEEE 1800.2-2020 §8.3.1.5.

### A-2 (S3) "Only two forms take a relative path" leaves out `uvm_component::set_inst_override`

- **Where:** `index.mdx:794` (quiz Q5 `explanation`) and `content/flashcards/I-UVM-4_Factory_and_Overrides.json:15` (`uvm4-instance`: "Only that shortcut with a parent argument and `uvm_component::set_inst_override_by_type(…)` are relative").
- **Problem:** The `uvm_component` by-name method `set_inst_override(string relative_inst_path, string original_type_name, string override_type_name)` is also relative to the calling component. It registers `{get_full_name(), ".", relative_inst_path}` (D.2.1.6). The page itself shows this signature at :213. The "only" statement is therefore false, and it contradicts the page.
- **Fix:** Q5 explanation: "Relative paths are taken by the type_id shortcut with a parent argument and by the uvm_component methods set_inst_override_by_type(relative_path, orig, ovr) and set_inst_override(relative_path, orig_name, ovr_name). The factory's own methods and the command line take absolute paths." Make the same change in the `uvm4-instance` answer, for example "…and `uvm_component`'s `set_inst_override_by_type` / by-name `set_inst_override` are relative…".
- **Source:** IEEE 1800.2-2020 D.2.1.4, D.2.1.6; uvm-core `uvm_component.svh:1139-1141, :1184-1186`.

### A-3 (S4) The object macro does more than change the constructor call

- **Where:** `index.mdx:95`, "The two macros differ only in how the proxy calls the constructor".
- **Problem:** `` `uvm_object_utils(T) `` also declares a virtual `create(string name = "")` method (`m_uvm_object_create_func`). `uvm_object::clone()` relies on that method, and the kata uses `clone()`. B.2.1.2 lists "Implement create" for objects. The component registry has no such member.
- **Fix:** "The two macros differ mainly in how the proxy calls the constructor (the object macro also adds a `create()` method, which `clone()` uses), which is why the constructors differ:".
- **Source:** uvm-core `uvm_object_defines.svh:311-314` versus `:417-419`; IEEE 1800.2-2020 B.2.1.2.

### A-4 (S4) The expected log begins at `RNTST` with no elision mark

- **Where:** `index.mdx:609` (and :906 in the kata).
- **Problem:** Unless `+UVM_NO_RELNOTES` is given, uvm-core prints the `UVM/RELNOTES` banner (`uvm_root::report_header`) before `RNTST`. Both logs are labelled illustrative, and other elisions are marked with `...`, so this is only a consistency nit.
- **Fix:** Add a `...` line above the `RNTST` line in both logs, or say "after the UVM banner" in the label sentence at :606.
- **Source:** uvm-core `uvm_root.svh:439-476`.
