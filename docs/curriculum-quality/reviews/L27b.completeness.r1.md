## Findings

### S3

1. **S3 explicit-vs-implicit.mdx:936, :948, :992, :1002, :1013, :1024 - the key is the longest option, by far, in 6 of 9 questions, and sits in position 2 in 6 of 9 (never position 4).** Measured option lengths: Q2 key 159 characters vs distractors 44-66; Q6 108 vs 24-32; Q7 167 vs 55-70; Q8 144 vs 29-67; Q9 125 vs 23-53; Q1 87 vs 45-62. `Quiz.tsx` does not shuffle answers, so a test-wise learner can score most of the quiz without the concept (spine §5.5: "the answer must not be guessable"). **Fix:** move the "why" and the remedy out of the keys into their `feedback` (for example Q8 key: "A RegModel mismatch error on BUSY"; Q9 key: "0"; Q7 key: "Either 0 or 1, depending on which prediction comes last"; Q2 key: "Wrong term, and predict() skips the field policies"), lengthen one or two distractors to match, and spread the keys across positions 1-4. Source: spine §5.5; `src/components/ui/Quiz.tsx` (no shuffle).

2. **S3 explicit-vs-implicit.mdx:1039 (with :346, :260, :266, :752) - Kata 1's worked solution gives the wrong reason for step 4, and the page describes step 4 inconsistently.** The solution says "Step 4 reports nothing because ERR is volatile", but step 4 of the bench never calls `mirror(UVM_CHECK)`: it calls `env.ral.int_status.read(st, rd)` (L752), and with check-on-read off a `read()` checks nothing, volatile or not. L346 also says the test checks the mirror "after each [change] with `mirror(UVM_CHECK)`", and the traced table (L260 "as in the Make It Work example") uses `ral.int_status.mirror(st, UVM_CHECK)` at step 2, which the bench does not do. A junior who compares the three will learn the wrong reason for "no error". **Fix (either):** (a) make step 4 call `check_reg(env.ral.int_status, "4 after MODE=3")` instead of the first `read()`, so volatility is what prevents the error, matching L266 and the kata (update the Expected output lines 799-800 and the table row at L818); or (b) keep the code and change L346 to "checks steps 1-3 with `mirror(UVM_CHECK)` and step 4 with a plain `read()`", L1039 to "Step 4 reports nothing because it uses `read()`, which checks nothing while check-on-read is off; ERR's volatility would also keep a `mirror(UVM_CHECK)` quiet", and L260 to "a variant of the Make It Work example". Source: page code L749-757; uvm-core `uvm_reg::do_read` (check only inside the auto-predict branch when check-on-read is on), `uvm_reg::mirror`.

3. **S3 explicit-vs-implicit.mdx:811-819, :1034 - Kata 1 asks the learner to predict a table they have already read.** The per-mode result table is printed in full in Make It Work, with no predict-first prompt, and the kata then says "cover it and predict". The page's own visuals follow introduce → predict → debrief; this one only reveals. **Fix:** in Make It Work, put a one-line prompt before the table ("Before reading on, predict which steps fail under each `+PRED` value: Kata 1") and wrap the table and the "Read the table by column" paragraph in a `<details>` ("Show the results for all four set-ups"), or move the table into Kata 1's solution and leave only the `EXPLICIT` column visible. Source: README §Visuals (predict, then debrief); spine §5.8.

4. **S3 explicit-vs-implicit.mdx:208-224 - passive prediction and check-on-read is the one core concept (objective 5, and a third set-up in objective 1) with no picture of its own and no worked example or trace.** The architecture diagram shows an active agent driven by the register model; the predictor SequenceDiagram shows check-on-read as one self-step. The full passive run is reasonably deferred (needs a second initiator), but a cheap trace is not. **Fix:** add a short traced table under "Passive prediction and check-on-read": firmware writes CTRL `'h5` (predictor: mirror 5); hardware sets STATUS.BUSY; firmware reads STATUS with BUSY `volatile = 0` (compare before predict → `RegModel` error; mirror then 1) vs `volatile = 1` (no compare on BUSY; mirror 1); firmware reads CTRL (compare passes). Optionally add one sentence to the ArchitectureDiagram caption: "A passive set-up is this picture without `sqr` and `drv`: the monitor path is the only path." Source: README completeness checklist items 5 and 6; plan.md §1.2 (a picture for every core concept); §18.2.5.3; `uvm_reg_predictor.svh` `write`.
