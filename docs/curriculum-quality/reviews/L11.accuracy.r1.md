## Findings

### S2-1. A `randc` use case promises a sliding-window guarantee it does not give

- **File:** index.mdx:146
- **Text:** "Use it when one object must visit every value before repeating, such as a 4-bit tag that must not collide with any of the last 15 tags."
- **Problem:** `randc` guarantees no repeat *within* one permutation. After the last value of a permutation, a new one is computed, and its first value may equal the value just returned. The page's own table shows it: calls 4 and 5 both return 1, and :170 says "A cycle guarantees no repeat inside it, not across cycles". So a tag can collide with the *previous* tag, not only with one 15 calls back. The cycle also restarts whenever the constraints on the variable change. A learner who follows this sentence for outstanding-transaction IDs, such as AXI IDs, builds a testbench that reuses an ID still in flight. Because this false guarantee sits in the definition paragraph, it is S2, not S3.
- **Fix:** "Use it when one object must visit every value before any value repeats within a cycle, such as cycling through all 16 values of a 4-bit tag. It is not a sliding window: the next cycle may start with the value the last one ended on, so tags that must not collide with ones still in flight need an explicit allocator." The kata's `id` rule (:755, "no repeat until all 16 values were used") is already worded correctly.
- **Source:** IEEE 1800-2023 §18.4.2 ("After it returns the last element of a permutation, it repeats the process by computing a new random permutation"; "no value is repeated within an iteration"; recompute "whenever the constraints change on that variable").

### S4-1. The macro citation names the wrong file for the `_with` macros

- **File:** index.mdx:590 and :868
- **Problem:** The page names `` `uvm_rand_send_with `` and `` `uvm_do_with `` and cites `src/macros/uvm_sequence_defines.svh`. In uvm-core 2020.3.1 both are deprecated wrappers in `src/deprecated/macros/uvm_sequence_defines.svh` (:69-70, :196-197). That file still gets included by `uvm_macros.svh:95`. The 1800.2-2020 forms are `` `uvm_do(item, , , {…}) `` and `` `uvm_rand_send(item, -1, {…}) ``. The behaviour the page describes is correct, because the wrappers expand to those macros.
- **Fix:** Cite both files. Or name `` `uvm_rand_send(item, -1, {…}) `` / `` `uvm_do(item, , , {…}) `` as the current forms, and mark the `_with` names as deprecated aliases.
- **Source:** uvm-core 2020.3.1 sources listed above.

### S4-2. "Order does not matter" holds only for hard constraints

- **File:** index.mdx:73; constraint-blocks.mdx:37
- **Text:** "All enabled blocks hold at the same time; their order in the class does not matter" / "whatever their order in the class".
- **Problem:** This is true for hard constraints. For soft constraints, declaration order sets priority, and the pages teach that later on (index :280; constraint-blocks :154-155).
- **Fix:** Add "(for hard constraints; soft constraints are ranked by order, see soft below)".
- **Source:** §18.5.13.1, first and second rules.

### S4-3. A size constraint does not straightforwardly allow "negative n"

- **File:** index.mdx:393
- **Text:** "`rand int n; data.size() == n;` allows huge or negative `n` values"
- **Problem:** A size cannot be negative, so `data.size() == n` with a negative `n` has no satisfying array. What a simulator does there (exclude the value, or report a size error) is not specified in Clause 18. The real hazard is the huge positive sizes, which the page states correctly at constraint-blocks.mdx:130.
- **Fix:** "allows enormous sizes, and a signed type adds negative values that a tool may reject with a size error (tool-dependent)". Or drop "or negative".
- **Source:** §18.4 (size constraint semantics); no LRM rule on negative sizes found.

### S4-4. The UVM macro limits need one more sentence

- **File:** index.mdx:595
- **Text:** "UVM's report-severity overrides can raise the RNDFLD warning to an error"
- **Problem:** This is correct. But `RNDFLD` is reported from inside the sequence, through its sequencer's report handler, so a per-component override must target the sequencer. A learner who sets it on the test will see no effect.
- **Fix:** Add "(set it on the sequencer, or use `+uvm_set_severity=*,RNDFLD,UVM_WARNING,UVM_ERROR`)". Optional polish.
- **Source:** uvm-core 2020.3.1 `uvm_sequence_item` report methods (they delegate to the sequencer's reporter); I-UVM-1D page.
